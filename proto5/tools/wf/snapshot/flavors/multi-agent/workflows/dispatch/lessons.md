# 派線踩過的坑

[dispatch](README.md)｜[WORKFLOWS](../../WORKFLOWS.md)

四條都是實跑之後才長出來的，寫在這裡是為了**下一份交接書送出前對一次**。

## 1. 派線前的預掃要涵蓋全部組別

不能只掃「已知的那幾組」。預掃做得好可以砍掉大半工作量——逐件比對「預期檔名＋預期大小」這種便宜檢查，常常讓一條線的實際工作量掉一個數量級。

但**漏掃的那組會在收線時才爆出來**：派線當下還查不出識別碼的那一組被跳過，結果「其實早就有了」是收線核驗時才發現的。**那是預掃範圍的缺口，不是線的錯。**

**交接書要嘛把預掃做完，要嘛明寫哪幾組沒掃過。**

## 2. 線推翻交接書時要接受，不要逼它湊數

實跑後線回報「交接書寫的三個其實只有兩個，理由是……」，或「照字面搬檔會觸發整批重算，成本比預期高一個量級」——這種通常是**線對、交接書錯**。它手上有你寫交接書時沒有的實測資料。

**驗收條數寫死是為了防它亂加驗證，不是要它為了湊滿數字造假失敗案例。** 收到這種回報就改交接書，別叫它再跑一次去「補齊」。

## 3. 交接書的「背景」與「工作步驟」自相矛盾就會出事

實例：背景寫「可以直接原樣複製過去」，步驟卻寫「佈局零改動」，而實際資料有一半不符合那個佈局假設。線只好二選一，選錯就整批白做。

**送出前對照一次背景與步驟，衝突處要寫死哪個為準。**（[TEMPLATE.handoff](../TEMPLATE.handoff.md) 檔尾有這條提醒。）

## 4. 整檔改寫用單一 Update 操作，不要拆成 Delete＋Add

有些 agent 工具的 patch 機制會**拒絕**「同一路徑同時 Delete＋Add」的原子 patch。線收到拒絕後會很自然地繞路，拆成兩份獨立 patch 送出：先刪、再加。中間**該檔在工作樹上真的不存在**——實測有過二十幾秒的空窗，被另一條線掃到並回報成疑似違規刪除。

後果不只是誤報：那段空窗內線若崩潰，工作區的主入口就缺檔。檔案雖然救得回來，線仍會留下壞掉的工作樹。

這**不是線的惡意**，是工具拒絕之後的自然繞路，所以下一條線還會這樣做。禁止 `rm` 防的是 shell 的 `rm`，這一類操作會從旁邊溜過去。兩條防呆：

1. **整檔改寫一律用單一 Update 操作**（一次完成、原子）。
2. **每個批次邊界跑 `git status --short | grep -E '^(D |.D)'`，要零命中。** 成本近乎零，上面那次就是這道檢查抓到的。
