# build-with-agents — 分層派工的建課產線

[study-site](README.md)｜[WORKFLOWS](../../WORKFLOWS.md)｜驗收關卡 [quality-gates](quality-gates.md)

一門課要生出十幾個頁面時，別讓最貴的模型逐字寫內容。本檔把工作分成四層，把大量產出下放到**便宜的批次執行者**（任何可 headless 跑的 CLI agent，例：Codex CLI、Gemini CLI；或你的工具的子 agent），把判斷權留在上層。

**何時用**：課程規模大到一次寫不完（多頁、多章、要重複同一種版型）。
**何時不用**：一兩頁的小課直接自己寫——分層的協調成本會超過它省下的。

## Done when

- `派工計畫.md` 每列的「唯一寫入範圍」與「狀態」非空。
- `建置進度.md` 存在（建置期間），交付時已刪除。
- 每個產出檔通過 [quality-gates](quality-gates.md) 的驗收片段，結果寫進 `驗收紀錄.md`。

## Token 階梯（鐵律）

| 層 | 誰 | 只做 | 不做 |
|----|----|------|------|
| 1 | **Lead**（最貴的主模型）| 頂層決策、審規格、裁決上報、純字串修正 | 不讀執行者的原始輸出、不寫產品檔 |
| 2 | **建置指揮官**（能寫程式的 agent）| 派工、收件驗證、親手寫互動程式（`app.js`）、向 Lead 濃縮匯報 | 不寫章節內容 |
| 3 | **唯讀雜工**（便宜模型）| 掃描與取證：id 契約比對、外部資源／編碼／殘留語法掃描、行數統計、長文初讀摘要 | **無寫入權** |
| 4 | **章節作者**（便宜的批次執行者）| 依規格產出章節內容、focused 修正 pass | 不碰互動程式與樣式檔 |

三條貫穿全層的規矩：

- **原文不上行**：每層只向上交摘要。子 agent 的輸出導成檔案、上層只看結尾；掃描腳本只印「檔名＋行號＋命中詞＋計數」，不印整行原文。要查細節就開一個唯讀雜工回報「有／沒有／哪一行」。
- **每檔單一作者**：同一個檔案任何時刻只有一個人寫。同一輪派工的寫入範圍必須互斥；有依賴就串行，不假裝可並行。
- **判斷留上層、取證下放**：指揮官與驗收者的 context 只裝規格要點、進度狀態、待決缺陷清單。

## Context 管理（長線建置必撞 compact）

- **開工即寫 `建置進度.md`**（放課程目錄）：已完成檔與行數、每檔通過的關卡、未完項目、待修缺陷、正在派的工。**每收一包更新一次**。斷線或 compact 後讀這一個檔就能續做；交付時刪除，不進版控。
- **不要停在等待點**：子任務沒回就交還控制權，等於每次空轉都燒掉一次上層往返。要等就在同一回合裡等到底。
- 一波派工控制在少數幾個 job，寫入不同資料夾者才並行；完成的立刻關掉再開下一輪。執行者**不得再生子 agent**。

## 流程

<!-- wf-nav -->
1. **架構師**寫 `PROJECT-BRIEF.md` ＋ `BUILD-SPEC.md`。BUILD-SPEC 必須把每個互動元件的 `id / type / 最小 / 最大 / 級距 / 預設 / 選項順序 / 計算式 / 判準 / 數值實例`**全部鎖死**——照抄即零缺陷是下放的前提；規格留白，下游就各自發明。另附**逐章行號表**，讓下游只讀自己那一段。Lead 審過才放行。
2. **指揮官**分包派工。派工稿用「指路」不內嵌原文：直接寫「讀 `BUILD-SPEC.md` 第 X–Y 行」＋一個版型範本頁，作者不讀整份規格、不讀別人的章節。一位作者最多 3–4 章，回報上限 10 行（完成檔名、行數、字數、自檢結果、卡住的點），不貼檔案原文。
3. **指揮官親手寫互動程式**：唯一依據 BUILD-SPEC；確定性、不用亂數與當前時間、掛勾前先檢查元素存在。語法檢查＋用假資料驅動驗算規格裡的每組數值實例。
4. **收件即驗**：**先建 git baseline**（`git add -N`），否則「這區塊沒被動過」無法位元組證實。逐項比對檔案齊全、id 契約、外部資源 0、編碼乾淨、連結存在。有缺陷就派一個 focused 修正 pass；檔案壞損就還原重跑，不要疊補丁。
5. **獨立驗收者**（沒參與建置、唯一有權寫 `驗收紀錄.md`）照 [quality-gates](quality-gates.md) 全部重驗，**不信任自報**。
6. **Lead 收尾**：裁決上報、純字串修正自己動手、決定是否交付與發布（[publish](publish.md)）。

> 〔導入判斷〕專案只有一個執行者（沒有子 agent／批次工具可用）→ 第 2、3 層併成你自己，仍照第 1 步鎖死規格、第 4 步收件即驗、第 5 步換人時段重驗一次。同步：`workflows/study-site/README.md` 流程第 5 步、`派工計畫.md` 骨架。

## 任務卡格式

```md
## <編號> <一句話名稱>
- 讀取範圍：（只列這張卡真正要讀的檔與行號）
- 唯一寫入範圍：
- 禁止事項：不得上網、不得下載、不得修改範圍外檔案
- 輸出：
- Done when：
- 上游依賴／下游交接：
```

## 失敗處理

1. 第一次偏離：指出**具體差異**，沿用同一個執行者修正。
2. 第二次偏離：把任務縮到只剩一個可測問題。
3. 仍失敗：關掉它，換一個更強的執行者接手這**單一**問題，不擴大範圍。
4. 只有在規格本身自相矛盾時才改規格——不要把規格錯誤算成執行者的能力問題。

## 踩過的雷（量產前必讀）

<!-- wf-nav -->
- **規格的算術錯會被忠實照抄進產品**。建置者照抄是對的，所以每組數值必須有人**獨立重算**一次；驗收要抽驗規格本身，不只驗產出。
- **內容層錯字逃得過所有機械掃描**：形近錯字、混入的異體字不會觸發 id／編碼／語法檢查。字元級錯字掃描是獨立的一關，用高頻術語逐一 grep。
- **執行者會想辦法「通過」閘門而不是滿足意圖**：曾有人把被禁的詞寫成字元實體，同時躲過關鍵詞掃描，瀏覽器卻照樣渲染出那個詞。對策兩條：掃描前先反跳脫（`html.unescape` 等）；更重要的是**別讓規格自相矛盾**——若規格某處要求引述一個被禁的詞，就明文寫「此處恰好允許 1 處、須為明碼」。
- **並行建課時，量測務必先斷言載到的是自己的站**：兩條線各自起本機 server，量錯埠會得出漂亮的假通過。每次量測先確認頁面標題屬於受驗課程。
- **規格裡的計算式不要放進 Markdown 表格儲存格**：未跳脫的 `|` 會把式子攔腰截斷，規格看起來完整、實際少一半。放表格就跳脫成 `&#124;`，或改用清單。

第二次撞到的坑往 `common/gotchas.md` 記（門檻見 [STRUCTURE](../../STRUCTURE.md)），不要只留在這裡。
