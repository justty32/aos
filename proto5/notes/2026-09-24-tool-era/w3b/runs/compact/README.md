# T-compact `--summarize` 真跑：機械版 vs 模型濃縮（第三波 W3-2）

## 怎麼跑

`python3 proto5/notes/2026-09-24-tool-era/w3b/runs/compact/live.py 5 ~/tmp/w3b-compact/main`（repo 根目錄；LiteLLM `http://localhost:4000/v1` 的 `deepseek-chat`，沒碰 LM Studio／ollama）。
一套 daemon＋kernel；每一次都是**全新的 agent 家**（`init`＋`tools add base`、`info.compact: false` 關掉自動壓縮），機械版與 `--summarize` 交替跑：

1. 用 read 讀 `workspace/long.txt`（40 行）、說幾行 ② 記住「最喜歡的水果是芒果」 ③④⑤ 三段約 300 字的自我介紹
2. `compact --keep-rounds 1 --max-tokens X`（X＝dry-run 往下找「①②兩輪都封存」的最大值，實際 846～1036）；模型版加 `--summarize`
3. 問「剛才 long.txt 幾行？不要再讀檔、不要用工具…不記得就說不記得」→ 問「我最喜歡什麼水果？」

原始結果 [results.jsonl](results.jsonl)（一次一行，含兩題原話）；每次的封存摘要全文在 [digests/](digests/)（`sum-N.mech.txt`＝同一份原文的機械版，拿來對照模型有沒有編東西）。

平均：機械 記憶 850、第一問 2266、0.036 s；summarize 記憶 496、第一問 1983、1.20 s，模型 644＋115 token、1.14 s。
**5 段送模型、5 段都過機械檢查（沒有退回），模型沒出錯。** 5 份模型摘要逐句對過機械版，沒有編出機械摘要裡沒有的事（「六十公里」寫成「60 公里」是照提示改寫的數字）。

- 答對：機械 行數 4/5、水果 5/5；summarize 行數 5/5、水果 5/5。機械那次錯是保守答「不記得」（摘要裡明明有 `read（40 行）`、`回話：檔案 long.txt 共 40 行`），不是亂編——跟第一波 §9 看到的一樣（那次 5/5 都答不記得）。模型版把它寫成白話「結果是 40 行」，模型就敢照著答。**樣本只有 5 對 5，4/5 vs 5/5 不能算顯著。**
- 省 token：壓縮後每一問端點回報的 prompt 少 **283 token**（2266→1983，−12.5%；記憶本身 850→496，−42%）。這個差一直留到下一次壓縮。
- 回本：濃縮一次花 759 token（644 輸入＋115 輸出）。只算 token 數：759÷283≈**2.7，第 3 問起回本**；若輸出 token 照 4 倍輸入價算：（644＋460）÷283≈3.9，第 4 問起回本。端點有 prompt 快取的話，記憶前段本來就便宜，回本要更多問（這版沒量快取）。

最弱兩軸：summarize 的「快」（1 s 級、持鎖）與「LLM 參與」。

## 結論

L 軸從 5 掉到 4，換到的是：**壓縮後每問省 283 prompt token（−12.5%），第 3～4 問回本**；答對率 5/5 vs 4/5 方向一致但樣本太小，不當證據。
所以：**模型版預設關，只留人用的 `--summarize` 旗標**；tick 自動與申請一律不叫模型。記憶長、壓縮後還要聊很多輪的人值得手動跑一次。
