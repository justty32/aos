# 評估軸：ai_core 的九軸 → 這次的工具／團隊評分表

## 1. 先講結論

- `~/repo/ai_core` 裡**找不到「六軸」**，也沒有「九軸縮成六軸」的紀錄（全 repo 搜「六軸／6 軸／six ax」、翻 commit 歷史都沒有）。
- ai_core 的**九軸**是「描述一個函式**怎麼跑**」的 metadata（輸入輸出、生命週期、狀態、資源…），**本來不是打分用的**。
- 真正在講「好壞」的是 ai_core 的**治理原則**（roadmap §3.4）：**LLM 預設不准進來，要證明非它不可、又測得夠穩，才發證書放行。** 使用者這次那句「llm 參與的越少越好」就是這條。
- 所以這份的做法：九軸原文照抄（§2）→ 把使用者的五句對上去（§3）→ 補第六軸「邊界」（**我的提案，等使用者拍**）→ 做成一張每軸 1～5 分的表（§4、§5）。

## 2. 原文

### 2.1 九軸（概念版）

來源：`~/repo/ai_core/workflows/spec/execution_forms/s0-axes.md` 第 5～19 行，逐字：

```
| 軸 | 描述的問題 | 例子 |
|---|---|---|
| **I/O 型態** | 輸入從哪來、輸出往哪去、是否需要執行途中的互動 | 無輸入、stdin、互動式（中途需 stdin）、streaming push、streaming pull |
| **生命週期** | 執行單元從啟動到結束的持續模式 | one-shot、persistent、lazy/warm、detached |
| **跨呼叫狀態** | 單次執行以外是否保有、影響或累積狀態 | stateless、stateful-external、stateful-internal |
| **資源特性** | 對計算資源的消耗或佔用（含時間） | 執行時間、記憶體、CPU、GPU；對應 `--metadata` 的聲明內容 |
| **可中斷性** | 是否可以被暫停、暫停後可否恢復、恢復後副作用為何 | 不可中斷、可暫停（SIGSTOP）、可恢復（checkpoint/restore） |
| **執行保證** | 對系統狀態的承諾，獨立於執行次數或中途失敗 | idempotent、transactional（ACID）、dry-run |
| **組合模式** | 執行單元如何與其他單元構成更大的結構 | fan-out/fan-in、proxy/wrapper、hook/callback、agentic loop |
| **環境模式** | 執行環境是預先存在還是動態建立與銷毀 | 固定環境、ephemeral/JIT |
| **確定性 / 隨機性** | 同輸入是否同輸出；隨機環節（LLM）的認證狀態 | deterministic（預設）、nondeterministic（未認證 / 帶證書）；見 [`axis_spec.md §9`](../axis_spec/README.md) |

> 「確定性 / 隨機性」是繼前八軸之後**新增的第九軸**。前八軸隱含「函式是確定性的」前提，無一能描述
> LLM 這種天生隨機的函式，且此性質無法由任何既有軸隱含——故獨立成軸。它同時承載治理原則的證書
> （見 `roadmap.md §3.4`）。詳見 `axis_spec.md §9` 與 `lib_spec.md §9`。
```

（表裡那個 `axis_spec.md` 連結是 ai_core 裡的相對路徑，在這裡點不到。）

### 2.2 九軸（metadata 欄位版）

來源：`~/repo/ai_core/workflows/common/conventions.md` 第 37 行：

> **九個軸**（`_KNOWN_FIELDS`）：`entries`、`lifecycle`（one_shot/persistent）、`state`（stateless/stateful_external）、`state_dirs`、`resources`、`interruptible`、`guarantee`（none<idempotent<transactional）、`dry_run`、`nondeterministic`（第九軸：`true`＝未認證隨機 / `{model,test_set,stability}`＝證書）。

### 2.3 演變：只有增加與收斂，沒有縮成六軸

- 八→九：第九軸「確定性／隨機性」是後來**加的**（`axis_spec/s9-nondeterminism.md` 第 3～4 行：「`execution_forms.md §0` 原本只列了八軸。本節是後續**新增**的第九軸。」）。
- 第 7、8 軸（組合、環境）規範裡寫「此軸不在本規範範圍內，不定義 metadata fields」；C++ 版又把軸 4（state_dirs）移出描述層（commit 45a8d82：「軸 4 純設施不入此層」）。所以**真正寫欄位的只剩六～七軸**——使用者記得的「可能剩六軸」大概從這裡來。**這是我的推測**，要使用者確認。
- commit 9a86e18「defs 九軸重新思考——對照 review 逐軸收斂（4 改 5 守）」：改了 4 軸的內容，軸數沒變。

### 2.4 真正講好壞的：治理原則

`~/repo/ai_core/workflows/roadmap/s3-endgame-governance.md` 節錄原文：

> §3.1　在成熟系統裡，系統大部分是確定性程式碼，**LLM 只剩兩個介面**：1. **意圖翻譯層**：人類的模糊意圖 → 程式可理解的結構化意圖。2. **模糊前沿的暫時處理者**：還沒被固化成程式碼的模糊地帶，暫由 LLM 扛著。

> §3.4　**舉證責任在「讓 LLM 進來」那邊。** LLM 預設零領地；要佔據某個環節，得通過**兩部分閘門**：1. **必要性**：千錘百鍊證明**確定性程式碼辦不到**、非 LLM 不可。2. **穩定性**：在測試組下**做得夠穩**，過可靠度門檻。

§3.2 有一句很好用的比喻：**LLM 是一個巨大 `switch` 的 `default:` 分支**——請求先過確定性的前濾網，命中就走程式，只有落穿的才交給模型。[workflows-as-team.md](workflows-as-team.md) 的「門房」就是照這句做。
§3.6 的「固化引擎」（把模型老在處理的同一類案例凍成程式分支）列在 [plan.md](plan.md) 第三波。

## 3. 使用者的五句 ↔ 九軸

| 使用者這次的話 | 對到九軸的哪幾軸 | 在 aos 裡看什麼 |
|---|---|---|
| **llm 參與的越少越好** | 第 9 軸 確定性／隨機性＋治理原則 | 問模型幾次（think 批數）、有幾步是模型做的 |
| **工具越穩定越好** | 第 6 軸 執行保證、第 5 軸 可中斷性、第 9 軸 | 同一件事跑 10 次成幾次、錯誤是不是結構化、崩了重跑會不會壞 |
| **資源占用量越少越好** | 第 4 軸 資源特性、第 2 軸 生命週期（常駐或一次性）、第 8 軸 環境模式 | 記憶體、cpu 秒、佔 kernel 幾顆 cpu 多久、**送給模型的 token**（proto2 的教訓：prompt 佔 96% 的 token，其中一半是用不到的工具表） |
| **越快完成越好** | 第 4 軸 資源特性（時間） | 從投話到交件的牆上時間；單支工具的 ms |
| **人類能愈輕鬆理解愈好** | 九軸**沒有**這一軸（新的） | 新手只拿 README 說不說得出它做了什麼；每一步有沒有留下人看得懂的檔或一行 |
| （我的提案）**邊界** | 第 3 軸 跨呼叫狀態、第 6 軸 執行保證、第 8 軸 環境模式 | 碰得到哪些檔、要不要進牢、壞了能不能靠重跑同一行收回來 |

**為什麼補第六軸「邊界」**：這一波很多工具會寫檔、會碰別的 agent。只看前五軸，一支「很快、不叫模型、很穩、但能改掉別人人格」的工具會拿高分，邊界軸把這種扣回來。要不要這一軸是 [README](README.md#要使用者拍的) 第 1 題（預設：要）。

## 4. 評分表：怎麼量、幾分

每軸 1～5，5 最好。**工具**和**團隊**量法不同的地方分開寫。量不到就寫「?」，不要猜。

### 軸 1　LLM 參與（越少越好）

| 分 | 工具 | 團隊（完成一件事） |
|---|---|---|
| 5 | 不叫模型 | 只有入口翻譯那一次（或 0 次：前濾網全命中） |
| 4 | 可選叫模型，預設不叫 | 每件 ≤ 3 次，而且每次都在「非它不可」的步驟 |
| 3 | 叫一次，結果有機械檢查兜底 | 每件 ≤ 10 次 |
| 2 | 叫好幾次 | 機械步驟（搬檔、跑 lint、改狀態表）也讓模型做 |
| 1 | 模型在迴圈裡輪詢、自己等自己 | 模型當排程器或郵差 |

量法：數 `prompts/history.json` 裡的 assistant 則數（每則＝問一次模型），團隊把所有成員加起來；另記「模型做的步數／總步數」。

### 軸 2　穩定

| 分 | 標準 |
|---|---|
| 5 | 同輸入跑 10 次，10 次都對、輸出一樣；錯誤一律是最後一行 JSON；崩在任何一步，重跑同一行都收得回來（有測試） |
| 4 | 10/10 對；錯誤結構化；崩潰恢復沒測 |
| 3 | 8～9/10 |
| 2 | 5～7/10，或錯誤是 Traceback／自由文字 |
| 1 | < 5/10，或會留下半截狀態、要人手修 |

量法：工具用固定輸入跑 10 次（寫成單元測試）；團隊把驗收例子跑 3～5 次。有模型的不可能每次一樣，看**結果**對不對（Done when 過不過）。

### 軸 3　資源

| 分 | 標準 |
|---|---|
| 5 | 一次性、峰值 < 50 MB、< 0.5 cpu 秒；不加常駐行程；給模型看的工具描述 < 300 token |
| 4 | 一次性、< 200 MB、< 2 cpu 秒；工具描述 < 800 token |
| 3 | 佔一顆 cpu 幾秒到幾十秒；或工具描述 < 2000 token |
| 2 | 要常駐一支行程（例如多一顆 cpu、多一份每秒醒一次的反覆工作） |
| 1 | 每個 agent 多一支常駐；或吃 GPU；或每次送整份大檔給模型 |

量法：`/usr/bin/time -v`（Maximum resident set size、User＋System time）；kernel 回音的 `ms`；工具描述 token 粗估＝工具檔那一段的字元數 ÷ 4；團隊另記「總共送了多少 token 給模型」（`work/*.out` 有 usage 就讀）。

### 軸 4　快

| 分 | 工具（單次） | 團隊（驗收例子，從 `say` 到 Done when 過） |
|---|---|---|
| 5 | < 100 ms | < 1 分鐘 |
| 4 | < 1 s | < 3 分鐘 |
| 3 | < 10 s | < 10 分鐘 |
| 2 | < 60 s | < 30 分鐘 |
| 1 | 更久或不一定 | 更久，或要人推才會動 |

量法：工具用 `time`；團隊用 `aos-team score`（第一波做，見 [catalog 的 T-score](catalog.md#t-score)）讀各家記憶檔與輸入封存檔的時間。
注意：aos 每走一格至少等一個 tick（預設 1 秒），一次工具呼叫本來就要 2～3 秒，所以團隊分數與其看絕對值，不如看「時間花在哪」。

### 軸 5　人易懂

| 分 | 標準 |
|---|---|
| 5 | 一句話說得清它做什麼；README ≤ 一頁；每一步都留下人看得懂的檔或一行（誰做、做了什麼）；新手試玩 ≥ 4 分 |
| 4 | 同上，但要翻兩份文件 |
| 3 | 要看原始碼或 `listen --show-calls-full` 才知道發生什麼 |
| 2 | 要看 `state.json`、kernel 帳本才知道 |
| 1 | 出事時人看不出是誰做的 |

量法：照現有試玩的做法（[play/](../play/README.md) 的五條標準），派新手只拿 README 玩，最後問他「剛才發生了什麼、每一步是誰做的」。

### 軸 6　邊界（提案）

| 分 | 標準 |
|---|---|
| 5 | 只碰宣告的路徑；不碰任何人的人格、設定、工具、記憶；重跑同一行不會多做（冪等） |
| 4 | 只寫自己的工作區；會唯讀地看別處 |
| 3 | 會寫到固定用途的別處（例如別人的 `input/`、共用任務表），但寫法是原子投檔、格式固定、模型選不了路徑 |
| 2 | 模型能決定寫哪裡（任意路徑），只靠工具自己檢查擋 |
| 1 | 關不住（例如 bash 沒進牢），或能改信任資料（`info.json`、工具檔、`access.json`） |

量法：讀工具碼，列出它會開來寫的路徑；看它進不進牢（[agent-access 提案](../2026-09-24-agent-access/README.md)）。
