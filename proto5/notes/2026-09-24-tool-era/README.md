## 一頁摘要

**六軸**：ai_core 的九軸是「函式怎麼跑」的描述，不是打分；講好壞的是它的治理原則「LLM 預設不准進來，證明非它不可又夠穩才放行」。
所以評分表＝使用者的五句（LLM 少、穩、省資源、快、人易懂）＋我補的「邊界」（碰得到什麼、壞了收不收得回），每軸 1～5，不加總、只看最低兩軸。

**workflows 變團隊**：workflows 是一套給 agent 照做的 Markdown 手冊（派發表、信箱、SESSION-LOG／WAIT_USER、心跳、Done when），**本身沒有執行引擎**——aos 正好補上。
團隊＝**三個會想的 agent**（領隊：拆派收；工人：照工作流做事；審查：只判要判斷的驗收條目）＋**四個不會想的機械員**（門房：前濾網，命中就不叫模型；郵差兼書記：搬信、記帳、替沒回終局狀態的人報 BLOCKED；驗收員：跑 Done when；心跳：routines／schedule 到期就派）。
交流全用現有的「投檔進 `input/`」：agent 寄信只寫自己的 `outbox/`，郵差搬；沒有「等回信」工具（proto2 教訓：模型會自己等自己）。

**工具**：29 個，只有 1 個（`wrap-cli`）可能要模型；「讀一個 python 檔納入工具」＝`tools wrap-py`，用 `ast` 讀型別與 docstring 生 JSON Schema，不 import、不叫模型。`/compact` 預設是機械的（保留最後幾輪、工具輸出換成一行摘要、原文封存），叫模型寫摘要是第三波的選項。

**三波**：
- 第一波（沒牆也安全，**4 隊並行＋1 隊收尾**）：骨架（`aos-team`、模板、門房、交接書）、郵差（寄信、郵差＋書記、驗收員、心跳）、檔案＋workflows 工具包（`json_edit`、`md_section`、`wf_*`、`aos-directives`）、記憶（`context`、`compact`、`note`）。驗收：三成員團隊真跑「把 heartbeat 包導入空專案」3 次、`aos-team score` 打分、新手試玩。
- 第二波（牆合進 main 後，3 隊）：造工具（`tools new／test／wrap-py`）、把第一波工具放進牢、申請類（碰資料夾、改人格都是「提案，人批」）。
- 第三波（挑著開）：模型生成員、模型寫工具、固化建議（把領隊老在派的句型變成門房規則）等「讓模型做更多」的。
