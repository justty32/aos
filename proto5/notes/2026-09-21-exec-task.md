# 任務書：proto5 第一支程式 aos-exec（2026-09-21）

使用者一句話：「開始依據規範做第一個程式：aos-exec，支援現有的 inst 格式」。

## 要做什麼

照 [spec/inst-posix.md](../spec/inst-posix/README.md)（規範先行）寫 proto5 自己的 inst 讀／驗／執行，
指示詞一律用現成的 [lib/aos_directives.py](../lib/aos_directives.py)（**不要重寫指示詞機制**、也不要改它；
它的 [README](../lib/README.md) 最下面「宿主怎麼用」就是預期的用法）。

放哪：

| 檔 | 職責 |
|---|---|
| `proto5/lib/aos_inst.py` | 讀 inst.json → 驗 `_metainfo`／七欄位 → 回一個執行者能直接用的結構（argv、cwd、四條串流各自的路徑＋選項旗標、envs＋clear、exit＋append／mkdir）。錯誤是 `InstError(code, msg)`，`str(e)`＝「代號: 白話」；指示詞的 `DirectiveError` 直接往上丟或包成同形狀，代號照 directives.md §6 |
| `proto5/lib/aos_exec.py` | 執行者：`run_target(...) -> (code, kind)` 照 inst-posix.md §6 做（驗完才跑、mkdir／append／inherit／merge、clear、setsid、逾時 SIGTERM→2 秒→SIGKILL、exit 檔 fsync 檔＋父目錄、125／2）＋ `main()` 命令列 |
| `proto5/cli/aos-exec` | 薄薄一層入口（`sys.path` 加 `../lib`），可執行 |
| `proto5/lib/test/test_inst.py`、`test_exec.py` | 測試，`cd proto5/lib && python3 -m unittest discover -s test` 要跟現有 101 條一起全綠 |
| `proto5/spec/exec.md` | aos-exec 的說明，**重點是命令列**：三種目標怎麼分、`--dir-target`／`--timeout-ms`／`--stderr`／`--`、退出碼 2／125／原樣、125 與 2 時 stderr 印什麼。行為部份**不必多說**——一句「照 inst-posix.md 跑」指過去就好（使用者原話：「行為部份不必多說，反正就是按照inst格式來，主要是cli部份」）。CLI 內容以 proto4-3 現況搬過來，開頭標明「命令列走法照 proto4-3 現況整理，使用者還沒逐條拍板」——不要自己發明新旗標 |

## 規則

1. **規範是老大**：inst-posix.md 與 directives.md 寫什麼就做什麼。程式跟規範對不上的地方
   **不要改規範檔**（另一個 agent 正在整理它），寫進回報讓我拿去問使用者。
2. 命令列形狀沿用 proto4-3 的 `aos-exec xxx [--dir-target REL] [--timeout-ms N] [--stderr PATH|-] [-- ARG...]`
   （三種目標：普通檔／`.json`／資料夾；規則見 [proto4-3/docs/exec.md](../../proto4-3/docs/exec.md) 前半），
   `run_target()` 的簽名也沿用（含 `on_spawn`、`stderr`、`args`），之後 aos-run 才能直接 import。
3. proto4-3 的 [aos_inst.py](../../proto4-3/aos_inst.py)／[aos_inst_resolve.py](../../proto4-3/aos_inst_resolve.py)／
   [aos_exec.py](../../proto4-3/aos_exec.py) 是**凍結的參考**，可以看、可以抄想法，不要 import、不要動它。
   它的測試 [proto4-3/test/](../../proto4-3/test/)（test_fields／test_opts／test_ref／test_fmt／test_env／
   test_reject／test_targets／test_api）是很好的案例來源，可以搬過來改成 proto5 的。
4. 只用 Python 3.12 標準庫。
5. `$env` 讀的是執行者自己的環境；`$ref` 中心路徑＝解出來的 `cwd`（頂層整份與 `cwd` 自己以 base 為中心）；
   解的順序：頂層整份 → `cwd` → `argv` → `envs` → 四個路徑欄。位置＝原始 JSON 實體路徑
   （`resolve_located` 走進容器時要帶回傳的 ctx／position）。
6. 各位置的選項表照 inst-posix.md 3.3：用 `option_names`／`parse_options` 的 `table`
   （`val: required|forbidden|optional`、`alone`）表達；`$opt` 出現在不吃選項的位置（argv 元素、envs 的值）
   ＝ `UnknownOption`（空表）。
7. 寫完：`proto5/lib/README.md` 加 aos_inst／aos_exec 兩節、`proto5/README.md` 程式表加列；
   `wf/workflows/common/code-map.md` 的表格加一列 proto5（指到 `proto5/README.md`）。
8. 回報：做了什麼、測試數字、規範對不上或含糊的地方（條列）、你自己拿不定的決定。
