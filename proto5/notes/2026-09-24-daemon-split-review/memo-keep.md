# 保留派：切使用者的理由打折了，兩支還是該分（Opus，故意站這邊）

## 結論先講

- **「daemon 要 sudo 才能切使用者」這句站不住**：不用 root 也做得到（[實驗 3](exp/README.md) 用系統原配的 subuid 就擋住了）；而且現在程式**完全沒切使用者**，09-22 決定維持兩支時也**沒寫權限**（[總結第 4 節第 3 題](../2026-09-22-daemon-kernel-summary.md)）。拿它當分開的理由，我不辯。
- **但分開還是對的**，靠的是別的理由：會長命、會拉行程的那支要小；會讀「任何人丟進來的單子」的那支不該握權力；kernel 一格一格跑、改了不用重開。
- **權限這條線：現在走 bwrap 牢，不切使用者。** 但若哪天要切，只准 daemon 做——這正是它該獨立、該小的原因。

## 題 2：剩下的理由，各有多重

| # | 理由 | 份量 | 誠實評語 |
|---|---|---|---|
| 1 | **權限分離**：握「能換身份／能拉行程」的那支極小，讀不受信單子的那支沒權力（OpenSSH、postfix 都這樣分） | **有條件的重** | 只在「真的切使用者」時才成立；走純 bwrap 路線時**等於零**，因為 bwrap 不用任何權力 |
| 2 | **subuid 路線下爸爸是假 root**：開 namespace 的那支讀得到所有家 | **重（限該路線）** | 而且 namespace 要靠一支**一直活著**的行程撐著；kernel 一格就退，撐不住，只能是 daemon。合一的話，假 root 就是「解析所有人丟來的單子」的那支——最糟的組合 |
| 3 | **kernel 一格崩了只丟一格、改 kernel 不用重開** | **中** | 老實說這主要來自「kernel 一格一格 exec」，不是來自「兩支」。但合一（I 隊的②④）就是把排程變長命，這個好處就沒了 |
| 4 | **kernel 崩了有人收屍、拉回** | **中** | kernel cpu 本來就是 daemon 用 `restart:true` 拉的（[aos_kernel_engine.py](../../lib/aos_kernel_engine.py)）。合成一支時，排程出 bug 會拖垮收屍；爸爸被 KILL，孩子不會跟著死 |
| 5 | **daemon 極簡不常改** | **輕～中** | daemon 430 行、只認 spawn／kill（[spec](../../spec/daemon/README.md)）。但它 09-23 才寫好，09-20 起 git 仍改了 4 次（kernel 13 次）；「不常改」還沒被時間證明 |
| 6 | **一個 daemon 管多個 kernel 家、K2** | **輕** | daemon 不認識 kernel，所以天生支援；但沒人真的這樣跑，兩個 kernel 各配一個 daemon 也行。而且同一個使用者下 K2 **不是權限邊界**（[cost-safety §2](../2026-09-24-cli-agents/cost-safety.md#2-誰能叫它們)），不能拿來講安全 |

**夠不夠撐兩支？夠。** 就算第 1、2 條算零，3＋4 兩條「中」對上的是合一的收益——主要是「開機少一步」，而那用 `aos up`／`aos down` 就包得掉（I 隊已這樣建議）。合一換到的小，丟掉的中等，不划算。第 1、2 條則是**留一扇門**：分著幾乎不花錢，哪天要切使用者時不用拆程式。

分開的代價我也認：兩個家、兩種死法（r5 撞過「daemon 死了 health 還叫你 boot kernel」）、每步至少等一格。這些是真的，但都不是權限問題。

## 題 3：I 隊結論變不變

[I 隊](../../../proto5-2/notes/2026-09-24-one-program/README.md)的「現在不動；要動選③分開＋kernel 帳本改 sqlite」**不變**，而且更站得穩：

- 權限理由少了一條，但 I 隊本來就沒靠它；它選③靠的是崩潰隔離、改程式不重開、碰最少前提——都還在。
- 補一條**否決條件**：若將來權限走「切使用者」（root 或 subuid），**②和④直接出局**，因為合一後握權力的那支同時在讀不受信的單子。
- 建議在 I 隊結論旁加一句：「daemon 是全系統唯一可能握權力的地方，合一會把權力跟排程綁在一起。」

## 題 4：權限怎麼走

**建議：現在只用 bwrap 牢；切使用者不做，但把「只有 daemon 能換身份」寫成原則。**

- **bwrap**：不用 root、已實測（[agent-access](../2026-09-24-agent-access/README.md)，1.3 ms）、還順便讓 `ws/` 別名成立。它擋工具靠的是「沒掛」，不是 uid（[實驗 2d](exp/README.md)）。agent 的工具是最主要的不受信來源，它擋得住。
- **切使用者**擋的是 bwrap 擋不到的：**cpu 本身**跑的任意 inst（能往 `K/requests/` 放檔就能跑任意指令）。但現在放單子的都跟你同一個身分、本來就能直接開 claude，切了只是多一道。需求還沒到。
- **兩者都要的時機**：真的有「不受信的人或機器來投單」、或多個 agent 要互相看不到彼此的家時。那時選 **subuid**（不用 sudo）：daemon 開 namespace、孩子各自降權；kernel 與 bwrap 照舊。代價先講：外面的你 `cat`／`rm` 不到孩子的家、祖先 700 資料夾要處理、kernel 要讀 cpu 家得靠群組權限或交給 daemon——`ls`／`cat` 範式會受傷。
- **不選** root daemon＋setuid、sudoers 白名單、系統層 systemd：都要動系統設定，跟「使用者自己跑、一個家一個主人」衝突。

## 題 5：要使用者拍的（附預設）

1. **daemon／kernel 維持兩支嗎？** 預設：維持；理由換成上表第 3、4 條寫進 daemon spec 沿革，「切使用者」那條劃掉。
2. **權限現在走哪條？** 預設：只走 bwrap 牢（照 agent-access 提案），不切使用者。
3. **「只有 daemon 能換身份、拉行程」要不要寫成原則？** 預設：要，一句話寫進 daemon spec 的「已拍板」；不寫程式。
4. **將來真要切使用者用哪種？** 預設：subuid＋daemon 開 namespace，不用 sudo；等出現「不受信投單者」再開題。
