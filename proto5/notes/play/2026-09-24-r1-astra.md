「卡住的地方」逐條如下；都未超過 15 分鐘。

1. **README → agent 三份規範，判斷能否使用時**  
   我以為版本狀態會一致。README 說已實作，`agent.md`、`aos-agent.md`、`aos-llm-call.md` 頁首卻寫「程式未跟」，甚至提舊模組。實際新流程能跑，這些頁首讓我無法確定該信哪一份。

2. **`kernel.md §6`、`aos-llm-call.md §1`，準備執行環境時**  
   我以為 init／boot 足以接起 CLI。實際還要讓 daemon 啟動時的 PATH 找得到 proto5 CLI，並在 llm cpu 設 AOS_LLM_CONFIG。文件有寫，但完整接法分散；我在首次 boot 前配置妥當才順利跑通。

3. **`kernel.md §2、§6`，查看 once 結果時**  
   我直覺「回音」會包含 date 輸出；實際只回執行狀態，內容得在 inst 指定 stdout 後另讀。照文件能理解，但需要主動切換兩種「結果」的概念。

4. **`aos-agent.md §11`，故意刪除 `llm.model` 後呼叫 stop**  
   我以為停止排程只需要知道 agent 名字。實際 tick 和 stop 都回 `LlmInvalid: llm 缺了 model`，stop 也被驗證擋住。補回欄位後可恢復；這次測試當下 agent 已取消登記，沒有造成失控，但控制介面的限制確實存在。

5. **`agent.md §3.3`，把工具頂層改成物件**  
   我想知道能否直接定位錯誤。實際訊息是 `ToolInvalid: <完整檔案路徑> 的工具頂層必須是陣列`，非常清楚；改回陣列後 tick 回 101，正常等待。這項故意撞牆的體驗很好。

6. **`aos-llm-call.md §5、§6`、`aos-agent.md §9`，錯 endpoint／短逾時**  
   我以為 agent log 就能直接看到原因。實際先看到「exit 1，看 log/llm.err」，再到 llm log 才看到 `Connection refused` 或「HTTP 等了 1 ms 仍未完成」。三次失敗後有清楚的 touch 指令；但必須在 agent 家建立檔案，修好設定本身不會解除等待。照做後兩種故障都恢復到 idle。

7. **`aos-agent.md §8`，tick 中途被殺**  
   我擔心輸入已搬走會遺失或重複。用尾端加大量空白的合法 JSON 拉長收件窗口，在 `intake` 已記錄、記憶尚未增加時 SIGKILL；退出為 -9。重跑 tick 後 intake 清空、轉 think，同一輸入只進記憶一次，模型最後回答「已恢復」。這次驗到收件窗口，沒有據此推論所有崩潰窗口都安全。

8. **`kernel.md §6`，確認完全停止時**  
   我以為 stop 返回就代表停乾淨。實際 kernel stop 只放通知，要再看 phase 與 daemon 孩子表；停止後 kernel cpu 的 requests 還留一份殘格。文件有解釋，但首次看到容易誤認仍有未完成工作。
