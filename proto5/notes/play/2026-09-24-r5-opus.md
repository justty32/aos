## 總結

README 照抄幾乎每一步都一次過：`booted 4 cpus`、`started`／`already started`、`say --wait` 約 13 秒回話、自寫工具 5555。fix-r5 新加的東西大多照文件運作：
- **連敗三階段**：兩個 agent 同時說話、port 改壞。約 4 秒後出現「重試中（連敗 1/3）」，8 秒到 2/3，13 秒變「連敗暫停」。`aos-kernel ls` 第一行也跟著變，最後停在「agent 暫停中：poet（連敗）、clerk（連敗）（…continue --all）」。
- **解除暫停**：port 改回後跑 `continue --all`，印「解除連敗暫停（等下一次成功）」和「continued 3／3」，連手動暫停的那個也一起解開。約 4 秒內三個都回 `ok`，暫停期間投的話全部有被回。
- **llm cpu `kill -9`**：閒著時殺，約 1 秒內出現「恢復中（llm cpu dead，daemon 重拉中）」、再 1 秒自己回 ok。工作中殺，先「恢復中」，再「重試中（連敗 1/3）、結果不明（Interrupted）」，4 秒後回 ok、回話照出。
- **`check --probe`**：port 錯 0.045 秒就 bad。模型名改成不存在的（暫時改共用 llm.json 做到的），正確給 warn。不帶 `--probe` 最後一行寫「未測模型連線」。
- **`--target` 三種來源**：kernel 和 agent 的錯誤行尾巴都寫「取自 --target／AOS_KERNEL_HOME／目前資料夾」，清楚。
- **搬走 `requests/`**：`ls`／`status` 都講「K 家缺目錄」；`say --wait` 立刻退 101 並寫「已投入，不要再說一次」；搬回來後那句有被處理。
- **沒 start／手動暫停時 `say`**：話照收，提示正確，帶 `--wait` 立刻退 101。start 或 continue 之後，兩則合成一輪回覆。
- **第 4 步小工具**：寫了一支 `list_dir`（列資料夾內容）交給 clerk，模型能自己多次呼叫、如實回報。工具沒執行位時，`check --agent` 會抓到；模型也看得到 exit 126 的說明。

## 五條標準

- **容易上手：4**。六段照貼都過。扣分只在一個坑：先 `say`（不等）、晚一點再 `listen --wait`，會等不到（見卡住 1）。
- **容易理解：4**。health 一句話加括號裡的指令，很好懂。扣分在這些字眼：`status` 的 wait 行印出內部檔名 `continue-aw-poet-…json 沒到`；`listen` 的時間行寫「記憶最後更新，這則更早」，看不懂在講什麼；`ls` 的 `chain`／`last_seq`／`requests 2` 對使用者沒意義。
- **複雜的東西藏好了：4**。崩潰恢復、批次合併、重拉 cpu 都不用我管。但失敗時 `say --wait`／`listen --wait` 把整段 status 印到 stdout，拿 stdout 當回話的腳本會吃到雜訊。
- **外層控制結構簡單但全面：4**。boot／halt／start／stop／pause／continue 能自圓其說。有三處不對稱：`stop` 沒登記的退 1（`start` 已登記卻退 0）；`aos-daemon halt` 指錯家也說 `not running` 退 0；`aos-kernel init` 沒有 `--force`。
- **要背的東西少：3**。要記的有：daemon／kernel 吃環境變數而 agent 不吃；`aos-llm call` 用位置參數不用 `--target`，還要自己設 `AOS_LLM_CONFIG`；加 cpu 要 halt、手改 `K/info.json`、再 boot；`listen` 三種模式的「新」是從哪時算起。

## 卡住的地方

1. **README 第 4 段，`listen --wait`（撞了 4 次）。** 我以為先 `say`（不等），之後 `listen --wait` 會等到這句的回話。實際上它只等「開始聽之後才來的」那則；如果回話在我開始聽之前就到了，就乾等到逾時（90／120 秒）。之後印「沒有新回話（status 看卡在哪）」，可是 status 全是 ok。三個 agent 輪流說話時，這個幾乎一定會撞到。
2. **`aos-kernel init` 對非空、不是 agent 家的資料夾。** 我以為會退 1 要求 `--force`。實際上直接成功、退 0，`a.txt` 跟 kernel 檔混在一起；它根本不認得 `--force`（Usage 錯誤、退 2）。README 和 help 也都沒提。指到 agent 家則會正確拒絕。（調度者按：`--force` 本來就只在 `aos-agent init`，這是我任務書寫錯，不是產品缺口——見文末附註。）
3. **README 第 4 段說「真的問成功了才標『已恢復』」。** 實際上第一行 health 直接從「已解除暫停，等下一次成功」變回 `ok`。「（已恢復）」只出現在 `last-error` 那行，沒有 health 叫「已恢復」。
4. **`aos-daemon halt --target 打錯的路徑`（或環境變數錯）。** 我以為會像 kernel 一樣在尾巴寫「用的是哪個家、從哪來」。實際上只印 `not running`、退 0。真的 daemon 還在跑，我會以為已經關了。
5. **README 第 5 段：`aos-kernel halt` 然後 `aos-daemon halt` 之後。** `ls` 的 health 寫「停機中（aos-kernel boot …）」，但 daemon 已經死了，照括號打 boot 會失敗（`NotRunning`）。應該先提醒開 daemon。只殺 daemon 的情況下它就講對了。
6. **停機腳本：`aos-agent stop` 對已經停掉的 agent。** 印 `NotFound: 沒有這個行程`、退 1。`start` 已經改成冪等退 0，`stop` 沒有；寫成 `set -e` 的收工腳本會斷在這裡。
7. **`check` 抓到 bad 時，尾巴一律寫「照上面的提示修好再 boot」。** 我的 kernel 早就 boot 了，在跑到一半用 `check --agent`、`--probe` 查東西時，這句很怪。
8. **README 第 1 段開 daemon 的那行沒有把 stdout 導走。** 我在管線（`| sed`）裡跑，daemon 一直抓著管線不放，整支腳本卡到 `aos-daemon halt` 才結束。加 `>/dev/null` 就好了。
9. **`aos-llm call`。** README 說三支指令都用 `--target`，它卻是位置參數 AGENT_DIR，帶 `--target` 會退 2。沒設 `AOS_LLM_CONFIG` 就報錯，README 也沒寫手動怎麼叫它。
10. **`halt --no-wait` 什麼都沒印。** 不知道到底有沒有送出。

## 改了會更順的清單（按痛度排）

1. `listen --wait`：如果最新回話比最新一則輸入還新就立刻印出；或者讓 `say` 回一個代號，`listen --wait` 等「這句」的回話。逾時訊息也不要叫人去看 status。
2. ~~`aos-kernel init` 碰到非空資料夾比照 `aos-agent init`：退 1，加 `--force` 才做~~（調度者按：任務書錯置，`aos-agent init` 已有此行為，不用再改 kernel）。
3. `aos-agent stop` 對沒登記的印 `already stopped`、退 0。
4. `aos-daemon halt`／`boot` 的訊息也附「D＝…，取自 …」。
5. 全部停機後，health 先說「daemon 沒在跑」再說 boot。
6. health 真的出現「已恢復」這個階段，或者 README 改成「變回 ok」。
7. 失敗時 `say --wait`／`listen --wait` 的 status 區塊改印到 stderr。
8. status 的 wait 行不要印內部檔名，只寫「等 continue」。
9. README 第 1 段開 daemon 那行加 `>/dev/null`（或 `>>$W/daemon.log 2>&1`）。
10. 加 cpu 給一個指令，不要 halt 後手改 info.json。
11. `check` 最後一行依狀況說「修好再 boot」或「修好即可（已在跑）」。
12. `aos-llm call` 也收 `--target`，README 加一行手動測試的例子。
