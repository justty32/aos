三個 agent 都用 `init` 建立，再分別配置人格與工具：嚴謹管家／`date`、活潑教練／`add`、冷靜檔管／自寫 `list_dir`。依序輪流各說三句，混用等待與不等待；能記住「阿青」、回顧先前算式，也能接續回答檔案數量。實測帶工具的兩次等待約 14.7、15.7 秒。

自寫工具以 stdin 讀 JSON，stdout 回傳排序後的檔名；模型兩次實際呼叫，列出 `待辦.txt`、`早餐.txt`，不是猜答案。重啟 daemon 與 kernel 後，檔管仍記得使用者名字。

故障測試：

- **沒 start 就 say：** 不等待時退 0，但清楚警告「目前沒登記、沒人處理」；`--wait` 約 0.03 秒退 101，沒有乾等，兩則輸入都保留。
- **已有家再 init：** 退 1，明講拒絕覆蓋；比對檔案內容，完全沒變。
- **非 agent 資料夾跑 status：** 退 1，`NotAnAgent` 並指出缺 `info.json`。
- **改壞模型 port：** 改為 `localhost:1`，只有管家當時在問模型。第一次、第二次失敗的 `error` 正確顯示 Connection refused、端點與模型，但第一行仍為 `health ok`。第三次後，第一行清楚變成「連敗暫停」，原因與恢復指令俱全。
- **改回 port＋continue：** 單改端點仍維持暫停，合理；`continue` 後成功回覆祝福。成功後 `error（無）`，舊錯另列 `last-error …（已恢復）`。不過「已恢復」其實在剛放下 continue 訊號時就出現，早於重試成功。
- **kill -9 正在工作的 llm cpu：** `ls` 下方已顯示 cpu `dead`，但 `ls`、agent `status` 第一行仍為 `health ok`。daemon 自動重拉；約兩秒後 cpu 已回來，agent 最終完成工具計算 `165`，歷史錯誤留下 `Interrupted`。無須手動修復。
- **搬走 K/requests/：** `ls`、`status` 第一行立即指出 K 缺目錄，`check` 退 1 並提示補目錄。保留缺目錄狀態 12 秒後搬回，自動恢復，後續聊天成功。只靠文件與診斷即可處理。

卡住的地方，主要是判讀上的停頓，沒有任何一項卡到 15 分鐘：

1. **README「每天重開機」／`spec/kernel.md` §6：cpu 死亡時看第一行。** 我以為 `health ok` 代表目前運作元件正常；實際上同一份輸出下方已寫 llm cpu `dead`。自動恢復有效，但第一行沒有表達「正在恢復」。
2. **README 第 4 段／`spec/aos-agent.md` §1.3–1.4：連败與 continue。** 我以為「已恢復」代表成功完成下一次模型請求；實際只解除暫停就會出現。另有一、兩次連敗時，上方 ok、下方錯誤並存。
3. **README 的 status／last 用法／`spec/aos-agent.md` §1：非同步查看回話。** 我以為 `last` 比較接近「最新完成的答案」；實際可能是工具呼叫前的「來算 18＋24～」，或新輸入尚未處理時的上一輪答案。規範有交代行為，但普通輸出沒有新舊輪次標記；暫停時則會警告舊答案，這點很好。
4. **README 第 2 段／`spec/kernel.md` §6：check 的保證範圍。** 我以為模型設定全綠也能提供基本連線信心；故意改壞 port 仍全綠。規範確實明寫不連 endpoint，但 CLI 的成功輸出沒有提醒這個界線。
5. **README「每天重開機」：重複 start。** 我以為同一套開機指令每天都能順利退 0；保留登記時回 `AlreadyExists`、退 1。文件已解釋可以忽略，因此能繼續，但寫成開機腳本時要額外處理。

改了會更順的清單，按痛度排序：

1. cpu `dead`／重拉中時，第一行顯示「降級／恢復中」，不要仍是單純 `ok`。
2. `continue` 後先標「已解除暫停，待重試」；收到成功結果才標「已恢復」。
3. 模型連敗一、兩次時，第一行顯示「重試中，第 N 次」，與 `error` 一致。
4. `last` 附回覆時間、是否仍有新輸入待處理，以及是否為工具呼叫中的訊息。
5. 重複 `start` 的訊息直接說「已登記，無須重啟」；提供適合每天照跑的啟動方式。
6. `check` 結尾明寫「設定檢查通過；未測試模型連線」，或提供可選的連線檢查。
7. README 加一份完整的每日開關機腳本，收好 PATH、W、`AOS_K` 與背景程序細節。
8. 一般 `status` 的歷史錯誤縮短，長批次名稱和原始 `touch` 提示留給 verbose，讓當前狀態更突出。

最後已依序停好所有測試程序；執行指定的 `pgrep -fa 'aos-cpu|aos-daemon|aos-kernel|aos-agent'`，排除指定項目後輸出為空。
