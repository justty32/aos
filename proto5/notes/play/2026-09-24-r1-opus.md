# proto5 試玩 r1（Opus，新使用者視角）

← [play/](README.md)

只從 README 進去，讀了七份規範，程式只看了一個 cli 入口。模型：本機 LM Studio `google/gemma-4-e4b`。

## 做了什麼、結果

1. **daemon → kernel**：`aos-daemon --home D &`、`aos-kernel init K`、`boot K --daemon D` 一次成功。
   once 工作 `add --once --wait-ms` 直接印回音 `{"code":0,"kind":"child",…}`，輸出在 inst 指的 stdout 檔。
   反覆行程第 5 次回 100 → `ls` 看到 `done`。停機 `aos-kernel stop` → 等 `phase stopped` → `aos-daemon stop`，乾淨。
2. **agent**：在 `K/info.json` 的 `cpus` 手加一顆 `llm`（pool llm、envs 放 `AOS_LLM_CONFIG`），下一格就自己拉起來；
   建 `bob/`（info、system、`date` 工具）、`AOS_K=K aos-agent start bob`、投 `input.json`，
   **12 秒走完 idle→think→act→think→idle**，第一次就成功。回話在 `prompts/history.json`。
3. **故意弄壞**：
   - info 刪 `llm` → `log/agent.err`：`LlmInvalid: info.json 缺了 llm`，10 次後 `ls` 顯示 `bad`；修好 → `stop`、`start` 回來。
   - 工具檔 JSON 壞 → `JsonSyntax: …/tools/read.json 不是合法 JSON：…line 2`；寫了 stdout → `ToolInvalid: 工具 _meta 必須是物件，且不能寫 stdin／stdout`；同名 → `ToolInvalid: 合併後工具同名：date`。
   - 工具 argv 指到不存在的程式 → 模型收到 `工具 read_file 失敗（exit 127）：`（後面空的），模型只能道歉。
   - llm.json 改錯 port → `agent.err` 指去 `log/llm.err`，裡面 `Connection refused`；連 3 次 → `stuck: … touch continue-aw-bob-….json 繼續`，修好 touch 就接上。
   - HTTP 逾時 1 ms、外圈逾時 300 ms：兩種訊息都讀得懂。
   - 先 `aos-agent stop`，手動 tick 60 次、隨機 15～45 ms `kill -9`，打中 6 次（收輸入、think 送件、act 送件、收回之間都有）：
     記憶沒有重複、沒有少，最後正常回 idle。**這部分非常穩。**
4. **第二個工具**：`tools/bin/read-file`（Python 20 行，stdin 讀 `{"path"}`、只准讀 `notes/`），工具檔 `_meta.argv=["tools/bin/read-file"]`、`stderr: merge`；
   加進 `info.tools`，下一問就用上；兩個工具同一則並列呼叫也正常。

## 卡住的地方

1. **README｜第一步**：以為 README 會有上手步驟，實際只有規範表，要自己決定讀哪份。`aos-daemon` 是前景程式，規範沒說要放背景或開另一個終端。
2. **agent.md／aos-agent.md／aos-llm-call.md｜標頭**：寫「程式還沒照這份改、現行仍是舊架構」，README 卻說已實作；以為要照舊版做，實際照規範做就對了。
3. **aos-llm-call.md §1、kernel.md §1.1｜llm cpu**：`aos-kernel init` 預設沒有 llm 池，`--cpu` 也不能帶 envs；以為要重 init，實際是手改 `K/info.json`，下一格就會建。
   若那顆 cpu 已經建過，envs 就不會再抄（要 stop、改 `cpus/llm/inst.json`、重 boot）——我是剛好第一次就寫對。
4. **aos-agent.md §11、aos-llm-call.md §1｜PATH**：`aos-agent`、`aos-llm-call` 靠 cpu 的 PATH 找，cpu 的環境又繼承 daemon 的。
   我是碰巧先 export 了 PATH 再開 daemon 才沒事；這個前提散在兩份規範各一句，沒寫在「怎麼開 daemon」那裡。
5. **daemon.md §1｜daemon.log**：文件列了 `D/daemon.log`，實際沒有這個檔，stderr 跟著啟動的終端走。
6. **kernel.md §6｜stop**：以為 `aos-kernel stop` 會等停好，實際立刻退 0、什麼都不印，要自己用 `ls` 等 `phase stopped`。
7. **agent.md §3.3｜工具跑不起來**：argv 寫錯時模型只收到「失敗（exit 127）：」加空字串；要知道 127＝找不到程式才看得懂。
8. **aos-agent.md §13｜看回話**：回話只能讀 `prompts/history.json`，文件有講，但每次都要 python 撈最後一則。

## 改了會更順的清單（痛的在前）

1. README 加一段「十分鐘上手」：daemon 放背景 → init → 加 llm cpu → boot → add → ls → stop 的順序，附最小 agent 家（info、system、一個工具、llm.json）。
2. 拿掉三份 agent 規範標頭「程式未跟」的過時句。
3. 把「daemon 啟動前 PATH 要含 `proto5/cli`（或在 cpu envs 設 PATH）」寫在 daemon 啟動那裡，否則 tick 和問模型都會 127。
4. `aos-kernel init` 能一次建出 llm 池（例如 `--cpu llm:llm --llm-config PATH`），或預設就帶一顆。
5. `aos-kernel stop` 像 `aos-daemon stop` 一樣等到停好、印 `stopped`。
6. 給一個看回話的指令（最後一則 assistant），不用自己撈 history.json。
7. 工具 126／127 時結果補一句「找不到／不能執行 argv[0]」。
8. `aos-kernel ls` 裡 `bad` 的行程附一句該看哪個 log（agent 的就是 `log/agent.err`）。
9. `ToolInvalid` 訊息帶檔名和第幾個元素。
10. daemon.md 的 `daemon.log` 跟實作對齊（要嘛真的寫、要嘛刪掉那行）。
11. `input.json.*.done`、`continue-*.done` 會在 agent 家越堆越多；放進一個子資料夾或給清理方式。
12. `start`／`stop`／`init` 成功時印一行（現在完全沒輸出，要自己 ls 確認）。
