**故障與復原**

- **沒 start 就 say：**普通 say 退 0、印投遞路徑。status 明確顯示「沒登記（aos-agent start）」。加 `--wait --timeout-ms 1500` 後逾時退 101，附狀態。照提示 start 後，待收輸入能接續處理。
- **已有家再 init：**退 1，`AlreadyExists` 明說拒絕覆蓋；原 info 內容不變。
- **非 agent 資料夾跑 status：**退 1，`NotAnAgent` 明說沒有 info.json。
- **改壞 llm.json：**會計連敗三次後暫停，say --wait 提前退 101；status 看得出連敗暫停，last 也提醒答案可能過期。check 指出缺 `_metainfo`。修回再 continue，原題接續算出 `17`，之後新對話正常。
- **llm cpu 工作中 kill -9：**daemon 自動重拉，新 PID、`last_exit 137` 可確認；agent 留下 `Interrupted`，自行重試後完成回答。
- **刪除 K/requests/：**check 立即指出缺目錄，提示 `mkdir -p`；add 回 `WriteFailed`。依提示補回後，不必 boot，待處理對話與新對話都成功。這次證明目錄與服務能恢復，不能據此推論被刪掉的任意在途請求都能找回。

以上復原均只靠文件與 CLI，沒有卡超過 15 分鐘。

**卡住的地方**

1. **README 第 1 段，背景 daemon：**我以為分段執行仍會存活，實際隨該 shell 結束停止。文件有重開方法，但沒有說明終端生命週期。
2. **README 第 4 段／aos-agent.md §1.2，未啟動就聊天：**我直覺以為成功代表有人會處理，實際只代表投檔成功。規範有寫，普通 say 現場沒有提醒。
3. **aos-agent.md §1.3、§9，連敗狀態：**我以為連敗三次會顯示 errors 3，實際暫停時已歸零，kernel 還顯示 running；必須讀 wait 才能判斷。
4. **aos-agent.md §1.3，恢復後 status：**我以為 error 是目前錯誤，實際是歷史最後一行；已成功回答，仍顯示 stuck。暫停時它又把真正的設定錯誤擠掉，要另看 log 或 check。
5. **kernel.md §6，requests 目錄被刪：**我以為 ls 或 agent status 會指出基礎設施壞了，實際仍顯示 running、忙碌工作。只有 check 清楚指出原因。
6. **aos-agent.md §1／CLI help：**我期待 `say -h` 直接示範語法，實際 usage 是 `[dir] TEXT [[dir] TEXT ...]`，比文件的兩種用法難懂。

**改了會更順的清單，按痛度排序**

1. status／ls 增加整體健康摘要，將缺目錄、停止推進與正常忙碌區分。
2. status 區分「目前故障」與「歷史錯誤」，標示時間及是否已恢復。
3. 未登記時 say 保留投遞能力，但立即提醒「目前沒人處理」並給 start 指令。
4. 連敗暫停直接顯示「已連敗 3 次、等待 continue」，避免 errors 0 造成誤解。
5. 暫停摘要同時保留根因；優先顯示 continue，長 touch 指令留給詳細模式。
6. README 補一段「每天重新開機」完整流程，串起 daemon、boot、三個 start 與檢查。
7. `say --wait` 提供簡短進度，例如排隊、問模型、執行工具；等待時間寫成範圍。
8. `say -h` 明列「目前資料夾」與「指定家」兩個例子，補 timeout 預設值。
9. README 說明背景 daemon 與終端關閉的關係。
10. 將文件標題中的輪次、審查沿革移到末尾，讓使用者先看到操作與故障索引。
