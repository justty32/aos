# 逾時：astra 原始調查報告（2026-09-22）（精簡版）
完整版：[../notes/2026-09-22-timeout-report-astra.md](../notes/2026-09-22-timeout-report-astra.md)

## 結論

**proto5 沒有整格限時、工具限時、等待期限，也沒有引擎連敗上限。**已有的 HTTP 120 秒是 socket timeout，不是整次思考的總期限；`waits` 每次檢查後退 101，可能跨無限多次呼叫一直等，並非單次呼叫一直阻塞。

這是 astra 對調查當時工作樹的唯讀分析；當時已有尚未提交的 agent／exec 實作。清理漏洞若未實跑，以下明列為源碼推論。所有新增數值與方案都是建議，尚未拍板。

## 最重要的 25 件事

| # | 事實 | 意義 |
|---|---|---|
| 1 | 通用 inst 只有七個執行欄位，沒有 timeout；未知 key 忽略。 | 直接加 `timeout_ms` 不生效。既有分工是 inst 說怎麼跑，執行者決定等多久。 |
| 2 | exec 支援 `--timeout-ms`／library 參數，預設 0＝不限。 | 到期 TERM 工具 group，最多等 2 秒再 KILL，另清殘留 group。 |
| 3 | exec 回 child 的實際退出碼，沒有 `timed_out`。 | 143／137 不能證明逾時；工具捕捉 TERM 後正常退出，也可能回 0。 |
| 4 | exec 的計時在 spawn 後開始。 | 讀驗、開檔、啟動、清理寬限、寫退出檔不包含在指定秒數內。 |
| 5 | HTTP 預設 120000 ms，必須正整數，0 不能表示不限。 | 失敗成為 `EngineFailed`，ask CLI 退 3；client 不重試、不改 agent state。 |
| 6 | HTTP 限制相關 socket 阻塞操作。 | DNS、逐地址連線、慢慢讀完 body 沒有共用總期限；本地關線也不保證遠端停止推論。 |
| 7 | idle 沒有整格限時。 | 無輸入通常立即退 101；有輸入則入記憶、rename `.done`、轉 think，讀寫卡住無 watchdog。 |
| 8 | think 只有內部 HTTP 限制。 | 成功有 calls→act，無 calls→idle；引擎失敗留 think、退 0，記憶不動。 |
| 9 | act 在一格內依序跑完所有 calls，再一次寫結果。 | 一個工具卡住，後面的工具與整批寫回都等著。 |
| 10 | agent 呼叫工具時沒傳 timeout，工具 `_meta` 也沒有相關契約。 | 目前工具跑多久等多久；加 `_meta.timeout_ms` 不會自動生效。 |
| 11 | agent 工具另開 session/group，沒有終止訊號轉送。 | 只砍 agent 不保證工具跟著死；group 清理也抓不到另開 group 的後代。 |
| 12 | `waits` 無期限、無最大檢查次數。 | `since`／mtime 是「只收某時後更新」，不是「最多等到何時」；101 不應算失敗。 |
| 13 | 引擎失敗沒有上限、退避或錯誤計數。 | 外面再叫就再問；目前也沒有 retry／stuck 狀態。 |
| 14 | 工具 stdout 與 HTTP body 都全量收進記憶體。 | 時間上限不能代替輸出容量上限。 |
| 15 | proto2 工具通常 60 秒、HTTP 300 秒；自製工具仍可能不限。 | exec／loop 沒有單格牆鐘上限，活著卻卡住的 PID 不會被自癒處理。 |
| 16 | proto2 等 LLM：仍在 queue/running 等 1800 格，否則 60 格；20 格後重試，第五錯停。 | 到期不撤舊單；旁線後來改 600 秒，避免格數受排程速度扭曲。 |
| 17 | proto4-3 由 run／exec 管每格及整體時間，預設都不限。 | 整體期限會縮短當格預算；child 逾時後 run 預設仍繼續。 |
| 18 | proto4-3 kernel 只數完成格數及非零結果，預設 `bad_after=10`。 | 沒 elapsed watchdog；101 不算壞。最後碼推算及換人清帳，使它不是精確的跨排程重試上限。 |
| 19 | proto4-3 daemon 自癒補死掉／缺少的 cpu。 | 不是活工作卡死診斷；run 若被 STOP，負責限時的人也停了。 |
| 20 | proto4-5 HTTP 預設 300 秒，preflight 與 chat 各拿完整預算。 | queue 無期限；低優先工作可能一直被插隊。 |
| 21 | proto4-5 worker 從 dispatch 算 T＋5 秒，下個 tick 才查。 | 只 TERM PID、未確認死便結帳；可能晚到覆蓋結果或帳面有空位、實際仍在跑，屬源碼推論。 |
| 22 | proto4-5 `--wait` 到期只停止等待；明確 `llm rm` 才嘗試 TERM／KILL。 | 不等了、撤回未收單、取消已執行工作，是三種不同結果。 |
| 23 | proto4-6 `wait_for` 的 since/checks 只記錄、不設期限。 | 等檔可永遠 101，`bad_after` 救不了。 |
| 24 | proto4-7 每工具 60 秒、模型等待 600 次檢查、20 次 idle 後再問。 | 600 次不是 600 秒；等超時不撤原單；8000 字元輸出是收完才截斷。 |
| 25 | proto4-7 五錯設 `stuck:true`，新信清帳；每題只計 ask，上限 60 次。 | 成功沒清 errors，實際是同題累積五錯；不是所有格都扣動作額度。 |

歷史教訓：排隊就放棄重送會留下舊請求繼續耗資源；互等回信可能死結；失敗回 idle 而沒人再喚醒會掉話。PID 活著、tick 增加都不等於任務有進展。使用者曾提出短格、長操作另交時鐘的方向，但未決定具體秒數；人工 pause 只停狀態機，不代表取消外部工作。

## 建議怎麼分工，以及不能漏的收尾

一次工作太久、等結果太久、反覆失敗、整格卡死與任務沒進展，必須分別處理。

| 關卡 | 原報告建議 | 理由與時機 |
|---|---|---|
| 一次 tool call | 工具私有 `_timeout_ms`，預設 60 秒可覆寫；agent 傳給 exec。 | 保留 `_meta` 純 inst；exec 共用 TERM→2 秒→KILL，回明確 tool_timeout，先做。 |
| HTTP | 保留 120 秒，不偷偷重試。 | 說清楚 socket 語意即可；遠端取消另需協定。 |
| 引擎連敗 | 總共三次，至少隔五秒；有效成功清零，明確 stuck，通知一次。 | agent 決定是否再送，避免 client／CPU 各重試而放大成本；先做。 |
| 整格硬上限 | 初值 300 秒可覆寫，外部 run／exec 監督，kernel 決定停排。 | agent 自己量抓不到永不返回；跟 run／kernel 一起做，第一版不自動重跑中斷的 act。 |
| 一般 waits／人工 pause | 不套預設期限。 | 人工暫停可以永遠等；有 owner 的非同步工作由 owner 保證有限終態。 |
| LLM CPU | queue 300 秒、worker 150 秒，皆可覆寫，第一版就做。 | 分清排隊與執行；owner 清理本地 worker 並寫唯一終態，不自動重送。 |

工具 timeout 應補對應 `tool_call_id` 的失敗訊息；一批 assistant calls 每個都要有結果，才能再問模型。硬砍整格則記 step_timeout、停排並保留原 state，不能假裝工具沒做過：A 已成功、B 卡住時，整批 history 可能尚未落盤，直接重跑會再做 A。自動恢復要另做逐 call 記錄、結果落盤與「結果未知」處置。

外層監督還要能清工具另開的 groups：可登記所屬 groups，或採共同容器如 cgroup，後者須驗證環境。只給 agent 的 wait 加 timeout 不代表整棵工作已清完；kernel 自癒也不能立即復活剛停排的工作。

若日後加 `until`，它與 `since` 不同；先查合格結果再查期限，若要求「期限前完成」，須用可信完成時間。過期不等於成功；往 input 丟通知也穿不過尚未開的 waits 門，而且 input 只在 idle 收。結果還要另行收取時，不可先 consume rename 走；晚到結果須按 request id 辨認，不能覆蓋終態或混入新題。

300 秒整格是資源上限，不能保證很多個 60 秒工具都跑完；要保證整批，得按 calls 計預算或改逐工具跨格。暫不做通用 inst timeout、全面 waits 期限、硬砍 act 自動重放、兩層重試、格數當秒數，或憑無進展自動判失敗。工具限時及連敗停屬低到中複雜度；整格清理與恢復中到高，LLM CPU 跨進程生命週期則高。
