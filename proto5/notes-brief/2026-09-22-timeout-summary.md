# 逾時：精簡總結與待拍板（2026-09-22）（精簡版）
完整版：[../notes/2026-09-22-timeout-summary.md](../notes/2026-09-22-timeout-summary.md)

## 結論

**現在有 exec 的可選限時，也有 HTTP 的 socket 逾時；agent 整格、工具、waits 與引擎重試都沒有完整上限。**Claude 建議先補每工具預算、連敗暫停，並說清楚 HTTP 的現有語意；整格保險和排隊期限等 kernel／LLM CPU 落地再做。這些仍是建議，決策由使用者做。

本篇整理 astra 對 proto2、4-3、4-5、4-6、4-7 與 proto5 的調查。要注意兩份文件的建議不同：astra 原報告主張新增明確 stuck；**本篇 Claude 建議沿用 waits 暫停，不加新狀態**。

## proto5 有哪些保護，缺哪些保護

| 環節 | 現況 | 會怎樣 |
|---|---|---|
| aos-exec 子程式 | 支援 `--timeout-ms`／`run_target(timeout_ms)`，預設 0＝不限。 | 真有設限才會 TERM 整個 group，等 2 秒後 KILL。 |
| aos-llm-ask HTTP | `engine.timeout_ms` 預設 120 秒。 | 限每次 socket 阻塞讀寫；回應持續慢慢滴回來，整次可以超過 120 秒。 |
| idle／think／act | 三種格都沒有整格限時。 | agent 自己卡住，沒有整格保險。 |
| act 中一個 tool call | 沒有限時；agent 呼叫 `run_inst` 時用預設 0。 | `_meta` 沒有生效的限時欄位，工具不回來就一直等。 |
| waits 門 | 沒期限。 | 每次沒等到退 101；單次檢查會返回，但整體可以永遠等。 |
| 引擎失敗重試 | 沒上限，也沒間隔。 | 每次 agent 退 0，外面下一次叫它便再問。 |
| 整個走一格呼叫 | 沒總期限，CLI 也沒旗標。 | 光有 HTTP 或子程式 timeout，並不能說整格已受保護。 |

兩個誤區要分清楚：**143／137 只代表 child 被 TERM／KILL，不能單憑退出碼判逾時**，目前也沒有 `timed_out` 欄位。另一個是工具另開 session，agent 沒轉送訊號，所以外面砍掉 agent，不能保證工具一起死。

## 歷代做法與留下的教訓

| 版本 | 怎麼限時／重試 | 要記住的問題 |
|---|---|---|
| proto2 | 工具 60 秒、HTTP 300 秒；主線等 LLM 1800 格；五次連敗到 stuck。 | 格數受排程速度影響；不等之後舊單仍在；互等會死結；失敗回 idle 可能掉話。 |
| proto4-3 | run／exec 管每格 `timeout_ms` 與整體 `time-limit-ms`，預設都是 0。 | kernel 沒 elapsed watchdog，只數非零退出到 `bad_after=10`；101 不算壞。 |
| proto4-5 | HTTP 300 秒；worker 派工起 T＋5 秒，只 TERM、不 KILL。 | 排隊沒期限；`--wait` 到期只停止等，不撤單。 |
| proto4-6 | wait_for 只記 checks，無等待上限。 | 有計數不等於有期限。 |
| proto4-7 | 每工具 60 秒、輸出 8000 字元；等模型 600 次檢查；errors≥5 到 stuck。 | 成功沒清 errors，實際是同題累積五錯；600 次檢查也不是固定秒數。 |

使用者自己的方向是：每步盡可能短，免得拖慢 tick；長操作另開時鐘處理；預期很快卻卡住時，通常先停在那邊等。這些是方向，並未直接決定這輪的秒數或逾時後動作。

## 四個問題，分別交給誰處理

| 問題 | 責任位置 | 到了怎麼辦 |
|---|---|---|
| 一次工具跑太久 | exec 量與終止。 | 砍工具，回對應的 tool 失敗訊息，讓模型知道失敗。 |
| 等結果等太久 | 建立等待的流程。 | 結算失敗，不能假裝結果已到。 |
| 引擎反覆失敗 | agent 記失敗次數。 | 到上限停下來等人。 |
| 整格卡死 | 外面另一個進程，例如 run／kernel。 | 外部計時與處理；agent 自量抓不到永遠不返回的呼叫。 |

## Claude 建議：先做三件，其餘跟所屬元件一起做

| 關卡 | 建議內容 | 理由／先後 |
|---|---|---|
| 每個 tool call | 預設 60 秒可覆寫；工具元素旁新增 `_timeout_ms`。 | `_` 開頭本來不送模型；`_meta` 保持純 inst，毋須改通用 inst 分工。**先做**。 |
| 引擎連敗 | `state.json` 加程式寫入的整數 errors；連三次失敗就暫停，有效成功清零。 | 到三次時往 waits 加 `continue.json`、errors 歸零、stderr 說一句；人 touch 才繼續，**不加新狀態**。先做，但要使用者同意例外。 |
| HTTP 說明 | 維持 120 秒。 | 文件明寫 socket timeout，不宣稱整次呼叫總上限；這項只改文件。 |
| 整格硬上限 | 300 秒起跳、可覆寫；外面 run／kernel 量與砍，kernel 記錄並停排。 | **不自動重跑**：act 中途被砍，重來可能把已做的工具再做一次。跟 kernel 一起做。 |
| waits 期限 | 先不加預設期限；之後有需要再加 until。 | 人工 pause 應能永遠等；有 owner 的非同步工作由 owner 給有限終態。 |
| LLM CPU 排隊／worker | 排隊 300 秒、worker 150 秒，由 CPU 管。 | agent 不另猜同一份期限；跟 LLM CPU 一起做。 |

連敗暫停方案會打破目前「aos-agent 對 waits 只劃不加」的規則，這正是需要拍板的地方。恢復要人 touch continue，不要任意新 input 自動恢復，否則無關輸入也會把失敗限制重置。

這輪先不做：通用 inst 加 timeout、每條 waits 自動套期限、被砍的 act 自動重放、用格數當秒數，或把「多久沒有進展」直接當失敗。理由是這些各自涉及分工、人工 pause、工具副作用或業務進度判斷，不能塞進同一個 timeout 欄位解決。

## 全部 5 題待拍板

| 題號／問題 | 選項與取捨 | Claude 建議與理由 |
|---|---|---|
| 1．工具預算放哪？ | **A** 工具元素旁 `_timeout_ms`。**B** `_meta.timeout_ms`，inst 會忽略、只有 agent 讀。**C** 通用 inst 欄位。 | **A**。模型看不到私有欄位，`_meta` 繼續是純 inst，也不推翻執行者管時限的分工。 |
| 2．工具預設幾秒？ | **A** 60 秒。**B** 120 秒。**C** 不限。 | **A**，但工具可覆寫。有限預算讓卡住的工具能結束，慢工具另外明示需求。 |
| 3．引擎連敗幾次停、怎麼恢復？ | **A** 三次，加入 continue.json 等人 touch。**B** 五次。**C** 一直試。 | **A**，沿用現有暫停機制，不加新狀態；errors 成功清零，暫停時也歸零。恢復限定 touch，不能新 input 自動解鎖；加 waits 的規則例外也需同意。 |
| 4．整格硬上限誰管？ | **A** 外面的 run／kernel，等 kernel 落地。**B** kernel 每 tick 查 elapsed。**C** agent 自量。 | **A，現在先不做**。必須由另一進程處理，agent 自量抓不到自身卡死；日後 300 秒起、記錄停排，不自動重跑中斷的 act。 |
| 5．waits 這輪加 until 嗎？ | **A** 不加。**B** 加可選 until；過期把該條劃掉，記一則失敗給模型，不能假裝結果到了。 | **A**。先保留可無限等待的人工 pause；非同步工作的有限終態交給 owner，有需要再補通用等檔期限。 |
