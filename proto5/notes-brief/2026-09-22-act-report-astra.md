# act 工具執行方式調查報告（精簡版）
完整版：[../notes/2026-09-22-investigations/2026-09-22-act-report-astra.md](../notes/2026-09-22-investigations/2026-09-22-act-report-astra.md)

## 結論

普通工具在 proto2、proto4-7、proto5 都是在一次 `act` 裡串行跑完。這是實作選擇；tool 訊息契約要求每個 call 配對結果，沒有要求等待時占住原 cpu。

先分清三件事：工具在哪跑、agent 是否退出讓位、模型等真結果還是先拿收據。**B 是讓出 cpu 但模型仍等結果；D 是先回收據，模型可以繼續。**兩者可以共用背景執行器。

本報告是靜態閱讀，沒有測試、啟動服務或改程式。涉及崩潰及排程競態的是推論。proto5 調查時已有未提交的 agent 實作，不能把工作樹現況當成已發布版本。

## 最重要的 26 件事

### 歷代工具怎麼跑

| # | 事實 | 對這次設計的意思 |
|---|---|---|
| 1 | proto2 普通工具在 act 串行跑完，整批結果最後才存 history；自訂 shell 沒有統一 timeout 或 returncode 格式。 | 中途崩潰可能重做已完成的工具。 |
| 2 | proto2 的 `fs.sh` 預設 60 秒、最多 120 秒；`jobs.run_long` 先回收據，另跑工作，期限約 3600 秒。 | 長短工具曾分流；長工作收據不是完成證明。 |
| 3 | proto2 的 jobs、think、branch 都有背景提交機制；完成後先存 side result，所屬 hook 有回文字才注入 user 訊息。 | async 不保證每種錯誤都會再餵給主模型；結果、喚醒、續跑三段缺一不可。 |
| 4 | proto3／3-1 是記憶體等待原型，沒有真正工具執行器；3-2 才在 act 同步叫一支 Janet 工具函式。 | 不能用 proto3 的 LLM queue 證明模型工具已非同步化。 |
| 5 | proto4-2／4-3 同步等 POSIX child；4-4 的一個 form、4-6 的一個 step 內也可以長時間阻塞。 | 「一格一動作」不等於「一格很短」。 |
| 6 | proto4-5 的 LLM dispatcher 開背景 worker 後返回，worker 才同步問模型、寫結果；worker 死且沒結果就記失敗，不自動重送。 | kernel tick 短靠派工方式，module 本身不保證非阻塞。 |
| 7 | proto4-7 的 act 串行跑整批，每工具 60 秒、結果預設截到 8000 字元；壞參數、不存在、啟動失敗都回 tool。 | LLM 有 ask／wait 分格，工具仍同步。 |
| 8 | proto5 的 act 串行跑整批，arguments 原字串送 stdin，stdout 整段返回；目前不限時、不截輸出，think 也同步問模型。 | 單一工具不回就卡整批；工具失敗會回 tool，agent 本身仍正常回 0。 |

### cpu、等待與暫停的真實意思

| # | 事實 | 對這次設計的意思 |
|---|---|---|
| 9 | aos cpu 是常駐 `aos-run` 行程，不是硬體核心；一次開一個直接 child 並等它退出。 | 工具即使幾乎不耗實體 CPU，也能占住 aos cpu。 |
| 10 | kernel 的行程是 inst 加外部狀態；agent 每次呼叫只走一格。kernel tick 和 agent tick 是不同呼叫。 | 退出後要靠落盤狀態續跑，不能保留本次記憶體等待。 |
| 11 | quantum 預設 5，算完成的 run 次數；interval 預設 1 秒，通常從上次完成後算。 | 都不是格內搶佔期限，改 cpu 的 inst 也不會殺掉當次 child。 |
| 12 | 0 表示本次正常；100 表示邏輯行程完成；101 表示本次已退出、正在等。 | 101 可讓其他排隊者先跑；沒人排隊仍可能留在 cpu 反覆輪詢。 |
| 13 | 舊 step 宣告 `wait_for` 的當格先成功、pc 前進、回 0；下次檔未到才回 101，檔到了同次繼續下一格。 | 等檔沒有 timeout 或主動事件喚醒；kernel 只看到 101，不知道等哪個檔。 |
| 14 | agent 格內阻塞拖住同顆 cpu 的其他行程；其他 cpu 可繼續。module hook 若阻塞，則拖住 kernel 後續排程。 | 背景 worker 和在 kernel hook 裡直接跑工具，影響完全不同。 |
| 15 | 舊 kernel 沒用 daemon 的 running 欄位擋換人。依完成次數換檔時，舊 child 可能還跑著，舊行程卻已回 queue 被另一 cpu 接走。 | **同一邏輯行程可能重疊執行，這是未實測的靜態推論。**agent 無鎖的前提需要交接保障。 |
| 16 | 使用者草稿中 pause 讓 agent 狀態機不前進，外部工作照跑、結果照存；stop 則 unregister。 | 草稿未選定 thread、工具 async 或阻塞上限，也未要求 pause 殺工作。 |

### proto5 能接什麼、不能保證什麼

| # | 事實 | 對這次設計的意思 |
|---|---|---|
| 17 | state 只有 idle／think／act；input 目前只在 idle 收。 | B 可留在 act 分送出、收回兩階段；D 的完成 input 可能延後才讀。 |
| 18 | waits 是走格前的門；多條都清空才開，agent 目前只劃不加。每條可等 exists 或 mtime，路徑可 any 或 all。 | B 若自己登記結果等待，必須改 waits 所有權契約。 |
| 19 | consume 會把到達檔改名 `.done`；只表示已消費。 | 若後續還要按原路徑讀結果，不能先 consume；檔存在也不代表成功或屬於本輪。 |
| 20 | 單檔用暫存檔再 rename，history 先存、state 後存；自癒能救 history 已寫但 state 未寫。 | 救不了工具已做、history 未寫；跨檔與外部副作用不是一筆交易。 |
| 21 | repo 要求 tool 訊息依原 calls 順序接回；同 id 配對是訊息要求。 | 可以晚點補齊真結果，不必同步等；並行執行也得按原序收回。 |
| 22 | 工具本來就是子進程；`run_target`、`run_inst` 都同步。on_spawn 是控制 child 的鉤子，並非 async API。 | 加 thread 後仍 join，就沒有讓出 aos cpu；跨格存活需要獨立 worker 與落盤協議。 |
| 23 | 工具元素只移除 `_` 開頭的頂層欄位再送模型；`_meta` 是 inst，未知 inst key 會被忽略。 | 裸 async 會漏送模型；把 timeout 或 cpu 塞進 inst 不會自動生效。 |
| 24 | 工具與 LLM 可共用 id、原子結果、queued/running/terminal、去重、失聯與容量骨架。 | payload、可否重試、資源限制各不同；結果接成 assistant、tool 或 user 仍由 agent 決定。 |
| 25 | 目前 inst 的 `$env`、相對路徑以 agent 的執行上下文解析。 | 移給 worker 後須明定傳原始 inst 加上下文，還是已解析內容，否則環境會偷偷變。 |
| 26 | 沒有既定「每格最多幾毫秒」。小工具也可能因大目錄、遠端檔案或輸出量而慢；串行 act 約為各工具耗時相加。 | B 縮短占住 agent cpu 的時間，C 可能縮短整批工期，D 改變模型等待語意；先決定要保護誰的延遲。 |

## 五種方案與恢復成本

| 方案 | 執行及模型看到什麼 | 代價、恢復與期限 |
|---|---|---|
| A：一格同步跑完 | 串行執行，整批真結果接 history，再 think。狀態最少、副作用有固定順序。 | 占住 cpu，耗時相加；崩潰可能重做整批。每工具 timeout 才能產生對應失敗回覆。 |
| B：交 tool cpu | act 存批次／call 對應、提交請求、登記 waits，未齊回 101；齊了按序接真結果。 | 多排隊與輪詢；需穩定 id、pending、重入對帳。worker 管執行期限，dispatcher 管失聯；失敗也必須有終局結果讓門打開。 |
| C：agent 內 pool | 獨立工具並行、最後 join，結果重排後整批接回。 | 不讓出 aos cpu；並行副作用、取消與 child 清理更難。想讓 agent 退出，就需要 B／D 的跨呼叫協議。 |
| D：收據加完成 input | 立即把接單收據當 tool；本批補齊後模型可繼續。完成後另注入 user。 | 接單不是成功；需 job id、提交與通知去重，失聯／逾時／取消也要通知，input 目前只在 idle 收。 |
| E：各工具選 A／B／D | 短工具同步、需真結果者送 cpu、長背景工作先回收據。 | 混合批次與恢復最複雜；同批只要有 B，模型仍得等它，其他收據不會讓整輪提早走。 |

## 文件跟程式對不上的地方，以及契約沒有保證的事

原報告沒有把以下全部判作文件錯誤；有些是尚未落地的方案或容易誤解的邊界。

| 重點 | 必須看清的落差 |
|---|---|
| 1．README 與工作樹 | README 仍說程式沒寫，實際已有未提交 agent 實作；現況是同步且不限時。 |
| 2．async 構想與現況 | 規範中的 async 是收據加 input，並非已完成的 tool cpu 真結果等待；不能混稱同一功能。 |
| 3．waits 只劃不加 | B 的「agent 提交後自己等結果」會撞上現行契約，必須修改或另存 pending。 |
| 4．自癒不是只執行一次 | 已做工具尚未存 history 仍會重跑；改逐筆寫 tool 還會讓只看尾巴的自癒誤認整批完成。需外存結果再整批接，或檢查全部 call id。 |
| 5．原子檔不等於完整交易 | consume 後未存 waits 可能永遠等已搬走檔；history 存了但 input 未改名會重收；多 worker 寫同一 input 會覆蓋。需要可對帳、去重與獨立訊息。 |
| 6．排程不保證單一執行者 | 換 inst 不停止舊 child；舊多 cpu 可能與 agent「同資料夾不可並跑」前提衝突。 |
| 7．有 timeout 參數不代表有用 | agent 沒把工具期限傳給 run_inst。工具另開 process group，外層殺 agent 也不能保證工具一起死。 |
| 8．pool 不能只包一層 | 目前捕錯會改共用的 sys.stderr，多 thread 可能互相干擾；pool 等待逾時也不等於 child 已終止。 |

所有方案都有「副作用已做、結果沒落盤」的窗口。可靠恢復要靠工具冪等鍵、查詢完成狀態或承認結果不明，不能把自動重試稱為只執行一次。舊 LLM 有去重範例，但 spawn 與記 pid 間也有窗口。

## 要使用者拍板的問題（全部 12 題）

**原報告刻意保留選項、不代選，以下沒有 astra 已選的方案。Claude 的具體建議另見 act-summary。**

| 題號／問題 | 選項與取捨 |
|---|---|
| ① 慢工具沒完，模型繼不繼續？ | 等真結果（A／B／C）：語意直接，但停在工具邊界。先收據（D）：可先做別的，需管理未完成工作與通知。 |
| ② 解決占住 cpu，還是整批太慢？ | B：讓出 cpu，增加提交／輪詢。C 並行 join：可能縮短整批，但仍占本次呼叫。兩者合併：都解，狀態更多。 |
| ③ 全工具統一還是各自選？ | 統一 A／B／D：規則少，有些工具承受不必要成本。E 混合：各自合適，但結果、收據、恢復更複雜。 |
| ④ 模式是一個標籤還是拆維度？ | 單一 sync／async／cpu：好懂，但混合執行地點與回覆語意。拆 backend＋回覆方式：表達完整，設定更多。 |
| ⑤ 執行器放哪？ | 獨立 cpu／服務：與 kernel 分離，須管存活。kernel module 只派工：沿用 LLM 接線，hook 必須短。agent 自管 worker：入口少，恢復清理集中在 agent。 |
| ⑥ 同批 calls 可否並行？ | 全串行：副作用順序穩、耗時相加。只並行明確獨立者：較快，要定判準。全並行：吞吐高，可能改變讀寫結果。 |
| ⑦ 格、工具、排隊各等多久？ | 只設工具期限：能回逾時，但整批仍久。另設整格／排隊期限：延遲有界，須定未完成工作收尾。不限：簡單，接受永久等待。 |
| ⑧ 結果不明怎麼辦？ | 自動重試：好續跑，可能重複副作用。回結果不明給模型／人：不盲重送，需後續判斷。只重試冪等工具：折衷，工具須保證。 |
| ⑨ async 結果何時進記憶？ | 只在 idle 收：改動少但延後。在安全格邊界也收：反應快，不能插進未補齊的 tool-call 區段。 |
| ⑩ pause／stop 怎麼對待背景工作？ | 依草稿跑完、照存結果：可恢復接續，仍耗資源。另提供取消：可止損，須區分已取消、已完成、結果不明。 |
| ⑪ tool 與 llm cpu 共用多少？ | 只共用檔案生命週期／錯誤外框：各自語意，兩種 payload。共用整個服務：少一套，但容量、重試、取消與型別都需通用化。 |
| ⑫ 要保證同 agent 絕不並跑嗎？ | 維持操作前提：機制少，但有舊排程重疊窗口。加所有權／鎖或交接確認：保障明確，須定崩潰接手方式。 |
