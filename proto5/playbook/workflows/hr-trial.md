# 試用 → 評分 → 調薪：一個位子能不能換便宜模型

← [workflows 索引](README.md)｜規範 [spec/team/hr.md](../../spec/team/hr.md)｜來源 [HR 部報告 09-25](../../notes/2026-09-25-hr/README.md)

**適合什麼活**：一支團隊已經用強模型做得出來、有**機械檢查得出好壞**的任務（例子 1 導入、arknights 一批角色補檔），想知道某個位子（模板）換成笨模型還行不行。
**不適合**：還沒有評分指令的任務（先做評分器，品管部的事）；一次只跑得起一次、結果起伏很大的任務（先想辦法固定初始狀態）。

## 三步

```text
① 試用（hr trial）         ② 評分（可插的評分指令）             ③ 調薪（規則，不用人判）
複製團隊、只換一個成員的模型 → 專案副本上跑機械檢查＋（有的話）評審 → 分數 ≥ 強模型基準 − margin 且機械全過
同一份任務集、同一個初始狀態    stdout 最後一行 {"score", "mech_ok"}    → 薪資表「最低通過」換成這顆（附證據編號）
```

1. **先定任務集**：一個資料夾放 `project/`（初始狀態，每次整份複製）、`routes.json`（要不要讓門房直接派，決定試的是哪個位子）、`taskset-*.json`（幾句話、等幾張單、時限、評分指令）。照抄 [`examples/hr/ex1/`](../../examples/hr/ex1/)。
   - 試**工人**：門房規則直接派給工人，領隊不經手，分數只反映工人。
   - 試**領隊**：不給門房規則，人那句話落穿給領隊，領隊自己寫單子；工人留強模型，分數主要反映領隊寫的單子好不好。
2. **先跑強模型一次當基準**（判定印「基準」）。基準沒有機械全過＝任務集或評分指令有問題，先修，別往下試。
3. **再跑便宜的**，一個配置 1 次先看；「通過」只是候選，真要換之前再多跑幾次（S 軸 10 次才給分）。
4. **人看 `hr trials` 決定換不換**，換就 `hr set NAME --model X`。薪資表不會自動改名冊。

## 在哪個點停下來看

- 便宜模型**分數一樣、token 反而多**（例子 1：deepseek 10 萬 vs astra 6 萬）：錢還是省（單價差很多），但多出來的步數是可以寫成程式的地方——往「換程式」那一步走之前先看它多做了什麼。
- 分數掉了、機械沒全過：看 `trials/tr-NNNN/team` 的 `aos-team mail`、`task show`，是模型能力不夠還是派工信寫得不清楚；後者改派工信再試，不算這個位子不行。
- 三個位子都換成笨模型都過了：下一步是把重複的步驟收成工具（研發部），不是再找更笨的模型。

## 哪裡可再用

- 評分指令是一支普通程式：arknights 用 `eval.sh`、別的產線用自己的；只要最後一行印 `{"score": 0~100, "mech_ok": bool}`。
- `trials.jsonl` 一行一次、帶 token 與秒數：財務部可以直接拿去算「每個位子一件多少錢」。
