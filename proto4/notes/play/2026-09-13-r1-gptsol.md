# aos 新手試玩報告

**總評：核心概念很有趣，逐格執行也真的看得見，但「第一個自己的程式」仍需要知道幾個 README 沒接好的路徑與常駐細節。容易上手 3/5｜容易理解 3/5｜複雜度隱藏 2/5｜外層控制 4/5｜少背東西 2/5。**

## 1. 只看 README 架起來

- 現象：從開始讀到看到第一份 `aos-kernel ls` 約 17 秒，主要是 daemon、init、add、`cd`、ls 共 5 個指令 → 我期待：原型至少要十幾分鐘才能架好 → 建議：保留這條短路徑，最好再包成一支 `aos-kernel-boot`。
- 現象：`aos-kernel ls` 必須先 `cd /tmp/play-gptsol/kernel`，不能直接給家目錄 → 我期待：像 `aos-daemon-ctl --home H ls` 一樣能指定目標 → 建議：補 `aos-kernel --home K ls`，或讓它自動從參數找家。
- 現象：我需要回頭再看一次 `docs/kernel.md` 才確認 `AOS_DAEMON_HOME` 必須讓 daemon、ctl、kernel 對上 → 我期待：設一次就一路傳下去 → 建議：開機指令統一管理 home，不要讓新手同時理解 `--home` 與環境變數的繼承差異。
- 現象：照 README 寫 `aos-daemon &`，啟動它的非互動 shell 結束後 daemon 也死了 → 我期待：丟到背景就會繼續活著 → 建議：明寫 `&` 只適用持續存在的終端，並給 `nohup`、systemd 或前台常駐範例。
- 現象：daemon 死後 `aos-kernel ls` 仍根據舊 state 顯示 CPU `running`，只有 `aos-daemon-ctl ls` 會警告「daemon 沒在跑」 → 我期待：kernel 畫面會直接標示硬體已離線 → 建議：`aos-kernel ls` 頂端加入 daemon alive/stale 狀態。

## 2. 自己寫逐步 Lisp

我的程式共有 7 個 form：載入 aos、`def`、`defn`、寫 `before.txt`、`aos/call-dir`、取 JSON value、寫 `after.txt`。

- 現象：README 的 `(import ./src/aos :as aos)` 放進外部資料夾後找不到模組；絕對路徑也被 Janet 當成模組名處理 → 我期待：README 給的 import 能直接用在自己的專案 → 建議：提供外部專案範本，明講要複製／連結 `aos.janet`，或由 `aos-step` 自動提供模組路徑。
- 現象：命令列直接設定 `JANET_PATH` 可讓普通 Janet 找到 `aos`，但經 `aos-step` 執行仍找不到；最後是在 `/tmp` 建 `aos.janet` symlink 才成功 → 我期待：同一套 Janet 模組尋找規則處處相同 → 建議：文件說明 `aos-step` 的模組載入邊界，最好不要求使用者知道 `JANET_PATH`。
- 現象：`aos/call-dir "./json-maker"` 預設尋找 `.aos/inst.json`，我放在資料夾根的 `inst.json` 因而得到 `kind "usage"` → 我期待：叫「call-dir」時會自然找根目錄的 `inst.json` → 建議：在範例旁直接標明預設目標，或提供明顯的資料夾 scaffold。
- 現象：加上 `@{:dir-target "inst.json" :read "./json-maker/result.json" :json true}` 後，shell 成功產生 JSON，結果也解成 Janet table → 我期待：`:read`＋`:json` 能一次完成讀檔與解碼 → 建議：這組介面很好用，值得放一個完整的外部程式範例。
- 現象：把 JSON table 直接交給 `string`，寫出的只有 `<table 0x…>` → 我期待：得到可讀的 JSON 或 table 內容 → 建議：README 補一個「解碼後如何取欄位／重新編碼」的小例子。
- 現象：前 7 次 `aos-step` 各跑一個 form 並讓 `pc` 從 0 到 7，第 8 次才回 100 → 我期待：最後一個 form 跑完當次就回 done code → 建議：保留目前語意也可以，但在範例旁強調「N 個 form 需要 N+1 次呼叫才收到 100」。
- 現象：丟入 `kernel/procs/42.json` 後，kernel 自動排程、跑完並搬到 `procs/done/42.json` → 我期待：完成的行程會被收走，不再占 CPU → 建議：這段流程清楚，`aos-kernel ls` 若能顯示最近完成項會更容易確認。
- 現象：kernel 啟動 CPU 的瞬間，`aos-kernel ls` 曾短暫顯示一顆 `running`、另一顆「沒插上」，下一輪便補齊 → 我期待：init 完便一次看到兩顆 CPU → 建議：顯示 `starting` 或「下輪重試」，避免像故障。

## 3. 故意弄壞三樣

- 現象：`43.json` 少 `cwd` 後，被搬到 `kernel/procs/bad/43.json`，`kernel.log` 寫「退件 43.json（沒寫 cwd）」 → 我期待：`aos-kernel ls` 直接告訴我退件及原因 → 建議：ls 增加 bad 數量與最近原因；目前只看佇列會以為檔案消失了。
- 現象：把 `spit` 寫成 `spitt` 時，stderr 明確顯示 `form 2 失敗："unknown symbol spitt"`，`pc` 留在 2，下一次仍重試 → 我期待：知道哪格錯、修好便能繼續 → 建議：這個錯誤已足夠清楚，只需補一句「編號是 0-based」。
- 現象：錯字的 `.aos-step/error` 還保存 stacktrace，`--status` 也能看到相同原因 → 我期待：錯誤不會只閃過一次 → 建議：保留目前雙重入口，但 status 可只給短訊息，完整 stacktrace 留在檔案。
- 現象：程式已跑兩格、`pc=2` 時在最前面插入 form，系統沒有警告；舊的 A 被重跑，新插入的 `INSERTED` 永遠沒跑，最後仍是 done → 我期待：程式內容改變後拒跑、要求 reset，至少不能靜默錯位 → 建議：狀態中保存程式 hash；內容變動便提示 `--reset` 或要求明確接受位移。
- 現象：中途插 form 是三個故障裡最危險的，因為沒有退出碼或錯誤訊息 → 我期待：最容易造成錯資料的情況應最醒目 → 建議：把來源版本檢查排在下一版高優先級。

## 4. 五個問題

### ① 容易上手：3/5

- 現象：OS 架起來只需 `aos-daemon`、`aos-kernel-init`、`aos-daemon-ctl add`、`cd K`、`aos-kernel ls` 五步 → 我期待：能用一條 boot 指令完成 → 建議：新增 boot，但保留分步指令供理解與除錯。
- 現象：第一個程式還要準備 `prog.janet`、子資料夾 `inst.json`、shell、模組連結、kernel 用的 inst，再手動呼叫 8 次 `aos-step` → 我期待：複製一個範本後只改程式內容 → 建議：提供 `aos-step-init DIR` 或完整 starter directory。

### ② 容易理解：3/5

- 現象：`pc` 很直觀，`aos-step prog.janet --status` 的 `pc 4 / n 7` 一眼就懂 → 我期待：它是下一個 form 的位置 → 建議：維持現在簡單的狀態格式。
- 現象：daemon＝硬體、`add`＝插 CPU 尚可理解，但 `--ncpu 2` 之外還另有跑 kernel 的第一顆 CPU；daemon 表實際有三支 `aos-run` → 我期待：`ncpu=2` 是整台機器總共兩顆 CPU → 建議：文件與 ls 分開標示 kernel CPU 和 process CPUs。
- 現象：`procs/42.json` 看起來更像工作描述或指令，不像一般理解的「行程」 → 我期待：行程有 pid、狀態和程式，而不是一份會被搬家的 inst.json → 建議：第一次出現時用一句話說明「這版以 inst.json 本身代表行程」。

### ③ 複雜的東西有沒有藏好：2/5

- 現象：為理解時間片，README 迫使我知道 `runs_at` 以及 `runs-runs_at` → 我期待：只需知道 quantum 是幾格 → 建議：主教學只講行為，演算法移到進階章節。
- 現象：我被迫知道切換行程靠 hard link＋rename，也必須知道 `--home` 不會傳給子孫 → 我期待：這些是實作者細節 → 建議：移到「內部原理／除錯」頁，快速入門只保留可靠操作方式。
- 現象：daemon 死後 state 仍像活的，逼我理解 pid、state.json 更新週期與常駐 shell → 我期待：工具自己區分 live 與 cached → 建議：所有 ls 統一顯示資料新鮮度。

### ④ 外層控制結構簡單但全面：4/5

- 現象：`init`、`add`、`ls`、`step`、自動 `tick` 已足夠完成建家、執行、觀察與收尾 → 我期待：原型工具少而各司其職 → 建議：維持拆分，不必合成一支巨大 CLI。
- 現象：缺的是一鍵 boot、顯式 enqueue、查看 bad/done；目前投遞要 `cp inst.json K/procs/42.json` → 我期待：日常動作都有正式指令 → 建議：補 `boot`、`submit`、`ls --bad/--done`，不要讓檔案操作成為主要 UI。
- 現象：`aos-step --reset` 與 kernel 的完成收走不重疊，各自語意清楚 → 我期待：step 管程式狀態，kernel 管排程 → 建議：保留這個邊界。

### ⑤ 要背的東西少：2/5

- 現象：日常至少遇到 `inst.json`、`prog.janet`、`.aos-step/pc`、`env.img`、`error`、`done`、`state.json`、`kernel.log`、`procs/bad`、`procs/done` → 我期待：只需記程式與 inst，其餘由 status/ls 呈現 → 建議：把內部檔名藏到查詢指令後面。
- 現象：同時要記 `PATH`、`AOS_DAEMON_HOME`，外部載入又撞到 `JANET_PATH`／本地 `aos.janet` → 我期待：安裝一次後不再管載入路徑 → 建議：正式安裝 CLI 與 Janet 模組，讓產生的 inst 自帶必要環境。
- 現象：常用旗標包含 `--home`、`--interval-ms`、`--quantum`、`--done-exit`、`--dir-target`、`:read`、`:json` → 我期待：大多有一致預設 → 建議：提供一份 home 設定檔，程式只寫偏離預設的項目。

## 前五名最該改的

1. 外部專案能直接載入 `aos`，並提供可複製的完整 starter directory——**中**。
2. 偵測運行中的 `prog.janet` 是否改變，避免 `pc` 靜默錯位——**中**。
3. 補 `aos-kernel-boot`，統一 daemon home、PATH、init 與第一顆 CPU 的啟動——**中**。
4. 讓 `aos-kernel ls` 顯示 daemon 是否存活、bad 原因與最近 done——**小**。
5. 補正式的 `submit/enqueue` 指令，不再要求新手手動 `cp` 到 `procs/<pid>.json`——**中**。
