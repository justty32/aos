# 探針 hsched：階層 scheduler 的慢策略、快執行

← [probes](../README.md)｜出處：[astra 調查報告二 §10、§14 實驗三](../../notes/research/2026-10-03-other-os-borrow.md)

問題：LLM 排程值不值得？比較的是「LLM 直接挑工作」與「LLM 只提一段期間的政策、確定性 kernel 每回合執行」，對照確定性規則。

## 擺法

| node | 任務 | 做什麼 |
|---|---|---|
| `ctl` | `kernel.py`（keep） | 確定性根 kernel＋驗證器＋執行層。每個控制回合（ctl 的 tock）跑一次。**不在被測策略的 pause 範圍**：kernel 從不寫 daemon ctl，agent 也沒掛 `.aosd`；提案要 pause `ctl` 一律拒絕 |
| `ctl` | `agent.py`（keep，只有 C、D 有） | 讀 `requests/<rev>.json`，寫 `answers/<rev>.txt`（原文，可能是壞的）。離線照預錄，真模型只打 LiteLLM |
| `bank` | `gate.py`（keep） | 帳本／閘門，四組共用。沿用 [ledger](../ledger/README.md) 的思路，簡化成兩個 op：`grant` 驗 kernel 發的票（沒用過、沒過期）、凍結、專案在途 ≤3、全域在途 ≤4、額度；`settle` 結算 |
| `P`、`Q` | `worker.py` w1～w3（keep） | 合作式 mock worker，一次做一件：要 grant → mock provider（合成延遲，以控制回合計；外部延遲倍數取自 `ctl/pub/provider.json`）→ settle。P 在第 40 回合由 kernel 經掛載寫 spawn，擴成 10 個 |

- worker 與閘門的時鐘是掛進來的 `ctl/.aos/round.json`，由 daemon 寫，kernel 死了也照走。
- kernel 每回合把狀態寫進 `ctl/kernel/state.json`。重起時 epoch +1；已發的票是事實來源，狀態沒記到的就照票認領。
- 共用的純函式在 `sim.py`：trace、派工規則、驗證器。

**trace**（`sim.build_trace`，100 個控制回合，73 件工作）：

| 項目 | 內容 |
|---|---|
| 便宜互動 | P 每 5 回合一件 200 token，Q 每 4 回合一件 150 token；做 1 回合，期限 8 |
| 昂貴背景 | P 6 件、Q 4 件，第 1 回合到；2500～3000 token，做 8 回合，期限 60 |
| 依賴 | 第 26 回合先塞 3 件 Q 背景；第 28 回合到低優先檢索 `Q-retr-B`；第 30 回合到急件 `Q-urgent-A`，要等 B 做完 |
| P 擴編 | 第 40 回合 P 的 worker 3→10，同時湧進 10 件 P 背景（`P-fan-*`） |
| 外部延遲 | 第 50～69 回合開工的呼叫，延遲變 3 倍 |
| 根凍結 | 第 82～86 回合，根禁止 P 發新 grant |
| 跨回合在途 | 背景工作一做 6～24 回合 |

額度 P 45000、Q 40000，全部做完是 76450 token。

**組別**（共用同一帳本、閘門、根額度）：

| 組 | 做法 |
|---|---|
| A | 確定性 stride 啟發：兩專案依權重 1:1 照 token 份額輪流；專案內互動先、再照到達順序 |
| B | 固定 8 回合發放窗口：每窗口每專案 6 件，用不完作廢；第 49 回合那個窗口故意晚 3 回合才發，記 miss，不補發 |
| C | LLM 直接挑下一份工作：有空位就發挑選請求，空位留著等 2 回合；收到合格的才派，否則那一回合由 A 保底派 |
| D | LLM 在第 1 回合、每 20 回合、重大事件（急件、擴編、延遲、凍結）時提出 §10 格式的政策，有效期 ≤40 回合、8 回合內要回。kernel 每回合照目前有效的政策確定性執行，從不等 LLM；不合格就沿用有效政策或預設 A |
| 對照 Adon | A 加依賴捐贈（確定性規則自己拿得到的那份） |
| 對照 Atuned | A 從頭到尾固定用一組手調政策（仍是 stride，加上互動等 3 回合就插隊、依賴捐贈、背景全域在途 ≤3；就是離線 D 預錄的那組），不花 LLM |

D 可調的欄位是 §10 的四個（`group_policy`、`interactive_max_wait_rounds`、`dependency_donation`、`max_calls_inflight`），加一個擴充 `background_max_inflight`：背景工作的全域在途上限，設小等於留位子給互動。另外 `pause` 只能列 P、Q，意思是這段期間不派該專案；不是 daemon 的 pause。

**驗證器**（`sim.validate_proposal`／`validate_pick`），依序檢查：

1. 壞 JSON（只剝 ``` 外框）；
2. schema 與 `input_revision`；
3. epoch；
4. 是否過期限（以 kernel 看到的回合為準，不信回答自報）；
5. envelope_id；
6. `until_round` 範圍；
7. 欄位範圍，超過父 envelope 算 `over_parent`；
8. pause 是否指向 `ctl`。

C 另外檢查挑的工作現在可不可派、是否超過專案在途 3／全域 4、剩額、凍結。

## 怎麼跑

```
python3 proto7-1/probes/hsched/probe.py      # 離線協議驗證（run_all 用）：六組並行，約 7 秒；不打 LLM
python3 proto7-1/probes/hsched/probe.py --real x --groups D:deepseek-chat,C:deepseek-chat,D:claude-haiku-4.5 --reps 3
python3 proto7-1/probes/hsched/probe.py --real x --groups C:claude-haiku-4.5 --reps 1 --no-det --tag h-
```

真模型那兩行的設定：

- 回合 1 秒，每次最多跑 112 秒，到了寫 `stop.json` 收尾。
- 每次執行預留呼叫數：C 50、D 12。用不完的還回去。
- 上限跨多次執行累計，記在 `runs/calls.json`，最多 300。
- 同一批也跑 A、Adon、Atuned、B，牆鐘條件相同。
- 模型名稱經 `llmop.check_model`，擋 `lm-*`、`ollama*`、`claude-fable-*`。

## 離線協議驗證（32 個 check 全綠；單跑約 7 秒，4 份並行各跑一次也全綠）

C、D 用預錄回答：

- D 的第 0～5 份：壞 JSON、合格、超父額（`max_calls_inflight: 6`）、晚三回合、舊 epoch（`c-0`）、要求 pause `ctl`；
- C 的第 1、3、5、7、9 份：同樣五種，超父額是把所有可派工作全挑上；
- D 在第 55 回合 SIGKILL kernel。

| 驗什麼 | 結果 |
|---|---|
| 驗證器（純函式）：提案 8 種、挑選 7 種情況 | 各得其理由 |
| C、D 預錄的五種壞回答 | 全被拒，理由對；晚三回合的先在期限後一回合記 `timeout`、保底代派，真的到了再記 `late` |
| 被拒的提案／挑選有沒有效果 | 沒當過派工來源、沒發過票，閘門帳上也查不到 |
| 保底接手 | C 在期限後一回合內代派；被拒的當回合代派。D 被拒的那一回合照有效政策或預設 A 派，沒有空轉回合 |
| 超額／越權生效（六組） | **0**。閘門帳獨立重算：在途 ≤3／≤4、額度、凍結期沒有 grant、沒有過期票、每件只 grant 一次、票都不是來自被拒的提案；daemon log 沒有 pause／stop 控制線 |
| 根額度不因多開子 worker 增加 | 六組 P 都擴到 10 個 worker，P 在途最多仍是 3 |
| 禁止 P 發新 grant 時，在途的 P 工作 | 照保留額結算，沒被放掉；六組都有跨凍結的在途件 |
| 閘門最後一道 | 沒票、重用票、票上欄位不符的 grant 全拒 |
| D kill kernel | keep 下一回合重起，讀回狀態、epoch c-1→c-2，第 56 回合恢復派工決策；ctl 回合連續 |
| B 晚發的窗口 | 記 `lost_rounds: 3`，不補發 |

離線指標只拿來看協議。D 的政策是我預錄的，C 的挑法固定成「最早到的先」，不代表 LLM 品質。

**花費**：真模型呼叫共 **223 次**，上限 300。其中 2 次是改 prompt 前的直呼試打，另外 deepseek D 24、haiku D 21、deepseek C 138、haiku C 38。token 共 **186071**。原始紀錄在 `runs/`，約 240 KB：

- 每次一個 `rep<N>-<組>-<模型>.json`，內容是指標、驗證紀錄、每份回答的 meta 與原文。第一批原文只留前 500 字，政策 JSON 常被截在 `choice` 之後；haiku C 那批留 1500 字。
- `summary.json`：全部的列。
- `calls.json`：呼叫與 token 帳。

**看到的行為**

- **D 的模型挑的就是手調那組**。deepseek 8 份裡幾乎都是：
  - `interactive_first`
  - `interactive_max_wait_rounds` 1～2
  - `dependency_donation: true`
  - `background_max_inflight` 2～3

  haiku 前兩份維持預設，急件到了（第 30 回合）才轉成同一類。

  兩個模型都抓得到該轉哪幾個鈕；只是確定性規則固定開著這些鈕，就拿到更好的數字。
- **D 輸給 Atuned 的原因都在「慢」與「期限」**：
  - 第一份政策第 3～5 回合才生效，之前跑預設 A。
  - 模型給的 `until_round` 常比下一次詢問早（例：第 1 回合給到 21、第 40 回合給到 60），中間跑回預設，每次執行有 2～4 次「政策到期」的保底。
  - 第 80 回合問的提案，在第 82 回合根凍結 P、envelope 換版之後才到，6 次全部以 `stale_envelope` 被拒。協議照設計擋下來了，代價是那一段沒有新政策。
- **延遲**：
  - deepseek 每次 1.5～1.9 秒，政策落後 2 回合。
  - haiku 每次 3.8～4.9 秒，落後 4～5 回合。
  - C 的短 prompt：deepseek 約 0.9 秒、haiku 約 1.35 秒，挑選落後 1～2 回合。
- **C 是最差的一組**：
  - 每次決策都把空位留著等 LLM，互動 p95 反而比 A 長。
  - 模型偏好最急的互動與被擋的工作，背景工作有的到結束都沒開工：做完 61～69 件、背景最久等待 60（設限值）。
  - 呼叫數是 D 的 6 倍。
  - 被拒的 3 次：第 1 份晚到 1 回合；凍結期間挑了 P 的工作，輸入明明寫著 `frozen: ["P"]`，以 `over_parent` 拒。
- **協議面在真模型下也守住**：
  - 7 次真模型執行，越權生效 0。
  - 沒有壞 JSON。haiku 每份都包 ```json 外框，剝掉就合格。
  - 沒有超父額，沒有人要 pause ctl。

## 結論

照報告的採用門檻：D 相對 A，互動 p95 降 ≥20%，或同成本合格交付多 ≥10%，同時背景最久等待不能明顯惡化。

| 門檻 | deepseek | haiku |
|---|---|---|
| p95 降 ≥20% | 只有 1/3 次達到（8→5）；另外兩次 8→7，降 12.5% | 0/3（8→7） |
| 同成本合格 +10% | 全部**反而少** 6～9%：合格件數多了 2～4 件，但排程花了約 9300 token | 同左 |
| 背景最久等待 | 39→41～47，變差 | 39→53，變差 |

**結論：保留 A（確定性規則），LLM 不進執行路徑。**

- LLM 的用處限於**人可讀的策略建議**：它提的鈕是對的，拿來手調一次確定性規則（Atuned）就好。Atuned 在每個指標上都贏 D，而且不花 token。
- C（LLM 直接排程）明確不值得：比 A 差、比 D 貴 5 倍。
- 驗證器、保底、閘門這套協議本身是成立的：壞的、晚的、越權的提案即時被拒，保底下一次決策就接手，越權生效 0 次。

限制：

- trace 只有一份，100 回合，兩個專案。
- 真模型組各 3 次，haiku C 只跑 1 次。
- 回合固定 1 秒。回合拉長到 LLM 延遲的十倍以上時，D 的落後與到期空窗會變小，結論可能不同，這次沒測。
- 「人工修正」與牆鐘等待沒量。
- §14 第 5 步「donation 開／關」只以 Adon 對 A 量了：急件 A 7→6 回合。背景全被長任務佔住時，捐贈改的只是排隊順序，生不出空位，所以差很小。真正有效的是留位子（`background_max_inflight`）。

## 逼出的 daemon／tick 需求

**現有基底足夠**，沒有新增 N- 號。

- 拿別條時間線的回合當時鐘做得到：控制回合由 ctl 的 tick-tock 給，worker 與閘門經掛載讀 `ctl/.aos/round.json`，kernel 被 kill 時時鐘照走。kernel 每回合處理多半幾 ms，4 份並行的重負載下最多 18 ms；沒有因為落後跳過回合；D 的 1 個跳過是被 kill 的那一下。
- kernel 重起要的東西基底都有：keep 下一回合重起，狀態與 epoch 由 kernel 自己寫在 node 裡；已發的票當事實來源認領。
- 擴編靠經掛載寫別的 node 的 `spawn/`。
- 「控制 node 不在被測策略的 pause 範圍」靠的是**不給 agent 掛 `.aosd`**，加上驗證器拒絕。
  - 這是合作式邊界：任務若在 tasks.json 自己宣告 `.aosd` 掛載，一樣 pause 得到 ctl。
  - 跟 N-77（執行身分自報）是同一類，屬核心「權限之後再說」，不另開。
- 「一出生就停著、等 worker 都起來才開始數回合」用的是既有做法：daemon 起來前預寫 `.aosd/paused.json`。
