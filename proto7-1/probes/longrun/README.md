# longrun 探針

**是什麼**：兩條時間線。

- `a`（interval 100 ms）：一個長任務（`spawn/` 起一次，每 0.1 秒寫一行進度、寫 50 行、完全不看 tock），加上四個「每收到 tock 就要寫 `report-<回合>.json`」的 keep 任務，輪詢快慢和每回合做事的時間不同。
- `b`（interval 100 ms）：一個 each 任務，每個跑 1 秒，比 interval 長很多。

**想讓基礎設施露出什麼**：`tock.json` 是覆寫的，慢一點的任務會漏掉幾回合；長任務會不會拖慢回合；基礎設施知不知道誰這回合回報了；each 任務會堆積多少；kernel 想判斷「該回報卻沒回報」要讀哪些檔。

**結果**（跑了 3 次，數字幾乎一樣，a 跑 51 回合）：

| 回報任務 | 輪詢／每回合做事 | 漏掉 | 報告寫出時已經過了下一個 tick | 報告比下一回合的 tock 還晚 | tock 到報告的中位數 |
|---|---|---|---|---|---|
| rep_fast | 10 ms／0 | 0 | 0 | 0 | 6 ms |
| rep_mid | 50 ms／60 ms | 5（10%） | 33 | 27 | 108 ms |
| rep_poll | 150 ms／0 | 17（33%） | 0 | 0 | 75 ms |
| rep_work | 10 ms／150 ms | 19（37%） | 31 | 31 | 208 ms |

- 漏掉的回合，任務自己看得出來（`tock.json` 的 round 會跳號）。基礎設施看不出來：rounds.jsonl 只記 alive 和 ended。
- 長任務沒有拖慢回合：從第 2 回合起 tick 沒再起它，所以 tock 不等它，大多數回合會提前進場。不過機器很忙時（第一次試跑剛好碰上別組同時在跑），tick 到 tock 一次要約 1 秒，長任務 5 秒只跨了 3 回合。「長任務跨幾回合」完全看機器快慢。
- each 會堆積：1 秒的任務在 100 ms 的回合下，同時最多 7～8 個，穩定時約 6～7 個。回合實際週期約 147 ms，b 的 tock 從來不會提前。each 沒有「上一個還在跑就跳過」，也沒有並行上限。
- kernel 要判斷違約，得自己拿 rounds.jsonl 每行的 `alive` 去對任務資料夾裡自己約定的報告檔，還要自己定寬限：rep_mid 有 27/51 份報告比下一回合的 tock 還晚出來。
