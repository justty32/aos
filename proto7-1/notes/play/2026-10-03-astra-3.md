## 三、新問題

### 三-1　移出成員的到期 resume 漏清 acc，加回後用同一筆用量再 pause〔bug〕

**牽涉 S-17、S-18，並影響 S-01 的理由可理解性。這是第二輪二-7 修補的延伸漏處理。**

重現步驟：

1. kernel members 設 `["a"]`，budget_tokens=10、cool_rounds=5；先讓用量 0 成為基準，再寫 usage.tokens=20。
2. 等 kernel 對 a 下 budget pause；把 members 改成 `[]`，等 kernel 到期 resume。
3. 用量完全不改，把 a 加回；再做一次移出、到期、加回。可跑 [kernel/repro.py](2026-10-03-astra-3-evidence/kernel/repro.py)。探針用真 daemon／kernel，寫入合規 usage 檔精確控制數值，沒有 LLM 費用。

看到什麼：移出分支會清 `paused`，卻留下 `usage["team/a"]={"last":20,"acc":20}`。加回時增量為 0，kernel 仍用舊 acc 再下「用量累計 20 > 10」。純規則與真 daemon 都重現；可以反覆移出／加回，同一筆 20 tokens 反覆觸發冷卻。[removed-readd.json](2026-10-03-astra-3-evidence/kernel/removed-readd.json)、[pure-rules.json](2026-10-03-astra-3-evidence/kernel/pure-rules.json)。

這不只是「第一次看到不算舊帳」的 K-8 選擇：spec 第 9 節說冷卻 resume 後**累計歸零**，正常在冊分支確實有清，移出補丁分支漏了。前輪「移出仍須 resume」已做到，但完整冷卻週期未收完。

### 三-2　成員搬走令 roster 掛載斷裂，寫名冊直接殺掉整個 kernel〔bug〕

**牽涉 S-01、S-16、S-17、S-18、S-23。**

重現步驟：

1. members=`["a","b"]`，kernel 已掛到兩者 `.aos` 並寫好 roster；cap_tokens=100。
2. 把 a 的 usage.tokens 寫成 120，等 cap pause 成立。
3. 將 `team/a` 搬成 `team/moved-a`，暫不改 members；等下一個 kernel tock。重現同上 [kernel/repro.py](2026-10-03-astra-3-evidence/kernel/repro.py)。

看到什麼：`write_rosters → fs.write_json → os.makedirs` 在 `kernel-r1/mnt/a` 的斷鏈上丟 `FileExistsError`，kernel-r1 **exit.code=1**。該回合在快照／規則之前就中斷，其他正常成員的管理也被打斷；keep 之後起 kernel-r5 接手。[roster-broken-mount.json](2026-10-03-astra-3-evidence/kernel/roster-broken-mount.json) 留有完整 traceback、前後 state、exit、decisions。

同一次重現還看到：重掛依既知 M-2 建回 `team/a/.aos` 空殼；新 kernel 在空殼讀到 usage=0，對 a 下 cap resume，why 卻說「總額上限改了（用量 0，上限 100）」。cap 設定沒有改，搬走的真實 usage 仍是 120。**本條新 bug 是 roster 的非必要寫入失敗拖垮整個 kernel**；空殼與搬家換 id 不另拆成舊問題，錯誤恢復理由則一併記錄其觀察後果。

### 三-3　memory=1 仍全讀、全排歷史，輸出固定也會增加時間及峰值記憶體〔技術選型〕

**牽涉 S-01、S-16、S-19；S-17 的資源管理也看不到這段準備成本。** 這裡量的是本地讀取成本，不是已知 R-9 的 prompt 變大或 R-10 的磁碟累積。

重現步驟：

1. 寫 sent.jsonl：0／1,024／16,384 封歷史信，每封 body 4,096 字，最後補一封很小、時間最新的信。
2. 每組啟動三個獨立 Python 程序，呼叫產品函式 `memory(node, 1)`，量 perf_counter 與 ru_maxrss；只回傳最新 1 封，不帶 work 檔。
3. 跑 [agent/probe.py](2026-10-03-astra-3-evidence/agent/probe.py)；大檔只生在 tmp，證據只留量測值。另以 32 MiB work 檔做截斷對照。

看到什麼：三組回傳 JSON **始終只有 103 bytes**，但程式先讀完 sent.jsonl、建立全歷史清單並排序，最後才切 `hist[-n:]`。

| 舊信數 | sent.jsonl bytes | 讀取中位 ms（3 次） | 峰值 RSS 範圍 KiB |
|---:|---:|---:|---:|
| 0 | 49 | 0.061 | 28,796 |
| 1,024 | 4,240,433 | 10.342 | 29,472～30,192 |
| 16,384 | 67,846,193 | 100.716 | 102,548～102,752 |

最後一組各程序讀取前的峰值約 28,924 KiB，讀完約 100 MiB；4 MiB 組受配置器／環境影響較大，不用三點擬合記憶體公式。相對地，32 MiB work 檔的確只讀 4,000 字，沒有全讀再截。

因此 `memory: N` 是**輸出筆數**，不是讀取資源上限。記憶體／耗時仍隨全部歷史增長；這段還在寫 llm_since **之前**，不能把 llm.jsonl 的呼叫耗時當完整 think 耗時。本輪沒有觀察到 OOM 或因此誤 restart，不做超出證據的宣稱。可考慮有界讀取、索引或歷史分段；核心未定演算法，列技術選型。[memory.json](2026-10-03-astra-3-evidence/agent/memory.json)。

## 四、長跑數字

**6 個 fake agent＋1 個 kernel，七條時間線，各 agent 實際處理 362～363 個 tock。** 三組持續 ping、max_ping=1,000,000、memory=12、interval=180 ms；kernel 的 budget／cap 都設 10¹²，這次長跑不混入限速。audit 關閉。Linux 6.18.49、Python 3.14.7、16 邏輯 CPU；同機還有其他探針，未隔離 CPU。

65.485 秒收尾完成，705 次假 LLM 呼叫、702 次寄件、699 封已處理信；每個 node 都只有 1 個 task，**沒有 restart、沒有 agent 漏 tock**。共 **5,070 次 tick／tock 程序呼叫，全部 exit 0**。停止時 daemon exit 0、七條時間線 stopped／live=[]，六 agent exit 0。

### tick／tock 有沒有越跑越慢？

| 各 node 的回合視窗 | tick 中位／P95 ms | tock 中位／P95 ms |
