### 實際跑了什麼

README 原指令，從指定 workspace 根執行：

```sh
python3 proto7-1/demo/play.py
python3 -m unittest discover -s proto7-1/tests
```

示範退出碼 0，末尾 10 項檢查全部 `[OK]`，含寄信、卡住重啟、預算 pause／resume、兩條巢狀控制路徑、無殘留程序。測試為 `Ran 34 tests in 9.862s / OK`。這些是本次結果，沒有把通過既有測試解讀成故障路徑也正確。摘要在 [baseline.txt](2026-10-03-astra-evidence/baseline.txt)。

自建空間沒有複製示範場景：`lab` 放一個 keep kernel；`lab/agents/ada`、`lab/agents/ben` 各放一個 keep agent，`llm: "fake"`、`max_ping: 12`；自創 `ledger` 時間線，每回合啟動 census 任務，讀兩個 agent 的已處理信件與成果，寫 `census.json` 和流水帳。四條 interval 分別是 180、140、160、150 ms；ledger 用 `dirs: ["../lab/agents"]` 宣告額外讀取範圍。

| node | 最終回合 | 成果 |
|---|---:|---|
| lab | 45 | kernel 因用量 392 > 300，分別暫停 ben／ada，各過自己的 3 回合後恢復。 |
| lab/agents/ada | 53 | 收到 ping 12，寫出 `work/done.txt`；手動 restart 從 `agent-r1` 接成 `agent-r27`。 |
| lab/agents/ben | 47 | 完成自己的互傳信步驟，最後 idle。 |
| ledger | 50 | 50 次 census 均 code 0；最後讀到 12 封已處理信、1 個完成成果。第 10 回合 pause，約 0.7 秒後仍是第 10 回合，再 resume。 |

操作全部透過原子寫入控制檔，沒有呼叫 `aos7-ctl`，也沒有 import 產品內部函式。Python 驗證腳本只是自動建檔、讀檔、等待與啟停程序。可重跑 [new_space.py](2026-10-03-astra-evidence/new_space.py)；[summary](2026-10-03-astra-evidence/new-space-summary.json)、[census 流水帳](2026-10-03-astra-evidence/new-space-census.jsonl) 和[關鍵原始檔](2026-10-03-astra-evidence/new-space-selected-files.json)保留結果。

### S-01：只靠 cat 和寫檔行不行

**一般操作可以；完整判定故障與存活狀態還不行。** 沿 README → spec，不看產品程式碼即可建立空間、寄信、觀察 agent 狀態、對照 birth／exit、pause／resume、restart 與 stop。任務崩潰的 traceback 在 `out.log`，退出碼在 `exit.json`，都能讀。自訂時間線也只需要文件所列協議。

限制有三種，不能混為一談：

- **主機邊界**：第一次啟動 daemon、故意 `kill -9` 與確定某 PID 已死，需要 Linux 程序操作；這落在 S-03。daemon 被強殺後，`status.json` 不會自己變成 stopped；單次 cat 只是舊快照，需隔時重讀或查程序。任務如何找到自己的檔案，文件已明示靠環境變數；這是既有 P-02，不另報新問題。
- **資訊分散**：本次知道「12 封信完成」是靠 inbox/done 和成果檔，回合總結並不記 agent 的工作內容。這驗證 I-2，並非新發現；ledger 是自行補的應用層統計。
- **真正要追程式的地方**：控制檔 `[]` 為何 daemon 層會拒絕，task 層卻持續破壞 tick／tock，以及為何 status 還停在 idle，文件無法解釋。cat daemon 的 log 已能看到 `AttributeError` 與 `ctl.get`；不必先讀碼才知道型別出了錯。為了精確解釋兩份回合數為何分岔、失敗後為何還回 idle，我在實驗後才追讀任務控制、tick 與 daemon 回合處理的實作（見二、1）。其餘自建、crash recovery、共享與巢狀操作都未靠產品源碼完成。

## 二、新發現的問題

已知的「keep 被 kill 後補起」「pause 不執行任務 ctl」「共享空間沒有強制隔離」等不另列新問題。下列明確區分新 bug 與已知問題的新證據。

### 1. 任務控制檔是合法 JSON 陣列時，整條時間線反覆失敗，且 status 不呈現錯誤〔bug〕

**重現步驟：**

1. 建 node `n`，120 ms 時間線，放一個 keep sleeper；另外建正常 node `healthy` 作對照。
2. 等 sleeper 出生，在 `n/.aos/tasks/sleeper-r1/ctl.json` 原子寫入 `[]`。
3. 等數回合，讀該 ctl、`n/.aos/round.json`、`.aosd/status.json`、任務 tock 與回合總結。
4. 把原 ctl 改成 `{"op":"kill","why":"repair malformed control"}`，再觀察。

**看到什麼：** 初測 `round.json` 已到 5、`open:true`，status 卻仍報 round 1／idle；ctl 一直在，沒有失敗回條。雙 node 複驗時，n 到 round 6 仍 open，status 仍停在 1；healthy 正常到 6。該次 n 尚無 tock／回合總結。改寫正確 kill 後，第 7 回合成功殺掉舊 sleeper，keep 補起 `sleeper-r7`，第 7～9 回合才有總結。不是整個 daemon 死掉，也不是單一任務請求被拒絕，而是壞請求持續阻斷該 node 的回合工作。

對照組：相同 `[]` 放在 daemon ctl，會收到 `ok:false / not a JSON object`；語法錯誤、`null`、未知 op 的其他控制案例也有失敗回條。不能把「JSON 可解析」當成「可用的控制物件」。這違反細部 spec 對壞檔可處理的預期，無須使用者先決定控制語意。

**事後讀碼確認：** `aos7_task.py:181–187` 只處理讀取結果為 None 的情況，對陣列直接呼叫 `.get`；daemon 控制讀取則先檢查 dict。tick 在處理 ctl 前就寫入新回合，卻在印成功 stdout 前因例外結束；`aos7_daemon_timeline.py:75–94` 從 stdout 更新記憶體回合，沒有輸出就沿用舊值，且只把非零 rc 寫入 log，仍切回 idle。這解釋了 status 與 round.json 不一致。原始 [log.jsonl](2026-10-03-astra-evidence/controls/task-array-recovery/.aosd/log.jsonl) 的 tick／tock 記錄已含 `rc:1` 和 traceback；daemon 的 stderr.log 為空。

**牽涉：** S-01（可讀錯誤／狀態）、S-06（daemon 承擔邊緣失敗）、S-08／S-11（回合與通知中斷）、S-17（控制失敗拖垮時間線）。

**證據：** [初測](2026-10-03-astra-evidence/controls/events.json)、[雙 node 與復原](2026-10-03-astra-evidence/controls/additional-events.json)。重跑 `python3 proto7-1/notes/play/2026-10-03-astra-evidence/controls/reproduce.py`，再跑同目錄 `additional.py`。故障後改寫 ctl 就能恢復，不需要重開 daemon；已跳過的回合不會因此補齊。

### 2. SIGKILL 後能續接任務，但被中斷的回合永久缺席〔技術選型；P-08／P-04 新證據〕

**重現步驟：** 建 live、paused 兩條 500 ms 時間線，各一個記錄 tock 的 keep worker；先用 JSON pause 第二條。等 live 的第 4 回合 `open:true`，對 daemon PID 執行 SIGKILL；等 0.8 秒，對原 root 重開 daemon，跑到第 8 回合後寫 stop＋kill。

**看到什麼：** live 沿用同一個 `worker-r1`、同一個任務 PID，沒有重複起任務；paused 也保留第 1 回合的暫停狀態。但重開直接進第 5 回合，最終 summary 編號為 `1,2,3,5,6,7,8`，worker 的 tock 觀察同樣由 3 跳到 5。第 4 回合的 open 狀態被覆寫，沒有 aborted／recovered 紀錄。這比「回合數接續」多出一個使用後果：數字接續不代表每個已開啟的回合都有結束或通知。

強殺後的 status 在 0.8 秒後仍一字未變：舊 PID、`stopping:false`、phase tick。這不是要求 SIGKILL 前能寫善後資料，而是說目前檔案介面沒有獨立的存活證明；不能只看這一份就認定系統還在跑。

**牽涉：** S-06、S-08、S-11；狀態可判讀性另涉及 S-01／S-03。核心未指定 crash recovery 的補回合政策，故列技術選型，不直接判違反核心。需要使用者理解的後果是：「收到 N 次 tock」與「round 增加 N」在 crash 後不等價。

**證據：** [重現腳本](2026-10-03-astra-evidence/restart/probe.py)、[四次快照索引與結果](2026-10-03-astra-evidence/restart/findings.md)、[outcome](2026-10-03-astra-evidence/restart/outcome.json)。

### 3. 巢狀接管後，送到舊 daemon 的 pause 會回成功，實際時間線仍繼續〔技術選型；P-10／P-11 新證據〕

**重現步驟：**

1. 父 daemon 先掃描沒有 `.aosd/` 標記的 `child/work`，在該 node 起一個 keep 任務。
2. 再以 `child` 為 root 起子 daemon，讓它接管既有 work 時間線。
3. 讓舊任務依出生時的 `AOS7_ROOT` 與 `AOS7_NODE_ID`，寫 `{"op":"pause","node":"child/work"}` 到父 daemon ctl。
4. 讀回條與父／子 status，再等幾回合。

**看到什麼：** 舊任務的 birth 與環境仍記 `child/work`，子 daemon 目前的 node id 已是 `work`。父 status 的 nodes 是空的，卻回 `ok:true / pause child/work`；收到回條時是第 8 回合，稍後已到第 13 回合，子 status 的 `paused` 仍是 false。

P-10 已提環境指舊 daemon；新增證據是**錯位控制有成功回條**，不只是找不到 node 或請求沒人處理。若操作者或 kernel 以回條代表「現在正在服務的那條時間線已停」，就會誤判。這也和 daemon 接受尚未存在的 node 作預先 pause 的行為相容，因此不直接判成 bug，更不代替使用者決定是否允許熱接管。

**牽涉：** S-01、S-14、S-15、S-18、S-21。

**證據：** [重現腳本](2026-10-03-astra-evidence/overlap/takeover-routing.py)、[原環境、回條與兩邊 status](2026-10-03-astra-evidence/overlap/takeover-routing-results.json)。

## 三、對 problems.md 裡 D-1～D-4 的看法

以下只列這次實測支持的證據與後果，不選方案。

**D-1：跨資料夾確實是正常工作的一部分。** 本次 kernel 的 birth.dirs 只有 lab，仍能寫 root 的 daemon ctl；ada 的 dirs 只有自己 node，仍能寄信給 ben。自訂 ledger 額外宣告兩個 agent 的共同上層資料夾後能統計成果；alpha／beta 也能共同寫 mail。這支持「跨 node 能力必須有位置可表達」，但宣告本身不是隔離、排他或投遞保證。共享資料夾實驗沒有證明併發讀改寫安全，也沒有證明越界已被阻止；採哪種限制與遞送方式仍是 D-1 的選擇。

**D-2：回合仍可作節奏與管理刻度，卻不能當工作的完成量。** 自建空間的 kernel 確實用自己的 3 回合完成冷卻；ledger 第 50 回合已穩定看見 12 封信與成果，所以回合不是毫無作用。但 agent 後續很多回合只是 idle，回合增加不代表多完成一件事。不理 tock 的任務也不阻止回合前進；SIGKILL 實驗又證明回合編號能增加而少一次通知。這次只跑 fake，沒有重測慢模型，不能新增真 LLM 延遲的結論。

**D-3：只結束實例和維持任務表，是兩個同時存在的效果。** 本次在 pause 解除後，舊 `busy-r1` 的 kill 回條成功、exit 是 -15，同一個 tick 就在 tasks.json 的 keep 規則下起了 `busy-r2`。崩潰任務亦已在 12 回合內不斷補起。後果不只是「下一回合又有」，還可能在使用者看到 kill 成功時替代實例已存在。這裡只確認實例死亡與任務表仍有效，沒有替 kill 定義持久停用語意。

**D-4：pause 停了時間線，但任務的現實工作繼續。** 實驗先 pause，確認 node round 與 task tock 都固定在 1，再寫 task kill；約半秒內自訂 heartbeat 從 4 增到 16，ctl 仍待處理、沒有 exit。resume 後到第 2 回合才執行 kill，並因 keep 起出替代實例。這是實際 I/O 在暫停期間繼續的證據，不能把 pause 當成停止耗用資源；本次沒有用真 LLM，故不把 heartbeat 的量直接解讀成 token 費用。另一方面，pause 經 SIGKILL／重開仍保存，重開 daemon 也不是解除 pause 的操作。是否允許控制穿過 pause，仍牽涉 S-17 的解讀。

D-3／D-4 的原始前後快照在 [pause-events.json](2026-10-03-astra-evidence/controls/pause-events.json)，可重跑同目錄 [pause.py](2026-10-03-astra-evidence/controls/pause.py)。

實驗結束後以 stop＋kill 清理，並核對任務與 runner 的程序狀態；沒有留下本次啟動的活程序。證據目錄保留腳本與快照，供重跑及核對。
