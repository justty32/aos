### S-01：只靠 cat 與寫檔，能不能知道誰掛誰、為何拒絕、信卡哪裡？

**正常路徑可以，故障時只能讀出部分真相。** 以下路徑均來自 README → spec，實驗可用相同 JSON 讀寫完成；Python 腳本只替代重複建檔、等待、啟停與收證。

| 要回答的事 | cat 的位置 | 本次結果與限制 |
|---|---|---|
| 誰掛了誰 | 寄件任務 `birth.json` 的 `node/tid/mounts`；`mount-done/*.json` 的 path／why／result | 可以建立宣告上的對照。但 birth 是可更新的清單，不是不可變出生紀錄；連結被改指後，它仍說 b，實際寫 c（問題 4）。 |
| 為什麼拒絕 | `mount-done/<請求檔名>.json` | 一般會明說不在 mount_allow、名稱已掛別處、路徑不合。name 為非空陣列時沒有回條，須追 `.aosd/status.json:last_error` 或 log 的 Python traceback（問題 1）。 |
| 信還在等嗎 | 寄件 node `outbox/*.json` ＋現任 task 的 `mount-req/` | 看得到信與未審請求；若寄件時間線 pause，再 cat daemon status 可以判定沒有下一個 tick。沒有逾期欄位或終止等待回條。 |
| 信被拒了嗎 | `outbox/failed/*.json` ＋舊任務 `mount-done/*.json`／`out.log` | failed 信只保留原信，原因要跨檔找；restart 後要回舊 tid 查。改 allow、刪拒絕回條不會搬回 failed 信。 |
| 信真的收到嗎 | 收件 node `inbox/*.json`、`inbox/done/*.json`，再看 timeline／daemon status | outbox 空只表示已寫到路徑。ghost 沒有 timeline 也會收到「成功投遞」；搬家後新信可能在舊地址空殼（問題 5、6）。 |

因此，不需要 CLI/RPC 才能操作；但目前文字檔不足以把「宣告掛載」「真實目標」「已寫入」「已被 agent 處理」合成同一個可信狀態。正常拒絕可讀，例外仍會露出實作堆疊。這是本輪比第一輪降低「容易理解」的主要理由。

## 二、新發現的問題

### 1. name 是非空陣列：請求被刪、沒有回條，當次 tick 跳過後續工作〔bug〕

**重現步驟：** 起 keep worker 與每回合 pulse；pause 該 node 後，在 worker 的 mount-req 依序寫 `01-good.json`（正常）、`02-bad.json`＝`{"name":["bad"],"path":"recipient/inbox"}`、`03-later.json`（正常）。resume，等下一個 tick。

**看到什麼：** 第 2 回合 tick code 1，`TypeError: cannot use 'list' as a dict key`；壞請求已不存在、也沒有 mount-done。`pulse-r2` 沒出生，r1／r3／r4 有；03-later 延到第 3 回合成功。01-good 的 birth 與成功回條已落盤，但 `rounds/2.json.mounts` 卻是空陣列。healthy 對照 node 繼續跑。

這次 status 的 `last_error` 已能記住錯誤、下一回合也恢復，**不是重報第一輪 ctl 陣列造成持續卡住與 status 假 idle**。新問題是加掛請求先刪後驗、型別例外逃出，並遺失本回合部分事件摘要。`aos7_mount.serve` 在 `check({name:path})` 建 dict 時就出錯，根本進不了 name 型別檢查。

**牽涉：** S-01、S-06、S-09、S-10、S-23。詳見 [daemon 複驗與原始回合／log](2026-10-03-astra-2-evidence/requests/additional-results.json)、[壞型別矩陣](2026-10-03-astra-2-evidence/requests/results.json)。重跑 `requests/probe.py` 與 `requests/additional.py`。

### 2. 合法 node 路徑的自動名稱碰撞，agent 無法自動寄給第二個對象〔bug〕

**重現步驟：** 建 `a/b` 與 `a_b` 兩個 node，sender 用 fake goal 先寄 `a/b`；成功後再寫 goal 寄 `a_b`。允許清單沒有禁止任一目標，不手填掛載名字。

**看到什麼：** `a/b/inbox` 與 `a_b/inbox` 都轉成 `a_b_inbox`。第一封成功，第二封被回覆「名字 a_b_inbox 已經掛了別的（a/b/inbox）」並進 outbox/failed；到第 16 回合第二個 inbox 仍空。正確的「同名不同目標應拒絕」規則沒有壞，壞的是 agent 自動取名把不同合法對象混為一個。單純刪拒絕回條仍會撞同一個名字；需人工用不同名字加掛，或預先提供涵蓋目標的掛載。

**牽涉：** S-01、S-14、S-19、S-23。新於 M-8：不是政策曾拒絕而不重試，而是正常 send 自己產生衝突。[兩次 fake send 的信件、birth、拒絕回條](2026-10-03-astra-2-evidence/requests/additional-results.json)，case `first-auto-name`／`second-auto-name`。

### 3. mount_allow 批准的是字面前綴，tick 會沿連結在空間外建資料夾〔bug〕

**重現步驟：** 在空間內設 `allowed/inside → c`、`allowed/outside → 空間根之外的實驗目錄`；a 的 `mount_allow:["allowed"]`。任務請求 `allowed/inside` 與 `allowed/outside/new-created-by-tick`，再經獲准掛載點寫檔。

**看到什麼：** 兩個請求都 `ok:true`。第一個實際寫 c，audit 也為 true；第二個由 tick 自己在空間外建立 `new-created-by-tick`，任務寫入亦成功，且因已在根外沒有 audit 紀錄。birth 與回條只顯示 allowed 下的字面路徑。

M-1 已明說任務可直接繞過；這裡新增的是**正常審核流程自己核准並執行越界目標**。即使 mount_allow 被理解為字面前綴政策，「目標不能跑出空間根」的檢查仍沒有涵蓋 symlink。沒有據此要求 OS sandbox 或被掛方同意，亦不重開使用者已決定的 M-10。

**牽涉：** S-07、S-10、S-23、S-01；直接對照細部 spec 第 4 節的路徑限制。[結果、實際檔案與連結](2026-10-03-astra-2-evidence/audit/results.json)、[原始 birth／回條／audit](2026-10-03-astra-2-evidence/audit/raw-files.json)。重跑 `audit/reproduce.py`。

### 4. Python audit 會把未准許的寫入記成 ok:true，甚至記錯路徑〔bug〕

**重現步驟 A（dir_fd）：** tick 起 a 的 Python 任務，不掛 b；開 b 的目錄 fd，以 `os.open(..., dir_fd=fd)` 寫 `dirfd.txt`，再以 dir_fd 執行 mkdir、rename、unlink。

**看到什麼 A：** 真正建立／改動的是 b 的檔案，audit 卻記為 a 下同名路徑，全部 `ok:true`。這些是 hook 有收到的 Python 事件，不是 M-3 已知的非 Python 缺漏。hook 把相對 path 一律接 cwd，忽略 dir_fd。

**重現步驟 B（改指）：** tick 宣告 `mnt/box → b`；任務自己移除這個連結並改指 c，不寫 mount-req、不改 birth；經 box 寫 `retarget.txt`。

**看到什麼 B：** birth 仍記 `to:b`，c 實際出現檔案，audit 卻 `ok:true`。hook 判斷失敗時重載掛載目標，用的是目前 `realpath(at)`，把任務自行改指的 c 當成已批准目標。已知「可以寫」不能解釋新增的「記成合法」。

**牽涉：** S-01、S-10、S-23；細部 spec 第 5 節聲稱 path 是實際位置、ok 是給定範圍。這兩種都使「scan 沒有 bad」不能證明遵守掛載。[實測結果](2026-10-03-astra-2-evidence/audit/results.json)、[raw audit](2026-10-03-astra-2-evidence/audit/raw-files.json)。

### 5. 刪除／搬走已掛收件夾後，send 直接讓 agent 崩潰〔bug〕

**重現步驟：** fake sender 動態掛 receiver/inbox 並寄出第一封；刪掉該 inbox，或把整個 receiver 搬到 moved；再用 goal 要 sender 寄第二封。

**看到什麼：** 兩個案例的 `agent-r1` 都在第 7 回合拋 `FileExistsError`、exit code 1，state 停 act／pc 0。resolver 只看 birth 就認為已掛；寫檔時對 dangling symlink 做 makedirs 失敗，例外未轉成工具失敗或 outbox 等待。keep 於 r8 補起，接續 act，重新請求加掛，r9 寄出。

成功自補不抹掉新 bug：只刪對方收件夾就令寄件 agent 整個退出。搬家案例還有新後果：tick 在原 `receiver/inbox` 重建空殼，第二封進舊址；`moved/inbox` 只有第一封。這個路徑身分問題另在問題 6 分類，不能把「自動重新找到 moved」當成核心既有承諾。

**牽涉：** S-11、S-19、S-23、S-01；搬家另涉 S-14。[刪除後 traceback／恢復](2026-10-03-astra-2-evidence/delivery/deleted-after-change.json)、[搬家後兩處 inbox](2026-10-03-astra-2-evidence/delivery/moved-after-change.json)。重跑 `delivery/reproduce.py`。

### 6. 掛載／投遞成功不代表存在收件 node：信能永久留在空殼〔技術選型；M-2／P-15 新證據〕

**重現步驟：** sender 寄給完全不存在的 `ghost`；跑到第 12 回合。另一案例是問題 5 的 receiver 搬家後繼續用舊 id 寄信。

**看到什麼：** ghost/inbox 被建起來、mount-done 成功、sender outbox 清空，信留在 ghost/inbox；ghost 沒有 timeline，也沒有 agent。搬家後的舊 receiver 同樣只剩 inbox，第二封也被當成寄出。觀察期內無退信或待處理標記；「如果一直不建立收件 node，便沒有任務會消費這封信」是依檔案／任務模型的推論，不是聲稱實測無限時間。

M-2 已記「打錯字會建空夾」，本次新增完整信件生命週期的證據：**不會一直卡在 outbox，而是顯示成功後卡在不存在的 node 地址**。P-15 已定搬家視為舊 id 消失、新 id 出現，因此不判缺少自動轉寄為 bug。是否要收件 node 存在驗證或消費確認，仍是通訊層技術選型。

**牽涉：** S-01、S-13、S-14、S-23。[ghost 第 12 回合](2026-10-03-astra-2-evidence/delivery/missing-after-12.json)、[搬家證據](2026-10-03-astra-2-evidence/delivery/moved-after-change.json)。

### 7. kernel 移除已被自己 pause 的成員後，不再履行冷卻 resume〔要使用者決定〕

**重現步驟：** 用上述三 agent 空間；kernel `cool_rounds:12`。第 26 回合讓預算規則 pause ben，確認 daemon status 也 paused 後，把 ben 從 members 移除；繼續跑到 kernel 第 51 回合，再加回 ben。

**看到什麼：** 刪除後經過 25 個 kernel 回合，ben 仍停在自己的第 27 回合；kernel-state 的 paused 還存 `ben:{at:26}`。同時被 pause、仍在 members 的 ada／cy 已如期恢復。ben 加回 members 後立即得到 resume，之後跑到第 41 回合。掛載一直保留符合 M-9，新增問題是**已下出的暫停仍有效，配套的恢復卻不再被排程**。

事後讀碼：budget 規則只迭代目前 members，resume 也放在這個迴圈內。核心未定移除成員時的控制交接，不能直接宣稱「一定要自動 resume」；需要決定移除時應清理自己造成的 pause、保留延後恢復責任，還是明示由使用者接手。此處僅列待決語意，沒有擅改選型。

**牽涉：** S-01、S-16、S-18、S-23；核心「kernel 管轄範圍之後再說」也是分類依據。[前後配置／status／kernel-state](2026-10-03-astra-2-evidence/space-events.json)、[pause／resume 決定](2026-10-03-astra-2-evidence/space-lab-files.json)。

### 8. restart 前未審的通用加掛請求，留在舊任務而沒有終態〔技術選型〕

**重現步驟：** worker 已動態掛上四個目標；同時寫 `mount-req/pending.json` 與 `ctl.json:{"op":"restart"}`。跑下一個 tick，再跑三個回合。

**看到什麼：** 新 worker-r24 繼承四個成功掛載、at 換成新 tid；pending.json 卻留在已退出 worker-r1，沒有拒絕、取消或移交回條，新任務也沒有那項掛載。tick 先執行 ctl，再只審活任務，所以舊請求不再獲處理。讀者須另外 cat exit／restart_of，才知道它已不是會被審的 pending。

細部 spec 只承諾 restart 帶「已加掛」的能力，沒有承諾任意未審請求移交，因此列技術選型。agent outbox 會自行重請，已實測恢復正常；不能把通用請求無終態誇大成待寄信遺失。

**牽涉：** S-01、S-17、S-23。[results.json](2026-10-03-astra-2-evidence/requests/results.json) 的 `restart-with-pending`、`pending-after-three-more-ticks`；[agent 的正常接續對照](2026-10-03-astra-2-evidence/delivery/pending-restart-after-restart.json)。

### 其他要求的覆蓋與新增證據（不另報已知問題）

| 情境 | 實測結果／界線 |
|---|---|
| 絕對路徑、`..`、普通 symlink 直接寫未掛 node | Python 任務三種都能寫成功，audit 各記 `ok:false`。確認 M-1 的界線；和問題 3、4 的誤准分開。 |
| 非 Python 寫檔 | sh 寫 b/shell.txt 成功，payload 無紀錄。新增可見性證據：shell-r1 仍有 Python runner 的 writes.jsonl，所以 scan 的 `tasks:5` 不能解讀為 5 個任務 payload 都受觀察。屬 M-3 新證據。 |
| 一般壞請求 | 壞語法、`[]`、null、數字、缺 path、非字串 path、非法名字、絕對／逃出根路徑均有拒絕回條；非空 list name 的例外見問題 1。 |
| 重複、人工同名衝突 | 不同請求檔重複同 name／path 回「已經掛了」成功；同名換 path 被拒、原掛載保持。同一請求檔名重用會覆寫回條；請求檔名和內容 name 可不同，回條依檔名。自動取名碰撞見問題 2。 |
| restart 已掛／未審／被拒 | 成功動態掛載帶入新 birth；舊未審 mount-req 留在已結束 tid，沒有取消／移交回條，新任務不會自動處理這份任意請求。拒絕回條也留舊 tid。需區分「繼承已核准能力」和「移交未完成操作」。 |
| restart 時 outbox 尚有信 | agent-r1 在 r2 放入 outbox，r3 前被 restart；新 agent-r3 依 node outbox 自己重請，r4 寄出，觀察到一封、沒有遺失。舊 mount-req 仍留著，不能只看舊請求判定信卡住。 |
| 改 allow、刪拒絕回條、再 restart | 到第 24 回合，原 failed 信仍在 failed、目標未收到；這些操作只解除未來重請的障礙，不把 failed 信重新排隊。M-8 新增復原操作證據。 |
