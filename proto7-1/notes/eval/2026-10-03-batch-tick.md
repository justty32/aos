# 評估：批次 tick（一個 tick 程序一次處理好幾條時間線）（2026-10-03）

← [proto7-1 README](../../README.md)｜要對照的：[核心 spec](../../../proto7/spec/core.md)（S-）、[分層筆記](../../../proto7/notes/2026-10-03-aos-layering.md)（「第 N 行」指這份）｜背景數字：[astra-4 第一節](../play/2026-10-03-astra-4-infra.md)、[infra-needs N-41](../infra-needs.md)｜證據：[2026-10-03-batch-tick-evidence/](2026-10-03-batch-tick-evidence/)

**這份是給使用者判斷用的評估，不是要說服誰。** 評估隊在 scratchpad 複製 proto7-1（commit b9633fec），做了一個最簡單的批次原型、一支極小的 C tick／tock，跟原版比。沒有改 repo 裡的程式，也沒有 commit。

## 結論（一段話）

**批次確實省，但幾乎只省「Python 啟動」這一項，而換成 C 也省得到同樣多；代價是改掉核心的兩個定義。** 空任務 200 條時間線：原樣每秒 332 回合、吃 14 核；tick＋tock 都批次後每秒 1,983 回合（到達設定的 100 ms）、2.3 核；不批次、只把 tick／tock 換成極小 C 程式，每秒 1,610～1,715 回合、1.6 核，效率跟批次差不多（每回合 CPU 約 1.0 ms 對 1.2 ms）。astra-4 的工作量（每回合 3 個短任務）下，批次只把吞吐從每秒 110 提到 195 回合（+75%），因為大頭是每個任務一個的 Python `aos7-run` 包裝程序，批次 tick 碰不到它。代價面：(1) 批次後「tick 所服務的」不再是一個資料夾，S-13 的 node 定義要改寫成「邏輯 tick」而不是「tick 程序」；S-04「一個動作一個程序」字面上破了，批內所有線也被迫用同一支 tick 程式。(2) 一條線出事會連累同批的其他線，而且實測到了：一條線的 `round.json` 卡在 I/O，單一批次形狀下**其他 19 條線全部停擺**；一個不理 SIGTERM 的任務被 kill，同批其他線的回合數**少一半**；一條線有 4,000 個舊任務資料夾，同批全部被拖到它的速度；kill -9 一個 40 條的批次，**21～35 條線**當回合的 tick 沒做。原樣下這些事都只影響出事的那一條。

## 一、批次的幾種形狀

| 代號 | 形狀 | 這次有沒有實測 | 說明 |
|---|---|---|---|
| A | 原樣：每條線每次 tick、tock 各一個程序 | 有 | 對照組 |
| B1 | **只批 tick**：daemon 收集「現在到期要 tick 的線」，開一個 `aos7-batch` 程序依序做，一次只有一個批次程序在跑；tock 照原樣 | 有 | 正在跑的那批結束前到期的線，排進下一批（自然成批） |
| B2 | **tick、tock 都批**（各一個收集者），一次一批、不限條數 | 有 | B1 加上 tock |
| B3 | tick、tock 都批，**每批最多 K 條、最多 P 批同時跑**（實測 K=16、P=4；故障面用 K=4、P=4） | 有 | 比較能用滿多核，也把一次出事的範圍限在 K 條 |
| B4 | **同一棵 node 樹一起批**（例如 `team` 與 `team/agents/*`） | 沒有（推演） | 各線 interval 不同，要嘛只批「剛好同時到期」的（退化成 B1），要嘛把整棵樹對齊成同一個節拍，那就等於把整棵樹當成一個 node（見第二節 S-13） |
| B5 | **全域節拍**：所有線對齊同一個 tick 時刻，一個程序一次做全部 | 沒有（推演） | 各線不再有自己的時間，等於 S-05 的「多條時間線」變成一條 |
| B6 | **常駐批次服務**：一個常駐程序替所有線做 tick（批次的極限：程序不退出） | 沒有（推演） | 就是 10-03 否決的「daemon 內呼叫 lib」換個位置；拿來當參照 |
| B7 | **依身分／程式分組**：只把「同一支 tick 程式、同一個身分」的線放同一批 | 沒有（推演） | 未來不同 node 用不同 tick 程式或不同身分時，批次只能這樣做 |

批次原型的細節（[code/](2026-10-03-batch-tick-evidence/code/)）：daemon 每條時間線的 thread 不變，只把「跑 `aos7-tick`」換成「交給收集者、等結果」。批次程序從 stdin 拿 `[{"node", "early"}]`，**每條做完就印一行**（`{"node", "rc", "out", "ms"}`），daemon 收到哪條就放哪條走，不等整批結束（所以每條線的「tick 結束」還是各自的時間點，S-08 的回合開始沒被拉到批尾）。每條各自 `try`，Python 例外只記在那一條。批次程序死掉時，還沒輪到的線一律回失敗。核心 tick／tock 的程式碼完全沒改，批次程序直接 import `aos7_tick.tick()`／`aos7_tock.tock()`。

## 二、對核心 spec 逐條看

「破」＝字面上不合，要改 spec 或改解讀；「可」＝合；「弱化」＝合，但原本靠它得到的性質變弱。

| 條 | 內容 | B1／B2（一次一批） | B3（K 條一組並行） | B4／B5（樹／全域對齊） | B6（常駐批次） |
|---|---|---|---|---|---|
| S-01 | LLM 可讀 | 可：協議仍是 JSON 行。弱化：LLM 手跑 `aos7-tick root node` 看一回合仍可行（批次程式要保留單條模式）；但「某條線為什麼沒 tick」要先找出它在哪一批、那批誰卡住 | 同左 | 同左 | 弱化：狀態在常駐程序記憶體裡，看檔看不到 |
| S-04 | 每個動作一次 POSIX 程序呼叫，保留任意語言的優勢 | **破**：N 個動作一次程序呼叫。「任意語言」也受限：同一批只能是同一支程式 | **破**（同左，K 越小越接近原樣） | **破** | **破**（等於 thread／lib 案） |
| S-05 | 一個 daemon 多條時間線，每條負責一個資料夾 | 弱化：各線還各數各的回合，但節奏互相牽連（實測：同批被拖到最慢那條的速度，見第三節） | 弱化（限在 K 條內） | **B5 破**：全部對齊一個節拍，就不是「多條」時間線；B4 在樹內破 | 弱化 |
| S-06 | 邊緣狀況歸 daemon，tick-tock 默認正常 | **弱化／反轉**：原本一條線的邊緣狀況只是那條線的事，daemon 收拾；批次後 tick 程序裡多了「跨線」的邊緣（誰做完、誰沒做、半做），要嘛批次程式自己處理（邊緣跑進 tick），要嘛 daemon 要懂批次的部分失敗 | 同左，範圍小 | 同左 | 同左，且常駐程序本身成了新的單點 |
| S-08 | tick 結束＝回合開始；不準時無妨 | 可（逐條回報）。若批次程式只在全批結束才回報，「回合開始」就變成「全批最後一條結束」，會失真 | 可 | 可 | 可 |
| S-09 | tick 只是起頭，很快結束 | 弱化：每條仍快，但批次程序本身不快（200 條、每條 3 任務時一批 ~0.9～1.3 秒） | 可 | 弱化 | — |
| S-10 | 任務一律由 tick 啟動；tick 把任務和 daemon 對接 | 字面可（任務還是 tick 起的）。弱化：任務的父程序是「替很多線做事的程序」，從程序樹看不出任務屬於哪條線，只能靠環境變數 `AOS7_NODE`／`AOS7_TID` | 同左 | 同左 | 同左 |
| S-11 | 任務可以跨回合 | 不受影響 | 不受影響 | 不受影響 | 不受影響 |
| S-12 | tick 是程式還是 lib 都可以 | **這條是批次最有力的依據**：「形式無所謂」可以讀成「一條線的 tick 可以是批次程序裡的一次函式呼叫」。但 S-04 是之後（10-03 看完 thread 評估）才定的、比 S-12 具體，兩條一起讀時，lib 只能活在「每個動作一個程序」之內 | 同左 | 同左 | 同左 |
| S-13 | node＝一條時間線服務的資料夾 | **要改寫**：一個 tick 程序服務 N 個資料夾。要保住 S-13，就得說「node 是**邏輯上的那次 tick** 服務的資料夾，不是 tick **程序**服務的」——node 從「看得見的程序 ↔ 資料夾」一對一，變成要靠協議裡的 `node` 欄位才分得出來 | 同左（一個程序服務 ≤K 個資料夾） | **B4 對齊版其實是另一回事**：整棵樹一個節拍，「tick 所服務的資料夾」變成樹根，等於把整棵樹定義成一個 node——合 S-13，但 node 的粒度變了 | 同 B1 |
| S-14 | node id＝相對路徑 | 不受影響 | 不受影響 | B4 對齊版：子資料夾不再有自己的 id 意義 | 不受影響 |
| S-15 | 重疊只管最基本 | 不受影響（批次按 daemon 分，子 daemon 的根本來就不掃） | 同左 | 巢狀 node 會被迫一起，跟「巢狀 node 各是各的時間線」衝突 | 同左 |

| S-18 | kernel 用 daemon ctl 停／繼續某條時間線 | 粒度不變（pause 還是對單一 node，daemon 決定誰「到期」）。實測 daemon ctl 回條反而變快（CPU 不再滿載） | 同左 | B5：停一條線＝從全域節拍拿掉它，可做 | 同左 |
| S-20 | 時間線像一個大號的任務（同像性） | **弱化**：任務＝一個程序、時間線的每個動作＝一個程序，這個對應在批次後斷了：沒有「一個程序服務很多任務」的對應物 | 同左 | 同左 | 同左 |
| S-21 | 路一（任務開子 daemon）、路二（寫別的 daemon 控制檔） | 可：批次只在同一個 daemon 內（世代、`action.lock` 的比對都是按 daemon 根），子 daemon 自己批自己的。但子 daemon 被父 kill（程序群組）時，若它正在跑一個大批次，SIGTERM 被 tick 忽略（照 spec 第 4 節「做完這個動作」）→ 等全批做完才退，退得比原樣慢 | 同左 | 同左 | 同左 |

**一句話**：最直接衝突的是 **S-04（字面破）與 S-13（要改寫成「邏輯 tick」）**；S-12 是唯一替批次說話的條文；S-05／S-06／S-20 不破但會變弱，弱在哪一點第三節有實測。

## 三、故障面

故障實驗：每個 daemon 20 條線、100 ms、空任務，壞的是 `n000`，出事後觀察約 6 秒，看其他 19 條。同一份腳本跑原樣（A）、一次一批（B2）、每批 ≤4 條 4 批並行（B3'）。原始數字在 [results/faults-all.json](2026-10-03-batch-tick-evidence/results/faults-all.json)、腳本 [code/faults.py](2026-10-03-batch-tick-evidence/code/faults.py)。

| 狀況 | A 原樣：其他 19 條 | B2 一次一批：其他 19 條 | B3' K=4、P=4：其他 19 條 |
|---|---|---|---|
| **卡住的 I/O**：`n000/.aos/round.json` 換成 FIFO（tick 一讀就永遠卡住） | 照跑，每條 38～41 回合（這輪宿主有別的重負載，間隔 P50 127 ms） | **19 條全部 0 回合：整個 daemon 的時間停了** | 這次照跑 60 回合（剛好 `n000` 那批只有它自己）；但那個批次程序永遠卡住、並行數從 4 剩 3，**有 4 條線卡住就全停** |
| **Python 例外**：`spawn/x.json` 是資料夾，tick 的 `os.remove` 丟例外 | 照跑 60 回合；`n000` 每回合 rc=1 | 照跑 60 回合（批次程式每條各自 `try` 才有這個結果） | 同左 |
| **吵鬧的鄰居**：`n000` 有 4,000 個舊任務資料夾（tick 全掃） | 每條 51～54 回合，間隔 P50 102 ms；`n000` 自己 24 回合 | **每條都是 47 回合、間隔 P50 129 ms，跟 `n000` 自己（46）幾乎一樣：整批被拖到最慢那條的節奏** | 57～61 回合，P50 100 ms |
| **不理 SIGTERM 的任務被 kill**（tick 裡等 1 秒才 SIGKILL），每秒一次 | 每條 60 回合，P95 113 ms | **每條 30 回合（少一半），P95 1,158 ms** | 大多 60 回合，同組的最大 1,190 ms |
| **kill -9 一個 tick 動作**（模擬 OOM killer、崩潰） | 1 條線受影響（就是被殺的那條；`round.json` 寫了、`started` 沒記，是原本就有的半做） | 見下面直接實驗 | 見下面直接實驗 |

**kill -9 的影響範圍**（直接實驗，40 條、每條 3 個任務的一批，批次程序開始後 30／60／100 ms 送 SIGKILL；[results/kill9-direct.txt](2026-10-03-batch-tick-evidence/results/kill9-direct.txt)）：

| SIGKILL 時間 | 已回報完成 | 回合數有前進 | 這回合沒做到 tick | 半做（round 寫了、started 沒記） |
|---:|---:|---:|---:|---:|
| 30 ms | 4 | 5 | **35** | 1 |
| 60 ms | 11 | 12 | **28** | 1 |
| 100 ms | 18 | 19 | **21** | 1 |

半做的永遠只有一條（跟原樣一樣），但「這回合沒 tick」的從 1 條變成整批剩下的。daemon 收到的是一批失敗，要記到每一條的 `last_error` 上。

其他故障面（推演，沒實測）：

- **資源歸屬**：原樣下「這個 tick 程序起了哪些任務」＝「這條線起的任務」，程序樹就看得出來。批次後任務的父程序（死前）是共用的批次程序；歸屬只剩環境變數與 `birth.json`。Q1（daemon 要不要擁有任務所有子孫）若選 (b) subreaper 或 (c) cgroup，批次程序要替每個任務分別「放進哪條線的帳」，原樣下 tick 程序本身就可以整個放進那條線的 cgroup。tick 自己吃的 CPU、記憶體也記不到哪條線上。
- **權限／身分**：之後若不同 node 用不同身分（uid、cgroup、帳號；使用者先前說過要把這些拉出 daemon），原樣下 daemon 可以用那個 node 的身分起它的 tick（一個程序一個身分，Linux 天生支援）。批次程序只能用一個身分：要嘛是所有 node 身分的聯集（等於特權程序，在裡面替每條線切換身分），要嘛只能把同身分的線放一批（形狀 B7），批次效益隨身分種類變少而消失。
- **巢狀 daemon**：批次不跨 daemon（世代、根不同），子 daemon 自己批自己的，結構上沒問題；問題在停機：tick 照 spec 忽略 SIGTERM、做完動作才走，批次的「一個動作」變成一整批，子 daemon 被父 kill 時退得慢，可能撞上 SIGKILL 保底而變成半做。
- **回合公平**：批內有先後，排在後面的線每回合固定晚一點；要公平就要輪換順序。實測反而看到另一面：**CPU 不夠時，批次讓各線的回合數更平均**（200 條、每回合 3 任務：原樣每線 3～14 回合，B2 是 14～16 回合），因為少了幾百個程序搶 CPU。
- **不同 tick 程式**：S-04 的理由是「保留任意程式語言的優勢」。今天 proto7-1 所有 node 用同一支 `aos7-tick`，所以能批；一旦 timeline.json 能指定自己的 tick 程式，不同程式的線就不能同批。

**順帶發現（跟批次無關，原樣也有）**：卡住的 I/O 實驗裡，**原樣的 daemon 也停不下來**（SIGTERM 後 5 秒仍在，被 SIGKILL，rc −9），因為 `run_prog` 的 `subprocess.run` 沒有逾時，卡住的那條線的 thread 永遠不回來，daemon 等所有線結束才退出。一條線的 tick 卡住能拖住整個 daemon 的停機。這是 S-06 的一個邊緣，交給做 proto7-1 的那隊看。

## 四、實測數字

方法：[code/bench.py](2026-10-03-batch-tick-evidence/code/bench.py)。每格一個 daemon、每條線 100 ms、15 秒視窗；前 5 條線各多一個 `keep` 的 `sleep 1000`，每秒寫一個 daemon ctl（`rescan`）並 kill 一個 keeper（任務 ctl，由 tick 執行），量回條延遲。回合間隔用 daemon log 的 tick 事件（tick 完成→下次 tick 完成，S-08）。「全組 CPU」是 harness 設 subreaper 後用 `RUSAGE_CHILDREN` 收的 daemon＋tick／tock＋批次＋aos7-run＋任務的 CPU 秒，除以牆鐘；「系統 CPU」是 `/proc/stat` 整機忙碌（含別的程序）。機器：AMD Ryzen 7 9800X3D、16 邏輯 CPU、Python 3.14.7。

注意：(1) 每格只跑一次（另挑 4 格重跑一次）；(2) 實驗期間另一隊的探針也在跑（看得到 `aos7probe-event` 的 daemon），15:39 起宿主另有一個重負載程式啟動，矩陣在它之前跑完，重跑與故障實驗是在它之後跑的；(3) 不是隔離主機的基準測試。完整表：[results/tables.md](2026-10-03-batch-tick-evidence/results/tables.md)，每格原始 JSON 在 [results/](2026-10-03-batch-tick-evidence/results/)。

## 五、跟其他路比較

| **原樣**（每動作一程序，Python） | 空任務 ~310 回合／秒；有任務 ~110 回合／秒 | 全合 | 最好：一條線出事只影響自己（卡住的 I/O 例外：原樣也會拖住 daemon 停機） | 使用者已答「慢就慢，寫清容量」 |
| **不批次＋之後換 C**（tick、tock，連 aos7-run 更好） | 實測 C tick／tock：空任務每回合 1.0 核·ms，跟批次同級；200 條 1,600～1,700 回合／秒，瓶頸換成 Python daemon | 全合，不用改任何條文 | 同原樣 | 有任務的工作量要連 `aos7-run` 一起換才有大效果；daemon 也換才過 ~2,000 回合／秒 |

## 六、使用者直覺「不妥」最可能對應的幾點

依可能性排列，每點都附這次看到的證據。

1. **node 的定義來自「一個 tick 服務一個資料夾」。** 分層筆記第 53 行原話是「目前 tick、tock 只服務一個資料夾，所以該資料夾天然就是一個 node」。批次後一個 tick 程序服務 N 個資料夾，「node」只能改說成「邏輯上那次 tick 服務的資料夾」，從看得見的「程序 ↔ 資料夾」一對一，退成要讀協議欄位才分得出來。使用者這次又重申「最核心的 node 定義是 tick 所服務的資料夾」，這是最直接的衝突點。
2. **S-04 的「每個動作一個程序」被字面打破，而且它保護的是「任意語言」。** 批次只能在「同一支 tick 程式」的線之間做；一旦允許不同 node 用不同 tick 程式（S-04 的理由本身就暗示這件事），批次就失效或要分組。
3. **一條線的事變成整批的事（S-06 的反轉）。** 原本 tick-tock 的邊緣默認正常、出事歸 daemon，而且只壞一條。實測：一條線卡在 I/O，單批形狀下另外 19 條全部停；一個不理 SIGTERM 的任務讓同批回合數少一半；一條歷史很多的線把同批拖到它的速度；kill -9 一批，21～35 條線那回合沒有 tick。要防這些就得在批次程式裡做逾時、隔離、部分失敗回報——等於把 daemon 的工作搬進 tick。
4. **時間線不再各自獨立（S-05）。** 批內的線節奏被綁在一起（「吵鬧的鄰居」實驗裡，同批每條都是 47 回合，跟壞掉那條的 46 幾乎一樣）。形狀推到極限（同一棵樹、全域節拍）就直接變成「一條時間線」。
5. **歸屬與身分。** 任務是誰起的、tick 吃的資源算誰的、用誰的身分起 tick：原樣下都是「那條線的那個程序」，Linux 天生就能分（uid、cgroup、程序樹）。批次程序只有一個身分，要嘛當特權程序替每條線切身分，要嘛按身分分組、效益隨之消失。
6. **同像性（S-20）。** 「時間線像一個大號的任務」，任務是一個程序；批次讓時間線的動作變成「一個程序裡的一段」，這個對應斷了。
7. **它要解的問題，使用者已經有別的答案。** 實測批次省下的幾乎全是 Python 啟動（tick 15 ms 裡做事不到 0.3 ms）；C tick 是 0.17 ms，效率跟批次同級，而且一條核心都不用動。使用者已經說「C 改寫以後再說」。

## 七、建議（只是建議，不代替使用者決定）

- **不建議把批次放進核心。** 它的效益換 C 也拿得到，代價卻落在使用者最看重的 node 定義與 S-04 上，故障連坐也實測到了。
- 若在換 C 之前就需要更多容量：
  - 先看工作量。任務多的場景（astra-4 那種），大頭是每任務一個的 Python `aos7-run`，**先換掉它**（C 包裝程式，或「每 node 常駐 runner 直接起任務」這條技術選型路）比批次 tick 有效。
  - 空任務、時間線多的場景，若非批次不可，最不傷的形狀是：**只當 daemon 內部的最佳化**（spec 上仍是每條線一個邏輯 tick、逐條回報、逐條寫 log）、**小批並行（K 小）**、**每條有逾時**、**只批同一支程式、同一個身分的線**。但就算這樣，S-13 的文字還是要改，第三節的連坐只是變小、不會消失。
  - 「每 node 常駐 runner」是唯一同時拿到效能、又讓「node＝一個程序服務的資料夾」更清楚的路，值得在換 C 時一起考慮；要使用者確認的是 S-04 能不能讀成「時間線是一個程序」。
- 跟批次無關、建議交給 proto7-1 那隊：`run_prog` 沒有逾時，一條線的 tick 卡在 I/O 時，daemon 收到 SIGTERM 也停不下來（實測要 SIGKILL）。
- 容量照 infra-needs 已寫的「這台約每秒 100～150 回合（有任務）」不變；本輪補一個數字：**空任務時約每秒 310 回合**，換 C tick／tock 後約 1,600～1,700（瓶頸換成 Python daemon）。
