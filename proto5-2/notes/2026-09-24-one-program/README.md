# daemon＋kernel 合成一支？脫離 JSON 檔？（調查，2026-09-24）

← [notes 索引](../README.md)｜[proto5-2 README](../../README.md)｜規模三題：[scale.md](../../spec/scale.md)

**只是調查，沒改程式、沒改規範。** 題目（使用者原話）：「daemon 和 kernel 的功能能否合在一起弄成一個程式，乃至於脫離現在的大量依託於 json 等檔案的體系？優缺點？」

誰寫的：甲（Opus，故意站「合一＋脫檔」）、乙（Opus，故意站「分開＋留檔」）各寫備忘，再互相反駁一輪；另有兩份 codex 獨立意見（沒看甲乙）。
**gpt-sol、gpt-terra、gpt-luna 這次在 codex 都回「不支援」**，第二份只好用同一顆 astra 換 high 檔位重開一次，所以兩份 codex 其實是同一家的意見，分量打折。

## 1. 先拆題：這是兩件事

- **合一**＝誰在跑：現在 daemon 是一直開著的爸爸，kernel 每一格開一次、做完就退（一格接一格）。合一＝排程搬進 daemon，變成一支一直開著的程式。
- **脫檔**＝東西放哪：現在交件、回音、帳本都是一個個 JSON 小檔。脫檔＝帳本改放資料庫（sqlite，它自己也是一個檔）、交件改走 socket。

四個人都同意：**兩件可以只做一件**。所以是四格：

| | 留檔案 | 脫檔（sqlite／socket） |
|---|---|---|
| **分開** | ① 現狀＋修規模（乙） | ③ 分開、帳本改 sqlite（甲乙反駁後都退到這） |
| **合一** | ② 一支程式、介面仍是檔案（兩份 codex 都選） | ④ 全合一（甲） |

## 2. 四格逐一看

「保留幾成」是粗估，沒量過；上千顆的判斷都沒壓測。

### ① 分開＋留檔，修規模
- **好**：什麼都不用重想；人和 agent 用 `ls`／`cat` 就看得到；kernel 一格崩了只丟那一格；改 kernel 程式下一格就是新版，不用重開；26 條「卡住再 KILL」崩潰測試照用。
- **壞**：修規模要拆帳本（乙的草圖是每格先寫一張「這格的決定」再逐檔套用，甲說這就是手寫一個資料庫，乙認了）；一支「管家」行程管 256 個 cpu 家、改 inotify 等檔案出現；**每步至少等一格，延遲是最弱處**。
- **崩潰**：照現在「先記帳再動檔」，拆帳本後要補跨檔的重做紀錄。
- **上千顆**：乙估千顆可以、萬顆要調系統上限；proto5-2 草稿本身還不夠，要把它的「要使用者拍的」1～3 題拍成「要修」。
- **手感**：`say／listen`、`aos-kernel ls` 不變；每天仍兩步重開，但包一支 `aos up`／`aos down` 就像一步。
- **保留**：約六成程式不動（aos-exec、inst、指示詞、aos-llm、agent）；kernel／daemon／cpu 主人重寫——本來 proto5-2 就要重寫。
- **支持**：乙；兩份 codex 當「退路」。

### ② 合一，介面仍是檔案
- **好**：開機一步；少掉 kernel cpu 與一格接一格的鏈；檔案照樣能 `cat`，cpu、agent 幾乎不用改。
- **壞**：**規模三題一題都沒解**（帳本整份讀寫、agent 讀帳本、一 cpu 一 Python 都還在）；排程出錯可能拖垮收屍；改排程程式要重開，在跑的工作（含幾十秒的模型呼叫）全變「結果不明」。
- **陷阱**（astra 點名）：現在 kernel 一格裡會「等 daemon 回音」（[aos_kernel_engine.py](../../../proto5/lib/aos_kernel_engine.py)），直接搬進同一個迴圈會等到自己，要改成內部呼叫。
- **崩潰**：照現在的對帳，由 systemd 之類重拉整支。
- **保留**：兩份 codex 估七～九成。
- **支持**：兩份 codex 都選它當第一個原型，理由是「改最少、先驗證合一值不值得」。

### ③ 分開，帳本改 sqlite（cpu 家與信箱仍是檔案）
- **好**：一筆交易改好幾件事，不用手寫恢復；agent 查自己那一筆，不用讀整份帳本；kernel 還是一格一格跑，出錯不連坐、改程式不用重開；daemon 不動。
- **壞**：人要看帳本得用 `sqlite3` 或 `aos-kernel ls`，不能 `cat`；sqlite 同時只能一個寫（kernel 本來就只有一個寫，沒差）；延遲照舊每步等一格。
- **崩潰**：帳本一致性交給 sqlite；「工作已啟動、結果還沒記」這種窗口照舊要對帳。
- **上千顆**：解掉帳本那一題和 agent 讀帳本那一題；一 cpu 一 Python 要另外解（管家）。
- **手感**：幾乎不變。
- **保留**：codex 估六～七成半。
- **支持**：甲乙在反駁裡都各自退到這格（甲：「只在 kernel 換 sqlite、不合程式，也是一條可行的中間路，我漏了」；乙：「帳本改 sqlite，kernel 仍一格一格、daemon 照舊、cpu 家照舊」）。

### ④ 全合一＋脫檔
- **甲的草圖**：一支 `aosd`＋指令 `aos`；帳在 sqlite；cpu 不再是行程，只是「池裡的名額」，派工＝`aosd` 直接開一支 `aos-exec`；講話走 Unix socket，信封仍是 JSON-RPC。
- **好**：崩潰窗口大多變成交易；沒有鏈、沒有每 0.2 秒掃資料夾、沒有一 cpu 一 Python；延遲最低；proto5-2 的通知檔、交接、對帳大半不用寫（乙也認了這點）。
- **壞**：單點——`aosd` 一死全停；改程式要重開、在跑的全中斷；乙指出**爸爸被 KILL 孩子不會跟著死**，要另外加機制才收得乾淨；`ls`／`cat` 看不到；崩潰測試整套重寫；agent 碰帳本的地方要改走 socket。
- **撞已拍板的前提至少五條**：cpu 範式（一個家一個主人、四樣檔）、kernel 一格一格的 exec、daemon 只管生死、多機才上 socket、link 原子投遞。
- **保留**：甲估 lib 四成重寫、測試三到四成重寫；乙說算輕了。
- **支持**：甲（反駁後自己承認「撞前提這點光它就可能決定結果」）。

## 3. 有共識的

1. **合一與脫檔是兩件事**，各有各的收益，不必綁在一起。
2. **沒有哪一格能讓「工具已經做完、還沒記下就崩」消失**：資料庫只保證帳對，不保證寄信、改檔這種外面的事只做一次。這個「結果不明」永遠要靠回報給 agent、不盲目重試（乙、兩份 codex 明說；甲沒反駁）。
3. **真正卡上千顆的是「一 cpu 一支 Python」和「agent 讀整份帳本」，跟合不合一無關**；每天兩步重開也能用 `aos up` 包掉，不用合程式（乙、兩份 codex；甲說「包起來只是把陷阱藏起來」，見分歧 2）。

附帶兩條小共識：斷電時兩邊都可能丟最後幾筆（現在寫檔沒有 fsync，[aos_home.py](../../../proto5/lib/aos_home.py)，四人都認）；r5 試玩最痛的 `listen --wait` 等不到先到的回話，是指令設計問題，換底層不會自己好。

## 4. 沒共識的

1. **第一步做哪格**：兩份 codex 選 ②（先合、留檔、看值不值得）；甲乙反駁完都退到 ③（先換帳本、不合）。差別在：② 解決開機步數、不解規模；③ 解決規模的一半、不動開機。
2. **每天兩步重開，包一層算不算解決**：乙和 codex 說 `aos up` 就夠；甲說底下仍是兩個家、兩種死法，r5 撞到的順序陷阱（daemon 死了 health 還叫你 boot kernel）只是被藏起來。
3. **延遲要不要緊**：甲說「每步等一格」是結構性的，只有④能根治；乙說讓 kernel 有新通知就提早開下一格能縮小差距，而且 agent 等模型本來就要幾秒。沒人量過。

另外 codex（high）挑了一句說法：`scale.md` 說「agent 每格讀整份帳本」偏重了。我翻過程式，agent 只在投遞前檢查「送過沒」、`status`、`start` 撞名時才讀帳本（[aos_agent_batch.py](../../../proto5/lib/aos_agent_batch.py) 的 `already_posted`），閒著的格不讀。上萬 agent 時仍是負擔，但沒那麼糟。

## 5. 我的建議

**現在不用動。** 使用者說過「規模先不動」（[WAIT_USER C 段](../../../wf/WAIT_USER.md)），這份調查沒挖到非現在做不可的東西。

**要動的話，選③，分三步，順著 proto5-2 做：**
1. **第一步（哪一格都需要，隨時可退）**：給 kernel 一個「查一筆行程」的正式入口（例如 `aos-kernel proc <名> --json`，或一支小函式），aos-agent 改用它，不再直接打開 `K/state.json`。這步做完，帳本放檔案還是 sqlite、合不合一，agent 都不用再改。
2. **實作 proto5-2 kernel 時**：帳本改 sqlite，cpu 家、`requests/`、`responses/` 仍是檔案；kernel 仍一格一格跑、daemon 不動。proto5-2 的 kernel 本來就要重寫，順路改，不多花一次。
3. **量過才決定**：延遲真的礙事，再考慮合一（②或④）；cpu 真的上千顆，再做「一支管家管多個家」。日常手感先用一支 `aos up`／`aos down` 包起來。

理由：③ 是唯一一格甲乙吵完都能接受的；它碰的已拍板前提最少（只有「kernel 的家也照 cpu 範式、帳本是 state.json」這條要放寬）；壞了能退回 ①。② 雖然兩份 codex 都選，但它不解規模、還多了「改程式要重開」和「自己等自己」兩個新坑，而且兩份 codex 其實是同一顆模型。

## 6. 要使用者拍的（附我的預設）

1. **這題現在要不要動？** 預設：不動，照 C 段；只在你點頭時做上面第 1 步（查一筆行程的入口）。
2. **你說的「合在一起」是要「開機只打一條指令」，還是真的要一支行程？** 預設：前者，用 `aos up`／`aos down` 包起來，程式不合。
3. **實作 proto5-2 的 kernel 時，帳本要不要換 sqlite？** 預設：要；cpu 家和信箱仍是檔案。
4. **「kernel 的家也照 cpu 範式、帳本是一份 state.json」可不可以只對 kernel 帳本放寬？** 預設：可以，其他家（cpu、daemon、agent）照舊四樣檔。
5. **工具做完、還沒記下就崩（結果不明），要不要規定工具得「重跑無害」？** 預設：不規定；照現在回報「結果不明」給 agent，不自動重試。
