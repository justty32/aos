**可以合一，也可以減少檔案依賴；但這是兩件可分開做的事。我會先選 B：合一、保留檔案介面。**

本次只讀文件與實作，未改檔、啟動服務、跑測試或碰模型。規模與保留比例皆為估計；proto5-2 尚未實作。

**先拆開「合一」的意思**

現在 daemon 是常駐的父行程；kernel 則是每格啟動、接好下一格、做完退出。這讓排程、agent、模型與工具共用「執行一次」機制。

同一執行檔的不同子命令仍可各跑一個行程，那主要改善包裝。以下 A、B 指 **daemon 與 kernel 共用一個常駐行程**，工具仍在外面執行。

另一條軸是資料怎麼交換、怎麼保存。JSON 是格式，檔案是載體；改 socket 仍可保留 JSON-RPC 2.0，協定本身不限定傳送方式。[JSON-RPC 規範](https://www.jsonrpc.org/specification)

SQLite 也會寫檔。因此合理目標是「不用大量小檔當信箱與帳本」，不是完全不落地；否則每天重開機就無法接續。

四案均可保留 `aos-exec` 工作、agent 只向 kernel 交件、模型／工具非同步排程、各池環境設定。

**A：全合一，記憶體排程＋SQLite，工作改走 socket**

- **優點／缺點：**省去兩邊檔案往返、tick 接棒與重讀帳本；可即時處理結果。但改動最大，排程出錯可能連孩子管理一起停，停機後也不能只靠 `cat` 查帳。
- **恢復：**接單先存資料庫，再回「已收到」；工作代號固定，重送不重建。派工、結果、待送回覆要記錄；重啟先處理舊孩子，再續派。自製 journal 則須自做重播。
- **上千顆：**有潛力，但必須另減少常駐 Python 數、避免全表掃描。合一或 SQLite 本身不保證吞吐量。
- **手感／前提：**可保留 `say／listen／ls` 指令，每天只啟動一個服務；但服務沒開時仍能 say、離線看舊回話，要另外設計。翻動 kernel tick 鏈、daemon 只管生死、實體四件套與原子放檔契約；可保留每個邏輯家的唯一寫入者。生死 pipe 若保留、工作另走 socket，就沒破「pipe 只管生死」；若混用 stdin/stdout 傳工作則會破。

**B：合一，但 requests／responses／state 仍是檔案**

- **優點／缺點：**省掉 kernel cpu 與 tick 接棒，保留手工投單、離線查帳和既有工具；改動較集中。但小檔、整份帳本寫入與共同故障範圍仍在。
- **恢復：**沿用先記帳再投遞、回音確認後才清除；快取只當加速，重啟以落地紀錄為準。舊 tick 鏈退出後，由外部服務管理器重拉整支程式，並重新對帳。
- **上千顆：**單做合一不足。檔案通知可少輪詢，但漏通知仍須巡檢；agent 讀大帳本、一顆 cpu 一支 Python 都沒有自動消失。
- **手感／前提：**聊天、`ls`、離線 say 幾乎照舊，每天開關可縮成一組。四件套、JSON-RPC、原子投遞、工作 cpu 的主人與 pipe 可保留；要改的是 kernel 每格外部執行及 daemon 只負責生死的邊界。內部仍應分兩個模組。

**C：daemon、kernel 分開，共用 SQLite**

- **優點／缺點：**保留故障隔離，以指定工作代號查一筆，不必讀整份帳本；同一筆交易可一起更新工作與待送回覆。但兩支程式共用資料格式、寫入可能互等，升級也需協調。SQLite 的 WAL 允許讀寫並行，仍同時只有一個寫入者。[SQLite 文件](https://sqlite.org/wal.html)
- **恢復：**資料庫處理未完成交易；程式仍須處理「已啟動孩子、尚未記好結果」的窗口，保存待執行項目、去重代號及主人世代。各筆狀態仍需指定主人。
- **上千顆：**比全帳本 JSON 更適合逐筆查改；要有索引、短交易、批次提交。整份 JSON 塞成一欄、鎖著等工具都不可取；行程數仍是另一題。
- **手感／前提：**CLI 可不變，檔案改為匯出供人看；每日仍有兩個角色要啟動，可用同一入口代辦。可保留 tick 鏈與生死分工，但需另定接棒方式；四件套由實體檔案改成資料表，原子投遞改成交易，外人只投單的規則改由存取介面維持。

**D：維持分工與檔案，針對規模改造**

- **優點／缺點：**最貼近 proto5／proto5-2：池式增減、通知＋巡檢、拆帳本、指定工作查詢、少量行程管多個 cpu 家。保留可觀察性，但檔案及跨檔恢復規則可能更多。
- **恢復：**沿用各家對帳；拆帳本後，要補跨檔提交紀錄，不能直接拆成幾份各寫各的。多家共用行程時，一次崩潰要逐家恢復。
- **上千顆：**完整做才有機會；只做 proto5-2 草稿仍留下三項已知瓶頸。cpu 名額不必等於常駐行程數；同時執行上千個程式仍有成本。
- **手感／前提：**聊天大致不變，`ls` 改池摘要，加減 cpu 可不用重開。每日自動拉回池是 proto5-2 的宣告式設計，不是合一才有的功能；先 kernel halt 清掉宣告後，仍需 kernel boot。通知保留既有信箱規則；拆帳本會改「唯一 state.json」及 agent 偷看帳本，合併 cpu 行程則需重訂一顆 cpu 與主人行程的關係、環境和生死隔離。

以「現有功能與設計可直接沿用多少」粗估，不是程式行數：

| 方案 | proto5 約保留 |
|---|---:|
| A | 四～六成 |
| B | 八～九成 |
| C | 六～七成 |
| D 完整版 | 七～八成；只加通知／池表則較高 |

**我會怎麼走**

選 **B 作第一個候選原型**：先驗證合一的收益，保留操作方式與恢復機制。A 更動太多，C 增加共享資料庫，D 則碰到你已說先不動的規模題。

若之後決定動工：

1. **第一步先拆開排程一步與啟動外殼。** 把睡眠、接下一格、等待 daemon 回覆移到外層，仍用舊檔案與獨立模式驗證行為。
2. 再由一個常駐主迴圈呼叫兩個模組；保留舊 CLI，先比較開關機、故障恢復與操作步數。
3. 只有量到瓶頸才另議儲存與 cpu 行程數；查單筆工作先建立穩定介面，避免 agent 綁死帳本長相。

這只是建議；`wf/WAIT_USER.md` C 段「規模先不動」仍有效。

**最大的三個風險**

1. **記帳成功不等於工具只做一次。** 工具已產生外部效果、結果尚未存下就崩潰，檔案與資料庫都不能替它倒帶；仍需「結果不明」、避免盲目重試，或讓工具自行去重。
2. **直接把現有兩個迴圈接起來會卡住。** kernel 現在會睡眠、等 daemon 回音；同一執行緒照搬可能等自己回覆，也延誤收屍與停機。合一必須重排等待方式，並避免工具阻塞管理者。
3. **遷移時出現兩份真相。** JSON 與資料庫若同時可寫，容易互蓋；每階段只能有一個正式帳本，另一份只供相容或展示。

**讀文件時需要修正的兩個印象**

- **原子換檔不等於斷電後一定留住。** `aos_home.py` 的寫入只有暫存檔＋replace／link，沒有明確同步到磁碟；既有崩潰測試主要是殺行程，不能據此宣稱突然斷電也安全。SQLite 也須選對持久化設定。[實作](../../../proto5/lib/aos_home.py)、[SQLite 落盤說明](https://sqlite.org/atomiccommit.html)
- **「agent 每格讀整份帳本」不是所有空閒 tick 都如此。** `aos_agent_runtime.py` 的 sweep 有待清項目才讀，而且可能每項重讀；status／等待回話又有其他讀取路徑。`proto5-2/spec/scale.md` 的每秒幾十 GB 是條件估算，不是實測磁碟流量；快取也不會消除 JSON 解析成本。

r5 試玩最痛的 `listen --wait` 只等「開始聽之後的新回話」、故障提示與加 cpu 操作，都可獨立改善，換底層不會自動修好。現行 `aos_agent_cli.py` 也**沒有 talk 子命令**；未來若加互動聊天，四案都能提供。
