# 反駁乙（回應備忘甲）
← [README](README.md)

## 站不住的幾句

1. **「記帳和交出去是同一筆交易，崩潰窗口消失」**：fork 出去的 `aos-exec` 會改外面的世界，這一步進不了 sqlite 的交易。工作跑完、結果還沒寫進 db 時 `aosd` 崩了，重開記 `Interrupted` 再重跑，副作用就發生兩次。窗口只是換了位置，還是得一個個想、一個個測。
2. **「跟 `aosd` 同一個行程組，`aosd` 死就一起收」**：爸爸被 KILL，同組的孩子不會跟著死，會變孤兒繼續跑。要靠 `PDEATHSIG`、subreaper 或 systemd 的 cgroup 才收得乾淨，甲沒寫。沒收乾淨，就是第 1 條的「重跑兩次」。
3. **「真正多出來的只是排程 bug 拖垮收屍」**：這句靠的是 proto5 的「daemon 重啟就要重 boot kernel」，但 proto5-2 已經改掉了（daemon boot 自己把池拉回來，kernel 鏈多半自己接上）。另外漏了一件：**改排程程式要重開 `aosd`，在跑的全部變 `Interrupted`**，連一次幾十秒的模型呼叫也算在內。現在是下一格就換新版，什麼都不斷。
4. **「兩步變一步、順序陷阱整類消失」**：`aos up` 包一層就能變一步，不用合程式。「halt 指錯家說 not running」是找家的問題，`aos.db` 放哪一樣要找，不會自己消失。
5. **「閒時零消耗」**：閒時是零，但每件工作都要 fork 一支 Python 的 `aos-exec`（約 50～100 ms），上萬件在跑也是上萬支。我的管家做法也一樣，所以這點兩邊打平，不是甲贏。
6. **遷移「四成」算輕了**：崩潰測試靠的是檔案當閘門，得整套重寫；規範方面，kernel、daemon、cpu 三份要換掉，另外還有五條使用者拍過的前提要請他重拍。

## 對方哪幾點我認了

- **延遲**：事件迴圈不用等一格，這是甲實打實的優勢，我的 inotify 提早開格只能縮小差距。
- **我的 `commits/` 就是在手工做一個資料庫**：要自己寫壓縮、自己寫恢復，甲說得對。一次交易改好幾件事，sqlite 比我自己寫的可靠。
- **proto5-2 的通知檔、巡檢、交接，不少是為了繞開檔案的限制才有的**，這份複雜度我在備忘乙 §6 也認了。
- **aos-agent 查自己的狀態只要查一列**，比偷看整份帳本好；我的「一行程一檔」只是在檔案上模仿這一點。
- 折衷可以考慮：**帳本改用 sqlite，但 kernel 仍一格一格跑、daemon 照舊分開、cpu 的家照舊用檔案**。這樣排程出錯不會拖垮收屍，改程式不用重開，交易也拿得到。
