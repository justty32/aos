# codex 獨立意見一：gpt-6-astra（medium）
← [README](README.md)｜[任務書](codex-task.md)

> 唯讀，沒看甲乙備忘。原文照錄，只把絕對路徑連結改成相對路徑。

**可以合成一支程式，也可以減少對 JSON 檔案的依賴；但這是兩個可分開做的改動。我的選擇是先 B，再視需要走向 A，不一次重寫。**

本次只讀文件與原始碼，未改檔、未啟動 daemon／kernel、未跑模型或測試。以下容量與保留比例都是設計判斷，沒有壓測背書。

「合一」改的是**誰負責執行**：現在 daemon 常駐管孩子，kernel 則每格啟動、讀帳本、排工作、退出。可以把排程搬進 daemon，同一行程內仍分成兩個模組。

「脫離檔案」改的是**怎麼交件、怎麼記住進度**。兩支程式可以共用資料庫；一支程式也可以繼續收檔案。SQLite 本身仍是檔案，真正能拿掉的是「每件工作都靠多個小檔案往返」的機制。JSON 設定、人格、工具定義也不必一起淘汰。

現在的檔案同時兼任信箱、帳本、斷線緩衝與除錯介面。拿掉之後，這四項能力都要有接替者。

以下「保留幾成」指既有功能、格式與模組可沿用的粗估，不是程式行數。

**A．全合一，記憶體排程＋SQLite，工作走本機 socket**

- **優點：**拿掉 daemon↔kernel 檔案往返與 tick 接鏈；只查、改相關工作，較容易即時通知。設定和工具檔仍可保留。
- **缺點：**排程錯誤可能連孩子管理一起拖垮；服務停止時，不能直接用 socket 投話，必須另有離線信箱。人工救援也要補查詢、匯出工具。
- **恢復：**先把工作與待發訊息一起存妥，再送出；用固定工作代號辨認重送，结果保存到簽收。重開後確認舊孩子已停，再處理未完成工作。Socket 傳成功不等於工作已存妥。
- **千顆：**最有改善空間，但若仍一顆 cpu 一支 Python，記憶體問題照舊。上千個登記與上千件同時執行，是不同難度。
- **手感：**`say／listen／ls` 名字可不變；每天可只開一個服務，但自動恢復哪些工作必須明定。直接摸信箱的腳本要改。
- **前提／保留：**改掉 kernel 的 exec 接鏈、四樣檔案介面與 `link` 投遞；「單一主人」、JSON-RPC 2.0、非同步工具仍可保留。控制 pipe 可繼續只管生死，工作另走 socket。約留 **四至六成**。

**B．合成一個常駐行程，保留檔案介面**

- **優點：**開關機較簡單；省掉 kernel 每格重新啟動與讀帳本，現有 cpu、agent、人工查檔方式大致沿用。最適合先驗證「合一到底值不值得」。
- **缺點：**小檔案往返、整份帳本寫入、agent 偷看帳本仍在。快取只能減少讀取，不能把「先記帳再派工」延到事後。
- **恢復：**保留帳本與待出貨清單，重新啟動時補送、對帳；需要外部啟動者重拉整個服務。檔案通知只作喚醒提示，漏通知仍須巡檢。
- **千顆：**單靠合一不夠，主要減少固定開銷，沒有消除三個規模瓶頸。
- **手感：**聊天、查狀態與停機時先投話均可保持；每天少一層開機。服務停著仍可讀最後帳本。
- **前提／保留：**改掉 kernel 接鏈與 daemon「完全不認識 kernel」的程式邊界；四樣檔案、JSON-RPC、原子投遞、cpu 主人規則可留。約 **七至八成半**。

實作不能直接把現有 tick 塞進 daemon 迴圈：tick 的 `_daemon_call()` 會等 daemon 回音，同一條迴圈就可能等自己。應改成內部呼叫，且排程不能阻塞孩子的收屍與停機。[實作](../../../proto5/lib/aos_kernel_engine.py)

**C．daemon、kernel 分開，共用 SQLite**

- **優點：**保留兩邊的故障隔離；帳本能逐筆查改，交件、結果與簽收也能放進資料庫。人看的 JSON 改成匯出資料。
- **缺點：**仍需處理兩支程式交接；共用資料表會增加耦合，不能讓雙方任意改彼此狀態。若只把整份 JSON 塞進一欄，主要瓶頸仍在。
- **恢復：**資料庫交易保護記帳一致性，但啟動孩子、執行工具不在交易內，仍須先記意圖、事後對帳、辨識重送。
- **千顆：**比整份帳本有利；SQLite WAL 同時仍只有一個寫入者，必須縮短交易、避免持鎖等工作完成。cpu 行程數問題另解。[SQLite 官方說明](https://www.sqlite.org/wal.html)
- **手感：**CLI 可保持；停止服務後仍能查資料、投件，前提是 CLI 支援資料庫信箱。每天開兩層的程序不會自動消失，可另包一個入口。
- **前提／保留：**保留分工、pipe 生死控制與 JSON-RPC；改掉實體四樣檔案、原子放檔與直接偷看帳本。各表仍可指定唯一負責者。約 **六至七成半**。

**D．維持分開與檔案，針對規模改善**

- **優點：**延續既有可觀察性與恢復經驗；拆帳本、逐工作查詢、回音通知、池式管理可以分項做。
- **缺點：**拆檔後，多份狀態如何一起更新會變難；不能直接拆開目前「一次寫入就全部生效」的帳本。檔案、日誌與清理工作仍多。
- **恢復：**保留先記帳、後投遞、收妥再簽收；跨檔變更另需可重做的操作紀錄。通知漏掉靠巡檢補。
- **千顆：**有機會，但 proto5-2 草稿本身還不夠：整份帳本、agent 讀帳本、一 cpu 一 Python 都還在。多個家共用一支執行程式才會改變最後一項，代價是一崩影響多顆。
- **手感：**聊天最接近現在；池式增減可免手改配置。重開機是否自動恢復取決於宣告是否保留，不能只看用了檔案還是資料庫。
- **前提／保留：**通知與拆帳本大致保留範式，但會改「唯一 state.json」及讀帳本契約；多家共用行程則需重訂 cpu 與父子關係，不能稱為純優化。約 **八至九成**。

規模限制與尚未實作的範圍，見 [proto5-2 scale.md](../../../proto5-2/spec/scale.md)。

**我會先選 B，但把它當可回退的一步。**

理由是目前已有的價值包含故障後能接續、檔案能直接查、agent 與工具能組合；先保住它们，再確認合併是否真的簡化使用。若主要目標變成上千顆低成本 cpu，才值得投資 A 的資料庫與共用執行者。

建議順序：

1. **第一步先訂清楚相容與恢復契約：**停機時能不能投話、何時算收件成功、重開是否自動續跑、結果不明能否重試。這些不能讓換儲存方式偷偷決定。
2. 經授權後做 B 的小原型，保留現有 CLI 與檔案；用假工作比較開關機、等待時間及崩潰恢復，不需要模型。
3. 有必要才把「交件、查單一工作、收結果」抽成共同入口，解除 agent 直接讀整份帳本的依賴。
4. 再決定接 SQLite、socket，或走 D 的檔案改善；cpu 行程數另案處理。

這次不把方案視為動工授權；[WAIT_USER C 段](../../../wf/WAIT_USER.md) 明確說規模三題先不動。

**最大的三個風險：**

- **重複做外部事情。**工具已完成、結果尚未記下就崩潰，任何方案都可能只知道「結果不明」。資料庫不能保證寄信、付款或改外部檔案只做一次。
- **合一擴大故障範圍。**排程卡住不能連停止孩子都做不到；舊孩子未確認停止，也不能讓新任搶同一份工作。
- **過渡期有兩份真相。**資料庫與 JSON 若都可改，就容易互相覆蓋。必須只有一份正式帳本，另一份只是匯出或明確的相容入口。

**另外三處值得釐清：**

1. **抗行程崩潰，不等於抗斷電。**目前 `aos_home.py` 用暫存檔＋替換／連結，沒有同步檔案及目錄落盤；既有 KILL 測試不能證明突然斷電也不丟資料。正常關機與硬斷電需分開談。[原始碼](../../../proto5/lib/aos_home.py)、[fsync 說明](https://man7.org/linux/man-pages/man2/fsync.2.html)
2. **「每天只開 daemon」有條件。**proto5-2 若先正常 `kernel halt`，池會縮零並消失；下次仍需 kernel boot。只有保留宣告時，daemon 重開才通常能拉回。[handoff.md](../../../proto5-2/spec/handoff.md)
3. **手感問題不全是儲存問題。**r5 的 `listen --wait` 會錯過開始聽之前已到的答案；換 socket 也不會自動修好，需要「等哪一句」的識別。目前 CLI 沒有 `talk`；將來可做聊天入口，四案都能加。[r5 紀錄](../../../proto5/notes/play/2026-09-24-r5-opus.md)
