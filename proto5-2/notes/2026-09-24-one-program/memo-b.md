# 備忘乙：保持分開＋保持檔案
← [README](README.md)

立場：**不合、不脫檔**，把規模問題在檔案體系裡修掉。先說清楚：「合一」跟「脫檔」是兩件事，可以只做一件；我兩件都反對，理由分開講。

## 1. 分開＋檔案現在換到了什麼

- **排程出錯不連坐**：kernel 最常改、最複雜（約 1400 行），但它不是常駐程式，一格崩了只丟那一格，下一格照接，cpu 全不受影響。daemon 最簡單（430 行）才當爸爸。合一後排程一個例外＝所有 cpu 的爸爸死掉＝全部重拉。
- **改 kernel 程式不用重開**：每格都是新行程，改完下一格就是新版；也不會越跑越吃記憶體。
- **崩潰恢復已經驗過**：daemon C-2／C-3、kernel C-7／C-8 共 26 條「卡住再 KILL」測試，**產品程式一行沒改就全過**。靠的是「先記帳（一次原子寫）再動檔」。合一或換資料庫，這批窗口要重想、重測。
- **人和 agent 都看得懂**：`cat`、`ls` 就能查；agent 用 POSIX 工具就能看系統狀態。任何語言寫個檔就是客戶，不用連線函式庫。
- **重開機自然**：狀態本來就在磁碟上，沒有「關機前要存檔」這一步。

## 2. 老實說：上千顆時哪裡會垮

| 問題 | 多嚴重 | 修法（仍是檔案） |
|---|---|---|
| kernel 帳本整份讀寫 | 萬顆約 3 MB，每格讀一次、寫最多四次 | 拆帳本（§3） |
| aos-agent 每格偷看整份 `K/state.json` | 全系統最大負擔，萬個 agent 每秒讀幾十 GB | 一行程一個小檔，agent 只看自己那檔 |
| 一顆 cpu 一支 Python | 萬顆約 100～200 GB 記憶體 | 一支「cpu 管家」行程管 256 個家 |
| cpu 每 0.2 秒掃資料夾 | 萬顆每秒 5 萬次列目錄（proto5 預設 20 ms 更糟） | 改 inotify：等檔案出現，沒事不掃 |
| `K/requests/` 單一資料夾 | syscall 和回音通知擠一起 | 通知另開 `K/notify/` |

**修完還剩的天花板**（沒量過，要先做壓測）：kernel 仍是一條鏈、一格一格串著跑，每格開一支 Python（約 50～100 ms）；agent 每走一步至少等一格，一輪對話要好幾格——**延遲是這條路最弱的地方**。緩解：kernel cpu 也用 inotify，有新通知就提早開下一格，不必睡滿 `tick_ms`。我估千顆舒服、萬顆要調系統上限（inotify、行程數、開檔數），十萬顆以上該換架構。

## 3. 設計草圖：檔案版的上千顆

```text
aos-daemon（只管生死；孩子數＝管家數，不是 cpu 數）
 ├─ kernel cpu（單獨一支，tick 鏈照舊）
 ├─ aos-cpu-host default#0   管 default/0..255 這 256 個家
 ├─ aos-cpu-host default#1   管 256..511
 └─ aos-cpu-host llm#0
K/state.json        小：chain、phase、池表、閒號堆疊
K/commits/<N>.json  這一格的全部決定（提交點，一次原子寫）
K/procs/<名>.json   一行程一檔；aos-agent 只看自己那檔
K/requests/  K/notify/
```

- **一格怎麼記帳**：算完 → 寫 `commits/N.json`（提交點）→ 逐檔套到 `procs/`、`state.json`（寫完整值，重做無害）→ 刪 commit 檔。崩在中間，下一格先把殘留的 commit 套完。仍是「每個決定一次原子寫」，只是寫的量＝這格有事的量。
- **cpu 怎麼接**：「一個家一個主人」不變，主人換成管家行程；每個家照舊有自己的 `requests/`／`responses/`、自己的鎖，開機對帳照 cpu.md §6.1 逐家做。真正的工作本來就另開子行程跑，管家只收單、派、寫回音，很輕。
- **停機與重開**：照 proto5-2：`aos-daemon halt` 留宣告，`boot` 把管家拉回、管家逐家對帳；kernel 鏈多半自己接上。
- **崩潰**：kernel 一格崩＝丟一格；管家崩＝那 256 顆在途的變 `Interrupted`、daemon 重拉（波及從 1 顆變 256 顆，這是代價）；daemon 崩＝同 proto5，新任殺光舊孩子重拉。

## 4. 使用者手感

- `aos-agent say／listen／talk`、`aos-kernel ls`：**完全不變**，底下換什麼看不到。
- 每天重開機仍是兩步（daemon boot → 必要時 kernel boot）、兩個家、兩個環境變數——試玩「要背的東西少」只拿 3 分，這是原因之一。**但這不用合程式來解**：加一支 `aos up`／`aos down` 包起來，外面像一支，裡面照樣分開。

## 5. 遷移代價

- **不用動**：aos-exec、inst、指示詞、aos-llm、agent 資料夾、aos-agent 大部分（約 3600 行，程式近六成）；這些部分的測試；崩潰測試的手法。
- **要改**：aos-agent 清檔與 status 改看 `K/procs/<名>.json`（幾十行，但要改 aos-agent.md §10）；cpu 主人改成管家＋inotify（約 600 行重寫）；kernel 帳本拆檔（kernel 約 1400 行，本來 proto5-2 就要重寫）。
- **跟 proto5-2 怎麼接**：proto5-2 已經是這條路的前半（池、宣告、通知檔、只碰有事的 cpu）；它 README「要使用者拍的」1～3 題，正好是 §2 的三個修法。**不用另開新架構，把那三題拍成「要修」就是這條路**。估計程式約六成不動、四成重寫，而那四成大多本來就在 proto5-2 範圍內。

## 6. 我這邊的弱點（先自己說）

延遲（每步等一格）；每格開行程的固定 CPU 成本；daemon 和 kernel 之間要協定（proto5-2 的 scale 單、交接、崩潰窗口表都是為此而生，這份複雜是真的）；管家讓一次崩潰波及 256 顆；原子改名沒有 fsync，斷電可能丟最後幾筆（資料庫不 fsync 也一樣）。
