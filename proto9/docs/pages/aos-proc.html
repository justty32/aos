aos proc 介面

一個 aos proc 是一個活著的行程，加上它擺出來的一個目錄。要控制它、看它的狀態、找它的東西，都是讀寫那個目錄裡的檔。

$ ls $AOS_ROOT/procs/repo/procs/agent/
ctl  status  settings  attrs  _metainfo.json  mailbox/  sock  persist
$ cat $AOS_ROOT/procs/repo/procs/agent/status
aos_name: repo/agent
aos_phase: running
aos_pid: 1502
…
$ echo pause > $AOS_ROOT/procs/repo/procs/agent/ctl

擺得出這個目錄、照這頁的格式回答的，就是 aos proc。是誰寫的、用什麼語言都不管。檔案不在硬碟上：有一支活著的程式在你讀寫的那一刻當場回答（第一步用 FUSE 做）。行程一死，目錄就走不進去了。

目錄裡有什麼

名字讀寫是什麼
ctl只寫控制它。純文字，一行一道指令
status只讀它現在怎樣。純文字，一行一個「名稱: 值」
settings只讀它的東西放哪。起來時就定，之後不變
attrs只讀它是哪一種身體、能不能當場回答、收哪幾種訊息。要用它的人看了自己決定怎麼做
_metainfo.json只讀它是什麼（定義帶來的那份，json）
persist—走到它要留下來的東西。身體沒了，這裡還在
mailbox/、msg、sock寫活著時收訊息的三個口，提供哪幾個自己選（見「送訊息」）

daemon 也是一隻 aos proc，另外多三樣：

名字讀寫是什麼
procs/讀底下每隻 proc 一項，走進去就是它的目錄。只有活著而且會回答的走得進去。別名 proc/
procs_ctl只寫管底下的 proc：加、拿掉、起、停、強制收
procs_status只讀底下每隻 proc 的狀態。死了、停著、卡住的也在這張表上

aos_ 開頭的名稱是 aos 標準的，意思照這份介面。其餘的名稱 proc 自己用，愛叫什麼叫什麼。不認得的行跳過。

怎麼走進去

  • AOS_ROOT 由人維護：根重開後提示自己的 PID，人自己 export。樹裡的 proc 由 daemon 起，daemon 直接交給它。
  • 別看錯層：Linux 自己的 /proc/1221/status 講的是那支 Linux 行程；aos 的在再下一層 /proc/1221/cwd/status。
  • 沙箱裡走不進來是本來就要的，有需要再把那個目錄開給它。

ctl：一次一個人，從寫進去到做完都鎖住

基礎的三個字

stop 做完手上這一步就結束；pause 停住，行程還在；resume 繼續。字表不訂死，其餘各 proc 想收什麼收什麼。

不認得的字：那次寫入失敗，原因記在回饋裡。一次寫入只收一道。

回饋在 status 裡

aos_ctl_cmd: pause
aos_ctl_state: done
aos_ctl_error: -
aos_ctl_count: 3

state 有四種：doing、done、failed（收下了但沒做成）、rejected（不收）。講的一定是最後收下的那一道。

鎖著的時候要強制收，不寫它自己的 ctl，寫它 daemon 的 procs_ctl。

status、settings、attrs

三個檔照「誰決定、什麼時候會變」分：status 一直變；settings 起來時定；attrs 是這種身體天生的。

status

aos_name: repo/agent
aos_phase: running
aos_pid: 1502
aos_started_at: 2026-11-25T15:48:45+08:00
aos_ctl_cmd: -
aos_ctl_state: -
aos_ctl_error: -
aos_ctl_count: 0
stage: think

最後一行不帶 aos_，是這隻 proc 自己加的。

settings

aos_persist: /tmp/aos/persist/repo/agent
aos_mailbox: /tmp/aos/persist/repo/agent/mailbox

attrs

aos_kind: fuse
aos_live: yes
aos_mailbox: yes
aos_sock: yes

aos_live: no 的 proc 沒人當場接：寫 ctl 回來不代表收到、鎖也擋不住，要用的人自己小心。

daemon：Linux 與 aos 之間的橋

起行程、收屍、送訊號這些 Linux 的事，只有 daemon 做。它記著底下每一隻的樣子，所以 proc 死了以後，還答得出來的只有它。

procs_ctl 的字

add 名字 路徑加一隻並起它
rm 名字收掉、從表上拿掉
stop／start叫它好好收尾後留在表上／再起
kill 名字現在就收。卡住、鎖著時用
register 名字 PID只登記、不起：已經在跑的行程來報到

這裡的「做完」是 daemon 這邊的動作做完，不等那隻 proc 真的結束；結果看 procs_status。

procs_status

agent.phase: running
agent.want: up
agent.pid: 1502
agent.stuck: no
agent.mailbox: /tmp/aos/persist/repo/agent/mailbox
arena.phase: stopped
arena.want: up
arena.code: 1
arena.reason: exited within 3s of start

want 是人要它怎樣，phase 是它實際怎樣。

  • 「登記」＝daemon 讀得到這隻 proc 的 settings。期限內讀不到就收掉，記成起動失敗。
  • proc 死掉後留下的掛載，daemon 收屍時順手清掉。
  • daemon 自己掛了，底下還活著的它不管，自行承擔風險。

卡住，以及不讓它傳染

「卡住」＝行程還在，但不回答了，讀它的 status 不會回來。讀的人會跟著卡住。被 Linux 暫停的行程也算。忙不算卡住：手上一直在做事、但讀得到 status 的是正常的。

一條規矩斷掉連鎖：回答只用自己記憶裡的東西。每隻 proc 至少留一條線專門回答別人，這條線上不做久的事、不去讀寫任何別的 proc。要問別人，放在做事的線上問，而且帶期限。

守這條規矩的上層，不會被壞掉的下層拖住。一台 daemon 卡住，代價是它底下那一整棵從名字路走不到了：底下的 proc 沒卡住、照樣在跑，只是被隔開。不守規矩的，自己承擔風險。

送訊息

基礎的走法分兩類：寫檔（普通檔案、FUSE 擺出來的檔）和串流（unix socket）。寄信（aos post）是建在寫檔之上的。不管走哪條，送的都是同一封信（一份 json：寄件人、標題、內文、回信位址）。

  • 一隻 proc 提供哪幾個口自己選，寫在 attrs。
  • socket 上送來的算直接進對話的話，還是信，proc 自己決定，預設是進對話。
  • socket 的回條意思是「收到」，跟 ctl 同一級。連不上、對方沒先開口、期限內沒回條，就改走寄信，用同一個信名，收的人照信名擋重複。
  • 問信箱在哪的時候要不要順手叫醒對方，是 daemon 自己的可選設定。

留下來的東西

身體是活的：行程在，目錄才在。要留的東西各自處理，推薦的位置是 persist，在哪以 proc 自己在 settings 說的為準；daemon 可以給預設位置。

遠期目標是把根的目錄整個複製走，就能把一切搬走。為了這個，現在先守兩條：每隻 proc 要留的東西從它自己的目錄走得到；留下來的檔裡指別人用名字路，不用絕對路徑、不用 PID。

抄了誰

沒有找到一模一樣的現成系統，最像的是 Plan 9 的 /proc（那邊由系統核心統一回答，這裡是每隻 proc 自己回答）。零件各有出處：ctl 與 status 的想法來自 Plan 9；信箱是 Maildir；寫一個檔就送出訊息是 Plan 9 的 plumber；socket 上一行一則照 JSON Lines；交給孩子的環境變數怎麼防誤認照 systemd；查卡住與放開卡住的人用的是 Linux 給 FUSE 的開關。
