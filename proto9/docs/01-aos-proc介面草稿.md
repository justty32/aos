# aos proc 介面（草稿第 1 版，11-25）

← [proto9](../README.md)｜原話與每輪定了什麼：[9P proc 談話紀錄](../../proto8/thinking/2026-11/25/9p-proc-1125.md)

**怎麼讀這頁**：每一條前面有一個記號。

- 【定】使用者說過的。原話在談話紀錄裡，這裡只寫結果。
- 【擬】eca-aos 自己挑的，還沒有使用者的話；他看了不對就改。
- 【開】還沒談。

寫這頁的是 `eca-aos`。還沒有任何正式的程式照這頁做；只有一個玩具實驗（[fuse-proc-1125](../experiments/fuse-proc-1125/README.md)），第 11 節是它查到的。

第 1 版（11-25 下午）：使用者看過第 0 版裡 eca-aos 挑的幾樣，答「好，我覺得都可以。」——`aos_` 開頭推到所有標準行、`status` 第一批、ctl 回饋四行、`procs_ctl` 的字、`procs_status` 的欄、`attrs` 的兩行與讀法，都改標【定】；加進 FUSE 小實驗的結果。

## 1. 一句話

【定】一個 **aos proc** 是一個活著的行程，加上它擺出來的一個目錄。別人要控制它、看它的狀態、找它的東西，都是讀寫那個目錄裡的檔。擺得出這個目錄、照這頁的格式回答的，就是 aos proc；是誰寫的、用什麼語言都不管。

【定】介面＝目錄的長相＋每個檔的內容格式。

【定】proto9 裡的 aos proc 要**當場回答**：有一支活著的程式在你讀寫的那一刻接手。第一步的做法是每隻 proc 用 FUSE 把自己的目錄掛出來。

## 2. 幾個詞

| 詞 | 意思 | |
|---|---|---|
| 身體（stack） | 一隻活著的 proc 的目錄。行程死了就走不到 | 【定】 |
| persists | 這隻 proc 要留下來的東西放的地方。身體沒了它還在 | 【定】 |
| daemon | Linux 與 aos 之間的橋。本身是 aos proc，另外多一個放「底下的 proc」的夾 | 【定】 |
| 根 | 最上面那台 daemon | 【定】 |
| kernel | 普通的 aos proc，只是帶了某種功能（發模型額度、管權限…） | 【定】 |
| 名字路 | 從根往下一路的名字，例 `repo-aos/eca-aos`。這是一隻 proc 的身分；名字可以自己指定 | 【定】 |

## 3. 怎麼走進去

- 【定】入口是根 daemon 的 PID：`AOS_ROOT=/proc/<根的 PID>/cwd`。Linux 的 `/proc/<PID>/` 不加任何東西；`cwd` 是核心本來就給的，指到那支行程站的資料夾，所以每隻 proc 都站在自己的目錄裡。
- 【定】`AOS_ROOT` 由人手動維護：根重開後提示自己的 PID，人自己 export。可以有方便的做法（例：用特殊指令起根，順手設好）。
- 【擬】樹裡的 proc 不用人管：daemon 起它時，把 `AOS_ROOT` 放進它的環境。要手動的只有樹外的殼。
- 【定】往下走：`$AOS_ROOT/procs/<名>` 就是那隻 proc 的目錄，一層一層可以一直走。`proc` 與 `procs` 兩個名字指同一處。
- 【擬】用舊的 `AOS_ROOT` 之前先認一下：根死了、PID 被別的行程拿走之後，舊值會安靜地指到別人的資料夾。讀 `$AOS_ROOT/status` 有 `aos_name` 那一行、而且是根，才算數。
- 【定】沙箱裡走不進來是本來就要的，有需要再開口子。換 Linux 帳號的 proc 怎麼進來，之後再想。

**容易看錯層的名字**：Linux 自己的東西在 `/proc/<PID>/` 那一層，aos 的在再下一層 `/proc/<PID>/cwd/`，兩邊不會撞。但 Linux 那層有 `status`、`attr`（少一個 s）、`stack`、`root`，跟 aos 的 `status`、`attrs` 長得像，下指令時看清楚有沒有 `cwd`。

## 4. 目錄裡有什麼

每隻 aos proc：

| 名字 | 是什麼 | 讀寫 | 格式 | |
|---|---|---|---|---|
| `ctl` | 控制它 | 只寫 | 純文字，一行一道 | 【定】 |
| `status` | 它現在怎樣 | 只讀 | 純文字，一行一個「名稱: 值」 | 【定】 |
| `settings` | 它的東西放哪（起來時就定的） | 只讀 | 同 `status` | 【定】 |
| `attrs` | 它是哪一種身體、能不能當場回答；要用它的人看了自己決定怎麼做 | 只讀 | 同 `status` | 【定】 |
| `_metainfo.json` | 它是什麼（定義帶來的那份） | 只讀 | json，照 aos 現有的 | 【定】 |
| `persists` | 走到它要留的東西 | — | 一個夾（或指過去的連結） | 【定】推薦位置；怎麼擺【開】 |

daemon 另外多：

| 名字 | 是什麼 | 讀寫 | |
|---|---|---|---|
| `procs/`（別名 `proc/`） | 底下每隻 proc 一項，走進去就是它的目錄 | 讀 | 【定】 |
| `procs_ctl` | 管底下的 proc（加、拿掉、起、停、強制收） | 只寫 | 【定】 |
| `procs_status` | 底下每隻 proc 的狀態，**死了、停著的也在** | 只讀 | 【定】 |

以後才有的：

- 【定】每個純文字檔另給一份 json：`settings.json`、`status.json`…（跟 `_metainfo.json` 同一種叫法）。之後再做。
- 【定】`status` 以外可以再多給別的檔，例：報 token 用量的檔。名字與內容【開】。
- 收訊息的 `sock` 與 `msg`（第 9 節）。

【擬】上面這些名字是保留的；proc 自己要多擺什麼檔都可以，別用這些名字就好。

## 5. 純文字的寫法

【定】一行一個「名稱: 值」。以下細節【擬】：

- 名稱：小寫英文字母、數字、底線。冒號後一個空白，之後到行尾都是值，原樣。沒有值寫 `-`。
- 【定】**`aos_` 開頭的名稱是 aos 標準的**，意思照這頁；其餘的名稱 proc 自己用，愛叫什麼叫什麼。`status`、`settings`、`attrs` 都照這條。
- 不認得的行跳過。現在不標版本。
- 行的先後沒有意思，照名稱找。

## 6. ctl

- 【定】一行一道，純文字。寫回來＝**收到**；做完沒有，看 `status`。
- 【定】字表不訂死。只訂基礎且通用的，其餘各 proc 想收什麼收什麼。
- 【擬】基礎的三個字：

  | 字 | 做什麼 |
  |---|---|
  | `stop` | 做完手上這一步就結束 |
  | `pause` | 做完手上這一步就停住，行程還在 |
  | `resume` | 解除 pause |

- 【定】**鎖**：一個人搶到之後，從他寫進指令到 proc 做完那個動作，都鎖住；另一個人會發現自己寫不進去。
- 【擬】鎖的細節：
  - 寫不進去＝那一次寫入當場失敗（忙），**不動 `aos_ctl_*`**，先搶到的人的回饋才不會被蓋掉。
  - 「做完」：`pause` 是停住了就算做完（鎖放開，才收得了 `resume`）；`stop` 是行程結束。
  - 鎖著的時候要強制收：寫它 daemon 的 `procs_ctl`（第 8 節）。proc 自己的 ctl 只有客氣的字。
- 【定】**回饋放 `status`，行名 `aos_ctl_` 開頭**，講的一定是最後一次 ctl。被拒的原因也在這裡。
- 【定】回饋的四行：

  | 行 | 值 |
  |---|---|
  | `aos_ctl_cmd` | 最後收下的那一道，原樣；還沒收過＝`-` |
  | `aos_ctl_state` | `doing`（在做，鎖著）／`done`（做完）／`failed`（收下了，做的時候失敗，原因看下一行）／`rejected`（不收，原因看下一行） |
  | `aos_ctl_error` | `代號 原因`，例 `CommandUnknown frobnicate`；沒事＝`-` |
  | `aos_ctl_count` | 起來之後收下過幾道；下指令的人記著自己那道是第幾，就知道回饋有沒有被後來的人換掉 |

- 【定】不認得的字：記成 `rejected`（原因在 `aos_ctl_error`），同時讓那次寫入失敗，下指令的人當場就知道。
- 【定】一次寫入只收一道；多行就拒。

## 7. status、settings、attrs

三個檔照「誰決定、什麼時候會變」分：`settings` 是起來時定的，之後不變；`attrs` 是這種身體天生的；`status` 一直變。

**`status` 第一批**（【定】）

| 行 | 值 |
|---|---|
| `aos_name` | 名字路，例 `repo-aos/eca-aos`；根自己是 `/` |
| `aos_phase` | `running`／`paused`／`stopping` |
| `aos_pid` | 回答的這支行程的 PID |
| `aos_started_at` | 這個身體起來的時間 |
| `aos_ctl_cmd`、`aos_ctl_state`、`aos_ctl_error`、`aos_ctl_count` | 見第 6 節 |
| （daemon）`aos_procs` | 底下有幾隻 |
| （daemon）`aos_procs_ctl_cmd`、`_state`、`_error`、`_count` | `procs_ctl` 的回饋，規則同 `aos_ctl_*` |

proto8 的 `updated_at`、`responded_at`、`boot_id`、`started_at_ticks` 沒收：那些是「檔會活得比行程久」才需要的；當場回答的 proc，讀得到就是活著。proc 自己的行（agent 的 `stage`、排著幾封信…）不帶 `aos_`，自己加。

**`settings`**（行【擬】）

| 行 | 值 |
|---|---|
| `aos_persists` | 它要留的東西在哪（硬碟上的真實位置） |
| `aos_mailbox` | 它掛了的時候，信投到哪 |

【定】persists 在哪，以 proc 自己在 `settings` 說的為準；daemon 起它之後來讀。daemon 可以給預設位置，在 `/tmp` 開一塊。proc 沒說就死了，daemon 就不知道。

**`attrs`**（【定】）

| 行 | 值 |
|---|---|
| `aos_kind` | 這個目錄是怎麼擺出來的：`fuse`／`file`（硬碟上的普通檔）／`tmp`（記憶體裡的普通檔）／… |
| `aos_live` | `yes`＝當場回答（寫 ctl 回來就是收到、鎖擋得住）；`no`＝沒人當場接，寫進去只是放著 |

【定】要用它的人照 `aos_live` 決定怎麼做，`aos_kind` 只是說明（以後會有新的種類）。沒有 `attrs` 就當 `aos_live: no`。

【定】proto9 自己做的 proc 全部當場回答。`attrs` 是留給別人做的別種身體（普通檔、記憶體裡的普通檔…）表明自己用的：它們也算 aos proc，只是要用的人得自己小心（寫 ctl 回來不代表收到、鎖擋不住）。

## 8. daemon 多的三樣

- 【定】`procs/<名>`：走進去是那隻 proc 的目錄。只有活著的走得進去。
- 【定】`procs_ctl`：管底下的 proc 的字寫這裡，不寫 daemon 自己的 `ctl`（那個只管 daemon 自己）。
- 【定】`procs_ctl` 的字：

  | 字 | 做什麼 |
  |---|---|
  | `add 名字 路徑` | 加一隻並起它。路徑是定義夾，或一份 json 檔（其餘參數放裡面） |
  | `rm 名字` | 收掉、從表上拿掉（persists 不刪） |
  | `stop 名字`／`start 名字` | 叫它好好收尾後留在表上／再起 |
  | `kill 名字` | 現在就收（強制；proc 卡住、ctl 鎖著時用） |
  | `register 名字 PID` | 只登記、不起：一支已經在跑的行程來說「我是 aos proc」 |

  proto8 的 `sleep`／`wake` 要不要留【開】。鎖與回饋的規則同第 6 節。

  【定】`procs_ctl` 的「做完」＝daemon 這邊的動作做完（例：`stop arena` 是把字送給 arena 了），不等那隻 proc 真的結束；結果看 `procs_status`。這樣 `stop` 很久的時候，`kill` 才下得進去。

- 【定】`procs_status`：底下每隻 proc 的狀態，純文字。proc 死了，它自己的 `status` 就沒了，這張表是唯一還答得出來的地方。
- 【定】行名是 `名字.欄名`，欄有 `phase`、`want`、`pid`、`code`、`reason`、`persists`、`mailbox`：

  ```
  arena.phase: stopped
  arena.want: up
  arena.pid: -
  arena.code: 1
  arena.reason: exited within 3s of start
  arena.persists: /tmp/aos/persists/repo-aos/arena
  arena.mailbox: /tmp/aos/persists/repo-aos/arena/mailbox
  ```

- 【定】照報告的推薦走的四件（細節都還【擬】）：
  - 想要的樣子（`want`：人要它活著還是停著）與實際的樣子（`phase`）分開記。
  - 死因（結束碼、被什麼訊號收的、原因一句）由 daemon 留在這張表。
  - 起了卻一直不登記（讀不到它的 `settings`）的，等到期限就收掉、記成起動失敗。
  - 強制手段歸 daemon。

### 卡住

「卡住」＝那隻 proc 的行程還在，但不回答了：讀它的 `status` 不會回來。讀的人會跟著卡住，要等那隻 proc 被收掉、或有人把它那條連線斷開（下面「放開卡住的人」）才放開。**忙不算卡住**：手上一直在做事、但 `status` 讀得到的，是正常的。

- 【定】每隻 aos proc 至少留一條線（thread 或 coroutine）專門回答別人的讀寫，手上的事再久也不佔用它。
- 【定】daemon 定期檢查底下的 proc 有沒有卡住；別人也可以問某隻有沒有卡住。
- 【定】被 Linux 暫停的行程（SIGSTOP、Ctrl-Z）算卡住。
- 【定】查到卡住之後只記、不收；要收，人或上面的 proc 自己寫 `procs_ctl` 的 `kill`。
- 【定】卡住的那隻從 `procs/<名>` 走不進去，免得後來的人再踩進去。（硬要看的人自己走 `/proc/<PID>/cwd`，後果自己擔。）
- 【擬】怎麼檢查：daemon 另開一條線去讀那隻的 `status`，給一個期限；期限內沒回來就記成卡住。daemon 自己不直接讀，才不會被拖住。之後又讀得到了（例：被暫停的行程繼續跑），就改回來，`procs/<名>` 也恢復。
- 【擬】怎麼問：讀 daemon 的 `procs_status`，多一欄 `名字.stuck`（`no`，或卡住起算的時間）。問的是 daemon、不是那隻 proc，所以問的人不會卡。
- 【擬】daemon 自己卡住了，由它上面那台查；根卡住只有人看得到。
- 【開】多久查一次、期限多長。
- 這個檢查查不到的另一種：回答正常，但手上的事一直做不完（`aos_ctl_state` 一直是 `doing`、agent 一輪一直不結束）。這種只能從 `status` 看它做多久了，沒有人替它判。

- **放開卡住的人**（C++ 小庫實測，11-25）：系統給每個 FUSE 掛載一個開關（`/sys/fs/fuse/connections/<編號>/abort`，掛的人自己就能寫，不用 root）。往裡面寫 1，卡在那隻 proc 上的人當場被放開、拿到錯誤；那隻 proc 的目錄從此是死的（它得重掛或結束）。所以不收掉行程也救得了被它拖住的人。【擬】daemon 的 `kill` 先做這一步再收行程；要不要另給一個只斷開、不收的字【開】。
- 卡住的人殺不殺得掉看情況（同一次實測）：那隻 proc 還沒把請求拿走（例：被暫停），卡住的人殺得掉；已經拿走卻不回，才殺不掉。

### 連鎖卡住與死結（【定】：使用者 11-25「總之就是要守規矩，就是要自己承擔風險，就是這樣。」）

使用者 11-25 擔心：daemon 可以嵌套，一台設計不良的 daemon 會不會讓根底下大半棵樹都卡住。

- 卡住會傳染的路只有一條：A 在自己**回答的那條線**上去讀 B；B 不回，A 的回答也停了，A 變成卡住；再有人這樣讀 A，就一路傳上去。A 與 B 互相這樣等，就是作業系統課本上的死結（循環等待）。自己讀自己的目錄是最短的一種，小實驗已經撞到。
- 斷掉它的規矩：**回答只用自己記憶裡的東西；回答的線上不去讀寫任何別的 proc，也不碰自己的目錄。** 要問別人，放在做事的線上、帶期限；同一個對象上一次還沒回來，就不再問第二次。
- 照這條，daemon 的 `procs_status`、`procs/<名>` 都是從自己記著的表回答，不是有人來讀時才去問底下的 proc。
- ctl 的鎖不會造成死結：搶不到是當場失敗，不是排著等。
- 守規矩的上層不會被壞掉的下層拖住：下層卡住，上層只是把它記成卡住、從 `procs/` 拿掉。
- 代價：一台 daemon 卡住，它底下那一整棵從名字路都走不到了。底下的 proc 沒有卡住，照樣在跑，只是被隔開；等那台 daemon 恢復，或被 `kill` 之後它們變成沒人管的（「自行承擔風險」那條）。
- 根是最後一道：根自己要守這條規矩。共用的小庫把這條做進去（回答的線只叫「當場給字串」的函數，指令交給另一條線做）。

### 死掉的掛載

- 【定】proc 死了之後留下的掛載（第 11 節第 1 點）由 daemon 收：替底下的 proc 收屍時順手卸掉。
- 【擬】根自己死掉留下的，下次起來時清。

## 9. 送訊息

【定】**基礎 IPC 機制分兩類，aos post 建在其中一類之上**（使用者 11-25，原話第 16～18 段：先說「基礎通訊協定」，改口「應該說，基礎IPC機制」，再分層）：

| 類 | 有哪些 | 上面跑什麼 |
|---|---|---|
| 寫檔 | 普通檔案（硬碟、tmp）、FUSE 的檔 | **aos post**（寄信）是建在「寫檔」之上的 |
| 串流 | unix socket（它不只是寫檔，跟串流分在一起） | 一行一則加回條那一套（下面「socket」） |

- 機制＝東西怎麼過去；aos post、socket 上那套話是機制之上的約定。
- `ctl`、`status` 也都是「寫檔」這一類；`attrs` 的 `aos_kind`（`fuse`／`file`／`tmp`）說的就是這一類裡的哪一種。

【定】送的都是同一份東西：今天那封信原樣（json：寄件人、標題、內文、回信位址…）。所以從活著的走法退到寄信，不用改一個字。

【定】socket 上送來的，算進對話的話（queue）還是信（mailbox），proc 自己決定；預設希望是 queue。

【定】proc 掛了、睡了、卡住：socket 送不到。要送的人讀它的 daemon 的 `procs_status` 裡 `名字.mailbox` 那一行（或問某個 kernel），改走寄信。問的時候要不要順手叫醒，是 daemon 自己的可選設定，以後再說。

**socket**（【定】，使用者 11-25「socket這塊我覺得OK」）

- 一行一則；收的人回一行 `ok` 或 `error 代號 原因`。回條＝收到（到它手上，還沒處理），跟 `ctl` 同一級。
- 收的人先開口：連上之後它先講一行，送的人看到才送。（對方被暫停時，連得上、寫得進去都會成功，但沒人在收。）
- 改走寄信的時機：連不上、對方沒先開口、期限內沒回條；用同一個信名，收的人照信名擋重複。對方明講 `error` 就算失敗，不改寄信。
- 順序：只保證同一個寄件人送的先後。收的人醒來先清信箱，再收 socket 上的。
- 收到後還沒處理就死：介面不保證。我們自己的實作先寫進 persists 再回條。
- 放哪：proc 的目錄裡，叫 `sock`。（C++ 小庫實測：FUSE 擺出來的目錄裡放得了 unix socket，從 `/proc/<PID>/cwd/sock` 連得上。）
- 對面是誰：socket 上拿得到對方的 PID（系統填的，改不了），先只記、不擋。

**寫檔**（【定】，使用者 11-25：「不能都做嗎？可以先把maildir弄好，因為這個我們有經驗。啊至於要提供哪種都可以，各自選。」）

活著的 proc 用寫檔收信，有兩種做法，兩種都做，一隻 proc 提供哪種自己選：

- **信箱資料夾**（照 Maildir，先做這個）：proc 在自己的目錄裡擺出 `mailbox/`，別人照 aos post 原樣把信放進去（先在 `tmp/` 寫好，再搬進 `new/`）。寄的人做的事跟寄給掛掉的 proc 一樣，只是這次對面是活的：信一放進去它當場知道，也可以當場拒收（那次放信失敗）。
- **一個只寫的檔**（照 Plan 9 的 plumber）：寫進去就是送一則，沒人收就讓寫入失敗。檔名【擬】`msg`。

【擬】一隻 proc 提供哪幾樣，寫在 `attrs`：`aos_mailbox: yes`、`aos_msg: yes`、`aos_sock: yes`；都沒寫就是活著時不直接收，只能寄到它 persists 的信箱。

要知道的一點：預設 queue 的話，同一句話活著時是直接進對話，掛了改寄信則是進信箱等它自己看，兩邊意思不一樣。

## 10. 留下來的東西與搬家

【定】名字是 `persists`（使用者 11-25：「persist我感覺應該改名為persists」；原本叫 `persist`）。【擬】`settings` 的那一行與 `procs_status` 的那一欄跟著改成 `aos_persists`、`名字.persists`。程式（小庫、daemon）下一批才跟上。

- 【定】`.stack` 這個夾以後沒有；身體是活的，要留的各自處理，推薦放 `persists`。
- 【定】可遷移性現在不動，設計時先考慮著。遠期目標：`cp AOS_ROOT` 就能把一切搬走。
- 【擬】為了那個目標，現在先守兩條：
  - 每隻 proc 要留的東西，從它自己的目錄走得到（`persists`）。
  - 留下來的檔裡，指別人用名字路，不用絕對路徑、不用 PID。

## 11. FUSE 小實驗查到的（11-25，[報告](../experiments/fuse-proc-1125/README.md)）

一隻玩具 proc 加一台玩具 daemon，Python 標準庫、不靠 FUSE 的函式庫。eca-aos 重跑過第 2、3 題，結果一樣。

做得到的：

- 掛得起來。殼裡的 `ls`、`cat status`、`echo stop > ctl`、`cd` 都正常；從 `$AOS_ROOT/procs/<名>/status` 連穿兩層讀得到。
- 鎖做得出來：鎖著時別人 `echo pause > ctl` 當場失敗（`Device or resource busy`，退出碼 1），`aos_ctl_*` 沒被動到。要在「開檔」與「寫入」兩步都擋，只擋開檔會漏。
- 行程被強制收掉，`/proc/<PID>/cwd` 那條路馬上不見。
- 閒著不吃 CPU。Python 版一隻約 14 MB、讀一次 `status` 約 0.4～1.7 毫秒（普通檔約 0.015 毫秒）：給人與 agent 看夠用，當高頻的訊息管道不行。

會影響介面或做法的：

1. **死掉的掛載會留下來**。行程被強制收掉後，掛載點還在（進去是 `Transport endpoint is not connected`），要有人卸。這台 FUSE 自帶的「死了自動卸」實測沒作用。做法：daemon 替底下的 proc 收屍時順手卸；根自己死掉留下的，下次起來時清。
2. **daemon 死了，底下的 proc 還活著**（eca-aos 重跑時撞到）：掛載被卸掉之後它們照樣回答，從 `/proc/<PID>/cwd` 還走得進去，只是沒有任何 `procs/<名>` 指到它們了。【定】這個不管：daemon 掛了之後底下還活著的，自行承擔風險。
3. **proc 的程式卡住，讀它的人會一起卡住，而且殺不掉**（只能收掉那隻 proc）。所以 daemon 自己去讀底下 proc 的 `settings`、`status` 時要防這個；`procs_ctl` 的 `kill` 是解法。使用者 11-25：這塊要多想想；方向是 daemon 定期檢查底下的有沒有卡住，別人也可以問某隻有沒有卡住（見第 8 節「卡住」）。
4. **`status` 的內容在開檔那一刻定下來**，一次讀到的是同一份，不會讀到一半變。
5. **不認得的 ctl 字**：玩具的做法是那次寫入照樣成功（收到了），錯誤只記在 `aos_ctl_*`。【定】同時讓寫入失敗（第 6 節）。
6. **一次寫入幾道**：玩具一次只收一道，多行就拒。【定】只收一道（第 6 節）。
7. **沙箱**：這台的沙箱（bwrap）裡走不進 `/proc/<PID>/cwd`，但把掛載點的真實路徑開給它就讀得到。這就是「有需要再開口子」的口子。
8. **沒測的**：別的 Linux 帳號；收訊息的 unix socket 能不能放在 FUSE 的目錄裡（退路：放在外面，`settings` 寫位置）；改寫成 C++（估 600～800 行）。

### C++ 小庫（11-25，[aos-procfs](../cpp/aos-procfs/README.md)）之後補的

- 一隻 proc 約 4 MB；讀一次 `status` 約 0.04～0.05 毫秒、寫一次 `ctl` 約 0.03～0.04 毫秒（Python 玩具是 0.25～0.3 與 1.5～1.9 毫秒；普通檔約 0.003 毫秒）。
- 殼裡 `printf 'a\nb\n' > ctl` 會被殼拆成兩次寫入，所以是兩道各自算，不會被「多行就拒」擋下；真的一次寫兩行才會被拒。
- 小庫碰到草稿沒寫的地方，先挑了保守的做法（【擬】，等使用者看）：
  - 還沒收過指令時，`aos_ctl_state` 是 `-`。
  - 被拒的那一道也算進 `aos_ctl_count`、也寫進 `aos_ctl_cmd`（回饋講的是最後一次）；只有鎖著被擋的不算。
  - 被拒時那次寫入的錯誤是「參數不對」（`Invalid argument`）；鎖著是「忙」（`Device or resource busy`）。
  - 空的寫入（`echo > ctl`）什麼都不動、算成功。
  - 收下了、做的時候失敗：小庫現在記 `done` 加原因；【定】（使用者 11-25）改成另開一種 `failed`，小庫要跟著改。
  - `aos_started_at` 用本地時間帶時差（`2026-11-25T15:48:45+08:00`）。

### 最小的 daemon（11-25，[aos-daemon](../cpp/aos-daemon/README.md)）之後補的

- **「回答只用自己記憶裡的東西」做得出來**：daemon 的 `status`、`procs_status` 只抄自己記著的表；凡是要碰底下 proc 目錄的事（讀它的 `settings`／`status`、寫它的 `ctl`、連讀 `add` 給的那份檔），都交給另起的小行程去做、帶期限、到期就放棄。實測底下一隻被暫停時，讀 daemon 的 `status`、`procs_status`、下 `procs_ctl` 都是幾毫秒；`procs_ctl` 最久鎖 1 秒（對卡住的那隻下 `stop`，放棄後回錯，接著 `kill` 下得進去）。
- **`kill` 不碰那隻的目錄**：先斷開它的 FUSE 連線（被它拖住的人當場被放開）、再收行程、死掉的掛載用不跟它講話的方式卸。
- **兩層嵌套通**：`$AOS_ROOT/procs/d1/procs/kid/status` 讀得到，`aos_name` 是 `d1/kid`；上面的 daemon `stop`，兩層的行程與掛載都收乾淨。
- 它碰到【開】的地方都挑了保守的（【擬】，等使用者看；整張表在它的 README）。最該先看的四條：
  1. `procs_status` 的 `phase` 用五個值：`starting`（起了、還沒登記）、`running`、`stopping`、`stopped`、`failed`（起動失敗）。**【定】**（使用者 11-25「1.可以。」）
  2. 掛載點放 `<mount-base>/<名字路把 / 換成 %>`，例 `d1%kid`。**【定】**（使用者 11-25「2.可以...不過%不會有問題吧。」——功能上沒問題；`%` 在 crontab、systemd 的 unit 檔、printf 的格式字串裡有特別意思，把這個路徑寫進那三種地方時要小心。平常走 `$AOS_ROOT/procs/…`，不會打到這個路徑。）
  3. 外來登記（`register`）的只收 `rm`；`stop`、`start`、`kill` 都拒；誰都能登記任何 PID、不驗身分。
  4. `add` 只收絕對路徑；檔讀不到時那次寫入照樣成功、錯誤記在回饋裡（回答的線不去讀那個檔）。
- 沒做：自動重起、`sleep`／`wake`、預設的 persists、底下的 stderr 收進 `reason`。`kill` 一台嵌套的 daemon，它底下的就沒人管（照「自行承擔風險」）。

## 12. 還沒定的（照我覺得該先談的排）

1. 卡住那一塊剩的細節（多久查一次、期限多長）。
2. 【定】基礎先用 C++ 做（第一塊：`proto9/cpp/aos-procfs/` 小庫，11-25 派出）。還沒定：掛載點放哪、daemon 與 agent 的身體放哪幾個夾。
3. `procs_ctl` 要不要留 proto8 的 `sleep`／`wake`。
4. `persists` 在目錄裡怎麼擺（真的夾、連結、還是 proc 當場回答）；proc 死了以後別人怎麼走到它的 persists（現在只有 `procs_status` 那一行路徑）。
6. 報 token 用量的檔。
7. 只登記、不起的入口（`register`）：誰可以登記誰、登記後 daemon 對它有多少權力。
