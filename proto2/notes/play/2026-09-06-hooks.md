# 掛勾輪記錄

## 撞到的

- 原本的測試把所有符合名字的 aos 進程都當殘留。這會誤傷正在工作的管家。
- `ctx.state` 原本是函式。新包需要直接改同一份 dict，所以改成屬性。
- 測試 helper 的 stderr 重導向順序寫反時，日誌會混進回覆檔路徑。
- `spawn` 原本只掃 `kids/`。鐘與關係掃不出來，所以補 `kids.json`。

## 我自己決定的

- `contacts.json` 正式寫成 `{名字: 世界絕對路徑}`。讀取時兼容值是 `{"dir": ...}` 的早期草稿。
- `kids.json` 是 `{名字: {name, dir, clock}}`。先只放目前真的知道的三個欄位。
- 非主線結果每格先順手收。主線的 `state`、`request`、`busy` 不因此改變。
- `on_result` 出錯時記 log，並退回「寄到自己的 `inbox/<kind>/`」。結果不丟掉。
- 模板存在時保留模板的 `prompts.json` 與額外 shell 工具。persona、父的 packs、共用 LLM 路徑再覆蓋。
- 掛勾出錯只記 log。單一工具包不能弄死整格。

## 後面各包要注意的

- 一包只動自己的四個檔。不要改 `aos-agent`、`aos_agent.py`、`test.sh` 或 README。
- 旁線請求一定用 `ctx.llm_request`。不要自己寫 pending，也不要靠檔名前綴猜 kind。
- 自訂狀態放 `ctx.state` 的自己欄位。不要改 `state`、`request`、`step`、`busy`。
- `on_idle` 每格都可能被叫。只做短的讀檔、判斷、投遞。
- `on_act` 會看見所有工具。成本包要自己決定哪些要略過。
- 寄信的 `source` 會成為資料夾名。用短名字，不放斜線。
- 寫 JSON 用 `ctx.write_json`。不要留下半個檔。

## 介面簡不簡潔（我自己的評分與哪裡可以更簡）

8/10。包只要認一個 `ctx`。非阻塞 LLM、信件、鐘各一個入口。

最不簡的是 `put_mail(target, source, content)` 的 `target` 同時吃名字和路徑。之後若常讓模型搞混，可拆成 `mail_to` 與 `mail_to_path`。這輪先照任務指定。

## 內部機理簡不簡單

8/10。仍是 JSON 檔、資料夾與幾個可選函式。沒有新類型系統或新協定。

較繞的是旁線結果：pending 要記 pack 名，再載回同一包。這是讓十幾包互不碰核心檔的必要接點。

## 效能與邊緣狀況（留給使用者看）

- 每格會掃 pending，數量很大時會一直查結果檔。現在先不做索引。
- 每次 `on_system_prompt` 都讀 prompt override。包多時會多幾次小檔讀取。
- `ctx.contacts()`、`ctx.kids()` 都是整份 JSON 讀寫。人多時會慢，也沒有鎖。
- 同一微秒寄兩封信仍可能撞檔名。
- 世界搬家後，contacts、parent、kids 裡的絕對路徑不會自動修。
- 晚到的主線超時結果會留在 LLM results。現在不清。
- 一個掛勾修改另一包的 state 欄位沒有隔離。各包要守名字前綴。
