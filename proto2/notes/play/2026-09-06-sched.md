# sched 試玩紀錄

## 做的時候的坑

- 排程規格把 requester 放在 priority 裡。計費規格要它在請求頂層。實作兩邊都讀，帳本只用最後採用的穩定名字。
- cost_class 不能信投遞者。實作先讀 engines.json，再讀 LLM 世界自己的 defaults.json。
- 既有 agent 沒傳 requester。先用請求檔名前綴備援，不改共用 agent 檔。
- `proto2/test.sh` 的舊用量測試直接索引平鋪鍵，跟已拍板的兩層新格式衝突。這輪不能改 test.sh；sched 自己另驗新格式與舊檔讀取。

## 玩的紀錄

- 第一次 `ls`：過期的 01 分數只有 -50，仍排第一。02 chat 是 630。久等的 03 background 靠等待上限排到 550。
- 第一次看到的順序：`01-late → 02-chat → 03-aged → 04-tool → 05-think`。
- deepseek-flash 實際開工順序完全相同。五筆結果都是 ok。
- `usage --by requester` 印出五個 requester，各一筆，沒有混帳。

## 玩的時候的坑

- deepseek-flash 有兩筆很慢。最慢約 63 秒。不是排程卡住，是 worker 還在跑。
- 要求只回一句，模型仍花了很多 reasoning token。短 prompt 不代表便宜。
- 等待中的 04、05 過了一分鐘後，實際開工分數比第一次 ls 多了等待分。每格重算確實看得到。

## 缺什麼接點

- `Ctx.llm_request` 沒有 requester、排程 kind、deadline 參數。現在只能靠檔名前綴和自己在 body／priority 裡補。

## 介面簡不簡潔（我自己的評分與哪裡可以更簡）

- 8/10。舊數字不必改。新物件的六個名字看得懂。
- `requester` 同時可能出現在頂層與 priority，這是目前最不簡潔的地方。

## 內部機理簡不簡單

- 8/10。只用 JSON、mtime、state.json 的最近十筆。沒有另開資料庫或排程服務。

## 效能與邊緣狀況（留給使用者看）

- 每開一筆都重算整條隊伍。請求很多時會變慢。
- deadline 沒時區或格式錯時，現在當成沒有期限。
- age_boost 用完整等待分鐘算。不到一分鐘不加分。
- requester 可冒名。這輪照規格故意不防。
