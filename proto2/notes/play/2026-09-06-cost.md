# cost 工具包實玩

## 做的時候的坑

- 主線 LLM 結果沒有 `on_result`。只能在下一個 `on_act`、`on_reply` 或 `on_idle` 看 `last_usage` 補帳。
- hook 看不到 wait 當格的 step。`round_steps` 只能用下一格倒推。
- `last_usage` 只有 token，沒有引擎名。要去 `llm-result.json` 找引擎，再讀 `engines.json` 的 price。
- `on_act` 只拿到解析後的 args。`args_chars` 是重新轉成 JSON 的字數，不是模型原字串的精確字數。

## 玩的紀錄

- 我：「請用 sh 工具依序做三件事：先執行 printf abc，再執行 printf 1234567890，最後執行 wc -c notes.txt。做完後用 cost_summary 查帳，回答我哪個工具最貴。」
- cost-agent：「今天總共只有 3 次工具呼叫，全都來自 sh。所以最貴的工具就是 sh。總價欄位顯示 null，表示還沒計到價錢。」
- 它三次都成功，帳本有三行。每行都有字數、token、`round_steps`、成功記號。
- 共用 deepseek-flash 沒寫 price。它也看懂 `total_cost: null` 是還不能算錢，不是零元。
- 回答後，`cost_summary` 自己也成為第四筆帳。最後 `pending_ledger` 已清空。

## 玩的時候的坑

- 三個很短的 shell 指令都量成 0 ms。毫秒整數看不出更短的差異。
- `cost_summary` 查到的是查詢前已補好的三筆；它自己的成本要等回答回來才補，這是合理的時間順序。

## 缺什麼接點

- 缺主線結果專用 hook。最好直接給 result、usage 和收回覆時的 step。
- `on_act` 最好再給原始參數字串與工具的明確成功／錯誤種類。現在自訂 shell 工具只回文字，包看不出退出碼。

## 介面簡不簡潔（我自己的評分與哪裡可以更簡）

- 8/10。只有兩個工具。`cost_summary` 只多一個日期，`cost_recent` 只多一個筆數。
- 如果帳本能由共用層寫，cost 包可以只剩兩個查詢工具。

## 內部機理簡不簡單

- 7/10。一包一檔，只用 os、json、hashlib 和 datetime。
- 為了補 jsonl 的後半段，要重寫當天檔案。為了避免累加算錯，每次會重算 summary。

## 效能與邊緣狀況（留給使用者看）

- 帳多了以後，每次補帳都掃全部日期，會慢。
- 沒做兩個進程同時寫同一本帳。
- 跨午夜、多個工具回傳都是空字串、壞掉的 jsonl，只做最直白的處理。
- token 分攤可能是小數。這是歸因值，不是供應商原始帳。
