# fs 包實作與試玩

## 做的時候的坑

- fs 草稿寫 `sh` 兩邊各截 4000 字；code-editing 的拍板格式寫最後 1500 字。我照後者做。
- `sh` 只停外層 shell 時，底下的程式可能繼續跑。最後用一個行程群組一起停。
- `write` 的 `mode` 沒指定字串。我用了 `overwrite` 和 `append`。
- `seconds` 沒指定精度。我回小數點後三位。
- 頂層規矩要求新增程式要補 code map，但本輪硬規則只准動四個指定檔。我沒有改 code map。

## 玩的紀錄

使用者：寫一個 hello.py 印 1 到 5 的平方，跑它，把輸出告訴我

agent：叫 `write` 寫入 `range(1, 6)`，再叫 `sh` 跑 `python3 hello.py`。

工具輸出：`1 4 9 16 25`。agent 照實回報。

使用者：把 5 改成 7 再跑

agent：叫 `edit` 把 `range(1, 6)` 換成 `range(1, 8)`，再叫 `sh`。工具輸出是 `1 4 9 16 25 36 49`，agent 照實回報。

## 玩的時候的坑

- deepseek-flash 會正確叫 `write`、`edit`、`sh`，參數也一次就對。
- 它沒有先叫 `ls`。第一次是新建檔，第二次又記得自己剛寫的完整內容，所以也沒有再 `read`。
- 兩輪都沒有卡住，也看得懂工具錯誤以外的正常回傳。

## 介面簡不簡潔（我自己的評分與哪裡可以更簡）

9/10。五個名字都很直白，必要參數少。
`sh` 多了兩個 `*_truncated` 布林值，但不加的話模型不知道尾巴前面還有內容。
`ls` 用文字一行一個，比一大包巢狀 JSON 短。

## 內部機理簡不簡單

8/10。全部在一個 Python 檔，只用 `os`、`subprocess`、`datetime`。
最複雜的是 `sh` 的逾時處理。它需要停整個行程群組，不能只停 shell。

## 效能與邊緣狀況（留給使用者看）

- `read` 為了回總行數，會把整個檔案讀進記憶體。超大檔以後會慢、會吃記憶體。
- `ls` 會先收完整份名字再排序。超大資料夾以後會慢。
- `write` 和 `edit` 沒有鎖，也不是原子換檔。兩個 agent 同時改會互相蓋掉。
- 文字固定當 UTF-8。二進位檔、奇怪編碼不做。
- 路徑沒有沙箱。`../`、絕對路徑、symlink 都可能走出世界。
- `sh` 沒有 tty，不適合互動程式。長工作交給 `run_long`。

## 缺什麼接點

- 缺「同名工具指定誰優先」的接點。共用載入器現在永遠讓 `tools.json` 先列的包贏。fs 和 shell 同時列時，只有把 fs 放前面，`sh` 才會由 fs 接手。單靠 fs 包無法保證反過來列也由 fs 贏。

## 還沒做的

- 沒做 `run_long`。它是別包的工具，本輪只在逾時時提示使用者改用它。
- 沒做上面列的效能和邊緣狀況。
