## 硬閘門判定

**只算「禁止下一筆 LLM」時部分通過；照文件的「整隊停」與 ticks 硬上限則不通過。**

1. `budget_block()` 只在 state 正要由 `llm` 送請求時檢查。owner 撞個人 token 額度後留下 `own:tokens`，證明這道門能阻止它的下一筆 LLM。
2. 個人額度的在途請求不能追回，所以 6,000 仍超到 10,038；這是有限但很大的 67.3% 超支。
3. 整隊跨過 300 ticks 時全員剛好 idle，沒有任何人走到 `llm` 檢查點；owner／chief 鐘沒有停，shared 成員也繼續逐格跑。帳面從 373 漲到 458 才人工 stop。
4. 因此 tick「硬上限」可無限被 idle tick 穿透；這不是只多一筆已在途 LLM 的有界超支。
5. sales 的個人 allocation 是 0，但程式只在 `limit > 0` 時判個人超額，所以它仍用了 7,011 tokens。零代表「尚未分配」卻被當成「不設限」，行為不對。
6. 若撞線後有人再進 `llm`，程式會設 `team:ticks` 並拒絕送出；本輪實際沒有這一步，也沒有自動停鐘或向甲方送追加詢問。

## 撞到的坑

1. **team ticks 把 idle step 也算進去，硬閘門卻只守 LLM 發送點。** 沒有新信時仍會超支，且鐘不停就一直增長。
2. **0 額度不是 0 上限。** sales 沒拿到 grant 仍可叫模型；這與「個人額度用完就不再叫 LLM」不一致。
3. **已在途請求讓個人 token 額度大幅超支。** max_concurrent=2 時 owner 連續兩筆，共超 4,038。
4. **模型協定失敗不算 LLM error。** PM 得到非空、HTTP 成功的殘缺工具標記，agent 當普通回覆送走，沒有重試或格式錯誤提示。
5. **sales 仍用舊帳與虛報證據。** 它沒叫 `team_budget`／`team_status`，把一封請求規格的信說成已交規格。

## 結論

公司 ollama 連線與收尾都正常，但本輪沒有驗到「100% 時全隊自動停」；反而重現一個更直接的 tick 閘門缺口。token 請求在個人門後停止增長，ticks 卻從上限 300 跑到 458。問題涉及每格檢查、shared／own 鐘與 daemon 收鐘，不是一行明顯修正，所以本輪只記錄、沒有改程式。
