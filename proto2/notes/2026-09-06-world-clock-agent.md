# 2026-09-06 抒發：檔案系統化作遊戲世界、daemon 時鐘、agent 信箱

這是使用者整理思緒的抒發原文，不是規格；可能跟 proto2 現有實作或文件衝突，衝突時以使用者之後的裁決為準。

## 打底：檔案系統化作遊戲世界

先不管git。LLM/agent相關先不管。我這邊要先做打底，也就是把檔案系統化作遊戲世界，這樣子的基礎架構。在這個基礎架構中，有所謂的daemon，他掌管所有的tick時鐘，他的運作方式就是一個持續跑著的process，每隔一小段時間就去看資料夾內有沒有相關請求或指令，比如請求開啟某個tick進程，對某個世界進行連續tick，或是請求關閉某個tick，並且還可以設定這個tick進程的user身份權限等。對，我知道這個其實linux也有做，只是說我們最好還是重造一個輪子...或是你有其他可以盡可能利用linux那套輪子的方法的話也可以給建議。

## daemon 掌管所有 tick 時鐘

好了，基礎架構打好後，我們就有了世界/時鐘的設定，再來才是agent，一個agent就是一個資料夾，被tick了才會進行下一步，就類似遊戲中的物件被_process()一樣，基本上agent的每一歩都是建議盡可能短小，否則可能會影響fps，也就是每次tick的時間。

## agent 被 tick 才動、長操作另開世界

但若是某些操作要跑很久，那通常會將該操作弄成新的世界，請求daemon另開一個時鐘去處理...這塊我覺得還可以有更好的方法，比如fork一個process，但那樣就會逃離daemon的管束。

## tick 內卡住怎麼辦

然後如果在tick內某些原本預期中很快就好的操作卡很久，通常情況下就是乖乖阻塞停在他那邊，但也可以設置說，是否在卡超過一段時間，就fork一個子進程繼續去tick其他同一回合的事情，這個卡住的process就變成一個獨立的時鐘這樣...再想想吧，作業系統相關理論應該早就有解決方案了。剛剛說的這些主要是針對一些shell操作超時的狀況，至於LLM，通常agent會將相關請求丟到某個資料夾，讓那個資料夾的時鐘處理。

## agent 之間的交流：信箱 IPC

再來是agent之間的交流，原本在agent之下的基礎架構層，大家都是靠權限，想存取哪些都可以，但在agent這塊，我們規定了一個資料夾應該長怎麼樣，才算是標準agent，其中包括所謂的信箱，也就是與其他agent，或其他機制之間的通訊方式。也就是IPC。和普通作業系統的IPC不同，因為粗粒度的時間和空間管理，所以我們可以放心的弄一些很理想化的，很吃資源的方式，我們目前就先只使用一種：寫檔案，每次tick看資料夾有沒有檔案，有的話就讀檔。在v0.1 agent規格標準中，每個agent都有一個信箱，信箱內有子信箱，所以可以對團隊, 他人, 機制各類來源去做來源分類，然後會提供工具，包括列出當前的來源列表（可以用是否有未讀信件來篩選），取得某來源的所有信件，讀取某信件...等。

## LLM 等私有機制走另一條通道

對了，對於LLM這個特殊機制，還有一些後續會添加的底層機制，通常是走另一個資料夾通道，並且不提供工具，整體來說是很私有且嵌入的，好比qwen這種`</think>`機制，就會在這邊被處理（看看狀況）。

## agent 的常規 tool 與預設 prompt

然後是agent的一些常規tool，包括使用shell指令，查看自身狀況的指令（context/運行時長/資料夾大小...)，產生與管理子agent的指令（父子的聯繫與時鐘脫節與否無關，這是管理權/從屬的問題），這些工具套件通常還會搭配一些預設prompt，這會是後續最有趣的部份，也就是規劃一個bot。

## 續：介面與底層要分開、daemon 的用法

以下是同一天稍後的補充原文，

我們現在做的這些工具都是cli型式，這主要是方便使用者使用。後續會把使用界面（也就是目前現有的cli功能規劃），還有底層運行機制分開，但目前的粗糙原型可以暫時先這樣就好。然後我重新審視整個底層架構，也就是daemon-世界-時鐘這個...

我之後預期的使用方式，是我會有一個環境變數：AOS_DAEMON_DIR，指向~/.aosd，然後我會把他註冊進systemd（這個以後再說，目前還是需要使用者手動輸入指令aos-daemon-kernel start/restart/stop ~/，其中~/可以省略，默認~/），然後他就會啟用一個持續性進程，內部實作怎樣都可以，怎麼方便怎麼來。指令aos-daemon是一個可以在PATH內被吃到的東西。然後我可以用aos-daemon register/unregister --config config.json xxx，來對xxx這個資料夾啟用時鐘，不指定config，那就是用默認方式啟用（繼承該指令的呼叫者的身份權限，使用默認設定）。也有aos-daemon-kernel ls，可以用來看現在有哪些時鐘在跑。想要暫時停止某個時鐘，也可以用aos-daemon pause/continue xxx，對，一個資料夾路徑只能有一個時鐘，所以這個路徑就是這個時鐘的id。內部實作這塊看是要丟檔案還是啥都可以，怎麼方便怎麼來。

那個aos-daemon-kernel start/restart/stop xxx，xxx如果不給，那就是AOS_DAEMON_DIR，如果沒有AOS_DAEMON_DIR就報錯。換成這樣吧。

現有的，已經register的時鐘，他的訊息也可以用檔案的方式儲存

還需要考慮aos-daemon在重啟後，能否接續先前的進度。然後我也在擔心，以後如果有成千上百個時鐘，那麼會不會很難管理，但這個是以後的事了，內部核心就是這樣就好，頂多相關.json檔案可以做合併減少體積，管理這塊就是後續另外做介面，核心機制就先這樣
