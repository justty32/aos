# aos-llm 的排隊優先度

一句話：現在每個人自己喊一個數字，喊得高的永遠贏，沒人管公平、期限和錢。

## 建議

先做方案 A。它先把排隊需要的資料放進請求。
方案 B 的主管可以替小孩填這些資料，方案 C 也能沿用同一個 `requester` 算限額。
先做主管，反而會先做出一套只有主管懂的排法。

## 方案 A：把 priority 變成物件

建議長這樣：

```json
{
  "priority": {
    "level": 5,
    "deadline": null,
    "kind": "chat",
    "requester": "group-a/kid-1",
    "cost_class": "normal",
    "age_boost": 1
  }
}
```

- `level`：事情有多急，通常用 0 到 9。預設 0。投遞者先填，主管可以改。
- `deadline`：最晚何時該開始。預設 `null`。真的有期限的人填，要帶時區。
- `kind`：分成 `chat`、`tool`、`think`、`background`。預設 `chat`。投遞工具照用途填。
- `requester`：誰丟的。預設 `unknown`。`write_request` 自動填穩定名字。
- `cost_class`：引擎是 `cheap`、`normal` 或 `expensive`。預設 `normal`。LLM 世界照引擎價格填，不能信投遞者自報。
- `age_boost`：每等一分鐘加幾分。預設 1。由 `defaults.json` 填，主管只能調低，不能自己灌高。

`requester` 建議用 `集團/agent`。
沒有斜線，就把整串當成一個集團。
帳本仍保留完整字串，排外部公平時只看斜線前面。

每格用同一套排法：

1. 已過 `deadline` 的先放前面。這只保證它贏過未過期的，不保證同一個人包場。
2. 其餘算分：`level × 100 + kind 分 + 等待分 - 費用分 - 近期占用分`。
3. `kind` 分是：`chat +40`、`tool +20`、`think 0`、`background -40`。
4. 等待分是 `等待分鐘 × age_boost`，最多加 300。
5. 費用分是：`cheap 0`、`normal 10`、`expensive 30`。
6. 近期占用分是：同一集團在最近 10 次開工中每占一次扣 25。
7. 最後照分數高、mtime 早、檔名小的順序走。

`aos-llm exec` 每格先收完 worker，再重算全部排隊請求。
每開一筆，就更新最近 10 次開工，再替剩下的重算一次。
某台 engine 滿了，就跳過那筆，看下一筆。
這樣一台滿載的引擎不會擋住別台。

舊的 `"priority": 5` 照舊可用。
讀進來時就當成 `{"level": 5}`。
舊的任何整數都照數值使用；新投遞工具只產生 0 到 9。

`aos-llm ls` 要印最後分數，也要印短理由。
例如：`score=465 level=5 chat +40 wait=10 normal=-10 recent=-75`。
過期的要另外標 `deadline=late`。
人要看得出為什麼被插隊，也要看得出是誰最近用太多。

## 方案 B：主管先替集團排

一個集團就是主管加一群小孩。
小孩不直接把請求丟進 LLM 世界。
它們先丟到主管家的 `llm-queue/`。
主管每格挑出該送的請求，補好 priority 物件，再轉投 LLM 世界。

主管每格做這些事：

1. 掃一次 `llm-queue/`，依小孩分組。每個小孩先只拿隊首一筆出來比。
2. 看任務的重要性。這個值來自主管派工作時留下的標記，不信小孩自己喊。
3. 看誰等最久。久等的小孩會慢慢往前，不會一直餓著。
4. 看集團今天還剩多少 token 和錢。快見底時先壓低深思與背景工作。
5. 看目標 engine 還有幾個空位。每格最多轉投能開工的數量，其餘留在主管家。
6. 填入集團名、小孩名、有效 `level`、`kind`、`deadline` 和降級理由。
7. 轉投後換下一個小孩先比。不能連續把同一個小孩整串送出去。

主管預設不叫模型來排。
固定規則比較快，也不會為了排隊再塞一筆進隊伍。
只有待排超過 20 筆，才准請模型看一次短摘要。
最多每 20 格叫一次，而且只能用有空位的便宜 engine。
模型只建議「任務重要性」。期限、預算和公平扣分仍由固定規則決定。
若便宜 engine 也忙，就完全不用模型。

小孩送出時立刻拿到一個請求編號。
主管在 `llm-queue/status/` 寫狀態。
狀態要有原本等級、有效等級、目前位置和一句理由。
小孩被降級時會看到 `budget_low`、`fair_turn` 或 `background`，不能只默默等。
這份筆記只規定排隊狀態。
主管、小孩、名冊和生死由集團那份設計決定。

很多小孩搶同一台本機模型時，方案 B 才值得做。
只有一兩個 agent 時，不值得多繞主管。
代價是至少多一格延遲，主管停住時整個集團都不能投遞。
主管也可能變成新的塞車點，所以每格只做讀檔、算分和搬檔。

兩個主管搶同一個 LLM 世界時，最後仍由方案 A 決定。
LLM 世界按 `requester` 的集團部分算近期占用。
兩邊同分時，較早到的先。
主管不能靠把全組都標成 9 來一直贏。

方案 B 不另造一套格式。主管只是「幫忙填 priority 物件的人」。
集團設計只要交給這裡四樣東西：穩定集團名、穩定小孩名、任務重要性、`llm-queue/` 位置。

## 方案 C：LLM 世界自己管限額

在 LLM 世界放一個 `quota.json`。
它按 requester 或集團寫每小時、每天最多多少 token 和錢。
`aos-llm exec` 派工前，先用帳本已花的量和這筆的 `max_tokens` 估一次。

建議分兩道線。
用到八成時，把 `think` 和 `background` 降到背景等級。
用滿時直接回錯誤，不再開 worker。
`chat` 和 `tool` 不偷偷降級；超過硬上限就清楚回錯。
本機價格是零，也仍可設 token 上限，避免一個人把機器占滿。

worker 的用量紙條要帶完整 `requester`。
每天帳本同時按模型和 requester 累加。
限額只讀這本帳，不另算第二套數字。

## 跟現在的程式接法

- `aos-llm exec`：把現在的整數排序換成上面的算分與近期 10 次開工紀錄。
- `defaults.json`：`priority` 改放預設物件；舊數字仍讀得懂。
- `aos_llm.write_request`：`priority` 接受整數或物件，再加 `requester`、`kind`、`deadline` 方便參數。
- `aos-llm worker`：結果保存原 priority、有效分數、理由和 requester。
- `aos-llm ls`：顯示分數、理由、期限和 requester。
- `README.md`：把整數排序改寫成物件排法，保留舊數字例子。

## 現在故意不做

- 不重排已經開跑的請求。
- 不取消已經送出的 HTTP。
- 不處理兩台機器時間不同或時間突然倒退。
- 不防 requester 冒用別人的名字。
- 不精準猜一筆最後會吃多少 token。
- 不退還估多的限額，也不預支明天的限額。
- 不處理主管搬檔到一半死掉後的自動修復。
- 不讓模型直接改期限、預算或公平分。
- 不自動調整各種加減分。

## 要使用者拍板

- T-61：`priority` 改成物件，舊數字一律當成 `{"level": n}`？建議是。
- T-62：採用「過期先行，再照固定分數，每次開工後重算」？建議是。
- T-63：集團內的小孩一律先進主管的 `llm-queue/`，不直接投 LLM 世界？建議很多小孩共用本機模型時才強制。
- T-64：主管平常只用規則，超過 20 筆才偶爾借便宜模型排一次？建議是。
- T-65：限額八成先壓低深思與背景，用滿就直接回錯？建議是。
