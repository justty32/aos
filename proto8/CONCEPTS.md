| loop（aos loop） | 讓 inst 持續執行（每隔幾秒一次）；實作上是一個 library，整個進 daemon | 3f.2、3g.3 |

| binding（繫結） | library／程式語言做的事：把 agent 那條很長的 list 裡固定的元素綁死，用時只填幾個引數 | 3g.9 |
| 工具 | agent 函式的引數之一；對 agent 來說就是被引用的標頭檔，內部怎麼跑不用懂；agent 也可以是工具；aos 體系的每個指令都是工具 | 3g.12、3g.13 |

## 2. 規則（使用者說「一定是這樣」的）

- **C-01** aos 存在的理由是讓大語言模型方便使用；目標多到只能靠模型寫，所以核心要讓模型好用。（2.1）
- **C-02** aos 蓋在現有作業系統上，硬體層的計算分配不重做。（2.5）
- **C-03** 由下往上：Linux → daemon → 時空 → 排程與資源分配 → agent。上層只透過下層。（2.5、2.10）
- **C-04** daemon 完全處理 Linux 那邊的事；它之上的東西不碰 Linux。（2.5）
- **C-05** 空間就是資料夾，時間就是 tick；這一塊已定，不再討論。（2.5、2.12）
- **C-06** tick 之間，所有與外部有關的狀態一致。（9/24）
- **C-07** 體系用的表達方式以模型天生就會的為準（檔案系統、POSIX、JSON），為的是讓它能自省。（2.6、9/23）
- **C-08** 計算任務＝一個 POSIX 行程，不是 thread；不必再往下分種類。（2.7）
- **C-09** 任務處理過程中用到的東西，只要有限，就是資源。（2.7）
- **C-10** 資源的有限用格數表示。（3b）
- **C-11** 排序演算法＝決定哪個任務先給哪個資源；就這樣，不多說。（2.7）
- **C-12** 排序與資源分配本身是計算任務；資源本身也當行程看——一切都是計算任務，核心沒有第二種東西。（2.8）
- **C-13** 每個計算任務都有固定的基礎特性（九軸）；其中確定性是任務自己的屬性。（2.9）
- **C-14** 基礎特性之外，人可以任意附加特性。（2.9）
- **C-15** 排序程式可以由人寫，也可以由「生成排序程式的程式」叫模型寫。（2.10）
- **C-16** tick-tock 的本質是定義時間、讓時間能停；停下來後 agent 看到的就是那個時間點的空間，可直接打包。（2.11）
- **C-17** 停下來時正在跑的任務可以不被迫停止；那個時間點的空間裡可以含「這件事正在跑」。（2.11）
- **C-18** agent 是狀態機、是函式、也是計算任務；直接接進核心，不特別處理。（2.13、2.14）
- **C-19** agent 的簽名＝腦（模型）＋記憶（核心人格、近期記憶）＋手腳（工具）。（2.17）
- **C-20** agent 是複合型任務（外迴圈便宜、叫的模型與工具貴），所以要被排程；最核心的一題是「很多 agent 時誰先用腦」。（2.18、2.19）
- **C-21** 可預測性有主體性，不是任務的屬性，是觀察者的認識。（2.14、2.15）
- **C-22** 提高 agent 可預測性的方法：當 S 表示式拆開，能寫死的節點換成程式，降低走進不可預測節點的機率。（2.16）
- **C-22b** 可預測性不只是函式本身的：同一函式在不同狀況、不同（例如老舊）硬體上跑，可預測性不一樣。節點＝函式內部＋它所在的執行環境，合起來才是執行節點。（3g.13c）
- **C-23** agent 內部怎麼設計是後面的事，先把底打好。（2.20）
- **C-24** 要最佳化的不是時間空間，是金錢、可預測性、人能不能理解。（9/1 ideas 01；2.1 重申）
- **C-25** 大操作（問模型、跑久的工具）丟到另一個資料夾讓另一個行程處理；agent 自己每次 eval 短促。（9/19）
- **C-26** 沒輸入就每 tick 沒事。（9/23）
- **C-27** tock 的時機（任務都結束就提前 vs 固定間隔）應該是可選的。（10-04 user-advice）
- **C-28** 沒法直接轉成 POSIX 呼叫的事（人手畫），用**間接抽象化**變成計算任務：拆成多個 POSIX 任務（寄信給畫家、收信、畫歸檔），人在這幾個任務之間、在系統外面做事。（3c）
- **C-29** 處理單元分兩種：普通 CPU（跑寄信、收信這類一般任務）；外部 PU（畫師、GPU、NPU）——跟外部設備的概念靠攏。（3d）
- **C-30** 空間的定義可以擴到外部設備：資料庫、硬碟、快取、記憶體、雲端都能納入空間，像 Plan 9。（3d）
- **C-31** 行程本身也是掛在空間裡的一個東西。資源、設備、PU、行程，全是空間裡掛著的節點。（3e）
- **C-32** 空間就是存放狀態的地方。（3h）
- **C-33** 處理單元／處理（process）＝過一段時間後造成的變化，變化指的是空間上的變化。（3h）
- **C-34** 求值＝放開讓它算、過一段時間看狀態變化的結果；求值的定義就是空間狀態的變化。對資料夾求值＝執行這個資料夾；求值還回來的是一個正在變動的資料夾，不是一個值。（3h、3f.1、3f.3）
- **C-35** Linux 檔案系統就是一個 LISP；資料夾＝list，list 裡有 list。（3f.1、9/19）

以下來自 10-11 晚的實作口述（§3g），使用者講得像定了的，所以也列進規則；要改隨時改：

- **C-36** 層層遞進：inst（求值一次）→ loop（持續求值）→ node（loop 服務的資料夾）→ daemon（統管 loop）；daemon 跑的 inst 可以是另一個 daemon。（3f.2）
- **C-37** 時空固定：空間照 Plan 9；時間是 tick-tock，一個可看可不看的時鐘；要先有時間後面才不會亂。tick-tock 可以跟 node 的狀態變化完全脫鉤，node 要看就訂閱。（3f.5、3g.5）
- **C-38** 第三層（kernel）的參照物就是時間（tick-tock）與空間（資料夾）：「三回合內搞定」「只動這三個資料夾」「每檔不超過幾 KB」。它只是最基礎的排程；PU 怎麼收任務請求各資料夾各做各的。（3g.6）
- **C-39** agent 是一個資料夾、一個 node、一條很長的 list（模型、context、工具、記憶……各占一個元素），持續被求值。最普通的 agent＝狀態機＋需要思考就丟 LLM。（3g.8、3g.9）
- **C-40** agent 要能當拋棄式函式用：引用一個設好的資料夾（標頭檔）、填幾個引數、讓它跑起來，執行環境在引用者這邊。library 做 binding 讓這件事簡單。（3g.9、3g.10）
- **C-41** 巢狀：list 的元素也是 list，求值時先對元素求值（畫家裡的畫筆 agent 先算）。（3g.11）
- **C-42** 工具＝被引用的標頭檔；agent 也可以是工具；aos 體系的每一樣（daemon、tick、task、inst、kernel）都基於 inst、都是 shell 指令，所以都是 agent 的工具——自我迴圈改進的閉環。（3g.12、3g.13）
- **C-42b** inst 的 JSON 裡可以多放東西：九軸特性、traits、資源標籤、優先順序標籤、工具……inst 不認的別人可以讀。工具用 JSON schema 限制引數；schema 怎麼轉成 argv——走 schema→argv 這條路，或先定義一些通用的東西，沒定。（3g.13b）
- **C-43** 最終效果：一套 library，寫完編譯成基於 aos 的類 LISP 程式，把 aos 當作業系統跑；人和 AI 都要能用。（3g.1、3g.12）

## 3. 用使用者的名詞重述兩個例子，標「定義沒說」的地方

只標、不填。這是在概念層挖邊緣狀況。

**scanf 例子（2.7）**：一個計算任務（行程）呼叫 scanf → 它需要「人類輸入」→ 人類一次只能處理幾件 → 人類輸入是資源，有幾格。
- 定義沒說：這個行程在等人的時候，它**占著格**還是**排著隊**；格是「正在被處理」還是「正在等」。
- 定義沒說：「需要人類輸入」是誰認出來的——任務自報、九軸的某一軸、附加特性、還是排序演算法判斷。
- ~~定義沒說：人類輸入這個資源「也是行程」（2.8）——一個不會結束的行程，它的「一次計算結束」是什麼。~~ **3c 答了一半**：人不是行程，是「寄信、收信、歸檔」那幾個任務在當行程；每個都會結束。剩下沒說的：這三個任務之間「等人」的那段時間，在系統裡算什麼。

**畫家例子（2.3）**：畫家是一顆 cpu、是資源；擅長人物不擅風景；一週三四張；畫完想休息；有靈感（快取）。十張人物需求、五張風景需求；另一個風景畫家很忙、一週只接一單。
- 定義沒說：「擅長人物」「會累」「有靈感」住在資源上、任務上、還是排序演算法裡；它們是九軸、附加特性、還是第三種東西。
- 定義沒說：「一週三四張」是時間上的有限，「一次只能處理三四件」是同時數上的有限——格數講的是哪一種；格跟 tick 有沒有關係。
- 定義沒說：一張畫（任務）被分給不擅長的畫家，結果比較差——「結果品質」在這套定義裡是誰的屬性、誰在看。
- 定義沒說：「這個畫家也能畫風景但畫不好」意思是一個任務有**多個候選資源**——排序「哪個任務先給哪個資源」要同時選任務和選資源，2.7 的定義只講了先後。

## 4. 概念之間還沒接起來的（三份合併，去重後 16 條；只列觀察）

1. 一個任務同時需要兩個資源（agent 要腦也要工具）時，「排序」是什麼意思。
2. 「任務排進格自己跑」（3b 的格數）和「別人把東西丟給資源、它一次處理一個」（2.8）主動方不同——任務跑，還是資源跑任務。（3c 之後：對人這種資源，「寄信」是任務在跑、人在外面跑；格數大概數的是「同時寄出去幾封還沒收回」——這是 AI 的讀法，使用者沒說。）
3. 格什麼時候算空出來：行程退出、任務說放、還是 tick 到了。
4. 資源「也是計算任務」（C-12）和「是格數」（C-10）怎麼同時成立——格數是誰在數。
5. 排序是計算任務，那誰排它；「一切都是計算任務」的遞迴底在哪。
6. 2.17 每個 agent 簽名裡的「腦」，和 2.18 很多 agent 搶的那個「大腦」，是不是同一個東西。
7. 「目標」是排序程式的輸入，還是就是排序程式本身。
8. 「優先級」是任務身上帶的，還是排序算出來的。
9. 人出現在三個位置：資源（人類輸入）、排序依據（「哪些人想先看」）、中途插話的人（9/19）——是不是同一個概念。
10. 排序演算法用的是確定性（任務屬性）還是可預測性（觀察者的認識）；排序演算法算不算一個觀察者。
11. 「tick 之間外部狀態一致」（9/24）和「停下來的空間裡含正在跑的任務」（2.11）——正在跑的任務算一致的狀態還是例外。
12. tick 什麼時候走：agent 可以叫它停（2.11），誰讓它動。
13. agent 是複合型任務，但計算任務是「一個行程」——核心看到的 agent 是外迴圈那一個行程，還是裡面每次模型呼叫各算一個。（3g.9 之後：agent 是一個資料夾＝一條 list＝一個 node，持續被求值；3g.11：元素也是 list、先求元素。「任務是一棵樹」（[四題](thinking/2026-10-11-questions.md) ①）看起來就是這個，但使用者沒直接答，不勾。）
14. 很多 agent 是共一個空間還是各有空間；~~資源住在哪~~（3d、3e 答了：設備、PU、行程全掛在空間裡）；格是空間裡的東西還是時間上的東西。
15. 9/19 說結果包含整套執行歷史——歷史是空間裡的東西嗎、屬於哪個 tick。
16. 9/19 的 list／eval 和 2.16 的 S 表示式——~~節點是資料夾還是行程~~（3e 之後：行程也是空間裡的節點，兩者不衝突）；「知道／不知道」的分界由誰判。（3f.1：資料夾＝list、list 裡有 list，9/19 與 2.16 是同一件事。）

## 5. AI 對自己的提醒（來自[診斷](thinking/2026-10-11-why-wrong.md)）

- 停在 2.4「有多任意」和 2.5「第 3 層還沒展開」的高度；那是使用者自己留的開口，不是空格。
- 主詞只用他的名詞（§1 表）。不在表裡的詞，他講出來以前不用。
- 寫觀察，不出題、不附預設、不要他拍板。等他講第 3 層；講完再從他的句子裡挑有縫的地方，像 (a) 那樣一次指一道。
- 不畫資料夾樹、不寫 JSON、不排步驤、不寫「第一版」。
