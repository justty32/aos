# 查證：頂層憑記憶講的八條（上）

每條：頂層講的（標題）→ 查證結果（【對】／【部分對】／【錯】）→ 原文（逐字）與出處 → 對使用者方法的哪一步。R 編號見 [C-54 命名方法](../../CONCEPTS/01-設計理念/C-54-命名方法.md)；「問 N」是 artifact 拍板題的編號，10-23 晚都已定（見 [thinking](../../thinking/2026-10-23-naming-method.md)）。

### man page 的 NAME 行是「名字 - 一句話」，whatis／apropos 查的就是它
- 【對】（細節一處記錯）
- > a section called "Name" or "NAME" must exist, must be the first section after the TH call, and must contain only text of the form topic[, another-topic]... \- summary-description for tools like makewhatis(8) or mandb(8) to index them.
（[man(7)](https://man7.org/linux/man-pages/man7/man.7.html)）

  > All words in this line (including the word immediately following the "\-") should be in lowercase, except where English or technical terminological convention dictates otherwise.
（[man-pages(7)](https://man7.org/linux/man-pages/man7/man-pages.7.html)）

  > whatis - display one-line manual page descriptions
（[whatis(1)](https://man7.org/linux/man-pages/man1/whatis.1.html)）

  記錯的：「NAME 行不加句點」**沒有明文**，只是慣例（man-pages(7) 只對 SEE ALSO 段寫了不加句點）；「一行」的明文在 whatis(1) 與 BSD 的 mdoc(7)，lexgrog(1) 甚至說描述可以跨行。
- ＝第 1 步「一句話描述」。R1 照這個格式，連小寫開頭都照抄。

### Rob Pike《Notes on Programming in C》：名字長度跟作用範圍成正比；kernel：區域短、全域清楚、反匈牙利
- 【部分對】
- > Length is not a virtue in a name; clarity of expression is. A global variable rarely used may deserve a long name, maxphysaddr say. An array index used on every line of a loop needn't be named any more elaborately than i.

  > I prefer minimum-length but maximum-information names, and then let the context fill in the rest. Globals, for instance, typically have little context when they are used, so their names need to be relatively evocative.
（[Pike, Notes on Programming in C（1989）](https://www.lysator.liu.se/c/pikestyle.html)）

  > The greater the distance between a name's declaration and its uses, the longer the name should be.
（[What's in a name?（2014）](https://go.dev/talks/2014/names.slide)）

  記錯的：「跟距離成正比」這句公式是 **Andrew Gerrand** 2014 年 Go 演講講的，不是 Pike。Pike 1989 年原文是「長名字給上下文少的全域、短名字給上下文多的區域」，意思一樣但沒有寫成公式。
- ＝第 6 步「簡化後仍唯一」的道理。R8 把它分成 aos 的四層。

### Linux kernel coding style：區域變數短（i、tmp）、全域要描述、匈牙利命名是腦殘
- 【對】
- > LOCAL variable names should be short, and to the point. If you have some random integer loop counter, it should probably be called i. Calling it loop_counter is non-productive, if there is no chance of it being mis-understood. Similarly, tmp can be just about any type of variable that is used to hold a temporary value.

  > GLOBAL variables (to be used only if you really need them) need to have descriptive names, as do global functions. If you have a function that counts the number of active users, you should call that count_active_users() or similar, you should not call it cntusr().

  > Encoding the type of a function into the name (so-called Hungarian notation) is asinine - the compiler knows the types anyway and can check those, and it only confuses the programmer.
（[kernel coding-style § 4 Naming](https://www.kernel.org/doc/html/latest/process/coding-style.html)）
- R8、R11。`cntusr()` 那句剛好是 R5 的門檻：縮到還原不了就不收。

### 老 Unix 結構體欄位帶前綴（`st_mtime`、`tv_sec`、`sin_port`），因為早期 C 的欄位名共用名字空間
- 【部分對】
- > early C did not tie structure pointers firmly to the structures they pointed to, and permitted programmers to write pointer->member almost without regard to the type of pointer; such an expression was taken uncritically as a reference to a region of memory designated by the pointer, while the member name specified only an offset and a type.
（[Ritchie, The Development of the C Language](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/chist.html)）

  > The same member name can appear in different structures only if the two members are of the same type and if their origin with respect to their structure is the same
（[Ritchie, C Reference Manual（1975）](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/cman.pdf)）

  > Implementations may add symbols to the headers shown in the following table, provided the identifiers for those symbols either: Begin with the corresponding reserved prefixes in the table
（表裡 `<sys/stat.h>`＝`st_`、`<sys/time.h>`＝`tv_`、`<netinet/in.h>`＝`sin_`…、`<dirent.h>`＝`d_`）（[POSIX.1-2024 § 2.2.2 The Name Space](https://pubs.opengroup.org/onlinepubs/9799919799/functions/V2_chap02.html)）

  記錯的：「成員名共用名字空間」有 Ritchie 原文；「所以才加前綴」這層因果 Ritchie 沒寫，是後人的推論。另外 POSIX 今天保留這些前綴的目的是讓實作日後能加新成員不撞到應用程式，跟 1970 年代的原因不同。
- ＝5d「主題在前」（R7）。前綴＝主題，一眼看出屬於誰；但 JSON 有巢狀，巢狀說了就不重複（R4）。
