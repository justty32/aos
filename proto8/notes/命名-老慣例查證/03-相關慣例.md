# 跟使用者方法直接相關的權威慣例

每條：慣例 → 原文（逐字）與出處 → 對應使用者方法的哪一步。「問 N」是 artifact 拍板題的編號，10-23 晚都已定（見 [thinking](../../thinking/2026-10-23-naming-method.md)）。

### GNU Coding Standards：全域名字要有資訊、區域可以短、縮寫少用但定義過就可常用、底線分字
- > The names of global variables and functions in a program serve as comments of a sort. So don't choose terse names—instead, look for names that give useful information about the meaning of the variable or function.

  > Local variable names can be shorter, because they are used only within one context

  > Try to limit your use of abbreviations in symbol names. It is ok to make a few abbreviations, explain what they mean, and then use them frequently, but don't use lots of obscure abbreviations.

  > Please use underscores to separate words in a name, so that the Emacs word commands can be useful within them.
（[GNU Coding Standards § Names](https://www.gnu.org/prep/standards/html_node/Names.html)）
- 第 3 步縮寫表（R5）：「定義幾個、解釋、然後常用」就是 abbr.json 的做法。底線分字＝C-54（R10）。長短＝R8。

### Google AIP-140：開發者都認得的縮寫用縮寫，不全拼
- > For well known name abbreviations among software developers, such as "config" and "spec", the abbreviations should be used in API definitions instead of the full spelling.
（[Google AIP-140](https://google.aip.dev/140)）（例子：`config`、`id`、`info`、`spec`、`stats`）
- 第 5b 步「有沒有公認縮寫」（R5）。跟 GNU 互補：公認的就用。注意它的例子是 `config` 不是 `cfg`；aos 的 `cfg` 靠表撐。

### POSIX：`_` 開頭的名字保留給系統實作；`E`＋大寫保留給 errno；`_t` 後綴保留
- > all identifiers that begin with an &lt;underscore&gt; and either an uppercase letter or another &lt;underscore&gt; are always reserved for any use by the implementation.

  > All identifiers that begin with an &lt;underscore&gt; are always reserved for use as identifiers with file scope in both the ordinary identifier and tag name spaces.
（[POSIX.1-2024 § 2.2.2](https://pubs.opengroup.org/onlinepubs/9799919799/functions/V2_chap02.html)）
- R11。老慣例讀 `_` 開頭＝「保留、內部」，`_entry` 剛好相反（問 8）。

### Go：名字長度跟範圍成正比、跟用的次數成反比；不重複套件名；縮寫大小寫一致
- > the length of a name should be proportional to the size of its scope and inversely proportional to the number of times that it is used within that scope.

  > When naming exported symbols, the name of the package is always visible outside your package, so redundant information between the two should be reduced or eliminated.
（例：`widget.NewWidget` → `widget.New`、`db.LoadFromDatabase` → `db.Load`）（[Google Go Style Guide, Decisions](https://google.github.io/styleguide/go/decisions)）

  > The basic rule: the further from its declaration that a name is used, the more descriptive the name must be.
／
  > Words in names that are initialisms or acronyms (e.g. "URL" or "NATO") have a consistent case.
（[Go Code Review Comments](https://go.dev/wiki/CodeReviewComments)）

  > in the implementation of a UserCount method, a local variable called userCount is probably redundant; count, users, or even c are just as readable.
（[同上](https://google.github.io/styleguide/go/decisions)）
- R4「巢狀說了就不重複」就是 Go 的「不重複套件名」（`loops.bob.pid` 不寫 `loop_pid`）。R8 四層。`users` 代替 `numUsers` 剛好是你「被數的東西加 s」的寫法。

### Plan 9 style(6)：變數與函式全小寫、不用底線；常數大寫；struct 標籤首字大寫
- > variable and function names are all lowercase, with no underscores.

  > enum or #defined constants should be Uppercase (or UPPERCASE).

  > struct tags are Uppercase, with matching typedefs.
（[Plan 9 style(6)](https://9p.io/magic/man2html/6/style)）
- 跟 aos 不同的一套：Plan 9 是連底線都不用（`maxphysaddr`）。aos 走 GNU／kernel 的底線路線（R10），這是選邊、不是對錯。

### Unix 指令名為什麼這麼短（`ls`、`cp`、`cat`）
- > Typing long names is slow on any keyboard, whether teletype or smartphone. I know of no other reason for short names.
（[Doug McIlroy，;login: 2016 訪談](https://www.usenix.net/system/files/login/articles/login_spring16_05_mcilroy.pdf)）（Teletype 的說法是訪談者 Rik Farrow 提的；沒有書面設計紀錄）
- 第 5b 步「少寫幾個字母」的來由。aos 的程式名帶 `aos-` 是 R8 第 2 層（PATH 範圍），不衝突。

### Pike：親戚變數要一致命名；Gerrand：好名字＝一致、短、準
- > If you call one variable maxphysaddr, don't call its cousin lowestaddress.
（[Pike 1989](https://www.lysator.liu.se/c/pikestyle.html)）

  > A good name is: Consistent (easy to guess), Short (easy to type), Accurate (easy to understand).
（[Gerrand 2014](https://go.dev/talks/2014/names.slide)）
- C-54「一次記住、全體系通用」（R4）。`paused`／`stop` 詞性不一就是這條在問（問 4）。

### PEP 8：單字 `l`／`O`／`I` 不用；`_x`＝內部用；縮寫在 CapWords 裡全大寫；對外的名字反映用途不反映實作
- > _single_leading_underscore: weak "internal use" indicator.

  > When using acronyms in CapWords, capitalize all the letters of the acronym. Thus HTTPServerError is better than HttpServerError.

  > Names that are visible to the user as public parts of the API should follow conventions that reflect usage rather than implementation.
（[PEP 8](https://peps.python.org/pep-0008/)）
- R11（`_` 開頭，問 8）。錯誤代號裡縮寫怎麼寫：aos 現在是 `WsMissing`、`CfgBad`（首字大寫），PEP 8 會寫 `WSMissing`；C-54 例子 `ApiKeyMissing` 已經選了首字大寫那派，不改。
