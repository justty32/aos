# 3. 監管樹：誰管誰

**s6／runit 怎麼做。** s6：`s6-svscan` 看一個 scandir，裡面每個服務資料夾起一支 `s6-supervise`；`s6-supervise` 只管一個服務，跑它的 `run`（長壽、不該結束），死了跑 `finish` 再重起（[s6-svscan](https://skarnet.org/software/s6/s6-svscan.html)、[s6-supervise](https://skarnet.org/software/s6/s6-supervise.html)）。runit 一模一樣的兩層：`runsvdir` 至少每 5 秒看一次資料夾有沒有變、每個子資料夾起一支 `runsv`（[runsvdir(8)](https://smarden.org/runit/runsvdir.8)、[runsv(8)](https://smarden.org/runit/runsv.8)）。**服務清單＝scandir 裡有哪些資料夾**：放一個 symlink 進去就起、拿掉就停。

**aos 怎麼做。** `aos-daemon` 管一群子項，清單是 daemon.json 或 ctl 的 `children`（整份期望，N-54），每個子項一個小格 `$AOS_STACK/<名字>/`，子項是經 aos-exec 起的 `aos-loop`；loop 再一拍一拍跑短命的 `aos-exec`（N-28）。

**對應關係。** aos-daemon ≈ s6-svscan／runsvdir；aos-loop ≈ s6-supervise／runsv；一拍 ≈ `run`。**但有一個根本差別**：s6 的 `run` 是長壽的，結束就是出事；aos 的一拍是短命的，退 0 就是正常、接著下一拍。換句話說 aos-loop 本身就是「死了就再跑」的監工，只是它管的對象本來就會一直結束。

**可借鏡。** 監管工具的分層（掃清單的一支、每個服務一支監工）跟 aos 的 daemon／loop 分層是同一個形狀，這點 aos 已經有了。scandir「資料夾存在＝要跑」的寫法其實很合 aos 的世界觀（C-51 資料夾與 JSON 互通、C-68 資料夾＝程式），只是使用者 10-16 刪了 N-10 之後選了 ctl 的 `children`，這裡只記下有這種寫法。

**aos 刻意不同的地方。** **接回**：s6／runit 的做法是讓監工本身不會死（s6-svscan 在一秒後重起死掉的 s6-supervise，s6-svscan 自己遇到致命錯 exec 成 `.s6-svscan/crash`），重複的實例靠 `lock-fd` 擋（[servicedir](https://skarnet.org/software/s6/servicedir.html)）；文件裡沒有「監工重起後認回還活著的服務」這回事。aos 的 `adopt` 讀上次的 state、pid＋啟動時間對得上就接回（N-17、N-28）——這是 aos 比 s6 多的一塊。

# 4. 重啟策略

**s6／runit 怎麼做。** s6：預設永遠重起；兩次起動之間至少隔 1 秒，但服務 ready 超過 1 秒才死就立刻重起；`down` 檔＝預設不起；`s6-svc -o` 跑一次、`-O` 死了不再起；**`finish` 退 125＝永久失敗、不再重起**；`timeout-finish` 管 `finish` 跑多久（[s6-supervise](https://skarnet.org/software/s6/s6-supervise.html)、[s6-svc](https://skarnet.org/software/s6/s6-svc.html)）。runit：`run` 或 `finish` 一起來就結束時等 1 秒再起；`finish` 拿到 `run` 的結束碼與訊號（[runsv(8)](https://smarden.org/runit/runsv.8)）。

**aos 怎麼做。** aos-loop：拍退 0＝下一拍、**10＝要求停（loop 以 0 結束）**、其他非 0＝loop 以原碼結束、不重試（N-43）。aos-daemon：**子 loop 結束後不自動重起**，停在 `exited`、記 `code`／`signal`；要再起就從 ctl 拿掉再放回（使用者 10-20「照預設」）。N-28 寫的 `policies.child_exit`、六態裡的 `backoff` 沒做。〔10-22 使用者改：兩者從規範拿掉、不是待補；要自動重起自己在鏈上接工具（例如外面用 s6／runit 管），見 [NORMS/04](../../NORMS/04-基礎設施-loop與daemon.md) N-28。daemon 重開＝重新開始、照名單起，不算自動重起。〕

**可借鏡。** ①**aos 的 10 ≈ s6 的 `finish` 退 125／`s6-svc -O`**：都是「被管的那個自己說：別再叫我了」。對照可以確認這個設計不是孤例。②**防爆衝的現成規則**：s6 的「兩次起動至少隔 1 秒；穩定跑過一段才死就不等」是為了不讓壞掉的服務秒速重起把機器打滿。aos-loop 現在遇到非 0 就整支結束，不會爆衝；但日後若要做 daemon 的自動重起（`policies.child_exit`、`backoff`），這條是最小、最好講的版本。③**收尾腳本拿到死因**：runit／s6 的 `finish` 拿到結束碼和訊號；aos 的對應物是 daemon state 裡的 `code`／`signal`，已經有了，不用再加 `finish`。

**aos 刻意不同的地方。** 監管工具的核心價值是「自動重起」，aos-daemon 目前偏偏不做——這是使用者 10-20 選的（失敗的子項要人看過），不是漏掉。

# 5. readiness：起來了不等於準備好了

**s6／runit 怎麼做。** s6：服務資料夾放 `notification-fd`（一個 fd 號碼），程式準備好時往那個 fd 寫一個換行、關掉，s6-supervise 更新 `supervise/status`、發出 `U` 事件；`s6-svc -wU` 可以等到 ready；不會通知的程式用 `s6-notifyoncheck` 反覆跑 `data/check` 代替（[notifywhenup](https://skarnet.org/software/s6/notifywhenup.html)）。s6-rc 靠這個做「依賴的服務 ready 了才起下一個」。runsv(8) 沒有對應的機制。

**aos 怎麼做。** 沒有 readiness。daemon 的 state 窗只有 `phase`（`running`／`exited`）；心跳只在兩拍之間跳。

**可借鏡。** aos 的拍是短命的，「第一拍跑完」（state 的 `lap` ≥ 1）就已經是個自然的「準備好了」，不必另開 fd。等日後 kernel 要排「誰先起、誰等誰」時，s6 的「寫一個換行」是最小的協定可以參考，換成 aos 的說法大概是 state 窗裡多一欄。

**aos 刻意不同的地方。** s6 用 fd／管道通知；aos 原則上用檔案（C-64：用檔案才能借 Linux 權限），所以只能借形狀、不能照搬做法。
