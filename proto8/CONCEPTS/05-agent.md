# agent

使用者 10-15：「把 fsm 也跟 tasks 放一起」——agent 狀態機那幾條（C-18、C-25、C-39）跟著 fsm 移到[基礎設施](03-基礎設施.md#fsm)。

## 腦、工具、可預測性

- **C-19** agent 的簽名＝腦（模型）＋記憶（核心人格、近期記憶）＋手腳（工具）。（2.17）
- **C-20** agent 是複合型任務（外迴圈便宜、叫的模型與工具貴），所以要被排程；最核心的一題是「很多 agent 時誰先用腦」。（2.18、2.19）
- **C-21** 可預測性有主體性，不是任務的屬性，是觀察者的認識。（2.14、2.15）
- **C-22** 提高 agent 可預測性的方法：當 S 表示式拆開，能寫死的節點換成程式，降低走進不可預測節點的機率。（2.16）
- **C-22b** 可預測性不只是函式本身的：同一函式在不同狀況、不同（例如老舊）硬體上跑，可預測性不一樣。節點＝函式內部＋它所在的執行環境，合起來才是執行節點。（3g.13c）
- **C-23** agent 內部怎麼設計是後面的事，先把底打好。（2.20）
- **C-40** agent 要能當拋棄式函式用：引用一個設好的資料夾（標頭檔）、填幾個引數、讓它跑起來，執行環境在引用者這邊。library 做 binding 讓這件事簡單。（3g.9、3g.10）
- **C-42** 工具＝被引用的標頭檔；agent 也可以是工具；aos 體系的每一樣（daemon、tick、task、inst、kernel）都基於 inst、都是 shell 指令，所以都是 agent 的工具——自我迴圈改進的閉環。（3g.12、3g.13）

## agent＝函數＋binding

- **C-46** agent 的使用＝函數＋binding：`agent_call(system, history, engine, tools)`；綁好就是 `agent_bob`，用時 `agent_bob.call(history, engine_args, tools_append)`。具體是一個 `bob/` 資料夾（定義：system、腦、工具、表），**呼叫時不變**，所以 bob 是可重複使用的函數。history 累積的地方（**frame**）是另一個參數，很像函數本體的 stack。**tools＝函數的包裝**，對 call 來說是「傳進去、可供它使用的函數」（像高階函數的參數）；bob/ 裡綁的 tools 只是預設值；tools 裡可以是另一個 agent 的呼叫（agent 當工具＝呼叫一次 bob），所以能一層層組合。（10-15 使用者定，概念層；[thinking 10-15 §11](../thinking/2026-10-15-topics/04-agent當函數.md#11-agent-當函數binding當工具)）
  **10-16 改：agent 當函數是概念上的，不是形式上的**（10-15 收工後那套 frame 資料夾＋`frame.json`（`parent` 鏈）＋`args.json` 進、`ret.json` 出、「放同名檔＝綁定」不要了）。使用者：「我不喜歡 args.json／ret.json。我知道這是昨天我說『把 agent 當函數用』的直觀體現，但這極致體現了 AI 的蠢蛋之處。把 agent 當函數用，不是說形式上，而是在概念上，不要皮似神不似。我們現在就是把 JSON＋資料夾當 Lisp 的 list，這就是一個函數啊，何必再造一個體系？」（[稿 § 一](../thinking/2026-10-16-agent-inherit.md#一使用者原話10-16整理版)）新的意思：**JSON＋資料夾（定義）本身就是函數**；呼叫＝`aos exec frame 定義`（C-60）；定義（bob）呼叫時不變；**frame**（cwd，C-59）就是函數的環境、像 stack，history 這類狀態落在這裡，**放哪由呼叫方決定**（10-15 原話：「agent在呼叫時，可以選擇frame要放哪」仍成立；10-16 白天一度叫「工作區」，10-16 夜改回 frame、「工作區」留給使用者的成品區，C-65；放哪的自由見 C-67；工具的小格開在呼叫者的 frame 裡，命名待定）；agent 的 stdin 只放定義、這次的話放在 frame（C-58）；工具的地址與參數見 C-61。binding（這次換腦、加工具）用什麼機制 10-16 沒定（[待定](../NORMS/08-待定.md)）。
  **10-15 深夜加嚴（C-52 徹底切割）**：agent 這層**只看到自己的工具清單**（名字、說明、參數），工具裡面在幹嘛——是不是另一個 agent、它的 frame 放哪、綁了什麼腦——agent 一概不管、不傳、不繼承；子 agent 只看自己的 frame、看不到呼叫方的（10-16 起沒有 `parent` 鏈）。要換子 agent 的腦，是那張工具 inst 自己的事（使用者：「agent他就是看到自己的工具，工具在幹嘛他就不管，拜託，乾淨，完全切割，徹底切割，不得有任何殘留。」）。
- **C-50** agent＝狀態機＋各狀態跑的 inst，複雜度集中在那些 inst（使用者：「agent基於狀態機，在某狀態下跑某個inst，所以複雜度主要集中在那些inst」）。「程式方面的實作可以擠在一坨，共用一些lib，但是在實際的資料夾布局和json那塊仍要保持單純」。（10-15 收工後意見 1～3，[thinking 意見 1～4](../thinking/2026-10-15-opinions-1-4.md)）
  **10-16 改**（原「一個 agent 的定義＝一張 inst（一份 JSON），裡面是怎麼拍（loop）、表（fsm）、每格一張 inst…；JSON 是正本，資料夾只是用指示詞拆檔」——10-15 深夜「C-50 選 a」那版）：**一個 agent 的定義＝一個 `.aos/` 資料夾**（定義／食譜，C-59），入口 `.aos/inst.json`，裡面的檔互相指一律寫 `.aos/x`、從 frame 算，不靠 `$ref`；檔少一點、寫成一份大 JSON 也行。agent 程式那層的 stdin 只放這份定義（C-58）。工具也各是一個定義資料夾（C-61）。定義裡**不含**「怎麼拍（loop）」：agent 由外面的 loop 驅動（10-16 KISS 重審拍板 4，C-62、[N-53](../NORMS/10-基礎設施-定義與工作區.md)）。葉子程式（`aos`、`date` 這類本來就是指令的）照舊用指令名；**定義之間互指不靠 PATH**（C-61）。

## agent 的入口與工具（10-16 使用者定）

出處：[稿 § 四](../thinking/2026-10-16-agent-inherit.md#四使用者決定10-16)。正式名詞：定義（食譜）、frame（廚房；10-16 夜改名，原叫工作區）、工作區（使用者的成品區，C-65）、門房（`aos exec`），見 [CONCEPTS 基礎設施 § 定義與工作區](03-基礎設施.md#定義與工作區食譜與廚房10-16)。規範 N-49、N-50、N-53；**程式還沒改**。

- **C-58** **agent 的 stdin 只放一份，這份是定義（食譜）**；**「這次的話」放在 frame（廚房）裡**，使用時指定 frame 的位置（10-16 夜改字：原寫「工作區」，C-65）。以後可以做類似 `aos exec` 的語法糖，例如 `aos-agent-say`、`aos-agent-init`。（使用者 10-16：「stdin只放一份，這份要食譜。」「放在廚房裡，然後使用的時候指定廚房的位置。以後可能會做類似aos-exec那樣的語法糖，比如aos-agent-say, aos-agent-init...」）
- **C-61** **工具的地址不用 PATH**：寫在呼叫者自己定義裡的一條相對捷徑（bob 的 `.aos/tools/brush` 指向隔壁的 brush 定義），兩份定義一起搬也不斷；**工具一律做成定義資料夾**（`date` 這種也是 `.aos/tools/date/`），所以工具格對每個工具都做同一件事：**站在自己的 frame，開一個小格、叫門房 `aos exec 小格 .aos/tools/<名>`**——門房掛好、跑（10-16 夜改字：原寫「工作區」「`work/<n>`」，C-65；小格命名待定）。工具站在哪：一般工具在入口 inst 寫一行站進使用者的工作區，agent 工具不寫＝站在自己的小格（它的 frame），工具格不分辨（C-66、N-56）。工具裡是不是另一個 agent，工具格不知道（C-52）。**工具參數走門房（`aos exec`）的 stdin，分兩層**：門房那層的 stdin 收參數，由 stub／旗標明寫把它放進工具的 frame（小格）；裡面 agent 程式那層的 stdin 仍然只放定義（C-58）；一般工具照 N-27（參數走 stdin）。PATH 只留給人在終端打指令。（使用者 10-16 夜：「可以不使用PATH嗎？」→ 看完提案：「好!」；兩層：「還是不太懂，但感覺OK，就先這樣吧，以後再來搞懂。」）

## agent 就是一台狀態機（10-16 使用者定）

- **C-62** **agent 的定義就是一台狀態機；這台狀態機怎麼跑、由誰跑，概念上都不管**（接 C-18、C-39）。aos 自己的 agent 怎麼跑是規範的事（[N-53](../NORMS/10-基礎設施-定義與工作區.md)：被外面的 loop 一拍一拍驅動）；別家的 agent（例 Claude Code）是一個行程持續跑，概念上同樣是 agent。（使用者 10-16：「agent的定義就是一個狀態機，至於這個狀態機怎麼跑、由誰跑，都無所謂。這是概念。但是我們的規範會說，為了讓agent方便審視自己，所以agent就是一個被人驅動的狀態機，需要外面有人用loop驅動他。這是我們的aos agent，至於我們常見的claude code，他們就是一個process持續執行，那是他們愛的。」，[KISS 重審拍板 4](../thinking/2026-10-16-kiss-recheck.md#使用者拍板10-16)）
