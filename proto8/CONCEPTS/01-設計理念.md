# 設計理念

- **C-01** aos 存在的理由是讓大語言模型方便使用；目標多到只能靠模型寫，所以核心要讓模型好用。（2.1）
- **C-02** aos 蓋在現有作業系統上，硬體層的計算分配不重做。（2.5）
- **C-03** 由下往上：Linux → daemon → 時空 → 排程與資源分配 → agent。上層只透過下層。（2.5、2.10）
- **C-04** daemon 完全處理 Linux 那邊的事；它之上的東西不碰 Linux。（2.5）10-16：檔案讀寫權限也是這層能借來用的（例 kernel 當某 daemon ctl 的唯一寫者），見 [C-64](#檔案權限10-16-使用者定)。
- **C-07** 體系用的表達方式以模型天生就會的為準（檔案系統、POSIX、JSON），為的是讓它能自省。（2.6、9/23）
- **C-24** 要最佳化的不是時間空間，是金錢、可預測性、人能不能理解。（9/1 ideas 01；2.1 重申）
- **C-45** 比起實作，更重要的是規範。aos 提供一些符合規範、方便的語法糖（例如 aos-inst、aos-fsm），但不要求所有人一定要用。例：aos 時空這個概念衍生出的規範＝大家都要看 tick-tock 時鐘、資料夾別亂弄。（10-12）
- **C-43** 最終效果：一套 library，寫完編譯成基於 aos 的類 LISP 程式，把 aos 當作業系統跑；人和 AI 都要能用。（3g.1、3g.12）**「編譯」在資料夾＝程式（C-68）之下的意思，10-19 晚使用者答**：「意思是我們要做這樣一套程式，要一個一個mkdir, vim修改檔案，等於是一個元素一個元素去堆疊出一個table，那不如直接用lua/lisp生成這麼一套資料夾佈局」——一套 aos 程式就是一堆資料夾與檔案（一個 table 一個元素堆出來的），與其手動 mkdir、vim 一個一個堆，不如用 lua／lisp 一類語言把整套資料夾佈局生成出來；那個生成就是「編譯」，library 就是做這件事的。（[ideas § 12](../thinking/2026-10-19-ideas.md)）
- **C-48** JSON 格式族：沿用 inst 單子族、loop／fsm 設定族，靠加 key 與任意 value 擴充（只處理認得的 key），除非必要不新增格式。兩個通則：**私有 key**——各功能可以在同一份 JSON 放只有自己看得懂的 key，藉此共享同一份格式，前提是 key 不重疊（私有 key 慣例：`_` 開頭的 key＝附註，宿主程式忽略、給別人看，例 `_tool`、`_metainfo`；給人寫的備註固定叫 `_notes`（跟 `_metainfo`＝被叫者自報的特性分開；10-15 使用者「都按照推薦」）；共用同一份檔的私有 key 真的撞名了才加功能前綴，例 `agent_`；各程式的說明列出自己認得的 key）；**值的雙形**——一個值除了字面純值，也可以寫成物件（展開形），像 Lisp 的 `3` 與 `(+ 1 2)`（例：`priority` 寫 `"low"` 或 `{"val", "deadline"}`；展開形的原值固定在 `val`，C-55），實作麻煩就權衡，太麻煩的地方可以不支援物件形。指示詞是這招的一種用法，現在只剩 `$env`：單子裡任何位置的 `{"$env": 名, "path": 子路徑}` 換成該環境變數底下的路徑，讀的是執行當下的環境、像 shell 的 `$HOME`，是正式機制（例 `{"$env": "AOS_STACK", "path": "plan"}`）；單子本來就能內嵌，不必拆檔，所以沒有 `$ref`。（10-15，[原文](../thinking/2026-10-15-json-families.md)；10-16 夜使用者：「可以用$env啊」→ 頂層給兩案，選 A：「A」；10-19 改，[CONVENTION P-31](../CONVENTION.md)、[N-45](../NORMS/06-基礎設施-命令列與指示詞.md)）
- **C-51** 資料夾與 JSON 可以互通：資料夾＝object、名字＝key，一份 JSON 本身也是一個小檔案系統，inst 體系以外的格式也能這樣套；「但是我會覺得，建議不要濫用，因為雖然可以互通，但畢竟在細節上有差異」——所以互通只當工具與思考方式，**不進規範**（aos_tree 這支互轉工具 10-15 深夜 KISS 批次 1 刪）。JSON 那半的入口怎麼找：C-72（10-19 晚）。JSON schema 在這套大量用 JSON 的體系裡有更多用處（當型別、interface、簽名，也能描述資料夾的形狀）；驗證選用，執行期先只驗 LLM 回話。隱藏檔一律略過；入口的位置由環境變數 `AOS_ENTRY` 指（預設 `.aos/exec`，C-68）。這也是使用者 10-19 說的「純粹把資料夾作為 lisp 的 list 或 lua 的 table」的根（[ideas § 1](../thinking/2026-10-19-ideas.md)；比喻 10-19 晚定用 table，C-71）。（10-15 收工後意見 5～7，[thinking 意見 5～7](../thinking/2026-10-15-opinions-5-7.md)）

## 最高原則（10-15 深夜使用者定，[原文](../thinking/2026-10-15-principles.md#10-15-深夜使用者拍板切乾淨kiss)）

- **C-56** **KISS 是最高原則，也是最後原則**：「我要的是徹底的純淨簡潔，KISS。把KISS納進最高原則。」（10-15 深夜）「KISS是最高原則，但也是最後原則，本質上是希望提出的設計在滿足各類需求和原則後，最後能回頭思考，把一些多餘的東西清掉。」（10-16，[原文](../thinking/2026-10-16-kiss-last.md)）接 [proto7 設計原則](../../proto7/notes/principles.md) 第 9 條（核心只做最基礎的保護、錯誤同類走同一分支、很多東西默認正常、誤用不歸組件管）。其他原則都在它底下，下面兩條（C-52 巢狀切乾淨、C-53 錯誤只處理自己的）是它在巢狀與錯誤上的樣子；但 KISS 是**最後一步的減法**：設計先滿足各類需求與其他原則，再回頭把多餘的清掉——不為了方便偷看一層、不為了邊緣狀況加機制；也**不拿「最乾淨、規則最少」當抄近路的理由**（使用者：「“最乾淨、規則最少”很容易導致一些問題，也就是抄近路反而導致繞遠路」），清的時候不能違反其他原則。**寫什麼就做什麼**（10-16 補）：給的值照字面意思用，不讓某些特定值偷偷變成另一種行為；不拿「要人記的暗規則」換少一個 key——減法清掉的是多餘的東西，不是把規則藏進值裡（使用者：「不要用這種方式添加規則，不直觀，這等同於埋雷，大家都預期“我給啥檔案，他就是往這個檔案塞東西”，你還要人家記“如果給的是這個檔案，那他會幹別的事情”，這太糟糕了。」）。例：inst 的 `stdout` 寫 `/dev/stdout` 就只是照字面打開那個路徑，不特判成直接繼承 fd（AI 提的特判被否決）；沒寫的串流就是接呼叫者的，不需要旗子（10-19 改，[bin/README](../bin/README.md)；[原文](../thinking/2026-10-16-kiss-last.md#原文寫什麼就做什麼10-16)）。

## 兩條總原則（10-15 使用者定，[原文](../thinking/2026-10-15-principles.md)；10-15 深夜加嚴）

- **C-52** 巢狀：**只管自己這一層，徹底切割、不得有任何殘留**。盡量保持簡單；之後一複雜，巢狀一定常見，所以每一層只管自己，處理上層時下層被乾淨切開、可以不管；真要管時心裡有一把尺——同一個原則在每一層重複、貫穿整個巢狀，只看最上層就能處理。10-15 深夜使用者加嚴：**想看子層的東西要另外透過其他機制，沒機制就別碰**（不偷讀下層的 stderr、不替下層驗它的東西）；**上層不需要、也不該知道下層是什麼**（fsm 不知道某格是不是另一個 fsm，agent 只看到自己的工具清單、不知道工具裡是不是另一個 agent，什麼都不往下傳、不繼承）。已有的例子：fsm 只管「格→結束碼」（C-49、N-36）、格的 stderr fsm 不讀（N-38）、inst 的結果只說子程式（N-30）、暫停與拍數交給拍它的 loop（N-39）、agent 不知道工具內部、子 agent 只看自己的 stack（C-46；P-17 給被叫者自己的小格）、巢狀時 aos 只訂被叫者自己的 `AOS_STACK`、子程式的 stack 由它自己訂（C-70）、整隻 agent 叫、不拿別人 fsm 的一拍（P-35）、被外層逾時殺掉就是那格失敗、不為內層說話（P-36）、每層出錯只說自己一行（P-21）、結束碼只說自己這一層（N-43）。（10-19 改，[CONVENTION](../CONVENTION.md)）
- **C-53** 錯誤：**各單元只處理自己的錯**（接 [proto7 設計原則](../../proto7/notes/principles.md) 第 9、10 條：錯誤分類同類走同一分支、很多東西默認正常、誤用不歸組件管、先定義組件要求什麼與保證什麼）。對別人的錯三種姿態，每個單元在說明裡寫清楚自己採哪種：(a) **入口**——你丟給我的就該是正常的：我不管、默認正常（N-18、N-20、卡死不防護），或我在入口檢查並處理（N-08）；(b) **出口**——我交出去的保證不出錯（N-05 半份不算）；(c) **事先列出**可能的錯（N-38、各程式說明裡的錯誤訊息）。錯誤路徑濃縮成少數幾條（N-43 結束碼只有三種、stderr 一行「程式名: 原因」〔P-21〕、N-38 出錯一律 phase 不動），減少「出了問題之後的行為」的複雜度。下層的錯**不轉述**（C-52 加嚴）：上層只說「下層結束碼非 0」，下層的錯誤內容留在下層自己寫的地方（stderr、stack 裡的檔）。之後可納入 kernel 評估（[待定](../NORMS/08-待定.md)）。

## 命名（10-15 使用者說，[原文](../thinking/2026-10-15-naming.md)）

- **C-54** 命名：**好懂、快速理解、快速記住**。資料夾布局、程式碼、JSON 格式最好一看就懂七七八八——先排結構，結構與名字本身就是說明；說明只要少量簡介，再直接甩出 pseudo code／JSON／資料夾。
  - **一次記住、全體系通用**：同一個詞在 aos 各處同義（`inst`、`ctl`、`state`…）。縮寫只用大家本來就知道的，而且**新縮寫要先進 [aos 認可縮寫表](abbr.json) 才能用**（10-15 使用者「要，縮寫表照推薦做」；表的欄位：縮寫、全稱、意思、例子）。
  - **難懂才加前後綴**（`ctl_dir`），表特性（`dir`、`path`、單位 `ms`）或子類時用；不用匈牙利命名法那種型別前綴。**可搜尋的標籤／主題放前面、由大到小**（`path_insert`、`path_query_sql`），排序、搜尋時同類排在一起。
  - **資料夾、檔名、JSON key：全小寫加底線**；**對外的指令名＝同一個名字把底線換成連字號**（`node_path` ⇄ `node-path`）；環境變數全大寫加底線（`AOS_ENTRY`）（10-15 使用者「指令名就是底線換連字號。」）。
  - **程式碼照該語言規範**（Python 照 PEP8），並跟檔名固定對上：程式的 `NodePath` ⇄ 檔名 `node_path`；程式裡可混大小寫表層級（`NodePath_SQL_Query`）。
  - **靠資料夾布局少用底線，複數資料夾裝同類**：裝同一類多個東西的資料夾用複數名（`insts/`、`cells/`、`tools/`），裡面的檔名不再重複類別（`insts/a.json`，不寫 `inst_a.json`、`insts/inst_a.json`）。複數一律只加 `s`（縮寫也是：`insts`、`cfgs`、`msgs`），不用不規則變化；本身已是複數或不可數的照原樣（`args`、`data`、`history`）；單一檔案用單數（`brain.json`、`ret.json`）（10-15 使用者「對了，還有複數形式，比如./inst-a.json, ./insts/a.json」，細節「都按照推薦」）。
  - **錯誤若帶代號，照 CamelCase、主詞在前**（新程式的錯目前只有 stderr 一行，P-21，沒有代號；有代號時照這條）：`ArgumentsBad`、`FlagUnknown`、`ApiKeyMissing`、`StateBad`，同主題的錯排在一起；「沒有某物」一律 `…Missing`、「不認得」一律 `…Unknown`、「壞了／不合」一律 `…Bad`（10-15 晚使用者「都按照推薦」，盤點 P7，舊的 `BadArguments`、`UnknownFlag`、`NoApiKey`… 已全改）。
  - **例外**（10-15 盤點後定，使用者「其他直接改」）：入口檔照 Unix 老慣例全大寫（`README.md`、`INDEX.md`、`CONCEPTS.md`、`NORMS.md`，`ls` 時排前面）；`bin/` 是 Unix 慣例名、單數照留；工具自己的慣例照工具（pytest 的 `tests/test_*.py`）；外部 API 的參數名照原名、不進縮寫表（`num_ctx`、`keep_alive`）；一個檔裝很多筆的串流／日誌檔可以用複數（`steps.jsonl`）。proto8 的 `demo/` 照留單數（原型期連結太多、收益低；下一個 proto 起用 `demos/`；10-15 晚使用者「都按照推薦」，盤點 P5）。`last_`／`max_` 這種修飾詞在前不算違反「主題在前」——`last_` 本身就是一個可搜尋的群組（state 窗裡「上一次的」排在一起），`max_` 是大家都知道的慣例。
  - 現況不合的地方（23 條）10-15 晚使用者「都按照推薦」，已全照推薦改完，見 [thinking 命名 § 盤點](../thinking/2026-10-15-naming/盤點.md)。

## 布局成長（10-15 使用者說，[原文](../thinking/2026-10-15-layout-growth.md)）

- **C-55** 布局成長：資料夾／檔案與 JSON 物件有同像性（C-51），所以**長大的規則同一套**。檔案那邊照 [wf/STRUCTURE.md](../../wf/STRUCTURE.md)（唯一出處）：一個檔內容太大、或一個檔扛不了那麼多職責，就變成資料夾，原檔變成入口（index＋readme），資料夾裡再照既有路徑長（index、readme 各自獨立出來）。JSON 那邊照同一套：一個純值不夠用（例 `priority: 3`），就長成物件（`priority: {"val": 1, "type": "normal task", "_notes": "haha", "timeout": 0}`）——key 不變，原本那個純值放進物件裡固定的一格，其他屬性當同層的 key，`_` 開頭的附註照 C-48，物件裡每個值再照同一套長；只剩原值那一格就縮回純值。這就是 C-48「值的雙形」的成長方向，讀的人兩形都收（純值＝只給了原值那一格）。**原值那一格一律叫 `val`**（ctl 的 `paused`／`stop`、`priority`、fsm 的格都是；程式讀值一律先收成物件再看自己認得的 key；10-15 使用者「都按照推薦」，選 A）。兩邊怎麼對見 [thinking 布局成長](../thinking/2026-10-15-layout-growth.md)。

## 檔案權限（10-16 使用者定）

出處：[thinking 10-16 結束碼與權限](../thinking/2026-10-16-exitcode-perm.md)（C-63 結束碼只是參考，10-19 被停止碼 10 取代，條號作廢）。

- **C-64** **用檔案（而不是程式之間的管道）的理由之一，是能借 Linux 的檔案讀寫權限做事**：例如讓 kernel 成為某個 daemon 的 ctl／清單唯一能寫的人——多人同時寫同一份會互相蓋掉的問題，靠權限讓它只有一個寫的人來解決。權限是 Linux 那邊的事，歸 daemon 那層（接 C-04）。（使用者 10-16：「之所以要用檔案，就是因為可以透過linux的檔案讀寫權限機制，來做一些神奇的事情。像是讓kernel成為某daemon的ctl/清單的唯一可讀寫者。」）

## 資料夾程式與環境變數（10-19 使用者定）

出處：[ideas § 1～§ 5、§ 10](../thinking/2026-10-19-ideas.md)；慣例：[CONVENTION](../CONVENTION.md)；規範：[N-57～N-60](../NORMS/10-基礎設施-定義與工作區.md)。

- **C-68** **資料夾＝程式**：「純粹把資料夾作為lisp的list或lua的table，然後有一個entry，在lisp就是第一個元素，在lua就是metatable裡面定義的那個，而在我們這邊，就是環境變數定義：AOS_ENTRY=.aos/inst，這個定義的目標必須是可執行檔。就這樣，非常簡單。」入口後來改名 `.aos/exec`（預設值，環境變數可覆寫）；兩個比喻 10-19 晚定只用 table（C-71）。寫程式＝定義一個資料夾（例 `agent-bob/`）、設好入口；使用＝在工作區跑它，簡化成 `aos-exec DIR [WS]`，也就是「在 WS 這個資料夾，執行 DIR 這個程式」；程式怎麼處理 cwd、工作區的內容，是它自己的事。（使用者 10-19，ideas § 1、§ 2、§ 5）
- **C-69** **aos 只訂環境變數**：`AOS_ENTRY`（入口）、`AOS_WS`（工作區）、`AOS_STACK`（執行中狀態放哪）。「entry這塊，"這次要做啥"，其實就隨意。因為AOS_ENTRY他是一個可執行檔案，他具體被怎麼使用我們管不著，反正我們就是訂下一些環境變數，就這樣。」aos-exec 只把多的 args、stdin 原樣交給入口。（使用者 10-19，ideas § 4）
- **C-70** **巢狀由程式自己訂子 stack**：「巢狀子程式那塊我們不管，我們就是訂下agent-bob他的stack在AOS_STACK，至於agent-bob他子程式的stack，就由agent-bob自己訂，有可能他會是AOS_STACK/think, /act」。以後會是巢狀嵌入、層層疊疊，act 用的工具可能又是另一個 agent，一層一層。aos 不管巢狀（接 C-52）。（使用者 10-19，ideas § 3、§ 10）
- **C-71** **資料夾的比喻用 lua 的 table，不用 lisp 的 list**：C-68 原話同時用了兩個比喻，頂層問「資料夾到底是 lisp 的 list（有序、看第一個元素）還是 lua 的 table（無序、靠名字）？入口之外的東西算什麼？」，使用者：「那其實還是table。不過老實說，他們的本質都只是"用index+巢狀方式分資料，只是index格式不同"而已。除了入口之外的東西就是其他元素，沒啥好說的。用table來比喻吧。」所以：**本質**＝用 index＋巢狀的方式分資料，list 與 table 只差 index 的格式（位置 vs 名字），資料夾的 index 是名字；**比喻**一律用 table（入口＝metatable 裡定的那個）；**入口之外的東西就是其他元素**，沒有別的身分。C-35、C-39、C-41 與名詞表裡的「list」字眼是舊比喻，意思不變，各處加註。（使用者 10-19，[ideas § 12](../thinking/2026-10-19-ideas.md)）
- **C-72** **JSON＝埋在檔案裡的 table＝單檔的微型檔案系統，入口的尋址方式同樣適用**：頂層問「資料夾入口是 `AOS_ENTRY`，單檔 JSON（`exec.json`／shebang `aos-inst`）的入口是 argv，C-51 說可互通但 JSON 那半沒對應說法」，使用者：「json本質上是埋入檔案中的table，也就是單檔的微型檔案系統，所以也可以套用同樣方式，js[".aos"]["inst"]，也就是entry尋址方式同樣可以套用。」所以 C-51 的互通在入口這件事上也成立：資料夾用路徑 `.aos/exec` 找入口，JSON 用 key 一層層找（`js[".aos"]["inst"]`），同一個「index＋巢狀」（C-71）。這是概念；現在單檔 JSON 的入口是 argv（`aos-inst FILE`、shebang，[CONVENTION P-28](../CONVENTION.md)），在 JSON 裡用 key 尋址入口現無實作。（使用者 10-19 晚，[ideas § 12](../thinking/2026-10-19-ideas.md)）
