# 設計理念

- **C-01** aos 存在的理由是讓大語言模型方便使用；目標多到只能靠模型寫，所以核心要讓模型好用。（2.1）
- **C-02** aos 蓋在現有作業系統上，硬體層的計算分配不重做。（2.5）
- **C-03** 由下往上：Linux → daemon → 時空 → 排程與資源分配 → agent。上層只透過下層。（2.5、2.10）
- **C-04** daemon 完全處理 Linux 那邊的事；它之上的東西不碰 Linux。（2.5）
- **C-07** 體系用的表達方式以模型天生就會的為準（檔案系統、POSIX、JSON），為的是讓它能自省。（2.6、9/23）
- **C-24** 要最佳化的不是時間空間，是金錢、可預測性、人能不能理解。（9/1 ideas 01；2.1 重申）
- **C-45** 比起實作，更重要的是規範。aos 提供一些符合規範、方便的語法糖（例如 tasks、aos-tick），但不要求所有人一定要用。例：aos 時空這個概念衍生出的規範＝大家都要看 tick-tock 時鐘、資料夾別亂弄。（10-12）
- **C-43** 最終效果：一套 library，寫完編譯成基於 aos 的類 LISP 程式，把 aos 當作業系統跑；人和 AI 都要能用。（3g.1、3g.12）
- **C-48** JSON 格式族：沿用 inst 族、ctl／state 窗族，靠加 key 與任意 value 擴充（只處理認得的 key），除非必要不新增格式。兩個通則：**私有 key**——各功能可以在同一份 JSON 放只有自己看得懂的 key，藉此共享同一份格式，前提是 key 不重疊（私有 key 慣例：`_` 開頭的 key＝附註，宿主程式忽略、給別人看，例 `_tool`、`_metainfo`；給人寫的備註固定叫 `_notes`（跟 `_metainfo`＝被叫者自報的特性分開；10-15 使用者「都按照推薦」）；共用同一份檔的私有 key 真的撞名了才加功能前綴，例 `agent_`；各 lib 說明頁列出自己認得的 key）；**值的雙形**——一個值除了字面純值，也可以寫成物件（展開形），像 Lisp 的 `3` 與 `(+ 1 2)`（例：`priority` 寫 `"low"` 或 `{"val", "deadline"}`；展開形的原值固定在 `val`，C-55），實作麻煩就權衡，太麻煩的地方可以不支援物件形。指示詞（`$ref`／`$env`）是這招的一種用法，只是拆檔與讀環境變數的便利，設計不依賴它——設計對它的認知只要「自己的一些檔案可以透過指示詞拆成小檔」就好。（10-15，[原文](../thinking/2026-10-15-json-families.md)）
- **C-51** 資料夾與 JSON 可以互通：資料夾＝object、名字＝key，一份 JSON 本身也是一個小檔案系統，inst 體系以外的格式也能這樣套；「但是我會覺得，建議不要濫用，因為雖然可以互通，但畢竟在細節上有差異」——所以互通只當工具與思考方式，**不進規範**（aos_tree 這支互轉工具 10-15 深夜 KISS 批次 1 刪）。JSON schema 在這套大量用 JSON 的體系裡有更多用處（當型別、interface、簽名，也能描述資料夾的形狀）；驗證選用，執行期先只驗 LLM 回話。隱藏檔一律略過，例外的資料夾名由環境變數 `AOS_DIRNAME` 定（預設 `.aos`，aos_inst 找 inst.json 也照它，N-35）。（10-15 收工後意見 5～7，[thinking 意見 5～7](../thinking/2026-10-15-opinions-5-7.md)）

## 最高原則（10-15 深夜使用者定，[原文](../thinking/2026-10-15-principles.md#10-15-深夜使用者拍板切乾淨kiss)）

- **C-56** **KISS 是最高原則**：「我要的是徹底的純淨簡潔，KISS。把KISS納進最高原則。」接 [proto7 設計原則](../../proto7/notes/principles.md) 第 9 條（核心只做最基礎的保護、錯誤同類走同一分支、很多東西默認正常、誤用不歸組件管）。其他原則都在它底下：下面兩條（C-52 巢狀切乾淨、C-53 錯誤只處理自己的）是它在巢狀與錯誤上的樣子；規範、實作兩難時，選**層最乾淨、規則最少**的那個，不為了方便偷看一層、不為了邊緣狀況加機制。

## 兩條總原則（10-15 使用者定，[原文](../thinking/2026-10-15-principles.md)；10-15 深夜加嚴）

- **C-52** 巢狀：**只管自己這一層，徹底切割、不得有任何殘留**。盡量保持簡單；之後一複雜，巢狀一定常見，所以每一層只管自己，處理上層時下層被乾淨切開、可以不管；真要管時心裡有一把尺——同一個原則在每一層重複、貫穿整個巢狀，只看最上層就能處理。10-15 深夜使用者加嚴：**想看子層的東西要另外透過其他機制，沒機制就別碰**（不偷讀下層的 stderr、不替下層驗它的東西）；**上層不需要、也不該知道下層是什麼**（fsm 不知道某格是不是另一個 fsm，agent 只看到自己的工具清單、不知道工具裡是不是另一個 agent，什麼都不往下傳、不繼承）。已有的例子：fsm 只管「狀態→inst」（C-49、N-36）、格的 stderr fsm 不讀（N-38）、內層 fsm 沒結束就回 `next: null`、外層不必知道它是 fsm（N-37、N-40）、內層 fsm 不繼承外層設定（N-40）、inst 的結果只說子程式（N-30）、暫停與拍數交給拍它的 loop（N-39）、daemon 只靠兩扇窗管子 loop、子項裡面不驗（N-28）、frame 找名字照 `parent` 往上找、綁定只到那一層、agent 不知道工具內部（C-46）、結束碼只說自己這一層（N-43）。
- **C-53** 錯誤：**各單元只處理自己的錯**（接 [proto7 設計原則](../../proto7/notes/principles.md) 第 9、10 條：錯誤分類同類走同一分支、很多東西默認正常、誤用不歸組件管、先定義組件要求什麼與保證什麼）。對別人的錯三種姿態，每個單元在說明裡寫清楚自己採哪種：(a) **入口**——你丟給我的就該是正常的：我不管、默認正常（N-18、N-20、卡死不防護），或我在入口檢查並處理（N-08、N-19、N-29 `InputExtra`）；(b) **出口**——我交出去的保證不出錯（N-05、N-12 半份不算）；(c) **事先列出**可能的錯（N-38、lib 各頁的錯誤代號）。錯誤路徑濃縮成少數幾條（N-43 只 0／非 0、N-29 一種形狀、N-38 出錯一律 phase 不動往外報），減少「出了問題之後的行為」的複雜度。下層的錯**不轉述**（C-52 加嚴）：上層只說「下層結束碼非 0」，下層的錯誤內容留在下層自己寫的地方（stderr 檔、err.json、ret.json）。之後可納入 kernel 評估（[待定](../NORMS/08-待定.md)）。

## 命名（10-15 使用者說，[原文](../thinking/2026-10-15-naming.md)）

- **C-54** 命名：**好懂、快速理解、快速記住**。資料夾布局、程式碼、JSON 格式最好一看就懂七七八八——先排結構，結構與名字本身就是說明；說明只要少量簡介，再直接甩出 pseudo code／JSON／資料夾。
  - **一次記住、全體系通用**：同一個詞在 aos 各處同義（`inst`、`ctl`、`state`…）。縮寫只用大家本來就知道的，而且**新縮寫要先進 [aos 認可縮寫表](abbr.json) 才能用**（10-15 使用者「要，縮寫表照推薦做」；表的欄位：縮寫、全稱、意思、例子）。
  - **難懂才加前後綴**（`ctl_dir`），表特性（`dir`、`path`、單位 `ms`）或子類時用；不用匈牙利命名法那種型別前綴。**可搜尋的標籤／主題放前面、由大到小**（`path_insert`、`path_query_sql`），排序、搜尋時同類排在一起。
  - **資料夾、檔名、JSON key：全小寫加底線**；**對外的指令名＝同一個名字把底線換成連字號**（`node_path` ⇄ `node-path`，同 N-22 的 key ⇄ 旗標）；環境變數全大寫加底線（`AOS_DIRNAME`）（10-15 使用者「指令名就是底線換連字號。」）。
  - **程式碼照該語言規範**（Python 照 PEP8），並跟檔名固定對上：程式的 `NodePath` ⇄ 檔名 `node_path`；程式裡可混大小寫表層級（`NodePath_SQL_Query`）。
  - **靠資料夾布局少用底線，複數資料夾裝同類**：裝同一類多個東西的資料夾用複數名（`insts/`、`cells/`、`tools/`），裡面的檔名不再重複類別（`insts/a.json`，不寫 `inst_a.json`、`insts/inst_a.json`）。複數一律只加 `s`（縮寫也是：`insts`、`cfgs`、`msgs`），不用不規則變化；本身已是複數或不可數的照原樣（`args`、`data`、`history`）；單一檔案用單數（`brain.json`、`ret.json`）（10-15 使用者「對了，還有複數形式，比如./inst-a.json, ./insts/a.json」，細節「都按照推薦」）。
  - **錯誤代號（N-29 的 `code`）照 CamelCase、主詞在前**：`ArgumentsBad`、`FlagUnknown`、`ApiKeyMissing`、`StateBad`，同主題的錯排在一起；「沒有某物」一律 `…Missing`、「不認得」一律 `…Unknown`、「壞了／不合」一律 `…Bad`（10-15 晚使用者「都按照推薦」，盤點 P7，舊的 `BadArguments`、`UnknownFlag`、`NoApiKey`… 已全改）。
  - **例外**（10-15 盤點後定，使用者「其他直接改」）：入口檔照 Unix 老慣例全大寫（`README.md`、`INDEX.md`、`CONCEPTS.md`、`NORMS.md`，`ls` 時排前面）；`lib/`、`bin/` 是 Unix 慣例名、單數照留；工具自己的慣例照工具（pytest 的 `tests/test_*.py`）；外部 API 的參數名照原名、不進縮寫表（`num_ctx`、`keep_alive`）；一個檔裝很多筆的串流／日誌檔可以用複數（`steps.jsonl`）。proto8 的 `demo/` 照留單數（原型期連結太多、收益低；下一個 proto 起用 `demos/`；10-15 晚使用者「都按照推薦」，盤點 P5）。`last_`／`max_` 這種修飾詞在前不算違反「主題在前」——`last_` 本身就是一個可搜尋的群組（state 窗裡「上一次的」排在一起），`max_` 是大家都知道的慣例。
  - 現況不合的地方（23 條）10-15 晚使用者「都按照推薦」，已全照推薦改完，見 [thinking 命名 § 盤點](../thinking/2026-10-15-naming/盤點.md)。

## 布局成長（10-15 使用者說，[原文](../thinking/2026-10-15-layout-growth.md)）

- **C-55** 布局成長：資料夾／檔案與 JSON 物件有同像性（C-51），所以**長大的規則同一套**。檔案那邊照 [wf/STRUCTURE.md](../../wf/STRUCTURE.md)（唯一出處）：一個檔內容太大、或一個檔扛不了那麼多職責，就變成資料夾，原檔變成入口（index＋readme），資料夾裡再照既有路徑長（index、readme 各自獨立出來）。JSON 那邊照同一套：一個純值不夠用（例 `priority: 3`），就長成物件（`priority: {"val": 1, "type": "normal task", "_notes": "haha", "timeout": 0}`）——key 不變，原本那個純值放進物件裡固定的一格，其他屬性當同層的 key，`_` 開頭的附註照 C-48，物件裡每個值再照同一套長；只剩原值那一格就縮回純值。這就是 C-48「值的雙形」的成長方向，讀的人兩形都收（純值＝只給了原值那一格）。**原值那一格一律叫 `val`**（ctl 的 `paused`／`stop`、`priority`、fsm 的格都是；程式讀值一律先 `aos_cli.expand(v)` 收成物件再看自己認得的 key；10-15 使用者「都按照推薦」，選 A）。兩邊怎麼對見 [thinking 布局成長](../thinking/2026-10-15-layout-growth.md)。
