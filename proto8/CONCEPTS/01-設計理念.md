# 設計理念

- **C-01** aos 存在的理由是讓大語言模型方便使用；目標多到只能靠模型寫，所以核心要讓模型好用。（2.1）
- **C-02** aos 蓋在現有作業系統上，硬體層的計算分配不重做。（2.5）
- **C-03** 由下往上：Linux → daemon → 時空 → 排程與資源分配 → agent。上層只透過下層。（2.5、2.10）
- **C-04** daemon 完全處理 Linux 那邊的事；它之上的東西不碰 Linux。（2.5）
- **C-07** 體系用的表達方式以模型天生就會的為準（檔案系統、POSIX、JSON），為的是讓它能自省。（2.6、9/23）
- **C-24** 要最佳化的不是時間空間，是金錢、可預測性、人能不能理解。（9/1 ideas 01；2.1 重申）
- **C-45** 比起實作，更重要的是規範。aos 提供一些符合規範、方便的語法糖（例如 tasks、aos-tick），但不要求所有人一定要用。例：aos 時空這個概念衍生出的規範＝大家都要看 tick-tock 時鐘、資料夾別亂弄。（10-12）
- **C-43** 最終效果：一套 library，寫完編譯成基於 aos 的類 LISP 程式，把 aos 當作業系統跑；人和 AI 都要能用。（3g.1、3g.12）
- **C-48** JSON 格式族：沿用 inst 族、ctl／state 窗族，靠加 key 與任意 value 擴充（只處理認得的 key），除非必要不新增格式。兩個通則：**私有 key**——各功能可以在同一份 JSON 放只有自己看得懂的 key，藉此共享同一份格式，前提是 key 不重疊（私有 key 慣例：`_` 開頭的 key＝附註，宿主程式忽略、給別人看，例 `_tool`、`_metainfo`；共用同一份檔的私有 key 真的撞名了才加功能前綴，例 `agent_`；各 lib 說明頁列出自己認得的 key）；**值的雙形**——一個值除了字面純值，也可以寫成物件（展開形），像 Lisp 的 `3` 與 `(+ 1 2)`（例：`priority` 寫 `"low"` 或 `{"level", "deadline"}`），實作麻煩就權衡，太麻煩的地方可以不支援物件形。指示詞（`$ref`／`$env`）是這招的一種用法，只是拆檔與讀環境變數的便利，設計不依賴它——設計對它的認知只要「自己的一些檔案可以透過指示詞拆成小檔」就好。（10-15，[原文](../thinking/2026-10-15-json-families.md)）
- **C-51** 資料夾與 JSON 可以互通：資料夾＝object、名字＝key，一份 JSON 本身也是一個小檔案系統，inst 體系以外的格式也能這樣套；「但是我會覺得，建議不要濫用，因為雖然可以互通，但畢竟在細節上有差異」——所以互通只當工具與思考方式，**不進規範**（同 aos_tree）。JSON schema 在這套大量用 JSON 的體系裡有更多用處（當型別、interface、簽名，也能描述資料夾的形狀）；驗證選用，執行期先只驗 LLM 回話。隱藏檔一律略過，例外的資料夾名由環境變數 `AOS_DIRNAME` 定（預設 `.aos`，aos_inst 找 inst.json 也照它，N-35）。（10-15 收工後意見 5～7，[thinking 意見 5～7](../thinking/2026-10-15-opinions-5-7.md)）
