# C-54 命名方法（R1～R12，10-23 晚）

**來源**：使用者 10-23 晚提的方法（「關於命名規則這塊，我想嘗試一些新的概念，在現有的原則與規則上添加一些能讓人更快看懂的...算小技巧吧」，全文見 [thinking](../../thinking/2026-10-23-naming-method.md#使用者原文整理版)），「先試試看，不要急着寫進去」；問「這種命名規則，那些unix年代的老人，或是linux的開發者，有慣例嗎」→「好，幫我去查，順便再幫我弄一套，結合了這些的新命名規則」；八題選完後「寫進去吧」。

骨幹是使用者的六步：**一句話說程式做什麼 → 要加功能先一句話說那個功能 → 替檔／主題取名 → 列格子、每格一句白話 → 從白話挑字造名 → 簡化**。下面 12 條是這六步加上 Unix／Linux 老慣例。C-54 原有的規則（一詞一義、縮寫表、主題在前、小寫底線、複數只加 s、錯誤代號四種、例外）照舊，這裡不重寫，只標出它們在哪一步用。

1. **R1 先寫一行 NAME：`名字 - 一句話`**。每支程式、每份檔、每扇窗，動手前先寫「它做什麼」一句話（使用者：「我在寫程式的時候，會先用簡短的介紹描述自己要做的東西，比如aos-loop，我會這樣說：以指定設定，定期執行某個aos-exec目標」）。格式照 man page 第一行：名字、空格、連字號、空格、一句話；英文小寫開頭、不加句號。放檔頭或 README 第一行；之後所有名字都要能從這行推回來。要加功能也一樣：先一句話說那個功能，再照句子加 key（C-48）（使用者：「然後我會給這些額外的功能添加更多說明……然後就按照這句話開始實作」）。
   例：`aos-loop - 以指定設定，定期執行一個 aos-exec 目標`、`state.json - loop 自己回報的現況，每跑一次寫一次`
2. **R2 每一格一句白話，先不想名字**（使用者：「把這些資訊寫出來後，在去將其命名」）。例：「跑到第幾次」「最多跑幾次」「兩次之間隔多久」「ctl 窗最近一次讀到壞的，原因是什麼」。
3. **R3 先查固定格，有就直接用**：原值 `val`（C-55）、這筆紀錄的時間 `at`、上限 `max`、種類 `kind`、結束碼 `code`、訊號 `signal`、流水號 `seq`、階段 `phase`、行程號 `pid`。這一步在挑字之前。`val` 只給「值的展開形」裡原值那一格（C-55）；**具名欄位不是展開形，照白話取名**——「要跑什麼」全體系一律叫 `exec`（loop.json、daemon.json 與子項、fsm 的每一格；`exec`＝交給 aos-exec 跑的目標），不叫 `val`〔10-23 晚使用者：「val寫要跑啥，通常不會用val，應該用run。」，loop／daemon 先改回 `run`、fsm 的格維持 `val`；10-23 深夜使用者「fsm.json，現在是用val，幫我改成exec」，頂層指出跟 `run` 不同名違反 R4 一詞一義，使用者選「exec，loop／daemon 的 run 也一起改 exec」〕。
4. **R4 主題字從白話的主詞來，全體系一詞一義；巢狀已經說了的，不再重複**。一句白話的主詞就是主題字（「ctl 窗讀到壞的」→ `ctl`）；同一個詞在 aos 各處只一個意思（C-54「一次記住、全體系通用」：`state` 是窗，所以窗裡的「現在在幹嘛」叫 `phase`）；外層已經說了的主題，裡層不重複（`loops.bob.pid`，不寫 `loop_pid`）。ctl 是宣告（N-06），key 一律用狀態詞；state 裡有對應的格時，用同一個字：`paused`、`stopped`（10-23 晚使用者選「改成 stopped」，原 `stop`）〔10-23 頂層代定（使用者「都隨意」）：原寫「key 用狀態詞、跟 state 回的同字」，放寬成這樣，因為 daemon ctl 的 `loops_added`／`loops_removed`（N-54）在 state 裡沒有同名的格〕。
5. **R5 縮寫只用縮寫表；新縮寫進表的門檻是「一眼還原得了」**（使用者：「也要看他是否有簡寫(容易認，少寫幾個字母)」）：要嘛是 Unix／POSIX 老慣例大家本來就認得（`pid`、`cwd`、`argv`、`ms`、`tmp`），要嘛看一眼就還原得了全字（`ctl`、`cfg`、`seq`）；「刪母音」式、光看還原不了的不收（`crt`、`umnt`）。**表上已有的不追溯**：`AOS_CF`／`AOS_CD`／`AOS_CO` 留著（10-23 晚使用者選「留著」）。門檻也寫在 [abbr.json](../abbr.json) 的 `note`。
6. **R6 修飾成分照表貼**：

   | 白話裡出現 | 貼什麼 | 例 |
   |---|---|---|
   | 最多、上限 | `max`（單獨，或前綴 `max_`） | `max`、`max_runs` |
   | 幾個（計數） | **前綴 `counter_`＋被數的東西**：`counter_<被數的東西>`（10-25 使用者「計數這塊，幫我改成counter_*」；原為「被數的東西加 s」）；**不用 `nr_`**（使用者：「nr_這東西還是建議不要用，現在這東西不太常見了」）；撞名時照 R9「撞名就換角度」，得到的名字不一定是「`counter_` 加名詞」（原寫「名詞加 s」）。只管「次數、個數」：一串東西本身（陣列、清單，例 `steps`、`tools`）照「複數只加 s」，不加 `counter_`；上限（`max`／`max_`）、時長（單位當後綴）、第幾個（`seq`、`idx`）照各自那一列〔10-25 頂層代定〕 | `counter_runs`（loop 跑過幾次）〔原 `runs`（10-23 晚改，原 `beats`，使用者「beats改runs」）；10-25 使用者 10-25「state.json中，runs改counter，at改成recorded_at」：loop／daemon 的 state.json 這兩格改叫 `counter`（跑過幾次）、`recorded_at`（這份 state 的時間），跟本列當時的規則不同；同日使用者「計數這塊，幫我改成counter_*」，計數規則改成本列，state.json 那格改叫 `counter_runs`，其他 JSON 的計數也照改（例 kernel-llm 的 `counter_tokens`、信的 `counter_hops`）〕 |
   | 多久、單位 | 單位當後綴 | `interval_ms`、`elapsed_ms` |
   | 啥時候（這筆紀錄） | 單獨 `at`，值 ISO 8601 UTC 到毫秒（10-23 晚使用者選「留 ISO」） | `at`〔10-25 使用者 10-25「state.json中，runs改counter，at改成recorded_at」：loop／daemon 的 state.json 這兩格改叫 `counter`（跑過幾次）、`recorded_at`（這份 state 的時間），跟本列的規則不同；規則本身沒改（trace 等其他紀錄的時間仍叫 `at`），要不要跟著改規則等使用者定〕〔10-25 同日：計數那半使用者定了（「計數這塊，幫我改成counter_*」，見上面「幾個」那列，state.json 那格現叫 `counter_runs`）；時間這半還等使用者定〕 |
   | 啥時候（某件事） | `<事件>_at`，值同上（10-23 晚使用者選「補」） | `started_at` |
   | 某件事的時間點、用別的單位記 | `<事件>_at_<單位>`（使用者：「後面接參照與單位(兩者可以合一)：started_at_ticks」；10-23 晚選「改成 started_at_ticks」） | `started_at_ticks` |
   | 上一次 | 前綴 `last_` | （現在沒有這種格；「上一次的結果」`last_code` 10-23 晚使用者選「先不加」） |
   | 在一排裡第幾個 | 不進縮寫表；真要用時寫 `idx`（使用者原本提 `_i`：「這可能不太好，要再想想」；10-23 晚選「`_i` 不進表，真要用時用 `idx`」） | — |

7. **R7 排字序：主題在前、由大到小，單位一律在最後**（C-54「可搜尋的標籤／主題放前面」）。同主題的 key 排在一起（`ctl_seq`、`ctl_warning`）；`max_`、`last_` 這種修飾詞在前是 C-54 已寫的例外〔10-25：計數的 `counter_` 同理（使用者「計數這塊，幫我改成counter_*」）〕。
8. **R8 名字的長度跟「要被認多遠」成正比**（使用者第 6 步「簡化後仍唯一」的道理；老慣例 Pike、kernel、Go 同）。從遠到近四層，越遠越長：
   1. 環境變數：全系統都看得到 → 全大寫、帶 `AOS_` 前綴（`AOS_STACK`）
   2. 程式名：整台機器的 PATH → 帶 `aos-` 前綴（`aos-loop`）
   3. 檔名、JSON key：只在這份檔裡要唯一 → 可以短到 `max`、`code`、`at`
   4. 程式內部的區域變數：照該語言慣例（C-54「程式碼照該語言規範」），`i`、`tmp` 就好
9. **R9 簡化：能省就省，條件是省完在同檔、同主題裡仍然獨一無二**（使用者：「簡短的原則是簡短後，不要與同檔案，或是同主題下的概念產生關聯，也就是簡短後也仍然保有獨特性，比如last_*，也就是"上次"，在現有的程式功能描述中，能夠配的上這個詞的，也只有"上次exec"」）。同檔只有一個上限 → `max`；只有一個結束碼 → `code`；同檔出現第二個同類的格，省掉的主題字就補回來（`max_runs`、`max_loops`）。所以 `last_` 只留給「上一次」，ctl 讀到壞檔的原因叫 `ctl_warning`（10-23 晚改名，原 `last_warning`）。
   **撞名就換角度**（使用者 10-23 晚：「像這種命名重複的，可以用另一個角度用白話描述其功能與特性」）：照前面幾步推出來的名字，如果跟同一個檔或同一個主題裡的名字撞了，不硬加前後綴，而是換一個角度，用白話重新描述它的功能與特性，再從那句白話取名（回到 R2）。得到的名字不一定合 R6 的固定貼法。
   例（**假設**，現在沒有這一格）：fsm 的 trace 若要記「這一格是這次 fsm 跑起來後的第幾格」，照 R6「被數的東西加 s」會得到 `states`，跟 fsm.json 的 `states`（狀態表）在同一個主題裡撞了；換個角度說成「從起跑到現在走了幾步」，就叫 `steps`。〔10-25 註：計數改 `counter_<被數的東西>` 後（使用者「計數這塊，幫我改成counter_*」），這一格照 R6 會得到 `counter_states`、不再跟 `states` 撞；例子只留著示範「換角度」怎麼做〕
10. **R10 形式照已定的**：C-54 上面那幾點——小寫底線、指令名換連字號、環境變數全大寫、副檔名三種（`.json`、`.jsonl`、`.txt`）、複數只加 s、錯誤代號四種（`…Missing`／`…Unknown`／`…Bad`／`…Failed`），另加 `Internal`（照理不會發生的錯）。
11. **R11 不用型別前綴；`_` 開頭不表「私有」**：C-54 原有「不用匈牙利命名法那種型別前綴」。10-23 晚已刪「`_` 開頭＝附註」（C-48）；**`_` 開頭的檔＝入口**（`_entry`，`ls` 時排前面、不跟使用者的檔撞），不是私有（10-23 晚使用者選「留 `_entry`，C-54 補一句」）。入口不叫 `_exec`（10-23 晚改名）也讓 `exec` 一字一義：**`exec`＝交給 aos-exec 跑的目標**（loop／daemon／fsm 那一格，R3），`_entry`＝aos-exec 進了資料夾之後跑的那個檔。
12. **R12 最後回頭清：每個名字要能從 R1 那一句推回來**（C-56 KISS 是最後一步的減法）。推不回來的，要嘛名字取錯，要嘛那一句話寫漏了功能——補 R1 的句子，不是硬記名字。多出來的修飾詞照 R9 清掉。
