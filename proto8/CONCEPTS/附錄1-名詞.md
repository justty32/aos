## 1. 名詞

| 詞 | 使用者的意思 | 出處 |
|---|---|---|
| aos | 蓋在 Linux 上、為「任意目標」最佳化、要讓大語言模型方便用的作業系統 | 2.1、2.5 |
| 目標 | 排程要最佳化的東西；AI 時代目標變多（可用性、人類可理解性……）而且任意 | 2.1、2.4 |
| 計算任務 | 一個照 POSIX 方式被叫起來的行程，不是 thread | 2.7 |
| 資源 | 處理計算任務時會用到、而且有限的東西；它自己也當行程看 | 2.7、2.8 |
| 格 | 資源的「有限」用幾個數來講：一個資源有幾格 | 3b |
| 排序演算法 | 決定哪個任務先給哪個資源處理；它自己也是計算任務 | 2.7、2.8 |
| 排程／資源分配 | 把任務分給擅長它的資源，有限時排優先級；使用者把這兩詞和「排序」幾乎互換用 | 2.2、2.3 |
| 優先級 | 有限資源下「誰先」的那個先後 | 2.2 |
| 空間 | 東西存在的地方＝資料夾體系；**就是存放狀態的地方**；資料庫、硬碟、快取、記憶體、雲端這類外部設備也可以納入空間（像 Plan 9） | 2.5、9/24、3d、3h |
| 時間／tick | 取得下一個時間點的狀態；tick 之間所有對外狀態一致（使用者叫這「時空法則」） | 2.5、9/24 |
| tick-tock | 讓時間停下來的機制；正常結束時 agent 看到的資料夾就是那個時間點的狀況；可以打包 | 2.11 |
| 變換 | 符合 POSIX 的呼叫（和 tick、空間並列的第三樣） | 9/24 |
| daemon | aos 與 Linux 之間的借階層；Linux 那邊的事（許可權、身份、記憶體、硬碟、行程）全在這層；有了它 aos 就有了「硬體」 | 2.5 |
| kernel | 管理正在跑的程式、分配 cpu、粗放式（Linux 是細粒度）、要讓 agent 能自省的那一層 | 9/19、9/23 |
| cpu（使用者的用法） | kernel 開來跑某個資料夾的一個執行單位；畫家也是一顆 cpu | 9/23、2.3 |
| 核心 | 到「排序程式可由模型生成」為止這一整塊；在它之上才是 agent | 2.10 |
| agent | 一個狀態機（想→做→循環）、一個函式、一個複合型計算任務 | 2.13、2.14、2.18 |
| 函式／黑箱 | 給東西、跑一跑、停下來；strcpy 和 LLM agent 對我們都是黑箱，差在使用方式與計算特性 | 2.14、9/19 |
| 腦 | agent 裡負責思考的大語言模型 | 2.17 |
| 核心人格 | system prompt | 2.17 |
| 近期記憶 | 一般上下文 | 2.17 |
| 手腳 | agent 可用的工具 | 2.17 |
| 九軸 | 每個計算任務固有的計算性特性：副作用、冪等、碰外部檔案、持續性、有無 entry、確定性…… | 2.9 |
| 附加特性 | 九軸之外、人隨意加的特性（例：「繪畫上偏現代」）；會多到只能靠模型處理 | 2.9 |
| 確定性 | 任務自己的屬性：有沒有機率問題；跑 LLM 的任務不確定 | 2.9、2.14 |
| 可預測性 | 觀察者對任務的認識，有主體性（對誰可預測）；確定性高不等於可預測 | 2.14、2.15 |
| S 表示式／節點 | 把流程看成一棵樹，有些節點我們知道、有些不知道；呼叫模型的節點是不知道的那種 | 2.16 |
| list／eval | 檔案系統看成 list；eval＝求某關卡之後的狀態，list 自己就是被跑的程式，其餘是環境 | 9/19 |
| 生成排序程式的程式 | 叫大語言模型幫忙定義資源、寫排序的那個程式 | 2.10 |
| 快取／靈感 | 資源手邊現成的東西；沒有就要去找，找的時間算進處理時間 | 2.3 |
| PU（處理單元） | 會「算」的東西：普通 CPU 跑一般任務；畫師、GPU、NPU 是另一種 PU，屬外部設備——工作丟給它、它用自己的方式算、算完收回 | 3d |
| 求值 | 放開讓它算，過一段時間看它狀態變化的結果；求值＝空間狀態的變化。對資料夾求值＝執行這個資料夾（inst） | 3h、3f.1 |
| 外部設備 | 系統外面但能掛進來用的東西：PU（畫師、GPU、NPU）與儲存（資料庫、硬碟、快取、記憶體、雲端） | 3d |
| 間接抽象化 | 沒法直接變成 POSIX 呼叫的事（人手畫），拆成幾個 POSIX 任務包起來：寄信給畫家、收信、畫歸檔 | 3c |
| inst（aos inst） | 指定一個檔案就去做對應的 POSIX 呼叫；指定一個資料夾就找裡面的 inst JSON 來跑＝對資料夾求值。吃 JSON、固定幾個 key、不認識的略過（但 JSON 裡可以多放九軸、traits、資源標籤、優先順序標籤、工具等有的沒的）；照指示庫組好再跑 | 3f.1、3g.2、3g.13b |
| loop（aos loop） | 讓 inst 持續執行（每隔幾秒一次）；實作上是一個 library，整個進 daemon | 3f.2、3g.3 |
| node（節點） | loop 所服務的那個資料夾；時間＋task 結合起來才是好的 node | 3f.2、3f.5 |
| daemon | 統一管理所有 loop：哪個資料夾歸誰管（排他）、監控；Linux 許可權全在它身上；可以吃一點控制；可牽動另一個 daemon；正式只承諾跑資料夾；本體非常短 | 3f.2、3g.3、3g.4 |
| task（aos task） | 一個 inst 裝不下多個任務，所以用 task JSON 裝一包；跑在 daemon 上的 argv 中介程式 | 3f.4 |
| kernel（核心） | 第三層；一個任務包，偏定義與概念，落成協議和格式；參照物是 tick-tock（時間）與資料夾（空間）；只是一個排程；切在 task 與 tick-tock 之上，不碰 loop 的下一個 inst | 3f.6、3g.6、3g.7 |
| 標頭檔 | 一個已經設好的資料夾（例如一個 agent：skills、memory、工具放好）；引用它＝用那個資料夾，不複製，跑起來時執行環境在引用者這邊；工具對 agent 而言也是標頭檔 | 3g.10、3g.12 |
| binding（繫結） | library／程式語言做的事：把 agent 那條很長的 list 裡固定的元素綁死，用時只填幾個引數 | 3g.9 |
| 工具 | agent 函式的引數之一；對 agent 來說就是被引用的標頭檔，內部怎麼跑不用懂；agent 也可以是工具；aos 體系的每個指令都是工具 | 3g.12、3g.13 |
