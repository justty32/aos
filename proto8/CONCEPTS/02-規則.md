## 2. 規則（使用者說「一定是這樣」的）

- **C-01** aos 存在的理由是讓大語言模型方便使用；目標多到只能靠模型寫，所以核心要讓模型好用。（2.1）
- **C-02** aos 蓋在現有作業系統上，硬體層的計算分配不重做。（2.5）
- **C-03** 由下往上：Linux → daemon → 時空 → 排程與資源分配 → agent。上層只透過下層。（2.5、2.10）
- **C-04** daemon 完全處理 Linux 那邊的事；它之上的東西不碰 Linux。（2.5）
- **C-05** 空間就是資料夾，時間就是 tick；這一塊已定，不再討論。（2.5、2.12）
- **C-06** tick 之間，所有與外部有關的狀態一致。（9/24）
- **C-07** 體系用的表達方式以模型天生就會的為準（檔案系統、POSIX、JSON），為的是讓它能自省。（2.6、9/23）
- **C-08** 計算任務＝一個 POSIX 行程，不是 thread；不必再往下分種類。（2.7）
- **C-09** 任務處理過程中用到的東西，只要有限，就是資源。（2.7）
- **C-10** 資源的有限用格數表示。（3b）
- **C-11** 排序演算法＝決定哪個任務先給哪個資源；就這樣，不多說。（2.7）
- **C-12** 排序與資源分配本身是計算任務；資源本身也當行程看——一切都是計算任務，核心沒有第二種東西。（2.8）
- **C-13** 每個計算任務都有固定的基礎特性（九軸）；其中確定性是任務自己的屬性。（2.9）
- **C-14** 基礎特性之外，人可以任意附加特性。（2.9）
- **C-15** 排序程式可以由人寫，也可以由「生成排序程式的程式」叫模型寫。（2.10）
- **C-16** tick-tock 的本質是定義時間、讓時間能停；停下來後 agent 看到的就是那個時間點的空間，可直接打包。（2.11）**10-12 改了，見 C-44**：tick-tock 就是時鐘、不保證什麼；打包是規範、由 kernel 做。
- **C-17** 停下來時正在跑的任務可以不被迫停止；那個時間點的空間裡可以含「這件事正在跑」。（2.11）
- **C-18** agent 是狀態機、是函式、也是計算任務；直接接進核心，不特別處理。（2.13、2.14）
- **C-19** agent 的簽名＝腦（模型）＋記憶（核心人格、近期記憶）＋手腳（工具）。（2.17）
- **C-20** agent 是複合型任務（外迴圈便宜、叫的模型與工具貴），所以要被排程；最核心的一題是「很多 agent 時誰先用腦」。（2.18、2.19）
- **C-21** 可預測性有主體性，不是任務的屬性，是觀察者的認識。（2.14、2.15）
- **C-22** 提高 agent 可預測性的方法：當 S 表示式拆開，能寫死的節點換成程式，降低走進不可預測節點的機率。（2.16）
- **C-22b** 可預測性不只是函式本身的：同一函式在不同狀況、不同（例如老舊）硬體上跑，可預測性不一樣。節點＝函式內部＋它所在的執行環境，合起來才是執行節點。（3g.13c）
- **C-23** agent 內部怎麼設計是後面的事，先把底打好。（2.20）
- **C-24** 要最佳化的不是時間空間，是金錢、可預測性、人能不能理解。（9/1 ideas 01；2.1 重申）
- **C-25** 大操作（問模型、跑久的工具）丟到另一個資料夾讓另一個行程處理；agent 自己每次 eval 短促。（9/19）
- **C-26** 沒輸入就每 tick 沒事。（9/23）
- **C-27** tock 的時機（任務都結束就提前 vs 固定間隔）應該是可選的。（10-04 user-advice）
- **C-28** 沒法直接轉成 POSIX 呼叫的事（人手畫），用**間接抽象化**變成計算任務：拆成多個 POSIX 任務（寄信給畫家、收信、畫歸檔），人在這幾個任務之間、在系統外面做事。（3c）
- **C-29** 處理單元分兩種：普通 CPU（跑寄信、收信這類一般任務）；外部 PU（畫師、GPU、NPU）——跟外部設備的概念靠攏。（3d）
- **C-30** 空間的定義可以擴到外部設備：資料庫、硬碟、快取、記憶體、雲端都能納入空間，像 Plan 9。（3d）
- **C-31** 行程本身也是掛在空間裡的一個東西。資源、設備、PU、行程，全是空間裡掛著的節點。（3e）
- **C-32** 空間就是存放狀態的地方。（3h）
- **C-33** 處理單元／處理（process）＝過一段時間後造成的變化，變化指的是空間上的變化。（3h）
- **C-34** 求值＝放開讓它算、過一段時間看狀態變化的結果；求值的定義就是空間狀態的變化。對資料夾求值＝執行這個資料夾；求值還回來的是一個正在變動的資料夾，不是一個值。（3h、3f.1、3f.3）
- **C-35** Linux 檔案系統就是一個 LISP；資料夾＝list，list 裡有 list。（3f.1、9/19）

以下來自 10-11 晚的實作口述（§3g），使用者講得像定了的，所以也列進規則；要改隨時改：

- **C-36** 層層遞進：inst（求值一次）→ loop（持續求值）→ node（loop 服務的資料夾）→ daemon（統管 loop）；daemon 跑的 inst 可以是另一個 daemon。（3f.2）10-12 夜落實：inst＝`aos_inst.py x.json` 跑一次；loop＝`aos_loop.py x.json` 包一個 inst、跑 times 次後退出，用一個 ctl.json 控制（N-06～N-08）；daemon＝`aos_daemon.py x.json`，表上每個 loop 是子程序、用控制資料夾下指令（N-10），自己也是一個 loop。
- **C-37** 時空固定：空間照 Plan 9；時間是 tick-tock，一個可看可不看的時鐘；要先有時間後面才不會亂。tick-tock 可以跟 node 的狀態變化完全脫鉤，node 要看就訂閱。（3f.5、3g.5）
- **C-38** 第三層（kernel）的參照物就是時間（tick-tock）與空間（資料夾）：「三回合內搞定」「只動這三個資料夾」「每檔不超過幾 KB」。它只是一個排程；PU 怎麼收任務請求各資料夾各做各的。（3g.6）
- **C-39** agent 是一個資料夾、一個 node、一條很長的 list（模型、context、工具、記憶……各占一個元素），持續被求值。最普通的 agent＝狀態機，在等待、思考、行動之間切換，需要思考就丟 LLM。（3f.7、3g.8、3g.9）
- **C-40** agent 要能當拋棄式函式用：引用一個設好的資料夾（標頭檔）、填幾個引數、讓它跑起來，執行環境在引用者這邊。library 做 binding 讓這件事簡單。（3g.9、3g.10）
- **C-41** 巢狀：list 的元素也是 list，求值時先對元素求值（畫家裡的畫筆 agent 先算）。（3g.11）
- **C-42** 工具＝被引用的標頭檔；agent 也可以是工具；aos 體系的每一樣（daemon、tick、task、inst、kernel）都基於 inst、都是 shell 指令，所以都是 agent 的工具——自我迴圈改進的閉環。（3g.12、3g.13）
- **C-42b** inst 的 JSON 裡可以多放東西：九軸特性、traits、資源標籤、優先順序標籤、工具……inst 不認的別人可以讀。工具用 JSON schema 限制引數；schema 怎麼轉成 argv——走 schema→argv 這條路，或先定義一些通用的東西，沒定。（3g.13b）10-13：這個抽屜定名 `_metainfo`，見 [thinking 10-13 §3](../thinking/2026-10-13-json-path.md)。
- **C-44** tick-tock 就是一個時鐘（「甲」）：不包任務、不保證什麼；「tick 之間可以安全打包」是後續大家要遵守的規範，不強制；打包這塊在後續 kernel 那邊做。（10-12）
- **C-45** 比起實作，更重要的是規範。aos 提供一些符合規範、方便的語法糖（例如 tasks、aos-tick），但不要求所有人一定要用。例：aos 時空這個概念衍生出的規範＝大家都要看 tick-tock 時鐘、資料夾別亂弄。（10-12）
- **C-43** 最終效果：一套 library，寫完編譯成基於 aos 的類 LISP 程式，把 aos 當作業系統跑；人和 AI 都要能用。（3g.1、3g.12）
