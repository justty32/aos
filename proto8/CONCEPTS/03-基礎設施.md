# 基礎設施

子主題：inst、loop、daemon、窗、命令列、指示詞與路徑、組合子（tasks、fsm）、定義與工作區（食譜與廚房，10-16）。窗、命令列、指示詞與路徑沒有專屬的概念條，只有規範（見上）。

## inst

實作：[lib inst.md](../lib/inst.md)。C-36 的層層遞進從 inst 起，條文放在下面 loop 與 daemon。

- **C-08** 計算任務＝一個 POSIX 行程，不是 thread；不必再往下分種類。（2.7）
- **C-34** 求值＝放開讓它算、過一段時間看狀態變化的結果；求值的定義就是空間狀態的變化。對資料夾求值＝執行這個資料夾；求值還回來的是一個正在變動的資料夾，不是一個值。（3h、3f.1、3f.3）
- **C-42b** inst 的 JSON 裡可以多放東西：九軸特性、traits、資源標籤、優先順序標籤、工具……inst 不認的別人可以讀。工具用 JSON schema 限制引數；schema 怎麼轉成 argv——走 schema→argv 這條路，或先定義一些通用的東西，沒定。（3g.13b）10-13：這個抽屜定名 `_metainfo`，見 [thinking 10-13 §3](../thinking/2026-10-13-json-path.md)。

## loop 與 daemon

實作：[lib loop.md](../lib/loop.md)、[lib daemon.md](../lib/daemon.md)。

> **daemon 兩義**：①[C-04](01-設計理念.md) 說的 daemon＝aos 與 Linux 之間的借階層（Linux 那邊的事全在這層）；②這裡的 daemon＝管一群 loop 的程式（`aos-daemon`，C-36）。[名詞表](附錄1-名詞.md)兩列都留。

- **C-36** 層層遞進：inst（求值一次）→ loop（持續求值）→ node（loop 服務的資料夾）→ daemon（統管 loop）；daemon 跑的 inst 可以是另一個 daemon。（3f.2）10-12 夜落實：inst＝`aos_inst.py x.json` 跑一次；loop＝`aos_loop.py x.json` 包一個 inst、跑 times 次後退出，用一個 ctl.json 控制（N-06～N-08）；daemon＝`aos_daemon.py x.json`，表上每個 loop 是子程序、用控制資料夾下指令（N-10），自己也是一個 loop。**10-16 改**：控制資料夾（N-10）整套刪，daemon 表上有誰改由它 ctl 的 `children` 宣告（[N-54](../NORMS/04-基礎設施-loop與daemon.md)，使用者「不留」，實作待改）。

## tasks 組合子

實作：[lib README](../lib/README.md)（`aos seq`／`par`／`if`；10-15 深夜從 proto8-1 併進 proto8/lib，aos-not 刪）。使用者 10-15：tasks 組合子「**地位等同於 C 語言的 stdlib**」。

- **C-41** 巢狀：list 的元素也是 list，求值時先對元素求值（畫家裡的畫筆 agent 先算）。（3g.11）

## fsm

使用者 10-15：「把 fsm 也跟 tasks 放一起」——fsm 是組合子、同為 stdlib 地位；[agent](05-agent.md) 是用 fsm 組出來的（一個定義資料夾，C-50）。規範：[NORMS 組合子 § fsm](../NORMS/07-基礎設施-組合子.md#fsm)（N-20、N-36～N-41）；實作：[lib fsm.md](../lib/fsm.md)（10-15 基礎實作）。

- **C-18** agent 是狀態機、是函式、也是計算任務；直接接進核心，不特別處理。（2.13、2.14）
- **C-25** 大操作（問模型、跑久的工具）丟到另一個資料夾讓另一個行程處理；agent 自己每次 eval 短促。（9/19）10-16：aos 的 agent 每次被叫只走一拍、由外面的 loop 驅動（C-62、[N-53](../NORMS/10-基礎設施-定義與工作區.md)）。
- **C-39** agent 是一個資料夾、一個 node、一條很長的 list（模型、context、工具、記憶……各占一個元素），持續被求值。最普通的 agent＝狀態機，在等待、思考、行動之間切換，需要思考就丟 LLM。（3f.7、3g.8、3g.9）
- **C-49** fsm 要很單純：「當現在是A狀態的時候，執行指定inst，就這樣，那個狀態內部、inst內部的東西，fsm不該管。」所以 fsm 只留表、`end` 與記現在狀態的 state 窗；錯誤處理、計數、暫停、格之間傳資料都歸格自己或拍它的 loop。（10-15 收工後，[thinking 意見 1～4](../thinking/2026-10-15-opinions-1-4.md)；規範 N-36～N-40）

## 定義與工作區（食譜與廚房，10-16）

規範：[NORMS 定義與工作區](../NORMS/10-基礎設施-定義與工作區.md)（N-46～N-51，草稿）；（N-55、N-56 frame 與工作區，10-16 夜）；實作：**程式還沒改**（現在沒有 `aos exec`、沒有 `.aos` 捷徑、沒有 `AOS_WS`，agent 還是舊式 frame＋args.json／ret.json，見 [lib agent.md](../lib/agent.md)）。

> 用詞（C-54）：「食譜」「廚房」是討論時的比喻；正式名詞是**定義**（食譜，一個 `.aos/` 資料夾）與 **frame**（廚房，跑的時候站的地方＝cwd；命令列原寫 `WD`）。「門房」＝`aos exec`。**10-16 夜改名**：今天稿／條文原本把 cwd 叫「工作區」，現在改叫 frame；「**工作區**」只留給使用者的檔與成品所在的資料夾（例 `/ws`，C-65）。見[名詞表](附錄1-名詞.md)。

- **C-57** **正規參數入口是 stdin**；`aos agent 路徑`、`aos exec WD TARGET` 這類 argv 寫法都是**語法糖**（接 N-12：stdin＝參數）。（使用者 10-16：「argv:[aos,agent,agents/brush]，其實，我一直覺得argv這塊的用法...就像我早期說的，正規參數入口就是stdin，像是aos-exec WD TARGET這個用法是語法糖...」，[稿 § 四](../thinking/2026-10-16-agent-inherit.md#四使用者決定10-16)）
- **C-59** **定義與 frame 的接法＝捷徑**（10-16 夜改字：原寫「工作區」，C-65）：定義（食譜）是一個 `.aos/` 資料夾；frame（廚房）裡放一條叫 `.aos` 的捷徑（symlink）指向那個 `.aos/`；定義裡的檔互相指一律寫 `.aos/x`——從 frame（cwd）算，**沒有第二種路徑規則**，誰站在 frame 誰就找得到。不靠 `$ref`、不寫絕對路徑、不編譯、不藏暗規則，靠檔案系統本來就有的捷徑自然組合（像 Plan 9 的 bind，C-30）。frame 就是那個 node（C-36、C-39），`.aos/` 是它的定義。（使用者 10-16 夜：「哇，可是我不想用 `$ref`……我也不想用絕對路徑。我也不想要用小工具編譯，我想要依靠機制自然組合。我也不想用暗規則……」→ 選捷徑：「捷徑。這塊細說」→「太優雅，太美了，這就是我要的。」，[稿 § 四](../thinking/2026-10-16-agent-inherit.md#四使用者決定10-16)）
- **C-60** **推廣到所有東西**：任何「可重複用的定義＋這次在哪做」——一支工作（inst）、一條 tasks 流水線、一個 loop、daemon 的子項、kernel 的判官、agent——都是「定義 `.aos/`＋frame（cwd）」，一律 **`aos exec frame 定義`**（門房：站進 frame、沒掛就把定義掛成 frame 的 `.aos`、跑 `.aos/inst.json`；10-16 夜改字：原寫「工作區」，C-65）。定義裡可以放一個 shebang stub（第一行寫「用 `aos exec` 跑我」），讓人在終端把定義當指令打；**體系內部不靠 PATH**（C-61），PATH 只留給人。（使用者 10-16 夜：「何等美麗的閉環，這就像是lisp的repl，/ws就是那個啥...」「前兩項我都OK」，[稿 § 四](../thinking/2026-10-16-agent-inherit.md#四使用者決定10-16)）

### frame 與工作區分開（10-16 夜）

出處：[稿 § 四](../thinking/2026-10-16-agent-inherit.md#四使用者決定10-16)（決定與原話）、[稿 § 八](../thinking/2026-10-16-agent-inherit.md#八工作區與-frame-分開10-16-夜重想ai-提案指標捷徑工具可直接-cwd-ws風險設計者自管已定)（使用者看完「三分鐘看懂（五）」：「我覺得不錯。」）。規範 [N-55、N-56](../NORMS/10-基礎設施-定義與工作區.md)；**程式還沒改**。

- **C-65** **frame 與工作區是兩個東西**：**frame**＝執行時才往裡放東西的地方——`.aos` 捷徑、history、fsm 狀態、loop 的窗、叫工具時開的小格；像函數跑起來的 stack frame（續聊＝同一個 frame 再跑，要忘記＝換一個）。**工作區**＝使用者的檔、成品要留的地方（例 `/ws`），像 C 的外部變數。agent／定義跑的時候**站在 frame**；**工作區保持乾淨**——跑完只多出成品，不留 `.aos`、history、`work/` 這類執行時的東西（frame 別放在工作區裡，除非呼叫方自己選，C-67）。（使用者 10-16 夜：「我記得先前還有一個叫做frame的概念，也就是agent當函數，函數運行時候的heap(還是stack?反正就是運行時才會往其中放資料的)，可以指定某個資料夾當heap。用捷徑也不錯。然後我不喜歡/ws底下出現一個work/，這太突兀了，工作區會變得不乾淨。」）
- **C-66** **影響外部＝透過指標，指標＝捷徑**：像 C 函數要改外部變數得拿到指標，工具要動呼叫者的工作區，也是拿到一個指向工作區的東西，不是自己伸手出去；在 aos 裡這個指標就是一條指向工作區的捷徑（或指向它的路徑，規範上由環境變數 `AOS_WS` 給，N-55）。能不能寫由 Linux 權限管（C-64），風險由工具的設計者自己管控。（使用者 10-16 夜：「除此之外，C語言函數想要影響外部變數，那也是透過指標」→「那就是捷徑」；「對，我覺得這樣會更方便。風險就設計者自己管控」）一般工具**預設站在工作區**、agent 工具（例 brush）**預設站在自己的 frame**（使用者：「我是覺得不用"遞"，而是就是默認true，默認ws就是工具的cwd...可以嗎？」「同樣用捷徑？」「brush這種agent工具，那就是他的cwd默認是他自己的frame。」）；這兩種預設怎麼寫才不是暗規則見 [N-56](../NORMS/10-基礎設施-定義與工作區.md)。
- **C-67** **frame 放哪由呼叫方自由決定**：被叫的 agent 不知道也不必知道（C-52）；「frame 在哪」只是一條捷徑的指向，改指向就得到不同效果，定義不動、規則一條都不用加——這是刻意保留的自由度。例（[稿 § 八 3b](../thinking/2026-10-16-agent-inherit.md#3b-frame-指到哪是呼叫方的自由概念層的一句)）：frame 指到工作區＝就地辦公（代價：執行時的東西全落進工作區、可能跟使用者的檔撞名）；兩個 agent 共用一個 frame＝共享記憶、接力（同時跑會互寫）；frame 放暫存目錄＝用完即丟（當機就沒了）；frame 長期保留＝下次接著聊（小格會一直堆）；frame 放在別人唯讀可看的地方＝旁人能審視、改不了（C-64）。代價都是呼叫方自己的選擇。（使用者 10-16 夜：「只是我們可以偷偷把它的frame設成ws」「我們可以自由管控他的frame要在哪裡，從而達到各種神奇效果」）
