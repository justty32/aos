## 十二、巢狀：層層疊疊（10-19 第二輪）

使用者 § 10：「以後會是巢狀嵌入，層層疊疊，act 中所使用的工具可能又是另一個 agent-cathy，一層一層這樣。」底下每條都照同一把尺：**每一層只管自己這一層、同一條規則在每層重複**（C-52）。aos 本身仍然只管那幾個環境變數（§ 4；10-19 下班前起五個，§ 19；10-21 晚加 `AOS_CO` 成六個），這一節全是慣例。

- **P-32 被叫者的工作區在呼叫方的小格裡。** 叫另一隻 agent 當工具，跟叫工具一樣先開小格 `sub=$AOS_STACK/<名>/`（P-17）；它若需要自己的工作區（它自己的說明會說，例如 cathy 認 `inbox/` 一題一檔），工作區就是 **`$sub/ws/`**：呼叫方照它的說明在那裡備好題目、叫它、再從那裡拿答案。一行寫完：`AOS_STACK=$sub aos-exec --ws "$sub/ws" tools/<名>`（10-21 起工作區用旗標給，原位置參數 `tools/<名> "$sub/ws"`，N-58）——**stack 與工作區兩個都明給**（`AOS_STACK` 已經有值，aos-exec 不會替巢狀給預設；只給工作區不給 stack，被叫者會把 `state`／`current` 寫進呼叫方的 stack，把呼叫方的狀態機弄壞）。不需要工作區的工具（stamp 這種吃 stdin 吐 stdout 的）不給 `--ws`（沿用），只給 stack。被叫者沿用呼叫方的 `AOS_WS` 只有一種情況正當：它的說明說它就是要動呼叫方的工作區（C-66 工具拿指標改外部變數）。使用者的工作區因此只多出 bob 自己的 `out/`、`done/`，cathy 的題目與答案全在 `.aos/cathy/ws/` 裡。**這不是「agent 之間走 inbox」的規則**：bob 寫 cathy 的 `inbox/` 是因為 cathy 的說明這樣寫（P-26 參數怎麼進由工具說明定）；換一隻吃 stdin 的 agent 就照它的。（§ 10；§ 9「inbox 先不管」；C-65 工作區只放使用者的東西、stack 放「叫工具時開的小格」；C-66；C-67 stack 放哪由呼叫方決定；C-52 被叫者不知道上面有誰；P-14 工作區其他東西不碰；P-17）
- **P-33 工具放在叫它的那一格的資料夾裡：`<格>/tools/<名>/`，格裡寫 `aos-exec tools/<名>`，永遠零個 `..`。** 相對路徑從 cwd 算，而格起跑時 cwd 就是格自己的資料夾（N-59），所以不管這格被埋在第幾層，路徑都一樣長、一樣對。bob 的 act 叫 `tools/cathy`，cathy 的 act 叫 `tools/stamp`——`agent-bob/act/tools/cathy/act/tools/stamp/` 這條路徑就是呼叫鏈本身（P-38）。內嵌單子格（think）的 cwd 是 agent 資料夾，它若要工具就是 agent 根下的 `tools/<名>`，同一條規則。**不給程式根變數**（aos 只訂那幾個變數，§ 4；而且 aos-exec 對每一格都是「一個資料夾程式」，不知道哪一層算「agent 的根」。§ 19 加的 `AOS_CD` 不是程式根：它是**這一格**自己的資料夾、每層覆寫，bob 的 act 格看到的是 `act/`，用途是 cd 走之後找回自己，例 `cd "$AOS_WS" && … && aos-exec "$AOS_CD/tools/stamp"`）；**不用 PATH**（C-61）。幾格共用一個工具、幾隻 agent 共用一隻 cathy：複製一份（demo 的做法，P-25 不跨 agent 互指），或在自己的 `tools/` 放一條捷徑指過去（C-61「相對捷徑、兩份一起搬也不斷」；Linux 才有，§ 9 先只考慮 Linux。本 repo 在 Windows checkout，所以 demo 不 commit 捷徑）。改掉 10-19 早上的 `../../tools/stamp`。（C-61 地址在自己資料夾裡、不用 PATH；N-50；C-56 KISS；§ 4）
- **P-34 小格不收、不清，連叫也用同一個；要全新就換名。** 第二題再叫 cathy 時，她的小格裡還有上一題的 `current`、`plan`、`trace.jsonl`、`ws/done/`——這是正常的：標準範本正常結束時 state 停在 `idle`（P-08），所以她從頭開始，`current`／`plan` 被新題蓋掉、`trace.jsonl` 與 `done/` 累積給人看。她若上次**失敗**停在半路（state＝`act`），呼叫方修好後再叫，她正是從那格接著做——這就是 P-20 要的。所以呼叫方**不在開工前 `rm`**（那會把 P-20 的接續抹掉）、**不用題名開新小格**（小格會跟著題目長、stack 樹不再等於呼叫樹）。真要全新：呼叫方給另一個小格名或自己 `rm`（C-67 呼叫方的自由）。被叫者的義務只有一條：**正常結束時自己的 stack 要停在起點**。（P-17 叫完不自動收；P-20 失敗停下、修好接著做；P-08；C-65「續聊＝同一個 stack 再跑，要忘記＝換一個」；C-67；拍板點 3 人來看）
- **P-35 格可以是一整隻 agent，不可以是別人 fsm 的一拍；10 只有 idle 退。** 當工具的 agent 入口一定是它自己的 loop（P-05），被叫一次就從現在的 state 跑到它的 idle 退 10 為止才回來；它的 loop 收到 10 退 0，所以呼叫它的格看到的是 0，上層的 loop 不會被誤停——cathy 的 10 到不了 bob。**不要**把另一隻 agent 的 `fsm.json` 直接拿來當自己的一格（`{"argv": ["aos-fsm", "tools/cathy/fsm.json"]}`）：那一拍她退 0 只代表「她走了一格」，你的 fsm 卻會換狀態、她還沒做完；她退 10 又會把你的 loop 停掉。舊做法（階層式 fsm、內層沒完回 `next: null`）靠的是 stdout JSON，現在只看結束碼，做不到，也不需要——要巢狀就整隻叫。格叫工具時**工具的非 0 一律當失敗、自己 `exit 1`**（`|| { echo "act: cathy 失敗" >&2; exit 1; }`），不把工具的碼原樣 `exit`——工具若退 10 會被 fsm→loop 當成「停」。（P-19；P-21 誰的錯誰講；C-52 上層不知道下層是 fsm；N-53 整隻 agent 由自己的 loop 驅動；ideas § 9 第 4 條）
- **P-36 逾時打整棵子樹；外層包內層。** **已做**（第二輪步驟 1，`test_fsm.py` 的 `test_outer_timeout_kills_nested_tree` 做整合驗證）。原先的問題：aos_inst 逾時只 SIGTERM／SIGKILL 它直接起的那一個程式；格是 `#!/bin/sh` 時 sh 被殺、sh 底下的 `aos-exec tools/cathy`→cathy 的 loop→她的格全變孤兒繼續跑（sh 收到 SIGTERM 直接死、不轉給前景子程式）。做法：單子起的程式自成一個行程群組（`start_new_session`；impls 線是 inst 的 C lib `new_session`、aos-exec 行程內跑單子時當監工轉訊號，§ 20 預設「逾時整群殺」），逾時與轉來的 SIGINT／SIGTERM／SIGHUP 都打整個群組（`killpg`），grace 到了 SIGKILL 整個群組；中間沒隔單子的那幾層（sh 格、`subprocess.call` 起的 aos-exec）本來就跟起它們的程式同一個群組，所以一刀下去整棵子樹一起收，下一層單子再轉給它自己的群組，層層往下。被殺的那格＝**失敗**（碼 128＋訊號、`trace.jsonl` 那行 `timed_out: true`），上面照 P-20 停下來等人，不當正常收工。N-52「SIGTERM 退 0」因此作廢（使用者 10-19「都按照建議」，[ideas § 9、§ 11](../thinking/2026-10-19-ideas.md)）；它的後半句留作慣例：**收到 SIGTERM 的程式先收好自己起的子程式、寫好狀態再結束，但結束碼是非 0**（被殺就是失敗；使用者 10-16 原話：「重點在於"把該做的事情做一做後，才結束"」）。**loop／fsm 自己收到 SIGINT／SIGTERM／SIGHUP**（10-19 晚使用者「1.好。」，兩版 loop／fsm 都照做，[ideas § 24](../thinking/2026-10-19-ideas.md)）：先轉給正在跑的那一拍（字串的 run／格＝那個子行程；單子＝inst 轉給整群、過 `grace_ms` SIGKILL 整群），等它收好，**不起下一拍**，以 128＋N（N＝第一個收到的訊號）結束；拍與拍之間收到＝不起下一拍、直接 128＋N；fsm 被中斷時那格跑完**照常寫 `trace.jsonl` 與 state**（格退 0 就照樣換狀態），再以 128＋N 結束——就是上一句「先收好、寫好狀態、結束碼非 0」落在 loop／fsm 身上。SIGINT（人按 Ctrl-C）跟 SIGTERM 同一種處理（原 [NORMS 待定](../NORMS/08-待定.md)「SIGINT 比照 SIGTERM」結案）。寫法：逾時寫在最靠近會卡的那格（think 問腦 120 秒）；要包住整隻子 agent，呼叫它的格在 `fsm.json` 寫成 `{"argv": ["aos-exec", "act"], "timeout_ms": …}`；**外層 ≥ 內層一圈各格逾時之和 × 內層 `max`**，不然外層會先殺人；`grace_ms` 外 ≥ 內（巢狀 grace 使用者 10-12 夜定「只當慣例、不進規範」：建議值也是程式預設——inst 2000、daemon 10000；外層宜大於內層；設錯自己負責。aos-inst 的 `grace_ms` 預設 2000 就是它；daemon 10-20 重寫時沿用 10000：收子 loop 時 SIGTERM 後等 10 秒才 SIGKILL）。aos 不替人算這個。代價：新群組沒有控制終端，格裡的程式不能去讀終端（agent 本來就不該，N-41）。（N-41 靠 `timeout_ms` 守；P-22；P-30 逾時收尾不留孫程式；C-52 每層只管自己直接起的；「巢狀 grace：外層宜大於內層」；N-52 作廢，見上）
- **P-37 不設深度上限、沒有人管遞迴。** 照 P-33 工具在呼叫者自己的資料夾裡、不用捷徑時，「cathy 又叫 bob」根本寫不出來（bob 不在 cathy 底下）；寫得出來的只有捷徑或絕對路徑，那是設計者自己選的。真遞迴下去，每層小格路徑多一段，撞到路徑長度上限時 `mkdir` 失敗、aos-exec 退 1、一路失敗往上停；或被最外層的 `timeout_ms` 一刀收掉（P-36）。不加深度計數、不加環境變數數層。（N-39「表裡的格指回自己（遞迴）fsm 不擋，卡死不防護」；C-53 誤用不歸組件管；C-56 不為邊緣狀況加機制）
- **P-38 stack 樹＝呼叫樹＝tools 資料夾樹；看全貌就看那棵樹。** 每層照 P-17 用工具名開小格，所以 `$AOS_STACK` 底下長出來的就是這次誰叫了誰：`.aos/{state,trace.jsonl,cathy/{state,trace.jsonl,ws/,stamp/runs}}`。每個 fsm 層有自己的 `trace.jsonl`；為了把各層的 trace 對到同一條時間線，每行加 `at`（這拍開始的 UTC 時間，ISO 格式）。看法：`find "$AOS_STACK" -name trace.jsonl | xargs cat | sort`（照 `at` 排就是整棵樹的時間順序）、`tree -a "$AOS_STACK"`；`demo/run.sh` 跑完印整棵樹。不另做彙整工具、不做跨層的 trace id。（拍板點 3 人來看；C-54 結構本身就是說明；C-56；N-39：10-15 待定「標準實作要不要每拍記時間」→ 這裡定要）
- **P-39 往下只流環境變數，別的都明給。** 六個變數分三類（原五個，§ 19 使用者「同意做」，分類是 fable 擬的；10-21 晚加的 `AOS_CO` 歸每層覆寫）：**叫別人時明給**——`AOS_WS`、`AOS_STACK` 每次叫別人都明寫（P-32）；**一路繼承**——`AOS_ENTRY`、`AOS_BRAIN_*` 整棵樹一致，所以**巢狀裡的 agent 不改 `AOS_ENTRY`**（上面改了名，底下每一格都要跟著有那個檔），demo 全用預設 `_exec`（10-19 晚改，原 `.aos/exec`），腦要換端點就在叫它那一行覆寫；**每層覆寫**——`AOS_CF`、`AOS_CD`（10-21 晚加 `AOS_CO`）由 aos-exec 每次呼叫重設（N-57），每層看到自己的、不用管也不該改，要往下傳自己的位置就拿它的值明給（例 `aos-exec "$AOS_CD/tools/stamp"`）。stdin 一路繼承到最底層，所以**agent 類工具不讀 stdin**（會卡在終端上），要餵東西就 `<` 明給（stamp 那種）。stderr 一路繼承，每層出錯只說自己一行（P-21），三層就是三行、由下往上，人看得出是哪層。`PATH`：**aos 的程式（aos-exec、aos-loop、aos-fsm，兩版）一律不動 PATH，原樣傳下去**；入口、格、run 裡要叫 `aos-exec`、`aos-fsm` 這些，由呼叫者自己讓它們在 PATH 上（10-19 晚使用者先對 loop／fsm 說「2.不要主動加」、再對 aos-exec 說「也套用，都不動path吧」，兩版都照做，[ideas § 24](../thinking/2026-10-19-ideas.md)；原本 aos-exec 每層把自己所在的 `bin/` 加到前面、「loop／fsm 等重寫後再定」，都拿掉，N-59）。**10-21 加 `.env`**（[N-59](../NORMS/10-基礎設施-定義與工作區.md) 第 4 件，[ideas 10-21 § 4](../thinking/2026-10-21-ideas.md#4-aos-exec-支援-env10-21)）：aos-exec cd 進入口資料夾後讀那裡的 `.env`，優先順序 旗標 ＞ `.env` ＞ 原本的環境變數 ＞ 預設，所以上面三類每一類都可能被被叫者自己的 `.env` 改掉（什麼都能設、風險自擔，使用者「2.可以，全都可以，不限制，風險自己擔。」）；`.env` 裡設的 PATH 是使用者自己寫的，aos 的程式仍不主動加 PATH。叫它那一行設的換腦變數會被 `.env` 蓋掉，使用者「先不管」；10-21 晚又說「換腦這塊不管，也不用待定，之後做到那邊的時候會改。」（不列待定）。（§ 4 aos 只訂環境變數；§ 19；N-55 環境變數自然往下傳；P-21；C-53）
- **P-40 JSON 入口怎麼寫（兩版 aos-exec 都適用）**：單子或 argv 陣列當入口時，寫成**沒 `+x` 的 JSON 檔**（`_exec.json`，或資料夾裡沒 `+x` 的 `_exec`、或 JSON 裡的 `js["_exec"]`），**不寫 shebang、不設 `+x`**（aos-exec 看到 `+x` 就 exec、不讀內容——`+x` 的 JSON 檔沒 `#!` 會被交給 `/bin/sh` 跑、當然跑不動，§ 22；沒 `+x` 才當 JSON 讀，第一行 `#!` 只是被跳過、留著會誤導人）。**不要**寫成 `#!/usr/bin/env aos-exec` 再 `chmod +x`：`+x` 的檔 aos-exec 會再 exec 它、kernel 再叫 aos-exec……原地無限 exec，aos-exec 照 P-37 不讀 `+x` 檔的內容去擋（原本還有一個理由「第二個位置參數是 WS、kernel 傳進來的 foo 會被當工作區」，10-21 aos-exec 改收旗標後沒了，N-58）。`js[$AOS_ENTRY]` 寫字串時指的是**另一個入口**（資料夾、檔、`檔#/指標`），不是 loop／fsm 的設定（§ 18 ① 使用者「確實要改寫例子」：要跑 loop 就寫 `"_exec": ["aos-loop", "loop.json"]`）。單子只認 bin/README 列的 10 個 key、其他忽略（§ 20 預設）；單子沒寫的串流接呼叫者的。**argv 陣列裡可以放 `$env`、`$ref`**（10-20 改，原本只能全是字串；N-45）；**argv[0] 寫別的資料夾程式**（資料夾、JSON 檔、`檔#/指標`）＝等同前面插 `aos-exec`，第二個元素起都是 args（10-21 改，原本照字面第二個元素是 WS、要傳參數寫 `["tools/stamp", "-", "a"]`；要換工作區寫 `["aos-exec", "--ws", WS, "tools/stamp", "a"]`，N-58）（N-61；10-20 使用者，見 [ideas](../thinking/2026-10-20-ideas.md) D2、D3、D5、D8）。（§ 14、§ 17、§ 18、§ 20；C-73、N-61；計畫 v2 衝突 6 的預設，使用者沒異議）
