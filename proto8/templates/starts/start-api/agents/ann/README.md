寄之前 `AOS_LLM_KERNEL` 沒設或只有空白＝觸發 `brain_failed` 後以 `LlmKernelMissing` 停下、不記冷卻、保留請求，要帶變數重掛；有設但 kernel 資料夾不在仍照 `SendFailed` 冷卻等待，wait 格等腦回信不設期限：寄出後每滿 10 分鐘在 stderr 印一行 `agent-fsm: warning: no reply from the brain for N minutes to letter <名>: <原因>; still waiting`、照樣等（原因＝信在 kernel 的哪一格：`requests/new/` 還在排隊沒開始、`cur/` kernel 正在跑〔附那封的 `stderr.txt` 路徑〕、或 `AOS_LLM_KERNEL` 沒設／不是資料夾；kernel 沒在跑由同一拍 `aos-llm recv` 那行說，two-machines B10）（提醒到第幾次記在 stack 的 `think/wait_warned.txt`）。

- `think/brain_wait.json`：寄出成功時原子記下信名 `letter` 與 kernel 絕對路徑 `kernel`，供 `listen`／`say` 提示；只採信與 `think/pending.txt` 相同的信，不必刪除。

kernel 回 `BudgetMissing`＝額度拒絕、不停下：先觸發 `brain_failed`（`name = BudgetMissing`、`reason` 原樣帶 kernel 的 `error.msg`，條件只有 `BrainFailed` 的 hook 不再匹配），再記 `cooldown.json`（同代號、30 秒起加倍到 30 分鐘，之後每 30 分鐘）、印一行 `agent-fsm: warning: BudgetMissing <msg>; waiting, the same request is sent again when the cooldown ends`、退 10 留在 wait；冷卻中不寄、到期重寄同一份 `request.json`，不寫 `observed.jsonl`、不加 assistant 訊息。好的回信接進 history 後清冷卻；只有因 endpoint／調整鍵改變而退 11 回 think 重組時，也會先清 `BudgetMissing` 冷卻（清不掉只 warning），其他代號與其他重組原因不清。recv 退非 0 時，其他 kernel 錯誤、stdout 不是 JSON 或沒有 error 物件，仍走原本 `BrainFailed`、退 1；冷卻檢查通過、正要寄出時，若 `priority.deadline` 可解為有限 epoch 秒數或帶時區的 ISO 時間，且已過或 5 秒內到期，wait 只印 warning、不寄出，退 11 回 think 重組，不觸發 `brain_failed`、不改 `request.json`／`cooldown.json`；解不開的 priority 仍交 kernel 判斷（出廠 brain.py 目前不寫 deadline）。
kernel 的 `error` 若多帶結構化欄位（`window`＝`hour`／`day`／`all`、`resets_at`＝下一個視窗起點，ISO 8601 帶時區，`all` 是 null；舊 kernel 只有 `code`／`msg`，行為不變）：`resets_at` 在未來＝冷卻到 `resets_at` ＋ 5 秒（不早於現在＋30 秒，`cooldown.fail_until`，`failures` 照樣加 1）；`resets_at` 剛過不到 60 秒＝現在＋30 秒；解不開、沒帶時區、更舊或沒有＝照上面的間隔表。`window` 是 `all`（永不重置）＝不重試：先觸發 `brain_failed`，再印 `agent-fsm: error: BudgetMissing <msg> (window all: it never resets; raise the budget, then start me again)`、退 1，不記冷卻、`request.json` 留著，加了額度再起＝重寄同一份。`brain_failed` 事件另帶 `error` 欄＝解到的 kernel error 物件（每種 kernel 回錯都有，沒解到就沒有這欄）；範本的 `brain_notify` 讀它：有 `resets_at` 時標題寫「waiting until <本機 HH:MM>」、說明到時自己重試；`all` 時標題寫「stopped」、說明額度不會重置、加額度再起 agent。注意：開了 `auto_restart` 的列碰到 `all` 退 1，daemon 會重起它，重寄的請求立刻又被拒（不耗 token），靠 daemon 的重起退避擋著；subagent 沒有 `auto_restart`。

goal 暫停中來信不自動 resume；只有 agent 自己暫停、history 尾段仍找得到最近的 goal 工具呼叫且之後有新訊息、答完又停下時，idle 才補一次 `[aos] goal: paused …` 提示，讓腦選 resume／done／繼續等，碰到既有 goal 提醒或 summary 就不補，外面或 aos 設的暫停與 goal.json 都不動。

**context 快滿與 /compact**：新範本預設掛 `context_wrap`（`on_clock`、每 5 秒、`config {"percent": 35, "wrap": false}`），用 `observed.jsonl` 最近一次有效 `think` 的 `usage.prompt_tokens` ÷ kernel 發布的 pack `context` 量用量；hook 的 `config.window` 可蓋過視窗，兩邊都沒有就不觸發。過門檻直接寄 `/compact`，收尾併進摘要；人也能寄 `/compact`：body 先把舊的工具輸出換成一行佔位（最後 3 則、最後一組、短於 300 字的不清，原文進 `history_removed.jsonl`），再叫腦在自己的對話裡寫摘要，那次不帶工具，之前的對話換成一則摘要，沒答的信原文留著，摺掉的原文在 `history_removed.jsonl`，摘要另存 `<stack>/handoff.md`。做到一半也收得到，等工具結果齊了才壓、壓完接著做；可摺的不到 4 則（例：剛壓完又來一封）就不問腦、不摺，當成正常做完：回一句 `compact not needed: …`，信記成答完、不寫警告。壓縮前後各有一個 hook 點（11-21 第 4 刀）：`before_compact`（可攔下、改給腦的指示、不清工具輸出、直接交一份摘要＝不叫腦）、`after_compact`（摘要寫進 history 之前，可改摘要、交一段補回的字，接在摘要後面、不多叫一次腦）；範本一個都不掛，各家要自己的 compact 方式就掛在這兩點，規矩見 [壓縮前後的 hook](../../docs/02-agent-fsm.md#壓縮前後的-hook)。改門檻要改 hook 格的 `config.percent`（`self_hook add` 帶不了 config）；關掉用 `self_hook` `{"op":"rm","name":"context_wrap"}`，或 stack 的同名 hook 格寫 `null`（`self_hook` 要選掛 events 包）。`context_wrap --reading <stack>` 可看讀數或讀不到的原因；完整行為、資料格式、限制與舊 agent 換檔順序見 [context 快滿與 /compact](../../docs/02-agent-fsm.md#context-快滿與-compact)。

**hook 預設**（[clock-hook](../../../thinking/2026-11/11/clock-hook/README.md)）：`loop.json` 的 `on_start`／`on_stop` 叫 `aos-hook fire -q --stop-on-nonzero --def $AOS_CD` 發 `after_start`／`after_stop`（handler 的碼原樣交給 aos-loop，非 0＝agent 停；after_stop 的 handler 讀環境變數 `AOS_LOOP_CODE`、`AOS_LOOP_SIGNAL`、`AOS_LOOP_CAUSE`（為什麼停：`stop`／`sleep`／`remove`／`shutdown`／`stuck`／`signal`／`max`／`body_exit`／`error`，舊版 aos-loop 沒給＝空；`cause` 跟表上的 `reason` 不同，`reason` 是給人看的一句話；撞限額沒有獨立的值，看表上的 `limit_hit`；`error` 只是停止的分類，不是錯誤代號；值表見 [aos-loop 01](../../../cpp/aos-loop/docs/01-用法.md)））；`before_run`／`after_run`（每一格前後）預設不接，要掛就照 `on_start` 的樣子在 `loop.json` 加 `on_before_run`／`on_after_run` 再重起；`hookeds.json`（被勾清單；`interfaces.json` 最外層 `"hookeds"` 指它，`"hooks"` 指 hook 點的宣告 `hooks.json` 與 aos-loop 的 `loop_hooks.json`，只是參考）帶一格 `timer`（`on_clock`、每 300000 ms、handler `py/tools/agent/hook_noop` 什麼都不做；每次起來、睡醒會先跑一次，之後每 5 分鐘）；另一格 `mail_notify`（`on_clock`、每 60000 ms＝每 1 分鐘、handler `py/tools/agent/mail_notify`：看自己的信箱，有沒通知過的新信才往 `queue/` 寄一則 `[aos] new_mail: N new letters from A, B. …`、多封合成一句、沒新信不動 history；睡醒時照已通知記錄比：睡前提醒過的不再提、睡著時新到的提醒一次；全新起來（沒有 `notified.json`，且 agent stack 的 `history.jsonl` 不在或是空的）時在等的只記成已知；跑過的 stack（有非空 history）當睡醒，在等的提醒一次；使用者「用on_clock」「預設開」「合成一句」，[mail-notify](../../../thinking/2026-11/11/mail-notify.md)；間隔與起來那次：使用者「每 1 分鐘」「只提醒新到的」「睡著時新到的要提」，[backlog-rulings](../../../thinking/2026-11/11/backlog-rulings.md)），history 不多任何一則。要定時叫醒腦＝同名換成往 `queue/` 寄信的 handler；不要＝`aos-agent hook -t 名 rm timer`。用法 [aos-agent docs/06](../../../py/aos/apps/agent/docs/06-hook.md)。
