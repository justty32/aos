變成一棵樹，並且消耗降低

turns: 描述了每一回合

以galtxt爲例子
會先規劃一些東西。首先輸入的資料，建議是已經結構化的，這樣好處理。
並且限制各類輸入範圍，比如場景內的東西就那幾種，人物背景就是那樣。相關詞匯就那些。
  也就是用enum等方式，或是json schema。
然後是評判器，可以先用agent做初步評判，先把連基礎邏輯都出錯的狀況處理掉，後續才是換人類給意見
優化器，目前是規劃要嵌入到一般樹中。有需要的話可以另外弄一棵樹。
評判器，優化器兩棵樹，可以和普通樹，共存在同一根節點下。

第一回合：一個資料夾，裏面存放了一些參考資料，一些prompts等，其_entry就是呼叫claude code cli
其_metainfo描述了相關東西：消耗token，消耗大量cpu/記憶體等，並且claude code cli不受控制，可以存取各種東西...
裏面有_improve，那是另一個_entry

一點五回合：呼叫_improve，給出指令：脫離claude code cli依賴
然後就是在這個資料夾同樣呼叫claude code cli，他會把自己這個資料夾內的東西，轉變爲aos loop-fsm-agent
然後重新去跑一些東西，或是拿一些現有的對比資料，重新寫下_metainfo。確定OK之後會更改_entry

第二回合：目前資料夾內是aos loop-fsm-agent，但是只是最基本的幾套工具，然後llm也是將請求直接丟到LLM kernel
其_metainfo內的各種東西，其實都沒有優化很多，並且performance可能還會有所降低

二點五回合：呼叫_improve，這次是正式進入優化環節。最重要的目標就是讓token消耗降到0
但是又保有一定程度的使用者好評。所以，一開始就會上fable優化器。
會先八股化，先把一些必然的句式固定下來。然後一些需要變化的句式，就會分別交給幾個函數
這些函數就是負責生成這些段落或句式。

第三回合：這次有了一些工具，並且也有一些函數可調用。那些函數負責不同句式。
有些函數是普通的將請求丟到LLM kernel的腳本，有些比較複雜的，就直接成爲agent
單檔腳本，通常不會有_metainfo。成爲資料夾之後才會有，或是成爲json之後。
而那些_metainfo內的欄爲，也是由優化器自行設定。通常來說

三點五回合：這次improve，就是假設一些段落的效果不好，然後主節點這邊會將責任交給那些應該負責的節點
這些子節點，他們只負責特定句式。如果需要負責的是那種單檔腳本，優化器會視情況，將其抬升爲agent。這通常是在單檔無法負擔的時候。
然後繼續...

隨着繼續優化繼續深入，隨着"降低token消耗"作爲最主要優化目標的執行，句式會繁多，詞匯也會繁多。
這些其實都沒啥問題。
真正會遇到瓶頸的是後續使用者給出意見，說某個環節，他那個句式應該要符合一些規則邏輯
