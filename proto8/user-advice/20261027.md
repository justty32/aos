我們將資料夾作爲函數。
但實作上，其實是將各類功能弄成posix呼叫，並跟資料夾綁在一起。
資料夾內因爲可以有多個檔案，所以可以擺放該函數的各類其他資訊。

LLM呼叫是一個函數，丟prompt，返回一串文字。
我們先定義agent的一輪動作爲"自輸入動作後，到agent不再呼叫任何工具並吐出回覆爲止"
那我們將一輪動作視爲一個函數，其實可以寫成如下pseudo code:
def one_round(endpoint, prompt, tools):
  result = llm_ask(endpoint, prompt, tools)
  while result.has_tools_call:
    deal_tools_call()
  return result.final_msg

這樣一個函數，途中可能還會有使用者丟入新的prompt，所以又可以在其中進行擴充
又有可能，途中還會有被暫停掉，yield去做其他事的情況。
但總之就是圍繞這幾個變數去做，我懶的寫了。
值得一提的是副產物，也就是final_msg之外的msg，不管是prompt或reply。

好，這樣一個函數，他的參數各有不同說法
endpoint：最容易出問題的地方，一個稍微複雜一些的結構，404啦等各類錯誤都需要處理
prompt：可以拆成初始prompt，還有後續額外prompt的入口(模型自身reply也會在其中)(算是需要處理的串流)
tools：外部可用函式庫。很簡單的形容，但也是靈活性最高的地方。
ps.一些想法：prompt其實有點像stdin/out，但...好吧，我不確定

這樣一個函數，我們將其納入aos體系，也就是將其弄成posix呼叫。
現有的方式是透過aos loop/fsm，這是靈活性極其高強的方法。但今天我想探討的不是這個。
我想探討的是，這樣一個函數，別人早就幫我們做好了，也就是claude code cli。甚至還配備了tui。
透過一些小技巧，我們可以輕鬆將其納入aos體系下，並且將我們的其他函數，透過aos-mcp接入其中
唯一問題就是他需要吃記憶體和cpu。但在我們剛起步的初期，可以先用他來快速上手。

首先，我們一樣是用_entry當入口，只是_entry這邊是一個小腳本。
他做的事情，就是把啓動claude code cli的一些flag擬好，然後把mcp json接入，並啓動。
這是最基礎用法。除此之外，我們還要利用claude code cli tui。
我會覺得，會有一個環境變數：AOS_CLAUDE_CODE_CLI_HUB，這指向一個資料夾。
那個資料夾內應該會跑着一個aos-kernel，管理着所有納入在aos體系下的這類函數實例。
  那個aos-kernel所做的事情，就是記錄當前哪個資料夾有claude code cli在跑。
  並且在該實例閒置太久時，將其關閉，歷史存到那個資料夾。
  另一方面，也提供一些指令供使用者查詢現在有哪些claude code cli instance，以及方便存取。
  比如在某個資料夾內，輸入aos-ccc state，就可以查詢此資料夾是否屬於aos納管下的claude code cli實例
  除此之外還有aos-ccc open，也就是打開tui。然後還有依託於shell的快捷鍵：ctrl+]，退出tui但不結束實例
  aos-ccc ls，列出當前所有正在跑的實例，與其所在資料夾。aos-ccc open ，也可以直接在後面接資料夾。
  aos-ccc stop，就是把實例暫停。以上這些指令，都依託於那個環境變數，和那個跑着的aos-kernel。
  預期是透過IPC手段與那個aos-kernel通訊...這些是技術細節，現在先不考慮。
這個aos-kernel或許也可能會做一些限制正在跑的claude code cli實例的數量的事情。
  乃至於分析當前與claude的連線數量，限制實例數量。畢竟一個賬號你同時間打一堆請求過去，不太好。
