## 場景

「上線前檢查」：服務要第 3 次檢查才會好。

```
pipeline = seq  reset  retry  work  finish
retry    = if   check  ok  again            ← 檢查過了跑 ok（空步驟 true）；沒過才跑 again（沒有 aos-not：分支對調就是反過來）
again    = seq  budget  pause  retry        ← 指回 retry 自己，就是重試迴圈
work     = par  report  notify              ← 兩件事一起做
```

| 步驟 | 做什麼 | 怎麼傳值 |
|---|---|---|
| `reset` | `tries` 寫 0，清掉上次的產物 | — |
| `check` | `tries` 加一；到了 `READY_AT` 次就印版本號、回 0，不然回 1 | 版本號寫到 `probe.out`（stdout） |
| `budget` | `tries` 到了 `MAX_TRIES` 就回 3（放棄） | — |
| `pause` | `sleep 0.3` | — |
| `report`、`notify` | 讀版本號，各寫一行（各 sleep 0.5，看得出是並行） | stdin＝`probe.out`，stdout＝`report.txt`／`notify.txt` |
| `finish` | 把兩份接起來，加上試了幾次 | 寫 `summary.txt` |

參數：最上層 `pipeline/inst.json` 的 `envs` 給 `MAX_TRIES`、`READY_AT`，一路繼承下去；`check`、`budget` 的 argv 用 `{"$env": "READY_AT"}`／`{"$env": "MAX_TRIES"}` 拿成 `$1`。

跑三個實例（一個跑完才 add 下一個，它們共用同一個 work 資料夾）：

- `pipeline`：MAX_TRIES=4 → 第 3 次過，並行兩件、收尾，`last_code` 0。
- `pipeline-fail`：argv 用 `{"$ref": "pipeline/inst.json#/argv"}` 借同一棵樹，MAX_TRIES=2 → 重試用完，`last_code` 3，`work`／`finish` 都沒跑。
- `pipeline-broken`：同一棵樹，**忘了給 READY_AT** → 看錯誤從哪裡冒出來（見發現 1）。

## 檔案

- `run.py`：mktemp 開暫存資料夾（`ctl/` 控制資料夾、`work/` 步驟間傳的檔、`log` 收 stderr（各層都是 JSON 串流，N-12）、`run/` 當 daemon 的 cwd，裡面放指回本資料夾三個 pipeline 的捷徑，tasks 的相對 TARGET 照樣找得到），起 daemon（PATH 前面加 `proto8/bin`），一個個 `add` loop.json、每 0.2 秒 `get` 等到 done，印 `last_code`、log、work 裡的檔；旁邊一條執行緒每 50ms 數一次活著的 tasks 程式。最後 SIGTERM daemon、等它結束，再刪暫存資料夾。
- `daemon.json`：`ctl_dir` 寫成 `{"$env": "DEMO_CTL"}`。
- `pipeline/loop.json`、`pipeline-fail/loop.json`、`pipeline-broken/loop.json`：daemon `add` 的就是這三個，`inst` 用 `$ref` 指同資料夾的 inst.json（跑 1 次）。
- `pipeline/inst.json`（最上層）和 `pipeline/*/inst.json`（11 個步驟，一個資料夾一個；`ok` 是空步驟）、`pipeline-fail/inst.json`、`pipeline-broken/inst.json`。tasks 讀子 aos_inst 的 stdout 那份結果 JSON 的 `code` 判斷子程式的結果（沒有 exit 檔）；各層 `stderr` 寫 `/dev/stderr` 把錯一路接上來。
