hook 點的宣告怎麼寫：硬性只有 id 與 input schema，其餘鍵想放什麼放什麼；aos 自己的宣告用了哪些鍵、誰讀。

使用者 11-21：「硬性規定要有id，要有input schema，剩下其他key就是想放啥放啥」；「block,if_block那些都不用，有需要的自己在input schema裏面添加，或是另外自己隨便加key」；「宣告這東西只是參考」。

## 格式

一份宣告檔是一個 JSON 物件：鍵是 hook 點的 id，值是那個點的說明；頂層的 `description` 是一句話、不是點。

```json
{"description": "Hook points of my-saver.",
 "before_save": {"description": "before a file is saved",
                 "input": {"type": "object", "properties": {"event": {"const": "before_save"}, "hook": {"type": "string"},
                           "stack": {"type": "string"}, "file": {"type": "string", "description": "the file name"}}},
                 "output": {"type": "object", "properties": {"file": {"type": "string", "minLength": 1}}},
                 "phase": "before", "block": true, "if_blocked": "the file is not saved"}}
```

- **硬性**：id 只用 `a-z`、`0-9`、`_`；每個點是物件、帶 `input`（JSON Schema 物件：handler 從 stdin 收到什麼）。這是 `aos.hook_point.read` 會查的全部；不合＝`PointsBad`。
- **其他鍵**都自由，寫了是「宣告說我大概會怎樣」。
- 同一個 id 在兩份宣告：先讀到的算，不報錯。
- **誰會查**：只有想讀宣告的程式（`aos.hook_point.read`／`declared`）與測試。`aos-hook fire`、引擎、agent 一家、kernel **都不讀宣告**：沒宣告的點照樣發、照樣掛得上；宣告了也不會因此多做什麼。`aos-gdb` 啟動時給 `--hooks FILE`／`--def-hooks` 才讀，當參考（列點、主詞、提醒、排事件；[apps/gdb/README](../../gdb/README.md#hook-宣告當參考--hooks-file--def-hooks)）。

## 放哪、怎麼指

- 定義夾的 `interfaces.json` 最外層：`"hooks": "hooks.json"` 或陣列，例 agent-fsm 範本 `"hooks": [{"$env": "AOS_HOME", "$path": "/lib/aos/apps/hook/loop_hooks.json"}, "hooks.json"]`（aos-loop 四點用指示詞動態連結 aos 裝的那份，agent-fsm 四格的點是夾裡那份）。
- 值只收**檔名、指示詞、或它們的陣列**；直接把宣告內容寫在 `interfaces.json` 裡不收（使用者第 7 則「1.不收」）。
- 沒有 `interfaces.json` 的程式（例如一支 shell 腳本）也可以寫一份 `hooks.json` 放旁邊給人看，沒有人會去找它。

## aos 自己的宣告用了哪些鍵

aos 自帶五份宣告：[agent-fsm](../../agent_fsm/hooks.json)、[eca](../../eca/hooks.json)（aos-eca-turn 與 compact_hook）、[mcp](../../mcp/hooks.json)（aos-mcp）、[aos-loop 四點](../loop_hooks.json)、[kernel 三點](../../../../tools/aos/kernel/kernel_hooks.json)（每個 kernel 定義夾一份抄本）。它們用的自由鍵：

| 鍵 | 意思 | 用在 |
|---|---|---|
| `description` | 一句話：什麼時候發 | 全部 |
| `output` | JSON Schema：handler 退 0 時 stdout 的 JSON 物件裡哪些鍵會被拿去改事件 | 能改的點（agent 的 before_queue／before_tool／after_tool、agent-fsm 的 before_compact／after_compact、eca 的 before_compact、kernel 三點） |
| `phase` | `before`／`after`／`on`：在那件事之前、之後、或只是時刻到了 | 全部 |
| `block` | `true`＝退 10 會攔下 | 能攔的點 |
| `if_blocked` | 攔下之後發生什麼 | 能攔的點 |
| `if_failed` | handler 失敗之後發生什麼 | aos-loop 四點 |
| `condition` | 被勾清單那格的 `condition` 拿事件的哪個欄位比 | agent 的 before_tool／after_tool／brain_failed／tool_added（`name`）、kernel 的 after_verdict（`verdict`） |
| `subject` | 那個欄位是什麼（`tool`／`code`）；`aos-gdb --hooks` 拿它當主詞的參數名 | 同上（agent） |
| `key` | 這次事件的識別欄（`letter`、`id`） | agent 的 queue／tool 點、kernel |
| `fired_in` | 哪支檔發的 | agent、kernel |
| `entry_keys` | 被勾清單那格這個點特有的鍵 | on_clock（`clock`、`every_cycles`、`every_ms`） |
| `environment` | handler 從環境變數讀到什麼 | aos-loop 的 after_stop／before_run／after_run |
| `notes` | 補充 | aos-loop 的 before_run／after_run |

**這些鍵沒有程式讀**（例外：`aos-gdb` 帶 `--hooks`／`--def-hooks` 時讀 `condition`、`subject`、`description`、`input`，只當參考）。它們說的規矩真正寫在各家的程式裡（agent 一家：[`agentlib/hooks.py`](../../../agentlib/hooks.py) 的 `POINTS`；kernel：[`tools/aos/kernel/hooks.py`](../../../../tools/aos/kernel/hooks.py) 的 `POINTS`；aos-loop 的退出碼規矩在 aos-loop 本身），宣告只是抄給人看。抄得對不對由測試 [`py/tests/test_hook_points_match.py`](../../../../tests/test_hook_points_match.py) 保證：`block`、`condition`、`output` 的鍵要跟 `POINTS` 一致，agent-fsm 與 eca 的點名要對得上，`on_clock` 的 `entry_keys` 要等於程式的那幾個鍵，手抄的說明（06-hook、知識庫、`self_hook` 的說明、`aos-agent hook --help`）每個點、每個欄位都要提到。

使用者第 7 則說「有提供這些key，就照着做，沒提供就用預設」，第 8 則更正「發事件的程式自己決定……我們提供的hook fire本身會參與這個過程」；現在的做法（第四層，使用者「簡化到第四層」「庫也極簡」）是：`aos-hook fire` 對這些鍵一律不看（等於全部用預設：只叫 handler、交回結果），規矩由發事件的那一家寫在自己的程式裡。

## 自己寫一份時

- 最少就是 id＋`input`。`input` 裡寫上 `event`、`hook`、`stack` 三鍵（每個 handler 都會收到，見 [03](03-寫handler.md)）再加你的欄位。
- 你的程式退 10 算不算攔、stdout 能改哪些鍵，寫在 `description`／`block`／`output` 裡讓人知道；照不照著做是你的程式的事。
- 例子：[`aos/cli/offer_hooks.md`](../../../../../knowledge/aos/cli/offer_hooks.md)（知識庫）與 [06](06-自己發事件.md)。
