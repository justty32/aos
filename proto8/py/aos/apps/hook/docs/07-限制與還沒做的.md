## 已知限制

| 限制 | 說明 |
|---|---|
| 每發一次 `aos-hook fire`＝起一支 Python | 沒人掛約 36 毫秒；loop 接了 `before_run` 等於每跑一次身體多一支（閒著的 agent-fsm 每秒 3 支）。要定時做事用 `on_clock`（在格程式裡判，沒到約 40 微秒）。Python 寫的發事件程式直接 import 引擎就沒有這筆 |
| 事後掛 `before_run`／`after_run` 不會立刻生效 | 要重新編譯並重起（使用者「編譯時決定」）；`aos-agent hook add` 只多印一行 warning |
| `aos-hook fire` 每個 handler 拿同一份資料 | 不串改；eca 的 before_compact 因此是「依名字順序後蓋前」，不是 agent-fsm 那種前一個改的後一個看得到 |
| loop 四點的 handler 拿不到 condition、事件欄位很少 | 事件只有 `event`、`hook`、`stack`；其餘自己讀 `AOS_LOOP_*` 與 `<stack>/stage.txt` |
| `after_run` 退 10 也算失敗、loop 收工 | 施工線的選擇（[施工 02 第 3 條](../../../../../thinking/2026-11/21/hook-新格式施工-1121/02-替使用者做的選擇.md)）：碼原樣交給 aos-loop |
| stdin 是一條不關的管子時 `aos-hook` 會一直等 | 它讀 stdin 到底；從別的程式起要給 JSON 或 `/dev/null`。前景跑 aos-loop 時的 on_start 會碰到 |
| 連鎖觸發不檢測 | hook 寄信給自己又觸發 queue 的 hook、handler 裡再叫 `aos-hook fire`，都不擋 |
| 誰都能替別人的 stack 發事件 | 不擋（同一個 Linux 帳號） |
| eca 看不到 CLI 自帶的工具 | `before_tool`／`after_tool` 只有經 aos-mcp 的 aos 工具；擋 Bash 之類用 Claude Code 自己的 hook |
| eca 的壓縮：hook 換不了摘要 | Claude Code 沒有那個口子；`restore` 只能在 `before_compact` 交 |
| 宣告與程式的規矩是兩份 | 宣告是手抄給人看的，靠測試 `test_hook_points_match` 對齊；程式不讀宣告（只有 `aos-gdb` 帶 `--hooks`／`--def-hooks` 時拿來當參考） |
| `kernel_hookeds.json` kernel 只讀定義夾那份 | kernel 三點不疊 stack 抄本（loop 四點經 `--def` 會疊） |

## 沒問過使用者、照施工線的讀法做的

- 「宣告只是參考」涵蓋到哪：現在所有程式都不因宣告擋人；但 agent 要有 `hookeds`（被勾清單）才掛得上 hook（`HooksMissing`），那是清單不是宣告。
- 最外層 `"kernel": {}` 裡放什麼：目前空的。
