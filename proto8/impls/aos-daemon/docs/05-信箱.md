### 信箱（N-28、N-16）

多個人要改名單時，不必搶寫同一份 `procs_ctl.json`：daemon.json 沒寫 `procs_requests` 就開在 `$AOS_STACK/procs_requests/`（寫別的名字＝開在那、寫 `null`＝不開；名字回報在 `procs_state.json` 的同名欄），大家各自投一封信（[aos-post](../../aos-post/README.md) 的 `send`），daemon 每圈收。
跟 procs_ctl 可以同時開（procs_ctl 沒寫＝預設 `procs_ctl.json` 照開；寫 `null`＝不開）：**信是一次性的改動，改的是底**；**procs_ctl 是宣告，每圈疊在底上**；同一圈先套完信、再疊 procs_ctl、再對表。

```sh
echo '{"procs_added": {"bob": "../agents/bob"}}' | aos-post send "$AOS_STACK/procs_requests"   # 加 bob（字串＝exec 型）
echo '{"procs_stopped": ["ann"]}' | aos-post send "$AOS_STACK/procs_requests"                  # 停 ann
echo '{"procs_removed": ["bob"]}' | aos-post send --reply-to 我的信箱 "$AOS_STACK/procs_requests"   # 刪 bob，套用完回一封 {"applied": true}（壞信回 applied: false）
```

- **起來時**：`aos::post::init` 建好 `tmp/`、`new/`、`cur/`（已在就沿用；`$AOS_STACK` 在但不是資料夾＝`MkdirFailed`、init 不替人建；`$AOS_STACK` 不在的話 daemon 起來時已先建好，見 [01](01-用法.md)）。
- **底**＝daemon.json 的 `procs`＋重起時 adopt 接回、不在 daemon.json 裡的（只留名、設定記 null，不會被重起；`stopped` 的列 start 時照 proc 的 stack 裡的 `loop.json` 起）＋依序套用的每封信；
  **接回的留在名單上，直到有信把它 `procs_removed`、或它結束**。自己結束（`done`）的從底一併拿掉；之後再有信同名 `procs_added`＝重新起。
- **每圈**（`stop`／`pause` 那圈不認領，信留在 `new/`，解除暫停那圈才套）：`new/` 全部認領（`aos-post take-all`，照處理順序：有序在前、照名字）→ 逐封驗、好的依序套進底（後面的蓋前面的）→ **全部套完、疊上 procs_ctl 才對一次表** →
  有 `reply_to` 的好信回一封 `body: {"applied": true}`、壞 body 的回 `{"applied": false, "error": {"code": "BodyBad", "msg": …}}`（見下面「壞信」；`in_reply_to`＝原信的信件名稱）→ 信收掉（`aos-post done`，不留 `archive/`）。起來時 `cur/` 不空（上次認領了、沒收完就死）＝照處理順序排在 `new/` 的前面重做。
- **信的 `body`**：物件，只認 `procs_added`（寫法同 `procs`）、`procs_removed`、`procs_stopped`、`procs_started`、`procs_slept`、`procs_woken`（名字的陣列）、`ping`（下一條）、`procs_state_path`（再下一條），其他 key 忽略（舊名 `loops_added`、`execs_added`…也是）；
  一封裡的套法：`procs_added`→`procs_removed`（名單與 stopped 集合都拿掉）→`procs_stopped` 加進集合→`procs_started` 從集合拿掉→`procs_slept` 加進 slept 集合→`procs_woken` 從 slept 集合拿掉（同名兩邊都寫＝醒）。沒有整份的 `procs`（整份宣告留給 procs_ctl）。相對的 `exec`、`ws`、`stack`、`def`、`$ref` 都從 daemon 的 cwd 算。
- **`{"ping": true}`＝問 daemon 在不在**（no-pid P2，[thinking no-pid](../../../thinking/2026-11/05/no-pid/README.md)）：不改底（名單、stopped／slept 集合都不動）；有 `reply_to` 回 `{"applied": true}`；收了信就算一次有反應（`responded_at` 更新，見 [04](04-兩個手把-兩扇狀態窗.md)）。`ping` 不是 `true`＝壞信（`mailbox_warning` 的原因寫 `... ping must be true`；有 `reply_to` 回 `applied: false`、`BodyBad`）。`ping` 跟其他 key 一起寫＝其他照常套。
  **paused／stopping 那圈不認領信＝不回**：寄信的人等到逾時就當這次呼叫失敗（no-pid 裁定「寄信不回＝呼叫失敗」），不去猜它是忙、不認得還是掛了；想知道為什麼，讀它的 `state.json`。最常用一行（`BOX` 先 `aos-post init`），回信 1 秒內出現在 `BOX/new/`：

  ```sh
  echo '{"ping":true}' | aos-post send --reply-to BOX $AOS_DAEMON/procs_requests
  ```
- **`{"procs_state_path": true}`＝問這台的表在哪**（11-13，[kernel 框架 03](../../../thinking/2026-11/12/kernel-framework/03-狀態查詢信.md)、K-F27）：不改底；有 `reply_to` 的回信多帶同名的 key——`{"applied": true, "procs_state_path": "/絕對路徑/procs_state.json"}`（`$AOS_STACK` 照字面轉絕對、不解捷徑；`procs_state` 窗設成 `null` 沒開＝值是 `null`）。可以跟別的 key 寫在同一封（例如跟 `procs_added` 並寫＝照常套、回信一樣帶路徑）。寫了卻不是 `true`＝壞信（原因 `procs_state_path must be true`，回 `BodyBad`、整封不套）。沒帶 `reply_to`＝沒人收得到答案。
  ```sh
  echo '{"procs_state_path":true}' | aos-post send --reply-to BOX $AOS_DAEMON/procs_requests
  ```
- **壞信**＝信封壞（`aos::post::see`）、`body` 不是物件、型別錯（含 `ping`、`procs_state_path` 不是 `true`）、`procs_added` 的項不合格、指示詞解不開：
  **丟掉、不套**，原因寫進 `state_flux.json` 的 `mailbox_warning`（`"letter <信件名稱> rejected: <原因>"`，最後一封壞信的；之後的圈沒有壞信就維持原值）；不影響同一圈的好信。
  **body 壞的也回信**（[kernel 討論 11-11](../../../thinking/2026-11/11/kernel/README.md) 裁定「改成會回」；[記錄](../../../thinking/2026-11/12/kernel-small-fixes.md)）：有 `reply_to` 的回 `{"applied": false, "error": {"code": "BodyBad", "msg": "<原因>"}}`（形狀同框架站拒信；`msg` 跟 `mailbox_warning` 冒號後那段同一句）；沒寫 `reply_to`＝沒地方回、只記 `mailbox_warning`；**信封壞的**讀不到 `reply_to`，不回、只記 `mailbox_warning`。aos-agent ctl、aos-daemon-ctl（沒給 `--reply-to` 時）收到就立刻報錯、不等到逾時。
- 回信寄不出去、收信失敗都不管，照樣往下走。要知道「加進去了沒」的標準做法是讀 `procs_state.json`。誰能寄：純靠 Linux 檔案權限（N-54 末）。

### 子項的工作區 ws

- **寫在哪**：proc 的**物件**多一個選填 key `ws`（字串或陣列寫法沒地方寫，要 ws 就寫成物件；exec 型物件 `{"exec", "ws"}` 仍是 exec 型）。daemon.json、procs_ctl 的 `procs`／`procs_added`、信都認。
- **值**：非空字串（指示詞照解）；**相對路徑從 daemon 的 cwd 算**，轉成絕對路徑（`abspath`）存進期望表。`null`＝當沒寫。其他型別、空字串＝壞（`CfgBad`／不採用／壞信）。在不在不驗（不在＝子項經 aos-exec 報 `WsMissing`）。
- **起子項時**：子行程的環境多設 `AOS_WS=<ws>`；**沒寫＝繼承 daemon 的環境**。loop 型的 `ws` 不寫進 `loop.json`，只進環境。`ws` 跟 `stack` 各管各的（`AOS_WS`／`AOS_STACK`）。
- **改了 ws**＝設定變了：已在跑的不重起、環境不變。列與 log 那兩行，起它時給了 `ws` 就多一欄 `"ws"`（起的那一刻的值）；沒給不寫這欄。`adopt` 照表上那列的 `ws` 留著。

### 子項的 AOS_DAEMON（11-04 晚改名）

daemon 起子項（loop 型、exec 型都算）時，子行程的環境多設 **`AOS_DAEMON`＝daemon 自己的 stack**（`$AOS_STACK` 轉成絕對、結尾補 `/`，建構時算好 `dstack_`），**只設這一個**，一律蓋過去（使用者 11-04 晚「AOS_DAEMON_STACK實在太醜，還是直接簡化成AOS_DAEMON就好了」）；`ws`、`stack` 都不影響它。
用處：兄弟（常駐 bob 的控制器與 bob）靠它找到共同的 daemon——讀 `procs_state.json`、叫 `aos-daemon-ctl`。
**daemon 自己的身體（`exec`）也拿得到**：daemon 起來就把自己行程的 `AOS_DAEMON` 設成自己的 stack（同一個值），身體繼承（[thinking 11-05 kernel-daemon 02 § 1](../../../thinking/2026-11/05/kernel-daemon/02-兩種模式.md) 模式 1「繼承式」：框架站、llm kernel 當身體時靠它找自己這台的 ctl 信箱；身體是 daemon 起的，照 N-64 ④ 同一句）。條文在 [N-63、N-64 ④](../../../docs/NORMS/10-基礎設施-定義與工作區.md)。
**蓋掉之前先記下來**（no-pid P2，[thinking no-pid](../../../thinking/2026-11/05/no-pid/README.md)）：繼承到的 `AOS_DAEMON`＝管這台的上一層 daemon，照字面記進兩扇窗頂層的 `daemon` 欄（沒設、空、或解開後就是自己＝`null`＝根 daemon），見 [04](04-兩個手把-兩扇狀態窗.md)。

### 指示詞與切檔（N-28、N-45）

- **daemon.json、ctl 與 procs_ctl 的指示詞**（使用者「aos 讀的 JSON 全部支援」）：同 aos-loop 只解自己讀的格——再加 `procs`（本身、每項本身）、`adopt`、`procs_ctl`、`procs_state`、`procs_requests`；
  項是目標＝整個解；是物件＝只解 `exec`、`max`、`interval_ms`、`ctl`、`state`、`state_flux`、`ws`、`stack`、`def`（搬進 proc 的 stack 後相對 `$ref` 會從 proc 的 stack 算，所以 daemon 先解），其他 key（`body`…）原樣。
  相對 `$ref` 從寫著它的那份檔所在的資料夾算（daemon.json 的資料夾；ctl、procs_ctl＝`$AOS_STACK` 底下那份的資料夾）。解不開：daemon.json＝`DirectiveBad` 退 1；ctl、procs_ctl＝不採用。
  **例外（two-machines B07）**：daemon.json 的 `procs` 裡**某一列**（`procs.<名>` 本身或它認的格）解不開（例 `{"$ref": "another/x.json"}` 那份檔不在、`$env` 的變數沒設）＝只有那列留 `stopped`、`reason` 寫 `cannot resolve directives in the daemon config (procs.<名>): <原因>; fix it, then restart this daemon`，stderr 一行 `aos-daemon: warning: procs.<名> in <設定檔>: cannot resolve directives: …; leaving it stopped, the other procs start …`，**其他列照起**。daemon.json 只在開門讀一次：改好檔要重起 daemon，那列就照常起（不用另外 `start`；認 reason 裡那句開頭）；沒重起前 `start` 它＝仍 `stopped`、reason `failed to start: DirectiveBad …`。同名的列已經接回而且還活著＝照跑、不去停它。`procs` 本身那層寫成單一 `{"$ref": "procs.json"}` 而那份讀不到＝整台 `DirectiveBad` 退 1（整份名單都不知道）；列的形狀不對（`CfgBad`）也退 1。
  **`$ref` 陣列其中一份讀不到（使用者選「跳過那份」）**：`"procs": {"$ref": ["one.json", "two.json"]}` 其中一份不在（或解不開）＝那份從陣列拿掉、它帶的列不起（daemon 不知道它們叫什麼，表上不會有這些列），stderr 一行 `aos-daemon: warning: procs in <設定檔>: cannot resolve directives: $ref cannot read …/two.json; skipping that file (its procs do not start), the other procs start (fix it, then restart this daemon)`，其他份照合、照起；全部讀不到＝空名單、daemon 照起。補好檔重起 daemon 那份的列就照常起。已經接回而且還活著的同名列照跑。只放寬 daemon 讀 daemon.json 的程序清單這一處；`$ref` 機制本身（aos-directive）別處缺檔就 `DirectiveBad`，procs_ctl、信也整份不採用。
  **`$ref` 進來那份檔裡的路徑**（B08；使用者 11-11 裁「維持現狀」，原話「喔不對，$ref是最底層機制，都是先用$ref弄好後，最後產出的那個檔，再拿去使用。最後產出的這個檔案就是不管$ref啥的了，就當作這是整份」——`$ref` 先把幾份接成一整份，daemon 讀的是接好的那整份，接進來的內容跟直接寫在 daemon.json 裡一樣看待）：`$ref` 的檔名本身從寫著它的那份檔算；但那份檔裡 proc 的 `exec`、`ws`、`stack`、`def` 的相對路徑**從 daemon 的 cwd 算**（＝引用它的那一邊，不是那份檔的資料夾）。例：`daemon.json` 寫 `"a": {"$ref": "another/a.json"}`，`another/a.json` 寫 `{"exec": "agents/a"}`＝`<daemon 的 cwd>/agents/a`，不是 `another/agents/a`。寫錯時小格 `stderr.txt` 的 `EntryMissing` 會印「從哪算、解成什麼」（見 aos-exec [05](../../aos-exec/docs/05-錯誤代號等.md)）。
- **`procs` 拆成好幾份**（使用者「當loop太多的時候，json超大，我會希望他會自動用$ref切，每個檔案一百個」）：用 `$ref` 陣列（aos-directive，N-45）——幾份照順序合成一份物件，同名後面的蓋前面的；
  合不起來＝`DirectiveBad`、合出來不是物件＝`CfgBad`。不拆也能整份 `"procs": {"$ref": "procs.json"}`。每項裡的相對 `$ref` 從它來自的那份檔的資料夾算。
- **procs_state 自動切檔**：`procs` 表超過 100 列（`PART_ROWS`，不開 key）才切，每份最多 100 列、照表的順序；100 列以內維持物件：

  ```json
  {"procs_requests": ..., "daemon": ..., "procs": {"$ref": ["procs_state_procs/3f9a2c1e07d45b6a.json", "procs_state_procs/<雜湊>.json", ...]}, "pid": ..., "updated_at": ...}
  ```

  分檔資料夾＝procs_state 檔名去副檔名＋`_procs`、跟它同一層（預設 `procs_state_procs/`）；檔名＝內容的 FNV-1a 64 雜湊。每份先寫 `.` 開頭暫存再改名，內容沒變的沿用不重寫；
  分檔都寫好才寫主檔（**主檔改名是唯一的提交點**）；寫完清掉這次與上一次主檔都沒用到的分檔（行程第一次寫時不清），上一次的那些等下一次要寫但沒變的那一下再清；縮回 100 以內、清空後拿掉資料夾。
  讀的人用 aos-directive 解主檔（`aos-directive < procs_state.json`，cwd＝它的資料夾）就拿回整張 `procs` 物件。`adopt` 也是這樣解。
