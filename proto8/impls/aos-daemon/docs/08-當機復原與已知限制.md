## 當機復原與已知限制

使用者 11-05 午：「你繼續多測試一些邊緣狀況吧。」邊緣狀況實測（跨元件、時間軸、壓力）見 [edge-round2](../../../thinking/2026-11/05/edge-round2/README.md)。

### daemon 沒走收工就死了（kill -9、斷電、`wsl --shutdown`、OOM）

- **表上 running、行程已不在**：adopt 拿不到結束碼，不分起法、照自然結束下表；auto_restart 的照樣重起。表上已有 stopped／sleeping 的照接回；重開仍依 daemon.json 名單起缺項。
- **表上 stopping**：依表內 `stop_mode` 接著收：stop 重新寫 ctl 並等自行退，sleep／remove 送 SIGTERM；sleep 退後留 sleeping、stop 留 stopped、remove 下表。收工時 running 的睡下（sleeping），stop 途中的留 stopped，sleep 途中的睡下，rm 途中的拿掉；收工途中被 kill -9，重開時照表上的 `stop_mode` 做，結果一樣。
- **起任何 proc 前看公開 state 窗**：proc 的 stack 裡子 loop 自己的 state 窗記的 pid＋`started_at_ticks` 對得上一支活著的＝接回、不另起一份（上一個 daemon「fork 了、表還沒寫」就死的那種）。接回的拿不到結束碼，退了下表（同 adopt）。
- **別棵樹的行程不接**（two-machines，使用者准「1.可以」）：pid＋`started_at_ticks`＋`boot_id` 都對上，還要看 `/proc/<pid>/environ` 的 `AOS_STACK`／`AOS_DAEMON`（解開捷徑）有一個是那一格或這台 daemon 的 stack；都指到別處（那裡還在）＝別棵樹的（同一台把還在跑的樹 `cp -a` 再起副本，表上記的是原樹的行程）＝當沒在跑：running 的列照收工那樣睡下、第一圈照起，不碰那支行程；起任何 proc 前看公開 state 窗（上一條）也一樣比。讀不到 environ（權限）、沒這兩個名字、指到的地方都不在（整棵樹搬走了）＝照前面比 pid＋`started_at_ticks`＋`boot_id` 的規則接回。
- **重開機過**（no-pid P1）：上次的表頂層 `boot_id` 跟這次開機不同（或沒寫）＝表上的行程都當不在了，不比 pid＋ticks（重開機後可能撞上別的行程）；這台讀不到 boot_id＝只比 pid＋ticks。公開 state 的 boot_id 也比對（P9）。
- **resume 那一圈先寫 state**（`paused: false`）與 state_flux（新的 `ctl_seq`）再套信對表，讓對外狀態先反映已套用的指令；未套用的 resume 再起後第一拍也會照做。
- **`state_flux.json` 被刪或寫壞**：要先手動清掉 `ctl.json` 再起 daemon，否則它會照 `ctl.json` 裡的舊 stop，一起來就停；放在 systemd 之類自動重起底下，就會變成起了又停的迴圈（使用者裁定：維持現狀、文件寫明）。
- **`procs_state.json` 寫不了**（stack 唯讀、磁碟滿）：不退（[edge-round2 題 1](../../../thinking/2026-11/05/edge-round2/README.md) 裁定）——stderr 一行、下一圈再寫、proc 照顧著（[06](06-結束碼等.md#結束碼)）。這段期間 daemon 被 kill -9＝磁碟上是最後寫成的那份，再起時照上面幾條接回；之後才加、信已收掉的那幾個不會回來（信還在 `cur/` 的會重套）。

### 一個 proc 的 stack、信箱出問題時不整台停

- **daemon 的 stop 寫不了子 loop 的 ctl**（proc 的 stack 唯讀）：不整台退，stderr 一行提醒 `aos-daemon: warning: cannot stop X through its ctl (…); waiting for it to exit`，那一列留 `stopping` 等自行退，退了留 `stopped`；不因寫不了就改送 SIGTERM。
- **信箱認領不了**（`new/` 唯讀）：不整台退，記進 `mailbox_warning`（`cannot take letters: …`）、下一圈再試。
- **收工途中又起一台**：`DaemonExists the daemon on this stack (…) is shutting down; start again after it exits`（不印 pid，只看 `state.json` 的 `phase`）。

### reason 的細節（接 [03](03-起-停-暫停.md)「出錯結束一律留」）

- 只看**這一支起來之後**寫進 `stderr.txt` 的（不引到前幾輩子的話）；`stderr.txt` 被截短過（copytruncate）就看整份。起點不在檔頭、又不是接在換行後面（截短後又長回超過起點，可能切在一行中間）＝從下一個完整的行開始取；後面沒有別的行就退回那一行的行首、取整行，不留半截。用 `truncate -s` 截在一行中間、子項接著寫，新的一行會黏在舊的半截後面（附加寫的本性，daemon 分不出來）；要截就截到 0 或截在換行後。
- 只取最後非空行，不依程式名或錯誤字句跳過任何行（K-2）。控制字元（CR、ESC 色碼、TAB…）換成空白；切 300 位元組時不切在 UTF-8 字中間，長行也照這個上限處理。
- **add 剛起的也算「起來」**：3 秒內退＝`failed to start: exited within 3s of wake/start…`（不是 `failed while running`）。3 秒從 daemon「看到它退了」那一刻算，最多晚一個 `interval_ms`。

### 已知限制（風險自擔，沒改）

- **proc 的 stack `stderr.txt` 沒有上限、不輪替**：子項每 10 毫秒印一行約每秒 3 KB、一天約 277 MB。要截就 `truncate -s 0`（copytruncate；daemon 用附加寫，截了從 0 接著寫、不留空洞）。**交給清道夫**：表上掛一列 `_sweeper`（[cmd/aos-sweeper](../../../cmd/aos-sweeper/README.md)，範本 daemon 預設帶），每 10 分鐘把 ≥ 1 MiB 的 `stderr.txt` gzip 封存到同 stack 的 `stderr_archives/` 再截成 0，封存預設留 7 天；手動 `aos-daemon-ctl sweep`、全刪 `aos-daemon-ctl sweep --purge`。清道夫一律截到 0、不留尾巴；最後一次複製到截的那一瞬間寫進來的幾行會掉（copytruncate 固有的小窗，實測每秒約 400 行時 0 遺失）。每台 daemon 只管自己表上的列，沒掛的那台沒人清。
- **表很大時每拍的 CPU 跟列數成正比**（每拍組一次整張表比有沒有變）：4300 列、`interval_ms` 10＝閒著 82%；200 個 running、`interval_ms` 200＝0.4%。表大就把 `interval_ms` 調大；**`interval_ms: 0` 會吃滿一顆 CPU**，身體又一直失敗時每秒重跑約 500 次。
- **身體一直失敗**：「碼變了才印」只管 daemon 自己那行；身體自己的 stderr、aos-exec 的錯（例 `EntryMissing`）每圈照印；碼在兩個值之間交替＝每圈都印。
- **INT／TERM／HUP、poke 三訊號、USR1／USR2 以外的訊號**（例 SIGRTMIN+4 以後、SIGALRM）＝照系統預設直接死、不收工，同 `kill -9`（再起照上面接回）。USR1／USR2 擋住、不理（[thinking daemon-interrupt](../../../thinking/2026-11/09/daemon-interrupt/README.md)）。
- **身體跑的期間 poke 不打斷**：身體是一支程式（`run_folder`）或內嵌單子（`run_inline`）都一樣，poke 排在 kernel 裡，身體跑完立刻補看；要身體馬上停，用 ctl `stop` 加 Ctrl-C／SIGTERM。
- **daemon 的 stop 沒有時間上限**（等子 loop 跑完這一次）：子 loop 被 SIGSTOP、身體卡死＝列一直 `stopping`，這時可下 `sleep` 改送 TERM、10 秒後仍在就 SIGKILL，退後保留 `stopped`、stack 與 launch，用 `start` 再起；`stop`／`start` 仍是 `PhaseBad`，`rm` 也會送 TERM、10 秒 SIGKILL，但拿掉列。
- **procs_ctl.json 是宣告、蓋過信**：它的 `procs` 或 `procs_added` 裡有（`procs_removed` 沒有）的名字，寄 `procs_removed`（`aos-daemon-ctl rm`）照收信、退 0，但下一圈又被疊回來、照跑。套這封信時 stderr 印一行 `aos-daemon: warning: letter <信的 id> removed <名字>, but <procs_ctl 路徑> still declares it, so it comes back next round; to really remove it, take it out of that file`——一封信一個名字只印一次，之後每圈不印；再寄一封 rm 再印一次（daemon 重開時重做 `cur/` 裡沒收完的信也算一封）。要真的拿掉，改 procs_ctl.json。**刪掉 procs_ctl.json＝什麼都沒宣告＝回初始值**（不沿用最後一份好的，N-06；前一份 state_flux 的 `procs_ctl_warning` 也一起清掉）。
- 起一大批時 `procs_state.json` 最多每 200 毫秒寫一次（每起一列寫一次整張表的話，表上千列、一批上千封信＝平方慢）；切檔的舊分檔退役後留 2 秒才刪（daemon 一秒寫好幾次表時，讀的人剛讀到的主檔可能已是兩次以前的）。
