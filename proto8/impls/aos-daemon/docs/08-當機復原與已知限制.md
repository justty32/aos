## 當機復原與已知限制（11-05 第二輪）

使用者 11-05 午：「你繼續多測試一些邊緣狀況吧。」第二輪實測（跨元件、時間軸、壓力）修的與只寫一句的，見 [edge-round2](../../../thinking/2026-11/05/edge-round2/README.md)。

### daemon 沒走收工就死了（kill -9、斷電、`wsl --shutdown`、OOM）

- **表上 `running`、行程已不在的列**：原本整列悄悄丟掉（信加的 proc 從此不見）。現在 **loop 型接成 `sleeping`、第一圈 wake**（同一個 stack 接著做，同收工後開門）；子 loop 自己的 state 窗寫 `done`（自己跑完了）的照舊不接；exec 型照舊不接。
- **表上 `stopping` 的列**（上一個 daemon 正在收它：stop 在等它跑完、sleep／rm 送了 TERM、收工途中）：原本不接＝行程照跑、表上看不到，daemon.json 裡的還會在同一格再起一份。現在**還活著的接回來接著收**（SIGTERM、10 秒 SIGKILL 整群）；退了（或本來就不在）＝上一個 daemon 死時在收工（它的 state 窗 `phase` 是 `stopping`）的留 `sleeping`，其他留 `stopped`——看不出當初是 stop、sleep 還是 rm，一律停著、看得到：要的 `start`，不要的再 `rm` 一次（代定）。
- **起 loop 型之前看小格**：小格裡子 loop 自己的 state 窗記的 pid＋`started_at_ticks` 對得上一支活著的＝接回、不再起一份（上一個 daemon「fork 了、表還沒寫」就死的那種；原本同一格兩支 aos-loop）。接回的拿不到結束碼，退了照舊下表（同 adopt）。
- **重開機過**（11-06 no-pid P1）：上次的表頂層 `boot_id` 跟這次開機不同（或沒寫）＝表上的行程都當不在了，不比 pid＋ticks（重開機後可能撞上別的行程）；這台讀不到 boot_id＝照舊只比 pid＋ticks。「起 loop 型之前看小格」那條還沒比 boot_id。
- **resume 那一圈先寫 state**（`paused: false`、新的 `ctl_seq`）再套信對表：原本對完一大批信才寫，這中間死掉再起＝照舊 state「起來先暫停」、ctl 裡那道 resume 又被當基準線＝一直停著。
- **`procs_state.json` 寫不了**（stack 唯讀、磁碟滿）：（11-05 起，[edge-round2 題 1](../../../thinking/2026-11/05/edge-round2/README.md) 裁定）不再退 1——stderr 一行、下一圈再寫、proc 照顧著（[06](06-結束碼等.md#結束碼)）。這段期間 daemon 被 kill -9＝磁碟上是最後寫成的那份，再起時照上面幾條接回；之後才加、信已收掉的那幾個不會回來（信還在 `cur/` 的會重套）。

### 一個小格、信箱出問題時不再整台停

- **daemon 的 stop 寫不了子 loop 的 ctl**（小格唯讀）：原本整台退 1、全部 proc 收掉；現在 stderr 一行 提醒行 `aos-daemon: warning: cannot stop X through its ctl (…); sending SIGTERM instead`，那一支改送 SIGTERM，退了照樣留 `stopped`。
- **信箱認領不了**（`new/` 唯讀）：原本整台退 1；現在記進 `mailbox_warning`（`cannot take letters: …`）、下一圈再試。
- **收工途中又起一台**：`DaemonExists the daemon on this stack (…) is shutting down; start again after it exits`（原本叫人「沿用」它；11-06 起不印 pid，只看 `state.json` 的 `phase`）。

### reason 的細節（接 [03](03-起-停-暫停.md)「出錯結束一律留」）

- 只看**這一支起來之後**寫進 `stderr.txt` 的（原本整份檔的最後一行，會引到前幾輩子的話）；`stderr.txt` 被截短過（copytruncate）就看整份。
- 控制字元（CR、ESC 色碼、TAB…）換成空白；切 300 位元組時不切在 UTF-8 字中間。一行 30 KB 以上原本會讓 daemon SIGSEGV（regex 遞迴），已改手寫比對。
- **add 剛起的也算「起來」**：3 秒內退＝`failed to start: exited within 3s of wake/start…`（原本寫成 `failed while running`）。3 秒從 daemon「看到它退了」那一刻算，最多晚一個 `interval_ms`。

### 已知限制（風險自擔，沒改）

- **小格 `stderr.txt` 沒有上限、不輪替**：子項每 10 毫秒印一行約每秒 3 KB、一天約 277 MB。要截就 `truncate -s 0`（copytruncate；daemon 用附加寫，截了從 0 接著寫、不留空洞）。
- **表很大時每拍的 CPU 跟列數成正比**（每拍組一次整張表比有沒有變）：4300 列、`interval_ms` 10＝閒著 82%；200 個 running、`interval_ms` 200＝0.4%。表大就把 `interval_ms` 調大；**`interval_ms: 0` 會吃滿一顆 CPU**，身體又一直失敗時每秒重跑約 500 次。
- **身體一直失敗**：「碼變了才印」只管 daemon 自己那行；身體自己的 stderr、aos-exec 的錯（例 `EntryMissing`）每圈照印；碼在兩個值之間交替＝每圈都印。
- **INT／TERM／HUP 以外的訊號**（USR1、USR2…）＝照系統預設直接死、不收工，同 `kill -9`（再起照上面接回）。
- **daemon 的 stop 沒有時間上限**（等子 loop 跑完這一次）：子 loop 被 SIGSTOP、身體卡死＝列一直 `stopping`，這時 stop／sleep／start 都是 `PhaseBad`（提示會說卡住就 `rm`）；`rm` 送 TERM、10 秒 SIGKILL 收得掉。
- **procs_ctl.json 是宣告、蓋過信**：它的 `procs_added` 裡有的名字，寄 `procs_removed`（`aos-daemon-ctl rm`）照收信、退 0，但下一圈又被疊回來、照跑（沒有 warning）。**刪掉 procs_ctl.json＝什麼都沒宣告＝回初始值**（11-05 第二輪修：原本沿用最後一份好的，跟 N-06 不符；前一份的 `ctl_warning` 也一起清掉）。
- 起一大批時 `procs_state.json` 最多每 200 毫秒寫一次（原本每起一列寫一次整張表：表上千列、一批上千封信＝平方慢，1500 封要 20 幾秒、Ctrl-C 要 30 秒才理）；切檔的舊分檔退役後留 2 秒才刪（daemon 一秒寫好幾次表時，讀的人剛讀到的主檔可能已是兩次以前的）。
