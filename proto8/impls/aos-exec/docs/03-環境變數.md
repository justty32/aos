### 環境變數（定義在 N-57；照 P-39 分三類；六個 `AOS_*` 加 PATH）

| 變數 | aos-exec 做什麼 | 類別 |
|---|---|---|
| `AOS_ENTRY` | aos-exec 自己只讀、不設；沒設（或空）＝`_entry`。資料夾裡與 JSON 裡用同一個名字；每次挑入口都重讀（`.env` 可能剛改過它） | 繼承 |
| `AOS_WS` | 每跳設：WS 的絕對路徑（`--ws` 給的，每讀完一份 `.env` 都蓋回去） | 叫別人時明給 |
| `AOS_STACK` | `--stack` 給的（每讀完一份 `.env` 都蓋回去）＞ 有設沿用 ＞ `$AOS_WS/.stack/`；相對的從呼叫當下的 cwd 算；都 mkdir -p、轉絕對、結尾 `/` | 叫別人時明給 |
| `AOS_CF` | 每跳覆寫：實際被執行的檔（解開捷徑的絕對路徑，不帶 `#/…`；往下走進 JSON 物件時不變；字串轉向後＝最後那個檔）。走進資料夾時先＝那個資料夾 | 每層覆寫 |
| `AOS_CD` | 每跳覆寫：`AOS_CF` 所在的資料夾＝cd 進去的地方 | 每層覆寫 |
| `AOS_CO` | 每跳覆寫（aos current obj）：入口在那份 JSON 檔裡的位置，JSON 指標、不帶 `#`（例 `/a/_entry`；`檔#/指標` 也算在內，之後每挑一格接 `/` 加照 `~0`／`~1` 跳脫的 key）；整份檔就是入口、或可執行檔＝空。走進資料夾時先設空 | 每層覆寫 |
| `PATH` | aos-exec **不動**，原樣傳下去（使用者「也套用，都不動path吧」）；要改由 `.env` 自己寫（`PATH=${AOS_CD}/bin:${PATH}`）。入口裡要寫 `aos-exec 別的`、`aos-loop`…，由呼叫者事先把那幾支的 `bin/` 放進 PATH | 繼承 |

最後讀的那一份 `.env` 自己設了 `AOS_CF`／`AOS_CD`／`AOS_CO` 的，挑完入口不蓋（見上面一跳的第 7 步）。

### inst 單子

**認 16 個 key，其他一律忽略**（10-19 的 10 個；11-04 補 `id`、`envs_clear`、`cwd_mkdir`、`stdout_mkdir`、`stderr_mkdir`、`stderr_merge`，使用者題 9「aos-exec 補認那 7 個」——schema 那份 17 個裡的 `flag` 不是 key）。

| key | 型別 | 沒寫 |
|---|---|---|
| `argv` | 非空字串陣列（必填）；args 接在後面 | — |
| `cwd` | 字串路徑，從入口所在的資料夾算 | 入口所在的資料夾 |
| `envs` | `{名: 字串}`，疊在現有環境上 | 沿用現有環境 |
| `stdin`／`stdout`／`stderr` | 字串路徑（`null`＝沒寫），從解出來的 `cwd` 算；stdout／stderr 覆寫 | **接呼叫者的**（aos-exec 自己的 fd 0／1／2） |
| `stdout_append`／`stderr_append` | true／false：改附加 | false |
| `timeout_ms` | 正整數或 `null`：到了先 SIGTERM **整群** | 不限 |
| `grace_ms` | 非負整數：SIGTERM 後等多久再 SIGKILL 整群（0＝直接 SIGKILL） | 2000 |
| `envs_clear` | true／false：不疊現有環境，子程式只拿到 aos-exec 的六個 `AOS_*`（有設的）＋`envs`；**`PATH` 也不留**（要就寫進 `envs`） | false |
| `cwd_mkdir` | true／false：先 `mkdir -p` 解出來的 `cwd`；建不了＝`MkdirFailed` | false（cwd 不在＝`LaunchFailed`） |
| `stdout_mkdir`／`stderr_mkdir` | true／false：先 `mkdir -p` 那個檔的上層資料夾；建不了＝`MkdirFailed`；沒寫那個串流＝不做事 | false |
| `stderr_merge` | true／false：stderr 併進 stdout（libaos 的 `merge`）；又寫了 `stderr`＝`LaunchFailed`（`PathConflict`） | false |
| `id` | 標籤，什麼型別都收、不看 | — |

- **先解指示詞再驗**：單子裡任何位置的 `{"$env": 名}`、`{"$ref": "檔#/指標"}`（位置只認 `#/`），可帶 `$path`（`join(值, $path)`）、`$prefix`（接在前面）
  先換掉（aos-directive，規則見它的 README 與 N-45；`$path` 是字串拼接）。在 aos-exec 設好六個環境變數、讀完 `.env` 之後才解，所以讀得到 `AOS_STACK`、`AOS_CF`、`AOS_CD`、`AOS_CO` 與 `.env` 設的值
  （例 `"stdout": {"$env": "AOS_STACK", "$path": "out"}`）。`$ref` 的相對檔名從入口檔所在的資料夾算（命令列不給 `run_inst` 的 `ref_base`，沿用 `base_dir`＝入口檔所在的資料夾）。
- **`argv[0]` 帶 `/` 又 exec 不了＝前面插 `aos-exec`**（從解出來的 `cwd` 看），`aos-exec` 照子程式的 PATH 找，找不到＝`LaunchFailed`（`CommandMissing`）。
- **型別不對**＝`EntryBad`（單子就是入口）；指示詞解不開（`$env` 沒設、`$ref` 讀不到或指到資料夾、指不到、繞圈）＝`DirectiveBad`；libaos 起不來＝`LaunchFailed`，原因是 libaos 的名字開頭
  （`CommandMissing`、`CommandBad`、`CwdMissing`、`OpenFailed`…；`OpenFailed` 時 aos-exec 不動檔地再看一次，說是哪個串流、哪個路徑、為什麼，例「stdout …/b.txt 開不了：上層資料夾不在（要自動建就加 stdout_mkdir: true）」；`PathConflict`＝「stderr_merge 是 true 又寫了 stderr」）；收不到結果＝`Internal`。這幾種錯的原因前面都再加「單子跑不起來：」，代號照舊分種類。
- **不認的 key**（打錯的、別人加的）一律忽略、不報錯（N-04）。11-04 以前 `id`、`envs_clear`、`*_mkdir`、`stderr_merge` 也在這裡被忽略，現在照上表認。
- **監工**：子程式自成行程群組（libaos `new_session`）；跑的期間 aos-exec 收到 SIGINT／SIGTERM／SIGHUP 自己不死，轉給**整個群組**，
  第一次轉過之後過 `grace_ms` 還沒結束就 SIGKILL 整群；逾時由 libaos 管（也是整群）。子程式結束後 aos-exec **以子程式的碼結束**（被訊號停掉＝128＋N，
  例 SIGTERM＝143，透明轉交 N-43）。子程式沒有控制終端，讀不了終端（P-36）。
- **正常結束時不收背景的孫行程**（11-05 B 線實測、代定）：子程式自己退了，它丟到背景的（`sleep 30 &`）留著繼續跑、沒人收——照 Unix 慣例，背景程式是單子自己的事；只有逾時、收到訊號（含 grace 到了）才整群收。不要留尾巴就在單子裡自己 `wait`，或別丟背景。
- **`argv[0]` 由 libaos 跑**（glibc 的 `execvp`）：所以單子裡 `+x` 但沒 `#!` 的檔會被 glibc 改用 sh 跑——跟上面可執行檔、argv 陣列入口一樣。
- **JSON 入口不要寫 `+x`**：拿掉 `+x` 的 `_entry`（第一行 `#!` 會被跳過）就能當單子跑。也**不要**寫成 `#!/usr/bin/env aos-exec` 再加 `+x`：
  `+x` 的檔 aos-exec 會 exec 它、kernel 又叫 aos-exec……原地無限 exec。aos-exec 不讀 `+x` 檔的內容去擋。
