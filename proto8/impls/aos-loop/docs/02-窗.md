### 窗（`ctl`、`state`、`state_flux`）

公開 C++ 協議在 `aos/loop.hpp` 的 `CtlWindow`／`StateWindow`／`StateFluxWindow`；預設檔名、設定 key、跨程式欄位照這份宣告讀寫。

三個設定 key `ctl`、`state`、`state_flux` 沒寫時分別用 `ctl.json`、`state.json`、`state_flux.json`，路徑在 `$AOS_STACK` 底下；寫 `null`＝不開。旗標 `--ctl FILE`、`--state FILE`、`--state-flux FILE` 蓋過設定。要開卻沒設 `AOS_STACK`＝`StackMissing`；直接跑而且不開窗時，三格都要寫 `null`。stack 不存在不自己建，寫不了＝`WriteFailed`、退 1。

- **ctl**：誰都能寫、loop 只讀；每跑一次讀一次、暫停中每秒讀一次。內容 `{"cmd": "pause"／"resume"／"stop", "max", "interval_ms", "seq"}`，都選填。pause 暫停、resume 解除、stop 在這次跑完以 0 結束（壓過同一道其他動作）。max／interval_ms 寫了從現在起生效、null 回旗標／設定值、沒寫不動；seq 是非負整數，只供回音。其他 key 忽略。
  解完的內容跟上次相同就不重做，檔留著不刪不改；檔消失後再寫都算新指令。**手寫每次換 seq**：同內容再寫不回應，父可能因此判 stuck。起來先從舊 state_flux 接有效 ctl_seq，第一道 seq 相同就不重做（stop 後 start 不會被同一道 stop 再停）；未開 state_flux、無有效舊 ctl_seq 或新指令沒 seq，就照一般指令處理。
  新的壞指令（讀不了、不是 JSON 物件、型別不對、未知 cmd、指示詞解不開）整份拒用，原因記 state_flux 的 ctl_warning；下一道好指令清回 null。好壞新指令都更新 responded_at，第一道已套用過的與檔不在不算。
- **state**：只有自己寫；先寫 `.state.json` 再改名。穩定欄為 `phase`、`max`、`interval_ms`、`paused`、`pid`、`started_at_ticks`、`boot_id`、最後的 `updated_at`；子類別可加穩定欄。結束多 `code`，phase 是 done（自己跑完或失敗）或 stopped（ctl stop、訊號、自己的錯）。max 不限時 null。
  有變才寫：比較時不含 updated_at，running／waiting 互換不算變（實際寫出仍是當下 phase）；啟動第一份與結束帶 code 的那份一定寫。updated_at 是真的寫出去那一刻（ISO 8601 UTC 到毫秒）。暫停與生效設定改變才會重寫，單純 ctl 回音不動這扇。
  起來從舊 state 的 paused 接回暫停狀態，第一拍尚未套用的 resume 可解除；max／interval_ms 回設定值，其他欄不接。行程身份看 pid＋started_at_ticks（/proc/<pid>/stat 第 22 欄）＋boot_id，不看檔案更新時間。
- **state_flux**：只有自己寫；先寫 `.state_flux.json` 再改名。欄位 `responded_at`、`ctl_seq`、`ctl_warning` 加子類別的 `flux_more()`，**沒有 updated_at**。第一份必寫，之後整份內容有變才寫，結束不強制另寫。寫序是 state、子類別穩定窗、最後 state_flux，所以看見 ctl_seq 追上時，狀態已落地。
  responded_at 起來是 null，只在處理新 ctl（好壞都算）、收到信、起或收子項時更新；身體跑完不更新。它不是心跳，閒著就不動。父用子 ctl mtime 與 state_flux 的 responded_at 判 stuck；要判就要開 state_flux。

**計數檔**：給 `--enable-counters` 且開了 state 窗，每次開跑前寫 state 同資料夾的 `counter_runs.txt`（十進位整數＋換行，先寫 `.counter_runs.txt` 再改名）；沒有身體也數，重起從 0 算，預設不碰檔。

沒有心跳；nap 最多 1 秒是為了讀 ctl。沒有 exec 的 daemon 一輪只 tend 一次、不寫 running，閒置時三扇窗都不動。

### 結束碼

| 情況 | 結束碼 | stderr |
|---|---|---|
| 那次退 0 | 下一次 | — |
| 那次退 10 | **0** | 不寫 |
| 那次退其他非 0（含被訊號停掉 128＋N、單子逾時被收掉＝143） | **那個碼** | 錯誤行 `aos-loop: error: RunFailed run N: 誰 failed with exit code C`（11-05 stdio-unify D4；碼是身體的，不是 1）（誰＝exec 的目標字串：字串 exec 原樣、陣列＝第一個元素；例 `loop.json#/body`；單子＝「設定檔名#指標」，例 `loop.json#/exec`） |
| 跑滿 `max` | 0 | 不寫（N-43） |
| 收到 SIGINT／SIGTERM／SIGHUP | **128＋N**（等那次結束之後） | 不寫 |
| 其他訊號（SIGUSR1、SIGUSR2、SIGKILL…） | 照系統預設（多半直接死，例 138） | 不收工、state 留著最後一份（同 `kill -9`；11-05 第二輪） |
| 自己的錯（含 exec 的單子壞、起不來） | 1 | 一行 `aos-loop: error: 代號 原因` |

那次找不到入口、單子壞等（那一層 aos-exec 的錯）：stderr 先有一行 `aos-exec: error: 代號 原因`，那次的碼是 1，接著是 loop 那行「aos-loop: error: RunFailed run N: … failed with exit code 1」——每層只說自己的（P-21）。所以字串目標指到的單子壞不是 loop 自己的錯，每次都會照跑一次 aos-exec、各自報。

### 訊號

整支程式的壽命都擋著 SIGINT／SIGTERM／SIGHUP（P-36「先收好自己起的子程式、寫好狀態再結束，結束碼非 0」）：

- **跑到一半收到**：轉給那次——`kill` 給那個子行程（那次的 aos-exec；它跟 aos-loop 同一個行程群組；不另設 SIGKILL 期限）；
  那次是單子時由那次的 aos-exec（監工）再轉給整群、過 `grace_ms` 還沒結束就 SIGKILL 整群。等那次結束，**不起下一次**，以 128＋第一個收到的訊號結束。
- **兩次之間收到**（含睡 interval、paused 的時候）：不起下一次，直接 128＋N（有開 state 窗就寫 `stopped`、`code`）。
- 在終端機按 Ctrl-C：那次的子行程跟 aos-loop 同群組，會直接收到一次、再收到 aos-loop 轉的一次（兩次）；單子的子程式自成群組，只收到那次的 aos-exec 轉的。

11-07 daemon 裁定 B：不論透過陣列或 argv 物件經 aos-exec 起 aos-loop，daemon 都往 proc 的公開 ctl 寫 stop；aos-loop 的預設 ctl 仍在 AOS_STACK/ctl.json。daemon 的 sleep 走訊號，ctl 協定沒有 sleep 指令。
