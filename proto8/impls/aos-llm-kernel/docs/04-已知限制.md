## 已知限制

- **token 靠 endpoint 函數照實寫 `usage`**：沒寫（或寫錯）就只算次數，`max_tokens` 額度看不到它；數字 kernel 不驗。
- **token 額度事後才知道**：掛之前不知道這封會吃多少，所以會超過一點（見 [02](02-token-回報與額度.md)「到頂怎麼判」）。
- **窗用本地時間**：kernel 的 `TZ` 換了、或日光節約，`since` 會變＝當成換窗歸零一次。`wait` 配 `window: "all"`＝到頂後永遠等（直到有人改 kernel.json 或刪 `used.json`）。
- **窗以系統牆上時鐘判**（額度的 kernel／包／寄件人三種同一個窗）：日曆日要跟牆上時間綁、`used.json` 又跨重啟保存，所以不用 monotonic。時鐘往回撥或往前跳＝`since` 跟現在算出的不同，當成換窗歸零一次（往回撥回到同一窗則不歸零；不會算出負數或卡住）：可能多給一窗額度、或晚一點換窗，這是天然行為。
- **睡醒、kill -9 可能多花一次腦**：daemon 收工時在飛的問腦被收掉、醒來從頭跑一次；死在半路的重掛一次。端點可能已經收到、答了，只是回信沒落地——多花的那次自己擔（使用者口徑「風險自擔」，[kernel-daemon 03 § 5](../../../thinking/2026-11/05/kernel-daemon/03-問腦改掛daemon.md)）。
- **有人對 `llm_<信件名稱>` 下 `stop`／`pause`**：那列停在表上、沒收尾，kernel 當它還在飛，那封一直等（佔一格），直到有人 `start`／`resume` 回去。（daemon 因出錯結束留的 `stopped`＋`reason` 不算這條，kernel 當收尾，11-05 晚。）
- **回信的 `reply_to` 存相對 kernel 信箱的根**（aos-post 11-05）：llm kernel 跟寄信的那台一起搬沒事；**只搬 llm kernel、不搬寄信的那台**＝在飛那幾封的回信寄不到（kernel 的 stderr 印一行，信照刪）。
- **人殼裡設了 `AOS_KERNEL`（指別台的掛信信箱）再起 llm 的 daemon**：kernel 繼承到它，掛信寄到那一台去，問腦 proc 掛錯台、這邊收不到。起 llm daemon 的殼別設 `AOS_KERNEL`（或在它的 `.env` 蓋掉）。非空路徑的 `new/` 不是資料夾時，每行程每路徑只印一次 warning；仍寄原路徑、不退回 daemon ctl 信箱，後續掛 proc 失敗仍回 `LaunchFailed`。
- **信處理完就刪、kernel 不留請求原文**（11-04 夜使用者「舊信根本不用留，就是刪」，[think-as-function 08 題 3](../../../thinking/2026-11/04/think-as-function/08-邊緣狀況實測.md#留給你的題白話推薦放第一)）：事後要查請求原文看 agent 自己的 history；kernel 這邊留 `used.json` 的總數與 `ledger.jsonl` 的逐封成本、時間（見 [02](02-token-回報與額度.md)）。寄完被刪掉的 agent 那封照跑、回信寄不進（kernel 的 stderr 印一行），信照刪，[think-as-function 04 #6](../../../thinking/2026-11/04/think-as-function/04-邊緣狀況.md)。（11-07 使用者裁定：翻 11-05 的 served.jsonl「也刪」，ledger 留；各層都記 usage、加總只加一層。見 [kernel-nest](../../../thinking/2026-11/07/kernel-nest/README.md)）
- 寄回信跟刪信之間 kernel 死掉（`reply_letter.txt` 還沒寫成）：下一次接手會再寄一封，收信的只拿第一封，第二封留在回信信箱的 `new/`。
- `ask` 被打斷、而 kernel 寄回信前一刻它還沒走完（`sender.flock` 還鎖著）：那封回信沒人撤、留在 `$AOS_LLM_KERNEL/requests/reply/new/`（窄縫）。
- **金鑰要給到端點小 proc 的環境**：起 llm daemon 的 root 殼沒 export 小定義 `--key-env NAME` 指定的變數＝那封 `EndpointFailed`；包在 sandbox 裡還要在 `env` 陣列明列名字。kernel.json 不放金鑰，正確定義下 `request.json` 不含金鑰；kernel 不替 endpoint 函數驗設定，`llm_http` 收到 `endpoint.key` 才報 `ArgumentsBad`。
- **寄信的人是誰 kernel 不驗**：`sender.flock` 只說「人還在」、不是身分，信封的 `sender` 也不看；寫得到信箱的程式就能用 kernel 的額度問 kernel 登記過的腦（但改不了包的 url 或端點小 proc 的金鑰、也不能叫 kernel 跑別的程式）。
- **共用信箱看得到別人的信**：寫得到信箱就讀得到別封信（請求內容）與回信；要分開就分信箱、分群組（Linux 權限）。kernel 自己建的信箱照 umask（多半 755），跨帳號用照 `setup.sh --mailbox` 先建好。
- **每個寄件人的額度靠信封 `sender`、kernel 不驗**（`budget.senders`，11-05 feat-proto 件 5；10-15「濫用：先信任」）：寫得到信箱的程式可以在信封寫別人的身分、用別人的額度，或換個 `AOS_WS` 起就變成沒列的人（沒列＝不限）。要真擋＝照 Linux 權限分帳號、分信箱（11-05 口徑自擔）。沒有「沒列的人一律 N 次」的預設格（要就逐個列）。`class` 不看。
- **寄件人的帳跟著相對 kernel stack 的路徑走**：整包搬家且相對位置沒變＝同一格帳；agent 換了工作區（`AOS_WS`）而相對位置改變＝新的一個人、`senders` 從 0 算；`used.json` 的 `senders` 每個寄過的人都記（沒列的也記），換窗歸零。
- **排程不做的**（[feat-proto 03 代定 5](../../../thinking/2026-11/05/feat-proto/03-scheduling.md)，以後的候選）：搶位（殺掉在飛的 low 讓 high 進——HTTP 一刀砍掉錢已經花了）、信裡寫 `max_cost`／`max_wait_ms`、包到頂自動降級（`fallback`；推薦不降級、回 `BudgetMissing`，留題給使用者）。
- **保留 high 格不保證立刻開跑**：`reserved.high` 只擋新的低級信，不會收掉已在飛的請求；調高保留數時仍要等在飛的跑完。high 也可能等在飛請求結束後，才用到保留範圍外的格；仍受總 `slots` 與端點包 `slots` 限制。`slots: 1` 不能正數保留；低級信即使靠 aging 升到 high，也沒有保留格資格。
- **包的 `slots` 只擋新掛的**：kernel.json 把某包的 `slots` 改小，已經在飛的照跑完，新的等它們降下來。
- **包的帳跟著代號走**：同一組改了名＝新的一包、`packs` 從 0 算；舊名的帳留在 `used.json` 直到換窗。
- **`speed` 同級時插隊**：同級、同 deadline 的信，快包的先、後寄的也一樣；慢包的靠 aging（每 `aging_cycles` 格升一級，預設 3）追上。有 `AOS_CLOCK` 數 kernel 自己樹的鐘，沒有用 `AOS_CLOCK_INTERVAL` 換牆鐘（預設約 3 秒升一級）；時鐘凍住＝不升級。

- **後端互斥只在本台 kernel**：兩台 kernel 都放同一 LM Studio 的本機包，就可能同時換模型；部署時把同服務的包收在一台，這版不做跨 kernel 鎖。
- **換包帳是掛信觀測**：只知自己最後掛的包，不知 LM Studio 是否成功載入、是否被外部切換；首次掛也算一次。max_packs 大於 1 時可有多包並跑，switched 仍只比較最後掛的包。重掛沿用第一次旗標；崩潰若落在掛信與 queue 落檔之間，帳可能少記一次，沒有跨檔交易保證。
