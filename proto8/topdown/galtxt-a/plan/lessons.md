# 由上而下拆一棵 aos 資料夾樹：經驗（fable 兩輪，2026-10-25；隊長與實作者往下追加）

← [round1.md](round1.md)、[round1-measure.md](round1-measure.md)、[round2-optimize.md](round2-optimize.md)、[round2-collapse.md](round2-collapse.md)

使用者 10-25：「在進行的過程中，可以適當將一些經驗留存下來。」「以後我們也會用 aos 體系，制作用來制作這套程式的程式」「到時候就會需要這些經驗。」所以每條寫成**一句結論＋一句依據**，並標「誰來做：腦／純程式」，給日後「做程式的程式」當流程草稿。

## 1. 哪些步驟可以寫成固定程序

| 步 | 輸入 → 產出 | 誰做 | 依據 |
|---|---|---|---|
| 讀題、定極小版 | 題目資料夾（只讀）→ 一個固定場景＋一題 benchmark | 腦 | 使用者「先從極小需求開始」；第一輪一個定點（河鹿堂讓書）就跑通了，兩題共用一套資料表 |
| 切大塊 | 目標一句話 → 5～7 個格（idle／brief／write／check／judge／pick） | 腦 | 切法沿用「生成端便宜多產、檢核端純程式砍、腦只做語意」（overgenerate-and-rank）；哪些格用腦一眼可定：只有「寫」「評」 |
| 每格寫 `_metainfo` | 格 → `kind`、`fs_needs`、`callers`、`reads`／`writes`、數字 | 腦填特性、**純程式填數字** | 數字手填全錯 3～6 倍（optimize § 2.2）；呼叫次數、份數、上限該由結構算出來 |
| 收表 | 樹 → `metatable` 的表 | 純程式 | 已有；只看表就能指出該優化什麼（optimize § 2.5） |
| 檢查一致 | 表 → P-36 逾時、上限 ≥ 子項和、同內容葉片、純容器 | 純程式 | 第一輪三處逾時算錯、兩處上限矛盾，全都是機械檢查能抓的（optimize O-7） |
| 實測回填 | trace.jsonl／usage.jsonl → `measured` 欄 | 純程式 | 第一輪是人手抄進 round1-measure.md；該是 metatable 的一個子命令 |
| 收攏 | 表＋判準 → 候選表 → 搬 | 純程式列候選、腦拍板、純程式搬 | collapse § 1 的判準八成只靠 `_metainfo`＋掃資料夾 |
| 證明不改行為 | before／after 同題假腦 → diff out／stack（抹時間） | 純程式 | fn-grow 的證明法；假腦是模板所以確定性 |

## 2. 判斷靠什麼資訊

- **該不該用腦**：看這格的輸出能不能用規則算對——護欄、格式、稱謂、合分都能，所以純程式；「像不像這個角色會說的」不能，才用腦。依據：Tier 0／1 純程式、Tier 2 腦，實測 6 份草稿護欄全過、腦只負責分辨好壞。
- **該不該平行**：`parallel=true` 但典型時間＝子項 × N 就是沒平行。依據：write 10440 ms ≈ 3 個寫手之和。
- **哪裡白花錢**：某格 `llm_calls` 比它底下的 `think` 多、而且多出來那次的輸入是確定的（lint `pass: true`）。依據：寫手第二次問腦佔 token 一半、6/6 次只是看一眼 pass 就交稿。
- **能不能縮**：`fs_needs` 空＋`callers` 1＋只有 `_entry`／`_metainfo`；再看 `_entry` 是單子還是腳本（表上沒有，要掃）。依據：collapse § 1 B-1／B-2。
- **不能縮的理由只有檔案系統特性**：own_stack、tool_json（腦列 `tools/`）、isolation（正解只給 pick）、mount、git 單檔 diff、捷徑掛點。依據：使用者 10-25「要考慮權限等檔案系統特性」；bench 留資料夾、cast 縮 JSON 的分界就在這。
- **表最大的洞是資料流不是數字**：`reads`／`writes`、「這格靠哪個 key 判做過了」沒印出來，第一輪兩個大偏離（逾時、換題不清）都在那裡。依據：optimize § 2.3 末。

## 3. 第一輪哪裡判錯、被實作修掉、以後怎麼防

| 錯 | 為什麼錯 | 以後怎麼防 |
|---|---|---|
| **逾時從內往外算錯**（write 格 900000 < 3 × 寫手 720000；頂層 1500000 不夠） | 每層手算一次、沒把 loop 圈數上限乘進去；P-36 是「外層 ≥ 內層一圈各格逾時之和 × 內層 max」 | 拆完自動檢查：對每個 fsm 格 `timeout_ms ≥ Σ 子格 timeout_ms × loop.max × 份數`；`time_ms.max` 與 `timeout_ms` 分開記（optimize § 2.4） |
| **換題不清舊草稿** | 規劃只想「重跑同題接著做」（P-20），沒想「一次放兩題」——兩個狀態 key（`current.txt` 與 `drafts/`）沒綁在一起 | 寫 `_metainfo` 時逼自己填 `state_key`（這格靠什麼判「做過了」）；每個「已有的不重做」都要配一條「key 變了清什麼」；測試固定加「兩題連放」 |
| **資料流接不上**（write 讀「題目的 drafts」，但題目在 ws、write 的 `reads` 沒 `ws:`） | 規劃寫 `reads`／`writes` 時沒逐格對「上一格寫的＝這一格讀的」 | 純程式檢查：每格 `reads` 的 `stack:*` 必須出現在前面某格的 `writes`；表加「誰寫→誰讀」一欄 |
| **agent 放在 `tools/` 底下** | 把「被 glue 叫的 agent」跟「腦的工具」混成一類 | `tools/` 只給有 `tool.json` 的（P-41）；agent 當 glue 的子項就放 glue 旁邊——collapse A-1／A-2 |
| **三份一樣的 idle** | 每隻 agent 抄範本時各帶一份 | metatable 算同內容葉片、建議捷徑（collapse B-4） |
| **數字手填堆邊際** | 每層都在子項上再加安全係數，根高估 6 倍 | 只在葉片手填（或實測回填），上層由 metatable 加總並標 `derived` |
| **`max` 一欄兩種意思**（逾時上界 vs 資源上限） | P-36 反推的逾時被寫進 `time_ms.max`，再被拿去當資源預算 | 拆兩個 key；上限欄由結構算（份數 × 子上限） |
| **估不準不等於判不對** | 數字全錯、方向全對（平行、拆重複腦、收攏候選都被實測加強） | 規劃階段的數字只用來排優先序，不用來承諾；上線前一定補實測欄 |

## 4. 給「做程式的程式」的幾句話

- 腦負責三件：切大塊、定哪格用腦、拍板縮不縮；其餘（填數字、收表、查一致、搬、證明）全是純程式，而且每件的輸入都是 `_metainfo`＋資料夾掃描，不用讀程式碼。
- `_metainfo` 的價值在**可以半自動判**；手填的數字價值最低、`fs_needs`／`callers`／`reads`／`writes` 價值最高。
- 工具要跟著規範長：aos-grow 不吃 `_metainfo`、不吃腳本入口，所以任何照規範寫的資料夾它都縮不回去（collapse § 5）。做規範的那一刻就要讓搬動工具認得。
- 證明永遠用假腦、兩份樹、同題 diff；真腦只跑一次看數字，不拿來證明結構。
