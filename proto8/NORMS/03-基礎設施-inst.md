# 基礎設施／inst

> **argv[0] 帶 `/` 又 exec 不了＝前面插 `aos-exec`**（10-20 定，10-20 使用者，見 [ideas](../thinking/2026-10-20-ideas.md) D3～D5；規則在 [N-61](10-基礎設施-定義與工作區.md)）：單子的 `argv[0]` 是資料夾、沒 `+x` 的檔、不在、或帶 `#/` 時，inst 改跑 `aos-exec argv...`，`aos-exec` 照 PATH 找（「分層衝突沒關係，就是要inst依賴PATH中的aos-exec」）；`+x` 的檔照舊直接跑、沒 `/` 照 PATH 找。loop／fsm 內嵌的單子也經 inst，一樣。bin 版 10-20 做、impls 10-21 對齊（impls 放在 aos-exec 的 `run_inst`，C 的 inst 庫不知道 aos-exec）〔10-23 註：bin 版刪了，只剩 impls〕。

- **N-04** inst 單子裡可以多放東西，inst 不認的別人可以讀（aos-inst 忽略不認的 key；10-22 起沒有 aos-inst 命令列，是 aos_inst 庫忽略〔10-23 起 aos_inst 庫刪了，是 aos-exec 的 `run_inst` 忽略：只驗 10 個 key，其他 key 忽略〕）。（3g.13b）
- **N-25**（D-4，草稿；10-19 改）程式內呼叫：`aos_inst.run(x)` 收路徑或一份單子（dict），回 `{"code","signal","timed_out","pid","elapsed_ms"}`〔10-23 註：10-23 起 Python 的 `aos_inst.run` 不在了，對應的是 impls aos-exec 的 `run_inst`（`run_inst(單子, 基準資料夾, args, ref_base)`，回 `Result`：`code`、`signal`、`timed_out`、`pid`、`ms`、`received`；C++ 欄位名照舊是 `ms`、沒改成 `elapsed_ms`，`received`＝跑的期間轉給子程式的第一個訊號；單子壞、指示詞壞、起不來是丟錯（`EntryBad`、`DirectiveBad`、`LaunchFailed`），見 [impls/aos-exec](../impls/aos-exec/README.md)）〕；aos-loop、aos-fsm 在行程內用它跑單子格（P-06、P-07、P-30）。**10-21 起呼叫者只剩 aos-exec**：loop 的 `exec`、fsm 格的 `exec`（loop 的 10-23 統合一度改名 `val`、同晚改回 `run`，深夜再改 `exec`（使用者：「exec，loop／daemon 的 run 也一起改 exec」）；fsm 格 10-23 深夜改名，原 `val`（使用者：「fsm.json，現在是用val，幫我改成exec」），[thinking](../thinking/2026-10-23-naming.md)）都只收 aos-exec 的目標，內嵌單子寫 `檔#/…/body`、由 aos-exec 行程內跑（[計畫 10-21](../thinking/2026-10-21-plan.md) L3、F2），loop／fsm 不再 import `aos_inst`。10-20 起 bin 版多收一個 `ref_base`＝單子裡 `$ref` 的起點（寫著單子的檔所在的資料夾；給路徑時自動取），loop／fsm 傳自己設定檔的資料夾（N-45；10-20 使用者，見 [ideas](../thinking/2026-10-20-ideas.md) D1）。（10-14）impls 線對應的是 aos-exec 公開 API 的 `run_inst(單子, 基準資料夾, args)`，回同一組欄位；之後的 loop／daemon「可以隨意使用指示詞,json schema，還有aos-exec的公開api」（使用者 10-19 晚，[ideas § 20](../thinking/2026-10-19-ideas.md)）。
- **N-27**（D-6，草稿；10-19 改，[CONVENTION P-26](../CONVENTION.md)）子程式的參數：aos-exec 把多的 args 與 stdin 原樣送到入口，怎麼進（args、stdin、或 stack 裡的檔）由工具自己的說明定；單子裡 `stdin: "params.json"` 照舊可以把一個檔交給子程式當 stdin，不加新 key。（10-14；10-16 起 agent 的工具見 [N-50](10-基礎設施-定義與工作區.md)）
- **N-30**（原 h4、h5，草稿；10-19 改）aos-inst 的結果 `{"code","signal","timed_out","pid","elapsed_ms"}` 回給行程內的呼叫者〔10-23 註：10-23 起 Python 的 `aos_inst.run` 不在了，對應的是 impls aos-exec 的 `run_inst`，回的欄位見 N-25 的 10-23 註與 [impls/aos-exec](../impls/aos-exec/README.md)〕（原本 aos-loop、aos-fsm；10-21 起只剩 aos-exec，它只拿 `code` 當自己的結束碼，所以 fsm 的 `trace.jsonl` 也拿掉了 `timed_out`，N-39）：`code`＝子程式的碼（照實轉交的資料，不是 aos-inst 的退出碼；被訊號停掉時是 128＋N，N-43）、訊號號碼另放 `signal`、被逾時殺掉的 `timed_out: true`。命令列上 aos-inst 的結束碼＝子程式的碼（透明轉交，N-43 例外），不另吐結果 JSON；aos-inst 自己出錯一律退 1、stderr 一行 `aos-inst: 原因`。inst 自己不開窗（沒有 state／ctl）。（10-14 深夜；10-19 改，P-21、P-30）impls 線：沒有 aos-inst 命令列，單子當入口時由 aos-exec 行程內跑、aos-exec 以子程式的碼結束（同樣是透明轉交，N-59 第 5 件）；單子壞＝aos-exec 自己的錯退 1（§ 20）。10-22 使用者改：bin 版的 aos-inst 命令列也刪了（「對於python版，aos-inst指令可以刪掉了，跟C++版一樣做成lib就好。」），兩版都照上面 impls 線那樣——單子壞＝aos-exec 退 1、stderr 一行 `aos-exec: 單子跑不起來：原因`（bin 版；impls 帶代號：`aos-exec: 代號 單子跑不起來：原因`，10-23 起只剩這個）；「命令列上 aos-inst 的結束碼」那句現無實作。
