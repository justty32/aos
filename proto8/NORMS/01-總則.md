# 總則

- **N-05** 給別人讀的檔，先寫 `.` 開頭的暫存檔再改名蓋過去；讀的人不讀 `.` 開頭的檔。這是 N-02 的細則之一；ctl.json、state 檔、`.done`、save 檔、時鐘檔都照這條。（10-12）
- **N-12**（10-14 定，草稿）可供呼叫的程式回歸 POSIX 原始本意：stdin＝參數，stdout／stderr＝結果，exit＝輔助。在 aos 規範中三者都是 JSON 串流（放寬：一串 JSON 值接著一串，每份可單行或跨行；只有一份就是普通 JSON）。stdin 有多份時，整串是一次呼叫，意思由程式自己解讀、寫在它的說明裡，規範只管格式。跑完的判定：以 stdout 吐出結果並且行程結束為準（exit 檔 10-15 深夜 KISS 批次 1 整個拿掉，原「有寫 exit 檔的話，exit 檔出現也算」10-14 深夜使用者定，見 [KISS 彙整批次 1](../thinking/2026-10-15-kiss/README.md#批次-1純刪彼此不相依不碰第四版的形狀已做10-15-深夜四個-commit自定點見-10-15-session-log) 1.1）。**半份不算**（10-14 深夜，[thinking 15](../thinking/2026-10-14-json-entry/15-ret與半份JSON.md)）：讀的人只認完整、能解析的 JSON；被殺時最後一份只寫一半、解析不了就忽略，因此找不到結果＝沒有結果（例：tasks 報 `ResultUnreadable`、loop 記 `code` null）。JSON 串流視為省略最外層 `[]` 的陣列，`檔#/位置` 照陣列索引指。inst.json 格式不變（作為與舊時代的橋樑）；規範管的是 inst 所呼叫的 argv[0] 程式。以函數來看：stdin＝args，exit＋stdout＝返回值，stderr＝途中拋出的錯誤（10-15 晚起不放警告，見 N-29）；stdout 可一份一份吐出（像 yield），不強制。aos-inst／loop／daemon 已照本條重做（10-14 使用者定；10-14 夜動工，基礎實作，命令列細則見 [N-21～N-27](../NORMS.md)）。（10-14）
- **N-43**（10-15 收工後定，草稿）結束碼：規範只定 **0＝通用正常、非 0＝有錯**。**aos 的程式說自己的錯一律退 1**，不另用 125～127、128＋N 等數字分種類：是哪種錯看 stderr 的 `code`（N-29），被哪個訊號停掉記在 state 窗或結果 JSON 的 `signal`（例 loop 的 state 窗與結束那份、aos-inst 結果的 `signal`）；沒窗的寫 stderr 一份 `Signaled`（10-15 晚使用者「按照推薦」，原本「別的數字規範不定、各程式可當慣例」，[thinking 原則](../thinking/2026-10-15-principles.md)新的待定 A）。**10-16 改**：收到 SIGTERM 是優雅收工、正常退出（N-52），不寫 `Signaled`、不退 1；`Signaled` 只剩程式沒當成收工的訊號（SIGINT、SIGHUP 怎麼算見[待定](08-待定.md)）。結果與錯誤的細節看 stdout／stderr 的 JSON（N-12、N-29、N-30）。**每層只說自己**（C-52；10-15 晚使用者「都同意。」，[盤點](../thinking/2026-10-15-principles.md)第 1 條）：不把下層的結束碼往上傳，下層的碼與錯誤只放 stdout／state 窗等 JSON——loop、daemon、fsm、閘門、aos-inst、tasks 自己都只退 0／1。**例外只有一種**（10-15 晚使用者「都按照推薦。」）：**透明轉交**別人的碼——閘門的碼＝target 的（等於 target 自己說話，lib kernel_llm.md）、tasks 的 seq／par／if 回子程式的碼（同 sh 的 `&&`），這時碼與 stderr 是下層的、不是自己的。（原本第二種「述詞」例外（`aos-not`）隨 aos-not 10-15 深夜 KISS 批次 1 刪，見 N-34。）**收到 SIGTERM 一律退 0**（10-16 改，見 N-52）：送 SIGTERM＝叫它優雅收工，是文件寫明的路，照下面「正常退出」的定義就是正常退出、不寫 stderr——daemon、loop、閘門、tasks、aos-inst 都一樣。原本只有 daemon（SIGTERM／SIGINT）退 0、「loop、閘門、tasks 被訊號停掉是半路被打斷，退 1」（10-15 晚使用者「都按照推薦」），10-16 使用者翻掉（「退0」，[KISS 重審拍板 3](../thinking/2026-10-16-kiss-recheck.md#使用者拍板10-16)）；實作待改（現在 loop、閘門、tasks 收到 SIGTERM 退 1、寫 `Signaled`）。SIGKILL 這類程式沒機會處理的不在此列（行程說不了話，呼叫方看到的是「被訊號殺掉」，例 aos-inst 結果的 `code`／`signal`，N-30）。另：inst 寫了 `stderr_inherit`＝stderr 上是子程式的、不是 aos_inst 的（N-26；10-15 深夜 KISS 批次 1 刪過、10-16 還原）；aos-inst 結果裡的 `code` 是子程式的碼（資料，N-30），不是 aos-inst 的退出碼。（使用者 10-15 收工後：「結束碼不要太依賴，我已經決定規範中只定下：0就是通用正常，非0就是有錯，沒了。」；10-16 概念面補上理由＝[C-63](../CONCEPTS/01-設計理念.md#結束碼與檔案權限10-16-使用者定)：結束碼只是參考、是 Unix 時代的遺留，結果與狀態看 JSON）**「正常退出」的定義**（10-15 晚補，盡量靠近 Unix 傳統）：該功能單元的行為照當初的設計構想、功能介紹、文檔走（走的是定義中正常退出那條路），而且是考慮過的狀況（被預料到、而且是正常的）。簡化判準：**正常退出不會在 stderr 噴東西**——寫了 stderr 就不算正常退出、不該退 0。反過來不成立：沒寫 stderr 不代表一定退 0，錯誤可以寫到別處（例 fsm 那拍的 stdout 行、agent 的 `ret.json`），只要寫在文件說好的地方。（使用者 10-15 晚：「喔剛剛那個我補一句：結束碼0代表正常退出，我這邊的定義(我希望盡量靠近unix傳統)，關於"正常退出"的定義，就是該功能單元中，其行爲有如當初的設計構想、功能介紹、文檔走(當然，走的是定義中正常退出的那條路)，並且是考慮過的狀況的一部分(有被預料到，且是正常的)，一個更簡單一些的定義是不會在stderr噴東西。」「當然，不在stderr噴東西，不代表結束碼就必須爲0。你當然可以把錯誤輸出到別的地方。」；與 C-53 錯誤路徑濃縮同一件事，現況不合的地方見 [thinking 原則](../thinking/2026-10-15-principles.md)）
- **N-52**（10-16 定，草稿）**收到 SIGTERM＝優雅收工**：先把該做的事做完——收好自己起的子程式、寫好最後的狀態（state 窗、結果 JSON）……——再自己結束，**退 0**（正常退出，不寫 stderr，N-43）。**不管手上有沒有事要做都走這條路**：沒事做就是「做完」得很快，不另分「被打斷」。所有 aos 的程式都守（loop、daemon、閘門、tasks、aos-inst、kernel…）；被哪個訊號停的照 N-43 記在 state 窗或結果 JSON 的 `signal`。SIGKILL 這類沒法處理的不在此列。收工要多久照各程式的 `grace_ms` 慣例（[待定](08-待定.md)「巢狀 grace」）。（使用者 10-16：「退0。應該說，SIGTERM之後，loop會做一些事情，然後再自己結束，也就是優雅收工。重點在於"把該做的事情做一做後，才結束"，不管有沒有事情要做，總之就是這樣。這塊也可以當原則」，[KISS 重審拍板 3](../thinking/2026-10-16-kiss-recheck.md#使用者拍板10-16)；收掉待定「argv[0] 程式的規矩」裡「收到 SIGTERM：收好自己起的子程式再退出」那點。）實作待改：loop、閘門、tasks 現在收到 SIGTERM 退 1、寫 `Signaled`。SIGINT 要不要比照，見[待定](08-待定.md)。退 0 之後要分「做完」與「被叫停」的，看 JSON（loop 結束那份的 `end`、state 窗的 `signal`），不看結束碼（10-16 使用者：結束碼只是參考，[C-63](../CONCEPTS/01-設計理念.md#結束碼與檔案權限10-16-使用者定)）。
- **N-18**（10-14 夜定，草稿）規範延伸出來的實作分兩級。**基礎實作**：最精簡，只確保符合概念與規範的要求。**標準實作**：考慮到邊緣狀況、經過一定程度精修。目前先做基礎實作；邊緣狀況能顧就顧，但不為了邊緣狀況把實作弄肥。錯誤歸類慣例：規範沒說的邊緣狀況，在基礎實作中預設不應出現，出問題算使用者的事（這是 [C-53](../CONCEPTS/01-設計理念.md) 的姿態 (a)「入口默認正常」）。（10-14）
- **N-29**（原 h3，草稿）stderr 的 JSON 形狀：錯誤一份 `{"error": {"code", "msg"}}`（原寫「同 N-10 回覆的 error」，N-10 10-16 刪），一份一行。**stderr 不放警告**（10-15 晚改，原有 `{"warning": {...}}` 一種）：跑起來之後預料到、不結束也不算錯的意外，有窗的記進窗（例 loop／daemon／kernel 的 state 窗 `last_warning`，「代號: 白話」），沒窗的寫在文件說好的地方（例 aos_tree 停住的 ref 帶 `stop`），兩樣都不合就是錯（非 0）——因為 N-43 正常退出不寫 stderr。stdin 有多份 JSON 而程式只要一份時＝入口錯 `InputExtra`（非 0；原為只看第一份、警告）。（10-14 深夜；10-15 晚改，使用者「都按照推薦。」，[盤點](../thinking/2026-10-15-principles.md) S1）
- **N-35**（10-15 定，草稿）路徑寫法 `檔#/位置`：凡是收「一份 JSON 設定」的地方（aos-inst／loop／daemon 的 TARGET、daemon 的 `children` 各項（原「daemon 指令裡的 id」，N-10 10-16 刪）、fsm 的格；指示詞等語法糖也接受（10-15 使用者『都照建議』，依 C-48 改）），都可以在檔名或資料夾後面接 `#/位置` 指到裡面的一塊。遇到第一個 `#` 就切（檔名含 `#` 的不支援），`#` 後面只認 `/` 開頭（`檔#x`＝錯）；位置照檔案系統寫法（D1a）：`#` 或 `#/`＝整份，結尾 `/` 與空段落忽略，代價是名字是空字串的 key 指不到；JSON 串流當省略最外層 `[]` 的陣列、照索引指（N-12）。指到的是一塊視窗不是切下來。TARGET 是資料夾時先照現有規矩找 inst.json 再套位置（找法：先 `<資料夾>/$AOS_DIRNAME/inst.json`、再 `<資料夾>/inst.json`；`AOS_DIRNAME` 是環境變數、單一資料夾名，沒設＝`.aos`；10-15 收工後使用者「都AOS_DIRNAME」，[意見 5～7](../thinking/2026-10-15-opinions-5-7.md)）。當設定用時指到的值不是物件＝錯。身分（id）＝`realpath#/位置`，沒位置或 `#/` 就是純 realpath（同一份檔兩個位置＝兩個 id）。一份 JSON 放好幾個 inst 可以（agent.json 或資料夾都行）。（10-15）**10-16**：定義（食譜）裡互指寫死 `.aos/x`、stack 用 `.aos` 捷徑接定義（10-16 夜改名：原叫工作區）（[N-48](10-基礎設施-定義與工作區.md)），跟本條「`$AOS_DIRNAME` 可改名」不合——`AOS_DIRNAME` 刪不刪、本條要不要收成一句、`aos exec` 還收不收 `#/位置`，使用者沒定，見[待定](08-待定.md)；程式照舊。
