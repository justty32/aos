# 基礎設施／命令列、指示詞與路徑

## 命令列

> **10-16 起**：正規參數入口是 stdin，下面這些 argv 寫法（TARGET、`-`、鏡射旗標）連同 N-24 的 `--` 都歸成**語法糖**（[N-46](10-基礎設施-定義與工作區.md)）；條文照舊描述糖怎麼用，程式未改。

- **N-21**（D-3，草稿）設定從哪來：aos-inst／loop／daemon 的設定（N-11 的「設定檔」）有兩個來源，**二選一**——命令列給 TARGET（檔，可接 `檔#/位置`）就讀那份檔、不讀 stdin；要從 stdin 讀就寫 `-`（N-12：stdin＝參數）。人手打 `aos-inst x.json` 照舊可用。TARGET 和 `-` 都沒給＝設定從 `{}` 起（只靠旗標與 `--`），不自動讀 stdin（原 h1，10-14 深夜定）。（10-14）
- **N-22**（D-1，草稿）鏡射旗標：設定的頂層 key 可以有同名旗標（`times` → `--times`、`timeout_ms` → `--timeout-ms`），機械對應、不另發明欄位，設定 JSON 本身一字不改。這是為了方便，不是硬規則：純量 key 鏡射；值是物件／陣列的，除非很小很少，不鏡射（要改就改檔（10-15 使用者『都照建議』，依 C-48 改）），各程式自由。旗標每個都要帶一個值；值先當 JSON 解（`3`、`null`、`true`），解不了當字串；布林寫 `--cwd-mkdir true`；只認純量 key，其他＝FlagUnknown（原 h2，10-14 深夜定）。只鏡射最外層，巢狀的（例如 loop.json 裡那份 inst）不鏡射。daemon／loop 起子程式一律走 stdin JSON，不走旗標。（10-14）
- **N-23**（D-3，草稿）優先序：旗標 ＞ 設定 JSON（檔或 stdin）。（10-14）

`--`、程式內呼叫、`*_inherit`、子程式參數（N-24～N-27）只跟 aos-inst 有關，在 [inst](03-基礎設施-inst.md)。

## 指示詞與路徑

路徑寫法 `檔#/位置` 大家都守，條文在[總則 N-35](01-總則.md)；`$ref` 是拆檔的語法糖、`$env` 讀執行當下的環境（10-16 夜起可當正式機制，見 N-45），怎麼用說明在 `aos_cli.py` 檔頭（`$ref` 只收「檔#/從根算的位置」；10-15 深夜 KISS 批次 1 拿掉 `$at`、相對位置、`~0`／`~1`，錯誤代號只剩 `DirectiveBad`），規範只有下面一條。

- **N-45**（10-15 深夜定，**10-16 夜改**，草稿）**設計不靠 `$ref`；`$env` 可以當正式機制**。
  - **`$ref`**：只是把自己的檔拆小的便利（C-48 原文：「設計對它的認知只要『自己的一些檔案可以透過指示詞拆成小檔』就好」）。規範、機制、呼叫方式都不得靠 `$ref` 才成立——把它手動展開、或完全不用，意思必須不變。**JSON 大不是問題**，不必為了檔小而設計機制。（使用者 10-15 深夜：「我記得有說過吧，在概念或規範那邊，有說過指示詞的用法」「啊...好啦，規範那邊說一下，後續就是都默認沒有指示詞能用，但是不用擔心json太大」；出處 [thinking inst-exec 第四版](../thinking/2026-10-15-inst-exec-v4.md)）
  - **`$env`**：讀的是**執行當下的環境**，像 shell 的 `$HOME`——不是把檔拆小，展開了就失去意思（同一份定義在不同環境下要指到不同地方），所以可以當正式機制用。例：一般工具的入口 inst 寫 `"cwd": {"$env": "AOS_WS"}` 站進工作區（[N-55、N-56](10-基礎設施-定義與工作區.md)）。寫什麼就做什麼（C-56）：值寫的就是「讀這個環境變數」，不是暗規則。（10-16 夜：頂層提環境變數 `AOS_WS`、指出 `"cwd": "WS"` 字面替換是暗規則；使用者：「可以用$env啊」；頂層指出跟本條原文衝突，給 A（`$ref` 仍只是拆檔便利、`$env` 讀執行當下的環境可當正式機制）／B（維持原條、改用 `cwd_env` key）；使用者：「A」。[稿 § 四](../thinking/2026-10-16-agent-inherit.md#四使用者決定10-16)）現況：`aos_cli` 讀設定時已會展開 `$env`（變數沒設＝`DirectiveBad`）。
