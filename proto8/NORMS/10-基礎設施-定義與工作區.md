# 基礎設施／定義與工作區

用詞（C-54）：**定義**＝「食譜」（一個 `.aos/` 資料夾）；**stack**＝「廚房」（跑的時候站的地方＝cwd，命令列原寫 `WD`）；**工作區**＝使用者的檔與成品所在的資料夾（`ws`，C-65）；**門房**＝`aos exec`。食譜、廚房是比喻，條文用正式名詞。**10-16 夜改名兩次**：N-46～N-51 原本把 cwd 叫「工作區」，先改叫 frame、同夜再改名 **stack**（條文意思不變）（使用者 10-16 夜：「不過frame那塊能不能換成stack(或heap)?。」→ 頂層推薦 stack →「好！」）；heap 保留給以後跨呼叫共用的記憶、目前沒有機制；「工作區」只指使用者的成品區（N-55、N-56）。檔名沿用「定義與工作區」不改（連結多）。

本檔 N-46～N-53 出自使用者 10-16 的決定、N-55、N-56 出自 10-16 夜（[稿 § 四](../thinking/2026-10-16-agent-inherit.md#四使用者決定10-16)），都是**草稿**；**程式還沒照改**，各條寫了「實作待改」的地方就是現況跟條文不合處。細節裡 AI 提了、使用者沒點頭的放在[待定](08-待定.md)。

- **N-46**（10-16 定，草稿）**正規參數入口是 stdin**（N-12）。`aos exec WD TARGET`、`aos agent 路徑`、TARGET 引數、鏡射旗標、`--` 這類 argv 寫法都是**語法糖**：方便人打，但規範與機制以「stdin 一份 JSON」那條為準，不得有只能靠 argv 才做得到的事。（使用者：「argv:[aos,agent,agents/brush]，其實，我一直覺得argv這塊的用法...就像我早期說的，正規參數入口就是stdin，像是aos-exec WD TARGET這個用法是語法糖...」）實作待改：現在 aos-inst／loop／daemon 還收 TARGET 與旗標（N-21～N-24），本條把它們歸成語法糖，程式先不動。
- **N-47**（10-16 定，草稿）**「定義＋這次在哪做」一律 `aos exec stack 定義`**（門房）：站進 stack；stack 還沒有 `.aos` 就把定義掛成 stack 的 `.aos`（N-48）；然後跑 `.aos/inst.json`（照 N-46，把它灌給 `aos inst` 的 stdin）。適用所有東西：一支工作（inst）、一條 tasks 流水線、一個 loop、daemon 的子項、kernel 的判官、agent、工具（N-50）。（使用者：「前兩項我都OK」——「食譜 `.aos/`＋廚房 cwd」一律 `aos exec 廚房 食譜`，推廣到所有東西。）`.aos` 已存在且指別處、捷徑斷了、stack 要不要先存在等邊緣怎麼報錯，見[待定](08-待定.md)。實作待改：`aos exec` 還不存在（KISS 彙整批次 2 的 `aos-exec TARGET` 也沒做）。
- **N-48**（10-16 定，草稿）**定義與 stack 用捷徑接**：定義是一個 `.aos/` 資料夾，入口是 `.aos/inst.json`；stack 裡放一條叫 `.aos` 的捷徑（symlink）指向它；**一個 stack 一份定義**（要兩份就開兩個 stack）。**定義裡的檔互相指，一律寫 `.aos/x`，從 stack（cwd）算——跟 inst 現行「路徑從 cwd 算」同一條，沒有第二種路徑規則**；不靠 `$ref`（N-45）、不寫絕對路徑。在定義自己的資料夾裡跑也成立（那裡本來就有 `.aos/`，不用掛）。（使用者選捷徑：「捷徑。這塊細說」→「太優雅，太美了，這就是我要的。」）實作待改：現在找 inst.json 照 N-35 的 `$AOS_DIRNAME`；N-36 原本「fsm 格的路徑從設定檔所在資料夾算」那半句 10-16 已刪，fsm 格也一律從 cwd 算（實作待改，`aos_fsm` 還照舊）。
- **N-49**（10-16 定，草稿）**agent 的 stdin 只放一份，這份是定義**；**「這次的話」放在 stack 裡**，使用時指定 stack 的位置（以後可以有 `aos-agent-say`、`aos-agent-init` 這類語法糖）。agent 當函數是概念上的：定義（JSON＋資料夾）就是函數、stack 就是它的環境，**不造 `args.json`／`ret.json`／`frame.json`**（C-46）。（使用者：「stdin只放一份，這份要食譜。」「放在廚房裡，然後使用的時候指定廚房的位置。」）話在 stack 裡叫什麼檔、什麼形狀、回答放哪（`say` 印回答），見[待定](08-待定.md)。實作待改：現在 agent 讀 frame 的 `args.json`、寫 `ret.json`、照 `frame.json` 的 `parent` 找名字（lib agent.md、frame.md）。
- **N-50**（10-16 定，草稿）**工具一律是定義資料夾，地址寫在呼叫者的定義裡、不用 PATH**：工具 `<名>` 的地址＝呼叫者定義裡的一條相對捷徑 `.aos/tools/<名>`（指向那個工具的 `.aos/`；`date` 這種一般指令也包成 `.aos/tools/date/`）。工具格對每一個工具做同一件事：**站在自己的 stack，在 stack 裡開一個小格（原寫 `work/<n>/`，命名待定），叫門房 `aos exec 小格 .aos/tools/<名>`**；它不知道工具裡是不是另一個 agent（C-52）。工具站在哪由工具自己的入口 inst 決定（N-56）。**工具參數分兩層**：參數走門房（`aos exec`）的 stdin，由 stub／旗標明寫把它放進工具的 stack（小格）；裡面 agent 程式那層的 stdin 仍只放定義（N-49）；一般工具照 N-27（參數走 stdin）。（使用者：「可以不使用PATH嗎？」→「好!」；兩層：「還是不太懂，但感覺OK，就先這樣吧，以後再來搞懂。」）旗標叫什麼、做哪幾件事見[待定](08-待定.md)。實作待改：現在工具是 `tools` 裡的內嵌 inst、agent 當工具是三張 `sh -c` 工具 inst（lib agent.md）。
- **N-51**（10-16 定，草稿）**定義可以帶一個 shebang stub**：定義的 `.aos/` 裡放一個小檔，第一行寫「用 `aos exec` 在這裡跑我」（`#!/usr/bin/env -S aos exec …`），人就能在終端把定義當指令打（另在自己的 PATH 放一條捷徑指到它）。**體系內部不靠 PATH**（N-50）；PATH 只留給人。（使用者同意「食譜裡放 shebang stub＋捷徑」，之後再定「不用 PATH」，PATH 只留給人在終端用。）stub 上的旗標與 `env -S` 的版本要求見[待定](08-待定.md)。實作待改：還沒有 stub。
- **N-53**（10-16 定，草稿）**aos 的 agent 是被外面驅動的狀態機**：agent 每次被叫只走一拍（跑現在那格、換狀態、退出），由外面的 loop 一拍一拍驅動——為的是讓 agent 方便審視自己（每拍之間狀態都落在 stack、看得到）。所以 **agent 的定義不含 loop**（要反覆、隔多久、跑幾拍是外面那個 loop 的事；走到 end 時那個 loop 靠 N-44 `stop_on_end` 停）。**腦出錯那一拍退 1、phase 不動**（同 N-38，下一拍重跑同一格）；**重試幾次看外面 loop 的 `times`，agent 自己不數連錯**。概念上 agent 只是一台狀態機、怎麼跑由誰跑都行（C-62）；本條只管 aos 自己的 agent。（使用者 10-16：「但是我們的規範會說，為了讓agent方便審視自己，所以agent就是一個被人驅動的狀態機，需要外面有人用loop驅動他。這是我們的aos agent」；頂層確認「腦出錯那一拍退 1、phase 不動，重試幾次看外面 loop 的 times，agent 自己不數」→「可以。」，[KISS 重審拍板 4](../thinking/2026-10-16-kiss-recheck.md#使用者拍板10-16)）**不採用**：AI 稿裡「`aos agent -` 自己一拍一拍跑到 end 才結束」（[agent-inherit 稿](../thinking/2026-10-16-agent-inherit.md) 拍板點 7、[KISS 重審](../thinking/2026-10-16-kiss-recheck.md) 4.5 原推薦）。實作待改：think 格的連錯計數（`halt_after`／`halt_state`、`halted`）要刪；agent 當工具時誰包那個 loop，見[待定](08-待定.md)。

## stack 與工作區（10-16 夜）

出自使用者 10-16 夜的決定（[稿 § 四](../thinking/2026-10-16-agent-inherit.md#四使用者決定10-16)；看完稿 § 八「三分鐘看懂（五）」：「我覺得不錯。不過是不是可以採用環境變數？所以cwd: WS? 具體命名幫我想想。」→ 頂層提 `AOS_WS` →「可以用$env啊」→ N-45 選 A：「A」）。概念 C-65～C-67。都是**草稿、程式未改**。

- **N-55**（10-16 夜定，草稿）**工作區的位置由環境變數 `AOS_WS` 給**（`ws`＝workspace，進[縮寫表](../CONCEPTS/abbr.json)）：呼叫方設，照 Linux 環境變數本來的樣子自然往下傳給所有子行程，巢狀多深都指同一個工作區、沒有人需要知道深度。agent／定義跑的時候站在 stack（N-47、N-48），**工作區保持乾淨**——執行時的東西（`.aos`、history、fsm 狀態、窗、小格）都放 stack，不放工作區（C-65；呼叫方自己把 stack 指到工作區是它的自由，C-67）。讀它用 `$env`（N-45）。實作待改：還沒有程式設 `AOS_WS`；誰設（人自己 export、或 `aos init`／`aos exec` 代設）見[待定](08-待定.md)。
- **N-56**（10-16 夜定，草稿）**工具站在哪，只看工具自己入口那一行**：
  - **一般工具**（`aos write`、`date` 這類）**的入口 inst 寫 `"cwd": {"$env": "AOS_WS"}`**，站進工作區；這一行**由 aos 的工具範本給好**，設計者抄範本就不用想。
  - **agent 工具**（例 brush）**不寫 `cwd`**＝照 inst 本來的規矩站在門房站的地方，也就是自己的小格＝它的 stack（history、狀態記在那）。
  - **工具格與門房對每個工具一律做同一個動作**，不分辨對方是不是 agent（C-52）；也**不偷改預設**（例「門房遇到沒寫 cwd 就改站工作區」——同一份 inst 用 `aos inst` 跑和用 `aos exec` 跑會站在不同地方，是暗規則，C-56）。「預設」落在範本給的那一行字上，寫什麼就做什麼。
  - 站在工作區的工具拿不到自己的 `.aos/`（`.aos/x` 從工作區算就不在），所以是「argv 程式＋stdin」那種；要帶自己的檔就留在小格。
  
  （使用者：「我是覺得不用"遞"，而是就是默認true，默認ws就是工具的cwd...可以嗎？」「同樣用捷徑？」「brush這種agent工具，那就是他的cwd默認是他自己的frame。」；看完「三分鐘看懂（五）」：「我覺得不錯。不過是不是可以採用環境變數？所以cwd: WS?」→「可以用$env啊」）實作待改：還沒有工具範本、`aos write`、門房；現行工具是 `tools` 裡的內嵌 inst（lib agent.md）。agent 工具怎麼碰工作區、每個小格還要不要放 `ws` 捷徑見[待定](08-待定.md)。
