# galtxt-b 過程經驗（給之後「用 aos 做制作程式的程式」參考）

← [galtxt-b README](../README.md)｜規劃紀錄 [round1](round1.md)、[round2](round2.md)

使用者 10-25：「在進行的過程中，可以適當將一些經驗留存下來。」「因爲我們目前都還是依賴claude code來操控，來制作這套程式。以後我們也會用aos體系，制作用來制作這套程式的程式」「到時候就會需要這些經驗。」

這份是隊長（opus）邊做邊記的操控經驗：誰做什麼、怎麼交接、哪裡卡住。之後要把「隊長＋規劃者＋實作者」這套流程本身做成 aos 程式時，這些就是那支程式要照做或要避開的事。

## 流程（實際走過的）

1. 隊長讀規矩、建 impls、看題目素材幾眼（只夠核驗用），**不自己拆**。
2. 規劃者（fable）第 1 輪：通讀規矩與原則 → 拆頂層 → 順手把骨架與 stub 建出來、跑通、還接真腦跑了一題。一輪約 29 分鐘、43 萬 token。
3. 隊長核驗：只重跑 demo.sh（結束碼、兩條路：一稿過／打回再寫），讀 round1.md 的「下一輪」與「衝突」兩節。
4. 規劃者第 2 輪：**只規劃不實作**（看得到第 1 輪做出來的樣子），約 8 分鐘。
5. 實作者（opus）照 round2.md 做；同時另派一隻做支線（MCP）。
   實作者約 17 分鐘、27 萬 token：照 round2 做完、自己代定 13 條（多半是規劃寫得不能同時成立的驗收要求，例如「每個紅案例恰中一條」跟文法規則重疊）、23 條測試、真腦兩題、`_metainfo` 收表工具。支線（MCP 設計＋小原型）約 5 分鐘、14 萬 token。
6. 規劃者第 3 輪：A 只看 `_metainfo` 表做優化盤點（刻意不給看程式）、B 反向收攏的判準與工作清單。
7. （待續）實作者執行收攏 → 隊長收線。

## 經驗

- **任務書要把「做到哪一步」寫死**：第 1 輪只說「拆頂層、建骨架與 stub」，fable 直接做到能跑真腦——好處是第 1 輪就有實物可看；壞處是規劃與實作混在一起，使用者要評「拆得好不好」時分不開。第 2 輪起明寫「只規劃不實作」。要分就在任務書第一句說。
- **規劃者續用同一隻**（帶著上一輪的 context）比每輪新開便宜：第 2 輪只花 2 次工具呼叫就寫完，因為規矩與素材已讀過。代價是它對自己第 1 輪的判斷不會重新懷疑；要「不被自己錨住」的審查得另開一隻。
- **規矩是會在途中變的**：本隊做到一半，main 上改了兩次命名（計數 `counter_*`、時間 `<事件>_at`、上限 `max_*`）。協調者轉來提醒後，隊長先 rebase、重建 impls、重跑 demo 確認沒壞，再把新規則寫進下一個任務書。→ 制作程式的程式要有「規矩版本變了 → 先同步再派下一棒」這一步，而不是到最後 rebase 才撞衝突。
- **核驗用「跑」不用「讀」**：隊長不讀 fable 的全部程式，只跑 demo 的兩條路、看結束碼與輸出；讀的只有規劃文件的衝突段。省 context，也符合「綠燈要能變紅」——但前提是 demo 本身涵蓋失敗路（q08 故意壞稿）。
- **worktree 隔離的工具限制**：在 worktree 裡 `cd X && for …` 這類複合指令會被擋（怕跑出 worktree）；改成寫一支腳本放 scratchpad、再 `sh 腳本` 跑就過。等背景工作也一樣（等某檔出現且資料夾 N 秒沒動的小腳本 `b_wait.sh`）。
- **規劃者寫的驗收要求會互相打架**：round2 要「每條規則一個紅案例、恰中那一條」，但文法規則本身就包含拍數下限，兩條必然同時中。實作者只能代定、在回報裡列出。→ 制作程式的程式要讓實作者有一個正式的「代定清單」出口，並回送給規劃者下一輪看，而不是埋在回報裡。
- **真腦會吐規劃沒想到的形狀**：director 的回覆偶爾在 JSON 表後面多吐一段（`Extra data`），按規劃原樣會整題退 1；實作者改成只取第一份 JSON。→ 規劃階段的「輸出格式」假設要用真腦跑一次才算數，假腦只證明管線通。
- **`_metainfo` 宣告是規劃者在沒跑過時估的**：實測 token 普遍低估 2～3.5 倍（腦的 prompt 帶整份稿紙與 history，規劃時只算了「要寫的台詞」）、時間普遍高估 2～4 倍。→ 宣告應該在第一次真跑之後回填一次（但 M7 說實測不回寫 `_metainfo`，所以要有人／程式「看實測、改宣告」這一步，是制作程式的程式該有的一格）。
- **收表工具要先有**：沒有一張表，誰都看不出 26 份 `_metainfo` 哪裡估錯；表一出來就能「只看表」做判斷，正好拿來試規劃者的盤點能力。
- **使用者在途中連續改方向（十幾句），規劃與實作會錯開**：第 4 輪 A 段實作者照「單一性格單一場景」先做完並發出人評樣本，同時規劃者寫的 round5 自己挑了另一個場景（四月讓書）。隊長要當「已發出的東西」的守門人：一旦有東西交給外面（樣本給網頁），就把它寫成固定前提傳給下一棒，而不是讓規劃者重選。→ 制作程式的程式要有「凍結點」：哪些產物已對外、不可再動。
- **方向改動要同時發給所有在跑的棒**：改方向的那一刻，規劃者與實作者都在跑；只告訴一邊會白做。隊長每收到一句就同時轉給兩邊（SendMessage 會在對方下一次工具呼叫時送到）。
- **使用者原話先記、再轉**：每收到一句就先逐字寫進 thinking，再轉給棒子；收線時不必回頭找。
- **兩隊同題、互不相看**：任務書裡明寫「不要讀 galtxt-a」並傳給每一棒（規劃者、實作者、支線），因為每個新 agent 都只知道任務書裡的事。

### 第 6 輪 B 段後半：判斷器、優化器一步、漂移、子樹彙總（10-25）

- **「省幾百 token」的改動，4 題×1 驗不出來**：兩條候選的預期差 111 token，單次跑的 token 雜訊 ±3,000（腦自檢一回還是兩回）。判斷器的 accuracy 要有意義，驗證得用確定性的量（補參次數、工具呼叫次數）當主指標，或把次數拉到雜訊以下。→ 預期梯度要附「這個量的雜訊多大」，判斷器與核對都該看它。
- **稀有事件的改動要在事件會發生的條件下測**：patch_act 只在腦漏參時動作，現在的樹漏參率 1/8，4 次驗證剛好 0 次——改動沒有機會表現。→ 驗證前先算「這輪預期觸發幾次」，< 2 就加壓（假腦開關、更多次）或標成「量不到」。
- **判斷器讀得到文字根據，規則表讀不到**：真腦判斷器抓到「拿掉 trim 可能讓漏參回來」，這只寫在根據那行、不在預期梯度的 key 裡。固化成 priority_rules 後這種交互作用會丟。→ 交互作用要變成梯度裡的 key（例如預期 counter_argbad 會升），規則表才看得到。
- **提案器第一次就提了荒謬的動作**：假腦上它把 lint（回意見、不回稿）也提成「交稿前必叫」。白名單要有前置條件寫在被動節點的宣告裡（tool.json 的 `returns: text`），不能只靠動作名。
- **漂移的基準要用同一把尺重評**：round4 存的分數是更早的 critic 打的，直接拿來比會把「尺換過」混進「樹進步」；改成 critic_v0 對 v0 稿重評一次存起來。critic 同稿評兩次的差（critic_gap）就有 ±0.1～0.15，2 稿的「進步 −0.06」在雜訊裡。
- **子樹彙總是「子樹裡有什麼」，不是「跑一次花多少」**：同 worktree 別人剛加的 lib/selfopt 宣告 15000 token，也被算進根。兩個數字都要有：rollup（結構）與 rollup.measured（實跑）。
