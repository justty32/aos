**只收使用者說過的。** 這兩份只放概念本體；例子、原話、出處在每組標題連的分檔。這份**沒有檔名、沒有格式、沒有程式結構、沒有步驤、沒有第一版**——那是下一層，使用者講了才有。條號不重編。

## 設計理念

**[基本](CONCEPTS/01-設計理念/01-C-01～C-48.md)**
- **C-01** aos 存在是為了讓大語言模型方便使用；目標多到只能靠模型寫，所以系統本體要讓模型好用。
- **C-02** aos 蓋在現有作業系統上，不重做硬體層的計算分配。
- **C-03** 由下往上：Linux → daemon → 時空 → 排程與資源分配 → agent，上層只透過下層（講誰排程誰；C-74 講誰依賴誰）。
- **C-04** daemon 完全處理 Linux 那邊的事，它之上的不碰 Linux；這是推薦，另搞風險自擔。
- **C-07** 表達方式以模型天生就會的為準（檔案系統、POSIX、JSON），好讓它自省。
- **C-24** 要最佳化的不是時間空間，是金錢、可預測性、人能不能理解。
- **C-45** 規範比實作重要；aos 給符合規範的語法糖（inst、aos-fsm），不要求一定用。
- **C-43** 終局：一套 library，用 lua／lisp 一類語言把 aos 程式（整套資料夾布局）生成出來（＝「編譯」），把 aos 當作業系統跑；人和 AI 都要能用。
- **C-48** JSON 格式族：靠加 key 擴充、除非必要不新增格式；可放私有 key；不認得的 key 一律忽略不報錯（給人打的旗標、只有自己讀的子物件可以報錯）；值有雙形（純值或展開成物件），指示詞 `$env`／`$ref` 是它的一種用法。

**[C-51、分層](CONCEPTS/01-設計理念/02-C-51.md)**
- **C-51** 資料夾與 JSON 可以互通（資料夾＝object、名字＝key），但只當工具與思考方式、不進規範；固定名字可以，建議限縮範圍（理想只固定一個入口，其餘由它指定）。
- **C-74** 分層（誰依賴誰）：基礎層（核心 aos-exec＋loop、daemon）→ 標準庫（fsm、tasks、其他）→ agent／kernel；「核心」只指 aos-exec，kernel 不譯核心，大範圍那塊叫系統本體。

**[最高原則與兩條總原則](CONCEPTS/01-設計理念/03-最高原則與兩條總原則.md)**（[續](CONCEPTS/01-設計理念/03-續-C-52-例外.md)、[C-53](CONCEPTS/01-設計理念/03-續-C-53.md)）
- **C-56** KISS 是最高原則，也是最後原則：先滿足需求與其他原則，最後回頭把多餘的清掉；不拿「規則最少」抄近路；寫什麼就做什麼，不把規則藏進特定值。
- **C-52** 巢狀只管自己這一層、徹底切割：上層不需要也不該知道下層是什麼，想看下層要另有機制，沒有就別碰；可認公開宣告的介面、不認身份。
- **C-53** 各單元只處理自己的錯，寫明對別人的錯採哪種姿態（入口、出口、事先列出）；錯誤路徑收斂、出錯要能輕鬆回復；下層的錯不轉述。

**[命名](CONCEPTS/01-設計理念/04-C-54.md)**（[命名方法 R1～R14](CONCEPTS/01-設計理念/C-54-命名方法.md)、[命名統合原話](CONCEPTS/01-設計理念/04-續-命名統合原話.md)）
- **C-54** 名字要好懂、快速理解、快速記住，結構與名字本身就是說明：一詞一義、全體系通用；縮寫先進縮寫表；小寫加底線（夾名推薦、不強制；環境變數全大寫）、指令名換連字號；取名照命名方法。

**[布局成長與檔案權限](CONCEPTS/01-設計理念/05-布局成長與檔案權限.md)**（[函數成長](CONCEPTS/01-設計理念/05-續-C-55-函數成長.md)）
- **C-55** 布局成長：資料夾／檔案與 JSON 長大同一套——太大或不夠用就長一級（檔→資料夾、純值→物件、原值推薦叫 `val`），key 不變；「要跑什麼」一律叫 `exec`；函數也照這套長，分六級。
- **C-64** 用檔案的理由之一是借 Linux 讀寫權限做事（例 kernel 當某 ctl 的唯一寫者）；份額、沙箱也借 Linux 現成機制，存取控制托底靠 Linux。

**[資料夾程式與環境變數](CONCEPTS/01-設計理念/06-C-68～C-72.md)**（[C-73](CONCEPTS/01-設計理念/07-C-73.md)）
- **C-68** 資料夾＝程式，有一個入口（`AOS_ENTRY`，預設 `_entry`）；寫程式＝定義資料夾，使用＝在工作區跑它。
- **C-69** aos 只訂環境變數（入口、工作區、stack 等六個）和一支 aos-exec；入口拿到後做什麼不管。
- **C-70** 巢狀由程式自己訂子 stack；aos 只訂被叫者自己的 `AOS_STACK`。
- **C-71** 資料夾的比喻用 lua 的 table、不用 lisp 的 list：本質都是 index＋巢狀分資料；入口之外的就是其他元素。
- **C-72** JSON＝埋在檔案裡的 table（單檔的微型檔案系統），入口的尋址同樣適用（`js[$AOS_ENTRY]`、`檔#/指標`）。
- **C-73** 入口要麼自己是可執行檔，要麼是 aos-exec 完整實作跑得動的檔：inst 單子、當 argv 的 JSON 陣列、`js[$AOS_ENTRY]` 的值。

**[介質、開銷、啟動](CONCEPTS/01-設計理念/08-C-76～C-78.md)**
- **C-76** JSON 是預設介質但不定死，優點擺著、工程上照需要斟酌；給 agent 讀的內容寫 JSON。
- **C-77** 開銷不算啥（LLM 本身最花時間），能包成 aos 函數的盡量包。
- **C-78** 啟動盡量快，四步：複製過去、起 daemon（已有就沿用）、設環境變數（盡量少）、aos-exec 開跑。

**[C-83](CONCEPTS/01-設計理念/09-C-83.md)、[C-85](CONCEPTS/01-設計理念/10-C-85.md)、[C-86](CONCEPTS/01-設計理念/11-C-86.md)**
- **C-83** 可遷移性是上位原則；經 daemon 是建議手段，判準是會不會破壞可遷移性；root daemon 例外、使用者保底；no-pid 那批不放寬。
- **C-85** 每支指令、每個機制的功能要能用一段白話講個大概；講不完的是該簡化或藏起來的候選。
- **C-86** 連字號拆成的獨立程式（`aos-daemon-ctl`）跟同一支的子命令視同一樣；要不要拆只看好不好維護，名字隨意。

## 時空

**[設計理念／時空](CONCEPTS/02-設計理念-時空.md)**
- **C-05** 空間就是資料夾，時間就是時鐘（clock），一格叫 cycle；已定。
- **C-06** 格與格之間，所有與外部有關的狀態一致。
- **C-16** 時鐘定義時間、讓時間能停；停下來後 agent 看到的就是那個時間點的空間，可以打包。
- **C-17** 停下來時正在跑的任務可以不被迫停止；現在只有硬凍：不是行程不停，靠 stack 醒來接著做。
- **C-79** image 模型：daemon＝硬體、stack＝記憶體、ws＝外置記憶體、定義＝source code；image＝root daemon 的 stack＋ws，凍住可搬到別台接著跑。
- **C-26** 沒輸入就每格沒事。
- **C-27** 時鐘走下一格的時機（任務都結束就提前，或固定間隔）應該可選。
- **C-30** 空間可以擴到外部設備（資料庫、硬碟、快取、記憶體、雲端），像 Plan 9。
- **C-31** 行程也掛在空間裡；資源、設備、PU、行程全是空間裡的節點。
- **C-32** 空間就是存放狀態的地方。
- **C-33** 處理（process）＝過一段時間後造成的空間上的變化。
- **C-35** Linux 檔案系統就是一個 LISP（比喻用 table：資料夾＝table、table 裡有 table）。
- **C-37** 時空固定：空間照 Plan 9；時間是時鐘、可看可不看；時鐘可跟 node 狀態完全脫鉤，要看就訂閱。
- **C-44** 時鐘就只是一個時鐘：不包任務、不保證什麼；「格與格之間可以安全打包」是規範、不強制；大家只認 `AOS_CLOCK` 指的那個鐘。
