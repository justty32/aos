## 內部狀態的外顯與窗的族譜

- **N-13**（10-14 定；10-22 定稿，使用者「條文草稿那邊要去解決」，[ideas 10-22 § 5](../../../thinking/2026-10/22/ideas/03-5-loop.md#5-loop10-22)；P-15、P-16）state／ctl＝程式內部狀態的外顯（程式願意分享給大家的，像 Plan 9／FUSE），跟 stdin／stdout／stderr 完全無關。外顯的檔落在 `$AOS_STACK` 底下，**名字與格式由程式自訂**（agent-bob 的 `state.txt`〔11-04 加註：fsm 的這個檔改名 `stage.txt`（使用者題 10「fsm改名，嘗試用同義詞」，[four-elements 07](../../../thinking/2026-11/04/four-elements/07-實作步驟.md) 步 3；fsm.json 的 `start`／`states` 不改）〕 是純文字一行、另有 `trace.jsonl`〔11-03 起 fsm 不寫〕）；需要 stack 的程式沒設 `AOS_STACK` 就退 1、stderr 一行原因（例 aos-fsm，N-38、N-39）；不外顯的就安靜不開、不提醒。外顯後程式自己每隔固定時間同步（讀 ctl、寫 state）時，格式與語意照 N-05～N-11（aos-loop、aos-daemon 照做，`src/engine/window.cpp`）。**11-02 晚補**（使用者「控制自身的 ctl/state 檔案，那就是 ctl/state，不加前綴」，[thinking 11-02 ctl-state-names](../../../thinking/2026-11/02/ctl-state-names/README.md)）：程式**控制自身**的 ctl／state 窗，慣用名 `ctl.json`／`state.json`、不加前綴（loop 這一系全照此：aos-loop、aos-daemon 自己、常駐 bob 控制器）；只有帶 ctl 的才算這一對，身體自己的紀錄檔（`relay_state.json`、`state.txt`〔11-04 起叫 `stage.txt`〕）照舊自訂名。共用 stack 時末端的 ctl／state 跟 base 格式不同，由末端把 base 那對改名加前綴（aos-loop 的 `ctl`／`state` key、`--ctl`／`--state` 旗標就是給這個用的），自己的用 `ctl.json`／`state.json`；例：`aos-foo` 自己認 `ctl.json` 又在同一 stack 起 aos-loop，就給 loop 那份 `"ctl": "loop_ctl.json", "state": "loop_state.json"`。FUSE 可選、以後再說。窗擴成一族（鎖、信箱、心跳…）見 [N-14～N-17](../05-基礎設施-窗.md)。（10-14）
  - **11-02 補**（[thinking 11-02 state 窗](../../../thinking/2026-11/02/state-window/01-使用者原文-11-02-逐字.md#決定11-02使用者)）：aos-loop、aos-daemon 的「寫 state」11-02 起有變才寫、沒有心跳（N-09 的 11-02 補、N-17）；讀 ctl 照舊每次一讀。
  - **11-03 補**（[thinking 11-03 procs](../../../thinking/2026-11/03/procs/README.md) § 5）：**管別人**的窗叫 `<被管的東西>_ctl`／`_state`——daemon 管 procs，所以 `procs_ctl.json`／`procs_state.json`（信箱 `procs_ctl_mailbox/`）；控制自身的照上面 11-02 晚補，仍是 `ctl.json`／`state.json`。
- **N-14**（10-14 定；10-29 定案，使用者 10-29「窗可以跟投遞並列」，看完衝突與方向題回「都照建議」，[thinking 10-29 medium-plan](../../../thinking/2026-10/29/medium-plan/README.md) 決定 1、條文草稿；[10-28 medium](../../../thinking/2026-10/28/medium/README.md) 決定 19）**窗＝只看最新那份的固定檔**：窗只收 state、ctl、公告（只有一人能寫的窗）這類**只有最新那份算數**的檔，每種一條規範。鎖、信箱不算窗：信箱歸投遞（N-16）、鎖另算（N-15，mkdir 那一招跟著鎖走）、一問一答＝投遞＋`reply_to`（N-16）、號誌＝鎖的用法。**強制落在 `$AOS_STACK` 的只有窗**；信箱放哪由擁有者定（N-16）。
  - **共通**：位置落在 `$AOS_STACK` 底下、名字由程式自訂（N-13）；內容是 JSON；原子性只靠 rename（照 N-05）；fsync 不強制；判斷變化比內容或序號，不比 stat；回音以序號 `seq` 為準（例：ctl 加 `seq`，state 回報 `ctl_seq`＝讀到第幾號）；等變化輪詢保底、inotify 加速（/mnt/c 上 inotify 會靜默失效）。
  - **窗不自述種類**（11-04 夜定案：使用者選「正式定下 (Recommended)」，[收斂報告 07](../../../../wf/workflows/tidy/reports/2026-11-03-收斂/07-11-04夜-代定與留給使用者.md#留給使用者看的)；原為 tidy 11-04 代定——11-02 使用者拿掉的是實作的 `kind`，通則改不改原本留給使用者，[thinking 11-02 state 窗 06](../../../thinking/2026-11/02/state-window/06-實作結論-11-02.md)；使用者 11-02「kind沒人在用，那就拿掉」，[thinking 11-02 state 窗](../../../thinking/2026-11/02/state-window/01-使用者原文-11-02-逐字.md#決定11-02使用者)）：aos-loop 的 state 窗、aos-daemon 的 state 與 `procs_state` 窗都不帶 `kind`。信箱的信封也不帶（N-16；使用者 11-03 晚「aos-post這塊都按照建議。」，[thinking 11-03 aos-post](../../../thinking/2026-11/03/aos-post/README.md) 決定 4）。
  - 例：loop 的 ctl 是指令，用「比內容」判新舊（跟上一次讀到的不一樣才算新指令），`seq` 只拿來回音（state 的 `ctl_seq`），寫的人不必先讀 state 算下一號（[thinking 11-03 ctl-commands § 2](../../../thinking/2026-11/03/ctl-commands/02-2-loop-怎麼知道這道是新的-沒有信.md#2-loop-怎麼知道這道是新的沒有信箱)）。
  - 公告的細節待實作時定，見 [IPC 研究頁](https://claude.ai/artifact/7QcbQjrK2h7U9LPcApwpvH)（AI 建議，未拍板）。FUSE 等效能很糟時再說。
