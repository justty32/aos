N-16 接續（上一份的子項到這裡繼續）：

  - **有順序的投遞**（使用者 10-28「另外設置一個檔案或資料夾，有鎖的，大家要投遞就去取鎖，取得順序」）：信箱多 `order.lock/`（N-15 的鎖）與 `order.json`（`{"counter_letters": N}`）；寄信人先照上面在 `tmp/` 寫好信 → 拿鎖 → 讀 N（沒有 `order.json`＝0）→ `order.json` 先寫 N+1（N-05）→ rename 進 `new/<N+1 零填 12 位>.<尾名>` → 放鎖。鎖握到 rename 完，所以到達 `new/` 的順序＝取號順序。**先寫計數再 rename**：死在兩步之間只會缺一個號、不會有兩封同號（使用者 10-29「都按照建議」照實作，[medium-plan 實作時代定](../../../../thinking/2026-10/29/medium-plan/07-實作時代定.md#實作時代定10-29隊長與工人照原則定的細節可翻案) 第 10 條）。
  - **有序、無序同箱**：`send` 帶不帶 `--ordered` 都收。處理順序（`take`、`take-all`、`see`／`done` 的預設都用同一套）：有序的全部在前、照序號；無序的在後、照名字（預設名時間開頭＝寄出先後）；無序的被有序的一直插隊也接受。有序缺號不等、直接拿下一號，照名字排好從頭拿、不逐號探（使用者「有序的人缺號時，我怕下一個號碼是幾百號之後，實作的時候要小心，不要每號都確認。」）。信經判官（`AOS_KERNEL`）轉寄時預設不保有序，見 N-42 (2)（[../09-kernel.md](../../09-kernel.md)；使用者裁定，出處 [wf/workflows/refactor/reports/2026-11-07-sol審查/11-使用者裁定.md](../../../../../wf/workflows/refactor/reports/2026-11-07-sol審查/11-使用者裁定.md) #3）。
  - **queue**（使用者 10-30「這一層更接近訊息的queue概念，請求的投遞倒是可以用信箱概念，但也可以用queue概念」、看完規劃回「都照建議」，[10-29 agent-bob](../../../../thinking/2026-10/29/agent-bob/04-頂層對八題的再想.md#決定10-30) 決定 33、36，[thinking 10-30 agent-lifecycle](../../../../thinking/2026-10/30/agent-lifecycle/07-衝突.md#決定10-30) 條文草稿、A-1、A-10）：agent 層把自己的輸入叫 **queue**，它就是本條的有順序投遞（同箱也收無序的，照上面排在後面），資料夾叫 `queue/`、位置在那隻 agent 的 `$AOS_STACK`（[CONVENTION P-11、P-42](../../../CONVENTION/02-題目stack停錯腦.md)）；「信箱」這個詞留給 agent 之間的請求投遞（一封封獨立的信，可能要回信、可以不照順序）。
  - **問腦總機自己的信箱**（[`lib/aos/kernel_llm`](../../../../lib/aos/kernel_llm/README.md)；[aos-llm](../../../../impls/aos-llm/README.md)，[thinking 2026-10-24-llm-kernel](../../../../thinking/2026-10/24/llm-kernel/README.md)；衝突 3；方向題 3，等 kernel 下一次大改再一起收）：信箱固定 `$AOS_STACK/requests/`（跟判官的收件箱同名，C-54 R14；使用者 11-06 選項框「現在統一 requests/」，[mailbox-naming](../../../../thinking/2026-11/06/mailbox-naming/README.md)）；`AOS_LLM_KERNEL`＝llm kernel 的 stack，寄信的人找 `<stack>/requests/`（N-42 (1)、N-63，[thinking 11-05 kernel-daemon 07](../../../../thinking/2026-11/05/kernel-daemon/07-llm-daemon佈局.md)）；kernel 用 flock 鎖整個信箱，flock 用的檔見 N-15「名字分清」。
    - **請求與回信**（使用者 11-04 晚「llm呼叫這塊，我希望是把請求丟到llm kernel(一個loop)，處理好後收回信」「然後aos llm,tool這兩個，我希望他們的定位是跟aos post一樣，作為基礎工具」，[thinking 11-04 think-as-function](../../../../thinking/2026-11/04/think-as-function/README.md)；細節 fable 代定、可翻案）：請求信由 `aos-llm` 寄，信只帶請求、全部在 `body`：body＝`{"endpoint"?, "request", "priority"?}`，信封 `reply_to` 必有——`aos-llm send --reply-to BOX` 寫寄信人自己的信箱（非同步），`aos-llm ask` 寫 `<stack>/requests/reply/`（同步、共用，靠 `in_reply_to` 認自己的）；kernel 照本條寄回信（`in_reply_to`＝原信件名稱、`body`＝`{"message", "usage", "model"}` 或 `{"error"}`）（[medium-plan](../../../../thinking/2026-10/29/medium-plan/README.md) 實作第 6 步後半、決定 3；[實作時代定](../../../../thinking/2026-10/29/medium-plan/07-實作時代定.md#實作時代定10-29隊長與工人照原則定的細節可翻案) 第 14 條；N-42 (1)）。
    - **不留紀錄**（使用者「很多都是自己要承擔的風險。舊信根本不用留，就是刪」，[think-as-function 08 題 3](../../../../thinking/2026-11/04/think-as-function/08-邊緣狀況實測.md#留給你的題白話推薦放第一)；使用者選「也刪」）：信寄完回信就整封刪掉（沒寫 `reply_to`、回信寄不進＝回信沒人收，信照刪），kernel 不留任何一封的紀錄。
  - 題目信箱（[CONVENTION P-11](../../../CONVENTION/02-題目stack停錯腦/01-P-11～P-14.md)）不算標準投遞（衝突 2）。
