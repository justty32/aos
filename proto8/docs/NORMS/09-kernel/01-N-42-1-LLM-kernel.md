# kernel 規範：N-42 (1) LLM kernel

（11-05 午從 [09-kernel](../09-kernel.md) 逐字搬來：那檔超過 8 KB；連結多一層 `../`。）

  - **(1) LLM kernel**（使用者 10-24「LLM kernel，也就是把brain這塊弄成一個請求，而不是直接打API，請求會被丟到某個地方，由kernel排隊跑」；照 [10-15 LLM kernel](../../../thinking/2026-10/15/llm-kernel.md) 已定的六條〔10-15 使用者「隨意」、照建議預設定案〕與 [kernel 截流](../../../thinking/2026-10/15/kernel-intercept.md) 的閘門／信箱草案，細節照推薦定、可翻案，見 [thinking 2026-10-24-llm-kernel](../../../thinking/2026-10/24/llm-kernel/README.md)；11-04 晚使用者「llm呼叫這塊，我希望是把請求丟到llm kernel(一個loop)，處理好後收回信」「也可以是一個daemon，實際endpoint呼叫就是aos exec」「包起來的」「我是希望走2」「各種llm設定也可以包裝，這樣寄信的時候只要寫簡單的代號就可以」，細節 fable 照原則代定、可翻案，[thinking 11-04 think-as-function](../../../thinking/2026-11/04/think-as-function/README.md)）：基於 daemon（kernel 是 daemon 或 loop 一次次拍的一張單子，C-47；範本 `kernel/llm-kernel`＝aos-loop 每 300 ms 拍一次 `aos-llm-kernel kernel.json`，可 `aos-daemon-ctl add` 掛成 daemon 的 proc；**11-05 改**：llm kernel 是自己一台 daemon〔daemon＋kernel 合一，daemon.json 的身體＝`aos-llm-kernel`，繼承式〕，[kernel-daemon 07](../../../thinking/2026-11/05/kernel-daemon/07-llm-daemon佈局.md)）。對外只有**信箱＋`aos-llm`**（「包起來的」＝裡面怎麼跑呼叫端不知道，C-52）：
    - **信帶請求、不帶單子**：請求信（N-16）的 body＝`{"endpoint"?: 代號, "request": OpenAI chat completions body 去掉端點, "priority"?}`，信封 `reply_to` 必有；回信 body＝`{"message", "usage", "model"}` 或 `{"error": {"code", "msg"}}`，`in_reply_to`＝請求信的名稱。`request` 寫 `stream`＝`RequestBad`（串流不做）。
    - **kernel 跑自己的 endpoint 函數**：`kernel.json`＝`mailbox`、`slots`、`budget`、`timeout_ms`（跑一封的上限，選填）、`exec`（預設 endpoint 函數＝aos-exec 目標，範本 `lib/base/llm_http`：stdin `{"endpoint", "request"}` → POST `{url}/chat/completions` → stdout `{"message", "usage", "model"}`）、`endpoints`（代號 → 一組設定，一組可自帶 `exec`，例 `fake`→`lib/base/llm_fake`；其他鍵原樣交給 endpoint 函數，指示詞照 N-45 解，金鑰寫 `{"$env"}`／`{"$ref"}`）、`endpoint`（預設代號）。kernel 用 aos-exec 跑那組的 `exec`（環境是 kernel 自己的、stack＝那封信的資料夾），stdout 當回信照 `reply_to` 寄回。代號錯：信沒寫、kernel 也沒預設＝`EndpointMissing`；信寫的表裡沒有＝`EndpointUnknown`；endpoint 函數退非 0＝`EndpointFailed`；body 不合形狀＝`RequestBad`。
      - **11-05 改**（使用者 11-05「同一回事，因為問腦，他本身也可以包裝成一個aos函數，掛成proc去跑。我也建議這樣。」「他的proc是掛在linux底下，而非daemon底下。不太...好，但demo可以這樣啦」「所以...還是都包成aos函數吧」「能包盡量包啦」；C-47 11-05 加嚴；細節 fable 照原則代定、可翻案，[thinking 11-05 kernel-daemon 03](../../../thinking/2026-11/05/kernel-daemon/03-問腦改掛daemon.md)）：上面「kernel 用 aos-exec 跑那組的 `exec`（環境是 kernel 自己的…）」改成 **kernel 不自己跑**：把每次問腦寫成一封 `procs_added` 信，請 daemon 掛成 **`max: 1` 的 loop 型 proc**——名字 `llm_<信件名稱>`、`stack`＝那封信的資料夾、內嵌單子 `{"argv": ["aos-exec", 那組的 exec], "stdin", "stdout", "timeout_ms"}`（`stdin`＝`request.json`、`stdout`＝`reply.json`）；下一拍從那個資料夾的 `state.json`（`phase`＋`code`）＋`reply.json` 收成品、照 `reply_to` 回信。掛信寄 `$AOS_KERNEL`（有設，N-63）、否則 `$AOS_DAEMON` 的 ctl 信箱；沒 `AOS_DAEMON`＝`DaemonMissing`（不在 daemon 下的不管）。信箱固定 `$AOS_STACK/mailbox/`，`kernel.json` 的 `mailbox` key 拿掉（寫了不看）。endpoint 函數的環境是 daemon 給子項的（`AOS_DAEMON`、daemon 的 `AOS_WS`），stack 仍是那封信的資料夾。一拍不再等子行程（收成品→收新信→補位到 `slots`），舊的「一次裡不補位」、`RunFailed` 退場。 **11-06 改名**（使用者 11-06 選項框「現在統一 requests/」，[mailbox-naming](../../../thinking/2026-11/06/mailbox-naming/README.md)）：llm kernel 的信箱 `$AOS_STACK/mailbox/` 改名 `$AOS_STACK/requests/`（跟判官的收件箱同名，C-54 R14），寄信的人找 `<stack>/requests/`，`ask` 的共用回信信箱跟著是 `<stack>/requests/reply/`；本條寫 `mailbox/` 的地方照這個讀，舊名不認（使用者 11-05「一律當成沒有舊版」）。
    - **非同步 `aos-llm send`／`recv`**：`send [--priority P] --reply-to BOX`（stdin＝整份 body）寄完印信件名稱、馬上回，不建 `sender.flock`——沒鎖檔＝kernel 不判寄信人存活、照跑；`recv BOX 名` 到 BOX 找那封的回信（0 到／10 沒到／1 錯）；**同步 `ask`**＝寄（回信信箱 `$AOS_LLM_KERNEL/reply/`〔**11-05 改**：`AOS_LLM_KERNEL`＝llm kernel 的 stack，信箱＝`$AOS_LLM_KERNEL/mailbox/`、回信信箱＝`$AOS_LLM_KERNEL/mailbox/reply/`，N-63〕、建 `sender.flock`）＋等＋印 `message`；`regret` 撤回還沒被認領的請求。
    - kernel 一次挑最該跑的（級數＋aging → 時限 → 等得久 → 先寄）、同時跑 `slots` 封；用量從回信的 `usage` 記；`budget` 設 `max_calls`／`max_tokens` 每窗上限，到頂回 `BudgetMissing`（或設成等下一窗），見 [thinking](../../../thinking/2026-10/24/llm-kernel/02-邊緣狀況.md#token-回報與額度10-24-下午)。
    - **11-04 晚已改**：原本 agent 那格跑閘門 `aos-llm-send`，閘門把「問腦」那張單子＋寄信那一刻的整份環境寫成信、站著等回信、原樣交回；kernel 照單子跑（排序多一條單子 `_metainfo.time_ms` 短的先）；kernel 跑信時給 `AOS_KERNEL_REPORT`、腦願意就寫 `usage`；`kernel.json` 的 `accept` 只跑名單裡的單子。現在信裡沒單子：`aos-llm-send` 改名 `aos-llm`、長出 `send`／`recv`／`ask`／`regret`（使用者 11-04 晚「然後aos llm,tool這兩個，我希望他們的定位是跟aos post一樣，作為基礎工具」「並且可以的話，考慮非同步呼叫，也就是正在跑的loop不停。」）；`_metainfo` 兩個排序依據、`AOS_KERNEL_REPORT`、`accept` 拿掉；舊閘門的信（頂層 `inst`／`env`）＝`LetterBad`。非同步沒鎖檔＝不判存活是衝突 2 照推薦 (a)，隊長先實作、可翻案（[05](../../../thinking/2026-11/04/think-as-function/05-衝突與方向題.md)）。
    - **11-06 改讀**：上句「衝突 2 照推薦 (a)，隊長先實作、可翻案」已有使用者 11-04 晚選「照跑不丟」定案；非同步沒有 `sender.flock` 就不判寄信人存活、照跑，已實作（[think-as-function 05](../../../thinking/2026-11/04/think-as-function/05-衝突與方向題.md)）。
    - **11-06 註**：llm kernel 的 `priority.deadline` 是跨樹信裡的期限，留毫秒（使用者 11-06「信裡用毫秒」）；kernel 內部計時才用自己樹的鐘。已定（11-06，[daemon-board](../../../thinking/2026-11/06/daemon-board/README.md)）；實作排在 T4（緊接 S9），兩鐘規則見 [N-65](../02-設計理念-時空.md)。**已實作（11-06 T4）**：`priority.deadline` 照舊 ISO 8601 或 epoch 秒、kernel 不讀信裡的 cycle 欄；kernel 自己的 aging 改數 cycle（`kernel.json` 選填 `aging_cycles`，預設 3），[tick-time 04](../../../thinking/2026-11/05/tick-time/04-T線實作結果.md)。
