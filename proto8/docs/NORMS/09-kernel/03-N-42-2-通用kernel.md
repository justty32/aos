# kernel 規範：N-42 (2) 通用 kernel

- **(2) 通用 kernel**：普通的掛 proc 請求去它那（C-47「多種 syscall」）。框架站（通用 kernel 的站，原判官已收進來）是 [`py/tools/aos/kernel`](../../../py/tools/aos/kernel/README.md)，零件與鍵見 [kernel README](../../../templates/kernels/README.md)；兩個範例擺法——0 號 proc 式範本 `kernel/procs-kernel`、繼承式範本 `kernel/daemon-kernel`（[kernel-daemon 02](../../../thinking/2026-11/05/kernel-daemon/02-兩種模式.md)，C-47「擺法只是範例」）。**以 agent 作判斷**走框架站的口：`after_verdict` hook 回 `hold` 把信先留著，agent 表態（`decisions/<信名>.json`），轉寄由站做；現成的搭法是工具 `kernel_gate`（[py/tools/aos/kernel README「先留著等表態」](../../../py/tools/aos/kernel/README.md)、[thinking 11-13 eca-as-kernel](../../../thinking/2026-11/13/eca-as-kernel.md)；使用者 11-13「1乙，總之先做。」）。
  - **框架是一包方便零件**（方向已定；以下各點同）——收信、規則＋hook、下一站、回信、排隊——不是概念，手寫一個也算 kernel；判官收進這個框架（使用者 11-11「判官這東西...我覺得應該將其吸納進我們之後的kernel框架中。」，[thinking 11-11 kernel](../../../thinking/2026-11/11/kernel/README.md)）。
  - **下一站照三段找**：先看設定檔 `kernel.json` 的 `next`（選項框「寫進 judge.json」，設定檔現在叫 `kernel.json`）；沒寫就看 `AOS_KERNEL`，它指到自己就跳過；再沒有才寄給 `AOS_DAEMON`（使用者 11-13：「Hmmm，好啦，next也可以。只是說，我會覺得AOS_KERNEL他就是在有需要掛一個aos proc的時候，就使用的一個目標，一個通用的，基礎的目標。好比所有C語言程式使用syscall的時候，只要沒有特別指定，不然就是走linux kernel那個記憶體位置。啊如果有需要其他目標...那就自己找方法指定」；三段的順序出自使用者 11-13 待裁頁 `kf-next:B*（備註：如果覺得麻煩，那就直接報錯算了）`，[回覆檔](../../../thinking/2026-11/13/decide_20261113_wu-r2.reply.txt)、[11-13 kernel-framework-開工](../../../thinking/2026-11/13/kernel-framework-開工.md)）。明寫的 `next` 指到自己＝設定錯、不跳過（代定，出處同一份開工紀錄）。`next` 只有一個；要照規則把不同的信轉給不同的下一站（一封只去一處），分流規則寫在 hook 裡——`after_verdict` hook 替那一封指定下一站，沒指定的照三段（使用者 11-13「按照規則分流吧。就用hook」；做法與限制是代定，在 [`py/tools/aos/kernel` README「分流」](../../../py/tools/aos/kernel/README.md#分流hook-替這一封指定下一站)與同一份開工紀錄第十三節）。
  - **數量另指**（「數量另外指一台」）：設定可另寫 `count_daemon`＝`max_running` 去哪台 daemon 數；寫了 `next`、或下一站取自 `AOS_KERNEL`、或 hook 替單封信指定了 `next`，又設了 `max_running`，就必須寫 `count_daemon`，沒寫＝`CfgBad`；只有下一站是從 `AOS_DAEMON` 來的才預設數 `AOS_DAEMON`（使用者 11-13 選「甲」，條文照程式）。
  - **hook 三個時機**（「判決前」「判決後」「回信經過時」，最後一個只在該站選了回信先回我時才有，沿用 agent 的 hook 契約）：事件名 `before_verdict`、`after_verdict`、`before_reply`，寫在 `kernel.json` 的 `hooks`；回信先回我的鍵是 `reply_via_me`。
  - 回信對 `reply_to` 二選一照 C-47「轉交也算」。停／收／睡／醒要不要判，是收件 proc 自己的事。同批另一題「daemon 收到壞的掛 proc 信」裁「改成會回」（回 `applied:false` 加原因），是 daemon 自己的事，跟框架分開。
    - 框架站的隊列只有先來先掛；要優先序、期限、額度＝寫一個 kernel 身體（llm kernel 是範例）。
    - **框架站排不排隊**是 `kernel.json` 的選項（使用者 11-06「我原本預期他就是能管准入也能管排隊...或許可以做選項？」）。程式本身沒寫＝不排（格滿立刻回 `SlotMissing`）；範本 `kernel/daemon-kernel` 的 `kernel.json` 預設寫 `queue: true`，照範本開出來的框架站格滿就排隊。（使用者裁定，出處 [sol 審查 11-使用者裁定](../../../../wf/workflows/refactor/reports/2026-11-07-sol審查/11-使用者裁定.md) #1）
    - **有序信經框架站**：使用者 11-07「我希望這是可選的。默認是不帶有序。」——`kernel.json` 有兩個各自獨立、照字面的開關，都選填、沒寫＝關：`keep_ordered`（照有序轉寄）與 `reply_via_me`（回信先回我、由框架站代回）。`keep_ordered` 關：框架站把有序信當一般信轉寄給 daemon，「有序」只保證到框架站門口；daemon 的回信對的是轉寄後的信名，要回信對得上原信就寄一般信。`keep_ordered` 開：照有序轉寄，轉寄後是新信名；只開它時下游直接回，回信的 `in_reply_to` 是新信名、對不上原信。`reply_via_me` 開：框架站自己記「新信名→原信名」的對照表，收到下游的回信後以原信名代回給原寄件人。要保有序又要回信對得上原信，兩個都開（[kernel docs 02](../../../templates/kernels/docs/02-kernel-modes.md)）。（使用者裁定，出處同上 #3；兩個開關各自獨立、照程式寫，出自使用者 11-13 待裁頁 `kf-t1:A*`，[回覆檔](../../../thinking/2026-11/13/decide_20261113_wu-r2.reply.txt)）
    - **停／收／睡／醒不必過框架站**：要不要判是收件 proc 自己的事；沙箱裡的東西只要一個信箱就夠，照 C-47 一律寄 `AOS_KERNEL`（使用者 11-05 晚對「只要一個信箱」的方向說「是的，你真聰明！」，[no-pid README「定下的」7](../../../thinking/2026-11/05/no-pid/README.md)）。
    - **`aos-daemon-ctl` 一律直寄**：要經 kernel 就走 `AOS_KERNEL` 的路（`aos-agent ctl`）；`aos-daemon-ctl` 是指名要碰某台 daemon 的工具，不看 `AOS_KERNEL`、一律直寄，能不能直寄靠 Linux 權限（C-47「安全的保底是 Linux 本身」；N-63 實例 `AOS_KERNEL`）；它是人直接敲板子的保底，「只能經過 kernel」只約束 proc（使用者裁定，選項框「維持直寄，它就是『指名 daemon』的工具」，[os-impl 08](../../../thinking/2026-11/06/os-impl/08-aos-daemon-ctl永遠直寄實作結果.md)；11-13 照現況，[裁定落地-1113](../../../thinking/2026-11/13/裁定落地-1113.md) kb-ctl）。
    - **ping**：框架站對 `{"ping": true}` 照 C-48 原樣轉寄，不另加判斷（[no-pid 10 P3](../../../thinking/2026-11/05/no-pid/10-P3實作結果.md)）。
