## 函數的 _metainfo.json：估的成本與逾時（11-07）

- **N-68**（11-07 使用者裁定，thinking [evolve-design](../../../thinking/2026-11/07/evolve-design/README.md)、[kb-ideas](../../../thinking/2026-11/07/kb-ideas/README.md)）**`_metainfo.json` 裡估的成本放 `cost`**。成本是三維：token、呼叫次數、時間（使用者 11-07 午後選「token／呼叫次數／秒」，傍晚又說「本機模型的速度很慢，也差不多到了將時間成本也算進去的時候了」）。key 照 C-54：`token`（`in`／`out`／`cached`）、`counter_calls`、`time_ms`；`cost` 裡還想放什麼就放（錢等等，C-14 人可以任意附加特性），不認得的 key 照 C-48 忽略。每個值照 C-48 的雙形：純數，或展開成 `{"val", "max"?}`。`cost` 是函數自己宣稱、估的，會隨輸入變；跑的時候誰都不改這個檔（待定之一「實測不回寫」照舊）。已定；讀它的 `lib/metainfo.py` 排在 evolve-design 落地步 1。

估多久跟多久就殺是兩件事，分兩個 key：`cost.time_ms` 是估時（宣告，給排程與審視參考，不強制）；頂層 `timeout_ms` 是逾時（行為：到了就殺，act、aos-mcp 照它）。頂層的 `time_ms` 拿掉，原本的 `time_ms.val` 搬到 `cost.time_ms`、`time_ms.max` 搬到 `timeout_ms`；工具檔用腳本一次改完、不做相容（照使用者 11-05「一律當成沒有舊版」）。已定；改檔與 act.py、aos-mcp 改讀排在 evolve-design 落地步 2（現在 lib 下 28 份 `_metainfo.json` 仍是頂層 `time_ms`）。

成本的值要隨輸入變，就寫公式；**公式用語言名當 key**（使用者 11-07：「直接寫"lua":"...."或"py":"..."，然後呼叫相應lua.exe/python.exe(這臺是linux，沒有)。或是直接跑aos函數。初期可以用簡單的四則+min/max。其實沒啥規定，就是隨着複雜度增加，可以替換到所需技術棧。搞不好到後面，就是呼叫aos　agent」）。例：`{"cal": "4000 + in_bytes * 1.2"}`（四則、括號、`min`／`max`）、`{"lua": "..."}`、`{"py": "..."}`、`{"aos": "<aos 函數路徑>"}`（stdin 給變數、stdout 印數字，裡面是腳本或 agent 都行）。key 決定用哪種求值器；複雜度上來就換 key，格式不變。同一格只寫一種。只有讀 metainfo 的人（審視者、measure 之類）會算；讀者沒有那種求值器，就當這格沒有估值，不報錯（C-48 不認得就忽略）。aos-exec 與指示詞不碰這些 key。已定；起步只實作 `cal`，排在 evolve-design 落地步 1；`lua`／`py`／`aos` 等用到再接。公式 key 不是指示詞、只有讀者算這一點，11-07 傍晚使用者在選項框照推薦裁定（[lift-to-norms](../../../thinking/2026-11/07/lift-to-norms/README.md) ltn-6）。

**設計者寫的估值與 agent 自報的估值要分清；metainfo 不強迫**（11-07 傍晚使用者裁定 evo-A，選「平常只報告；要拿估值排程或挑目標時，不準的定義改用他見的中位數」，備註原話）：「hmmm，函數自報估值，老實說，應該是函數的設計者當初給函數寫下的估值，而agent作爲函數他確實會自報估值。兩者要分清。函數設計者給函數寫下的估值，這件事，hmmm，首先我要說，不是所有函數設計者都會寫這種估值，所以不能假定永遠都有metainfo，而且我們也不該強迫。一些比較笨的agent，你讓他報估值他也會報錯，那不如就只看他的說明就好。函數九軸是基礎特性，我們是建議不管多簡單或多笨的函數或agent都準備一份描述這個的metainfo啦，但不強迫。產出metainfo這件事，也是可以優化的一環，但我覺得除非是改進者之流，不然這屬於比較次要的要優化的東西。」白話：`_metainfo.json` 裡的估值是**函數設計者**當初寫下的；agent 作為函數在跑的時候也可能**自己報**估值，兩者分開記、分開評，不混成一份。不是每個設計者都會寫，所以讀者不能假定 `_metainfo.json` 一定存在，也不強迫寫；**建議**不管多簡單的函數或 agent 都備一份描述九軸（[C-13](../../CONCEPTS/04-kernel.md)）的 metainfo。比較笨的 agent 報估值常報錯，就不要它報、只看它的說明。估值不準不擋路：平常只報告，kernel 或審視者要拿估值排程、挑目標時，被評為不準的定義改用實測的中位數。把 metainfo 寫好也是可以優化的一環，但除了改進者這類函數，算次要目標。已定；評估工具 `metainfo_check` 排在 evolve-design（[README](../../../thinking/2026-11/07/evolve-design/README.md)）。

**AI 用起來順不順：`comfort` 與 `aos-feedback`**（使用者 11-07 晚想法 18：「如果高階AI覺得這個命令行用法不順手，說明看不懂，或是有一些其他建議。也都可以順便提出來順便改進。metainfo中，或許可以有所謂的人體工學舒適度(AI工學舒適度？wwwwww)。如果高階AI有意見的是aos體系的基礎函數和標準庫那些，那可能先搜集意見，等有空再來做了」；補充：「因爲人體工學舒適度需要我這個使用者評分，所以可以先用AI的角度去評價。一個值可以細分這樣。」「claude系在這塊比較擅長，gpt系會稍弱，所以AI子項又可以分成這兩項。乃至gemini系，qwen系...，還有高中低階的各階位AI評分。」）白話：任何 agent 用 aos 指令覺得不順，就用 `aos-feedback add <指令> <哪裡不順> [建議]` 送一筆，存在 `proto8/feedback/<指令>.jsonl`；aos 基礎函數與標準庫的意見只收、有空再改，各線自己的工具可以當場改。`_metainfo.json` 可選填 `comfort`（設計者自稱），形狀是 AI 角度四個子項（`usage` 用法、`help` 說明、`errors` 錯誤訊息、`args` 參數，各 0～1）、按評分者家族與階位分開的 `ai_by`、預留的 `user`（使用者評分，現在一律 null、有需要再等他有空）與匯總的 `val`；照 C-48 只寫一個數字＝只有 `val`。他見的舒適度不回寫，由 `aos-feedback score` 從意見的評分與帳裡的錯誤、重試算出，公式是起步值、可再改（想法 15）。評分者的家族、階位是自由字串，對照表在 `proto8/feedback/raters.json`，加新家族加一列。代定，[impl-plan 代定 9、10](../../../thinking/2026-11/07/impl-plan/代定.md)；實作排在 impl-plan 批 4b。
