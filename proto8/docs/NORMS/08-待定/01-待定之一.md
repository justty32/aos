（只列真的還沒定的；有答案的、被推翻的整條刪。）

- 【agent】**agent 當工具時，題目怎麼交給它**（10-19，方向問題甲）：bob 的 act 叫 cathy。cathy 是標準範本，認 `$AOS_WS/new/` 一題一檔（認領時搬到 `cur/`）（舊協議；走 queue 的 agent 看 `$AOS_STACK/queue/`，P-11）。預設 (a)＝**呼叫方照被叫者自己的說明備題**：cathy 的說明說她看 `new/`，所以 bob 在她的小格裡開 `ws/new/<題名>`、叫她、從 `ws/out/<題名>` 拿答案；這不是規則、是 cathy 的介面（CONVENTION P-26）。另一條路 (b)＝agent 當工具時統一「題目 stdin 進、答案 stdout 出」（像 stamp）：bob 叫 cathy 跟叫 stamp 一行一樣，代價是 cathy 得多一層入口把 stdin 寫進自己的 `new/`、跑完 `cat out/`，又回到 10-15 被使用者否決的 `sh -c '…; …'` 那種殼。要不要定一個共同的題目／答案通道，等於把 `new/` 或 stdin 定成共同形狀，跟使用者 10-19「inbox 先不管」要再對一次。沒回答就照 (a)。腦的工具呼叫（[CONVENTION P-41](../../CONVENTION.md)，[thinking 2026-10-23-tool-calls](../../../thinking/2026-10/23/tool-calls/README.md)）只定「腦可以叫的工具」stdin 進、stdout 出；agent 當腦的工具要在它自己的 `_entry` 轉接；(a)(b) 仍未定。
- 【daemon、kernel、tasks、tick】**照「資料夾＝程式」重寫**：daemon 與窗（N-28、N-54、N-17）已重寫，是 impls 的 aos-daemon、aos-loop（使用者 10-23「python版本可以刪掉了。aos-exec/loop/daemon都用C++」，tick 先留 Python）；tick 已照 10-12 的規格重寫成 `proto8/cmd/aos-tick/bin/aos-tick`（[計畫](../../../thinking/2026-10/21/plan/README.md) 第 4 段），N-01～N-03 的時鐘有實作、打包（N-03）仍無；LLM kernel 第一版做了（使用者「LLM kernel，也就是把brain這塊弄成一個請求」，impls 的 aos-llm-kernel＋aos-llm-send〔11-04 晚改名 aos-llm、信改帶請求，[think-as-function](../../../thinking/2026-11/04/think-as-function/README.md)〕，[thinking](../../../thinking/2026-10/24/llm-kernel/README.md)）；信長怎樣、資料夾式信箱 N-16 照那份紀錄（照推薦定、可翻案；10-29 投遞標準已定，見 [N-16](../05-基礎設施-窗/05-N-16.md) 的 10-29 改口）。還沒做的：通用 kernel（N-42）、tasks 的 seq／par／if（N-34）、鎖 N-15（條文 10-29 已定），概念（C-36、C-09～C-15、C-47、C-41、C-44）與規範留著、標「現無實作」。tick、seq／par／if 都是幾十行的資料夾程式；通用 kernel 在新做法下還沒討論過。等使用者說要哪個。
- 【fsm】**相對於這格的 exec**（10-24，[thinking](../../../thinking/2026-10/24/exec-relative/README.md)）：已解——使用者「不過exec本來就應該要可以直接放內嵌單子吧」「好，就這樣做」：`exec` 直接放單子物件（路 3），跑的期間 `AOS_CO`＝`/states/<名>/exec`，不必再指回自己（N-36），[thinking 10-24](../../../thinking/2026-10/24/exec-relative/01-使用者原文.md#10-24-exec-直接放單子)。路 1（fsm 解格前把 `AOS_CO` 設成那格的位置；使用者「勉強可接受」）不做（頂層代定，可翻案）。
- 【kernel】**kernel 評估納入錯誤路徑**（使用者 10-15：錯誤路徑濃縮「這塊後續也可以納入kernel評估中」，[原文](../../../thinking/2026-10/15/principles/README.md)，C-53）：kernel 看一個程式（或一棵呼叫樹）時，除了九軸、資源，也可量「出問題之後的行為」有多複雜——例：會退出的錯誤種類、結束碼種類、出錯後的分支數（重試、退回、停住、等人）、是否宣告了三種姿態。量法、寫在哪（`_metainfo`？）、拿來做什麼（排序？警告？）都還沒定。

- 【基礎設施／inst＋kernel】**`_metainfo`**：單子裡給 kernel 參考的抽屜（九軸、資源特性），inst 格式的可選 key（地位同 `argv`）、inst 與完整實作忽略；裡面格式自由，通用的寫法（含資源）之後規定——出處 [thinking 10-13 §3](../../../thinking/2026-10/13/json-path/README.md)。**10-24 已照推薦定、待落條文**：使用者 10-24「一個函數是用_entry去跑。其特性我想要將其寫到_metainfo，裏面可以存放該函數要跑多久，要喫多少資源這種東西。相關的.json格式也要規劃。然後kernel也可以透過這個，來做參考」，規劃後「都按建議做」——三處同名（資料夾 `_metainfo` 檔、JSON 物件與單子的 key；**11-04 註**：資料夾裡的檔改名 `_metainfo.json`、key 名不變，使用者 11-04 題 8「留 _、加 .json」，[four-elements 06](../../../thinking/2026-11/04/four-elements/06-要使用者裁的題.md#使用者裁定11-04選項原文或他的話逐字)）、找法同找入口、通用 key 全選填、`timeout_ms` 才強制、實測不回寫，M1～M10 見 [thinking 10-24 `_metainfo`](../../../thinking/2026-10/24/metainfo/README.md)；CONCEPTS／NORMS 正文等頂層統一落。
- 【總則／布局】**函數成長**（10-24，[thinking](../../../thinking/2026-10/24/fn-grow/README.md)）：一個函數太大或特性到了就長一級（0 內嵌 → 1 同檔具名 → 2 單檔 `x.json` → 3 資料夾只有 `_entry` → 4 不只入口 → 5 有子函數），第 2 級起呼叫方只寫 `"x"`；門檻沿用 [STRUCTURE](../../../../wf/STRUCTURE.md) 加被幾處叫、伴隨檔、`_metainfo` 特性；搬時只改 `cwd`／`$ref`／`$env AOS_CD` 指回原處。使用者 10-24「都按建議做」→ **已照推薦定、待落條文**（預定補進 C-55；原型 [grow/](../../../cmd/aos-grow/README.md)）。
