N-43 接續（上一份的子項到這裡繼續）：

  - **錯誤分類靠 stderr 代號，結束碼仍一律 1**（使用者 10-28「照新做法」，[thinking 10-28 agent-ops 決定 11](../../../thinking/2026-10/28/agent-ops/02-決定.md#決定10-28)；細節照原則代定、可翻案，[agent-round § 4 endpoint 的錯](../../../thinking/2026-10/28/agent-round/02-2-round-一輪本身.md#4-單位介面)）：要讓別人分種類的錯，寫在 stderr 錯誤行的代號裡（`名: error: 代號 原因`，代號照 C-54；例 endpoint 函數 `lib/base/llm_http` 退 `EndpointFailed`、`KeyBad`、`ReplyBad`，`aos-llm` 退 `LlmKernelMissing`、`RequestBad`；要分 429 跟 503 看原因裡的數字），不另用結束碼分。
  - **stderr 只有兩種行**（使用者 11-05，問「退 0 時提醒能不能印 stderr」答：「可以，固定格式："error:", "warning:"後面接你那個」；[thinking 11-05 stdio-unify](../../../thinking/2026-11/05/stdio-unify/README.md) R1）：aos 自己的程式寫 stderr 只有兩種行——
    - **錯誤行** `程式: error: 代號 原因`（例 `aos-post: error: MailboxMissing no mailbox at /x`）：代號＝`error: ` 後第一個字（C-54），解析代號的地方都照這個拆；要附用法放在原因後面 `(usage: …)`（CONVENTION P-44）；開頭可以是 agent 名（P-21）。
    - **提醒行** `程式: warning: 句子`（不帶代號）：長駐程式的 log、給人看的狀態句（attaching、watching…）、「沒出錯但該讓人知道」的事都寫成這種；互動提示符（aos-agent chat 的 `> `）不算一行（代定 D5）。
    - 退 0 可以有提醒行；**有錯誤行就不准退 0**。其他雜訊（括號句、`note:`、不帶前綴的 log）改成提醒行或拿掉。透明轉交（exec 交棒、照下層碼結束）不受影響：那時的 stderr 是下層的。
  - **塞進對話的文字只有一種形狀**（使用者 11-10 提到 `[aos] warning: ...`、`[aos] summary: ...` 這種寫法，頂層提議統一成 `[aos] 種類: 內容`，使用者「1.可以。2.好，統一。」，[tonight-rulings 項 A](../../../thinking/2026-11/10/tonight-rulings/README.md)）：aos 自己塞進 agent 對話的文字（摘要、換對話的開場、時鐘信、hook 攔下、工具逾時與退碼、提醒…）一律寫成 `[aos] 種類: 內容`。各種類的名字（`summary`、`session`、`clock`、`hook`、`tool`、`warning`、`new_mail`、`goal`、`fork`、`slash`；現有種類表在 `py/aos_flags.py`）是代定、可翻案（[tonight-rulings 項 A](../../../thinking/2026-11/10/tonight-rulings/README.md)）。畫面開著的 claude 身把信投進 CLI 的收件口時（CONVENTION P-43），外面多一層 CLI 的訊息信封：署名（寄件人或「aos通知中心」）與尾巴一行英文說明是信封上的字，不算這種文字；信的內文照舊是這個形狀。
  - **10 的兩種讀法**（照盤點推薦，[thinking 11-05 stdio-unify](../../../thinking/2026-11/05/stdio-unify/README.md) R9）：(a) 基礎工具（aos-post、aos-lock、`aos-llm recv`、`aos-json check`…）的 10＝「**查了，沒有**」（沒信、沒鎖、還沒回、驗不過有問題〔aos-json check，代定 D1〕），不是錯、不寫錯誤行；(b) fsm 格的**分岔碼**（照物件 `next` 查表的碼，例 templates/agent-fsm wait 格的 10「還沒回」、11「回 think 重組」）是給那張 fsm 表看的，被表接住就不算錯（同上一份「10 是對直接收到它的那層說的」）。
  - **轉交的碼**（照盤點推薦，[thinking 11-05 stdio-unify](../../../thinking/2026-11/05/stdio-unify/README.md) R8）：轉交的碼不改數字、不另用數字分種類；分得出誰錯靠 stderr——**退非 0 時 stderr 有 `我的名字: error:` 這一行＝我自己錯；沒有＝下層的碼**。會轉交碼的程式（aos-exec、`aos-tools call`、aos-sandbox、aos-loop、aos-fsm、kernel/llm-kernel 的 fake_slow…）各自 README 寫這一句。有一個已定的例外——aos-loop 的 `RunFailed`（代定 D4，[special-cases](../../../thinking/2026-11/06/special-cases/05-衝突與方向題.md)）：aos-loop 身體退非 0 時照樣寫一行 `aos-loop: error: RunFailed run N: X failed with exit code C` 再以那個碼結束，這行說的是「第幾次、誰、碼幾」（P-21），碼仍是身體的——看到 `RunFailed` 就是下層的碼，其他代號才是自己錯。
  - **訊號**（照盤點推薦，[thinking 11-05 stdio-unify](../../../thinking/2026-11/05/stdio-unify/README.md) R12）：子程式被訊號殺、而我照轉交碼結束時，一律換算成 128＋N（不把 Python 的負數 returncode 直接當碼）；Python 寫的程式被 Ctrl-C 不吐 traceback、退 130（＝128＋2）；被 TERM 照現狀（有接的退 128＋15）。
  - **stdout 被關**：Python 經 `aos_flags.run` 的入口，stdout 被讀端先關時安靜退 141（含最後 flush）；寫子行程 stdin 的 BrokenPipeError 不在此範圍。lib 工具經 `tool_io.start` 設 SIGPIPE 預設處理；見 [J5 結果與適用邊界](../../../thinking/2026-11/05/json-argv/10-J3到J7實作結果.md#j5-aos_flags-去重sigpipe)。
