# 基礎設施／資料夾程式與執行

（檔名沿用「定義與工作區」。）用詞（C-54）：**資料夾程式**（定義）＝一個資料夾；**入口**＝`$AOS_ENTRY` 指的檔（可執行檔，或 aos-exec 完整實作（N-18）跑得動的檔——inst 單子、argv 陣列、`js[$AOS_ENTRY]`，C-73；[ideas § 14](../../thinking/2026-10/19/ideas/README.md)）；**stack**＝被叫的程式自己的 `$AOS_STACK`（執行中狀態）；**小格**＝叫別的資料夾程式時給它的 stack；**工作區**＝使用者的檔與成品所在的資料夾（`ws`，C-65）。見[名詞表](../CONCEPTS/附錄1-名詞.md)。

N-57～N-62 是 aos 保證的底，使用者 10-19 的原話在 [ideas § 1～§ 5、§ 14～§ 21](../../thinking/2026-10/19/ideas/README.md)（N-57～N-60 對應 [CONVENTION](../CONVENTION.md) P-01～P-04）。N-50、N-53、N-55 是 10-16 定的。其餘全是慣例（P-05～P-40，在 CONVENTION），不是大家都要守的。都是**草稿**。

> **實作**：這些條文講的是「aos-exec 這個角色」，不分實作。現在的實作是 `proto8/impls`（C++，使用者寫的參考實作；使用者 10-23「python版本可以刪掉了。aos-exec/loop/daemon都用C++」，fsm 也改 C++、tick 先留 Python）：命令列有 `aos-exec`、`aos-loop`、`aos-fsm`、`aos-daemon` 四支〔11-04 加註：impls 另有 aos-schema、aos-directive、aos-json、aos-lock、aos-post、aos-llm-*，`cmd/` 也各有命令列；aos-exec 以外的形狀照慣例 [P-44](../CONVENTION/02-題目stack停錯腦/07-P-44.md)〕；inst 是 C lib、不提供 `aos-inst` 命令列（§ 20；使用者 10-22「對於python版，aos-inst指令可以刪掉了，跟C++版一樣做成lib就好。」，[ideas 10-22](../../thinking/2026-10/22/ideas/README.md)），單子由 aos-exec 在行程內交給 C lib 跑；錯誤一行是 `aos-exec: 代號 原因`（10-22 使用者「錯誤訊息多代號也遵循」）；loop／daemon 的 `exec`、fsm 格的 `exec` 見 N-11、N-36（key 名：使用者「fsm.json，現在是用val，幫我改成exec」「exec，loop／daemon 的 run 也一起改 exec」，[thinking](../../thinking/2026-10/23/naming.md)）。實作上要知道的：impls 沒有 `aos-tick`（`proto8/cmd/aos-tick` 的 Python 版；10-22 使用者定 C++ 先不補）；impls 的 loop／fsm 每次、daemon 起子 loop 不叫 PATH 上的 aos-exec，而是 fork 後在子行程裡呼叫 aos-exec 的公開 API `run_cli`（效果等同；argv 陣列裡插進去的 aos-exec、daemon 要的 aos-loop 照樣照 PATH 找）——**使用者 10-22 接受**（「Python 版照舊去 PATH 找 aos-exec 就好，只是 C++ 版這樣做我接受」，理由「因為以後可能會變成一個aos指令，後面接子指令。比如aos exec, aos loop這樣」）；可執行檔入口拿到的 `argv[0]` 是 `./檔名`；讀設定檔會跳過第一行 `#!`、`.env` 去前導空白只認 ASCII 空白（使用者「C++版比較寬鬆這塊，希望python也遵循」）；`.env` 格式與 `--dotenv-override` 見 [ideas 10-22 § 3](../../thinking/2026-10/22/ideas/02-3-env-基礎子集與---dotenv-ove.md#3-env-基礎子集與---dotenv-override10-22)、N-58、N-59 第 4 件、N-60。
