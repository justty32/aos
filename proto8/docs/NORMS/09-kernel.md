    - 框架站的隊列只有先來先掛；要優先序、期限、額度＝寫一個 kernel 身體（llm kernel 是範例）。
    - **框架站排不排隊**是 `kernel.json` 的選項（使用者 11-06「我原本預期他就是能管准入也能管排隊...或許可以做選項？」）。程式本身沒寫＝不排（格滿立刻回 `SlotMissing`）；範本 `kernel/daemon-kernel` 的 `kernel.json` 預設寫 `queue: true`，照範本開出來的框架站格滿就排隊。（使用者裁定，出處 [wf/workflows/refactor/reports/2026-11-07-sol審查/11-使用者裁定.md](../../../wf/workflows/refactor/reports/2026-11-07-sol審查/11-使用者裁定.md) #1）
    - **有序信經框架站**：使用者 11-07「我希望這是可選的。默認是不帶有序。」——`kernel.json` 有兩個各自獨立、照字面的開關，都選填、沒寫＝關：`keep_ordered`（照有序轉寄）與 `reply_via_me`（回信先回我、由框架站代回）。`keep_ordered` 關的時候，框架站把有序信當一般信轉寄給 daemon，「有序」只保證到框架站門口；daemon 的回信對的是轉寄後的信名，所以要回信對得上原信，就寄一般信。`keep_ordered` 開的時候，框架站照有序轉寄，轉寄後是新信名；只開它時下游直接回，回信的 `in_reply_to` 是轉寄後的新信名、對不上原信。`reply_via_me` 開的時候，框架站自己記「新信名→原信名」的對照表，收到下游的回信後，以原信名代回給原寄件人。要保有序又要回信對得上原信，兩個都開（kernel docs 02（[../../kernel/docs/02-kernel-modes.md](../../kernel/docs/02-kernel-modes.md)））。（使用者裁定，出處 [wf/workflows/refactor/reports/2026-11-07-sol審查/11-使用者裁定.md](../../../wf/workflows/refactor/reports/2026-11-07-sol審查/11-使用者裁定.md) #3；兩個開關各自獨立、照程式改寫，出自使用者 11-13 待裁頁 `kf-t1:A*`，[回覆檔](../../thinking/2026-11/13/decide_20261113_wu-r2.reply.txt)、[11-13 kernel-framework-開工](../../thinking/2026-11/13/kernel-framework-開工.md)）
    - **停／收／睡／醒不必過框架站**：要不要判是收件 proc 自己的事（上句）；沙箱裡的東西只要一個信箱就夠，照 C-47 一律寄 `AOS_KERNEL`（使用者 11-05 晚對「只要一個信箱」的方向說「是的，你真聰明！」，[no-pid README「定下的」7](../../thinking/2026-11/05/no-pid/README.md)）。
    - **`aos-daemon-ctl` 一律直寄**：要經 kernel 就走 `AOS_KERNEL` 的路（`aos-agent ctl`）；`aos-daemon-ctl` 是指名要碰某台 daemon 的工具，不看 `AOS_KERNEL`、一律直寄，能不能直寄靠 Linux 權限（C-47「安全的保底是 Linux 本身」；N-63 實例 `AOS_KERNEL`）。（使用者裁定，出處 [proto8/thinking/2026-11/06/os-impl/08-aos-daemon-ctl永遠直寄實作結果.md](../../thinking/2026-11/06/os-impl/08-aos-daemon-ctl永遠直寄實作結果.md)；選項框「維持直寄，它就是『指名 daemon』的工具」）〔加註：使用者 11-13 裁定照現況——`aos-daemon-ctl` 是人直接敲板子的保底，「唯一的門」只約束 proc（[裁定落地-1113](../../thinking/2026-11/13/裁定落地-1113.md) kb-ctl）〕
