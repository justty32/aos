# kernel 規範

- **N-42**（草稿）先做兩種 kernel，都基於 daemon：(1) 管 LLM 呼叫的 kernel；(2) 通用管理的 kernel（以 agent 作判斷）。兩支不併成一支（使用者 10-16：「兩隻kernel不併成一支。」，[KISS 重審拍板 5](../../thinking/2026-10/16/kiss-recheck.md#使用者拍板10-16)）。出自 C-47。
  - **方向（使用者未明確確認）**：使用者 11-11「在我的規劃中，我們會有一個通用的kernel框架，在這個框架下，我們去擴充更多功能如llm之類」。頂層的理解是框架一份、問腦＝框架＋問腦專屬那包（能力包、額度、帳），這會翻掉上句「兩支不併成一支」；使用者沒有明確確認，所以上句先不改。使用者 11-12：等圖紙（原話「2.等圖紙。」），跟通用 kernel 框架的圖紙一起裁。現有問腦總機何時併進框架也沒定。不論併不併，`AOS_LLM_KERNEL` 與 `AOS_KERNEL` 維持兩個變數（選項框「維持兩個變數」）。
  - **(1) LLM kernel**：全文逐字在分檔 [09-kernel/01-N-42-1-LLM-kernel](09-kernel/01-N-42-1-LLM-kernel.md)；能力包、排程、每寄件人額度在 [02-N-42-1-能力包與份額](09-kernel/02-N-42-1-能力包與份額.md)。
  - **(2) 通用 kernel**：普通的掛 proc 請求去它那（C-47「多種 syscall」）。**現況**：判官 [`lib/aos/judge`](../../lib/aos/judge/_entry)，兩個範例擺法——0 號 proc 式範本 `kernel/procs-kernel`、繼承式範本 `kernel/daemon-judge`（[kernel-daemon 02](../../thinking/2026-11/05/kernel-daemon/02-兩種模式.md)，C-47「擺法只是範例」）；判官腦（以 agent 作判斷）仍未做。**方向（已定，未實作）**：通用 kernel 框架是一包方便零件——收信、規則＋hook、下一站、回信、排隊——不是概念，手寫一個也算 kernel；現有判官以後收進這個框架（使用者 11-11「判官這東西...我覺得應該將其吸納進我們之後的kernel框架中。」，[thinking 11-11 kernel](../../thinking/2026-11/11/kernel/README.md)）。選項框裁的這三題，頂層解讀成框架要有的能力、不急著改在現有判官身上：下一站寫進設定（「寫進 judge.json」，沒寫照舊寄給 `AOS_DAEMON`）；數量另指（「數量另外指一台」：設定可另寫 `max_running` 去哪台 daemon 數，沒寫且下一站不是 daemon 時設了 `max_running`＝報設定錯）；hook 三個時機都要（「判決前」「判決後」「回信經過時」，最後一個只在該站選了回信先回我時才有，沿用 agent 的 hook 契約）。回信對 `reply_to` 二選一照 C-47「轉交也算」。停／收／睡／醒要不要判，是收件 proc 自己的事。同批另一題「daemon 收到壞的掛 proc 信」裁「改成會回」（回 `applied:false` 加原因），是 daemon 自己的事，跟框架分開。
    - 判官的隊列只有先來先掛；要優先序、期限、額度＝寫一個 kernel 身體（llm kernel 是範例）。
    - **判官排不排隊**是 `judge.json` 的選項（使用者 11-06「我原本預期他就是能管准入也能管排隊...或許可以做選項？」）。程式本身沒寫＝不排（格滿立刻回 `SlotMissing`）；範本 `kernel/daemon-judge` 的 `judge.json` 預設寫 `queue: true`，照範本開出來的判官格滿就排隊。（使用者裁定，出處 [wf/workflows/refactor/reports/2026-11-07-sol審查/11-使用者裁定.md](../../../wf/workflows/refactor/reports/2026-11-07-sol審查/11-使用者裁定.md) #1）
    - **有序信經判官**：使用者 11-07「我希望這是可選的。默認是不帶有序。」——`judge.json` 選填 `keep_ordered`，沒寫＝關。關的時候，判官把有序信當一般信轉寄給 daemon，「有序」只保證到判官門口；daemon 的回信對的是轉寄後的信名，所以要回信對得上原信，就寄一般信。開的時候，判官照有序轉寄，自己記「新信名→原信名」的對照表，收到 daemon 的回信後，以原信名代回給原寄件人（kernel docs 02（[../../kernel/docs/02-kernel-modes.md](../../kernel/docs/02-kernel-modes.md)））。（使用者裁定，出處 [wf/workflows/refactor/reports/2026-11-07-sol審查/11-使用者裁定.md](../../../wf/workflows/refactor/reports/2026-11-07-sol審查/11-使用者裁定.md) #3）
    - **停／收／睡／醒不必過判官**：要不要判是收件 proc 自己的事（上句）；沙箱裡的東西只要一個信箱就夠，照 C-47 一律寄 `AOS_KERNEL`（使用者 11-05 晚對「只要一個信箱」的方向說「是的，你真聰明！」，[no-pid README「定下的」7](../../thinking/2026-11/05/no-pid/README.md)）。
    - **`aos-daemon-ctl` 一律直寄**：要經 kernel 就走 `AOS_KERNEL` 的路（`aos-agent ctl`）；`aos-daemon-ctl` 是指名要碰某台 daemon 的工具，不看 `AOS_KERNEL`、一律直寄，能不能直寄靠 Linux 權限（C-47「安全的保底是 Linux 本身」；N-63 實例 `AOS_KERNEL`）。（使用者裁定，出處 [proto8/thinking/2026-11/06/os-impl/08-aos-daemon-ctl永遠直寄實作結果.md](../../thinking/2026-11/06/os-impl/08-aos-daemon-ctl永遠直寄實作結果.md)；選項框「維持直寄，它就是『指名 daemon』的工具」）
    - **ping**：判官對 `{"ping": true}` 照 C-48 原樣轉寄，不另加判斷；見 [no-pid 10 P3](../../thinking/2026-11/05/no-pid/10-P3實作結果.md)。
