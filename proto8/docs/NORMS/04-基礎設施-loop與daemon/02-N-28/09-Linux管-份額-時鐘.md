N-28 接續（上一份的子項到這裡繼續）：

  - **沒掛 daemon＝Linux 管**（使用者 10-30「沒有的話也沒關係，linux本身的proc管理就夠，aos體系就是用ps aux+kill去管理」，[10-29 agent-bob](../../../../thinking/2026-10/29/agent-bob/04-頂層對八題的再想.md#決定10-30) 決定 34）：直接 `aos-exec` 跑的東西歸 Linux 管（`ps`、`kill`），aos 不另做程式；要納進 aos 就掛 daemon（寫進 `procs`）。從外面把東西掛上、拿下的命令列是 [aos-daemon-ctl](../../../../py/docs/05-commands.md)（工具、不是規範；哪個 daemon＝`--daemon` ＞ `$AOS_DAEMON`，[N-63](../../10-基礎設施-定義與工作區.md)）。
    - **aos-daemon-ctl add 的自動識別看入口最終指到的 JSON**（使用者題 4「拿掉，不應該看特定檔案。add這塊，就是看最終指向的json的內部結構。」；這句只作 add 自動識別的出處，不推廣成通則，[four-elements 題 4](../../../../thinking/2026-11/04/four-elements/06-要使用者裁的題.md)）：不看 XXX 裡有沒有 `loop.json`；照 aos-exec 的找法（N-61／N-62 的子集）走到入口，最後指到「沒 `argv`、有 `exec`」的物件＝loop 型（只有 `exec` 時補 `interval_ms: 0`），其他＝exec 型——陣列與有 `argv` 的物件（含 `["aos-loop", 設定檔]`）都原樣交 aos-exec，不特別辨認（見「型別怎麼判」）；`.env` 不讀，繞圈＝`EntryBad`。細節照實作，[aos-daemon-ctl](../../../../py/docs/05-commands/03-aos-daemon-ctl.md)。
  - **列的 `limits`**（[feat-proto 件 5](../../../../thinking/2026-11/05/feat-proto/05-資源份額.md) E3，使用者「會想要限制特定aos proc所占用的資源。以及daemon/kernel自己本身被限制占用資源，並且會分配份額給proc」「讓daemon偷偷給底下的proc包s6」）：procs 每列選填 `limits`（`mem_mb`、`cpu_s`、`procs`、`file_mb`、`files` 正整數，`user` 帳號名；同 aos-sandbox 的 key），daemon.json 頂層 `limits`＝沒寫、null 或 `{}` 的列用的預設；列寫非空數字份額整份取代預設，要的鍵都要寫全，預設 `user` 會補上（列自帶 user 優先）。
    - `limits_max` 是數字天花板，預設須含所有被封頂的鍵且不超額；列超過或漏掉被封頂鍵＝該列 `LimitBad` 起不來、不夾，想保留的預設數字鍵要放進 max。
    - daemon 在 fork 出的子行程裡自己 setrlimit（soft＝寫的值，hard 同值，cpu_s 多 1 秒；繼承 hard 不容許多 1 秒時退回同值）／換帳號，**等同 s6-softlimit／s6-setuidgid**（不 exec s6、不依賴 PATH；使用者 11-05 裁「維持自己 setrlimit (Recommended)」，[feat-proto 六題裁定](../../../../thinking/2026-11/05/feat-proto/README.md)），proc 自己不知道。
    - 寫壞＝同 `stack` 三條（`CfgBad`、procs_ctl 不採用、壞信）；做不到（比 daemon 自己的 hard 寬、`user` 沒 root）＝小格 `stderr.txt` 一行 `LimitBad`、子行程退 1（照「出錯結束一律留表」留 `stopped`＋`reason`）；`procs_state` 每列多生效的 `limits`。份額是每個行程各自的上限、不從 daemon 總額扣（天然差異）；daemon 自己被限＝起它的人包（rlimit 繼承）。細節 [aos-daemon docs/09](../../../../cpp/aos-daemon/docs/09-份額.md)。
  - **換成 subuid**（[kernel-limits-plan](../../../../thinking/2026-11/13/kernel-limits-plan.md) 段 3，K4／K6／K16／K18 已裁；11-19 [subuid-1119](../../../../thinking/2026-11/19/subuid-1119.md) 接上最小一刀）：`limits.user` 寫 `"sub:N"`（1～60000）＝免 root 換成這個帳號名下的 subuid：每支 proc 自己一個 user ns、daemon 跑 newuidmap／newgidmap；主群組＝daemon.json `group`（一台 daemon 一個，預設 60001）；起前小格 0700＋ACL（那個 uid 與使用者）；換身分前清環境（白名單、`HOME=/nonexistent`）、關多餘 fd；走不到小格、cwd、ws 就 `LimitBad … cannot reach`。信箱與共用夾的權限不歸 daemon（用 `aos-share`）。
  - **可選 cgroup**：頂層 `cgroup: off|auto|on`（預設 off），自行提供委派；`mem_total_mb`／`procs_total` 管每列連子孫的 memory.max（swap.max=0）／pids.max，沒開成 warning＋limits_ignored，開成可讀事件標 mem/procs 並收整格；不改 graceful stop 或退 0 下表，亦不防同 uid 故意改寫 cgroupfs（詳見 [份額](../../../../cpp/aos-daemon/docs/09-份額.md)）。
  - **時鐘**：daemon 程式不認時鐘——`daemon.json` 沒有 `clock` key（寫了當沒看到、不報錯、不展開），不設 `AOS_CLOCK`，也不認跑鐘那列。要時鐘就在 `procs` 寫一列跑 `aos-clock` 的普通 loop 型 proc，`AOS_CLOCK` 由定義資料夾的 `.env` 給、底下照繼承；範本只有**根** daemon 帶這列＋`.env` 一行（寫法與坑見 [aos-daemon docs/02](../../../../cpp/aos-daemon/docs/02-看寫法決定怎麼起.md#時鐘普通一列)）。daemon 跟任何 proc 一樣讀環境的 `AOS_CLOCK`（判 `stuck_after_cycles` 用），不自己設它。想看時鐘走不走，讀鐘檔（`$AOS_CLOCK` 指的檔）或看跑鐘那列是不是 `running`。使用者 11-09「現在的_clock是與daemon耦合很深...我希望別那麼深」，裁「拿掉，走 B」（[thinking clock-decouple](../../../../thinking/2026-11/09/clock-decouple/README.md)）。
    - 子 daemon 的鐘**聽外層**：沒帶鐘列就繼承上層的 `AOS_CLOCK`；自己帶了鐘列＋`.env`，`.env` 預設不蓋已有的 `AOS_CLOCK`＝仍聽外層，它的鐘白跑；要用自己的，在掛它的那列寫成內嵌單子加 `--dotenv-override`，不另加機制。使用者 11-09「預設聽外層。然後開clock這個選項，daemon設定檔預設是不開。大家也通常只在root daemon才開，除非有特殊需求。」（[thinking clock-decouple](../../../../thinking/2026-11/09/clock-decouple/README.md)）。
