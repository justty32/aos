## 五、stack

- **P-15** 執行中的一切（狀態、草稿、紀錄、小格）只寫 `$AOS_STACK`，**定義資料夾不被寫**；所以同一個 agent 可以同時被兩個工作區跑。（C-65；§ 2；原型測試已驗）
- **P-16** agent 自己的格（idle／think／act）共用同一個 `$AOS_STACK`——它們是同一台狀態機。stack 裡放什麼、叫什麼，agent 自訂；agent-bob 的 `state.txt`、`current.txt`、`plan.txt`、`trace.jsonl`〔11-03 起 fsm 不寫〕是例子不是規範。（拍板點 1「stack 內部自由」；§ 2「剩下的你自己想」；§ 3）
- **P-17** 叫**別的**資料夾程式（工具、另一個 agent）時，給它自己的 stack（**小格**）：`sub=$AOS_STACK/tools/<名>/`、`AOS_STACK=$sub aos-exec tools/<名>`（例：cathy 的 act 用 `AOS_STACK=$sub aos-exec tools/stamp`，工具的 `runs.txt` 落在 `$AOS_STACK/tools/stamp/`）。小格名＝工具資料夾名（P-38 靠這點）。**11-02 改**（使用者 11-02「未來，搞不好會出現agent+kernel的變體，.stack底下會有一大堆東西。擋名字會擋不過來。所以我覺得最好還是tools/<name>更好」，[thinking 11-02 stack-tools](../../../thinking/2026-11/02/stack-tools.md)）：小格由 `$AOS_STACK/<名>/` 改 `$AOS_STACK/tools/<名>/`，呼叫方給的名字跟格自己的固定名分開命名空間；`tools` 從此是 stack 頂層的保留名（格自己不能在 stack 頂層放叫 `tools` 的固定東西）。被叫的只看到自己的 stack、不知道上面有誰。叫完不自動收——留著給人看；要收由呼叫方自己 `rm`。巢狀時小格怎麼給、被叫者的工作區放哪，見第十二節 P-32。（§ 3「子程式的 stack 由 agent-bob 自己訂，有可能他會是 AOS_STACK/think, /act」；C-52 子 agent 只看自己的 stack；C-65 stack＝「叫工具時開的小格」；C-67 stack 放哪由呼叫方決定；拍板點 3「人來看」。這是原討論稿拍板點 4 的答案）
- **P-18** 一個工作區同時跑兩個 agent 時，呼叫方給不同的 `AOS_STACK`（例 `$AOS_WS/.stack/bob/`）；預設值只保證「一個工作區一個 agent」不撞。（C-67；C-53 入口默認正常、誤用不歸組件管）

## 六、停與錯

- **P-19** 結束碼三種：`0`＝這次好了、下一次；`10`＝正常停（idle 看 `new/` 空了）（舊協議；走 queue 的 agent 看 `$AOS_STACK/queue/`，P-11 的 10-30 改口）；其他非 0＝失敗。loop 收到 10 以 0 結束；收到其他非 0 以那個碼結束；跑滿 `max` 以 0 結束、stderr 不寫（N-43 正常退出不噴 stderr；要知道有沒有跑滿看 `trace.jsonl` 行數〔11-03 起沒有 trace，看 loop 的 state 窗或 log〕）；loop 自己收到 SIGINT／SIGTERM／SIGHUP 時收完那次以 128＋N 結束（P-36）。（拍板點 1；原型現狀。跟 C-63 相撞處使用者 10-19 定照用、C-63 作廢，[ideas § 9](../../../thinking/2026-10/19/ideas/README.md)；N-43） **11-04 加註**（loop／fsm agent，使用者 11-04 衝突 2 選「think 也退 10，條文加註」，[thinking 11-04 loop-fsm-agent](../../../thinking/2026-11/04/loop-fsm-agent/04-衝突與方向題.md#決定11-04使用者)）：「`10`＝正常停（idle 看 queue 空了）」是字串 `next` 的表；物件 `next`（N-36）的表上，別的格也可以退 10、意思仍是 N-43 的「沒東西」——`demo/agent-fsm` 的 think 在腦給了最後答案（沒有 `tool_calls`）時退 10，表上 `"10": "idle"` 接住、到不了 loop（同 P-35 的 10-30 加註）。
- **P-20** 任一格失敗＝整個 agent 停下來等人：fsm 不換狀態、loop 以那個碼結束；人修好後再 `aos-exec` 一次，從 `$AOS_STACK/state.txt` 接著做同一格、同一題。不自動重試、不數連錯。（拍板點 3；N-53 腦出錯那次 phase 不動；N-38）
  - **10-30 加註：表上沒接住時才是預設停**（使用者 10-30「都照建議」，[thinking 10-30 aos-round](../../../thinking/2026-10/30/aos-round/07-決定.md#決定10-30) 衝突 3）：用 aos-round（或自己寫物件 `next`，N-36）的 agent，「任一格失敗＝停下等人」是**表上沒接住那個碼時**的預設；表上接了就照表走（風險自擔，loop 的 `max` 是唯一的煞車）。範本表不接錯誤碼，所以範本仍是失敗就停；endpoint 的 retry／switch 照 10-28 在 think 格內問 `hook/on_error`、數 `AOS_ROUND_MAX_RETRIES`，不寫在表上。 **11-01 加註**（使用者 11-01 晚「3.這就是濫用...除非真的有必要的，否則不要用。」「明明現有的機制組合一下就能搞定，偏偏在那邊亂搞一通」，[thinking 11-01 playground-bob 03](../../../thinking/2026-11/01/playground-bob/03-旋鈕改-argv-與檔-實作.md)）：格自己的旋鈕不再走環境變數——能刪的寫死成常數，刪不掉的改 argv 或格／stack 裡的檔；本條提到的 `AOS_ROUND_MAX_RETRIES` 已刪（think 寫死重來 3 次）。條文原意改不改由使用者定。 **11-04 加註**（round 已刪後的條文整理，使用者 11-04「照建議」，[收斂報告 § round 刪掉後](../../../../wf/workflows/tidy/reports/2026-11-03-收斂/03-round刪掉後的條文之一.md#round-刪掉後沒實作撐的條文11-04給使用者裁)）：後半「endpoint 的 retry／switch 照 10-28 在 think 格內問 `hook/on_error`、數 `AOS_ROUND_MAX_RETRIES`」已無實作（round、endpoint 格、`hook/` 都已刪，那條 10-28 加註 11-04 也刪了）；前半「表上沒接住時才是預設停」照舊，由 aos-fsm 的物件 `next`（N-36）撐著。
- **P-21** 誰的錯誰自己講：格的錯寫在格自己的 stderr；fsm 什麼都不轉述；loop 只說「第幾次、誰、結束碼幾」。（C-53；N-43 每層只說自己）**10-28 改口**：錯寫 stderr 是 agent 範本與 lib 的格、aos-loop／aos-fsm 這幾支自己的約定，照 Unix 慣例，不是 aos 函數都要守的標準（stderr 只是每個 proc 都有的檔案；使用者 10-28「照你的建議，留著改口，JSONL 那半條刪掉」，[thinking 10-28 medium](../../../thinking/2026-10/28/medium.md)，見 N-43「適用範圍」）。
- **P-22** 逾時：shell 版沒人管——某格卡住（模型沒載入、網路不通）loop 只會等，也殺不到孫程式。要逾時就把那格換成 inst 版、寫 `timeout_ms`（P-29）：直接寫 `"exec": {"argv": …, "timeout_ms": …}`，fsm 行程內當監工收整群（[thinking 10-24](../../../thinking/2026-10/24/exec-relative/01-使用者原文.md#10-24-exec-直接放單子)）；或寫 `"exec": "fsm.json#/states/<名>/body"`、單子放 `body`，由 aos-exec 當監工收整群（P-07）。（N-41「靠那張 inst 的 timeout_ms 守」；inst 討論的結論）
