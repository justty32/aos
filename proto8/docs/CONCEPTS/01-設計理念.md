# 設計理念

- **C-01** aos 存在的理由是讓大語言模型方便使用；目標多到只能靠模型寫，所以核心要讓模型好用。（2.1）〔這裡的「核心」＝名詞表的「系統本體」（大範圍那個），不是 C-74 分層裡的核心 aos-exec〕
- **C-02** aos 蓋在現有作業系統上，硬體層的計算分配不重做。（2.5）
- **C-03** 由下往上：Linux → daemon → 時空 → 排程與資源分配 → agent。上層只透過下層。（2.5、2.10）（註：C-03 講的是誰排程誰〔排程與資源分配＝kernel 排在 agent 下面，因為它排 agent〕，[C-74](#分層10-22-使用者定) 分層講的是誰依賴誰〔kernel 與 agent 同在最上層，都用基礎層與標準庫寫成〕，兩條軸不衝突。）
- **C-04** daemon 完全處理 Linux 那邊的事；它之上的東西不碰 Linux。（2.5）檔案讀寫權限也是這層能借來用的（例 kernel 當某 daemon ctl 的唯一寫者），見 [C-64](#檔案權限10-16-使用者定)。
- **C-07** 體系用的表達方式以模型天生就會的為準（檔案系統、POSIX、JSON），為的是讓它能自省。（2.6、9/23）
- **C-24** 要最佳化的不是時間空間，是金錢、可預測性、人能不能理解。（9/1 ideas 01；2.1 重申）
- **C-45** 比起實作，更重要的是規範。aos 提供一些符合規範、方便的語法糖（例如 aos-inst、aos-fsm），但不要求所有人一定要用。例：aos 時空這個概念衍生出的規範＝大家都要看 tick-tock 時鐘、資料夾別亂弄。（10-12）〔現況：inst 是 impls 的 C lib（[inst](../../impls/inst/README.md)），沒有 aos-inst 命令列；只有 C++ 版（使用者「python版本可以刪掉了。aos-exec/loop/daemon都用C++」）。〕
- **C-43** 最終效果：一套 library，寫完編譯成基於 aos 的類 LISP 程式，把 aos 當作業系統跑；人和 AI 都要能用。（3g.1、3g.12）**「編譯」在資料夾＝程式（C-68）之下的意思，10-19 晚使用者答**：「意思是我們要做這樣一套程式，要一個一個mkdir, vim修改檔案，等於是一個元素一個元素去堆疊出一個table，那不如直接用lua/lisp生成這麼一套資料夾佈局」——一套 aos 程式就是一堆資料夾與檔案（一個 table 一個元素堆出來的），與其手動 mkdir、vim 一個一個堆，不如用 lua／lisp 一類語言把整套資料夾佈局生成出來；那個生成就是「編譯」，library 就是做這件事的。（[ideas § 12](../../thinking/2026-10-19-ideas.md)）
- **C-48** JSON 格式族：沿用 inst 單子族、loop／fsm 設定族，靠加 key 與任意 value 擴充（只處理認得的 key），除非必要不新增格式。兩個通則：**私有 key**——各功能可以在同一份 JSON 放只有自己看得懂的 key，藉此共享同一份格式，前提是 key 不重疊（共用同一份檔的私有 key 真的撞名了才加功能前綴，例 `agent_`；各程式的說明列出自己認得的 key）；**不認得的 key 一律忽略、不報錯**，不分開頭是不是 `_`（10-23 使用者「不認得的key就是忽略」）〔使用者「_開頭=附註這個概念刪掉」（[thinking](../../thinking/2026-10-23-naming.md)）：`_` 開頭的 key 是普通 key，沒有附註或 `_notes` 慣例；入口預設名 `_entry` 只是入口的名字；`.env` key 是為了跟資料夾的 `.env` 檔對上（C-51），檔名照 dotenv 生態〕；**值的雙形**——一個值除了字面純值，也可以寫成物件（展開形），像 Lisp 的 `3` 與 `(+ 1 2)`（例：`priority` 寫 `"low"` 或 `{"val", "deadline"}`；展開形的原值固定在 `val`，C-55），實作麻煩就權衡，太麻煩的地方可以不支援物件形。指示詞是這招的一種用法，有 `$env` 與 `$ref` 兩個，修飾詞是 `$path`、`$prefix`（N-45）：`{"$env": 名, "$path": 子路徑}` 換成該環境變數底下的路徑，讀的是執行當下的環境、像 shell 的 `$HOME`，是正式機制（例 `{"$env": "AOS_STACK", "$path": "plan"}`）；單子本來就能內嵌，不必拆檔；`$ref` 指位置只寫 `檔#/指標`（使用者「把$at刪掉，就都只認#/。」），也可以寫成陣列＝幾份照順序合成一份（都是物件合 key、同名後面的蓋前面的；都是陣列接起來；混在一起＝解不開），例 `{"$ref": ["a.json", "b.json#/c/d"]}`，原話與細則見 N-45；argv 陣列也能放指示詞。aos 讀的 JSON 都解（使用者選「aos 讀的 JSON 全部支援」）——規範是 aos 自己的程式一律支援，別人的程式不一定支援是事實、不是規範；每支程式只解自己讀的格，見 N-45。（10-15，[原文](../../thinking/2026-10-15-json-families.md)；10-16 夜使用者：「可以用$env啊」→ 頂層給兩案，選 A：「A」；[CONVENTION P-31](../CONVENTION.md)、[N-45](../NORMS/06-基礎設施-命令列與指示詞.md)、[ideas 10-20](../../thinking/2026-10-20-ideas.md) D1、D2、D8）
- **C-51** 資料夾與 JSON 可以互通：資料夾＝object、名字＝key，一份 JSON 本身也是一個小檔案系統，inst 體系以外的格式也能這樣套；「但是我會覺得，建議不要濫用，因為雖然可以互通，但畢竟在細節上有差異」——所以互通只當工具與思考方式，**不進規範**。JSON 那半的入口怎麼找：C-72。JSON schema 在這套大量用 JSON 的體系裡有更多用處（當型別、interface、簽名，也能描述資料夾的形狀）；驗證選用，執行期先只驗 LLM 回話。隱藏檔一律略過（一個例外：aos-exec 讀入口資料夾裡的 `.env` 設環境變數，[N-59](../NORMS/10-基礎設施-定義與工作區.md) 第 4 件、[ideas 10-21 § 4](../../thinking/2026-10-21-ideas/02-4-aos-exec-支援-env.md#4-aos-exec-支援-env10-21)）；入口的位置由環境變數 `AOS_ENTRY` 指（預設 `_entry`，C-68）。這也是使用者 10-19 說的「純粹把資料夾作為 lisp 的 list 或 lua 的 table」的根（[ideas § 1](../../thinking/2026-10-19-ideas.md)；比喻用 table，C-71）。（10-15 收工後意見 5～7，[thinking 意見 5～7](../../thinking/2026-10-15-opinions-5-7.md)）
  - **10-31 加註：固定名字可以、但限縮範圍**（使用者 10-31「固定，是可以的，但建議線限縮範圍，比如只有一個檔案固定，剩下的，則都由這個檔案指定。」，拍板「要寫入，但這條我後續還會有一些想法要追究。」，[thinking 10-30 eca § 10-31 原則](../../thinking/2026-10-30-eca/10-10-31-使用者原文-turn-的定義檔只認固.md#10-31-使用者原則固定名字可以但限縮範圍判準)）：檔名當 key 固定可以，但固定的範圍要限縮——理想是只有一個檔案固定當入口、其餘由它指定；要更靈活就用環境變數或 argv 指定；參與者少又穩定時固定就好，變化多時再斟酌（例：`_entry`＋`AOS_ENTRY`〔C-68、C-72〕；eca 的 `cli.json`、`eca.json` 現階段維持固定）。**使用者尚有後續想法待追究（10-31），本加註可再補**。

## 分層（10-22 使用者定）

- **C-74** **分層：基礎層（核心 aos-exec＋loop、daemon）→ 標準庫（fsm、tasks、parts、其他）→ agent／kernel**。使用者 10-22：「我先定個方向：aos exec這是基礎，在基礎上弄loop/daemon/fsm等標準庫(其中loop/daemon算是介於基礎與標準庫之間，或者說aos exec是核心，而loop/daemon/fsm是基礎，其他才是標準庫)，再來才是agent/kernel」；接著改：「loop等一下，我們先把那個基礎、核心的定義弄好。我會覺得，aos-exec是core，是基礎中的基礎，所以可以叫他"基礎層中的核心"，然後fsm還是歸進標準庫好了」；頂層整理成下表、並提三條撞名的處理後：「對，分層照這樣記。剩下三條撞名照你的建議處理。」（[ideas 10-22 § 4](../../thinking/2026-10-22-ideas/02-3-env-基礎子集與---dotenv-ove.md#4-分層方向10-22)）

| 層 | 有什麼 | 實作（C++ `proto8/impls`，aos-tick、aos-parts 例外） |
|---|---|---|
| 最上層 | agent、kernel | [demo](../../demo/README.md) 的 agent-bob、agent-ann、agent-dan（真腦＋工具）；kernel 現無實作 |
| 標準庫 | fsm、tasks、parts、其他 | [`aos-fsm`](../../impls/aos-fsm/README.md)；[`aos-parts`](../../bin/README.md)（Python，在 `proto8/bin`；註冊檔 `parts.json`）；tasks 現無實作 |
| 基礎層 | **核心**＝aos-exec（含 inst 庫、指示詞、旗標）；loop、daemon | 核心：[`aos-exec`](../../impls/aos-exec/README.md)（[inst](../../impls/inst/README.md) 是 C lib、單子的 JSON 在 aos-exec 的 `src/inst/`；指示詞 [aos-directive](../../impls/aos-directive/README.md)；旗標在 [aos-util](../../impls/aos-util/README.md)）；[`aos-loop`](../../impls/aos-loop/README.md)（含 ctl／state 窗）、[`aos-daemon`](../../impls/aos-daemon/README.md)（繼承 aos-loop 的 `Loop`） |
| 不歸層 | aos-tick（擱置中） | `aos-tick`（[proto8/bin](../../bin/README.md)，Python） |

  分層講的是**誰依賴誰**（上層用下層寫成）；C-03（本檔開頭）講的是**誰排程誰**，兩條軸不衝突（見 C-03 的註）。用詞（三條撞名照頂層建議）：分層的「核心」只指 aos-exec；**kernel 不譯作「核心」**，條文與名詞表一律寫 kernel；名詞表大範圍的那一整塊（到「排序程式可由模型生成」為止）叫**系統本體**（新詞頂層代定）；repo 根的 `core/` 是舊一代 C++ 版的「必要模組」資料夾，資料夾名不動、跟這裡的核心無關。實作兩級（N-18）叫**最小實作／完整實作**。「基礎設施」是**主題**（[03](03-基礎設施.md)、NORMS 03～07、10，照內容分），不是層：inst、loop、daemon、資料夾程式屬基礎層，組合子 tasks、fsm 屬標準庫。這裡的「標準庫」是 aos 的這一層，跟「純標準庫 Python」（只用 Python 自帶的庫）是兩回事。

  **10-31 使用者定：parts 進標準庫、與 fsm 平級**（「因爲他相比symlink，多了可以用$env/$ref指定東西的功能，喔天啊，這真的很實用。我估計他會是跟aos-exec/loop/daemon做一桌，好啦，基本上跟fsm平級，就是底層標準庫那樣。只是說他的一些指令用法，json格式啥的還需要微調，這個之後再說」，[thinking 10-28 agent-round § 10-31 使用者原文](../../thinking/2026-10-28-agent-round/09-實作時代定.md#10-31-使用者原文parts-的定位)）：parts＝`aos-parts` 與註冊檔 `parts.json`（名字→路徑的表，見 [C-61](05-agent.md) 的「10-28 再補」）。指令用法與 JSON 格式之後再微調。

## 最高原則（10-15 深夜使用者定，[原文](../../thinking/2026-10-15-principles/02-結論-已有的實例.md#10-15-深夜使用者拍板切乾淨kiss)）

- **C-56** **KISS 是最高原則，也是最後原則**：「我要的是徹底的純淨簡潔，KISS。把KISS納進最高原則。」（10-15 深夜）「KISS是最高原則，但也是最後原則，本質上是希望提出的設計在滿足各類需求和原則後，最後能回頭思考，把一些多餘的東西清掉。」（10-16，[原文](../../thinking/2026-10-16-kiss-last.md)）接 [proto7 設計原則](../../../proto7/notes/principles.md) 第 9 條（核心〔proto7 用語，＝名詞表的「系統本體」，不是 C-74 分層的核心〕只做最基礎的保護、錯誤同類走同一分支、很多東西默認正常、誤用不歸組件管）。其他原則都在它底下，下面兩條（C-52 巢狀切乾淨、C-53 錯誤只處理自己的）是它在巢狀與錯誤上的樣子；但 KISS 是**最後一步的減法**：設計先滿足各類需求與其他原則，再回頭把多餘的清掉——不為了方便偷看一層、不為了邊緣狀況加機制；也**不拿「最乾淨、規則最少」當抄近路的理由**（使用者：「“最乾淨、規則最少”很容易導致一些問題，也就是抄近路反而導致繞遠路」），清的時候不能違反其他原則。**寫什麼就做什麼**（10-16 補）：給的值照字面意思用，不讓某些特定值偷偷變成另一種行為；不拿「要人記的暗規則」換少一個 key——減法清掉的是多餘的東西，不是把規則藏進值裡（使用者：「不要用這種方式添加規則，不直觀，這等同於埋雷，大家都預期“我給啥檔案，他就是往這個檔案塞東西”，你還要人家記“如果給的是這個檔案，那他會幹別的事情”，這太糟糕了。」）。例：inst 的 `stdout` 寫 `/dev/stdout` 就只是照字面打開那個路徑，不特判成直接繼承 fd；沒寫的串流就是接呼叫者的，不需要旗子（[aos-exec](../../impls/aos-exec/README.md)；[原文](../../thinking/2026-10-16-kiss-last.md#原文寫什麼就做什麼10-16)）。

## 兩條總原則（10-15 使用者定，[原文](../../thinking/2026-10-15-principles.md)；10-15 深夜加嚴）

- **C-52** 巢狀：**只管自己這一層，徹底切割、不得有任何殘留**。盡量保持簡單；之後一複雜，巢狀一定常見，所以每一層只管自己，處理上層時下層被乾淨切開、可以不管；真要管時心裡有一把尺——同一個原則在每一層重複、貫穿整個巢狀，只看最上層就能處理。10-15 深夜使用者加嚴：**想看子層的東西要另外透過其他機制，沒機制就別碰**（不偷讀下層的 stderr、不替下層驗它的東西）；**上層不需要、也不該知道下層是什麼**（fsm 不知道某格是不是另一個 fsm，agent 只看到自己的工具清單、不知道工具裡是不是另一個 agent，什麼都不往下傳、不繼承）。已有的例子：fsm 只管「格→結束碼」（C-49、N-36）、格的 stderr fsm 不讀（N-38）、inst 的結果只說子程式（N-30）、暫停與次數交給跑它的 loop（N-39）、agent 不知道工具內部、子 agent 只看自己的 stack（C-46；P-17 給被叫者自己的小格）、巢狀時 aos 只訂被叫者自己的 `AOS_STACK`、子程式的 stack 由它自己訂（C-70）、整隻 agent 叫、不拿別人 fsm 的一次（P-35）、被外層逾時殺掉就是那格失敗、不為內層說話（P-36）、每層出錯只說自己一行（P-21）、結束碼只說自己這一層（N-43）。（[CONVENTION](../CONVENTION.md)）
  - **10-28 例外：round 與每一格拿 agent 資料夾當第一個參數**（使用者 10-28「照新做法」，[thinking 10-28 agent-ops 決定 11](../../thinking/2026-10-28-agent-ops.md#決定10-28)；[agent-round § 1 佈局](../../thinking/2026-10-28-agent-round/01-白話版.md#1-佈局)）：照 round 拆成格的 aos agent，round 把 agent 資料夾的絕對路徑原樣當第一個參數給每一格，格靠它找同一隻 agent 的其他格（P-33 的 10-28 例外）。這是明給的參數、跟 fsm 拿 fsm.json 同一種，不是環境變數。理由：aos-exec 解開捷徑後 cwd 在共用件那邊，共用件靠 cwd 找不到引用它的 agent。其餘照本條。
- **C-53** 錯誤：**各單元只處理自己的錯**（接 [proto7 設計原則](../../../proto7/notes/principles.md) 第 9、10 條：錯誤分類同類走同一分支、很多東西默認正常、誤用不歸組件管、先定義組件要求什麼與保證什麼）。對別人的錯三種姿態，每個單元在說明裡寫清楚自己採哪種：(a) **入口**——你丟給我的就該是正常的：我不管、默認正常（N-18、N-20、卡死不防護），或我在入口檢查並處理（N-08）；(b) **出口**——我交出去的保證不出錯（N-05 半份不算）；(c) **事先列出**可能的錯（N-38、各程式說明裡的錯誤訊息）。錯誤路徑濃縮成少數幾條（N-43 結束碼只有三種、stderr 一行「程式名: 原因」〔P-21〕、N-38 出錯一律 phase 不動），減少「出了問題之後的行為」的複雜度。下層的錯**不轉述**（C-52 加嚴）：上層只說「下層結束碼非 0」，下層的錯誤內容留在下層自己寫的地方（stderr、stack 裡的檔）。之後可納入 kernel 評估（[待定](../NORMS/08-待定.md)）。

## 命名（10-15 使用者說，[原文](../../thinking/2026-10-15-naming.md)）

- **C-54** 命名：**好懂、快速理解、快速記住**。資料夾布局、程式碼、JSON 格式最好一看就懂七七八八——先排結構，結構與名字本身就是說明；說明只要少量簡介，再直接甩出 pseudo code／JSON／資料夾。
  - **一次記住、全體系通用**：同一個詞在 aos 各處同義（`inst`、`ctl`、`state`…）。縮寫只用大家本來就知道的，而且**新縮寫要先進 [aos 認可縮寫表](abbr.json) 才能用**（10-15 使用者「要，縮寫表照推薦做」；表的欄位：縮寫、全稱、意思、例子）。
  - **難懂才加前後綴**（`ctl_dir`），表特性（`dir`、`path`、單位 `ms`）或子類時用；不用匈牙利命名法那種型別前綴。**可搜尋的標籤／主題放前面、由大到小**（`path_insert`、`path_query_sql`），排序、搜尋時同類排在一起。
  - **資料夾、檔名、JSON key：全小寫加底線**；**對外的指令名＝同一個名字把底線換成連字號**（`node_path` ⇄ `node-path`）；環境變數全大寫加底線（`AOS_ENTRY`）（10-15 使用者「指令名就是底線換連字號。」）。
  - **程式碼照該語言規範**（Python 照 PEP8），並跟檔名固定對上：程式的 `NodePath` ⇄ 檔名 `node_path`；程式裡可混大小寫表層級（`NodePath_SQL_Query`）。
  - **靠資料夾布局少用底線，複數資料夾裝同類**：裝同一類多個東西的資料夾用複數名（`insts/`、`cells/`、`tools/`），裡面的檔名不再重複類別（`insts/a.json`，不寫 `inst_a.json`、`insts/inst_a.json`）。複數一律只加 `s`（縮寫也是：`insts`、`cfgs`、`msgs`），不用不規則變化；本身已是複數或不可數的照原樣（`args`、`data`、`history`）；單一檔案用單數（`brain.json`、`ret.json`）（10-15 使用者「對了，還有複數形式，比如./inst-a.json, ./insts/a.json」，細節「都按照推薦」）。
  - **錯誤若帶代號，照 CamelCase、主詞在前**（錯是 stderr 一行「程式名: 代號 原因」，P-21；代號一律「主詞＋`…Missing`／`…Unknown`／`…Bad`／`…Failed`」四種結尾，另加 `Internal`〔既有 impls 代號使用者先裁定照舊沿用（「都按照建議做。」），同日「都先幫我統合」翻案（[thinking](../../thinking/2026-10-23-naming.md)），舊名 → 現名：`Usage` → `ArgumentsBad`（不認得的旗標 `FlagUnknown`）、`FieldType`／`JsonSyntax`／`Conflict` → `CfgBad`、設定檔讀不到的 `ReadFailed` → `CfgMissing`（不在）／`CfgBad`（讀不了）、設定檔 `#/` 指不到 → `CfgMissing`、fsm 的 state 讀不了 → `StateBad`、`WorkspaceMissing` → `WsMissing`、`EnvBad`／`EnvReadFailed` → `DotenvBad`、`CommandNotFound` → `CommandMissing`、`CommandNotExecutable` → `CommandBad`、直接叫庫跑單子檔時檔本身的 `ReadFailed`／`JsonSyntax` → `EntryMissing`／`EntryBad`；aos-tick 也帶代號（`ArgumentsBad`、`FlagUnknown`、`ClockBad`、`WriteFailed`）〕）：`ArgumentsBad`、`FlagUnknown`、`ApiKeyMissing`、`StateBad`，同主題的錯排在一起；「沒有某物」一律 `…Missing`、「不認得」一律 `…Unknown`、「壞了／不合」一律 `…Bad`（10-15 晚使用者「都按照推薦」，盤點 P7）；「動作做不成」一律動作＋`…Failed`（`LaunchFailed`、`MkdirFailed`、`WriteFailed`、`OpenFailed`），`Internal`＝照理不會發生的錯（10-23 使用者逐條認可）。
  - **例外**（10-15 盤點後定，使用者「其他直接改」）：入口檔照 Unix 老慣例全大寫（`README.md`、`INDEX.md`、`CONCEPTS.md`、`NORMS.md`，`ls` 時排前面）；`bin/` 是 Unix 慣例名、單數照留；工具自己的慣例照工具（pytest 的 `tests/test_*.py`）；外部 API 的參數名照原名、不進縮寫表（`num_ctx`、`keep_alive`）；一個檔裝很多筆的串流／日誌檔可以用複數（`steps.jsonl`）。proto8 的 `demo/` 照留單數（下一個 proto 起用 `demos/`；10-15 晚使用者「都按照推薦」，盤點 P5）。`last_`／`max_` 這種修飾詞在前不算違反「主題在前」〔計數的 `counter_` 同理，使用者 10-25「計數這塊，幫我改成counter_*」〕——`last_` 本身就是一個可搜尋的群組（state 窗裡「上一次的」排在一起），`max_` 是大家都知道的慣例。
  - **副檔名、時間、計數、上限**（[thinking](../../thinking/2026-10-23-naming.md)；使用者 10-23 逐條選過，副檔名選「純文字也帶 .txt」）：JSON 帶 `.json`、JSON Lines 帶 `.jsonl`、純文字帶 `.txt`（`state.txt`、`stderr.txt`、`current.txt`；入口檔 `_entry` 是程式不是資料、`.env` 照 dotenv 生態，都不帶）；時間點一律 `<發生了什麼>_at`（`recorded_at`、`started_at`、`sent_at`、`served_at`），不用單獨的 `at`（使用者 10-25「state.json中，runs改counter，at改成recorded_at」，回頂層兩題「都好」，頂層代定、可翻案），值一律 ISO 8601 UTC 到毫秒，時長與其他單位照後綴（`_ms`、`_ticks`）；計數一律 `counter_<被數的東西>`（`counter_runs`；使用者 10-25「計數這塊，幫我改成counter_*」），一串東西本身（陣列）不算計數、照「複數一律只加 s」；上限叫 `max` 或前綴 `max_`（例 llm-kernel 的 `max_calls`／`max_tokens`）；細則見 [C-54 命名方法 R6](01-設計理念/C-54-命名方法.md)。daemon 管的 loop 叫 `loops`（不叫 `children`），也是照「複數一律只加 s」。
  - **命名方法（10-23 晚，[thinking](../../thinking/2026-10-23-naming-method.md)）**：使用者提了一套取名的步驟（「關於命名規則這塊，我想嘗試一些新的概念，在現有的原則與規則上添加一些能讓人更快看懂的...算小技巧吧」），「先試試看，不要急着寫進去」；問了「這種命名規則，那些unix年代的老人，或是linux的開發者，有慣例嗎」，查過老慣例合成 12 條，八題選完後「寫進去吧」。取名照 R1～R13 走（R13 程式名＝`aos-<領域>-<功能>` 是 10-30 夜加的；細則逐條在 [C-54 命名方法](01-設計理念/C-54-命名方法.md)）：**先寫一行 NAME `名字 - 一句話`**（照 man page 第一行，每支程式的 README 開頭都有）→ 每格一句白話 → 先查固定格（`val`、`max`、`kind`、`code`、`signal`、`seq`、`phase`、`pid`）→ 主題字從主詞來 → 修飾成分照表貼 → 排字序 → 名字長度跟要被認多遠成正比（環境變數＞程式名＞檔名與 key＞區域變數）→ 簡化到同檔同主題仍唯一（撞名就換一個角度，用白話重新描述它的功能與特性再取名；使用者 10-23 晚「像這種命名重複的，可以用另一個角度用白話描述其功能與特性」）→ 最後回頭清、每個名字都推得回那一句。細則裡的規則：時間點一律 `<發生了什麼>_at`（ISO 8601 UTC 到毫秒），同一個時間點用別的單位記就把單位接在後面（`started_at_ticks`，使用者原例「started_at_ticks」）；計數不用 `nr_`（使用者「nr_這東西還是建議不要用，現在這東西不太常見了」），一律 `counter_<被數的東西>`（使用者「計數這塊，幫我改成counter_*」）；「第幾個」的 index 不進縮寫表，真要用寫 `idx`；縮寫進表的門檻是一眼還原得了、表上已有的不追溯（`AOS_CF`／`AOS_CD`／`AOS_CO` 照留）；**`_` 開頭的檔＝入口**（`_entry`），不是私有；ctl 的 key 是宣告狀態、一律用狀態詞，state 裡有對應的格時用同一個字（`paused`、`stopped`；頂層代定（使用者「都隨意」），見 [R4](01-設計理念/C-54-命名方法.md)）。照規則取的名字：state 窗 `started_at_ticks`、ctl `stopped`、state 窗 `ctl_warning`（主詞是 ctl；`last_` 留給「上一次」）；「上一次的結果」`last_code` 先不加。「要跑什麼」全體系一律叫 `exec`（loop.json、daemon.json 與子項、fsm 的每一格，見 C-55；使用者：「改，beats改runs，然後val寫要跑啥，通常不會用val，應該用run。」，衝突時選「只有 loop、daemon 用 run」；深夜使用者「fsm.json，現在是用val，幫我改成exec」，頂層指出跟 loop／daemon 的 `run` 不同名會違反一詞一義，使用者選「exec，loop／daemon 的 run 也一起改 exec」）；條文與訊息裡說「次」，不說「拍」（使用者：「"拍"，其實我們人類不常用這個來說，我們都是說"次"。」）。

## 布局成長（10-15 使用者說，[原文](../../thinking/2026-10-15-layout-growth.md)）

- **C-55** 布局成長：資料夾／檔案與 JSON 物件有同像性（C-51），所以**長大的規則同一套**。檔案那邊照 [wf/STRUCTURE.md](../../../wf/STRUCTURE.md)（唯一出處）：一個檔內容太大、或一個檔扛不了那麼多職責，就變成資料夾，原檔變成入口（index＋readme），資料夾裡再照既有路徑長（index、readme 各自獨立出來）。JSON 那邊照同一套：一個純值不夠用（例 `priority: 3`），就長成物件（`priority: {"val": 1, "type": "normal task", "timeout": 0}`）——key 不變，原本那個純值放進物件裡固定的一格，其他屬性當同層的 key，物件裡每個值再照同一套長；只剩原值那一格就縮回純值。這就是 C-48「值的雙形」的成長方向，讀的人兩形都收（純值＝只給了原值那一格）。**原值那一格一律叫 `val`**（ctl 的 `paused`／`stopped`（N-06）、`priority` 都是；程式讀值一律先收成物件再看自己認得的 key；10-15 使用者「都按照推薦」，選 A）**`val` 只用在這裡**（值長成物件時放原值）；「要跑什麼」是**具名欄位**、不是某個值的展開形，所以不叫 `val`，全體系一律叫 **`exec`**（loop.json、daemon.json 與子項、daemon 寫進小格的 loop.json、fsm 的每一格）——**`exec`＝交給 aos-exec 跑的目標**（字串或 `[目標, 參數...]`），跟執行器 `aos-exec` 同字同義；aos-exec 進資料夾後找的入口另叫 `_entry`（C-54 R11），兩者不混（使用者選「exec，loop／daemon 的 run 也一起改 exec」，[thinking](../../thinking/2026-10-23-naming.md)）。兩邊怎麼對見 [thinking 布局成長](../../thinking/2026-10-15-layout-growth.md)。

## 資料夾程式與環境變數（10-19 使用者定）

出處：[ideas § 1～§ 5、§ 10、§ 14～§ 20](../../thinking/2026-10-19-ideas.md)；慣例：[CONVENTION](../CONVENTION.md)；規範：[N-57～N-62](../NORMS/10-基礎設施-定義與工作區.md)。

- **C-68** **資料夾＝程式**：「純粹把資料夾作為lisp的list或lua的table，然後有一個entry，在lisp就是第一個元素，在lua就是metatable裡面定義的那個，而在我們這邊，就是環境變數定義：AOS_ENTRY=.aos/inst，這個定義的目標必須是可執行檔。就這樣，非常簡單。」入口預設 `_entry`（環境變數可覆寫；原話裡的 `.aos/inst`、`_exec` 是當時的名字）。使用者：「然後其實我有點想要把AOS_ENTRY的默認值換成_exec。也就是js["_exec"]。」「換。AOS_ENTRY 預設改成 _exec，工作區的 .aos/ stack 照舊」——入口只佔資料夾一層，跟 table 的一個 key 對上；工作區的 `.stack/` 是 stack 的預設位置，跟入口無關（[ideas § 13](../../thinking/2026-10-19-ideas.md)）；比喻只用 table（C-71）。寫程式＝定義一個資料夾（例 `agent-bob/`）、設好入口；使用＝在工作區跑它，「在 WS 這個資料夾，執行 DIR 這個程式」，命令列是 `aos-exec [--ws WS] XXX [args...]`（XXX 可為資料夾、檔、`檔#/指標`，N-58）；程式怎麼處理 cwd、工作區的內容，是它自己的事。（使用者 10-19，ideas § 1、§ 2、§ 5）原話裡「目標必須是可執行檔」由使用者自己放寬成 C-73（入口也可以是 aos-exec 完整實作跑得動的檔）。
- **C-69** **aos 只訂環境變數**：`AOS_ENTRY`（入口）、`AOS_WS`（工作區）、`AOS_STACK`（執行中狀態放哪）。「entry這塊，"這次要做啥"，其實就隨意。因為AOS_ENTRY他是一個可執行檔案，他具體被怎麼使用我們管不著，反正我們就是訂下一些環境變數，就這樣。」aos-exec 只把多的 args、stdin 原樣交給入口。（使用者 10-19，ideas § 4）另外三個由 aos-exec 每層覆寫：`AOS_CF`（current file＝實際被執行的那個檔）、`AOS_CD`（current dir＝它所在的資料夾＝aos-exec cd 進去的地方），讓程式 cd 走之後還找得回自己的東西（使用者：「然後我想要再加上兩個環境變數：AOS_CF, AOS_CD，也就是current file，current dir。」→ 定義由 fable 擬 →「同意做」；[ideas § 19](../../thinking/2026-10-19-ideas.md)）；`AOS_CO`（current obj＝實際入口在那份 JSON 檔裡的位置；使用者「AOS_CF不動。但是我們再加上AOS_CO」「aos current obj」，[ideas 10-21 § 6](../../thinking/2026-10-21-ideas/04-6-JSON-物件當資料夾-一路往下-AOS_C.md#6-json-物件當資料夾一路往下aos_co10-21-晚) J6）；共六個，定義與三類分法在 [N-57](../NORMS/10-基礎設施-定義與工作區.md)、P-39。「只訂環境變數」這句不變：aos 仍然只訂環境變數和一支 `aos-exec`，入口拿到之後要做什麼不管。
- **C-70** **巢狀由程式自己訂子 stack**：「巢狀子程式那塊我們不管，我們就是訂下agent-bob他的stack在AOS_STACK，至於agent-bob他子程式的stack，就由agent-bob自己訂，有可能他會是AOS_STACK/think, /act」。以後會是巢狀嵌入、層層疊疊，act 用的工具可能又是另一個 agent，一層一層。aos 不管巢狀（接 C-52）。（使用者 10-19，ideas § 3、§ 10）
- **C-71** **資料夾的比喻用 lua 的 table，不用 lisp 的 list**：C-68 原話同時用了兩個比喻，頂層問「資料夾到底是 lisp 的 list（有序、看第一個元素）還是 lua 的 table（無序、靠名字）？入口之外的東西算什麼？」，使用者：「那其實還是table。不過老實說，他們的本質都只是"用index+巢狀方式分資料，只是index格式不同"而已。除了入口之外的東西就是其他元素，沒啥好說的。用table來比喻吧。」所以：**本質**＝用 index＋巢狀的方式分資料，list 與 table 只差 index 的格式（位置 vs 名字），資料夾的 index 是名字；**比喻**一律用 table（入口＝metatable 裡定的那個）；**入口之外的東西就是其他元素**，沒有別的身分。C-35、C-39、C-41 與名詞表裡的「list」字眼是舊比喻，意思不變，各處加註。（使用者 10-19，[ideas § 12](../../thinking/2026-10-19-ideas.md)）
- **C-72** **JSON＝埋在檔案裡的 table＝單檔的微型檔案系統，入口的尋址方式同樣適用**：頂層問「資料夾入口是 `AOS_ENTRY`，單檔 JSON（`exec.json`／shebang `aos-inst`）的入口是 argv，C-51 說可互通但 JSON 那半沒對應說法」，使用者：「json本質上是埋入檔案中的table，也就是單檔的微型檔案系統，所以也可以套用同樣方式，js[".aos"]["inst"]，也就是entry尋址方式同樣可以套用。」所以 C-51 的互通在入口這件事上也成立：資料夾用路徑找入口，JSON 用 key 一層層找（`js[".aos"]["inst"]`），同一個「index＋巢狀」（C-71）。預設入口是 `js["_entry"]`——資料夾 `agent-bob/_entry`、JSON `js["_entry"]` 都只一層（使用者：「然後其實我有點想要把AOS_ENTRY的默認值換成_exec。也就是js["_exec"]。」，[ideas § 13](../../thinking/2026-10-19-ideas.md)）。規則（[ideas § 14、§ 15、§ 17、§ 19](../../thinking/2026-10-19-ideas.md)）：aos-exec 找到的檔若是 JSON 但不是單子，就往檔內找 `js[$AOS_ENTRY]`（預設 `js["_entry"]`），值可以是單子、argv 陣列、或字串路徑（C-73、N-61）；要指到更深的位置用 `檔#/指標`（JSON pointer，N-62）——`js[".aos"]["inst"]` 那種多層就是 `檔#/.aos/inst`；impls 的 C++ aos-exec 照做。（使用者 10-19 晚，[ideas § 12](../../thinking/2026-10-19-ideas.md)）使用者 10-21 晚「因為沒有argv的物件，我們就把他當資料夾看待」——沒 `argv` 的物件跟資料夾一樣：有 `.env` key 就套、照當下的 `$AOS_ENTRY` 取那格、一路往下；入口在檔裡的位置由 `AOS_CO` 給（N-57、N-61，[ideas 10-21 § 6](../../thinking/2026-10-21-ideas/04-6-JSON-物件當資料夾-一路往下-AOS_C.md#6-json-物件當資料夾一路往下aos_co10-21-晚)）。
- **C-73** **entry 的定義：要麼自己是可執行檔，要麼是 aos-exec 完整實作跑得動的檔**（10-19 下班前使用者口述）〔原話裡的「標準實作」＝現在的完整實作，見 [N-18](../NORMS/01-總則.md)〕：「要麼自己是可執行檔，要麼是可以被aos-exec的標準實作所執行的檔案(aos-exec _exec)。aos-exec的標準實作，支援inst json格式，也支援json array(視為argv[])，也支援shebang、可執行檔。然後按照"json等同於單檔內的微型檔案系統"的定義，js["_exec"]，也是可以被aos-exec執行的，具體來說就是js["_exec"]的value必須是inst json格式或json array(argv)。」所以完整實作認**四種**：可執行檔（含 shebang 檔；kernel 跑它）、inst 單子（JSON 物件、有 `argv`）、JSON 陣列（當 argv）、`js[$AOS_ENTRY]` 的值——單子、陣列，**或字串**（§ 17 補：「不過js[AOS_ENTRY]的值可以是字串……這等同於aos-exec loop.json，等於是複用那個規則」，字串＝路徑、整套找入口的規則再來一遍）；**值是沒 `argv` 的物件＝當資料夾、一路往下**（套它的 `.env` key、照當下的 `$AOS_ENTRY` 再取，使用者「因為沒有argv的物件，我們就把他當資料夾看待」「2.b」，[ideas 10-21 § 6](../../thinking/2026-10-21-ideas/04-6-JSON-物件當資料夾-一路往下-AOS_C.md#6-json-物件當資料夾一路往下aos_co10-21-晚) J1、J2；N-61）。這把 C-68「目標必須是可執行檔」放寬了：一個只有 aos-exec 跑得動的 JSON 入口（沒 `+x`、`./_entry` 直接跑不起來）也是合法入口。可執行檔與單子誰優先、怎麼判種類是規範的事（N-61）。（使用者 10-19 下班前，[ideas § 14、§ 17、§ 18](../../thinking/2026-10-19-ideas.md)，§ 21「舊版一起改」；完整實作是 `proto8/impls` 的 C++ 版）
