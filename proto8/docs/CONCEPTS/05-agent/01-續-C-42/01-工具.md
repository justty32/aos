## 腦、工具、可預測性（續）

- **C-42** 工具＝被引用的標頭檔；agent 也可以是工具；aos 體系的每一樣（daemon、clock、task、inst、kernel）都基於 inst、都是 shell 指令，所以都是 agent 的工具——自我迴圈改進的閉環。（3g.12、3g.13）
  **腦可以叫的、管 agent 的工具**（使用者 11-05 午「讓agent給自己改tool」「讓agent利用aos指令產出另一個agent」，[feat-proto 01、04](../../../../thinking/2026-11/05/feat-proto/README.md)；分塊：使用者「首先是我希望拆成幾大塊：掌管子agent的管理與生滅，掌管agent定義的創造修改，掌管與其他agent的交流」「agent_def」，[agents-split](../../../../thinking/2026-11/10/agents-split/README.md)；`subagent` 這個名字見 [subagent-rename](../../../../thinking/2026-11/11/subagent-rename.md)）：
  - `lib/agent/self_tools`：改**自己這隻的**工具覆蓋層（add／rm／ls），定義不動、加減的工具同一輪就生效（使用者 11-10「3.同一輪就生效」，[tools-def](../../../../thinking/2026-11/10/tools-def/README.md)）；改自己的其他幾支見 [C-90](../06-C-90～C-92-self一家與goal.md)。
  - `lib/agent/subagent`：生、叫、收**自己生的**子 agent（add／rm／ls／state／stop／start／sleep／wake／pause／resume／say／listen／ask），出生後還能調子的 tools／llm／history／hook／system；工具自己記帳、數配額。
  - `lib/agent/agents_ctl`：`aos-agent ctl` 的純包裝，對象是 daemon 表上任何一隻，不記帳、不算配額，成不成看權限。
  - `lib/agent/agent_def`：new＝把範本整夾複製成新定義、check＝轉叫 `lib/aos/defs` 看一份定義合不合格；tools／llm／system＝把工具、腦設定、system 文字直接寫進某份定義（`args` 形狀照 self_*）；new 時在新定義寫一次血緣紀錄（[agent-def-fine-lineage](../../../../thinking/2026-11/12/agent-def-fine-lineage.md)；血緣是定義的出處，見 [C-89](../05-C-89-不同質與族譜.md)；[檔名見 NORMS 命名續](../../../NORMS/命名-續-概念搬來的檔名.md)）。

  執行時「誰生的誰」不另記：父自己的子帳有、子 rm 掉就消失（使用者 11-12「執行時誰生的誰不用另外記。」，[small-rulings](../../../../thinking/2026-11/12/small-rulings.md)）。第三塊「交流」：`aos-agent say`／`listen` 接近直接存取 history，是底層、偏使用者專屬，agent 要用只能對自己的子 agent（`subagent` 的 say／listen／ask）；agent 之間真正的交流走信箱 `aos-mailbox`（使用者「就是說，aos-say/listen目前是接近於直接存取history，這對於agent來說是底層工具，並且我希望這是偏向於獨屬於使用者的。如果要讓agent使用的話，我會希望只讓他能夠對子agent做。至於真正的agent間交流，我打算去看看a2a協議，或是用aos-post實現wf/inbox協議」「a2a看過了，太繁重了。我們先做純inbox協議。」，[mailbox](../../../../thinking/2026-11/10/mailbox/README.md)）。這幾支都不繼承腦與工具，只轉手下層（`aos-agent`；agent_def 轉手 `lib/aos/defs`、`aos-tools`、`aos-json`），沒有新協定；整台的總量交給判官 `max_running`。
