## agent 的工具（10-16 使用者定，10-19 改）

出處：[稿 § 四](../../../thinking/2026-10/16/agent-inherit/02-四-使用者決定.md#四使用者決定10-16)、[ideas § 4、§ 10](../../../thinking/2026-10/19/ideas/README.md)。名詞：資料夾程式、stack、小格、工作區，見 [CONCEPTS 基礎設施 § 資料夾程式、工作區與 stack](../03-基礎設施/02-資料夾程式-工作區與-stack.md#資料夾程式工作區與-stack10-19)。規範 N-50、N-53；慣例 P-11（題目與答案）、P-17（小格）、P-25、P-33（工具）。

- **C-61** **工具的地址不用 PATH**（使用者 10-16 夜：「可以不使用PATH嗎？」→ 看完提案：「好!」）：**agent 的工具由自己資料夾的 `tools.json` 登記**（`aos-tools add`；使用者 10-28 aos-tools，[thinking](../../../thinking/2026-10/28/aos-tools/README.md)）：登記對象可以是資料夾、JSON 檔或可執行檔，可以放在任何地方（註冊檔存絕對路徑）；範本裡手寫的 `tools.json` 用相對路徑（從註冊檔的資料夾算），兩份定義一起搬照樣不斷。〔11-04 夜刪：parts.json 那半已無實作，使用者選「刪掉那一半」（[收斂報告 05 § 留給使用者看的 第 3 題](../../../../wf/workflows/tidy/reports/2026-11-03-收斂/05-11-04晚-P2-P3-P4續.md#留給使用者看的)）。刪的是「格也走註冊檔」那段（照 round 拆成格的 agent 自己的格登記在 `parts.json`、註冊檔與固定名字共存）；那段的使用者原話 10-28「全部走註冊檔好了，捷徑就是方便使用」「註冊檔案中沒寫的，那就是走固定名字」留在 [thinking 10-28 agent-ops 01](../../../thinking/2026-10/28/agent-ops/01-使用者原文.md)、[決定 16](../../../thinking/2026-10/28/agent-ops/02-決定.md#決定10-28)，11-01「2.兩者可以共存的。」留在 [thinking 10-31 parts-round](../../../thinking/2026-10/31/parts-round/README.md)；同段在 P-25 的 10-28 補照 round 那批原字不動〕`..` 只出現在方便用的捷徑與手寫的相對路徑裡（使用者 10-28「撞到就撞到」，[thinking 10-28 agent-ops 決定 10](../../../thinking/2026-10/28/agent-ops/02-決定.md#決定10-28)）。**沒經 `tools.json` 的叫法**（例 topdown 的 agent、bob 的 `act/tools/cathy`）：工具是資料夾程式，放在呼叫它的那一格自己的資料夾裡（例 `act/tools/cathy/`），格裡寫 `aos-exec tools/<名>`——從自己 cwd 算的相對路徑、永遠零個 `..`（P-25、P-33），兩份定義一起搬也不斷；**工具一律做成資料夾程式**（`date` 這種也是），所以叫每個工具都做同一件事：給它一個小格（它自己的 stack，P-17）、`aos-exec` 它。以下不分叫法：工具裡是不是另一個 agent，呼叫的格不知道（C-52）。**工具的參數怎麼進（args、stdin、或 stack 裡的檔）由工具自己的說明定**，aos-exec 保證 args 與 stdin 原樣送到（P-26）。例外：aos 自己的指令（`aos-exec`、`aos-loop`、`aos-fsm`；沒有 `aos-inst`，[ideas § 20](../../../thinking/2026-10/19/ideas/README.md)）入口裡直接寫指令名（N-59、P-39）——那是 aos 的指令，不是工具；**aos 的程式都不動 PATH**（使用者「也套用，都不動path吧」，[ideas § 24](../../../thinking/2026-10/19/ideas/README.md)），這些指令由呼叫者自己放進 PATH。PATH 其餘的只留給人在終端打指令。〔腦可以叫的工具另有 `_tooldef.json`（給模型看的說明），`arguments` 從 stdin 進、stdout 出，P-41〕**11-05 午註**（[feat-proto 01](../../../thinking/2026-11/05/feat-proto/01-self-tools.md) 代定 1）：工具的小格是 `<agent 的 stack>/tools/<名>/`（P-17），工具裡 `aos-agent ctl who` 拿這個小格查 daemon 的表就認出叫它的那隻——`self_tools` 靠它改那隻的 `tools.json` 覆蓋層（登記照樣存絕對路徑）；工具程式裡不寫 `..`。
- **C-82** **aos 函數與 tool 呼叫要能無痛互轉；argv 有兩面；設計之初就想好給誰用**（使用者 11-05 晚，[thinking 11-05 json-argv](../../../thinking/2026-11/05/json-argv/README.md)、[07 使用者回覆](../../../thinking/2026-11/05/json-argv/07-使用者回覆-11-05晚.md)）：「我們aos函數他也是透過json去定義的，並且aos函數是aos體系的基石，和tool呼叫，兩者之間應該要是可以無痛轉換。」argv：「一面是一連串argv[]組合起來，等同於一個method，至於這個method的實際input，在aos體系下通常都來自於stdin，output也是stdout/err。另一面則是這東西可以給人使用，畢竟你讓人去寫json，其實不太方面。」應對：「若是要給人操作的(或是agent使用shell工具操作的)，那就是用法要遵循unix/linux習慣，man/--help要有，設計要符合人體工學(以人爲主)。若是單純的aos函數，不需要給人操作的，那就是argv的旗標盡量不要濫用，大多東西都走要給stdin的json，要包成工具的也通常是這類(另一類就是走shell工具)。」「設計理念上我們會覺得給人用的，跟單純的aos函數，要分開，但實作上可以根據需要去權衡。」問到給人用的程式要不要用 JSON 定義生旗標：「從一開始設計程式的時候就該想好這個程式是設計給誰用的了。不過就像先前說的，依據實際需要去做吧，比如方便與否。」白話：一串 argv＝指定呼叫哪個 method、input 走 stdin JSON；給人用的照 unix 習慣；要不要用 JSON 定義生旗標照實際需要定，不一刀切（fable 推薦的「不做」沒被採成硬規）。

## agent 就是一台狀態機（10-16 使用者定）

- **C-62** **agent 的定義就是一台狀態機；這台狀態機怎麼跑、由誰跑，概念上都不管**（接 C-18、C-39）。aos 自己的 agent 怎麼跑是規範的事（[N-53](../../NORMS/10-基礎設施-定義與工作區/06-N-50～N-53.md)：被外面的 loop 一次一次驅動）；別家的 agent（例 Claude Code）是一個行程持續跑，概念上同樣是 agent。（使用者 10-16：「agent的定義就是一個狀態機，至於這個狀態機怎麼跑、由誰跑，都無所謂。這是概念。但是我們的規範會說，為了讓agent方便審視自己，所以agent就是一個被人驅動的狀態機，需要外面有人用loop驅動他。這是我們的aos agent，至於我們常見的claude code，他們就是一個process持續執行，那是他們愛的。」，[KISS 重審拍板 4](../../../thinking/2026-10/16/kiss-recheck.md#使用者拍板10-16)）
