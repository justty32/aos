## 腦、工具、可預測性（續）

- **C-42** 工具＝被引用的標頭檔；agent 也可以是工具；aos 體系的每一樣（daemon、clock、task、inst、kernel）都基於 inst、都是 shell 指令，所以都是 agent 的工具——自我迴圈改進的閉環。（3g.12、3g.13）腦可以叫的工具（使用者 11-05 午「讓agent給自己改tool」「讓agent利用aos指令產出另一個agent」，[feat-proto 01、04](../../../thinking/2026-11/05/feat-proto/README.md)）：`lib/agent/self_tools`（改**自己這隻的**工具覆蓋層：add／rm／ls，定義不動、加減的工具同一輪就生效——使用者 11-10「3.同一輪就生效」，[tools-def](../../../thinking/2026-11/10/tools-def/README.md)；改自己的其他幾支見 [C-90](06-C-90～C-92-self一家與goal.md)），和管別隻 agent 的三支（使用者「首先是我希望拆成幾大塊：掌管子agent的管理與生滅，掌管agent定義的創造修改，掌管與其他agent的交流」「agent_def」，[agents-split](../../../thinking/2026-11/10/agents-split/README.md)；`subagent` 這個名字見 [subagent-rename](../../../thinking/2026-11/11/subagent-rename.md)）：`lib/agent/subagent`（生、叫、收**自己生的**子 agent：add／rm／ls／state／stop／start／sleep／wake／pause／resume／say／listen／ask，出生後還能調子的 tools／llm／history／hook／system；工具自己記帳、數配額）、`lib/agent/agents_ctl`（`aos-agent ctl` 的純包裝，對象是 daemon 表上任何一隻，不記帳、不算配額，成不成看權限）、`lib/agent/agent_def`（new＝把範本整夾複製成新定義、check＝轉叫 `lib/aos/defs` 看一份定義合不合格；tools／llm／system＝把工具、腦設定、system 文字直接寫進某份定義，`args` 形狀照 self_*，new 時在新定義的 `_metainfo.json` 記 `lineage`，[agent-def-fine-lineage](../../../thinking/2026-11/12/agent-def-fine-lineage.md)；`lineage` 是定義的出處，見 [C-89](05-C-89-不同質與族譜.md)）。執行時「誰生的誰」不另記：父的 `subagents.json` 有、子 rm 掉就消失（使用者 11-12「執行時誰生的誰不用另外記。」，[small-rulings](../../../thinking/2026-11/12/small-rulings.md)）。第三塊「交流」：`aos-agent say`／`listen` 接近直接存取 history，是底層、偏使用者專屬，agent 要用只能對自己的子 agent（`subagent` 的 say／listen／ask）；agent 之間真正的交流走信箱 `aos-mailbox`（使用者「就是說，aos-say/listen目前是接近於直接存取history，這對於agent來說是底層工具，並且我希望這是偏向於獨屬於使用者的。如果要讓agent使用的話，我會希望只讓他能夠對子agent做。至於真正的agent間交流，我打算去看看a2a協議，或是用aos-post實現wf/inbox協議」「a2a看過了，太繁重了。我們先做純inbox協議。」，[mailbox](../../../thinking/2026-11/10/mailbox/README.md)）。都不繼承腦與工具，只轉手下層（`aos-agent`；agent_def 轉手 `lib/aos/defs`、`aos-tools`、`aos-json`），沒有新協定；整台的總量交給判官 `max_running`。
  **知識庫、do_task／fork、生子 agent**（使用者 11-05 原話；沒標排程的都已實作）：
  - **知識庫便攜、多隻共享**（[agent-knowledge](../../../thinking/2026-11/05/agent-knowledge/README.md)）：「隨著repo出廠，不一定要走環境變數(現在可以先用這個，因為這個最方便)。最主要在於我希望這東西是便攜的，隨意複製，隨意修改，隨意給agent指定、隨意拆卸增添。」「並且這套知識庫還可以給多個agent共享！」——知識庫是普通資料夾；多隻指同一個資料夾就是共享。記憶庫是純 JSON 樹（使用者 11-10「記憶庫這東西，我原本以爲會是純json做的」…）：節點＝`.json` 檔與裡面的 key、表＝`_index`，形狀見 [json-memory](../../../thinking/2026-11/10/json-memory/README.md)。
  - **分層**：「頂層可以是簡介、index目錄之類，並且盡量講簡單(ELI5風格？)，然後agent有需要的話，再去透過工具，或是一些其他東西去抽取更深一層的知識(或者是當初在規劃該agent用途的時候，就考慮到它需要這個，然後在定義那邊就給他配上)。」
  - **依託檔案系統**（只限記憶這件事，不升成總原則）：「現有的資料夾、檔案系統，本身就是一個很好用的東西，盡量依託於這塊。」**格式不限**：「markdown, json, yaml之類的格式都可以。"人類可讀性"可以是次要考慮選項」。
  - **做成工具、不做成 agent 機制**（[small-thought](../../../thinking/2026-11/05/small-thought/README.md)）：「我也不建議把這做為agent機制，我更推薦將其作為工具。」「其實記憶這項，他本身也算是任務」——做法是兩支工具 `do_task` 與 `fork`（使用者 11-11：「就是說，他有兩種實現方式，一種是fork……另一種是save/load，也就是從在呼叫do_task那時候留下一個紀錄點，等做完task後使用self_history修改history，將進行這段task的過程中的history做總結，然後退回load那邊」；選項框裁「把fork單獨拉出來做為工具。do_task改成save/load模式。」「do_task有兩個子指令，一個是開始，一個是結束。結束的時候要附上總結」「eca 不給 do_task」，派一件事給乾淨子 agent 的小幫手能力「拿掉這個能力」，[fork-and-do-task](../../../thinking/2026-11/11/fork-and-do-task/README.md)）：`lib/agent/do_task` 是 save／load——`start` 在自己的 history 留紀錄點、`end` 附總結把紀錄點之後的訊息換成一則總結（經 aos-agent history，原文照舊留在 `history_removed.jsonl`），不生子、不抄子帳，只給 agent-fsm 的身體。任務期間別人送進來的訊息（信、goal 提醒、新信通知）預設一起摺進總結，可選留在總結後面（使用者「可選。預設清掉。」，[fork-and-do-task 02](../../../thinking/2026-11/11/fork-and-do-task/02-do_task.md)）。整份複製自己去做的那半是 `fork`：「一律連對話複製」——定義同一份，history 整份、self 一家改過的工具、腦、hook、system 一起帶，給分身一個目標、只拿回結論；只給 agent-fsm 的身體（使用者「eca不給fork。」，eca 叫到就報錯、指向 `subagent`）；分身不能再 fork（深度 1，代定、可翻案，[fork-and-do-task 01](../../../thinking/2026-11/11/fork-and-do-task/01-fork.md)）。
  - **帳沿呼叫樹往上收**：會收掉子 agent 的工具，收之前把子公開宣告的帳抄進自己小格的 `observed/<子名>/`——`subagent` 在 `ask`／`listen` 回來與 `rm` 前，`fork` 在收分身前；`do_task` 不生子、不抄。（11-07 使用者裁定，傍晚選項框 ltn-5 選推薦，[lift-to-norms](../../../thinking/2026-11/07/lift-to-norms/README.md)）
  - **生子 agent 兩種、工作區不固定**（[feat-proto](../../../thinking/2026-11/05/feat-proto/README.md)）：「生子agent有分兩種，一種是產出新agent定義，另一種是用現有定義生(可能會稍微改一些設定)。我希望兩種都有」——「產出新定義」是 `agent_def` 的 `new`（只把範本整夾複製成新定義，不掛上；改內容用 `agent_def` 的 tools／llm／system 或一般檔案工具），「用現有定義生」是 `subagent` 的 `add`（記帳的子）或 `agents_ctl` 的 `add`（不記帳），要改的設定照 `aos-agent ctl add` 的旗標給；工作區「不要固定，因為各有不同需求。」——這兩支的 `add` 收 `ws`（沒給＝沿用父的 `$AOS_WS`；使用者 11-06 被問到這條跟 P-32「被叫者不沿用呼叫方 `AOS_WS`」照哪邊，答「移除P-32」，[special-cases 05 第 3 處](../../../thinking/2026-11/06/special-cases/05-衝突與方向題.md#條文裡已經互相矛盾的不用問給條文隊)）。出處 [agents-split](../../../thinking/2026-11/10/agents-split/README.md)。
  - **上限兩道關**（使用者 11-06）：「工具自己有紀錄，會看到說超過四個，直接回error」——兩道關各數各的：`subagent` 自己數這隻父生了幾隻（`max_subagents`，預設 4，超過回 `SubagentSlotMissing`、不寄信，[subagent-rename](../../../thinking/2026-11/11/subagent-rename.md#11-11-稍後周邊一起改成-subagent-系)），判官管整台總量（`max_running`）；`agents_ctl` 不數。
  - **知識庫存什麼、給人看什麼**（使用者 11-07 午，收 arknights 語料時裁）：「節點名確實建議英文，剩下隨意。內部內容建議按照語料原文，這樣能最大程度保持原意。這是儲存方面，至於使用者想看的時候，可以透過其他界面，比如做一份附屬知識庫，其中是翻譯過的白話，或是直接準備一個agent幫忙解答問題。類似RAG。」白話：節點名（路徑上那一段）用英文，其他像標題怎麼寫都隨意。從外部語料收進來的知識庫，節點內文照語料原文逐字存，不翻譯、不改寫，這樣原意最完整。這是**存**的那一層；人要看時走另一層：另做一份翻成白話的附屬知識庫，或者準備一隻問答 agent 回答問題（類似 RAG）。兩層分開，存的那層不為了好讀而改原文。（「人類可讀性可以是次要考慮」見上面「依託檔案系統」那條。）已定；問答 agent 原型在試驗場（arknights-kb 06），附屬白話庫還沒做。（出處 [proto8/thinking/2026-11/07/arknights-kb/README.md](../../../thinking/2026-11/07/arknights-kb/README.md)） 原文要讓連結指到「第幾段」時，可以把原文存成逐段陣列：內容仍逐字，只是容器從一整段字串變成陣列，連結就能用 `節點#/paras/N` 這種 JSON 指標指進去（使用者 11-07 午後選「可以，存成逐段陣列」）。怎麼切（現在是照換行切、`"\n".join` 要跟原文逐 byte 相同）是試驗場的代定，不是規則。已定；試驗場已照做（arknights-kb 10-第二輪設計）。（出處 [proto8/thinking/2026-11/07/kb-ideas/README.md](../../../thinking/2026-11/07/kb-ideas/README.md)）
