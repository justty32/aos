# kernel

- **C-09** 任務處理過程中用到的東西，只要有限，就是資源。（2.7）
- **C-10** 資源的有限用格數表示。（3b）
- **C-11** 排序演算法＝決定哪個任務先給哪個資源；就這樣，不多說。（2.7）
- **C-12** 排序與資源分配本身是計算任務；資源本身也當行程看——一切都是計算任務，核心沒有第二種東西。（2.8）〔這裡的「核心」＝名詞表的「系統本體」，不是 C-74 分層裡的核心 aos-exec〕
- **C-13** 每個計算任務都有固定的基礎特性（九軸）；其中確定性是任務自己的屬性。（2.9）
- **C-14** 基礎特性之外，人可以任意附加特性。（2.9）
- **C-15** 排序程式可以由人寫，也可以由「生成排序程式的程式」叫模型寫。（2.10）
- **C-28** 沒法直接轉成 POSIX 呼叫的事（人手畫），用**間接抽象化**變成計算任務：拆成多個 POSIX 任務（寄信給畫家、收信、畫歸檔），人在這幾個任務之間、在系統外面做事。（3c）
- **C-29** 處理單元分兩種：普通 CPU（跑寄信、收信這類一般任務）；外部 PU（畫師、GPU、NPU）——跟外部設備的概念靠攏。（3d）
- **C-38** 第三層（kernel）的參照物就是時間（時鐘）與空間（資料夾）：「三回合內搞定」「只動這三個資料夾」「每檔不超過幾 KB」。它只是一個排程；PU 怎麼收任務請求各資料夾各做各的。（3g.6）
- **C-47** kernel 的定義分兩層。**原生定義**（寬泛，10-15 使用者定）：能夠管理哪些東西被執行或被使用的一個東西。**aos 的說法：kernel＝「資源管理＋排程」，而且是從外面看進去的身分**（使用者 11-11「我覺得kernel定義要改一下，回歸初始，變成"資源管理+排程"。」，[thinking 11-11 kernel](../../thinking/2026-11/11/kernel/README.md)）：一個 agent（或其他函數）有掛 proc 或其他 syscall 的請求，把請求寄到哪，那個地方對它就是 kernel。寄出去之後要不要處理、什麼時候執行，是對方說了算，所以對寄件人來說，對方就具有資源管理與排程的功能——啥都不管也是一種管理。收件的 proc 自己不必知道自己是 kernel；只能處理掛 proc 或只能處理問腦的都算，不太限制。使用者 11-11：「kernel這個身分是從外面看進去的，對於一個有掛proc(或其他syscall)的需求的agent(或其他函數)來說，把掛proc這個請求寄到哪去，那個地方對他而言就是kernel。但對於能夠處理這個請求的proc來說，他沒必要有自己是kernel的自覺。然後有些kernel他可能只能處理掛proc或只能處理llm call，都無所謂，不太限制。因為你把請求寄出去後，是否要處理這個請求，或是說有決定這個請求啥時候要被執行的權力的，就是對方那個proc了，所以對你來說，那個proc就是具有資源管理與排程功能(啥都不管也是一種管理)的kernel。」相關：資源與排序 C-09～C-15、處理單元 C-29、參照物 C-38、間接抽象化 C-28；kernel 的規範見 [N-42](../NORMS/09-kernel.md)。
  - **一律寄 `AOS_KERNEL`**：像 Linux 的 user space proc 只看得到 kernel、看不到硬體，一般 proc 寄 syscall 請求只寄 `AOS_KERNEL`；寄出去之後背後是黑盒子，不管信會去哪（使用者 11-11「我的想法是一律寄到AOS_KERNEL，然後就如同linux一樣，user space的proc他只能看到kernel，除非有特殊需求，否則他看不到硬體」「寄送出去之後，我們就不管這封信會去哪了，他背後就應該是黑盒子了。」）。`AOS_KERNEL` 沒設就寄 `AOS_DAEMON` 那台的 ctl 信箱——daemon 自己就是最基礎的 kernel（來者不拒，[附錄1](附錄1-名詞.md) daemon 列）。兩個都沒設時再找 cwd 的 `./.stack`，那裡也不是資料夾才報 `DaemonMissing`（[N-63 例外「`AOS_DAEMON` 沒設＝找 cwd 的 `./.stack`」](../NORMS/10-基礎設施-定義與工作區/07-hub-型環境變數與父子交代/02-N-63-實例-AOS_DAEMON與沒有AOS_HUB.md)）。`AOS_DAEMON` 照樣傳給一般 proc，約定不用（使用者選項框「照傳，約定不用」）。
  - **多種 syscall**：有一個通用的基礎 kernel，普通的掛 proc 請求都去它那；另有多種 syscall，有些走另一個 kernel，例：問腦走 `AOS_LLM_KERNEL`，跟 `AOS_KERNEL` 維持兩個變數（使用者選項框「維持兩個變數」）。使用者 11-11：「所以我們這邊和linux kernel不一樣，我們有一個通用的基礎kernel，類似linux kernel，所有普通的掛proc請求都到他那邊去，類似syscall。但我們有多種syscall，有些syscall是走另一個kernel。」
  - **轉交也算，鏈是自然形成的**：判斷後把請求轉交給另一個 kernel 的也算 kernel，命名可以帶 kernel、別濫用（使用者 11-05「假如他判斷要跑這個請求的時候，所做的動作是把請求轉交給另一個真正有權限的kernel，那他也算kernel嗎？我覺得是算的，他的命名中也可以帶有kernel，只是說，建議不要濫用...。」，[thinking 11-05 kernel-daemon 05](../../thinking/2026-11/05/kernel-daemon/05-衝突與方向題.md)）。所以一封掛 proc 請求可以走 agent→kernel_1→kernel_2→…→daemon，中間站本身也可以是一台 daemon（它的 loop 裡有 kernel 功能）。鏈上的站不必有「鏈」的概念，只知道這份請求的 src／dst、自己做點處理（使用者 11-11「而chain這東西就是自然而然形成的，chain上的kernel可以沒有這個概念，他們就是只知道這份請求的src/dst，然後自己做一些處理而已，當然，有需要的話我們後續可以再做一些格式上的改進。」）。站與站之間一律走 aos-post：共通的只有 aos-post 信封，請求放在 body 裡，body 各類自理、不多做限制（使用者 11-11「然後"請求"格式，他是被包在aos-post格式的body內的。在請求格式之內，就不用多做限制。」）。回信怎麼走看各站設定：每站轉寄時對信封上的 `reply_to` 二選一——不動它＝回信跳過我，改成自己＝回信先回我；不記走過哪些站、不帶最初寄件人，所以後站無法跳過已把回信位址改成自己的前站，風險使用者自擔（使用者 11-11「1.看各站kernel怎麼設定」「都可以的，使用者自行承擔風險。」「2.不記。」）。
  - **擺法只是範例**：繼承式（daemon.json 的 `exec` 身體當判官、判完轉寄進自己的 ctl 信箱）與 0 號 proc 式（daemon 底下一個專門收請求的 proc，判完替人寄進 daemon 的 ctl 信箱）是兩個範例擺法，範本 `kernel/daemon-judge`、`kernel/procs-kernel`（[kernel-daemon 02](../../thinking/2026-11/05/kernel-daemon/02-兩種模式.md)）；不是只有這兩種，自己寫一個收請求的 proc 也算 kernel。
  - **安全的保底是 Linux 本身**（使用者 11-11「我這邊還是一樣的立場：非正規操作的風險由使用者自行承擔、最基礎與通用，同時也是保底的安全機制，就是linux本身，包括使用者、權限啥的。」）：aos 不驗寄件人。人也改用 kernel：人平常用的 `aos-agent ctl` 照 `AOS_KERNEL` 寄；想直接碰 daemon 或更深的 kernel，靠 Linux 權限（使用者 11-11「人這邊也改用kernel，想要存取daemon或更深的kernel？靠linux權限。」）。權限沒設也可以，繞過的風險自己承擔（使用者 11-05「linux權限沒設也可以(因為我知道有些人嫌麻煩，或是還處在demo狀態)，就自行承擔風險。」）。`aos-daemon-ctl` 是指名要碰某台 daemon 的工具：一律直寄那台的 ctl 信箱、不看 `AOS_KERNEL`，有 Linux 權限就能用（使用者選項框「維持直寄，它就是『指名 daemon』的工具」「aos-daemon-ctl 永遠直寄」，[os-impl 08](../../thinking/2026-11/06/os-impl/08-aos-daemon-ctl永遠直寄實作結果.md)）。
  - **已裁定、未實作**：① 一般 proc 讀狀態＝kernel 給一個狀態位址（使用者選項框「kernel 給一個狀態位址」）：「狀態在哪」是又一種請求信，不用 symlink（使用者 11-11「然後kernel給狀態位址...希望不是使用symlink，我不希望aos體系硬性依賴symlink，或許可以折衷？寄信問，取得狀態位址這樣。」）；問來的位址記不記，工具自己決定（使用者選項框「工具自己決定」）。做好之前，一般路徑上直接讀 daemon 檔的有兩處：`aos-agent ctl` 查表、hook 的 clock 名字解析（[現況查核](../../thinking/2026-11/11/kernel/02-現況查核.md#誰直接碰-daemon)）。② 通用 kernel 框架：一包方便零件、不是概念，框架一份，現有判官與問腦總機都收進來，`AOS_LLM_KERNEL`、`AOS_KERNEL` 仍是兩個變數（使用者 11-12「問腦總機要收進框架」「kernel先這樣就好，開工等假日。我自己也要思考一下」，[kernel-framework](../../thinking/2026-11/12/kernel-framework/README.md#已裁問腦總機收進框架)；N-42 (2)）。
  - **一切都可以嵌套**（使用者 11-07，[arknights-kb](../../thinking/2026-11/07/arknights-kb/README.md)）：「agent可以成千上萬個，反正可以sleep，交給llm kernel的thinking請求也有排程，並且thinking請求還可以經過一些額外關口，比如一個隊伍使用一個llm_kernel，然後這個llm_kernel負責排程與將請求轉交給另一個llm_kernel，直到轉交給實際打API的llm_kernel，一切都可以嵌套。對，工具也是，工具可以是開一個agent做事，或是將請求交給專精此道的kernel，所以才說會有成千上萬個agent。就好比LLM的神經元，不是每個區域都會被激活。」白話：llm kernel 可以一層一層轉交：隊伍的 kernel 負責排程，再交給上一層 kernel，一路交到真正打 API 的那台。工具也一樣，可以開一隻 agent 去做，也可以把請求交給專精這件事的 kernel。所以 agent 可以有成千上萬個，但同一時間只有一小部分在動，像神經元不會全部一起亮。轉交型算 kernel（上面「轉交也算」），「建議不要濫用」那句照樣有效（兩句怎麼一起讀見 [lift-to-norms C-T09](../../thinking/2026-11/07/lift-to-norms/04-打架.md)）。一層轉交（隊 kernel → 總機）排在 evolve-design 落地步 6，更深的嵌套、排程、跨層對帳交給 kernel-nest。
  - **C-11／C-12 與本條**（說明，不是新規則；[os-concepts 02](../../thinking/2026-11/06/os-concepts/02-OS與kernel-能借鑒.md#跟既有原則已裁的關係)）：C-11／C-12「排序＝kernel 的事」就是本條的「資源管理＋排程」——排序與准不准由收件的 kernel 決定，實際掛上去由 daemon 執行（daemon 來者不拒照掛）。
