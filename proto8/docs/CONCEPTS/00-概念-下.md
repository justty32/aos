# proto8 概念（下）：基礎設施、kernel、agent——一條一兩句

← 上半：[概念（上）](../CONCEPTS.md)（設計理念、時空；寫法同上半）｜名詞 [附錄1](附錄1-名詞.md)

## 基礎設施

**[inst、loop 與 daemon、tasks、fsm](03-基礎設施/01-inst至fsm.md)**
- **C-08** 計算任務＝一個 POSIX 行程，不是 thread；不再往下分種類。
- **C-34** 求值＝放開讓它算、過一段時間看空間狀態的變化；對資料夾求值＝執行它，還回來的是正在變動的資料夾、不是一個值。
- **C-42b** inst 的 JSON 可以多放東西（九軸、traits、標籤、工具…），inst 不認的別人可以讀；這個抽屜叫 `_metainfo`。
- **C-36** 層層遞進：inst（求值一次）→ loop（持續求值）→ node（loop 服務的資料夾）→ daemon（統管 loop）；daemon 跑的可以是另一個 daemon。
- **C-41** 巢狀：table 的元素也是 table；元素要不要先求值由 entry 決定（像 lisp 的 quote）。
- **C-18** agent 是狀態機、是函式、也是計算任務；直接接進系統本體，不特別處理。
- **C-25** 大操作（問模型、跑久的工具）丟給另一個行程；agent 每次被叫只走一次、很短，由外面的 loop 驅動。
- **C-39** agent 是一個資料夾、一個 node、一張 table（模型、context、工具、記憶各占一個元素），持續被求值；最普通的 agent＝在等待、思考、行動之間切換的狀態機。
- **C-49** fsm 要很單純：在某狀態就執行指定的 inst，裡面的事 fsm 不管；錯誤、計數、暫停、傳資料歸格自己或跑它的 loop。

**[proc 之間的交流](03-基礎設施/01-續-C-75.md)**
- **C-75** proc 之間的交流三種基本概念：投遞、窗、父子交代，其餘是組合；鎖不是交流；非同步呼叫建在 aos-post 收發信上，不跟它耦合太深。

**[資料夾程式、工作區與 stack](03-基礎設施/02-資料夾程式-工作區與-stack.md)**
- **C-65** stack 與工作區是兩個東西：stack＝被叫的程式執行時放東西的地方（狀態、紀錄、小格，像呼叫堆疊）；工作區＝使用者的檔與成品，只放交辦的東西與成果。
- **C-66** 影響外部＝透過指標，指標就是 `AOS_WS`；能不能寫由 Linux 權限管，風險設計者自管。
- **C-67** stack 放哪由呼叫方自由決定，被叫的不必知道；改值就得到不同效果，程式不動。
- **C-87** 往下「變成」另一套＝共用同一個 stack（像繼承）；「叫」另一個程式＝給它小格（像組合）；撞名不做隱性命名空間，各自管好。
- **C-80** 不在任何 daemon 下的不管；體系的基礎是 daemon／loop／exec 三者合一，指到 daemon 外風險自擔。
- **C-81** stack 是 proc 自己的地盤、放什麼自訂；對外介面要守原則、保持靈活：命令列參數、環境變數、stdin／stdout／stderr／結束碼、信箱內容格式。

## kernel

**[kernel](04-kernel.md)**
- **C-09** 任務處理中用到的東西，只要有限就是資源。
- **C-10** 資源的有限用格數表示。
- **C-11** 排序演算法＝決定哪個任務先給哪個資源。
- **C-12** 排序與資源分配本身也是計算任務，資源也當行程看——系統本體沒有第二種東西。
- **C-13** 每個計算任務都有固定的基礎特性（九軸），確定性是任務自己的屬性。
- **C-14** 基礎特性之外，人可以任意附加特性。
- **C-15** 排序程式可以人寫，也可以由「生成排序程式的程式」叫模型寫。
- **C-28** 沒法直接轉成 POSIX 呼叫的事（人手畫）用間接抽象化，拆成幾個 POSIX 任務，人在系統外面做事。
- **C-29** 處理單元分兩種：普通 CPU，與外部 PU（畫師、GPU、NPU，靠攏外部設備）。
- **C-38** kernel 的參照物是時間（時鐘）與空間（資料夾）；它只是一個排程，PU 怎麼收請求各做各的。
- **C-47** kernel＝資源管理＋排程，是從外面看進去的身分：請求寄到哪，那裡對寄件人就是 kernel（啥都不管也是管理）；一律寄 `AOS_KERNEL`、背後是黑盒；轉交也算，鏈自然形成；安全保底是 Linux 本身。

## agent

**[腦、工具、可預測性；函數＋binding](05-agent/01-腦-工具-可預測性與agent函數binding.md)**（[C-22](05-agent/01-續-C-22.md)、[C-42](05-agent/01-續-C-42.md)）
- **C-19** agent 的簽名＝腦（模型）＋記憶（核心人格、近期記憶）＋手腳（工具）。
- **C-20** agent 是複合型任務（外迴圈便宜、模型與工具貴），所以要被排程；最核心的一題是很多 agent 時誰先用腦。
- **C-21** 可預測性有主體性：不是任務的屬性，是觀察者的認識。
- **C-22** 提高可預測性：當 S 表示式拆開，能寫死的節點換成程式；優化目標是確定性。
- **C-22b** 可預測性也看執行環境：節點＝函式內部＋它所在的執行環境。
- **C-23** agent 內部怎麼設計是後面的事，先把底打好。
- **C-40** agent 要能當拋棄式函式用：引用設好的資料夾、填幾個引數就跑，執行環境在引用者這邊；library 做 binding。
- **C-42** 工具＝被引用的標頭檔，agent 也可以是工具；aos 的每一樣都是 agent 的工具——自我迴圈改進的閉環。
- **C-46** agent 的使用＝函數＋binding：定義資料夾呼叫時不變、可重複用，stack 是另一個參數；是概念上的函數、不是形式上的；agent 只看到自己的工具清單，徹底切割。
- **C-50** agent＝狀態機＋各狀態跑的 inst，複雜度集中在 inst；一個 agent 的定義＝一個資料夾，布局與 JSON 要保持單純。

**[工具、狀態機](05-agent/02-agent-的工具與agent-就是一台狀態機.md)**
- **C-61** 工具的地址不用 PATH：由自己的 `tools.json` 登記，或放在呼叫它的那格裡；工具一律是資料夾程式；共用的收成函式庫，引用不複製。
- **C-82** aos 函數與 tool 呼叫要能無痛互轉；argv 有兩面（指定 method、給人用），input 走 stdin JSON；設計之初就想好給誰用。
- **C-62** agent 的定義就是一台狀態機，怎麼跑、由誰跑概念上不管。

**[C-84](05-agent/03-C-84.md)**、**[C-88](05-agent/04-C-88-記憶與index.md)**、**[C-89](05-agent/05-C-89-不同質與族譜.md)**、**[C-90～C-92](05-agent/06-C-90～C-92-self一家與goal.md)**
- **C-84** 系統自己改進函數：改好的自動換上、變差自動退回、容忍短暫退步；判準本身也能改，審視者可以一層層疊。
- **C-88** 整個檔案系統＋json 就是 agent 的記憶，缺的只是 index：一條路徑尋址（`aaa.json#/xxx`）；`_index` 是視角不是事實，天然在被描述節點的上一層，只給太大的補。
- **C-89** 不同質 agent：定義就是身份；同不同質看簽名、差一軸就算，同質是缺陷不是合併令；族譜＝資料夾樹＋出生時的 `lineage`；狀態看所在位置。
- **C-90** self 一家：每支 `self_X` 是人用指令 `aos-agent X` 的純包裝、目標改成自己（改 stack 那份、定義不動）；人用的指令先有。
- **C-91** goal：agent 自己停下來時，aos 把目標丟回給它，它自己宣告完成或暫停；todo 放自己小格、不自動帶進 prompt。
- **C-92** 工具說明塞不進小模型的 context 就先把 context 開大；真裝不下，那模型不適合當 aos agent，只當普通 aos 函數。
