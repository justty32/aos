## 使用者裁定（11-06，選項框）：C-52 的讀法、准讀下層 stderr 改成判準＋現行表

出處 [special-cases 使用者裁定](../../../thinking/2026-11/06/special-cases/README.md#使用者裁定11-06選項框)。上文與主檔原句全留，照下面改讀。

- **讀法：不認身份、可認公開介面**（選項「不認身份、可認公開介面 (Recommended)」）：本條「上層不需要、也不該知道下層是什麼」讀成——上層可以依賴下層**公開宣告**的介面（對外標頭、schema、`interfaces.json`、README 寫明的檔名與格式），**不准**認對方的程式名、內部檔名、錯誤字句來分支。例：daemon 的 loop 型可以用 aos-loop 公開的 `ctl`／`state` 窗，但不准認 aos-loop 錯誤行的字句。現況不合的幾處（daemon 認 aos-loop 錯誤行、預設檔名兩邊各寫一份；llm kernel 讀 daemon 表的字句、手拼掛 proc 的信；lib 工具認範本）實作排在 [apply-ideas 02 § special-cases](../../../thinking/2026-11/06/apply-ideas/02-排程.md#11-06-special-cases-排程k-隊)。
- **准讀下層 stderr：一條判準**（選項「改成判準＋現行表 (Recommended)」）：一層的出口讀者看不到下層的 stderr（外部 agent、腦、回信的收件人、看表的人）時，這一層**失敗時**可以把下層錯誤行的「代號與原因」接進自己那一行，或附下層 stderr 最後 2 KB；成功時不附；下層 stderr 照樣原樣透出。aos 內部上下層之間（讀者是程式）不適用。照判準推得出來的不必再逐項裁；透出的程式在自己的 README 寫一行「透出：哪種、給誰」。主檔的「三處」「只限 aos-mcp」「出口都是給人或外部 agent」與編號 ①～⑤ 改讀成下表。

## 特例怎麼處理：升格門檻（11-06）

使用者 11-06 選項框「第 3 次升格 (Recommended)」（[special-cases 04](../../../thinking/2026-11/06/special-cases/04-升格建議與慣例草稿.md)）。不只 C-52，條文與程式裡所有「一般規則＋例外」都照這幾條：

1. **認名型第一次就消**：例外要成立得讓 A 寫死認得 B 的程式名、內部檔名、格式或錯誤字句 → 改成「B 宣告、A 照宣告」或任何人都能寫的通用欄位（例：P6 → `auto_restart`）。
2. **同一形狀第 3 次升格**：同一句「一般規則＋例外理由」在 3 個不同的程式或條文出現 → 寫一條判準取代逐項清單，之後照判準推得出來的直接做。第 1、2 次維持特例，在例外處註明「同型第 N 次」。
3. **清單 5 項或 3 天 2 項就改寫**：一份例外清單到 5 項，或 3 天內加了 2 項 → 改寫成「判準＋現行表」（現行表只列現在有效的；原句照舊留在原處）。
4. **「先不做」要寫等什麼**：範圍限縮型的例外寫一句「等 X 才動」，X 發生了照 1～3 重審。
