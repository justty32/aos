- **C-01** aos 存在的理由是讓大語言模型方便使用；目標多到只能靠模型寫，所以核心要讓模型好用。（2.1；使用者 11-17 選項框「改回「核心」」；C-74 分層裡的「核心」專指 aos-exec，見 C-74）
- **C-02** aos 蓋在現有作業系統上，硬體層的計算分配不重做。（2.5）
- **C-03** 由下往上：Linux → daemon → 時空 → 排程與資源分配 → agent。上層只透過下層。（2.5、2.10）（註：C-03 講的是誰排程誰〔排程與資源分配＝kernel 排在 agent 下面，因為它排 agent〕，[C-74](02-C-51.md#分層10-22-使用者定) 分層講的是誰依賴誰〔kernel 與 agent 同在最上層，都用基礎層與標準庫寫成〕，兩條軸不衝突。）
- **C-04** daemon 完全處理 Linux 那邊的事；它之上的東西不碰 Linux。這是推薦：aos 自己的程式盡量照它；別人要另搞也可以、風險自擔（使用者 11-12，[small-rulings](../../../thinking/2026-11/12/small-rulings.md#11-12-下午再裁三條agent_def-兩題沙箱與-c-04)）。（2.5）檔案讀寫權限也是這層能借來用的，見 [C-64](05-布局成長與檔案權限.md#檔案權限10-16-使用者定)。
- **C-07** 體系用的表達方式以模型天生就會的為準（檔案系統、POSIX、JSON），為的是讓它能自省。（2.6、9/23）
- **C-24** 要最佳化的不是時間空間，是金錢、可預測性、人能不能理解。（9/1 ideas 01；2.1 重申）
- **C-45** 比起實作，更重要的是規範。aos 提供一些符合規範、方便的語法糖（例如 [inst](../../../cpp/aos-inst/README.md) 庫、aos-fsm），但不要求所有人一定要用。（10-12）
- **C-43** 最終效果：一套 library，用 lua／lisp 一類語言把一套 aos 程式（整套資料夾布局）生成出來——那個生成就是「編譯」——把 aos 當作業系統跑；人和 AI 都要能用。（3g.1、3g.12；新舊打架，11-17「新的覆蓋舊的」：10-19 晚「用lua/lisp生成這麼一套資料夾佈局」較晚）一套 aos 程式就是一堆資料夾與檔案（一個 table 一個元素堆出來的），與其手動 mkdir、vim 一個一個堆，不如用語言生成；library 就是做這件事的。10-19 晚使用者答「編譯」在資料夾＝程式（C-68）之下的意思：「意思是我們要做這樣一套程式，要一個一個mkdir, vim修改檔案，等於是一個元素一個元素去堆疊出一個table，那不如直接用lua/lisp生成這麼一套資料夾佈局」（[ideas § 12](../../../thinking/2026-10/19/ideas/README.md)）
- **C-48** JSON 格式族：沿用 inst 單子族、loop／fsm 設定族，靠加 key 與任意 value 擴充（只處理認得的 key），除非必要不新增格式（10-15，[原文](../../../thinking/2026-10/15/json-families.md)）。
  - **私有 key**：各功能可以在同一份 JSON 放只有自己看得懂的 key，藉此共享同一份格式，前提是 key 不重疊（共用同一份檔的私有 key 真的撞名了才加功能前綴；各程式的說明列出自己認得的 key）。
  - **不認得的 key 一律忽略、不報錯**，不分開頭是不是 `_`（10-23 晚使用者「不認得的key就是忽略」，[逐字原話](../../../thinking/2026-10/23/naming.md)）。`_` 開頭的 key 是普通 key，沒有附註慣例（使用者「_開頭=附註這個概念刪掉」）。程式改名或拿掉後的舊 key 也是不認得的 key，一樣忽略、不報錯、不過渡（使用者 11-03「1. 當沒看到。」，[thinking 11-03 procs](../../../thinking/2026-11/03/procs/README.md) § 4）。函數的 stdin JSON 同此（使用者 11-05 晚，[json-argv 07](../../../thinking/2026-11/05/json-argv/07-使用者回覆-11-05晚.md)）：「我第一時間想到的是c++的std::bind，面對一個已經bind到剩下兩個參數的函數，我們塞給他四個參數，他也只能吃其中兩個，剩下兩個忽略。是的，不報錯，因爲json的格式自由，而我們只吃json裏面我們想吃的。」
  - 不在此列：給人打的旗標，不認得的仍是 `FlagUnknown`（P-44，打錯要知道）；只有自己讀的子物件（沒有私有 key 的需求）可以對不認得的 key 報錯，幾支程式共用的檔，頂層照舊忽略（使用者 11-09「剩下都OK」＝照推薦，[format-versioning 04 D3](../../../thinking/2026-11/09/format-versioning/04-設計問題.md#d3-同一份檔裡兩套規則)、[README 裁定 4](../../../thinking/2026-11/09/format-versioning/README.md#使用者-11-09-裁定)）。
  - **值的雙形**：一個值除了字面純值，也可以寫成物件（展開形），像 Lisp 的 `3` 與 `(+ 1 2)`；展開形的原值推薦用 `val`（C-55；11-07 使用者「程式不動，條文改成"推薦用val"」，[kernel-nest](../../../thinking/2026-11/07/kernel-nest/README.md)）。aos 自己的程式盡量兩形都收（推薦），太麻煩的地方可以只收純值（例外）（使用者 11-17「推薦兩形都收，可例外」）。
  - **指示詞**是值的雙形的一種用法，有 `$env` 與 `$ref` 兩個，修飾詞是 `$path`、`$prefix`：`$env` 換成該環境變數底下的路徑，讀的是執行當下的環境、像 shell 的 `$HOME`，是正式機制；`$ref` 指到別處的值，也可以幾份照順序合成一份；寫法與合成細則見 N-45；單子本來就能內嵌，不必拆檔；argv 陣列也能放指示詞（10-16 夜使用者「可以用$env啊」，頂層給兩案、選「A」；[CONVENTION P-31](../../CONVENTION.md)、[N-45](../../NORMS/06-基礎設施-命令列與指示詞.md)、[ideas 10-20](../../../thinking/2026-10/20/ideas.md) D1、D2、D8）。函數描述裡的公式 key 不是指示詞，是普通 key，只有讀描述的人算，aos-exec 不碰（N-68；11-07 使用者裁定 ltn-6 選推薦，[lift-to-norms](../../../thinking/2026-11/07/lift-to-norms/README.md)）。
  - aos 讀的 JSON 都解（使用者選「aos 讀的 JSON 全部支援」）：規範是 aos 自己的程式一律支援，別人的程式不一定支援是事實、不是規範；每支程式只解自己讀的格，見 N-45。
  - 程式把某一欄搬出 JSON、寫成純文字外顯檔，不算新增格式：那是 N-13 允許程式自訂名字與格式的外顯檔，照 C-54 帶純文字副檔名；什麼欄搬出、怎麼寫見 [N-09](../../NORMS/05-基礎設施-窗/02-N-09～N-11.md)（使用者 11-09 五題「都照推薦」，[clock-and-hot-writes](../../../thinking/2026-11/09/clock-and-hot-writes/README.md)）。

  檔名與檔內格式的細節：[檔名見 NORMS 命名續](../../NORMS/命名-續-概念搬來的檔名.md)。

- C-48 值的雙形：`priority` 寫 `"low"` 或 `{"val", "deadline"}`；問腦總機（`py/tools/aos/kernel_llm`）的 priority 展開形用 `level`。指示詞：`{"$env": "AOS_STACK", "$path": "plan"}`、`{"$ref": ["a.json", "b.json#/c/d"]}`。
