- **C-01** aos 存在的理由是讓大語言模型方便使用；目標多到只能靠模型寫，所以核心要讓模型好用。（2.1）〔這裡的「核心」＝名詞表的「系統本體」（大範圍那個），不是 C-74 分層裡的核心 aos-exec〕
- **C-02** aos 蓋在現有作業系統上，硬體層的計算分配不重做。（2.5）
- **C-03** 由下往上：Linux → daemon → 時空 → 排程與資源分配 → agent。上層只透過下層。（2.5、2.10）（註：C-03 講的是誰排程誰〔排程與資源分配＝kernel 排在 agent 下面，因為它排 agent〕，[C-74](02-C-51.md#分層10-22-使用者定) 分層講的是誰依賴誰〔kernel 與 agent 同在最上層，都用基礎層與標準庫寫成〕，兩條軸不衝突。）
- **C-04** daemon 完全處理 Linux 那邊的事；它之上的東西不碰 Linux。（2.5）檔案讀寫權限也是這層能借來用的（例 kernel 當某 daemon ctl 的唯一寫者），見 [C-64](05-布局成長與檔案權限.md#檔案權限10-16-使用者定)。
- **C-07** 體系用的表達方式以模型天生就會的為準（檔案系統、POSIX、JSON），為的是讓它能自省。（2.6、9/23）
- **C-24** 要最佳化的不是時間空間，是金錢、可預測性、人能不能理解。（9/1 ideas 01；2.1 重申）
- **C-45** 比起實作，更重要的是規範。aos 提供一些符合規範、方便的語法糖（例如 aos-inst、aos-fsm），但不要求所有人一定要用。例：aos 時空這個概念衍生出的規範＝大家都要看 tick-tock 時鐘、資料夾別亂弄。（10-12）〔現況：inst 是 impls 的 C lib（[inst](../../../impls/aos-inst/README.md)），沒有 aos-inst 命令列；只有 C++ 版（使用者「python版本可以刪掉了。aos-exec/loop/daemon都用C++」）。〕
- **C-43** 最終效果：一套 library，寫完編譯成基於 aos 的類 LISP 程式，把 aos 當作業系統跑；人和 AI 都要能用。（3g.1、3g.12）**「編譯」在資料夾＝程式（C-68）之下的意思，10-19 晚使用者答**：「意思是我們要做這樣一套程式，要一個一個mkdir, vim修改檔案，等於是一個元素一個元素去堆疊出一個table，那不如直接用lua/lisp生成這麼一套資料夾佈局」——一套 aos 程式就是一堆資料夾與檔案（一個 table 一個元素堆出來的），與其手動 mkdir、vim 一個一個堆，不如用 lua／lisp 一類語言把整套資料夾佈局生成出來；那個生成就是「編譯」，library 就是做這件事的。（[ideas § 12](../../../thinking/2026-10/19/ideas/README.md)）
- **C-48** JSON 格式族：沿用 inst 單子族、loop／fsm 設定族，靠加 key 與任意 value 擴充（只處理認得的 key），除非必要不新增格式。兩個通則：**私有 key**——各功能可以在同一份 JSON 放只有自己看得懂的 key，藉此共享同一份格式，前提是 key 不重疊（共用同一份檔的私有 key 真的撞名了才加功能前綴，例 `agent_`；各程式的說明列出自己認得的 key）；**不認得的 key 一律忽略、不報錯**，不分開頭是不是 `_`（10-23 使用者「不認得的key就是忽略」）〔使用者「_開頭=附註這個概念刪掉」（[thinking](../../../thinking/2026-10/23/naming.md)）：`_` 開頭的 key 是普通 key，沒有附註或 `_notes` 慣例；入口預設名 `_entry` 只是入口的名字；`.env` key 是為了跟資料夾的 `.env` 檔對上（C-51），檔名照 dotenv 生態〕；**值的雙形**——一個值除了字面純值，也可以寫成物件（展開形），像 Lisp 的 `3` 與 `(+ 1 2)`（例：`priority` 寫 `"low"` 或 `{"val", "deadline"}`；展開形的原值固定在 `val`，C-55），實作麻煩就權衡，太麻煩的地方可以不支援物件形。指示詞是這招的一種用法，有 `$env` 與 `$ref` 兩個，修飾詞是 `$path`、`$prefix`（N-45）：`{"$env": 名, "$path": 子路徑}` 換成該環境變數底下的路徑，讀的是執行當下的環境、像 shell 的 `$HOME`，是正式機制（例 `{"$env": "AOS_STACK", "$path": "plan"}`）；單子本來就能內嵌，不必拆檔；`$ref` 指位置只寫 `檔#/指標`（使用者「把$at刪掉，就都只認#/。」），也可以寫成陣列＝幾份照順序合成一份（都是物件合 key、同名後面的蓋前面的；都是陣列接起來；混在一起＝解不開），例 `{"$ref": ["a.json", "b.json#/c/d"]}`，原話與細則見 N-45；argv 陣列也能放指示詞。aos 讀的 JSON 都解（使用者選「aos 讀的 JSON 全部支援」）——規範是 aos 自己的程式一律支援，別人的程式不一定支援是事實、不是規範；每支程式只解自己讀的格，見 N-45。（10-15，[原文](../../../thinking/2026-10/15/json-families.md)；10-16 夜使用者：「可以用$env啊」→ 頂層給兩案，選 A：「A」；[CONVENTION P-31](../../CONVENTION.md)、[N-45](../../NORMS/06-基礎設施-命令列與指示詞.md)、[ideas 10-20](../../../thinking/2026-10/20/ideas.md) D1、D2、D8） **11-03 加註**（使用者 11-03「1. 當沒看到。」，[thinking 11-03 procs](../../../thinking/2026-11/03/procs/README.md) § 4）：程式改名後的舊 key 也是不認得的 key，一樣忽略、不報錯、不過渡（例 daemon 的 `loops`、`execs`、`loops_ctl` 改名 `procs` 一系之後）。 **11-04 例**（aos-post 改版，使用者 11-03 晚「aos-post這塊都按照建議。」，[thinking 11-03 aos-post](../../../thinking/2026-11/03/aos-post/README.md) 決定 4）：aos-post 信封拿掉的 `kind`——舊信帶著也當不認得的 key 忽略。 **11-06 註**（使用者 11-05 晚，[thinking 11-05 json-argv 07](../../../thinking/2026-11/05/json-argv/07-使用者回覆-11-05晚.md)）：函數的 stdin JSON 同此——「我第一時間想到的是c++的std::bind，面對一個已經bind到剩下兩個參數的函數，我們塞給他四個參數，他也只能吃其中兩個，剩下兩個忽略。是的，不報錯，因爲json的格式自由，而我們只吃json裏面我們想吃的。」給人打的旗標不在此列：不認得的旗標仍是 `FlagUnknown`（P-44，打錯要知道）。
