## 布局成長（10-15 使用者說，[原文](../../../thinking/2026-10/15/layout-growth.md)）

- **C-55** 布局成長：資料夾／檔案與 JSON 物件有同像性（C-51），所以**長大的規則同一套**。檔案那邊照 [wf/STRUCTURE.md](../../../../wf/STRUCTURE.md)（唯一出處）：一個檔內容太大、或一個檔扛不了那麼多職責，就變成資料夾，原檔變成入口（index＋readme），資料夾裡再照既有路徑長（index、readme 各自獨立出來）。JSON 那邊照同一套：一個純值不夠用（例 `priority: 3`），就長成物件（`priority: {"val": 1, "type": "normal task", "timeout": 0}`）——key 不變，原本那個純值放進物件裡固定的一格，其他屬性當同層的 key，物件裡每個值再照同一套長；只剩原值那一格就縮回純值。這就是 C-48「值的雙形」的成長方向，讀的人兩形都收（純值＝只給了原值那一格）。**原值那一格推薦叫 `val`**（ctl 的 `paused`／`stopped`（N-06）都是；aos-llm-kernel 的 `priority` 展開形用 `level`，C-48、11-07 使用者裁定；程式讀值一律先收成物件再看自己認得的 key；10-15 使用者「都按照推薦」，選 A）**`val` 只用在這裡**（值長成物件時放原值）；「要跑什麼」是**具名欄位**、不是某個值的展開形，所以不叫 `val`，全體系一律叫 **`exec`**（loop.json、daemon.json 與子項、daemon 寫進小格的 loop.json、fsm 的每一格）——**`exec`＝交給 aos-exec 跑的目標**（字串或 `[目標, 參數...]`），跟執行器 `aos-exec` 同字同義；aos-exec 進資料夾後找的入口另叫 `_entry`（C-54 R11），兩者不混（使用者選「exec，loop／daemon 的 run 也一起改 exec」，[thinking](../../../thinking/2026-10/23/naming.md)）。兩邊怎麼對見 [thinking 布局成長](../../../thinking/2026-10/15/layout-growth.md)。**函數**（aos-exec 跑得動的東西）也照這套長，分六級，見 [函數成長](05-續-C-55-函數成長.md)。

## 檔案權限（10-16 使用者定）

出處：[thinking 10-16 結束碼與權限](../../../thinking/2026-10/16/exitcode-perm.md)（C-63 作廢，見[條號表](../附錄3-條號表.md)）。

- **C-64** **用檔案（而不是程式之間的管道）的理由之一，是能借 Linux 的檔案讀寫權限做事**：例如讓 kernel 成為某個 daemon 的 ctl／清單唯一能寫的人——多人同時寫同一份會互相蓋掉的問題，靠權限讓它只有一個寫的人來解決。權限是 Linux 那邊的事，歸 daemon 那層（接 C-04）。（使用者 10-16：「之所以要用檔案，就是因為可以透過linux的檔案讀寫權限機制，來做一些神奇的事情。像是讓kernel成為某daemon的ctl/清單的唯一可讀寫者。」）**份額**（使用者 11-05 午「會想要限制特定aos proc所占用的資源。以及daemon/kernel自己本身被限制占用資源，並且會分配份額給proc」「讓daemon偷偷給底下的proc包s6」，[feat-proto 05](../../../thinking/2026-11/05/feat-proto/05-資源份額.md)）：**份額＝daemon 表那列的 `limits`**（`mem_mb`／`cpu_s`／`procs`／`file_mb`／`files`／`user`，同 aos-sandbox 的 key），daemon 在子行程裡 `setrlimit`／`setuid`、proc 不知道——同樣是借 Linux 現成的機制；daemon 自己被限＝起它的人包（rlimit 繼承）。`aos-daemon-ctl add --limits` 帶、aos-agent 照宣告送，llm kernel 另有包與寄件人額度（[aos-daemon docs/09](../../../impls/aos-daemon/docs/09-份額.md)）。 **遠期、沒排**（使用者 11-12 晚「一個帳號一整棵樹。然後這個root daemon本身也可以作爲agent，畢竟他有body」「以今晚爲準。」，[linux-user](../../../thinking/2026-11/12/linux-user.md#續念頭-droot-user-的-root-daemon)）：以後一個 Linux 帳號一整棵樹，用帳號設權限（誰能寫誰的 ctl 信箱、誰能讀誰的 stack）；跟 aos-sandbox 的 `s6-setuidgid`、上面 `limits` 的 `user` 同一條線。這次不做、不預留 key。
  **沙箱**（使用者 10-24「linux權限和沙箱可以開始做了，藉助s6那套」「都按建議做」；同晚「像這種存取控制，我們就是純靠linux，至於cpu/網路/記憶體限制，s6也可以幫忙，或者也可以用其他東西如docker/bwrap之類」；10-30「linux是托底，我們可以充分利用linux的檔案存取權限機制，但我們也可以實作自己的機制」；[thinking 10-24 sandbox](../../../thinking/2026-10/24/sandbox/README.md)）：存取控制托底靠 Linux——帳號、群組、權限位、看得到哪些路徑；CPU、記憶體、網路的上限交給現成工具；aos 可以在上面再加自己的機制。把一個函數關起來跑分兩層：**身分**（`s6-setuidgid` 換帳號，要 root、要先有帳號）＋**命名空間**（bwrap，免 root），上限用 `s6-softlimit`。做成一支不常駐的 [`aos-sandbox 設定 prog...`](../../../cmd/aos-sandbox/README.md)：排好這條鏈就 exec 走，結束碼與串流都是 prog 的。**誰關＝呼叫方**：寫在叫的那一方的 argv 最前面（函數自己關自己沒有意義），aos-exec 一行不改，也不經 daemon。**強制只在 argv**（寫了 `aos-sandbox` 才被關）；函數可以在 `_metainfo` 寫一格 `sandbox`（同一套設定 key）宣告自己需要什麼，呼叫方要照它關就明寫 `aos-sandbox _metainfo.json#/sandbox …`（[N-69](../../NORMS/10-基礎設施-定義與工作區/11-N-69.md)）。設定是白名單：沒列到的路徑看不到、`net` 預設 false、環境只帶一份預設清單、金鑰不帶。能不能用 llm kernel＝看不看得到它的信箱（`rw` 綁 `$AOS_LLM_KERNEL/requests`），不另設開關；kernel 只跑自己 `kernel.json` 的 endpoint、金鑰在它那邊，沙箱裡的 agent 看不到。格裡接 aos-sandbox 不逃出行程群組（N-41）。管 agent 的工具（`subagent`、`agents_ctl`、`self_tools`）在沙箱裡照樣能用：設定裡 `rw` 綁 daemon（`$AOS_DAEMON`），程式不改（使用者 11-06 選「現在正式支援 (Recommended)」，[no-pid 13](../../../thinking/2026-11/05/no-pid/13-P5實作結果.md#使用者裁定11-06)；範例 [subagent-boxed](../../../cmd/aos-sandbox/examples/subagent-boxed/sandbox.json)）；遠期等判官成為權限閘門，沙箱裡只留一個信箱、寫子 stack 那幾步改成寄信。上面 daemon 給 proc 的份額 `limits` 用同一套 key，是另一條路（daemon 在子行程裡設）。呼叫方自己關、不經 daemon，跟 C-04 不算衝突：C-04 是推薦（11-12 使用者：aos 自己的程式盡量照它；別人要另搞也可以、風險自擔，[small-rulings](../../../thinking/2026-11/12/small-rulings.md#11-12-下午再裁三條agent_def-兩題沙箱與-c-04)。）
