## 命名（10-15 使用者說，[原文](../../../thinking/2026-10/15/naming/README.md)）

- **C-54** 命名：**好懂、快速理解、快速記住**。資料夾布局、程式碼、JSON 格式最好一看就懂七七八八——先排結構，結構與名字本身就是說明；說明只要少量簡介，再直接甩出 pseudo code／JSON／資料夾。
  - **一次記住、全體系通用**：同一個詞在 aos 各處同義（`inst`、`ctl`、`state`…）。縮寫只用大家本來就知道的，而且**新縮寫要先進 [aos 認可縮寫表](../abbr.json) 才能用**（10-15 使用者「要，縮寫表照推薦做」；表的欄位：縮寫、全稱、意思、例子）。
  - **難懂才加前後綴**（`ctl_dir`），表特性（`dir`、`path`、單位 `ms`）或子類時用；不用匈牙利命名法那種型別前綴。**可搜尋的標籤／主題放前面、由大到小**（`path_insert`、`path_query_sql`），排序、搜尋時同類排在一起。
  - **資料夾、檔名、JSON key：全小寫加底線**；**對外的指令名＝同一個名字把底線換成連字號**（`node_path` ⇄ `node-path`）；環境變數全大寫加底線（`AOS_ENTRY`）（10-15 使用者「指令名就是底線換連字號。」）。
  - **程式碼照該語言規範**（Python 照 PEP8），並跟檔名固定對上：程式的 `NodePath` ⇄ 檔名 `node_path`；程式裡可混大小寫表層級（`NodePath_SQL_Query`）。
  - **靠資料夾布局少用底線，複數資料夾裝同類**：裝同一類多個東西的資料夾用複數名（`insts/`、`cells/`、`tools/`），裡面的檔名不再重複類別（`insts/a.json`，不寫 `inst_a.json`、`insts/inst_a.json`）。複數一律只加 `s`（縮寫也是：`insts`、`cfgs`、`msgs`），不用不規則變化；本身已是複數或不可數的照原樣（`args`、`data`、`history`）；單一檔案用單數（`brain.json`、`ret.json`）（10-15 使用者「對了，還有複數形式，比如./inst-a.json, ./insts/a.json」，細節「都按照推薦」）。
  - **錯誤若帶代號，照 CamelCase、主詞在前**（錯是 stderr 一行 `程式名: error: 代號 原因`，代號＝`error: ` 後第一個字，N-43、P-21）：`ArgumentsBad`、`FlagUnknown`、`ApiKeyMissing`、`StateBad`，同主題的錯排在一起。
    - **結尾是推薦**（使用者 11-11：「Hmmm，錯誤代號本身就千變萬化。concept內應該只是列出幾項基礎的、很通用大眾的，跟大家說類似的就盡量遵循這個。但其他的也可以自己隨意定。就是說偏向於推薦啦。」，[knowledge-fix 03](../../../thinking/2026-11/11/knowledge-fix/03-六題裁定與施工.md)）：下面幾個基礎、通用的結尾，遇到類似的情況盡量照用；其他情況可以自己定（`DepthExceeded`、`SubagentQueued`、`ChildrenExist` 照用、不改名）。
      - 「沒有某物」`…Missing`、「不認得」`…Unknown`、「壞了／不合」`…Bad`（10-15 晚使用者「都按照推薦」，盤點 P7）。
      - 「動作做不成」動作＋`…Failed`（`LaunchFailed`、`MkdirFailed`、`WriteFailed`、`OpenFailed`；可以再試一次）；`Internal`＝照理不會發生的錯（10-23 使用者逐條認可）。
      - `…Exists`＝已經有同名的（aos-post 自己給的信件名稱撞名＝`LetterExists`；跟既有的 `InstanceExists`、`FileExists`、`ToolExists` 一致；11-03 晚使用者「aos-post這塊都按照建議。」，[aos-post 原話與衝突 1](../../../thinking/2026-11/03/aos-post/01-使用者原文-11-03-晚-看完頂層整理.md)）。
      - `…Rejected`＝守門的說不（判官、daemon 不收），**這是決定、別重試**——要嘛改請求（拿掉東西、要少一點）、要嘛回報；跟 `…Failed` 分開。既有的 `AddRejected`、`CtlRejected` 照用、名字不改（使用者 11-06 選項框選「C-54 補第六種 (Recommended)」，[arch-refactor 06](../../../thinking/2026-11/05/arch-refactor/06-工作量與排程.md) S9 列；選項逐字原話的出處待核）。
    - **基礎層共用的代號**（10-23 使用者「都先幫我統合」，[thinking](../../../thinking/2026-10/23/naming.md)）：用法不對 `ArgumentsBad`、不認得的旗標 `FlagUnknown`；設定檔不在或 `#/` 指不到 `CfgMissing`，讀不了、JSON 語法錯、欄位型別錯、互相衝突 `CfgBad`；fsm 的 state 讀不了 `StateBad`；工作區不在 `WsMissing`；`.env` 讀不了或壞 `DotenvBad`；要跑的指令找不到 `CommandMissing`、不能執行 `CommandBad`；直接叫庫跑單子檔時，檔本身不在 `EntryMissing`、讀不了或語法錯 `EntryBad`；aos-clock 也帶代號（`ArgumentsBad`、`FlagUnknown`、`ClockBad`、`WriteFailed`）。
  - **例外**（10-15 盤點後定，使用者「其他直接改」）：入口檔照 Unix 老慣例全大寫（`README.md`、`INDEX.md`、`CONCEPTS.md`、`NORMS.md`，`ls` 時排前面）；`bin/` 是 Unix 慣例名、單數照留；工具自己的慣例照工具（pytest 的 `tests/test_*.py`）；外部 API 的參數名照原名、不進縮寫表（`num_ctx`、`keep_alive`）；一個檔裝很多筆的串流／日誌檔可以用複數（`steps.jsonl`）。`last_`／`max_` 這種修飾詞在前不算違反「主題在前」〔計數的 `counter_` 同理，使用者 10-25「計數這塊，幫我改成counter_*」〕——`last_` 本身就是一個可搜尋的群組（state 窗裡「上一次的」排在一起），`max_` 是大家都知道的慣例。
  - **副檔名、時間、計數、上限**（[thinking](../../../thinking/2026-10/23/naming.md)；使用者 10-23 逐條選過，副檔名選「純文字也帶 .txt」）：JSON 帶 `.json`、JSON Lines 帶 `.jsonl`、純文字帶 `.txt`（fsm 的 `stage.txt`、`stderr.txt`、`current.txt`；入口檔 `_entry` 是程式不是資料、`.env` 照 dotenv 生態，都不帶）；時間點一律 `<發生了什麼>_at`（`recorded_at`、`started_at`、`sent_at`、`served_at`），不用單獨的 `at`（使用者 10-25「state.json中，runs改counter，at改成recorded_at」，回頂層兩題「都好」，頂層代定、可翻案），值一律 ISO 8601 UTC 到毫秒，時長與其他單位照後綴（`_ms`、`_cycles`）；計數一律 `counter_<被數的東西>`（`counter_runs`，不放 state.json、寫成旗標後面的 `counter_runs.txt`〔N-09〕；使用者 10-25「計數這塊，幫我改成counter_*」），一串東西本身（陣列）不算計數、照「複數一律只加 s」；上限叫 `max` 或前綴 `max_`（例 llm-kernel 的 `max_calls`／`max_tokens`）；細則見 [C-54 命名方法 R6](C-54-命名方法.md)。daemon 管的子項都是 proc，名單叫 `procs`（不叫 `children`），照「複數一律只加 s」（使用者 11-03「連名單也合一」，[thinking 11-03 procs](../../../thinking/2026-11/03/procs/README.md)）。
  - **命名方法（10-23 晚，[thinking](../../../thinking/2026-10/23/naming-method/README.md)）**：使用者的取名步驟（「關於命名規則這塊，我想嘗試一些新的概念，在現有的原則與規則上添加一些能讓人更快看懂的...算小技巧吧」）結合 Unix／Linux 老慣例（使用者「寫進去吧」）。取名照 R1～R14 走（R13 程式名＝`aos-<領域>-<功能>`、R14 信箱取名；細則逐條在 [C-54 命名方法](C-54-命名方法.md)）：**先寫一行 NAME `名字 - 一句話`**（照 man page 第一行，每支程式的 README 開頭都有）→ 每格一句白話 → 先查固定格（`val`、`max`、`kind`、`code`、`signal`、`seq`、`phase`、`pid`）→ 主題字從主詞來 → 修飾成分照表貼 → 排字序 → 名字長度跟要被認多遠成正比（環境變數＞程式名＞檔名與 key＞區域變數）→ 簡化到同檔同主題仍唯一（撞名就換一個角度，用白話重新描述它的功能與特性再取名；使用者 10-23 晚「像這種命名重複的，可以用另一個角度用白話描述其功能與特性」）→ 最後回頭清、每個名字都推得回那一句。細則裡的規則：時間點一律 `<發生了什麼>_at`（ISO 8601 UTC 到毫秒），同一個時間點用別的單位記就把單位接在後面（`started_at_ticks`，使用者原例「started_at_ticks」）；計數不用 `nr_`（使用者「nr_這東西還是建議不要用，現在這東西不太常見了」），一律 `counter_<被數的東西>`（使用者「計數這塊，幫我改成counter_*」）；「第幾個」的 index 不進縮寫表，真要用寫 `idx`；縮寫進表的門檻是一眼還原得了、表上已有的不追溯（`AOS_CF`／`AOS_CD`／`AOS_CO` 照留）；**`_` 開頭的檔＝aos 認的固定檔**（入口 `_entry`、資料 `_tooldef.json`…，見 [R11](C-54-命名方法.md)），不是私有；loop 這一系（含 daemon）控制自身的 ctl 是一道指令（`cmd`＋動詞）；daemon 管別人的 `procs_ctl.json` 是宣告、key 一律用狀態詞，state 裡有對應的格時用同一個字（頂層代定（使用者「都隨意」），見 [R4](C-54-命名方法.md)）。照規則取的名字：state 窗 `started_at_ticks`、state_flux 窗 `ctl_warning`（主詞是 ctl；`last_` 留給「上一次」；回音欄在 state_flux，N-09）；「上一次的結果」`last_code` 先不加。「要跑什麼」全體系一律叫 `exec`（loop.json、daemon.json 與子項、fsm 的每一格，見 C-55；使用者「fsm.json，現在是用val，幫我改成exec」，一詞一義、使用者選「exec，loop／daemon 的 run 也一起改 exec」，[原話 naming-method 02](../../../thinking/2026-10/23/naming-method/02-照規則改的名字.md)）；條文與訊息裡說「次」，不說「拍」（使用者：「"拍"，其實我們人類不常用這個來說，我們都是說"次"。」）。
