## 命名（10-15 使用者說，[原文](../../../thinking/2026-10/15/naming/README.md)）

- **C-54** 命名：**好懂、快速理解、快速記住**。資料夾布局、程式碼、JSON 格式最好一看就懂七七八八——先排結構，結構與名字本身就是說明；說明只要少量簡介，再直接甩出 pseudo code／JSON／資料夾。
  - **一次記住、全體系通用**：同一個詞在 aos 各處同義（`inst`、`ctl`、`state`…）。縮寫只用大家本來就知道的，而且**新縮寫要先進 [aos 認可縮寫表](../abbr.json) 才能用**（10-15 使用者「要，縮寫表照推薦做」；表的欄位：縮寫、全稱、意思、例子）。
  - **難懂才加前後綴**（`ctl_dir`），表特性（`dir`、`path`、單位 `ms`）或子類時用；不用匈牙利命名法那種型別前綴。**可搜尋的標籤／主題放前面、由大到小**（`path_insert`、`path_query_sql`），排序、搜尋時同類排在一起。
  - **資料夾、檔名、JSON key：全小寫加底線**；**對外的指令名＝同一個名字把底線換成連字號**（`node_path` ⇄ `node-path`）；環境變數全大寫加底線（`AOS_ENTRY`）（10-15 使用者「指令名就是底線換連字號。」）。
  - **程式碼照該語言規範**（Python 照 PEP8），並跟檔名固定對上：程式的 `NodePath` ⇄ 檔名 `node_path`；程式裡可混大小寫表層級（`NodePath_SQL_Query`）。
  - **靠資料夾布局少用底線，複數資料夾裝同類**：裝同一類多個東西的資料夾用複數名（`insts/`、`cells/`、`tools/`），裡面的檔名不再重複類別（`insts/a.json`，不寫 `inst_a.json`、`insts/inst_a.json`）。複數一律只加 `s`（縮寫也是：`insts`、`cfgs`、`msgs`），不用不規則變化；本身已是複數或不可數的照原樣（`args`、`data`、`history`）；單一檔案用單數（`brain.json`、`ret.json`）（10-15 使用者「對了，還有複數形式，比如./inst-a.json, ./insts/a.json」，細節「都按照推薦」）。
  - **錯誤若帶代號，照 CamelCase、主詞在前**（錯是 stderr 一行「程式名: 代號 原因」〔11-05 起 `程式名: error: 代號 原因`，代號＝`error: ` 後第一個字，N-43〕，P-21；代號一律「主詞＋`…Missing`／`…Unknown`／`…Bad`／`…Failed`」四種結尾，另加 `Internal`〔既有 impls 代號使用者先裁定照舊沿用（「都按照建議做。」），同日「都先幫我統合」翻案（[thinking](../../../thinking/2026-10/23/naming.md)），舊名 → 現名：`Usage` → `ArgumentsBad`（不認得的旗標 `FlagUnknown`）、`FieldType`／`JsonSyntax`／`Conflict` → `CfgBad`、設定檔讀不到的 `ReadFailed` → `CfgMissing`（不在）／`CfgBad`（讀不了）、設定檔 `#/` 指不到 → `CfgMissing`、fsm 的 state 讀不了 → `StateBad`、`WorkspaceMissing` → `WsMissing`、`EnvBad`／`EnvReadFailed` → `DotenvBad`、`CommandNotFound` → `CommandMissing`、`CommandNotExecutable` → `CommandBad`、直接叫庫跑單子檔時檔本身的 `ReadFailed`／`JsonSyntax` → `EntryMissing`／`EntryBad`；aos-tick 也帶代號（`ArgumentsBad`、`FlagUnknown`、`ClockBad`、`WriteFailed`）〕）：`ArgumentsBad`、`FlagUnknown`、`ApiKeyMissing`、`StateBad`，同主題的錯排在一起；「沒有某物」一律 `…Missing`、「不認得」一律 `…Unknown`、「壞了／不合」一律 `…Bad`（10-15 晚使用者「都按照推薦」，盤點 P7）；「動作做不成」一律動作＋`…Failed`（`LaunchFailed`、`MkdirFailed`、`WriteFailed`、`OpenFailed`），`Internal`＝照理不會發生的錯（10-23 使用者逐條認可）。 **11-04 加註**（aos-post 改版衝突 1，使用者 11-03 晚「aos-post這塊都按照建議。」，[thinking 11-03 aos-post](../../../thinking/2026-11/03/aos-post/README.md)）：代號結尾多第五種 **`…Exists`＝已經有同名的**（aos-post 自己給的信件名稱撞名＝`LetterExists`；跟 extras 既有的 `InstanceExists`、`AgentExists`、`FileExists`、`ToolExists`、`CellExists` 一致）；上面「四種結尾」照五種讀。 **11-06 加註**（大重構 S9 撞到 aos-agent 的 `AddRejected`／`CtlRejected` 不在五種裡、知識庫卻教腦 `…Rejected`；使用者 11-06 選項框選「C-54 補第六種 (Recommended)」，[arch-refactor 06](../../../thinking/2026-11/05/arch-refactor/06-工作量與排程.md) S9 列）：代號結尾多第六種 **`…Rejected`＝守門的說不**（判官、daemon 不收），**這是決定、別重試**——要嘛改請求（拿掉東西、要少一點）、要嘛回報；跟 `…Failed`（動作做不成、可以再試一次）分開。既有的 `AddRejected`、`CtlRejected` 照用、名字不改。上面「四種結尾」照六種讀（11-04 那句「照五種讀」原句留著）。
  - **例外**（10-15 盤點後定，使用者「其他直接改」）：入口檔照 Unix 老慣例全大寫（`README.md`、`INDEX.md`、`CONCEPTS.md`、`NORMS.md`，`ls` 時排前面）；`bin/` 是 Unix 慣例名、單數照留；工具自己的慣例照工具（pytest 的 `tests/test_*.py`）；外部 API 的參數名照原名、不進縮寫表（`num_ctx`、`keep_alive`）；一個檔裝很多筆的串流／日誌檔可以用複數（`steps.jsonl`）。proto8 的 `demo/` 照留單數（下一個 proto 起用 `demos/`；10-15 晚使用者「都按照推薦」，盤點 P5）。`last_`／`max_` 這種修飾詞在前不算違反「主題在前」〔計數的 `counter_` 同理，使用者 10-25「計數這塊，幫我改成counter_*」〕——`last_` 本身就是一個可搜尋的群組（state 窗裡「上一次的」排在一起），`max_` 是大家都知道的慣例。
  - **副檔名、時間、計數、上限**（[thinking](../../../thinking/2026-10/23/naming.md)；使用者 10-23 逐條選過，副檔名選「純文字也帶 .txt」）：JSON 帶 `.json`、JSON Lines 帶 `.jsonl`、純文字帶 `.txt`（`state.txt`〔11-04 加註：fsm 的這個檔改名 `stage.txt`（使用者題 10「fsm改名，嘗試用同義詞」，[four-elements 07](../../../thinking/2026-11/04/four-elements/07-實作步驟.md) 步 3）〕、`stderr.txt`、`current.txt`；入口檔 `_entry` 是程式不是資料、`.env` 照 dotenv 生態，都不帶）；時間點一律 `<發生了什麼>_at`（`recorded_at`、`started_at`、`sent_at`、`served_at`），不用單獨的 `at`（使用者 10-25「state.json中，runs改counter，at改成recorded_at」，回頂層兩題「都好」，頂層代定、可翻案），值一律 ISO 8601 UTC 到毫秒，時長與其他單位照後綴（`_ms`、`_ticks`）；計數一律 `counter_<被數的東西>`（`counter_runs`，11-09 起不放 state.json、寫成旗標後面的 `counter_runs.txt`〔N-09 的 11-09 補〕；使用者 10-25「計數這塊，幫我改成counter_*」），一串東西本身（陣列）不算計數、照「複數一律只加 s」；上限叫 `max` 或前綴 `max_`（例 llm-kernel 的 `max_calls`／`max_tokens`）；細則見 [C-54 命名方法 R6](C-54-命名方法.md)。daemon 管的 loop 叫 `loops`（不叫 `children`），也是照「複數一律只加 s」。〔11-03 統稱 `procs`：daemon 管的子項不論 loop 型、exec 型都是 proc，名單合一叫 `procs`（使用者 11-03「連名單也合一」，[thinking 11-03 procs](../../../thinking/2026-11/03/procs/README.md)）〕
  - **命名方法（10-23 晚，[thinking](../../../thinking/2026-10/23/naming-method/README.md)）**：使用者提了一套取名的步驟（「關於命名規則這塊，我想嘗試一些新的概念，在現有的原則與規則上添加一些能讓人更快看懂的...算小技巧吧」），「先試試看，不要急着寫進去」；問了「這種命名規則，那些unix年代的老人，或是linux的開發者，有慣例嗎」，查過老慣例合成 12 條，八題選完後「寫進去吧」。取名照 R1～R13 走（R13 程式名＝`aos-<領域>-<功能>` 是 10-30 夜加的；細則逐條在 [C-54 命名方法](C-54-命名方法.md)）：**先寫一行 NAME `名字 - 一句話`**（照 man page 第一行，每支程式的 README 開頭都有）→ 每格一句白話 → 先查固定格（`val`、`max`、`kind`、`code`、`signal`、`seq`、`phase`、`pid`）→ 主題字從主詞來 → 修飾成分照表貼 → 排字序 → 名字長度跟要被認多遠成正比（環境變數＞程式名＞檔名與 key＞區域變數）→ 簡化到同檔同主題仍唯一（撞名就換一個角度，用白話重新描述它的功能與特性再取名；使用者 10-23 晚「像這種命名重複的，可以用另一個角度用白話描述其功能與特性」）→ 最後回頭清、每個名字都推得回那一句。細則裡的規則：時間點一律 `<發生了什麼>_at`（ISO 8601 UTC 到毫秒），同一個時間點用別的單位記就把單位接在後面（`started_at_ticks`，使用者原例「started_at_ticks」）；計數不用 `nr_`（使用者「nr_這東西還是建議不要用，現在這東西不太常見了」），一律 `counter_<被數的東西>`（使用者「計數這塊，幫我改成counter_*」）；「第幾個」的 index 不進縮寫表，真要用寫 `idx`；縮寫進表的門檻是一眼還原得了、表上已有的不追溯（`AOS_CF`／`AOS_CD`／`AOS_CO` 照留）；**`_` 開頭的檔＝入口**（`_entry`），不是私有；ctl 的 key 是宣告狀態、一律用狀態詞，state 裡有對應的格時用同一個字（`paused`、`stopped`；頂層代定（使用者「都隨意」），見 [R4](C-54-命名方法.md)）。照規則取的名字：state 窗 `started_at_ticks`、ctl `stopped`、state 窗 `ctl_warning`（主詞是 ctl；`last_` 留給「上一次」）；「上一次的結果」`last_code` 先不加。「要跑什麼」全體系一律叫 `exec`（loop.json、daemon.json 與子項、fsm 的每一格，見 C-55；使用者：「改，beats改runs，然後val寫要跑啥，通常不會用val，應該用run。」，衝突時選「只有 loop、daemon 用 run」；深夜使用者「fsm.json，現在是用val，幫我改成exec」，頂層指出跟 loop／daemon 的 `run` 不同名會違反一詞一義，使用者選「exec，loop／daemon 的 run 也一起改 exec」）；條文與訊息裡說「次」，不說「拍」（使用者：「"拍"，其實我們人類不常用這個來說，我們都是說"次"。」）。
