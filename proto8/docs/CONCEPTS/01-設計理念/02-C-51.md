- **C-51** 資料夾與 JSON 可以互通：資料夾＝object、名字＝key，一份 JSON 本身也是一個小檔案系統，inst 體系以外的格式也能這樣套；「但是我會覺得，建議不要濫用，因為雖然可以互通，但畢竟在細節上有差異」——所以互通只當工具與思考方式，**不進規範**。JSON 那半的入口怎麼找：C-72。JSON schema 在這套大量用 JSON 的體系裡有更多用處（當型別、interface、簽名，也能描述資料夾的形狀）；驗證選用，執行期先只驗 LLM 回話。隱藏檔一律略過（一個例外：aos-exec 讀入口資料夾裡的 `.env` 設環境變數，[N-59](../../NORMS/10-基礎設施-定義與工作區/03-N-59.md) 第 4 件、[ideas 10-21 § 4](../../../thinking/2026-10/21/ideas/02-4-aos-exec-支援-env.md#4-aos-exec-支援-env10-21)）；入口的位置由環境變數 `AOS_ENTRY` 指（預設 `_entry`，C-68）。這也是使用者 10-19 說的「純粹把資料夾作為 lisp 的 list 或 lua 的 table」的根（[ideas § 1](../../../thinking/2026-10/19/ideas/README.md)；比喻用 table，C-71）。（10-15 收工後意見 5～7，[thinking 意見 5～7](../../../thinking/2026-10/15/opinions-5-7.md)）
  - **10-31 加註：固定名字可以、但限縮範圍**（使用者 10-31「固定，是可以的，但建議線限縮範圍，比如只有一個檔案固定，剩下的，則都由這個檔案指定。」，拍板「要寫入，但這條我後續還會有一些想法要追究。」，[thinking 10-30 eca § 10-31 原則](../../../thinking/2026-10/30/eca/10-10-31-使用者原文-turn-的定義檔只認固.md#10-31-使用者原則固定名字可以但限縮範圍判準)）：檔名當 key 固定可以，但固定的範圍要限縮——理想是只有一個檔案固定當入口、其餘由它指定；要更靈活就用環境變數或 argv 指定；參與者少又穩定時固定就好，變化多時再斟酌（例：`_entry`＋`AOS_ENTRY`〔C-68、C-72〕；eca 的 `cli.json`、`eca.json` 現階段維持固定）。**使用者尚有後續想法待追究（10-31），本加註可再補**。註冊檔與固定名字可以共存（11-01 使用者「2.兩者可以共存的。」，[thinking 10-31 parts-round § 決定（11-01 使用者）](../../../thinking/2026-10/31/parts-round/README.md#決定11-01-使用者)）：agent 資料夾的 `parts.json` 有寫的優先、沒寫的看固定名字；本加註不當成要去掉固定名字的理由。 **11-04 加註**（aos-agent，使用者 11-04 晚「一個入口小程式。並且要是aos資料夾函數。可以設計宣告介面。」「程式語言中定義class/struct的後，也會宣稱說自己繼承於/遵守於某些介面，比如golang interface之類。」，[thinking 11-04 aos-agent 03](../../../thinking/2026-11/04/aos-agent/03-種類與契約.md)）：上面的例子多一個 `interfaces.json`——資料夾宣告自己遵守哪些介面的檔（`{"aos-agent": {…}}`、子介面資料夾裡 `{"aos-agent/screen": {}}`），全體系第二個固定名，其餘檔名由它指定（`screen`、`tools`、`llm` 的值）；`eca.json` 拿掉（11-04 起不寫、沒人讀）。

## 分層（10-22 使用者定）

- **C-74** **分層：基礎層（核心 aos-exec＋loop、daemon）→ 標準庫（fsm、tasks、其他）→ agent／kernel**。使用者 10-22：「我先定個方向：aos exec這是基礎，在基礎上弄loop/daemon/fsm等標準庫(其中loop/daemon算是介於基礎與標準庫之間，或者說aos exec是核心，而loop/daemon/fsm是基礎，其他才是標準庫)，再來才是agent/kernel」；接著改：「loop等一下，我們先把那個基礎、核心的定義弄好。我會覺得，aos-exec是core，是基礎中的基礎，所以可以叫他"基礎層中的核心"，然後fsm還是歸進標準庫好了」；頂層整理成下表、並提三條撞名的處理後：「對，分層照這樣記。剩下三條撞名照你的建議處理。」（[ideas 10-22 § 4](../../../thinking/2026-10/22/ideas/02-3-env-基礎子集與---dotenv-ove.md#4-分層方向10-22)）

| 層 | 有什麼 | 實作（C++ `proto8/impls`，aos-tick 例外） |
|---|---|---|
| 最上層 | agent、kernel | agent-bob、agent-ann（11-04 前在 [demo](../../../demo/README.md)，demo 刪了搬去當測試的固定資料；agent-nia 11-03 刪了；11-02 晚 agent-dan 刪除，原本列它）；走 queue 的是 [demo/agent-fsm](../../../demo/README.md#agent-fsm)（11-04 加）；kernel 現無實作（**11-05 註**：[aos-llm-kernel](../../../impls/aos-llm-kernel/README.md) 11-05 起改成請 daemon 掛問腦 proc，是照 C-47 加嚴後定義算的 kernel 實作；判官範本 `lib/base/judge`〔kernel-daemon 模式 1／2 的形狀〕，[thinking 11-05 kernel-daemon](../../../thinking/2026-11/05/kernel-daemon/README.md)） |
| 標準庫 | fsm、tasks、其他 | [`aos-fsm`](../../../impls/aos-fsm/README.md)；tasks 現無實作 |
| 基礎層 | **核心**＝aos-exec（含 inst 庫、指示詞、旗標）；loop、daemon | 核心：[`aos-exec`](../../../impls/aos-exec/README.md)（[inst](../../../impls/inst/README.md) 是 C lib、單子的 JSON 在 aos-exec 的 `src/inst/`；指示詞 [aos-directive](../../../impls/aos-directive/README.md)；旗標在 [aos-util](../../../impls/aos-util/README.md)）；[`aos-loop`](../../../impls/aos-loop/README.md)（含 ctl／state 窗）、[`aos-daemon`](../../../impls/aos-daemon/README.md)（繼承 aos-loop 的 `Loop`） |
| 不歸層 | aos-tick（擱置中） | `aos-tick`（[proto8/bin](../../../bin/README.md)，Python） |

  分層講的是**誰依賴誰**（上層用下層寫成）；C-03（本檔開頭）講的是**誰排程誰**，兩條軸不衝突（見 C-03 的註）。用詞（三條撞名照頂層建議）：分層的「核心」只指 aos-exec；**kernel 不譯作「核心」**，條文與名詞表一律寫 kernel；名詞表大範圍的那一整塊（到「排序程式可由模型生成」為止）叫**系統本體**（新詞頂層代定）；repo 根的 `core/` 是舊一代 C++ 版的「必要模組」資料夾，資料夾名不動、跟這裡的核心無關。實作兩級（N-18）叫**最小實作／完整實作**。「基礎設施」是**主題**（[03](../03-基礎設施.md)、NORMS 03～07、10，照內容分），不是層：inst、loop、daemon、資料夾程式屬基礎層，組合子 tasks、fsm 屬標準庫。這裡的「標準庫」是 aos 的這一層，跟「純標準庫 Python」（只用 Python 自帶的庫）是兩回事。

  **parts 不歸標準庫，是 agent 慣例層的約定**（11-01 使用者裁，原文「1.拆成薄殼...搞不好連薄殼都不用，盡量去做吧。」，[thinking 10-31 parts-round § 決定（11-01 使用者）](../../../thinking/2026-10/31/parts-round/README.md#決定11-01-使用者)；翻掉 10-31「parts 進標準庫、與 fsm 平級」，那句原文留在 [thinking 10-28 agent-round § 10-31 使用者原文](../../../thinking/2026-10/28/agent-round/09-實作時代定.md#10-31-使用者原文parts-的定位)）：parts＝agent 資料夾裡一份 aos-exec 格式的 `parts.json`（名字→路徑的表；C-61 原本寫這張表的那半 11-04 夜已刪、已無實作，見 [P-25 的 11-04 加註](../../CONVENTION/02-題目stack停錯腦/05-P-23～P-26.md)）；每槽 `$env`／`$ref` 是 aos-exec 本來就有的能力（C-72、N-61），不是 parts 多出來的。實作以不需要 `aos-parts` 這支程式為目標，做不到才留最小的殼——11-01 已做到：`aos-parts` 刪了，器官共用 `lib/agent/parts.py` 找格（[05 § 實作計畫](../../../thinking/2026-10/31/parts-round/05-方向題與實作計畫.md#實作計畫)）。**11-03 已刪**：`lib/agent/parts.py` 隨 round 那套用格組起來的 agent 一起刪、沒有現行替代（使用者 11-03 晚「封存這條線，1.該刪的都刪光刪乾淨」，commit cb6b49e0），概念收在 [archive agent-round-concepts § 格怎麼找、怎麼叫](../../../archive/agent-round-concepts/README.md#格怎麼找怎麼叫parts)；本句照 11-01 原字不動。
