## C-47 kernel 的定義（續）

C-47 的本文與前幾點在 [01-C-47](01-C-47.md)。

- **擺法不限**：收請求的擺法有範例（見下面例子），不是只有那幾種，自己寫一個收請求的 proc 也算 kernel。
- **安全的保底是 Linux 本身**（使用者 11-11「我這邊還是一樣的立場：非正規操作的風險由使用者自行承擔、最基礎與通用，同時也是保底的安全機制，就是linux本身，包括使用者、權限啥的。」）：aos 不驗寄件人。人也改用 kernel：人平常用的 `aos-agent ctl` 照 `AOS_KERNEL` 寄；想直接碰 daemon 或更深的 kernel，靠 Linux 權限（使用者 11-11「人這邊也改用kernel，想要存取daemon或更深的kernel？靠linux權限。」）。權限沒設也可以，繞過的風險自己承擔（使用者 11-05「linux權限沒設也可以(因為我知道有些人嫌麻煩，或是還處在demo狀態)，就自行承擔風險。」）。`aos-daemon-ctl` 是指名要碰某台 daemon 的工具：一律直寄那台的 ctl 信箱、不看 `AOS_KERNEL`，有 Linux 權限就能用（使用者選項框「維持直寄，它就是『指名 daemon』的工具」「aos-daemon-ctl 永遠直寄」，[os-impl 08](../../../thinking/2026-11/06/os-impl/08-aos-daemon-ctl永遠直寄實作結果.md)）。
- **已裁定**：① 一般 proc 讀狀態＝kernel 給一個狀態位址（使用者選項框「kernel 給一個狀態位址」）：「狀態在哪」是又一種請求信，不用 symlink（使用者 11-11「然後kernel給狀態位址...希望不是使用symlink，我不希望aos體系硬性依賴symlink，或許可以折衷？寄信問，取得狀態位址這樣。」）；問來的位址記不記，工具自己決定（使用者選項框「工具自己決定」）。② 通用 kernel 框架：一包方便零件、不是概念，框架一份，判官與問腦總機都收進來，`AOS_LLM_KERNEL`、`AOS_KERNEL` 仍是兩個變數（使用者 11-12「問腦總機要收進框架」「kernel先這樣就好，開工等假日。我自己也要思考一下」，[kernel-framework](../../../thinking/2026-11/12/kernel-framework/README.md#已裁問腦總機收進框架)；N-42 (2)）。框架分兩層：最底層是 hook＋判斷，上限這類放在框架之上的通用基礎包（使用者 11-13「就是說我們做的是框架，最底層就是最簡單的hook+判斷。你說的上限這塊，是在框架之上的通用基礎包，所以可以隨意，可以簡單並通用一些。」）。agent 自己也可以當門：hook 把信先留著、agent 表態、站轉寄（使用者 11-13「一個普通的agent隨便弄些hook、json設定啥的，就可以收請求了。請求進來後agent收到通知，他自己判斷要不要過，然後再去轉送」「反正json，不認得的key，只要沒設限制，就能過」，[thinking 11-13 eca-as-kernel](../../../thinking/2026-11/13/eca-as-kernel.md)）。〔現況：框架開工（使用者 11-13「kernel框架現在就可以開工了。只是說我們現在只有eca能用。」）；框架的骨架、掛 proc 那一包（含原判官）、hook 三個時機在 [py/tools/aos/kernel](../../../py/tools/aos/kernel/README.md)，問腦總機在 [py/tools/aos/kernel_llm](../../../py/tools/aos/kernel_llm/README.md)，① 的狀態查詢信也有了（`aos-agent ctl who` 先問再讀，N-63），agent 當門的工具是 `kernel_gate`。（新舊打架，11-17「新的覆蓋舊的」：11-14 的現況較晚）〕
- **一切都可以嵌套**（使用者 11-07，[arknights-kb](../../../thinking/2026-11/07/arknights-kb/README.md)）：「agent可以成千上萬個，反正可以sleep，交給llm kernel的thinking請求也有排程，並且thinking請求還可以經過一些額外關口，比如一個隊伍使用一個llm_kernel，然後這個llm_kernel負責排程與將請求轉交給另一個llm_kernel，直到轉交給實際打API的llm_kernel，一切都可以嵌套。對，工具也是，工具可以是開一個agent做事，或是將請求交給專精此道的kernel，所以才說會有成千上萬個agent。就好比LLM的神經元，不是每個區域都會被激活。」白話：llm kernel 可以一層一層轉交，工具也可以開一隻 agent 去做或把請求交給專精的 kernel；agent 可以有成千上萬個，同一時間只有一小部分在動。轉交型算 kernel（上面「轉交也算」），「建議不要濫用」那句照樣有效（兩句怎麼一起讀見 [lift-to-norms C-T09](../../../thinking/2026-11/07/lift-to-norms/04-打架.md)）。一層轉交（隊 kernel → 總機）排在 evolve-design 落地步 6，更深的嵌套、排程、跨層對帳交給 kernel-nest。
- **C-11／C-12 與本條**（說明，不是新規則；[os-concepts 02](../../../thinking/2026-11/06/os-concepts/02-OS與kernel-能借鑒.md#跟既有原則已裁的關係)）：C-11／C-12「排序＝kernel 的事」就是本條的「資源管理＋排程」——排序與准不准由收件的 kernel 決定，實際掛上去由 daemon 執行（daemon 來者不拒照掛）。

### 例子

- 鏈：一封掛 proc 請求可以走 agent→kernel_1→kernel_2→…→daemon，中間站本身也可以是一台 daemon（它的 loop 裡有 kernel 功能）。
- 擺法：繼承式（daemon 定義的 `exec` 身體當判官、判完轉寄進自己的 ctl 信箱）與 0 號 proc 式（daemon 底下一個專門收請求的 proc，判完替人寄進 daemon 的 ctl 信箱），範本 `kernel/daemon-kernel`、`kernel/procs-kernel`（[kernel-daemon 02](../../../thinking/2026-11/05/kernel-daemon/02-兩種模式.md)；daemon 定義的檔名見 [NORMS 命名續](../../NORMS/命名-續-概念搬來的檔名.md)）。
- 嵌套：一個隊伍用一台 llm kernel 排程，再交給上一層，一路交到真正打 API 的那台。
