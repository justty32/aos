## C-47 kernel 的定義

- **C-47** kernel 的定義分兩層。**原生定義**（寬泛，10-15 使用者定）：能夠管理哪些東西被執行或被使用的一個東西。**aos 的說法：kernel＝「資源管理＋排程」，而且是從外面看進去的身分**（使用者 11-11「我覺得kernel定義要改一下，回歸初始，變成"資源管理+排程"。」，[thinking 11-11 kernel](../../../thinking/2026-11/11/kernel/README.md)）：一個 agent（或其他函數）有掛 proc 或其他 syscall 的請求，把請求寄到哪，那個地方對它就是 kernel。寄出去之後要不要處理、什麼時候執行，是對方說了算，所以對寄件人來說，對方就具有資源管理與排程的功能——啥都不管也是一種管理。收件的 proc 自己不必知道自己是 kernel；只能處理掛 proc 或只能處理問腦的都算，不太限制。使用者 11-11：「kernel這個身分是從外面看進去的，對於一個有掛proc(或其他syscall)的需求的agent(或其他函數)來說，把掛proc這個請求寄到哪去，那個地方對他而言就是kernel。但對於能夠處理這個請求的proc來說，他沒必要有自己是kernel的自覺。然後有些kernel他可能只能處理掛proc或只能處理llm call，都無所謂，不太限制。因為你把請求寄出去後，是否要處理這個請求，或是說有決定這個請求啥時候要被執行的權力的，就是對方那個proc了，所以對你來說，那個proc就是具有資源管理與排程功能(啥都不管也是一種管理)的kernel。」相關：資源與排序 C-09～C-15、處理單元 C-29、參照物 C-38、間接抽象化 C-28；規範見 [N-42](../../NORMS/09-kernel.md)。
  - **一律寄 `AOS_KERNEL`**：像 Linux 的 user space proc 只看得到 kernel、看不到硬體，一般 proc 寄 syscall 請求只寄 `AOS_KERNEL`；寄出去之後背後是黑盒子，不管信會去哪（使用者 11-11「我的想法是一律寄到AOS_KERNEL，然後就如同linux一樣，user space的proc他只能看到kernel，除非有特殊需求，否則他看不到硬體」「寄送出去之後，我們就不管這封信會去哪了，他背後就應該是黑盒子了。」）。`AOS_KERNEL` 沒設就寄 `AOS_DAEMON` 那台的 ctl 信箱——daemon 自己就是最基礎的 kernel（來者不拒，[附錄1](../附錄1-名詞.md) daemon 列）；兩個都沒設的找法見 [N-63](../../NORMS/10-基礎設施-定義與工作區/07-hub-型環境變數與父子交代/02-N-63-實例-AOS_DAEMON與沒有AOS_HUB.md)。`AOS_DAEMON` 照樣傳給一般 proc，約定不用（使用者選項框「照傳，約定不用」）。
  - **多種 syscall**：有一個通用的基礎 kernel，普通的掛 proc 請求都去它那；有些 syscall 走另一個 kernel：問腦走 `AOS_LLM_KERNEL`，跟 `AOS_KERNEL` 維持兩個變數（使用者選項框「維持兩個變數」）。使用者 11-11：「所以我們這邊和linux kernel不一樣，我們有一個通用的基礎kernel，類似linux kernel，所有普通的掛proc請求都到他那邊去，類似syscall。但我們有多種syscall，有些syscall是走另一個kernel。」
  - **轉交也算，鏈是自然形成的**：判斷後把請求轉交給另一個 kernel 的也算 kernel，命名可以帶 kernel、別濫用（使用者 11-05「假如他判斷要跑這個請求的時候，所做的動作是把請求轉交給另一個真正有權限的kernel，那他也算kernel嗎？我覺得是算的，他的命名中也可以帶有kernel，只是說，建議不要濫用...。」，[thinking 11-05 kernel-daemon 05](../../../thinking/2026-11/05/kernel-daemon/05-衝突與方向題.md)）。鏈上的站不必有「鏈」的概念，只知道這份請求的 src／dst、自己做點處理（使用者 11-11「而chain這東西就是自然而然形成的，chain上的kernel可以沒有這個概念，他們就是只知道這份請求的src/dst，然後自己做一些處理而已，當然，有需要的話我們後續可以再做一些格式上的改進。」）。站與站之間一律走 aos-post：共通的只有 aos-post 信封，請求放在 body 裡，body 各類自理、不多做限制（使用者 11-11「然後"請求"格式，他是被包在aos-post格式的body內的。在請求格式之內，就不用多做限制。」）。回信怎麼走看各站設定：每站轉寄時對信封上的回信位址二選一——不動它＝回信跳過我，改成自己＝回信先回我；不記走過哪些站、不帶最初寄件人，所以後站無法跳過已把回信位址改成自己的前站，風險使用者自擔（使用者 11-11「1.看各站kernel怎麼設定」「都可以的，使用者自行承擔風險。」「2.不記。」）。
