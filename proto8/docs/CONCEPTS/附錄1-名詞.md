## 1. 名詞

| 詞 | 使用者的意思 | 出處 |
|---|---|---|
| aos | 蓋在 Linux 上、為「任意目標」最佳化、要讓大語言模型方便用的作業系統 | 2.1、2.5 |
| 目標 | 排程要最佳化的東西；AI 時代目標變多（可用性、人類可理解性……）而且任意 | 2.1、2.4 |
| 計算任務 | 一個照 POSIX 方式被叫起來的行程，不是 thread | 2.7 |
| 資源 | 處理計算任務時會用到、而且有限的東西；它自己也當行程看 | 2.7、2.8 |
| 格 | 資源的「有限」用幾個數來講：一個資源有幾格 | 3b |
| 排序演算法 | 決定哪個任務先給哪個資源處理；它自己也是計算任務 | 2.7、2.8 |
| 排程／資源分配 | 把任務分給擅長它的資源，有限時排優先級；使用者把這兩詞和「排序」幾乎互換用 | 2.2、2.3 |
| 優先級 | 有限資源下「誰先」的那個先後 | 2.2 |
| 空間 | 東西存在的地方＝資料夾體系；**就是存放狀態的地方**；資料庫、硬碟、快取、記憶體、雲端這類外部設備也可以納入空間（像 Plan 9） | 2.5、9/24、3d、3h |
| 時間／tick | 取得下一個時間點的狀態；tick 之間所有對外狀態一致（使用者叫這「時空法則」） | 2.5、9/24 |
| tick-tock | 讓時間停下來的機制；正常結束時 agent 看到的資料夾就是那個時間點的狀況；可以打包 | 2.11 |
| 變換 | 符合 POSIX 的呼叫（和 tick、空間並列的第三樣） | 9/24 |
| daemon | aos 與 Linux 之間的借階層；Linux 那邊的事（許可權、身份、記憶體、硬碟、行程）全在這層；有了它 aos 就有了「硬體」 | 2.5 |
| kernel | 管理正在跑的程式、分配 cpu、粗放式（Linux 是細粒度）、要讓 agent 能自省的那一層 | 9/19、9/23 |
| cpu（使用者的用法） | kernel 開來跑某個資料夾的一個執行單位；畫家也是一顆 cpu | 9/23、2.3 |
| 系統本體（10-22 前叫「核心」） | 到「排序程式可由模型生成」為止這一整塊；在它之上才是 agent。使用者原話是「aos 作業系統核心」；10-22 改名，免得跟分層的核心（aos-exec，C-74）撞（新詞頂層代定） | 2.10 |
| agent | 一個狀態機（想→做→循環）、一個函式、一個複合型計算任務 | 2.13、2.14、2.18 |
| 函式／黑箱 | 給東西、跑一跑、停下來；strcpy 和 LLM agent 對我們都是黑箱，差在使用方式與計算特性 | 2.14、9/19 |
| 腦 | agent 裡負責思考的大語言模型 | 2.17 |
| 核心人格 | system prompt | 2.17 |
| 近期記憶 | 一般上下文 | 2.17 |
| 手腳 | agent 可用的工具 | 2.17 |
| 九軸 | 每個計算任務固有的計算性特性：副作用、冪等、碰外部檔案、持續性、有無 entry、確定性…… | 2.9 |
| 附加特性 | 九軸之外、人隨意加的特性（例：「繪畫上偏現代」）；會多到只能靠模型處理 | 2.9 |
| 確定性 | 任務自己的屬性：有沒有機率問題；跑 LLM 的任務不確定 | 2.9、2.14 |
| 可預測性 | 觀察者對任務的認識，有主體性（對誰可預測）；確定性高不等於可預測 | 2.14、2.15 |
| S 表示式／節點 | 把流程看成一棵樹，有些節點我們知道、有些不知道；呼叫模型的節點是不知道的那種 | 2.16 |
| list／eval | 檔案系統看成 list；eval＝求某關卡之後的狀態，list 自己就是被跑的程式，其餘是環境。「list」10-19 改用 table 比喻（C-71），意思不變 | 9/19 |
| 生成排序程式的程式 | 叫大語言模型幫忙定義資源、寫排序的那個程式 | 2.10 |
| 快取／靈感 | 資源手邊現成的東西；沒有就要去找，找的時間算進處理時間 | 2.3 |
| PU（處理單元） | 會「算」的東西：普通 CPU 跑一般任務；畫師、GPU、NPU 是另一種 PU，屬外部設備——工作丟給它、它用自己的方式算、算完收回 | 3d |
| 求值 | 放開讓它算，過一段時間看它狀態變化的結果；求值＝空間狀態的變化。對資料夾求值＝執行這個資料夾（inst） | 3h、3f.1 |
| 外部設備 | 系統外面但能掛進來用的東西：PU（畫師、GPU、NPU）與儲存（資料庫、硬碟、快取、記憶體、雲端） | 3d |
| 間接抽象化 | 沒法直接變成 POSIX 呼叫的事（人手畫），拆成幾個 POSIX 任務包起來：寄信給畫家、收信、畫歸檔 | 3c |
| inst（單子；`aos-inst FILE` 命令列 10-22 刪） | 讀一張單子（JSON：`argv`、`cwd`、`envs`、`stdin`／`stdout`／`stderr`、`timeout_ms`…）去做對應的 POSIX 呼叫、跑一次。吃 JSON、固定幾個 key、不認識的略過（但 JSON 裡可以多放九軸、traits、資源標籤、優先順序標籤、工具等有的沒的）；單子也可以第一行寫 `#!/usr/bin/env aos-inst` 當入口（`proto8/bin` 版，10-22 刪了 aos-inst 命令列後不行了，10-23 Python 版整個刪了、現在沒有任何版本能用；impls 線 inst 是 C lib、沒有 aos-inst 命令列，單子當入口時由 aos-exec 行程內跑、不設 `+x`，[ideas § 20](../thinking/2026-10-19-ideas.md)） | 3f.1、3g.2、3g.13b |
| loop（`aos-loop`） | 讓一個程式一次一次執行：`loop.json` 寫 `{"exec", "max"}`〔原名 `run`；10-23 統合一度改名 `val`、同晚使用者改回 `run`（「只有 loop、daemon 用 run」），深夜再改 `exec`（使用者「exec，loop／daemon 的 run 也一起改 exec」），[thinking](../thinking/2026-10-23-naming.md)〕，每次 `aos-exec` 子資料夾或跑一張單子，子程式退 10 就停；原本設想整個進 daemon | 3f.2、3g.3 |
| node（節點） | loop 所服務的那個資料夾；時間＋task 結合起來才是好的 node | 3f.2、3f.5 |
| daemon | 統一管理所有 loop：哪個資料夾歸誰管（排他）、監控；Linux 許可權全在它身上；可以吃一點控制；可牽動另一個 daemon；正式只承諾跑資料夾；本體非常短 | 3f.2、3g.3、3g.4 |
| task（aos task） | 一個 inst 裝不下多個任務，所以用 task JSON 裝一包；跑在 daemon 上的 argv 中介程式 | 3f.4 |
| kernel（10-22 起不譯「核心」，C-74） | 第三層；一個任務包，偏定義與概念，落成協議和格式；參照物是 tick-tock（時間）與資料夾（空間）；只是一個排程；切在 task 與 tick-tock 之上，不碰 loop 的下一個 inst | 3f.6、3g.6、3g.7 |
| 標頭檔 | 一個已經設好的資料夾（例如一個 agent：skills、memory、工具放好）；引用它＝用那個資料夾，不複製，跑起來時執行環境在引用者這邊；工具對 agent 而言也是標頭檔 | 3g.10、3g.12 |
| binding（繫結） | library／程式語言做的事：把 agent 那條很長的 list 裡固定的元素綁死，用時只填幾個引數（「list」10-19 改用 table 比喻，C-71） | 3g.9 |
| 工具 | agent 函式的引數之一；對 agent 來說就是被引用的標頭檔，內部怎麼跑不用懂；agent 也可以是工具；aos 體系的每個指令都是工具 | 3g.12、3g.13 |
| 資料夾程式（定義） | 一個資料夾＝一個程式；入口是 `$AOS_ENTRY`（預設 `_entry`；10-19 晚改，原 `.aos/exec`；10-23 改名，原 `_exec`）指的檔（原「可執行檔」，10-19 下班前放寬成四種，見「入口」）；agent、工具、loop 一次裡的格都是。呼叫時不變（C-46、C-68）。就是上面說的「標頭檔」 | 10-19 |
| 入口（`AOS_ENTRY`） | 資料夾程式裡被執行的那個檔，在資料夾裡的相對位置，預設 `_entry`（10-19 晚改，原 `.aos/exec`；10-23 改名，原 `_exec`；只佔一層，跟 JSON 的 `js["_entry"]` 對上，C-72）；像 lua table 的 metatable 裡定的那個（C-68；原註「像 lisp list 的第一個元素」，10-19 晚改用 table 比喻，C-71）。入口之外的東西就是其他元素。**10-19 下班前定義（C-73）**：要麼自己是可執行檔（含 shebang 檔），要麼是 aos-exec 完整實作跑得動的檔——inst 單子、JSON 陣列（當 argv）、或 JSON 裡 `js[$AOS_ENTRY]` 的值（單子、陣列、字串路徑；10-21 晚起沒 `argv` 的物件＝當資料夾、一路往下再取）；找法 N-61 | 10-19 |
| `AOS_CO` | current obj（使用者「aos current obj」）：實際入口在那份 JSON 檔裡的位置，JSON 指標、不帶 `#`（例 `/dev/sub`）；整份檔或不是 JSON＝空字串；aos-exec 每層覆寫（N-57） | 10-21 晚 |
| `AOS_CF`、`AOS_CD` | current file、current dir：aos-exec 每層覆寫的兩個環境變數——實際被執行的那個檔的絕對路徑（不帶 `#/…`）、它所在的資料夾（＝cd 進去的地方）。程式 cd 走之後靠它們找回自己的東西（`aos-exec "$AOS_CD/tools/stamp"`）（C-69、N-57；[ideas § 19](../thinking/2026-10-19-ideas.md)） | 10-19 下班前 |
| `檔#/指標`（JSON 尋址） | aos-exec 的入口路徑可以指進 JSON 裡：`cfg.json#/tools/stamp`＝cfg.json 裡 `/tools/stamp` 那個值（JSON pointer）；第一個 `#` 就切，檔名不能含 `#`（N-62；使用者「#/。」「尋址一定值得。」） | 10-19 下班前 |
| table（比喻） | 資料夾比喻成 lua 的 table：靠名字找元素、裡面還能放 table；跟 lisp 的 list 本質一樣是「用 index＋巢狀方式分資料，只是 index 格式不同」，比喻一律用 table（C-71）。舊條文與舊討論裡的「list」都是它 | 10-19 |
| `aos-exec [旗標...] XXX [args...]`（原 `aos-exec DIR`、`aos-exec XXX [WS [args...]]`） | 「在工作區執行 XXX 這個程式」：XXX 前面是 aos-exec 自己的旗標（目前只有 `--ws WS`＝工作區，沒給沿用 `$AOS_WS`；10-21 改），之後原樣傳給入口；XXX 可以是資料夾、檔、或 `檔#/指標`（10-19 下班前放寬）；找到入口、設好 `AOS_WS`、`AOS_STACK`、`AOS_CF`、`AOS_CD`，cd 到入口檔所在的資料夾，讀那裡的 `.env`（10-21 加；旗標 ＞ `.env` ＞ 環境變數 ＞ 預設；10-22 改：預設不蓋已有的〔旗標 ＞ 環境變數 ＞ `.env`〕，加 `--dotenv-override` 才是前面那個順序），開跑——可執行檔與 argv 陣列 exec、inst 單子行程內跑（C-68、N-58、N-59、N-61）。impls 線 aos-exec 是唯一提供的命令列（[ideas § 20](../thinking/2026-10-19-ideas.md)；§ 23 後也有 aos-loop、aos-fsm，10-21 加 aos-daemon；aos-exec 10-21 的改動 impls 10-21 晚對齊） | 10-19、10-21 |
| stack（`AOS_STACK`） | **被叫的那個程式自己的執行中狀態放哪**（預設 `$AOS_WS/.stack/`；10-23 改名，原 `.aos/`）：狀態、草稿、`trace.jsonl`、叫別的程式時開的小格。像函數的呼叫堆疊（C-46、C-65）。放哪由呼叫方自由決定（C-67）。10-16 白天叫「工作區」，10-16 夜先改叫 frame、同夜再改名 stack（使用者：「不過frame那塊能不能換成stack(或heap)?。」→ 頂層推薦 stack →「好！」） | 10-16 夜、10-19 |
| 小格 | 叫別的資料夾程式（工具、另一個 agent）時給它的 stack：`$AOS_STACK/<名>/`，小格名＝工具資料夾名；叫完不自動收（P-17） | 10-19 |
| heap | **保留**：以後指跨呼叫共用的記憶，目前沒有機制（10-16 夜，改名 stack 時一起定） | 10-16 夜 |
| 工作區（`ws`，workspace） | 使用者的檔、成品要留的地方；保持乾淨，只放交辦的東西與成果。位置由環境變數 `AOS_WS` 給（C-65、C-66、N-55） | 10-16 夜 |
| 指標 | 工具要影響外部（呼叫者的工作區）時拿到的那個東西；在 aos 就是環境變數 `AOS_WS`（C-66） | 10-16 夜 |
| 基礎層 | 分層的最下層：核心 aos-exec（含 inst 庫、指示詞、旗標）＋ loop、daemon（C-74） | 10-22 |
| 核心（分層） | 基礎層中的核心＝aos-exec（使用者「aos-exec是core，是基礎中的基礎」）；只指這個，kernel 不叫核心（C-74） | 10-22 |
| 標準庫 | 基礎層之上：fsm、tasks、其他；再上去是 agent／kernel（C-74）。跟「純標準庫 Python」（只用 Python 自帶的庫）是兩回事 | 10-22 |
| 基礎設施 | **主題**名（CONCEPTS 03、NORMS 03～07、10），不是層：橫跨基礎層與標準庫。repo 根 `core/README` 的「基礎設施」＝C++ 建置目錄 `common/`、`app/`、`cmake/`，另一回事 | 10-22 |
| `core/`（repo 資料夾） | 舊一代 C++ 版的「必要模組」資料夾（拿掉它 aos 就不成立），名字不動；跟分層的核心無關 | 10-22 |
| 最小實作／完整實作（原基礎實作／標準實作） | 實作兩級：最小實作只做最少步驟、確保合規（aos-exec＝cd → 設環境變數 → 跑檔）；完整實作顧邊緣狀況、精修過（10-23 起是 `proto8/impls` 的 C++ 那幾支；原寫 `proto8/bin` 那幾支，Python 版 10-23 刪）。10-22 改名免得跟基礎層撞（新詞頂層代定；N-18） | 10-14、10-21、10-22 |
