### 3. say／listen 現在的契約，三方怎麼對上

| | aos agent（agent-dan／bob 範本、這次的 bob-2） | aos-hub 接的 claude／codex | say／listen 認什麼 |
|---|---|---|---|
| 題放哪 | `$AOS_WS/new/<題名>` | `<資料夾>/.stack/new/<題名>`（kernel 替它收） | say：工作區的 `new/`；沒設 `AOS_STACK` 且 `.stack/new/` 在＝改丟 `.stack/new/` |
| 答在哪 | `out/<題名>` | 同左（在 `.stack/` 裡） | listen 等 `out/<題名>` |
| 誰在服務 | `/proc` 猜 aos-loop／fsm／exec；bob-2 寫 `server.txt` | kernel 寫 `server.txt` | listen 兩個都認 |
| 卡在哪、失敗 | fsm 的 `trace.jsonl` 每格一行；bob-2 每題一行 | kernel 每題一行（`question`、`error`） | listen 讀 stack 的 `trace.jsonl` 最後一行 |
| 中途偷看 | agent-dan 的 `$AOS_STACK/history.jsonl` | CLI 自己的對話檔、`live.jsonl`（`aos-hub watch`） | `listen --follow` 讀 **stack 裡的** `history.jsonl` 與 `trace.jsonl` |
| 暫停、停 | bob-2：`$AOS_STACK/ctl.json`（N-07）；fsm 範本：沒有 | `aos-hub pause`（關畫面、**照樣收題**）／`stop`（歸檔、不再收） | 沒有 |

- **say（塞話）三方已經共用**：P-11 的 `new/`＋out/ 同名，就是 [hub-adapter 結論一](2026-10-28-hub-adapter.md#結論一agent-對話協議從-aos-saylisten-抽出來的)的「agent 對話協議」。
- **listen 等答案也共用**；**「偷看」不共用**：listen 只看 stack 的 `history.jsonl`，bob-2 照 A 的代定把對話簿放在工作區，所以 `--follow` 看不到它在說什麼；claude／codex 的中途要走 `aos-hub watch`，是另一條路。
- **暫停／停沒有共用**：bob-2 用 ctl.json，hub 用自己的指令，兩邊的「pause」意思還不一樣（見下面衝突 3）。
- **建議的三方最小契約**（只提、repo 程式沒改）：
  - **say＝往目標信箱的 `new/` 丟一題**，信箱的找法照現在（工作區，或 `.stack/`）。
  - **listen＝看三樣**：答案 `out/<題名>`；誰在服務 `server.txt`；中途在幹嘛＝stack 的 `trace.jsonl`（每題／每格一行）＋ `history.jsonl`（一行一則 `{"role","content"}`）。服務者要讓人偷看，就把對話簿放 stack（P-41 本來就這樣），或在 stack 留一份。
  - **暫停／停＝服務者 stack 裡的 `ctl.json`（N-07 的 `paused`／`stopped`）**：aos agent 自己讀；hub 代答的實例由 kernel 讀它那格的 ctl.json（`paused`＝不收題、`stopped`＝等於 `aos-hub stop`）。這樣「外面那層」不管是人、hub、還是別的程式，都只寫一份檔。

### 4. 對照 aos-hub：拿它包 bob-2，缺什麼、多什麼

試法：`aos-hub-kernel &`、`aos-hub add --tool hub-bob ws-hub`，`hub-bob` 是自己寫的**一題一答**工具（stdin `{"prompt"}`、stdout 回答、對話簿照樣記 `history.jsonl`，跟 bob-1 一樣是 `claude -p`）。

- **能直接套的那半**：hub 的 kernel **本身就是那個停著等的循環**。say「招牌一杯多少」85 元（6.5 秒）、「那兩杯呢」170（5.9 秒，記憶對），`listen --status` 顯示「在跑 aos-hub-kernel」，`aos-hub stop` 歸檔、kernel 關掉後 `ls` 報 `KernelMissing`。也就是說：**「停著等的腦」＝hub kernel＋一題一答的工具，bob-2 自己那個循環 hub 已經有了。**
- **缺的**：
  1. hub 包不了「自己會循環的程式」：它只會起一題一答的工具、或 claude／codex 的畫面（tmux）。bob-2 那種自己 `aos-exec` 起來、自己等的，hub 不會開、不會關，也不會替它寫 ctl.json。
  2. **hub 的 pause 不是「不收題」**：`aos-hub pause` 回「本來就沒畫面（已收起）」，之後 say 的題照答（hub 的 pause＝關畫面、對話留著）。要「先別動」的那種暫停，hub 沒有。
  3. `aos-hub open` 只認 `kind` 是 claude／codex（`CfgBad`）；自己的工具沒畫面可接。
  4. 中途偷看：hub 的 `watch` 只讀 claude／codex 非互動那條的 `live.jsonl`，自己的工具沒有。
- **多的**（bob-2 用不到）：畫面（tmux、Ctrl-]）、對話 id 與 `--resume`、stop 時拷 CLI 自己的對話檔、閒 30 分自動收起、只登記的實例、`SessionBad` 重試。

### 新做法跟既有原則的衝突

1. **對話簿放工作區 vs P-41／listen 放 stack**：A 的代定 3（輸入放工作區）沿用到 bob-1／bob-2；P-41 與 agent-round 放 `$AOS_STACK/history.jsonl`，`aos-listen --follow` 也只看 stack。**事實**：bob-2 跑著時 `listen --follow` 看不到它的對話。**後果**：放工作區＝外面一眼看得到、能手動接一句，但通用接口偷看不到；放 stack＝listen 原樣能偷看，跟 agent-dan 一致。**建議**：搬回 stack（照 P-41），A 的代定 3 翻案。
2. **「agent 這層沒有 ctl」**：NORMS 窗那份開頭寫「agent 這層沒有 ctl：停＝退 10 或送訊號（P-19）」。bob-2 是 agent，卻讀 ctl.json。**後果**：照字面，bob-2 只能用訊號停、沒有暫停；但使用者要的射後有理就是「跑著的時候能停一下」。**建議**：改成「**停著等的 agent**（自己不退的那種）也開 ctl 窗」——它其實就是「會反覆跑的東西」，跟 loop／daemon 同一類；一次跑完就退的 agent 照舊沒有。
3. **hub 的 pause ≠ N-07 的 paused**：hub-kernel 決定 5 的 pause＝關畫面、對話留著、**題照收**；N-07 的 paused＝不起新的一次。**事實**：`aos-hub pause` 之後 say 的題照答。**後果**：同一個詞兩個意思，用通用接口暫停時會猜錯。**建議**：hub 的那個改叫「收起」（10-27 的原名），`paused` 留給「不收新題」。
4. **兩種信箱**：任務書原本要用 N-16（aos-post），通用接口 say／listen 用的是 P-11 的題目信箱（10-29 加註：不算標準投遞）。**建議**：射後有理的塞話一律走 P-11（say 認得），N-16 留給 agent 之間的信；兩個不混。

### 原則推不出的方向題

1. **通用接口的契約定在哪一層**：say／listen 自己（程式說明）、agent 定義（每隻自己說信箱在哪）、還是介質條文（N-16／N-14）？**事實**：三方現在靠的是 P-11～P-14 加 hub 補的 `server.txt`、trace 兩樣（hub-adapter 代定 1：「沒升進 CONVENTION，用穩再說」）；bob-2 照這套一行沒改就接上了，缺的只有偷看（對話簿位置）與暫停（ctl）。**建議**：定在 CONVENTION 的 agent 對話協議（P-11～P-14 那節），把 `server.txt`、trace、stack 的 `history.jsonl`、`ctl.json` 四樣補進去；不放 N-16（那是標準投遞，信封不同）。
2. **外面管生命週期那層是誰**：aos-hub、aos-daemon，還是新東西？**事實**：hub kernel＋一題一答的工具已經做完 bob-2 的全部（等、收題、答、歸檔），不用自己寫循環；但它包不了自己會循環的程式、pause 意思不同、只會開 claude／codex 的畫面。**建議**：用 hub——它已經是「管停著的實例」的那層（hub-kernel 決定 9：hub 是 kernel 的一種）；補「一題一答的 aos agent 也能 add」（今天已經能跑）和讀 ctl.json 兩樣就夠，不另做新東西。
3. **bob-2 的「暫停」跟 aos-loop／aos-fsm 的 paused 是不是同一個**：**事實**：意思一樣（不起下一次、手上那次做完），差在「一次」多大——bob-2 是一題，loop 是一次 exec，fsm 是一格；使用者說的「暫停其狀態機、去修改更多東西」要停在格與格之間，bob-2 做不到（它沒有格）。**建議**：同一個詞、同一個意思（N-07），「一次」由各程式自己說；要停在格之間的，就是 aos-fsm agent 才有的細度。
4. **射後有理要「停著等的腦」自己寫循環，還是一律用 hub＋一題一答**：**事實**：兩種都跑通，延遲同級（3～6 秒，都是 claude 的時間）；自己寫的循環約 120 行，hub 那條只要 20 行的工具。**建議**：預設走 hub＋一題一答；只有腦本身就停著等（互動式 claude、pi 的 rpc 模式）才需要自己的循環——這正是使用者說的「寫死在定義裡」。

## 頂層對八題的再想（10-29 晚；使用者「幫我多想想」後，未定）

> **頂層提法（10-29 晚，使用者還沒定，明天繼續想）**——不是決定。使用者原文見上面「使用者原文」一節。

**底層形狀：say／listen 就是「投遞＋窗」套在對話上。** `aos-say`＝把一句話**投遞**進 agent 的 queue，對話順序是意思的一部分，所以該用**有順序的投遞**（N-16 `--ordered`）；`aos-listen`＝看 agent 的**窗**（history，N-14）。通用接口不用發明新東西，是白天定的兩個基本概念的組合。

**第 4 題反對「兩種信箱並存」**：運行中塞話走 say／listen 的題目信箱（P-11 `new/`／`out/`）、agent 之間寄信走標準信箱（aos-post）＝兩套機制做同一件事（都是「有人把東西投進我的資料夾」）。題目信箱是 10-24 的老寫法、標準信箱是 10-29 才正規化的；既然 say 要當通用接口，它該走標準信箱且用 `--ordered`（隊長這次剛好沒用 `--ordered`，所以沒撞到）。順帶好處：**pending 信箱每輪開頭排進 history，兩個場景都適用**——場景一只是沒人投；對多回合的射後不理 agent，也能在回合之間插話，不必它停著等。

**第 2、6、7、8 題其實是一題：「停著等」由誰提供。** bob-2 是我們自己寫循環讓 `claude -p` 這種一答就退的腦看起來像停著等——這不是腦的本性，是裝的。使用者說「結不結束是腦的性子」對互動式 claude 成立（真的停著）；`claude -p` 的性子是退，要它停著一定有誰在外面繞圈。三個候選：

- 寫在 agent 裡（bob-2）：每個停著等的 agent 都要重做 paused／stopped／ctl 清理，隊長發現的兩個瑕疵（ctl 不清、status 看不出暫停）正是重做漏掉的。不建議。
- aos-hub：替有畫面的外部 CLI 做的（開畫面、Ctrl-]、接回舊對話），包 aos agent 多了用不到的、少了「先別動」。削足適履。
- aos-loop：10-28 定「aos-loop＝常駐＋暴露狀態＋控制手把的包裝」（medium 決定 2），paused／stopped、ctl 清理都有；一答就退的 agent 外面套 aos-loop 就是停著等。

建議：**agent 永遠是一個函數（一輪進、一輪出），停著等交給 aos-loop。** 於是第 2 題（agent 沒有 ctl）照舊不改規範；第 7 題暫停本來就是 aos-loop 的 paused；第 8 題不自己寫循環；aos-hub 只留給真的停著的外部 CLI。頂層自承：使用者先前說「這跟 aos-loop 沒關係」，那時頂層把 aos-loop 用在「退不退」上、用錯了；這次是另一題「一個會退的腦怎麼變成停著等」——對不對待使用者定。

**第 1、3、5 題同意隊長，補理由**：① history 放 `.stack/`——history 是這次執行的狀態、不是交給上層的成果（決定 26「紀錄 aos 不管」），暫停時要改的就是它；③ hub 的 pause 改名「收起」，同字兩義一定出事；⑤ 規則寫進 CONVENTION 的 agent 對話協議，但內容改成「agent 的 queue 信箱＝N-16 標準信箱的有順序實例、history＝N-14 的窗」，引用現有條文、不另定四樣新東西。

**還沒試到**：使用者的場景二「如果是 aos agent，還可以暫停其狀態機、去修改更多東西」——今晚兩個 bob 都是 `claude -p` agent、不是狀態機 agent；「停在格與格之間改東西」只有 aos-fsm agent 做得到，沒碰。下一輪試驗場值得拿一個 fsm agent 跑場景二。

**歸結成三題待使用者**：① say 改走標準信箱＋`--ordered`、題目信箱退場；② 停著等交給 aos-loop、agent 保持是函數；③ 其餘三題（1、3、5）照隊長建議。

## 決定（10-30）

使用者說「照直覺」回答，三條都可翻案；細節規劃交 fable（另一檔）。

- **決定 33**：say 可以改走標準的有順序投遞、題目信箱退場；但 **agent 這一層不用「信箱」這個詞，這層是訊息的 queue**。「請求的投遞」（agent 之間寄信）可以叫信箱、也可以叫 queue。
  - 頂層理解：queue 是概念名、有順序投遞是它底下的實作，條文與工具命名照這個分。
- **決定 34**：**aos-loop 是 aos agent 這支程式的內部組件**（停著等由它提供，agent 保持是函數）。其他 coding agent（claude code、codex）內部是黑盒子，要管它們的生命週期就在外面包東西、包括掛到 aos-daemon 底下；daemon 若管不了純 aos-exec 的東西，就擴充（aos-daemon-3 或 aos-hub 之類），總之要有一個東西能把純 aos-exec 的 proc 納管進 aos；沒有也行，Linux 的 `ps aux`＋`kill` 就夠。用現有 loop 規格把純 aos-exec 的 proc 包成 `max: 1` 掛到 aos-daemon 底下，可以。
- **決定 35**：其餘三題照隊長建議（對話簿放 stack、hub 的 pause 改名「收起」、規則寫進 CONVENTION 引用 N-16／N-14）；**另加：claude code cli 這類自己存 session 的，aos 體系要弄一份 symlink 或複製一份過來管理**。
