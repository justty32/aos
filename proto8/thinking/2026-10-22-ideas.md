## 1. Python 版 aos-inst 刪掉、寬鬆度與錯誤代號照 C++ 版（10-22）

背景：impls（C++）與 bin（Python）「刻意沒對齊」的五處與兩條寬鬆度差別（[session log 10-21](../../wf/session_logs/2026-10/2026-10-21.md)）。

使用者原話：

> 對於python版，aos-inst指令可以刪掉了，跟C++版一樣做成lib就好。C++版比較寬鬆這塊，希望python也遵循，錯誤訊息多代號也遵循。子行程直接呼叫我覺得OK。

第 4 點（子行程直接呼叫）頂層問過之後，使用者補：

> Python 版照舊去 PATH 找 aos-exec 就好，只是 C++ 版這樣做我接受

> 因為以後可能會變成一個aos指令，後面接子指令。比如aos exec, aos loop這樣

決定：

1. bin 版刪掉 `aos-inst` 命令列；inst 只剩 Python 庫 `aos_inst.py`，單子一律經 aos-exec 在行程內跑（同 C++ 版 inst 是 C lib）。
2. Python 照 C++ 的寬鬆：設定檔（loop／daemon／fsm）第一行 `#!` 跳過、不再報錯；`.env` 去前導空白只認 ASCII 空白。
3. 錯誤一行照 C++ 多一個代號：`程式名: 代號 原因`（例 `aos-exec: EntryMissing 原因`、`aos-loop: Usage usage: …`）。
4. C++ 版 loop／fsm／daemon 在子行程裡直接呼叫 `run_cli`、不叫 PATH 上的 aos-exec：使用者接受這個差異（以後可能收成一支 `aos` 加子命令）；**Python 版不改**，照舊叫 PATH 上的 aos-exec。

結論：

- 沒有 aos-inst 命令列，只有它才跑得動的兩種寫法也不成立——+x 的 `_exec` 第一行寫 `#!/usr/bin/env aos-inst`（CONVENTION P-28 的 (A)），和小殼 `exec aos-inst _exec.json`（(1) 寫成 `exec aos-exec _exec.json`）；同一個檔拿掉 `+x` 就是兩版都認的 JSON 入口（(B)）。
- bin 的 aos-exec、aos-loop、aos-daemon、aos-fsm 自己的錯都是 `程式名: 代號 原因`，代號照 impls 原始碼（對照在 [bin/README](../bin/README.md)）；aos-tick 不在 impls，沒加。
- 10-23 使用者看過回報：「都按照建議做。」——inst 單子錯誤訊息兩版字面不同的兩處（原因開頭、`OpenFailed` 帶不帶檔名）照現狀不改。代號的名字照 [命名統合](2026-10-23-naming.md)（它翻案了這裡「既有 impls 代號沿用、不改名」「aos-tick 不加代號」兩條）。

## 3. `.env` 基礎子集與 `--dotenv-override`（10-22）

接 § 2 的 (b)。規範：[N-57～N-60](../docs/NORMS/10-基礎設施-定義與工作區.md)；改的是 [10-21 § 4](2026-10-21-ideas/02-4-aos-exec-支援-env.md#4-aos-exec-支援-env10-21) 的 E2、E3、E4 與 § 4.3。

### 3.1 原話

1. > .env這塊，我們目前是繼承？也就是讀.env的時候，是只增添，不是整個拿掉換成.env內的定義？我會希望能夠盡量跟dotenv那塊相同，但太麻煩的功能就不做，只做一些簡單基礎，因為要更多功能的話不如直接用source env.sh。然後我會覺得拿掉變數這個功能沒必要。
2. > 那不應該繼承吧...dotenv那邊不是繼承吧，我們盡量依照大家現有的經驗、共識去做。
3. > override選項...我們能添加相關旗標或選項嗎？然後我們的選項名稱改disable override，所以默認就是會override？還是說我們跟他們就一樣，就給override選項，默認不override，我傾向這個。
4. > 好麻煩...我覺得還是以旗標為最優先，貫串始終。然後.env這塊我看能不能完全按照python dotenv來走，override與否，就用旗標來表示，不要用AOS_ENV_OVERRIDE。
5. > 往下每一跳的 aos-exec 都是重新起的程式 <- 那就不傳，我的意思是aos-exec每次起來，他的旗標設了override，這次起來就是override，下次起來就看下次有無旗標。
6. > 完全按照python-dotenv...看起來他東西一堆，那還是不要完全照他的來好了，我們只做基礎的功能，太麻煩的不做
7. > 旗標這塊，命名應該要是env override
8. > dotenv override

頂層把三處衝突帶給使用者（10-21 E2 優先順序；C-56「照字面」vs 引號、註解、去空白；字串轉向吃不吃旗標，10-21 E4 vs 第 5 句），使用者拍板：

> 照建議：1 改成預設不蓋、加 --dotenv-override 才蓋；2 引號、註解、去空白都做；3 字串轉向算新的一跳、不吃旗標。可以開始做。

做完審查後，頂層帶回三題（`a#b`、`#fff` 照字面要不要改報錯；值頭尾的全形空白等 Unicode 空白；預設不蓋之後「`.env` 改 `AOS_*`」那套規則留不留），使用者：

> .env這三題：報錯、按照python-dotenv把它當空白去掉、留著

接著更正第 1 題：

> 喔等等，a#b報錯這塊，原來python dotenv是不報錯留著，那還是跟python一樣吧

### 3.2 決定

1. **預設不蓋**：開始讀一份 `.env` 那一刻環境裡已有的名字，那一行跳過（格式照驗、壞了照報錯）；同一份檔裡同名照樣後者贏（同 python-dotenv `load_dotenv`）。多層 `.env` 不蓋時外層（先讀的）贏。
2. **旗標 `--dotenv-override`**（不帶值、重複給＝一樣）＝`.env` 蓋掉已有的。只管這一次起來的 aos-exec：這一跳一路往下讀的每份 `.env`（資料夾、`$AOS_ENTRY` 沿路、JSON 物件的 `.env` key）都吃；插進 argv 的下一跳、loop／fsm／daemon 每拍叫的 aos-exec 不吃，要的人自己在 argv 寫（例 loop 寫 `{"run": "loop.json#/body", "body": ["aos-exec", "--dotenv-override", "think"]}`）。不經任何環境變數往下傳。
3. **優先順序**：沒旗標＝旗標 ＞ 原本的環境 ＞ `.env` ＞ 預設；有旗標＝旗標 ＞ `.env` ＞ 原本的 ＞ 預設（＝10-21 E2）。`--ws` 兩種都贏。10-21 E3「`.env` 什麼都能設、含 `AOS_*`」要加旗標才整句成立（讀 `.env` 前已設的 `AOS_WS`、`AOS_STACK`、`AOS_CF`、`AOS_CD`、`AOS_CO` 不加旗標改不了；`AOS_ENTRY` 不 export，外面與外層沒設時不加也設得了）；PATH 接舊值那行要那一跳加旗標。
4. **字串轉向＝全新一跳、不吃旗標**（照 10-21 E4）。
5. **格式＝基礎子集**（不寫完整 python-dotenv 解析器）：行首 `export ` 忽略；`=` 兩邊空白忽略；沒引號的值去頭尾空白；空白＋`#` 起是行尾註解（`a#b`、`#fff` 照字面，第 7 點；空白算哪些見第 8 點）；單、雙引號只剝一對、不跳脫、不跨行，引號後只能接空白或 `#` 註解；雙引號裡展開 `${名字}`、單引號裡照字面；`$X` 不帶大括號照字面。準則：收下的寫法給的值跟 python-dotenv 一樣，各家給的值不一樣的寫法一律 `.env 壞`——`X= # c`、引號裡有 `\`、單引號裡有 `${`、引號沒收尾、引號後的雜字、`${X:-y}`。其他照舊（`X=` 空字串、只有名字＝錯、名字 `[A-Za-z_][A-Za-z0-9_]*`、BOM／NUL／非 UTF-8＝錯、錯誤只印檔名行號）。JSON 物件的 `.env` key 格式不變，只套蓋不蓋。
6. **不做**：unset、多行、跳脫、`${X:-y}`；aos-exec 照舊只用標準庫（§ 2 (a)）。
7. **`a#b`、`#fff`（沒引號、`#` 前面沒空白）照字面**，同 python-dotenv（以使用者更正那句為準）。
8. **值的頭尾、`#` 前面的空白照 python-dotenv 認 Unicode 空白**（全形空白、不換行空白等，跟 Python `str.isspace` 同一套），一律當空白去掉。行首的前導空白照舊只認 ASCII 空白（§ 1 第 2 點照 C++ 的寬鬆）：行首是全形空白 python 會跳過、aos 報錯，是報錯、不是靜靜不同，所以兩條不衝突。
9. **「`.env` 改 `AOS_*`」那套規則留著**（只在加 `--dotenv-override` 時用得上）。

### 3.3 結論

- bin 與 impls 都照這樣做；`aos_flags.py` 收不帶值的旗標。收下的寫法跟 python-dotenv 逐案比過一樣（有裝 python-dotenv 才跑的對照測試，`tests/test_exec_dotenv.py`）。demo 不靠 `.env` 蓋原有。

## 5. loop（10-22）

頂層把 loop 的四個實際問題（每拍沒有時間上限、兩個 loop 共用 state 檔會撞暫存檔名、state 寫不了吐 traceback、loop 跑途中改 `.env` 不生效）與幾處條文還標「草稿」、跟程式對不上的地方帶給使用者。使用者原話：

> loop這塊，那四個實際問題我的意見如下：1.每拍沒有時間上限沒關係，想要時間上限就自己在argv加timeout之類，這是使用者自己要承擔的風險。2.使用者自己承擔風險。3.沒關係。4.使用者要自己承擔。小地方那些我都OK，就是條文草稿那邊要去解決。

決定：

1. 四個問題都不改程式，寫成「使用者自行承擔」：每拍上限自己在 argv 接 `timeout`（或用單子的 `timeout_ms`）；共用 state 自己避免（或接 s6-setlock，頂層補的做法）；traceback 接受；`.env` 不即時生效接受，要蓋就在 `run` 指的單子 argv 寫 `--dotenv-override` 或重開 loop。落在 [NORMS/04](../docs/NORMS/04-基礎設施-loop與daemon.md) 開頭。
2. loop 相關的條文照 bin 程式定稿（程式 > 文件）：N-13、N-17、N-28、N-32、N-33、N-54。N-17 的心跳間隔照 N-32 定為 1 秒；N-32 補寫 `interval_ms` 的語意（上一拍結束到下一拍開始，不是固定週期；ctl 改它對正在睡的那段不生效）；P-06 列 loop.json 實際的五個 key；N-28 子 loop 的輸出檔：aos 不保證不無限長，要控制大小使用者自己處理（logrotate、單子的 `stderr` key、s6-log 等是頂層補的例子）。
3. 窗一族的總則 N-14、鎖 N-15、信箱 N-16 還沒有完整實作可對，照舊標草稿。

## 6. daemon（10-22）

頂層帶給使用者 daemon 的三件：① daemon 被 SIGKILL 期間死掉的子項，daemon 再起時會被重起；② 子項名字叫 `state.json`／`ctl.json`（跟 daemon 自己的 ctl／state 同名）時 daemon 會 traceback 當掉或 ctl 被佔；③ N-28 列了卻沒做的：`policies.child_exit`、backoff、stderr 輪替、不接回時清掉舊小格、「有 argv 就包成跑一次」。使用者原話：

> daemon 照建議：1 daemon 重開時照表起，算重新開始、不算自動重起；2 子項名字擋掉跟 ctl／state 同名；3 N-28 未做的從規範拿掉、改寫自己接工具。

決定：

1. **程式不改**：「不自動重起」管的是 daemon 開著的時候；daemon 重開＝重新開始，照名單起表上缺的（含停機期間死掉的），活著且對得上的照 `adopt` 接回。測試釘住（`test_restart_starts_children_died_while_down`）。
2. **擋撞名**：會撞的名字＝daemon 的 ctl、state 落在 `$AOS_STACK` 底下時相對路徑的第一段（`state.json`、`ctl.json`、`"w/c.json"` 的 `w`；在外面的、沒開的不算；頂層照程式定）。起來時撞＝一行錯誤、退 1；ctl 的 `children` 撞＝那份 ctl 不採用、維持上一份好的、原因進 state 的 `last_warning`。
3. **N-28 沒做的從規範拿掉**：`policies.child_exit`、`backoff` 隨「不自動重起」不做；輸出的選填路徑、輪替、清舊小格不做，要的話自己在鏈上接工具（拍的單子用 `stderr` key 導走接 s6-log／svlogd、外面 logrotate；舊小格自己在起 daemon 前刪）；「沒 `run` 有 `argv` 就包成跑一次」不做，要跑一次單子寫 `{"run": "daemon.json#/children/<名字>/body", "body": 單子, "max": 1}`。

結論：bin 與 impls 的 aos-daemon 都擋撞名（測試 `tests/test_daemon.py`；起來時撞名的代號 `Conflict`，10-23 使用者認可）；N-17 六態不含 `backoff`。`.env` 預設不蓋，所以 daemon 環境裡已有的變數會壓過子項 `.env` 同名的值。

舊小格的 `ctl.json`（daemon 重新起子項、非接回時，舊的還寫著 `stop` 就一起來就停）使用者 10-22 原話：

> ctl.json 照舊，使用者自己刪，算自己承擔

決定：daemon 不自動清，使用者自己刪，算使用者自行承擔。

## 7. fsm（10-22）

頂層把 fsm 的幾個實際問題（a state 檔在但讀不了、b 某格的 `next` 指到表上沒有的狀態、c `next` 是空字串，與其餘幾件）和 fsm 條文還標「草稿」的事帶給使用者。使用者原話：

> fsm 照建議：a state 讀不了就退 1；b、c 開跑時查整張表；其餘算使用者自己承擔，條文定稿。

決定：

1. **a**：`$AOS_STACK/state` 在但讀不了（沒權限、是資料夾、不是 UTF-8…）＝fsm 自己的錯，退 1、stderr 一行、不跑格；檔不存在照舊＝從 `start` 起。
2. **b、c**：開跑時（讀表後、跑格前）查整張表——`start` 要在表上，每一格的 `next` 要是表上有的狀態名、不能是空字串；不合＝表壞、退 1、不跑格。state 檔裡的狀態不在表上照舊退 1。一起查（實作時代定）：每一格的形狀與 `val`、`next` 頭尾不能有空白、不能有換行（state 檔是純文字一行、讀回來會去頭尾空白）。
3. **其餘使用者自行承擔**，不改程式，寫在 [NORMS/07](../docs/NORMS/07-基礎設施-組合子.md) 開頭：每格沒有時間上限（自己接 `timeout` 或用單子的 `timeout_ms`）；兩隻 fsm 共用同一個 stack 會撞暫存檔；state／trace 寫不了吐 traceback、下一拍重跑同一格；`trace.jsonl` 不設上限；loop／fsm 被 SIGKILL 時格變孤兒、重開時可能重疊；無窮轉移只有 loop 的 `max` 擋；`val` 的相對路徑從 cwd 算；`.env` 外層贏，`val` 陣列傳不了 `--dotenv-override`（要寫成 body 單子）。
4. **條文定稿**：fsm 的 N-20、N-36、N-38、N-39、N-41 照 bin 程式定稿（程式 > 文件）；a、b、c 寫進 N-36、N-38。NORMS/07 開頭補「fsm 屬標準庫」（C-74）。tasks 的 N-34 現無實作、沒有程式可對，照舊標草稿。

結論：bin 與 impls 都照這樣做（`tests/test_fsm.py`；表壞的代號 `FieldType`、state 讀不了 `ReadFailed`、state 裡的狀態不在表上 `StateUnknown`；`FieldType`、`ReadFailed` 10-23 使用者認可）。
