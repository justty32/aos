# 環境變數盤點：要使用者裁的問題（11-01 晚，隊長擬）

← [入口](../2026-11-01-playground-bob.md)｜涵蓋：要使用者裁的問題｜上一份 [01-環境變數盤點](01-環境變數盤點.md)（判準、分類小計、[資料檔](env-vars.json)）

每題附判準（照它答就行）與兩邊的後果；個數、檔數出自 [env-vars.json](env-vars.json)。


## 問題 1：hub 型（整棵樹共用的一個位置）算不算必要？

涉及 `AOS_KERNEL`、`AOS_DAEMON`（N-63 已定的 hub 實例）與長得像 hub 的 `AOS_HEAP`、`AOS_ROSTER`、`AOS_AI_ROOT`。
判準：值是「一個位置」，讀它的程式在**兩層以上**、中間層不知道它存在 → 算必要。
後果：算 → 5 個升必要，N-63 照舊、什麼都不用改；不算 → N-63 要改成「hub 用固定檔名（例 `$AOS_WS/roster.json`）或 argv」，牽 aos-llm-send、aos-daemon-ctl、aos-eca-hub、memory、send_message 等十幾檔與測試約 3 檔。`AOS_KERNEL_REPORT`（kernel 告訴腦 usage 寫哪）、`AOS_IMPROVE_SANDBOX`（self-improve 的頂層開關、深處的 try_run 讀）一起跟這題走。

## 問題 2：腦的三個變數（`AOS_BRAIN_URL`、`MODEL`、`KEY`）留環境變數，還是改一份腦設定檔？

判準：同一棵樹裡「不同格要用不同的腦」若常發生（例如 ≥2 隻 demo 需要），環境變數一路繼承反而礙事 → 改檔（每格或每隻 agent 資料夾一份 `brain.json`）；不常發生 → 留著（P-39 本來就把它歸「一路繼承」）。
後果：改檔牽讀的 23 檔、設的 14 份 `.env`、測試 4～8 檔。`AOS_BRAIN_KEY` 建議不管怎樣都留環境變數（放 argv 會在 `ps` 被看到，放檔要另管權限）。

## 問題 3：「格自己的旋鈕」42 個，要不要照 11-01 `--on-empty` 的先例一次性全改？

判準：只有一支程式讀、中間沒有別層要知道 → 改；改 argv 還是改檔照判準第 3 題（≤3 個用 argv、一大串併成一份設定檔）。
後果：改 → 約 40 個檔、測試約 15 檔，demo 的 `.env` 多數刪掉，`parts.json` 那槽的 `.env` key 可能跟著退場（槽改寫成 argv 陣列）；不改 → 維持 10-31 的 `AOS_` 前綴版，名字不撞但仍是 dyn。也可以只改 lib（器官 16＋工具 7），demo 先不動（demo 是例子，改了也沒人依賴）。

## 問題 4：傳話筒（`AOS_ROUND_AGENT`、`AOS_IVY_BRAIN`、`AOS_IMPROVE_RUN`）要不要為了拿掉它而加機制？

這三個是「上面設、立刻被 `{"$env"}` 塞回 argv」，要拿掉得讓 aos-fsm 的表（或 daemon.json、aos-sandbox 的設定）能接叫它時給的參數。
判準：KISS（C-56）——只有這 3 處就不加機制、留著；如果你想把「argv 裡的 `$env`」整個收緊，才加。
後果：加 → aos-fsm 多一個「表裡引用參數」的寫法（C++ 與規格都要動）；不加 → 這 3 個留著，表上標「傳話筒、刻意保留」。

## 問題 5：`AOS_ENTRY`（入口檔名，一路繼承）要不要拿掉、固定叫 `_entry`？

它正是 dyn 的毛病：上面改了名，底下每一格都要跟著有同名的檔（P-39 已經說巢狀裡不改它），而且現在**沒有任何程式或 demo 設它**。
判準：想不到「整棵樹換入口名」的實際用途 → 拿掉。
後果：拿掉 → aos-exec C++ 4 檔、aos-daemon child、aos-ai 模擬、aos-grow 跟著改，測試 6 檔，aos-exec 規則裡「`.env` 設 `AOS_ENTRY` 有作用、多段 `$AOS_ENTRY`」那幾條作廢；留 → 不動。順帶：沒人讀的 `AOS_CO` 要不要也一起拿掉，可以同一句回。

## 使用者裁定（11-01 晚）

使用者原文（逐字）：

> 1. 不用。2.腦這東西未來會被統一管理，大多agent都是向某個kernel遞送請求，由那個kernel統一向endpoint發起。那塊就到時候再說。倒是可以有個AOS_BRAIN，用於指向那個kernel或之類的。3.啥。4.啥？5.不

第二輪使用者原文（逐字）：

> 3.這就是濫用...除非真的有必要的，否則不要用。4.我聽不懂，我不知道這是啥

決定：
- 問題 1（hub 型算不算必要）：不用改，hub 型照舊、N-63 不動。
- 問題 2（腦的三個變數）：到時候再說——腦之後由某個 kernel 統一管理，大多 agent 向 kernel 遞送請求、kernel 統一向 endpoint 發起；可以有一個 `AOS_BRAIN` 指向那個 kernel（或類似的東西）。
- 問題 3（42 個格自己的旋鈕要不要一次全改）：**改**。使用者定調：這就是濫用，除非真的有必要，否則不要用環境變數。實作已派隊長在 worktree 做（進度見 SESSION-LOG）。
- 問題 4（傳話筒三個）：使用者兩次沒聽懂，頂層第三次改用具體例子重講，待補。
- 問題 5（`AOS_ENTRY` 要不要拿掉）：不拿掉。

### 使用者原文（11-01 晚，第 3 題裁「改」之後連講的，逐字）

> 明明現有的機制組合一下就能搞定，偏偏在那邊亂搞一通

> 幾支小程式，每個都一大堆機制，搞到最後亂成一團

> 一大堆東西根本就是不需要的

頂層當場的處置：這幾句轉給改旋鈕的隊長當指導原則——只用現有機制組合（aos-exec 的 argv、格資料夾裡的檔、既有 `.env`／`$env` 語法）、不發明新機制；每支程式的機制要變少不是變多；能刪的旋鈕先刪、寫死成預設值。「一大堆東西根本就是不需要的」可能牽到更大範圍的瘦身（KISS 批次 2～6 自 10-16 暫停，見 SESSION-LOG），範圍由使用者定、頂層不代開。
