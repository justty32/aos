# PLAN 的洞：對照 restart.md §2 逐條檢查

只讀了 [restart.md](2026-10-11-restart.md)、[9/19 草稿](../../thinking/2026-09-19.md)、[9/23 情境](../../thinking/2026-09-23.md)、[PLAN.md](../PLAN.md)、[a-day](2026-10-11-a-day.md)，proto7-2 只翻 README／spec 目錄／lib 檔頭對照。沒跑程式、沒改別的檔。每條括號裡是依據的 restart.md 節號。

## A. PLAN 哪裡違背或偷渡了使用者的想法

1. **核心認了第二種東西：`in/`／`out/`。** PLAN §3「任務之間只靠寫檔到對方的 `in/`」、§2「stdout／stderr 也落 `out/`」、§7「退出碼落 `out/exit`」、§8 檔名 `<回合>-<序號>.json`＋`"re"` 對應——核心（tick）得知道 `out/` 在哪才能導 stdout；這就是 proto7-2 的 mail 包、proto2 的 inbox／outbox 換名回來（2.8「核心沒有第二種東西」；9/19 只說「丟到另一個資料夾讓另一個 proc 處理」，沒說資料夾長什麼樣）。
2. **核心讀標籤決定行為。** PLAN §8 第 2 點「等多久就是 life 這一軸，核心只認這兩種」——九軸是給排序器／LLM 看的計算性特性（2.9），核心一旦讀 `axes.life`，軸就從「描述」變「指令」，往後每一軸都會想被核心讀。2.11 明說停下來後「正在跑的任務要不要被迫停止？可以，也可以不用」，使用者沒要核心等任何人。
3. **tock「等本回合會結束的任務退出（或到期限）」是 proto7-2 慣例回流。** PLAN §3 第 5 行。這正是 10-04 user-advice 罰過的「等任務都結束就提前 tock」，而且「到期限」接下來就是 kill、就是「是不是同一個 pid」——proto7-2 `lib/aos7_proc.py` 276 行就是這條路的終點（2.11 tick-tock 的本質只是「讓時間停下來」，不是收任務）。
4. **`capacity` 是偷渡的第二種概念。** PLAN §1 表、§2「資源的 task.json 多一個 `capacity: 1`」、§8 第 3 點。使用者說的是「人類輸入這個資源最好也是一個 POSIX 行程……一次只能處理一個，所以資源可能就是三四個 POSIX 行程」（2.8）——容量＝幾個資料夾，不是一個數字欄位。有了 `capacity` 欄位，排序器就得懂它、資源程式就得自己實作它，a-day 的 `llm-local` 改 `capacity 2` 立刻暴露這點。
5. **`axes.needs: ["llm"]` 把「依賴哪個資源」寫成九軸的一軸。** PLAN §2 task.json 示意。2.7 說資源是由任務的某個特定行為（`scanf`）定義出來的；九軸的「資源特性」是計算性特性，不是指名某個資料夾。這一欄一寫，核心／排序器就有了資源名字表。
6. **`belief.json` 是 AI 自己的發明，卻列在「今天說的每一條都對得上」。** PLAN §1 表最後一列、§2 `scheduler/belief.json`。2.14～2.16 說可預測性有主體性，提高它的方法是「把 agent 當 S 表示式拆、節點換成寫死的程式」（2.16 原話「agent 可預測性的提高，就是這一塊」）；沒有任何一句說要把某觀察者的認識落成檔案。這是 restart §3 AI 整理那段推出來的，不是使用者說的。
7. **`steps.json` 進了世界佈局和核心路線。** PLAN §2、§4 第 5 步、§1 表。使用者 2.20：「agent 內部怎麼設計……是後面的事，先把底打好」。`steps.json` 要有人執行，那個執行器就是 proto2 的 `aos-agent`／9/19 的 `inst.json`——又是一套格式與一支程式。第 5 步「數節點」的精神對，但它是 agent 的事，不該在 proto8 核心階段定格式。
8. **`traits.priority: 3` 把排序結果寫成標籤。** PLAN §2。2.2：「算出誰優先級最高，本身就是一套新的排序演算法」——優先級是排序器算出來的，不是人填的。
9. **`.aos/` 自相矛盾。** PLAN §2 註「只有核心寫」，同一張圖 `order.json` 是排序器寫的，a-day 還有人去 `touch .aos/snapshot`。小事，但顯示「核心的本子」邊界沒想清。

## B. PLAN 漏掉使用者說的什麼

1. **§5 五題全是行政題，使用者真正留白的設計題一題都沒問。** restart §4 列了「資源怎麼宣告、排序程式怎麼掛、生成排序程式的程式長怎樣」，2.5 第 3 層「還沒展開，使用者說要先回頭看一下」。PLAN §2 用 `capacity`、`.aos/order.json`、「我手寫→模型生成」直接把三題答掉，然後問他「用哪個模型、proto7-2 怎麼放」。這違反 AGENTS.md 鐵律 5（大方向是使用者的）。
2. **2.4「到底有多任意」沒有任何一步去試。** §4 六步只有一種資源（llm）、一條規則（照 traits 分／便宜優先）。2.3 畫家例子裡有「畫四五張就想散心、隔一週再回來」——資源可用性隨時間變，PLAN 的 `human/` 整天沒出場（a-day 疑問 3 自己承認），第二種資源從頭到尾沒進 demo。
3. **2.10「生成排序程式的程式」不見了。** PLAN §4 第 4 步「再讓模型照同一批檔案生成一版」——是誰在聊天視窗叫模型，不是世界裡的一個計算任務。照 2.8，生成器本身也該是個資料夾。至少要寫明「這次由 AI 在外面做，生成器任務化是以後的事」。
4. **2.11「agent 可以說把 tick-tock 停下來」、2.12「我要看某個 tick 底下的世界」——發起方是 agent，PLAN 給了人。** §2 snapshots、§4 第 6 步、a-day 睡前 `touch`，都是人在做；agent 怎麼要求停、怎麼讀舊 tick 的世界（讀側），一字沒有。
5. **2.18「哪些人類使用者想先看哪個 agent 的回覆」——人類注意力是排序輸入。** PLAN 排序器只看 `in/` 件數與 traits。使用者說「我現在想先看 painter-b」要往哪寫，沒有位置。
6. **2.19「這個 agent 什麼時候該跑變成要排程的事」——「不跑」怎麼表達。** PLAN §3 `order.json` 只定義先後；「這回合不起某人」是不是把它從表裡拿掉？沒寫（見 C-6）。
7. **2.5 第 1 層 daemon 整層消失。** PLAN §3 把「daemon 每 N 秒 tick 一次」當註腳，§7 說「權限、身份、掛載以後再接」。可以延後，但 PLAN 的 tick 已經在做行程管理（procs.json、起 argv、等退出）——那是使用者分給第 1 層的事（2.5「行程……最好都在這一層」）；至少要寫一句「這支 200 行是 L1＋L2 合著寫，日後拆」。
8. **2.6「自省」沒有 demo。** 六步裡沒有任何一步讓 agent 自己 `ls` 世界、讀 `.aos/tick.json` 或自己的 `out/`。LLM 好處理是整套的立論（2.1 末、2.6），卻只有人在自省。
9. **9/23 情境的開頭沒了。** 使用者自己寫的一天從「`aos-agent init <template>`、`register`、`say hello`」開始；a-day 和 PLAN 的 painter-a 憑空存在，沒說一個新 agent 資料夾怎麼生出來（task.json＋run.py＋prompts/ 誰寫）。

## C. §3 的 tick 一支 ≤200 行真做得出來嗎

**做得到，但前提是 A-2、A-3 那兩段拿掉。** 「等退出＋期限＋殺＋判 pid 是不是同一個」四件事加進來就是 proto7-2 `aos7_proc.py`＋`aos7_task.py` 的 600 行。只做「round++、讀 order、起沒在跑的、寫 tick.json、旗標→zip」約 120～150 行純標準庫。寫下去一定會碰到、PLAN 沒提的決定：

1. **誰算任務。** 掃 `world/` 一層還是遞迴？`.aos/` 排不排？→ 只掃一層、只認有 `task.json` 的直接子資料夾，其他全不理。
2. **「沒在跑」怎麼判。** 讀 `procs.json` 的 pid 再 `kill -0`？pid 重用？→ tick 是**一個長跑行程**，自己 `Popen`、自己 `poll()`，不落 pid 再讀回；`procs.json` 只是寫給人看。代價：tick 重啟後舊子行程變孤兒照跑、下回合可能起第二份——接受，寫進 README。
3. **等不等。** → 不等。回合＝固定 N 秒（user-advice 10-04 要固定 interval）。跑超過一回合的就是「還在跑」，下回合不重起，就這樣。
4. **期限與殺。** → 不做。人用 `kill`；排序器想殺也用 `kill`（它是行程，有權）。
5. **stdout／stderr 去哪。** → 繼承 tick 的（demo 就是看螢幕）。要留日誌是任務自己 `> log` 的事；核心不認 `out/`。
6. **`order.json` 是排序還是選擇；過期怎麼算。** → `{"round": R, "run": [...]}`，tick 只起表裡的；`round` 不是上一回合就當沒有、起全部。排序器漏掉自己 → 下回合表過期 → 全起 → 排序器復活，不用特判它。
7. **`.aos/` 誰能寫。** → `tick.json`／`procs.json`／`snapshots/` 核心寫；`order.json` 誰都能寫（人手寫一份也是特性）；PLAN §2 註解照改。
8. **任務怎麼找別人。** → `$AOS_ROOT/<名字>/`，環境給 `AOS_ROOT`、`AOS_ROUND` 就夠，不再加。
9. **兩個任務同回合寫同一個資料夾，檔名撞、半檔被讀。** → 一句慣例寫在 README 給任務作者：檔名含自己資料夾名，先寫 `.tmp` 再 rename。核心不管。
10. **退出碼。** → 核心不記，tick 的 stderr 印一行 `painter-a exit 1`。
11. **處理完的輸入誰刪。** → 讀的人刪，處理完就刪（10-04「垃圾要定期清」）。寫在 README，不是核心。
12. **snapshot 哪一刻 zip。** → tick 開頭看到 `.aos/snapshot` 旗標：這回合不起任何人、zip（排除 `.aos/snapshots/` 自己）、刪旗標；正在跑的照跑，zip 裡就含「這件事正在跑」（2.11）。
13. **round 計數器重啟後接續。** → 起步先讀 `tick.json` 的 round。
14. **`task.json` 壞掉或 argv 起不來。** → stderr 一行、跳過、不寫任何東西。
15. **兩個 tick 同時對一個 world。** → 不管（§7 已說不上鎖），README 一句「一個 world 一個 tick」。

## D. §7「不做」清單哪幾條會在第 2～4 步被逼著做

1. **「上鎖、並行」——第 3 步就來。** 兩個 agent 同回合並行、都寫 `llm/in/1833-1.json`：撞名＋半檔。不會真的上鎖，但 C-9 的檔名慣例＋原子寫就是它的最小形態；不先寫下來，第 3 步 demo 會莫名少一件。
2. **「退出碼契約、error_path」——第 3 步。** llm/ 呼叫失敗（金鑰錯、超時），agent 下回合讀 `out/` 要分「還沒回」和「失敗了」——回覆 JSON 就得有 `error` 欄；加上 §8 的 `"re"`，這已經是一份協定。§7 自己寫的 `out/exit` 也是契約。
3. **「崩潰恢復、once 保證」——第 3 步，在 llm/ 裡。** agent 是 per-tick 重起的，它得記「我已經問過、在等 1833-1」→ 要狀態檔；llm/ 若在呼叫後、寫回覆前死掉，請求還在 `in/`，下回合重打一次＝重複扣錢。「先搬走再呼叫」就是 once，誰寫 llm/run.py 誰會被逼寫它。這是 budget／grant 的縮影——放任務裡是對的（2.9 冪等是標籤上的事），但 PLAN 要承認第 3 步會寫到。
4. **「監督者 kernel」——第 4 步。** 第 3 步只要丟過一次回覆，agent 就永遠等；§7 說「排序器看 procs.json 和 out/ 就知道誰卡住」，那第 4 步那 30 行排序器就得含這條規則，否則 demo 會卡住給使用者看。
5. **「信箱包」——第 3 步，換了名字。** `in/`＋`out/`＋`re`＋檔名規則＝信箱。不是不做，是沒叫它信箱。
6. 帳本、權限／身份、1444 測試：前四步不會被逼。

## E. 日記裡哪些動作使用者實際不會做、或做了會煩

1. **`echo … > painter-a/in/1832-1.json`——人不會先 `cat tick.json` 查回合號來替檔案取名。** 他會寫 `in/want.json`。檔名規則漏到人身上就是煩；給人的入口檔名任意。
2. **一張畫等 3～4 個 tick（15～20 秒）、每問一次模型多兩回合。** 日記的 1833→1835 其實少算一回合（排序器寫的表是給下一回合用的）。agent 三步就是五回合起跳；他 10-04 說「每回合產新資料夾我的老天」，這裡是每回合產新檔案而且沒人清（a-day 疑問 2 自己承認）。
3. **`cp -r llm llm-local` 會把 `in/`、`out/`、`usage.json` 整包複製。** 下一回合 llm-local 把舊請求再答一遍、painter 收到兩份回覆。使用者會覺得「我只是想多一顆 GPU」。另外他改的 `model` 欄位在 §2 的 task.json 裡根本沒有。
4. **需求丟兩個地方（painter-a/in 或 scheduler/in），而且丟給 scheduler 的檔會被搬走。** `ls scheduler/in/` 空的，他會問「我的檔去哪了」。
5. **改 `steps.json` 把 llm 換成 `understand.py`——日記寫得像改一行 JSON，實際是寫一支 Python。** 而且這是 agent 內部（2.20「後面的事」）。
6. **睡前 `touch .aos/snapshot`——打包的價值是給 agent 看「某個 tick 的世界」（2.11、2.12），人睡前要備份會直接 `zip -r`。** 把這動作給人，等於沒展示它真正的用途；還違反 §2「.aos/ 只有核心寫」。
7. **「整天沒用一個 aos 指令」是過度矯正。** 使用者 9/23 自己寫的一天是 `aos-agent init <template>`／`register`／`say "hello"`——他**要**指令，要的是少而順手。日記裡 painter-a 的 task.json、run.py、prompts/ 憑空存在；真用起來第一件事就是手刻這三樣，他會煩。
8. **`traits.priority: 3` 要人填**——填 3 是什麼意思、跟 1 差多少，使用者不會知道（A-8）。
