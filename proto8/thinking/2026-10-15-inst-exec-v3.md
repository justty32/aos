## 原文（這次，10-15 深夜，照貼）

看完第二版未決 A：「我希望是aos-exec TARGET 旗標 -- argv。frame.json是啥小？怎麽會亂寫一堆檔案？aos-exec的功能邏輯怎麽這麼醜？沒去看規範嗎？整套都給我重新思考」

先前的原文（10-15 晚，照貼，第二版已收）：

- 場景：「我現在有個 /home/a/workspace/ 資料夾，然後有 /home/a/agents/bob/ 資料夾，然後我會 cd 到 workspace 資料夾，然後跑 `aos-inst ../agents/bob`」「拿 ../agent/bob 作爲函數呼叫，讓他在 ./ 工作，然後我又不想碰環境變數」。
- 規範重申：「當初的規範定下來，就是說 stdin 作爲標準輸入，inst.json 的內容就是走 stdin 進去，這是標準使用，命令行是要空出來的」。
- 流程：「aos-inst 從 stdin 讀到一份 json 後，他就是先按照 aos-inst 自己的 cwd，去解指示詞（$ref/$env），然後是根據解出來的東西，同樣根據 aos-inst 自己的 cwd 去把 stdin/out 等檔案路徑定下來，然後要真正執行之前，再去將 cwd 切到指定的 cwd 路徑。」
- 「從 stdin 來，其實更像是在 workspace 中創造一個叫做 inst.json 的檔案，然後將內容交給 aos-inst 這樣。然後 aos-inst TARGET 這樣的用法我覺得應該拿掉，就是完全從 stdin 來就好，要用 aos-exec TARGET 作爲語法糖。」
- 「首先 $ref 確實應該用該檔案所在的位置開始算」；symlink：「捷徑我覺得他更像是一個懶得每次都 copy 過去的方法，所以就是從 symlink 所在開始算。」；「TARGET 這東西都拿掉。」；「aos-tree 我覺得可以先刪掉」；「$abs_path 真的有必要嗎？我覺得不用吧」。
- 約束（[C-48 原文](2026-10-15-json-families.md)）：「不要把指示詞納入正規設計……設計中對此的認知只要有『自己的一些檔案可以透過指示詞拆成小檔』這樣就好，不要依賴她。」

## 前提（使用者 10-15 深夜追加的兩條，本稿每一條都要過這兩關）

1. **KISS 納進最高原則**——徹底的純淨簡潔（[原則稿](2026-10-15-principles.md)、C-56）。
2. **層要徹底切割**：「agent他就是看到自己的工具，工具在幹嘛他就不管，拜託，乾淨，完全切割，徹底切割，不得有任何殘留。」「想要看子層的東西請另外透過其他機制，沒機制就別碰。」所以 agent lib **不能知道某個工具是 agent**；工具就是一張 inst，裡面怎麼叫 bob 是工具自己的事（「tool 步驟認資料夾、開 work/、寫 frame.json」違反這條，不採）。

## 已定（使用者拍板，同第二版，不重開）

1. `$ref` 的相對檔名從**那個指示詞所在的檔**的資料夾算（`dirname(abspath(檔))`，**不解 symlink**）；stdin 那份＝當成 cwd 裡放了一份 inst.json，基準＝cwd；Python 傳 dict 基準＝呼叫者 cwd；取回來的東西裡再有 `$ref`，從被取的那份檔算。
2. inst 的 `cwd`、`stdin`／`stdout`／`stderr`／`exit` 一律從 aos-inst 自己的 cwd 算；`cwd` 只決定子程式在哪跑。沒寫 `cwd`＝子程式在呼叫者站的地方跑。
3. **aos-inst 拿掉 TARGET，設定只從 stdin 來**（N-12 標準用法；命令列空出來）。
4. **`aos-exec TARGET` 是語法糖**，給人用。
5. **TARGET 全拿掉**：命令列的（inst／loop／daemon／fsm／gate）與 JSON 裡寫的 TARGET 字串（daemon `children`、閘門 `target`、kernel 的 gates／judges、fsm 的格、tasks 的 argv）。替代＝**內嵌 inst 物件**（同像性，`(daemon (fsm b c))`）；要拆成小檔就 `$ref`，那是拆檔便利、不是機制。
6. 刪 aos_tree；`$abs_path` 不做；呼叫機制不靠指示詞、不靠環境變數。

## 從規範推出來的 aos-exec（結論）

第四版照抄，只把 TARGET 改成必填（第四版已定 1）。

```
aos-exec TARGET [--key 值 ...] [-- argv...]
```

aos-exec 是 inst 這一層給人用的糖（N-21～N-24、N-35 的 TARGET、`檔#/位置`、資料夾找 inst.json、鏡射旗標、`--` 整包搬進來），不知道 agent、frame、loop，不寫任何檔。步驟：

1. TARGET 切 `檔#/位置`（N-35 的切法不變）。檔是資料夾＝找 `<資料夾>/$AOS_DIRNAME/inst.json`，沒有再找 `<資料夾>/inst.json`。
2. 讀那份 JSON，解指示詞——基準＝那份檔所在的資料夾（已定 1），`#/位置` 指到的那格仍是整份檔的視窗。
3. 旗標蓋 key（N-22 鏡射，N-23 旗標＞檔）、`--` 蓋 `argv`（N-24）。
4. 得到的那張 inst 交給 aos-inst 跑；結果（N-30）與錯誤（N-29）原樣就是 aos-exec 的 stdout／stderr、退出碼照 N-43（aos-exec 自己只多三種錯：`ArgumentsBad`、`InstMissing`、指示詞的錯）。

不 cd、不寫檔、不讀自己的 stdin 當設定、不認得 agent。

## 第四版照推薦定案的未決（B、E、I、J、K、L）

使用者答第三版未決時說「剩下都按照推薦」（原文見[第四版](2026-10-15-inst-exec-v4.md#原文這次10-15-深夜照貼)）；A、C、D、F、G、H 另答或重推，見第四版。

- **B.** aos-exec 同行程跑 `aos_inst.run(dict)`，不另起 aos-inst 行程：aos-exec 自己的 stdin 沒被設定用掉，inst 寫 `stdin_inherit` 就能接到終端機或管線（`echo hi | aos-exec x.json -- cat`）；N-26 的 Conflict 只在設定真的從 stdin 來時才發生。
- **E.** frame.json／`parent` 鏈退場：C-46 的「找名字往上找」那句拿掉，frame＝cwd；`aos_frame.py` 的 `chain()` 退場，`lookup()` 只剩「cwd 的檔 → stdin 那份」。
- **I.** 旗標與 `--` 只在 aos-exec：aos-inst／loop／daemon／fsm／gate 命令列零引數（多給＝`ArgumentsBad`）；`-` 與「都沒給＝`{}`」退場。人要從檔起 loop／daemon／fsm：`aos loop < loop.json`；不站在那個資料夾就包一張 inst 給 aos-exec。
- **J.** Python 的 `run(x)`（N-25）：`aos_inst.run(dict)` 只收 dict（基準＝呼叫者 cwd）；路徑形改 `aos_exec.run(target, flags=None, argv=None)`。
- **K.** 閘門的信把呼叫者 stdin 寫成旁檔 `reply/<名>.stdin`：這輪不動，等 kernel 那條線再收。
- **L.** `_schema`、`_tool` 等私有 key 裡的路徑只是資料，不進規範；要程式幫忙就 `{"$ref": "schema.json"}`。
