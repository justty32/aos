## 0. 使用者原文（打字，去贅字）

1. proto8 這塊，我有些想法：我會覺得，json 本身也是一個檔案系統，他幾乎可以無縫銜接檔案路徑，比如 `inst.json#/argv/0` 這樣。考慮到 `#` 在檔案路徑中也是合法的（只是說在 shell 中可能不太友好），其實我們的 `aos-inst xxx`，那個 xxx 也是可以支援這套。所以 loop.json 的格式那塊，可以把 inst 放到頂層，然後 loop 相關的放到 `"loop"`。
2. 接著丟了一份檔試單檔自指：`{"argv":["aos-loop", {"$env":"AOS_INST_SELF"}], "loop":{"interval_ms":1000}}`
3. 修正：應該是 `"argv":["aos-loop", {"$ref":{"$env":"AOS_INST_SELF"}, "$at":"loop"}]`
4. damn... 可能最後還是要兩個檔案：1. `{"argv":["aos-loop", "loop.json"]}` 2. `{"interval_ms":2000, "inst":{...}}`
5. 對 AI 列的三條的回覆：「1. 要，這個很便宜方便。2. 這個會不會太…感覺沒必要，因為在程式實作的時候，那個資料結構還是現在這樣會比較直觀。3. 不要。」
6. 不要做，都先記下筆記。我們現在是討論環節。

## 1. 決定（2026-10-13）

- **D1 命令列 TARGET 支援 `檔#/位置`**（aos-inst／aos-loop 的 TARGET、`run(path)`、daemon 指令裡的 id）：跟指示詞 `$ref` 同一套寫法（`#` 後面是 JSON pointer）。使用者：「要，這個很便宜方便。」**已做**：照 §2 的預設做進 [proto8/lib](../lib/README.md)（`aos_directives` 的 `split_target`／`target_id`／`locate`、`resolve(at=)`）。
- **D1a `#/` 統一成檔案系統的寫法**（10-13 晚，家機）：命令列與 `$ref` 用同一套——`#`、`#/`＝整份，結尾 `/` 與空段落忽略（`/a/`＝`/a`）；代價是名字是空字串的 key 指不到、跟 JSON pointer 標準差一點。使用者在「照檔案系統／照 JSON pointer 標準」兩案中選「甲」（照檔案系統）。已做。
- **D2 loop.json 排法不動**：維持 inst 包在 `"inst"` 格、節奏在外層。理由（使用者）：程式實作時資料結構現在這樣比較直觀。「inst 放頂層、節奏收進 `loop`」的提案收回。
- **D3 不做 `AOS_INST_SELF`**（aos-inst 塞「我正在跑的這份 inst 的路徑」環境變數）。使用者：「不要。」

## 2. 結論（討論後）

- **單檔自指是套娃**：inst 的 argv 寫成「aos-loop 自己」，aos-loop 讀到的 inst 又是「aos-loop 自己」，每層等下一層、沒有一層跑完第一次，程序鏈無限長。要讓單檔成立得拼出 `<自己>#/job` 這種字串，現在的指示詞沒有拼字串的（`$ref` 是取值不是給路徑，`$at` 要 `/` 開頭，指示詞不能巢狀），得發明新東西。最後定**兩個檔**：一份啟動單子 `{"argv":["aos-loop","loop.json"]}`、一份 loop 本體。這是 Unix 慣常的形狀，不用加任何新功能。
- **兩個檔的坑**：啟動單子裡的 `"loop.json"` 是相對路徑，照現有規矩從呼叫者的 cwd 算，不是從啟動單子所在的資料夾算。在別處 `aos-inst /x/start.json` 會找不到。解法：單子寫 `cwd` 或寫絕對路徑。**規矩不改**。
- **D1 實作時的預設**（AI 提出、使用者沒回應，照 [user.md](../../wf/workflows/common/user.md) 沒回答的邊緣狀況通則留著供實作時參考，不追問）：
  - 遇到第一個 `#` 就切，檔名含 `#` 的不支援。
  - 命令列的位置只認 `/` 開頭，空的＝整份。
  - id＝realpath 加 pointer；沒 pointer 或 `#/` 就是純 realpath（同一份檔兩個位置＝兩個 id）。
  - 指到的值不是物件就報錯。
  - 指到的那塊裡面的 `$ref` 可以用 `../` 往外摸到旁邊的東西（是視窗不是切下來），照留。
  - TARGET 是資料夾時，先照現有規矩找 inst.json 再套位置。
- **順帶**：有了 `檔#/位置`，一份 JSON 可以放好幾個 inst（如 `node.json#/clock`），要不要這樣用沒定。

## 3. `_metainfo`（10-13 第二段）

> 一樣只記筆記，沒動程式。

### 使用者原文（打字，照記）

1. 「路徑這塊就這樣。然後，我會希望添加一個 _metainfo key，在 inst 格式中。先前有提到說所謂的函數九軸，我們可以在這裡定義。也包括資源特性啥的。」
2. 「_metainfo 這塊，我的概念是，這是一個在 aos 體系中，被 aos inst 和相關標準實作所忽略的東西，它的作用是在後續 kernel 規劃時，提供參考。_metainfo 中所表述的，就是這個 inst 跑下去後的特性。我是覺得啦，我們的初衷之一，就是把 linux 檔案系統變成 lisp，而對一個 list 求值，我們就是統一用 aos inst。」
3. （AI 問後面是不是還有話）「沒，只是說，這是很適合用來作為 kernel 的參考。」
4. 「早期在 ai_core 中，我就有提出一個概念，就是說，對於靜態的，空間上的變化，我們有檔案屬性描述，描述他佔用了多少空間（kb、mb），還有他歸屬於誰，其特性如何（副檔名）。但是函數，這種動態變化，我們缺乏描述他性質的一些東西。」

### 決定（D4）

- inst.json 加 `_metainfo` key。意思＝「關於這個 inst 跑下去會是什麼樣子」的描述：九軸（C-13：I/O 型態、生命週期、跨呼叫狀態、資源特性、可中斷性、執行保證、組合模式、環境模式、確定性）、資源特性、乃至其他特性。這就是 `_metainfo` 的由來：檔案有 `ls -l` 那排屬性，函數沒有；`_metainfo` 就是函數的那排屬性。
- **aos inst 與所有標準實作一律當它不存在**（N-04 那個抽屜的固定名字）；它是給之後 kernel 做規劃時參考用的。
- **還沒動工**（使用者說先記筆記）。
- 跟 10-12 的關係：10-12 說「不做 _metainfo」指的是 proto7-2 那個「這份 inst 是哪種格式、第幾版」（`_type`／`_version`）的 `_metainfo`，那個仍然不做；10-13 的 `_metainfo` 是另一個意思。
- 來源：CONCEPTS C-13、C-14、C-42b；九軸逐軸套到 aos 的表在 [proto7 axes-astra](../../proto7/notes/thinking/2026-10-04-axes-astra.md)；ai_core 原文 `~/repo/ai_core/docs/kb/kb-ss/doc_05_axes_metadata.md` 在家機，公司機沒有。

### 3.2 格式（10-13 晚，家機）

AI 起草了九軸 key／值表與六題給使用者選（三格分法、資源寫法、跟 inst 欄位重疊、包別人的 inst 誰寫、沒寫的軸算什麼、版本號；草稿只在對話，不留）。

#### 使用者原文（照記）

「_metainfo 裏面的格式，是自由的，但是我們會規定一些通用的東西。資源表示方式也是自由的，在我們的通用規範中會規定一些東西。跟 inst 已有的欄位重疊？管他呢。_metainfo 是跟 inst 格式綁在一起的，他是可選的 key，地位跟 argv 那些等同，但是可選。所以是在 inst 那格裏。雖然說是自由的，但我們後續在做通用 kernel 的時候會做一些大家常用的東西。」

#### 決定（D5）

- **格式自由**：`_metainfo` 裡面寫什麼不限；通用規範（NORMS）之後會規定一些通用的東西。不預先分格。
- **資源表示也自由**，通用規範之後規定一些。
- **跟 inst 已有欄位重疊（如 `timeout_ms`）不管**。
- **`_metainfo` 是 inst 格式的一部分**：可選的 key，地位跟 `argv` 等同。所以 loop 的情況放在 loop.json 的 `"inst"` 格裡（跟著那份 inst 走，不放啟動單子或 loop.json 頂層）。
- 常用的寫法等之後做通用 kernel 時再整理出來。
- 包別人的 inst（seq／loop…）的 `_metainfo` 自報還是由內層推、沒寫的軸算什麼、要不要版本號：使用者「那些都是自由的，後續再說。」

### 3.1 函數屬性能拿來做什麼（10-13 第三段）

#### 使用者原文（照記）

- 「想想看，作業系統可以針對檔案屬性，去做一些其他的各種各樣的事情。那麼函數屬性呢？」
- 「就是要自報的契約。因為同一個 posix 呼叫，在不同環境下進行，其行為也會不同。剩下你說的這些就先記下來。」

#### 結論（使用者定）

`_metainfo` 是**作者自報的契約**，不是量出來的事實。原因：同一個 POSIX 呼叫換個環境，行為就不同，沒有人能替它量。kernel 拿它當參考。

#### 對照表（AI 推演；使用者說先記下來，哪幾條真用上等 kernel 做規劃時再看）

| 檔案屬性 → 作業系統拿來做什麼 | 函數屬性（`_metainfo` 的軸）→ kernel 可以拿來做什麼 |
|---|---|
| 權限（誰的、可不可以執行）→ 能不能動 | 能碰哪些資料夾、能不能碰外部（對應 N-02）→ 起它之前就擋、或給受限環境 |
| 大小 → 配額、放不放得下 | 資源特性（要幾格 CPU、記憶體、端點額度）→ 准入、排隊（排序程式） |
| 型別（副檔名、magic）→ 用什麼程式打開 | I/O 型態（吃什麼、吐什麼、一包或串流）→ 接管線、判斷誰的輸出能餵誰（組合模式的相容檢查） |
| 修改時間 → make 要不要重建、rsync 要不要傳、快取要不要作廢 | 確定性 → 確定的同輸入不重跑、結果可快取可重播；不確定的永遠不快取 |
| immutable、noexec 這類旗子 → 政策 | 可中斷性、執行保證 → 騰資源時先停「可安全中斷」的；失敗時冪等的直接重試、不冪等的先查做到哪 |
| 掛載點、在哪顆碟 → 放哪裡 | 環境模式（需要哪些掛載、哪台機器）→ 派到哪個 node |
| `find`／`ls` 按屬性篩 | 屬性統一後查詢免費：「列出所有在跑的非確定性服務」「找出所有會寫外部的任務」 |

#### 順帶（AI 提、使用者沒回應，留著）

自報的契約之外，kernel 可以事後補量（跑過幾次、花多久、用多少資源、同輸入是否同輸出），那會是另一份「實測出來的」。自報的給規劃用、實測的給驗證用；要不要做、放哪沒定。
