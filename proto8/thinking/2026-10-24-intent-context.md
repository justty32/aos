## 使用者原文（逐字，10-24）

前文：

> 然後我這邊有不少想法，都麻煩你試着去思考去實作。我隨便說，你隨便做，反正只是嘗試

> 我現在沒空管這些小事，都按建議做

> …agent說想要看某些json，那就是給他json頂層，他說想看特定key，再逐一給他看細節。修改的時候也是，AI可以一次生成一大堆函數，也可以一次生成一個值。這就需要用到小念頭概念，也就是拆成"找到要修改的key"->"提供值"

本題：

> 對，因爲現在history.jsonl就是一直累積，但問題在於那太多冗餘資訊了，我希望AI能夠按照意圖去做

## 決定

- 使用者 10-24「都按建議做」：下面的細節都是照推薦定、**可翻案**。
- 做法定為**混合**：程式先照字面挑（便宜、不多叫一次腦），不夠時腦自己用 `recall` 工具漸進展開。另外兩種（只靠程式挑、只靠腦要）列在文末選項。

## 結論（照推薦定、可翻案）

### 1. 分兩層：原始紀錄照存，給腦看的另外組

- **原始紀錄**：`$AOS_STACK/history.jsonl` 跟 agent-dan 一模一樣（一行一則 OpenAI message、只附加、不改寫、不刪；P-41）。所以 say／listen 的 `--trace`、人工追查都照舊。
- **工作 context**：每次 think 問腦前現組一份，不存（組了什麼記一行到 `$AOS_STACK/context.jsonl`：哪幾題被展開、為什麼、粗估 token、整份全送的話是多少）。
- **一題**＝從一則 user 開始，到一則沒有 `tool_calls` 的 assistant 為止。中間的工具來回（叫了什麼、工具原始輸出、中間嘗試）是**過程**，最後那則 assistant 是**結論**。舊題回到主線只帶「問題＋結論」，過程留在原始紀錄裡（「小念頭」的意思用在題的粒度上：做事時的冗長過程不回主線）。

### 2. 工作 context 長這樣（由上到下）

1. `system.txt`（核心人格，同 dan，不進 history）。
2. **先前對話的目錄**：一題一行 `#N 問：前 40 字 → 答：前 60 字（用了 read）`，最多列最近 50 題，更早的只說「還有幾題，用 recall 找」。這是漸進展開的第 0 層。
3. **記憶庫**（有接才有）：見第 5 點。
4. **挑出來的舊題**：照時間順序，每題一對 user／assistant（問題原文＋結論，結論超過 800 字截斷、註明用 recall 看全文）。
5. **這題到目前為止的完整訊息**（含這題自己的 `tool_calls` 與工具結果，不然 OpenAI 的工具協定接不上）。

### 3. 「按意圖」怎麼挑（程式，零額外呼叫）

- **上一題**：一律展開。
- **指代詞**（剛剛、剛才、上一、上個、前一、上次、前面、之前、那個、那題、這個、它）：再加上上一題的前一題。
- **「第 N 題」「第三個」**：展開那一題（阿拉伯數字或一～九十九的中文數字）。
- **字面重疊**：問題跟每題（問＋答）比，英數詞＋中文兩字一組，重疊 ≥ 2 的取最多兩題；超過一半的舊題都有的字不算（題數 ≥ 4 才扣）。
- **不夠的時候腦自己要**：`recall` 工具（`tools/recall/`）——`search` 用關鍵字找舊題（回目錄格式的幾行）、`read` 展開一題的問與答、`detail=true` 連當時叫的工具與工具原始輸出一起看（每段最多 3000 字）。這是第 1、2 層。
- **短的時候不挑**：整份 history（加 system）粗估 ≤ 1500 token（`KAI_FULL_UNDER`）就照 dan 全送——短對話挑了反而貴，也不會漏。

### 4. 摘要：不另外做

- 結論＝腦的最後回答原文；目錄那一行是程式截字。**不叫模型做摘要**（多一次呼叫、會失真，而且結論本來就短）。
- 代價是結論沒寫到的細節不會留在主線：`system.txt` 請腦「回答裡把關鍵的數字、名稱寫完整（之後只會留下你的回答當這題的結論）」，不夠時靠 recall 或重新用工具查。

### 5. 跟其他嘗試接軌

- **pi-tools 的 read**：`tools/read` 是連到 `demo/pi-tools/read` 的符號連結（同 agent-pip 的做法）。
- **agent-meg 的記憶庫**（[thinking 10-24 memory](2026-10-24-memory.md)）：kai 本身不帶；放一個 `tools/memory` 連到 `demo/agent-meg/tools/memory`、記憶庫在（`$AOS_HEAP`，沒設＝`$AOS_WS/.heap/`）時，brain 每題用它的介面（`aos-exec tools/memory`，stdin `{"op": "search", "query": 題目, "limit": 3}`）找相關幾筆附進 system（不進 history），腦也能自己 save／search。只用介面、不 import meg 的程式。
- **小念頭（agent-gus，[thinking 10-24 thoughts](2026-10-24-thoughts.md)）**：沒接。kai 是在「題」的粒度把過程收掉；要把一題裡的冗長步驟丟出去，接法是加一個工具資料夾，`_entry` 轉 `AOS_STACK=<小格> aos-exec <agent-gus>/thought.json`（stdin `{goal, context, needs}`、stdout 只有結論），主線就只收到那段結論。
- **JSON 漸進展開**（[thinking 10-24 aos-json](2026-10-24-aos-json.md)、`demo/file-tools/view`）：那兩樣對的是「檔」（`檔#/指標`、`view` 照 pointer 一層層看），history 是 `.jsonl`、而且要先切成題才有層次，所以沒直接用。`recall` 是對 history 的最小替代，形狀照同一個想法（目錄＝頂層、read＝看某一題、detail＝再往下一層）。之後接法：把切好的題寫成一份 JSON（`turns` 陣列，每題 `question`／`answer`／`tools`／`steps`，放 stack 裡），recall 就換成 `view` 指著那份檔「先看頂層、再看某 key」。

### 6. 名字（C-54）

| 名字 | 一句白話 |
|---|---|

| `KAI_FULL_UNDER` | 整份粗估 token 在這以下就全送（預設 1500） |

recall 的錯：沒設 `RECALL_HISTORY`＝`HistoryMissing`、紀錄壞了＝`HistoryBad`（退 1）；模型的錯（op 不對、沒這題）照實回給它、退 0。agent-kai 其他錯誤代號全同 agent-dan。

## 代定（「都按建議做」，可翻案）

1. 混合：程式照字面先挑、腦用 recall 要更多（不另叫一次腦判斷意圖）。
2. 舊題只帶問題＋結論，過程留在原始紀錄；這題自己的過程照原樣帶。
3. 不做摘要：結論＝回答原文（800 字截）、目錄行＝程式截字（問 40、答 60）。
4. 挑的規則：上一題一律、指代詞加上兩題、第 N 題、字面重疊取最多兩題（≥ 2）。
5. 整份粗估 ≤ 1500 token 全送（`KAI_FULL_UNDER`）。
6. 目錄最多 50 題；recall 的 detail 每段 3000 字。
7. recall 讀哪份紀錄用環境變數 `RECALL_HISTORY` 指（不讓工具自己往上找呼叫者的 stack，C-52）；act 給每個工具都帶這個變數（簡單，沒用到的工具忽略）。
8. 記憶庫是選配：放 `tools/memory` 才接；每題自動 search 3 筆附進 system。
9. 名字 `agent-kai`（demo 用人名，`agent-ivy` 已被 kernel-llm 的 demo 用掉）。
10. token 粗估：英數 4 字 1 個、其他每字 1 個。

## 邊緣狀況

- **挑錯意圖、漏掉關鍵上下文**：字面比對對同義詞無力（「房間號碼」對「房號」、「小動物」對「貓」）；目錄每行截字，關鍵資訊在句尾就看不到（第 13 題）。沒有 recall 就答錯；有 recall 也要腦「知道自己不知道」——真模型可能直接猜（system.txt 有叫它別猜，但沒驗過）。
- **摘要失真**：結論只是回答原文，回答沒寫的（文件其他段、工具輸出裡的其他欄位）就不在主線；腦回答寫得越省，後面越要 recall。結論本身寫錯，之後每次被展開都在傳播錯誤（原始紀錄沒錯，但沒人會回頭看）。
- **「剛剛那個」指代**：「剛剛」＝上一題或上兩題，規則能接；「前天說的那個」「你一開始講的」這種跨很遠、又沒字面線索的，只剩目錄與 recall。「它」「這個」很常見，常常白白多展開一題（多花 token、不會錯）。「第 N 題」的 N 是整個 stack 從頭數，換 stack 就重編；使用者心裡的「第三題」可能是今天的第三題，不是這個 stack 的。
- **成本反而變高**：短對話（固定開銷 ＋400／次，靠 `KAI_FULL_UNDER` 擋）；要用舊過程細節的題（約 2 倍）；**供應商的 prompt cache**——dan 每次的前綴都一樣（只在尾巴加），快取命中率高、實際計費可能便宜很多；kai 每次組的前綴不同（目錄會長、展開哪題會變），幾乎吃不到快取。這點假腦量不到，要等真跑看帳單或 `usage` 裡的 cached tokens。
- **目錄自己也會長**：一題一行，50 題約 3K token；更早的只剩 search。題目很多時目錄本身就是新的「太長」。
- **題沒答完就失敗**：照 dan，題目留在 `cur/`、history 停在那題中間；重跑時「這題」的範圍仍從最後一則 user 算，沒有問題。手動往 history 塞了不成對的訊息（只有 user 沒有結論）會被當成「這題」的一部分。
- **記憶庫與目錄重複**：同一件事在記憶與舊題各出現一次，白花 token；兩者衝突時（記憶過時）腦要自己判斷。
- **recall 看得到整份紀錄**：包括當時工具讀過的檔內容；工具輸出裡有不該再給腦看的東西（密碼之類）時，recall 會再拿出來。

## 選項（沒做，要的話再說）

- **只靠程式挑**（kai0）：最省（本次 −54%），但漏了就是錯、腦沒有補救的路。
- **只靠腦要**：只給目錄、不自動展開任何舊題，全部由腦 recall。最省的時候比 kai0 還省，但幾乎每個回頭引用的題都多一次呼叫，延遲變長；模型不愛叫工具時就答錯。
- **先叫一次（小）模型判斷意圖**：每題多一次呼叫（送目錄，約 1～3K），挑得比字面準（同義詞、跨很遠的指代）。可以用便宜的模型。
- **答完時讓腦順手寫一行摘要**（或另叫小模型摘要）：目錄行與結論都換成摘要，細節保留得比截字好；多花一點輸出 token、摘要可能失真。
- **舊題的工具輸出改存成「小念頭的結論」**：讀檔這種大輸出當下就交給小念頭（agent-gus）讀、只回要用的那幾句，主線與原始紀錄都小；代價是之後要別的段落得再讀一次。
- **跟 prompt cache 配合**：前綴固定（system＋目錄只在換題時更新、展開的舊題放在最後），讓快取吃得到。
- **等 LiteLLM 開著真跑一次**：`python3 proto8/tests/bench_intent_context.py --upstream http://localhost:4000/v1`，拿真的 `prompt_tokens` 與答對率換掉上表。
