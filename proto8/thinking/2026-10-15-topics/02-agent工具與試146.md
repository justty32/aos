## 5. agent 的工具與思考介面

**原文**：「工具這塊，我記得先前有考慮過，關於把inst格式接入的可能性。除此之外，思考這塊，希望能弄一個統一的呼叫格式介面，在這個介面之下，我們可以輕鬆換成llm endpoint，或是inst」。問到模型怎麼表示要用工具：「就直接走 openai 內建的。剩下都按照建議。」

**決定**
- 工具＝inst：agent.json 寫 `"tools": {"名": inst}`；工具的說明與引數 schema 放在工具自己那張 inst 的 `_tool`（`{"description", "parameters"}`），不用 `_metainfo`。
- 模型要用工具走 OpenAI 內建的 tool calling（`tool_calls`），不是在文字裡吐 JSON。
- 思考統一介面＝一支 inst（N-12 的特化）：stdin `{"messages", "tools"}`（OpenAI 形狀）→ stdout 最後一份＝OpenAI assistant 訊息；出錯照 N-29。換腦＝換一張 inst（假腦、真 endpoint、別的 inst 都行）。
- 工具結果回模型：`{"role": "tool", "tool_call_id", "content"}`，content＝`{code, result}` 的 JSON 字串，不截。
- 邊緣狀況（照建議）：工具名不認得＝回模型「不認得這個工具」、不算 fsm 的錯；一次好幾個 tool_calls＝一拍照順序跑完、每個回對應 id（[litellm 拍板 3](../2026-10-15-litellm-live.md#拍板10-15)）；引數不合 schema＝不驗、工具自己報錯回模型。
- 這套先當**實作慣例**，接過真的 endpoint 跑順再升規範。
- 10-13 的未決「OpenAI 工具呼叫 JSON 和 inst（argv）怎麼配合」：引數＝JSON 走 stdin（N-12），說明在 `_tool`。

## 6. agent 格庫改名、設定走 stdin

**原文**：改名「aos-agent-lib.py」；設定怎麼給格，使用者選「乙」。

**決定**
- 格庫叫 `aos_agent_lib.py`：proto8/lib 的模組一律底線（連字號 import 不了），所以不照字面用連字號。它不是 agent 本體（agent＝fsm＋表），是現成格（think、tool）的庫。
- 乙＝設定也走 stdin（[06 §11](../2026-10-14-json-entry/06-fsm.md) 原設計）。格的 stdin 現行見 [意見 1～4](../2026-10-15-opinions-1-4.md) Q2（fsm 不給格 stdin）。

## 7. 試 146 ollama（小模型）

**原文**：「可以試試看 146 ollama，但試之前先確定 146 的 cpu/gpu 效能占用，因為 146 上跑著很重要的東西」「要試的話請盡量用小模型」；又補「gemma3:1b 和 deepseek-r1:8b 兩個都試」。

**規矩**：146 的規矩五條記在 [dev-env](../../../wf/workflows/dev-env/01-跨機與外部工具.md#跨機--離線差異)；腦走 ollama 原生 `/api/chat`（帶 `num_ctx`、`keep_alive`；`/v1` 設不了 num_ctx）。

**結果**：gemma3:1b、deepseek-r1:8b 在 ollama 上都不支援 tools（400「does not support tools」），載模型之前就被拒、沒佔 GPU／CPU。要在 ollama 上跑工具得換有 tools 能力的模型（146 上有的都比 8b 大，使用者沒准）。

**挖到的**：腦失敗後 fsm 停在原狀態、下一拍又叫一次腦（沒退避、沒上限）；腦的真正原因被吞掉。

**決定（使用者「照建議」）**：兩條都處理；現行做法：fsm 不讀格的 stderr，要看原因在那張 inst 寫 `stderr` 檔（[原則](../2026-10-15-principles.md)「切乾淨」第 4 條）；think 連錯自己回 `next: halted`、`halted` 只在各表的 `end`（原則盤點第 8 條）。
