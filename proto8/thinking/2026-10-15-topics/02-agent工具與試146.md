## 5. agent 的工具與思考介面

**原文**：「工具這塊，我記得先前有考慮過，關於把inst格式接入的可能性。除此之外，思考這塊，希望能弄一個統一的呼叫格式介面，在這個介面之下，我們可以輕鬆換成llm endpoint，或是inst」。問到模型怎麼表示要用工具：「就直接走 openai 內建的。剩下都按照建議。」

**決定**（實作在 lib agent.md（已刪，見 git 歷史 5546be29））
- 工具＝inst：agent.json 寫 `"tools": {"名": inst TARGET}`（可接 `#/`，N-35）；工具的說明與引數 schema 放在工具自己那張 inst 的 `_tool`（`{"description", "parameters"}`），不用 `_metainfo`。
- 模型要用工具走 OpenAI 內建的 tool calling（`tool_calls`），不是在文字裡吐 JSON。
- 思考統一介面＝一支 inst（N-12 的特化）：stdin `{"messages", "tools"}`（OpenAI 形狀）→ stdout 最後一份＝OpenAI assistant 訊息；出錯照 N-29。換腦＝換一個 TARGET（假腦、真 endpoint、別的 inst 都行）。
- 工具結果回模型：`{"role": "tool", "tool_call_id", "content"}`，content＝`{code, result}` 的 JSON 字串，截 8000 字。
- 邊緣狀況（照建議）：工具名不認得＝回模型「不認得這個工具」、不算 fsm 的錯；一次好幾個 tool_calls＝基礎實作只跑第一個、其餘回「沒跑」並在 stderr 警告；引數不合 schema＝不驗、工具自己報錯回模型；工具被中斷＝`prev.interrupted`（N-38），回模型「被中斷」。
- 這套先當**實作慣例**，接過真的 endpoint 跑順再升規範。
- 10-13 的未決「OpenAI 工具呼叫 JSON 和 inst（argv）怎麼配合」就此解決：引數＝JSON 走 stdin（N-12），說明在 `_tool`。
- 後續：一次好幾個 tool_calls 改成一拍照順序跑完、`Skipped` 拿掉（[litellm 拍板 3](../2026-10-15-litellm-live.md#拍板10-15)）；截 8000 字與「被中斷」被 KISS 1.7 刪（[KISS 彙整](../2026-10-15-kiss/README.md)）。

## 6. agent 格庫改名、設定走 stdin

**原文**：改名「aos-agent-lib.py」；設定怎麼給格，使用者選「乙」。

**決定**
- `aos_agent.py` 改名 `aos_agent_lib.py`：proto8/lib 的模組一律底線（連字號 import 不了），所以不照字面用連字號。它不是 agent 本體（agent＝fsm＋表，不變），是現成格（think、tool）的庫。
- 乙＝設定也走 stdin，回到 [06 §11](../2026-10-14-json-entry/06-fsm.md) 原設計：格的 stdin 變 `{"state","step","prev","cfg"}`，`cfg`＝這份 fsm 設定整份（指示詞解好、旗標併進去、fsm 不認得的 key 照帶）→ N-37。think／tool 從 `cfg` 拿 `brain`、`tools`、`history`、`work`，demo 的 inst 拿掉 argv 的 `agent.json`。
- 巢狀：內層給自己格的 `cfg` 是內層那份；要外層的 key 就 `$ref`（N-40）。demo 的 `think/fsm.json` 加四行 `$ref` 到 `agent.json`。
- 後續：格的 stdin 改成 fsm 設定本身＋`fsm_state`、`cfg` 形狀作廢，N-40 外層設定當預設、demo 不再 `$ref`（[json-families § 動工](../2026-10-15-json-families.md#動工10-15使用者都照建議)）。

**動工時定的（等使用者看）**
- `cfg` 裡的相對路徑原樣給、不轉絕對；格照自己的 cwd 算（沒寫 `cwd` 的格＝跟 fsm 同一個 cwd）。跟指示詞的 base（cwd）、TARGET「相對路徑一律從呼叫者 cwd 算」一致。
- 沒 `cfg`（直接敲格、沒經 fsm）＝`NoConfig`、退出 1。

## 7. 試 146 ollama（小模型）

**原文**：「可以試試看 146 ollama，但試之前先確定 146 的 cpu/gpu 效能占用，因為 146 上跑著很重要的東西」「要試的話請盡量用小模型」；後來補「gemma3:1b 和 deepseek-r1:8b 兩個都試」。

**做了什麼**：負載由 ops-notes 先查（02:44Z，很輕、ollama 閒著）；規矩五條記在 [dev-env](../../../wf/workflows/dev-env/01-跨機與外部工具.md#跨機--離線差異)。新腦 `aos_brain_ollama.py`（原生 `/api/chat`，帶 `num_ctx: 4096`、`keep_alive: "30s"`；`/v1` 設不了 num_ctx 所以不走），demo 加 `brain/ollama146.json`。在 scratchpad 複製 demo、換腦、inbox 放「現在幾點？」一拍一拍敲。

**結果**（10-15 02:47～02:50Z）

| 模型 | 支援 tools | 延遲 | 叫了工具 | 回覆 |
|---|---|---|---|---|
| gemma3:1b | 否（400「does not support tools」） | 約 0.3 秒就被拒 | 沒有 | 沒有回覆，ask 格 `CellFailed` |
| deepseek-r1:8b | 否（同上） | 約 0.2 秒就被拒 | 沒有 | 同上 |

- `/api/ps` 試前、兩顆之間、試後都是 `{"models":[]}`：ollama 在載模型之前就拒了，沒佔 GPU／CPU，不用卸載。
- 照規矩 5 停手，沒換大模型。共打 146 約 14 次（3 次 `/api/ps`、2 次直接問錯誤訊息、9 次 `/api/chat`）。

- 挖到的：ask 格失敗後 fsm 停在 thinking、下一拍又叫一次腦（沒退避、沒上限，gemma 那輪 8 拍＝白打 7 次）；錯誤只進 `last_error: "CellFailed: 格 ask 結束碼 1"`，腦的 `HttpError`（真正原因）被吞掉。要在 ollama 上跑工具得換有 tools 能力的模型（146 上有的都比 8b 大，使用者沒准）。

**決定（使用者「照建議」）**：上面兩條邊緣狀況照建議做了。
- 真正原因：`CellFailed` 的 `last_error` 帶那格 stderr 最後一份 N-29 錯誤，例 `CellFailed: BrainFailed: HttpError: …回 400：…does not support tools`；think 格把腦的錯誤接進自己的 `BrainFailed`。
- 不再狂打：state 加 `fails`（連續出錯次數，成功歸零）與 `halted`；連錯 `max_fails`（預設 3）次就停住、之後的拍不起格。有 `error` 格照舊跳去。人接手＝把 state 的 `halted` 拿掉（或刪整份 state）。腦錯「可重試／不可重試」不分，先一律算次數。
- 落點：[N-38、N-39](../../NORMS/07-基礎設施-組合子.md#fsm)、lib fsm.md（已刪，見 git 歷史 5546be29）；測試 test_fsm 4 個、test_agent 1 個（假 ollama 回 400 → 錯 3 次、只打 3 次就停）。
- 後續：fsm 不再讀格的 stderr（10-15 深夜「切乾淨」第 4 條，`CellFailed` 只寫結束碼）；think 連錯回 `next: halted`、`halted` 只留在各表的 `end`（原則盤點第 8 條），見 [原則](../2026-10-15-principles.md)。
