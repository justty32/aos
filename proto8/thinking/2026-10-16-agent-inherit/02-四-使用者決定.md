## 四、使用者決定（10-16）

- 正規參數入口是 stdin，`aos agent 路徑`、`aos-exec WD TARGET` 這類 argv 寫法都是語法糖（使用者：「argv:[aos,agent,agents/brush]，其實，我一直覺得argv這塊的用法...就像我早期說的，正規參數入口就是stdin，像是aos-exec WD TARGET這個用法是語法糖...」）。
- **agent 的 stdin 只放一份，這份是食譜（定義）**（使用者：「stdin只放一份，這份要食譜。」）。
- **「這次的話」放在廚房（工作區）裡，使用時指定廚房的位置**；以後可能做類似 aos-exec 的語法糖，例如 `aos-agent-say`、`aos-agent-init`（使用者：「放在廚房裡，然後使用的時候指定廚房的位置。以後可能會做類似aos-exec那樣的語法糖，比如aos-agent-say, aos-agent-init...」）。
- **agent 當函數是概念上的**：JSON＋資料夾就是 Lisp 的 list、本身就是函數，不造 args.json／ret.json（frame.json 那套跟著不要）——原話在[第一節](01-三分鐘看懂.md#一使用者原話10-16整理版)第 2 段。
- 以下各條是 10-16 夜陸續定的（落成見 [CONCEPTS C-46、C-50、C-57～C-61](../../docs/CONCEPTS.md)、[NORMS N-46～N-51](../../docs/NORMS/10-基礎設施-定義與工作區.md)）。
- **食譜與廚房的接法選「捷徑」**（第五節候選 A：廚房放 `.aos → 食譜的 .aos` 的 symlink，食譜裡互指一律寫 `.aos/x`；使用者：「捷徑。這塊細說」）。
- **第六節前兩項同意**：食譜裡放 shebang stub＋PATH 上放捷徑（bob 的工具寫 `{"argv": ["brush"]}`）；「食譜 `.aos/`＋廚房 cwd」一律 `aos exec 廚房 食譜`，推廣到所有東西（使用者：「何等美麗的閉環，這就像是lisp的repl，/ws就是那個啥...」「前兩項我都OK」）。
- **工具參數走門房（`aos exec`）的 stdin，分兩層**：使用者問「關於工具的參數不能再走stdin這塊，這是為啥？」——答：stdin 只放食譜指的是 agent 程式那一層；工具行程（門房 `aos exec`）那一層的 stdin 是空的，照 N-27 收參數，由 stub／旗標明寫把它放進廚房。使用者：「還是不太懂，但感覺OK，就先這樣吧，以後再來搞懂。」
- **不用 PATH（第七節）**：brush 的地址寫在 bob 食譜裡的相對捷徑（`.aos/tools/brush`）；工具格站在自己廚房叫門房 `aos exec work/<n> .aos/tools/x`；**工具一律做成食譜資料夾**（`date` 也是 `.aos/tools/date/`）（使用者：「可以不使用PATH嗎？」→ 看完第七節：「好!」）。PATH 只留給人在終端用。
- **agent 是被外面驅動的狀態機、定義不含 loop、連錯不數**（10-16，在 [KISS 重審拍板 4](../2026-10-16-kiss-recheck.md#使用者拍板10-16) 定）：使用者：「agent的定義就是一個狀態機，至於這個狀態機怎麼跑、由誰跑，都無所謂。這是概念。但是我們的規範會說，為了讓agent方便審視自己，所以agent就是一個被人驅動的狀態機，需要外面有人用loop驅動他。」所以 `aos agent` 每次被叫只走一拍，由外面的 loop 驅動，不自己跑到 end（落成 C-62、N-53）。

- **指標＝捷徑**（10-16 夜，第八節之前定）：工具要影響呼叫者的工作區，像 C 函數影響外部變數一樣要透過指標——由呼叫方遞一條指向工作區的捷徑進去，不是工具自己伸手出去；能不能寫由 Linux 權限管（C-64）。（使用者：「除此之外，C語言函數想要影響外部變數，那也是透過指標」→ 頂層問「指標＝一條指向工作區的捷徑？」→「那就是捷徑」）。
- **一般工具預設站在工作區、agent 工具預設站在自己的 frame**（10-16 夜，看了第八節第一版後）：「還要『端菜』，我還以為就是直接把ws當作工具指令的cwd呢」→ 頂層：工具的 inst 自己寫 `"cwd": "ws"` →「對，我覺得這樣會更方便。風險就設計者自己管控」；再補：「我是覺得不用『遞』，而是就是默認true，默認ws就是工具的cwd...可以嗎？」「同樣用捷徑？」「brush這種agent工具，那就是他的cwd默認是他自己的frame。」；兩種預設各寫在哪見第八節 3。
- **frame 指到哪是呼叫方的自由**（10-16 夜）：「只是我們可以偷偷把它的frame設成ws」「我們可以自由管控他的frame要在哪裡，從而達到各種神奇效果」——frame 放哪由呼叫方決定、agent 不知道也不必知道（C-52）；指到 ws 也合法（代價：history、狀態、`.aos` 都落進 ws，ws 不再乾淨、可能撞名，是呼叫方自己的選擇）；這是概念層刻意保留的自由度，例子與邊緣見第八節 3b。
- 同時說的（原話，第八節要處理）：「我記得先前還有一個叫做frame的概念，也就是agent當函數，函數運行時候的heap(還是stack?反正就是運行時才會往其中放資料的)，可以指定某個資料夾當heap。用捷徑也不錯。然後我不喜歡/ws底下出現一個work/，這太突兀了，工作區會變得不乾淨。」
- **frame 與工作區分開（看完第八節「三分鐘看懂（五）」）**：使用者：「我覺得不錯。不過是不是可以採用環境變數？所以cwd: WS? 具體命名幫我想想。」——（五）的內容算定了：frame 與工作區分開、/ws 零殘留、工具格與門房對每個工具一律同一動作、一般工具入口 inst 寫一行站工作區、agent 工具不寫＝站自己的 frame、那一行由範本給不偷改預設、frame 放哪是呼叫方的自由。**名詞**：執行時站的資料夾叫 **frame**（後改名 stack，見下）；「工作區」只指使用者的成品區。（落成 C-65～C-67、N-56）
- **工作區位置用環境變數 `AOS_WS`、讀它用 `$env`**：頂層提名 `AOS_WS`（ws＝workspace，進縮寫表），並指出 `"cwd": "WS"` 字面替換是暗規則；使用者：「可以用$env啊」。頂層指出跟 N-45（設計不靠指示詞）衝突，給 A（`$ref` 仍只是拆檔便利；`$env` 讀執行當下的環境，可以當正式機制，像 shell 的 `$HOME`）／B（維持 N-45、改用 `cwd_env` key）；使用者：「A」。所以一般工具的入口寫 `"cwd": {"$env": "AOS_WS"}`（由 aos 的工具範本給好）。（落成 N-45、N-55、N-56、C-48、abbr.json 的 `ws`）
- **frame 改名 stack**（10-16 夜，上一條之後）：使用者：「不過frame那塊能不能換成stack(或heap)?。」→ 頂層推薦 **stack**（每次呼叫疊一層 `calls/<n>/`、結束收掉＝呼叫堆疊；大家一看就懂；frame 其實是 stack 裡的一層），**heap** 保留給以後跨呼叫的共用記憶（第八節提過的 `mem` 捷徑）→ 使用者：「好！」。所以概念與規範裡指「執行時站的資料夾」的一律叫 stack（名詞表有 stack／heap 兩列）。
