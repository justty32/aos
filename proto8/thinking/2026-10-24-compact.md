## 使用者原文（逐字，10-24）

前文（按意圖組 context 那段）：

> 對，因爲現在history.jsonl就是一直累積，但問題在於那太多冗餘資訊了，我希望AI能夠按照意圖去做

> 我現在沒空管這些小事，都按建議做

本題：

> 做一套土法compact吧。先把工具呼叫的東西讓便移AI總結出一句話他在幹嘛，結果簡單來說如何。然後是讓AI逐段，可能每幾kb讓AI產總結，產總結的過程中，可以選擇一些json line留下，並打上標記，最後自己修飾

（「便移AI」＝便宜的 AI。）

## 決定

- 三步照使用者說的：① 工具呼叫交給便宜模型各產一句「在幹嘛，結果如何」；② 逐段（每幾 KB）讓 AI 產總結，同時挑 json line 原樣留下並打標記；③ 最後讓 AI 自己修飾。
- 其餘細節使用者 10-24「都按建議做」，照推薦定、可翻案（見下方「結論」）。

## 結論（照推薦定、可翻案）

### 1. 放哪、怎麼叫

- 新範本 **`demo/agent-hal/`**：照抄 agent-dan（brain.py、act.py 只改錯誤訊息開頭），不改 agent-dan；fsm 多一格 **`idle → compact → think → act → idle`**。
- 壓縮程式是 agent-hal 裡的資料夾程式 **`compact/`**（`_entry`＝`python3 compact.py "$@"`；`ask.py` 問腦、`prompts/{note,segment,final}.txt` 三步的 system 訊息、`.env` 設定）。
- **觸發**：compact 格每次 think 前都跑；看檔案大小，`history.jsonl` 沒超過 `COMPACT_OVER_KB`（32）就直接退 0，不問腦（不數 token、不數則數）。題目答到一半（剛跑完工具回 idle）也會經過這格。
- **手動**：`aos-exec --ws <工作區> proto8/demo/agent-hal/compact --force`（`--force`＝不看門檻；`AOS_STACK` 沒給就是 `<工作區>/.stack/`）。別隻 agent 的 stack 也能這樣壓（只要 history 是 agent-dan 的形狀）。

### 2. 三步

| 步 | 輸入 | 模型（`.env`） | 一次叫幾次 | 產物（`$AOS_STACK/compact/run/`） |
|---|---|---|---|---|
| ① note | 每則帶 `tool_calls` 的 assistant＋它的 tool 結果（結果超過 2000 字截中間）、前一個 user 問題 | `COMPACT_MODEL_NOTE`＝`chatgpt-gpt-6-luna-low` | 每則叫工具的 assistant 一次（裡面幾個呼叫一起問、各回一句） | `notes.json`、`stage1.jsonl` |
| ② segment | ① 之後的紀錄，每 `COMPACT_SEG_KB`（8）切一段，一行 `L行號 角色：內容` | `COMPACT_MODEL_SEG`＝`chatgpt-gpt-6-luna-low` | 每段一次 | `seg/0001.json`… |
| ③ final | 更早的摘要（壓縮再壓縮時）＋各段摘要＋候選保留行 | `COMPACT_MODEL_FINAL`＝`chatgpt-gpt-6-sol` | 一次 | `final.json` |

- 網址用 `COMPACT_URL`，沒設沿用 `AOS_BRAIN_URL`。
- ① 每個呼叫換成一行 `tool_note`：`{"role": "tool_note", "tool_call_id", "name", "ok", "content": 一句話}`，`_n`＝[叫的那行, 結果那行]（之後追查得回原文）。`ok`＝模型判斷；沒有結果（中途停了）一律 false。
- ② 每段回 `{"summary", "keep": [{"n", "tag", "why"}]}`。**標記五種**：`user_words`（使用者原話、要求、偏好）、`decision`（關鍵決定）、`number`（之後會被引用的數字）、`open`（沒解決的）、`other`。
- ③ 回 `{"summary", "keep": [id…]}`，從候選裡選最後要留的（上次壓縮留下的保留行 id 是 `old:L…`）。
- 保留行上限：每段最多 3 行、最後最多 12 行、一行最多 1500 字；超過的記 `dropped`。最近 2 題（`COMPACT_KEEP_TURNS`）與沒答完的那題原樣不壓。
- 切段：同一則 assistant 叫的幾個工具（連同它順便說的話）算一塊、不拆；超過一段時盡量切在一則 user 前（前半至少半段）；一行本身就超過一段＝自己一段，給模型看時截中間。
- 保留行的「原文」＝① 之後那一行（一般訊息就是原樣；工具呼叫是那一句——原始的大結果不進新 history，要看去 `orig.jsonl`）。

### 3. 新 history 長怎樣（agent-dan 的 brain 直接能用）

```
{"role": "user", "content": "【compact】run=<run> 第 K 次壓縮。以下是先前對話（原本 N 則、X KB）的摘要與原樣保留的幾則；原始紀錄在 $AOS_STACK/compact/<run>/orig.jsonl。\n\n## 摘要\n…\n\n## 原樣保留的訊息（keep）\n- [L1 user_words：理由] {\"role\": \"user\", \"content\": \"…\"}"}
{"role": "assistant", "content": "好，我已讀過先前對話的摘要與保留的原文，接著往下。"}
……最近 COMPACT_KEEP_TURNS（2）題與還沒答完的那題，原樣一行不改
```

- 只用 user／assistant 兩種角色、不加多餘的 key；保留行一律寫在摘要那則的文字裡、不當成獨立訊息放回去（OpenAI 的工具協定要求 `tool` 訊息前面一定有對應的 `tool_calls`，原樣放回會被 API 拒）。
- 「一題」的切法跟 agent-kai 一樣（從 user 起、到沒有 `tool_calls` 的 assistant 止），所以摘要那一對在 kai 眼裡就是第 1 題。
- agent-hal 的 `system.txt` 多一句：開頭是【compact】的那則是摘要，用得到就照它答，沒有就說不確定或重查。

### 4. 原始 history 怎麼保留（像 log 輪替）

- 原本那份 `history.jsonl` **整份原封收進** `compact/<run>/orig.jsonl`（hard link，不複製也不改）；新的先寫 `run/history.new.jsonl`，再一步換上去（rename）。
- 每次一個資料夾 `compact/<run>/`：`orig.jsonl`、`stage1.jsonl`、`notes.json`、`seg/`、`final.json`、`source.json`、`report.json`；`compact/log.jsonl` 一次一行報告。
- **report.json**：壓縮前後的大小與則數、被壓那段多大、① 之後多大、三步各叫幾次、prompt／completion token（回覆有 `usage` 就用，沒有就粗估、標 `estimated`）、退路次數、保留行候選幾個、最後留哪些、丟了哪些和原因、用了哪些模型與設定、花幾秒、第幾輪（`round`）。

### 5. 錯與中斷

- 一律 stderr 一行 `compact: 代號 原因`、退 1，history 不動；fsm 停在 compact 格，修好再跑一次接著做（P-20）。
- 代號：`StackMissing`、`ArgumentsBad`、`SettingBad`、`HistoryBad`（有一行不是 JSON 物件）、`BrainFailed`、`ReplyBad`（回覆不是 OpenAI 的形狀）、`SummaryEmpty`（某段或最後的摘要是空的——換上去那段就整個不見，寧可停）、`HistoryChanged`（壓的期間 history 被別人接了一行，這次不換）。
- **每步做完就落檔**：做到一半掛掉，重跑時第 1 步問過的不再問、做好的段不再做（`source.json` 記原檔的 sha256；原檔變了＝舊的半成品改名 `stale-<時間>` 收著、不刪，重新來）。
- **模型沒回 JSON**：不算錯，走退路——① 照字面拼一句（`叫 math（參數）→ 結果第一行`）、② 整段回覆當摘要、不收保留行、③ 整段回覆當摘要、候選全留（上限內）；次數記在報告的 `fallbacks`。
- **壓完沒變小**：不換上去，半成品收成 `nosave-<run>`；同一份 history 在 fsm 裡不再重壓（多接幾行才再試）。
- 同一個 stack 一次只壓一個（`compact/.lock` flock；手動跑跟 fsm 格撞到，後到的等）。

### 6. 跟 agent-kai（按意圖組 context）怎麼搭配

- **kai** 省的是「每次送出去的」（紀錄照存、每題現組 context）；**compact** 把紀錄**本身**換成短的，代價是摘要可能失真、recall 翻不到被壓掉的過程。兩者可以疊用。
- **建議的疊法**：kai 在前、compact 在後當第二道防線——題很多時（例如超過 50 題、目錄本身也變長）再 compact，把最早那一大段收成摘要一對；kai 會把它當第 1 題列進目錄、需要時 `read` 展開。門檻要開大（kai 的 history 比 dan 大，recall 的結果也照存）。
- **接法**（沒做，kai 的檔不動）：kai 的 fsm 加一格 compact（把 `agent-hal/compact/` 抄進去）；kai 的 `recall` 若要翻到被壓掉的原文，要多讀 `compact/*/orig.jsonl`（`detail=true` 時）。
- 疊用時：kai 的「第 N 題」編號在壓完後會變（摘要那對變第 1 題）。

## 已知限制

- **總結失真**：便宜模型可能把數字抄錯、把「先不要修」講成「已修」、把使用者的否定句（「不要用 5432」）縮掉否定。保留行是對策，但挑哪幾行也是模型決定的；挑漏了就只剩摘要。失真會隨壓縮再壓縮累積。原文都在 `orig.jsonl`，但沒有工具讓腦去翻。
- **壓縮再壓縮**：上次的摘要那一對不再切段，當「更早的摘要」直接交給 ③；上次的保留行變成 `old:` 候選。
- **一題就超過門檻**（還沒答完）：那題原樣不動、沒東西可壓，記一行 skip，每次 think 前都再檢查一次（只讀檔）。真的會撐爆腦的上下文——要靠工具本身限制輸出。
- **成本**：一次壓縮＝每則叫工具的 assistant 一次＋每段一次＋一次強模型；壓縮那一題會慢（呼叫串著跑、不平行）。壓完前綴整個換掉，供應商的 prompt cache 從頭來。
- **壓的期間有人寫 history**（手動跑時 agent 也在跑）：換之前再比一次 sha256，變了就不換；比完到換上去之間仍有極小的窗。fsm 裡當一格就沒這問題。
- **compact 格沒有自己的逾時**：每次問腦 120 秒（`COMPACT_TIMEOUT_S`），段多時整格可能跑很久；要整格逾時就把格寫成單子（`{"argv": ["aos-exec", "compact"], "timeout_ms": …}`）。

## 未決

- **跟原則的衝突（要使用者看）**：P-41「history 只附加、不改寫」、P-14「不為清理加機制」——compact 會讓 `history.jsonl` 這個路徑換成另一份內容。現在照推薦用**輪替**（舊檔一個字不動地搬進 `compact/<run>/`、新檔另起，每一份檔本身仍是只附加）。若要嚴守「這個路徑永遠只附加」：照 kai 的做法（紀錄照長、送出去的另外組），或 compact 只產一份「給腦看的」檔、brain 改讀那份（brain 就不再跟 dan 一樣）。
- 選項（沒做，要的話再說）：
  - **給腦一個翻原文的工具**：像 kai 的 `recall`，但讀 `compact/*/orig.jsonl`（摘要裡有 `L` 行號可以對回去）。
  - **只做第 1 步**（最便宜，大部分是這一步省的）：加 `COMPACT_STAGES=1`（要換成合 OpenAI 協定的形狀）。
  - **① 平行問**：各則 assistant 互不相干，可以同時問幾個。
  - **按 token 而不是 KB 觸發**：用回覆的 `usage.prompt_tokens` 判斷。
  - **讓 kai 接 compact**：見第 6 點的接法。
