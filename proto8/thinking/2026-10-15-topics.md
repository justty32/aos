**原文**：「雖然我們分出了概念 規範 實作，但仍然要用"主題"去分……inst/loop/daemon 分在基礎設施這個主題下，基礎設施下又分多個子主題。每個主題都有自己的概念、規範、實作。fsm 在 agent 這個主題下。」稍後改：「把 fsm 也跟 tasks 放一起。」

**五題答覆與決定**
1. 採方案一（輕）：NORMS.md、CONCEPTS.md 留當入口，分檔改按主題拆；條號不重編、條文原樣搬；入口各有「條號 → 檔」表；每份分檔第一行寫出該主題的概念、規範、實作在哪。
2. 時空：「時空這塊應該在設計理念這個主題下」——當時暫定；後來「隨你」定案（見下）。
3. tasks 組合子（seq／par／if／not）歸基礎設施，「地位等同於 C 語言的 stdlib」。fsm 跟 tasks 放一起（同為 stdlib 地位）；agent 是用 fsm 組出來的（例：agent.json），agent 主題連過去。
4. daemon 兩義（C-04 Linux 借來的那層 vs 管 loop 的程式）：名詞表留兩列，daemon 子主題開頭註明。
5. 待定不拆，每條前面標主題。

主題：設計理念（含時空）／總則（跨主題：N-05、N-12、N-18、N-29、N-35）／基礎設施（inst、loop、daemon、窗、命令列、指示詞與路徑、組合子 tasks＋fsm）／kernel／agent。總則與設計理念目前分兩份，當時未決，後定案（見下）。

**「都隨你」三點定案**（10-15）
1. 總則與設計理念維持分開：總則＝跨主題的規範，設計理念＝概念。
2. 時空留在設計理念下，去掉「暫定」。
3. N-02 刪去「亂弄具體指什麼還沒定，見待定」半句（該待定已於早上結案）。

## 3. fsm 補細則

**原文**：心跳——「基礎實作中連時間都不寫，保持極簡。」六處細節——「全照推薦」。

**決定**（寫進 N-36、N-38、N-39，條號不增）
- 心跳：fsm 是單次程式、壽命一拍，不適用 N-17／N-32 的每秒心跳；生死看拍它的 loop 的 state 窗；基礎實作 fsm 的 state 不寫時間、不帶 pid／started／boot_id。58 題頁 Q12「心跳可選」與 N-32 的不一致就此**對齊結案**。
- 第一拍：state 窗位置有、檔還沒有＝從 `start` 起。
- 跳去 `error` 格：phase 改成 `error`，下一拍才跑（一拍一格），原狀態與錯誤放進 `prev`。
- `error` 格自己出錯：不再跳，留在 `error`＋`last_error` 等人；`step` 在回到 `start` 或進 `error` 格時歸零（`max_steps` 自上次回 `start` 起算）。
- 格跑完、ret 落了、state 還沒寫就被殺：下一拍重跑、不撿舊 ret（N-20），`prev.interrupted: true`；fsm 起格前先把 `step` 寫進 state 窗。
- fsm 結束碼：只在 fsm 自己出錯（設定錯、窗缺、拿不到鎖）才非 0；格出錯由表處理、fsm 退 0。要外層接手，就讓內層 `error` 格回 `end` 名單裡的 `next`。
- state 窗記 `phase`、`data`、`step`、`last_error`；lock 選填，拿不到＝fsm 自己出錯、不碰 state；ctl 選填，`paused`／`stop` 對單次程式都＝這拍不起格就退出。

**補決（動工後，使用者『照它做的寫進規範』）**：
- state 窗加 `running`：起格前寫 true、跑完改 false；下一拍讀到 true＝上一拍被殺一半（N-38、N-39）；另記 `ctl_seq` 回音。
- 格收到的 stdin＝`{"state","step","prev"}`〔註：10-15 稍後加 `cfg`，見 §6〕；`prev` 三形狀：平常＝上一格 `data`；被殺一半＝`{"interrupted": true, "data": …}`；進 error 格＝`{"state","error","data"}`（N-37）。

**未決**：標準實作的 fsm 要不要每拍記時間（列進待定）。

## 5. agent 的工具與思考介面

**原文**：「工具這塊，我記得先前有考慮過，關於把inst格式接入的可能性。除此之外，思考這塊，希望能弄一個統一的呼叫格式介面，在這個介面之下，我們可以輕鬆換成llm endpoint，或是inst」。問到模型怎麼表示要用工具：「就直接走 openai 內建的。剩下都按照建議。」

**決定**（實作在 [lib agent.md](../lib/agent.md)）
- 工具＝inst：agent.json 寫 `"tools": {"名": inst TARGET}`（可接 `#/`，N-35）；工具的說明與引數 schema 放在工具自己那張 inst 的 `_tool`（`{"description", "parameters"}`），不用 `_metainfo`。
- 模型要用工具走 OpenAI 內建的 tool calling（`tool_calls`），不是在文字裡吐 JSON。
- 思考統一介面＝一支 inst（N-12 的特化）：stdin `{"messages", "tools"}`（OpenAI 形狀）→ stdout 最後一份＝OpenAI assistant 訊息；出錯照 N-29。換腦＝換一個 TARGET（假腦、真 endpoint、別的 inst 都行）。
- 工具結果回模型：`{"role": "tool", "tool_call_id", "content"}`，content＝`{code, result}` 的 JSON 字串，截 8000 字。
- 邊緣狀況（照建議）：工具名不認得＝回模型「不認得這個工具」、不算 fsm 的錯；一次好幾個 tool_calls＝基礎實作只跑第一個、其餘回「沒跑」並在 stderr 警告；引數不合 schema＝不驗、工具自己報錯回模型；工具被中斷＝`prev.interrupted`（N-38），回模型「被中斷」。
- 這套先當**實作慣例**，接過真的 endpoint 跑順再升規範。
- 10-13 的未決「OpenAI 工具呼叫 JSON 和 inst（argv）怎麼配合」就此解決：引數＝JSON 走 stdin（N-12），說明在 `_tool`。

**挖到的邊緣狀況（攤給使用者）**
- ask 格失敗後 fsm 停在 thinking、**下一拍又叫一次腦**（沒退避、沒上限）：gemma 那輪 8 拍＝白打 7 次請求，才發現每拍都 400。對共用機器這會變成穩定的騷擾流量。要不要：腦錯幾次就轉 error 格／idle、或腦錯分「可重試」（連線斷）與「不可重試」（400 模型不支援）？
- 錯誤只進 state 窗的 `last_error: "CellFailed: 格 ask 結束碼 1"`，腦吐的 `HttpError` 訊息（真正原因）被吞掉，要自己直接敲腦才看得到。
- 要在 ollama 上跑工具，得換有 tools 能力的模型（例如 qwen 系；146 上有的都比 8b 大，使用者沒准）。

**決定（使用者「照建議」）**：上面兩條邊緣狀況照建議做了。
- 真正原因：`CellFailed` 的 `last_error` 帶那格 stderr 最後一份 N-29 錯誤，例 `CellFailed: BrainFailed: HttpError: …回 400：…does not support tools`；think 格把腦的錯誤接進自己的 `BrainFailed`。
- 不再狂打：state 加 `fails`（連續出錯次數，成功歸零）與 `halted`；連錯 `max_fails`（預設 3）次就停住、之後的拍不起格。有 `error` 格照舊跳去。人接手＝把 state 的 `halted` 拿掉（或刪整份 state）。腦錯「可重試／不可重試」不分，先一律算次數。
- 落點：[N-38、N-39](../NORMS/07-基礎設施-組合子.md#fsm)、[lib fsm.md](../lib/fsm.md)；測試 test_fsm 4 個、test_agent 1 個（假 ollama 回 400 → 錯 3 次、只打 3 次就停）。
