## 跟 AI 討論後的整理（待議）

以上面原文為準：

- **parts 彆扭在哪**：一身兼「名字→路徑對照表＋每槽帶 env＋固定名字 fallback＋綁 agent 資料夾」，不是純變數表、不是純 symlink 目錄、也不是純設定。
- **aos 已有「變數」的取用側**：`$env`（讀環境變數）、`$ref`（引用別處 JSON 值）；缺的是**定義側**——一個乾淨的地方宣告 name=value，加上定義／查詢的命令或約定。
- **核心問法**：aos-var 是**新增一個機制**，還是把散在 `$env`／`$ref`／`parts.json`／`.env` 的具名綁定**收攏成第一級的「變數」概念**？若統一，parts 成為 aos-var 的特例（值剛好是可執行檔／格），`tools.json` 同理。
- **跟今天其他判準的連結**：呼應「固定名字 vs 間接」判準（C-51 10-31 加註）與「何時該拆＝檔案系統公民」（aos-round 10-31 節）。
- **會動到 parts 的定位**：parts 今天（10-31 早）剛定進 C-74 標準庫、與 fsm 平級；若 parts 變成 aos-var 的特例，層級要重看。

## 使用者後補（10-31 傍晚，逐字）：收回 aos-var、改問 parts 能否組出來

> Hmmm，其實 $ref,env 本身就有變數定義與取用的功能，硬要再一個 aos var 其實不是很好。aos parts 是否可以用 aos exec 和 ref,env 以及其他一些東西組出來？

**決定（10-31 傍晚）**：

- **收回 aos-var**：`$ref`／`$env` 已有變數定義與取用，不疊新機制。
- **新的待議題**：parts 能否用 aos-exec＋`$ref`／`$env`＋其他現成東西組出來（parts 不必是專屬程式）。

跟 AI 討論後的分解（以原文為準；**待驗證，未對 aos-exec 契約核對**）：

- parts 各功能對現成原語：
  - 存名字→路徑＝JSON map，或 agent 資料夾裡同名 symlink／資料夾（即固定名字那條）；
  - 查＝`$ref` 到 `parts.json#/parts/<槽>/path`，或不查、直接 `aos-exec <agent>/<槽>`；
  - 跑＝aos-exec；
  - 每格 env＝目標資料夾的 `.env`（aos-exec 本來就讀）；
  - 改＝`aos-json set`／`del` 或 `ln`。
- parts 真正多出的只剩：集中表的便利（但「檔案系統公民」原則下 JSON blob 的紅利反而少）、註冊檔→固定名字 fallback 的膠水、驗證與錯誤碼；若偏純檔案系統，parts 可瘦到接近「約定而非程式」。
- 待驗證：aos-exec 能否接 `$ref` 當執行目標、並從同一個 ref 取 env；env overlay 的合併規則。

## round 重切草圖（10-31 傍晚，唯讀 session 推的設計素材、待議、非行動）

來源：唯讀 session aos-ce 經使用者授意轉來，接在上面 parts 組合化待議之後存著，供之後收斂用。使用者定調（逐字）：

性質：**待議設計素材、不是行動**；本批不碰 round 結構、不改碼、不改條文。以下草圖全文原樣收錄（只改排版）：

**判準**＝使用者今天的尺：一塊要不要析出成格，看它換不換得到「檔案系統公民」紅利——(a)會否被單獨抽換 (b)需否跨棧 POSIX 串接 (c)使用者/agent 會否單獨叫 (d)演進要否被 git 單獨追；四項弱→收進單體，夠強→留成格。

**現狀（全拆端）**：aos-round 驅動 ＋ fsm 表(fsm-stop/fsm-idle) ＋ 五薄格 idle/think/act/more/finish（共用 roundlib.py） ＋ 跑時叫 endpoint/<名>、hook/*、queue 格、history 格、aos-tools、aos-post。

**逐塊判定**：

- endpoint/<名>：常抽換(換模型/供應商/假腦)、可跨棧、會被叫→留成格（強）
- hook/*：每隻 agent 自訂、使用者丟自己程式→留成格（最強，hook 不是檔就不叫 hook）
- compact：壓縮策略可換→留成格（中強）
- tools（模型叫的）：本就一堆獨立程式、經 tools.json→留成格
- idle/think/act/more/finish：五個緊耦合、共用 roundlib、改一起改、不會單獨換/串/叫→收進單體（四項全弱）
- queue/history 的 append/claim/finish/read：薄操作、郵箱介面已由 aos-post/say/listen 提供→收進單體（直接叫 aos-post）

**重切後**：aos-round＝一支程式，內部直接跑 idle→think→act→more→finish（不再 exec 五格），queue 直接叫 aos-post、history 自己 append（如 aos-eca-turn 現在的做法）；只往外叫真正值得的格 endpoint/<名>、hook/*、compact、tools。

**兩個現成佐證**：①aos-eca-turn 就是此重切的預演（沒拆五格、自己叫 aos-post、只把腦留外面經 cli.json）②今天剛加的 --on-empty 旗標正是「fsm 表收進程式」範本——控制流收進 aos-round 後，fsm-stop/fsm-idle 之別塌成 --on-empty stop|idle（同 aos-eca-turn），兩張 fsm 表可免。

**代價**：fsm 當資料看的好處淡掉（折衷：aos-round 內部仍讀一張小 fsm 表當資料、只是不 exec 五支）；逐狀態單獨抽換沒了（價值低）；trace 一格一行可從內部保留。

**匯流**：round 不再用五個 parts 格跑內部步驟→parts 在最大用戶 round 身上需求少一大半，剩 endpoint/hook/compact 這類外掛用 symlink＋.env 指就夠→印證「parts 可退成約定、不必是程式」。

先存著，不改碼。

狀態：**待議、非行動**；收斂時與 parts 組合化一起交 fable，先對 aos-exec 契約核對。
