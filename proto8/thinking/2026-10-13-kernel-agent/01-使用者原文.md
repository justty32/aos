# 2026-10-13 kernel／agent：使用者原文

← [kernel／agent 入口](../2026-10-13-kernel-agent.md)

## 0. 使用者原文（語音，去贅字）

底子其實已經打好了：把檔案系統當 lisp 來做，核心就是 inst 這塊碼在跑；上面包了 loop；loop 上面又有管理多個 inst 在跑的 daemon。到這邊基礎已經打好了，接下來直接針對 agent 的需求，進入 agent。

先前的概念說要先做 tick、再做 task、再做 kernel、再做 agent——其實它們不是分層，都是概念。概念先定下來，再基於 inst 這塊技術去顯化。所以可以直接跳到最終想達到什麼效果。

kernel 本質上就是管排程、管資源之類的概念。先前做過嘗試：kernel 把 loop 當 CPU 在用、去管它——後來發現真的沒有必要。**所有能夠管某個任務是否在執行、管某個任務可以去執行的，就叫 kernel。**

拿 agent 來說：指定一個 inst，它 argv 的第 0 個元素就是 agent。agent 本身也是一個 loop，持續跑某個狀態機變換。所以 agent 既是一個持續執行的 inst，也是一個 loop；它本身的機理元素就是一個 loop 在持續呼叫一個狀態機變換程式。可以拆成這三塊。

agent 可不可以當 kernel？可以。agent 可以基於 loop，也可以基於 daemon。如果基於 daemon，它就可以自己管理底下還可以再跑哪些額外的任務、這些任務什麼時候跑——那 agent 就是 kernel 了。所以 daemon 本身也是一個 kernel：**只要是能管理任務的 instance，就是 kernel。**

在此之上，要想的是如何更有效利用這種管理任務的方式。例如 agent 想執行某個任務：

- 它看一下這個任務可以執行，就操作自己的 ctl，用自己身為 daemon 的能力去跑它；
- 或者 agent 本身只是一個 loop，它下的指令是下給另外一個 daemon，讓那個 daemon 去管是否真的要跑。

## 0b. 使用者原文續（語音，去贅字）

管理任務、管理排程、管理資源，這些行為就是 kernel 的行為。你做了類似概念的事情，你就是 kernel。

agent 也是：只要符合機器人的三樣模型——**記憶、思考中心、工具**——三個都有，又是一個狀態機在跑，那你就是 agent。不用想太多，就是那樣。

所以它們都是概念。只是在這些概念之上，我們要定義一個通用的規範，為了達到未來目的的規範。

未來目的：**讓 agent 有足夠的自省性**——能自己審理自己、自己看自己在幹嘛、讓自己變得更好，也就是自我改進。怎麼改進？一個 agent 天然就帶有瀏覽檔案系統的能力，所以當然先來做 agent。

狀態機怎麼跑：可以是一個 loop，每次跑一個 inst；inst 在某一個特定的時候執行，或是 GPT Codex 那些東西都可以。只是如果用 Codex 這種持續在跑的程式，會不方便。如果是 loop 單次跑一個狀態，狀態停下來之後，可以很輕鬆地打包成 ZIP——任何狀態切換之後，都可以用 git 存下來；而不像 Codex 或 Claude Code，還要額外去把它們的狀態存下來。

## 0c. 使用者原文續二（語音，去贅字）

agent 就是一個 loop 持續跑的某一個 instance，那個 instance 就是 agent 的狀態機切換程式。就是這樣。

kernel 這一塊：我們可以先自己定一些通用的規範、資源，也可以預留一些介面，讓人定義可用的資源；只是我們可以定義一個**通用的格式來定義資源**。就像剛剛說的 meta info（`_metainfo`）。檔案空間上的屬性就是檔案、資料夾屬性，那些不用說；時間上的屬性，Linux 本身也有 PID 那些，也是通用屬性。`_metainfo` 更進一步，是在九軸（九個 axis）上的。

所以這邊稍微定一下標準規範的系統：**kernel 管理任務**；在我們的標準規範中，kernel 管理任務＝**管理某一個 instance 是否要執行，它是基於 daemon 的。daemon 是 kernel 的基本**；kernel 就是有權控制 daemon 要跑哪些 instance 的東西。要跑哪些 instance，可以看 instance 的屬性（在幹嘛）來決定要不要跑，也可以透過其他方式。這是 kernel 的基礎。

## 0d. 使用者原文續三（語音，去贅字）

kernel 機制定下來之後：假如一個 agent 的**宿主是一個 daemon**，它就天然擁有操控自己的能力，自己底下就可以天然去跑一些額外的 inst。所以 agent 的宿主是 daemon 的時候，agent 就是一個 kernel。

kernel 這一塊：首先是任務的特性。除了基本的空間特性和時間特性——也就是 Linux 的**行程屬性和檔案屬性**——之外，還有我們的九個軸和一些有的沒的。九個軸是我們在這套體系上提出的概念，用來實施我們的想法，就是後續自我改進的概念。必定會有的是行程屬性和檔案屬性，不用說，而且是**隱性的**：我們既然身在 Linux 之上，就一定會有。

kernel 就是看某些屬性來決定這個東西要不要跑。剛剛說的屬性**只有定義**；要不要跑，是那個程式自己的決定，**怎麼決定是它內部的演算法，隨便**。

## 0e. 使用者原文續四（語音，去贅字）

這樣定義下來，kernel就是管理要跑什麼的一個機制。agent 也不用想太多，它就是一個狀態機。

工具這一塊當然可以隨意，因為它靠 agent 的狀態機程式去跑。狀態機切換就是思考。所以 agent 這一塊，只要符合狀態機切換，而且每個狀態之間可以通過檔案儲存——**這不是必要的，只是建議**，不然不方便，就失去了最基礎的「通過檔案系統做改進」的能力。

我們提供**第一個標準版本**：agent 基本三種狀態的狀態機切換程式——**等待、思考、工具執行**。

- 思考：呼叫某一個程式（某一個 inst），讓它去跑大語言模型，把大語言模型的結果丟給我。
- 工具執行：要想一下 **OpenAI 的工具呼叫 JSON 格式和我們的 inst 格式之間怎麼配合**，可能要定個規範——OpenAI 的工具呼叫，引數是丟 JSON 進去；我們 inst 的引數是走 argv。

使用者：「工具和 inst 之間怎麼去定義，這個是後續的事情，沒關係，先這樣。」

## 0f. 使用者更正與收尾（打字）

- agent 就算不跑在 daemon 底下，只要能操控某些東西被執行，也算 kernel——好比它往某個資料夾寫檔，另一個獨立的 daemon 會讀；乃至於那個被執行的東西不是 inst 也 OK。只是後續自我改進這塊，預期都以 inst 為基礎。
- agent 也不一定要用 loop 不停跑狀態切換程式，也可以是一個 inst 執行 Claude Code 之類。只是後續做自我改進時，會用 loop＋狀態切換，方便自省。
- Codex 和 Claude Code 都是一直開著跑的，不好用，所以才想用 loop＋狀態切換，這樣可以直接用 zip／git；**不是要去改 Codex／Claude Code**。
- 今天主要是釐清概念。
- daemon 管另一個 daemon 這件事確實麻煩。
