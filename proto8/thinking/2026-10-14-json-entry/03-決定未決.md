## 2. 決定（10-14）

- 不全面退守 `system("...")`，損失太大；記為以後的一個方向。
- 可供呼叫的程式：stdin 作為參數，stdout／stderr 作為結果，exit 作為輔助（以函數來看的細分見本節後段）。
- 回歸 POSIX 原始本意。
- aos 規範中 stdin／stdout／stderr 都是 **JSON 串流**（POSIX 本身不要求），採放寬寫法：一串 JSON 值接著一串，每份可單行（即 JSONL）或排版跨行；只有一份就是普通 JSON（使用者 10-14「放寬」）。
- 跑完的判定：以 stdout 吐出結果並且行程結束為準；有寫 exit 檔的話，exit 檔出現也算（N-12，見 [14 §41](14-h拍板.md#41-結論與未決)）。
- JSON 串流本質上＝最外層省略的 `[]` 陣列，所以 `檔#/位置` 自然適用：`檔#/0` 是第一份、`檔#/3/key` 是第四份的 key、`檔#`（整份）＝整個陣列（使用者 10-14）。
- stdin 多份＝整串一次呼叫，程式自己解讀（使用者 10-14 選項題）；規範只管格式不管意思。
- 規範：NORMS N-12。
- 三支程式改從 stdin 收設定後，要指 `檔#/位置` 時 stdin 內容寫 `{"$ref": "x.json#/clock"}`，用現成指示詞，不發明新東西（使用者 10-14「都按照建議」）。
- 寬鬆：人手動打 `aos-inst x.json`（argv[1] 給路徑）保留，stdin 與 argv[1] 兩種都收（同上）。
- loop／daemon 的 stdout 不是每回合吐狀態 JSON（使用者 10-14「三件事都按照建議」）；stdio 與 state／ctl 無關。
- aos-inst 自己的 stdio 與它所呼叫程式的 stdio（inst.json 的 stdin／stdout／stderr key 指定的檔）分開，不是同一回事（同上）。
- state.json／ctl.json＝程式內部狀態的外顯（像 Plan 9／FUSE）；位置由 stdin 參數指定（使用者 10-14）
- 外顯之後，程式自己每隔一段固定時間跟外顯的狀態同步（讀 ctl、寫 state）（使用者 10-14）。
- 參數沒指定外顯位置時：單次程式沒給窗＝不開、不提醒（Q9，[05 §7](05-aos-llm-agent題.md)）；loop／daemon 的 state／ctl 窗必填、fsm 的 state 窗必填（N-19，[12](12-七題回覆.md)、[13](13-動工前拍板.md)）。
- 窗的名字統一為 `state`、`ctl`（使用者 10-14「按照建議」）；ctl 是別人寫、程式讀的可寫面，state 是唯讀面（同上）。
- daemon 的控制資料夾先不管（同上）。
- FUSE 可選，用了更舒服，以後再說（同上）。
- stdin／stdout／stderr＝程式本身的標準對外窗口（輸入、輸出、錯誤）；state／ctl＝程式內部的東西、程式願意分享給大家；兩者完全沒關係（同上）。
- 以函數來看：stdin（一串 JSON）＝args；返回值 ret＝exit＋stdout；途中拋出來的東西（錯誤、警告）＝stderr（使用者 10-14）。
- stdout 可以承擔 yield 的職責（一份一份吐出），但不強制（使用者 10-14：「沒有那麼死」）。
- aos 版 IPC 走狀態外顯側，盡量不碰 stdio（必要時可合）；盡量用 Linux 原生機制（使用者 10-14）。
- stdout（返回值）怎麼設計由程式自己決定，想吐什麼就吐什麼（yield 也好、亂回也好），規範不管（使用者 10-14）。
- daemon 繼承於 loop，所以 daemon 的 stdout 也照 loop 的建議（每回合一份結果＋最後一份總結），不只收工時一份（同上）。
- 放寬 10-12「子程式的結束碼只寫進 exit 檔」：exit 檔照寫，aos-inst 的返回值（stdout）也可以帶子程式的碼（同上）。
- IPC 只需改名、建資料夾、檔案鎖就能達到類似效果；原子性只靠 rename、mkdir（O_EXCL）、flock 三種（使用者 10-14 §1p）；fsync 不強制（第 8 題）。
- 以後還可以配合檔案權限、限制掛載等方式做更多（使用者 10-14，方向，未展開）。
- FUSE 等以後效能很糟時再說（使用者 10-14）。
- daemon 判斷 loop 讀到 ctl 時「4 ms 內連寫兩份會提早回覆」的殘留：等重做 inst／loop／daemon 時一起做，ctl 加流水號 seq、回音改報 seq（使用者 10-14 選「甲」）。
- 窗擴成一族進規範（鎖、號誌、信箱、公告、一問一答…），每種一條：位置由 stdin 參數指定、內容 JSON、用哪個原子動作（研究頁第 1 題）。
- 鎖＝建資料夾（mkdir）＋租約（名牌 holder.json），flock 只當同機加速（第 2 題）。
- 收屍＝pid（＋啟動時間）＋租約並用；確認持有者已死或租約過期，搶的人可以自己收，帶序號防兩人同時收（第 3 題）。
- 等變化＝輪詢保底、inotify 加速；判斷變化比內容或序號，不比 stat（第 4 題）。
- 信箱兩種都收：Maildir 資料夾（一封封信）、JSONL 追加檔（一條流）（第 5 題）。
- 參數寫法＝攤平 key，窗內自述種類 kind（第 6 題）。
- state 規定心跳：pid＋啟動時間＋開機 id、內容沒變也定期碰、超過 3 倍間隔沒動靜算疑似死亡（第 7 題）。
- fsync 都不強制（第 8 題）。
- 規範：NORMS N-14～N-17。
