## 3f. 使用者第二輪口述：從頭開始，從 daemon 說起（10-11 晚，照原意整理）

使用者：「我要從頭開始，從我們的 daemon 開始。」回到最開始的源頭——我們要對 agent 代理人做排程、資源管控；agent 是一個函式，這個函式是一個 S 表示式，**S 表示式我打算拿來當 LISP 用**。

### 3f.1 檔案系統就是 LISP；aos inst 是求值動作

- 更早之前就想過：**Linux 檔案系統就是一個 LISP**。
- 在此之上設計了 **aos inst**：指定某一個檔案，它就去執行相關的 POSIX 呼叫。
- aos inst 的定義分兩層：
  - 最基礎：就是普通 POSIX 呼叫，不用說。
  - 更深層：**指定一個資料夾**，它會自動尋找資料夾裡的 inst JSON 檔。這等於**在執行這個資料夾**＝**對這個資料夾求值**＝把資料夾當 LISP 的 list。
- **我們取的就是這個定義：執行某個資料夾＝對某個資料夾求值。這是一個求值動作。**

### 3f.2 inst → loop → daemon：層層遞進

- 有了對資料夾求值的動作，接著是怎麼讓它變成 daemon。它是慢慢演進來的：
  1. **aos inst**：一個求值動作。
  2. **aos loop**：讓它持續執行，可能每隔幾秒執行一次——早期的 aos loop 就是連續執行 inst。
  3. **node**：再上一層引入節點的概念——aos loop 所服務的那個資料夾就是一個節點。
  4. **daemon**：節點這麼多、loop 這麼多，要統一管理，就是 daemon。最早的 daemon，所有的 loop 都在這邊管理；它會根據節點區分資料夾是誰管理的、做排他性；也可以做監控。
- **daemon 可以牽動 daemon**：daemon 所指定的 inst 可以是另外一個 daemon。daemon 跑了一個 inst、跑了一個 loop，去跑某一個東西，那個東西可能是另一個 daemon。所以是層層遞進：普通 inst → loop → daemon。

### 3f.3 inst 求值不像普通 LISP 會還你一個值

- 普通 LISP 求值完會還給你一個東西。**inst 求值之後，它搞不好就一直在那邊跑，根本不理你。**
- 它所謂「還給你的東西」，就是**還給你一個正在執行、正在被變動的資料夾**。
- 所以返回要自己去做。使用者：「這就是組合語言嘛，assembly。」

### 3f.4 task 與 tick：跑在 daemon 上的中介程式

- task 和 tick 怎麼來的？它們是**在 daemon 上跑的**，是 inst 所執行的程式——**一個 argv 程式**（使用者更正：語音誤成 ARGB，實為 argv），反正就是**一個中介程式，跟 inst、daemon 本身沒啥關係**。
- **task**：最基礎的目標是——單一的 inst 指令、inst 格式沒辦法承擔多個任務，所以有 task、task JSON 去承擔多個任務。不用多說，很好說。
- **tick**：時間，一個定時脈衝、period，反正就是那種存在。一個 daemon 其實只要跑一個 tick 就可以，當然也可以跑多個；**建議每一個節點跑一個**，都可以。

### 3f.5 時空早就成熟：空間照 Plan 9，時間就是 tick-tock

- **空間**：空間就不用說——Plan 9 作業系統、那套 Unix 哲學早就把空間搞定一切了。（語音原話「空間就是只要牙齒不用鎖」，使用者校正為「空間就不用說」。）
- **時間**：就是 tick-tock。tick-tock 就是跑一個 init、跑一個 aos loop，被 daemon 跑著。**大家都可以有自己的時間限制、自己的時間軸、自己的時間觀感。**
- tick-tock 是一種**時間的標準，就是一個時鐘**——你可以看、也可以不看，反正它就在那邊。
- 為什麼要有 tick-tock？**要有時間，後續東西才不會混亂。**
- **時間跟 task 結合起來，才是一個好的 node、一個好的節點。** 這是第二層。
- **所以時空都已經固定下來了。**

### 3f.6 第三層（kernel／核心）：一個任務包，傾向定義與概念，概念落成協議和格式

- 就像先前說的，第三層本身就是**一個任務包、一些任務的集合**。只是這一層比較傾向於**定義、概念**。
- 概念這一塊會變成**協議和格式**；後續再各自去做實作或擴充。**有了協議和格式大家才可以互通**，這是比較通用的東西。
- kernel／核心這一塊：資源定義、排程定義有的沒的，之前早就說過了（原話「志誠早就說過了」，照上下文記為「之前」），反正就是這樣。要做的是**在 daemon、tick、tasks、inst 的格式上，做我們自己 kernel 的格式**——定義資源的格式、排程能力的格式，那些有的沒的。
- 這個後續再說。使用者相信**最後的協議、最後的規範一整個可能一夜就能描述完，它一定是最簡單的東西**——因為這一層本身就是靈活性很高的東西。
- 這些都是概念定義，後續再說。

### 3f.7 為什麼準備這麼多：全是為了 agent 代理人；agent 本質是狀態機

- 為什麼要準備這麼多東西？**為了最後的 agent 代理人。準備這麼多，都是為了服務 agent。**
- agent 的本質：**一個狀態機，就是變化、變化、變化。每次變化就是在「物件、思考、行動」之間做切換**，就這樣而已。（「物件」為語音原字，照記。）
- 這個狀態機的概念放到我們這套體系下實作，就是 inst、tick-tock，就這一套而已，不用說。
- 使用者：**先玩概念。概念定好，再去做額外的那些東西。** 「其實我們剛剛早就說完了，反正就這樣子；這些弄一弄弄一弄，差不多可以搞了。」
