### 3g.7 kernel 的位置：切在 task 和 tick-tock 之上，不碰 loop 的「下一個 inst」

- 更早期（proto2 還是 proto3 時）說過：**kernel 就是管鎖**；也有點想說 **inst 就是下一個要執行的指令**——那 kernel 就是管「這個 aos loop 下一個要執行的 inst 要誰的指令」。
- 使用者：可以啊，**可是這牽太深了，我不希望。我希望隔開：kernel 就在 task 和 tick-tock 之上就好**（原話「task 和 t-task」，照上下文記為 tick-tock）。在 task 和 tick-tock 之上，kernel 就可以隨便做。
- 切開之後更乾淨。對 kernel 來說資源也「隨便走隨便走」。
- **所以 kernel 這一塊，後續做 agent 的時候順便做就好，因為各家有各家的做法。**

### 3g.8 agent：最普通的很簡單，先做一個 demo；真正的目標是「怎麼讓這個函式方便人寫」

- agent 說是麻煩，**但如果只是要做最普通的，那就很簡單：就是狀態機；過程中需要思考就丟東西到 LLM 那邊**。有需要就直接實作，**先實作一個 demo 出來**，看實作出來的協議（原話「協優波」，照上下文記為「協議」）符不符合概念——其實沒差，後續再改進就好。
- **重點在實作這塊最終要達到的目標**：以 LISP 的形式，做出一個**可以依賴於 LISP 的編譯器**這種東西（語音誤成「編輯器」，使用者更正：編譯器）。那要怎麼把 agent 代理人這個函式——把所有函式——**做成一個可以被呼叫的函式，而且方便人類編寫**。
- 最後搞不好要用 LISP 寫；不過使用者之前早就承諾過：**任何程式語言都可以做 library**（原話「任何程式庫都可以做 library」）。
- 它會長怎麼樣：**回到最開始——一個資料夾就是一個列表；如何編排一個資料夾，就是寫 LISP。**

### 3g.9 agent 是一個資料夾、一個很長的 list；拋棄式使用；library 做的事是 binding

- **agent 是一個資料夾、是一個 node，持續被求值、持續變化。**
- 想請一個（已經設定好的）agent 做事，就是呼叫某一個函式——這個函式可以就是一支程式——丟請求給 agent，agent 就想。使用者：**這太簡單太普通。我要的是可以隨時隨地開啟一個 agent，把 agent 當函式、當一次性的拋棄式使用。**
  - 例：設定一個資料夾，裡面是已經設定好的一個 agent，還沒被 daemon 跑起來。**把這個資料夾複製過來，讓它跑一次，它開始思考。**
- （使用者口中反覆「不對不對、對對對」後落定：）**agent 是一個資料夾、是一個 list。只是 agent 的 list 一般會很長**：要用哪個大語言模型是一個元素、它的 context 又占一個元素、有的沒的又占一個元素、工具又占一個元素……列表很長。
- **所以程式語言（library）做什麼？做 binding、做繫結**：把早就固定好的東西固定好，函式就簡化了，**使用時只要填其中幾個引數就好。**

### 3g.10 例子：引用一個標頭檔＝引用一個已經設好的 agent 資料夾，填一個引數就跑

- **我引用一個標頭檔。** 這個標頭檔已經先幫我定義好了某一個擅長做某些事的 agent——**定義這個 agent 就是某一個資料夾**，裡面已經放好相關的 skills／技能、memory／記憶、有的沒的、還有相關的工具。
- 我引用這個標頭檔＝「我要使用這個資料夾、引用這個資料夾」。
- 具體使用時**不用複製過來**（修正了 3g.9 的「複製過來」）：**就讓它跑起來，但跑起來時它的執行環境在我這邊。**
- 因為它列表裡的元素都已經設定好了，所以我就輕鬆說：**「我要使用這個畫家 agent」，引數就是「幫我畫這一幅畫」。** 它就設定好了、開始跑。就這麼簡單。

### 3g.11 巢狀：list 的元素也是 list，求值時先對元素求值

- **list 內部的元素也可以是另外一個 list。求值時，可能先對列表中的元素求值。**
- 例：畫家 agent 的 list 裡有一個元素是「畫筆 agent」（幫它準備一些東西）。**先對這些元素求值；求值完，畫家 agent 才真正開始對自己主要的元素求值。** 畫筆 agent 本身搞不好也要用大語言模型——**這就是巢狀。**
- 使用者：這很正常的使用方法，一定會遇到的東西。

### 3g.12 人寫這套一定超麻煩，要讓人和 AI 都能用；工具就是被引用的標頭檔，agent 也可以是工具

- 使用者直說：**這塊東西人寫一定會超級麻煩**，要想辦法把這一套弄成**人和 AI 都可以用**的東西。
- 工具就是工具。當初為什麼這樣設：**agent 本身就有執行能力，可以自己吃檔案、做這些事**；所以這一塊可以變成工具。
- agent 這個函式的引數包括大語言模型、上下文等等，也包括工具。使用者發現：**工具對 agent 函式來說，就是被引用的標頭檔**——工具內部真正怎麼執行，agent 不需要懂，會用就好。
- 所以反過來，**agent 也可以變成 agent 的工具**。對啊。
- **所以協議這一塊也要想辦法做相容**（agent 與工具同一種引用方式）。

### 3g.13 閉環：aos 體系的每一樣都基於 inst、都是 shell 指令，所以都是 agent 可用的工具

- 剛剛說的 aos 體系這麼多東西——daemon、tick、task、inst、kernel 等等——**全部都基於 inst**（原話「init」，照上下文記為 inst），**而且本身都是可以在 shell 中被執行的指令**。
- 那是不是：**它們就是 agent 可以使用的工具。** 所以**自我迴圈改進的基礎就這麼閉環、閉合了。搞定。**

### 3g.13b 補：inst 的 JSON 不只那幾個 key；工具的 JSON schema 怎麼變成 argv

（收工後補的。）

- 3g.2 說 inst「只認那幾個 key、不認識的略過」——使用者補：**這個 JSON 裡搞不好會再加別的東西**：九軸的那些特性、traits 特性標籤、資源標籤、乃至優先順序標籤，**各種有的沒的都可以加**。
- **工具這一塊也可以加**在 JSON 裡。agent 的工具加上去之後，就是「呼叫」這塊：**工具是用 JSON schema 做引數限制的**；**引數限制如何轉成 argv**（原話「argb」，同前更正為 argv）——搞不好可以選擇走這條路（schema → argv），**或者我們先給它定義一些通用的東西**。兩條路都還開著。

### 3g.13c 補：可預測性不只看函式本身，執行環境也算在節點裡

- 目前看起來可預測性像是**函式本身的東西，但其實不一定**：同一個函式在不同狀況下執行，可預測性也不一樣；**在比較老舊的硬體上執行，可預測性又會下降**。
- 所以這個函式的每個「可預測性節點」，**不止函式內部的東西，也包括它所在的執行環境**——**一整個合起來才是所謂的執行節點**。
