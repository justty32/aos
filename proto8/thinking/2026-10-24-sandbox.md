## 決定（照推薦定、可翻案；使用者 10-24「都按建議做」）

- **S1 兩層**：**身分**＝s6（`s6-setuidgid`，要先有帳號、要 root）；**命名空間**＝bwrap（user namespace，免 root）。上限＝`s6-softlimit`（免 root）。
- **S2 怎麼套：一支 chain-loading 的小程式 `aos-sandbox`**，寫在叫的那一方的 argv 最前面：`aos-sandbox 設定檔 prog args...`。它排好 `[s6-softlimit …] [s6-setuidgid 帳號] bwrap … -- prog args...` 就 exec 走、不常駐，結束碼與串流都是 prog 的。**aos-exec 一行不改**（使用者 10-22「aos-exec先維持只用標準庫」；s6 報告「別把 aos-exec 養肥」）。不選「aos-exec 依單子欄位自動串」與「只靠手寫 argv」，理由見選項。
- **S3 順序**：上限 → 身分 → bwrap → prog。身分要在 bwrap 前面（bwrap 開了 user namespace 就換不了別的 uid）；不加 `--new-session`（會逃出行程群組，單子的 `timeout_ms`、fsm 轉的訊號打不到，N-41）。
- **S4 宣告與強制的分界**：**強制只在 argv 上**——誰的 argv 寫了 `aos-sandbox` 誰就被關（C-56 寫什麼就做什麼）。**宣告放 `_metainfo`**：函數可以在自己的 `_metainfo` 寫一格 `sandbox`（同一套 key）說「我只需要這些」，kernel 與人看（同 M4：`_metainfo` 只是承諾）；呼叫方要照它關，就明寫 `aos-sandbox _metainfo#/sandbox …`——宣告被拿去用了，但強制仍是 argv 上看得到的那一支。aos-exec、loop、fsm 都不讀它。
- **S5 誰決定關不關：呼叫方**。函數自己關自己沒有意義（要防的就是它）；同 C-67「stack 放哪由呼叫方決定」。
- **S6 設定的 key**（C-54；全選填、不認得的忽略 C-48）：`user`、`base`、`commands`、`ro`、`rw`、`net`、`mem_mb`、`cpu_s`、`procs`、`file_mb`、`files`。**白名單**：沒列到的路徑一律看不到；`/proc`、`/dev`、空的 `/tmp` 一定有；`base` 預設 `/usr /bin /sbin /lib /lib64 /etc` 裡存在的；`net` 預設 `false`（沒給的就是不給）。`commands`＝照 PATH 找到那支指令、把它的資料夾唯讀綁進來（aos 的指令走 PATH，C-61 例外）。`mem_mb` 跟 `_metainfo` 通用 key 同名同義。設定檔可寫 `檔#/指標`；值只解 `$env`（含 `$path`、`$prefix`），不解 `$ref`（N-45 每支程式只解自己讀的格）。
- **S7 錯誤**（P-21、C-54）：stderr 一行 `aos-sandbox: 代號 原因`、退 1：`ArgumentsBad`、`FlagUnknown`、`CfgMissing`、`CfgBad`、`PathMissing`、`CommandMissing`、`UserBad`；`--dry-run` 印出那條 argv、不跑。
- **S8 放哪、什麼語言**：`proto8/sandbox/`（`bin/aos-sandbox`、`root/setup.sh`、`examples/`），Python 純標準庫（同 aos-tick）。不進 impls（不改既有子專案）。
- **S9 自我改進的接線（最小）**：交辦工作區有 `sandbox.json` 就關（沒有＝照舊，寫什麼就做什麼；10-24 晚改成預設就關，見 S11）；run 格跑函數時在 argv 前面接 `aos-sandbox`、把這次的暫時資料夾放在 `IMPROVE_RUN` 給設定用；改進者的 try_run 經 `IMPROVE_SANDBOX` 拿同一份設定。**判準是檢查程式時不關檢查程式**（它就是判準）。改了三個檔共 17 行：`common.py`（`sandbox()`、`run_target` 接線）、`improve.py`（傳 `IMPROVE_SANDBOX`）、`improver/tools/try_run/_entry`。
- **S11 self-improve 預設就關**（10-24 真腦實測前定；使用者 10-24「我開litellm了。其他都按照建議」，照本份原定的翻案判準「拿真模型跑 self-improve 之前」翻過來；**代定、可翻案**）：交辦工作區沒放 `sandbox.json` 也關，用 [demo/self-improve/sandbox.json](../demo/self-improve/sandbox.json)（`commands` aos-exec、只寫得到 `$IMPROVE_RUN`、斷網、`env` 白名單；不放要 s6 的上限，免得沒裝 s6 就跑不了）。為了不成暗規則：預設那份是看得到的檔；工作區的 `sandbox.json` 優先，內容寫 `false`＝明寫不關；要關卻找不到 `aos-sandbox` 或 `bwrap`＝`self-improve: SandboxMissing` 退 1，不靜靜改成不關。翻案＝`common.py` 的 `sandbox()` 改回「沒放就不關」。
- **S12 環境白名單**（同上、代定）：設定多一格 `env`（環境變數名陣列）：有寫＝`--clearenv` 再只帶外面有設的那幾個；沒寫＝照舊整份帶。self-improve 兩份設定都只帶 `PATH`、`LANG`、`LC_ALL`、`LC_CTYPE`、`TZ`、`PYTHONDONTWRITEBYTECODE`、`PYTHONIOENCODING`（這台外面有 `DEEPSEEK_API_KEY` 等，原本被改的函數讀得到、印出來會經失敗例子回到改進者的對話）。
- **S13 `mem_mb` 改接 `-a`＋`-d`**（10-24 真腦實測撞到的修正）：原本接 `-m`，它把堆疊上限也設成同一個數；glibc 開執行緒照堆疊上限配，位址空間馬上不夠，入口是單子的 aos-exec 每次退 1「Resource temporarily unavailable」（給 8 GB 也一樣）。改成只限位址空間與資料段。
- **S14 kernel 信箱預設堵**（使用者 10-24「都隨意」，代定可翻案）：設定多一格 `kernel`（布林，預設 `false`）。`false`＝`AOS_KERNEL` 不帶進沙箱；信箱（`$AOS_KERNEL`）落在任何綁進來的路徑裡、包住某個綁進來的路徑、或 `env` 列了 `AOS_KERNEL`＝`CfgBad`（明說錯，不偷偷蓋掉使用者寫的 `rw`，C-56）。`true`＝信箱可寫綁進來、`AOS_KERNEL` 帶進去。kernel 那邊多一格 `accept`（[aos-kernel-llm](../impls/aos-kernel-llm/README.md)）：`[{"argv", "cwd"}]`，信裡單子的 argv 與 cwd 要一字不差、不能自帶 `envs` 與串流，不合＝回 `InstUnknown`、不跑；有 `accept` 時環境用 kernel 自己的、只疊信裡 `AOS_` 開頭的（寄信的改不了 `PATH`、`LD_PRELOAD`；key 可以只放 kernel 這邊）。沒寫 `accept`＝照舊（閘門透明）。翻案＝`aos-sandbox` 的 `kernel_box()` 拿掉、`serve.cpp` 的 `accepted()` 拿掉。
- **S15 沙箱裡的 agent 現在用不了 kernel**（S14 實測發現，殘項）：bwrap `--unshare-all` 開了自己的行程編號，閘門寫進信號的 pid 是沙箱裡的（例 2），kernel 在外面照 pid＋啟動時間看寄信的人，對不上＝當他不在、把信丟掉（閘門 `LetterMissing`）。不開行程編號那層又會讓沙箱裡的程式 `kill` 得到外面同一個使用者的行程（實測殺得到），所以沒改。要通得換「寄信的人還在」的判法（例：閘門對信裡一個檔拿著 flock，kernel 拿得到鎖＝人不在；flock 跨 namespace 有效），那是動 [llm-kernel](2026-10-24-llm-kernel.md) 結論 4、10 的信號設計，沒做。反過來，信號也不是身分：寫得到信箱就能冒充一個活著的行程（測試用外面 init 的 pid 1），所以 `kernel: true` 一定要配 `accept`。
- **S16 環境白名單改成預設就開**（使用者 10-24「都隨意」，代定可翻案；翻 S12 的「沒寫＝照舊整份帶」）：設定沒寫 `env`＝只帶 `PATH`、`LANG`、`LC_ALL`、`LC_CTYPE`、`TZ`、`PYTHONDONTWRITEBYTECODE`、`PYTHONIOENCODING` 與 aos 的六個（`AOS_ENTRY`、`AOS_WS`、`AOS_STACK`、`AOS_CF`、`AOS_CD`、`AOS_CO`；路徑、不是祕密，裡面的 aos-exec 要 `AOS_WS`、`AOS_STACK` 才接得上原本的 stack）；寫了就只照它（同 `base` 的寫法：預設是看得到的一份表，`aos-sandbox` 的 `ENV_BASE`）。例子跟上：`bash-boxed` 用預設；`cli-tool.json` 另帶 `HOME`、`TERM`（CLI 靠 `~/.claude`、`~/.codex` 的檔登入，不帶 key）；`agent.json` 寫 `kernel: true`、另帶 `AOS_BRAIN_URL`、`AOS_BRAIN_MODEL`（不帶 key）。翻案＝`ENV_BASE` 換成整份。
- **S10 要 root 的步驟寫成腳本、預設乾跑**：`proto8/sandbox/root/setup.sh`；帳號叫 `aos-run`（跑不信任的函數；系統帳號、沒家目錄、不能登入）；工作的地方 `/srv/aos-run`（擁有者是使用者、群組 `aos-run`、2770）；sudoers 只准「`s6-setuidgid aos-run *`」（換得成 aos-run、換不成 root）。

## 實際擋住了什麼（`tests/test_sandbox.py` 22 個，10-24 晚全過；約 5 秒）

- **自我改進的被改函數讀不到判準**：同一支「照 stdin 去 `judge/cases.json` 找答案」的偷看函數——工作區**沒** `sandbox.json`：2/2 滿分、流程以 0「達成」收工；**有** `sandbox.json`（[examples/self-improve.json](../sandbox/examples/self-improve.json)）：兩組都印「看不到判準」、0/2、預算 0 輪用完退 2。try_run 也一樣（不關看得到答案、關了看不到）。
- 沒列的路徑看不到（判準檔、家目錄）；`ro` 寫不進、`rw` 寫得進、`/usr` 唯讀；`/tmp` 是空的私有一份。
- 斷網：預設連不到外面 loopback 上開著的 port，`net: true` 連得到。
- 結束碼、stdin、stdout 原樣轉交；單子的 `timeout_ms` 打得到沙箱裡的程式（143、不留孤兒）。
- `commands: ["aos-exec"]` 才在沙箱裡跑得了 aos-exec。
- s6 那層：`mem_mb` → `MemoryError`、`cpu_s` → 152（SIGXCPU）。
- 身分那層（假 root：`unshare --user --map-root-user --map-auto`）：同一個 600 的檔、同樣綁進沙箱，不換身分讀得到，`user: "1001:1001"` 就 `Permission denied`。
- pi-tools 的 bash 原封不動包一層（[examples/bash-boxed](../sandbox/examples/bash-boxed/)）：寫得進工作區、讀不到外面的檔、連不了網。
- **kernel 信箱**（S14）：預設的沙箱裡 `AOS_KERNEL` 沒帶進去、閘門 `MailboxMissing`、直接寫信箱也寫不到，kernel 跑一次什麼都沒收到；綁的路徑包住信箱＝`CfgBad`。`kernel: true` 時沙箱裡冒充寄信的人寄「`cat` 判準」：kernel 有 `accept`＝`InstUnknown`、判準沒出現在任何回信；沒 `accept`＝判準被印出來（後門真的在）。環境預設白名單（S16）：外面的 key 帶不進去、`AOS_WS` 帶得進去。拿掉信箱檢查、預設改回整份帶，各有一案紅；kernel 拿掉 `accept` 比對或環境過濾，`test_cli` 的 I 段紅（10-24 晚實測後還原）。
- 會紅：拿掉 self-improve 的接線 → 「有 sandbox.json 也讀得到」那個紅；拿掉 `--unshare-all` → 斷網與 argv 形狀兩個紅（10-24 實測後還原）。原本 self-improve 的 11 個測試照舊全過。

## 要使用者用 root 做的

```
sh proto8/sandbox/root/setup.sh            # 先乾跑看要做什麼
sudo sh proto8/sandbox/root/setup.sh --apply
sudo -n /usr/local/bin/s6-setuidgid aos-run id      # 驗：uid 是 aos-run
```

做了四件：s6 四支（`s6-setuidgid`、`s6-applyuidgid`、`s6-envuidgid`、`s6-softlimit`）從試驗場放進 `/usr/local/bin`（或改裝 AUR 的 s6）；建 `aos-run`；開 `/srv/aos-run`；加 `/etc/sudoers.d/aos-run`（先 `visudo -c` 驗過才放）。拆掉的指令在腳本最後一行。之後要用身分層：`sudo -n s6-setuidgid aos-run aos-sandbox 設定檔 prog…`（身分在最外面，設定裡不寫 `user`），或由 root 起的 daemon／kernel 在設定裡寫 `"user": "aos-run"`。

## 邊緣狀況（還沒問使用者）

- **kernel 信箱**：S14 預設堵、開了要配 `accept`。還剩：`accept` 名單裡的腦照信裡的 `AOS_WS`、`AOS_STACK` 動檔（agent-ivy 的 brain.py 會搬 `$AOS_WS/new/` 的題目、寫 `$AOS_STACK/current.txt`），寄信的人把它們指到別的 agent 的工作區就能借 kernel 的手去動；共用信箱看得到別人的信（含整份環境）；aos-sandbox 只認 `AOS_KERNEL` 這個名字，信箱用別的名字傳進來的它看不出來；沙箱裡用 kernel 走不通（S15）。
- **環境變數**：S16 起沒寫 `env` 也只帶預設那幾個；`env` 自己列了 key 的照帶。
- **`procs`（`-p`）是整個使用者的行程數**：用自己的帳號跑時，瀏覽器等行程都算進去，設小了一開跑就失敗；只有專用帳號（`aos-run`）時才有意義。比較準的是 cgroup（選項）。
- **`mem_mb` 是虛擬記憶體上限**：會先預留大塊虛擬記憶體的程式（Go、Java、Node、某些 LLM 函式庫）可能一起跑就失敗；Python 小程式沒事。
- **綁進來的路徑會帶出上層資料夾的名字**：綁 `/home/lorkhan/repo/…/x`，沙箱裡 `ls ~` 看得到 `repo`（空殼、看不到內容）。
- **cwd 不在沙箱裡**：bwrap 靜靜改到 `/`；相對路徑的 prog 會找不到。
- **符號連結指出去**：`ro`／`rw` 裡的連結會照指到的地方綁；函數在 `rw` 裡自己做的連結指到外面，沙箱裡看不到（指到的地方沒綁）。
- **身分層的權限**：換成 `aos-run` 之後，它進不了 700 的家目錄、也進不了 `mkdtemp` 開的 700 暫時資料夾——self-improve 的暫時資料夾要改到 `/srv/aos-run` 底下才能配身分層用（現在只配命名空間層）。`sudo` 預設清環境，`PATH`、`AOS_*` 要另外帶（`sudo --preserve-env=…`）。
- **stack 也得綁**：包住 `aos-exec` 時，它會在沙箱裡建 `$AOS_STACK`；stack 沒列進 `rw` 就建不了（或建在沙箱的 `/tmp`、跑完就沒了）。
- **巢狀的沙箱**：沙箱裡再叫 `aos-sandbox`：bwrap 在 user namespace 裡再開一層可以，但 `user` 換不了（不是真 root）。
- **只在 Linux、要開 user namespace**：有的發行版或容器關了 unprivileged userns，bwrap 就起不來（`aos-sandbox` 不會降級成不關，直接是 bwrap 的錯）。
- **`/etc` 整個唯讀綁進來**：`/etc/passwd`、`/etc/hosts` 看得到（本來就是誰都能讀的）；`/etc/resolv.conf` 指到 `/run` 的機器上 `net: true` 也解析不了名字（`/run` 沒綁）。

## 選項（沒做）

- **aos-exec 依單子欄位自動串**（例單子多一個 `sandbox` key，aos-exec 在 `argv` 前面插 `aos-sandbox`）：要改 aos-exec（`src/inst/fields.cpp` 收第 11 個 key、`run_inst` 前面插 argv；impls 的 aos-exec README 單子表多一列），也撞使用者 10-22「aos-exec先維持只用標準庫」與 s6 報告的「加旗標前先問能不能交給鏈上另一支」。現在用 argv 前面接 `aos-sandbox` 就做得到，沒做。
- **cgroup 上限**：`systemd-run --user --scope -p MemoryMax=… -p TasksMax=…` 接在鏈上，記憶體算實際用量、行程數只算這一棵；這台可用。
- **landlock**：kernel 有開，可以不靠 namespace 限制路徑（巢狀、容器裡也能用）；要另寫一支小程式或裝 landrun。
- **kernel 也關**：aos-kernel-llm 跑信時接 `aos-sandbox`（設定照信的寄件者），一併堵信箱後門。
