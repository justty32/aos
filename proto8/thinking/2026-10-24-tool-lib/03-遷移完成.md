## 遷移完成（10-24 下午，照推薦做、可翻案）

使用者 10-24：「就，我們在做工具集，這其實挺像是在做函式庫。因爲agent是函數，我們給他的工具就是他在內部自己跑的時候會呼叫的外部函數。既然是這樣，那我們就要把抽象做好，把函數庫做好」；「我現在沒空管這些小事，都按建議做」。今天各處長出來的工具都收進 lib，行為不變為準（各測試照過）。

**lib 現在的樹**（索引在 [lib/README](../../lib/README.md)）：

- `base/` 15 個：read、write、edit、bash、ls、stat、view、json_read、json_edit、mkdir、move、copy、trash、math、clock、run_python。
- `aos/` 10 個＋共用模組 `aos_ws.py`：memory（連 heap.py）、send_message、check_inbox、spawn_agent、ask_agent、agent_status、make_json、make_tool、explain_aos、try_run。
- `agent/` 3 個＋共用模組 `agent_tool.py`、`cli_session.py`：pyfix（子 agent 在裡面）、claude、codex。

**逐項**：

1. demo/pi-tools、demo/file-tools 收進 base 後刪掉：ls 只有一份（含 file-tools 的 `children`、`aos` 記號、`exec`、JSON 頂層 key）；file-tools 的 `common.py` 攤回各工具、錯一律 stdout 同一行（不用 `{"error"}`）；agent-pip、agent-kai 的 read、self-improve 改進者的 read／write／edit、sandbox 的 bash-boxed 都指 base（bash-boxed 用 `timeout_s`）。
2. json_edit 介面不變、交給 aos-json 寫（代定 14）：先在記憶體照規則全部做一遍（錯誤代號在這裡定），合了才 `aos-json batch --parents`／`append`／`del`，只重寫有變的那塊。路上經過 `{"$ref"}` 物件時 aos-json 拒絕（`WriteFailed`）。**json_read 不換 aos-json**：aos-json 的 peek 輸出跟 json_read 的摺疊不同，要分錯誤代號又得自己先解析一次。
3. math、clock 在 base（照契約：錯也印 stdout、壞 stdin＝`ArgumentsBad`；clock 是 python3 才能驗 stdin）；hal、kai、talk 掛捷徑。**agent-dan 自己那份留著**：它是 aos-ai spawn 的預設範本、也是 artifact 的對象；agent-liv 的 clock 也留著，示範「同名自己的贏」。
4. 錯誤要停 vs 回給腦（lib/README「工具只報錯、停不停由 agent 決定」）：所有庫工具「模型的錯」也退 1、一行錯；靠腦自己改的 agent（agent-meg、talk 的 member、agent-gus、pyfix-agent）act 是「工具退非 0 回給腦、不停」（同 agent-pip）。talk 自動回信寄不成寫在答案後面、環境壞了才停。
5. run_python 在 base（不是 agent 層：它是行程原語）：逾時算 `CommandFailed`、整群 TERM→KILL；程式寫在自己的小格（規則 8 的例外）。try_run 在 aos（跑一個 aos 函數的暫時複本）：參數 `timeout_s`、逾時算錯。
6. memory、send_message／check_inbox、ai_tools 六個在 aos；`$AOS_HEAP`、`$AOS_ROSTER`、`$AOS_AI_ROOT` 照原樣留（規則 4 的例外，寫進 README）。ai 六個的錯代號照 aos-ai 的（`NameBad`…）。`aos-ai spawn --tool` 從 lib/aos 拿。
7. human（aos-say／listen／chat）與 aos-ai 的「放題、等答案、讀 stack」共用 `lib/aos/aos_ws.py`（放題一律先寫工作區頂層暫存檔再 link 進 `new/`）。
8. pyfix 在 agent 層：① 根：子 agent 的 act 一律 `aos-exec --ws $PYFIX_DIR tools/<名>`（沒設＝`DirMissing` 停），自己的 `$AOS_WS` 是收題交答案的小格；② 模型的錯：照 4。子工具是 base 的 ls、read、write、edit、bash（參數名跟著庫，system.txt 照寫）；`PYTHONDONTWRITEBYTECODE` 往下帶。轉接的通用那段在 `agent_tool.py`。
9. agent-fay 的 claude、codex 在 agent 層、`cli_session.py` 是庫的共用模組（不假設自己在哪隻 agent 底下；agent-fay 根留一條捷徑給 attach）；工具叫的錯照契約開頭是工具名、stdout 也印，參數錯是 `ArgumentsBad`。
10. 從 agent-dan 抄的 eve、pyfix-agent、fay、hal、kai、liv、meg、pip、talk member、self-improve 改進者都有 `AOS_KERNEL_REPORT` 那幾行（gus 的 shared.py、hal 的 compact/ask.py 問腦寫法不同，沒抄）。
11. aos-ai spawn：範本裡指出範本的相對捷徑（掛庫的工具）複製後改成絕對捷徑。
12. agent-liv 的 act 照 agent-pip：庫的工具出錯回給腦、不停（見上「做了什麼」）。

**沒搬的**：agent-gus 的小念頭 `thought.json`／`thought.py`（見下 10-25）；aos-json 自帶的 `tools/json`、`tools/json_edit`（小念頭式兩步改）留在 impls、跟它的測試在一起。agent-bob 的 `cathy`、`stamp` 是非腦的工具（格直接叫），不在範圍。

**現行行為**（照 lib/README 的規則）：工具的錯一律在 stdout 也印一行、退 1；用 agent-dan 範本的 agent 也把工具錯回給腦（[tool-calls 文末](../2026-10-23-tool-calls/02-結論.md#10-24-定叫工具與小念頭的失敗回給腦)）；meg、talk、gus、pyfix-agent 的工具「環境錯」（`HeapBad`、`RosterBad`…）也回給腦、不停（think 那頭的 `HeapBad` 停）；bash／run_python／try_run 逾時算錯；bash、try_run 收 `timeout_s`。

## 邊緣狀況（攤出來，不擋）

- **捷徑只有 Linux**；repo 在別的檔案系統 checkout 會變成普通檔，agent 叫工具時 aos-exec 讀到一個不是 JSON 的小檔＝`EntryBad`。10-19 使用者「先只考慮在linux上」。
- **複製 agent 時捷徑會被解開或斷掉**：`cp -r` 會把庫的工具複製成真資料夾——行為一樣，但那隻就不再跟著庫更新；`shutil.copytree(symlinks=True)` 留捷徑，但相對捷徑複製到別處會斷（aos-ai spawn 改成絕對捷徑）。要保留捷徑用 `cp -a`。
- **庫一改全部的 agent 立刻變**（沒有版本釘）；要釘住的複製一份。
- **工具的 `AOS_CD` 是庫的位置**（aos-exec 解開捷徑）：工具若想找「掛它的那隻 agent 的檔」找不到——本來就不該（C-52）。
- **bash 擋不住出工作區**、**stack 在工作區裡時腦改得到自己的 history**（pi-tools 紀錄已列）；要隔離靠容器、或把 `AOS_STACK` 放工作區外。
- **json_edit**：`set` 到不存在的中間層會建**物件**（`/zz/0` 建出 `{"zz": {"0": 1}}`，不是陣列）。
- **錯誤行在 stdout 與 stderr 各一份**：被 dan 式「退非 0 就停」的 act 叫時 stdout 那行沒人看，無害。
- **同一個檔兩隻 agent 同時 edit**：沒有鎖，後寫的贏（N-15 鎖現無實作）。
- **形狀檢查只看 `lib/`**：demo 裡各 agent 自己的工具不在檢查範圍，想一起守就把 `test_lib.py` 的 `lib_tools()` 擴到 `demo/*/tools/`。
