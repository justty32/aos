### 中途結論（10-25，原隊長交棒前；B 段還在做，新隊長接著補）

**題目與範圍**：給定場景條件 → 一小段 galgame 台詞＋結構化分數。照使用者兩次限縮，現在是**單一性格單一場景**：宮澤柚葉（傲嬌，精簡寫死的人物卡）、梅雨傍晚河鹿堂、進新書日；題目只動「誰先開口」×「第二組必提詞」兩個開關（4 題）。場景與人評樣本已交頂層、凍結。**這輪沒有人評**（使用者在外面），只用自動評分＋外部可驗的錨。

**fable 的拆法（目前的樹）**：
```
galtxt-b/   agent：loop→fsm 一圈六格（fsm 沒有條件轉移 → 每格「不是我的回合就退 0」，靠 stack 檔決定誰做事）
  idle/ brief/(+tables/) draft/ check/ judge/(+benchmarks/) deliver/   純程式為主
  draft/tools/director/   agent → 單發腦函數 → 查表純程式（走完一生，舊版留 versions/）
  draft/tools/plan_lint/  純函數（beat 表文法）
  draft/tools/writer/     agent（還靠腦），已抽出 tools/trim（純程式）、tools/lint（捷徑）
  judge/tools/critic/     單發腦函數，評分的尺、刻意凍結
  lib/lint/               純函數，check 與 writer 共用
  train/ human/           訓練迴圈（score、pick 已做）與人評匯入
```
每層理由：一圈六格是 galtxt「固化階梯／評分級聯」的直譯（查表→寫→檢→評→交），貴而不確定的節點（寫、評）各自獨立一塊；第 2 輪在「寫」前面插一個可驗的程式節點（beat 表＋文法校驗），把一個大 LLM 步拆成「規劃→校驗→填句」。**刻意不拆**：蒸餾表的工廠期 agent（要人審、沒自動驗收）、overgenerate-and-rank（排序沒校準）、翻 repo 外語料的工具（撞沙盒契約，改用 samples 表）。

**實跑**（luna-low）：一題約 1.7～2.4 萬 token、14～20 秒、3～5 次問腦；round2 Q01 6／Q08 4，round3 收攏後 5／5；限縮場景基準 6 次平均 4.33／6，同題總分 σ 0.58（全部來自 lint 語域規則——腦多寫一行旁白或多一個感嘆號就扣分，交給程式就歸零，所以抽出 `trim`）。

**`_metainfo` 盤點（第 3 輪 fable 只看表）**：token 宣告普遍低估 2～3.5 倍（只算了要寫的台詞，沒算 prompt 帶的稿紙與 history 重送、沒算自檢）、時間普遍高估 2～4 倍；max 都沒撞到。錢在 writer（約 60% token）、時間在 director（約 37%）。優化前三名：director 換純程式、writer 自檢改成程式先跑、稿紙分視圖。格式缺口：每次 vs 每題混用（要 `unit`）、捷徑列沒資料、data／dir 夾沒大小、prompt 與 completion 沒分、沒有品質欄、量測方法不透明、樣本數。**之後使用者說壓平成一張表不好**（要樹中有樹、每棵子樹對外描述自己），收表程式降為除錯工具。

**反向收攏（第 3 輪）**：判準先問要不要檔案系統特性（可執行入口、捷徑、腦要叫的 `tools/<名>/`、權限、多寫者／版本庫單獨追蹤、>8 KB、要自己的 stack、被 ≥2 處叫），撞到就不動；沒撞再看薄的訊號。結果：director、critic 由 agent 縮成單發腦函數（5→4 級）、plan_lint 從 lib 搬回唯一呼叫者；沒有任何葉片縮成 JSON（撞到的全是上述特性）；`tools/` 單工具中間層撞慣例 P-33、留給使用者。aos-grow 的 `down` 不夠用（不認 agent 形、捷徑、併層、`_metainfo` 跟著搬），原型 `plan/aos-fold`。使用者後來說「子樹會很深」、目標是整棵樹不靠 LLM——**收攏不急，只併真的空殼**。

**節點生命週期（B 段已做的一步）**：director 走完 agent → script（查表、查不到才問腦）→ pure（只查表），前版留在節點內 `versions/`；呼叫方一字未改。表外的輸入照 ML 的做法：降級照產（通用 default 表）、記難例到自己的小格，下一輪由腦當老師示範再蒸餾進表（待做）。

**對 fable 的評估（中途）**：拆得好的——第 1 輪就看出 fsm 沒條件轉移、用 stack 檔繞過並標成方向性問題；第 3 輪只看表就抓到「錢在 writer、時間在 director」並給出可驗的優化順序；收攏判準先列檔案系統特性再逐個套，結論保守而有據；每輪都把跟原則衝突的點單列、不硬拍板。要人修的——宣告值是沒跑過時估的（「跑一次就回填」這一步規劃裡沒有）；驗收要求偶爾互相打架（實作者代定）；第 5 輪自己重選了場景、沒對齊已發出的樣本（隊長攔下）；規劃文件越寫越長（round4 45 KB），實作者要的只是清單。

director 自己 3.5k → 0、時間 −24%、分數沒掉；但根 token 只 −4.6%（驗收要 −15%）——writer 漏給 lint 參數多一次來回、多自檢一回，把省下的抵掉。trim：腦 6/6 有叫、6 次改字 0（lint 自檢已修乾淨），token 反 +4%。**結論：確定性的提升主要來自 director 固化成表；trim 的價值是「保證」不是「改善」**，叫它的那趟來回才是成本——所以下一步是把「最後過 trim」與「補 lint 漏參」寫進程式（act），不留給腦決定（見自我優化）。

**接不住的輸入（照 ML）**：表外題（道具「舊車票」）→ 純程式 director 降級用 default 表照產（5/6）、難例寫自己的小格 → `train/record` 收 → `train/apply teach`：拿 `versions/v0_agent`（舊的腦版）當老師示範一次（3.5k token）、plan_lint 驗、專名換回佔位、寫進 `plans.json` → 第 2 輪同題不再降級（5/6）。即「降級照產＋難例＋下輪補」能跑，老師就是節點自己的前一階版本；缺口：腦用的短名（「柚葉」）沒換回佔位，換人物時要短名對照表。

**梯度＝與 `_metainfo` 同形的 diff**：數值給 `delta`、非數值給 `from/to`（評級、stage）、集合給 `added/removed`、文字進 `notes`；只算被動到的節點與往上一路。teach 那一步的真實梯度：plan_template `rollup.counter_rows 4→5`、`counter_degraded 1→0`，director `hard_cases.counter_open 1→0`，根 `反差 +0.1、承接 −0.2`。分攤（`gradient_share`）：有貢獻按 |貢獻| 比例，沒有就分給這一步動到的工具；`gain`＝好變化÷千 token，進挑子樹的分數（`λ_gain`）。**貢獻**目前只有 ablation 開關量得出（關掉某子樹看分數變多少）：trim 開關前後分數差在雜訊內 → 量不出貢獻；director 的貢獻主要在確定性與時間，不在分數。準度受雜訊限制：4 題×1 的單次 token 浮動約 ±3k，比多數候選改動的預期差大一個量級——**要比較小改動得加樣本或改用確定性高的指標**。像反向傳播的地方：誤差（梯度）沿樹往上記、往下分給負責的工具；不像的地方：沒有可微的連續量，分攤靠「誰被動到」與 ablation，判斷輕重靠另一棵樹。

**判斷器樹與三樹關係**：`train/arbiter/` 是 critic 形的單發腦函數，讀兩條候選的預期梯度回 `better／why／weights_used`；判 ≥8 次後把權重平均成 `priority_rules.json`（固化成表、只在平手時問腦），帳記在它自己的 `_metainfo.ratings.judgments`（accuracy、human_agreement）。實跑一次：候選 a＝交稿前必過 trim、b＝補 lint 漏參；它選 b，理由裡自己讀出「拿掉 trim 叫用後漏參可能回來」這個表上沒有的交互作用。套 b 跑 4 題：分數全 5，但腦 4 次都自己帶了參數、補參沒觸發，根 token 反 +3.4k（自檢兩回，與 b 無關）→ 只核了一邊（`partial`），accuracy 這輪算不出。關係：台詞樹被優化器改、被 record 寫；優化器（`train/optimize`，程式從 `_metainfo` 推候選）提兩條、判斷器挑、apply 只改被挑的子樹；判斷器只讀梯度、被 record 回頭查；三者都有 `_metainfo`、都走同一條 agent→表的固化路。錨只進台詞樹的分數與判斷器的核對，不被任何樹改。

**自我優化（使用者途中補）**：`lib/selfopt/` 一包可掛到任何節點：read_self、read_runs、edit_self（只准改白名單檔、寫前存 `versions/`）、extract_tool、run_self_test（分數由凍結的 check／judge 打，不是自己打）、note、claude_code（`claude -p`，cwd＝節點複本、只給讀寫檔工具）。越界由程式擋（`guard.py`：只寫自己資料夾、凍結節點與 `_metainfo`／測試／量尺一律拒、記 `attempted_violation`、預算上限），不靠 prompt。三次實跑（訓練場，不動 repo 樹）：
- gpt 優化 writer：引「trim 6 次沒改字」把 trim 拿掉 → 根 token −16%，但自測就掉回 4 分、旁白違規回來；它的 note 承認沒驗證，改動仍留著——**自己拆自己的安全網**。
- claude code 優化 writer（8 輪、24 秒、0.10 美元）：保留 trim、改成交稿後程式自動叫、lint 漏參由程式補（用的正是 apply 剛加的 `act_rules.json`）→ 5 分、0 違規、根 token −32%（1 次）；無越界。
- gpt 優化純程式節點 plan_template（臨時配腦）：第一次照字面替換猜錯縮排、預算用完；加 JSON 指標寫入後第二次把難例補成表的一列（等同 teach）。
自我 vs 外部優化器：自我的好處是看得到自己的細節（讀自己的 history 找出漏參）、一步就改到位；風險是改壞自己（拿掉安全步驟）與作弊（改測試、改量尺）——後者只能靠程式邊界＋量尺凍結＋外部重跑擋；**改動要外部重跑 ≥2 次、分數掉就自動退回**（還沒做）、拿掉「保證型」步驟前要先有 ablation 證據。工具包成熟前 claude code 當主力（使用者原話），台詞樹本身的腦仍是 gpt。

**結構化場景（使用者途中補）**：人物卡、地點卡、事件節拍、稱呼規則、禁詞拆成一格一事實（243 格，id＝`<表>/<路徑>`；柚葉題用到 189 格），仍是 JSON、不長成資料夾（沒有任何一格要單獨權限、單獨被寫或單獨 git 追蹤）；brief 照版面組回原樣，**給腦的稿紙逐字不變**（7 份比對 diff 為空，不必重跑真腦），另帶 `cells_used`。粒度判準：拆到「程式會單獨查／改／歸因」為止。拆了有用的：稱呼、禁詞、穿幫詞、預算、口癖（lint 違規現在帶 `cell`，梯度能說扣分是哪一格）、兩個開關對到 `opening/<誰先>`、`props/<道具>`（加題＝加一格）、傲嬌的「否認→讓步→遮掩」三段已是可接 hand_over 句式表的格。沒用（現在只有腦讀）：profile 事實、語氣片段、習慣；不該拆：風格示範 samples（拆句毀節奏）、一條 canon 內的子句。

**子樹對外描述（樹中有樹）**：每個節點 `_metainfo.rollup` 由 `train/record/rollup.py` 每輪由下往上算（子樹 token、最不固化的階、確定性、難例數、節點數），只寫訓練場複本；repo 的樹只印不寫。捷徑子樹照抄目標的 rollup——重用時帶著走。現況（`rollup.txt`）：brief、check、deliver、director 整棵、plan_lint、trim、lint 都是 pure（0 token、確定性 1.0）；**還靠腦的只剩 writer（約 2 萬／次，tools 階）與 critic（約 3.6k，刻意凍結的量尺）**。下一步最該固化的是 writer 的「交稿順序」（freeze_order／補參，claude code 那次已示範）與反差拍句式表（hand_over，未做）。和六級／收攏的接法：生命週期往下走一階，資料夾就變得更「實」（腦殼→表→純函數），收攏只併真的空殼。

**錨與漂移**：有錨＝lint 的護欄／稱謂／canon／必提詞（規則寫死、不被任何樹改）、雜訊 σ、表外題的降級旗標；沒錨＝critic 的語意四維與判斷器的權重（分數的大半）。漂移量了兩條線：critic 檔案與凍結的 critic_v0 相同 → 漂移 0；critic_v0 評現在的稿 −0.06，在同稿重評的雜訊（±0.1～0.15）內；lint 維與 critic 維沒有「critic 升、lint 沒升」的可疑型。能看見、擋不住；真擋要人評或人手寫的正解（這個場景沒有）。

**塔**：這輪做到第二層（判斷器、優化器各自有 `_metainfo` 與固化路）就停；第 N 層的成本是下一層每步驗證的倍數（判斷器一次判斷要兩條候選各跑 4 題才核得到，≈8 萬），雜訊也一路疊上去——第三層（優化優化器）在現在的樣本量下量不出東西。

**代定（照推薦先做，使用者可翻）**：① apply 的改動只進訓練場、不自動畢業回 repo 樹（claude code 那次只有 1 次樣本，先多跑再畢業）；② 結構化場景的題目檔（凍結）仍是散文，事件格只在逐字對得上時記；③ lint 標 frozen 但加了 `cell` 輸出欄（只加欄、分數不變）；④ claude_code 不用 bwrap（要帶帳號設定與網路），靠限工具＋事後整樹比對還原；⑤ 「實測誰較好」：總分差 ≥0.5 高者勝，否則根 token 少 ≥5% 勝，否則平手；⑥ B 段 gpt 份額超 1 萬（自我優化第一次失敗那趟）。

**對 fable 的評估（最終）**：round6 規劃（20 KB、§7 有序清單＋驗收＋預算）是這幾輪最好用的一份，實作者照順序做就收得了線，預算估 58 萬、實花約 58 萬。看得準的：「確定性」要定一個量法並先量一次、難例寫小格不寫定義、梯度做成同形 diff、判斷器只判二選一、錨的盤點與「沒錨的是大半」。估錯的：驗收寫了「根 token −15%」「抽 trim token 不增」，沒料到 writer 會因漏參與多自檢把省的吃掉——它對 agent 節點的**行為成本**（來回次數）估不到，只估得到結構；兩條候選的預期差（約 100 token）小於雜訊 30 倍，判斷器示範注定判不出。整體：系統設計（切哪、什麼該凍結、往哪個方向固化、怎麼記帳）拆得好；數字預期要靠跑一次回填，這仍是人／隊長要補的一環。
