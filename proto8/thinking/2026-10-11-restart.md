## 2. 使用者 10-10 晚上河堤邊的思考（10-11 口述，照原意整理）

### 2.1 目標：aos 是什麼、為什麼要有它

回頭看現在這套「aos 時空架構」，它本身是為了一個構想：**方便大語言模型使用**。再往上一層，它是**一套新的作業系統**。

為什麼需要新的：
- 現有作業系統的最佳化目標很單純——排程、資源分配，為的是速度、記憶體消耗。
- **AI 時代要最佳化的東西變多了**：可用性、人類可理解性，還有有的沒的。
- 不同的最佳化目標需要不同的演算法、不同的東西。所以需要一套新的作業系統核心。
- 這麼多樣的東西不可能全靠人手寫，最後還是得用大語言模型去做——所以繞回來，**還是得讓大語言模型方便使用這個東西**。

### 2.2 例子一：agent 的能力就是資源，分任務就是排程

- 某個 agent 處理某方面比較方便，就把那類任務分配給它——這是一種資源分配、一種排程。
- 如果這個 agent 一次只能處理三四個任務，就得排優先級：有限資源下，誰優先級最高。
- **算出誰優先級最高，本身就是一套新的排序演算法。** 現有 OS 從頭到尾只照速度和記憶體最佳化；未來的最佳化目標是多元多樣的。

### 2.3 例子二：畫家就是一顆 CPU

一個人類畫家，擅長畫人物、不擅長畫風景，一週能畫三四張；畫了四五張就想出去散心，隔一週再回來。

- 他是一種**運算資源**。CPU 是我們給指令、它算出東西；畫家是我們給指令、他產出畫。
- CPU 同時只能處理一些東西，有快取：手邊有的直接用，沒有的要再去找，找的時間影響處理時間。畫家也一樣——他有靈感（手邊有的），沒靈感就要去找。
- 分派問題：手上有十張人物畫需求、五張風景畫需求。這個畫家也能畫風景，但畫不好；另一個風景畫家很忙，一週只接一次單。那這週要給人物畫家分配多少、分配什麼？
- **這是全新的資源分配、全新的排程**，這就是 aos 要處理的東西。

### 2.4 目標的邊界（使用者說「目標先到這邊」）

要搞清楚的是：所謂的**任意目標、任意資源、任意排序演算法、任意排程演算法——到底有多任意，範圍可以有多寬廣。**

### 2.5 技術棧：照目標往下疊

有了目標，接著是怎麼照目標設計技術棧。由下往上：

**第 0 層：現有作業系統（Linux）。**
一切終究要拿去運算。現有 OS 已經能承擔基礎的事——CPU、GPU 和各類硬體運算資源的分配。作業系統本質上就是幫忙管理計算，所以**aos 蓋在現有 OS 上**，不重做這一塊。（使用者：不用管這算不算作業系統，反正就是我們的技術棧。）

**第 1 層：基建層＝daemon。**
需要一個介面把 aos 和 Linux 分開，讓這一層**完全處理 Linux 那邊的事**：許可權、身份、記憶體、硬碟、行程……最好都在這一層。這就是 daemon。有了它，aos 等於有了「硬體」。

**第 2 層：時空。**
在 daemon 之上實作時間和空間，這兩樣最重要。
- 空間＝東西存在的地方＝**資料夾**。
- 時間＝**tick**。不用特別定義，反正它很重要。
- 這一塊**已經定好了，不用再說**。

**第 3 層：資源分配、排程等等。** 在時空之上。（還沒展開，使用者說要先回頭看一下。）

### 2.6 為什麼是檔案系統、POSIX、JSON

因為**大模型好處理**。這些東西是模型天生就會的，所以它對這套體系有天生的**自省、自我反省的能力**。

### 2.7 三個定義：計算任務、資源、排序演算法

先定義什麼叫資源，而這要先定義什麼叫計算任務。

**計算任務＝一個符合 POSIX 呼叫方式的行程**（process），不是 thread。定下來了，不用想太多。這一塊歸 Linux 管，很舒服。所有計算任務都源自 POSIX（argv 能呼叫的東西）；在它之上可以再分種類，但其實不用分，反正看 POSIX 就好。

**資源＝有限的、處理計算任務的能力。**
- 任何計算任務都能透過 CPU 處理；但處理過程中會用到其他東西。**用到的東西若是有限的，它就是資源。**
- 更精確：一個計算任務（以 POSIX 行程為單位）若需要某個**有限的、用來處理它某些特定行為的東西**，那個東西就叫資源。
- 例子：一個任務呼叫 `scanf` 請求人類輸入；人類一次最多處理三四件事。所以這個 `scanf` 需求的是「**人類輸入**」這個資源。

**排序演算法＝分配哪個計算任務先給哪個資源處理。** 就這樣，不用多說。

### 2.8 一切都是計算任務

- **排序、資源分配本身也是計算任務。**
- **資源本身也當作 POSIX 行程來看。** 例如「人類輸入」這個資源，在這套體系下最好也是一個 POSIX 行程：別人把東西丟給它，它一次只能處理一個。所以資源可能就是三四個 POSIX 行程。
- 收斂到這裡：**一切都是計算任務。**

### 2.9 計算任務的特性：九個軸＋人類附加的

每個計算任務（不管是什麼）都有幾個固定的基礎特性，例如：
- 有沒有副作用
- 冪等性（處理完這個再處理下一個，方式是否一樣）
- 要不要碰外部檔案
- 是不是持續性的
- 有沒有 entry
- 確定還是不確定（跑大語言模型的任務就是不確定的）

這些跟資源有點像，但它們是**計算性特性**。這幾個基礎特性就是我們現在說的**九個軸**（nine axes；原文在 repo 外 `~/repo/ai_core/docs/kb/kb-ss/doc_05_axes_metadata.md`，套到 aos 的討論見 [proto7 axes-astra](../../proto7/notes/thinking/2026-10-04-axes-astra.md)：I/O 型態、生命週期、跨呼叫狀態、資源特性、可中斷性、執行保證、組合模式、環境模式、確定性）。

基礎特性之外，還有**人類附加的特性**，可以隨意定義。例如：「這個計算任務在繪畫上偏現代性」——它就被定義成在繪畫層面有現代性。之後會有一大堆東西，**所以才需要大語言模型來處理**。

### 2.10 排程、排序、資源定義——靠 JSON，可以讓模型生成

- 排程、排序、資源定義這一塊靠 JSON；技術棧一直有這一層，後續很多東西會很容易長出來。
- 排程本身有演算法，可以任意設計程式去寫。
- 可以再做**「生成排序程式的程式」**——它呼叫大語言模型來幫忙生成排序。例如跟模型說「幫我生成一個處理繪畫任務的排序」，模型幫我們定義資源、寫排序。手寫當然可以，但終究不方便。

**到這裡，aos 作業系統核心已經搞定。** 在此之上是 agent。

### 2.11 tick-tock 的本質：讓時間停下來（先簡單提）

agent 的事先不展開，只提一點：
- tick-tock 本質是**定義時間**，讓 agent 可以依據它行事。
- agent 可以說「把 tick-tock 停下來」。只要 tick-tock 正常結束，agent 看到的資料夾狀況**就是那個時間點的狀況**。
- 停下來後，正在跑的任務要不要被迫停止？可以，也可以不用——agent 看到的狀況裡可以含「這件事正在跑」。
- tick-tock 是為了**時間停止**。停止之後，資料夾狀況就可以直接**壓成 zip 打包**，很舒服。一般就這樣走。

### 2.12 agent（代理人）看到的時空

- 對 agent 來說，**空間＝資料夾＝它的世界**；時間＝tick。它知道現在是哪個 tick，也可以說「我要看某個 tick 底下的世界」——某個時間點的世界。
- 對 agent 而言，時空就這樣定下來了。

### 2.13 agent 的本質：狀態機，也是計算任務

- agent 本質是一個**狀態機**：這個 tick 在這個狀態，另一個時間點在思考，再一個時間點在動作，一直迴圈。不用多說。
- agent 本身是一個計算任務；它所依託的大語言模型計算，也是一個計算任務。所以它可以直接接進核心，不用特別處理。

### 2.14 agent 也是函式；黑箱；確定性 vs 可預測性

- agent 本質上是一個**函式**。像寫 C 語言 include 標頭檔、用裡面的函式——對我們都是黑箱。
- 一個 LLM agent 持續跑狀態機迴圈、呼叫工具做事，給它東西、它跑一跑、停下來——也是函式。`strcpy` 這類函式和 LLM agent，對我們來說**都是黑箱**。
- 最大區別只在：**使用方式不一樣、計算特性不一樣**。LLM 最重要的差別是**確定性**和**可預測性**不一樣。

**確定性 ≠ 可預測性：**
- `strcpy`：看註解知道它是字串複製，它是確定性的，沒有機率問題。
- 但它可預測嗎？**不是。** 同樣叫字串複製的函式，有的搞不好有記憶體洩漏。
- 所以**可預測性是有主體性的**——「對我而言可預測嗎？對他人而言可預測嗎？」
  - 對寫這個函式的人：100% 可預測。
  - 對我：只看到註解，照經驗想「這函式可能寫錯吧」，可預測性就那樣。
  - 知道它是 C 寫的，可以預測「可能有記憶體洩漏」，但不知道機率。可預測性稍微提高一點，終究不是 100%。

### 2.15 為什麼 `strcpy` 對我可預測、LLM 不可預測

- `strcpy` 我們自己手寫過：一個 for 迴圈、i++、逐字複製。**每一個分支、每個分支的終點、裡面會跑什麼計算，我們都知道**，甚至 CPU 複製哪個位元都清楚。所以對我而言它是確定性＋可預測性都最高。
- 大語言模型不是：它跑一跑會呼叫哪個工具，我哪知道。

### 2.16 怎麼提高 agent 這個函式的可預測性：拆成多個函式，把節點換成寫死的程式

用另一個例子：C++ 的**陣列複製函式**。
- 它對每個元素遍歷，每個元素呼叫它的複製函式——可能是遞迴呼叫自己；元素若是結構，就呼叫結構的複製函式。
- 「跑 for 迴圈、逐元素複製」這段流程我們知道；但**結構複製那個函式我們不知道**。
- 所以：流程的某些部分我們知道，更細微的部分不知道。把流程當成一棵 **S-expression**（S 表示式），就是**有些節點我們知道、有些節點不知道**。

回到 agent：
- agent 也可以當成 S 表示式去跑。只是**呼叫模型的那個節點**，我們不知道它具體會跑到哪裡。
- **要讓 agent 這個函式變可預測，就是把它當 S 表示式去拆**：表示式裡有些節點可以寫成普通程式（可預測性較高的程式），就把那個節點**替換成寫死的程式**。
- 這樣，整個流程**進入「可預測性不高的節點」的可能性就降低**，整體可預測性就提高。
- **agent 可預測性的提高，就是這一塊。**

### 2.17 LLM agent 這個函式的簽名

用機器人比喻，agent 這個函式由三樣組成：
- **腦袋＝大語言模型**：負責思考。
- **記憶**，分兩種：
  - **核心人格＝system prompt**（系統提示詞）
  - **近期記憶＝一般上下文**（普通的提示詞內容）
- **手腳＝可用的工具**。

這就是 LLM agent 的函式簽名。

### 2.18 agent 是複合型的計算任務，所以要排程

- agent 這個函式是一個計算任務；它是一個**狀態機函式**，途中需要呼叫 LLM——而 LLM 本身也是一個計算任務。
- 所以 agent 是**複合型**的計算任務，要做作業系統層面的資源分配與排程。
- 最核心的一個資源分配：**很多 agent 時，誰可以先用大語言模型這個大腦思考。**
- 排序演算法要看的例如：哪個 agent 做的事比較重要、哪些人類使用者想先看哪個 agent 的回覆——照這些排。

### 2.19 agent 自己的消耗很低；貴的是它叫的東西

- agent 的狀態機迴圈本身就是一個 for 迴圈（外迴圈），**計算消耗很低**，可以一直跑，不太需要管它。
- 主要的消耗都在**呼叫大語言模型**那邊；另外**它用的工具**也可能很大，要算進去。
- 但情況會變：例如 agent 換了工具，或它用的模型換成比較貴的、或本地的（要等）。這時候「這個 agent 什麼時候該跑」就變成要排程的事。

### 2.20 今天到這裡

再往下就是 agent **內部**怎麼設計——那塊現在很多人都在做，是後面的事。重點是**先把底打好**，才能做屬於自己的 agent 框架。後續再說。

## 3. AI 整理：今天收斂出來的骨架（給下次接著用）

技術棧    Linux → daemon（完全處理 Linux 那邊）→ 時空（資料夾＋tick）→ 排程資源 → agent
三定義    計算任務＝POSIX 行程；資源＝有限的處理能力；排序＝誰先給誰
收斂      一切都是計算任務（排序是、資源也是）→ 核心沒有第二種東西
標籤      九個軸（計算性特性）＋人類附加的特性（隨意定義）→ 多到只能靠 LLM 處理
格式      全是 JSON；排序程式可以讓模型生成
核心完    ──────────────────────────────────────
agent     狀態機；也是函式、也是計算任務；簽名＝腦袋＋（人格、近期）記憶＋手腳
時間停止  tick-tock 讓 agent 看到某個時間點的世界；停下來就能打包

## 3c. 使用者補充：人手畫這類任務怎麼變成計算任務（10-11，看完圖解後）

> 像是人手畫，這類任務沒辦法直接轉成 POSIX 呼叫，所以更接近**間接抽象化**：由多個任務組成——寄信給畫家、收信、畫歸檔——這樣就能讓他成為計算任務。

AI 讀法：畫家本人不是行程；「請畫家畫一張」這件事被拆成三個 POSIX 任務（寄信、收信、歸檔），畫家在這三個任務之間、在系統外面做事。所以「資源也是計算任務」對人這種資源是成立的——成立在那一串任務上，不是在人身上。
