## 2. 使用者 10-10 晚上河堤邊的思考（10-11 口述，照原意整理）

### 2.1 目標：aos 是什麼、為什麼要有它

回頭看現在這套「aos 時空架構」，它本身是為了一個構想：**方便大語言模型使用**。再往上一層，它是**一套新的作業系統**。

為什麼需要新的：
- 現有作業系統的最佳化目標很單純——排程、資源分配，為的是速度、記憶體消耗。
- **AI 時代要最佳化的東西變多了**：可用性、人類可理解性，還有有的沒的。
- 不同的最佳化目標需要不同的演算法、不同的東西。所以需要一套新的作業系統核心。
- 這麼多樣的東西不可能全靠人手寫，最後還是得用大語言模型去做——所以繞回來，**還是得讓大語言模型方便使用這個東西**。

### 2.2 例子一：agent 的能力就是資源，分任務就是排程

- 某個 agent 處理某方面比較方便，就把那類任務分配給它——這是一種資源分配、一種排程。
- 如果這個 agent 一次只能處理三四個任務，就得排優先級：有限資源下，誰優先級最高。
- **算出誰優先級最高，本身就是一套新的排序演算法。** 現有 OS 從頭到尾只照速度和記憶體最佳化；未來的最佳化目標是多元多樣的。

### 2.3 例子二：畫家就是一顆 CPU

一個人類畫家，擅長畫人物、不擅長畫風景，一週能畫三四張；畫了四五張就想出去散心，隔一週再回來。

- 他是一種**運算資源**。CPU 是我們給指令、它算出東西；畫家是我們給指令、他產出畫。
- CPU 同時只能處理一些東西，有快取：手邊有的直接用，沒有的要再去找，找的時間影響處理時間。畫家也一樣——他有靈感（手邊有的），沒靈感就要去找。
- 分派問題：手上有十張人物畫需求、五張風景畫需求。這個畫家也能畫風景，但畫不好；另一個風景畫家很忙，一週只接一次單。那這週要給人物畫家分配多少、分配什麼？
- **這是全新的資源分配、全新的排程**，這就是 aos 要處理的東西。

### 2.4 目標的邊界（使用者說「目標先到這邊」）

要搞清楚的是：所謂的**任意目標、任意資源、任意排序演算法、任意排程演算法——到底有多任意，範圍可以有多寬廣。**

### 2.5 技術棧：照目標往下疊

有了目標，接著是怎麼照目標設計技術棧。由下往上：

**第 0 層：現有作業系統（Linux）。**
一切終究要拿去運算。現有 OS 已經能承擔基礎的事——CPU、GPU 和各類硬體運算資源的分配。作業系統本質上就是幫忙管理計算，所以**aos 蓋在現有 OS 上**，不重做這一塊。（使用者：不用管這算不算作業系統，反正就是我們的技術棧。）

**第 1 層：基建層＝daemon。**
需要一個介面把 aos 和 Linux 分開，讓這一層**完全處理 Linux 那邊的事**：許可權、身份、記憶體、硬碟、行程……最好都在這一層。這就是 daemon。有了它，aos 等於有了「硬體」。

**第 2 層：時空。**
在 daemon 之上實作時間和空間，這兩樣最重要。
- 空間＝東西存在的地方＝**資料夾**。
- 時間＝**tick**。不用特別定義，反正它很重要。
- 這一塊**已經定好了，不用再說**。

**第 3 層：資源分配、排程等等。** 在時空之上。（還沒展開，使用者說要先回頭看一下。）

### 2.6 為什麼是檔案系統、POSIX、JSON

因為**大模型好處理**。這些東西是模型天生就會的，所以它對這套體系有天生的**自省、自我反省的能力**。

### 2.7 三個定義：計算任務、資源、排序演算法

先定義什麼叫資源，而這要先定義什麼叫計算任務。

**計算任務＝一個符合 POSIX 呼叫方式的行程**（process），不是 thread。定下來了，不用想太多。這一塊歸 Linux 管，很舒服。所有計算任務都源自 POSIX（argv 能呼叫的東西）；在它之上可以再分種類，但其實不用分，反正看 POSIX 就好。

**資源＝有限的、處理計算任務的能力。**
- 任何計算任務都能透過 CPU 處理；但處理過程中會用到其他東西。**用到的東西若是有限的，它就是資源。**
- 更精確：一個計算任務（以 POSIX 行程為單位）若需要某個**有限的、用來處理它某些特定行為的東西**，那個東西就叫資源。
- 例子：一個任務呼叫 `scanf` 請求人類輸入；人類一次最多處理三四件事。所以這個 `scanf` 需求的是「**人類輸入**」這個資源。

**排序演算法＝分配哪個計算任務先給哪個資源處理。** 就這樣，不用多說。

### 2.8 一切都是計算任務

- **排序、資源分配本身也是計算任務。**
- **資源本身也當作 POSIX 行程來看。** 例如「人類輸入」這個資源，在這套體系下最好也是一個 POSIX 行程：別人把東西丟給它，它一次只能處理一個。所以資源可能就是三四個 POSIX 行程。
- 收斂到這裡：**一切都是計算任務。**

### 2.9 計算任務的特性：九個軸＋人類附加的

每個計算任務（不管是什麼）都有幾個固定的基礎特性，例如：
- 有沒有副作用
- 冪等性（處理完這個再處理下一個，方式是否一樣）
- 要不要碰外部檔案
- 是不是持續性的
- 有沒有 entry
- 確定還是不確定（跑大語言模型的任務就是不確定的）

這些跟資源有點像，但它們是**計算性特性**。這幾個基礎特性就是我們現在說的**九個軸**（nine axes；原文在 repo 外 `~/repo/ai_core/docs/kb/kb-ss/doc_05_axes_metadata.md`，套到 aos 的討論見 [proto7 axes-astra](../../proto7/notes/thinking/2026-10-04-axes-astra.md)：I/O 型態、生命週期、跨呼叫狀態、資源特性、可中斷性、執行保證、組合模式、環境模式、確定性）。

基礎特性之外，還有**人類附加的特性**，可以隨意定義。例如：「這個計算任務在繪畫上偏現代性」——它就被定義成在繪畫層面有現代性。之後會有一大堆東西，**所以才需要大語言模型來處理**。

### 2.10 排程、排序、資源定義——靠 JSON，可以讓模型生成

- 排程、排序、資源定義這一塊靠 JSON；技術棧一直有這一層，後續很多東西會很容易長出來。
- 排程本身有演算法，可以任意設計程式去寫。
- 可以再做**「生成排序程式的程式」**——它呼叫大語言模型來幫忙生成排序。例如跟模型說「幫我生成一個處理繪畫任務的排序」，模型幫我們定義資源、寫排序。手寫當然可以，但終究不方便。

**到這裡，aos 作業系統核心已經搞定。** 在此之上是 agent。

### 2.11 tick-tock 的本質：讓時間停下來（先簡單提）

agent 的事先不展開，只提一點：
- tick-tock 本質是**定義時間**，讓 agent 可以依據它行事。
- agent 可以說「把 tick-tock 停下來」。只要 tick-tock 正常結束，agent 看到的資料夾狀況**就是那個時間點的狀況**。
- 停下來後，正在跑的任務要不要被迫停止？可以，也可以不用——agent 看到的狀況裡可以含「這件事正在跑」。
- tick-tock 是為了**時間停止**。停止之後，資料夾狀況就可以直接**壓成 zip 打包**，很舒服。一般就這樣走。

### 2.12 agent（代理人）看到的時空

- 對 agent 來說，**空間＝資料夾＝它的世界**；時間＝tick。它知道現在是哪個 tick，也可以說「我要看某個 tick 底下的世界」——某個時間點的世界。
- 對 agent 而言，時空就這樣定下來了。

### 2.13 agent 的本質：狀態機，也是計算任務

- agent 本質是一個**狀態機**：這個 tick 在這個狀態，另一個時間點在思考，再一個時間點在動作，一直迴圈。不用多說。
- agent 本身是一個計算任務；它所依託的大語言模型計算，也是一個計算任務。所以它可以直接接進核心，不用特別處理。

### 2.14 agent 也是函式；黑箱；確定性 vs 可預測性

- agent 本質上是一個**函式**。像寫 C 語言 include 標頭檔、用裡面的函式——對我們都是黑箱。
- 一個 LLM agent 持續跑狀態機迴圈、呼叫工具做事，給它東西、它跑一跑、停下來——也是函式。`strcpy` 這類函式和 LLM agent，對我們來說**都是黑箱**。
- 最大區別只在：**使用方式不一樣、計算特性不一樣**。LLM 最重要的差別是**確定性**和**可預測性**不一樣。

**確定性 ≠ 可預測性：**
- `strcpy`：看註解知道它是字串複製，它是確定性的，沒有機率問題。
- 但它可預測嗎？**不是。** 同樣叫字串複製的函式，有的搞不好有記憶體洩漏。
- 所以**可預測性是有主體性的**——「對我而言可預測嗎？對他人而言可預測嗎？」
  - 對寫這個函式的人：100% 可預測。
  - 對我：只看到註解，照經驗想「這函式可能寫錯吧」，可預測性就那樣。
  - 知道它是 C 寫的，可以預測「可能有記憶體洩漏」，但不知道機率。可預測性稍微提高一點，終究不是 100%。

### 2.15 為什麼 `strcpy` 對我可預測、LLM 不可預測

- `strcpy` 我們自己手寫過：一個 for 迴圈、i++、逐字複製。**每一個分支、每個分支的終點、裡面會跑什麼計算，我們都知道**，甚至 CPU 複製哪個位元都清楚。所以對我而言它是確定性＋可預測性都最高。
- 大語言模型不是：它跑一跑會呼叫哪個工具，我哪知道。

### 2.16 怎麼提高 agent 這個函式的可預測性：拆成多個函式，把節點換成寫死的程式

用另一個例子：C++ 的**陣列複製函式**。
- 它對每個元素遍歷，每個元素呼叫它的複製函式——可能是遞迴呼叫自己；元素若是結構，就呼叫結構的複製函式。
- 「跑 for 迴圈、逐元素複製」這段流程我們知道；但**結構複製那個函式我們不知道**。
- 所以：流程的某些部分我們知道，更細微的部分不知道。把流程當成一棵 **S-expression**（S 表示式），就是**有些節點我們知道、有些節點不知道**。

回到 agent：
- agent 也可以當成 S 表示式去跑。只是**呼叫模型的那個節點**，我們不知道它具體會跑到哪裡。
- **要讓 agent 這個函式變可預測，就是把它當 S 表示式去拆**：表示式裡有些節點可以寫成普通程式（可預測性較高的程式），就把那個節點**替換成寫死的程式**。
- 這樣，整個流程**進入「可預測性不高的節點」的可能性就降低**，整體可預測性就提高。
- **agent 可預測性的提高，就是這一塊。**

### 2.17 LLM agent 這個函式的簽名

用機器人比喻，agent 這個函式由三樣組成：
- **腦袋＝大語言模型**：負責思考。
- **記憶**，分兩種：
  - **核心人格＝system prompt**（系統提示詞）
  - **近期記憶＝一般上下文**（普通的提示詞內容）
- **手腳＝可用的工具**。

這就是 LLM agent 的函式簽名。

### 2.18 agent 是複合型的計算任務，所以要排程

- agent 這個函式是一個計算任務；它是一個**狀態機函式**，途中需要呼叫 LLM——而 LLM 本身也是一個計算任務。
- 所以 agent 是**複合型**的計算任務，要做作業系統層面的資源分配與排程。
- 最核心的一個資源分配：**很多 agent 時，誰可以先用大語言模型這個大腦思考。**
- 排序演算法要看的例如：哪個 agent 做的事比較重要、哪些人類使用者想先看哪個 agent 的回覆——照這些排。

### 2.19 agent 自己的消耗很低；貴的是它叫的東西

- agent 的狀態機迴圈本身就是一個 for 迴圈（外迴圈），**計算消耗很低**，可以一直跑，不太需要管它。
- 主要的消耗都在**呼叫大語言模型**那邊；另外**它用的工具**也可能很大，要算進去。
- 但情況會變：例如 agent 換了工具，或它用的模型換成比較貴的、或本地的（要等）。這時候「這個 agent 什麼時候該跑」就變成要排程的事。

## 3f. 使用者第二輪口述：從頭開始，從 daemon 說起（10-11 晚，照原意整理）

使用者：「我要從頭開始，從我們的 daemon 開始。」回到最開始的源頭——我們要對 agent 代理人做排程、資源管控；agent 是一個函式，這個函式是一個 S 表示式，**S 表示式我打算拿來當 LISP 用**。

### 3f.1 檔案系統就是 LISP；aos inst 是求值動作

- 更早之前就想過：**Linux 檔案系統就是一個 LISP**。
- 在此之上設計了 **aos inst**：指定某一個檔案，它就去執行相關的 POSIX 呼叫。
- aos inst 的定義分兩層：
  - 最基礎：就是普通 POSIX 呼叫，不用說。
  - 更深層：**指定一個資料夾**，它會自動尋找資料夾裡的 inst JSON 檔。這等於**在執行這個資料夾**＝**對這個資料夾求值**＝把資料夾當 LISP 的 list。
- **我們取的就是這個定義：執行某個資料夾＝對某個資料夾求值。這是一個求值動作。**

### 3f.2 inst → loop → daemon：層層遞進

- 有了對資料夾求值的動作，接著是怎麼讓它變成 daemon。它是慢慢演進來的：
  1. **aos inst**：一個求值動作。
  2. **aos loop**：讓它持續執行，可能每隔幾秒執行一次——早期的 aos loop 就是連續執行 inst。
  3. **node**：再上一層引入節點的概念——aos loop 所服務的那個資料夾就是一個節點。
  4. **daemon**：節點這麼多、loop 這麼多，要統一管理，就是 daemon。最早的 daemon，所有的 loop 都在這邊管理；它會根據節點區分資料夾是誰管理的、做排他性；也可以做監控。
- **daemon 可以牽動 daemon**：daemon 所指定的 inst 可以是另外一個 daemon。daemon 跑了一個 inst、跑了一個 loop，去跑某一個東西，那個東西可能是另一個 daemon。所以是層層遞進：普通 inst → loop → daemon。

### 3f.3 inst 求值不像普通 LISP 會還你一個值

- 普通 LISP 求值完會還給你一個東西。**inst 求值之後，它搞不好就一直在那邊跑，根本不理你。**
- 它所謂「還給你的東西」，就是**還給你一個正在執行、正在被變動的資料夾**。
- 所以返回要自己去做。使用者：「這就是組合語言嘛，assembly。」

### 3f.4 task 與 tick：跑在 daemon 上的中介程式

- task 和 tick 怎麼來的？它們是**在 daemon 上跑的**，是 inst 所執行的程式——**一個 argv 程式**（使用者更正：語音誤成 ARGB，實為 argv），反正就是**一個中介程式，跟 inst、daemon 本身沒啥關係**。
- **task**：最基礎的目標是——單一的 inst 指令、inst 格式沒辦法承擔多個任務，所以有 task、task JSON 去承擔多個任務。不用多說，很好說。
- **tick**：時間，一個定時脈衝、period，反正就是那種存在。一個 daemon 其實只要跑一個 tick 就可以，當然也可以跑多個；**建議每一個節點跑一個**，都可以。

### 3f.5 時空早就成熟：空間照 Plan 9，時間就是 tick-tock

- **空間**：空間就不用說——Plan 9 作業系統、那套 Unix 哲學早就把空間搞定一切了。（語音原話「空間就是只要牙齒不用鎖」，使用者校正為「空間就不用說」。）
- **時間**：就是 tick-tock。tick-tock 就是跑一個 init、跑一個 aos loop，被 daemon 跑著。**大家都可以有自己的時間限制、自己的時間軸、自己的時間觀感。**
- tick-tock 是一種**時間的標準，就是一個時鐘**——你可以看、也可以不看，反正它就在那邊。
- 為什麼要有 tick-tock？**要有時間，後續東西才不會混亂。**
- **時間跟 task 結合起來，才是一個好的 node、一個好的節點。** 這是第二層。
- **所以時空都已經固定下來了。**

### 3f.6 第三層（kernel／核心）：一個任務包，傾向定義與概念，概念落成協議和格式

- 就像先前說的，第三層本身就是**一個任務包、一些任務的集合**。只是這一層比較傾向於**定義、概念**。
- 概念這一塊會變成**協議和格式**；後續再各自去做實作或擴充。**有了協議和格式大家才可以互通**，這是比較通用的東西。
- kernel／核心這一塊：資源定義、排程定義有的沒的，之前早就說過了（原話「志誠早就說過了」，照上下文記為「之前」），反正就是這樣。要做的是**在 daemon、tick、tasks、inst 的格式上，做我們自己 kernel 的格式**——定義資源的格式、排程能力的格式，那些有的沒的。
- 這個後續再說。使用者相信**最後的協議、最後的規範一整個可能一夜就能描述完，它一定是最簡單的東西**——因為這一層本身就是靈活性很高的東西。
- 這些都是概念定義，後續再說。

### 3f.7 為什麼準備這麼多：全是為了 agent 代理人；agent 本質是狀態機

- 為什麼要準備這麼多東西？**為了最後的 agent 代理人。準備這麼多，都是為了服務 agent。**
- agent 的本質：**一個狀態機，就是變化、變化、變化。每次變化就是在「物件、思考、行動」之間做切換**，就這樣而已。（「物件」為語音原字，照記。）
- 這個狀態機的概念放到我們這套體系下實作，就是 inst、tick-tock，就這一套而已，不用說。
- 使用者：**先玩概念。概念定好，再去做額外的那些東西。** 「其實我們剛剛早就說完了，反正就這樣子；這些弄一弄弄一弄，差不多可以搞了。」

## 3g. 使用者第三輪口述：實作上的想法（10-11 晚，照原意整理）

### 3g.1 最終要達到的效果

- 最終會有一個**很方便的、類似程式設計師在用的東西**——一些 library、一些庫。
- 用它寫出來的東西，**最終編譯成基於 aos 體系的一個類似 LISP 的程式**。
- 這個程式**把 aos 體系當作作業系統**，在上面跑東西。
- 這一塊**會很適合 agent**。

### 3g.2 inst 的實作

- 最基礎的早就做過了（原話「install 過了」，照上下文記為「實作過了」）。這邊只是自己再描述一遍：
- inst **吃一些 JSON，有固定的幾個 key**。
- 它會先**按照指示庫（指示集）把它組成一個 JSON**。照指示庫組的時候，**相對路徑會長怎麼樣**是個點：可以透過 **argv 選擇**找目錄是從 **cwd** 來、還是從執行處來——反正就這一塊，哪樣都可以。
- 吃 JSON key 的時候，**它吃它想要的；其他不認識的 key 沒關係**（忽略）。
- 指示庫：使用者本想說最終可以只留兩三個，後來說「算了算了，**都留都留**」。
- 解完之後它就跑。

### 3g.3 loop 與 daemon 的實作

- **loop**：不管它，它會**變成一個 library，整個進 daemon**。
- **daemon**：各種 **Linux 許可權有的沒的，全部都在它身上跑**。它也可以**吃一點控制**（接受一些控制輸入）。
- 這些早就想過了，其實都已經很完善；最終可能再調整一下，重新把控一下狀況——使用者會**去 survey 一下 code**。
- 使用者的判斷：除去一些必要的庫、必要的樣本程式碼（處理比較複雜的那塊、Linux 那塊的東西），**daemon 會是非常非常非常簡短的東西**。

### 3g.4 tick-tock 的實作（使用者講到一半說「這塊我掌握的不夠全」）

- tick-tock 其實早就定下來了，就長那個樣子。這裡只是重新複述：
- **丟給 daemon 跑的都是一個資料夾。** 跟 daemon 說「我要跑這個資料夾」。inst 本身可以跑 daemon、也可以跑資料夾；daemon 當然也能跑一些指定指令，**但那不在正式的使用範圍承諾內**。
- 跟 daemon 說要跑這個資料夾時，可以說：**只跑一次／跑好幾次／無限跑，每次跑間隔多少**——daemon 收這些指令。
- tick-tock 通常是這樣：丟一個資料夾給 daemon，說「這個資料夾的 inst 每五秒跑一次」。這個 inst 指向的是 **aos task（跑多工的那個指令）**；任務表中**最前面是 tick、最後面是 tock**——「不一定不一定，它可能就是兩個連在一起，都可以再想想」。tick-tock 連起來，中間任務跑一跑。
- 講到「其中有些任務它是……」時使用者停下：「**不對，我發現這塊我掌握的不夠全。**」→ 到此為止，不補。

### 3g.5 回頭講 tick-tock：可以跟 node 的狀態變化完全脫鉤；它是一個抬頭看的時鐘

（接在 3h 的概念補充之後講的；因為是實作想法，放這裡。）

- 使用者發現：現在做的 tick-tock 是跟 node 的狀態變化掛在一起的（原話「所打勾的」，照上下文記為「掛鉤」）。**其實 tick-tock 本身可以脫鉤，完全脫鉤。**
- 樣子：**一個 daemon 底下跑一個 tick-tock，loop 持續跑 tick-tock**。被 daemon 管理的其他 node，**有些會訂閱 tick-tock 的通知**，大家就知道現在第幾回合。**它就是一個可以抬頭看的時鐘，就這樣。**
- 要不要給 tick-tock 一個更好的定義：**保證在 tick-tock 之間（或 tick 之後到下個 tick 之間），可以安全地把資料夾壓縮、打包帶走**——時間之間的穩定狀況。
  - 比如 tick 就是起任務（原話「啟用人物」，照上下文記為「啟用任務」）、通知大家第幾回合開始；再通知大家這回合結束、「麻煩把狀態穩定儲存，因為這回合結束了」；之後下個回合會不會來也不知道。
- 這是很重要的特性，**但要不要做成標準配備，不一定**：搞不好是 kernel 的配備；搞不好也不是 kernel 的、也不在 tick-tock 裡——「隨便，反正就是**可選項、但很重要**的東西」。

### 3g.6 脫鉤之後：協議變簡單；kernel 的參照物是時間（tick-tock）與空間（資料夾）

- tick-tock 脫鉤之後「就解放了」：**協議不用那麼麻煩，拆開之後大家都變簡單**。訂閱搞不好也可以更簡單；tick-tock「隨便啊」，後續很容易寫出來，再說。
- tick-tock 和 task 都有了，接下來 kernel 這邊也差不多了。kernel 就是先前說的那個任務包。使用者「簡單隨便說一下」：
- **tick-tock 對 kernel 是一個重要參照物。** 現有 Linux kernel 以**時間、空間、消耗資源**（原話「小號資源」，照上下文記）作為重要的規劃目標；aos 體系裡**時間和空間被 tick-tock 和資料夾壟斷了**，所以 kernel 的參照物就是這兩個。例子：
  - 「我希望你**三回合之內**搞定這一切，不然我就換個人做。」（時間）
  - 「我希望你**只動這三個資料夾**」「只用這幾個檔案」「每個檔案不得超過幾 KB」。（空間）
  - 就這麼簡單——**kernel 只是一個排程**（語音原話「最技術的排程」，使用者校正為「只是一個排程」）。
- 排程這一塊：早前一直卡在「PU 這塊如何實作任務請求、如何處理」。使用者：**這就各資料夾各家各做各的，那只是一個概念，你想怎麼做都可以。** 例子：
  - 跟大家說「你把檔案寫在這邊」——有許可權的就是有許可權，沒許可權的再說。
  - 搞不好再多寫一個檔案說「你的優先多高」。
  - 搞不好另一個人說「你寫下來，OK，我再處理一下」。
  - 「都可以都可以。」

### 3g.7 kernel 的位置：切在 task 和 tick-tock 之上，不碰 loop 的「下一個 inst」

- 更早期（proto2 還是 proto3 時）說過：**kernel 就是管鎖**；也有點想說 **inst 就是下一個要執行的指令**——那 kernel 就是管「這個 aos loop 下一個要執行的 inst 要誰的指令」。
- 使用者：可以啊，**可是這牽太深了，我不希望。我希望隔開：kernel 就在 task 和 tick-tock 之上就好**（原話「task 和 t-task」，照上下文記為 tick-tock）。在 task 和 tick-tock 之上，kernel 就可以隨便做。
- 切開之後更乾淨。對 kernel 來說資源也「隨便走隨便走」。
- **所以 kernel 這一塊，後續做 agent 的時候順便做就好，因為各家有各家的做法。**

### 3g.8 agent：最普通的很簡單，先做一個 demo；真正的目標是「怎麼讓這個函式方便人寫」

- agent 說是麻煩，**但如果只是要做最普通的，那就很簡單：就是狀態機；過程中需要思考就丟東西到 LLM 那邊**。有需要就直接實作，**先實作一個 demo 出來**，看實作出來的協議（原話「協優波」，照上下文記為「協議」）符不符合概念——其實沒差，後續再改進就好。
- **重點在實作這塊最終要達到的目標**：以 LISP 的形式，做出一個**可以依賴於 LISP 的編譯器**這種東西（語音誤成「編輯器」，使用者更正：編譯器）。那要怎麼把 agent 代理人這個函式——把所有函式——**做成一個可以被呼叫的函式，而且方便人類編寫**。
- 最後搞不好要用 LISP 寫；不過使用者之前早就承諾過：**任何程式語言都可以做 library**（原話「任何程式庫都可以做 library」）。
- 它會長怎麼樣：**回到最開始——一個資料夾就是一個列表；如何編排一個資料夾，就是寫 LISP。**

### 3g.9 agent 是一個資料夾、一個很長的 list；拋棄式使用；library 做的事是 binding

- **agent 是一個資料夾、是一個 node，持續被求值、持續變化。**
- 想請一個（已經設定好的）agent 做事，就是呼叫某一個函式——這個函式可以就是一支程式——丟請求給 agent，agent 就想。使用者：**這太簡單太普通。我要的是可以隨時隨地開啟一個 agent，把 agent 當函式、當一次性的拋棄式使用。**
  - 例：設定一個資料夾，裡面是已經設定好的一個 agent，還沒被 daemon 跑起來。**把這個資料夾複製過來，讓它跑一次，它開始思考。**
- （使用者口中反覆「不對不對、對對對」後落定：）**agent 是一個資料夾、是一個 list。只是 agent 的 list 一般會很長**：要用哪個大語言模型是一個元素、它的 context 又占一個元素、有的沒的又占一個元素、工具又占一個元素……列表很長。
- **所以程式語言（library）做什麼？做 binding、做繫結**：把早就固定好的東西固定好，函式就簡化了，**使用時只要填其中幾個引數就好。**

### 3g.10 例子：引用一個標頭檔＝引用一個已經設好的 agent 資料夾，填一個引數就跑

- **我引用一個標頭檔。** 這個標頭檔已經先幫我定義好了某一個擅長做某些事的 agent——**定義這個 agent 就是某一個資料夾**，裡面已經放好相關的 skills／技能、memory／記憶、有的沒的、還有相關的工具。
- 我引用這個標頭檔＝「我要使用這個資料夾、引用這個資料夾」。
- 具體使用時**不用複製過來**（修正了 3g.9 的「複製過來」）：**就讓它跑起來，但跑起來時它的執行環境在我這邊。**
- 因為它列表裡的元素都已經設定好了，所以我就輕鬆說：**「我要使用這個畫家 agent」，引數就是「幫我畫這一幅畫」。** 它就設定好了、開始跑。就這麼簡單。

### 3g.11 巢狀：list 的元素也是 list，求值時先對元素求值

- **list 內部的元素也可以是另外一個 list。求值時，可能先對列表中的元素求值。**
- 例：畫家 agent 的 list 裡有一個元素是「畫筆 agent」（幫它準備一些東西）。**先對這些元素求值；求值完，畫家 agent 才真正開始對自己主要的元素求值。** 畫筆 agent 本身搞不好也要用大語言模型——**這就是巢狀。**
- 使用者：這很正常的使用方法，一定會遇到的東西。

### 3g.12 人寫這套一定超麻煩，要讓人和 AI 都能用；工具就是被引用的標頭檔，agent 也可以是工具

- 使用者直說：**這塊東西人寫一定會超級麻煩**，要想辦法把這一套弄成**人和 AI 都可以用**的東西。
- 工具就是工具。當初為什麼這樣設：**agent 本身就有執行能力，可以自己吃檔案、做這些事**；所以這一塊可以變成工具。
- agent 這個函式的引數包括大語言模型、上下文等等，也包括工具。使用者發現：**工具對 agent 函式來說，就是被引用的標頭檔**——工具內部真正怎麼執行，agent 不需要懂，會用就好。
- 所以反過來，**agent 也可以變成 agent 的工具**。對啊。
- **所以協議這一塊也要想辦法做相容**（agent 與工具同一種引用方式）。

### 3g.13 閉環：aos 體系的每一樣都基於 inst、都是 shell 指令，所以都是 agent 可用的工具

- 剛剛說的 aos 體系這麼多東西——daemon、tick、task、inst、kernel 等等——**全部都基於 inst**（原話「init」，照上下文記為 inst），**而且本身都是可以在 shell 中被執行的指令**。
- 那是不是：**它們就是 agent 可以使用的工具。** 所以**自我迴圈改進的基礎就這麼閉環、閉合了。搞定。**

### 3g.13b 補：inst 的 JSON 不只那幾個 key；工具的 JSON schema 怎麼變成 argv

（收工後補的。）

- 3g.2 說 inst「只認那幾個 key、不認識的略過」——使用者補：**這個 JSON 裡搞不好會再加別的東西**：九軸的那些特性、traits 特性標籤、資源標籤、乃至優先順序標籤，**各種有的沒的都可以加**。
- **工具這一塊也可以加**在 JSON 裡。agent 的工具加上去之後，就是「呼叫」這塊：**工具是用 JSON schema 做引數限制的**；**引數限制如何轉成 argv**（原話「argb」，同前更正為 argv）——搞不好可以選擇走這條路（schema → argv），**或者我們先給它定義一些通用的東西**。兩條路都還開著。

### 3g.13c 補：可預測性不只看函式本身，執行環境也算在節點裡

- 目前看起來可預測性像是**函式本身的東西，但其實不一定**：同一個函式在不同狀況下執行，可預測性也不一樣；**在比較老舊的硬體上執行，可預測性又會下降**。
- 所以這個函式的每個「可預測性節點」，**不止函式內部的東西，也包括它所在的執行環境**——**一整個合起來才是所謂的執行節點**。

## 3h. 使用者看完概念圖解後補充：空間存狀態、處理＝空間的變化、求值＝看狀態變化的結果（10-11 晚）

看了概念 artifact 裡「另一種 PU」「外部設備掛進空間」那幾張圖後補的，是**概念層**的補充定義：

- **空間：就是存放狀態的地方。**
- **處理單元／計算單元、所謂 process 處理：就是過一段時間之後會有一些變化——變化指的是空間上的變化。**
- **求值（evaluate）**：「我放開、允許你開始計算，過一段時間之後，我要看到你狀態變化的結果大概是什麼」——**求值的定義就是空間狀態的變化。**
