## 決定（11-03，使用者）

- **統稱 `proc`**：daemon 管的子項，不論是包在 aos-loop 裡一直跑的（loop 型）還是 aos-exec 跑一次的（exec 型），都是 proc；exec 是基石、loop 是另一種基本形式、以後可能更多。跟 Linux 的 proc 撞名「沒差」。
- **名單合一**：`loops`＋`execs` 兩份名單合成一份 **`procs`**，每項帶 **`kind`**。手把、狀態窗、信箱、小格資料夾全部跟著統稱改名。
- **被推翻（已定、不再是待裁）**：
  - [11-02 state 窗 § 決定（晚）](2026-11-02-state-window.md#決定11-02-晚使用者實作中陸續裁的)：「loops 這塊保留，但裡面兼容 execs」「喔等等，那還是不要合併了」「loops_state 的 `loops`／`execs` 仍分開」——11-03 以「連名單也合一」為準。
  - [10-29 medium-plan § 四 1](2026-10-29-medium-plan/03-四-aos-daemon-的兩個手把-兩扇狀態窗.md) 定的窗名 `loops_ctl.json`／`loops_state.json`、信箱 `loops_mailbox`（11-02 改 `loops_ctl_mailbox`）→ 改 `procs_*`；**拆兩對窗這件事本身不動**（控制自身的一對 `ctl.json`／`state.json`、管別人的一對 `procs_ctl.json`／`procs_state.json`，照 [11-02 晚](2026-11-02-ctl-state-names.md) 的原則）。

### 「proc」這個字在 aos 裡已經是什麼

- [縮寫表](../docs/CONCEPTS/abbr.json)已有 `proc`＝process（行程），例子是 Linux 的 `/proc/<pid>/stat`。
- [C-75](../docs/CONCEPTS/03-基礎設施.md)（10-29）：「**proc 之間**的交流有三種基本概念：投遞、窗、父子交代」；[10-29 medium-plan § 七](2026-10-29-medium-plan/04-七-身分-擁有與收屍-介質可套-人算-proc.md)「人算 proc、路徑是 `~/`」。所以 aos 裡 proc 早就是「體系裡一個會跑、會交流的東西」的統稱，daemon 管的子項叫 procs 是順著這條，不是新造詞；跟 Linux 的 proc 同字同義（都是行程），不是撞名、是借名——使用者「撞名也沒差」。
- [附錄1 名詞](../docs/CONCEPTS/附錄1-名詞.md)還沒有 proc 這一列（規劃 § 5 補）。

### 2. `kind` 的規則（代定）

1. **物件一定要寫 `kind`**，沒寫＝寫壞（daemon.json＝CfgBad 退 1；`procs_ctl`＝整份不採用、原因進 `ctl_warning`；信＝壞信、原因進 `mailbox_warning`——三處同今天名字不合格的處置）。不給預設值：忘了寫的 loop 設定若默默當 exec 跑，`max`／`interval_ms` 就被吞掉，正是 C-56 不要的暗規則；若默默當 loop，又跟「exec 是基石」反過來。寫一個字不貴。
2. **字串／陣列＝exec 型的簡寫**（上表）。`{"kind": "exec", "exec": 目標或單子, "ws"?}` 是完整形；exec 型物件照 10-30 的規矩只看 `kind`、`exec`、`ws`，其他 key 忽略。
3. **`kind` 不認得的值**（例 `"fsm"`、`"Loop"`）＝寫壞，處置同 1。值的集合現在只有兩個，以後多一種形式就多一個值（見[方向題 1](#方向題-1kind-以後怎麼長封閉的幾個值還是程式名)）。
4. **loop 型的 `kind` 不寫進小格的 `loop.json`**：daemon 寫小格時把 `kind` 拿掉（它是給 daemon 看的，不是 loop 設定）；其他 key 照舊原樣灌給子 loop、不驗。
5. **名字唯一、跨 kind**：`procs` 是一個 JSON 物件，同名本來就只剩一個（`$ref` 陣列合檔時後面的蓋前面的，照 N-28 10-23 晚 ①）；`check_apart` 退場。同一個名字**換 kind**（ctl 或信把 `bob` 從 loop 改成 exec）＝今天「表上的種類跟期望表的不一樣」那條：收掉舊的、下一次起新的，小格同一個。
6. **exec 型跑完**：照 11-02 的規矩不變——`done` 印 log 一行、從表上拿掉、記在 `ended_`（名字＋kind）、本次執行不再起；同名再 `procs_added`（信）或名單有一圈沒有它（ctl）＝重新起。loop 型同理。`ended_` 的比對連 kind 一起比，所以「exec 型 bob 做完、再用 loop 型 bob 加回來」＝不同的 proc、照常起。
7. **`procs_removed` 只寫名字**，不帶 kind：拿掉的就是表上叫那個名字的那一個。

### 衝突 1：C-48「不認得的 key 一律忽略」vs 舊 key 報錯

- **大白話**：改名之後，舊的 daemon.json 裡還是寫 `loops`。照你 10-23 定的 C-48（「不認得的 key 就是忽略」），daemon 應該當沒看到——結果是 daemon 安安靜靜起來、一個子項都不起，你要盯半天才發現是名字過期。另一邊，10-25 改 kernel.json 的 `budget.calls` → `max_calls` 時我們是「舊名＝CfgBad 退 1、stderr 說一句」，那次沒人反對。兩個先例打架。
- **選項**：
  - (a) **舊 key 報錯**（fable 建議、上面規劃就這樣寫）：daemon.json 有 `loops`、`execs`、`loops_ctl`、`loops_state`、`loops_ctl_mailbox` 任一個＝CfgBad 退 1，一句話說改成什麼；`procs_ctl.json`／信裡的舊 key＝整份不採用／壞信、原因寫「已改名」。後果：等於承認 C-48 有例外——「本程式自己的舊名」不算不認得；多五個字串比對。
  - (b) 照 C-48 字面忽略：零特例、程式最少；後果是上面那種「默默空跑」，試驗場 `daemons/main` 第一次升級就會中。
- 若選 (a)，順手在 C-48 補半句「程式自己改掉的舊 key 不算不認得，當寫壞報」，以後改名就不用再問。

### 方向題 1：`kind` 以後怎麼長——封閉的幾個值，還是程式名

- **大白話**：你說「搞不好以後還會有更多形式」。現在 `kind` 只有 `loop`、`exec` 兩個值，不認得的就報錯；以後多一種形式（比方直接包成 aos-fsm 跑一次），要改 daemon 的 C++ 加一個值、教它那種形式怎麼起。另一條路是讓 `kind` 直接寫**包它的程式名**（`"kind": "loop"` 就是 aos-loop、以後 `"kind": "fsm"` 就是 aos-fsm），daemon 不認死值、看到 `kind: X` 就「寫小格設定、起 `aos-X 設定檔`」。
- **選項**：
  - (a) **封閉的幾個值，多一種就加一個**（fable 建議、規劃照這個）：`loop`、`exec` 兩個，不認得＝寫壞。理由：兩種的起法根本不同（loop 要寫小格 `loop.json`、補 ctl／state、蓋 `_entry`；exec 不寫檔直接 aos-exec），第三種八成也有自己的起法，daemon 反正要懂它；KISS、現在不為還沒出現的形式開口。後果：以後加一種要改 C++、改 N-28。
  - (b) `kind`＝程式名、daemon 通用起法：daemon 把物件（去掉 `kind`）寫成小格 `<kind>.json`、起 `aos-exec 小格/<kind>.json#/_entry`、`_entry` 寫死 `["aos-<kind>", {"$env": "AOS_CF"}]`。後果：現在就要把 exec 型硬塞進這個形狀（它沒有設定檔、也不該寫小格），反而多一個特例；而且 `kind: fsm` 跑一次就結束，跟 `kind: exec` 差在哪說不清。**不建議**，但這是方向、你定。
