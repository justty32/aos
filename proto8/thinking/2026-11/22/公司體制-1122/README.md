# 公司體制：發想（11-22）

## 使用者原話（11-22，語音輸入，逐字）

> 再幫我開一條線去規劃一下就是說我預期到未來我們會有一大堆代理人在這邊工作那當然他們可以都用同一個daemon，但我覺得分會比較好一些那就這次要的我是說可能我會需要請你幫我規劃他們的私有工作區怎麼去安排那還有就是你知道的就是說他們是要交流訊息然後也要有些儲存資料的地方那或許所謂的公司體制，也是不錯的方式那就好比部門之間可以有交流比較近的部門可以直接走到週邊座位上然後去跟他說話，部門內部也有所謂的不能資產然後部門經費那種東西

### eca-aos 的讀法（都是猜的，沒問過使用者；要確認的列在 [03](03-要問的.md)）

- 「分會比較好」＝將來很多 agent 不全掛在同一台 daemon，傾向分成好幾台（例如一個部門一台）。**為什麼分比較好，他沒說**；理由不同，適合的樣子差很多（03 第 1 題）。
- 「不能資產」多半是語音辨識錯字，應該是「部門資產」（03 第 5 題順便確認）。
- 「部門經費」＝部門的額度或預算。
- 「比較近的部門可以直接走到週邊座位上然後去跟他說話」有兩種讀法：信不用經過上層轉、直接寄；或是能直接把話送進對方正在進行的對話。今天的 aos 只有前一種做得到（03 第 4 題）。

## 大白話摘要

1. **這次交的是發想，不是計劃。** 需求還在成形，所以只盤點現有零件、擺出四種可能的樣子、列出要你回答的七題；沒有任何一樣東西被定下來。
2. **「公司」的零件 aos 大半已經有了，缺的是把它們串起來的那一層。** daemon（跑 agent 的那台「機器」）可以一台掛在另一台底下；信可以跨 daemon 寄；私有地盤今天剛建；共用夾有現成的權限樣板；問模型的額度有三層上限、還有一份你 11-14 已經點頭但沒施工的「部門配額樹」。
3. **缺的主要是四樣：** 一份「誰屬於哪個部門」的正式紀錄；跨 daemon 的上下級（今天一隻 agent 只能在自己那台 daemon 上帶下屬）；一本通訊錄（今天寄信給別台 daemon 的人要自己知道那台的資料夾在哪）；以及牆（今天全部 agent 用同一個 Linux 帳號，誰都讀得到、改得到別人的東西）。
4. **你 11-13 其實已經替「部門＝一台 daemon」打過底**：那時你裁了「一台 daemon 一個群組，同一台裡要再分隊就拆成子 daemon」。所以將來要蓋牆，部門剛好就是牆的單位。
5. **四種樣子**：甲，全部留在一台 daemon，部門只是名冊與資料夾；乙，一個部門一台子 daemon，全掛在同一個 `_stack` 的根底下；丙，一個部門一台各自獨立的 daemon，並排、沒有共同的根；丁，先寫一份組織名冊當正本，哪個部門要不要自己一台 daemon 之後再逐個決定。
6. **如果現在一定要我指一個，我傾向乙**：它跟今天定的「整個 `_stack` 一包帶著換機」最合，整個部門可以一起停、一起醒，也對得上你裁過的群組單位。但它要補「跨 daemon 帶下屬」這個缺口，而且這個傾向取決於第 1 題的答案。
7. **經費這塊最大的盲點不變**：最貴的 Claude 用量根本不經過 aos 的 llm kernel（代管問模型的那一站），aos 管不到，只能量。你今天早上也才說過額度「等以後規模大了才需要另外設計」，所以我建議這次只留位置、不做。
8. **換機**：四種樣子裡，只有丙會讓「一包帶走」變成「好幾包」；另外不管哪種，新加的通訊錄與名冊都不能寫死本機路徑，不然換台就斷。
