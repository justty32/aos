「公司體制」可能長成的四種樣子（甲～丁）：部門怎麼對到 daemon、stack、地盤、權限，怎麼交流，資產與經費放哪，換機怎麼跟著走，各自的好處、代價與會出問題的地方（11-22 發想，沒有一種被定下來）。

# 02 可能的樣子

← [入口](README.md)｜上一份：[01-現況](01-現況.md)｜下一份：[03-要問的](03-要問的.md)

這份是發想：把路擺出來給使用者挑，不替他選。每種樣子最後都有一句「什麼情況下它最合適」。文中「今天的決定」指 [工作區與stack-1122](../工作區與stack-1122/README.md) 的 A～E。

## 先看一眼

| | 甲：一台 daemon，部門只是名冊 | 乙：一個部門一台子 daemon，同一個根 | 丙：一個部門一台獨立 daemon，並排 | 丁：名冊當正本，daemon 逐個決定 |
|---|---|---|---|---|
| 部門是什麼 | 名冊上的一組名字，加一個資料夾 | 根 daemon 表上的一列，那一列本身是一台 daemon | 一台自己當根的 daemon，各有各的 stack | 名冊上的一格；可以附帶一台 daemon，也可以沒有 |
| 要新做多少 | 最少 | 中 | 最多 | 中，但可以分次 |
| 整個部門一起停、一起醒 | 做不到，要一隻一隻來 | 做得到（停那一列） | 做得到 | 有 daemon 的部門才做得到 |
| 將來蓋牆 | 單位對不上（群組是一台 daemon 一個） | 單位剛好對上 | 單位對上，還能一個部門一個 Linux 帳號 | 有 daemon 的部門才對得上 |
| 換機 | 一包 | 一包 | 好幾包 | 一包 |
| 跟「分會比較好」 | 不合 | 合 | 合 | 部分合 |

## 甲：一台 daemon，部門只是名冊

全部 agent 照今天這樣掛在同一台 daemon 上。部門靠一份名冊（哪幾隻是同一個部門）加一個部門資料夾來表示。使用者說「分會比較好」，所以這一種主要是拿來當對照：看看不分 daemon 的話，少了什麼。

- **對應**：部門＝名冊上的一格。stack 照舊平放在 `_stack/procs/<名>/`。地盤照今天的規矩（`wf/ws/<上層>/<名>/`），部門的夾就是帶隊那隻的地盤。
- **交流**：同一台 daemon，寄信只要寫名字，今天就能用。
- **近的部門直接說話**：寫信本來就誰都寄得到；「近」只能靠名冊上寫誰跟誰是鄰居，再讓守信的規矩（進場配給裡的 `AOS_MAIL_ALLOW`）照著填。
- **資產**：部門地盤裡開一個共用夾，進 git。
- **經費**：llm kernel 的「每個寄件人」那一層，照名冊把同部門的加起來看；或直接施工 11-14 那份部門配額樹（它本來就是「記帳的樹，不管信怎麼走」）。
- **換機**：跟今天規劃的完全一樣，一個 `_stack` 帶走。
- **好處**：幾乎不用新做；今天的決定一條都不用動；名字全公司不重複，通訊錄不用做。
- **代價與會出問題的地方**：
  - 一張表上幾十上百列，名字要靠前綴才不打架（今天就是這樣，全景頁才會去猜前綴，使用者嫌的正是這個）。
  - 不能整個部門一起停、一起凍結。
  - 一台 daemon 出事，全公司一起停。
  - 將來要蓋牆時，「一台 daemon 一個群組」等於全公司一個群組，部門之間分不開；到時候還是得拆。
- **最合適的情況**：如果「分比較好」只是為了看起來有條理，而不是為了起停、牆或搬遷。

## 乙：一個部門一台子 daemon，全掛在同一個根底下

`_stack` 的根 daemon 表上，每個部門是一列，那一列本身是一台 daemon；部門裡的 agent 掛在部門 daemon 上。根上只留全公司共用的東西（時鐘、清道夫、頂層的 agent）。

```
_stack/                      根 daemon（公司）
  procs/eca-aos/             頂層 agent（董事長秘書）
  procs/<部門A>/             部門 A 的 daemon（根表上的一列）
    procs/<部長>/            部門 A 的 agent
    procs/<員工>/
  procs/<部門B>/ …
```

- **對應**：
  - daemon：一個部門一台，都是根的子 daemon。聽根的時鐘（今天的預設），各自帶清道夫。
  - stack：部門 daemon 的 stack 在根的 stack 裡，部門成員的 stack 又在部門 daemon 的 stack 裡。這剛好回答了進度檔裡開著的那題「stack 要不要也照層級嵌套」：照 daemon 的層級嵌，不用另外設計。
  - 地盤：讓「部門 daemon」在掛的層級裡也算一層，變成 `wf/ws/<部門>/<agent>/<下屬>/`。今天那句規矩「路徑照掛的層級」一個字都不用改，只是層級裡多了部門。部門那一層的夾（`wf/ws/<部門>/`）正好放部門資產。
  - 權限：一台 daemon 一個群組（使用者 11-13 裁的）＝一個部門一個群組。部門內共寫、部門外看不到，直接套 `aos-share` 的樣板。每個部門 daemon 前面還可以各放一個權限站（部門的櫃檯），管這個部門最多幾個人在跑。
- **部門內交流**：同一台 daemon，寫名字就寄得到；主管對下屬用 `subagent` 的說話。跟今天一樣。
- **部門間交流**：`mailbox_send` 加上對方部門 daemon 的資料夾。部門 daemon 都在 `_stack/procs/<部門>/`，所以**部門名就能算出路徑**，通訊錄可以很薄：一支「部門名加人名 → 信箱」的小查詢，照樹的長相找，不用另外維護一張表。
- **近的部門直接說話**，幾種做法（可以並用）：
  - 最鬆：誰都能直接寄給任何部門的任何人（今天沒牆，本來就這樣）。
  - 每個部門一份小小的「章程」檔，放在部門 daemon 的定義夾裡，寫著鄰居是誰；守信的規矩照它放行，鄰居可以直寄到人，不是鄰居的只能寄到那個部門的收發室。
  - 收發室：每個部門 daemon 開一個投遞箱（`aos-share drop` 那種：外人只能丟、不能看），部長或部門秘書去收、再轉給裡面的人。
  - 「近」也可以照樹來定：同一個上層底下的部門互為鄰居（部門底下還可以再有子部門）。
- **資產**：
  - 要跟著 git 走的（文件、任務書、部門自己做的 agent 定義、工具）：`wf/ws/<部門>/`。
  - 執行期的（部門的信、帳、狀態）：部門 daemon 的 stack，跟著 `_stack` 走。
- **經費**：
  - 問模型：每個部門 daemon 的環境把 `AOS_LLM_KERNEL` 指到部門自己的隊 kernel（`llm-team` 那種），它轉給這台機器的主站。主站就一個部門一格帳，部門站自己再分給每個人。或者不串站，直接用部門配額樹記帳。
  - 人頭：部門櫃檯的 `max_running`。
  - 記憶體：根表上那一列的 `limits`、cgroup 總量，一設就是整個部門（子 daemon 再分給底下的只能更緊）。
- **換機**：整棵樹在一個 `_stack` 裡，照今天規劃的「shutdown → 換機 commit → 另一台起」一包帶走；部門之間的相對位置兩台一樣。
- **跟今天的決定怎麼接**：A（`_stack` 在 repo 裡）、C（`temp/` 不進 git）、D、E 都不動；B 的地盤路徑多一層部門（見上）。換機工具與說明書（今天的線 4、線 9）不用改形狀。
- **好處**：
  - 整個部門可以一起停、一起睡、一起醒；一個部門出事不拖累別的部門。
  - 組織圖就是 daemon 的樹，不用猜：全景頁照樹畫就好，使用者嫌的「設定檔、名字前綴、規則」那一套可以整個拿掉。
  - 名字只要部門內不重複，不必再靠長長的前綴。
  - 牆的單位、帳的單位、起停的單位都是同一個東西。
- **代價與會出問題的地方**：
  - **跨 daemon 的上下級今天沒有工具。** 頂層（在根上）想帶一位在部門 daemon 裡的部長：`subagent` 只會掛在自己那台。要嘛給 `subagent` 加「掛到哪台 daemon」的能力，要嘛讓部長住在上一層、它帶的人才住在部門 daemon 裡（那樣部長就不在自己部門的表上）。這是乙最大的缺口，要做原型才知道哪種順。
  - 調部門＝換 daemon：stack 要搬、llm kernel 那邊按 stack 路徑記的帳會變成新的一格。
  - 部門 daemon 停著的時候，寄給裡面的信照樣進信箱（信箱是資料夾），不會丟；但沒人讀，寄的人等不到回音，也看不出對方是停了還是在忙。
  - 記在檔案裡的絕對路徑會變多（通知信箱、上層 stack），今天線 3 正在修的那三處要連巢狀的情形一起驗。
  - 層數一多，路徑變長（`_stack/procs/a/procs/b/procs/c/…`）。
  - 部門 daemon 的定義夾放哪要定（今天根的定義在 `wf/tree/root/`，照樣放 `wf/tree/<部門>/` 是最順的延伸）。
- **最合適的情況**：要整部門起停、將來要部門之間有牆、而且整間公司還是一起搬。

## 丙：一個部門一台獨立的 daemon，並排，沒有共同的根

每個部門自己當根，各有各的 stack（例如 `_stack/<部門>/` 並排，或各放各的地方）。沒有一台 daemon 管所有部門；公司只是一份「有哪些部門、各在哪」的名單。

- **對應**：daemon、stack、時鐘都是每個部門自己一份。地盤可以跟乙一樣（`wf/ws/<部門>/…`）。權限上能做到最硬：每個部門 daemon 用不同的 Linux 帳號跑，那就是真的牆。
- **部門內交流**：同乙。
- **部門間交流**：只能寄信（給對方 daemon 的路徑），而且**一定要有通訊錄**，因為沒有共同的樹可以推路徑。時鐘各走各的，跨部門的信不能寫「第幾圈」，只能寫真實時間（`world.md` 的規則）。
- **近的部門直接說話**：同乙的收發室與鄰居表；但鄰居表沒有樹可以依靠，只能明寫。
- **資產與經費**：同乙。經費更乾淨：每個部門可以有完全獨立的 llm kernel。
- **換機**：
  - 整間一起搬：要 shutdown 好幾台、帶走好幾個 stack、另一台照順序起好幾台；今天的換機工具與說明書都假設「一個 `_stack`、一個根」，要改。
  - 一個部門單獨搬去另一台機器：這是丙獨有的能力。但信箱不跨機，搬走的部門就跟留下的部門斷了線，除非另外做「跨機傳信」（今天只有 git 加 `wf/inbox/`）。而且今天定的「同一時間只有一台在跑」要改成「同一個部門同一時間只有一台在跑」，兩台同時動同一個 repo，git 會更常打架。
- **好處**：部門之間最獨立；一個部門可以單獨起、停、搬、重灌；牆可以蓋到最硬。
- **代價與會出問題的地方**：
  - 新做的最多：通訊錄、一次起停全部的指令、沒有根之後「頂層 agent 住哪」、全景頁要看好幾台。
  - 沒有一個地方看得到全公司。
  - 跟今天的決定 D（一個 `_stack` 取代 `~/aos-home`）要重談。
  - 跨部門的上下級比乙更難（連共同的上層都沒有）。
- **最合適的情況**：真的想讓不同部門在不同機器上、或不同部門要用不同的 Linux 帳號隔開。

## 丁：名冊當正本，daemon 逐個決定

先寫一份明確的組織名冊（部門、成員、主管、鄰居、資產夾、經費），所有工具與全景頁都以它為準；至於某個部門要不要有自己的一台 daemon，是名冊上的一個欄位，以後逐個部門決定。起步時全部在一台 daemon（＝甲），哪個部門長大了或需要牆，再把它搬成子 daemon（＝乙）。

- **對應**：部門＝名冊上的一格。有 daemon 的部門照乙；沒有的照甲。地盤一律 `wf/ws/<部門>/<agent>/`（照名冊，不照掛的層級；今天那句規矩要改寫）。
- **交流、近鄰**：通訊錄就是名冊（名字 → 在哪台 daemon），鄰居也寫在名冊。
- **資產、經費**：寫在名冊的欄位；11-14 的部門配額樹本來就是一份表，可以併進來。
- **換機**：一個 `_stack`，同乙；名冊在 git 裡，跟著走。名冊裡不能寫本機路徑。
- **好處**：可以今天就開始用公司的說法，不用等 daemon 那邊補齊；改組只改名冊；跟 llmk2 的結論（「部門樹是記帳的樹，改組＝改表」）同一個想法。
- **代價與會出問題的地方**：
  - **名冊與實況會對不上**：名冊說某人在某部門，表上它卻掛在別處；誰來對、對不上聽誰的。
  - 這等於又一份中央設定檔。使用者嫌全景頁醜的點之一就是「靠設定檔」；差別只在這份是唯一的正本、不是猜測用的補丁。他接不接受要問他（03 第 3 題）。
  - 同一件事（搬成子 daemon）以後每個部門都要做一次，等於把乙的缺口延後而不是免掉。
- **最合適的情況**：想先把組織講清楚、馬上用起來，daemon 怎麼切以後再說。

## 不管選哪種都會遇到的事

1. **分 daemon 本身不是牆。** 只要還是同一個 Linux 帳號，別的部門照樣讀得到、改得到你的東西。分 daemon 是為牆打好單位；牆要等每隻 agent 換身分（`sub:N`）真的開起來。
2. **「直接說話」今天只有上對下。** 平輩或跨部門若真的要「走到座位上說話」（話直接進對方正在進行的對話，而不是一封等他有空再看的信），是新能力，而且有打斷別人、塞爆別人對話的風險；kernel 攔截那份調查也指出，今天沒有任何一站攔得到「塞別人的對話」。
3. **寄件人是自己報的。** 鄰居表、收發室這些規矩，在沒有牆之前都靠大家守規矩。
4. **經費管不到 Claude。** 用 Claude Code 當腦的 agent 不經過 llm kernel。部門經費如果只蓋在 llm kernel 上，會漏掉最貴的那一塊；那一塊只能量（llmk2 的「Claude 電表」）加上從派工下手（少派、派便宜的）。
5. **帳本今天定了不跟著換機走**（決定 E 與使用者「額度…心裏有數就好」）。部門經費若有「這個月用了多少」這種跨天的帳，換機那天會歸零或分成兩本，除非把部門的帳放進 `_stack`。
6. **現有的四隻怎麼算**：eca-aos 加三個 subagent（templates、kb、frontend）。它們是一個部門、三個部門、還是「總部」？三個 subagent 今天都掛在 eca-aos 底下，若各自成為部門，在乙底下就會撞到「跨 daemon 的上下級」那個缺口。
7. **wf 的部長制**（回報與 commit 放行找部長）是做事流程上的部門，跟這裡說的部門（daemon、地盤、資產、經費）是不是同一批，要對齊；不然會有兩套「部門」。
8. **名冊、章程、通訊錄都不能寫死本機路徑**（家機 `/home/lorkhan`、公司 `/home/guanyu`），要從 repo 根或 `_stack` 算相對位置。
9. **一個部門幾個人、最多幾層**沒有天然上限。今天每隻最多 4 個下屬；部門改成 daemon 之後，人數上限變成部門櫃檯的 `max_running`，兩個數字的關係要講清楚。
10. **部門解散或改名**：地盤夾、stack、信箱裡沒讀的信、llm kernel 上的帳，各自怎麼收。照使用者的偏好（proto8 一律當成沒有舊版、不寫遷移），改名可能就是「新開一個、舊的封存」。

## 值得先做的小原型（等使用者點頭才做）

照規矩「快速做原型讓他試」：在暫存樹（repo 外）起一個根加兩台子 daemon、各掛一兩隻用假腦的 agent，實際走一遍：部門間寄信與回信、整個部門停下再醒、頂層想帶部門裡的人會卡在哪、整棵樹搬到另一個路徑再起。半天內可以做完，能把乙的缺口從猜的變成看到的。
