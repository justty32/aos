# 03 要問的

← [入口](README.md)｜上一份：[02-可能的樣子](02-可能的樣子.md)

第 1、2 題決定大方向，其他五題可以晚點答。樣子甲～丁的細節在 [02](02-可能的樣子.md)。

## 第 1 題：你說「分會比較好」，主要是為了什麼？（可以複選）

白話：把 agent 分到好幾台 daemon 有幾種不同的好處，要的好處不同，適合的樣子差很多。

| 選項 | 意思 | 後果 |
|---|---|---|
| a | 好管：一個部門可以整個一起停、一起醒，表不會長到看不完，名字不用靠長前綴 | 乙就夠 |
| b | 將來要有牆：部門之間不能互看、互改 | 乙或丙；分 daemon 只是先把單位打好，牆要等 agent 換 Linux 身分那一步 |
| c | 部門可以分開搬：不同部門放在不同機器上跑 | 只有丙做得到，而且要另外做跨機器傳信，今天「同一時間只有一台在跑」的約定要改 |
| d | 出事不連坐：一個部門掛了不拖累別的 | 乙或丙 |
| e | 只是覺得這樣比較有條理，沒有特別的理由 | 甲或丁就夠，不用急著拆 daemon |

推薦：無（這是你的想法，我不猜）。我的觀察只有一點：你今天說地盤「是未來的權限的基礎」、11-13 裁過「一台 daemon 一個群組」，這兩句合起來最像 a 加 b。

## 第 2 題：先朝哪一種樣子想下去？

| 選項 | 樣子 | 後果 |
|---|---|---|
| 甲 | 全部留在一台 daemon，部門只是名冊與資料夾 | 幾乎不用新做；不能整部門起停；將來要牆還是得拆 |
| 乙 | 一個部門一台子 daemon，全掛在同一個 `_stack` 的根底下 | 今天的換機規劃不用改；組織圖就是 daemon 的樹；要補「上層帶別台 daemon 裡的下屬」這個缺口 |
| 丙 | 一個部門一台獨立 daemon，並排 | 最獨立、能分機器；新做的最多；今天「一個 `_stack`」的決定要重談 |
| 丁 | 先寫一份組織名冊當正本，哪個部門要自己一台 daemon 以後逐個決定 | 可以馬上用；多一份中央設定檔，名冊跟實況可能對不上 |

推薦：**乙**，並且先做一個半天的小原型（暫存樹裡一個根加兩台子 daemon）讓你實際看到缺口，再決定要不要正式規劃。前提是第 1 題的答案裡沒有 c；有 c 就要認真看丙。

## 第 3 題：「誰屬於哪個部門」寫在哪裡才算數？

白話：你嫌過全景頁靠「設定檔、名字前綴、規則」去猜上下級。新的體制需要一個不用猜的來源。

| 選項 | 意思 | 後果 |
|---|---|---|
| a | 照結構：agent 掛在哪台部門 daemon 上，就是那個部門。部門自己的事（鄰居、經費）寫在那個部門 daemon 的定義夾裡，一個部門一小份 | 沒有中央設定檔，不可能跟實況對不上；只在乙、丙成立；調部門＝真的搬過去 |
| b | 照名冊：一份全公司的組織名冊是正本，工具與全景頁都讀它 | 改組只改一個檔；多一份要維護的檔，會跟實況對不上，要有人定期對 |
| c | 照誰掛誰（今天的樣子）：帶隊的 agent 加它的下屬就是一個部門 | 不用新做；部門沒辦法有「不屬於任何一隻 agent」的東西，帶隊的那隻一換，部門就散了 |

推薦：**a**（如果第 2 題選乙或丙）。它最接近「結構自己會說話」，也最不像你嫌的那種設計。

## 第 4 題：「比較近的部門可以直接走到座位上說話」是哪一種？

白話：今天 agent 之間有兩種溝通。寫信：放進對方信箱，對方有空才看。說話：直接進對方正在進行的對話，今天只有主管對自己的下屬才行。

| 選項 | 意思 | 後果 |
|---|---|---|
| a | 近的部門可以直接寄信給裡面的人；遠的部門只能寄到那個部門的收發室，由部長或秘書轉 | 今天的零件就做得到；要定「誰算近」 |
| b | 近的部門連「說話」都可以：話直接進對方的對話 | 是新能力；會打斷對方手上的事，也可能塞爆對方的對話；今天沒有任何一站攔得住 |
| c | 不分遠近，誰都能直接寄信給誰；「近」只是習慣上的說法 | 就是今天的樣子，不用做；人一多，每隻的信箱會變吵 |

推薦：**a**。說話保留給上下級。另外請順便告訴我「近」怎麼算：同一個上層底下的部門就算近（照樹），還是每個部門自己列鄰居。我傾向照樹，少一張要維護的表。

## 第 5 題：「不能資產」是不是「部門資產」？指的是哪些東西？

白話：語音辨識那句「部門內部也有所謂的不能資產」，我們猜是「部門資產」。想確認，也想知道你心裡想的是什麼。

| 選項 | 意思 | 後果 |
|---|---|---|
| a | 是部門資產，主要是檔案：部門共用的文件、資料、筆記 | 最簡單：`wf/ws/<部門>/` 那一層的夾就是，進 git、跟著換機走 |
| b | 是部門資產，而且包含工具、agent 的定義、部門自己的知識 | 同 a 的夾，再多定「部門的工具與定義放哪、別的部門能不能借用」 |
| c | 還包含金鑰、帳號這類不能進 git 的東西 | 要另外找地方放（repo 外），換機不會自動跟著走，要寫進換機說明書 |
| d | 不是「部門資產」，是別的意思 | 請告訴我原本想說的詞 |

推薦：**b**，c 那類先不碰。

## 第 6 題：「部門經費」現在要做到哪裡？

白話：經費可以指好幾樣：問模型的次數或 token、Claude 的週額度、同時能開幾個人、記憶體。其中 Claude 的額度 aos 管不到，只能量。你今天早上才說過額度「使用者自己心裏有數就好，等以後規模大了才需要另外設計」。

| 選項 | 意思 | 後果 |
|---|---|---|
| a | 先不做，只在設計裡留位置 | 跟今天早上的話一致；部門先沒有經費的限制 |
| b | 先只記帳、不設上限：看得到每個部門用了多少 | 要施工一部分 11-14 的部門配額樹（報表那半）；換機時帳本的去留要定 |
| c | 記帳加上限：部門用完就停 | 完整施工部門配額樹；Claude 那塊仍然管不到；會出現「部門被卡住等額度」的新狀況 |

推薦：**a**。等公司體制的樣子定了、agent 真的多起來，再接上 11-14 那份你已經點頭的部門配額樹，不用重新設計。

## 第 7 題：換機的時候，整間公司一起搬，還是部門可以分開搬？

白話：你的核心訴求是能跨機器搬遷。今天定的是「換台前全部停下、同一時間只有一台在跑」。

| 選項 | 意思 | 後果 |
|---|---|---|
| a | 整間一起搬，維持今天的約定 | 今天的換機規劃原樣可用；甲、乙、丁都合 |
| b | 希望將來某個部門可以單獨搬到另一台，兩台同時各跑幾個部門 | 只有丙合；要做跨機器傳信；兩台同時動同一個 repo，git 會更常打架 |

推薦：**a**。b 留著當以後的可能，不為它付現在的代價。
