## 會限制設計的幾件事實

1. **一隻 agent 只屬於一台 daemon，下屬也只能掛在同一台。** `subagent`、`agents_ctl` 兩支工具都沒有「掛到別台 daemon」的參數（`world.md:20`「Subagents you start go on the same daemon」〔已核〕）。人可以用 `aos-agent --daemon D ctl add` 掛到別台，但那樣掛出來的不算誰的下屬，掛的人不能用 `subagent` 對它說話。
2. **跨 daemon 寄信做得到，跨機器做不到。** 信箱是本機的資料夾（`proto8/thinking/2026-11/12/linux-user/03-各念頭的讀法與後果.md:108`〔已核〕）。跨機今天靠 git 與 `wf/inbox/` 的信。
3. **信上的寄件人是自己報的，沒人驗**（`kernel.md`「self-reported and not checked」〔已核〕）。
4. **子 daemon 的 stack 在上層 daemon 的 stack 裡面**（上層把它當普通的一列，預設放在 `procs/<名>/`），所以整棵樹是一個資料夾，一起搬。子 daemon 聽根的時鐘、自己帶清道夫（`proto8/cpp/aos-daemon/docs/10-根daemon.md:34,49`〔已核〕）。
5. **使用者 11-13 已經裁過群組的單位是 daemon。** 原話：「都按照推薦。然後每隻agent一個自己的群組，感覺有點浪費，我會覺得，在普通用途下，一個kernel/daemon一個群組就好，可以再去想想。」當時的結論：共寫夾以 daemon 為單位；同一台裡想再分隊，改成拆子 daemon；子 daemon 不帶上層的群組，上層要分享就點名（K17）；子 daemon 沒寫群組就沿用上層的（K18）（`proto8/thinking/2026-11/13/kernel-limits-plan/08-群組用法.md:61,100-107`〔已核〕）。這是「部門＝一台 daemon」最硬的既有依據。
6. **今天大家的工作區都是 repo 根**，所以任何一站用「工作區在哪」都分不出誰是誰（[工作區與stack-1122 02-規劃](../工作區與stack-1122/02-規劃.md)「怎麼接上別的規劃」〔已核〕）。
7. **全部 agent 跟使用者同一個 Linux 帳號。** 所以今天所有「不准」都只是規矩：地盤、權限站、`kernel_gate`、guard 都擋不住不守規矩的。使用者 11-21：「我覺得原則是只防走規矩的存取，不守規矩的就是要自己承擔風險。真的要硬防，那就要多依賴linux的權限體系」（`proto8/thinking/2026-11/21/kernel-攔截daemon存取-1121/README.md:42`〔已核〕）；11-18：「權限管理這塊，其實都想要，但是先做防呆就好，先考慮單人使用，模型可信。」
8. **最貴的用量不經過 llm kernel。** 用 Claude Code 當腦的 agent（eca）是自己去問 Claude，llm kernel 看不到；llm kernel 只管派出去的 agent-fsm（[工作區與stack-1122 01](../工作區與stack-1122/01-決定與調查.md) 第二輪〔已核〕；llmk2-1114 稱它「最大盲區」）。
9. **llm kernel、權限站今天定了各台自己跑、放 repo 外**（決定 E），用量帳本換機不跟著走；使用者：「這個沒差，額度就是使用者自己心裏有數就好，等以後規模大了才需要另外設計」。

## 沒有的（要新做才有）

- 「誰屬於哪個部門」的正式紀錄。今天只有三種間接線索：誰掛誰、名字前綴、全景頁的設定檔。
- 跨 daemon 的上下級：一隻 agent 帶一個在別台 daemon 上的下屬。
- 通訊錄：用名字找到別台 daemon 上的人。
- 平輩之間「直接說話」的工具。
- 部門資產放哪的慣例，與部門這一層的地盤。
- 部門這一層的經費（規劃有、程式沒有）；Claude 用量只能量、不能管。
- 牆：機制有（換身分加群組），沒有任何一隻在用；地盤的規矩也還沒接上它。
- 「公司體制」「部門經費」「部門資產」這幾個詞，repo 裡以前沒出現過。
