wf/user 在一天裡怎麼用的三個情境：在外面用手機口述想法、晚上在 VS Code 改一行交代、放一份不想公開的參考資料（照 02 的推薦寫）。

# 03 情境

← [README](README.md)｜上一份 [02-規劃](02-規劃.md)｜下一份 [04-待裁](04-待裁.md)

三個情境都照 [02](02-規劃.md) 的推薦寫，也就是假設 [04](04-待裁.md) 六題都選推薦。

## 情境一：中午在外面，用手機口述一條想法

1. 你在 Remote Control 跟 eca-aos 說：「記一下，以後 kb 的條目都要附一個例子。放 wf/user。」
2. eca-aos 判斷這是交代（給 agent 的指示），就寫進 `wf/user/交代.md` 最上面：
   ```
   ## 11-23 kb 條目要附例子（agent 代寫，使用者 11-23 口述）
   原話：「記一下，以後 kb 的條目都要附一個例子。放 wf/user。」
   ```
   你叫它寫，所以這是允許的；它標了「代寫」，以後分得出不是你手打的。
3. 它接著把這條抄進 `common/user.md`（或轉給 eca-aos-kb 記進它的筆記），附原話、指回 `wf/user/交代.md`。原文那段不動。
4. 交件走 commit-request，commit 訊息寫「使用者原話：…」。
5. 它回你一句：「記在 wf/user/交代.md 第一條，已 commit。要 push 嗎？」你說要，push 之後你在 GitHub app 打開 `wf/user/交代.md` 就看得到。

## 情境二：晚上回家，在 VS Code 改一行交代

1. 你在 VS Code 打開 `wf/user/交代.md`，在最上面加一行：「11-23 晚：明天先做公司那台的 _stack，其他先放著。」存檔。你沒跟任何 agent 說。
2. 隔天早上 eca-aos 開場，掃完信箱和 `wf/progress.json`，接著掃 `git status --short wf/user`，看到 `M wf/user/交代.md`。
3. 它跟自己的 `wf/ws/eca-aos/user-seen.json` 對一下：上次讀到「11-23 kb 條目要附例子」那條，所以新的只有最上面這行。
4. 它照做：把公司那台的線排第一，其他線先停。它在自己的 `user-seen.json` 記「讀到 11-23 晚那條」，**不在你的檔上打勾**。
5. 你這行還沒進 git。到了收工，eca-aos 用選項框問你一題：「wf/user/交代.md 有你改的一行還沒交，要交嗎？」你點「交」，它原樣交件，不改一個字。
6. 要是它覺得「其他先放著」範圍不清楚（例如有一條線正在跑到一半），它不自己猜，寄一題到使用者專區，出現在全景頁上。

## 情境三：放一份不想公開的參考資料

1. 你有一份 15 MB 的 PDF，想讓 agent 規劃時參考，但不想放上 GitHub。
2. 你把它丟進 `wf/user/private/`（第 1 題選 a 之後，這夾在 `.gitignore` 裡）。
3. 你在 Remote Control 說：「參考 wf/user/private/報告.pdf 去規劃 X。」agent 讀得到，因為現在不是牆；它不會把這份抄進 git 追蹤的地方，引用時只寫路徑和它自己的摘要。
4. 這份不跟換台走。你到公司那台要用，就自己帶過去（隨身碟、雲端都行）。要是之後這類東西多了，可以另外開一個私人的 repo 專門放，再談。
5. 要是你一不小心把它放在 `wf/user/筆記/` 而不是 `private/`：agent 交件時會被 1 MB 檢查退回來，它會回報「這份太大，是不是該放 private/？」，不會硬塞進 git。小於 1 MB 的私人檔就沒有這道保險，所以 agent 在交 wf/user 的檔之前，要先問你一次。
