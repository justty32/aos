## 一、「自動回這種信的東西」放哪一層

骨架一輪：`collect → check → order → 逐封 [before_verdict → admit → after_verdict] → 放／拒／排／留`（`py/tools/aos/kernel/round.py:75-127`）。

| | 放哪 | 長什麼樣 | 誰自動有 | 代價、跟現有的關係 |
|---|---|---|---|---|
| **甲 骨架在 `order` 之前攔** | `round.py` 拿到這輪新信（`:76`）之後、交給 `order` 之前 | 骨架認得問句信，讀那份 json、直接回、收掉原信；不交給包 | 所有用骨架的 kernel（問腦總機、掛 proc 的站、以後的）都有，包不用改 | 骨架第一次「認得一種請求」——今天骨架說自己「不認得任何一種請求」（`kernel/README.md:9`）。問句信不排隊、不佔格、不等 `order`。hook 看不看得到要另定（不經 `before_verdict` 就看不到） |
| **乙 各包的 `admit` 自己認** | 問腦那包、掛 proc 那包各加一段 | 包看到問句信就回答案（掛 proc 那包要「不轉寄、自己回」，今天它沒有這條路） | 只有改過的包 | 兩份程式；新寫的包要記得自己加。跟他說的「框架弄一個」不太一樣，是最貼現況的 |
| **丙 一支標準 hook，框架附帶** | 像 `kernel_gate` 那樣是一支現成的 handler，kernel 主人在 `kernel.json` 掛上才有 | 每封新信跑它；不是問句就不說話 | 掛了才有（「可選」自動成立） | **今天的 hook 不能回信**（`hooks.py:8-12`），只能走歪路（本線原型 A：自己寄答案再退 10 讓站拒掉，問的人收到兩封）。每封信多一次起行程（約 20 ms，[aos-kres-1120/09](../aos-kres-1120/09-接成hook試跑.md)）；hook 壞了預設整站停 |
| **丁 hook 多一種回話：「這封我答了」** | `hooks.py` 的回話規則多一個鍵（例：`before_verdict` 回 `{"answer": {...}}`＝骨架把它當回信寄出、收掉原信、不判） | 骨架提供「hook 可以直接回答」這個通用能力；自動回問句信只是用它的一支 hook（就是丙去掉歪路） | 掛了才有 | 改 hook 的回話規則＝動到 hook 介面那條線（`aos-hook-plan-1120`、`hook_points.json` 要多一欄）。能力是通用的，hook 也能拿它回別種信 |
| **戊 分流到一個「答問小站」** | 掛 proc 那包的 `after_verdict` 回 `next`（`kernel/README.md:128-154`），把問句信轉給另一個信箱，由一支小程式回 | 站不用改；答問小站是另一個常駐或被叫的程式 | 掛 proc 的站才行；**問腦總機沒有 `next` 這個口**（`kernel/README.md:33`） | 多一個要起的東西；它跟站是兩個行程，站掛了它可能還在（反之亦然） |
| **己 daemon 本體回** | 像今天的 `procs_state_path`，C++ 的 ctl 信箱認它（`mailbox.cpp:118`、`:187`） | daemon 讀一份宣告檔回 | 信最後轉到 daemon 的站；問腦總機前面沒有 daemon 的 ctl 信箱 | daemon 不是 kernel 框架；回的是「最後那台 daemon」的事，不是收信那一站的規則 |
| **庚 不用信，放檔** | 像 `endpoints.json` 窗（`kernel_llm/packs.py:254-271`），kernel 每輪寫一份到 stack，`aos-llm ls` 那樣直接讀 | 問的人自己去讀 | — | 他說先做寄信問；放在這裡當對照：同機最快、不用 kernel 醒著；跨機、跨帳號讀不到 |

可以混：例如丁＋框架附一支用丁的標準 hook；或甲當預設、包可以蓋掉。

### 跟三個 hook 點、`admit`／`order` 口的關係（一句一條）

- `before_verdict`：今天問句信會經過它（新信都會，`round.py:101-107`），所以丙、丁放這裡最自然；甲在它之前，hook 就看不到問句信。
- `after_verdict`：問句信要先被包判過才到這裡；問腦總機會先判成 `LetterBad`，hook 再改判也只能放／拒／換站，不能回答。戊用的是它。
- `before_reply`：只看「回信」，跟答問句無關；但掛 proc 站開了 `reply_via_me` 時，daemon 回的 `{"applied": true}` 會經過它——今天唯一能在這裡「把回信改成答案」的歪路（本線沒試）。
- `admit`：包的口，乙就是它。
- `order`：骨架叫的口。甲在它之前；問腦總機的 `order` 今天把驗不過的信排最前（`llm_rules.py:425-432`），問句信等於「當輪最先處理」。

## 二、問句信長什麼樣

| | 樣子（示意，名字不是提案） | 後果 |
|---|---|---|
| **一 一個專用鍵** | 像 `{"procs_state_path": true}`：`{"<某個鍵>": true}` | 跟今天唯一的問句信同一個樣子；daemon 那邊驗「有寫就必須是 true」（`mailbox.cpp:118`），新的照抄就好。要問別的事就再加一個鍵 |
| **二 一個鍵帶「要問什麼」** | `{"<某個鍵>": ["reads", "rules"]}` 或 JSON Pointer | 一封可以只問一段；回信小。要定「可以問哪幾段」 |
| **三 信封上標** | aos-post 信封多一欄（今天信封只有 `sender`、`sent_at`、`reply_to`、`in_reply_to`、`body`） | 要改 aos-post（C++），所有站都看得到；C-47 說「共通的只有 aos-post 信封，body 各類自理」（`docs/CONCEPTS/04-kernel/01-C-47.md`），等於多一條共通規定 |

另外兩件跟著要想：問句跟真請求能不能寫在同一封（`procs_state_path` 今天可以：其他鍵照套，`mailbox.cpp:14`）；回信長什麼樣（兩種 kernel 的回信形狀不同：daemon 與掛 proc 的站回 `{"applied": …}`，問腦總機回 `{"message"}`／`{"error"}`，問的人要兩種都會讀，或答問句有自己的一種形狀）。

## 三、「另外一個 json」怎麼擺

他說：「另外一個json吧。interfaces和hook都是另外的用途。」裡面裝的是他第 8 題的兩樣：「看請求 json 的什麼」（資源基底的放話 schema）與「自己有哪些規則」。名字他沒說，本線不取；原型暫用 `kask.json`（線名，用完即丟）。

### 位置

| | 放哪 | 後果 |
|---|---|---|
| **定義夾** | 跟 `kernel.json`、`interfaces.json` 同一夾 | 跟著定義走、可以 git；同一份定義起兩台 kernel，兩台說一樣的話。kernel 今天沒有「編譯」，改了就是人手改檔（`kernel.json` 每輪重讀，這份也可以每次被問時重讀）。「kernel 之後也要編譯」那條線（[aos-compile-base-1120](../aos-compile-base-1120/README.md)）若成真，它是編譯產物的一件 |
| **stack** | kernel 執行期的資料夾 | kernel 自己（agent）改了下一封就生效；換一台要自己抄。跟 aos-kres-1120 第 3 題「經驗存哪」（他答先不定）綁在一起 |
| **定義一份、stack 蓋上去** | 定義夾那份是出廠，stack 那份有就用它 | 沿用 agent 那套「定義一份、stack 同名覆蓋」的慣例（`py/aos/declared_files.py:1`）；要定「整份蓋」還是「逐鍵蓋」 |
| **`kernel.json` 裡的一個鍵** | 不另開檔 | 跟他說的「另外一個json」不合，列著只是對照：`kernel.json` 是「設定」，給 kernel 自己讀 |

### 誰寫、誰讀

- **寫**：kernel 的主人手寫；kernel 自己（是 agent 時）改；框架從 `kernel.json` 算出一部分自動填（例：問腦總機的能力包清單今天就算得出來，`endpoints.json` 窗）、其餘人寫。「schema 誰說了算」他在 aos-kres-1120 第 4 題答「先不定」，這裡不重問。
- **讀**：自動回信的那個東西（讀了放進回信）；同機的人與工具直接讀檔；htop／gdb 這類看全局的工具。
- **每次被問時重讀**還是**起來時讀一次**：前者改了立刻生效（原型就是這樣）；後者省一次讀檔，改了要重起。

### 命名的幾種可能（只列方向，不取名）

- 照用途取（講的是「我收什麼」）；照讀者取（給寄請求的人看）；跟問句信的鍵同名（記一個字就好，但檔名與鍵名從此綁在一起）。
- 要不要跟 `interfaces.json`、`hook_points.json` 同樣 `…s.json` 的長相：同長相好認是「宣告檔一家」，也容易讓人以為三份是同一種東西。

## 四、跟 `interfaces.json`、`hook_points.json` 怎麼分工不打架

| 檔 | 回答的問題 | 給誰 | 今天誰讀 |
|---|---|---|---|
| `interfaces.json` | 「這個定義夾提供哪些介面、那些檔在哪」 | 要找檔的工具（`aos-agent` 讀它的 `aos-agent` 鍵） | agent 那邊有；kernel 的 `aos-ledger` 沒人讀（`附錄4-持久檔.json:411`） |
| `hook_points.json` | 「我這支程式在哪些時機讓人插 hook、事件長怎樣」 | 要掛 hook 的人與工具 | `aos.hook_point`、`aos-hook`（執行期還沒人叫，`hook_point.py:3-6`） |
| 另外一個 json | 「我這台 kernel 收什麼請求、看請求 json 的什麼、自己有哪些規則」 | 要寄請求給它的人 | （還沒有） |

不打架的條件（都是可以選的，不是規定）：

- 新的那份**不列 hook 點**、**不列檔在哪**，那兩件歸原本兩份。
- 要不要在 `interfaces.json` 寫一行「另外那份在哪」：寫了，工具有地方找（跟 `aos-ledger` 同一招）；不寫，就是固定檔名、固定位置。他說 interfaces 是另外的用途，這一行算不算佔用它，列成題（[05 第 4 題](05-要他定的題.md)）。
- 規則清單（「自己有哪些規則」）若以後也要讓 hook 掛在某條規則上，會跟 `hook_points.json` 碰到；今天沒有這需求，只記一筆。
