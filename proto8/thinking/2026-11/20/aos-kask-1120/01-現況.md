## 二、一封問句信今天怎麼走

兩種 kernel 跑同一份骨架 `py/tools/aos/kernel/round.py` 的 `run`（`round.py:49`）：

```
collect → check → order → 逐封：before_verdict hook（新信）→ admit → after_verdict hook → pass／refuse／queue／hold
```

骨架本身不認得任何請求（`py/tools/aos/kernel/README.md:9`），問句信要被怎麼對待，全看包的 `admit`。

### 問腦總機（llm kernel）：當壞信拒掉，不進帳

1. `order` 先驗每封；body 沒有 `request` 的驗不過（`py/tools/aos/kernel_llm/llm_rules.py:367-368`），驗不過的排最前（`llm_rules.py:425-432`）。
2. 它是新信，所以**照樣先跑 `before_verdict` hook**（`round.py:101-107`）——hook 看得到這封問句信，也能攔下它。
3. `admit` 回拒（`llm_rules.py:470-471`），回信 `{"error": {"code": "LetterBad", "msg": "cannot understand the letter: ..."}}`（訊息在 `llm_rules.py:21-22`）。
4. 拒掉的信沒掛去跑，**不記帳、不扣額度**（帳只記掛上去過的，`llm_rules.py:245-247`），也不跑 `before_reply`（`kernel_llm/README.md:47`）。

實跑：`{"kernel_ask": true}`（原型暫用的鍵）與 `{"procs_state_path": true}` 用 `aos-post send` 直接寄進總機的 `requests/`，分別 0.46 秒、1.5 秒拿到 `LetterBad`（[04 第一段](04-原型.md)）。也就是說，**拿問表在哪的信去問問腦總機，今天是被拒的**。

**還寄不出去**：問腦的寄信工具 `aos-llm send` 在寄之前就驗 body，沒有 `request` 的直接 `RequestBad`、不寄（實跑；規則見 `cpp/aos-llm/docs/01-用法等.md:16`）。所以今天要問問腦總機任何「不是問腦」的事，只能繞過 `aos-llm`、用 `aos-post` 直接寄。

### 掛 proc 的站（daemon-kernel、procs-kernel、kernel_gate 也是它）：原樣轉給 daemon，daemon 回「收到」

1. `admit`：body 沒有 `procs_added`／`procs_started`／`procs_woken`，算出來「不加任何名字」（`py/tools/aos/kernel/procs_rules.py:190-191`），放行（`procs_rules.py:228`；完全沒設 `allowed`、`max_running` 時更早就放行，`:215-217`）。
2. `dispatch` 轉寄給下一站（`procs_rules.py:249`），通常是 daemon 的 ctl 信箱。
3. daemon 不認得的鍵忽略（`mailbox.cpp:11` 檔頭說明），回 `{"applied": true}`。寫了 `procs_state_path` 的，多帶表的路徑。

實跑：`{"kernel_ask": true}` 寄給 daemon-kernel 範本的站，0.49 秒拿到 `{"applied": true}`——**看起來像成功，其實沒人懂這個問題**；`{"procs_state_path": true}` 0.71 秒拿到 `{"applied": true, "procs_state_path": "/…/t/pk/st/procs_state.json"}`。

### 兩種一比

| | 問腦總機 | 掛 proc 的站 |
|---|---|---|
| 不認得的問句信 | 拒：`LetterBad` | 轉給 daemon，回 `{"applied": true}` |
| `procs_state_path` | 拒：`LetterBad` | daemon 回表的路徑 |
| 算不算一次請求 | 不算：不掛、不記帳 | 會轉一次、daemon 認領並回信；站不記帳（它本來就不記用量） |
| 排隊 | 不排（驗不過排最前、當輪拒） | 不加名字的信不要格，不會被隊首擋（`kernel/README.md:78`「不增加 running 的信照轉」） |
| hook 看得到嗎 | 看得到（`before_verdict`、`after_verdict`） | 看得到（三個都行；`before_reply` 要開 `reply_via_me`） |

## 三、「自動回這種信」今天能掛在哪（只列事實，形狀在 02）

- **三個 hook 都不能「回一封信」**。它們只能改 body（`before_verdict`）、改判決／錯誤／下一站（`after_verdict`）、改回信 body（`before_reply`）（`py/tools/aos/kernel/hooks.py:8-12`）。退 10＝拒信，拒因是 stdout 的字（`hooks.py:55-72`）。所以 hook 想「回答」只有兩條歪路：自己去寄回信、再退 10 讓站拒掉（站會多寄一封拒信）；或把 body 改成站本來就會處理、而且結果剛好是答案的請求（問腦總機：改成問一個會回答案的假腦）。兩條本線都試了（[04](04-原型.md)）。
- **`admit` 口是包的**，問腦總機與掛 proc 那一包各寫一份；要在這裡認問句信，兩包都要改（或骨架在叫 `admit` 之前先攔）。
- **`order` 之前**：骨架在 `check` 之後、`order` 之前拿得到這輪所有新信（`round.py:76-77`），是骨架唯一「看得到全部、又還沒交給包」的地方。
- **分流**：掛 proc 那一包收 `after_verdict` 的 `next`，可以把問句信轉給另一個信箱，由別的程式回（`kernel/README.md:128-154`）；問腦那一包沒有這個口（`kernel/README.md:33`）。
- **daemon 本體**：今天唯一真的會回問句信的，就是它（`procs_state_path`、`ping`）。它是 C++，不是 kernel 框架。
