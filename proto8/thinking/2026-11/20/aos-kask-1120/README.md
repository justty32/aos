## 先講結論

1. **今天的「問 kernel」**：只有一種問句信 `{"procs_state_path": true}`（「表在哪」），回它的是 aos-daemon 的 C++ 信箱，不是 kernel 框架；框架站只是照「不認得就原樣轉」把它交給 daemon。另外兩樣是讀檔：問腦總機的窗 `endpoints.json`（`aos-llm ls` 讀）、`interfaces.json` 的 `aos-ledger`（沒有程式讀）（[01 第一節](01-現況.md)）。
2. **一封問句信今天的下場**：問腦總機回 `LetterBad`，不記帳；而且問腦的寄信工具 `aos-llm send` 根本不讓它出門。掛 proc 的站把它轉給 daemon，回 `{"applied": true}`——看起來成功，其實沒人懂（實跑，[01 第二節](01-現況.md)）。
3. **「自動回這種信」能放的地方有七種**：骨架攔、各包自己認、標準 hook、hook 多一種「我答了」的回話、分流到答問站、daemon 本體、乾脆放檔（[02 第一節](02-可能的形狀.md)）。今天的三個 hook 都**不能回一封信**，只能改 body、改判決、攔下。
4. **「另外一個 json」**：可以放定義夾、stack、或定義一份 stack 蓋；跟 `interfaces.json`（找檔）、`hook_points.json`（我提供哪些 hook 點）各講一件事，不打架的條件是新的不列 hook 點、不列檔在哪；`interfaces.json` 要不要寫一行指過去是題（[02 第三、四節](02-可能的形狀.md)）。名字不取。
5. **原型跑通了**：一支 `before_verdict` hook，兩種 kernel 都回了一份 json；沒放檔時回 `null`。代價：每問一次收到兩封（答案＋`HookRejected`）；問句和真請求同一封時整封被拒；30 封問句讓後面的普通請求從約 2.7 秒變 14.4 秒；kernel 停了就沒人回。另一種做法（改成問一個會回答案的假腦）只要一封，但進帳本、佔格、只有問腦總機能用（[04](04-原型.md)）。
6. **邊緣狀況十六條**，任務書點名的八條在前（[03](03-邊緣狀況.md)）。
7. **八題等你**，每題都能答先不定（[05](05-要他定的題.md)）。

## 這條線替你做的選擇與不確定的

- 「這種信」讀成「問 kernel 你吃什麼形狀」的問句信；回的內容讀成那份「另外一個 json」。兩件是不是同一件你沒明說，列成第 2 題。
- 「我們的 kernel 框架」讀成骨架一帶（兩種 kernel 共用的 `round.py`），不是某一台自己寫。
- 原型的名字（`kernel_ask`、`kask.json`、`kask-answer`）、兩份示意宣告的內容與欄位、做法 A 的「自己寄答案再退 10」、做法 B 的假腦、答案外面包一層 `{"kernel_ask": …}`，都是示意。
