## 怎麼接

兩台的定義夾各多三樣，`kernel.json` 多一段 hooks（`kernel.json` 每輪重讀，換檔不用重起）：

```
def/
  kernel.json      ← 加 "hooks": {"kask": {"event": "before_verdict", "handler": "kask/answer"}}
  kask/answer      ← hook：body.kernel_ask 是 true 才動，否則不說話
  kask.json        ← 「另外一個 json」的示意（兩台內容不同：問腦那份說看 resource、priority；掛 proc 那份說看 procs_added、queue_wait_ms）
  kask_answer/     ← 只有問腦那台：一個假腦，回答的內容就是 kask.json（做法 B 用）
```

hook 的兩種做法：

- **做法 A**：讀 `kask.json`，用 `aos-post send --in-reply-to <信名> <reply_to>` 自己把 `{"kernel_ask": <那份 json>}` 寄回去，再退 10。站把退 10 當成「hook 攔下」，照規矩回一封 `HookRejected` 拒信、收掉原信。
- **做法 B**（只有問腦總機）：hook 把 body 換成「問 `kask-answer` 這個能力包」的普通請求，總機照常排隊、掛去跑、回信；那個假腦回的 message 內容就是 `kask.json`。

## 看得到什麼

1. **做得到**：兩種 kernel 都回了「另外一個 json」，同一支 hook、同一種問法；沒放檔時回 `null` 加一句原因。問句跟 `procs_state_path` 或真請求寫在同一封時，hook 先答問句，但**整封被拒**——同一封的真請求沒跑（b1x、b3）。這是做法 A 的寫法造成的，不是非這樣不可。
2. **每問一次收到兩封**：一封答案、一封 `HookRejected`。原因是 hook 只能「攔下」不能「回答」（`py/tools/aos/kernel/hooks.py:8-12`、`:55-72`）。問的人要靠內容分辨哪封是答案；不認識這個協議的人會以為被拒了。兩封都留在問的人信箱裡（`b1 leftovers in new/: 2`）。要乾淨就要骨架多一種「這封我答了」的回話（[02 丁](02-可能的形狀.md)）或骨架自己攔（甲）。
3. **做法 B 不用兩封，但它是一次真的問腦**：進帳本（`ledger.jsonl` 多一列 `endpoint: kask-answer`）、算額度、佔一格、要等掛上 daemon 跑完（2.1 秒，做法 A 約 0.7 秒），答案被包在 `message.content` 的字串裡。只有問腦總機做得到；掛 proc 的站沒有「自己跑」的東西可以借。
4. **灌爆會拖慢真請求**：hook 對每封新信都跑一次、一封一封來，30 封問句信讓排在後面的普通請求從約 2.7 秒變 14.4 秒。站每輪把所有新信跑完才下一輪，問句信沒有自己的快車道。
5. **kernel 停了就沒人回**：問的人只能自己等到逾時；信留在 kernel 的 `requests/new/`（本線的問的人沒撤回；`state_path.py` 那種寫法逾時會撤，`py/aos/daemon_ctl/state_path.py:68`）。
6. **寄件人是自報的路徑**：從 Windows 目錄下指令時帳本記成 `/mnt/c/…`（run1），從暫存夾下指令時是暫存夾。答案寄去哪由信裡的 `reply_to` 決定，hook 照寄。

## 卡點（不改程式時）

- hook 不能回信 → 兩封、或整封被拒。
- `aos-llm send` 不讓不是問腦的信出門 → 問問腦總機只能用 `aos-post` 直接寄。
- 掛 proc 的站沒掛 hook 時，問句信被當成「沒事的信」轉給 daemon，回 `{"applied": true}`——問的人分不出「它懂、答了空的」和「它根本沒聽懂」。
- 問腦總機的 `reply_to` 是相對路徑時，hook 要自己照站的 `requests/` 解（原型照 `llm_rules.py:198` 的算法寫）。

## 想自己試

全部在公司 WSL `~/.aos/scratch/aos-kask-1120/`（腳本開頭都先清 `AOS_*`；樹 `t/` 已建好、兩台都已收掉）。

```sh
S=~/.aos/scratch/aos-kask-1120
. $S/env.sh
cd $S/t/llm && setsid aos-exec --stack $S/t/llm/stacks/llm def > $S/llm.log 2>&1 < /dev/null &
cd $S/t/pk  && setsid aos-exec --stack $S/t/pk/st def > $S/pk.log 2>&1 < /dev/null &
cd $S
python3 asker.py llm   $S/t/llm/stacks/llm $S/boxes3/x1 '{"kernel_ask": true}'     # 問問腦總機
python3 asker.py procs $S/t/pk/st/requests $S/boxes3/x2 '{"kernel_ask": true}'     # 問掛 proc 的站
cp $S/t/llm/kernel.nohook.json $S/t/llm/def/kernel.json    # 拔掉 hook（下一輪生效）；kernel.hook.json 是掛上的
# 改 $S/t/llm/def/kask.json 或刪掉它，下一封就照新的答
bash $S/down.sh                                            # 收掉兩台
```

整套重跑：`run2.sh`（問腦總機那幾段、灌 30 封、停機）；`run.sh` 是第一次跑的版本（問腦那幾段因為用了 `aos-llm send` 沒寄出去，留著當證據）。
