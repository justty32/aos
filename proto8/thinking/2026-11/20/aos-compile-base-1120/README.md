## 先講結論

**A. 有沒有通用的編譯底座：沒有，兩支編譯程式共用 0 行。**

| | agent（`agent.py`） | 工具（`tool.py`） | kernel、daemon-root、工具包、kit |
|---|---|---|---|
| 能從 Python 編譯 | 能 | 能 | 都手寫 |
| 程式 | `agent_spec` 四支 1264 行 | `tool_spec` 300 行 | — |

- 兩支裡同一件事寫兩份的大約六件、約 50 行（例外、推名字、旗標殼、寫檔…）（[02](02-現況-agent_spec與tool_spec.md)）。
- 拿 `agent_spec` 直接編 kernel 會卡六處，大多是 agent 的骨架寫死在 `compile()` 裡（[03](03-A-kernel與loop-fsm.md)）。
- **loop、fsm 在執行期早就是獨立積木**（`aos-loop`、`aos-fsm` 吃任何一份），編譯期還不是：fsm 只差一個「單獨寫出 `fsm.json`」的出口，loop 連宣告都沒有。
- 攤了五個形狀（甲 各一支＋小底座、乙 底座＋積木、丙 整套是程式庫、丁 等第三種再抽、戊 共用一支寫檔後端），都跟昨天裁的「C 與 .o」等規則合得來；差在現在要動多少（[04](04-A-形狀甲乙丙.md)、[05](05-A-形狀丁戊與對照.md)）。

**B. Python 函數直接當工具／hook：做得到，分歧點只有一個。**

```
@defs.tool def add(...)  ──編譯──►  抽出來：fn/add.py（之後跟 agent.py 無關，守 C 與 .o）
                                  或
                                  回頭跑：執行時再跑 agent.py 的 add（產物依賴原始碼）
```

- 工具與 hook 在執行期都是「另起一支程式、stdin 進 stdout 出」，`agent.py` 執行期沒人叫，所以函數要嘛編譯時搬出去、要嘛執行時回頭跑（[06](06-B-現況與差幾步.md)、[07](07-B-形狀.md)）。
- 說明與參數可以從函數名、docstring、型別註記抽出合格的 tooldef。
- 原型兩種都走通；抽出來的那種，函數用到 `agent.py` 裡的常數或別的函式，**編譯時就報錯**；每次叫約 15 ms，回頭跑約 76 ms（[08](08-B-原型.md)）。
