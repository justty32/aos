A 題之二：「通用編譯底座」可能長成的三個形狀——甲 各一支 spec 共用小底座、乙 底座＋積木、丙 整套是一個程式庫；各自的寫法示意、要動多少、跟昨天裁的合不合、邊緣狀況。不排名。

## 甲：每種東西各一支 xxx_spec，共用一個小底座

```python
from aos.py.kernel import defs          # 新的 kernel_spec；「defs 不只會在 agent」那句的延伸
DESCRIPTION = "Main llm kernel"
KNOBS = {"slots": 2, "reserved": {"high": 1}}
ENDPOINTS = {"luna": defs.endpoint("endpoints/litellm", url="http://localhost:4000/v1", model="chatgpt-gpt-6-luna-low")}
HOOKS = {"prio": defs.hook("before_verdict", "hooks/prio")}
BODY = defs.daemon()                    # 或 defs.proc()：自己一台／當一列
defs.main(DESCRIPTION, KNOBS, ENDPOINTS, HOOKS, BODY)
```

- **底座**是一支小的（例 `aos/spec_base.py`）：一個 `SpecBad`、推名字、`--compile`／`--dry-run`／`--help` 的旗標殼、多份暫存檔＋改名的 `write`、`home`／`env`、`extern`、`load` 的機制。
- **要動多少**：把上面幾樣從 `agent_spec` 搬出來（百來行），`agent_spec`、`tool_spec` 改成用它、產物一字不變；另寫 `kernel_spec`（兩三百行，主要是 `kernel.json` 怎麼驗）。
- **跟昨天裁的**：C 與 .o、直接蓋、N-70、資料夾即命名空間、gcc 式連結選項都照搬，沒有衝突。
- **邊緣**：
  - 每多一種（daemon-root、kit、llm-team…）就多一支 spec；哪些值得有，要一種一種問。
  - 底座要容得下 `tool.py` 那種「沒給旗標＝當工具執行」，agent、kernel 沒有這層。
  - 底座太早抽，會照 agent、tool 兩個樣本把形狀定死；第三種長得不一樣時要回頭改底座。
- **像什麼**：gcc 這支「驅動程式」底下各語言各一個前端（`cc1`、`cc1plus`），旗標與輸出共用。

## 乙：一個通用底座＋積木（loop、fsm…），agent／kernel 是積木組起來的

```python
from aos.py import build as b
std = b.std
cells = b.fsm("idle", [b.state("idle", ["python3", "idle.py"], {0: "think", 10: "idle"}), ...])
agent = b.agent(DESCRIPTION, system=SYSTEM, tools=[std.pack("look")], llm={},
                body=b.loop(cells, every_ms=300), hooks=HOOKS)
kernel = b.kernel(KNOBS, hooks={...},
                  body=b.loop(b.program(std.tool("aos/kernel"), "kernel.json"), every_ms=300))
b.main(agent)                            # 或 b.main(kernel)
```

- **一塊積木＝執行期一支程式吃的一份檔**：fsm 積木 → `fsm.json`（`aos-fsm` 吃）；loop 積木 → `loop.json`（`aos-loop` 吃）；agent 積木 → `_entry`、`interfaces.json`、內容檔，再加它身體那塊；kernel 積木 → `kernel.json`、`daemon.json`。
- **要動多少**：大。`agent_spec.compile()` 裡寫死的 loop、fsm 兩段要拆成積木；`defs.fsm` 已經是 fsm 積木的一半。今天的 `defs.main(DESCRIPTION, SYSTEM, TOOLS, LLM, FSM)` 可以留作「agent 積木的簡寫」，骨架照舊能用。
- **跟昨天裁的**：C 與 .o、直接蓋、N-70（積木也可以 `load` 來換一塊）、連結選項都合。**資料夾即命名空間要補一條**：一塊積木單獨編譯時寫進哪一夾、跟別塊同夾時檔名怎麼不撞。
- **貼現況的地方**：執行期本來就是這樣分（C-74：fsm 在標準庫層、loop 在基礎層；procs-kernel 已經是「loop＋別的程式」）。
- **邊緣**：
  - 哪些組合合法要有人查：agent-fsm 的格程式會去讀 `tools.json`，換成別的 loop 內容就不一定成立；eca 身體的 loop 跑的是 `aos-eca-turn`，不是 fsm。
  - 錯誤訊息要指回是哪一塊、在 `agent.py` 第幾行。
  - 積木多了，給 AI 填格子的骨架會變長、變難教（[庚第 4 題](../../19/aos-compile-庚/10-使用者裁定.md)「先只給人用」）。
- **像什麼**：Bazel 的 rule 組合、AWS CDK 的 construct；11-18 調查提過 CDK for Terraform 已被官方棄用，是個提醒。

## 丙：不講編譯器，整套就是一個 Python 程式庫，編譯只是其中一個函式

```python
from aos.py import std
from aos.py.agent import defs
from aos.py import kernel                        # 假想
rev = defs.Agent("Review a change", system=open("system.txt").read(), tools=[std.pack("look")])
rev.compile("defs/reviewer")                     # 編譯＝一個方法，直接蓋
k = kernel.Llm(slots=2); k.endpoint("luna", "endpoints/litellm", model="...")
k.compile("llms/def")
# 同一個庫也能操作活的（今天就有）：agent.attach("ann").say("hi")
```

- **今天已經走了半步**：`aos.py` 本來就是程式庫（`agent.attach`、`daemon_ctl`、斷點、`defs`）；`defs.compile(...)`／`defs.write(夾, 結果)` 本來就能在 REPL 裡當函式叫。丙是把「寫定義」也做成同一套可以組、可以傳來傳去的物件，`agent.py` 的旗標殼只是方便。
- **要動多少**：看做多深。最淺＝什麼都不動，只把「`defs.compile` 是函式」寫清楚；做成物件＝宣告寫法大改（大寫常數 → 物件），骨架要重寫。
- **跟昨天裁的**：C 與 .o、直接蓋照舊（`compile` 照樣整份蓋）；N-70 要小心——Python 自己的 class 繼承也只在編譯時，不違反，但寫法會跟 `defs.load` 兩套並存。C-43 原文「一套 library…那個生成就是『編譯』」就是這個說法；11-19「以後搞不好可以統合…aos.py.std…或是aos.std」也是同方向（只是想法）。
- **邊緣**：
  - 一支腳本可以一口氣編十隻 agent 加一個 kernel（像建置腳本），「這份產物的原始碼是哪支」會變模糊。
  - 同一個庫能編譯也能操作活的：編譯完馬上 `ctl add` 很順，也容易在 import 時就碰到活的樹；`aos.py` 現在的規矩「寫定義那邊不載入跑指令的東西」要守住。
  - 大寫常數的骨架對 AI 好填；物件 API 比較自由，也比較難教。
- **像什麼**：Pulumi（用程式語言寫基礎設施）、setuptools 的 `setup.py`、Python dataclass 式宣告。
