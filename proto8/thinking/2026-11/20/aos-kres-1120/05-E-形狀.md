# E. 可能的形狀：「誰在每封信的路上」三種、「基底提供到哪」三層；不排名、不推薦，標出哪些單人就值得、哪些等多人合作才有意義

← [README](README.md)｜上一份：[04-D](04-D-原型.md)｜下一份：[06-F-待定題](06-F-待定題.md)

兩條軸互相獨立：甲乙丙說「每封信來時誰判」，一二三說「aos 內建給多少」。任選一格都說得通。

## 軸一：每封信來時誰判

| | 長什麼樣 | 今天缺什麼 | 代價 | 單人／多人 |
|---|---|---|---|---|
| **甲 agent 每封親自看** | 信進來先扣著，agent 讀宣稱、自己判、點頭；它的經驗就是它的記憶 | 起停那站有 `kernel_gate` 可直接用；**問腦那台沒有 hold**，而且 agent 自己問腦會排進自己的隊（[02](02-B-對照現況.md) 雞生蛋） | 每封一次問腦：慢、花 token；agent 回合中或睡著時整站不動；信裡的字可能騙它 | 單人用不太上（大家都守同一套）；多人時最能接奇形怪狀，但也最貴 |
| **乙 agent 寫規則、規則跑、agent 定期回頭改**（頂層的猜測，你沒確認） | 原型那樣：規則檔＋每封跑的小程式（hook），看不懂的收進樣本；agent 隔一陣子讀樣本與帳、改規則、加版本 | 三個 hook 夠跑規則；缺「定期回顧」的時機（另一隻 proc 自己排）、缺規則檔放哪的慣例 | 規則跟不上新寫法時，那段時間的信照舊規則（或看不懂）處理；agent 改壞要靠版本退 | 單人時規則幾乎不用改，等於一支普通 hook；多人時「定期改」才有事做 |
| **丙 規則由使用者寫、agent 只提建議** | 你（或 kernel 的主人）寫規則檔；agent 看樣本後寄信說「建議加這個讀法」，你點頭才改 | 同乙，另缺「建議」怎麼寄、怎麼點頭的慣例（可借使用者專區的 decide 信） | 每次改都等人；人不在時新寫法一直看不懂 | 單人時就是今天寫 hook 的做法；多人時人會變瓶頸 |

三者也能混：乙為主、改規則時某些段落要使用者點頭（就是丙的一半）。

## 軸二：「基底」提供到哪

| 層 | 內建給什麼 | 其餘誰寫 | 今天有多少 | 單人／多人 |
|---|---|---|---|---|
| **一 只給位置** | 請求裡有一個約定好的 key 放資源宣稱（例：`resource`）；帳上多記一欄原樣宣稱 | 粗化、schema、回顧全是各 kernel 自己的事 | 多寫的 key 今天就不會被拒；帳不收宣稱（llm kernel 的 ledger 欄位固定） | 單人就值得：至少帳上對得起來「說的 vs 實際」 |
| **二 加上格式** | 一之外，還有：schema 放在 kernel 的哪個檔、怎麼被問到（像 `{"procs_state_path": true}` 那種問句信）；粗化規則檔的格式（讀者、單位、公式、版本、看不懂怎麼辦）；帳一列記什麼 | 規則內容、回顧怎麼做 | 都沒有；`interfaces.json` 有「宣告這是哪個檔」的先例 | 多人才有意義：一個人時 schema 就在你腦中；格式的價值在讓別人的 kernel、別人的請求者讀得懂 |
| **三 加上流程** | 二之外，還有：收集樣本的固定位置、定期回顧的時機（kernel 的「每輪一次」或一隻標準回顧 proc）、改規則的路（版本、退回、使用者建議與鎖定） | 回顧時怎麼判斷、公式長怎樣 | 都沒有；時機那半跟 [aos-hook-iface-1120](../aos-hook-iface-1120/README.md) 的「loop 層通用點」（形狀丁）同一件 | 多人才有意義，而且要先有二 |

## 跟其他線的接點（只列，不設計）

- 規則檔放定義夾就跟「kernel 之後也要編譯」綁一起（[aos-compile-base-1120](../aos-compile-base-1120/README.md)）；放 stack 就是執行期狀態。
- 基底算不算「灌 kernel」的一件（[aos-init-kernel-1120](../aos-init-kernel-1120/README.md)）：一層只動 llm 件的帳；二、三層橫跨 llm 件與起停那站。
- 認人：不管哪種，宣稱都掛在自報的寄件人身上（昨天第 3 題你答照舊自報）。
