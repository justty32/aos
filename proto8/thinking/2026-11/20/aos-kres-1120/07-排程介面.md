- 級數、優先是 llm kernel 自己的機制，不是基底；優先這類也算資源（「資源的另一種表現方式，非被動的」），放在請求者帶的那塊 json 裡，**json 內放什麼都可以**；排程規則由各 kernel 自己設計。

- 第七段（以下是**頂層的解讀**）：通用的部分只要「請求的先後」（在等的幾封之間誰先）；宣告只要兩樣——這台看請求 json 的哪些東西、自己有哪些規則；另立插槽、規則做成 hook 點、佇列與格的宣告都不用。
- 第八段：「看請求 json 的哪些東西」算在資源基底（就是對外放話的 schema），不屬排程介面。
- 「排程已經有了＝llm kernel 的排隊」：頂層的解讀是你確認這套是 llm kernel 自己的，不等於通用排程基底。

## 一、骨架現在有沒有「先後」（讀 HEAD `15f6a5bc1`）

兩種 kernel 都跑同一份骨架 `kernel/round.py` 的 `run`（`round.py:49`），每輪：

```
collect → check → order（誰先）→ 逐封：before_verdict hook → admit（pass／refuse／queue）→ after_verdict hook → dispatch／refuse → finish
```

- **骨架有「誰先」的口**：包的 `order(ctx, incoming)`，回一串信名（`round.py:77`；口的名單 `kernel/README.md:29`）。
- **誰先的規則不在骨架**，兩包各寫一份：起停那站先來先排（`procs_rules.py:163-168`）；問腦總機級數＋等久升級 → 期限 → 同後端黏著 → 包的快慢 → 等得久 → 信名（`llm_rules.py:425`、`order.py:128-170`）。
- **這個口 hook 碰不到**：三個 hook 都是一封一封的事件（`kernel/hooks.py:8-11`），看不到別封；`order` 也在 hook 之前就跑完（`round.py:77` 對 `:100` 附近）。所以 hook 讀了宣稱、把新信改成 high，這輪排位已定，留隊後下一輪才照新的排（看程式推的，沒實跑）。
- **只靠骨架＋hook 做得到的是逐封的事**：改這封（`before_verdict`）、放／拒／換下一站（`after_verdict`，`hooks.py:32-34`）、扣著等人表態（hold；只在起停那站，包要有 `held`，`procs_rules.py:231`、`round.py:62`）。`after_verdict` 不能改成 queue（`hooks.py:32`）。

**骨架要補的是不是只有這一件？** 「先後」本身就這一件：讓 kernel 不寫整包也能給「誰先」的規則。但有一個事實要知道：**先後只有在有信要等的時候才有差**。信要等，是因為包的 `admit` 說「沒格、先排著」（`round.py:108`、`:113-118`）；格數在包裡、兩包各一套（`procs_rules.py:170`、`slots.py:5`）。一台沒有任何上限的 kernel，每封當輪就放，排誰先都一樣。你說格的**宣告**不用；格本身今天就在各包裡，不用動，只是先後要搭著它才看得到效果。

## 二、「先後」放進骨架的最小樣子：缺什麼、作者要給什麼、llm kernel 搬不搬得上

- **今天缺**：一個不用寫整包就能給的「誰先」規則；骨架在 `order` 那一步找不到包的 `order` 時，用它。
- **kernel 作者要給骨架的**：一個「誰先」的規則，吃在等的那幾封（每封：信名、寄件人、整塊請求 json、等了多久），回順序。用什麼形式給（一支程式、一個 Python 函式、一份資料檔）是實作的事，這裡不攤。
- **骨架要多給規則的一樣東西**：「等了多久」。今天這是包自己記的（問腦總機記在 `queue.json` 的 `seen_at_ms`／`seen_at_cycles`，`order.py:59`、`:113`；起停那站記上一輪的順序，`queue_fifo.py:27`）；規則要做等久升級或先來先排，就要骨架或包把它交進來。
- **llm kernel 那套搬上去會卡的三處**：
  1. 它比的不只是請求 json：「包的快慢」「同後端黏著」讀的是 kernel 自己的狀態（`a["pack"]["speed"]`、`backends`，`order.py:144`、`:150-169`），規則的輸入要能帶 kernel 自己的東西。
  2. 級數也被 `admit` 用：保留給 high 的格只認宣告的級數（`llm_rules.py:490`），先後規則若把優先讀成別的形狀，保留格那段還是讀舊的 `priority`，兩處要對齊。
  3. 驗不過的信排最前（輪到就回錯，`llm_rules.py:426-431`），這是它的 `order` 順手做的事，搬走時要有人接。

## 三、宣告「自己有哪些規則」的最小樣子（示意，不定案）

「這台看請求 json 的哪些東西」照你第八段算在資源基底裡，就是對外放話的那份 schema（[02](02-B-對照現況.md)、[04 原型](04-D-原型.md) 的 `schema.json`），這裡不重寫。排程這邊只宣告規則，列名字與一句話：

```json
{"rules": [{"name": "level_then_deadline", "summary": "higher claimed level first, then nearer deadline; waiting long raises the level"},
           {"name": "budget_per_sender", "summary": "a sender over its budget waits for the next window"}]}
```

放哪的候選與接點：

| 候選 | 接點 |
|---|---|
| kernel 定義夾的 `interfaces.json` 多一段 | 今天 llm kernel 已用它宣告 `aos-ledger`（帳本在哪）；同機讀得到 |
| 跟 hook 點的宣告放同一份 | hook 介面設計線在定宣告式事件表；格式等它定了才知道塞不塞得下 |
