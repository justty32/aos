# 使用者原話：kernel 的資源基底框架與排程介面（11-20 下午八段，逐字）、頂層當時的理解與他回的「對的」

## 第一段：想法（頂層轉）

> 然後kernel那邊我有想法，就是說，我預想中我們會提供很自由的資源框架基底，方便後續其他使用者規劃排程或管理。就是說，善用json特性和agent適應性，比如一個kernel，他一開始是一個agent，然後他開始收請求，他一看請求，發現裡面所宣稱的資源需求是{"cost":{"token":{"in":123, "out":122}}, "time":122, "time_unit":ms}，(當然，實際的資源需求，可能kernel之後幫它跑的時候會自己另算，並在自己的本本上記一筆)，然後下個請求則是有點類似但細節不同的，比如token那邊沒有in，然後out的值卻是一個檔案路徑，然後沒有time,time_unit，而是time_ms，再下個請求又可能是cost:{token:123,time:"32s"}，多種多樣。agent會收集一段時間的資料，然後去改進自己，讓自己適應這些東西，這就是agent適應性。然後json特性這塊，可利用的比如說可以只讀自己想看的key，所以agent這邊在寫程式的時候就可以比較舒服，當然，也可以寫得比較嚴格。然後還有一個可利用的地方，也就是json的粗化和細化，好比說agent這邊，使用者交代說，你的排程就是看cost值，這個cost值是一個float，以1.0為滿值，那agent這邊如何處理呢？agent可以一邊向外放話說，他就是看資源obj中的cost，並且那個cost會是float，也就是提供一個json schema，然後有想要用這個kernel的人就會遵守，當然，也會有人不遵守。所以agent這邊就會做適應，適應的話就是做粗化，比如agent會自己判斷(經歷幾次後會有經驗)，判斷說cost:{token:123,time:123, time_unit:"ms"}這塊，可以用某公式(token*10+time)，將其粗化成cost:0.2這樣。這個公式會是agent自己提的然後使用者可能會給一些建議。但反正就是這樣，agent會嘗試把奇形怪狀的資源宣稱，變成自己能看得懂、能處理的，那，這個過程可以善用json的忽視key，還有粗化細化等能力...同級的key也是可以啦，反正agent會自己處理。總之，我會在想，是否可以規劃這樣一個kernel資源基底框架。

## 頂層的理解（頂層當時講給他聽的，不是他的話）

1. 基底很鬆：資源宣稱是一塊不強制形狀的 json。
2. kernel 一開始是一隻 agent，對外放一份 json schema。
3. 不守的它自己粗化成看得懂的數；公式自己提、使用者可給建議；收集一段時間資料後改進自己。
4. 宣稱歸宣稱，實際用量 kernel 自己另算、記本子。

頂層同時講了五個會挖的邊緣：每個請求都叫 agent 看會很慢很貴（頂層猜：agent 寫粗化規則、平常規則跑、agent 定期回頭改，要他確認）；看不懂的宣稱怎麼辦；值是檔案路徑的權限；公式寫錯餓死某類請求；kernel 改自己改的是定義還是執行期規則、改壞怎麼退。

## 第二段：他聽完上面之後回（頂層轉）

> 對的，這塊的功能，在只有單個使用者的時候可能用不太上，因為大多agent和函數都會遵守一套宣稱，但在多使用者、一大堆體系需要合作的時候，ㄟ，那就很有用了

怎麼讀：「對的」是對頂層整段回覆（四點理解＋五個邊緣）說的，所以上面四點記成「使用者 11-20 回『對的』」；**他沒有逐條確認**，頂層那個「agent 寫規則、規則跑、agent 定期改」的猜測仍是題目（[06 第 2 題](06-F-待定題.md)）。新資訊是使用情境：價值在多使用者、多體系合作；單一使用者時大家多半守同一套宣稱，用不太上。

## 第三段：他自己解釋「細化」（頂層轉）

> 細化，就是有人可能只丟一個cost:43，然後kernel他本身吃cost:{token:13,time:123}，他可能會自己把cost:43細化成...當然，這會有問題，但反正agent會自己處理，使用者也會看

怎麼讀：細化＝粗化的反方向——請求給的比 kernel 吃的粗（只有一個數），kernel 把它拆成自己吃的細形狀。他知道這是在補原本沒有的資訊，態度是交給 agent 與使用者看著辦，所以這件不列成待定題，只在 [03](03-C-邊緣狀況.md) 記一筆事實。

## 第四段：問排程基底（頂層轉）

> 這是kernel的資源基底，那排程基底這塊，我們目前的樣貌？

頂層照 aos-htop-1119 的盤點答了現況（問腦先後在 llm kernel：級數＋等久升級＋期限＋格數＋保留格＋三層額度；誰能起在權限站；誰先醒沒人管；級數沒人寫、優先只在擠時有效、請求裡沒有資源宣稱的欄位、認人靠自報、比順序的邏輯寫死、沒有每輪一次的時機）。

## 第五段：他接著說（頂層轉）

> 級數、優先這塊，都是llm kernel自己的機制。排程這塊的資源宣稱，也會被納入剛剛的資源基底中，包括基底、優先級，也都可以算在資源中，或者說，他是資源的另一種表現方式，非被動的，但總之會納入資源基底中...反正就是發起請求者自己會帶一個json，說這個請求怎樣怎樣，啊這個json內放啥都可。排程的規則本來也該是kernel自己設計。認人靠自報...對，現在先這樣，等以後權限體系穩了，應該就能解決。每輪一次...之後hook點好了就可以捕。我要的是，是否有一個通用的kernel排程介面，好比hook點介面宣稱那樣，

從這段記下的決定（不再列題）在 [07](07-排程介面.md) 開頭。「排程已經有了＝llm kernel 的排隊」：頂層的解讀是他確認這套是 llm kernel 自己的，不等於通用排程基底。

## 第六段：聽完「kernel 站有共用骨架……排隊那套是 llm kernel 自己寫的（待核實）」之後（頂層轉）

> 喔喔，看起來我說的排程介面，就是kernel骨架本來就有的東西。

頂層當時回「一部分是、排先後那塊待核實」。本線核過的答案在 [07 第一節](07-排程介面.md)：一半對。

## 第七段：收窄排程介面（頂層轉）

> 請求的先後確實應該有。看起來也只需要這個就好了，你要線加做的2，除了宣告要看json的啥、我自己有啥規則之外，感覺都不用。

「你要線加做的2」指頂層講給他聽的三種形狀：① kernel 宣告「我看請求 json 的哪些鍵、有哪些佇列與格、規則是哪支程式」；② 基底只給「待排清單＋下一個是誰的插槽」；③ 排程規則本身是一個 hook 點。**頂層的解讀**：通用的部分要有「請求的先後」，骨架只需要補這一件；宣告只要「看請求 json 的哪些東西」與「自己有哪些規則」；②、③ 的攤開比較與「佇列與格」的宣告不用做。

## 第八段（頂層轉）

> 不過宣告要看json的啥，這應該是算在資源基底中

所以「看請求 json 的哪些東西」（對外放話的 schema）歸資源基底；排程介面只剩先後與「自己有哪些規則」。
