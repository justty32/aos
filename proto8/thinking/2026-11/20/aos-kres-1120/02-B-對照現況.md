## 今天兩種 kernel 收到什麼、記什麼、依什麼排

| | llm kernel（問腦總機） | 框架站（procs-kernel／daemon-kernel，kernel_gate 也是它） |
|---|---|---|
| 信裡看的 | `body.endpoint`（能力包代號）、`body.request`（對話）、`body.priority`（`low`／`normal`／`high` 或數字只看正負，可帶 `deadline`） | 要起停哪個 proc、`queue_wait_ms`（寄件人的期限） |
| **資源宣稱欄** | **沒有**。最接近的是 `priority`（「我急不急」），不是「我要用多少」 | **沒有** |
| 多寫的 key | 不檢查、不拒，但也**不轉進** `request.json`、**不記帳**；hook 看得到整份 body | 不檢查、不刪，**原樣轉給下一站**；kernel_gate 把它們當「寄件人的話」秀給 agent |
| 記什麼 | `ledger.jsonl` 每封一列：寄件人、包、模型、何時收到／掛上／跑完、`elapsed_ms`、`usage`（模型回報的 token）、錯誤碼；`used.json` 是按窗加總（總、每包、每寄件人） | 判決紀錄；不記用量 |
| 依什麼排 | 級數（含等久升級）→ 期限 → 同後端黏著 → 包的快慢 → 等得久 → 先寄；格數、保留給 high 的格 | 名單、同時幾個在跑、沒格先來先排 |
| 額度 | 三層（總、每包、每寄件人）×窗（時／日／全部）的 `max_calls`／`max_tokens`；**事後照實際 usage 扣**，判的時候只看「已經用到頂沒」，**沒有事先預估**（`_metainfo` 第二步 `llm_tokens` 預估額度沒做，程式裡沒有） | 無 |
| cooldown | 不在 kernel：eca 自己記 `cooldown.json`；fsm 收到 `BudgetMissing` 照 `resets_at` 等 | — |

所以他說的第 9 件「自己另算、記一筆」**今天就有**：ledger 記的正是實際的 token 與時間。缺的是**宣稱那一半沒人記**，帳上對不起來「說要多少 vs 實際用多少」。

## 三個 hook 時機夠不夠做他說的事

昨天實測過 llm kernel 掛 hook（[aos-htop-1119 03](../../19/aos-htop-1119/03-自訂kernel-形式與最小實測.md)），三個時機：判之前（`before_verdict`，看並改 body）、判之後（`after_verdict`）、回信之前（`before_reply`，看得到 `usage`）。

| 他的零件 | 今天怎麼做 | 夠不夠 |
|---|---|---|
| 1 宣稱 | 寄件人在 body 多寫一個 key（例 `resource`） | 夠：不會被拒 |
| 3 只讀想看的 | hook 自己決定讀哪個 key | 夠 |
| 4 放話 schema | 沒有固定地方放；可以放 kernel 定義夾或 stack 的一個檔，`interfaces.json` 有「宣告這是哪個檔」的先例 | 缺慣例 |
| 5 粗化、6 細化 | `before_verdict` handler 讀規則檔、算出數 | 能算，**但算出來沒地方用**：llm kernel 只認三級＋期限，0～1 的 float 只能壓成 low／normal／high 或換算成期限 |
| 7 收集資料 | handler 把看不懂的樣本寫自己的檔（原型的 `unreadable.jsonl`） | 夠 |
| 7 改進自己 | 另一隻 agent 定期讀樣本、改規則檔；規則檔每封都重讀 | 能做，但**沒有「每輪一次／定期」的時機**，回顧要另一隻 proc 自己排 |
| 8 使用者建議 | 改規則檔或寄信給那隻 agent | 沒有慣例 |
| 9 另算記帳 | ledger 已有實際值；`before_reply` 可把「宣稱＋粗化結果＋實際」寫一列自己的帳 | 能做，但要 hook 自己把判之前看到的宣稱留著、回信時再對（ledger 本身不收宣稱） |

框架站那邊一樣：hook 讀得到多寫的 key，可以照粗化結果放行、拒或 hold；它沒有「先後級數」，只有先來先排。

## 「kernel 一開始是一個 agent」在今天是什麼意思

- **llm kernel 不是 agent**：它是一包 Python，由它那台 daemon 每 300 ms 叫一輪，不叫腦。它**沒有 hold**（不能把信扣著等人點頭），只有框架站有。
- **框架站可以是 agent**：`kernel_gate` 讓任何 agent 當門，規則放行的先扣著，agent 一封封點頭；站只在 agent 兩個回合之間、醒著的時候跑。
- **雞生蛋**：agent 當 kernel 時，它自己問腦的信寄 `AOS_LLM_KERNEL`。
  - 它管的是「起停 proc」那種請求：問腦歸 llm kernel，不打結。
  - 它要管的是「問腦」請求（自己當 llm kernel）：它自己的問腦信會排進自己的隊，而它在回合中站不跑——**卡死**，除非它的問腦走另一台 llm kernel，或規則裡寫「寄件人是我就直接放」（寄件人自報，別人也能冒充成它）。
  - 所以「一開始是 agent」今天能直接套的是：agent 寫規則、規則由 hook 每封跑、agent 自己不在每封信的路上（頂層的猜測那形狀）；或 agent 只管起停那一站。

## 單人時今天這樣就夠，多人多體系時缺什麼

他第二段說的：單一使用者時大家多半守同一套宣稱。

- **單人**：所有 agent 是同一個人用同一套範本編譯的，宣稱形狀本來就一樣；要「依宣稱排」寫一支 `before_verdict` hook 就做得到，不需要粗化、不需要 agent 適應。今天缺的只有「放話 schema 放哪」的慣例，而一個人用時，那份 schema 就是他腦中的那套。
- **多人、多體系**：缺的是——
  1. **別人知道去哪看 schema**：今天沒有「問 kernel 你吃什麼形狀」的問句信（有先例：`{"procs_state_path": true}` 那種問句）。
  2. **宣稱的來處**：今天寄件人是信封上自報的路徑；另一個體系來的信，路徑在別人的樹上，`budget.senders` 那種「按寄件人」的表接不住。
  3. **跨機、跨帳號送信**：今天信是同一台、同一個 Linux 帳號的資料夾；兩機之間靠 git／rv 搬樹。別人的體系怎麼把信送進我的 kernel，今天沒有路（這不是本題，是本題的前提）。
  4. **對帳**：kernel 自己幫它跑的（例如問腦），實際用量照樣量得到；只是「排個先後」、實際在別人那邊跑的，kernel 量不到，只能信它的宣稱或它的回報（跟昨天「eca 的花費不經過 kernel」同一類）。
