# F. 要你定的九題（1～7 資源基底、8～9 排程介面）：每題都有「先不定」；第 5、7 題標了沒把握是不是題

不代選。選項與後果可以直接貼成選項框。「細化會憑空補資訊」你已說交給 agent 與使用者看，不列題。

**第 1 題：kernel 資源基底，aos 內建要給到哪一層？**
- a. 只給位置：請求裡約定一個放資源宣稱的 key，帳上多記原樣宣稱——最小；粗化、schema 全由各 kernel 自己來，別人的 kernel 長什麼樣沒有共通點。
- b. 再給格式：schema 放哪、怎麼問到，粗化規則檔與帳一列的格式——不同人的 kernel 與請求者讀得懂彼此；要先定一批格式。
- c. 連流程都給：收集樣本、定期回顧、改規則與退版——「agent 改進自己」開箱就有；要多一個回顧的時機，跟 hook 那線的「loop 層通用點」綁在一起。
- d. 先不定。

**第 2 題：每封信來時誰判？（頂層猜的是 b，你還沒確認）**
- a. agent 每封親自看——最能接怪寫法；每封一次問腦，慢、花錢，agent 回合中整站不動。
- b. agent 寫規則、規則每封跑、agent 定期回頭改——平常快、不花 token；規則跟不上新寫法的那段時間會看不懂。
- c. 規則由使用者寫，agent 只提建議——你握著；你不在時新寫法一直看不懂。
- d. 先不定，各 kernel 自己選。

**第 3 題：「agent 改進自己」改的是什麼、經驗存在哪？**
- a. 一份規則檔，放在 kernel 的 stack（執行期）——下一封就生效、有版本可退；換一隻 kernel 要自己抄過去。
- b. 規則寫在 kernel 的定義裡，改＝重新編譯——跟 agent 那套一樣整齊、可 git；每改一次要編譯、重掛。
- c. 留在 agent 的記憶（它的 stack 筆記），判斷時參考——最自然；別人看不懂、換一隻就沒了、改壞了沒版本可退。
- d. 先不定。

**第 4 題：對外放話的 schema 誰說了算？**
- a. kernel 的主人（使用者）定，agent 只負責收不守的——放話穩定；大家都不守某條時，只能等主人改。
- b. agent 也可以改 schema（例：發現大家都寫 token，就改收 token）——跟著請求者走；請求者看到的 schema 會變。
- c. 先不定。

**第 5 題（沒把握是不是題，跟第 1 題選 b 以上才有關）：請求者怎麼知道一台 kernel 吃什麼形狀？**
- a. kernel 定義夾裡固定一個檔（像 `interfaces.json` 那樣宣告），請求者自己去讀——同機好做；跨機、跨帳號讀不到。
- b. 寄一封問句信問 kernel，它回 schema（像今天問表在哪的那種信）——跨體系也能用；kernel 要一直有人回。
- c. 都不提供，請求者愛怎麼寫就怎麼寫，靠 kernel 粗化——最省；放話就沒地方放。
- d. 先不定。

**第 6 題：資源宣稱亂報（報小一點好插隊），態度跟身分那題一樣嗎？**
- a. 一樣：照舊自報，風險自擔——kernel 只記，不罰。
- b. kernel 拿實際帳對宣稱，說少用多的下次排後或打折——有記性的 kernel 才做得到；誰算「說少用多」也是規則的一部分。
- c. 先不定，各 kernel 自己選。

**第 7 題（沒把握是不是題）：現在只有你一個使用者，這個基底現在做到哪？**
- a. 只留這份紀錄，等真的有多人、多體系要合作再說。
- b. 先做最小那層（第 1 題 a）：單人也有用，帳上對得起「說的 vs 實際」。
- c. 把原型接成 llm kernel 的一支 hook 在乾淨複本上試一次，看手感——不改程式；只是試，不留成功能。
- d. 先不定。
