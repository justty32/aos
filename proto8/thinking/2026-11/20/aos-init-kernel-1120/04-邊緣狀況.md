# 邊緣狀況：照「llm 件＋權限件、都可選」去切時會碰到的八種情形，今天程式實際怎樣、各切法下是什麼意思

← [README](README.md)｜上一份：[03-可能的形狀](03-可能的形狀.md)｜下一份：[05-待裁題](05-待裁題.md)

1. **兩件都不裝，agent 怎麼叫模型？** 今天叫不了：agent-fsm／agent-python 只會寄信給總機，`AOS_LLM_KERNEL` 沒設＝第一次問腦就 `LlmKernelMissing` 停（`templates/agent-fsm/wait.py:459-464`）。會直接打 HTTP 的只有總機那頭的 `llm_http`。所以「llm 件可選」今天只對「不會想的 proc」與 eca-claude（自己帶 `claude` CLI）成立。若要真可選，有三條路：維持（不裝就不能想）、agent 自己直連（等於把總機縮進每隻 agent，額度與帳本就沒了）、板子出廠帶一個假腦當保底。這是 05 的第 2 題。

2. **只裝 llm、不裝權限**：就是今天的預設，跑得動。llm kernel 不假設站存在。它自己的 `budget.senders` 是一小塊權限（誰能問多少），而且也靠自報的寄件人。

3. **只裝權限、不裝 llm**：站能跑（它不假設 llm 在）；agent 一樣不能想（見第 1 條）。另一個細節：權限站要管「問腦」，得把它擺在總機信箱前面（站的 `next` 指總機）；今天的站與總機是兩個地址，權限件不會自動管到問腦。

4. **一塊板子上兩個 llm 件**：今天可以，但每隻 agent 只認一個 `AOS_LLM_KERNEL`（從 `.env` 繼承，要不同就在 add 時另給環境）。兩本帳分開，htop 那條線要的「一本帳」就要合帳。另一種是 llm-team 那樣，一台轉發給主台（`templates/kernel/llm-team/kernel.json`）。

5. **kernel 件自己掛掉或升級**：
   - llm 件掛掉：agent 只是等，信堆在總機的 `new/`，不壞（`templates/daemon-root/README.md`）；掛在板子上的有 `--auto-restart` 會自己起。
   - 權限站掛掉：比較兇。一旦設了 `AOS_KERNEL`，連「我是誰」、讀信箱都經它，3 秒不回就 `KernelFailed`（體檢 P4；使用者 11-19 選維持現狀只寫明）。
   - 升級：今天是抄範本，升級要自己 diff 重抄、`kernel.json` 手動合（`thinking/2026-11/17/重建步驟單.md:63`）。若之後 kernel 也編譯，升級＝重新編譯，見 [aos-compile-base-1120](../aos-compile-base-1120/)。

6. **沒裝權限件時，文件裡的「權限」還成不成立？** 只剩兩樣：Linux 檔案權限，與 daemon 本體的 limits／`sub:N`（寫了才套）。知識庫入口說 kernel「decides whether and when the request runs」、「The daemon itself is the simplest kernel」——沒裝站時，daemon 不替誰把關（C-47：最簡單的 kernel，不拒）。若切成兩件，文件要寫明「沒裝權限件＝只有 Linux 與份額」，否則讀者會以為有個守門的。

7. **權限件擋得住誰？** 寄信的人自己選要不要經過站：`AOS_KERNEL` 是寄件人自己的環境變數，拿掉它就直接寫 daemon 控制信箱（寄件人自己設 `AOS_KERNEL` 才會經過站，`py/tools/agent/kernel_gate/_entry:106`）。今天能擋住這一步的只有 guard（擋寫 daemon 控制信箱與 `requests`），而 guard 尚未建議掛；真正的牆是換 Linux 帳號，但換了帳號的 agent 今天寄不了信（`thinking/2026-11/19/subuid-1119.md`）。所以在「同帳號沒有邊界」與「身分自報」都維持的前提下，權限件是**給守規矩的人用的規矩**，不是牆。這跟使用者已定的方向一致，只是要寫明。

8. **另開一台 vs 掛同板，在兩件切法下是什麼意思**：
   - llm 件：另開一台＝關板子時不跟著關、多塊板子共用一個總機（起手範本這樣做）；掛同板＝板子管它的生死、`--auto-restart`（教學這樣做）。兩種都能跑，只差誰管它的命，金鑰要在起它的那個視窗 export（教學第 07 章只寫了掛同板那種）。
   - 權限件：站可以是 daemon 的身體（`daemon-kernel`，站就是板子本人）、板子上一列（`procs-kernel`）、或某隻 agent 身上（kernel_gate）。「另開一台」對權限件比較怪：它管的是這塊板子開不開 proc，另一台的站最後還是寄到這塊板子的控制信箱；而且換帳號由 daemon 執行，站只能填 `sub:N`。daemon 身體當站還有體檢 P3 的毛病：身體跑的時候 daemon 不顧子項（使用者已答風險自擔）。

另一個沒把握是不是問題的：教學（掛同板、`${AOS_STACK}/procs/llm`）與起手範本／重建步驟單（另一台、`${AOS_WS}/llms/stacks/llm`）說法不同。兩種都是允許的擺法（教學 03 的折疊段也寫了另一種），但「灌 kernel」到底指哪種，使用者的說法會影響文件選哪個當主線。
