# 「特殊信箱」能怎麼有：信箱就是一個資料夾，誰 init 誰就有；kernel 的 requests/ 本來就是 body 自己建的、不是 daemon 建的，所以第二個信箱不用動 daemon；六種做法與後果，不代選

## 一、今天一個 kernel 的信箱是誰建、誰認

拿起手範本 start-api 的兩台來看（llm kernel 掛成根上的一列 `llm`，權限站 `perm`）。跑起來之後兩台的 stack：

```
.stack/procs/llm/              ← daemon 開這列時建的資料夾（reconcile.cpp:243）
  procs_requests/              ← llm kernel 自己也是一台 daemon：這是它 C++ 的 ctl 信箱
  requests/                    ← body（kernel_llm → 骨架 round.py）每輪 aos-post init 建的
.stack/procs/perm/
  requests/                    ← body（loop 的 exec → 骨架 round.py）每輪 aos-post init 建的
```

| 信箱 | 誰建 | 誰認（誰收信、誰回） | 出處 |
|---|---|---|---|
| daemon 的 ctl 信箱 `procs_requests/` | aos-daemon 起來時 `aos::post::init` | daemon 本體（C++）：認 `procs_added` 那幾個鍵、`ping`、`procs_state_path` | `cpp/aos-daemon/src/daemon/daemon.cpp:91-98`（名字可在 daemon.json 改、null＝不開）、`mailbox.cpp:32-37` |
| kernel 的 `requests/` | **body 自己**：骨架每輪開頭 `letters.init(requests)`＝`aos-post init` | 骨架＋包（`round.py` 的一輪） | `py/tools/aos/kernel/round.py:56,63`、`letters.py:27-29` |
| 問的人等回信的信箱 | 問的人自己 | 問的人 | 例：`daemon_ctl/state_path.py:28-39` |

重點：

- **信箱就是一個資料夾**（裡面有 `tmp/`、`new/`、`cur/`），位置由擁有者定（`cpp/aos-post/docs/01-用法與元素.md:21`）。`aos-post send` 只驗那個資料夾的 `tmp/`、`new/` 在、而且自己寫得進去（同檔 `:22`）。沒有「註冊信箱」這回事，daemon 也不管一個 proc 有幾個信箱。
- 所以**寄件人能寄到一個 kernel 的第二個信箱**：只要那個資料夾在、寫得進去。不能的只有一種情形——那個資料夾還沒建（kernel 從沒跑過）：`aos-post send` 直接失敗 `MailboxMissing`、退 1（原型實跑，[04 第 6 條](04-邊緣狀況.md)）。
- **寄件人怎麼找到 kernel**：今天兩條路都只指一個地方。掛 proc 的站：`AOS_KERNEL`＝站的 `requests/`（例 `…/procs/perm/requests`）。llm kernel：`AOS_LLM_KERNEL`＝stack，`aos-llm` 固定加 `requests/`（`cpp/aos-llm/src/send/send.cpp:17,34`）。第二個信箱在哪，今天沒有任何地方寫。
- **前例：信箱裡面再放一個信箱**。人的殼走 kernel 問表在哪時，等回信的信箱是 `$AOS_KERNEL/reply/`，就建在站的 `requests/` 資料夾裡（`state_path.py:37`）；`aos-llm ask` 的回信箱也是 `$AOS_LLM_KERNEL/requests/reply/`（`cpp/aos-llm/src/common/common.hpp:13`）。aos-post 只看 `tmp/`、`new/`、`cur/`，裡面多一個資料夾不礙事。

## 二、特殊信箱能怎麼有（六種，順序不代表推薦）

| | 做法 | 寄件人怎麼找到 | 要動誰 | 後果 |
|---|---|---|---|---|
| **甲 stack 底下並排一個** | body 每輪看 `<stack>/<某名>/`，沒有就建 | 從 kernel 的位址推：站＝`AOS_KERNEL` 的上一層再加名字；llm＝`AOS_LLM_KERNEL` 再加名字。兩種 kernel 推法不一樣 | 只動骨架 | 跟 `requests/` 平起平坐，一眼看得出是另一個信箱；寄件人要知道「上一層」這個約定 |
| **乙 requests/ 裡面放一個** | 同甲，但位置是 `requests/<某名>/`（像 `requests/reply/` 那樣） | 站＝`$AOS_KERNEL/<某名>`；llm＝`$AOS_LLM_KERNEL/requests/<某名>`。站那邊只要記一個 `AOS_KERNEL` 就夠 | 只動骨架 | 跟今天的 `reply/` 同一招；`requests/` 夾裡從此不只一種東西，`ls` 時要分得出來 |
| **丙 同一個信箱，進請求路之前先分出去** | 不開新資料夾；骨架在 `check` 之後、`order` 之前，把 body 是問句的信挑出來回掉 | 不用找，照舊寄 `requests/` | 只動骨架 | 不算「特殊信箱」，是「特殊的信」；寄件人不用多學位址。今天寄錯（把問句寄進 `requests/`）的問題就不存在。但問句仍要等前面的 `collect`（收回信、llm 收成品）做完，hook 要不要看到它也要另外寫 |
| **丁 daemon 認第二個信箱** | daemon.json 多一個鍵，列「這列還收哪些信箱」，C++ 建、回報在表上 | 讀 daemon 的表（`procs_state.json` 多一欄） | 動 aos-daemon（C++）與表的格式 | 位址有地方查；但回答的程式還是 body，daemon 只管建資料夾，等於多一層。llm kernel 是 daemon 有 body，權限站是 loop、沒有 daemon 的表可寫，兩種不一樣 |
| **戊 宣告檔寫位址** | 位置隨各台定，寫在某份宣告裡（例：`interfaces.json` 一行，或那份「另外一個 json」自己寫） | 先讀宣告檔再寄 | 動骨架＋宣告檔 | 名字與位置各台可改；寄件人要多讀一次檔、要讀得到那個定義夾。他說 interfaces 是別的用途，這一行算不算佔用它是題 |
| **己 aos-post 認「信的種類」** | 信封多一欄，aos-post 把問句信放進同一信箱的另一個子夾 | 照舊寄 `requests/`，加旗標 | 動 aos-post（C++），所有信箱都受影響 | C-47「共通的只有 aos-post 信封」會多一條共通規定 |

甲、乙、戊可以混（例：預設甲或乙的位置，宣告檔可以改）。

## 三、原型選了哪一種，為什麼（權宜）

原型用**甲**：`<stack>/kask/`，跟 `requests/` 並排。理由只有一個：**完全不用動 daemon、aos-post、寄件工具**，改的只有骨架一個檔加一個新檔，而且沿用上一條線的示意名 `kask` 方便對照。這是原型的權宜，不是提案；乙只差一個路徑，換起來是一行。寄件人怎麼找到它，原型沒做（實跑時直接寫路徑）。
