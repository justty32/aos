## 一張圖

```
 問的人 ──{"kernel_ask": true}──► <kernel 的 stack>/kask/      （特殊信箱：跟 requests/ 並排，body 自己建）
                                       │
 骨架一輪（llm kernel 與權限站共用 round.py，每 300 ms）：
   讀設定 → 拿鎖 →【新：答 kask/ 裡的問句】→ collect → check → order → hook／admit → 放／拒／排
                                       │
 回一封：{"kernel_ask": <定義夾的 kask.json>}；沒放＝{"kernel_ask": null, "why": ...}；格式錯＝AskBad
```

## 先講結論

1. **特殊信箱不用動 daemon 就能有**：信箱只是一個資料夾，誰 `aos-post init` 誰就有；kernel 的 `requests/` 本來就是 body（骨架）自己每輪建的，不是 daemon 建的。第二個信箱同理。難的是**寄件人怎麼知道它在哪**：今天沒有任何地方寫。六種做法在 [01](01-信箱怎麼有.md)；原型挑「stack 底下並排一個 `kask/`」，因為只改骨架，是權宜。
2. **改了骨架兩行＋一個 56 行的新檔**（[02](02-原型做法.md)，diff 全文在 [附件](02-附件-diff.md)）。骨架與兩包的測試改前改後一樣（122／80／20 支都過）。
3. **一問一答**：上一條線掛 hook 是一問兩答；這次一封。連問 30 次的中位數 llm 398 ms、權限站 364 ms，多半在等下一輪（[03](03-實跑與數字.md)）。
4. **灌爆的樣子變了**：上一條線灌 30 封，後面的普通請求慢了約 5 倍；這次 30 封沒變慢（0.97 秒對單獨 1.21 秒）。灌 100 封會拖慢同一輪（一封約 19 ms）。問句與真請求一起來，互不影響。
5. **問句不排隊、不過 hook、不進帳**（實跑：試 hook 只看到普通請求；問 60 次帳本 0 列）。代價：hook 擋不了問句、帳上看不到誰問過；一輪卡住時問句也跟著等（實跑 3 秒）；設定檔壞了也答不了。
6. **kernel 停了**：信留在 `kask/new/`，起來第一輪全答。**從沒起過**：寄件當場 `MailboxMissing`，分得出「沒這個信箱」與「有、但不給」。
7. **寄錯信箱還是今天的樣子**：問句寄到 `requests/`，權限站照樣回假成功 `{"applied": true}`（[04](04-邊緣狀況.md)）。
8. **十題等你**（[05](05-要他定的題.md)），每題都能答先不定；名字全是示意，不列成題。

## 這條線替你做的選擇

- 「放在body」讀成兩種 kernel 共用的骨架 `round.py`，不是 daemon 的 C++、不是 hook。
- 信箱放 `<stack>/kask/`、答問句放在拿鎖之後收信之前、一輪全答、不過 hook、不記帳、每封重讀 `kask.json`、沒放檔＝不給（回 `null`＋原因）、只認 `{"kernel_ask": true}`、別的鍵不看、寄錯信箱不管——都是原型的最小做法，每一條都列成了 05 的題。
- 名字沿用上一條線的示意名，回信外面包一層 `{"kernel_ask": …}` 也照上一條線，方便對照。
- 兩份示意的 `kask.json` 直接用上一條線那兩份，內容沒改。
- 讀的是 HEAD `640f227dc`；工作樹裡別線沒交的改動沒看、沒碰。
