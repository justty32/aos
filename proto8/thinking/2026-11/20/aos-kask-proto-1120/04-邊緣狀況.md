# 邊緣狀況：寄錯信箱照今天（站回假成功）；格式不對回 AskBad；信封壞的丟掉；堆了舊信起來第一輪就答；另外九條順手看到的——只列會怎樣，不定怎麼辦

← [README](README.md)｜上一份：[03-實跑與數字](03-實跑與數字.md)｜下一份：[05-要他定的題](05-要他定的題.md)

「實跑」＝暫存夾 `run.out`／`run2.out`／`run3.out` 跑出來的；其他是讀程式推的。

## 實跑的

1. **寄錯信箱（問句寄到一般請求的 `requests/`）**：原型沒管這條路，所以跟今天一樣。llm 回 `{"error": {"code": "LetterBad", "msg": "cannot understand the letter: …"}}`；**站回 `{"applied": true}`——假成功**，問的人分不出「它答了空的」和「它根本沒聽懂」（實跑）。
2. **問句信格式不對（寄到 kask）**：`{"kernel_ask": "yes"}`、`{"kernel_ask": false}`、`[]`、`{}` 都回一封 `{"error": {"code": "AskBad", "msg": "a question letter must be {\"kernel_ask\": true}"}}`（實跑）。
3. **問句加別的鍵**：`{"kernel_ask": true, "endpoint": "fake", "request": {...}}` 寄到 kask＝只答問句，那個真請求**沒跑、也沒有回信說它沒跑**；`{"kernel_ask": true, "what": ["reads"]}`＝`what` 不看，照樣回整份（實跑）。
4. **信封壞的**（`letter.json` 不是 JSON）：讀不到 `reply_to`，回不了；llm 的 `stderr.txt` 印 `kernel_llm: warning: letter brokenq is broken; dropped`，信從 kask 拿掉（實跑）。跟 `requests/` 的壞信同一套。
5. **沒寫 `reply_to` 的問句**：照樣處理、不回、收掉（實跑）。
6. **信箱裡堆了舊信後 kernel 才起來**：停機時寄的 11 封，`start` 之後第一輪全答（llm 0.30～0.33 秒、站 0.64～0.79 秒），答的是起來那時的 `kask.json`（實跑）。
7. **kernel 從沒起過**：`kask/` 還不存在，寄件當場 `MailboxMissing`、退 1（實跑）。今天不認識這個協議的 kernel（沒有原型這段程式的）也是這樣——問的人分得出「沒這個信箱」與「有、但不給（`null`）」。
8. **kernel 停著**：信留在 `<stack>/kask/new/`，問的人只能等到逾時；原型的問的人逾時沒撤信（`state_path.py` 那種寫法會撤，`py/aos/daemon_ctl/state_path.py:68`），所以起來後會答一封沒人等的信，那封回信留在問的人的信箱（實跑：停機時那封就是這樣）。
9. **設定壞了、hook 壞了**：設定壞＝問句也不答（答問句排在讀設定之後）；hook 壞＝問句每輪還是先答，但站的 loop 跟著退出、等 daemon 重起，實跑等了 7.4 秒（[03 第八節](03-實跑與數字.md)）。
10. **一輪很久**：問句跟著等那一輪做完（實跑 3 秒）。llm kernel 平常一輪很快（問腦是掛出去跑的），會變久的是 hook 慢、信很多。

## 讀程式推的、順手看到的

11. **寄件人找不到這個信箱**：今天只有 `AOS_KERNEL`（站的 `requests/`）與 `AOS_LLM_KERNEL`（llm 的 stack），兩種推法不一樣；權限件那行 `AOS_KERNEL` 寫在 ann 的 `.env`（[aos-kinit-tpl-1120](../aos-kinit-tpl-1120.md)），沒開權限件的 agent 根本沒有站的位址。`aos-llm`、`aos-agent` 都還不會寄問句。
12. **鏈上誰答**：信一律寄到哪一站就是哪一站答（答的是自己定義夾的那份），不往下轉。站後面的根、根後面的別台，問的人要自己一站一站問。今天的 `procs_state_path` 是一路轉到最後的 daemon 才答，兩種習慣不一樣（上一條線 05 第 8 題）。
13. **kask 信箱沒有鎖之外的保護**：答問句在 `requests/.flock` 鎖裡面做，兩輪不會同時答；但 kask 有自己的 `new/`、`cur/`，別的程式（或另一份 kernel）去 `take-all` 它就會搶走問句。今天 `requests/` 也是一樣的。
14. **同一份定義起兩台**：答案讀定義夾，兩台答一樣的話；kernel 自己改那份檔＝改到定義（上一條線 05 第 3 題）。
15. **寄件人是自報的**：答案對誰都一樣，冒名沒好處；但能拿問句叫 kernel 往任何寫得進去的信箱塞一封回信（今天任何信都一樣）。
16. **答案多大**：每問一次整份讀檔、整份回；檔大或問得勤時，每封 19 ms 的成本會往上走。
17. **權限**：kask 跟 `requests/` 一樣是 `755`、只有同帳號寫得進去；跨帳號要能寫進 kask，也要 kernel 寫得進問的人的回信箱。
18. **清道夫**：kask 的 `cur/` 裡只有一輪中的信，正常不會留；kernel 在答到一半時死掉，下一輪會從 `cur/` 再答一次（可能重答一封）。`aos-sweeper` 管不管這個資料夾，沒查。
19. **改名＝寄件人要跟著改**：信箱名、檔名、鍵名一旦有人在用，改哪一個都要通知所有寄件人；三個名字現在都是示意（見 [05](05-要他定的題.md) 開頭）。
