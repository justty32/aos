# 實跑與數字：一問一答；中位數約 0.4 秒（多半在等下一輪）；灌 30 封不拖慢後面的請求；問句與真請求互不影響；一輪卡 3 秒問句就等 3 秒；kernel 停了信留在 kask/new、起來第一輪就答

## 怎麼跑的

- 乾淨複本 `mine/`（HEAD `640f227dc`＋[02](02-原型做法.md) 的改動）跑 `install.py`。
- 暫存樹 `t/`＝起手範本 start-api 原樣抄出：根、掛在根上的 llm kernel（`llm`）、掛上去的權限站（`perm`，`kernel.json` 出廠的 `{}`）。兩台的定義夾各放一份示意的 `kask.json`（上一條線那兩份）。
- 只用假腦（`fake`），沒叫真模型。llm 的普通請求＝問 `fake` 一句；站的普通請求＝`{"ping": true}`（站轉給根、根回 `{"applied": true}`）。
- 原樣輸出在暫存夾 `run.out`、`run2.out`、`run3.out`；下面是節錄。

## 一、問一次：一封回信

```
--- llm   {"ms": 70,  "replies": 1, "body": {"kernel_ask": {"description": "Trial declaration ...", "version": 1, "kind": "llm", "reads": {...}, "rules": [...], ...}}}
--- perm  {"ms": 292, "replies": 1, "body": {"kernel_ask": {"... kind": "procs", "reads": {"procs_added": ..., "queue_wait_ms": ...}, ...}}}
```

沒放 `kask.json` 時：`{"kernel_ask": null, "why": "this kernel gives no declaration"}`，也是一封。

## 二、跟上一條線原型 A（hook 自己寄答案再退 10）對照

| 量 | 上一條線：掛 hook（原型 A） | 這條線：放 body |
|---|---|---|
| 問一次收到幾封 | **2 封**（答案＋`HookRejected`） | **1 封** |
| 問一次多久 | 各一次：llm 0.70 秒、站 1.74 秒 | 各一次：llm 0.07 秒、站 0.29 秒。**連問 30 次的中位數**：llm 398 ms（179～563）、站 364 ms（220～391） |
| 灌 30 封問句，再寄一封普通請求 | llm：問句最後一封 12.7 秒，普通請求 **14.4 秒**（單獨約 2.7 秒）；站：最後一封 8.9 秒 | llm：問句中位 161 ms、最後一封 0.60 秒，普通請求 **0.97 秒**（單獨中位 1.21 秒）；站：最後一封 0.58 秒，普通請求 0.19 秒（單獨中位 0.40 秒） |
| 進不進帳本 | 不進（被拒的信不記帳） | 不進：問 60 次之後 llm 的 `ledger.jsonl` 還是 0 列；之後 10 封普通請求＝10 列 |
| 問句與真請求寫在同一封 | 整封被拒、真請求沒跑 | 寄到 kask 的：只答問句、真請求沒跑（一封回信）；寄到 requests 的：照今天（見 04） |
| kernel 停了 | 沒人回、信留在 `requests/new` | 沒人回、信留在 `kask/new`；起來第一輪就答 |

**對照要打折**：上一條線跑的時候同機有別線在建置，普通請求單獨也要 2.7 秒；今天單獨是 1.2 秒。所以絕對秒數不能直接比。能比的是**形狀**：上一條線灌 30 封，普通請求慢了約 5 倍；這次沒變慢（0.97 秒對單獨 1.21 秒，在晃動範圍內）。原因是 hook 每封問句都起一次 hook 行程（一封一封排在同一輪裡），body 這邊每封只多兩次 `aos-post`，而且在請求那條路的前面一次做完。

**問一次多半在等下一輪**：兩台都是每 300 ms 跑一輪；信剛好在一輪開頭前到就很快（最快 70 ms），剛錯過就要等一整輪再加這一輪的時間。中位數約 0.4 秒就是這樣來的。

## 三、灌更多：100 封

```
llm: {"questions": 100, "sent_ms": 1998, "answered": 100, "first_ms": 1998, "median_ms": 2742.5, "last_ms": 3926, "normal_request_ms": 5226}
```

光寄 100 封就花 2 秒（每封一次 `aos-post send`）。100 封約 1.9 秒答完，**一封約 19 ms**（30 封那次也是約 17 ms）。普通請求排在它們後面寄出，寄出後約 3.2 秒回（單獨 1.2 秒）：問句在同一輪、排在請求路前面一次答完，所以量大時**會拖慢同一輪的請求**，只是比掛 hook 輕很多。原型沒有每輪上限、也沒有每個寄件人的上限。

## 四、問句與真請求同時來

一封問句、一封普通請求一起寄，各五次：

```
llm   question_ms 272 247 262 231 273   normal_request_ms 1002 977 1000 958 1001
perm  question_ms 271 170  81 375  68   normal_request_ms  312 283 287 487 283
```

跟各自單獨問的中位數（llm 問句 398、普通 1206；站問句 364、普通 396）比，**兩邊都沒變慢**。每次都是兩封回信，各回各的。

## 五、問句不過 hook

兩台都掛一支試 hook `seen`（`before_verdict`，把看到的每一封記進 `seen.log`），各寄一封問句、一封普通請求：

```
llm seen.log:   {"letter": "01795154052699692400...", "keys": ["endpoint", "request"]}
perm seen.log:  {"letter": "01795154056929405852...", "keys": ["ping"]}
```

只有普通請求被 hook 看到；問句照樣答了（llm 293 ms、站 75 ms）。

## 六、kernel 某一輪跑很久

`seen` 碰到 body 有 `"slow": true` 就先睡 3 秒（造出一輪 3 秒）。先寄一封這種請求，0.3 秒後寄問句：

```
llm   {"slow_request_ms": 3827, "question_ms_from_its_own_send": 3143}
perm  {"slow_request_ms": 3331, "question_ms_from_its_own_send": 3365}
```

問句在慢的那一輪中間到，**要等那一輪做完、下一輪開頭才答**：約等於那一輪剩下的時間。body 一輪只有一條線，沒有「問句先走」的另一條。

## 七、kernel 停了

`aos-daemon-ctl -d .stack stop llm`（站也一樣）之後問：

```
--- llm   {"no_reply_within_s": 3.0, "letter": "01795154090588854384..."}   llm kask/new: 1
--- perm  {"no_reply_within_s": 3.0, "letter": "01795154093623875950..."}   perm kask/new: 1
```

信留在那台的 `<stack>/kask/new/`。再堆 10 封、再 `start`：

```
llm   {"questions": 10, "in_kernel_box_while_stopped": 11, "answered_while_stopped": 0, "answered_after_start": 10, "first_ms": 295, "last_ms": 327}
perm  {"questions": 10, "in_kernel_box_while_stopped": 11, "answered_while_stopped": 0, "answered_after_start": 10, "first_ms": 638, "last_ms": 789}
```

起來第一輪全部答完（包括停機時那一封），信箱清空。答的是**現在**那份 `kask.json`，不是寄信時的。

從沒起過的 kernel（`kask/` 還沒建）：寄件當場失敗 `aos-post: error: MailboxMissing mailbox not found: …/kask`、退 1——不用等逾時。

## 八、body 自己壞了（只試了站那台）

- `perm/kernel.json` 改成壞的 JSON：問句 3 秒內沒回（這一輪在讀設定時就 `CfgBad` 退出，還沒走到答問句那一行）。修好後下一封 155 ms 回。
- 掛一支起不來的 hook（`on_error` 預設 stop），再寄一封普通請求卡在那裡：問句 **7.4 秒**才回。每輪先答問句、再死在那封信上；但 loop 的 `exec` 退 1 時 aos-loop 自己也退出（`aos-loop: error: RunFailed …`），要等 daemon 把站重起，中間這段沒人答。
- llm kernel 那台（daemon 的 body）壞了會怎樣，這條線沒試。
