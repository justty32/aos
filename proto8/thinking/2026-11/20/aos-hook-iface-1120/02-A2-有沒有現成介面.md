## 結論

- **引擎那層算一套介面，但只管「怎麼跑」**：提供點的一方交一張事件表給 `hook_run.fire`，表的每一列只有三格——拿哪個欄位比 `condition`、能改哪些鍵、能不能攔。agent 那張（9 種）與 kernel 那張（3 種）**形狀相同、各寫一份**。
- **不在表裡的**：事件帶哪些欄位、這是「之前」還是「之後」、哪種身體會觸發、被攔下時呼叫端要做什麼。這些只寫在文件與各處手抄（[04](04-B2-誰假設只有這九種.md)）。
- **沒有條文規範提供點的一方**：NORMS、CONVENTION、CONCEPTS 裡沒有一條在講「提供 hook 點要守什麼」。
- **掛 hook 的一方已經統一**：agent 與 kernel 同一套 handler 規矩。

## 引擎那層給了什麼（`py/aos/hook_run.py`）

| 零件 | 行 | 給提供點的人用來做什麼 |
|---|---|---|
| 事件表形狀 | `:9-10` | `{事件: {"condition": 欄位名或 None, "intercept": (鍵…), "block": bool}}` |
| `validate_name`、`validate_entry`、`complete` | `:43-80` | 讀清單時驗格、補預設值 |
| `fire(event, data, entries, stack, events, warn, only, check)` | `:190-228` | 走到時機時叫；回 `data`、`changed`、`blocked`、`hook`、`text` |
| `HooksBad`、`HookFailed` | `:35-40` | 引擎只丟錯，**怎麼報由呼叫方自己說**（`:5`） |

清單放哪、幾份疊、事件專用的鍵，引擎明說不管（`:6`）。所以 agent 用 `interfaces.json` 宣告 `hooks`（`py/aos/declared_files.py:18` 只認 `aos-agent` 那格）＋stack 那份疊上；kernel 用 `kernel.json` 的 `hooks` 鍵（`py/tools/aos/kernel/round.py:42`）。這兩種「清單在哪」也是各寫各的。

## 在 kernel 或全新子程式提供點（例：kernel 的「每輪一次」）

aos-htop 11-19 實測卡住的第 5 點就是「沒有每輪一次的時機，三個 hook 都是每封信觸發」（[aos-htop-1119/03](../../19/aos-htop-1119/03-自訂kernel-形式與最小實測.md) 第 13 行），拿它當例子：

| 要做的 | kernel 現在在哪 | 全新的 Python 子程式 |
|---|---|---|
| 事件表 | `py/tools/aos/kernel/hooks.py:8-12` 加一列 | 自己寫一張 |
| 清單在哪、讀與驗 | `kernel/hooks.py:15-26`＋`round.py:42`（kernel_llm 借同一份：`kernel_llm/_entry:50`） | 自己決定放哪、照 `kernel/hooks.py:15-26` 抄一份（約 12 行） |
| 觸發 | `round.py` 一輪開頭或結尾叫 fire | 自己找那一行 |
| 失敗怎麼報 | `round.py:131-132` 接 HookFailed 改成 die | 自己寫 |
| 能改的值合不合 | `kernel/hooks.py:29-40` 的 `check` | 自己寫 |
| 事件專屬的設定規則 | 像 before_reply 要 `reply_via_me`（`kernel/procs_rules.py:30`、`kernel_llm/llm_rules.py:253`） | 自己寫 |
| 文件 | `kernel/README.md`、`kernel_llm/README.md`、`kernel_llm/_entry:37` HELP、`knowledge/aos/cli/parts/llm_kernel.json`、`templates/kernel/docs/02-kernel-modes.md` | 自己寫 |
| 條文 | N-42 寫著「三個時機」，要改條文（要你點頭） | — |
| 測試 | `kernel/tests/test_kernel_hooks.py`、`kernel_llm/tests/test_hooks.py` | 自己寫 |

kernel 這邊**沒有** `self_hook`／`aos-agent hook` 那樣的指令（清單手改 `kernel.json`），**也沒有** gdb、編譯（kernel 不從 Python 編譯；aos-compile-base-1120 [03](../aos-compile-base-1120/03-A-kernel與loop-fsm.md) 第 30 行另指出 `agent_spec` 用 agent 的表驗 hook，`before_verdict` 會被當錯）。

**非 Python 的子程式**（C++ 的 aos-loop、aos-daemon）叫不到 `hook_run`。現在唯一的先例是 aos-loop 的 `on_start`／`on_stop` 去 exec 一支 Python 小程式 `py/tools/agent/hook_fire`，由它照 agent 的清單發事件；而 `hook_fire` 只認 agent 的兩個事件（`hook_fire/_entry:27`）。沒有通用的「發一個事件」指令。

## 掛 hook 的一方（handler）：已統一

| 項 | 規矩 | 出處 |
|---|---|---|
| 怎麼被叫 | `aos-exec --stack <stack>/hooks/<名>/ <handler>`，事件寫進那格的 `event.json` 也從 stdin 進 | `hook_run.py:132-146` |
| 事件共通欄位 | `event`、`hook`、`stack`（擁有者的 stack）＋各事件的欄位 | `hook_run.py:136-137` |
| 結束碼 | 0＝照常；10＝攔下（只有表上 block 的事件算，其他當 0）；其他＝失敗 | `hook_run.py:207-213` |
| 回話 | stdout 一個 JSON 物件，只認表上 intercept 的鍵；空＝不改 | `hook_run.py:169-187` |
| 選項 | `intercept`、`async`、`on_error`、`timeout_ms`；`condition` | `hook_run.py:30`、`:43-67` |
| 多個 hook | 照名字排序、前一個改的後一個看得到、攔下就停 | `hook_run.py:198-228` |

小差別在提供方，不在 handler 規矩：kernel 的 after_verdict 一格一格發、攔下時會去解 stdout 的 `BudgetMissing`（`kernel/hooks.py:54-69、79-128`）；agent 的 `content` 要是字串（`agentlib/hooks.py:152-155`）。
