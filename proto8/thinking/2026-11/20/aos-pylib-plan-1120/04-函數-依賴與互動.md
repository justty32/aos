設計之四：函數用到自己以外的東西（import、常數、別的函式）時怎麼辦；編譯時怎麼知道 hook 有哪些事件、能改什麼、能不能攔；跟靜態／動態連結、defs.load、工具同名規則、eca 身體怎麼互動；哪些地方取決於還沒裁的題。

## 函數用到外面的東西

使用者選「抽出來」時，選項上寫明的後果是「函數不能用 agent.py 裡的常數和別的函式（編譯時就報錯）」。照這句定的預設：

| 函數裡用到的名字 | 編譯時 | 為什麼 |
|---|---|---|
| Python 內建的（`len`、`str`…）、函數自己的參數與區域變數 | 沒事 | |
| 檔案最上層 `import x`／`from x import y` 進來的（標準庫、裝好的套件） | 只搬用到的那個名字：一個名字重寫成一行 import（`import os, re` 只用到 `re` 就只寫 `import re`） | 原型已經這樣做；執行時那個 `python3` 要裝得有 |
| 最上層 import 進來、但那支模組是放在 `agent.py` 旁邊的自己的檔（`helpers.py`） | `SpecBad`：`add imports helpers, a module next to agent.py; a compiled function cannot find it at run time` | 產物住在定義夾的 `fn/`，執行時找不到它；要不要開放見下面 |
| `fn`（`fn.fail`、`fn.block`） | 沒事，產物本來就 import `fn` | |
| 編譯庫的東西（`defs`、`std`、它們回的物件） | `SpecBad`：`add uses defs, the compile library; at run time use fn.fail / fn.block` | 原型踩到的坑；產物不能拖著編譯庫 |
| `agent.py` 最上層自己定義的常數、函式、類別、另一個 `@fn.tool` 函數 | `SpecBad`，訊息說出路：搬進函數裡 | 選項上寫明的後果 |
| 閉包、lambda、函式裡面再定義的函式、類別的方法、別的裝飾器包過的 | `SpecBad`：要是檔案最上層的普通 `def`，上面只能有 `fn` 那一個裝飾器 | 原始碼拿不到或拿到不對的 |

裝飾器那一行與預設值裡用到的名字也照同一張表算（`@fn.tool(params=PARAMS)` 的 `PARAMS` 就是「最上層自己定義的常數」）。

**怎麼找「用到哪些外面的名字」**：用 Python 自帶的 `symtable`（編譯器自己的符號表）問那個函數哪些名字是外面的，不自己寫一套判斷（推導式、`with … as`、`:=` 這些它都算得對；Argon B1）。`fn.block(`、`fn.fail(` 是看語法樹裡的呼叫，不是在原始碼字串裡找字。

**想共用常數或小函式時，有三種更鬆的做法，都沒採用，列成 [08](08-待裁題.md) 第 5 題**：

| 做法 | 寫起來 | 代價 |
|---|---|---|
| 旁邊模組、自己放 | 定義夾放 `helpers.py`，函數裡用 `helpers.clean(...)`；產物把定義夾排進找模組的路徑 | `--compile 別的夾`、`defs.load` 衍生時那一夾要自己再放一份（沒放＝編譯報錯）；定義夾裡的 `agent.py` 也變成 import 得到 |
| 旁邊模組、編譯時一起寫進 `fn/` | 同上，但 `helpers.py` 由編譯寫成 `fn/helpers.py`（Argon B3） | 它也變成產物（第二份）；它自己再 import 別的旁邊模組時要一路跟 |
| 同檔的普通函式與字面常數跟著抽 | 什麼都不用搬 | 常數在產物裡是第二份；「哪些能跟著抽」多一套規則；會動的值仍要報錯 |

前兩種原型走過第一種（[09](09-原型.md)），第三種也走過。預設不開，是因為選項上寫明的後果就是報錯，而且每一種都多帶一套規則。

**找模組的路徑**：產物開頭把自己所在的 `fn/` 從路徑拿掉（先比對第一格真的是 `fn/` 才拿），所以一支叫 `json` 的工具（`fn/json.py`）不會害別支產物 import 錯。

**說明書的快取**：`aos-tools` 對可執行檔工具的說明書有快取，只看那支檔的修改時間與大小：手改會重算；`$AOS_HOME/lib` 的 `fn` 升級不會（文件寫一句）。

## 編譯時怎麼知道事件

函數 hook 放進哪個物件，就問那個物件要事件表（[02](02-去留對照與kernel接口.md) 的 `events()`）：`defs.Agent` 今天回 agent 那張（九種，`aos/agentlib/hooks.py`），以後 kernel 回 kernel 那張。它是方法不是固定的表，因為 hook 介面那條線（[aos-hook-plan-1120](../aos-hook-plan-1120/08-給編譯線的接口.md)）的設計裡，表是照「身體」算的：同是 `defs.Agent`，有沒有 fsm 會發的事件不同。表的每一列今天有三格，編譯時各拿來做一件事：

| 表上的格 | 編譯時查什麼 | 錯了報 |
|---|---|---|
| 有沒有這個事件 | `@fn.hook("before_tol")` | `SpecBad`，列出這種東西有的事件（今天 `HOOKS` 寫錯事件也是這樣報，同一支驗法） |
| `condition`（拿哪個欄位比） | 這個事件不收條件卻寫了 `condition=` | 同上 |
| `block`（能不能攔） | 函數的原始碼裡有 `fn.block(`，事件卻不能攔 | `SpecBad`：`after_tool cannot be blocked; fn.block has no effect there`（今天手寫的 handler 退 10 在這種事件會被靜靜當成 0） |
| `intercept`（能改哪些鍵） | 不在編譯時查（回什麼要跑了才知道） | 照舊由引擎在執行時只認表上的鍵 |

其餘（`on_clock` 專用的鍵、`timeout_ms` 的範圍…）直接叫今天那支 `validate_entry`，不另寫一份。

**取決於 hook 十題的地方**（本線只讀「一張表」，表怎麼來不管）：

| 題 | 對這裡的影響 |
|---|---|
| D2（事件表要不要變宣告式）、D4（事件帶哪些欄位進不進表） | 選了宣告式＝編譯時多一項能查：函數裡 `event["xxx"]` 的欄位在不在；不選＝不查，其餘不變 |
| D3（agent 與 kernel 共用一種格式） | 選了＝kernel 那個類別的 `events` 直接可用；不選＝kernel 接上時要多寫一層轉換 |
| D5（表記不記「哪種身體會觸發」） | 本線只查「事件在不在 `events()` 回的表上」，不在＝`SpecBad`（今天就這樣）。選了且表照身體給＝掛到這隻不會發的事件自然被擋（hook 線的設計預設）；裁成「只警告」＝表多給一格、這裡多一個分支；不選＝照舊掛得上、不跑、不報。三種都接得上，不寫死 |
| D6（fsm 與 eca 同名不同義，要不要分名） | 分名＝事件名變多，表上自然有，設計不變 |
| D1（每圈觸發）、D8（kernel 每輪一次） | 多出來的事件名自動能用；每圈都起一支 Python（原型量到一次約 20 毫秒）是 D10 的效能題 |
| D7、D9、D10 | 不影響 |

**跟 hook 介面那條線（`aos-hook-plan-1120`，已交設計稿，都還是設計預設、不是裁定）的接點**：

- 拿表：它給 `hook_point.read()`、`engine_table()`、`for_definition(夾)`，回的表跟今天同形狀；它施工之後，本線只換 `Agent.events()` 裡拿表的那一處。兩條線互不等。
- 它的表多出來的格（事件帶的欄位、能改的鍵與型別、這個事件收哪些額外的鍵）本線先不用，三項檢查照舊；要多查是之後的事。
- 它要編譯多寫兩樣：`interfaces.json` 的 `hook_points`、`loop.json` 的接線（`on_start`／`on_stop` 改叫 `aos-hook fire`，多 loop 層的兩個點）。這兩樣跟本線都會動到 `agent_spec` 寫 `loop.json` 的那一段：**由後開工的那條線帶**，本線的刀不改它們的內容（[07](07-施工計劃.md)）。
- 它的新名字（loop 層的點 `before_run`／`after_run`、`aos-hook fire`、`hook_points`）本稿的示意碼沒寫到；用到時照它定案的名字。

## 跟已有機制的互動

| 機制 | 函數工具／hook 會怎樣 |
|---|---|
| 靜態連結（預設） | 函數工具跟「自己寫的工具」同一類：一格寫進 `tools.json` 的 `tools` 表 |
| 動態連結（`--dynamic`） | 同上，寫在 `tools` 表、跟 `$override` 並存（今天「包給不出的才寫進表」那條）；函數本身不分靜態動態——它的程式永遠在定義夾裡，比 std 工具（程式在 `$AOS_HOME`）更凍 |
| 「靜態連結只固定工具名單」 | 對函數工具要多說一句：名單與程式都固定在定義夾；但產物執行時 import 的 `fn` 仍從 `$AOS_HOME/lib` 讀，aos 升級會影響（文件要寫） |
| hook 同名 | 函數 hook 跟 `hooks=[…]` 裡手寫的那格同名＝後面的蓋前面（同今天自己寫的 dict）；兩個函數 hook 同名＝`SpecBad`；函數 hook 跟函數工具最後同名（會搶同一個 `fn/名.py`）＝`SpecBad` |
| 同名 | 函數工具跟包裡的工具同名＝函數那支蓋掉包那支（同今天 `defs.tool`）；兩支函數工具最後的名字相同＝`SpecBad`；動態包裡被蓋的那支照今天的檢查（欄位沒給齊＝`SpecBad`，叫人把包改靜態） |
| 別的庫的前綴（`庫名_`） | 不適用；函數工具不屬於哪個庫，名字就是函數名或 `name=` |
| `defs.load` | 底的函數工具與 hook 跟著欄位過來；**衍生那支編譯時在自己的夾重抽一份 `fn/…`**，不指回底那一夾（N-70：編出的是完整一份）。`base.pack(prefix=, rename=)` 改了工具名，抽出的檔名跟著工具名走，所以底的 `check` 改名成 `base_check` 之後，衍生可以有自己的 `check` |
| `defs.drop("add")` | 拿掉那一格；`fn/add.py` 這次不寫（舊的不刪） |
| 不宣告 fsm（eca 身體） | 一樣：`tools.json`／`hooks.json` 多一格、定義夾多 `fn/` |
| `agent_def new` 抄一份定義 | 整夾抄，`fn/` 跟著過去。**邊緣**：`agent_def new` 今天會把 `tools.json` 裡的相對路徑改成「指回原來那一夾」（`rebase_tools`，對所有相對路徑的工具都這樣），所以新夾的工具格指的是原夾的 `fn/add.py`、新夾自己那份 `fn/add.py` 沒人用（手改它沒效果、原夾刪了工具就壞）；hook 的 handler 不改寫，指的是新夾自己那份。這跟「產物能照常手改」有出入，要不要動 `agent_def` 列成 [08](08-待裁題.md) 第 10 題；沒裁之前不動、寫進文件 |
| stack 那一層（`self_tools`、`aos-agent hook`） | 不變；它們疊在定義那份上面 |
| `agent_def check` | 今天就會查工具路徑與 handler 在不在，`fn/x.py` 被手刪會被查到 |
| 斷點（aos-gdb） | 不變；函數 hook 就是普通 hook |

## 取決於還沒裁的題

| 題 | 沒裁之前怎麼做 | 裁了之後 |
|---|---|---|
| B4（函數裡的相對路徑從哪算） | 不特別處理＝照今天工具的規矩，從程式自己那一夾（`fn/`）算；工作區要寫 `$AOS_WS`。文件要講，因為 `fn/` 這個起點比今天更不直覺 | 選「先切到工作區」＝`fn.main` 裡加一行，只動一處 |
| A2（kernel 的 defs 怎麼叫） | 不影響函數這一半（`fn` 哪裡都一樣） | 只影響 kernel 那個類別掛在哪個名字下 |
| A3（`loop.json` 改不到） | 不影響 | — |
