設計之一：一個子程式怎麼宣告「我提供這些 hook 點」——放哪個檔、長什麼樣、每個點記什麼、驗什麼；一隻 agent 怎麼說「我身上有哪幾份宣告」。

← [README](README.md)｜下一份 [02 現有的點改寫成宣告](02-現有的點改寫成宣告.md)

名字、檔名、鍵名都是本線擬的設計稿，沒寫成程式。

## 結論

- **誰發事件，誰的資料夾裡放一份 `hook_points.json`**。一份檔＝一個提供者（provider，發事件的那支程式）會發的全部點。
- 每個點記七件事：什麼時候、之前還是之後、帶哪些欄位、拿哪個欄位比 `condition`、能改哪些鍵、能不能攔、認「是哪一次」的欄位。現在引擎那張表的三格（比什麼、能改什麼、能不能攔）是它的子集。
- **一隻 agent 身上有哪幾份**，寫在定義夾的 `interfaces.json`（多一個鍵 `hook_points`，一個清單）。掛得上的事件＝這幾份的聯集。kernel 不用寫這個鍵：kernel 框架自己就是唯一的提供者。
- 掛 hook 的一方（handler 怎麼被叫、結束碼、回話、`on_error`…）**一個字都不變**。

```
 aos-loop 這層（四個點）        身體這層（各自的語意事件）
 loop_points.json        ＋    agent-fsm/hook_points.json     ＝ 這隻 fsm agent 掛得上的事件
 after_start before_run        before_queue after_queue
 after_run   after_stop        before_tool after_tool brain_failed tool_added on_clock
        ▲                                ▲
        └──── interfaces.json 的 "hook_points": [這兩份的路徑] ────┘
```

這張圖就是他早上那句「基於loop……然後在此之上去疊機制」：loop 的點是底，身體的事件是另一份宣告疊上去。

## 檔案長什麼樣

```json
{"description": "Hook points fired by the agent-fsm cells.",
 "provider": "agent-fsm",
 "points": {
   "before_tool": {
     "when": "act: before each tool call runs",
     "phase": "before",
     "fields": {"name": "tool name", "id": "tool call id", "arguments": "the JSON object the tool will get"},
     "condition": "name",
     "subject": "tool",
     "change": {"arguments": "object"},
     "block": true,
     "if_blocked": "the tool does not run; the brain gets the hook's stdout (or a default line) as the tool result",
     "key": "id",
     "fired_in": ["act.py"]}}}
```

## 每個點的鍵

| 鍵 | 必填 | 意思 | 誰用 |
|---|---|---|---|
| `when` | 是 | 一句英文：哪支程式走到哪裡時發 | 文件、`self_hook`、`aos-hook points` |
| `phase` | 是 | `before`（事情還沒發生）、`after`（已經發生）、`on`（跟某件事的前後無關，例 on_clock） | gdb 分「扣住」或「暫停」；驗證 |
| `fields` | 是（可空 `{}`） | 事件帶的欄位：`{名: 一句英文}`；值也可以寫成物件 `{"about": …, "env": 環境變數名, "type": "int"｜"string"}`，表示這個欄位由發事件的指令從環境變數取（給 aos-loop 這種只會設環境變數的提供者，見 [05](05-發事件指令.md)） | 文件、知識庫、`self_hook`；發事件的指令 |
| `condition` | 否 | 拿哪個欄位比掛的人寫的 `condition`；不寫＝這個點不收 `condition` | 引擎 |
| `subject` | 否 | `condition` 比的東西叫什麼（一個英文名詞：`tool`、`code`、`stage`） | gdb 的參數名、文件 |
| `change` | 否 | handler 能改的鍵：`{鍵: 型別}`，型別＝`string`、`nonempty_string`、`object`、`any` | 引擎（只認這些鍵、驗型別） |
| `block` | 否，預設 false | handler 退 10 算不算「攔下」 | 引擎 |
| `if_blocked` | `block` 為 true 時必填 | 一句英文：被攔下時這個提供者會怎麼做 | 文件、`self_hook` |
| `key` | 否 | 認「是哪一次」的欄位（工具呼叫 id、信名） | gdb 放行時認哪一次 |
| `entry_keys` | 否 | 掛這個點時，清單的格可以多寫的鍵名（例 on_clock 的 `every_ms`） | 驗清單：這些鍵只有掛這個點的格能寫，別的點寫了＝`HooksBad`（取代程式裡寫死的那份 on_clock 專用鍵名單）；值的規則仍由提供者自己驗。`config` 是每個點都能寫的共通鍵，不列在這裡 |
| `fired_in` | 否 | 提供者資料夾裡哪幾支原始檔會發它 | 測試（抓「宣告了卻沒人叫」） |

不認得的鍵不管（C-48 的老規矩）。

## 讀的時候驗什麼（不對＝`PointsBad`，一句英文說哪份檔哪個點）

1. 檔是 JSON 物件，`provider` 是非空字串，`points` 是物件；點的名字只有小寫字母、數字、底線。每一格的型別都要對（`fields` 是物件、`condition`／`key`／`subject` 是字串、`change` 是物件、`block` 是真假值、欄位寫成物件時 `env` 是非空字串、`type` 是 `int` 或 `string`）；型別不對一律是 `PointsBad`，不讓 Python 自己的錯誤冒出來。
2. `phase` 是三個值之一；`block: true` 不能配 `phase: on`；`block: true` 時 `if_blocked` 必填。
3. `condition`、`key`、`change` 的每個鍵都要在 `fields` 裡。
4. `change` 的型別是四個值之一。
5. 同一隻 agent 的幾份宣告裡出現同名的點：`phase`、`condition`、`subject`、`change`、`block`、`key`、`entry_keys` 必須逐項相同，否則 `PointsBad`（兩個提供者對同一個名字的說法對不上，掛的人無所適從）。合起來時 `fields` 取聯集（同名欄位的說明用清單裡排前面那份的），`when`、`if_blocked` 兩份都留著、列事件時各列一行並標是哪個提供者說的。

## 一隻 agent 身上有哪幾份：`interfaces.json`

```json
{"aos-agent": {"entry": "body.json", "hooks": "hooks.json",
               "hook_points": [{"provider": "aos-loop"}, "hook_points.json"]}}
```

- 清單的每一項＝一份宣告，兩種寫法：**字串**＝檔的路徑（相對路徑從定義夾算，也可以寫絕對路徑）；**`{"provider": 名字}`**＝aos 自己帶的提供者，由小庫照名字找到那份檔（`aos-loop`、`agent-fsm`、`eca`、`mcp`；名字與檔的對照只寫在小庫一處）。
- 這個鍵由小庫的 `hook_point.for_definition(定義夾)` 自己讀、自己驗（不經 `declared_files.py`：那支只收「定義內的相對檔名」，而且別處拿它抄 stack 覆蓋檔，這個鍵兩樣都不是）；寫壞了＝`PointsBad`。
- 這個鍵**不收指示詞**（`$env` 那種）：Python 這邊沒有行程內解指示詞的函式，為它每格多起一支 `aos-directive` 不划算；`provider` 的寫法已經涵蓋「指到 aos 自己帶的檔」，而且沒裝之前在 `py/` 原地跑測試與裝好之後在 `lib/` 跑，找到的都是同一棵樹裡的那份。
- **沒寫 `hook_points`＝這隻 agent 沒有任何點可掛**：清單裡有 hook 就是 `HooksBad`。不留「沒寫就當九種」的舊行為（proto8 當成沒有舊版）。
- 各範本寫什麼：

| 身體 | `hook_points` |
|---|---|
| agent-fsm 範本自己 | `{"provider": "aos-loop"}`＋`"hook_points.json"` |
| 用 `std.fsm()` 編譯出來的、reviewer（借 agent-fsm 的格程式） | `{"provider": "aos-loop"}`＋`{"provider": "agent-fsm"}` |
| eca-claude、eca-pi | `aos-loop`、`eca`、`mcp` 三個 `provider` |
| 自己寫格程式的 agent | 至少可以寫 `aos-loop` 那份（只要 loop.json 有接線，見 [06](06-loop層的點.md)）；自己的格程式要發別的事件就再放一份自己的 |

## kernel

kernel 的三個點搬進 `py/tools/aos/kernel/hook_points.json`，格式相同。`kernel.json` **不加新鍵**：kernel 框架自己知道那份檔在哪。這只是把 kernel 現有的表換個放法，不替「自訂 kernel」先定任何形狀（對照見 [07](07-對照與衝突.md)）。

## 加一個點，以後要動幾處

| | 現在（調查線數的） | 照這份設計 |
|---|---|---|
| 一定要改 | 16 處、16 個檔 | **2 處**：宣告加一段、觸發那一行 |
| 漏改會靜靜不對 | 4 處（self_hook 選單、gdb 三處） | 0（都改成讀宣告） |
| 還是要人寫的 | — | 給人看的長說明（教學、範本說明）；有測試比對名字與欄位有沒有漏 |

## 這份設計替使用者定的預設（他沒裁，可翻）

- **D4 預設「要」**：欄位寫進宣告當唯一來源。
- **D5 預設「要」**：用「一個提供者一份檔＋agent 列出自己有哪幾份」來記誰會觸發，掛到這隻不會發的事件上當場擋。
- 鍵名 `change`（引擎內部那張表仍叫 `intercept`，由讀宣告的函式轉）、檔名 `hook_points.json`、錯誤代號 `PointsBad`。
