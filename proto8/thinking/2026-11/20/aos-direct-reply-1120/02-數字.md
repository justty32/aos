## 怎麼量的

- 乾淨複本：`git archive HEAD`（`f522b5570`）只抄 `proto8/`、在暫存夾 `~/.aos/scratch/aos-direct-reply-1120/src/` 裡 `install.py`。repo 的程式沒動。
- **kernel**：不起 daemon、不起 aos-loop，直接用 `aos-exec` 手跑 body 一輪（`kround.sh`、`kmeter.sh`），計一輪從起到退的牆上時間（含起 Python）。要比「body 答」與「預先寫成檔」，在**複本裝好的 `lib/`** 裡放上原型線的 `kask.py`，多加一支「答案變了才寫 `<stack>/kask_answer.json`」的小函式，用環境變數切三種：不多做事／寫檔／答信箱（`patch.sh`，約 30 行，只在暫存夾）。
- **agent-fsm**：把 `templates/agent-fsm` 抄成定義夾、手跑 `python3 idle.py`（`meter.py`）。沒叫腦、沒起 daemon（所以 stderr 有 `AOS_CLOCK is not set` 的 warning，不影響收信）。
- 「每答一封」：用 `aos-post` 照原型的做法（`take-all`、逐封 `see`、`done --reply`）在一般 Python 行程裡量，跟誰的 body 無關，兩種都適用（`meter.py` 第 5 段）。
- 原樣輸出：暫存夾的 `meter.out`；kernel 兩支的輸出抄在下面。一台公司機、同機有別線在跑，數字會晃 ±20%。

## 二、多一種「直接回」的信箱，空的時候每輪多付多少

| 怎麼看 | 一次多少 | 出處 |
|---|---|---|
| 在 body 自己的行程裡 `listdir` new/、cur/（原型的做法：空的就不起子行程） | **約 0.024 ms** | 本線 `meter.py` |
| 每輪起一次 `aos-post take-all` 去看 | 約 4.5 ms | 本線 |
| kernel 實跑：不多做事／寫檔／答信箱（信箱空）三種的空輪 | llm 85.8／83.8／82.9 ms；掛 proc 73.0／68.8／63.1 ms | 本線 `kmeter.sh`，三者在晃動範圍內，量不出差別 |

所以**每多一種信箱**，只要「空的時候不起子行程」，固定開銷是每輪幾十微秒，十種也不到 1 ms。若每種都起一次子行程看，每種每輪約 4.5 ms。

## 三、每答一封多少、灌多少封會拖多久

### kernel 一輪（本線實跑，body 答，答案是定義夾裡現成的 `kask.json`）

| 那一輪信箱裡有幾封 | llm kernel 一輪 | 掛 proc 的 kernel 一輪 | 留到下一輪 |
|---|---|---|---|
| 0（空輪中位） | 83 ms | 63 ms | — |
| 1 | 118 ms | 70 ms | 0 |
| 10 | 196 ms | 130 ms | 0 |
| 30 | 324 ms | 316 ms | 0 |
| 100 | 992 ms | 828 ms | 0 |

每封約 **8～9 ms**（llm）、**7～8 ms**（掛 proc）。這一輪多出來的時間，就是同一輪排在後面的普通請求被拖的時間（原型把答問句放在收信之前）。141 封回信全部收到。

原型線量的是「從問的人寄出到收到回信」：一封約 19 ms、30 封普通請求沒變慢、100 封普通請求從單獨 1.2 秒變 5.2 秒（[aos-kask-proto-1120/03](../aos-kask-proto-1120/03-實跑與數字.md) 第二、三節）。本線的 8 ms 比它小，是因為只量 body 那一半、沒算寄信的那一半。

### 在一般 Python 行程裡答（`meter.py`；跟 body 是誰無關）

| 答幾封 | 答案是現成的小檔（約 300 字） | 現算一點東西（走一遍 templates 數檔名） | 答案 1 MB |
|---|---|---|---|
| 1 | 24 ms | 29 ms | 115 ms |
| 10 | 178 ms（每封 18） | 249 ms（25） | 1.07 s（107） |
| 30 | 686 ms（23） | 731 ms（24） | 3.9 s（129） |
| 100 | 2.17 s（22） | 2.41 s（24） | 12.8 s（128） |

- **現成檔 vs 現算**：這裡的「現算」很輕，只多 2～7 ms；真要現算的東西多重，就多那麼多，跟信箱機制無關。
- **答案大**：1 MB 的回答每封約 0.11～0.13 秒（回信要整份抄進信封），100 封就 13 秒。
- 每封的開銷幾乎都在起 `aos-post see`、`aos-post done --reply` 兩個子行程（各約 4～10 ms）；讀答案檔本身 0.06 ms。

### agent-fsm 的 agent（本線實跑 idle 格）

| idle 一拍收到 | 一拍多久 |
|---|---|
| 沒信 | 144 ms（中位） |
| 1 封普通信 | 212 ms |
| 10 封普通信 | 412 ms |
| 30 封普通信 | 879 ms |
| 100 封普通信 | 2.43 s |
| 1 封 `/compact`（可摺的不夠，idle 自己回「不用壓」） | 224 ms，history 多 1 列 |

- agent 收一封普通信約 22 ms，跟答一封差不多（都是兩三次 `aos-post`）。所以若把「直接回」放在 idle 格，灌 10／30／100 封，**同一拍的普通信晚 0.2／0.7／2.2 秒進 history**（按每封 22 ms 推，未實作、未實跑）。
- **agent 比 kernel 多一件要緊的事**：idle 格只在 agent 沒在想、沒在做的時候跑。fsm 是 idle → think → wait（每 300 ms 一拍等腦）→ act → think …，腦在想或工具在跑的那幾十秒到幾分鐘，**idle 不跑**（`templates/agent-fsm/fsm.json`）。今天 `/compact` 太短的直接回也一樣，要等這一輪答完回到 idle 才答。放在 idle 的「直接回」，最壞要等一整個回答做完；要隨時答，就得放進 think／wait／act 每一格（act 的 `timeout_ms` 是 0，一個工具可以跑很久，那一格中間也答不了）。

## 四、預先寫成檔 vs body 答（同一張表）

| | 預先寫成檔（寫的人每輪變了才寫） | body 答信箱 |
|---|---|---|
| 寫的人／答的人每輪固定開銷 | 變了才寫：比對約 0.035 ms；每輪都重寫約 0.6 ms；kernel 實跑空輪量不出差別 | 信箱空：約 0.024 ms，量不出差別 |
| 每多一個人問 | **0**（寫的人不知道有人問） | 每封 8～22 ms，加在那一輪 |
| 問的人等多久 | 讀一次約 0.02 ms（同行程）、起 `cat` 約 7 ms | 中位約 0.4 秒（多半在等下一輪；最快 70 ms），那一輪慢就等那一輪（原型實跑 3 秒） |
| 灌 100 個人問 | 寫的人不受影響 | 那一輪多 0.8～2 秒 |
| 答案有多新 | 最新到「上一輪寫的」；寫的人停了，檔還在、內容停在停的那一刻 | 答的那一刻讀的；對方停了＝沒人答，信留著，起來第一輪答（原型實跑） |
| 問的人要知道 | 檔在哪、讀得到（同機同權限） | 信箱在哪；寄得進去 |

kernel 實跑的「寫檔」模式：檔寫出來了、內容跟答信箱的回信一樣，問的人讀一次約 20 µs。

## 五、順便量的：daemon 代答今天有多快

start-api 的根（daemon 沒寫 interval＝預設 200 ms）單獨起來，`aos-daemon-ctl -d .stack ping` 20 次（`dping.sh`，量完 `shutdown`）：整支指令中位 **202 ms**（173～292），其中起 `aos-daemon-ctl` 本身約 72 ms，工具自己印的「replied in 121 ms」那一次＝等 daemon 下一圈。daemon 每封的開銷本線沒拆開量（C++，不起子行程）。
