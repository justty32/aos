# json → md 實際轉出來的樣子：四種形狀、三種轉法，哪種好看哪種糟

← [README](README.md)｜上一份：[04-外面現成的](04-外面現成的.md)｜下一份：[06-往返與最短解](06-往返與最短解.md)

原型腳本 `~/.aos/scratch/top-1121-mdjson/proto/mdj.py`（暫存夾，不進 repo），三種轉法：

- **樹**：鍵變標題；短值變 `- **鍵**: 值`；同一組欄位的物件陣列變表格。
- **卡片**：同上，但物件陣列改成「每列一個小標題＋欄位清單」。
- **註解**：只給「鍵 → 一篇 md」那種，每篇原樣貼上、前面一行 `<!-- #/鍵 -->`。

## 形狀與結果一覽

| 來源 | 形狀 | 轉法 | 好不好看 |
|---|---|---|---|
| thinking 每天的 `_index.json` | 鍵 → `{description}` | 兩欄表格 | **最好**：一列一份，連結點得到 |
| 知識庫 `aos/me.json` | 鍵 → 一篇 md | 註解 | 好：讀起來就是一份文件 |
| 同上 | 同上 | 樹 | 普通：每篇文章自己的標題和「鍵」標題疊在一起 |
| `逐項表.json`（wf-table，9 欄、20 列） | 物件陣列，格子是長中文 | 卡片 | 好：一列一張卡 |
| 同上 | 同上 | 表格 | 糟：原始檔一列幾百字，預覽要橫捲 |
| `decide_20261113_wu-r2.json` | 物件陣列，格子裡還有物件陣列 | 表格 | **最糟**：一列 8,379 bytes，格子裡塞 json |
| `wf/progress.json` | 一條一個鍵、每條七欄 | 樹 | 普通：短欄是清單、長欄是小標題，順序被打散 |

## 普通：同一頁用「樹」轉

```md
# _description

# Who am I
…
# stack

# What is in your stack
```

鍵 `stack` 和文章標題 `What is in your stack` 變成兩個並排的一級標題，看得懂但囉嗦；而且再從 md 讀回來時，分不出哪個標題是鍵、哪個是文章自己的。

## 好看：wf-table → 卡片

```md

- **item**: 起停掛拆：aos-agent ctl add／rm／start／stop／sleep／wake／set-def（含工具 agents_ctl、subagent、fork、self_ctl 的 stop／sleep／rm）
- **how**: 寄信到 AOS_KERNEL（沒設＝daemon 的 procs_requests）
- **class**: a 已經過 kernel
- **kernel_sees**: 整封 body（procs_added 含 exec、envs、limits；procs_stopped 等名單）＋信封 sender

```

卡片標題是 `id`；用更有意思的欄（`item` 前幾個字）當標題會更好認，但那就要每種表各自設定。

## 從樣本看出來的

- **形狀決定好不好看**，不是轉法：「鍵 → 一句」「鍵 → 一篇文章」轉 md 很自然；「寬表、長格子」轉成表格很糟、轉成卡片可以；「巢狀的表」怎麼轉都囉嗦。
- 一支通用轉法照形狀自動挑（短的擠一行、同一組欄位且格子短才用表格、否則卡片），就能涵蓋上面大部分；`aos-json-view` 在終端裡做的其實就是這套判斷，只是印成縮排文字而不是 md。
- **字串陣列有兩種意思**：aos 的規矩說「全是字串的陣列＝一段文字」，但 `columns: ["id", "item", …]` 是名單不是文章。照規矩轉，`columns` 會變成九行連在一起的字；在 md 預覽裡九行還會被併成一行（md 的單一換行不算換段）。
