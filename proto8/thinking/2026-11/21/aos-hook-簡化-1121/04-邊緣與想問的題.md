## 邊緣狀況

1. **小格夾名**：handler 的工作夾是 `<stack>/hooks/<hook 名>/`。檔名對調後 `hooks.json`＝點的宣告、`hookeds.json`＝被勾清單，`hooks/` 這個夾名跟「被勾著的那些」對不上。改成 `hookeds/` 的話，gdb（讀觸發器的 `trigger.json`、`count.json`）、on_clock 狀態檔、`hook_tools_seen.json` 旁的說明、範本 handler 的說明都要跟著改。
2. **stack 那份覆蓋檔改名**：`<stack>/hooks.json` → `<stack>/hookeds.json`。已經在跑的樹（家機 `~/aos-home`）裡 agent 用 `aos-agent hook add` 加過、關過的 hook，裝新版後**默默不見**（舊檔沒人讀，也不報錯）。照「proto8 當成沒有舊版」不做遷移，但要在更新 `~/aos-home` 的步驟寫一句。
3. **`hooks` 這個鍵換了意思**：今天 `interfaces.json` 的 `hooks` 指清單。換成指宣告後，若有一處程式漏改、還把 `hooks` 當清單讀，`hook_lists` 讀到的是 `{id: 點}`、`doc.get("hooks", {})` 拿到空的＝**默默沒有任何 hook**，不報錯。讀這個鍵的地方：`agentlib/hooks.declared`、`aos-agent hook`（`HooksMissing` 那句也寫著 `{"aos-agent": {"hooks": "hooks.json"}}`）、gdb 的 `HOOKS_FIX`、編譯、知識庫 `cli/hook.json`。建議施工時加一支測試掃「`declared_files` 的 `hooks` 只被讀宣告的程式用」。
4. **同一個 id 在兩份宣告**：`interfaces.json` 的 `hooks` 陣列裡兩份檔都有 `before_tool`（例如有人把 agent-fsm 與 mcp 兩份都列進來）。現在是逐鍵比、不一致就 `PointsBad`；新格式沒有一致檢查的根據。選項：先寫的算、後寫的蓋、報錯、input schema 合併。`hooks.EVENTS`（四份 aos 自帶合起來）今天就有同名（agent-fsm 與 eca 都有 `before_queue`、`after_queue`、`brain_failed`、`tool_added`、`on_clock`），它們的 `block`／`condition` 剛好一樣。
5. **自由鍵寫錯**：`"block": "yes"`（字串）、`"blok": true`（錯字）。第 7 則「有提供就照做」：前者算不算提供？後者一定被當成沒寫＝不能攔，handler 退 10 被當放行。現在 `block` 的型別有驗、錯字一樣默默略過（C-48）。
6. **input schema 要不要拿來驗事件資料**：硬性要有 input schema，但 `aos-hook fire` 要不要照它驗發出去的資料？驗＝要做一小塊 JSON Schema、發事件的程式資料錯了 hook 不跑；不驗＝schema 純粹是給人與 handler 看的說明。他沒說。
7. **env 放在 schema 裡**：`{"type": "integer", "env": "AOS_LOOP_CODE"}`，`env` 不是 JSON Schema 的關鍵字；別的 JSON Schema 工具會忽略它（不會壞），但 `aos-hook fire` 讀它就等於 aos 自己的擴充鍵。
8. **`interfaces.json` 支援指示詞**：誰解、什麼時候解？今天 `interfaces.json` 由 Python 的 `declared_files` 讀、不解指示詞。換成「讀到字串或陣列就逐項過 `aos-directive`」，測試要先裝好、設 `AOS_HOME`（`$AOS_HOME/lib/...` 才找得到），引入寫法稿 06 已提過。
9. **「起來後第一次 on_clock 一定跑」搬家**：今天是 `aos-hook fire --agent … after_start` 順手清狀態（#6）。第 2 層起把它拿出 `aos-hook` 的話，得找別處：在範本 hookeds 掛一個 `after_start` 的 handler 清狀態（變成可被 null 關掉的普通 hook）；或 `hook_clock` 自己比「loop 這次起來的時間」（例如 stack 裡 aos-loop 寫的 state 的起始時間）跟狀態檔。前者簡單但多一支行程，後者要找一個可靠的「這次起來」記號。
10. **旗標檔的維護者**：第 4 層 `aos-hook fire` 不再碰旗標的話，手改定義那份 `hookeds.json` 掛了 `before_run` 的 agent，起來沒有旗標＝那個 hook 永遠不跑（k5b 遇過、`hook_fire` 換掉才補上的那個洞會回來）。
11. **after 點的退 10**（第 3、4 層）：aos-loop 對 `on_after_run`、`on_start`、`on_stop` 的非 0 一律當失敗。今天 `aos-hook` 把不能攔的點的 10 換成 0；拿掉這個換法，有人寫的通用 handler「不想要就退 10」掛在 after 點會讓 agent 收工。
12. **kernel 的宣告不在 `interfaces.json`**：procs-kernel、kernel-python 沒有 `interfaces.json`，kernel 的三個點宣告在程式夾。「唯一約定＝在 interfaces.json 宣告」kernel 今天不符合；他說「kernel……我再想想」、另派了 fable 調查。格式刀只換 kernel 那份宣告的格式、不搬位置，免得跟調查結果打架。
13. **第 4-丙（指令極簡、庫照舊）的混用**：同一隻 agent 的 `hookeds.json` 裡，`on_error: continue` 掛在 `before_tool` 有用、掛在 `before_run` 沒用；`condition` 同理。`aos-agent hook add` 不知道會被哪一家發，擋也擋不了、說明也難寫。
14. **測試量**：第 1、2 層主要改 `test_hook_point*`、`test_hook_points_match`、`apps/hook/*`、`test_agent_hooks`；第 3、4 層會動到 gdb、eca、agent-fsm 的大測試（`test_gdb_live` 685 行、`templates/tests/agent-fsm/test_hooks` 358 行…），工作量大約翻倍。

## 想問他的題

### 第 1 題：`aos-hook` 簡化到第幾層？

| 選項 | 後果 |
|---|---|
| 第 1 層：只做新格式帶走的 | 少約 200 行；行為全不變；最快 |
| 第 2 層：再合併重複、agent 專用的拿出 `aos-hook` | 少約 450 行；行為對掛 hook 的人不變；少幾個事先擋；on_clock「起來先跑一次」要搬家（邊緣 9） |
| 第 3 層：引擎不讀宣告的鍵 | 再少約 100 行、各家多約 60 行；condition 寫法改；after 點的 10 要處理；跟第 7 則衝突 |
| 第 4 層：`fire` 只叫 handler | 核心剩約 300 行；C-90 三個選項、condition、旗標檔要重定；跟第 7 則、C-90、第 11 題衝突 |

看法（不是替他選）：第 2 層。理由是它跟格式刀改的是同一批檔、不碰他說過的任何一句；第 3、4 層省下的行數有一大半會搬到 agent 一家，不是真的消失。

### 第 2 題：`aos-hook fire`（給非 Python）跟 Python 的庫（agent 一家、kernel 用）要不要同一套規矩？

| 選項 | 後果 |
|---|---|
| 同一套（現在） | 同一份 `hookeds` 掛在哪個點規矩都一樣；簡化時兩邊一起動 |
| 指令可以比庫簡單 | 第 4-丙那種；指令省約 200 行；同一份清單在 loop 點與 fsm 點行為不同（邊緣 13） |

### 第 3 題：旗標檔（沒人掛時 loop 不起 `aos-hook`）照舊由誰對？

| 選項 | 後果 |
|---|---|
| 照舊：`aos-agent hook` 改清單時＋`aos-hook fire … after_start`＋`aos-hook check` | 第 1～3 層的樣子；`aos-hook` 裡留一段旗標的事 |
| 只由 `aos-agent hook` 對（加一個 `sync` 動作給手改的人） | `aos-hook` 不碰旗標；手改清單後起來沒旗標，要記得跑一次 |
| 不要旗標，改成編譯時決定接不接線 | 沒人掛的 agent 完全沒這兩格；執行中新掛的要重起；跟 11-20 第 11 題的選擇不同 |

### 第 4 題：條件比對（`condition`）放哪？

| 選項 | 後果 |
|---|---|
| 宣告裡寫比哪個欄位（現在；新格式下是自由鍵） | 掛的人只寫值；`aos-hook fire` 要讀宣告 |
| 掛的人在格裡寫欄位與值 | 引擎不必讀宣告；`--condition` 旗標要改；gdb 跟著改 |
| 拿掉 | handler 自己篩；只想管一支工具的 hook 每次工具都會被起一次 |

### 第 5 題：handler 的小格夾 `<stack>/hooks/<名>/` 跟著改名嗎？

| 選項 | 後果 |
|---|---|
| 改成 `<stack>/hookeds/<名>/` | 名字跟「被勾著的」對得上；gdb、on_clock、範本說明一起改，跟檔名對調同一刀 |
| 不改 | 少改一批；`hooks` 這個字在 stack 裡指「被勾著的那些的工作夾」、在定義裡指「點的宣告」，兩個意思 |
