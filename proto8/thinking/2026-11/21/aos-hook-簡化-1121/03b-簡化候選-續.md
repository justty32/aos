## 第 3 層：引擎不讀宣告裡任何鍵

**一句話**：第 2 層＋`aos-hook fire` 與引擎完全不看宣告的自由鍵；能不能攔、能改哪些鍵、型別對不對，交回給發事件的程式；條件比對改由掛的人在清單那格自己寫「比哪個欄位」。宣告只剩「有這個點、input 長這樣」，給人、給 gdb、給編譯讀。

- **留下**：讀清單；照事件名挑格；條件比對（形狀改成掛的人寫，例如 `"condition": {"name": ["agent_def"]}`，引擎拿 `data["name"]` 比，不必問宣告）；照名字排、前一個改的後一個看得到、退 10 就停；四個選項與逾時；環境變數取欄位（`env` 仍寫在 input schema 裡，因為 aos-loop 只會設環境變數）；旗標檔。
- **拿掉**：`engine_table`；「只有 `block: true` 才算攔」（引擎一律回 `blocked: true`，after 點的程式自己當放行）；「只取 `change` 的鍵」與型別驗（引擎把 stdout 的物件原樣交回，程式自己挑）；`fn.block` 的編譯期檢查；`hooks.EVENTS` 只剩驗事件名一個用途。
- **約少**：第 2 層之外再少約 100 行（引擎約 40、型別驗約 12、表與各處約 50）；但發事件的程式要多約 60 行。
- **誰多做事**：
  - agent 一家（`agent_hooks` 一處就好）：`guard_tool`／`take_letter`／`after_tool` 自己挑 `arguments`／`content`、驗型別；after 類的點遇到 `blocked` 當放行。
  - kernel：自己挑 `verdict`／`error`／`next`／`body`（現在已經在驗值，只多挑鍵）。
  - aos-loop：`aos-hook fire` 退 10 原樣交回；**`after_run`、`after_start`、`after_stop` 的 handler 退 10 會被 aos-loop 當失敗而收工**（現在是 `aos-hook` 把不能攔的點的 10 換成 0）。要嘛 `aos-hook fire` 加一個 `--no-block` 旗標讓 loop.json 寫明，要嘛 aos-loop 改。
  - 掛 hook 的人：condition 要多寫欄位名；`aos-agent hook add --condition` 要改成能給欄位名（或照事件猜一個預設欄位，那就又回到讀宣告）。
  - gdb：觸發器裝 condition 的寫法跟著改。
- **少了的能力**：handler 回了不該改的鍵或錯型別，只有發事件的程式自己有驗才擋得住；`aos-hook fire` 給 shell 用時，shell 要自己判斷「這個 10 算不算攔」。
- **衝突**：第 7 則說 `aos-hook fire`「有提供這些key，就照着做」，這層等於 aos 自己那一家不照做。見 [05](05-衝突.md) 第 1 條。

## 第 4 層：`aos-hook fire` 只叫 handler

**一句話**：`aos-hook fire` 只做一件事——照 `hookeds` 清單把掛在這個事件上的 handler 叫起來、把 input 丟給它、把每個 handler 的輸出與退出碼交回去，其餘全交給發事件的程式。

- **留下**：讀清單（後蓋前、null 關）；照事件名挑；照名字排；寫 `event.json`、`aos-exec` 起 handler（含指示詞解路徑）；輸出 `[{"hook": 名, "code": 碼, "stdout": "…"}, …]`。兩個子選擇：
  - **4-甲 逾時留不留**：留＝`timeout_ms` 照舊（殺整群這件事 shell 很難自己做）；不留＝handler 卡住發事件的程式就卡住。
  - **4-乙 退出碼怎麼給**：「第一個非 0 的 handler 的碼，之後的不跑」＝aos-loop 的 `before_run` 照舊能攔、失敗照舊收工，但上面「after 點退 10 被當失敗」的問題一樣在；「一律退 0、結果只在 JSON 裡」＝aos-loop 讀不懂 JSON，四個點都攔不了也停不了。
- **拿掉**：宣告不再被 `aos-hook` 讀（`--points` 沒了，只剩 `--list`／`--agent`）；條件比對；`intercept`、`async`、`on_error`；改欄位與型別；攔的判斷；環境變數取欄位、`--field-file`、`--field-default`（handler 自己讀 `AOS_LOOP_*`、`stage.txt`）；旗標檔維護（誰對要另外定）；`points`、`check`。
- **約多少**：hook 這套的核心剩約 300 行（`aos-hook` 約 100、跑 handler 約 120、讀清單約 50、說明）。另外有兩條路：
  - **4-丙 Python 庫照舊豐富、只有指令極簡**：agent 一家、kernel 照用現在的引擎（第 2 層的樣子），只有 `aos-hook fire` 變極簡。省下的只有指令那約 200 行；**同一份 `hookeds` 在 fsm 的點與 loop 的點規矩不一樣**（例如 `condition`、`on_error: continue` 在 loop 點沒作用）。
  - **4-丁 Python 庫也極簡**：引擎整份換成上面那約 300 行，各家自己做規矩。專給 hook 的 Python 從約 2,000 行到約 300 行＋各家多出來的。
- **誰多做事（4-丁）**：
  - agent 一家：攔、改、型別、`on_error`、`async`、condition 全部自己做；四格、eca、mcp 共用 `agent_hooks` 一處，所以「自己做」多半是把現在引擎那約 150 行搬到 `agent_hooks`，總行數省不多。
  - kernel：同上，自己做 `after_verdict` 逐格的那套（現在也幾乎是自己做）。
  - aos-loop／loop.json：四個點的語意（誰能攔、失敗停不停）全靠 aos-loop 讀退出碼，after 點的 10 要處理；`stage` 等欄位沒了，`before_run` 不能照格名篩，handler 每格都會被起來再自己判斷（每格多約 36 毫秒起跳）。
  - gdb：condition 沒了，只篩工具名的斷點每次工具都要起 handler；`--no-intercept`、`--on-error continue` 沒有意義（等於一律通知）。
  - 寫 handler 的人：同一個退出碼在不同點意思不同，要看各點宣告自己寫的說明。
  - 掛 hook 的人：`aos-agent hook add` 的旗標剩 `--event`、`-n`、`--timeout-ms`、`--replace`、`--path-json`；寫錯不會被擋。
- **少了的能力**：C-90 的 `intercept`／`async`／`on_error` 三個選項；條件比對；事先擋掛錯的條件與選項；非 Python 程式拿到「整理好的結果」（現在 shell 呼叫一次就知道改過的 data 與是否被攔）；loop 四點的事件欄位；旗標檔若沒有人接手，就沒有「沒人掛時零成本」。
- **衝突**：第 7 則、C-90、待裁第 11 題（旗標檔）、待裁第 4 題（事件欄位以宣告為唯一來源）。見 [05](05-衝突.md)。
