## 丙：讓 `$ref` 的路徑可以由 `$env` 給（改 N-45 與 aos-directive）

乙的毛病是 `$ref` 只收字串、指不到 `$AOS_HOME` 底下。丙把這條放寬：`$ref` 的值（或陣列的元素）本身是 `$env` 指示詞時，先解成字串再當 `$ref` 用。今天這種寫法是「原封不動」，沒有任何檔在用，所以放寬不會讓舊檔變意思。

```json
"hook_points": {"$ref": [{"$env": "AOS_HOME", "$path": "/lib/aos/apps/hook/loop_points.json"}, "hook_points.json"]}
```

陣列寫法（兩份都寫成陣列時接起來）：

```json
"hook_points": {"$ref": [{"$env": "AOS_HOME", "$path": "/lib/aos/apps/hook/loop_points.json"}, "#/aos-agent/own_points"]}
```

- **看不看得出哪來**：看得出，路徑完整。
- **跟指示詞相不相容**：是指示詞本身的延伸，任何用 `aos-directive` 的程式（C++ 的 loop、daemon、fsm，Python 經 `directive_value`）都一起得到這個能力；對 tools.json 的 `$override`、kernel.json 的 `$ref` 沒影響。
- **合起來認不出誰說的**：跟乙一樣——物件同名後蓋前、不報錯，來源丟了；`aos-directive` 是通用的，不能替 hook 做「同名說法要一樣」的檢查。
- **靜態或動態**：動態。
- **搬家**：同甲（靠 `AOS_HOME`）。
- **非 Python 的程式**：叫 `aos-directive` 就拿到合好的內容。
- **要動的程式**：`cpp/aos-directive`（解 `$ref` 前先解它的值；繞圈判斷照舊）、它的測試與 README；N-45 那句「`$ref` 的值不是字串＝換不了」要改（**條文**）；`hook_point.py` 讀之前先過 `aos-directive`、新格式。要 `make`、`install.py` 才生效。

## 丁：新增一個指示詞 `$include`，原地展開（最像 C 的 #include）

C 的 `#include` 是把那份檔的內容**貼在那一行的位置**。丁照這個意思：`{"$include": 路徑或指示詞}` 放在陣列裡＝那份檔的項目一個個貼進這個陣列；放在物件的鍵位置＝那份檔的鍵貼進這個物件。這是通用的指示詞，寫進 `aos-directive`，任何 aos 讀的 JSON 都能用。

ann 的 `hook_points.json`（物件）：

```json
{"description": "Hook points of an agent-fsm agent …",
 "$include": {"$env": "AOS_HOME", "$path": "/lib/aos/apps/hook/loop_points.json"},
 "before_tool": {…}, "…": "其餘六個點"}
```

直接寫在 `interfaces.json`（陣列）：

```json
"hook_points": [{"$include": {"$env": "AOS_HOME", "$path": "/lib/aos/apps/hook/loop_points.json"}},
                {"id": "before_tool", …}, …]
```

寫起來跟甲**一模一樣**；差在誰解：甲是 hook 點的讀者自己解（只在 `hook_points` 有效），丁是 `aos-directive` 解（哪裡都有效，讀者拿到的已經是貼好的）。

- **看不看得出哪來**：看得出。
- **跟指示詞相不相容**：要改規範。N-45 說「指示詞有兩個」，而且指示詞是「整個物件換成指到的值」；丁是「把內容貼進外面那一層」，外面那一層的形狀會變，是新的一種語意。跟 `$ref` 陣列的合法也要講清楚誰先誰後。
- **合起來認不出誰說的**：同乙、丙——貼完就不知道哪個點來自哪份檔，同名的點誰蓋誰要另外定（`aos-directive` 不懂 hook 的規矩）。
- **靜態或動態**：動態。
- **搬家**：同甲。
- **非 Python 的程式**：叫 `aos-directive` 就拿到貼好的內容。
- **要動的程式**：`cpp/aos-directive`（新指示詞、物件與陣列兩種位置、繞圈）、測試、README；N-45 加一個指示詞（**條文**）；`hook_point.py` 讀之前先過 `aos-directive`。

## 戊：C 角括號式的「系統路徑」

C 裡 `#include <stdio.h>` 去系統的夾找、`#include "my.h"` 從本夾找。戊照抄：

```json
"$include": "<hook/loop_points.json>"
```

角括號＝從 `$AOS_HOME/lib/aos/apps/` 找，沒有角括號＝從本夾找。

- **看不看得出哪來**：比 `{"provider": "aos-loop"}` 好（有檔名），但「`<>` 從哪個夾找」仍是一條要背的暗規則。
- **跟指示詞相不相容**：不相容，而且跟條文衝突：C-56「寫什麼就做什麼」、P-31／N-45「不做字串內插、不把規則埋進字串」；要指到環境變數底下的檔，規範的寫法就是 `{"$env": …, "$path": …}`。
- 其餘同甲。列出來只是因為它最像 C；不建議。

## 建議（是建議，不是定案）

**甲**。理由：寫法跟 repo 裡已經在用的兩處（procs-kernel `loop.json` 的 `--points`、tools.json 的 `$override`）同一個樣子；不改指示詞、不改條文、不動 C++；hook 自己的規矩（同名要一致、記誰說的）還能做。丁跟甲寫起來完全一樣，以後真的有別的 JSON 也想要「原地展開」，再把甲升成通用指示詞，宣告檔一個字都不用改——這條升級路是甲的另一個好處。
