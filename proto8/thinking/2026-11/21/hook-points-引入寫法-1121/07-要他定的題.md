## 第 1 題：別家的點怎麼引入

| 選項 | 長相 | 後果 |
|---|---|---|
| 甲 `$include` 鍵，讀者自己解 | `"$include": {"$env": "AOS_HOME", "$path": "/lib/aos/apps/hook/loop_points.json"}` | 不改指示詞、不改條文、不動 C++；跟 procs-kernel `loop.json`、tools.json `$override` 同一個樣子；同名檢查與「誰說的」保得住。只在 hook 點宣告裡有效 |
| 乙 現成 `$ref` | `{"$ref": ["../../../../lib/aos/apps/hook/loop_points.json", "hook_points.json"]}` | 什麼都不用加；但路徑只能相對或絕對，定義一搬就斷；合完同名後蓋前、不知道誰說的 |
| 丙 `$ref` 收 `$env` 給的路徑 | `{"$ref": [{"$env": "AOS_HOME", "$path": "/lib/…/loop_points.json"}, "hook_points.json"]}` | 改 aos-directive 與 N-45 一句，全系統的 `$ref` 都能這樣寫；合完同乙，來源丟了 |
| 丁 新指示詞 `$include`（原地展開） | 寫起來同甲 | 最像 C 的 #include、全系統能用；要改 aos-directive、N-45 加第三個指示詞而且是「貼進外層」的新語意；來源丟了 |
| 戊 角括號系統路徑 | `"$include": "<hook/loop_points.json>"` | 最像 C；跟 C-56、P-31「不把規則埋進字串」衝突 |

**建議**：甲。以後別的 JSON 也想要原地展開時，再把它升成丁，宣告檔一字不改。

## 第 2 題：block、condition、entry_keys 這種「今天有行為」的自由鍵，程式讀不讀

他第 2 則說這些「不是硬性影響，宣告我大概會怎樣，具體實作怎麼應用後續再說」；查實的結果是今天 `block`、`condition`、`entry_keys` 會改變 hook 的行為（[02](02-各鍵程式讀不讀.md)）。

| 選項 | 後果 |
|---|---|
| a 照舊讀：寫了照做，沒寫照預設（不能攔、不收 condition、沒有專用鍵） | 行為跟今天一樣，掛錯會當場擋（例：在不能攔的點上退 10 不算攔、在沒 condition 的點寫 condition＝`HooksBad`）；這幾個鍵「不必寫」，但寫了有作用 |
| b 不讀，全部只當說明 | 引擎不知道誰能攔、拿哪個欄位比 condition：要嘛每個點都能攔、condition 一律不收，要嘛改由發事件的程式在 `fire` 時自己說（每支發事件的程式都要改）；`on_clock` 的 `every_ms` 這種專用鍵擋不住寫錯位置 |
| c 讀，但只讀 `block` 與 `condition`；`entry_keys` 交給各家自己驗（agent 已經有 `CLOCK_KEYS` 一份） | 引擎的兩件事照舊；宣告少一個有行為的鍵 |

另外 `phase`、`subject`、`key` 今天沒人讀，但 hook 第 6 刀（gdb 讀宣告）原本要讀它們。選 b 的話第 6 刀只能照名字猜或照舊手寫。

**建議**：a。這幾個鍵仍然不是硬性（不寫也合格），符合「想放啥放啥」；只是寫了的會被用上。

## 第 3 題：引入是動態連結還是靜態連結

| 選項 | 後果 |
|---|---|
| a 動態：讀宣告的時候才去讀被引入的檔 | loop 那份改了（`install.py`），下次讀就是新的，不用重新編譯；搬到別台讀的是那台的版本；那台沒有這份檔或沒設 `AOS_HOME`＝讀不進來 |
| b 靜態：agent.py 編譯時把引入的點抄進定義夾 | 定義自己帶齊，搬到哪都一樣、不靠 `AOS_HOME`；loop 加了點或改了說法，要重新編譯才看得到，沒編譯就是舊的（跟 loop 實際發的對不上也不會報錯） |
| c 兩種都給：寫 `$include` 是動態；編譯可選擇抄進來 | 彈性最大；多一個選項要說明、要測 |

**建議**：a。今天 `{"provider": …}` 就是動態，行為不變；手寫定義也照這樣。

## 第 4 題：物件寫法裡哪些鍵不是點（以及陣列寫法放在檔裡時 description 放哪）

物件寫法 id 當鍵，`description`、`provider` 的名字也合 id 規則。

| 選項 | 後果 |
|---|---|
| a 值是物件的鍵才是點；`$` 開頭的鍵是讀者自己的（`$include`）；其餘是自由鍵（樣本用這個） | 檔頂層的 `description` 照 repo 慣例放第一行；不能有「值是物件」的檔層自由鍵 |
| b 保留字清單：`description`、`provider` 不能當 id，其餘都是點 | 規則一眼看懂；以後想加檔層的鍵要改清單 |
| c 物件寫法頂層只收點與 `$` 開頭的鍵，說明寫 `$description` | 最不會撞；跟 repo「JSON 第一個鍵 description」的慣例不同 |

陣列寫法放在一份檔裡時，檔頭那句 `description` 沒地方放：樣本用「第一項只有 `description`，不帶 `id` 的項不是點」湊（建議同 a 的精神：帶 `id` 的項才是點）。也可以規定**檔一律用物件寫法，陣列只在 `interfaces.json` 直接寫時用**。

**建議**：a；檔建議用物件寫法。

## 小處（本線照樣本的寫法代定，他不同意再改）

- 硬性兩鍵叫 `input`、`output`（他說的 input schema、output schema）；點的說明用 `description`（取代 `when`，他第 1 則說「id 配上 description」）。
- 欄位從環境變數取值的 `env` 寫在 `input` 那個欄位的 schema 裡（JSON Schema 會略過不認得的關鍵字）。
- 引擎自己加給 handler 的 `event`、`hook`、`stack` 不寫進每個點的 `input`。
