一棵 aos 樹實際可以從哪些切點拆開、直接用 aos-exec 接上 Linux，每個切點少了上層給的什麼，哪些位置拆不開（線 top-1121-kintercept 讀程式為主，標「實測」的在暫存樹試過）。

## 先講結論

- **切點＝有自己入口、能被 `aos-exec` 直接起的資料夾或檔**。從大到小有八種：根 daemon、子 daemon（含 llm kernel）、kernel 站、agent 的身體、fsm 的一格、單一工具、hook 處理程式、板子的核心列程式（鐘、清道夫）。
- **起的時候 aos-exec 自己補兩樣**：`AOS_WS`（沒給＝`.`）與 `AOS_STACK`（沒給＝`$AOS_WS/.stack/`，自動建，`cpp/aos-exec/docs/03-環境變數.md`）。所以每個切點都拿得到一個 stack；少的是**上層才給得出的東西**：表上那一列、`AOS_DAEMON`、`AOS_CLOCK`、`AOS_LLM_KERNEL`、`AOS_KERNEL`。
- **拆不開的不是程式，是掛接資料**：表上那一列、時鐘登記、子 agent 帳、「我是誰」，這些住在 daemon 那邊，切下來的那一塊帶不走。
- agent 定義夾本身**不是**切點：`agent-fsm` 的 `_entry` 是 `aos-agent ctl add`（把自己掛到某台 daemon），真正的切點是它的 `body.json`。

## 八個切點

| 切點 | 怎麼直接起 | 拆下來少了什麼 | 依據 |
|---|---|---|---|
| 根 daemon（`start-api/root/`、`templates/daemon-root/`） | `aos-exec root`（stack 預設 `./.stack`） | 什麼都不少：它就是頂。`.env` 自己給 `AOS_CLOCK`、`AOS_LLM_KERNEL`；同一個 stack 只能有一台（`DaemonExists`） | 實測（本線起樹） |
| 子 daemon（`start-api/llm/`、`kernel/llm-kernel/`、`daemon-kernel/`、`llm-team/`） | `aos-exec --stack X llm`，入口就是 `aos-daemon` | 上層表上的那一列（`auto_restart`、別人用名字找到它）；上層 `.env` 給的 `AOS_CLOCK`、`AOS_LLM_KERNEL`（`llm/.env` 只設 `AOS_HOME`）。它自己的 `AOS_DAEMON` 由自己的身體設成自己。`llm-team` 的下一層寫在 `kernel.json` 的 `{"$env": "AOS_STACK", "$path": "../llm-kernel"}`，拆到別處那條路就指空 | 讀程式；llm 是一台 daemon 是實測（起樹後兩個 aos-daemon 行程） |
| kernel 站當 proc（`start-api/perm/`、`kernel/procs-kernel/`） | `aos-exec --stack X perm`（`aos-loop loop.json`，每 300 ms 跑一輪站） | 下一站：沒寫 `next`、沒有 `AOS_DAEMON` 時連空輪都 `DaemonMissing`；寫了 `next` 就能單獨跑 | 實測（站程式單獨跑一輪） |
| agent 的身體（`agents/ann/body.json`；`eca-claude/` 夾本身，入口是 `aos-loop loop.json`） | `aos-exec --stack S --ws W agents/ann/body.json` | `AOS_LLM_KERNEL`（不給就在第一次叫腦時 `LlmKernelMissing`，知識庫 `aos/kernel.json`）；`AOS_CLOCK`（三個 on_clock hook 停用、各一行 warning）；表上那一列（所以要「認自己」的工具全部 `DaemonMissing`：self_*、goal、mailbox_*、clock_register add…；`todo`、檔案工具照通）；自動重起、份額、換身分（都是 daemon 起它時才套） | 實測：只給 `AOS_LLM_KERNEL`，回 `FAKE ANSWER to: hello standalone`；`self_tools` 報 `DaemonMissing` |
| fsm 的一格（`fsm.json`，入口 `aos-fsm`） | `AOS_STACK=S aos-fsm fsm.json`：一次只跑 `stage.txt` 記的那一格 | 同上一列，另外少了「一直叫它」的 aos-loop；每格的 `.py` 也能單獨 `python3` 跑，要的是 `AOS_STACK`、`AOS_CD` | 讀程式（`cpp/aos-fsm/README.md`） |
| 單一工具（`lib/tools/agent/*`、`lib/tools/base/*`） | `aos-exec --ws W --stack S <工具夾>`，JSON 從 stdin 進 | 不認自己的工具什麼都不少；認自己的少表上那一列（`DaemonMissing`），設了 `AOS_KERNEL` 的還要站回話 | 實測（`todo` 照通、`self_tools` 失敗） |
| hook 處理程式 | `aos-exec --stack <小格>/ <handler>`，事件 JSON 從 stdin 進（kernel 站與 agent 都這樣叫） | 叫它的那個事件；它自己不知道是誰叫的 | 讀程式（kernel 站 README「hooks」） |
| 板子的核心列（`aos-clock`、`aos-sweeper`） | 寫在根的 `daemon.json` 裡、不是資料夾，但命令本身能直接下：`aos-clock <鐘檔>` | daemon 定時叫它（`interval_ms`）；單獨下就只走一格 | 讀程式（`root/daemon.json`） |

## 拆不開、或拆了會少一塊的位置

1. **stack 不是切點**：stack 是資料（記憶），沒有入口；要「起一個 stack」其實是拿某個身體配 `--stack` 指它。整份 stack 帶著走、換台 daemon 跑，早上的搬家實測過（[aos-daemon-env-1121 追加](../aos-daemon-env-1121.md)）。
2. **表上的列、時鐘登記、子 agent 帳**：住在 daemon 的 stack 裡，切下來的那一塊帶不走，到新的上層要重新 `ctl add`、重新登記（同上）。
3. **`.env` 寫死上層變數的定義夾**：例如打開權限件後 ann 的 `.env` 寫 `${AOS_DAEMON}/procs/perm/requests`，沒有 `AOS_DAEMON` 就 `DotenvBad`，身體起不來（實測）。出廠那行是註解，拆得下來。
4. **`kernel_gate` 的站**：它是 agent stack 裡的一個 on_clock hook，站程式本身能單獨跑，但「留著等人表態」的那個人是那隻 agent，拆開就沒人表態。
5. **相對位置綁著兄弟的夾**：`llm-team` 指 `../llm-kernel`、覆蓋檔的 `$override` 指回定義（早上搬家的「差一點」第 1 條），兩塊一起搬沒事，只搬一塊會指空或指錯。
6. **定義夾 `_entry` 是「掛上去」的那種**（`agent-fsm`、`start-api/agents/ann`）：`aos-exec` 它＝`aos-agent ctl add`，要一台 daemon（`-d` 或 `AOS_DAEMON`）；這個夾的「接上 Linux」要改從 `body.json` 進。

## 註

- 這份只列事實，沒有判斷哪個切點「該」怎樣。
- 「侵入式／非侵入式」使用者說只是比喻、不實測，這裡沒碰。
