## 先講結論

- **沒有任何一條指令是「連上 daemon 的 socket 請它做事」**。aos 指令碰活著的東西只有三種手法：放一封信到某個信箱資料夾、直接改某個 stack 裡的檔、（唯一一處）送一個 Linux 訊號。daemon 與 agent 都是在自己的那一圈裡「之後才發現」。
- **指令行程本身是 daemon 管不到的 Linux 行程**：它是終端機那個 shell 的孩子，不在 daemon 的表上，沒有列、沒有 phase，daemon 的份額、重起、stuck 偵測都跟它無關。
- **人從 shell 打的指令，跟 agent 用工具做的事，是同一支程式**。`self_hook`、`self_ctl`、`subagent` 這些工具就是包一層 `aos-agent`。差別只在三件事：是誰的後代、帶什麼 `AOS_*` 環境變數、經不經 kernel。

## 七型

| 型 | 怎麼碰 | 哪些指令 | daemon 有沒有經手 | 對方什麼時候知道 |
|---|---|---|---|---|
| 一 寄信請 daemon 做 | 用 `aos-post send` 把一封信放進 daemon 的 `procs_requests/`（設了 `AOS_KERNEL` 就改放 kernel 站的信箱），再輪詢自己的回信箱等回信 | `aos-agent ctl add／rm／start／stop／sleep／wake`、`aos-daemon-ctl` 的同名動作、`ping` | 有，daemon（或 kernel）決定做不做 | daemon 下一圈（輪詢，通常一秒內）|
| 二 寫對方的 ctl 窗 | 直接把 `{"cmd","seq"}` 寫進對方 stack 的 `ctl.json`（暫存檔再改名），再看對方 `state_flux` 的 `ctl_seq` 追上沒 | `aos-agent ctl pause／resume`（寫 agent 的）、`aos-daemon-ctl shutdown`（寫 daemon 自己的）| pause／resume 沒有；shutdown 是 daemon 自己讀 | 對方的 loop 兩步之間讀到；一步跑到一半不打斷 |
| 三 往對方的 queue／信箱塞信 | 直接 `aos-post send` 到 agent stack 的 `queue/`、某個 `mailbox/`、使用者專區 | `aos-agent say／ask／chat`、`aos-mailbox send`、寄使用者專區 | 沒有 | 收的那方自己下一輪拿；沒在跑就一直排著 |
| 四 直接改對方 stack 裡的設定 | 讀檔、改、寫回（暫存檔再改名，沒有鎖）| `aos-agent hook add／rm／reset`（連旗標檔）、`tools`、`llm`、`system`、`history rm／set／summarize`、`goal`；`ctl rm` 最後自己刪整個 stack | 沒有 | 下一個事件、下一輪 |
| 五 送訊號 | 讀 daemon `state.json` 的 pid，核對開機編號與起始時間，用 pidfd 送 `SIGRTMIN+n` | `aos-daemon-ctl poke`；`shutdown` 寫完窗也按一下 | 有，但訊號不帶內容，只叫它「現在看一次檔」| 立刻（身體跑到一半則等身體跑完）|
| 六 就地起一棵行程樹 | 指令行程自己走進資料夾、設環境、起子行程 | `aos-exec root`（aos-exec 留在那個視窗當監工，aos-daemon 是它的孩子）、`aos-exec 某工具`、`aos-hook fire`（就地跑 hook 的處理程式，小格寫進 `--stack` 指的那個 stack）、`aos-sandbox`、`aos-asuser` | 沒有（`aos-exec root` 起出來的就是 daemon 本身）| 不適用 |
| 七 純讀 | 讀表檔 `procs_state.json`、讀 stack 裡的檔 | `ctl ls／state／who／where`、`listen`、`history ls`、`hook ls`、`aos-daemon-ctl ls`、`aos-mailbox peek`、aos-gdb 的 `a.look` | 沒有（例外見下）| 不知道 |

幾條指令是好幾型疊起來的：`ask`＝三＋七（塞一句再輪詢答案）；`ctl rm`＝一＋四；`ctl set-def`＝停、換、掛回三段；aos-gdb 的斷點＝四（掛一個 hook）＋二（處理程式觸發時寫 `pause`），而 aos-gdb 本身是一個常駐的 Python 行程，每個動作起一支 `aos-agent`。

「純讀」有兩處不純：設了 `AOS_KERNEL` 時，要讀表得先寄一封查詢信問「表在哪」（變成一＋七）；`aos-mailbox read` 讀了就把信拿走，等回信的指令會順手建回信箱、清十分鐘前的舊回信。

## 每一型共通的五件事實

1. **它是誰的孩子**：shell 指令行程的上一代是終端機的 shell。daemon 起的 proc 的上一代是 aos-daemon。Linux 層面上這是兩棵不相干的行程樹，連 `aos-exec root` 也是——板子本身是那個終端視窗的後代，關機後那個視窗的 `aos-exec` 才結束。
2. **它有沒有 stack，看環境變數**。人的 shell 只要 `source env.sh`，`AOS_*` 除了 `AOS_HOME` 全被清掉（`env.sh` 註明是 11-13 15:24 事故後加的：agent 的 shell 帶著 `AOS_STACK` 起了 root，root 繼承了它）。沒有 `AOS_STACK` 的指令行程就沒有自己的 stack：回信箱借 daemon ctl 信箱底下的 `reply/`，對 eca 說話的署名退成 Linux 登入名。帶著 `AOS_STACK` 的（agent 的工具、agent 開的 shell）回信箱在那隻自己 stack 的 `daemon_reply/`，署名會查表認回那隻的名字。
3. **身分是自報的**。信封的 `sender` 是寄件人自己填的 stack 路徑，沒人驗（知識庫 `aos/kernel.json`）。所以「這條指令是誰下的」等於「它帶了什麼環境變數」，跟它是不是從終端機打的無關。
4. **人的 shell 預設不經 kernel**。`aos-agent` 只在設了 `AOS_KERNEL` 時才把信寄給 kernel 站；`env.sh` 把它清掉了，所以人不特別 `export` 就是直寄 daemon。`aos-daemon-ctl` 則是永遠直寄。二、三、四、五、六型本來就不寄給任何人，kernel 根本看不到。
5. **全部同一個 Linux 帳號**，所以以上每一種寫法都寫得進去，沒有東西擋。子帳號（`limits.user: "sub:N"`）接上之後才會變，見 [03 第 6 條](03-邊緣狀況.md)。

## 「往另一個程序的記憶體內 stack 塞指令」對到哪些動作

| 他的話 | 實際最接近的動作 | 貼不貼 |
|---|---|---|
| 塞一筆「待辦」進去，等對方輪到時做 | 三型：`say` 把一則訊息放進 agent 的 `queue/` | 很貼。但塞的是一句話，腦可以不照做 |
| 改對方正在用的控制位 | 二型：寫 `ctl.json` 的 `pause`／`resume`／`stop` | 很貼，而且對方不能拒絕，只是要等它兩步之間讀到 |
| 在對方的指令中間插新指令 | 四型：`hook add`、`tools add`、`history set` | 貼。這就是他 11-19 說的「在他的指令中央插入新指令」 |
| 請管理者代勞 | 一型：寄信給 daemon 或 kernel | 不算「塞進別人記憶體」：是放進管理者的收件箱，可以被拒 |
| 直接讓對方的行程停住或改它的行程記憶體（gdb／ptrace 那種）| 沒有這種指令 | 不貼。aos 不碰別人的 Linux 行程，唯一的訊號是給 daemon 的 poke |
