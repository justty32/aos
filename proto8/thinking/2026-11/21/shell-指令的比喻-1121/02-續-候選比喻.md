## 戊 服務處理器（伺服器主機板上的 BMC）

**一句話**：伺服器主機板上另有一顆獨立的小處理器，專門給管理員用：主機關著它也活著，能開關主機電源、看狀態、改設定，走的是跟主機作業系統無關的另一條線。shell 就是那顆小處理器的操作介面。

| 實際的東西 | 在這個比喻裡 |
|---|---|
| shell | 服務處理器的操作介面 |
| 指令行程 | 服務處理器執行的一道管理命令 |
| daemon | 主機本體 |
| kernel | 主機的作業系統；服務處理器繞過它 |
| stack | 主機的記憶體與設定；服務處理器直接碰得到 |
| 被動到的 agent | 主機上跑的工作，被帶外管理介入 |

```
 [服務處理器＝shell 這一側] ──帶外線──▶ [主機＝daemon＋kernel＋各 proc]
        （主機關著它也在）
```

**貼的地方**：這是唯一同時說得通「板子沒開也能動」和「`aos-exec root` 開機」的比喻。`aos-daemon-ctl`「永遠直寄、繞過 kernel」正是帶外管理的定義；既有附錄寫的「判官睡著是設計系統的人要管的風險，手動 `aos-daemon-ctl wake`」就是這個用法。遠端下指令也順：服務處理器天生是給遠端管理用的。它也貼他說的「另一個 cpu」——真的是另一顆。

**不貼的地方**：服務處理器是常駐的，shell 指令是來了就走。它是管理員專用，agent 不該有；可是 agent 的工具用同一支程式。每天的 `say`、`chat` 是在跟 agent 講話，不是管理主機，放進「帶外管理」太重。

**採用會暗示什麼**：有一條不經 kernel 的管理通道是正當的、而且應該一直留著；這條通道屬於「顧板子的人」，值得有自己的身分和紀錄；日常對話（三型）要另外歸類。

## 己 使用者是樹外的一顆 PU，shell 指令是他的工具呼叫

**一句話**：不把 shell 當特別的東西。使用者本人就是一個會「算」的執行單位（像畫家例子裡的畫家），他有自己的 stack（知識庫把使用者專區 `~/.aos/user/` 寫成「使用者自己的 stack」）；shell 是他的身體，一條指令是他的一次工具呼叫——跟 agent 的身體叫工具是同一種事，只是這顆 PU 不在任何 daemon 的表上。

| 實際的東西 | 在這個比喻裡 |
|---|---|
| shell | 使用者這顆 PU 的身體（相當於 agent 的 agent-fsm 或 eca）|
| 指令行程 | 一次工具呼叫 |
| daemon | 他去拜託的那塊板子（他不住在上面）|
| kernel | 他如果願意，可以照規矩先寄給它；現在預設不經過 |
| stack | 別人的記憶體；他的權限大到直接改得到 |
| 被動到的 agent | 另一顆 PU；兩顆之間用信講話 |

```
 [使用者＝樹外的 PU] ─工具呼叫（指令行程）─┐
                                            ├─▶ 信箱、窗、stack 裡的檔
 [agent＝板上的 PU]  ─工具呼叫（同一支程式）┘
```

**貼的地方**：這是唯一能把「人從 shell 打 `aos-agent hook add`」和「agent 自己叫 `self_hook`」講成同一種東西的比喻，而事實上它們就是同一支程式。「帶什麼環境變數就是誰」直接成立：環境變數就是這次工具呼叫的身分。agent 開 shell 再下 aos 指令（裡面打外面）也不用另外解釋。它也是他原話「另一個 cpu」的另一種讀法：那顆 cpu 就是人自己，指令行程是他的手腳。

**不貼的地方**：它沒說出「強行」那個味道——人的 shell 實際上比任何 agent 都有權（不經 kernel、沒有份額、不會被 daemon 收掉）。使用者專區今天只是一個收信的地方，shell 並不會自動帶 `AOS_STACK=~/.aos/user`。`aos-exec root`（開板子）不是哪顆 PU 的工具呼叫能解釋的。這個候選比較像「換個分類」而不是硬體比喻，跟板子那套畫面接得沒那麼直接。

**採用會暗示什麼**：人與 agent 對稱——人的指令也可以帶身分、也可以照規矩經 kernel、也可能被拒；「shell」本身不特別，特別的是「沒上表」；知識庫規則 2「用工具，不用 shell 把戲」的界線會變成「有沒有照自己的身分走」而不是「是不是 shell」。

## 庚 不用一個詞：依型分開講

**一句話**：shell 不是一個東西，是板子外面的那張工作桌；桌上同時有電源開關、探針、接到信箱的線、門鈴按鈕。每一型指令各用既有比喻裡已經有的那個零件來講。

| 型 | 比喻 | 既有文件裡有沒有 |
|---|---|---|
| 六型 `aos-exec root` | 上電、bootloader | 有（板子附錄）|
| 一型 寄信給 daemon 或 kernel | 板外送進 mailbox FIFO 的請求（丁）| 信箱已有 |
| 三型 塞 queue、寄信箱 | 同上 | 信箱已有 |
| 二型 寫 ctl 窗 | 寫記憶體映射暫存器 | 窗已有 |
| 五型 poke | 拉中斷線（門鈴）| 有 |
| 四型 直接改 stack 的檔 | 探針或另一個主控直接寫 RAM（甲、乙）| 沒有，這一型是新的 |
| 七型 純讀 | UART／JTAG 讀出 | 有（daemon-board 對照表）|

```
            ┌──────── 工作桌＝shell ────────┐
 [電源鍵]  [信箱投入口]  [暫存器]  [門鈴]  [探針]  [讀出線]
   六型      一、三型      二型     五型    四型     七型
            └──────────▶ 板子＝daemon ◀─────┘
```

**貼的地方**：每一型都貼，因為是逐型挑的。跟既有體系完全不打架：附錄已經是「`aos-daemon-ctl`＝直接敲、`aos-agent`＝經作業系統、aos-exec＝bootloader」這樣逐條對的。新東西只有四型一格要補。

**不貼的地方**：它沒有回答他問的那一句「在 shell 內執行指令可以比喻為啥」——答案變成「看是哪一條指令」。「工作桌」只是一個容器，不是真的比喻。複合指令（`ask`、`ctl rm`、aos-gdb 的斷點）要用兩三個零件才講得完。

**採用會暗示什麼**：指令的分類（寄信／寫窗／直寫／就地起）會比「是不是從 shell 來」更重要；四型會被單獨拎出來看，因為只有它在既有比喻裡沒有位置。

## 七個候選一張表

| 候選 | shell 指令是 | 講得最好的 | 講不通的 |
|---|---|---|---|
| 甲 另一個匯流排主控 | 不經板上處理器、直接寫 RAM 的外來主控 | 二、三、四型；「強行」| 一型、開機；「cpu」撞名 |
| 乙 除錯探針 | 探針的一次操作 | 四、七型；aos-gdb；凍住時也能改 | 日常的 `say`；多人同時；agent 自己下指令 |
| 丙 前面板 | 按一下面板的鍵 | 開機、關機、看表 | 直寫型；agent 自己下指令 |
| 丁 板外送來的請求 | 板外設備的一次傳輸 | 一、三、五型；指令死掉；另一台機器 | 四型；開機 |
| 戊 服務處理器 | 帶外管理命令 | 板子沒開、開機、繞過 kernel、遠端 | 日常對話；來了就走；agent 自己下指令 |
| 己 使用者是樹外的 PU | 使用者的一次工具呼叫 | 人與 agent 同一支程式；身分看環境；裡面打外面 | 「強行」；開機；跟板子畫面較遠 |
| 庚 依型分開講 | 看哪一型 | 全部，逐型 | 沒有單一答案；複合指令 |
