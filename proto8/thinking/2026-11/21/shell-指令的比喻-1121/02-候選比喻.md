「在 shell 裡下 aos 指令」的候選比喻甲到丁：另一個匯流排主控、除錯探針、前面板、板外送來的請求；每個用同一組小標，只攤開、不選。

## 甲 另一個匯流排主控（他原話的直讀版）

**一句話**：板子（daemon）上本來只有一顆處理器在管事；shell 指令是臨時接上同一條匯流排的另一個主控，不經板上那顆處理器，直接讀寫板上的 RAM（各個 stack）。真實世界的對應物是多主控匯流排、DMA、多處理器之間互相寫共享記憶體。

| 實際的東西 | 在這個比喻裡 |
|---|---|
| shell | 那個外來主控平常待的地方（板外）|
| 指令行程 | 外來主控上線的那一次：搶到匯流排、做幾筆讀寫、放掉 |
| daemon | 板上原本的處理器，對這幾筆讀寫不知情 |
| kernel | 板上處理器跑的管理程式；外來主控繞過它 |
| stack | 被直接寫的 RAM |
| 被動到的 agent | RAM 被改了的那支程式，下次讀到才發現 |

```
 [外來主控＝指令行程] ──┐
                        ├─ 匯流排 ─→ [RAM＝各個 stack]
 [板上處理器＝daemon] ──┘
```

**貼的地方**：二、三、四型幾乎字面成立（寫 ctl 窗、塞 queue、改 hooks 清單，daemon 全程沒經手）。「強行」也貼：沒有東西擋。agent 自己的工具做同樣的事也說得通——板上的周邊本來就能當主控。

**不貼的地方**：一型是寄信請 daemon 做，那是「拜託板上處理器」，不是自己寫。真的多主控匯流排有仲裁，aos 沒有（四型沒有鎖）。「cpu」這個字在既有文件已有兩個用法，再用會撞名。它也解釋不了 `aos-exec root`：板子還沒開，哪來匯流排。

**採用會暗示什麼**：shell 指令跟 daemon 平起平坐，不是它的下屬；「同時寫怎麼辦」會變成比喻自己逼出來的問題；kernel 管不到它是正常的，不是漏洞。

## 乙 除錯探針（JTAG／SWD）

**一句話**：shell 是接在探針另一頭的那台電腦；一條指令是探針的一次操作——讀記憶體、寫記憶體、叫核心停住、放行、燒錄。板子上的程式不知道探針存在。

| 實際的東西 | 在這個比喻裡 |
|---|---|
| shell | 探針另一頭的主機 |
| 指令行程 | 探針的一次操作 |
| daemon | 被接上探針的板子；探針不需要它配合 |
| kernel | 板上跑的作業系統；探針在它底下、看不到它的規矩 |
| stack | 被探針讀寫的 RAM |
| 被動到的 agent | 被除錯的那支程式 |

```
 [主機＝shell] ══探針線══▶ [板子＝daemon｜RAM＝stack｜程式＝agent]
```

**貼的地方**：既有對照表已經把 `aos-daemon-ctl ls`、翻 stack 對到 UART／JTAG。aos-gdb 自然落在這裡。「凍住時也能改」貼：核心停住時探針照樣讀寫，就像整棵樹睡著時 shell 照樣改得到 stack。「不留痕跡」「有實體接觸就是全權」也貼。常駐的指令（aos-gdb、`chat`、`listen --follow`）像探針一直插著。

**不貼的地方**：探針通常一次一支，aos 可以好幾個 shell 一起下。探針要板子有電才能用，aos 板子關著照樣改得到（stack 是檔案）。探針是開發時的東西，正式出貨會拔掉；可是 `say`、`ctl add` 是每天正常使用的入口。agent 自己叫 `self_hook` 變成「程式自己拿探針戳自己」，很怪。

**採用會暗示什麼**：shell 指令是「開發與除錯通道」，跟 agent 之間的正式通道（信）是兩回事；叫它停下的人要負責放行（探針線拔了，核心就一直停著）；不經 kernel 是天經地義。

## 丙 前面板／操作員主控台

**一句話**：板子的機殼上有一排開關和按鍵，shell 就是那塊面板；每條指令是按一下某顆鍵。老式大型主機的面板可以撥開關放資料進記憶體、看某個位址、按開機鍵。

| 實際的東西 | 在這個比喻裡 |
|---|---|
| shell | 面板 |
| 指令行程 | 按一下鍵 |
| daemon | 機器本體，面板的線直接接到它 |
| kernel | 機器上跑的作業系統；面板的鍵有的經過它、有的不經過 |
| stack | 面板的「放入／查看」鍵碰得到的記憶體 |
| 被動到的 agent | 機器上被操作員介入的那個工作 |

```
 ┌─ 面板＝shell ─────────────────────┐
 │ [開機] [看表] [停] [放入] [查看] │──▶ [機器本體＝daemon]
 └───────────────────────────────────┘
```

**貼的地方**：`aos-exec root` 就是開機鍵、`shutdown` 是關機鍵、`ctl ls` 是指示燈，這幾顆最順。「使用者顧板子，板子顧底下」跟「操作員站在面板前」是同一個畫面。面板是機器的正式零件，不是除錯時才有。

**不貼的地方**：面板的鍵是固定的幾顆，aos 的直寫型（四型）可以改任何檔，更像拆開機殼。面板只有一塊、只有操作員能按；agent 也能下同樣的指令，等於機器裡的程式自己伸手出來按面板。面板不解釋「放一封信等回音」。

**採用會暗示什麼**：shell 能做的事應該是一張數得出來的清單，每一樣機器都認得；直接改 stack 的那幾型就不算面板，而是另一種東西（要另外取名）；面板屬於人，agent 不該碰。

## 丁 板外送來的請求（周邊或另一塊板）

**一句話**：shell 指令行程是板子外面的另一台設備，它不碰板子內部，只把東西放進板子對外開的入口——信箱（mailbox FIFO）、窗（記憶體映射暫存器）、門鈴（中斷線）——板子照自己的節奏處理。

| 實際的東西 | 在這個比喻裡 |
|---|---|
| shell | 板外的另一台設備（或另一塊板）|
| 指令行程 | 那台設備的一次傳輸 |
| daemon | 收東西的板子，下一圈才處理 |
| kernel | 板子對外的第一道收件口，可以拒收 |
| stack | 板子的 RAM；其中 `queue/`、`ctl.json` 是特意開給外面寫的那幾格 |
| 被動到的 agent | 從自己收件格裡拿到東西的那支程式 |

```
 [板外設備＝指令行程] ─信─▶ [信箱] ─┐
                      ─寫─▶ [窗]   ─┼▶ 板子下一圈自己來拿
                      ─鈴─▶ [門鈴] ─┘
```

**貼的地方**：一、三、五型完全貼，而且用的全是既有比喻裡已經有的零件（信箱、窗、門鈴）。「放下就走、對方之後才發現」「對方可以拒絕」「指令死了，已經放進去的照樣處理」都自然。另一台機器、另一棵樹下指令也接得上（跨樹的信本來就有規則）。agent 寄信跟人寄信是同一回事，不必分。

**不貼的地方**：四型（改 hooks、改 history、刪 stack）不是「放進開好的入口」，是伸進去改，這個比喻只能說它越界。它把 shell 講得太客氣：實際上沒有任何東西逼它只走入口。`aos-exec root` 也不在裡面。

**採用會暗示什麼**：shell 沒有特權，跟任何寄信的人一樣；直接改別人 stack 的指令會被看成例外，要嘛另外解釋、要嘛顯得不正當；「身分」會變重要（信封上寫誰）。
