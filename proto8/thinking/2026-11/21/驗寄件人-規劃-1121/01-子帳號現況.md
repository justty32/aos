# 甲、子帳號那一哩做到哪

← [README](README.md)｜上一份：[00](00-使用者原話.md)｜下一份：[02-信從哪裡進來](02-信從哪裡進來.md)

**子帳號**（subuid）像公司發給你的一疊「分身員工證」：`/etc/subuid` 寫著 lorkhan 名下有 100000～165535 這一段號碼，不用 root 就能讓自己的程式換成其中一張證跑。11-18 的紀錄寫「daemon 還不認 `sub:N`」，那是 11-18 的程式；**11-19 線 subuid-1119 已經接上**（commit `368719e7a`，同日 `72bc0c67c` 修 `procs` 順序），以下以今天的程式（HEAD `42a50a5f9`）為準。

## 一、`limits.user: "sub:N"` 寫了之後，daemon 做什麼

照 `cpp/aos-daemon/src/child/subuid.cpp`、`limits.cpp`、`child.cpp` 與 [daemon docs/09「換成 subuid」](../../../../cpp/aos-daemon/docs/09-份額.md)：

1. **fork 之前**：查 `/etc/subuid`、`/etc/subgid` 這個帳號的第一段、PATH 上的 `newuidmap`／`newgidmap`，缺就那一列 `stopped`＋`LimitBad`。備好換身分後的環境：只留 `PATH`、`LANG` 等幾個與 `AOS_*`，`HOME=/nonexistent`，有工作區就帶 git 的 `safe.directory`；金鑰類變數不傳。
2. **替小格開門**：proc 的 stack（daemon 建的小格 `procs/<名>`）改 `0700`，ACL 給那個真 uid `rwx`，預設 ACL 給它和 daemon 自己的 uid（**ACL** 像門上另貼的「這幾個人也能進」名單）。
3. **子行程**：進 cgroup、setrlimit 之後 `unshare(CLONE_NEWUSER)`（開一個自己的 **user namespace**，像一間自己的辦公室，裡面的工號跟外面不同），經 socketpair 叫 daemon 跑 `newuidmap PID 0 1000 1 N <真 uid> 1`；再設 `procs`、`setgroups({})`、`setresgid(群組)`、`setresuid(N)`，關掉 3 以上的 fd。
4. **換完檢查走不走得到**：小格要 rwx、daemon 的 cwd 與工作區要 x；走不進去就點名第一層卡住的夾、退 1。
5. 號碼：`sub:5` 在外面是 100004；群組一台 daemon 一個（daemon.json `group`，預設 60001＝外面 160000）。

**kernel 站**照 `users` 表（proc 名字樣式 → `sub:N`）替要起的 proc 填身分、丟掉寄件人自帶的 `user`（`py/tools/aos/kernel/limits_rule.py`）。注意這張表**對的是要起的 proc 的名字，不是寄件人**。

## 二、斷在哪（照順序，前一個不過就看不到後一個）

| # | 斷點 | 現況 |
|---|---|---|
| 1 | **路走不到** | 家機家目錄是 `drwx------`（700）：換了身分的 proc 連 `/home/lorkhan` 都穿不過，daemon 照設計報 `cannot reach /home/lorkhan` 讓那支起不來（下面實測）。公司 WSL 11-19 使用者已把家目錄改 751，那台過得去 |
| 2 | **寄不出信** | 換了身分的 agent 寫不進別人的信箱：daemon 的 `procs_requests`、kernel 站、llm kernel 的 `requests/`、別隻 agent 的 `<stack>/mailbox/` 都是使用者 uid 的一般夾（755）。K16 定成用 `aos-share drop` 開投遞門，**還沒有任何一處開**；範本也沒有 |
| 3 | **收信方收不下它的信** | 本線實測發現：信是**一個夾**，收信方 `take`（`new/`→`cur/` 改名）時，Linux 要求對**那封信的夾本身**有寫權限（改它的 `..`）。子帳號寄的信夾預設 755、歸子帳號，收信方改名被拒。要信箱的 `new/` 帶預設 ACL 把收信方加進去（`aos-share drop` 的樣板有 `d:u:ME:rwX`，剛好夠；小格的預設 ACL 也有 daemon 的 uid） |
| 4 | 沒有人看擁有者 | 全 repo 沒有一處拿信的擁有者跟 `sender` 比（[02](02-信從哪裡進來.md)）；kernel-limits-plan K9 已裁「要」，沒施工 |
| 5 | 其他沒做的 | 子 daemon 沿用父的 `group`（K18 後半）、信上的 `groups`、K10 收緊活樹權限、清道夫讀不到子帳號行程的 environ、`rm` 時用同一個子帳號清垃圾；eca 本體照 K7 留使用者 uid |

**範本**：沒有任何範本寫 `users`、`limits.user`、`by_sender`、`budget.senders`。所以今天整棵樹不會有一支 proc 換身分，**demo 就是全同帳號**。

## 四、實測（家機，`git archive HEAD` 的乾淨複本 `~/.aos/scratch/top-1121-ownerplan/`）

| # | 做什麼 | 結果 |
|---|---|---|
| T1 | 複本跑 aos-daemon 的 `test_subuid`（9 條；fixture 放 `exp/tests/`，先 unset 全部 `AOS_*`） | 5 條過；4 條真機條 skip，原文 `LimitBad user sub:5: cannot reach /home/lorkhan: Permission denied`。這行是**換完身分之後**才印的，代表開 ns、`newuidmap`、`setresuid` 在家機都過了，只差路 |
| T2 | 不經 daemon：先 `cd` 進暫存夾，`unshare --map-users=0:1000:1 --map-users=5:100004:1 … --setuid 5` 照 aos-post 的做法寄一封（`mkdir tmp/L1`、寫 `letter.json`、改名進 `new/`） | 外面看信夾與 `letter.json` 都是 **`100004:160000`**；信封自報 `"sender": "/fake/eca_main"`，擁有者照實是子帳號 |
| T3 | 同上，ns 裡 `stat` | 自己的信是 `5`、使用者的檔是 **`0`**、另一個子帳號（100005）寫的夾是 **`65534`** |
| T4 | 使用者把 T2 的信 `mv` 進 `cur/`、或搬到別的信箱 | **Permission denied**（斷點 3）。改在帶預設 ACL 的信箱再寄一次，使用者 `take` 就過 |
| T5 | 使用者（同 uid）在帶預設 ACL 的信箱：原地覆寫子帳號寄的 `letter.json`；`cp -r` 一份；在信夾裡改名換掉 `letter.json` | 原地覆寫後擁有者**仍是 100004**、內容已換；複製的那份擁有者變 1000；換掉的 `letter.json` 擁有者變 1000、信夾仍是 100004 |

T2 能跑是因為 cwd 先進了夾（相對路徑不檢查祖先）；daemon 起的 proc 不靠這招，會被第 1 個斷點擋住。實測的信夾歸子帳號、使用者刪不掉，留在暫存夾 `exp/owner/`。公司 WSL 的真機換身分（`/proc` 的 Uid 是 100004、寫的檔 `100004:160000`、使用者改得動）11-19 已驗（[subuid-1119](../../19/subuid-1119.md)），本線沒重做。
