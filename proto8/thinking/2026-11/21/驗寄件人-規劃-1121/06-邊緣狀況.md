# 乙 5、邊緣狀況

← [README](README.md)｜上一份：[05](05-擋不住的.md)｜下一份：[07-切刀](07-切刀.md)

標「實測」的見 [01 第四節](01-子帳號現況.md)（T1～T5）與本份 T6；其他是讀程式或推的。

## 一、搬家與兩台機器（他很在意可遷移）

1. **搬家那一刻還沒收的信**：`cp -r`、`rsync` 不帶 `-o`、`git clone` 到新地方，檔的擁有者都變成**搬的人**（實測 T5 複製那份變 1000）。新地方的 kernel 看到的全是樹主 uid ＝「同帳號、檢查不啟用」，不會誤擋；但這批信的寄件證據就沒了。用 `tar` 保留數字擁有者搬，則變成「新機器上某個號碼」——若新機器的子帳號段不同，號碼對到別人或沒人。我替使用者定：**不帶擁有者搬是正常情形**，檢查照「樹主 uid＝不啟用」處理，不寫任何遷移。
2. **號碼段不同**：對照表只存 `sub:N`（[03](03-對照表與耦合.md)），真號在新那台由 `/etc/subuid` 現算，所以設定照用。新那台段的個數比 N 小＝daemon 起不了那支（`exceeds this user's subuid range`），驗的那邊也推不出身分，兩邊一致。
3. **使用者本人的 uid 不同**（家機 1000；別台可能 1001）：檢查用「樹主＝我現在的 uid」，不寫死 1000，就沒事。
4. **沒有 ACL 的檔案系統**（WSL 的 `/mnt/c`、某些網路磁碟）：擁有者是假的（全部顯示同一人），daemon 設小格 ACL 那步就會失敗（`LimitBad cannot set the ACL`），所以不會有子帳號的信落在那裡。

## 二、git 管理的 stack

5. git 不存擁有者：`checkout`、`pull` 出來的檔歸執行 git 的人。stack 用 git 管時，從 git 拿回來的信全是樹主 uid＝檢查不啟用。stack 的 `.gitignore` 若沒排除 `mailbox/`、`queue/`，子帳號寄進來的信被使用者 `git add` 時，git 也只存內容。
6. 子帳號 agent 在使用者的 repo 裡 commit：daemon 已帶 `safe.directory`（11-13 X27）；`.git/objects` 下會冒出歸子帳號的夾，使用者之後 `git gc` 可能刪不掉（要預設 ACL，kernel-limits-plan 08 G8 已記）。

## 三、信被搬動、複製

7. **收信方收不下**（實測 T4）：信是夾，`take` 要對信夾本身有寫權限。沒有預設 ACL 的信箱收不下子帳號的信，這是「寄得進、收不下」的新狀況：信卡在 `new/`、收信方 `take` 報錯跳過（aos-post 11-19 起會列進 `skipped`、daemon 記 `mailbox_warning`）。
8. **搬到別的信箱**：同一個檔案系統內 `mv` 不改擁有者——但對夾來說要有那封信夾的寫權限（T4 使用者搬不動）。有權限的人把 A 寄給 X 的信搬去給 Y，Y 看到的擁有者仍是 A：**擁有者只證明「誰寫的」，不證明「寫給誰」**。跨檔案系統的 `mv` 等於複製，擁有者變成搬的人。
9. **複製**：擁有者變成複製的人（T5）；`cp -a` 由使用者做也拿不回原擁有者（不是 root 不能 chown）。
10. **信裡的附檔**：`aos-post send` 的 `files` 由寄件人複製進信夾，擁有者跟信夾一樣；之後被換掉的附檔擁有者會變，但收信方多半只看 `letter.json`。要不要也看附檔，列為可晚點再答。

## 四、回信、kernel 代寄、子 agent

11. **回信**：回信是回的人在 `reply_to` 那個信箱新寄一封，擁有者是回的人。agent 的回信箱在它自己的小格裡，小格預設 ACL 有 daemon 的 uid，所以**樹主 uid 的 kernel 回得進子帳號 agent 的回信箱**；別的子帳號回不進（要 `aos-share drop`）。
12. **`reply_to` 不限地方**：llm kernel、daemon 都照信上的 `reply_to` 寫回信，用的是**收信方自己的權限**。子帳號 agent 寫一個 `reply_to` 指到它自己進不去、但 kernel 寫得進的夾，就能借 kernel 的手在那裡放一封信（擁有者是 kernel）。這是今天就有的，換身分後反而更顯眼；擁有者驗證不管這個方向。
13. **kernel 代寄**：轉出去的信擁有者是 kernel（02）。下一站只認得 kernel；要帶原寄件人得加 key（04 第四節）。
14. **子 agent**：`subagent` 經 kernel／daemon 起，身分由 kernel 站 `users` 表照**子 agent 的名字**給。父 agent 取名字，所以父 agent 選得到子 agent 的號碼（05 第 6 條）。子 agent 的 `notify_box` 指父的信箱：子帳號之間寫不進彼此的信箱，父要先開投遞門，子才回報得了。
15. **daemon 自己寄的信**（ctl 回信、`mailbox_warning` 之類）：擁有者是樹主 uid＝檢查不啟用，跟今天一樣。

## 五、沙箱、aos-share、有序投遞

16. **沙箱裡寄信**：`aos-sandbox` 沒設 `user` 時跟呼叫方同 uid（bwrap 布景不改擁有者）；設 `user: "sub:N"` 時前面接 `aos-asuser`，跟 daemon 換的是同一套號碼，擁有者照樣對得上。bwrap 自己的 `--uid` 只改布景裡看到的號碼，外面的擁有者仍是真 uid。
17. **`aos-share` 開過門的夾**：`team`（2770）會把群組蓋成夾的群組，但擁有者不變——認人靠擁有者、不靠群組（kernel-limits-plan 08 已記）。`drop`（1730）的預設 ACL 只給收信方，剛好讓 T4 那種收不下的情況不發生。
18. **有序投遞撞 sticky**（實測 T6）：queue 用 `aos-post send --ordered`，要改寫信箱根的 `order.json`（寫暫存檔再改名蓋過）。信箱根設成 sticky（1730）時，第二個 uid 改名蓋不過第一個 uid 建的 `order.json`（`Operation not permitted`）。所以 **queue 若要給好幾個 uid 投，不能直接套 `drop` 樣板**；收信方之前就得想好 queue 用什麼門。
19. **收完刪不掉**：`done` 不留時是改名回 `tmp/` 再刪，刪夾裡的 `letter.json` 要對信夾有寫權限；沒有預設 ACL 時收信方刪不掉子帳號的信夾（跟 T4 同一個原因）。本線的暫存夾 `exp/owner/` 裡就留著幾個使用者刪不掉的信夾。

## 六、時間差

20. **檢查與使用之間被換**：驗完擁有者、讀內容之前，有寫權限的人換掉 `letter.json`。信已在收信方的 `cur/` 裡（只有收信方與 ACL 點名的人進得去），所以實際上只剩樹主 uid 這一群做得到（05 第 1 條同一個洞）。守規矩的碰不到。
