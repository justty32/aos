## 共同的落地方式

**全部寄信都經 `aos-post`**（C++ 庫或命令列；Python 沒有一處自己寫信檔）：寄件人自己 `mkdir tmp/<名>`、寫 `letter.json`、`rename` 進 `new/`（`cpp/aos-post/src/send/send.cpp`）。改名不換擁有者，所以**信夾與 `letter.json` 的擁有者＝實際寄出那支行程的 uid**，收信方 `take`（`new/`→`cur/`）之後也不變。`aos-post` 沒有任何 chmod、chown。

信封的 `sender` 是自報的：`aos::identity()`＝`$AOS_WS`＞`$AOS_STACK`＞`$AOS_CF`＞cwd 的絕對路徑；aos-llm 用 `stack_identity()`（`$AOS_STACK` 優先）；aos-mailbox、`user_send` 會清掉 `AOS_WS`、設 `AOS_STACK`。命令列沒有 `--sender`，但改環境變數就改得掉（11-18 E1）。

**另有兩個自報的名字**：信 body 的 `from`（aos-mailbox 的信、peek 顯示的「from」）；`aos-agent say` 寄給 eca 時 body 的 `name`（`--from` 任寫＞`$AOS_STACK` 在表上是哪隻＞登入名，`py/aos/apps/agent/sender.py`）。擁有者只能對信封，對不了這兩個。

## 逐處

| 收信處 | 誰收、怎麼讀 | `sender` 拿來做什麼 | 擁有者＝寄件人成立嗎 |
|---|---|---|---|
| **agent 的 queue**（`<stack>/queue/`） | agent 的身體；`aos-agent say`／`chat` 經 `aos_ws.put` → `aos-post send --ordered` | 沒用到；eca 的訊息署名用 body `name` | 成立（寄的那支建的）。但 `--ordered` 要改寫信箱根的 `order.json`：若信箱照投遞箱設 sticky（1730），**第二個 uid 改名蓋不過第一個 uid 的 `order.json`**（實測 T6：`Operation not permitted`），有序投遞與多 uid 投遞箱互撞 |
| **agent 的 mailbox**（`<stack>/mailbox/`） | `aos-mailbox`／`mailbox_*` 工具，經 aos-post 命令列 | 只顯示（`sender`、body `from`） | 成立 |
| **daemon 的 `procs_requests`** | aos-daemon 信箱模式（`src/daemon/mailbox.cpp`：take → see → 照 body 加減 proc） | **完全不看**；誰寫得進這個夾誰就能加、停、刪 proc，回信寄到信上的 `reply_to` | 成立；但今天沒有東西要它 |
| **kernel 站**（`py/tools/aos/kernel/`） | `aos-post see` 拿 `letter["sender"]`（`letters.py`） | `limits.by_sender[sender]`（只有這裡真的分人）；hook 事件帶 `sender`（kernel_gate 只顯示、記帳）；記進 `forwarded.json`。**`allowed` 與 `users` 對的是要起的 proc 名字，不是寄件人** | 第一站成立。轉寄用 `aos-post send` 重寄一封，**下一站看到的寄件人與擁有者都是 kernel 站自己**，原寄件人只留在站內紀錄 |

| **使用者專區**（`~/.aos/user/mailbox/`） | `aos-user`（程式只在活樹 `~/aos-home/ws/tools/aos-user/`，**不在 repo**，本線沒開） | 每個寄件人每小時 10 封（key 是 `sender`，沒有再看 body `from`）；`verify` 驗回信：寄件人是專區＋跟專區留底逐欄一樣＋專區 log 有同一筆 | 成立。專區寫回 agent 信箱的回信擁有者＝跑 `aos-user` 的人；但今天人和 agent 同 uid，擁有者分不出 |

## 讀下來的幾件事

1. **第一站全部成立**：只要寄件人用 aos-post 寄、沒人事後動手，信夾擁有者就是真寄件人。這是「只防走規矩的存取」剛好夠用的形狀。
2. **今天真正「照寄件人分人」的只有三處**：kernel 站 `by_sender`、llm kernel `budget.senders`／slots、使用者專區的每小時上限與 `verify`。其餘地方的 `sender` 只是顯示或記帳。**範本裡三處都沒開。**
3. **daemon 根本不看寄件人**：保護它的是「誰寫得進 `procs_requests`」——這本來就是 Linux 權限，不是擁有者驗證。子帳號 agent 寫不進就碰不到 daemon（01 斷點 2 的另一面）。
4. **轉寄會換人**：每一站只認得上一站（kernel-limits-plan 05 丙案已提）。要讓下一站知道原寄件人，得在信上多一個 key（C-48「靠加 key 擴充」），而那個 key 又是上一站自報的——下一站只能選擇相信上一站。
5. **粒度不對齊**：額度與 `by_sender` 的 key 是 stack／工作區路徑；擁有者是 uid。同一個 uid 底下好幾個 stack（今天全部）時，擁有者只能說「是這一夥的」，說不出是哪一個 stack。
