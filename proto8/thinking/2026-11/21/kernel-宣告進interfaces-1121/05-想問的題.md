想問使用者的六題：粗細、鍵放哪一層、被勾清單放哪、沒宣告能不能用、endpoint 清單指哪一份、對外那份 json 跟 11-20 的是不是同一件；每題擺選項與後果，我的看法另外標明、不替他選。

每題都可以答「先不定」。第 2、3 題不答，連甲都寫不出確定的樣子；其餘可以晚點。

## 第 1 題：做到多細

| 選項 | 樣子 | 後果 |
|---|---|---|
| 甲 | 只搬 `hooks`、`hookeds` 兩鍵 | 每一格都有程式讀；kernel 收什麼、有哪些 endpoint 照舊看文件與 `aos-llm ls`；完全沒碰對外介面，之後那份對外 json 怎麼做都行 |
| 乙 | 再加 `requests`、`endpoints` | 一眼看得出是哪種 kernel、收什麼；多出的兩格現在沒有程式讀（`aos-ledger` 的處境）；要先定「請求的 id 怎麼取」「endpoint 指哪一份」 |
| 丙 | 每樣一個鍵、包成 `aos-kernel` 格 | 最完整、跟 agent 對稱、`ctl add` 有格可以認；要新定好幾個約定，多數沒有讀者；`files` 把 stack 的位置寫死，之後對外的東西搬地方要跟著改 |
| 甲先做，其餘等有人要讀再加 | — | 跟他 11-20「以後有需求再去定規矩」同一個做法；「kernel 提供什麼去看 interfaces.json」這句話暫時只對 hook 成立 |

我的看法（只是看法）：三種不互斥，甲是乙的子集、乙是丙的子集，先做甲不會擋到後面。乙的 `requests` 是我覺得類推得最自然的一格，但它對外、又沒有讀者，照他補的那句話，比較像是等對外那份 json 一起想的東西。

## 第 2 題：`hooks`、`hookeds` 放 `interfaces.json` 的哪一層

現況：agent 那邊這兩樣都在 `"aos-agent": {…}` 格**裡面**；他寫的是 `"hooks": …`，沒說哪一層；kernel 現在沒有自己的格。agent 跟 kernel 要一起定。

| 選項 | 後果 |
|---|---|
| 最外層（agent 的也搬出來） | hook 體系一種讀法通吃 agent、kernel 與以後的別種；最外層從此混著介面名與普通的字；一個夾兩種身分時兩組點混在一張表 |
| 各自的格（agent 留在 `aos-agent`，kernel 新增 `aos-kernel`） | 跟現況與條文一致；`aos-hook` 要知道去哪幾格找 |
| 另立一格 `aos-hook` | 最貼條文「宣告自己遵守哪些介面」；跟他寫的字面差最遠 |

## 第 3 題：kernel 的被勾清單放哪

現況：`kernel.json` 的 `hooks` 鍵（loop 的四個點另在 `loop_hooks.json`）。

| 選項 | 後果 |
|---|---|
| 留在 `kernel.json`，`"hookeds": "kernel.json"` | 不用拆檔、kernel 程式不用改；被指的檔大半不是清單；`kernel.json` 裡那個鍵叫 `hooks`，跟新命名相反 |
| 留在 `kernel.json`，但鍵改名 `hookeds` | 命名一致；仍然不是獨立的檔 |
| 拆成 `hookeds.json`，`kernel.json` 用 `$ref` 指回去 | 一份來源、kernel 程式幾乎不用改；llm kernel 這樣寫行不行沒實測 |
| 拆成 `hookeds.json`，kernel 改照 `interfaces.json` 找 | 跟 agent 同一套；沒有定義夾的站（`kernel_gate`）沒有 `interfaces.json` 可讀，要另想 |

連帶一小題：`hookeds` 收不收字串陣列（loop 身體有兩份清單），以及 `hookeds.json` 裡面長什麼樣（樣本照 `hooks.json` 類推成「物件、hook 名當鍵」），他都還沒說。

## 第 4 題：「有宣告就能用」反過來，沒宣告的 kernel 夾怎麼算

| 選項 | 後果 |
|---|---|
| 照跑，宣告只是給人與工具看 | 現有四個沒宣告的範本、`kernel_gate`、手寫的站都不用動；宣告跟實際對不上不會被發現 |
| 沒宣告 `hooks` 就不派發 hook（跟 agent 一樣） | 一致；`{}` 的最小 kernel 也要多一份 `interfaces.json` 才掛得了 hook；`kernel_gate` 與手寫的站要例外或另給地方 |
| 沒宣告連信都不收、掛都不給掛 | 每個 kernel 都要先宣告；跟「收請求的 proc 不需要知道自己是 kernel」「daemon 就是最簡單的 kernel」對不上；也會讓 `interfaces.json` 變成對外介面的唯一依據，擋到之後那份對外 json |

## 第 5 題：endpoint 代號清單算哪一種，宣告指哪一份

（選甲可以跳過。）

| 選項 | 後果 |
|---|---|
| 算設定＋清單：夾裡一份 `endpoints.json`，`kernel.json` 與 `interfaces.json` 都指它 | 一份來源、跟 `hookeds` 同一個做法；`url`、`exec` 這些對內的鍵跟著在裡面，所以它只能當來源、不能直接給別人；跟 stack 的窗同名不同內容；檔內的 `$ref` 要跟著調 |
| 算執行時的窗：宣告說「窗在 stack 的 `endpoints.json`」 | 指到的就是別人實際讀的那份；路徑要從 stack 算（跟 `hooks` 從定義夾算不同）；stack 的位置寫死在宣告裡 |
| 不宣告，照舊 | 最省；`interfaces.json` 看不出這個 kernel 有哪些模型 |

連帶：`allowed`（可掛的名字）跟 endpoint 代號是同一種東西，要不要比照。

## 第 6 題：今天說的「對外的介面宣告另外一份 json」，跟 11-20 那幾樣是不是同一件

11-20 他已經有：那份答「kernel 吃什麼資源」的「另外一個json」（原型叫 `kask.json`，寄信問、整份原樣回）；stack 的 public 資料夾（「先試固定位置，沒有才寄信問」「框架放固定幾樣、其餘自己加」）。細節在 [07](07-對外與對內.md) 第三節。

| 選項 | 後果 |
|---|---|
| 同一件：對外的介面宣告就是放進 public 資料夾、也可以寄信問到的那份 | 放哪、怎麼拿他大半已經答過，之後只剩「裡面裝什麼」；資源宣告與請求形狀、endpoint 清單會在同一份裡 |
| 各是各的 | 會有兩三份都給別人看的 json，各自要定位置與拿法 |
| 先不定 | 不影響這次；只要現在不讓別人的程式去讀 `interfaces.json`、不把 stack 的位置寫死在裡面，兩種都還走得通 |

## 不列成題、但他可能想知道的

- 名字（程式夾那份叫 `hooks.json`、loop 的叫什麼、請求的 id）都是樣本自己取的。
- 「收什麼請求」的宣告要不要真的拿去驗信（[04](04-邊緣狀況.md) 第 7 條）——選乙或丙才有這題。
- 兩支 kernel 程式共用的點宣告要不要拆成兩份（[03](03-後果對照.md) 第 4 點）。
