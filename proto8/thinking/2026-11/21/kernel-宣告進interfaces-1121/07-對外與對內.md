使用者補的一句「界面有分對外與對內…對外的界面宣告的json，需要另外準備一份」：每樣宣告歸對外還是對內、那份對外 json 可能的形狀與後果、跟 11-20 兩條調查的重疊，以及現在定 interfaces.json 寫法時哪些會把這條路堵住。

## 原話（使用者 11-21，逐字，頂層轉）

「kernel那塊，界面有分對外與對內，interfaces.json中當然兩者都可以有，只是說未來，對外的界面宣告的json，需要另外準備一份，用於讓他人存取」

讀法（頂層的，我讀起來也一樣）：對外＝給別人用的（收什麼請求、可挑的 endpoint、回什麼）；對內＝自己這邊用的（hook 點、帳本、設定）。`interfaces.json` 兩類都可以寫；未來另有一份只放對外的 json，是讓別人拿的。

原話沒說的兩點（不替他補）：

- 「另外準備一份」是另一個**地方**的檔（別人拿得到的地方），還是定義夾裡另一個**檔**、由 `interfaces.json` 指過去。前者才解得了「寄信的人看不到定義夾」；我照前者往下想，後者當成它的來源。
- 「他人」包不包含別台機器、別的 daemon 底下的東西。

這句話直接回答了 [04](04-邊緣狀況.md) 第 1 條（寄信的人找不到定義夾）：他的方向不是讓別人來讀 `interfaces.json`，而是另外給一份。

## 一、每樣宣告歸對外還是對內

「別人」＝寄信來的 agent 與程式；「自己這邊」＝這個夾的主人、起它的人、掛 hook 的人、看帳的人。

| 東西 | 歸哪邊 | 說明 |
|---|---|---|
| 收什麼請求（信的 body） | 對外 | |
| 回信的形狀、拒信代號 | 對外 | hook 可以回任意代號，所以只能是「至少有這些」 |
| 可挑的 endpoint 代號與屬性、思考程度級別 | 對外 | 但 `url`、`exec`、`fixed` 是對內的；同一張表兩邊各佔一半 |
| 信箱在哪 | 對外 | 別人已經靠環境變數拿到了 |
| hook 點 | **對內**（我的看法，難分） | 能掛 hook 的只有改得了這個夾設定的人，所以是「寫程式的人給夾的主人看」，不是給寄信的人。但它也是一種「別人照著寫才不會錯」的約定，只是那個別人是自己這邊的人 |
| 被勾清單 | 對內 | 寄信的人可能想知道「有沒有 hook 會改我的信」，但那是主人願不願意說的事 |
| `kernel.json` 認哪些鍵、要哪些環境變數 | 對內 | |
| 帳本 `ledger.jsonl` | 對內（難分） | 讀的人是審視者、上層的量測，是另一支行程但跟主人同一邊 |
| `queue.json`、`used.json` 這些窗 | 對內（難分） | 寄信的人看了能知道自己排第幾、額度剩多少，要不要給是主人的事 |
| `hold.json`＋`decisions/` | **難分** | 給「替這個 kernel 表態的人」讀寫；那個人通常就是站所在的 agent 自己（對內），知識庫也教別人來寫（對外，但只對被信任的人） |
| `allowed` | 對內的設定，對外有意義 | 跟 endpoint 代號同構：別人想知道自己的名字掛不掛得上 |

**`endpoints.json` 這個窗，現在就是一份「另外準備的對外 json」**：它從對內的設定（`kernel.json` 的 `endpoints`）每輪算出來、拿掉內部鍵、解完指示詞、放在別人拿得到的地方（stack）、有一支指令（`aos-llm ls`）專門讀它。他說的未來那份，可以看成把這個做法從 endpoint 一樣東西推廣到整個對外介面。

## 二、那份對外 json 可能的形狀

不是設計，只列得出來的幾種與後果。

**放哪、別人怎麼拿**

| 放法 | 別人怎麼拿到 | 後果 |
|---|---|---|
| stack 裡一份檔（像今天的 `endpoints.json` 窗） | 手上有 kernel 的 stack 就直接讀 | 讀的人不花 kernel 的時間；只有同一台機器、讀得到那個夾的人拿得到；kernel 停了檔還在、可能是舊的；kernel 從沒起過就沒有 |
| kernel 代答（寄信問、回信給內容） | 寄一封問句信 | 拿得到現算的內容、主人可以不給；每答一封吃一輪的時間（11-20 量到 8～22 毫秒）、kernel 停著就等不到 |
| daemon 代答 | 問 daemon | daemon 要認得哪一列是 kernel、去讀它的夾；跟「不跟 daemon 耦合」反方向；11-20 的調查列過、沒實作 |
| 留在定義夾，由 `interfaces.json` 指過去 | 要有定義夾的路徑 | 寄信的人沒有，等於沒解決 |

**誰寫出來**

| 做法 | 後果 |
|---|---|
| 手寫一份 | 最簡單；跟 `interfaces.json` 裡對外那幾格是兩份，會對不上 |
| kernel 起來或每輪從宣告算出來 | 一份來源；kernel 要解完指示詞、把被指到的檔的內容攤進去（別人解不了 `$AOS_HOME` 以外的指示詞、也讀不到被指的檔）、拿掉對內的鍵。`endpoints.json` 窗今天就是這樣算的 |
| 編譯時寫出來 | 只有用 `kernel.py` 編譯的夾才有；手寫夾要自己顧 |

**跟 `interfaces.json` 對外那幾格的關係**：可以是同一份內容的兩個樣子——`interfaces.json` 那幾格是**來源**（一格一個檔名，檔是「id＋schema」的物件），對外那份是**攤平後的成品**（不含檔名與指示詞，自己就讀得懂）。hooks 那套的物件檔正好適合：每份都是自足的 id 表，合起來就是對外那份，格式不用另外發明。

**跟 `aos-llm ls` 與 `endpoints.json` 窗**：窗是對外那份的一個現成特例。未來可以併進去（`ls` 改讀對外那份的 endpoint 那一段），也可以並存；`ls` 現在靠「有 `endpoints.json` 又有 `requests/`」認出 llm kernel，窗一搬這個認法就要跟著換。

**別台機器、別的 daemon 底下的東西**：別的 daemon 底下、同一台機器的，讀檔與寄信都行（kernel 的位址本來就是一個路徑）。別台機器讀不到檔，只能靠到得了那台機器的管道；這次沒查現在跨機器有什麼。

## 三、跟 11-20 兩條調查幾乎是同一件事

他 11-20 已經說過、選過的（[aos-kres-1120/08](../../20/aos-kres-1120/08-使用者已答.md)、[aos-kask-proto-1120/07](../../20/aos-kask-proto-1120/07-使用者已答.md)、[aos-direct-reply-1120/06](../../20/aos-direct-reply-1120/06-使用者已答.md)）：

- 問「kernel 宣告自己有哪些規則」放哪：「另外一個json吧。interfaces和hook都是另外的用途。」
- 請求者怎麼知道 kernel 吃什麼形狀：「可以先做寄信問kernel，然後我們的kernel框架也可以弄一個自動回這種信的東西。算是基礎協議吧。」
- 寄信問 kernel 的十四題：信箱在 stack 底下跟 `requests/` 並排、固定約定、不過 hook、不記帳、「整份原樣回」、那份 json「定義夾一份、stack 有就蓋上去」、沒放那份 json 就是不給、留一格「問什麼」。
- 通用的「問特定的東西、直接回」：「在stack開一個public資料夾」、「先試固定位置，沒有才寄信問」、「混著：預設讀檔，要現算的才寄信」、「框架放固定幾樣、其餘自己加」。

對照起來：

| 今天這句 | 11-20 已有的 |
|---|---|
| 對外的介面宣告另外一份 json | 那份「另外一個 json」（原型叫 `kask.json`）；當時裝的是「吃什麼資源宣告」 |
| 用於讓他人存取 | public 資料夾（讀檔）＋寄信問（現算） |
| 未來 | public 資料夾那題他說「先記著吧」，實作「等明天吧。倒是可以先來做規劃」 |

**沒定的是這三樣是不是同一份**：(a) 11-20 那份答「吃什麼資源」的 json、(b) public 資料夾裡框架固定放的那幾樣、(c) 今天說的對外介面宣告。如果是同一份，「對外那份放哪、怎麼拿」他大半已經答過了（stack 的 public 夾、先讀固定位置、沒有才寄信問），這次不用再問；如果不是，就會有兩三份都叫「對外」的 json。這是 [05](05-想問的題.md) 第 6 題。

有一處要他知道的不一致：11-20 那句「interfaces和hook都是另外的用途」是把 kernel 的規則宣告放在 `interfaces.json` **外面**；今天是「interfaces.json中當然兩者都可以有」。兩句可以同時成立（`interfaces.json` 可以有，但給別人的那份是另外的），列在 [06](06-衝突.md) 第 4 條。

## 四、現在定寫法時，哪些會把這條路堵住

他說的是未來，所以這次不必設計那份 json；要顧的是別讓今天的寫法之後得拆。

**會堵的**

1. **讓別人的程式去讀 kernel 的 `interfaces.json`。** 例如為了解決「寄信的人找不到宣告」，讓 `aos-llm ls` 或 `aos-agent ctl` 從 daemon 的表查定義夾、或在 stack 抄一份 `interfaces.json` 給外面讀。一旦有程式這樣讀，`interfaces.json`（含對內的格與指到 `$AOS_HOME` 的路徑）就變成對外的東西，未來那份會變成第二個來源。
2. **「沒在 `interfaces.json` 宣告就不收信」。**（[03](03-後果對照.md) 第 5 點的第三種。）這等於讓 `interfaces.json` 當對外介面的唯一依據；之後對外那份跟它不一致時要聽誰的，就成了問題。對 hook（對內）做這條規則不受影響。
3. **把 stack 裡的位置寫死在 `interfaces.json`。** 丙的 `files`（`queue.json`、`decisions/` 的路徑）與「`endpoints` 指到 stack 的窗」那種落法。之後對外的東西若集中到 public 資料夾，這些格全部要改，照它讀的程式也要改。
4. **對外的宣告檔長成別人讀不了的樣子。** 檔裡帶指示詞、帶內部鍵、或要再開別的檔才看得懂。乙的 `endpoints.json`（清單兼設定，有 `url`、`exec`）就是；它當**來源**沒問題，但不能直接拿去當對外那份，名字上也別讓人以為它是。

**不會堵的**

- **甲**：只搬 hook 兩鍵，全是對內的，完全沒碰對外。之後對外那份怎麼做都行。
- **乙的 `requests`**：指到的是自足的「id＋schema」物件檔，之後攤進對外那份就好；前提是只當來源、不叫別人來讀。
- **被指到的檔都用同一個樣子（物件、id 當鍵、schema）**：未來對外那份可以直接是幾份這種物件的合併，不用換格式。
- **鍵放最外層或包成一格**：兩種都不堵。包成格有一個順手的地方——哪幾格算對外，可以用格來分（例如對外的鍵集中在一格），之後「從 `interfaces.json` 算出對外那份」時不用另外標記；這是觀察，不是建議的寫法。

**我的看法（只是看法）**：照他這句話，乙、丙多出的那些鍵裡，對外的部分（`requests`、`endpoints`、`errors`）最終的讀者會是「未來那份對外 json 的產生程式」，不是寄信的人；在那份還沒做之前，它們沒有讀者。這讓「現在先做甲、對外的等那份一起想」更站得住；但要不要先把來源備著，是他的判斷。
