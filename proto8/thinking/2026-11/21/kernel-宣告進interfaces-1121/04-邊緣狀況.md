把 kernel 的宣告放進 interfaces.json 會碰到的十六條邊緣狀況：只攤事實與後果，前三條影響最大（寄信的人找不到定義夾、指示詞是讀的人在解、有三種 kernel 沒有定義夾）。

## 影響最大的三條

1. **寄信的人找不到定義夾。** 寄信給 llm kernel 的人手上是 `AOS_LLM_KERNEL`＝kernel 的 **stack**；寄給一般 kernel 的人手上是 `AOS_KERNEL`＝`<stack>/requests` 這個**信箱**（兩種連位址的指法都不一樣）。`interfaces.json` 在定義夾，從 stack 走不回去。所以「想知道這個 kernel 收什麼」的那個人，正好是看不到宣告的人。三條出路：
   - stack 也有一份（有先例：`aos-observed` 就是程式在 **stack** 的 `interfaces.json` 補的，附錄 4 寫明 stack 那份存在）。後果：kernel 每次起來要把宣告抄或寫進 stack；兩份可能不同。
   - 從 daemon 的表查那一列的定義夾。後果：要先知道它是哪台 daemon 的哪一列；別棵樹的 kernel 查不到；跟「不跟 daemon 耦合」反方向。
   - 不管：宣告是給「手上有定義夾的人」看的（夾的主人、編譯、`aos-hook`）。後果：`requests`、`endpoints` 的宣告對寄信的人沒用，寄信的人照舊看知識庫與 `aos-llm ls`。
   他後來補的那句（對外的介面宣告另外準備一份）走的是第四條路：給別人的另有一份，前兩條出路反而會擋到它，見 [07](07-對外與對內.md) 第四節。
2. **指示詞是讀的人在解，用的是讀的人的環境。** `$AOS_HOME` 通常兩邊一樣，沒事。但 `$AOS_STACK`、`$AOS_CD` 是每個行程自己的：別人讀 kernel 的 `interfaces.json` 時，`{"$env": "AOS_STACK", "$path": "/endpoints.json"}` 會解成**讀的人自己的** stack。所以 stack 裡的東西（窗、帳本、`decisions/`）不能用指示詞指。現有的 `"aos-ledger": {"file": "ledger.jsonl"}` 靠的是「這一格的檔名從 stack 算」的默契，檔裡沒寫；而他定的 `"hooks": "hooks.json"` 是從定義夾算。同一份 `interfaces.json` 裡的相對檔名於是有兩種起算點，從字面分不出來。
3. **三種 kernel 沒有定義夾可以放 `interfaces.json`。**
   - **daemon 本身**：知識庫說「daemon 本身就是最簡單的 kernel」；`templates/start-api/root` 只有 `daemon.json`、`_entry`。一般 kernel 原樣轉寄的那些信，真正的收件介面是 daemon 的。
   - **agent 身上的 `kernel_gate`**：站的設定在 `<agent 的 stack>/hooks/kernel_gate/kernel.json`，信箱在同一個小格；定義夾是 agent 的，裡面的 `interfaces.json` 是 agent 的。
   - **知識庫教的手寫站與從頭寫的程式**：工作區裡一份 `gate/kernel.json` 加一支 `gate/run`，或任何會收信的程式。
   「有宣告才能用」若套到 kernel，這三種要嘛例外、要嘛得替它們想出放宣告的地方。

## 「收什麼請求」這份檔

4. **一般 kernel 是轉寄站。** 它會判的只有三個鍵（`procs_added`、`procs_started`、`procs_woken`），其餘的鍵（`procs_stopped`、`procs_slept`、`procs_removed`、`procs_state_path`…）原樣交給下一站。宣告只寫三個，看的人會以為只收三種；寫全，等於把 daemon 的介面抄一份，daemon 改了要跟著改。串好幾站時，每一站的宣告都只是整條路的一段。
5. **id 跟信對不齊。** 一般 kernel 的一封信可以同時帶 `procs_added` 與 `procs_started`，一封信對到兩個 id；llm kernel 的信沒有種類欄，id 只能憑空取。hook 點沒有這個問題（一次事件就是一個點）。
6. **hook 會改掉介面。** `before_verdict` 能把 body 換掉（原本不合格的信可以被改成合格的）、`after_verdict` 能把拒改成放行或給出任意代號、`before_reply` 能改回信。掛了 hook 的 kernel 實際收什麼、回什麼，是被勾清單決定的；共用的請求宣告只講得了「沒掛 hook 時」。`kernel_gate` 的說明更是明寫寄信的人可以加任意鍵、aos 不檢查。
7. **拿 schema 去驗信，就多了一道擋信的規則。** 現在是「不認得的鍵略過」（C-48）、沒寫規則時一般 kernel 連 body 是不是物件都不驗。宣告只給人看就沒事；一旦有程式照 `input` 驗，寫了 `additionalProperties: false` 的宣告會把原本放行的信擋掉。hook 那邊他說的是「有提供這些 key 就照著做」，請求這邊照不照，沒有定論。

## 檔的形狀與名字

8. **物件檔裡，哪些鍵不是 id。** 每份 json 第一個鍵慣例是 `description`，它跟 id 同一層。hook 點的名字有限制（小寫、數字、底線），錯誤代號大寫開頭，都還分得開；**endpoint 代號是主人自己取的任意字串**，真的可以有一包叫 `description`。而且 `kernel.json` 用 `$ref` 讀同一份檔時，kernel 會把 `description` 當成一組 endpoint（值不是物件，那一組應該會報設定錯；沒實測）。
9. **新舊名字正好撞在一起。** `loop_hooks.json` 現在是 loop 的**被勾清單**；照新命名，被勾清單該叫 `…hookeds`，而點宣告該叫 `…hooks`——同一個檔名在改名前後是相反的東西。`kernel.json` 裡的 `hooks` 鍵同理。proto8 當沒有舊版，不用做相容；只是 `~/aos-home` 這種已經在跑的樹，照舊名留著的檔會被新程式當成另一種東西讀。
10. **`endpoints.json` 會有兩份同名、內容不同的檔。** 定義夾那份是清單兼設定（有 `url`、`exec`）；stack 那份是每輪算出來的窗（沒有內部鍵、壞的那組是 `{"error": …}`）。人容易看錯份；定義夾與 stack 若是同一個夾會互相蓋掉（沒查現有佈局有沒有這種情形）。
11. **把 `endpoints` 拆成獨立檔，檔內的 `$ref` 會指錯。** 範本裡 `sol` 寫 `"reasoning_efforts": {"$ref": "#/reasoning_effort_levels/gpt"}`，`#/…` 指的是同一份檔裡的表；拆出去後那張級別表也要跟著搬，或改寫路徑。沒實測拆出去後解不解得開。
12. **JSON Schema 的 `$ref` 跟 aos 指示詞的 `$ref` 同名不同物。** 宣告檔裡的 schema 若想引用別份（例如 hook 點的 `body` 引用請求檔的 `input`），寫出來是 `{"$ref": "…"}`；這份檔一旦先過 `aos-directive`，那個物件會被整個換成指到的內容——剛好是想要的效果，但規則是 aos 的（解不開就報錯、`#/` 的意思也不同），不是 JSON Schema 的。讀宣告的程式過不過指示詞，要說清楚。

## llm kernel 專屬

13. **轉交的 llm kernel（`llm-team`）。** 它的 `endpoints` 是轉交表（`{"to": "sol", "kernel": 隔壁的 stack, "reasoning_efforts": "forward"}`），真正的屬性在下一層 kernel。宣告指它自己的清單，只看得到「有哪些代號、轉給誰」，級別寫的是 `forward` 不是實際收哪幾級。
14. **清單上有，不代表現在能用。** 某一組的指示詞解不開、金鑰沒設、後端沒開，靜態清單都看不出來；只有 stack 的窗會把壞的那組標成 `error`。「這個 kernel 提供哪些」與「現在哪些能用」是兩個問題，前者才是宣告答得了的。

## 一個夾兩種身分、編譯

15. **同時是 agent 又是 kernel 的夾。** 鍵放最外層時只有一個 `"hooks"`：agent 的點（`before_tool`…）與 kernel 的點（`before_verdict`…）要並在同一個陣列、同一張表，被勾清單也混在一起，看不出哪個點是哪個身分的。包成各自的格就分得開。（現在的 `kernel_gate` 不走這條路——站是掛在 agent 的 `on_clock` hook 上的另一支程式——所以今天還沒有夾真的碰到。）
16. **重新編譯會整份蓋掉 `interfaces.json`。** `kernel_llm` 現在就是這樣（固定只寫帳本那格）。宣告變多之後，編譯寫的格與人手加的格（「想加啥就加啥」）會在同一份檔裡，重新編譯一次，手加的就沒了；agent 那邊的編譯有沒有同樣的行為，這次沒查。
