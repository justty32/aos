甲乙丙三種候選在九個面向上的後果：一眼看不看得出、搬不搬得走、`kernel.json` 既是設定又是清單怎麼落、兩支程式共用點宣告怎麼落、沒宣告能不能用、誰來讀、`aos-daemon-ctl add` 看不看、要不要 `aos-kernel` 一格、編譯怎麼配。

## 1. 使用者一眼看不看得出這個 kernel 提供什麼

- **甲**：看得出「能掛哪些 hook、現在掛著哪些」。看不出它是哪種 kernel、收什麼信——perm 的 `interfaces.json` 跟任何 loop 身體的一般 kernel 一模一樣，llm kernel 只多一行帳本。
- **乙**：多看得出「收什麼請求」（指到 `kernel_llm/requests.json` 還是 `kernel/requests.json`，路徑本身就說了是哪種 kernel）與「有哪些 endpoint」。這兩樣正是人最常想查的。
- **丙**：都看得出，但 `interfaces.json` 本身變成一串指到 `$AOS_HOME` 的路徑，要再開五六份檔才看得到內容；「找自己想看的」要多走一步。

三種都一樣的一點：他不收直接寫內容，所以 `interfaces.json` 永遠只是目錄，內容在別的檔。對 hook 是好事（宣告長）；對 `"config": "kernel.json"` 這種本來就一行的，沒差。

## 2. 整夾搬走還指不指得到

- 夾內的檔（`hookeds.json`、`endpoints.json`、`kernel.json`）跟著走。
- 指 `$AOS_HOME` 的（三個點、請求的形狀）：新地方裝了 aos 就指得到，而且拿到的是**新地方那一版程式的宣告**——跟那裡實際跑的程式對得上，這是動態連結的好處。`daemon.json`／`loop.json` 本來就用同一種指示詞指程式，所以沒有多出新的耦合。
- 反過來：如果把宣告靜態連結進夾裡（抄一份），搬到程式版本不同的地方，宣告說的跟實際跑的會對不上，而且沒有東西會發現。
- **跟 daemon 沒有耦合**：三種候選都沒有任何一格寫 daemon 的路徑。
- 丙的 `files`（路徑從 stack 算）搬家不受影響，但「從哪個 stack 算」讀的人要自己知道（[04](04-邊緣狀況.md) 第 1、2 條）。

## 3. `kernel.json` 既是設定又是清單，怎麼落

`kernel.json` 裡有兩樣東西同時是設定與「清單」：`hooks`（被勾著哪些）與 `endpoints`（有哪些代號）。三種落法，哪種候選都要選一個：

| 落法 | 樣子 | 後果 |
|---|---|---|
| 指進 `kernel.json` | `"hookeds": "kernel.json"` | 不用拆檔、程式不用改讀法；但「字串就是檔名、檔就是清單」不成立了——那份檔大部分內容不是清單，讀的人要知道看裡面哪個鍵。`"endpoints"` 這樣指還會把 `url`、`exec` 一起給人看 |
| 拆出去、`kernel.json` 用 `$ref` 指回來 | `hookeds.json`＋`kernel.json` 寫 `"hooks": {"$ref": "hookeds.json"}` | 一份來源、兩邊都指它。`endpoints` 這樣拆 llm kernel 的文件寫明支援；`hooks` 這樣拆：一般 kernel 整份設定先過 `aos-directive`，照理可行；llm kernel 的 `hooks` 是另一條讀法，**沒實測** |
| 拆出去、kernel 改成自己讀那份檔 | kernel 照 `interfaces.json` 的 `hookeds` 找清單 | 跟 agent 一致（agent 就是照宣告找）；但 kernel 程式現在只拿到 `kernel.json` 的路徑，要多認一份 `interfaces.json`，而 `kernel_gate` 那種沒有定義夾的站沒有這份檔可讀 |

另一個連帶：`kernel.json` 裡那個鍵現在叫 `hooks`，在他的新命名裡 `hooks` 是「有哪些鉤子」。不拆的話，同一個字在 `interfaces.json` 與 `kernel.json` 是相反的意思（[06](06-衝突.md) 第 2 條）。

## 4. 兩支 kernel 程式共用一份 hook 點宣告、行為有差

現況的差別：`before_reply` 一般 kernel 要開 `reply_via_me` 才有、llm kernel 一定有；`hold` 這個判決只有一般 kernel 收；`after_verdict` 的 `next`、`decision` 兩欄各只有一種站有；`body` 的形狀完全不同。

| 落法 | 後果 |
|---|---|
| 維持一份共用，差別寫在 description（樣本的做法） | 最省；宣告不精確，但照他的話「就是宣告說我大概會怎樣」。`body` 的形狀交給請求檔（乙、丙才有） |
| 兩支程式各一份完整的 | 精確；三個點寫兩遍，改一邊要記得改另一邊 |
| 共用一份，llm kernel 的夾在陣列裡再疊一份只寫差別的 | 省字；但**同一個 id 出現在陣列的兩份檔裡要怎麼算**（後面蓋前面？合併？報錯？）他沒說過。現在的程式是「同名點要說得一樣，不然報錯」 |

甲只能選第一或第二種（沒有請求檔可以分擔 `body`）。

## 5. 沒宣告的 kernel 還能不能用

「有宣告就能用」是他對 hook 說的。反過來「沒宣告就不能用」要不要成立，後果差很多：

- **不成立（宣告只是給人與工具看）**：kernel 程式照舊只讀 `kernel.json`，四個沒有 `interfaces.json` 的範本、`kernel_gate`、手寫的 kernel 全部照跑。代價是宣告可能跟實際對不上而沒人發現，宣告變成比較正式的文件。
- **對 hook 成立（沒宣告 `hooks` 就不派發 hook）**：跟 agent 一致（附錄 4：「interfaces.json 沒宣告＝沒有 hook 機制」）。後果：`templates/start-api/perm` 的 `kernel.json` 現在是 `{}`，最小的 kernel 夾得多一份 `interfaces.json` 才掛得了 hook；`kernel_gate` 的站住在 agent 的 hook 小格裡，沒有定義夾可放（[04](04-邊緣狀況.md) 第 3 條）。
- **對請求也成立（沒宣告 `requests` 就不收信）**：等於每個 kernel 都要宣告才能當 kernel。跟知識庫那句「收請求的 proc 不需要知道自己是 kernel」「daemon 本身就是最簡單的 kernel」對不上（[06](06-衝突.md) 第 5 條）。

## 6. 誰來讀這些宣告

現況：kernel 的 `interfaces.json` 沒有任何程式讀（`aos-ledger` 宣告了沒人讀）。各樣東西可能的讀者：

| 宣告 | 可能的讀者 | 現在它怎麼知道 |
|---|---|---|
| `hooks` | `aos-hook points／check`、kernel 的 `hooks.py`、編譯時驗 hook | `hooks.py` 讀同夾固定路徑；`aos-hook` 要人用 `--points` 給路徑；`--agent` 對 kernel 夾默默給 0 點 |
| `hookeds` | 同上 | `kernel.json` 的 `hooks` 鍵 |
| `requests` | **沒有現成的讀者**。寄信的是 `aos-agent ctl`、`aos-llm`、agent-fsm 的格程式，形狀都寫死在程式裡；會查的只有人與 agent（agent 現在查知識庫） | 知識庫 `aos/kernel.json`、`aos/brain.json` |
| `endpoints` | `aos-llm ls`、想挑模型的 agent | 讀 stack 的窗；自動找 llm kernel 靠「有 `endpoints.json` 又有 `requests/`」 |
| `errors` | 沒有現成的讀者（agent-fsm 認 `BudgetMissing` 是寫死的） | 文件 |
| `files` | `kernel_gate`（讀 `hold.json`、寫 `decisions/`） | 寫死 |

所以甲宣告的每一樣都有讀者；乙多出的兩樣，`endpoints` 有一個半讀者、`requests` 只有人與腦；丙多出的沒有讀者。宣告了沒人讀，就是 `aos-ledger` 現在的樣子。

另外：會想讀 `requests`、`endpoints` 的都是**寄信的那一方**，而它手上沒有定義夾的路徑（[04](04-邊緣狀況.md) 第 1 條）。這比「要不要宣告」更先卡住。

## 7. `aos-daemon-ctl add` 要不要看

- 現況：`aos-agent ctl add` 會擋沒宣告 `aos-agent` 的夾（`InterfaceMissing`）；`aos-daemon-ctl add` 什麼都不看，kernel 就是用它掛的。
- 要它看：`aos-daemon-ctl` 是 C++ 寫的、不讀 `interfaces.json`、也不解指示詞以外的東西；它掛的是「任何 proc」，不知道哪一列是 kernel。要擋只能另開一支給 kernel 用的掛載指令，或讓它認一格（丙的 `aos-kernel`）。
- 不要它看：維持「daemon 掛什麼都行」。甲、乙沒有一格可以認，本來也不好擋。
- 能擋的只有丙；擋了以後，沒宣告的 kernel 夾連掛都掛不上。

## 8. 要不要 `aos-kernel` 一格

**現況查到的**：agent 的 `interfaces.json` 把所有鍵包在 `"aos-agent": {…}` 裡，`hooks`、`hook_points` 都在那格裡面（`templates/start-api/agents/ann/interfaces.json`；`declared_files.py`、`hook_point.for_definition` 都只讀 `aos-agent` 那格）。最外層只有介面名（`aos-agent`、`aos-observed`、`aos-ledger`）。他說的 `"hooks": …` 沒說是哪一層。

| 放法 | agent 那邊 | kernel 這邊 | 後果 |
|---|---|---|---|
| 鍵放最外層 | `hooks`、`hookeds` 從 `aos-agent` 格搬出來 | 直接寫，不用格（甲、乙的樣本） | hook 體系不管對方是 agent 還是 kernel，`aos-hook` 一種讀法通吃；最外層從此有兩種鍵（介面名、東西的種類），`requests`、`endpoints` 這種普通的字會跟別人撞名 |
| 包在各自的格 | 留在 `aos-agent` 格 | 新增 `aos-kernel` 格（丙的樣本） | 跟現況與條文一致；`aos-hook` 要知道去哪一格找（agent 看 `aos-agent`、kernel 看 `aos-kernel`、以後別種再加），或兩格都看；一個夾同時是 agent 又是 kernel（`kernel_gate`）時兩格各有一份 `hooks` |
| 另立一格專放 hook | `"aos-hook": {"hooks": …, "hookeds": …}` | 同左 | hook 體系有自己的介面名，agent、kernel 都宣告「我遵守 aos-hook」；最符合條文「宣告自己遵守哪些介面」的讀法，但跟他寫的 `"hooks": …` 字面差最遠 |

格名要不要分 `aos-kernel` 與 `aos-llm-kernel`：丙的樣本分了（`endpoints` 只有 llm kernel 有）。不分的話一格通吃，llm 專屬的鍵有就寫、沒有就不寫，比較接近他說的「想加啥就加啥」。

## 9. 編譯（`from aos.py.kernel import defs`）怎麼配

- 現況：`program="kernel_llm"` 每次編譯整份蓋掉 `interfaces.json`（固定只寫帳本那格）；`program="kernel"` 不寫。
- 三種候選都會讓編譯多寫東西：`hooks=` 有給就寫 `hookeds.json`（現在是寫進 `kernel.json` 的 `hooks`）、`interfaces.json` 兩種 program 都寫。寫 `kernel.py` 的人不用自己碰這些檔，這對甲乙丙沒有差別。
- 手寫夾（`templates/kernel/` 那幾份）才有「多幾份檔要維護」的差別，丙最多。
- 整份蓋掉這件事會變得更明顯：手加進 `interfaces.json` 的格（「想加啥就加啥」），重新編譯就沒了。
