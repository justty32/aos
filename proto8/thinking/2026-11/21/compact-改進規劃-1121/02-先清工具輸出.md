「先清工具輸出」的六種清法拿四份真模型 history 實算：清掉最後 3 則以外的工具輸出最划算（history 少 27%～78%）；我定的預設是「留最後 3 則與最後一組、短的不清、arguments 不清」，清完夠不夠低要不要省掉摘要留給使用者定（Q1）。

## 樣本與算法

- 樣本（都是真模型跑出來的 agent-fsm history，在 repo 外的暫存區，只讀）：
  - skyrim 三隻（sol-high，`~/.aos/scratch/swap-1115/r1/ws/.stack/procs/` 下的 `skyrim-alt-chores`、`skyrim-alt-l10n-translate-1115a`、`skyrim-alt-l10n-migrate-1115a`；11-15 從真樹抄出來的）。
  - n-luna（luna，`~/.aos/scratch/top-1121-tooldesc/trees/n-luna/.stack/procs/ann/`，今天 tool-desc 線的小任務）。
- 每份都當成「現在要壓」，對整份 history 套清法，比 JSON 字數。佔位字是一行 `[aos] tool output cleared by compact (N chars); the original is in history_removed.jsonl`（約 90 字）。
- 換成 token：用同一隻 stack 的 `think/request.json`（最後一封請求全文）字數 ÷ `observed.jsonl` 最後一則 think 的 `prompt_tokens`，得每 token 幾字（skyrim 3.21～3.27、n-luna 4.09），再把省下的字數換掉。不是 tokenizer 算的，當量級看。
- 腳本 `~/.aos/scratch/top-1121-compactplan/measure.py`，輸出 `measure-out.txt`。

## 六種清法實算

| 清法 | chores | translate | migrate | n-luna |
|---|---|---|---|---|
| A 舊的全清 | −67% | −68% | −78% | −71% |
| B 留最後 3 則、其餘全清 | −67% | −68% | −78% | −27% |
| C 留最後 3 則、只清 >2000 字的 | −59% | −66% | −70% | −18% |
| D 留最後 3 則、其餘各留頭尾 500 字 | −50% | −60% | −62% | −16% |
| E ＝B＋舊的工具呼叫 arguments >2000 字也清 | −81% | −80% | −78% | −27% |
| F 只清最後一封 user 之前的 | −64% | −68% | −10% | −27% |

估成 prompt token（B）：chores 68,329→約 29,800；translate 62,356→約 27,300；migrate 47,880→約 19,000；n-luna 17,800→約 14,500。以 272k 視窗算，skyrim 三隻從 18%～25% 掉到 7%～11%。

讀出來的：

- **B 跟 A 幾乎一樣**：舊的大輸出才是大頭，留最後 3 則幾乎不損失省量；n-luna 例外，因為最大那則（20,585 字）剛好在最後 3 則裡。
- **C、D 省得少、留下的多半沒用**：頭尾 500 字對 `ls`、`json_get` 那種輸出常常剛好是沒用的那段。
- **F 對長任務沒用**：migrate 從頭到尾只有一封信，「最後一封 user 之前」幾乎沒東西。
- **E 只對寫檔多的 agent 有差**（chores、translate 多 13 個百分點），其他幾乎沒差。

## 各做法的後果

| 做法 | 好處 | 壞處 |
|---|---|---|
| 清完再摘要（清只是讓摘要那次變小） | 摘要請求小一半以上、接近滿時也放得下；行為跟今天一樣（壓完一樣只剩摘要） | 腦寫摘要時看不到舊工具輸出的細節，只看得到自己當時怎麼回應它（品質掉不掉沒量）；仍要叫一次腦 |
| 清完夠低就不摘要 | 不叫腦、零 token；對話原文（腦自己的話、信、工具呼叫）全留；do_task 紀錄點不斷（清只改內容、不刪列） | 要估「清完剩多少」（見下）；history 一直長，下次再清時能清的越來越少，終究要摘要；寄 `/compact` 的人可能預期有摘要、`handoff.md` 不會多一節（見 [06](06-衝突.md) 第 1 條） |
| 清 arguments | 寫檔多的 agent 多省一成多 | 腦看到自己以前的呼叫變成佔位，可能學著照抄；某些端點要 arguments 是合法 JSON，佔位也得是 JSON |
| 頭尾各留一段 | 腦還看得到一點樣子 | 省得少；佔位裡夾原文，品質也不一定比全清好 |

## 我定的預設（細節照原則自己定，Q1 之外不問）

- **清什麼**：`role: tool` 列的 `content`。列本身留著（OpenAI 格式要求每個 tool_call 都有對應的 tool 列），只把內容換成一行英文佔位，寫出原本幾字、哪支工具、原文在 `history_removed.jsonl`。
- **留什麼**：最後 3 則工具輸出（跟 Anthropic API 的 context editing 預設 `keep: 3` 同數；拿來當材料，不是照抄）；最後一組工具呼叫的結果一律留（做到一半壓時腦正要看它）；短於 300 字的不清（佔位就要 90 字，清了等於沒省）；已經是佔位的不再清。
- **arguments 第一版不清**：省的只集中在寫檔多的 agent，壞處（腦照抄佔位）沒驗過。之後真的有 agent 卡在這裡再開。
- **原文去哪**：照現在 `history_removed.jsonl` 的格式接一列 `{removed_at, op: "clear_tools", line, message}`（`message` 是整則原 tool 列），跟 compact、summarize 同一套「改掉的原文搬到旁邊」。
- **什麼時候清**：在 `compact.ask` 之前（idle 與 think 兩條路都是），先清、再算要不要叫腦。清跟摺一樣要「讀 → 寫暫存 → 指紋沒變才改名」（照 `compact.replace` 的做法），history 中途變了就重來，三次不成就放棄清、照舊摘要。
- **快取**：清會改到 history 前段，下一次請求從被改的那列起不中快取，一次性的；摘要本來也一樣。

## 「清完還不夠才摘要」的門檻（Q1 選了要省才用得到）

- body 沒有 tokenizer，用量測過的換算估：`清完估計 ≈ 最後一則 think 的 prompt_tokens − 清掉的字數 ÷（think/request.json 字數 ÷ 那次 prompt_tokens）`。四份樣本的換算值穩定在 3.2～4.2，夠估量級。
- 視窗照 `context_wrap` 同一套（`aos.agentlib.context_use`：kernel 公開的 pack `context`，hook 的 `config.window` 蓋過）。
- **清完估計低於門檻的一半**（門檻讀生效的 `context_wrap` 格的 `config.percent`，沒掛或沒寫＝35，一半＝17.5%）才省掉摘要；只剛好掉到門檻下面的話，幾輪後又會觸發、又改一次前段斷一次快取，不如這次就摘要。
- 讀不到視窗或沒有任何 think 讀數（例：人在全新 agent 上寄 `/compact`）＝照舊摘要，不猜。
- 清完沒東西可清（例：剛清過又寄一封）＝不重清；估計已低於一半就照 11-20「當成正常做完」回 `compact not needed`，不然就摘要。
