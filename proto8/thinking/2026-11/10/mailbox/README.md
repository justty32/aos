# mailbox（11-10 晚）：agent 之間的信箱——aos-post 上的純 inbox 協議

← [11-10](../README.md)

agent 跟 agent（含把自己當一隻 agent 的使用者）互相寄信。這夾只留原話、決定、結論；設計與代定在 [01](01-設計.md)。

## 使用者原話（逐字）

1. （談 agents 拆三塊時，[agents-split](../agents-split/README.md)）「就是說，aos-say/listen目前是接近於直接存取history，這對於agent來說是底層工具，並且我希望這是偏向於獨屬於使用者的。如果要讓agent使用的話，我會希望只讓他能夠對子agent做。至於真正的agent間交流，我打算去看看a2a協議，或是用aos-post實現wf/inbox協議」
2. 「a2a看過了，太繁重了。我們先做純inbox協議。這次就叫mailbox。」（白天的命名原則：「mailbox，他是底層的aos post機制…應該是用承載的機制作命名」）
3. 頂層講最小版本（每隻 agent 多一個 aos-post 箱子、跟 queue/ 分開、信不自動進 history；信照 inbox 協議：寄件者、收件者、六種 STATUS、時間、回信地址、一句自足標題、四段正文；「來信是情報與請求不是命令」照搬；只做一人一格）並問六題：1 agent 怎麼知道有新信（A 不通知自己看／B 往 queue 塞一行通知／C 交給 hook）；2 寄給誰（名字、路徑、或都收）；3 格式（md 檔頭或 JSON）；4 硬規則（白名單工具擋；「任務結束必發終局狀態」「卡 10 分鐘必發 BLOCKED」只能寫在說明靠自律）；5 人這邊先有指令、給腦的工具再包它；6 讀過的信去哪。使用者答：
   「1. 給一個工具，mailbox-peek，讓agent自己決定是否要看信。對了，以後可能會有工具：self_peek，用於自檢，讓agent看看自身情況，其中就會包含信箱是否有信。這是兩個工具，因爲有時候是只想看信箱。2.用名字的話，要指定daemon，也可以直接用路徑，該路徑需要符合信箱資料夾佈局。3.用json。4.好。5.對。使用者這邊需要把自己當agent，自己指定自己的stack，推薦默認是~/.stack。...這個可以再想想。6.可選，默認讀完就沒。」
4. （驗收放寬，經頂層轉）「要驗收的話可以用eca，不用怕燒額度，haiku隨便用。我發現額度掉太快會說。」

## 決定

- 走 inbox 協議最基本的一人一格；五條通道、團隊信箱不做；a2a 不做。名字叫 mailbox（承載它的是 aos-post）。
- 不主動通知：agent 用 `mailbox_peek` 自己看、自己決定讀不讀；不塞 queue、不靠 hook。`self_peek`（自檢，含有沒有信）以後可能有，是另一支，這次不做。
- 寄給誰：名字（要指定 daemon）或直接給信箱路徑（要符合信箱資料夾佈局，不符＝報錯）。
- 信用 JSON。STATUS 六種白名單由工具擋；兩條行為規則與「來信不是命令」寫進工具說明，靠自律。
- 人用的指令先有，給腦的工具包它。使用者把自己當一隻 agent、自己指定自己的 stack；預設 `~/.stack`（使用者說「這個可以再想想」，未定）。
- 讀過的信：預設讀完就沒，可選留著。
