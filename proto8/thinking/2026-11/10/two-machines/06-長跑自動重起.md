# 長跑自動重起

## 旗標

```
aos-agent ctl add --auto-restart [其他旗標] XXX
aos-daemon-ctl add --auto-restart [其他旗標] XXX
```

- 布林旗標，沒有值。作用只有一件：掛子信裡那一列多一個 `"auto_restart": true`——daemon 本來就認這個 key（11-06 no-pid P6），表上本來就會記。不動任何格式。
- 改的地方：`py/daemon_ctl/entry.py` 的 `add_letter` 多一個參數、兩支指令各多一個旗標與一行說明。
- 已經掛上的想打開：`aos-agent ctl rm <名>` 再 `add --auto-restart`（`rm` 不刪 stack，接著原來的做）。
- 開了之後的行為（daemon 現成的）：退了就重起、不看結束碼；`stop` 照樣停得住（留 stopped）；根收工時睡、開門時醒。
- **只給常駐的 agent 用**。「射後不理」那種（eca 用 `--on-empty stop`，信箱空就結束）加了會變成結束→重起→馬上又結束，三次就被判停。說明裡寫一句。

## daemon 現有的保護是什麼、夠不夠

現有的只有一條（[tend.cpp](../../../../impls/aos-daemon/src/daemon/tend.cpp) `look`）：**重起後 3 秒內又退，連續 3 次＝留 `stopped`、原因寫「restarted 3 times in a row」**。沒有延遲、沒有退避。

| 情況 | 現有保護下會怎樣 | 夠嗎 |
|---|---|---|
| 定義寫壞、設定檔壞（每次馬上失敗） | 三次就停、原因在表上 | **夠**，這正是它該擋的 |
| fsm：LM Studio 剛好在重開、litellm 回 502（kernel 馬上回錯） | 重起→從 wait 重寄同一份請求→馬上又錯→**幾秒內三次、判停** | **不夠**：暫時性的失敗撐不過 3 秒 |
| fsm：kernel 逾時（120 秒才回錯） | 每 120 秒重試一次、永遠不會被判停 | 夠（不空轉），但看不出它在反覆失敗 |
| eca：額度用完、登入過期、逾時 | 那批信已收→重起→信箱空、閒著。**不會空轉**；但下一批信進來又整批交出去、又全掉 | **不夠**：額度窗那幾個小時，進來幾封掉幾封 |

## 補的東西：失敗後冷卻（Python、兩個地方、不動 daemon）

失敗時在這隻的 stack 寫一個 `cooldown.json`（不進 git）：

```json
{"failures": 4, "until": "2026-11-10T02:41:07Z", "at": "2026-11-10T02:33:07Z",
 "code": "CliFailed", "reason": "claude exited 1: usage limit reached", "dropped": 3}
```

| | 寫的人 | 冷卻期間 | 冷卻到了 |
|---|---|---|---|
| **eca** | `aos-eca-turn`：交出去之後的失敗（`CliFailed`、`ReplyMissing`） | **不收信**、退 0 照常空轉——信留在 `queue/new/`，不會被吃掉 | **只拿最舊的一封去試**；成功＝刪 `cooldown.json`、下一輪恢復整批收；失敗＝那一封掉了（裁定 5）、次數加 1、再冷卻 |
| **fsm** | `wait.py`：`BrainFailed`、`SendFailed` | 退 10（留在 wait、不寄） | 重寄同一份請求（本來就是重試，不掉信）；成功＝刪檔 |

- **間隔**：30 秒、1、2、4、8、15、30 分鐘，之後固定 30 分鐘。成功一次就歸零。
- **額度用完時**：最多每 30 分鐘試一次。一次試探的成本是起一次 claude、馬上被拒，幾乎不花額度；eca 每次試探最多掉一封。五小時的額度窗最壞掉十封左右，而不是進來幾封掉幾封——這個數字能不能接受是 [09 題 2](09-衝突與要裁的.md#題-2額度用完那幾個小時的信)。
- **為什麼失敗還是退 1、讓 daemon 重起**，而不是自己吞掉：結束碼的意思不變（P-20「停下等人」）、daemon 的紀錄照樣有這一筆；沒開 `--auto-restart` 的 agent 行為跟今天完全一樣（停著等人，只是多了一個檔說明原因）。重起之後它在冷卻裡活超過 3 秒，所以不會撞到「三次判停」。
- **寫壞了的定義不受影響**：那種失敗不在上面兩個點，照舊三次判停。
- **時間用牆上時鐘**，不用樹的鐘：要等的是外面的服務。兩台時鐘差幾秒沒差；殘留的舊檔 `until` 早過了，頂多讓下一次變成「只拿一封試」。
- eca 一輪最長 10～15 分鐘卡住的情況由現有的 `timeout_ms` 管，不另加。daemon 另有現成的 `stuck_after_ms`／`restart_on_stuck`，這輪不接旗標。

## 停著時信怎麼累積

- 冷卻中、`stopped`、`sleeping`、整棵收工：寄給它的信都落在它 stack 的 `queue/new/`（maildir，一封一個資料夾），沒有上限、照寄的順序。醒來照順序處理。
- 冷卻結束後第一輪只拿一封；成功後下一輪把剩下的整批一起交（11-03 的批次照舊）。
- 信跟著 image 走：A 機累積的信，到 B 機開工後照樣處理。
- 寄信的人不會收到「對方在冷卻」的通知（`say` 只管投遞）。要知道就看下面。

## 一眼看出誰在反覆重起、為什麼

`aos-image status`（[03](03-收工與開工.md#aos-image-status)）每隻一列：`RESTARTS`（`failures`）、`COOLDOWN`（到幾點、第幾次）、`LAST ERROR`（代號＋原因）、`QUEUE`（積了幾封）、`dropped`（這一串失敗掉了幾封）。資料全來自各 stack 的 `cooldown.json` 與 `queue/new/`，不問 daemon、樹沒在跑也能看。

細節要追：那隻的 `stderr.txt`（每次失敗一行 `aos-eca-turn: error: CliFailed …`；太大時清道夫封存到 `stderr_archives/`）；被判停的看 `aos-daemon-ctl ls` 的 `REASON`。

沒做的（記給大修）：daemon 自己的重起退避（`restart_delay_ms` 之類）才是通用解，但要動 C++ 與表的欄位；認得「額度用完」的字樣直接睡到重置時間，要靠 CLI 的錯誤訊息、沒實跑不敢做。
