把現役所有指令與子命令攤成一棵 `aos <a> <b> <c>` 的樹，照使用者 11-10 的新原則（連字號程式與子命令視同一樣）檢查撞名、層次與讀起來怪的名字。

## 使用者原話（11-10，頂層轉達）

> 「我這邊給個原則，跟這個不太有關係，就是突然想到：aos體系下的指令，sub command這塊，aos-daemon-ctl和aos daemon ctl視同一樣，在設計時也必須遵守這個規則。至於為何不做aos-daemon ctl，是因為程式架構上，兩者拆開會比較好維護，不然aos-daemon一個程式要負責那麼多子指令功能。對，名字上就隨意，至於要不要用-弄成不同程式，就是看好不好維護，就這樣」

頂層的轉述（非原話）：整個 aos 指令是一棵 `aos <a> <b> <c>…` 的子命令樹；用連字號拆成獨立程式還是寫成同一支的子命令，只是維護上的實作選擇，設計上兩者等價。這條原則會另外寫成條文；本檔只照它檢查，只列發現與選項，不代定。

## 發現

### T1　`aos daemon ctl` 與 `aos agent ctl`：同一個節點名、十個同名動作、語意不齊（最大的一項）

兩個 `ctl` 底下 add、rm、ls、where、stop、start、sleep、wake、pause、resume 十個字一模一樣，而且 `aos agent ctl` 的這些動作不只管 agent——表上任何一列都收（實跑：`aos-agent ctl rm t4` 刪掉了一個不是 agent 的列與它的 stack；`aos-agent ctl ls` 列出 `_clock`、`_sweeper`）。照新原則把兩者當同一棵樹來看，同名動作的差別是：

| 動作 | `aos daemon ctl` | `aos agent ctl` |
|---|---|---|
| 指名字 | 位置參數 | `-t`（rm 例外） |
| `add` | 任何東西；印信名；撞名安靜成功；ws 預設 daemon 的 | 只收宣告了 aos-agent 介面的；印 stack；撞名報 `InstanceExists`；ws 預設現在站的地方；設了 `AOS_KERNEL` 就經判官 |
| `rm` | 留 stack | **刪 stack**（終端上會問） |
| `ls` | PHASE／PID／CODE；尾行講上司 | STATE（看得到 paused）／QUEUED；`-l` 加健康欄 |
| `where` | `--stack 名字` | `[--stack｜--ws] -t 名字` |
| stop 等六個 | 印信名或數字；已到位＝退 1 | 印一句話；已到位＝退 0；等 daemon 做完才回 |
| 只有這邊有 | prune、poke、ping、shutdown、sweep | state、who |

aos-daemon-ctl 的 help 自己有一句定位：「Letters always go straight to this daemon's ctl mailbox; AOS_KERNEL is not read. To go through the judge (AOS_KERNEL), use aos-agent ctl instead.」——也就是說兩者的本意是「直達的底層」對「經判官、替人多做幾步的上層」。這個分工合理，但名字上看不出來，同名動作的小差異（尤其 rm、已到位、輸出）沒有一個是分工需要的。

選項（方向題，README Q2）：
- 甲：分工照舊，把同名動作的寫法與後果對齊到「只剩分工必要的差別」（指名字兩邊都收位置參數與 `-t`、已到位都退 0、`rm` 的差別在成功行與 help 第一行講明或改成同一預設）。後果：兩支都要動，但都是命令列與訊息層。
- 乙：`aos agent ctl` 只留 agent 專屬的（add、rm、state、who），其餘八個生命週期動作只留在 `aos daemon ctl`。後果：樹最乾淨；但 `aos-agent ctl stop` 那些「印一句話、等做完、提醒還有幾封信」的好處要搬到 daemon-ctl，或就沒了；agents 工具（lv6）等呼叫者要改。
- 丙：不動，只在兩支 help 頂端各加一張對照表。後果：最省；差異繼續存在。

### T2　`llm` 出現在兩層、是兩件事；`aos llm kernel` 掛在 `aos llm` 底下卻不是同類

- `aos llm …`（send、recv、ask、regret、ls）＝「寄請求給問腦總機」。
- `aos agent llm …`（show、set、reset）＝「這隻 agent 的腦設定」（寫的是 `llm.json`）。
- `aos llm kernel kernel.json`＝「總機自己跑一圈」，是 daemon 的身體，不是人下的子命令；但在樹上它跟 send／ask 是兄弟。

同名不同義的程度：中。兩個 `llm` 不會打錯（層不同），但 `aos-agent llm set endpoint=…` 跟 `aos-llm ls`（列 endpoint）其實是一對（先 ls 看有哪些、再 set），help 互相沒提。`aos llm kernel` 的位置問題是「一個節點既是指令（有自己的子命令）又是另一支程式的前綴」——`aos daemon`／`aos daemon ctl` 同型（見 T4）。

選項：只補說明（`aos-agent llm` 的 help 加一句「available endpoints: aos-llm ls」）；名字要不要動留大修。使用者設計-53～55 已有 kernel 相關待裁題，不另開。

### T3　`tools` 出現在兩層：`aos tools` 與 `aos agent tools`

意思相同（都是工具通訊錄），後者是「這隻 agent 自己那份」。問題不在名字而在動作不齊：`add` 的參數形狀不同（`[--name N] PATH` 對 `NAME PATH`）、後者沒有 `--envs`／`--env-file`／`--path-json`、沒有 `call`／`override`、多一個 `reset`。照新原則，同名節點底下的同名動作應該長一樣。細節 [01](01-aos-agent.md) A9；改法 [08](08-改法與施工順序.md) 乙1。

### T4　一個節點同時是「吃位置參數的指令」與「別支程式的前綴」

`aos daemon daemon.json`（跑一台 daemon）與 `aos daemon ctl …`；`aos llm ask` 與 `aos llm kernel kernel.json`。現在因為是不同執行檔所以不衝突；照「視同一樣」來讀，`aos daemon X` 的 X 可能是設定檔也可能是 `ctl`。使用者原話已經說明為什麼拆（「不然aos-daemon一個程式要負責那麼多子指令功能」），所以這不是要改的東西；只是之後設計新指令時要留意：**同一節點底下，位置參數與子節點名不能混**（例如不要再做一支 `aos-exec-something`）。列為條文可以考慮帶上的一句，由使用者決定。

### T5　`aos eca`：有子節點、沒有本體；`aos eca screen` 跟 `aos agent open／close／watch` 是同一件事

- `aos-eca` 這支不存在（`cmd/aos-eca/bin/` 底下是 turn 與 screen 兩支）。樹上沒問題（節點可以只是前綴）。
- `aos agent open／close／watch` 把 `aos eca screen open／close／watch` 壓平了一層（少了 `screen`）。同一個動作在樹上兩個位置、深度不同；一個是給人的入口、一個是被轉呼叫的實作，aos-eca-screen 的 help 有講明。可以接受。
- 讀起來怪的是 `aos agent watch` 對 `aos agent listen --follow`：都是「跟著看」，一個看畫面事件、一個看問答，help 互相有指路（`ScreenMissing … follow answers with aos-agent listen --follow`）。

### T6　同名動作跨節點的意思

| 動作名 | 出現在 | 一致嗎 |
|---|---|---|
| `ls` | daemon ctl、agent ctl、agent tools、tools、llm、feedback | 一致（列東西）；長相不一（[06](06-跨指令不一致.md) X7） |
| `add`／`rm` | daemon ctl、agent ctl、agent tools、tools、feedback(add) | 一致（登記／拿掉）；`rm` 的後果不一（T1） |
| `regret` | post、llm | 一致（撤回還沒被接的信）——好 |
| `send` | post、llm | 一致 |
| `where` | json（值從哪個檔來）、daemon ctl／agent ctl（stack 在哪） | **不同義**，不同節點、不會打錯 |
| `show` | lock（鎖是誰的）、agent llm（腦設定）、feedback | 一致（印一個東西） |
| `get` | json、tools、agent tools | 一致 |
| `open／close／watch` | agent、eca screen | 一致 |
| `reset` | agent tools、agent llm | 一致（刪掉自己那份、回到定義） |
| `stop` 對 `shutdown` 對 `close` | 停一列／停整台／關畫面 | 分得開——好 |
| `sweep` 對 `sweeper` | `aos daemon ctl sweep` 與 `aos sweeper` | 同一功能掛兩處、預設不同（[05](05-其餘指令.md) O7） |
| `check` 對 `prune` | `aos json check`；`aos daemon ctl prune` 不加旗標其實只是 check | prune 名實不符（[02](02-aos-daemon-ctl.md) B10） |
| `state`／`status` | agent ctl 兩個都收 | 同義詞並存；`aos daemon ctl` 沒有看單一列的動作 |
| `env` | `aos json env`（寫一個 `$env` 指示詞） | 跟「環境變數」「`.env` 檔」「`--envs`」同字，讀起來要想一下 |

**沒有發現**「某支程式的子命令名剛好等於另一支連字號程式的尾名、卻是不同功能」的硬撞：`ctl`（aos-agent 的子命令）與 `-ctl`（aos-daemon-ctl 的尾名）是同一類功能（T1）；`llm`（aos-agent 的子命令）與 `aos-llm` 是相關但不同的事（T2）；`tools`（aos-agent 的子命令）與 `aos-tools` 是同一類（T3）。最接近硬撞的是 T2。

### T7　在樹上讀起來怪的名字

| 名字 | 讀起來像 | 其實是 | 分類 |
|---|---|---|---|
| `aos clock` | 看現在幾點 | 把鐘檔的數字加一 | 只是不熟（零件） |
| `aos post` | 發文 | 資料夾信箱 | 只是不熟（底層名，使用者已定位） |
| `aos grow` | ？ | 把一格指令升級成檔／資料夾 | 只是不熟（lv6） |
| `aos daemon ctl prune` | 修剪 | 不加旗標只檢查 | 補說明 |
| `aos daemon ctl poke` 對 `ping` | 都是「戳一下」 | poke＝叫它現在醒來看一眼（不等回應）；ping＝問它還在不在（等回應） | 補說明（頂層 help 各一行已分得開） |
| `aos agent ctl who` | 誰？ | 這個 stack 是哪一隻的 | 只是不熟（給工具用） |
| `aos eca` | ？ | external coding agent（外部的 claude／codex） | 縮寫只在 aos-eca-turn 的 help 第一行解釋一次 |
| `copy-out` | — | 不在樹上、沒有 `aos-` | 命名題（[03](03-aos-exec與copy-out.md) C5） |
| `aos llm ls` 的「endpoint pack」 | — | 一個可選的腦 | 補說明 |
| `aos daemon ctl sleep` | 等幾秒 | 叫一個列睡下（SIGTERM） | 設計如此；跟 shell 的 `sleep` 同字 |

### T8　層次合不合理（整體）

- **合理的**：`json／lock／post／fsm／loop／exec` 各管一件事、互不重疊；`eca turn`／`eca screen` 是同一個東西的兩個面；`daemon ctl` 掛在 `daemon` 底下。
- **可以問的**：
  1. `aos sweeper`、`aos clock` 是「只給 daemon 表上某一列用的零件」，卻在樹的第一層跟 `agent`、`tools` 並排。它們不是人會下的指令。（選項：不動；或之後收到 `aos daemon` 底下。屬命名／大修。）
  2. `aos mcp` 的對象是工具通訊錄，功能上是 `aos tools` 的一個出口（「把這份通訊錄用 MCP 端出去」）；現在在第一層。（選項：不動；或看成 `aos tools mcp`。）
  3. `aos agent` 底下五組（ctl、說話、畫面、tools、llm）裡，說話三個與畫面三個是直接掛在 `agent` 下的動作，另外三組多一層；`ctl` 這層收的其實是「生命週期＋查詢」。（選項：不動。壓平或加層都會動到每天打的指令，不建議現在碰。）

這三點都不是「日常會一直撞到」的，全部歸留大修；只有 T1、T3 進這輪的快選題。
