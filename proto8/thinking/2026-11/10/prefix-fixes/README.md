## 使用者裁定（11-10 快裁，大修時可重看）

- 快裁的性質：「因為是快速抉擇，主要靠直覺，其中可能有些錯誤，但沒關係，大修的時候再來處理」
- 不趕：「好。不要因為太敢就省略東西，時間沒有緊急到那樣。」（「太敢」＝太趕）→ 61 列、驗收、文件、大修材料同步都做完，做不完跨日。
- **q-stderr（設計-34）不照原選項**，改做常駐清道夫，另有規劃員出設計，本輪不做：「1. 錯誤記錄檔...我記得那是daemon轄下的procs那邊的東西。幫我做一個daemon的常駐loop proc，類似clock那樣，每十分鐘跑一次，對各種東西進行清理與封存。stderr就是封存，封存後的是git ignore。然後我記得daemon-ctl有一個指令是進行清理，沒有的話做一個，就是把這些封存的一次清掉。」「那個常駐proc，有點類似清道夫，清理與封存的同時，也會看到那些殭屍行程，會幫忙清掉。然後daemon ctl的指令...兩個吧，一個是主動叫一次清道夫，另一個是把封存的東西刪除。也可以合併，弄成--purge」
- **q-wait（坑-74）**：「2.等腦回信沒前線...理論上這是要自己承擔的風險。但是確實也可以如你這樣所說，就是自己當monitor，過一段時間沒收到，那就印提醒，或是直接失敗。」→ 頂層取輕的：選項 A（等超過 10 分鐘印一行 warning、之後每 10 分鐘再印、照樣等，不判失敗、不動格式）。
- **坑-52 的範圍**：「3.按照你的推薦」→ 所有經 aos-inst 起的子程式都套 PDEATHSIG。用途（說明為什麼要驗接回與 eca）：「我要拿aos去做知識庫運用，並且要長時間做事，應該會大量使用eca。」
- open-11 子命令代定名 `shutdown`；其餘 01／02 標「代定可翻案」的照代定做，代定表在 [04](04-施工結果.md#代定表可翻案)。
- **跨機輪流跑**（坑-73、坑-92 的路徑寫法因此重做）：問「兩台是各跑各的，還是同一批 agent、同一份知識庫要兩台輪流接著跑？」答「後者」；「所以就請盡量支援相對路徑...」「會頻繁遷移，透過github」→ 寫進會進 git 的檔的路徑不含 home、使用者名、repo 的機器位置；使用者用選項框裁 A「本機捷徑錨點 (Recommended)」，選項原文：「每個資料夾放一條不進 git 的捷徑 .aos-proto8 指向這台的 repo，進 git 的檔寫經過它的相對路徑。兩台愛放哪就放哪；換台後要多跑一個重建捷徑的指令（可包進開工指令）。」→ `copy-out --relink`（見 [04](04-施工結果.md)）。
- **線 6 改名**（結果在 [05](05-procs_requests改名.md)）：「對了，就是說，有一個我想要改名的地方：procs_ctl_mailbox，這太長了，有點奇怪。我覺得可以將其改為procs_ctls。」「或是procs_requests」「我記得aos agent那邊也有一個queues，也可以改成request/ctls之類」「queue先不動吧。就是說，mailbox，他是底層的aos post機制。但我們是將其作為其他機制的承載者，我們不該直接拿mailbox做命名。應該是用承載的機制作命名」「1.requests。2.不用。然後有序的...有序無序感覺也沒差」（1＝改成 procs_requests；2＝其他帶 mailbox 的機制名不跟著改；最後一句是隨想、不是派工）。
