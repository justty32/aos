# 實測（11-10 晚，WSL ext4 的 `/tmp/tpl-cp-inv/`，做完已刪）

**一句話**：拿掉 symlink、範本自帶 `.env` 的版本，只 export `AOS_HOME` 就照答，搬家也照答；把 `AOS_HOME` 寫進 `.env` 的話，0 個 export 也照答。留著 symlink 再用 `cp -r` 的話，agent 起不來。

## 怎麼搭的

- **假 proto8**：`p8/{lib,py,knowledge,cmd,impls}` 是 symlink 到 `~/repo/aos-tools/proto8` 的同名夾；`p8/templates/`、`p8/kernel/` 放手改過的範本。做法是先 `copy-out` env 模式抄一份，把 `AOS_PROTO8` 換成 `AOS_HOME`，再把 JSON 蓋回原範本的 `cp -rP` 複本上，**symlink 照原樣留著**。這樣 symlink 在「repo 原位」解得開，跟範本真的放在 repo 裡一樣。
- 每輪都先把殼裡的 `AOS_*` 全部 unset，`AOS_HOME=…/p8`；指令用 `~/.local/bin`（就是這份 clone 的工作樹）。
- 每輪：`aos-exec --stack stacks/llm def`（llms）→ `aos-exec --stack stacks/root defs`（proj）→ `aos-agent -d stacks/root ctl add --auto-restart -w . defs/ann` → `say`／`listen`（假腦會叫一次 wall_clock）→ 在 `defs/ann` 直接 `aos-tools call memory` → 兩邊 `shutdown`。

## 結果

| 輪 | 做法 | 結果 | 卡在哪 |
|---|---|---|---|
| r1 | 留 symlink 的範本用 **`cp -rL`** 抄出、export `AOS_HOME`＋`AOS_LLM_KERNEL` | **通**：`FAKE ANSWER to: question r1 (tool said: …)`、memory 列得出知識庫。整夾 `mv` 到 `moved/x/y` 再起：**通**。tree 裡沒有舊路徑（log、jsonl 除外） | — |
| r2 | 同一份範本 `cp -r`（symlink 原樣抄）、**AOS_HOME 不設** | 起得來，但 agent 一跑就停在表上 | `aos-json: error: DirectiveBad environment variable AOS_HOME is not set` → `aos-tools: error: DirectiveBad tool agents (…tools.json#/tools/agents): directives cannot be resolved` → `agent-fsm: error: ToolsBad aos-tools ls exited 1`（在 `procs/ann/stderr.txt`）。`listen` 只看得到 `RunFailed run 12: fsm.json failed with exit code 1`。llm kernel 那邊是 `aos-llm-kernel: error: DirectiveBad environment variable AOS_HOME is not set`，每一拍重試 |
| r3 | `cp -r`（**symlink 斷了**）、AOS_HOME 有設 | agent 起來 3 秒內就停，冷卻後再試也一樣 | `aos-tools: error: ToolDefMissing tool memory (…/tools/memory…): … is a dir and needs _tooldef.json inside`。訊息沒說「那個 _tooldef.json 是斷掉的 symlink」。奇怪的是 `aos-tools call memory` 照樣跑得動（call 不需要 tooldef），壞的是 `ls` |
| r4 | **拿掉 `tools/` 夾**：`tools.json` 的 memory 改成 `{"path": {"$env":"AOS_HOME","$path":"/lib/agent/memory"}, "env": {"AOS_MEMORY": {"$env":"AOS_HOME","$path":"/knowledge/aos"}}}`；root 範本 `.env` 帶 `AOS_LLM_KERNEL=${AOS_WS}/../llms/stacks/llm`；**`cp -r`、只 export `AOS_HOME`** | **通**（0 條 symlink）。問腦的 `think/request.json` 裡有 `Knowledge base root (from tool memory…)`，表示 brain 的 `--memory` 有拿到根。整夾 `mv` 再起：**通** | — |
| r5 | 同 r4，**殼裡 0 個 export**；`AOS_HOME=…` 寫進 `proj/defs/.env` 和 `llms/def/.env` | **通**。`ctl add`、`say`、`listen`、`shutdown` 都不需要殼裡有 `AOS_HOME` | 只有使用者自己在殼裡打 `aos-tools call／ls`（或 `aos-agent tools ls`）時要 `AOS_HOME`：`DirectiveBad … AOS_HOME is not set` |
| r6 | `AOS_HOME` 只寫在 **agent 自己的** `defs/ann/.env`（根的 `.env` 沒寫） | **通**：daemon 起 agent 時會讀 agent 資料夾的 `.env` | — |
| r7 | 範本放在原位、範本 `.env` 寫 `AOS_HOME=${AOS_CD}/../..`、不 export | 原地掛：**通**。把它 `cp -r` 到 `defs/bob` 再掛：**壞**，而且錯得不明顯 | `aos-tools: error: PathMissing tool agents (/tmp/…/proj/lib/agent/agents, …)`：AOS_HOME 默默變成錯的地方，訊息完全沒提 AOS_HOME。**所以範本 `.env` 不要放這種「只在原位對」的預設** |
| r8 | 根的 `.env` 末尾加 `AOS_HOME=${AOS_HOME}`（必填檢查） | 沒設：`aos-exec: error: DotenvBad bad .env: …/defs/.env line 6 (variable referenced by ${...} is not set)`，**起根當下就退 1**。有設、或上面一行自己寫了 `AOS_HOME=…`：照常起 | — |

另外驗了（只解指示詞、列工具，沒有跑起來）：eca-claude、reviewer 用 `cp -rL` 抄出後 `aos-tools ls` 列得齊，路徑指到 `p8/lib/…`；reviewer 的 `fsm.json` 解成 `p8/templates/agent-fsm/brain.py`；judge-llm 抄出去後 `aos-exec` 跑得起來（報自己的 `ArgumentsBad`）；llm-team 的 `exec` 解成 `p8/lib/aos/llm_forward`；daemon-judge 的 argv 要等 aos-exec 給了 `AOS_CD` 才解，這是正常的。

對改好的範本跑 `copy_def.Rewriter`（env 模式）：agent-fsm（無 symlink 版）、reviewer、llm-kernel、daemon-root **改寫 0 處**。eca-claude 因為還留著 symlink，照舊把它們換成複本。

每輪結束都 `pgrep` 過，沒有殘留行程；`/tmp/tpl-cp-inv` 已刪。
