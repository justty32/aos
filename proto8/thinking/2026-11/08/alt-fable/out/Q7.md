# Q7：錘子設計圖 v1（整合 Q1～Q6 與經驗庫 E0）

## 一、ELI5 結論

錘子＝一棵**活的資料夾樹**。每個資料夾是節點：有自我介紹、能跑的入口、收信的信箱，並指向「誰審我、誰改我」。公式、Python 搜尋器、LLM agent 長得一樣，差別只在入口跑什麼。lv1 錘子＝把 r08 的 `grow/` 學習迴圈拆成這種樹，掛在 aos-daemon 下，每 tick 跑一個 epoch；使用者 `cd` 進去看帳、看健康、往信箱丟一行字就能干預。

lv1→lv2 只量一件事：**樹內節點（不是人、不是 agent 手改）成功改了一個審查或改進節點，且那條管線的盲測不退、自己的開銷不超過 1.5 倍**。r07、r08 兩輪旋鈕全 Δ=0 說明 lv1 現在「改不動自己」，所以 v1 的重點不是再轉旋鈕，而是把人寫死在 Python 裡的門檻、拆法、判準**搬成資料夾裡的可搜尋節點**，先從最有料、最便宜能評的守門判準搜起，再把殘差分成「餓死」與「飽和」決定往下拆或往上改。

Q1～Q6 大方向一致，但有七處互相打架（§8），其中四處得使用者裁（§11）；最大一題是**錘子的第一個病人是空種子樹還是舊手寫樹**，我推薦雙軌。

## 二、設計圖

### 1. 總綱：三種角色、四層、一條 lv2 門

- 節點 `kind` 只分 `program`／`agent`／`generator`；審查、改進是**角色**（被別人 `review`／`improve` 指到），同一支統計程式可審十個節點（Q1）。
- 被改的東西分四層：0 積木、1 求解器旋鈕與拆法、2 審查與改進節點的參數或程式、3 判準與預算政策（Q1＋Q4）。第 3 層 r09 只有人能碰。
- **lv2 門**（修正 Q1）：`ledger.jsonl` 出現 `layer:2`、`by` 為樹內節點、`accepted:true` 一列，並通過**該管線**的不同源判準：學習曲線管線用 AUC_L ≥4/5 不退、H24 淨增 ≥0；守門管線用 evaluation 收輪誤擋 0、答錯不增。代價：審查＋改進節點每 pass 開銷 ≤1.5 倍。輔助數字 `self_share`、`layer2_attempts`（r09 目標 ≥5、accepted ≥1）。
- 經驗：支持 T1（改進節點第一產出是原語或拆法，不是參數）、條 24（旋鈕到頂、改進者本身要能被改）、意見 8（不要求單調上升，看多輪方向）。警示 條 11（放寬門檻的假進步，所以效果只用固定題組曲線量、不用 accepted 數）。

### 2. 節點模型與記錄（Q1 為地板，吸收 Q2、Q3 的節點內檔）

`_metainfo.json` 補六個選填 key：`io`（格式名或 seedlib `sig`）、`review`、`improve`（指標路徑，≤2 層）、`born{epoch,by}`、`impl{level:agent|tool|prog, llm_share, prev, guard}`（Q3）、`ladder{...}`（Q2）。

| 放哪 | 檔 | 格式 | 誰寫 |
|---|---|---|---|
| 錘子根（權威） | `hammer/epochs/<n>/{runs,eval,residuals}.jsonl`、`stall.json` | `hammer-run/1`、`hammer-eval/1`、`hammer-residual/1`、`hammer-stall/1` | 根入口、`grow/stall.py` |
| 錘子根（權威） | `hammer/ledger.jsonl` | `hammer-change/1`＝現有 meta 列＋`target, by, layer, direction, judge` | 改進節點或判準程式 |
| 節點內（衍生快照） | `_health.json`、`_ladder.jsonl`、`shadow.jsonl` | 由 `review/stats` 從根帳算出，給 `cd` 看 | 審查節點 |
| 節點內（本體） | `_rule.json`／`judge.json`／`params.json`、`versions/`、`guard.json` | 各節點自己 | 改進節點，經 `candidate/` |
| 節點內（信箱） | `_gradients.jsonl` | node-pool 列，`case` 統一枚舉 `advice, hold, harden, thaw, force_rung, direction, pin` | 人、審查節點、`pool grad` |

Q4 的 `attempts.jsonl` 併入 `ledger.jsonl`；Q2 的 `_ctl/` 第二信箱取消；Q2、Q5 的 `freeze` 改叫 `hold`（別改我），Q3 的 `freeze` 改叫 `harden`（立刻固化），避免同字反義。`by` 由判準程式填，不由 agent 自填。所有格式進 `proto8/py/aos_metaopt/formats.py`，`node.py` 讀寫，arcagi 與 aos import 同一份。

- 經驗：支持 條 27（身體形式不由寫法決定）、條 29（干預通道以信件與資料夾為準）、鐵律 6（同質列走資料檔）。警示 條 26（帳一處寫，節點內只放衍生物，否則錢會算錯）。

### 3. 審查梯與固化（Q2＋Q3 合併成一套枚舉器、兩種病人）

**梯子**（Q2，嘗試順序按成本 L0 統計 → L2 專用替換 → L1 符號迴歸 → L3 LLM；L2 由 L1 的接受紀錄蒸餾而來，同一編輯簽名 ≥3 次、影子 2 epoch 命中 ≥80% 才 live）。**固化**（Q3）是同一支枚舉器換病人：把 agent／tool 節點最近 20 次 I/O 當 ground truth，找得到重現程式就固化並附 `guard.json` 前提檢查，不在前提內棄權、自動回 `impl.prev`；整塊找不到就依 trace → 殘差 → 見證三種拆法切子節點。進度只看 `llm_share` 降幅，拆出腳本但 `llm_share` 不降記成失敗。

三個判準各司其職，寫進 `hammer/frozen.json`，任何層不可改：

| 判準 | 用在 | 規則 |
|---|---|---|
| J-進步 | 旋鈕、拆法、往上長 | Q4 兩段：先數新解題（5 seed 全 ≥1、H24 不退、L 掉題 seed ≤1），全 0 才比 logcost ≥max(1,2SE)＋符號檢定 70% |
| J-不退 | 固化、分區、壓縮 | AUC_L ≥4/5 不退 **且** 成本降（枚舉節點和 ≥10% 或 `llm_share` ≥5 pp） |
| J-兩折 | 守門、aos 晉升門 | 折 A `right−3×wrong` 前 20 → 折 B right ≥基準＋2、wrong ≤基準，AB／BA 都過 |

錢：Q2 的報銷、分紅、`spend_cap`、`improver_cut` 全部**r09 只算不扣**（影子帳，`would_block` 只報），見方向題 4。

- 經驗：支持 T4、條 10（最底層是程式對真值）、條 7（固定成工具 −92% token）、T8（改進必須比生產便宜一個量級）、條 15（一條有理論依據的門勝過一堆經驗門）。反對／警示 條 6（殘差無結構就別硬蒸餾，固化前先看殘差分類）、條 33（只固化無關痛癢子功能，故用 `llm_share` 計成敗）、條 32（改進流程先不限用量，故錢只影子）。

### 4. epoch、殘差、停滯、往下／往上（Q4，吸收 Q2「上」的第二義）

epoch＝考一次、算殘差、改一次、記一筆。`stall.json` 每 epoch 判：`accepted=0` 且 `clean_P=0`、近解 ≥3 題 → **餓死 → 往下**（殘差簽名相同 ≥3 題開 `sub/<sig>/` 子節點，預算 ≤父的一半、深 ≤2、每次 ≤4 個）；`accepted=0`、`coverage ≥0.6`、近解 <3 → **飽和 → 往上**；兩者皆否 → `stop`（誠實報缺原語）。回放驗收：r08 `pool` 判餓死、r08 meta 判飽和。

「往上」拆成兩義並寫進 `direction` 欄：`up-params`（Q4：下一層改進者的 `params.json` 當搜尋空間，預算 ≤下層 1/4、只在 `up` 時排程、預期多半 Δ=0）與 `up-expr`（Q2：往產生器或 `propose` 寄信「缺特徵／缺拆法」，要新表達力）。r09 政策寫死：下 → up-expr → up-params。三道鎖：層 ≤3、(target, layer) 只建一次、凍結集不可寫。

- 經驗：支持 T3、條 8（停滯判準用整數事件與跨題 bootstrap，禁重跑方差）、條 3（餓死是主瓶頸所以往下先）、條 18（真值供給與改進程式同等重要）。反對 Q4 把「上」只定義成參數：條 1、條 24 實測參數層全 0，只有新原語與人手改優化器加過分，所以 up-expr 排在 up-params 前。

### 5. 用暴力搜節點樹本身（Q6＋Q1 的 layer-2 最小版）

把三種零件都寫成可枚舉的小 AST 或 JSON：守門 `review/guard/judge.json`（`hammer-judge/1`，`metaopt-ast/1` 的 S 式，特徵 10 個、常數白名單、深 ≤3；現行守門必須能寫出來當基準，400 題 trace 重判逐位相同）；拆法與預算 `solve/policy.json`（`hammer-policy/1`，進現有 meta 一回合一格）；CRN 判準 `review/crn/params.json`（**只記不搜**，校準列累到 ≥30 才准搜，r10）。全枚舉只用在「評一個候選只要查表」的地方（守門，10⁵～10⁶ 棵、CPU ≤10 分鐘）；要重跑曲線的維持一格一格動。鐵律：**審者的評分訊號不得與被審者同源**（本體←train；守門←training test 兩折；policy←L16＋H24；判準←校準集）。

這就是 Q1「讓 lv1 能改 layer 2」的最小辦法：`review/stats`、`improve/knobs` 的門檻參數搬進 `params.json` 列進 `targets`，守門判準由 `improve/guard_search` 真搜。

- 經驗：支持 條 5（對原始碼文字變異無效，只能對結構化旋鈕搜）、條 2（表示法是工程題不是能力題，沿用現成 AST）、條 16（合成變體才抓得到背答案）、T6（評分先做套利測試：`wrong ≤基準`、棄權不加分）。警示 條 9、條 17（evaluation 永不參與選；只收輪量一次）。

### 6. 規模與排程（Q5 裁到 r09 能用的部分）

區由簽章族＋同程式共用自己長出來，`cap 64`、`hot 16`，跨區 ×1.2 過路費、拆分合併走 J-不退。但空種子樹只有個位數積木，r09 任何門檻都觸發不了；所以 r09 只做三件事：`hammer/sched/`（錢買 CPU 份額、底線 10%、OOM 預算砍半、>400k 節點派 C++ `arcbatch`、LLM agent ≤2 隻在保留核）、`hammer/index/`（簽章→位置、`lookup`）、對舊樹 474 節點的**離線分區預檢**（多數票純度 ≥0.7 才算演算法可用）。記憶體照使用者既定規矩 16GB、workers ≤12、`nice 19`，Q5 的 24GB 不採。

- 經驗：支持 條 22（LLM 並行個位數、非 LLM 吃滿核心）、T10。警示 條 4（省節點不算進步，分區主指標是枚舉節點和，AUC_L 只是底線）、條 12（門檻先預核：「區數 ≥2」在空樹上結構性達不到，故改預檢）。

### 7. 活樹與干預（意見 7）

根 `~/code/playground-arc1/ws/hammer/`，`aos-agent ctl add --name hammer --ws ws ws/hammer`，daemon 每 tick 叫根 `_entry`＝一個 epoch；搜尋仍在 Python 程序內跑，資料夾是**權威來源**，pass 邊界重讀活檔（`knobs.json`、`policy.json`、`params.json`、`status`）。arcagi 現有 `aos/blocks`、`aos/pool`、`aos/meta` 不搬，當舊樹對照。使用者能做：

```
cd ws/hammer && cat epochs/7/stall.json ledger.jsonl | tail      # 看停滯判定與最近改動
cd review/guard && cat judge.json _health.json                     # 看判準與健康快照
echo '{"trace":".../trace.json"}' | aos-exec . --ws ../..          # 對一題重判
pool grad --def improve/compress --say "只抽 2 題以上共用" --score 0.5   # 投信
pool grad --def hammer --say "改往上" --score 0        # case: direction，下 epoch 覆蓋一次
aos-agent say -t propose "缺兩半拆法"                   # 對 agent 節點說話
aos-agent ctl pause hammer                              # 凍在 pass 邊界
```

每招在 `ledger.jsonl` 留 `by: human`。

- 經驗：支持 條 29（a2a 卡批准，信件與資料夾才通）、條 27。警示 Q1 風險：改到一半被讀到，`candidate/` 以外的改動一次寫完再改名。

## 五、要使用者裁的方向題（§11，最多 5 題）

1. **錘子第一個病人是誰？** A 空種子樹（純，但兩輪 Δ=0、梯子與分區沒料）；B 舊手寫樹（474 節點、133 公式、400 題 trace，有料但不是從零）；**C 雙軌（推薦）**：梯子、分區預檢、守門搜尋在有料的舊樹與 400 trace 上驗機制，**lv2 計分只認空樹曲線與 H24**。後果：C 工作量約多三成，但避免 r08「0 題過 train 所以什麼都學不到」；選 A 則 r09 很可能再交一輪否定結果；選 B 違背最終目標的「從零」。
2. **判準改兩段並收下 halves？** **推薦改**（Q4 兩段，第一段規則進凍結集、H24 不退硬條件），halves 記為接受但帶 `whitebox:true` 旗標。後果：主樹 AUC_L 帳面 32→48，有白盒過擬合風險；不改則 lv1 結構上永遠接受不了任何東西，lv2 無法出現。
3. **lv1 錘子裡 LLM 的配額。** A 完全 0；**B（推薦）**：只在 `stall.json` 為 `stop`（缺原語）時 `propose` 可叫一次，每 epoch ≤1 次、≤2k token，只寫 `candidate/`，計 `llm_calls_meta`，曲線 `llm_calls` 維持 0（比照 np21 q1:B 的先例）。後果：A 乾淨但冷啟動只能靠人；B 多一條訊號源，須防它把答案塞進候選（經 J-進步與 H24）。
4. **錢制 r09 影子還是實扣？** **推薦影子**：報銷、分紅、房租、`spend_cap` 全算，只報 `would_block`、`suggest_retire`，不擋不刪。後果：r09 學不到「錢選梯子」是否成立，但不會在新樹第一輪就餓死主力；實扣則 Q2 核心假設當輪可驗，風險是誤殺加上錢制本身第一次上線。
5. **放寬單批記憶體 16GB→24GB、保留 4 核給 LLM agent？** 推薦使用者在家時放寬到 24GB、外出維持 16GB，由 `sched/params.json` 一鍵切。後果：不放寬則 400k 預算以上一律走 C++ 後端；放寬可讓 Python 端多跑一倍練習池。

## 六、風險與不做的事

- **layer-2 搜出「放寬門檻」的假進步**：效果只用固定題組曲線與 H24 量、`wrong ≤基準`、凍結集不可寫（條 11、T6）。
- **r09 又全 Δ=0**：up-params 很可能是 0，照實寫、不降門檻；真正的賭注在守門搜尋（有 400 trace）與往下拆（有近解），這兩處有料。
- **雙軌讓人以為舊樹成績是錘子的成績**：舊樹上的一切只算「機制驗證」，簡報分欄寫，不進 `self_share`。
- **活樹每 pass 重讀被半寫檔**：只在 pass 邊界讀，寫完再改名（N-05）。
- **信箱 `say` 被 agent 當指令執行**：`propose` 只讀信進 report，人的 `direction` 一次覆蓋即失效。

不做：第 3 層自動化；搜 CRN 判準；LLM 當裁判或改進者；對原始碼文字做變異；區中區；sqlite 或嵌入檢索；GUI；任何對 H24、purity、三判準規則的程式化修改；定義 lv3；把 Python 搜尋改成逐節點 shell 呼叫。
