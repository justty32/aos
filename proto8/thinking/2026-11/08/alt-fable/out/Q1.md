# Q1：lv1 錘子的設計圖（統一節點模型）

## 一、ELI5 結論

錘子就是一棵資料夾樹。樹上每個資料夾是一個「節點」：有一份自我介紹（`_metainfo.json`），一個可以執行的入口（`_entry`），一個收信的信箱（`_gradients.jsonl`）。自我介紹裡寫三件事：我吃什麼、吐什麼（契約）；誰負責檢查我做得好不好（審查節點的路徑）；誰負責把我改好（改進節點的路徑）。公式 `x=2*y`、一支 Python 搜尋器、一個 LLM agent，長得一模一樣，差別只在入口裡跑的是什麼。

lv1 錘子＝現在 r08 的 `pool` 學習迴圈，拆成這種節點樹，掛在 aos-daemon 底下每 tick 跑一個 pass。使用者 `cd` 進去就看得到每個節點的帳與信，往信箱丟一行字就能干預。

「錘子造錘子」的第一步只量一件事：**lv1 的改進節點，有沒有成功改動過一個審查節點或改進節點（而不只是解題積木），而且改完之後，用同一顆空種子、同一份題組、同一預算跑出來的學習曲線更好。** 做到一次，就叫 lv2。

## 二、設計

**1. 節點＝資料夾，三個檔，一個契約**

沿用 proto8 既有規範，不發明新機制：C-68 資料夾即程式、N-68 的 `_metainfo.json`、node-pool 03 的 `_gradients.jsonl` 與 `improve` 指標路徑。只補四個選填 key：`io`、`review`、`improve`、`born`。arcagi 的 `aos/blocks/<name>/` 已經是這個形狀，只差 `io` 與兩個指標。

```json
{
  "name": "compress",
  "kind": "program",
  "doc": "G1: extract shared subtrees from solved programs into seedlib blocks",
  "io": {"in": "hammer-solved/1", "out": "hammer-blocks/1"},
  "cost": {"time_ms": 3000, "counter_calls": 0, "token": 0},
  "timeout_ms": 60000,
  "review": "../../review/stats",
  "improve": "../knobs#/targets/compress",
  "born": {"epoch": 0, "by": "human"},
  "status": "live"
}
```

- `kind` 只分三種：`program`（確定性，入口不碰 LLM）、`agent`（入口是 aos-agent 的 fsm，會問腦）、`generator`（吐出新節點）。審查、改進不是 kind，是**角色**：誰被別人的 `review`／`improve` 指到，誰就扮那個角色。所以同一個統計程式可以同時是十個節點的審查者。
- `io` 寫**格式名**，不寫 schema 本體。格式名對到 `aos_metaopt/formats.py` 裡一條檢查函式（aos-self-opt 03 §2 已有 `metaopt-q/1` 那套，照加）。seedlib 積木的 `sig` 字串（例 `(list[list[a]]) -> list[list[a]]`）也算合法的 `io.in`／`io.out` 值，型別導向枚舉直接吃。
- `review`／`improve` 是指標路徑（相對本資料夾，或 `檔#/指標`）。省略時用錘子根的預設：`review` 預設 `hammer/review/stats`，`improve` 預設 `hammer/improve/none`。兩層以內（node-pool 已定審查鏈最多 2 層）。
- `born.by` 填改它的節點路徑，或 `human`、`agent:<名>`。這一格是 lv1 到 lv2 判準的根據，不可省。
- LLM agent 節點只多一個 `queue/`（aos-agent 的 say／listen），其他完全相同。`_gradients.jsonl` 每個節點都有；agent 節點的 fsm 在 think 格先讀未處理的信。

**2. 兩種共用記錄列（arcagi 與 aos 同一份）**

跑一次留一列，改一次留一列。放在錘子根，不放節點內（節點內只放信箱）。

| 列 | 一列長這樣 | 誰寫 |
|---|---|---|
| `hammer-run/1`，`hammer/runs/<epoch>.jsonl` | `{epoch, node, task, ok, out_sha, cost:{wall_ms, nodes, llm_calls, token}}` | 錘子根的入口，每個節點被叫一次寫一列 |
| `hammer-change/1`，`hammer/ledger.jsonl` | arcagi `aos/meta/ledger.jsonl` 現有那列（`action, knobs_before/after, auc_*_seeds, se, not_worse, accepted, commit`）**再加** `target`（被改的節點路徑）、`by`（改它的節點路徑或 `human`）、`layer`（0／1／2，見第 4 點） | 改進節點 |

node-pool 的錢（`pool/ledger.jsonl`）照舊獨立，`hammer-run/1` 的 `cost` 就是 `pool pay` 的輸入來源；兩邊不合併。

**3. lv1 錘子的具體樹（arcagi r09，`~/code/playground-arc1/ws/hammer/`）**

```
hammer/                 _entry = 跑一個 pass（包現有 grow.curve 單 pass）
├ solve/                program；seed 枚舉＋演繹分解；knobs.json 是活檔
├ review/stats/         program；讀 runs/，算每節點近 10 epoch 成功率、成本中位數
├ improve/compress/     program；G1（現有 grow/compress.py）
├ improve/knobs/        program；層 1 CRN 旋鈕判準（現有 grow/meta.py）
├ improve/propose/      agent；提案新拆法或改 review/improve 的程式，只能寫 candidate/
├ candidate/            提案暫存；過 improve/knobs 判準才搬進正式位置
├ runs/  ledger.jsonl  report.json
```

- 搜尋仍在 Python 程序內跑（r02 設計已定，速度考量不變）。資料夾變成**權威來源**：每個 pass 開頭重讀 `solve/knobs.json`、`seedlib/`、各節點 `status`，使用者改檔下個 pass 就生效。
- 掛法：`aos-agent ctl add --name hammer --ws ws ws/hammer`，daemon 每 tick 叫一次入口＝一個 epoch。`ctl pause` 凍結在 pass 邊界。
- 干預三招：對 program 節點 `pool grad --def improve/compress --say "試試只抽 2 題以上共用的" --score 0.5`（進信箱，`review/stats` 讀到後把它寫進 report，`propose` 會看到）；對 agent 節點 `aos-agent say -t propose "..."`；直接改活檔（`knobs.json`、`status`）。這三招都會在 `ledger.jsonl` 留 `by: human` 一列。
- 現有 `aos/blocks/`、`aos/pool/`、`aos/meta/` 不搬，`hammer/` 是新的根；purity 腳本加掃 `hammer/solve/`。

**4. lv1 到 lv2 的判準（錘子造錘子第一步怎麼量）**

先定三層「被改的東西」：

| layer | 被改的是 | r08 現況 |
|---|---|---|
| 0 | 解題積木（seedlib 積木） | 已在長（G1 `take 2`、`map (λ sort)`） |
| 1 | 求解器的旋鈕與拆法（`knobs.json`、`decomp_set`） | 已在做，全部 Δ=0 |
| 2 | 審查節點或改進節點本身（`review/*`、`improve/*` 的程式或參數） | **沒有** |

**lv2 的定義**：`hammer/ledger.jsonl` 裡出現至少一列 `layer: 2`、`by` 是樹內節點（不是 `human`、不是 `agent:`）、`accepted: true`，而且同一列的判準通過：

- 效果：固定空種子（tag `r09-seed0`）、固定題組 L16＋H24、固定每 pass 預算；5 個 CRN seed 下，改後 AUC_L 不比改前差的 ≥4/5，平均增量 ≥ max(1, 2×配對 SE)；H24 淨增 ≥0（照 r08 已定門檻，不另發明）。
- 代價：改後錘子自己一個 pass 的花費（`runs/` 裡 review 與 improve 節點的 `wall_ms` 和＋`llm_calls`）≤ 改前的 1.5 倍。
- 誠實：`solve/` 的 `llm_calls` 仍為 0；purity 過。

**兩個輔助數字**（進 `report.json`，不設門檻，給使用者看趨勢）：`self_share`＝ledger 裡 accepted 列中 `by` 為樹內節點的比例；`layer2_attempts`＝layer 2 提案數（含被拒的）。r09 的目標是 layer2_attempts ≥ 5、accepted ≥ 1。

**lv1 可以改 layer 2 的最小辦法**（不然永遠是 0）：`review/stats` 與 `improve/knobs` 的門檻參數（近 N 次、不退步幾比幾、增量倍數、`lib_cap`）全部搬進各自資料夾的 `params.json`，列進 `improve/knobs` 的 `targets`。這樣現有的 CRN 旋鈕機制不用改一行，就能搜自己的判準。這是 Q6「門檻變節點」的最小版本，與它銜接。

**5. aos-self-opt 第二輪的對應動作**

- `proto8/py/aos_metaopt/` 加 `node.py`（讀寫 `_metainfo.json` 四個新 key、追加 run 列與 change 列、讀信箱）與 `formats.py` 兩條新格式。兩邊 import 同一份。
- `~/code/playground-so1/hammer/`：`solve/`＝linker 規則枚舉（03 §3 的 `enum.py`）、`review/stats`＝`judge.py` 的兩折覆蓋率、`improve/promote`＝晉升門、`improve/knobs`＝深度與錯判比的 CRN。第二輪驗收除了 G0 到 G6，加一條：**同一支 `review/stats` 程式同時被 arcagi 與 aos 的樹指到**，不改程式碼只換 `io` 格式名。這是「共用」的實證。
- 第二輪不要求 layer 2 accepted，只要求 ledger 有 `layer` 與 `by` 欄、report 印出 `self_share`。

## 三、風險與不做的事

**風險**

- layer 2 的搜尋空間是門檻參數，很容易搜出「把門檻放寬讓更多東西 accepted」的假進步。擋法已在判準裡：效果必須用**固定題組上的學習曲線**量，不用 accepted 數量量；H24 盲測不退。
- r07、r08 的旋鈕全部 Δ=0，layer 2 很可能也是 0。這本身是有價值的否定結果：代表 lv1 的改進節點表達力不夠，要走 Q4 的「往上長」而不是繼續轉旋鈕。r09 若 layer2_attempts ≥5 而 accepted＝0，收輪簡報照實寫，不降門檻。
- 活樹每 pass 重讀資料夾，使用者改到一半被讀到。只在 pass 邊界讀，且 `candidate/` 以外的改動要求一次寫完再改名（N-05）。
- `born.by` 靠寫的人誠實。agent 節點提案的改動經 `candidate/` 與判準，`by` 由判準程式填，不由 agent 自己填。

**不做**

- 不把 Python 搜尋改成 shell 逐節點呼叫；資料夾只管身分、狀態、帳、信，不管速度。
- 不統一錢與帳：`pool/` 照 node-pool 03，`hammer-run/1` 只是它的輸入。
- 不定義 lv3；lv2 到 lv3 等 lv2 出現一次再量。
- 不在 r09 讓 `propose` agent 直接改正式節點；只寫 `candidate/`。
- 不在本題處理成本階梯（Q2）、固化判準（Q3）、停滯判準（Q4）、分區（Q5）、搜尋表示法（Q6）；本題只給它們共同站的地板：三個檔、四個 key、兩種記錄列、一條 lv2 門檻。
