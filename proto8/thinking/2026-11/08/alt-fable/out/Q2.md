# Q2 審查與改進的成本梯

## ELI5 結論

每個節點旁邊站一排「醫生」，從便宜到貴：先是免費量體溫的統計程式，再是會換零件的專用小工具，再是暴力試遍所有配方的符號迴歸，最後才是 LLM。節點要看哪個醫生，**由它自己的錢包決定**：審查與改進都是向池裡的醫生節點「買服務」，從被改節點的錢包報銷；醫生治好了，病人往後幾個 epoch 的分紅抽成給它。便宜又有效的醫生會變富，貴又沒用的會餓死，梯子的形狀是錢選出來的，不是人定的。使用者說的「專用替換程式」不是手寫的，是把符號迴歸反覆找到的同一種修法蒸餾出來的（意見 3 用在改進者自己身上）。

## 一、梯子：出生順序 vs 嘗試順序

| 階 | 節點（資料夾程式） | 做什麼 | 成本量 | 結果 |
|---|---|---|---|---|
| L0 審查 | `ladder/stat` | 讀節點 `_runs.jsonl` 最近 `window` 次：通過率 p、趨勢、失敗例（含 ground truth） | 毫秒；記 `wall_s` | 寫 `_health.json`，決定要不要升 |
| L2 專用替換 | `ladder/patch_<kind>` | 對本體套一小組**具名變換**（公式：改常數±1、換特徵、加奇偶項、加守衛） | 毫秒 | 候選 body |
| L1 符號迴歸 | `ladder/symreg_<kind>` | 在該 kind 的文法內按大小枚舉，預算＝節點數 | 秒；記 `nodes_k` | 候選 body 或 `no_fit`＋殘差 |
| L3 LLM | `ladder/llm_improve` | 只在 L1 回 `no_fit` 且殘差指向「文法缺東西」時，對**產生器**（不是節點）提一個新原語，進 shadow | token | 候選積木 |

使用者原話的順序（統計→符號迴歸→專用替換→LLM）是**出生順序**：L2 是從 L1 的歷史蒸餾出來的，所以晚生；但一旦存在，**嘗試順序按成本**：L0→L2→L1→L3。這是我對原話唯一的細節修正。

## 二、升降規則（起步值，全寫在 `_metainfo.json#/ladder`，本身是 Q6 可搜尋的旋鈕）

```json
"ladder": {"review":"ladder/stat","improve":["ladder/patch_formula","ladder/symreg_formula"],
 "window":10,"p_low":0.5,"patience":2,"stable":{"p":0.9,"windows":3},
 "spend_cap":0.3,"llm":false}
```

- **升**：L0 量到 p < `p_low` 且有 ≥1 個帶真值的失敗例 → 走 `improve` 清單第一階；某階連續 `patience` 次沒產出被接受的候選（或回 `no_fit`）→ 下一階。每階開跑前先問錢包：本 epoch 改進花費不得超過餘額 × `spend_cap`，付不起就停在這階，寫 `_health.json#/blocked_by: money`。
- **升到 L3 的額外門**：`ladder.llm` 為真、L1 與 L2 都報 `exhausted`、節點在 ≥2 題解路上。否則改成往上寄信給 `generator` 節點的信箱（Q4 的「往上長」），由產生器決定。
- **降**：(a) 蒸餾：同 kind 的 L1 接受紀錄裡，同一種編輯（以「舊 body→新 body 的樹差」正規化後的簽名）出現 ≥3 次 → `ladder/distill` 把它寫成 `patch_<kind>` 的一條變換（先 shadow：下 2 個 epoch 跟 L1 同題對跑，命中率 ≥ L1 的 80% 才轉 live）。(b) 健康：p ≥ `stable.p` 連續 `stable.windows` 個窗 → 審查間隔 10 次→50 次，改進階重置到清單第一階。
- **接受候選的門**（防背答案，沿 r08 D-r8-6）：新 body 要過舊 support 全部＋train 留一，且大小增加 ≤ 每多覆蓋一例 2 個節點；只貼合失敗例的不收。舊 body 存 `_history/<epoch>.json`，可回退。

## 三、記帳（接 node-pool 03 §3 與 arcagi `aos/pool`）

1. **量**：`pool/config.json#/cost` 加一鍵 `nodes_k: 0.01`（枚舉節點數／千），LLM 照 `ktoken`。
2. **報銷**：每次審查／改進，被改節點錢包付給醫生節點，ledger 一行 `{epoch, def, kind:"improve", rung:"L1", to:"ladder/symreg_formula", amount, evidence:"<def>/_ladder.jsonl#/3", cost}`；審查 `kind:"review"`。醫生節點有自己的錢包、房租、退休建議，跟其他節點一樣。
3. **分紅**：候選被接受後，被改節點 `_metainfo.json#/credit` 記 `{improver, until: epoch+3}`；這 3 個 epoch 它分到的紅利抽 `improver_cut`（沿用現有 `generator_cut` 0.2）給醫生。治了沒用（之後 p 沒升）醫生只拿報銷、沒分紅。
4. **不會通膨**：報銷是錢包間轉帳，不是頂層新發；LLM 花費走 `ktoken` 立刻扣，窮節點叫不起。

## 四、`x=2*y` 走一遍（arcagi 公式節點 `formula_2y`，`_rule.json#/body = ["lin","h_in",2,0]`）

| epoch | 事件 | 階 | 花費（分） | 帳 |
|---|---|---|---|---|
| e0 | `_gen/formula` 枚舉出它（出生本身就是 L1），support 3 題 | — | 由產生器付 | `clone_seed` |
| e1～e3 | 每 epoch L0 看 `_runs.jsonl`：p=0.8 | L0 | 0.001 | `review` 三行 |
| e4 | 練習池新題：h_in=3→7、5→11 答錯，p=0.5 → 升。`patch_formula` 還不存在 → L1 symreg 預算 min(餘額×0.3, 200k 節點)：`["lin","h_in",2,1]` 貼新例卻破舊 support，拒；`["add",["lin","h_in",2,0],["mod","h_in",2]]` 5/5、大小＋2，接受。舊 body 進 `_history/4.json` | L1 | 120k 節點＝1.2 | `improve` 一行；`credit:{symreg, until:7}` |
| e5～e7 | p 回 0.9，三窗穩定 → 審查間隔放寬到 50 次；分紅 20% 流向 symreg | L0 | ~0 | `bonus` 抽成 |
| e6 | 全池 formula_* 的 L1 紀錄裡「加奇偶項」出現第 3 次 → distill 寫進 `patch_formula`，shadow 兩個 epoch後 live；下次同病只花 0.01 分 | 降 | — | distill 的 `review` 行 |
| e9 | 新失敗：h_out 其實等於物件數，特徵表沒這欄 → L2 無變換命中、L1 `no_fit` 殘差非零 → 往上寄信給 `_gen/formula` 信箱「缺特徵」；`ladder.llm=false` 的曲線跑只記 `would_call_llm+1`，不叫 | 往上 | 0.6 | 信一封 |

## 五、活樹（意見 7）

錘子跑在試驗場 `$AOS_WS/defs/`（arcagi r09 先用現成 `aos/blocks/`）：`aos-daemon` 每 epoch 跑一次 `ladder/tick`，對 scope 內每個節點叫它的 `review` 指標。cd 進節點能看：`_metainfo.json`、`_runs.jsonl`、`_health.json`、`_gradients.jsonl`、`_ladder.jsonl`（每次審查／改進：階、花費、結果）、`_history/`。手動操作全是既有工具形狀：

```
echo '{"def":"formula_2y"}' | aos-exec --ws $WS defs/ladder/stat        # 看體溫
echo '{"def":"formula_2y","dry_run":true}' | aos-exec --ws $WS defs/ladder/symreg_formula   # 看候選不寫
pool grad --def formula_2y --say "h_out 跟物件數有關" --score -0.5       # 投梯度信
```

干預走 N-16／N-66 一箱一函數：節點信箱 `_ctl/` 接 `ladder/ctl`，body 只有兩種 `{"op":"force_rung","rung":"L1"}`、`{"op":"freeze"}`；tick 每次先讀信箱。

## 六、r09 與 aos-self-opt 第二輪的具體動作

- **arcagi r09**：(1) 求解器 trace 多寫每積木 `_runs.jsonl`（在解路上＝ok；近失敗＝fail＋真值）。(2) 新資料夾 `aos/ladder/{stat,patch_formula,symreg_formula,distill,tick,ctl}`，`_entry` 轉 `python -m arcagi.ladder.*`。(3) scope 只開 `formula_*`（133 個）與 `pred_*`；`ladder.llm` 全關，曲線 `llm_calls` 維持 0。(4) config 加 `nodes_k`、`improver_cut`。(5) 量法：梯子開／關各 5 個 CRN seed；門檻＝審查成本每節點每 epoch ≤0.01 分、4 個 epoch 後接受的改進中 L2 佔 ≥30%、`clean_P` 與 AUC_L 不低於 r08 主樹、symreg 節點餘額 >0、essential 無人因改進費破產、`would_call_llm` 只報不用。
- **aos-self-opt 第二輪**：節點＝`rules/<run>/<rule_id>/`；L0＝該規則在最近折的 solved／wrong；L1＝`enum.py` 限定只改 AST 一個子樹（預算 5 萬節點）；L2 起步兩條變換「`and` 收緊」「Int 常數 ±1」；帳走 `aos_metaopt/ledger.py` 同欄位；L3 關。

## 風險與不做的事

- **窗 10 次是整數顆粒**（r07 教訓）：p 跳 0.1 一格，升降會抖。對策：升降只看節點自己、不看全局；梯子整體效果一律 CRN 對照。
- **改進費把常失敗的節點先弄破產**：這是設計意圖（退休訊號），但難題集中時會誤殺；`spend_cap` 30% 與 essential 兜底，第一輪只建議不自動退休。
- **L2 蒸餾出雜訊變換**：≥3 次＋shadow 才 live；變換也有錢包，沒人用就餓死。
- **接受門仍可能背答案**：留一＋MDL 是 r08 已驗的門；synth 欄只審計不決策。
- 不做：LLM 進曲線跑；自動退休；LLM agent 節點（arknights）的梯子；信箱 op 超過兩種；任何 GUI；梯子參數的自動搜尋（留給 Q6）。
