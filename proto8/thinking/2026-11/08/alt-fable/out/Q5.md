# Q5：產業園區（節點池到千、萬級怎麼組織，單機怎麼排）

## 一、ELI5 結論

節點一多，兩件事會先壞：搜尋器把庫裡每塊積木都當候選，枚舉空間爆掉；記憶體被十幾個 worker 一起吃光，而這台機器 swap 只有 512MB，吃光就是被 OOM 殺。產業園區就是對這兩件事的解法：**把節點池切成「區」，每區自己有一張出口表、一本帳、一份索引；搜尋器一次只載入一區的熱門積木（上限 16），不是整池。** 區不是人手劃的「2D 區」「改進區」，而是由**型別簽章＋同程式共用關係**自己長出來：住一起的積木常被同一支程式一起用。人只做兩件事：給區取別名、釘住不准合併。

區的面積要花錢：房租隨區內人口上漲，擠就有人被淘汰，退休的搬到 `retired/` 可復活；跨區引用要付過路費，付太多就該搬家（複製進本區）或兩區合併。排程方面，**錢買 CPU**：每區拿到的 CPU 份額照它的錢包餘額比例分，底線 10%；每個 worker 硬限 2GB、整個 pass 限 24GB、OOM 一次就把那題預算砍半重排。全部是檔案，使用者 `cd` 進區就看得到人口、帳、佇列。

## 二、設計

### 1. 區＝資料夾一層（接 Q1 的 `hammer/` 根）

```
hammer/zones/<zone>/_zone.json         # hammer-zone/1
hammer/zones/<zone>/_index.jsonl       # hammer-index/1，每節點一列，pass 邊界重建
hammer/zones/<zone>/<node>/            # Q1 的三個檔；_metainfo 多 zone、tier 兩個選填 key
hammer/index/sig.json                  # 簽章 → [zone/node]，全局
hammer/index/route.json                # hammer-route/1：題目簽章 → 各區命中率
hammer/retired/<zone>/<node>/<時間>/   # 退休封存，可 revive
hammer/sched/{params.json,queue.jsonl,report.json}
```

`_zone.json`：
```json
{"name":"z-7f3a","alias":null,"pinned":false,"born":{"epoch":3,"by":"improve/zoning","from":"z-root"},
 "sig_family":["(list[list[a]]) -> list[list[a]]"],"cap":64,"hot":16,
 "exports":["g1_f726","take2_h0"],"wallet":0,"rent_base":1.0}
```

- 一個節點只住一區（`_metainfo.json#/zone`）；`tier` 三級：`hot`（搜尋器載入，每區 ≤16，r08 已定的活躍庫上限直接變成每區上限）、`warm`（在區內磁碟上、有索引、`lookup` 可按需載入）、`cold`（退休，只剩索引列）。
- 區的 `exports` 是出口表：區外只能引用出口表上的積木。出口表由區的審查程式每 epoch 從 `uses` 排序自動產生（前 8 名），人可加。
- 起步只有一區 `z-root`（32 通用原語），其餘全由第 3 節的拆分長出來；arcagi 不手劃「2D 區」，但 `list[list[a]]` 簽章的那區長出來就是 2D 區，人給它 `alias: "2d"` 即可。這樣 purity 不破。

### 2. 引用、索引、檢索

- **區內引用**：直接名字，免費。
- **跨區引用**：程式體用 `zone/name` 全名，帳上花費 ×1.2（過路費，`pool/config.json` 加 `cross_zone_factor`）。過路費是信號不是懲罰：連續 3 epoch 某節點跨區被用 ≥5 次，`improve/zoning` 提案把它**複製**進用它的區（想法 20 原話「複製一個新的類似節點」），`born.from` 記來源。
- **索引**：`_index.jsonl` 每列 `{name, sig, kind, tier, uses, saving, idle, balance, exported}`；全局 `sig.json` 只放簽章到位置的對照。萬級節點就是萬行 jsonl，pass 邊界掃一次 `_metainfo.json` 重建，實測一萬個小檔讀取在 1 秒內，不需要資料庫。
- **檢索**（枚舉器用的）：`hammer lookup --sig S --zone Z --top k`，分數 = `uses × saving / (1 + idle)`，先區內 hot，不足 k 才查本區 warm，再查其他區 exports。型別導向枚舉本來就按簽章取候選，改成問這支函數即可。
- **路由**（題目進哪區）：`route.json` 每列 `{task_sig, zone, tried, solved}`。一題先進 `solved/tried` 最高的區（60% 預算），餘下 40% 給次高區；都沒紀錄就進 `z-root`。從零起跑時這張表是空的，第一個 epoch 全走 root，拆分後才有分流。

### 3. 房租、淘汰、區的生長與合併

錢照 node-pool 03 的規則（先報銷、再分紅、每 epoch 扣房租、連 3 次 0 建議退休），本題只加三條：

| 規則 | 公式／門檻 | 作用 |
|---|---|---|
| 房租隨人口漲 | `rent = rent_base × (1 + live/cap)` | 擠的區自己清人，cap 64 時房租翻倍 |
| 拆分 | 區內 live > cap 連續 2 epoch → 用「同程式共用」圖做二分（貪婪模組度，不用矩陣分解）；先按簽章族分，簽章同族才看共用 | 區自己長出來，`born.by` 記 `improve/zoning` |
| 合併 | 兩區跨區引用 > 各自區內引用的 50% 連續 3 epoch，或兩區 live 皆 < 16 | 過路費太高就合併，太空也合併；`pinned` 的不動 |

拆分與合併都是 Q1 第 4 點的 **layer 1 meta 動作**：寫進 `hammer/ledger.jsonl`（`target` 填區路徑），用 r08 的 CRN 判準：5 個配對 seed，AUC_L 不退 ≥4/5，且**解出題的枚舉節點和下降 ≥10%**。分區的本職就是縮搜尋空間，所以第二個數字才是它的主指標；AUC_L 只是不准退的底線。不過判準就回滾，回滾只改 `zone` 欄與索引，程式體不動。

退休：`pool retire` 搬到 `hammer/retired/`，`sig.json` 保留一列標 `cold`；`lookup` 預設不查 cold，`--all` 才查；`revive` 從 root 撥一筆起始金。

### 4. 單機排程（16 核、60GB、512MB swap）

排程器是一個 program 節點 `hammer/sched/`，一 tick 一 pass，`params.json` 起步值：

```json
{"workers":12,"reserve_cores":4,"mem_pass_gb":24,"mem_worker_gb":2,
 "wall_pass_s":600,"share_floor":0.1,"oom_halve":true,"oom_heavy_after":3,"llm_agents_max":2}
```

- **工作項**＝`(task, zone, budget)`；佇列 `queue.jsonl` 排序：L16 計分組 → P32 練習池按近解距離升冪 → H24 量測。同一題的兩個區是兩個工作項，先到先得，有一個解出就撤另一個。
- **錢買 CPU**：每區 CPU 份額 = `區錢包 / Σ 錢包`，底線 10%（新區才活得下來）。份額換算成該區工作項在佇列裡的配額，不搶佔正在跑的 worker，只在解題邊界重排。
- **記憶體**：依據是 r08 S1 實測，Python 枚舉 1M 節點、6 worker 超過 8GB 被殺，C++ 同設定峰值 1.8GB。所以 Python worker 用 `prlimit --as` 硬限 2GB，整個 pass 跑在 `systemd-run --scope -p MemoryMax=24G`，留 36GB 給系統、LLM agent 與使用者。節點預算是記憶體的真正驅動（觀察等價表），超過 400k 節點的工作項一律派給 C++ 後端 `arcbatch`，Python 只接 ≤400k。
- **OOM 處理**：worker 以 137 結束 → `hammer-run/1` 那列記 `oom: true`，該工作項預算砍半重排；同一題累計 3 次 → 標 `heavy`，只走 C++ 或跳過。swap 既然等於沒有，目標就是 OOM 數為 0，而不是靠 swap 撐。
- **LLM agent 節點**（Q1 的 `propose`）不進 worker 池，跑在保留的 4 核上，同時 ≤2 隻，產出只寫 `candidate/`，下個 pass 邊界才被讀。
- **量法**：`hammer-run/1` 加 `rss_peak_mb`（`getrusage` 子程序）、`oom`、`zone`；`sched/report.json` 每 pass 印 CPU 利用率（目標 pass 期間 12 核 ≥70%）、OOM 數（目標 0）、尾延遲、各區實得份額 vs 應得份額。

### 5. 干預（意見 7）

全部是檔案與現成指令：`cd hammer/zones/z-7f3a && cat _zone.json _index.jsonl` 看人口與帳；`cat ../../sched/queue.jsonl` 看誰在排；`pool grad --def zones/z-7f3a/g1_f726 --say "..." --score 0.5` 投信；`hammer zone pin z-7f3a`、`hammer zone alias z-7f3a 2d`、`hammer zone freeze z-7f3a`（凍結＝不拆不合不收房租）；改 `sched/params.json` 下個 pass 生效。每一招在 `ledger.jsonl` 留 `by: human`。

### 6. 落地到 r09 與 aos-self-opt 第二輪

**r09（arcagi）**：
1. 新檔：`hammer/zones/`、`hammer/index/`、`hammer/sched/`、`hammer/improve/zoning/`、`hammer/review/zone_stats/`；格式 `hammer-zone/1`、`hammer-index/1`、`hammer-route/1` 進 `aos_metaopt/formats.py`。
2. 枚舉器候選取法改走 `lookup`；`grow/backend.solve_with` 加 `zone` 參數。
3. **離線預檢**（施工前就能做）：對舊手寫樹 `aos/blocks/` 474 個節點，用 r06 traces 的共用關係跑一次拆分演算法，看分出的區跟既有 `kind`（primitive／pred／formula／extract／macro）多像。多數票純度 ≥0.7 才上線，否則先修演算法。這是唯讀，不碰種子樹。
4. 門檻：purity 過；區數從 1 自動長到 ≥2；分區後 L16 解出題枚舉節點和 ≤ 不分區的 90%，AUC_L 不退（5 CRN、≥4/5）；L16＋P32 一個 pass 在 400k 預算下牆鐘 ≤10 分鐘；OOM 0；CPU 利用率 ≥70%；`route.json` 首選區命中率 ≥60%（從第 3 epoch 起算）。

**aos-self-opt 第二輪**：規則池照 `Action` 簽章分區（`link_exact`／`link_class`／`nolink` 三族），`linker/`、`review/`、`improve/` 是角色不是區；`aos_metaopt/sched.py` 與 arcagi 共用同一支排程器，只換工作項的產生函數。驗收加一條：195 條舊規則走完 covered 與房租後，`z-*` 區數 ≥2 且總有效規則數不高於 06 設計的 110。

## 三、風險與不做的事

**風險**
- 分區縮小候選集，可能把跨區才解得出的題擋掉。擋法：40% 預算永遠給第二區、`exports` 永遠可見、CRN 判準 AUC_L 不退；若 r09 出現「不分區解得出、分區解不出」的題，收輪簡報照實列，不放寬門檻。
- 錢買 CPU 會富者愈富。底線 10% 與新區起始金是兩道緩衝；若某區連續 5 epoch 份額 >70%，審查程式發信提醒，不自動介入。
- 拆分演算法用貪婪模組度，可能切出不自然的區。離線預檢就是為了這點，純度不到 0.7 就不上線。
- 房租隨人口漲，在小區（<16）形同沒有；這是刻意的，小區由合併規則處理。

**不做**
- 不用 sqlite、向量檢索或嵌入；萬級節點 jsonl 索引夠用。
- 不手劃「2D 區」進種子樹；區只能長出來，人只給別名。
- 不搶佔正在跑的 worker，不做跨機。
- 不讓區擁有程式碼；`review/`、`improve/` 的程式節點照 Q1 住在角色資料夾，區只管積木與規則。
- 不定義區的層級（區中區）；萬級以下一層夠，十萬級再議。
