# 錘子 v4 深挖：預算分配與信用分配（Argon 問題 3）

## 一、ELI5 結論

v3 的 UCB 錯在**把「當輪拿到的位元」當成「這條路值多少錢」**。睡眠造詞像擺攤賣飲料，當天見現金；縱拆像種樹、鑄模像蓋廠房，要兩三輪後別人用它的見證或原語解出題才回本。即時獎勵的 UCB 一定把錢全給擺攤的。

解法不是發明新演算法，而是**把帳記對**：每個見證、每條原語都記「誰生的、哪一輪生的」（血統），解出一題時價金沿血統往回分（這就是 eligibility trace，只是用帳本實作）；bandit 只拿「已經過了成熟期的出手」算平均，還沒到期的出手一律當「可能很好」留寬信賴區間（延遲回饋 bandit 的標準作法）；三條常規路線各有**底薪**，bandit 只分配剩下的四成。孵化槽改成逐次減半：孵化中的算子每輪比命中率，墊底一半 TTL 砍半，但行為簽名獨一無二的不砍（開放式進化的踏腳石）。

算子二分的錯在**責任按出生順序找**。改成三步：先看帳（每列每輪的 tried 成本與「必要解」收益，這張單列邊際帳不用重跑）；再只對本輪剛轉正的差集 ΔR_t（通常 1～3 列）做留一消融；差集 ≤3 列就直接算精確 Shapley（最多 8 條短曲線），六條各加 8% 分支的累積效應會被均分責任，不會讓最後一條揹黑鍋。更前面一道：活算子表有**分支容量**，轉正要先騰位，位子由邊際帳最差的讓，累積超時在源頭就擋住，多數時候根本走不到消融。

誠實說一句：r09 一輪約 8～16 個 epoch，解題是稀疏整數事件，bandit 在這個樣本量下學不到多少，底薪與血統帳才是主收益——它讓人與第 3 層看得見「縱拆每百萬次評估換幾題」，方向對不對一目了然。

## 二、問題的根：帳少記了兩個維度

v3 的 `ledger.jsonl` 只記「哪一輪、接受與否、Δ」，缺**列**（哪條算子、哪條路線）與**時間差**（產物何時兌現）。三個症狀同源：

| 症狀 | 缺的維度 | 後果 |
|---|---|---|
| UCB 餓死縱拆、鑄模 | 時間差 | 當輪位元 0 → 永不被選 |
| 二分誤殺好算子 | 列 | 沒有單列成本／收益，只能靠出生順序切 |
| 算力浪費 | 兩者 | 帳上明明有線索，卻重跑 log₂N 條曲線 |

經驗庫早定了方向：條 26「先報銷再分紅加房租」、鐵律 7「壓縮與解題分帳」、鐵律 6「評分先做套利測試」。v4 的機制全部是這三條的延伸。

## 三、設計 A：血統帳——延遲獎勵的信用分配

### 1. 每個產物帶血統

`ops.jsonl` 與 `_witness.jsonl` 每列加兩欄：

```json
{"id":"op_31","kind":"comb","status":"incubating",
 "lineage":[{"route":"rt_vsplit","epoch":7},{"via":"wit_204"}],
 "born_epoch":8, "parent_route":"rt_vsplit"}
```

`lineage` 是有向鏈：路線 → 見證 → 算子 → 程式。深度 ≤3（路線出手、產中間物、產算子），與 Q4 層數封頂一致。

### 2. 解題付價，沿血統回流

沿用 `blocks/pool/ledger.py` 的 `settle` 邏輯，改三個名字：

- 一題**真解**（train 池，過留一與 MDL；H24 與鍛造題永不付價）付 `price=1000`，頂層留 20%，其餘按被選程式的靜態引用分給算子列，等同現行 `selected_steps`。
- 算子列把收入的 `passdown=0.5` 往 `lineage` 上一跳傳，再上一跳再傳一半。所以縱拆路線從一題解得 `800 × 0.5 × 0.5 = 200`，鑄模路線同理。這就是 Sutton 的 eligibility trace，λ 在這裡是每跳 0.5，不隨時間衰減——**只要那條原語還在被用，當年種樹的路線就持續領錢**。
- 壓縮另開一本：同一題前後兩輪都解出、評估次數下降，省下的 log₂ 位元封頂 2 bits／題（D-r8-10 已定），同樣按程式引用分給算子、再沿血統上傳。兩本帳不相加；排序時解題帳優先，解題帳同分才看位元帳（接 Q4 兩段判準的整數事件優先原則）。

### 3. ledger 新增列型

```json
{"type":"pull","epoch":9,"route":"rt_vsplit","cost_evals":412000,"produced":["wit_204","wit_205"]}
{"type":"dividend","epoch":11,"to":"rt_vsplit","from_task":"3bd67248","book":"solve","amount":200,"hops":2,"origin_epoch":9}
{"type":"dividend","epoch":11,"to":"op_31","from_task":"3bd67248","book":"bits","amount":1.4,"hops":0}
```

`origin_epoch − epoch` 就是實測的兌現延遲，餵給設計 B 的成熟期。

### 4. 鑄模的位置

依已裁定的方向題 1，鑄模只在 `stall=stop` 觸發，**移出常規 bandit 臂**（解掉 Argon 指出的 §三.1 與 §三.6 矛盾）。但鑄模的 `pull` 列照記，成本含 LLM 折算稅 10⁵ evals／call（Argon 量法補丁 2），分紅照領。目的不是讓它搶預算，而是讓 `routes.json` 裡「鑄模廠每 10⁵ 稅換幾題」這個數字存在，供人與第 3 層判斷鑄模廠該不該開。

## 四、設計 B：成熟窗 bandit 與底薪組合

### 1. 三臂底薪

常規臂三條：縱拆、橫拆、睡眠造詞。每 epoch 預算 60% 按 20% 底薪平分，**只有 40% 由 bandit 分配**。理由是經驗條 1 與 24：旋鈕層實測增量 0，不該讓一個還沒學會的 bandit 掌握全部預算；Q5 給次高區留 40% 也是同一邏輯。底薪沿用 `budget.shares` 的 `floor` 參數，不另寫。

### 2. 只算成熟出手

每臂帶 `maturity` K_r（起步先驗：睡眠造詞 1、橫拆 1、縱拆 2；鑄模不在臂內但記 4）。第 t 輪：

- 成熟出手 M_r = epoch ≤ t − K_r 的 `pull`；未成熟 P_r = 其餘。
- 收益率 μ_r = 成熟出手至今收到的解題帳分紅 ÷ 成熟出手總成本（單位：解題價金／百萬 evals）。
- 分數 = μ_r + c·√(ln T / M_r)，**P_r 不計入 M_r**，所以慢熟臂的信賴區間自然更寬。這是 Joulani、György、Szepesvári 2013 處理延遲回饋的作法：待決回饋不算樣本，遺憾只多一個與延遲成正比的加項；我們的回饋有血統可歸屬，比 Pike-Burke 等 2018 的「匿名聚合延遲」簡單得多。（兩篇都不在論文庫內，憑記憶引述。）
- 40% 預算切成 4 份，依分數逐份指派並樂觀地把 M_r 加一（批次 UCB），避免單輪全押一臂。
- 實作直接改 `grow/meta.py` 的 `pick_knob_gauss`：reward 改讀 `dividend` 列而非當輪 logcost，加成熟期過濾。

### 3. 成熟期自我校正

每 4 個 epoch，用 `dividend.origin_epoch` 的延遲分布重算 K_r ＝ 90 分位延遲（下限 1、上限 4）。鑄模若實測要 5 輪才回本，帳上會直接顯示，而不是被某個寫死的 K 掩蓋。

### 4. 兩個不採用的方案與理由

- **learning progress（Graves 等 2017、Oudeyer 的 ALP）當路線獎勵**：進度是整體競爭力的導數，無法歸屬到單一路線；但它正是鍛造爐抽樣該用的量，Argon 提的 `p̂(1−p̂)+|Δp̂|` 已是這個思路，v4 保留在鍛造爐，不用在路線。
- **預付分紅給見證（novelty 即現金）**：會被刷見證套利（鐵律 6）。見證一律零現金，只靠血統回流。

## 五、設計 C：孵化槽逐次減半與獨特簽名保留

孵化中的算子現在是一條平隊列，睡眠造詞一輪可產數十條 comb，蠟模來的 1～2 條 decomp 會被淹沒。改為 Jamieson 與 Talwalkar 2016 的 successive halving：

1. 每 epoch 影子預算 B 平均分給 n 條孵化列（每列 B/n 次影子套用）。
2. 輪末按「每次套用的命中率」排序，墊底一半 `ttl` 砍半、名額讓給上半（上半下輪得 2 倍套用）。
3. 連 2 epoch 命中 ≥80% 轉 `live`（v3 原規則）；`ttl` 到 0 轉 `dormant`。
4. **保留例外**：墊底列若行為簽名獨一無二就不砍——簽名用 Argon `kind:sieve` 的 5 張探針網格輸出雜湊，「沒有任何命中率更高的列與它同簽名」即保留。這是論文庫 DNS（2502.00593）「同時較差且相似才淘汰」的競爭規則，踏腳石（N5'）靠它活下來，不靠人工 TTL。
5. **配額**：任一來源路線佔孵化槽不得超過 50%。超出的新列排隊，不進槽。

## 六、設計 D：單列邊際帳、差集消融、容量門

### 1. 單列邊際帳（不重跑）

`RewriteLedger` 已逐規則記 `tried`、`hits`。擴成每列每輪一行：

```json
{"type":"marginal","epoch":11,"op":"op_31","tried":38200,"hits":41,
 "necessary_solves":2,"solves_used":5,"bits_saved":3.1,"evals_added":38200}
```

- `evals_added`＝該列展開產生的候選數（成本）。
- `necessary_solves`＝該題所有過 train 的程式都含此列的解題數（收益的保守下界；沒它就沒這題）。
- 淨值 = 解題帳分紅 − `evals_added` 折價 − 房租。這就是 Argon 要的「現成單列邊際帳」：退步時第一件事是排序這張表，而不是跑曲線。

### 2. 分支容量門（防患於源頭）

活表有總容量 C_evals（起步＝基準曲線每題預算的 25%，由 `frozen.json` 鎖）。ΔR_t 要轉正時，Σ`evals_added` 超容量就**先騰位**：淨值最低的 live 列轉 `dormant`，與新列成對原子提交（Argon 方向題 5 建議）。六條各加 8% 的累積效應會在第四、五條時就撞容量，根本不會累到壓線超時。D-r8-12 的 `lib_cap=16` 是這條的粗版，v4 改按 evals 計。

### 3. 退步時的消融

觸發沿 v3：ΔAUC_total < 0 兩折皆退，或 H24 退。程序：

1. **查帳**：ΔR_t 加上 `tried` 跳升 >50% 的舊列，按淨值排序。
2. **差集留一**：只對 ΔR_t 跑 4-pass 短曲線（CRN 同 seed，等於 2610.31544 的「同運氣不同選擇」反事實）。|ΔR_t| ≤ 3 時直接跑全部 2^|ΔR_t| 子集（≤8 條），算精確 Shapley；每列責任 = 其 Shapley 值，責任超過總退幅 50% 的轉 `dormant`，否則**全部留下、調降其 `evals_added` 配額**。累積效應的正解是分攤，不是殺一條。
3. |ΔR_t| > 3 才退回按 `kind` 分組對半切，成本 log₂ 組數。
4. ledger 記 `{"type":"blame","epoch":12,"set":["op_31","op_33"],"method":"shapley","shares":{"op_31":0.7,"op_33":0.3},"action":"dormant:op_31"}`。

與 v3 比：最壞成本從 log₂(列數) 降到 ≤8，且多數退步在步驟 1 就結案。

## 七、套利測試與風險

上線前做四條對抗回放（鐵律 6），用 r08 ledger 加假臂重跑結算：

| 攻擊 | 設計的擋法 | 驗收 |
|---|---|---|
| 刷見證 | 見證零現金，無解題即無分紅 | 假臂產 1000 條見證，分紅 0 |
| 刷淺題壓縮 | 位元帳封頂 2 bits／題且不進排序主鍵 | 假臂壓 10 題淺題，解題帳仍 0，分數不升 |
| 洗血統（新列掛在高收益路線名下） | `lineage` 由引擎寫，`by` 非引擎者一律 `by:human` 不分紅 | 手改 lineage 的列分紅 0 |
| 塞孵化槽 | 配額 50% ＋逐次減半 | 一路線產 60 列，槽內 ≤ 半數 |

風險照實寫：

- **樣本量**：16 epoch、K=2，每臂成熟出手 ≤14 次，解題事件多半為 0。bandit 近乎均分，主收益是帳可見。若 r09 收輪時三臂 μ_r 全為 0，報告寫「路線層無訊號」，不放寬門檻。
- **血統深度**：0.5 每跳在三跳後剩 12.5%，鑄模路線可能永遠帳面小。這是刻意的，鑄模貴，帳就該難看；人要開鑄模是方向題，不由帳決定。
- **Shapley 的 CRN 假設**：確定性搜尋下子集重跑可比；若未來引入隨機後端，改配對 bootstrap。
- **容量門可能擋掉需要大分支的真解**：容量只鎖 live 表，孵化槽不受限；真解會先在孵化槽以命中率證明自己再騰位。

## 九、建議寫進 v4 的修改

1. §三.5 算子列加 `lineage`、`parent_route`、`born_epoch`；見證列同。
2. §三.6 路由改「三臂（縱拆、橫拆、睡眠造詞）＋底薪 20%×3 ＋ 40% 批次 UCB」，獎勵改讀解題帳分紅，壓縮帳只當次鍵；鑄模移出臂、只在 `stall=stop` 觸發，`pull` 與分紅照記。
3. §三.6 加成熟窗：K_r 先驗 1／1／2（鑄模 4），每 4 epoch 以實測延遲 90 分位重算，限 1～4；未成熟出手不計入樣本數。
4. §三.4 ledger 新增 `pull`、`dividend`（含 `book:solve|bits`、`hops`、`origin_epoch`）、`marginal`、`blame` 四種列型；結算復用 `blocks/pool/ledger.py` 的 `settle`，`macro_passdown` 改名 `lineage_passdown=0.5`。
5. §三.5 孵化槽改逐次減半：每輪墊底半數 TTL 砍半，探針簽名獨一者豁免，單一來源路線配額 ≤50%。
6. §三.4 新增分支容量門 C_evals（基準每題預算 25%，入 `frozen.json`），轉正須騰位，與汰出列成對原子提交。
7. §三.4 算子二分改為三段：查邊際帳 → 只對 ΔR_t 留一，|ΔR_t|≤3 用精確 Shapley 分責，責任 >50% 才 `dormant`，否則調降配額 → |ΔR_t|>3 才按 kind 分組對半。
8. N 規範新增 **N12 血統帳**：任何產物的價值只能經血統回流取得，見證與孵化列零即時現金；`lineage` 僅引擎可寫。
9. §四步 8 驗收加四條套利回放（刷見證、刷淺題、洗血統、塞孵化槽）皆分紅 0 或受配額限制。
10. §三.3 鍛造爐抽樣明寫採 learning progress 式權重 `p̂(1−p̂)+|Δp̂|`（Argon 類比四），並註明此量不用於路線獎勵。
11. 候選 CONCEPTS 新增：血統帳、成熟窗、底薪臂、逐次減半孵化、分支容量門、差集 Shapley。
12. 收輪簡報固定欄位：三臂 μ_r 與 M_r、鑄模每 10⁵ 稅換解題數、容量門騰位次數、blame 列方法分布；若三臂 μ_r 皆 0，照實寫「路線層無訊號」。
