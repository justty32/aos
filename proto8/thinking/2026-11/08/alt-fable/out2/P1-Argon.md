作為共同設計者，我看完 fable 的 P1 掃描與使用者 11-08 晚間的八條原話後，核心判斷很明確：**fable 找對了零件目錄，卻畫錯了機器藍圖**——它把一把「能自己敲自己、長在檔案樹上的活錘子」，設計成了一台「寫死在宿主程式裡的重型論文縫合機」。

以下分 **(A) 審查** 與 **(B) Argon 共同設計提案** 兩部分說明。

---

### (A) 審查：P1 產出的盲點、原意偏離與過度設計

1. **偏離核心總綱（意見 5、6）：「錘子造錘子」退化成「固定引擎＋擴充原語表」**
   使用者要的是 lv1 錘子敲出 lv2 錘子，且**用同一套暴力模式匹配同時優化本體、審查與改進**。但 fable 建議把壓縮換成 Stitch、篩子換成 babble/eggp、路由換成 EvoLattice——這些全都是**寫死在宿主底座（Harness）裡的固定演算法**。當錘頭本身不可被同構拆解與改寫，演化的就只剩扁平的 DSL 算子表（只打鐵劍零件，沒在改錘子）。
2. **漏掉拓撲生長與漸進固化（意見 3、4）：把「長樹、拆樹」偷換成「定期叫昂貴 LLM 看診」**
   意見 3 與 4 描繪的是動態結構變形：卡住時**往上長**（拉一個新節點去改進「改進程式」），或**往下拆**（把大節點拆細，子塊夠小就從 Agent → Tool → 純函數逐步退火固化）。Fable 的修改 4、5 卻將其簡化為 SpecEvo 式的「固定檢查點呼叫鑄模廠 LLM 分三級介入」與一次性軌跡擬合，完全抹平了「二階改進函數節點」與「半固化混合樹」的層級結構。
3. **園區降格與「活樹干預」完全蒸發（意見 1、7）**
   使用者說的「產業園區」，是當上千個非 LLM 函數節點併發暴增時的**職能分群與局部協作機制**；fable（修改 13）卻把它窄化成離線 FTA 快取表（`parks/cache/`）。更嚴重的是意見 7（能 `cd` 進正在跑的樹看狀態、發訊息干預）在 14 條修改中**零著墨**——一旦核心邏輯塞進記憶體內的 e-graph 與離線自動機，人類就失去了透過檔案系統直接巡檢與插手的能力。
4. **過度保守的統計官僚（違背意見 2、8）：假陰性死鎖**
   意見 2 強調單一節點的審查極度低廉（如「看近 10 次成功率」）；意見 8 明言「效果往後退正常，上上下下，方向對就好」。Fable 卻疊加了 HarnessLens「配對執行且零回歸」（修改 7）、RQGM「bootstrap 下界顯著才替換」（修改 6）與 Ratchet `Nmin=100` 證據地板（修改 9）。在 ARC 稀疏獎勵下，要求零回歸加百次樣本，會把所有「修好新結構但弄壞舊巧合」的踏腳石全部槍斃，系統將凍死在起點。
5. **過度複雜的機制疊床架屋**
   尚未跑通 lv1 閉環，v4 清單就塞進近 20 篇論文：Stitch 與 babble 功能重疊，DNS 局部競爭、Ratchet 容量門與 SMCEvolve ESS 又是三套淘汰/停滯邏輯。確定性程式搜尋硬套粒子濾波 ESS，徒增調參黑盒。

### (B) Argon 的設計提案：同構活樹、觀測指紋桶與熱棘輪量法

我們不拼裝重型外掛，而是用**一套同構資料結構＋一套暴力匹配原語**貫穿全部八條意見。

#### 提案一：「三指針活節點（Tri-Pointer Node）」與型別園區（落實意見 1、3、7）
* **類比**：**Unix `/proc` 檔案樹 ＋ 幹細胞分化**。廢除「宿主框架 vs 算子表」的割裂，解題本體、審查器、改進器全是掛在目錄樹上的同構節點。
* **具體資料格式**：每個節點即一個目錄 `parks/<park_name>/<node_id>/`，內含：
  1. `node.json`（統一契約）：
     ```json
     {
       "id": "rot_trim_07",
       "tier": "fn",
       "sig": "Grid->Grid",
       "judge": "../../judge_park/hit_rate_10",
       "improver": "../../imp_park/ast_swap_02",
       "children": ["../crop_fn_01", "../orient_agent_03"]
     }
     ```
     （`tier` 標記 `"agent" | "tool" | "fn"`；當 `children` 全部退火為 `"fn"`，父節點自動拔除 LLM 依賴升級為 `"fn"`。）
  2. `run.py`（或 `prompt.md`）：節點執行體。
  3. `ring.tsv`（固定保留最近 16 次執行的 `in_hash, out_hash, res_bits, us`）與 `inbox/` 目錄：使用者隨時 `cd` 進任何節點，`tail ring.tsv` 看即時表現，丟一行文字進 `inbox/msg`（如強制拆解、凍結、提示方向）即可在下一輪 epoch 生效。
* **園區真義**：園區按強型別簽章 `sig` 分群（如 `grid_2d`、`obj_set`、`judge_park`、`imp_park`）。同園區共享微型探針與佇列，暴力組合只在同一園區相容型別間發生，防止全局組合爆炸。

#### 提案二：「觀測指紋桶」同構自舉 ＋ 停滯雙向裂變（落實意見 2、4、5、6）
* **類比**：**硬體電路合成的 LUT（查找表）映射**，以零依賴的雜湊撞桶取代重型 e-graph，且**對審查與改進節點自我適用**：
  1. **解題園區**：固定 32 個微型標準網格作探針，節點輸出壓成 `uint64` 觀測指紋；指紋撞桶即語意等價（毫秒級自動合併 `rot90∘rot270`，免建 e-graph）。
  2. **審查園區（暴力優化審查）**：探針換成「64 條歷史成敗軌跡特徵」，輸出是 `uint64` 判決位元串；用暴力位元遮罩／深度 2 決策樹枚舉，合成耗時 $<10\mu\text{s}$ 且對齊真值的新 `fn` 審查節點。
  3. **改進園區（暴力優化改進）**：收集歷史成功的 `(舊AST切片, 殘差指紋) -> 新AST切片` 配對當 ground truth，暴力反合一抽出局部替換規則，直接固化出意見 2 說的「只做特定替換的低廉改進程式」。
* **停滯雙向生長判準**：當某節點連續 $W=3$ 個 epoch 殘差無改善：
  * **往下拆（Down-split）**：檢查中間變數指紋，將跨輸入不變或已收斂的前半段切出為獨立 `"fn"` 子節點，縮小剩餘搜尋空間；
  * **往上長（Up-grow）**：若卡住的是改進節點 $I_1$，在 `imp_park` 生成二階節點 $I_2$ 掛入 `I_1.improver`，專責對 $I_1$ 的替換權重與算子表做暴力回歸。

#### 提案三：「熱棘輪雙軌帳本」與三個硬量法（落實意見 8）
* **類比**：**模擬退火棘輪（Thermal Ratchet）**。主樹允許非單調震盪：只要某改動開闢出前所未見的「新殘差指紋簇」，即使總分小退（在容忍溫度 $\beta$ 內）仍予保留；旁路僅用一個唯讀符號連結 `parks/BEST -> snapshot_k` 保底，徹底拔除零回歸死鎖。
* **帳本格式**（根目錄 `epochs.jsonl`，每輪一行）：
  ```json
  {"ep":12, "mdl_gain_bits":142.6, "fn_ratio":0.84, "cpu_s":3.2, "llm_tok":0, "res_clusters":27}
  ```
* **三個核心量法**：
  1. **邊際淨壓縮 $\Delta L(v)$（一把尺取代 TTL 與 Nmin）**：
     $$\Delta L(v) = \sum_{t} \big(H(Y_t) - H(Y_t \mid v)\big) - |v|_{\text{code}}$$
     沒完全解開但壓低了殘差條件熵（部分見證）也給正位元分；節點程式碼越肥扣越多。當 $\Delta L(v) \le 0$ 即標記可退休（交人確認），不必苦等 100 次試驗。
  2. **結晶率 $\sigma_{\text{fn}}$（量意見 3 固化進度）**：全樹解題與改進呼叫鏈中，`tier == "fn"` 佔總執行步數的比例（目標由初期 $<0.2$ 推向 $>0.98$）。
  3. **錘子自舉斜率 $\gamma_{\text{hammer}}$（量意見 5 錘子升級）**：計算滾動視窗 $K=5$ 輪內，「每 CPU 秒敲出的淨壓縮位元率 $\frac{\Delta \text{MDL}}{\text{CPU\_s}}$」的線性回歸斜率。單輪容許上下起伏，只要 $\gamma_{\text{hammer}} > 0$，就證明我們不只是多解了幾題，而是**錘子本身的敲擊效率正在升階**。
