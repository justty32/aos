## 0 一句話

第五輪的「壓縮」只做**零 LLM 的機械歸納**：被同判決更短規則蓋住的 91 條標 `covered`、嵌詞表 9 個「X後／後X」收成一條模板、短名嵌長名寫成一個函式；反判決的留成死記例外；量「條數、留出題不掉、換題不掉」。LLM 歸納本質推到第六輪。

## 1 「本質」在這個語料上的形狀

兩種都要，但是同一份資料的三種 `kind`，不另開檔：

```
# W/distill/rules.jsonl 每條加欄位
kind:      general | exception | covered | literal
parent:    <被它蓋住／它所例外的規則 id>，literal 為空
pattern:   {side:"left"|"right"|"both", text:"〈", tmpl:null}
           tmpl 只允許固定模板：null（字面）或 "X後"/"後X"/"X尾"（單字＋固定位）
verdict:   link | nolink
stats:     {fired, right, wrong}   # 既有欄位不動
```

- **general（一般化）**：同側、同判決、文字是另一條前綴／後綴的更短規則；被蓋住的改 `kind: covered, parent: <general id>`，不觸發、不刪、影子計分。04 §2 的 91 條直接套。
- **exception（差異記錄）**：跟某條 general 同側、文字包含它、**判決相反**。匹配時長的先比。這就是「只記與既有記錄的差異」。
- **literal（死記）**：找不到 parent 的孤兒，維持原樣。
- **嵌詞表** `K/index/inword.json` 拆兩區：`tmpl: ["X後","後X"]`（一條本質吃 9 筆）＋ `literals`（其餘 14 筆死記）。
- **短名嵌長名**：本質是函式 `embedded_in_longer(name, left, right) -> bool`：緊鄰字是漢字、不在嵌詞表、不在修飾尾、非標點 → 判「嵌在更長的未知名字裡」不連。配死記例外 `K/index/short_ok.json`（已知可連的「短名＋鄰字」，起步空）。
- **不碰**：名字表（是事實不是規則）、修飾尾（已是本質）、事實表（路線已關）。

## 2 誰歸納、多久、LLM 花多少、怎麼退回

- **誰**：腳本 `distill compress`，零 LLM，只做三件事：算蓋住、算反判決例外、inword 收 tmpl。語意歸納（孤兒之間找共同本質）第五輪不做（Q1）。
- **多久**：每批收輪跟 live／shadow／candidate 升降（代定 74）同一步跑，不另加時機。
- **LLM**：第五輪壓縮流程 LLM 呼叫數 = 0。這是量法 f 的硬門檻。
- **怎麼知道錯了**：general 有 `stats`，covered 也影子計分。任一成立標 `suspect` 進隊長名單：(a) general 在新題錯連 ≥ 2；(b) general 的 wrong 率 > 其 covered 子規則合計 wrong 率 ＋ 5 個點。
- **怎麼退回**：`distill uncompress <id>`：general 降一級，子規則從 covered 恢復到 `covered_from` 存的原等級。降級自動；升級照代定 74。

## 3 死記例外怎麼留、留多少

- 例外就是 `kind: exception` 那些條，留在同一份 rules.jsonl，不另開檔；短名嵌長名的例外在 `short_ok.json`。
- **不設上限**（代定 45）。但例外數是健康指標：某 general 的例外觸發 ≥ 它自己觸發的 20% → 標 `suspect`，隊長決定拆回 literal 或留。
- 例外不能再有例外：深度 ≤ 1。一條既是例外又想當 general 的，直接當 literal。
- 匹配時 literal＋exception 永遠先於 general：**具體贏一般**，這是「壓縮會丟東西」的唯一兜底。

## 4 跟節點池（02／03）共用與不共用

**共用（形狀與術語，不共用資料）**

- 「新東西先找最像的」同一形狀：節點池 `defs ls` → `lineage.reuse_checked`；規則池 `find_parent(rule)` → `parent`。欄位名統一 `parent`、`reason`。
- 「對錯統計 ≈ 錢」：`stats` 是規則層餘額，到門檻只標 `suspect` 建議、不自動刪，同 02「扣到 0 只建議退休」。
- 「封存不是刪」：covered 留原檔，跟 `defs.retired/` 同精神。

**不共用**

- 規則不是節點（02 已定）：不進 `_gradients.jsonl`、不進 `pool/config.json#/cost`、不用抽象分數（規則沒 token 成本）。
- 退休機制不共用：規則用代定 74 的三級升降＋`covered`，不用 `pool retire/revive`。
- 理由：C-56，兩個池各自可試、各自可退場。

## 5 第五輪最小可試版本與量法

**做**（施工單隊長補細節，gpt 系照單施工）：

- M1 `distill compress`：蓋住歸併＋反判決例外＋inword tmpl。
- M2 匹配器：exception／literal 先、general 後、covered 只影子計分。
- M3 `distill uncompress <id>`＋`suspect` 判定進收輪報告。
- M4 `embedded_in_longer` 函式＋`short_ok.json`，掛在 linker 連結前。

**不做**：LLM 語意歸納、任意正則、跟 pool 腳本整合。

**量法**（在第四輪留出 113 題＋第五輪新題上跑，壓前壓後同題對比）：

| 項 | 門檻 | 不過怎麼辦 |
|---|---|---|
| a 條數 | 有效規則（general＋exception＋literal，不含 covered）≤ 110（186 的 −40%） | M1 沒壓到東西，想法 21 在規則池語料停，寫檢討 |
| b 留出題不掉 | 覆蓋 ≥ 36%、純度 ≥ 80%（第四輪 T 後值）；掉 > 3 個點算掉 | 整批 uncompress，查哪條 general 害的 |
| c 換題不掉 | 第五輪新題上，壓後覆蓋 ≥ 壓前（同題） | 同 b |
| d 短名嵌長名 | 第三、四輪已知 5 例擋住 5/5；誤擋（原本對的連結被擋）≤ 2/90 | M4 退回代定 73 兜底，`short_ok` 擴充不算修 |
| e 例外膨脹 | exception 總數 ≤ general 數 × 3 | 例外比本質多，說明一般化方向錯，拆回 literal |
| f LLM | 壓縮流程 LLM 呼叫 = 0 | 違反就不是第五輪該做的 |
| g 退回可用 | 注入一條錯 general，uncompress 後子規則等級 100% 恢復 | M3 沒過 M1 不上 live |

**退場**：a 或 b 任一不過 → 想法 21 第五輪收、不進第六輪；d 不過只退 M4，不牽連 M1～M3。

## 6 邊緣狀況處置表

| 狀況 | 處置 |
|---|---|
| 壓縮會丟東西（04 §4-1） | 只標 covered 不刪；反判決留 exception；具體贏一般 |
| 本質靠 LLM 歸納（04 §4-2） | 第五輪零 LLM，只做機械歸納；孤兒 literal 留著等第六輪 |
| 本質過時（04 §4-3） | `suspect` 兩訊號＋`uncompress` 自動降級；子規則等級存 `covered_from` |
| 效率怎麼量（04 §4-4） | §5 a／b／c 當代理；186 條量級看不出「大專案效率」，不宣稱證明 |
| 跟想法 20 共用結構（04 §4-5） | §4：共用形狀與術語，不共用資料與腳本 |
| 兩條 general 互蓋 | 只在文字相等時發生，留 id 小的，另一條 covered |
| general 想蓋 live 規則 | general 自己也要是 live；否則先進 shadow，子規則不動 |
| 例外的例外 | 不允許，深度 ≤ 1，降成 literal |
| 一條規則是兩條 general 的子 | 認最長的那條，`parent` 單值 |
| tmpl 誤匹配過寬（「後」吃掉人名尾字） | 只有固定三型，命中仍過 `embedded_in_longer`；誤擋計入 d |
| 舊格式 rules.jsonl | 不遷移，第一次 compress 補 `kind: literal` 重建 |

## 7 衝突

**衝突 1：想法 21 vs C-56／02 衝突 4（第五輪只做帳＋封存）**
壓縮是第五輪第三個新機制。全做 → 出錯分不清誰的；不做 → 違使用者 11-08 排法 A。**推薦**：做，但只做 §5 零 LLM 機械版、掛在 distill 肚子裡、不碰 pool 腳本，兩邊各自退場。

**衝突 2：想法 21「記本質」vs C-22／11-07 檢討（削減 LLM）**
本質靠 LLM 歸納，等於主要功能仍壓在 LLM 上，正是 11-07 擔心的；零 LLM → 語意本質歸納不到。**推薦**：第五輪零 LLM，先看機械壓縮能壓多少（a）；孤兒 literal > 50% 再開 Q1。

**衝突 3：壓縮「刪」規則 vs 鐵律 2（刪要授權）／代定 45（改善側只記錄）**
真刪 → 違鐵律；不刪 → 檔案不縮。**推薦**：不刪，covered 留原檔；「條數」量有效條數，檔案行數不是指標。

**衝突 4：general 蓋住 live 規則 vs ad-3（退休永遠隊長按）**
live 被蓋住實質等於退休。自動蓋 → 違 ad-3；全要隊長按 → 91 條按不完。**推薦**：只有 live 子規則被蓋需隊長按（6 條內），shadow／candidate 自動；uncompress 自動，因為是恢復不是退休。

**衝突 5：使用者目標「大專案效率」vs 當前語料量級**
186 條量級省下的成本量不出來；硬量 → 數字沒意義；不量 → 沒判準。**推薦**：量 a／b／c 當代理，檢討明寫「只證明不掉命中率，沒證明效率」，大方向不改。

**衝突 6：M4 寫死 `embedded_in_longer` vs 代定 73（不補詞兜底）**
73 是「不補詞」，M4 是「看鄰字」，兩層可能互相擋。**推薦**：M4 疊在 73 之上不改 73，d 的誤擋 ≤ 2/90 就是兩層打架的量法；過不了只退 M4。

## 8 方向題

**Q1 LLM 語意歸納（孤兒 literal 之間找共同本質）第五輪開不開**
- A｜不開，孤兒留 literal｜零 LLM，但壓縮率受限於機械可見的本質
- B｜開，每批收輪 ≤ 1 次呼叫、≤ 2k token、只進 candidate｜多一個變數，但能看到 LLM 歸納的本質形狀
- C｜全開，LLM 直接重寫規則池｜違 C-22，且無法對照
**推薦 A**。理由：a 的數字出來再決定要不要花 LLM。

**Q2 本質的表達形式**
- A｜只允許字面＋三型固定模板（X後／後X／X尾）｜能寫死、可枚舉、誤匹配可控
- B｜任意正則｜表達力強，但 LLM 寫的正則難審、誤匹配難量
- C｜自然語言描述由 LLM 執行｜最像「啟發式」，但每次匹配都花 LLM
**推薦 A**。理由：C-22，三型已覆蓋 04 §2 看到的全部本質。

**Q3 covered 規則最後命運**
- A｜永留原檔｜最安全，檔案只增不減
- B｜連續 3 批 covered 且 parent 不曾 suspect → 進隊長名單，隊長按才移到 `rules.retired.jsonl`｜檔案能縮，照 ad-3
- C｜compress 當場刪｜違鐵律 2
**推薦 B**。理由：跟節點池「只建議、隊長按才封存」同一套話，使用者已裁過。

**Q4 短名嵌長名邏輯放哪**
- A｜當規則池一條 general（side: both）｜統一在一個池，但規則格式要加「鄰字類別」
- B｜linker 裡一個函式＋`short_ok.json` 例外｜最直接，C-22
- C｜嵌詞表擴成「名字用字表」逐筆死記｜百科式，正是想法 21 要避的
**推薦 B**。理由：它判的是「鄰字是不是名字用字」，不是字面，塞進規則格式會撐歪。

**Q5 嵌詞表 9→1 要不要做**
- A｜做，當 M1 的 tmpl 示範｜數字小看不出效果，但證明模板這一型能跑
- B｜不做，23 筆太小不值得｜少一件事，但 tmpl 這型就沒實例
**推薦 A**。理由：唯一現成零風險的「本質」實例，不另設量法，掉了退回 literal。
