## 0. 一句話

每個定義資料夾是一個「節點」；上級用一行「梯度」（一句改進方向＋分數＋證據）投進它的信箱；一支腳本 `pool` 每個 epoch 照實際用量算錢、分錢、扣錢；錢扣到 0 只是「建議退休」，隊長按了才封存（不刪）。審查流程仍是現在的審視者，只是多讀信箱。

## 1. 節點

- **什麼算節點**：有 `_metainfo.json` 的定義資料夾。快照（image）不算，它是節點跑起來的實例，錢和梯度都歸回定義。蒸餾規則一條不算，`distill` 整個定義才算（規則是它肚子裡的資料）。
- **最小紀錄**（兩個檔，都放節點資料夾裡）：
  - `_gradients.jsonl`：信箱，一行一封，見第 2 節。
  - `_metainfo.json` 多一欄 `improve`：指標路徑，指向池中負責改我的節點，省略＝`reviewer`。
- **錢包不放節點裡**，集中在 `$AOS_WS/pool/wallets.json`（餘額）＋ `pool/ledger.jsonl`（每筆收支），只由 `pool pay` 腳本寫（C-22：能寫死的用程式）。節點自己不碰錢。

## 2. 梯度

- **形狀**：一行 JSON：`{t, epoch, from: 上級節點名, case: 證據路徑, say: 一句改進方向, score: -1～+1}`。score 像老師打分：-1 很不滿、0 沒意見、+1 很好。
- **誰寫**：第五輪只有兩種人寫——使用者／隊長寫給頂層節點（就是「我們給的方向」）；`review_round` 審視完上級節點後，對它叫過的子工具各寫一行（審視者本來就看呼叫樹）。一般 agent 不寫（保 C-52，見衝突 3）。
- **多上級怎麼綜合**：改進者（審視者）處理一個節點時讀完它信箱所有未處理的信，依 score 絕對值大的優先；處方開完把處理過的信標 `handled: <review id>`。不加權不投票，先用最笨的。
- **不合意就複製**的判準（規則，不靠 LLM 感覺）：同一節點連續 2 個 epoch 收到兩個上級 score 符號相反、且審視者處方只能滿足一方 → 第七步寫建議 `specialize`，由隊長按 `agents new --reason specialize`（ad-3 前三次隊長按，之後可自動）。複製品歸要求方上級，引用由該上級改指；原節點留給另一方。

## 3. 改進流程＝指標路徑

- `improve` 用 C-71 語法：`"reviewer"`（池中節點名）或 `"reviewer#/flows/strict"`（指到該節點某個檔的某段）。第五輪全樹都省略＝`reviewer`，所以跟現況一樣，一條線都不用改。
- `review_round` 不改七步，只加三處：第一步讀目標的信箱當輸入；處方換上後把信標 handled；第七步退休建議多一個輸入「餘額」（第 5 節）。
- **審查鏈停點**：最多 2 層。節點 → 它的 `improve` → 那個節點的 `improve`；指回自己、指到已走過的、或為空 → 停，交隊長。`reviewer` 的 `improve` 留空＝隊長人工（C-84 續：審視者做得好就不必改）。第二層只有在 reviewer 連續 2 epoch 處方接受率 < 50% 才由隊長開。

## 4. 節點池

- **放哪**：就是 `$AOS_WS/defs/`（ad-5），不新造目錄。
- **找輪子**：`defs ls 關鍵字` → `defs dup` 看同質組，夠用。新規矩一條：`agents new` 前必跑 `defs ls`，查過的名字寫進 `lineage.reuse_checked`。這樣「重複造輪子」可以數。
- **封存區**：`$AOS_WS/defs.retired/<名>/<時間>/`（defs 工具說退休樹放 defs 根旁同層）。`defs ls` 預設不搜，`--all` 才搜。復活＝`pool revive <名>`：搬回去＋頂層撥一筆起始金。
- **資產抽出**：kit 既有，不動。封存區不進 kit。

## 5. 錢財制度

全部是起步值。

- **單位**：token（kernel 帳 usage 的 prompt＋completion），1 元＝1k token。不另造貨幣，生活費就等於實測用量，不用換算。
- **錢從哪來**：每個 epoch（＝一批任務跑完＋一次 review_round）給頂層節點預算＝上一 epoch 全樹實耗 ×1.2（多 20% 是給長新東西的餘裕）。第一個 epoch 用第四輪 A 批 kernel 帳算基數。
- **截留**：每層留 20%，80% 往下分（頂層也一樣）。
- **往下怎麼分**：腳本算，不靠上級判斷。一半按「靜態引用」（`defs refs`，被引用一次算一份），一半按「本 epoch 實叫用量」（measure 呼叫樹逐節點 tokens）。梯度 score 只做乘數 0.5～1.5，不是主因。沒被引用也沒被叫＝0。只分一層：我分給我直接叫的，它再分它的。
- **生活費**：每 epoch 扣該節點本 epoch 實耗 tokens。來源用 measure 的呼叫樹（kernel 帳 `sender` 只到 ws、不到定義；若要精準，`agents ask` 把定義名寫進 sender 是一行改，第六輪再說）。
- **扣到 0**：不刪、不自動封存。連續 3 個 epoch 餘額 0 → 第七步列「建議退休」，隊長按 `pool retire <名>` 才搬進封存區（沿用 promote 的 `DefBusy` 檢查）。
- **複製的錢**：複製品的起始金＝原節點上 epoch 收入 ×1，從要求複製的上級錢包撥；撥不出就不能複製。每 epoch 最多複製 2 個。
- **為什麼不會通膨**：預算＝實耗 ×1.2，分下去又被生活費扣掉，淨增只有頂層截留的那點；那筆錢就是「生孩子錢」。

### 八條邊緣狀況處置

| # | 狀況 | 處置 |
|---|---|---|
| 1 | 功勞分錯餓死好節點 | 分配是算的不是判的（引用＋實叫），梯度只做 0.5～1.5 乘數；退休要隊長按，分錯最多慢一輪 |
| 2 | 少用但關鍵 | 一半靜態引用份保底；連續 3 epoch 才列建議；備案：`_metainfo.json` 標 `essential: true` 不列退休（隊長手標，起步 ≤ 5 個） |
| 3 | 複製膨脹、初始資金 | 上級付生孩子錢，付不出就不能生；每 epoch ≤ 2 個 |
| 4 | 扣到 0 刪或封存 | 封存到 `defs.retired/`，`defs ls --all` 找得到，`pool revive` 復活。git 在，刪也回得來，但先不刪 |
| 5 | 審查節點也在池 | reviewer 也有錢包、也記帳，但不列退休（代定 45，見衝突 2）；鏈最多 2 層，到 reviewer 止 |
| 6 | 引用成環 | 分配沿本 epoch 實測呼叫樹（已展開、無環）且只分一層、不回流；靜態引用份環內各算一份、不遞迴 |
| 7 | 共用節點被兩上級並行改 | 不並行：兩方的信都進同一信箱，由該節點的 improve 一次處理（審視者一次一處方＋promote `DefBusy`）；先後按 epoch 時間；誰認看下一 epoch 的 score，不認就走複製 |
| 8 | 正在跑時扣到 0 | 沒有「扣到 0 立刻動作」；退休是建議，隊長按時 `pool retire` 沿用 `DefBusy`，忙就等下一 epoch |

## 衝突

1. **ad-3「退休永遠隊長按」／鐵律 2 刪檔要授權 vs 原話「扣到 0 就刪掉」**。照原話：池自動瘦身快，但會誤殺少用節點、違反兩條既有規矩。照 ad-3：慢一輪，不會誤殺。**推薦照 ad-3**：錢只產生建議，隊長按才封存，封存不是刪。
2. **代定 45「改善側只記錄、不設上限」vs 審視者也扣錢**。扣：審視者可能因為貴被退休，正是代定 45 要防的。不扣：審視者成本看不見。**推薦記帳但免死**：reviewer 有錢包、有帳，餘額 0 不列退休。
3. **C-52／C-53「上層不該知道下層是什麼」vs 上級分梯度、分錢給子節點**。讓 agent 自己分：它得知道子結構、還得學會算錢。讓腳本分：agent 只收預算、只寫「給工具名」的一句話（它本來就知道工具名，不知道那是 agent 或腳本）。**推薦腳本分、審視者寫梯度**，一般 agent 完全不知道有錢和梯度這回事。
4. **C-56 KISS vs 使用者自評「這比較複雜」**。全套上：一輪驗證多個新機制，哪個壞了分不清。只做帳：少一半機制，但能先驗「錢是不是比『連續 N 輪沒被叫』更好的退休訊號」。**推薦第五輪只做帳＋封存**（見方向題 Q3）。

## 方向題

**Q1 錢的單位**
- A｜純 token（1 元＝1k token）｜最簡單、跟 kernel 帳一對一；看不見牆鐘時間。
- B｜token＋時間（例：1k token＋10 秒各 1 元）｜第四輪並行吞吐那種「快」會被獎勵；但兩個單位要定匯率，匯率本身又是起步值。
- C｜複雜性分數（想法 16 式抽象）｜最靈活；第五輪沒有基礎數據可黏。
- **推薦 A**。理由：先讓錢等於一個現成的數字，匯率等第六輪有兩輪資料再定。

**Q2 梯度誰能寫**
- A｜只有審視者（review_round）＋隊長／使用者寫頂層｜一般 agent 不知道有梯度，守住 C-52；但梯度全靠審視者一雙眼。
- B｜任何 agent 叫完子工具可以順手寫一行（想法 5 呼叫者視角）｜訊號多、即時；每個 agent 的定義都要加一段「寫梯度」，而且 agent 寫的分數不一致。
- **推薦 A**。理由：第五輪先看審視者一雙眼寫出來的梯度有沒有用，B 是純加法、隨時可加。

**Q3 第五輪做到哪**
- A｜只做帳：`pool pay`、信箱、退休建議多一個輸入；不封存、不複製｜最小，但「池膨脹受控」量不到。
- B｜帳＋封存＋復活（`pool retire/revive`，隊長按）；複製照現況由第七步建議、隊長按 `agents new`｜量得到池大小與退休訊號品質；複製不自動。
- C｜全套含「不合意就複製」自動化｜最接近原話；一輪驗太多東西。
- **推薦 B**。理由：B 新造的只有一支 `pool` 腳本，其他全是現有工具；C 的自動複製等 B 的退休訊號被驗證再開。

## 第五輪最小可試版本

**不動第四輪**：第四輪 `PG` 唯讀；先用第四輪 A 批的 kernel 帳＋measure 結果離線跑一次 `pool pay`，當「第 0 epoch」看錢的分布合不合直覺（餓死名單 vs 隊長人工判斷）。這一步今天就能做，不碰生產。

**新造的東西只有一支腳本** `L/pool`：`pay`（算一個 epoch 的分配與扣款，寫 wallets.json＋ledger.jsonl）、`grad`（往節點信箱 append 一行）、`retire`／`revive`（mv ± `DefBusy`）。`review_round` 加三處（第 3 節）。`agents new` 加 `reuse_checked`。其餘沿用。

**試在哪片樹**：第五輪新試驗場，defs 從第四輪 kit 抽出；錢和梯度只開在「第一線 agent＋它直接叫的子節點」（約 5～8 個定義），其他節點只記帳不分錢。順了再開全樹。

**量什麼算有效果**（起步判準，第五輪結束時看）：

| 指標 | 判準 |
|---|---|
| 池大小 | 定義數 ≤ 起點 ×1.3 |
| 重複造輪 | `defs dup` 同質組數不增；新建定義 100% 有 `reuse_checked` |
| 退休訊號品質 | 餘額 0 名單 vs 隊長人工「可退休」名單重合 ≥ 2/3；錢 0 但隊長認為關鍵的 ≤ 1 個 |
| 改進效率 | 帶梯度的處方接受率 ≥ 第四輪基線；每處方審視成本不升超過 20% |
| 成本 | 單任務平均 token ≤ 第四輪 A 批 |
| 鏈長 | 審查鏈實際 1 層；第二層沒開 |

**退場條件**：退休訊號重合 < 1/3，或單任務成本升超過 20% → 關掉 `pool pay`，信箱與 `improve` 欄位留著（它們不花錢），錢財制度回到設計桌。
