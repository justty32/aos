## 1. 第 0 epoch 試算（11-08，唯讀，第四輪 A 批 20 地）

資料：`PG/runs/4/A-*/tasks/*/steps.json`（每步 definition、caller、tokens、秒數）＋`W/*/_metainfo.json#/calls`（靜態引用）。腳本在 scratchpad，沒動試驗場。

| 事實 | 數字 |
|---|---|
| 一個地點走的定義 | place_run → kb_slug、kb_store、kb_mentions、kb_link（→ linker、kb_mentions、kb_rules）、kb_tag、kb_lint2；place_run 子樹共 12 個定義 |
| 有花 token 的 | **只有 kb_link**（20 地 170.5k token、443 秒）；其他五步 0 token、合計不到 4 秒 |
| 靜態引用 | 46 個定義資料夾裡 32 個有 `_metainfo.json`；**33 個沒有任何定義宣告叫它**（batch_run、reviewer、judge 這些由隊長或批次腳本直接叫的入口）；沒有環 |
| `defs ls` 對 `W` | 失敗：`DefBad aos-agent.tools must name a file`（有一個 agent 的工具宣告壞了），`defs refs` 也跟著不能用 |

照 02 原樣算（預算＝實耗×1.2、每層留 20%、一半按引用一半按自己的用量、生活費＝實耗）跑 3 個 epoch：

1. **真正幹活的 kb_link 第一個被扣到 0**，0 token 的腳本反而越存越多（kb_mentions 存到 145）。原因：kb_link 收到的錢按「自己的用量」算，但它又得把 80% 往下分，自己留的不夠付自己的帳。→ **改 1：先報銷、再分紅**（§3）。
2. 0 token 的腳本生活費是 0，**一旦有過餘額就永遠不會到 0**，退休訊號對腳本無效。→ **改 2：每個節點每 epoch 固定扣一筆房租**（§3）。
3. 把預算綁在「實耗×1.2」時，樹越便宜錢越少，模擬「kb_link 不再被叫」後全部節點一起貼近 0，分不出誰該退。→ 預算改綁「接受的任務數」（§3），省下來的才是利潤、才有錢分紅。
4. 33 個入口定義不在任何上級底下，照「從頂層往下分」永遠是 0。→ 第五輪只開 place_run 子樹（02 已這樣定，這裡確認：12 個定義），入口定義只記帳、不分錢、不列退休。

試算用改過的規則再跑：kb_link 不再餓死；把 kb_link 用量設 0、房租 0 時餘額六輪不動（印證改 2 必要）。

## 2. 檔與格式

全部放試驗場工作區：`$AOS_WS/pool/`（錢）＋各節點自己的 `_gradients.jsonl`（信箱）。

`pool/config.json`（隊長寫）：

```json
{"root": "place_run", "scope": ["place_run"], "unit": "ktoken",
 "price_per_task": null, "price_factor": 1.2, "keep": 0.2, "rent": 1.0,
 "zero_epochs": 3, "clone_cap": 2, "essential": [], "chain_max": 2}
```

- `scope`：開錢的子樹根；不在任何 scope 子樹裡的定義只記帳。`price_per_task: null`＝用第 0 epoch 的「每任務中位 token × price_factor」算一次後寫回。
- `essential`：隊長手標免列退休，起步 ≤ 5 個。

`pool/wallets.json`（只由 `pool pay` 寫，wf-table/1）：每列 `{def, balance, zero_streak, last_epoch, status: active|retired}`。

`pool/ledger.jsonl`（只追加）：每行 `{epoch, def, kind: budget|reimburse|bonus|rent|living|clone_seed|revive_seed, amount, from, evidence}`。`evidence` 指到 steps.json 或 measure 樹的路徑（C-72 `檔#/指標`）。

`pool/epochs/<epoch>.json`：該 epoch 的輸入摘要（任務數、接受數、每節點用量）與輸出（每節點收支、建議退休名單）。

節點信箱 `<def>/_gradients.jsonl`：照 02 §2，`{t, epoch, from, case, say, score, handled}`；`handled` 初始 `null`。

`_metainfo.json` 加兩欄（選填）：`improve`（C-71 指標路徑，省略＝`reviewer`）；`lineage.reuse_checked`（`agents new` 前跑過 `defs ls` 的查詢字與結果數）。

## 3. 錢怎麼算（取代 02 §5 的「往下怎麼分」「錢從哪來」「生活費」三句）

每個 epoch（一批任務跑完）一次：

1. **用量**：每節點本 epoch 的 token（steps.json 的 `in_tokens+out_tokens`，單位千 token）。子節點用量照 steps.json 的 `caller` 歸，measure 樹有更細的就用 measure。
2. **頂層預算**＝接受的任務數 × `price_per_task`＋ scope 內節點數 × `rent`。樹變便宜→利潤變多；任務被擋→收入變少。
3. **往下分，每層一樣**：收到的錢先**報銷**——自己的用量＋每個子節點子樹的用量照實付；剩下的叫利潤，自己留 `keep`（20%），80% 照「靜態引用次數」分給直接子節點（引用來源＝`_metainfo.json#/calls` 聯集 `defs refs`）。梯度 score 平均值換成 0.5～1.5 的乘數乘在分紅份上（沒信＝1）。利潤是負的（入不敷出）就從自己的報銷份扣，不往下扣。
4. **扣款**：每節點扣自己的用量＋`rent`；扣完 ≤ 0 就記 0、`zero_streak +1`，否則歸 0。
5. **建議退休**：`zero_streak ≥ zero_epochs`、不在 `essential`、不是 reviewer → 寫進 `epochs/<epoch>.json#/suggest_retire`，並在 review_round 第七步的 retire 建議裡附上餘額。

環：分配沿 steps.json 的實際呼叫（已展開、無環）；靜態引用只算一層、不遞迴，所以環不會讓錢打轉。

## 4. `pool` 腳本（`L/pool`，Python，一支四個 op，stdin JSON／旗標同源照 aos_flags）

| op | 輸入 | 做什麼 | 錯誤代號 |
|---|---|---|---|
| `pay` | `{ws, epoch, steps: [steps.json 路徑…], accepted: N}` | §3 一次；寫 wallets、ledger、epochs | `ArgumentsBad`、`PoolMissing`、`StepsBad` |
| `grad` | `{ws, def, from, case, say, score}` | 往 `<def>/_gradients.jsonl` 追加一行；score 不在 -1～1 回錯 | `DefMissing`、`ScoreBad` |
| `retire` | `{ws, def, daemons}` | 走 promote 同一套 `DefBusy` 檢查，把定義搬到 `$AOS_WS/defs.retired/<def>/<時間>/`、wallets 標 retired | `DefMissing`、`DefBusy`、`SwapFailed` |
| `revive` | `{ws, def}` | 取最新封存搬回、從 root 撥 `price_per_task` 當起始金（記 `revive_seed`） | `RetiredMissing`、`DefExists` |

輸出一律英文、錯誤經 `tool_io`。不叫 LLM。複製（specialize）照舊走 `agents new`，起始金由隊長在按 new 後跑一次 `pay` 的 `clone_seed`——第五輪不自動化（02 方向題 Q3 推薦 B）。

## 5. 接進現有工具（改動清單）

1. **review_round**：第一步讀目標 `_gradients.jsonl` 裡 `handled: null` 的信放進審視包；處方換上後把用到的信標 `handled: <review id>`；審完上級後對它叫過的子定義各呼 `pool grad` 一次（`from`＝上級名，`say`＝處方裡跟該子定義有關的那句，沒有就不寫）；第七步 retire 建議合併 `pool/epochs/<epoch>.json#/suggest_retire`。
2. **agents new**：`lineage.reuse_checked` 選填欄，有給就照存。
3. **defs**：`ls` 預設不進 `defs.retired/`，加 `all: true` 才進；先查出 `W` 裡那個 `tools` 宣告壞掉的 agent，修定義（不是放寬 defs）。
4. **batch_run**（第五輪的版本）：批末多跑一次 `pool pay`。

## 6. 第五輪最小可試版本

- 試驗場：第五輪新開的試驗場（從第四輪 kit 抽 defs），第四輪 `PG` 不動。
- 範圍：只有 place_run 子樹 12 個定義有錢；梯度只由 review_round 與隊長寫（Q2 推薦 A）。
- 步驟：E0 用第四輪 A 批跑 `pool pay` 當基線（今天的試算即是雛形）→ 第五輪每批一個 epoch → 每批後隊長獨立寫一份「我覺得可退休」名單（**在看餘額之前寫**，免得被帶偏）。

量法（取代 02 的表裡兩項，其餘照 02）：

| 指標 | 怎麼量 | 判準 |
|---|---|---|
| 退休訊號品質 | 每批：錢的建議退休名單 vs 隊長名單；同時跟 review_round 現行「連續 N 輪沒被叫」比 | 跟隊長名單重合率 ≥ 2/3，**且不低於**「沒被叫」法 |
| 誤殺 | 錢 0 但隊長認為關鍵的 | 整輪 ≤ 1 個 |
| 錢的分布合不合理 | 每 epoch 最貴節點的餘額是否 > 0 | 第五輪每個 epoch 都 > 0（試算前的 02 規則會不過這條） |
| 其餘 | 池大小、重複造輪、處方接受率、單任務成本、鏈長 | 照 02 |

退場條件照 02。

## 代定（11-08，照推薦往下寫；可翻案）

1. 方向題 Q1～Q3、衝突 1～4 都照 fable 推薦寫進本圖紙（已放決定頁等使用者裁）。
2. 02 的「預算＝實耗×1.2」改成「接受任務數 × 每任務價」、往下分改成「先報銷再分紅」、加固定房租——試算出 02 原規則會先餓死最貴的節點、腳本永遠不退（§1）。這是細節修正、不違反原話（原話「每次的最上層改進epoch都會給最上層一筆錢」本來就是一筆錢，不是報銷），所以不另問。
3. 第五輪入口定義（沒有上級的 33 個）只記帳、不分錢、不列退休。
