跨 agent 的資源鎖往 kernel 想：現況有哪些零件、「往 kernel」的四種意思與各自的邊緣狀況、給使用者的五題；推薦「代跑式」的資源 kernel（格＝一件在飛的工作）。

# 跨 agent 資源鎖往 kernel 想（發想，2026-11-24）

← 使用者 11-24 原話：「跨agent的資源鎖這塊，可以往kernel那邊想想。」

這份只發想、不定方向。沒改任何程式、範本、知識庫，也沒實跑；下面標「沒實跑」「沒查」的是讀程式與文件的推論。

## 四句話

1. **零件幾乎都在**：kernel 骨架（收信、排隊、期限、hook）、「自己掛去跑」的零件 `runner.py`、llm kernel 的格數與優先序、`aos-lock`（有名牌、看得到誰拿著）。缺的是把它們接成「一種資源一排格子」的那一包，以及給 agent 用的入口。
2. **arena 那個「每逾時一次多叫一次 LLM」不是 aos 造成的**：agent-fsm 的 act 格不設時限，工具的時限看它自己的 `_metainfo.timeout_ms`（0＝不限）。工具卡著等的期間不叫腦。它們自己把等鎖上限寫死 180 秒才會重試。把上限放寬今天就能止血，不用等 aos。
3. **kernel 能多給的是四樣**：有先後的隊（flock 沒有）、看得到誰在用誰在等、持有者死了格子自己回來、等的人可以不卡著（輪到再叫醒）。
4. **推薦「代跑式」**：請求寫「替我跑登記過的這件工作」，kernel 有格才掛成 proc、跑完回結果。格子的生死就是那支 proc 的生死，不需要「還鎖」這個動作，邊緣狀況最少。它就是 llm kernel 的形狀，把「問腦」換成「跑一件工作」。

## 起因

arena_cheater 的意見（`/mnt/c/code/mine/arena_cheater/wf/notes/investigations/aos-feedback.md`「資源分配」「工具等鎖上限固定」）：

- 全機一次只能跑一份 Node。`arena_verify`、`arena_e2e` 兩支工具自己拿 `/tmp/aos/arena_cheater/locks/node.lock` 的 flock，每步再包一個 systemd scope（4G、400%、256 個工作）。
- 等鎖的寫法是每 50 ms 試一次不等待的 flock，上限 1～180 秒（`arena_verify/tool.py` 第 78～93 行）。試到的人拿，沒有先後。
- 鎖被別的專案佔住超過上限＝工具回 `lock_timeout`，腦再叫一次工具。4a 那次重試 4 次。

先前定過的：11-23 晚隔離等級「甲，先只防失誤」；六題的第 ③ 題「只做回報那半——有效限制、peak、OOM 看得到，鎖／排隊等准入先不做」（`wf/progress.json` 第 502 行那條）。這份是在那之後重新打開「排隊」這半。

## 現況：拿得來用的東西

| 東西 | 在哪 | 給了什麼 | 少了什麼 |
|---|---|---|---|
| kernel 骨架 | `py/tools/aos/kernel/round.py` | 每拍一輪：鎖收件箱、收信、排先後、三個 hook 時機、照判決放行／拒／留隊。不認得任何一種請求，規則由「包」給 | 沒有格數的概念，格數是包的事 |
| 掛 proc 的包 | 同夾 `procs_rules.py`、`queue_fifo.py` | `max_running`、`queue: true`（滿了留隊、先來先掛）、寄件人期限 `queue_wait_ms`、`allowed`、每支 proc 的份額 `limits` | 數的是整台 daemon 的 running，不分資源；不管工作跑完的結果 |

| 問腦的包 | `py/tools/aos/kernel_llm/` | 總格 `slots`、保留格 `reserved.high`、每包格、每後端格（`slots.py`）；排序＝級數加 aging → 期限 → 等得久（`order.py`）；每寄件人額度；窗 `slots.json`、`queue.json`、逐封帳 `ledger.jsonl`；`aos-llm ls` 最後一行印在飛幾封、排隊幾封 | 只收問腦信（`request.messages` 必有） |
| 寄件人死活 | `kernel_llm/docs/01-用法.md` 第 47 行 | 同步的 `aos-llm ask` 在信裡放 `sender.flock` 並鎖到行程結束；kernel 試鎖得到＝人走了，還在排的信直接刪 | 非同步的信不判死活 |
| `aos-lock` | `cpp/aos-lock/` | mkdir 掛名牌 `holder.json`（誰、何時、備註）、`--wait-ms`、租約按格算、庫持有者死了別人可以收 | 命令列 `acquire` 拿完就退出，死了不回收（要自己 `release` 或給租約）；每 20 ms 重試、沒有先後；沒有「拿著鎖跑一個指令」；沒有 agent 工具 |

請求怎麼進出：請求是一封 aos-post 的信，寄進 kernel 的 `requests/`；kernel 每拍（300 ms）是一個新行程，做一輪就結束；回信寄到信封的 `reply_to`。同步的寄件人自己等回信（`aos-llm ask`、`aos-agent ctl` 都是），非同步的之後再來收。

llm kernel 的格怎麼算：一格＝一封「掛出去還沒收」的信。上一輪還在飛的加這一輪新掛的不超過 `slots` 才放行；沒格的信留在 `new/` 不回信，下一輪再排。**格子是 kernel 自己掛的 proc 佔的，proc 結束就還**，所以它沒有「誰忘了還」的問題。這一點是下面比較的關鍵。

## 「往 kernel 想」的四種意思

### 甲：代跑式（推薦）

請求＝「跑 `arena_verify` 這件工作，參數如下」。kernel 設定裡登記資源與工作，寫法比照 llm kernel 的端點包：

```json
{"resources": {"node": {"slots": 1}},
 "jobs": {"arena_verify": {"exec": "jobs/arena_verify", "needs": ["node"], "timeout_ms": 600000}}}
```

- 一輪：收跑完的工作、回結果 → 看排隊的信 → `needs` 的資源都有格才交給 `runner.mount`；沒格留隊。
- 信只能選工作的代號，改不了它跑什麼（同端點包「信只能選代號」）。這條一定要有：工作是跑在 kernel 那台 daemon 底下，不在寄件人的沙箱裡；收任意指令就等於替受限的 agent 開了一個出口。
- 份額順手就有：工作是 daemon 的 proc，`limits`（含整支的 cgroup 上限 `mem_total_mb`、`procs_total`）可以寫在登記裡，取代它們自己包的 systemd scope。（沒實跑；Node 在 `mem_mb` 下會壞，要用 `mem_total_mb`。）
- 新寫的量：一包規則（驗信、算格、回信），骨架與 runner 不用改。估 300～500 行 Python 加測試；沒細算。

### 乙：發牌式

請求＝「要一格 node」。kernel 有格就回信「給你了」，持有者在自己那邊做事，做完寄一封「還了」。

- 好處：資源可以跨好幾個回合拿著（開著的瀏覽器、dev server），工作在持有者自己的環境與沙箱裡跑。
- 代價是邊緣狀況全落在「還」上：忘了還、持有者死了、回信晚到時格子空等。要有租約加續租，或持有者全程鎖著一個 flock 讓 kernel 判死活。這些 `aos-lock` 已經各有一半。
- 一件工作要兩種資源時會互等（甲拿了 A 等 B、乙拿了 B 等 A）。甲式由 kernel 一輪內一起給或都不給，不會發生。

### 丙：不寫新包，用現成的掛 proc 站

一種資源＝一台專用的子 daemon，前面放一個 `procs-kernel` 站，`max_running: 1`、`queue: true`、`count_daemon` 指那台。要跑的人經這個站 `add` 一支 proc。

- 今天就能排出來，零新程式。（沒實跑。）
- 缺：站只管「掛不掛」，工作跑完的結果、退出碼要寄件人自己去那台的表與 stack 看，跑完還要自己拔列。這正是 `runner.py` 在做的事。所以丙加上 runner 與回信，就長成甲。可以當甲的第一刀試水。

### 丁：不碰 kernel，只出工具

`aos-lock` 加一個「拿著鎖跑一個指令」（庫版的鎖，持有者死了別人能收），再包成 agent 工具；等待不設上限。

- 解決的：每個專案不用自己寫 flock；名牌看得到誰拿著（合「可觀測」）；不再有逾時重試。
- 沒解決的：沒有先後、看不到誰在等、等的人只能卡著。
- 量最小。跟甲不互斥：甲的工作在跑的時候也可以順手拿這把鎖，讓不走 aos 的人（人在殼裡手動跑 npm）跟它互斥。

「把 llm kernel 的 slots 一般化」不單獨算一種：它是甲、乙的做法問題（格數與排序要不要抽成共用模組），見第 5 題。

## 跟「准入不做」的界線

先前不做的是「aos 替你擋」。這裡四種都只到「你來排，我才排你」：

- 不預設開。沒登記資源的樹，行為跟今天一樣。
- 不擋繞過的人。直接跑 npm、自己拿 flock 的，kernel 不知道也不管。跟知識庫對權限站的說法一致：是給守規矩的 proc 的規則，不是牆。
- kernel 只在三種情況拒：工作代號沒登記、寄件人自己給的期限過了、設定壞了。沒格不算拒，是等。

會越線的做法（都不推薦，列出來）：在每支會用 Node 的工具前面強制過站；替沒來排的 proc 數格子；格滿時把別人正在跑的工作停掉。

## 等的方式，以及跟閒置輪詢的接點

| | 同步等 | 非同步、輪到叫醒 |
|---|---|---|
| 做法 | 工具寄信後卡著等回信（同 `aos-llm ask`），信裡帶 `sender.flock` | 工具寄完就回「排第幾」，agent 收工；結果由 kernel 寄進 agent 的 `queue/` |
| 叫腦幾次 | 1 次（工具結果直接回給腦） | 2 次（一次看到「已排隊」，一次被叫醒） |
| 等的時候 | 不讀信、不回話 | 照常收信、做別的 |
| 寄件人死了 | kernel 試鎖得到，排著的直接刪 | 判不出來，照跑（同 llm kernel 對非同步信） |

- 只算叫腦次數，同步反而省。非同步買到的是「等的時候還能做事」。
- eca（Claude Code）經 MCP 叫工具時，它那邊對單次工具呼叫的時限是多少，沒查。很長的等待在 eca 上可能只能走非同步。
- **叫醒要寄 `queue/` 不寄 `mailbox/`**：寄 `mailbox/` 要等 `mail_notify`（最晚 60 秒）。甲式晚到只是晚知道；乙式晚到的那段格子空佔著。
- **跟閒置輪詢的閘（`aos-idle`，[02-切法](../閒置輪詢C++重寫-1124/02-切法.md)）**：
  - 等的 agent：閘看到 `queue/new` 有信就放行，所以叫醒不用新機制，延遲最多一拍（300 ms）。保底拍 60 秒接住漏的。
  - 資源 kernel 自己：也是每拍起一支 Python 的站，閒著時一樣該掛 `aos-idle kernel`（`requests/new`、`requests/cur` 都空就跳過）。有工作在飛時 `cur/` 不空，每拍照跑去收成品，跟 llm kernel 同一個形狀。使用者對那邊第 4 題的答覆是「kernel 先只掛閘」，這台照辦即可。
  - [03 的 2a／2b](../閒置輪詢C++重寫-1124/03-優化方向.md)（poke、inotify）不是這件事的前提。

## 邊緣狀況

以甲為主；乙不一樣的另標。

1. **工作跑到一半死了**：`runner.settle` 看 daemon 的表，proc 沒了就收，格子下一輪回來。乙：要靠租約到期或 flock，才知道持有者死了。
2. **工作卡住不結束**：登記裡的 `timeout_ms`，到了 daemon 整群收。沒寫＝不限，格子會一直佔著，所以登記時應該必填。
3. **重掛**：runner 對「被收掉、死在半路」的會自動重掛一次。E2E 這種跑一半重來會留髒資料的工作不該重掛，要有一個「不重掛」的開關。（runner 現在有沒有這個開關，沒查。）
4. **工作留下的孤兒行程**：daemon 逾時收的是整群；工作自己再開 systemd scope 的話，scope 裡的行程不一定跟著死。這跟六題第 ② 題「工具死掉時 scope 收乾淨才放資源」是同一件，用 daemon 的 cgroup 上限取代 scope 可以一起解。（沒實跑。）
5. **寄件人在排隊時死了**：同步的有 `sender.flock`，kernel 刪信、不白跑。寄件人在工作跑的時候死了：llm kernel 的做法是照跑完、回信沒人收就撤；資源比腦貴，可以改成馬上停。兩種都做得到，要選一個預設。
6. **kernel 或那台 daemon 重起**：排隊的信、在飛的工作（`cur/<信>/proc.json`）都在 stack 裡，重起後照舊接。
7. **kernel 停著**：信留在 `requests/new/`，同步的寄件人一直等。llm kernel 的說法是「agent 只等、不失敗」；資源這邊寄件人自己帶期限比較合理。
8. **跨 daemon、跨專案**：kernel 是一個信箱路徑，寫得到的都能用。「全機一份 Node」要全機只有一台，放根 daemon，位址用環境變數往下傳（同 `AOS_LLM_KERNEL`）。沙箱裡的 agent 要把那個信箱列進可寫路徑。寄件人是誰 kernel 不驗（同 llm kernel 的已知限制），合「只防失誤」。
9. **不走 aos 的使用者**：人在殼裡跑 npm，kernel 看不到。要跟他們互斥，工作跑的時候同時拿一把約定位置的 flock（arena 現在那把就可以）。
10. **優先級與插隊**：`order.py` 的級數、aging、`reserved.high` 可以照搬。第一刀先來先跑就夠；arena 沒提過要插隊。
11. **一件工作要多種資源**：甲在一輪內全有才放行。隊首的大工作會被後面的小工作一直超過；llm kernel 用 aging 處理，這裡可以先規定「隊首沒格就擋住後面要同一種資源的」（掛 proc 那包現在的做法）。
12. **觀測**：窗比照 llm kernel——每種資源幾格、誰在跑（工作代號、寄件人、開始時間）、誰在排（第幾、等多久）；逐件帳記等了多久、跑了多久、退出碼。六題第 ③ 題要的 peak、OOM 可以記在同一行。再給一支 `ls`。這一塊完全在「可觀測」之內，四種裡甲給得最全。
13. **工作的環境不是寄件人的**：cwd、環境變數、身分都是登記時定的。結果檔寫到哪要在參數裡講明，寄件人的工作區路徑要用絕對路徑傳。
14. **一拍 300 ms 的顆粒**：放格到下一件開始，最多慢一拍。對分鐘級的 Node 工作沒差；毫秒級的互斥不該走 kernel，用 `aos-lock`。

## 給使用者的五題

大方向是使用者的。推薦只是照上面查到的排的。

### 第 1 題：「往 kernel 想」走哪一種

- a. **甲 代跑式**：請求是登記過的工作，kernel 有格才跑、回結果（推薦）
- b. 乙 發牌式：請求是一格，持有者自己做事、自己還
- c. 丁 只出工具：`aos-lock` 加「拿著鎖跑指令」，不碰 kernel
- d. 都先不做，只回 arena「把等鎖上限放寬」

**推薦 a。** 格子跟 proc 同生死，不用處理「忘了還」「死了沒還」「回信晚到空佔」；多種資源不會互等；觀測最全；份額可以一起登記。b 只有在資源要跨回合拿著時才需要，arena 的兩支工具都是「跑一段就結束」。不管選哪個，d 那句話今天就可以先回給 arena。

### 第 2 題：界線——這樣算不算先前不做的「准入」

- a. **不算：只排自己來排的人，不預設開、不擋繞過；工作只收登記過的代號**（推薦）
- b. 算，維持不做：那就只剩第 1 題的 c 或 d
- c. 做硬一點：會用到資源的工具一律要過站

**推薦 a。** 跟隔離等級「只防失誤」同一條線，也跟權限站「是規則不是牆」的說法一致。「只收登記過的代號」不是為了擋人，是因為工作跑在寄件人的沙箱外。

### 第 3 題：等的方式

- a. **先做同步等（工具卡著、不叫腦），非同步叫醒排第二刀**（推薦）
- b. 一開始就兩種都做
- c. 只做非同步

**推薦 a。** 同步只叫腦一次，寄件人死活判得出來，做法跟 `aos-llm ask` 一樣。非同步要多一則叫醒訊息的格式、判不出寄件人死活，等有人真的需要「等的時候還要回話」（多半是 eca）再做。

### 第 4 題：放哪、幾台

- a. **根 daemon 上一台，全機共用，位址用環境變數往下傳；工作跑的時候另拿一把約定的 flock，跟不走 aos 的人互斥**（推薦）
- b. 每棵樹自己一台
- c. 併進 llm kernel 那台

**推薦 a。** 「全機一份 Node」本來就是機器層級的事，分樹各一台就鎖不住別的專案。c 省一個行程，但 llm kernel 的設定與帳會混進不相干的東西，壞了也互相拖累。變數名、範本夾名照 C-54 由 eca-aos 與使用者定。

### 第 5 題：怎麼蓋、第一刀多大

- a. **新寫一包資源規則接在骨架與 runner 上；第一刀只有「每種資源幾格、先來先跑、同步等、窗與 `ls`」，格數與排序的程式先不從 llm kernel 抽共用**（推薦）
- b. 先用丙（現成掛 proc 站加專用子 daemon）排一個食譜給 arena 試，不寫程式
- c. 先把 llm kernel 的格數、排序抽成共用模組，再蓋資源包

**推薦 a。** 骨架那層 11-13 定的是「框架只做 hook 加判斷，上限是包的事，可以簡單」；第一刀的格數只是一個計數，抽共用要動剛穩的 llm kernel，等兩包真的長出重複再抽。b 可以當 a 之前的半天試驗：它驗得到「排隊加專用 daemon」這個形狀對不對，但結果要寄件人自己撈，arena 用起來不會比現在的工具順。

## 不列成題目、順手記的

- arena 的等鎖上限 180 秒是它們工具自己寫的；aos 這邊工具不設時限就能一直等、不叫腦。回 main 時可以先講這句。
- `aos-lock` 的命令列 `acquire` 拿完就退出、死了不回收，agent 拿它當資源鎖會留下死鎖（除非給租約）。知識庫 `aos/cli/parts/lock.md` 有沒有講清楚，沒查。
- 知識庫 `aos/kernel.md` 開頭就把 kernel 定義成「資源管理加排程」，但現成的只有掛 proc 與問腦兩種請求。資源包做出來，是第三種。
