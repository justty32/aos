# 03 優化方向

← [入口](README.md)｜上一份 [02](02-切法.md)

## 估算用的底

都拿報告第 3 節（`wf/ws/eca-aos/eca-aos-core/report-1124.md`）的數，機器滿載時量的。

| 項 | 數 |
|---|---|
| 閒置輪詢合計 | 約 4.3 核（8 核機） |
| 閒著的 eca 9 隻 | 約 2.4 核（每隻 0.23～0.29；一拍 170～200 ms） |
| 閒在 idle 的 fsm 7 隻 | 約 1.6 核（每隻 0.19～0.24；`idle.py` 120～140 ms） |
| llm kernel 1 台 | 約 0.24 核（一拍約 190 ms） |
| context_wrap | 約 0.23 核（每秒 2.3 支、每支約 100 ms；**已經算在 eca、fsm 那兩列裡**） |
| `_clock` | 0.07 核 |
| 每隻每秒拍數 | 1.2～1.7 |
| C++ 小程式起一次 | 約 1 ms（`aos-fsm --help` 1.2 ms；這次量 0.6～0.7 ms） |

下面的「剩多少」都是估的，寫「約」。每刀做完要照報告的量法再量一次。

## 0. 主幹：C++ 的閘

[02](02-切法.md) 寫的那一套。放在這裡是為了跟其他方向比。

- **效果**：閒著的一拍從 120～200 ms 變約 1 ms（fsm 連 `aos-fsm` 都不起）。
  - eca 9 隻、fsm 7 隻的輪詢本身：約 4.0 核 → 約 0.03 核（16 隻 × 1.5 拍 × 1 ms）。
  - **但 on_clock 會讓閘放行**。`context_wrap` 每 5 秒到一次，每次放行要起身體（eca 約 0.19 秒、fsm 約 0.13 秒）加 handler（約 0.1 秒）。算下來 eca 9 隻約 0.5 核、fsm 7 隻約 0.3 核，合計約 0.8 核。**所以閘一定要跟第 6 節（context_wrap 的頻率）一起做**，不然 4.3 核只降到約 1.2 核。
  - context_wrap 改成 60 秒之後：每隻每分鐘放行一到兩次（context_wrap、mail_notify 各 60 秒，再加保底拍），16 隻合計約 0.1～0.15 核。
  - kernel 掛閘：整棵樹都沒人問腦時 0.24 → 約 0.005 核；有人在問腦時不省。
- **代價**：C++ 約 600～900 行，引擎約 100 行，Python 約 40 行，範本每份一行。
- **風險**：閘漏擋＝退回現在的行為，沒事。閘錯擋＝agent 該動沒動，最晚保底拍接回。錯擋的來源只有「Python 的決定看了記號以外的東西」，靠 [02 的對等測試](02-切法.md#對等驗證)抓。

## 1. 閒置退避、拉長 interval

兩種：固定拉長（改 `interval_ms`），或閒越久拉越長（退避）。

- **效果（沒有閘時）**：報告算過，interval 拉到 1／2／5／10 秒，剩約 2.0／1.1／0.5／0.25 核。
- **效果（有閘之後）**：閘的輪詢只剩約 0.03 核，再拉長到 2 秒也只是變 0.008 核。幾乎沒有意義。
- **代價**：
  - 固定拉長：今天就能做，不用寫程式。`ctl.json` 的 `interval_ms` 執行中改、不用重起；loop.json 的要重起。
  - 退避：aos-loop 約 60 行（連續跳過或連續「沒事」N 拍後把間隔乘 2，到上限；有事那拍歸位）。「沒事」要有訊號：有閘就是閘退 10；沒閘的話身體沒事也退 0，loop 分不出來，要另外約定結束碼。
- **風險**：閒著的 agent 最晚 N 秒才看到新信。fsm 的 wait 格也跟著慢（等腦回信多等 N 秒）。kernel 拉長＝每一封問腦的信都慢。
- **定位**：**閘做出來之前的止血**。現在就把閒著的 agent 的 `ctl.json` 改成 1000 ms，馬上省約 2.3 核，代價是回信慢 0.7 秒。要不要做是營運的決定（ops 或使用者）。

## 2. 有信或有事才醒

讓 loop 平常睡著，有事才被叫醒，不再每 300 ms 看一次。兩條路。

### 2a. poke：寄信的人順手叫醒收件人

aos-loop 引擎已經有 `wake_`／`woke` 掛鉤（`cpp/aos-loop/src/engine/loop.cpp` 的 `nap`），aos-daemon 用它接 `aos-daemon-ctl poke`。aos-loop 自己沒接。

- 做法：aos-loop 也宣告一個喚醒訊號、寫進 `state.json`；`aos-post send`、`aos-agent say` 寄完信，照收件人的 state 窗送訊號（比對 pid、`started_at_ticks`、`boot_id`，用 pidfd 送，跟現成的 `py/aos/daemon_ctl/poke.py` 一樣）。
- 代價：aos-loop 約 60 行；寄信那邊要從信箱路徑找回是哪個 stack，C++ 的 `aos-post` 與 Python 各一份，約 150 行。
- 風險：11-09 的 [daemon-interrupt 04](../../09/daemon-interrupt/04-方向題與結論.md) 討論過——寄件人跑在沙箱或別的帳號時送不了訊號；寄件人要知道收件人的 pid，跟 no-pid 的方向相反。當時的結論是訊號只給 daemon 叫自己的子項用。
- 只解決「信」。冷卻到期、on_clock 還是要有人看時間。

### 2b. inotify：loop 自己盯著資料夾

- 做法：`nap` 從 `sigtimedwait` 改成 `ppoll`（或 signalfd）同時等訊號與一個 inotify fd。盯 `queue/new`、`ctl.json`（kernel 盯 `requests/new`、`requests/cur`）。有動靜就提前算一圈。盯哪些路徑寫在 loop.json 的新鍵（例 `"wake": ["queue/new"]`）。
- 效果：
  - CPU：有閘之後只剩約 0.03 核可省，幾乎是零。
  - **延遲**：新信從「最晚 300 ms」變成幾毫秒。這才是它買到的東西。
  - 有了它，`interval_ms` 可以放心拉到 5～10 秒當保底，閘的那 1 ms 也跟著少。
- 代價：引擎約 200～300 行，動的是 `nap`——每一支 loop、daemon 都走的地方。
- 風險：
  - 資料夾被刪掉重建（`aos-post init`、reset、clone）後 watch 會失效，要重掛。
  - 事件滿了會丟（`IN_Q_OVERFLOW`），要當成「有動靜」。
  - WSL：ext4 上正常；`/mnt/c` 上從 Windows 那邊改的檔收不到事件。
  - 所以 interval 輪詢一定要留著當保底，不能拿掉。
- 要算「下一次該醒是什麼時候」（冷卻的 `until`、on_clock 的下一個 cycle）才能真的睡久。這要閘在行程內、能回「最晚幾毫秒後再問我」，也就是 [02 的乙](02-切法.md#三種深度)。

**定位**：排在閘之後。閘做完先量，如果剩下的 0.03 核與 300 ms 延遲都可以接受，這個方向可以不做。

## 3. 常駐 vs 每拍起

讓身體變成一支一直活著的 Python，loop 每拍只是戳它一下。

- **效果**：起動成本整個消失，閒著與忙著都省。閒著的部分跟閘一樣約省 4 核；忙著的部分是閘省不到的（fsm 每一輪工具呼叫要起 `brain.py`、`wait.py`、`act.py`，每支 100 ms 上下）。
- **代價**：
  - 記憶體：每支 Python 約 20～30 MB，17 隻約 0.4～0.5 GB。報告說記憶體不緊。
  - 身體跟 loop 之間要新的協定（管線或 socket），aos-loop 的 `run_once` 要多一種跑法。
  - 「一拍是一支獨立行程」是現在很多東西的前提：逾時怎麼殺、訊號怎麼轉（P-36）、出錯退 1 就收工、`sys.exit` 到處用。常駐之後每一條都要重想。
- **風險**：
  - 改了 `py/` 跑 `install.py` 不會生效，要重起每一隻。現在是下一拍就用新的。
  - 兩拍之間的狀態殘留（模組層的變數、快取）。現在每拍都是乾淨的。
  - 一支 Python 掛了或漏記憶體，要有人重起。
- **定位**：跟閘不互斥，但對「閒置」是重複的；跟使用者說的「用 C++ 重寫」也不是同一條路。**不建議現在做**。之後如果重點變成「忙的時候每輪的起動成本」，再跟 [02 的丙](02-切法.md#三種深度)（整支改寫成 C++）一起比。
- 唯一值得單獨考慮常駐的是 kernel，見第 5 節。

## 4. 減少 fork／exec 與起動成本

幾個小項，各自獨立。

### 4a. 補 `.pyc`（這次量到的）

`lib/` 有 208 支 `.py`，只有 25 支有 `.pyc`。原因：`install.py` 抄 `py/` 到 `lib/` 時跳過 `__pycache__`，生出來的入口又有 `sys.dont_write_bytecode = True`，工具的 `_entry` 也有。結果大部分模組每次起動都從原始碼重新編譯。

- **效果**（[06](06-這次補量的數字.md)，交錯各量 25 次）：

  | 指令 | 現在 | 全部有 `.pyc` | 省 |
  |---|---|---|---|
  | `aos-eca-turn --help` | 178 ms | 93 ms | 48% |
  | `kernel_llm --help` | 138 ms | 75 ms | 45% |
  | `idle.py --help` | 124～157 ms | 81～103 ms | 約 35% |
  | `aos-hook --help` | 83 ms | 58 ms | 31% |
  | `aos-clock --help` | 70 ms | 48 ms | 32% |
  | `context_wrap --help` | 81 ms | 63 ms | 22% |

  照比例估，閒置輪詢 4.3 核 → 約 2.6 核（eca 2.4→1.3、fsm 1.6→1.05、kernel 0.24→0.13、clock 0.07→0.05）。**忙的時候每一支 Python 也一樣省**（`brain.py`、`act.py`、每個工具、`aos-mcp`），這是閘給不了的。
- **代價**：`install.py` 抄完 `lib/` 之後跑一次 `compileall`，約 10 行。
- **風險與要先問的**：
  - 現在有一條明寫的慣例「不在庫的資料夾留 `__pycache__`」（`kernel_llm/_entry` 的註解；定義資料夾是 P-15）。`lib/` 是 `install.py` 的產物、被 git 忽略，裡面已經有 25 個 `.pyc`，所以實務上沒在守。但這是改慣例，要使用者點頭（[05 第 5 題](05-給使用者的題目.md#第-5-題要不要先補-pyc)）。
  - 不想讓 `lib/` 裡有 `__pycache__` 的話，可以用 Python 的 `pycache_prefix`：`.pyc` 全放到另一棵樹（例 `$AOS_HOME/.pycache/`），入口設 `sys.pycache_prefix`。`_entry` 那種直接被 `aos-exec` 起的要靠環境變數 `PYTHONPYCACHEPREFIX`，要確認每一層 daemon 都帶得到。
  - `.pyc` 會對原始碼的修改時間，手改 `lib/` 也不會用到舊的。
  - `install.py` 抄完會 `prune` 掉 `lib/` 裡 `py/` 沒有的東西。`__pycache__` 會不會被它清掉要讀那一段確認；會的話就把編譯放在 `prune` 之後，每次裝完重編一次。
  - 定義資料夾（`templates/`、使用者自己的定義）不在這條裡，照舊不寫。

### 4b. 少 import、晚 import

`aos-eca-turn` 一起來就 import 整包：`slash`、`cli_ask`、`cli_print`、`handoff`、`midturn`（136 個模組）。閒著那條路用不到大部分。

- 效果：補了 `.pyc` 之後還剩約 90 ms，其中 Python 自己約 25 ms、`json`＋`subprocess` 約 20 ms，aos 自己的約 45 ms。把 import 往後挪，大概再省 20～30 ms。
- 定位：有閘之後閒著根本不起，這項只對「忙的時候」有用，而且每次只省幾十毫秒。**優先度低**。

### 4c. `python3 -S`／`-I`

報告量過：`-I -S` 比預設省約 18 ms（這次量到 12 ms）。入口要自己處理 `sys.path`。小錢，風險是使用者環境的 site-packages 用不到。不建議單獨做。

### 4d. 閘不 fork（行程內）

閘做成函式庫之後，aos-loop 直接連進來呼叫，省掉每拍 1 ms 的 fork。約 0.03 → 0.003 核。本身不值得，是 2b 的前置。

### 4e. hook 起兩層 Python

loop 的四個點現在是 `aos-hook fire`（Python）再起 handler（多半也是 Python）。`on_start`／`on_stop` 只在起停時跑，不在熱路徑上。`before_run`／`after_run` 沒人掛。現在不用管；哪天有人掛了每拍的 hook，就要有閘（閒著不發）或把 `aos-hook fire` 改成 C++。

## 5. kernel 的 run-once 改法

現在 aos-daemon 每 300 ms 起一支 `kernel_llm`，跑一輪就退。四條路：

| | a 掛閘 | b 閘再聰明一點 | c 常駐 | d 整支 C++ |
|---|---|---|---|---|
| 做什麼 | `requests/new`、`cur` 都空就不起 | 有在飛的信時也擋：只在「有新信、有一封飛完了、額度窗換了、某個期限到了」才起 | `kernel_llm --serve`：自己一個迴圈，每圈跑現在的一輪 | `kernel_llm` 與 `kernel` 骨架約 3200 行 Python 改寫 |
| 整棵樹沒人問腦時 | 0.24 → 約 0.005 核 | 同 a | 約 0.01 核（一輪的實際工作很少） | 約 0.005 核 |
| 有人在問腦時 | 不省，照舊 0.24 核 | 約 0.02～0.05 核 | 約 0.01～0.02 核 | 約 0.005 核 |
| 代價 | 第 0 節已含 | C++ 要讀 `cur/<信>/` 裡問腦那支行程的記錄、對 daemon 的表，判斷飛完了沒；約 200 行，而且要跟 `runner.settle` 的判法對齊 | Python 約 80 行；daemon.json 從「身體」改成「一列常駐的 proc」；kernel 範本與文件要改寫法 | 很大 |
| 風險 | 小 | 中：判「飛完了沒」是兩份實作 | 中：改了程式要重起 kernel；例外沒接好整台停（靠 `auto_restart`）；「kernel 是 daemon 的身體」這個模型變了 | 大 |

- kernel 整台只有一支，常駐的記憶體成本可以不計，這點跟 agent 不一樣。
- 樹上只要有一隻 agent 在工作，kernel 就一直有信在飛，a 等於沒省。**a 是閒置時的解，b／c 才是平常的解**。
- 推薦：先做 a（跟著閘順手就有），再量「有人在問腦的時間佔多少」。佔得多再做 b 或 c；兩個選哪個是[第 4 題](05-給使用者的題目.md#第-4-題kernel-走哪條)。

## 6. context_wrap 的頻率

現在每 5 秒一支，整棵樹每秒約 2.3 支、約 0.23 核。有了閘之後它更貴：每次到了都要連身體一起起（第 0 節算過，約 0.8 核）。

它看的東西只在一輪跑完時才變（[01 第 4 節](01-閒著時判斷了什麼.md#4-on_clock-的-hookcontext_wrap)），所以有三種改法：

| | a 拉長到 60 秒 | b 加「有變才跑」 | c 改掛在一輪結束 |
|---|---|---|---|
| 做什麼 | 四份 `hookeds.json` 的 `every_ms` 5000 → 60000 | on_clock 的 hook 多一個選填鍵（例 `"when_changed": ["history.jsonl", "letters.json", "queue"]`）：這些檔跟上次跑時一樣就不起 handler，也不算到了 | 不掛 on_clock，改成身體每次真的跑完後發的一個點 |
| 效果 | 0.23 → 約 0.02 核；配閘時每隻每分鐘多放行一次 | 閒著時 0；忙著時照 5 秒 | 閒著時 0；忙著時每輪一次 |
| 代價 | 範本四行 | `hooks.py`（鍵的檢查）、`hook_clock.py`（比記號、算進摘要檔）約 60 行，hook 的文件與測試 | 要有那個點：eca 的 `after_run` 現在失敗會收工，規矩跟 on_clock（失敗只是 warning）不一樣；fsm 沒有「一輪結束」的點，要新開 |
| 風險 | 「該收尾了」的信最晚晚 60 秒寄到。35% 的門檻離滿還很遠，晚一分鐘不礙事 | 小；鍵是選填的 | 中：動 hook 的點與規矩 |
| 使用者會不會感覺到 | 會，慢一點 | 不會 | 不會 |

推薦先做 a（最便宜，跟閘同一刀），b 排在後面當正解。使用者 11-15 定的是「門檻用 35%」；5 秒這個間隔我沒找到他定的紀錄，看起來是實作時取的。頻率要不要動是[第 3 題](05-給使用者的題目.md#第-3-題context_wrap-多久看一次)。

**同一份清單上的 `mail_notify`（60 秒）**：有了 2a 或 2b 的喚醒之後它可以更快甚至即時，但那是另一題，這裡不動。

## 7. 共用一個行程看多隻 agent

讓一支行程替很多隻 agent 做閒置判斷，不是每隻一支 loop 各看各的。

- **放在哪**：最自然的是父 daemon。它本來每圈就在看每個子項（判卡住、收結束的），多看一眼子項的信箱，沒事就不叫醒子項的 loop——等於把 2a 的 poke 做成「daemon 叫自己的子項」，這正是 11-09 那次裁定允許的用法。
- **效果**：有閘之後每隻 loop 的閒置成本約 0.002 核，17 隻加起來 0.03 核。集中到一支也就省這些。行程數不會少（每隻的 aos-loop 還在）。
- **代價**：daemon 要認得子項的信箱在哪（現在它不看子的信箱，是 11-06 明確裁定的）；子項的 loop 要能「一直睡到被叫」。
- **風險**：父 daemon 變成單點；跟「每層只管自己」的分層相反。
- **定位**：**不建議**。它要解的問題（每隻各自輪詢太貴）閘已經解掉了。只有在 agent 數量到幾百隻、連每隻一支 aos-loop 都嫌多的時候才值得回頭看。

## 8. 其他

- **`_clock` 改 C++**：`aos-clock` 每秒一支 Python，0.07 核 → 約 0.001 核。約 50 行 C++，最簡單的一刀。或者補了 `.pyc` 先降到 0.05。
- **`_clock` 的節奏**：它是整棵樹 on_clock 的時基（1 秒）。拉長會讓所有 on_clock 變粗，不建議動。
- **wait 格**：[01 第 5 節](01-閒著時判斷了什麼.md#5-報告沒算到的fsm-的-wait-格waitpy)。同一個閘再多認一格。等腦的每隻 fsm 省約 0.2 核；冷卻中的也是。樹越忙省越多。
- **`mail_notify`、`timer`**：60 秒、300 秒一次，每次會讓閘放行。16 隻合計約 0.05 核。`timer` 的 handler 什麼都不做，只是留個位置；有閘之後它每 5 分鐘白起一次身體，可以考慮範本預設關掉。小錢。
- **顯示端與量測**：做完之後 `aos-view`、daemon 表上閒著的 agent 會一直是 `waiting`。可以順手在 `aos-agent ctl ls` 加一欄「上次真的跑身體是什麼時候」（讀 `idle_gate.json` 的 `passed_at_ms`），方便看閘有沒有在擋。
- **每刀都重量一次**：報告的量法（讀每支 aos-loop 的 `cutime+cstime`）可以包成一支常備的腳本，放進 `wf/tools/`，每刀做完跑一次、數字記進進度條目。
