# 06 這次補量的數字

← [入口](README.md)｜上一份 [05](05-給使用者的題目.md)

主要的量測在報告（`wf/ws/eca-aos/eca-aos-core/report-1124.md` 第 3 節），這裡只補寫規劃時多量的。

- 時間：11-24 上午 11:10 前後（本機時間），公司 WSL，8 核，當時 load 約 12～13。
- 只跑 `--help` 與 `ps`。沒起停任何 daemon，沒叫模型，沒讀別人的 history、信箱、environ。
- 腳本與複本都在 `~/.aos/scratch/idle-cpp-plan-1124/`。
- 機器有負載，同一個指令兩輪之間會差到兩三成。下面的數字看比例，不要看到個位數。

## 1. 現在有幾支

`count.sh`（只讀 `ps`）：`aos-loop` 29 支、`aos-daemon` 22 支。

## 2. 起動一次的 CPU

`startup.py`，每個指令跑 15 次取平均（user＋sys，讀子行程的 rusage）。

| 指令 | CPU | 其中 sys |
|---|---|---|
| `/bin/true` | 0.6 ms | 0.1 |
| `aos-fsm --help` | 0.7 ms | 0.0 |
| `aos-post --help` | 0.6 ms | 0.1 |
| `python3 -c pass` | 25 ms | 4 |
| `python3 -I -S -c pass` | 13 ms | 3 |
| `python3 -c 'import json, subprocess'` | 44 ms | 8 |
| `aos-eca-turn --help` | 123 ms | 22 |
| `idle.py --help` | 61 ms | 11 |
| `kernel_llm --help` | 103 ms | 14 |
| `context_wrap --help` | 58 ms | 11 |
| `aos-hook --help` | 71 ms | 16 |
| `aos-clock --help` | 55 ms | 9 |

- 比報告的數低（報告：`aos-eca-turn --help` 200 ms、`idle.py --help` 146 ms）。報告是 8 核全滿時量的，這次 load 低一些。兩次的比例一致：靜態連結的 C++ 小程式不到 1 ms，Python 的入口是它的 80～200 倍。
- **閘的成本就拿「C++ 小程式起一次約 1 ms」估**。閘另外要做的事（十來次 `stat`、列兩個資料夾、讀兩三個小 JSON）是微秒級。

## 3. `lib/` 幾乎沒有 `.pyc`

- `find lib -name '*.py'`：208 支。`find lib -name '*.pyc'`：25 支（只在 `aos/__pycache__/` 與 `aos/agentlib/__pycache__/`）。
- 原因：
  - `install.py` 的 `copy_lib` 抄 `py/` 到 `lib/` 時跳過 `__pycache__`；
  - 生出來的入口（`ENTRY`）有 `sys.dont_write_bytecode = True`；
  - 工具的 `_entry` 也各自設了（註解寫「不在庫的資料夾留 `__pycache__`」）。
- 所以多數模組每次起動都從原始碼重新編譯。有的那 25 支，應該是哪次沒經過入口直接跑時留下的。

### 補齊之後省多少

`pyc2.py`、`pyc3.py`：把 `lib/` 複製兩份到 scratch，`libraw` 照原樣、`libcopy` 跑過 `compileall`。同一個指令兩份輪流各跑 25 次（交錯，抵掉負載的起伏）。

| 指令 | 現在（libraw） | 全部有 `.pyc`（libcopy） | 省 |
|---|---|---|---|
| `aos-eca-turn --help` | 178 ms | 93 ms | 48% |
| `kernel_llm --help` | 138 ms | 75 ms | 45% |
| `idle.py --help`（第一輪） | 124 ms | 81 ms | 35% |
| `idle.py --help`（第二輪） | 157 ms | 103 ms | 35% |
| `aos-hook --help` | 83 ms | 58 ms | 31% |
| `aos-clock --help` | 70 ms | 48 ms | 32% |
| `context_wrap --help` | 81 ms | 63 ms | 22% |

這一輪量的時候負載比第 2 節高，所以「現在」那一欄比第 2 節的數大。比例是穩的。

照比例套到報告的閒置輪詢：eca 2.4 → 約 1.3 核、fsm 1.6 → 約 1.05、kernel 0.24 → 約 0.13、`_clock` 0.07 → 約 0.05，合計 4.3 → 約 2.6 核。這是估的，沒在活樹上驗。

`idle.py` 自己是被直接執行的那支，本身不會有 `.pyc`（Python 不快取主程式）；省的是它 import 的模組。三分之後它搬進 `lib/aos/apps/agent_fsm/`，同一套辦法照樣適用。

## 4. import 的錢花在哪

`imports.sh`（`python3 -X importtime`，累計時間由大到小）。

`aos-eca-turn --help`：共 import 136 個模組，累計約 120 ms（這個旗標自己會讓時間變長，只看相對大小）。

| 模組 | 累計 |
|---|---|
| `aos.apps.eca`（整包） | 約 120 ms |
| 　`aos.apps.eca.common` | 51 ms |
| 　　`aos.agentlib.cli_ask` | 43 ms |
| 　`aos.apps.eca.turn` | 42 ms |
| 　　`aos.apps.eca.slash` | 18 ms |
| 　`aos.flags` | 23 ms |
| `site` | 20 ms |
| `json`、`re`、`threading`、`subprocess` 這幾個標準庫 | 各 8～13 ms |

`idle.py --help`：102 個模組。大的是 `site`（15 ms）、`subprocess`（11 ms）、`pathlib`（11 ms）、`json`（10 ms）、`urllib.parse`（6 ms）、`aos.agentlib.agent_hooks`（7 ms）。

看得出來的事：

- eca 閒著那條路用不到 `slash`、`cli_ask`、`cli_print`、`handoff`、`midturn`，但一起來就全 import 了。
- 就算把 aos 自己的 import 全拿掉，Python 加幾個標準庫也要 40 ms 上下。**在 Python 裡面再怎麼省，一拍也下不到 C++ 的 1 ms 的四十倍以內**。這是閒置判斷該搬到 C++ 的根據。
