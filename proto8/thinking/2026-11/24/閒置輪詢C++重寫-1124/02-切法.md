## 三種深度

「用 C++ 重寫閒置輪詢」可以切在三個深度。選哪個是使用者的題目（[05 第 1 題](05-給使用者的題目.md#第-1-題重寫到多深)），這裡先比。

| | 甲：閘＋小程式 | 乙：內建進引擎 | 丙：整支改寫 |
|---|---|---|---|
| 做什麼 | 新寫一支 C++ `aos-idle`。loop／daemon 每拍先叫它，它說沒事就不起身體 | 同一套判斷連進 aos-loop、aos-daemon，行程內直接問，不 fork | `aos-eca-turn`、`idle.py`、`kernel_llm` 整支用 C++ 重寫 |
| 閒著一拍的成本 | 約 1 ms（多一次 fork 加 exec 靜態連結的小程式） | 約 0.05 ms（幾次 `stat`、兩次列資料夾） | 約 1～2 ms |
| 新的 C++ | 約 600～900 行（含測試以外的全部） | 甲的全部，再加引擎約 100 行 | 近一萬行：eca 那邊 Python 約 1900 行加 `agentlib` 約 4800 行；kernel 兩包約 3200 行（`kernel_llm` 1700、`kernel` 1500） |
| Python 要改 | 只有 `hook_clock.py` 多寫一個摘要檔 | 同甲 | 三支退場，測試全部重對 |
| 兩份實作會不會走鐘 | 不會：C++ 不重做 Python 的判斷，只看「有沒有變」 | 同甲 | 沒有兩份，但改寫期間新舊要逐條對 |
| 跟條文的關係 | loop.json、daemon.json 多一個選填鍵 | 引擎要認得「信箱」「冷卻」這些 agent 的東西，跟 C-52「loop 不知道身體是什麼」衝突 | 不動介面 |
| 忙的時候省不省 | 不省（wait 格例外，見第 5 刀） | 同甲 | 省：每一輪的起動也變快 |
| 風險 | 小：閘壞了就放行，退回現在的行為 | 中：引擎的錯會影響每一支 loop、daemon | 大：eca 的畫面、收件口、重試、slash 都是近兩週才穩的 |

**推薦甲，而且把判斷寫成函式庫**（`libaos-idle.a`），命令列只是薄薄一層。這樣之後要升成乙（為了事件喚醒，見 [03 第 2 節](03-優化方向.md#2-有信或有事才醒)）不用重寫。丙留到「忙的時候的起動成本」變成下一個重點時再談。

下面都照甲寫。

## `aos-idle`：一支只回答「這拍要不要跑」的小程式

暫名；照 C-54 的命名規則，名字由 eca-aos 與使用者定。位置 `cpp/aos-idle/`，跟其他 C++ 專案一樣一個 lib 加一支薄命令列，連 aos-util、aos-post（列信箱）與 nlohmann json。

```
aos-idle eca    [--max-skip-ms N]
aos-idle fsm    [--idle NAME] [--wait NAME] [--max-skip-ms N]
aos-idle kernel [--max-skip-ms N]
```

- 要 `AOS_STACK`。`fsm` 另外讀 `$AOS_STACK/stage.txt`；`--idle`、`--wait` 是那兩格在 `fsm.json` 的名字，預設 `idle`、`wait`。
- **結束碼**：0＝這拍要跑；10＝確定沒事，跳過；1＝自己出錯（stderr 一行 `aos-idle: error: 代號 原因`）。跟 `on_before_run` 的「退 10＝跳過這一圈」同一個意思。
- **原則：只擋確定沒事的**。檔讀不懂、資料夾少了、摘要是別次 loop 寫的、任何沒想到的情況，一律回 0。
- `--max-skip-ms`：保底拍，預設 60000。離上次放行超過這麼久就回 0。0＝不保底。
- 每種的判斷順序照 [01](01-閒著時判斷了什麼.md) 各節的「最小集合」。

### 它自己記的一個檔

`$AOS_STACK/idle_gate.json`（暫名），**只在放行時寫**，跳過的拍不碰任何檔：

```json
{"loop": ["<boot_id>", 12345, 678910], "passed_at_ms": 1795484557450, "sig": {"cooldown": "none", "goal.json": [inode, size, mtime_ns, ctime_ns], "history.jsonl": [...], "queue/new": [], "queue/cur": []}}
```

- `loop`：這次 loop 是誰（讀 `$AOS_STACK/state.json` 的 `boot_id`、`pid`、`started_at_ticks`，跟 `hook_clock.py` 的讀法一樣）。換了＝第一拍，放行。
- `sig`：放行**之前**取的記號。下一拍取到的跟它一樣，而且信箱是空的＝Python 上次就是看著這個狀態決定沒事的，這次也會一樣。
- 先寫 `.idle_gate.json.<pid>.tmp` 再改名（N-05）。寫不成＝印一行 warning、回 0。

### 為什麼「記號一樣就是沒事」站得住

Python 那一拍的決定只看三樣：stack 裡的檔、現在的時間、畫面被不被佔。

- **檔**：都在記號裡。Python 跑完檔沒變，再跑一次也是同樣的結果。Python 跑的時候改了檔（收了信、丟了 goal），下一拍記號就不一樣，會再放行一次；那一次沒再改，才開始跳過。所以每次真的做事之後，會多一拍「確認沒事」的 Python，跟現在每拍都起比是零頭。
- **時間**：只有兩處看時間——冷卻的 `until` 與 on_clock。這兩處 C++ 自己算。
- **畫面被佔**：只在有信的時候才看。有信一律放行。

**記號取在放行之前**，所以「取完記號、Python 還沒讀」之間寄來的信會被 Python 看到；「Python 讀完之後」寄來的信會讓下一拍的記號不一樣。兩邊都不會漏。

### 記號的弱點

這台 Linux 6.6 的檔案修改時間是粗的（跟著核心的 tick，約 1～10 ms）。同一個 tick 裡改兩次、大小又一樣，修改時間會相同。擋法：

- 信箱不看修改時間，直接列名字。
- `cooldown.json`、`goal.json`、`retry.json`、`compact.json` 都是「寫暫存檔再改名」，inode 會換。記號含 inode 與 ctime。
- `history.jsonl` 只附加，大小會變。
- Python 起動至少 10 ms 以上才讀到檔，比一個 tick 長。
- 最後一道是保底拍：真的漏了，最晚一個保底時間後接回來。

stack 放在 `/mnt/c`（WSL 的 Windows 磁碟）時修改時間更不可靠。現在兩台的 stack 都在 ext4。要支援那種位置，就把那隻的 `--max-skip-ms` 調短，或不掛閘。

## `gate` 鍵：loop.json 與 daemon.json 各多一個選填鍵

```json
{"exec": {"argv": ["aos-eca-turn", "--on-empty", "idle", "--on-busy", "yield", {"$env": "AOS_CD"}], "timeout_ms": 0},
 "gate": {"argv": ["aos-idle", "eca"]},
 "interval_ms": 300, "…": "…"}
```

- 寫法同 `exec`（字串、陣列、單子物件）。沒寫＝行為跟現在完全一樣。
- **什麼時候問**：沒暫停、到時間了、要跑身體之前；在 `on_before_run` 之前。
- **退 10**＝這拍跳過：不跑身體、不算一次（`max` 不扣、`counter_runs` 不加）、`on_before_run`／`on_after_run` 不發、state 維持 `waiting`。下一拍＝現在加 `interval_ms`。
- **退 0**＝照現在的路走。
- **其他碼、逾時、起不來**＝印一行 warning、**照跑身體**（放行）。同一個原因只印一次，不洗 log。這跟四個點「失敗就收工」不一樣，是故意的：閘是省錢用的，壞了不該讓 agent 停。這一條要不要改成收工，寫進條文前由使用者或 eca-aos 定。
- 期限 `gate_timeout_ms`，預設 1000。
- ctl 照舊每拍讀，`pause`／`stop`／`interval_ms` 不受影響；父 daemon 判 `stuck` 看的是 ctl 的回音，也不受影響。
- aos-daemon 的 `poke --all`（強迫提前跑身體）不問閘。

**為什麼不借用現成的 `on_before_run`**：它退 10 也是跳過，機制一樣。但它已經給 hook 的 `before_run` 用（編譯時有 hook 掛那個點才寫進 loop.json），兩個用途會搶同一個鍵；aos-daemon 又不收 `on_*` 這四個鍵（寫了＝`CfgBad`），kernel 用不到。所以另開一個鍵。

**替代做法**（不推薦，列出來）：fsm 那邊不在 loop 層擋，改在 `fsm.json` 的格上加 `gate`，由 `aos-fsm` 起格之前問。好處是「哪一格是 idle」寫在定義格子的地方；壞處是要改兩個引擎（aos-loop 為了 eca、aos-fsm 為了 fsm），每拍也多一次 fork。推薦只在 loop 層做一處，`aos-idle fsm` 自己讀 `stage.txt`。

### 順帶少掉的寫檔

現在有身體的 loop 每拍寫兩次 `state.json`（`running`、`waiting`）。跳過的拍 phase 一直是 `waiting`，「有變才寫」就不寫了。每隻閒著的 agent 每秒少約 3 次寫檔。

## 跟現在不一樣的地方

掛了閘之後，使用者或別的 agent 看得到的差別。每一條都有保底拍兜底（預設最晚 60 秒）。

1. **閒著時設定壞掉，不會馬上停**。現在 `cli.json`、hook 清單壞了，下一拍（300 ms 內）就 `CfgBad`／`HooksBad` 收工，daemon 表上看得到。之後要等到有信、on_clock 到了、或保底拍才發現。hook 清單檔有進記號，改壞它當拍就會放行；`cli.json` 沒進（要進也可以，多一個 `stat`）。
2. **`before_run`／`after_run` 兩個 hook 點，閒著的拍不發**。現在有掛的話每拍都發。之後只在真的跑身體時發。現在 aos 自己的範本沒掛東西在這兩點。
3. **`state.json` 的 phase** 閒著時一直是 `waiting`，不再 `running`／`waiting` 來回跳。看 phase 判斷忙不忙的顯示端會更準。
4. **`counter_runs.txt`、kernel 的 `counter_kernel_runs.txt`** 數的是真的跑的次數。
5. **等太久的提醒**（wait 格，第 5 刀才有）最多晚一個保底時間。

三層，由便宜到貴。

1. 跑 `aos-idle`，比期望。
2. **只要閘回 10**：把同一份 stack 複製一份，照舊直接跑 Python 那一拍，斷言它的結束碼是「沒事」的碼，而且 stack 裡除了白名單（`hookeds/*/on_clock.json`、小格的 `env.json`、`idle_gate.json`）以外一個位元組都沒變。

第 2 步就是「等價」的定義：閘擋掉的每一拍，Python 本來就什麼都不會做。

### 二、同一串事件，新舊兩版跑完比結果

`templates/tests/agent-fsm/test_gate_same.py`、`py/tests/apps/eca/test_gate_same.py`（名字暫定）。同一份定義起兩次 aos-loop，一次帶 `gate`、一次不帶，餵同一串事件：寄信、等回答、寄 `/compact`、設 goal、弄一次腦失敗進冷卻、`self_hook add` 一個 1 秒的 on_clock。跑完比：

- `history.jsonl` 逐行一樣（時間欄位除外）；
- `letters.json`、`goal.json`、`compact.json` 一樣；
- on_clock handler 被叫的次數一樣（差一次以內，起跑時間不同）；
- 身體起了幾次：帶閘的要少一個數量級。這一項同時是省錢的證明。

現成的測試（`templates/tests/agent-fsm/` 27 支、`py/tests/apps/eca/`、`kernel_llm/tests/`）用的定義帶上 `gate` 之後要全過，這是最大的一張網。

### 三、活樹上先只看不擋

`aos-idle` 加一個環境變數（暫名 `AOS_IDLE_DRY=1`）：照常判斷、照常寫 `idle_gate.json`，但一律回 0，另外在 `$AOS_STACK/idle_gate.log` 記「這拍本來會擋」。掛在一兩隻真的 agent 上跑半天，看兩個數：

- 閒著時「本來會擋」的比例（預期 95% 以上；低很多表示記號裡有每拍都在變的檔，要找出來）；
- 有沒有哪一拍「本來會擋」但 Python 那拍其實做了事（比前後的 `history.jsonl` 大小與 `queue` 的名字）。有的話是閘的錯，補樣本。

第三層要起停 agent，要使用者或 ops 同意才做。
