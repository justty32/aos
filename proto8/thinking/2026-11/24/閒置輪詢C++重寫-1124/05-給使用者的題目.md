# 05 給使用者的題目

← [入口](README.md)｜上一份 [04](04-分刀與順序.md)

大方向是使用者的。下面每題我列選項、給推薦與理由，由他定。第 1、2 題不回，第 1 刀之後動不了；第 3、4、5 題可以晚一點回。

## 第 1 題：重寫到多深

「用 C++ 重寫閒置輪詢」，寫到哪一層？比較表在 [02](02-切法.md#三種深度)。

- **a 閘＋小程式**：新寫一支 C++（暫名 `aos-idle`），每拍先問它，確定沒事就不起 Python。Python 那幾支不動，只在有事時才起。閒著一拍約 1 ms。新的 C++ 約 600～900 行。
- **b 內建進引擎**：同一套判斷直接連進 aos-loop、aos-daemon，不 fork。閒著一拍約 0.05 ms。引擎要開始認得「信箱」「冷卻」這些 agent 的東西。
- **c 整支改寫**：`aos-eca-turn`、`idle.py`、`kernel_llm` 整支換成 C++。近一萬行 Python 要重寫，忙的時候也變快。

**推薦 a**，而且判斷寫成函式庫，之後要升成 b 不用重寫。

理由：

1. 4.3 核裡約 4 核是「起 Python」的錢，a 就拿得掉；b 比 a 多省的只有約 0.03 核。
2. a 的 C++ 不重做 Python 的判斷，只看「信箱空不空、時間到了沒、檔變了沒」。兩邊不會各說各話，測試也好寫：閘說沒事的每一拍，直接跑 Python 驗它真的什麼都沒做。
3. c 的量大，而且 eca 的畫面、收件口、重試、slash 都是這兩週才穩下來的。等「忙的時候的起動成本」變成下一個重點再談比較實在。
4. a 壞了的下場是「放行」，等於退回現在；b、c 壞了是 agent 不動。

想確認的是：「乖乖用 C++ 重寫」是不是包含 c 的意思。如果是，分刀要整個重排，先做哪一支也要再問。

## 第 2 題：行為差異收不收，保底拍多久

掛了閘之後，有幾處跟現在不一樣（[02 的清單](02-切法.md#跟現在不一樣的地方)）。最主要的兩處：

- 閒著的 agent，`cli.json` 壞了不會在 300 ms 內就停下來讓人看到，要等到有信、on_clock 到了、或保底拍。
- `before_run`／`after_run` 這兩個 hook 點，閒著的拍不發。

保底拍＝不管閘怎麼說，隔一段時間照舊起一次 Python。它同時是「閘萬一漏了什麼」的安全網。

- **a 收，保底 60 秒**：16 隻 agent 的保底成本約 0.04 核。
- **b 收，保底 10 秒**：約 0.25 核；差異最晚 10 秒就接回來。
- **c 收，不要保底**：0 成本；閘漏掉的情況沒有人接。
- **d 不收**：閒著的拍也要驗設定、也要發那兩個點。那就不能用 a 的切法，等於第 1 題選 c。

**推薦 a**。

理由：

1. 60 秒剛好跟 `mail_notify` 的間隔一樣，那一拍本來就要起 Python，保底等於不花錢。
2. 設定壞掉這種事，晚一分鐘知道跟晚 300 ms 知道，處理起來沒有差別。
3. 那兩個 hook 點現在 aos 自己的範本沒掛東西；「真的跑了才發」也比較符合它們的名字。
4. 不留保底（c）是把正確性全押在測試上，第一版不值得冒。跑一陣子、沒抓到漏的，再拉長或拿掉。

## 第 3 題：context_wrap 多久看一次

現在每隻 agent 每 5 秒起一支 Python 看 context 用了幾成，整棵樹約 0.23 核。有閘之後它每次還會把身體一起叫起來，會變成約 0.8 核，是閘做完後最大的一塊。它看的東西只在一輪跑完時才變，閒著時每次看都一樣（[03 第 6 節](03-優化方向.md#6-context_wrap-的頻率)）。

- **a 改成 60 秒**：範本四行。約 0.02 核。「該收尾了」的信最晚晚一分鐘寄到。
- **b 維持 5 秒，加「有變才跑」**：on_clock 的 hook 多一個選填鍵，相關的檔沒變就不起。閒著時 0，忙著時照 5 秒。核心程式約 60 行加測試。
- **c 改掛在「一輪跑完」**：不照時鐘。要動 hook 的點與規矩。
- **d 不動**：閘做完後閒置輪詢剩約 1.2 核，不是 0.45。

**推薦先 a，b 排在後面（第 6 刀）當正解**。

理由：

1. a 最便宜，可以跟閘同一刀交，數字馬上到位。
2. 門檻是 35%，離滿還很遠；晚一分鐘寄收尾信不會出事。
3. b 做完可以改回 5 秒，使用者感覺不到差別。但它動 hook 的介面，不該跟閘擠在同一刀。
4. 你 11-15 定的是「門檻用 35%」；5 秒這個間隔我沒找到你定的紀錄，所以問一次。

## 第 4 題：kernel 走哪條

llm kernel 每 300 ms 起一支 Python 跑一輪，約 0.24 核。比較表在 [03 第 5 節](03-優化方向.md#5-kernel-的-run-once-改法)。

- **a 只掛閘**：沒有信在排、沒有信在飛就不起。整棵樹安靜時約 0.005 核；**只要有一隻 agent 在問腦，就照舊 0.24 核**。跟著主幹順手就有。
- **b 閘再聰明一點**：有信在飛時也擋，只在有新信、有一封飛完、或期限到了才起。C++ 多約 200 行，要跟 Python 判「飛完了沒」的寫法對齊。
- **c kernel 改常駐**：一支一直活著的 Python 自己跑迴圈。kernel 整台只有一支，記憶體不是問題；但改了程式要重起 kernel，「kernel 是 daemon 的身體」這個模型也變了。
- **d kernel 整支改寫成 C++**：約 3200 行 Python。

**推薦先做 a，量過再回來選 b 或 c**。

理由：

1. a 不用另外花工。
2. b、c 值不值得，要看「樹上有人在問腦」的時間佔多少。現在沒有這個數，第 3 刀做完量得到。
3. 如果到時候要選，我傾向 b：它不改 kernel 的模型，壞了一樣是放行。c 省得更乾淨，但它是這份規劃裡唯一要把 run-once 改成常駐的地方，跟你說的方向不同路，所以不替你選。
4. d 的量跟第 1 題的 c 一樣大，kernel 又是全樹共用的，風險最高。

## 第 5 題：要不要先補 `.pyc`

這次順手量到：`lib/` 的 208 支 `.py` 只有 25 支有 `.pyc`，所以每次起 Python 大半的模組都在重新編譯。全部補上，`aos-eca-turn` 起動省約 48%、`kernel_llm` 約 45%、`idle.py` 約 35%（[06](06-這次補量的數字.md)）。

它**不是 C++ 重寫**，是 `install.py` 加大約 10 行。但它跟誰都不衝突：閘省的是閒著的拍，它省的是每一次起 Python，忙的時候（`brain.py`、`act.py`、每個工具、`aos-mcp`）也省。

卡在一條慣例：程式裡明寫「不在庫的資料夾留 `__pycache__`」。

- **a 做，`.pyc` 直接放 `lib/` 裡**：最簡單。`lib/` 是 `install.py` 的產物、git 不追，現在裡面本來就有 25 個。等於把那條慣例改成「定義資料夾不留，`lib/` 可以留」。
- **b 做，`.pyc` 放另一棵樹**（例 `$AOS_HOME/.pycache/`）：`lib/` 保持乾淨，慣例不用改。多一點工：入口要設路徑，被 `aos-exec` 直接起的工具要靠環境變數，要確認每層 daemon 都帶得到。
- **c 不做**：只走 C++ 那條。

**推薦 a，排成第 0 刀，跟 C++ 的第 1 刀同時進行**。

理由：

1. 半天的工，閒置輪詢估計從 4.3 核先掉到約 2.6 核，C++ 那幾刀做的期間機器就先鬆一半。
2. C++ 做完之後它還是有用：有事的每一拍、每一次工具呼叫都省 2～5 成的起動。
3. 那條慣例要保護的是定義資料夾（P-15：定義不被寫）。`lib/` 不是定義，是裝出來的。
4. 選 b 也可以，只是要多驗環境變數有沒有傳到每一層；選 a 沒有這個風險。

## 沒有列成題目、但要讓使用者知道的

- **止血**：C++ 做出來之前，把閒著的 agent 的 `interval_ms` 先調到 1000，約省 2.3 核，回信慢 0.7 秒。不用寫程式。這是營運的事，ops 可以直接做，做不做你說一聲就好。
- **事件喚醒（inotify）與拉長 interval**：先不做。閘做完，輪詢只剩約 0.03 核，它能再買到的是「新信幾毫秒就醒」而不是 CPU。等前幾刀量完，要做再另出一份設計給你看。
- **wait 格**：報告沒算到。fsm 等腦回信、冷卻中，一樣每拍起 Python。排在第 5 刀。樹越忙，這一刀越值錢。
- **閘壞了是放行，不是收工**：跟 loop 的四個點「失敗就收工」不一樣。理由是閘只是省錢用的。你覺得該一致的話，寫進條文前改得動。
- **程式的名字**：`aos-idle`、`gate`、`idle_gate.json`、`on_clock_next.json` 都是暫名。
