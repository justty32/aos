想法攤開：「一個 MCP 存放 eca 自己的工具」可能的四種意思，各自長什麼樣、跟 aos 現有零件的關係。

# 02 想法攤開

← [README](README.md)

先講一個對照，後面都用得到。aos 裡跟「一批工具」有關的現成零件：

| 零件 | 是什麼 | 誰寫 |
|---|---|---|
| 工具夾 | 一個夾＝一支工具（`_entry`、`_tooldef.json`、`_metainfo.json`） | 誰都可以 |
| 登記檔 | 一份 JSON，列「名字 → 工具夾路徑」。可以用 `"$override"` 疊在別份上面 | `aos-tools`、`self_tools` |
| pack（包） | 就是一份登記檔，放在 `lib/packs/`，給很多定義疊 | 做定義的人 |
| kit | 一份系統文字加一份 `tools.json`，蓋在某隻的 stack 上 | 人（`ctl add --kit`） |
| `aos-mcp` | 翻譯櫃台：把登記檔裡的工具講成 MCP。自己不存工具 | aos 起 CLI 時自動接 |

重點：**在 aos 裡「存放工具」的是資料夾與登記檔，MCP 只是講給 CLI 聽的那一層。** 所以「弄一個 MCP 來存放」拆開看，其實是「存在哪」加「怎麼講給 CLI 聽」兩件事。

## 意思甲：每隻 eca 一個私有工具箱，經 MCP 掛回自己

**今天已經是這樣。** 工具箱＝`<stack>/tools.json`，櫃台＝那台 `aos`。

- 樣子：eca 寫好工具夾 → `self_tools add` → 下一則回覆出現 `mcp__aos__<名>`。
- 還缺的：工具夾放哪沒有慣例；`reset` 或換 kit 後清單會掉（01 最後一段）。
- 要不要為它另開第二台（例如 `mcp__mine__*`）？好處只有一個：名字上分得出「這是我自己做的」。這個用 `self_tools ls --long` 的來源欄已經看得到。

## 意思乙：一個共用的工具庫，多隻 agent 共享

樣子有三種，由輕到重：

- **乙一，共用夾**：一個大家都讀得到的夾放工具夾（像 ops 的 `org/tools/`），各隻自己 `self_tools add`。今天就能做。缺點是每隻、每支都要掛一次，新工具不會自己出現。
- **乙二，共用包**：再加一份登記檔（就是一個 pack），各隻的 `tools.json` 把它疊進 `"$override"`。往包裡加一支，所有疊它的 agent 都看到。這是 aos 原本的做法，`lib/packs/` 就是這樣。今天的限制：`self_tools add` 一次只加一支，不能加一個包；知識庫說包要在做定義時加，不要在跑的時候加（`knowledge/aos/packs.md:53`）。暫存夾實測手改 `<stack>/tools.json` 的 `"$override"` 成兩份是通的，但有兩個洞（03 第 2、4 條）。
- **乙三，共用的一台 MCP server**：一個常駐行程，各隻 CLI 連上去。這是字面上最像原話的樣子。但 aos 的工具每次呼叫都是新行程、需要呼叫者自己的 `AOS_WS`、`AOS_STACK`；一台共用的常駐 server 不知道是誰在叫，工具的小格、相對路徑、hook 都對不上。要補的東西很多，換到的只是「少起幾個行程」。

乙二跟乙三給腦看到的東西一樣（多一批工具），差在乙二沒有新行程。

## 意思丙：把 aos 工具夾自動轉成 MCP 工具的轉接器

**這就是 `aos-mcp`，已經有了。** 它不挑工具是哪來的，登記檔裡有就轉。反方向（把外面的 MCP 工具轉成 aos 工具）也有，是 `aos-mcp-import`。

所以丙不用做。真要補，是補它的邊角：壞掉的工具怎麼告訴腦、撞名怎麼處理（03）。

## 意思丁：不是 MCP，是「自產工具的家」

使用者的原話重點可能在「存放」，不在「MCP」：做了很多工具，要有個地方收、找得到、下次還在。那答案是一個**夾加一份索引**：

- 夾：例如工作區的 `tools/`。
- 索引：`tools/_index.json`（一行一支：名字、一句話）。eca 範本本來就有 `index_view`，一行一項地看，要哪支再讀它的 `_tooldef.json`。
- 掛不掛進工具清單，是第二步，按需要一支一支掛。

這個樣子跟「資料夾＝程式」最貼：工具庫本身就是一個可以 `ls`、可以 git、可以用 `index_view` 走的夾。

## 跟 Claude Code 自己的 skill、自訂指令比

| | aos 工具（經 MCP） | Claude Code 的 skill | 腳本＋README |
|---|---|---|---|
| 是什麼 | 有參數表的函式 | 一份說明（`SKILL.md`）加可帶的腳本，腦照著做 | 就是腳本 |
| 平常佔 context | 整份定義，每次呼叫都送 | 只有名字與一句描述；內文要用才讀 | 不佔 |
| 誰能用 | fsm、claude、codex、pi | 只有 Claude Code | 有 Bash 的 |
| 放哪 | 任何夾，登記進清單 | 工作區的 `.claude/skills/`（範本 `--setting-sources project,local` 下，使用者家目錄那層的同步 skill 不載） | 任何夾 |
| aos 的 hook 與紀錄 | 看得到 | 看不到 | 看不到 |
| 適合 | 固定輸入輸出的一步 | 一套多步的做法、要判斷的流程 | 偶爾用、輸出要接管線的 |

自訂指令（slash command）現在跟 skill 是同一套東西，差在是人打的還是腦自己挑的。範本的 `--tools` 有開 `Skill`（`templates/eca-claude/cli.json:2`），所以 eca 今天就能用工作區的 skill（沒測）。

看法：**skill 不能取代 aos 工具，因為 fsm 用不到；但「eca 自己才用的一套做法」放 skill 比掛成工具省 context。** 兩者可以共用同一支腳本，就像 ops 的 `run.py` 同時給 Bash 與 fsm。
