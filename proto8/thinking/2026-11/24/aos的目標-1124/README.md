## 反饋（`main` 給使用者，11-24 23:0x）

**一句話**：六層連得起來，每一層 repo 裡都有東西；最大的問題是層跟層之間的線沒接上——`_metainfo` 沒有任何程式拿去做決定，kernel 不讀它，aos-exec 也不讀它。

### 1. aos proc（使用者說「走歪了」的那塊）：證據支持他，而且離他要的不遠

- **現況**：「是不是 aos proc」由 daemon 的表上有沒有那一列決定，進表的唯一方法是讓 daemon 起你。一個外來行程自己擺出 ctl／state，`ls`、`who`、用名字寄信、stop 都認不得它；能用的只有直接寫它的 `ctl.json` 和 `mailbox --box 路徑`（[蒐集/04](蒐集/04-aos-proc與daemon.md) 第三節）。
- **界面其實已經有了**：`ctl.json`／`state.json`／`state_flux.json` 是公開格式，N-17 也寫了「父只看公開 ctl／state_flux 窗判卡住，任何有窗的 proc 都能用」。缺三樣：
  - 一頁「aos proc 界面」規格（現在散在好幾條 NORMS 和 C++ 標頭裡，`interfaces.json` 裡也沒有 `aos-proc` 這個名字）；
  - 一個「只登記、不起」的入口；
  - 一個不靠 pid 的活著判斷。
- **硬碟上的檔和 9P／FUSE 上的檔有本質差別**：9P 的檔是活的行程當場回答的，行程死了檔就沒了；硬碟上的檔是行程留下的，被 `kill -9` 之後 state 還寫著 running。所以界面裡一定要有一條「怎麼知道你還活著」，而且不能靠 pid（遠端沒有 pid）。
- **使用者自己早就給過答案**：11-05「寄信不回，等同於呼叫失敗」。做法是寫 ctl 換一個 seq，看 `state_flux` 有沒有跟上。這個機制現在有，只是只用在判卡住，而且預設關著。daemon 用 pid 判自己的子，可以當成本機的加速，不當成定義。
- **用詞**：11-05 說「以daemon爲界面」（daemon 當橋），11-24 說 proc 自己擺出界面，字面是兩個方向。C-83 已把前者降成「建議」，所以不算矛盾，是程式還照舊的那句在做。

### 2. agent：「就是 fsm」這句可以放鬆

- eca-claude 不是 fsm，是把 Claude Code 包成 proc。照第 1 點，agent 該定義成「擺出 queue、history、ctl 的 aos proc」，fsm 是其中最輕的原生實作。10-30 map-review 的結論 3 已經這樣寫（共同點＝queue／history／ctl 三樣）。
- 「好修改自身」目前打了折：`fsm.json`、`loop.json` 沒有覆蓋檔，agent 改不了自己的狀態表；`self_*` 七支裡範本預設只開兩支（[蒐集/05](蒐集/05-aos-agent與fsm.md)）。

### 3. kernel：方向認同，三件事要分清楚

- **「agent 設計排程」和「agent 執行每一次排程」是兩回事。**
  - 設計便宜：偶爾想一次，寫成規則。
  - 執行貴：每個決定都問一次腦，而且會卡住。`kernel_gate` 就是 agent 逐封點頭，它回合一長整站停，底下的呼叫 3 秒後 `KernelFailed`。
  - 問腦那條更糟：kernel 自己問腦的信會排進自己的隊（11-20 aos-kres 結論 4 就撞到了）。
  - 嵌套正好解這題：上層 kernel 的腦由下一層更笨的 kernel 供應，**最底下一定要有一層不用腦的**。這跟「aos 把 Linux 當硬體」是同一個形狀。
  - kernel 自己也可以走使用者寫過的那條「token 降下來」的路：一開始是 agent 在決定，跑一陣子後把常見的決定固化成規則。
- **「間接硬體」其實有兩種。**
  - 可以分的：token、端點格數、金額、使用者的注意力。請求會消耗它，kernel 可以分配、排隊、記帳。
  - 只能量的：耦合度、可理解性、掌控度。沒有人「消耗」它，它是一個讀數，kernel 看讀數改策略（使用者 11-19 舉的「耦合度過高時讓負責規劃的 agent 優先」就是這種）。Linux 裡對應的是溫度：不分配，量了之後降頻。
  - 一樣東西要被 kernel 管，得有三件：誰量、算誰的、kernel 能做什麼動作。現在三件齊全的只有 token。
- **上千個 agent 大多在待命時，最要緊的決定是「誰醒來」**，不是「醒著的誰先問腦」。現在喚醒先後沒有任何 kernel 在管，優先級只在問腦那條有。「上千個」本身也還沒實測（使用者 11-15 自己註「尚未實測」）。

### 4. 已經有很多 kernel，只是沒叫它 kernel

- 現成的有五套，各寫各的：commit-request 管「main 分支」（排隊、檢查、放行）；11-24 晚建的家機組織，`main` 管位子的喚醒、名額、push 權；aos-user 專區管使用者的注意力；aos-lock 管鎖；llm kernel 管端點。
- 檢驗「任意資源 kernel」最便宜的辦法：挑一個不是 LLM 的現成資源搬到通用 kernel 骨架上跑。候選是 commit 的隊，或 arena 那把 Node 鎖（就是同一天[跨 agent 資源鎖](../跨agent資源鎖-kernel-1124/README.md)那五題）。搬得舒服，框架就是通用的；搬不上去，就知道骨架缺什麼。
- 現在全系統最搶手的資源不是端點，是使用者：`wf/progress.json` 裡一排「等使用者答」。

### 5. `_metainfo`、九軸、生長

- **九軸沒有定稿**：repo 裡有兩份名單（10-11 的六個例子；九個只有名字的軸，原文在 repo 外的 `ai_core`），檔裡實際寫的又是另外六個鍵（[蒐集/03](蒐集/03-metainfo與九軸.md)）。
- **「動態」和現況有落差**：現在的 `_metainfo` 是手寫的靜態檔，實測不回寫（N-69，使用者定的）。平常沒差；但生長那條路需要量到的數字流回去，才知道哪個節點該拆、該改。
- **接起來看**：「哪個節點值得花 token 去改進」本身就是資源分配。所以生長和 kernel 是同一件事的兩個時間尺度：kernel 管這一秒誰先跑，生長管這個月哪個節點該長，兩邊都要讀 `_metainfo`。這就是「線沒接上」是最大斷點的原因。
- `_entry`／aos-exec 在這張圖裡的價值，可能不在「接各種技術棧」（現在 91 個工具入口裡 90 個是 Python），而在「所有呼叫都長同一個樣子、過同一個口」：有了同一個口，屬性才有地方掛、kernel 才有地方量。（`main` 的看法，沒跟使用者談過。）

### 6. index 和 Plan 9

- 使用者說差別在 description。`main` 覺得還有一個更大的：Plan 9 的 namespace 是每個行程看到的世界可以不一樣，自己拼；aos 現在所有 agent 看同一棵樹。要讓 agent 眼中的世界單純，「只給它看 20 樣」比「959 個資料夾各附一句話」有效（`main` 的判斷）。
- index 本來就做得到：項目可以是 `$ref` 指到別處（`index_view` 的說明自己寫「A view, not the facts」）。每個 agent 有自己的根 index，就是 Plan 9 的 bind 加上 description。這也接得上使用者 11-22 說私有地盤「是未來的權限的基礎」。
- 現況：959 個有追蹤的資料夾裡 66 個有 `_index.json`；`#` 尋址只有 json 那批工具吃，read／grep／glob 不吃（[蒐集/01](蒐集/01-單一路徑尋址與index.md)）。`main` 自己平常大多還是用 Bash 和 Read。
