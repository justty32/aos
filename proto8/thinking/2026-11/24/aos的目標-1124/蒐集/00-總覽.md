# aos 目標對照：總覽（11-24 晚，蒐集隊）

七份報告都在這個夾。只寫事實和差距，不寫方案。標「觀察」的是隊長的看法。

## 1 單一路徑尋址與 index（01）
- 現況：`FILE#/POINTER` 在 18 支 json 工具、`index_view`、`$ref`、`aos-json` 之間是同一套。解析只在一處：`proto8/py/aos/refpath.py` 的 `spot()`，C++ 端共用同一張對照表。md 能讀，不能寫。
- 最大的差距：檔案工具（read、ls、grep、glob）不吃 `#`，`view` 把路徑和指標拆成兩個參數。相對路徑有三種起點。index 只覆蓋 66 / 959 個夾，`proto8/knowledge` 是手寫的。
- 「跟 Plan 9 namespace 不一樣」這個說法，repo 裡沒有寫過對照。
- 先讀：`proto8/py/aos/refpath.py`、`proto8/py/aos/index.py:31-35`、`wf/progress.json:110`（index 三題，還在等使用者）。

## 2 `_entry` 與 aos-exec（02）
- 現況：入口有五種。aos-exec 是 C++ 寫的，約 1528 行。指示詞只有四個：`$ref`、`$env`、`$path`、`$prefix`。共有 215 個 `_entry`；`py/tools` 裡 91 個中有 90 個是 Python。
- 最大的差距：「接各種技術棧」實際上幾乎全是 Python。stdin／stdout 和退碼的規矩，N-43 明說「不是 aos 函數都要守」。工具契約只由 Python 的 `tool_io.py` 強制，其他語言沒有。
- 先讀：`proto8/cpp/aos-exec/`、NORMS N-43（`proto8/docs/NORMS/`）、報告 02 的「缺點」節（有啟動成本的數字）。

## 3 `_metainfo` 與九軸（03）
- 現況：repo 裡有 95 份 `_metainfo.json`。九軸沒有定稿。有兩份名單對不上：一份是 10-11 舉的六個例子，一份是轉述 repo 外 `ai_core` 的九個名字，每軸的意思都沒寫。實際寫進檔的鍵是另外六個。
- 誰讀它：kernel、aos-exec、daemon（整個 `cpp/`）都不讀。真的起作用的只有 `timeout_ms`、`parallel`、`sandbox`、`arbitrary_exec`。`deterministic`、`interrupt` 沒人讀。
- 「動態、相對於檔案屬性」11-06 講過（`wf/user/advice/20261106.md:49`）。但現在的 `_metainfo` 是手寫、不回寫的靜態 JSON。
- 「生長型」只在今天這段話裡出現。最近的舊東西是 C-55 函數成長六級和 `aos-grow` 原型。`wf/STRUCTURE.md` 的「四級成長」講文件結構，不是同一件事。

## 4 aos proc 與 daemon（04）
- 現況：proc 的定義是「daemon 起的、記在 `procs_state.json` 裡的一列」。窗（`ctl.json`／`state.json`）是公開格式，N-13 也寫了「像 Plan 9／FUSE」，但沒被拿來當 proc 的定義。
- 最大的差距：綁死本機或 daemon 的地方列了 33 條，包括 fork／waitpid、`/proc`、boot_id、pidfd、flock、rename 原子性、mtime 判 stuck。思想實驗的結果：一個外來行程只擺出這些檔，ls、who、mailbox --to、pause、stop、重起都認不得它。能用的只有直接寫它的 ctl，和 `mailbox --box`。
- 用詞有歧義：11-05 說的「daemon 為界面」是指 daemon 當橋，跟今天說的「界面」是兩個意思。FUSE／9P 11-09 規劃過，當時選了訊號（poke）。
- 先讀：`proto8/thinking/2026-11/05/no-pid/README.md`、`proto8/docs/NORMS/05-基礎設施-窗/03-N-13～N-14.md`、報告 04 的第二、三節。

## 5 aos agent（fsm）（05）
- 現況：定義夾不抄。daemon 的表記下 def／ws／stack，stack 只放 overlay 和歷史。fsm 有四格，由 aos-loop 每 300 ms 推一格。四格程式 11-24 搬進 `lib/aos/apps/agent_fsm/`，所有 agent 共用。
- 最大的差距：「就是 fsm」只對 agent-fsm 成立。eca-claude 是把 Claude Code 包成 proc，沒有 `fsm.json`。「好改自己」方面，`self_*` 七支裡範本預設只開兩支，而且 `fsm.json`、`loop.json` 沒有 overlay，agent 改不了自己的狀態表。ws 是起點，不是圍欄。
- 「這會有些缺點」：使用者沒列出來。報告整理了 repo 已記下的八條相關風險，並標明不一定是他說的那些。
- 先讀：`proto8/knowledge/aos/world.md`、`proto8/py/aos/apps/agent_fsm/README.md`、`proto8/templates/agents/`。

## 6 aos kernel（06）
- 現況：kernel 是「每拍起一次的 Python 站，加一份定義夾」，分兩條。問腦（向 LLM 發請求）那條管格數和三層額度，排序公式寫死在 `kernel_llm/order.py`。啟動 proc 那條管 `max_running`、queue、limits。cpu／mem 的 cgroup 在 daemon 那邊。
- 自訂和嵌套：有程式，共五種自訂形式，嵌套靠 `llm_forward` 和 `next`。但 agent 能決定的只有 `kernel_gate`（啟動請求逐封點頭），問腦那條沒有 agent 版。
- 最大的差距：資源裡只有 token 有程式。金額、人類可理解性、耦合度只在討論裡：11-06、11-13、11-19 講過，11-19 使用者說「先不定，讓它自然長」。
- 先讀：`proto8/thinking/2026-11/24/跨agent資源鎖-kernel-1124/README.md`（五題，沒找到答案）、`proto8/py/tools/aos/kernel_llm/README.md`、11-19 的 aos-htop-1119 線。

## 7 外部對照（07）
- Plan 9：per-process namespace 加 9P，`/proc` 的 ctl／status 檔名幾乎一樣。但 Plan 9 的 `/proc` 是核心做的。使用者說的「誰擺出佈局誰就是 proc」更像 9P 檔案伺服器。節點描述（description）在 Plan 9 裡沒有對應。
- AIOS：一個人寫死的 kernel，摘要沒提可替換。MemGPT 只管 context。
- sched_ext、exokernel、scheduler activations：都是「策略交給上層」，跟「Linux 當硬體」的分層相呼應。但都不是由 agent 來寫策略。
- 「檔案系統當 agent 介面」的現成專案沒找到，因為沒有搜尋工具，只用 curl 抓網頁。

## 跨主題的觀察
- 觀察：主題 4 的差距，一部分是主題 5 造成的。agent 的實例化本身就是「daemon 表裡的一列」。stack 不抄定義、靠 `AOS_CD` 指回去，這也要 daemon 起行程才成立。只要 proc 還等於「daemon 的一列」，agent 就跟著綁在本機上。
- 觀察：主題 3 和 6 斷開了。九軸本來是「後續很多東西的基礎」，但 kernel 排程不讀 `_metainfo`，`resource`、`interrupt` 這些軸也沒有人消費。
- 觀察：主題 1 和 4 是同一種不一致。路徑尋址對 json 統一、對檔案工具沒統一；窗格式對 aos-loop 統一，但沒有獨立的協議文件，C++ 和 Python 各寫一份。「主打 json、串接先前概念」目前停在約定，沒有一份規格。
- 觀察：今天的「界面」和 11-05 的「daemon 為界面」用了同一個詞，指的卻是兩件事。談之前值得先對齊這個詞。
