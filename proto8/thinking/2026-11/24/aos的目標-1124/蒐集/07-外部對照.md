## 1. Plan 9：namespace、9P、行程即檔案、合成檔案系統

### 1a. per-process namespace、bind、union directory
- 是什麼：Plan 9 每個行程各有一份自己的「名字空間」（namespace，就是這個行程看到的目錄樹）。`bind(new, old, flags)` 把一塊已有的樹也掛到另一個路徑。「union directory」是把幾個目錄疊在一起，照順序搜尋。
- 論文原話：系統建在兩個想法上，一是 per-process name space，二是簡單的訊息式檔案協定。`rfork` 可選擇名字空間是共用還是複製。
- 像：「單一路徑尋址」、「讓 agent 眼中的世界單純」這個目標。Plan 9 也是用一棵路徑樹去看一切。
- 不像：使用者自己說過 aos index 加了 description 等描述。Plan 9 的 bind 只改「看到哪些路徑」，不附說明文字給使用者讀。
- 觀察：使用者說「和 plan 9 namespace 不太一樣」。我沒查到 Plan 9 本身有每個節點的描述欄位，這個差異點站得住。我不確定 aos 有沒有 per-process 視圖與 bind（這段話沒提）。
- 網址（已開）：https://9p.io/sys/doc/names.html

### 1b. 9P 協定
- 是什麼：Plan 9 用來連接系統各部分的網路協定。檔案代表視窗、網路連線、行程，幾乎一切。後來改版叫 9P2000。Inferno 裡叫 Styx。
- 像：使用者說「網路上也行，這就是單純的 plan 9 思想」，指的就是這個。
- 不像：9P 傳的是位元組與檔案操作，沒有規定內容格式。使用者主打的是 json。
- 網址（已開）：https://en.wikipedia.org/wiki/9P_(protocol)

### 1c. 行程即檔案：Plan 9 /proc 與 Linux procfs
- 是什麼：Plan 9 的 `/proc/n/` 底下每個行程有一組檔案：`ctl`（寫文字訊息控制行程）、`status`（唯讀狀態）、`note`（送訊號式訊息）、`mem`、`fd`、`ns`、`wait` 等。Linux 的 procfs 也是類似做法，但以唯讀資訊為主。
- 像：使用者說「任何 proc 只要提供 ctl／status 等可存取檔案佈局，就是 aos proc」。這和 Plan 9 的 /proc 檔名慣例很接近。
- 不像：Plan 9 的 /proc 是核心替真的行程做出來的。使用者的版本反過來，是「誰提供這個佈局誰就是 proc」，位置不限（硬碟、/tmp、fuse、網路）。這其實更像 Plan 9 的檔案伺服器想法（任何程式都能經 9P 提供檔案樹），不是 /proc 本身。
- 網址（已開）：https://9p.io/magic/man2html/3/proc 、https://en.wikipedia.org/wiki/Procfs 。我確認了 `ctl`、`status`、`note` 的檔名都在 man 頁裡；`ctl` 的具體指令語法我沒細讀。

### 1d. 合成檔案系統（synthetic file system）、FUSE、Inferno
- 是什麼：檔案其實不在硬碟上，是某個程式即時變出來的（Plan 9 的 rio、acme 就是這樣給外部程式操作）。FUSE 是 Linux 讓一般程式在使用者空間實作檔案系統的機制。Inferno 是貝爾實驗室接在 Plan 9 後面的分散式系統，協定叫 Styx。
- 像：使用者說「在硬碟、/tmp、fuse 都可以」，就是承認這種「檔案是假的，後面是程式」的做法。
- 不像：這些做法沒有內建 json 當資料格式，也沒有「agent」這層。
- 網址（已開）：https://en.wikipedia.org/wiki/Filesystem_in_Userspace 、https://en.wikipedia.org/wiki/Inferno_(operating_system) 。rio、acme 的檔案介面我只憑背景知識，沒開專頁（未開）。

## 2. 給 agent／LLM 用的作業系統式框架

### 2a. AIOS
- 是什麼：論文提出「AIOS kernel」，把 LLM 與工具的資源從 agent 應用裡隔離出來，由核心統一提供排程、context 管理、記憶管理、儲存管理、存取控制。另附 SDK。論文宣稱服務各框架做的 agent 最多快 2.1 倍。COLM 2025 論文。
- 像：「很多 agent 搶有限資源（LLM 端點、權限、優先級）」這個問題設定一樣。
- 不像：AIOS 的排程與資源演算法是人先寫好、固定在一個 kernel 裡。使用者說的是「讓 agent 自己設計 kernel，而且可以嵌套」。從摘要看，沒有「kernel 可替換、可堆疊」這個點（沒讀全文）。AIOS 也不是以檔案系統為介面（摘要只提 SDK／API）。
- 網址（已開，只讀摘要頁）：https://arxiv.org/abs/2403.16971

### 2b. MemGPT／Letta
- 是什麼：把 LLM 的有限 context 當成「快記憶體」，仿作業系統的分頁，在快慢記憶層之間搬資料，並用中斷處理控制流程（「虛擬 context 管理」）。專案後來改名 Letta，主打有狀態、有記憶的 agent。
- 像：兩者都借作業系統的概念來管 agent，不只是比喻。
- 不像：MemGPT 只管「記憶／context」這一項資源。使用者的 kernel 想管的範圍更寬（token 用量、可理解性、耦合度）。
- 網址（已開）：https://arxiv.org/abs/2310.08560 、https://github.com/letta-ai/letta 。Letta 頁面顯示現在的主要原始碼在 letta-code，我只讀了首頁開頭。

## 3. 階層排程、把策略交給上層

### 3a. Linux cgroup v2
- 是什麼：把行程組成一棵樹，資源（CPU 等）沿著樹往下分配，每個行程只屬於一個 cgroup，新行程繼承父的 cgroup。控制器逐層開啟（`cgroup.subtree_control`）。
- 像：「kernel 可嵌套堆疊」、「資源由上往下分」。
- 不像：cgroup 樹的規則是核心寫死的（固定的控制器與權重模型）。使用者想要每一層的策略由 agent 自己設計。
- 網址（已開）：https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html

### 3b. sched_ext
- 是什麼：Linux 的一種排程類別，行為由 BPF 程式（可在執行期載入的受限小程式）決定。可隨時開關，核心保證不論 BPF 排程器寫得多爛，系統整體不會壞。
- 像：這是「排程策略可由外部程式替換」的現成例子，而且有安全兜底（壞了退回預設排程）。
- 不像：它換的是單一層的排程演算法，不是 kernel 疊 kernel；寫的人是人類，用 BPF 受限語言。
- 網址（已開）：https://docs.kernel.org/scheduler/sched-ext.html

### 3c. exokernel、library OS
- 是什麼：MIT 的設計。核心極小，只負責保護與多工，盡量不強加抽象；應用自己帶一個「library OS」去決定怎麼用記憶體位址、磁碟區塊等。
- 像：「把策略往上交」、「kernel 為了好用硬體」這種說法。使用者把 Linux 當「硬體」、把更抽象的東西當「間接硬體」，這個分層和 exokernel 的「核心只暴露資源」有點呼應。
- 不像：exokernel 的上層是應用程式帶的函式庫。使用者的上層是 agent 設計的 kernel，且能再疊。
- 網址（已開）：https://en.wikipedia.org/wiki/Exokernel

### 3d. scheduler activations
- 是什麼：一種執行緒機制，核心與使用者空間的執行緒系統互相通知（核心給「虛擬處理器」，使用者空間自己決定上面跑哪個執行緒）。1990 年代初由 Anderson、Bershad、Lazowska、Levy 提出。
- 像：「核心把處理器交給上層、上層自己排」。
- 不像：它只解決執行緒層級的兩層排程，不是通用的 kernel 嵌套。
- 網址（已開）：https://en.wikipedia.org/wiki/Scheduler_activations
- microkernel 的 user-level scheduler：沒另外開專頁（未開），不寫。

## 4. 資料夾／JSON 當程式；生長型神經網路

### 4a. code as data（homoiconicity）
- 是什麼：程式本身可以被該語言當成資料操作（Lisp 的程式就是串列）。
- 像：使用者說「把檔案系統當 lua／lisp 用」，也就是以目錄結構當程式。
- 不像：Lisp 的程式與資料在同一種結構裡，由同一個直譯器執行。使用者的做法是靠 `_entry` 加 POSIX 呼叫去串各種技術棧，核心只有 aos-exec。使用者自己也說這個舉動「有好有壞」。
- 網址（已開）：https://en.wikipedia.org/wiki/Homoiconicity
- 「以目錄結構當設定或程式」的現成工具（如 Plan 9 的 rc 腳本、plan9 的 `/lib`、service 目錄那類）：沒找到、沒開。

### 4b. 生長型神經網路
- 是什麼：網路結構會在訓練中長出新節點或連線，而不是一開始就固定。NEAT（2002，Stanley 與 Miikkulainen）是代表：用遺傳演算法同時演化權重與結構，從簡單的網路開始，逐步加複雜度，同時保護物種多樣性。
- 像：使用者說「從單一資料夾開始，逐步長出子資料夾，像生長型神經網路」。
- 不像：NEAT 靠演化與適應度篩選。使用者這段話沒說靠什麼機制長；他自己也說之後再談。
- 網址（已開）：https://en.wikipedia.org/wiki/Neuroevolution_of_augmenting_topologies 。維基沒有 "Constructive neural network" 專頁（404），那個詞我沒查到來源。
