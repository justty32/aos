## 修了什麼（各一個 commit）

1. **knowledge_read 能指定 root**：給腦看的參數 `root`，接受資料夾，相對路徑從工作區算。優先順序是 `--root` > `root` > `_knowledge.json` > `AOS_KNOWLEDGE`，人用 `--root` 釘死的時候，腦改不了。寫完後用同一個 root 就能讀回。tooldef、出廠庫 `aos/knowledge.json`（read、where 兩節）、README、測試都改了。
2. **eca 範本拿掉 subagent 包**：拿掉 subagent、agents_ctl、fork 和 `subagents.json`。**代定**：def 包（agent_def、tools_def）留著，因為它只寫定義和工具資料夾、不會生出 agent，而且 tools_def 是 11-10 使用者要加回來的。出廠庫的 `aos/agents.json`、`aos/packs.json` 跟著改。
3. **mailbox_send 寄給自己的提示**：腦把 `to` 寫成 `self` 時，InstanceMissing 會多一句「寄給自己用自己的名字 X」。tooldef 也寫明 `to` 不能用 self 或 me。
4. **json_write 引號提示**：鍵被包上引號（如 `"'/n'"`）時，PointerBad 會多一句「去掉引號，寫成 /n」。

## 第 2 點裡沒做的（要使用者裁）

使用者說 root 可以是「檔案、資料夾或 json 物件（`xxx.json#/aaa/bbb`）」。現況是 read 和 write 的 root **只收資料夾**，給檔案會報 KnowledgeBad。要改成收檔案或物件，得先定 path 怎麼接在後面，例如 root 是 `a.json#/x` 時，path `y` 算不算 `a.json#/x/y`。這會動到 knowledge_fs 的路徑模型，這次只記下來沒改。

目前的替代辦法：path 用 `/` 開頭的絕對路徑，本來就能讀任何檔案裡的任何物件（`/abs/a.json#/x/y`）。另外 knowledge_export 和 knowledge_sync 兩支只收 `--root`、`_knowledge.json` 和 `AOS_KNOWLEDGE`，沒有 `root` 參數；它們本來就不是給腦臨時指定別的庫用的，這次照舊。

## 第二輪發現

1. **codex 只會用自己的唯讀沙盒判斷「能不能寫」。** eca_cody 的 `cli.json` 設了 `sandbox_mode="read-only"`，目的是逼它走 aos 工具。結果 luna 和 terra 連 aos 的 write、mkdir、knowledge_write 都不試，直接回「工作區唯讀」。sol 先這樣講，後來還是用 aos 的 write 做完了，可見 aos 工具其實寫得進去。**要使用者裁**：改成 `workspace-write`（codex 就能用自己的 shell 寫，不一定走 aos）？還是在 eca_cody 的 system 裡寫一句「改檔用 aos 工具，你的沙盒唯讀不影響它們」？

3. **mailbox_send 的 `box` 可以指到 agent 的 queue 資料夾。** luna 不知道自己的信箱在哪，猜成 `.stack/procs/fl/queue`。queue 也是同一種三夾佈局，所以「信」直接進了自己的待處理隊列，等於繞過信箱、直接 `say`。**要使用者裁**：`box` 該不該拒收 queue 資料夾？

5. **eca 拿掉 subagent 之後沒有副作用**：37 支，全部題目照常。
6. **knowledge_read 指 root 讀回**：除了 gemma 和兩隻自認唯讀的 codex，其他模型一次就成功。

## root 收三種形狀：設計與代定（明天施工）

> **使用者看完本節後（11-11 晚 23:00 前，逐字）**：「啊？等等，我記得關於json路徑，指示詞已經有挺詳細的規定了吧，對於一個json檔案內，其根就是#/，而檔案系統是/，兩者不同。json write的時候，比如他要改xxx.json#/aaa/bbb，那他就是給這一整串。引號...別管」
>
> 隊長快查：指示詞條文在 [NORMS N-45](../../../../docs/NORMS/06-基礎設施-命令列與指示詞.md)（`$ref` 寫 `檔#/位置`、位置只認 `#/`）。本節第 2、3 條的「path 寫 `x/y`」**跟條文打架，明天施工前要照條文重寫**：json 內的位置一律寫成 `#/…`，`/` 開頭只代表檔案系統。root 是物件時 `#/` 指哪裡，還要請使用者定。

照字面接，跟 `$ref`／JSON Pointer 現有的寫法一樣：root 是一個「位置」，path 從那個位置往下走。

1. **root 是資料夾**：跟現在一樣，path 是 `folder/file.json#/key`。
2. **root 是檔案 `a.json`**：path 是檔內的鍵路徑，寫成 `x/y`，等於 `a.json#/x/y`；`""` 是整份檔。path 裡不能再有 `#`，也不能有 `.json/`，以免檔中有檔，這兩種都報 PathBad。
3. **root 是物件 `a.json#/aaa/bbb`**：path `x/y` 等於 `a.json#/aaa/bbb/x/y`；`""` 是那個物件本身。
4. **root 是非 .json 檔**：只收 path `""`（讀全文），其他報 TargetBad。
5. **以 `/` 開頭的 path** 照舊是檔案系統絕對路徑，不受 root 影響。
6. **寫入**：add、set、rm 在物件裡照現行物件規則走，表是物件的 `_index` 鍵。add 資料夾（path 以 `/` 結尾）在檔案或物件 root 下報 TargetBad；rm root 本身照舊報 PathBad。
7. **四種給法同一套**：`--root`、`root` 參數、`_knowledge.json` 的 base、`AOS_KNOWLEDGE` 都能寫成三種形狀，相對路徑的起點照舊。
8. **export 跟著 knowledge_fs 走**，三種都收。**sync 只收資料夾**，因為要 git 工作樹的根，給檔案或物件就報 KnowledgeBad 並說明原因。
9. **印出的路徑**相對於 root，照舊能直接貼回 path。

改的地方：`lib/agent/knowledge_fs.py`（`knowledge_root` 回位置而不只是資料夾、`parse`、`show`），read、write、export 三支的說明與測試，出廠庫 `aos/knowledge.json`。
