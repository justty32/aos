# kernel 討論的使用者原話與經過（11-11，依時間）

← [kernel README](README.md)｜[2026-11-11](../README.md)

「」內是使用者原話，一字不改照錄；選項框裁定照選項文字。

## (1) 立場與範本

頂層先整理了 kernel 現況與已知的坑（身分全靠自報、判官在飛的請求不算 running 等）。使用者：

> 「Hmmm，那些坑都是邊緣狀況。我這邊還是一樣的立場：非正規操作的風險由使用者自行承擔、最基礎與通用，同時也是保底的安全機制，就是linux本身，包括使用者、權限啥的。 然後我想知道，假如我以後想要弄一個kernel定義，我(或是agent)有可以參考的範本嗎」

頂層答：[`proto8/kernel/`](../../../../kernel/README.md) 有四個範本（llm-kernel、llm-team、daemon-judge、procs-kernel），但知識庫沒有教 agent「怎麼定義一個 kernel」的節點，四個都是規則型。

## (2) 鏈與 hook

> 「一個常見的掛proc請求，可能是agent->kernel_1->kernel_2->kernel_a->kernel->daemon。其中kernel_2可能自身也是一個daemon，只是他的loop中有kernel功能。所以他們之間的交換，就是都走aos-post，內部格式看能不能通用，這樣方便在這條chain上做新增刪除。知識庫等等，我們先聊完。規則型...或許可以搭配hook，有新的請求來的時候，攔下並修改結果這樣」

頂層擺四個岔路（回信怎麼走／記不記走過哪些站／hook 慢怎麼辦／最初寄件人），使用者：

> 「1.看各站kernel怎麼設定，可能某站kernel說請後續的原路返回，但是後面一站搞不好又說我直接回信。都可以的，使用者自行承擔風險。後站kernel可能會跟前站說我直接回信這樣。2.不記。3.等他，如果不想等，那就hook那邊走async。4.這會依賴格式，我建議是目前就不管最初了，有需要的話後續再更改。然後"請求"格式，他是被包在aos-post格式的body內的。在請求格式之內，就不用多做限制。比如llm kernel一類的呼叫chain，他可能會夾帶一些其他東西，其他類的可能又是別的。」

頂層推出的樣子（使用者沒反對）：共通的只有 aos-post 信封，body 各類自理；回信靠 `reply_to` 二選一（上面結論 5）；信封**不加**「這封是哪一類」欄位，靠寄到哪個信箱分（頂層代定，使用者沒反對）。現況（判官與 daemon 收同一種信、判官下一站寫死 `$AOS_DAEMON`、沒有 hook 點等）見 [01 § 鏈](02-現況查核.md#鏈與-hook-的現況)。

選項框四題（使用者選的）：

| 題 | 裁定 |
|---|---|
| 判官的下一站寫在哪 | 「寫進 judge.json」（沒寫照舊寄給 `AOS_DAEMON`） |
| `max_running` 在下一站不是 daemon 時 | 「數量另外指一台」：judge.json 可另寫去哪台 daemon 數；沒寫且下一站不是 daemon 時設了 `max_running`＝報設定錯 |
| 判官 hook 時機 | 三個都要：「判決前」「判決後」「回信經過時」——最後一個只在該站選了「回信先回我」時才有；沿用 agent 那套 hook 契約（退 0 加輸出＝修改、退 10＝攔下、逾時、on_error） |
| daemon 收到壞的掛 proc 信 | 「改成會回」：回 `applied:false` 加原因 |

（這四題後來依 (7) 的解讀，是**通用框架要有的能力**，不急著改在現有判官身上。）

## (3) 通用框架

> 「Hmmm，等等，咱們繼續聊。就是說，請用一段白話重新描述kernel作用。emmm，在我的規劃中，我們會有一個通用的kernel框架，在這個框架下，我們去擴充更多功能如llm之類」

頂層的理解：骨架一份（收信、規則＋hook、下一站、回信、排隊），問腦＝「骨架＋問腦專屬那包（能力包、額度、帳）」；這會翻掉 10-16「兩隻kernel不併成一支」（[N-42](../../../../docs/NORMS/09-kernel.md)），以新的為準；現有問腦總機何時真的併進來沒定。**這是頂層的理解，使用者未明確確認，後續發言方向一致**（他沒直接答「對」，接著講了 (4)）。

## (4) 定義回歸、只認 kernel

> 「等等。關於這段話我有些想法：有人想讓某件事被執行，他就是將請求寄到某個地方...先前說過，daemon就是最基礎的kernel，所以daemon也算kernel。但我們有AOS_DAEMON與AOS_KERNEL，所以到底要寄送到哪？我的想法是一律寄到AOS_KERNEL，然後就如同linux一樣，user space的proc他只能看到kernel，除非有特殊需求，否則他看不到硬體，所以他可能就是只有AOS_KERNEL。這樣我們整個架構都可能有變化...或是還好？應該說，kernel可能要作為user space proc訪問daemon時的中轉站。然後寄送出去之後，我們就不管這封信會去哪了，他背後就應該是黑盒子了。kernel自己本身不執行任何東西？不，linux kernel那個root proc也是會做一些事情的。我覺得kernel定義要改一下，回歸初始，變成"資源管理+排程"。」

現況（一般 proc 其實已大多經 aos-agent 寄、直讀 daemon 檔的只有兩處）見 [01 § 誰直接碰 daemon](02-現況查核.md#誰直接碰-daemon)。

選項框四題（使用者選的）：

| 題 | 裁定 |
|---|---|
| 一般 proc 讀狀態 | 「kernel 給一個狀態位址」 |
| 問腦要不要也走 `AOS_KERNEL` | 「維持兩個變數」 |
| `AOS_DAEMON` 還傳不傳給一般 proc | 「照傳，約定不用」 |
| 11-05「判完自己 fork 去跑的不算 kernel」 | 「整句刪掉」 |

## (5) 多種 syscall、人也走 kernel、狀態位址用問的

> 「關於llm呼叫這塊，確實比較棘手，因為單純從linux kernel的角度來看，所有掛proc請求，確實就都是走同個linux kernel。可是我們這邊，把請求分成了多種，如最普通的掛proc，以及其他類型的如呼叫llm。我們當然可以說呼叫llm等同於讓llm kernel掛proc的請求...對啦，就是這樣。所以我們這邊和linux kernel不一樣，我們有一個通用的基礎kernel，類似linux kernel，所有普通的掛proc請求都到他那邊去，類似syscall。但我們有多種syscall，有些syscall是走另一個kernel。人這邊也改用kernel，想要存取daemon或更深的kernel？靠linux權限。然後kernel給狀態位址...希望不是使用symlink，我不希望aos體系硬性依賴symlink，或許可以折衷？寄信問，取得狀態位址這樣。」

頂層推出（使用者沒反對）：「狀態在哪」是又一種請求信（daemon 已有查詢信 `ping` 的先例）；最底的 daemon 回自己狀態檔路徑；中間站預設原樣轉，要給刪減版就用「回信經過時」的 hook 換路徑；讀不讀得到看 Linux 權限；`AOS_KERNEL` 維持指到信箱、不必變成資料夾。

選項框兩題（使用者選的）：

| 題 | 裁定 |
|---|---|
| aos-daemon-ctl | 「維持直寄，它就是『指名 daemon』的工具」：定位從「人的保底手把」改成「指名要碰某台 daemon、有 Linux 權限就能用」；人平常用的 `aos-agent ctl` 走 kernel |
| 問來的狀態位址要不要記 | 「工具自己決定」 |

## (6) kernel 是從外面看的身分

> 「我這邊再補充一些東西：kernel這個身分是從外面看進去的，對於一個有掛proc(或其他syscall)的需求的agent(或其他函數)來說，把掛proc這個請求寄到哪去，那個地方對他而言就是kernel。但對於能夠處理這個請求的proc來說，他沒必要有自己是kernel的自覺。然後有些kernel他可能只能處理掛proc或只能處理llm call，都無所謂，不太限制。因為你把請求寄出去後，是否要處理這個請求，或是說有決定這個請求啥時候要被執行的權力的，就是對方那個proc了，所以對你來說，那個proc就是具有資源管理與排程功能(啥都不管也是一種管理)的kernel。而chain這東西就是自然而然形成的，chain上的kernel可以沒有這個概念，他們就是只知道這份請求的src/dst，然後自己做一些處理而已，當然，有需要的話我們後續可以再做一些格式上的改進。AOS_KERNEL沒設的話就走AOS_DAEMON，兩個都沒設，那就報錯，代表你沒辦法用syscall。」

頂層推出的後果（使用者沒反對）：

- 不必讓 daemon 自動設 `AOS_KERNEL`，「沒設就退回 daemon」留著。
- 兩個都沒設時 `aos-agent` 現在還會猜 cwd 的 `./.stack`（[`py/daemon_ctl/table.py`](../../../../py/daemon_ctl/table.py) 的 `find_daemon`），照原話應改成報錯。
- 停／收／睡／醒要不要判是收件 proc 自己的事。
- 「通用 kernel 框架」定位是一包方便零件、不是概念，手寫一個也算。
- 條文方向：定義改成從寄件人角度講；「繼承式／0 號 proc 式」降成兩個範例擺法；「唯一能下 ctl」三級改成一句「靠 Linux 權限」。

## (7) 收尾

> 「判官這東西...我覺得應該將其吸納進我們之後的kernel框架中。不過沒關係，今天釐清了概念，後續架構規劃上就很輕鬆了。」

頂層的解讀（是解讀、不是使用者原話）：現有判官（`lib/aos/judge`）以後收進 kernel 框架，所以 (2) 選項框裁的「判官加下一站、數量另指、三個 hook 時機」是**框架要有的能力**，不急著改在現有判官身上；今天這場只到概念釐清，**沒有排任何施工**。
