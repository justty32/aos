## 1. 結論

- **兩套補的是同一樣缺的東西**：現在「一種 kernel 是什麼」沒有地方寫，全寫死在 mini 的程式裡（下面第 2 節，照程式核對過）。所以自己寫的 kernel 只能跑、不能 `merge`、沒有 effective、層數一律當 1；11-28 要加的 seccomp kernel、inotify 上限、時間上限，每加一樣都要改 mini 裡四五個地方。
- **A 檔案夾式**：一種 kernel＝一個夾，夾裡 `.aos/call` 是程式、`.aos/interfaces/aos/kernel/` 底下七個小檔寫它是哪一種、佔幾層、欄位怎麼合。pi 在裡面看到的跟現在一樣（一檔一值、`cat` 就讀得到）。使用者寫的設定檔一個字都不用改。
- **B manifest 式**：一種 kernel＝一份 `kinds/<種類>.json`（欄位表用 JSON Schema 的幾個關鍵字），mini 用四個呼叫（`version`、`check`、`merge`、`run`）跟 kernel 的程式講話。pi 在裡面改讀一份 `env.json`。每份檔都帶 `"aos": "格式/版號"`。
- **推薦 A**。理由三個：(1) pi 的工具是讀、寫、改、shell，一檔一值不用解析，「存取得到＝有」是 11-26 定的規矩；(2) 11-27 定的五件（每格固定檔、唯讀鎖、effective 一欄一檔、blame、lock）都已經照檔案做完、驗收過，A 約改 300～400 行【估】、驗收輸出不變，B 約 1000～1500 行【估】、五支驗收都要改、而且要使用者重新定那五件的形狀；(3) aos-daemon 的 `aos/ctl`、`procs/<名>/` 已經是檔案式，B 會變成兩種寫法並存。
- **B 比 A 好的地方**（照實寫）：起之前能照欄位表檢查設定、錯在哪一欄講得出來；別人寫的 kernel 能自己決定怎麼合；裡面一次讀一份就拿到全部；版本寫在每份檔上。其中第一項 A 也做得到（欄位表有型別），第二項以後要的話 A 可以只加一個可選的 `.aos/merge` 程式。

## 3. 兩套都不動的（已經定的）

1. 設定照名字放 `$AOS_HOME/kernels/<名字>.json`；一包＝夾加 `_chain.json`；`merge`、`use`＋`replace`／`without`（11-27）。
2. `--kernels a,b,c`，寫在前面的在外層；疊法是嵌套，不是合併（11-27 使用者：「後一層就是運行在前一層給出的環境裡，環境套環境」）。
3. 一隻 proc 在哪些 kernel 上，起它之前就定好（11-27 第 6 條）。
4. pi 先看 `$AOS_ENV`，沒設就看 `/`；宣告交給內層前鎖成唯讀（11-27）。
5. 夾叫 `.aos`、裡面的名字不加 `__`；存在＝存取得到（11-26、11-27）。
6. 普通程式什麼都不用知道；proc 自己的宣告放 `~/.aos`，`/.aos`（或 `$AOS_ENV/.aos`）講的是管它的那一方（11-27 第 5 條、第 159 段）。
7. 每次起來有 effective（附誰決定的）與 lock；`--explain`、`--diff`（11-27 七題第 7 題）。
8. Linux 巢狀約 32 層的上限寫成提醒，使用者自己合併；相鄰 cgroup、mask 照舊自動攤平（11-28）。

第 4、5、7 條的「內容」兩套都留；**形狀**只有 A 原樣留，B 會改（一檔一值變成 JSON 裡的欄位），所以選 B 等於請使用者重新定這幾條的形狀。

## 4. 為什麼是這兩套

main 建議的一對（A 檔案與資料夾、B 一份 manifest 加小呼叫協定）我讀完之後照用。分界是「約定寫在哪」：

- A：約定寫在**檔名與文字格式**裡。讀的一方只要會開檔。
- B：約定寫在**一份有欄位表的 JSON** 裡，加上程式之間的呼叫。讀的一方要會解析 JSON。

想過、沒選的另一對：「B 改成 OCI 那種一隻 proc 一份大 `config.json`，kernel 只是往裡面併的片段（像 systemd drop-in）」。不選的原因：那是合併模型，跟第 3 節第 2 條「嵌套、不是合併」相反；而且 kernel 就不能是任意程式了。

## 5. A：檔案夾式

一句話：**一種 kernel 是一個夾；一格宣告是一個夾；一個值是一個檔。**

### 5.1 kernel 作者寫什麼

一個夾。mini 自己的五種放 `proto9/mini-sandbox/kinds/<種類>/`，別人的放 `$AOS_HOME/kinds/<種類>/` 或任何路徑【擬】。

```
kinds/cgroup/
  .aos/call                          可執行檔，什麼語言都行
  .aos/interfaces/aos/kernel/        有這個夾＝「這個夾是一種 kernel」
      description   cgroup kernel: cpu, mem, pids for everything inside
      kind          cgroup           裡面那一格叫什麼（…/interfaces/aos/cgroup/）
      userns        1                佔幾層 user namespace
      flat          yes              沒有常駐行程，相鄰的可以一次做完
      place         any              any 或 innermost
      auto_mask     yes              裝了它就自動加 aos/mask/run-user
      fields        每行：欄位 合法 型別（見下）
```

`.aos/call` 就是 11-26 定的「用 `__call` 取代 `_entry`」改名後的寫法；「資料夾＝程式」。

cgroup 的 `fields`（後兩行是 11-28 待做的，先擺位置）：

```
cpu      min  percent
mem      min  size
pids     min  int
inotify  min  int
time     min  seconds
```

llm 的夾（`kind` 是 `llm`、`userns` 1、`flat` 是 `no`、`auto_mask` 是 `yes`）的 `fields`：

```
models       and   list
limit        min   int
upstream     same  text
state        same  path
fake_script  same  json
```

net：`allow and cidrs`、`host_ports and ports`、`down min rate`、`up min rate`、`quota min size`、`subnet same text`、`host_addr same text`；`userns` 是 `2`。mask：`paths or paths`、`keep and paths`。uid：`uid same int`，`place` 是 `innermost`。

合法只有五種【擬】，對上現在 `chain.py` 五個 merge 函式在做的事：

| 合法 | 意思 | 現在誰在用 |
|---|---|---|
| `min` | 取小 | cpu、mem、pids、limit、quota、up、down |
| `max` | 取大（數字越大越嚴的） | 新：sys 的 `preset` |
| `and` | 交集（`cidrs`、`ports` 照範圍算，不照文字） | allow、host_ports、models、keep |
| `or` | 聯集 | mask 的 paths；新：sys 的 `deny` |
| `same` | 要一樣，不一樣報 `KernelMergeBad` | upstream、state、fake_script、uid、subnet、host_addr |

型別【擬】：`int` `percent` `size` `rate` `seconds` `text` `path` `list` `paths` `cidrs` `ports` `json` `flag`。

mini 照 `fields` 做四件事：檢查設定的欄位認不認得、`merge`、算 effective 與 blame、算「內層寫得比外層鬆」。現在這四件各有五個寫死的函式。

**寫不進 `fields` 的，留在 mini**（照實寫）：llm 在 net 裡面時切掉網路、兩個 llm 要串起來（`KernelOrderBad`）、net 放行了 llm 上游時拒絕、mask 的「同一條路徑 tmpfs 與 null 不能混」。這些是兩種 kernel 之間的關係，不是一個欄位的事。

程式被叫的方式不變：`.aos/call --name N [--from 包] --json <config> -- 下一層…`，做完自己的事就 `exec` 下一層。這是 `nice`、`chroot`、`unshare`、`bwrap`、`systemd-run` 共用的形狀。改的只有一點：mini 不再用 `python3 -I` 去跑，直接執行 `.aos/call`，所以什麼語言都行。

### 5.2 使用者寫什麼

**跟現在一模一樣。** `<名字>.json`＝`{"description", "program", "config"}`，`_chain.json` 照舊。

- `"program": "cg_kernel.py"` 這種舊寫法照認（對到 `kinds/cgroup`）。
- 新寫法：`"program": "cgroup"`（種類名）或一個夾的路徑。

```json
{"description": "low limits", "program": "cgroup",
 "config": {"cpu": "20%", "mem": "512M", "pids": 64, "inotify": 128, "time": 3600}}
```

### 5.3 pi 在裡面看到什麼

跟現在一樣，加三條寫死的規矩。

```
$AOS_ENV/.aos/
  kernels                     一行一層：<種類> <名字> [from <包>]
  host_uid  host_subuid
  lock.json                   每層的檔、sha256、config
  effective/cgroup/cpu        20%
  effective/cgroup/blame      cpu 20% <- layer 1 aos/base/cg from aos/base
  interfaces/aos/cgroup/      description name layer status [from flattened] cpu mem pids asked namespace
  interfaces/aos/llm/         description name layer status kind path protocol api base models limit relay network
```

pi 怎麼用：`cat $AOS_ENV/.aos/effective/cgroup/mem`；`ls $AOS_ENV/.aos/interfaces/aos/` 看外面裝了哪幾種 kernel；`cat $(cat …/llm/status)` 看模型還能問幾次。

文字格式的規矩（前四條是現在已經在做的，寫成條文；第 5 條是建議；後三條是 11-27 留下的同名不同義，在這裡給答案【擬】，會碰到決策審查第 3 題）：

1. 一檔一值；清單一行一筆、空白分欄；檔尾換行。
2. 狀態檔一行一個 `key: value`，頭兩行固定 `state:`、`updated:`。
3. 每格固定 `description` `name` `layer` `status`。
4. 不認得的檔跳過。
5. 新加的檔把單位寫進名字（`_ms`、`_at`；cgroup v2 的做法，[02-可以抄的現成做法](../../../../proto9/docs/02-可以抄的現成做法.md) 建議過）。
6. 沒上限一律寫 `max`；空檔＝沒有、空清單。（net 的 `quota` `up` `down` 要改。）
7. 路徑：`/` 開頭是絕對，否則以宣告所在的夾起算。
8. `kind` 只表示「怎麼跟我講話」（`file` 或 `socket`）；net 的 `veth` 改叫 `link`。要收指令的 kernel 擺一個 `ctl`，照 `aos/ctl`。

### 5.4 命名與版本

- 名字：`a/b/c`，不准 `..`、`_` 開頭的段（現在的 `check_name`）。`aos/` 開頭是我們自己的；使用者的用別的開頭【擬】。
- 種類名：一個小寫的字，就是裡面那一格的名字（`cgroup`，不是 `cg`）。別人的種類帶自己的前綴，那一格就在 `interfaces/<前綴>/<種類>/`【擬】。
- 錯誤代號：照現在，一個英文名字（`KernelNotFound`、`KernelMergeBad`…），不是數字。
- **版本：檔案上不寫版號。規矩是「只加檔，不改既有檔的意思；要改意思就換介面名」**（`aos/llm` → `aos/llm2`，兩個可以同時擺）。這是 Plan 9、sysfs、cgroup v1→v2 的做法。proto 一向當沒有舊版，這條現在不花成本。

### 5.5 proc、agent、daemon 怎麼放在上面

- 普通程式：只多一個它不看的 `AOS_ENV`。
- agent：讀上面那些檔得知東西在哪（模型的 socket 在哪、上限多少）。宣告只用來查位置與數值，安全靠外層實際設的限制。
- proc 自己要宣告：寫 `~/.aos/interfaces/<誰>/<什麼>/`，同一套文字規矩。
- aos-daemon：它的 `.aos/interfaces/aos/ctl/{kind,path,commands}`、`procs/<名>/{name,pid,state,…}`、空檔 `aos/proc` 已經是這個形狀（`proto9/cpp/aos-daemon/README.md`），不用改。daemon 當基底時就是最外面那一層，它的宣告在 `/.aos`。

### 5.6 抄了誰

| 抄誰 | 抄什麼 |
|---|---|
| Plan 9 `/proc/n/ctl`、`status` | 一個東西一個夾、`ctl` 寫指令、`status` 讀狀態、`ls` 就是說明 |
| cgroup v2 的檔案慣例 | 一檔一值、沒上限寫 `max`、單位寫進名字、核心檔與各家檔用名字分 |

| systemd 容器介面（`/run/host`、`container=`）、credentials 夾、Kubernetes downward API | 外層寫好一個唯讀夾加一個環境變數給裡面讀 |

## 6. B：manifest 式

一句話：**一種 kernel 是一份 JSON；mini 用四個呼叫問它；裡面讀一份 JSON。**

### 6.1 kernel 作者寫什麼

一份 manifest 加一支會答四個呼叫的程式。

`kinds/cgroup.json`：

```json
{
  "aos": "kind/1",
  "kind": "cgroup",
  "description": "cpu, mem, pids limits for everything inside",
  "program": ["python3", "-I", "cg_kernel.py"],
  "userns": 1, "flatten": true, "place": "any", "auto_mask": true,
  "config": {
    "cpu":     {"type": "percent", "merge": "min"},
    "mem":     {"type": "size",    "merge": "min"},
    "pids":    {"type": "int", "minimum": 1, "merge": "min"},
    "inotify": {"type": "int", "minimum": 0, "merge": "min"},
    "time":    {"type": "seconds", "merge": "min"}
  },
  "calls": ["version", "check", "run"]
}
```

`kinds/llm.json`：

```json
{
  "aos": "kind/1",
  "kind": "llm",
  "description": "the only way to the model: HTTP on a unix socket, counts and caps requests",
  "program": ["python3", "-I", "llm_kernel.py"],
  "userns": 1, "flatten": false, "place": "any", "auto_mask": true,
  "config": {
    "models":      {"type": "list", "merge": "and", "required": true},
    "limit":       {"type": "int", "minimum": 0, "merge": "min", "required": true},
    "upstream":    {"type": "text", "merge": "same"},
    "state":       {"type": "path", "merge": "same"},
    "fake_script": {"type": "json", "merge": "same"}
  },
  "calls": ["version", "check", "merge", "run"]
}
```

`config` 那一段用 JSON Schema 的關鍵字（`type`、`minimum`、`enum`、`required`），加一個我們自己的 `merge`。Python 標準庫沒有 JSON Schema 驗證器（`jsonschema` 是另外裝的套件，MIT）；mini 現在只用標準庫，所以要嘛多一個相依、要嘛自己做這幾個關鍵字的子集【擬：自己做子集】。

四個呼叫（形狀抄 CNI：動詞、JSON 從 stdin 進、JSON 從 stdout 出）：

| 呼叫 | 進 | 出 |
|---|---|---|
| `version` | 無 | `{"aos": ["kind/1"]}`：我會哪幾版 |
| `check` | `{"name", "config", "outer": <外層的 env.json>}` | `{"config": <整理過的>, "declares": {…}, "warnings": […]}`；什麼都不起 |
| `merge`（可選） | `{"configs": [a, b]}` | `{"config": …}`；沒有這個呼叫就照 manifest 的 `merge` 合 |
| `run` | `run --name N --json <config> -- 下一層…` | 不回，做完 `exec` 下一層（跟現在一樣；包住下一層的事沒辦法做成一問一答） |

錯誤：退出碼非 0，stdout 一行 `{"error": "ConfigBad", "message": "…"}`（名字不是數字，varlink 的做法）。

### 6.2 使用者寫什麼

設定檔改兩處：加 `aos`，`program` 換成 `kind`。

```json
{"aos": "kernel/1", "kind": "cgroup", "description": "low limits",
 "config": {"cpu": "20%", "mem": "512M", "pids": 64, "inotify": 128, "time": 3600}}
```

`_chain.json` 加一行 `"aos": "bundle/1"`，其餘照舊。好處：編輯器照 schema 提示欄位；mini 起之前一次把整串檢查完，錯在哪份檔哪一欄講得出來。

### 6.4 命名與版本

- 名字規則同 A。
- **版本：每份檔第一個鍵 `"aos": "<格式>/<版號>"`**：`kind/1`、`kernel/1`、`bundle/1`、`env/1`、`lock/1`、`status/1`。repo 裡已有同樣的寫法（`wf-table/1`）；OCI 是 `ociVersion`。kernel 的程式用 `version` 呼叫說自己會哪幾版（CNI 的做法）。版號不合時 mini 在起之前就拒絕。

### 6.5 proc、agent、daemon 怎麼放在上面

- 普通程式：同 A。
- agent：要會讀 JSON。
- proc 自己要宣告：寫 `~/.aos/env.json`【擬】。
- aos-daemon：它現在的 `aos/ctl/{kind,path,commands}` 與 `procs/<名>/` 是檔案式。選 B 的話要嘛改成 `procs/<名>/state.json`（像 OCI 的 state：`id`、`status`、`pid`…），要嘛兩種寫法並存。

### 6.6 抄了誰

| 抄誰 | 抄什麼 |
|---|---|
| OCI runtime-spec | 一份 JSON 講完一件事、`ociVersion` 那種版本欄、state 的固定幾欄（`id` `status` `pid`）、hook 從 stdin 收 JSON |
| CNI | 外掛程式的呼叫形狀：動詞、stdin 進 JSON、stdout 出 JSON、`VERSION` 問會哪幾版 |
| JSON Schema | 欄位表的關鍵字（`type` `minimum` `enum` `required`）；自己加 `merge` |
| varlink | 錯誤是名字加參數；服務答得出「我會哪些」 |
| NixOS 模組系統 | 型別決定怎麼合 |
| OCI／Docker 的 seccomp profile JSON | 同 A |
| repo 自己的 `wf-table/1` | `"格式/版號"` 的寫法 |

OCI、CNI 的規格是 Apache-2.0；只借形狀與欄位的想法，不照抄條文。

|---|---|---|

## 8. 11-28 待做的幾件放哪（兩套一樣，只是寫法不同）

| 待做的 | 放哪【擬】 | A 怎麼寫 | B 怎麼寫 |
|---|---|---|---|
| 每層 inotify／fanotify 上限 | cgroup 種類多兩個欄位 | `fields` 加 `inotify min int`、`fanotify min int` | `config` 加兩項 |
| 時間上限 | cgroup 種類多一個欄位 `time`（到了殺整個 scope；不另開一種，省一層） | `time min seconds` | 一項 |
| seccomp kernel 三份預設 | 新種類 `sys`，設定叫 `aos/sys/loose`、`aos/sys/strict`、`aos/sys/allowlist`；`flat` 是 `yes`（filter 只能加，相鄰的合成一張表） | `preset max int`、`deny or list` | 同樣三項寫進 `config` |
| speculation 開關 | `sys` 種類的一個欄位 | `speculation or flag` | 一項 |
| 預設多遮 `/proc/interrupts` 等 | 不是格式的事：改 `aos/mask/…` 的設定檔 | — | — |
| 巢狀約 32 層 | 種類自己說佔幾層 | `userns` 檔 | `"userns"` 欄 |

現在的做法下，這幾件每件都要改 `chain.py` 的表、`MERGE`、`effective.py`、`flat_kernel.py`。有了種類的定義（A 或 B 都行），加欄位只要改種類的那份定義和那支程式。

`sys` 的 `preset` 用 `max` 合（1 少量危險的、2 比較嚴、3 白名單）是我擬的；「全擋」到底是不是白名單，main 的信說做之前要跟使用者確認一句，這裡不替他答。

## 9. 並排

| | 現在 | A 檔案夾式 | B manifest 式 |
|---|---|---|---|
| 一種 kernel 的定義 | 寫死在 mini 的五張表、十個函式 | 一個夾：`.aos/call` 加七個小檔 | 一份 `kinds/<種類>.json` |
| 自己寫的 kernel | 只能 Python；不能 merge、沒 effective | 任何可執行檔；照 `fields` 就有 merge、effective | 程式要會答四個呼叫；可以自己決定怎麼合 |

| 起之前的檢查 | 各支程式起來時自己查 | mini 照 `fields` 查欄位與型別 | mini 照 schema 查，再問每支 `check` |

## 10. 推薦

**A。** 具體理由就是第 1 節那三個；一句話講：缺的只有「一種 kernel 的定義沒地方寫」，A 用最少的改動補上，其他已經做好、驗過、使用者定過的都不動。

B 裡值得留意的兩樣，以後要的話可以單獨加進 A，不用整套換：

- **設定檔可選的 `$schema`**：從 `fields` 生一份 JSON Schema 給編輯器用，mini 不靠它。
- **kernel 自己決定怎麼合**：種類夾裡多一個可選的 `.aos/merge` 可執行檔（11-26 定過「可執行檔與 `.json` 都有時聽可執行檔的」，同一個道理）。

## 11. 等使用者的六題

1. **選哪一套？**
   - 甲（推薦）：A。pi 在裡面看到的不變；你的設定檔不用改；約 300～400 行。
   - 乙：B。pi 要會讀 JSON；你的 11 份設定檔各改兩處；11-27 定的五件形狀重來；約 1000～1500 行。
   - 丙：A，另外加上面那兩樣 B 的東西。比甲多約 100 行【估】；建議等真的有人要再加。
2. **一種 kernel 的定義要不要從 mini 搬出來？**（選 A 或 B 都要答）
   - 甲（推薦）：搬。之後加 sys、inotify、時間上限只改那一種自己的定義。
   - 乙：不搬，維持寫死。這次什麼都不用改；之後每加一種要改 mini 四五處，自己寫的 kernel 照舊不能 merge。
3. **自己寫的 kernel 程式可以是任何語言嗎？**
   - 甲（推薦）：可以，mini 直接執行那個檔。
   - 乙：維持只收 Python（現在是用 `python3 -I` 去跑）。
4. **版本怎麼標？**
   - 甲（推薦，配 A）：檔上不寫版號；只加不改，要改意思就換介面名。
   - 乙（B 的做法，A 也能用）：每份 JSON 檔加 `"aos": "格式/版號"`。你的設定檔每份多一行。
5. **同名不同義那三件，這次一起定嗎？**（11-27 你說跟決策審查第 3 題一起定；那題四小項的報告在公司機，我沒讀到）
   - 甲（推薦）：這次定，照 5.3 的規矩 6～8（沒上限寫 `max`；`/` 開頭絕對、否則相對宣告夾；`kind` 只表示怎麼連，net 的改叫 `link`）。pi 在裡面：跨種類讀這三樣時意思一致。
   - 乙：繼續等第 3 題。通用格式的這三條先空著。
6. **11-28 那幾件放哪，照第 8 節嗎？**（這題 main 的信說由 main-alt 決定，不答就照甲）
   - 甲（推薦）：inotify、時間上限放 cgroup 種類；seccomp 與 speculation 放新的 `sys` 種類。
   - 乙：時間上限另開一種 kernel。多佔一層 user namespace。

## 12. 沒驗的與猜的

- 兩套都**沒有寫任何程式**；行數是照現有檔案大小估的（非空行：`chain.py` 531、`effective.py` 284、`nest.py` 329、五支 kernel 共 1311、五支驗收共 2054），沒試做。
- 抄誰那兩張表（OCI、CNI、JSON Schema、varlink、NixOS、bwrap、systemd、cgroup v2）是憑記憶寫的，這次沒有上網逐條核對（這隻沒有上網的工具）。Landlock 我記得沒有通用的設定檔格式，所以沒列。
- 「`fields` 五種合法就夠」是照現在五個 merge 函式歸納的；net 的 `quota` 在 effective 裡還帶「各層自己的計數」這種註記，通用函式要留一個地方放註記，沒細想。
- 決策審查第 3 題（`aos/ctl` 的形狀四小項）的報告在公司機，沒讀到；第 5 題的甲會碰到它。
- `$AOS_HOME/kinds/` 這個放的位置、`aos/sys/…` 的名字、`time` 放 cgroup，都是我擬的。
- B 的 `env.json` 每層要不要整份重寫（跟現在每層整份抄 `.aos` 同樣的成本）沒量。
