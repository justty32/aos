# 追加方向：長成 Linux 安裝包的形狀

你的原話（11-17 下午）：「cmd只留薄入口...看要不要直接組成bin/, lib/, include/，就如同linux的標準安裝包？」

## 先講結論

- **「原始碼長什麼樣」跟「裝好長什麼樣」是兩件事。** Linux 安裝包的 `bin/ lib/ include/` 是裝好的樣子；原始碼通常另外照語言分。你路徑-2 選了 B（樹直接指 repo、沒有安裝這一步），所以只有兩條路：repo 自己長成裝好的樣子，或把安裝這一步加回來。
- **它跟「`lib` 改名 `py`」撞名**：安裝包形狀裡 `lib/` 是保留字，Python 的東西要住在 `lib/` 底下，頂層就不會有 `py/`；C++ 原始碼沒有位子，要另開 `src/`，頂層也不會有 `cpp/`。兩句話只能選一句當頂層。
- **有一個兩邊都拿得到的折衷（L-輕）**：頂層照語言分（`cpp/`、`py/`），只把「可以跑的」收成一個頂層 `bin/`——剛好就是「`cmd` 只留薄入口」做到底的樣子，`PATH` 只加一個夾。

## 一張表：四種做法並列

| | 照語言分（[11](11-備案-cpp標準形式.md)、[12](12-備案-py標準形式.md) 的推薦） | L-輕：照語言分＋一個 `bin/` | L-1：repo 就是安裝包 | L-2：照語言分＋安裝一步 |
|---|---|---|---|---|
| 頂層 | `cpp py cmd templates knowledge docs thinking archive` | `bin cpp py templates knowledge docs thinking archive` | `bin lib include src share docs thinking archive` | 原始碼同第一欄；另有裝出來的 `bin lib include share` |
| 有沒有安裝步驟 | 沒有 | 沒有 | 沒有 | **有**（每次改完要再裝） |
| `AOS_HOME` 指哪 | repo 的 proto8 | repo 的 proto8 | repo 的 proto8 | 裝出來的那包 |
| `PATH` 加幾段 | C-中後 22（`cmd` 21＋`cpp/build/bin`） | **1** | **1** | **1** |
| `lib` 改名 `py` | 做 | 做 | **不做**（`lib` 留著、意思變寬） | 原始碼做；裝出來的仍叫 `lib` |
| 指示詞 `/lib/base/read` | 要改（223 處） | 要改（223 處） | **不用改** | 看裝出來的長相，可以不改 |
| `cmd` 的邏輯 | 你裁（卡點 2） | 一定搬進 `py`（＝P-大） | 一定搬進 `lib/python` | 一定搬 |
| 跟今天定的事 | 都合 | 都合（八夾仍是八夾） | 八夾的名字換掉五個 | 動路徑-2（樹不再直接跑 repo） |

## L-輕：照語言分＋一個頂層 `bin/`

```
proto8/
  bin/          可以跑的全在這：21 支 Python 薄入口（各 4 行，進 git）
                ＋ 10 支 C++ 執行檔（編出來的，不進 git）
  cpp/          C++ 原始碼（C-中；產物的執行檔寫到 ../bin，.a 留在 cpp/build/lib）
  py/           Python 套件、工具、packs、schema、測試（P-大：應用邏輯也在這）
  templates/  knowledge/  docs/  thinking/  archive/
```

- `cmd/` 併進 `bin/` 後消失；`cmd` 裡不是程式的東西（aos-view 的 `ui/ web/ systemd/ aide-def/`、各支 README、`cmd/docs`）跟著邏輯進 `py/`。
- `env.sh` 的 `PATH` 從掃 31 個夾變成一行 `PATH="$AOS_HOME/bin:$PATH"`。
- 薄入口找套件只往上一層（`../py/src`），比現在的 `../../../lib` 短。
- 代價：就是 P-大的代價（約 16,700 行、108 支測試搬家），外加 `bin/` 裡進 git 的與不進 git 的混放（見下）。
- 不想混放的變體：C++ 執行檔留在 `cpp/build/bin`，`PATH` 兩段。

## L-1：repo 自己就是安裝包（不用安裝步驟）

```
proto8/
  bin/          同 L-輕
  lib/
    python/aos/   Python 套件（原 lib 頂層模組＋lib/agent 共用模組＋cmd 的應用邏輯）
    base/ aos/ agent/ packs/   工具與工具包——位置不變，$AOS_HOME/lib/base/read 照舊
    schema/
    libaos-*.a  libaos-inst.so   C++ 編出來的（不進 git）
  include/aos/  C++ 公開標頭（原始碼，進 git；8 個專案的 include/ 併成一個）
  src/          C++ 的 .cpp、CMake、測試（原 impls；Linux 安裝包裡沒有它的位子，只好另開）
  share/        templates/ knowledge/（要不要搬見下）
  docs/  thinking/  archive/
```

- 好處：`lib` 不改名，**最貴的那筆（約 1,075 處、其中指示詞 223 處）省掉**；`PATH` 一段；看起來就是 `/usr/local` 的樣子。
- 代價：
  - 沒有 `cpp/`、`py/` 這兩個名字，跟你前一句「改名為 cpp/、py/」二選一。
  - `lib/` 變成三種東西同層：進 git 的 Python 與工具、不進 git 的 `.a`。
  - C++ 一個專案的標頭在 `include/aos/`、實作在 `src/aos-exec/`，分在兩棵樹；而且現在「誰能 include 誰」是靠每個專案只露自己的 `include/` 管的，併成一個頂層 `include/` 之後任何專案都 include 得到任何標頭，分層少一道把關。
  - `src/` 這個名字只裝 C++，Python 的原始碼卻在 `lib/python/`，「原始碼在哪」的答案變兩個。

## L-2：原始碼照語言分，另加一步安裝

```
proto8/（原始碼）                     <prefix>/（裝出來的，＝AOS_HOME）
  cpp/ py/ cmd/                  →     bin/  lib/  include/  share/
  templates/ knowledge/ …
```

- 這是教科書做法：`cmake --install`＋把 Python 與範本抄過去。`<prefix>` 可以是 `proto8/dist/`（不進 git）或 `~/aos-home` 本身。
- 好處：跑的那份跟正在改的那份分開（agent 改到一半的程式不會被跑著的樹用到——這正是路徑-2 選 B 時你接受的缺點）；裝出來的形狀最乾淨。
- 代價：**把今天拿掉的「抄樹」加回來**——每次改完要再裝才生效；重建步驟多一步；測試要分「測原始碼」與「測裝好的」；要寫並維護安裝規則（C++ 的 `install()`、Python 與範本的抄法）；動到路徑-2 的答案。

## 你問到的五件事

**1. `bin/` 混放行不行、`.gitignore` 怎麼寫**（暫存 git 倉實測）

| 寫法 | 結果 | 代價 |
|---|---|---|
| 逐名列出 10 支 C++ 執行檔 | 行。薄入口正常進 git | 新增一支 C++ 執行檔忘了加，`git status` 會把它列成新檔（看得到，但可能被誤交） |
| 整個 `bin/` 忽略，薄入口用 `git add -f` 強加 | 行。已進 git 的入口之後改動照常 `git add` | 每個新入口第一次要 `-f`；`commit-request` 支不支援沒查 |
| 不混：C++ 留 `cpp/build/bin` | 不用特別寫 | `PATH` 兩段 |

還有一個要小心的：C++ 執行檔與 Python 入口同夾，名字一樣就會互蓋（現在 31 個名字沒有重複）。

**2. `lib/` 收什麼、跟改名 `py` 怎麼並存**：見上面 L-1 的樹。並存的辦法只有兩個——頂層叫 `lib/`、Python 住 `lib/python/`（L-1）；或頂層叫 `py/`、不要頂層 `lib/`（L-輕）。C++ 的 `.a` 在 L-輕裡留在 `cpp/build/lib`，沒人從外面連它。

**3. `include/` 有沒有人用**：沒有。C++ 標頭只有 aos 自己編的時候用；repo 裡沒有別的專案 `#include <aos/…>`（`impl_cpp/` 是你另寫的，不連這些）；執行期也沒有東西讀標頭。放到頂層的唯一用處是「哪天有外部 C++ 專案要連 aos 的函式庫」。現在放，只付代價（上面講的分層少一道把關）沒有收益。

**4. `templates`、`knowledge`、`docs`、`thinking` 放哪**

| 選項 | 後果 |
|---|---|
| 留頂層 | 不動。`$AOS_HOME/knowledge/aos/_description.json`（寫在 `AGENTS.md` 與派工提示裡）、`$AOS_HOME/templates/…` 照舊。`/opt/<包>` 式的安裝包本來就可以有自己的頂層夾 |
| 進 `share/` | 最像 `/usr/share`。`$AOS_HOME/templates`、`$AOS_HOME/knowledge` 兩種指示詞全部要改（今天路徑規劃數過，`AOS_HOME` 指示詞約 200 處）；`thinking` 一搬約 5,300 行連結要重算（八夾規劃數過）。純粹為了長相，沒有功能上的收益 |

`docs`、`thinking`、`archive` 是給人看的紀錄，不是「裝好要用的東西」，哪個做法都建議留頂層。

**5. 跟其他方案的關係**：L-輕＝C-中＋P-大＋「`cmd` 改名 `bin` 並攤平」，可以排在施工單最後一步，前面的步驟一步都不用改；L-1 要在施工前就定（它決定 `lib` 改不改名）；L-2 是在任何一種原始碼形狀上再加一層，隨時可以加。
