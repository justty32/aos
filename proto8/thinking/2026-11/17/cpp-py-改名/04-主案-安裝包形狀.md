# 主案：原始碼在 `cpp/`、`py/`，安裝腳本把成品與入口放進 `bin/`、`lib/`、`include/`

你的原話全文（六句）在[入口](../cpp-py-改名.md)。這一檔照的是其中三句：「原始碼在 cpp/、py/，成品與入口另外放bin,lib,include」「跑個安裝腳本，編譯一下C++…python也稍微處理一下，然後bin/,lib/include就都會有東西」「git pull下來，重跑安裝腳本，然後就一切搞定」。

## 先講結論

- **推薦：執行期只認安裝產物。** 安裝腳本把 `py/` 抄成 `lib/`（不含測試與說明）、把 C++ 編進 `bin/` 與 `lib/`、在 `bin/` 產生 Python 入口。跑起來的東西只看 `bin/`、`lib/`（加上 `templates/`、`knowledge/`），永遠不看 `cpp/`、`py/`。
- **這樣有兩份 Python，但規則只有一句、沒有例外**：「改原始碼→重跑安裝才生效」，C++ 與 Python 同一套。今天那顆雷的病根是三種找法混用（連結、抄本、repo 各一份）；這裡只有一種。
- **代價要講明**：開發時每改一次 `py/` 要重跑 `install.py` 才看得到（Python 那段是抄檔，約一秒）；「改 repo＝改活樹」不再成立——對跑著的樹反而是好事（agent 改到一半的程式不會被用到）。
- 另一條路「入口直接用 `py/`」也攤在下面：方便，但 `lib/` 形同虛設。

## 樹（推薦做法）

```
proto8/                      ＝ AOS_HOME（不變）
  install.sh  env.sh  README.md
  cpp/        C++ 原始碼（原 impls，11 個專案原樣；怎麼編照舊）          進 git
  py/         Python 原始碼                                           進 git
    aos/        一個套件：共用模組＋cmd 搬來的應用（aos/apps/…）
    tools/      「資料夾＝程式」的工具：base/ aos/ agent/（90 個）
    packs/  schema/
    tests/  docs/  entries.json（哪些指令、各指到哪個模組）
  templates/  knowledge/  docs/  thinking/  archive/                  進 git，照舊
  ─────────── 以下全是 install.sh 的產物，不進 git ───────────
  bin/        9 支 C++ 執行檔 ＋ 21 支 Python 入口（各約 5 行，照 entries.json 生）
  lib/        aos/  tools/  packs/  schema/   ← py/ 的抄本（不含 tests、docs）
              libaos-*.a  libaos-inst.so      ← C++ 編出來的
  include/    aos/*.hpp                       ← 各專案公開標頭的抄本
```

`lib/` 的擺法刻意跟 `py/` 一模一樣（只少測試與說明）：同一支程式不管在 `py/` 還是 `lib/`，用「自己的位置找鄰居」都找得到，不用寫兩套找法。

頂層資料夾：進 git 的 7 個（`cpp py templates knowledge docs thinking archive`）＋產物 3 個（`bin lib include`）。

## 最要緊的一題：執行期認哪一份（題 L-1）

| | 甲：只認安裝產物（推薦） | 乙：入口直接用 `py/` 原始碼 | 丙：`lib/` 放連結 |
|---|---|---|---|
| `install.py` 對 Python 做的 | 抄 `py/` → `lib/`；產生入口 | 只產生入口 | 建連結 `lib/…`→`py/…`；產生入口 |
| 一支 Python 程式幾份 | 2（原始碼、成品） | 1 | 1（兩個路徑名） |
| 改了 `py/` 何時生效 | 重跑 `install.py` 之後 | 存檔就生效 | 存檔就生效 |
| `git pull` 之後 | 重跑 `install.py`（你說的流程） | Python 馬上是新的、C++ 還是舊的，直到重跑——**會有一段新舊混搭** | 同乙 |
| 跑著的樹會不會吃到改到一半的程式 | 不會 | 會（今天路徑-2 B 的已知代價） | 會 |
| `lib/` 裡有什麼 | Python 套件、工具、工具包、`.a` | 只有 `.a`，形同虛設 | 看起來有，其實是 `py/` |
| 指示詞 | `/lib/tools/base/read` | `/py/tools/base/read` | `/lib/tools/base/read` |
| 開發的人（你與 agent） | 每改一次重裝；測試前要先裝，不然「經指令跑的」測到舊的、「直接 import 的」測到新的 | 跟現在一樣 | 跟現在一樣 |
| 會踩的雷 | 改到 `lib/` 的抄本（下次安裝被蓋掉，而且 `lib/` 不進 git、`git status` 看不到） | 無新雷 | 程式用真實位置與表面位置算出來的層數不同 |
| 壓雷的辦法（都不是新機制） | 安裝時先清再抄；抄本設成唯讀；`lib/` 整夾被 git 忽略所以不可能被誤交 | — | 全部統一用真實位置 |
| 對今天的答案 | 路徑-2 B 的字面還在（`AOS_HOME` 指 repo 的 proto8），但「樹跑的就是 repo 當下的程式」變成「repo 上次安裝的程式」 | 不動 | 不動 |

推薦甲的理由：你三句話講的都是「安裝」這個模型（裝了才有、更新就重裝）；它讓 C++ 與 Python 同一條規則；`git pull` 到重裝之間樹還是完整的舊版，不會新舊混搭；對公司機「改 repo＝改活樹」那條要小心的硬規則，反而解套。

甲的一個實作前提：這個 repo 的測試本來就規定在 `git archive` 抄出的乾淨複本上跑，流程變成「抄出來→`install.py`→測」，多一步但不改習慣。

## 哪些進 git

| 夾 | 進 git | `.gitignore` |
|---|---|---|
| `cpp/`、`py/`、`templates/`、`knowledge/`、`docs/`… | 全部（除了 `cpp/build/`、`__pycache__/`） | 根現有的 `build/` 規則已涵蓋 |
| `bin/`、`lib/`、`include/` | **全部不進** | 加三行 `/proto8/bin/`、`/proto8/lib/`、`/proto8/include/`；現有給 `cmd/*/bin/` 的例外，`cmd` 收掉後一起拿掉 |

後果：剛 clone、還沒跑 `install.py` 的 repo 裡一支指令都沒有。之前擔心的「`bin/` 裡進 git 的與不進 git 的混放」不存在了。

## 執行期去哪找（甲）

| 找什麼 | 去哪 | 怎麼找 |
|---|---|---|
| 指令與 C++ 執行檔 | `bin/` | `PATH` 一段：`$AOS_HOME/bin`（現在是 30 段） |
| Python 套件 `aos` | `lib/` | 家裡：入口加 `../lib`；工具從自己的位置往上找到有 `aos/` 的那層。家外（抄出去的格）：`$AOS_HOME/lib` |
| 工具、工具包 | `lib/tools/…`、`lib/packs/…` | 定義裡的指示詞 `{"$env":"AOS_HOME","$path":"/lib/tools/base/read"}` |
| 範本、知識庫 | `templates/`、`knowledge/` | 照舊（它們不用處理，直接就是成品） |
| C++ 函式庫、標頭 | `lib/*.a`、`include/` | 執行期沒人找；外面的 C++ 專案要連 aos 時才用 |
| `cpp/`、`py/` | — | **執行期沒有任何東西去那裡** |

`AOS_HOME` 不變，還是 proto8 那一夾；`env.sh` 與它的分工見 [13](13-安裝腳本與新使用者流程.md)。

## 工具資料夾放哪（題 L-2）

90 個工具（89 個 Python、1 個 sh）＋18 份工具包清單。原始碼一定在 `py/`（你裁的）；`lib/` 照抄，所以底下怎麼擺決定指示詞長相：收一層 `tools/`（`/lib/tools/base/read`，約 190 處指示詞要插一段）或照現在（`/lib/base/read` 一字不改，但工具群 `aos/` 會跟套件 `aos/` 同層同名）。選項表在 [06 第 2 點](06-卡點.md)。

## C++ 標頭與 `include/`（題 L-4）

現況：8 個專案各有 `cpp/<專案>/include/aos/…`，只有 aos 自己編的時候用；repo 裡沒有別的東西 `#include <aos/…>`（`impl_cpp/` 有自己的標頭，不連這些）。

推薦安裝時抄一份到 `include/aos/`：跟 `lib/` 同一個道理（原始碼在 `cpp/`，成品是抄本），「誰能 include 誰」照舊由各專案只露自己的 `include/` 把關。另兩個選項（標頭直接搬到頂層、先不設）在 [08](08-要裁的題.md) 題 L-4。

## 「不考慮 vcpkg、cmake」我們的讀法（題 L-3，要你確認）

你前面說「C++這塊也先不考慮vcpkg, cmake啥的」，後面又說安裝「可能會需要vcpkg, cmake, gcc等」。我們讀成：**照舊用 cmake＋vcpkg 編；不去做 CMake 的標準專案形式（presets、`install()` 目標、套件化）。** 主案對 C++ 只動一件事：10 份 CMakeLists 裡「成品寫到哪」那一行，從各專案自己的 `bin/`、`lib/` 改成頂層的。實測見 [09](09-實測紀錄.md)。

## 沒有走的路（一句話帶過）

- repo 直接就是 `bin/lib/include`、原始碼住在 `lib/` 裡：你裁了原始碼在 `cpp/`、`py/`。
- Python 做成可 `pip install` 的套件、C++ 做成標準 CMake 專案：你說先不考慮；定案前攤的留在 [11](11-備案-cpp標準形式.md)、[12](12-備案-py標準形式.md) 當紀錄。
- 安裝到 repo 以外的地方（`~/aos-home`、`/usr/local`）：你描述的是在 clone 下來的 repo 裡原地裝；`AOS_HOME` 指 repo 的 proto8。
