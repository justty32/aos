# 要你裁的題：每題選項、後果、推薦

先選方案（甲／乙／丙，或只做第一步），下面的題多半就跟著定了；想分開答也可以。

## 題 0　走哪個方案

- A 甲，分三步（推薦）：8 個；活樹五夾變三夾，要換樹兩棵各一次。
- B 只做第一步：11 個；小工、不碰活樹。之後要不要往下再說。
- C 丙：9 個；活樹不動，`archive` 搬出 proto8。
- D 乙：7 個；大工，要改「`AOS_HOME`＝proto8 本身」的說法。

## 題 1　頂層三個檔（`README.md`、`_index.json`、`install.sh`）算不算

- A 不算、留原地（推薦）：`README.md` 是入口；`_index.json` 是 `index_view` 要讀的生成物，位置固定；`install.sh` 用自己所在位置找 `impls`、`cmd`，文件與活樹的 `env.sh` 提示都寫 `proto8/install.sh`。
- B `install.sh` 搬進 `cmd/`：頂層只剩兩個檔，但要改腳本找夾的寫法與所有提到它的地方。

## 題 2　`thinking` 留在 proto8 嗎

- A 留、原地不動（推薦）：一行連結都不用改。
- B 搬去別處（repo 根或 `wf/`）：proto8 少一夾，但它自己約 5300 行連結的相對路徑全要重算，別處約 1200 行指進來的也要改；條文 `docs` 的出處連結幾乎都指它。
- C 併進 `docs/thinking/`：同 B 的代價，而且你今天才要 `docs` 精簡成幾個小檔就看得完。

## 題 3　`archive` 的去處

- A 留 `proto8/archive`（推薦）：合現行規則「封存進所屬的 `archive/`」。
- B 搬去 repo 根 `archive/proto8/`：proto8 少一夾（丙案靠這個），活文件 38 行要改；repo 根的 `archive/` 現在只放舊世代，混進現役世代的封存。

## 題 4　`extras` 解散還是留；aos-view 何時搬

- A 解散，aos-view 等改名那次一起搬進 `cmd/`，其餘現在就各歸各位（推薦）：最後 8 個；改名前先停在 9。
- B 留著當「還沒定位」的夾：甲案就是 9 個。
- C 現在就把 aos-view 搬進 `cmd/`：早一點到 8，但它改名時路徑又要壞一次。
- 附帶：`langs`（Janet／Lua）封存可以嗎；`tree-swap`、`aos-home` 進 `cmd/` 還是等路徑規劃後看要不要留。

## 題 5　`user-advice` 去哪

- A `thinking/user-advice/`（推薦）：thinking 本來就收「使用者原文」；跟月份夾並列。
- B `docs/user-advice/`：它是草稿不是條文，放 docs 會混。
- C 併進 `wf/advices`：那裡你說是「蒐集 AI 對 aos 的意見」，你自己的稿放進去會混。
- 後果都一樣：thinking 裡有 104 行連到舊位置（題 11）。

## 題 6　`feedback` 去哪

- A `wf/advices/feedback/`（推薦）：你 11-17 說「prot8/feedback 也幫我弄進 wf/advices」；今天因為程式預設位置在 proto8 才沒搬。要改 `storage.py` 一個函式與測試。
- B `cmd/aos-feedback/` 裡面：資料跟著指令走，程式改得最少，但意見檔藏比較深。
- C 留在 proto8 頂層：那就多一夾。

## 題 7　`notes`（AI 寫的參考筆記 4 篇）去哪

- A `docs/notes/`（推薦）：都是給人讀的；README 照舊寫明「不算數、條文為準」。
- B `archive/`：10 月寫完就沒再動，當封存；活文件有 5 行連它要拿掉。
- C `thinking/notes/`：跟你 10-12 定的「整份 AI 產出不放 thinking」相撞，不建議。

## 題 8　`py` 要不要併進 `lib`

- A 併成 `lib/py/`（推薦，跟路徑規劃同一次做）：活樹少一夾；約 30 處程式要改；`lib` 不 import `py` 的單向規矩照舊（變成 `lib` 其他部分不 import `lib/py`）。
- B 模組直接平鋪進 `lib/`：少一層，但 `lib` 頂層已有 20 支 `.py`，「腦叫的工具」跟「指令共用模組」會分不清。
- C 不併：甲案最少 9 個。
- D 併進 `cmd/`：不行，活樹沒有 `cmd`，而 agent-fsm 的格在活樹裡要用 `aos_flags`。

## 題 9　`kernel` 要不要併進 `templates`

- A 併成 `templates/kernel/`（推薦）：`kernel/` README 自己說是「可以直接抄去用的 kernel 範本」；C-74 最上層 agent、kernel 並列，都算範本。`cp -r $AOS_HOME/kernel/<名>` 改成 `$AOS_HOME/templates/kernel/<名>`。
- B 四份平鋪進 `templates/`（`templates/llm-kernel` 等）：路徑短，但 agent 範本與 kernel 範本混在一層。
- C 不併：多一夾。
- 注意：`kernel` 這個詞照 C-54 一詞一義，資料夾併了，詞不變。

## 題 10　跟 11-16 的「路徑規劃」併不併

- A 第一步現在做，第二步等路徑規則定了一起做（推薦）：小夾沒踩地雷，不用等；`py`、`kernel` 正好是地雷本身，先定規則（要不要只認 `$AOS_HOME`、還要不要「往上找」），搬夾與改找法一次到位。
- B 全部等路徑規劃：最穩，但 17 個夾會再放一陣子。
- C 先搬再說：快，但 22 支指令與測試的路徑寫法可能改兩輪。

## 題 11　舊紀錄裡指到舊夾的連結

- A 舊紀錄不改，在 `thinking/README` 的改名表加一段「11-17 以後：`py` → `lib/py`…」（推薦）：照 11-06 重劃夾的前例與 moving-things「當時的紀錄不改」。後果：那些連結點下去是壞的（甲約 410 行、只做第一步約 210 行）。
- B 用腳本只改連結的目標、不動文字：連結都活著，但動到上百份歷史檔，要逐份對。
- 活文件（條文、README、wf）的連結不在這題，一律跟著改。

## 題 12　空的 `proto8/bin/` 刪不刪

- A 刪，`.gitignore` 的 `!proto8/bin/` 一起拿掉（推薦）：裡面只有沒進 git 的 `__pycache__`；刪檔照鐵律 2 要你點頭，兩台機器各刪一次。
- B 留著：不進 git 所以別人 clone 看不到，但你本機會一直看到它。
