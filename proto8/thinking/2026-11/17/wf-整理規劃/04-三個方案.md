# 04 三個方案

三個是疊上去的：A 是 B 的前兩步，B 是 C 的前半。都接在 11-13 的 [wf-into-aos-plan](../../13/wf-into-aos-plan.md) 上，不另起一套。

已定、三個方案都照著走的（11-13 使用者裁）：歷史紀錄原地凍結（Q1）；進度表單條化成 json（Q5）；HANDOFF 只留一條（Q12）；待使用者的新題寄專區；樹內的信走 aos 信箱、`wf/inbox` 只收樹外；code map 在 `wf/knowledge/`；段 3 以後的工作流「用到才換」成 json（Q6）；最後 WORKFLOWS、INDEX、STRUCTURE 退場、手寫 `wf/_index.json`（段 9）。

三個方案共同的一條原則：**還在用的規矩檔現在不搬位置**。它們遲早照段 4～6 轉成 json、路徑本來就會變，現在先搬等於搬兩次。

## 方案 A：最小（只清死掉的與重複的，不搬夾、不改程式）

做四件：

1. `SESSION-LOG.md` 瘦身：done 的 3 條刪掉；內文已寫做完的逐條核、完了就刪；剩下的每條縮成「一句現況＋下一步＋連結」，長的來龍去脈搬到它連的那份 thinking 檔。目標 8 KB 內。
2. `WORKFLOWS.md`：8 列死入口收成一句「已封存：…」；`WORKFLOWS-parts/` 三個小檔（共 1.7 KB）併回來。併完還在 8 KB 內。
3. `wait-user/` 四份併回 `WAIT_USER.md`（真的開著的只有 2 條）；「待派工」三條搬進進度。
4. 小清：`dispatch/CLAIMS.md` 刪已收線的歷史列；`wf/inbox/` 頂層三封信看完歸 `done/`；HANDOFF 下次 compact 換新。

```
wf/                                   7 檔 9 夾（18 → 16）
  SESSION-LOG.md（8 KB 內）  WAIT_USER.md  HANDOFF.md
  WORKFLOWS.md  INDEX.md  STRUCTURE.md  _index.json
  INDEX/
  workflows/  knowledge/  public/  advices/
  inbox/  session_logs/  salvage/  tools/  (temp/)
```

頂層 18 → 16（少 `WORKFLOWS-parts/`、`wait-user/`）；`workflows/` 還是 26 個。

- **必讀**：開場 62.6 → 約 31 KB（知識庫入口 2.5＋AGENTS 10.8＋user.md 7.6＋進度 8 內＋WAIT_USER 約 2）。被派的 agent 不變。
- **代價**：搬 0；併 2 組（7 個小檔消失，交件要帶一次 `--rm`）；封存 0；程式與寫死路徑 0；活文件連結約 8 個檔。
- **風險**：進度縮條目時把還用得到的細節弄丟。做法是「搬到連結指的檔」不是刪，git 也留著。SESSION-LOG 是只有頂層能寫的檔，要頂層做或任務書明說放行。
- **工**：小，半天內。四件各自一個 commit，各自能退。

## 方案 B：中等（推薦）

A 之外再做四件：

5. **規矩卡**：寫一張 8 KB 內的卡，被派出去的 agent 只讀「知識庫入口＋這張卡＋任務書」。內容：六條鐵律各一句、使用者偏好的要點（繁中大白話、只有 main、不 push 不刪、交件走 `commit-request`、程式輸出英文、問題寄專區）、活樹旁九條硬規則的標題、回報怎麼寫、要更多去哪查。`AGENTS.md`、`user.md`、`aos-teams.md` 裡「通讀 wf/ 規矩（…等）」那句改成指這張卡。
6. **進度轉 json（已排的段 2b）**：一條一個鍵（哪個工作流、一句現況、下一步、連結、哪天起）。同一個 commit 改 `commit_queue.py` 的兩個 op 與測試、`compact_reload.sh`、AGENTS.md。`WAIT_USER.md` 剩的 2 條寄專區後整檔退場。
7. **死入口集中**：`workflows/` 那 8 個搬進 `workflows/archive/`；`salvage/` 搬進 `advices/archive/salvage/`。原位置不留指標頁。
8. **`INDEX.md`＋`INDEX/` 退場**：repo 佈局 AGENTS.md 第一段與 proto8/README 已經有，wf 頂層一覽 `_index.json` 已經有；`AGENTS.md` 的授權細節下放到 `user/01`，瘦到 8 KB 內。

```
wf/                                   5 檔 7 夾（18 → 12）
  _index.json
  WORKFLOWS.md          唯一的地圖
  STRUCTURE.md          整理時才讀；等段 9 退場
  progress.json         進度（檔名見題 3）
  HANDOFF.md
  workflows/  knowledge/  public/  advices/
  inbox/  session_logs/  tools/  (temp/)

wf/workflows/                         26 → 19，活的 18 個原地不動
  _index.json  TEMPLATE.handoff.md  TEMPLATE.workflow.md
  common/               多一張規矩卡
  dispatch/  refactor/  tidy/  feature-dev/
  team-model.md  team-model/  dev-env.md  dev-env/
  testing.md  investigation.md  planning.md  resources.md
  decisions.json  inbox.json
  archive/              hackathon、workshop、digest、experiments、investigations、ideas、spec、decide-page
```

- **必讀**：開場 62.6 → 約 26 KB（知識庫入口 2.5＋AGENTS 8 內＋user.md 7.6＋進度每條一句 8 內）。被派的 agent 29.5～90 → **約 10.7 KB**（知識庫入口 2.5＋規矩卡 8 內）；碰程式的再讀 `conventions/01`（7.1 KB），當線隊長的再讀 `aos-teams.md`（11.4 KB）。
- **代價**：
  - 搬：9 組（8 個死入口約 332 檔 0.97 MB、salvage 9 檔 0.08 MB），都是已封存的東西。
  - 併與退場：`WORKFLOWS-parts/`、`wait-user/`、`INDEX.md`＋`INDEX/`、`SESSION-LOG.md`、`WAIT_USER.md`。
  - 新檔 2 個：規矩卡、`progress.json`。
  - 寫死路徑：`commit_queue.py`（1 個常數、2 個 op、測試 20 處）、`compact_reload.sh`、`index_gen_desc.json` 的鍵；通用版 `live-lists.json` 對照一句。
  - 活文件連結：約 120 檔次，大半是第一行的麵包屑（SESSION-LOG 30、WAIT_USER 42、INDEX 32、死入口約 10、「讀規矩」那句 4 處）。
  - 紀錄類的舊連結：不改，在 thinking README 的改名表加一段。
  - 要你親手或點頭：第 7、8 件帶 `--rm`（agent 的權限跑不了），集中成一次。
- **風險**：
  - 規矩卡跟原文走樣、或 8 KB 裝不下：先試寫一版給你看；驗法是派一隻全新的 sonnet 只讀卡回答五題（能不能 push、怎麼交件、活樹能不能碰、問題寄哪、回報怎麼寫）。
  - 進度轉 json 那一刻有線正在用 `--op log_upsert`：挑沒線在跑時做，或 `commit_queue.py` 先兩種都認、過一輪再拿掉舊的。
  - 第 7 件跟 11-13 的 Q1「歷史不搬」、11-14 的「預設留指標頁」有出入，所以單獨列成題 4；你說不搬，B 的其他幾件照做，只是 `workflows/` 還是 26 個。
- **分步**（每步一個或幾個 commit，各自能退）：A 的 1→2→3→4 → 5 規矩卡 → 6 進度轉 json → 7 死入口集中 → 8 INDEX 退場。5 之後的順序可以換。
- **工**：中。兩三條 opus 線、一到兩天。規矩卡是濃縮你的規矩，不派 sonnet。

## 方案 C：一步到位（把 wf-into-aos 剩下的段一口氣做完）

B 之外：段 4（planning、investigation、feature-dev、testing、tidy、refactor 轉 json）、段 5（conventions、gotchas、dev-env、data-files、team-model、user 轉 json）、段 6（dispatch、CLAIMS 轉 json，aos-teams 進共用知識庫）、段 9（WORKFLOWS、STRUCTURE 退場，AGENTS.md 改成最後的輪廓）。

```
wf/                                   3 檔 7 夾（18 → 10）
  _index.json           手寫的路由，就是派發表
  progress.json  HANDOFF.md
  workflows/            一個工作流一個 json 節點；旁邊是凍結的 archive/、reports/
  knowledge/            user.json conventions.json gotchas.json dev-env.json
                        data-files.json team-model.json claims.json ＋ code map
  public/  advices/  inbox/  session_logs/  tools/  (temp/)
```

- **必讀**：開場約 18～20 KB（估：知識庫入口 2.5＋AGENTS 約 6＋user.json 的要點約 5＋進度一句話清單約 5）。被派的 agent 跟 B 一樣約 10.7 KB，或用 `json_get` 只拿任務要的那幾鍵，再少一些（估）。
- **代價**：約 45 份規矩 md 轉成約 20 個 json 節點；aos-teams 8 份改寫成不綁這個 repo 的版本進知識庫（換樹重抄才到活樹）；活文件連結約 350～400 檔次；`compact_reload.sh` 改讀 `user.json`。
- **要先過的三關**：
  - 11-13 你裁的 Q6 是「段 3 以後用到才換」，C 等於改成排時程一口氣換。
  - 段 3 那句「請使用者看一次 `decisions.json` 好不好讀」到現在沒答。答案是不好讀的話，C 整個不成立。
  - `public/`、`advices/` 今天剛照你的話精簡成 md 小檔，跟「規矩全 json」不一致，要不要也轉得另外問。
- **風險**：規矩轉寫時走樣（每份都要逐句對讀）；施工期間別的線還在照舊路徑讀規矩；大工，多條線、估一週上下。

## 想過、不建議的

- **開一個 `wf/state/` 夾把進度、交接、待使用者、inbox 收進去**：頂層再少 3 個，但改掉 11-13 定的目標形狀，寫死的路徑全要動。
- **把 `session_logs/`、各 `reports/` 搬去 `proto8/thinking`**：違反 Q1「歷史不搬」，連結上千條。
- **現在先把活的規矩檔搬整齊**（例如 `team-model`、`resources` 收進 `dispatch/`）：之後轉 json 又要搬一次。
