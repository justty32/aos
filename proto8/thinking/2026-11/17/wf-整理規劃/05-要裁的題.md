# 05 要你裁的題

每題的推薦寫在選項後面。題 2～8 是方案 B 裡各自獨立的小決定：選了 A 就只需要答題 1；選 B 或 C 才需要答後面的。

## 題 1：選哪個方案

- **A 最小**：只清進度、死掉的派發列、兩組小檔。半天內。開場必讀 62.6 → 約 31 KB，被派的 agent 不變。
- **B 中等**（推薦）：A＋規矩卡＋進度轉 json＋死入口集中＋INDEX 退場。一到兩天。開場約 26 KB，被派的 agent 約 10.7 KB。頂層 18 → 12。
- **C 一步到位**：B＋剩下的規矩全轉 json。估一週上下。要先改掉 11-13 的「用到才換」，也要你先看過 `decisions.json` 好不好讀。

推薦 B 的理由：最有感的兩個數字（開場、派工）B 就拿到大半；C 多做的是「規矩全變 json」，那一塊你 11-13 已經定了用到才換，而且 json 好不好讀你還沒看過。

## 題 2：三軸（信、進度、待使用者）要不要改形狀

現在開場要掃：信（樹內信箱＋`wf/inbox`）、`SESSION-LOG.md`、`WAIT_USER.md`（再點進 `wait-user/` 四份）。

- **a 三軸照舊，但每一軸只剩一個地方**（推薦）：信＝aos 信箱（樹外才看 `wf/inbox`）；進度＝一個檔；待使用者＝使用者專區。`WAIT_USER.md` 與 `wait-user/` 把剩的 2 條寄進專區後退場，「待派工」三條併進進度。後果：開場從掃五六個地方變三個；AGENTS.md 開場那句要改。
- b 完全照舊：不用改任何東西；WAIT_USER 繼續是一個只剩 2 條的檔加四份分類檔。
- c 三軸併成一個檔（或一個 `wf/state/` 夾）：頂層最乾淨，但改掉 11-13 定的形狀，`commit_queue.py`、`compact_reload.sh` 與上百個連結都要動。

## 題 3：進度轉 json（已排的段 2b）現在做不做

- **a 今天先在 md 裡瘦身，等今天這批線收了再轉 json**（推薦）：瘦身不用改程式、馬上有感（開場少 29 KB）；瘦過以後每條都是「一句現況＋下一步＋連結」，轉 json 是照抄。轉的那個 commit 要同時改 `commit_queue.py`，挑沒線在跑時做。
- b 今天就轉：今天有五條以上的線在跑，都可能用 `--op log_upsert` 寫進度，容易撞。
- c 只瘦身、不轉了：要改掉你 11-13 的裁定（Q5「進度表單條化成json」）。

附帶一小題，檔名：11-13 的規劃寫的是 `wf/session-log.json`。它跟每日日誌 `session_logs/` 名字幾乎一樣，而且內容不是 log 是「還沒做完的事」。推薦趁轉檔改叫 `wf/progress.json`（舊路徑反正會消失，改名不多花錢）；不想改就照原規劃。

## 題 4：已封存工作流的空入口要不要留

`workflows/` 26 個裡 8 個是死入口；頂層還有 `salvage/`。

- **a 集中搬進 `workflows/archive/`（salvage 進 `advices/archive/`），原位置不留指標頁**（推薦）：`workflows/` 26 → 19，打開就只看到活的。後果：這 9 個在 11-13 的 Q1「歷史不搬」與 11-14「預設留指標頁」上開例外；交件帶 `--rm`，要你親手跑一次或點頭；舊紀錄裡約 250 檔次提到這些舊路徑，不改，在 thinking README 的改名表加一段。
- b 夾留著、只從派發表拿掉那 8 列：零成本、不用 `--rm`；`workflows/` 還是 26 個，`index_view wf/workflows` 還是會列出它們（說明寫「已封存」）。
- c 維持現狀。

同一題順便問：停用的看板 `tools/progress_board/`（0.59 MB）與離線待裁頁 `tools/decide_page/` 要不要一起收進 `tools/archive/`。推薦收（11-13 你裁的是「凍結」，11-14 兩個都停用了）；不收也不礙事。

## 題 5：`wf/` 跟 `proto8/thinking`、`proto8/knowledge` 的分工線畫在哪

推薦的線（跟 proto8 那份方案對得上：thinking 留在 proto8、紀錄都進 thinking）：

| 放哪 | 收什麼 |
|---|---|
| `wf/` | 在這個 repo 做事的規矩、還沒完的事（進度、交接、樹外的信）、做事用的腳本、各隊共用的做法與坑（public）、對 aos 的意見（advices） |
| `proto8/thinking/` | 所有「哪天討論、決定、規劃、調查、實測、盤點了什麼」的紀錄 |
| `proto8/knowledge/` | 出廠給樹裡 agent 讀的：aos 怎麼用、通用版 wf。不綁這個 repo |
| `proto8/docs/` | 條文（概念、規範、慣例） |

照這條線有兩個小決定：

- **(i) 每日日誌 `wf/session_logs/`**：11-14 起就沒寫了，這幾天「哪天做了什麼」實際記在 thinking 的日索引。**a 停寫、整夾凍結，AGENTS.md 拿掉「日誌」那一行**（推薦，兩處記同一件事只會有一處是真的）；b 補寫 11-14～11-17 並繼續寫。
- **(ii) `tidy/reports/`、`refactor/reports/` 以後的新報告**：**a 寫進當天的 thinking，兩個 reports 夾凍結**（推薦，今天的盤點在 reports、兩份規劃在 thinking，已經分岔了）；b 照舊寫在工作流底下。

舊的都不搬（Q1）。

## 題 6：派工時「通讀 wf 規矩」要不要改成讀一份濃縮的規矩卡

這句是你的原話（10-20「派agent時要讓他們通讀wf/規矩，除了幹雜活的」、11-06、11-13 都重申），所以一定要你裁。

- **a 改成讀一張 8 KB 內的規矩卡**（推薦）：被派的 agent 讀「知識庫入口＋卡＋任務書」約 10.7 KB，現在照字面 29.5 KB、老實讀 58～90 KB。卡上寫明「碰程式再讀慣例、當隊長再讀隊形短卡」。後果：卡跟原文要同步，原文改了卡要跟著改（卡上每條附出處，改原文的人順手改卡）。
- b 照舊通讀，但把清單寫死（拿掉「等」字）：量不變，至少每隻讀的一樣。
- c 不寫卡，改成任務書範本自帶規矩：每張任務書都長一截，而且各線各自抄會走樣。

## 題 7：坑與經驗要不要只留一處

現在六處：`common/gotchas`、`tidy/gotchas`、`dispatch/lessons`、`public/pitfalls*`、`public/` 其餘、`advices/`。

- **a 等 public 那條線收完，再把 `common/gotchas`（14 KB）、`dispatch/lessons`（15 KB）、`tidy/gotchas`（4 KB）併進 public，名字統一叫一個詞**（推薦）：查坑只去一個地方。後果：三組檔退場、估約 30 個活文件的連結要改；`advices/` 不併（它收的是「aos 該改什麼」，不是坑）。
- b 照舊各放各的：工作流專屬的坑留在工作流旁邊，查的時候要知道去哪一個。
- c 現在就併：會撞正在精簡 public 的那條線。

## 題 8：`INDEX.md` 與 `STRUCTURE.md` 什麼時候退場

11-13 已定兩個最後都退場（段 9）。問的是時間。

- **a `INDEX.md`＋`INDEX/` 現在退，`STRUCTURE.md` 等段 9**（推薦）：INDEX 的內容三處都有了，退掉只是改約 32 個檔的麵包屑。STRUCTURE 是現行的拆檔與封存規則出處，proto8 的活文件有 32 個連到它，等通用版接手再退。
- b 兩個都等段 9：現在不用動，頂層多兩個東西。
- c 兩個現在都退：STRUCTURE 的內容得先搬進 `tidy/` 或通用版，比較大。

## 沒查到、沒把握的

- **活樹裡現役定義的提示**（`~/aos-home/agents/` 的 `opus-kernel`、`fable-kernel` 等）有沒有寫死 wf 路徑或「通讀 wf 規矩」那句：沒查到。我對 WSL 多個路徑的查詢被權限擋了，只讀了知識庫入口一檔；改「讀規矩」那句之前要有人看一眼。
- **`wf/temp/`**：這台 Windows 工作樹沒有這個夾（不進 git），WSL 那邊多大、幾條線的東西沒量。
- **沒跑 `wf/tools/` 的檢查**（index_check、check_anchors）：沿用今天盤點報告的數字。
- **SESSION-LOG 54 條**我只看了每條開頭，沒逐條判斷哪些已經做完；「瘦到 8 KB 內」是目標，沒試做。
- **規矩卡 8 KB 裝不裝得下**：沒試寫。裝不下的話可能要兩張（一般的、活樹旁的）。
- **B、C 的必讀量**是用 8 KB 目標估的，不是量的。token 數全都沒量，只量位元組。
- **連結數**是「有幾個檔提到」，不是逐條解析；同名字串（例如別處也有 `INDEX.md`）會多算一些。
- **`wf/inbox/` 頂層那三封信**是不是真的沒處理，沒讀內容。
- **日誌 11-14 起沒寫**是不是有人決定停的：沒找到使用者說停的話，也可能只是沒人寫。
- **`wf/public/` 最後的樣子**看不到（別的線正在改），題 7 等它收完再定細節。
- **proto8 那份方案**建議把 `proto8/feedback` 搬到 `wf/advices/feedback/`：那會讓 advices 多一個子夾，跟你說的「advices 只剩兩三個小檔」怎麼算，兩份方案都沒替你決定。
- **段 0**（compact 後 hook 在 eca 身裡跑不跑）一直沒有結果；方案 B 的第 6 件改 `compact_reload.sh` 前最好先補驗。
