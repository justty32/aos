## 必修（不修照做會失敗或驗收不可能過）

1. **隊 kernel 的每 writer 額度不成立**（[03](02-設計/03-kernel與git.md)「並發與 80%」、T6）：kernel 的寄件人＝相對 kernel stack 的 `AOS_WS` 路徑（04-已知限制 第 20 條），所有 writer 都在同一個 `ws/` 跑＝同一個寄件人；照寫「各 writer ws 各列一格」會是同一格，兩個 key 算出同一人還會 `CfgBad`。要嘛每隻 writer 各自一個 ws（`ws/w-places-1/`…，kb 放外面用 `_memory.json` 指），要嘛改成「整隊一格」。
2. **`max_calls 200／日` 不夠跑第一輪**（同段）：40 封×跑兩次＝80 封，每封至少 3 次問腦（read→write→回信），約 240 次，第二趟中途就 `BudgetMissing`。照 1 改完後要重算，或第一輪先不設 `max_calls`、只記帳。
3. **places 是 40 檔不是 41**（[04](02-設計/04-第一輪與施工.md)「第一輪」、驗收①、T2「41 筆」、T3「41/41」）：41 含 `INDEX.md`；「單檔最大 2.9 KB 要拆」那檔也是 INDEX，內容檔最大 1.3 KB——第一輪根本不必拆，`kb_split` 可整個延到第二輪（C-56）。
4. **路徑寫錯、gpt 照抄會撞牆**（T4 Done when、[02](02-設計/02-agent與工具.md) writer 列、[01](02-設計/01-庫.md) 節點格式）：`read`／`write` 限 `$AOS_WS` 內、路徑相對 ws，信裡寫 `ws/corpus/...`、`ws/kb-ak/...` 會指到 `ws/ws/...`；應是 `corpus/arknights/lore/places/X.md`、`kb-ak/ak/places/Y.md`（若照必修 1 分 ws，還要再改）。`sources:` 寫 `lore/...` 但沒說相對哪個根，`kb_lint` 驗「路徑存在」無從驗——要寫死「相對 `corpus/arknights/`」。
5. **`[[…]]` 目標存在檢查會讓第一輪全滅**（[01](02-設計/01-庫.md) 節點格式、T3）：places 的 relations 一定指向 characters／factions，那兩類第二輪才有節點，`kb_lint` 退 1 → 一個 commit 都出不來。改成「目標 slug 在 `names.tsv` 裡」就算過，或第一輪 system.txt 禁寫 relations。
6. **一個壞節點卡死後面所有批**（T5、[03](02-設計/03-kernel與git.md)「git」）：`kb_lint` 掃整個 `kb-ak/ak/`，壞節點留在 working tree，之後每批 lint 都退 1、永不 commit；而 batch.py 用「檔案存在」判斷做過沒，壞節點也不會再派。改成：lint 只驗本批檔；「做過」以 `git ls-files` 為準（沒 commit＝沒做，壞的移到 `work/quarantine/` 並記 `manual.md`）。這同時解了當機復原（寫到一半的檔不算數）。
7. **T1 的 `git mv corpus ws/corpus` 做不到**：corpus 還沒追蹤、又在 `.gitignore`，且 `corpus/arknights` 自帶 `.git`（會被當 embedded repo）。改 `mv`，`.gitignore` 寫 `ws/corpus/`。

## 設計問題

1. **確定性驗收③「重跑 diff 率 ≥ 80%」定義不了也達不到**（02「確定性怎麼量」1、驗收③）：LLM 改寫一段話，兩次逐字相同（去空白）幾乎不會發生，又沒寫溫度／seed 怎麼固定。建議第一輪只「記數」不「卡關」，並同時記結構面的比（`sources:` 行集合相同率、facts 條數差）；溫度 0 用包的 `fixed` 寫死。
2. **C-52：`tool_stats.py` 直接讀 `ws/.stack/procs/*/history`**（02 工具表、三階段表）：上層腳本鑽進 agent 的 stack 偷看。乾淨做法是工具層自己記——包一支 `defs/bash_logged`（跑 bash＋把指令 append 到自己的 log），統計只讀這個 log；stopped 原因走 `aos-agent ctl ls` 公開介面。
3. **中文本文撞 2 KB 慣例**（01 節點格式、裁題 1）：2048 bytes ≈ 680 漢字；`knowledge/README` 的 2 KB 是為英文訂的。places 沒事，characters／operators 會大量拆。裁題 1 的代價應寫明這點，或讓本庫改用「字數」上限。
4. **規模到 5000 節點沒想**：`operators/` 400、`characters/` 上千個子節同一層，`memory read`／目錄一次印全部→token 爆；`find` 只列 20 筆。要在第三輪前定：按首字母分桶，或目錄只給 index 節點。
5. **使用者的「成千上萬 agent 可 sleep」「工具可以是開 agent／轉交 kernel」沒有一輪去驗**（04 第二～四輪表）：設計只到 3 隻並行、嵌套兩層、0 個「工具＝agent」。KISS 選擇可以，但要明寫是代定並排進某一輪（例：第三輪掛 400 個 operator 定義各睡、按需喚醒；reviewer 的「查證」做成開 helper 的工具）。
6. **token 成本沒有總估**：沒引 [01-盤點-語料](01-盤點-語料.md) 的 token 粗估、沒算每封固定開銷（盤點實測 LiteLLM 每封多 1636 prompt tokens、think 每次自動帶 memory 根）。至少給「全庫轉一遍約多少 token／錢」與每日上限。
7. **人工介入只有「寫進 `manual.md`」**：沒說誰看、多久看、處理完怎麼回流（手改後是否再 lint、算不算人工次數）。寫一句流程即可。
8. **併發**：batch.py 若被 cron 與人同時起會重派、搶 commit——加一把 `flock`。

## 建議

1. 工具表與 T 步不一致：`kb_dedupe`、`kb_split` 在表上卻沒施工步驟；`kb_lint --diff` 把「比較」塞進 lint，拆成獨立小腳本較乾淨。
2. T5 要能分派給多隻 writer（驗收說第 3 批掛第 2 隻）：加 `--agents a,b` 輪流派。
3. `names.tsv` 撞名 `-2` 依順序而定——寫死「按檔名排序後生成」；拼音由繁體來，順手註明。
4. reviewer「抽查 10%」用 slug 雜湊取樣，重跑抽到同一批（確定性）。
5. T6 Done when「最多 4 在飛」要能看到：用 fake 慢劇本（每封睡幾秒）測，不要用真 gpt。
6. `defs/` 同時放工具資料夾與 batch.py／watch.sh 這類指令，`defs_index.py` 靠「每夾 README 第一行」會漏掉單檔腳本；指令另放 `bin/`。
7. writer 第一輪其實用不到 `memory`（kb 還是空的），可先不登記，少一次自動帶根的 token。
