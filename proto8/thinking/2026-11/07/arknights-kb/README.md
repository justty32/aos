## 已定（使用者說的）

- 目標：把 `~/repo/narratives/arknights` 歸納進 aos 的資料庫（知識庫）體系；慢慢做，邊做邊找不足、再規劃與優化。
- 系統設計與架構規劃由 Claude 系做（fable 從旁規劃、opus 審查）；gpt 系照圖施工、雜活，aos 裡跑的 agent 的腦盡量用 gpt 系。
- 優化目標＝確定性：shell 工具先開放 → 再謹慎 → 最後全部專屬工具；git 是重要概念；agent 專精窄領域，越窄越能工具化、模型越便宜、token 越省。
- 規模：agent 可以成千上萬（可 sleep）；llm kernel 可嵌套轉交（隊伍 kernel → … → 實打 API 的 kernel）；工具也可以是開 agent 或轉交給專精的 kernel。
- 效能：開監控，80% 以內都可以。
- 留紀錄與得失；放手擴充工具與 agent 定義，期待系統自我演化出大量定義（原始碼），每批附讓使用者好懂的說明文件。

## 使用者裁定（11-07 午，對隊長六題）

原話逐字：「1.節點名確實建議英文，剩下隨意。內部內容建議按照語料原文，這樣能最大程度保持原意。這是儲存方面，至於使用者想看的時候，可以透過其他界面，比如做一份附屬知識庫，其中是翻譯過的白話，或是直接準備一個agent幫忙解答問題。類似RAG。2.不搬。3.可以。4.好。5.不限制。6.不用，按照現在的路走，會很自然的慢慢膨脹到上千上萬。」

決定：
1. 節點名英文；條目內文**照語料原文**存（保原意），不翻譯、不改寫；給人看的走另一層——附屬知識庫（翻成白話）或一個問答 agent（類似 RAG）。標題等其餘隨意。
2. `lore/evidence` 不搬進知識樹。
3. 格式檢查過就 commit，事後抽查。
4. 重跑一致率只記錄、不當門檻。
5. gpt 呼叫不設每日上限。
6. 不特地安排「上千 agent」測試輪；照現在的路走，自然膨脹。
