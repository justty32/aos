結論：「蒸餾」＝把 LLM 每次都在重判的知識，一次抽成兩種資料檔（關係事實表、條件→結論規則），第三輪只做影子跑（規則偷偷答、跟 sol 參考比同意率、不改路由），第四輪才按數字讓規則接手 T2 的一部分，第五輪讓規則庫自己長、自己退休；最先該放的是 E1（lore 抽事實表）＋E3（題紀錄統計語法模式），兩者零風險、低成本、其餘實驗都靠它們。

## 0. 一頁結論

| 問題 | 答案 |
|---|---|
| 蒸餾在主要功能（linker 裁連結）上指什麼 | 把「這個名字是不是那個人」所需的知識，從 lore 自然語言與已裁題目，抽成腳本查得到的資料檔；LLM 從「每題判」改成「一次抽、偶爾審」 |
| 規則從哪來 | 三條路並行：A 從已裁題目歸納（統計）、B 從 lore 抽關係事實表（LLM 抽一次、腳本驗）、C LLM 寫規則、腳本回歸驗 |
| 規則長什麼樣 | 純資料檔（JSON Lines），每條帶：條件、結論、信心、出處、來源題號、狀態（候選／試用／生效／退休） |
| 怎麼證明可信 | 兩把尺：對 sol 參考答案的同意率、對已接受快照的回歸；外加「誤剪率」（剪枝把正解剪掉）必須 0 |
| 第三輪做什麼 | 六個影子實驗 E1～E6，排 C2～C5，全部只記錄、不改路由 |
| 第四輪做什麼 | 規則池按數字接手「剪枝」（少備選）→ 再接手部分 T2 裁決；參考閘照抽規則答的題 |
| 第五輪做什麼 | 規則庫自長自退：每批題紀錄自動餵歸納管線、人只審抽樣；通用規則進 kb-kit，Arknights 事實表留 kb |
| 最重要的推薦 | **先做 E1＋E3（C2）**。E1 的事實表是 E2、E6 的燃料；E3 零模型、直接回答「通用語法規則值不值得做」 |

兩件事要先說白：

1. **蒸餾不是把 LLM 換成規則，是把 LLM 的錢從「每題」挪到「每詞條一次」。** 指標公式只算單任務，所以蒸餾後生產指標會降，但抽取成本要另外記一本帳（見 §4 Q1）。
2. **第三輪一條規則都不上生產。** 影子跑的意思是：規則在旁邊答，答案寫進紀錄，生產路由照舊。隊長看了數字才開處方。

## 1. 蒸餾具體指什麼

### 1.1 現在 LLM 在判什麼（真要 LLM 的 252 題拆開看）

| 題型 | 例 | 要什麼知識才能不問 LLM | 可不可蒸餾 |
|---|---|---|---|
| 單字名指向（最多） | 百灶「望」＝人物望、「歲」＝派系歲 | 候選的關係事實（望是歲的碎片）＋文中共現（同段有「歲」「陵」） | 可，靠事實表＋共現規則 |
| 真名／別名 | 「炎武」＝魏彥吾 | 別名表（已有 65 條） | 已蒸餾一半，只缺補齊 |
| 語法位置 | 「X 言」「入 X 陵」「X 道」 | 通用語法模式 | 可，靠統計 |
| 派系 vs 人物同名 | 候選同時是幹員與派系 | 候選所屬、本地點的勢力 | 可，靠事實表剪枝 |
| 詞內誤切 | 「鎮歲源石」的「歲」 | 詞內表（已有） | 已蒸餾 |
| 真歧義 | 文本故意雙關 | 沒有 | 不可，留給 LLM |

所以蒸餾的對象很具體：**前四列**。最後一列永遠留 LLM，這是「主要判斷責任在 LLM」的合理殘留，不用硬壓。

### 1.2 規則的三條來源

| 路 | 來源 | 誰做 | 產出 | 適合哪類題 |
|---|---|---|---|---|
| A 歸納 | 已接受快照（76 條，C2～C4 再加）＋題目紀錄（485＋C1） | 腳本統計，零模型 | 語法模式表、共現表 | 語法位置、單字名共現 |
| B 事實表 | lore 人物／派系詞條的「故事定位」「關鍵事實」 | LLM 抽一次（terra 或 12B），腳本對別名表驗 | 關係事實表 | 真名、所屬、親屬、敵對、碎片／本體 |
| C LLM 寫規則 | T2 題紀錄（含 sol 參考、judge） | sol 寫、腳本回歸驗 | 條件→結論規則草稿 | 任何；但只收通過回歸的 |

三條路不互斥，B 的事實表是 A、C 的輸入之一（規則條件可引用事實表）。

### 1.3 規則長什麼樣

兩個資料檔，都放試驗場 `~/code/playground-ak/runs/3/distill/`，都是 JSON Lines，一行一條。

**關係事實表 `facts.jsonl`**

| 欄 | 例 | 說明 |
|---|---|---|
| subj | `魏彥吾` | lore 詞條 id |
| rel | `alias` / `faction` / `kin` / `enemy` / `fragment_of` / `home` / `era` | 封閉集合，初版就這七種 |
| obj | `炎武` | 詞條 id 或字串 |
| conf | `0.9` | 抽取模型自報＋腳本驗後調整 |
| src | `lore/魏彥吾.md#關鍵事實` | 出處段落 |
| by | `llm:terra` / `table:alias` | 誰產的 |
| status | `candidate` / `verified` | 腳本對照別名表或人工審過才 verified |

**規則表 `rules.jsonl`**

| 欄 | 例 | 說明 |
|---|---|---|
| id | `R-ctx-001` | |
| kind | `prune` / `decide` | 剪枝（少備選）還是裁決（直接答） |
| when | `{"left":"入","right":"陵","cand_type":"person"}` | 條件：提及左右字、候選型別、事實表查詢（`fact(cand, fragment_of, X) and X in para`） |
| then | `{"link":true,"to":"cand"}` 或 `{"drop_cand_type":"faction"}` | 結論 |
| conf | `0.95` | ＝歷史純度 |
| support | `[Q-C1-百灶-03, Q-B4-婆山-11]` | 支持題號，至少 3 |
| counter | `[]` | 反例題號，必須空才能 verified |
| by | `stat` / `llm:sol` / `human` | 誰寫的 |
| status | `candidate` → `shadow` → `live` → `retired` | 第三輪最高到 shadow |

條件語言故意窄：只能查「提及左右 N 字、候選型別、候選數、事實表、同段／同地點是否出現某名」。不能寫自由程式。這樣 gpt 寫的執行器一百行就夠，規則也看得懂。

### 1.4 怎麼證明規則可信

| 尺 | 怎麼量 | 門檻（第三輪建議，隊長可改） |
|---|---|---|
| 參考同意率 | 規則答案 vs sol 參考答案（參考閘已有） | decide 規則 ≥95%，且 ≥20 題 |
| 快照回歸 | 對所有已接受快照重放，已接受的連結不能消失 | 0 條消失 |
| 誤剪率 | prune 規則剪掉的候選裡，有沒有最後被接受的那個 | 0 |
| 覆蓋 | 規則能答掉幾道原本的 T2／T3 題 | 只記錄，不設門檻 |
| 單任務指標 | (token in＋out)÷(原文 bytes×2)，影子跑時另算「如果規則生效」的假想值 | 只記錄 |

**三個狀態才能升一級**：candidate（剛產出）→ shadow（跑過回歸 0 消失、誤剪 0）→ live（隊長看影子同意率後開處方）。第三輪卡在 shadow。

## 2. 第三輪小實驗（E1～E6）

## 3. 第四、五輪推進（給第四輪的材料）

### 3.1 大方向

| 輪 | 規則角色 | LLM 角色 | 一句話 |
|---|---|---|---|
| 三 | 影子 | 全判 | 證明規則不會壞事 |
| 四 | prune 上 live；decide 上 live 限「有事實表支撐」的子集 | 判剩下的＋審規則答的抽樣 | 規則少備選，LLM 判得更準更便宜 |
| 五 | 規則庫自長自退 | 抽事實（本機 12B）、寫規則草稿、審抽樣 | LLM 從判官變成規則的作者與審稿人 |

### 3.2 第四輪階段

| 階段 | 做什麼 | 進下一階段的條件 |
|---|---|---|
| 4a prune 上線 | 誤剪 0 的 prune 規則進生產，候選變少，T2 題可能降為 T1 | 兩批 prune 誤剪仍 0 |
| 4b decide 限定上線 | 只讓「條件引用 verified 事實」的 decide 規則答題，規則答的題當 T0 處理，但參考閘對它抽 30%（同 T1） | 參考同意率 ≥95% 持續兩批 |
| 4c 事實表擴面 | 對 C2～C4 新 12 地的候選詞條補抽（E1 流程） | alias 召回仍 ≥80% |
| 4d 退休機制 | 任一 live 規則累計 counter ≥2 → 自動降回 shadow；三批沒命中 → retired | 跑一次即可 |

**什麼時候讓規則接手生產**：只看兩個數：誤剪 0、同意率 ≥95%（≥20 題）。達到就接，達不到就不接。不看「省多少」——省多少是結果，不是條件。

### 3.3 第五輪：規則庫自己長、自己退

| 環節 | 自動 | 人 |
|---|---|---|
| 新地點跑完 | 題紀錄自動餵 E3 統計＋E4（改用 terra，不用 sol）出草稿 | 無 |
| 新候選詞條 | 自動餵 E1 流程（本機 12B，E1b 已驗可用才行） | 無 |
| candidate→shadow | 腳本回歸自動升 | 無 |
| shadow→live | 影子兩批達標 | 隊長抽看 5 條後開處方 |
| live→retired | counter 或零命中 | 無，但退休清單進批報告 |
| 事實表更新 | lore 詞條改動 → 該詞條事實重抽、舊事實標 stale、引用它的 live 規則降 shadow | 無 |

### 3.4 和審視者 R0→R2、kb-kit 的關係

簡報沒展開審視者 R0→R2 的定義，這裡只定介面，第四輪再對：

| 對象 | 規則庫要給它什麼 | 它給規則庫什麼 |
|---|---|---|
| 審視者 R0（最輕） | 規則答的題清單＋規則 id | 抽樣同意／不同意 |
| 審視者 R1 | 不同意的題＋規則 support／counter | 判「規則錯」還是「參考錯」→ 寫進 counter 或忽略 |
| 審視者 R2（最重） | 整批退休／升級清單 | 開處方 |

| kb-kit 放什麼 | 留在 arknights-kb |
|---|---|
| rules.jsonl／facts.jsonl 的格式定義 | 實際的 facts.jsonl、rules.jsonl 內容 |
| 條件語言執行器（查左右字、候選型別、事實表） | 七種 rel 以外的 Arknights 特有關係（若有） |
| E1／E3／E4 的腳本與提示模板 | 提示裡的 Arknights 詞條段落名（故事定位、關鍵事實） |
| 回歸、誤剪、同意率的計算腳本 | 門檻數字（每個 kb 自己定） |
| 通用語法模式（E3 跨 kb 純度仍 ≥95% 的那幾條） | 單一 kb 才成立的模式 |

原則：**格式與驗證工具通用，知識內容不通用**。「某角色仇恨另一角色」這種關係的 rel 名（enemy）可通用，但哪個角色恨哪個是 kb 的事。

## 4. 方向題（與原則衝突或原則推不出）

| # | 題 | 衝突哪條／為何推不出 | 選項與後果 |
|---|---|---|---|
| Q1 | 抽事實表的 token 算不算指標 | 指標公式只算單任務；E1 一次 22 萬 token 分攤到哪個地點？ | a) 不算，另記「建庫成本」一本帳——生產指標好看，但隱藏成本；b) 按詞條被引用次數分攤——公平但算法複雜；**建議 a，但批報告必列建庫成本** |
