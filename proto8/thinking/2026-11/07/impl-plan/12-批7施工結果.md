## 判準逐條結果

1. **cmake build 過：通過。** 在副本 `proto8/impls` 執行 `cmake --build build -j8`，退出碼 0，全家建到 100%。
2. **priority 與 seen_at：通過，真跑。** `test_nesting_live.py` 用真 daemon、真 kernel 與真 aos-llm 寄信，自帶端點讀 stdin 後暫停，讓測試實讀 `request.json`／`proc.json`。驗了 ISO 時區 deadline 比 timeout 早、timeout 比信 deadline 早、只有信 deadline、只有 timeout、兩者皆無；deadline 與首次 mounted_at 的計算值精確相等，輸出為浮點 epoch 秒。另驗沒級數預設 normal、字串／數字級數原值保留，proc 有浮點 seen_at。預備夾補驗 queue 毫秒轉秒、掛後刪 queue 那格、aging 不向下傳，以及兩種重掛入口沿用首次 request 位元組與 seen_at。既有 ledger 預備夾也驗 proc 缺 seen_at 時記 null、不報錯。
3. **child 入帳、回信拿掉：通過，真跑。** fake 成功印含巢狀額外資料的 child；recv 收到的 body 沒有 child，其他鍵保留。ledger 的 child 完全相同、seen_at 等於 proc、code 為 null、switched 為 false，且全部欄位順序與圖紙相同。無 child 的真跑也驗 child 為 null。
4. **透明錯誤與原失敗：通過，真跑。** fake 退 2、stdout 印 `{"error":{"code":"X","msg":"y","details":{"kept":true}}}`，寄信方收到同一個物件，ledger code 為 X。fake 退 1 印普通文字時，仍回 EndpointFailed，原因只帶第一行。預備夾另外驗頂層多鍵、錯型別、陣列、多行 JSON、空白行、尾巴雜訊等都不透明轉交；error 內額外鍵與跳脫換行保留；退 0 的 error 為 ReplyBad；143／137 的真正逾時先走原逾時分支。
5. **ask／recv full：通過，真二進位＋回信預備夾。** `test_full.py` 的 ask 真的寄到 new/，測試拿剛寄的信名回覆；recv 以指定信名收預備回信。兩者成功 full 都只有一行 JSON，letter 對到原請求信名；錯誤 full 只有一行完整 error body，stderr 精確維持原行、退出碼 1。不帶 full 時仍只印 message，錯誤 stdout 為空、stderr／退出碼相同。另驗 full 的本地輸入錯誤不憑空印 body，recv 沒回信維持 10 且無輸出，help 有新說明。真 daemon 測試也覆蓋 recv full 的成功與失敗。
6. **五組既有測試全綠：通過。** 同一輪依序跑指定五組，含新增測試，共 63 個方法，無失敗、無跳過。

## 小選擇與施工時看到的差異

- 首次掛上取同一個牆鐘時間樣本，寫入 proc.mounted_at 並計算 priority.deadline，避免兩次取時造成兩邊不相等。重掛的 mounted_at 照原制更新，但 request 與 seen_at 不重寫，所以上層期限不延長。
- 單行 JSON 可沒有行尾、帶一個 LF 或 CRLF；真正的換行／第二行不合格。JSON 字串中的跳脫換行不算第二行。原樣回指 JSON 內容不增刪，序列化仍走原本的 aos::dumps。
- 內部 reply.json 保留 endpoint 成品的 child，寄出的 body 才拿掉；這樣收尾若重進仍有 child 可記帳，不另加欄位或檔案。
- 原碼的成功分支其實透過 read_reply 接受 error，與任務書「退 0 的 error＝ReplyBad」不符；本批照較高優先序的任務書擋下，並加回歸測試。
- 143 非逾時且 stdout 是合格 error 時也依 K3 透明轉交；非合格 error 才照原制重掛。
- judge 原測試斷言沒有 letter，已隨 K4 改為核對帳上的 id；沒有為舊輸出留相容層。呼叫者失敗時不會誤解析新增的 stdout。
- 初次測試有兩條把 JSON 空白寫死的斷言，以及上述 judge 舊契約斷言失敗；已修成驗內容與新契約，最後整輪全綠。
