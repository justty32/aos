## 0. 題目、規矩與產出要求

**題目**（請求 C，使用者 11-07 上午原話見 §1c）：「shell 先開放 → 再謹慎 → 最後全專屬工具」這條演進路，aos 要怎麼支援與管理：

1. 每個 agent／工具目前處在哪一階段，怎麼表示（宣告在定義裡？）；
2. 從 shell 到專屬工具的轉換怎麼發生（誰發現重複的 shell 用法、怎麼抽成工具、怎麼收回 shell 權限）；
3. 確定性怎麼量（今天的實測：溫度 0 重跑仍 0% 一致；第二輪把步驟固定成腳本後「規則重跑一致」——確定性要分層量：腳本步、LLM 步、整體）；
4. 跟沙箱與權限（aos-sandbox、bwrap、s6、`--limits`）的接法；
5. 降級階梯（sol→terra→luna→本機）在其中的角色：降級失敗的環節就是該工具化的候選。

**分界**（同批四題，只做自己那題，碰到別題寫一句「交給 X」）：
- **evolve-design**：自我改進機制本身（反向傳播怎麼做成系統的一部分）、metainfo 的格式（任意 JSON 值、公式、自我宣稱 vs 他者觀測）、成本 JSON、專精 agent 怎麼長出來。**本題可以引用 metainfo，但不定它的格式**；本題要的「階段」「確定性數字」如果要放進 metainfo，只說放哪個 key、交 evolve-design 定總格式。
- **kernel-nest**：llm kernel 嵌套、排程、跨層記帳（ledger）。
- **kb-scale**：知識庫全庫規模、「給人看」的那層。
- **tool-evolve（本題）**：權限與工具化的演進階段＋確定性量測。

**規矩（必守）**：
- 大方向是使用者的（鐵律 5），你在他已定的路上設計細節；照 §3 的原則自己定細節、寫成結論。
- 要帶給使用者的只有兩種：**新想法跟既有原則的衝突**（哪條、衝突在哪、各自後果），以及**原則推不出答案的方向題**（擺選項與後果、標推薦）。
- **KISS 是最高原則也是最後原則**（C-56），**每層只管自己**（C-52）。
- proto8 **不做舊版相容、不寫遷移**（使用者 11-05「一律當成沒有舊版」）。
- 少用 `sh -c` 拼字串（使用者 10-15「拜託，少用sh」）。
- 白話總結要真的白話：使用者讀不動術語密集、多線交叉引用的文字；完整句子、一段一個重點、術語第一次出現用日常比喻帶過、編號引用點到為止。
- 只讀本簡報；不改任何檔、不 commit。

**請產出**（一份 markdown，第一行一句話標題）：
1. 白話總結。
2. 設計：概念、機制、資料格式（給 JSON 範例）、各層誰負責（aos-exec／aos-sandbox／daemon／aos-tools／agent 範本／lib 工具／試驗場腳本／隊長）。
3. 與既有 CONCEPTS／NORMS 的衝突。
4. 方向題（選項、後果、推薦）。
5. 落地順序：可交給 gpt 照圖施工的小步（每步一句完成條件）。gpt 不做設計決策，圖紙要夠細。

### 1a. user-advice/20261106.md（使用者指定全文給 fable）

寫於2026/11/06的深夜

我認爲這是the new age of programming。
lisp仍是最終最好的抽象，那爲啥大家都不用？我不知道，但是對我而言，就是debug不方便，並且沒辦法控制底層，因爲我是從C++起家，深入其template meta programming，浸淫已久。我知道lisp的meta programming更好更方便，但是...好了，總之閒聊到此爲止。
OK，那我覺得我這套體系能解決這個問題。
我們把filesystem作爲lua來使用，一個簡單的手段就是準備一個程式aos-exec，這個程式可以把資料夾當做檔案來執行，只需要資料夾內有一個_entry檔案即可。第一個好處就是能夠白嫖linux的檔案權限機制，其次就是能夠跨程式語言實作功能。不過最重要的，是agent原生就有操控資料夾的能力。
如果想要用lisp實作agent，並讓agent自己修改自己，那就是在lisp執行中跟agent說，請做這個做那個，你得把lisp相關東西抽象給agent，並且還要要求agent寫lisp程式，這是有風險也比較麻煩的。不過話說到這裏，好像這也是可行的，齁齁，之後有空來做做看。
不過我要說的是，相比跟agent說：這個list就是你，請你修改自己。不如直接把一個資料夾跟幾個python程式和json檔案交給agent，跟他說這就是你，請你新增一個資料夾，裏面弄一個新工具，然後給你自己做擴充。這其實agent更好懂，並且也能輕鬆完成。甚至還可以利用到python的各種wheel。不過說到這裏，好像lisp也能做到，之後來試試看吧。
OK，總之，我這邊要強調的就是檔案系統之於LLM的原生理解性與原生可操作性。
而在這個基礎上，我們實作了aos loop/fsm agent。秉承unix哲學與傳統，沿襲plan9理想，各種東西都盡量以檔案表示，其本體程式盡量簡短。

然後是忘記誰說的(應該是andrew karpathy)，agent就是一個函數。我覺得他觸摸到了本質，而我要替他進一步闡述。agent作爲函數，其pseudo code應如下：
func agent(llm, prompts, tools):
    while 1:
        if has_tool_call:
            do_tool & break
        elif has_prompt:
            add_prompt & break
大約如此，其中的llm就是大語言模型的api呼叫，而prompts則是一個[]string，可以在外部或內部增加或減少東西，至於tools，那就是一些丟進去的外部函數。假如沒有tools，那這個agent函數只能針對[]string做增減，但有了tools，那根據丟給他的東西，這個函數就可以做到任何事。

然後是比較跳躍性的聯想。一個cpu所做的事情可以想成以下pseudo code:
func cpu(insts):
    while 1:
        exec insts[counter]
        counter++
假設這個insts就是一個fsm機器，持續去跑先前那個agent的幾個狀態，比如呼叫llm中，執行工具中...等，那agent就可以拆成一個loop加上一個fsm。而這個loop就可以類比爲cpu。
既然有了cpu，那自然要考慮到其運行在哪個硬體上。在我們這個aos體系中，agent是一個持續執行着fsm的loop程式，通常情況下，他就是一個linux proc。但這樣子的proc一多，就很麻煩。
通常來說我們會將其交由另一個程式管理，所以有了aos daemon。既然我們將其比喻爲cpu，那daemon自然就是硬體了，他是一個可以自由增減cpu核心的嵌入式單板。爲何說是嵌入式單板？等以後daemon的功能一多，那自然就是主機板，乃至伺服器主機了。
後續的比喻就不多說了，總之在這個比喻下，我們有了aos-exec/loop/daemon，分別對應cpu指令/cpu/硬體板子。

有了板子與cpu，下一步，就是作業系統了。在我的想象中，作業系統就是硬體上的一號行程，具備最高權限。而其作用，或者說目標，就是輔助人類更好的使用硬體，具體作用方式就是管理與排程其他行程，以及分配各種資源，還有權限上的管理等等，不一而足。
而在此之上，我先規劃了aos kernel，這是aos的核心，其回歸本質，以幫助人類更好的使用硬體爲目標。
這裏說的硬體，並非是物理世界中的電腦，而是aos exec/loop所仰賴的各種東西，首先看到的就是linux系統，除此之外還有一些抽象的概念。而更好的使用，相比linux這類普通作業系統相比，其意義也更加廣泛。
linux等普通作業系統，其優化目標以時間，資源消耗最小化爲主。但在agent時代，還有其他目標如token用量，人類可理解性，易操作性等等。所以aos系統的目標就是優化任意目標。
到了這裏，我們就有了很好用的工具。
ps.aos kernel被設計爲一號行程，但實際上，我們在aos體系中標明，任何管理行程與資源的行程，都可以用kernel做稱呼，只是說標準實作上我們提供的kernel通常都是一號行程，占有對於某個daemon的唯一控制權。

下一步，是這工具可以用在什麼地方。
既然可以優化任意目標，那我們可以將目光放在一個LLM agent的痛點上：不確定性。
不確定性，其本質就是脫離掌控的程度。倘若脫離的目標是客觀世界，那就等同機率性。其他的，可以是對於人類而言的不確定性，可以是對於你我他任何一個特定人的不確定性。
除此之外，脫離掌控的東西也可以任意的，比如token消耗的程度之類。
而我想要的，就是讓agent可以完全隨我心意去做。常規做法，以先前那個pseudo code所描述的模式來說，就兩種，一種是prompt engineering，另一種是對工具做操作。
這裏不多做贅述，總之要達到完全隨心意這點，有很多方式。
我要做的，是用RSI的方式，使其隨我心意。而我窮，且又看不得AI如此之笨，所以我要做的事情可以這樣描述：
在aos體系的幫助下，實現以RSI方式，持續降低token消耗直至0，並且提升AI智商的路途。

雖然現在仍在給aos體系打基礎，但我可以先簡單起個頭，說明我想怎麼做：
我想讓agent完全隨我心意去做，等同於我想讓這個函數的一些屬性達到一個目標。
那麼一個函數可能有啥屬性？最基本，四處都通用的就是這個函數九軸特性。
這個函數屬性，他是相對於檔案屬性的，一個是動態一個是靜態。真要細說的話，那其實可以是維度上的區別，檔案屬性，就好比物體的長寬高，很容易理解，而函數屬性，則描述了時間軸上的區別，乃至於世界線上的區別(機率)。
除此之外，屬性這東西，除了客觀也還有主觀。應該說，有光才有影，有了相對才有存在，所以你要找一個參照物作爲你的值的基準，對於物體而言，其參照物就是現實物理規律，而函數九軸的參照物則是現實公理基礎。
那假如其基準，是一個抽象化的東西，或者說，乾脆就是人的主觀認知呢？比如一個用agent產出galgame臺詞的函數，對於我這個臭宅男來說，這個函數的臺詞傲嬌程度就是0.4。並且也不一定要是值，甚至可以是一個字串或json物件，比如"缺乏靈活性"、{"pretty":12, "good":true}。

講完了函數屬性的性質，接下來講如何優化他。
一個函數可以拆分爲多個子函數，這個函數的屬性自然由這些子函數決定。所以假如這個函數是機率性的，自然只要將其具備子函數中具備幾率性的，給替換掉即可。
換到agent中，從pseudo code中可以看到，不確定性來自於那個llm呼叫。要降低這個函數的不確定性，自然就是減少llm呼叫，盡量讓工作都堆積到tools。
好比一個生成llm臺詞的任務，常見的做法是只走prompt engineering，tool只給基本的read/write/shell等，讓llm自己去查相關背景。想要提高確定性，那就是稍微改一下，將臺詞拆成景色描寫與人物對話，景色這塊可以用工具找固定描述，人物對話這塊可以透過工具，將需求丟給專管各人物的各agent，讓他們生成。

好，我這邊做個收尾
既然可以優化任意目標，那，是否可以將目標設置爲：提高智能，以及，提高"提高智能"的速度？
RSI的飛輪，自此而始
ps.其實AI不笨。只是說AI缺乏持續學習之類的，並非死記硬背的智能面向。

### 1c. 本題原話（11-07 上午，arknights-kb 開工時；逐字）

**優化方向（確定性）**：

> 可以參考user-advice內的，優化目標就是確定性，我這邊給幾個建議：shell工具一開始可以隨意開放，後面改成謹慎，最後改成全部都有專屬工具。git是很好的東西與重要概念。讓agent專精特定領域，領域越是狹小，能夠變成工具的地方就越多，所需的llm model就越是不用那麼高級，token也能省下來。

**規模與嵌套**（同一段，跟「工具可以是 agent」有關）：

> agent可以成千上萬個，反正可以sleep，交給llm kernel的thinking請求也有排程，並且thinking請求還可以經過一些額外關口，比如一個隊伍使用一個llm_kernel，然後這個llm_kernel負責排程與將請求轉交給另一個llm_kernel，直到轉交給實際打API的llm_kernel，一切都可以嵌套。對，工具也是，工具可以是開一個agent做事，或是將請求交給專精此道的kernel，所以才說會有成千上萬個agent。就好比LLM的神經元，不是每個區域都會被激活。

## 3. 相關條文（條號＋原文摘錄；路徑相對 `proto8/docs/`）

### 3a. 總原則

- **C-56 KISS**：「KISS是最高原則，但也是最後原則，本質上是希望提出的設計在滿足各類需求和原則後，最後能回頭思考，把一些多餘的東西清掉。」不為了方便偷看一層，不為了邊緣狀況加機制，也不拿「最乾淨、規則最少」當抄近路的理由。**寫什麼就做什麼**：值照字面意思用，不讓某些特定值偷偷變成另一種行為（「這等同於埋雷」）。
- **C-52 只管自己這一層，徹底切割、不得有任何殘留**：想看子層的東西要另外透過其他機制，沒機制就別碰（不偷讀下層的 stderr，不替下層驗它的東西）；上層不需要、也不該知道下層是什麼（agent 不知道工具裡是不是 agent）。11-06 讀法：**不認身份、可認公開介面**（標頭、schema、`interfaces.json`），不准認對方的程式名、內部檔名、錯誤字句來分支。認名型的例外第一次出現就消掉，改成「B 宣告、A 照宣告」或通用欄位。
- **C-53** 錯誤只處理自己的。
- **C-77** 開銷不算啥，能包成 aos 函數的盡量包：「LLM本身就是最消耗時間的。」**C-78** 啟動四步（複製、起 daemon、設環境變數、aos-exec 開跑），新東西讓啟動多一步要標出來。
- **C-82** aos 函數與 tool 呼叫要能無痛互轉。

### 3b. 確定性與可預測性

- **C-13** 每個計算任務都有固定的基礎特性（九軸）；**其中確定性是任務自己的屬性**。九軸含副作用、冪等、碰外部檔案、持續性、有無 entry、確定性……
- **C-14** 九軸之外，人可以任意附加特性。
- **C-21** **可預測性有主體性，不是任務的屬性，是觀察者的認識。**
- **C-22** 提高 agent 可預測性的方法：當 S 表示式拆開，**能寫死的節點換成程式**，降低走進不可預測節點的機率。
- **C-22b** 可預測性不只是函式本身的：同一函式在不同狀況、不同硬體上跑，可預測性不一樣。節點＝函式內部＋它所在的執行環境，合起來才是執行節點。
- 現行 `_metainfo.json` 已有布林 `deterministic`（例：memory `true`、thought `false`、bash `false`），還有 `side_effect`、`idempotent`、`interrupt`、`parallel`、`time_ms.{val,max}`、`resource`。

### 3c. 工具、定義、覆蓋層

- **C-61** 工具地址不用 PATH，由 agent 自己的 `tools.json` 登記；**工具一律做成資料夾程式**；腦可以叫的工具另帶 `_tooldef.json`（給模型看的說明），`arguments` 從 stdin 進。
- **N-50** 工具放在 `<格>/tools/<名>/`，叫它時給一個小格 `$AOS_STACK/tools/<名>/`，不知道工具裡是不是 agent。
- **工具＝函式庫**（NORMS 待定之一，已照推薦定、待落條文）：一個工具＝`_entry`＋`_tooldef.json`＋`_metainfo`，收在 `lib/<層>/<名>/`，被引用而不複製；契約 stdin JSON、stdout 結果、錯一律 `工具名: error: 代號 原因`；**bash、run_python 在 stdout 最後一行寫 `[exit code N]`，被跑的指令自己退非 0 不算工具的錯**；沙盒只認 `$AOS_WS`；引用＝agent 的 `tools/<名>` 一條相對捷徑指到庫、同名自己的贏、**版本＝git**。
- **函數成長**（待定之一，已照推薦定、待落條文）：一個函數太大或特性到了就長一級（0 內嵌 → 1 同檔具名 → 2 單檔 `x.json` → 3 資料夾只有 `_entry` → 4 不只入口 → 5 有子函數）；門檻含被幾處叫、伴隨檔、`_metainfo` 特性。
- **`_metainfo`**（待定之一，已照推薦定、待落條文）：單子裡給 kernel 參考的抽屜，地位同 `argv`，inst 忽略；三處同名（資料夾 `_metainfo.json`、JSON 物件與單子的 key）；通用 key 全選填，**只有 `timeout_ms` 強制，實測不回寫**。
- **C-46** agent＝函數＋binding。**定義資料夾呼叫時不變**，history 落在 stack。11-05 註：工具會被 `self_tools` 改進覆蓋層，「定義（函數本體）照樣不變、漂移只在 stack」。
- **P-15** 執行中的一切只寫 `$AOS_STACK`，**定義資料夾不被寫**；`aos-agent tools` 改的是 stack 裡只存差異的覆蓋層；**改定義是人有意的事、不是執行中寫：工具用 `aos-tools`**。11-06 註：實例只指向定義、不存定義副本。
- **C-42** aos 的每一樣東西都是 agent 的工具，形成「自我迴圈改進的閉環」；`self_tools` 改**自己這隻的**工具覆蓋層（add/rm/ls，下一格起生效）；`agents new` 寫一份新定義並起它。
- **C-50／N-53** 重試幾次由外面決定，**agent 自己不數連錯**。
- 自我改進：沙箱紀錄 S11「self-improve 預設就關」（代定）。

### 3d. 權限、沙箱、份額

- **C-04** daemon 完全處理 Linux 那邊的事。**C-64** 用檔案的理由之一是借 Linux 權限（例：讓 kernel 成為 daemon ctl 唯一能寫的人）；權限是 Linux 那邊的事，歸 daemon 那層。11-05：**份額＝daemon 表那列的 `limits`**（`mem_mb`／`cpu_s`／`procs`／`file_mb`／`files`／`user`，同 aos-sandbox 的 key），daemon 在子行程裡 `setrlimit`／`setuid`、proc 不知道。遠期一個 agent 一個 Linux 帳號（不預留 key）。
- **C-66** 工具動呼叫者的工作區靠指標 `AOS_WS`，「能不能寫由 Linux 權限管、風險由工具的設計者自己管控」。**C-80** 指到 daemon 外面就是自行承擔風險。
- **沙箱決定**（thinking 10-24 sandbox，照推薦定、待落條文，接 C-64、C-04）：
  - S1 兩層：身分＝s6-setuidgid（要 root）；命名空間＝bwrap（免 root）；上限＝s6-softlimit。
  - S2 一支 chain-loading 的 `aos-sandbox 設定檔 prog args...`，寫在**叫的那一方**的 argv 最前面，exec 走、不常駐；aos-exec 一行不改。
  - **S4 宣告與強制的分界：強制只在 argv 上**——誰的 argv 寫了 `aos-sandbox` 誰就被關（C-56）。**宣告放 `_metainfo`**：函數可以在自己的 `_metainfo` 寫一格 `sandbox` 說「我只需要這些」，kernel 與人看（只是承諾）；呼叫方要照它關就明寫 `aos-sandbox _metainfo.json#/sandbox …`。aos-exec、loop、fsm 都不讀它。
  - **S5 誰決定關不關：呼叫方**（函數自己關自己沒有意義）。
  - S6 設定 key 全選填：`user`、`base`、`commands`、`ro`、`rw`、`net`、`mem_mb`、`cpu_s`、`procs`、`file_mb`、`files`、`env`；**白名單**：沒列到的路徑看不到，`net` 預設 false。
  - S17 存取控制純靠 Linux、上限交給現成工具，aos 不另做一套。S18（10-30）：Linux 托底，aos 也可以實作自己的機制。
- **N-41** 格自己不 setsid（aos-sandbox 因此不加 `--new-session`）。
