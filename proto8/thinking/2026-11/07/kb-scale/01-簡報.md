## 0. 題目、規矩與產出要求

### 題目

arknights 知識庫這條線（`proto8/thinking/2026-11/07/arknights-kb/`）第二輪一次只做一個地點，現在才做完 2 個（婆山鎮、切爾諾伯格），之後也只打算做 8～10 個地點。語料 `lore/` 有 5,390 檔、約 360 萬漢字（§3）。**請想到全庫規模時的知識庫體系**，五個子題：

1. **節點結構在全庫下**：今天已定的是「節點名英文、內文照原文存成逐段陣列（`source.json` 的 `paras`）、`節點#/段落索引` 連結、tags 只放機械抽出的」（§2、§3）。全庫時的**命名衝突**（92 個名字同時出現在兩類以上、43 個單字名）、**別名**、**版本與更新**（語料 repo 還在長：最新 commit「更新第一百四十三批…」，每批約 19 檔、10 新增 9 改；原文一改，`sha256` 與逐 byte 比對就不過）怎麼辦。
2. **tag 體系**怎麼長、誰維護、怎麼查（使用者：「知識庫一多，查詢起來就費勁。可以加上一些tag啥的」）。
3. **連結的節制規則**：什麼值得連（使用者：「連結那塊，盡量別濫用」；現實：一個 1.2 KB 的地點節點就有 16 條連結）。
4. **「給人看」那層**：附屬白話庫 vs 問答 agent（06 原型實測答對 90%、每題約 1.6 萬 token），兩者怎麼並存、怎麼不跟原文庫脫節。
5. **git 在其中的角色**（使用者：「git是很好的東西與重要概念」）。

### 同批別題（只做自己這題；碰到就寫一句「交給 X」帶過）

- evolve-design：aos 怎麼支援「反向傳播式自我改進」（metainfo 自我宣稱／他者觀測、成本 JSON 值、專精 agent 長出來）。
- kernel-nest：llm kernel 嵌套、排程與跨層記帳。
- tool-evolve：工具權限演進（shell 開放→謹慎→專屬工具）與確定性的量測。

### 規矩（必守）

- **大方向是使用者的**，你在他已定的路上設計細節；照 §4 的原則自己定細節、寫成結論。要帶給使用者的只有兩種：**新想法跟既有原則的衝突**（哪條、衝突在哪、各自後果），以及**原則推不出答案的方向題**（擺選項與後果、標推薦）。
- **KISS 是最高原則也是最後原則**（C-56）；**每層只管自己**（C-52）——例如知識庫工具（aos 本體的 `memory`）不該知道 arknights 這條線的名字表長怎樣。
- proto8 **不做舊版相容、不寫遷移**（使用者：「一律當成沒有舊版」）。
- 你只讀這份簡報；不改任何檔、不 commit。

### 請產出（一份 markdown，第一行一句話標題）

1. **白話總結**：使用者讀不動術語密集的文字——完整句子、一段一個重點、術語第一次出現用日常比喻帶過、別讓他查表。
2. **設計**：五個子題各自的概念、機制、資料格式（給 JSON 範例）、各層誰負責（aos 本體的 `memory`／`memory_write`／新工具 vs arknights 這條線的定義 vs 隊長／審視 agent vs 人）。
3. **與既有 CONCEPTS／NORMS 的衝突**（條號、衝突在哪、各自後果）。
4. **方向題**（選項、後果、推薦）。
5. **落地小步**：可交給 gpt 照圖施工的小步，每步一句完成條件（gpt 只施工、不做設計決策）。

### 1a. user-advice/20261106.md（使用者指定全文給 fable）

寫於2026/11/06的深夜

我認爲這是the new age of programming。
lisp仍是最終最好的抽象，那爲啥大家都不用？我不知道，但是對我而言，就是debug不方便，並且沒辦法控制底層，因爲我是從C++起家，深入其template meta programming，浸淫已久。我知道lisp的meta programming更好更方便，但是...好了，總之閒聊到此爲止。
OK，那我覺得我這套體系能解決這個問題。
我們把filesystem作爲lua來使用，一個簡單的手段就是準備一個程式aos-exec，這個程式可以把資料夾當做檔案來執行，只需要資料夾內有一個_entry檔案即可。第一個好處就是能夠白嫖linux的檔案權限機制，其次就是能夠跨程式語言實作功能。不過最重要的，是agent原生就有操控資料夾的能力。
如果想要用lisp實作agent，並讓agent自己修改自己，那就是在lisp執行中跟agent說，請做這個做那個，你得把lisp相關東西抽象給agent，並且還要要求agent寫lisp程式，這是有風險也比較麻煩的。不過話說到這裏，好像這也是可行的，齁齁，之後有空來做做看。
不過我要說的是，相比跟agent說：這個list就是你，請你修改自己。不如直接把一個資料夾跟幾個python程式和json檔案交給agent，跟他說這就是你，請你新增一個資料夾，裏面弄一個新工具，然後給你自己做擴充。這其實agent更好懂，並且也能輕鬆完成。甚至還可以利用到python的各種wheel。不過說到這裏，好像lisp也能做到，之後來試試看吧。
OK，總之，我這邊要強調的就是檔案系統之於LLM的原生理解性與原生可操作性。
而在這個基礎上，我們實作了aos loop/fsm agent。秉承unix哲學與傳統，沿襲plan9理想，各種東西都盡量以檔案表示，其本體程式盡量簡短。

然後是忘記誰說的(應該是andrew karpathy)，agent就是一個函數。我覺得他觸摸到了本質，而我要替他進一步闡述。agent作爲函數，其pseudo code應如下：
func agent(llm, prompts, tools):
    while 1:
        if has_tool_call:
            do_tool & break
        elif has_prompt:
            add_prompt & break
大約如此，其中的llm就是大語言模型的api呼叫，而prompts則是一個[]string，可以在外部或內部增加或減少東西，至於tools，那就是一些丟進去的外部函數。假如沒有tools，那這個agent函數只能針對[]string做增減，但有了tools，那根據丟給他的東西，這個函數就可以做到任何事。

然後是比較跳躍性的聯想。一個cpu所做的事情可以想成以下pseudo code:
func cpu(insts):
    while 1:
        exec insts[counter]
        counter++
假設這個insts就是一個fsm機器，持續去跑先前那個agent的幾個狀態，比如呼叫llm中，執行工具中...等，那agent就可以拆成一個loop加上一個fsm。而這個loop就可以類比爲cpu。
既然有了cpu，那自然要考慮到其運行在哪個硬體上。在我們這個aos體系中，agent是一個持續執行着fsm的loop程式，通常情況下，他就是一個linux proc。但這樣子的proc一多，就很麻煩。
通常來說我們會將其交由另一個程式管理，所以有了aos daemon。既然我們將其比喻爲cpu，那daemon自然就是硬體了，他是一個可以自由增減cpu核心的嵌入式單板。爲何說是嵌入式單板？等以後daemon的功能一多，那自然就是主機板，乃至伺服器主機了。
後續的比喻就不多說了，總之在這個比喻下，我們有了aos-exec/loop/daemon，分別對應cpu指令/cpu/硬體板子。

有了板子與cpu，下一步，就是作業系統了。在我的想象中，作業系統就是硬體上的一號行程，具備最高權限。而其作用，或者說目標，就是輔助人類更好的使用硬體，具體作用方式就是管理與排程其他行程，以及分配各種資源，還有權限上的管理等等，不一而足。
而在此之上，我先規劃了aos kernel，這是aos的核心，其回歸本質，以幫助人類更好的使用硬體爲目標。
這裏說的硬體，並非是物理世界中的電腦，而是aos exec/loop所仰賴的各種東西，首先看到的就是linux系統，除此之外還有一些抽象的概念。而更好的使用，相比linux這類普通作業系統相比，其意義也更加廣泛。
linux等普通作業系統，其優化目標以時間，資源消耗最小化爲主。但在agent時代，還有其他目標如token用量，人類可理解性，易操作性等等。所以aos系統的目標就是優化任意目標。
到了這裏，我們就有了很好用的工具。
ps.aos kernel被設計爲一號行程，但實際上，我們在aos體系中標明，任何管理行程與資源的行程，都可以用kernel做稱呼，只是說標準實作上我們提供的kernel通常都是一號行程，占有對於某個daemon的唯一控制權。

下一步，是這工具可以用在什麼地方。
既然可以優化任意目標，那我們可以將目光放在一個LLM agent的痛點上：不確定性。
不確定性，其本質就是脫離掌控的程度。倘若脫離的目標是客觀世界，那就等同機率性。其他的，可以是對於人類而言的不確定性，可以是對於你我他任何一個特定人的不確定性。
除此之外，脫離掌控的東西也可以任意的，比如token消耗的程度之類。
而我想要的，就是讓agent可以完全隨我心意去做。常規做法，以先前那個pseudo code所描述的模式來說，就兩種，一種是prompt engineering，另一種是對工具做操作。
這裏不多做贅述，總之要達到完全隨心意這點，有很多方式。
我要做的，是用RSI的方式，使其隨我心意。而我窮，且又看不得AI如此之笨，所以我要做的事情可以這樣描述：
在aos體系的幫助下，實現以RSI方式，持續降低token消耗直至0，並且提升AI智商的路途。

雖然現在仍在給aos體系打基礎，但我可以先簡單起個頭，說明我想怎麼做：
我想讓agent完全隨我心意去做，等同於我想讓這個函數的一些屬性達到一個目標。
那麼一個函數可能有啥屬性？最基本，四處都通用的就是這個函數九軸特性。
這個函數屬性，他是相對於檔案屬性的，一個是動態一個是靜態。真要細說的話，那其實可以是維度上的區別，檔案屬性，就好比物體的長寬高，很容易理解，而函數屬性，則描述了時間軸上的區別，乃至於世界線上的區別(機率)。
除此之外，屬性這東西，除了客觀也還有主觀。應該說，有光才有影，有了相對才有存在，所以你要找一個參照物作爲你的值的基準，對於物體而言，其參照物就是現實物理規律，而函數九軸的參照物則是現實公理基礎。
那假如其基準，是一個抽象化的東西，或者說，乾脆就是人的主觀認知呢？比如一個用agent產出galgame臺詞的函數，對於我這個臭宅男來說，這個函數的臺詞傲嬌程度就是0.4。並且也不一定要是值，甚至可以是一個字串或json物件，比如"缺乏靈活性"、{"pretty":12, "good":true}。

講完了函數屬性的性質，接下來講如何優化他。
一個函數可以拆分爲多個子函數，這個函數的屬性自然由這些子函數決定。所以假如這個函數是機率性的，自然只要將其具備子函數中具備幾率性的，給替換掉即可。
換到agent中，從pseudo code中可以看到，不確定性來自於那個llm呼叫。要降低這個函數的不確定性，自然就是減少llm呼叫，盡量讓工作都堆積到tools。
好比一個生成llm臺詞的任務，常見的做法是只走prompt engineering，tool只給基本的read/write/shell等，讓llm自己去查相關背景。想要提高確定性，那就是稍微改一下，將臺詞拆成景色描寫與人物對話，景色這塊可以用工具找固定描述，人物對話這塊可以透過工具，將需求丟給專管各人物的各agent，讓他們生成。

好，我這邊做個收尾
既然可以優化任意目標，那，是否可以將目標設置爲：提高智能，以及，提高"提高智能"的速度？
RSI的飛輪，自此而始
ps.其實AI不笨。只是說AI缺乏持續學習之類的，並非死記硬背的智能面向。

### 1c. 本題的原話（逐字）

##### 節點：`ak/<class>/<slug>/{README.md,source.json,links.json,tags.json}`

- README 只有一行：`# 婆山鎮 (poshan-zhen)`。lint 要求它符合 `# .+ \(<目錄名>\)\n`。
- source.json：`{"from":"lore/places/婆山鎮.md","sha256":"7472…bfa1","paras":["### 婆山鎮（畫中天地）","","實為十二代理人之一「夕」…",…]}`。`paras` 是原檔按 `\n` 切開的陣列，保留空段和尾端換行；婆山鎮切成 5 段，1,241 B。
- links.json：`{"links":[{"name":"夕","in":"source#/paras/2","at":[10,11],"to":"lore:characters/夕.md","state":"pending","by":"llm:sol","lore":"lore/characters/夕.md"},…]}`。
  - `in` 用 JSON Pointer 指段落，`at` 是段內 Unicode 字元的左閉右開區間。
  - 目標節點已存在時，`to` 寫 `ak/...` 或 `node#/pointer`，`state` 為 `ok`。
  - 婆山鎮 16 條連結全是 pending（llm:sol 13、rule 3），其中 9 條指向夕；切爾諾伯格也是 16 條（llm:terra 11、rule 5）。
- tags.json：`{"tags":["class:places","group:炎國／歲"]}`。`class:` 取 lore 第一層目錄名；`group:` 取同目錄 `INDEX.md` 裡連到本檔的那條連結所在的最近 `##`～`######` 標題。不做語意推論。
- 別名分片：`ak/index/aliases/<class>-NN.json`，內容 `{"description":…,"aliases":{"煮傘居士":["lore/characters/夕.md"]}}`。
  - 每片連說明在內不超過 8,000 B，滿了開下一片，讀取時也檢查。
  - 同一別名對到多個目標時保留為模稜。
  - `places-01.json` 目前 7,595 B、126 個別名；`characters-01.json` 145 B、1 個別名。
- kb_mentions：把 `rglob` 掃到的所有 `lore/**/*.md` 檔名 stem（排除 INDEX、README、`_` 開頭）都當候選名，再加上別名，做最長優先比對。單字名或同位置多候選標成 `ambiguous`，交給 linker 裁決。

  - extra 名字的 offset 有誤時，只有該名字在指定段唯一才由腳本重定位，並記 supplied／located。
- kb_lint2 規則：
  1. `'\n'.join(paras)` 逐 byte 等於原檔，sha256 相符。
  2. README 標題合格。
  3. 每條連結的 `in` 段號存在，`at` 切出的字正好是 `name`。
  4. `state` 與目標是否存在一致。
  5. pending 必須是 `lore:` 開頭、`.md`、檔案存在、不越界，且與 `lore` 欄一致。

## 3b. aos 本體現行知識庫機制（memory／memory_write；備料 E）


簡稱：KW＝`proto8/thinking/2026-11/05/knowledge-write/`；AK＝`proto8/thinking/2026-11/05/agent-knowledge/`；AR＝`proto8/thinking/2026-11/07/arknights-kb/03-W1到W4施工結果.md`；FS＝`proto8/lib/agent/memory_fs.py`。

#### 1. 現況一句話

知識庫＝一個普通資料夾樹，不登記。三支工具：`memory`（唯讀 read／ls／find）、`memory_write`（add／edit／rm）、`memory_export`（整棵印成一份 Markdown）。三支共用 FS（找根、定址、列子節點）。出處：AK/README、KW/README、FS。

#### 2. 節點格式與路徑規則（FS、AK/01「節點與定址」）

- 路徑：段用 `/` 接，段名只能 `[a-z0-9_-]+`；`""` 或 `/`＝根；有 `.`、`..`、空段、大寫、其他字＝`PathBad`。尾巴 `/` 會被 strip（Haiku 實測後加，AK/04）。路徑不帶副檔名（帶 `.md`＝`PathBad`，KW/04-續 #31）。
- 磁碟對應：資料夾節點＝`<根>/<路徑>/`，文在裡面 `README.md`（沒有＝文空）；葉節點＝`<路徑>.md` 或 `<路徑>.json`。定址優先序：資料夾 ＞ `.md` ＞ `.json`（`locate`/`leaf_file`）。
- 子節點：子資料夾＋`*.md`／`*.json`（README.md 除外），`.`、`_` 開頭不算，名字不合 SEGMENT 不列，照名字排序（`children`）。實測：`D.md`、`e.MD`、`f.yaml`、`g h.md` 一律不可見；空資料夾 `c/`＋`c.json` 時內容被遮（KW/04-續 實測「同名」）。
- 文的格式：md 第 1 行 `# 標題`、其後第一個非空行＝摘要（`ls`/目錄印這句）；json 取頂層 `title`／`summary` 鍵（`title_summary`）。yaml 不認（AK/01）。
- `read` 可帶 `節點#/JSON/Pointer`（RFC6901），只限 `.json` 葉；`ls`/`find` 拒 `#`。錯碼 `TargetBad`、`PointerMissing`、`FileBad`（`proto8/lib/agent/memory/README.md`、`_tooldef.json`；commit 61a7ed360 加入）。

#### 3. 大小限制

- 節點文目標 ≤ 2 KB（建議，膨脹即拆，照 wf/STRUCTURE；AK/01、`proto8/knowledge/README.md`）。
- `memory read` 預設印 ≤ 8000 bytes，超過截斷附 `[truncated: N more bytes]`（`memory/_entry` DEFAULT_MAX_BYTES）。
- `memory_write` 硬限 text ≤ 8000 bytes（含補上的結尾換行），超過＝`TextBad … split into child nodes`；段名 ≤ 200 bytes（`memory_write/_entry`、`writing.py text_bytes`）。
- `memory_export` 預設 `max_bytes` 50000（`memory_export/_tooldef.json`）。
- `find` 最多列 20 筆，再多印 `… N more`（`FIND_LIMIT`）。

#### 4. 讀寫 op

- `memory`：stdin JSON `{"op","path","query","max_bytes"}`；`read`＝`node: 路徑`＋文＋`children:` 目錄（每行「名 摘要」，資料夾名加 `/`）；`ls`＝只列子節點；`find`＝見 §5。`_metainfo`：side_effect false、parallel true（`memory/_metainfo.json`）。
- `memory_write`：`add {path,text}` 建 `.md` 葉（父要在、一次只長一層、不 `mkdir -p`；父是葉時升級 `父.md → 父/README.md`）；`edit {path,text}` 整段換文（無 append／patch）；`rm {path, recursive?}`（有子節點需 `recursive:true`，否則 `ChildrenExist`）。不做 `mv`。`add` 一律建 `.md`；`.json` 葉 edit 只驗合法 JSON。成功輸出 `node: <路徑>`＋`written N bytes`／`removed`。`_metainfo`：side_effect true、parallel false、idempotent false。出處：`memory_write/_tooldef.json`、`writing.py`、KW/02。
- `memory_export`：`{path, max_bytes}`，JSON 節點印成 code block；捷徑繞回上層只印一行 `not followed`（AK/06）。
- 根怎麼進 agent：`brain.py --memory NAME`／`aos-mcp --memory NAME` 呼叫該工具 `{"op":"read"}`，原樣接在 system prompt；每回合重讀（AK/06 代定 7、9）。

#### 5. find 的查法

- 實作：子行程 `grep -R -i -l -F --include=*.md --include=*.json --exclude=.* --exclude-dir=.* -- query target`（`memory/_entry grep()`）。即：**全文、固定字串子字串、不分大小寫**，掃標題＋摘要＋本文（整個檔內容），**不查檔名**、無排名、無正規式、無多關鍵字邏輯。
- 每次呼叫即時掃整棵（或 `path` 子樹），沒有索引。命中後每檔再讀一次取標題；結果照路徑排序、截 20 筆。
- 跟捷徑（`-R`），命中路徑用 grep 印的掛載路徑、不 realpath（W1 改，AR）。grep 退 2 但有命中照印；無命中才 `ReadFailed`。旁邊反覆建刪 `.rm.*` 時 1000 次 0 失敗（AR W1）。
- 被同名資料夾或 `.md` 遮住的檔命中會被濾掉（`file_node`）。

#### 6. 多庫（KW/03）

- 已裁、已做：方案 A＝一個資料夾放幾條捷徑各指一庫，`_memory.json` 的 `base`（字串）或 `AOS_MEMORY` 仍指一個資料夾；路徑第一段＝庫名。掛／卸＝`ln -s`／`rm`，無設定格式。根 README 由人寫目錄句。
- `rm` 遇捷徑只拆捷徑、不進去；寫入落到真資料夾，鎖也在真資料夾。兩捷徑指同一庫＝find 命中印兩次（自擔）。斷捷徑不列。
- 方案 B（`base` 收 `{"名":"路徑"}`、工具合成虛擬根、逐庫 find 合併）＝可選 W7，未做。`AOS_MEMORY` 維持單一路徑。
- 一支 memory＝一個根；腦不能挑庫（無 `base` 參數）。找根優先序：工具資料夾 `_memory.json` ＞ `AOS_MEMORY`（相對＝相對 `$AOS_DAEMON`，無則 cwd）；另有登記格 `env`（R1）。都沒有＝`MemoryMissing`（FS `memory_root`）。

#### 7. 寫入權限與鎖

- 權限兩層，程式不驗身分：①工具清單有沒有配 `memory_write`；②Linux 權限（資料夾不可寫＝`WriteFailed … read-only for you`，`locking.py with_lock` 先 `os.access` 檢查）。KW/02-續。
- 根 `/` 不給 edit／rm（`PathBad root is read-only`），以 realpath 比對擋捷徑繞過（AR W3）。
- 鎖：每次呼叫自動對「要改目錄項的那個資料夾」`aos-lock acquire --wait-ms 3000 --lease-ticks ceil(10000/tick_interval_ms) --note "memory_write <op> <path>"`，鎖在 `<資料夾>/.lock/`；寫完 release（失敗只 warning）。拿不到＝`LockFailed`。沒有 lock/unlock op（W8 可選未做）。圖紙原寫 `--lease-ms`，現行 aos-lock 已改 ticks（AR「偏離」）。
- 鎖範圍：add/rm 鎖父資料夾（升級時鎖祖父），edit 鎖節點所在資料夾。**鎖沒有上下層**：鎖 `p/c/` 不擋別人拿 `p/`（KW/04-續 實測）。recursive rm 前 `os.walk` 掃子樹活鎖，掃完到刪之間有空窗（自擔）。
- 讀不鎖；兩回合間 read→edit 是後寫者贏（lost update，自擔，KW/04 #3）。
- 原子寫法：同資料夾 `mkstemp(.tmp.*)`→`fchmod` 留原權限→`edit` 用 `os.replace`、`add` 用 `os.link`（目標已在＝`NodeExists`）；升級＝建 `.new.*`→rename→unlink 舊葉；刪資料夾＝rename 成 `.rm.*` 再 rmtree；超過 10 分鐘的殘骸由下個拿鎖者清（`writing.py`）。

- 實測數字：aos-lock 每 20 ms 輪詢；十人搶鎖約 0.22 秒換一人、非先來先得；段名 252 字可建但 `.tmp.`/`.lock` 撞 255；每段 200 字深 20 層撞路徑上限。read/ls 對捷徑迴圈無防護。

#### 11. tag／別名／連結／索引

- **tag：沒有。別名：沒有**（唯一近似是捷徑，屬檔案系統層，find 會重複命中）。**索引：沒有**，find 每次即時 grep 全掃。
- **連結：沒有機制**。節點之間只靠本文自然語言寫「see node `errors`」「child node `me/self_tools`」（例：`knowledge/aos/me/README.md`、`rules.md`、`errors/codes.md`）；工具不解析、不驗證。`knowledge/aos` 少數檔含 Markdown `](` 連結（cli/README 10 處等），工具同樣不處理。
- 唯一結構化導覽＝父子目錄（`read` 印 children＋摘要）。

#### 12. 已定案 vs 規劃中

- 已定案且已實作：節點格式／路徑規則、三支工具與 op、find＝grep 全文、多庫方案 A、寫入權限兩層、每次寫自動鎖、原子寫法、根唯讀、不做版本（交給 git）、JSON Pointer 讀。
- 已定案未實作：W5 範本接線、W6 教 agent 寫的知識節。
- 規劃／可選未做：W7 方案 B、W8 lock op、W9 JSON 後端（`memory_fs` 六函數接口已預留：locate、read_text、children、write_text、make_child、remove；KW/02-續）、W10 mv、`_meta.json`、yaml 葉、跨機器一致性。

#### 13. 現況規模（`proto8/knowledge/`）

- 目錄：`knowledge/README.md`、`knowledge/aos/`（根 README＋`world`、`brain`、`status`、`rules` 葉；`me/`、`agents/`、`errors/`、`cli/` 資料夾）。共 24 檔、內容合計約 49 KB；最大檔 `agents/thought.md` 3651 bytes（已超 2 KB 目標）。
- 節點例：`knowledge/aos/me/self_tools.md` 第 1 行 `# Changing your own toolbox`、第 3 行一句摘要，後接呼叫例與規則；英文短句。

#### 14. 對全庫規模（5,000+ 節點、數百萬字）可能吃緊的點（只列觀察）

1. find 無索引，每次 `grep -R` 全掃子樹，且每個命中檔再開一次讀標題；現行實測都在 24 檔規模。
2. find 結果硬截 20 筆、照路徑字母排序、無相關度排名；`… N more` 只給數字。
3. find 只支援單一固定字串子字串，無多詞、無檔名查、無同義詞／別名。
4. 無 tag、無交叉連結、無反向連結；跨分支關係只能靠本文自然語言。
5. 導覽只有樹；根 `read /` 每回合進所有 agent 的 system prompt，根的 children 目錄行數隨頂層節點數線性成長。
6. 節點 2 KB 建議／8000 bytes 硬限，數百萬字約需數千節點；段名 `[a-z0-9_-]` 限 ASCII 小寫（中文、大寫檔名不可見）。
7. 寫入每次呼叫叫 aos-lock 子行程（wait 3 秒）；同一資料夾寬而扁時所有 add/rm 共用一把父鎖；鎖無階層。
8. 無 metadata（來源、時間、作者），歷史只能靠外部 git；工具不碰 git。
9. 多庫方案 A 靠捷徑；同庫多掛重複命中；斷捷徑靜默不列。
10. memory_export 預設 50000 bytes 上限，整庫輸出遠超此值需分子樹多次匯出。
11. `edit` 只能整段換；`mv` 不存在，搬節點＝rm＋add，子樹搬遷無原子操作。
12. 已有節點超出 2 KB 目標（thought.md 3.6 KB），建議值無工具強制（只有 8000 硬限）。

## 4. CONCEPTS／NORMS 相關條文（備料 C＋本題補）


路徑都相對 `proto8/docs/`。C-＝概念、N-＝規範。只摘條文，條文以外沒有加推論。

#### 1. 最高原則與分層

- **C-56 KISS＝最高原則，也是最後原則**（CONCEPTS/01-設計理念/03-最高原則與兩條總原則.md）：「KISS是最高原則，但也是最後原則，本質上是希望提出的設計在滿足各類需求和原則後，最後能回頭思考，把一些多餘的東西清掉。」做法是最後一步做減法：不為了方便偷看一層，不為了邊緣狀況加機制，**也不拿「最乾淨、規則最少」當抄近路的理由**，清的時候不能違反其他原則。**寫什麼就做什麼**：值照字面意思用，不讓某些特定值偷偷變成另一種行為（「這等同於埋雷」）。例：`stdout` 寫 `/dev/stdout` 就照字面打開那個路徑。
- **C-52 巢狀：只管自己這一層，徹底切割、不得有任何殘留**（同檔）：每層只管自己，同一個原則在每層重複出現。**想看子層的東西要另外透過其他機制，沒機制就別碰**（不偷讀下層的 stderr，不替下層驗它的東西）。**上層不需要、也不該知道下層是什麼**（fsm 不知道某格是不是 fsm，agent 不知道工具裡是不是 agent，什麼都不往下傳、不繼承）。
  - 11-06 讀法（續檔 03-續-C-52-例外.md）：**不認身份、可認公開介面**。上層可依賴下層公開宣告的介面（標頭、schema、`interfaces.json`），**不准**認對方的程式名、內部檔名、錯誤字句來分支。
  - 准讀下層 stderr 的判準：出口的讀者看不到下層 stderr 時（外部 agent、腦、回信方、看表的人），**失敗時**可以接下層的「代號與原因」或附 stderr 尾 2 KB。現行表有 ①aos-mcp ③llm-kernel ④act ⑤agents/self_tools/aos_json/json_rewrite ⑥thought ⑦aos-daemon。
  - 例外的升格門檻：認名型的例外第一次出現就消掉，改成「B 宣告、A 照宣告」或通用欄位；同型例外再出現時，問「往後會更多嗎、好處遠大於壞處嗎」；「先不做」要寫明等什麼。
  - 父 daemon 對子項只看它活不活著：「子daemon管好自己，父daemon只看他有沒有活着…盡量解耦合。」
- **C-53 錯誤只處理自己的**（01-設計理念/03-續-C-53.md）：對別人的錯有入口、出口、事先列出三種姿態；錯誤路徑濃縮成少數幾條。
- **C-03** 由下往上依序是 Linux → daemon → 時空 → 排程與資源分配 → agent，上層只透過下層。**C-04** daemon 完全處理 Linux 那邊的事。
- **C-74 分層**（01-設計理念/02-C-51.md）：基礎層（核心＝aos-exec；loop、daemon）→ 標準庫（fsm、tasks）→ agent／kernel。分層講的是「誰依賴誰」，C-03 講的是「誰排程誰」，兩條軸不衝突。kernel 不譯作「核心」。
- **C-77 開銷不算啥，能包成 aos 函數的盡量包**：「LLM本身就是最消耗時間的。」**C-78** 啟動四步：複製、起 daemon、設環境變數（盡量少）、aos-exec 開跑。新東西若讓啟動多一步，要標出來。**C-83** 可遷移性是上位原則。
- **C-80** 不在任何 daemon 下的不管：「指到daemon外面就是自行承擔風險」。**C-81** stack 是 proc 自己的地盤，對外介面四類：命令列參數、環境變數、stdin/out/err/exit、信箱內容格式（03-基礎設施/02-資料夾程式-工作區與-stack.md）。

#### 2. 資料夾程式、路徑、引用

- **C-68 資料夾＝程式**（01-設計理念/06-C-68～C-72.md）：入口是 `$AOS_ENTRY`（預設 `_entry`）。呼叫寫成 `aos-exec [--ws WS] XXX [args...]`，XXX 可以是資料夾、檔或 `檔#/指標`。**C-69** aos 只訂環境變數，共六個：`AOS_ENTRY`、`AOS_WS`、`AOS_STACK`，以及每層由 aos-exec 覆寫的 `AOS_CF`、`AOS_CD`、`AOS_CO`（N-57）。**C-70** 巢狀時子 stack 由程式自己訂。
- **C-71** 資料夾比喻成 table：「本質都只是"用index+巢狀方式分資料"」。11-06 註：「沒有庫、子庫之分，資料夾…本來就是一種資料庫、記憶庫。」
- **C-72 JSON＝埋在檔案裡的 table**，入口的尋址方式照樣適用（`js[".aos"]["inst"]`）。要指更深就寫 `檔#/指標`。
- **C-51** 資料夾與 JSON 可以互通，但「建議不要濫用」，所以互通**不進規範**。JSON schema 可以當型別、interface、簽名用，驗證選用。
- **C-73** entry 有四種：可執行檔、inst 單子、argv 陣列、`js[$AOS_ENTRY]` 的值（單子、陣列、字串路徑；沒 `argv` 的物件當資料夾，一路往下）。
- **N-61**（NORMS/10-基礎設施-定義與工作區/05-N-61～N-62.md）規定找入口的順序：資料夾 → `XXX/$AOS_ENTRY` → `$AOS_ENTRY.json`，同名時資料夾贏；字串值＝路徑轉向，等於全新一次 aos-exec；繞圈由 aos-exec 自己偵測。這條**「是每層只管自己（C-52）的唯一例外」**，11-06 改讀成 aos-exec 這一層的例外。argv[0] 帶 `/` 而 exec 不了時，等於在前面插 `aos-exec`。
- **N-62 路徑支援 `檔#/指標`**：寫法是 RFC 6901，**第一個 `#` 就切、不支援檔名含 `#`**，`#` 後一定要 `/`。只用在 aos-exec 的入口路徑；另外 `$ref` 的檔名與 argv[0] 也認。**單子裡的 `$env` 路徑不認 `#`**；`AOS_CF` 不帶 `#/`，位置在 `AOS_CO`。（使用者：「#/。」「尋址一定值得。」）
- **C-48 JSON 格式族**（01-設計理念/01-C-01～C-48.md）：靠加 key 擴充；**不認得的 key 一律忽略、不報錯**；私有 key 不重疊即可共用一份檔。**值的雙形**：純值也可以寫成物件（展開形），原值放在 `val`（C-55）。指示詞只有 `$env`、`$ref`，修飾詞 `$path`、`$prefix`（N-45）。`$ref` 指位置只寫 `檔#/指標`，也可以是陣列，多份合成一份。
- **C-55 布局成長**：檔案與 JSON 長大照同一套規則。純值不夠用就長成物件，只剩原值就縮回純值。
- **C-65/C-66/C-67 工作區與 stack**：stack＝執行中的狀態、草稿、紀錄、小格；工作區（`AOS_WS`）**保持乾淨**，只放交辦的東西與成果。影響外部要透過「指標」，也就是 `AOS_WS`。stack 放哪由呼叫方自由決定，兩隻 agent 共用一個 stack＝共享記憶、接力。11-06 K7：外人只能寫對方在 `interfaces.json` 宣告為可寫的覆蓋層，其他走信箱或 ctl。
- 名詞「介面」（CONCEPTS/附錄1-名詞.md）：資料夾程式在頂層 `interfaces.json` **宣告自己遵守**哪些約定（像 Go 的 interface）；用的一方只認宣告，不猜。
- **C-64** 用檔案的理由之一是借 Linux 權限。份額寫在 daemon 表那列的 `limits`；遠期打算一個 agent 一個 Linux 帳號（沒排）。

#### 3. metainfo、工具定義、函數宣告

- **C-42b**（CONCEPTS/03-基礎設施/01-inst至fsm.md）：inst 的 JSON 可以多放東西，例如九軸特性、traits、資源標籤、優先順序、工具；inst 不認的別人可以讀。工具用 JSON schema 限制引數，schema 怎麼轉成 argv 沒定。這個抽屜叫 `_metainfo`。
- **C-13** 每個計算任務都有固定的基礎特性（九軸），其中確定性是任務自己的屬性。**C-14** 基礎特性之外，人可以任意附加特性（CONCEPTS/04-kernel.md）。
- **`_metainfo` 還在【待定】**（NORMS/08-待定/01-待定之一.md）：它是單子裡給 kernel 參考的抽屜，地位同 `argv`，inst 忽略它，格式自由。10-24 使用者說：「其特性我想要將其寫到_metainfo，裏面可以存放該函數要跑多久，要喫多少資源這種東西…kernel也可以透過這個，來做參考」，規劃已照推薦定、待落條文：三處同名（資料夾的 `_metainfo.json` 檔、JSON 物件與單子的 key），找法同找入口，通用 key 全選填，**只有 `timeout_ms` 強制，實測不回寫**。
- 同一待定檔還有：kernel 評估納入錯誤路徑（量法、要不要寫進 `_metainfo` 都沒定）；**函數成長**分 0～5 級（內嵌 → 同檔具名 → 單檔 → 資料夾只有 `_entry` → 不只入口 → 有子函數），門檻包含 `_metainfo` 特性；**工具＝函式庫**：一個工具由 `_entry`、`_tooldef.json`、`_metainfo` 組成，收在 `lib/<層>/<名>/`，被引用而不複製。工具契約：stdin JSON，stdout 結果，錯一律寫 `工具名: error: 代號 原因`。
- 命名（CONCEPTS/01-設計理念/C-54-命名方法/02-R8～R13.md 的 R11、NORMS/附錄3-舊名對照.md）：`_` 開頭＝aos 認的固定檔。`_entry` 是程式，不帶副檔名；`_tooldef.json`、`_metainfo.json` 是資料，帶 `.json`。只有 `_tooldef` 沒有副檔名＝`ToolDefMissing`；只有 `_metainfo` 沒有副檔名＝當沒有。abbr.json：`_metainfo` 沿用、不改成 `_meta`，是普通 key。
- **C-61**（CONCEPTS/05-agent/02-agent-的工具與agent-就是一台狀態機.md）：工具地址不用 PATH，由 agent 自己的 `tools.json` 登記（存絕對路徑）。**工具一律做成資料夾程式**；腦可以叫的工具另帶 `_tooldef.json`，那是給模型看的說明，`arguments` 從 stdin 進。
- **C-82 aos 函數與 tool 呼叫要能無痛互轉**：「aos函數他也是透過json去定義的…和tool呼叫，兩者之間應該要是可以無痛轉換。」argv 有兩面：給人用的照 unix 習慣、要有 `--help`；純 aos 函數「argv的旗標盡量不要濫用，大多東西都走要給stdin的json」。要不要用 JSON 定義生旗標，照實際需要決定。
- **N-66 一箱一函數**（NORMS/05-基礎設施-窗/08-N-66.md）：一個信箱後面接一個 aos 函數，body＝那函數的 stdin JSON；**函數的 `_tooldef.json` 就是這箱接什麼的說明**。
- **N-50** 工具放在 `<格>/tools/<名>/`，叫它時給一個小格 `$AOS_STACK/tools/<名>/`，不知道工具裡是不是 agent。

#### 4. agent

- **C-19** agent 的簽名＝腦＋記憶（核心人格、近期記憶）＋手腳（工具）。**C-20** agent 是複合型任務，要被排程；最核心的一題是「很多 agent 時誰先用腦」（05-agent/01-腦-工具-可預測性與agent函數binding.md）。
- **C-21 可預測性有主體性，不是任務的屬性，是觀察者的認識。** **C-22** 能寫死的節點換成程式，提高可預測性。**C-22b** 執行節點＝函式加上所在的執行環境。
- **C-40** agent 要能當拋棄式函式用。**C-46** agent＝函數＋binding。定義資料夾**呼叫時不變**，history 落在 stack（`history.jsonl`）。腦寫在 `llm.json` 的 `endpoint` 代號；stack 裡放同名副本可以蓋過定義。「agent 當函數是概念上的，不是形式上的」。agent 只看到自己的工具清單，子 agent 只看自己的 stack，沒有 `parent` 鏈。11-05 註：工具會被 `self_tools` 改進覆蓋層，**「定義（函數本體）照樣不變、漂移只在 stack」**；工具查「叫我的是哪隻」用 `aos-agent ctl who`，經 daemon 表查，不從路徑往上爬。
- **C-50 / C-62 / N-53**：agent＝狀態機＋各狀態跑的 inst；定義就是一台狀態機，怎麼跑、由誰跑，概念上不管。aos 的 agent 被外面的 loop 一次一次驅動，「為的是讓 agent 方便審視自己」。**重試幾次由外面決定，agent 自己不數連錯。** C-39：agent 是一個資料夾，持續被求值。
- **C-42 工具＝被引用的標頭檔；agent 也可以是工具**（05-agent/01-續-C-42.md）：aos 的每一樣東西都是 agent 的工具，形成「**自我迴圈改進的閉環**」。11-05 落實了兩支工具：`self_tools` 改**自己這隻的**工具覆蓋層（add/rm/ls，定義不動，下一格起生效）；`agents` 在同一台 daemon 上生、叫、收別隻 agent，不繼承腦與工具。
  - 記憶：`memory` 是唯讀的層級式知識庫，就是資料夾樹，用 `AOS_MEMORY` 指，定義裡的 `_memory.json` 蓋過它。知識庫便攜，可以多隻共享；頂層 ELI5，深的再抽。規劃中：寫入另開一支 `memory_write`，出廠的 `knowledge/aos` 不給 agent 寫（W1～W10）。
  - **thought 做成工具、不做成 agent 機制**：「我更推薦將其作為工具。」「其實記憶這項，他本身也算是任務」。thought 派給乾淨的子 agent，只拿回短結論；深度用 `AOS_THOUGHT_DEPTH` 在起子時給。
  - **生子 agent 兩種**：`new` 產出新定義，`add` 用現有定義加覆蓋；`ws` 不固定。上限分兩道關：工具自己數 `max_children`，判官管整台的 `max_running`。
- 名詞：sleep＝休眠到磁碟（附錄1-續）；daemon 收工時，活著的 proc 留在 `sleeping`，再開時 wake（N-17、N-28）。**C-16** 的 sleep＝資料夾凍住，暫停是為了遷移；**C-79** image 模型：daemon＝硬體、stack＝記憶體、ws＝外置記憶體、定義＝source code。

#### 5. kernel／llm kernel、計費

- **C-09～C-12** 有限的就是資源，用格數表示；排序＝決定哪個任務先給哪個資源；排序本身也是計算任務。**C-15** 排序程式可以叫模型生成（CONCEPTS/04-kernel.md）。
- **C-47 kernel 定義**：原生定義＝管理哪些東西被執行；aos 實作定義（11-05 加嚴）是：**被管的 proc 要掛在 daemon 下**；判斷後**自己 fork 跑原生程序或函數的不算** kernel；**轉交給有權的 kernel 的算**，可以帶 kernel 字，但「建議不要濫用」。daemon 是最基礎的 kernel，來者不拒。
- **N-42**（NORMS/09-kernel.md）：先做兩種 kernel，**兩支不併成一支**——(1) LLM kernel，(2) 通用 kernel（判官，以 agent 判斷，現無判官腦）。遠期判官要長成「誰能對誰做什麼」，stop、rm、sleep 也要過判官。
- **N-42(1) LLM kernel**（09-kernel/01-…、02-…）：信 body 是 `{"endpoint"?, "request", "priority"?}`，回信是 `{"message","usage","model"}`。**kernel 不自己跑**，每次問腦都請 daemon 掛一個 `max:1` 的 proc。掛信寄給 `$AOS_KERNEL`，沒設就寄 `$AOS_DAEMON`。**用量從回信的 `usage` 記**；`budget` 設每窗 `max_calls`／`max_tokens`，到頂回 `BudgetMissing`。**能力包**：`endpoints` 的一組就是一個能力，帶 `slots`、`budget`、`speed`、`fixed`，換模型＝換代號。屬性表每拍寫成窗 `endpoints.json`。每寄件人額度記在 `budget.senders`，用量在 `used.json` 的 `packs`、`senders`，key 相對 kernel stack，**寄件人不驗**（先信任）。計數欄位叫 `counter_calls`／`counter_tokens`。舊版的 `_metainfo.time_ms` 排序依據 11-04 已拿掉。
- 待定：額度快見底時留一段只給 `high` 過；kernel 公告。
- 條文裡**沒有「ledger／計費」字樣**；記帳只有上面的 `used.json`／`usage`／`budget`。也沒有談 llm kernel 能否嵌套的條文，只有 C-47 說轉交型也算 kernel，以及 `AOS_LLM_KERNEL` 是 hub、一路繼承（N-63）。

#### 可能與新想法衝突的條目（只指張力）

1. **統一路徑 `a/b#/c/1`**：N-62 只准在 aos-exec 入口路徑、`$ref` 檔名、argv[0] 用 `#/`，**單子裡的 `$env` 路徑不認 `#`**，**也不支援檔名含 `#`**。`AOS_CF` 與 `AOS_CO` 分開放。C-51 說資料夾與 JSON 互通「不進規範」、「建議不要濫用」。N-61 規定同名時資料夾贏、`.json` 自動補找，這跟「一條路徑跨檔」的歧義有關。
2. **metainfo 為任意 JSON 值、可寫公式 `{"cal":"x*2"}`**：C-56 要求「寫什麼就做什麼」，不讓特定值偷偷變成另一種行為；C-48 只有 `$env`／`$ref` 兩個指示詞，加新的會碰到「除非必要不新增格式」；C-48/C-55 的值雙形規定展開形原值放在 `val`；待定稿說 `_metainfo` 只有 `timeout_ms` 強制、通用 key 全選填、**實測不回寫**。
3. **自我宣稱 vs 他者觀測**：C-21「可預測性…是觀察者的認識」，跟 C-13「確定性是任務自己的屬性」並存；`_metainfo`「實測不回寫」；C-52 規定上層只認下層公開宣告的介面；kernel 寄件人不驗（先信任）。觀測要寫到哪也有限制：窗沒有歷史，trace 已拿掉，C-52 不准偷讀下層。
4. **agent 成千上萬、可 sleep**：C-80 要求每個 proc 都在 daemon 下；sleep 是 daemon 級的硬凍（N-03 現況），C-16 是整樹凍住；C-20 把「誰先用腦」列為最核心的題目；上限有 `max_children` 與 `max_running` 兩道關；C-78 要求啟動步驟少。
5. **llm kernel 可嵌套**：C-47 說轉交給有權 kernel 的算 kernel，但「建議不要濫用」；N-42 規定兩種 kernel 不併；llm kernel 對每封信都請 daemon 掛 proc，信寄 `$AOS_KERNEL`／`$AOS_DAEMON`。嵌套時上層看不看下層的用量，會碰到 C-52（不認身份、只認公開介面）。
6. **重複任務長出專精 agent**：C-46 規定定義**呼叫時不變**，`self_tools` 的漂移只在 stack；`agents new` 已經能產出新定義；待定稿的「函數成長」0～5 級是另一條成長規則；記憶寫入規劃是出廠庫不給 agent 寫；N-53「agent 自己不數連錯」，計數交給外面；沙箱稿說 self-improve 預設關。

### 本題另補的條文與規矩（上面摘錄沒寫全的）

- **C-71 註（11-06）**：「嚴格來說，沒有庫、子庫之分，資料夾、子資料夾、檔案，本來就是一種資料庫、記憶庫。」——層級式記憶工具 `memory` 就照這個做（指到哪個資料夾，那就是根）。

## 5. 隊長看到的張力（只指出、不設計；判斷交給你）

1. **原文會變 vs 逐 byte 綁定**：`source.json` 綁 `sha256`、lint 要求 `"\n".join(paras)` 逐 byte 等於原檔；語料每批會改導航檔（INDEX、character_map），人物詞條也可能被補段。原文一改，段號可能位移，所有 `節點#/paras/N` ＋ `at` 連結跟著失準。git 本身有歷史（語料 repo 有 198 commits；最後一個 commit 是 2026-09-05，但工作樹另有 146 個未追蹤草稿、四池還有 70 人是草稿，下一段從第 144 批起），知識庫也在 git 裡（試驗場 playground-ak 是一個 git，節點靠 `place_run --commit` 逐節點提交）。
2. **名字空間**：`names.tsv` 現 46 筆，全庫人物 686＋幹員 398＋…；92 個名字跨類同名（夕在 characters、operators、character_deep_dive）；43 個單字名一律交 LLM 裁；kb_mentions 把 evidence 子檔的結構性檔名（基本資訊 159 次、關鍵關係 148 次）也當候選名。slug 只在同 class 內唯一。
3. **連結數量**：婆山鎮 5 段就 16 條連結（9 條指夕），全 pending；全庫照這密度會是數萬條，且 `retarget` 要掃全庫 links.json。使用者說「別濫用」。
4. **tag 只放機械抽出的**：現在只有 `class:`、`group:`（INDEX 分組小標）兩種；語料本身沒有 tag 欄，events 有「分類」欄、operators 有「檔案」欄（出身地、種族）。aos 本體 `memory` 沒有 tag、沒有索引，`find` 是即時 `grep -R` 全文單一字串、截 20 筆、無排名。
5. **索引檔 vs 節點大小**：別名分片 40 地點就用掉 7,595／8,000 bytes；全庫的名字表、tag 索引、反向連結表都會遠超 2 KB 建議、8,000 bytes 硬限；wf 有「>1 KB 同質條列走 .json／.csv」的習慣，aos 本體沒有。
6. **兩個試驗場的庫不同**：問答原型掛的是第一輪改寫版 `kb-ak`（40 個 .md 節點、有 `## facts`），不是現在照原文存的 `kb-ak2`（2 個節點）。問答 agent 在「照原文存」的庫上還沒測過；它主要直接 grep `lore/` 原文。
7. **「給人看」那層會不會變成第二份真相**：白話庫是 LLM 產物，會漂移、會錯（問答錯的兩題都是多實體／立場題、查得越久越錯）；原文庫是唯一真相。
8. **層的歸屬**：哪些東西屬 aos 本體（`memory` 認 tag？反向連結？多庫？），哪些屬 arknights 這條線的定義（名字表、別名、linker），C-52 要求本體不知道上層的格式。
