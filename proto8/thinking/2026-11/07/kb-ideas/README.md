## 原話（11-07 午後）

1. （11-07 午後）「hmmm，首先是路徑，就是說假設某筆資料與另一筆資料有所關聯，那可以用a/b#/c/1這種方式，不止包含檔案路徑也包含json路徑。」
2. （11-07 午後）「然後我覺得，一次可以不用先找一大堆資料開始做，我們可以先挑一個地點，把這個地點的資料儲存做好，看看其資料結構有哪裏可以改進的，比如有一些連結到人物或事件的，或是弄一些小函數用於透過連結找到目標，或是解除連結，或是建立連結。一個地點一個地點去做。」
3. （11-07 午後）「一輪就做了40個條目？太多了，難怪會出問題。我們就一個一個慢慢做，一邊做一邊改進整個體系。然後還可以嘗試從gpt-sol降到terra，看看錯誤出在哪，再去思考是否一些環節可以做成工具或是定死成函數，也就是把困難的地方先用聰明的模型搞定，笨模型就可以玩流水線了」
4. （11-07 午後）「或者說，一次做一條這件事，只是表象，重點在於"格式檢查不是目標"，目標是這個產出資料條目的過程，他的成本要盡量低。把user-advice我昨晚寫的那篇丟進去給fable，跟他說，優化目標就是一個任意的json value，object/array/value都可以。並且這個值還可以細節化，比如成本用美金去算，那就是cost:0.01，但也可以變成cost: {val:100, unit:token}，乃至於cost: {money:0.01, time: 15s, token: {in:100,out:100}這樣」
5. （11-07 午後）「好吧，優化目標這件事可以以後再說。只是說我們這邊在定函數的metainfo的時候，可以用這套。除此之外，函數定義中的metainfo，是函數自己宣稱的。並且這東西有時候是推估的，因爲會隨着input不同而變化，比如面對較多的input string length，那其成本自然有變化。ps.可以將成本寫成equation: cost: {"cal": "x*2"}。然後agent或函數也可以自己宣稱，在他自己的視角來看，某個工具或函數，其metainfo是啥樣的，這可以是在函數呼叫過程中自己統計的」
6. （11-07 午後）「然後知識庫一多，查詢起來就費勁。可以加上一些tag啥的。然後先前說的連結那塊，盡量別濫用。」
7. （11-07 午後）「然後是一些老生常談：不要給agent太多上下文，只給他頂層簡介和目錄(可以的話盡量少)，讓他自己透過記憶工具去資料庫搜，還有一些工具讓他去原文找目標(當然，會給些初步指引)。不要把事情都堆積給一個agent，盡量分派，並且可以嵌套分派，也就是大任務拆成小任務後繼續拆，並且善用thought工具，減少對後續有影響的無用上下文。弄一弄之後會發現到說有些任務一再出現，就可以弄一些專精負責這塊的agent定義。一項地點弄好後，可以稍微停一下，審視一下自己的所作所爲，改進一下，把一些常用的函數寫成工具或程式。做出來的工具或程式包括起新agent或呼叫其他agent，改進的時候，這些被影響到的子函數自然也可以一起優化，好比神經網路的反向傳播。這種改進行爲我會特別關注。」
8. （11-07 午後）「我希望這輪增加一百個agent，並且每個都不要太同質化，不要只有prompt相似，要有獨特工具，獨特設定與記憶。好了，可以交給fabel了。我去睡個午覺，半小時後回來。」

## 使用者對 fable 四題的裁定（11-07 午後，選項框）

fable 規劃 [09 §七](../arknights-kb/09-第二輪規劃-fable.md) 的四題：

1. 一百個 agent 是硬目標還是方向：「方向，不湊數」。
2. 原文能否存成逐段陣列（內容仍逐字）：「可以，存成逐段陣列」。
3. 成本單位：「token／呼叫次數／秒」。
4. 降級階梯（沒有 terra）：「去幫我加terra，加好了跟我說，我去重啓litellm」。
