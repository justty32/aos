## 0. 題目、規矩與產出要求

### 0a. 題目（請求信原文，aos-a0 寄，11-07 下午）

使用者原話：「交給llm kernel的thinking請求也有排程，並且thinking請求還可以經過一些額外關口，比如一個隊伍使用一個llm_kernel，然後這個llm_kernel負責排程與將請求轉交給另一個llm_kernel，直到轉交給實際打API的llm_kernel，一切都可以嵌套。」

> kernel 嵌套怎麼做才乾淨：隊伍 kernel → 轉交 → 實打 API 的 kernel。要想清楚：①轉交時的記帳（第一輪實測「轉交後上層讀到 0 token」，第二輪 P1／P2 剛加了 usage 回傳與逐封 ledger）；②各層排程與優先權（判官排隊、`reserved` 留格、`keep_ordered`、寄件者逾時）在嵌套下怎麼疊；③時間成本（使用者 11-07：要把時間算進成本，含排隊）；④**本機 LM Studio 同一時間只能載入一個模型**（使用者硬規矩）——這是 kernel 層的排程限制：要不要由「本機那顆 kernel」按模型批次排、換模型的成本怎麼算；⑤嵌套下的失敗與逾時怎麼往上報（C-52 每層只說自己的）。

同批另外三題（碰到就寫一句「交給 X」帶過，不展開）：
- **evolve-design**：aos 怎麼支援「反向傳播式自我改進」（metainfo 自我宣稱／他者觀測、成本 JSON 值、專精 agent 長出來）。成本 JSON 的**通用格式**歸它；本題只管 kernel 這層記什麼、怎麼往上帶。
- **kb-scale**：知識庫全庫規模與「給人看」的那層。
- **tool-evolve**：工具權限演進（shell 開放→謹慎→專屬工具）與確定性的量測。

### 0b. 規矩（給 fable 的提醒）

- **大方向是使用者的**（鐵律 5）：嵌套這件事他已經定了要做；你做的是在他定好的路上把細節設計乾淨。要帶回給他的只有兩種：新設計跟既有原則的**衝突**（哪條、衝突在哪、各自後果），以及原則推不出答案的**方向題**（選項＋後果＋推薦）。
- **KISS 是最高也是最後原則（C-56）**；**巢狀每層只管自己（C-52）**：不認身份、可認公開介面；上層不知道下層是什麼。條文原文見 §5。
- **proto8 不寫舊版遷移、不做舊格式相容**（使用者 11-05）。
- 程式輸出（訊息、落檔文字、log）一律英文；文件繁中。命名：全小寫加底線，計數 `counter_*`、時間點 `*_at`、上限 `max_*`、時長帶單位後綴（`_ms`、`_s`）。
- gpt 系模型之後只照圖施工，所以落地步驟要寫成「照圖就能做」的小步。
- 你只讀這份簡報；不改其他檔、不 commit。

### 0c. 產出要求

寫到 `02-fable規劃.md`：第一行一句話標題；然後
1. **白話總結**——給使用者讀：完整句子、一段一個重點、術語第一次出現用日常比喻帶過、不要編號互引讓他查表。
2. **設計**：概念、機制、資料格式（JSON 例子）、各層誰負責什麼。至少回答 0a 的 ①～⑤。
3. **衝突**：哪條、衝突在哪、照新設計 vs 照舊條文各自的後果。

5. **落地小步**：每步一句完成條件。

### 1a. user-advice/20261106.md（使用者指定全文給 fable）

寫於2026/11/06的深夜

我認爲這是the new age of programming。
lisp仍是最終最好的抽象，那爲啥大家都不用？我不知道，但是對我而言，就是debug不方便，並且沒辦法控制底層，因爲我是從C++起家，深入其template meta programming，浸淫已久。我知道lisp的meta programming更好更方便，但是...好了，總之閒聊到此爲止。
OK，那我覺得我這套體系能解決這個問題。
我們把filesystem作爲lua來使用，一個簡單的手段就是準備一個程式aos-exec，這個程式可以把資料夾當做檔案來執行，只需要資料夾內有一個_entry檔案即可。第一個好處就是能夠白嫖linux的檔案權限機制，其次就是能夠跨程式語言實作功能。不過最重要的，是agent原生就有操控資料夾的能力。
如果想要用lisp實作agent，並讓agent自己修改自己，那就是在lisp執行中跟agent說，請做這個做那個，你得把lisp相關東西抽象給agent，並且還要要求agent寫lisp程式，這是有風險也比較麻煩的。不過話說到這裏，好像這也是可行的，齁齁，之後有空來做做看。
不過我要說的是，相比跟agent說：這個list就是你，請你修改自己。不如直接把一個資料夾跟幾個python程式和json檔案交給agent，跟他說這就是你，請你新增一個資料夾，裏面弄一個新工具，然後給你自己做擴充。這其實agent更好懂，並且也能輕鬆完成。甚至還可以利用到python的各種wheel。不過說到這裏，好像lisp也能做到，之後來試試看吧。
OK，總之，我這邊要強調的就是檔案系統之於LLM的原生理解性與原生可操作性。
而在這個基礎上，我們實作了aos loop/fsm agent。秉承unix哲學與傳統，沿襲plan9理想，各種東西都盡量以檔案表示，其本體程式盡量簡短。

然後是忘記誰說的(應該是andrew karpathy)，agent就是一個函數。我覺得他觸摸到了本質，而我要替他進一步闡述。agent作爲函數，其pseudo code應如下：
func agent(llm, prompts, tools):
    while 1:
        if has_tool_call:
            do_tool & break
        elif has_prompt:
            add_prompt & break
大約如此，其中的llm就是大語言模型的api呼叫，而prompts則是一個[]string，可以在外部或內部增加或減少東西，至於tools，那就是一些丟進去的外部函數。假如沒有tools，那這個agent函數只能針對[]string做增減，但有了tools，那根據丟給他的東西，這個函數就可以做到任何事。

然後是比較跳躍性的聯想。一個cpu所做的事情可以想成以下pseudo code:
func cpu(insts):
    while 1:
        exec insts[counter]
        counter++
假設這個insts就是一個fsm機器，持續去跑先前那個agent的幾個狀態，比如呼叫llm中，執行工具中...等，那agent就可以拆成一個loop加上一個fsm。而這個loop就可以類比爲cpu。
既然有了cpu，那自然要考慮到其運行在哪個硬體上。在我們這個aos體系中，agent是一個持續執行着fsm的loop程式，通常情況下，他就是一個linux proc。但這樣子的proc一多，就很麻煩。
通常來說我們會將其交由另一個程式管理，所以有了aos daemon。既然我們將其比喻爲cpu，那daemon自然就是硬體了，他是一個可以自由增減cpu核心的嵌入式單板。爲何說是嵌入式單板？等以後daemon的功能一多，那自然就是主機板，乃至伺服器主機了。
後續的比喻就不多說了，總之在這個比喻下，我們有了aos-exec/loop/daemon，分別對應cpu指令/cpu/硬體板子。

有了板子與cpu，下一步，就是作業系統了。在我的想象中，作業系統就是硬體上的一號行程，具備最高權限。而其作用，或者說目標，就是輔助人類更好的使用硬體，具體作用方式就是管理與排程其他行程，以及分配各種資源，還有權限上的管理等等，不一而足。
而在此之上，我先規劃了aos kernel，這是aos的核心，其回歸本質，以幫助人類更好的使用硬體爲目標。
這裏說的硬體，並非是物理世界中的電腦，而是aos exec/loop所仰賴的各種東西，首先看到的就是linux系統，除此之外還有一些抽象的概念。而更好的使用，相比linux這類普通作業系統相比，其意義也更加廣泛。
linux等普通作業系統，其優化目標以時間，資源消耗最小化爲主。但在agent時代，還有其他目標如token用量，人類可理解性，易操作性等等。所以aos系統的目標就是優化任意目標。
到了這裏，我們就有了很好用的工具。
ps.aos kernel被設計爲一號行程，但實際上，我們在aos體系中標明，任何管理行程與資源的行程，都可以用kernel做稱呼，只是說標準實作上我們提供的kernel通常都是一號行程，占有對於某個daemon的唯一控制權。

下一步，是這工具可以用在什麼地方。
既然可以優化任意目標，那我們可以將目光放在一個LLM agent的痛點上：不確定性。
不確定性，其本質就是脫離掌控的程度。倘若脫離的目標是客觀世界，那就等同機率性。其他的，可以是對於人類而言的不確定性，可以是對於你我他任何一個特定人的不確定性。
除此之外，脫離掌控的東西也可以任意的，比如token消耗的程度之類。
而我想要的，就是讓agent可以完全隨我心意去做。常規做法，以先前那個pseudo code所描述的模式來說，就兩種，一種是prompt engineering，另一種是對工具做操作。
這裏不多做贅述，總之要達到完全隨心意這點，有很多方式。
我要做的，是用RSI的方式，使其隨我心意。而我窮，且又看不得AI如此之笨，所以我要做的事情可以這樣描述：
在aos體系的幫助下，實現以RSI方式，持續降低token消耗直至0，並且提升AI智商的路途。

雖然現在仍在給aos體系打基礎，但我可以先簡單起個頭，說明我想怎麼做：
我想讓agent完全隨我心意去做，等同於我想讓這個函數的一些屬性達到一個目標。
那麼一個函數可能有啥屬性？最基本，四處都通用的就是這個函數九軸特性。
這個函數屬性，他是相對於檔案屬性的，一個是動態一個是靜態。真要細說的話，那其實可以是維度上的區別，檔案屬性，就好比物體的長寬高，很容易理解，而函數屬性，則描述了時間軸上的區別，乃至於世界線上的區別(機率)。
除此之外，屬性這東西，除了客觀也還有主觀。應該說，有光才有影，有了相對才有存在，所以你要找一個參照物作爲你的值的基準，對於物體而言，其參照物就是現實物理規律，而函數九軸的參照物則是現實公理基礎。
那假如其基準，是一個抽象化的東西，或者說，乾脆就是人的主觀認知呢？比如一個用agent產出galgame臺詞的函數，對於我這個臭宅男來說，這個函數的臺詞傲嬌程度就是0.4。並且也不一定要是值，甚至可以是一個字串或json物件，比如"缺乏靈活性"、{"pretty":12, "good":true}。

講完了函數屬性的性質，接下來講如何優化他。
一個函數可以拆分爲多個子函數，這個函數的屬性自然由這些子函數決定。所以假如這個函數是機率性的，自然只要將其具備子函數中具備幾率性的，給替換掉即可。
換到agent中，從pseudo code中可以看到，不確定性來自於那個llm呼叫。要降低這個函數的不確定性，自然就是減少llm呼叫，盡量讓工作都堆積到tools。
好比一個生成llm臺詞的任務，常見的做法是只走prompt engineering，tool只給基本的read/write/shell等，讓llm自己去查相關背景。想要提高確定性，那就是稍微改一下，將臺詞拆成景色描寫與人物對話，景色這塊可以用工具找固定描述，人物對話這塊可以透過工具，將需求丟給專管各人物的各agent，讓他們生成。

好，我這邊做個收尾
既然可以優化任意目標，那，是否可以將目標設置爲：提高智能，以及，提高"提高智能"的速度？
RSI的飛輪，自此而始
ps.其實AI不笨。只是說AI缺乏持續學習之類的，並非死記硬背的智能面向。

## 2. llm kernel 現行機制（`proto8/impls/aos-llm-kernel/` docs 01～04 摘要，opus 讀原文整理）

比喻：醫院掛號櫃台。候診室（信箱 `requests/new/`）每張掛號單寫要問什麼、找哪位醫生（代號）、急不急；櫃台每 300 ms 看一眼，先把看完的結果寄回，再照優先序叫號，診間（`slots`）空幾間叫幾個，叫到的交給院方（daemon）排進一間診間（問腦 proc），櫃台不站門口等。

- **形狀**：`aos-llm-kernel kernel.json` 是 daemon 的身體，每拍跑一次就結束。寄信方用 `aos-llm send／recv／ask／regret`；`AOS_LLM_KERNEL`＝kernel 的 stack，信箱固定在 `$AOS_LLM_KERNEL/requests/`。
- **信**（`letter.json`）：信封 `sender`（寄件人身分＝`$AOS_WS` ＞ `$AOS_STACK` ＞ `$AOS_CF` ＞ cwd，**不驗**）、`sent_at`、`reply_to`；body＝`{"endpoint"?: 代號, "request": OpenAI chat body, "priority"?}`。`priority`：`"low"/"normal"/"high"`、數字、或 `{"level", "deadline"}`（deadline 帶時區 ISO 8601 或 epoch 秒，牆鐘）。只有同步 `ask` 會建 `sender.flock`，kernel 用它判「寄信的人還在不在」，不在就不白跑。
- **回信**：`{"message", "usage"?, "model"?}` 或 `{"error": {"code", "msg"}}`。寄完整封信刪掉，不留請求原文。
- **kernel.json 重點欄**：`slots`（總在飛數）、`reserved: {"high": N}`（留 N 格給宣告 high 的信；aging 升上來的不算；不搶占）、`aging_ticks`（預設 3）、`exec`（預設 endpoint 函數）、`endpoints`（代號→能力包）、`endpoint`（預設代號）、`timeout_ms`（跑一封的上限）、`budget`（`max_calls`、`max_tokens`、`window` hour/day/all、`spent` refuse/wait、`senders.<寄件人>`）。
- **能力包**（一個代號）：kernel 看的四鍵 `exec`／`slots`（這包同時幾封在飛）／`budget`／`speed`（fast/normal/slow）；其餘（`url`、`model`、`fixed`、`cost`、`context`、`summary`、任意 key）原樣交給 endpoint 函數。信撞 `fixed` 或包已釘 `model`＝`RequestBad`；換模型＝換代號；包額度到頂＝`BudgetMissing`、**不替人降級**（使用者 11-05 已裁）。窗 `endpoints.json` 給人與腦挑代號（含 `speed`、`cost`、`context`、`slots`、`summary`）。
- **排序**：級數＋`waited_ticks / aging_ticks` 大的先 → deadline 近的先 → 包的 `speed` → 等得久 → 先寄。不搶位；包的 `slots` 滿＝跳過看下一封（別包補位）；kernel 額度 `wait` 時停整列，包／寄件人額度 `wait` 只擋那封。
- **跑一封**：認領 `new/`→`cur/<信>/`，寫 `request.json`＝`{"endpoint": 那包（去掉四鍵）, "request"}`；寄掛信 `procs_added: {"llm_<信>": {"exec": {"argv": ["aos-exec", <exec>], "cwd": <信>, "stdin": "request.json", "stdout": "reply.json", "timeout_ms"}, "max": 1, "stack": <信>}}` 到 `$AOS_KERNEL`（沒設＝`$AOS_DAEMON` 的 ctl 信箱）；寫 `proc.json`（`endpoint`、`sender`、`mounted_at`、`retries`）。下一拍看 daemon 表與 `state.json` 收：退 0 且 `reply.json` 讀得懂＝原樣回信；退非 0＝`EndpointFailed`＋`reply.json`／`stderr.txt` 第一行**原樣**（C-52 例外 ③）；143／137 且超過 `timeout_ms`＝逾時 `EndpointFailed`；被收／半路死＝重掛一次，再死＝`EndpointFailed … ran twice without a result`。
- **endpoint 函數契約**：stdin `{"endpoint", "request"}` → stdout 一行 `{"message", "usage", "model"}` 退 0；錯退非 0、stderr 一行。環境＝daemon 給子項的（不是 kernel 轉交的）；金鑰歸端點小 proc。**注意：endpoint 函數的 stdin 不含信的 `priority`、`sender`、信名。**
- **用量**：`usage.total_tokens`（沒有就 prompt＋completion；沒 usage＝token 記 0 只算次數）。`used.json`：`{"window","since","counter_calls","counter_tokens","counter_all_*","packs":{代號:{...}},"senders":{寄件人:{...}}}`。到頂判法：`counter_calls`＋在飛＋新掛 ≥ `max_calls`，或 `counter_tokens` ≥ `max_tokens`（token 事後才知，會超一點）；判序 kernel → 包 → 寄件人。掛過的才算一次（`EndpointFailed`、`ReplyBad` 算）。
- **逐封帳 `ledger.jsonl`**（P2）：每封收尾追加 `{"id","endpoint","sender","model","mounted_at","finished_at","elapsed_ms","usage"}`；錯誤回信也記，沒掛過的不記；kernel 不輪替；可能缺行或重複行（用 `id` 辨識）。**`elapsed_ms` 從掛上算，不含在 `new/` 排隊的時間；沒有狀態／錯誤碼欄。**
- **已知限制裡和本題相關的**：排程刻意不做搶位（「HTTP 一刀砍掉錢已經花了」）、信裡 `max_cost`／`max_wait_ms`、包到頂自動降級；`reserved` 不保證立刻開跑；起 llm daemon 的殼別設 `AOS_KERNEL`（否則問腦 proc 掛錯台）；睡醒或 kill -9 可能多花一次腦（風險自擔）。
- **範本裡的本機包**（`proto8/kernel/llm-kernel/kernel.json`）：`"stupid-fast": {"url": "http://localhost:1234/v1", "model": "qwen3-1.7b", "fixed": {"temperature": 0.7}, "slots": 1, "speed": "fast", "cost": "free", "context": 4096, "summary": "LM Studio qwen3 1.7b on this machine: quick and rough, one at a time"}`——`slots: 1` 只限**這一包**；兩個指向同一台 LM Studio、不同 `model` 的包，各自 `slots: 1`，kernel 會讓它們同時在飛（現制沒有「同一後端只能有一種模型」的表達）。

## 4. 各層排程現況（判官、reserved、keep_ordered、寄件者逾時、路由；備料員唯讀盤點）


縮寫：OI＝`proto8/thinking/2026-11/06/os-impl/`；KD＝`proto8/kernel/docs/`；LK＝`proto8/impls/aos-llm-kernel/docs/`；DD＝`proto8/impls/aos-daemon/docs/`；J＝`proto8/lib/aos/judge/_entry`；SOL＝`wf/workflows/refactor/reports/2026-11-07-sol審查/11-使用者裁定.md`。

### 4.0. 三種角色一句話

- **daemon＝板子**：只有一條路能掛 proc——往它的 ctl 信箱（預設 `$AOS_STACK/procs_ctl_mailbox/`）寄一封 `procs_*` 信；每圈收信、套進名單「底」、對表、回 `{"applied": true}`。它本身不排隊、不看優先權。（DD/05）
- **判官（judge）＝唯一的「掛不掛」kernel**：同一支 `lib/aos/judge` 兩種擺法——模式 1 當 daemon 的身體（阻塞、跑在 daemon 那一圈裡）、模式 2 當 daemon 底下一個 loop proc（0 號，自己也算一列 running）。只管一種資源（running 格）、一種順序（FIFO）。（KD/02、OI/03「跟 N-42 的界線」）
- **llm kernel（aos-llm-kernel）＝問腦總機**：daemon 的身體；每封問腦信請 daemon 掛成一個 `llm_<信名>` 的 `max: 1` loop proc，下一拍收成品。它才有優先序（級數＋aging→deadline→speed→等得久→先寄）、slots、reserved、budget。（KD/01、LK/02）
- N-42「兩隻 kernel 不併」：判官隊列只有先來先掛；要優先序／期限／額度＝寫一個 kernel 身體（llm kernel 是範例）。（OI/03）

### 4.1. daemon 收掛 proc 信 與 判官排隊

### 1.1 daemon ctl 信箱（DD/05）
- 每圈：`aos-post take-all` 認領 `new/`（有序信先、再照信名）→ 逐封驗、依序套進底 → 疊 procs_ctl → 對一次表 → 有 `reply_to` 的好信回 `{"applied": true}`（`in_reply_to`＝原信名）→ `done`。
- body 只認 `procs_added`／`procs_removed`／`procs_stopped`／`procs_started`（11-05 起另有 `procs_woken`／`procs_slept`，見 J 檔頭）、`{"ping": true}`；其他 key 忽略（C-48）。
- **paused／stopping 那圈不認領＝不回**；壞信丟掉、不回，原因寫 `procs_state.json` 的 `mailbox_warning`。
- **`applied: true` 只表示「信已套進名單」，不表示那列還在跑**（OI/09 根因 3，`mailbox.cpp:144-146`）。

### 1.2 判官政策檔與判法（J 檔頭、KD/02）
範本 `proto8/kernel/daemon-judge/judge.json`：
```json
{"allowed": ["clock","clock2","fsm1","kid","kid1","kid2","kid3","kid4"], "max_running": 4, "queue": true, "keep_ordered": false}
```
模式 2 範本 `proto8/kernel/procs-kernel/judge.json`：`{"allowed": ["clock","clock2"], "max_running": 2}`（含 0 號自己）。
- `allowed`：名字白名單，null／沒寫＝不限；只判 `procs_added`。
- `max_running`：數 `$AOS_DAEMON/procs_state.json` 裡 phase running 的列＋本輪已放行＋這封的新名字；`procs_started`／`procs_woken` 也算新名字（不再判 allowed）。表上 `_tick`（daemon 自帶時鐘 proc）也算一格。
- stop／rm／sleep／ping、不認的 key：原樣立刻轉（騰格的信不被隊首擋）。
- 不掛：回 `{"applied": false, "error": {"code": "...", "msg": "..."}}`；代號 `NameUnknown`／`SlotMissing`／`BodyBad`／`ForwardFailed`；判官 stderr 一行 `judge: warning: letter <名> refused: 代號 原因`。信沒 `reply_to`＝只收掉。
- 掛：body 原樣轉進 daemon ctl 信箱，daemon 直接回 `applied: true` 給原寄件人（判官不轉手）。
- 模式 2 已知限制：轉了、daemon 還沒套的「在飛」不算 running，連寄可能多放幾個；模式 1 無此問題。（KD/02）

### 1.3 `queue`（排隊）（OI/03、OI/06、KD/02、J）
- 程式沒寫＝`false`＝滿格立刻 `SlotMissing`；範本開 `true`（SOL #1，11-07）。
- 只有要格的 add／start／wake 會排；**信留在 `$AOS_STACK/requests/cur/` 不 done**；FIFO，不認 `priority`、不 aging；隊首格不夠時後面要格的不插隊。
- 排隊中**不算 running**；不回「queued」信（一請求一回信，N-66）。
- 窗 `$AOS_STACK/queue.json`：
```json
{"queued": [{"letter": "<信名>", "names": ["clock2"], "queued_at": "2026-11-07T01:02:00.208Z", "queued_at_ticks": 123, "expires_at": "..."}]}
```
  陣列順序＝順位；`queued_at_ticks` 有 `AOS_TICK` 才寫、`expires_at` 信有 `queue_wait_ms` 才寫；只在進隊時記，每輪重用。窗讀不懂＝warning、當空窗、從 `cur/` 重排（SOL #2、#5）。

### 1.4 對照：llm kernel 的 `queue.json`（不同形狀）（LK/01）
```json
{"counter_runs": 42, "seen_at_ms": {"<信名>": 1794013299459}, "seen_at_ticks": {"<信名>": 120}}
```
- `seen_at_ms` 一律寫、`seen_at_ticks` 有 `AOS_TICK` 才寫；只留還在排的。排法＝優先序，不是 FIFO（C-54 R14，11-06）。
- `waited_ticks`：有時鐘且信有 `seen_at_ticks`＝現在 tick 減它；否則 `(now_ms − seen_at_ms)/AOS_TICK_INTERVAL`（預設 1000）。每 `aging_ticks`（預設 3）升一級、不封頂；時鐘凍住＝不升級。（LK/02 第 5 步）
- **排隊時間記在「收件那一層」第一次看到信的時刻**，不是信封 `sent_at`；判官的期限卻從 `sent_at` 起算（見 2）。

### 1.5 `keep_ordered`（SOL #3，11-07；OI/03 補註；KD/02）
- 選填布林，沒寫／null＝false；其他值 `CfgBad`。
- 關：有序信（名字 `^[0-9]{12}\.`）用尾名當一般信轉寄、保留原 `reply_to`；**經判官不保有序**，daemon 回信 `in_reply_to` 是尾名，對不上原信名——要對上就寄一般信。
- 開：`--ordered` 轉寄；有原 `reply_to` 才改指 `$AOS_STACK/judge_replies/`，`judge_ordered.json`＝`{新名: {"letter": 原名, "reply_to": 原回信箱或 null}}`；每輪先領回信、查表、用原名代回，成功才刪列。
- 已知（edge-1107 E2）：對照表寫壞＝每輪退 1 `StateBad`、回信卡住；重送 bug 11-07 已修，仍留兩個當機窗口（重送一次／回信重轉一次）。（`proto8/thinking/2026-11/07/edge-1107/README.md`）

### 4.2. 寄件者自設逾時（OI/05、05-續、05-續2、06）

| 項 | 事實 |
|---|---|
| 寄件人等多久 | `aos-agent ctl add／rm／stop／start／sleep／wake --timeout-s S`，**秒**，預設 30，>0、不設上限；由 aos-agent 自己用 `time.monotonic` 數 |
| 等滿算什麼 | add／start／wake 另有 `--on-queued fail｜ok`，預設 `fail` |
| 信裡期限 | `fail` 時 body 加 **`queue_wait_ms`＝S×1000（毫秒）**；`ok` 不加＝可能永遠排著（SOL #4） |
| 誰數期限 | **判官**：每輪先查 cur 裡所有帶 `queue_wait_ms` 的信（`queue: false` 也查），從信封 **`sent_at`** 牆鐘起算；轉寄前再查一次 |
| 排隊時間算不算 | **算**：期限從寄出那刻算，含在信箱裡等判官、在隊裡排的全部時間 |
| `0` | 不排；有格照轉、沒格立刻 `SlotMissing`；非負整數以外＝`BodyBad` |
| 到期 | 不轉、`done`、回 `{"applied": false, "error": {"code": "SlotMissing", "msg": "queued N ms, no slot freed (queue_wait_ms M)"}}`；「判官拿到時已過期」也一律 `SlotMissing`（OI/06 代定 1，不加新代號）|
| daemon 收到 `queue_wait_ms` | 忽略（其他 key 忽略），判官不刪欄 |
| 鐘 | 牆鐘；凍住醒來首輪已過期的一起拒（SOL #6；edge-1107 E3 實測 7.2 秒凍住、5～6 秒期限三封首輪全拒，ok 那封照排） |

aos-agent 等滿當下（OI/05 表、OI/06）：
- 已收回信＝照回信；`applied: false`＝立刻報 `AddRejected`（start／wake 被擋＝`CtlRejected`），不等滿。
- 信在 `queue.json`：`fail` 再等 `REPLY_GRACE` 1 秒收判官拒信（收到＝`SlotMissing`）；`ok` 印 `queued NAME at position N (letter L; applied when a slot frees)`、退 0。
- 都沒有：先 `aos-post regret` 撤信，再報錯。11-07 起（SOL #28）：沒設／資料夾不在＝`DaemonMissing`；有 daemon 但沒回＝`DaemonFailed … letter withdrawn` 或 `… could not withdraw it; it may still be applied`（edge-1107 E5）。
- **撤不回的競態**：信已轉進 daemon ctl 或已被 daemon 領走就撤不回，可能報失敗後仍掛上；直接 ctl／繞過判官不受判官期限保護。（`proto8/cmd/aos-agent/docs/02-已知限制.md`）
- 晚到回信留共用信箱 `$AOS_STACK/daemon_reply/`（人殼＝`<daemon stack>/procs_ctl_mailbox/reply/`），10 分鐘後由下一個開箱者收掉。（同上）

腦（lib `agents` 工具）：`ctl_timeout_s`（預設 30、上限 1700）、`on_queued`；保險 `max(90, ctl_timeout_s+30)`。已知限制：ok 排隊的孩子之後被拒，工具沒收拒信，`max_children` 配額一直佔著。`thought` 不開 `on_queued`（固定 fail、30 秒）。（OI/05、OI/06 代定 3、4）
- `max_children` 只是 agents 工具自己的配額；**整台 daemon 同時掛幾個只靠判官 `max_running`**。（OI/06 P9 裁定 3、KD/02）

人殼 `aos-daemon-ctl`：寄信子命令 `--timeout-s`（預設 3，＝等信被**認領**，不是等套用；與 `--reply-to` 互斥）、pause／resume `--timeout-s`（預設 5）。`--queue-wait-s` 11-07 已拿掉（直寄不經判官，留著無作用）。（OI/08）

llm kernel 那層的對應物：寄件人在 body 寫 `priority.deadline`（帶時區 ISO 8601 或 epoch 秒，牆鐘，N-65 ③）；輪到前已過＝回 **`DeadlineBad` "deadline passed before its turn; not run"**（`proto8/impls/aos-llm-kernel/src/serve/scan.cpp:116`；OI/05 文中寫 `DeadlineMissed`，與程式不符）。aos-llm 自己不管等多久（`proto8/impls/aos-llm/docs/01-用法等.md:29`）。kernel.json `timeout_ms`（範本 120000）＝收信者自己跑那封的上限，逾時＝`EndpointFailed`。

### 4.3. 路由：`AOS_KERNEL`／`AOS_DAEMON`、C5 留格

- **`AOS_DAEMON`**：daemon 起任何子項（含自己的身體，11-05 起）都把它設成 daemon 自己的 stack、一律蓋過；蓋前把繼承到的值記進兩扇窗頂層 `daemon` 欄（null＝根 daemon）。（DD/05）
- **`AOS_KERNEL`**＝「要掛 proc 往哪寄」：沒設＝寄 `$AOS_DAEMON` 的 ctl 信箱（模式 0）；模式 1 設 `<daemon stack>/requests`、模式 2 設 `<0 號 stack>/requests`；可由人設或寫進 daemon 的 `.env` 帶給子項。（KD/02）
- 誰看它：
  - `aos-agent ctl`：看（經判官），stderr `aos-agent: warning: routing via AOS_KERNEL=…`；指不到＝`MailboxMissing`、不退回 daemon 信箱（SOL #8：退回會繞過判官）。不再從表上認誰是判官（K-3）。
  - `aos-daemon-ctl`：**11-07 起永遠直寄、不看**（OI/08）；實測直寄可繞過判官 `max_running`（表上 3 列 > 2）。
  - **llm kernel**：掛 `llm_<信名>` 的掛信寄 `$AOS_KERNEL`（非空），否則 `$AOS_DAEMON` 的 ctl 信箱（那台沒開＝`MailboxMissing` 退 1）。`AOS_KERNEL` 非空但 `<它>/new` 不是資料夾＝每行程每路徑一次 warning、照用原路徑、掛失敗回 `LaunchFailed`（OI/07、LK/01、LK/04）。文件明說「起 llm daemon 的殼別設 `AOS_KERNEL`」否則問腦 proc 掛錯台。
- 掛信形狀（LK/02 第 3 步）：
```json
{"procs_added": {"llm_<信名>": {"exec": {"argv": ["aos-exec", "<exec 絕對路徑>"], "cwd": "<信>", "stdin": "request.json", "stdout": "reply.json", "timeout_ms": 120000}, "max": 1, "stack": "<信>"}}}
```
  寄送用 `aos::post::send(box, body, SendOpts{})`（`src/daemon/daemon.cpp:85`），程式裡沒看到帶 `reply_to`；kernel 靠讀 daemon 表與 `<信>/state.json` 收成品。「表上沒列、state.json 也沒有＝daemon 還沒套，照樣佔一格」；`mailbox_warning` 提到這封＝`LaunchFailed`。（LK/02 第 4 步）
  - **由此推得、未實測**：若 llm kernel 的 `AOS_KERNEL` 指向一個判官，`llm_*` 名字要在 `allowed` 裡、且算進判官 `max_running`；被判官拒時判官因無 `reply_to` 只收掉＋stderr 一行，llm kernel 看不到拒信，依上句會一直當「還沒套」佔格。
- 另一個未實測連帶（OI/09）：`aos-daemon-ctl add <agent 定義資料夾>` 跑的是它的 `_entry`（`aos-agent ctl add 自己`），內層 aos-agent 繼承 daemon 環境，若有 `AOS_KERNEL` 就**經判官**——直寄在這條路上沒直寄。使用者沒回應這條（照通則不處理）。
- 問腦另走 `AOS_LLM_KERNEL`，跟 `AOS_KERNEL` 各管一事；好幾台 agent daemon 可共用一台 llm kernel，頂層 `slots`／`reserved`／`budget` 是整台電腦共用。（KD/01）

C5 留格（OI/07；LK/01、LK/03、LK/04）：
- `kernel.json` 頂層 `"reserved": {"high": N}`，只認 high，N 非負整數且 < 頂層 `slots`；範本 `slots: 2, reserved: {"high": 1}`（SOL #7）。
- 宣告級數低於 high 的信只補到總在飛 `slots − N`；被擋的留 `new/`、繼續往後找 high（不停整列）；**aging 升上來的不算 high**；只管頂層 slots，不管端點包 slots；非搶占。
- 實測：兩封慢 low 佔格時 high 17.5 ms 掛上，無留格對照 3065 ms。
- 留格只在 llm kernel；判官沒有 priority、沒有留格。降優先權／釘核由 exec 包 `nice`／`taskset`，不新增 daemon 的 `limits.nice`（SOL #34-4）；`limits.nice`／`sched` 列為 C3 只規劃（OI/01-續）。

### 4.5. 跟「疊加／優先權／時間成本／失敗上報」相關的其他事實

- **兩種排隊各自獨立**：判官 FIFO（數 daemon 表 running）與 llm kernel 優先序（數自己在飛＋包 slots）沒有互相認識的介面；llm kernel 的在飛問腦是 daemon 表上的列，若同一台有判官就會吃判官的 `max_running`（推論，見 3）。
- **期限語意不同層不同**：判官 `queue_wait_ms` 毫秒、從 `sent_at`、牆鐘；llm kernel `priority.deadline` 絕對時刻、牆鐘；aging 用自己樹的 tick（沒 tick 退牆鐘）；`timeout_ms` 是收信者執行上限；寄件人 `--timeout-s` 是單調鐘。毫秒寫的跨樹期限一律牆鐘（N-65 ③；SOL #11 加註「格式不限」）。
- **時鐘停則一起停**：判卡住、鎖租約、tick 逾時（SOL #12）；但判官期限是牆鐘，不停。
- **時間成本記帳**：llm kernel 每封收尾追加 `ledger.jsonl`：`id`、`endpoint`、`sender`、`model`、`mounted_at`／`finished_at`（epoch 秒）、`elapsed_ms`、`usage`；重掛的 `mounted_at` 是最後一次；**不含進 kernel 前的排隊時間**（只從掛上算；排隊時間只在 `queue.json` 的 `seen_at_*`，信掛出後即移除）。（LK/02）agent-fsm 的思考觀測紀錄 11-07 加了信名 `letter` 可與 ledger `id` 對帳（commit 3281e6b65 訊息）。
- **額度**：kernel 總 `budget`、包 `budget`、寄件人 `budget.senders`（寄件人＝信封 `sender`，不驗身分）；`refuse` 回 `BudgetMissing`、`wait` 留 `new/`；不替人降級換包（C-56）。用量帳 `$AOS_STACK/used.json`。（LK/02）
- **失敗往上報的形狀**：一請求只一封最後回信（N-66，「進度看窗」）；daemon 不回＝寄件人自算逾時當呼叫失敗（no-pid「寄信不回＝呼叫失敗」）；判官拒＝`applied:false`＋代號；llm kernel 回 `{"error": {"code","msg"}}`，`EndpointFailed` 的 msg 原樣帶下層錯誤行（含 `程式: error:` 前綴，看得出誰錯）；問腦 proc 半路死＝重掛一次，第二次仍死＝`EndpointFailed … ran twice without a result`。不加新錯誤代號是既有代定（no-pid 代定 7）。（OI/06、LK/02）

### 5.7. 其他相關條（取自 evolve-design 備料的條文摘錄，原文節錄）

- **C-03** 由下往上依序是 Linux → daemon → 時空 → 排程與資源分配 → agent，上層只透過下層。**C-74 分層**：基礎層（核心＝aos-exec；loop、daemon）→ 標準庫（fsm、tasks）→ agent／kernel。分層講「誰依賴誰」，C-03 講「誰排程誰」，兩條軸不衝突。
- **C-48 JSON 格式族**：靠加 key 擴充；**不認得的 key 一律忽略、不報錯**；私有 key 不重疊即可共用一份檔。值的雙形：純值也可以寫成物件（展開形），原值放在 `val`（C-55）。指示詞只有 `$env`、`$ref`。
- **介面**（名詞附錄）：資料夾程式在頂層 `interfaces.json` **宣告自己遵守**哪些約定；用的一方只認宣告，不猜。
- **N-66 一箱一函數**：一個信箱後面接一個 aos 函數，body＝那函數的 stdin JSON；函數的 `_tooldef.json` 就是這箱接什麼的說明。一請求只一封最後回信（進度看窗）。
- **C-77** 開銷不算啥，能包成 aos 函數的盡量包：「LLM本身就是最消耗時間的。」**C-78** 啟動四步：複製、起 daemon、設環境變數（盡量少）、aos-exec 開跑；新東西若讓啟動多一步要標出來。**C-83** 可遷移性是上位原則。
- **C-80** 不在任何 daemon 下的不管。**C-81** stack 是 proc 自己的地盤，對外介面四類：命令列參數、環境變數、stdin/out/err/exit、信箱內容格式。
- **C-21** 可預測性有主體性，是觀察者的認識；**C-13** 確定性是任務自己的屬性。**`_metainfo` 待定稿**：「實測不回寫」。
- **N-53**：重試幾次由外面決定，agent 自己不數連錯。

## 6. 張力清單（只指出，不下結論）

### 6a. 條文面（備料員從條文看出的）


1. **轉交型 kernel vs 不知道下層是什麼**：C-47 明文說轉交給有權 kernel 的算 kernel（別濫用）；C-52 讀法「不認身份、可認公開介面」——隊伍 kernel 只能靠下層公開宣告（`requests/`、回信形狀、`endpoints.json`）分支，不能認程式名。
2. **跨層記帳 vs 不偷看**：C-52「沒機制就別碰」；現有公開機制只有回信 `usage`。讀下層 `used.json`／`queue.json` 是內部檔。
3. **記帳主體**：寄件人額度 key＝信封 sender（相對 kernel stack、不驗）。嵌套後實打 API 的 kernel 看到的是隊伍 kernel；要按原 agent 記帳得多帶欄位，碰 N-66「一箱一函數…不在信封放協議欄位」、C-56「不為邊緣狀況加機制」。
4. **錯誤往上報**：N-43／P-21／C-53「不轉述」vs C-52 表 ③（llm kernel 透原因給寄信方）。隊伍 kernel 再轉述一層，是照判準自動成立，還是新例外（觸發門檻 2「同型再出現問一次」），條文沒寫。
5. **不降級**：「不降級，回 BudgetMissing」「換模型＝換代號」已裁；上層 kernel 替人改派別包會相衝，除非上層自己就是寄信人、自己換代號。
6. **兩層各排一次**：llm kernel 序寫死「級數＋aging → 時限 → speed → 等得久 → 先寄」；判官只有先來先掛。`priority` 是否原樣下傳、aging 兩層各算、跨樹期限只有「信裡毫秒」一句（N-65 ③）。
7. **時間成本無條文**：最近的是 C-38、`_metainfo`「要跑多久」（待落條文，且「實測不回寫」）與 11-04 晚拿掉的 `_metainfo.time_ms` 排序。「實測不回寫」跟「用實測時間排程」有張力。
8. **一次只載一個模型**：docs 無。現制 `slots` 是每包與 kernel 總數，換模型的切換成本沒欄位；「同模型湊一起」＝多一條排序依據，要動 N-42 寫死的順序。
9. **逾時層層包**：P-36「外層 ≥ 內層…aos 不替人算」；`timeout_ms` 只管「跑一封」，排隊等待不在任何一層的上限裡，外層 think 格可能先殺；被殺＝那格失敗、不為內層說話。
10. **兩支不併＋hub 名**：隊伍 kernel 若同管掛 proc 與 llm 排程，碰「兩隻kernel不併成一支」；`AOS_KERNEL`（通用）／`AOS_LLM_KERNEL`（llm）已分，新中間層用哪個名要照 N-63＋N-67 ⑨；P-39 要 `AOS_LLM_KERNEL` 整棵樹一致，子樹指不同 kernel 有張力。
11. **daemon 身體失敗不停**：llm kernel 失敗「記一行、下一圈再跑」；上層要知道下層壞了，公開途徑只有回信或不回（「寄信不回，等同於呼叫失敗」）與父 daemon 只看活著（使用者 11-06 晚「子daemon管好自己，父daemon只看他有沒有活着…」）。
12. **待定未裁**：額度快見底留 high、kernel 公告、kernel 評估納入錯誤路徑都還沒定，設計依賴它們＝先替使用者定。

### 6b. 實況面（opus 從機制與試驗場看出的；都是事實，怎麼處理留給你）

1. **轉交會丟掉信的排程資訊**：endpoint 函數的 stdin 只有 `{endpoint, request}`，沒有原信的 `priority`（級數、deadline）、`sender`、信名。試驗場的 forward 因此另寄一封「普通、沒有 deadline」的新信；下層看到的寄件人是隊伍 kernel 的 stack，信名也是新的。
2. **兩層帳對不起來**：兩層 ledger 的 `id` 不同，沒有「上游信名」欄；配對只能靠行序（usage 數字常重複）。agent 的 `observed.jsonl` 的 `letter` 只對得上最上面那層。兩層 usage 是同一筆錢的兩份觀測，**相加會重算**（試驗場文件已註「不可相加」）。
3. **時間少記了一截**：每層 ledger 的 `elapsed_ms` 從「掛上」算；信在 `new/` 排隊的時間、等 daemon 套用的時間、本機換模型的載入時間都沒有欄位。實測每多一層約多 0.3～0.9 秒（兩層各 300 ms 一拍）。上層的 `elapsed_ms` 自然包含下層排隊，但看不出哪段是排隊、哪段是真的在算。
4. **逾時層層包但不知道**：兩層 `timeout_ms` 都 120 s，上層先起算；下層排隊吃的是上層的時限。上層殺掉 forward proc 時，forward 寄出去的那封下層信不會被撤（照文件推得、未實測：`aos-llm ask` 被殺，`sender.flock` 釋放 → 下層信若還在 `new/` 會被收拾掉；已掛上的照跑、照花錢，回信被撤）。
5. **失敗字串一層包一層**：實測錯誤是 `aos-llm: error: EndpointFailed endpoint function exited with code 1: forward: error: EndpointFailed upstream aos-llm ask exited 1: ['aos-llm: error: EndpointFailed … llm_http: error: EndpointFailed HTTP 500: … Lm_studioException - Connection error.']`——代號每層都是 `EndpointFailed`，真原因在第四層；嵌套越深字串越長。ledger 失敗那行只有 `usage: null`，沒有錯誤碼欄。
6. **一次只載一個模型沒有任何機制表達**：同一台 LM Studio 後面的不同模型，在 kernel 裡是不同包，各自 `slots: 1`、彼此獨立，kernel 會讓兩種模型同時在飛。試驗場的本機包還經過 LiteLLM（`:4000`）再到 LM Studio，kernel 看到的 url 跟 gpt 包一樣。換模型的時間（載入幾秒到幾十秒）目前沒地方記、排序也不看。現有排序裡「同包信先跑」沒有規則（只有 speed、aging、deadline）。
7. **判官與 llm kernel 兩套排隊互不認識**：判官 FIFO、數 daemon 表 running；llm kernel 優先序、數自己在飛。llm kernel 的掛信若經判官（`AOS_KERNEL` 指判官），`llm_*` 要在 `allowed` 裡、吃判官 `max_running`；掛信不帶 `reply_to`，被判官拒時 llm kernel 收不到，會一直當「還沒套」佔格（推論，未實測）。現行文件建議起 llm daemon 的殼別設 `AOS_KERNEL`。
8. **期限的單位與起點每層不同**：判官 `queue_wait_ms`（毫秒、從信封 `sent_at`、牆鐘、含排隊）；llm kernel `priority.deadline`（絕對時刻、牆鐘）；aging 用自己樹的 tick；`timeout_ms` 從掛上算；aos-agent `--timeout-s` 用單調鐘。
9. **寄件人額度在嵌套下只看得到一格**：下層的 `budget.senders` 只看到隊伍 kernel；隊內誰用多少只在隊伍 kernel 自己的 `used.json`／ledger。arknights-kb 設計稿曾寫「下游 senders 只見隊一格**不改**（嵌套本意＝一隊一格）」（隊長代定，非使用者裁）。
10. **`AOS_LLM_KERNEL` 在子樹裡換值**：試驗場隊伍 kernel 的 daemon 把自己子項的 `AOS_LLM_KERNEL` 改指總機（forward 才寄得到總機），而 agent 們指隊伍 kernel——同一棵樹兩個值，跟 P-39「整棵樹一致」、N-67 ⑨「跨樹 hub 只在 root 層設」有張力。
11. **proto8 本身沒有轉交函數**：forward 是試驗場自寫的 7 行 Python（全文 §3.4）。`_tooldef.json` 沒有。
