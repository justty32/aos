## 0. 先講結論
- 本體是 C++ 的 aos-llm-kernel；它「一輪＝一次行程」：daemon 每 300 ms 起一次、做完退出（kernel/llm-kernel/daemon.json:1 `interval_ms: 300`；K/serve/serve.cpp:115 `Server::run` 是一輪的全部）。狀態全在檔案裡，每輪重讀。
- Python 版（lib/aos/kernel_llm，lib/aos/kernel 骨架）是並存的同介面版（lib/aos/kernel_llm/README.md 第 3 段）；範本掛的是 C++ 那支。下面逐項只講 C++。
- 「端點同時只能十幾個」這件，kernel 的 slots 正好就是答案（總格＋每包格＋保留 high 格）；放行側夠用。撐不住的是「等待的信很多」與「agent 端每隻都在輪詢」，不是端點側。

## 1. 一輪怎麼跑
- 順序（K/serve/serve.cpp:115-134）：find_host → 建夾 → 鎖 → read_queue → used.json → 讀 daemon 的整張表 → 寫 endpoints.json（沒變不寫）→ collect()（掃 cur/）→ sweep()（清寄件人已死的信）→ scan()（掃 new/）→ order() 排序 → 逐封放行 → write_queue。
- 收件箱掃法：每輪對 new/ 做 readdir 全部（aos::names_in，aos-util/src/dirs.cpp:25-45，每個條目 is_directory 一次 stat），然後對每一封「打開 letter.json、整份 JSON 解析」（K/serve/scan.cpp:75-78）。請求本體（含整段 messages 歷史）就在 letter.json 裡，所以每輪每封等待的信都被完整讀入、解析一次；`Waiting w.letter = *letter` 再複製一份、`ws.push_back(w)` 又複製（scan.cpp:91、141）。成本 ≈ O(等待信數 × 每封大小) 每 300 ms。
- 另外每封都做 pick()：從 kernel.json 解那個代號的指示詞（aos::resolve，scan.cpp:41）、parse_pack、fixed_clash（scan.cpp:27-65）。同一個代號每封各解一次，沒有快取。
- sweep()（serve.cpp:88-113）：tmp/ 全 readdir；new/ 全部再 readdir 一次，每封 stat sender.flock＋open＋flock(LOCK_SH|LOCK_NB) 試鎖（letter.cpp:38-52）。又是每輪每封 3～4 次系統呼叫。
- 排序（K/queue/queue.cpp:76-127）：std::stable_sort，比較鍵＝等級＋aging → deadline → 包 speed → 等多久 → 信名。O(N log N)，拷貝 Waiting（含整份 letter JSON）；後面還有一段同級內「同後端黏著」的分區，最壞每組再掃一次。
- 輪間隔：300 ms，來自 daemon.json:1；daemon 自己的 interval 預設 200（D/daemon.cpp:59）。不是事件驅動，信來了最多晚 300 ms 才被看到。
- 鎖：整個 mailbox 一把 flock（`<requests>/.flock`，LOCK_EX|LOCK_NB，serve.cpp:75-84）＝同一信箱一次只准一個 kernel；撞到就丟 LockFailed 退出。沒有細鎖，也就是只能單 kernel 水平不擴（要擴＝多個信箱、多個 kernel，各自 slots）。寄信端不拿這把鎖（靠 tmp→new 改名）。
- 每輪另外讀寫：`counter_kernel_runs.txt`（只有 --enable-counters，serve.cpp:26-58，讀＋原子寫一次）；queue.json 內容沒變不重寫（queue.cpp:59），但新信到／舊信走就會重寫整份（含所有等待信的 seen_at_ms／seen_at_cycles 兩個 map，queue.cpp:50-66，write_json 還 fsync：aos-util/src/files.cpp:256-264）。

## 2. slots、priority、budget
- slots：「在飛」＝cur/ 裡有 proc.json 且 settle() 回 nullopt 的信，由 collect() 每輪掃 cur/ 數出來（K/serve/proc.cpp:278-315，++busy_）；放行時 `n + busy_ >= slots_` 就 break（serve.cpp:149-151）。所以在飛數是從檔案數的、跨輪、跨重啟都對。上限只受 cur/ 大小（＝slots，小）影響，這部分便宜。
- 另有三層格：reserved.high（serve.cpp:152，只認宣告級數、不含 aging）、每包 `slots`（serve.cpp:191，pack_busy_）、每後端 `slots`／`max_packs`（serve.cpp:194-203，給本機模型換載用）。
- priority：letter body.priority（level／deadline）；order() 排。aging_cycles 預設 3，每等 3 格升一級、不封頂（docs/04-已知限制.md 最後一段；queue.cpp:68-74）。
- budget：三層，各自「到頂 wait 就留著、否則 refuse 回 BudgetMissing」：整窗（kernel 次數／token）、每包 packs.<代號>、每寄件人 senders.<sender>（serve.cpp:140-190）。全記在 `$AOS_STACK/used.json`（K/budget/budget.cpp:195 read_used、:266 寫）。每輪開頭整份重讀；每「收尾一封」（finish→add_used，reply.cpp:158-160）就整份改寫一次（含 senders 全表、write_json 有 fsync）。senders 每個寄過的人都記一列（docs/04 倒數第 N 條「used.json 的 senders 每個寄過的人都記」）→1 萬隻 agent＝used.json 有 1 萬列，每完成一次請求重寫一次整份。另有 ledger.jsonl 逐封 append（reply.cpp:129-131）。
- 寄件人身分＝信封 sender（相對 kernel stack 的路徑），kernel 不驗（docs/04）。

## 3. 每個放行的請求是不是起一個 proc
- 是。放行時 mount()（K/serve/proc.cpp:111-144）寄一封 `procs_added: {"llm_<信名>": {exec: {argv: [aos-exec, <endpoint 函數>], cwd: 信夾, stdin: request.json, stdout: reply.json}, max: 1, stack: 信夾}}` 給 daemon 的 ctl 信箱；daemon 把它變成表上一列、起一個 loop 型子行程，裡面再 fork aos-exec 跑端點函數（litellm 預設是 python3 lib/base/llm_http，kernel/llm-kernel/endpoints/litellm/_entry）。所以每個請求＝1 列表＋fork（aos-loop 子行程，D 的 tend 管）＋aos-exec＋一支 Python。1 萬封信＝1 萬次這樣的組合，但**同時只有 slots 個**，所以不是 1 萬個同時 fork；時間上是序列化的。
- 每個請求另外：1 封掛信（post/send，含 tmp→new 改名）、request.json 一份、proc.json 一份（還可能多寫 state.json／reply.json）、完成時 `procs_removed` 又一封信、再 remove_tree 整個信夾。檔案操作約每請求 15～30 次，相對 LLM 秒級延遲可忽略。
- daemon 表多大才慢：表只含在飛的列（slots 個）＋被移除前的殘列，所以 llm daemon 的表很小。但 daemon 對表的壓力有實測：edge-round2（thinking/2026-11/05/edge-round2/README.md:28-34）——3000 封 add＋stop、RSS 2.9→15.7 MB 持平；50/100/200 個 loop 型 proc 全起 0.1～0.34 s、`ls` 24～38 ms；表 4300 列且 interval_ms 10 時「閒著 82% CPU」；一批上千封每列寫一次整張表曾是平方慢（1500 封 21 s，已修成 1.2 s，D/reconcile.cpp:11,260 FLUSH_MS 200）。procs_state 表切成每份 100 列（D/windows.cpp:105 PART_ROWS）。kernel 每輪 read_table 把整張表（所有分檔）讀回來解析（K/daemon/daemon.cpp:63-83）→表若有幾千列這步才變貴；放行側表很小，所以現況不是問題。
- 但注意：**agent 自己的 daemon 與 llm daemon 若是同一台**，那 1000 隻 agent 的列（每隻一個 aos-loop）就在同一張表裡，上面「閒著 82% CPU（4300 列 10 ms）」那種情況才是風險；建議 llm daemon 與 agent daemon 分開（daemon.json 本來就是獨立一台）。

## 4. 等待的信放哪、上限、公平、超時
- 放 `<requests>/new/<信名>/`，一封一個資料夾（letter.json＋sender.flock 等）。**沒有任何上限**：沒有最大等待數、沒有每寄件人上限（BudgetMissing 只在 budget.senders 有列該人且到頂時才擋，serve.cpp:172-190；沒列＝不限，docs/04「沒有『沒列的人一律 N 次』的預設格」）。
- 公平性：排序鍵沒有「寄件人」。同級、同 deadline、同 speed 時 waited 久的先（queue.cpp:92-97）＝近似全域 FIFO。一個人一次寄 1 萬封，後來的別人就排在那 1 萬封之後（除非等級較高或 aging 追上）；aging 是「每封自己等久了升級」，灌的那 1 萬封也都在 aging，所以不會讓別人餓死到永遠，但延遲＝前面全部的處理時間。要防灌爆只能：budget.senders 設每人 max_calls（每窗，不是同時在飛數；沒有「每人同時在飛」上限的獨立設定——sender_busy_ 只拿來算 spent_of 的在飛加成，serve.cpp:176-178）、或把大戶分到另一個信箱／kernel。
- 超時：(a) 掛上去後 `timeout_ms`（kernel.json:1 的 120000）→ mount 時寫進 daemon 單子 timeout_ms（proc.cpp:119-121），逾時回 EndpointFailed（proc.cpp:228-233）；(b) 信自己的 priority.deadline：還在 new/ 排隊時過了＝每輪 scan 回 DeadlineBad（scan.cpp:115-118）；(c) **排隊本身沒有逾時**——信不寫 deadline 就一直等（docs/04 也說 wait 配 window all＝永遠等）。agent 端 wait.py 也沒有自己的逾時，只每 10 分鐘印一行 warning（T/wait.py 檔頭註解）。
- 寄信的 agent 死了：sweep 會把 new/ 裡 sender.flock 沒人鎖的信清掉（serve.cpp:88-113，只對同步寄的有 sender.flock）。

## 5. 檔案系統面
- 每封信＝1 個資料夾（new/<id>/ 內至少 letter.json，同步寄的還有 sender.flock，另有 tmp/ 階段）。1 萬封＝1 萬個目錄 inode＋2～3 萬檔案 inode；ext4 的單層 readdir 1 萬項不是問題（頁快取內 ms 級），但每 300 ms 做 3 次完整 readdir＋每封 3～4 個 syscall（names_in、sweep 的 new/ 一次、scan 的 open/read、sweep 的 sender.flock open＋flock）＝約每輪 4～5 萬個 syscall＋把全部 letter.json 讀入並解析。若每封 letter.json 因為帶歷史而有 50 KB～數百 KB，1 萬封就是每輪 0.5～數 GB 的讀＋JSON 解析，這是最先爆的地方（CPU 單核 >300 ms 就會一輪沒做完，daemon 下一輪不重疊——body 是「跑完才排下一次」，D/body.cpp:19,40）。沒有 inotify，沒有目錄快取，沒有 index。
- 每封信的 reply 是寄進寄件人自己的 reply_to 信箱（每隻 agent 一個，T/wait.py：think/reply），所以 1 萬 agent＝1 萬個回信信箱，各自很小。
- write_json 都 fsync（aos-util/src/files.cpp:256-264）：queue.json／used.json／proc.json／request.json 每寫一次一個 fsync；在 SSD 上 ~ms、在 HDD／網路碟會成為 slots 吞吐的固定開銷。

## 6. agent 端（只從程式推）
- 每隻 agent 是一個 loop 型 proc：loop.json `interval_ms: 300`、exec `["aos-loop","loop.json"]`（T/loop.json:1、T/body.json）。常駐的是 daemon 底下一支 aos-loop（C++，輕量，空閒時主要是 sleep/ppoll）。**每 300 ms 一拍**，一拍＝aos-fsm 起一次，按狀態再起 `python3 idle.py`／`wait.py`／`brain.py`／`act.py`（T/fsm.json:1-9）；也就是每拍都是一個**新的 Python 行程**（冷啟動並 import aos_flags、hooks、goal_state、cell_common 等，idle.py 開頭 import 一堆）。
- 等腦回信時在 wait 格：每拍 wait.py → 再 subprocess `aos-llm recv --quiet think/reply <名>`（T/wait.py 註解：「每拍一下就退」「平常每拍帶 recv --quiet」），所以等一次腦回覆期間每 300 ms ＝ 1 個 Python＋1 個 aos-llm 行程＋讀 llm-kernel 資料夾。idle 時：idle.py 每拍讀 queue、hooks.clock_tick 讀清單、mail_notify hook 每 60 秒、goal 判斷（idle.py 註解）。也就是 **idle 也在輪詢，沒有事件喚醒**（有 aos-post 的響鈴機制用在 daemon-interrupt 設計，但 agent-fsm 範本沒見用它；thinking/2026-11/09/daemon-interrupt 有討論，我沒確認是否已接到範本）。
- 粗估（無測量，Python 冷啟動 20～50 ms CPU、每個 aos-llm／aos-fsm 起一次幾 ms）：每隻 agent 每秒約 3.3 拍 × (aos-fsm＋python＋可能再一個 aos-llm) ≈ 每秒 7～10 次 fork/exec、約 30～80 ms CPU/秒＝3～8% 單核。1000 隻 ≈ 30～80 顆核的輪詢負載→一台普通機器（8～16 核）撐不住；100 隻 ≈ 3～8 核，勉強。記憶體：常駐只有 aos-loop（約 1～3 MB RSS 量級，edge-round2 的 daemon 本體 RSS 3→16 MB）×1000 ≈ 數 GB 內；瞬時的 Python（每個 ~10～20 MB）同時存在的個數＝並發拍數，通常幾十個，不會 1000 個同時。行程總數：常駐約 1000（aos-loop），暫態 ±數十～數百；另 daemon 表 1000 列，edge-round2 實測 200 個 loop proc 無 fd 洩漏、4300 列 interval_ms 10 閒著 82% CPU（那是 10 ms 間隔；300 ms 間隔會輕很多但無實測）。
- 把拍子拉長（interval_ms 300→3000）是最便宜的槓桿；但 kernel 回信的延遲也跟著加。

## 瓶頸排名（由先爆到後爆）
1. **agent 端每拍重起 Python 的輪詢**（idle／wait 每 300 ms 一個新 python＋aos-llm recv）：1000 隻≈每秒數千次 fork/exec，單機先吃滿 CPU，遠早於 kernel。證據：templates/agent-fsm/fsm.json:1-9（python3 idle.py／wait.py）、templates/agent-fsm/loop.json:1（interval_ms 300）、templates/agent-fsm/wait.py 檔頭（每拍 recv --quiet）。
2. **kernel 每輪全掃 new/**：每 300 ms readdir 全部＋逐封開檔解析整個 letter.json（含歷史）＋逐封 pick 解指示詞＋sweep 再逐封試 flock＋stable_sort 拷貝整份信；O(N×信大小) 且無快取、無上限。證據：impls/aos-llm-kernel/src/serve/scan.cpp:75-141、serve/serve.cpp:88-113、queue/queue.cpp:76-98、aos-util/src/dirs.cpp:25-45。
3. **沒有等待上限、沒有每人公平／同時在飛上限、排隊沒逾時**：一隻 agent 灌 1 萬封＝全域 FIFO 把別人擠到最後；budget.senders 是每窗總量不是同時數；排隊無逾時。證據：serve.cpp:172-190、queue.cpp:92-97、docs/04-已知限制.md（「沒有『沒列的人一律 N 次』的預設格」「wait 配 window all＝永遠等」）。
4. **used.json／queue.json 整份重寫＋fsync，senders 每人一列**：每完成一次請求重寫整份 used.json（1 萬寄件人＝1 萬列），queue.json 隨等待數長大；吞吐上限＝slots／(LLM 延遲)，這步多半不是瓶頸但隨寄件人數線性變貴。證據：budget/budget.cpp:195-266、serve/reply.cpp:158-160、queue/queue.cpp:50-66、aos-util/src/files.cpp:256-264。
5. **單信箱單 kernel 單 flock＋每請求 fork 一串 proc**：放行吞吐受 300 ms 輪＋每輪放行數（slots 內補位）限制；端點只有十幾格，所以夠用；daemon 表在 llm 這台很小（在飛數）。若 agent 與 llm 共用一台 daemon，表上千列且 interval 小時 daemon 自己會 CPU 高（edge-round2 實測 4300 列 82%）。證據：serve.cpp:75-84,149、proc.cpp:111-144、kernel/llm-kernel/daemon.json、thinking/2026-11/05/edge-round2/README.md:28-34。
