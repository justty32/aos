### 1.3 用量怎麼算（單位）
- lib/aos/kernel_llm/budget.py:243-254 `tokens_of(reply)`｜回信的 `usage`→token 數：先取 `usage.total_tokens`（非負整數）；沒有 total 且有 `prompt_tokens`＋`completion_tokens` 就相加；其餘（沒 usage、error 回信、形狀不對）＝None，只算次數不算 token。
  格式實例（llm_http 回的）：`{"message": {...}, "usage": {"prompt_tokens": 12, "completion_tokens": 5, "total_tokens": 17}, "model": "..."}`（lib/base/llm_http/_entry:123-124；llm_fake/_entry:95 回 usage 全 0）
- 事實：單位只有兩種計數＝「次數」(`calls`) 與「token 總數」(`tokens`，in+out 合一，不分 in/out、不分 cached)；沒有金額、沒有幣別、沒有 per-model 單價。

- budget.py:226-240 `spent` / `spent_of`｜判斷：`calls + started >= max_calls`（started＝在飛＋本輪新掛，所以是預扣次數）或 `tokens >= max_tokens`（token 只能事後知道，所以可能超一點；沒預扣）。
- CPP 對應：impls/aos-llm-kernel/src/budget/budget.cpp（323 行）、budget.hpp:1-24（註解寫明格式與語意）。

## 2. kernel 站／框架（lib/aos/kernel + 總機）

骨架檔：lib/aos/kernel/{round.py,hooks.py,hold.py,letters.py,runner.py}；掛 proc 規則包：procs_rules.py、queue_fifo.py。問腦規則包＝1 節。說明文件 lib/aos/kernel/README.md。

### 2.1 kernel.json 鍵（README.md:"kernel.json" 表；程式 lib/aos/kernel/procs_rules.py:10-35, 99-125）
| 鍵 | 值 | 預設 |

| `count_daemon` | 數 running 的 daemon stack | 下一站從 AOS_DAEMON 來才用它 |

| `keep_ordered` / `route_ordered` / `reply_via_me` | bool | false / true / false |

### 2.2 規則怎麼寫、怎麼判（procs_rules.py:167-240）
- `verdict(body, allowed, cap, running, admitted)`（167-198）：body 的 `procs_added`（物件，鍵＝proc 名）、`procs_started`、`procs_woken`（字串陣列）。名字不在 allowed → `("NameUnknown", "x not in allowed")`；`len(running)+len(admitted)+len(fresh) > cap` → `("SlotMissing", "max_running is N, M running now (...), this letter adds K")`。
- 單位：`max_running` 數的是「同時 running／stuck 的 proc 個數」，從 daemon 表讀（procs_rules.py:59-80 `state_view`）；不是額度、不是時間。
- 信 body 可帶 `queue_wait_ms`（非負整數；queue_fifo.py:51-59）：從 `sent_at` 起算最久排多久，過了拒 `SlotMissing`；0＝有格就過、沒格不排。
- 判決回信格式（骨架 round.py）：放行→轉寄到下一站；拒→`{"applied": false, "error": {"code": "...", "msg": "..."}}`；留隊→記進 `queue.json`：`{"queued": [{letter, names, queued_at, queued_at_cycles?, expires_at?}]}`。
- 拒信代號表（README「拒信代號」）：BodyBad、NameUnknown、SlotMissing、HoldRefused、ForwardFailed、HookRejected。

### 2.3 hooks（lib/aos/kernel/hooks.py；執行 lib/hook_run.py）
- 三事件：`before_verdict`（可改 body）、`after_verdict`（可改 `verdict`＝pass/refuse/hold、`error`、`next`）、`before_reply`（可改回信 body）。退 10＝攔下（`HookRejected`）；`on_error: stop|continue`；`timeout_ms` 預設 60000。
- hook 事件 JSON 實例欄位：`event, hook, stack, letter, sender, sent_at, reply_to, body, verdict, error, next, decision`（README hooks 表）。
- 分流：after_verdict hook 回 `{"next": "<絕對信箱路徑>"}`（只有一個 next 能寫在 kernel.json）。

### 2.4 kernel_gate 與 hold（「先留著等表態」）
- lib/aos/kernel/hold.py:1-92｜hook 回 `{"verdict":"hold"}` → 信留在 `requests/cur/`，記進 `<stack>/hold.json` `{"held":[{letter, held_at, held_at_cycles?, expires_at?}]}`；表態檔 `<stack>/decisions/<信名>.json`：`{"verdict":"pass"}` 或 `{"verdict":"refuse","error":{"code":"NotNow","msg":"..."}}`（先寫暫存再改名）。pass＝重判一次（內建規則仍可拒）；refuse 沒寫完整 error 則 `HoldRefused`。留著的信不佔格（不算進 max_running）。只有掛 proc 那包收 hold；問腦那包遇 hold＝hook 自己失敗。
- lib/agent/kernel_gate/_entry:1-120｜把叫它的 agent 變成 kernel 門：op `on|off|ls|pass|refuse`；on＝在 agent stack 的 `hooks/kernel_gate/` 建站（`kernel.json` 預設 `{"hooks":{"hold":{"event":"after_verdict","condition":"pass","handler":...}}}`＋`requests/` 信箱），並加一支 on_clock hook（每 1 cycle 跑站一輪、通知 agent「[aos] kernel_hold: ...」）。agent 回 pass/refuse，轉寄由站做。
- lib/agent/kernel_gate/_metainfo.json｜`"cost": {"time_ms": 1000}, "timeout_ms": 120000, "resource": "cpu"`。

### 2.5 判官／總機
- 程式裡沒有叫「判官」的獨立元件：「判決」＝上述 admit／verdict／hook 的結果；kernel/llm-kernel/kernel.json 的 `"judge"` 是一個端點名（給 templates/judge-llm 用）。templates/judge-llm 是「用 LLM 比較兩個資料夾」的工具（不是 kernel 判官）：judge.json `{"endpoint":"judge","max_bytes":60000}`，_entry 把 usage 記到 `observed.jsonl`：`{"kind":"think","endpoint":...,"model":...,"usage":{...},"elapsed_ms":...,"letter"?}`。

## 3. daemon limits、aos-exec timeout_ms、aos-sandbox

### 3.1 daemon `limits`
- impls/aos-daemon/src/child/limits.hpp:1-50、limits.cpp:20-33,70-179｜鍵：`mem_mb`（RLIMIT_AS＋RLIMIT_DATA，MB→byte）、`cpu_s`（RLIMIT_CPU）、`procs`（RLIMIT_NPROC）、`file_mb`（RLIMIT_FSIZE，MB→byte）、`files`（RLIMIT_NOFILE）皆正整數；`user`（非空字串，本機 /etc/passwd 的帳號，setgroups+setgid+setuid）。soft＝hard＝寫的值；先 setrlimit 再換身分。
  格式：daemon.json 頂層 `"limits": {"files": 256}`（沒寫 limits 的列的預設）；每列 `"procs": {"bob": {"exec": "...", "limits": {"mem_mb": 1024, "cpu_s": 3600}}}`（`{}`＝不限、`null`＝用預設）。
- 讀取點：daemon.cpp:132-134（頂層）、procs.cpp:205,236,285（每列、procs_ctl）；信 body 也能帶（procs_added 內的 `limits`）；`aos-daemon-ctl add --limits JSON`（cmd/aos-daemon-ctl/bin/aos-daemon-ctl:110,143,436-441）。
- 表上回寫：child.cpp:297-299｜procs_state 每列帶 `"limits": {...}`（生效的那份，不限則不寫）。
- 失敗：做不到＝子行程 stderr 一行 `aos-daemon: error: LimitBad mem_mb 4096 exceeds the daemon's own hard limit` 並 _exit(1)（limits.cpp:148-179）；超額＝rlimit 天然行為（MemoryError、SIGXCPU、open 失敗、SIGXFSZ），daemon 只看「退非 0＝留 stopped＋reason」。
- 事實：rlimit 是每行程各自上限，不從 daemon 總額扣（limits.hpp:11）；沒有 cgroup、沒有總額記帳；kernel 的 `budget` 與 daemon 的 `limits` 之間沒有任何程式連結。

### 3.2 aos-exec timeout
- impls/aos-exec/src/inst/fields.cpp:5,87-103｜inst 單子欄位：`timeout_ms`（正整數或 null；0＝不限）、`timeout_cycles`（正整數或 null，與 timeout_ms 擇一，都寫＝EntryBad）、`grace_ms`（非負整數，預設 2000，到期後 TERM→等 grace→KILL 整群）。
- impls/aos-exec/src/inst/run.cpp:135-150｜timeout_cycles 的換算：有 AOS_CLOCK 就用 `deadline_after(cycles)`（以 cycle 為期限）；沒時鐘 `timeout_ms = cycles * clock_interval_ms()`（AOS_CLOCK_INTERVAL，預設 1000）。這是程式裡 cycle↔毫秒的一處明確換算。

## 8. 觀察到的共同點與不一致

單位與形狀
1. 「cost」一詞有三種不同東西：(a) kernel.json 端點的 `cost`＝自由字串 "high"/"free"，只被抄進窗 endpoints.json 與 `aos-llm ls`，沒有任何判斷或排序使用它；(b) _metainfo 的 `cost`＝物件 `{"time_ms":n}`（可能有 `token.{in,out,cached}`、`counter_calls`），單位是毫秒／token／次，是「宣稱的預估」，只有 metainfo_check 拿來跟觀察比（比值 0.8～1.25＝close）；(c) measure 的 cost＝同 (b) 的形狀但是量測值。三者沒有換算關係。
2. 花費的實際記帳只有兩個維度：次數（counter_calls）與 token 合計（counter_tokens＝total_tokens，缺就 prompt+completion）；毫秒（elapsed_ms）只記在 ledger.jsonl，不參與額度判斷。沒有金額欄；"high"/"free" 與 token 數之間沒有對應。
3. 額度判斷：次數是預扣（`calls + started >= max_calls`），token 是事後（`tokens >= max_tokens`，可能超一點）。窗是本地時間 hour/day 或 all，換窗歸零，`counter_all_*` 不歸零。
4. token 的 in/out/cached 分開只出現在 _metainfo 的 `cost.token` 與 measure/ledger.py；kernel 的 used.json、ledger.jsonl 的 usage 只用 total（ledger 列保留完整 `usage` 原物件，所以 in/out 在 ledger.jsonl 還在）。
5. `max_running`（個數）、`slots`（同時在飛信數）、`max_subagents`（個數）、`limits`（rlimit：mem/cpu/procs/file/files）、goal `limit`（提醒次數）、`budget`（次數／token 每窗）、`queue_wait_ms`（排隊毫秒）、`timeout_ms`／`timeout_cycles`、cooldown（失敗後秒數）：各自獨立，沒有共同的資源模型，沒有跨層扣額或繼承（例外：llm-team 把請求轉給主 kernel，主 kernel 把整台上層看成一個寄件人 `senders` key，budget.senders 各層各記各的）。
6. 「粗化」或「換算」的程式：
   - cycle→毫秒：aos-exec 沒時鐘時 `timeout_cycles * AOS_CLOCK_INTERVAL`（run.cpp:135-150）；tool_io.deadline_after、order.waited（沒時鐘用牆鐘差÷interval）同。
   - priority 數字→三級：order.py:27-28 數字只看正負（粗化成 -1/0/1）；aging 把等待 cycle 數 ÷ aging_cycles 加到級數（effective，不封頂）。
   - speed 字串→索引 fast/normal/slow（排序用）。
   - MB→byte（limits、sandbox）。
   - 窗起點取整（hour＝整點、day＝午夜）。
   - 沒有任何「cost 字串→token／金額」或「token→錢」或「多個資源合成一個總額」的程式。metainfo 的 `cal` 公式是唯一的「算式」機制，且只用於預估比對、無人使用。
7. 不一致：
   - `resource` 在 _metainfo.json 有字串（"cpu"）與陣列（["cpu","llm"]）兩種寫法，tool_spec.py:148-150 的檢查要求非空字串，與實際陣列寫法衝突（陣列不會通過該檢查；未實測，只讀程式）。
   - `cost` 型別：tool_spec 要求物件；metainfo.eval_cost 的值層級另接受數字、`{"val"}`、`{"cal"}`；llm-forward 寫 `counter_calls` 在 cost 內，而 kernel 的帳也叫 `counter_calls`。
   - `budget` 同名但層級不同：頂層 `budget`（含 window、spent、senders）與端點內 `budget`（只有 max_*，寫 window/spent 會 CfgBad）。
   - PY 與 CPP 兩支 llm kernel 規則重複實作，README 說對外相同；差異列在 lib/aos/kernel_llm/README.md「跟 C++ 那支的差別」。
   - 時鐘：沒有 AOS_CLOCK 時「cycle」退化成牆鐘毫秒；daemon `stuck_after_cycles` 預設 10、`stuck_after_ms` 只用牆鐘。
8. 「額度」目前只擋 llm 呼叫（budget）與 proc 個數（max_running、max_subagents）；cpu／記憶體靠 rlimit（天然超額行為＝行程死掉），沒有記帳；工具的 `cost` 宣告不擋任何事。
