## 題目原話

> 正統規劃，架構設計流程，我記得先前應該說過？就是讓opus帶隊，sonnet/gpt蒐集資料，opus匯總交給fable，fable弄好後讓opus深化細化，弄出實作計劃，最後實作再讓astra帶sol做。　好，總之我先說想法：就是說，aos的全名，就是akatosh operating system，這個操作系統很特別，他並非基於硬體，而是基於任意資源。linux操作系統的功能是讓軟體能夠很好的使用硬體這個資源，而aos他的資源可以是任意的東西，只要最後能夠影響到linux proc/aos proc就算，甚至沒有影響也可以。這塊我記得先前有講過，就是拿linux系統當硬體去模擬，我先不贅述。然後是proc的定義，就是說，他是所謂的過程，代表一段時間(這裏的時間，其根據未必要是現實世界時間)中，他應當造成的影響，或是這段時間中，某項事物其應該有的樣貌，類似三維空間中某物體，沿着x軸看，其切片在每個點上都有不同。只是proc這塊還要考慮外在影響，考慮幾率，不同世界線這塊。這有點抽象了，回到正題。aos系統的硬體就是linux，所以他的基礎資源會是抽象過的，處理過的，比如權限，資料夾...等等，當然，他也可以去訪問更本質的cpu/mem等，這些都是基礎，aos更強大的力量在於，基於我們所設計的技術棧架構，其資源的表示會是json，他可以是任意東西，並且複雜到人類難以處理，反正是ai看。既然是json，那就有幾個好處，首先是key隨意，反正程式只需要認他要的，這是在資源定義自由的情況下使其能隨意流通的一個優勢。另一方面是可以細化或粗化，比如一個資源cost，他的表示可能是cost:{token:10,time:1s}，要粗化，那就是cost:7，這可能是透過某種公式轉的，公式定義可以隨意，要細化，那可以是cost:{token:{in:6,out:4},time:1s}，具體要化成怎麽樣的obj乃至arr/str都可以隨意定義，反正AI能處理。對，重點在於這份自由性，以往需要人類處理，所以必須要先定下規範，還要討論，最後實作也要花時間，現在有AI，哪怕是陌生的東西，Ai也能給你給你粗略答案(準不準另說)，相關定義/規範/實作，人類隨口一說就能產出，所以這份自由就變成了可能。好，基於這份自由的資源定義，我們的aos在進行資源分配，並進行進一步的排程管理的時候，自然也可以很自由，畢竟有AI能處理。　所以我們的aos能處理很多東西，也讓很多東西變成了可能。

## 第二段（23:50 左右，頂層轉來，逐字）

> ps.aos技術棧還有一個好處，就是AI能輕鬆掌握。下一步，aos既然能處理很多東西，那我們的目標就可以稍微廣泛一些，首先是人類的可理解性這類，就可以透過aos kernel來優化了。然後還有，現在大家都還是在透過下prompt，配合RAG，來進行AI的調整，大多都還是用應用程式，雖然有些人已經開始學會自由，比如pi coding agent, deepseek harness這類，但我們的aos就是啥都是檔案，啥都是json，AI用起來最舒服。我知道有人會說aos效能不好，確實，但相比於LLM的花那麼多時間輸出東西，這點效能不算啥，並且有些時候，可理解性等東西比速度重要多了。而且端點同時間也只能處理十幾個請求，想必也只有aos這套能夠最好的處理上千上萬個agent(共享一個端點)。好，再來是aos的真正絕殺：ai的可預測性優化

頂層對這段的拆題（不是使用者的話）：(1) 人類可理解性可以當成 kernel 能優化的一種資源或目標；(2) 什麼都是檔案、什麼都是 json，跟 prompt＋RAG、應用程式式的做法比 AI 用起來最順（pi coding agent、deepseek harness 只當外部對照）；(3) 效能取捨：跟 LLM 輸出的時間比 aos 的開銷不算什麼，可理解性有時比速度重要；(4) 上千上萬個 agent 共用一個端點（端點同時只接十幾個請求）：盤點現有 llm kernel 撐到什麼規模、瓶頸在哪。使用者還在講「可預測性優化」，下一段會再轉來。

## 第四段（同晚，頂層轉來，逐字）：在 aos 上開發軟體

> 今天講的，很多都是這個.md中說過的。我繼續說一些額外的：有了作業系統，那我們就可以開始開發軟體了。在aos體系下開發軟體的體驗有點類似lisp的理想狀況。你先從一個能幫你開發函數的函數開始，然後改進這個函數，使其變得能更好的開發函數，如此下去，直到他開發的函數達到你的預期。對，這個第一個開發函數的函數，就是一個agent，然後你逐步給他擴充工具，子agent...等，直到他的功能符合你的需求。不用我說吧，如果他能自我開發改進的話...這會需要很多的agent，而aos就是爲此而生。我的其中一個目標，就是靠着這樣的自我改進函數，持續優化直到能夠用純粹程式實現原本只有agent系統才能達到的功能，也就是循環優化不確定性之類的東西。

頂層要計劃裡想的（頂層的話）：aos 現有的 `agent_def`、`self_*` 工具、`self_hook`、agent-fsm 這些「自我修改」的零件，哪些已經能當「開發函數的函數」的雛形；第一個開發函數長什麼樣、拿什麼量它進步了沒有。fable 開跑後才到，這段由 opus 細化時補進去。還有第五段「更進一步的 aos 軟體開發」會再轉來。

## 第五段（同晚，頂層轉來，逐字）：用 lisp／lua 寫、化成資料夾或 json

> 好，首先是這些軟體都可以用lisp或lua去寫，然後將其化爲資料夾，使其能夠用aos體系執行。然後aos體系中，json和檔案系統有同像性，所以也可以是化爲json。總之這塊之後可以再探索，重點是讓人能夠透過寫程式的方式去規劃(或理解)一些復雜的aos系統，同時也要考慮到資料夾嵌套可能對linux造成的性能影響，如何平衡在檔案系統內/在json內/在程式內，各部分的邏輯佔比，也是一門學問。ps.其實整個aos體系都可以用lisp/lua實現，但linux太香了，有現成的各種東西，所以就先這樣。之後如果有人像在lisp/lua內開發，然後用plan9方式接入aos，那也是好事。

頂層的話：使用者自己說「之後可以再探索」，計劃裡只放探索項目、不排進第一步。重點四條：lisp／lua 寫完化成資料夾交 `_entry` 執行（json 與檔案系統同像，也可化成 json）；目的是讓人用寫程式的方式規劃、理解複雜的 aos 系統；取捨是邏輯在檔案系統／json／程式三處的佔比，資料夾嵌套太深對 linux 的效能影響（請 sonnet 盤點現況：樹多深、檔案多少、`index_view`／`$ref` 碰到深樹會不會出事）；整套 aos 用 lisp／lua 實作與外部 plan9 式接入當未來方向。fable 開跑後才到，由 opus 細化時補進去。還有第六段（開頭「寫普通程式語言時很多東西我們都沒注意到」）會再轉來。

## 第六段（同晚，頂層轉來，逐字）：寫普通程式時沒注意到的資源

> 比如我們寫一個普通的a=1+2函數，表面上看，他的功能就這樣，沒啥好說的，那我們有考慮到他占用了多少資源嗎？當然，他占用了一些bytes，跑起來需要極短的時間。那除此之外呢？人類理解他需要多久？他的原始碼會佔用多少空間？他的其他額外影響，比如a這個變數的命名是否會覆蓋掉其他變數？這些都是資源，作業系統只管他的mem/cpu，沒有管其他這些，而aos可以管。軟體的威力可不止現在這樣，我們可以開發各種各樣以前沒想過的軟體，這些都需要藉助AI，而藉助AI的話，不止先前我們所說的，還有其他一堆以前覺得沒差的東西都要來優化管理，aos就是爲此而生。可能是互相成就吧，我們優化管理了這些，就能開發更大更神奇的軟體，而爲了開發更大更神奇的軟體，我們也就有了更多樣的優化管理需求，如此螺旋上升。

頂層的話：理解時間、原始碼大小、命名衝突都算資源，linux 只管 mem／cpu，aos 要能管全部；接第一段「任意資源、json、粗化細化」，可考慮放進 `_metainfo` 與它的客觀／通用／主觀三種觀點；螺旋上升＝要有讓新種類資源隨時加進來、不用先改 kernel 程式的方法；請想最小落地點，例如給一個工具或函數記下「理解成本、原始碼大小、命名衝突」三種資源，再讓 kernel 或某個工具讀得到。後面會不會還有段落頂層也不知道，先照現有內容推進。
