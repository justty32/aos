## 結論先講

1. **管線是六步：記 → 分 → 試 → 換 → 盯 → 退。** 後四步（`measure`、`promote`、`watch`、`rollback`、`review_round`）已經做好。缺的是前兩步：現在 `observed.jsonl` 只記用量，看不出「這次問腦是在決定什麼」，所以沒辦法說哪些呼叫是同一類。
2. **沉澱的單位叫「呼叫點」**：agent 在「上一步做完 X」的情況下問腦、腦決定「下一步做 Y」，(X, Y) 這一對就是一個呼叫點。同一個呼叫點如果十次有九次都選同一個 Y，這次問腦就是多餘的，把 X、Y 併成一個工具就少一次呼叫。這跟 arknights 線的實測一致（降下來的大半是「不用問了」）。
3. **「任意資源」不需要新的大機制**，需要一句定義和一張表。定義：**資源＝有人替它記帳的 JSON 值**；「有限」是某個 kernel 對它的態度，不是它的本性。態度有三種：**擋**（超過就不放行）、**排**（拿來排順序）、**記**（只記不管）。「沒有影響也可以算資源」＝只記。
4. **kernel 在主軸裡做兩件事**：一是所有腦請求都經過它，它是天然的記帳點；二是「改善」本身也花 token，kernel 要把改善當成一種要批准的請求，照「花下去的要賺得回來」分配，否則會重演 11-08「改善花費是生產的 8.9 倍」。
5. **規模那句話跟主軸是同一件事**：十幾格的端點一天大約只能答五萬次（見第 7 節的算式與假設）。一萬隻 agent 共用它，等於每隻一天只能問五次——只有沉澱到幾乎不問腦的 agent 才住得下。沉澱度就是容量的倍數。

## 0. 主軸：把 agent 逐步沉澱成純函數的管線

### 0.1 六步與零件

| 步 | 做什麼 | 零件 |
|---|---|---|
| 記 | 每次問腦留一筆「指紋」：上一步是什麼、這一步腦選了什麼、花多少 | 【改】`observed.jsonl` 的 think 列加一格 `site`；第一階段先不改程式，離線從 `history.jsonl` 補算 |
| 分 | 把指紋相同的呼叫歸成一個呼叫點，算每點的次數、token、「定型率」 | 【新】一支純函數腳本（零 LLM），產出「呼叫點表」 |
| 試 | 給候選呼叫點做替代品，在隔離環境拿 case 跑，比品質與成本 | 【已有】`lib/aos/measure`（case 夾、比對器、呼叫樹、重跑一致性）、`templates/judge-llm` |
| 換 | 過門、成本有降才換上，舊版留著 | 【已有】`lib/aos/promote` |
| 盯 | 換上後開窗看品質與成本 | 【已有】`lib/aos/watch` |
| 退 | 變差自動退回 | 【已有】`lib/aos/rollback` |

替代品誰寫：第一、二階段由人或隊伍（astra 帶 sol）照呼叫點表手寫；之後才交給審視者（`review_round` 目前只開處方，自己寫替代品那段沒做，【改】放第四階段）。

### 0.2 怎麼算「同一類」

指紋取三樣，都不需要讀懂 prompt 的意思：

- **上一步**：對話最後一則是什麼（哪個工具的結果／一封信／開場）。
- **這一步**：腦的回覆是什麼動作（叫哪個工具＋參數的骨架，只留 key 名與值的型別；或是「純文字收尾」）。
- **fsm 狀態**（如果紀錄裡拿得到）。

呼叫點＝（上一步, fsm 狀態）這個「情況」。每個呼叫點算兩個數：

- **定型率**＝這個情況下，最常見的那個「這一步」佔幾成。
- **token 佔比**＝這個呼叫點花的 token 佔整隻 agent 的幾成。

定型率高、佔比大的先動。定型率低的呼叫點是真的在做判斷，留給腦。

### 0.3 能換成什麼（由便宜到貴，依序試）

| 招 | 適用的呼叫點 | 換上後 |
|---|---|---|
| 剪掉 | 問了也是白問：重複查同樣的東西、結果沒被用到 | 少一次呼叫 |
| 併步 | 定型率 ≥ 0.9，且 Y 的參數能從 X 的結果照規則算出來 | X、Y 併成一個工具，少一次呼叫 |
| 查表／模板 | 輸入種類有限（enum、詞表），輸出是固定句式填空 | 純函數；附錄 B 的「八股化」就是這招 |
| 降級 | 還是要語言能力，但範圍窄 | 小模型或專屬小 agent（`review_round` 的逐級降模型【已有】） |
| 留著 | 真的要理解文字 | 不動。使用者 11-08 自己說過這類 token 會保持一定量 |

換的時候呼叫方不用改：C-55 第 2 級起呼叫方只寫名字，所以替代品是「同名、內部不同」的定義副本，`promote` 換的是副本。

### 0.4 kernel 的角色

- **記帳點**【已有】：llm kernel 的 `ledger.jsonl` 跟 agent 的 `observed.jsonl` 用信名對得起來，token 的真值以 kernel 這本為準。
- **批准改善**【新，第三階段】：一次審視、一次試跑都是花 token 的請求。kernel 給「改善」單獨一個額度，並照「回本」排：預估省下的 token（呼叫點的 token 佔比 × 預期還會跑幾次）大於改善要花的，才放行。這就是把「token 降到 0」當目標去分配——不是 kernel 自己會優化，而是它決定優化的錢花在哪個呼叫點。
- **把目標寫成檔**【新，第三階段】：每個被改善的函數夾旁放一份目標（門是什麼、目標是哪個成本 key、容忍多少退步），`review_round`、`watch` 都讀它。現在這些數字散在程式的代定值裡。
- **kernel 自己也是被沉澱的對象**：見第 4 節。

### 0.5 人在哪一步給 ground truth

- **根節點的 case 與比對器由人出**（附錄 B：「這是人類要出的題目」）。一個 case＝`run.json`＋`expect/`＋`check.json`【已有】。
- **子節點的「人」是父節點**：把父節點實際跑過、且整體過門的那幾次，子節點當時的輸入輸出就是子節點的 case。這讓 case 可以從歷史自動長出來，人只需要守住根。
- **主觀屬性**（傲嬌 0.4、可讀性）：人給幾筆分數，用來校準 `judge-llm`；之後日常由裁判給分，人抽查。
- 人不必批准每次換上（C-84 是自動換、自動退），但每次換上要留一筆人看得懂的紀錄：換了哪個呼叫點、前後數字。

## 2. 資源的表示

**定義（待裁 D2）**：資源＝有人替它記帳的 JSON 值。它不必有限、不必有影響；一旦某個 kernel 給它設了上限，它對那個 kernel 就是有限的。C-09「有限才是資源」變成特例：「被擋的資源」。這跟「kernel 是主觀的」「`_metainfo` 每格都是觀點」是同一個想法。

**誰宣告、放哪**——三個地方，各說各的，互不改寫（沿用 evolve-design 的兩本帳）：

| 誰說 | 放哪 | 內容 |
|---|---|---|
| 函數自己 | `_metainfo.json` 的 `cost`、`resource`【已有】 | 我估計會用多少（自稱） |
| 看它的人 | `observed.jsonl`、`ledger.jsonl`【已有】 | 它實際用了多少（他見） |
| 管它的 kernel | `kernel.json` 的 `resources`【新】＋`used.json`【已有】 | 我認哪些 key、各是什麼態度、上限多少、剩多少 |

`resources` 的每一列大致是：key 名、態度（擋／排／記）、上限與窗、從請求的 `cost` 怎麼算出這個 key 的數（公式，見第 3 節）。現有的 slots、`max_calls`、`max_tokens` 就是三列「擋」，不必搬家，只是以後新增的資源走這張表。

**怎麼不至於讀不懂**：

- 不設全域資源登記處。agent 要知道「我有什麼資源、剩多少」，問的是它寄請求的那道門。【新】給 agent 一個看的入口（併進 `self_state` 或一個小工具），內容就是那個 kernel 的 `resources` 加上這個寄件人的已用量。這補掉備料缺口 4。
- 不認得的 key 忽略（C-48）。kernel 遇到請求裡有它資源表沒有的 cost key，就是「記」或直接略過，不報錯。
- 需要有身分的資源（一個端點 pack、一台外部設備）才做成空間裡的節點；token、可理解性這種量不需要節點。
- 知識庫 `aos/*.json` 補一條「資源」的定義與三種態度【新】，agent 才查得到。

順手修：`resource` 欄字串與陣列兩種寫法並存、`tool_spec` 只收字串，定一種即可【改】。

## 3. 粗化／細化

**一句話：粗化＝寫出 `val`；細化＝展開形裡的其他 key。兩者住在同一個值裡，不是互相取代。**

C-48 的值雙形正好夠用：

```
7                                            純值（最粗）
{"val": 7, "token": 10, "time_ms": 1000}     展開形：val 是粗的，其餘是細的
{"val": 7, "token": {"in": 6, "out": 4}, "time_ms": 1000}   更細
```

要數字的讀者拿 `val`，要細節的讀者看其他 key，不認得的忽略。所以粗化不會毀掉資訊，細化也不需要「反推」。

| 問題 | 回答 |
|---|---|
| 公式住哪 | 住在**需要那個數的人**那邊。kernel 要判額度，公式在它 `resources` 的那一列；人要看報表，公式在報表工具的設定裡。函數自己也可以在 `cost` 裡先算好 `val`，那是它的自稱 |
| 誰提供 | 沿用 N-68 的語言 key：`cal`（四則）→`lua`→`py`→`aos`（叫一隻 agent）。【改】`lib/metainfo.py` 的 `eval_cost` 現在只吃單一公式，要讓它能吃「一份 cost JSON＋一條公式→一個數」 |
| 結果是誰的觀點 | 算的人的。kernel 算出來的 7 是 kernel 的 7，不寫回函數的 `_metainfo` |
| 換錯了怎麼辦 | 拿換算值跟事後實測比（`metainfo_check` 的 0.8～1.25【已有】）。不準就當沒估值（N-68 原規則），kernel 退回「事後照實測扣」 |
| 細→粗、粗→細 | 細→粗是公式，確定的。粗→細（只有 `cost:7`，想知道 in／out 各多少）沒有唯一答案，只能是估計；估計值要標明是估的，而且只准用在「排」和「記」 |

一條我建議寫死的界線：**「擋」只用實測值或 `cal` 這類確定的公式；叫 agent 換算的結果只用在「排」和「記」。** 理由：擋錯了會讓工作卡死，而 agent 的換算不可重現。

誰真的需要換算：現階段只有兩個——kernel 判額度（把 in／out／cached 換成它擋的那個數），和人看報表（把一堆 key 壓成一兩個數）。agent 自己估算那一側先不做。

## 4. 自由的分配與排程

政策分四級，越上面越自由也越貴。原則：**每封信都要過的地方不問腦；問腦只發生在例外，而且問過的要沉澱下去。**

| 級 | 是什麼 | 每封信成本 | 狀態 |
|---|---|---|---|
| 0 | Linux 硬擋（rlimit、cgroup、沙箱） | 零 | kernel-limits-plan 已裁未做 |
| 1 | 規則表：slots、budget、priority、`allowed`、`max_running` | 零 | 【已有】；要補每寄件人公平與等待上限（第 7 節） |
| 2 | 排序／判斷程式：掛在 kernel 的 hook 上，可以是人寫或 AI 寫，但**跑的時候是純函數** | 零 LLM | hook 時機【已有】；「排序鍵可換成一支程式」【改】 |
| 3 | AI 當門：`kernel_gate`，請求留著等一隻 agent 表態 | 一次問腦 | 【已有】 |

接法：

- 第 1、2 級處理不了的才升到第 3 級（超額的、帶著不認得的大額 cost 的、規則互相打架的）。平常的信不經過 AI。
- **第 3 級的每次表態都記下來**，它跟一般 agent 的呼叫點一樣可以分類：同一種情況 AI 門連續給同樣的答案，就把它寫成第 2 級的一條規則。**當門的 agent 本身就是主軸的沉澱對象。**
- **第 2 級的程式是一個函數**，所以用同一條管線管：AI 寫出新排序程式 → `measure` 拿一段歷史信流重放比較（等待時間、拒絕率、token 合計）→ `promote` → `watch` → 變差 `rollback`。「誰能改政策、改壞了怎麼退」就由這條管線回答，不另造機制。
- 能改政策的人：擁有那個 kernel 定義夾寫入權的（Linux 權限保底，C-47）。

沒把握的地方：重放歷史信流來評政策，需要 `ledger.jsonl` 有每封信的到達時間與等待時間，備料只說有 `elapsed_ms`。

## 5. proc 新定義：三種讀法

使用者自己說這段抽象，我只給讀法與各自的第一個落腳點，建議先做 A。

| 讀法 | 意思 | 第一個落腳點 | 何時 |
|---|---|---|---|
| **A. 預期與實際** | proc＝「這段時間應當造成的影響」。起跑前有一份預期，跑完有一份實際，兩者的差就是它多不受控 | 【改】daemon procs 表每列可帶 `expect`（從 `_metainfo` 的 `cost` 與九軸抄來），結束時補 `actual`；比對用 `metainfo_check` 的算法 | 現在可做，直接餵主軸的「可預測性」 |
| **B. 切片** | 沿時間軸每一格看 proc 的樣貌 | 【改】`observed.jsonl` 每列帶 cycle 編號；「軌跡」就是這串列。時鐘可脫鉤，所以時間本來就不必是真實時間 | 小改，第二階段順手 |
| **C. 世界線與機率** | 同樣的起點放開跑多次，結果會分岔；分岔的散布＝機率 | 【已有】`measure` 的重跑一致性 `consistency` 就是在抽樣世界線：同一個 case 跑 N 次＝N 條世界線。不用新機制，只要在條文裡把它講成這個意思 | 現在就成立 |
| C 的遠期 | 把活著的整棵樹在某一格凍住、複製、各走各的再比 | image 模型（C-79）＋影子世界 | 遠期，另開題 |

「外在影響」在這套讀法裡＝case 沒有固定住的輸入（中途來的信、端點的變動）。`run.json` 固定住的算已知，其餘算外在；一致性量到的散布是「模型機率＋外在影響」的合計，現階段不拆。

條文面：C-33 加一句擴充即可（process 是一段時間後的變化；帶預期時，預期與實際的差是它的可預測性；重跑的散布是它的世界線）。

## 6. 可理解性與可預測性

**可預測性**——三個現成或近乎現成的數，都不用問腦：

| 量 | 意思 | 來源 |
|---|---|---|
| 重跑一致性 | 同輸入跑多次結果一不一樣（客觀、世界線） | 【已有】`measure` 的 `consistency` |
| 宣稱與實測之比 | 它自己說的準不準（觀察者是「讀了 `_metainfo` 的人」） | 【已有】`metainfo_check` |
| **沉澱度** | 一個 case 裡不問腦的步數 ÷ 總步數；配上每 case 的問腦次數與 token | 【新】由呼叫點表直接算 |

沉澱度是主軸的主指標：它到 1 就是「token 0、純函數」。既有的 `open`／`boxed`／`none` 三段（C-22）是它的粗化版。

**可理解性**——它一定有「對誰而言」，所以每筆分數都帶兩格：誰打的（`by`）、替誰打的（`for`）。

- 粗量法（零 LLM）：輸出多長、是不是結構化的、人要開幾個檔才看得到結論。
- 細量法：`judge-llm` 照人給的評分準則打分，用人親手打的幾筆校準。
- 記在哪：他見帳（`observed.jsonl` 或 case 的結果裡），值可以是數、字串或 JSON（附錄 A 的 `{"pretty":12,"good":true}`）。

**kernel 怎麼用（待裁 D9）**：我建議先當**門**，不當排程目標。也就是寫進 `check.json` 的比對器與 `min_score`——可理解性不夠就不准換上；門內再比 token。這是 evolve-design 第五條「門與目標分開」。等到同一份工作真的有多個可選的 pack／agent、而且分數校準過了，再讓 kernel 拿它排序（那時它在資源表裡的態度從「記」升到「排」）。理由：分數是 AI 給的、會飄，拿會飄的數去排每一封信，政策就不可預測了。

## 7. 規模

**兩句話的關係（待裁 D8）**。先算容量（假設每次問腦平均 20 秒，這是我的假設，備料沒給）：

- 12 格 ÷ 20 秒 ＝ 每秒 0.6 次 ≈ 每小時 2,160 次 ≈ 每天 5.2 萬次。
- 1,000 隻 agent：每隻每天約 52 次。10,000 隻：每隻每天約 5 次。

所以「上千上萬個 agent 共用一個端點」只在一種情況成立：**絕大多數 agent 絕大多數時間不問腦**。這跟 11-08 那句「上千的是無 LLM 的函數節點」不矛盾，是同一句話的前後：萬隻 agent 是沉澱過的 agent，偶爾才碰到要腦的呼叫點。排隊久一點也可以是輔助，但光靠排隊撐不到萬隻。

**架構上要動的**：

| 項目 | 歸屬 | 說明 |
|---|---|---|
| 每寄件人公平、等待上限、排隊逾時、每人同時在飛上限 | **這題**（第 1 級規則，第三階段） | 【改】`lib/aos/kernel_llm` 排序鍵加寄件人；`kernel.json` 加幾個上限 |
| 信的「信封」與「內文」分開，kernel 掃等待信時只讀小信封（寄件人、priority、pack、deadline、cost 估值） | **這題的介面，另一題的實作** | cost 估值本來就該在信封上；全掃改索引的工程另開 |
| 事件喚醒取代 300 ms 輪詢 | **另開題**（daemon-interrupt 已有討論） | 最先爆的瓶頸，但跟資源模型無關 |
| `used.json`／`queue.json` 改增量寫 | 另開題 | 純工程 |
| 多信箱多 kernel 水平擴 | 【已有】llm-team 串主 kernel | 夠用，不動 |

建議另開的「規模」題先只做一件事：用假端點灌 1,000 封等待信，量 llm kernel 一輪掃多久、agent 輪詢吃幾核——備料的數字都是推的，沒量過。

## 8. 分階段

### 第一階段（一到兩天，不停樹、不改活樹的程式）：呼叫點表＋一次手工沉澱

| 項 | 內容 |
|---|---|
| 做什麼 | (1) 挑一隻現成 agent（判準見 D7）。(2) 寫一支離線腳本，唯讀它的 `history.jsonl`、`observed.jsonl`、kernel 的 `ledger.jsonl`，產出呼叫點表。(3) 挑表上排第一的呼叫點，手工做替代品（併步或查表）。(4) 從歷史挑 5 個 case，用 `measure` 跑改前、改後各 3 次 |
| 用到的 | 【已有】`measure`、case 夾格式、`judge-llm`（需要時）；【新】離線分類腳本一支、替代工具一個 |
| 使用者看到 | 一張表：這隻 agent 的 N 次問腦分成 K 個呼叫點，各佔多少 token、定型率多少；加一行結果：「第 1 個呼叫點換成工具後，每 case token A→B、問腦次數 a→b、品質過門、一致性 c1→c2」 |
| 事先講好的失敗樣子 | 如果沒有任何呼叫點同時滿足「token 佔比 ≥ 20%、定型率 ≥ 0.9」，就不硬做替代品，改交「這隻 agent 的呼叫都是真判斷」這個結論，並換一隻再跑一次表。這本身是有用的發現 |
| 不做的 | 不改 `observed` 格式、不動 kernel、不自動換上（手動比數字即可） |

### 第二階段（約一週）：指紋進源頭，任何 agent 都看得到自己的呼叫點表

- 【改】agent 範本寫 think 列時帶 `site` 指紋（上一步、這一步、fsm 狀態、prompt 雜湊），附 cycle 編號（第 5 節讀法 B）。
- 【新】呼叫點表做成正式工具；沉澱度進 `self_state` 或報表。
- 【改】`templates/reviewer` 的處方加「併步」「剪掉」兩招（現有 extract 只管 shell 用法）。
- 【已有】第一階段的替代品走完整的 `promote`→`watch`→`rollback`。
- 驗收：對兩隻以上 agent 各跑出一張表、各完成至少一次自動換上且 `watch` 沒退；使用者能用一個指令看到任一隻 agent 的沉澱度。

### 第三階段（一到兩週）：資源帳與改善額度

- 【新】`kernel.json` 的 `resources` 表（擋／排／記）；【改】`eval_cost` 支援 cost JSON→數；【新】agent 看得到自己的資源與餘額。
- 【新】改善額度與回本規則；目標檔。
- 【改】每寄件人公平、等待上限、排隊逾時。
- 【改】procs 表的 `expect`／`actual`（第 5 節讀法 A）。
- 驗收：一個新資源 key（例如「改善 token」）只靠改 `kernel.json` 就被擋住；一次改善請求因為不回本被 kernel 拒絕，agent 收到看得懂的理由。

### 第四階段（遠）：自己寫替代品、政策沉澱、影子世界

- 審視者自己寫替代品（fix／split）；AI 門的表態沉澱成第 2 級規則；排序程式走管線；活樹分支對照。
- 驗收：一隻 agent 在沒有人寫程式的情況下沉澱度上升，且累計改善花費小於累計省下的。

另外兩個我看到、但不算分岔的矛盾，請使用者知道：

- **「token 降到 0」與「同時提升智能」**：沉澱只會把已經會的事固定下來，不會讓它學會新的事。提升智能要靠「留著」的那些呼叫點加上新 case。兩個目標用的是同一條管線、不同的門，但不會自動同時發生。
- **「公式可以隨意、AI 處理」與「可預測性」**：換算越自由，結果越不可重現。所以第 3 節把 AI 換算擋在「擋」之外。如果使用者要連「擋」也交給 AI 換算，那是放寬這條界線，要明講。

## 我沒把握的（opus 請回 repo 驗）

1. **`history.jsonl` 能不能跟 `observed.jsonl` 的 think 列一對一對上**（靠信名還是靠順序）；history 有沒有被裁剪或壓縮過。第一階段全靠這個。
2. **fsm 狀態有沒有被記在任何一份紀錄裡**。沒有的話，指紋先只用（上一步, 這一步）。
3. **`measure` 能不能拿「一隻活 agent 的定義副本＋從歷史抽出來的輸入」當 case 跑**，還是 case 只能從頭起一隻新的。若只能從頭跑，子節點的 case 要另想辦法。
4. **現在樹裡有哪些 agent、各有多少 think 列**。D7 的判準（≥ 200 列）是我猜的門檻。
5. **kernel 的 hook 能不能換掉排序鍵、能不能自己回信**（D11 與第 4 節第 2 級需要）。備料只說有三個時機。
6. **`kernel.json` 加新的頂層 key（`resources`）會不會被現有讀取程式拒絕**。照 C-48 應該忽略，但要看實作。
7. **`ledger.jsonl` 有沒有每封信的到達時間、等待時間、寄件人**。重放信流評政策、每寄件人公平都要。
8. **信能不能拆成信封與內文**而不破壞「信＝含 letter.json 的資料夾」；或者信封就是 letter.json 裡固定幾個頂層 key、內文另放一檔。
9. **`review_round` 的 extract 處方長什麼樣**，「併步」能不能沿用它的格式。
10. **`py/aos_metaopt` 落地到哪**。如果能用，它是「查表／模板」那招的現成求解器。
11. **第 7 節的每次問腦 20 秒**是假設；實際值從 `ledger.jsonl` 的 `elapsed_ms` 取中位數就有，容量數字要照它重算。
12. **備料第 5 節的輪詢負載（30～80 核）**是推估，我沒有據此做任何設計決定，只把它歸到另開題。
