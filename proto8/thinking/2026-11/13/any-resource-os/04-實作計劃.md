## 二、第四段補進來：「開發函數的函數」

使用者第四段：「你先從一個能幫你開發函數的函數開始，然後改進這個函數，使其變得能更好的開發函數……這個第一個開發函數的函數，就是一個agent」。

**對到管線**：fable 的六步裡，「試」之前有一步「寫替代品」，fable 放在人手（第一、二階段）與審視者（第四階段）。開發函數的函數＝**專門做這一步的 agent**。它吃一個呼叫點（附 case），吐一個替代品函數；管線（`measure`→`promote`→`watch`→`rollback`）就是它的考官。

**現成雛形**（[01f](01f-蒐集-自我修改零件.md)）：

| 零件 | 能做 | 缺 |
|---|---|---|
| `tools_def new／check`＋`self_tools add` | 從 `templates/tool-python` 抄骨架、改、check 會照跑說明裡的 Example、加進自己的工具，下一次想就叫得到（11-10 gemma 第 4 輪做成乘法工具） | 只有那一次小模型實測；check 只跑 Example，不跑 case 夾 |
| `agent_def new`＋`subagent add` | 生新定義（寫 lineage）、改 tools／llm／system、起成子 agent | 改不了 fsm.json、hooks.json、subagents.json；沒有 reset；沒有實跑紀錄 |
| `measure`、`promote`、`watch`、`rollback`、`review_round` | 量、換、盯、退 | 是 `lib/aos` 函數，**沒包成腦叫得到的工具** |
| gpt 隊（`gpt-lead`＝astra、`gpt-worker`＝sol，[gpt-fsm-team](../gpt-fsm-team.md)） | astra 照圖紙派 sol 寫碼、自己驗收；已真跑（假工單 astra 29 次／37.5 萬 token） | 它開發的是 repo 的碼，不是 aos 函數；沒量過「開發得好不好」 |

**第一個開發函數的函數長這樣**（推薦，待裁 D12）：就是 **astra 帶 sol 這一隊本身**，工單換成「把呼叫點 X 做成一個 aos 函數夾（`_entry`＋`_tooldef.json`＋`_metainfo.json`），附的 case 要過」。理由：使用者本來就要「實作讓 astra 帶 sol 做」，這一隊同時是本題的施工隊與第一個被改進的開發函數，不用另造一隻。

**拿什麼量它進步了沒有**（每張「做成函數」的工單記一列，存 `C/any-resource-os/devfn-ledger.jsonl`）：

| 指標 | 意思 | 越好 |
|---|---|---|
| 一次過門率 | 交出來的函數第一次跑 case 就過門的比例 | 高 |
| 開發花費 | 做出這個函數 astra＋sol 共花的 token（llm kernel 帳照寄件人加總） | 低 |
| 回本件數 | 開發花費 ÷ 這個函數每次省下的 token | 低 |
| 人介入次數 | 隊長退件、手改的次數 | 低 |

它自己的改進＝對它（astra 的呼叫點）跑同一條管線：astra 派工、驗收的呼叫點也會出現在呼叫點表上（活樹 gpt-lead 已有 60 列 think），定型的就沉澱成工具。這就是「改進這個函數，使其變得能更好的開發函數」的第一圈。

**跟使用者舊稿對齊**（[`user-advice/README.md`](../../../../user-advice/README.md) 的回合式例子：galtxt 一個節點從「`_entry` 叫 claude code cli」一回合回合長成一棵樹、token 逐回合降；`_improve` 是同夾的另一個入口；優化器、評判器兩棵樹跟普通樹同根並存；`_improve` 吃 input／output／ground truth、評判器可併進去；「對子節點來說，他的人類就是父節點」）：

| 舊稿 | 本計劃 |
|---|---|
| `_improve`＝節點裡的另一個入口 | `aos-exec` 本來就照 `$AOS_ENTRY` 挑入口（`find.cpp`），所以 `AOS_ENTRY=_improve` 今天就能叫；但舊稿自己說「最好還是解耦」→ 推薦 `_improve` 只做薄殼：把「本節點路徑＋本節點 case 夾」交給共用的開發函數的函數（D16） |
| input／output／ground truth、評判器併進 `_improve` | 就是 `measure` 的 case 夾（`run.json`＋`expect/`＋`check.json`）；評判＝`check.json` 的門，不另做評判器樹 |
| 子節點的「人類」是父節點 | case 由上一層出：第一階段由 opus 出、支線 F 由 astra 出給 sol 的產物 |
| 第二回合→二點五回合：八股化、固定句式交給函數 | 第一階段 1.5 的「併步／查表」就是八股化的第一刀 |
| 三點五回合：效果不好時把責任交給負責的子節點、單檔撐不住就抬升成 agent | 呼叫點表能定位到哪一步出事；「抬升」是第四階段，不排 |
| 單檔腳本沒有 `_metainfo`，成資料夾後才有，欄位由優化器自訂 | 跟二之二一致：`_metainfo` 任意 key、優化器（`footprint` 與之後的 `_improve`）自己寫 |

第一階段等於舊稿「第二回合→二點五回合」的一小步：拿一隻已是 agent-fsm 的節點，第一次把定型的步驟換掉，看 token 降多少。

## 二之二、第六段補進來：mem／cpu 以外的資源，最小落地點

使用者第六段：`a=1+2` 除了 bytes 與時間，還吃「人類理解要多久」「原始碼多大」「名字會不會蓋掉別人」；linux 不管，aos 要管；管得越多軟體越大、軟體越大要管的越多（螺旋上升）。

**放哪裡**：放函數夾自己的 `_metainfo.json`。理由：(1) 它已是「節點描述自己」的地方，任意 key 都可放，壞掉的格算沒寫、不擋（11-12 已裁「全都是觀點」）；(2) 已有 `cost` 一格（目前只有 `time_ms`），`lib/metainfo.py` 的 `eval_cost` 已會讀；(3) 寫在 `_metainfo.json` 的＝通用視角（公開給別人的聲稱），某隻 agent 私下的估計＝主觀、放它自己那邊，正好是第一段「粗化／細化」與 11-12 三觀點的交會。

**三種資源的寫法**（量得到的才寫成數，猜的標來源）：

```json
"cost": {
  "time_ms": 30,
  "source_bytes": {"val": 4210, "from": "measured"},
  "read_min": {"val": 6, "from": "estimate", "by": "<誰估的>"}
},
"occupies": {"names": ["tool:callsite", "env:AOS_CALLSITE_MAX"]}
```

- 原始碼大小：`source_bytes`，量函數夾全部檔的 bytes，純函數算得出，`from: measured`。
- 理解成本：`read_min`，沒有客觀量法；第一版用代理值（行數、token 數）＋可選的 agent／人估計，`from: estimate`。照 fable 的界線，估出來的**只准排序與記帳、不准擋**。
- 命名衝突：不是一個「量」，是「佔用了哪些名字」——寫 `occupies.names`（工具名、環境變數、輸出檔名），衝突由工具跨節點比對算出來，不寫死在一個函數身上。

**新種類資源不改 kernel 程式就能加**：第三階段 3.1 的 `resources` 表每列用 `from` 指一個 JSON 指標（例如 `_metainfo.json#/cost/source_bytes`）＋可選公式；kernel 只認「指標＋態度（擋／排／記）」，不認識資源名。加一種新資源＝在 `_metainfo` 寫一格、在 `kernel.json` 加一列，零行程式。這是螺旋上升要的那個口子。

**最小落地點**（第一階段 1.8，只加新檔）：新純函數 `P/lib/aos/footprint/`，給一個函數夾或一整包：算 `source_bytes`、代理 `read_min`（行數÷每分鐘行數，係數寫在參數裡，不寫死）、收集所有 `occupies.names` 與工具名找重複；`--write` 時把算得出的那兩格寫回 `_metainfo.json#/cost`（不動別的格）。第一個戴上這三格的是 1.2 的 `callsite` 自己。讀得到它的：`footprint` 本身、`json_get`；kernel 讀它要等 3.1。

## 二之三、第五段補進來：lisp／lua 寫、化成資料夾或 json（只放探索）

使用者自己說「之後可以再探索」，所以**不排進第一、二階段**，只列探索題與觸發門檻。

**現況**（sonnet 11-14 唯讀盤點）：
- 活樹很小：984 檔、368 夾、最深 11 層（都是 agent 巢狀記錄子 agent 的 observed，如 `procs/gpt-lead/tools/subagent/observed/sol-T02/tools/shell/observed.jsonl`），九成檔在 2～5 層；`os.walk` 走完全樹 0.015 秒。repo 的 `lib` 533 檔、最深 5 層。
- 瓶頸是輪詢間隔（daemon 100～300 ms、時鐘 1 秒），不是檔案系統（11-12 autosave：`~/` 與 `/tmp` 跑 10 輪差 2 秒內）。沒有任何「檔案數 vs 掃描時間」的量測。
- `aos-exec`（`impls/aos-exec/src/find/find.cpp`）找 `_entry`：資料夾可一層層進，沒深度上限、有繞圈偵測；入口用 `execvp` 跑，所以 `#!/usr/bin/lua` 的 `_entry` **今天就能跑**。這台有 lua、luajit、fennel、guile、sbcl、clisp。
- 同像：條文 C-51（資料夾＝object、名字＝key，「建議不要濫用」）、C-68（資料夾＝程式）、C-71（比喻用 lua 的 table）、C-43（最終像類 LISP 程式）。沒有資料夾⇄json 互轉工具。`$ref`（`impls/aos-directive/src/ref.cpp`）有繞圈偵測、沒深度上限；`index_view` 只看一層、不走訪。
- N-68 的成本公式 key 有 `lua`，批 2 只做了 `cal`，`lua` 回未支援（當時這台沒 lua，現在有）。

**探索題**（每題一兩天，等使用者點）：

| 題 | 做什麼 | 判準 |
|---|---|---|
| X1 lua／fennel 寫的函數 | 用 `#!` 寫一個 `_entry`，配 `_tooldef.json`、`_metainfo.json`，在暫存樹給 agent 叫 | `tools_def check` 過、agent 叫得到；做不到就記卡在哪 |
| X2 一段程式化成一棵夾 | 一個 fennel／lua 檔描述一組函數夾（含 `_metainfo` 的 cost），工具展開成資料夾、也能收回成一份 json（C-51 互轉） | 展開再收回逐 byte 相同 |
| X3 深樹壓力 | 暫存樹灌 10 萬檔、深 30 層，量 `find`、`$ref` 連鎖、daemon 一拍掃多久 | 一拍掃描 > 100 ms（300 ms 拍的三分之一）才算出事，那時再定「檔案系統／json／程式」的佔比規則 |
| X4 公式支援 lua | 把 N-68 的 `lua` key 接上（lua 已裝） | 一條 lua 公式算出 cost，跟 `cal` 版同值 |

「三處佔比」本題先不定規則：現在樹太小，量不出差別；X3 過門檻才回來定。整套 aos 用 lisp／lua 重寫、外部 plan9 式接入：記為遠期方向，不排。
