## 三、改後的開發函數的函數（取代 04 支線 F 與 D12 推薦）

| 步 | 做什麼 | 驗收 |
|---|---|---|
| F.0 | `agent_def new --from` 複製兩支受測定義：`devfn-solo`（gpt-worker 副本＋2.3 工具包＋`tools_def`、`self_tools`）、`devfn-team`（gpt-lead＋gpt-worker 副本）；施工隊本尊不動 | 兩支 `agent_def check` 0 problems |
| F.1 | 建固定基準 `devfn-bench`：5 題，每題＝一個呼叫點描述＋輸入輸出例＋3 個 case 夾（從第一階段表抽） | 5 題都有 case，原 agent 過門 ≥ 2/3 |
| F.2 | 兩支各跑 5 題（v0）。花費＝受測 agent 與其子 agent 的 observed think 列 token 加總 | 零介入一次過門 ≥ 3/5；同過門率選花費低的（預期 solo ≤ 8 萬／題、team ≤ 25 萬／題） |
| F.3 | 對勝出那支跑呼叫點表、沉澱出 v1（例如「`tools_def check` 再 `measure`」併成一步） | v1 過門率 ≥ v0、平均問腦次數降 ≥ 25%、平均開發 token 降 ≥ 20%、平均回本件數 ≤ 30 |
| F.4 | 跟舊稿 `_improve` 接上（D16 (a)）：受測節點夾放 `_improve` 薄殼，`AOS_ENTRY=_improve` 時把本節點路徑＋case 夾交給勝出那支 | 同一支 devfn 對兩個不同節點各做出一個過門替代品 |

devfn 的 system 加一段建議（不是硬規則）：判斷分支、迴圈、字串解析寫在 `_entry` 程式裡；json 只放結構、表、資源描述；資料夾只在需要獨立 `_metainfo`、獨立量測或權限時才開。

## 四、改後的第二、三階段（只列跟 04 不同的）

- 2.1：`P/templates/agent-fsm/brain.py` 寫 `prev`、`prompt_hash` 進 `think/sent.json`；`wait.py` 寫 think 列時帶上並補 `next`、`cycle`。
- 2.5：`watch` 驗收＝暫存樹連續餵 5 個後續 case 觸發結算 `kept`；餵 1 個壞 case 觸發 `rolled_back`。
- 2.6：`aos-agent status` 印 `tools_per_think`（每次問腦帶動幾步工具）與 `think_saved`（比基準少問幾成）。
- **2.7（新，第六段寫回）**：`P/lib/tool_spec.py` 產 `_metainfo.json` 時自動填 `cost.source_bytes`（from measured）與 `cost.read_min`（from estimate）；`footprint` 加 `occupies` 自動掃與 `defs dup` 查重。驗收：對 `P/lib/aos/` 全跑 `footprint` 後再 `tools_def check`，兩格都還在、0 報錯；植入一個重名工具與一個同簽名定義都被抓到。
- **2.8（新，3A 回本剎車）**：`P/lib/aos/review_round/` 開改善前算「每次省下 token × N（預設 50）」，小於預估改善花費就拒、回算式。驗收：餵「每次省 200 × 50＝1 萬 < 5 萬」的呼叫點，0 真腦 token 就被拒。
- 3.1（3B）：`resources` 表每列 `from` 可指信的 `body.cost.<key>`、ledger 欄或 `cal` 公式；kernel 不認資源名。驗收：暫存樹 `kernel.json` 加一列 `{"key":"source_bytes","stance":"block","max":5000,"from":"body.cost.source_bytes"}`，寄 `body.cost.source_bytes=6000` 的信被擋，kernel 程式改 0 行。（`from: estimate` 的值若被寫成 `stance: block`，載入時拒。）
- 3.2：`eval_cost` 同時接上 N-68 的 `lua` key（原 X4）。
- 3.5 移到 2.8；其餘 3.x 照 04、依賴照 04。
