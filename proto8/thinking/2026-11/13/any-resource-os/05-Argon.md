## (A) 審查：04 實作計劃的問題清單

### A1.【嚴重度：高】步驟 1.2 驗收「token 合計＝ledger 裡該寄件人那批的合計（差 0）」與事實衝突，不可執行
- **位置**：04 第一節 #2、#7；第三節步驟 1.1、1.2。
- **理由**：
  1. **Ledger 的 `sender` 分不開單一 agent**：01g #7 與 04 第一節 #7 明載，`ledger.jsonl` 的 `sender` 值是**工作區路徑**（如 `/home/lorkhan/repo/aos`），同工作區的 agent 全是同一個寄件人。01g #4 與 #7 顯示活樹 `gpt-lead`（60 列）與 `gpt-lead2`（25 列）共用 `astra-high`（ledger 共 86 列），按 `sender` 根本切不出 `gpt-lead` 的 60 列，驗收必敗。
  2. **History 缺乏時間戳，無法「依時間合併還原」**：04 第一節 #2 寫「把 `history.jsonl`＋`history_removed.jsonl` 依時間合併還原」。但 01g #1 指出 `history_removed.jsonl` 格式為 `{removed_at, op, line, message}`（只有移除時間與原行號），且 `summarize` 會把原文換成 `[aos] summary: …` 留在 `history.jsonl`（01f #2）。若不剔除 summary 行並依 `line` 逆向還原，順序無法對齊；且 01g #1 只驗過 `gpt-lead`（33+27=60），**未查證** `gpt-lead2`（14 vs 25）還原後是否剛好對上。
  3. **試驗場有無 `history`／`ledger` 未查證**：1.1 要抄 `playground-ak`／`ak5` 的 `observed` 與對應 `history`，但 01g #4 只查到 1,538 個極小的 `observed.jsonl`，**未查證**它們是否有對應的 `history.jsonl` 與 `ledger.jsonl`。
- **建議改法**：
  - 1.2 的 token 對帳改為：用 `observed.jsonl` think 列的 `letter` 欄一對一 join `ledger.jsonl` 的 `id`（01g #1、#7 證實兩邊都有信名）。
  - History 還原改為剔除 `[aos] summary:` 行後依 `line` 重組，並將驗收改為「`letter` 對上 `ledger.id` 率 = 100%；history 配對失敗列歸入 `unpaired` 且比例 ≤ 10%」。
  - 1.1 先確認 `playground-ak/ak5` 有無 `history.jsonl`，無則僅跑 `H/` 的 5 隻 agent。

### A2.【嚴重度：高】步驟 1.5、2.5 與第二節（支線 F.1）：混淆「新工具夾」與「同名 agent 定義副本」，且「併步」無法不改呼叫方就生效
- **位置**：04 第二節、第三節步驟 1.5、2.5、支線 F.1。
- **理由**：
  1. **產物定義前後矛盾**：1.5 說替代品放 `defs/<定義名>/`、驗收跑 `agent_def check`（這是整隻 agent 的定義夾）；但第二節與 F.1 卻說開發函數的函數輸出是 `defs/` 下一個「aos 函數夾（`_entry`＋`_tooldef.json`＋`_metainfo.json`）」（這是 tool 夾，驗收應為 `tools_def check`）。
  2. **「併步」必須動到 agent 的 `tools.json` 或 `system.txt`**：03 (0.2/0.3) 的「併步」是把 `上一步 tool X → 這一步 tool Y` 併成一個工具以省下中間那次問腦。若只做一個新工具夾 `XY`（或改寫工具 `X`），卻不更新呼叫方 agent 的 `tools.json` 與 `system.txt` 說明，腦根本不知道 `X` 已含 `Y`，仍會照舊問腦或再叫一次 `Y`。
  3. **`promote`/`watch` 的作用單位未查證**：01f #1、#6 顯示 `measure`、`promote`、`watch` 針對的是 agent 定義副本，文件中**不確定**能否直接對單一 tool 夾做 `promote`/`watch`，也未說明在暫存樹跑完 3 個 case 後，`watch` 在沒有持續流量的暫存樹裡要「盯」什麼。
- **建議改法**：明確規定一次「併步／查表」沉澱包含兩件產物：(1) **新工具夾**（過 `tools_def check`）；(2) **掛上該新工具並更新 `tools.json`／`system.txt` 的同名 agent 定義副本**（過 `agent_def check`）。1.7 與 2.5 的 `measure`／`promote`／`watch` 統一以該「agent 定義副本」為操作單位；2.5 的 `watch` 驗收明定為「在暫存樹連續餵入 N 個後續 case 觸發 `watch` 視窗結算」。

### A3.【嚴重度：高】步驟 1.6、1.7 與 D7：多步長對話 agent 無法直接從頭重跑單一呼叫點，且 Token 預算算式嚴重低估風險
- **位置**：04 第三節步驟 1.6、1.7、第五節 D7。
- **理由**：
  1. **Case 可重放性風險**：01g #3 明載 `measure` 每次起全新 `ws` 與全新 `stack`，只餵一則 `say` 從頭跑。若 D7 選 `gpt-lead`（帶 `sol` 子 agent、多輪收發信，1 張假工單跑 29 次 think 花 37.5 萬 token），要測試第 15 步的某個呼叫點，從頭餵一則 `say` 既可能因為前 14 步分岔而走不到該呼叫點，也必須連動起子 agent。反之，若選 `playground-ak`（單發問答，每個檔 < 3 KB），只有 1 次 think，根本沒有「工具 X → 工具 Y」可併步。
  2. **Token 上限必爆**：若跑 `gpt-lead` 全程 case，1 張工單 37.5 萬 token，1.7 要跑「改前＋改後 × 3 cases ×（初跑 1 次＋repeat 3 次）＝ 24 趟」，總計約 **900 萬 token**，直接衝破 1.7 訂的 200 萬 token 上限。
- **建議改法**：見 (B) 提案 1（改用局部歷史切片 Case 或單步代理 Case，並將 1.7 的 `repeat 3` 限制在單趟 ≤ 5 萬 token 的 case 上）。

### A4.【嚴重度：高】第二節、支線 F.1～F.3、D12：拿活體施工隊 `astra` 兼任被改進的實驗對象，存在統計失真與搞垮施工隊的風險
- **位置**：04 第二節、第三節支線 F.1～F.3、第四節、第五節 D12。
- **理由**：
  1. **自改弄壞施工隊且無 reset**：第四節規定主線由 `astra` (`gpt-lead`) 帶 `sol` 施工；F.3 卻要對 `astra` 自己跑管線沉澱自改。01f #1 明載 `agent_def` 直接改定義本身，且**沒有 reset**、改不了 `fsm.json`/`hooks.json`/`subagents.json`。一旦 F.3 把 `gpt-lead` 改壞，主線第三階段就失去施工隊。
  2. **連 3 張不同工單無法量化進步**：F.2/F.3 用「連續 3 張工單」量「問腦次數減少、開發花費降低」。但不同工單的難度差異遠大於沉澱省下的 1～2 次呼叫，N=3 且題目不固定，量化指標不具可比性。
  3. **開發花費無法用 ledger `sender` 算**：第二節寫「llm kernel 帳照寄件人加總」，同樣撞上 A1 的 `sender`＝工作區路徑問題。
- **建議改法**：見 (B) 提案 2。

### A5.【嚴重度：中】二之二、步驟 1.8、步驟 3.1：第六段最小落地點與 `tools_def check` 機制及 Kernel 收信事實衝突，且拖累第一階段
- **位置**：04 二之二、第三節步驟 1.8、步驟 3.1、第五節 D14。
- **理由**：
  1. **與 `tools_def check` 重產機制衝突**：01f #3 明載 `lib/tool_spec.py` 自動產 `_metainfo.json`，且 `tools_def check` 會**重產兩份定義**。若 1.8 的 `footprint --write` 直接把 `source_bytes`、`read_min` 寫進 `_metainfo.json#/cost`，下次跑 `tools_def check` 時會被覆蓋或因未寫入 `tool.py` 的 `META` 而失同步。
  2. **3.1 Kernel 讀不到函數夾的 `_metainfo.json`**：二之二與 3.1 說在 `kernel.json` 用 JSON 指標指 `_metainfo.json#/cost/source_bytes`。但 01g #7、#8 顯示 `kernel_llm` 收到的是信（`letter.json`），內容只有 `sender`（工作區路徑）與 `body`（`endpoint/request/priority`），**完全沒有呼叫方函數夾路徑**，kernel 無從去讀某個 `_metainfo.json`。
  3. **偏離使用者第六段原意且讓第一階段變胖**：使用者第六段說「`a` 變數命名是否覆蓋其他變數」，指的是**執行期／組合期的環境與命名空間污染**；1.8 做成在 `_metainfo` 手填 `occupies.names` 字串，既不自動也與第一階段「驗證呼叫點沉澱」無關。
- **建議改法**：把 1.8 移出第一階段（保證第一階段夠小，聚焦 1.1～1.7），並依 (B) 提案 3 修正機制。

### A6.【嚴重度：低】步驟 2.1、2.6、分步順序：指紋寫入時機與沉澱度分母定義不清
- **位置**：04 第三節步驟 2.1、2.6、第三階段依賴。
- **理由**：
  1. **2.1 `wait.py` 拿不齊指紋**：01g #1 指出 `think/request.json` 在 `brain.py` 產生（含 `--history task` 裁剪後的最後一則訊息與 prompt），而 `observed` think 列在 `wait.py:395` 寫入。若不在 `brain.py` 把 `prev` 與 `prompt_hash` 寫進 `think/sent.json`，`wait.py` 收信時（尤其當腦回 `BrainFailed` 時）難以單獨湊齊 `site`。

- **建議改法**：2.1 改為 `brain.py` 寫 `prev`/`prompt_hash` 進 `sent.json`、`wait.py` 補 `next`；2.6 改印 `tools_per_think` 與 `settled_calls_ratio`；3.5 的回本檢查提早到第二階段的 `review_round` 工具內執行（見提案 5）。

## (B) 提案：我會怎麼做得不一樣（5 條）

### 提案 1（回應問題 4）：第一階段「雙層指紋＋局部切片 Case」，以及當 1.4 沒有可沉澱點時的明確退路
- **做法**：
  1. **先把 1.8 移出第一階段**，讓第一階段只做 1.1～1.7。
  2. **1.2 分類器做雙層指紋**：
     - **層 A（動作鏈指紋，對多步 agent 如 `gpt-lead`/`sol`）**：先看精細的 `(prev_tool, next_tool + 參數 key 集合)`；若無點過門檻，自動退一步做**粗化指紋** `(prev_tool, next_tool_name)`（忽略參數差異，看是不是固定連招）。
     - **層 B（結構映射指紋，對單發問答如 `playground-ak`）**：算 `(prompt 模板固定前綴雜湊, 輸出 JSON/句式骨架)`，抓出可「查表／八股化（03 0.3）」的單步呼叫。
  3. **若 1.4 在原門檻（佔比 ≥ 20% 且定型率 ≥ 0.9）下完全沒有點，下一步這樣走（三步退路）**：
     - **退路一（放寬佔比、看粗化指紋）**：維持定型率 **≥ 0.85**、出現次數 **≥ 5 次**，但把單點 token 佔比門檻降到 **≥ 8%**（因為多步 agent 的呼叫點自然分散，見 03 D1 判準「前 3 點合計 < 30%」）。

     - **退路三（造 3 張同構小工單補樣本）**：若 125 列真的全是發散判斷，不硬寫替代品，先交出這張基準表，接著給 `sol` 連跑 3 張同類型的標準小任務（如「替 3 個現有小工具補 README 例題並跑 check」，每張約 5～8 步），對這批新歷史跑 1.4，必出高定型率呼叫點。
  4. **1.6 改用「局部切片 Case」**：不從頭起 `gpt-lead` 跑整張工單，而是從歷史把該呼叫點前的對話截成靜態 `history.jsonl` 放進 `case/ws`（或透過 `self_history` 載入），只測該呼叫點往後的 1～2 步。
- **為什麼比較好**：徹底解決 `gpt-lead` 僅 60 列太少、`arknights` 單步無連招、以及從頭跑長工單爆 200 萬 token 預算的三大死結，確保第一階段兩天內一定拿得出前後對比數據。
- **代價**：`callsite` 需多寫約 60 行支援粗化指紋與跨 agent 匯總；1.6 需寫一個從 `history.jsonl` 切出局部 case 的小輔助腳本。
- **可執行判準（門檻數字）**：
  - 1.4 若在「佔比 ≥ 20%、定型率 ≥ 0.9」命中數 = 0，啟動退路一＋二後，在「跨 agent 次數 ≥ 5、定型率 ≥ 0.85、佔比 ≥ 8%」下命中數 **≥ 1**；若仍 = 0 則走退路三（上限耗用 **≤ 20 萬 token**）後命中數 **≥ 1**。
  - 1.7 局部切片 Case 跑完「3 cases × 改前改後 × (1 + repeat 3)」總真腦花費 **≤ 30 萬 token**，且目標呼叫點的問腦次數從 **1 次降為 0 次**（併步後少問一次）。

### 提案 2（回應問題 1）：「開發函數的函數」雛形——拆開施工隊與受測體、先比「單兵 vs 雙人」，並用「固定 5 題微基準集」量進步
- **做法**：
  1. **04 選 `astra 帶 sol` 對不對？只對一半**：拿現成會寫碼的 agent 當起點是對的（不用從零造），但**直接拿活體施工隊 `gpt-lead` 本尊當受測與自改對象是錯的**（一改壞定義無 reset、且雙人派工固定開銷高達數十萬 token，開發一個 20 行的小函數可能永遠回不了本）。
  2. **改法（雙雛形同台競技）**：用 `agent_def new --from` 複製出兩支獨立受測定義（不碰施工隊本尊）：
     - **`devfn-solo`**：單兵 `sol` 定義副本，直接掛上 `tools_def` + 2.3 的 `measure` 工具包，自己寫、自己跑 case。
     - **`devfn-team`**：`astra` + `sol` 定義副本。
  3. **怎麼量它進步（廢除以零散工單量進步，改建固定微基準集 `devfn-bench`）**：
     - 從第一階段歷史抽出 **5 道固定題目**（每題＝1 個真實呼叫點描述＋輸入輸出範例＋3 個 `measure` case 夾）。
