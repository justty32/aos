### 1.4 主軸（頂層 11-13 定，照這個往回推）

**aos 是能優化任意資源、任意目標的作業系統；最終拿去做的事是「把 agent 逐步換成沒有機率性的純函數」。** 你的架構要從這條主軸往回推：哪些機制能把一個 agent 的 llm 呼叫一個一個辨認出來、沉澱成工具或純函數；怎麼量確定性、token、可理解性這類屬性；kernel 怎麼把它們當優化目標；跟現有 kernel、limits、llm kernel、metainfo views、astra 怎麼接。第一步要最小、可量化（頂層舉例：挑一個現有 agent，記錄它的 llm 呼叫，把其中一類固定成工具，量 token 前後差——只是舉例，你自己判斷）。

20261106.md 的要點（頂層摘、以原文為準）：agent(llm, prompts, tools) 是函數；loop＝cpu、fsm＝指令、daemon＝硬體板子、kernel＝一號行程；目標是「優化任意目標」（token、人類可理解性、易操作性）。不確定性的本質＝「脫離掌控的程度」，基準可以是客觀世界（＝機率）或某個人的主觀認知。函數屬性（九軸）是動態的，有時間軸與世界線（機率）兩個維度；檔案屬性是靜態的；屬性有客觀有主觀，值可以是數、字串或 json。優化法：函數拆子函數，把帶機率的子函數換掉；對 agent＝減少 llm 呼叫、工作堆到 tools（台詞例：景色走固定描述工具、人物對話交給各角色專屬 agent）。最終：RSI 把 token 降到 0、同時提升智能，再把「提高智能的速度」也當目標＝RSI 飛輪。

### 1.5 頂層最早對題目的理解（不是定論）

aos＝以「任意資源」為對象的作業系統；資源用自由 key 的 json 表示、可粗化／細化（轉換公式自由、AI 處理）；在這之上的資源分配與排程也自由、AI 處理；proc＝一段（不一定是真實）時間裡的影響或樣貌切片，考慮外在影響、機率、世界線。第二段加：人類可理解性是 kernel 可以優化的目標；「什麼都是檔案、json」讓 AI 最好用；效能換可理解性值得；上千上萬 agent 共用十幾格的端點。

## 2. aos 速覽（給你的心智模型）

- aos＝「資料夾＝程式」的 AI agent 體系，蓋在 Linux 上，每隻 agent 是一個普通 Linux 行程、住在資料夾裡。
- 八個詞：**definition**（定義資料夾＝原始碼）、**stack**（一個在跑的東西的狀態夾＝記憶體）、**workspace**（工作夾＝外接硬碟）、**daemon**（機器：一張 proc 表＋一雙照表起停行程的手）、**proc**（daemon 底下一個在跑的東西）、**kernel**（請求寄去的地方，決定准不准、何時跑）、**letter／mailbox**（信是一個含 letter.json 的資料夾，丟進信箱夾）、**tool**（可呼叫的資料夾，吃 JSON、stdout 回答）。
- 分層（C-02、C-03、10-11 技術棧）：第 0 層 Linux → 第 1 層 daemon（「有了它，aos 等於有了『硬體』」）→ 第 2 層時空（空間＝資料夾、時間＝時鐘，一格叫 cycle，約 1 秒，可停、可脫鉤）→ 第 3 層資源分配與排程（**當年標「還沒展開」**）→ agent。
- **image 模型**（C-79）：daemon＝硬體、stack＝記憶體、ws＝外置記憶體、定義＝source code。整樹可凍住搬家。
- **kernel 是門、daemon 是手**（11-12 使用者同意）：「每一層的硬體是它的上一層」——根 daemon 的硬體是 Linux，子 daemon 的硬體是根。kernel 是**主觀的**概念：對寄請求的 proc 來說，請求寄去的那道門就是它的 kernel；什麼都不管（來者不拒）也算一種管理。kernel 可以串成鏈（agent → kernel_1 → kernel_2 → … → daemon），站與站之間都是信。名字都不改。
- 任何 agent 都能當 kernel（`kernel_gate` 工具：請求先留著等 agent 表態 pass／refuse）。astra（gpt 指揮者）當 kernel、底下掛 sol 的規劃已裁照推薦、未施工。
- 問腦＝寄信給 **llm kernel**（`AOS_LLM_KERNEL`），它照 endpoint pack 的 slots／priority／budget 挑信，放行一封就在 daemon 掛一個短命 proc 去打端點。

## 3. 已裁、不能翻的原則（設計要順著它們）

| 原則 | 出處 | 對這題的意思 |
|---|---|---|
| JSON 不認得的 key 一律忽略、不報錯；各功能可在同份 JSON 放私有 key；值有「雙形」：純值 `3` 或展開形 `{"val":3,…}`，像 Lisp 的 `3` 與 `(+ 1 2)` | C-48（使用者 10-23「不認得的key就是忽略」） | 「key 隨意、程式只認它要的」**早就是規範**。粗化／細化跟「雙形」是近親。例外：工具參數不認得的 key 報 `ArgumentsBad`（給人或給工具的嚴格介面） |
| `_metainfo` 裡每一格（`cost`、`timeout_ms`、`sandbox`、`resource`…）**全是觀點、參考用，出事自負**；壞掉＝當沒寫、略過不擋；被記下來且非私有的＝通用視角（公用視角，「自己公開給別人的聲稱」），私有的＝主觀、放哪不規定 | N-69、metainfo-views（11-12 裁） | 資源的描述天生是「誰的觀點」；沒有唯一客觀描述。真要擋，靠 Linux 權限／rlimit／沙箱 |
| `cost` 是函數自己宣稱的估值，三維 token（in/out/cached）、呼叫次數、時間；「還想放什麼就放（錢等等）」；值可寫公式，**公式用語言名當 key**（`cal`→`lua`→`py`→`aos`），「搞不好到後面，就是呼叫aos agent」；讀者沒那種求值器＝當沒估值 | N-68（使用者 11-07） | 「透過某種公式轉、公式定義可以隨意」**已有骨架**：求值器可換、最後可以是 agent |
| 資源＝「有限的東西」，有限用「格數」表示；資源本身也當行程看；**一切都是計算任務** | C-09～C-12（10-11） | 新話把資源放寬到「任意，甚至沒影響也可以」——跟「有限才是資源」有張力，要處理 |
| 排序程式可以由人寫，也可以由「生成排序程式的程式」叫模型寫；「目標多到只能靠模型寫，所以核心要讓模型好用」 | C-15、C-01 | 「排程自由、AI 處理」是 10-11 就有的方向，第 3 層從沒展開 |
| 要最佳化的不是時間空間，是**金錢、可預測性、人能不能理解** | C-24 | 第二段的「可理解性」「可預測性」**早就寫在條文**，只是沒有機制 |
| 可預測性有主體性：是觀察者的認識，不是任務屬性；確定性≠可預測性；能寫死的節點換成程式，降低走進不可預測節點的機率 | C-21、C-22、C-22b | 「可預測性優化」的已知立足點 |
| process＝過一段時間後造成的變化，變化指空間上的變化；求值＝放開讓它算、過一段時間看狀態變化 | C-33、C-34 | 新的 proc 定義是 C-33 的擴充：加「應當」（預期）、切片、外在影響、機率、世界線 |
| 空間可以擴到外部設備（資料庫、雲端…，像 Plan 9）；資源、設備、PU、行程全是空間裡掛著的節點；大家可以有自己的時間軸 | C-30、C-31、10-11 3f.5 | 資源「住在」空間裡＝資料夾節點 |
| kernel 只定政策、daemon 在 fork 時真的套（setrlimit、可選 cgroup、免 root subuid 換身分） | kernel-limits-plan（11-13 已裁、未施工） | Linux 那層「本質資源」的限制已有規劃 |
| 安全的保底是 Linux 本身（使用者、權限）；非正規操作風險自負 | C-47 | — |
| 被拒是決定不是 bug；agent 回報或調整，不硬闖 | 知識庫規則 5 | 資源分配的結果給 agent 看的方式 |

## 4. 現有零件：跟「資源、花費、額度、排程」有關的全部（事實）

### 4.1 有實際行為的

| 零件 | 管什麼 | 單位／格式 | 位置 |
|---|---|---|---|
| llm kernel 的 **slots** | 同時在飛的腦請求數；總格、每 pack 格、每後端格、`reserved.high` 保留格 | 個數 | `kernel.json` 頂層與每 pack |
| llm kernel 的 **budget** | 每窗（hour/day/all）的 `max_calls`、`max_tokens`；三層：整台、每 pack、每寄件人（`senders`）；到頂 `spent:"refuse"` 回 `BudgetMissing` 或 `"wait"` 留隊等下一窗；**不替人換便宜 pack** | 次數、token 合計（in+out 不分） | `kernel.json`；帳在 `$AOS_STACK/used.json`、逐封 `ledger.jsonl`（含原始 usage、elapsed_ms，無金額） |
| llm kernel 的 **priority** | `low/normal/high`（數字只看正負）＋`deadline`；等久了每 `aging_cycles` 升一級；排序鍵：有效級→期限→同後端黏著→pack 速度→等多久→先寄 | 三級＋時間 | 信的 `priority` |
| kernel 站（掛 proc 那包） | `allowed` 名單、`max_running`（同時 running 的 proc 數）、`queue`、`queue_wait_ms`、`next`（串下一站）、三個 hook 時機（判前、判後、回信經過）、hold 等表態 | 個數、毫秒 | `lib/aos/kernel`、`kernel.json` |
| daemon 的 **limits** | setrlimit：`mem_mb`、`cpu_s`、`procs`、`file_mb`、`files`、`user` | MB、秒、個數 | daemon.json 每列；只是每行程各自上限，不從總額扣 |
| aos-sandbox | bwrap＋s6-softlimit：看得到哪些夾、網路、同上五種上限 | 同上 | `_metainfo.json#/sandbox` |
| `max_subagents` | 同時活著的子 agent 數（預設 4） | 個數 | `subagents.json` |
| aos-exec `timeout_ms`／`timeout_cycles` | 牆鐘或 cycle 逾時；沒時鐘時 cycle×`AOS_CLOCK_INTERVAL` 換成毫秒 | 毫秒／cycle | inst 單子 |
| goal `limit`、cooldown、`--max-tool-calls` | 沒進展提醒次數、外部服務失敗退避秒數、一輪思考的工具呼叫數 | 次數、秒 | agent 範本 |

### 4.2 只是宣告、沒有程式拿來做決定的

- kernel.json pack 的 `cost:"high"|"free"`、`context`（`speed` 例外：用來排序）——只被抄到 `aos-llm ls`。
- 所有工具 `_metainfo.json` 的 `cost`（實際全是 `{"time_ms": n}`，只有 `llm_forward` 寫了 token）與 `resource`（`"cpu"`、`"disk"`、`["cpu","llm"]`…，字串陣列兩種寫法並存，`tool_spec` 檢查只收字串——小不一致）。

- `lib/aos/measure`：另一套量測聚合，token 分 in/out/cached。

### 4.3 缺口（四份蒐集一致）

1. **沒有統一的資源模型**：個數、次數、token、毫秒、cycle、MB 各管各的，沒有共同表示、沒有跨層扣額或繼承（例外：llm-team 轉給主 kernel 時，主 kernel 把整台上層算一個寄件人）。
2. **沒有任何換算／粗化／細化的程式**：唯一的換算是 cycle↔毫秒、priority 數字→三級、speed 字串→索引、MB→byte。沒有「cost 字串→token→錢」、沒有「多資源合成一個總額」。
3. **`cost`（估計、觀點）跟 `limits`／`budget`（強制）沒接起來**：估值不擋任何事，強制的那幾個不讀估值。
4. **「資源」在知識庫沒有定義**，agent 看不到「我有什麼資源、剩多少」的統一視圖（只有 self_state 的 limits、記憶體、cpu 時間）。
5. **proc 在程式裡只是一列表**（pid、phase、reason、limits…），沒有「預期影響」「軌跡」「機率」任何欄位；時鐘只有一條（可脫鉤），沒有分支或世界線。
6. **人類可理解性、可預測性只在條文（C-24、C-21/22）**，沒有任何被量、被當資源或目標的機制。`metainfo_check`（宣稱 vs 實測）是唯一跟「可預測」沾邊的程式。

## 5. 規模：上千上萬個 agent 共用一個端點（只從程式推，沒實測）

- 端點那側：slots 機制夠用，「十幾格」就是設 slots；每放行一封＝掛一個短命 proc，同時只有 slots 個。
- 瓶頸由先爆到後爆：
  1. **agent 端輪詢**：每隻 agent 每 300 ms 一拍，每拍起一支新 Python（idle／wait 格），等腦時每拍再起一支 `aos-llm recv`。粗估 1000 隻≈30～80 顆核的輪詢負載，**遠早於 kernel**。拍子拉長是最便宜的槓桿，但延遲變大；daemon-interrupt（事件喚醒）有討論、範本沒接。
  2. **llm kernel 每輪全掃等待信**：每 300 ms readdir 全部、逐封整份解析 letter.json（含對話歷史）、逐封解 pack、排序拷貝。O(等待數×信大小)、無快取。1 萬封帶歷史的信＝每輪讀解 GB 級。
  3. **沒有公平與上限**：排序鍵沒有寄件人（近似全域 FIFO），一隻灌 1 萬封會把別人擠到後面；沒有等待上限、沒有每人同時在飛上限、排隊沒逾時（不寫 deadline 就永遠等）。
  4. `used.json`／`queue.json` 每完成一封整份重寫＋fsync，`senders` 每個寄過的人一列。
  5. 單信箱單 kernel 一把鎖；水平擴＝多個信箱多個 kernel（llm-team 已能串到主 kernel）。
- 從沒量過 llm kernel 的大量等待信；daemon 層壓過 3000 信、200 loop、4300 列表（10 ms 間隔閒著 82% CPU）。
- 使用者 11-08 自己說過：「LLM endpoint 同時間只能處理十幾個請求…不可能一臺電腦上跑上千個 LLM agent」，上千的是「無 LLM 的函數節點」。第二段說「上千上萬個 agent（共享一個端點）」——**這兩句的關係要你指出**（是大多數 agent 大多數時間不在問腦？還是排隊等很久也可以？）。

## 6. 要你設計的（請逐題回答）

**0. 主軸：把一個 agent 逐步沉澱成純函數的管線（最重要，先答）。** 從 1.4 往回推：一隻 agent 的每次 llm 呼叫怎麼被記下、分類（哪些是「同一類」）、評估能不能固定（固定成模板／查表／一般程式／更小的專屬 agent）、換上、量前後（token、確定性、品質）、變差退回；這條管線在 aos 裡由哪些零件組成（4.4 的現成零件能用多少）；kernel 在其中扮演什麼（把「token 降到 0」「確定性」當優化目標去分配與排程）；人在哪一步給 ground truth。下面 1～9 題都從這條主軸的需要回答，跟主軸無關的部分可以簡答。

1. **一張總圖**：「任意資源」放進 aos 分層後長什麼樣——第 3 層（資源分配與排程）終於展開時，由哪些零件組成、跟 daemon（手）、kernel（門）、時鐘、資料夾、`_metainfo`、llm kernel、kernel_gate、kernel-limits-plan 怎麼接。哪些是「Linux 給的本質資源」（cpu/mem/權限/資料夾），哪些是「aos 抽象出來的資源」（腦請求、token、子 agent 格、人的注意力、可理解性…），兩者怎麼放在同一個模型裡。
2. **資源的表示**：自由 key 的 JSON 怎麼當「資源描述」用，又不至於誰都讀不懂。誰宣告資源（資源自己？kernel？通用視角檔？）、放在哪（空間節點？`_metainfo`？kernel stack？）、怎麼被找到。「有限才是資源（C-09）」跟「任意、甚至沒影響也可以」怎麼並存。
3. **粗化／細化（換算）**：`cost:{token:10,time:1s}` ↔ `cost:7` ↔ `cost:{token:{in:6,out:4},time:1s}`。換算公式住在哪、誰提供（寫死的公式、`cal`/`py`、叫一隻 agent）、換算結果是誰的觀點、換錯了怎麼辦、需要換算的是誰（kernel 判額度時？agent 自己估時？人看報表時？）。跟 C-48 值雙形、N-68 公式 key 的關係。
4. **自由的分配與排程**：kernel 的政策怎麼「自由」——規則表、hook、AI 寫的排序程式、AI 當門（kernel_gate）各在哪一級；AI 參與時怎麼避免每封信都要問腦（成本、延遲）；誰能改政策、改壞了怎麼退。
5. **proc 新定義**：「一段時間中應當造成的影響／某事物應有的樣貌、沿時間軸的切片、外在影響、機率、世界線」。在 aos 裡怎麼表示才有用（例如：proc 帶一份「預期軌跡」、時鐘的每格是一個切片、實際 vs 預期的差、分支＝凍住的 image 複本？）。哪些現在就能做、哪些是遠期。**這是使用者自己說「有點抽象」的部分，給他幾種讀法與各自的第一個具體落腳點就好，不要過度設計。**
6. **可理解性與可預測性當作 kernel 能優化的目標**：怎麼量（哪怕粗略、由 AI 給分）、記在哪、kernel 怎麼拿它來排程或分配（例：同樣的工作，派給輸出更好讀的 pack／agent；可預測性＝宣稱 vs 實測的差，`metainfo_check` 已有雛形）。
7. **規模**：上千上萬 agent 共用十幾格端點，架構上要動什麼（事件喚醒取代輪詢、kernel 的等待信索引、每寄件人公平、等待上限、分層 kernel 串接…），哪些屬於這題、哪些該另開題。
8. **分階段**：從現在到「有一個看得到的成果」的最小第一步（要小、**可量化**、一兩天、不停樹最好；例：挑一個現有 agent、記它的 llm 呼叫、把一類固定成工具、量 token 前後差），以及後面兩三個階段。每階段說清楚：產出、用到哪些已有零件、驗收時使用者看得到什麼。
9. **待使用者裁**：所有方向性分岔列表，每題：選項、你的推薦、後果、可執行判準（門檻數字或看得到的現象）。

linux等普通作業系統，其優化目標以時間，資源消耗最小化爲主。但在agent時代，還有其他目標如token用量，人類可理解性，易操作性等等。所以aos系統的目標就是優化任意目標。
到了這裏，我們就有了很好用的工具。
ps.aos kernel被設計爲一號行程，但實際上，我們在aos體系中標明，任何管理行程與資源的行程，都可以用kernel做稱呼，只是說標準實作上我們提供的kernel通常都是一號行程，占有對於某個daemon的唯一控制權。

下一步，是這工具可以用在什麼地方。
既然可以優化任意目標，那我們可以將目光放在一個LLM agent的痛點上：不確定性。
不確定性，其本質就是脫離掌控的程度。倘若脫離的目標是客觀世界，那就等同機率性。其他的，可以是對於人類而言的不確定性，可以是對於你我他任何一個特定人的不確定性。
除此之外，脫離掌控的東西也可以任意的，比如token消耗的程度之類。
而我想要的，就是讓agent可以完全隨我心意去做。常規做法，以先前那個pseudo code所描述的模式來說，就兩種，一種是prompt engineering，另一種是對工具做操作。
這裏不多做贅述，總之要達到完全隨心意這點，有很多方式。
我要做的，是用RSI的方式，使其隨我心意。而我窮，且又看不得AI如此之笨，所以我要做的事情可以這樣描述：
在aos體系的幫助下，實現以RSI方式，持續降低token消耗直至0，並且提升AI智商的路途。

雖然現在仍在給aos體系打基礎，但我可以先簡單起個頭，說明我想怎麼做：
我想讓agent完全隨我心意去做，等同於我想讓這個函數的一些屬性達到一個目標。
那麼一個函數可能有啥屬性？最基本，四處都通用的就是這個函數九軸特性。
這個函數屬性，他是相對於檔案屬性的，一個是動態一個是靜態。真要細說的話，那其實可以是維度上的區別，檔案屬性，就好比物體的長寬高，很容易理解，而函數屬性，則描述了時間軸上的區別，乃至於世界線上的區別(機率)。
除此之外，屬性這東西，除了客觀也還有主觀。應該說，有光才有影，有了相對才有存在，所以你要找一個參照物作爲你的值的基準，對於物體而言，其參照物就是現實物理規律，而函數九軸的參照物則是現實公理基礎。
那假如其基準，是一個抽象化的東西，或者說，乾脆就是人的主觀認知呢？比如一個用agent產出galgame臺詞的函數，對於我這個臭宅男來說，這個函數的臺詞傲嬌程度就是0.4。並且也不一定要是值，甚至可以是一個字串或json物件，比如"缺乏靈活性"、{"pretty":12, "good":true}。

講完了函數屬性的性質，接下來講如何優化他。
一個函數可以拆分爲多個子函數，這個函數的屬性自然由這些子函數決定。所以假如這個函數是機率性的，自然只要將其具備子函數中具備幾率性的，給替換掉即可。
換到agent中，從pseudo code中可以看到，不確定性來自於那個llm呼叫。要降低這個函數的不確定性，自然就是減少llm呼叫，盡量讓工作都堆積到tools。
好比一個生成llm臺詞的任務，常見的做法是只走prompt engineering，tool只給基本的read/write/shell等，讓llm自己去查相關背景。想要提高確定性，那就是稍微改一下，將臺詞拆成景色描寫與人物對話，景色這塊可以用工具找固定描述，人物對話這塊可以透過工具，將需求丟給專管各人物的各agent，讓他們生成。

好，我這邊做個收尾
既然可以優化任意目標，那，是否可以將目標設置爲：提高智能，以及，提高"提高智能"的速度？
RSI的飛輪，自此而始
ps.其實AI不笨。只是說AI缺乏持續學習之類的，並非死記硬背的智能面向。
