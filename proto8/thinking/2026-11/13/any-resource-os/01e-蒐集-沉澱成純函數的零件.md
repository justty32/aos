## 1. 函數九軸

**重要事實：aos 條文沒有逐條列出九軸。** 條文只寫「九軸」二字，名單散在兩處，且兩處不是同一份。

- 條文：`docs/CONCEPTS/04-kernel.md:9` C-13「每個計算任務都有固定的基礎特性（九軸）；其中確定性是任務自己的屬性。」；`:10` C-14「基礎特性之外，人可以任意附加特性。」；`docs/CONCEPTS/附錄1-名詞.md:32`「九軸｜每個計算任務固有的計算性特性：副作用、冪等、碰外部檔案、持續性、有無 entry、確定性……」（只列六個，用「……」收尾）。
- 使用者口述原版（10-10 河堤）`thinking/2026-10/11/restart/02-河堤後段.md:3-17`（2.9）：列六條——有沒有副作用／冪等性（處理完這個再處理下一個，方式是否一樣）／要不要碰外部檔案／是不是持續性的／有沒有 entry／確定還是不確定（「跑大語言模型的任務就是不確定的」）。同段括號：「原文在 repo 外 `~/repo/ai_core/docs/kb/kb-ss/doc_05_axes_metadata.md`，套到 aos 的討論見 proto7 axes-astra：**I/O 型態、生命週期、跨呼叫狀態、資源特性、可中斷性、執行保證、組合模式、環境模式、確定性**」——這是完整九個（proto7 版）。
- `thinking/2026-10/24/metainfo/01-位置與格式.md:53,64`：「行為（九軸裡 kernel 用得上的幾軸）」，其餘「I/O 型態、生命週期、組合模式、環境模式先不列通用 key，要用的人自己加」。
- 使用者 11-06 `user-advice/20261106.md:49-51`：「最基本，四處都通用的就是這個函數九軸特性…函數九軸的參照物則是現實公理基礎」（主客觀的參照物之說）。
- evo-A 備註（`thinking/2026-11/07/evolve-design/README.md`）：「函數九軸是基礎特性，我們是建議不管多簡單或多笨的函數或agent都準備一份描述這個的metainfo啦，但不強迫。」

### `_metainfo` 通用 key 與九軸對應（N-69，`docs/NORMS/10-基礎設施-定義與工作區/11-N-69.md:10-11`；表在 01-位置與格式.md:40-62）

| key | 型 | 意思（逐字） | 對應九軸（proto7 名單） |
|---|---|---|---|
| `side_effect` | bool | 「會不會動到自己 stack 以外的東西」 | 執行保證／資源（口述「副作用」「碰外部檔案」） |
| `idempotent` | bool | 「同樣的輸入重跑一次，結果跟跑一次一樣」 | 執行保證（口述「冪等」） |
| `deterministic` | bool | 「同樣的輸入每次輸出一樣（問腦的通常 false）」 | 確定性（作者宣稱） |
| `interrupt` | `safe/unsafe/resumable` | 被殺掉會怎樣 | 可中斷性 |
| `parallel` | bool | 同函數可否同時跑多份 | 跨呼叫狀態／組合（近似） |
| `resource` | 字串或陣列 | `llm/gpu/cpu/disk/net/human` | 資源特性 |
| `arbitrary_exec` | bool | 呼叫者給什麼就跑什麼的工具；C-22「是 C-14 的附加特性、不是第十軸」 | 附加特性（非九軸） |
| `summary`、`cost`（`token.in/out/cached`、`counter_calls`、`time_ms`）、`timeout_ms`、`comfort`、`sandbox`、`lineage` | | 見 N-68 | 非九軸（成本／行為／血緣） |

沒有 key 的軸：I/O 型態、生命週期、組合模式、環境模式（「要用的人自己加」）；「持續性」「有無 entry」口述有，但 `_metainfo` 沒對應 key（entry 由 `_entry` 檔表達，N-57/N-61）。

實例（`lib/aos/watch/_metainfo.json`，全文）：
`{"summary":"Track promoted definitions and roll back failed quality or cost windows","resource":["disk","process"],"side_effect":true,"idempotent":false,"deterministic":false,"interrupt":"unsafe","parallel":false}`

讀的人：aos-mcp 把 `side_effect/idempotent/resource` 轉成 MCP 提示；act/aos-mcp 照 `timeout_ms` 殺；`shell_report` 看 `arbitrary_exec`；`metainfo_check` 讀 `cost`；kernel 不讀（N-69:11）。讀取程式 `lib/metainfo.py`（`read`、`timeout_ms`、`eval_cost`；壞的當沒寫）。
注意：「確定性」是作者宣稱，不是量出來的；量出來的「確定性」是 C-22 的「同一份定義、同一 case 重跑的自洽」（measure 的 `consistency`）。

## 2. 自我改進機制

### 條文
- **C-22**（`docs/CONCEPTS/05-agent/01-續-C-22.md:5-`）：「提高 agent 可預測性的方法：當 S 表示式拆開，能寫死的節點換成程式，降低走進不可預測節點的機率。」「**優化目標是確定性**…領域越狹小，能夠變成工具的地方就越多，所需的llm model就越是不用那麼高級，token也能省下來。」三段：`open`（有任意執行工具、沒沙箱）→`boxed`→`none`（全是專屬工具），階段由工具清單推出、不存欄位；「機器只往緊收」：審視者三招 extract（把一種 shell 用法做成專屬工具）／box／unshell，「同一形狀連續 2 個 case 出現才算數」，「三招現在只開處方、不自動做」。確定性＝重跑自洽，分腳本步、LLM 步、整體三層報。
- **C-84**（`docs/CONCEPTS/05-agent/03-C-84.md:5`）：「系統自己改進函數：改好的自動換上，變差自動退回，容忍短暫退步」；「品質一次不合格就退；成本看換上後 3 個 case 的平均，貴超過一成才退」（代定、可改）。「換上、退回與盯梢已實作」；「處方階段已實作（審視者範本 templates/reviewer）；**還沒做的是審視者放手自己寫 fix／split 副本，以及第二層審視**」。語意錯先交高階模型當裁判（`templates/judge-llm` 已實作）。「程式門驗過的規則是資料，門就是審…實作未排」。
- **C-55**（`docs/CONCEPTS/01-設計理念/05-續-C-55-函數成長.md:6`）六級：0 內嵌單子 → 1 同檔具名 `fsm.json#/fns/x` → 2 單檔 `x.json` → 3 資料夾只有 `_entry` → 4 資料夾含腳本/prompt/`_metainfo.json` → 5 資料夾內有子函數（自有 loop/fsm）。「呼叫方從第 2 級起只寫名字」，故 agent→子函數拆開、呼叫方不用改。往上長訊號：≥2 格同單子、被 ≥2 檔叫、有 ≥2 個步驟要暫停續跑、估時 ≥60000 ms。
- **C-89**（`docs/CONCEPTS/05-agent/05-C-89-不同質與族譜.md`）：「定義就是身份」；簽名比工具／腦／記憶；`lineage` 出生時寫一次、之後不回寫；退休＝搬進 `retired/` 樹。

  - 一次思考的輸入：`$AOS_STACK/think/request.json`（`{"messages": system + history}`，brain.py:191、203-212；system 每次從檔讀、不存進 history）；`think/pending.txt`（信名）、`think/sent.json`（時間、endpoint）、`think/reply/`（信箱）。
