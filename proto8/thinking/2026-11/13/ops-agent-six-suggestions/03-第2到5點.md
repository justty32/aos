## 第 2 點：索引沒有檢查工具

**事實：對（讀碼）。** index 包（`lib/packs/index.json`）只有一支 `index_view`；`lib/aos_index.py` 不查節點在不在。這是設計時明講的：[C-88](../../../../docs/CONCEPTS/05-agent/04-C-88-記憶與index.md)「index 是視角，不是事實」「index 沒列到的節點不管」、`index_view`「只讀這兩格，其他鍵不讀、不檢查、不印」；[index-tools](../../12/index-tools/README.md) 的結論「不查節點在不在、不附型別大小」。使用者當時還留了一句「後續什麼agent自己存、更新啥的……就後續再說」，所以檢查工具沒有被否決過，只是沒做。

**分類：新功能。** 跟原則沒有衝突——檢查工具只回報「視角跟實際差在哪」，不強迫補齊；「檔在但沒列」照 C-88 本來就不算錯，所以只能是參考訊息。

**最小做法：**

- 新工具 `index_check`（唯讀），放 `lib/base/index_check/`（殼）＋ `lib/aos_index.py` 多一個函數（共用 `spot()`，index 放哪仍只寫一處）；登記進 `lib/packs/index.json`。eca 範本的 `tools_sub.json` 本來就整包疊 index 包，登記進去子 agent 就自動有，只要改它 description 裡列的工具名。
- 參數：`path`（一個夾或一個 json 檔）、`recursive`（預設 false）、`unlisted`（預設 false；true 才列「在但沒列」）、`limit`／`offset`（同 `index_view` 的分頁）。
- 一行一則，前綴分四種：`[missing]` 索引有列但節點不在；`[link]` 條目的 `index`（或字串形的 `_index`）指不到東西；`[shape]` 條目不是物件或沒有字串 `description`（順便收掉第 3 點）；`[unlisted]` 在但沒列（要了才給）。最後一行總計；有沒有問題都退 0（查到問題不是工具出錯，照 P-41 只有工具自己壞才退 1）。
- 邊緣狀況：鍵是 json 指標（`data.json#/items/0`）要解到檔裡面去查；`_metainfo.json#/index` 那一處也要查（N-69，壞的 `_metainfo` 照舊略過＋註記）；遞迴時跳過 `.git`、`.stack`、隱藏夾與符號連結迴圈；大樹要有上限；`_index.json`、`_metainfo.json` 自己不算「沒列」。
- 動的檔：`lib/aos_index.py`、新 `lib/base/index_check/`（`_entry`、`_tooldef.json`、`_metainfo.json`）、`lib/packs/index.json`、`lib/tests`、knowledge（`tools/index_check.json`、`tools/_index.json`、`packs.json#/about` 的支數、`tools/index_view.json` 加一句指路）、`templates/eca-claude/tools_sub.json` 的說明、範本 README 的支數、code map。
- 工作量：一人半天到一天。

**另一條路（寫手建議先走這條）：** ops-agent 說它會先自己寫一支 Python。請它直接寫成 aos 工具的形狀（一個資料夾、`_entry`、stdin 一份 JSON、錯誤一行，P-41），用 `self_tools` 掛在自己身上跑一陣子；好用再照上面的規格收進 index 包。這是使用者 11-07 說的路（「agent作爲萬能函數，拆出來的子功能……後續再慢慢優化成函數」），也讓規格先被真實的幾十份索引磨過。兩條路不衝突，差在先後。

## 第 3 點：`index_view` 對字串形條目

**事實：一半對（實測＋讀碼）。** 文件確實只寫物件形。但「照樣印出」不準確：字串形的那一項**只印出鍵，那句話被整個丟掉**，沒有警告、退 0。重現：

```text
d/_index.json:
{"README.md": "one line as a plain string", "a.md": {"description": "object form"}, "n.md": 5}

index_view {"path": "d"} 印出：
[index] d/_index.json, 3 entries
README.md
a.md	object form
n.md
```

程式在 `lib/aos_index.py` 第 215～219 行（「項目壞掉或沒有 description：只印鍵」）。這是設計時的代定 I14「項目壞掉不報錯、只印鍵；整份 index 不是物件才 `IndexBad`」（[index-tools 01-圖紙](../../12/index-tools/01-圖紙.md)，依 C-48「不認得的忽略」）。格式本身使用者定過：C-88「格式 `{名: {"description": …}}`，值用物件，以後不只放 description」。順帶一提，使用者 11-12 第一次口述時舉的例子就是字串形（`{"xxx":"store some values"}`，[index](../../12/index.md) 原話），後來才改口定成物件——所以 agent 會寫出字串形並不意外。

**分類：文件缺（補一句）；要不要多印一個記號是小設計題。**

**文件怎麼改**（`proto8/knowledge/aos/tools/index_view.json` 的 `_description`，在「An entry may hold any other keys too; index_view reads only `description` and `index`…」那句後面加）：

> An entry must be an object: `"a.md": {"description": "..."}`. A plain string (`"a.md": "..."`) is not an entry: only the key is printed and the text is lost, with no warning.

同一檔最上面那句 `one line per entry KEY<TAB>description` 不用動。

**小設計題（照原則已可代定，不必問）：** 要不要讓 `index_view` 在這種行尾印個記號。照 I14 與 C-88「不檢查」＝不加；形狀檢查歸第 2 點的 `index_check`（`[shape]`）。「字串形也當 description 收」不建議：C-88 明定值用物件，收了等於多一種格式。

## 第 4 點：mailbox 留底進不了 workspace

**事實：對（讀碼＋實測）。** `mailbox_read` 的 `keep` 只收布林（`lib/agent/mailbox_read/_tooldef.json`），留的地方固定是 `<stack>/mailbox/archive/<信名>/letter.json`（`aos-mailbox read --keep` → `aos-post done --keep`）。[P-48](../../../../docs/CONVENTION/02-題目stack停錯腦/10-P-48.md)「預設讀完就沒，可選留著（`archive/`）」。另外它沒提到但同樣存在的一半：**寄出去的信，寄件人這邊完全沒有留底**（實測：寄完之後寄件人的 `mailbox/` 是空的）。

照原則怎麼看：[C-65](../../../../docs/CONCEPTS/03-基礎設施/02-資料夾程式-工作區與-stack.md)「對話（queue、history）也是這次執行的狀態、落在 stack」、C-79「stack＝記憶體、ws＝外置記憶體」——信預設落 stack 是對的；但「agent 之間約定的紀錄要給人看、進 git」是成果，放工作區也對。兩邊不衝突：預設不變，agent 自己選要不要多抄一份到工作區。

**分類：新功能（小）；現在就有避法。**

**現在就能用的避法（實測過）：** eca 有 Bash，`aos-mailbox` 本來就能印 JSON：

```sh
aos-mailbox -s "$AOS_STACK" read --all --keep -j >> mail/inbox-2026-11.jsonl
```

一封一行（`letter`、`from`、`status`、`title`、`what`、`sent_at`、`reply_to`…），同時照舊留在 `archive/`。已經讀掉、留在 archive 的舊信：`cat "$AOS_STACK"/mailbox/archive/*/letter.json`。寄出的信要自己在寄的時候另記。**注意**：每行的 `sender`、`reply_to`、`to` 是絕對路徑（帶家目錄與機器上的擺法），直接進 git 會把這些帶進去，要先濾掉或接受。

**最小做法：**

- `aos-mailbox read` 加旗標 `--keep-to FILE`（把讀到的每封照 `-j` 那一行的格式接在 FILE 後面；可以跟 `--keep` 併用）；`mailbox_read` 的 `keep` 收 `true` 或一個路徑字串（相對路徑從工作區算，比照 `self_history` 的 `"keep": "FILE"`）。
- 寄件那邊對稱：`aos-mailbox send --keep-to FILE`、`mailbox_send` 加 `keep`，把寄出的那封接進同一個檔——不然紀錄只有一半。
- 邊緣狀況：先寫檔、寫成功才把信從信箱收掉（寫不了＝`WriteFailed`、信留在 `cur/`，下次 read 還讀得到）；`--all` 讀到一半寫失敗＝前面幾封已收、這封與後面的留著；壞信照舊丟、不進檔；絕對路徑欄位要不要在留底時改寫（建議留底那行不放 `sender`／`reply_to` 的絕對路徑，只留 `from`／`to` 名字與信名）；兩個行程同時接同一個檔（一次 `write` 一行、開檔用 append）。
- 動的檔：`cmd/aos-mailbox/aos_mailbox/__init__.py`、`lib/agent/mailbox_read/`、`lib/agent/mailbox_send/`（`_entry`、`_tooldef.json`）、`cmd/aos-mailbox/tests`、knowledge（`mailbox.json#/tools`、`cli/mailbox.json`）、P-48 一句、code map。
- 工作量：一人半天。跟原則沒有衝突（P-15 定義不被寫：不碰定義；寫的是工作區）。

留底檔的格式（jsonl 給程式讀，還是 md 給人讀）原則推不出來；ops-agent 要的是「人也讀得到」。寫手代定 jsonl（跟 `self_history` 的 keep 同一種、不丟欄位），人要看的 md 由 agent 自己從 jsonl 轉；要翻案改這一句即可。

## 第 5 點（意見，不必回）：eca 沒有放在 workspace 的跨 session 清單

**事實：對（讀檔）。** `packs.json#/about`：eca-claude 不掛 goal、todo；`tools/todo.json#/where`：清單在 `<stack>/tools/todo/todo.json`、上限 50 條、別的 agent 看不到。

**一句話記下：** ops-agent 的決定（跨 session、給人看、進 git 的進度與「等使用者做的事」繼續用工作區的 md，不轉 aos 的 todo）跟今天 [main-session-in-aos 第四題](../main-session-in-aos.md)的結論完全同向——「跨 session 還沒做完的事不是 todo，照舊記 `wf/SESSION-LOG.md`（進 git）；todo 只是一段對話裡的小抄」，依據是使用者 11-11「eca基本都有goal，所以goal不用給eca。todo也不用。」（P-43）與 C-91「清單放自己小格」。**沒有要補的結論。** 它最後那句「若 aos 之後想接，需要的是放在 workspace、人讀得懂、可分類的清單」記在這裡當需求線索，不立題。

**分類：不做（已有結論，雙方一致）。**
