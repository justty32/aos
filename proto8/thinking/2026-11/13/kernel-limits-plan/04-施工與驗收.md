6. `procs: 10` 不換 uid → stderr 一行 warning。
7. 既有 aos-daemon 測試全過。

## 段 3：換成 subuid（C++＋小程式，免 root，**要先裁 K4～K7、K10**）

| 改什麼 | 檔 |
|---|---|
| `user` 多認 `sub:N`（1～65536）；fork 後子行程 `unshare(CLONE_NEWUSER)`、管子通知、daemon 跑 `newuidmap`／`newgidmap`、子行程換身分；之前 `close_range`、照 `env` 白名單清環境 | `limits.{hpp,cpp}`、`child.cpp` |
| 起前檢查工作區與 stack 每層祖先能不能走到 | `child.cpp`（fork 前） |
| `aos-asuser sub:N [--gid-user] -- prog…`（給 aos-sandbox 與清理用） | `cmd/aos-asuser/`（新，Python 或 C 皆可；要 exec 前後兩段，C 比較直） |
| aos-sandbox 的 `user` 認 `sub:N` → 前面接 `aos-asuser` | `cmd/aos-sandbox/bin/aos-sandbox`、README、知識庫 `cli/sandbox.json` |
| 活樹權限收緊（`~/aos-home` 755→750／700、信箱、使用者專區 `mailbox/` 以外 700） | 活樹，使用者放行後另派；清單與指令先寫在這段的施工紀錄 |
| 使用者專區 L3 | 跟 [user-zone-plan](../user-zone-plan/README.md) 段 6 合併做 |

驗收：

1. `sub:5` 的 proc：`/proc/<pid>/status` 的 Uid 是 100004；它寫的檔外面看 `100004:1001`（K6 選主群組時）。
2. 讀不到 `~/.aos/user/done/` 下 600 的檔；寫得進 `~/.aos/user/mailbox/new/`。
3. `kill -0` 使用者的 shell 失敗；daemon 能停它（`stop` 走得通）。
4. `procs: 5` 在 sub uid 下照常。
5. 公司 WSL：`sub:N` 報 `LimitBad … newuidmap missing`（或真的能跑，看那台的 `/etc/subuid`）。
6. eca 身保持 1000，畫面照開得起來。

## 段 4：cgroup 總量（二期，K3）

- daemon 起的時候看自己在不在可寫、有委派 `memory pids` 的 cgroup：在＝自己搬進 `<格>/daemon/`、每支 proc 一格 `<格>/procs/<名>/`（fork 後、exec 前把 pid 寫進 `cgroup.procs`）；不在＝表上 `cgroup: none`。
- 新鍵：`limits` 多 `mem_total_mb`→`memory.max`、`procs_total`→`pids.max`（名字待裁時一起定）。
- 怎麼讓 daemon 起在有委派的格裡：樹的起法加一層 `systemd-run --user --scope -p Delegate=yes`（`launch.json` 的 `wrap`，[two-machines 02](../../10/two-machines/02-機器專屬設定.md)）。11-05 在 WSL 這樣試退 1，要先在家機試。
- 驗收：`mem_total_mb: 256` 的 python 配 1GB → 被 OOM 收掉、`limit_hit: "mem"`；`procs_total: 20` 的 fork 炸彈停在 20。

## 段 5：要 root 的（不做，K8）

真帳號、只准換成指定帳號的 helper／sudoers——現成的 `cmd/aos-sandbox/root/setup.sh`（預設乾跑）就是它的位置；daemon 的 `user: <帳號名>` 已經寫好，有 root 就能用（沒在真 root 下跑過）。使用者親手 `sudo` 起整棵樹才會用到。

## 停樹與順序

段 1 與段 3 的 C++ 都要停樹換執行檔，盡量併成一次；段 2 只換 Python 源頭、活樹重抄就生效。順序 1→2→（裁）→3→4。段 1、2 可以平行。
