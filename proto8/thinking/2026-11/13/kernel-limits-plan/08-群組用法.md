## 先講三個底層事實

1. **使用者自己就能在自己的夾上寫「別的 uid／gid」的 ACL**，不用是那個群組的成員、不用 root（X14）。所以「哪隻 agent、哪個隊能進哪個夾」全靠使用者擁有的夾上的 ACL 就能講清楚。
2. **使用者在外面 `chgrp` 成 subgid 不行**（不是成員），**進 ns 當 ns 的 root 就行**（X15）。ACL 做得到的就不必 chgrp。
3. **使用者的附屬群組（wheel 等）對不進 ns**，`newgidmap` 只准使用者的主群組 1001 加 subgid 段（X16）。agent 想「加入使用者現有的群組」要 root（[09](09-有root的話.md)）。

## K6 多一個選項 C，推薦改 C

| 選項 | 寫出來的檔 | 使用者改得動嗎 | agent 能碰使用者其他檔嗎 | 隊與隊分得開嗎 |
|---|---|---|---|---|
| A 主群組（原推薦） | `100004:1001` | 能（群組權限） | **能**寫使用者那些群組可寫的檔 | 分不開，全部 agent 同一群 |
| B 各自 subgid | `100004:100004` | 不能（要進 ns） | 不能 | 分得開，但共用夾難做 |
| **C 各自 subgid＋隊伍群組＋ACL** | `100004:100004`（或 setgid 夾的群組）＋ACL `user:lorkhan` | 能（預設 ACL） | 不能 | 分得開（G1） |

**推薦 C**：A 的代價（agent 能寫使用者群組可寫的檔、隊與隊分不開）C 都沒有，多的只是「共用夾要設 ACL」；ACL 由 daemon 與一支小指令設（K16）。A 留著當檔案系統不吃 ACL 時的退路（家機 ext4、tmpfs 都吃；公司 WSL 的 `~` 是 ext4 應該也吃，`/mnt/c` 不吃，沒驗）。

## 號段（K15 的推薦一起寫）

- `/etc/subuid`、`/etc/subgid` 給 lorkhan 的是 100000～165535（ns 裡 1～65536）。
- agent：`sub:N` 的 N 用 1～60000（uid 與自己的主群組同一個號）。
- 隊伍群組與功能群組（金鑰群…）：ns 60001～65536（真 160000～165535），名字→號碼寫一張表。
- 誰屬哪個隊：kernel 站照 `users` 表一起填，跟 `user` 同一套規則（請求自帶的一律丟）：

```json
{"users": {"sol-*": {"user": "sub:2001", "groups": ["t1", "llm-key"]}},
 "groups": {"t1": 60001, "llm-key": 60100}}
```

daemon 只照信上的 `groups` 套（`newgidmap` 多對這幾個 gid、`setgroups`），不自己決定誰在哪隊。

## 一個 daemon 一個群組（11-13 晚使用者裁）

原話（逐字）：「都按照推薦。然後每隻agent一個自己的群組，感覺有點浪費，我會覺得，在普通用途下，一個kernel/daemon一個群組就好，可以再去想想。」

→ K12～K16 照推薦；K6 方向採 C 的思路（各自的 uid＋共用夾用 ACL 把使用者加進去），但**群組的粒度改成「普通用途一台 daemon 一個群組」**：同一台 daemon 起的 agent，主群組都是這台的群組（不另給每隻一個 subgid、沒有附屬群組）；子 daemon 是另一台、另一個群組。uid 照舊每隻一個（`sub:N`）。

補測在 `~/code/limits2-1113/g3`（[06](06-試驗紀錄.md) X29～X37）：A、B＝同一台 daemon（ns gid 60＝真 100600），C＝它底下的子 daemon（ns gid 61＝真 100601），`setpriv --clear-groups`、umask 002。

### 各用法在這個粒度下

| # | 用法 | 成立／失去 | 這個粒度下的做法 | 實測 |
|---|---|---|---|---|
| G1 | 共寫夾 | **成立，單位從「隊」變成「daemon」** | 夾 `2770`＋ACL `g:<daemon 群組>:rwx`＋預設 `u:lorkhan`；同台的 agent 互相改得動 | 同台 B 改得動 A 的檔（X29）；子 daemon 的 C 進不去（X30） |
| — | 同一台裡隊與隊分開 | **失去** | 替代：拆成兩台子 daemon（各一個群組）；拆不了才走進階的隊伍群組 | X30 |
| G2 | 唯讀分享夾 | 成立 | ACL 點名要給看的 daemon 群組（可以同時點上層與子 daemon） | 子 daemon 的 C 讀得到上層點名給它的分享夾（X31） |
| G3 | 金鑰門 | **群組版失去**（同台全在一個群組） | 替代：金鑰檔 ACL 直接點名 uid（`u:<subuid>:r`），不用群組 | 點名的 A 讀得到、同台的 B 讀不到（X34） |
| G4 | 可改不可刪 | 成立（靠 sticky＋uid，不靠群組） | 同前 | 同台 B 刪不掉 A 的檔、A 刪不掉使用者的；但 B 改得動 A 的檔（同群組可寫）（X35） |
| G5 | 投遞箱 | 成立（靠預設 ACL 的 `g::---`，同群組也讀不到） | 同前，ACL 改成 `g:<daemon 群組>:wx` | 同台 B 列不出、讀不到、刪不掉 A 的信；使用者照讀（X33） |
| G6 | stack 隔離 | 成立（**靠 uid＋ACL 就夠**，不靠群組） | 同前：`700`＋`u:<subuid>:rwx`＋預設 `u:lorkhan` | 同台 B 進不去、照路徑也讀不到（X32） |
| G7 | 使用者修被鎖的檔 | 成立（跟群組無關） | 同前 | — |
| G8 | git `safe.directory` | 成立（跟群組無關） | 同前 | — |
| — | agent 互殺行程 | 成立（靠 uid） | — | 同台 A 對 B 的行程 `kill -0` 被拒（X36） |
| — | kernel 認寄件人 | 成立（靠信檔擁有者 uid，不靠群組） | — | 信檔 `100004:100600`（X33） |

一句話：**隔離本來就是 uid 在擋，群組只負責「這台的 agent 共用什麼」**；改成一台一個群組，失去的只有「同一台裡再分隊」與「用群組當金鑰門」，前者拆子 daemon、後者點名 uid 都補得回來。

### 進階：什麼時候才值得細到每隊／每隻一個群組

| 情況 | 先用普通做法 | 開細群組的判準 |
|---|---|---|
| 某份權限（金鑰、某個夾）只給同台裡的幾隻 | ACL 點名 uid | 同一份權限要點名的 agent **超過 3 隻**，或名單**每天在變** → 開一個功能群組（例：金鑰群），點名換成「加不加這個附屬群組」 |
| 同一台裡兩群 agent 不准看到彼此的工作 | 拆成兩台子 daemon，各一個群組 | **拆不了**（兩群必須吃同一份 kernel 規則或同一個額度格）才開隊伍群組，當附屬群組掛上 |
| 每隻一個群組 | 不用：uid＋ACL 已分得開（X32、X33、X36） | 幾乎沒有。唯一想得到的：agent 得在共寫夾裡放「同台別隻不能讀」的檔——放進自己的 stack 就好，所以仍不推薦 |

進階群組照 K15（照推薦）由 kernel 站的 `users` 表填 `groups`、號碼取 ns 60001～65536 段；普通用途用不到 `groups`。

### 跟前面幾節的關係

- 「K6 多一個選項 C」那節的 C 改讀成：**各自的 uid＋這台 daemon 的群組（主群組）＋預設 ACL 把使用者加進去**；「隊與隊分得開」那格改成「daemon 與 daemon 分得開，同台要分就拆子 daemon」。
- 「號段」那節：daemon 的群組也從 ns 60001～65536 段取；agent 的 `sub:N` 不再需要同號的 subgid。
