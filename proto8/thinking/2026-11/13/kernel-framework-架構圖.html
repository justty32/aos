kernel 框架架構圖

截至 2026-11-13 13:37（機器時鐘）、main＝fd9ae490a（kernel 程式最後一個 commit 是 d8384df9b）。照當下 main 上的程式畫；圖紙與程式不一樣的地方，照程式畫、摺疊裡註一句。

四句話看完
  1. daemon 是手、kernel 是門。手真的去起、關行程；門決定「這個請求放不放」。一個 proc 想掛另一個 proc，就寄信給門。
  2. 框架站＝一份固定的骨架＋可換的「包」。框架最底層就是「hook＋判斷」；數量上限、排隊、期限這類是蓋在上面的通用基礎包（掛 proc 那一包）的事。掛 proc 那一包已在 main；問腦那一包的 Python 版也進 main 了，只是還沒換上。
  3. 請求往哪寄：沒特別指定就寄 AOS_KERNEL；站自己找下一站照三段：next → AOS_KERNEL → AOS_DAEMON。next 只有一個；要照規則分流，寫 hook 替那一封指定下一站。
  4. agent 也能自己當門：兩次工具呼叫，請求進來先留著、它收到通知、自己表態過不過，機器再去轉寄。
① 總圖② 往哪寄③ 站的裡面④ hook⑤ 設定檔⑥ agent 當門⑦ 問腦那包⑧ 查詢信⑨ 進度地圖

① 總圖：一封請求怎麼走到「手」

結論：proc 不直接叫 daemon 動手，而是把請求信寄給「門」；門放行才轉到「手」。門可以只有一站，也可以串好幾站；門和手也可以是同一台 daemon（它自己的身體就是框架站）。

python3 proto8/extras/kernel-chain-check/check.py   # 暫存夾起一棵「兩站＋daemon」的樹，七段都過會印 7/7 ok
細節：手與門的出處、三種擺法、檔案位置

  • daemon 故意很笨：只有一張表＋一雙照表做事的手，不決定「該不該起」——那是門的事。

② 請求往哪寄：AOS_KERNEL、next、AOS_DAEMON

使用者 11-13 原話（逐字）。站設定檔的 next 就是「自己找方法指定」的其中一種。

結論：AOS_KERNEL 是「沒特別指定時的通用目標」，像 C 程式的 syscall 預設走 linux kernel。站自己放行後要轉去哪，先看明寫的 next，再看 AOS_KERNEL，最後才是 AOS_DAEMON。人拿 aos-daemon-ctl 直接敲 daemon 是保底的旁路。next 只有一個；要照規則分流（一封只去一處），寫 after_verdict hook 回 {"next": 路徑}，沒回的照三段。

③ 一個框架站裡面：骨架一輪做什麼

「就是說我們做的是框架，最底層就是最簡單的hook+判斷。你說的上限這塊，是在框架之上的通用基礎包，所以可以隨意，可以簡單並通用一些。」
使用者 11-13 下午原話（逐字）。

結論：骨架只管「順序」，放不放由「包」（pack＝一組規則）說。包的判決有三種：pass 放行轉寄、refuse 回拒信、queue 等格子排隊；hook 還能回第四種 hold：先留著，等別人寫表態檔，下一輪照表態轉寄或回拒。掛 proc 那一包管三件事：名字在不在白名單、同時幾個在跑、寄件人給的期限過了沒。

aos-exec proto8/lib/aos/kernel <kernel.json>   # 手跑一輪（要先設 AOS_STACK）；平常是 daemon 每一圈替你叫
細節：五個口、掛 proc 那包的規則、站的 stack 長相、錯誤代號
口（包要提供）做什麼

④ hook：三個時機插在一輪的哪裡

結論：hook＝在固定時機自動跑的小程式。站有三個時機：判之前（可改信）、判之後（可改判、可替這一封指定下一站、可回 hold 先留著）、代回回信之前（可改回信）；三個都能用「退出碼 10」攔下。執行的引擎是從 agent 的 hooks 抽出來的同一份，但 agent 那邊還沒換過來（批 1b：使用者同意直接改，另一條線施工中、還沒接線）。留著的信不再問 hook；有人表態 pass 的那一輪重問一次，這次回 hold 不算數。

出處：使用者 11-13「next只能一個嗎？」→「按照規則分流吧。就用hook」。

{"hooks": {"rewrite": {"event": "before_verdict", "handler": "rewrite"}}}   # 寫進 kernel.json；handler 是同一夾裡的可執行檔

⑥ agent 自己當門：收到通知、自己判、機器轉寄

「讓agent成為kernel，我期望看到的景象是：一個普通的agent隨便弄些hook、json設定啥的，就可以收請求了。請求進來後agent收到通知，他自己判斷要不要過，然後再去轉送」
使用者 11-13 原話（逐字）。同一天：「各種的...都可以大家自己設定」。

結論：agent 不用另外寫一支 kernel：加一個工具包、叫一次 on，它身上就多一個框架站。請求進來先留著，agent 收到通知後只表態（過／不過），轉寄、回拒、驗期限都是機器做。這個工具包預設不掛進範本，要當門的 agent 自己加。

kernel_gate {"op": "pass", "letter": "<信名>"}   # agent 對留著的那一封表態放行；不放行用 "op": "refuse" 加 "reason"
細節：on 做了什麼、請求能帶什麼、還在的缺口
  • 兩次工具呼叫：self_tools {"op": "add", "path": "<AOS_HOME 的實際路徑>/lib/agent/kernel_gate"} → kernel_gate {"op": "on"}。
  • on 做三件事：建站的 stack（<agent 的 stack>/hooks/kernel_gate/，含 requests/ 收件信箱）；沒有 kernel.json 才寫預設那份（一支 hold hook、condition: "pass"＝規則拒的直接拒、不吵腦）；在自己身上掛一支 on_clock hook（每個時鐘週期跑站一輪＋發通知）。印出的第一行就是「把請求寄到這個路徑」。
  • 其他動作：ls 看留著的、off 收掉（把還留著的全部回拒 HoldRefused、拿掉 hook；信箱與設定留著，再 on 接著用）。
  • 請求信是 json：寄的人想加什麼 key 都行，站沒設限制就能過（使用者：「我那個只是舉例，實際上大家就隨便加，反正json，不認得的key，只要沒設限制，就能過。」）。通知把 procs_*、queue_wait_ms、ping 算成 request，其餘 key 整包原樣印一行。
  • 提示注入：額外的 key 原樣進 agent 的對話，風險自己承擔（使用者：「提示注入這塊就是風險自己承擔」）。
  • 預設不掛：不進任何範本（使用者：「預設不掛」）。
  • 混合用法：kernel.json 寫 allowed／max_running 讓機器先照規則判，hook 自己決定哪些信才留給腦。
  • 不用新工具也行：只靠 self_hook、手寫 kernel.json 與一支 hook、表態＝寫一個檔；步驟在知識庫 aos/kernel.json 的 write_your_own。
  • 還在的缺口：門正在自己的一輪裡、睡著或停著時站不跑，信躺在信箱沒人認領（使用者裁先不補）；只通知一次、不再提醒；沒帶期限的信會一直留到有人表態；門死了沒有人知道；兩隻互相當下一站不偵測。
  • 驗過什麼（照 eca-as-kernel 第十節寫的，我沒重跑）：真 haiku 實跑過一次；單元測試；整鏈劇本第 8 段。
  • 活樹什麼時候有：~/aos-home 用的是抄本，下次重抄才有；重抄後也要 agent 自己加才會用到。
  • 程式：proto8/lib/agent/kernel_gate/、proto8/lib/packs/kernel_gate.json、骨架的口在 proto8/lib/aos/kernel/hold.py。說明：proto8/kernel/docs/02-kernel-modes.md「agent 當門」。設計與邊緣狀況：proto8/thinking/2026-11/13/eca-as-kernel.md。commit：6f83a431a（骨架的口）、306078925（工具包）、1c973e47e（通知種類登記）、dd32bef00（劇本第 8 段）。
