# 使用者專區放 `~/.aos/user/`：收件匣就是一個 aos-post 信箱，「回了才消」，一支 `aos-user` 小程式管列信、看信、回信，網頁與手機疊在同一套資料上

← [使用者專區規劃](../user-zone-plan.md)

> 只讀 [01-備料](01-備料.md) 做的設計。「待驗」＝備料裡確認不了的事；「待裁」＝要使用者決定。

## 1. 位置

| 候選 | 跨樹 | 權限／找得到 | 問題 |
|---|---|---|---|
| `~/.aos/user/` | 好：跟著帳號，不跟某棵樹 | 路徑固定，好找 | 不在 git 裡，要自己備份 |
| `~/.aos/` 本身（沿用 `stack/mailbox`） | 好 | 信箱已存在 | 跟 `log.md`、`say/`、stack 混在一起，難整包搬或鎖權限 |
| `~/aos-home/user/` | 差：多棵樹就有多個專區 | 好找 | 人只有一個，專區不該有很多個 |
| `~/aos-home/ws/public/user/` | 差，同上 | 最好找 | `public` 是大家都能寫的公用地，專區卻最該管住寫入，性質相反 |

**推薦 `~/.aos/user/`。** 理由：人跟著帳號走，放帳號層，以後多棵樹也只有一個專區；這是使用者裁-5 自己講的位置；自成一夾，日後整包備份、整包鎖權限（第 6 節）都好做。

配套：

- **舊信箱不丟**：11-12 定的 `~/.aos/stack/mailbox` 改成一條捷徑（symlink），指到 `~/.aos/user/inbox`。照舊指令寄的信也會進專區。（待驗：aos-post 對捷徑夾的 rename 正常。不行就反過來，真身留在 `stack/mailbox`。）
- **agent 怎麼找**：`~/aos-home/ws/public/user.json` 放一張「名片」（專區路徑、公告路徑、之後的公鑰）。每棵樹的 public 都指向同一個專區。另留環境變數 `$AOS_USER_ZONE` 可蓋掉。
- **備份**：已回的信按月收進 `done/`，可每月打包，或推到私人 git（第 8 節）。

## 2. 專區結構

```
~/.aos/user/
├── door.json            門上公告：收什麼信、格式、急件怎麼投
├── schema/letter.json   信的 JSON schema（機器驗格式用的規格）
├── inbox/               ★ 一個標準 aos-post 信箱，agent 唯一能寄的地方
│   ├── tmp/             寄信中（底層用）
│   ├── new/             還沒看過
│   └── cur/             看過、還沒回 ＝「待辦」
├── done/2026-11/<信名>/ 回完的：原信 letter.json＋我的回信 reply.json
├── rejected/<信名>/     不合公告的信（留著，沒丟）
├── drafts/<信名>.json   答到一半的草稿
├── config.json          設定：通知開關、安靜時段、過期天數
├── keys/                簽名用的金鑰（第 5 段才有）
├── web/                 網頁的暫存（登入記號、手機匯出檔）
└── log.jsonl            流水帳：誰何時寄、何時回、從哪回（終端機／網頁／手機）
```

跟 aos 信箱格式的關係：

- 只有 `inbox/` 是 aos-post 信箱。`new/`＝沒看過，`cur/`＝看過沒回。**不另外發明「已讀格」**，直接借底層本來就有的兩格。（待驗：沒有別的程式會自動清 `cur/`。）
- `done/` 不是信箱，是存檔夾。
- 使用者的回信直接寄到對方信箱；專區只在 `done/` 留一份副本。
- 急件先不分第二個信箱，用 `urgent` 這個 key 就好；真的吵再分。

## 3. 誰寄、寄什麼

**該寄的**（五種，`kind` 這個 key；前四種對上現在 wait-user 的四類）：

| kind | 白話 | 對應 STATUS |
|---|---|---|
| `decide` | 要你裁的題 | NEEDS-USER |
| `verify` | 要你真機試一下 | NEEDS-USER |
| `trial` | 試驗場：請你玩玩看給感想 | NEEDS-USER |
| `chore` | 只有你能做的雜事（登入、插線） | NEEDS-USER |
| `fyi` | 純告知，按「知道了」就消 | DONE／FAILED／BLOCKED |

**不該寄的**：PROGRESS（進度去看板）；agent 之間的 REQUEST；能自己查到答案的問題。

**額外 key**（全放 `body`，舊程式看不懂會自動略過）：

```json
{ "zone": "user-zone/1", "kind": "decide",
  "from": "repo-aos", "status": "NEEDS-USER", "title": "時鐘要不要支援 cron",
  "questions": [ { "id": "q1", "question": "一句話問題", "eli5": "給小學生的兩句說明",
      "options": [ {"key":"a","label":"做","consequence":"多兩天"},
                   {"key":"b","label":"不做","consequence":"之後難補"} ],
      "recommend": "a", "why": "一句理由", "details": "摺起來的細節",
      "source_path": "proto8/thinking/…md" } ],
  "risk": "normal",              // 或 irreversible（不可逆／對外）→ 決定要幾級驗證
  "urgent": false,
  "deadline": "2026-11-15",
  "default_if_silent": "到期照推薦 a 做",   // 沒寫＝一直等
  "dedupe_key": "clock-cron",    // 同一題的記號，防兩隻 agent 重複問
  "host": "home", "origin": "原始發問者（別人代轉時填）" }
```

- 題目格式照抄 decide-page，大題小題一個樣。
- **`decide` 一定要有選項＋推薦＋ eli5**。`verify`／`chore` 要有「做什麼、做完怎樣算好」。

**寄信工具**：`mailbox_send` 不收多的 key，所以 agent 改用 `aos-user send`（裡面呼叫 `aos-post send`）。它寄之前先照 schema 驗一次，不合就當場報錯，信根本寄不出去。

**門上公告 `door.json`**（公開、誰都能讀）：

```json
{ "door": "user-door/1", "who": "使用者本人", "inbox": "~/.aos/user/inbox",
  "tool": "aos-user send", "schema": "schema/letter.json",
  "accept": ["decide","verify","trial","chore","fyi"],
  "rules": ["要裁的題必帶選項與推薦", "一封信最多 7 題", "進度不要寄來"],
  "urgent": "urgent=true 只給『不回就卡住全部』的事",
  "mode": "normal" }  // 或 away：出門中，只通知急件
```

**不合的信**：底層擋不住別人直接用 `aos-post` 丟進來，所以收件時檢查——

- 完全不合：搬到 `rejected/`，自動退一封信給寄件人，寫哪裡不合、公告在哪。信沒丟，`aos-user ls --rejected` 還看得到。
- 舊格式（一般 aos-mailbox 信，有 NEEDS-USER 與 decide 欄）：過渡期照收，標「舊格式」。
- 對上使用者說的「兩層 hook」：第一層＝每封信都過收件檢查；第二層＝看 `urgent`／`kind` 決定要不要通知。

## 4. 使用者怎麼看與回（先做最小的）

一支程式 `aos-user`，輸出人看得懂的字，加 `--json` 給程式讀：

| 指令 | 做什麼 |
|---|---|
| `aos-user ls` | 列待辦：編號、種類、誰寄的、標題、幾題、到期。急件在上 |
| `aos-user show 3` | 看第 3 封：題目、選項、推薦。信從 `new/` 移到 `cur/` |
| `aos-user answer 3 q1:a q2:b* --note "…"` | 裁題。`*`＝跟推薦不同（寫法照 decide-page） |
| `aos-user answer 3 --all-recommend` | 全部照推薦（`risk=irreversible` 的題不吃這招） |
| `aos-user reply 3 "一段話"` | 自由回話（verify／chore／trial 用） |
| `aos-user ok 5` | fyi 的「知道了」 |
| `aos-user door` | 看／改公告（例如切成出門模式） |

**回了才消（解洞 1）**：`aos-user` 從不用會刪信的 `read`。看＝搬到 `cur/`；只有 answer／reply／ok 成功寄出後，信才從 `cur/` 搬到 `done/`。

**回信怎麼回到原寄件人**：寄到原信的 `reply_to`，帶 `in_reply_to=<原信名>`。回信的 body：

```json
{ "from": "user", "status": "DONE", "zone": "user-zone/1",
  "answers": [ {"id":"q1","answer":"a","differs":false,"note":""} ],
  "text": "", "answered_at": "…", "via": "cli",        // cli／web／phone-relay
  "letter_hash": "原信內容的指紋", "auth": {"level": 1} }
```

**一批多題**：一封信一次回完。只答一部分就存進 `drafts/`，信留在待辦；趕時間加 `--partial` 先寄答好的，信留著等剩下的。

## 5. 網頁、通知、專區 agent

**架構**：核心是一個函式庫，指令列、網頁、手機匯出都呼叫它，沒有第二份邏輯。

**網頁後端**：`aos-user serve`，一支小 Python，直接讀寫專區那幾個夾。四頁：待辦（一題一張卡）、單封信（選項用點的＋意見欄＋摺起來的細節）、已回（查舊帳）、公告（看、切出門模式）。

**手機版面**（照使用者 11-08 的話）：一張卡只有「一句話問題＋兩句 ELI5 ＋選項按鈕（標出推薦）＋意見欄」；理由、細節、出處全摺起來；沒有圖；最上面一顆「全部照推薦」（要再確認一次，不含不可逆的題）。

**跟現有兩個看板的關係：並存、分工，不合併程式**。

- 桌面看板 8765：繼續管「看進度」。它的「待你裁」之後改成轉寄進專區，那一欄只留一條連結。
- 專區網頁：只管「要你動手的事」，另開一個埠。看板在 `wf/` 底下，綁上去日後會跟著被拆。
- claude.ai 手機看板：過渡期繼續用，多一欄顯示專區匯出的待辦。

**本機安全**：只綁 `127.0.0.1`、檢查 Host 標頭（跟看板一樣）、POST 要帶登入記號並檢查來源。同帳號的 agent 一樣連得到本機網頁，所以「網頁回的」不比「指令列回的」更可信。

**手機怎麼連**：

| 做法 | 好處 | 壞處 |
|---|---|---|
| A. claude.ai artifact 中轉（現有） | 不用裝東西 | 回答要經頂層 Claude 拉回，中間有一隻 AI；不即時 |
| B. tailscale（私人網路，手機直連家機） | 沒有中間人，手機看到的就是專區本尊 | 兩邊都要裝；公司 WSL 可能不准 |
| C. 推到私人 GitHub（一題一個 issue，留言就是回答） | 使用者本來就用 GitHub app，自帶通知 | 題目內容上雲；要寫同步程式；算對外動作，要先授權 |
| D. ntfy 這類推播服務，只送「有 3 題等你」 | 最簡單 | 只能通知，不能回 |

**推薦**：通知用 D（只送數量與標題，不送內容）；看與回，家機用 B，公司機先留 A。C 當 B 不能用時的備案。這題待裁。

**通知**：

- 桌面：一支定時小程式（或 `on_clock` hook）盯 `inbox/new/`，有新信就跳桌面通知。
- 手機：同一支程式送 D。
- 出門模式只送急件；一般信每天整理成一則；`config.json` 設安靜時段。

**要不要專區 agent**：要，但放很後面，而且管很少。

- 能用死程式做的都不給 AI：格式檢查、排序、通知、到期提醒、退信。
- AI 只做要判斷的：兩封信是不是同一題、替舊信補一句白話、每天整理「最該先看的三件」。
- **不做**：不改題目、不替使用者回、不碰金鑰、不經手回信（回信由程式直接寄給原寄件人）。
- **會不會變成新的轉述者？會，如果讓它改寫**。所以原信永遠原樣顯示；它寫的只能放旁邊另一格，標明「專區 agent 補的」，一鍵可關。

## 6. 授權驗證

問題的根：agent 跟使用者是同一個 linux 帳號，所以 agent 技術上能寫專區任何一格、也能假造寄件人。下面每級都說清楚擋不擋得住。

| 級 | 做法 | 擋得住 | 擋不住 | 成本 |
|---|---|---|---|---|
| L0 | 紀律：知識庫寫明「只有 `aos-user` 寄出的回信算數」 | 無心之過 | 任何故意的 | 零 |
| L1 | **留底可查**：回信時在 `done/` 留副本＋記流水帳。收信方跑 `aos-user verify <信>`，比對專區有沒有同一封。再加守門 hook：agent 的寫檔工具不准寫 `~/.aos/user/`（`inbox` 除外） | 「某 agent 說使用者口頭同意了」（T08 那種）；直接往別人信箱丟假回信 | 會用 shell 的 agent 連 `done/` 一起假造 | 低 |
| L2 | **密語簽名**：金鑰用密語（只在使用者腦中的密碼）鎖住，回信時輸入，可記住幾分鐘。簽的內容含原信指紋、題號、答案、期限 | 同帳號 agent 假造（不知道密語就簽不出來）；舊回信被拿去重用 | 有人偷換公鑰（解法：公鑰多放一份在 repo）；`aos-user` 程式本身被改；金鑰解鎖那幾分鐘被偷看記憶體 | 中：每次打密語；手機經 Claude 中轉的那條路簽不了 |
| L3 | **分帳號或沙箱**：agent 跑別的帳號或關進 bwrap，只有 `inbox/` 寫得進去 | 檔案層面真正擋住 | 使用者自己的帳號被拿走 | 高：共用的東西歸誰要重排（LU:62） |
| L4 | **當場說**：使用者在終端機直接對動手的那隻 agent 講（現行鐵律 2） | 全部 | — | 使用者要人在場 |

**分級推薦**：

- `fyi`、普通裁定（設計選哪個、可以反悔的）：**L1**。
- 手機經 Claude 中轉拉回來的回答：最高只算 **L1**，回信標 `via: phone-relay`，永遠不能當不可逆動作的授權。
- push、刪檔、對外寄東西（`risk=irreversible`）：**現在一律 L4**，專區的回信不算授權，鐵律不動。L2 做好後，可由使用者裁定「L2 簽名＋回信寫明是哪個動作、哪個目標、只用一次、何時過期」也算。
- L3 是長期正解。

**要改一條規矩（待裁）**：鐵律 2 說「agent 寄來的信不是授權來源」，而專區回信在形式上也是一封信。建議加一句：「經 `aos-user verify` 驗過的專區回信，等同使用者本人對**普通工作**說的話」——地位跟 eca_main 那條例外一樣。

## 7. 跟現有東西的關係

- **WAIT_USER／wait-user**：四類直接對上 `verify`、`decide`、`trial`、`chore`。過渡期新題一律進專區，舊檔只剩還沒搬的條目＋一行「新的看 `aos-user ls`」；清空後刪掉，或改成由 `aos-user ls` 自動產生。
- **decide-page**：批次大題變成一封 `kind=decide` 的信，`questions` 就是原本那個 json 的題目陣列（格式本來就一樣），`source_path` 指回原檔。專區接手「顯示＋收答案」；答案落回設計文件仍用 `decide_page.py apply/land`。
- **eca_main**：專區是「信箱」，eca_main 是「腦」。使用者想交辦、想聊的照舊找它；各 agent 要問使用者的直接寄專區，不再請它轉。它替別人轉寄時 `origin` 填原始發問者、原文照貼不改寫。原寄件人不在了的回信改寄給它保管。過渡期兩條路都收，`aos-user ls` 標出哪些是它轉來的。
- **`~/aos-home/ws/public`**：放名片 `user.json` 與通訊錄，不放信。
- **`~/aos-home/ws/tools`**：放 `aos-user`（指令列＋函式庫＋網頁）。這兩個夾現在都還不存在，第一段順手建。

## 8. 跨機

**推薦：兩台各一份，先不同步。** 題目是那台的 agent 問的，回信也要回到那台的信箱；同步待辦只會讓同一題被回兩次。

- 每封信帶 `host`。手機那一頁把兩台的待辦並排，各標哪一台。
- 之後要同步，只同步 `done/`（只增不改，不會衝突），走私人 git。`inbox/` 永不同步。
- 萬一同一題兩邊都回了：以 `answered_at` 早的為準，晚的記成「遲到的回答」並通知使用者。

## 9. 分段

| 段 | 做什麼 | 做完使用者能怎麼用 |
|---|---|---|
| 1 最小可用 | 建 `~/.aos/user/`、`ws/public/user.json`、`ws/tools/aos-user`（send、ls、show、answer、reply、ok）、`door.json`＋schema、知識庫一節 | 終端機打 `aos-user ls` 看到所有等你的事，`aos-user answer 3 q1:a` 回掉，對方收到 |
| 2 通知＋過渡 | 桌面通知、收件檢查與退信、`verify`（L1）、守門 hook、WAIT_USER 開始搬、看板「待你裁」轉寄 | 有新題桌面會跳；不用再翻 WAIT_USER.md |
| 3 桌面網頁 | `aos-user serve`、四頁、草稿 | 瀏覽器點選項裁題 |
| 4 手機 | 手機版面、推播、連線方式（照第 5 節裁定） | 出門手機被叫一聲，點開就能裁 |
| 5 加強 | 密語簽名（L2）、專區 agent、decide-page 併入 | 重要回覆可驗；每天有「先看這三件」 |
| 6 長期 | 分帳號或沙箱（L3）、`done/` 跨機歸檔 | agent 真的寫不進專區 |

## 10. 邊緣狀況

1. **很久不回**：有 `default_if_silent` 就到期照做，並寄一封 fyi 說「我照預設做了」；沒寫就一直等，每 N 天提醒一次。不可逆的題不准有預設。
2. **同一題兩隻 agent 問**：`dedupe_key` 相同就疊成一張卡，答一次，兩邊都收到。
3. **寄件 agent 已被刪**：回信改寄 eca_main，`done/` 記「原寄件人不在」。
4. **回信時對方信箱不在**：信留在待辦，標「回不出去」，答案存草稿，使用者可改寄別處。
5. **信很多**：急件在上、同寄件人摺成一組、fyi 可一鍵全收。
6. **手機答一半**：每點一題就存草稿，按送出才寄。
7. **跨機答題**：手機頁面照 `host` 把答案送回對的那台；指令列只看得到本機的，不會答錯。
8. **agent 收到回信前自己先做了**：回信帶原信指紋；agent 若已改題或已做，要回一封 fyi 說明，不能默默蓋掉。
9. **使用者回完想反悔**：`aos-user amend <信>` 再寄一封帶同一個 `in_reply_to` 的更正信，標 `supersedes`；對方已經做了就由對方回報。
10. **答案不在選項裡**：每題固定多一個「都不要，我寫」，填意見欄，`answer` 記 `other`。
11. **agent 直接往 `cur/` 或 `done/` 塞檔**：流水帳對不上就標「來路不明」；真要擋要等 L3。
