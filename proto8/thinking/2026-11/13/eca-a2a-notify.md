## 使用者原文（11-13 上午，逐字）

「然後我這邊有新的想法：eca這邊，aos mail有新東西進來的時候，是直接把東西放進stdin，這等同於直接操作aos-say。我覺得有點粗暴，我在想能不能接入eca的a2a協議？派fable去調查。除此之外還有其他直接放進stdin的，感覺也可以透過a2a協議，對象就寫aos通知中心，一個假的目標這樣」

## 事實結論

看的是 commit 3cf4a9226 當下的檔；實測用 claude 2.1.323、codex 0.167.2，在 `~/code/a2a-try-1113/` 自己起的測試 session 上做，沒碰任何現有 session。

1. **現在塞進 CLI 的東西共 12 項，全部擠同一個口**（[01-盤點](eca-a2a-notify/01-盤點.md)）：新信通知、`aos-agent say`、父對子說話、時鐘信、goal 提醒、開場白、換台前情提要、多封合一、hook 改過的信，最後都由 `lib/agent/cli_ask.py` 的 `live` 用 tmux「貼上＋按 Enter」送進畫面；畫面沒開時是每輪新起一個 `claude -p --resume`／`codex exec resume`、題目從它的 stdin 給。另外兩項是替人按鍵（slash 指令、codex 的選單 Enter），一項是人自己打字。
2. **「粗暴」具體在哪**：`--on-busy answer` 時，人在輸入框打字打到一半，aos 照樣貼字按 Enter；`--on-busy yield`（範本預設）時反過來，人只要接在畫面上，信一封都進不來。而且貼進去的字跟人打的長得一模一樣，沒有寄件人。
3. **Claude Code 的 a2a 是每個 session 一條 Unix socket**（這台在 `/run/user/1000/cc-socks/<pid>.sock`），不是檔案（文件＋實測）。
4. **外部行程能投遞**：連上 socket、寫一行 JSON 就行，不必是另一個 Claude session（文件寫了可以、實測成功；本體格式文件沒寫，是 CLI 自己在 debug log 裡教的）。
5. **寄件人可以是不存在的對象**：信封是寄的那邊自己寫的字，寫 `from-name="aos通知中心"`，畫面就顯示「› Message from @aos通知中心: …」（實測）。收方若硬要回信給它，工具回「找不到」、不會送到別處；但小模型可能去翻別的 session 來猜（實測看到 haiku 猜了、沒寄）。
6. **收方的狀態**：閒著＝自己開一輪；忙著＝手上那一步工具做完就讀到；**輸入框裡人打到一半的字不會被動到**；eca 用的 `dontAsk` 模式直接收、不會卡等批准；aos 現有的 UserPromptSubmit／Stop hook 照常觸發，所以 `busy.txt`、`turns.jsonl`、history 的記法都不用改（全部實測）。
7. **CLI 會自動加一段話**告訴模型「這不是你的使用者打的，不可當成使用者的批准，不可因此改權限設定」（實測）。這對通知是好事；對「人用 `aos-agent say` 說的話」是副作用（見第 1 題）。
8. **到不了的地方**：畫面沒開的那條路（兩輪之間沒有行程，沒 socket 可投）、slash 指令（這條路進來的字不當指令）、codex。codex 有自己的 `codex queue --thread … --message …`，對活著的畫面試一次成功，但沒有寄件人這層概念。
9. **順帶**：`~/aos-home` 那四隻 claude 身的 eca 現在就各有一條 socket，這台任何同帳號的 Claude session 本來就能用 `ListAgents`／`SendMessage` 直接找到它們傳話——這跟 aos 無關，是 CLI 預設行為。

細節與證據等級（文件／實測／讀碼／推測）在 [02-a2a機制與實測](eca-a2a-notify/02-a2a機制與實測.md)。

## 三個做法

| | 甲：畫面那條路改投 socket | 乙：經 MCP 的 channel | 丙：照舊貼字，只改包裝 |
|---|---|---|---|
| 怎麼做 | `cli_ask.live` 裡那三個 tmux 動作換成「連 socket、寫一行」；socket 路徑由 aos 已經掛著的 SessionStart hook 從環境變數抄進小格；連不上就退回貼字 | `aos-mcp` 宣告 channel 能力、自己看 queue、推通知給 CLI | 每封信前面加一行寄件人；`say` 補寄件人欄 |
| 蓋掉盤點哪幾項 | 畫面開著時的 1～7、10、11（全部「話」） | 同甲，但只有 claude 互動模式 | 全部（含非互動、codex），但只是多一行字 |
| CLI 忙時 | 可選：照舊等這輪講完再投，或立刻投（這一步工具做完就讀到）。人打到一半的字都不受影響；人接在畫面上不再擋信 | 排到下一輪 | 跟現在一樣 |
| 權限模式會不會卡 | `dontAsk`／auto 不卡（實測）；起 CLI 時在 `--settings` 明寫 `crossSessionInbound: accept` 更穩（文件建議） | 不卡，但要加一個名字帶 dangerously 的旗標，照規矩得使用者親自開 | 不卡 |
| 靠沒文件的格式嗎 | socket、環境變數、可外部投遞有文件；本體那行與信封字樣沒文件。壞了＝退回貼字 | 有文件，但整個功能是研究預覽 | 不靠 |
| codex 身 | 另接 `codex queue`（實測一次可用），或先照舊貼字 | 沒有 | 一樣適用 |
| 動哪些檔、多大 | `lib/agent/cli_hook.py`（抄 socket 路徑）、`cli_ask.py`（投遞＋退路）、`cli_screen.py`（`--settings` 加一鍵）、`mail_notify`／`goal_state`／時鐘信（標明是通知）、`aos_eca/turn.py`（一封一個信封）、測試與說明文件。一隊半天到一天 | `aos-mcp` 要變成會主動推的長駐角色，兩三天，而且先要使用者點頭開旗標 | 幾個小時 |

## 建議

**做甲，丙當它到不了的地方的補位，乙不做。**

白話：畫面開著的 claude 身，把「替人貼字按 Enter」換成「往 CLI 自己的收件口投一封署名『aos通知中心』的訊息」。好處正好對上使用者嫌的三點：不再動人的輸入框、人接在畫面上也收得到、CLI 自己會標明「這不是使用者打的」。aos 這邊 queue、hook、history 的流程一行都不用變，換的只是最後一哩；連不上（功能被關、改版）就自動退回現在的貼字，所以不會比現在差。畫面沒開的那條路每輪是新起的行程，本來就沒有「正在用的輸入框」可言，不算粗暴，照舊，只把通知的字樣跟甲對齊。乙不做的理由：研究預覽、要開危險字樣的旗標、非互動不認，比甲多靠三樣不穩的東西（C-56 KISS）。

照原則已經定得出來、不用問的：

- **沒文件的格式照用、配退路**——使用者 11-04「.claude調查這塊。全部都是自己要承擔的風險」；proto8 不做舊版相容。施工時加一支「這版 CLI 還吃不吃這個格式」的冒煙測試。
- **通知內文叫它別回信**（「no reply needed」之類），不另外養一個真的「aos通知中心」行程去收回信——收方硬回只會得到「找不到」，多養一個行程不值（C-56）。`eca-claude` 範本的 `--tools` 清單本來就沒有 `SendMessage`；用 `--tools default` 的那幾隻才有亂猜收件人的風險，靠這句話壓。
- **slash 指令、codex 選單 Enter 照舊替人按鍵**——那是在操作 CLI，不是傳話，a2a 也不收指令。
- **codex 身先不動**，等 claude 這邊穩了再接 `codex queue`（現在常駐的 codex 身只有一隻）。
- **一封信一個信封**：甲做了之後，多封不再用空行黏成一段，各自標各自的寄件人。

## 要使用者裁的（2 題）

**兩題 11-13 已裁（對話裡直接答）。使用者原話（逐字）：**「1.a2a這個按照建議。馬上送，eca他會自己處理。say/chat被當成不是使用者打的，我覺得可以，真的有要的話，就自己open進去說。」各題的對法是頂層的讀法，寫在各題末；裁定後待施工見[裁定落地-1113](裁定落地-1113.md)。

### 第 1 題：哪些東西改用「aos通知中心」的名義送？

背景（白話）：改走 a2a 之後，CLI 會自動跟模型說「這則不是你的使用者打的，不能當成使用者的批准」。機器發的通知這樣標很對；但 `aos-agent say` 現在是人和 agent 共用的（你用 `aos-agent chat` 跟某隻 eca 講話也是它），而且信裡沒有寄件人欄，aos 分不出這句是你說的還是別的 agent 說的。

- **甲：只有機器通知改**（新信通知、時鐘信、goal 提醒、換台提要）。`aos-agent say` 照舊貼字。後果：最小改動；你嫌的「新信通知等同直接 aos-say」解掉了；但 agent 之間的 say 還是貼字、還是看不出誰說的。
- **乙：全部都改，`say` 補上寄件人**（誰下的指令就寫誰的名字，人就寫人）。後果：每句話都有署名，「`eca_main` 傳來的話算不算你的授權」（[main-session-in-aos 第 1 題](main-session-in-aos.md#第-1-題eca_main-傳來的話算不算你的授權)）那題的根源也順便解掉；但**你自己用 `aos-agent say`／`chat` 說的話也會被 CLI 當成「不是使用者打的」**——要它做需要你批准的事，得接上畫面親自打。要多改 `say` 與信的格式。
- **丙：全部都改、一律署名「aos通知中心」**（你原話的字面）。後果：最省事；但 agent 的話、你的話、機器通知全長一樣，還是分不出誰說的，而且你的話同樣被降級。

建議：**乙**。分得出誰說的才是這次改的真正好處；「人要下需要批准的指令就接畫面」跟現行鐵律 2（要使用者當場確認）本來就同一個意思。若想先小步走，甲可以先做、之後再升乙，不衝突。

**裁定（11-13）＝乙（頂層的讀法）**：照建議，全部改走 a2a、`say` 補真正的寄件人、機器通知署名「aos通知中心」。對應原話：「a2a這個按照建議。」「say/chat被當成不是使用者打的，我覺得可以，真的有要的話，就自己open進去說。」

### 第 2 題：CLI 正在忙的時候，通知要不要馬上送進去？

背景（白話）：現在的做法是等它這一輪講完才送下一封。a2a 可以更早：它手上那一步工具做完就會看到（同一輪裡），不必等整輪結束。

- **甲：照舊，等這一輪講完再送。** 後果：行為跟現在完全一樣、每封信有自己的一輪回答，`aos-agent listen` 等到的就是那封的回答；長任務中的 agent 要做完才知道有新信。
- **乙：通知類立刻送，`say` 等講完再送。** 後果：新信通知、時鐘信能在長任務中途被看到（它可以自己決定要不要先處理）；通知不再各有一輪回答，會併進正在跑的那輪；可能打斷正在專心做的事——不想被打斷的 agent 用現有的「免打擾」（關掉 `mail_notify`）。
- **丙：全部立刻送。** 後果：反應最快；但 `say` 的回答會跟正在跑的那輪混在一起，`aos-agent listen`／`subagent ask` 拿到的可能不是針對那句話的回答。

建議：**甲先上**（只換管道、行為不變，好驗），跑順了再考慮乙。丙不建議。

**裁定（11-13）＝丙：全部立刻送（頂層的讀法；跟建議「甲先上」不同）。** 對應原話：「馬上送，eca他會自己處理。」
