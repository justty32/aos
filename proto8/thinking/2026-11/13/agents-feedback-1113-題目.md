## 逐題

### T01 子 agent 不能寄信，主 agent 變傳話筒

- **出處**：[A 第 1 點](agents-feedback-1113.md#a-卡到或不順依提到的次數排)（3 隻提到）。
- **白話**：主 agent 派出去的子 agent 只拿到唯讀的那幾支 aos 工具（`aos_sub`），不能寄信。ops-agent 的子 agent 跑了三、四小時，十多封對外通知都要主 agent 轉寄。它們想要一支受限的寄信工具：只能寄給母 agent，或寄給主 agent 指定的名單，署名「代母 agent」。
- **現況**：全新。claude 身的子 agent 拿的那台是 `lib/agent/cli_mcp.py` 的 `aos_sub`，裡面沒有 `mailbox_send`；相關的未裁題是 [eca-task-subagent U2](../12/eca-task-subagent.md#未定題要使用者裁)（Explore、Plan 這類子 agent 要不要也給少功能那台），跟這題不是同一件。codex 身的子 agent 已裁「不管」（U1 丙），所以 codex 的子 agent 現在反而拿得到 `mailbox_send`——兩身不一樣。
- **優先**：高。三隻都提，每次跑長任務都會卡；不做的話，主 agent 的 context 一直被轉寄吃掉，長任務期間主 agent 也沒辦法空出來。
- **要裁**：見 [裁-1](#裁-1t01子-agent-要不要能寄信)。

### T02 new_mail 通知太陽春，打斷的成本高

- **出處**：[A 第 2 點](agents-feedback-1113.md#a-卡到或不順依提到的次數排)（4 隻提到，最多）。
- **白話**：新信通知只說「幾封、誰寄的」，每封都要再叫一次讀信。信裡明寫「不必回」的純告知信也會把 agent 叫醒一輪。想要：通知那行直接帶 status 和標題；同一個人短時間連寄的合成一則；PROGRESS 這類純告知的安靜收、REQUEST 照樣馬上通知；或加一種 FYI status、一個「不必回信」欄位。
- **現況**：全新。通知是 `lib/agent/mail_notify/_entry` 拼的一行，當初照 11-11 的設計「只帶封數與寄件人，不帶標題與內文」（[mail-notify](../11/mail-notify.md)）；每分鐘看一次，已經會把一分鐘內到的幾封合成一則。使用者 11-11 原話：「具體這是可調整的，agent自身也可以調整hook，類似免打擾」——agent 現在就能自己關掉或改間隔，但不能「只關 PROGRESS」。
- **優先**：高。四隻提到、每天發生，wf-agent 一天來回二十多封；不做的話，忙的 agent 一直被沒事的信打斷。
- **要裁**：見 [裁-2](#裁-2t02new_mail-通知要改成什麼樣)。

### T03 寄出的信沒有回執；回應沒帶寄出時間

- **出處**：[A 第 3 點](agents-feedback-1113.md#a-卡到或不順依提到的次數排)。
- **白話**：寄出去看不到對方讀了沒；自己這邊也查不到寄過什麼（ops-agent 要更正前一封的時間只能憑記憶，結果 14:13 記成 14:45）；`mailbox_read` 預設讀完就刪，壓縮對話後查不回原文。
- **現況**：部分做。
  - 已做：收信、寄信都能在工作區留一行底（`keep` 收檔名、`--keep-to`，線巳 `d23e1528e`，[ops-fixes-施工結果 § A1](ops-fixes-施工結果.md#a1-信的留底進工作區第-3-題甲)）；留底那行有 `sent_at`。讀信要留原文也早就有 `keep: true`。
  - 沒做：寄信工具的回應只印 `sent letter <名>; …`，沒帶 `sent_at`；沒有辦法看自己寄出的信對方取走了沒（「回執」）。另外留底要寄的人自己記得給 `keep`，預設仍不留。
- **優先**：中。避法已經有（給 `keep`）；不做的話，沒給 `keep` 的那幾封仍然查不回、對方有沒有讀仍然不知道。回應補 `sent_at` 是一行的事，可以順手做。
- **邊緣狀況**：回執要靠「對方信箱 `new/` 裡那封還在不在」來判斷，對方的信箱是別人的 stack，照 [rules.json](../../../knowledge/aos/rules.json) 第 2 條不能碰別人的 stack——要做就得由 daemon 或信箱工具代查，不是寄件人自己去看。

### T10 獨立 proc 的停法不清楚

- **出處**：[A 第 10 點](agents-feedback-1113.md#a-卡到或不順依提到的次數排)。

- **現況**：全新。

## 要使用者裁的

### 裁-1（T01）：子 agent 要不要能寄信？

背景：現在子 agent 只有唯讀的 aos 工具；主 agent 要替它轉寄。codex 身的子 agent 因為 U1 裁了「不管」，其實已經拿得到寄信工具——兩身現在就不一樣。

- **A 不做**：維持主 agent 轉寄。後果：零工作；主 agent 的 context 繼續被轉寄吃掉。
- **B 子 agent 只能寄給自己的母 agent**：`aos_sub` 多一支寄信工具，收件人寫死成母 agent。後果：子 agent 能直接回報、不用等主 agent 來問；但 ops-agent 那種「對外的十多封通知」還是要母 agent 轉。
- **C 子 agent 能寄給母 agent，加上主 agent 指定的名單**（預設只有母 agent），署名「代 某某」。後果：三隻提的場景都解；要多設計「名單放哪、誰能改」，名單寫在主 agent 自己的 stack；子 agent 寄錯對象的風險被名單框住。
- **D 子 agent 拿完整的寄信工具**：後果：最省事；子 agent 能寄給任何人，等於把主 agent 的對外權力整份交出去，跟「子 agent 拿少功能那台」的原意相反。

推薦：**C**。B 解不了最常見的對外通知；D 跟子 agent 少功能的原意衝突；C 用預設只有母 agent 的名單，多出來的權限由主 agent 自己決定給不給。

#### 使用者裁定（11-13 晚）

> 1.子agent寄信，他用的身份是主agent的。如果主agent覺得子agent可以用他的身份寄信，那就可以，隨意。

- **結論**：子 agent 寄信用的是主 agent 的身份；要不要把寄信工具交給子 agent，由主 agent 自己決定。底層不另做名單機制（推薦的 C 不採）。
- **後續**：見[待辦](#裁定後的待辦只列沒施工) 1。

### 裁-2（T02）：new_mail 通知要改成什麼樣？

背景：現在每分鐘看一次信箱，有新信就送一行「幾封、誰寄的」。選項由小到大，後一個包含前一個。

- **A 通知那行帶上每封的 status 和標題**：後果：agent 看一眼就知道要不要讀，不用每封都叫讀信；但純告知的信照樣會把它叫醒一輪。
- **B A，再加 PROGRESS 安靜收**：PROGRESS 的信不送通知，等下一則要送的通知（或下次醒來）時一起列出來；REQUEST、BLOCKED 等照樣馬上送。後果：打斷少很多；要處理「一直只有 PROGRESS 進來，就一直沒人看」——加一條上限（例如安靜累積超過 5 封或 30 分鐘，仍送一則）。
- **C B，再加一種 status 叫 FYI（或一個「不必回」欄位）**：後果：寄件人能明說「這封不用回」；但會動到大家都說好用的信件格式，六種 status 變七種，知識庫、檢查、範本都要跟著改。
- **D 不改**：後果：零工作；四隻 agent 繼續被打斷。

推薦：**B**。A 只省讀信那一步、沒省打斷；C 要改大家說請保留的信件格式，而 PROGRESS 本來的意思就接近「不用回」，B 已經能涵蓋。

#### 使用者裁定（11-13 晚）

> 2.純告知？這個說說。

（調度者解釋了「純告知」就是 PROGRESS 信、四個選項 A～D、推薦 B 之後）

- **結論**：底層不改（對底層來說是 D）：信件格式、`aos-post` 和相關工具都不動。信件是 JSON，多出來的 key 程式會忽略，要附加資訊就加額外的 key 或寫進 body。亂寄信、打擾人本質上是 AI 紀律問題，靠 prompt 或 agent 之間的約定解決。要的功能（例如通知過濾、PROGRESS 攢著一起看）做成一套**通用新程式**，放 `~/aos-home/ws/tools` 給大家共用。

### 裁-5（T08、T09）：使用者的話怎麼讓各 agent 直接讀到？

背景：兩題同一個根——使用者的話只能靠某隻 agent 轉述。T08 是「同意」能不能驗證，T09 是「裁定」放哪。鐵律 2 已經說轉述不算授權，所以現況不會出錯，只是多問、多轉。

- **A 維持現況**：轉述的同意不算、再問一次；裁定照 decide-page 落在當天的 thinking 夾、靠信件轉述。後果：零工作；偶爾多打擾你一次、轉述可能漏句。
- **B 裁定總表**：在會抄進活樹的知識庫放一份固定的表，每批裁完由出題線追加（日期、題、裁定、你的原話、落地檔）；樹裡的 agent 看表、不看轉述。後果：T09 解了；表還是 agent 寫的，T08 的「能驗證」沒解；新裁定要等下一次重抄才到樹裡（見 T05）。
- **C 你自己用 aos 的身分寄出核可**：你用自己的 linux user（11-12 已定「人當成一個 agent 收信」）寄一封信，信的寄件人是 aos 照寄件那方填的；收到的 agent 看寄件人就知道是你本人。後果：T08 真的能驗證；你要多打一個指令；寄件人欄位到底能不能被別的 agent 偽造，沒驗過，要先查。
- **D B＋C 都做**。

推薦：**B**。T09 是每天都在發生的、T08 一天兩次而且現在的規矩不會出錯。判準：如果一週內「轉述的同意」又讓 agent 卡住三次以上，再加 C。
