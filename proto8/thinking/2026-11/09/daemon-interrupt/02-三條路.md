# 02 三條路（照使用者四條前提；fable 規劃、opus 補）

← [README](README.md)｜上一份 [01](01-現況與實測.md)｜下一份 [03 衝突與邊緣](03-衝突與邊緣.md)

## 四條共通設計（照前提推出）

1. **鈴不帶內容**：中斷只叫 daemon（或 loop）「現在就跑一圈、看一次檔」；指令照舊是 ctl.json／procs_ctl.json／信箱，一個字不改。鈴丟了等下一圈（最多 1 秒），多響只是多看（N-09 沒變不寫）。
2. **只住在 daemon／loop＋寄件人函式庫**：proc 呼叫的仍是 `aos-daemon-ctl`、`aos-post send`、Python `daemon_ctl`，只多選填 `--urgent`（`urgent=True`）；Linux 那件事由函式庫做。proc 的程式裡沒有 SIG、socket、FUSE。
3. **被叫的一方在公開窗宣告**：daemon.json（loop.json 同）頂層選填 `interrupt`，沒寫＝關。開了，state 窗多 `interrupt` 欄說「接哪種鈴、在哪」（例 `{"kind": "socket", "path": …}`）；寄件人只看這欄，沒宣告就不響（C-52 可認公開介面）。
4. **關著時零差異**：不多開 fd、不改遮罩、nap 照舊 `sigtimedwait`。判準：沒寫 `interrupt` 的 daemon 跑 60 秒，`strace -c -f` 的系統呼叫種類與次數跟現在相同（±2%）。

兩種中斷分開看：**喚醒**＝閒著時提早看檔；**搶占**＝身體跑到一半也叫得到。

## ① 收到特定訊號後去讀特定檔案

- **怎麼運作**：鈴號（預設 SIGUSR1，可設 SIGRTMIN+n）加進全程擋著的那組訊號。閒著：nap 等到鈴就醒、回頂端看檔。跑身體：鈴號加進 signalfd，**不轉給身體**（轉了會打死它），改去插播（見下「搶占」）。寄件人：寫完檔，讀 state 的 pid、`started_at_ticks`、`boot_id`，對得上 `/proc` 才 `kill`。
- 圖：`proc ─寫 ctl.json→ 磁碟；proc ─kill(SIGUSR1)→ kernel → daemon 醒 → 讀磁碟`。鈴走 kernel、內容走磁碟。
- **延遲**：寫檔到表上看到約 5 毫秒內。
- **誰能送**：同帳號或 root。**跨帳號（模式 2）EPERM；bwrap 沙箱看不到外面的 pid**，同號可能是別的行程。跨 stack 同帳號可以。
- **丟了／漏了**：標準訊號同號會合併——鈴不帶內容，合併＝去重。漏寫只響＝白看一眼。
- **daemon 當掉／沒開**：沒 state＝`DaemonMissing`（同今天）；pid 對不上就靜靜不響，照今天等回信、逾時 `DaemonFailed`。
- **git-image**：不落地，只有 daemon.json 的設定跟著走。
- **改動量**：小～中，7～8 檔（aos-util 訊號集、loop 的 nap／signal_got／state 欄、folder.cpp 與 child.cpp 的 unblock、Python 三個口）。
- **opus 補：一個不撞 no-pid 的用法**——daemon 本來就管自己子項的 pid，所以「**daemon 叫子項**」（例 `halt` 寫子的 ctl stop 之後順手響）用訊號完全合規；而且子項的 stack 常很深，用訊號可以避開 socket 路徑上限（見 03）。前提是子的 state 有宣告接這個鈴，否則 SIGUSR1 會把一次性的 proc 打死（11-07 裁定 B：daemon 不分類，只能看公開窗）。

## ② 開一個 Unix socket 檔給人寫，並提供指令

- **怎麼運作**：daemon 在自己的 stack 建 `interrupt.sock`（AF_UNIX、stream、非阻塞），state 宣告路徑。開著時 nap 換成 `poll(signalfd＋socket)`；有人連就醒，把排隊的連線全收下、各讀一行、關掉，回頂端看檔。跑身體：`wait_forwarding` 的 poll 多一個 socket。寄件人：寫完檔，非阻塞 connect（200 毫秒逾時）、送 `ring`、關。
- **「提供相關指令」**：照 N-06 與使用者 11-03「誰能寫ctl.json就能控制」，讀成**寄件人這邊的子命令**（`aos-daemon-ctl pause --urgent`）；socket 上只跑鈴。socket 要不要自己載指令是方向題 2。
- 圖：`proc ─寫 ctl.json→ 磁碟；proc ─connect＋"ring"→ daemon 醒 → 讀磁碟`。
- **延遲**：同①，約 5 毫秒內。
- **誰能送**：看檔案權限（socket 檔寫權＋目錄搜尋權）。**跨帳號可（0660＋群組），bwrap 沙箱可**（路徑型 socket 不受 pid／net namespace 影響，沙箱本來就 rw 綁 `$AOS_DAEMON`）。**不碰 pid**。
- **丟了／漏了**：沒有訊號；每次醒全收＝合併。backlog（128）滿了寄件人當沒響，退回 super loop。先寫檔、後響鈴。
- **daemon 當掉／沒開**：檔不在（ENOENT）或沒人聽（ECONNREFUSED）都只跳過響鈴，不拿來判死活。重起時先拿 stack 的 flock，拿到才刪殘留 socket 再建。
- **git-image**：socket 存不進 git，列進「不進 image」；新機由 daemon 重建。
- **改動量**：中（socket 模組約 150 行、nap 與 wait_forwarding 的 poll 版約 80 行，關著走舊路、開著走新路＝兩條路徑要維護，Python 連線端約 40 行）。

## ③ plan9 路線：把 /proc 映射過去

這句可能有三種意思，由淺到深：

- **只把 Linux /proc 鏡射成資料夾**（子項的 `/proc/<pid>/stat` 以名字為鍵映到 `procs/<名>/…`）：只是「狀態可見」的加強、跟中斷無關，procs_state.json 已是它的 JSON 版，no-pid 後也不想把 pid 攤給別人。不當中斷方案。
- **daemon 自己當一個合成檔案系統（FUSE）**：掛 `$AOS_DAEMON/live/`，裡面 `ctl`、`state`、`procs/<名>/ctl`……；**讀＝即時回 daemon 記憶體裡的狀態，寫＝呼叫**——寫 `live/ctl` 等於下一道 ctl，daemon 收到就寫穿到真的 ctl.json、立刻跑一圈。這是 plan9 `ctl` 檔的正統做法，也最貼「proc 看到的仍是檔案」。以下照這個展開。
- **9P server**：daemon 講 9P，Linux 用 `mount -t 9p`（要 root）或使用者空間 `9pfuse` 掛上來；最後還是落到 FUSE 或 root，比上一種只多依賴不多能力。

- **怎麼運作**：libfuse3 低階 API 掛 `live/`，`/dev/fuse` 的 fd 塞進同一個 poll，不開第二條執行緒（保住現在單執行緒、fork 安全）。一次 open→write…→release＝一道指令（release 時才整份驗，照 N-06～N-08 與 ctl_warning）。信箱也能映：在 `live/mailbox/new/` 建檔寫完＝投進真的 Maildir、立刻認領。
- 圖：`proc ─write(live/ctl)→ kernel FUSE → daemon 的 fd 醒 → 寫穿真 ctl.json＋跑一圈 → write 回成功`。proc 眼裡就是寫了個檔。
- **延遲**：一趟 0.1～0.5 毫秒。**反向的坑**：FUSE 請求會把呼叫者卡到 daemon 回應為止，daemon 正在起一大批子項或卡死，所有碰 `live/` 的人一起卡。
- **誰能送**：合成檔的權限由 daemon 定；但 FUSE 預設只有掛的人看得到，跨帳號要 `allow_other`，而 `/etc/fuse.conf` 沒開（改要 root，C-78 多一步）。bwrap 遞迴綁 `$AOS_DAEMON` 會把掛載帶進去，同帳號應可通，要實測。
- **多對一要不要上鎖**（使用者 10-30 的疑問）：不用，daemon 照到達順序處理每次 release，等於 daemon 替大家排隊。
- **daemon 當掉／沒開**：沒開＝沒有 `live/`，函式庫改寫真檔走 super loop；**當掉沒卸＝殭屍掛載，連 stat 都回 ENOTCONN**，下一台起來要先 `fusermount3 -u`。
- **git-image**：掛載點不進 image；殭屍時 `git add` 會失敗，image 工具要跳過 `live/`。
- **改動量**：大（vcpkg 加 libfuse、FUSE 模組 600～900 行、掛卸清殭屍、poll 整合、寫穿）；Python 端幾乎不用改。

## 三條路共用：搶占

- **只在 `run_folder`（身體是一支程式）做**：鈴的 fd／訊號加進 `wait_forwarding` 的 poll，醒了插播。`run_inline`（內嵌單子）等待在 aos-exec 裡、期間有工人執行緒，fork 不安全，第一版只喚醒、不搶占，身體跑完才看檔。
- **loop 插播**：讀一次 ctl——**鈴聲期間讀到的 `stop` 立刻把 SIGTERM 轉給身體**（走 Ctrl-C 那條既有路），`pause`／`interval_ms`／`max` 等身體跑完才生效（跑到一半的 LLM 呼叫沒法暫停）。super loop 自己讀到的 stop 照舊等身體跑完；ctl 不必加新 key。
- **daemon 插播**：跑一次「小 tend」＝讀 procs_ctl、認信、對表、回信、寫表，**跳過自己的身體**（避免重入）；這時主行程只有一條執行緒，對表時 fork 子項安全。
- 鈴不提早跑身體，只提早看檔。
