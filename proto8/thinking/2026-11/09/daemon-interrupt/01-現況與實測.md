## 怎麼睡、怎麼醒

- **主循環**（aos-loop 的 `main_loop`，daemon 繼承它）：每圈 讀 ctl → `tend`（daemon 在這裡讀 procs_ctl、認領信箱、對表、看子項死活、判卡住、跑自己的身體）→ 停不停 → 沒到時間就 `nap`。daemon 預設 `interval_ms` 200。
- **nap**：`sigtimedwait` 等 SIGINT／SIGTERM／SIGHUP，**一次最多睡 1 秒**，暫停中固定睡 1 秒。這三個訊號整支程式壽命都擋著、排在 kernel 裡，所以一來就醒、以 128＋N 收工（子項 SIGTERM、10 秒後整群 SIGKILL、寫好 state）。
- **沒有** inotify、eventfd、socket、FIFO。全 repo 只有 aos-exec 等單子時用 signalfd＋eventfd。
- **子項結束**：daemon 不靠 SIGCHLD 叫醒，每圈對每列 `waitpid(WNOHANG)` 輪詢；`auto_restart` 的「同一拍重起」實際是下一圈。收工時每 50 毫秒輪詢一次。
- **跑身體**：`run_folder` fork 子行程後，主執行緒卡在 `poll(signalfd{三訊號＋SIGCHLD}, 無限等)`；三訊號轉給身體，SIGCHLD 才 waitpid。**整段期間不讀 ctl**。daemon 自己有身體時（`run_body`）同理：身體跑的期間 tend 不跑，信箱、procs_ctl、子項死活都不看。身體是內嵌單子時走 `run_inline`（行程內 run_inst，有工人執行緒）。
- **SIGUSR1／SIGUSR2／SIGRTMIN**：沒擋、沒處理＝預設處置＝行程直接死。daemon 起子項的 `child.cpp` 在子行程裡**寫死只 unblock 三個訊號**（不是叫 `the_signals()`），將來加鈴號這裡也要改。
- **寄件人那頭**：`aos-daemon-ctl ping`、`ctl add`、`ctl_wait` 在 Python 端每 50 毫秒輪詢回信檔或表。

## 實測（WSL2，/tmp 複本，寫檔後到 state／procs_state 反映出來，毫秒）

| 情況 | 結果 |
|---|---|
| daemon interval 200，procs_ctl 加一列 | 51～191（約 130） |
| 同上，ctl `pause` | 100 |
| 同上，暫停中寫 `resume` | 700 |
| daemon interval 5000，procs_ctl 加一列 | 301～735（被 1 秒上限救了） |
| 同上，ctl `pause`／`resume` | 700／700 |
| aos-loop 身體 `sleep 3`，跑到一半寫 ctl `pause` | **2800**（等身體跑完） |
| 對 daemon 送 SIGTERM（帶子項） | 64 毫秒退出、退 143 |
| 對 daemon 送 **SIGUSR1** | **daemon 當場死（-10）、子項成孤兒、state 停在 `waiting`** |

白話：閒著時「慢」最多 1 秒，對 LLM 動輒幾秒到幾分鐘的節奏來說不算大（C-77）；真正叫不動的是身體跑的那段。

## 環境（公司 WSL）

有 `/dev/fuse`、setuid 的 `fusermount3`、`libfuse3` 執行期（沒開發標頭；vcpkg 有 `libfuse` port）；`/etc/fuse.conf` 沒開 `user_allow_other`；Python 沒 fuse 模組；有 bwrap、沒 s6；inotify 上限 524288。Linux 內建 9P 客戶端掛載要 root（WSL 的 `/mnt/c` 本身就是 9p）。
