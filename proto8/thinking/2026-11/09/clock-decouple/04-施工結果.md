## 結論

- **daemon 不認鐘了**：`daemon.json` 的 `clock` key、`expand_clock`、`setenv AOS_CLOCK`／`AOS_CLOCK_INTERVAL` 全刪（`daemon.cpp` 約 60 行）。寫了 `"clock": …` 照 C-48 當沒看到（不報錯、不展開）。daemon 對鐘只剩「跟任何 proc 一樣讀環境的 `AOS_CLOCK` 判 `stuck_after_cycles`」。
- **鐘＝普通一列**（只根帶）：
  `"_clock": {"exec": {"argv": ["aos-clock", {"$env": "AOS_DAEMON", "$path": "clock"}]}, "interval_ms": 1000, "auto_restart": true, "stuck_after_ms": 10000}`＋根定義資料夾 `.env` 一行 `AOS_CLOCK=${AOS_STACK}/clock`。
- **範本不帶鐘**：`kernel/llm-kernel`、`daemon-judge`、`llm-team` 拿掉 `clock`；判官不再替 `_clock` 留格。`extras/image-move-check` 改成只有根帶鐘列＋`.env`。
- **子 daemon 聽外層**；要用自己的鐘，掛它的列寫成內嵌單子：`{"exec": {"argv": ["aos-exec", "--dotenv-override", "../daemon"]}, …}`。**陣列寫法 `["aos-exec", "--dotenv-override", …]` 不行**（陣列第一個是 aos-exec 的目標，報 `EntryMissing entry not found: aos-exec`；01 § 四那句寫法要照這裡讀）。
- **新通用列欄 `stuck_after_ms`**：正整數毫秒、跟 `stuck_after_cycles` 擇一（兩個都寫、0、超出 signed 64-bit＝`CfgBad`）；寫了就用牆鐘判卡住、不讀鐘（期限相加飽和）；表列寫了才輸出、adopt 讀回；reason `control window has not been answered within N ms`。其他列照舊 cycles（11-07 #12 不動）。
- **條文與文件**：N-28 兩註、N-65 ②、N-17／N-15 的 #12 句加 11-09 註、四種性質表 `AOS_CLOCK` 格、CONVENTION 佈局、板子比喻、C-05／C-44 只加註、條號表兩份、舊名對照；aos-daemon README 與 docs 01/02/04/09/10、impls/docs/03、cmd/docs/02/04、kernel/docs 01～03、templates/docs/02、aos-agent 搬家 01/03、knowledge world.md；桌面三頁（三扇門那頁不用改）。順手修：桌面「詳細參考」ping 逾時代號 `DaemonMissing`→`DaemonFailed`（`aos-agent ctl` 等不到回信也是 `DaemonFailed`，`cmd/aos-agent/aos_agent/common.py`，同頁一併改、錯誤表補一列）。

## 代定（隊長，可翻）

1. 鐘列被 SIGSTOP 後要有一次 ctl 刺激才會判 `stuck`（判卡住本來就是「刺激沒回應」；沒人碰它的 ctl 就不判）。測量從 STOP 起算 10.6 秒（10 秒期限＋一圈），不另做「鐘檔 mtime 不動就判」。
2. repo 裡沒有「根 daemon 範本」資料夾，根帶鐘列的寫法放在文件範例（aos-daemon docs/10、搬家 03）、image-move-check 與試驗場根；不新建範本夾。
3. 子 daemon override 的寫法定為內嵌單子（見結論），文件與試驗場 README 照寫。
4. `stuck_after_ms` 溢位用飽和；表上 ms 列不再輸出 `stuck_after_cycles`。
5. aos-daemon docs/02 舊錨點（名字帶 clock）有 4 處連入，保留 `<a id>`；新錨點另加。
