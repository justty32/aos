## 怎麼量的

- 把 `~/code/playground`（三層：根 100 ms 一拍＋總機 llm kernel 300 ms＋領班 200 ms，三台都開 `tick: true`）`cp -a` 一份到暫存資料夾，在那份上 `nice -n 15` 起根，掛 `fsm_ann`（假腦）。這台沒有 strace，所以用 Python 透過 ctypes 叫 inotify，數每個檔的 `IN_MOVED_TO`（先寫暫存再改名）和 `IN_CLOSE_WRITE`（直接寫、追加）次數。
- 量三段：掛好以後閒置 10 秒、第一題 `what time is it?`（4.09 秒，問腦兩次：先叫 clock、再回答）、第二題（4.09 秒）。兩題的數字幾乎一樣。
- 跑完把整份暫存資料夾刪掉、確認沒有殘留程序；沒有開任何 agent CLI。
- 牆上時間：閒置時整棵樹**每秒整份重寫約 25 次**。一題約 155 次，其中約 125 次是 4 秒裡「時間過去」本來就會寫的，約 30 次是這題造成的。

有身體的 loop 每跑一次都會重寫 state，原因如下：

- 11-02 起 state「有變才寫」，`counter_runs` 不算變動（N-09 11-02 補）。
- 11-06 no-pid P5b 加了 `responded_at`，而且「身體跑完一次（不論結束碼）都更新」，又算進有變才寫（NORMS 05 窗細則的 11-06 註；`aos-loop/src/engine/loop.cpp` 的 `run_once` 之後馬上 `responded()`）。
- 所以結果是每跑一次就重寫一次，`counter_runs` 只是順便被看到在變。使用者說的「loop 的 runs 變得太頻繁」，看到的就是這個現象，但元兇是 `responded_at`。
- daemon 的表還多一個 `tick` 觀察值（T7，`windows.cpp`）：只要開了時鐘，表每走一格就重寫一次。

## 三、旁邊的發現（不在這題範圍，只記下來）

- `interfaces.json`、`think/sent.json`、`reply.json` 有一次是直接寫，沒有先寫暫存再改名；它們是不是「給別人讀的檔」（N-05）要另外看。
- 開銷大頭應該是起程序：閒置的 fsm agent 每 300 ms 起一次 `aos-fsm` 和 `python3 idle.py`，總機每 300 ms 起一次 `aos-llm-kernel`，三個時鐘每秒各起一次 Python 寫的 `aos-tick`。一次改名寫小檔遠比起一個 Python 便宜。這點**沒量，只是推估**；要定優先順序，先量這個（判準：閒置整棵樹的 CPU 有多少比例花在 exec，有多少花在寫檔）。
