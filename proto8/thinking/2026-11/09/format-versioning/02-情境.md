判斷標準：**大聲壞**（退非 0 或表上看得到 reason）可以接受，照 11-05 重建就好；**默默錯**（照跑、換了預設值、資料不見）才是問題，因為使用者不知道要重建。

| 情境 | 現在會怎樣 | 大聲／默默 |
|---|---|---|
| **A. 新版程式開舊 git image**（例：家機 `playground-ak5` 的 tag `base-v0`，是 11-09 前凍的） | ① daemon.json 的 `tick` 被忽略，整棵樹沒有樹時鐘、退牆鐘（01 #1）；② 表上的 `_tick` 列起不來、留 stopped（#7，看得見）；③ **曾 stop→start 過的列一開門就下表**（#6b）；④ 定義裡的 `timeout_ticks`／`stuck_after_ticks` 被當沒寫（#3、#4） | ②大聲，①③④**默默** |
| **B. 試驗場與家機版本不一** | image 會帶自己的 `lib/`、範本複本（Python 工具、`act.py`、`wait.py`），C++ 執行檔卻用 PATH 上的。舊 lib 對新執行檔：舊工具打舊旗標＝`FlagUnknown`（大聲）；舊工具寫進 inst／信件的舊 key＝新執行檔忽略（默默，像 #4） | 混合 |
| **C. 子 daemon 跟父版本不同** | 同一台機器上子項都從 PATH 起，平常同版。會不同的時機是**樹跑著時重建 impls**：記憶體裡是舊 daemon，新起的子項是新 aos-loop。11-09 拆分這種：舊父讀子的 state.json 找 `responded_at` 找不到＝不判卡住（少判，不誤殺）；新 ctl 等 state_flux 等不到＝提醒行 | 多半大聲或無害 |
| **D. 腦或使用者手寫的檔**（daemon.json、ctl.json、`_entry.json`、`_memory.json`、knowledge） | 照舊文件、舊例子、腦記憶裡的舊名寫 → 新 key 名不對＝默默忽略。打錯字（`proc` 寫成 `procs`）也是同一條路，跟「舊格式」分不出來 | **默默** |
| **E. knowledge 長期累積**（memory_write 寫的、從語料收的） | 格式本身是 md／json 葉，很穩；風險在內文寫著舊指令／舊環境變數，腦照做 → 指令不存在（大聲）或 key 被忽略（默默）；鎖檔若殘留舊 holder 會一直 `LockFailed` | 內文漂移看不出來 |
| **F. 跨機器 clone**（image 或 repo） | 不 clone stack 以外的東西（stderr、信箱已擋）；同版程式就沒事。不同版＝A 或 B | 同 A／B |
| **G. 狀態檔寫壞**（當機、磁碟滿、手改壞） | procs_state 讀不了＝整份當沒有、蓋成空表（01 #8）；state_flux 壞＝照 ctl 舊 stop（文件已寫明要先清 ctl） | **默默** |

## 今天兩件的實例

- **tick→clock 改名**：照 11-05「重建」。**能重建，但使用者不會知道要重建**——程式不報錯，跑起來像正常，只是沒鐘、沒逾時。安全的重建法是「定義資料夾照新名改、stack 整份刪掉重起」；只改定義、留著舊 stack 會踩到 `_tick` 孤兒列。
- **state_flux 拆分**：**舊 stack 不能直接留著用**。舊 stack 裡 `ctl_seq` 在 state.json，新程式只看 state_flux.json，於是把已經做過的 stop 再做一次（#6、#6b），列安靜地下表。要重建就得刪 stack（或至少刪每格的 ctl.json），這跟 daemon docs/08 已寫的「state_flux 壞要先清 ctl.json」是同一件事。

**一句話**：11-05 的「舊資料壞了就重建」前提是「壞了看得出來」；現在因為 C-48 的「舊 key 忽略」，很多種壞看不出來。
