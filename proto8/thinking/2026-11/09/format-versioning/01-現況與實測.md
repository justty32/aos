## 二、程式讀到不認得／缺／壞時的反應（規則面）

- **條文**：[C-48](../../../../docs/CONCEPTS/01-設計理念/01-C-01～C-48.md)「不認得的 key 一律忽略、不報錯」；11-03 加註「程式改名後的舊 key 也是不認得的 key，一樣忽略、不報錯、不過渡」。加上 11-05「proto8 當沒有舊版」，兩條合起來的效果是：**舊 key＝缺 key＝用預設值**。
- **旗標相反**：不認得的旗標是 `FlagUnknown`（P-44，「打錯要知道」）。所以舊版腳本打舊旗標會大聲壞，舊版 json 寫舊 key 會安靜地換成預設。
- **型別錯、JSON 壞**：設定檔大多會報 `CfgBad`（daemon 的 `max`、`clock`、`auto_restart`、`stuck_after_cycles` 型別錯都擋）。
- **同一份檔裡規則不一**：daemon.json 頂層多的 key 忽略，但 `clock` 物件裡多的 key＝`CfgBad`（[docs/02](../../../../impls/aos-daemon/docs/02-看寫法決定怎麼起.md#自帶時鐘-clock選填)）。
- **程式自己寫、下次自己讀的狀態檔**（procs_state、state、state_flux、holder）：讀不了多半「當沒有」，不報錯也不提醒。

讀程式得到、沒實跑的：

- **鎖**：holder 檔若是舊 key（`lease_ticks`）又沒有 `flock`，`memory_write` 的 `live()` 當成永遠持有，子樹一直 `LockFailed`（看得見，但原因指錯）；`aos-lock` 本身同樣沒有租約就不收。
- **父判卡住**：子項沒有 `state_flux.json`（舊版子項、或關掉）＝`clear()`，永遠不判卡住；方向是「少判」，不會誤殺。
- **aos-daemon-ctl 等回音**：讀子項 `state_flux.json` 的 `ctl_seq`，舊版子項寫在 state.json → 等不到、印提醒行（看得見）。
- **llm kernel**：`aging_cycles` 寫成舊名＝沒有老化，低優先可能一直排不到（安靜）。
- **knowledge**：節點名不合 `[a-z0-9_-]`、`.`／`_` 開頭＝不算節點，安靜地看不見；內容是 md，沒有格式版本問題，但**內文**會過時（例如寫著舊指令名），腦會照著舊說明做——這是語意漂移，版本標記管不到。
