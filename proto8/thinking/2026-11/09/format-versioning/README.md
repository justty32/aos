## 結論

- **現況**：proto8 程式讀寫的 json 和資料夾佈局**都沒有版本標記**，也沒有升級機制；只有 wf 工具有 `wf-table/1` 那類契約名，人看的有 [NORMS 附錄 3 舊名對照](../../../../docs/NORMS/附錄3-舊名對照.md)。
- **真正的問題不是「沒有相容」，是「壞了看不出來」**：C-48「不認得的 key 忽略」（11-03 起舊 key 也算）加上 11-05「沒有舊版」，結果是改名後舊資料**默默換成預設值**。11-05 的「壞了就重建」要先看得出壞了才會去重建。
- **實測最危險的三個**（WSL /tmp 複本，[01](01-現況與實測.md)）：
  1. **11-09 state_flux 拆分前的 stack 用新程式開**：曾經 stop 再 start 過的列，一醒來就把舊的 stop 再做一次，`done code 0` 從表上消失，沒有任何警告（01 #6b）。
  2. **舊 key 被當沒寫**：daemon.json 的 `tick` 被忽略＝整棵樹沒有時鐘、退牆鐘；inst 的 `timeout_ticks` 被忽略＝逾時保護沒了（`sleep 5` 跑滿 5 秒）；`stuck_after_ticks` 被忽略＝門檻變回 10（01 #1、#3、#4）。
  3. **procs_state.json 讀不了**（寫壞、形狀不對、有一列壞）：daemon 退 0、不提醒，把表蓋成空的，上一班睡著的 proc 全部失聯（01 #8）。這條跟版本無關，當機也會踩。
- **大聲壞的**（可以接受）：型別錯、JSON 壞＝`CfgBad`；舊旗標＝`FlagUnknown`；表上 `_tick` 列找不到 `aos-tick`＝留 stopped＋reason。
- **選項**（[03](03-正式版機制與種子.md)）：A 現狀＋不默默錯（現在，不衝突）→ B 持久檔帶 `format` 版本、不對就拒讀（正式版當天，不衝突）→ C 獨立的 `aos-upgrade` 腳本（正式版後第一次改格式，衝突所以只在正式版後）→ D 程式內建讀舊版（不推薦）。
- **現在先埋的便宜種子**：S1 列「持久檔」清單；S2 讀持久檔收成單一入口（以後加檢查只改一處）；S3 狀態檔讀不了要說話、壞檔留證；S4 改持久格式時 thinking／日誌寫一句「要重建什麼」；S5（可選）stack 記「誰寫的」。都不跟 11-05 衝突。版本號本身可以等正式版當天再寫（規則訂成「沒標記＝proto 時代＝拒讀」效果一樣）。

## 報告

### 必修（proto 期就該處理，跟要不要做版本無關）

1. **adopt 讀不了 procs_state 會默默蓋成空表**（01 #8、04 D5）：至少印 `warning:`、把壞檔改名留著。這是當機復原的洞。
2. **11-09 前凍的 image／stack 不能直接用新程式開**（家機 `playground-ak5` 的 tag、各 git image）：要重建＝定義裡 `tick` 改 `clock`、`*_ticks` 改 `*_cycles`，**stack 整份刪掉重起**（只刪每格 `ctl.json` 也能避開 #6b，但 `_tick` 孤兒列與舊鐘檔還在）。建議在 [clock-and-hot-writes 06](../clock-and-hot-writes/06-state拆分施工結果.md) 與桌面試驗場說明補這句（S4）。

### 設計問題（細節 [04](04-設計問題.md)）

- D1 「舊 key 忽略」＋「沒有舊版」合起來會藏住壞。
- D2 C-48 的私有 key 讓「不認得就報錯」做不到，版本偵測只能靠明寫標記。
- D3 daemon.json 頂層寬鬆、`clock` 物件嚴格，條文沒寫判準。
- D4 旗標嚴格、json 寬鬆，舊例子寫 json 會默默失效。
- D5 狀態檔沒有「讀不了」的復原路徑（＝必修 1）。
- D6 image 是「舊 Python 複本＋PATH 上新 C++」的混合版本，也不記是哪個 commit 凍的。
- D7 改持久格式那天沒有「舊 stack 怎麼辦」這一步（state_flux 施工只驗了新 stack）。
- D8 舊名對照表只有人看的 md 版。

### 建議

- 現在做 S1、S3、S4；S2 跟著平常改檔順手收；S5 看使用者要不要。
- 正式版當天開 B：一種持久檔一個 `format` 名，沒標記或不對＝拒讀＋英文提示；配置檔（人寫的）可以不帶，狀態檔（程式寫的）一定帶。
- 正式版之後要改持久格式，寫 C（獨立腳本、先備份），不寫 D。
- 正式版前把 NORMS 附錄 3 轉成資料檔，給 C 當來源。

### 要使用者裁定

1. **什麼時候算正式版**：候選判準（[03 §三](03-正式版機制與種子.md#三什麼時候算正式版要使用者定的判準候選擇一或組合)）——有資料要活過一次改版（重建超過 30 分鐘或丟了不能重來）、有第二個使用者或第二台長期機器、宣布拿掉 proto、一個月內持久格式沒改。推薦以前兩條任一成立為準。
2. **現在埋哪些種子**：推薦 S1＋S3＋S4 現在做、S2 順手、S5 可選。
3. **正式版的舊 key 政策**：維持 C-48「忽略」只靠版本標記擋（推薦，因為 D2），還是另加「已退休 key 報 `KeyRetired`」清單（跟 C-48 11-03 加註衝突）。正式版前定就好。
4. **D3 要不要寫成條文**：「只有自己讀的子物件可以對不認得的 key 報錯」——推薦寫進 C-48 當註。
