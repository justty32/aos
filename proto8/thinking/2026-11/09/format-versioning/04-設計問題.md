# 04 設計問題（照 user/02「審」：冗餘、沒考慮到的狀況、跟原則打架）

## D1 「舊 key 忽略」＋「沒有舊版」合起來，會把壞藏起來

C-48 11-03 加註讓舊 key 跟不認得的 key 一樣忽略；11-05 讓程式不做相容、不留提示。單看都合理，合起來就是：**改名＝舊資料默默換成預設值**。11-05 的「壞了就重建」需要「壞了看得出來」，這個前提目前不成立（02 的 A、D、G）。這是原則之間的縫，不是哪支程式寫錯。

## D2 C-48 的私有 key 讓「不認得就報錯」做不到

C-48 允許幾支程式共用一份 json、各放自己的 key（例：daemon.json 裡 daemon 的 key 和交給子 loop 的 key 混在一起）。所以讀者**不能**用「有不認得的 key」來判斷「這是舊格式」——它分不出是別人的私有 key、打錯字、還是舊名。要偵測版本只能靠明寫的標記（03 的 B／S5），不能靠嚴格讀。

## D3 同一份檔裡兩套規則

daemon.json 頂層不認得的 key 忽略，`clock` 物件裡不認得的 key 卻是 `CfgBad`。兩種都說得通（`clock` 物件只有 daemon 自己讀，沒有私有 key 的需求），但條文沒寫「只有自己讀的子物件可以嚴格」這條判準，下次別的物件會各寫各的。

## D4 旗標嚴格、json 寬鬆，兩邊落差

舊腳本打舊旗標＝`FlagUnknown`，同一個意思寫進 json＝默默忽略。例：`--timeout-ticks` 大聲壞，inst 的 `timeout_ticks` 安靜失效（01 #4）。腦和人照舊例子寫 json 的機會比打旗標多。

## D5 程式寫的狀態檔沒有當機復原的「讀不了」路徑

procs_state 讀不了、某列壞，adopt 直接當沒有並蓋成空表（01 #8）。這不只是版本問題：當機、磁碟滿、手改壞都會走這條，睡著的 proc 全部失聯、stack 變孤兒，沒有任何一行提示。跟 daemon 自己宣稱的「收工途中被 kill -9，重開時結果一樣」那套復原承諾不一致。

## D6 image 是混合版本

image 帶 `lib/`、範本的 Python 複本，C++ 執行檔用 PATH 上的。image 本身不記是哪個原始碼 commit 凍的，打開時也沒人比對。所以「一份 image＝一個版本」不成立，它是「舊 Python＋新 C++」。

## D7 改持久格式的那天沒有「舊 stack 怎麼辦」這一步

state_flux 拆分的施工結果（[06](../clock-and-hot-writes/06-state拆分施工結果.md)）驗了「image clone 後 stopped 列 start」，用的是新程式寫的新 stack；沒驗「拆分前凍的 image 用新程式開」。照 11-05 這不用相容，但至少要有一句「舊 stack 要刪」，否則就是 01 #6b。

## D8 冗餘：人看的改名表有，機器看的沒有

[NORMS 附錄 3](../../../../docs/NORMS/附錄3-舊名對照.md) 已經是一份完整的「舊名→新名」表，只給人看。正式版要做升級腳本（C）或舊名報錯時，這張表就是現成的資料來源；現在它是 md 表格，以後要自己再抄一次成資料檔。不急，正式版前轉成 `wf-table/1` 資料檔就行。
