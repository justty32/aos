# 06e 切換步驟（11-24 早上）

← [06 入口](06-三分的施工設計.md)｜起樹、停樹的指令出自 [dev-env/03-換機](../../../../../wf/workflows/dev-env/03-換機.md#起樹停樹)｜改表的細節與家機在 [06f](06f-改表的做法與家機.md)

## 結論

- eca-aos 自己也在樹上，停樹時它也停。所以**整張清單由使用者本人（或他開的一個樹外的視窗）照著打**，不靠樹裡任何一隻。
- 能先寫成腳本的都先寫：`switch.sh` 一步一個子指令，每步印出結果就停，等人看過再打下一步。
- 順序：停 → 對齊漂移、出補丁 → 套到工作樹 → `install.py` → 交 commit → 改表與別的專案的定義 → 起 → 驗。**先交 commit 再起樹**，樹裡的 agent 醒來看到的就是交好的 main。
- 每一步都有退路；沒 push 之前都退得回去。

## 每一列怎麼驗（第 12 步）

1. **表**：每台 daemon 各打一次 `aos-daemon-ctl -d <stack> ls`，跟第 0 步存的比：列一樣多；停之前 running 的現在 running，停之前 stopped 的還是 stopped；沒有哪一列的原因寫 `failed to start`。
2. **路徑**：`stack_paths.py --root ~/aos-home/.stack` 再跑一次「只列不改」，該改的檔裡命中是 0（daemon 起來會重寫表，重寫後還是新路徑才算數）。任何一個 stack 裡都沒有 `procs_state.json.bad-*`。
3. **eca-claude 的 11 列**：每棵樹至少挑一隻問一句（`aos-agent -d <stack> -t <名> ask '回一個字'`）。`eca-aos` 另外看 `aos-agent -t eca-aos tools ls`，它自己加的兩支工具還在。
4. **agent-fsm 的列**（`mine_paper/main`、`mine_mecha/main`，以及用那 6 份定義的）：看 `<它的 stack>/stderr.txt` 沒有新的錯、`state.json` 的格在走；有腦可用的問一句。格的路徑錯了，症狀是那一列很快變 `stopped`。
5. 這棵樹的四列（`eca-aos`、`-kb`、`-templates`、`-core`）全看。

個別一列壞了、其他都好：不用整棵退，照 06f「個別一列的備案」修那一列。

## 出錯怎麼退回

| 停在哪 | 怎麼退 |
|---|---|
| 第 4～6 步（還沒交 commit、表沒動） | `switch.sh unapply`：`git apply -R out/tri-split.patch`、清新夾留下的快取 → `install.py` → 起樹。樹跟切換前一樣 |
