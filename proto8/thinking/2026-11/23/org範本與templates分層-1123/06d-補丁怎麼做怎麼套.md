# 06d 補丁怎麼做、怎麼套

← [06 入口](06-三分的施工設計.md)｜既有的做法與坑：[wf/public/patch-and-commit](../../../../../wf/public/patch-and-commit.md)

## 結論

- **在 repo 外的一份 `git clone` 上做**，工作樹一個檔都不動，直到停樹。
- 東西分兩層：**機械層**是一支可重跑的搬遷腳本（[06c](06c-要改的每一處與分工.md) 的 R1～R5），**手改層**是各位子在複本上的 commit。main 往前走了，就在新的 main 上重跑腳本、再把手改的 commit 接上去。
- **帶回的形式是一份補丁檔**：從測過的那個複本 commit 對 main 算出來，停樹後 `git apply` 到工作樹，再走 `commit-request` 交成一個大 commit。
- 推薦理由：機械的部分重跑不怕漂移；補丁保證工作樹等於測過的那一份；最後仍然是 `commit-request` 產生的 commit，生成物由排隊重生。

## 在哪裡做

```
~/.aos/scratch/tri-split-1123/
├─ aos/      git clone --no-hardlinks ~/repo/aos（只在它自己的 main 上 commit，永不 push）
├─ tools/    split.py（搬遷腳本）、moves.tsv（對照表）
├─ out/      tri-split.patch、檔名清單、測試 log、pre-switch.txt
└─ t-*/      各位子跑測試用的 git archive 複本
```

- 用 clone 不用 `git archive`：要 git 認得改名、要能三方合併、要能把新的 main 抓進來。
- 防誤推：clone 完下 `git -C aos remote set-url --push origin no-push`。它的 commit 只是做補丁的中間產物，不是 repo 的分支。
- 「只有一個 `main`、不開分支」說的是 repo；這份複本用完就丟。這是替使用者做的小選擇，他不要的話退路是 `git archive` 加 `git init`，代價是漂移時要手動三方合併。

## 兩層

| 層 | 內容 | 怎麼產生 | main 往前走了怎麼辦 |
|---|---|---|---|
| 機械層 M | 搬夾、相對連結、所有換路徑字 | `tools/split.py --apply`（對乾淨的 main 跑；跑兩次結果一樣），整合的人 commit 成一個 | 丟掉舊的 M，在新的 main 上重跑一次 |
| 手改層 H | 程式六處、README 改寫、測試對照表、生成設定、重新編譯出的 `agent-python` | 各位子改檔，整合的人一個位子一個 commit | `git cherry-pick`；只有漂移剛好改到同一行才要手解 |

`split.py` 是一次性的施工工具，放 scratch、不進 `proto8/`，不是產品裡的遷移程式；對照表抄在 [06a](06a-目標目錄.md) 留底。

## 幾個位子怎麼在同一份複本上合作

1. **設一個整合的人**（建議 eca-aos 派一條專線，一隻 Claude，線名 `tri-split-1123`）。只有它在複本裡下 git、跑 `install.py`。
2. 整合的人先寫 `split.py`、跑出 M、commit。
3. 各位子**只改複本裡自己範圍的檔**（跟在 repo 裡同一套範圍），不下 git；改完寄信給整合的人，附檔名清單。順序：核心程式 → 範本 → 知識庫、前端代班、`wf/`、條文同時。
4. 整合的人看 `git status`、`git diff -- <那個位子的範圍>`，只收範圍內的，一個位子一個 commit。
5. 測試一律在複本 HEAD 的 `git archive` 上跑（`t-<位子>/`，跑前清掉所有 `AOS_*`、在那份複本裡 `install.py`），不在 `aos/` 裡直接跑。
6. 在 repo 那邊**不要 claim**：claim 會擋住今晚還在正常交件的線。切換當下樹是停的，沒有人會搶。

## 做完怎麼驗（今晚）

1. `split.py --check`：舊路徑的樣式只剩在「不碰的範圍」。
2. 全套測試對照：同一支腳本在「main 原樣」與「複本 HEAD」各跑一次 `proto8` 底下每個 `tests` 夾，只看新出現的紅。
3. 預演交件：`commit-request submit --repo <複本> --cache <暫存夾> --dry-run …`。看生成器過不過（新夾沒說明會報 `DescMissing`）、舊位置留下的 `_index.json` 怎麼處理。**這一步我沒試過**，結果由整合的人回報。
4. 預演改表：見 [06e](06e-切換步驟.md)「今晚要備好的」第 3 項。

## 漂移：從現在到明早

今天 16:55 還會 push 一次，之後各位子可能還有零星 commit。明早**停樹之後 main 就不會再動**（會 commit 的都停了），這時才做最後一次對齊：

1. `git -C aos fetch origin main`；`git log --stat <上次的底>..origin/main` 看動了什麼。沒有新 commit 就直接出補丁。
2. 有：新的 main 上重跑 `split.py --apply` 得到新的 M，再 `cherry-pick` 各個 H。
3. `split.py --check` 再跑一次：漂移帶進來的新句子如果寫了舊路徑，會在這裡被抓到（R4 會順手改掉，只剩 R5 抓不到的要人看）。
4. 只重跑漂移碰到的那幾夾測試；漂移碰到 `proto8/py` 或 `templates` 才重跑全套。
5. 把這次的底（main 的 hash）記進 `out/pre-switch.txt`。

要讓這一步快：今晚先約好「22:00 之後除了急件不交 `proto8/` 的 commit」之類的時間，由 eca-aos 定。

## 帶回 repo（停樹後；指令在 06e 的清單裡）

1. 出補丁：`git -C aos diff --binary -M <main 的 hash> HEAD > out/tri-split.patch`，排除生成物（`wf/knowledge/code-map/` 與知識庫以外的 `_index.json`；`commit-request` 不收它們，由它重生）。同時出兩份檔名清單：`out/files.txt`（新增與修改）、`out/rm.txt`（刪掉與搬走的舊路徑）；中文檔名用 `git -c core.quotepath=off`。
2. repo 這邊先確認補丁會動到的檔在工作樹是乾淨的（`git status --short` 跟兩份清單沒有交集；有的話先讓那條線交件）。
3. `git apply --check out/tri-split.patch`，過了才 `git apply`（只動工作樹，不動 index）。
4. 清掉舊夾留下的 `__pycache__` 與空夾（例 `proto8/templates/agent-fsm/__pycache__`；它們不在 git 裡，補丁搬不走）。
5. 核對：補丁動到的每個檔，工作樹的內容等於複本 HEAD 的（逐檔比雜湊）。
6. `commit-request submit --line tri-split-1124 --files $(cat out/files.txt) --rm $(cat out/rm.txt) --msg-file … --dry-run`，沒問題再正式交。日索引、月索引、`progress` 用 `--op`。

**為什麼不用別的方式帶回**

| 方式 | 不選的理由 |
|---|---|
| 停樹後直接在 repo 跑 `split.py` 再套手改的補丁 | 工作樹是現算的，不是測過的那一份；出錯時不好說是腳本還是補丁 |
| `git pull` 複本的 main | 繞過 `commit-request`（生成物、排隊的檢查）；等於從別處拉一條線進來 |
| 現在就出補丁、明早直接套 | main 一漂移就套不上，或套上了卻漏掉新句子裡的舊路徑 |

## 這個 commit 之後

不 push（使用者說了才 push）。家機要等 push 之後才 pull、才照做（[06f「家機照做」](06f-改表的做法與家機.md#家機照做)）。
