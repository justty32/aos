# 歸群：同一個原則的不同面，還是巧合

每群的列數、典型 id 見 [01-盤點](01-盤點.md)；這裡只寫每群的「形狀」與判斷。

## 一眼看懂：15 群其實只有四種形狀

| 形狀 | 群 | 底下的共同原則 | 判斷 |
|---|---|---|---|
| **甲 認名**：某一層寫死認得另一層的名字、檔名、字句 | G01 層級認名、G02 角色特權（認名的那一半）、G11 越界寫入 | C-52「上層不知道下層是什麼」被破 | 同一個原則，**該消掉**（P6 去耦合就是範本） |
| **乙 出口**：給「看不到下層的讀者」多給一點 | G03 下層錯誤往上透、G09 人殼與程式兩條路 | 出口的讀者是誰，決定能給什麼 | 同一個原則，**該升格成一條判準** |
| **丙 預設**：沒給時怎麼辦、誰的值贏 | G04 hub 環境變數、G05 時間來源、G14 範本與程式預設、G13 保留字 | 「沒設」與「誰贏」散在各處各自決定 | 大半是同一個原則，**升格**；個別的旋鈕特許維持 |
| **丁 清單**：「只有這幾個」 | G06 名額與清單、G07 命名代號、G15 範圍限縮、G08 生命週期特准、G10 重複實作、G12 平台捷徑 | 有判準的清單會自己長；沒判準的每次都要再裁 | 各自不同；**共同的是寫法**——清單要附判準 |

## 甲 認名（消掉）

- **G01 層級認名**：daemon 寫死 `aos-loop` 的入口、`ctl.json`／`state.json` 的名字與格式、aos-loop 錯誤行的字句（I28～I30、I41）；llm kernel 讀 daemon 的 `procs_state.json`、手拼 `procs_added` 信（I51～I53）；aos-json `check` 寫死哪些 key 底下有 exec（I66）；thought 寫死 `templates/agent-fsm`、上限照範本 act 格算（P44、P09）；P7 規劃讀子的 ctl 信箱（D06、T52）。
- **G02 角色特權裡「認名」的那一半**：aos-agent 的 `is_kernel` 認判官、`post.py` 認判官、判官兩種掛法各給一套提示（P03、P04）；`AOS_KERNEL` 一設，`ctl add` 整個改走判官（T15、D35）。
- **G11 越界寫入**：thought 在子的 stack 寫 `thought.json`（P12）、aos-agent／agents 改目標 stack 的覆蓋檔（P13）、daemon 自建每個 proc 的 stack（I21，條文說只有 aos-exec 建）。
- **判斷**：三群是同一件事——**A 為了做事，去認 B 是誰、B 的內部長怎樣**。差別只在認的是程式（G01）、角色（G02）還是地盤（G11）。P6 證明這型可以消：把「認出子是 daemon」換成「任何 proc 都能寫的通用布林 `auto_restart`」，父就不用認。

**要分清楚的一點**：「認身份」跟「用公開介面」不一樣。daemon 提供「loop 型」是使用者定的功能（N-28），它依賴 aos-loop 是合理的；壞在**檔名與格式在兩邊各寫一份**、**認 aos-loop 錯誤行的字句**——這些不是公開介面，是對方的內部。所以消掉的方向是「改成認對方宣告的介面」，不是「什麼都不准認」（見 [05 方向題 1](05-衝突與方向題.md)）。

## 乙 出口（升格）

- **G03 下層錯誤往上透**：C-52 明文例外 ①aos-mcp、③llm-kernel、④act、⑤給腦工具轉接最後一行；**沒列進表、程式已經在做的**：daemon 讀 `stderr.txt` 末行當 reason（I41）、thought 也轉接（P18）、agents 成功時轉印下層 warning（P19）；**規劃中**：通用 runner 讀函數 stderr 轉回信（T04）。
- **G09 人殼與程式兩條路**：終端才問 `[y/N]`（T12）、stdin 是終端就當 `{}`、人殼不給 `--queue-wait-s` 就永遠排（T38）、chat 的 `> ` 提示印在 stderr（P37）、工作區沒設時有的報 `WsMissing`、有的拿 cwd（P29）。
- **判斷**：同一個原則。每一處的理由都是同一句——**這個出口的讀者看不到下層／不是程式**（外部 agent 看不到 MCP log、腦只看 tool 訊息、寄信方只看回信、人只看終端）。逐項裁了五次，下一次（runner）已經排著，正好符合「越來越多、好處遠超過壞處」。

## 丙 預設（大半升格）

- **G04 hub 環境變數**：N-63 ②「沒設＝`<名字>Missing`」已經有三個有退路的（`AOS_KERNEL` 沒設寄 daemon 的 ctl 信箱 D20、`AOS_DAEMON` 沒設找 `./.stack` D22、`AOS_TICK` 沒設退牆鐘 D18）；「近的贏」用了三次（`AOS_TICK_INTERVAL`、`.env` 外層、子 daemon 自帶時鐘）；`AOS_AGENT`、`AOS_TICK_INTERVAL` 是有使用者原話的特許。
- **G05 時間來源**：兩鐘已升格成 N-65；剩的是不一致——T 隊「時鐘檔不在＝0」對 tick-time 03「退牆鐘」（T20）、`--timeout-s` 用秒對等回信用 tick（T08）、寫死的 10／30／3 秒抄在 N-17、N-63、N-66 三處（D86）。
- **G14 範本與程式預設**：範本帶 `tick: true`、範本出廠 `--enable-logs`、判官 `queue` 程式預設不開——三次都是「程式預設照現況、範本可以開」。
- **G13 保留字**：`_tick`、`_entry`、`_tooldef.json`、`ping`、固定信箱名；目前沒有任何條文說「`_` 開頭是 aos 的」。
- **判斷**：G04、G14、G13 是同一個原則的三面——**沒給的時候，結果要能從一條寫下來的規則推出來**，而不是每個名字各自決定。`AOS_TICK_INTERVAL` 這種「使用者明說很不想、但太香」的旋鈕特許是**真的特例**，維持。

## 丁 清單（各自不同，寫法要統一）

- **G06 名額與清單**：九個短名（白名單、沒列不准開）、三個不可逆（**有判準**：刪掉的東西別處沒副本、又沒有 `--dry-run`）、C-42 兩道關、inst_proc.c 300 行。
- **G07 命名代號**：C-54 結尾 11-04 加 `…Exists`、11-06 加 `…Rejected`（三天加兩次）；aos-inst C ABI 的 `PathConflict`、`PathNotAbsolute` 不合 C-54（I02、I03）；退 10 有三種意思（I22、I23）；設定檔名 usage 三種寫法（I26）。
- **G08 生命週期特准**：「某一型 proc 准重起」出現三次（子 daemon、`_tick`、P7 的 restart_on_stuck）→ 15 已收成通用 `auto_restart`，**這群已經升格完了**。
- **G10 重複實作**：`.env` 解析兩份（`cmd/aos-tools/bin/aos-tools:440`、`impls/aos-exec/src/env/dotenv.cpp:169`）、判活多套、預設檔名兩處寫、py↔lib 互相依賴（P40、P41）。
- **G12 平台捷徑**：已經有 C-83 當判準（看會不會破壞可遷移性、root 例外）；違規的只有「靠 PATH 上 aos-tools 的真位置找共用模組」（P42）。
- **G15 範圍限縮**：「先不補」「直接起的先不管」「只限掛在 daemon 上的」——刻意縮範圍，本來就是暫時的。
- **判斷**：這幾群不是同一個原則。共同點只在**寫法**：三個不可逆有判準，所以新指令自己就知道算不算；九個短名、C-54 結尾、C-52 例外表沒有判準或判準藏在註裡，所以每多一個就要再裁一次。G10、G12 的違規各自消掉即可。
