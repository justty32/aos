## 使用者原文（11-06）

> 然後再派一個隊伍，去調查現在有哪些是"特例"，去綜覽，並提出一些建議，關於這些"特例"可能造成的影響，以及這套特例是否有相似性，或者是某項特例往後可能還會有更多(其好處超過壞處很多)，是否值得成為慣例

前情：同一天看完 P6 說「對於daemon來說，子daemon對他來說就只是一個普通的proc。不要耦合」。

## 一句話結論

特例本身多半無害，**會累積成耦合的只有一種：某一層寫死認得另一層的名字、檔名或字句**（耦合「是」的 50 列有一半在這一群）——這種一律消掉，做法就是 P6 那樣「把認型別換成任何人都能寫的通用欄位」；另外有兩型已經重複出現 3～8 次、理由每次都一樣（**出口給看不到下層的讀者時多給一點**、**沒給的時候怎麼辦**），值得各收成一條判準，取代現在一項一項裁、一層層加註的例外表。

## 數字

289 列（條文 88、impls 70、程式 69、thinking 62），去同件約 226 件，分 15 群＋其他；15 群其實只有四種形狀：甲 認名（消掉）、乙 出口（升格）、丙 預設（大半升格）、丁 清單（各自不同，寫法統一）。

## 推薦升格的慣例（全文見 [04](04-升格建議與慣例草稿.md)）

- **升格判準**：認名型第一次就消掉；同型再出現時問往後會不會更多、好處是否遠大於壞處，是才升格；第 3 次、5 項或 3 天 2 項只當提醒，不當開關（11-07 使用者裁定 sol 審查 #23）；清單決定升格時改寫成「判準＋現行表」；「先不做」要寫等什麼。
- K1 出口的讀者看不到下層時，可以附下層最後的錯｜K2 只保留原件的終端問／非終端不問｜K3 hub 變數沒設＝Missing 或寫明唯一退路｜K4 近的贏只限 tick｜K5 程式預設照現況、新行為由範本開只列那幾件個案、不作通則（11-07 使用者裁定 sol 審查 #25）｜K6 `_` 開頭的名字是 aos 的｜K7 別人的 stack 對方宣告了才寫。
- **推薦消掉**：G01 層級認名、G02 裡認判官名字的部分、G11 越界寫入、G10 重複實作（`.env` 解析兩份等）、P42 靠 PATH 真位置找模組、C-54 的違規代號。
- **已經升格完的範本**：`auto_restart`（「某型 proc 准重起」三次 → 通用布林）、N-65 兩鐘。

## 方向題（推薦放第一；細節與後果見 [05](05-衝突與方向題.md)）

1. C-52「不知道下層是什麼」讀成「不認身份、可以認公開介面」？推薦**是**｜照字面什麼都不認（loop 型也拆成 exec 型）。
2. C-52 例外表改成一條判準（K1）＋現行表？推薦**改**｜維持逐項裁。
3. hub 變數「沒設」改寫成 K3？推薦**改**｜照現況各自例外。（「設了指不到印 warning」已裁。）
4. `_` 開頭保留給 aos（K6）？推薦**是**｜撞名再說。
5. 別人的 stack：對方宣告的覆蓋層准寫、其他經信箱或 ctl（K7）？推薦**是**｜照 C-81 一律不准寫。
6. 升格判準的數字：推薦**第 3 次升格、清單 5 項或 3 天 2 項就改寫**｜第 2 次就升格。
