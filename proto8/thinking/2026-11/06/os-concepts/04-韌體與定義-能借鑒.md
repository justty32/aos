# 子題 2 能借鑒的

全部零程式（條文一句、名詞表幾行、P8 食譜幾行、範本改一行）；排程對照 [apply-ideas 02](../apply-ideas/02-排程.md)。

### A. 「值住哪＝什麼時候定」四層表（編譯期 vs 執行期的 aos 版）

- **白話**：新 key 該放定義、`.env`、覆蓋層還是 ctl，現在靠經驗。
- **選項**：① **≤10 行寫進 CONCEPTS 附錄1「板子比喻」那一欄旁**（使用者已裁要寫那欄）：**改了要凍住才生效 → 定義（ROM）；一台跟一台不同 → `.env`／hub 變數（取樣腳）；一隻跟一隻不同、要跟 image 走 → 覆蓋層（EEPROM）；跑中隨時翻、不留歷史 → ctl（暫存器）**。後果：之後 `tick`（定義）、`AOS_TICK_INTERVAL`（取樣腳）、`limits`（表、ctl 可改）各有歸位理由，少一輪討論。② 不寫，讀 N-57／N-59／aos-agent docs 自己拼——下次又問「slots 能不能跑中改」。③ `aos-agent ctl state` 印每個值來自哪層（1～2 h）——之後另排。
- **推薦 ①**；判準：出現第 2 個「這 key 放哪」的討論就寫。**落**：附錄1，跟板子欄同 commit。**排**：T8 條文日。

### B. A/B 分區與回滾 → 不做雙份定義，食譜寫三行

- **白話**：改壞定義醒來起不來，現在知道要 `start`，不知道怎麼退回舊版。
- **選項**：① **P8 食譜加「改定義前 `git commit`（或 tag）→ 醒來 `ls` 看到 `stopped`＋`reason` → `git checkout -- <定義>` → `aos-daemon-ctl start <名>`」；另一句「跑著改定義＝XIP 時寫 flash，先 sleep 再改」**。② daemon 起不來自動 `git checkout`——daemon 不該知道定義是 git（C-52）。③ 定義旁留 `def.prev/`（真 A/B）——違 11-05 不存副本、搬家體積翻倍。
- **推薦 ①**；判準：一週內人手回滾 >3 次才考慮工具。**落**：P8 食譜。**排**：P8。

### C. 斷電安全：rename 已是 double-buffer，差 fsync；不加程式、食譜一句

- **白話**：窗與信箱寫法已對，只有真拔電才有「兩份皆空」風險。
- **選項**：① **P8 食譜「存 image＝全 sleep → daemon 退出 → `sync` 一次 → 再 cp／commit／拔碟」**。② `procs_state.json` 寫入加 fsync（只這一扇）——約 0.5 h C++，每圈 200 ms 一次 fsync 傷碟、慢。③ 窗加 CRC 欄——JSON 壞了本來就 `CfgBad`／留上一份好的，多餘（C-56）。
- **推薦 ①**；判準：P9 實測 `kill -9` daemon ×50＋模擬掉電出現壞 JSON ≥1 次才做 ②。**落**：P8／P9。

### D. 狀態機寫法：fsm.json 維持純表驅動，條文一句對上 HSM 四樣

- **白話**：韌體 HSM 的 entry／exit／guard／history，aos 已各有歸處，別加 key。
- **選項**：① **N-36 旁或名詞表板子欄一句：「entry／exit＝格自己做（格是程式）、guard＝結束碼、history＝`stage.txt`（stop→start 從停的那格接回，免費）、子狀態機＝格裡放一隻 fsm」**。② fsm.json 加 `on_enter`／`on_exit`——違 C-49「fsm 很單純」。
- **推薦 ①**；判準：≥3 個範本在每格開頭重複同一段 entry 程式才翻案。**落**：N-36 旁。**排**：T8 條文日。

### E. 靜態配置：`slots`／`max_running` 是編譯期常數，跑中改＝凍住再醒 → README 方向題 5

- **白話**：池大小寫在定義是對的（無 malloc 精神），只要讓人知道改它要重起。
- **選項**：① **A 的表裡一行「`slots`、`max_running`＝定義；`limits`、loop `max`＝表／ctl」；kernel docs 一句「改 slots 要重起 kernel」**。② kernel／judge 開 ctl 收 `slots`／`max_running`（各約 1 h）——多兩個 ctl 面、三種上限三種改法。
- **推薦 ①**；判準：使用者一週內想跑中改 slots ≥1 次才做 ②。**落**：T8；程式之後另排。

### F. 產線校正參數：`endpoints` 是這台的、跟 source 混層——標天然差異、食譜一句，不拆

- **白話**：搬家 #17 已列自擔，差一句「搬完先改哪」。
- **選項**：① **P8 食譜「能力包是這台的：搬家後先改 kernel.json 的 `endpoints[*].url`／`model`」**。② 拆成 `endpoints.json` 用 `$ref` 引、搬家只換一檔——指示詞現成、範本改一行；但範本不拆檔是慣例（P-27 那條線），`$ref` 給要拆的人用。③ url 寫 `{"$env": "AOS_LLM_URL"}`——多一個環境變數，使用者不要。
- **推薦 ①**；判準：同一份 kernel 定義在 ≥2 台機器常駐才做 ②。**落**：P8。

### G. debug vs release：單一 build 是對的；範本「出廠 debug on」

- **白話**：`--enable-logs` 要改 `_entry` 才開，試驗場每次手加很煩。
- **選項**：① **試驗場與 `templates/` 的 daemon `_entry` 預設帶 `--enable-logs`（daemon stdout 本來就是 log，無害），正式用自己刪一個字；kernel 範本 `endpoint` 維持 `fake`（測試樁）**——改範本一行。② 不動，食譜提醒——每次手加。③ `.env` 開關——argv 陣列裡 `{"$env"}` 空字串會變成一個空參數，沒乾淨寫法，不做。
- **推薦 ①**；判準：P8 試驗場跑三次都手加就改範本。**落**：P8（跟範本 `tick: true` 同 commit）。

## 方向題全文（README 題 4、5）

**題 4：改定義「什麼時候生效」要不要統一？** 現況：brain／act 每格重讀 `tools.json`／`llm.json`（下一題生效）；aos-fsm 每圈起時讀 `fsm.json`；aos-loop 的 `loop.json`、kernel 的 `kernel.json`、daemon 的 `daemon.json` 只在起時讀一次（之後走 ctl）。
- **推薦：不統一**——各程式 README 一句「我什麼時候讀定義」，食譜兜底「改定義一律先 sleep 再改、醒來生效」（跟已裁的 OTA 食譜同一句）。後果：零程式；行為照舊、只是寫明。
- 替代 a：全部改成只在起時讀（真「複製到 RAM」）——brain／act 要改、覆蓋層「下一題生效」（feat-proto 件 1 已定）會變成要重起，違已裁。
- 替代 b：全部每格重讀——loop／kernel 跑中改 `interval_ms`／`slots` 多一條路跟 ctl 打架（一件事兩個地方，C-56）。

**題 5：`slots`／`max_running` 要不要開 ctl 讓人跑中改？** 推薦：**不開**，當編譯期常數、改＝凍住再醒（E）；判準一週內想跑中改 ≥1 次才開。替代：kernel／judge 各加 ctl key（各約 1 h）；後果多兩個 ctl 面、`limits` 已走表、三種上限三種改法。
