# 其他手段與跟原則的衝突

## 手段（推薦放第一，每條附門檻）

| # | 手段 | 推薦 | 判準（門檻） | 依據 |
|---|---|---|---|---|
| 1 | **image 用專門的 repo，不跟原始碼混** | **推薦，一律** | 沒有門檻：image 會一直改寫歷史（下一條），原始碼 repo 不能這樣做；image 的大檔也不該拖慢原始碼的 clone | [02](02-極限分析.md) |
| 2 | **image repo 只留最新一份**：每次凍住做一個沒有父親的 orphan commit ＋ `push --force`，舊的要留就打 tag 少量留 | **已裁：只留最新一份** | `.git` 超過工作樹壓縮後大小的 **2 倍**、或超過 **1 GB** 就一定要；實測 squash 後 `.git`＝單份 image（B N=400：322→19 MiB） | [03](03-實測數據.md) |
| 3 | 搬家用 `git clone --depth 1`（或 `git bundle` 只包最新） | 推薦（沒做第 2 條時） | 歷史大於一份 image 的 **3 倍**時；實測 B N=400 完整 clone 386 MiB、depth 1 只要 82 MiB（.git 19 MiB） | 03 |
| 4 | **關自動 gc**（image repo 設 `gc.auto=0`），凍住、commit 完再手動 `git gc`（或做第 2 條就幾乎不用 gc） | 推薦 | loose 物件超過 6700 就會自動 gc：實測 A 模式第 9 次 commit、archive 變體第 2 次就觸發，而 gc 是最慢的一步（B N=400 單次 319 秒） | 02、03 |
| 5 | history 分段（寫滿 64 KB 封存、開下一段） | 方向題（改程式） | 只在**要留完整 git 歷史**時才值得：實測 D 21 MiB vs B 99 MiB（N=200），保留 request.json 的 F 則是 120 MiB；但 `think/request.json` 照樣整份重寫，不一起改就只省一半 | 03 |
| 6 | `think/request.json` 改成可重建（無 pending 且 request 不在時退 11 回 think 重組；有 pending 先收原回信），然後擋掉 | **已裁：改成可重建、擋掉** | 它跟 history 一樣大、一樣平方成長；擋掉＝git 量直接少一半 | [04](04-gitignore建議.md) |
| 7 | 調大打包的 delta 視窗（`--window=250`） | **不推薦** | 有效（F N=200：100→18 MiB），但單執行緒 546 秒，E 與 A 超過 10 分鐘沒跑完（預設 71～244 秒）；第 2 條不用打包就達到同樣大小 | 03 |
| 8 | log 上限：`stderr.txt` 超過 **1 MB** 由外部 copytruncate（`failure.cpp` 已容許）；`live.jsonl` 每輪換新檔或超過 **10 MB** 輪替 | 推薦（但跟 git 無關） | 它們已經被 .gitignore 擋了，上限只是為了磁碟；一隻 eca 跑一週約 200 MB | 01 |
| 9 | archive 定期輪替出 image（有人開 `--keep` 時） | 推薦 | archive 超過 **1 萬封**或 **100 MB** 就移到 image 外按日期壓縮；實測 archive 變體 50 隻 × 50 輪就 1.4 萬檔、status 0.12 秒、第 2 次 commit 就觸發自動 gc | 03 |
| 10 | `.trash/` 擋掉不搬、人定期清 | **已裁** | 超過 **100 MB** 或 **30 天**由人清；已在 .gitignore 擋掉 | 01-續 |
| 11 | git-annex／LFS | **不推薦** | 它們是給「少數大的二進位檔」的；image 全是文字、會長的是只附加檔，LFS 每版存一份完整檔、沒有 delta，比 git 本身更糟。等真的出現單檔 **> 50 MB 的二進位**（今天 0 個）再談 | 01 |
| 12 | shallow 的反面：`git replace`／`filter-repo` 事後清歷史 | 不推薦 | 第 2 條從一開始就不留歷史，比事後清簡單 | — |

**一句話**：做 1＋2＋4 加上 [04](04-gitignore建議.md) 的 .gitignore，就不會失控——git 量≈一份 image，跟跑多久無關；image 本身（主要是 history）仍會線性長，那是 agent 的記憶，該長。

## 跟現有原則的衝突（保留調查脈絡，三題裁定見入口）

| 原則 | 衝突在哪 | 各自的後果 |
|---|---|---|
| **N-16** 信箱 `archive/` 選用、`done --keep` 才進 | N-16 允許留紀錄；但 archive 在 image 裡是名字唯一、只進不出的最壞情況（[02](02-極限分析.md)） | 擋 `**/archive/`＝紀錄只留原機器；不擋＝第 2 次 commit 就自動 gc、檔數 250 萬封／週。今天沒人用 `--keep`，所以**現在不衝突**，有人開了才衝突 |
| **C-17** 靠 stack／state.json 醒來接著做（11-06 改讀：只有硬凍） | 醒來需要的「在途狀態」全在檔裡，包括 `think/request.json`——它同時是 history 的一份副本 | wait 的恢復規則：無 pending 且缺 request 退 11 重組，有 pending 先收原回信，因此 request 可擋，pending 與在途回信仍須搬 |
| **C-79** image 模型「實例不存 source 的副本」（portable-flow 02） | `think/request.json` 把定義裡的 `system.txt` 與 tools 定義整份抄進 stack，每輪重寫 | 小（幾 KB／隻），但跟原則字面不合；已裁不讓 request 進 image，一起解 |
| **N-67** 可遷移性檢查單 | 六項都在講「搬不搬得動」，沒有一項講「搬的成本會不會隨時間失控」；⑥ 檢驗法寫「`cp -a`／git」並列 | 不改條文；這份的結論可以當 ⑥ 的註（git 要配 .gitignore＋只留最新） |
| P-15 定義執行期不寫 | 不衝突：定義資料夾幾乎不變，git 量可忽略 | — |
| KISS（C-56） | 分段 history、可重建 request 都是多一點程式 | 只留最新一份（手段 2）不用改程式，最 KISS |
