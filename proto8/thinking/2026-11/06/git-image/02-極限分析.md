# 極限分析：50 隻 agent 連跑一週、每次凍住都 commit

## 情境

- 50 隻 agent-fsm，每分鐘一輪，連跑 7 天＝每隻 **10080 輪**。
- 每小時凍住一次、`git add -A && git commit`＝**168 個 commit**（每個 commit 隔 60 輪）。
- 每輪 history 長 3 KB（一般）；大量讀檔的 agent 一輪 30 KB（重度，[03](03-實測數據.md) 有敏感度）。
- 變體：「archive 只進不出」＝每封信都 `done --keep`（今天沒有，[01](01-盤點表.md)）。

一週後**工作樹本身**（只看 history）：50 × 10080 × 3 KB ≈ **1.5 GB**，`think/request.json` 再一份等大的 ≈ 3 GB；壓縮後約 0.8 GB。這是「image 本身」的大小，跟 git 無關——**不管怎麼存，搬一份 image 至少要搬這麼多**。

## git 為什麼會膨脹（白話）

git 每個 commit 存的是**整份檔案的快照**，不是「這次多了哪幾行」。一個只附加的檔（`history.jsonl`）每次 commit 都變了，git 就再存一份**完整的新版本**（壓縮後約 1/3.8）。

- 第 1 次 commit 存 60 輪那麼長，第 2 次存 120 輪那麼長……第 168 次存 10080 輪那麼長。全部加起來＝**1 + 2 + … + 168 份**，是 168 份的 85 倍。這就是「平方成長」：時間拉長 2 倍，git 大約大 4 倍。
- 公式：`.git ≈ Σ(c=1..C) 每次 commit 時所有「有變的檔」的大小 ÷ 壓縮率`。只附加的檔 → `≈ agent 數 × 每輪 byte × K × C²/2 ÷ 3.8`。
- 拿這個公式對實測 B 模式 N=200、K=10：算出 81 MiB，實測 gc 前 99 MiB（多出來的是 state 等小檔與目錄物件）；一週：算出 **34.6 GB**，跟 codex 的外推 34.5 GiB 一樣。所以外推可以信公式，不用信冪次擬合。

**`git gc` 本來應該救得回來**：打包時 git 會把「同一個檔的前後版本」存成差異（delta），只附加的檔差異極小，理論上壓回接近一份最終大小。**實測沒救回來**：A 模式 gc 只省 17%（329→272 MiB），B 模式也是 17%。原因（假設，[03](03-實測數據.md) 驗證）：git 找 delta 對象時按「檔名尾巴＋大小」排序、只在相鄰 10 個裡找；**50 隻 agent 每格都叫 `history.jsonl`、`request.json`**，相鄰的多半是別隻的同名檔、內容完全不同，配不到自己的上一版。這是 aos 小格「每隻都用同樣檔名」的佈局碰上 git 預設值的結果。

**其他會膨脹的來源**：

| 來源 | 怎麼膨脹 | 一週量級（推算） |
|---|---|---|
| `think/request.json` | 跟 history 等大、每輪整份重寫 → 跟 history 一樣平方成長 | 再一倍（≈ B 的 2 倍） |
| eca `live.jsonl` | 只附加、一輪幾十 KB → 平方成長 | 10 隻 eca × 20 KB／輪＝每輪 200 KB，比 50 隻的 history 加起來（150 KB）還多 |
| archive 變體 | 每輪 5 封信、名字唯一＝每封都是新檔、新目錄；kernel 請求信 body＝那輪的 request（又是 history 大小） | 檔數 50×10080×5≈**250 萬封**；內容≈history 的平方和再一份 |
| 刪了也留在歷史裡 | `ctl rm` 的小格、清掉的 `.trash`、輪替出去的 log，舊 commit 還有 | 只能靠改寫歷史（squash）才回收 |
| 名字唯一的小檔 | thought 子小格、`.trash/<時間>/` | 量小，但每個都多 2～3 個樹物件 |

## 會在哪裡變慢

| 動作 | 跟什麼成正比 | 極限下（推算／實測） |
|---|---|---|
| `git status` | 工作樹檔數（stat 每個檔）＋被擋的資料夾能不能整夾跳過 | 2000 檔時 0.01～0.03 秒；archive 250 萬封時要掃 250 萬個檔＋目錄——**擋了也要走**（git 得進資料夾才知道裡面被擋，除非規則是整個資料夾 `**/archive/`，那就整夾跳過） |
| `git add -A` | **這次變了的檔的總大小**（每個都要整份重算雜湊、壓縮） | 只附加大檔＝每次 commit 都要重讀全部 history；一週後每次 add 要處理 1.5～3 GB（實測 A N=200 已 1.7 秒） |
| `git commit` | 目錄物件數 | 小；archive 變體時每封信一個目錄，commit 變慢（A+archive N=50 已 0.35～0.74 秒） |
| `git gc`／repack | 物件總大小 × 找 delta 的視窗 | **最慢的一步**：A N=100→200 從 31 秒變 244 秒（8 倍）；B N=400 要 319 秒。調度者 11-06 要求改單執行緒後更慢（[03](03-實測數據.md)） |
| clone／搬到別台 | pack 大小（全部歷史） | 一週 B 模式 ≈ 29 GiB 要傳；`--depth 1` 只要一份 image（≈ 0.4～0.8 GB） |
| 自動 gc | loose 物件 > 6700 就在 commit 後自己跑 | 實測 K=10：A 第 9 次、B／C／D 第 35～37 次、A+archive **第 2 次** commit 就觸發；一週 168 次一定會跑，跑的就是上面那支最慢的 gc |

## 結論

**會失控，而且是平方失控**——但失控的只有兩三種「只附加、每次整份進 git」的檔（history、request、live），加上假設中的 archive。兩個獨立的槓桿各砍一大截：

1. **不讓 log 進 image**（擋 `live.jsonl`、`stderr.txt`、`archive/`）：A→B 實測 329→99 MiB（N=200）。
2. **不讓 git 每次存整份 history**：分段（封存段不再變，D 模式 21 MiB）、或只留尾巴（C 模式 16 MiB）、或讓 delta 配得到（調大視窗，[03](03-實測數據.md)）。
3. 第三個槓桿是**根本不留歷史**：image 只要「最新那份」，用 squash／`--depth 1`／每次新 orphan commit（[05](05-其他手段與衝突.md)）。
