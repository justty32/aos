> 啊，我又有一個想法，還得再派一隊：之所以大多東西都要走json+檔案系統，這是為了可遷移性。而雖然我們有.env，但環境變數的濫用仍可能對可遷移性造成損害。請綜覽我們的現狀，給出評估，看看有哪裡需要注意。

## 一句話結論

環境變數**只活在行程裡**時都沒事——醒來時新機器重給一份，正好就是「搬家後用這台的值」；出事的是**值被寫進檔**的四處：kernel 把解開的**金鑰明文寫進信資料夾**、`aos-tools add` 把 **env 值與絕對路徑凍進登記檔**（而且蓋過新機器的；使用者 11-06 選「C 照現況」：已知代價、不修——「用${HOME}/...，本來就是在命令行這個階段展開」，存展開後的值跟命令列一致）、claude／codex 型 agent 的小格**記下絕對 ws／stack**、叫回畫面時讀回（程式判斷）、文件建議把**絕對 hub 路徑寫進定義的 `.env`**。前兩個與最後一個在 /tmp 複本實測重現過；另一個實測重現的「寄件人絕對路徑當額度鍵、搬了上限悄悄失效」T 隊 b190e00c 已改相對、降成要注意。所以要加的規矩不是「少用環境變數」，而是「**從環境讀到的值不准落檔**」。

**Q2＋Q3 使用者補的理由（11-06，逐字）**：

> 然後那個工具登記檔aos-tools add --envs那件事，登記的時候把路徑展開...就是說，我們在命令行使用指令的時候，用${HOME}/...，本來就是在命令行這個階段展開。

解讀：命令列打 `--envs DATA=${HOME}/data` 時 `${HOME}` 本來就由 shell 當場展開，aos-tools 拿到的已經是值；登記檔存展開後的值跟命令列語意一致，不算 bug。`--env-file` 檔裡的 `${…}` 是 aos-tools 自己展開的（實測 X2：`FOO=${HOME}/foo` 存成 `/home/guanyu/foo`），照同一個邏輯＝**檔裡的 `${…}` 照命令列那樣，在 add 當下展開**。只差一點：檔裡沒大括號的 `$NAME` 不展開、照字面存（照 N-59 `.env` 基礎子集只認 `${名字}`，使用者 10-22 已定的格式），shell 則會展開——不另開題。

照原則直接做、不用問的兩項也排了步：P3 eca 小格 `ws.txt`／`stack.txt` 存相對（R7）排在 2c 的 E3；P4 kernel docs/01 改寫（R4）排在 2c 的 E4。排程見 [apply-ideas 02](../apply-ideas/02-排程.md) 序 2c「env 可遷移性修補」。

## 方向題（細節與後果見 [05](05-衝突與方向題.md)；推薦放第一；裁定見上段）

3. **Q3 `--envs`／`--env-file` 存什麼**：推薦存原字串、call 時才展開 `${}`＋help 寫「密鑰別用 --envs」｜只准存名字指示詞｜照現況存展開後字面。
4. **Q4 N-67 加三項要不要交條文隊**：推薦要｜只寫進各程式 README。
5. **Q5 `AOS_KERNEL`／`AOS_TICK` 設了但指不到時**：推薦印 warning 行｜照現況悄悄退路。

不用問、照原則能直接做的：kernel docs/01 改建議（跨樹 hub 只在 root 層 export，或寫 `${AOS_CD}/..`）、kernel 在飛的 exec 存相對、eca 小格存相對、搬家九步併 P8。
