# 判官排隊做成選項

使用者 11-06 裁：「做成選項」；頂層當時代定預設不開。11-07 已裁：程式未寫 `queue` 仍預設 false，`daemon-judge/judge.json` 範本改開 `queue: true`。（11-07 使用者裁定 sol 審查 #1）以下照原則定細節（可翻案）；程式只讀 [`lib/aos/judge/_entry`](../../../../lib/aos/judge/_entry)（223 行 Python）、[llm kernel 的隊列](../../../../impls/aos-llm-kernel/src/queue/queue.cpp)（`queue.json` 記 `seen_at_runs`、信留信箱 `cur/`）、[kernel/docs/02](../../../../kernel/docs/02-kernel-modes.md)。

## 定下的（一句一條）

| 項 | 定法 | 為什麼 |
|---|---|---|
| key | `judge.json` 加選填 **`queue`**，值 `true`／`false` | C-54 小寫；一個布林就夠（KISS）；物件形式等有第二格再開 |
| 預設 | 程式沒寫＝`false`＝滿格 `SlotMissing`；`daemon-judge/judge.json` 範本開 `queue: true`。（11-07 使用者裁定 sol 審查 #1） | 範本開排隊，程式本身預設仍關 |
| 誰排隊 | 只有**要格的信**（`procs_added`、`procs_started`、`procs_woken`）沒格時排；`stopped`／`removed`／`slept`／`ping`／不認的 key 照舊立刻轉 | 不排的信能把格騰出來，隊首不會卡死自己 |
| 隊列存哪 | **信就留在 `$AOS_STACK/requests/cur/` 不 `done`**；判官另寫一扇窗 `$AOS_STACK/queue.json`（排隊中的信名、要幾個新名字、`since_at`，有 `AOS_TICK` 加 `since_at_ticks`） | 隊列在樹裡、跟 image 走、凍住不丟（可遷移性檢查單 1、4）；跟 llm kernel 同形；窗＝進度（N-66「進度看窗」、N-14 一人寫） |
| 順序 | **先來先掛**（取信順序照 aos-post：有序先、再名字），不認 `priority`、不 aging | 判官只有一種資源（running 格）、一種順序；多一種就該寫 kernel 身體 |
| 每輪怎麼看 | 新進的信照舊 `see`；已排的只看 `queue.json` 的名字與格數，有格就從隊首轉 | 模式 1 跑在 daemon 圈內要快；隊長 50 封也不每輪 50 次 `aos-post see` |
| 有格時 | 照現有 `forward`：一般信帶原 `reply_to` 轉進 ctl 信箱、daemon 套完回 `{"applied": true}` 給原寄件人；有序信改依下方 11-07 註的 `keep_ordered`；轉完才 `done`。（11-07 使用者裁定 sol 審查 #3） | 判官不轉手、不自己跑（C-47） |
| 排隊時回不回信 | **不回**「queued」信 | 一封請求一封回信（N-66）；進度看窗 |
| 寄件人等多久 | 照舊：`aos-agent ctl add` 30 秒沒回信＝`DaemonMissing`（「寄信不回＝呼叫失敗」），訊息加半句「or queued by the judge: see `$AOS_KERNEL/../queue.json`」；信留著、之後有格照掛 | 跟「daemon 睡著、信留箱裡之後照套」同一先例。**11-06 使用者裁後改**：等多久、等滿算什麼都由寄信者設，見 [05](05-寄信者自設逾時.md) |
| 撤掉排隊的 | 人手 `aos-post done <requests> <信名>`（不回信） | 現成指令；`regret` 只撤 `new/` 的 |
| 上限／過期 | v1 **不加**；要時加 `max_wait_ticks`（兩鐘規則、沒 tick 退牆鐘），過期回 `SlotMissing` 帶等了多久 | 寫什麼做什麼；判準：P9 試驗場出現「排了一小時沒人知道」才加。**11-06 使用者裁後改**：不放 `judge.json`，由寄信者在 body 寫 `queue_wait_ms`、判官到期回拒信（[05](05-寄信者自設逾時.md)） |
| 算不算 running | 排隊中**不算**；`max_running` 仍數表上 running＋本輪已放行 | 格是 daemon 表上的事；模式 2 的已知限制不變 |
| 判官睡著／凍住 | 模式 1 daemon sleep＝身體不跑、信留 `cur/`、`queue.json` 不動；醒來先將牆鐘期限已過的信一起拒絕；要跨凍住排隊，用 `--on-queued ok` 不帶期限。（11-07 使用者裁定 sol 審查 #6）模式 2 的 0 號同 docs/02 已知限制 | 零程式；正是「隊列在樹裡」的好處 |
| 有序信 | 排隊規則一樣（只排要格的那封）；同一寄件人「有序 add 再有序 stop 同名」會 stop 先到 | 自擔：有序保證的是投遞順序，認領後歸收件者 |

## 11-07 有序轉寄補註

`judge.json` 新選填布林 `keep_ordered`，沒寫或 null 為 false；關時有序信以尾名一般轉寄，原 `reply_to` 保留，經判官不保有序，daemon 回信的 `in_reply_to` 是尾名，要對上請寄一般信。（11-07 使用者裁定 sol 審查 #3）開時保留 `--ordered` 轉寄；原有 `reply_to` 才指回判官 `judge_replies/`，`judge_ordered.json` 記新名對原名與原回信箱，每輪先收回信並用原名代回；無原 `reply_to` 不接回箱、不記表。上方舊轉寄敘述以本註為準。（11-07 使用者裁定 sol 審查 #3）

## 跟 N-42「兩隻 kernel 不併」的界線

開了 `queue` 的判官仍只管**「掛不掛、什麼時候掛」**：一種資源（running 格）、一種順序（先來先掛）、不看 body 裡的任務、不問腦、不認 `priority`、沒有 deadline／speed／budget。llm kernel 排的是**問腦任務**（級數＋aging → deadline → speed → 等得久，還有 slots 分包、budget）。寫成一句放 N-42 (2) 旁：「判官的隊列只有先來先掛；要優先序、期限、額度＝寫一個 kernel 身體（llm kernel 是範例）」。所以不違 N-42，也不違 C-47 加嚴（判官照樣只轉寄）。C-11／C-12 的「排序」在判官這裡只到「誰先掛」，11-06 註已說明。

## 排在哪、插不插大重構

- **不插大重構**：判官是 `lib/aos/judge/_entry`，不在 S7～S11 任一步的檔裡（S8 Python 已做完）；之後做不重搬檔、不重改介面。
- **排程建議**：apply-ideas 02「大重構後」序 2（P6～P9）**之後**獨立一步「判官排隊」（2 h；11-06 裁定後併上寄信者自設逾時、合計約 4.5 h，已排進 apply-ideas 02），可跟 W 線並行。理由：P8 試驗場是驗它的場地（agent 生 agent 件 4 撞 `SlotMissing` 的劇本）、P9 清單含 ping 洪水；v1 不用 tick，不等 T 線。
