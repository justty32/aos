# 三個口子（之二：②、③）

場景同 [02](02-三個口子.md)：`~/sum/mailbox` 後面接著 `summarize`，寄信方 `~/me/agent`。

## ② 收信方看不懂 body：只靠「不回」，還是回錯誤信

### 選項 A（Recommended）：有 `reply_to` 就回錯誤信；信封本身壞的照舊不回

白話：**分兩層**——`letter.json` 不是 JSON、缺 `body`（信封壞）＝aos-post 的 `LetterBad`，照 N-16 決定 27 丟掉、記 `mailbox_warning`、不回（連 `reply_to` 都可能讀不出來）；**信封好、body 不合**＝函數的事：有 `reply_to` 回 `{"error": {"code", "msg"}}`，沒有就只記 `mailbox_warning`。`code` 照三扇門錯誤行的代號。

```
寄：echo '{"pth": "notes.md"}' | aos-post send --reply-to ~/me/agent/reply ~/sum/mailbox
summarize 的 stderr：summarize: error: ArgumentsBad missing required key path (usage: …)   退 1
回信 body：{"error": {"code": "ArgumentsBad", "msg": "missing required key path (usage: …)"}}
函數退非 0 又沒錯誤行（下層的碼，R8）：{"error": {"code": "RunFailed", "msg": "summarize exited 3"}}；被訊號殺：{"error": {"code": "RunFailed", "msg": "summarize killed by signal 15 (exit 143)"}}
逾時（inst timeout_ms）：{"error": {"code": "TimedOut", "msg": "summarize killed after 60000 ms"}}
stdout 不是 JSON：{"error": {"code": "ReplyBad", "msg": "stdout is not JSON"}}（kernel 現況）
```

後果：寄信方分得出「它不認得我」跟「它忙／它掛了」（使用者的 SaaS 比喻：4xx 對 timeout）；三扇門一條線接到底（錯誤行 → 回信）；代價：收信者要寫回錯誤信那條路（kernel、判官有了，daemon ctl 信箱要補）；這是**非同步呼叫層自己的規則**，N-16／aos-post 不改（信封壞不回仍是 aos-post 的事；[03 衝突 2](03-邊緣與衝突-續.md)）；通用 runner 讀函數 stderr 的第一行要列進 C-52 例外表（[03 衝突 3](03-邊緣與衝突-續.md)）。

### 選項 B：只靠「不回＝失敗」（daemon ctl 信箱現況）

白話：看不懂就丟、記 `mailbox_warning`，寄信方逾時自己算失敗。
後果：規則最少；但寄信方永遠分不出為什麼，重試也沒意義；要查得去翻收信者的 `procs_state.json`／`mailbox_warning.txt`（no-pid「想知道原因讀對方上一層的表」那條管的是「它掛了」，管不到「它不認得」）。

### 選項 C：回信永遠包一層 `{"result": …}`／`{"error": …}`（JSON-RPC 原樣）

白話：成功也包 `result`，兩者擇一、頂層只有一個 key。
後果：形狀最整齊、退 10（「查了，沒有」）也能帶 `{"result": …, "code": 10}`；但每個收信者多包一層、現成三個都要改、`aos-llm recv` 印出來的東西也變。**推薦維持 kernel 現況**：成功＝stdout 原樣、失敗＝頂層 `error`；條件寫進說明——「回信函數的 stdout 頂層別用 `error` 這個 key」。退 10 照 N-43 不是錯，stdout 原樣回（函數自己說「沒有」）。

## ③ 長時間呼叫的進度

使用者：「這套就自己做，我們之後有需要的話再往上疊。」所以只擺形狀，不建議現在做。

### 選項 A（Recommended）：先不定；要看就讀那封信資料夾裡的窗

白話：跑那封信的 stack 就是 `cur/<信名>/`（kernel 代定 3：問腦單子 `cwd`＝信資料夾、stack＝它）；函數若有進度就照 N-14 開窗寫 `state.json`，寄信方（知道信箱、知道信名）去讀。經 daemon 掛的（kernel 現況）再多一張 daemon 的表可看。

```
cat ~/sum/mailbox/cur/<信名>/state.json     # {"phase": "running", "counter_done": 3, …}
```

後果：零新機制、凍住時照樣看得到（fs-image）；代價：寄信方要讀得到收信者的信箱（同帳號可以；沙箱或以後「一個 agent 一個帳號」時讀不到→那時再疊 B）。

### 選項 B：進度信（LSP `$/progress` 那套）

白話：收信者對同一個 `in_reply_to` 多寄幾封 `{"progress": {…}}`，最後一封才是結果。

```
回 1：{"sender": …, "in_reply_to": "<信名>", "body": {"progress": {"done": 3, "total": 10}}}
回 2：{"sender": …, "in_reply_to": "<信名>", "body": {"summary": "…"}}
```

後果：沙箱內外、跨帳號都通；但要多一條「哪封是最後」的約定（看 body 有沒有 `progress` 鍵，又是保留字），而且 `aos-llm recv`／`ask`、no-pid 的 `ask()` 都假設**一封信只有一封回信**、拿到第一封就 `done`——要改。先不做，等真的有需要。

### 選項 C：長工作改成「請 daemon 掛一個 proc」

白話：寄信只請對方掛 proc（kernel 現況），進度看 daemon 表那列的 `phase` 跟 proc 自己的窗。
後果：這其實就是 A 經 daemon 的樣子，不另算一條；寫在這裡只為了說明「進度」跟「no-pid 讀表判活」是同一件事。
