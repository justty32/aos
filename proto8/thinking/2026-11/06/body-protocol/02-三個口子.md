# 三個口子（之一：①）

下面的例子都用同一個場景：`~/sum/` 是一台收信者（一個資料夾程式），寄信方是 `~/me/agent`，想請它把 `notes.md` 摘要成 200 字。

## ① 「支不支援看接收者的 PATH」不好在哪

使用者自己說「這好像不太好」。具體不好在四點：
1. **寄信方看不到對方的 PATH**，只能猜；猜錯＝不回＝跟「它忙／它掛了」分不開。
2. **PATH＝整台機器的指令**：能寫信箱＝能叫收信者跑 PATH 上任何東西（`rm`、`curl`）——這正是 10-24 kernel 要加 `accept` 白名單、11-04 乾脆把 inst 從信裡拿掉的病（[sandbox 02 S18](../../../2026-10/24/sandbox/02-決定-照推薦定-可翻案-使用者-10-2.md)、[think-as-function 02 § 1](../../04/think-as-function/02-設計-信與kernel.md)「kernel 不替人跑單子、不帶走寄信人的環境」）。「能寫檔就有權限」在這裡變成「能寫檔＝整台機器的權限」，太大。
3. 「支援」變成**收信者環境的副作用**，不是收信者的決定：PATH 多裝一支程式，所有信箱同時「支援」它。
4. `argv[0]` 不帶 `/` 照 PATH 找、帶 `/` 照收信者的 cwd 算——同一封信在兩台收信者意思不同。

### 選項 A（Recommended）：信箱即能力——一箱一函數，body＝那個函數的 stdin JSON

白話：**信箱後面接著哪個函數，就支援哪個函數。** 收信者的定義寫「這個信箱＝跑這個 aos-exec 目標」，每封信跑一次、body 餵 stdin、stdout 當回信。要支援兩種事就開兩個信箱（或照 json-argv 題 2「子資料夾＝子動作」在 body 放 `op`，由那個函數自己分）。這就是使用者「多開 mailbox 分權」的直接形狀，也是 daemon ctl、llm kernel、判官現在的樣子。

```
~/sum/def/serve.json      {"mailbox": "mailbox", "exec": "../tools/summarize", "timeout_ms": 60000, "interval_ms": 300}
~/sum/mailbox/            tmp/ new/ cur/          ← 擁有者開的；誰寫得進＝Linux 權限（S17）
~/sum/tools/summarize/    _entry  _tooldef.json   ← 普通 aos 函數；_tooldef.json 就是「我接什麼」的說明

寄：echo '{"path": "notes.md", "max_chars": 200}' | aos-post send --reply-to ~/me/agent/reply ~/sum/mailbox
letter.json：{"sender": "/home/me/agent", "sent_at": "…", "reply_to": "../../../me/agent/reply", "body": {"path": "notes.md", "max_chars": 200}}
收信者做的：take → 在 cur/<信名>/ 寫 stdin.json＝body → run_inst({"argv": ["aos-exec", "--stack", "cur/<信名>/", "../tools/summarize"], "cwd": "cur/<信名>", "stdin": "stdin.json", "stdout": "reply.json", "stderr": "stderr.txt", "timeout_ms": 60000}) → done --reply < reply.json
回信 body：{"summary": "…"}      （summarize 的 stdout 原樣）
```

後果：
- 寄信方不需要知道對方 PATH、不需要清單——它只要知道信箱在哪（hub 型變數或明給，N-63，跟今天一樣）。
- **安全**：信只提供輸入，不提供程式；函數讀 `path` 讀到哪由函數自己管（C-53 入口姿態），跟「腦叫工具」同一套信任模型（P-41）。
- 跟 json-argv 無痛互轉成立：**腦叫 tool 的 `arguments`＝寄信的 body**，同一份 `_tooldef.json`。
- 代價：想「隨便叫任何東西」得先有人開信箱接；一台收信者要接 N 種事＝N 個信箱或一個帶 `op` 的函數。
- 「收信→跑→回信」這段是通用的（kernel 多的只是 `endpoints` 代號表、slots、額度）——可以抽成一支通用 runner（暫名 aos-serve；kernel 之後變成它的一種設定），**什麼時候做交 apply-ideas**。

### 選項 B：直接寄 inst、跑不了就回錯誤信（使用者的暫定原樣）

白話：body 就是一張 inst 單子，收信者是「跑單子的人」，用自己的環境跑；`argv[0]` 找不到＝回 `{"error": {"code": "LaunchFailed", "msg": "CommandMissing summarize"}}`，不是不回。

```
寄：echo '{"argv": ["summarize", "--max-chars", "200"], "stdin": "notes.md"}' | aos-post send --reply-to ~/me/agent/reply ~/w/inst-mailbox
回：{"error": {"code": "LaunchFailed", "msg": "inst cannot run: CommandMissing summarize"}}   或成功時 stdout 原樣
```

後果：
- 最通用、零登記；PATH 問題照舊存在，但**從「不回」變成看得見的錯誤信**（解掉 ① 的第 1 點，解不掉第 2～4 點）。
- 「寫得進信箱＝以收信者身分跑任何指令」：`envs` 能蓋 PATH、`stdin`／`stdout` 能指任何檔、`$env` 指示詞能把收信者的祕密解進 argv（[03 邊緣](03-邊緣與衝突.md)）。**只有收信者本來就是「專門跑別人單子的沙箱 worker」時合理**（aos-sandbox 包起來、帳號 `aos-run`、信箱 2770、`envs_clear` 強制、body 裡的指示詞不解）。
- 跟 11-04 的決定對撞（[03 衝突 1](03-邊緣與衝突-續.md)）。
- **推薦的位置**：不當通則，當 A 的一個特例——開一個「inst 信箱」，它接的函數就是「跑 body 這張單子」（`"exec": "aos-run-inst"` 之類），這樣 A 的規則一條都不用破。
- 變形 B′（body 是 inst 但收信者只認 `argv`、其他 key 全忽略、`argv[0]` 只在收信者的 `tools/` 裡找）：安全了，但那其實就是 A 加一個 `op`，不如直接寫 A。

### 選項 C：信箱旁放一份「我接得了哪些」清單（頂層 11-05 夜提的 `_tooldef.json`）

白話：收信者在信箱旁放 `accepts.json`（幾個 tool schema），寄信方先讀再寄，腦也能直接拿它當工具表。

```
~/sum/mailbox/accepts.json   [{"name": "summarize", "description": "…", "parameters": {…}}]
```

後果：
- 寄信方事先知道、腦能當 tool schema——這是 json-argv 要的「無痛互轉」。
- 清單是**第二份真相**：說有、跑了沒有，會脫節；還是要靠 Linux 權限才保證「能不能」。
- **若採 A，C 就不用另發明**：一箱一函數，函數自己的 `_tooldef.json` 就是清單；要讓人找得到，信箱資料夾放一個指向函數的捷徑或 serve.json 寫著 `exec`，`aos-tools add <那個函數>` 直接登記給腦。所以 C 併進 A，不獨立成選項。
