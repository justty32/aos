# 要使用者裁的（10 題；寫給不看術語的人，每題附例子與建議）

**題 1｜`AOS_STACK` 沒設，到底誰可以給預設？**（打架 A）
- (a) 只有 aos-exec 給預設（它是入口、負責建 stack），其他程式一律報 `StackMissing`——程式現況，N-63 加一句「`AOS_STACK` 由 aos-exec 建、所以它例外」。(b) 全部報錯，`aos-exec` 沒 `--stack` 也不建。(c) 全部給預設。
- 例：`aos-fsm fsm.json` 直接跑（不經 aos-exec）——(a) 報錯叫你設；(c) 默默寫到 `./.stack/`。
- **建議 (a)**，加註。

**題 2｜`AOS_` 前綴底下的四種性質要不要寫成一張表？**（打架 B、C）
- (a) N-57 或 N-63 加一張表：執行環境（aos-exec 設）／hub（資料夾、沒設報錯）／人殼預設（`AOS_AGENT`，像 `EDITOR`）／旋鈕（原則上不用；真要用帶 `AOS_`、寫在 `.env`），每個活變數歸一格；R8 11-01 加註那句「原意改不改由使用者定」順便收掉。(b) 不寫，個案裁。
- 例：下次有人想加 `AOS_XXX`，照表先問「你是哪一種」。
- **建議 (a)**。

**題 3｜daemon 的 proc 型別怎麼認？**（打架 F，高）
- 現況：`{"exec": X}` 只跑一次；多寫任何 key 就變一直跑。(a) **物件＝loop 型、字串／陣列＝exec 型**，不看 key 多少；`{"exec": X}` 就是用預設的 loop。aos-daemon-ctl 不用再硬塞 `ctl`／`state`。(b) 加一個明講的 key（例 `"loop": true`）。(c) 不動、文件寫清楚。
- 例：`"bob": {"exec": "../agents/bob"}`——(a) 一直跑；現況 跑一次就下表。
- **建議 (a)**：少一條暗規則、不加 key（C-56）。

**題 4｜aos-daemon-ctl `add` 用 `XXX/loop.json` 在不在判 loop 型，要不要拿掉？**
- (a) 一律 loop 型（XXX 是資料夾程式，`aos-exec XXX` 就是它的一次；要窗就看題 5）。(b) 加旗標 `--once` 明講 exec 型。(c) 不動（規劃 aos-agent 不看檔，但底下還是叫 aos-daemon-ctl）。
- **建議 (a)**；題 3 選 (a) 的話這題自然解。

**題 5｜`ctl.json`／`state.json` 是旋鈕還是固定名？**
- 現況 aos-loop 是選填 key、沒預設名；daemon、aos-daemon-ctl、P-42、aos-say 全當固定。(a) **規範定死名字**：aos-loop 去掉 `ctl`／`state` 兩個 key，改 `"window": true`（或預設開），名字固定——少兩個旋鈕（KISS 減法）。(b) aos-loop 保留 key、但沒寫時預設就叫 `ctl.json`／`state.json`（跟 daemon 的 `procs_ctl` 預設名同一種做法）。(c) 不動。
- 例：loop.json 現在要寫 `"ctl":"ctl.json","state":"state.json"` 八個字才有窗；(a)／(b) 不寫就有。
- **建議 (b)**：最小改、daemon-ctl 不用補、P-42 不用動。daemon 的 `procs_ctl_mailbox` 同理給預設名（現在沒寫就不開，aos-daemon-ctl 卻寫死要它）。

**題 6｜daemon 寫進子項 stack 根的 `loop.json`／`exec.json`／`stderr.txt` 要不要搬？**（11-04 晚「地盤」原則）
- (a) 搬到 daemon 自己那邊：`procs/<名>/` 給子項、daemon 的檔放 `procs_meta/<名>/`（或 `procs/<名>.json`）。(b) 留在子項 stack 根、但加前綴（`.daemon_loop.json`？會撞 N-05 的「`.` 開頭＝暫存」）。(c) 不動、P-42／N-28 加一句「子項別用這三個名字」。
- 例：agent 自己想寫 `stderr.txt` 記自己的錯——現況會跟 daemon 寫的撞。
- **建議 (c) 先加註**，等真的撞到再搬（C-56 不為邊緣狀況加機制）；但要寫下來。

**題 7｜命令列統一形狀要不要升成規範？**（打架 G）
- (a) NORMS 06 加一條 N-：所有 aos 程式照 `parse_cli` 那套（旗標在前、`--`、長旗標連字號、無短旗標、`FlagUnknown`、錯時印 usage、不做 `--help`）；五支自製的改過來（aos-eca 隨刪、aos-mcp／grow／sandbox 小改）。(b) 只進 CONVENTION 當慣例。(c) 不動。
- 例：`aos-grow up X --to y` 旗標在後、`aos-exec --ws W X` 旗標在前，現在兩種都對。
- **建議 (a)**，順便把「aos 的命令列只有 aos-exec」那句改掉。

**題 8｜`_tooldef`／`_metainfo` 這兩個名字**
- R11 說 `_` 開頭＝入口、R10 說 JSON 帶 `.json`；它們是資料、lib 裡不帶副檔名。(a) 改 `tooldef.json`／`metainfo.json`。(b) 留 `_` 但一律帶 `.json`。(c) 不動、R11 加例外「`_` 開頭＝aos 認的固定檔，含入口」。
- **建議 (c)**：`_` 的好處（`ls` 排前面、不跟使用者的檔撞）對這兩個一樣成立，只是條文那句要放寬。

**題 9｜inst 單子 17 個 key vs aos-exec 認 10 個**
- (a) aos-exec 補認那 7 個（C lib 本來就支援）。(b) schema 刪成 10 個、C lib 那 7 個標「只給直接叫 lib 的人」。(c) 不動。
- 例：有人在單子寫 `"envs_clear": true` 想清環境——現在靜默沒效果。
- **建議先查**（這是 investigation）：那 7 個有沒有人用；沒人用選 (b)。

**題 10｜`state` 一詞二義：`state.json`（loop 的窗）與 `state.txt`（fsm 的狀態名）同在 stack 根**
- (a) fsm 的改名（例 `fsm_state.txt`、或 `current.txt`）。(b) 不動、N-39 加一句「loop 的 `state` 別設成 `state.txt`」。
- **建議 (b)**；`state.txt` 已在 N-39、P-07 定過，改名牽 69 檔那種規模不划算。

## 使用者裁定（11-04，選項原文或他的話，逐字）

1「只有 aos-exec 給 (Recommended)」　2「寫一張表 (Recommended)」　3「不動，文件寫清楚」　4「拿掉，不應該看特定檔案。add這塊，就是看最終指向的json的內部結構。」　5「留 key、沒寫時預設就是這兩個名 (Recommended)」　6 先問「這不是子項自己的定義中所寫的嗎？」（頂層解釋：stack 裡的 `loop.json`／`exec.json` 是 daemon 照自己名單生出來、包住子項入口的設定，不是子項定義資料夾那份；`stderr.txt` 是 daemon 接子項 stderr 的；三個都 daemon 寫）→「是否能在json中設置？但默認用這些名」　7「只進 CONVENTION 當慣例」　8「留 _、加 .json」　9「aos-exec 補認那 7 個」　10「fsm改名，嘗試用同義詞」

決定：1 aos-exec 以外一律 `StackMissing`、aos-tools 改；2 N-63 加 `AOS_` 四種性質表；3 daemon 型別判法不改、文件寫清楚；4 aos-daemon-ctl `add` 不看 `loop.json` 在不在，改看 XXX 入口最終指到的 JSON 的內部結構；5 aos-loop 留 `ctl`／`state` key、沒寫＝`ctl.json`／`state.json`（`procs_ctl_mailbox` 同理給預設名）；6 daemon 寫進子項 stack 的三個名字可在 daemon.json 設、沒設＝現名；7 命令列形狀進 CONVENTION 當慣例（不升規範）；8 `_tooldef.json`／`_metainfo.json`，`_` 留、副檔名加；9 aos-exec 補認那 7 個 key；10 fsm 的 `state.txt` 換同義詞（fable 挑，見 [07](07-實作步驟.md)）。實作步驟在 [07](07-實作步驟.md)、[08](08-實作步驟-等aos-agent後.md)。
