## 要你看的題

### 題 1：同一個 daemon 資料夾被兩個 daemon 用、或舊表讀不懂時，要不要擋

**白話**：daemon 起來時會讀上次留下的名單（`procs_state.json`），把還活著的子項接回來。現在它不檢查「上一個 daemon 是不是還活著」，也不說「舊名單讀不懂」。所以：
- 你不小心在兩個視窗各起一次同一個 daemon，第二個會把第一個的 agent 搶過去；第二個關掉時把它們全收掉，第一個以為它們做完了、從表上拿掉（#7）。
- daemon 被 kill -9 之後名單又剛好壞了，舊的 agent 沒人管、繼續跑，aos-agent 看不到也拔不掉；daemon.json 寫的 `llm` 會再起一個，**同一個 stack 跑兩個 kernel**（#8、#14）。

**選項**：
1. **（推薦）起來時擋＋說一聲**：舊名單頂層的 `pid`＋`started_at_ticks` 對得上一個活著的行程＝不起、報一行（例 `DaemonBusy 這個 stack 已經有 daemon 在跑（pid N）`）；舊名單在但讀不懂＝照現在當沒有、但 stderr 印一行「舊表讀不懂，沒接回任何子項」。後果：多一個錯誤代號；要改 C++（aos-daemon 的 `adopt` 一帶，十幾行）。資料都是現成的（aos-daemon-ctl 判「daemon 還活不活」用的就是這兩欄）。
2. **只說一聲不擋**：讀不懂印一行；兩個 daemon 照樣讓它起。後果：#7 照舊會發生。
3. **不管**：照 P-18／C-53「同一個 stack 只跑一個是呼叫方的事、入口默認正常」。後果：上面兩種情形照舊、而且沒有任何提示。

### 題 2：`aos-agent say` 要不要先確認對象是 agent

**白話**：`aos-agent ls` 會列出 daemon 表上全部的 proc（包括 llm kernel 這種不是 agent 的）。`say --target llm …` 現在照寄，在 kernel 的 stack 建一個沒人讀的 `queue/`，`state` 還會顯示「queue 1 封」，看起來像在排隊（#9）。`tools`、`llm` 子命令會先查定義的 `interfaces.json`，`say`／`listen`／`chat` 不查。

**選項**：
1. **（推薦）say／listen／chat 也先查宣告**：定義沒宣告 `aos-agent`＝`InterfaceMissing`、不寄。後果：每次 say 多讀一個小檔；表上沒有 `def` 欄的舊列（11-04 前掛的）也會被擋，要 rm 再 add。
2. **只提醒不擋**：照寄，stderr 一行「llm 沒宣告 aos-agent 介面，可能沒人讀 queue」。
3. **不管**：說錯對象是人的事。

### 題 3：add 被 daemon 拒絕時，要不要馬上說原因

**白話**：名字像 `a/b`、`.x`、`..` 這種 daemon 不收的，daemon 會把原因寫在自己窗上的 `mailbox_warning`，但 `aos-agent add` 只會傻等 30 秒，最後說「daemon 還沒把它放上表」，沒講為什麼（#10）。

**選項**：
1. **（推薦）等的時候順便看 `mailbox_warning`**：裡面提到這封信（aos-daemon-ctl 印的信件名）就馬上退、把 daemon 那句原樣轉出來。後果：aos-agent 多讀窗上一欄；代號要定（沿用 `WaitFailed`，或新的 `AddRejected`）。
2. **aos-agent 自己先驗名字**：照 daemon 的規則先擋。後果：同一套規則寫兩處，daemon 改規則時會對不上。
3. **不管**：30 秒後 `WaitFailed`，人自己看 `procs_state.json`。
