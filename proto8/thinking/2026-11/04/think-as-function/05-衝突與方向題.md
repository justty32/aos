# 要使用者看的（白話；推薦放第一）

只有兩種：新方向跟既有裁定／條文打架的（衝突），和原則推不出答案的（方向題）。其餘細節照原則定了、在 [02](02-設計-信與kernel.md)～[04](04-邊緣狀況.md)，可翻案。你一句「照建議」就夠。

## 衝突 1：你 11-04 晚先說「aos-llm 改定義」，後說「aos-llm 跟 aos-post 一樣是基礎工具」

- **哪條**：11-04 晚「aos-agent llm改正在跑著的，aos-llm改定義」（[aos-agent 06](../aos-agent/06-衝突與方向題.md#使用者原文11-04-晚逐字toolsllm)）→ 做成了 `bin/aos-llm <定義> show|set`（經每隻 agent 自己的 `llm/` 入口程式改 `.env`／`cli.json`）。今晚「aos llm, tool 定位跟 aos post 一樣，基礎工具」「aos-llm＝寄單／收回信那支」。同一個名字兩種意思。
- **(a) aos-llm＝寄單／收回信（推薦，已照此寫）**：`aos-llm send／recv／ask／regret`（[02/01 § 5](02-設計-信與kernel/01-endpoint函數-aos-llm-kernel形態.md)）。改定義裡的腦設定（現在只剩 `llm.json` 的 `endpoint`／`model` 兩個鍵）＝人直接 `aos-json set <定義>/llm.json#/endpoint sol`，跟 aos-tools 改定義一樣是人的事；`bin/aos-llm`（Python）、每隻的 `llm/` 入口程式、`aos-eca-llm` 全刪。後果：少三支程式、一個名字一個意思（C-54）；代價是改定義要記 aos-json 一行（跟改 `tools.json` 以外的任何設定一樣）。
- **(b) 兩個都要**：寄信那支叫 `aos-llm`，改定義那支留著改名（例 `aos-llm-cfg`）。後果：多一支只包 aos-json 一行的程式。
- **例子**：想讓 bob 的定義預設用 sol——(a) `aos-json set agents/bob/llm.json#/endpoint sol`；(b) `aos-llm-cfg agents/bob set endpoint=sol`。
- **11-04 晚隊長照推薦先實作，可翻案**（使用者在外、授權「出門時大小決策頂層先自己做、做錯可以改回」）。翻案要動的地方：從 git 歷史救回 `proto8/bin/aos-llm`（Python）改名 `aos-llm-cfg`、bin README 與 code map 06 加回一列。

## 衝突 2：kernel「寄信人不在就丟、不跑」（10-24 沙箱 S15 定）對上非同步「寄完就走」

- **哪條**：kernel 用 `sender.flock` 判寄信人還在不在，不在＝`sweep` 丟掉不跑（省一次腦）。非同步的 think 格寄完就退了，照這條每封都會被丟。
- **(a) 沒鎖檔＝不判、照跑（推薦，已照此寫）**：`aos-llm send` 不建 `sender.flock`，kernel 看不到檔就不判；`aos-llm ask`（同步）照舊建、照舊判。後果：agent 寄完被 `rm` 的那封會白跑一次（回信寄不進、記 `reply_error`，[04 #6](04-邊緣狀況.md)）；排隊中可以 `aos-llm regret` 撤。
- **(b) 非同步也要證明自己還在**：寄信人在信裡寫自己的 state 窗路徑，kernel 跑前讀窗的心跳。後果：kernel 要懂 loop 的窗、多一條規則（C-56）；agent `pause` 中心跳也停，會被誤判不在。
- **例子**：bob 寄了信、人馬上 `aos-agent rm bob`。(a) kernel 照跑、回信丟不進、served 記一行；(b) kernel 讀不到窗、丟掉不跑。
- **11-04 晚隊長照推薦先實作，可翻案**。翻案要動的地方：信裡多一個寄信人 state 窗路徑（`aos-llm send` 寫）、`impls/aos-llm-kernel` 的 `sweep` 改讀窗的心跳判存活、kernel README。

## 方向題 1：非同步等回信的期間，要不要順便收新信？

- **背景**：你 11-04 裁「思考中來信等答完回 idle 再收」（loop-fsm-agent 方向題 2）。那時 think 是卡住的、沒得選；現在 loop 照跑，wait 格**技術上可以**順便把 queue 收進 history。原則兩邊都講得通：收＝loop 不停的好處用滿；不收＝一題一答、history 不會在腦想到一半時多出一則 user。
- **(a) 不收（推薦，已照此寫）**：wait 只看回信；新信留在 queue，答完回 idle 再收。後果：對話順序乾淨；人連說兩句要等第一句答完才看到第二句被收。
- **(b) 收**：wait 每拍也跑 idle 的收信；收到就接進 history。後果：回信到時 history 最後一則可能是 user、不是 tool／assistant，下一輪 think 要重組；腦答的是舊的上下文。
- **例子**：你問「現在幾點」、三秒後又問「今天星期幾」。(a) 先答幾點、回 idle 收第二句、再答；(b) 第二句先進 history，幾點的回信接在它後面，看起來像答錯題。
- **11-04 晚隊長照推薦先實作，可翻案**。翻案要動的地方：`demo/agent-fsm/wait.py` 每拍沒回信時先跑一次 idle 的收信（或叫 `idle.py`），`brain.py` 下一輪照 history 重組；demo/docs/02-agent-fsm.md。

## 方向題 2：agent-fsm 範本預設就走 kernel（沒 kernel 跑不動），還是留一條不經 kernel 的直連？

- **背景**：你說「把請求丟到 llm kernel」。照這句，agent 問腦只有一條路：`$AOS_KERNEL`。原則上一條路最乾淨（C-56、C-54 一次記住），但 demo／試驗場從此一定要先起一個 kernel（多一個 proc）。
- **(a) 只走 kernel（推薦，已照此寫）**：`demo/agent-fsm` 的 think／wait 只會寄信收信；試驗場 daemon 多掛一個 `llm` proc（`demo/llm-kernel`），`env.sh` export `AOS_KERNEL`。假腦＝kernel 的一組 `fake` 代號。後果：沒 kernel＝`KernelMissing`、agent 停下；所有腦的用量都在一處記帳。
- **(b) 另留直連**：`lib/base/llm_http` 也登記成 agent 的工具，think 格可以 `aos-tools call llm_http` 直接問、不排隊。後果：兩條路、兩套設定放哪（直連的 url／key 又要放回 agent 這邊——就是你不喜歡的那塊）。
- **例子**：家機沒開 kernel 就 `aos-agent say --target ann "hi"`。(a) ann 的 wait 格退 1、stderr `aos-llm: KernelMissing`；(b) ann 直接問 LM Studio 答了。
- **11-04 晚隊長照推薦先實作，可翻案**。翻案要動的地方：`demo/agent-fsm` 的 `tools.json` 登記 `../../lib/base/llm_http`、think 格多一條直連分岔（`llm.json` 寫 url／model 時不寄信、`aos-tools call llm_http`），fsm.json 的 think／wait 分岔跟著改。
