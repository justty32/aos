# 邊緣狀況實測（11-04 夜）

使用者 11-04 夜（在打遊戲、沒空回答）：「你先多嘗試，看看各種邊緣狀況」。明確 bug 直接修，涉及取捨的寫成題。

## 修了的

- llm_http 端點回到一半斷線：回 `EndpointFailed … 回覆沒收完整`（`d2f20e6f`）。
- llm_fake 收到 `tools` 不是陣列：`ArgumentsBad`（`d2f20e6f`）。

其餘實測（端點 500／429／HTML／卡住／超大回覆、代號錯、kernel 被殺、regret 各階段、兩個 recv 搶同一封…）行為都同 [04](04-邊緣狀況.md)，不另處理。

## 留給你的題（白話；推薦放第一）

**題 1：`AOS_KERNEL` 打錯路徑時，寄信默默成功**——`aos-llm send` 不驗那是不是 kernel 信箱，打錯路徑 agent 會永遠停在 wait。

> **11-04 夜使用者：「很多都是自己要承擔的風險。」——不處理**（照現況、不改程式）。

**題 2：kernel 搶不到信箱的鎖時，整個 loop 停掉**——loop 被硬殺後馬上重起，新的會撞到舊的那一拍還沒跑完而自己停；兩個 kernel 指同一信箱，撞上的那個停掉。

> **11-04 夜使用者：「很多都是自己要承擔的風險。」——不處理**（照現況、不改程式）。

**題 3：kernel 的舊信**——每封信帶整段對話，留著會平方成長。

> **11-04 夜使用者：「很多都是自己要承擔的風險。舊信根本不用留，就是刪」——定案：舊信不留，處理完就刪**（回信寄失敗的也照刪、沒有 `done/`）。已落實 `6a2e0880`：kernel 寄完回信就整封刪掉；`ask` 被打斷時寄完回信當場撤回；`aos-llm ask` 判 `LetterMissing` 只看 `new/`、`cur/`。剩一條窄縫：`ask` 被打斷而 kernel 寄回信那一刻它還沒走完＝那封回信留在 `$AOS_KERNEL/reply/new/`（kernel 已知限制）。

> **11-05 使用者：`served.jsonl` 選「也刪」**（延續「舊信根本不用留，就是刪」）——kernel 不寫 `served.jsonl`；回信寄不出去改成 kernel 的 stderr 印一行 `aos-llm-kernel: 代號 原因（信 … 的回信寄不出去，信照刪）`、不退（照原則定的細節、可翻案）。
>
> **11-07 使用者裁定翻案**：ledger.jsonl「留，明寫是翻案（推薦）」——kernel 逐封帳 `ledger.jsonl` 保留；各層都記 usage、加總只加一層。（[kernel-nest](../../07/kernel-nest/README.md)）

**題 4：`aos-llm recv` 分不出「還沒回」和「永遠不會回」**——信被撤了、kernel 換了新信箱、`pending.txt` 被改，`recv` 都只會一直說「還沒到」，agent 永遠停在 wait。

> **11-04 夜使用者：「很多都是自己要承擔的風險。」——不處理**（照現況、不改程式）。
