## 留給你的題（白話；推薦放第一）

**題 1：`AOS_KERNEL` 打錯路徑時，寄信默默成功（#5）**
現在 `aos-llm send` 只看那個資料夾在不在，不在就建 `new/` 把信放進去，所以路徑打錯（指到別的資料夾）不會報錯，agent 永遠等。
- (a) **寄信前要求信箱已經有 `new/`（kernel 起過一次就會有），沒有就報 `KernelMissing`**（推薦）。後果：kernel 從沒起過時寄不出去，要先起 kernel（範本說明本來就是先起 kernel）。
- (b) 照現況。後果：可以先寄信、晚點才起 kernel；打錯路徑要等很久才發現。

> **11-04 夜使用者：「很多都是自己要承擔的風險。」——不處理**（照現況、不改程式）。

**題 2：kernel 搶不到信箱的鎖時，整個 loop 停掉（#6、#7）**
同一個信箱一次只准一個 kernel，這靠一把鎖。搶不到的那一拍現在當成「出錯」，loop 照 P-20 停下。結果：loop 被硬殺後馬上重起，新的會撞到舊的那一拍還沒跑完而自己停；兩個 kernel 指同一信箱，撞上的那個停掉（可能是原本在服務的）。
- (a) **搶不到鎖＝這一拍不做、印一行警告、loop 照跑**（推薦）。後果：鎖照樣保證一次只有一個在跑；重起不會卡；兩個 kernel 設錯也不會停，只靠那行警告發現。
- (b) 照現況。後果：設定錯（兩個 kernel 搶同一信箱）會被逼出來；硬殺後重起要等舊的那一拍跑完。

> **11-04 夜使用者：「很多都是自己要承擔的風險。」——不處理**（照現況、不改程式）。

**題 3：kernel 的 `done/` 是平方成長（#8、#14）**
每封信都帶「整段對話」，跑完整份留在 `done/`，非同步的信又永遠不收拾。實測 20 題（對話 127 KB）就 3.2 MB，1000 題會上 GB，kernel 每拍也會跟著變慢。
- (a) **回信寄成功後就把 `done/` 裡那封刪掉，只留 `served.jsonl` 一行紀錄**（推薦）。後果：事後查不到 kernel 這邊的請求原文（agent 自己的 history 還在）；回信寄失敗的（`reply_error`）照留，方便查。
- (b) 留 `done/` 但只刪請求內容（保留信封、回信）。後果：小很多但還是線性成長，要另外定誰清。
- (c) 照現況、人手刪。

> **11-04 夜使用者：「很多都是自己要承擔的風險。舊信根本不用留，就是刪」——定案：舊信不留，處理完就刪**（比 (a) 更徹底：回信寄失敗的也照刪、沒有 `done/`）。已落實 `6a2e0880`：kernel 寄完回信、寫完 served 那行就整封刪掉（`cur/<信>/`），舊 kernel 留下的 `done/` 下一次整個刪；`ask` 被打斷時寄完回信當場撤回；`aos-llm ask` 判 `LetterMissing` 改成只看 `new/`、`cur/`。手跑：寄 20 封非同步信、kernel 跑完後信箱只剩 `tmp/`、`new/`、`cur/`（都空），20 封 `recv` 全拿到、再收退 10；舊 `done/` 被刪；`ask` 正常拿到；`timeout 1.5 ask` 一封 3 秒的信＝回信寄出當場撤回（回信信箱 `new/` 0 封）；`regret` 排隊中撤得掉、跑完的回 `RegretFailed`（同前）；回信信箱被刪＝`reply_error: MailboxMissing`、信照刪。剩一條窄縫：`ask` 被打斷而 kernel 寄回信那一刻它還沒走完＝那封回信留在 `$AOS_KERNEL/reply/new/`（kernel 已知限制）。

> **11-05 使用者：`served.jsonl` 選「也刪」**（問的是「每封信一行代號／模型／用量的紀錄要不要也拿掉」，延續「舊信根本不用留，就是刪」）——定案：kernel 不再寫 `served.jsonl`，kernel 這邊不留任何一封的紀錄；額度照舊靠 `used.json` 的總數。原本記在那行的 `reply_error`（回信寄不出去）改成 kernel 的 stderr 印一行 `aos-llm-kernel: 代號 原因（信 … 的回信寄不出去，信照刪）`、不退（照原則定的細節、可翻案）。舊 kernel 留下的 `served.jsonl` 不讀不刪。手跑（fake 代號）：寄兩封非同步信（一封的回信信箱先刪掉）、再一封 `ask`，kernel 跑完兩封回信都拿到、刪掉的那封 stderr 印一行，`$AOS_STACK` 只剩 `queue.json`、`used.json`。
>
> **11-07 使用者裁定翻案**：ledger.jsonl「留，明寫是翻案（推薦）」——kernel 逐封帳 `ledger.jsonl` 保留；各層都記 usage、加總只加一層。（[kernel-nest](../../07/kernel-nest/README.md)）

**題 4：`aos-llm recv` 分不出「還沒回」和「永遠不會回」（#9）**
信被撤了、kernel 換了新信箱、`pending.txt` 被改，`recv` 都只會一直說「還沒到」，agent 永遠停在 wait。同步的 `ask` 已經會查（`LetterMissing`）。
- (a) **`recv` 也看一眼 `$AOS_KERNEL`：信不在 kernel 的 new／cur／done、回信也沒到＝`LetterMissing` 退 1**（agent 停在 wait、重跑＝重寄）（推薦）。後果：`recv` 要多讀 `AOS_KERNEL`；若題 3 選 (a)，要先查回信信箱再查 `done/`（回信已到就不會誤判）。
- (b) 照現況，人看 `stage.txt`＋kernel 的 `served.jsonl` 自己判斷。

> **11-04 夜使用者：「很多都是自己要承擔的風險。」——不處理**（照現況、不改程式）。
