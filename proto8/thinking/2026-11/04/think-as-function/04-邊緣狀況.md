# 邊緣狀況（挖出來的；每條寫代定或現成機制，可翻案）

| # | 狀況 | 誰看到、怎麼辦 |
|---|---|---|
| 1 | 端點連不上、HTTP 非 2xx、回覆不是 OpenAI 形狀 | endpoint 函數退 1（stderr 一行）→ kernel 回信 `error: EndpointFailed／ReplyBad`（msg＝它 stderr 第一行）→ `aos-llm recv` 退 1 → wait 退 1，fsm 停在 wait（P-20 停下等人、不自動重試）。人重跑＝wait 看到沒 pending、`request.json` 在→重寄。kernel 自己不壞、照跑下一封。 |
| 2 | kernel 的額度用完（`budget`） | 回信 `error: BudgetMissing`（或 kernel 設成等下一窗、信留著）；同上停在 wait。 |
| 3 | 端點跑太久 | kernel.json `timeout_ms` → 整群 TERM → 回信 `error: EndpointFailed 143`。呼叫端 wait 沒有自己的逾時（kernel 是權威；它要嘛回、要嘛收拾）；真要上限就在 `priority.deadline` 寫（輪到之前過期＝`DeadlineMissed`，現成）。 |
| 4 | kernel 不在（沒起、死了） | 信堆在 `new/`、wait 每拍退 10 一直等（跟今天閘門「kernel 不在＝一直等」同義）；人從 `stage.txt`＝wait、`pending.txt` 看得出來。kernel 起來就接著跑。kernel 死在半路：`cur/` 殘骸由 `recover` 回 `RunFailed`（現成）。 |
| 5 | 寄完 agent 被 `stop`／`pause` | 這就是非同步的好處：wait 格一下就退，ctl 每拍生效。重 `start` 同一 stack：`pending.txt` 在→接著 `recv`，回信早到了也還在信箱裡（信箱是 agent 的）。 |
| 6 | 寄完 agent 被 `rm`（stack 刪了） | kernel 照跑、回信寄不進（信箱沒了）→ `served.reply_error` 記一行、`done/` 留紀錄；**浪費一次腦**。要避免就先 `aos-llm regret <pending>`（還在 `new/` 才撤得掉；aos-agent `rm` 要不要順手撤＝實作時代定、建議不做：aos-agent 不懂 stack 裡有什麼）。 |
| 7 | 取消（人改主意） | 排隊中：`aos-llm regret 名`；跑了：撤不了，回信到了被誰收？`pending.txt` 刪掉就沒人認；留在 agent 自己的信箱 `new/`——是它自己的地盤、自己清（`aos-post take-all`＋`done`）。kernel 這邊 `regret_reply`（收拾 `done/` 時撤回沒人拿的回信）只對有 `sender.flock` 的信做，非同步的不做。 |
| 8 | 同時好幾封 | 一隻 fsm 一次一封（pending 只有一個）。好幾隻 agent 各寄各的，kernel `slots` 決定幾封並行、`priority` 決定先後——C-20「誰先用腦」就落在這裡。一隻想同時問幾個（fan-out）：自己管好幾個 pending、用自己的信箱＋`recv 名` 一封封收，aos 不另給機制。 |
| 9 | 共用回信信箱（`ask` 用 `$AOS_KERNEL/reply/`） | `recv` 照 `in_reply_to` 只拿自己的（現成 `find_reply`）；沒人拿的回信堆在那裡：寄信人有 `sender.flock` 時 kernel 收拾 `done/` 會撤回（現成）。非同步一律用自己 stack 的信箱，所以共用箱只有 `ask` 在用。 |
| 10 | 舊信、舊回信（stack 重用、上一代留下的） | `recv` 認名字，不是自己 pending 的不碰；`pending.txt` 寫的是這一代寄的。`think/request.json` 每次 think 覆寫。 |
| 11 | 串流 | 不做（[02/01 § 6](02-設計-信與kernel/01-endpoint函數-aos-llm-kernel形態.md)）。request `stream: true`＝`RequestBad`。要看即時字＝endpoint 函數自己寫小格的 `stream.txt`，介面不變。 |
| 12 | 成本 | kernel 的 `used.json`／`served.jsonl` 從回信 `usage` 記 token（取代 `AOS_KERNEL_REPORT`）；每封信的 `done/<信>/reply.json` 有 `usage`。agent 自己不記（它不知道價錢；要看去 kernel）。經 eca 的 CLI 不在這套裡。 |
| 13 | 金鑰 | 只在 kernel 的 `kernel.json`（`{"$env"}`／`{"$ref"}`，或直接寫——寫了就別把 kernel 定義 commit 進 repo）；不再跟信走、不進 agent 的環境。`aos-agent llm show` 看不到也不該看到。kernel 的 `request.json`（信資料夾裡）**含 endpoint 整個物件**→ 信箱要在 kernel 自己的 stack（現成 README 的已知限制照舊）；代定：kernel 跑完把 `request.json` 刪掉、`done/` 只留 `letter.json`＋`reply.json`。 |
| 14 | 請求太大（history 很長） | 信＝一個資料夾、`letter.json` 一份檔，沒有大小上限；端點回 4xx 就是 1 號狀況。對話太長本來就是另一題（SESSION-LOG「對話太長」）。 |
| 15 | 換模型、換端點 | 信寫代號 `endpoint`（kernel 的 `endpoints` 表，[02 § 3](02-設計-信與kernel.md)）；臨時換同端點的模型＝`request.model`；信寫不認的代號＝`EndpointUnknown`；信改不了 url／key。agent 平常用哪組＝它的 `llm.json` 的 `endpoint`（副本可換，`aos-agent llm set endpoint=sol`）。要**另一個額度**才另起一個 kernel。 |
| 16 | 沙箱裡 | 斷網 agent 只有 `rw` 的 `$AOS_KERNEL` 這條路（現成）；非同步回信信箱在 agent stack（`rw`），跨帳號時 kernel 要寫得進——照 WAIT_USER 既有的 `setup.sh --mailbox` 那題。 |
| 17 | `interval_ms` 太長 | 回信到了也要等下一拍才收：wait 的延遲＝最多一拍。要快就把 `interval_ms` 調小；kernel 自己的 loop 也一樣（兩邊各一拍）。想要「回信一到就醒」＝N-14 的 inotify 加速，以後。 |
| 18 | 同一台 kernel 給 eca 用？ | 不給：eca 的腦是 CLI、自己有對話狀態。eca 不在額度裡（使用者 11-01「大多」agent 經 kernel，不是全部）。 |
| 19 | `aos-llm ask` 被訊號打斷 | 撤信（`new/`→`tmp/`）、已跑的讓它跑完、回信由 kernel 之後撤回——今天閘門的行為原樣。 |
| 20 | 從舊信過渡 | kernel 讀 `body.request` 才算新信；信裡只有頂層 `inst`／`env`（舊閘門寄的）＝`LetterBad`、回 error——舊閘門同一個 commit 退場，不留兩種信（C-54 一次記住）。 |
