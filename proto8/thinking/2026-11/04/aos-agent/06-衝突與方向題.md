## 使用者回覆（11-04，逐字）

對「`.aos/agent.json` 寫進工作區、佔資料夾」：

- **舊指令**：aos-agent 測試全綠後直接刪 extras/human、extras/eca（單獨一個 commit）。

## 使用者回覆（11-04 稍晚，逐字）：say 的名字

> 啊，claude code讀cwd的.claude，這需要去看看，在daemon,eca的共同作用下會發生啥事。然後aos-say這塊，我覺得可以用aos-agent say --to bob "..."這樣。然後有需要的話就是讓人用source using-aos-agent.sh，然後我們就可以直接say --to bob "..."，有點類似命名空間。然後省略--to的話，就是找環境變數AOS_AGENT。

決定（11-04）：
- 省略對象旗標＝看環境變數 `AOS_AGENT`（裡面是名字）；兩個都沒有＝報錯（旗標名見下一段）。
- 給一支 `using-aos-agent.sh`，`source` 之後可以直接打 `say`（像命名空間）。
- 另開一題調查：Claude Code 會讀 cwd 的 `.claude`，daemon＋eca 一起跑時會發生什麼（調查與使用者還沒答的兩題在 [eca-claude-dir](../eca-claude-dir.md)）。

## 使用者回覆（11-04 晚，逐字）：介面細節

> --to，改成--target吧。這東西沒給的話就是吃AOS_AGENT。然後rm後面不用接--target，aos-agent rm xxx這樣就好。aos-agent add --name bob ../agents/bob這樣。然後我預期add這件事，他就是只吃指定介面，內部實現無所謂，你要是eca/fsm都可以。我就是不太喜歡要透過特定檔案去判斷是哪個這種。之後跟我說說這個介面長啥樣。加上一個status作為state的別名。然後幫我弄個aos-agent chat指令，ctrl-c退出。然後AOS_DAEMON_STACK實在太醜，還是直接簡化成AOS_DAEMON就好了，就跟剛剛那個AOS_AGENT一樣，原本我還想要用AOS_AGENT_TARGET的。

決定（11-04）：
- 指定對象的旗標是 **`--target 名字`**；沒給＝環境變數 **`AOS_AGENT`**。
- **`aos-agent rm 名字`**：rm 用位置參數，不用 `--target`。
- **`aos-agent add --name bob ../agents/bob`**。
- **add 只吃一個指定的介面**，裡面怎麼做（eca、fsm 或以後別的）無所謂；**不靠特定檔案（cli.json、loop.json 長相）判斷是哪一種**；介面契約在 [03](03-種類與契約.md)。
- `status` 是 `state` 的別名。
- 新增 **`aos-agent chat`**：互動對話，Ctrl-C 退出。
- 環境變數 **`AOS_DAEMON_STACK` 改名 `AOS_DAEMON`**（全 repo 一起改）。

## 使用者原文（11-04 晚，逐字）：介面與 stack

> 然後我這邊有些想法：就是說，一個proc，你在stack中放啥都可以，因為那是你的地盤，頂多你要考慮到繼承於你的傢伙，在設計他自己的stack的時候是否會容易命名衝突，導致你可能要把一些路徑放在.json中去設定(比如eca他固定吃cli.json...)。但是你對外的各種介面都必須在遵守原則的情況下保持靈活。基本就三類：命令行參數、吃/設的環境變數、stdin/out/err/exit、信箱內容格式。

> 去讀寫agent stack裡面的檔案，這沒問題。程式語言中定義class/struct的後，也會宣稱說自己繼承於/遵守於某些介面，比如golang interface之類。

決定（11-04 晚）：stack 是 proc 自己的地盤；對外介面四類（原文說三類、列了四樣，照四樣）；aos-agent 讀寫 agent stack 裡的檔沒問題；介面像 Go 的 interface——一組約定，agent **宣告自己遵守**，aos-agent 只認宣告、不猜（[03](03-種類與契約.md)）。

## 使用者原文（11-04 晚，逐字）：tools／llm

> 啊，還有，aos-agent tools/llm

頂層問他是哪個意思，他選「**aos-agent 加兩個子命令**」（例如 `aos-agent tools --target bob` 看／改它的工具箱、`aos-agent llm --target bob` 看／換它用的模型端點）。

對 [06/03](06-衝突與方向題/03-新題-tools-llm.md) 衝突 3（改定義 vs P-15）：

> 改副本。改定義那塊用aos-tools

對方向題 3（llm 怎麼接）：

> 一個入口小程式。並且要是aos資料夾函數。可以設計宣告介面。

再補：

> llm這塊也是，aos-agent llm改正在跑著的，aos-llm改定義

決定（11-04 晚）：aos-agent 多 `tools`、`llm` 兩個子命令，做成選配子介面；**改的是正在跑那一隻 stack 裡的副本**（`tools.json`、`llm.json`），改定義不經 aos-agent；「stack 有就用 stack 的」寫成子介面的承諾。`llm` 的做法同晚照 [think-as-function](../think-as-function/README.md) 改成設定檔宣告（[03/01](03-種類與契約/01-tools-llm-與兩個範本要改什麼.md)）；`screen` 是資料夾程式、自己宣告遵守介面 `aos-agent/screen`（[03/02](03-種類與契約/02-子介面規格.md)）。副本跟不跟定義：「不跟」（[06/03](06-衝突與方向題/03-新題-tools-llm.md#方向題-4副本要不要跟著定義變)）。
