## 使用者回覆（11-04，逐字）

衝突 1（`.aos/agent.json` 寫進工作區）：

> 算了，還是不做擴充了。找agent這塊我再想想，因為給名字...有時候就是想不起來，並且一個常見的場景是一個ws內起一個agent，然後我們就是一直跟他對話，這個時候我能預想到的簡單方式就是cd過去，然後aos-say "..."，就這樣。先不做擴充吧。不過工作區這塊，你知道的，claude code會吃其cwd的.claude，後續在這個資料夾工作的另外的claude code也會吃這個。好吧沒事，總之先不做這個擴充

方向題 1（誰寫 `.aos/agent.json`）：隨衝突 1 不做，不用答。方向題 2（say 的名字怎麼給）：

> 我再想想

方向題 3（舊指令退場）：選「測試全綠就直接刪」。

決定（11-04）：
- **`.aos/agent.json` 擴充先不做**；`occupy`／`release` 子命令拿掉。工作區不放 aos-agent 的東西（C-65、P-42 照舊）。
- **找 agent 怎麼給名字：使用者還在想**（常見場景＝一個工作區起一隻 agent、cd 過去直接 `aos-say "…"` 一直對話；名字有時想不起來）。實作前要再問。
- **舊指令**：aos-agent 測試全綠後直接刪 extras/human、extras/eca（單獨一個 commit，好 revert）。

## 使用者回覆（11-04 稍晚，逐字）：say 的名字

> 啊，claude code讀cwd的.claude，這需要去看看，在daemon,eca的共同作用下會發生啥事。然後aos-say這塊，我覺得可以用aos-agent say --to bob "..."這樣。然後有需要的話就是讓人用source using-aos-agent.sh，然後我們就可以直接say --to bob "..."，有點類似命名空間。然後省略--to的話，就是找環境變數AOS_AGENT。

決定（11-04）：
- 方向題 2 定案：**`aos-agent say --to 名字 "…"`**；省略 `--to`＝看環境變數 `AOS_AGENT`（裡面是名字）；兩個都沒有＝報錯。其他對單隻 agent 的子命令比照（實作時代定，回報時列）。
- 另給一支 `using-aos-agent.sh`，`source` 之後可以直接打 `say --to bob "…"`（像命名空間）；要不要順便設 `AOS_AGENT` 等細節實作時代定。
- 另開一題調查：Claude Code 會讀 cwd 的 `.claude`，daemon＋eca 一起跑時會發生什麼。

## 使用者回覆（11-04 晚，逐字）：介面細節

> --to，改成--target吧。這東西沒給的話就是吃AOS_AGENT。然後rm後面不用接--target，aos-agent rm xxx這樣就好。aos-agent add --name bob ../agents/bob這樣。然後我預期add這件事，他就是只吃指定介面，內部實現無所謂，你要是eca/fsm都可以。我就是不太喜歡要透過特定檔案去判斷是哪個這種。之後跟我說說這個介面長啥樣。加上一個status作為state的別名。然後幫我弄個aos-agent chat指令，ctrl-c退出。然後AOS_DAEMON_STACK實在太醜，還是直接簡化成AOS_DAEMON就好了，就跟剛剛那個AOS_AGENT一樣，原本我還想要用AOS_AGENT_TARGET的。

決定（11-04）：
- 指定對象的旗標是 **`--target 名字`**（取代 `--to`）；沒給＝環境變數 **`AOS_AGENT`**。
- **`aos-agent rm 名字`**：rm 用位置參數，不用 `--target`。
- **`aos-agent add --name bob ../agents/bob`**。
- **add 只吃一個指定的介面**，裡面怎麼做（eca、fsm 或以後別的）無所謂；**不要靠特定檔案（cli.json、loop.json 長相）去判斷是哪一種**——「種類自動認」那套（03 檔）作廢，改成定一份 agent 要提供的介面契約（待 fable 重新規劃、規劃完跟使用者說介面長怎樣）。
- `status` 是 `state` 的別名（原規劃已有，照舊）。
- 新增 **`aos-agent chat`**：互動對話，Ctrl-C 退出。
- 環境變數 **`AOS_DAEMON_STACK` 改名 `AOS_DAEMON`**（全 repo 一起改）。

## 使用者原文（11-04 晚，逐字）：介面與 stack

> 然後我這邊有些想法：就是說，一個proc，你在stack中放啥都可以，因為那是你的地盤，頂多你要考慮到繼承於你的傢伙，在設計他自己的stack的時候是否會容易命名衝突，導致你可能要把一些路徑放在.json中去設定(比如eca他固定吃cli.json...)。但是你對外的各種介面都必須在遵守原則的情況下保持靈活。基本就三類：命令行參數、吃/設的環境變數、stdin/out/err/exit、信箱內容格式。

> 去讀寫agent stack裡面的檔案，這沒問題。程式語言中定義class/struct的後，也會宣稱說自己繼承於/遵守於某些介面，比如golang interface之類。

決定（11-04 晚）：stack 是 proc 自己的地盤；對外介面四類（原文說三類、列了四樣，照四樣）；aos-agent 讀寫 agent stack 裡的檔沒問題；介面像 Go 的 interface——一組約定，agent **宣告自己遵守**，aos-agent 只認宣告、不猜。本規劃 [03](03-種類與契約.md) 照這個定。
