> 11-04 晚改名 `AOS_DAEMON`：本檔寫的 `AOS_DAEMON_STACK` 是當時的名字（[aos-agent 步 0](../aos-agent/05-實作步驟/01-步0範圍與測試清單.md)）。

本檔逐字是入口檔「結論」底下的各狀況（超過 8 KB 拆出）；每條：會發生什麼、證據（E1～E3 是 11-04 的 WSL 實驗，文件＝官方 Claude Code 文件）、嚴重度。

## 各狀況

1. **畫面開在沒信任過的工作區＋有人 say＝claude 退出、信丟、這隻從 daemon 表掉下來**（嚴重度：高）。E3：`aos-eca open -d ec` 畫面停在「信任這個資料夾嗎」（游標在 No, exit），`cli_session.start` 只看畫面穩了就放行；接著 `aos-say` 的字被貼進提問、Enter 選到 No → claude 退出 → `aos-eca-turn: CliFailed 畫面在講完之前關掉了`。信在 Enter 時已收（history 只有 user 那則），子 loop 錯退後 `aos-eca ls` 看不到它，`aos-eca rm ec` 回 `InstanceMissing`，stack 留在原地。非互動 -p 沒這問題（不問信任）。信任記在 `~/.claude.json` 的 `projects[<路徑>].hasTrustDialogAccepted`；git repo 以 repo 根為準，非 git 時信任上層會涵蓋下層（文件 permissions 頁；本機 `~/repo/simple_tools` 已信任，所以裡面的 aos clone 不會問）。
2. **工作區自己的 hooks、CLAUDE.md、agents／commands／skills 都會進 eca**（嚴重度：中）。工作區＝aos 這個 repo 時：CLAUDE.md「去讀 AGENTS.md」會讓 eca 照 wf 規矩做事（掃 inbox、讀 SESSION-LOG…，多花錢、答非所問）；`/wf-tick`、`/wf-lint` 會出現在它的指令清單；SessionStart hook 的 matcher 是 `compact`，平常不跑，但 eca 一直 `--resume` 同一段對話、長了會自動 compact，那時 `compact_reload.sh` 會把 user.md 與 HANDOFF 塞進 eca 的對話。（aos repo 本身沒實跑：自動權限判斷擋下在 WSL clone 裡跑 claude，這條是照 E1 的機制推的。）
3. **eca 自己不在工作區建檔**（嚴重度：低）。E1、E2 的 -p 兩次、畫面答信任＋問一題，事後 `find -newer` 都是空的；session、memory、信任都寫在 `~` 底下。會寫進工作區 `.claude/` 的只有三條路，寫了之後同 repo 的人與其他 eca 都會讀到：人在畫面上選「Yes, and don't ask again」→ `.claude/settings.local.json`（文件 settings 頁）、人打 `/init` → `CLAUDE.md`、cli.json 給了 Write／Bash 讓它自己寫。另外**試驗場的 daemon 在工作區起，stack 就在 `ws/.stack/`**：E3 的 `git status` 多一行 `?? .stack/`，裡面每隻 eca 的 history、mcp.json 都在 claude 用 Glob／Read 讀得到的地方（同工作區的兩隻能讀到彼此的 history）。
4. **同一工作區兩隻 eca（或一隻＋人）：session 不撞**（嚴重度：低）。都存在 `~/.claude/projects/<工作區路徑把非英數換成 ->/<id>.jsonl`，同一個資料夾；E3 兩隻各自 uuid、各自 `--resume`，各答各的。同一個 `--session-id` 再用會報 `Session ID … is already in use`（eca 只有第一次給新 uuid，不會撞）。`--resume <id>` 換了 cwd 也找得到、寫回原檔（E1c），所以同一個 stack 換了 `--ws` 前文還在、但 cwd 變了。人自己的 `claude --continue` 不挑 -p 的對話（文件 sessions 頁）；畫面開的那段會不會出現在人的 `/resume` 清單沒驗。**auto memory**（`~/.claude/projects/<repo>/memory/`，以 git repo 為單位、預設開）是同 repo 的人與所有 eca 共用的：E1 的 -p 一跑就建了空的 `memory/`；現在 eca 只有 Read／Glob／Grep 寫不進去，給了 Write 就會互相影響。
5. **環境變數**（嚴重度：中）。daemon 的環境一路傳到 claude，再加 `AOS_WS`、`AOS_STACK`、`AOS_DAEMON_STACK`、`AOS_CD`、`AOS_CF`、`AOS_CO`（E3 hook 看到的）。`CLAUDECODE`、`CLAUDE_CODE_SESSION_ID`、`CLAUDE_CODE_ENTRYPOINT` 就算 daemon 是從 Claude Code 裡起的也會被 claude 自己蓋掉（E3 故意帶假值，hook 看到的都是 eca 那隻自己的），`CLAUDECODE=1` 也不會讓 -p 拒跑（E1d）。要留意的是 `AOS_STACK`＝**這隻 eca 自己的 stack**：cli.json 一給 Bash，claude 在裡面叫 aos 指令時沒給 `--stack` 就會用到它自己的 stack（例如寄信寄給自己）。畫面那條的 tmux 是 `aos-eca open` 那個人的 shell 起的，環境跟 daemon 起的 -p 不同（看程式推的，沒逐一比）。
6. **codex**（簡述，沒實跑成）：codex 讀 `~/.codex/config.toml`、`~/.codex/AGENTS.md`，加上從 git 根到 cwd 每層的 `AGENTS.md`；對話放在 `~/.codex/sessions/年/月/日/`、跟 cwd 無關；eca 帶 `--skip-git-repo-check`。實驗卡在 WSL 的 `~/.codex/config.toml` 預設模型 `gpt-6.1-sol`，ChatGPT 帳號回 400 `model_not_found`——WSL 上掛 codex 的 eca 現在一定 `CliFailed`，cli.json 要自己帶 `-m`。
