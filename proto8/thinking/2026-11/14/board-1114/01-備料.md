## 〇、使用者要什麼（原話一字不改，出自任務書）

1. 「我有自己的公告欄，可以在上面宣告我目前的狀態，agent想要的話可以自己主動來讀，比如我去睡覺的時候，agent寄信給我發現很久沒回，他就會去看」
2. 「比較有自覺的agent也會自己去看。然後這個公告欄，agent自己也可以有。」
3. 「規劃公告欄的時候，也可以順帶去規劃更進一步的信件分級，比如急件，平信,...之類」
4. 「當然，不要修改到aos-post這個基礎程式，而是另外做，但是格式相容，並且給agent的工具也順便準備」
5. 「這條線的優先級跟llm kernel第二層一致」（不趕）
6. 「啊還有，廣播和頻道功能。agent可以選擇是否加入某個頻道，並將信寄到那個頻道，有加入那個頻道的agent就能看到。這個頻道就是一個簡單proc，或許可以透過我們快弄好的權限系統做權限管理？這個頻道prco可以先做最基礎的，後續再來做可以指定管理員agent或proc之類的」
7. 「對了ok-view那邊，或許我也可以看到agent的公告欄？然後公告欄/信件種類這些，希望能夠做成一套schema或協議，這樣就不止agent能用，普通proc也好處理」

頂層據此定的硬框（任務書）：
- **不改** `proto8/impls/aos-post`（C++）與 `proto8/cmd/aos-mailbox`；疊在上面另做。
- **格式相容**：新信給舊程式（aos-mailbox、mailbox_read、xiaosi、gate 自動處理）讀不壞；舊信給新程式讀不壞；計劃要寫怎麼驗。
- **一套協議**：有版本號、機讀定義（如 JSON Schema）、規格文件；普通 proc 用 shell／Python／C++ 幾行就能讀寫；CLI 與 MCP 都只是實作之一。要不要進 NORMS、怎麼編號，計劃提出。
- 工具兩種：MCP（寄分級信、讀寫自己或別人的布告欄、頻道的加入／退出／列／寄／讀）＋一行 CLI（給 shell 與便宜模型）。工具放哪、怎麼掛進 tools.json，跟 ok-onboard 的「配給包」對口。
- 頻道第一版最基礎：建、加入、退出、寄、成員收到；留管理員、誰能加入、誰能發言的接口。權限寫明 aos 層做得到的（kernel_gate、成員表）與要等 ok-sec Linux uid 層的。
- 只規劃不施工。ok-view 全景 v2.0 已預留：員工卡最上方顯示該 agent 布告欄、部門卡摘要（幾隻請勿打擾、幾隻在等人）、在等使用者的進左欄待辦——**schema 要早定、早交 ok-view**。

## 一、現有的「布告欄」類東西

- **使用者布告欄**（aos-view 的功能，不是 aos 本體）：`~/.aos/view/board/user.json`（最新一筆）＋`user.jsonl`（歷次）；內容 `{at, text, back, by:"user"}`，text ≤1000 字、back（預計回來）是自由文字 ≤100 字；空 text＝清除；**沒有到期判斷**。agent 讀：`aos-view board`（`--all` 連各隊最新留話、`--json`）。網頁 127.0.0.1:8767 上方「貼上布告／清空（我回來了）」。〔aos-view:1886、API.md:83、ui/v1/app.js:684〕
- **隊長留話**（aos-view note）：`aos-view note [--team T] [--on NAME] STATUS TEXT` → `~/.aos/view/teams/<team>/notes.jsonl`，每筆 `{at,status,text,on}`，status ∈ start/progress/done/blocked/decision/handoff/ask，text ≤2000；**一隊一串，不是每隻一張**；沒給 --team 時取 `$AOS_STACK` 名字核對 daemon 表。最新一筆一直顯示、無到期；非 done 超過 60 分鐘且無待答信 → 隊伍黃燈。〔aos-view:1961、:538、:665、:960〕
- **ok-view 計劃 0.7**：「每隊的布告欄就是隊長留話，不另做每個 agent 一張」——使用者這次要更進一步。另有「助手觀察」（模型看成員 history 寫 ≤120 字、標模型來源）與「員工 bot」Now／Did／Said（點開才讀、不落地）；`/api/agent` 已給現在狀態、信箱、最近 30 則 history 摘要。〔view-1114/03-計劃.md:292、:155、:217〕
- **使用者專區**（`~/.aos/user`，aos 本體）：每帳號每機一份 stack，mailbox 是普通 aos 信箱；收 kind ∈ decide/verify/trial/chore/fyi；已有粗粒度使用者模式 door 的 normal/away 與 `quiet_hours`：出門或安靜時段只通知急件、其餘延後不丟。這跟使用者布告欄的自由文字是兩份資料。〔user_zone.json、user-zone-plan/02-fable設計.md:95、08-段2施工.md:26〕

## 三、信件現況

- **兩層**：aos-post 管「信封」，aos-mailbox 管「agent 信件 body」。
  - 信封 `letter.json`（每封一個資料夾，Maildir：tmp→new 原子 rename，認領 new→cur）：必有 `sender`（寄件 stack 路徑）、`sent_at`、`body`（任何 JSON）；選填 `sent_at_cycles`、`reply_to`、`in_reply_to`。**讀取不拒絕未知信封欄位**，整份保留；**沒有版本欄**；body 不在這層驗。〔aos-post take.cpp:67、:104；send.cpp:175〕
  - body（aos-mailbox send 寫）：from、to、status、title、what、outputs、not_done、decide（後三預設 "none"）；status 白名單六種 REQUEST/DONE/BLOCKED/NEEDS-USER/FAILED/PROGRESS 只在**寄件端**驗；**沒有任意額外欄位的寄送介面**。〔aos_mailbox/__init__.py:14、:337、:345〕
- **未知欄位的命運**（相容性關鍵）：
  - `aos-mailbox read`／MCP `mailbox_read`：攤平印出時用 `setdefault` **加入未知 body 欄位**（不覆蓋既有）；未知信封欄位不印。〔__init__.py:222〕
  - `peek`／MCP `mailbox_peek`：只印 letter/from/status/title（JSON 多 to、sent_at），**不印未知欄位**。〔__init__.py:204〕
  - kernel 框架站轉寄：只把 `letter["body"]` 重新 post → **未知 body 欄位會傳下去，未知信封欄位會掉**。〔lib/aos/kernel/letters.py:263〕
  - JSONL 留底（keep=檔名）排除 sender、reply_to、絕對路徑 to。〔__init__.py:254〕
- **排序**：信名「20 位 UTC 奈秒.pid.started_at_ticks」；`--ordered` 前加 12 位序號（鎖 order.lock）。讀者先所有有序信、再無序信，各組字典序，不看 sent_at、不看 status。**mailbox 沒有任何急件插隊**。〔aos-util proc.cpp:126、aos-post mailbox.cpp:127〕
- **通知與喚醒**：`mail_notify` hook 每分鐘 peek，把未通知的信合成一則 `[aos] new_mail: N new letter(s) from X` 有序寄進 queue（只有封數與寄件人，看不到標題）。**信件不會喚醒 sleeping/stopped 的 proc**；sleeping 要 wake 或 daemon 重開；睡眠中 on_clock 不跑。〔mail_notify/_entry:95、mailbox.json#check、clock.json#rules〕已開畫面的 Claude eca 可經 socket 在當輪收到 queue 新訊息（midturn）。〔aos-eca midturn.py:1〕
- **已有的「優先」概念（在別處）**：
  - llm kernel 的 `body.priority`：low/normal/high、正負數、或 `{level, deadline}`；另有 aging、期限。〔aos-llm-kernel letter.cpp:156、queue.cpp:67〕
  - 使用者專區 schema 有 `urgent`、`deadline`、`risk`、`default_if_silent`、`dedupe_key`。〔~/.aos/user/schema/letter.json:6〕
  - xiaosi：system.txt 定「URGENT -> forward to repo-aos at once」（NEEDS-USER、問題／決策、擋線、活樹操作、push/delete、可能傷別線、完成／交棒；不確定就當急），其餘 ROUTINE 寫 digest、每 20 分鐘一封。wf 規定「xiaosi 只看 status 與標題分輕重」。〔xiaosi/system.txt:6、:9；07:33〕
  - quiet（wf/tools）：安靜期只攔 new_mail／kernel_hold **通知**，不動信；`urgent_senders` 以寄件人名字子字串放行；結束後補一則 quiet_over。autoreply_tick：安靜期新信回 PROGRESS「已收到，稍後處理」，跳過自己、urgent/no_reply 寄件人、`[auto] ` 標題，每封最多一次。〔quiet_hook.py:11、autoreply_tick.py:1〕
  - 「aos通知中心」只是 Claude socket 訊息的預設署名（原碼稱假的目標），不是服務。aos-user tick 有 notify-send 桌面通知（施工紀錄，未核對現碼）。〔cli_a2a.py:24〕
- **廣播**：CLI 與 MCP send 都只接受單一收件者；沒有 to-all helper；xiaosi 群發是一封封寄（徵稿群發九隊）。〔__init__.py:310、xiaosi/digest-sent.md:36〕

## 四、schema 與協議的現況

- **沒有通用信件 JSON Schema**（任務書說的 `schema/letter.json` 其實是使用者專區的 `~/.aos/user/schema/letter.json`，JSON Schema 2020-12、`$id:"user-zone/1/letter"`、`zone.const:"user-zone/1"`）。agent 信件 body 只有程式內檢查。〔sol-1b A〕
- 現有版本標記都是各自的字串：`user-zone/1`、view 信 `body.zone:"view/1"`、`format:"view-tree/0"`、`contract:"wf-table/1"`、`kind:"decide-page/1"`。〔aos-view:789、:312；decide_page/model.py:44〕NORMS 附錄4：「正式版當天起」全體持久檔加 `format` 版本標記、不符拒讀、不做舊格式相容。〔NORMS/附錄4-持久檔.md:12〕
- NORMS：正文 `N-xx` 編號按主題分檔、不重編、作廢留號；只收使用者已定規範（未定放「08-待定」）。信箱／信封在第 05 章「窗」**N-16**（Maildir 佈局、letter.json、rename 認領、有序投遞，明載「aos-post 是 IPC 基底、body 由接收者定」）；**N-66**「非同步呼叫」（一箱一函數、body＝stdin JSON，明載 aos-post 不加協議版本、不驗 body）。附錄4 盤點持久檔（path/lifetime/writer/reader/image/on_bad），不是逐欄 schema。命名.md：純文字 `.txt`、時間點 `_at`。〔NORMS 主題.md:15、05-N-16.md:3、08-N-66.md:3、命名.md:5〕

## 五、會碰到的骨架

- **stack**：每 proc 一夾；`tools/<名>/` 是工具自己的小格（工具看到的 `AOS_STACK` 是 `<agent stack>/tools/<名>/`，不是 agent 根）；`self_*` 用 `ctl who` 找自己。hook 事件的 `stack` 欄是 agent 根。〔aos-tools:1180、ctl/who.py:29、hook_run.py:141〕
- **hook 事件**九種：before_queue、after_queue、before_tool、after_tool、brain_failed、tool_added、after_start、after_stop(code,signal)、on_clock；**沒有 sleep／wake／turn_end／idle 事件**。睡＝daemon SIGTERM（經 after_stop），醒＝重起（after_start）。eca 的 Claude 畫面 hook：UserPromptSubmit 寫 `busy.txt`、Stop 刪掉並追加 turns.jsonl。〔hooks.py:53、cli_hook.py:260、:291、aos-daemon docs/03:62〕
- **工具**：pack＝`proto8/lib/packs/*.json`，形狀 `{"tools":{"名":{"path":{"$env":"AOS_HOME","$path":"/lib/…"}}}}`；定義的 tools.json 用 `$override` 陣列疊包，null 關單支；mailbox 包只有 peek/read/send。fsm 範本預載 15 包；eca 預載 gadgets/events/self/def/mailbox/json/jsonx/index；CLI 子 agent 用 tools_sub（不載 self/mailbox）。**沒有「新工具自動給所有 agent」**。〔packs/README.md:57、templates/*/tools.json〕
- **ok-onboard** 在規劃角色×模型等級的「配給包」（蒐集員、施工員、審稿員、小助手、隊長），配 prompt/tools/hooks/權限。〔wf/temp/ok-onboard/任務書.md:71〕
- **非 LLM proc**：daemon 可掛 `_entry` 程式或 loop 設定；最小例 `proto8/kernel/procs-kernel`：`_entry=["aos-loop","loop.json"]`、每 300ms 跑一輪，用 `AOS_STACK/requests` 信箱、`aos-post take-all/see/done` 收信，不用 queue/history。〔procs-kernel/_entry:1、lib/aos/kernel/round.py:49〕
- **讀別隻**：`ctl where NAME` 拿 stack 路徑，之後同一 Linux 帳號都讀得到（規則禁止改寫別隻 stack）；設了 AOS_KERNEL 時 ls/who/where 先寄 `procs_state_path` 問 kernel。`ctl ls` 只列一張表、不遞迴；上層由 `daemon` 欄連；subagent 所有權在各自帳本 `tools/subagent/subagents.json`。〔ctl/where.py:38、state_path.py:58、ctl/ls.py:108〕
- **權限現況**：kernel_gate 只管「起／改 proc」的請求（hold/pass/refuse，pass 不能蓋過規則）；`allowed` 是可新增的 proc 名單；**aos 不驗寄件人**（`sender` 是寄件端自己寫的），任何能寫信箱夾的行程都能投信；硬性阻擋只能靠 Linux 目錄權限。ok-sec 規劃 uid 分配、跨 uid 寄信 helper（未定每 agent 還是每子樹一個 uid）；ok-limits 已有 aos-run uid 951、共享目錄 2770。〔kernel.json#gate、procs_rules.py:172、kernel-limits-1114.md:247、ok-sec 任務書:28〕

## 六、要 fable 設計的題目（我列的，不含答案）

1. **一套協議**怎麼切：布告欄、信件分級（種類）、頻道是一份協議的三節還是三份；版本號放哪（信封？body？檔內 `format`？）；機讀定義的形狀；進不進 NORMS、編號建議（N-16/N-66 旁）。
2. **布告欄**：存哪（agent stack 的固定檔？那就是 aos 本體功能）；欄位（在忙什麼、在等誰、預計多久／到期、請勿打擾、睡了）；寫（一行 CLI、MCP；不花模型）；讀（單隻、整隊、全部、嵌套匯整——注意 ctl ls 不遞迴、kernel 鏈不是父子樹）；過期（附預計時間，過期標灰）；自動部分（例：after_stop 寫「睡了」、after_start 清掉；eca busy.txt 已有）；跟 state.json、隊長留話、使用者布告欄、使用者專區 door/quiet_hours、員工 bot 的關係（合併、引用、並存？使用者布告欄要不要搬進同一協議）。
3. **信件分級**：幾級、各級意思、誰能用、防濫用（人人寄急件就沒意義）；跟 status 是兩個維度還是合併；放在 body 哪個欄位才能「舊程式不認得也不壞」（見三：read 會印未知 body 欄位、peek 不印、kernel 轉寄留 body 丟信封）；收件端怎麼處理——插隊（不改 aos-post 的排序前提下：`--ordered`？另一個信箱？只改通知？）、叫醒睡著的 eca（信件本身叫不醒）、通知使用者、布告欄「請勿打擾」時只收急件；跟 quiet／autoreply、xiaosi 彙整、使用者專區 urgent 的關係；mail_notify 那行要不要帶級別；全景頁怎麼顯示。
4. **頻道與廣播**：頻道 proc 的最小形（照 procs-kernel 那種 loop 站？）；成員表存哪；成員收法（每人一份複本 vs 去頻道讀）；已讀未讀；歷史留多久；廣播＝全員頻道？；頻道急件會不會叫醒全員；一隊一頻道、嵌套隊伍；第一版 vs 留接口（管理員、誰能加入、誰能發言）；權限哪些 aos 層做得到（成員表、kernel_gate）、哪些等 ok-sec uid 層（因為 aos 不驗寄件人）。
5. **工具**：MCP 工具清單與 CLI 指令清單（一套協議的兩種實作）；放哪個 pack、預設給誰（fsm、eca、tools_sub）、跟 ok-onboard 配給包怎麼對。
6. **相容性驗證法**：新信給舊程式、舊信給新程式，各要驗哪些程式（aos-mailbox read/peek、MCP mailbox_read/peek、xiaosi、gate、kernel 轉寄、autoreply/quiet）。
7. **哪些動到 aos 本體**（要進 ok-release 公開版文件），哪些只是 wf/tools 或 aos-view。
