# board-1114 03 計劃：`comm/1`（布告欄＋信件分級＋頻道）

← [board-1114](../board-1114.md)｜上一份 [02-fable稿](02-fable稿.md)｜2026-11-14｜ok-board（opus）

## 〇、結論

- **照 02 稿走**：一套協議 `comm/1` 三節——布告欄 `<stack>/board.json`（`format: board/1`）、信件分級 `body.comm.level`（urgent／normal／low，缺省 normal）、頻道＝不用模型的 loop proc。aos-post、aos-mailbox 一字不改。
- **我改了 6 處**（第一節），最重要的是 **C1：讀信工具不能 `take-all`**，否則沒讀的信全卡進 `cur/`，`peek`、`mail_notify`、autoreply、全景頁的信件數都會少算。改成直接看 `new/`、只認領挑中的那一封。
- **核對了 fable 要我查的 5 件事實**（第二節），兩件跟稿子預期不同：`ctl wake` 走寄件人自己的 kernel，叫醒別隊的 agent 多半會被拒；`proto8/schema/` 不存在、要新開。
- 施工 4 批（第三節），照硬規則第 5 條「新碼先放新檔、接到既有路徑放最後一個 commit」。只規劃，施工要使用者另外點頭。
- 待使用者裁仍是 02 稿的 U1～U6（預設都採甲），加我的 U7（叫醒走誰）。

## 一、我對 02 稿的改動

| # | 改什麼 | 為什麼 |
|---|---|---|
| C1 | `comm_read`／`aos-comm read` **不用 `aos-post take-all`**。改為：直接列 `<box>/new/*/letter.json`（N-16 的 Maildir 佈局本身就是協議，讀 new/ 不需要 aos-post）→ 照「級別、再信名」挑一封 → `rename new/<名> → cur/<名>`（跟 aos-post 認領同一個動作，rename 失敗＝別人拿走了，換下一封）→ `aos-post see`＋`aos-post done`。沒挑中的留在 `new/` | 查過 aos-post：`take` 不能指定信名（main.cpp:7），`take-all` 會把整箱搬進 `cur/`；而 `aos-mailbox peek`、`mail_notify`（`_entry:7`「列還在 new/ 的信」）、wf/tools autoreply 都只看 `new/`。照 02 稿做，沒讀的急件會從通知裡消失 |
| C2 | 頻道 proc 的定義放 **`proto8/templates/channel/`**，不放 `proto8/kernel/` | `kernel/` 裡是 daemon-kernel、llm-kernel、procs-kernel 這類「替別人轉請求」的站；頻道是普通 proc，跟 `templates/judge-llm` 同類（不用模型的定義） |
| C3 | schema 放 **`proto8/schema/comm/1/`**（新開資料夾），規格文件 `proto8/docs/COMM.md`（跟 NORMS.md、CONCEPTS.md 同層的入口），知識庫 `aos/comm.json` | `proto8/schema/` 現在不存在；使用者專區的 schema 在 `~/.aos/user/schema/`，那是活資料不是原始碼。規格先獨立一份，U1 定了再收進 NORMS |
| C4 | `mail_notify` 的改法：判斷邏輯寫在新庫 `lib/aos/comm/notify.py`，`mail_notify/_entry` 只加「import 得到就呼叫、import 不到就照舊」幾行，**放在最後一個 commit** | `lib/agent/*` 存檔即生效（06 硬規則 5）；先把庫寫好、測到綠，接線最後做、做前回報。既有 10 支測試（`lib/agent/tests/test_mail_notify.py` 9、`templates/tests/agent-fsm/test_mail_notify_daemon.py` 1）原封不動要全綠，另加一支「沒有 comm、沒貼布告欄時輸出逐位元相同」 |
| C5 | `wake_on_urgent` 的叫醒：第一版**不自動發 `ctl wake`**，只在 `comm_send` 回傳與 `no_reply` 那行寫明「對方睡著、對方同意急件叫醒、你可以請它的上層 kernel 叫」並附上層名字 | 查過 `ctl wake`：設了 `AOS_KERNEL` 就把請求寄給**寄件人自己的** kernel（phase.py:230 `via_kernel()`），那個 kernel 管不到別隊的 agent，多半被拒；硬要成功就得繞過 kernel，違背 gate 的用意。誰該替睡著的人收急件、叫醒它，列 U7 |
| C6 | 寄給 `user` 不另做轉換層：`comm_send --to user` 直接拒（`UseUserSend`），提示改用 `user_send`／`aos-user send` 並帶 `urgent` | 使用者專區有自己的 schema 與 kind（decide／verify…），一般信件 body 硬塞過去是兩套格式混用；分開最不易錯。02 稿 3.7 的欄位對應改成寫進說明文件 |

其餘 02 稿內容（欄位表、核心表 3.3、防濫用四道、頻道五條防迴圈、相容驗證表、第七節 ok-view schema、邊緣狀況）照收，不重抄。
