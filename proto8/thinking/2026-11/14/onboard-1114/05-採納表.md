# 05 採納表：Argon 的審查與提案，逐條決定

← [onboard-1114](../onboard-1114.md)｜原文 [04](04-Argon原文.md)｜判斷人 ok-onboard（opus），11-14。下表每條都對過事實；改過的計劃見 [03](03-計劃.md) §9「v2 修改」。

| # | Argon 說的 | 決定 | 理由（對過的事實） |
|---|---|---|---|
| A1.1 | 第七個洞：用 write／edit 直接改自己的 stack 或定義夾（tools.json、hooks.json、system.txt），下一次問腦就生效 | **採納** | 屬實：檔案工具不擋工作區外（`proto8/lib/tool_io.py:234`），stack 和定義也是同一個 uid 寫得到的檔。改法：write_guard 加一張**改不掉的禁寫清單**，優先於准寫清單，內容是 `$AOS_STACK`、定義夾 `$AOS_CD`、daemon 的 procs 夾、站台給的禁寫路徑（活樹、使用者專區）。P0 還沒有守門，所以 P0 的「看」包寫檔限制也只是約定，文件寫明 |
| A1.2 | 漏關 `tools_def`、`run_python` | **不採納，但把文字寫清楚** | `tools_def` 在 def 包、`run_python` 在 shell 包（`proto8/lib/packs/shell.json:4`），這兩包在「看」包整包不掛，所以不會漏。03 §2.1 補一句「整包拿掉的包裡有哪幾支」 |
| A1.3 | 沒有 mail_guard 時，可以寄控制信給 kernel 或高權限 agent，借它的手解限制 | **採納** | 寄信沒有收件白名單（`proto8/cmd/aos-mailbox/aos_mailbox/__init__.py:310,358`）。mail_guard 的禁寄清單加上 daemon 的控制信箱和各 kernel 信箱。P0 列為已知風險 |
| A2.1 | 准寫清單掃全部字串參數，會把 `content` 裡出現的路徑當成目標而誤擋 | **採納** | 屬實：`user_zone_guard` 會掃每一個像路徑的字串（`_entry:6`）。當禁寫清單用時很少誤擋，改成准寫清單就會常常誤擋。改成照工具名對參數鍵名（採 B2 前半） |
| A2.2 | 目標檔還不存在時 realpath 的問題、符號連結的 TOCTOU、03 刪掉了「禁寫優先於准寫」 | **部分採納** | 禁寫優先補回（同 A1.1）。目標還不存在時，取最深一層存在的父夾做 realpath 再接回剩下的路徑（採 B2）。TOCTOU 只有在有 shell 能換掉符號連結時才成立，也就是「做」包；它本來就只算約定，交 ok-sec |
| A2.3 | 隊長怎麼替單一隊員帶專屬的環境變數 | **不採納（已有）** | `subagent add` 本來就收 `envs`，而且給的值優先（`proto8/lib/agent/subagent/_entry:6-8,181`）。沒有 shell 的 agent 改不了自己的環境變數，所以准寫清單繼續走 env，不另做 policy.json |
| A3 | 禁令和收尾規矩推去小卡，開場只讀一次，history 一裁就忘；凍結清單改了，正在跑的也拿不到 | **採納**（併 B1） | 對：system 每次問腦都重讀，小卡讀一次就留在 history 開頭。改成：所有禁令、回報三條、凍結的線都寫進站台層 `site.txt`，跟著 system 走；小卡只留**隊長派工時才用的流程**（commit 怎麼交、命名、投稿格式），隊員不讀小卡。站台規矩一改就重拼一次 system |
| A4.1 | 產品的 build 角色文字混進了站台規矩（拋棄式複本、不 commit） | **採納** | 搬到 `site.txt`。產品版的 build 只寫「只改任務書准的地方、跑點名的檢查、貼上指令與輸出」 |
| A4.2 | 中立檢查只 grep 路徑太窄 | **採納** | 檢查清單加上：模型別名（sol、astra、terra、luna、fable、opus）、內部 agent 名（xiaosi、repo-aos、ok-*）、中文字、`wf`、`commit-request` |
| A4.3 | 產品範本直接 `agent_def new`，會留下沒換掉的 `<KNOWLEDGE>` 這類記號 | **採納** | 產品範本的 system.txt 放**已經拼好的「沒有站台」版**：記號換成產品預設，例如 `$AOS_HOME/knowledge`；沒有布告欄就整段拿掉。`aos-kit check` 和 `agent_def check` 對剩下的 `<…>` 記號報錯 |
| A5.1 | P1 還沒有守門，就不能測越界寫入 | **採納**（併 B3 前半） | 順序改成：守門先在暫存樹的 `git archive` 複本裡做出原型（不動 repo、不動活樹），再跑 P1。repo 裡正式的守門照舊在 P2 |
| A5.2 | N=3 時百分比門檻其實就是 100% | **採納** | sol 每格改成 5 次，門檻改寫成次數，例如 A 級開場照做 ≥ 14/15。小模型每格 3 次，只看趨勢，不當成過不過的門檻 |
| A5.3 | token 門檻會被問腦次數干擾；T2 沒有門檻 | **採納** | 主要指標改成「做第一件正事之前的 prompt token」：新組 ≤ 舊組的 30%。T2 加兩條門檻：測試通過 ≥ 4/5；原樹沒被改動 5/5 |
| A6 | goal pause 之後，信來了忘了 resume，就無聲停住 | **採納，另投 aos 意見** | 規矩改成：隊員只有在寄了 BLOCKED 之後才 pause；system 寫「收到信時，若 goal 是 paused，先 goal resume」。同時寫一則 aos-advice：信進來時讓 idle 把 paused 的 goal 自動恢復，或至少提醒一次 |
| B1 | 廢掉小卡，規矩進 system，角色規矩隨任務書附上 | **部分採納** | 隊員這邊照做（同 A3）。隊長多半是 opus eca，它本來就讀 wf，小卡留給它當派工流程表 |
| B2 | 照工具名對參數鍵名；准寫和准寄改用 stack 裡的 policy.json | **前半採納、後半不採納** | 鍵名對照表和「最深一層存在的父夾做 realpath」都採納。policy.json 放在 stack 裡，等於要守門自己保護自己的設定檔；env 沒有 shell 就改不了，比較簡單（同 A2.3） |
| B3 | 守門提前；sol 每格 5 次；開場資訊全部由 add 預填，只剩 goal set | **前兩項採納；第三項只用在 C、D 級** | A 級保留一次 `self_state`：只要一次呼叫，又能核對 add 填的值和實際一致，省下來的有限。C、D 級本來就是預填（02 §1.6） |

## 因此要投的 aos 意見
