# 07 追想：董事長自訂「焦點」資源（例：離 Skyrim modding 核心功能多近），讓做那件事的 agent 先被處理（11-14，只想不做）

← [llmk2-1114](../llmk2-1114.md)｜接 [03 計劃](03-計劃.md)；不改 v1 範圍

## 使用者原話（11-14，經全景頁，一字不改）

> 好，幫我追加想想，假如這個llm kernel第二層他是一個agent，然後我跟他說我想要定義一種特殊的資源，比如是否更接近skyrim modding的核心功能，對，因爲可能在整個樹中，我更想要這個功能先被實現，所以我希望正在實現這個功能的agent的LLM請求先被處理

## 結論

- **做得到，但要拆成兩半**：「誰離目標多近」交給第二層 agent 判斷（慢、會想），「哪封信先處理」交給現有的站照數字排（快、不想）。agent **不站在每次呼叫的路上**：每封信都問模型會又慢又貴，而且它自己的呼叫也在吃同一份資源。
- **它其實不是新資源，是新的排序依據**：額度還是那幾種（次數、token、Claude 週額度）；「焦點」決定的是同樣有額度時誰先拿。叫「焦點」比叫「資源」準。
- **先只插隊、不搶保底**：靠近焦點的信優先級往上加，但別人的保底照給，老信照舊會因為等太久而升級（aging）。焦點要能直接搬額度的話，是第二步，要董事長另外點頭。
- **Claude 那邊要誠實講**：Claude 的呼叫不經站，所以「先處理」在 Claude 上做不到逐封插隊。能做的是派工層級：建議暫停或放慢無關的線，把 Claude 額度留給焦點線（03 §9 第 4 題說的派工閘）。v1 電表先量出焦點線實際燒了多少。

## 怎麼運作

1. **董事長定義焦點**：一句話＋期限，例「接近 Skyrim modding 核心功能，到 11-30」。第二層 agent 先問清楚「核心功能」指什麼，寫成可檢查的說法，回給董事長確認。
2. **agent 打分**：看每條線（每個 sender）的任務書、最近的信件標題、工作區與部門位置，給 0～3 級並附一行理由。
   - 要把「卡住焦點的前置工作」也算進來，例如焦點功能要靠的工具或 kernel 修補，依賴要往回傳。
   - 分數由 agent 看證據給，**不收 agent 自己報的「我很相關」**，免得大家都說自己相關。
   - 只在任務變動時，或每隔一段時間重打一次。
3. **寫進表**：`plan.json` 加 `focus` 欄（id、說明、期限、各 sender 的級數與理由），驗表照舊，壞表照舊 fail-open。
4. **站照數字排**：級數換成優先級加成（例 3 級＝升到 high）；保底與 `reserved.high` 照舊，避免焦點把整棵樹餓死。
5. **董事長看與改**：電力卡多一欄「焦點」，列出各線級數與理由，可以直接改級數或撤掉焦點。期限到了焦點自動失效，免得一直插隊。

## 風險

- **判斷錯**：agent 可能把無關的線打高分，或漏掉前置工作。所以要附理由、董事長能一鍵改；開頭幾天先只顯示、不生效。
- **焦點太多就等於沒有焦點**：同一時間限一到兩個。
- **餓死其他線**：靠保底和 aging 兜底；劇本要測「焦點滿載時，非焦點線仍拿得到保底」。

## 放在哪一版

v1 不動（表、站內樹狀額度、報表、Claude 電表）。焦點適合放在 v2：
- 先做「只顯示分數」；
- 確認判得準以後再讓它影響排隊；
- Claude 的派工建議放 v3，和派工閘一起做。
