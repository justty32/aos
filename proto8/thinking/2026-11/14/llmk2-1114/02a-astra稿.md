# 02a astra 對照稿：分層預算室＋共用候補池（ok-llmk2-astra-1，astra-high，原文照錄）

← [llmk2-1114](../llmk2-1114.md)｜只讀 01 備料獨立寫，沒看 fable 稿

結論：我提議走「分層預算室＋共用候補池」，不把這一層當電力部門，也不另造一套模型排程器。它決定各部門能花多少、哪些工作先做；現有 llm kernel 繼續負責排隊、呼叫與記帳。實體是一個不需要問模型的管理 proc，配上各部門既有的 forwarding llm kernel 站。

這是供比較的提案，不是定案；最後由 ok-llmk2 與 fable 裁定。本稿只依備料與指定知識庫推論，未核驗活樹部署、未改檔。

## 一、為什麼用預算室，而不是電力

LLM 資源有兩種不同的稀缺：現在能同時跑幾件，以及今天／這週還能花多少。`slots` 管前者，預算管後者；有額度不代表馬上有空位，有空位也不代表可以繼續花。

預算室比電力更貼近三件事：部門可以先拿基本額度、臨時申請追加；昂貴模型與便宜模型不等價；某些工作即使有資源，也不值得現在做。它也容得下 Claude 訂閱週限這種「不是逐次付費、但確實會耗盡」的限制。

缺點是比較不直觀：看得懂剩餘額度，未必看得懂延遲與服務品質。因此畫面必須並列「剩多少」與「等多久」，不能只畫預算條。

我不選內部競價。agent 自己報價容易把所有工作都喊成重要，且目前沒有可靠金額或任務價值資料。第一版讓主管分配，比建立虛構價格市場更容易查錯。

## 二、這一層是什麼，怎麼接現有 kernel

暫稱 `llm-budget-office`：一個收管理信、產生設定、彙整帳目的普通 proc，不是逐封思考的 agent，也不是每次問腦都必須再經過的中央閘門。

它管理的路徑如下：

```text
agent → team station → department station → provider station → model
                   ↑
          llm-budget-office
        policy / allocation / reports
```

部門站重用現有 `llm_forward`。每站只認直接來往的 agent 或子站，利用原本三份帳：

- 站總帳：限制整個部門，包含本人與所有子部門。
- pack 帳：限制某種模型／服務類別的消耗。
- sender 帳：限制直屬 agent 或子部門站。

provider station 繼續管理實際端點、後端與總並行。組織樹不直接等於路由樹；一個部門只有真的接入這條路，才標為受管。

管理介面新增的檔案與欄位都是提案：

- `policy.json`：`nodes`、`parent`、`station`、`members`、`limits`、`revision`，存組織對應與核准政策。
- `allocations.jsonl`：記錄每次配額異動，包含 `order_id`、前後版本、理由及套用結果。
- `report.json`：對外的正式報表，包含 `schema`、`as_of`、`coverage`、各節點的 `self` 與 `rollup`。
- 管理信：`demand` 申報需求、既有 `power` 單申請調整、`report` 取得報表；回信明確區分核准與已生效。

問腦信仍維持 `endpoint`、`request`、`priority`，不要求每隻 agent 自己填部門。部門由管理設定對應寄件 stack／子站身分，避免把任意自報欄位當權限。

新東西的理由很窄：現有站會執行限制，但沒有跨站分配、預設 sender 配額、組織對應及正式報表。這些補在管理層，不重寫底下的 scheduler。

## 三、優先級、需求、額度怎麼分

### 把「想要」與「可以花」分開

需求信提議使用 `target`、`period`、`requested_calls`、`estimated_tokens`、`deadline`、`reason`、`allowed_packs`。申報需求不會自動加額度；未回報也不代表需求為零。

額度沿用 `max_calls`、`max_tokens`、`window`。第一版以日為共同窗口，不替每層各發明一套週期。政策借用限制線的外形：

```text
limits.default
limits.by_sender
limits.max
```

`default` 是直屬成員預設，`by_sender` 是完整覆寫，`max` 是該層可核准的天花板；不默默逐欄合併。管理層將它展開成現有 `budget` 設定。未知 sender 在政策檢查處拒絕，不能沿用「沒列名就沒有個別上限」的漏洞。

### 基本額度＋候補池

例如根部門每天可用 1,000 次，先分甲 400、乙 300、本人 100，留下 200 次候補。這些是可花的額度，不是保證模型一定服務成功。

第一版不自動借貸，也不結轉隔日。需要追加就從候補池撥；候補池不夠，再由主管決定是否收回別處未用額度。不能因為某部門今天沒呼叫，就猜它不需要。

申請數字超出天花板，回覆拒絕與可申請範圍，不靜默夾小；否則主管可能以為拿到完整預算。

### 優先級仍只有三級

部門設定 `priority_default` 與 `priority_max`，站在排程前填入或限制信的優先級，解決 stock agent-fsm 沒填 priority 的現況。各級仍是 `low/normal/high`，不創造百分制權重。

部門站先處理內部先後；上游再按該部門的授權範圍限制宣告級別。既有 aging 照常運作，但只改善該站的等待，不宣稱跨多站具有全域公平保證。`reserved.high` 也仍只保障宣告 high，不因 aging 變成 high 就取得保留格。

優先級不會增加額度，也不會搶停在飛請求。高優先部門用完預算，仍須等窗口或取得追加。

### 不夠時的順序

有額度但沒有空位，留在現有排程隊列。額度耗盡則第一版採 `spent: refuse`，讓 agent 走既有 `BudgetMissing` 冷卻與去重通知，不再建立第二套重試器。

換便宜模型必須先得到任務授權，政策可新增 `fallback_packs`。只在尚未送出呼叫時選擇；模型已執行但回覆不明，不自動換模型重做，避免重複付費與不同答案。

換包也不能繞過父部門總額。若碰到的是昂貴 pack 的子額度，而總額仍有餘裕，才可能改走核准的替代包；整個部門已用完 calls，換 sol 也不會憑空多出一次。

「便宜」還不等於適合。規劃工作不能因成本較低就自動交給未獲授權的模型；現有模型分工是替代清單的硬限制。

## 四、部門下還有部門：只對直接孩子分帳

任意深度都用同一條規則：

```text
本人額度 + 各直接子部門額度 + 候補額度 ≤ 本部門額度
```

孫部門的配額算在子部門裡，不在祖父那裡再加一次。父站的總帳則包住全部實際流量；這與 rlimit「每隻各自有上限」不同，是真的有共同父池。

例如甲拿到 400 次，可再分甲一 200、甲二 120、本人 50、候補 30。甲一再往下分，仍只能在自己的 200 裡切。設定不寫死深度，但檢查父子循環、路由循環及重複歸屬。

`llm_forward` 在下一站把上一站當 sender，對這個方案反而剛好：上游只需要管「甲部門用了多少」。但實際 sender 身分須在註冊時核對，不能假定一定等於站 stack；備料指出 forwarding 實作涉及站的 workspace。因此不同部門站必須使用可區分的身分，不能共用後被合帳。

全景的名字前綴可以協助顯示，不能直接成為扣帳依據。預算樹須明確登記；掛到新主管底下，也不代表已有的在飛請求跟著搬家。

動態收回額度是最容易超發的地方。第一版只允許由未分配候補池追加；部門間轉移則安排在換窗，或先停止新放行、結清在飛請求，再減舊額、增新額。減額尚未生效時，不能先把同一份額度發給別人。

這也避免第一版就需要跨站交易協定。後續若需要即時借還，再補可恢復的分配交易，不靠多份 JSON「應該差不多一起改完」。

## 五、Claude 不經 kernel：納入報表，不假裝已控住

我的選擇是「第一版納入外部觀測；沒有資料就明示未知」，不是先不管，也不是立即把所有 eca 改成 agent-fsm。

Claude eca 的程式身體、工具與訂閱路徑都不同。強行改道已超出預算層的小原型，而且會把最緊的資源管理變成整套執行環境遷移。

每個節點新增 `control_mode`：

- `enforced`：問腦真的經過受管站，calls 限制可執行。
- `observed`：從正式外部來源取得用量，只能記帳。
- `unknown`：來源尚未建立，不能報成零。

目前不知道 Claude 是否有可讀且可信的逐次用量來源，因此第一版只定義外部輸入契約：`source`、`account_id`、`period`、`observed_at`、`scope`、`usage`、`confidence`。可先接受人工回報帳號週用量，但要標明時間與來源；若只有帳號總量，就記在未分攤帳，不按人數或執行時間假造各部門數字。

週額度緊時，主管可以要求 eca 收斂、暫停新派工，但那是協作政策，不是每次呼叫的硬閘門。`kernel_gate` 可以管新 proc，不能因此控制已存在的 Claude session。

GPT 與 Claude 各有自己的池。減少 GPT 呼叫不會讓 Claude 週額度回來；儀表板不可把兩者合成一個看似可互換的剩餘百分比。

## 六、董事長怎麼看、怎麼調；一天究竟燒多少

沿用全景 `POST /api/order` 的 `kind: power`，不用先改 UI 名稱。管理 proc 成為接單者，頁面仍不直接修改 kernel 設定。

目前 `priority` 是自由文字，接單端只接受明確的三級對應；其他描述回覆要求修正，不默默猜。`quota` 在後續契約中明定 `max_calls`、`max_tokens`、`window`，`what` 保留理由。

每單以 `order_id` 去重，回覆 `accepted`、`applied`、`rejected` 或 `needs_approval`，並列出實際生效值與版本。信封寫 `from: user` 不是驗證；調整權限須接既有可信的使用者授權流程，不能讓任意 agent 偽造董事長單。

「電力」卡讀正式 `report` 介面，不自行翻 stack。顯示：

- 本日 calls、tokens、剩餘配額與候補池。
- 排隊數、等待時間、在飛數與 `BudgetMissing` 次數。
- 部門 `self`／`rollup`，以及受管、只觀測、未知的覆蓋狀態。
- Claude 週用量與資料時間；沒有資料就是 `not recorded`。

記帳重用 `ledger.jsonl`、`used.json`。前者做逐次稽核，後者做快速狀態；跨站用 `(station, id)` 去重，不能假定所有站的 id 全域唯一。利用 `child` 串起同一次呼叫，公司總量只計實際端點葉子；父站的記錄拿來歸屬，不再加一次。

串鏈缺失時列為未歸屬或待核對，不猜配對。組織異動前的呼叫保留原歸屬，不能因今天搬部門就重寫昨天的成本。

「一天燒多少」先分兩個答案：實測消耗是 calls、輸入／輸出／cached tokens、耗時；金額只有在價目與計費口徑可靠時才計算。訂閱月費不能按 token 偽裝成實際逐次支出；astra 約 sol 三倍只能作粗略選型參考，不是帳單。

另須明示：現有 token 不預扣，可能被在飛請求超過上限。第一版 calls 可作硬配額，token 只能作軟上限與觀測；要承諾金額或 token 硬封頂，必須另做可界定的預留與結算，不能只改欄位名字。

## 七、最小第一版與三個最大風險

第一版只做一個管理 proc、一棵三層小預算樹、既有 forwarding 站，以及正式報表。固定日 calls 配額，人工分配候補；priority 由站套用，保留 aging。自動降級只留政策契約，不先實作；Claude 接一筆標為人工來源的週用量，其他未知明示。

在 repo 外獨立暫存樹，用 fake endpoint 驗：

- 父額度先耗盡時，子部門有餘額也不能越過；未知 sender 被拒。
- 三層流量只計一次總消耗，`self`／`rollup` 對得上。
- 重複 `power` 單不重複加額；重啟後仍知道哪些調整已生效。
- BudgetMissing 走既有冷卻；priority、aging 與在飛不搶占照常。
- 報表有時間戳，Claude 未知不報零；全景只讀正式介面。

未完成這些前，不接活樹、不叫真模型驗預算，也不宣稱已管理全公司支出。

最大的三個風險如下：

1. **覆蓋與權限是假象。** eca 繞外路、sender 不驗真、組織與路由不同，都可能讓報表看似完整。必須逐節點標明覆蓋；同帳號下的合作規則不等於安全隔離。
2. **串站放大等待與記帳不確定。** 上游轉送會占住在飛格，下游又排隊；深層鏈可能卡住兄弟部門，且 aging 不跨站累積。第一版量三層等待，有限逾時、禁止循環；缺帳明示，不靠加總所有 ledger 補洞。
3. **調額與在飛用量競爭。** 收回尚未結清的額度再發給別人會超發，token 後扣也會超限。第一版限制即時轉移、保留父池總閘，只承諾 calls 硬配額；更強保證留待有預留與恢復協定後再做。

這份方案的取捨很明確：先把「誰能花多少、誰真的受管、數字從哪裡來」做準，再談自動借貸、競價與跨模型最佳化。
