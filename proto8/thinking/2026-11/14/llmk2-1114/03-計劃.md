# 03 計劃：llm kernel 上一層＝「配額樹」——站內照樹放行、站外改表與報帳、Claude 先量不管

← [llmk2-1114](../llmk2-1114.md)｜依據：[01 備料](01-備料.md)、[02 fable 稿](02-fable稿.md)（主幹）、[02a astra 稿](02a-astra稿.md)（對照）、[02b Argon 早評](02b-Argon早評.md)｜只規劃、不施工；施工另等使用者點頭（鐵律 2），且使用者說這條線排在 ok-release 後面。

## 0. 結論（先看這段）

1. **比喻**：機制是「配給＋排程」（像 cgroup：保底、上限、優先級，父格圈住子孫），帳用「預算」的話講，**頁面照舊叫「電力」**。電力不貼合三處：模型有品質等級、Claude 有週上限、訂閱不按量計價（02 §1）。內部市場不做。
2. **實體**：不是新 kernel 類型，也不是每部門一站。是三件：
   - **配額表** `plan.json`（部門樹、每格的優先級／保底／上限、哪些 sender 屬於它）；
   - **現有 llm kernel 站加一層「樹狀額度」**：站每拍讀表，信進來時查它屬哪個部門、蓋上部門的優先級、沿祖先鏈用「已用＋在飛」判放不放行，超了照舊回 `BudgetMissing`（agent 那邊 AK17 冷卻、`brain_notify` 全部沿用）；
   - **站外一支固定程序** `aos-llm-quota`：驗表、改表（接董事長 `power` 單）、跨站與 Claude 的報表、每日結算。不經模型。
3. **部門樹是記帳樹，不是路由樹**（fable、Argon 同意，astra 的「每部門一站」只留給要實體隔離時）。agent 照舊直寄供應站，不必改 `AOS_LLM_KERNEL`；改組＝改表。
4. **Claude 先「只量不管」**：從 Claude Code 本機對話紀錄抄 usage（已核：每則回覆帶 model、usage、cwd、sessionId、timestamp），按工作區對到部門，標 `observed`；「派工閘」（部門 Claude 超了就不准再開 Claude agent）等量準了再說。
5. **第一版**：配額表＋驗表、站上的樹狀額度（在 repo 外暫存樹的複本上做）、報表（gpt 站帳＋Claude 本機紀錄）。只有次數是硬上限；不做降級、不做「點數」、不接活樹。

## 1. 三稿怎麼取捨（摘要；逐條在 05 採納表）

| 題 | fable | astra | Argon | 本計劃 |
|---|---|---|---|---|
| 樹 | 記帳樹 | 路由樹（每部門一站） | 記帳樹 | **記帳樹**；forward 只做隔離 |
| 判放行在哪 | 站外分配器每 N 秒寫 `gate.json`，站上 hook 查 | 站外管理 proc 產生各站 `budget` | **站內**即時判（站本來就有在飛數） | **站內**（理由見 §2.3） |
| 分配 | 保底＋上限，可超賣 | 嚴格切塊＋候補池 | 同 fable，補遞迴保底 | **保底＋上限可超賣＋遞迴有效保底** |
| 越界 | priority 夾值 | 申請超天花板拒絕 | 改表時拒、執行時夾 | **改表時拒（`PlanBad`）、信的 priority 夾** |

## 2. 這一層是什麼、跟現有 llm kernel 怎麼分工

### 2.1 圖

```
董事長（全景 power 單）─信─▶ 接單者（v2：一隻小 agent 或 repo-aos）─叫─▶ aos-llm-quota set …
                                                                       │ 驗表通過才寫
                                                                       ▼
                                                    plan.json（唯一真相，rev 遞增）＋changes.jsonl
                                                                       │ 每拍讀
agent ──照舊寄信（endpoint, request）──▶ 供應站 llm-gpt：查部門 → 蓋 priority → 祖先鏈判額度 → 排隊／掛出／BudgetMissing
                                                                       │ 照舊寫
                                                              ledger.jsonl、used.json（多一格 groups）
                                                                       │ 讀
Claude Code 本機紀錄（~/.claude*/projects/**.jsonl）──讀──▶ aos-llm-quota report ──▶ report.json、daily/<日>.json ──▶ 全景「電力」卡
```

### 2.2 分工

| 誰 | 管 | 不管 |
|---|---|---|
| 供應站（現有 `kernel_llm`＋新的樹狀額度） | slots、排隊、打端點、ledger；**部門歸屬比對、蓋 priority、祖先鏈放行、各部門已用／在飛／被拒計數** | 不改表、不讀 Claude、不做跨站加總 |
| `aos-llm-quota`（新，固定程序） | `check` 驗表、`set` 改表（寫 `changes.jsonl`）、`report` 跨站＋Claude 報表、`daily` 結算 | 不碰信、不在熱路徑上 |
| 接單者（v2） | 把 `power` 單翻成 `set` 指令、回信講改了什麼 | 不自己決定分配 |
| agent | 照舊寄信；被擋就冷卻重試 | 不用自己填部門、不用填 priority |

### 2.3 為什麼判放行放站內（不採 fable 的站外分配器）

- 已核：站**每拍是新行程、每拍重讀 `kernel.json`**（`kernel_llm/docs/02` §額度那段），所以讀一份 `plan.json` 也是每拍熱讀，不用新常駐程序。
- 已核：站判額度時本來就算「已完成＋在飛」（`budget.py` `spent_of`、`llm_rules.py` `over_budget`／`admit`），站外只讀 ledger 看不到在飛，必超（Argon A-2）。
- 已核：`before_verdict` hook 能改 `endpoint`／`priority`、退 10 能拒，但拒的代號是 `HookRejected`，**不是** `BudgetMissing`——agent-fsm 只對 `BudgetMissing` 走 AK17 冷卻，`HookRejected` 會變成 BrainFailed 停機。所以 hook 路線還是得改站，不如直接在站的額度模組加一層。
- 改法小而集中：`budget.py` 的三份帳（總、pack、sender）旁加第四份「groups」，`admit` 多查一條祖先鏈；`order` 排序前用部門的 priority 改寫信的級。

### 2.4 介面

**`kernel.json` 新鍵**（只有一個）：

```json
{"budget": {"window": "day", "spent": "refuse", "plan": "plan.json"}}
```

`plan` 是相對 kernel 定義夾的路徑；沒寫＝跟現在一模一樣（不影響舊站）。`budget.senders` 照舊可用，跟樹**兩邊都要過**。

**`plan.json`**（`llm-quota-plan/1`）：

```json
{
  "schema": "llm-quota-plan/1",
  "rev": 7,
  "default": {"cap": {"calls": 50}, "priority": "low"},
  "tree": {
    "id": "company",
    "cap": {"calls": 1500, "tokens": 30000000},
    "priority": "high",
    "children": [
      {"id": "repo-aos", "match": ["procs/repo-aos"], "priority": "high",
       "self_reserve": {"calls": 10},
       "children": [
         {"id": "ok-release", "match": ["procs/ok-release", "procs/ok-release-*"],
          "priority": "high", "guarantee": {"calls": 400}, "cap": {"calls": 900}},
         {"id": "ok-llmk2", "match": ["procs/ok-llmk2", "procs/ok-llmk2-*"],
          "priority": "low", "cap": {"calls": 200}}
       ]}
    ]
  },
  "observed": {
    "claude":     {"window": "week", "source": "~/.claude/projects"},
    "claude-alt": {"window": "week", "source": "~/.claude-alt/projects"}
  },
  "ws_match": {"repo-aos": ["~/repo/aos"], "ok-llmk2": ["~/repo/aos/wf/temp/ok-llmk2"]}
}
```

- `id`：跟全景節點同一套 id（報表直接貼上全景節點）。
- `match`：比的是 sender 正規化後的字串——信封 `sender` 是寄件 agent 的**絕對 stack 路徑**（現有 `budget.senders` 也是這樣認），站先轉成「相對 daemon stack 根」（例 `procs/ok-llmk2-sol-1`）再比；格式寫法：完整字串，或尾端 `*` 的前綴。**最長樣式優先**（完整字串勝過 `*`；`procs/ok-release-hotfix-*` 勝過 `procs/ok-release-*`）；驗表拒絕兩格有完全相同的樣式。沒寫＝`procs/<id>` 與 `procs/<id>-*`（對上「`<eca名>-<角色>-<n>`」命名慣例）。另有 `aos-llm-quota match <sender>` 印命中哪格、祖先鏈、有效 priority、剩多少（換上活樹對舊 sender 名時用）。
- `priority`：low／normal／high。**信沒帶 priority（stock agent-fsm 現況）→ 填部門級；信有帶且高於部門級 → 夾到部門級、記 `priority_clamped`；低於部門級 → 照信的。**子不高於父（驗表時拒）。
- `cap`：任何格可寫；`guarantee`：**只准寫在葉格**（沒有 `children` 的格）；`self_reserve`：只准寫在有 `children` 的格（主管本人用）。都是 `{"calls": N}`；`tokens` 可寫但 v1 只亮燈不擋（§3.4）。窗用 `kernel.json` 的 `budget.window`。
- `default`：沒對上任何格的 sender 共用**一個**格；它是**根底下一個隱含的葉格**（算進根的 cap，可寫自己的 `cap`、不准寫 `guarantee`）。
- `observed`：不經站的池，只記帳不擋。**每個帳號一個池**（`claude`＝`~/.claude`、`claude-alt`＝`~/.claude-alt`，週上限各自算、各自校正）；`ws_match` 把工作區路徑對到部門，**最長路徑前綴優先**（eca 沒有 stack sender 可比）。

**`used.json` 多一格 `groups`（站每拍重算、整格覆寫的快照）**：站現有 `used.json` 已有每個 sender 當窗的帳；每拍用**當拍的表**把「各 sender 已用＋在飛 proc＋排隊信」歸戶加總成 `"groups": {"<id>": {"self": {...}, "rollup": {"calls", "tokens", "in_flight", "waiting"}}}`。所以改表或改組時，**當窗用量跟著 sender 走**（方向題 8）。只有 `refused`、`priority_clamped` 兩個計數是發生當下按 sender 記（`used.json` 的 sender 格多兩欄），歸戶時一樣跟 sender 走。

**回信**：照舊；被樹擋＝`{"error": {"code": "BudgetMissing", "msg": "group ok-llmk2 cap 200 calls/day reached"}}`，msg 寫是哪一格、哪個量。

## 3. 優先級、需求、額度

### 3.1 放行判準

記號：`u(N)`＝格 N **本人**當窗已用＋在飛（次數）；`U(N)`＝N 與所有後代的 `u` 加總。

```
未用保留（由下往上算）：
  葉格 L：          rem(L) = max(0, guarantee(L) − u(L))
  有孩子的格 A：     rem(A) = max(0, self_reserve(A) − u(A)) ＋ Σ_{c∈children(A)} rem(c)
信的主人 X 自己能用的那份：
  own(X) = rem(X)            若 X 是葉格
  own(X) = max(0, self_reserve(X) − u(X))   若 X 有孩子（主管本人寄信，不能動孩子的保底）
放行：沿 X 到根、每個有寫 cap 的格 A 都要
  cap(A) − U(A) − (rem(A) − own(X)) > 0
```

全部成立才放行；任何一格不成立回 `BudgetMissing`。`rem(A) − own(X)`＝A 底下**除了 X 自己那份以外**所有還沒用掉的保底與主管保留，一律先扣下來。

白話：**父格圈住所有子孫；別人（不論多遠的親戚）還沒用到的保底先扣下來；沒人保的額度先到先用。**

為什麼這樣寫（04 審出的兩個洞）：保底只放葉格，所以「沒保底的兄弟用了量」不會抵銷別人的保底（保底跟著葉格本人的 `u` 走，不跟著部門的 `U`）；扣的是整棵 A 子樹的 `rem`，所以隔一層的旁系也吃不到。`self_reserve` 算進 `rem(A)`，子孫寄信時一定被扣，主管本人寄信時 `own` 把它還回來。

### 3.2 驗表（`aos-llm-quota check`，`set` 每次也跑；不過就不寫）

- id 不重複、無環；沒有兩格的 `match` 樣式完全相同；
- `guarantee` 只在葉格、`self_reserve` 只在有孩子的格、`default` 不准有 `guarantee`；
- 每格 `G(A) ≤ effcap(A)`：`G(A)`＝A 子樹裡所有 guarantee 與 self_reserve 的總和，`effcap(A)`＝A 到根路上最近一個寫了 cap 的值（含 A 自己）——**保底不准超賣**；
- 子格的 `cap` 不准大於 `effcap(父)`（大了沒意義，拒掉免得人誤會）；兄弟 `cap` 加總可以超過父（**准超賣**）；
- 子 priority ≤ 父；
- 錯了回 `PlanBad <原因>`，原表不動。
- **站讀表**（站每拍是新行程，要靠檔記狀態）：`plan.json` 的 (mtime, size) 跟 `plan.applied.json` 記的一樣 → 直接用 applied，不驗不寫；變了 → 驗，過了就寫成新的 `plan.applied.json`；沒過或讀不到 → 沿用舊的 applied，壞檔的 hash 記在 `plan.bad.txt`，**同一份壞檔只印一次 warning**（跟現有 `budget_warned.txt` 同一招）。從來沒有好的 applied＝當作沒有 `plan`（＝現況）。表壞不會全擋（fail-open 到「只剩站總量與 pack 上限」）。

### 3.3 需求

- **量到的就是需求**：每部門每窗 `used`、`refused`、`in_flight`、排隊數與等待時間（站算、報表讀）。「用了多少＋被擋多少」不用人填表。
- **申請**：主管寄信給接單者（同 `power` 單形狀），v1 不收，v2 由接單者轉董事長。

### 3.4 不夠時

| 段 | 觸發 | 動作 |
|---|---|---|
| 排隊 | slots 滿 | 照部門級排；`reserved.high` 留格；low 靠 aging 不餓死（現有） |
| 拒絕 | 祖先鏈任一格可用 ≤ 0 | `BudgetMissing` → agent AK17 冷卻（30 秒…每 30 分）＋ `brain_notify` 寄 BLOCKED 給主管（現有） |
| 通報 | 部門當窗第一次被拒 | 報表亮紅；v2 由接單者每部門每窗寄一封給頂層 |
| 降級 | — | **v1 不做**。之後要做：部門寫 `fallback: {"astra-high": "sol-high"}` 才開，只在還沒掛出時換 |

**v1 站內只按次數擋**；格上寫的 `tokens` 只在報表亮 `soft` 燈、不擋（token 事後才知、不預扣，一次長文就能把部門鎖死）。站總量與 pack 原有的 `max_tokens` 照舊。

### 3.5 誰能調

- **v1–v2：只有董事長**（`power` 單或直接改檔）。寫檔權限＝檔案擁有者，跟現況一樣不是安全邊界（sender 也不驗真，屬 uid 那條權限線）。
- v3 起（方向題 5）：主管可在自己格內重分子樹。

## 4. 嵌套

- 層數不限，就是 `children` 往下長；放行沿祖先鏈逐格算。
- 跟全景：同一套 id、報表同樣分 `self`（本人）與 `rollup`（含後代）。**歸屬以表上的 `match` 為準**，不吃全景推出來的父子（全景是四段推論，拿來扣帳不穩）；兩邊對不上的列在報表 `unmatched`／`view_mismatch` 給人修。
- 跟 kernel 樹：gate 樹（誰能起 proc）和配額樹（誰能花多少）是兩棵，**不自動同步**。
- **要實體隔離時才切站**（另一台機器、外包部門、部門要自己的 slots）：上游部門站用 `llm_forward` 轉到供應站；供應站的表裡把「上游站」當一個 sender 掛在該部門格；部門內部怎麼分由上游站自己的 `plan.json` 管（它的根 cap ≤ 上層給的 cap）。帳用 ledger `child` 串，報表按 `(station, id)` 去重、只算葉子列。

## 5. 董事長怎麼看、怎麼調

### 5.1 看

`aos-llm-quota report [--node ID] [--json]`（正式讀取介面；全景後端包成 `GET /api/power`，不翻 stack）：

```json
{
  "schema": "llm-quota-report/1",
  "as_of": "2026-11-14T12:00:05+08:00", "plan_rev": 7, "stale": false,
  "pools": {
    "gpt":    {"control": "enforced", "window": "day", "stations": ["llm-gpt"], "used_pct": 37},
    "claude":     {"control": "observed", "window": "week", "coverage": "local transcripts", "calibrated_pct": null},
    "claude-alt": {"control": "observed", "window": "week", "coverage": "local transcripts", "calibrated_pct": null}
  },
  "nodes": {
    "ok-release": {"parent": "repo-aos", "priority": "high",
      "gpt": {"self": {"calls": 12}, "rollup": {"calls": 371, "tokens": {"in": 0, "out": 0, "cached": 0},
              "elapsed_ms": 5400000, "in_flight": 1, "refused": 3, "waiting": 1},
              "guarantee": {"calls": 400}, "cap": {"calls": 900}, "used_pct": 41, "state": "ok",
              "by_model": {"sol-high": {"calls": 350}, "astra-high": {"calls": 21}}},
      "claude": {"rollup": {"turns": 210, "tokens": {"in": 0, "out": 0, "cached": 0}}, "by_model": {}}}
  },
  "unmatched": ["procs/gpt-lead2"], "ledger_bad_lines": 0
}
```

- `control`：`enforced`（經站、真的擋）／`observed`（只量）／`unknown`（沒來源，卡片寫 `not recorded`，**不報 0**）。
- `state`：`ok`／`soft`（過 80%）／`hard`（被擋中）；`stale: true`＝站或報表超過 5 分鐘沒更新。
- Claude 跟 gpt、兩個 Claude 帳號之間都**分池顯示、不合成一個百分比**（不能互換）；部門卡上的 Claude token 可以兩帳號合計（`nodes.<id>.claude` 下分 `by_account`）。

### 5.2 調：`power` 單（v2）

全景表單改成結構欄（給 ok-view 的需求）：`target`（部門 id）、`pool`（gpt／claude）、`field`（cap／guarantee／priority）、`value`、`unit`（calls／tokens）、理由放 `what`。接單者只把它翻成 `aos-llm-quota set --node ok-release --cap calls=1200 --order <信名>`；`set` 驗表、`rev`+1、寫 `changes.jsonl`（誰、何時、哪張單、前後值）、同一張單（信名）只套一次；回信帶 `{"applied": {"before", "after", "plan_rev"}}` 或 `PlanBad` 原因。看不懂的欄位回信問，不猜。`aos-llm-quota undo --rev N` 回退。

### 5.3 要 ok-view 補的

## 6. 成本與觀測

- **單位**：次數、token（in／out／cached 分開）、秒（`elapsed_ms`）。不做「點」，不算錢（訂閱吃到飽，沒有可靠價目；astra≈3×sol 只當選型參考，報表 `by_model` 讓人自己看）。
- **一天燒多少、誰燒的**：`aos-llm-quota daily` 每天寫 `daily/<日期>.json`＝各部門 × 各模型的次數／token／秒／被拒，**寫當時的歸屬**（改組不改歷史）。
- **Claude 電表**（v1，唯讀）：掃 `~/.claude/projects/**/*.jsonl` 與 `~/.claude-alt/projects/**`（兩個帳號＝兩個池）裡有 `message.usage` 的列（已核：列上有 `message.model`、`message.usage`、`cwd`、`sessionId`、`requestId`、`timestamp`）。只讀這幾欄，**不讀、不抄對話內容**。
  - 去重：同一則回覆可能分成好幾列寫（工具呼叫），以 `message.id`（沒有就 `requestId`）為鍵，**取 `output_tokens` 最大的那列**；增量狀態檔存「當週已見的鍵 → 已計 usage」，新列比舊的大就補差額；檔尾沒換行的半截列跳過、下次再讀。（施工第一步先拿實檔確認「多列」的實際樣子，需核。）
  - 歸戶：`cwd` 對 `ws_match`，最長路徑前綴優先；各 eca 的工作區多半各自分開（`wf/temp/<名>`），落在共用的 `~/repo/aos` 的歸 `repo-aos` 並在報表註明；對不上的列 `unmatched_ws`。子 agent（Agent tool 派的 fable 等）寫在同一工作區的紀錄裡，算派它的那條線。
- **校正**：有人看到 `/usage` 週百分比時寫一行 `calibrations.jsonl`（時間、帳號、百分比），報表算「這週每 1% ≈ 多少 token」並列出估計剩幾成；沒校正過就只給 token，不給百分比。
- **讀帳紀律**：ledger 按 `(station, id)` 去重、壞行跳過並計數、記位移；ledger 不輪替屬站的另案。

## 8. 風險與邊緣狀況

1. **管錯對象**：gpt 不缺、Claude 才缺。v1 就把 Claude 電表放進來，避免只蓋了一套管不缺資源的制度。
2. **sender 不驗真**：agent 可冒別人 stack 寄信吃別部門額度；配額層不解（屬 uid 權限線），報表只列異常。
3. **match 前綴誤中**：`procs/ok-r*` 這種寬前綴會吃到別人；驗表拒絕「同深度重疊」，預設 match 用 `<id>`／`<id>-*` 精確兩條。
4. **保底讓額度閒置**：保底是硬保護，設太大＝別人用不到。報表列「保底 vs 實用」讓董事長調；預設不給保底。
5. **token 會超**：不預扣，在飛的大請求可超過 token cap；只承諾次數。
6. **換窗一擁而上**：冷卻中的 agent 同時醒；冷卻序列錯開一部分、照部門級排，可接受。
7. **Claude 估不準／紀錄格式會變**：只亮燈不擋；格式認不得的列計入 `unparsed` 不猜；`.claude-alt` 是另一池。
8. **改組與歷史**：daily 寫當時歸屬；當窗用量跟 sender 走（一搬就可能超），報表註記。
9. **站的改動何時進活樹**：活樹 `llm-gpt` 的 loop 叫的是 `$AOS_HOME/lib/aos/kernel_llm`（活樹的 lib 是複本，重抄才生效，06），所以改 repo 不會立刻換掉活樹的站；但仍照硬規則 5 新檔先、接口最後、事前報備，換上活樹走 v1.5 的停樹換檔。
10. **gate 樹與配額樹不同步**：新掛的 agent 若不照命名慣例，會掉進 `default` 格；`unmatched` 告警＋命名慣例已存在（07）。
