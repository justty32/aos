# sol 的可寫範圍只寫一份：shell 沙箱那一半的圖紙（ok-fsm，11-14，Argon 審後第 2 版；還沒動手）

← [ok-fsm-1114](../ok-fsm-1114.md)｜題目出處 [wf/advices/fsm範本.md](../../../../../wf/advices/fsm範本.md)「sol 的可寫範圍寫在兩份清單裡，換工作區要兩邊都改」（ok-misc 11-14）

## 結論

`aos-sandbox` 的設定多一個鍵 `"scope": true`。開了以後，沙箱的可寫路徑直接向 ok-onboard 的 write_guard 問（`lib/agent/guard/_entry --scope`），不再自己列。之後換工作區、加一棵暫存樹，只要在掛 agent 時改一個環境變數 `AOS_WRITE_ALLOW`，檔案工具的守門和 shell 沙箱一起跟著走。

## 現況

- 寫檔守門那一半已經解了：ok-onboard 的 write_guard（20b65475c，`proto8/lib/agent/guard/`）。範圍只有一個來源：`$AOS_WS` 加 `AOS_WRITE_ALLOW`；禁寫是自己的 stack、`$AOS_CD`、定義夾、`AOS_WRITE_DENY`、任何 proc 的 stack。`_entry --scope` 印一行 JSON：`{"allow": [{"path", "from"}], "deny": [{"path", "from"}], "rules": ["proc-stack"]}`，路徑都 realpath 過。
- shell 沙箱那一半：`proto8/cmd/aos-sandbox/examples/shell-boxed/_metainfo.json` 的 `sandbox.rw` 出廠是 `[$AOS_WS, $AOS_STACK]`，本來就跟著工作區走。出事的是各線自己抄的那份：ok-misc 的 `defs/sol-worker/shell-boxed/_metainfo.json` 把五條絕對路徑寫死在 `rw`，同樣五條又寫死在 `guard.json` 的 `write_roots`。多一棵樹就要兩邊各加。
- `aos-sandbox`（`proto8/cmd/aos-sandbox/bin/aos-sandbox`，368 行）的 `ro`／`rw` 只認路徑和 `{"$env"}`。`$env` 換出來是一個字串，裝不了「用冒號分隔的好幾條」，所以現在沒辦法讓它直接讀 `AOS_WRITE_ALLOW`。

## 設計

### 1. aos-sandbox 加 `"scope": true`（預設沒有＝行為完全不變）

開了以後，在算 `ro`／`rw` 的那一步：

1. 跑 `$AOS_HOME/lib/agent/guard/_entry --scope`（子行程，環境原樣傳），讀 stdout 那一行 JSON。
2. `allow` 的每條路徑加進 `rw`。
3. `deny` 的每條路徑，如果落在某條 `allow` 底下而且存在，加進 `ro`。沙箱本來就是「深的那條說了算」（T32），所以工作區可寫、裡面的 stack 和定義夾唯讀。
4. 設定裡原本寫的 `ro`／`rw` 照舊併進來。shell 工具自己的小格（`rw` 裡的 `{"$env": "AOS_STACK"}`，是 `<agent stack>/tools/<名>`）比 agent 的 stack 深，仍然可寫。
5. `rules` 裡的 `proc-stack`（任何 proc 的 stack 都不准寫）沒辦法列成路徑。沙箱這邊只做得到一部分：工作區底下第一層若有 `.stack` 夾，加進 `ro`。其餘靠檔案工具那邊的 guard。這個落差寫進 README。

### 2. 問不到範圍時：不跑（跟現有的「設定壞了就不套沙箱」相反）

- 現有規矩：設定讀不了、型別不對、`$env` 沒設＝當沒寫、不套沙箱直接跑。
- `"scope": true` 例外：`AOS_HOME` 沒設、guard 不在、`--scope` 退非 0、輸出不是那個形狀，一律不跑程式，印 `aos-sandbox: error: ScopeFailed <原因>`、退 1。
- 理由：寫了 `scope` 的人就是要用它來限制寫入；問不到就放行，等於整個沒關。

### 3. shell-boxed 範例改用它

`examples/shell-boxed/_metainfo.json`：`sandbox` 加 `"scope": true`，`rw` 只留 `{"$env": "AOS_STACK"}`（`$AOS_WS` 由 scope 的 allow 帶進來）。README 補一段「換工作區只改 `AOS_WRITE_ALLOW`」。

看得到哪裡（`ro` 裡的其他樹、執行檔白名單）仍然手列。這次只統一「能寫哪裡」，「能看哪裡」是另一件事。

### 4. fsm-guard 的擋下訊息

`wf/public/tools/fsm-guard`（ok-astra 的站台工具）擋下時多印設定檔路徑（advice 的建議 3）。它的 `write_roots` 不動：那是站台工具，新的線改用 write_guard 就沒有兩份清單的問題。這一點交 ok-astra，或我改完給它審。

## 第 2 版改了什麼（Argon 審後，11-14 14:25）

原文在 [04-Argon審圖紙03-原文](04-Argon審圖紙03-原文.md)。上面「設計」節以這一節為準，衝突處照這裡。

**先講清楚這個鍵給的是什麼**：`"scope": true` 讓沙箱和檔案工具的守門用同一份「可寫的根」。它不是把 write_guard 搬進沙箱。沙箱只在啟動那一刻綁路徑，之後不看每一次寫入，所以守得比 guard 鬆，鬆在哪裡要在 README 白紙黑字寫出來（見第 6 點）。

1. **guard 從哪裡找：不看 `$AOS_HOME`**。用 `aos-sandbox` 自己的真實路徑往上推到 `lib/agent/guard/_entry`。這樣改環境變數換不掉被執行的那支程式。
2. **範圍變數信誰**：`AOS_WS`、`AOS_WRITE_ALLOW`、`AOS_WRITE_DENY`、`AOS_STACK` 來自 agent 被掛上去時的環境，一路由 aos 傳給工具；腦叫工具只給 JSON 參數，改不了工具的環境。所以前提是「能改工具環境的人本來就能不經沙箱跑東西」。這個前提寫進 README。Argon 提議的「從 stack 裡的啟動快照讀環境」不做：那是 aos-exec 和 daemon 的改動，超出這一條。
3. **deny 一定壓過 allow**：算好 allow、deny 之後，任何 allow（和設定裡寫的 rw）只要等於某條 deny 或落在它底下，就從 rw 拿掉；唯一例外是工具自己的小格（`rw` 裡的 `{"$env": "AOS_STACK"}`）。不能只靠「深的說了算」。
   - `$AOS_STACK` 的指涉：工具跑起來時 `$AOS_STACK` 是 `<agent stack>/tools/<名>`。`scope.py` 會把這種小格算成 `<agent stack>` 再放進 deny，所以 deny 的是整個 agent stack、rw 的是比它深的小格，兩邊不撞。施工時要有一支測試鎖住這件事。
4. **還不存在的禁寫路徑**：沙箱綁不了不存在的路徑。落在 allow 底下、啟動時不存在的 deny，印一行 warning 說明沒擋到哪條，照樣跑；README 列為沒擋的情況。
5. **`.git` 和各層 `.stack`**：對每一條 allow 的根，第一層已存在的 `.stack`、`.git` 一律加進 ro（不只工作區）。`--scope` 現在沒列 `deny_parts`，這一步是沙箱自己補的；等 ok-onboard 把 `deny_parts` 放進輸出就改讀它的。
6. **README 要寫的邊界**（照 Argon 的句子改寫）：「`scope: true` 只在沙箱啟動那一刻同步可寫的根和當時已存在的禁寫路徑，不等於 write_guard 的逐筆攔截。下面這些沙箱擋不住，只能靠檔案工具那邊的 guard：第二層以下或啟動後才出現的 `.stack`、`.git`；啟動時還不存在的禁寫路徑；禁寫路徑的上層夾可寫時，把上層夾改名再重建同名路徑；禁寫路徑本身是符號連結時把連結換掉。禁寫的東西請放在可寫根的第一層。」
7. **版本**：請 ok-onboard 在 `--scope` 的輸出加 `"version"`。沙箱遇到不認得的版本或不認得的 `rules` 名字＝ScopeFailed、不跑。
8. **寫了 `scope: true` 的設定整份關緊**：不只「問不到範圍」，設定裡任何一格壞掉（讀不了、型別不對、`$env` 沒設）都不跑、退 1。沒寫 `scope` 的設定照舊（要不要全面改成關緊是底座部的決定，不在這一條）。
