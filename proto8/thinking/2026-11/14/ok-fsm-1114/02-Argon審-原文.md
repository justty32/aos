## (A) 審閱意見（Review：事實／推論錯誤、風險、遺漏）

### 1. `[高]` 【裁斷 (2)】以 `self_tools add` 作為預設 opt-in 機制並不穩妥，且核心前提尚未實測
* **未驗證的事實**：結論第 1 點以「agent 自己一句 `self_tools add` 掛回來」作為推翻 11-10 裁定的核心配套，但內文卻坦承「要先實測一份 pack 檔能不能這樣整包加」。在未確認 `self_tools add` 能否吃 pack 檔（以及 `<AOS_HOME>` 環境變數能否在工具參數中自動展開）前，不應直接送交使用者裁決。
* **多花問腦輪次與擊穿快取（風險）**：
  1. Agent 從發現缺工具 → 查 `aos/packs.json` 找路徑 → 呼叫 `self_tools add` → 下一輪才真正呼叫工具，至少多耗 **1～2 次問腦**（以中段 5 萬 token 計，多花 5～10 萬 token，直接吃掉省下的 7～10 輪額度）。
  2. **動態改工具會擊穿提示快取**：工具清單位於提示最開頭（prefix），執行中呼叫 `self_tools add` 會改變 prefix，導致該 agent 累積數萬 token 的對話快取在下一輪**全部失效（0 命中）**。
* **權限與語意衝突**：既然 07 規定 `sol` 的 `max_subagents: 0`，又在通用 `system.txt` 提示所有 agent 可以自己去掛 `subagent` 與 `def`，會誘導卡關的 `sol` 浪費輪次去掛自己無權使用的包。此外，若某個定義已透過 `kits` 掛了 `subagent`，`system.txt` 仍寫「`subagent` 未預設載入」會造成提示自相矛盾。

### 2. `[高]` 【裁斷 (1)】砍這四包方向正確，但漏查實際呼叫頻率，且「只改範本不改現有 `sol`」拿不到帳本預期的效益
* **四包切法合理性**：拿掉 `jsonx`、`subagent`、`events`、`def` 是對的第一刀——這四包佔字元 41%（平均每支 2,742 字元，是其餘工具的近兩倍），且高度綁定特定角色（隊長／設定維護／常駐事件），尤其 `jsonx` 與 `json` 語意重疊易害弱模型選錯。
* **遺漏的關鍵數據**：手上有 `ledger.jsonl` 的 1,599 次問腦紀錄，卻**只量了 `_tooldef.json` 靜態字元數，沒統計 55 支工具的實際呼叫次數**。留下的 `json`（9 支，11%）與 `self`（6 支，14%）合計佔剩餘工具量的 **43%**；若不看實際呼叫分佈，無法確認留下的 11 包裡有沒有從未被呼叫的「死工具」（例如 `self` 裡除 `self_state`、`self_tools` 外的 4 支，或 `index`、`gadgets`）。
* **範圍與效益脫節**：第 2 節寫「已經存在的定義不受影響：各線的 `defs/sol` 都有自己的 `tools.json`」。但帳本裡 1.18 億 token 正是現有各線 `defs/sol` 燒出來的！如果只改 `templates/agent-fsm` 而不改現有 `defs/sol`，短期內實際省下的 token 接近 **0**。

### 3. `[高]` 【裁斷 (3)】提示快取 29% 的現象解讀有偏差，且提議的單機實驗無法重現問題
* **對 `19968/68068` 的解讀偏差**：稿中推論「工具清單最常被快取，沒被快取的大多是對話」。但 OpenAI 的 prefix cache 是**從第 0 個 token 連續比對**的，不可能「只快取前段、同台機器卻漏掉後段對話」。出現 `19968/68068` 的真正原因是：**該次請求被路由到剛服務過「另一隻 `sol`」的機器**——兩隻 `sol` 共享前 `19,968` token（`system` + 55 支工具），從第 `19,969` token（各自的第一封任務信）開始分岔，所以只命中 `19,968`。
* **對排隊 2 分鐘過期的推論錯誤**：OpenAI prompt cache 的閒置 TTL 為 **5～10 分鐘**（離峰更長），且多隻 `sol` 同時密集問腦會不斷刷新共同 prefix；llm kernel 排隊 2 分鐘**不會**導致快取過期。
* **為什麼會有 `0/50847`、`0/95151`（連 19,968 都沒中）**：
  1. 多隻 `sol` 同時送出完全相同的前 256 token，觸發供應商對單一 prefix 負載過高時的跨節點溢流（overflow 到冷機）；
  2. LiteLLM 若設定了多把 API Key 或多個 endpoint 輪詢，不同 Key 之間快取完全隔離；
  3. 或是請求組裝時，`tools` 順序／`system` 內動態欄位在部分輪次發生變動。
* **原實驗設計無效**：稿中建議「同一隻 agent 帶與不帶 `prompt_cache_key` 各跑 20 次」。**單一隻 agent 在無併發競爭下連跑 20 次，就算不帶 key 也不會發生跨機溢流，命中率本來就會很高（常達 80%+）**，測不出差異。

### 4. `[中]` 【裁斷 (4)】給使用者的問題設計過早且缺漏關鍵決策點
* 在實測 `self_tools add` 能否載入 pack 之前，選項 A 的前提不成立。
* 漏問使用者**是否同步更新現有各線的 `defs/sol`**（否則省額度效果不會發生在現有產線）。
* 選項 C（「`self` 只留兩支、`json` 只留讀」）在現有以「包（pack）」為單位的架構下無法直接靠拿掉 `$override` 項目做到，必須拆包（例如拆出 `self-core`／`json-ro`），稿中未說明此工程成本。

## (B) 具體提案（Proposals）

### 1. 工具包切分與掛載機制（針對問題 1 & 2）
1. **補跑一行統計再定案**：先從 `ledger.jsonl` 撈出這 1,599 次問腦中**各工具實際被 tool_call 的次數**附在表上。
   * 確定先拿掉 `jsonx`、`subagent`、`events`、`def` 四包。
   * 若 `self` 另外 4 支（除 `self_state`、`self_tools` 外）或 `json` 寫入工具在一般 `sol` 呼叫率極低，將 `self` 拆為 `self`（核心 2 支）與 `selfx`（進階 4 支），比整包留 14,084 字元更划算。
2. **區分「角色靜態配發」與「執行期動態加掛」**：
   * `subagent`、`def` 屬於**角色權限**，應在建立定義或套用 `aos-kit add`（如隊長 kit）時**靜態寫入 `tools.json`**，不要叫 agent 執行中自己 `self_tools add`（避免破壞快取與多花輪次）。
   * `jsonx`、`events` 才作為少數情境的動態加掛（或專用 kit）。
3. **`system.txt` 提示改為不與 kit 衝突的寫法**：
   * 不要寫死哪四包沒載入，改寫為：`"Optional tool packs (see aos/packs.json) can be attached in tools.json or via self_tools."`
4. **施工前先實測 `self_tools add`**：立即實測 `self_tools {"op": "add", "path": "..."}` 能否吃 `lib/packs/*.json`。若不支援整包格式，應直接擴充 `self_tools` 支援 `"pack": "<pack_name>"`（免填絕對路徑，也解決 `<AOS_HOME>` 展開問題）。

### 2. 驗證提示快取的正確實驗（針對問題 3，交給 `ok-llmk2`）
分兩步，第一步不用花錢跑新實驗就能定案：
1. **離線比對（0 成本，立刻可做）**：
   * 從 `llm-gpt` 紀錄中取出同一隻 `sol` 出現 `19968/68068 -> 64000/74779 -> 0/95151` 的連續三筆原始 request payload，直接 diff 前 20,000 token 的 JSON 字串是否 100% 相同，並檢查 LiteLLM 是否跨多組 API Key／deployment 分流。
2. **併發 A/B 實驗（驗證 `prompt_cache_key`）**：
   * 不能單隻跑。必須在**多隻 `sol` 同時工作的高峰情境**（或同時啟動 6 隻併發壓測 agent，每隻連跑 15 輪）：
     * **對照組（3 隻）**：不帶 `prompt_cache_key`。
     * **實驗組（3 隻）**：在 LiteLLM／OpenAI 請求帶上 `prompt_cache_key: "<agent_name>"`（把同一隻 agent 的連續對話釘在同一台快取節點，避免被共同的 19,968 開頭打散）。
   * 比較兩組的「完整對話命中率（命中 token 佔上輪總 token 比例）」。

### 3. 建議改寫「要使用者裁的題目」（針對問題 4）
先完成 `self_tools` 實測與 `ledger.jsonl` 呼叫次數統計後，改向使用者提問以下兩題：

> **問題 1：agent-fsm 範本預設工具縮減幅度？**
> - **A. 縮 4 包（推薦，55 → 40 支，工具定義省 41%）**：拿掉 `jsonx`、`subagent`、`events`、`def`。隊長類角色改由 `kits` 靜態掛上 `subagent`／`def`；臨時需要 `jsonx`／`events` 的 agent 可用 `self_tools` 動態掛回。
> - **B. 縮 4 包＋拆細 `self` 包（55 → 36 支，省約 50%）**：除 A 的 4 包外，將 `self`（佔 14%）拆為預設載入的 `self`（只留 `self_state`、`self_tools`）與選配的 `selfx`。
> - **C. 維持 11-10「全部預設開啟（55 支）」**：完全只靠 `kits` 替特定角色刪減。
>
> **問題 2：若採 A 或 B，現有各線已建立的 `defs/sol` 要不要一併同步瘦身？**
> - **要（推薦）**：直接更新現有各線 `sol` 的 `tools.json`，立刻省下線上 6～12% 的提示額度。
> - **不要**：只改 `templates/agent-fsm`，僅對未來新建的定義生效。
