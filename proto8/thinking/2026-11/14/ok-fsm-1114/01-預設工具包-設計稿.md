# agent-fsm 範本預設工具包：設計稿（ok-fsm，11-14，Argon 審後第 2 版）

← [ok-fsm-1114](../ok-fsm-1114.md)｜題目出處 [wf/advices/fsm範本.md](../../../../../wf/advices/fsm範本.md)「agent-fsm 範本預設掛 55 支工具」

## 結論

1. 範本預設從 15 包 55 支縮成 11 包 40 支：拿掉 jsonx、events、subagent、def 四包。要用的角色在做定義時就寫進 `tools.json`（或用 kits 蓋上去），不靠 agent 執行中自己加。工具清單少約四成。
2. 使用者 11-10 定的「通用四包預設開」（look、change、delete、shell）不動。
3. 按角色再縮，交給 ok-onboard 的 kits，不在範本做第二套。
4. 工具說明分短版長版先不做。
5. 另外發現一件比縮工具更大的事：問腦的提示快取只命中 29%。這不在本線範圍，建議另開。

第 1 點改的是使用者 11-10「2.都開吧」的裁定，要他點頭。

### 工具清單在一次問腦裡佔多少

llm-gpt 的帳本（`ledger.jsonl`，11-14 13:30，1,599 次問腦）：

- 提示合計 1.18 億 token，其中快取命中 3,480 萬，**29%**。
- 55 支工具加 system 大約 2 萬 token。一隻 sol 做到第 20 次問腦時，提示常在 7～15 萬 token，所以工具清單大約佔提示的 15～30%，其餘是越疊越長的對話。
- 快取命中的樣子很亂。同一隻 sol 連續幾次問腦：`0/50847 0/56446 19968/68068 64000/74779 0/95151 95488/96139`（命中／提示）。常見的 19,968 正好是工具清單加 system 那段。
- 這份帳本裡的 sol 大多不是 55 支：各線的 `defs/sol` 早就自己縮過（例如只掛 look、change、json 三包的 sol，開頭那段只有 3,840 token）。所以帳本上的 1.18 億 token 不是範本預設燒的，改範本省的是「之後照範本新做的 agent」。
- 沒量到的：55 支各被叫過幾次。帳本只記用量、不記叫了哪支工具；要量得讀各線 sol 的 history，那不在本線可讀的範圍。

所以這題的效果要老實講：拿掉四包，工具清單少四成，整體提示大約少 6～12%。有用，但不是大頭。

## 設計

### 1. 範本預設改成 11 包

`proto8/templates/agent-fsm/tools.json` 的 `$override` 拿掉四項：

| 拿掉 | 為什麼可以不預設 |
|---|---|
| jsonx（8 支） | 只有改 aos 設定檔（帶 `$ref`／`$env`）才需要。一般資料用 json 包就夠，兩包的說明還很像，弱一點的模型會選錯。 |
| subagent（3 支） | 只有帶隊的 agent 要。07 規定 sol 不再往下派（`max_subagents: 0`），掛著只是白送。 |
| events（2 支） | 定時叫醒、自己掛 hook，是進階用法。`self_hook` 一支就 5,111 字元，全表最大。 |
| def（2 支） | 做新定義、做新工具，只有帶隊或做工具的 agent 要。 |

留下 self 整包的理由：`self_tools` 在，agent 才能自己把包掛回來；知識庫的五條規則也叫 agent「改自己用 self_*」。

**要用這四包的怎麼掛**（Argon 審後改）：在做定義的時候就寫好，不叫 agent 執行中自己加。

- 做定義的人（隊長、kits）在那份定義的 `tools.json` 的 `$override` 加一項，例如帶隊的加 `lib/packs/subagent.json` 和 `def.json`。這跟現在各線縮包是同一個動作，方向相反。
- 不靠 `self_tools add` 的三個理由：
  1. 查程式看起來 `add` 一次收一支工具，不收整份 pack 檔。
  2. 執行中換工具清單會讓提示開頭變掉，這隻 agent 累積的對話快取下一次全部失效。
  3. agent 要先發現缺工具、查路徑、加、下一輪才能用，多花一兩次問腦，把省下的吃回去。
- 臨時真的要（例如只用一次 `clock_register`），`self_tools add` 逐支加仍然可以，知識庫寫明路徑就好，不當成主要做法。

**範本 `system.txt` 不寫「哪四包沒載入」**：寫死會跟已經掛了 subagent 的定義自相矛盾，也會引誘不能往下派的 sol 去掛。知識庫 `aos/packs.json` 寫清楚就夠。

### 2. 誰會受影響

- 已經存在的定義不受影響：`agent_def new` 是整夾複製，各線的 `defs/sol` 都有自己的 `tools.json`，而且大多已經縮過。不去動各線自己的定義。
- 之後從範本新做、又要當隊長的 fsm agent（例如 astra 當 kernel）：要自己加 subagent 包。kits 之後的「帶」包會處理。
- eca-claude 範本不動（它本來就只有 8 包，另一題）。
- 要跟著改的文字：`lib/packs/README.md`（哪幾包預設開）、知識庫 `aos/packs.json`（「fifteen packs: 55 tools」）、`aos/kits.json` 的數字、`templates/agent-fsm/README.md`、`templates/docs/02-agent-fsm.md`。
- 要跟著改的測試：範本測試裡假設某支工具在預設清單的（施工前先 grep subagent、agent_def、clock_register、self_hook、jsonx_ 在 `templates/tests/` 的用法）。

### 3. 不做的

- **不在範本做角色機制**。按角色選包就是 ok-onboard 的 kits（蓋在定義上的覆蓋檔，`aos-kit add`）。已跟它講定。
- **工具說明分短版長版先不做**。說明文字佔送出內容的 43%（37,021／85,725），其餘是參數 schema。分兩版等於 55 支工具各維護兩份文字，而這些說明是一路照「讓弱模型看得懂」磨出來的，縮短的風險是工具用錯。先做第 1 點，量了再說。
- **comm 包（ok-board 新做的 5 支 board_*）不進範本預設**。頂層已決定不接範本 `tools.json`；kits 的看包自己掛了其中兩支。

### 4. 知識庫補一句成本

`aos/packs.json` 加：每多掛一包，每次問腦多送多少字元（附上表），以及怎麼自己掛回來。

## 要使用者裁的一題

> agent-fsm 範本預設的工具，要不要從 55 支縮成 40 支（拿掉 jsonx、subagent、events、def 四包；要用的 agent 自己一句話掛回來）？
> - A 縮（推薦）：每次問腦的工具清單少四成，整體提示約少一成。代價是要帶隊、要定時、要改設定檔的 agent 得先掛包。
> - B 不縮：維持 11-10「都開」。省額度只靠 kits 按角色掛。
> - C 縮更多：A 之外，self 包只留 self_state、self_tools（另外四支在範本 `tools.json` 逐支關掉，不用拆包）。55 → 36 支，約少五成。代價是 agent 預設不能自己整理對話紀錄、不能自己停。沒有各工具的實際使用次數，我不推薦現在就做。

## 另外發現：提示快取只命中 29%（不在本線範圍）

對話是只往後加的，照理每次問腦前面一大段都該命中快取，實際上常常整次 0。Argon 審後的解讀：

- 快取是從開頭連續比對的。只命中 19,968 的那幾次，是請求被送到剛服務過「另一隻 sol」的機器：兩隻的 system 加工具清單一樣，從各自的第一封任務信開始分岔，所以只中開頭那段。
- 整次 0 的可能原因（都還沒查證）：十幾隻 sol 同時送出開頭一樣的請求，供應商把同開頭的請求溢流到別台機器；或 LiteLLM 後面有多把金鑰、多個端點輪流，彼此快取不通；或組請求時工具順序、system 裡有會變的欄位。
- 排隊 2 分鐘不是原因（快取閒置幾分鐘內不會過期）。

建議交給管 llm kernel 的線（ok-llmk2），分兩步：

1. 不花錢的先做：取同一隻 sol 連續三次的原始請求，比對開頭那段是不是逐字相同；查 LiteLLM 有沒有分流到多把金鑰。
2. 再做併發對照：6 隻同時跑、每隻 15 輪，3 隻不帶 `prompt_cache_key`、3 隻帶（值用 agent 名字），比完整對話的命中率。單獨一隻連跑測不出來，因為沒有別人搶。

如果命中率能從 29% 拉到 80%，省下的比縮工具多好幾倍。

### 第一步查證結果（ok-fsm，11-14 13:55，全程唯讀；頂層 13:41 裁定歸本線）

**第 1 件：同一隻 sol 連續幾次請求的開頭有沒有逐字相同 → 相同。**

- 資料：我自己的 ok-fsm-sol-1、sol-2 的 `think/request.json`，隔約一分鐘取兩次，只存各段的雜湊（腳本與結果在 `~/code/fsm-1114/cache/`）。
- 請求只有 `messages` 和 `tools` 兩個鍵，沒有時間戳之類會變的欄位。
- 工具清單的雜湊兩次相同，兩隻 sol 之間也相同（同一份定義）。system 那則相同。
- 對話只往後加：sol-1 從 53 則變 55 則，前 53 則逐則雜湊相同。
- 所以不是 aos 組請求時把開頭弄變了。
- 沒查到的：這是 aos 寫出去的樣子。LiteLLM 轉成 ChatGPT 後端格式之後長怎樣（它會在前面加一段自己的預設 instructions）沒有紀錄可看。

**第 2 件：LiteLLM 有沒有把請求分到多把金鑰或多個端點 → 沒有。**

- 設定在 `~/repo/llm_proxy/litellm.yaml`，模型表在 `models/chatgpt.yaml`（82 項）。只看結構，沒讀任何金鑰值。
- `chatgpt-gpt-6.1-sol-high` 只有一項、指向 `chatgpt/gpt-6.1-sol`，沒有同名的第二項，所以沒有輪流分流。
- chatgpt 這組沒有 api_key 欄，走的是 ChatGPT 帳號登入，一個帳號。
- 沒有 router_settings；`drop_params: true`、`num_retries: 2`；這個模型的 `allowed_openai_params` 只有 `reasoning_effort`。

**查的時候另外看到、最可能的原因（讀 LiteLLM 程式看到的，還沒做實驗證實）：**

- LiteLLM 1.87.5 的 chatgpt 後端每個請求都帶一個 `session_id` 標頭。它的取法（`llms/chatgpt/common_utils.py` 的 `get_chatgpt_session_id`）依序是：呼叫方給的 `litellm_session_id`／`session_id`、`metadata.session_id`、再沒有就用這次呼叫的 `litellm_call_id`，最後才是隨機 uuid。
- aos 的 llm kernel 沒有送任何 session id（`lib/aos/kernel_llm` 裡找不到這幾個字）。所以每一次問腦都是一個新的 session id。
- 如果 ChatGPT 後端是照 session 分配快取的機器（Codex CLI 就是整段對話用同一個 session），那每次都換 session 就等於每次都碰運氣，跟帳本上「有時全中、有時只中共同開頭、有時 0」的樣子對得上。
- 要改的話：llm kernel 送請求時帶一個固定的 session id（例如寄件 agent 的 stack 路徑的雜湊）。這是改 llm kernel 送出去的內容，屬方向題，本線不動手，交 head-tools 決定要不要做第二步實驗。
