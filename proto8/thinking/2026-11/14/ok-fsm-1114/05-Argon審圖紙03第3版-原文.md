### (A) 改回 `$AOS_HOME` 是否可接受？少了 binary-relative 會漏掉什麼具體攻擊？

**可接受。** 在「所有工具與 hooks 本來就經由 `$AOS_HOME` 載入，且 LLM 只能傳 JSON 參數、無法控制執行環境變數」的前提之下，改回 `$AOS_HOME` 不會擴大對 LLM 的信任面；反之，在活樹架構下，這能避免沙箱與檔案工具讀取不同版本的 guard，也避免 repo 工作區的修改存檔即直接影響活樹沙箱。

**Binary-relative 本可擋下、但 `$AOS_HOME` 擋不住的具體攻擊：**
1. **沙箱內或跨身分邊界的遞迴呼叫（環境變數劫持）：** 由於 scope 是在換成 `aos-run`／subuid 之前用呼叫者身分計算並執行 `_entry --scope`，若已經在沙箱內的程式（例如 agent 透過 bash 執行的腳本）或任何能控制自身環境變數的呼叫者，直接再次執行 `AOS_HOME=/tmp/fake aos-sandbox ...`，`aos-sandbox` 會在進沙箱／降權前執行 `/tmp/fake/lib/agent/guard/_entry`，不僅能偽造任意 `allow` 清單，還能在目標身分下直接執行任意程式碼。
2. **間接污染環境的啟動路徑：** 若有任何外層 wrapper、測試腳本或 `.env` 載入機制允許工作區覆寫環境變數，攻擊者只需改動 `AOS_HOME` 就能整包替換 guard，而 binary-relative（若 binary 位於唯讀系統路徑）則不受環境變數影響。

### (B) 只檢查「guard 資料夾不可寫」夠不夠？有哪些低成本項目應一併加入？

**不夠。** 僅檢查 `$AOS_HOME/lib/agent/guard` 不落在 `allow` 底下太窄，建議用同一個 realpath 比對函式一併納入以下低成本檢查：

1. **整個 `$AOS_HOME/lib`（realpath）：** 不只 `guard/`，若沙箱內能寫入 `lib/` 下的共用模組或其他工具，下次呼叫任何工具時同樣能繞過防護。
2. **`aos-sandbox` 自身（含 symlink 本身與 `realpath` 後的 `cmd/aos-sandbox`）：** 活樹的 `aos-sandbox` 指回 repo 的 `cmd/`，若工作區剛好涵蓋該 repo，沙箱內程式可直接改寫 `cmd/aos-sandbox` 或換掉 `~/.local/bin/aos-sandbox`。
3. **本次使用的沙箱設定檔本身（realpath）：** 尤其在第 8 點尚未修補前，只要沙箱內能改寫設定檔、故意弄壞其中任意一格，下一次執行就會觸發整份設定 fail-open（沙箱完全不套用）。
4. **比對邏輯補齊（同樣極低成本）：**
   - 應比對**最終可寫集合**（`allow` 加上設定檔本身的 `rw`，扣除有效的 `deny`），而非只看 `allow`。
   - 應做**雙向包含檢查**：除了「保護路徑落在可寫路徑底下」，也要擋「可寫路徑落在保護路徑底下」（例如只把 `guard/_entry` 或 `lib/某子夾` 掛成可寫）。

### (C) 適合直接放進 README 的兩句話（說明 `scope` 保證與不保證什麼）

> 當設定檔其餘欄位皆合法時，`"scope": true` 保證 `aos-sandbox` 必須成功向 `$AOS_HOME/lib/agent/guard/_entry --scope` 取得範圍並確認 guard 本身不可寫，只要無法算出範圍或保護條件不成立就一律拒絕執行（ScopeFailed）。但由於目前仍沿用「設定檔其他欄位損壞時視同未設定、直接放行」的規則，`"scope": true` **不保證**整份設定檔 fail-closed——若同份設定檔中任何其他欄位格式錯誤，整個沙箱（連同 `scope` 限制）仍會被略過而不套用。
