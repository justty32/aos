## 結論

- **三圈**：
  - 內圈：使用者帳號，裡面有使用者、專區、daemon、kernel 站、LLM kernel、金鑰。
  - 中圈：每隻 agent 一個 `sub:N`（subuid，免 root），一台 daemon 共用一個群組。
  - 外圈：外來程式一律進 aos-sandbox。
- **怎麼開門**：夾的擁有者都是使用者，用 ACL 開給 agent，不靠 setgid。主線零 root、不寫新的 setuid 程式。全部可選、預設關，照 11-05「linux權限沒設也可以」。
- **疊在已裁的基礎上**：11-13 kernel-limits-plan（K1～K18）與 11-14 ok-limits 的 B1～B6，不推翻。
- **第 0 期在家機暫存夾實測 8 項（E1～E4、E7、E8、E10），都免 root**：
  - 跨 uid 丟信可行，sticky 擋得住刪、改別人的信。
  - git、tmux 照常。
  - 使用者殺得到 `sub:N` 的行程，但讀不到它的 environ。daemon 的收養、清掃要先改認人方法，這是任何換 uid 的前提。
  - mkstemp 的 0600 會壓掉 ACL mask；寄件人能做出毒信。兩種情況內圈都用 `aos-asuser --fix` 救得回。
  - 收件人能原地改寫信、st_uid 不變。
  - 家目錄 700 時，私有 mount ns 綁定可以不打洞就讓 subuid 走到樹。
- **跟 ok-release 的關係**：
  - 第 1 期（底座：體檢與退回工具、daemon 認人改法、只收緊內圈專用的秘密）不改用法，可以平行做。
  - 第 2 期單隻自願換 uid，可選、預設關。
  - 第 3 期（`security: on`）起會改安裝與用法，排在公開 demo 之後。
- **老實講的洞**：eca 身（Claude Code）在第 5 期之前都算內圈，OS 層管不到它。

## 後續候選（第 1 期交件時記下）

- 審稿員的非阻擋點（下一筆或第 2 期前處理）：
  1. `secret-open` 會誤報：判法是 `mode & 0o044`，有擴充 ACL 的檔 group 位顯示的是 mask，`aos-share key` 做出來的 0640＋命名 ACL 會被報。
  2. `reset` 遇到第一個失敗就停：`setfacl -R -b` 因 sub uid 的檔失敗時，後面的 `chmod g-s,-t` 不跑；README 步驟順序要對上。
  3. `reset` 對 `/`、`~`、活樹沒有防呆，PATH 以 `-` 開頭會不會被當選項沒查；第 2、3 期拿它當退路前要補。
  4. 第 2 期威脅清單：認人退路只比 uid、不比 AOS_STACK／AOS_DAEMON，state 窗是 agent 自己寫的；帳本上線後一格能把 pid 指到同一個 sub uid 的任何行程（含別棵樹）。
- `exec.json` 收成 600：要另改 daemon 寫檔（現在每次重寫都是 0666&~umask）。
- kernel-limits 段 3（daemon 用 newuidmap 起 sub:N、認 `limits.groups`）：本線接，排第 2 期「單隻自願換 uid」，連帶寫 `uids.json` 帳本；1d 要先上或同一次換樹上（head-core 11-14）。
- 「daemon 起 proc 用環境白名單、非模型 proc 不拿 API key」：出處 ok-board 的 aos-advice「原型傾印環境的風險」第 4 條；排第 3 期 security:on 一起考慮。`aos-share check` 第 1 期不加查 `*_KEY`（要讀活樹行程的 environ，超出規格 10；sub:N 的行程本來就讀不到）。
- ok-devt 身分模型：`notify_box` 跨 uid 時要不要限「只能指向請求者自己寫得進的信箱」、在哪一層限，歸本線定（第 2、3 期）。
