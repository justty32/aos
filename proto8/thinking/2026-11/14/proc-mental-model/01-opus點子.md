先把使用者那句拆成五個零件，下面每個模型都是挑其中幾個零件組起來：

| 零件 | 原話 |
|---|---|
| 軸 | 「一段時間（根據未必要是現實世界時間）」 |
| 切片 | 「沿着 x 軸看，其切片在每個點上都有不同」 |
| 應當 | 「他**應當**造成的影響」「**應該**有的樣貌」 |
| 外在 | 「還要考慮外在影響」 |
| 分岔 | 「考慮幾率，不同世界線」 |

---

## M1. 軸可以換：proc 是「沿某個有序量」的切片，時鐘只是其中一種軸

**一句話**：先決定拿什麼當 x 軸，proc 才有樣貌；同一件事換一根軸，是另一張圖。

```
同一隻 agent 做同一件事，三根軸：
  x = cycle     : ▁▁▂▅▅▅▂▁   （何時忙）
  x = 累計 token : ▁▂▃▄▅▆▇█   （錢花在哪）
  x = 寄出的信序 : ①──②──③    （對外說了幾次話）
```

**好想**：「時間未必是現實時間」直接成立——C-37 早就讓時鐘跟狀態脫鉤，這裡只是再往前一步：軸是使用者（或 kernel）挑的。kernel 想優化 token，就沿 token 軸看 proc；想優化人類理解，就沿「人看了幾個檔」軸看。軸＝優化目標的投影方向。
**盲點**：軸要是有序的。很多量只有偏序（兩隻 agent 各寄一封信，誰先？），一旦多個 proc 一起看，全序的軸就不存在，要換成 M4 的光錐。

## M2. 樂譜與演奏：「應當」是一份譜，跑起來是一場演奏

**一句話**：proc 有兩層——譜（應當的樣貌，規範性）與演奏（實際的切片，描述性）；說「proc」時得先說是指哪一層。

```
譜   ：♩ ♩ ♪♪ ♩ ─        ← _metainfo 寫的：cost、九軸、應寫哪些檔
演奏 ：♩ ♩ ♪♪♪ ♩ ─ ♩    ← observed：多寫了一個檔、多花一格
差   ：      ^      ^    ← 不受控的地方
```

**好想**：使用者那句「原本是那樣，發現不是那樣，就去找 _metainfo、_index」就是在演奏時發現走音、回頭翻譜。粗化／細化也對得上：粗的譜只記「這首 3 分鐘」，細的譜每小節都記。上一輪的 A（預期與實際）是這個模型的特例，但樂譜多給一個概念——**同一份譜可以被不同樂手演奏**：同一個 `_metainfo` 被 haiku 跑、被 opus 跑、被純函數跑，都是同一個 proc 的不同演奏。
**盲點**：誰寫譜？很多 proc 根本沒有事先的譜（agent 自由發揮），這時「應當」只能事後歸納（從過去的演奏反推譜），變成雞生蛋。

## M3. 世界線束：proc 是一把線，不是一條線；RSI 就是把這把線捏細

**一句話**：從同一個起點出發，每一格都可能分岔；proc＝這整把可能的軌跡，機率＝每條線的粗細。

```
起點 ●
      ╲═══════╗          粗＝常走的線
       ╲───╮   ╚════●    細＝少見的線
        ╲  ╰──●          ● ＝結局
         ╲·····●
越往右越散開＝越不可預測。純函數＝整把收成一條線。
```

**好想**：使用者的主軸（把 agent 換成沒有機率性的純函數）在這張圖上就是「讓束收窄」。每一次沉澱一個呼叫點，就是在某個分岔點把幾條細線剪掉。可預測性有了幾何意義：束的粗細。`measure` 重跑 N 次＝抽 N 條線（上一輪 C）。
**盲點**：束只能抽樣、看不到全貌；而且「同一個起點」很難真的相同（端點、時間、信箱都在變），抽到的散布混著模型機率與外在影響（見 M5）。

## M4. 光錐：proc 在每一格「碰得到什麼、被什麼碰到」

**一句話**：proc 的樣貌不只是它自己的狀態，還有它在空間（資料夾）裡的影響範圍——未來光錐是它能改的，過去光錐是能改它的。

```
         ws/out/  mailbox(bob)        ← 未來光錐：我這一格起可能寫到的
              ╲   ╱
   ───────────  ● me @ cycle 40  ──────
              ╱   ╲
       ws/in/   mailbox(me) ← ann    ← 過去光錐：能影響我這一格的
```

**好想**：「外在影響」有了明確邊界——過去光錐裡不是自己寫的東西就是外在。權限、沙箱、`kernel` 拒絕，都是在削光錐。可預測性：光錐越窄越好預測，所以「把 proc 關進小資料夾」本身就是降不確定性。「我這行 a=1 會不會蓋掉別人的 a」（第六段）就是在問光錐有沒有重疊。
**盲點**：aos 共用 ws、共用腦端點，光錐常常重疊得一塌糊塗；而且很多影響不經檔案（端點變慢、使用者心情），畫不進資料夾空間。

## M5. 開放系統：proc＝自己的規則＋邊界上流進來的東西

**一句話**：把 proc 想成一個有邊界的容器，裡面照規則走，邊界上有東西流進流出；機率分兩種來源——裡面擲骰（模型取樣）和外面丟東西進來（信、端點、人）。

```
         信、端點回應、人
            │ │ │  （流入：外在影響）
   ┌────────▼─▼─▼────────┐
   │ 規則（fsm＋工具）    │──► 寫檔、寄信（流出：它造成的影響）
   │   🎲 llm 取樣         │
   └──────────────────────┘
```

**好想**：把「不確定」拆兩半，對應兩種不同的修法——裡面的骰子靠沉澱（換成純函數），外面的流入靠固定（`run.json` 釘住輸入、錄放外在事件）。上一輪 03 說「一致性量到的是兩者合計、現階段不拆」，這個模型說明了**以後為什麼要拆**：修法不同。
**盲點**：邊界畫在哪是任意的。把信箱畫進邊界，信就不是外在；把腦端點畫進去，llm 就是內部。同一件事，邊界一換，「外在」與「機率」就換來換去。

## M6. 展開的 fsm：proc＝狀態圖在時間上攤開

**一句話**：fsm 是「規則」（靜態、一張圖），proc 是這張圖沿時間攤開成的路徑；有機率的只有某幾條邊。

```
fsm（定義）:    idle ─► ask_llm ─?─► do_tool ─► idle
                              ╰─?─► reply
攤開（proc）:   idle·ask·do·idle·ask·reply      ← 一條世界線
               idle·ask·reply                   ← 另一條
?＝機率邊（llm 決定走哪）；其他邊是確定的
```

**好想**：接得上 11-06 那份「agent＝loop＋fsm、loop 像 cpu」：cpu 執行指令串，攤開就是 proc。「沉澱」在這裡最具體——把一條 `?` 邊換成確定邊，世界線數立刻少一半。也接得上 Linux：Linux proc 的程式碼是圖、執行軌跡是攤開。
**盲點**：只適用有明確 fsm 的 agent；eca（Claude Code 一整坨）內部的圖看不到，只能看外面的切片。

## M7. 函數 vs proc：函數是定義，proc 是它在某段軸、某條世界線上的一次實現；九軸是束的統計量

**一句話**：使用者 11-06 已經說了函數屬性「描述時間軸上的區別，乃至世界線上的區別」——那函數屬性量的對象，其實就是 proc。

```
檔案屬性  ↔ 物體的長寬高（一個切片就看得到）
函數屬性  ↔ proc 這把線的形狀（要看整條軸、整把束才量得到）
   例：「確定性」＝束的粗細；「耗時」＝沿 cycle 軸的長度；
       「token」＝沿 token 軸的長度；「傲嬌 0.4」＝某觀察者看整把束的印象
```

**好想**：「函數九軸」與「proc」不再是兩套東西：一個是名詞（函數、定義），一個是那名詞在時空裡留下的痕跡。`_metainfo` 寫的是「預期的束統計量」，`observed` 量的是「實測的束統計量」。
**盲點**：九軸裡有些軸跟時間無關（例如原始碼大小、可讀性），硬說它們是 proc 的屬性會扭曲；可能要承認屬性分「定義上的」和「跑出來的」兩種。

## M8. proc 本身可以粗化／細化：一格可以展開成一串子 proc

**一句話**：切片的解析度不固定；粗看一個 proc 是一格，細看是一串子 proc，每個子 proc 又是一串……

```
粗： [ 寫一段台詞 ]                              cost: 7
細： [ 找景色 ][ 問 A 角色 ][ 問 B 角色 ][ 拼 ]   cost: {token:{in:6,out:4},time:1s}
更細：         [ 讀 A 的 _metainfo ][ ask ][ 回信 ]
```

**好想**：跟第一段的資源粗化／細化同一套語言——proc 就是一種資源，可以 `cost:7` 也可以展開。也對上使用者最後那行：「原本以為是那樣（粗的預期），發現不是（實際），就去找 _metainfo、_index（往細一層翻）」——差異出現的地方，就是該細化的地方。`_index`＝proc 往下一層的目錄。
**盲點**：子 proc 之間的時間軸不一定對齊（一個用 cycle、一個用信序），細化時要決定子 proc 的軸怎麼映回父 proc 的軸。

## M9. 事件溯源：proc＝一串對空間的差分，樣貌＝差分累加

**一句話**：C-33 的直讀——proc 不是狀態，是「狀態的變化」；把每格的變化記下來，任何一格的樣貌都能從起點加回去。

```
cycle:   0     1        2         3
diff :   ∅   +a.json  ~a.json   +b/  -a.json
樣貌 ：  {}   {a}      {a'}      {a',b}  {b}
```

**好想**：image（C-16、C-79）、git、重播、回溯都自然；「切片」就是累加到某一格；「世界線」就是 git 分支——同一個 commit 兩邊各自 diff。aos 一切皆檔，這個模型幾乎不用新東西。
**盲點**：對外的副作用（寄出的信、問過的腦、使用者看到的畫面）無法重播或倒退；差分只記空間，不記「為什麼」。

## M10. 天氣預報與紀錄：proc 跑之前是預報（帶機率），跑完是紀錄（只剩一條線）

**一句話**：同一個 proc 有兩種時態——未來式的它是一張機率分佈，過去式的它是一條確定的軌跡；「應當」屬於未來式。

```
cycle 10 時看：  ┄┄ 過去：一條線 ━━━━━━● 現在 ┄┄ 未來：扇形 ⟨ 70% / 20% / 10% ⟩
cycle 20 時看：  ━━━━━━━━━━━━━━━━━━━━━━● ⟨ … ⟩      ← 扇形塌了一段成線
```

**好想**：把 M2（應當）和 M3（世界線）放在同一張圖上：「現在」這條線往右是束、往左是線。預報準不準（預報說 70%、實際發生的頻率）就是可預測性的一種量法；kernel 排程看的是預報，帳本記的是紀錄。
**盲點**：預報要有人做（誰來算那 70%？），在 agent 身上這份預報本身就要花 token；而且對「只跑一次」的 proc，機率沒辦法驗證。

## M11. 觀察者相對：proc 的樣貌取決於誰在看

**一句話**：同一段過程，人看是進度與可讀性、kernel 看是 token 與排隊、另一隻 agent 看是信件往來；沒有「唯一的」proc 樣貌，只有「對某觀察者的」proc。

```
           ┌─ 使用者看： 「做到一半，看不懂它在幹嘛」
proc X ────┼─ kernel 看： 「已用 3 萬 token，排第 2」
           └─ bob 看：   「寄了 2 封信給我，1 封沒回」
```

**好想**：接得上 11-06「有光才有影，要找參照物」與上一輪「可理解性每筆分數帶 by／for」。M1 的「軸」與 M4 的「光錐」都可以理解成「觀察者挑的」。「不確定性」也是相對的（11-06：「對於你我他任何一個特定人的不確定性」）。
**盲點**：全相對就沒有可以比較的東西；需要至少一個大家同意的「客觀觀察者」（例如 daemon 的帳、`observed.jsonl`）當共同參照。
