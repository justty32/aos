## 1b `aos-share check`／`aos-share reset`（新子命令；Python；`proto8/cmd/aos-share`）

`aos-share check [-R] PATH...`：唯讀體檢，一行一個問題，最後一行是總數。有問題退 1，沒問題退 0。分四類：

| 類 | 判法 | 輸出 |
|---|---|---|
| `secret-open` | 祕密檔讓 group 或 other 讀得到。祕密檔的判法：檔名是 `.env`、`*.env`、`token*`、`*token*.json`、`*.key`、`exec.json`、`*secret*`，或被某個 `tools.json` 的 `env_file` 指到（只看掃描範圍內的） | `secret-open PATH mode=0644` |
| `acl-masked` | 有命名的 ACL 項目，但 mask 把它的有效權限壓掉了一部分（`getfacl` 看到 `#effective:`） | `acl-masked PATH entry=u:100004:rwx effective=r--` |
| `acl-missing` | 父夾有預設 ACL，這個項目卻沒有對應的擴充 ACL（多半是 `mv` 進來的，E4） | `acl-missing PATH (parent has default ACL)` |
| `acl-present` | 只在 `--list-acl` 時列：所有帶擴充 ACL 的項目，給 `reset` 前後比對用 | `acl-present PATH` |

`aos-share reset [-R] [--dry-run] PATH...`：正式的退回工具，當第 2、3 期的退路。

1. `setfacl [-R] -b PATH`：清掉擴充 ACL 和預設 ACL。
2. 拿掉 aos-share 樣板加上的特殊位：夾做 `chmod g-s,-t`。rwx 位不動。
3. `--dry-run` 每一步只印 argv，跟現有的 dry-run 一致。
4. 產權還原（`aos-asuser --fix --recursive`）**不併進來**：那要在 userns 裡跑，另外寫進 README 當第二步。

不改：現有六種 KIND、旗標和錯誤代號原樣不動。新增錯誤代號：沒有。check 讀不到的項目印 `unreadable PATH errno`，照樣算一個問題。

測試：照 `cmd/aos-share/tests/test_share.py` 的寫法，暫存夾裡造出四類毛病，各一支：
- 能變紅：有毛病退 1、輸出對；
- 能變綠：`reset` 後 check 退 0，`getfacl` 看不到擴充項。

## 1d daemon 認人改法（讀不到 environ 時有退路；今天的行為不變）

現況：
- adopt `same_tree()`（`impls/aos-daemon/src/daemon/adopt.cpp:55`）：讀不到 environ 就回 true，也就是照舊接回。
- sweeper `_orphan()`（`py/aos_sweep_proc.py:130`）：讀不到 environ 就回「left alone」。

E1 實測過：uid 1000 讀不到 `sub:N` 行程的 environ。

改法：先比對 pid、`started_at_ticks`、`boot_id`（兩邊原本就有），對上之後：
1. 讀得到 environ：**完全照舊**。今天全部是同一個 uid，永遠走這一條，所以行為不變。
2. 讀不到（EACCES）：改讀 `/proc/<pid>/status` 的實際 `Uid`，跟**可信來源**給的「這一格應該是哪個 uid」比對。
   - **adopt**：可信來源是表上那一列的 `limits.user`，解析成數字 uid，用 daemon 現有的解析方式。那一列沒寫 `limits.user`，或解析失敗，就照舊回 true。寫了而且相符，回 true；不相符，回 false，當成別人的行程，不接回。
   - **sweeper**：孤兒已經不在表上，所以可信來源是 daemon stack 裡的帳本 `uids.json`。格式照 02 稿：`{"<cell 相對 daemon stack 的路徑>": N}`，表示 `sub:N`。
     - 帳本不在、或沒有這一格：**照舊 left alone**。今天沒有帳本，所以行為不變。
     - 有這一格，而且 status 的 Uid 等於 `sub:N` 換出來的真號：當成這一格的孤兒，照現有流程收。
     - 不相等：left alone，說明寫 `uid mismatch`。
   - 絕不拿 state 窗裡寫的 uid 當依據，因為那個窗是 agent 自己寫得到的。
3. 帳本這期只有讀，沒有寫的人（寫帳本是第 2 期）。`sub:N` 換真號照 aos-share 的規則，讀 `/etc/subuid` 第一筆；測試可以用 `AOS_SHARE_SUBUID` 指定替代檔。

測試：
- 既有的 adopt、sweeper 測試全過。
- 新增 sweeper 測試：用 `aos-asuser sub:N -- sleep` 起一個 environ 讀不到的行程，偽造它那一格的 state 窗。
  - 沒有帳本：left alone；
  - 帳本相符：會收；
  - 帳本 N 不符：left alone。
  - 要用 E1 的擺法：家機有 newuidmap，跑不了就 skip，並寫出原因。
- adopt 的 C++ 測試照 `impls/aos-daemon/tests` 的寫法：同一個 uid 時行為不變。換 uid 的情形只能手測，記進報告。
