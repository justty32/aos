## 一、結論

1. **骨架照 fable 稿**：分三圈。內圈是使用者帳號，裡面有使用者、專區、daemon、kernel 站、LLM kernel 與金鑰。中圈是每隻 agent 一個 `sub:N`，一台 daemon 共用一個群組。外圈是外來程式，一律進 aos-sandbox。夾的擁有者都是使用者，用 ACL 開給 agent，不靠 setgid。主線不用 root、不寫新的 setuid 程式，全部可選、預設關。
2. **第 0 期先試了四項（E1～E4），都在免 root 的暫存夾做**，結果見第二節。三項證實 fable 的推法：跨 uid 丟信可行；git 加預設 ACL 照常能用；tmux 格子裡換 uid、畫面照常。有一項推翻 fable 的推法：使用者帳號**殺得到** `sub:N` 行程，但**讀不到**它的 `/proc/<pid>/environ`。所以 daemon 收養（adopt）、清掃（sweeper）在換 uid 之前要改認人的方法。
3. **fable 稿漏了一個會擋路的地方：祖先夾走不進去**。家目錄 `/home/lorkhan` 是 700，subuid 連 `~/aos-home` 都走不到。不能用在家目錄打洞（給 `--x`）的方式解決，Argon 指出那樣會讓 subuid 讀到家目錄裡所有 644 的檔。推薦的做法是：換 uid 時開一個私有 mount ns 綁定樹，E10 實測可行。這是使用者看得到的改動，歸第 3 期，見 Q9。
6. **Argon 審過、補測 E7、E8、E10 之後改的地方**（逐條見 [05 採納表](05-採納表.md)）：
   - 預設 ACL 只保證「刪得掉、救得回」，不保證「照樣能改」（mkstemp 的 0600 會壓掉 mask）。
   - 信推薦改成單檔投遞（Q10）。
   - st_uid 只在內圈拿來記額度，不拿來驗專區回信（Q4）。
   - `.env` 收緊跟「改走 LLM kernel」綁在同一期。
   - 號段要避開系統帳號、要登記、不能撞號。
   - eca 的畫面要由 daemon 在它自己的 uid 裡起 tmux（第 5 期）。
4. **跟 ok-release 的關係**：第 0、1 期不改安裝與用法，可以跟 ok-release 平行。第 1 期只動活樹的權限位，而且是使用者自己跑的 chore。第 2 期可選、預設關。第 3 期起會改安裝或用法，一律排在公開 demo 之後。
5. **eca 身（Claude Code）前四期都算內圈**，OS 層管不到它。這一點要寫進發佈版的「已知限制」嗎？這件事要問 ok-release，已經寫信經 xiaosi 轉。

## 二、第 0 期實測（11-14 12:03，家機，免 root）

做法：腳本放 `~/code/sec-1114/`（`e12.sh`、`e4.sh`），都經 `clean.sh` 清掉 `AOS_*` 再跑。跨 uid 的資料夾放 `/tmp/ok-sec-1114/`，因為家目錄是 700，subuid 進不去（這本身就是發現，見結論第 3 點）。換身分用 repo 裡現成的 `proto8/cmd/aos-asuser`；整段對照則用 `unshare --map-users=1:100000:65536 --map-groups=1:100000:65536 --map-root-user`。家機 `/etc/subuid` 是 `lorkhan:100000:65536`，`/tmp` 支援 ACL。輸出全文在 `~/code/sec-1114/e12.out`、`e4.out`。

### E1：訊號與 /proc（fable 稿標「待試」）

| 誰 → 對誰 | 結果 |
|---|---|
| 使用者 1000 → `sub:5`：`kill -0`、`SIGTERM` | **可以**（使用者擁有那個 user ns） |
| 使用者 1000 → `sub:5` 的 `/proc/<pid>/environ` | **讀不到**：`Permission denied` |
| `sub:6` → `sub:5`：kill、讀 environ | 都不行：`Operation not permitted`、`Permission denied` |
| 另一次 `sub:5`（另一個 ns，同一個真號 100004）→ `sub:5` | kill 得到（同一個真 uid＝同一個人） |
| `sub:5` → 使用者的 shell：kill、讀 environ | 都不行 |

**這件事的意思**：daemon 對自己送出去的行程可以送訊號，`stop`、`kill` 都走得通。但 adopt 靠讀 environ 認人（`impls/aos-daemon/src/daemon/adopt.cpp:54`，讀不到就回 true），sweeper 也靠 environ（`py/aos_sweep_proc.py:130`，讀不到就不管）。換 uid 之後，前者會把每個讀不到的都當成自己的，後者則一隻都清不到。**改法**（交給管 daemon 的線）：daemon 在表上記 pid 加 `/proc/<pid>/stat` 的啟動時間（stat 人人可讀），收養時用這兩樣比對，不讀 environ。這件事排在第 2 期的第一步，任何換 uid 都要等它先做好。

### E2：跨 uid 丟信（fable 稿第四節 mailbox 那格，標「待試」）

擺法：收件人 `sub:5`，同台的寄件人是 `sub:6`、`sub:7`，都帶群組 `sub:600`；外人 `sub:9` 不在群組裡。`tmp/`、`new/` 的擁有者是收件人，群組是 daemon 群組，模式 `1730`（sticky、群組只能寫和進），`cur/` 是 `700`。三個夾都加 `u:lorkhan:rwx`，再加預設 ACL：`d:u:lorkhan:rwx`、`d:u:<收件人>:rwx`、`d:g::---`、`d:o::---`。擁有者和 ACL 由使用者進一個整段對照的 ns、以裡面的 root 身分設定，不用真 root。

| 動作 | 結果 |
|---|---|
| `sub:6`、`sub:7` 照 aos-post 的做法丟信（`tmp/<信>/` 寫 letter.json，再 rename 進 `new/`） | 成功 |
| `sub:6` 列 `new/`、讀 `sub:7` 的信（知道信名也一樣）、刪或改名 `sub:7` 的信 | 都被擋：`Permission denied`、`Operation not permitted` |
| `sub:9`（不在群組）丟信 | 被擋 |
| 收件人 `sub:5` 列 `new/`、把信從 `new/` 搬到 `cur/`、讀信、刪自己 `cur/` 裡的信 | 都成功 |
| 使用者丟信給 `sub:5`、`sub:5` 收；使用者讀 `cur/`、列 `new/` | 都成功 |

**這件事的意思**：fable 的「只能丟」投遞口在 OS 層是真的，aos-post 的寫法不用改，它是用 `access(W_OK|X_OK)` 檢查，ACL 認得。有一個前提：**收件夾的擁有者必須是收件人**，不然 sticky 會擋收件人搬別人的信。建夾的時候要進整段對照的 ns 做 chown，所以 `aos-share` 要多一種樣板（暫名 `mailbox`），或由 daemon 建 stack 時直接做。

### E4：git 與預設 ACL

| 動作 | 結果 |
|---|---|
| 使用者的 repo，子夾加 `u:100004:rwx` 與預設 ACL；`sub:5` 改檔、加新檔、帶 `--git-safe` 跑 `git status` | 成功；新檔是 `100004:100004`，ACL 讓使用者照樣能改 |
| 使用者 `git add`、`commit` subuid 寫的檔 | 成功 |
| `git checkout` 重寫檔案後 | 新檔吃到預設 ACL（有效權限 rw），`sub:5` 照樣能寫 |
| 從別處 `mv` 進來的檔 | **沒有 ACL**，`sub:5` 寫不進（跟 fable 推的一樣） |

**這件事的意思**：git 不是問題。`mv` 進來的檔會漏掉 ACL，所以 `aos-share check`、`repair` 是必要的，不是可有可無。

### E3：tmux 格子裡換 uid（12:15）

做法：tmux server 由使用者起，socket 放在 `~/code/sec-1114/tmux.sock`；格子裡跑的程式前面接 `aos-asuser sub:5 --`。腳本是 `e3.sh`，輸出在 `e3.out`。結束後收掉 server：記下的 pid 是 738772，kill 前先確認它的 cwd。

| 看什麼 | 結果 |
|---|---|
| 格子裡的身分 | `id -u` 印 `5`。在 ns 裡看到的是 5，外面看是 100004 |
| 打字、`capture-pane` | 正常 |
| tty | `/dev/pts/6` 的擁有者仍是 1000、模式 620；用繼承來的 fd 照常讀寫 |
| 改視窗大小 | `stty size` 從 30×120 變成 20×100，跟著變 |
| 格子裡的程式去連 tmux socket | `Permission denied`：控制不了別的格子，也開不了新畫面 |

**這件事的意思**：fable 說「畫面接法不變，只有格子裡的指令前面多接一段」，這點成立。另外要知道：程式在 ns 裡看到的 uid 是 N，不是真號。寫 log、比對 uid 的工具不能拿「自己看到的 uid」當真號。

## 六、給使用者拍板的題（定稿）

**Q4（改寫）要不要讓內圈（LLM kernel、daemon）看請求信的 Linux 擁有者，拿它當寄件人記帳？**
1. **要，只在內圈看、只當「最後一站是誰」**（推薦）——LLM 額度冒不了名（B3）。前提是收件那頭沒有別人能寫（Q10 選 1 最穩）。它**不能**拿來驗專區回信：收件人能原地改寫信、st_uid 不變（E7c），那一塊等 L2 簽章（第 4 期）。
2. 不要——完全照 P1 字面，額度繼續靠信封 sender。

**Q9（改寫）樹在家目錄底下、家目錄是 700，subuid 走不進去，怎麼辦？**
1. **換 uid 的同時開一個私有 mount ns，把樹（或它的工作區與 stack）綁到 agent 看得到的地方**（推薦）——家目錄不動、維持 700。E10 實測：讀寫得到樹，碰不到家目錄的點檔，`..` 逃不出去，自己 umount 不掉。代價：agent 看到的路徑跟外面不同，要讓路徑一樣得再做 E11；daemon 換 uid 的那段程式多一步。
2. 樹搬到家目錄外（例如 `/srv/aos-<使用者>`）——最直白；代價是要搬家、改所有路徑，等於改安裝。
3. ~~在家目錄給群組 `--x`~~——**不採**：subuid 會透過 other 位讀到家目錄裡所有 644 的檔（Argon A1）。

**Q10（新；與使用者 11-14 指示衝突，待定）信要不要從「一封一個夾」改成「一封一個檔」？**
> **與使用者 11-14 指示衝突，待定**：使用者 11-14 對 ok-board 說過「不要修改到aos-post這個基礎程式」，Q10 選 1 會改 aos-post 的信件格式。頂層會連這個衝突一起問使用者；答覆之前，第 2 期 2d 先照選項 2（不改格式、壞信由 daemon `--fix` 後隔離）規劃。

1. **改成一個檔，信箱的預設 ACL 只給收件人和使用者唯讀**（推薦）——刪檔只看父夾，毒信一定刪得掉；收件人改不了信，st_uid 就算數；建信箱也不用跨 ns chown（E7b、E7c）。代價：要改 aos-post 的信件格式與所有讀信的程式；有附件的信要另外想法子（例如附件另放、信裡寫路徑）。照「不遷移舊版」，舊信直接重建。
2. 不改格式，遇到壞信由 daemon `--fix` 後隔離——程式改得少；代價是毒信還做得出來、st_uid 不能當寄件人，跨 ns chown 也要留著。

**Q11（新）aos-sandbox 的設定檔壞了，現在是「警告、不套沙箱、照跑」。要改嗎？**
1. **只在換了 uid 的 agent 呼叫時（或 `security: on` 時）改成拒起**（推薦）——安全模式下不會默默裸跑；平常的用法不變。
2. 一律改成拒起——最一致（跟 P6「不能默默退回」同脾氣）；代價是改到現在的用法，要排在發佈版之後。
3. 不改。
