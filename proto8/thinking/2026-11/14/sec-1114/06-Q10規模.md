## 三、為什麼算大：有兩處語意改變，不只是「夾變檔」

1. **附件**。N-16 寫「信是一個夾，其他檔隨意」，aos-post 有 `SendOpts::files` 把檔附進信裡。改成單檔，附件就沒地方放，只能改成「附件另放、信裡寫路徑」。這是格式語意的改變。附件另放還會在跨 uid 時帶出另一個問題：附件誰擁有、誰能讀。
2. **LLM kernel 的同步請求靠信夾裡的鎖檔**。`aos-llm` 的 `send_held` 在信夾裡放 `sender.flock`，寄信人活著就一直鎖著。kernel 的 `sweep()` 看這把鎖判斷寄信人還在不在，不在就收掉那封信（`serve.cpp:85–110`）。單檔信放不了第二個檔。可以改成鎖信檔本身（flock 跟著 inode 走，rename 進 cur/ 也還在），但這要把 LLM kernel 的「寄信人還活著嗎」整套重寫，C++ 和 Python 兩份都要改。

再加上讀信端分散在 7 個元件（C++ 和 Python 都有），還有 ok-board 剛定稿、照「夾」設計的 comm/1。這不符合「aos-post 只動局部、讀信端改動少且機械」，所以算大。

## 四、舊信怎麼辦

照 proto8「不做遷移」：換版時各信箱的 `new/`、`cur/` 要清空或重建。信箱裡的信，寄信人收不到回信就會重寄，大多沒事。要小心的是：
- daemon 的 `cur/` 殘骸本來會重做，舊夾會被當壞信；
- 專區的 `rejected/` 和使用者還沒回的信，要使用者自己決定留不留。

## 五、選項與推薦

1. **先不做**（推薦）。第 2 期（可選、預設關）照 03 計劃的選項 2：不改格式，壞信由 daemon `aos-asuser --fix` 後移到隔離夾（E7 已實測 `--fix` 救得回毒信）。等到第 3 期（`security: on`，排在公開 demo 之後）要開跨 uid 信箱之前，再跟管 aos-post 的線和 ok-board 一起議。那時 comm/1 已經施工，讀信端可以一次改齊。
   - 代價：第 2 期毒信還做得出來，st_uid 不能當寄件人（Q4 照樣只當「最後一站」用，前提照舊）。
2. 現在就做。照第二節逐一改，附件改成「另放＋路徑」，LLM kernel 改鎖信檔本身。要跟 ok-board 協調，請它把 comm/1 C1 改成讀檔。
   - 代價：動到 aos-post、aos-llm、aos-llm-kernel、kernel_llm、gate、aos-mailbox 和 wf/tools，大約一整條線的工作。

折衷（不推薦）：兩種格式並存，只有跨 uid 的信箱用單檔。這樣每個讀信端都要認兩種格式，比直接改更亂。
