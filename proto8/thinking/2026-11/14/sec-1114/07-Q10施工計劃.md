## 〇、比 06 多查到的兩件事

1. **LLM kernel 把 `cur/<信名>/` 當成工作目錄。** 認領後，kernel 在信夾裡寫 `request.json`，endpoint 的 stack 和 cwd 就設在信夾（`aos-llm-kernel/src/serve/serve.cpp:205`、`proc.cpp:111`）。進度也放在信夾裡：`proc.json`、`state.json`、`reply.json`、`stderr.txt`、`reply_letter.txt`（`proc.cpp:173,241,281`、`reply.cpp:63`）。N-66 把這寫成了規範（`08-N-66.md:7`）。agent-fsm 的 `wait.py:248` 也去讀 `requests/cur/<信名>/stderr.txt`。所以單檔化不只換掉信封，**還要替 kernel 另開工作目錄**。
2. **附件功能其實沒人在用。** `SendOpts::files` 找不到呼叫者，CLI 也沒有附檔旗標（sol-5 B）。`send_prepared` 唯一的呼叫者是 aos-llm 的 `send_held`，它的 callback 只用來建 `sender.flock`。

## 一、新格式（定案點，請 Argon 重點看）

| 項目 | 現在 | 改成 |
|---|---|---|
| 一封信 | `<格>/<信名>/letter.json`（夾） | `<格>/<信名>`：一個一般檔，**檔名就是信名，不加副檔名**，內容是原本的 letter.json，信封欄位一個不改 |
| 寄（佔名） | `mkdir tmp/<名>`，撞名換一個名字 | `open(tmp/<名>, O_CREAT\|O_EXCL\|O_WRONLY, 0666)`，撞名換一個名字；直接寫在這個 fd 上，不另做暫存改名，因為 tmp/ 沒有讀者 |
| 投遞、認領、歸檔、撤信 | `rename` 夾；目標已有非空夾時失敗（`ENOTEMPTY`），這就是 `LetterExists` 的來源 | C++ 一律用 `renameat2(..., RENAME_NOREPLACE)`。檔案系統不支援（`EINVAL`）時，退回 `link` 再 `unlink`。目標已存在＝`EEXIST`，跟原本的語意一樣 |
| 有序投遞 | `new/<12 位序號>.<名>` 夾 | 同名的檔，鎖和 `order.json` 都不變 |
| 附件 | 信夾裡「其他檔隨意」（N-16、P-13） | **拿掉**：刪 `SendOpts::files` 和複製迴圈。慣例改成「附件另放，body 寫絕對路徑」，信封不加欄位 |
| 壞信 | `letter.json` 讀不到或不是 JSON | 另加一條：格子裡的項目是資料夾（舊版信）＝壞信，原因寫 `old folder letter (proto8 does not migrate)`。`done` 照樣丟掉，丟法依類型分：檔用 `unlink`，夾用 `remove_tree` |
| `names_in`、排序 | 列出非隱藏項目 | 不變（本來就不分檔或夾） |

Python 端認領（`daemon_ctl._claim`、ok-board C1）照舊用 `os.rename`。對檔案而言，`os.rename` 會蓋掉同名目標；但信名是奈秒加 pid，cur/ 有同名檔本來就是異常。兩人搶同一封時，後到的會拿到 `ENOENT`，跟夾的情形一樣。這點寫進 N-16 備註，不另做輔助函式。

## 二、LLM kernel（最大的一塊）

### 2a 寄信人鎖：改成鎖信檔本身

- **aos-llm `send_held`**：
  1. `open(tmp/.<id>, O_CREAT|O_EXCL|O_RDWR|O_CLOEXEC, 0666)`。
  2. 馬上 `flock(LOCK_EX)`。
  3. 寫信封＋body，信封多一個鍵 `"held": true`。aos-post 的 `why_bad` 不擋多出來的鍵（`take.cpp:67-95`）。
  4. `renameat2` 進 `new/<id>`。
  5. fd 一直不關，持有到行程結束（跟現在一樣）。flock 綁在 inode 上，rename 進 new/、cur/ 後鎖都還在。
- **kernel**：
  - `has_sender(信)` 改成「信封有 `held: true`」。
  - `sender_alive(信)` 改成對信檔本身試 `LOCK_SH|LOCK_NB`，被 `EWOULDBLOCK` 擋住才算還活著。這跟現有判法相同，只是對象從 `sender.flock` 換成信檔（`letter.cpp:38,49`）。
  - 唯讀開檔也能 flock，E8 測過。
- **sweep 裡「正在寫」的規則**：tmp/ 裡點開頭的檔，如果讀不成 JSON（空檔或寫到一半），就跳過，對應現在「點開頭、還沒有 letter.json＝跳過」（`serve.cpp:97`）。讀得成 JSON、有 `held`、又沒人鎖著，就刪掉。
- `aos-post::send_prepared` 的介面改成：callback 拿到已開好的 fd 和 tmp 路徑，寫信封仍由 aos-post 做。aos-llm 的 `hold_sender` 改成在這個 fd 上 flock，並把 fd 留著。

### 2b 工作目錄：搬到信箱的新格 `work/`

- 信箱多一格 **`<信箱>/work/<信名>/`**，只有 kernel 會建它；aos-post 的 `init` 不建，因為一般信箱用不到。
- 認領：`new/<名>` → `cur/<名>`（檔），接著 `mkdir work/<名>/`，寫 `request.json`。endpoint 的 stack 和 cwd 改成 `work/<名>/`。
- 回復（kernel 重啟後掃 cur/）：
  - `work/<名>/proc.json` 在＝追蹤；
  - 只有 `reply.json`＝補寄；
  - 兩個都沒有＝把信搬回 new/，並清掉 `work/<名>/`。
  - 對照現有 `proc.cpp:278`，判斷位置從信夾換成 work/。
- 收尾：寄出回信，把 `reply_letter.txt` 寫進 work/，接著先刪 `cur/<名>`，再刪 `work/<名>/`。
  - 死在兩步之間會留下沒有信的 work/。kernel 每拍掃一次 work/：`cur/<名>` 不在、也沒有正在跑的 proc，就清掉。
- N-66 的「執行 stack／進度窗＝`cur/<信名>/`」改成 `work/<信名>/`。agent-fsm 的 `wait.py:246-248` 改讀 `requests/work/<信名>/stderr.txt`。
- C++（`impls/aos-llm-kernel`）和 Python 雙胞胎（`lib/aos/kernel_llm/llm_rules.py`，以及共用的 `lib/aos/kernel/runner.py` job 目錄）兩份同改，測試也成對改。

### 2c 回信端

- aos-llm `wait.cpp:36,49` 改讀檔。
- 撤信本來是 `remove_all`，改成 `unlink`（`wait.cpp:148`）。

## 五、怎麼上：整包在換樹那一刻上

- repo＝活樹，Python 一 commit 就生效；C++ 要等換樹 build 才生效。**新舊格式不能混用**：舊 aos-post 寫的夾，新的 Python 讀信端讀不到。所以**不能分批 commit 到 main**。
- 做法：
  1. 施工在 `~/code/sec-1114/q10/`：從 `git archive <main 最新>` 解出，裡面另起本機 git，一個元件一個 commit，方便看。
  2. 全套測試在這份乾淨複本上跑。
  3. 換樹前，在最新的 main 上重做一次：rebase，或者重套 patch；ok-misc、ok-llmk2 等線這段時間可能動到相同的檔。
  4. 再跑一次全套測試，交給 ok-kf 的換樹步驟表。
  5. 換樹當下依序做：停 daemon → commit（問過 repo-aos）→ build C++ → **清空並重建所有信箱的 new/、cur/、archive/、work/**（proto8 不遷移）→ 同時換上 `aos-user verify` → 起 daemon。
- 清信箱前，先列出各信箱還在 new/、cur/ 的信，由頂層決定要不要先讀完。專區的 `rejected/` 和使用者還沒回的信，由使用者決定。
