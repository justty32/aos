## 結論

- **比喻**：機制用「配給＋排程」（像 cgroup：保底、上限、優先級，父格圈住子孫），帳用預算的話講，頁面照舊叫「電力」。電力不貼合三處：模型有品質等級、Claude 有週上限、訂閱不按量計價。內部市場不做。
- **實體**：一份配額表 `plan.json`（部門樹）＋現有 llm kernel 站加一層「樹狀額度」（每拍讀表、查部門、補／夾 priority、沿祖先鏈用「已用＋在飛」判放行，超了回 `BudgetMissing`，agent 那邊 AK17 冷卻與 `brain_notify` 全沿用）＋站外一支不經模型的 `aos-llm-quota`（驗表、改表、報表、每日結算）。
- **部門樹是記帳樹、不是路由樹**：agent 照舊直寄供應站；改組＝改表。`llm_forward` 串站只在要實體隔離時用。
- **分配**：上限可超賣、保底不准超賣；保底只寫在葉格，主管另有 `self_reserve`；放行式見 [03 §3.1](llmk2-1114/03-計劃.md#31-放行判準)（Argon 審出兩個多層漏洞後改過，模擬驗過）。
- **最大盲區**：多數 llm 呼叫（Claude eca、fable、Argon）根本不經 llm kernel，而最緊的正是 Claude 週額度。v1 就接「Claude 電表」：唯讀 Claude Code 本機紀錄的 usage 與 cwd，按工作區歸部門，兩個帳號分兩池，標 `observed`；派工閘等量準了再說。
- **第一版**：表與驗表、站內樹狀額度（repo 外暫存樹）、報表（gpt 站帳＋Claude 電表）；只有次數是硬上限，不做降級、不做點數、不接活樹。交給使用者看的是兩張表：「昨天誰燒多少 gpt」「本週各線 Claude token」。
- **方向題已裁**：8 題（比喻名字、層數、分配方式、Claude 處理深度與帳號顯示、誰能調、沒列名 sender、何時施工、改組時已燒的量算誰）**全照預設**，見 [03 §9](llmk2-1114/03-計劃.md#9-要使用者拍板的方向題)。施工等 ok-release 收線後再開（第 7 題）。
