## 先講結論

- 兩邊的 `wf/` 是同一套骨架長出來的（skyrim 戳 v0.6、aos 戳 v0.5），團隊三層、context 管理、逐模型指揮心得、交接書六條、WAIT_USER 分類表這些 **aos 本來就有同一份**。所以真正能借的不多，集中在三處：**交接書多出來的幾欄、「任務類型→必用工具」那張表、領導往上轉信的三條規矩**。
- 對 aos 本體最有參考價值的不是 skyrim 的信箱機制（aos 11-13 才把同一套撤掉、換成 stack mailbox），而是它**用了三個月撞出來的事故**：終局回報該自動往上游走、「看過／通知過／辦完」是三件事、看不出一條線是卡住還是在寫、配額往下派不該逐層倍增。這幾條 aos 現在的 mailbox、subagent、`ctl ls` 都還沒有對應。
- skyrim 11-05 起的「過時即刪、不留 archive」跟 aos 的規矩相反（aos 刪檔要使用者說），列在不適用。wf-lint 使用者 11-13 已說整支刪掉，凡是靠它落實的檢查都不建議搬回來，只借它查的那條規矩本身。

下面路徑：`S/`＝`~/repo/moddings/skyrim/`，`A/`＝`~/repo/aos/`，`K/`＝`~/aos-home/knowledge/aos/`。「出處」是我或隊員實際讀過的檔；細節在蒐集檔。

## 一、可直接抄的 wf 慣例

改的都是 `A/wf/` 的文件，屬「直接做、不用問」那一類；這裡只列方向，誰改、何時改由頂層排。

### 1. 領導往上轉信的三條規矩

- **skyrim**：`S/agentctl/tools/agent_inbox/PROTOCOL/wake-policy.md`「領導轉發的三條規矩」——重寫標題（寫你的判斷，不是工人原話）、附上你已經排除的可能、標明你要什麼（裁決／資源／只是報備，寫在標題裡）。
- **aos 現況**：11-14 剛設小廝 xiaosi 分流，頂層通知只說「title 要一眼看得出輕重」。`A/wf/workflows/dispatch/aos-teams/04-進度回報.md` 管看板，沒有管信怎麼往上轉。
- **值不值得**：值得，而且正好用得上。xiaosi 每 20 分鐘彙整、要緊的立刻轉，本質就是 skyrim 的領導層；三條規矩一字不改就能套。
- **怎麼借**：寫進 ok-* 回報與 xiaosi 轉信的規矩裡（07「11-14 補」或 inbox.json 的樹內那段）。

### 2. 交接書多出來的四欄

- **skyrim**：`S/agentctl/templates/BRIEF.md`、`S/agentctl/docs/driving-codex/handoff-contract.md`。aos 範本沒有的四樣：
  - **子 agent 數量上限必填**（可填 0），往下派要「分配並傳遞本線總配額，不逐層倍增」。
  - **失敗分兩路**：實際跑出錯結果→照指定方式回滾本線、回 `FAILED`；根本沒跑成、沒證據→不回滾、保持現狀、回 `BLOCKED`、寫解除條件，「不拿舊 log 冒新證據」。
  - **錯誤來源分流**：工具或環境壞→`BLOCKED`；自己寫的臨時腳本錯→自己修，不算阻塞。
  - **REPORT 末尾固定一段「以後交接書該點名的工具」**（工具＋用途＋何時用；沒有就寫無）。
- **aos 現況**：`A/wf/workflows/TEMPLATE.handoff.md`（2.6 KB）有單一目標、硬限制、絕對交付路徑、固定驗收；沒有上面四樣。`A/wf/workflows/dispatch/aos-teams.md` 還寫著隊員「無上限派子 agent」。
- **值不值得**：值得。失敗兩路最實用（aos 的線回 BLOCKED 還是 FAILED 目前靠各自理解）；子 agent 上限跟第二類第 4 條是同一件事的文件面。
- **怎麼借**：TEMPLATE.handoff 加這四欄。「無上限」那句是使用者 11-06 原話，不動它，只在範本裡讓每張任務書自己填數字（填「不限」也是填）。

### 3. 「任務類型 → 必用工具」表，交接書從表上抄

- **skyrim**：`S/agentctl/docs/tool-index.md`。開頭一句是理由：「沒被交接書點名的工具就沒人用」。表四欄：任務類型｜必用工具｜用途｜狀態（現役＝有測試有人用過；新＝有測試還沒實跑）。BRIEF 的「必用工具」段從這張表抄，配上面第 2 條 REPORT 末尾那段回填，形成一個小循環。母 repo 的 AGENTS 只放一行指標。
- **aos 現況**：`A/wf/knowledge/code-map.json` 是「哪個檔負責什麼」，照檔排；知識庫 `K/` 是照工具排。沒有一張「我要做某件事→該用哪支」的表。今天各條 ok-* 線各自摸索「怎麼掛一隻 sol 的 agent-fsm」（07 的待補三條還空著），就是這張表缺的那一列。
- **值不值得**：值得。成本低（一張 md 導航表），直接減少重複摸索。
- **怎麼借**：在 `A/wf/` 放一張同形狀的表，先收今天各線已經摸出來的幾列（掛 gpt 的 agent-fsm、設 prlimit、開 kernel_gate、看腦用量 ledger、清環境起暫存樹）。skyrim 那支檢查表中路徑還在不在的腳本不必搬。

### 4. 活狀態檔寫明大小預算

- **skyrim**：`S/agentctl/handoffs/README.md`「保留期」——根 `SESSION-LOG.md` ≤ 2 KB 只列 open、每場 `STATE.md` ≤ 8 KB 只寫本場不抄前場、`NEXT-SESSION.md` ≤ 4 KB。理由見 `S/wf/workflows/decisions.md` 11-05 使用者說要瘦身。
- **aos 現況**：`A/wf/STRUCTURE.md` 有一般的 8 KB 門檻與「只列 open」，但沒有給這幾份每場必讀的檔個別數字；`A/wf/SESSION-LOG.md` 現在 17 KB，而它是每個 session 開場必讀。
- **值不值得**：數字本身值得（每隻 agent 開場都付這筆 token，見 03 的用量）；skyrim 靠 wf-lint 報超標那半不借。
- **怎麼借**：在 SESSION-LOG 檔頭或 STRUCTURE 寫一個預算數字當「該收斂了」的訊號，由寫的人自己看。

### 5. 交棒與接手的兩個動作

- **skyrim**：`S/agentctl/docs/driving-codex/monitoring.md`——「領導交棒時，線會空轉」：某次第二棒接手才發現四條線有兩條空轉、一道指令根本沒送出。定的規矩：交棒書列每條線的確切狀態與下一步；**接手第一件事是逐線巡視，不假設它們仍在跑**。同檔另一條「禁區措辭不可變成收線條件」：寫「你不可以寫 X」，不要寫成 X 必須是某狀態，曾有三條線把禁區讀成結案條件。
- **aos 現況**：`A/wf/workflows/dispatch/README.md`「管理者休眠前的自檢」有交棒要寫誰在跑、卡在哪；沒有「接手先巡」。禁區那條沒找到。
- **值不值得**：值得。今天多隻 ok-* 互相交棒正是這個情境；我接手時前任的暫存樹有沒有停乾淨，就是照交棒書去對了一次才確定。
- **怎麼借**：dispatch README 的自檢段與 lessons 各加一句。

### 6. 驗收的兩條補充

- **skyrim**：`S/agentctl/docs/team-model/roles.md`「工人」——要兩份獨立意見時換不同工具、資料來源或模型體系，「兩份同模型對話不能算完整交叉佐證」；`monitoring.md`——「結構驗收過了不等於內容正確」，某次筆數、結構全過，換一種來源抽內容才抓到幾百欄殘缺譯文。
- **aos 現況**：dispatch README 有「逐條對證據，不對自我宣告」；這兩條更細的沒找到。
- **值不值得**：值得，各一句話。這次我讓 astra 抽查 sol 的報告，就是「換模型體系覆核」的用法（結果見 03）。
- **怎麼借**：加進 dispatch「多信任它、但收線對證據」那段。

### 7. 開場一次講完編制與資源的範本（可有可無）

- **skyrim**：`S/agentctl/docs/session-goal-template.md`——使用者每場開場貼的一段：幾隊、每隊幾隻、能不能用鍵鼠螢幕、網路、幾點收尾。
- **aos 現況**：這些散在 aos-teams 與 07 的原話裡，每場由使用者口頭補。
- **值不值得**：普通。aos 的編制現在一天改好幾次，範本很快過時；等隊形穩了再說。

## 二、可當 aos 功能參考的

這一類是「skyrim 用腳本和文件硬撐出來、aos 可以在體系裡做對」的東西。都只是參考方向，要不要做是使用者與規劃線的事。

### 1. 終局回報自動往上游走，工人不必知道上游叫什麼

- **skyrim**：`S/agentctl/tools/agent_inbox/PROTOCOL.md`「收件人模型」、`inbox_send.sh`。工人只下「回報」，腳本照 `teams/<隊>/members` 第一行決定寄給誰；改上游只改名冊一處。當初加這層的理由（`wake-policy.md`）：工人的細節全灌給頂層，頂層被每一則吵醒。
- **aos 現況**：`mailbox_send` 要自己寫 `to`。今天「回報改寄 xiaosi、不要寄 repo-aos」是頂層對每隻 ok-* 各發一則通知，每隻自己記；我的隊員則是寫死在任務書裡。
- **值不值得**：值得參考。aos 其實已經有上游的資料：`subagent` 掛的隊員有 owner，`AOS_KERNEL` 指向上面那個 gate。「回報給我的上游」可以從這些推出來，不必再維護一份名冊。
- **方向**：`mailbox_send` 多一種收件寫法（例如「我的上游」），由體系解析成現在該收的那一格；分流（像 xiaosi）變成上游那邊的設定，不是每個寄件人的知識。

### 2. 「看過摘要／通知過／辦完」是三件事

- **skyrim**：`inbox_poll.sh`（看過摘要、記在 `.state/poll/`）、`notify_watch.sh`（通知過）、`inbox_ack.sh`（辦完，在 STATE 記一行、原信移走）。ack 工具是事後補的，檔頭自述之前手工搬信做了約 95 輪。
- **aos 現況**：`K/mailbox.json`——`mailbox_peek` 不拿走，`mailbox_read` 讀了預設就刪；`mail_notify` 有 notified 記錄。也就是有「通知過」和「讀了」，沒有「接了還沒辦完」。
- **值不值得**：值得參考。agent 讀完信被 compact 或換手，那封 REQUEST 就只剩對話裡的記憶；規矩說「接了事就得回終局狀態」，但體系查不出誰欠誰一封回信。
- **方向**：信多一個「已接、未結」的位置或記號，回了終局信才消掉；`self_state` 的 mailbox 那格能列出自己欠的回信。

### 3. 一眼看出一條線是在寫、在等、還是卡住

- **skyrim**：`S/agentctl/tools/cx_watch.sh`——不信畫面上的字（註解寫 Working 可能只是死掉的舊畫面），改看行程樹有沒有活的子行程；另抓批准提示字樣、畫面 900 秒沒變算停滯；各種情況各一個退出碼；等的人把它丟背景，行程結束就是被叫醒。
- **aos 現況**：`agents_ctl ls` 幾乎永遠是 `running`。這次我要分辨隊員狀態，得自己去讀它 stack 的 `stage.txt`、`history.jsonl` 的修改時間、llm kernel 的 `requests/cur`（03 第 3 條）。前任在交棒裡記了同一件事。
- **值不值得**：很值得，兩任隊長都撞到。資料 aos 都有，只是沒有攤在一個地方。
- **方向**：`ls --long` 或 `subagent state` 把「現在在哪一格、上次 history 動是幾秒前、有沒有一封腦的信在排隊或在跑」列出來；再往前一步是一個「等到某隻停下或停滯就回來」的原語。

### 4. 配額往下派時是分配，不是每層各有一份

- **skyrim**：`S/agentctl/docs/team-model.md`「現行派工基準」——每線必寫子 agent 上限，「往下派須分配並傳遞本線總配額，不逐層倍增」；外部程序數與同程序子 agent 分開算。
- **aos 現況**：`subagents.json` 的 `max_subagents`（預設 4）是每隻 agent 各有一份，三層就是 4×4×4；腦的預算照寄件 stack 各算各的（`K/brain.json`）。kernel 站有 `max_running`，但只管經過它的請求，而 `subagent add` 不經門（今天線星階段 0.4 實測）。
- **值不值得**：值得參考，這是「kernel 管資源」主線本來就要回答的題；skyrim 的答案是「配額是一筆從上面傳下來、可以切給下面的額度」。
- **方向**：留給 kernel-limits／any-resource-os 那幾條線當一個現成的需求寫法。

### 5. 獨佔資源的鎖：owner 要完全相符、鎖序固定、沒有自動過期

- **skyrim**：`S/agentctl/docs/resource-locks.md`、`tools/lock.sh`——兩把 mkdir 鎖（桌面輸入、遊戲），鎖序固定先桌面後遊戲、反序就死鎖；放鎖要 owner 完全相符；刻意沒有 TTL，孤兒鎖由人判斷後收；CPU 不用鎖、用限流，而且「按行程樹限流，不要按名稱」。
- **aos 現況**：kernel 站管的是可數的名額（slots、max_running、budget）；`A/wf/workflows/resources.md` 是文件約定。獨佔型資源（一個 GUI、一台實機、一棵活樹的停機時段）目前沒有體系內的表示。
- **值不值得**：當參考。aos 目前最接近的獨佔資源是活樹本身（停樹換檔）與 git index（下一條）。
- **方向**：給 any-resource-os 當一個例子——獨佔資源也是一種向 kernel 要的東西，名額為 1、帶 owner、多把時有固定順序。

### 6. commit 收工工具擋「index 裡有別人的暫存」

- **skyrim**：`S/agentctl/tools/wrap.py`、`wrap_git.py` 的 `guard_index()`——只收明確點名的檔；index 裡有清單以外的暫存改動就停，訊息是「可能是別隊的；先處理再收工（不替別人 commit）」；推之前先 fetch，遠端領先就全停。
- **aos 現況**：11-14 當天已啟用 `A/wf/tools/commit-request`（排隊、claim 擋衝突、在乾淨副本上組 commit，`A/proto8/thinking/2026-11/14/commit-queue-1114.md`），它的測試 T2 就是「共用 index 裡有別人 staged 的檔不會被帶進去」。
- **值不值得**：aos 已經做得比 skyrim 完整（skyrim 是發現就停、叫人處理；aos 是根本不經過共用 index）。不用借。
- **方向**：無；列在這裡只是說明這題兩邊都撞到、aos 的解法更徹底。

### 7. 指示是「下一步的補充」，不是剎車

- **skyrim**：`S/wf/lessons/dispatch-cli-agents.md`（09-25）——一道「不要降版、還原」的指示寫進 orders 時，那條線已經做完最後一個 commit，下一步才讀到。定論：orders 是下一步的補充，緊急要直接中斷 session。
- **aos 現況**：`subagent say` 同樣排在 queue、等這一輪結束才進對話（前任與我都遇到）；aos 另有 `pause`、`sleep` 可以真的停。語意其實一樣，只是沒寫出來。
- **值不值得**：值得寫一句進知識庫，讓隊長知道 `say` 不是剎車、要停用 `sleep`。功能面不缺東西。
