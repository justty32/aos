# 信箱查證：收件目標須明填；親子帳在父端；讀信不是接案；pause 與 sleep 不同

結論：第 1 題成立；第 2、3、4 題部分成立。關鍵差別是「父端知道自己掛了誰」不等於「子端有 owner」，控制請求的 AOS_KERNEL 也不等於工作回報收件人；pause 不會中斷正在跑的格。以下只據原始碼判讀，沒有執行程式或測試。

來源路徑均相對 `/home/lorkhan/repo/aos/`；行號是本次讀取的工作樹版本。查證對象為 `proto8/thinking/2026-11/14/skyrim-agentctl/02-借鑑清單.md`「二、可當 aos 功能參考的」第 1、2、7 項；結論的程式證據列在各節。

## 1. mailbox_send 須填 to 或 box，沒有「我的上游」寫法

判定：成立。

證據：

- `proto8/lib/agent/mailbox_send/_entry:40` 先取必填內容：`tool_io.arguments("status", "title", "what")`；第 41 行要求 to、box 恰有一個非空值：`if bool(args.get("to")) == bool(args.get("box")):`，否則報 `give to ... or box ... one of them`。第 45 行把這兩欄直接轉成 `--to`、`--box`，沒有上游解析分支。
- `proto8/lib/agent/mailbox_send/_tooldef.json:24` 的 to 描述是 `the agent's name`；box 是信箱資料夾，in_reply_to 是正在回答的信名。參數沒有 parent、owner 或 upstream 欄。
- `proto8/cmd/aos-mailbox/aos_mailbox/__init__.py:310` 的 `target_box` 同樣只分兩路：box 檢查資料夾佈局；to 用 `row = dc.row_of(d, to)` 找 daemon 表上的名字。沒有保留字「上游」或自動挑父 agent。
- `proto8/lib/agent/mailbox_call.py:36` 明寫：`Answer with mailbox_send to the letter's reply_to (box) and in_reply_to (letter).` 回原信可以用信封提供的路徑，不必知道對方名字，但仍須由呼叫者填入。

隊長那句可改為：

> mailbox_send 必須明填收件 agent 的 to，或信箱路徑 box；回信可填原信的 reply_to 與 in_reply_to。目前沒有「寄給我的上游」這種收件語法。

依據：本節 `_entry:41`、`target_box:310`、`mailbox_call.py:36`。

## 2. subagent 有親子資料，但不是子端 owner；AOS_KERNEL 不會自動指向掛它的人

判定：部分成立。「有親子資料」成立；「隊員自己有 owner、AOS_KERNEL 自動代表工作上游」不成立。

證據：

- `proto8/lib/agent/subagent/_entry:18` 記帳規則原文：`$AOS_STACK/subagents.json`，此處 AOS_STACK 是父 agent 的 `tools/subagent/` 小格。第 194 行實際建立 `{"name": name, "stack": ...}` 或 `{"name": name, "queued_letter": ...}`，第 195 行寫回父端帳本。這是父端的「我掛了誰」，不是寫進子 stack 的「誰掛了我」。
- `proto8/cmd/aos-agent/aos_agent/ctl/state.py:185` 同樣從父端讀帳：`book = os.path.join(a.stack, "tools", "subagent", "subagents.json")`。查到的是子清單，沒有反向 owner 欄。
- `proto8/py/daemon_ctl/entry.py:340` 掛子信回傳 `{"procs_added": {name: spec}}`；此函式完整建 spec 的流程只有入口、def、ws、stack、limits、envs 包裝等，沒有自動加掛載者欄。`proto8/impls/aos-daemon/src/child/child.cpp:254` 的整個 `row()` 產生 daemon 子項列，也沒有 owner／parent 欄。
- `proto8/impls/aos-daemon/src/child/child.cpp:65` 啟動子行程時設 `AOS_STACK`，第 66 行設 `AOS_DAEMON`，有 ws 才設 `AOS_WS`。沒有把「發出 add 的 agent」或它的 gate 填到環境。子行程由 daemon fork，不是由提出請求的父 agent fork。
- `proto8/lib/agent/agents_cmd.py:229` 只取呼叫者提供的 `envs = args.get("envs", {})`，再轉 `--envs`；`proto8/py/daemon_ctl/entry.py:305` 寫 `spec["exec"]["envs"] = dict(envs)`。因此可明傳 AOS_KERNEL，但 subagent 不會自行算出它。
- `proto8/impls/aos-exec/src/inst/lib_input.cpp:7` 原文含 `envs 有東西＝現有環境` 與 `沒有＝傳 NULL 沿用`。子程式可能繼承 daemon 已有的 AOS_KERNEL，也可能被 envs 或定義設定改掉；不是每隻必有，更不保證等於掛載者的 gate。
- `proto8/py/daemon_ctl/post.py:29` 的 `mailbox_of` 在設了 AOS_KERNEL 且非 direct 時，把控制信寄到該信箱；`proto8/lib/agent/kernel_gate/_entry:106` 明說：`A sender uses it by setting AOS_KERNEL to that path`。它是控制請求入口，不是終局工作回報的路由。
- `proto8/impls/aos-daemon/src/daemon/daemon.cpp:159` 確有 `parent_ = std::string(inherited)`，但 inherited 是 daemon 啟動時的 AOS_DAEMON；`proto8/impls/aos-daemon/src/daemon/windows.cpp:220` 把它放在整張表的 `doc["daemon"]`。這是 daemon 層的上一層資料，不是某個 subagent 的建立者。

隊長那句可改為：

> subagent 在掛載者自己的工具帳本記錄子 agent 名字與 stack；目前這條建立路徑不會在子項列或子 stack 自動寫 owner／parent。子項有 AOS_DAEMON 指向啟動它的 daemon；AOS_KERNEL 可繼承或明傳，代表控制請求入口，不能直接當作工作回報上游。

依據：本節 `_entry:194`、`child.cpp:65`、`agents_cmd.py:229`、`post.py:29`。

## 3. 讀信、留底、通知都有；一般工作信沒有接案未結帳

判定：部分成立。一般 agent mailbox 的說法成立；若擴成整個 aos 完全不用 in_reply_to 對帳，就不成立。

證據：

- `proto8/cmd/aos-mailbox/aos_mailbox/__init__.py:208` 的 peek 只列 `new = os.path.join(my_box(False), "new")`，讀取 letter.json 後印摘要，沒有 take 或 done。它不拿走信，也不涵蓋中斷讀信後留在 cur/ 的信。
- `proto8/lib/agent/mailbox_read/_entry:39` 將 keep 字串轉成 `--keep-to`，keep 為 true 轉成 `--keep`。`proto8/cmd/aos-mailbox/aos_mailbox/__init__.py:277` 設 `done = ["done"] + (["--keep"] if opts.get("keep") else [])`；先讀 cur/ 殘留，否則 take，印出後第 303 行直接 `post(*(done + [box, name]), ...)`，沒有等到任務結束才 done。
- `proto8/impls/aos-post/src/take/take.cpp:125` 的 done 在 keep 且信封有效時執行 `make_dir(mb.archive())`、搬到 archive；預設搬到 tmp 再 `drop(t)`。所以 keep:true 是留底，不是留在待辦位置。
- `proto8/cmd/aos-mailbox/aos_mailbox/__init__.py:295` 的 `keep_line(..., "received")` 在印出與 done 前寫入工作區檔案；寫失敗讓該信留在 cur/。留底欄是 received／sent，完整 read／send 流程沒有 accepted／未結案帳。寄信的 keep 也只是 JSONL 留底。
- `proto8/lib/agent/mail_notify/_entry:34` 設 `SEEN = "notified.json"`；第 110 行比對未見信名，第 115 行把提醒寄進自己的 queue，寄成後更新記錄；第 117 行 `keep = sorted(r["letter"] for r in rows)` 只保留仍在信箱 new/ 的信名。它記通知去重，不記工作完成；第 107 行的全新 agent 首次啟動分支還可能只記成已知而不提醒。
- `proto8/cmd/aos-agent/aos_agent/ctl/state.py:172` 的 `part_mailbox` 只呼叫 `peek --json`，第 178 行輸出 `{"waiting": len(rows), "letters": rows}`，不列已讀 REQUEST 或欠回信。
- 一般 mailbox 的 in_reply_to 用於傳遞與顯示：`proto8/cmd/aos-mailbox/aos_mailbox/__init__.py:229` 攤平信封欄；第 365 行轉成 aos-post 旗標。完整 read／send 沒有拿終局回信消除「已接未結」記錄。
- 但其他通道確有對帳：`proto8/py/daemon_ctl/post.py:128` 用 `envelope.get("in_reply_to") != letter` 排除非本次控制請求的回信；`proto8/lib/aos/kernel/letters.py:231` 以 `letter.get("in_reply_to")` 查 `ctx.forwarded`，代回後第 245 行 `del ctx.forwarded[key]`。這是控制請求與轉寄回信的對應，不是一般工作信的終局狀態帳。

隊長那句可改為：

> agent mailbox 的 peek 只看 new/，read 成功後立即收掉；keep:true 存 archive，keep:檔名寫 JSONL 留底。mail_notify 記通知去重。這組工作信工具沒有另記「已接、未結」或用終局回信銷帳；但控制請求與 kernel 轉寄層已有 in_reply_to 對應。

依據：本節 `__init__.py:277`、`mail_notify/_entry:117`、`post.py:128`、`letters.py:231`。

## 4. say 等 idle 收；pause 等格結束；sleep 才送終止訊號

判定：部分成立。say 排 queue 並等回 idle 成立；把 pause、sleep 並列成「立即停」不準。

證據：

- `proto8/lib/agent/subagent/_entry:230` 的 say 只轉叫 `cmd.agent(["say", "--target", name], text=words)`；`proto8/cmd/aos-agent/aos_agent/sender.py:45` 再呼叫 `aos_ws.put(...)`。`proto8/py/aos_ws.py:102` 的 put 建 user message，用 `post(["send", "--ordered", box], ...)` 寄進 queue，沒有中斷目標動作。
- `proto8/templates/agent-fsm/idle.py:147` 的 take 收 cur/ 與 new/；第 166 行 append 到 history，第 170 行 `post(["done", box, sig])`。接進 history 的位置在 idle，不是每次呼叫工具前。
- `proto8/templates/agent-fsm/brain.py:119` 的 think 只讀 `history = cell_common.read_history(...)`，不是讀 queue。`proto8/templates/agent-fsm/fsm.json:11` 的 act 成功分支是 `"0": "think"`，無待執行工具才回 idle；think 無事做也才回 idle。因此連續工具呼叫期間，say 可一直排著，不保證下一次 think 就看到。
- `proto8/templates/agent-fsm/loop.json:1` 用 `"exec": "fsm.json"` 跑身體；`proto8/impls/aos-fsm/src/main.cpp:34` 原文 `Run one step of the state table`，實作每次只 run_once 一格。外層 loop 的一次是跑一格，不是完整對話回合。
- `proto8/cmd/aos-agent/aos_agent/ctl/phase.py:89` 的 pause 說明明寫 `a running step is not interrupted; it pauses`，下一行接 `between steps`。`proto8/impls/aos-loop/src/engine/loop.cpp:145` 在迴圈頂端 read_ctl，第 170 行 paused 才跳過執行，第 192 行 run_once 期間不回頭讀 ctl。pause 阻止後續格，不能打斷目前那格，也不會替 say 插入 history。
- `proto8/impls/aos-daemon/src/daemon/reconcile.cpp:249` 的 sleep 設 `c.nap = true` 再 `term(c)`；`proto8/impls/aos-daemon/src/daemon/tend.cpp:70` 實際 `kill(c.pid, SIGTERM)`。同檔第 18 行寬限是 `GRACE_MS = 10000`，第 113 行逾限後對相關行程群組送 SIGKILL。退下後保留 stack 與 sleeping 列；不是 SIGSTOP 式凍結原行程。
- `proto8/cmd/aos-agent/aos_agent/ctl/phase.py:55` 的 sleep 說明區分：running 變 sleeping，wake 或 daemon 重啟可回來；原先已在 stop 途中則變 stopped，要 start。`proto8/cmd/aos-agent/aos_agent/say.py:10` 另明寫 `A paused or sleeping agent still queues it`，寄成功不代表已讀。

隊長那句可改為：

> subagent say 只往 queue 排訊息；agent-fsm 回到 idle 才接進 history，連續工具回合不會即時讀到。pause 在目前這格結束後暫停後續格，resume 繼續；sleep 經 daemon 送 SIGTERM，必要時升級 SIGKILL，保留 stack 後由 wake 重起。say 不是剎車，pause 也不是立即中斷。

依據：本節 `idle.py:166`、`fsm.json:11`、`phase.py:89`、`tend.cpp:70`。
