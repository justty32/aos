## 一、資源鎖與 always-on 鐵律

### 1. 是什麼

桌面與遊戲各有一把 mkdir 鎖，CPU 不取鎖而限流；頂層另列八條隨時適用的鐵律。（出處：`agentctl/docs/resource-locks.md`〈三種資源，兩個鎖〉、`agentctl/AGENTS.md`〈鐵律〉。）

### 2. 出處

`agentctl/AGENTS.md`〈鐵律〉；`agentctl/README.md`〈目錄〉；`agentctl/docs/resource-locks.md`〈授權與持有邊界〉、〈遊戲鎖〉；`agentctl/docs/resource-locks/README.md`；`agentctl/tools/lock.sh`；`agentctl/tools/test_lock_sh.py`。

### 3. 怎麼運作

八條鐵律逐條是（共同出處：`agentctl/AGENTS.md`〈鐵律〉1～8）：
1. 重構／整理不改原意；開發行為不變且 unittest discover 綠燈，非開發按 `Done when:`。
2. push、刪除、下載安裝、對外送出、動 DB 要使用者當場確認或親登清單。
3. 流程放工作流入口；>1 KB 表／清單用 JSON／CSV、`wf-table/1`、tabledb；人用導航留 md。
4. 「遊戲是獨佔資源」，先桌面再遊戲。
5. 使用者在場可佔螢幕，不可搶輸入；不能暫停的遊戲是硬禁區，不確定就問。
6. 不從 Steam 啟動，走開始選單或 `../instance/tools/launch-mo2.sh`，核 `selected_profile=modpack-main`。
7. codex 用 `tmux send-keys`、送出鍵分送，驗收條數寫死。
8. 限流按行程樹、不按名稱，防 `pgrep -f` 自我匹配。

第6條理由與細文不同：public buildid 下 Play 不更新、只開 redirector；Verify 才重灌。（`agentctl/docs/product-constraints.md`〈固定產品約束〉。）
- 桌面鎖為 `~/shared_agent_locks/desktop.lock`，遊戲鎖為 `agentctl/.lock/game.lock`；BRIEF 指名可拿的鎖即預授權。`BUSY` 就改做離線段或報 `BLOCKED`，「不強拆別人的鎖」。純文件不取這兩把鎖。（`agentctl/docs/resource-locks.md`〈授權與持有邊界〉、〈三種資源，兩個鎖〉。）
- 統一入口：`agentctl/tools/lock.sh acquire|release|status desktop|game --owner <線名>`。`mkdir` 成功寫 ISO 時間、owner、note；同 owner 再取也會 BUSY。取遊戲鎖前核桌面同 owner，預設 WARNING 仍取，`--strict` 才拒絕；釋放反序，先放桌面也只警告。（`agentctl/tools/lock.sh`〈usage〉、`cmd_acquire`、`cmd_release`。）
- 放鎖核 owner 第二欄，不同則拒絕；`--force` 可強放但只印警告，這是腳本能力，不等於文件授權。不存在回 `NOT_HELD`／0；`status` 顯示 HELD／FREE 與 age，有鎖回 10。沒有 TTL、自動續租、自動破鎖或死鎖偵測；age 只是檔案 mtime 差值。文件要求用完即放、收工核 owner 與自己程序，沒有訂逾時多久可拆鎖。（`agentctl/tools/lock.sh`：`owner_field`、`lock_age_seconds`、`cmd_release`、`cmd_status`；`agentctl/docs/resource-locks.md`〈收工檢查〉。）

### 4. 為什麼這樣定

- 「搶資源不會報錯，只會讓兩邊的觀測結果都不可信」；反序取雙鎖會死鎖，兩線同開 MO2 會互寫 profile。限 CPU 是「別操使用者的電腦」，約 80% 是上限不是目標。（`agentctl/docs/resource-locks.md`開頭、〈遊戲鎖〉、〈CPU 限流〉。）
- 2026-08-30 使用者裁示：佔螢幕可 alt+tab，搶輸入才真正打斷操作。腳本保留不持桌面仍可取 game 的預設，理由是有不佔螢幕的 profile 施工情境。（`agentctl/docs/resource-locks.md`〈使用者在電腦前時可以做什麼〉；`agentctl/tools/lock.sh`〈usage〉。）

### 5. 靠什麼落實

`lock.sh` 的 mkdir 與 owner 核對是機械限制；鎖序預設警告而非硬擋，八條鐵律也不是都由它執行。`test_lock_sh.py` 覆蓋 BUSY、同／異 owner、strict 拒絕、force、反序釋放、status 回碼；所有測試把 HOME 與兩把鎖導向 tempdir，並檢查輸出沒有真鎖路徑。本次只讀測試，未執行。（`agentctl/tools/lock.sh`；`agentctl/tools/test_lock_sh.py`：`setUp`、`run_lock` 與各 test。）

### 6. 實際有沒有在用

看得到歷史 owner 證據：`agentctl/handoffs/done/2026-09/home-2026-09-24/block-crash/desktop-lock-released/owner` 記 `2026-09-24T09:12:36.759487+08:00 skyrim-cx-sbms 單變量煙霧`；不能由此推定現在真鎖已放。2026-11-07 的離線收尾明寫不取鎖；工具索引仍把 `lock.sh` 標為「新」，不能把已有測試等同已實跑新 CLI。（`agentctl/handoffs/home-2026-11-07/wrap/REPORT.md`末段；`agentctl/docs/tool-index.md`〈取鎖／放鎖／查鎖〉列。）

## 二、領地、衝突與正典入口

### 1. 是什麼

領地表管「誰能寫哪裡」，產品約束管跨批次不變條件，backlog 管可續工作，已知問題與 docs 導航另放；它們不互相取代授權。（出處：`agentctl/docs/line-claims.md`開頭；`agentctl/docs/product-constraints.md`開頭；`agentctl/docs/backlog.md`開頭；`agentctl/docs/README.md`〈狀態與限制〉。）

### 2. 出處

### 3. 怎麼運作

- 「同一時間，一個目錄只能有一條線持有寫入權。」領地表首句是派線前讀、派後即登記；Windows 派線文件則寫派線前登記。共同點是先核領地、不重疊，收線即刪列、不留 history。（`agentctl/docs/line-claims.md`開頭、〈現役〉；`agentctl/docs/dispatch-windows.md`〈三〉。）
- 按獨立 repo 或明確不重疊檔案清單切線，不按功能；同工作樹只一個 commit 者，其餘不碰 index。`-C` 加額外可寫目錄的聯集不得超出 claims。衝突由調度者仲裁；共用 hub、gitlink、領地表既有內容指定唯一維護者，不由各線改。（`agentctl/docs/driving-codex.md`開頭、〈一、切線〉。）
- 線只可「只追加自己那一格」，不得改既有內容；收線刪列仍由管理者。母 repo 根與 gitlink 歸調度者，未分配的 projects repo 不得寫。`instance/` 公司端禁寫，表內另留 2026-08-27 單一授權的只追加例外。（`agentctl/docs/line-claims.md`開頭與〈保留給調度者〉。）
- 整合前把合併差異與主樹未提交檔取交集，「重疊即停」，不自行 stash／restore 使用者改動。主樹 commit／index 是獨佔資源，但此工作區沒有 aos `.lock/worktree.lock`，文件明說不假裝已有機械鎖。（`agentctl/docs/driving-codex.md`〈七、收線〉；`agentctl/docs/resource-locks.md`〈授權與持有邊界〉。）
- docs 導航集中 README；產品約束列唯一 profile、公司 instance 唯讀、gitlink 指 commit；backlog 舊候選不等於授權。KNOWN-ISSUES 要求下載前直接核程式五項修法。（`agentctl/docs/README.md`開頭；`agentctl/docs/product-constraints.md`〈固定產品約束〉；`agentctl/docs/backlog.md`〈歷史候選〉；`agentctl/docs/KNOWN-ISSUES.md`末節。）

### 4. 為什麼這樣定

2026-08-27 曾發生規則自撞：要求線自行登記，卻把整個 docs 劃給調度者；`opus-follower-looks` 因而違反另一條。裁定只追加自己一格，理由原句：「落後的claims 表比沒有更危險」。gitlink 統一收線更新是避免多線在母 repo 打架。（`agentctl/docs/line-claims.md`開頭、〈保留給調度者〉。）

### 5. 靠什麼落實

claims 是文件登記與調度仲裁，未在本次讀到的資料中見到領地衝突自動 gate；Windows 文件用 `-C`／`--add-dir` 限定可寫聯集，但沒展示自動比對 claims 的腳本。commit／index 也明示沒有機械鎖。（`agentctl/docs/dispatch-windows.md`〈三〉；`agentctl/docs/resource-locks.md`〈授權與持有邊界〉。）

### 6. 實際有沒有在用

## 三、交接書、場次與 open 分流

### 1. 是什麼

派線契約、完成報告、本場現況、跨場續行、agent open、等使用者是不同用途。範本共有三類：agent 的 BRIEF、使用者實機清單、artifact 頁；不是三類場次夾。（出處：`agentctl/templates/README.md`表；`agentctl/handoffs/README.md`〈現役〉、〈保留期〉；母 repo `SESSION-LOG.md`開頭。）

### 2. 出處

`agentctl/handoffs/README.md`〈保留期〉；`agentctl/handoffs/home-2026-11-07/STATE.md`；母 repo `SESSION-LOG.md`〈現役工作〉；其他來源隨文列。

### 3. 怎麼運作

- 「一份交接書 = 一條線 = 一個獨立 repo 或明確的檔案範圍。」BRIEF 成品放 `handoffs/home-<日期>/<線>/BRIEF.md`；REPORT 直接落指定絕對路徑，不只貼回覆。使用者實機清單放母 repo `wf/user/<日期>-<主題>.md`；artifact 可放 scratchpad 或線目錄。（`agentctl/handoffs/README.md`開頭、〈怎麼寫〉；`agentctl/templates/README.md`表；`agentctl/templates/BRIEF.md`〈交付〉。）
- 場次層是 `home-<日期>/` 或當場一次性代號目錄；STATE 只記本場、≤8 KB，不抄前場；NEXT 只記續行、≤4 KB，不留歷史快照。根 SESSION ≤2 KB，只列 open，凍結一句加連結。（`agentctl/handoffs/README.md`〈保留期〉。）
- 場次保留「30 天或最近 5 場（取較多）」；已完成、推翻、到期的交接書／場次直接刪，追溯靠 git log，不搬 done。到期刪場前，活文件引用的結論先吸收，使用者原句照抄；其餘連結降純文字，commit 訊息寫刪除理由。刪／搬場次後跑全庫 `python3 ../tools/check_markdown_links.py`，不帶 paths。（`agentctl/handoffs/README.md`開頭、〈保留期〉、末節。）
- 母 repo SESSION 在多步工作開始前寫 open，每次 commit 更新／刪除；格式 `- [工作流] 一句 open 狀態 → 下一步 / 連結`。能由 agent 推進才放這裡，需要人、實機、權限或素材放 WAIT_USER。（母 repo `SESSION-LOG.md`開頭。）
- WAIT_USER hub 只留四類計數表，內容放 `wait-user/` 子檔；每個子檔一個 `#` 容器、每項一個 `##`。結案直接刪、不留 closed JSON；開場與增減後核 `tools/waituser_count.py --check`。（`WAIT_USER.md`開頭；`wait-user/README.md`〈規則〉；`tools/waituser_count.py`檔頭。）
