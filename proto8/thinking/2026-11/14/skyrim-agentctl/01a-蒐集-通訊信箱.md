# T1：skyrim agent 通訊盤點（唯讀調查）

## 一頁結論

1. skyrim 的五通道確實是 `new / orders / mail / topics / teams`；`read`、`done` 不是額外通道，而是歷史處理位置。
2. 終局往上游走靠 `teams/*/members` 首行，不靠 ROSTER 或環境中的 agent 身分；寄件 session 是呼叫者傳入的位置參數。
3. ROSTER 是人／agent 自己維護的身分聲明，不是路由資料庫；現況只剩 dispatcher 一格，沒有 TTL 或心跳。
4. 工人每做完一步必須 poll；背景預設 20 秒；領導用 `--wait` 等輸出結束醒來；頂層 hook 每次使用者輸入列 `new` 摘要。
5. poll 的「看過摘要」、watch 的「通知過」、ack 的「辦完移出投遞區」是三種不同狀態，沒有通用 `new→read→done` 狀態機。
6. 2026-11-05 廢掉 done/history：ack 後 STATE 記一行，原信實作上移入 gitignored `.state/acked`，不是立刻從磁碟 unlink。
7. 現場有 330 個保留的信件檔（含退役副本，不能當唯一寄信量）；另有大量零內容 marker。`new/read` 皆 0，現役 teams 名冊 0，mail 仍留 23 封。
8. 發信採隨機 tmp→mv，但撞名只有事前檢查、沒有鎖；並行競爭、名冊 read-modify-write 與 ack 同 basename 覆蓋並未消失。
9. 通訊事故有實據：搬家後路徑失效、hook 靜默失敗、只盯 new 漏領導 mail、orders 來不及剎車、名冊／小信積壓；git 有分層、ack 工具與刪歸檔的修正紀錄。
10. aos 已於 11-13 明文撤掉同套五通道／ROSTER／收發腳本；樹內改 stack mailbox＋每分鐘合批 queue 通知，樹外仍保留手寫 md 信與 done 位置。

## 1. 五通道與共用信件契約

### 1.1 每條通道具體做什麼

| 通道 | 誰投、誰收／誰可動 | 檔名與內容 | 讀取、辦結與保留 |
|---|---|---|---|
| `new/` | 正常是領導／無團隊線上呈頂層 dispatcher；`--to dispatcher` 可明確越級。工作線不得自己搬動 new | `<YYYYmmddTHHMM>-<session>-<STATUS>.md`；from/status/at，正常沒有 to | `inbox_read` 只列摘要、無副作用；dispatcher poll 也掃；ack 移 `.state/acked`。11-05 後不進 done |
| `mail/<session>/` | 任何人投給某個 session；只有收件人可搬動／標記自己的信。工人終局也會由 send 自動落領導 mail | 同上；frontmatter 多 `to:`；第一次寄就建目錄 | poll 寫該收件人的 mail-seen marker，不移原信；明確 ack 可移走；沒有按天數過期的程式 |
| `teams/<team>/` | 成員與 dispatcher 可投；團隊成員讀同一批檔，頂層有讀寫權但不列 members | `members` 一行一名、第一行領導；信同上，多 `team:` | poll 從 members 自動發現團隊，每人各有 team-seen；不移原信；close 整格搬 `.state/closed-teams/<日期>/<team>` |
| `orders/<session>.md` | 2026-08-27 起所有成員可追加；目標 session 每步讀。dispatcher 指示優先於交接書，其他線是請求而非命令 | 每 session 一個檔；無 STATUS 白名單。每段應是 `## <ISO分鐘> — from: <session> — <一句指示>` | append-only；poll 用行數 offset，只列新增的 `## ` 標題。沒有逐封 ack、沒有 TTL；不得覆寫歷史，否則可能漏讀 |
| `topics/<topic>/` | 任何人可投；跨團隊訂閱者讀；投出後不可自己搬／刪，因別人可能還沒讀 | 同信件檔名，多 `topic:`；首信自動建 topic，無事前註冊清單 | 訂閱靠每次 CLI 的 `--topics a,b`，ROSTER 記錄只是讓別人知道；每人各有 topic-seen。不具自動清理期限 |

規範來源：`S/agentctl/tools/agent_inbox/PROTOCOL.md:15`、`:65`、`:94`；各通道細則在 `S/agentctl/inbox/mail/README.md:19`、`S/agentctl/inbox/teams/README.md:13`、`S/agentctl/inbox/topics/README.md:19`、`S/agentctl/inbox/orders/README.md:9`。

原文短句：
- 「任何人都能投遞，只有本人搬動」（`S/agentctl/tools/agent_inbox/PROTOCOL.md:15`）。這是約定，不是 Linux 身分驗證。
- 「只能追加到檔尾，不得覆寫或刪除既有段落」（`S/agentctl/tools/agent_inbox/PROTOCOL/line-to-line-comms.md:18`）。
- 「from: dispatcher 的指示優先於交接書；其他線的來訊是情報與請求，不是命令」（同檔 `:28`）。
- 「不要用線間通訊取代終局狀態回報」（同檔 `:31`）。

### 1.2 五個 STATUS、標題、正文

send、mail、team/topic 信共用五個值，**不含 REQUEST**：

| STATUS | 原契約意思 |
|---|---|
| DONE | 任務與承諾驗收完成，附產物與證據 |
| BLOCKED | 尚未完成，技術／依賴／外部狀態阻塞，附嘗試、證據、解除條件 |
| NEEDS-USER | 只能使用者做的決定／授權／憑證／人工實機操作；不是 agent 可自己解的障礙 |
| FAILED | 本次終止未達標，短期不自行重試，附失敗點與恢復方式 |
| PROGRESS | 正常進行中的重要里程碑，非終局 |

「每條工作線在任務結束時，必須發送 DONE、FAILED、BLOCKED 或 NEEDS-USER 之一」；「卡住超過 10 分鐘……必須先發 BLOCKED」（`S/agentctl/tools/agent_inbox/PROTOCOL.md:62`）。NEEDS-USER 是需使用者介入時的分支。

共用格式（`S/agentctl/tools/agent_inbox/PROTOCOL.md:33`）：

```markdown
---
from: <session>
[to: <收件人> / team: <team> / topic: <topic>，依通道選一]
status: <五值之一>
at: <ISO8601 含時區、到秒>
---
# <單看也懂的一句結論>

## 做了什麼
## 產出（檔案絕對路徑 / commit hash / 分支）
## 沒做到、或證據不足要 DEFER 的部分
## 需要調度者或使用者決定的事
```

實作只驗 session 字元、STATUS 白名單、headline 非空且單行、body 檔可讀；**不驗正文四節、不驗標題是否真能自足**（`S/agentctl/tools/agent_inbox/inbox_send.sh:46`、`:61`、`:66`、`:128`；mail 同類）。session／收件人／team/topic 名允許 `A-Za-z0-9._-`。

### 1.3 指令介面與交付判準

```text
inbox_send.sh <session> [--to <recipient>] <STATUS> '<headline>' [body_file]
inbox_mail.sh <from> (--to <session>|--topic <topic>|--team <team>) <STATUS> '<headline>' [body_file]
```

不給 body_file 就讀 stdin；成功 stdout 印正式檔絕對路徑。send 另在 stderr 印 `delivered to <recipient>`。body_file 是位置參數，沒有 `--body-file`。

## 2. 上游路由與身份來源

### 2.1 實際路由演算法

權威實作：`S/agentctl/tools/agent_inbox/inbox_send.sh:74`。

1. 預設 `delivered_to=dispatcher`、目的地 `new/`。
2. 有 `--to`：dispatcher→new，其他名字→`mail/<recipient>`；**跳過團隊搜尋**。
3. 沒 `--to`：逐個 `teams/*/members` 用整行精確比對 session；命中的檔案第一行當 leader。
4. 命中大於一隊就 fail；命中一隊且 session 不是第一行→`mail/<leader>`；是 leader 或沒隊→new。
5. 名冊的 leader 空值 fail。收件人 mail 不存在則建立。

**不讀 ROSTER**，也不從 tmux／AOS_STACK／其他 session 環境變數猜身分。身分就是 `inbox_send.sh` 第 1 參數；`inbox_mail.sh` 也如此。`AGENT_INBOX_ROOT` 只改資料根位置，預設由腳本自身往上找 `../../inbox`（send `:7`）；與誰是上游無關。`AGENT_STATE_FILE` 只管 ack 的 STATE 落點。

這只有一跳：領導向 dispatcher，沒有用 ROSTER 或多層 parent 圖遞迴往上找。檢查基於呼叫者自報名字，未見帳號／簽章綁定。

## 3. ROSTER 身份聲明簿

**用途**：讓別人知道「誰是誰、能問什麼、別碰哪個領地」，避免兩線寫同檔。與 `docs/line-claims.md` 分工：claims 管可寫目錄，ROSTER 管身分與可回答範圍（`S/agentctl/inbox/ROSTER.md:3`）。

**誰寫、何時寫**：
- 上線第一件事，先讀別人的聲明，再在「現役成員」末尾追加自己的格，不改別人的；用 send 發一封 PROGRESS、正文貼聲明（ROSTER `:9`；`S/agentctl/tools/agent_inbox/PROTOCOL/line-to-line-comms.md:9`）。
- 必填模板：session 標題、狀態、我是誰、團隊、上游、領地、答得出什麼、答不出什麼、怎麼找我、訂閱主題（ROSTER `:17`）。團隊／上游必須與 members 一致；topics 的聲明不會被 poll 自動轉成訂閱。
- 收線自己刪格；整理者看到已收線殘留也直接刪（ROSTER `:12`、`:50`）。11-05 起不留 roster-history.json，STATE 記一行。

## 4. 輪詢、通知與防漏的實際界線

### 4.1 inbox_poll：工作步驟之間自己拿摘要

介面：

```text
inbox_poll.sh <session> [--topics a,b] [--from <line>]
              [--once|--watch|--wait [--timeout N]] [--interval N]
```

- 預設 once、間隔 20 秒；watch 循環；wait 先掃一次，有輸出立即 exit 0，之後按 interval 掃，timeout exit 3 且 stdout 空；無 timeout 永等（`S/agentctl/tools/agent_inbox/inbox_poll.sh:55`、`:272`）。
- 固定讀個人 mail、members 含自己的所有 team、參數列出的 topics、自己的 orders。session **字面等於 dispatcher** 才額外掃 new（同檔 `:248`）。
- 只印 `[MAIL] / [TEAM:x] / [TOPIC:x] / [ORDERS] / [INBOX]`、from、status、標題、原檔路徑；**不印信件全文**。
- `--from`（10-03 新增）只輸出該 from，其他正常信不標已讀；跳過 orders，避免吞掉與 sender 無法一一對應的指示（`:213`、`:264`）。
- `.state/poll/<session>/` 下分 `mail-seen`、`team-seen/<team>`、`topic-seen/<topic>`、dispatcher 的 `new-seen`，marker 名就是原信 basename；orders 則存 `orders-offset` 行數（`:146`）。

規則原文：「每個成員在每完成一個工作步驟後，都要跑一次」（`S/agentctl/tools/agent_inbox/PROTOCOL.md:94`）。這是**一個工作步驟**的延遲上限，不是保證每 20 秒：只有 watch／wait 才是時間間隔。`S/agentctl/docs/driving-codex/communication.md:18` 明寫四個線間通道沒有推播。

### 4.2 各層醒鐘是人為政策，不是 STATUS filter 程式

`S/agentctl/tools/agent_inbox/PROTOCOL/wake-policy.md:14`：
- 頂層：NEEDS-USER、FAILED、領導 DONE、資源／鎖請求該醒；領導 PROGRESS/BLOCKED 等下次使用者輸入 hook 順帶看到。
- 領導：五值全醒，背景 Bash 跑 `--wait --timeout 1800`，程序結束後看摘要；只把自己解不了的轉頂層，重寫標題、附已排除可能與要什麼。
- 工人：每步 once；codex 本身沒有這套背景醒鐘。

**程式差別**：poll/watch 都沒有按 STATUS 過濾。上表是啟動／關注政策；不是傳入腳本就自動只為某些 STATUS 喚醒。dispatcher 雖被授權讀所有 team，poll 自動發現仍只測 members 是否含該名字；規定 dispatcher 不列 members，所以它不會因此自動掃遍全部 team。

### 4.3 notify_watch：stdout 通知＋tmux 孤兒判斷

`S/agentctl/tools/agent_inbox/notify_watch.sh:9`、`:60`、`:105`：
- 每 20 秒掃 **new 而已**，可用 `AGENT_INBOX_POLL_SECONDS` 改；合法 from/status/headline 的新檔印 `[INBOX]` 後 touch `.state/announced/<basename>`，每檔一次。
- `watch.list` 每行 tmux session。取最後 60 行畫面；capture 失敗且未通知過→`[GONE]`。
- 曾看見 `Working (` 或 `Waiting for background terminal (` 才算曾工作；後者也算活著，註解說 08-22 對 codex-pandora 誤報兩次才補（`:125`）。
- 之後閒置、new/read 沒有該 from 訊息時先記 orphan-pending，下一輪仍符合才印 `[ORPHAN]`；seen-working／orphan-announced marker 防重複。

## 5. ack、read、done、marker 不是同一件事

**ack 要解的事**：把「看摘要、找 REPORT、搬信、記 STATE」合成一個工具，避免同樣的手工收信反覆做。10-03 初版原始碼自述「取代過去手動做了約 95 輪」；`97ca5af2` 新增工具與測試。

```text
inbox_ack.sh (<message>...|--all|--from <line>)
             [--state '<一行>'] [--state-file PATH] [--apply]
```

來源：`S/agentctl/tools/agent_inbox/inbox_ack.sh:13`、`:82`、`:106`。
- 預設 dry-run；`--apply` 才動。
- 裸檔名先找 new，再找 mail/*；給實體路徑也可。`--all` 只選 new；`--from` 選 new＋所有 mail 中 frontmatter from 相同的信，不選 teams/topics。
- 驗檔名正規式、父目錄位於 inbox；印 `[ACK] from STATUS — title` 及正文抓到的 `REPORT.md` 路徑，**不是印完整正文**。
- apply 後 `os.replace(path, .state/acked/path.name)`。本機保留原信，正式投遞處不再有它。
- 有 `--state` 才附 `- HH:MM <from STATUS…>：<一行>`；一批只寫一行。目標優先 `--state-file`→`AGENT_STATE_FILE`→`agentctl/handoffs/home-<今天>/STATE.md`，必要時建父目錄。
- 所以文件說 ack 後一定記 STATE 是規範；**程式允許不給 --state 而只移信**。每封移動完成後才在批次末尾追加 STATE，中途失敗沒有 rollback。

差異表：

| 名稱 | 真正代表什麼 | 是否還在投遞區 | 是否內容歸檔 |
|---|---|---|---|
| poll `*-seen` | 某 session 已輸出過摘要 | 是 | 否，通常零內容 marker |
| watch announced | watcher 已報過一次 | 是 | 否，零內容 marker |
| read/ | 歷史手搬位置，watch 仍兼讀 | 非目前 new | 目前沒有工具推進到它，現場空 |
| done/ | 舊版已辦日期檔／messages.json | 否 | 11-05 廢除，不再新增；現場只剩空目錄 |
| `.state/acked/` | 已移出 new/mail 的原件安全網 | 否 | 本機檔案還在，不 tracked、不再併 done |

**為何不應把 11M 全當信**：大部分是 poll marker；同一 basename 在 mail、不同人的 team-seen、announced 可能各有一個。acked 才是原件內容的保留區之一。

**現場與歷史證據**：acked 有 269 原信，最早檔名 08-30、最新 11-07；它包含 ack 工具新增前的信，只能說那些信被搬入，不能說當時已用該工具。最新 wrap DONE 的 `:46` 明記本場 65 封＋首三封 wrap 進度共 68 封用 inbox_ack 處理、STATE 留摘要、沒有建立 done/history，是比單純檔數更直接的實用證據。

**aos 對應**：`K/mailbox.json#/tools` 的 peek 無副作用；read 預設就刪、`keep:true` 才存 stack archive，也可 keep 到 workspace JSONL（寫失敗原信留著）；不像這邊先 poll 摘要再另叫 ack。aos 樹外 `A/wf/workflows/inbox.json:18` 還採位置區分待辦／done，與 skyrim 11-05 刪 done 的政策不同。

## 6. 團隊生命週期與並行安全

### 6.1 create／add／close

`S/agentctl/tools/agent_inbox/inbox_team.sh:113`：

```text
inbox_team.sh create <team> <leader> [member ...]
inbox_team.sh add <team> <session> [session ...]
inbox_team.sh close <team>
```

- create 驗名字、參數內不得重複、team 不存在、每個 session 不得已屬其他 team；先 mkdir 該 team，members 用根下 mktemp→mv，leader 是傳入的第一名。失敗 trap 嘗試清 tmp／空 team 目錄。
- add 驗目標 members 存在、每個新人不在任一隊（連已在本隊也拒），讀原 members＋新名寫 tmp 再 mv；第一行不動。
- close 以當日 `YYYY-MM-DD` 作目的地，已有同日同隊目標則 fail；把整格 mv 至 `.state/closed-teams/<日期>/<team>`；盡力更新 ROSTER 狀態，找不到／更新失敗只 stderr 診斷。
- 沒有 remove／換 leader 子命令，也沒有建立者身分參數；dispatcher 不列名冊是文件規範，這支 valid_name 本身沒有禁止該字面名字。

**證據**：現役 teams 只剩 README，沒有 members；本機 `.state/closed-teams` 也不存在。退役 fde920 格保留 34 封廣播但無名冊；git `4c0b0451` 曾關 83 stale 隊，`dc450672` 刪 9 份已收線名冊。這些是用過／清掉的證據，不代表現有任何隊在運作。

| 操作 | 有做的保護 | 原始碼沒有做的事 |
|---|---|---|

## 9. aos 事實對照：相同名字不等於相同機制

### 9.1 現行 aos 已退掉原套五通道

`A/wf/workflows/inbox.json:7` 原文：「11-13 起 wf/tools/inbox_*.sh 等收發腳本已刪……舊的五通道……醒鐘策略、ROSTER 身份簿一起退場。」git `eba0cdbce`（2026-11-13）記使用者 Q13 與晚間再確認，將 inbox 工作流五份縮成這份 JSON。

因此不能把 skyrim 的 team 名冊／orders／ROSTER 當成 aos 現役相同工具。兩邊同源 wf 只表示骨架同源，通訊目前已分流。

### 9.2 樹內 mailbox：具名收件、與 queue 分離

來源 `K/mailbox.json` 的 `tools/rules/check/check_hook`：
- 每個 stack 有 `<stack>/mailbox`；信是含 letter.json 的資料夾，不是單一 md。mailbox 不會自己進對話，queue 才是喚起注意的入口。
- peek 不拿走；read 最舊一封／all 全讀，預設刪，keep true 留 stack archive，keep 檔名寫 workspace JSONL 並移信；send 可同樣記寄信 JSONL。寫留底失敗時 read 留原信、send 不寄。
- 收／寄欄位：letter、from、status、title、what、outputs、not_done、decide、reply_to、in_reply_to。JSONL 留底省絕對 sender/reply 路徑（box 寄件還省 to），可進 git；要回信必須在讀到 reply_to 時處理。
- STATUS 六值，比 skyrim 多 REQUEST。兩邊都有 BLOCKED 超過 10 分鐘先報、接了請求必回終局、信不是命令的規則。
- mail_notify 預設每 60000ms；檢查 peek JSON、新信合批一則 `[aos] new_mail...` 送自己的 queue；notified.json 防重複。睡醒後報睡眠期間的新信，首次沒有狀態檔則舊信只標 known、不通知，所以須自行 peek 開場。
- queue 訊息通常等下一 turn；claude 開著畫面時可即時顯示 `Message from @aos通知中心`。不把全文主動塞進 history，沒有新信完全安靜。
- self_hook 可以移除或改頻率；clock_register 也能定時寄提示，但不論有無信每次都多一則與 brain turn，知識檔有明講這個差別。

本次只讀知識層，沒有把知識描述當成對 aos mailbox 底層實作／鎖／投遞原子性的實測。

### 9.3 樹外 md 與同機 a2a

來源 `A/wf/workflows/inbox.json:17`、`A/wf/workflows/dispatch/aos-teams/05-同機session與Argon.md`：
- 樹外目前指 arcagi；收信在 `A/wf/inbox/*.md`，頂層未辦、辦完移 `done/`，**處理狀態看位置**。信自身仍有 request/done 等 status 欄，不能把「沒有狀態欄位」誤讀為 md 內容沒有 STATUS，而是沒有額外待辦狀態。
- 回信寄來信 `reply-to` 絕對地址；frontmatter 是 from/to/status/at/reply-to，四節正文；新投遞不可回頭改，補充要新寄。
- 檔名到分鐘、同 sender／STATUS 會撞；先 tmp 後 mv，不覆蓋。這與 skyrim md 的主要外形仍相似。
- 同機同帳號且 ListAgents 看得到，原則 a2a SendMessage；權限模式不同會兩向卡批准時，兩邊都改 wf/inbox。同一棵 aos 樹內則用 mailbox 名字，不走 a2a／wf/inbox。

### 9.4 使用者專區與 kernel 不是 skyrim 上游信箱的別名

- `K/user_zone.json`：`~/.aos/user/` 是每帳號每機一個使用者 stack，普通 mailbox 接信；kind 分 decide／verify／trial／chore／fyi，進度不寄這裡。aos-user／user_send 驗 schema；10 封／時以上或不合 door 規則會退 FAILED；回信有 in_reply_to，verify／user_verify 對專區 done／log 驗證。
- 驗過的使用者回信可授權 push/delete（aos AGENTS 鐵律 2），但同 Linux 帳號的 shell 可連兩邊造假，文件明說不是抵禦惡意同帳號的隔離。skyrim NEEDS-USER 主要先上呈領導／dispatcher，本題沒看到同等 user-zone schema／verify 機制。
- `K/kernel.json`：控制請求用 `$AOS_KERNEL`（未設→daemon ctl），brain 用 `$AOS_LLM_KERNEL`；kernel station 可 hold/pass/refuse，且回絕不可繞過。kernel_gate 明說來源 from 不由 aos 身分驗證。這是資源與排程請求，不是 ROSTER／團隊終局報告系統。
- `A/wf/workflows/dispatch/aos-teams/07-預設流程與agent-fsm.md` 的「11-14 補」另記現行樹內小廝 `xiaosi` 收所有 ok-* 回報：要緊立刻轉頂層，普通通知每 20 分鐘彙整一封，靠頂層 clock 項 `xiaosi-digest`。這是 aos 已記載的角色式分流／彙整，不是 skyrim 的 members 自動路由；本次只讀這份規則，未查其 stack 或實際信量。同頁另明定 sol 蒐集／施工走 agent-fsm，設計判斷仍歸 opus／fable。
- `A/wf/workflows/dispatch/aos-teams/04-進度回報.md`：start／progress／done／blocked／decision／handoff／ask 走 progress_post 看板；開線、做完一批、代定、卡住、交棒都報。匯總者預設至少 15 分鐘，**不寄信、不 SendMessage，只寫檔**；頂層只收一兩句、需要時讀 summary。這是 aos 另一路「減少頂層 context 污染」的現行事實，不能混成 mailbox STATUS。
