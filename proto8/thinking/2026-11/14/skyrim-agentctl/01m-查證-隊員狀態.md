## 1. ls 幾乎永遠 running，看不出在寫、等腦、等話

判定：部分成立。預設短表確實不是工作階段表；但「所有介面都看不出」不成立，JSON 已有 `busy`。`running` 出現的頻率沒有實測。

證據：

- `NAME`、`WORKSPACE`、`REASON`：`A/proto8/cmd/aos-agent/aos_agent/ctl/ls.py:112` 原文 `cols = [a.name, label(a), a.row.get("ws") or "-"`；名字是表的鍵，工作區與原因來自 daemon 表。`A/proto8/cmd/aos-agent/aos_agent/common.py:127` 原文 `self.phase = row.get("phase")`，並把 reason 換行攤平。
- `STATE`：`A/proto8/cmd/aos-agent/aos_agent/hints.py:34` 原文 `return "paused" if loop_paused(a) else "running"`。表上 running 時另外讀子 loop 的 state 窗判 paused；其餘回原 phase。因此它能分停起、暫停、stuck，不能直接分 FSM 的 idle／think／wait／act。
- `REASON` 的來源：`A/proto8/impls/aos-daemon/src/child/child.cpp:289` 原文 `r["reason"] = c.reason`；stuck 是控制窗逾期未回應，不等於模型慢。
- `QUEUED`：`A/proto8/cmd/aos-agent/aos_agent/hints.py:39` 原文「queue 排幾封（new/＋cur/）」；沒有 queue 資料夾回 `None`，短表印 `-`。信已接進 history 就移掉，所以 0 不能當 idle 證據；接信後 `post(["done", box, sig])` 見 `A/proto8/templates/agent-fsm/idle.py:170`。
- `--long` 的 `QUEUE`：`A/proto8/cmd/aos-agent/aos_agent/ctl/ls.py:45` 原文 `return len(aos_ws.names(a.stack, "new"))`，只數 new，與前一欄不同。`RESTARTS` 是 cooldown 的連續 failures，不是 daemon 重啟累計；`COOLDOWN` 是本地時間 `until HH:MM (N)` 或 `due (N)`；`LAST ERROR` 優先取冷卻 code＋reason，否則表上 reason，最多 60 字。來源同檔 `:83` 的 `long_cols`，以及 `A/proto8/lib/agent/cooldown.py:73` 原文 `failures = old.get("failures", 0) + 1`。
- JSON：`A/proto8/cmd/aos-agent/aos_agent/ctl/ls.py:106` 原文 `auto_restart=a.row.get("auto_restart") is True`、`busy=busy(a)`；同列另有 name、state、phase、ws、stack、queued、reason、queue、cooldown。cooldown 物件含 failures／until／code／reason／dropped／state（同檔 `:48`）。
- `busy` 的判法與優先序：`A/proto8/cmd/aos-agent/aos_agent/ctl/ls.py:60` 原文 `if os.path.exists(os.path.join(s, "think", "pending.txt")):` → `think`；stage 是 act → `act`；stack 根或 tools 下一層有 busy.txt → `cli`；都沒有 → `None`。此處 `think` 實際表示已寄腦請求、等回信，不是 stage 名。

事實改寫：

「短表的 running 不分工作階段。JSON 的 busy 可粗分等腦、act、CLI；null 不保證 idle，也可能尚未留下記號或在冷卻。」依據 `A/proto8/cmd/aos-agent/aos_agent/ctl/ls.py:60` 的檔案判法與 `A/proto8/templates/agent-fsm/wait.py:335` 原文 `sys.exit(NOT_YET)`（冷卻中尚未寄出）。

## 2. stack 的 stage／history 與 kernel requests 可查狀態

判定：成立（就標準 agent-fsm 的檔案與請求位置）；不是每種身都有相同四格，也不是所有現成指令已把這些合在一起。

證據：

- stage 誰寫、何時寫：`A/proto8/impls/aos-fsm/src/main.cpp:72` 讀目前狀態，`:86` 原文 `next_for(cell, b.code)`，有接住該結束碼才 `write_state(stack, *next)`。不是四格 Python 自己寫。`A/proto8/impls/aos-fsm/src/state/state.cpp:18` 原文 `return start`（檔不存在）；`:35` 用 `name + "\n"`，內容相同不改檔，否則從 `.stage.txt` 原子換入。故 stage 的 mtime 不是心跳。

## 3. listen 給 timeout_s 580，仍被 60 秒砍掉

判定：部分成立。該錯誤字串可定位到 MCP 外層，但目前 repo 的 subagent 宣告不限時，不能據此認定每次都會在 60 秒被砍。

證據：

- `A/proto8/cmd/aos-mcp/bin/aos-mcp:268` 原文 `"%s timed out (%g s); its process group was killed"`，正是題目的 CommandFailed 字串。`:109` 預設 `60.0`；`:197` 優先工具 metainfo 的 max_s，沒有才用 MCP 的 timeout_s；`:203` 原文 `timeout=None if limit == 0 else limit`。工具 arguments 的 timeout_s 不會變成這個外層 limit。
- `A/proto8/lib/agent/subagent/_metainfo.json:16` 原文 `"timeout_ms": 0`；不是 `_tooldef` 的等待參數。MCP 用 metainfo.timeout_ms 解析它（`aos-mcp:185`）；所以讀到這份宣告時，外層不限時。
- 580 的去處：`A/proto8/lib/agent/subagent/_entry:239` 原文 `"--timeout-s", "%g" % sec`，交給 aos-agent listen；同時工具內 runner 用 `sec + 30`，即 610 秒保險。`A/proto8/lib/agent/agents_cmd.py:77` 用 communicate 等子指令，內層到期錯誤是 `did not finish in ... (killed)`，不是題目字串。listen 自己等待到期則報 AnswerMissing，見 `A/proto8/cmd/aos-agent/aos_agent/listen.py:110` 原文 `"waited %s; %s was handed over and is not answered yet"`。
- FSM 不是 MCP：`A/proto8/templates/agent-fsm/act.py:164` 也取 metainfo；`:167` 原文 `milliseconds not in (None, 0) else None`，未宣告或 0 不限時，沒有 MCP 的預設 60 秒。整個 act 格另有 `timeout_ms: 1800000`，見 `A/proto8/templates/agent-fsm/fsm.json:10`。

事實改寫：「曾遇到的是 aos-mcp 外層工具逾時；subagent 的 timeout_s 580 只管內層等回答，不能覆蓋外層。現行 repo 的 subagent metadata 已是 timeout_ms=0；當時執行的是哪份宣告、為何得到 60 秒，這次未核實。」來源為上述 MCP `:197`、subagent `:239` 與 `_metainfo.json:16`。

## 4. 純文字結束這輪，goal 在沒信時提醒

判定：成立；精確條件是「最後 assistant 沒有 tool_calls」，不是檢查文字格式，也不是把 agent 行程結束。

證據：

- `A/proto8/templates/agent-fsm/act.py:108` 原文 `calls = history[last].get("tool_calls")`，沒有 calls 就 `sys.exit(10)`；`A/proto8/templates/agent-fsm/fsm.json:11` 原文 `"10": "idle"`，因此回 idle 等信。
- `A/proto8/templates/agent-fsm/idle.py:245` 原文 `if take() or (opening() and take()) or goal_turn():`，先收信再看 goal。`:214` 只處理 active；`:229` 看 due；`:239` 把提醒直接寫成 user 訊息進 history，再退 0 去 think。
- `A/proto8/lib/agent/goal_state.py:139` 原文 `not history[-1].get("tool_calls")` 定義停下；`:148` 原文 `return not history or stopped(history)`，空 history 也可把 goal 當開場題。
- 同檔 `:114` 原文 `reminded = 0 if progressed else rec["reminded"]`；`:150` 的 progressed 只看上次提醒後有沒有叫 goal 以外的工具，不證明任務真的有成果。`:115` 已達 limit 才改 paused，故先給 limit 次普通提醒，下次再給暫停通知。預設 limit=10（`:18`）。
- goal 工具只是包 aos-agent goal，見 `A/proto8/lib/agent/goal/_entry:101` 原文 `out = agent(*cmd, text=given)`；提醒由 idle 寫入，不是工具主動發信。

事實改寫：「標準 FSM 收到不帶工具呼叫的最後回答便回 idle；無新信且 goal active 時，idle 把提醒接進 history 再去 think。工具呼叫只用於重算提醒次數，不是成果驗證。」來源為本節 act `:108`、idle `:245`、goal_state `:150`。
