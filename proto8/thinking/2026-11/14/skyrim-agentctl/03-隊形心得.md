# 03 隊形心得：fable 當 kernel，在活樹裡帶 LiteLLM 上的 sol 與 astra（agent-fsm）實際怎麼樣

← [README](README.md)｜[02 借鑑清單](02-借鑑清單.md)｜前一任（樹外 Claude subagent）的版本在 [交棒](交棒.md)「隊形心得草稿」，那段不重抄，這份寫第二任（活樹裡的 fable eca「ok-skyrim」）實際撞到的。

## 先講結論

1. **「fable 帶 sol 蒐集」成立，而且很划算**：三隻 sol 各 15～22 分鐘交一份 20 KB、帶出處的報告，astra 抽查 12 條對 11 條、部分對 1 條、沒有錯的。fable 自己只花在寫任務書、判斷借不借。
2. **「fable 當 kernel」這次名義上有、實質上沒用到**：我開了 `kernel_gate`，但從頭到尾沒有任何請求進來。隊員是我用 `subagent add` 掛的，那條路不經門；隊員也沒有往下再掛東西。真正在管資源的是 `llm-gpt` 那台 llm kernel（排 sol 的兩個槽、記帳）。
3. **astra 這次改當「驗收員」比當「小隊長」有用**：前一任讓 astra 帶 sol，它掛了兩隻就卡在 `listen` 空等。這次不讓它管人，只給它「抽查三份報告＋編跨檔索引」，交件紮實。但它很貴：一隻 astra 吃的輸入 token 比三隻 sol 加起來還多。
4. **最大的三個摩擦**都跟「隊長看不到、叫不動」有關：隊員讀完必讀清單只回一句「我會做」就停；`listen` 等超過 60 秒整個被砍；分不出隊員是在寫、在排隊等腦、還是停了。三條都有繞法，寫在下面。

## 實際的隊形

```
repo-aos（頂層，kernel_gate）
 └ ok-skyrim（fable eca，kernel_gate 開著但沒收到請求）── 寫任務書、判斷借鑑、收件
     ├ sky-sol-a（agent-fsm，腦 sol-high）  通訊 → 第二張：派線事故與場次
     ├ sky-sol-b（agent-fsm，腦 sol-high）  隊形、任務書、外部 CLI
     ├ sky-sol-c（agent-fsm，腦 sol-high）  資源鎖、領地、交接、衛生
     └ sky-astra-d（agent-fsm，腦 astra-high）兩邊 wf 差異 → 第二張：驗收抽查＋跨檔索引
   腦都走活樹既有的 llm-gpt（LiteLLM 127.0.0.1:4000）；沒用 terra、沒用 codex、沒起暫存樹。
```

- 定義：`agent_def new` 從 `agent-fsm` 範本複製到我的工作區 `defs/gather`，改四處——工具只留看、寫、小工具、待辦、json 讀、index、信箱（後來補 goal）；`llm.json` 寫 `sol-high`；system text 放必讀清單與硬規則；加一個 `before_tool` hook 擋 `write`／`edit` 寫到 `out/` 以外。沒給 shell，所以不需要沙箱。
- 掛上去：`subagent add`，`envs` 帶 `AOS_LLM_KERNEL` 指到 `llm-gpt`；astra 那隻再用 `subagent llm set` 換成 `astra-high`。
- 從讀完規矩到四隻開始讀檔約 12 分鐘（前一任在暫存樹起隊花了約 20 分鐘）。省下來的時間是因為活樹裡 llm kernel、packs、範本都現成。

## 好用的地方

- **在活樹裡掛隊比樹外起暫存樹省事很多**：不用清環境、不用起 daemon、不用記一串 pid 再 shutdown。收隊是四次 `subagent rm`，stack（含完整對話）留著可查。
- **`agent_def` ＋ `subagent` ＋ `self_hook` 式的守門夠用**：唯讀任務只要「不給 shell、寫檔加一個路徑守門 hook」。守門 hook 這次一次都沒擋到東西（隊員沒有試圖寫別處）；收尾時 skyrim 的 `git status` 跟開工前一樣只有原本那個 ` m instance`。
- **sol 一輪會平行叫好幾支工具**（最多 9 支），三四十次問腦就讀完五六十個檔；會自己用 `todo` 排步驟、用 `stat` 核對檔案大小是否落在任務書要求的範圍。
- **sol 守規矩**：三份報告六格齊全；astra 專門去找有沒有偷寫「建議、值得、應該」，一句都沒找到。會主動寫「沒讀到／不確定的」，會糾正任務書寫錯的路徑。
- **astra 當驗收員**：它真的回 skyrim 原檔逐條對，連「這個大小檢查是寫在 elif 裡、前一個條件命中就不會跑」這種細節都抓得到；還指出舊報告之間看似矛盾、其實是兩個不同 repo 的同名檔。這等於照 skyrim 自己那條「獨立覆核要換模型體系」做了一次。
- **ledger**：誰花了多少、等了多久，一支腳本就算得出來。

## 摩擦（照撞到的順序）

1. **隊員讀完必讀清單就回一句「我會做」然後停下**。四隻全部如此（sol 三隻、astra 一隻），各浪費一輪。agent-fsm 的規則是「回純文字＝這一輪結束」，而模型習慣先報告計劃。繞法：補掛 `goal` 工具，再 `say` 一句「先 goal set，輸出檔寫完才可以用純文字回答」，之後四隻都一路做到完。第二張任務書我直接把這句寫進去，就沒再發生。
   - 下次：gpt 隊員的定義一開始就掛 `goal`，system text 寫明「純文字回答＝宣告整件事做完」。
2. **`subagent listen` 等超過 60 秒，整個呼叫被砍**（`CommandFailed subagent timed out (60 s); its process group was killed`），即使我給了 `timeout_s: 580`。也就是 eca 身的隊長沒辦法用 `listen` 等一件十分鐘的事。繞法：用 Bash 迴圈每 15 秒看一次隊員 stack 的 `stage.txt`，全部 `idle` 才回來；這個迴圈本身也被砍過兩次（一次 session 中斷、一次 exit 137），所以每輪別等超過三四分鐘。
3. **分不出隊員是在寫、在等槽、還是停了**。`agents_ctl ls` 四隻永遠是 `running`、queued 0。我實際用的判斷法：`stage.txt`（idle＝停下等話、wait＝在等腦或等工具、think、act）＋`history.jsonl` 的修改時間＋`llm-gpt/requests/cur` 與 `new` 裡有沒有它的信。這跟前一任交棒寫的第 5 條是同一件事；skyrim 那邊為了同樣的問題寫了一支 `cx_watch`（借鑑清單第二類第 3 條）。
4. **`say` 進不了正在跑的那一輪**，只能排隊。這次影響不大（我是在它們停下時才 `say`），但中途頂層來了兩則改規矩的通知（回報改寄 xiaosi、改用 `--limits`），如果要傳給正在跑的隊員，只能等它那輪結束。
5. **prlimit 設在哪個 pid 上其實不確定有沒有罩到**。我照指示對 daemon 表上那四個 pid 設了位址空間 6 GB、開檔數上限；事後才注意到那四個 pid 的命令列顯示是 `aos-daemon …`，常駐記憶體只有 2 MB，看起來是 daemon 分出來看著隊員的那一層，真正跑迴圈和工具的是它底下的子行程。prlimit 只會傳給設定之後才生出來的子行程，所以大概有罩到後面的每一格，但我沒有驗證。頂層後來通知 s6 裝好了、改用 `ctl add --limits`，這個疑問之後不存在。
6. **名額剛好卡在 4**：`max_subagents` 預設 4，我四隻用滿。想加第五隻（例如把事故那張另派一隻）就得先 `rm` 一隻；所以改成讓先做完的 sol-a 接第二張。接第二張的好處是它已經讀過規矩，壞處是它的對話越背越長（sol-a 第二張的每次問腦都帶著第一張讀過的所有檔）。
7. **規矩一天內改了好幾次，交棒當下的指示到收尾時已經過期**：開工時說「commit 用 `git commit -F`、自己跑 index_gen、回報寄 repo-aos、用 prlimit」，收尾時四樣都換了（commit-request、不自己跑 index_gen、寄 xiaosi、`--limits`）。兩則是頂層直接通知我的，另兩則是我 commit 前去看 07 才發現。接手或收尾前重讀一次 06、07 是必要的。
8. **astra 的用量**：它一輪最多平行叫 16 支工具、把九份報告和一堆原檔全讀進對話，輸入 1079 萬 token。驗收抽查值這個價；但若只是蒐集，sol 就夠，而且 astra 單價約是 sol 的三倍。

## 「fable 當 kernel」到底有沒有成立

照 aos 的定義，kernel 是「請求寄到我這裡、我決定放不放行」。分三層講：

- **資源面（腦的名額與帳）**：由 `llm-gpt` 管，不是我。這層運作得很好，兩個槽的排隊就是它在做事。
- **行程面（誰可以起、起幾隻）**：我開了 gate，但 `subagent add` 是我自己直接對 daemon 下的，不經過任何門；我往上的請求經不經頂層的 gate，我沒有看到任何 hold 或 refuse 的跡象，四隻都是秒掛上。隊員沒有掛子 agent 的工具，所以也沒有請求往我這裡來。gate 開了 25 分鐘，收到 0 件。
- **調度面（寫任務書、派工、收件、判斷）**：這是我實際在做的事，但這是「隊長」，不是 aos 意義上的 kernel。

所以老實的說法是：**這次驗到的是「fable 當隊長、在活樹裡用 subagent 帶 gpt 的 agent-fsm」這個隊形可行且順；「fable 當 kernel 審請求」沒有被用到**。要讓它被用到，得是隊員自己會往下掛東西（例如給 astra `subagent` 工具並把它的 `AOS_KERNEL` 指到我的 gate），而前一任試過 astra 往下掛，卡在 `listen`。兩任合起來看，目前合適的分工是：fable（或 opus）當隊長直接帶 sol；astra 不帶人，當第二雙眼睛。

回合制的問題比前一任輕：我是樹裡的 eca，gate 的站在我回合之間會跑、信來了 `mail_notify` 會叫我。但只要我在一個長回合裡（例如那個等隊員的迴圈），gate 一樣不會動；這跟知識庫 `kernel.json` 寫的一致。

## 必讀清單：有沒有照讀、讀了有沒有差

- **有照讀**：四隻的第一輪都是先讀 system text 列的六份再讀任務書，回話裡各自說了「六份必讀與任務書已讀完」；從 history 看得到那六次 `read`／`json_get`。
- **看得出差別的地方**：報告拿 aos 現況對照時用的是最新狀態（知道 aos 11-13 撤了五通道與 wf-lint、新的待使用者題改寄專區、commit 前只跑生成器）；格式是繁中、結論先講；沒有越界給建議。
- **代價**：六份約 40 KB，每次問腦重送。四隻合計 188 次問腦，粗估光必讀清單就佔兩百萬 token 上下。額度撐得住，但這是「每隻都讀規矩」的實際價錢。
- 沒有跑「不讀規矩」的對照組，所以差多少說不出數字。

## 下次怎麼派

- 蒐集：一隻 sol 一題、直屬隊長；任務書規定固定格子（這次是六格）與「分段寫」，外面看得到進度，報告也好比對。
- 定義一開始就掛 `goal`、不給 shell、寫檔加路徑守門；資源上限用 `ctl add --limits`。
- 等隊員用「看 `stage.txt` 的短迴圈」，每輪三分鐘內；不要用 `listen` 等長事。
- astra 留給「驗收抽查」與「跨好幾份歸納」，不讓它帶人；一次就好，別讓它重讀所有原檔。
- 同一隻接第二張任務可以省掉重讀規矩，但對話會變長；超過兩張就換一隻新的。
- 收尾前重讀 06、07，規矩可能已經變了。
