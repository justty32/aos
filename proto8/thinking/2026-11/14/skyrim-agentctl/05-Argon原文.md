# 05 Argon 原文：Gemini 4 Argon (High) 審 02 借鑑清單的 (A) 審查與 (B) 提案（11-14，原文照收；採納表在 06）

**先講結論**：
這份清單抓到了最核心的痛點（信箱缺「已接未結」狀態、看不出隊員卡死、配額逐層倍增），大方向準確。但審查下來有四個問題：
1. **分類錯置**：有 3 條放錯籃子（**一.7、二.6** 應移去「不適用」；**二.7** 只是寫進文件，應移去「第一類 wf 慣例」）。
2. **前後矛盾**：**一.2** 要在交接書必填「總配額分配、不逐層倍增」，卻又說保留「無上限」原話可填不限，且 **二.4** 才說體系目前根本沒這機制；**一.4** 既然已有 8 KB 規定還爆到 17 KB，再寫一個 2 KB 讓人自己看一樣沒用。
3. **角色與概念混同**：**一.1** 把負責分流的 `xiaosi` 當成負責排查的隊長；**二.1** 把資源放行站（`AOS_KERNEL`）、行程母子（`owner`）跟收回報對象混成同一件事。
4. **怎麼借可以更省事**：aos 是「資料夾＝程式」，信箱三態（**二.2**）、上游回報（**二.1**）、判活（**二.3**）都能直接用現有資料夾與信箱機制解，不必造新表或讓系統猜拓撲。

### (A) 審查（逐條檢視）

#### 一、可直接抄的 wf 慣例
* **一.1**：**「值得」成立，但套錯對象**。`xiaosi` 是郵務分流員，不可能像帶兵隊長那樣幫每封信「附上已排除的可能」；這三條規矩應該定給寄信的 `ok-*` 隊長，而不是讓 `xiaosi` 轉信時才生出判斷。
* **一.2**：**理由自相矛盾**。後面「失敗分兩路、錯誤分流、REPORT 回填工具」很值得抄；但第一項要求「分配並傳遞本線總配額」，底下卻說保留「無上限」原話、填「不限」也行——填「不限」就無從分配起，且 **二.4** 已說明體系層還沒做配額傳遞，單改表格會淪為空文。
* **一.3**：**「值得」成立，但放的位置會造成雙重維護**。文中舉例的「怎麼掛 agent-fsm、開 kernel_gate」其實是操作食譜而非單一工具，既然 `K/` 已經照工具排，再在 `A/wf/` 另起一張表很容易跟 `K/` 脫節。
* **一.4**：**「怎麼借」站不住且自相矛盾**。`A/wf/STRUCTURE.md` 本來就有 8 KB 門檻與「只列 open」，結果 `SESSION-LOG.md` 還是長到 17 KB，證明「寫個數字由寫的人自己看」根本沒效，改寫成 2 KB 也不會自動變短。
* **一.5**：**判斷合理、分類正確**。不過「接手先巡」屬交棒流程，「禁區措辭別寫成結案條件」屬任務書寫法，抄的時候後者應放進 `TEMPLATE.handoff.md`（跟 **一.2** 一起改）才不會放錯地方。
* **一.6**：**判斷合理、分類正確**。換模型體系交叉覆核與抽查內容，直接補進驗收規矩即可。
* **一.7**：**分類放錯**。第一類定義是「直接做、不用問」，但本條結論自己寫「等隊形穩了再說」，代表現在不做，應移到「**三、不適用（暫緩）**」。

#### 二、可當 aos 功能參考的
* **二.1**：**值得參考，但推論證據不足、混同概念**。`AOS_KERNEL` 是審批資源的門、`subagent owner` 是行程生父、`xiaosi` 是頂層秘書，三者在 aos 裡不是同一條線；在沒讀 `proto8/` 程式碼的情況下，直接假設能從 `owner` 與 `AOS_KERNEL` 自動推出「回報該寄給誰」並不牢靠。
* **二.2**：**非常值得、分類正確**。讀信即刪確實會讓 compact 或交棒後的待辦REQUEST 蒸發，是 stack mailbox 目前真正的缺口。
* **二.3**：**非常值得、分類正確**。`stage.txt`、`history.jsonl` 時間戳與 `llm kernel` 的 `requests/cur` 檔案都在資料夾裡，只是缺一層匯總檢視與等待原語。
* **二.4**：**值得參考、抓到關鍵漏洞**。點出 `subagent add` 繞過 kernel 門、且 `max_subagents` 與腦預算逐層各自計算的問題，這才是解決配額倍增的正途（也因此 **一.2** 的配額欄應等這條通了再推）。
* **二.5**：**證據偏弱、過度引申**。aos 已有 `kernel` 站可管 `slots=1` 的排隊放行，連 git index 也已有 `commit-request` 解決；skyrim 是因為沒 kernel 才用 `mkdir` 硬定鎖序，aos 真正能借的只有「獨佔租約不設自動過期（無 TTL）、孤兒由外層判活回收」這一點。
* **二.6**：**分類放錯**。結論已明確寫「aos 已做得比 skyrim 完整、不用借、方向無」，應直接放進「**三、不適用**」最後一列（aos 已有且更完整）。
* **二.7**：**分類放錯**。內文自己說「功能面不缺東西，值得寫一句進知識庫」，既然不改 aos 功能、只補文件認知，應移去「**一、可直接抄的 wf 慣例**」。

#### 三、不適用（含可靠度說明）
* **三（整體）**：排除項判斷大多合理，但把 **二.5** 裡提到的「按行程樹限流」與 **一.4** 背後「趁固定動作順手歸檔」連同遊戲鎖／`wf-lint` 一起丟掉了；另外文末坦承沒讀 `proto8/` 程式，這讓第二類凡是涉及底層現況的推論（如 **二.1、二.5**）只能當需求描述看。

### (B) 提案（漏掉的亮點與更省事的借法，共 6 條）

1. **【二.2 更省事的借法】用「資料夾＝狀態」解信箱三態，不必造新狀態表**
   aos 本來就是「資料夾＝程式」，既然 `llm kernel` 都有 `requests/cur`，stack mailbox 只要規定「接任務先用 `mailbox_peek`（或把 `mailbox_read` 改為搬進 `cur/` 而非直接刪除），等寄出終局回報時才刪信」，那留在信箱（或 `cur/`）裡的 REQUEST 檔案本身就是「自己欠誰回信」的清單，連 `self_state` 都不必大改。

2. **【二.1 更省事的借法】在信件或 stack 放一個 `reply_to` 欄位，別讓系統去猜 `AOS_KERNEL` 或 `owner`**
   與其讓 `mailbox_send` 寫複雜邏輯去從 `owner` 和 `AOS_KERNEL` 推算上游、還要處理 `xiaosi` 分流，不如直接在派工信或隊員 stack 資料夾裡放一個 `reply_to`（例如頂層把自己的 `reply_to` 設成 `xiaosi`）。工人永遠只對著 `reply_to` 回信，要改分流對象只改派工源頭一處，簡單又不會把資源門跟收信人搞混。

3. **【清單漏掉的點】「卡死／異常退出自動發信叫醒」比「隊長自己跑 `ls --long` 巡視」更重要**
   **二.3** 只借到把狀態攤開給人看，但文中描述 skyrim 的 `cx_watch.sh` 精髓在於「丟背景等它結束＝被動叫醒」。aos 雖然有 `mail_notify`，但隊員如果卡死或無聲退出根本不會寄信；與其叫隊長巡視，不如讓守護行程在「隊員無子行程、沒在排 `llm kernel`、`history.jsonl` 超過 N 秒沒動」時，自動塞一封 `[STALLED]` 信進上游 mailbox，直接接上現有的 `mail_notify` 叫醒隊長。

4. **【清單漏掉的點】資源限流與清理要綁「行程樹（process group / cgroup）」，不能只靠單一行程 `prlimit`**
   **二.5** 敘述裡閃過一句 skyrim 的「按行程樹限流，不要按名稱」，**二.3** 也提到「看行程樹有沒有活的子行程」，但清單沒把它拎出來。aos 的 agent 常會跑腳本或起暫存樹（**一.3** 提到各線在摸索設 `prlimit` 與清環境），若只對單一 PID 設 `prlimit` 或 `sleep`，子行程照樣在背景吃資源或變孤兒；aos 的 `subagent` 管控與限流應直接以整個行程樹為單位。

5. **【一.3 更省事的借法】把「任務類型 → 必用工具／食譜」直接長在 `K/` 入口，別在 `A/wf/` 多養一張表**
   既然 `K/`（知識庫）已經照工具排，而隊長想收的「掛 agent-fsm、開 kernel_gate、看腦 ledger」其實是標準操作食譜，最省事的做法是在 `K/` 放一份輕量的情境導航（或在 `TEMPLATE.handoff.md` 規定「必讀知識庫條目」直接填 `K/` 的檔名），搭配 **一.2** REPORT 末尾回填「這次缺哪份 `K/` 食譜」，就不會出現 `A/wf/` 跟 `K/` 兩套工具表各寫各的。

6. **【一.4 更省事的借法】把 `SESSION-LOG` 瘦身綁進「交棒自檢（一.5）」或「commit 生成器」**
   刪掉 `wf-lint` 後，與其在檔頭寫「預算 2 KB」期待大家自律，不如搭便車：直接放進 **一.5** 的「管理者休眠／交棒前自檢」清單裡（「交棒前把 `SESSION-LOG` 已結案項目移入 archive」），或讓 commit 前本來就會跑的生成器順手在檔案超長時印出提醒，才真的落得下來。
