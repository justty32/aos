## 11-14 早（頂層 repo-aos 轉來，逐字）

> 我剛剛有稍微看過那些了。我其實會覺得，你們太早就開始規劃實作與架構了，我覺得你們可以先發想，類似頭腦風暴那樣。先再去弄一輪吧。我這邊想一下再回答你的問題...邊打遊戲邊想，可能一題一題回，你可以在頭腦風暴中途將其加入。我先說一些我的想法：首先是agent換成固定程式這塊，先不用急着做，這會是後續aos用多了就自然而然會發生的事情，不用特意規劃，他會自己長出來。資源這塊也是不用特別規劃，kernel在做判斷的時候，可能會參考各種東西，那時候自然就會有定義出來了，各種kernel的定義各不相同。所以基本上你太早開始規劃了，現在都還沒有清晰的需求出來，你現在就規劃，反而會限制到很多可能性。改善也是，這是自然而然的事情。擋門的AI這塊我們也不要這麼早就給他劃定界限。arknights先不動，我要凍結到至少一個月後。上千上萬個agent確實如你所想的那樣，好比LLM，他一次只會有一些神經元被激活。好不好懂這塊應該近期我就會開始着手，但你可以開始簡單想想，我這邊起個頭...人本身也是一個外部計算單元，取得好不好懂這個值就靠這個，然後這個計算單元有些特性，比如他一次只能處理一些事，並且很慢很懶www，或許可以弄個kernel來作爲管理？proc新定義這塊我是在胡言亂語，這塊的新心智模型我還在初期思考，先不用管，但你也可以單獨派線幫我想想，這個不急。開發函數的函數是形容，同樣是以後自然而然

## 讀法（這一輪怎麼吸收）

| 原話 | 這輪的讀法 |
|---|---|
| 太早規劃、先發想 | 本輪只出點子與可丟棄的小實驗；不出實作計劃、D 題、門檻數字、階段 |
| agent 換成固定程式、資源定義、改善、開發函數的函數，都是用多了自然長出來 | 不替它們設計管線；點子裡只想「怎麼讓長出來的時候看得見、接得住」，不想「怎麼做出來」 |
| 開發函數的函數「現在就是了」 | 現在這套 agent 體系（agent 能 `agent_def`、`self_*` 改自己、派子 agent）本身就是開發函數的函數，不另做 devfn；上一輪 06 第三節的 devfn-solo／devfn-team 作廢 |
| 擋門的 AI 不劃界限 | 上一輪「第 3 級才問 AI 門、表態要沉澱成規則」只當一種可能，不當規矩 |
| arknights 凍結到至少一個月後 | 寫進 wf（至少到 2026-12-14），本輪點子不拿 arknights 當試驗場 |
| 千萬 agent 像 LLM 稀疏激活 | 使用者確認這個意象，本輪延伸它 |
| 人是外部計算單元、好不好懂靠它、慢、懶、一次只做少量事、或許弄個 kernel 管 | 本輪重點題，近期使用者要著手 |
| proc 新定義 | 另一條線處理，本輪不碰 |
| 粗化細化跟 `_metainfo`、`_index` 有關 | 本輪主題軸之一 |
| D14：`_metainfo` 可以放資源，當**宣告**；每個 agent 對資源有自己**私有的看法** | 「公開宣告 vs 私有看法」當一組張力發散；上一輪 D14 的 (a)「`_metainfo` 由 `tool_spec` 自動產、kernel 從 `body.cost` 讀」只取「放 `_metainfo`、是宣告」這半，解讀權在各 agent |
| D15：lisp／lua 不急，至少等 kernel 穩定 | 本輪 lisp／lua 只留幾條遠期點子，不出實驗 |
| 其餘舊 D 題「都是自然而然的…我不急」 | 上一輪 D1～D16 全部結案：沒單獨答的都不裁、不列待辦，用到時自然浮現；本輪產出**不出任何待使用者裁的題目** |
