## 結論

這份設計稿抓對了病根（**舊條文蓋住現行做法、入口沒接新工具**），但解法有三個致命傷：
1. **疊床架屋**：不把既有入口檔瘦身到底，反而新增 `quick.md` 和 `pitfalls.json`，製造新的同步黑洞與多餘跳轉。
2. **不敢碰經驗庫**：放著 `wf/public` 與 `wf/advices` 裡的 50 條經驗不合併、不標過期，只放連結指過去，Agent 點進去還是踩坑。
3. **舊文放錯地方**：在現役資料夾裡塞 `沿革.md`，會污染目錄索引與關鍵字搜尋，讓 Agent 誤讀舊規矩。

下面先列設計稿的問題（A），再給更省讀取量、更能避坑的替代方案（B）。

---

## (A) 設計稿審查：問題、風險與缺漏

1. **【嚴重】D2 新增 `quick.md` 會變成新的同步黑洞，且沒真正省到讀取量**
   - **問題**：同一條規矩同時出現在 `AGENTS.md`、`quick.md`、`aos-teams.md` 與 `07`。下次改規矩只要漏改一處，又會重演「找到但互相衝突」。
   - **實務後果**：`quick.md` 只寫「一行一件事加連結」，Agent 為了看具體參數（如怎麼寫 `commit-request`、怎麼掛 `sol`），還是得點開連結讀目標檔。多一層跳轉只是多讀一個檔案。

2. **【嚴重】「不碰 `wf/public`、`wf/advices` 本文」違反題目要求**
   - **問題**：題目明確要求「合併重複、標示過期、避開已知的坑」。這兩處累積了 50 條各隊隨手寫的經驗，裡面混有舊代（codex、terra）的過期做法與重複紀錄。
   - **實務後果**：規矩檔只放一行指過去，卻不清理目標檔，Agent 順著指標讀進去反而讀到過期經驗或花大量 token 翻找。

3. **【中度】D5 新增 `aos/pitfalls.json` 與「去哪查坑」，不符合 Agent 查資料的習慣**
   - **問題**：設計稿把坑拆成「產品的坑（`pitfalls.json`）」跟「團隊的坑（`wf/public`）」。
   - **實務後果**：Agent 做事時是**按任務或按工具查文件**（例如要派工就查 `subagent.json`，要交件就看 commit 規矩），不會在動手前特別去翻兩個「坑專區」並自己分辨這是產品坑還是團隊坑。坑不寫在工具與步驟旁邊，就只能等撞牆後才查得到。

4. **【中度】D1 把舊文搬去「同夾的 `沿革.md`」，會污染 `INDEX.md` 與搜尋結果**
   - **問題**：鐵律要求所有檔案透過 `index_gen` 進索引。若每個現役資料夾都多出 `沿革.md`（加上 `07` 拆成三份），這些歷史檔會跟現行規矩並排。
   - **實務後果**：Agent 掃描目錄或搜尋關鍵字時，極易讀到 `沿革.md` 裡的舊做法（如自己跑 `index_gen`）。此外，拆檔與新增沿革檔屬於結構變更，需明確列出清單由使用者拍板。

5. **【中度】D5 漏掉「7 支沒頁的 CLI 指令」，也沒檢查 JSON 單一 Key 的肥大問題**
   - **問題**：盤點說「沒頁的工具 23 支、沒頁的指令 7 支」，設計稿卻只交代 23 支工具怎麼指，**7 支 CLI 指令完全沒下文**。另外，雖然 JSON 是按鍵讀取（`json_get FILE#/key`），但設計稿沒檢查是否有「單一 key 動輒好幾 KB」或「`_index.json` 描述太簡略導致 Agent 盲猜亂讀」的問題。

6. **【輕度】缺少多團隊平行運作下的「止血與交件順序」**
   - **問題**：現在多支隊伍同時在跑（`sol-1`、`ok-astra` 也在改知識庫），大改寫要等使用者批准，這段空窗期新人還是在讀衝突的鐵律 3 與舊的 07。

## (B) 改進提案：怎樣真正做到「找得快、讀得少、不踩坑」

1. **【反對 D2】不建 `quick.md`，直接把入口鏈的 `aos-teams.md` 壓成 4 KB 實戰速查**
   - **做法**：既然 D1 要把 `aos-teams.md`（現 8 KB）的舊文搬走，搬空後直接把「最常查的 5 件事（commit、掛 sol、等隊員、問使用者、活樹禁忌）」的**具體指令與參數**寫在 `aos-teams.md` 正文（控制在 4 KB 內）。
   - **好處**：新人順著既有入口 `AGENTS.md → user.md → aos-teams.md` 讀完（合計約 10 KB）就能直接開工，80% 情境根本不用再往下讀 `06`、`07`，也不用多維護一張 `quick.md`。

2. **【反對 D1/D5】舊文統一隔離到 `wf/archive/history/`；坑直接釘在工具 Key 與步驟旁**
   - **舊文隔離**：不准在現役資料夾放 `沿革.md`。所有移出的舊條文統一搬去 `wf/archive/history/<原檔名>-沿革.md`（請使用者批准此結構），原檔底部只留一行指過去。確保現役目錄與索引 100% 只有現行做法。
   - **坑隨工具走**：不建 `aos/pitfalls.json`。產品的坑直接寫進該知識庫 JSON 的固定欄位（例如統一在相關檔案加 `#/pitfalls` key，或在 `#/overview` 結尾加 3 行 `⚠️ Pitfalls`）；團隊的坑直接寫進對應規矩檔的步驟底下。Agent 查工具或看步驟時必定同時看到警告。

3. **【補齊缺口】把 `wf/public` 與 `wf/advices` 的 50 條經驗做「升格、合併、標過期」**
   - **升格**：已變成團隊常規的做法（如 `commit-request` 細節），提煉 2～3 行併入現役規矩檔；原經驗檔開頭加上 `[已併入 XXX，本文留存備查]`。
   - **合併**：講同一件事的多篇經驗，合併到主篇，舊篇全文移至主篇底部的 `# 歷史紀錄` 段（一字不刪）。
   - **標過期**：codex / `/mnt/c` 年代的經驗，在檔案第一行摘要直接標 `[過期：proto5/codex 年代]`，讓 `index_gen` 產出的索引一眼看出不必讀（整檔封存或合併清單交使用者拍板）。

4. **【強化 D5】把 `_index.json` 改成「直達路由表」，補齊 7 支 CLI，限制單一 Key 大小**
   - **直達路由**：在 `tools/_index.json` 與 `cli/_index.json` 補齊 23 支工具與 **7 支漏掉的 CLI 指令**時，直接寫明目標路徑與一句話用途（如 `"self_xxx": "-> me/xxx.json#/usage : 用於..."`），讓 Agent 讀完 `_index.json` 就能直接對目標下 `json_get`，少跳一層。
   - **Key 瘦身**：清查知識庫，規定單一 JSON key 不超過 2 KB；太長的拆成 `#/overview`、`#/args`、`#/examples`，保證每次 `json_get` 讀到的都是精準短文。

5. **【調整執行順序】先做「不需審批的衝突標註與索引修復」，再送「一頁式裁決表」**
   - **立即止血**：在等使用者拍板改鐵律與拆檔前，先在 `07` 等檔案舊段落開頭補上 `[以下為歷史做法，現行請見第 X 行]`（屬於小幅事實標示，不刪改原文），並先交 D5 的錯誤代號表、壞指標與工具索引。
   - **一頁拍板**：把「鐵律 3 新舊字面對照、要搬進 archive 的檔案清單、8 KB 門檻放寬」整理成一張核對表交給使用者一次勾選。
