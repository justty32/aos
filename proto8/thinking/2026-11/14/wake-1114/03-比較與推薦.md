# wake-1114 03 比較與推薦：沒開畫面的 eca claude 怎麼及時收到 aos 信

← [wake-1114](../wake-1114.md)｜實測 [02](02-實測.md)｜備料 [01](01-備料.md)｜Argon 審過，採納見 [05](05-採納表.md)（本稿是採納後的版本）

## 結論先講

- **主案 S：stdin 改用 stream-json、先不關。** 非互動那條路照樣「一輪起一個 `claude -p`」，只是 stdin 改成 `--input-format stream-json`。
  - 第一批信寫進去先不關 stdin。等回答的時候，queue 來了新信就再寫一行進去。
  - 看到 result、而且沒有要投的信，才關 stdin，讓它結束。
  - 一輪在跑時，信在**下一個工具空檔**就進對話（手上工具剩下的時間＋1～2 秒）；行程在等背景任務時約 1 秒。
  - 官方介面，不靠 Claude Code 沒寫進文件的 socket，也不用開「跨 session 訊息直接收」；不會有收尾時才投信的競態。
  - 實測見 02 的 stdin 探針。這是 Argon 的提案 B-1。
- **備案 A：沒畫面也走收件 socket**，也就是本線原本的主案。原型已在暫存樹跑通，15 封不掉、不重複。主案 S 哪裡不行（例如 stream-json 輸入跟 `--resume` 或某些旗標不合），就換這條。
- **第二備案 B：Claude Code 自己的 hook**，也就是 PostToolUse 加 additionalContext，或 Stop hook 加 `decision: block`。兩種都要在 system 先講明「aos 的信會從這裡來」，不然模型當成提示注入。
- **配套 C（兩案都要）：長工作丟背景。** 一個 30 分鐘的前景 Bash，任何做法都只能等它做完。eca 的 system 寫明「長指令用 run_in_background，再用 Monitor 看」。
- **冷卻中不叫醒**：冷卻代表剛失敗過，叫醒只會再失敗。急件要不要略過冷卻，交使用者選。
- **判斷：中改，要使用者看一眼再施工**（Argon 第 12 條）。
  - 程式只動 `lib/agent/cli_print.py`、`cli_ask.py` 和 `cmd/aos-eca/aos_eca/midturn.py`，主案估 120～150 行。
  - 但「一輪一個題目、一個回答」的前提變了，而且存檔當下，活樹所有沒開畫面的 eca 都會受影響。
  - 所以加開關 `live_mail`，**預設關**，先開一兩隻試。

## 主案 S 施工要點（給施工線，不在本線做）

1. **開關**：cli.json 寫 `"live_mail": true` 才走；預設關。codex 不走這條。
2. **起 CLI**：argv 加 `--input-format stream-json`。題目包成一行 `{"type":"user","message":{"role":"user","content":...}}`。
   - 寫完先不關 stdin，然後叫 handed。
   - 有 reseed 的話，跟原本一樣接在題目前面。
3. **讀寫迴圈**：用 select 讀 stdout（with selector，0.5 秒節流，EOF 時處理最後沒換行的那段）。每 0.5 秒醒一次：
   - 還沒到上限，就用 `more.take()` 拿信，寫進 stdin，叫 `more.sent()`。寫進 stdin 就算交出去，跟現況一致。
   - 看到一個 result，就把那段回答馬上寫進 history，一個 result 接一行 assistant。
   - 看到 result、而且 queue 沒有新信，就關 stdin。
4. **上限**：一輪最多中途投 5 封，或一輪跑超過 300 秒就不再投（數字交使用者定，預設照這個）。到上限就關 stdin，剩下的留給下一輪。
5. **逾時**：被砍或結束碼不是 0，就不再寫新信。還沒寫進去的信留在 queue；已經寫進 history 的回答保留。
6. **midturn.More**：
   - 改成一次能拿好幾封；遇到 slash 指令就停在它前面。
   - 修 Argon 第 10 條的 `cur/` 卡住：先寫測試重現，確認是現況的 bug，畫面那條路也一起修。
   - 冷卻剛到期那一輪照舊不給 More。
7. **急件**（接 ok-board）：普通信和急件要不要分時機（Argon B-3），預設交使用者選。急件的信封開頭標「急件」。
8. **測試**：
   - 單元測試：讀寫迴圈、上限、逾時、多個 result。
   - 暫存樹 haiku 實測：重跑 02 那幾組。
   - **開開關前要驗**：sonnet 或 opus 在三步改檔的中途收到普通信和急件，原本的工作有沒有做完、新信有沒有回（Argon 第 3 條）。
9. **說明**：`cli_session.py` 開頭、`aos-eca-turn` docstring、`templates/eca-claude/README.md`、`templates/docs/01-eca-claude.md`、知識庫 `aos/cli/eca.json` 改「沒開畫面」那段。知識庫是活樹的複本，由頂層換。

## 跟鐵律有沒有衝突

- **鐵律 2（不開新工作）**：本線只研究、只做原型，沒動 proto8 的程式。施工要另外放行。
- **06 第 5 條（改 repo＝改活樹）**：`lib/agent/*.py`、`cmd/aos-eca` 存檔當下，活樹的 eca 就在用，包括頂層 repo-aos 和各條 ok-* 線。所以：
  - 新程式先放在新函式裡，測到綠。
  - 開關預設關。
  - 接線放在最後一個 commit，動手前先回報。
- **鐵律 5（方向是使用者的）**：「施工不施工」「預設全開還是逐隻開」「急件要不要略過冷卻、要不要插隊」都寄使用者專區。

## 跟其他線的接點

- **ok-board（急件）**：急件走 S 的路，在 turn 中途進對話，不用另做叫醒。睡著或停掉的 agent，照 ok-board U7 第一版不叫醒。
- **ok-kf（C′ screen_linger）**：S 不靠畫面，跟 linger 沒有衝突。畫面開著時照舊走畫面那條路。
- **ok-pilot（hook 實測）**：B 用的是 Claude Code 自己的 hook，跟 aos 的 before_tool、after_tool 不同；aos 那組看不到 CLI 自己的 Bash。
- **11-13 a2a 線**：T6 已經實測過 `-p` 有 socket。當時只做畫面那條路，沒畫面那條「照舊」，沒寫理由（01）。本線接著做那一半。
