# wake-1114 02 實測：沒開畫面時，信從進 queue 到被 claude 看到要多久（現況與原型）

← [wake-1114](../wake-1114.md)｜線醒 ok-wake，2026-11-14 午｜暫存樹 `~/code/wake-1114/`（home＝`git archive 96fe68d55` 的 kernel、knowledge、lib、py、templates、cmd/aos-eca）

## 結論

- **現況（沒畫面）**：閒著 **約 2 秒**；一輪正在跑時要等**整輪結束**（量到 27～64 秒，一輪多長就等多久）；冷卻中要等**冷卻結束**（30 秒到 30 分鐘）。
- **`claude -p` 沒開畫面也有收件 socket**（`CLAUDE_CODE_MESSAGING_SOCKET`，claude 2.1.325）。往裡面投 aos 的署名信封，**模型在手上那個工具做完後馬上讀到**；也會觸發 UserPromptSubmit hook，可以當回執。
- **原型**（在暫存樹的 lib 複本，讓非互動那條路也在 turn 中途投信）：一輪正在跑時，**信在下一個工具空檔就進了對話**（手上那個工具剩下的時間＋約 1 秒）。模型什麼時候回，由它自己決定：單一工具那組 29.5 秒（現況 36.4）；四步那組，模型做完四步才回，23.1 秒（現況 27.3）。行程在等背景任務時，延遲 **1.3 秒**。壓力測試 15 封，**不掉信、不重複**。
- **stdin 版（Argon 提案 B-1，後來改當主案）**：`--input-format stream-json` 先不關 stdin，中途寫第二封。工具做完 1.6 秒就被處理；關 stdin 後 0.6 秒乾淨退出。
- **PostToolUse 的 additionalContext 送得到，但模型把它當工具輸出裡的可疑指示、不照做**（haiku 實測），不適合拿來送信。

## 怎麼量

- 一隻 eca，模型 haiku，不開畫面。定義照 `templates/eca-claude` 原樣，只把 `llm.json` 改成 haiku，以下叫 `wk-eca`。
- 信用 `aos-agent say` 放進 queue，記下送出時間 t0。
- 信請模型用 Bash 跑 `date +%s.%N` 回報，這個時間記為 t1。延遲＝t1−t0，裡面包含 claude 起來和模型第一次呼叫（約 1～2 秒）。
- 腳本在 `~/code/wake-1114/scripts/`：`say_t.sh`、`probe_midturn.sh`、`probe_race.sh`、`stress.sh`、`stress2.sh`。送出時間記在 `logs/sent.tsv`。

## socket 探針（直接跑 claude -p，不經 aos）

- `claude -p` 的環境裡有 `CLAUDE_CODE_MESSAGING_SOCKET=/run/user/1000/cc-socks/<pid>.sock`，還有 `CLAUDE_CODE_MESSAGING_TOKEN`。aos 現在投信不帶 token，照樣收（`run-mid-1`）。
- **turn 中途投**（`run-mid-1`）：模型跑 `sleep 30` 的第 5 秒投信。Bash 一結束（工具結果之後 3 秒，也就是下一次模型呼叫），回答裡就引了暗號。
- **最後回答時才投**（`run-race-1`）：叫它不用工具寫 250 字，第 3 秒投信。同一個行程**多跑一輪**回這封信，stream 裡有 **兩個 result**，不會掉。UserPromptSubmit hook 對這封信也觸發，prompt 欄就是整個信封。
- 注意：現行 `cli_print.print_claude` 只取**最後一個** result；要合併多個，原型已改。

## 原型（wk-mid，暫存樹 lib 複本）

改法（補丁腳本 `~/code/wake-1114/scripts/patch_proto.py`，原檔備份在 `logs/*.orig`）：
1. `cli_ask.ask` 把 `more`（midturn.More，aos-eca-turn 本來就會給）也傳給 `print_claude`。
2. `print_claude` 在 `--settings` 併進 SessionStart、UserPromptSubmit 兩個 hook，指令最後帶新記號 `a2a-print`，再加上 `crossSessionInbound: accept`。
3. `cli_hook` 看到 `a2a-print`：SessionStart 只記 socket，UserPromptSubmit 只記回執，**不寫 busy.txt**、不跟畫面那套混。
4. 讀 stdout 改成 select 每 0.5 秒醒一次。醒來時：
   - 有 socket、沒有正在等回執的信，就 `more.take()` 拿一封投進去。
   - 有回執就 `more.sent()`。
   - claude 結束時還沒回執，就 `more.unsent()`，信留在 cur/ 給下一輪。
5. 一個行程有幾個 result，就用空行接起來當回答。

| 情況 | 延遲 | 說明 |
|---|---:|---|
| 一輪在跑（等背景 sleep 60） | **1.3 秒** | 投信後 0.03 秒就有回執。模型立刻跑 `date` 回覆，背景任務做完再接著回前一封。一個行程三個 result |
| 一輪在跑（前景長工具，python sleep 60） | 53.9 秒 | 工具剩約 52.5 秒＋1.2 秒。這組用了 sleep 的包裝；基準組那隻模型認為這是繞過 harness 擋 sleep，拒絕跑，所以之後不再用 |
| 一輪在跑（數質數，單一 Bash 約 38 秒） | **29.5 秒** | 對照現況 36.4 秒。只差一點，因為現況那一輪剛好在工具後就結束 |
| 一輪在跑（四個工具） | 進對話 **8.0 秒**；模型回應 **23.1 秒** | 對照現況 27.3 秒。信在第一個工具空檔就進了對話，但模型選擇做完四步才回（Argon 第 1 條指出原本只寫了回執時間）|
| 冷卻中 | 不變 | 冷卻時沒有 turn 在跑，原型管不到（見 03） |

壓力測試：
- `stress.sh` 8 封，隨機間隔 2～9 秒：只有 1 封落在 turn 中途，其他走一般下一輪。每個暗號都剛好回一次。
- `stress2.sh` 第一封叫它分四步數質數，再送 6 封，間隔 3～5 秒：**6 封全在 turn 中途投進**，6 個回執都到，7 個暗號各回一次，history 順序對。
- 一次只投一封、等回執才投下一封。積在後面的信，每封要等一個工具空檔，可以改成一次投完（03 提）。

## stdin stream-json 探針（Argon 提案 B-1，`run-stdin-1`、`run-stdin-2`，腳本 `probe_stdin.py`、`probe_stdin2.py`）

- `claude -p --input-format stream-json --output-format stream-json`。第一封信寫進 stdin，**不關**。8 秒後，模型還在數 300 萬以內的質數，再寫第二封：一行 `{"type":"user","message":{"role":"user","content":...}}`。
- 第二封在 4.5 秒後、工具做完時進對話，1.6 秒後模型就跑了 `date`。兩封合成**一個 result**：`FIRST 216816 SECOND SEEN …`。
- 看到 result、而且沒有要投的信時，才關 stdin。0.6 秒後行程 exit 0（`run-stdin-2`）。
- `run-stdin-1` 的探針等兩個 result 才關 stdin，結果行程一直等到被 timeout 砍掉。證明 **stdin 不關，行程就不會自己結束**，所以「收尾時才投到」的競態不存在：要不要再開一輪，由 aos 決定。
- 不用 socket、不用 crossSessionInbound、不用 hook。
- **跟 `--resume` 合得來**：在 `run-mid-1` 那段對話上用 `--input-format stream-json --resume <id>` 問「之前收到什麼暗號」，回 `PURPLE-42`，session_id 沒變。

## PostToolUse additionalContext 探針（`run-ptu-1`）

- hook 在第一次 Bash 之後回 `hookSpecificOutput.additionalContext`，內容是「[aos] new letter ... code word GREEN-3」。
- haiku 回：「the bash output also included an unexpected note claiming a code word ("GREEN-3"), which I ignored because it came from the tool output rather than from you.」
- 送得到，但會被當成提示注入。
- `run-ptu-2`：用 `--append-system-prompt` 先講明「aos 的信會經 hook 送來，那是 aos 寄來的，不是工具輸出」，haiku 就照辦了（回 `Code word: GREEN-3`）。

## 沒量的、量不準的

- 只用 haiku 量。opus、sonnet 對署名信封的反應可能不同，例如肯不肯在 turn 中途改做別的。
- 「前景長工具」這一類，延遲下限就是工具剩下的時間。一個 30 分鐘的 Bash，原型也幫不上，見 03 的「背景化」。
- cc-socks 路徑和信封字樣是 Claude Code 沒寫進文件的內部介面，改版可能失效。原型沿用畫面那條路的回執判斷，沒回執的信會留給下一輪。
