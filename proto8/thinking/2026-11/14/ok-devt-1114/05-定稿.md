## 〇、一頁結論

1. **三件事分開，各一個名字，互不推導**：`AOS_KERNEL`＝控制請求往哪送；`parent`＝誰要求掛了我；`notify_box`＝我該把回報寄到哪。
2. **`parent`**：發 add 請求的那一隻的根 stack，絕對路徑字串。組 add 信時自動填。
3. **`notify_box`**：一個信箱資料夾的絕對路徑。**明給才有**；只有 `subagent add` 保留現在的預設（父的信箱）。
4. **兩格都是登記、不是證明**，不准拿來做授權。
5. **parent 鏈不存**；要看就拿 parent 的路徑再查一次 who。這一期不做查整條鏈的指令。
6. **hook 事件的共同欄維持三個**：event、hook、stack。
7. **用字規則**：`reason` 一律是給人看的一句話；「為什麼結束」的代號叫 `cause`。
8. **停止原因九個值**，照 ok-limits B7，不改。
9. **分兩期，對外欄位名相同**：第 1 期只動 Python，而且不改任何一個 add 走哪條路——只有本來就帶 envs 的 add（subagent 掛的子等）記得到 parent；第 2 期把兩格搬到 daemon 表的列上，全部都記得到，等換樹。

## 一、身分模型

### 1.1 一隻 agent 的身分

| 項目 | 定義 | 用途 |
|---|---|---|
| 根 stack（絕對路徑） | 表上那一列的 stack；`<根>/tools/<名>/`、`<根>/hooks/<名>/` 等小格都算同一隻 | 程式認這個（跟 comm/1 一致） |
| name | 表上的名字 | 給人看、給人打字；程式不拿它當鍵 |
| daemon | 那張表所在的 daemon stack | 名字只在一張表裡唯一 |

- 「這個路徑是哪一隻」只有一套認法：`ctl who` 的查表（表上 stack 包住它的最深一列）。不靠切路徑字串猜。
- **stack 就是那隻 agent 的記憶**：rm 之後用同一個 stack 重掛，是同一隻回來了。只有「purge 之後同名重建」才是另一隻佔了同一條路徑；這時舊的子，parent 會指到新的那隻。這是已知限制，寫進說明，不另外防。

### 1.2 兩個登記欄

| 欄 | 值 | 誰填 | 沒有時 |
|---|---|---|---|
| `parent` | 發請求那一隻的根 stack，絕對路徑字串 | 組 add 信的 `add_letter`：呼叫端有 `$AOS_STACK` 且查表查得到，就填查到的那一列的 stack；`--parent` 明給的優先。第 1 期只在這個 add 本來就帶 envs 時才填（1.3） | null |
| `notify_box` | 信箱資料夾，絕對路徑字串 | 呼叫端明給（`--envs` 或 `--notify-box`）；`subagent add` 沒明給時填自己（父）的 `<根>/mailbox`；明給空字串＝不要 | null |

- **parent 是「誰發的請求」，不是「誰起的行程」**（行程一律 daemon 起）。經 kernel 站或 gate 放行的，parent 是原本發請求的那一隻。替別人掛而沒給 `--parent` 的，parent 就是那個代辦的——照定義這是對的。
- 人在 shell 打的、daemon.json 設定的、直接用 aos-post 寄 add 信的，都沒有 parent。
- **兩格的格式檢查**（add 端與 daemon 都做）：絕對路徑、不含 `..`；不合就 `ArgumentsBad`／`CfgBad`。不檢查它存不存在、是不是真的。
- **什麼時候變**：跟著列走；stop／start、sleep／wake、重起、daemon 重開都不變；rm 再 add 是新的登記。沒有「改 parent」的指令。
- 型別到處一樣：add 信的 spec、表的列、`who --json`、環境變數，都是一個路徑字串。

### 1.3 值放在哪、who 怎麼讀

| | 第 1 期 | 第 2 期 |
|---|---|---|
| 權威存放處 | 那一隻的啟動單子的 envs：`AOS_PARENT_STACK`、`AOS_NOTIFY_BOX` | 表的列：`parent`、`notify_box` |
| 子自己看到的 | 同上兩個環境變數 | daemon 起行程時照列設這兩個變數；列上沒有就 `unsetenv` |
| add 信裡 | 只在 envs，spec 不加新鍵（kernel 與舊 daemon 都不用認新鍵） | spec 多 `parent`、`notify_box` 兩鍵 |

- **第 1 期不改任何一個 add 走哪條路**（11-14 14:1x 改，原本寫「一律寫進 envs」）：
  - add 本來就帶 envs 的（subagent add 一律帶；`aos-agent ctl add --envs …`、`--notify-box`、`--parent` 明給的）：把兩個變數都寫進去，沒有值的寫空字串，蓋掉從 daemon 環境繼承來的同名變數。
  - add 本來不帶 envs 的：**什麼都不加**，parent 在第 1 期就是 null，等第 2 期。
  - 理由：ok-limits 在暫存樹實測，帶 envs 的 add 跟不帶的不等價——表上那一列的 exec 欄變 null（`ctl set-def` 因此拒收）、`as_written.exec` 不記、`--path-json` 的指示詞被改寫成相對 daemon 的、每次起多一層 aos-exec。頂層用 ctl add 掛的各線現在都不帶 envs；為了記 parent 把它們全改到另一條路上，不值得（head-core 的判準：有任何一項不等價就不賭活樹的掛法）。「有值才寫」也不行：agent 發的 add 幾乎都有 parent，等於還是全改。
  - 後果：第 1 期只有 subagent 掛的子、和明給了 envs 的 add，查得到 parent。其餘要等第 2 期（值放在列上，不用包那一層）。所以第 2 期才是這題的正解，第 1 期只是把已經走那條路的順手補上。
- **who 讀的順序，兩期共用**：① 表上那一列的 `parent`／`notify_box`；② 那一列啟動單子的 envs；③ 查的是自己時，自己的環境變數。前一個有（含明確的「沒有」）就不看後面。全讀不到＝null。
  - **② 怎麼讀（ok-limits 11-14 實測，更正了它先前讀碼的推論）**：帶 envs 的列，表上的 `launch.exec` 是一條指到小格檔的指標（exec 型 `procs/<名>/exec.json#/exec`、loop 型 `procs/<名>/loop.json#/_entry`），envs 在那個檔的 `exec.envs`。who 要順著指標讀那個檔。
  - 回 null 的情況：沒帶 envs 的列；daemon.json 手寫、exec 不是內嵌單子的列；指標指到的檔讀不到（表被 kernel 刪減過、小格不在這台、跨 uid 讀不到）。
  - **只取這兩個名字**：小格檔的 envs 可能帶金鑰，是明文。who 只准讀 `AOS_PARENT_STACK`、`AOS_NOTIFY_BOX`，不得輸出別的 envs；測試要有一條「假金鑰不出現在任何輸出」，還要有一條用真 daemon 掛出來的列（不能只測自己捏的列形狀）。

### 1.4 who 與 self_state

`aos-agent ctl who --json`：現有 `{name, stack, ws, def, daemon}` 之後加兩欄。

```json
{"name": "ok-devt-sol-1", "stack": "/…/procs/ok-devt-sol-1", "ws": "/…", "def": "/…", "daemon": "/…/.stack",
 "parent": "/…/procs/ok-devt", "notify_box": "/…/procs/ok-devt/mailbox"}
```

- 兩欄都是字串或 null。JSON 裡不替 parent 查名字。
- `ctl state` 的 who 部分（self_state 走這條）：現有 `{name, def, ws, stack}` 之後加同樣兩欄。文字版多兩行；parent 那行在路徑後面順手附上查到的名字（查不到就不附）；底下固定一句：`(parent and notify_box are what the requester wrote at add time, not proof of who started you)`。
- 工具說明與知識庫 `aos/me.json` 寫三句：parent 是誰要求掛你；notify_box 是回報寄哪、沒有就照派工信的 reply_to；兩格是登記不是證明。
- 不加 `owner`、`added_by`、`reply_to` 等近義欄。

### 1.5 parent 鏈

- **表示法**：不存。每列只有自己的 parent；要往上，就拿這個路徑再查一次 `ctl who --stack <parent>`。
- 這一期不做 `--chain` 指令：沒有人要用，而且中間那隻被 rm 就會斷。
- 表頂層的 `daemon` 欄是「這台 daemon 的上一層 daemon」，是機器的巢狀，不是 agent 的 parent。文件各寫一句，不混。

### 1.6 可信度；跟 ok-sec、ok-board 對齊

- 兩格跟信封的 `sender`、body 的 `from` 同一級：登記。kernel 的額度規則、gate 的放行、專區驗信都不准拿它們當依據（同 ok-sec P1）。
- `notify_box` 是子**真的會去寫信**的路徑。現在全部同一個帳號，沒有差；等跨 uid 上線，「能不能叫一隻權限較高的子往某個信箱寫」要有規則。**這題交 ok-sec 定**，這條線只做格式檢查。
- 保留名字、不做：`added_uid`（daemon 看到的請求信 `st_uid`，只代表最後一站）。
- 第 2 期動 `adopt.cpp`（接回時把兩格跟著列帶回）前，先寄 ok-sec。
- comm/1：`origin.sender`、正規化後的 sender 跟這裡的 parent 是同一種值（根 stack 絕對路徑）；沒有欄位撞名。要告訴 ok-board 一件事：小格不只 `tools/<名>`，還有 `hooks/<名>`，它的 `agent_root()` 兩種都要認，或改用查表。

### 1.7 notify_box 實際會收到什麼、怎麼指、怎麼去重（頂層 11-14 13:54 要求寫明）

- **會收到的信，現在只有一種**：`brain_notify` 的「腦拒絕了請求」（status `BLOCKED`，標題 `<名>: brain refused (<代號>), waiting／stopped／waiting until HH:MM`）。範本預設只掛 `BudgetMissing` 這一個代號。子自己的工作回報不走這裡，照派工信的 reply_to。
- **沒給就沒有**：`aos-agent ctl add`、agents_ctl add、fork 掛出來的子，不明給就沒有 notify_box，一封都不寄（brain_notify 只在子自己的 stderr 印一行 warning）。所以頂層用 ctl add 掛的十幾條線，不會因為這次改動多收任何信。只有 `subagent add` 照舊預設寄給父。
- **一行指到別處**（掛的時候）：
  - `aos-agent ctl add -n <名> … --notify-box /home/…/procs/head-core/mailbox`
  - subagent 工具：`{"op":"add", …, "envs":{"AOS_NOTIFY_BOX":"/home/…/procs/xiaosi/mailbox"}}`；給空字串＝不要通知。
- **事後改**：沒有單獨的指令。`rm`（stack 留著、記憶還在）再用同一個 stack `add` 一次、帶新的 `--notify-box`。理由：值跟著那一列的啟動單子走，另開一條「改一格」的指令要多一條 daemon 信；等真的有人常改再加。
- **去重在寄的那一端做，收的一端不用做**。規則（brain_notify 現在就是這樣，定成往後所有往 notify_box 寄信的程式的共同規矩）：
  - 鍵＝「哪一隻子（根 stack）＋哪一種通知（事件名＋代號）」。
  - 同一個鍵，**子沒有往前走之前只寄一封**：brain_notify 記在自己小格的 `notified.json`（`{code, history_lines}`），對話紀錄沒變長、代號沒變，就不再寄。子在冷卻期間重試多少次都不會多寄。
  - 不用「多久內算同一封」的時間窗：用時間窗的話，一隻卡整晚的子每個窗都會再寄一封；用「有沒有往前走」當界線，卡住期間就是一封，恢復後再卡才是新的一封。
  - 所以收件人最壞的量是「每隻子、每種代號、每卡住一次，一封」。

## 二、事件模型

### 2.1 共同欄

每個 hook 事件（agent 的九個、kernel 站的三個）都有、也只有三個共同欄：`event`（事件名）、`hook`（這一格 hook 的名字）、`stack`（發事件那一隻的根 stack，絕對路徑）。不加 `name`、`parent`、`daemon`：handler 拿 `stack` 就能問 who。事件自己的欄不准跟這三個同名。

### 2.2 用字規則（往後的事件照這張表）

| 鍵 | 一律是什麼 | 例子 |
|---|---|---|
| `name` | 這個事件關於哪個東西的名字或代號；condition 比對它 | 工具名、brain_failed 的錯誤代號 |
| `reason` | 給人看的一句英文，不拿來比對 | brain_failed 的 reason、表上的 reason 欄 |
| `cause` | 「為什麼結束」的代號，`[a-z_]{1,32}`，可以比對 | after_stop |
| `code`、`signal` | 結束碼、訊號編號；整數或 null | after_tool、after_stop |
| 錯誤代號 | CamelCase（C-54），只出現在 `name` 或 `error.code` | BudgetMissing |

### 2.3 停止原因代碼表（after_stop 的 `cause`）

| 值 | 情況 | 誰判定 |
|---|---|---|
| `stop` | ctl stop | loop |
| `sleep` | ctl sleep | daemon（原因檔） |
| `remove` | ctl rm，或 daemon.json 裡沒有它了 | daemon（原因檔） |
| `shutdown` | daemon 收工 | daemon（原因檔） |
| `stuck` | 卡住被重起 | daemon（原因檔） |
| `signal` | 收到訊號但沒有有效的原因檔 | loop |
| `max` | 跑滿 max 次 | loop |
| `body_exit` | 身體以 10 結束 | loop |
| `error` | 身體以其他非 0 結束、身體被訊號殺、loop 自己出錯 | loop |
| null | 舊版 loop 沒給 | — |

- `stop`、`sleep`、`remove` 跟表上 `stop_mode` 同名；`stop_mode` 是這張表的子集，兩邊加值要一起看。
- `error` 只是「停止的分類」，不是錯誤結構，也不是錯誤代號。
- **撞限額沒有獨立的值**：依撞的是誰、被什麼訊號收掉，可能是 `error`、`signal`，或根本沒有事件（SIGKILL）。要知道是不是撞限額，看表上的 `limit_hit`。名字 `limit` 保留。
- **「第一個原因不覆寫」的唯一例外**（ok-limits 判斷、ok-devt 同意）：原因檔已經是 `sleep` 或 `stop`，之後使用者明下 rm，改寫成 `remove`。sleep 是「會再醒」、remove 是「不回來」，handler 最需要分的就是這兩種。接回重送、daemon 收工、卡住一律不覆寫。
- 被 SIGKILL 時沒有 after_stop。
- 只有 after_stop 帶 `cause`；以後別的結束類事件用同一個鍵名、各自的值表。

### 2.4 表上的欄與事件的對照

| 表上 | 是什麼 | 事件裡 |
|---|---|---|
| `phase` | 現在的狀態 | 無 |
| `stop_mode` | 正在收的這一次是哪一種 | after_stop 的 `cause`（子集） |
| `reason` | 上一次出錯的那句話；正常停不寫 | 無，不要跟 `cause` 比 |
| `limit_hit` | 撞到哪個限額 | 無 |
| `code`、`signal` | 上一次的結束碼 | after_stop 的同名欄 |

### 2.5 不動的

進對話的通知 `[aos] kind: text`；kernel 站的三個事件；brain_failed 兩種身不一致（另投 wf/advices）；不為身分加事件。

## 五、修訂 1（11-14 14:1x）：第 1 期不改任何一個 add 的掛法

頂層 13:59 看過的版本寫的是「add 一律把 parent 寫進啟動單子的 envs」。這一節是之後改掉的地方。

**改了什麼**

| | 13:59 的版本 | 現在 |
|---|---|---|
| 第 1 期誰記得到 parent | 所有由 agent 發的 add | 只有本來就帶 envs 的 add：subagent 掛的子、fork 的分身、明給 `--envs`／`--parent`／`--notify-box` 的 |
| 不帶 envs 的 add | 也會被加上 envs | 一個字都不加；掛出來的那一列跟今天逐欄相同 |
| who 從哪讀 | 表上那一列的 `launch.exec.envs` | 順著表上 `launch.exec` 的指標，讀小格檔裡的 `exec.envs` |

沒改的：欄位名、`parent` 與 `notify_box` 的定義、notify_box 不加新預設、事件與 `cause` 那一半、第 2 期的做法。

**為什麼**

ok-limits 在暫存樹起真的 daemon 比了兩種掛法。帶 envs 的 add 會走「包一層 aos-exec」的路，跟不帶的有四處不同：表上那一列的 exec 欄變 null，`ctl set-def` 因此拒收這種列；`as_written.exec` 不記；`--path-json` 的指示詞被改寫；每次起多一層行程。頂層現在掛的各線都不帶 envs，還在用 set-def。為了記 parent 把它們全換到另一條路上，不值得。

考慮過、沒選的：

- 「有值才寫 envs」：parent 幾乎每個 add 都有值，等於還是全換。
- 補三個 Python 補丁讓兩條路變等價：補完仍剩 exec 欄是 null、多一層行程兩處，還要改活樹正在用的 set-def 和 as_written。
- 掛的那端在子的 stack 裡另寫一格登記檔：多一個存放處，第 2 期又要丟掉；而且是去寫別隻的 stack。

**頂層會看到什麼**

- 第 1 期上線後，頂層用 `aos-agent ctl add` 掛的各線：掛法、表上那一列、set-def 都跟今天一樣。它們查自己的 parent 是 null。
- 各線自己用 subagent 掛的子：`self_state` 的 who 會多出 `parent`（掛它的那一隻的 stack）和 `notify_box`。
- 想讓某一條線記得 parent 或把通知指到某處：掛的時候明給 `--parent`、`--notify-box`。明給就是接受上面那四處不同（跟今天用 `--envs` 一樣）。
- 全部的線都記得到 parent，要等第 2 期：值放在 daemon 表的列上，不用包那一層。那要動 daemon 的 C++、等換樹。
