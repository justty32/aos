# ok-devt-1114 04：Argon 審查採納表（11-14）

← [ok-devt-1114](../ok-devt-1114.md)｜原文 [03](03-Argon原文.md)｜改後的定稿 [05](05-定稿.md)

**結論**：Argon 提 7 點問題、答 5 題、4 個提案。採納後設計變簡單了三處：notify_box 不再有「預設用 parent 的信箱」；`who --chain` 不做；`parent` 到處都是一個路徑字串。另加一處：第 1 期就讓別人查得到（讀表上那一列的啟動單子，不讀自己的環境）。

## (A) 問題

| # | Argon 說 | 採納 | 怎麼改／為什麼不改 |
|---|---|---|---|
| 1-1 | `notify_box=""` 跟 daemon「必須非空，否則 CfgBad」矛盾 | 採納 | 空字串＝不要：第 2 期不把這個鍵寫進 spec |
| 1-2 | 子會繼承 daemon 自己環境裡的 `AOS_PARENT_STACK`、`AOS_NOTIFY_BOX` | 採納 | 第 1 期：add 一律把兩個變數都寫進啟動單子的 envs，沒有就寫空字串，蓋掉繼承來的；who 把空字串當 null。第 2 期：列上沒有就 `unsetenv` |
| 2-1 | 「第一個原因不覆寫」會記錯（sleep 之後才被 stuck、rm 收掉） | 部分 | Argon 假設 sleep 沒收掉的行程會繼續跑；實際上 `term()` 之後 10 秒就 SIGKILL，on_stop 根本跑不到，所以「兩小時後才 shutdown 讀到舊的 sleep」不會發生。剩一個真的情況：sleep 收到一半、10 秒內又 rm，現在會回 `sleep`。這題交給 ok-limits 判斷要不要讓「使用者明下的 rm」蓋過 sleep。「重起時刪原因檔」不採納：不刪檔，舊檔本來就靠 ticks＋boot_id 失效 |
| 2-2 | 自然結束跟訊號搶，會把 max 誤報成 shutdown | 不採納 | B7 6.3 已寫死：只有「收到的是 SIGTERM 且原因檔有效」才用檔裡的值，其餘照 loop 自己判。Argon 沒看到 B7 原文 |
| 2-3 | 外面包 sandbox 時 ticks 對不上；撞限額的不一定是身體 | 部分 | ticks：B7 6.1 第 2 種情況已處理外殼。限額：02 的 2.3 寫「撞到限額的是身體」太武斷，改成「可能落在 error、signal，或根本沒有事件（SIGKILL）；看表上的 limit_hit」。「daemon 主動殺超限行程時寫 limit」不採納：daemon 不主動殺，limit_hit 是事後從死因看出來的 |
| 3 | 同名重掛會重用 stack 路徑，舊子的 parent 會指到新的那隻；鏈會接錯 | 部分 | 在 aos 裡 stack 就是那隻 agent 的記憶：同一個 stack 重掛＝同一隻回來了，parent 指著它是對的。真的認錯只有「purge 之後同名重建」這一種，寫成已知限制。不記 `parent_ticks`：ticks 每次重起都變，父只是 stop／start 就會被當成不在。鏈的問題因為不做 `--chain`（見 B3）而消失 |
| 4-1 | 第 1 期查別隻回 null，跟「本來就沒有」分不出來 | 採納 | 見 B1：第 1 期就從表上那一列的啟動單子讀，別隻也查得到 |
| 4-2 | 在工具小格裡查自己會被當成「不是自己」 | 已經如此 | ok-limits 的 `notify_box_of` 用的是「`$AOS_STACK` 落在那列的 stack 底下」，小格算自己。改成 B1 之後這個判斷只剩兜底用 |
| 4-3 | 升第 2 期時，第 1 期掛的行程會變成查不到 | 採納（換做法） | 不在 adopt.cpp 轉；who 讀的順序定成「列上的欄 → 那一列啟動單子的 envs → 查自己時的環境變數」，兩期共用，沒有斷層 |
| 4-4 | 空字串第 1 期印 `""`、第 2 期是 null | 採納 | 一律 null |
| 5 | `agent_root()` 只切 `tools/`，`hooks/<名>` 會算錯 | 採納（換做法） | 填 parent 不靠切路徑：用 `ctl who` 同一套查表（表上 stack 包住 `$AOS_STACK` 的最深一列）。表查不到才不填。跟 ok-board 的對齊點改成「告訴它 hooks 小格這件事」 |
| 6-1 | `notify_box` 是子真的會去寫信的路徑；跨 uid 時可被拿來叫別人代寫 | 採納一半 | add 端與 daemon 都檢查：絕對路徑、沒有 `..`。「跨 uid 時要不要限制 notify_box 只能指向請求者自己寫得進去的信箱」是 ok-sec 第 2、3 期的規則，寄給 ok-sec，這條線不定。不另外擋「daemon 的控制信箱」這種特例 |
| 6-2 | `who --json` 把 daemon 保證的欄跟自填的欄混在一層，還替 parent 查出名字，看起來像驗過 | 部分 | JSON 裡的 `parent` 改成單純的路徑字串，不查名字（B3）；名字只在文字版順手顯示。欄位維持平的，不另包一層：說明文字與知識庫寫明這兩格是登記 |
| 6-3 | `added_uid` 經過站時是站的 uid | 已經如此 | 02 的 1.6 已寫「只代表最後一站」 |
| 7-1 | `parent` 在 spec／表是字串、在 who 是物件 | 採納 | 到處都是字串。環境變數仍叫 `AOS_PARENT_STACK`（名字說明值是 stack 路徑，也是 advice 原提案的名字） |
| 7-2 | 預留的時間欄叫 `at`，不合 `_at` 結尾的規則 | 採納 | 那一句刪掉，不預留 |
| 7-3 | `cause: "error"` 要說明不是錯誤結構 | 採納 | 值表加一句 |

## 頂層 11-14 13:54 的兩個要求（head-core 轉）

頂層看的是初稿（02）的做法「沒明給 notify_box 就預設寄給掛它的人」，回覆同意、算修補，並要求寫明兩件。定稿採了 Argon 的 B2，那個預設已經拿掉，所以頂層擔心的「掛 16 條線、信箱被灌爆」不會發生；兩個要求仍照答，寫在 05 的 1.7。

| 要求 | 定稿怎麼寫 |
|---|---|
| 一行能把通知改指到部長或 xiaosi | 掛的時候 `--notify-box <信箱路徑>`（subagent 工具用 envs 的 `AOS_NOTIFY_BOX`）。事後改＝rm 再 add，不另開指令 |
| 同一種通知要去重 | 寄的那端做。鍵＝哪一隻子＋事件名＋代號；界線不用時間窗，用「子有沒有往前走」（brain_notify 現有的 `notified.json` 就是這樣）。定成所有往 notify_box 寄信的程式的共同規矩 |

如果頂層其實想收 ctl add 掛出來的線的額度通知：掛的時候加 `--notify-box`，指給自己、部長或 xiaosi 都行；不需要改預設。
