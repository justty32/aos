## 三、上線順序（要緊）

Python 存檔就生效，C++ 要換樹才生效。**舊的 daemon 不認這兩個新鍵**。所以：

1. C++ 先在 repo 外編好、暫存樹測過，排進換樹清單，交 ok-kf。
2. **換樹之後**，第二節的 Python 才 commit。換樹之前 commit 的話，每一個 add 都會被舊 daemon 當成壞設定退回。
3. 第二節 commit 之前，在暫存樹用「新 daemon＋新 Python」跑一次全套 add 路徑；另外確認「舊 Python＋新 daemon」照常能掛（新 daemon 對沒有這兩鍵的 spec 行為不變）。

**兩個時點之間的過渡期（新 daemon 已換上、Python 那半還沒 commit）**：行為跟第 1 期完全一樣，不會壞。

- add 還是第 1 期的寫法：帶 envs 的 add 把兩個變數放在啟動單子的 envs，spec 裡沒有新鍵。新 daemon 看到的列沒有這兩欄。
- who 照 1.3 的順序：① 列上沒有 → ② 順著指標讀小格檔，讀得到。所以 subagent 掛的子照樣查得到 parent；不帶 envs 的 add 照樣是 null。
- 新 daemon 對沒有這兩欄的列會 `unsetenv` 這兩個名字，但帶 envs 的列，變數是後面那一層 aos-exec 照 envs 設的，子行程照樣拿得到。唯一的差別是好的：子不會再繼承到 daemon 自己環境裡的同名變數。

第 1 期掛的行程（值在啟動單子的 envs）不用遷移：who 讀不到列上的欄，就照舊往下讀小格檔；它們自己環境裡的變數由 aos-exec 那一層照 envs 設，不受 daemon `unsetenv` 影響。

## 四、測試

**daemon（暫存樹，clean.sh）**

- spec 帶兩鍵 → 表上那一列有兩欄；子行程環境裡有兩個變數。
- spec 不帶 → 列上沒有這兩欄；daemon 自己的環境裡故意放這兩個變數，子行程環境裡**沒有**。
- 值是相對路徑、帶 `..`、空字串、不是字串 → `CfgBad`，列沒有掛上。
- stop／start、sleep／wake 之後兩欄還在。
- 殺掉 daemon 再開、接回：兩欄還在。沒有現成的接回 fixture 就在交件信寫「沒測、只讀程式」。
- 這兩鍵沒有出現在子 loop 的設定檔裡。
- **不帶 envs 的 add，除了多這兩欄之外，那一列跟改動前逐欄相同**（exec 欄、as_written、launch）。

**Python**

- `aos-agent ctl add`（不帶 envs）由一隻 agent 發 → 列上 parent 是它的根 stack；列的 exec 欄不是 null；`ctl set-def` 照常能用。
- subagent add 沒明給 → notify_box 是父的 mailbox（頂層點名的那條，改成看列上的欄）。
- 經 kernel 站轉的 add → 兩欄還在。
- who：別隻查、自己查都拿得到；交件信附一段真 daemon 起出來的那一列與 `who --json` 的實際輸出（envs 只列變數名）。

## 五、跟別線的交界

- **ok-sec 的 1d**（ok-sec 11-14 14:16 回「可以」）：它在 `adopt.cpp` 改 `same_tree()`、`live_in_cell()`（多一個 expected_uid 參數）與 `Daemon::adopt()` 的呼叫點（約 :279），不動「帶回舊列欄位」那段（約 :282-283），也不帶回任何 uid 欄。兩處只差幾行，rebase 時 git 可能報相鄰衝突，內容不衝突。接回時從舊的 `procs_state.json` 帶回這兩欄，不違反它「不信 state 窗」的規矩（那條指的是小格裡 agent 寫得到的 state.json）；條件是這兩欄永遠不當授權依據。它第 2 期寫環境白名單時會把 `AOS_PARENT_STACK`、`AOS_NOTIFY_BOX` 算進去。

- **ok-sec 第 2、3 期**：`notify_box` 跨 uid 的限制放在 kernel 的 procs 規則（ok-sec 定）。這一件的 daemon 只做格式檢查。
