## 二、事件

- **hook 事件九個**：before_queue、after_queue、before_tool、after_tool、brain_failed、tool_added、after_start、after_stop、on_clock（lib/agent/hooks.py:53-63）。
- **每個事件都有的欄**：`event`、`hook`、`stack`（agent stack 絕對路徑）；事件自己的欄不能蓋這三個（lib/hook_run.py:135-136）。
- **各事件自己的欄**：

| 事件 | 欄 |
|---|---|
| before_queue、after_queue | letter、content |
| before_tool | name、id、arguments |
| after_tool | name、id、arguments、content、code、timed_out |
| brain_failed | name（＝錯誤代號）、reason（一句話）、error?（只有 agent-fsm 身有） |
| tool_added | name、path |
| on_clock | clock、cycle、interval_ms、first、last_cycle、missed |
| after_start | 無 |
| after_stop | code、signal |

- **after_stop 的來源**：aos-loop 的 on_stop 設 `AOS_LOOP_CODE`、`AOS_LOOP_SIGNAL`（impls/aos-loop engine/loop.cpp:84-117），hook_fire 轉成事件（lib/agent/hook_fire/_entry:29-50）。stop＝0／null；sleep、rm、shutdown 都是 143／15；跑滿 max、身體退 10 也是 0／null。唯一的消費者 screen_linger 只用 event 與 stack。
- **daemon 表**：phase 存的值是 running、stopping、done、stopped、sleeping，`stuck` 是顯示時的投影；`stop_mode` 只在 stopping 時出現，值 stop、sleep、remove；`limit_hit` 的值是 limits 的鍵名（cpu_s、file_mb、mem、procs）；`reason` 是英文句子（`failed to start: …`、`failed while running: exited with code N: …`），正常的 stop／sleep／rm／shutdown 不寫（impls/aos-daemon child.hpp:62-63、failure.cpp:13-71、tend.cpp）。
- **命名慣例（C-54）**：錯誤代號 CamelCase、主詞在前、結尾 Missing／Bad／Failed／Rejected…；JSON 鍵小寫加底線；時間欄 `_at` 結尾（docs/CONCEPTS/01-設計理念/04-C-54.md:8-20）。沒有集中的 reason 清單。
- **kernel 站的 hook**：before_verdict、after_verdict、before_reply，用同一個 hook_run 引擎，共同欄一樣是 event、hook、stack（lib/aos/kernel/hooks.py）。
- **進對話的通知**：`[aos] kind: text`，kind 列在 `NOTE_KINDS`（py/aos_flags.py:102-118）。

## 三、蒐集時看到、不在這條線範圍的不一致（已報 head-core）

- limits 的鍵三處規則不同：daemon、daemon_ctl 七鍵且不認得就報錯；aos-sandbox 五鍵、不認得就忽略；kernel limits_rule.py 五鍵。
- kernel 的 users 規則往 limits 寫 `groups`，daemon 不認這個鍵 (推測會被當壞信)。
- brain_failed 兩種身不一致：agent-fsm 有 error 欄，eca 沒有。
- aos-daemon-ctl help 寫 rm 是「stop, then remove」，實作是直接 SIGTERM。
