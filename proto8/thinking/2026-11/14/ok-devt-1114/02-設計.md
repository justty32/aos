# ok-devt-1114 02：daemon 給 agent 的「身分」與「事件」模型（設計稿，送 Argon 前）

← [ok-devt-1114](../ok-devt-1114.md)｜上一份 [01-現況](01-現況.md)

> ok-devt（fable）11-14 設計。現況事實都在 01，這裡只寫決定與理由。還沒過 Argon，不是定稿。
> 範圍：who 與 self_state 要有哪些欄位、hook 事件 JSON 的共同欄位與原因代碼、parent 鏈怎麼表示；跟 ok-board comm/1、ok-sec uid 認人對齊；據此審 ok-limits 的三條小修。

## 〇、一頁結論

1. **三件事分開，各有一個名字**：`AOS_KERNEL`＝控制請求往哪送；`parent`＝誰要求掛了我；`notify_box`＝我該把回報寄到哪。三者互不推導，只有一條預設：沒明給 `notify_box` 時，預設是 parent 的信箱。
2. **`parent` 與 `notify_box` 記在 daemon 表的列上**，由發出 add 的那一端填、daemon 照抄。環境變數 `AOS_PARENT_STACK`、`AOS_NOTIFY_BOX` 只是給子自己看的副本。
3. **它們是「登記」，不是「證明」**：跟信封的 sender 同一個可信度，不拿來做授權。
4. **parent 鏈不存**，要看時沿著表一格一格往上查。
5. **事件的三個共同欄不變**（event、hook、stack），不加新的共同欄。定一條用字規則：`reason` 一律是給人看的一句話；「為什麼結束」的代號叫 `cause`。
6. **停止原因代碼表**九個值，照 ok-limits B7 的值，一個不改。
7. **分兩期**：第 1 期只動 Python，馬上能用，但別人查不到某隻的 parent；第 2 期動 daemon 的 C++，等換樹。兩期對外的欄位名相同。

## 一、身分模型

### 1.1 一隻 agent 的身分是什麼

| 項目 | 定義 | 給誰用 |
|---|---|---|
| 根 stack（絕對路徑） | 表上那一列的 stack。`<根>/tools/<名>/`、`<根>/hooks/<名>/` 這些小格都算同一隻 | **程式認這個**。跟 comm/1「程式認的是 stack 絕對路徑」一致 |
| name | 表上的名字 | 給人看、給人打字。會重複、會被重用，程式不拿它當鍵 |
| daemon | 那張表所在的 daemon stack | 名字只在一張表裡唯一，所以「name＋daemon」才指得到一隻 |

「小格 → 根」的換算只留一份實作：ok-board A2 要新增的 `agent_root()`。這條線要用到的地方（1.3 填 parent）直接呼叫它，不另寫。

### 1.2 新增兩個登記欄

| 欄 | 值 | 沒有時 |
|---|---|---|
| `parent` | 要求掛這一隻的 agent 的根 stack，絕對路徑字串 | 不寫這個鍵。人在 shell 打的、daemon.json 設定的，都沒有 parent |
| `notify_box` | 一個信箱資料夾的絕對路徑：這一隻該把回報、通知寄到哪 | 不寫這個鍵 |

- **parent 的意思是「誰要求的」，不是「誰起的行程」**。行程一律是 daemon 起的（misc-1114 已指出）。經 kernel 站或 gate 放行的 add，parent 仍是原本發請求的那一隻，不是站，也不是 gate。
- **parent 用路徑、不用名字**：名字會被重用。要顯示名字時，查表換算（1.4）。
- **parent 用絕對路徑**：parent 可能在別台 daemon 上（上層 kernel 往下層 daemon 掛），相對路徑會指錯。
- **notify_box 跟 parent 分開存**：派工的人常常要回報寄到別處（部長、彙整員），這正是 skyrim 的結論「派工時明寫回報寄到哪」。

### 1.3 誰填、怎麼流

```
發請求的 agent ──add 信（body.procs_added.<名> 裡帶 parent、notify_box）──▶ [kernel 站／gate：body 原樣轉] ──▶ daemon
                                                                                              │ 照抄進表的列
                                                                                              ▼
                                                             子行程環境：AOS_PARENT_STACK、AOS_NOTIFY_BOX（副本）
```

- **填的地方只有一處**：`py/daemon_ctl` 組 add 信的 `add_letter`。所以 `aos-agent ctl add`、agents_ctl add、subagent add、fork 四條路自動一致，不用各改一次。
  - `parent`：呼叫端有 `$AOS_STACK` 時，填 `agent_root($AOS_STACK)`；沒有就不填。呼叫端可以用 `--parent` 明給（kernel 代別人掛時用），明給的優先。
  - `notify_box`：明給的優先（含空字串＝不要，沿用 2368ee3af 的語意）；沒明給而有 parent 時，填 `<parent>/mailbox`；兩者都沒有就不填。
- **寫在 body 的 spec 裡、不靠信封**：kernel 站轉寄時 body 原樣轉、信封的 sender 會變成站自己，所以寫在 body 才不會在半路變掉。
- **daemon 只照抄**：收到 spec 裡的 `parent`、`notify_box`（都必須是非空字串，否則 `CfgBad`），存在列上，寫進 `procs_state.json`；起子行程時設成 `AOS_PARENT_STACK`、`AOS_NOTIFY_BOX`。daemon 不查這個 parent 存不存在、是不是真的。
- **什麼時候變**：跟著列走。stop／start、sleep／wake、卡住重起、daemon 重開接回，都不變。rm 之後重新 add，是新的一列、新的登記。沒有「改 parent」的指令；要換回報地址，rm 再 add，或派工信裡另寫 reply_to。
- **`aos-daemon-ctl add`**（人用的底層指令）：同一個 `add_letter`，規則相同。人的 shell 通常沒有 `$AOS_STACK`，所以沒有 parent。

### 1.4 who 與 self_state 的欄位

`aos-agent ctl who --json`：

```json
{"name": "ok-devt-sol-1", "stack": "/…/procs/ok-devt-sol-1", "ws": "/…", "def": "/…", "daemon": "/…/.stack",
 "parent": {"stack": "/…/procs/ok-devt", "name": "ok-devt"},
 "notify_box": "/…/procs/ok-devt/mailbox"}
```

- `parent`：沒有登記時是 `null`。有登記時是物件：`stack` 照抄；`name` 是查詢當下在**同一張表**上找到的名字，找不到（已被 rm、或在別台 daemon）就是 `null`。
- `notify_box`：字串或 `null`。
- `ctl state` 的 who 部分（self_state 走這條）：現有四欄之後加同樣兩欄。文字版多兩行 `parent`、`notify_box`，底下一句固定的話：`(parent and notify_box are what the requester wrote at add time, not proof)`。
- 不加 `owner`、`added_by`、`reply_to` 這些近義欄。一件事一個名字。

### 1.5 parent 鏈

- **不存**。每列只記自己的 parent；祖父以上存了會過期（中間那隻被 rm、重掛）。
- **要看時現查**：`aos-agent ctl who --chain`（JSON 多一欄 `chain`，陣列，最近的在前，每項 `{stack, name}`）。做法是拿 parent 的 stack 回同一張表找那一列、讀它的 parent，重複到：沒有 parent、表上找不到、走回已經走過的 stack，或滿 16 層。停在哪一種，寫在最後一項的 `end`：`top`、`unknown`、`loop`、`depth`。
- **不跨 daemon 查**：parent 在別張表時，鏈停在那裡（`unknown`）。跨表要知道別台的表在哪，那是 kernel 的事，這一期不做。
- **daemon 的上下層是另一條軸**：表頂層的 `daemon` 欄記的是「這台 daemon 的上一層 daemon」，是機器的巢狀，不是 agent 的 parent。兩者不混，文件各寫一句。

### 1.6 可信度，以及跟 ok-sec 對齊

- `parent`、`notify_box` 是發請求那端自己寫的，跟信封的 `sender`、body 的 `from` 同一級：**登記，不是證明**。任何規則（kernel 的 by_sender 額度、gate 的放行、專區驗信）都不准拿它們當授權依據。這跟 ok-sec 的 P1「不驗信封上的 sender」同一個立場。
- daemon 表是 daemon 寫的，別人改不了表；但表裡這兩格的**內容**來自請求信。所以「表上寫著」只代表「當初有人這樣登記」。
- 留一個名字、這一期不做：等 ok-sec 的 uid 層上線，daemon 可以把請求信檔案的 `st_uid` 記成列上的 `added_uid`。那一格才是 daemon 自己看到的事實。照 ok-sec 的 Q4，它只代表「最後一站」。
- 這條線不碰 `adopt.cpp` 的認人邏輯、不碰 `aos_sweep_proc.py`。但第 2 期「daemon 重開接回時，這兩格要跟著列帶回來」會動到 adopt 帶回舊列欄位的那一段（現在帶回 reason 的地方），**動手前先寄 ok-sec**。

### 1.7 跟 ok-board comm/1 對齊

- comm/1 的 `origin.sender`、消帳用的「正規化後的 sender」，跟這裡的 `parent` 是同一種值：agent 的根 stack 絕對路徑。同一個 `agent_root()`。
- comm/1 的 `waiting_on.who` 用名字（給人看），跟 1.1「名字給人、路徑給程式」一致。
- 沒有欄位撞名：comm/1 的新欄都收在 `body.comm` 底下；這裡的新欄在表的列、who 的輸出、add 信的 spec 裡。
- 要跟 ok-board 確認的只有一件：`agent_root()` 放在哪個模組，讓 `py/daemon_ctl` 也能 import。

## 二、事件模型

### 2.1 共同欄：維持三個

每個 hook 事件（agent 的九個、kernel 站的三個）都有、也只有這三個共同欄：

| 欄 | 值 |
|---|---|
| `event` | 事件名 |
| `hook` | 這一格 hook 的名字 |
| `stack` | 發事件的那一隻的根 stack，絕對路徑 |

- **不加 `name`、`parent`、`daemon`**：handler 有 `stack` 就能問 `ctl who`；每個事件都先查表會拖慢每一次工具呼叫。
- **不加時間欄**：現有 handler 沒人要；之後真要加，名字用 `at`（跟信封的 `sent_at` 同一套 `_at` 規則）。
- 事件自己的欄不准跟這三個同名（引擎已經這樣擋）。

### 2.2 用字規則（新定，往後的事件都照這張表）

| 鍵 | 一律是什麼 | 現有例子 |
|---|---|---|
| `name` | 這個事件「關於哪個東西」的名字或代號，condition 比對的就是它 | before_tool 的工具名、brain_failed 的錯誤代號 |
| `reason` | **給人看的一句英文**，不拿來比對 | brain_failed 的 reason、表上的 reason 欄、gate refuse 的 reason、錯誤行的後半 |
| `cause` | **「為什麼結束」的代號**：小寫加底線，`[a-z_]{1,32}`，可以拿來比對 | 新：after_stop |
| `code`、`signal` | 結束碼、訊號編號，整數或 null | after_tool、after_stop |
| 錯誤代號 | CamelCase（C-54），只出現在 `name` 或 `error.code` | BudgetMissing |

理由：同一批事件裡，brain_failed 的 `reason` 已經是句子。after_stop 再拿 `reason` 裝代號，寫 handler 的人會把兩種混著比對；表上的 `reason` 欄也會被誤認成同一個東西。

### 2.3 停止原因代碼表（after_stop 的 `cause`）

| 值 | 什麼情況 | 誰判定 |
|---|---|---|
| `stop` | ctl stop（走 ctl 窗，行程自己收工） | loop |
| `sleep` | ctl sleep | daemon（原因檔） |
| `remove` | ctl rm，或 daemon.json 裡沒有它了 | daemon（原因檔） |
| `shutdown` | daemon 收工 | daemon（原因檔） |
| `stuck` | 卡住，被 daemon 重起 | daemon（原因檔） |
| `signal` | 收到訊號，但沒有有效的原因檔（人手 kill、SIGINT、SIGHUP） | loop |
| `max` | 跑滿 max 次 | loop |
| `body_exit` | 身體以 10 結束 | loop |
| `error` | 身體以其他非 0 結束、身體被訊號殺掉、loop 自己出錯 | loop |
| `null` | 舊版 loop 沒給 | — |

- `stop`、`sleep`、`remove` 跟表上 `stop_mode` 的三個值同名，`stop_mode` 是這張表的子集。這點寫進文件，以後兩邊加值要一起看。
- **limits 超限這一期沒有獨立值**，落在 `error`。撞到限額的是身體，loop 只看得到「身體被訊號殺」；真正的判定在 daemon（`limit_hit`），而且是行程退了才寫。文件寫一句：要知道是不是撞限額，看表上的 `limit_hit`。名字 `limit` 保留，之後要加由 daemon 經原因檔給。
- loop 對 daemon 給的值不寫死清單，格式合法就照傳（B7 6.4），所以 daemon 之後加值不用換 loop。
- 被 SIGKILL 時 on_stop 跑不到，沒有事件。這是現況，文件照寫。
- 只有 after_stop 帶 `cause`。現在「結束類」的事件只有這一個；以後有別的結束類事件（例如工具被中止），用同一個鍵名、另一張值表。

### 2.4 表上的欄跟事件的對照（寫進文件，免得再被混）

| 表上的欄 | 是什麼 | 事件裡對應的 |
|---|---|---|
| `phase` | 現在的狀態 | 無 |
| `stop_mode` | 正在收的這一次是哪一種（只在 stopping 時有） | after_stop 的 `cause`（子集） |
| `reason` | 上一次**出錯**的那句話；正常停不寫 | 無。不要拿它跟 `cause` 比 |
| `limit_hit` | 撞到哪個限額 | 無（見 2.3） |
| `code`、`signal` | 上一次結束碼 | after_stop 的 `code`、`signal` |

### 2.5 不在這一期動的

- 進對話的通知 `[aos] kind: text`：是另一條管道，kind 清單在 `NOTE_KINDS`，不改。
- kernel 站的三個事件：共同欄已經一致，不改。
- brain_failed 兩種身的 `error` 欄不一致：記成 wf/advices 意見，不在這條線修。
- 不為「身分」加事件（例如 parent 被 rm 時通知子）：沒有人要，先不做。

- 兩期都不寫遷移：已經在跑的 agent 沒有登記就是沒有，重掛才有。

## 四、據此審 ok-limits 的三條

| 條 | 它的做法 | 合不合 | 要它改的 |
|---|---|---|---|
| files／nofile | 不收別名，報錯時列出認得的鍵；說明的例子改用 files | 合。沒有新欄位 | 無（已正式同意，可先交） |
| after_stop 原因（B7） | daemon 先寫原因檔再送 SIGTERM；loop 用啟動 ticks＋boot_id 認是不是寫給自己；第一個原因不覆寫；九個值 | 機制與值都合 | 只改名字：事件欄 `reason` → `cause`；環境變數 `AOS_LOOP_REASON` → `AOS_LOOP_CAUSE`；原因檔 `stop_reason.json` → `stop_cause.json`，檔裡的鍵 `reason` → `cause`。文件加 2.3、2.4 兩張表 |
| who 的 notify_box | `ctl who --json` 與 `ctl state` 的 who 加 `notify_box`，只有查自己時照實給 `$AOS_NOTIFY_BOX`，否則 null | 合，正好是第 1 期的樣子；欄位名不用改 | (1) 同一處再加 `parent`（讀 `$AOS_PARENT_STACK`，形狀見 1.4）；(2) 那句說明改成 1.4 的固定句；(3) `AOS_NOTIFY_BOX`、`AOS_PARENT_STACK` 改由 `add_letter` 統一補——這一項是新工作，誰做由 head-core 分 |

## 五、請 Argon 特別看的地方

1. 1.3「parent 寫在 add 信 body 的 spec 裡、daemon 照抄」：有沒有哪條 add 路徑不經 `add_letter`，會漏掉？kernel 站改寫 body 的規則（limits 夾限）會不會把這兩個鍵弄丟？
2. 1.3 的預設「沒明給 notify_box 就用 parent 的信箱」套到 fork、agents_ctl add 之後，有沒有壞處（例如通知信迴圈、parent 已經不在時信箱不存在）？
3. 1.5 鏈不存、現查：有沒有非存不可的用途？
4. 2.2 把 `reason` 定成句子、另立 `cause`：值得為一致性改名嗎，還是照 advice 原提案叫 `reason` 就好？
5. 三、第 1 期用環境變數當暫時的存放處：ok-sec 第 1 期之後 environ 跨 uid 讀不到，「只有自己查得到」這個限制會不會在第 2 期前就害到誰？
