## 一、不同之處：先定義交付物，再寫宣傳

「同 repo 加 `docs/`、改 README」最快，但解決的是入口，不一定解決外人拿到什麼、如何成功、哪些資料跟著公開。

我的主張是把兩個角色分開：

- 開發倉庫保留研究與施工脈絡，不為這次發佈大搬家。
- 公開倉庫只接收審核過的產品快照、安裝說明、範例與網站。
- 每次公開版本對應同一份程式、文件、範例與已知限制，不追著開發中的 `main` 跑。
- 第一個成功標準不是「首頁漂亮」，而是陌生人在乾淨環境中照文件完成啟動、派工、觀察與停止。

代價是多一個倉庫與匯出流程；回報是發佈邊界清楚，不必把「研究現場」硬整理成「產品展示間」。公開倉庫不是另一條研發線，不接受雙邊獨立修補；修正回到來源，再重新產生快照。

## 二、發佈範圍與內部資料

首版定位為「單機 Linux、可觀察的 agent 執行環境 demo」，不宣稱完整作業系統、企業平台或安全隔離產品。

**包含：**

- 經依賴核對後的 proto8 執行元件、Python 指令與工具庫。
- 起樹所需的 kernel、daemon-root、agent-fsm，以及審核過的出廠知識庫。
- fake endpoint 路線、真模型接線指南、少量自包含範例。
- 使用者手冊、安裝手冊、概念入門、版本限制與停止方式。
- eca-claude 作為進階選配；只在完整流程驗收後列為支援。

**不包含：**

- `wf/`、thinking、user-advice 原文、私人 notes／feedback、內部 agent 指示。
- 舊代 archive、手寫重寫中的 `impl_cpp/`，以及與 demo 無關的實驗。
- 私人樹複本、端點憑證、實際對話、公司派工紀錄與真實看板截圖。
- 多機自動部署、跨主機權限隔離、正式服務監管的保證。

匯出採「明列允許檔案」，不採「先全抄，再排除幾個資料夾」。首版保留必要的 proto8 相對路徑，避免為了漂亮目錄破壞安裝器與 import。排除的目錄若仍被程式依賴，必須補成公共資源或暫停該功能，不能留下壞連結。

**乾淨發佈不等於舊資料消失。** 備料已指出原公開倉庫與 Git 歷史含私人路徑、帳號及 email；新倉庫只能避免繼續夾帶，不能撤回既有曝光。這部分另列曝露清單，由使用者決定接受現況、限制入口或授權後續處理，不自行改歷史。

發佈前掃描涵蓋來源白名單、產生後網站、壓縮包、圖片、Git metadata 與下載附件。文字掃描後還要人工看頁面與截圖；若發現有效憑證，須先撤銷／輪換，刪字不能代替處理。文案引用原話另做逐句確認表。

## 三、安裝分級與軟體包

等級按「需要多少外部條件」分，不讓第一次體驗先被模型服務卡住。

- **L0 看懂，不安裝：** Pages 上提供流程圖與標明版本的錄影；明說是示範，不假裝瀏覽器正在執行 agent。
- **L1 離線跑通：** Linux、bash、Python 與 aos 執行元件；使用 fake endpoint，不需模型帳號。展示的是系統流程，不是 AI 能力。
- **L2 真模型工作：** L1 加一個驗證過的 OpenAI 相容端點；LiteLLM 是可選轉接器，不是 aos 必裝依賴。金鑰只放本機環境或排除追蹤的設定。
- **L3 外部 CLI 與進階工具：** eca-claude 另需 claude CLI、帳號與 tmux；bubblewrap／s6、newuidmap、setfacl 按使用功能選裝，不全塞進新手清單。

原始碼安裝另需 CMake ≥ 3.21、C++20 編譯器、C 工具鏈及 nlohmann-json，並交代 vcpkg bootstrap。建議先把 Python 3.12 設為候選驗收基準，不把它誤寫成全部核心功能的已確認最低版本。首版只承諾一組實測 Linux 發行版與架構；其他環境列為未驗證。

備料確認目前沒有預編包。我建議以一個 Linux x86_64 預編包作為降低門檻的優先項，但它需要額外授權施工與乾淨環境驗收；不能因為使用 `-static-pie` 就宣稱到處可跑。若不核准此工作，首版只能誠實稱為「原始碼體驗版」，不能打「五分鐘即用」。

一鍵入口應分成兩個明確動作：

- 安裝：顯示將下載／建置什麼，核對版本與雜湊，安裝到指定位置，檢查必要依賴。
- 建立 demo：在新的獨立目錄建立定義、工作區與 stack，確認後才啟動。

不使用 sudo、不改 shell rc、不讀取既有憑證、不自動安裝 CLI、不碰既有 aos 樹、不自動起模型代理或背景服務。必須檢查繼承的 `AOS_*` 環境，拒絕含糊的目標路徑。停止只針對本次記錄的樹與程序；移除須先列清單，不刪使用者產物。

現有 `install.sh` 只是連結指令與寫入 Python 路徑，不把它包裝成已具備上述能力。

## 四、文件站結構與產生器

建議公開倉庫使用 VitePress，站台源碼放 `site/`，經 GitHub Actions 建置並部署 Pages，不另開 `gh-pages` 分支。理由是首頁版型與教學可共存、支援語系路由、Markdown 容易反覆修改；Node 只用來建站，不進產品執行依賴。

以下是建議結構，每篇只承擔一件事：

```text
README.md

  install/

    daemon-and-kernel.md
  reference/

```

- `README.md`：一句話、成果圖、選路入口、支援環境、授權與限制；不重抄整本手冊。
- `index.md`：產品頁；`choose.md`：選安裝等級；`first-run.md`：完成第一輪；`expected-result.md`：對照成功狀態。
- 安裝五篇：分別交代環境、發佈包、原始碼、模型端點及外部 CLI，避免把所有依賴混在一起。
- 使用三篇：分別解釋建樹掛 agent、送任務與觀察、停止及重建；不承諾 prototype 格式跨版相容。
- 教學兩篇：新增一個小工具、完成兩個 agent 的分工；範例索引列需求、輸入、成果與清理方式。
- 概念兩篇：解釋資料夾與程序、daemon 與 kernel；參考索引只連公開且版本相符的規格。
- 支援四篇：依症狀排錯、安全邊界、未支援事項及各版差異。

頁面採「先圖與結論，再操作，細節摺疊」。錯誤與安全警告不可藏在摺疊區。文件中的可執行步驟與範例由同一套已驗收材料取得，避免複製多份命令逐漸分歧。

## 五、產品頁與標語

首頁順序建議是：一句話定位 → 一輪工作流程圖 → 兩個入口「先看成果／本機試跑」→ 三個可見特色 → 範例成果 → 安裝選路 → 限制與安全 → 願景。

三個特色只講目前能證明的：資料夾承載定義、agent 以 Linux 程序執行、用 kernel 協調請求。不要把「使用 Linux 權限」寫成「已安全隔離」；同帳號 agent 的工具權限仍可能影響其他資料。

標語候選均是新草案，不冒充使用者原話：

1. **「把 agent 放進資料夾，讓工作跑成程序。」** 已實作定位；推薦主標，具體且可示範。
2. **「先不用模型，也能看懂 agent 怎麼運作。」** 已有 fake 路線支撐，但整套新手體驗仍待驗收；適合 demo 副標。
3. **「讓今天交給 AI 的工作，逐步成為明天可重用的程式。」** 願景；放後段，不暗示已有自動零 token 轉換。

不把 RSI、零 token 或任意資源作業系統放成首屏既成成果。原話若要引用，再從來源逐句核對、交使用者確認。

## 六、四個範例與佈署方式

1. **沒有模型的第一棵樹，L1。** 建樹、掛一隻 FSM agent、送入測試訊息；預期看到 agent 狀態、請求與固定回應，再正常停止。成功代表線路通了，不代表模型理解任務。
2. **把三個數字算成結果，L1。** 用固定測試路徑呼叫算術工具；預期得到確定數值及可追查的工具紀錄。需先確認現有 fake 能驅動此流程，否則列為新增範例工項。
3. **整理一份公開樣本，L2。** 模型只讀隨包附上的樣本文字，產生摘要檔；預期檔案存在、包含指定欄位，不要求逐字一致。揭露內容會送到所選端點，並提供使用者設定的費用停止條件。
4. **兩隻 agent 接力，L2。** 一隻整理樣本，一隻檢查遺漏；預期看到交接訊息與最終結果。若需額外編排，明列待施工，不用錄影代替可重現範例。

eca-claude 暫列延伸教學，不綁首版成功條件。單機佈署圖只畫「獨立 demo 目錄 → daemon／kernel → agent → 指定工作區」。多機只解釋現況與責任邊界，不提供未驗證的跨機一鍵腳本；遠端模型端點也不等於多機 agent 佈署。

## 七、三大風險與直覺做法的坑

**第一，入口變漂亮，公開邊界卻沒變。** 原倉庫的私人紀錄與歷史仍可讀；不連結不等於不公開。白名單快照降低新增曝露，舊曝露仍須單獨裁決。

**第二，作者機器能跑，被誤認為陌生人能用。** 本機已有 vcpkg、PATH、端點與憑證，容易掩蓋缺步驟。直覺做法常把安裝文件寫完就算完成；本案應要求乾淨環境中，不靠作者補命令即可完成全部步驟。

**第三，宣傳速度超過能力與安全證據。** fake demo 容易被誤讀為真模型成果，程序可見性容易被誤讀為隔離，願景容易變成功能承諾。每個首頁主張都應對應一個可展示範例或明確標示願景。

建議發佈門檻是：一組指定環境完成所有承諾範例、零未裁決的隱私／授權阻擋項、停止流程確認無本次殘留程序、所有公開連結有效、使用者批准首頁草稿。這些是發佈驗收，不是擅自新增全專案的 commit 規則。

## 八、請使用者拍板

1. **發佈載體：同 repo／乾淨公開 repo。** 推薦後者；接受多一套匯出維護，換取清楚的交付邊界。原倉庫入口改成短導引，兩邊 README 不維護兩套教學。
2. **首版承諾：原始碼可跑／預編包降低門檻。** 推薦核准一個環境的預編包；若不核准，就取消限時即用宣傳。
3. **主角：FSM／eca／兩者並列。** 推薦 FSM 主線、eca 選配，避免帳號與外部 CLI 擋住第一次成功。
4. **語言：中文／英文／完整雙語。** 推薦英文主站與手冊、繁中首頁及快速開始；翻譯不足時標明，不維護兩套不同版本的操作命令。
5. **授權：MIT／Apache-2.0／暫不決定。** 推薦自有程式 MIT、文件 CC BY 4.0 作討論起點；第三方授權與再散布義務另查。沒有定案前，不宣稱可自由再散布。
6. **既有曝露：接受現況／另授權治理。** 推薦先盤點交使用者逐類裁決；新發佈不得再夾帶，但不擅自改舊歷史。

執行順序建議是：先交首頁線框與可點的文件目錄 → 使用者確認定位 → opus 深化匯出與安裝計劃 → Argon 審查 → 授權後施工及乾淨環境驗收 → 再請准 push 與開 Pages。每輪留草稿版本與採納表，但不把內部討論直接發布。最終取捨交由 opus、fable 整合，再由使用者拍板；本次未寫檔、未跑指令、未寄信。
