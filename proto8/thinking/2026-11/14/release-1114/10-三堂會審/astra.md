## 1. 第一屏讀完：這是什麼？要我做什麼？

我的理解是：

**這大概是一套管理多隻 AI agent 的執行環境：把相關東西放進資料夾，讓 agent 共用模型服務，並且讓我自訂工具和排隊規則。**

但這是我從四個優勢拼出來的，不是標題、副標告訴我的。「新時代的軟體技術棧」範圍太大；「讓unix哲學再次偉大」沒有交代產品用途。

它想讓我點「開始用」，去跑這套東西；不然就先看演示。

第一屏沒有回答的是：**我現在遇到什麼問題，才需要它？** 是模型呼叫太多？agent 難部署？想讓 agent 自己寫工具？四個優勢各指一個方向，我不知道主打哪個。

## 2. 依閱讀順序，我卡住的地方

### ① Linux、CPU、板子：我不知道實際對應到什麼

> aos 把 Linux 當成硬體，在上面重新分一次：誰是 CPU、誰是板子、什麼可以拿來算。

我知道這是比喻，但接下來一直用比喻解釋比喻。agent 是 CPU，管理 agent 的程式是板子，然後又出現 kernel。

**「板子」跟 kernel 是同一支程式嗎？** 如果不是，兩者各管什麼？我還沒看懂實際元件，就得先記住一套重新命名。

### ② 「照樣排程」把差別一筆帶過

> 這樣包起來，他對 aos 來說就是一個處理單元（PU），跟一張 GPU、一個外部的模型服務是同一類，照樣排程。

寄信、等回信、歸檔，我懂。但「可以把工作交出去」到「可以同樣排程」，中間還缺東西。

排畫家的工作，是排寄信順序，還是管理他的接案量與交付時間？跟排模型呼叫共用的是哪個介面？**我看懂了包裝的想法，沒看懂統一之後具體能管理什麼。**

### ③ 嵌套的形狀可以想像，用途不明

> kernel 上面分兩塊，一塊是做事的 agent，一塊是另一個 kernel；那個 kernel 上面，又可以再分一次。

「分兩塊」是固定結構，還是舉例？多套一層會得到什麼能力？跟同一層多放幾隻 agent 差在哪？

這裡只告訴我結構可以遞迴，沒有告訴我為什麼會想這樣用。

### ④ 從「成本很多種」跳到「kernel 可以優化」

> aos 的 kernel 就是為剩下的那些成本設計的：每個請求都先經過它，要優化什麼，由你來定。

前面列了看懂程式的時間、原始碼大小、名字相撞、token，還有畫家的專長與產量。這些不是同一類問題。

我卡在：**它怎麼取得這些資訊，又能做什麼操作來降低成本？** 是量測、排隊、拒絕請求，還是改寫程式？

到「今天做到哪」才知道目前驗證的是模型呼叫排隊與次數限制。前面的概念範圍遠大於後面的實際機制。

### ⑤ 資料夾怎麼就成了函數？

> 我們的答案是檔案系統：一個資料夾就是一個函數，裡面用什麼語言寫都行，權限直接用 Linux 的，出了問題打開來看就知道。

資料夾可以裝程式，我懂；但資料夾本身怎麼被呼叫，我不懂。

入口在哪？參數怎麼傳？結果從哪裡拿？怎樣區分普通資料夾和可呼叫的資料夾？

我不需要完整規格，但需要一個最小例子。否則「資料夾就是函數」仍然只是一句命名宣告。

### ⑥ 加工具不等於完成自我改進

> 這件事可以叫 agent 自己來：跟它說「這個資料夾就是你，替自己加一個新工具」，它在自己的資料夾裡加一個資料夾就行了。

我卡在「就行了」。

加出一個工具，跟讓原來的流程確實改用它，是兩件事；改用它，跟維持原來的結果，又是另一件事。這句把中間最需要解釋的部分省略了。

### ⑦ 為什麼打開來，就會有五個步驟？

> 打開來看：它其實是五個小步驟：讀檔名、照類型分、判斷內容在講什麼、改名、寫目錄。每一步都在問模型。

「打開來看」是打開哪裡？流程定義、對話紀錄，還是程式碼？

前一步只說把需求交給 agent，這一步卻突然有五個固定、可逐一替換的小步驟。**這個結構是 agent 自己產生的，還是演示作者事先拆好的？** 兩者差很多。

### ⑧ 最難的一步，被「換掉以後」帶過了

> 最後剩「判斷內容在講什麼」：這一步最難，是 aos 要去的方向。換掉以後，這個函數不再問模型，它是一支程式。

這就是我最想知道怎麼做的地方，卻直接跳到完成後的結果。

如果只處理固定種類的文件，可能可以寫規則；如果仍要處理任意內容，這頁沒有說明替代方法。這裡是未解問題，不只是演示還沒接上去的一步。

### ⑨ 排隊的門也問模型，那門自己怎麼排？

> 這種話很難用公式算。設計上，讓門自己也是一隻 agent，由它讀了決定誰先。

前面要解決模型端點不足，現在決定誰能用模型的元件，也需要模型。

它用的是同一個端點嗎？它的請求需不需要排隊？這個判斷新增的等待與模型成本，怎麼跟排程收益比較？

我不是直接判定做不到，而是這裡出現了一個新的資源問題，文字沒有接著處理。

### ⑩ 到了「今天能做的」，又換了一套詞

> 不用模型起一棵樹，對假腦的 agent 說話，看對話檔與資料夾。

「樹」是前面的 kernel 嵌套結構嗎？「假腦」會回什麼？跑完這個示例，我驗證到的是訊息傳遞、狀態保存，還是 agent 行為？

這應該是最容易懂的入門段，卻要我再猜一次術語。

另外，反覆出現的「用了多少模型長度只是示意，沒有量過」，我不直接當作文案重複問題，因為可能是抽取圖表文字造成的。但既然沒有量過，我也不能從那些長度判斷節省幅度。

## 3. 哪些段落接不起來？

- **四個優勢 → 重造計算模型。** 我剛知道它能搬、能排隊、能自訂，接下來想看一次實際操作，卻先被帶去理解 CPU、板子和作業系統。從使用價值突然切到作者的世界觀。
- **可以嵌套 → 以往沒考慮過的成本。** 結構可以一層套一層，跟理解成本、命名衝突之間，有什麼必要關係？「有了這個計算模型」只是指回上一段，沒有真正說明因果。
- **成本與排程 → Lisp 與檔案系統當語言。** 上一段在講資源管理，下一段開始論證程式可以修改自己。我不知道這是同一套機制的延伸，還是 aos 的另一項獨立設計。

問題不是不能講這些，而是**每次換題目，都沒先說這個新題目要回答哪個使用問題。**

## 4. 哪些詞沒有解釋，或解釋不足？

我不需要 Linux、CPU、GPU、GitHub 的基礎科普；比較需要交代的是專案自己的詞，以及會影響我理解數字的詞。

- 「一棵樹」：包含哪些東西？跟一個 aos 執行環境是不是同義？
- 「假腦／真腦」：假腦具體模擬什麼？跟「假模型」是不是同一個東西？
- 「模型位子」：是端點數、同時執行的名額，還是別的限制？「2 個模型位子」不等於明確說明有幾個端點。
- 「token／用了多少模型／長度」：這幾個表達是不是指同一種量？到底是在算 token、呼叫次數，還是費用？
- 「板子／kernel」：都有比喻性說明，但彼此的實際分工沒有交代。
- 「照字跑過」：指照哪份文件、做到什麼結果？在這頁內看不出驗證邊界。
- 「OpenAI 相容端點／工具呼叫」：對相關領域的人可能夠，但若這是接真模型的前提，至少要說明需要具備什麼能力。

另外，「八個詞講完整套概念」承諾了一份概念清單，但這頁沒有明列哪八個。讀完我仍然不知道應該記住什麼。

## 5. 哪些話我不相信，或覺得說太滿？

我不一定懷疑測試有沒有做；**我不接受從那些測試直接跳到這些標題。**

- **「完全可遷移」**：目前證明的是同一台機器上停機、複製、重啟後可以續接。跨機器沒有驗證，就不該叫「完全」。
- **「超高可併發」**：100 隻 agent 共用 2 個位子、假模型下全部完成，能支持「這個測試中排隊沒有掉請求」。沒有吞吐量、等待時間、真端點行為等資訊，支持不了「超高」。
- **「可全自由定義」**：驗過工具、端點和一條排程規則，可以說這三項可自訂；不能從三個例子推出「全自由」。
- **「最好的寫程式方式，Lisp 早就示範過」及「那為什麼大家不用？不好除錯，也碰不到底層」**：這頁沒有支持這些廣泛判斷。我也不需要先接受這套 Lisp 評價，才能理解你為什麼選檔案系統。
- **「出了問題打開來看就知道」**：看得到檔案，不等於知道問題在哪。這句把可觀察性說成了可理解性與可除錯性。
- **「這個函數哪裡不確定、哪裡花 token？都出在問模型那一步」**：花 token 可以這樣說，但不確定性不只來自模型。工具執行、檔案狀態、外部服務也可能改變結果。
- **「讓 token 一路往零走」**：我知道這裡寫的是目標，不是現況。但兩套演示都以「不再問模型」收尾，仍讓它看起來像必然終點。哪些任務能做到、如何確認品質沒有下降、改寫過程本身花多少，都沒交代。

「先放一隻什麼都能做的 agent」也太滿。直接說「先用 agent 完成目標任務」就夠了，不需要「什麼都能做」。

## 6. 讀完會不會想照著試？

**目前不會立刻試。**

不是因為它是原型，而是這頁要求我付出的成本，比它展示的當下收益清楚：

- 我知道要準備隔離環境，因為 agent 能動到我帳號碰得到的檔案。
- 我知道只有一台 Manjaro 機器驗過，還涉及 vcpkg 建置。
- 但最吸引人的兩件事——agent 自行把流程改成程式、排程器自行改進——都還不能拿來試。
- 現在能試的清單有操作項目，卻缺少一個完整的小案例，讓我知道做完能解決什麼、會看到什麼結果。

我不要求宣傳頁放完整安裝手冊。至少要讓我看見：**「我帶著這個問題來，跑完這個已驗證案例，會得到這個結果。」**

現在我比較像讀完一份未來設計提案，不是找到一個今天想裝來解決問題的工具。

## 7. 只能改三個地方，我會改什麼？

### ① 重寫第一屏：直接說產品類型，優勢改成可核對的事實

把標題、副標改成：

> 在 Linux 上執行 agent，集中管理模型呼叫  
> aos 是一套以資料夾組織 agent 與工具的原型執行環境。你可以接入模型端點、自訂工具與排程規則，也可以先不用真模型，跑一次對話流程。

四個優勢改成：

> 核心規模：三支程式，約 7500 行。  
> 同機搬移：停機後複製資料夾，可從新位置接續對話；跨機器尚未驗證。  
> 呼叫排隊：假模型測試中，100 隻 agent 共用 2 個位子，全部完成。  
> 可自訂：工具、模型端點與排程規則已有照文件執行的案例。

先讓我知道它是什麼，也不要讓標題比證據大。

### ② 把介紹開頭換成一次具體的執行流程

先拿掉 CPU、板子、作業系統的連續類比，開頭直接寫：

> 一隻 agent 反覆執行三件事：問模型、用工具、再問模型。當多隻 agent 共用模型服務時，aos 的 kernel 先接收模型呼叫，依設定的規則安排執行順序。agent 與工具以資料夾組織；目前已驗證的能力包括模型呼叫排隊，以及限制每個寄件人一天的呼叫次數。

然後接一個真正的「資料夾函數」最小例子：目錄裡有哪些檔案、用什麼指令呼叫、輸入和輸出長什麼樣。

這些細節原文沒有，不能靠我補寫。**應該用實際跑過的例子補上，不要再補一個比喻。**

### ③ 把「今天能做的」移到演示前，演示不要再以零 token 當必然結局

先讓讀者看到已完成範圍、隔離要求和第一個可執行案例，再看未來構想。

兩套演示前的說明改成：

> 以下是尚未完成的開發流程構想，不是目前可操作的功能展示。  
> 我們想嘗試把規則固定、可驗證的步驟，從模型呼叫改成程式，以減少執行時的模型用量。哪些步驟適合替換、替換後能否維持結果，仍需要實作與測試；不是每個任務都能降到零 token。

最後一格不要用「換掉以後，它就不再問模型」略過關鍵難題。改成：

> 剩下需要內容判斷的步驟，仍由模型處理。能否繼續替換，取決於任務範圍與驗證結果；這部分尚未完成。

這三處先改，讀者才不用讀完整頁，才發現自己前面理解成「產品能力」的東西，其實大半是「設計方向」。
