# 先講結論（Executive Summary）

1. **備料最大的設計風險（會把 fable 帶偏）**：
   - **死守「不改程式／腳本」會毀掉第一印象**：目前編譯強綁 `vcpkg`（只為了一個 header-only 的 `nlohmann-json`）且開了 `-static-pie`（外人 Linux 常缺靜態庫編不過），起樹還要手敲 8 步底層指令。如果不做**最小限度的建置與一鍵腳本包裝**，外人 clone 下來 5 分鐘內一定放棄。
   - **把「Fake 腦」當主打 Demo 會有反效果，把「LiteLLM」當真腦必經之路又太重**：Fake 腦只能當「L0 安裝驗證」，若沒有搭配**看得見資料夾變化的互動劇本**，外人完全感受不到「資料夾＝程式」的威力；而接真腦（L1）應該直接支援設一個 `OPENAI_API_KEY`（或直連本機 Ollama / OpenRouter），**不要逼外人先架 LiteLLM Proxy**。
   - **Repo 門面與 1.2 萬個內部檔混居**：工作樹 90% 是 `archive/`、`wf/`、`thinking/`（含 700 個個人路徑檔），產品本體卻縮在 `proto8/`。不解決門面問題，外人進 repo 會像進了私人備份硬碟。
2. **提案核心主張**：
   - **安裝分三級（L0 零依賴劇本展演 → L1 單一環境變數接真腦 → L2 Claude/多模型完整工作台）**，並補一支頂層 `quickstart.sh`（申請最小腳本／CMake 調整許可）。
   - **GitHub Pages 採「雙層結構」**：首頁（Landing Page）用原生單頁 HTML/SVG 做高視覺圖解（延續使用者偏好的架構圖與全景風格，好改不綁框架）；手冊區用 **MkDocs Material** 或 **VitePress**（共用 `docs/` Markdown，支援細節摺疊與搜尋）。
   - **文件與 `proto8/knowledge` 分工**：人類手冊重寫為「圖解＋結論先行」；`knowledge/` 與 `C-01~C-92` 退居底層 Reference，不拿給小模型讀的法條當外人入門書。

# (A) 審查：備料缺漏、誤導風險、外人卡關點、隱私安全盲區

## 一、備料漏掉、可能錯、或會把設計帶偏的地方

1. **[高] 「原則上不改程式」與「clone 下來馬上能用」直接衝突**
   - **問題**：備料第 2 點顯示目前 C++ 建置預設找 `~/dev/vcpkg`（作者私人路徑習慣），且只為了 `nlohmann-json`；`install.sh` 不建 `AOS_HOME`、不檢查 `PATH`；起樹分散在三份文件共 8 個手動步驟。
   - **為何會帶偏**：如果 fable 把這 8 步跟 `vcpkg` 原封不動寫進 README Quickstart，這就不叫「馬上能用」，而是「核心開發者除錯手冊」。
   - **修正**：應向使用者申請**「不改核心邏輯，但允許調整 CMake 依賴尋找方式與新增頂層一鍵 Demo 腳本」**（見 B 段）。

2. **[高] 把 LiteLLM Proxy 當成「FSM 接真腦」的預設門檻（方向錯誤）**
   - **問題**：備料寫「要真腦就用 `sol` 這類 pack 指向 `http://localhost:4000/v1`」「文件缺 LiteLLM 怎麼裝與寫 `litellm.yaml`」。
   - **為何會帶偏**：外人只是想試玩 aos，手上有 OpenAI / OpenRouter / DeepSeek API Key 或本機跑著 Ollama，為什麼要先學裝 LiteLLM 並維護一個 proxy 行程？`llm-kernel` 底層既然是標準 OpenAI HTTP 格式，應該提供**直連 OpenAI 相容端點的預設 pack**，把 LiteLLM 放到「進階：多模型路由管理」再去教。

3. **[高] 混淆「Fake 腦管線測試」與「產品價值展示」**
   - **問題**：備料推論「fake 腦＋FSM 是最適合當五分鐘跑得動的第一條路」。
   - **為何會帶偏**：如果跑起來只是敲 `say hello`、fake 腦回一句死板的假字串，外人會問：「這跟寫個 10 行 shell script 有什麼差別？『資料夾＝函數』在哪裡？」
   - **修正**：L0 用 fake 腦沒問題，但必須設計成**「開箱即見的資料夾劇本」**——跑完指令後，引導外人用 `tree` 或 `cat` 看見信箱投遞、FSM 狀態檔切換、Agent 在資料夾裡長出產物，親眼見證「檔案系統就是狀態機與呼叫堆疊」。

4. **[中] C++ `-static-pie` 與 Python 3.12 的跨環境相容性未驗**
   - **問題**：
     1. 備料提到執行檔編譯開 `-static-pie`。在乾淨的 Ubuntu / Debian / Fedora 上，預設不會裝 `libc.a` 與 `libstdc++.a`（static 套件），外人跑 `cmake --build` 會在 link 階段直接爆錯。
     2. 備料說「Python 最低版本沒明文，`aos-asuser` 要 3.12」。Ubuntu 22.04 LTS 預設是 Python 3.10、Debian 12 是 3.11。若未標明或未測 3.10 相容性，大量 Linux 使用者會卡死。

5. **[中] 誤以為 `proto8/knowledge`（給小模型讀的英文知識庫）可當文件站單一來源**
   - **問題**：備料第 7.5 提問「知識庫能不能當單一來源」。
   - **為何會帶偏**：給 LLM 塞 context 的知識庫講求高密度規則與邊界定義；給人類外人看的文件（照使用者風格）講求**「圖多、只講結論、細節摺疊、白話」**。兩者受眾完全相反。硬共用會做出沒人讀得下去的規格書網站。

6. **[低] 宣傳素材未區分「現在 clone 下來就能跑的（已實作）」與「架構願景（Roadmap）」**
   - **問題**：備料第 4 點收集了「持續降低 token 消耗直至 0」「把 agent 逐步替換成純程式函數」「RSI 飛輪」等金句。
   - **為何會帶偏**：這些是極佳的願景（Why aos），但如果放在產品頁沒標清楚「現有 Demo 能力 vs 演進願景」，外人 clone 下來會找「哪個指令可以自動把 agent 編譯成 C++ 函數？」，找不到就會覺得宣傳不實。

## 二、外人第一次 clone 下來最可能卡在哪？（按發生順序）

1. **[高] 第一關（Clone 後第 10 秒）：迷失在根目錄**
   - 打開 repo 看到 `archive/`（8,600 檔）、`wf/`、`impl_cpp/`、`proto8/`，不知道哪個才是本體，也不知道為什麼一個 demo repo 下載了快 300 MB。
2. **[高] 第二關（建置）：死在 `vcpkg` 與 `-static-pie`**
   - 照著跑 `cmake -B build`，立刻報錯找不到 `nlohmann_json`（因為外人沒有 `~/dev/vcpkg`）；就算裝了套件，又可能因缺 `libstdc++-static` 死在 `-static-pie`。
3. **[高] 第三關（安裝）：`command not found` 與環境變數蒸發**
   - `proto8/install.sh` 把執行檔連到 `~/.local/bin`，但多數全新 Linux 環境預設沒把 `~/.local/bin` 加進 `PATH`，或者外人沒重開 shell。接著沒設 `AOS_HOME`（或換個視窗就失效），每個指令都報錯。
4. **[高] 第四關（起樹）：多行程背景管理的黑盒感**
   - 起 `llm-kernel`、起 `daemon-root`、掛 `agent-fsm`，外人不知道哪些在背景跑、socket 在哪、失敗時 log 去哪裡看、怎麼一鍵乾淨重來（殘留行程或 lock 檔卡住下次啟動）。
5. **[中] 第五關（體驗）：看不見「資料夾＝程式」的實體變化**
   - 敲完 `say/listen/chat` 後，終端機只有文字輸出，沒有人帶他去看資料夾裡到底發生了什麼變化，錯失產品核心亮點。

## 三、隱私／安全還有什麼沒想到？

1. **[高] 只掃了「目前工作樹（HEAD）」，沒掃「Git 歷史 4,430 個 Commit 的增刪紀錄」**
   - **盲區**：sol-1 與 opus 用 `git grep` 只會掃到**現在還留著的檔案**。過去 4,430 個 commit 裡，有沒有曾經 commit 過 `.env`、`litellm.yaml`、真 `sk-` 金鑰、私人路徑或對話，後來才刪除？只要進過 git history，外人 `git log -S` 就能全部挖出來。
2. **[高] 700 個含個人路徑檔與內部紀錄（`wf/`、`thinking/`、`user-advice/`）留在公開分支的「肉搜拼圖」風險**
   - **盲區**：即使 README 和網站「不放連結」，只要這些檔案還在公開 repo 的 `main` 分支裡，GitHub 搜尋與外部爬蟲就能直接讀到 `wf/inbox`、`wf/session_logs`、`proto8/thinking`、`user-advice`。裡面除了 `/home/<使用者>` 和 2 個 email，還可能包含使用者的工作習慣、本機網路拓樸、其他私人專案名稱、甚至對特定工具或事物的私人評價。
3. **[高] 缺乏嚴格的 `.gitignore` 防呆，未來更新極易誤傳執行期密鑰**
   - **盲區**：備料發現 `.vscode/settings.json` 含個人路徑卻沒被 ignore。當使用者或外人在 repo 內起樹（如 `stacks/`、`defs/`、寫 `litellm.yaml` 或 `.env`），若 `.gitignore` 沒預先封鎖執行期目錄與金鑰檔名，下一次 commit 就可能把真實 API key 或私人對話 log 推上公開 GitHub。
4. **[中] 圖片、HTML、C++ 預編檔（若有）與測試案例中的殘留路徑**
   - **盲區**：
     - 既有 `.html`（如 `aos-home-手冊.html`、`guide*.html`）原始碼內可能寫死本機絕對路徑或私人伺服器 port。
     - 若未來提供預編二進位檔，C++ 編譯時的 `__FILE__` 巨集與 debug info 會把編譯機的 `/home/<帳號>/...` 烙進 binary（需加 `-ffile-prefix-map` 或 `strip`）。
5. **[中] 缺少對外人的「執行期安全聲明（Security Disclaimer）」**
   - **盲區**：aos 的 Agent 是真正在 Linux 上跑的行程，具備直接操作檔案系統與執行指令的能力。如果外人沒開 `aos-sandbox`（bubblewrap）就直接接上外部 LLM 並在重要目錄跑，有誤刪檔案或 prompt injection 風險。README 與手冊必須像 OpenHands / smolagents 一樣，明確標示沙箱現況與安全建議。

## 3. GitHub Pages 產品頁與文件站架構

- **存放位置與部署**：放在 repo 的 **`docs/` 資料夾**，透過 GitHub Actions（或直接設定 Pages 讀取 `docs/`）發佈。這樣**文件跟程式碼同一個 commit 演進**，不會有 `gh-pages` 分支不同步的問題。
- **產生器推薦：VitePress 或 MkDocs Material + 獨立客製首頁（Landing Page）**
  - **推薦理由**：
    1. **首頁（`docs/index.md` 或獨立 `index.html`）**需要極高的視覺自由度來放架構圖、互動區塊與對照表（符合使用者「圖多、只講結論、細節摺疊」的風格，且能直接嵌入改寫自 `kernel-framework-架構圖.html` 的視覺元件）。
    2. **手冊頁**需要左側導覽樹、程式碼一鍵複製、原生 `<details>` 細節摺疊、全文搜尋。**MkDocs Material**（Python 生態，跟 aos 技術棧一致，不需碰前端框架）或 **VitePress**（多語切換最乾淨）最能兼顧「好看」與「純改 Markdown 就好維護」。
- **如何做到「長期好改、不跟程式脫節」**：
  - 手冊**不手抄**詳細 CLI 參數與底層欄位格式，只寫「概念圖解＋核心工作流」；
  - 寫一支小腳本 `scripts/gen-cli-docs.py`，自動跑 19 支 `cmd/` 與 12 支 `impls/` 的 `--help` 匯出成 `docs/reference/cli.md`；程式改了重跑腳本就更新。
  - `proto8/knowledge/` 與 `proto8/docs/CONCEPTS` 放在「進階規格（Specs）」區供查閱，不混入新手教學。

## 4. 產品頁（Landing Page）區塊與宣傳文案設計

遵循使用者風格：**白話、先講結論、圖解優先、細節摺疊、誠實區分「現況與願景」**。

### 首頁 6 大區塊：
1. **Hero 區（第一眼結論）**：
   - **主標語候選 A（直球版）**：**「我們將資料夾作為函數。」—— 原生長在 Linux 檔案系統上的 AI Agent 作業系統**
   - **主標語候選 B（定位版）**：**Akatosh OS (aos)：秉承 Unix 哲學、沿襲 Plan 9 理想的「資料夾＝程式」Agent 體系**
   - **副標（一句話講清楚它是什麼）**：在 aos 裡，Agent 不是黑盒框架裡的 Python 物件，而是**住在資料夾裡的 Linux 行程**——`daemon` 當手管行程、`kernel` 當門管請求、用檔案信箱（Mailbox）溝通，直接複用 Linux 權限與跨語言工具。
   - **視覺**：一張「一個 Agent 資料夾展開圖 ↔ 終端機 3 行指令跑起來」的並排對照圖。
   - **行動按鈕**：`[3 分鐘快速開始]`、`[線上架構圖解]`、`[GitHub Repo]`
2. **為什麼是「資料夾＝程式」？（3 張對比圖卡，點開看細節）**：
   - **卡 1：對 LLM 原生透明**（LLM 天生就會 `ls/cat/write`，資料夾結構就是最直覺的狀態與介面，不需學私有 SDK）。
   - **卡 2：白嫖 Linux 數十年基建**（跨語言 C++/Python/Bash 混寫、權限隔離、行程監管、檔案鎖，不重新造輪子）。

## 9. 需要使用者拍板的 5 個方向題（選項＋推薦）

請 fable 將以下方向題整理給使用者裁決：

### 【方向題 1】Repo 裡的內部紀錄（`wf/`、`thinking/`、`user-advice/`）與舊代封存（`archive/` 8,600 檔）怎麼處理？
- **選項 A（推薦：雙軌或移出主幹）**：將 `archive/`、`wf/`、`proto8/thinking/`、`user-advice/` 移到私人分支／私人開發 repo（或在 `main` 分支刪除它們的追蹤，只留 `proto8/` 產品本體與 `docs/`；舊紀錄仍留在 git 歷史或私人處）。
  - *理由*：工作樹從 12,850 檔瘦身到 ~1,500 檔，外人 clone 快、結構乾淨，且直接消除 700 個含個人路徑檔案與內部交接信件在公開分支被瀏覽／爬蟲抓走的風險。
- **選項 B（同 Repo 原地保留，只改門面＋去識別化）**：所有資料夾原地不動，只改頂層 `README.md` 引導外人看 `proto8/`，但發佈前先跑腳本把現存追蹤檔內的 `/home/<使用者>` 等個人字串清掉。
  - *理由*：完全不動內部工作流（`wf/`）的現有路徑，但外人仍看得到內部看板與 `thinking/`。
- **選項 C（另開乾淨 Release Repo，例如 `aos-demo`）**：原 repo 轉私人（或維持開發用），對外發佈用腳本同步 `proto8/` 產品本體＋`docs/` 到一個全新的乾淨公開 repo。
  - *理由*：最徹底隔離內部 `wf/` 與 4,430 個歷史 commit，外人看到的是 100% 純淨的開源專案。

### 【方向題 2】為了讓外人「clone 下來馬上能用」，是否同意做兩項最小建置改良？
- **選項 A（推薦）**：同意 ① 在 `CMakeLists.txt` 內附或自動抓取單檔 `nlohmann/json.hpp`（免除裝 `vcpkg`）並讓 `-static-pie` 可自動退回動態連結；② 新增一支頂層 `./quickstart.sh` 一鍵完成建置與 L0 起樹。
- **選項 B**：完全不改 `CMakeLists.txt` 與任何腳本，在安裝手冊裡教外人一步步裝 `vcpkg` 跟敲 8 步指令。

### 【方向題 3】對外文件與產品頁的語言策略？
- **選項 A（推薦：雙語——中文母本優先對齊使用者，同步產出英文版設為預設或並列）**：
  - *理由*：使用者本人會長期頻繁審閱與微調文案（「這是大事，我後續看過後會再來調整」），用**繁體中文當母本**最能精準傳達使用者的哲學（如「白嫖 Linux 權限」「資料夾作為函數」）；同時因為 GitHub 開源受眾與程式輸出皆為英文，由 Agent 自動同步維護對等的英文版（`README.md` 英文 + `README.zh-TW.md` 中文，網站支援中英切換），兩全其美。
- **選項 B（純英文）**：符合國際開源慣例、維護單一語言最省力，但使用者自己審稿改文案時較不直覺。
- **選項 C（純繁體中文）**：最快上線、最貼合現有 `proto8/docs` 素材，但外國開發者無法直接閱讀。

### 【方向題 4】GitHub Pages 產生器選擇？
- **選項 A（推薦：客製 HTML 首頁 ＋ MkDocs Material / VitePress 手冊，放 `docs/`）**：首頁完全照使用者的視覺圖解風格自由排版，手冊區享受現成搜尋、摺疊與目錄導覽。
- **選項 B（純原生 HTML + CSS，不套任何產生器）**：極致輕量、零建置依賴（直接複用現有 `.html` 圖解風格），但手冊多起來後要自己維護側邊欄與搜尋。
