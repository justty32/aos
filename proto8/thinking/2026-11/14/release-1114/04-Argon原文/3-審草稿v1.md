這份 v1 草稿**底子非常誠實，核心動線（Get Started 的假腦實跑）已經立起來了**；但現在最大的問題不是文筆，而是**「作者寫給審查員看的防呆備註（批 0、未實跑、本稿沒逐檔核對、連結待補）」直接印在給外部讀者看的內文裡**，加上**主打口號「資料夾就是函數（`_entry`）」在 Quickstart 和教學 1 裡居然一次都沒出現**。

只要在 v2 把「內部施工備註」收進註解、補上一小段真正看到 `_entry` 的展示、並把宣傳頁 A 的圖解嵌進宣傳頁 B 的工作台版面，這份發佈版就能從「內部草稿」變成「能讓外部工程師眼睛一亮又信任的公開 demo」。

## (A) 審查：以「第一次聽說 aos 的開發者」眼光逐頁看

### 1. 跨頁共通問題（先抓這三件，不然每頁都在卡）

1. **【高】主打「資料夾就是函數（`_entry`）」，但跑完 Quickstart 與教學 1 完全沒看到 `_entry`**
   - **哪裡卡／誤會**：README、首頁大標都喊「Folders are functions / 資料夾裡放一個 `_entry` 就能被呼叫」。但讀者照著跑完 `README`、`get-started.md`、`01-first-tree.md`，看到的全部是 `procs/ann/history.jsonl`（那是「對話紀錄是檔案」），從頭到尾沒 `ls` 過任何一個含 `_entry` 的資料夾，也沒用 `aos-exec` 呼叫過任何一個函數資料夾。跑完會覺得文不對題。
   - **具體改法**：在 `get-started.md` 第 3 步或 `01-first-tree.md` 加兩行指令，讓讀者親眼看到 `_entry` 真的存在，例如：
     ```bash
     ls $AOS_HOME/kernel/llm-kernel/   # 看見裡面的 _entry 與設定檔
     ls defs/ann/                      # 或看工具資料夾裡的 _entry
     ```
2. **【高】內部查核黑話（「批 0 #3b」、「本稿沒逐檔核對」、「未實跑」）直接裸露在讀者眼前**
   - **哪裡不信任**：誠實標明「實驗功能／尚未支援」會增加信任；但在教學表格裡寫「*用途本稿沒逐檔核對，標待驗*」、在需求表寫「*批 0 #1*」、「*四種容器：待驗，沒有跑過*」，會讓陌生人覺得這是一份還沒寫完的內部交差筆記，連作者都不知道自己的檔案是幹嘛的。
   - **具體改法**：所有「批 0 #X」、「本稿未核對」全部移進 HTML 註解 `<!-- source: ... -->`。對讀者只要講產品事實（例如：「內部執行狀態檔，日常不必手改」、「目前僅在 Manjaro Linux 實測過，其他發行版歡迎回報」）。
3. **【低】所有中文文件（`.md`）都把摘要句寫在 `# 大標題` 的上面**
   - **哪裡怪**：`01-first-tree.md`、`install/index.md`、`requirements.md`、`security.md`、`troubleshooting.md`、`faq.md`、`status.md` 的第 1 行都是一句話摘要，第 3 行才是 `# 標題`。在 GitHub 上看，標題頭上頂一行字很像排版壞掉。
   - **具體改法**：統一把第 1 行的摘要句移到 `# 標題` 的正下方。

#### ① `README.draft.md`
* **【高】Quickstart 第 2 行 `cmake` 隱藏了 vcpkg 路徑陷阱，陌生人複製貼上會直接卡死**

  * **具體改法**：在 Quickstart 的 `cmake` 前加一行註解：
    ```sh
    export VCPKG_ROOT=/path/to/vcpkg      # optional if vcpkg is at ~/dev/vcpkg or using system nlohmann-json
    cd ~/aos/proto8/impls && cmake -B build && cmake --build build -j
    ```

  * **具體改法**：若還沒做中文版 README，先拿掉 `README.zh-TW.draft.md` 連結，改標 `[Docs (zh-TW; English coming soon)](docs/zh/get-started.md)`。

  * **具體改法**：改為 `(about 6 MB for proto8/ itself)`。

#### ② 兩版宣傳頁對決：`landing.zh.html` (A 版) vs `landing-b.zh.html` (B 版)

**先講結論與推薦：選 B 版當基底，把 A 版的兩張核心 SVG 圖解和具體列點嫁接進來。**

### 3. `06-草稿/文案表.json` 審查：哪幾句最好、哪幾句最該改

#### 保留不動（寫得最好、最有力的 6 句）：
* **H1**：「資料夾，就是函數。」/ `Folders are functions.`（極簡、好記）
* **P1**：「aos 把 AI agent 當成一般的 Linux 行程，住在資料夾裡。每個工具、每隻 agent、每封信，都是你可以 ls、可以讀、可以設權限的資料夾或檔案。」（一句話講透系統本質）
* **C1**、**C4**、**L1**：把 `_entry` 與 `exec / loop / daemon / kernel` 講得非常清楚。
* **V1 + V2**：「從一隻 agent 開始，最後換成一支程式。」「一步一步把 agent 換成確定的程式，token 用量往零走。」（最能打動工程師的長期願景）
* **S1 + SEC**：老實交代原型限制與帳號權限風險。

#### 最該改的 4 句（附直接可用的替換句）：

1. **【中】`H2`（太玄，第一次看一定誤會）**
   * **原句**：「給 agent 的作業系統，不靠硬體，靠任意資源。」/ `An operating system for agents, built on any resource.`
   * **問題**：工程師看到「不靠硬體」第一反應是「騙人，哪有軟體不靠硬體？」（作者原意是傳統 OS 抽象化硬體，aos 抽象化任意資源，但濃縮成八個字就歪了）。
   * **具體改法**：
     * **推薦直接換成 `H2b`**：`把 unix 哲學帶進 agent 時代。` / `Unix philosophy for the age of agents.`
     * **若要保留 H2 原意，改寫為**：`傳統 OS 把硬體變成檔案；aos 把模型、工具與 agent 變成資料夾。` / `Where Unix turns hardware into files, aos turns models, tools, and agents into folders.`
2. **【中】`C3`（講過頭，與安全說明衝突）**
   * **原句**：「站在 Linux 上。權限就是檔案權限；工具用什麼語言寫都行。」
   * **問題**：目前檔案工具不擋工作區外路徑、同帳號無隔離、L3 沙箱還在實驗，直接說「權限就是檔案權限」會讓人誤以為已經有開箱即用的權限隔離。
   * **具體改法**：`站在 Linux 上。agent 就是一般行程，工具用什麼語言寫都行；權限與環境直接走 Linux 原生機制。` / `Rides on Linux. Agents are normal processes and tools can be written in any language, using native Linux mechanisms.`
3. **【中】`C5`（把還沒寫教學的 L2 當成現成主打）**
   * **原句**：「腦和身都自己帶。先用假腦試、接任何 OpenAI 相容端點，或把你的 Claude Code 掛進樹裡當一隻 agent。」
   * **具體改法**：`腦和身都自己帶。先用內建假腦免金鑰試跑，之後可換接 OpenAI 相容端點，或掛入外部 CLI agent（如 Claude Code，實驗中）。`
4. **【低】`V3`（中文連三個「函數」太繞口）**
