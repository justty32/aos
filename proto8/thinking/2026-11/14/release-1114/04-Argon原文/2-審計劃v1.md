## (A) 審查

### 0. 審查總結論

這份實作計劃 v1 骨架清楚、節奏務實，上一輪早審的核心意見（L0 強調「看資料夾變化」、批 0 先驗 CMake/static-pie、獨立安全頁、git 歷史深掃、文案單一正本）都已到位，**整體可進入批 0 執行**。

但計劃裡還有 **3 個高風險矛盾／漏洞** 與 **幾個中低度缺口** 必須在批 0～批 1 修補：
1. **【高】「同 repo 發佈（乙案）」與「`user-advice` 不公開＋只掃公開清單」自相矛盾**：同一個 repo 設為 Public 後，外人在 GitHub 網頁就能直接點開 `proto8/user-advice/`、`thinking/`、`wf/`；但第 7 節工作樹掃描卻只掃 `public-surface.json` 清單內的檔案，造成嚴重的隱私掃描死角。
2. **【高】本機沒裝 Ruby 卻用 Jekyll，會讓批 1「雙擊審全站草稿」與「步 3 掃描 HTML 產物」同時卡死**，且 GitHub Pages 免 workflow 的內建 Jekyll 預設不會渲染 ```` ```mermaid ````、也不支援非白名單主題（如直裝 `just-the-docs`）。
3. **【高】README 教 `git clone --depth 1` 避開 192 MB，但批 0 沒查這 192 MB 在哪**：如果大檔案還在目前 HEAD 工作樹裡，`--depth 1` 下來還是一樣肥。

### 2. 計劃哪裡會出錯、漏掉、互相矛盾、或驗收不夠硬？

1. **【高｜互相矛盾】第 2 節說「`user-advice` 原文不公開」，卻把它放在公開 repo 的「原地不動」區**
   - **問題**：同一個 GitHub repo 沒有「某個資料夾對外隱藏」的功能。只要採乙案且 `proto8/user-advice/` 原地不動，外人直接在 GitHub 就能讀到每一篇 `user-advice` 原文。
   - **修法**：第 2 節必須修正表述——若 `user-advice` 原文真的不公開，公開前必須將 `proto8/user-advice/`（及不願公開的私人筆記）移出公開分支的工作樹（且若歷史裡已有，還要考慮是否採乾淨 repo 方案）；若使用者同意留在 repo 讓人翻，才叫「原地不動、只不主動放連結」。
2. **【高｜會出錯】批 1 驗收要求「雙擊 `v1/index.html` 可審、掃描步 3（Jekyll 產物 HTML）零命中」，但本機沒裝 Ruby**
   - **問題**：第 10 節批 0 寫「本機沒 Ruby → 記為待使用者或改 Actions」。如果批 0 跳過 Jekyll 建置，到了批 1，除了首頁 `index.html` 是手寫 HTML 外，其餘 Get started、安裝、教學 01、安全頁全部是 `.md` 原始碼，使用者雙擊 `v1/index.html` 點進子頁只會看到未渲染的 Markdown 純文字，步 3（掃描產物 HTML）與步 4（檢查壞連結）也無從跑起。
   - **修法**：不依賴本機 Ruby。在 `docs/_tools/` 備一個純 Python 標準庫（或外掛單一 HTML 殼載入本機/CDN `marked.js` + `mermaid.js`）的草稿渲染腳本，把 `.md` 全部輸出成 `06-草稿/v1/**/*.html`，讓使用者雙擊就能看完整排版與 mermaid 圖，掃描腳本也能直接驗 HTML。
3. **【中｜驗收不夠硬】4.2 節範例驗收只寫「`expected.txt` 由實跑抄錄」，沒處理動態輸出**
   - **問題**：aos 執行時的 `history.jsonl`、信件 ID、時間戳記、PID、路徑每次跑都不一樣。直接抄錄 `expected.txt` 下次跑比對一定不會過；如果不比對，就只是「跑過沒崩潰」而不是自動驗收。
   - **修法**：每個範例的 `run.sh` 結尾必須寫**確定性斷言（assertions）**（例如檢查特定狀態檔存在、用 `grep`/`python3 -c` 驗證最後一筆回覆內容與狀態碼、確認停樹後 `pgrep` 無殘留行程），並將輸出中的時間戳、PID、路徑正規化為 `<TIME>`、`<PID>`、`<AOS_HOME>` 後再產生 `expected.txt`。
4. **【中｜漏掉】Get started 手打指令沒防「跑第二次時殘留 daemon / lock 卡死」**
   - **問題**：批 1 不等 `quickstart.sh`，讓使用者在 `get-started.md` 手打指令起 `llm-kernel` 與 daemon。新手最常在半路關視窗或重頭再試一次，結果舊的背景行程或 lock 檔沒清掉，第二次跑直接報錯。
   - **修法**：`get-started.md` 結尾固定放「一行停樹與確認乾淨」指令，`troubleshooting.md` 第一條放「如何一鍵清掉殘留行程與 lock」；批 1 驗收加硬為：**「在同一個乾淨複本內，照 `get-started.md` 連續跑完兩輪，第二輪也必須零錯誤過關」**。
5. **【低｜漏掉】散落各處的「跨領地寫入申請」沒有統一成表**
   - **問題**：計劃裡要動到 `ok-release` 領地外的路徑散在各節（第 2 節頂層 `README.md`/`LICENSE`/`docs/`、第 4.2 節 `proto8/examples/`、第 4.3 節三件程式、第 7 節頂層 `.gitignore`），交接給 xiaosi 放行時容易漏報。
   - **修法**：在第 4.3 節合併成一張「跨領地寫入與放行時機總表」（見下方提案）。

### 3. 批 0 的驗事實清單（11 項）有沒有漏？

現有 11 項抓得很準，但漏了以下 **4 個直接影響文件與發佈決策的事實**，應補進批 0：

1. **【高】補第 12 項：192 MB 體積拆解與 `--depth 1` 實測大小（擴充第 9 項）**
   - **怎麼測**：跑 `git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' | sort -k3 -n | tail -30` 找出最肥的前 30 個物件是在歷史裡還是在目前 HEAD 工作樹裡；再實測 `git clone --depth 1 file://...` 下來的大小是幾 MB。
   - **為什麼重要**：如果 HEAD 工作樹裡（例如 `impl_cpp/` 或 `archive/`）還留著幾十 MB 的編譯產物，README 教 `--depth 1` 也沒用，必須在批 1 前申請從 HEAD `git rm` 掉。
2. **【高】補第 13 項：「不寫家目錄（第 2 項）」停樹後的零污染與零殘留驗證**
   - **怎麼測**：跑完 L0 一條龍並執行停樹指令後，檢查：① `HOME` 下有沒有被偷偷新增任何檔案；② `ps` 裡還有沒有殘留的 `aos` / `llm-kernel` 孤兒行程；③ 緊接著原地在同一個 shell 再起一次樹能不能成功。
3. **【中】補第 14 項：CMake、GCC/Clang 的實際最低版本與編譯記憶體峰值**
   - **怎麼測**：確認 `CMakeLists.txt` 與 C++20 語法在主流 LTS（如 Ubuntu 22.04 的 GCC 11 + CMake 3.22）會不會過，以及 `/usr/bin/time -v` 量出編譯峰值記憶體（避免使用者在 2GB RAM 的小容器／WSL 裡編到 OOM）。
4. **【中】補第 15 項：GitHub Pages 免插件的 Mermaid 渲染與無 Ruby 預覽方案實測（擴充第 10 項）**
   - **怎麼測**：確認不靠 Ruby gem、純靠 HTML layout 引入 `mermaid.min.js` 能否把 Markdown 的 ```` ```mermaid ```` 畫出來；若本機無 Ruby，驗證 Python 預覽打包腳本能否產出雙擊可看的 HTML。

### 4. 隱私掃描（第 7 節）還有沒有洞？

第 7 節已納入歷史深掃與個人規則檔外置，但還有 **4 個實務漏洞**：

1. **【高】洞 1：步 2 只掃 `public-surface.json`，漏掉同 repo 裡所有其他被追蹤檔案**
   - **問題**：若採乙案（同 repo 發佈），`wf/`、`proto8/thinking/`、`proto8/user-advice/`、`proto8/notes/`、`AGENTS.md`、`CLAUDE.md` 全都在 GitHub 上公開可見，卻不在 `public-surface.json` 裡，步 2 完全沒掃它們！而步 5（git 歷史）只掃「金鑰形狀與 `.env`/`litellm.yaml` 檔名」，沒掃個人帳號、家目錄路徑、主機名、真名、內網 IP。
   - **修法**：步 2 必須拆成兩層：
     - **步 2A（全倉工作樹掃描）**：對 `git ls-files` **全倉 100% 檔案**掃描金鑰、Token、密碼、個人路徑、帳號名、真名、email、主機名、內網位址。
     - **步 2B（公開清單嚴格掃描）**：對 `public-surface.json` 內的檔案，額外檢查不得出現內部專用代號、未點頭的原話與草稿標記。
2. **【中】洞 2：SVG 內嵌路徑、圖片 EXIF、以及壓縮／資料庫 fixture**
   - **問題**：① 畫圖工具（Inkscape、Draw.io 等）匯出的 SVG 常在 `<metadata>` 或 `export-filename` 屬性裡藏本機絕對路徑（`/home/<user>/...`）。② 螢幕截圖 PNG 常在 tEXt / EXIF chunk 帶電腦名或作者名。③ 二進位壓縮檔或 `.sqlite` 用文字 `grep` 掃不進去。
   - **修法**：`docs/_tools/scan` 必須：① 對 SVG 強制檢查 `metadata`、`sodipodi`、`export-filename` 與路徑字串；② 對所有 PNG/JPG 檢查並剝除 EXIF/tEXt chunks；③ 公開清單內若有任何非純文字檔（圖片除外），腳本直接報警拒絕。
3. **【中】洞 3：步 5（git 歷史）若只掃 diff patch，會漏掉 Commit Message、Tag 訊息與 Branch 名稱**
   - **問題**：有時敏感路徑、內部機器名、或私人代號是寫在 commit message 裡，不是寫在檔案內容裡。
   - **修法**：步 5 除了掃 `git log --all -p` 的內容外，還要對 `git log --all --format="%H %an <%ae> %cn <%ce> %B"`（所有作者欄與完整提交訊息）跑同樣的 `scan-private.txt` 與金鑰規則。
4. **【低】洞 4：大小寫與路徑變體漏網**
   - **問題**：帳號名或主機名首字母大寫、或出現在 URL encode（如 `%2Fhome%2F...`）時，純字面匹配會漏。
   - **修法**：`scan` 腳本對 `scan-private.txt` 律用 `grep -i`（不分大小寫）。

### 1. 我會加或改什麼（只列跟計劃不同的地方）

#### 改動 ①：把「中性 `openai-compatible` 端點＋示範 pack」從批 2 提早到批 1.5 隨初版上線
- **原計劃**：批 1.5 只上 L0，中性端點與 pack 留到批 2 才申請與上線。
- **改法**：批 0 第 7 項在暫存夾實測接通 OpenAI 相容端點時，順手把那個中性端點腳本（`endpoints/openai-compatible`）與示範 pack 寫好；批 1 跟 `proto8/examples/` 一起送放行（純新增兩個小檔案，完全不改既有程式碼）。批 1.5 初版上線時，README 與 `install/index.md` 就能給出 3 行真正能跑的 L1 接真腦指令；長篇教學（教學 02～04）照舊留批 2 寫。

#### 改動 ②：在第 4.3 節補一張「跨領地寫入與放行總表」
- **原計劃**：要寫入 `ok-release` 領地外的檔案散在各節。
- **改法**：統一收成一張表，分三級風險送審，避免因為高風險項目（改 CMake）卡住低風險項目（純新增文件與範例）：

| 風險級別 | 路徑 | 動作 | 放行時機 |
|---|---|---|---|
| **零碰程式碼（純文件／設定新增）** | 頂層 `README.md`、`README.zh-TW.md`、`LICENSE`、`docs/`、頂層 `.gitignore` 加固 | 新增／追加 | 批 1.5 上線申請時一次放行 |
| **零改既有程式（`proto8/` 下純新增）** | `proto8/examples/`、`proto8/kernel/llm-kernel/` 下的中性 `openai-compatible` 端點與示範 pack、`proto8/quickstart.sh` | 只新增檔案，不改任何現有檔案 | `examples` 與中性 pack 批 1.5 放行；`quickstart.sh` 批 2 放行 |
| **碰活樹建置（有條件修改）** | `proto8/impls/.../settings.cmake`（無 vcpkg 退路、static 連結退路） | 修改既有檔 | **只有批 0 實測證明卡死才送**；在 repo 外編測全過後照停樹規矩交換 |

#### 改動 ③：加一個百行內的 `docs/_tools/build-draft.py`，解決無 Ruby 審稿與 Mermaid 渲染
- **原計劃**：本機沒 Ruby 就記為待使用者或改 Actions；Jekyll 主題待煙霧測試後定。
- **改法**：
  1. Jekyll 版面不依賴外掛 gem，直接在 `docs/_layouts/default.html`（或 `_includes/head-custom.html`）內建前端 `mermaid.min.js` 啟動腳本，確保 GitHub Pages 免 workflow 原生建置也能100% 畫出 mermaid 圖。
  2. `docs/_tools/build-draft.py` 把 Markdown 草稿套上同一個 HTML 外框輸出到 `06-草稿/v1/`，讓使用者雙擊 `v1/index.html` 點進任何子頁都是渲染好的網頁，同時讓第 7 節步 3、步 4 掃描在沒有 Ruby 的機器上也能照跑。

#### 改動 ④：Get started（L0）劇本強化「前後對照 diff」與「乾淨停樹重跑」
- **原計劃**：每一步後面 `ls`、`cat .../history.jsonl | tail -1`，結尾一張圖。
- **改法**：
  1. 在「跟假腦說一句話」前後，不只 `cat` 最後一行，而是帶使用者看 **`procs/ann/` 資料夾裡狀態檔與信箱在收信前後的差異**，讓「資料夾就是活的函數與狀態機」一眼看懂。
  2. 最後一步固定加上「停樹＋確認背景零殘留」指令，並確保同一串指令複製貼上連跑兩次都不會因為殘留 lock / daemon 失敗。

### 2. 第 12 節「方向題總表」的措辭與推薦修改建議

建議將第 12 節中 **★3、★4、★5、題 11** 的措辭與推薦改為以下版本（其餘題目維持原案）：
