# (A) 審查：問題逐條列出

## 一、使用者體驗（一眼掌握全局、往下看、下指令與說話）

### 1. [高] 決定單蓋住中間畫面，卻又把中間畫面移到出題部門，產生視覺遮擋與操作衝突
- **位置**：`02c §4.3`（決定單）、`02c §3.2`（Esc 順序）
- **為什麼是問題**：
  `02c §4.3` 設計「點待辦欄的藍色那張，中間蓋上一張決定單……中間的畫面同時移到出題的部門，右欄開那個部門」。如果決定單是蓋在中間欄之上的遮罩/彈窗（`02c §3.2` 把決定單列在 Esc 關閉的最上層），那中間畫面就算移到了出題部門，也正好被決定單擋住，董事長根本看不到該部門底下的員工狀態與子部門燈號。此外，當使用者想參考右欄的往來紀錄或點選部門成員時，決定單若作為頂層覆蓋層，容易阻擋點擊或因誤觸外部而關閉。
- **建議怎麼改**：
  將決定單定位為**中間欄內嵌的「上層工作卡（可收合/置頂面板）」或與右欄並排的專注檢視**，而非遮死中間欄的 Modal：或者讓決定單佔據中間欄上半部（下半部仍顯示該部門的卡片牆），且與右欄完全無遮罩並存，讓董事長能自由在右欄翻閱往來、點看成員，不會因為點右欄而關掉決定單。

### 2. [中] v2.0 砍掉完整樹狀清單又延後地圖，導致超過兩層的部門失去「一眼掌握全局」能力
- **位置**：`02c §0.8`、`02c §3.3`（部門牆和地圖並存）、`02c §8`（分期）
- **為什麼是問題**：
  `02c §3.3` 決定「不另外保留 v1 那種整棵樹的長清單」，而地圖又排到 v2.1。在 v2.0 只有「部門牆（一次只畫一層，子部門卡上只畫色點與最糟燈號）」。當公司有 3～4 層結構（例如 `公司 › ok-kf › ok-kf-b › sol-1`）時，董事長站在頂層「公司」只看得到一級部門有紅燈，卻看不出是哪個二、三級子部門出事，也無法一眼對比多個子部門的主管留話，必須一層層盲點進去或完全退化為只看左欄扁平清單，喪失了「公司部門空間感」的核心價值。
- **建議怎麼改**：
  在部門牆的「子部門卡」上，除了色點外，**直接列出該子部門底下「亮紅/黃燈或有新留話」的子節點小籤（最多 2～3 個，可直接點擊跳轉）**；或者在左欄/麵包屑旁提供一個輕量的「部門樹狀快速導覽（Tree Popover）」，彌補 v2.0 沒有地圖時的跨層級視野。

### 3. [中] 「點一下選、點兩下進、點已選中的部門進」在 Web 介面會造成誤跳轉與右欄閃爍
- **位置**：`02c §3.2`（怎麼走）
- **為什麼是問題**：
  1. **點已選中＝走進去**：如果某個部門已經處於選中狀態（例如剛從網址還原、用方向鍵移過去、或本來就選著它），使用者想把焦點拉回中欄而隨手點一下該部門卡，就會意外觸發「走進去（drill-down）」切換整個中欄。
  2. **點兩下（dblclick）的請求浪費**：對一個未選中的部門點兩下時，第一下 `click` 會先改變 `selection` 並觸發右欄抓取該部門資料；0.2 秒後的第二下又觸發路由進入該部門。而且文中**未定義「走進一個部門後，預設 `selection` 是誰」**（是維持選中該部門本身＝即主管桌，還是清空選取？）。
- **建議怎麼改**：
  1. 取消「點一下已選中的部門＝走進去」的隱晦規則。改為：**點卡片任意處＝選中；點卡片標題/「進入 ▸」按鈕、雙擊卡片、或按 Enter＝走進去**。
  2. 明確定義：走進某部門時，`focus` 設為該部門，且預設 `selection` 就是該部門本身（對應第 0 格主管桌），這樣第一下選中與第二下走進去的右欄對象完全一致，不會引發兩次不同的 API 請求與畫面閃爍。

### 4. [低] 什麼都沒選時顯示「公司總覽」，與「永遠在那裡的打字框」行為未定義
- **位置**：`02c §2`（最後一段）、`02c §4.1`（一個打字框，三種模式）
- **為什麼是問題**：
  `02c §2` 說「什麼都沒選時，右欄顯示『公司總覽』」，但 `02c §4.1` 說「打字框釘在右欄底部，永遠看得到」。當剛打開頁面、什麼都沒選時，打字框的「對：[ ? ]」是空的，這時使用者按 `/` 打字並按 `Ctrl+Enter` 會發生什麼事？
- **建議怎麼改**：
  明確定義：當 `selection` 為空時，打字框的對象欄顯示「`對：[+ 點此或按 Ctrl+K 選對象]`」（或預設帶入當前所在部門 `focus` 的主管）；若對象為空時按送出，游標自動聚焦到對象選擇器並提示選取對象，但允許先打字存為「未指定對象草稿」。

## 二、互動細節的漏洞（狀態、快捷鍵衝突、草稿、焦點、即時更新干擾）

### 5. [高] 決定單與右欄打字框同時存在時，`Ctrl+Enter` 與數字鍵 `1`–`4` 發生嚴重快捷鍵衝突
- **位置**：`02c §4.1`、`02c §4.3`、`02c §4.8`（鍵盤一覽）
- **為什麼是問題**：
  1. **雙 `Ctrl+Enter` 致命衝突**：決定單開著時，右欄同時開著該部門的往來與底部打字框（`02c §4.3`）。兩邊的送出按鈕都綁定 `Ctrl+Enter`！如果使用者在看決定單時，剛點過右欄或打字框，按 `Ctrl+Enter` 到底送出的是打字框的話，還是決定單（甚至可能是不可逆的決定單）？極易造成誤送。
  2. **數字鍵 `1`–`4` 衝突與選項編號矛盾**：`02c §4.8` 定義 `1`–`4` 是「頁首四個數字的篩選」；`02c §4.3` 卻說在決定單裡「數字鍵選選項」。且 §4.3 畫的選項是 `(●) a`、`( ) b`，題號才是 `1.`、`2.`。決定單打開時按 `1` 到底是選選項 `a`、跳第 `1` 題、還是觸發頁首篩選把左欄洗掉？
- **建議怎麼改**：
  1. `Ctrl+Enter` **嚴格綁定當前 DOM 焦點所在的表單容器（form scope）**：焦點在右欄打字框內才送出打字框；焦點在決定單內才送出決定單；焦點在兩者之外時，`Ctrl+Enter` 不動作（或僅對決定單生效但必須有明顯焦點框）。對於「不可逆」決定單，禁用 `Ctrl+Enter` 直接送出，必須手動點擊按鈕或二次確認。
  2. 頁首篩選改用 `Alt+1`～`Alt+4`（或決定單開著時停用頁首數字鍵），決定單選項統一對應鍵盤 `a/b/c` 或 `1/2/3` 並標示在介面按鈕上。

### 6. [高] 中文輸入法（IME 組字）下按 `Esc` 與 `Enter` 會誤觸離開輸入框或直接跳轉
- **位置**：`02c §3.2`（Esc 行為）、`02c §4.8`（鍵盤一覽）
- **為什麼是問題**：
  在繁體中文環境（注音、倉頡）打字時，使用者按 `Esc` 是為了「取消選字清單或清除未確認的注音符號」，按 `Enter` 是為了「確認中文組字」。
  1. `02c §3.2` 規定：「游標在有字的輸入框裡時，Esc 只會讓游標離開輸入框」。若未檢查 `KeyboardEvent.isComposing`（或 `keyCode === 229`），使用者打中文按 `Esc` 取消選字時，輸入框會直接被 `blur()` 踢出焦點！
  2. 更糟的是，如果輸入框原本是空的（剛開始拼第一個中文字，尚未確認上字，`value` 仍為 `""`），按 `Esc` 取消注音時，系統判定為「沒字的輸入框」，會直接把決定單關掉或取消目前選取的對象！
- **建議怎麼改**：
  全域與區域鍵盤監聽器必須統一加上守衛：`if (e.isComposing || e.keyCode === 229) return;`。且只要游標在輸入框內（不論有無字），按第一次 `Esc` 一律只是 `blur()` 離開輸入框，絕不直接關閉面板或取消選取。

### 7. [中] 草稿以「對象＋模式＋指令種類」為 Key，導致切換「說話／寄信」或增減對象時草稿憑空消失
- **位置**：`02c §4.1`、`02c §4.2`、`02c §4.6`（草稿）
- **為什麼是問題**：
  1. 使用者在「說話」模式打了長文，打到一半決定改用「寄信」模式（加上標題），一點「寄信」，因為草稿 Key 裡綁死了 `模式`，原本打的內文瞬間變成空白！使用者體驗上就像草稿丟了一樣。
  2. 在多選對象（`02c §4.2`）時，若 Key 綁定對象集合，使用者增減一個收件人，剛剛打好的群發草稿也會瞬間消失。
  3. `localStorage` 若無上限與過期清理，已收隊（gone）的 agent 草稿會永遠卡在頁首的「草稿 N」清單中。
- **建議怎麼改**：
  將草稿結構改為**以「主要對象（或單一工作階段）」為單位儲存一個包含全欄位的物件**：`{ text, mailTitle, mailStatus, orderKind, expandFields, hireFields, powerFields, updatedAt }`。如此一來，在同一個對象下切換「說話 ↔ 寄信 ↔ 指令」時，共用的正文 `text` 與各指令欄位都能無縫保留，完全不閃退。

### 8. [中] 右欄開著時「自動更新」與「打開就算已讀（seen）」結合，會把使用者沒注意到的新回信自動銷帳
- **位置**：`02c §2`（待辦欄消失條件）、`02c §4.5`（右欄自動更新）、`02c §9.4`
- **為什麼是問題**：
  `02c §9.4` 定調「打開那段往來就算看過了（從待辦欄消失）」，而 `02c §4.5` 規定「右欄開著時每 15 秒或一收到通知就自己更新」。如果董事長把右欄停在 `ok-kf` 的往來頁，但視線正在看中欄地圖、或往來捲軸停在上面看舊信，此時背景抓到一封新回信，因為「往來正開著」就被自動寫入 `seen`，這封新回信將**永遠不會出現在左欄待辦的「✉ 回了話」**，造成漏信！
- **建議怎麼改**：
  只有在以下情況才觸發標為 `seen`：
  1. 使用者**主動點擊切換**到該對象的「往來」頁籤時；
  2. 或者往來已開著時收到新信，必須滿足**「分頁在前景（`document.visibilityState === 'visible'`）＋往來捲軸位於底部＋使用者在頁面有滑鼠/鍵盤活動（或點擊該欄）」**才標為已讀；若捲軸不在底部，應在往來底部顯示「↓ 有 1 則新回覆」並保留在左欄待辦。

### 9. [中] 方向鍵在「中欄卡片移動選取」與「右欄長文捲動」之間缺乏焦點隔離
- **位置**：`02c §3.2`、`02c §4.8`
- **為什麼是問題**：
  `02c §4.8` 定義方向鍵為「移動選取」。當使用者點了右欄的「往來」或「做過・說過」想用上下方向鍵捲動閱讀長紀錄時，如果方向鍵是全域綁定，按「下」就會把中間部門牆的選取換成下一個員工，導致右欄瞬間切換成別人的卡片，打斷閱讀。
- **建議怎麼改**：
  明確劃分三欄的鍵盤焦點區域（Roving Tabindex 或 Focus Zone）：只有當焦點在「中間欄（部門牆/地圖）」或全域無特定區域聚焦時，方向鍵才移動卡片選取；當焦點在左欄時，上下鍵移動待辦項目；當焦點在右欄捲動區時，保留瀏覽器原生的上下鍵捲動行為。另外請統一 `02c §4.8` 中 `J`/`K` 的大小寫定義（建議統一小寫 `j`/`k`，不需按 Shift）。

## 三、技術選擇與離線建置的風險

### 10. [高] `pnpm install --offline` 必然失敗：`vite` 等套件在 npm 快取而非 pnpm store，且缺離線解析 metadata
- **位置**：`03 §12.1 #3`、`03 §12.2`（技術棧相依砍到最少）
- **為什麼是問題**：
  `03 §12.1 #3` 實查發現：`react`、`tailwindcss` 在 **pnpm store**（`~/.local/share/pnpm/store`），但 `vite@8.3.5`、`rolldown@1.2.15`、`@playwright/test@1.64.1`、`postcss@8.5.31` 是在 **npm 快取（`~/.npm/_cacache`）**！
  然而 `03 §12.2` 卻計畫在全新目錄跑 `pnpm install --offline`。**pnpm 的離線模式完全不會讀取 `~/.npm/_cacache`**，且在沒有現成 `pnpm-lock.yaml` 的情況下，pnpm 需要完整的 registry package metadata 才能解析龐大的子相依樹（transitive dependencies），直接跑 `pnpm install --offline` 100% 會報 `ERR_PNPM_NO_OFFLINE_META` 或找不到 `vite`。
- **建議怎麼改**：
  `01c §3` 已經指出本機有現成的 `~/code/web-template/`（含 React 19 + Tailwind 4 + TS 5）與 `~/repo/game_dev/mecha-srpg`（含 Vite 8.3.5 + Playwright 1.64.1）。施工第 1 步不要盲跑 `pnpm install --offline`，而是**直接對照這兩個現成專案的 `package.json` 與 lockfile（或直接複用/連結它們已安裝好的 `node_modules` 結構，或用 `npm install --offline --prefer-offline` 搭配 npm cache）**，能省掉連網下載的風險。

### 11. [中] Node 24 `node --test` 原生型別剝除（Type Stripping）與 Vite 模組寫法存在相容性陷阱
- **位置**：`03 §12.2`（表格第 4 列）
- **為什麼是問題**：
  計畫用 `node --test` 直接跑 `.ts` 測試。但 Node 24 的原生 Type Stripping 有兩個嚴格限制：
  1. 強制要求 import 路徑寫出完整副檔名（例如 `import { calc } from './layout.ts'`），而一般 TS/Vite 專案習慣省略 `.ts`（會導致 Node 執行時報 `ERR_MODULE_NOT_FOUND`）。
  2. 不支援 `enum`、parameter properties 等語法，且 `node --test` 環境沒有 `window`、`localStorage`（草稿測試會用到）。
- **建議怎麼改**：
  在 `tsconfig.json` 開啟 `"allowImportingTsExtensions": true`、`"erasableSyntaxOnly": true`（TS 5.8+ 支援，編譯期就能擋掉 Node 不支援的語法），並規定所有 `src/` 內部匯入一律寫 `.ts`／`.tsx` 副檔名；草稿與狀態測試將 storage 介面抽象注入（或引入 `mecha-srpg` 現有的 `happy-dom`）。

## 四、後端新接口（pulse/rev/ETag、outbox、ui-state、第二個 port）的正確性與安全

### 12. [高] `B3 /api/outbox` 的「120 秒內有 pulse 才查」與「只查 24 小時內」會造成冷啟動狀態過期與舊信卡死
- **位置**：`02c §7 B3`、`03 §12.1 #1`、`03 §12.3 B3`
- **為什麼是問題**：
  1. **冷啟動延遲（Stale on Open）**：`03 §12.1 #1` 規定「只在最近 120 秒內有 8768 頁面打過 `/api/pulse` 時才查」。這代表當董事長離開半小時後打開 8768 時，前 120 秒都沒有 pulse，所以他打開頁面第一眼拿到的 `/api/outbox` 是**半小時前的舊狀態**！如果當時有 18 封未回信，每輪（約 22 秒）只查 6 個對象，董事長要乾等超過 **1 分鐘**，頁面上的「等很久」與「已讀/已回」才會全部更新完，直接違反「打開第一眼掌握全局」與驗收第 4 條。
  2. **24 小時斷崖**：API 定為 `GET /api/outbox?days=7`，但後端只替「24 小時內、還沒回」的送出物更新狀態。若董事長週五晚上寄信、agent 週六滿 25 小時後才讀或回，這封信在 7 天寄件匣裡會**永遠卡在 `queued`**！
  3. **拖慢主採樣**：把最多耗時 1 秒的 6 個 CLI 呼叫塞在原本的 collector 主迴圈，會讓原本 2.4 秒的採樣變成 3.4 秒，連 v1（8767）也一起被拖慢。
- **建議怎麼改**：
  1. 當收到 `/api/pulse` 或 `/api/outbox` 且距離上次更新 `outbox` 超過 30 秒時，**立即在背景執行緒觸發一次 `outbox` 狀態檢查**，不要等下一個 20 秒 tick。
  2. 擴大檢查範圍：24 小時內的每輪查，24 小時～7 天內未結案的改為每 5～10 輪查一次（或收到新 relay 信件時比對收件人立即更新）。

### 13. [高] `B2 /api/pulse` 扣除時間欄位加上靜態雜湊，會導致「等很久」無法準時觸發、外部服務檢查時間凍結
- **位置**：`02c §2`、`02c §7 B2`、`03 §12.1 #4`
- **為什麼是問題**：
  1. **「等很久」的門檻是時間函數**：`02c §2` 規定閒著 10 分鐘沒讀、一輪裡 30 分鐘、讀了 60 分鐘沒回會進入待辦欄「⏳ 等很久」。當時間一分一秒過去，跨過 10/30/60 分鐘門檻的那一刻，後端的 `tree` 與 `outbox` 內容本身完全沒變，所以 `rev.tree` 與 `rev.outbox` 的雜湊不會變，前端不會重抓資料。若前端把「待辦清單計算」綁在 API 資料更新時才算，時間到了待辦欄跟分頁標題 `(N)` 根本不會跳出來！
  2. **外部服務 `checked_at` 凍結**：`03 §12.1 #4` 把外部服務的 `active_at`（即 `checked_at`）從 `rev.tree` 雜湊中扣掉。結果只要外部服務一直健康、狀態沒變，`rev.tree` 就永遠回 304，前端右欄外部服務卡上的「上次檢查時間（`02c §4.5`）」就會永遠停在幾小時前，誤導使用者以為健康檢查停擺。
- **建議怎麼改**：
  1. 前端「待辦欄（含等很久）」與「幾分鐘前」的計算必須訂閱一個**每 10 秒觸發一次的本地 Tick state**，將 `pulse.now`（伺服器最新時間）代入重新衍生計算，不依賴 `rev` 變化。
  2. `pulse` 回傳的物件既然每 5 秒抓一次，可在 `pulse` 中直接附帶 `ext_checked_at: epoch_s`（或前端直接用 `pulse.tick.at` 作為健康檢查的最後確認時間），確保外部服務卡的時間是活的。

### 14. [中] `B4 /api/ui-state` 缺乏 `rev` 同步、整包覆寫（Lost Update）且無容量清理機制
- **位置**：`02c §7 B2`、`02c §7 B4`、`03 §12.1 #5`、`03 §12.3 B4`
- **為什麼是問題**：
  1. `/api/pulse` 的 `rev` 字典裡只有 `tree, asks, relay, outbox, board, answered`，**漏掉了 `ui-state`**！因此「跨視窗同步已讀（`seen`）與知道了（`dismissed`）」（`02c §7 B4` 的設計目的）根本不會生效——視窗 B 不知道視窗 A 改了 `ui-state`。
  2. 更嚴重的是，因為 `PUT /api/ui-state?key=seen` 是整包 JSON 覆寫，當視窗 B 稍後將另一封信標為已讀時，會把視窗 B 記憶體裡的舊陣列整包 `PUT` 上去，直接**洗掉視窗 A 剛標記的紀錄**。
  3. `seen` 與 `dismissed` 只增不減，時間一久會塞滿無效歷史 ID。
- **建議怎麼改**：
  1. 在 `/api/pulse` 的 `rev` 中加入 `"ui_state": str`（四個 JSON 檔的 mtime/size 雜湊），視窗發現 `rev.ui_state` 變了就重抓並與本地狀態聯集（merge）。
  2. `seen` 與 `dismissed` 改存 `{ "<id>": epoch_s }` 字典，前端或後端在寫入時自動清理超過 14 天的舊紀錄，防止檔案無限膨脹。

### 15. [中] `B1` 第二個 port（8768）的 Host / Origin 檢查與 `poll.ts` 的 304 快取細節有漏洞
- **位置**：`02c §7 B1`、`03 §12.2`（`poll.ts`）、`03 §12.3 B1 & B2`
- **為什麼是問題**：
  1. **Host/Origin 檢查**：`02c §7 B1` 寫「Host／Origin 檢查本來就照各自 listener 的 port 算，不用改」。務必確認現有 Python 後端驗證 `Host` 與 `Origin` header 時，是讀取 `self.server.server_port`（各自實例的 8767 或 8768），而非讀取全域 `config["port"]`（8767）。若是讀 config，8768 發出的所有 `POST`/`PUT` 都會因 `Origin: http://127.0.0.1:8768 != 8767` 被擋下。
  2. **`poll.ts` 與 `/api/pulse` 重複工作**：`02c §7 B2` 設計前端每 5 秒問一次 `/api/pulse`，哪個 `rev` 變了才去抓哪個 API；但 `03 §12.2` 又寫 `poll.ts` 對每種資料定時抓並用 `ETag`/`If-None-Match` 拿 304。如果 `poll.ts` 自己定時抓 6 個端點，那 `/api/pulse` 就形同虛設；反之，如果靠 `pulse` 觸發，要注意瀏覽器原生 `fetch` 在收到 304 時會自動由瀏覽器 HTTP Cache 轉成 200 回傳給 JS（除非設 `cache: 'no-store'` 手動管 ETag），實作時若混淆這兩種機制會導致 `fetched_at` 計算錯誤。
- **建議怎麼改**：
  1. 明確檢查後端 `check_origin()` 邏輯，確保同時允許 `config` 中的所有 `ui_ports`。
  2. 統一輪詢架構：**前端只定時每 5 秒輪詢 `/api/pulse`**（加上右欄開著時每 15 秒抓當前對象的 `/api/agent` 與 `/api/thread`）。6 個全域資源（`tree, asks, relay, outbox, board, answered`）完全由 `pulse.rev.<key>` 變化來驅動 `fetch`，前端記憶體直接持有上一次的資料與 `rev`，既省去每輪發 6 個 304 請求的開銷，邏輯也最單純。

### 16. [中] 分期前後矛盾：後端 `B5`（更正關聯、批次）在 v2.0 實作，前端顯示卻拆到 v2.2
- **位置**：`02c §4.3`、`02c §7 B5`、`02c §8`（分期表）
- **為什麼是問題**：
  `02c §4.3`（v2.0 決定單）已經有「已處理頁的更正鈕」，且後端 `B5` 在 v2.0 就把 `correction_of` 與 `/api/answered` 的 `corrections` 欄位做好了；但 `02c §8` 卻把「更正跟原回答掛在一起」排到 **v2.2**。這導致 v2.0 使用者點了更正送出後，在「已處理」頁看不到自己剛寄出的更正，且後端 B5 的程式碼在 v2.0 寫完卻沒有前端對接與驗證。
- **建議怎麼改**：
  將「更正跟原回答掛在一起」直接納入 **v2.0**（因為 B5 後端已就緒，前端只差在已處理卡片下多印一行關聯信件）；至於 `batch`（多選群發）則可隨前端多選功能留在 v2.2，或 B5 只先留欄位。

### 17. [中] v2.0 驗收標準漏測「輸入與即時更新抗干擾」、「快捷鍵防呆」與「狀態持久化」
- **位置**：`02c §8`（v2.0 的驗收）、`03 §12.6`
- **為什麼是問題**：
  現有 6 條驗收只測了基本正向流程（Happy Path），完全沒測出 v1 最痛的互動邊界與本次新增的狀態機制：
  1. 沒測「正在看決定單或正在右欄閱讀時，背景 `pulse` 更新不會弄亂畫面或誤送」。
  2. 沒測「中文輸入法組字按 Esc、決定單與打字框並存按 Ctrl+Enter」等快捷鍵邊界。
  3. 沒測「B4 `ui-state`（標記紅燈知道了、回信已讀）重新整理後不會復活」。
- **建議怎麼改**：
  在 v2.0 的 Playwright 自動化驗收中補上這 3 條測試案例：
  - **驗收 7**：打開決定單同時在右欄打字框輸入文字，按 `Ctrl+Enter` 只送出焦點所在的表單；在有字的輸入框按 `Esc` 僅移開游標，決定單與草稿均不關閉/不遺失。
  - **驗收 8**：對紅燈節點按「知道了」、對新回信打開往來標為已讀後，重新整理頁面，該紅燈與回信不會再回到待辦欄。
  - **驗收 9**：在決定單作答到一半時，觸發後端 fixture 更新 `tree` 與 `asks`（新增一張決定單），當前作答中的決定單選項與備註不跳頁、不丟失。

# (B) 提案：6 條更好的做法

### 提案 1：用「單一 Pulse 驅動 + 本地時間 Tick」取代 `poll.ts` 的多路 ETag 輪詢
與其在 `poll.ts` 為 6 個 API 各自寫定時器、管理 `If-None-Match` 與 304（`03 §12.2`），不如徹底發揮 `B2 /api/pulse` 的優勢：
- **做法**：前端只有**一個**每 5 秒跑一次的 `/api/pulse` 輪詢器。它拿到 `rev` 字典（含新增的 `rev.ui_state`）後，與前端 `store` 裡的 `lastRev` 比對，**哪個 key 的 `rev` 變了，才發 `fetch` 去抓那個 API**。
- **好處**：平常沒事時，每 5 秒永遠只有 1 個極小的 `pulse` 請求（而非 6 個 304 請求）；搭配一個每 10 秒跳一次的本地時鐘 Tick 來重算「幾分鐘前」與「⏳ 等很久」，架構更乾淨，程式碼可從 120 行砍半到 60 行以內。

### 提案 2：草稿以「對象 ID」為單一 Key 儲存完整表單快照，支援跨模式無損切換
改善 `02c §4.6` 按「對象＋模式＋指令種類」切碎草稿的問題：
- **做法**：每個對象在 `localStorage` 只存一筆 `draft:<targetId>`，內容為 `{ mode, text, mailTitle, mailStatus, orderKind, orderParams, updatedAt }`。
- **好處**：董事長對某部門打字打到一半，不管怎麼切換「說話／寄信／指令（擴充、加人、電力）」，打過的文字跟填過的參數永遠都在，不會因為換模式而以為字不見了。

### 提案 3：決定單改為「中欄上方停駐（Docked Card）」，下半部保留部門牆視野
改善 `02c §4.3` 決定單蓋死中欄的問題：
- **做法**：點選待辦欄的「🔵 要你決定」時，決定單停駐在**中間欄的上半部（最多佔 55% 高度，可收折）**，中間欄下半部同步切換為該出題部門的「部門牆」，右欄開啟該部門的「往來」。
- **好處**：董事長在批閱決定單時，視線往下就能看到該部門所有員工（sol）現在是在跑還是停了，視線往右就能看主管留話與歷史往來，真正做到「三欄資訊同時輔助決策」，也消除了彈窗遮罩與右欄打字框的層級衝突。

### 提案 4：部門牆的「子部門卡」直接穿透顯示異常的深層節點小籤（解決 v2.0 無地圖盲區）
在 v2.0 還沒有地圖、又拿掉完整樹狀清單的過渡期：
- **做法**：當某個子部門底下（不論第幾層）有亮紅燈、黃燈或待決定的節點時，在部門牆的「子部門卡」裡，除了畫色點外，直接列出最多 3 個**可點擊的異常節點小籤**（例如 `🔴 ok-kf-b-sol-2 (exited 143)`）。
- **好處**：站在公司頂層就能一眼看到深層出事的具體員工，點一下小籤直接跨層級飛過去，不用像走迷宮一樣一層層點進去猜是哪一格紅燈。

### 提案 5：先由 opus 寫好「全域快捷鍵與焦點管理中心（`src/shell/keys.ts`）」，再交給 sol 並行開發
針對 `03 §12.6` 多個 agent 分頭寫 `inbox`、`stage`、`inspector`、`composer` 四塊面板的風險：
- **做法**：禁止各面板元件自己掛 `window.addEventListener('keydown')`。由 opus 在第一階段連同 `store.ts` 一起寫好唯一的 `keys.ts`，集中處理：
  1. `e.isComposing || e.keyCode === 229`（中文輸入法保護）；
  2. 當前活躍區域判定（`activeZone: 'inbox' | 'stage' | 'decision' | 'inspector' | 'composer'`）；
  3. `Esc` 堆疊與 `Ctrl+Enter` 的歸屬分派。
- **好處**：四個面板只透過 props 或 store 接收語意化動作，徹底杜絕快捷鍵互搶與中文選字誤觸。

### 提案 6：直接從本機現成專案提取離線套件或使用本地 tarball，確保 Step 1 零網路建置必過
針對 `03 §12.1 #3 & §12.2` 中 `vite` 在 `~/.npm/_cacache` 而非 pnpm store 的問題：
- **做法**：在執行 `pnpm install --offline` 之前，先從本機已有的 `~/repo/game_dev/mecha-srpg` 與 `~/code/web-template` 檢查已安裝的套件版本，或用 `npm cache` 匯出／直接複製這兩個專案的 lockfile 與離線快取設定（甚至在開發環境直接 link 現成專案的 toolchain）。
- **好處**：100% 避免因為跨套件管理員（pnpm vs npm）快取不通而被迫向使用者請求連網權限（省去 `03 §12.5` 第 2 件備案）。
