### (A) 審查

#### 一、跟現況／實測不符與資料結構矛盾

1. **[高] `ctl ls --json` 沒有 `code`，葉子節點的紅／灰燈與結束碼顯示會失靈（03 §9.1 #1 vs 02b §3.1/§3.2）**
   - **問題**：03 §9.1 實測第 1 項已確認 `aos-agent ctl ls --json` 的輸出**沒有 `pid`、`code`、`kind`**；第 2 項實測 `ctl state -t NAME all -j` 提到 `resources` 有 `pid`，但沒確認 `ctl state` 是否回傳結束碼 `code`。然而 02b §3.2 定義葉子節點亮紅燈是「停了且結束碼非 0／被訊號殺掉」、亮灰燈是「正常結束（code 0）」，§3.1 的 `rollup.line` 也寫 `stopped, code 143`。而且 03 §9.2 只對「新出現的名字問一次 `ctl state` 快取 `kind`」，沒有在節點變成 `stopped` 時重查。這樣在 0a 期，固定程序根本拿不到 `code` 來區分正常結束（灰）與異常崩潰（紅）。
   - **建議**：施工前先實測 `ctl state -t NAME -j` 對已停止的 proc 是否回傳 `state.code` 與 `signal`。若有，當 `ctl ls` 發現節點剛進入 `stopped` 時，觸發一次 `ctl state` 並把結果快取進 `state/stopped/<名>.json`；若連 `ctl state` 都沒給 `code`，則紅／灰燈改依賴 `ctl ls` 的 `reason`（非空錯誤訊息亮紅、空字串亮灰）與 `cooldown.failures > 0` 判定。

2. **[高] 主管同時是「部門房間」與「房間裡第一張桌子（lead）」，在單一節點格式下會產生渲染與燈號衝突（02b §3.1 vs §3.2 vs §5.4）**
   - **問題**：02b §3.1 定義有 `children` 的節點就是部門，`ok-kf` 的 `children` 是 `["ok-kf-aide-1", "ok-kf-sol-1", "ok-kf-b"]`；但 §5.4 展開部門時卻在房間裡多畫了一張不在 `children` 裡的桌子 `ok-kf (lead)`。這會造成三個漏洞：
     1. **燈號污染**：§3.2 說把第一輪的隊伍燈號（如「隊長停了底下還在跑＝紅」「小助手沒聲音＝紅」）原樣搬來當作有孩子節點的 `self.light`。但如果 `self.light` 存的是「整個部門的異常」，那房間裡代表主管本人的 `ok-kf (lead)` 桌子要亮什麼燈？主管本人明明正常 `running`，卻因為小助手失聯而在自己的桌子上亮紅燈？
     2. **第 5 期點不開主管的 bot 卡**：§5.3 規定「有孩子的大於 360px 展開孩子，葉子大於 360px 變 bot 卡」。主管有 `children` 不是葉子，若沒有獨立的 `lead` 桌子元素，使用者拉近主管只會放大房間，永遠打不開主管本人的 Did / Said 卡。
     3. **`rollup.nodes` 算術不一致**：`ok-kf` 有 3 個直屬 children，加上孫輩共 6 個節點，若畫面裡多畫一張 `lead` 桌又把 `aide` 算在 `nodes` 裡，畫面上的桌子數與 `nodes` 數字會對不上。
   - **建議**：將「主管個人（`self`）」與「部門整體（`rollup`）」徹底切開：`self.light` **只反映主管本人的程序狀態與待決單**（跟葉子同一套規則）；「隊長停了底下還在跑、小助手失聯、60 分鐘沒進度」算在 **`rollup.worst` / `rollup.why`**。凡是有 `children` 的 agent 房間，前端固定在左上角第一格（`slot 0`）渲染一張代表 `self` 的 `lead` 桌子，拉近這張桌子即可打開主管本人的 bot 卡。

3. **[中] 小助手（`aide`）放進 `children` 會佔用桌子座位並誤觸「底下還在跑」紅燈（02b §1 vs §3.1）**
   - **問題**：02b §1 說「小助手畫成部門房間門口的一個小圖示（不佔一張桌子）」，但 §3.1 的 JSON 卻把 `"ok-kf-aide-1"` 放進 `children` 裡。一旦進了 `children`，它就會領 `slot`、被當成一般孩子畫出桌子；更嚴重的是，當隊長與隊員都已正常停止（code 0），只剩小助手還在跑最後一輪 tick 準備寄 `DONE` 並自停時，固定程序看到「隊長停了、但 `children` 裡的 `aide` 還在 running」，就會誤判整隊亮紅燈！
   - **建議**：被認定為部門小助手的節點，只放進該部門節點的 `aide: {...}` 欄位，**不放進 `children`、不發 `slot`、也不計入「底下還有成員在跑」的紅燈判準**。

4. **[中] 單次腦工作 `llm_<id>` 若先當成節點再收進計數格，會塞爆 `layout.json` 並讓 304 快取失效（03 §9.1 #7 / §9.2 #4 vs 02b §5.2）**
   - **問題**：03 §9.1 實測確認 `llm-gpt` 是主樹上的一列，而單次工作 `llm_<id>` 也是主樹 daemon 表上來來去去的獨立列；§9.2 說將 `llm_` 開頭的算 `proc` 並收進 `llm_* ×N` 計數格。但若照 02b「每個 daemon 表上的列都是節點、配發 `slot` 並保留空位 24 小時」，幾百個短命的 `llm_<id>` 會把 `state/layout.json` 的座位表灌爆，且每次 `llm_<id>` 生滅都會改變 `tree.json` 使 `rev` 加一。
   - **建議**：在固定程序讀完 `ctl ls` 的最前端就直接攔截 `^llm_` 開頭的列，**不生成個別節點、不進 `layout.json`**，直接聚合成 `machine` 下的一個固定虛擬節點 `id: "llm-workers"`（顯示 `active: N`）。

#### 二、邊緣狀況与組樹漏洞

5. **[高] 每 tick 限查 30 個 running 的 `subagents`，會讓新子節點先掉進 `unassigned` 再跳回部門，破壞座位穩定（03 §8 vs 02b §5.2 / 0b 驗收）**
   - **問題**：03 §8 規定「跑著的每個 tick 最多查 30 個 `ctl state -t NAME subagents`，輪著查」。當系統 running 節點超過 30 個，且某隊長新開了一個名字不帶隊長前綴的子 agent（如 `sky-sol-1`），若這輪 tick 沒輪到查該隊長，新節點會先被歸進 `unassigned` 領一個 `slot`；下一輪查到隊長時又跳回部門領新 `slot`，在 `unassigned` 留一個 24 小時空位，直接違反 0b 驗收「位置不亂跳」。
   - **建議**：
     1. 跑著的 agent 的 `state/subagents/<名>.json` 快取在未輪到重查前**必須持續沿用**，不可視為空白。
     2. 當本輪 `ctl ls` 發現有「新出現且靠名字前綴歸不到隊」的 agent 時，優先把所有 running 的主管排進本輪 30 個查詢額度的最前面，確保新節點第一次進樹就歸對位置。

6. **[高] `/api/state` 回 304 時前端收不到新的 `last_tick`，3 分鐘後會誤報斷線橫幅（02b §3.5 / §5.5）**
   - **問題**：02b §5.5 規定「樹沒變時 `rev` 不變，伺服器回 304；頁首顯示 `last tick`，超過 3 分鐘出橫幅」。同時 `tree.json` 裡又有 `generated_at`、`seen_at` 與 claim 的 `age_s`。這裡有兩個死結：
     1. 如果把 `generated_at`、`seen_at`、`age_s` 算進「樹有沒有變」，那每分鐘 tick `rev` 必定加一，永遠不會有 304。
     2. 如果扣除時間欄位來算 `rev`，當系統平靜無事連續 4 分鐘沒變動時，伺服器每次都回 304（無 body），前端拿不到新的 `generated_at`，頁首的 `last tick` 就會超過 3 分鐘而**誤彈紅色警告橫幅**！
   - **建議**：
     1. JSON 內所有時間一律存絕對時間戳（如 `claimed_at`，不存相對秒數 `age_s`），「幾分鐘前」由前端自算；`rev` 只在扣除 `generated_at`/`seen_at` 後的實質內容改變時才遞增。
     2. 伺服器回傳 200 或 **304** 時，都在 HTTP 回應標頭帶上 `X-Last-Tick: <ISO時間或epoch>`，讓前端就算收到 304 也能更新頁首的 `last tick` 計時器。

7. **[中] `commit-request` 帳本（`log.jsonl`）的線名對映與時區跨日問題（03 §9.1 #5 / §9.2 #1）**
   - **問題**：03 §9.1 改讀 `~/.cache/aos-commit-queue/<repo-id>/log.jsonl` 的 `{"at","line","commit","paths"}` 來算部門卡的 `today: N commits, M files`。但：(1) `log.jsonl` 的 `line` 記錄的若是任務線名（如 `view-1114` 或 `skyrim`），而樹上的部門節點 `id` 是 agent 名（如 `ok-view`、`ok-skyrim`），直接字串相等會全部對不上；(2) 若用 UTC 切「today」，台灣時間早上 8 點前會切錯天。
   - **建議**：先確認 `log.jsonl` 裡 `line` 的實際命名慣例，支援正規化對映（例如雙向比對 `<id>` 與去掉 `ok-`／去掉 `-MMDD` 後的字根，或允許 `aide.json` 指定 `line` 名）；時間統計改用本機時區當日 00:00（或「過去 24 小時內」），且只從檔案尾端往前讀，不整檔掃描。

8. **[中] 子 daemon 節點 ID 含斜線 `/` 會弄壞 `/api/node/<id>` 的 HTTP 路由（02b §3.1 / §3.5）**
   - **問題**：02b §3.1 規定子 daemon 裡的 proc ID 格式為 `<daemon 節點 id>/<名字>`，而 §3.5 與 §6.4 的 API 路徑是 `/api/node/<id>` 與 `/api/node/<id>/bot`。一旦 `<id>` 含有 `/`，HTTP path routing 會把斜線當成路徑層級而解析失敗。
   - **建議**：將階層 ID 的分隔符改為冒號 `:`（如 `subdaemon:proc1`），或把 API 改為 `/api/node?id=<id>`。

9. **[中] `view_note blocked '...' --on <對方>` 指向收隊節點、拼錯字或形成死鎖時的畫法未定義（02b §4）**
   - **問題**：主管手敲 `--on <節點名>` 時可能拼錯、對方可能已收隊不在畫面上、或對方縮在某個還沒展開的子房間裡，這時跨房間的「waiting on」虛線箭頭沒有終點座標可連；若 A `--on` B 且 B `--on` A 還會形成死鎖。
   - **建議**：若目標節點縮在某個祖先房間內，箭頭終點自動吸附到**當前畫面上可見的祖先框**；若目標不在樹上，不畫箭頭，改在自身房間顯示文字籤 `waiting on <名> (missing)`；若固定程序發現等待鏈成環，兩邊標記 `deadlock!`。

#### 三、前端可行性（零依賴 SVG、語意縮放、手機）

10. **[高] 原生 SVG `<text>` 不支援自動換行與撐開框高，純 SVG 畫卡片在實作上極度脆弱（02b §5.2 / §5.4）**
    - **問題**：02b §5.2 決定用「零依賴的 SVG」畫所有房間、桌子與兩行長句（最多 120 字的留話與觀察）。但原生 SVG 的 `<text>` **沒有自動換行（word-wrap），也沒有 CSS Flexbox 排版**！要把兩行變動長度的中英文句子、數字籤、claim 標記排進框裡還不重疊、不爆框，純靠 SVG `<tspan>` 算字寬在手機與桌機不同字體下會變成排版災難。
    - **建議**：維持「零依賴」但調整 DOM 結構——**房間與卡片用一般 HTML `<div>`（放在一個用 CSS `transform: translate3d(x,y,0) scale(k)` 縮放的容器裡，或包在 SVG `<foreignObject>` 內），只用一層透明 `<svg>` 畫跨房間的虛線箭頭**。這樣卡片內部直接享有標準 CSS Grid / Flexbox 與文字自動換行，程式碼少一半且絕不破版。

11. **[高] 語意縮放以「父框 > 360px 展開孩子」為門檻，在孩子數量多寡不同時會導致子框過擠或父框尺寸跳動（02b §5.2 / §5.3）**
    - **問題**：02b §5.3 規定父框在螢幕上 `120～360px` 時畫兩行字＋孩子畫小點，`> 360px` 時文字縮成標題列、把每個孩子用同一張表畫出來。問題是：
      1. 一個有 16 個孩子的部門，當父框剛滿 360px（排 4×4）時，每個子框只有 `70px` 寬；而只有 2 個孩子的部門，父框 350px 時明明空間超大卻還只能畫兩個小點。
      2. 當父框從 359px 放大到 361px 的瞬間，內部從「兩行大字」切換成「4×4 子框格子」，若父框在世界座標（world space）的長寬比固定，很容易裝不下或留白過大；若動態調整父框大小，又會推擠旁邊的部門，違反「位置一個像素都不動」。
    - **建議**：
      1. **所有框在世界座標的尺寸與 `slot` 位置在排版時一次算定，縮放過程絕不改變盒子的幾何尺寸**，只切換盒子內部的顯示細節（LOD）。
      2. 把「何時把孩子從小點變成名牌／卡片」的判斷，從「看父框是不是 > 360px」改為**「直接看子框自己在螢幕上的像素寬度（`<24px` 圓點、`24～120px` 簡卡、`>120px` 詳卡）」**。這樣不管一個部門有 2 個還是 20 個孩子，每一層真的都只靠同一條規則運作。

12. **[中] 大螢幕拉近時多個葉子同時 > 360px，或拖曳掃過葉子，會瞬間觸發大量 `/api/node/<id>/bot` 請求（02b §5.3 / §5.5 / §6.4）**
    - **問題**：在桌機大螢幕拉近時，畫面上很容易同時有 4～8 張員工桌子寬度超過 360px；使用者平移畫布時更會連續掃過十幾張桌子。若葉子一超過 360px 就自動打 `/api/node/<id>/bot`（並每 5 秒輪詢），後端就會同時 spawn 十幾個 `aos-agent` CLI 子程序。
    - **建議**：葉子放大超過門檻時，只直接顯示 `tree.json` 已有的 **Now** 資訊；需要現場跑 CLI 的 **Did / Said（`/api/node/<id>/bot`）**，必須等使用者**明確點擊該員工卡（或點擊 `[Did]` / `[Said]` 頁籤）**才對當前選中的唯一一張卡發送請求。

#### 四、安全與資源成本

13. **[高] `/api/node/<id>/bot` 在 HTTP handler 內即時呼叫 `aos-agent` CLI，有阻塞伺服器與子程序風暴風險（02b §6.4 / §6.5）**
    - **問題**：第 5 期點開 bot 卡時，HTTP 伺服器要現場執行 `aos-agent ctl state -t NAME all -j` 與 `aos-agent history -t NAME ls -j`。Python 標準庫 `HTTPServer` 預設是單執行緒，跑一次 CLI 動輒數百毫秒至 1 秒以上，期間會把所有 `/api/state` 輪詢與決策單提交全部卡死；若改多執行緒但無併發上限，連點幾個員工就會產生 subprocess 風暴；此外 `<id>` 若未對照 `tree.json` 白名單，直接餵給 CLI 也有參數探測風險。
    - **建議**：
      1. 伺服器使用 `ThreadingHTTPServer`，但對 CLI 呼叫加上全域 `Semaphore(2)`（最多同時跑 2 個 `aos-agent` 子程序）與 `timeout=5s`，超時回 `504` 不卡死。
      2. `<id>` 必須先在記憶體中的 `tree.json` 查驗存在且 `kind == "agent"` 才放行。

14. **[中] 第 7 題（是否准許唯讀翻 stack）選項 b 直接讀 `claude/live.jsonl` 的風險與代價（01b A / 02b §10 第 7 題）**
    - **問題**：01b A 實測單一 `live.jsonl` 就有 1.36 MB（長線甚至可達數十 MB），內含完整對話、Bash 輸出與檔案寫入內容。若選 b 讓 `aos-view` 直接去讀它，不僅違反知識庫規則 1 的邊界，每次點開 eca 卡都要解析數 MB 的 JSONL，且讓含敏感資訊的完整對話進入 `aos-view` 記憶體。
    - **建議**：第 5 期堅守 **選項 a（只走正式介面，eca 的 Did 標 `not recorded`）**；若使用者未來真的需要看 eca 用過哪些工具，建議走 **選項 c（在 `aos-agent` 正式指令或 eca hook 補一個只輸出工具名與時間的輕量摘要介面）**，不要開「外部工具直接翻 `live.jsonl`」的破口。

15. **[低] 03 §9.3 第 2 期「一天查一次 `ss`」在每分鐘單次執行的 systemd tick 下需要落盤快取（03 §9.3）**
    - **問題**：`aos-view` 的 tick 是每分鐘啟動一次的短命程序，若不把 `ss` 的檢查時間與結果存進 `state/`，每次 tick 都會重跑或不知道上次何時跑過。
    - **建議**：將 `ss -tlnH sport = :4000` 的結果與 `checked_at` 寫入 `state/externals.json`，距離上次超過 86400 秒才重跑。

### (B) 提案（不推翻骨架與第一輪定稿的具體改良）

1. **「HTML 盒子樹 ＋ 頂層單一 SVG 圖層」取代全 SVG 繪製**
   - 畫布底層用 `<div id="world">` 搭配 CSS `transform: translate3d(x,y,0) scale(k)` 負責平移縮放，裡面的部門房間與員工桌子全用一般 HTML `<div>`（天然支援 CSS Grid、文字自動換行、省略號與無障礙選字）。
   - 畫布上層蓋一張全螢幕透明 `<svg id="overlay">`，專門畫**跨部門的 `waiting on` 虛線箭頭**與**不隨縮放變小的紅／藍圖釘**（直接用螢幕座標 `getBoundingClientRect()` 畫，圖釘與線寬永遠保持固定像素，連反除 `scale` 都省了）。依然 100% 零依賴，且單檔 `export` 照常運作。

2. **用「盒子自身螢幕寬度」做單一規則的碎形語意縮放（True Fractal LOD）**
   - 廢除「父框 > 360px 展開孩子」的特例，改成每個節點框（不論第幾層）都只看**自己在螢幕上的渲染寬度 `w = world_width * scale`**：
     - `w < 24px`：只顯示圓點（部門用 `rollup.worst` 色，葉子用 `self.light` 色）。
     - `24px ≤ w < 120px`：顯示燈號＋名字（部門加 `+N`）。
     - `120px ≤ w < 320px`：顯示標題、燈號、兩行句子（主管留話／助手觀察）、數字籤；有孩子者底部只顯示孩子色點列，不渲染子框 DOM。
     - `w ≥ 320px`：若有孩子，文字縮成頂部標題列，內部格線渲染子節點框（每個子框再依自己的 `w` 套用同一張表）；若為葉子，顯示 Now 詳情與 `[載入 Did / Said]` 按鈕。

3. **部門房間內固定 `slot 0` 為「主管桌（Lead Desk）」，切開 `self` 與 `rollup` 燈號**
   - 任何有 `children` 的節點，其 `self.light` 只算主管個人狀態，`rollup.worst` 才算部門級狀態（含「隊長停了底下還在跑」「小助手失聯」）。
   - 當房間放大到 `w ≥ 320px` 展開內部格線時，左上角第 0 格固定渲染主管本人的桌子（讀 `self`），後面才依 `slot` 排 `children`（不含 `aide`）；`aide` 固定畫在房間標題列右上角當狀態徽章。這樣主管本人可被點擊查看 bot 卡，也不會跟小助手搶座位。

4. **304 快取搭配 `X-Last-Tick` Header 與絕對時間戳**
   - `tree.json` 內所有時間一律存 UTC ISO 字串（前端自算 `3m ago`）；固定程序對扣除 `generated_at` / `seen_at` 後的樹算 hash，有變才把 `rev` 加一。
   - `/api/state` 回傳 `304 Not Modified` 時，固定帶上 `X-Last-Tick: <generated_at>` 與 `X-User-Ask-Count: <N>`，讓前端在不重傳 JSON、不重繪 DOM 的情況下，仍能即時更新頁首的 `last tick` 秒數。

5. **停機節點狀態快取（`state/stopped/`）與新孤兒優先查 `subagents`**
   - 當節點在 `ctl ls` 首次呈現 `stopped` 時，查一次 `ctl state -t NAME -j` 存入 `state/stopped/<名>.json`，確保拿得到 `code` / `signal` 與最後資源快照，之後不再重查。
   - 每分鐘 30 個 running `subagents` 查詢額度，優先分給「本輪有新節點誕生時的所有 running 主管」，且舊快取在被覆蓋前持續有效，保證沒有任何節點會在 `unassigned` 與部門之間跳動。

6. **Bot 卡採「點選才拉取（Click-to-Fetch）＋ 後端 Semaphore(2)」**
   - 縮放或平移經過員工桌子時絕不自動呼叫 `/api/node/<id>/bot`；只有當使用者明確點擊某張員工桌進入聚焦模式（或點開 `Did` / `Said` 頁籤）時才發請求，且離開或切換節點就停止。後端以 `Semaphore(2)` + 30 秒記憶體快取保護 `aos-agent` CLI 不被併發打爆。
