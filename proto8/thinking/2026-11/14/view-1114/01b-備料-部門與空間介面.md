## 使用者追加原話（11-14，一字不改，頂層轉）

> 讓我掌握全景這塊，我這邊還有個餿主意：就像是管理公司一樣，要讓我這個董事長掌握狀況，所以就是分部門這樣

> 就是說，我們人類使用者，比較擅長3d/2d空間的縮放移動，我可以拉高視角看到各部門，也可以點進去看到各部門內部各員工的狀況(這個比較麻煩，未必一定要做)。

> 然後這可以嵌套

> 啊，要看員工狀況，就是用bot模型，他現在處在啥狀態，他過去幹了啥，說了啥。

> （頂層問「bot 模型」是不是指把每個 agent 當成 bot 看狀態和紀錄）對，就是這個意思。普通的proc，或許...也可以看到狀況？

頂層轉述的要求（任務書「補充」節）：
- 公司比喻是**第二個點子**，跟「小助手＋中轉信箱＋網頁」一起考慮，可以合起來用，也可以各成一套方案比較。要想清楚：部門怎麼分（按線、按性質如 kernel／工具／外部專案，或別的）、主管是誰（現有 opus eca 還是另設）、董事長看到的層次（先看部門報告，需要時往下鑽）、部門之間怎麼協調、怎麼對上 aos 現在的 kernel 樹（頂層 gate → ok-* → sol）。
- **空間式介面**，2D 或 3D：拉高看各部門，點進部門看每個員工（這一層「未必一定要做」，列為可選的後期項目）。要比較 2D／3D、技術、手機能不能操作、資料怎麼即時更新、每層顯示什麼；字要白話、只講結論。
- **嵌套**：部門裡再有部門，縮放一層層往下都通；每層同一套畫法與資料格式（像碎形），層數不限，對上「kernel 底下再掛 kernel」。
- **bot 模型**＝把每個 agent 當成一個 bot，看三樣：現在的狀態（fsm 的 idle/think/wait/act、eca 的 running/stopped/sleeping、queue 幾封）、過去做了什麼（用了哪些工具、改了哪些檔、commit 了什麼）、說了什麼（寄出的信、回覆）。**資料先用現成的，不另造紀錄**。
- **普通 proc 第二優先**（使用者說「或許」）：daemon 表的 exec 列、clock、hook、sweeper、llm kernel、LiteLLM proxy。至少有 phase、pid、啟動時間、退出碼、stderr 尾巴、資源用量；有 state.json 的再加。**agent 與普通 proc 最好共用同一套外殼**，agent 只是多「說了什麼」和「腦在想什麼」兩層。

## 結論先講

1. **bot 模型的資料多數現成**：狀態（`state.json`、fsm 的 `stage.txt`、queue）、做了什麼（fsm 的 `observed.jsonl`＋`history.jsonl`；eca 的 `claude/live.jsonl`）、說了什麼（history、eca 的 live.jsonl 裡的 `mailbox_send` 呼叫與結果）。**沒有現成帳的兩樣**：「改了哪些檔」（eca 用 Bash 改的檔沒有逐檔紀錄）與「commit 歸屬」（沒有 ledger；`commit-request` 的回傳只在呼叫者的紀錄裡）。
2. **普通 proc 有一套共用的生命週期資料**：daemon 表 `procs_state.json`（phase、pid、started_at_ticks、code、signal、reason、limits、auto_restart）＋`<stack>/stderr.txt`＋`/proc` 的用量。有 loop 的另有 `state.json`／`state_flux.json`；llm kernel 有 `used.json`、`ledger.jsonl`、`queue.json`；clock 有 `clock_register.json`。**LiteLLM proxy 不在 daemon 表上**（找不到 row、stack、服務紀錄）。
3. **「誰在誰底下」分三種關係記，沒有一處列全樹**：請求路由（`AOS_KERNEL`、gate 的 `next`）、subagent 所有權（父的 `tools/subagent/subagents.json`）、daemon 管轄（`procs_state.json`；daemon 可以是另一個 daemon 的 proc，可巢狀，沒有固定深度上限）。所以「部門樹」要由固定程序把三種關係合起來算，或由隊伍自己宣告（01 的 `aide.json`／信裡的 `parent`）。
4. **前端**：本機有 node v24，但沒有現成的 three.js、d3、pixi；現有看板前端是純 JS、零依賴。claude.ai artifact 的 CSP 擋所有對外連線（01 B）。

## A. 員工層（bot 模型）：現成紀錄對照

只盤點 ok-view 自己的兩個 stack（fsm：`procs/ok-view-sol-1`；eca：`procs/ok-view`），沒開別人的。

| 要看的 | 現成來源 | fsm | eca | 注意 |
|---|---|---|---|---|
| 狀態：程序 | `<stack>/state.json`（`phase paused pid code updated_at`） | ✓ | ✓ | 快照，不是時間線；`running` 不等於正在想 |
| 狀態：fsm 格子 | `<stack>/stage.txt`（純文字 `idle`／`think`／`wait`／`act`） | ✓ | — | 停了就是最後停的那格 |
| 狀態：排隊 | `<stack>/queue/new`、`cur`（信封 `sender sent_at body`） | ✓ | ✓ | 暫存，不是收件歷史 |
| 狀態：綜合 | `aos-agent ctl state -t NAME all -j`（who、state、history、mailbox、resources…） | ✓ | ✓ | 正式介面，不必直接翻 stack |
| 做了什麼：工具名、耗時、結果碼 | fsm `<stack>/observed.jsonl`（`kind name code elapsed_ms in_bytes out_bytes`；無參數、無正文） | ✓ | — | 父 agent 的 `tools/subagent/observed/<子>/observed.jsonl` 有副本；也沒有逐筆時間戳 |
| 做了什麼：完整參數與回傳 | fsm `history.jsonl`（`tool_calls[].function.name arguments`、tool 結果） | ✓ | ✗（eca 的 history 只有 queue 訊息與每輪最後回答） | 一題就 20 萬 bytes；內容可能含私人文字、秘密 |
| 做了什麼：eca 的原生工具 | eca `<stack>/claude/live.jsonl`（`type timestamp message.content[] name input tool_use_id`；含 Bash、Write、mcp 工具） | — | ✓ | ok-view 的約 1.36 MB／627 行；另有 `claude/transcripts/<session>.jsonl` 連到 `~/.claude/projects/` |
| 做了什麼：改檔 | Write／Edit 的參數（`file_path`）可抽；Bash 改的檔沒有 | 部分 | 部分 | **沒有逐檔帳、沒有 diff** |
| 做了什麼：commit | 只能從工具紀錄裡的 `commit-request` 回傳抽 hash | 部分 | 部分 | **沒有 commit ledger**；commit-request 的訊息檔 trailer 有線名（可反查 `git log`） |
| 說了什麼：收到、最後回答 | `history.jsonl`；`aos-agent history -t NAME ls`（每則 200 字） | ✓ | ✓（範圍窄） | eca 的 history 不留信封寄件人 |
| 說了什麼：寄出的信 | fsm history 的 `mailbox_send` 呼叫＋結果；eca live.jsonl 同 | ✓ | ✓ | 寄件方預設不留副本（沒給 `keep`）；要連結果一起看才知道寄成功沒 |
| 說了什麼：信件本身與回信串 | `mailbox/{new,cur,archive}/<信>/letter.json` | ✓ | ✓ | 讀了預設就刪；`keep` 才留 archive |
| 腦在想什麼 | fsm `think/request.json`（最後一份腦請求，含整段對話與工具定義，22 萬 bytes）、`think/sent.json` | ✓ | —（eca 在 live.jsonl） | 只有最後一份 |
| 子 agent | `tools/subagent/subagents.json`（`[{name, stack}]`）＋`observed/` | 有開才有 | 有開才有 | 名冊，不是啟停時間線 |

其他：`hooks/*/event.json`、`on_clock.json`（最近一次 hook 事件）、`hooks/mail_notify/notified.json`、`stderr.txt`、`queue/order.json`（計數器）。`history.jsonl` 可被 summarize／rm 改寫（移掉的進 `history_removed.jsonl`）；`observed.jsonl`、`live.jsonl` 沒查到輪替或上限。

## B. 普通 proc

| 欄位 | 來源 | 注意 |
|---|---|---|
| 名稱、phase、pid、code、signal、reason、limits、auto_restart、restart_on_stuck | daemon stack `procs_state.json` 的 `procs`（`proto8/impls/aos-daemon/src/child/child.cpp:262`） | 檔案快照；超過 100 列會拆成 `$ref` 分檔；`updated_at` 有變才更新 |
| 啟動時間 | `started_at_ticks`（`/proc/PID/stat` 第 22 欄） | 開機後 ticks；`ctl state` 換成 `up_seconds` |
| stderr 尾巴 | `<stack>/stderr.txt`（表頂 `procs_stderr` 宣告名字）；`reason` 會摘最後一行（約 300 bytes） | sweeper 可輪替 |
| 用量 | `/proc/PID/stat`、`statm` 沿 PPID 加總；`ctl state` 輸出 `memory_bytes cpu_seconds processes`（`proto8/cmd/aos-agent/aos_agent/ctl/state.py:208`） | 限制值在 `limits`，不是用量 |
| 重起次數 | **沒有公開欄位**；CLI 的 RESTARTS 取自 `cooldown.json.failures`（連續失敗數，只有 fsm／eca 寫） | — |
| `_sweeper` | loop 的 `state.json`／`state_flux.json`；`stderr_archives/` | 沒有持久的清掃歷史 |
| clock | `~/aos-home/.stack/clock`（cycle 整數）＋`clock_register.json`（登記項與目標 box） | |
| llm kernel `llm-gpt` | `endpoints.json`、`queue.json`、`used.json`（窗口、calls／tokens、分 pack、分 sender）、`ledger.jsonl`（逐封：endpoint sender model 時間 usage code；不存內容）、`budget_warned.txt` | 適合做「這個部門今天花了多少」 |
| `llm_<id>` 單次腦工作 | `requests/cur/<id>/` 的 `proc.json request.json reply.json` | 做完就清，不是歷史 |
| kernel station／kernel_gate | `<宿主 stack>/hooks/kernel_gate/`：`requests/`、`kernel.json`（`next`）、`hold.json`、`decisions/`；gate 自動初審另有 `triage.jsonl` | 不列「誰把我當上級」 |
| LiteLLM proxy | **不在 daemon 表上**；只有 `ss` 看得到它聽 `0.0.0.0:4000`（pid 36898） | 要看它只能從表外（`/proc`、`/v1/models` 健康檢查） |

## C. kernel 樹＝組織圖的材料

| 關係 | 記在哪 | 是不是「上下屬」 |
|---|---|---|
| 請求經誰審 | 寄件者的 `AOS_KERNEL`；gate 的 `kernel.json.next`；最後退到 daemon ctl 信箱 | 路由；每封信可分流，不一定成樹 |
| subagent 歸誰 | 父的 `tools/subagent/subagents.json` | 所有權；`agents_ctl add` 不記；經 gate 放行也不算 |
| proc 歸哪個 daemon | daemon 的 `procs_state.json` | 管轄；daemon 可以是另一個 daemon 的 proc，可巢狀，沒有固定深度上限 |

- 沒有一處列出整棵樹。
- 11-14 實況：頂層 repo-aos 開 gate、ok-* 是 opus eca 掛在它底下（工作區 `wf/temp/<名>`），ok-* 再掛 sol／astra（agent-fsm）；但 ok-view 與 ok-pilot 的環境沒有 `AOS_KERNEL`，起 sol 沒經過頂層 gate，所以「路由樹」跟「所有權樹」已經對不上。名字規矩 `<eca名>-<角色>-<n>` 是 11-14 才定的，之前的 `sky-sol-*` 不合。
- 07 的現行隊形就是一層層的：頂層（董事長的秘書）→ 線（opus eca，像部門主管）→ sol／astra（員工）→ 可再開 gate 掛自己的。
