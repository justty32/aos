## 0. 結論先講

1. **兩個點子合成一套**。第一輪（小助手 → 中轉信箱 → `aos-view` → 8767）是**資料怎麼來**；公司比喻與空間介面是**資料怎麼排、怎麼看**。兩者不搶同一個位置，沒有「二選一」可比。骨架一步不動。
2. **部門不另外劃，從樹長出來**：底下掛了東西的節點就是一個部門，主管就是它自己（現有的隊長），不另設主管。想按性質看（kernel、工具、外部專案）就貼標籤，標籤只影響顏色與篩選，不影響樹。
3. **每一層同一個「節點」格式**：自己的狀態（`self`）＋底下的彙總（`rollup`）＋孩子名單。部門、員工、普通 proc、daemon、外部服務都是它。彙總全由固定程序算，不經模型。
4. **樹的骨幹用「歸屬」**（宣告 → subagent 紀錄 → 名字前綴），歸不到的掛在管它的 daemon 底下，所以每個 proc 一定有位置。請求路由（gate）畫成疊在上面的標記，不當骨幹。
5. **空間介面定 2D、零依賴 SVG**，像一張辦公室平面圖：部門是房間、員工是桌子、房間裡可以再有房間。顯示多少看「這個框在螢幕上有多大」，所以層數不限、每層同一套畫法。
6. **決策卡不在地圖裡**，固定釘在螢幕邊（桌機右側、手機底部），縮放藏不掉；地圖上另有一個不隨縮放變小的藍色圖釘指出是哪個部門在等。
7. **董事長這頁只呈現協調、不做協調**：顯示誰 claim 了哪些檔、誰在等誰、哪張決策單兩個部門都在等。不新增任何協調機制。
8. **員工層（bot 卡）排成可選的後期**，先只走正式介面（`aos-agent ctl state`、`aos-agent history`）；「改了哪些檔」「commit 歸屬」不補帳，改在**部門層**用 `git log` 的線名 trailer 與 `commit-request claims` 顯示，員工層標 `unknown`。
9. **普通 proc 用同一個外殼**，只是少「說了什麼」一頁。基本狀態（phase、退出碼、reason）daemon 表本來就有，第 0 期就跟著出現；細節（用量、llm kernel 今天花多少、LiteLLM 健康檢查）排第 2 期。
10. **空間介面第 0 期就出現**（拆成 0a 清單、0b 地圖，都不用模型、不改活樹）。

要問使用者的：**7 題方向性問題**（第一輪 5 題，其中第 2 題更新；新增 2 題）＋第一輪的 4 件點頭照舊，這輪沒有新增要點頭的事。

## 1. 兩個點子怎麼合

**定案：合成一套。** 理由：

- 第一輪定的是管線（誰蒐、怎麼送、誰收、怎麼回），公司比喻定的是組織語言與畫面。把它們當兩套方案比較，等於拿「水管」跟「水龍頭的樣子」比。
- 公司比喻要的「部門匯報」正好就是第一輪的 `report` 信；「董事長往下鑽」正好就是第一輪「點一隊展開」。第二輪只是把它從一層變成任意層、從清單變成地圖。
- 分開做兩套會有兩份樹、兩種燈號算法，之後一定對不上。

**對照表**（之後文件與頁面都用這套字）：

| 公司 | aos／第一輪 | 說明 |
|---|---|---|
| 董事長 | 使用者 | 只看、只答決策 |
| 董事長秘書 | 頂層 `repo-aos` | 07 已經這樣叫；它也是一個部門節點（底下掛各線） |
| 部門 | 一支隊伍＝一個「底下有東西」的節點 | 第一輪的「隊」 |
| 部門主管 | 隊長（現有的 opus eca，或自己兼任的） | 不另設 |
| 員工 | 成員（sol、astra…） | 葉子節點 |
| **部門秘書** | **小助手 `<隊>-aide-1`** | 幫主管把部門狀況往上送；不做事、不做判斷、不代寫公文 |
| 公文／簽呈 | 決策單 | 主管自己寫，秘書只遞（第一輪四道保證照舊） |
| 收發室 | 中轉信箱 `~/.aos/view/mailbox` | |
| 總務（做報表的） | 固定程序 `aos-view` | 純程式，彙總都它算 |
| 董事長的桌面 | 全景頁 8767 | |
| 董事長的簽核匣 | 使用者專區 | 授權只在這裡產生，照舊 |
| 機房、設備 | 普通 proc、daemon、LiteLLM | 第 7 節 |
| 子公司／大樓 | 另一個 daemon（例 `llm-gpt` 自己是一個 daemon） | 嵌套的最外層 |

小助手在地圖上畫成部門房間門口的一個小圖示（不佔一張桌子），點它看的是「這個部門的回報正不正常」（最後一封信多久前、`summary_by`、`aide unfit`）。

## 2. 部門怎麼分

**定案：不預先分。部門＝樹上任何有孩子的節點，由 kernel 樹與歸屬紀錄自然長出來。**

- 「按線分」其實就是這個：現在每條線是一隻 opus eca 帶幾隻 sol，樹長出來就是一線一部門。
- 「按性質分」（kernel、工具、外部專案）現在沒有任何現成資料支持，要分就得有人維護一張分類表，而且今天六條線怎麼歸類還沒有穩定答案。這正是 user/03 說的「用多了自然長出來的，不特意規劃」「不要這麼早劃定界限」那一類。
- **所以設計成「長出來時接得住」**：
  1. 節點有一個選填欄位 `tags`（自由字串陣列，例 `["kernel"]`、`["external:skyrim"]`）。來源是主管聘小助手時在 `aide.json` 寫的，沒寫就空。
  2. 頁面對 `tags` 只做兩件事：上色、篩選（「只看 kernel 類」）。不拿它分組、不拿它算彙總。
  3. 哪天使用者覺得某種分法穩定了，再加一個「按標籤重排」的檢視，資料不用改。
  4. 主管可以在 `aide.json` 把 `parent` 寫成任何節點名（第一輪就有），所以想把三條線收進一個「大部門」時，只要有一個節點當它們的 parent，不必改程式。
- **主管是誰**：就是那個節點自己。不另設「部門主管 agent」——多一隻就多一層轉述，第一輪已定「上層不轉述下層」。
- **歸不到任何部門的**：agent 收在根底下的 `unassigned`；不是 agent 的 proc 掛在管它的 daemon 節點下（第 7 節）。這兩個是程式算出來的容器，不是我替他劃的部門。

這題的方向（自動長 vs. 使用者自己劃）留一題問他，見第 10 節第 6 題。

## 3. 嵌套的統一格式

### 3.1 一個節點

每一層都是同一個形狀。程式輸出，欄位名英文。

```json
{
  "id": "ok-kf",
  "kind": "agent",
  "body": "eca",
  "name": "ok-kf",
  "parent": "repo-aos",
  "parent_by": "declared",
  "slot": 2,
  "tags": [],
  "self": {
    "light": "green",
    "why": "",
    "state": "running",
    "activity": "working",
    "queued": 0,
    "code": null,
    "reason": "",
    "line": "B2 drawings revised, waiting for build",
    "line_by": "leader",
    "line_at": "2026-11-14T10:31:00Z"
  },
  "rollup": {
    "worst": "red",
    "worst_path": ["ok-kf-b", "ok-kf-b-sol-2"],
    "lights": {"red": 1, "blue": 0, "yellow": 0, "green": 4, "gray": 1},
    "nodes": 6,
    "running": 5,
    "asks": 0,
    "line": "1 red below: ok-kf-b-sol-2 (stopped, code 143)"
  },
  "children": ["ok-kf-aide-1", "ok-kf-sol-1", "ok-kf-b"],
  "aide": {"name": "ok-kf-aide-1", "last_letter_at": "…", "summary_by": "terra-aide", "status": "ok"},
  "marks": [{"type": "not_behind_gate"}, {"type": "claim", "files": 3, "age_s": 5700}],
  "seen_at": "2026-11-14T10:33:02Z"
}
```

| 欄位 | 意思 |
|---|---|
| `kind` | `agent`、`proc`（daemon 表上不是 agent 的列）、`daemon`、`external`（不在 daemon 表上的服務）、`group`（程式算的容器：根、`unassigned`） |
| `body` | `eca`、`fsm`、`exec`、`daemon`、`http`、`virtual`。只影響「自己那格」有哪些細節，不影響格式 |
| `parent_by` | 這條父子線是怎麼知道的：`declared`（`aide.json`／信裡的 `team`、`parent`）、`subagent`、`prefix`、`daemon`（都歸不到，掛在管它的 daemon 下） |
| `slot` | 在父節點裡的固定座位號，固定程序發、不重排（第 5 節：畫面位置不能亂跳） |
| `self` | 這個節點自己：燈、為什麼、程序狀態、一句話、那句話是誰寫的 |
| `rollup` | 自己加上所有後代的彙總；葉子的 `rollup` 就是自己一個 |
| `children` | 孩子的 id。有孩子＝部門（畫成房間），沒孩子＝員工或設備（畫成桌子） |
| `aide` | 這個部門的秘書狀況；沒有就 `null` |
| `marks` | 疊在節點上的標記（第 3.3、4 節） |

**「部門」不是另一種型別**：它只是有 `children` 的節點。主管自己的狀態在 `self`，部門的狀況在 `rollup`。所以畫法只有一條規則：「畫自己，再把孩子用同一條規則畫在裡面」。

`id`：頂層 daemon 底下直接用 daemon 表上的名字（整台唯一，07 的命名規矩）；另一個 daemon 裡的 proc 用 `<daemon 節點 id>/<名字>`，嵌幾層就幾段。

### 3.2 彙總怎麼算（全部由固定程序算，不經模型）

| 項目 | 算法 |
|---|---|
| 燈 `rollup.worst` | 自己與所有後代的 `self.light` 取最嚴重的；順序沿用 03 §8：紅 → 藍 → 黃 → 綠 → 灰 |
| `worst_path` | 從這個節點走到最嚴重那個後代的 id 路徑（點一下直接飛過去） |
| 數字 | `lights`（各色幾個）、`nodes`、`running`、`asks`（底下等使用者的決策單張數） |
| 一句話 `rollup.line` | 程式照固定句型組：`N need you, M red below: <id> (<why>)`；都正常就 `all N fine`。只講最嚴重的一個，其餘看數字 |
| 部門自己那句 `self.line` | 沿用 03 §8 的兩行：主管留話（`notes.jsonl` 最新一筆，`line_by: "leader"`）；沒有就用助手觀察（`line_by: "aide:<pack>"`）；都沒有就程式句（`line_by: "program"`，例 `running, 3 members`） |

- **上層的一句話不是下層幾句話的摘要**，是程式挑出最嚴重的那一個照抄它的 `why`。這保住第一輪「上層小助手不彙整下層」：往上只傳事實與數字，不傳改寫過的話。
- 03 §8 的燈號規則（隊長停了底下還在跑＝紅、小助手沒聲音＝紅、全停且 DONE＝灰…）原樣搬來，成為**有孩子的節點的 `self.light`**。
- 葉子的 `self.light` 是這輪新加的（第一輪成員只有狀態字、沒有燈）：

| 葉子的燈 | 條件 |
|---|---|
| 紅 | 停了而且結束碼不是 0／被訊號殺掉，同時它的部門還沒收隊；或 `cooldown.failures ≥ 3`；`external` 健康檢查失敗 |
| 黃 | 第 3 期起：03 §8 的 `looping?`（最近 5 則重複 3 則以上）、忙著但 60 分鐘沒新訊息 |
| 綠 | 在跑 |
| 灰 | 正常結束（code 0）、睡著、或部門已收隊 |

  藍燈只出現在有決策單的節點上（寫單的那個主管）。

### 3.3 三種關係：誰當骨幹

| 關係（01b C） | 在這個設計裡 | 怎麼顯示 |
|---|---|---|
| **歸屬**（宣告、subagent 紀錄、名字前綴） | **骨幹**。優先序照 03 §8：宣告 → subagent 紀錄（含停掉的主管）→ 前綴 | 房間套房間 |
| **daemon 管轄** | **兜底＋最外層**。每個 daemon 是一個節點；歸屬歸不到的 proc 掛在管它的 daemon 下。daemon 是另一個 daemon 的 proc 時，自然就是節點裡的節點 | 最外圈的大框（大樓）；`parent_by: "daemon"` |
| **請求路由**（`AOS_KERNEL`、gate 的 `next`） | **不當骨幹**，當標記 | 節點上的小標記＋可開關的虛線圖層 |

為什麼骨幹選歸屬：

- 公司比喻問的是「這個人是誰的人」，那是歸屬。路由問的是「他的申請單送去哪蓋章」，每封信可以分流、不一定成樹（知識庫 kernel.json：`after_verdict` hook 可以逐封換 `next`）。
- 11-14 的實況路由樹與歸屬樹已經對不上（ok-view、ok-pilot 沒有 `AOS_KERNEL`，起 sol 沒經過頂層 gate）。拿路由當骨幹，這兩條線會從圖上消失或掛錯位置。
- daemon 管轄一定完整（每個 proc 恰好屬於一個 daemon），所以拿來兜底，保證沒有節點沒地方放。

路由怎麼顯示：

- 節點標記 `gate_on`（這個節點自己開了 gate）、`not_behind_gate`（它的歸屬上層開了 gate，但它的請求沒經過）。第二個正是 11-14 那種「對不上」的情況，值得董事長一眼看到。
- 圖層開關「show request routes」：打開才畫虛線（從節點連到它的 kernel）。預設關，免得畫面變蜘蛛網。
- **待查**：一個 proc 的 `AOS_KERNEL` 是什麼、某節點有沒有開 gate，正式介面（`aos-agent ctl state -t NAME all -j` 的 who 部分）給不給。給不了的話，第 0 期這兩個標記顯示 `unknown`、不猜；要不要讓固定程序去讀 stack 裡的 `hooks/kernel_gate/kernel.json`，屬於第 10 節第 7 題。

### 3.4 層數不限：效能與畫面

- **資料**：`state/tree.json` 存成平的一張表（`nodes: {id: node}`＋`root`），不是巢狀 JSON。算彙總是一次由下往上走完，節點數的線性時間；幾百個節點在每分鐘一次的 tick 裡不算什麼。
- **查歸屬**：照 03 §8（每 tick 最多查 30 個跑著的、輪著查；停掉的快取）。多一個 daemon 就多一次 `ctl ls --json`。
- **給網頁**：`/api/state?root=<id>&depth=3` 只回某個節點往下三層；更深的只給 `rollup`。網頁拉近到哪就要到哪。整棵小於 300 個節點時直接整棵給（現在大約 30 個）。
- **畫面**：一個框在螢幕上太小就不畫裡面，只畫一個顏色點與 `+N`（第 5 節）。所以不管幾層，同時畫出來的東西有上限。
- **環**：宣告的 `parent` 繞成圈（A 的 parent 是 B、B 的是 A）時，固定程序切斷較晚出現的那條、兩邊標 `parent_loop`，改用下一個來源。

### 3.5 這題改了第一輪的什麼

| 東西 | 改法 |
|---|---|
| `state/tree.json` | **改**：從「隊伍清單＋成員」變成 `{"schema":"view-tree/2","rev":N,"generated_at":…,"tree_down_since":…,"root":"company","nodes":{…}}`，節點如 3.1。`state/teams/<隊>.json` 留著放部門的細節（最近幾封信、事實表） |
| 新增 `state/layout.json` | 每個父節點底下的座位表（`slot`），固定程序維護 |
| `report` 信 | **欄位不加不減**。只放寬兩個意思：`parent` 可以是任何節點 id（不限「隊」）；`facts.members[]` 仍只列直屬的孩子 |
| `aide.json` | 加選填 `tags` |
| `view_note` | 加選填 `--on <節點名>`（第 4 節），寫進 `notes.jsonl` 那一筆的 `on` 欄位 |
| `/api/state` | 加 `root`、`depth` 參數與 `rev`；另加 `/api/node/<id>`（一個節點的細節） |
| 燈號 | 規則不改；多了葉子的燈與 `rollup` |

## 4. 部門之間怎麼協調

**定案：這頁只呈現，不做協調。** 董事長不該變成各部門的調度台（那是頂層 agent 與各主管的工作），而且任何「在網頁上調度」的按鈕都會碰到第一輪第 3 題（自由下指令）的同一個風險。

能從現成東西呈現的，呈現三樣：

| 呈現什麼 | 資料從哪來 | 畫成什麼 |
|---|---|---|
| 誰 claim 著哪些檔、多久了 | `wf/tools/commit-request claims`（現成指令，唯讀）。**待查**：有沒有 JSON 輸出；沒有就解析它的文字 | 部門上的標記 `claim 3 files, 95m`；超過 config 門檻（預設 120 分鐘）變黃字，不改燈 |
| 誰在等誰 | 主管卡住時 `view_note blocked '一句' --on <對方>`（`--on` 是這輪加的選填欄位）。沒寫 `--on` 就只是 `BLOCKED`，照第一輪亮黃 | 兩個房間之間一條虛線箭頭「waiting on」；被等的那邊也看得到有人在等它 |
| 一張決策單幾個部門都在等 | 專區現成的 `dedupe_key`（`aos-user ls --json`） | 決策卡上列出所有在等的部門；地圖上每個都有藍圖釘 |

不做、也不新增的：

- 不提供「幫 A 釋放 B 的 claim」「叫 A 讓 B 先」這類按鈕。
- gate 手上保留的請求數：資料在宿主 stack 的 `hooks/kernel_gate/`，沒有給外人的正式介面（`kernel_gate ls` 是宿主自己的工具）。先不顯示，跟第 10 節第 7 題一起看。
- 信件的 `in_reply_to` 鏈：中轉信箱裡只有寄給 view 的信，部門之間直接寄的信 view 看不到（信讀了預設就刪）。所以「誰欠誰一封回信」現在算不出來，不做；`--on` 是它的替代。

## 5. 空間介面

### 5.1 2D，不做 3D（定案）

| | 2D（平面圖） | 3D |
|---|---|---|
| 手機操作 | 捏合、拖、點，人人會 | 要轉視角，單手難用；點小東西容易點錯 |
| 白話呈現 | 字是平的、永遠正對你 | 字會斜、會被擋住；要另做「永遠朝向鏡頭」的標籤 |
| 施工難度 | 幾百行純 JS | 要相機、光、拾取、標籤層 |
| 依賴 | 零（瀏覽器內建 SVG） | 本機沒有 three.js，要 vendored 一份（約 600KB 以上）；artifact 不能從網路載，得整包塞進單一檔 |
| 嵌套 | 框裡有框，直覺 | 要想「下一層在哪」：樓層？抽屜？ |
| 多得到什麼 | — | 好看；資訊量沒有變多 |

使用者原話是「3d/2d空間的縮放移動」，兩種都在他說的範圍內；user.md 的頁面風格（白話、只講結論、手機 ELI5、artifact 承載力有限）與現有前端零依賴的前例都指向 2D。所以我直接定 2D，不列成問題。節點格式跟畫法無關，之後真想要 3D，是換一層皮，資料與後端不動。

### 5.2 技術

- **零依賴的 SVG**，跟現有看板與專區網頁同一個做法（純 JS、標準庫伺服器）。不 vendored 任何函式庫。
- 為什麼 SVG 不是 Canvas：節點數是幾十到幾百，SVG 夠快；字是真的字（可選取、可放大不糊、CSS 管樣式）；每個框本來就是可以點的元素，不用自己算點到誰。上千個節點同時在畫面上才需要 Canvas，而 5.3 的規則保證不會發生。
- 縮放與移動：一個 `<g transform>`，自己處理 pointer 事件（滑鼠滾輪、拖曳、雙指捏合），大約一百多行。
- **排版**：每個房間裡用固定格子排孩子，孩子照 `slot` 入座。`slot` 由固定程序發、寫在 `state/layout.json`：新來的坐最後一個空位；離開的座位留空 24 小時才回收。**同一個部門永遠在同一個位置**——空間記憶是使用者要這個介面的原因，位置每 5 秒跳一次就白做了。房間大小照「後代節點數」分級（小、中、大三級），不是連續值，同樣為了不亂跳。
- **artifact**：`aos-view export` 產出單一 HTML（JS 內嵌、資料內嵌成一份快照），同一份地圖程式照用。因為零依賴，CSP 擋外連不影響；只是資料是快照（第一輪第 2 題的限制不變）。

### 5.3 語意縮放：看「這個框在螢幕上多大」

不看全域縮放倍率，看每個框自己在螢幕上的寬度。這一條規則對每一層都一樣，所以嵌幾層都通：

| 框在螢幕上的寬度 | 畫什麼 |
|---|---|
| 小於 24px | 只有一個顏色點（部門用 `rollup.worst`，葉子用 `self.light`） |
| 24～120px | 顏色＋名字；部門加 `+N` |
| 120～360px | 名字、燈、**一句話**、數字籤（`2 red` `1 ask` `5 running`）；孩子畫成小點 |
| 大於 360px | 上面那些縮到框頂變標題列；框內把每個孩子**用同一張表**畫出來 |
| 葉子大於 360px | 變成 bot 卡（第 6 節）或設備卡（第 7 節） |

- 拉高：只看到幾個部門的顏色與一句話。拉近一個部門：它的標題列留著，裡面的員工從點變成有名字、有狀態的桌子。再拉近一張桌子：變成那個員工的卡。
- 畫面外的、小於 8px 的一律不產生元素。
- 模型寫的字與程式抄的字照第一輪用不同底色，縮放不改這條。

### 5.5 即時更新

- 沿用第一輪：前端每 5 秒問 `/api/state`。加一個 `rev`（樹有變才加一），前端帶上次的 `rev`，沒變伺服器回 304、不重畫。
- 有變時照節點 id 比對，只改變了的框；燈變色做一下閃動，讓人注意到。位置由 `slot` 決定，不會動。
- 不做 WebSocket／SSE：資料本身一分鐘才算一次（tick），5 秒輪詢已經比資料新；多一條長連線只多出要處理的斷線狀況。
- 拉近到某個節點看細節時，另外每 5 秒問 `/api/node/<id>`；離開就停。
- 頁首照第一輪顯示 `last tick`，超過 3 分鐘出橫幅。

### 5.6 手機

- 手勢：雙指捏合縮放、單指拖、**點一個框＝飛到那個框剛好佔滿螢幕**。最後這個是主力——點一下進一層，等於一般的「點進去」，不用會捏。
- 頁首一條路徑 `company › repo-aos › ok-kf`，點前面任一段就退回那一層；另有一顆「回最高」。
- 手機直式時房間改成直排（同一張座位表，欄數從 4 變 1～2），字級不隨縮放變小到看不見（低於門檻就換成上一級的畫法）。
- 第一輪的清單版留著當第二個檢視（頁首切換 `map`／`list`）：螢幕閱讀、很窄的螢幕、或地圖出錯時的退路；也是 0a 期先交的東西。手機預設開地圖，只顯示有事的（紅、黃、藍）加一行「其他 N 個正常」的規則，在清單版照舊。

### 5.7 決策卡放哪（不能被縮放藏起來）

- **決策卡不屬於地圖**。它在地圖之上的固定層：桌機是右側一欄，手機是底部一條可往上拉的抽屜。縮放、拖動都不影響它。
- 頁首三個大數字（要你決定、可能卡住、在跑）也是固定層，永遠在。
- 地圖上，寫單的那個節點有一個**藍色圖釘，畫成固定的螢幕大小**（不隨縮放變小）。節點小到看不見時，圖釘往上掛到看得見的那個祖先上，寫 `2`。所以拉到最高也看得到「哪一區在等我」。
- 卡片上一顆 `locate`：飛到寫單的部門。點圖釘：打開抽屜、捲到那張卡。
- 紅燈同理有紅圖釘（走 `worst_path`）。黃燈不給圖釘，免得滿圖都是。
- 答題的後端完全照 03 §8（`aos-user answer`，授權只在專區產生），這輪不動。

## 6. 員工層（bot 模型）——可選後期

使用者說這層「比較麻煩，未必一定要做」，所以排在第 5 期、可以不做；前面各期不依賴它。但節點格式已經留好位置，做的時候只是葉子拉近後多一張卡。

### 6.1 三頁各從哪讀

| 頁 | 內容 | 來源（先只走正式介面） |
|---|---|---|
| **Now** 現在的狀態 | `activity`、排隊幾封、跑多久、記憶體與 CPU、最後一則訊息多久前 | `aos-agent ctl state -t NAME all -j`（一次拿 state、mailbox、resources…）。01b A：這是正式介面，不必翻 stack |
| **Did** 做了什麼 | 最近用過的工具（名字、成不成功），一行一筆 | `aos-agent history -t NAME ls -j`：fsm 的 history 有 `tool_calls`；**eca 的 history 沒有工具呼叫**（01b A） |
| **Said** 說了什麼 | 收到的話、它每輪最後的回答、寄出的信（fsm：history 裡的 `mailbox_send`），每則最多 200 字 | 同上 `history ls -j` |

「腦在想什麼」（`think/request.json`、eca 的 `live.jsonl`）**不做**：那是整段對話原文，最容易帶秘密，而且使用者要的三樣裡沒有它。

### 6.2 fsm 與 eca 怎麼抹平

卡片只認一個共同格式，後端各自轉：

```json
{"schema":"view-bot/1","id":"ok-kf-sol-1","body":"fsm",
 "now":{"activity":"acting","state":"running","queued":1,"up_s":2520,"mem_bytes":3145728,
        "last_message_age_s":120,"coverage":"full"},
 "did":{"items":[{"tool":"look","ok":true,"ms":41,"at":null}],"coverage":"partial","source":"history"},
 "said":{"items":[{"dir":"in","from":"ok-kf","text":"…","at":"…"},
                  {"dir":"answer","text":"…","at":"…"}],"coverage":"full","source":"history"}}
```

| 欄位 | fsm | eca |
|---|---|---|
| `activity` | `stage.txt` 的四格直接對：`idle` `thinking` `waiting` `acting`（從 `ctl state` 拿；**待查**它有沒有帶 stage） | 只分得出 `working`（跑著而且 busy）與 `idle`（跑著不忙）；分不出在想還是在用工具，就不裝懂 |
| 停、睡 | 兩邊一樣：`stopped`（附 code、reason）、`sleeping` | |
| `did` | 工具名、成敗；沒有逐筆時間就 `at: null` | `coverage: "none"`，卡上寫 `not recorded for this kind of agent` |
| `said` | 收到、回答、寄出的信 | 只有 queue 訊息與每輪最後回答（`coverage: "partial"`） |

每頁都帶 `coverage`（`full`／`partial`／`none`）與 `source`。**看不到的就寫看不到**，不拿別的東西湊；這跟第一輪「模型寫的字與程式抄的事實分開標」同一個精神。

### 6.3 「改了哪些檔」「commit 歸屬」

**定案：不補帳，不新造紀錄。** 使用者說「資料先用現成的」。現成的東西能回答到**部門**這一層，回答不到員工：

| 要看的 | 部門層（做） | 員工層 |
|---|---|---|
| commit 了什麼 | `git log` 找訊息 trailer 裡線名等於這個部門的 commit（`commit-request` 的訊息檔 trailer 有線名，01b A），列今天的 hash 與標題。唯讀、不碰任何 stack。**待查**：trailer 的確切鍵名 | `unknown`。commit 是整條線交的，本來就不歸某一隻 |
| 改了哪些檔 | 上面那些 commit 的檔名（`git log --name-only`）＝已交的；`commit-request claims`＝正在改的 | fsm：history 裡 Write／Edit 類工具的 `file_path` 可以抽，標 `partial`；Bash 改的沒有紀錄。eca：`unknown` |

這樣放在部門卡上是一小段「today: 3 commits, 12 files · working on 3 files」。它出現在第 1 期（跟 claim 標記一起），不必等員工層。

如果之後使用者真的要「每個員工改了哪些檔」，那是替 aos 加一本新帳（例如工具層記 `file_path`），屬於 aos 本體的新功能，不在這條線的範圍，到時另開。

### 6.4 秘密與隱私

- **只在使用者打開那張卡時才讀**（`/api/node/<id>/bot`），結果在記憶體裡留 30 秒，**不寫進 `state/`、不進 `done/`、不進 `export`**。所以 history 的內容不會多一份副本，也不會跟著快照離開這台機器。
- 只顯示：工具**名字**與成敗、每則訊息前 200 字（`history ls` 本來就截好的）。不顯示工具參數、不顯示工具回傳、不提供「看全文」。要全文，卡上給一行可複製的 `aos-agent history -t NAME ls -l`，使用者自己在終端機看。
- 200 字預覽照 03 §8 的規則遮 key（明確前綴與 `*KEY=` 類賦值）。
- 網頁本來就只綁本機、要 token；這層沒有新增誰看得到。

### 6.5 這算不算「碰別人的 stack」、誰來讀

- **走正式介面不算**。`aos-agent ctl state`、`aos-agent history` 是 aos 給的看別人狀態的指令（01 D：不會讓對方多想一輪），第一輪的小助手 hook 已經在用。
- **由固定程序讀，不由小助手讀**。員工層是使用者臨時想看才看，交給小助手等於每 5 分鐘替每個員工多蒐一份、還要塞進信裡；固定程序在使用者點開時讀一次就好，也不花模型。
- **直接讀 stack 裡的檔**（`observed.jsonl`、eca 的 `claude/live.jsonl`、`stage.txt`）能補上 eca 的 Did 與更細的時間，但那就是知識庫規則 1 說的別人的 stack。`aos-view` 不是 agent、是使用者自己的工具，規則 1 的字面管不到它；可是 01 D 也記著「不該直接讀」。**這是原則的邊界，不替使用者定**：第 5 期先做只走正式介面的 5a，要不要有 5b（白名單唯讀）列第 10 節第 7 題。

## 7. 普通 proc（第二優先）

**同一個外殼**：也是節點，也是拉近變一張卡，卡只有兩頁（沒有 Said）。

| 頁 | 內容 | 來源 |
|---|---|---|
| **Now** | phase、pid、跑多久、結束碼／訊號、`reason`（stderr 最後一行）、記憶體／CPU／程序數、限制值、`auto_restart` | daemon 表（`aos-agent ctl ls --json` 的那一列；第 0 期就有）＋`aos-agent ctl state -t NAME`（用量，01b B）。**待查**：`ctl state` 對不是 agent 的列給不給用量 |
| **Did**（有的才有） | llm kernel：今天各 pack 用了幾次／上限多少、排隊幾封、哪個部門用最多；clock：現在第幾個 cycle、登記了幾項 | llm kernel 的 `used.json`、`queue.json`；clock 的 `clock_register.json`。這些在各自的 stack 裡，**待查**有沒有正式介面讀；沒有就跟第 10 節第 7 題一起走 |

- 沒有重起次數（01b B：沒有公開欄位），卡上不放這一格，不拿 `cooldown.failures` 冒充。
- 放哪：歸屬歸不到的 proc 掛在它的 daemon 節點下。畫面上每個 daemon 框裡，agent 部門排前面，其餘 proc 收在一個 `machine` 小區（程式依 `kind` 分的，不是部門劃分）。
- `llm-gpt` 自己是一個 daemon → 它是公司底下另一個大框，裡面是它的 `llm_<id>`（單次腦工作，來來去去，只顯示數量不逐個畫）。這就是「kernel 底下掛 kernel」在畫面上的樣子。要看哪幾個 daemon 寫在 `config.json` 的 `daemons`（預設主樹一個）。
- **llm kernel 的用量是部門彙總的好材料**（「這個部門今天花了多少」）：`used.json` 有分 sender。排第 2 期，接得上就在部門的數字籤加一個 `calls today`。

**LiteLLM 不在 daemon 表上**：

- 用 `kind: "external"` 的節點表示「aos 沒在管、但大家靠它」的服務。清單寫在 `config.json`：

```json
{"externals":[{"name":"litellm","check":{"type":"http","url":"http://127.0.0.1:4000/v1/models","timeout_ms":2000}}]}
```

- 固定程序每個 tick 打一次健康檢查：通＝綠、不通＝紅（`why: "no answer on :4000"`）。卡上寫 `not managed by aos` 與回應時間；不去 `/proc` 找它的 pid、不顯示它的環境變數。
- 順帶把第一輪記的旁支顯示出來：它聽在 `0.0.0.0`，卡上一行 `listens on all interfaces`（**待查**：用 `ss` 讀得到，要不要每個 tick 都查）。
- external 節點掛在根底下的 `machine` 區。以後有別的表外服務（本機模型伺服器之類）加一行設定就出現。

原則不變：每期做完能單獨停下來用；第 0 期不用模型、不改活樹（裝進 `ws/tools` 與啟用 systemd 那一步仍要點頭，照 03）。

## 10. 要問使用者的

### 第一輪的 5 題

**第 2 題（更新）：出門時要用手機看到什麼程度？**
白話：這台機器現在沒有對外的通道，手機只能看 claude.ai 上那一頁，而且要 Claude 手動幫您更新。這輪多了地圖，它在那一頁上照樣能縮放、能點進去，只是看到的是「上次更新那一刻」的樣子。

### 新增的 2 題

**第 6 題：部門讓它自己長出來，還是您要自己劃？**
白話：現在每條線（一個隊長帶幾個員工）自然就是一個部門，不用誰去分。您說的「分部門」如果是這個意思，什麼都不用做；如果您心裡有另一種分法（例如 kernel 部、工具部、外部專案部），那要有一張您定的分類表。
- a（推薦）：照樹自己長。部門＝隊伍；想按性質看就用標籤上色、篩選。後果：今天就能用，分法跟著實際的隊形走；畫面上不會有「kernel 部」這種大框，除非真的有一個節點帶著那幾條線。
- b：您給一張分法（幾個大部門、哪些線歸哪個）。後果：畫面照您的心裡地圖排；每開一條新線要多填一格歸哪個部門，沒填的掉進 `unassigned`。
- 為什麼要問：公司比喻是您的點子，「部門」指什麼只有您知道。我照 user/03「不要太早劃定」先設計成 a，而且 a 的資料不用改就能走到 b。

**第 7 題：全景頁的程式可以唯讀翻 agent 的 stack 嗎？**
白話：aos 的規矩是「不碰別人的 stack」，要看別人走正式指令。正式指令看得到大部分，但有幾樣看不到：Claude 那種 agent 用過哪些工具、頂層手上壓著幾封請求、llm kernel 今天各部門花了多少。這些檔就在 stack 裡，程式讀得到，只是沒有正式的門。
- a（推薦）：只走正式指令。看不到的地方頁面寫 `not recorded`／`unknown`。後果：規矩一條都不用動；Claude 型員工的「做了什麼」是空的，gate 保留數與 llm 用量先不顯示（若查到有正式指令就照常顯示）。
- b：准許全景頁的程式照一張白名單唯讀（只讀、不寫、名單寫在設定檔裡，例如 `observed.jsonl`、`claude/live.jsonl` 只取工具名、`hooks/kernel_gate/hold.json`、llm kernel 的 `used.json`）。後果：那幾樣都看得到；等於承認「使用者自己的工具」不受那條規矩限制，之後別的工具會拿這個當前例；`live.jsonl` 裡有完整對話，程式只取工具名，但讀的那一刻內容進了程式的記憶體。
- c：缺的那幾樣替 aos 補正式指令（例如 `aos-agent observed -t NAME`）。後果：最乾淨；是 aos 本體的新工作，要另開一條線。
- 為什麼要問：這是既有原則（知識庫規則 1、01 D「不該直接讀」）跟新需求（員工層要看 eca 做了什麼）的衝突，照 user/03 只有這種要帶給您。它只影響第 5b 期與最後一期的幾個數字，不擋前面任何一期。
