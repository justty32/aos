## 1. 記什麼

### history 列

只加一個鍵 `aos`，值是物件。原始碼目前沒有任何 history 列用到 `aos` 這個鍵（11-14 grep 過）。mailbox 的 `in_reply_to` 不改，也不借用這個名字。

- **信的 user 列**：`"aos":{"letter":"<信名>"}`
  - 寫的人：fsm 的 `idle.take()`（`templates/agent-fsm/idle.py:166-167`）；eca 的 `Handoff.handed()` 和 `extra()`（`cmd/aos-eca/aos_eca/handoff.py:23-24、39`）。
  - 時機：先加進 `letters.json` 的 `pending`，再附加 history，最後 `done`（施工時定，見下表）。
  - 寫入時**覆蓋**信 body 原本的 `aos` 鍵，免得寄信的人偽造。eca 會保留 body 裡除了 `name` 以外的鍵。
- **最終回答列**：`"aos":{"answer_to":["<信名>",…]}`
  - 最終回答＝assistant、沒有 `tool_calls`。
  - 值是清單：一則回答可能同時回好幾封信。
  - 沒信可回時不加這個鍵。
  - fsm 附加端點回覆之前，先把回覆裡原本的 `aos` 拿掉，再寫我們的。

### `<stack>/letters.json`（新持久檔）

格式：`{"pending":[信名…],"dropped":[{"letter","reason","at"}…]}`

- 寫法：先寫點開頭的暫存檔 `.letters.json.<pid>.tmp`，再 `os.replace`（點開頭的 stack.gitignore 擋得到）。
- `dropped` 只留最近 50 筆。
- `reason` 只有三種：
  - `bad`：壞信
  - `blocked`：被 before_queue hook 擋掉
  - `failed`：交給 CLI 之後失敗

**誰改它、什麼時候改：**

| 時機 | fsm | eca |
|---|---|---|
| 收到好信 | `idle.take()`：先加進 `pending`，再附加 history，最後 `done` | `handed()`、`extra()`：同左 |
| 丟掉壞信或被擋的信 | `done` 之前記進 `dropped` | 同左（`turn.py:50`、`midturn.py`、`hook.py:24`） |
| 寫最終回答 | `wait.py`：`answer_to = pending`，附加 history 之後清空整份 `pending` | `turn.py:84`：`answer_to = hand.good`，附加 history 之後只從 `pending` 拿掉這幾封（別輪留下的不順手清）；slash 回答照樣處理，`slash_turn` 在 `turn.py:84` 之前 return，不重複 |
| 交出去之後失敗 | brain 失敗後會重試，`pending` 不動。下一則最終回答把它們一起算進去，這是有意的：模型看得到那些信 | `CliFailed`／`ReplyMissing`：把這輪已收掉（離開 queue）的信從 `pending` 移到 `dropped`，`reason` 記 `failed`；還在 `cur/` 的下一輪重交，重交時 `letters_take` 會把它從 `dropped` 拿掉 |

**為什麼要這個檔**（Argon A6、A7）：

- 從 history 現算會出錯：本輪的 user 列可能被 do_task 折疊、summarize 或 self_history 改掉；上一則最終回答被刪掉時，已經答過的信又會被算進來。
- `pending` 不管 history 怎麼改，都只會記到「還沒被最終回答蓋到」的信。
- 有 `dropped`，被丟的信可以立刻報錯，不用乾等到逾時，也不會像 `mailbox_warning.txt` 那樣只留最後一封。

## 2. 讀的一方

回傳 `(狀態, 文字或原因)`。**查的順序固定，照信件流動的方向，從上游往下游查**（Argon A1、A2）：

2. `history.jsonl`：
   - 有最終回答的 `answer_to` 含它 → `answered`，取第一則。
   - 有 user 列的 `aos.letter` 是它 → 記一筆「已交出」，往下查。
3. `history_removed.jsonl`（路徑照 interfaces 宣告）：

## 5. 換樹與落地順序（v3：使用者 11-14 14:22 答 land: one）

**讀寫同一個 commit，換樹當晚一起上。** 原本推薦分兩次，使用者選一次。他知道的後果是：那晚沒跟著換的 agent（還開著的舊畫面）可能配不到回答，退路比較少。

### 一個 commit 帶哪些檔

- 寫的一方：
  - `templates/agent-fsm/`：`idle.py`、`wait.py`、`brain.py`、`cell_common.py`
  - `cmd/aos-eca/aos_eca/`：`handoff.py`、`turn.py`、`slash.py`、`midturn.py`、`common.py`
- 讀的一方：
  - `py/aos_ws.py`
  - `cmd/aos-agent/aos_agent/`：`listen.py`、`ask.py`、`chat.py`
  - `lib/agent/subagent/_entry` 和它的說明
- §4 列的測試和文件

### 生效時間不一致

同一個 commit 裡的檔，不是同一刻生效：

- `cmd/`、`py/` 一進 main，活樹就跟著用（ok-kf 11-14）。這包括 eca 的寫的一方，以及 aos-agent 和 aos_ws 的讀的一方。
- `templates/agent-fsm/`、`lib/` 要等換樹第 5 步。

所以 **submit 排在換樹當晚，換樹前最後一個 commit**，把「新讀舊寫」的空窗壓到最短。逐檔的生效方式，交件時寫明。

### 退路：舊身體被問到時不會壞

一次上之後，還沒重起的 agent（舊身體）不會寫 `aos.letter`、`answer_to` 和 `letters.json`。讀的一方遇到它時，必須退回現行配法，不能卡死，也不能報假錯。分兩次時準備的東西，保留下面這些：

- **保留：發信前快照退路**（原 Argon 創見 3、A11）。
  - 條件：`ask` 等到信已經離開 queue，`answer_for` 還是 `unknown`，而且 `history[before_rows:]` 裡有不帶 `aos` 的一般 user 列（不是 `[aos] ` 開頭的）。
  - 判定：收這封信的是舊身體。
  - 做法：改走現行的「等最新那則」，條件是 `handed_unanswered` 為假，而且回答數大於 `before_answers`。stderr 印一句：「<agent> 的身體還沒升級（沒有 aos.letter），這次照舊配法：拿的是最新那則回答，不保證是回這封信」。
  - `chat` 同樣照此辦理。
- **保留：`listen` 不給信名時的現行規則**（§2，A13 的第三種情況），舊身體走的就是這條。
- **新增：不給假的 `LetterDropped`。** 只有 `letters.json` 的 `dropped` 裡有這封信，才報 `LetterDropped`。舊身體沒有這個檔，最壞就是走退路或逾時報 `AnswerMissing`，訊息裡加「可能是身體還沒升級」。
- **subagent op ask**：`lib/` 要等換樹。換樹前它還是舊的 say＋listen，listen 不帶信名，走現行規則，行為跟今天一樣。
- **不做的事**：
  - 不搬遷舊 history，不留舊格式相容。
  - 寫的一方不判斷讀的一方的版本。多一個鍵，舊讀者照樣能用（sol-8 §2）。

### head-tools 11-14 補的兩點

1. **對上 ok-kf 的 pin。** ok-kf 在收件截止時刻釘下 main 的 HEAD，再在乾淨複本預演全套。今晚的例子是 16:00 收件、16:45 換樹。
   - 這個 commit 必須在那次換樹的收件截止前進 main，並且排在最後一個。日期一定下來，就先跟 ok-kf 講好。
   - 從進 main 到換樹之間，`cmd/`、`py/` 已經是新的，`templates/`、`lib/` 還是舊的，今晚的例子是 45 分鐘以上。這段空窗裡，活樹每隻 agent 都是「新讀舊寫」。
   - 所以快照退路**每次換樹都會走到，是主路，不是邊角**。測試要當主路來測：多隻 agent，fsm 和 eca 都要，`ask`、`chat`、`listen`、subagent op ask 各測一次。
2. **新 eca 寫、舊 lib 讀。** `cmd/aos-eca` 一進 main 就生效，活樹的 `lib/`（subagent 的 `_entry` 等）還是舊的。這個組合也要放進測試矩陣：用舊版 `_entry` 和舊版 `listen` 的邏輯，讀帶 `aos` 鍵的 history 和 `letters.json`，結果要跟今天一樣。

### 給頂層的換樹當晚清單

1. **submit 時機**：換樹第 1 步之前，作為最後一個 commit。head-tools 放行後才 submit。
2. **要重起的 agent**：
   - **fsm 身體**：每隻都要重起，或者確認它的 cell 是每輪重新載入範本檔。重新載入的話，換樹第 5 步之後的下一輪就生效。施工時核實，結果寫進交件。
   - **eca（claude／codex）**：aos-eca-turn 每輪是新行程，所以不用重起。開著的畫面要看它是不是自己有一份長駐的行程。施工時核 `cli_ask`、`print_claude` 的路徑，寫明哪種畫面要關掉重開。
   - **subagent 工具**：在 `lib/`，隨換樹生效，不用另外處理。
3. **怎麼驗**（暫存樹、乾淨環境，不碰活 daemon，除非頂層的換樹程序本來就有那一步）：
   - **新身體**：在換好的樹上，對一隻 fsm 和一隻 eca 各做一次 `aos-agent ask`。要拿到自己那封信的回答；history 的 user 列有 `aos.letter`；最終回答有 `aos.answer_to`；stack 裡有 `letters.json`，而且 `pending` 清空了。
   - **兩人同問**：兩個 `ask` 同時問同一隻，各拿各的。
   - **舊身體**：用換樹前的身體跑一次，要走退路，stderr 有「身體還沒升級」那句，不能卡住。
   - **活樹 agent**：看每隻收過信之後，stack 裡有沒有 `letters.json`。沒有的就是還沒升級，列給使用者決定要不要重起。這一步只看檔在不在，不讀內容。
