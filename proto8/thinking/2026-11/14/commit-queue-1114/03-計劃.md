## 跟 fable 稿不同的地方

1. 快取放 `~/.cache/aos-commit-queue/<repo 路徑 sha1 前 10 碼>/`（測試用 clone 與真 repo 分開，鎖也分開）；可 `--cache` 指定。
2. `month_bump` 份數＝摘要段是新的才加一（A5）。
3. `log_upsert` 的鍵不另造格式：`key` 是該行開頭的一段原字（例 `- **open｜commit 排隊`），以「行首等於 key」認行；認到 0 行加在段尾、1 行換掉、2 行以上 BLOCKED。`text` 是整行。
4. `day_upsert` 鍵＝`| [名](連結) |` 那段；給 `name`、`link`、`summary`。日索引在 HEAD 還不存在（新的一天）時，允許它出現在 `files`（新檔照一般檔走）。
5. `rm` 的檔要申請者自己先在工作樹刪掉；排隊不替人刪檔（「不刪檔」）。工作樹還在就拒絕。
6. 符號連結照 git 的方式收（mode 120000、內容＝連結目標），不拒絕。
7. 回信：結果同步印在申請者 Bash（最後一行 JSON）；`--notify <aos 名>` 第一版不做，列為之後可加。
8. pre-commit 護欄第一版不裝（會擋到頂層手動 commit；要裝由頂層或使用者決定），只寫在紀錄裡當選項。

## 指令

```
commit-request submit --line L [--files F…] [--rm F…] --msg-file M [--op JSON]… [--ops-file J] [--dry-run] [--keep-claim] [--repo R] [--cache C] [--wait S]
commit-request claim   --line L F…
commit-request release --line L F… | --line L --all | --force F…
commit-request claims
commit-request doctor [--repair]
```

結果：stdout 最後一行 JSON `{"status": "DONE|BLOCKED|FAILED", "code": "...", "commit": "<hash>", "files": [...], "generated": [...], "warnings": [...], "hint": "..."}`。exit：0 DONE、1 內部錯誤、2 BLOCKED、3 申請不合格、4 生成器失敗、5 忙碌、6 repo 狀態異常。

## 處理流程（持鎖，fcntl.flock，等 `--wait` 秒，預設 120）

1. 有 `journal.json` → 先照它補步驟 10、11，刪日誌。
2. repo 狀態：`HEAD` 是 `refs/heads/main` 的符號參照；沒有 `MERGE_HEAD`／`rebase-*`／`CHERRY_PICK_HEAD`。記 `OLD`。
3. 驗申請：路徑正規化、在 repo 內、不是資料夾、`git check-ignore` 不中；`files` 每檔存在且 blob ≠ HEAD 的（新檔算有改）；`rm` 每檔在 HEAD 有、工作樹已不在；三份共用檔（日索引已存在時）與生成物不在 `files`；訊息檔非空；claim 規則（下節）。
4. 快取樹對齊 `OLD`：`read-tree --reset -u OLD`，再 `clean -fdq`（只在快取樹）。
5. 清單檔從共用工作樹讀位元組（`hash-object -w`），寫進快取樹與快取 index（`update-index --add --cacheinfo mode,blob,path`）；`rm` 的 `--force-remove` 並刪快取樹那份。
6. 在快取樹的三份共用檔上套 ops，`update-index --add`。
7. 跑 `index_gen.py --root <快取樹> --apply`（用快取樹裡那支，＝HEAD＋本次的版本）；rc≠0 → FAILED exit 4，stderr 原文附上。`status --porcelain` 找出變動：只收生成物白名單；白名單外的變動 → FAILED。生成物 `update-index --add`（被刪的 `--force-remove`）。
8. `write-tree` → `commit-tree -p OLD -F M` → `NEW`。`--dry-run` 到這裡就印 `diff --stat OLD NEW` 結束，不推。
9. 寫 `journal.json`（OLD、NEW、這次的路徑），`update-ref -m "commit-queue <L>" refs/heads/main NEW OLD`；CAS 失敗 → 回步驟 2，最多 3 次。
10. 共用 `.git/index`：這次 commit 的每條路徑 `update-index --cacheinfo`（新 blob）或 `--force-remove`；遇 `index.lock` 重試 10 秒，不行就 DONE＋警告、日誌留著。原本該路徑在共用 index 有別人 staged 的別的版本 → 警告。
11. 共用工作樹：清單檔不動；生成物寫成 NEW 版；三份共用檔若工作樹那份＝OLD blob → 寫 NEW 版，否則在工作樹那份上重套同樣的 ops（冪等），套不上只警告。寫檔一律先寫暫存再改名。
12. 刪日誌，`log.jsonl` 加一行，放掉這次 commit 的檔的 claim（除非 `--keep-claim`），印結果。

## 操作語意（全部冪等）

- `{"op": "day_upsert", "date": "2026-11-14", "name": "x", "link": "x.md", "summary": "…"}` → `proto8/thinking/2026-11/14/README.md` 的表；以 `| [name](link) |` 開頭認列，有就換、沒有加在表最後一列之後。
- `{"op": "month_bump", "date": "2026-11-14", "segment": "…"}` → `proto8/thinking/2026-11/README.md` 那天的列；摘要已含這段（字串包含）就不動；否則份數加一、摘要尾加「；segment」；那天沒有列就照日期插入，份數 1。
- `{"op": "log_upsert", "key": "- **open｜主題", "text": "- **open｜主題**：…"}` → `wf/SESSION-LOG.md` 的「## 最新進度」段。
- `{"op": "log_delete", "key": "- **open｜主題"}` → 刪那一行；找不到只警告；2 行以上 BLOCKED。

## 衝突規則

- `claim` 紀錄在快取夾的 `claims.json`（同一把鎖）。被別條線 claim 著的檔：`claim` 失敗、`submit` BLOCKED（exit 2），回 holder 與時間與「寄信給那條線協調，或等它交出」。
- 沒 claim 的檔照樣放行，結果裡警告「未 claim」（第一階段）；`--strict` 之後再開。
- submit 時也查：清單檔沒改動 → BLOCKED。

## 測試（`~/code/cq-1114`，clone 出來的 repo，不碰真 repo）

- T1 兩條線同時申請：兩個行程同時 submit 不同檔，兩個都 DONE、main 前進兩格、各自只含自己的檔。
- T2 共用 index 有別人 staged 的檔：submit 後那個 staged 檔仍在共用 index、沒進 commit。
- T3 索引列合併：兩條線各帶 day_upsert／month_bump／log_upsert，先後 commit；HEAD 兩列都在；工作樹另有人手加一列沒 commit，commit 後工作樹那列還在、HEAD 沒有。
- T4 衝突擋下：A claim 檔 X，B submit X → BLOCKED exit 2，main 不動。
- T5 新檔沒一句話 → FAILED exit 4，main 與共用樹不動。
- T6 CAS：處理中途（測試鉤子）有人手動 commit → 重做後 DONE，兩個 commit 都在。
- T7 update-ref 之後被殺（測試鉤子）→ 下一次呼叫補回共用 index、工作樹。
- T8 生成物：新增 `wf/tools/` 底下的檔，commit 帶著 `wf/tools/_index.json`；別人工作樹裡沒交的新檔頭不進這次的生成物。

## 啟用

2. 07「頂層也當 kernel」那條下加申請者用法。
