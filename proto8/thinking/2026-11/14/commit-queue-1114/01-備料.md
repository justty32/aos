## 問題

家機的 aos 樹（`~/aos-home`）裡，頂層 `repo-aos`（Claude Code eca，工作區 `~/repo/aos`）底下掛了六隻 opus／fable eca：ok-kf、ok-astra、ok-limits、ok-misc、ok-skyrim、ok-pilot（工作區 `~/repo/aos/wf/temp/<名>`，已 gitignore），另有小廝 xiaosi（sonnet）。它們做完一段，都在**同一個工作樹 `~/repo/aos` 的 main 上直接 commit**。已發生：

1. 一條線 commit 時把別條線還沒 commit 的日索引列、SESSION-LOG 列一起帶進去（例：`9e9d3a952` 說明「日索引那列與 SESSION-LOG 第 30 列已隨 68ee51c7b 進 main（線星 commit 時一起帶進去）」）。
2. 有人 `git add` 了沒 commit，留在共用的 `.git/index` 裡；別人下一個 `git commit`（不帶 pathspec）就會帶走。
3. 大家都改同一批共用檔：
   - 日索引 `proto8/thinking/2026-11/14/README.md`：一張表，每份一列「| [名](連結) | 一句話 |」，追加在表尾。
   - 月索引 `proto8/thinking/2026-11/README.md`：一天一列「| [2026-11-14](14/README.md) | 份數 | 分號串起的摘要 |」——**不是追加一列**，是改既有那一列：份數加一、摘要尾端加一段。
   - `wf/SESSION-LOG.md`：「## 最新進度」下一行一條 `- **open｜主題**：…`；各線通常是**改既有那一行**或加一行，完成就刪行。
   - 生成物：`python3 wf/tools/index_gen.py --apply` 重生的各夾 `_index.json`（repo 裡 36 份）與 `wf/knowledge/code-map/proto8/<夾>.json`。

## 硬限制（不能違反）

- 本地與遠端都只有一個 `main`；不開分支、不開 worktree 分支、不 push。
- commit 只能 `git commit -F msg -- 檔案…`（或等效的「只動點名的路徑」），不准 `add -A`／`add .`。
- commit 前必跑 `index_gen.py --apply`，生成物跟程式同一個 commit。
- 新檔第一行寫一句話（index_gen 靠它）。
- trailer 由申請者寫在訊息裡，排隊機制不改訊息。
- 盡量確定性、不靠 LLM。
- 不動活樹 `~/aos-home` 的 lib／py／knowledge；`proto8/cmd`、`proto8/py` 存檔即生效（本題不需要碰）。
- 要在活樹 repo-aos 身上掛 hook／agent，指令交頂層去掛（kernel_gate 在頂層手上）。
- 只 kill 自己記下 pid 的程序；不刪檔。

## 現況量測（opus 11-14 量的）

- repo：12763 個進版控檔、工作樹 188 MB（不含 .git）、`.git` 87 MB。
- `index_gen.py`（檢查模式）約 0.12 秒。它用 **`git ls-files`** 決定列哪些檔：**新檔沒進 index 就不會被列進 `_index.json`**。它也讀工作樹的檔頭——所以在共用工作樹上跑，別條線還沒 commit 的檔頭改動、別人 staged 的新檔，都會被算進生成物。
- 生成物會被「整份重寫」；兩條線各自新增檔案時，兩邊的 `_index.json` 正確版本不同，誰後 commit 誰的要包含前一個的。
- aos 的定時手段（知識庫 `aos/clock.json`）：
  - `clock_register`：信進 queue，每次都進 agent 的對話（一個腦回合）。
  - `on_clock` hook（`self_hook add event on_clock every_ms N path P`）：在 agent 的 loop 裡跑程式、不進對話；**每個 step 開頭檢查，agent 正在一個 turn 裡時不跑、睡著不跑**。頂層 repo-aos 常常一個 turn 很長，掛在它身上的 hook 會被拖住。
  - agent-fsm 身（四格迴圈 idle／think／wait／act，腦是寄信給 llm kernel）；可以掛 hook，可以設 rlimit。
- aos 信：`aos-mailbox -s <stack> send ...`／`mailbox_send`；六種 STATUS（REQUEST、DONE、BLOCKED、NEEDS-USER、FAILED、PROGRESS）。各 ok-* 是 eca（Claude Code），手上有 Bash，也有 `mailbox_send`。

## 頂層的初步構想（任務書原文的要點）

一個 commit 排隊機制，所有線把 commit 交給它，一個一個做：

- 形式自選，例：`wf/tools/commit_queue.py`，由一個 on_clock hook 或一隻 agent-fsm 掛在 repo-aos 底下跑。
- 申請：一封 aos 信或丟進某資料夾的 json；內容＝線名、檔案清單、commit 訊息、共用索引檔要追加的列（「追加這一列」語意，不是整檔）。
- 處理（加鎖、同時只做一件）：① 清單裡每檔確實有改動 ② 不帶清單外的檔，包括 index 裡別人 staged 的（pathspec 或暫存 index）③ 把索引列合併進共用檔 ④ 跑 `index_gen --apply`，只帶它為這次改動重生的檔 ⑤ commit，回信附雜湊或錯誤原文。
- 衝突：同一檔兩條線都改了、另一條還沒交出來時，擋下並回信說明，不硬 commit。
- 附申請者用的小指令，例 `commit-request --line ok-kf --files a b --msg-file m`。

## opus 想到的別條路與疑點（給 fable 參考，不是結論）

1. **誰來跑排隊**：
   - (a) 掛在 repo-aos 的 on_clock hook：頂層 turn 長時排隊不動。
   - (b) 一隻 agent-fsm 掛在 repo-aos 底下：要一隻常駐 agent，但它其實不需要腦；fsm 閒著時 hook 跑不跑要查。
   - (c) **不要常駐者**：申請指令自己拿 `flock`、當場處理（自己的那件＋佇列裡排在前面的），同步印出雜湊或錯誤。沒有背景行程、不用頂層掛任何東西、也不用回信（結果直接回在申請者自己的 Bash 裡）。缺點：申請者的 shell 要等鎖。
2. **生成物怎麼只反映「這一次」**：在共用工作樹跑 index_gen 會吃進別人的改動。選項：
   - 在一個**乾淨的副本**上做 commit：副本＝HEAD＋本次的檔，跑 index_gen，commit，然後讓 main 指到新 commit、共用工作樹同步。副本形式：`git worktree add --detach`（沒有分支，但有 worktree）；或完全不留 worktree 中繼資料：`GIT_DIR=~/repo/aos/.git GIT_WORK_TREE=<暫存夾> GIT_INDEX_FILE=<暫存 index>`，在 repo 外一個常駐快取夾（例 `~/.cache/aos-commit-queue/tree`）做增量 checkout。
   - 寫回共用工作樹：commit 後要把 `main` 往前推（`git update-ref refs/heads/main new old`，CAS），共用 `.git/index` 裡這幾個路徑要對到新 HEAD（但別人 staged 的別的路徑要留著），工作樹裡生成物與共用索引檔的內容要更新成新版本，別人在共用索引檔上沒 commit 的改動要保住。
3. **共用索引檔用「操作」而不是「整檔」**：申請帶的是操作，不帶檔：
   - 日索引：`append_row`（表尾加一列）。
   - 月索引：`bump_day`（那天的份數加一、摘要尾加一段；那天沒有列就新增）。
   - SESSION-LOG：`upsert_line`（以 `**open｜主題**` 認行，換掉或新增）／`delete_line`。
   - 排隊機制在「HEAD 版」上套操作得到要 commit 的內容；共用工作樹那份也套同一個操作（保住別人在上面沒 commit 的字）。
   - 申請者自己**不要**手改這三份；舊習慣手改了怎麼辦要定。
4. **衝突怎麼認**：共用工作樹裡同一檔的改動分不出是誰寫的。可能的做法：
   - **先宣告（claim）**：開工時 `commit-request claim --line X 檔…`，排隊機制記一份「誰在改哪些檔」；申請時清單中有檔被別條線 claim 著、還沒交出→擋下並說是誰。交出或 `release` 才解。缺點：要大家養成習慣，沒 claim 的照樣分不出。
   - **申請時快照**：申請當下把清單檔的內容（blob 雜湊）記下，處理時內容變了＝有人在申請後又動了→擋。只防申請到處理之間的競爭，防不了申請前的混寫。
   - 兩者合用？
5. **每條線各自 clone 一份、排隊機制 cherry-pick／apply 回 main**：各 ok-* 的工作區本來就在 `wf/temp/<名>`。但 clone 會帶出一個本地 `main` 分支（算不算違反「只有一個 main」？clone 是另一個 repo，不是本 repo 的分支），而且各線是在共用工作樹裡改 `proto8/…`（存檔即生效那幾夾本來就要改在真 repo），整個換成「各自 clone」改動很大；可以只拿來給**想要隔離的線**選用（交 patch／bundle 給排隊）。
6. 規模：一天十幾個 commit，不追求吞吐；正確性與「不弄壞別人的工作樹」優先。

## 要 fable 回答的

1. 選哪種形式跑排隊（上面 1 的 a／b／c 或別的），理由。
2. commit 在哪裡組（共用 index 加 pathspec、暫存 index、乾淨副本），生成物怎麼確保只反映這一次，寫回共用工作樹的步驟與失敗時怎麼退。
3. 申請格式（欄位）、共用索引檔的操作清單與語意。
4. 衝突偵測的規則（claim、快照或別的），擋下時回什麼。
5. 有沒有比「排隊」更好的整體做法（例如各自 clone＋排隊 apply、detached worktree），在不違反「只有一個 main」下。
6. 你看到的邊緣狀況（失敗、半途被殺、鎖殘留、HEAD 被別人手動 commit 往前推、生成器報錯、新檔沒寫一句話…），各要怎麼處理。

請精簡：一份設計稿，條列，可直接細化成施工計劃。不必讀 repo；備料不夠的地方列成「假設」。
