# 別人怎麼做：把 Linux（或一顆核心）當底層、上面再做一層管理的七種作法

← [README](README.md)｜上一份：[02-aos現況](02-aos現況.md)｜下一份：[04-邊緣狀況](04-邊緣狀況.md)

上網查證過的附來源；沒附來源的是一般常識，標「常識」。

## 先講結論

- **蓋在 Linux 上的那幾家（Android、systemd、容器）走同一條路，四步**：①每個單位發一個自己的 uid（身分）→ ②用 namespace 搭布景（看得見什麼）→ ③用 cgroup 管用量 → ④用 seccomp／capabilities 管能做什麼。順序也幾乎一樣：**身分最先，其他是後來一層層加的**（Android 的年表最清楚）。
- **另一條路是 Plan 9、Fuchsia、微核心**：「**看不見就碰不到**」——一個程式能碰的東西＝別人明確交給它的東西（掛進它命名空間的檔、遞給它的 handle），沒有「我是某某所以我可以」這種全域身分。
- aos 天生兩條都沾：資料夾＝空間、照 Plan 9（C-30、C-37），沙箱就是「布景」；daemon＝硬體、kernel 是「寄去的地方」，像微核心的 server。**缺的是第一條路的第①步（身分）**。

## 1. 容器（Docker／Podman）

- **作法**：一個容器＝一組 namespace（自己的行程表、網卡、檔案系統視野）＋一個 cgroup（用量）＋預設的 seccomp 規則與砍過的 capabilities。Docker 官方文件說 namespace 是「第一層隔離」，cgroup 管資源「但不防一個容器讀另一個的資料，主要防阻斷服務」。[Docker security](https://docs.docker.com/engine/security/)
- **教訓一：管理者本身是最大的洞**。Docker daemon 預設要 root，「只有信得過的人才能控制 Docker daemon」，因為能叫它把主機的夾掛進容器＝等於控制主機。[同上](https://docs.docker.com/engine/security/)——這跟 sbx-fix 的「沙箱裡叫 daemon 掛一隻新 agent，那隻在沙箱外跑」是同一件事。
- **教訓二：免 root 的那一版（rootless Podman）用的就是 subuid**：`/etc/subuid` 給使用者一段號碼（例 100000～165535），`newuidmap`／`newgidmap` 把它對進 user namespace；容器裡的 root 對到你本人，容器裡的 uid 1 對到第一個 subuid。掛進去的夾常撞「Permission denied」，要用 `podman unshare` 進去看擁有者。[podman rootless tutorial](https://github.com/containers/podman/blob/main/docs/tutorials/rootless_tutorial.md)——這正是 `aos-asuser` 的做法，連「進去才看得懂擁有者」（`aos-asuser --fix`）都一樣。
- **跟 aos 的距離**：很近。aos 已經有 bwrap（布景）＋rlimit／cgroup（用量）＋subuid（身分，未接上）。容器多了 seccomp 預設規則與一個「映像檔」的概念（aos 的 image＝stack＋ws，C-79）。

## 2. systemd（unit、DynamicUser、sandboxing 選項）

- **作法**：每個服務寫一張 unit（設定檔），裡面一排開關就把服務關起來，不用寫程式。[systemd.exec](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)
  - `DynamicUser=yes`：服務起來時**臨時發一個 uid**（61184～65519 這段），停了就收回；連帶 `ProtectSystem=strict`、`ProtectHome=read-only`、`RemoveIPC=`；狀態夾放 `/var/lib/private` 底下，免得號碼被下一個服務撿到時看到前人的檔。
  - `ProtectSystem=`、`ProtectHome=`、`PrivateTmp=`、`ReadWritePaths=`：布景。
  - `PrivateNetwork=`：只剩 loopback；`RestrictAddressFamilies=`：只准用哪幾種 socket。
  - `NoNewPrivileges=`、`CapabilityBoundingSet=`、`SystemCallFilter=`（違規預設 SIGSYS 殺掉）：能做什麼。
  - `PrivateUsers=`：替服務開 user namespace。
- **重點**：systemd 把「身分、布景、用量、能做什麼」**收成同一張宣告**，而且是「宣告式」：服務自己不知道被關（像 aos daemon 的份額「偷偷」，C-52）。
- **跟 aos 的距離**：aos 的 daemon 表＋沙箱設定＋kernel 站的 `users`，拼起來就是一張「aos 版 unit」，只是分散在三處、由三支程式各管一點。另外 `DynamicUser` 的「臨時發號、用完收回」是 aos 沒想過的一種號碼管法（kernel-limits-plan 是每隻 agent 固定 `sub:N`）。注意 DynamicUser 要 systemd 的 system 層（root）；user 層的 systemd 沒有這招（常識）。

## 3. Android（每個 app 一個 uid）

- **作法**：每個 app 裝好時發一個自己的 Linux uid、跑在自己的行程裡，**靠的就是普通的 uid／gid 檔案權限**，所以 app 預設讀不到彼此的資料。[Android Application Sandbox](https://source.android.com/docs/security/app-sandbox)
- **一層層加上去的年表**（同來源）：5.0 加 SELinux（但 app 之間還是靠 uid 分）→ 6.0 家目錄預設私有 → 8.0 加 seccomp 系統呼叫過濾 → 9 每個 app 各自的 SELinux 沙箱 → 10 檔案系統視野再過濾（看不到共用的相簿夾，只看自己的）。
- **重點**：**最先、最便宜、最有用的是「一個 app 一個 uid」**，其他都是十年間補上去的。權限（相機、通訊錄）是另一層：app 要用就向系統申請，系統（或使用者）點頭才給——**權限本身是要寄請求去拿的資源**。
- **跟 aos 的距離**：「一隻 agent 一個 subuid」＝Android 第一步。「app 向系統申請權限、使用者點頭」很像 aos 的「寄信給 kernel、kernel 或使用者專區裁」（見 [05 庚](05-發想.md)）。

## 4. Plan 9（每個行程自己的命名空間）

- **作法**：每個行程有一份**私有的命名空間**（自己的檔案樹），由它能碰到的資源拼起來；所有資源（本機、遠端、設備、網路、行程控制）都是說 9P 協定的檔案伺服器。`/proc` 取代 `ptrace`、`kill`，`/net/tcp` 的 `ctl`、`data` 檔取代專門的網路系統呼叫；只有建行程與共享記憶體還是系統呼叫。[The Use of Name Spaces in Plan 9](https://9p.io/sys/doc/names.html)
- **重點**：**權限＝你的命名空間裡掛了什麼**。沒掛進來的你連名字都叫不出，不需要另外的「拒絕」。
- **跟 aos 的距離**：C-30「空間可以擴到外部設備，像 Plan 9」、C-37「空間照 Plan 9」早就定了；aos-sandbox 的 `ro`／`rw` 清單就是一份「這隻 agent 的命名空間」。差別是 aos 的命名空間是「布景」（bwrap 一次搭好），Plan 9 是行程自己可以一直 `bind`／`mount` 改的，而且能傳給子行程。

## 5. Fuchsia（capability 系統）

- **作法**：capability＝「能碰某個資源」＋「能做哪些事」綁在一起的一張票。元件在宣告檔裡寫自己提供什麼、要用什麼；父元件把票 `offer` 給子、子 `expose` 給父、要用的 `use`。**沒有「全域權力」（no ambient authority）**：元件能碰的只有遞到它命名空間裡的那幾張票。[Fuchsia capabilities](https://fuchsia.dev/fuchsia-src/concepts/components/v2/capabilities)
- **重點**：權限不是「看你是誰」，是「看你手上有哪幾張票、票是誰遞給你的」——一條看得見的轉手鏈。
- **跟 aos 的距離**：aos 的工具宣告（`_tooldef.json`、`tools.json` 決定 agent 有哪些工具）、knowledge 裡的「定義夾」已經有一點宣告式味道；「父 agent 把哪些夾遞給子 agent」（subagent、子 daemon）就是 offer。aos 缺的是「遞了才有、沒遞就沒有」的強制——今天沒遞的夾，同 uid 下照樣碰得到。

## 6. 微核心的 server 模型（MINIX 3、seL4 一類）

- **作法**：驅動程式與系統服務都是**一般使用者模式的行程**，壞了不會拖垮整台；「轉生伺服器」（reincarnation server）定期檢查每個驅動，掛了或不回應就換一個新的。核心替每個行程限死它能用哪些核心呼叫、哪些 I/O 埠、**能寄信給誰**（最小權限）。[MINIX 3 reliability](https://wiki.minix3.org/doku.php?id=www:documentation:reliability)
- **重點**：**「能寄信給誰」本身就是權限**。系統就是一群互寄訊息的 server，安全靠「誰能跟誰說話」的表。
- **跟 aos 的距離**：非常像。aos 的 kernel 是「寄去的地方」（C-47），daemon 的 `auto-restart`＋清道夫就是轉生伺服器。差在 MINIX 的「能寄給誰」由核心強制；aos 的信箱是一般資料夾，同 uid 誰都丟得進去。換了 uid 之後，「信箱的寫入權限＝能寄給誰」就是現成的那張表（kernel-limits-plan 08 的投遞箱 G5）。

## 7. 多使用者 Unix 的傳統

- **作法**（常識）：一台大電腦、很多人共用。每人一個帳號（uid）、一個家目錄（700 或 750）、共用的專案用群組（`chgrp`＋setgid 夾）、`/tmp` 用 sticky（只准刪自己的）、系統服務各自一個帳號（`www-data`、`postgres`…）、誰能當 root 用 `sudo` 名單管、誰用了多少磁碟用 quota、行程用 `ulimit`。
- **重點**：這套最老、最無聊，也最穩：**所有 Linux 工具（`ls -l`、`ps`、`top`、`du`、`find -user`、防火牆、journald）天生就會照 uid 分**。換了 uid，aos 不用寫任何程式就多出一堆「看誰在吃資源」「誰寫的檔」的現成工具。
- **跟 aos 的距離**：kernel-limits-plan 08 的十種群組用法，就是這套傳統的免 root 版（ACL 代替 `usermod -aG`）。

## 七家一張表

| 作法 | 身分 | 看得見什麼 | 用多少 | 能做什麼 | 要 root？ |
|---|---|---|---|---|---|
| Docker／Podman | 容器裡自己一套；rootless 用 subuid | namespace | cgroup | seccomp＋capabilities | Docker 要；Podman 免 |
| systemd | DynamicUser 臨時發號 | Protect*／ReadWritePaths | cgroup（Memory*／CPU*） | SystemCallFilter、Capability* | system 層要；user 層能用一部分 |
| Android | 一個 app 一個 uid | 後來加的視野過濾 | — | seccomp、SELinux | 系統本身就是 root 管的 |
| Plan 9 | 有，但不是重點 | **私有命名空間＝權限** | — | 沒掛的就沒有 | — |
| Fuchsia | 不靠全域身分 | 遞進來的票 | — | 票上寫的權利 | — |
| 微核心 | 每個 server 一個行程 | — | — | 能用哪些呼叫、**能寄給誰** | — |
| 多使用者 Unix | 每人一個帳號 | 家目錄權限、群組 | ulimit、quota | sudo 名單 | 建帳號要 |
| **aos 今天** | **全同一個 uid**（工具有，未接上） | bwrap（有） | rlimit＋可選 cgroup（有） | 無 | 刻意免 root |
