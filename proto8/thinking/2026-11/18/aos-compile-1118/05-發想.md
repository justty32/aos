# 發想：「用一個文字檔描述整個 aos 程式」可能長成的幾種樣子

← [README](README.md)｜上一份：[04-邊緣狀況](04-邊緣狀況.md)｜下一份：[06-除錯與停下來看資源](06-除錯與停下來看資源.md)

照 11-14「需求不清時先發想、不急著規劃」：這是頭腦風暴，不出施工圖、不排階段、不設門檻數字。每案寫好處、代價、跟八個詞與五條規則合不合、會不會「以後自然長出來」。最後的傾向是推薦，**由使用者拍板**。

八個詞＝定義、stack、工作區、daemon、proc、kernel、信／信箱、工具；五條規則＝①不手改定義、不碰別人的 stack ②用工具不耍 shell ③看錯誤行 ④路徑相對工作區 ⑤被拒是決定不是 bug（[知識庫入口](../../../../knowledge/aos/_description.json)）。

## 先講結論

- **這題 aos 已經想過，名字叫 C-43**：「一套 library，用 lua／lisp 一類語言把整套資料夾布局生成出來——那個生成就是『編譯』」。這次是把語言換成 Python。**使用者 11-14 說 lisp／lua「至少等 kernel 穩定」**，所以時程上這題本來就排在後面；不衝突、也不用重想方向。
- **九個樣子**：甲 維持 mkdir；乙 一份 JSON 展開成夾；丙 Python lib＋build（C-43 的 Python 版，01 玩具就是它）；丁 Python 描述本身就是入口（跑的時候才生）；戊 雙向（夾⇄原始碼）；己 只做「展開預覽」（一個文字檔看整個架構）；庚 把 `tool_spec` 那套往上長一格（agent 也用一支 Python 宣告）；辛 lisp／lua 原案；壬 帶除錯資訊的 lib（追加題，見 06）。
- **最便宜又不跟「夾就是程式」打架的是己**：文字檔只拿來**看**、夾照舊是原始碼，手改問題整個消失。**最自然會長出來的是庚**：`tool_spec` 已經證明「一支 Python 宣告 → JSON」這招在 aos 好用，往 agent 長一格就是同一招。
- **推薦（由你拍板）**：現在不開 lib 大工程；想往前一步就從己（預覽）或庚（agent 版 tool_spec）挑一個小的，丙留給 C-43 真的要做的那天。不管走哪條，守兩條底線：**生成物是普通、能手改的 aos 夾**（沒有 lib 專用格式，C-45）；**指示詞原樣吐出、不在編譯時展開**（可遷移）。
- **要你先答一題**（末節）：你要的「一個文字檔」主要是拿來**寫**的，還是拿來**看**的？

## 甲：維持 mkdir（＋現有的半自動）

- **是什麼**：照今天：`agent_def new` 抄範本、`tools_def` 生工具、手改 JSON、`ctl add` 掛上。
- **好處**：零成本；agent 最會的就是改夾（使用者 11-06「不如直接把一個資料夾跟幾個python程式和json檔案交給agent」）；沒有生成物 vs 手改的問題。
- **代價**：沒有「一眼看全貌」；骨架散在十個檔、互相用 `$env` 路徑指（01 第二節）；同一套東西改一處要記得改幾處。
- **合不合**：完全合，就是現在。
- **會不會自然長**：不用長。

## 乙：一份 JSON（或 YAML）展開成一棵夾

- **是什麼**：C-51「資料夾＝object、名字＝key」反過來用：寫一份大 JSON，一支小工具把物件變夾、字串變檔；再一支把夾收回 JSON。fable 11-14 的 L1／實驗也提過（用 lua）。
- **好處**：最小（幾十行）；**可以完全雙向**（JSON⇄夾，因為兩邊都是資料、沒有迴圈和函式）；agent 讀寫 JSON 很穩。
- **代價**：沒有抽象——十隻相似的 agent 還是要寫十份；C-51 明說「互通只當工具與思考方式、不進規範」「細節上有差異」（可執行位、純文字檔、隱藏檔、陣列怎麼變夾）。
- **合不合**：合，前提是當工具、不當規範。
- **會不會自然長**：會——哪天有 agent 嫌一個個 `write` 太慢，自己就會寫一支。

## 丙：Python lib＋build 指令（C-43 的 Python 版）

- **是什麼**：01 的玩具長大：`Tool`、`Fsm`、`Agent`、`Loop`、`Kit`… 類別，`build(out)` 生整棵夾，每份帶 `_from` 指回原始碼行。像 CDK 的 `synth`。
- **好處**：真正的抽象（迴圈生十隻 agent、函式包共用設定）；編譯時就能查錯（fsm 的 `next` 指到不存在的狀態、工具參數型別），**錯誤直接報 `prog.py:13`**；Python 的除錯器、編輯器、測試全都能用。使用者 11-06 說 lisp「debug不方便」——Python 這點比 lisp 好。
- **代價**：04 第一節全部要接（手改、重生、反推）；多一層要維護（03：cdktf 已被棄用）；agent 未必會用（04 第 21 條）；lib 只認自己的類別，要留「原樣吐 dict」的逃生門（04 第 23 條）。
- **合不合**：合。lib 寫的是定義（＝原始碼），跟 `agent_def` 同一個位置，規則 ① 不破；生成物照常用 aos-exec 跑，八個詞都不用加。
- **會不會自然長**：半自然：要有人想清楚第 04 的幾條；但形狀已經被 C-43 定了，不用再想方向。

## 丁：Python 描述本身就是入口（跑的時候才生）

- **是什麼**：一個夾只放 `prog.py`，`_entry` 就是它；aos-exec 跑它時，它把整棵夾生進 `$AOS_STACK` 再 aos-exec 那裡的入口。像 Nix「求值完才有東西」。
- **好處**：**永遠不會有過時的生成物**（每次跑都重生）；git 只有原始碼；04 第 1、12 條消失。
- **代價**：人和 agent 看不到「那棵夾」（只在 stack 裡）、也不能手改；每次跑多一段生成時間（C-77「開銷不算啥」）；`self_*` 的差異要疊在每次新生的定義上。
- **合不合**：大致合（C-68 入口做什麼 aos 不管、C-70 子 stack 自己訂）；但跟 C-07「讓模型能自省」有張力——agent 要讀懂自己，得讀 Python 而不是夾。
- **會不會自然長**：不太會；記著是「有這一招」。

## 戊：雙向（夾⇄原始碼）

- **是什麼**：丙＋一支「反編譯」：讀一棵夾，印成一份 Python（或 lua）。fable 11-14 L2「把活著的資料夾樹印成一段 lua／lisp 給人讀，當作一種粗化視圖」。
- **好處**：手改不再是問題——改了就反編回來；agent 改夾、人改原始碼，兩邊都行。
- **代價**：03 的結論：**沒有人做到全自動**。JSON 那半能反推，Python 原始碼的迴圈與函式反推不回來；反推出來的是「攤平」的版本，抽象丟了。
- **合不合**：合。
- **會不會自然長**：只長得出「JSON 那半的反推」（＝乙）；完整雙向不會自己長。

## 己：只做「展開預覽」——一個文字檔看整個架構

- **是什麼**：不改寫法，加一支唯讀指令：從一個入口出發，把 `_entry`→`body.json`→`loop.json`→`fsm.json`→各格、`tools.json` 的 `$override`／`$ref`／`$env` 全部展開，印成**一份**縮排文字或一份 JSON（像 lisp 的 `macroexpand`、`helm template`、`cue export`）。
- **好處**：使用者要的「一個文字檔描述整個軟體架構」**直接有了，只是方向反過來**——夾是原始碼、文字檔是生成的總覽；手改問題整個不存在；agent 也能用（看懂自己長怎樣）；也正好是 11-14 粗化細化「名字→`_index`→`_metainfo`→本體」的一種視圖。N-45 說「每支程式只解自己讀的格」，所以今天**沒有任何地方能一次看到全展開的樣子**，這支補的就是這個洞。
- **代價**：只能看、不能寫；要知道各程式認哪些 key（`interfaces.json` 指誰、`tools.json` 的 `$override` 是 aos-tools 的私有 key）——要嘛照現有程式各讀一遍，要嘛只展開通用的 `$ref`／`$env`。
- **合不合**：完全合（唯讀工具）。
- **會不會自然長**：會，而且已經有零件（`aos-json-view`、`aos-agent ctl state` 的十一類、`index_view`）。

## 庚：把 `tool_spec` 往上長一格

- **是什麼**：今天一個工具＝一支 `tool.py`，`tools_def check` 從它重生 `_tooldef.json`／`_metainfo.json`。同一招給 agent：一支 `agent.py` 宣告 `SYSTEM`、`TOOLS`、`LLM`、`FSM`，`agent_def check` 重生 `interfaces.json`、`tools.json`、`llm.json`、`fsm.json`。
- **好處**：**照現有先例長**（使用者 11-10 自己要的「方便AI弄json schema, metainfo啥的」那一路）；一次只長一格（C-55 布局成長的精神）；工具這格已經驗證過「生成物進夾、照常手改也行、check 時重生」的共存法。
- **代價**：agent 的檔比工具多、彼此有引用，`check` 要決定「手改的 JSON 和 Python 宣告打架時誰贏」（工具那格是「Python 贏、重生」）。
- **合不合**：合。
- **會不會自然長**：**最可能自然長出來的一條**——agent 寫了幾隻相似的 agent 之後就會想要它。

## 辛：lisp／lua 原案（C-43 原文）

- **是什麼**：fennel（lisp 語法）→ lua → table → 夾；本機已有 lua 和 fennel（11-14 fable L1）。
- **好處**：最貼使用者原本的比喻（程式即資料、巨集）；lua 的 table＝C-71 的比喻。
- **代價**：使用者 11-06「lisp……debug不方便」；agent 寫 lisp 不如寫 Python 穩；**11-14 裁「至少等 kernel 穩定」**。
- **合不合**：合（就是 C-43）。
- **會不會自然長**：等 kernel 穩定再說，這份不展開。

## 壬：帶除錯資訊的 lib（追加題）

- **是什麼**：丙或庚生出來的每一格、每封信都帶「出自原始碼哪一行」，跑起來時可以在 kernel 那層停住、對回原始碼、看當下資源。細節在 [06](06-除錯與停下來看資源.md)。
- **一句話**：`_from` 免費（C-48），但「停住」只有 loop 的一拍、fsm 的一格、kernel 收的那幾種信攔得住；工具呼叫和寫檔不經過 kernel。

## 我的傾向（推薦，由你拍板）

1. **現在不開「Python lib 編譯整套 aos」的大工程**：C-43 早就定了方向，11-14 說等 kernel 穩定；需求（要寫什麼樣的 aos 程式）還在使用中浮現。
2. **想往前一小步，就在己與庚之間挑**：己最便宜、零衝突，直接給你「一個文字檔看整個架構」；庚照現有先例長、最可能自然發生。兩個都不排斥日後做丙。
3. **底線兩條，不管哪條路都守**：生成物是普通、能手改、不靠 lib 也跑得動的 aos 夾（C-45、04 第 19、20 條）；指示詞原樣吐出（04 第 6 條）。
4. **`_from` 這招現在就能用、成本是零**：任何人或 agent 生成 JSON 時順手寫一個出處 key，aos 本來就忽略。

## 要你先答的題

1. **你要的「一個文字檔」主要是拿來寫，還是拿來看？**
   - **寫**：文字檔是原始碼，夾是生成物、別手改 → 丙（或先庚）；要先決定 04 第 1 條「手改了怎麼辦」。
   - **看**：夾照舊是原始碼，文字檔是展開出來的總覽 → 己；手改問題不存在。
   - **兩個都要**：先己後丙，或戊（但反推只做得到一半）。
2. （追加題）**「停在某個指令」你想停在哪一層？** 一拍、一格、一次工具呼叫、還是一封給 kernel 的信——今天前兩層就停得住，後兩層要動程式（[06](06-除錯與停下來看資源.md)）。
