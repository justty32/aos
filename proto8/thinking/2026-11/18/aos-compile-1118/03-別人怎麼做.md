# 別人怎麼做：「用一門語言寫，編譯成一堆設定檔／檔案樹」

← [README](README.md)｜上一份：[02-比喻對照](02-比喻對照.md)｜下一份：[04-邊緣狀況](04-邊緣狀況.md)

11-18 晚由子 agent 上網查證，每段附來源。標「一般知識」的是常識補充、沒有逐句對過來源；標「未查證」的是沒查到。除錯那一組（gdb、rr、Temporal……）在 [06](06-除錯與停下來看資源.md)。

## 先講結論

- **大家走的路可以分三種**：
  1. **語言直接生檔、生完就不管**（CDK、cdktf、Helm、Jsonnet、Dhall、CUE export）：生成物是「一次性輸出」，**手改會被下次蓋掉**，大家都約定「別改生成物，改原始碼」。
  2. **語言描述、工具自己管一份「現況」並對帳**（Pulumi、Terraform、Nix、Guix）：重點不是檔，是「想要的樣子 vs 現在的樣子」的差；**有人在外面手改就叫「漂移」**，靠 `refresh`／`preview` 抓出來。
  3. **不用模板、在人寫的底稿上疊補丁**（kustomize；aos 的 kit、`self_*` overlay 其實是這種）：**跟手改共存最好**，因為底稿本來就是人寫的。
- **「從生成物回到原始碼」幾乎沒人做到全自動**：Pulumi 的 `pulumi import` 能把現有資源印成程式碼讓你貼回去，但官方自己提醒要再 preview 確認、秘密欄位要手補；CDK 的 `cdk import` 只納入、不產生程式碼。**反推一般只做到「把資料匯回來」，不做到「把你的迴圈、函式還原」**。
- **錯誤指回原始碼哪一行，做得好的是「在生成前就驗」的**：Jsonnet 報錯帶堆疊、Dhall 和 CUE 有型別檢查／`cue vet`；CDK 這類到部署層才出錯的，很難指回原始碼行。
- **lisp 巨集的 `macroexpand` 是最方便的「預覽」**：展開一層給你看、不真的跑。對 aos 最值得抄的就是這招＋「生成物不手改」的約定。

## 各家一段

**Nix／NixOS**。`.nix` 寫「怎麼造」，求值後變成 derivation（存在 `/nix/store/<雜湊>-<名>.drv`），造好的東西放 `/nix/store/<雜湊>-<名>`，唯讀。NixOS 的模組系統讓很多模組設同一組選項並自動合併（清單相接、單值衝突報錯、`mkForce` 強制）。取捨：原始碼宣告式、好讀，但生成物路徑是雜湊、人讀不懂；可以用 `nixos-option`、`nix repl` 查合併後的值；store 唯讀，**根本不讓你手改**。錯誤是否指回原始碼行：未查證。來源：<https://nix.dev/manual/nix/stable/language/derivations.html>、<https://nixos.org/manual/nixos/stable/#sec-writing-modules>

**Guix**。用 Scheme（一種 lisp）寫一份 `operating-system` 宣告，`guix system reconfigure` 建出整台系統並切換，舊的一代留著可以退回。取捨：設定本身就是程式能操作的資料（lisp 的程式即資料）；手改 `/etc` 會在下次 reconfigure 被蓋掉（一般知識）。來源：<https://manpages.opensuse.org/Tumbleweed/guix/guix-system.1.en.html>、<https://guix.gnu.org/manual/html_node/Using-the-Configuration-System.html>（後者只看到搜尋摘要）

**Pulumi**。用一般程式語言（Python、TypeScript…）寫資源，它比對現況後直接呼叫雲端 API，並自己記一份「狀態」——**不是先生一堆檔**。`pulumi import` 把既有資源納入，並印出程式碼讓你貼回原始碼；官方提醒貼完要跑 `pulumi preview` 確認沒差異、唯寫欄位（密碼）要手補、匯入的預設加保護。取捨：可以用該語言原本的除錯器（一般知識）；雲端上手改＝漂移，要靠 refresh／preview 對帳。來源：<https://www.pulumi.com/docs/iac/guides/migration/import/>

**AWS CDK**。用程式語言寫，`cdk synth` 合成出 CloudFormation 範本（放 `cdk.out`）。`cdk import` 只把既有資源納入堆疊、**不產生程式碼**，要自己先寫出一模一樣的 construct，且官方說它不檢查屬性是否完整。取捨：生成的範本又長又難讀，`cdk.out` 是暫存產物、不該手改；部署時的錯在 CloudFormation 那層，很難指回原始碼哪一行（一般知識）。來源：<https://docs.aws.amazon.com/cdk/v2/guide/ref-cli-cmd-synth.html>、<https://docs.aws.amazon.com/cdk/v2/guide/ref-cli-cmd-import.html>

**Terraform CDK（cdktf）**。`cdktf synth` 輸出 Terraform JSON 到 `cdktf.out`（可改輸出 HCL），官方說這個目錄是暫時的、之後可能被清掉。**官方頁面寫明 CDKTF 自 2025-12-10 起棄用、不再維護**——「程式語言包一層生設定檔」這條路不是穩贏的。`terraform import` 與 import 區塊可把既有資源納入狀態，不是所有資源都支援。來源：<https://developer.hashicorp.com/terraform/cdktf/cli-reference/commands>、<https://developer.hashicorp.com/terraform/cli/import>

**Dhall**。刻意做成「不能寫無窮迴圈」的設定語言（非圖靈完備、一定會算完），`dhall-to-json`、`dhall-to-yaml` 算成 JSON／YAML。取捨：有型別檢查，生成前就擋錯；輸出只是結果、不留函式呼叫的痕跡，反推不回去（一般知識）。來源：<https://www.haskellforall.com/2016/12/dhall-non-turing-complete-configuration.html>、<https://github.com/dhall-lang/dhall-lang/blob/master/README.md>

**Jsonnet**。JSON 加上變數、函式、條件、import；**任何 JSON 都是合法的 Jsonnet**（跟 aos「JSON 是預設介質」最順）。取捨：錯誤（語言本身、`error`、`assert`）附堆疊追蹤，是除錯上的優點；輸出 JSON 不留來源位置（一般知識）。來源：<https://jsonnet.org/learning/tutorial.html>

**CUE**。型別和值放在同一個格子裡，用 `&` 把幾份「合在一起」（統一），**結果跟合併順序無關**；`cue export` 算成 JSON／YAML，`cue vet` 只驗不輸出。取捨：順序無關，理論上可以把手寫的和生成的用 `&` 疊在一起、衝突就報錯（實務未查證）；有 `cue import` 匯入既有 JSON／YAML，細節未查證。來源：<https://cuelang.org/docs/concept/the-logic-of-cue/>、<https://cuelang.org/docs/concept/using-the-cue-export-command/>、<https://cuelang.org/docs/reference/command/cue-help-vet/>

**Bazel／Starlark**。BUILD 檔用 Starlark（長得像 Python 的小語言）寫；**巨集**在載入 BUILD 時呼叫、展開成一堆規則；**規則**才定義真正的建置動作。巨集生出的目標名字必須以巨集的 `name` 開頭——**用命名規則讓人從生成物認得出是誰生的**。取捨：BUILD 可手寫與巨集混用（一般知識）；展開結果怎麼查：未查證。來源：<https://bazel.build/extending/macros>

**Helm**。YAML 模板裡夾 `{{ }}`，`helm template` 在本機渲染成純 YAML（`--output-dir` 寫成檔、`--show-only` 只看某份、`--debug`）。取捨：模板夾在 YAML 縮排裡，複雜時很難讀（一般知識）；渲染結果回到模板要人工比對、不宜手改。來源：<https://helm.sh/docs/helm/helm_template/>

**kustomize**。不用模板：底檔是人寫的普通 YAML，上面疊 patch、overlay，`kustomize build` 輸出結果。取捨：**跟手改共存最好**（底檔就是手寫的）；表達力比模板弱（一般知識）。來源：<https://kubectl.docs.kubernetes.io/references/kustomize/>（參考頁只列欄位，overlay 概念是一般知識）

**make**。目標檔不在、或比它依賴的檔舊，就重做；**全靠檔案的修改時間**。取捨：手改目標檔會讓它變「新」，make 就不再重建，你的手改被默默留著、也可能從此跟原始碼不一致；漏寫依賴就不重建（一般知識）。來源：<https://www.gnu.org/software/make/manual/html_node/Rule-Introduction.html>（沒開成）、<https://manpagez.com/info/make/make-4.4.1/Rule_Syntax.php>

**lisp 巨集**。程式本身是串列資料，所以巨集就是「吃一段程式、回傳另一段程式」的函式，`defmacro` 定義；`macroexpand-1` 展開一層、`macroexpand` 一直展開到不是巨集為止。取捨：**正向預覽最方便**；展開物在記憶體裡，沒有「檔被手改」的問題；從展開結果倒推原始碼沒有自動機制（一般知識）。來源：<http://www.lispworks.com/documentation/HyperSpec/Body/m_defmac.htm>、<http://www.lispworks.com/documentation/HyperSpec/Body/f_mexp_.htm>

## 一張表

| | 生成物在哪 | 手改生成物 | 反推回原始碼 | 錯誤指回原始碼 |
|---|---|---|---|---|
| Nix／Guix | 唯讀 store／整台系統 | 不讓改／下次蓋掉 | 查合併後的值可以 | 未查證 |
| Pulumi | 不生檔，記狀態 | 叫漂移，對帳抓出 | `import` 印程式碼（要人貼、要補） | 用語言自己的除錯器 |
| CDK／cdktf | `cdk.out`／`cdktf.out`（暫存） | 不該改 | `import` 只納入、不生碼 | 部署層才錯，難 |
| Dhall／Jsonnet／CUE | 你指定的 JSON／YAML | 下次蓋掉 | 只能匯入資料 | 生成前驗（型別、堆疊、vet） |
| Bazel | `bazel-out` | 不該改 | 靠命名規則認得 | 未查證 |
| Helm | 渲染出的 YAML | 不宜 | 人工比對 | 弱 |
| kustomize | 疊完的 YAML | 底檔本來就手改 | 底檔就是原始碼 | 好（沒有中間語言） |
| make | 目標檔 | 會被當成「新」而留下 | 無 | 無 |
| lisp 巨集 | 記憶體 | 無此問題 | 無 | `macroexpand` 預覽 |

## 對 aos 的意思

- **aos 已經同時有第 1 種和第 3 種**：`tool_spec`／`index_gen` 是「生了就不手改」（第 1 種），kit、`self_*` overlay、`$override` 是「底稿上疊補丁」（第 3 種）。新的 Python lib 要選哪種，或兩種並存，是 05 的主軸。
- **第 2 種（記一份狀態、對帳）在 aos 的對應物是 stack**：定義是「想要的樣子」，stack 是「現在的樣子」。但 aos 的 stack 是 agent 自己會改的（`self_*`），不像雲端資源是被動的——04 第二節。
- **cdktf 被棄用是個提醒**：「拿程式語言包一層生設定」會多一層要維護；aos 的 C-45「語法糖不強制」剛好是保險——就算 lib 停了，資料夾照樣能手寫。
