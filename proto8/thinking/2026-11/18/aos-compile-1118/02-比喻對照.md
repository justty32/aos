# 比喻對照：「資料夾＝指令、proc＝CPU、aos-exec＝推一步、檔案系統＋JSON＝lisp」逐條對真正的 aos

← [README](README.md)｜上一份：[01-現況](01-現況.md)｜下一份：[03-別人怎麼做](03-別人怎麼做.md)

## 先講結論

- **最貼的一條**：「aos-fsm＋aos-loop＝會自己取下一條指令的 CPU」。`stage.txt` 就是**程式計數器**（現在跑到哪），`fsm.json` 的 `next` 表就是**跳轉指令**（看結束碼決定下一格，像 CPU 看旗標決定跳不跳），`aos-loop` 是**時脈**（每 `interval_ms` 推一拍）。01 的小實測裡手打五次 `aos-exec counter.json`，`stage.txt` 照 tick→tick→done 走，字面成立。
- **最不貼的一條**：「kernel＝syscall 介面」只對一半。aos 的 kernel 只收「信」：起停 proc、問腦，以及寄給它的其他請求。**讀檔、寫檔、跑工具都不經過 kernel**，直接打 Linux（而且大家同一個 uid，見 [linux-as-hw-1118](../linux-as-hw-1118/README.md)）。所以它像一張**只有兩三格的 syscall 表**，其餘指令都能「直接碰硬體」。這不是錯，是值得想的點（06 的除錯就卡在這裡）。
- **「一個指令」的大小差很多**：CPU 的一條指令都差不多快；aos 的一「格」可以是 0.03 秒的 `math`，也可以是十分鐘的一次問腦。比較像「每條指令都是一次函式呼叫」——比喻成**微程式**或**巨集指令**更貼。
- **lisp 那條，aos 自己已經改過一次**：C-71 定「比喻用 lua 的 table、不用 lisp 的 list」，本質是「index＋巢狀分資料」。lisp 真正搬得過來的是**程式即資料**：aos 的程式（定義夾）跟資料（工作區的夾）是同一種東西，agent 用同一組工具（`ls`、`read`、`write`）就能讀、能改、能生——這就是 homoiconicity 在 aos 的樣子，而且比 lisp 更「天生」（C-07：模型天生就會檔案系統和 JSON）。

## 逐條對照

| 使用者的比喻 | 真正的 aos 行為 | 貼不貼 | 不貼的地方是天然差異，還是值得想 |
|---|---|---|---|
| 一個資料夾／JSON／執行檔＝一條 CPU 指令 | 三者都是 aos-exec 認得的「能跑的東西」（N-61：資料夾找 `_entry`、JSON 找單子或 `js[_entry]`、可執行檔直接 exec） | **貼**：aos-exec 就是「解碼器」，把三種寫法統一成「跑起來」 | 一條「指令」本身可以是一整支程式，裡面又有自己的 loop、fsm、子 agent（C-70 巢狀）。**天然差異**：aos 的指令是「呼叫一個函式」，不是「加兩個暫存器」 |
| Linux proc＝CPU | 單次 `aos-exec` 會 `exec` 成入口：那個 proc **就是**這條指令的執行，跑完就沒了；一直活著、反覆推的是 `aos-loop` 那個 proc；daemon 是**主機板**（C-79「daemon＝硬體」，[板子比喻](../../../../docs/CONCEPTS/附錄1-續-板子比喻.md)） | **半貼**：`aos-loop` 的 proc＝一顆 CPU 核心；單次 aos-exec 的 proc 比較像「一次指令執行」 | 值得想一點點：多隻 agent＝多核心，daemon 的表＝哪顆核在跑誰。比喻延伸得下去，不用改 aos |
| 「它不知道下一條是什麼」 | 單次 aos-exec 只跑一格、不看下一格；N-53「agent 是被外面驅動的狀態機，每次被叫只走一次」 | **貼**，而且是 aos 刻意的設計 | — |
| 「也不確定有沒有下一條」（單次 aos-exec） | 對；有沒有下一拍是外面（loop、人、kernel）決定 | **貼** | — |
| 跑 aos-exec＝手動推 CPU 走一步 | 對 fsm 字面成立（01 實測）；對工具＝一次完整呼叫；對 agent-fsm＝走一格（idle／think／wait／act 之一） | **貼**，粒度看你推的是哪一層 | 值得想：要「單步」時，使用者想停的可能是 **fsm 的一格**，也可能是 **格裡面的一次工具呼叫**、甚至**一次寄信**（06） |
| aos-loop／fsm＝自己取下一條指令的 CPU | `stage.txt`＝PC、`next`＝條件跳轉、`aos-loop` 的 `interval_ms`＝時脈、`max`＝跑幾拍、`ctl.json` 的 pause＝暫停鍵 | **最貼** | — |
| kernel＝syscall 介面 | kernel＝「你把請求寄去的地方」（[知識庫 kernel.json](../../../../knowledge/aos/kernel.json)）；請求是信、非同步、可以排隊或拒絕；只收起停 proc、問腦等；**檔案與工具不經過它** | **半貼** | 值得想：(1) 真 syscall 是同步「陷入」，aos 的是寄信等回信，比較像微核心或 Plan 9 的訊息；(2) 表很小，大部分動作繞過它——要拿 kernel 當除錯攔截點（06），攔得到的只有那幾種 |
| 檔案系統＋JSON＝lisp 的 S 式 | C-35「Linux 檔案系統就是一個 LISP」，但 C-71 改成用 table 比喻（有名字的格子，不是有順序的串列）；C-51 資料夾⇄JSON 互通「只當工具與思考方式」 | **貼一半**：是巢狀資料、能當程式跑；但不是串列 | 天然差異（已經由 C-71 裁過）。真正有用的是下一節的「程式即資料」 |
| 「一個文字檔描述整個軟體架構」 | 今天沒有一份總檔：骨架散在每夾的 `_entry`、`interfaces.json`、`tools.json`、`loop.json`、`fsm.json`，彼此用 `$env` 路徑互指（01 第二節） | **還沒有**，但做得出來 | 這就是本題要的東西，05 的各個樣子 |

## lisp 的三個詞在 aos 對應什麼

| lisp | 意思（白話） | 在 aos |
|---|---|---|
| **程式即資料**（homoiconicity，同像性） | 程式碼本身就是語言裡的普通資料（串列），所以程式可以拿程式來讀、改、生 | 定義夾就是普通的夾；agent 用 `ls`／`read`／`write`／`json_set` 就能改程式。`self_*` 改自己（在 stack 寫差異）、`agent_def` 生新 agent、`tools_def` 生新工具——都是「程式在改程式」。使用者 11-14 說的「開發函數的函數……現在就是了」就是這件事 |
| **巨集**（macro） | 吃一段程式、吐另一段程式的函式，在真正執行前展開 | aos 裡「吃夾吐夾」的東西：`$ref`／`$override` 在讀的時候展開（像**讀取巨集**）、kit 疊上 stack、`agent_def new` 抄範本改名、`tool_spec` 把 Python 宣告展開成 JSON。**這次要的 Python lib 就是一個大巨集**：吃 Python，吐整棵夾 |
| **quote／eval** | quote＝「這段當資料、別跑」，eval＝「跑它」 | C-41（10-19 晚使用者「lisp的quote就是那個功能」）：入口決定哪些元素要跑、預設是資料；eval＝`aos-exec` |
| **macroexpand** | 把巨集展開一層給你看，不真的跑 | aos 沒有現成的「把 `$ref`／`$override` 全展開印出來」的指令（各讀者自己解，N-45）；如果要做 Python lib，**「展開預覽」是最便宜也最有用的一招**（03 lisp 那段） |

## 「一條指令」到底該對到什麼——給 06 的鋪墊

使用者要「停在某個指令看資源」。依上表，aos 裡可以當「一條指令」的單位有四層，從粗到細：

1. **一拍**：aos-loop 推一次（`state.json` 的拍數）。
2. **一格**：fsm 跑一個狀態（`stage.txt` 換一次）。
3. **一次叫**：格裡面跑一次工具（agent-fsm 的 act 格）或一次 aos-exec。
4. **一封信**：寄給 kernel 的一個請求（起 proc、問腦）。

前兩層 aos 今天就停得住（`ctl pause`、只打一次 aos-exec）；第 3 層要改格的程式；第 4 層是 kernel 的位置，最像 syscall 攔截。細節在 [06](06-除錯與停下來看資源.md)。
