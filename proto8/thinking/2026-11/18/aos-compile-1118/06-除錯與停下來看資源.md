# 追加題：跑一支用 lib 寫的程式，「step in」停在某條指令，看當下的資源

← [README](README.md)｜上一份：[05-發想](05-發想.md)

使用者同晚追加：「最好可以適應我們的aos kernel，比如我直接跑一個使用了這個python lib的程式，然後step in去debug，然後我停在某個指令，我可以看到在這個狀態下，我們的一些資源的狀況？」（[00](00-使用者原話.md)）

這份只調查與發想、不改程式。現況讀的是 HEAD 的知識庫與今晚的教學 13、17、18；**下面「已經停得住」的四層，第 1、2 層在暫存樹實跑過（01 第四節），第 3、4 層只讀了文件與程式說明、沒實測**。

## 先講結論

1. **aos 今天就有四個「停住點」，粒度從粗到細**（02 末節的四層）：
   - **一拍**：`aos-agent ctl pause`／`resume`（寫 `ctl.json`，這輪做完才停，教學 13）。
   - **一格**：不讓 loop 推，自己一次一次打 `aos-exec fsm.json`，`stage.txt` 就是「現在停在哪條指令」（01 實測）。
   - **一次工具呼叫**：`before_tool` hook **可以擋下那次呼叫、改參數**，`after_tool` 可以看結果、改結果；hook 的 `timeout_ms` 給 0 就能一直等——**這就是現成的斷點**，不用改 aos 程式，只要寫一支「等人按繼續」的 hook（[知識庫 self_hook](../../../../knowledge/aos/me/self_hook.json)）。
   - **一封給 kernel 的信**：kernel 框架的 `after_verdict` hook 可以回「先留著」（hold），或用 `kernel_gate` 讓一隻 agent 親自審每封信——**這就是 syscall 攔截**，但只攔得到起停 proc、問腦這幾種（02：檔案、工具不經過 kernel）。
2. **停住時看得到的資源已經不少**：`aos-agent ctl state` 一句話印十一類（who、state、tools、llm、system、hooks、history、mailbox、subagents、**resources**：limits／記憶體／CPU／行程數、time）；`ctl ls -l` 有排隊數、重啟數、冷卻、最後錯誤；stack 裡有 `cooldown.json`、`letters.json`、`queue/new/`、`stderr.txt`；kernel 每封信記 `ledger.jsonl`（教學 17、18）。
3. **缺的是三樣**：(a) **「現在這一步對到原始碼哪一行」**——加 `_from`（05 底線第 4 條）就有；(b) **一個把上面全部攤在一起的「除錯畫面」**——零件都在、沒人串；(c) **倒帶**——腦的回答不重現、寫檔寄信是真的發生，只能像 Temporal 那樣「把腦的回答錄下來、重播時直接用錄的」。
4. **跟 kernel 最貼的比喻是 strace／seccomp 的「攔系統呼叫」，不是 gdb 的「停在任意一行」**：kernel 只看得到信，看不到 agent 裡面在想什麼。要 gdb 那種細度，停住點得放在 agent 自己的 hook（第 3 層）。

另外兩個跟「全世界一起停」有關的：

- **時鐘**：C-16「時鐘定義時間、讓時間能停；停下來後 agent 看到的就是那個時間點的空間，可以打包」——這是最接近「整台機器按暫停」的概念，但 `aos-clock` 目前擱置。
- **睡著搬家**（C-79、N-67⑥）：root daemon 的 stack＋ws 凍住可以搬——等於「整台機器的快照」，但不是用來單步的。

## 三、發想：lib 寫的程式跑起來時怎麼「step in」

照 11-14 的規矩，以下是點子，不是設計。

**D1 一行原始碼 ↔ 一步。** lib 在每個生成物寫 `_from`（`prog.py:13`）。四層停住點各自怎麼對回去：
- 一格：`fsm.json` 的那個狀態帶 `_from` → 停在 `stage.txt` 的狀態，就知道是原始碼哪一行。
- 一次工具呼叫：`before_tool` 事件給工具名 → 查那個工具夾的 `_tooldef.json` 的 `_from`。
- 一封信：信裡沒有原始碼行；要嘛寄信的那格／工具帶著（agent 自己知道），要嘛 lib 生的 agent 在信的私有 key 裡附上（C-48 允許）。
- 一拍：對到 `loop.json` 的 `_from`，粒度太粗、意義不大。

**D2 「step」的三種意思**（像 gdb 的 step／next／finish）：
- **step over**＝跑完這一格、停在下一格（手打一次 aos-exec，或 loop 的 `max: 1`）。
- **step in**＝鑽進這一格裡面：格是 agent-fsm 的 act → 停在它叫的每個工具前（before_tool）；格是子 agent → 停在子 agent 的格（C-70 巢狀，每層自己的 stack）。
- **continue to**＝跑到某個狀態／某個工具名才停（before_tool 的 `condition` 已經能「只對某個工具名」）。

**D3 停住時的「資源面板」**，把今天散在各處的東西拉成一頁（像 Erlang Observer）：
- 這隻：`ctl state` 的十一類（含 limits、記憶體、CPU、行程數）、`stage.txt`、`cooldown.json`、`queue/new/` 數量、`letters.json` 的 pending。
- kernel：排隊中幾封、`max_running` 用了幾個、問腦的 slots 與 budget 剩多少、`ledger.jsonl` 最後幾封。
- Linux：cgroup 用量（有開的話）、這隻的行程樹。
- 原始碼：現在這步的 `_from`。
- 這不需要新概念，是一支唯讀工具（跟 05 的己同一個性質：**只看、不改**）。

**D4 kernel 當斷點的位置**：寫一個「除錯 kernel」掛在 `AOS_KERNEL`／`AOS_LLM_KERNEL` 前面，每封信都 hold，人看完按放行。好處是**不碰 agent 本身**（C-52：上層不知道下層），換掉環境變數就拆掉；代價是只攔得到信。照 linux-as-hw 的調查，大家同一個 uid，agent 也可以繞過它直接寫 daemon 的信箱——**除錯用夠了，防賊用不夠**（使用者剛答「先做防呆、模型可信」，剛好合）。

**D5 改了再續跑**：pause 時改 stack（`self_*` 的差異檔、`stage.txt`）、before_tool 時改參數、after_tool 時改結果、kernel hold 時改下一站——四種「改」今天都有門，缺的只是「改完記一筆」，免得事後看不出是人改的。

**D6 倒帶（重播）**：照 Temporal：把「對外的動作」的結果錄下來——腦的回答已經在 history 與 kernel 的 `ledger.jsonl`，工具結果在 history 裡；重播時用 `llm_fake` 端點餵錄好的回答、工具換成「印錄好的結果」。**寫檔、寄信、起 proc 不能重做**，只能跳過或在暫存樹（複製一份 stack＋ws，教學 01「停 daemon 複製 stack 重開」）裡重來。

**D7 用多了自然長出來的**：「等人按繼續」的 before_tool hook 是幾十行的小程式，第一個需要它的人會寫；資源面板也是。照 11-14，這些不用先設計，記得「門已經在那裡」就好。

## 四、邊緣狀況

1. **多隻 agent 並行時停一隻**：別隻照樣寄信給它，信堆在 `queue/new/`（教學 14 實測）；恢復後一次湧進來。寄件人的 `listen` 會等到逾時（`AnswerMissing`）。
2. **停在 kernel 時別的信照樣來**：hold 只卡那一封；但 kernel 的 `max_running`／排隊會照算，hold 太久可能讓後面的排隊信看起來「卡住」。
3. **期限會過**：問腦信可帶 `priority.deadline`、掛 proc 那包的 `held` 會驗寄件人的期限——**停太久，kernel 自己會把信拒掉**。除錯模式要嘛不設期限，要嘛承認「停住時時間照走」（除非 C-16 的時鐘停）。
4. **hook 的逾時**：`before_tool` 預設 `timeout_ms` 60000，停超過一分鐘就算 hook 失敗（`on_error` 預設 stop，agent 會停）；除錯 hook 要給 0。
5. **腦的回答不重現**：同一段 history 再問一次，答案可能不同；所以「重跑這一格」跟「重播這一格」是兩件事（D6）。
6. **真副作用**：寫檔、寄信、起 proc 在重播時會真的再做一次；Temporal 靠「activity 只執行一次」解，aos 要嘛錄、要嘛在複製的暫存樹裡重來。
7. **eca 本體（claude、codex、pi）**：它們的工具呼叫在外部 CLI 裡，aos 的 before_tool 攔得到多少要看各身體的接法（eca-pi 有自己的 hook 轉接）；**未查**。
8. **停在格的中間**：pause 不打斷正在想的那輪（教學 13）；要停在「腦答完、工具還沒跑」只能靠 before_tool；要停在「問腦送出前」得靠 kernel hold。
9. **子 agent 與巢狀**：step in 到子 agent 時，它有自己的 stack、自己的 loop；父那邊的 before_tool 在等子 agent 的工具（`subagent`）回來——兩層同時停住時要分清楚是誰在等誰。
10. **除錯 kernel 本身也是 proc**：它掛了，所有信卡住；拿掉它要改 `AOS_KERNEL`，已經在跑的 agent 環境變數改不到（N-63 子行程繼承，起來時就定了）。

## 五、要你答的（跟 05 第 2 題同一題）

**「停在某個指令」你最想停在哪一層？** 一拍（今天就有）、一格（今天就有）、一次工具呼叫（門在、缺一支等人按繼續的 hook）、還是一封給 kernel 的信（門在、缺一個除錯用的 kernel 站）。你答了哪層，就知道「資源面板」要先放哪些東西。
