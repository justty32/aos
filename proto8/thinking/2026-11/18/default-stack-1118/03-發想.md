# 預設 stack 的發想：「cd 過去就能說」可以長成哪幾種樣子

← [README](README.md)｜上一份：[02-邊緣狀況](02-邊緣狀況.md)

照 [user/03「需求不清時先發想、不急著規劃」](../../../../../wf/workflows/common/user/03-討論紀錄與規劃.md#需求不清時先發想不急著規劃2026-11-14-定)：這份只擺點子、好處、代價、跟既有原則合不合，**不排實作、不估工時**。方向是使用者的（鐵律 5），最後的推薦只是推薦。

## 先講結論

- 七個樣子，從「什麼都不改」到「站在哪就跟誰說」排開：甲 維持現狀、乙 只改錯誤訊息、丙 一句「進去」的殼指令、丁 agent 的 stack 裡放一張路標、戊 像 git 一樣往上找、己 站在定義夾裡說、庚 不查表直接往 `./queue/` 丟。
- 乙、丙不動任何找法規則；丁加一條「只看 cwd 這一層」的退路，跟今天的 `./.stack` 同一級；戊、己、庚會推翻以前定過的事（N-63「不往上層找」、11-04「不比工作區」「不留 --stack」）。
- **我的推薦：丙＋乙**——一句 `aos-agent` 的「進去」把你 cd 到那隻的 stack、順便把 daemon 和名字設進這個殼，之後怎麼 cd 都對它說；加上把三句會誤導的錯誤訊息改清楚。規則一條都不動。想要「任何殼、什麼都不 source 也能說」，再看丁。由你拍板。
- 還有一題要你先說：你要的「cd 過去」是 cd 到 **agent 的 stack**（`.stack/procs/ann/`，你 11-18 下午的原話），還是 **agent 的定義夾**（`agents/ann/`，頂層派工的寫法）？這兩個差很多，見己。

## 對照用的幾條既有規矩

- **八個詞**：定義＝原始碼、stack＝那隻的記憶體、daemon＝機器（表在它的 stack）、ws＝它工作的地方。一份定義可以跑好幾隻；一個 stack 只屬於一隻。
- **五條規則**裡跟這題有關的是第 1 條（agent 不碰別人的 stack、不手改定義）——那是對 agent 說的，人 cd 進去看、說話不違反；但規則要是做成「cwd 推對象」，agent 和工具也會吃到。
- **N-63 ②**：沒給就報錯、不猜位置；`AOS_DAEMON` 沒設的唯一退路是 `./.stack`，「不往上層找」。
- **C-52**：上層要看下層要經機制，「只查表、不從路徑往上爬」（`ctl who` 就是這樣寫的）。
- **C-56**：寫什麼就做什麼，不把規則藏在特定值裡（暗規則）。
- **11-04**：對象＝`--target` ＞ `AOS_AGENT`、「不比工作區」；「cd 進去就能說」當時的答案就是殼裡設 `AOS_AGENT`（他說「有點類似命名空間」）；直接跑、不在 daemon 上的，aos-agent 不管（「不留」）。
- **C-79／搬家**：表上全是相對 daemon stack 的路徑，整棵樹搬走照樣對得上；新的東西最好也這樣。

## 甲、維持現狀

今天：`-d` ＞ `AOS_DAEMON` ＞ `./.stack`；`-t` ＞ `AOS_AGENT`。站在樹根打 `aos-agent -t ann say …`；要 cd 到處走就 `export AOS_DAEMON=$(realpath .stack) AOS_AGENT=ann` 一次。

- 好處：零改動；規則短、講得完（C-85）；11-04、11-05 定的全照舊。
- 代價：「cd 過去就能說」做不到；站在 agent 夾裡要打 `-d ../.. -t ann`，`-d .` 又會報一句誤導的錯（02 第 16 條同類）。
- 合不合：全合。

## 乙、只改錯誤訊息（可以跟任何一案一起）

規則不動，只讓走錯的人一眼看出該怎麼打。三處：

1. 站在 agent 的 stack 裡報 `DaemonMissing` 時，多一句「這裡看起來是某隻 agent 的 stack；daemon 的 stack 通常在它上兩層：`-d ../..`」。
2. `-d` 指到 agent 的 stack 時，`StateMissing` 不說「daemon not started yet」，改說「這是 agent 的 stack，不是 daemon 的」（教學 02 發現的問題 1）。
3. `using-aos-agent.sh` 在沒有 `.stack/` 的夾裡 source 時提醒一句，不默默設成 `$PWD/.stack`（教學 02 發現的問題 2；01 第 8 列實測證實）；`aos-exec` 在定義夾裡跑 `_entry` 那句 `StateMissing`（01 第 5 列）同理。

- 好處：最小；不碰任何裁過的題。
- 代價：還是要打 `-d`、`-t`；第 1 條的「看起來是」本身是猜的，只能放在錯誤訊息裡、不能拿來做事。
- 合不合：合（只動訊息）。第 1 條要小心別寫成「幫你接上」。

## 丙、一句「進去」：cd 過去，順便把命名空間設好

給人殼一個「進入某隻」的動作，例如 `using-aos-agent.sh` 多一個函數（名字隨便，像 `enter ann`），做三件事：查表拿到 ann 的 stack、`cd` 過去、`export AOS_DAEMON=<daemon 絕對路徑> AOS_AGENT=ann`。之後在這個殼裡 `say`、`listen`、cd 到子夾、cd 走都對 ann 說，直到 `enter` 別隻或開新殼。

- 好處：手感就是「cd 過去就能說」；規則一條不動（變數是人明給的，N-63 ② 照字面成立）；就是 11-04「命名空間」那個想法多一步 cd；子資料夾、`-s` 放別處的 stack 都沒問題（查表來的）。
- 代價：要先 source 那份殼檔（或在 `env.sh` 末尾自己加一行）；殼裡記的是絕對路徑，樹搬了要重 enter；用一般的 `cd` 進去不算數——**是「enter」才算，不是「cd」**；cd 到別棵樹還是對 ann 說（02 第 4 條，今天就這樣）。
- 合不合：合。C-45「語法糖」那一類。

## 丁、agent 的 stack 裡放一張路標，只看 cwd 這一層

掛上時（daemon 或 `ctl add`）在每隻的 stack 寫一張小檔，例如 `{"daemon": "../..", "name": "ann"}`（相對路徑）。aos-agent 在 `-d`、`AOS_DAEMON`、`./.stack` 都沒有，而且 `-t`、`AOS_AGENT` 也沒有時，讀 **cwd 這一層**的這張路標，再回表上核對「ann 的 stack 真的就是這裡」，對上才用，對不上就報錯。

- 好處：任何殼、什麼都不設，`cd .stack/procs/ann && aos-agent say hi` 就行；相對路徑，搬家、複製整棵樹照樣對（02 第 11、12 條）；回表核對，`ctl rm` 留下的、表上換人的 stack 不會被誤認（02 第 9 條會報錯而不是亂寄）；不往上爬。
- 代價：多一個固定檔名（C-51 希望固定名越少越好）；N-63 的退路表要多一列，`AOS_AGENT` 本來沒有退路，要開一條；「誰寫這張路標」要選（daemon 寫＝daemon 開始往 proc 的 stack 放東西；ctl add 寫＝`aos-daemon-ctl add` 掛的就沒有）；子資料夾不靈（02 第 7 條）；工具的小格不在 cwd 這一層，不會誤中（02 第 19 條），但要寫明。
- 合不合：大致合——跟 `./.stack` 同一級的「只看 cwd、寫明的唯一退路」；跟 C-52 的「經公開宣告」也合（路標是公開的、不是從路徑猜）。要改 N-63 一列、要你同意開 `AOS_AGENT` 的退路。

（丁的一個變形：不寫路標，改成「cwd 的 `../../procs_state.json` 在、表上有一列的 stack 就是 cwd」就用它。少一個檔，但只認預設位置 `procs/<名>/`，`-s` 放別處的不靈，而且這就是在猜位置。）

## 戊、像 git 一樣往上找

從 cwd 一路往上，找到第一個有 `procs_state.json` 的夾當 daemon，再用 `ctl who` 的查表法反查 cwd 在哪隻的 stack 底下。

- 好處：最像 git；任何子資料夾都靈；不寫新檔。
- 代價：直接推翻 N-63「不往上層找」和 C-52「不從路徑往上爬」；巢狀 daemon 會先找到最近那台（02 第 5 條）；沙箱、工具裡的行程只要 cwd 在樹裡就摸得到 daemon（02 第 18、19 條，今天的沙箱缺口會變大）；規則變成「看你站在哪」這種看不見的條件（C-56 暗規則）。
- 合不合：不合三條既有規矩，要你明確翻案。

## 己、站在定義夾裡說（頂層派工的那種讀法）

`cd agents/ann && aos-agent say hi`：拿表上的 `def` 欄反查掛這份定義的那隻；只有一隻就對它、好幾隻就報錯要你 `-t`；（再進一步）一隻都沒掛就順手 `ctl add`。

- 好處：「我在寫 ann、順手試一下 ann」的手感；搭今天已有的 `aos-exec agents/ann`（＝掛上）很順。
- 代價：定義跟 agent 是一對多（01 實測 ann、ann2 共用一份），常常猜不出；定義夾不在 daemon 底下、甚至被好幾棵樹共用，daemon 從哪來還是要 `AOS_DAEMON`（02 第 17 條）；「順手掛上」要猜名字、工作區（預設會是定義夾本身，等於讓 agent 在自己的原始碼裡做事），而且是偷偷改 daemon 名單（11-04「add／rm 對象要明講」）。
- 合不合：只反查、不自動掛的那半勉強合；自動掛的那半跟 11-04 衝突。概念上是對「原始碼」說話（C-79），我覺得是最不順的一種。

## 庚、不查表，直接往 `./queue/` 丟

站在某個 stack 裡（有 `queue/`、`history.jsonl`），`aos-agent say` 就直接把信丟進 `./queue/`、`listen` 直接讀 `./history.jsonl`，不找 daemon、不查表。

- 好處：真正的「預設 stack＝這裡」；不在 daemon 上、直接 `aos-exec` 跑的 agent 也能說；兩台機器、daemon 沒開都照寫（等它醒來答）。
- 代價：推翻 11-04「不留」（aos-agent 只管 daemon 表上的）；沒有表就不知道它活不活、在不在答，`listen` 的那些提醒（暫停中、停了、下表了）全沒了；history 檔名今天由定義的 `interfaces.json` 宣告，不查表就拿不到定義，只能寫死 `history.jsonl`；daemon 沒開時「說了沒人答」更難察覺（02 第 10 條）。
- 合不合：跟 11-04 衝突；也繞過了 kernel（設了 `AOS_KERNEL` 時表要問 kernel，02 第 21 條）。

## 我的推薦（推薦，由你拍板）

**丙＋乙。** 理由：

1. 你 11-04 自己定的「命名空間」就是這題的答案的雛形，丙只是把「cd」跟「設命名空間」綁成一個動作，手感就是你說的「cd 過去」，但規則一條都不用翻。
2. 今天會讓人卡住的，一大半是錯誤訊息講錯方向（`-d .` 說 daemon 沒開、`using-aos-agent.sh` 在 agent 夾裡默默設錯）。乙把這幾句改對，甲的用法也順很多。
3. 戊、己、庚都要翻你以前裁過的題，而且會讓沙箱、工具多一條「看你站在哪」的暗路；在需求還在長的時候先不碰。
4. 如果用了丙一陣子，還是想要「開新視窗、什麼都不 source、cd 進去就能說」，丁是最乾淨的下一步（只看一層、相對路徑、回表核對）；那時再談，也比較知道路標要誰寫。

**要你先回答的一題**：你說的「cd 過去」，是 cd 到 agent 的 stack（`.stack/procs/ann/`），還是 agent 的定義夾（`agents/ann/`）？前者丙、丁都接得住；後者只有己，而且我不推薦。
