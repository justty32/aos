# 預設 stack 的邊緣狀況：「cd 過去就能說」會在哪裡出事

← [README](README.md)｜上一份：[01-現況](01-現況.md)｜下一份：[03-發想](03-發想.md)

## 先講結論

最要緊的三個：

1. **同一夾兩個終端同時說**：兩句會被同一輪收走、合成一個回答，兩邊印出一樣的字（實測）。這是今天就有的，跟怎麼找 agent 無關；但「cd 過去就能說」會讓「幾個人站在同一隻裡同時說」變得更常見。
2. **夾還在、agent 不在**：`ctl rm` 留下的 stack、daemon 沒開的 stack，cd 進去看起來跟活的一模一樣。照「站在哪就跟誰說」的規則，信會丟進一個沒人收的 `queue/`，或報一句讓人摸不著頭腦的錯。
3. **agent 的 stack 底下還有別人**：工具的小格（`<agent stack>/tools/<名>/`）、子 daemon 的 stack 都可能長在 agent 的 stack 底下；沙箱也看得到整棵樹。「從 cwd 推出對象」的規則，會讓工具不帶 `-t` 就對自己的 agent 說話、讓沙箱裡的東西更容易摸到 daemon。

下面每條寫：今天怎樣、換成「cd 過去就能說」會怎樣。標「實測」的是 [01](01-現況.md) 暫存樹跑過的，其他是讀程式或推的。

## 一、同一隻、好幾個人

1. **兩個終端同時 say／ask**（實測）：from-A、from-B 被 agent-fsm 同一輪收進 history，假腦只答一則；兩個 `ask` 都印那一則。`say s1; say s2; listen` 兩次 `listen` 也都印同一則。這是照設計（回答的 `answer_to` 包含兩封信），但對人來說像「我的問題被吃掉了」，還看得到別人那句。
2. **不給信名的 `listen`** 等的是「最新那封」，別人剛 say 的那封會蓋過你的。`ask` 與 `listen --letter` 認得自己那封。
3. **eca 有畫面時**：有人開著 tmux 畫面在打字，另一個終端 say，兩邊的話進同一個對話。

## 二、找錯 daemon、找錯隻

4. **換 daemon／兩棵樹**：今天殼裡 export 過的 `AOS_DAEMON` 會一直留著，cd 到另一棵樹也照樣對舊那棵說（教學 02 實測過 `ctl ls` 列出另一棵的表）。若改成「看 cwd 決定」，就反過來：cd 對了就對；但「環境變數贏過 cwd」這條要不要改，會撞到 11-05 定的順序。
5. **巢狀 daemon**：子 daemon 的 stack 可以在某隻 agent 的 stack 底下（C-70 巢狀由程式自己訂）。若從 cwd 往上找 daemon，會先碰到最近那台子 daemon；名字只在一台 daemon 裡唯一，兩台各有一隻 `ann` 是可能的。
6. **stack 不在預設位置**：`ctl add -s` 可以把 stack 放到任何地方（不在 `procs/<名>/`）。靠「往上兩層就是 daemon」的推法會錯；靠查表（`ctl who` 那種）不會錯，但先要知道 daemon。
7. **子資料夾**：cd 到 `procs/ann/queue/` 或 `procs/ann/think/`。只認「cwd 本身」的規則在這裡就不靈；往上找的規則才靈，但往上找又是 N-63 寫明不做的。
8. **`using-aos-agent.sh` 在 agent 夾裡 source**（實測）：`AOS_DAEMON` 被設成 `…/procs/ann/.stack`，之後每句都 `DaemonMissing`。今天就踩得到。

## 三、夾還在、agent 不在

9. **`ctl rm` 留下的 stack**（實測）：stack 照留（使用者定的「兩支都留 stack」），cd 進去樣子一樣，`say` 報 `InstanceMissing`。若規則是「在 stack 裡就自動對它說」，要決定：報錯、還是順手 `ctl add` 回來（這就變成會偷偷改 daemon 名單，11-04 定的「add／rm 對象要明講」）。
10. **daemon 沒開**：`say` 今天照寄（信進 `queue/`，daemon 再開時睡著的自己醒來答）。cd 進去說話「看起來成功了」，但沒人在答；`ask` 會一直等。
11. **搬過、複製過的樹**：`cp -r` 一份樹出來（教學 01），兩份裡都有 `procs/ann/`。cd 進複本那份說話，對的是複本的 daemon（如果它有開）；沒開就落進 10。若靠 stack 裡寫死的 daemon 絕對路徑，複本會對回原本那棵——**這是靠相對路徑才不會錯的地方**。
12. **兩台機器**：image（`.stack/`＋ws）進 git 帶到另一台，那邊 daemon 還沒起，同 10。表上存的是相對路徑，cd 規則跟搬家合得來；殼裡 export 的絕對 `AOS_DAEMON` 合不來。

## 四、定義那一邊

13. **一份定義、好幾隻**（實測 `ann`、`ann2` 共用 `agents/ann`）：站在定義夾裡說，「對誰」本來就猜不出來；表上的 `def` 欄反查會有好幾列。
14. **定義還沒掛**：若「站在定義夾就能說」連帶自動掛上，掛上要的名字、工作區、`--auto-restart` 全得用猜的。工作區預設是 cwd＝定義夾本身，agent 會在自己的原始碼裡工作（規則 1：定義不要手改）。
15. **定義改了**：agent-fsm 的 system、tools、hooks 每輪（每次事件）重讀，改了下一輪就生效；表上 `def` 記的是路徑，換定義要 `ctl set-def`。站在定義夾裡直接改檔、直接說，效果會落在「所有掛這份定義的 agent」上，不只眼前這隻。
16. **在定義夾裡 `aos-exec .`**（實測）：aos-exec 先在 cwd 建一個暫時的 `.stack/`，ctl add 找到它就當成 daemon，報 `StateMissing … is not an aos-daemon stack`，退出時空的 `.stack/` 又被收掉。錯誤訊息說的跟真正的原因（這裡沒有 daemon）對不上。
17. **定義夾不在樹裡**：定義可以放在別處、被好幾棵樹共用（`$AOS_HOME/templates/...`）。從定義夾推不出是哪棵樹的 daemon。

## 五、沙箱、權限、kernel

18. **沙箱**：[沙箱實機檢查](../沙箱隔離-實機檢查.md) A 條已經發現：起手範本的 daemon stack 在樹裡，只綁樹當工作區的沙箱就能 `aos-daemon-ctl ls`、能對 ann 說話。今天的 `./.stack` 退路在這裡已經幫了倒忙；再加「往上找」或「cwd 推對象」，沙箱裡任何 cwd 落在樹裡的行程都更容易找到 daemon。
19. **工具小格在 agent stack 底下**：工具的 stack（小格）是 `<agent stack>/tools/<名>/`（P-17）。工具跑起來的 cwd 在哪我沒逐支查；只要它 cd 進自己的小格、或規則改成也看 `AOS_STACK`，「在某隻的 stack 底下就對那隻說」就會讓工具裡一句不帶 `-t` 的 `aos-agent say` 變成自己對自己說（可能繞成迴圈）。今天它會 `TargetMissing`，反而安全。
20. **換帳號（aos-asuser）**：別的 uid 的 stack，人可能 cd 得進去、寫不進 `queue/`（推的，沒實測）；cd 規則改不了這件事，只是讓人更常走到這裡。
21. **設了 `AOS_KERNEL`**：表要問 kernel，kernel 可以刪減表。cwd 推出來的對象若不在刪過的表上，就是 `InstanceMissing`；不能為了「cd 過去就能說」繞過 kernel 直接讀 daemon 的表（N-63：問不到就 `KernelFailed`、不退回）。
22. **agent 自己的殼**：agent 叫 Bash 時已經帶 `AOS_DAEMON`，cwd 是它的工作區不是 stack。cd 規則對它沒影響，除非它 cd 進別人的 stack（規則 1 本來就不准碰別人的 stack）。
