# aos-llm 四個方案的比較與實測數字

← [README](README.md)｜上一份：[03-歷史](03-歷史.md)

## 先講結論

- **速度不是理由**：一次問腦（假腦）來回約 1.3 秒，aos-llm 自己只佔其中約 25 毫秒（send）＋每拍約 1～4 毫秒（recv）；剩下全是 kernel 每 300 ms 一輪、掛 proc、跑 endpoint。真腦還要再加模型的幾秒。
- 改成**獨立的 Python 指令**，每次叫多 50～200 毫秒（Python 起動），wait 格每拍從約 265 ms 變約 400 ms；不痛，但是倒退。
- 改成 **Python 函式庫、wait.py 直接 import**（丁案），每拍反而省掉一次開子行程，寄／收在同一行程裡只要 0.2～0.3 毫秒。
- **整支拿掉（乙）不划算**：它做的那幾件小事（寄件人＝stack、找回給我的信、鎖、撤信、提醒）會散進 4 個呼叫端各寫一份，還會改掉額度的寄件人。

## 實測（公司 WSL，暫存複本 `~/.aos/scratch/llm-survey-1118/`，HEAD `0f1b7b7af` 用 `git archive`）

同時有別線在跑，機器偏忙，**絕對數字偏大、看比例**。每項 30 次取中位數（ask 10 次、來回 5 次）。

| 量什麼 | 中位數 | 最小 |
|---|---|---|
| `/bin/true`（開一個子行程的底） | 5.9 ms | 1.9 ms |
| `python3 -c pass` | 70～88 ms | 35 ms |
| `python3 -I -S -c pass` | 49 ms | 17 ms |
| `python3 -c "import json,os,time,shutil"` | 121 ms | 47 ms |
| **`aos-llm send`（C++）** | **25 ms** | 10 ms |
| 等價的最小 Python 腳本 send（`mini_llm.py`，只寫信、不含提醒） | 234 ms | 103 ms |
| **`aos-llm recv --quiet` 沒到（C++）** | **1～4 ms** | 0.7 ms |
| 等價 Python 腳本 recv 沒到 | 143 ms | 93 ms |
| `aos-llm ls`（C++） | 2 ms | 0.8 ms |
| Python 函式庫在同一行程裡 send | 0.34 ms | 0.24 ms |
| Python 函式庫在同一行程裡 recv 沒到 | 0.18 ms | 0.11 ms |
| `python3 wait.py --help`（wait 格每拍本來就要付的 Python 起動＋import） | 264 ms | 153 ms |
| **`aos-llm ask` 端到端（假腦）** | **1332 ms** | 1258 ms |
| send＋每 20 ms 輪詢 recv 的來回：C++ | 1326 ms | 1254 ms |
| 同上：Python 腳本 | 1413 ms | 1303 ms |
| 起樹問一句（`say hello`＋`listen`，假腦，含 think／wait／act 幾格） | 6.1 秒；第二句 9.8 秒 | — |
| 從乾淨的建置夾編 aos-llm 連它的三個相依庫（`make BUILD=… aos-llm`，-O3 靜態） | 85 秒 | — |

讀法：wait 格每拍＝起 `python3 wait.py`（約 265 ms）＋叫一次 `aos-llm recv`（約 1～4 ms）；aos-llm 佔不到 2%。換成 Python 指令＝每拍多約 100～150 ms；換成函式庫＝每拍少約 1～4 ms。端到端差距在雜訊裡（1326 對 1413 ms，5 次）。拿掉 aos-llm 本身**省不到多少建置時間**：aos-post、aos-lock、aos-util 還要給 aos-daemon 用，省的只有 aos-llm 自己 5 個 .cpp。

## 四個方案

| | 甲：維持現狀 | 乙：整支拿掉 | 丙：Python 重寫成獨立指令 | 丁：Python 函式庫＋薄指令（推薦） |
|---|---|---|---|---|
| 做法 | 不動 | 呼叫端改直接用 `aos-post` 加自己的幾行 Python | `py/aos/apps/llm/` 一支 `aos-llm`（entries.json 生入口），行為逐條照 C++ | 協定放 `py/aos/llm_client.py`（或併進 kernel_llm 旁）：`send`／`recv`／`ask`／`regret`／`ls` 五個函式；`aos-llm` 指令變成它的薄殼；wait.py、judge-llm、llm_forward 改 import |
| 要改的檔 | 0 | 程式 4～6、測試 10～12、文件約 90（指令消失，全要改寫） | 新增 2～4；刪 `cpp/aos-llm/` 16；`cpp/Makefile` 3 行；測試改指 6；文件 15～25（只改「C++」那些字） | 丙的全部，再加 wait.py 兩份、judge-llm、llm_forward 4 個；agent-fsm 假指令的測試 7＋2 支要改成假函式庫 |
| 工作量（agent 時數，粗估） | 0 | 6～10 小時，大半在改文件 | 6～8 小時 | 10～14 小時 |
| 對外行為 | 不變 | **會變**：寄件人從 stack 變 `$AOS_WS`（`aos-post send` 的規則），一隻 agent 一份額度失效，除非 aos-post 加 `--sender`（又是改 C++）；人手沒有 `aos-llm ask`／`ls` 可打；知識庫要 agent 改查法 | 指令、旗標、退出碼、stderr 一行都照舊；只是每次慢約 0.1 秒 | 指令同丙；wait 格不再開子行程、錯誤改成函式丟例外再由 wait.py 印同一行 |
| 風險 | 無；只是 C++ 多一支要顧 | 高：4 個呼叫端各寫一份撿回信、鎖、撤信，以後改協定要改 4 處 | 低～中：`ask` 的鎖與撤信、信件名稱格式（`<奈秒>.<pid>.<起動 tick>`，Python 要讀 `/proc/self/stat`）、回信信箱相對路徑要照抄對；有 6 支黑箱測試接著 | 中：除丙的風險外，wait.py 改的是**範本**，使用者已經抄出去的定義（`~/aos-home/agents/ann/wait.py`）不會自己更新，舊抄本仍去 PATH 找 `aos-llm`——所以薄指令一定要留 |
| install.py／Makefile | 不變 | Makefile 拿掉 `llm`（`DEPS_llm`、`LIBS`、`BINS` 三處） | 同乙；`py/entries.json` 加一列；install.py 程式不用改 | 同丙 |
| 好處 | 不花工 | C++ 少 1058 行 | C++ 少 1058 行＋標頭；問腦信格式只剩 Python 一份（可跟 kernel_llm 共用 priority、body 檢查）；符合 11-17「C++ 放 Linux 機制」 | 丙的好處＋每拍少開一個子行程；judge-llm、llm_forward 也不用再解析子行程的 stdout／stderr |

## 也想過、不推薦的

- **併進 agent-fsm（wait.py 自己寫信）**：等於乙，只是集中在 wait.py；judge-llm、llm_forward 還是要另一份。
- **併進 kernel_llm 當它的用戶端**：位置上合理（同一份協定），但 kernel_llm 是工具夾（`py/tools/aos/`），給別人 import 不順；放 `py/aos/` 共用模組、kernel_llm 也去 import 它比較乾淨。這是丁的一種擺法，不另列。

## 我的推薦

**丁，但不急**。理由：一、協定的兩頭（寄信端與 kernel）會在同一種語言、同一份程式碼裡，以後改信的格式只改一處——這是 11-13 kernel 改 Python 的同一個理由；二、符合使用者 11-17 定的「C++ 放與 Linux 機制牽扯的東西」，aos-llm 不是；三、效能不退反進（函式庫）；四、指令名、用法、錯誤行全留著，文件與舊抄本都不用跟。若只想少花工，**丙**是丁的前半段，先做丙、之後再把 wait.py 改 import 也行。**甲**完全可以接受：現在沒有壞、沒有痛點，速度也不是問題。**乙**不推薦。
