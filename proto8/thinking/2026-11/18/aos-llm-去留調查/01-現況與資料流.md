# aos-llm 現況與資料流：它是什麼、一次問腦經過哪幾支程式

← [README](README.md)｜下一份：[02-呼叫點清單](02-呼叫點清單.md)

## 先講結論

aos-llm 是一支 **C++ 的小郵差**：把一份問腦請求寫成一封信丟進 llm kernel 的信箱，再去自己的回信箱撿回信。**它不打 HTTP、不排隊、不重試、不管逾時、不管 cooldown**，那些都在 Python 的 llm kernel、endpoint 函數與 agent-fsm 的 wait 格裡。它本身大多是「把 aos-post 的寄信、認領包一層，加上問腦信的格式檢查和幾句提醒」。

## 它在哪、多大

| 項 | 內容 |

## 五個子指令

| 子指令 | 做什麼 | 誰在用 |
|---|---|---|
| `send --reply-to BOX` | stdin 的 body（`{"endpoint"?, "request": {"messages"...}, "priority"?}`）驗過，寄進 `$AOS_LLM_KERNEL/requests/`，印信件名稱；kernel 沒在跑就多印一行 warning、照寄 | agent-fsm 的 wait 格 |
| `recv [--full] [--quiet] BOX 名` | 到 BOX 找 `in_reply_to`＝那個名字的回信；沒到退 10；到了印 `message`（`--full` 印整份）並把回信收掉；回信是 error 就 stderr 一行、退 1；沒到時還會猜原因（kernel 沒跑、權限寫不進） | wait 格（每拍一次） |
| `ask [--full]` | 同步版：寄、等（每 20 毫秒看一次）、印；寄的時候建 `sender.flock` 鎖住到行程結束，kernel 靠它認「寄信的人還在」；收到 Ctrl-C 會撤信 | judge-llm、llm_forward、人手打、文件範例 |
| `regret 名` | 信還在 `new/` 就抽回 | 只有文件與測試 |
| `ls [--json] [--kernel]` | 讀 kernel 寫的 `endpoints.json` 列能力包；沒指定時從 daemon 表找唯一的 llm kernel | 人手打、知識庫叫 agent 用 |

## 一次問腦的路（start-api 範本，假腦或真腦都一樣）

```
agent 那台 daemon（aos-daemon，C++）每 300 ms 叫一次 agent 的 loop／fsm（aos-loop／aos-fsm，C++）
 │
 ├─ think 格  python3 brain.py（Python）：組好 $AOS_STACK/think/request.json
 │
 ├─ wait 格   python3 wait.py（Python）第一拍：
 │     aos-post init think/reply                          （C++）
 │     aos-llm send --reply-to think/reply < request.json （C++）← 這支
 │        → 信寫進 <llm kernel stack>/requests/new/<名>/letter.json
 │
 │   llm 那台 daemon（aos-daemon，C++）每 300 ms 跑一輪 kernel_llm（Python，py/tools/aos/kernel_llm）：
 │     認領 new/→cur/、排隊、看額度、請 daemon 把這封掛成一個 proc（aos-exec，C++）
 │       └─ endpoint 函數：llm_http（Python）POST 到 OpenAI 相容端點（例 LiteLLM 127.0.0.1:4000）
 │          或 llm_fake（Python 假腦）、llm_forward（Python，轉給下一台 kernel，內部叫 aos-llm ask）
 │       → 印 reply.json
 │     下一輪收成品、記帳，aos-post send --in-reply-to <名> think/reply（C++）寄回信
 │
 ├─ wait 格   之後每拍：aos-llm recv --full --quiet think/reply <名>（C++）← 這支
 │     沒到＝退 10 留在 wait；到了＝接進 history.jsonl → act 格
 │     出錯＝wait.py 自己判 cooldown、重送、停下（Python，agentlib/cooldown.py）
 │
 └─ act 格    python3 act.py（Python）跑工具 → 回 think
```

**要點**：這條路上 aos-llm 只佔兩個點（寄一次、每拍看一次），兩頭都是 Python（wait.py 叫它、kernel_llm 收它寄的信）。中間那封信的格式、排隊、回信，kernel 那側 11-13 已經全是 Python；只剩寄信端這一小段是 C++。

## 只有 aos-llm 才做的事（別處沒有現成的）

| 事 | 細節 | Python 有沒有現成的零件 |
|---|---|---|
| 問腦信 body 的格式檢查 | `request` 必須是物件、`messages` 是陣列、priority 形狀 | kernel_llm 收信時也驗一次（兩邊各一份） |
| 寄件人＝stack | 信封 `sender` 用 `$AOS_STACK` 優先（11-13 T31：一隻 agent 一份額度）；`aos-post send` 是 `$AOS_WS` 優先，直接換會變 | 沒有，要自己寫一行 |
| `sender.flock` | `ask` 鎖住到結束，kernel 據此丟掉「人已經走了」的信 | kernel_llm 的 `sender_alive` 已經是 Python 的另一半（`fcntl.flock`） |
| 照 `in_reply_to` 找回信 | aos-post 只會「照順序認領」，不會「找回給我的那封」 | 沒有命令列，要自己掃 `new/` |
| 沒回信時猜原因 | kernel 沒在跑（看 `state.json` 的 phase／pid）、BOX 權限寫不進 | 沒有，wait.py 另有一半（10 分鐘提醒、信不見了） |
| `ask` 撤信 | SIGINT／SIGTERM／SIGHUP 時把還在 `new/` 的信抽回 | 沒有 |
| `ls` 找 kernel | 讀 daemon 表（含分檔）找唯一 llm kernel | `agentlib/context_use.py` 已經自己讀 `endpoints.json`（只讀窗，不找 kernel） |

**沒有的**：串流（kernel 明擋 `stream: true`）、HTTP、逾時（交給 kernel 與 deadline）、重試與 cooldown（在 wait.py）、大檔（body 整份讀進記憶體寫一個 letter.json，跟 Python 一樣）。效能上它唯一的優勢是起得快（實測見 [04](04-方案比較與實測.md)）。
