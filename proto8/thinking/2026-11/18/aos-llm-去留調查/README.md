# aos-llm 去留調查（11-18）：還要不要它、要不要改 Python

← [2026-11-18](../README.md)

使用者 11-18：「對了，派個線去調查一下，是不是aos-llm這個東西不需要了，或是直接用python寫，其實更好」。線 llm-survey-1118 做，純調查、沒改程式；實測在公司 WSL 暫存複本（HEAD `0f1b7b7af`，`git archive` 取的）。

## 先講結論

1. **aos-llm 還在用，不能直接拿掉**：每隻 agent 每次問腦都經過它（agent-fsm 的 wait 格寄一次、每拍收一次），judge-llm 範本和 llm_forward 工具也用它的 `ask`。它是一支 1058 行的 C++ 小郵差：把請求寫成信丟進 llm kernel 的信箱、撿回信，外加幾件小事（寄件人算成 stack、鎖住表示「我還在等」、Ctrl-C 撤信、kernel 沒在跑時提醒一句、列能力包）。**它不打 HTTP、不排隊、不重試**，那些都已經在 Python。
2. **改 Python 是合理的，但不是為了快**：實測一次問腦來回約 1.3 秒，aos-llm 自己只佔約 25 毫秒；wait 格每拍本來就要起一次 Python（約 265 ms），aos-llm recv 只佔 1～4 ms。
3. **推薦丁案**：協定寫成一份 Python 函式庫，wait.py 等呼叫端直接 import；`aos-llm` 指令留著當它的薄殼（名字、旗標、退出碼、錯誤行全照舊）。這樣問腦信的格式只剩 Python 一份（跟 kernel 同語言，11-13 kernel 改 Python 是同一個理由），也合使用者 11-17 定的「C++ 放與 Linux 機制牽扯的東西」。工作量粗估 10～14 小時，C++ 少 1058 行。不急：甲（不動）也完全可以。
4. **注意**：11-17 改名施工的待裁 X-4，使用者選了 A「`directive json fsm llm` 不動」；改不改等於重新決定這一題。

2. （選丙或丁才有）**什麼時候做**：現在開線／等手上的線收完。
