# 發想（上）：在 Python REPL 裡做「條件成立 → 停 → 檢閱 → 續」，程式邊跑邊長——四個樣子的前三個

← [README](README.md)｜上一份：[07-怎麼把它停下來](07-怎麼把它停下來.md)｜續：[05-續-兩個問號與要你先說的題](05-續-兩個問號與要你先說的題.md)

照「需求不清時先發想」：這是頭腦風暴，不出施工圖、不排步驟、不定檔案格式。每案裡的 `$` 與 `>>>` 都是**示意，不是設計**，函式名隨手取的。第四個樣子、一覽表、推薦、要你先說的題在[續篇](05-續-兩個問號與要你先說的題.md)。

## 先講結論

1. **你說的斷點，今天不改 aos 任何程式就湊得出來。** 條件是一支普通程式（掛成 hook，或在外面當觀察者）；停是 `aos-agent ctl pause`；檢閱是讀 stack 的檔；續是 `ctl resume`。這四段 [07](07-怎麼把它停下來.md) 都實測過，續了不丟東西。
2. **你說的「發stop」，建議用 pause 這一招來做，不用 `ctl stop`。** pause 是行程不死、停在兩格之間、信照收；`ctl stop` 是行程真的退出、換 pid（續得回來，但動靜比較大）。hook 和外面的 proc 用的是同一招，所以「條件放哪」跟「怎麼停」可以分開想。
3. **四個樣子只差在「條件放哪」。** 甲是只用 shell 的對照組；乙把條件放在 agent 裡的 hook；丙把條件放在外面的觀察者；丁是兩者合用、收成一包現成的觸發器。hook 是「事情發生時被叫」，準；觀察者是「隔一陣子看一眼」，實測晚一格，但完全不碰那隻 agent，而且看得到跨好幾格、跨好幾隻的事。
4. **「程式邊跑邊長」在四案的走法都一樣**：停著的時候加工具、加 hook，寫在這隻自己的 stack 疊層，續了就生效；插一格 fsm 寫的是定義夾。條件不綁位置，所以後來長出來的工具，不指名的觸發器照樣看得到。
5. **還缺的只有一件小事**：停了以後表上只寫 `paused`，不說是誰、為什麼停的（[04](04-邊緣狀況.md) 第 28 條）。各案都是讓觸發器停的時候自己留一張字條來補。
6. **推薦（由你拍板）**：先讓你試乙，丙接著，丁是兩者用久了自然收成的樣子。**沒有要你先說的題**，理由在續篇。

## 四案共用的底：停、看、改、續

這一段四案都一樣，後面各案只寫不一樣的地方。

**停**：`ctl pause` 寫的是 agent 的控制窗（像在它桌上放一張「請暫停」的紙條），loop 在兩格之間看到就停。行程活著、stack 全在；表上顯示 `paused`。腦正在答的時候按也沒事：實測 0.4 秒內停住，答案先放在信箱，續了才收（07 的 T4）。

**看**：一句話版是 `aos-agent ctl state -t <名> all`；細的都是 stack 裡的普通檔——`stage.txt`（停在哪一格）、`history.jsonl`（對話與工具呼叫）、`observed.jsonl`（每次想、每次工具的流水帳）、`think/request.json`（最後一次問腦的整份）、`queue/new/`（堆著還沒收的信）。照你說的「畢竟我們都是狀態機了」，看這些就夠，不對回原始碼。

**改（也就是程式邊跑邊長）**：停著時加工具、換 system、加 hook、換腦，都寫在這隻自己的疊層（只記這隻改過什麼的那幾份檔），像程式跑起來後再載入的 lib，重生碰不到。要在指令中間插一格，改的是定義夾的 `fsm.json`，下一格就生效；它沒有疊層，所以用同一份定義的 agent 會一起變，`agent.py` 重生也會重寫它（事實表在 [06](06-使用者回應.md)）。停著的時候兩格之間沒有東西在跑，是插東西最不會踩到腳的時機（這句是推想）。

**續**：`ctl resume`。停著時寄來的信照收、堆在信箱，續了才處理；寄信的人等太久會先逾時（[04](04-邊緣狀況.md) 第 2 條）。

**三招不拿來當斷點**（07 第 4 點）：讓 hook 故意失敗，agent 會掛掉、被 daemon 連續重起、每次又撞同一個 hook（04 第 25 條）；Linux 的 `SIGSTOP` 凍得住也續得回來，但 aos 完全不知道它停了，表上照寫 running，各種期限照樣在倒數（第 26 條）；kernel 的 hold 只卡「起 proc」的信，停不了已經在跑的。

## 甲（對照組）：不做庫，只用 shell

```
$ cat stop_on_write.sh          # 一支普通程式：收到事件就叫 ctl pause --no-wait，再回 0
$ aos-agent hook add -t ann --event before_tool --condition write ./stop_on_write.sh
$ aos-agent say -t ann "整理 notes"
$ aos-agent ctl state -t ann all                       # 表上已經是 paused
$ aos-agent tools add -t ann -n math2 ./tools/math2    # 停著加一個工具
$ aos-agent ctl resume ann
```

- **條件放哪、用什麼停**：agent 裡的 hook；hook 程式裡一行 `ctl pause --no-wait`。這就是 07 的 T1，hook 機制一個字沒動：hook 發停後約 2 秒已停住，`stage.txt` 是 `think`。
- **停在哪**：這一格做完才停。在 `before_tool` 發的，那次工具照跑、結果寫進 history，停在下一格開頭。
- **邊跑邊長**：全用現成指令，同上面共用的那段。
- **好處**：今天就能用；零新概念；完全是你說的「一個普通程式，發現有問題就發stop」。
- **代價**：每個人各寫各的腳本。條件每次成立都會再停，要「只停一次」得腳本自己記，或停完就把 hook 拿掉。腳本寫壞了（退出碼不是 0）就變成「hook 失敗」，撞上第 25 條的連環重起。表上只有 `paused`，不知道是哪支腳本、為什麼停（第 28 條）。沒有 Python REPL。
- **合不合、會不會自然長、擋不擋 Lisp**：完全合；已經長出來了；不擋。

## 乙：條件是 agent 裡的 hook，aos-gdb 庫幫你裝、幫你問「為什麼停」

```
>>> import aos_gdb as g
>>> p = g.attach("ann")                               # 只是記住它的 stack 在哪
>>> p.stop_when("before_tool", tool="write", once=True)   # 現成的小條件
>>> p.stop_when("after_tool", prog="./too_slow.py")       # 你自己寫的普通程式當條件
>>> p.say("整理 notes"); p.wait_paused()
>>> p.why(); p.where()        # 哪個觸發器、什麼事件讓它停的；現在在哪一格
>>> p.add_tool("math2", "tools/math2")                # 就是 aos-agent tools add
>>> p.resume()
```

- **是什麼**：把甲收成一個薄殼。`stop_when` 做的事就是「把一支會發停的小程式掛成這隻的 hook」；條件可以是庫裡現成的（哪個事件、哪個工具、信裡有哪個字），也可以是你自己寫的任何可執行檔。庫的每個方法背後是一條 shell 指令或讀一個檔，所以 REPL 和 shell 可以混著用，就是你說的「python repl + shell指令」。
- **條件放哪、用什麼停**：agent 裡的 hook，掛在這隻自己的疊層，下一個事件就生效、不用重起（[02](02-aos現況.md) 實測）；停用 `ctl pause`。
- **比甲多做的三件小事**：一、觸發器發停的同時在 stack 留一張字條（誰、哪個事件、當時的內容），`p.why()` 就是讀它，補第 28 條；二、「只停一次」由觸發器自己記；三、把你寫的條件程式包一層，它自己壞掉時不讓 hook 變成失敗，避開第 25 條。
- **停在哪、看什麼**：同甲，這一格做完才停。hook 是事件當下被叫的，所以條件看得到「當下」的東西：腦點了哪個工具、參數是什麼、信的內容。這是「下一步看不到」能看到的最早一刻。要是哪天需要「工具還沒跑就攔住」，hook 本來就能擋下那一次（回 10）或改參數（[02](02-aos現況.md) 實測），那是加在觸發器裡的另一個動作，不是另一套機制。
- **邊跑邊長**：停著時 `p.add_tool`、`p.stop_when` 再加新的觸發器，都寫疊層。新加的工具，不指名工具的觸發器（例如「任何工具回了錯誤行」）照樣看得到它，不用另外補（推想：hook 的工具名條件本來就是選填）。插 fsm 格可以包成一個方法，但它寫的是定義夾，方法名和說明要讓人看得出這點。
- **好處**：最貼你這次的原話；全部是既有概念（hook 是任何可執行檔、設定在疊層、檔案即狀態）；REPL 關掉也沒事，觸發器還掛著、停住的那隻誰都能用 shell 續；agent 的程式不用改。
- **代價**：只看得到單一事件當下，「連續三次都失敗」「半分鐘沒動靜」這種跨好幾格的條件，hook 得自己記帳。每個事件多起一支小行程。eca 身（claude、codex 當腦）自己的工具 hook 攔不到（04 第 13 條）。停著時進來的信，續了之後可能馬上又觸發一次。
- **會不會自然長、擋不擋 Lisp**：會，甲被用第二次就會收成這樣。不擋：條件是可執行檔，Lisp 寫的也行；薄殼換一層就好。

## 丙：條件在外面，另開一個觀察者盯著，agent 完全不碰

```
>>> p = g.attach("ann")
>>> w = g.watch(p, every=0.2)                         # 觀察者：隔一陣子看一眼它的檔
>>> w.stop_when(lambda s: s.tool_calls("write") >= 3)         # 條件是 REPL 裡的一個函式
>>> w.stop_when(lambda s: s.brain_tokens > 50_000, times=2)   # 連續兩次看到才算
>>> p.say("整理 notes"); w.wait()
>>> w.why()                   # 哪一條條件、看到什麼
>>> p.resume()
```

- **是什麼**：你說的「另外開個proc，觸發之後直接把要debug的那個proc停下來」。觀察者讀的是 agent 寫出來的檔（工具流水帳、對話、現在哪一格、信箱、腦的帳本與用量），條件成立就叫同一招 `ctl pause`。
- **實測**：07 的 T7，一支 15 行的 bash 每 0.2 秒看一次 `observed.jsonl`，看到新的工具紀錄就發停，說話後約 2.5 秒停住，停在 `think`。
- **停在哪**：**晚一格**（04 第 27 條）。觀察者看到「工具跑過了」的時候，工具已經跑了，停在下一格開頭；看一眼的間隔越長就越晚。今天沒有「檔一變就通知」的機制，只能隔一陣子看。
- **好處**：被除錯的那隻一個檔都不用動，連 hook 都不用掛。條件可以跨好幾格（次數、多久沒動、用量累計）、跨好幾隻 agent（A 在等 B 的回答、B 卡住了）。條件就寫在 REPL 裡，隨手改、隨手換。防誤停的「連續 N 次才算」是外部監看的常見做法（[03-續二](03-續二-條件觸發.md)），放在觀察者這邊最順。觀察者壞了不會害到 agent，沒有第 25 條的問題。
- **代價**：攔不到「事前」，只能事後停。觀察者是另一個要顧的東西：它跟著 REPL 活，REPL 關了就沒人盯，已經停住的那隻還是 `paused`、誰都能續，還沒停的就不會再被停；它要是做成掛在 daemon 上的 proc，自己也會被暫停、也會掛（04 第 8 條）。表上同樣只有 `paused`，原因得靠觀察者留的字條。
- **邊跑邊長**：同共用那段。另外，觀察者自己也能邊跑邊長——停著的時候在 REPL 多加一條條件，不用碰 agent。
- **合不合、會不會自然長、擋不擋 Lisp**：合（檔案即狀態；被看的那隻不知道有人在看）。會自然長，第一次想盯「跨好幾格的事」就會寫出來。不擋 Lisp：條件函式是 Python 寫的，但它不留任何東西在 agent 身上，換成 Lisp 寫的觀察者，底下還是同一招 `ctl pause`。
