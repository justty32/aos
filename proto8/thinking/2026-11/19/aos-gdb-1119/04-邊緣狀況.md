# 邊緣狀況：在 aos 裡停住、單步、插新指令、重播時會撞到的事（28 條）

← [README](README.md)｜上一份：[03-續-REPL與邊跑邊改](03-續-REPL與邊跑邊改.md)｜下一份：[05-發想](05-發想.md)

標「實測」的在 `~/.aos/scratch/aos-gdb-1119/` 有 log；標「讀程式」的有出處；其餘是推想。只列出來，不解；使用者沒回答的不追問。

## 先講結論

- **最常撞到的三條**：停在斷點時從外面看不出來（第 1 條）、停一隻時信照樣進來而且下一封又撞同一個斷點（第 2 條）、腦的回答不重現所以「重跑」不等於「重播」（第 9 條）。
- **第 16 條改寫過**：第一輪把「插進 json 的東西重生就沒了」當成跟庚的「C 與 .o」衝突；使用者回「.o也可以在運行途中給自己加lib啊」，所以不是衝突，只是「加法寫在哪」的事實（[06](06-使用者回應.md)）。
- **第二輪停法實測多出四條**：第 25～28 條（hook 失敗會連環重起、SIGSTOP 沒人知道、觀察者晚一格、pause 不說是誰）。

## 一、停住的時候

1. **停在斷點上，外面看不出來**（實測 09.log）：`before_tool` hook 等著時，`ctl state` 照寫 `running`、`ctl ls -l` 沒標記。另一個人（或另一隻 agent）會以為它在想，可能去 `ctl stop` 它。
2. **信照樣進來，而且會再撞**（實測）：停著時 `say` 的信照收；放行第一個斷點後，第二封信的工具呼叫又停在同一個斷點，寄件人的 `listen` 逾時回 `AnswerMissing`。斷點是「每次都停」，沒有「只停一次」。
3. **停住的 agent 佔著東西**：行程活著（記憶體、行程數照算進 `limits`）；它在 kernel 的格子（掛 proc 那包的 `max_running`）也佔著。停太久會讓排隊的別人看起來卡住。
4. **期限會過**：問腦信可帶期限；掛 proc 的 `held` 會驗寄件人期限——停太久，kernel 自己會拒掉（昨天 [aos-compile 06](../../18/aos-compile-1118/06-除錯與停下來看資源.md) 第四節第 3 條）。
5. **hook 的逾時**：預設 60 秒，逾時算 hook 失敗，`on_error: stop` 會讓 agent 停下。除錯用要給 0（不限時，`py/aos/hook_run.py` 第 149 行），但給 0 之後**人走開了它就永遠等**。`after_start`／`after_stop` 另受 `aos-loop` 的 `on_timeout_ms`（預設 5 秒）管，兩層逾時哪個先到未實測。
6. **pause 停不進一格中間**（實測）：pause 是這輪做完才停；要停在「腦答完、工具還沒跑」只能靠 `before_tool`；要停在「問腦送出前」得靠 kernel 的 hold。
7. **多隻互相等時停一隻**：A 在等 B 的回答（`subagent` 工具或信），B 停在斷點——A 的工具呼叫一直不回，A 自己的逾時可能先到。兩層都停住時要分得清誰在等誰。
8. **除錯器自己是不是一隻 agent**：如果 aos-gdb 本身是掛在 daemon 上的 proc（像 `kernel_gate` 那樣由 agent 審），它也會被 pause、被清道夫看到、會掛；它掛了，被它停住的全部卡住。如果是人在 REPL 裡跑的普通程式，REPL 關掉時被停住的 agent 要有人放行。

## 二、重跑、重播、單步

9. **腦的回答不重現**：同一份 `think/request.json` 再問一次，答案可能不同。「重跑這一格」＝再問一次；「重播這一格」＝拿錄下的答案。兩者要分開叫。
10. **重播要不要真的再問腦**：真問＝花錢、吃額度（`BudgetMissing`）、答案可能變；不問＝要有錄好的答案。aos 有劇本腦（`llm_fake`＋`script`），但要有人把 history 轉成劇本；這台公司機沒有真模型端點，只能假腦。
11. **單步時工具有副作用**：已經寄出的信、已經寫的檔、已經起的 proc，重跑會再做一次。Temporal 靠「activity 只做一次、結果記下」，LangGraph 明說恢復時節點從頭重跑、副作用要冪等。aos 要嘛錄、要嘛在複製出來的暫存樹裡重來。
12. **手打 `aos-exec fsm.json` 跟 loop 搶**：loop 還在跑時手打，兩邊同時推同一個 `stage.txt`。要先 `pause` 或 `stop`。手打還要自己設 `AOS_LLM_KERNEL` 等環境變數（實測 wait 格回 `LlmKernelMissing`）。
13. **eca 身裡面看不進去**：claude、codex 的內建工具（Bash、Edit…）不經 aos，`before_tool` 攔不到；只有經 `aos-mcp --hooks` 服務的 aos 工具攔得到（讀 `py/aos/apps/eca/__init__.py` 第 44～47 行，未實測）。eca 身的「一步」是一整回合。

## 三、程式邊跑邊長、插新指令

14. **`fsm.json` 沒有疊層**（實測）：要在一隻 agent 的指令中間插一格，只能改定義夾，用同一份定義的所有 agent 一起變。工具、system、hook、llm 有「這隻自己的」疊層，fsm 沒有。
15. **`loop.json` 只讀一次**（實測）：改了節拍、改 `exec`，要重起 loop 才生效；`fsm.json` 每格重讀，會立刻生效。兩份檔看起來同一層，生效時機不同。
16. **加法寫在哪，決定重生碰不碰得到**（第二輪改寫）：庚的「C 與 .o」——重生直接蓋定義夾裡 `agent.py` 宣告到的檔。使用者說這跟程式持續增長不衝突：「.o也可以在運行途中給自己加lib啊」。事實是：`tools add`、`self_tools`、`system set`、`hook add`、`llm set` 寫在這隻的 stack 疊層（像跑起來後載入的 lib），重生碰不到；在 `fsm.json` 插格、`agent_def tools` 等寫在定義夾，重生會蓋。逐項表在 [06](06-使用者回應.md)。剩下的小邊緣只有一條：同一個「加一個工具」有兩條路、落點不同，人不一定記得自己走的是哪條。（庚那邊 [11](../aos-compile-庚/11-跟除錯那條線的接點.md) 仍把它列為待解的邊緣狀況，本線不改它的檔。）
17. **插入沒有紀錄**：疊層檔只有現在的樣子；定義夾被改了也沒痕跡（除非在 git 裡）。事後看 backtrace，對不回「那時候的程式長什麼樣」。Pharo 用 `.changes` 記、Jupyter 沒記所以畫面跟狀態脫鉤（[03-續](03-續-REPL與邊跑邊改.md)）。
18. **生成時加的除錯觸發器管不到後來插的**：使用者說「編譯時加 debug flag」的實際意思是生成時多一個選項、多生一些除錯用的觸發器（[06](06-使用者回應.md) 第 6 條）。那些觸發器（例如 hook）寫在定義夾，跑到一半插進疊層的工具、格不會自動帶上。旗標放哪他說「後續自然而然就知道」，這條只記下。

## 四、符號表（json ↔ 原始碼行）

使用者第二輪說「不必一定要全部對回原始碼，畢竟我們都是狀態機了」——下面三條降級為「做不做都行」時的參考，不是缺口。

19. **今天全 repo 沒有出處 key**（讀程式）：找不到 `_from` 一類；最近的是 `agent_def new` 在 `_metainfo.json` 記 `lineage`、hook 清單完成時補的 `from`（清單檔路徑，`hook_run.py` 第 76 行）。
20. **加 key 本身不會壞東西**：C-48「不認得的 key 一律忽略不報錯」，所以在生成的 json 裡多一個出處 key，跑的程式都不會在意。但 `stage.txt` 只寫格名、事件只帶工具名，要從「停在哪」反查到出處，得再查一次 json。
21. **一行原始碼對多個 json 位置、或反過來**：庚的 `agent.py` 一行 `TOOLS = [...]` 生出整份 `tools.json`；`FSM` 一個字典生出整份 `fsm.json`。行號粒度可能太粗。

## 五、權限與機器

22. **誰都能附身**：全部 agent 跟使用者同一個 Linux 帳號，任何 agent 都能對別隻 `hook add`、改它的 stack、讀它的 history（[linux-as-hw](../../18/linux-as-hw-1118/01-對照表.md)）。除錯器的「附身」沒有門檻，也就擋不住別的 agent 拿同一招。使用者 11-18 晚已裁「先做防呆、模型可信」，這條只記下。
23. **兩台機器**：REPL 在一台、樹在另一台時，「讀 stack 的檔」要走網路或共享資料夾；hook 是在樹那台起的行程，要等的「放行」訊號得跨機器送過去。
24. **Python 綁內部**：從 REPL 直接 `import aos.apps.agent.say` 用，是綁在不承諾的內部函式上；`install.py` 換掉 `lib/` 之後，已經 import 的 REPL 還拿著舊模組（Python reload 的老坑）。

## 六、第二輪停法實測多出來的（[07](07-怎麼把它停下來.md)）

25. **hook 失敗會連環重起**（新測 T2）：hook 退 1、`on_error: stop` → 那格報 `HookFailed` → loop 結束 → daemon 自動重起 → 又撞同一個 hook，0.7 秒內 4 次，然後「not restarting again」。拿「hook 失敗」當停法會讓 agent 掛掉、表上記一筆重起失敗；乾淨的停法是 hook 裡叫 `ctl pause`。
26. **SIGSTOP 沒人知道**（新測 T5）：整個行程群被凍住時，daemon 表、`state.json`、`ctl state` 全程照寫 running；別人看到「running 卻不動」。凍著時 hook 的逾時、fsm 格的 `timeout_ms`、kernel 的期限照樣用牆上時間在算。C-04 也說 Linux 那邊的事交給 daemon，aos 之上不直接碰。
27. **觀察者晚一格**（新測 T7）：外面輪詢的 proc 看到「工具跑過了」時，工具已經跑了；pause 停在下一格。要停在事情發生「之前」，條件得放在 agent 裡的 hook（`before_tool`、`before_queue`）。輪詢間隔越長越晚。
28. **pause 不會說是誰、為什麼**：表上只有 `paused`。一個人手動 pause、一個觀察者因條件 pause、agent 自己 `self_ctl` pause，看起來一樣；誰該按 resume 不清楚。
