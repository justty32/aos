# 別人怎麼做（補）：「條件觸發式」除錯——條件成立就停或記，尤其「觀察者在外面、目標不用改」這一類

← [README](README.md)｜上一份：[03-續-REPL與邊跑邊改](03-續-REPL與邊跑邊改.md)｜下一份：[04-邊緣狀況](04-邊緣狀況.md)

使用者第二輪的斷點定義：「特定條件發生時，暫停loop或fsm，停下來等待檢閱」，條件由 hook 或另一個 proc 判斷（[06](06-使用者回應.md)）。11-19 子 agent 上網查證，網址都實際打開過；沒讀到的照實標。

## 先講結論

- **這在別人那邊是很常見的分工**：條件與動作都放在外面、目標程式不改——gdb 的條件斷點加 `commands`、Erlang 的 trace 加 `sys:suspend`、DTrace 的條件加 `stop()`、monit 的 if-then、混沌工程的「穩態不成立就中止」。aos 的 hook 與觀察者 proc 是同一種分工。
- **防誤報的現成設計**：「連續 N 次才算」「一段時間內幾次才算」（monit 的 `for N cycles`、k8s 的 `failureThreshold`、Erlang supervisor 的 intensity／period）。單次就停容易誤停。
- **停了能不能續，要先決定**：AWS FIS 的停止條件一觸發，實驗就**不能續**；LangGraph 的 interrupt 靠 checkpoint 才能續；aos 的 `ctl pause` 是能續的那種（[07](07-怎麼把它停下來.md) 實測）。
- **外面看檔天生晚一點**：輪詢的觀察者看到條件時，目標可能已多走一格（aos 實測正是晚一格）；要停在事前，得讓目標在每個邊界自己看一眼（aos 的 hook）。

## 各家

**gdb 條件斷點與 `commands`**：`break 位置 if 條件`，或事後 `condition 編號 條件`；條件由 gdb 在每次命中時算（某些遠端目標可把條件下放到目標端算）。`commands 編號 … end` 讓斷點命中時自動跑一串指令，第一行 `silent`、最後 `continue` 就變成「命中、記一筆、繼續」不停。tracepoint 則只收集資料、不停（只適用遠端目標）。<https://sourceware.org/gdb/current/onlinedocs/gdb.html/Conditions.html>、<https://sourceware.org/gdb/current/onlinedocs/gdb.html/Break-Commands.html>、<https://sourceware.org/gdb/current/onlinedocs/gdb.html/Tracepoints.html>

**Erlang：trace pattern＋`sys:suspend`＋supervisor**：`dbg:tpl` 加 match spec 指定「哪些呼叫要產生追蹤訊息」，判斷在 VM 裡、目標程式不改；追蹤訊息送給 tracer 行程，tracer 看到條件成立就 `sys:suspend` 停那個行程（這個組合是兩頁各自的功能拼起來的，官方沒寫成一條配方）。supervisor 在 period 秒內重起超過 intensity 次就整組停、往上報。<https://www.erlang.org/doc/apps/runtime_tools/dbg.html>、<https://www.erlang.org/doc/apps/stdlib/sys.html>、<https://www.erlang.org/doc/apps/stdlib/supervisor.html>

**看門狗類（外部監看）**：systemd 的 `WatchdogSec` 要目標定期報平安，沒報就送訊號、可重起（目標要改）。monit 每個輪詢週期檢查 `if <條件> then <動作>`（alert、restart、stop、exec），可設「連續 N 次才算」；目標不改。supervisord 的 event listener 是外部程式，訂閱行程狀態事件與定時 tick，自己決定要做什麼。<https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html>、<https://mmonit.com/monit/documentation/monit.html>、<https://supervisord.org/events.html>

**eBPF（bpftrace）與 DTrace 探針**：探針掛在函式進出或事件上，`/條件/` 寫在探針後，判斷在核心裡、目標不改、事件驅動。bpftrace 的 `signal("SIGSTOP")` 可停目標（要 `--unsafe`，官方沒保證停在探針那一刻）；DTrace 的 `stop()` 讓觸發的行程在下次離開核心時停住，方便接 gdb，要明確開「破壞性動作」。<https://github.com/bpftrace/bpftrace/blob/master/docs/language.md>、<https://github.com/bpftrace/bpftrace/blob/master/docs/stdlib.md>、<https://docs.oracle.com/en/operating-systems/oracle-linux/dtrace-guide/dtrace-ref-ActionsandSubroutines.html>

**執行時驗證（invariant monitor）**：JavaMOP 把性質寫成規格、織進程式，違反時跑自訂處理（監控碼與目標同行程；官方站沒打開，只讀到論文頁）。TLA+ 的 trace validation 是事後把執行紀錄對到規格，檢查有沒有走出允許的範圍——不停目標、事後才知道。<https://arxiv.org/abs/1112.5761>、<https://docs.tlapl.us/using:tlc:trace_validation>

**混沌工程的中止條件**：Chaos Toolkit 的 steady-state hypothesis 由探針加容許範圍組成，可持續檢查、一偏離就判失敗並中止。AWS FIS 的 stop condition 指向一個 CloudWatch 警報，警報響就停實驗，**停了不能續**。<https://chaostoolkit.org/reference/usage/run/>、<https://docs.aws.amazon.com/fis/latest/userguide/stop-conditions.html>

**加分**：k8s 的 liveness／readiness probe 是外部定期探測，失敗幾次才處置。LangGraph 的 `interrupt()` 可以寫在節點的條件分支裡，條件由目標自己判斷，靠 checkpoint 續。<https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/>、<https://docs.langchain.com/oss/python/langgraph/interrupts>
