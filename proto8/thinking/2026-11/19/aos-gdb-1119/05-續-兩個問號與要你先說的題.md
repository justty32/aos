## 丁：hook 當感應器、觀察者當裁判，收成一包現成的觸發器

```
>>> p = g.attach("ann", debug=True)       # 一句話掛上一整包除錯用的觸發器
>>> p.triggers()                          # 工具回錯誤行、腦失敗、同一個工具連叫 N 次、太久沒動靜…
>>> p.trigger("tool_error").action = "log"    # 這一個改成只記一筆、不停
>>> p.say("把上個月的帳加總"); p.wait_paused()
>>> p.why()                               # 停因：tool_error   math: error: ArgBad …
>>> p.add_tool("sum_csv", "tools/sum_csv")    # 發現缺一個工具，當場補上
>>> p.resume()
```

- **是什麼**：乙和丙合起來用，再把常用的條件收成一包。這就是你說的「可以加個選項，選了之後就會添加一些除錯用的觸發器」——這包東西本身只是一組可以掛上去的普通程式，在 REPL 裡是一句話掛上；哪天生成時要有那個選項，做的事也只是「把同一包掛上」。所以旗標放哪一層，這包都用得上，可以照你說的後續自然知道。生成那邊怎麼接，是你之後看 aos-compile 時的事，這裡不替你想。
- **條件放哪**：兩邊各管擅長的。看「事件當下」的放 hook：工具回了錯誤行（`after_tool`）、腦失敗（`brain_failed`）、某個工具要被叫（`before_tool`）、某種信要進來（`before_queue`），hook 可以當場發停，也可以只把事件記一筆。看「跨好幾格」的放觀察者：同一個工具連叫 N 次、多久沒動靜、用量累計、另一隻 agent 在等它。「定時看一眼」還有第三種放法：aos 的 `on_clock` hook 是在 agent 裡、每隔幾格或幾毫秒被叫一次（[07](07-怎麼把它停下來.md) 第四節），不用另開行程。
- **用什麼停**：全部同一招 `ctl pause`。因為停法只有一種，同一隻被 hook 和觀察者同時叫停也只是停一次；兩邊各留一張字條，`p.why()` 一起讀出來。
- **觸發後不一定要停**：你原話是「把他停下來(或是不停)」。每個觸發器的動作可以是「停」或「只記一筆」；gdb 也有「命中、記一筆、繼續」的用法（[03-續二](03-續二-條件觸發.md)）。先全掛成只記，看一輪之後再決定哪幾個值得停，比較不會被誤停煩到。
- **停住時看什麼、改什麼**：同共用那段；多一樣是字條上的「停因」。最常見的情況會是「工具回了錯誤行」或「腦一直叫同一個工具」——這通常就是發現萬能函數缺一個零件的那一刻，停下來補一個工具或插一格寫死的程式格，再續。這正是你說的新範式：每停一次，程式多長一塊。
- **邊跑邊長**：同共用那段。這一案特別要提的是 [04](04-邊緣狀況.md) 第 18 條：事先掛好的觸發器管不管得到後來才加的東西？條件型的觸發器只要不指名（「任何工具回錯誤行」），後加的工具自動算在內；指名的（「`write` 被叫」）就只管那一個，新工具要自己再加一條。這是推想，沒有另外實測。
- **好處**：不用事前知道斷點該下在哪，這對「下一步看不到」最對症——不猜它下一步做什麼，只等「出事了」的訊號。兩種放法互補：hook 準、觀察者看得廣。離 Lisp 那種「出錯時停在原地、看要怎麼接下去」的體驗最近（[03-續](03-續-REPL與邊跑邊改.md)）。
- **代價**：一包觸發器一旦有人用，裡面每一個的名字和意思就不好改。觸發器多了會誤停，得有「連續幾次才算」和「只記不停」來調。同時掛很多 hook，每個事件要多起好幾支小行程。只抓得到「看得出異常」的毛病，沒報錯但做錯的，還是得自己寫條件。乙、丙的邊緣它都繼承：hook 那半要防條件程式壞掉引起連環重起（04 第 25 條），觀察者那半晚一格（第 27 條），停因靠字條（第 28 條）。
- **合不合、會不會自然長、擋不擋 Lisp**：合，用的全是既有的零件。半自然：乙和丙各自用久了，重複的條件會被收成一包，但「哪些該進這一包」要有人挑。不擋 Lisp：包裡是可執行檔和一招 `ctl pause`，外面那層換什麼語言都行；動作清單那種體驗反而是 Lisp 遠景的預演。

## 推薦（是推薦，由你拍板）

1. **先讓你試乙。** 它就是你這次說的那句話的直譯：條件主要由 hook 承載、是一支普通程式、發現有問題就發停、hook 不用動。零件 07 都實測過，比甲多的只有「留字條」「只停一次」「條件程式壞了不連累 agent」三件小事，這三件正好補掉實測撞到的三個邊緣。
2. **丙接著做，而且做得很薄。** 它是你說的「不拘泥於 hook」那一半，15 行 bash 就驗證過。它補乙看不到的東西：跨好幾格、跨好幾隻的條件。兩案用同一招停，所以先後做不會互相卡住。
3. **丁不另外設計，讓它從乙、丙長出來。** 哪些條件值得收進那一包，等你實際用乙、丙停過幾次之後才看得出來；現在先定一包，多半會挑錯。
4. **停一律用 `ctl pause`。** 理由在 07：行程不死、兩格之間、信不丟、表上看得到 `paused`、hook 和外面的 proc 都叫得動。hook 故意失敗、`SIGSTOP`、kernel 的 hold 都不拿來當斷點。
5. **薄殼就好。** aos-gdb 的每個動作背後是一條 shell 指令或讀一個檔，這樣 REPL 和 shell 才能混著用，之後換成 Lisp 也只是換掉最外面那一層。

## 要你先說的題

**沒有要你先說的題。** 你這次已經把方向說完了：斷點是「條件成立就停」、條件主要由 hook 承載而 hook 不動、不必對回原始碼、另開 proc 也可以、旗標放哪之後自然知道、程式持續增長跟「C 與 .o」不衝突。照這些就能直接做出乙讓你試，試了之後你想改什麼再說。

[06](06-使用者回應.md) 留下「待判斷要不要問」的四件，逐一看過，現在都不需要你定，先照下面的走，用到再說：

1. **aos-gdb 的本體是檔案與指令，還是 Python 物件？** 先照「檔案與指令為本，Python 是薄殼」。在這次的方向下這幾乎不是選擇：停是 `ctl pause`（一條指令、寫一個檔），條件是普通程式，本來就不是 Python 物件。唯一活在 Python 裡的是丙案寫在 REPL 的條件函式，它不留東西在 agent 身上，REPL 關了頂多是沒人盯。
2. **在 fsm 中間插一格只能改共用的定義夾。** 先照今天的樣子：插格就是改定義夾，用同一份定義的 agent 一起變，重生會重寫它。事實已經攤在 06 的表裡；它跟 aos-compile 有關，那塊你說之後來看。等真的常常要「只替這一隻插格」的時候再談。
3. **停住時外面看不看得見？** 改用 `ctl pause` 之後，表上本來就會顯示 `paused`，別人不會以為它還在跑。剩下的只有「是誰、為什麼停的」，先照「觸發器自己留字條、`p.why()` 讀它」，不動 aos 現有的程式。要不要讓表和全景頁也顯示原因，等有第二個人或另一隻 agent 會看到它的時候再說。
4. **重播要不要拿錄好的腦答案？** 這次的主軸是「停下來當場看、當場補」，沒有重播。先不做；哪天想「同一步反覆試」再回來談。
