## 先講結論

1. **板子到應用程式那半段，aos 幾乎每格都有**（daemon＝板子、aos-exec＝bootloader、kernel 站＝作業系統、定義夾＝可執行檔、stack＝記憶體）；**除錯那半段是零件很多、沒有成品**——沒有一個坐下來就能停、看、改、續的駕駛座，沒有符號表，也沒有 REPL（[01](01-對照表.md)）。
2. **你的直覺對：aos 的「下一步」事前看不到，所以斷點只能下在邊界上**。fsm 的格與箭頭事前畫好了，但走哪條箭頭、腦點哪個工具，要等腦決定。能停的邊界有四個：一拍、一格、一次工具呼叫、一封給 kernel 的信；step、backtrace、斷點位置都要照「邊界」重新定義（[02](02-aos現況.md) 第一節）。
3. **你想像的流程，最陽春的版本今天就做得出來**：實測一支十來行、會等「放行檔」的 `before_tool` hook 就是斷點——agent 真的停在「腦決定叫工具、工具還沒跑」那一刻，停多久都能接續；不用重起就掛得上（[02](02-aos現況.md) 第三節）。差的是：外面看不出它停住（`ctl state` 照寫 running）、沒有正式的放行通道、斷點每次都停、停的地方對不回原始碼。
4. **「邊跑邊長」今天大半做得到而且不用停**：加工具、換 system、加 hook 寫在這隻自己的疊層，下一輪生效；在 `fsm.json` 插一格，下一格就生效。例外：`loop.json` 只在起跑讀一次；`fsm.json` 沒有「這隻自己的」疊層，插格等於改共用的定義（[02-續](02-續-插入與Python.md)）。
5. **從 Python 驅動**：`aos` 套件 import 得到，但沒有給人用的 API，函式都是「吃命令列參數、印到螢幕」的形狀；今天 REPL 裡最穩的是 `subprocess` 叫指令加直接讀 stack 的 JSON（[02-續](02-續-插入與Python.md) 第二節）。
6. **別人的作法**（[03](03-別人怎麼做.md)、[03-續](03-續-REPL與邊跑邊改.md)）：跟 aos 最像的是 Erlang（停一隻、看、改、續，別隻照跑）；跟你想像最近的是 Lisp 的 SLIME＋condition／restart（出錯停在原地、列出可以怎麼接下去、現場改了再續）；「重播不花錢」要像 rr、Temporal 把腦的回答當錄下來的輸入。另外 LangGraph、OpenAI Agents SDK 官方都沒說能「跑著時加新工具」，aos 這點反而走在前面。
7. **最該你注意的邊緣**（[04](04-邊緣狀況.md)，24 條）：跑到一半插進定義夾 json 的東西，依今天庚的「C 與 .o」裁定，下次從 `agent.py` 重生就**無聲消失**；插在疊層的不受影響，但人不一定分得出自己插在哪。
8. **六個樣子**（[05](05-發想.md)）：甲 shell＋會等的 hook 腳本（對照組）、乙 斷點是一個檔、Python 只是薄殼、丙 斷點是一個 Python 函式、丁 REPL 當 loop 一格一格手搖、戊 出錯才停、列出可以怎麼接下去、己 不停全錄、事後翻帶子（對照組）。兩個大分岔：斷點活在檔裡還是 Python 物件裡（決定 REPL 關掉會不會出事、擋不擋將來用 Lisp）；靠停下來還是靠錄下來。
9. **你的兩個問號**（[05-續](05-續-兩個問號與要你先說的題.md)）：斷點是不是 hook——工具呼叫與收信這兩層是，**格這一層不是**（九個事件裡沒有「某一格開始前」），跟你昨晚「主要是loop那邊」有落差；debug 旗標可放生成時、插入時、執行時三層，不互斥，跟「C 與 .o」最合的是執行時，能回答「當時程式長怎樣」的只有插入時記一筆。
10. **推薦（由你拍板）**：乙當底、丁當 loop 層的第一個動作、戊做成乙上的一種斷點、丙只當薄殼、己先只錄不重播。**要你先說的七題**在 [05-續](05-續-兩個問號與要你先說的題.md) 末節，第一題是「斷點先顧哪一層」。
