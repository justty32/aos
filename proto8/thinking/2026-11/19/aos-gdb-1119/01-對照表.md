# 對照表：現代軟體棧「從買板子到除錯」每一格 ↔ aos 的對應物（有沒有、在哪、貼不貼）

← [README](README.md)｜上一份：[00-使用者原話](00-使用者原話.md)｜下一份：[02-aos現況](02-aos現況.md)

## 先講結論

- **前半段（板子、開機、kernel、行程、程式格式、編譯器）aos 幾乎每格都有對應**，而且大多早就寫進[板子比喻](../../../../docs/CONCEPTS/附錄1-續-板子比喻.md)。
- **後半段（除錯、觀察、REPL）是零件很多、沒有成品**：看狀態、停、單步、攔截、事後看，各自都有一個指令或一個檔做得到（[02](02-aos現況.md) 實跑過），但**沒有一個把它們串起來、讓人坐在一個地方操作的「gdb」**，也**沒有符號表**（這一步對到原始碼哪一行）和 **REPL**。
- **最貼的除錯比喻不是 gdb，是 Erlang 的 shell＋`sys` 模組**：gdb 停的是「一行機器指令」，aos 能停的最細是「一格狀態機」「一次工具呼叫」「一封信」——都是邊界，不是任意一行。原因是 agent 的「腦」在模型那邊，aos 看不到它裡面（像 gdb 看不進一顆加密晶片）。
- 標記：**有**＝有程式在用；**半**＝有零件或做一半；**無**＝沒有；**對不上**＝比喻本身不成立，照實寫。

## 一、從買板子到跑起應用程式

| 買板子、通電 | 一塊會自己跑的硬體 | **root daemon**（`aos-daemon`）：顧一張 proc 表，起、重起、停、報狀態 | 有 | `cpp/aos-daemon/`；起手包 `templates/start-api/` |

## 二、觀察與除錯（這次的重點）

| 現代軟體棧 | 白話與比喻 | aos 的對應 | 有？ | 在哪 |
|---|---|---|---|---|
| **gdb（整套）** | 一個讓你停住、看、改、繼續的駕駛座 | **沒有成品**。零件散在 `aos-agent ctl`、`hook`、`history`、手打 `aos-exec` | 半 | 見 [02](02-aos現況.md) 第五節逐件 |
| attach（附身到在跑的程式） | 不用重開，直接接上 | 不需要附身：狀態本來就是檔，誰都讀得到；「接上」＝指定 `-d <stack>`、`-t <名>` | 有（天生） | 任何 `aos-agent -t` |
| 中斷點 break | 跑到這裡就停 | **hook**：`before_tool`（工具要跑前）、`before_queue`（信要進對話前）可看、可改、可擋；kernel 的 `after_verdict` 可回 hold。**但都是「看一眼再放行／擋掉」，不是「停住等人」**——hook 回之前 agent 確實停著，所以「停住等人」得靠一支會等的 hook（`timeout_ms: 0`＝不限時） | 半 | `py/aos/hook_run.py`、`py/aos/agentlib/hooks.py` |
| 單步 step／next | 一次走一步 | 一格：不起 loop，手打 `aos-exec fsm.json` 一次推一格（實測） | 有 | `cpp/aos-fsm/` |
| continue | 繼續跑 | `aos-agent ctl resume`；hook 回 0 就放行 | 有 | 同上 |
| 暫停整支 | Ctrl-C 停住 | `aos-agent ctl pause`：這一輪做完才停，行程不死，信照樣堆進來 | 有 | 實測見 02 |
| print（看變數） | 看某個值 | `aos-agent ctl state`（十一類）、`history ls`、直接讀 stack 的檔 | 有 | `py/aos/apps/agent/ctl/state.py` |
| 改變數再繼續 | 把值改掉接著跑 | 停著時改 stack 的檔（`stage.txt`＝跳到別格）、`aos-agent tools/llm/system/history/hook` 改疊層、before_tool 改參數、after_tool 改結果 | 有（分散） | 同上 |
| backtrace（呼叫堆疊） | 我是怎麼走到這裡的 | `history.jsonl`（對話與工具呼叫）、`observed.jsonl`（每次想、每次工具）、子 agent 的父子關係（`ctl state who`）。**沒有「格的走法紀錄」**：`stage.txt` 只留現在這格，走過哪些格沒記 | 半 | stack 檔 |
| watchpoint（值一變就停） | 盯著某個值 | 沒有。最接近：Linux 的 inotify（aos 沒用，全輪詢） | 無 | — |
| 符號表／行號表（DWARF） | 機器位址 ↔ 原始碼第幾行 | **沒有**。全 repo 找不到 `_from` 一類出處 key；最近似的是 `agent_def new` 在 `_metainfo.json` 記 `lineage`（從哪個範本抄的）、hook 清單完成時補的 `from`（清單檔路徑） | 無 | `py/aos/hook_run.py` 第 76 行起 |
| debug flag（`-g`） | 編譯時多塞一份除錯資訊 | 沒有。庚的設計稿打算記「每份生成檔的指紋」——那是**辨認手改**用的帳，不是行號，但放得進同一個位置 | 無 | [庚 05](../aos-compile-庚/05-打架規則-總則.md) |
| core dump | 當掉那一刻的記憶體快照 | **天生就有**：stack 是檔，停掉後全留著；最像快照的是 `think/request.json`（最後一次送給腦的整份請求）＋`history.jsonl`＋`hooks/<名>/event.json`（各 hook 最後收到的事件） | 有（天生） | 實測見 02 第六節 |
| `/proc` | 看每支行程的狀態 | daemon 表（`aos-daemon-ctl ls -j`）＋每隻的 `state.json`；`ctl state resources` 讀的就是 `/proc` | 有 | `ctl/state.py` 的 `proc_use` |
| strace（攔系統呼叫） | 看程式向 OS 要了什麼 | llm kernel 的 `ledger.jsonl`：每次問腦一行（誰、哪個端點、等多久、用量）；kernel hook 能攔 | 有 | `py/tools/aos/kernel_llm/` |
| ltrace（攔函式庫呼叫） | 看程式叫了哪些函式 | `observed.jsonl` 的 tool 行；`before_tool`／`after_tool` hook | 有 | `py/aos/observed.py` |
| perf（時間花在哪） | 取樣統計 | `observed.jsonl` 的 `elapsed_ms`、ledger 的 `elapsed_ms`、`used.json`；沒有彙總工具 | 半 | 同上 |
| 日誌（journald） | 大樓總登記簿 | 各 stack 自己的 `stderr.txt`（hook 的 stderr 也進這裡）、history、observed、ledger；沒有集中 | 半 | 清道夫歸檔 `stderr_archives/` |
| 測試框架（pytest） | 自動檢查程式對不對 | Python `unittest`，散在 `py/tests/`、各工具夾、`cpp/*/tests/`；**沒有「測一隻 agent」的框架**，但有劇本腦（`llm_fake`＋`script`）可以讓腦照固定劇本答 | 半 | `templates/start-api/llms/def/kernel.json` 的 `fake-demo-self` |
| REPL | 打一行、立刻跑、狀態留著 | **沒有**。最接近的是 `aos-agent chat`（跟 agent 一行一則對話），那是「跟程式講話」，不是「操縱程式」 | 無 | `py/aos/apps/agent/chat.py` |
| 除錯用的程式庫（gdb 的 Python API） | 用程式寫斷點、寫腳本操縱除錯器 | **沒有可 import 的穩定 API**：`aos` 套件 import 得到，但各指令的函式是「吃 argv、印 stdout」的命令列形狀（見 02 第七節） | 半 | `proto8/lib/aos/` |
| IDE／圖形除錯器 | 一頁攤開全部 | 前端全景頁（`aos-frontend serve`）看整棵樹的燈號、最後回答；**不能停、不能單步** | 半 | `proto8/frontend/` |
| 倒帶（rr） | 錄下來、往回跑 | 沒有。錄的素材在（history、ledger、request.json），劇本腦能拿來「照錄的答」，但沒人把兩者接起來 | 無 | — |
| 熱更新（改了不重啟） | 跑著換程式 | 有一半：`aos-agent hook/tools/llm/system` 改的是 stack 疊層，**下一個事件就生效**、不用重起（實測 hook） | 有 | `py/aos/apps/agent/hook.py` |

## 三、比喻對不上的格（照實寫，不硬湊）

1. **「任意一行」對不上**：gdb 能停在原始碼任何一行；aos 的「程式」一半是狀態機（停得到格），一半是模型的腦（停不進去）。腦想的過程沒有「行」。
2. **「暫存器只有 CPU 能改」對不上**：aos 的 stack 誰都能改（agent 自己、hook、kernel、daemon、人），而且大家同一個 Linux 帳號。gdb 的世界裡只有被除錯的程式和 gdb 會碰記憶體；aos 裡除錯器只是「又一個會寫檔的人」。
3. **「重跑會一樣」對不上**：gdb 重跑同一支程式、同樣輸入，結果一樣；aos 問腦每次答案可能不同、還要花錢。所以「重跑」與「重播」在 aos 是兩件事（見 [04](04-邊緣狀況.md)）。
4. **「除錯器在程式外面」半對**：gdb 是另一支行程附身；aos 的 hook 是 agent 自己叫起來的小程式，等於「程式自己邀請除錯器進來」。這比較像 Python 的 `breakpoint()`（程式自己寫一行請除錯器進來）。
5. **「單一行程」對不上**：一個 aos 應用常是好幾隻 agent 互相寄信。gdb 預設停住整支程式的所有執行緒；aos 停一隻、別隻照跑（像 gdb 的 non-stop 模式）。
