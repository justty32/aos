# 使用者原話：把 aos 對到現代軟體技術棧，「那，gdb 在哪？」與後來補的四段（11-19，逐字）

← [README](README.md)｜下一份：[01-對照表](01-對照表.md)

## 第一段：提出問題

「對了，aos-compile那塊，我又有新想法，同樣麻煩派正規調查流程去幫我想想：就是說，我們重新跟隨現代軟體技術棧去走，首先我們架起daemon讓他跑起來(買一塊板子並開機)，然後灌kernel(用現有的kernel定義，掛個aos proc上去)，接著我們開始寫我們自己的應用程式(不管是用aos-compile還是自己手動mkdir建資料夾之類)，那，gdb在哪？Hmmm，我想像中」

最後一句「我想像中」後面沒打完就送出了。頂層問他後半句是什麼，他回：「先照現有的派」。

## 第二段：後來補上「想像中」的樣子

線開工後，使用者在對話裡補了兩句（頂層逐字轉來）：

「然後gdb那塊我還在想」

「gdb那塊，我預期到時候的開發體驗，會是接近python repl + shell指令...搞不好最終我會用lisp整個給他整合好...就是說，我先用python產出一份粗定義，然後進入python repl，用aos-gdb庫，下斷點(hook？編譯時加debug flag，然後hook就有東西？)，然後跑。」

所以原本「最後一句沒打完、不知道他想像中的樣子」已經不成立：他想像的是 **Python REPL（互動式直譯器，打一行跑一行的那個 `>>>`）＋ shell 指令** 的開發體驗。依這段，頂層把調查重心收窄成：

1. 先用 Python 產出粗定義（接 aos-compile 的「庚」：一支 `agent.py`）。
2. 進 Python REPL，`import` 一個 `aos-gdb` 庫，下斷點，然後跑。
3. 他自己拋出的兩個問號要正面回答（攤現況與選項，不替他定）：
   - (a) 斷點是不是就用 hook 做？
   - (b) 「編譯時加 debug flag，然後 hook 就有東西」——生成時多生一份除錯用的東西，可行的樣子與代價。
4. 「搞不好最終我會用 lisp 整個給他整合好」是**遠景**：記著、看現在的設計會不會擋到它，不為它設計。

## 第三段：為什麼 aos 的 gdb「比較特別」、新的開發範式

再補一段（頂層逐字轉來，一字不改，含原本的錯字）：

「不過考慮到gdb那邊，cpu他未來要執行哪個指令，其實是看的到的，就是往後看記憶體位置就好，但是我們的aos中，pu多種多樣，好比aos loop/fsm，他就是持續執行單一指令，但是它具體會做啥我們不知道，所以gdb這塊就會變得比較特別。另一方便，實際上我們也會有新的開發範式，也就是說，先前我們是比較直觀的直接規劃指令順序，比如第一步執行A指令，第二部執行B指令，一路往下規劃，寫程式碼，把一整個流程要執行啥指令都寫好。但是我們新的開發範式，就是先前我忘記哪次thinking有提過的，就是先用agent作為萬能函數，然後逐步給他添加工具...也就是說其實比較接近lisp那樣，就是執行途中，發現有問題，那就把他停下來(或是不停)，在他的指令中央插入新指令，我們的程式碼是持續在增長的，所以gdb這塊就變得比較特別...或許插入新指令的時候就要放debug旗標了？」

依這段，調查多三件事：
- (a) **下一步看不到**：盤點各種 pu（loop、fsm、eca 身）各自的「一步」是什麼、哪些邊界事前看得到、哪些只能事後看（[02](02-aos現況.md) 第二節、[01](01-對照表.md) 第三節）。
- (b) **程式邊跑邊長**：今天「跑到一半插入新東西」做得到哪些（[02-續](02-續-插入與Python.md) 第一節實測）。
- (c) **debug 旗標放哪一層**（生成時、插入時、執行時），連同第二段的「編譯時加 debug flag」一起攤選項（[05](05-發想.md)）。

### 他說「先前某次 thinking 提過」的那段，找到了

關鍵字「萬能函數」在 repo 裡只有一個源頭：**11-07 傍晚檢討點 13**（經頂層轉述逐字），收在 [kb-ideas/README](../../07/kb-ideas/README.md) 第 40 行、[arknights-kb/14](../../07/arknights-kb/14-第二輪總結簡報.md) 第 13 行，並被規矩 [user/03](../../../../../wf/workflows/common/user/03-討論紀錄與規劃.md) 引用：

「換成腳本是更好的選擇，這是超出我預期的好。我預期的是agent作爲萬能函數，拆出來的子功能先弄成agent呼叫，後續再慢慢優化成函數。但我也擔心，是否變成腳本的，都是一些無關痛癢的子功能，而主要功能仍需大量依賴LLM，而不是我設想的，逐步削減LLM的級別與使用。」

相關的概念條：**C-22**「提高可預測性：當 S 表示式拆開，能寫死的節點換成程式；優化目標是確定性。」（[CONCEPTS 下](../../../../docs/CONCEPTS/00-概念-下.md)）。後來被引用的地方：[convention-vs-agent-fsm](../../13/convention-vs-agent-fsm.md) 第 745 行（P-24）、[ops-agent-six-suggestions/03](../../13/ops-agent-six-suggestions/03-第2到5點.md) 第 22 行。**「逐步給他添加工具」這幾個字本身沒找到原文**；11-07 那段講的是「拆出來的子功能先弄成 agent 呼叫、再慢慢換成函數」，方向相同（從全交給模型，往確定的程式一步步長）。`proto8/docs/CONCEPTS.md` 上半本身沒有「萬能函數」一詞。

## 第四段：同一天庚那邊的新裁定（頂層轉來，供對齊）

使用者今天對 aos-compile 庚裁：「agent.py產出東西後，產出後的東西就跟他沒關係了。好比C語言和.o之間的關係。」——生成物不記指紋、重生直接蓋、工具照樣可以改生成檔。它跟「邊跑邊插新指令」的互動寫在 [04](04-邊緣狀況.md)。本線不改庚那夾的檔。

## 第五段：看完第一輪結論之後的回應（要我們「回去重新想想」）

頂層逐字轉來：

「斷點這塊，我們也可以搞特殊，也就是說，原本gnu gdb的斷點是在特定記憶體位置加上hook，跳到那邊就觸發，停下來等待檢閱，那我們這邊不必拘泥，就直接可以是在"特定條件發生時，暫停loop或fsm，停下來等待檢閱"，這個特定條件可以主要以hook承載，就是一個普通程式，發現有問題就發stop這樣，hook不用動。然後也不必一定要全部對回原始碼，畢竟我們都是狀態機了。然後也不必拘泥於hook，搞不好另外開個proc，觸發之後直接把要debug的那個proc停下來也可以...反正就是能把他停下來的都可以。debug旗標這塊或許隨著發展，後續自然而然就知道放哪。程式持續增長...當然跟C和.o沒關係，.o也可以在運行途中給自己加lib啊。編譯時加debug flag，這只是比喻，實際上就是編譯時，可以加個選項，選了之後就會添加一些除錯用的觸發器這樣。總之回去重新想想。aos-compile這塊我之後來看看。」

這段對第一輪的題與「對不上」表了態，逐條對應寫在 [06-使用者回應](06-使用者回應.md)；據此重心移到「怎麼把它停下來」（[07](07-怎麼把它停下來.md)），05 重寫。

## 這一題的前提：昨晚 aos-compile 的原話與裁定

- 11-18 晚原題：「我們現在的寫aos程式的方式，仍是mkdir這樣，那，是否可以做一套python lib，讓他最終編譯成aos資料夾+json呢？」同晚追加「……然後step in去debug，然後我停在某個指令，我可以看到在這個狀態下，我們的一些資源的狀況？」（[aos-compile-1118/00](../../18/aos-compile-1118/00-使用者原話.md)）
- 11-18 晚裁定（[07](../../18/aos-compile-1118/07-使用者裁定.md)）：
  - 「1.都想要，初期是想先做一個方便的工具，讓我不必在那邊mkdir半天，後期是當我想縱覽全局的時候，可以有個方便東西把架構濃縮，但不必精細。」→ 初期做**庚**（一支 `agent.py` 生出定義夾的 json），後期做**己**（一頁總覽）。
  - 「2.主要是loop那邊。然後你說的把tool_spec往agent長？」→ 除錯**以 loop 那層為主**；缺的兩樣是「一頁攤開資源的畫面」與「這一步對到原始碼哪一行」。
  - 「喔對的對的，這太方便了。好，都記進去，明天再正式開始」
