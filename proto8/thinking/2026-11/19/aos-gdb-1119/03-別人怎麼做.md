## 先講結論

- **除錯器的共同骨架是「先停住，才能看與改」**。gdb 停的是一條機器指令；跟 aos 像的那幾家（Erlang、LangGraph、Temporal）停的都是**邊界**——訊息之間、節點之間。aos 也只能停在邊界（[02](02-aos現況.md) 第一節），所以該抄的是後者。
- **「重播不花錢」靠把外部回答當成錄下來的輸入**：rr 錄系統呼叫、Temporal 錄 activity 結果，重播時直接拿。LangGraph 的 time travel 預設**會重打模型**（官方明講），結果可能不同。aos 的腦回答就是那個「不可重現的輸入」。
- **最像 aos 的是 Erlang**：很多小行程、各有信箱，`sys:suspend` 停一隻、`get_state` 看、`replace_state` 改、`resume` 續，別隻照跑。

## 一、gdb／lldb 本身

- **怎麼停**：用 Linux 的 ptrace 接上別的行程；ATTACH 送 SIGSTOP 停住它。停住時才能讀寫它的記憶體與暫存器。
- **軟體中斷點**：把那個位址的指令換成一條「特殊指令」（x86 是 int3），跑到就交回 gdb；gdb 平常只在程式跑時插入、停下就還原。
- **硬體 watchpoint**：用 CPU 的除錯暫存器盯一個值，全速跑、改值那條指令就停；數量很少（通常 4 個左右）。軟體 watchpoint 要一步一步檢查，官方說慢「數百倍」。
- **符號表**：DWARF 是編譯器多塞給除錯器的資料（`gcc -g` 就是開這個），讓「機器位址 ↔ 原始碼第幾行」對得起來。
- **non-stop 模式**：只停一條執行緒，其他照跑——對應 aos「停一隻、別隻照跑」。
- **core dump**：記憶體與暫存器的快照；`gcore` 對活著的行程也能傾印。
- **限制**：所有看與改都建立在「它先停下」；Linux 的 Yama 預設只准 ptrace 自己的後代。
- 來源：<https://man7.org/linux/man-pages/man2/ptrace.2.html>、<https://sourceware.org/gdb/current/onlinedocs/gdb.html/Set-Breaks.html>、<https://sourceware.org/gdb/current/onlinedocs/gdb.html/Set-Watchpoints.html>、<https://sourceware.org/gdb/current/onlinedocs/gdb.html/Non_002dStop-Mode.html>、<https://lldb.llvm.org/use/tutorial.html>
- **跟 aos 的距離**：aos 不需要 ptrace（狀態本來是檔）；但也沒有「任意一行」可停。aos 的 stack 誰都能寫，gdb 的世界只有程式與 gdb 會碰記憶體。

## 二、strace、ltrace、perf

- **strace**：記下系統呼叫的名稱、參數、回傳值，可 `-p` 接上在跑的；被追的程式會變慢。<https://man7.org/linux/man-pages/man1/strace.1.html>
- **ltrace**：同上，記的是函式庫呼叫。<https://man7.org/linux/man-pages/man1/ltrace.1.html>
- **perf**：取樣，每秒約一千筆記「現在在哪」，再排序看時間花在哪。<https://perfwiki.github.io/main/tutorial/>
- **跟 aos 的距離**：aos 的 llm kernel `ledger.jsonl` 就是腦這條的 strace；`observed.jsonl` 是工具這條的 ltrace；耗時資料有、彙總工具沒有。

## 三、Erlang／OTP（跟 aos 最像）

- **observer**：圖形工具，列每個行程的記憶體、**信箱長度**、狀態，看監督樹；可連遠端節點。<https://www.erlang.org/doc/apps/observer/observer_ug.html>
- **sys 模組**：`suspend`（停了只回應系統訊息，一般信堆著）、`resume`、`get_state`、`replace_state`（用你給的函式改狀態；官方說僅供除錯）、`trace`（印出系統事件）。這些是行為模組內建的，不用外掛。<https://www.erlang.org/doc/apps/stdlib/sys.html>
- **dbg、recon_trace**：文字介面追函式呼叫與訊息；recon 加安全閥（總則數或速率上限、斷線自動關）。<https://www.erlang.org/doc/apps/runtime_tools/dbg.html>、<https://ferd.github.io/recon/recon_trace.html>
- **限制**：sys 預設 5 秒逾時；重度追蹤會掉訊息、拖垮節點；分散式節點不加 TLS 等於把整台交出去。
- **跟 aos 的距離**：幾乎一一對上——`suspend`＝`ctl pause`（aos 實測信也是堆著）、`get_state`＝`ctl state`、`replace_state`＝改 stack 疊層、observer＝aos 缺的那一頁。差別：Erlang 的狀態在行程記憶體裡，aos 的在檔裡（所以 aos 停掉後還看得到）。

## 四、rr：錄下來、重播、倒著跑

- `rr record` 錄整次執行，`rr replay` 開 gdb 在錄影上除錯；位址、系統呼叫結果每次一樣；`reverse-continue` 等倒著跑，配 watchpoint 能問「這個值最後是誰改的」。
- 錄的是「所有不確定的輸入」（系統呼叫結果、訊號、排程時機）。
- 限制：錄製慢 1.2～4 倍；全壓在單核；要較新 CPU；不能錄跟外部共用記憶體的程式。
- 來源：<https://rr-project.org/>、<https://github.com/rr-debugger/rr/wiki/Usage>
- **跟 aos 的距離**：aos 的「不確定輸入」主要是腦的回答，已經寫在 history 與 ledger；aos 有劇本腦（`llm_fake`＋`script`，`templates/start-api/llms/def/kernel.json`）能照固定劇本答。缺的是「從 history 抽出劇本」這一步。多隻 agent 並行正是 rr 不做的。

## 五、Temporal（durable workflow 的重播）

- 事件歷史是真相；恢復時從頭重跑流程程式，把記錄的事件餵回去。
- 流程程式必須確定性；時間、亂數走 SDK 的 API。
- **對外的動作（API、資料庫、LLM、檔案）放 activity：只執行一次、結果記進歷史，重播時直接用記錄值**。
- Web UI 看歷史（時間軸、JSON）；Python 有 `Replayer` 拿歷史驗新程式。
- 限制：改了程式，舊的進行中流程可能重播失敗，要版本管理；UI 看的是事件不是變數；重播是驗證，不是「改了再續」。
- 來源：<https://docs.temporal.io/workflow-definition>、<https://docs.temporal.io/workflows>、<https://docs.temporal.io/web-ui>、<https://docs.temporal.io/develop/python/testing-suite>
- **跟 aos 的距離**：把「問腦、寄信、寫檔」當 activity 是最值得抄的一招。但 aos 程式邊跑邊長（[02-續](02-續-插入與Python.md)），Temporal 最怕的正是「程式改了，舊歷史對不上」。

## 六、XState inspector（狀態機的觀察畫面）

- 把 `inspect` 傳進 actor，就會開一頁即時畫狀態機圖（現在在哪格）與序列圖（誰傳訊息給誰）。
- 只看、不停、不改（官方頁沒寫停與改）。
- 來源：<https://stately.ai/docs/inspector>
- **跟 aos 的距離**：aos 的 `fsm.json` 就是那張圖，`stage.txt` 就是「現在在哪格」，信箱就是序列圖的素材——畫出來的零件都在。

## 七、LLM agent 框架的除錯工具

- **LangGraph checkpoint／time travel**：每一步存一個 checkpoint。Replay＝從舊 checkpoint 重跑；Fork＝先 `update_state` 改狀態（產生新分支、不回滾）再跑。**之後的節點全部重跑、LLM 會再打、結果可能不同**（官方明講）。<https://docs.langchain.com/oss/python/langgraph/use-time-travel>、<https://docs.langchain.com/oss/python/langgraph/persistence>
- **LangGraph interrupt／斷點**：`interrupt()` 在節點裡暫停，`Command(resume=…)` 回來；`interrupt_before`／`interrupt_after` 是靜態斷點，官方說主要給除錯。坑：恢復時**那個節點從頭重跑**，`interrupt()` 之前的副作用會再做一次。<https://docs.langchain.com/oss/python/langgraph/interrupts>
- **LangGraph Studio**：看每一步的 prompt、工具呼叫、回傳、token、延遲，可從任一步重跑。<https://docs.langchain.com/oss/python/langgraph/studio>
- **LangSmith**：trace 由多個 run 組成；可把某次 LLM 呼叫丟進 Playground 改 prompt 再測（每次都真打模型；Playground 細節只讀到搜尋摘要）。<https://docs.langchain.com/langsmith/observability-concepts>
- **OpenAI Agents SDK tracing**：預設開；每次生成、工具呼叫、handoff 一個 span；事後看，不能回放。<https://openai.github.io/openai-agents-python/tracing/>
- **AutoGen Studio**：即時看 agent 間訊息流、可暫停或停止；官方說是研究原型。<https://microsoft.github.io/autogen/stable/user-guide/autogenstudio-user-guide/index.html>
- **跟 aos 的距離**：LangGraph 的「節點」＝aos 的「格」，`interrupt_before`＝在某格前停；但 LangGraph 的狀態是一個 Python 物件、存在 checkpointer 裡，aos 的狀態是一堆檔、誰都能寫。aos 沒有每步快照。

## 八、Jupyter

- kernel 是獨立行程，前端只是送一格程式過去；狀態（變數、除錯器的斷點）留在 kernel，前端斷了也沒事。
- `%debug` 是事後驗屍（進最近一次例外的堆疊）；`%pdb on` 每次例外自動進 pdb；新版訊息協定支援標準除錯協定（DAP）。
- 來源：<https://jupyter-client.readthedocs.io/en/stable/messaging.html>、<https://ipython.readthedocs.io/en/stable/interactive/magics.html>
- **跟 aos 的距離**：「人在外面一格一格送、狀態活在另一個行程」跟 aos 同型——REPL 是前端、跑著的樹是 kernel。

| Erlang | 停一個行程；trace 按訊息 | 狀態、信箱、記憶體、監督樹 | 能（`replace_state`） | 不能 | 照常 |
