**這節是淺的，深的另外派**（使用者 11-19：「繼承這塊也可以去想想...淺淺想一下就好，深的就之後另外派」）。只擺地圖，不出設計、不列待裁題。

## 先講結論

1. aos 今天沒有叫「繼承」的機制，10-14 明講不做（「沒有 extends、沒有搜尋路徑……範本資料夾不是父類」，[json-entry 08](../../../2026-10/14/json-entry/08-fsm拍板與改寫.md) 第 9 行；「『繼承』只是一種形容，還沒進規範」，[12](../../../2026-10/14/json-entry/12-七題回覆.md) 第 4 題）。但**像繼承的東西已經有六種**，差別在「抄」還是「借」、「生成時」還是「執行時」。
2. **有了 `agent.py`，「定義繼承定義」可以完全在生成時用 Python 做掉**：`agent.py` 是普通 Python，`from base_agent import TOOLS, SYSTEM` 再加幾項就是衍生。生出來的 json 裡沒有任何「我的上一層是誰」——跟「C 與 .o」、10-14「不做繼承」、C-89「血緣不是執行時的上層」三條同時相容。這可能就是 aos 的繼承該待的地方，不用另做機制。
3. **命名空間跟繼承搶同一個動作**：繼承要「同名的我蓋掉你」，命名空間要「同名的別悄悄蓋」。所以命名空間那邊一定要分得出「**我明寫要蓋**」與「**兩個不相干的來源碰巧同名**」；分得出來，兩件事才不打架。

## 「繼承」可能指什麼

| 指什麼 | 白話 | 今天有沒有 |
|---|---|---|
| 一、定義繼承定義 | 新 agent ＝某個現成 agent ＋幾處不同 | 部分有：`tools.json` 可以 `$override` 別份定義的工具表；`hooks.json`、`llm.json`、`system.txt` 沒有；fsm 靠一格一格借 |
| 二、範本衍生 | 從範本做出一隻新的 | 有，是**抄**：`agent_def new` 整夾抄、寫 `lineage`；抄完各走各的 |
| 三、庫繼承庫 | 我的庫＝std＋我加的、我換的 | 包可以 `$override` 別的包，所以技術上有；沒人這樣用過 |
| 四、執行時「變成」另一套 | aos-exec 一環套一環、共用同一個 stack | 有，C-87 用「像繼承」形容的就是這個；它管的是 stack 裡的檔名 |
| 五、實例蓋定義 | 跑起來的這一隻跟原始碼有幾處不同 | 有：stack 那份蓋定義那份（工具、腦設定、hook），kit |

## 今天已有的類似機制，照「抄／借」與「何時」排

| 機制 | 抄還是借 | 何時定下來 | 像哪種繼承 |
|---|---|---|---|
| `agent_def new`、`ag.stock_hooks()` | 抄 | 做的那一刻 | 複製貼上；上游改了不跟（`stock_hooks` 重生才跟） |
| `ag.stock_fsm()`、reviewer 借四格、`$AOS_HOME/lib/…` 指示詞 | 借 | 每次用到才解 | 動態連結；上游一改就跟著變 |
| `$override`（工具表、包） | 借，逐欄合併 | 每次讀表 | 最像類別繼承：可多層、可多個底、`null` 拿掉 |
| stack 蓋定義、kit | 借底、蓋差異 | 每次讀 | 實例對類別（C-52「漂移只在 stack」） |
| C-87「變成」 | 共用 | 執行時 | 使用者自己的比喻；但他說「在呼叫這塊，其實沒有 base class, deriative class 之分」 |
| `lineage` | 只是紀錄 | 出生時 | 族譜，執行時沒人讀（C-89） |

## 跟命名空間怎麼互相牽動

- **繼承要能指名「底是誰」**。今天指的方式是路徑（`$override` 指一個檔）。命名空間若是路徑式（[03](03-設計選項.md) 的 B），這件事不用另外想；若是名字式（C），「底」也要寫全名，多一道解析。
- **「同名」的意思要先定**。今天工具表同名＝後面的逐欄蓋前面的，不分是不是故意的（[01](01-現況盤點.md) 結論 2）。繼承需要這個行為，命名空間要擋這個行為。分法可以很簡單：**自己那一格蓋底下的＝故意；同一層並排的兩個底互相同名＝碰巧**，後者才報。
- **抄與借在命名空間裡是兩種不同的「用」**。借＝名字一直指向庫裡那一份（庫改了我就變）；抄＝拿來的那一刻就成了我自己的東西，不再屬於那個庫。`stock_hooks` 今天裁的是抄，所以抄進來的 hook 名不帶庫的身分，這跟命名空間不衝突。
- **逐欄合併會留殘渣**：蓋一個工具時前一份的欄位可能殘留（01 結論 2）。這在「繼承」裡是特性（只改一欄），在「兩個庫撞名」裡是 bug。同一個機制兩種期待。

## 各走向一兩句的後果

| 走向（見 03） | 對繼承的後果 |
|---|---|
| A 前綴慣例 | 想換掉 std 的 `std_read`，只能讓自己的工具也叫 `std_read`——名字就說謊了；或改叫 `my_read` 再把 `std_read` 關掉，那就不是「蓋」而是「換一支」。 |
| B 路徑即命名空間 | `agent.py` 生成的 `tools.json` 改成把包展開（Argon 審後，[06](06-Argon審與採納.md)），「蓋掉某支」變成在 Python 裡整格換、沒有殘渣；手寫 json 與 stack 的 `$override` 照舊。「定義繼承定義」交給 `agent.py` 的 Python。執行期不動。 |
| C 定義檔裡寫全名 | 最乾淨：`std.read` 寫在自己那格＝明講要蓋它，`my.read`＝新的一支，不可能誤會。代價是登記表整個改。 |
| D 搜尋路徑 | 搜尋順序本身就是繼承（前面的庫蓋後面的）——正是 10-14 說不做的那一種，而且是隱性的。 |

## 留給深挖那一輪的問題（只列，不答）

- 「定義繼承定義」在 `agent.py` 用 Python 的 `import` 做，夠不夠？被 import 的那支放哪、怎麼找得到（Python 自己的搜尋路徑又回來了）。
