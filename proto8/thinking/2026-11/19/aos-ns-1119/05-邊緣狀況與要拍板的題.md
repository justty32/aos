# 命名空間這題的邊緣狀況清單，與要使用者拍板的七題（選項、後果、推薦）

← [README](README.md)｜上一份：[04-繼承-淺想](04-繼承-淺想.md)｜下一份：[06-Argon審與採納](06-Argon審與採納.md)

邊緣狀況由設計者（fable）列、線隊長補了兩條（標「隊長補」）、Argon 審後改了幾條並補一條（標「Argon」，[06](06-Argon審與採納.md)）。題目照規矩只攤選項與後果，**由使用者拍板**；推薦是設計者與隊長的意見。

## 要你拍板的題

### 第 1 題：走哪個方向（細節在 [03](03-設計選項.md)）

白話：「命名空間」就像姓氏——兩個人都叫「小明」，加上姓就分得開。問題是姓要寫在哪裡。

| 選項 | 長怎樣 | 後果 |
|---|---|---|
| A 前綴慣例 | 名字自己帶姓：`std_read`、`std_look` | 沒有新機制，最貼 C-87「各自加前綴」；腦每次多讀 62 個 `std_`，全部範本、知識庫的工具名都要改；撞名仍然悄悄蓋，只是比較難撞 |
| **B 路徑即命名空間（推薦）** | 庫＝一個資料夾，`std` 是隨 aos 發的那一個；`agent.py` 寫 `std.pack("look")`、別的庫 `my = ag.lib("my", 路徑)`；生成時把包展開成一支支工具寫進 `tools.json`，json 只有全路徑 | 不加執行期機制，解析在生成時做完（＝「C 與 .o」）；別的庫的工具自動帶前綴、還撞就生成時報錯；第一刀只改 `agent_spec`、可丟 |
| C 定義檔裡寫全名 | `tools.json` 的鍵變 `std.read`，登記表送腦前翻成短名 | 撞名最乾淨；但要改執行期（登記表、腦、act、mcp、self_tools、全部範本），大約 B 搬家那刀的兩倍 |
| D 搜尋路徑 | `AOS_LIBPATH=my:std`，寫短名照順序找 | 跟 10-14「沒有搜尋路徑」、C-87「不做隱性操作」正面衝突；不推薦 |

### 第 2 題：腦看到的工具名要不要帶前綴

白話：LLM 叫工具用的名字只准英數、`_`、`-`，不能有 `.`、`/`。所以「這工具是哪個庫的」跟「腦叫它什麼」得分開想。**你答題時說的是「工具名本身就帶前綴」，這題要你確認是不是指腦看到的這個名字。**

| 選項 | 後果 |
|---|---|
| a 腦看到短名：「屬於哪個庫」只在路徑與 `agent.py` 裡；兩個庫都有 `read` 就在生成時報錯，由寫 `agent.py` 的人改名或拿掉一個 | 腦不多花字；std 的名字（`read`、`ls`…）不變，知識庫與 system.txt 不用改；但腦看不出來源 |
| **b std 短名、別的庫預設加 `庫名_`（`my_read`）（推薦）** | 來源在腦那邊也看得出來，對得上「工具名本身就帶前綴」；std 的名字不變、知識庫與 system.txt 不用改；包本來就要在生成時展開（第 7 題），加前綴只是改鍵名，執行期不動；跟 MCP 的 `<server>_<tool>` 同一招。寫 `agent.py` 的人可用 `prefix=`、`rename=` 改 |
| c 全部帶前綴（`std_read`） | 等於 A 的代價：全部改名、腦多讀字 |

### 第 3 題：C-87 說「契約或機制，那是以後的事情」，現在算不算「以後」

白話：11-02 你說撞名「大家各自管好自己的手」、不做隱性命名空間，機制以後再說。這次你要的「不同來源的同名東西不會撞」是一種機制。C-87 原本講的是共用 stack 時**檔名**撞名，跟工具名不是同一件，但精神相通。

| 選項 | 後果 |
|---|---|
| **a 算，只做「看得見的」機制（推薦）**：B 的庫長相固定、生成時查撞名，不做任何執行期的暗中查找 | C-87 補一句「工具與庫的名字另見某條」，stack 檔名那段照舊 |
| b 算，連執行期一起做（C） | C-87 的「不做隱性」要重寫成「做明的」 |
| c 還不算 | 只能走 A（純慣例） |

### 第 4 題：std 要不要真的搬進 `lib/std/`

| 選項 | 後果 |
|---|---|
| a 搬 | 路徑一看就是 std；`py/tools`、`py/packs`、`templates` 都要搬，上百條路徑字串改、活樹要重建（跑著的 agent 的 stack 存著舊路徑） |
| b 不搬：`$AOS_HOME/lib` 與 `templates` 就算 std 的根 | 便宜；但路徑裡沒有「std」三個字，「看名字知道是誰的」只對別的庫成立 |

推薦：先 b（第一刀就是這樣），試過手感再決定要不要 a。不搬時 std 是「`lib/tools`、`lib/packs`、`templates` 三個固定位置」的特例，工具寫 `std.tool("base/read")`（類夾當路徑的一段，不搜尋）；搬家時可拍平成 `std.tool("read")`（三類 91 支今天沒有同名），hook 組與 fsm 格程式也可各自獨立一夾（Argon A4、A6、提案 4）。

### 第 5 題：「標準庫」這個詞撞到 C-74

白話：C-74（10-22）裡「標準庫」是一層——aos-fsm、tasks 那種用基礎層寫成的組合子；範本、agent 在它上面。這次的 `std` 會裝工具、包、範本，跟那一層不是同一批東西。

| 選項 | 後果 |
|---|---|
| a `std` 照用，C-74 加註「層的標準庫」與「隨 aos 發的庫 std」是兩回事 | 同一個詞多一個意思（C-74 已經另註了「純標準庫 Python」是第三種） |
| b 這個庫換名（例 `stock`、`aos`） | 詞不撞；`aos` 會跟 Python 套件 `lib/aos/` 撞夾名，`stock` 跟今天 `stock_fsm` 同字 |

這題沒推薦，看你對「std」這個字的感覺。

### 第 6 題：別的庫放哪、怎麼被找到

| 選項 | 後果 |
|---|---|
| **a `agent.py` 裡明寫路徑（推薦）**：`my = ag.lib("my", ag.env("AOS_WS", "/lib/my"))`，像 Python 的 `import x as y` | 零新機制；庫名只在那支檔裡有效，兩個人都叫 `my` 也不撞；兩台機器路徑不同要靠 `$env` |
| b 一台一個固定庫夾（例 `$AOS_HOME/libs/<庫名>`），庫名＝夾名 | 跟「一台 daemon 一張表」同構；要一條新的固定位置，庫名在一台上要唯一 |
| c 一份庫名表 | 多一份要維護的表，最像 npm |
| d 每個庫一個變數 `AOS_LIB_<庫名>`，沒設就找 `$AOS_HOME/lib/<庫名>`（Argon 提案 3） | 兩台機器各設各的就可攜；多一族新變數；庫名在一台上要唯一 |

不管選哪個，**生成時一定要讀得到庫根**，讀不到報錯、不靜默跳過（Argon A3：庫根若寫成 `$AOS_WS` 底下，跑 `agent.py` 的當下常常沒設這個變數）。選 a 時 `agent_def new` 抄範本沒有 `agent.py` 可查，只能收 `std/…`，別的庫的範本照舊用 `from` 給路徑；選 b、d 才能收 `my/…`（Argon A2）。

### 第 7 題：包是「生成時抄進來」還是照舊「執行時借」（Argon 審後新增）

白話：今天 `tools.json` 只寫「我要 look 這包」，每次跑才去讀包裡有哪些工具（借）；展開＝生成時就把包裡的工具一支支抄進 `tools.json`（工具本身的程式仍是借的）。

| 選項 | 後果 |
|---|---|
| **a 生成時展開（推薦）** | 撞名才解得開（照舊借的話，另取名只是多一格、`no` 會連 std 的一起拿掉，[06](06-Argon審與採納.md) A1）；沒有逐欄合併的殘渣；包之後多加的工具要重生才拿得到——跟你裁的「`stock_hooks` 是抄」同性質；`tools.json` 從幾行變成幾十行 |
| b 照舊借 `$override` | 包加工具不用重生；但第 2 題的前綴與撞名報錯都做不到，只剩 A 式慣例 |

注意：這題只管 `agent.py` 生出來的 `tools.json`；手寫的 json、kit、stack 的 `self_tools` 照舊用 `$override`。

### 設計者直接定、不另問的（proto8 當成沒有舊版）

- 走 B 時，`ag.pack("look")`、`ag.stock_hooks()`、`ag.stock_fsm()` 直接換成 `std.pack("look")`、`std.hooks("agent-fsm")`、`std.fsm("agent-fsm")`（組名可省、預設就是這組；跟 `hooks` 對稱，Argon A9-1），不留舊名。**行為不變**：hooks 照舊是抄、骨架照舊不帶 hook（今天已裁的兩件不動）。
- hook 名、fsm 格名、proc 名、endpoint 名不進命名空間：它們的範圍本來就是「一張表」（一隻 agent、一台 daemon、一台 kernel）。

## 邊緣狀況

1. **`_` 當分隔有歧義**：庫 `json` 的 `get` 拼成 `json_get`，跟 std 的 `json_get` 同名；從腦的名字反推不出庫。（第 2 題選 b 才會遇到）
2. **64 字上限**：加前綴可能超長；MCP 凍結名已是 `<server>_<tool>`，再加庫前綴成三段；eca 那邊 Claude 看到的 `mcp__<server>__<tool>` 又多一層。
3. **`lib/` 底下已被佔的名字**：`aos/`（Python 套件）、`tools/`、`packs/`、`libaos-*`；庫若放 `lib/<庫>`，這些是保留名。
4. **搬家後活樹裡的舊路徑**：stack 的 `tools.json`（`self_tools add` 存的路徑）、`hooks.json`、kit 蓋進去的檔都指 `/lib/tools/…`、`/lib/packs/…`；install 後跑著的 agent 當場斷。（第 4 題選 a 才會）
5. **start-api／start-eca 是範本的逐字抄本**，`test_start.py` 比對；路徑一改兩邊都要改。
6. **手寫 json 沒有生成步驟**：B 的撞名檢查只在 `agent.py` 生成時；手寫的 `tools.json`、kit、`tools_sub.json` 仍然悄悄蓋（[01](01-現況盤點.md) 實測），除非 `defs check` 也補一條。
7. **「故意蓋」跟「碰巧撞」怎麼分**：展開後，`agent.py` 裡明寫 `ag.tool("read", …)` 換掉某支＝故意（整格換）；兩個包展開出同一個鍵＝碰巧，報錯。兩個包都疊同一個底包（菱形）時，比**解完的整格**，完全相同才不算撞；有一邊改過欄位就報（Argon A8）。
8. **逐欄合併的殘渣**：同名蓋時前一份的欄位（`env` 之類）殘留；在繼承是特性、在撞名是 bug。
9. **`ag.no("read")` 拿掉誰**：多庫後兩個 `read` 撞名報錯，若叫人用 `no` 解，`no` 照鍵名拿掉會兩個一起拿掉；要能寫「拿掉 my 的 read」。
10. **腦看到的名字若會變**（第 2 題 b／c 或走 C）：知識庫、範本 system.txt、`history.jsonl` 裡的舊工具名、小模型（C-92）都受影響；規則必須靜態，不能「撞了才加前綴」——否則多掛一個包，既有工具就改名。
11. **別的庫的根在兩台機器不同**：要靠 `$env` 才可攜；那個變數要不要 `AOS_` 前綴（第三方用 `AOS_` 撞 R8 的意思）。
12. **生成時讀不到庫根**：今天 `ag.pack` 在 `AOS_HOME` 沒設時跳過「包在不在」的檢查（`agent_spec_parts.py` 70-73）；別的庫的根若寫成 `$AOS_WS` 底下，跑 `agent.py` 時常常沒設（Argon A3）。要展開包就一定得讀得到，改成報 `SpecBad`。
13. **借的東西事後才撞**（隊長補）：包若照舊借（第 7 題 b），生成之後某個包多加了一支同名工具，跑的時候又變回悄悄蓋，重生之前不會被發現。第 7 題選 a 就沒這條；工具本身的程式仍是借的，上游改了會跟著變（這是想要的：修 bug 不用重生）。
14. **庫名本身撞**：兩個來源都叫 `my`。第 6 題 a 下庫名只在一支檔裡有效所以不撞；b／c 下問題上移一層。
15. **`lineage` 記什麼**：`{"template": "agent-fsm"}` 要不要寫成 `std/agent-fsm`。
16. **範本名兼 hook 組名**：`stock_hooks(template=)`；hook 組若有自己的位置，範本自己的 `hooks.json` 跟庫那組是兩份還是一份（又一個抄本同步問題）。
17. **多層範本名**：`kernel/llm-kernel`、`kits/gather` 今天用 `template` 叫不到；`std/kernel/llm-kernel` 要不要准；`agent_def` 擋 `/` 是為了小模型（11-10 gemma 實測，`agent_def/_entry` 92 行），放寬要防 `..`。
18. **抄進來的 hook 撞自己的 hook**：今天 `HOOKS` 串列「後面的贏」不報錯；stack 的 `hooks/<名>/` 小格跟著 hook 名走，這才是 C-87 意義下「該自己加前綴」的地方。
19. **借的格程式屬於誰**：`stock_fsm` 指 `templates/agent-fsm/*.py`，是範本的一部分還是庫裡獨立的一組。
20. **第三方庫的 Python 程式碼怎麼被找到**：工具殼靠 `$AOS_HOME/lib` 在 `sys.path`；別的庫自己的 Python 模組要另找——Python 的搜尋路徑從後門回來。[04](04-繼承-淺想.md) 的「用 import 做定義衍生」同一個問題。
21. **第三方庫要不要出指令**：`bin/` 只有一個、`aos-` 前綴強制（`entries.json`）。
22. **`aos-tools add` 預設名＝夾名**：兩個庫的同名夾，第二支要帶 `--name`。
23. **subagent 的 `tools_sub.json`、kit 的 `$override` 直接指包**：不經 `agent.py`，路徑要手改，也查不到撞名。
24. **知識庫首段 `aos/` 跟庫名 `std`** 是不是同一個東西的兩個名字；庫附不附知識庫。
25. **版本**：先不碰；但多庫之後「哪個庫改了害我壞」比今天難查（第 13 條是它的一個樣子）。
26. **`std` 誰能往裡放**：C++ 不准使用者往 `std` 加東西；`install.py` 用 `dirs_exist_ok` 抄，使用者自己丟進 `$AOS_HOME/lib` 的夾不會被清、也沒人擋。
27. **第一刀做到多少「後者」**（隊長補、Argon A5 後改）：第一刀不搬檔，std 的路徑裡沒有「std」三個字；但別的庫的工具在 `tools.json` 裡帶前綴、同名不撞，這一半是「後者」。驗收要用一個真的放在別處、也有 `read` 的小庫，不要只用 std 驗。
28. **執行期在 stack 加別的庫的工具**（Argon A9-3）：`self_tools add`／`aos-agent tools add` 不經 `agent.py`，名字預設是夾名、不會自動加 `庫名_`；加進來的若跟定義那份同名，照今天的 `$override` 逐欄蓋。要不要讓它們也懂庫與前綴，留到真的有第三方庫再說。
