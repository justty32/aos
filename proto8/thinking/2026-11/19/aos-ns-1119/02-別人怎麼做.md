# 別人怎麼做命名空間與標準庫：各自解決撞名、來源可辨、搜尋路徑、版本哪一個，哪些值得抄、哪些是包袱

← [README](README.md)｜上一份：[01-現況盤點](01-現況盤點.md)｜下一份：[03-設計選項](03-設計選項.md)

憑常識整理，沒上網查；細節以各家文件為準。四件事的意思：**撞名**＝兩個來源都有 `read` 時不打架；**來源可辨**＝看名字就知道是誰的；**搜尋路徑**＝寫短名時去哪幾個地方找、誰先；**版本**＝同一個庫的新舊版共存。

## 先講結論

1. 大家的命名空間幾乎都是**「路徑或前綴」＋「一個短名的捷徑」**兩件事湊起來：全名永遠唯一（`std::vector`、`@scope/pkg`、`/nix/store/<雜湊>-x`），短名靠 `using`／`import`／搜尋路徑臨時借用。
2. **最值得抄**：npm scope 的「前綴＝發行者」（`@org/x`）、Python 的「資料夾就是套件」（跟 aos「資料夾＝程式」同一個想法）、Lisp package 的「名字在讀進來那一刻就定死」（跟「C 與 .o」同一個想法：解析在生成時做完，產出物裡只有全名）。
3. **最大的包袱**：搜尋路徑（C 的 include path、Python 的 `sys.path`、`PATH`）——方便，但「到底用到哪一份」要跑起來才知道，正是 aos 今天工具表「後面的悄悄蓋前面的」的同一種病。C++ 的 ADL（自動往參數的命名空間找）、Python 的 `from x import *` 也屬這類「隱性」，C-87 已經說不要。
4. **版本先不碰**：Nix／Guix 用雜湊把版本塞進路徑，乾淨但重；aos 現在的「庫」只有一份 `$AOS_HOME/lib`，版本是 git 的事。

## 各家

| 誰 | 名字長怎樣 | 主要解決 | 值得抄 | 包袱 |
|---|---|---|---|---|
| C++ `namespace`＋`std` | `std::vector`；`using namespace std;` 借短名 | 撞名、來源可辨 | 標準庫在一個固定前綴底下、使用者的東西不准放進 `std`；「全名寫法永遠能用」 | `using namespace` 一開就又撞回去；ADL 是隱性查找；命名空間跟檔案位置無關，找定義要靠工具 |
| C | 沒有命名空間，靠前綴慣例（`pthread_`、`SDL_`） | 撞名（靠自律） | aos 今天的 `aos-`、`AOS_` 就是這套；最簡單 | 沒人擋，撞了是連結期才知道 |
| Python 套件 | `os.path.join`；資料夾＋`__init__.py`＝套件；`import x as y` | 撞名、來源可辨、搜尋路徑 | **資料夾即命名空間**；`import` 時可改名（`as`）；標準庫就是直譯器旁邊那個夾 | `sys.path` 順序決定一切，同名模組誰先被找到誰贏（遮蔽標準庫是經典坑） |
| Common Lisp package | `cl:car`、`my-pkg::helper`；`:` 是公開、`::` 是內部 | 撞名、公開／內部之分 | **讀進來那一刻就把符號定到某個 package**，之後不再查——像「C 與 .o」；`cl` 這個 package 誰都不准改 | 讀入時的「目前 package」是隱性狀態；新手常被搞混 |
| Nix／Guix | `/nix/store/<雜湊>-hello-2.12`；channel 或 flake 是來源 | 版本、來源可辨、可重現 | 「引用永遠寫全路徑、不靠搜尋」；來源（channel／flake input）明寫 | 很重，雜湊路徑人讀不了；aos 現在用不到 |
| npm scope | `@anthropic/sdk`；沒 scope 的是全域一張表 | 撞名（發行者分開）、來源可辨 | **前綴＝誰發的**，一看就知道；沒 scope 的舊名照舊能用 | 全域那張表搶名字；`node_modules` 一層層往上找是搜尋路徑 |
| k8s namespace | `kubectl -n team-a get pods`；物件全名 `命名空間/名字` | 撞名（同一叢集多組人）、權限邊界 | 名字範圍＝一個「房間」，跟 aos 的「一台 daemon 一張表」已經同構 | 不是每種物件都在命名空間裡（有些是叢集級），容易搞混 |
| Go module | `github.com/x/y/pkg`；import 路徑就是網址 | 來源可辨、版本 | 「名字＝去哪拿」，不另建表 | 長；搬家要改所有 import |
| MCP／Claude Code | `mcp__server__tool` | 撞名（多個 server） | aos 自己 eca 那邊已經在用；證明「腦看得懂帶前綴的工具名」 | 名字長、吃 token；前綴是硬拼字串，不是結構 |

## 對 aos 的意思

- aos 的工具名受 LLM function name 規則限制（`[A-Za-z0-9_-]{1,64}`，見 [01](01-現況盤點.md) 第 1 類），**`.`、`/`、`:` 不能直接進腦看到的名字**。所以「寫法」跟「腦看到的樣子」要分開想：在 `agent.py`、json、shell 裡可以寫 `std/look`，送給腦時得換成 `std_look` 或乾脆短名——這一步要在**生成時**做完（Lisp 式、「C 與 .o」式），產出的 json 裡不留需要再解析的東西。
- aos 已經是「路徑即名字」的體系（Nix／Go 那一派），短名只在幾處（工具名、包名、範本名、endpoint 名）。所以命名空間最省力的做法，是**讓那幾個短名也變成「路徑的短寫」**，而不是另造一張名字表。
- 搜尋路徑能不做就不做；要做，至少要讓「到底用到哪一份」在生成時就印得出來（像 `which`）。
