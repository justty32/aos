## 第 3 題：建斷點的寫法——裁：`a.bp.add.before_tool("x")`

- 選項框題目：「建斷點的寫法要哪一種？（這題線沒有推薦）」
- 使用者選：「a.bp.add.before_tool("x")」
- 選項說明：「按 tab 補得出有哪些事件，打錯當場知道。add 同時是動作又是一組名字。」
- **跟稿不同的地方**：05 這題的 b 原寫 `a.bp.stop.before_tool()`；頂層問的時候 b 改寫成 `a.bp.add.before_tool("x")`，使用者選的是這個。「兩種都留」沒選，所以字串式 `a.bp.add("before_tool", tool="x")` 不留。

## 補：`defs.defs(...)` 換名，改用編譯的說法（11-19，線 aos-defs-rename2-1119）

- 使用者 11-19 原話（逐字）：
  - 選項框題「改名後有個函式變成 defs.defs(...)（算出定義但不寫檔）。要不要幫它換名？」→ 他自己寫：「要，可以參考那些程式語言的類似的功能的名字」
  - 背景：「agent.py產出東西後，產出後的東西就跟他沒關係了。好比C語言和.o之間的關係。」；同日問「生成、重生、抄，這都是啥意思。」
  - 隨後定用詞：「然後以後也用編譯、重新編譯來說，不要再用生、重生這樣」
- 候選（函式＋旗標成套）：

| 組 | Python（算出不寫／寫進夾） | 指令（寫／只印） | 參考 | 理由 | 缺點 |
|---|---|---|---|---|---|
| 甲（選這組） | `defs.compile(...)`／`defs.write(夾, 結果)` | `--compile [夾]`／`--dry-run` | cc、`make -n`、rsync／npm 的 `--dry-run` | 跟使用者一路用的「C 與 .o」「aos-compile」同一個字；dry-run＝試跑不寫，大家都懂 | `compile` 撞 Python 內建名（只在模組裡蓋掉，`defs.compile` 用起來沒事）；dry-run 這裡印的是整份內容不只清單 |
| 乙 | `defs.build(...)`／`defs.write(...)` | `--build [夾]`／`--check` | cargo build／check、go build | build 白話 | `check` 跟 `agent_def check`（驗掛上的定義）撞意思；cargo check 不印產物 |
| 丙 | `defs.plan(...)`／`defs.apply(...)` | `--apply`／`--plan` | terraform | 先看後做的節奏清楚 | plan 讓人以為印的是「跟現況差在哪」，其實是整份；使用者沒用過這個比喻 |
| 丁 | `defs.compile(...)`／`defs.emit(...)` | `--compile`／`--no-emit` | TypeScript `tsc --noEmit` | emit＝把產物吐出來 | emit 不白話；tsc 的 --noEmit 什麼都不印 |

- 選甲，理由：使用者自己的比喻就是編譯器，同日又裁「以後也用編譯、重新編譯來說」，直接定了方向；`--dry-run` 是建置工具最常見的「只演一遍、不動檔」。
- 落到哪：`python3 agent.py --compile`（編譯＋寫）、`python3 agent.py --dry-run`（編譯、印出、不寫）；Python `files = defs.compile(...)`、`defs.write(夾, files)`。舊旗標 `--write-defs`／`--defs`、舊函式 `defs.defs`／`defs.write_defs` 不留（proto8 當沒有舊版）。行為不變：骨架用 `--compile` 重新編譯後，編譯產物一字不差。
- 用詞：中文說「編譯／重新編譯／編譯產物／靜態連結（抄）／動態連結（借）」，英文 compile／recompile／compiled files／static／dynamic；規矩記進 `wf/workflows/common/user/01-說話授權與記憶.md`「說話方式」與規矩卡。N-70 的「重生／生成時」改成「編譯時／重新編譯」，規矩不變。
- 沒改：`tool_spec`（工具骨架 `tool.py`）的 `--write-defs`／`--tooldef`／`--metainfo` 與 `write_defs`——不在 `agent_spec`，`tools_def` 工具與知識庫 `tools_def.json`／`cli/tool_flags.json` 都靠它，要對齊另開一刀。

## 補：`defs.no`／`defs.by_hand` 換名、工具骨架旗標對齊（11-19 下午，線 aos-defs-rename3-1119）

- 使用者 11-19 下午選項框原話（逐字，頂層轉）：
  - 題「defs.no("grep") 是「從繼承來的工具裡拿掉這支」。名字要不要改？」→ 選「改 defs.drop」
  - 題「defs.load("../reviewer") 是「拿另一隻 agent 當底，回傳它的欄位」。名字要不要改？」→ 選「留 defs.load」
  - 題「defs.by_hand(檔) 是「這個檔是我手寫的，編譯時別蓋它」。名字要不要改？」→ 選「改 defs.extern」
  - 題「工具骨架 tool.py 現在還是用舊旗標 --write-defs，跟 agent.py 的 --compile／--dry-run 不成套。要不要另開一刀對齊？」→ 選「開一刀對齊 (Recommended)」
- 結論（第一筆）：
  - `defs.drop("grep")`＝從包（含 `defs.load` 的底）裡拿掉一支；`defs.extern("system.txt")`＝這份檔你自己寫，`agent.py` 只指到它，編譯時不寫不蓋（像 C 的 `extern`：這裡只宣告，定義在別處）；`defs.load` 不動。舊名不留。
  - `defs.fsm(base.FSM, [...], drop=[...])` 本來就有 `drop=`：意思一樣（從底拿掉格子），一個是模組的函式、一個是 `fsm` 的關鍵字參數，`fsm` 裡不叫 `drop()`，不撞。
  - 行為不變：agent-python 骨架照預設重新編譯，跟 git 一字不差。
- 結論（第二筆，工具骨架 `tool.py`）：
  - 指令 `python3 tool.py --compile [位置]`（編譯＋寫 `_tooldef`／`_metainfo`）、`python3 tool.py --dry-run`（兩份放一個物件 `{"_tooldef.json": …, "_metainfo.json": …}` 印出、不寫）；Python `tool_spec.write(位置, td, mi)`。舊旗標與舊函式名不留。
  - `--tooldef`／`--metainfo` **留著**，理由：`--tooldef` 是 aos-tools 的協定——登記成可執行檔的工具，aos-tools 跑 `那支 --tooldef` 讀定義（`py/aos/apps/tools/tooldef.py`），改了就斷；`--metainfo` 是它的另一半，`tools_def` 一步一步做（`add_metainfo`／`add_tooldef`）時各只要一份，併進 `--dry-run` 要多拆一層、沒好處。兩份一起看用 `--dry-run`。
  - 不另加 `tool_spec.compile()`：`agent_spec` 的 `compile` 是「算出全部檔」；`tool_spec` 算的兩支本來就叫 `tooldef()`／`metainfo()`（就是兩份產物的名字），再包一支沒多出東西。
  - `tools_def` check 的結果行標籤 `made` 沒改（輸出的關鍵字，知識庫與測試認它）；說明文字「remakes／重產」改「recompiles／重新編譯」。
  - 現有工具夾裡編好的定義（tool-python 骨架）用 `--compile` 重新編譯後一字不差。
- 邊緣（沒處理、沒問）：參數名叫 `compile`、`dry_run`、`tooldef`、`metainfo` 的工具，第一個旗標寫成 `--compile` 等會被當成上面的指令，不會當參數；`--tooldef` 一直如此。
- 沒改：今天其他紀錄（含 [aos-base-audit-1119](../aos-base-audit-1119/) repro 裡的 `agent.py` 寫著 `defs.by_hand`）是當時的紀錄，不回頭改。
