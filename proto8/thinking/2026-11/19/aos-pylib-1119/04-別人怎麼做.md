# 別人怎麼做：有命令行又有 Python 庫的系統，「生成 vs 手寫」「薄殼 vs 重寫」「物件式 vs 指令式」各自的下場（簡短）

← [README](README.md)

隊長憑公開文件的一般知識整理，沒有逐家實測；只取跟本題有關的那一點。

| 系統 | 命令行 ↔ 庫怎麼對 | 屬哪一型 | 下場（值得抄／包袱） |
|---|---|---|---|
| **docker** 與 docker SDK for Python | CLI 跟 SDK 都打同一個 HTTP API；SDK 是手寫的物件式（`client.containers.run(...)` 回 `Container` 物件，`c.stop()`） | 手寫、重寫、物件式 | 好用，但 CLI 有的旗標 SDK 常常晚到或名字不同（例如 CLI 的組合指令 SDK 要自己拼）；兩邊各自維護、對不上是常態。教訓：**手寫一層＝第二份真相** |
| **kubernetes** 與 kubernetes-client/python | client 從 OpenAPI 規格**生成**；`kubectl` 另寫 | 生成、物件式 | 什麼都有、不會漏，但名字又長又機械（`CoreV1Api().list_namespaced_pod`），人在 REPL 裡不想打；大家另寫薄的小包裝。教訓：**機械對應保完整，人手感要另外補一點點** |
| **git** 與 GitPython | GitPython 一半是 `repo.git.log("--oneline", n=5)`＝照規則把呼叫翻成 `git log --oneline -n 5`（通用代理），一半是手寫物件（`repo.heads`、`Commit`） | 薄殼代理＋手寫物件 | 代理那一半最耐放：git 加什麼子指令它自動有；手寫物件那一半是 bug 與「跟 git 行為不一樣」的主要來源。**跟本稿推薦的「代理＋少數具名延伸」同形** |
| git 與 **pygit2** | 直接綁 libgit2（C 庫），不經 `git` 指令 | 重寫 | 快、可細控，但行為跟 `git` 指令不完全一樣（設定、hook、新功能要等 libgit2）；兩套實作永遠在追 |
| **sh**／**plumbum** | `sh.git.log("--oneline", n=5)`、`plumbum.local["git"]["log"]`：任何指令都變成 Python 函式，關鍵字參數翻成旗標 | 純薄殼代理、指令式 | 規則一條就全通、零維護；代價是**打錯名字要到執行才知道**、回傳只是字串（結構要指令自己有 json）。本稿的通則表就是這套的收窄版 |
| **boto3**（AWS） | 跟 AWS CLI 共用同一份服務描述檔（botocore 的 json），兩邊都從它**生成**；另有手寫的「resource」物件層 | 生成＋薄的手寫物件 | 描述檔是唯一真相，CLI 與庫永遠對得上；手寫的 resource 層後來官方宣布不再加新功能——**手寫層長不動** |
| **Fabric**／Invoke | 自己定義「任務」，同一個任務既是 Python 函式也是命令行 `fab 任務名` | 庫為主、命令行從庫長出來 | 方向跟 aos 相反（aos 是指令為主）；值得抄的是「一個任務兩種叫法、名字同一個」 |
| **IPython magics** | REPL 裡 `!ls`、`%run`：shell 與 Python 混著打，`!` 的輸出可接回 Python 變數 | REPL 體驗 | 「python repl + shell」最成熟的樣子；本稿的 `sh("…")`＋echo 印出背後指令，是同一種體驗的最小版 |
| **gdb** 與 gdb 的 Python API | `gdb.execute("break foo")` 跑任意 gdb 指令（通用殼）＋ `gdb.Breakpoint("foo")` 物件（增刪改查、有 id） | 通用殼＋斷點物件 | 斷點既能用指令下、也能用物件下，兩邊看到同一批；這正是使用者要的「以斷點為核心增刪改查、以 id 查」 |

## 歸納成三句

1. **生成 vs 手寫**：從同一份描述生成（k8s、boto3）或照一條規則代理（GitPython 的 `repo.git`、sh、plumbum）的，CLI 加東西庫自動跟上；手寫的那一層（docker SDK、boto3 resource、GitPython 物件）一定會落後、長不動。→ 本稿：主體用代理，手寫只留少數具名延伸。
2. **薄殼 vs 重寫**：重寫（pygit2）快但行為永遠跟指令差一點；薄殼慢一點（每呼叫起一個行程）但「Python 做的＝shell 打的」。→ aos 的指令都是幾十毫秒級、人在 REPL 打，薄殼的慢不是問題；而且薄殼對將來 Lisp 整合最友善。
3. **物件式 vs 指令式**：純指令式（sh）零維護但沒有「這一隻」的把手；純物件式（docker SDK）好用但要手寫。多數活下來的走中間：**一個記住對象的小把手＋底下全是代理**（GitPython 的 `Repo` 物件＋`repo.git`、gdb 的 `gdb.execute`＋`gdb.Breakpoint`）。→ 本稿走向甲就是這個。
