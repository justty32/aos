## 各層一段

- **aos-daemon（板子）**：它是 aos-loop 的加大版。沒寫 `exec` 就只當監工；寫了 `exec`，那支程式就是它每圈要跑的「身體」——三個 kernel 範本都這樣掛站。身體是**同步跑**的：身體在跑時，daemon 不看子項（見問題清單 P3）。輸入是 `daemon.json`、環境的 `AOS_STACK`、兩個手把檔與一個信箱；輸出是三份狀態窗與每列的小格。份額與身分在 fork 之後、exec 之前設好。
- **C++ 底件**：aos-exec 照 `_entry`／`argv`／`.env`／指示詞把一個資料夾變成一次執行，cwd 是 `$AOS_WS`；aos-loop 一次次跑並寫 state 窗；aos-fsm 一次跑一格；寫檔都走 aos-util 的「寫暫存再改名」（這點各隊都確認過，可以放心）。
- **信箱**：Maildir 式的三個夾。寄件人只碰 `tmp/`、`new/`，處理者用改名認領。信封上的 `sender` 是寄件人自己報的路徑，而且 aos-post 報 ws、aos-llm 報 stack、aos-mailbox 報 stack（問題清單 P15）。
- **時鐘與 hook**：daemon 本身不認鐘；`on_clock` 是 agent 走到自己的格時才看鐘，所以 agent 在長回合或睡著時，`on_clock` 不跑——掛在 `on_clock` 上的 kernel_gate 也跟著不跑。
- **kernel 站**：全是信進信出。llm kernel 自己不跑模型，是請 daemon 掛一列問腦 proc；框架站判放行、排隊、hold；kernel_gate 是「把站塞進某隻 agent 的鬧鐘」。份額（limits、cgroup）歸 daemon，不歸 kernel。
- **agent 範本**：`_entry` 就是「把自己掛上 daemon」。每支工具一開頭都用 `aos-agent ctl who` 問「我是誰」，而這一步在設了 `AOS_KERNEL` 時要經 kernel 問表（問題清單 P4）。
- **11-19 新上層**：agent.py 只在生成時跑，產出定義夾之後就跟執行期無關（使用者說的「C 和 .o」）。但**正在跑的 agent 跟定義夾是活連結**：定義夾裡的檔有的起跑時讀一次（loop.json），有的每格讀（fsm.json、tools、system），stack 裡的「自己那份」照定義當下宣告的檔名去找——使用者 11-19 定為特性（「重新編譯這塊，我更願意稱其為"特性"」），實測樣子記在問題清單的「特性」一節（P6、P7、P13）。

## 邊界上誰擁有哪個檔

| 檔 | 誰寫 | 誰讀 | 保證 |
|---|---|---|---|
| `procs_state.json`、`state*.json` | 只有 daemon | ctl、上層、gdb、全景頁 | 原子寫；procs_state 最多每 200ms 寫一次 |
| `ctl.json`、`procs_ctl.json` | 人、工具 | daemon | 宣告式，procs_ctl 會蓋過信 |
| `procs_requests/` | 任何寄件人 | daemon | 改名投遞；一封認領不了會卡整箱（P2） |
| 定義夾 | agent.py、agent_def、人 | aos-loop／fsm／tools 在執行期 | 沒有版本、沒有快照；重生逐檔改名 |
| `<stack>/tools.json` 等「自己那份」 | self_*、tools 指令 | agent | 用 `$override` 指回定義夾的絕對路徑 |
| `used.json`、ledger | llm kernel | llm kernel | 壞了就每輪報錯，問腦全停（P5） |
| 時鐘登記表 | 任何 agent、aos-clock | aos-clock | 讀改寫沒鎖（P9，推測） |
