## 先講結論

**基底整體是穩的，平常的路走得很順；洞都在「出事的時候」。** 打個比方：板子（daemon）開機、跑程式、關機、被拔掉程式再開都正常，零件之間傳紙條（信箱）不丟不亂；但板子上只有一個管理員，他一被纏住或被一張大紙壓垮，整塊板子就停；一張卡住的紙條能堵死整個收件匣；管理員沒好好下班就斷電的話，他記的「誰在跑」那張名單會掉一大半。

現有的 293 支測試在乾淨複本上全綠，但**這次找到的問題沒有一條是現有測試會抓到的**——它們都落在測試沒走到的縫裡。

### 最該擔心的五件

1. **一個 daemon 管全部，而它會被拖住或拖垮**（P1、P3；使用者 11-19 已答 P3 這類結構風險「自行承擔」，見下）。daemon 的「身體」（三個 kernel 範本的站就掛在這）跑的時候，它不顧任何一支子項；一隻 proc 失敗時，daemon 會把它整份錯誤記錄讀進記憶體——記錄 1 GB 就吃 2 GB，記憶體受限時 daemon 自己倒、旁邊沒事的 proc 一起被收。一隻狂印的 proc 5 秒就能寫 200 MB 錯誤記錄。P1 是一處小修（只讀檔尾），不是結構問題，仍列在第 4 題。
2. **一封認領不了的信能堵死整個信箱**（P2）。不用崩潰就會發生：daemon 的控制信箱、kernel 站、llm kernel 被一封權限不對的信擋住後，之後所有的信都不處理，那封信還在就一直擋。今天要有人弄壞權限才會碰到，但換身分的 agent 寄信（sub:N 的下一刀）會自然碰到。
3. **kernel 這層變成「連問自己是誰都要經過它」**（P4、P5）。設了 `AOS_KERNEL` 而那個 kernel（例如 kernel_gate 那隻 agent 正在長回合）3 秒不回，底下的 agent 連自己的信箱都讀不了、鬧鐘也設不了。llm kernel 的額度帳本壞一次，全樹的腦就無聲卡住，表上看起來一切正常。
4. **沒好好收工就斷電或重開機，動態掛上的 agent 會從表上消失**（P18，Argon 審後升級）；崩潰復原還有幾個邊角（P8 stack 一時寫不了再起會掉列；P11 剛起一批 exec 型 proc 時 daemon 被殺，重起後跑兩份）。
5. **出事時看不出來、同帳號下沒有邊界**（P12、P14、P19；P15、P16）。撐過 3 秒才掛的 proc 會被無限重起、表上一直顯示 running；stop 卡在 stopping 沒有上限、也不說卡在哪；端點程式壞了 agent 無限冷卻重送。信封上的寄件人是自己填的，三種寄法還填得不一樣，額度帳因此可能記錯本；每支 proc 拿到整份環境（含 API key），sub:N 是「把它關住」而不是「保護別人」。

另外，今天的「重新編譯」（agent.py 重生、set-def）改定義夾時，跑著的 agent 會立刻讀到——使用者 11-19 定為**特性**，報告照實記下它的樣子（[02「特性」一節](02-問題清單.md)），方向只留「文件寫明哪些檔起跑讀、哪些每格讀」。

### 可以放心的

- **寫檔都是原子的**（寫暫存再改名）：狀態窗讀 3 萬多次、重生途中讀定義夾 3 萬多次，沒有一次讀到半寫的 JSON。注意這只擋「讀到半個檔」，不擋「兩個人讀改寫互蓋」（P9）、也沒查有沒有 fsync（真斷電沒測）。
- **信的投遞不丟不亂**：200 封連寄、兩個行程並發寄、有序寄都不丟不重；壞信（壞 JSON、缺欄、空夾）不會卡住收件人；寄給已移除的收件人會明確報錯。例外是上面第 2 件：權限擋住的那一封會卡整箱。
- **daemon 被 kill -9 再起，loop 型的 proc 照 pid 接回、不重起**；鎖立刻放、子行程不帶著鎖（O_CLOEXEC 加 atfork）；同一個 stack 不會起兩台。
- **llm kernel 被 kill -9 很穩**：在途的照收、不重打、帳不重複。額度三層、hold、期限、兩個 kernel 都照文件。
- **份額（rlimit 五種）都真的會命中**，表上看得到（`procs` 數的是整個帳號的行程，文件與 warning 已寫明）；sub:N 真換身分的身分、檔擁有者、收得掉、接得回都照文件——但它**還寄不出信**（已知），所以目前跑不了要收發信的 agent。
- **起停、sleep／wake、時鐘、hook 失敗的處理**都照文件；現有 293 支測試全綠。

### 沒查到、沒測到的

- cgroup（這台沒 systemd user）、系統時鐘跳（不能 sudo）、磁碟滿與 inode 用完、真斷電與 fsync、真的跨帳號寄信、eca 身上的斷點扣住、長時間（數小時）運轉、真的重開機（P18 的重開機那半是讀程式）。
- Argon 提的、本線沒驗的失敗模式（[06](06-Argon審與採納.md)）：持 aos-lock 的行程被 SIGSTOP 或斷點扣住時有序寄信會不會全卡、llm kernel 掛的問腦列會不會在表上越積越多、ledger 半行壞掉、大信在收件端的記憶體、單一環境變數超過 128 KB 時 exec 失敗、壞信讓 mail_notify 一直假喚醒。
- `aos.py` 入口與 `ag.load`：不在基準 HEAD 3c4cc4c52（之後的 commit 才交），只讀了設計。
- NORMS／CONCEPTS 只對了跟基底直接有關的條文（N-16、N-17、N-28、N-42、C-47），其餘抽查。

### 還沒答的

- **第 2 題：「我是誰」要不要繞過 kernel？**（P4）(a) 有 `$AOS_STACK` 就直接答——kernel_gate 底下的 agent 不再被主人拖住；要注意 `who` 回的欄位（列名等）若要表上的資料，光看環境拿不全；(b) 問不到時退回問 daemon——改動小，但**等於留一條繞過 kernel 的路**，而且仍有 3 秒延遲（Argon A15）；(c) `who` 改成直接唯讀 daemon 的狀態窗（procs_state.json），不寄信——不經 kernel 排隊也不繞過 kernel 的放行判斷，但讀的是哪一台的窗要定（Argon A15 補的選項）；(d) 只補知識庫——行為不變。
- **第 4 題：要不要開一條修補線，修幾個不牽涉方向的小洞？** 候選：P1（只讀錯誤記錄的檔尾）、P2（認領失敗跳過那一封）、P5（帳本壞了從 ledger 重算並上表——不是歸零）、P12（auto-restart 加退避並上表）、P8／P18（沒收工就不在時，列改留 stopped 不刪）；Argon 補的候選：P9（時鐘登記表加鎖）、P10（`aos-mailbox read` 預設不讀專區）、P20（gate 的 stop 帶期限）。(a) 開，一條修一刀、每刀配測試；(b) 只修 P1、P2、P18；(c) 先不修，留在清單。
- **第 5 題：同帳號下的邊界要收到多緊？**（P15、P16）(a) 照現在「單人使用、模型可信」的前提，只寫明；(b) 先做便宜的：envs 檔 0600、proc 只傳需要的環境變數——**只擋得住換了身分（sub:N）的 proc，同帳號沒換身分的照樣讀得到**（Argon A18）；(c) 排上「信夾擁有者認寄件人」（K9）與活樹權限收緊（K10）——sub:N 寄信那一刀前要先有。另：P15 寄件人三種寄法不一致，已經讓 per-sender 額度可能記錯本，這半不必等邊界大方向就能修（Argon C5）。

## 怎麼重跑

重現腳本假設放在 `~/.aos/scratch/aos-base-audit-1119/<隊員名>/repro/`，旁邊有 `../bin/clean`（unset 全部 `AOS_*`、`AOS_HOME` 指乾淨複本、PATH 加複本的 bin）與 `../src/`（`git archive` 抄出、`install.py` 過的複本）：

```sh
S=~/.aos/scratch/aos-base-audit-1119
mkdir -p $S/src && git -C ~/repo/aos archive HEAD | tar -x -C $S/src
(cd $S/src/proto8 && <清環境後> python3 install.py)
cp -r proto8/thinking/2026-11/19/aos-base-audit-1119/repro/<隊員名> $S/<隊員名>/repro
cd $S/<隊員名> && ../bin/clean bash repro/<腳本>      # e-upper 先 up.sh、mkdefs.sh，做完 down.sh
```

每支腳本第一行寫它測什麼；它們只在自己的子夾起 daemon、收尾時 shutdown 自己的。
