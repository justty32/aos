## 會卡死（5 條）

### P1　一隻 proc 的 stderr 很大，失敗時會拖垮整台 daemon　✔隊長重現
- **現象**：proc 退非 0 時，daemon 把它的 `stderr.txt` **整份**讀進記憶體只為了取最後一行當 reason。1 GB 的檔讓 daemon 記憶體衝到約 2.1 GB、那列 10 秒後才更新；daemon 的位址空間限 600 MB 時，daemon 自己 `Internal std::bad_alloc` 退出，**旁邊無辜的 proc 一起被收**。而 stderr.txt 長得很快：一隻狂印的 proc 不到 5 秒寫 200 MB（約 40 MB/s），清道夫 10 分鐘才來一次。
- **重現**：`repro/f-struct/e1_big_stderr.py 1024 600`（看 daemon 死）；`repro/c-daemon/t10_logs.sh`（看長多快，帶 200 MB 上限）。
- **嚴重度**：會卡死（整台倒，一隻 proc 害全部）。沒設記憶體上限時是被 OOM 收掉還是只是慢，是推測。
- **影響**：所有掛在 daemon 上的東西；kernel 站掛了，上面的 agent 全等。
- **方向**：(a) 只讀檔尾幾 KB 取最後一行（最小改動）；(b) 再加 stderr 的大小上限或輪替；(c) 只寫進文件 08。
- **依據**：實測。`cpp/aos-daemon/src/daemon/failure.cpp:22`、`cpp/aos-util/src/files.cpp:138-164`。

### P2　信箱裡一封認領不了的信，整個信箱停擺　✔隊長重現
- **現象**：`aos-post take` 改名碰到權限這類錯時整次報錯，不跳過那一封。daemon 的 ctl 信箱被擋住後，之後的 add／rm／stop 全不套、ping 回 `DaemonFailed`；kernel 站、llm kernel、`aos-mailbox read` 也一樣每輪報錯。另外，已經搬進 `cur/` 的好信要等 daemon 重起才套。
- **重現**：`repro/d-mailkern/daemon_ctlbox_bad.sh`（「unclaimable letter」段）、`daemon_ctlbox_stuck_after.sh`。
- **嚴重度**：會卡死。今天要有人把信夾權限弄壞才觸發；**跨帳號寄信**（sub:N 往下走就會有，信夾屬別的 uid）會自然碰到——這點是推測。
- **影響**：sub:N 的下一刀（換身分的 agent 寄信）；所有收信的站。
- **方向**：(a) 認領失敗的那封跳過並記 warning，其他照收；(b) 移到「壞信」夾；(c) 先不動，做 sub:N 寄信前一定要先處理。
- **依據**：實測。`cpp/aos-util/src/dirs.cpp:51-60`、`cpp/aos-daemon/src/daemon/mailbox.cpp:42-58`。

### P3　daemon 的「身體」在跑時，整台 daemon 不照顧任何子項　✔隊長重現（a-docs、f-struct 各一支）
- **現象**：daemon 自己的 exec（三個 kernel 範本的站都掛在這裡）是同步跑、沒有時間上限。身體跑的期間，子項退出不收、stuck 不判、auto_restart 不起、10 秒強收不做、ping 不回。實測身體 `sleep 6` 時子項第 7 秒才被看到退出；身體 `sleep 12` 時 ping 10 秒才回。文件只寫了「poke 不打斷身體」。
- **重現**：`repro/a-docs/A-body-blocks.py`、`repro/f-struct/e2_body_blocks.py`。
- **嚴重度**：會卡死（站一輪慢，整台一起慢；站的 hook 設 `timeout_ms: 0` 就是無限）。
- **影響**：llm kernel 那台的每一列問腦 proc；kernel_gate 以外的所有站。
- **使用者 11-19 已答**：「整塊板子只有 daemon 一個管理員 <- 自行承擔風險。」（頂層的理解：維持現狀、不改 daemon 核心，頂多文件寫明。）
- **原列的方向（留底）**：(a) 文件寫明，站改用「站是一列 loop proc」的擺法——Argon A14 補：那樣站的 stdout 會進 /dev/null（P22）、掛問腦 proc 要多寄一封信、站自己的 hook 卡住照樣卡站；(b) 身體改成非同步子行程；(c)/(d) 給身體與站內 hook 預設時間上限。
- **依據**：實測。`cpp/aos-daemon/src/daemon/tend.cpp:297`、`body.cpp:23-28`。

### P4　設了 `AOS_KERNEL`、而那個 kernel 一時不回，agent 連自己的信箱都讀不了　✔隊長重現
- **現象**：每支工具開頭用 `aos-agent ctl who` 問「我是誰」，設了 `AOS_KERNEL` 時這一步要寄信問 kernel、等 3 秒。kernel 不回時，`mailbox_peek`、`mailbox_send`、`clock_register`（連給了 box 也一樣）、`self_*` 全部 `KernelFailed`。kernel_gate 的 kernel 就是某隻 agent，牠在長回合或睡著時站不跑——**底下的 agent 全部收發不了信**。知識庫的錯誤頁也查不到 `KernelFailed`。
- **重現**：`repro/a-docs/B-kernel-who.sh`。
- **嚴重度**：會卡死。
- **影響**：kernel_gate 底下的每一隻；aos.gdb 的 `say`／`listen`（也走 aos-agent）。
- **方向**：(a) `who` 有 `$AOS_STACK` 就直接答，不問 kernel；(b) 問不到退回 `$AOS_DAEMON`；(c) 只補知識庫。
- **依據**：實測。`py/aos/agentlib/mailbox_call.py:16-25`、`py/aos/apps/agent/ctl/who.py:40`、`py/tools/agent/clock_register/_entry:57`。

### P5　llm kernel 每輪出錯時，所有問腦無聲卡住　✔隊長重現
- **現象**：`used.json`（額度帳）壞一次，llm kernel 每輪報 `UsedBad`、什麼都不處理；`aos-llm ask` 沒有逾時一直等（實測 `timeout` 收掉，退 124）。daemon 表、狀態窗都正常，只有 stderr 每輪一行錯，agent 端的提醒只看 kernel 的 pid 活著就不提醒。P2 的情況也會讓它這樣。
- **重現**：`repro/d-mailkern/llmk_budget.sh`（「corrupt used.json」段）。
- **嚴重度**：會卡死（全樹的腦停掉，看起來一切正常）。
- **影響**：每一隻問腦的 agent（agent-fsm、agent-python、eca 經 kernel 的）。
- **方向**：(a) 帳本壞了改名留底、從明細帳 `ledger.jsonl` 重算（不要直接從 0 開始——那等於額度歸零、繼續花錢；Argon A17），重算不了就照舊拒絕但把 `UsedBad` 寫上表；(b) 每輪錯誤寫進 state 窗讓表看得到；(c) 給 ask 預設逾時。
- **依據**：實測。`py/tools/aos/kernel_llm/budget.py`。

## 特性：改定義夾，跑著的 agent 立刻讀到（使用者 11-19 定為特性）

使用者 11-19 看了初稿：「重新編譯這塊，我更願意稱其為"特性"。」（頂層的理解：維持活連結，不做快照、不加拒絕檢查；方向只留「文件寫明哪些檔起跑讀、哪些每格讀」。）所以下面三條不列嚴重度、不列成問題，只照實記下這個特性在實測裡的樣子，給寫文件的人用。

- **哪些檔什麼時候讀**（實測＋讀程式）：`loop.json` 只在起跑時讀一次；`fsm.json`、`tools.json`、`system.txt`、`llm.json`、`hooks.json` 每格讀；stack 裡「自己那份」照定義當下宣告的檔名去找，`$override` 寫的是定義夾的絕對路徑。重生是逐檔「寫暫存再改名」：讀 38520 次沒讀到空檔或壞 JSON，有 133 次新舊混搭（腦看舊工具、act 用新工具時腦收到 `ToolMissing`，agent 不死；Argon A2 提醒：混搭若落在 fsm.json 與格子腳本之間，可能轉錯格，沒實測）。
- **P6　重生把狀態機的格改名**：停在舊格的 agent 下一拍 `StateUnknown`；帶 auto-restart 的連死三次後停；`ctl start` 救不回（`stage.txt` 還寫舊格名），要手改。✔隊長重現，`repro/e-upper/e2_fsm_rename.sh`（先 `up.sh`、`mkdefs.sh`，做完 `down.sh`）。
- **P7　`ctl set-def` 後 stack 那份工具仍疊在舊定義上**：system、llm 換成新的，工具還是舊定義那組（set-def 印一行提醒）；之後刪掉舊定義夾，下一封信 `PathMissing` → `ToolsBad` → stopped。✔隊長重現，`repro/e-upper/e5_setdef_old_tools.sh`。
- **P13　重生拿掉或改名的東西，stack 的覆寫與斷點跟著不生效**：斷點下好後重生拿掉 HOOKS，before_tool 不再停；重生把 system 改檔名後先前 `system set` 的那份不生效、檔還在、沒提示（實測，`repro/e-upper/e10_regen_drops_hooks.py`、`e7_own_copy_orphaned.sh`；tools、llm、hooks 改名是推測）。另：agent-python 骨架不帶 hooks（使用者 11-19 裁定維持），但知識庫 mailbox.json、world.json 寫「範本都有 mail_notify」——這條是文件舊，跟特性無關，照列。
- **文件要寫明的**（方向，照頂層轉述只留這一條）：哪些檔起跑讀、哪些每格讀；改格名、刪舊定義夾、拿掉 hooks 時跑著的 agent 會怎樣；set-def 後 stack 那份 tools 指著誰。

## 會丟資料（4 條）

### P18　daemon 沒好好收工就不在了（被殺、WSL 被關、斷電、重開機），期間死掉的 proc 重起後整列消失（Argon 審後升級）
- **現象**：daemon 不在的期間 proc 死了，daemon 再起時那一列（沒設 auto_restart、不是寫在 daemon.json 的）直接下表，沒有 log、沒有原因；同樣的死法發生在 daemon 醒著時卻留 stopped＋code＋reason。**重開機走同一條路**：表上的 boot_id 跟這次開機不同＝表上的行程都當不在，所以 daemon 沒來得及正常收工就重開機（`wsl --shutdown`、斷電、daemon 被 OOM 收掉）時，所有用 `ctl add` 掛上、沒帶 `--auto-restart` 的 agent 都從表上消失；定義夾與 stack 夾還在，要人一隻隻重掛。正常 shutdown 再開機不會（收工時列會睡下）。文件 08 寫了「照自然結束下表」，沒寫重開機的後果。
- **重現**：`repro/c-daemon/t03_crash_adopt.sh`、`t09_table_truth.sh`（daemon 不在時殺 proc）。重開機那半讀程式：`cpp/aos-daemon/src/daemon/adopt.cpp:197-199`（same_boot）、`:306-310`（running、沒 auto_restart、不在收工中＝跳過）。
- **嚴重度**：會丟資料（丟的是「有哪些 agent 在跑」的登記）。
- **影響**：所有用 `ctl add`、subagent、agent.py 生出後掛上的 agent；全景頁。
- **方向**：(a) 改留 stopped（或 sleeping）＋reason「daemon 不在時結束」，讓人決定要不要起；(b) 至少寫 log；(c) 維持，文件寫明「沒正常收工就重開機＝動態列會掉，要留就用 auto_restart 或寫進 daemon.json」。
- **依據**：daemon 不在時殺 proc＝實測；重開機＝讀程式推的（沒重開機實測）。


### P8　崩潰後若 stack 一時寫不了，重起會收掉健康的子項，用信加的列整列消失　✔隊長重現
- **現象**：daemon 被 kill -9 後，在寫不了的 stack 上再起：第一份窗寫不成就退 1，但退之前把剛接回、還健康的子項全送 TERM；stack 修好再起，用信或 `ctl add` 加的列不見了，只剩 daemon.json 寫死的列。
- **重現**：`repro/a-docs/A-ro-restart.py`。
- **嚴重度**：會丟資料（丟的是表上的登記與正在跑的工作；stack 夾還在）。觸發條件少見（磁碟滿、權限暫時錯）。
- **影響**：所有用 `ctl add` 掛的 agent、sub:N 列。
- **方向**：(a) 寫不了就直接退，不走收工；(b) adopt 遇到死掉的 running 列改留 stopped 不刪；(c) 只寫進文件 06／08。
- **依據**：實測。`cpp/aos-daemon/src/daemon/table.cpp:81`、`loop.cpp:252-258`、`adopt.cpp:309`。

### P9　時鐘登記表的讀改寫沒有鎖（推測）
- **現象**：時鐘寄信、每 100 格自我檢查、agent 的 add／rm 都是「讀整份、改、整份寫回」，同時發生時後寫的蓋掉先寫的，新加的鬧鐘可能默默不見。程式註解自己承認。
- **重現**：沒做成穩定重現。
- **嚴重度**：會丟資料（罕見）。
- **影響**：clock_register、eca 的叫醒、agent 的定時。
- **方向**：(a) 用現成的 aos-lock 加鎖；(b) 知識庫寫明。
- **依據**：讀程式推的。`py/aos/clock_register.py:258-306`、`py/aos/apps/clock_register/main.py:215-236`。

### P10　`aos-mailbox read` 沒帶 `-s` 時預設讀使用者專區、讀完即刪（推測）
- **現象**：設了 `AOS_LINUX_USER_STACK` 的 shell 裡，任何 agent 打 `aos-mailbox read` 都會讀到使用者專區的信並收走。11-13 的問題總表就記了，沒找到修的 commit。
- **重現**：未重現（不碰專區）。
- **嚴重度**：會丟資料（使用者的信）。
- **影響**：使用者專區（現在 aos-user 本體壞著，暫時碰不到）。
- **方向**：(a) 預設改成 `$AOS_STACK`；(b) 讀專區要明寫旗標。

### 其他會誤導的小條（推測或影響小）
- **手動 sleep 不跨 daemon 重開保留**（Argon A7 建議從「只是醜」升上來）：為了止血把一隻 sleep 掉，daemon 一重起它自己醒來（實測，`repro/c-daemon/` 報告 F9）。
- **`rm` 回 0 時列還在 stopping**，`rm X && add X` 會被擋（實測，同上）。
- **shutdown 時在途的問腦**醒來會重打端點（每封 2 次），帳只記 1 次，額度少算（實測，`repro/d-mailkern/llmk_shutdown_two.sh`）。kill -9 時反而不會（可以放心那段）。
- **信箱的靜默失敗**：daemon 回信寄不出、信收不掉時例外直接吞掉；`mailbox_warning` 只留最後一封壞信的原因（推測，`cpp/aos-daemon/src/daemon/mailbox.cpp:96-98,176-188`）。
- **判 stuck 用牆鐘**：系統時鐘往前跳可能誤判 stuck，設了 `restart_on_stuck` 的會被重起（推測，`stuck.cpp:46-75`；這台改不了時鐘，沒測）。
- **`aos-post take` 不驗檔型**：在信箱放一根 FIFO，認領時 open 會永遠卡住（推測；要有不信任的寫入者才成立）。
- **觀察者 proc**：目標被 rm 後，每圈往自己的 stderr.txt 寫約 350 位元組 warning，不會停（實測，`repro/e-upper/e6_watcher_target_life.py`）。
- **clock.json 說「給了 box 就不用在表上」**，其實照樣要先問「我是誰」（實測，同 P4 腳本）。
- **daemon-kernel 範本的 `max_running` 把自帶的 `_sweeper` 也算一格**（實測，`repro/d-mailkern/kstation.sh`）。

## 只是醜
- auto_restart 上限訊息寫「restarted 3 times」，實際重起 2 次；退 0 也寫「failed to start (code 0)」。
- 重生是逐檔「寫暫存再改名」，38520 次讀取沒讀到空檔或壞 JSON，但有 133 次新舊混搭；腦看舊工具、act 用新工具時腦收到 `ToolMissing`，agent 不死。
- 信沒有大小上限（50 MB 正文 send 吃 258 MB 記憶體；Argon A1 提醒收件的 daemon／kernel 解大信也可能同樣放大到撐爆，沒測收件端，推測）；peek 與 mail_notify 把壞信也算成新信。
- 撞到 `file_mb` 時 Python 預設忽略 SIGXFSZ，表上沒有 `limit_hit`，只看得到 code 120。
- `ctl add` 對沒 +x 的腳本只說「不是 JSON」；llm kernel 身體偶發退 141 一輪、下一輪就好（原因沒查明）。
- 文件小舊：07-建置與測試只列 6 支（實有 14 支）；04 的 state.json 欄位表漏 `cgroup`、`group`；definition.json 的檔案清單不全。
