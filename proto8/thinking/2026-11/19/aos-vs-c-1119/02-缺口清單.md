aos 跟 C 比真的有同一個問題、而且現在會痛或很快會痛的缺口，依痛感排序；每條寫現象與重現、不補會怎樣、最小補法、跟已裁事項的關係。做不做由使用者定。

排序的想法：**無聲**的排前面（壞了沒人說，比壞了會報錯痛）；**一次倒一片**的排前面；只是不方便的排後面。

**痛感順序（Argon 審後）：G1 > G2 > G3 > G7 > G6 > G4 > G5 > G8 > G9 > G10 > G11 > G12 > G13。** 編號是初稿就有的代號、留著好對照；G7（相依改了下游無聲跑舊的）照上面的原則比 G4（照標準流程跑 `tools_def check` 就不會發生、發生時有錯誤行）與 G5（只在兩個 `AOS_HOME` 並存時）痛，所以往前移（Argon A18 採納）。重現腳本在 [repro/](repro/)，腳本裡的路徑寫的是暫存夾 `~/.aos/scratch/aos-vs-c-1119/`。「最小補法」只寫一兩句長什麼樣，不是設計稿。

## G1　沒有「undefined reference」：編譯和 check 都放行不存在的工具、格程式、錯型別的 LLM 值

- **現象**：`defs.tool("ghost", defs.home("/lib/tools/base/nope"))`、狀態格 `["python3","nocell.py"]`、`LLM={"temperature":"hot"}`、`model:"no-such-brain"`，`python3 agent.py --compile` 都退 0，`agent_def check` 都回 `{"problems": []}`。掛上以後：ghost 從腦的工具清單**無聲消失**（只在 `stderr.txt` 每格一行 `skipped: PathMissing`，表上照樣 running）；格檔不在、LLM 型別錯則一起來就停（`RunFailed`、`CfgBad`）。三位隊員各自撞到，頂層另跑一次 ghost 確認。
- **重現**：`repro/b/r1_missing_tool.sh`、`repro/a/t06-runtime.sh`（e2 e6 e7）、`repro/c/repro-lint.sh`。
- **不補會怎樣**：寫錯一個路徑要掛上、等到腦需要那支工具才發現；腦看不到那支工具就當它不存在，不會說「少了 X」。在 C，這是連結器第一個會擋的錯。
- **最小補法**：三件分開看（Argon A15 採納）：
  - LLM 的值套 agent-fsm 執行期那套型別規則：純記憶體內的檢查，跟現在查 `timeout_ms` 是整數同類，不用讀任何檔、對交叉編譯沒代價。
  - 工具路徑：每個 `path` 都是一個檔路徑（或指示詞），解一次查在不在，跟 `std.tool()` 今天做的一樣。
  - 格程式：`argv` 是任意命令列，編譯器分不出哪個字串是檔名；只能查寫成 `defs.home`／`defs.env` 指示詞的、或檔在本夾裡的。
  - model 名在編譯時看不到 kernel，只能留給執行期。
- **跟已裁的關係**：不碰「不記帳」「check 不順手重新編譯」——這是唯讀的檢查。

## G2　「靜態連結」只靜態了名單；`AOS_HOME` 一變（升級）就無聲壞或一次倒一片，也沒有版本可比

- **現象**：預設 `--static` 只把「包裡有哪些工具」抄進 `tools.json`，每支工具仍寫成 `$AOS_HOME/lib/tools/…`，工具程式、`_tooldef`、狀態格程式都在執行時讀。所以 std 改了一支工具的參數名，靜態連結的 agent 下一次問腦就換新說明；搬走一支，清單少一支、沒人報錯。模擬升級時拿掉一格（`templates/agent-fsm/idle.py` 改名）：**這個 home 上 9 隻 agent 3 秒內全部 `stopped 2`，停著不會自己回來**。包、工具、std、aos 本身都沒有版本號。
- **重現**：`repro/b/r4_home_change_kills.sh`（會停掉那棵樹上的 agent，用自己的暫存樹跑）。
- **不補會怎樣**：`git pull`＋`install.py`（它會刪孤兒檔）之後，要一隻一隻 `ctl start`，而且事前不知道哪些定義引用了被拿掉的東西。兩台機器版本不同時，同一份定義在兩邊行為不同、看不出原因。
- **最小補法**（互相獨立，可單選）：
  - 一支唯讀檢查「掃表上每隻 agent 的定義、解每個 `$env` 路徑、列出缺的」，升級前後各跑一次；
  - `install.py` 在 `$AOS_HOME` 寫一個版本或 commit 戳，兩台機器、兩個 home 一比就知道是不是同一版；
  - 真的靜態連結：一個編譯選項把用到的工具（或至少 `_tooldef.json`）、格程式抄進定義夾，之後 std 怎麼改都不影響它；也順便解了 G3 的搬家（Argon A12 補的選項）。代價：定義夾變大、std 的修正要重新編譯才到、抄進來的工具程式還是 import `$AOS_HOME/lib` 的 aos 套件，不是全斷開。
  - 把版本戳寫進 `_metainfo.json` 會碰到「編譯產物不記帳」的精神、也讓不同版上編出的產物不再一字不差，這裡不列（Argon A12）。
- **跟已裁的關係**：「跑著的 agent 立刻讀到重新編譯後的**定義夾**」是已裁特性；這條講的是**std（`AOS_HOME`）**變了，同一個「活連結」性質延伸到庫。若使用者認為這也屬於那個特性，本條只剩「事前看得出受影響的有誰」那半。骨架 README 開頭第三點其實寫了工具程式與格「read when the agent runs, like a library linked dynamically」（頂層初稿說沒寫，Argon A1 指正），但它說「shows up at the agent's next start」，實測是下一次問腦就變。

## G3　分享與搬家時依賴不跟著走：庫綁在 `AOS_WS`、`defs.load` 把底的路徑改寫成本機絕對路徑

- **現象**：
  - 庫根寫 `defs.env("AOS_WS", "/lib/my")` 時，同一份編譯產物換一個 `-w` 掛上，庫的工具**無聲消失**（表上 running，stderr 3 行 skipped）。
  - `defs.load("../base2")`（收字串路徑，README 的例子也這樣寫）把底裡寫成相對路徑的工具改寫成本機絕對路徑（`/home/…/base2/mytool`），沒有警告；收指示詞 `defs.load(defs.env(...))` 時寫成指示詞，沒這個問題（Argon A2 指正、頂層核過 `_moved`）。README 說「the base folder does not have to be there later」講的是定義不記上一層（N-70）；工具實體若放在底夾，底夾刪了照樣 PathMissing。
  - 底的狀態格 `argv` 只在「那個檔在底夾裡存在」時才改寫成底夾路徑（`agent_spec_load.py` 約 179 行）：編譯當下檔還沒放好就不改寫，衍生夾無聲改去自己夾裡找；argv 裡剛好跟底夾某檔同名的普通參數會被改寫（Argon A7，讀程式確認、沒實跑）。
  - tar 一夾定義到另一個 `AOS_HOME`：自己的庫沒跟著走（工具 broken）、動態包少的工具無聲不見、`AOS_WS` 沒設時 `aos-tools ls` 整個失敗、在新地方重新編譯 SpecBad（庫根不在）。
  - 庫沒有清單檔：不能寫要哪個 aos、依賴哪些 std 工具。
- **重現**：`repro/b/r5_lib_needs_ws.sh`、`repro/c/repro-pack.sh`、`repro/a/mk.sh der2b repro/a/bodies/der2.py` 後 `--dry-run | grep -A2 '"loc"'`。
- **不補會怎樣**：把一隻 agent 給另一台機器（家機↔公司機）或另一個工作區時，少工具而且只有 stderr 知道。今天兩台機器並行，很快會碰到。
- **最小補法**：編譯時寫進絕對路徑（含 `defs.load` 的改寫）印一行 warning；庫根放一個小清單檔（名字、要的 aos 戳記、用到的 std 工具），`defs.lib` 編譯時讀它查。配 G1 的路徑檢查就能在掛上前抓到「ws 不對」。
- **跟已裁的關係**：`-I` 已裁「先明寫」，這條不提搜尋路徑；只講明寫的路徑換地方後無聲失效。

## G4　`tool.py`：執行的是原始碼、腦看的是編譯產物，沒重新編譯時兩邊不一樣

- **現象**：`tool.py` 加了一個必填參數 `c`、沒重新編譯：`aos-tools get` 給腦看的仍是 `{a,b}`；照說明傳 `{"a":2,"b":3}` 得到 `ArgumentsBad missing c (required)`。執行時 tool_spec 用的是 `tool.py` 現在的 PARAMS。
- **重現**：`repro/a/t05-tool.sh`（drift 那段）。
- **不補會怎樣**：腦照說明叫，一直被拒，錯誤行看不出原因，會一直重試（接 G9）。改的是選填參數、預設值、說明文字時連錯誤都沒有，只是腦拿到的說明是舊的。照標準流程（改完跑 `tools_def check`，它會重新編譯）不會發生，跳過那步才會。
- **跟 C 比**：初稿寫成「標頭和 .c 不一致」不準——`PARAMS` 與 `run` 寫在同一支 `tool.py`，只有一份原始碼；不一致是因為 `_entry.json` 直接跑原始碼、腦讀的是編譯產物。比較像「改了 .c 沒重新編譯，卻有人直接解譯原始碼在跑」，是 G7（沒有 make）在工具上的特例（Argon A11 採納）。
- **最小補法**：aos-tools 讀工具時，夾裡有 `tool.py` 就把它算出的 tooldef 跟 `_tooldef.json` 比內容，不同就在 agent 的 stderr 印一行 warning（給人看，Argon A14 補的選項）。初稿的兩個補法各有洞（Argon A14 採納）：在工具錯誤行加「run --compile」——錯誤行是回給腦的，腦不一定能改 `$AOS_HOME` 的工具，而且沒報錯的那幾種抓不到；比檔案時間——`git checkout`、`cp -r` 後時間順序不可靠，會誤報。
- **跟已裁的關係**：「編譯產物直接蓋、不記帳」不受影響；這是執行時比對兩份現有的檔。

## G5　`ldd` 會說錯：`tools ls` 用的是叫它的人的 `AOS_HOME`；一隻 agent 可以執行檔與庫混版

- **現象**：用 `ctl add --envs AOS_HOME=home2` 掛的 agent，從原本的視窗 `aos-agent tools ls -l` 說 glob 在 `src/…/glob`，`observed.jsonl` 記的卻是 `home2/…/glob`。這隻 agent 的 `aos-loop`／`aos-fsm` 走 daemon 的 `PATH`（舊 home 的 `bin`），工具與格走 home2。表與 `ctl state -j` 都不顯示它的 `AOS_HOME`。
- **重現**：`repro/b/r3_ldd_wrong_home.sh`。
- **不補會怎樣**：查「這隻到底連到哪裡」時拿到錯答案；兩個 home 並存（換版、測試）時最容易出事。
- **最小補法**：`tools ls`、`ctl state` 用 agent 的 `exec.json` envs（沒有就用 daemon 的）來解路徑，並把用的 home 印出來。

## G6　動態連結的包長出同名工具，無聲換掉；骨架 README 說的讀取時機不對

- **現象**：編譯後在另一個動態包加一支同名 glob，agent 下一次問腦就換成新那支，stderr 一個字都沒有（README 有寫會「merged without a word」）。另外骨架 README 兩處（開頭第三點、「Linking tool packs」）寫動態連結的東西「read … every time the agent starts」「shows up at the agent's next start」，實測是**每次問腦前讀、不用重起**；`--compile` 自己印的「see the change from their next brain call」才是對的。
- **這是執行期的事**：撞名發生在編譯之後、aos-tools 疊 `$override` 時；編譯當下就撞的，靜態動態都已經 SpecBad。所以它的 warning 是執行期 loader 印的，不屬於編譯器的 `-Wall`（Argon A16 採納）。
- **重現**：`repro/b/r2_dynamic_silent_merge.sh`。
- **不補會怎樣**：std 新增一支剛好跟某 agent 工具同名的，用 `--dynamic` 編的那隻就換了工具，沒人知道。
- **最小補法**：疊 `$override` 遇到兩層同名時在 stderr 寫一行 warning（跟現有 PathMissing warning 同一種寫法）。README 那兩句改成「每次問腦前」——這是文件事實錯誤，不牽涉方向。
- **跟已裁的關係**：動態連結的行為本身是使用者選的（第 7 題），這條只要它出聲。

## G7　沒有 make：相依改了，沒有東西說「這夾過時了」

- **現象**：改了庫的包、底的 `agent.py`、`templates/agent-fsm/hooks.json`，靜態連結的夾都還是舊的，`agent_def check` 說沒問題；要找該重新編譯哪幾夾只能一夾一夾 `--dry-run` 去比。沒有東西列出一支 `agent.py` 這次讀過哪些檔（像 `gcc -M`）。
- **重現**：`repro/a/t04-stale.sh`。
- **不補會怎樣**：多隻 agent 共用一個庫時，改了庫有的重新編譯了、有的沒有，行為不一致且沒人知道。今天 agent 少，痛感中等；庫一多就痛。
- **最小補法**（不在產物記帳）：`agent.py --deps` 印出這次編譯讀過的檔；`agent.py --check`＝重新算一次、跟夾裡現有檔比、不同退 1，交給 make 或人自己比。注意不能直接拿 `--dry-run` 的輸出比：`--dry-run` 的 `README.md` 只有一行、`_metainfo.json` 只有 `summary` 與 `META`，而 `--compile` 會保留已有的 README、合併 `_metainfo.json` 裡的 `lineage` 等鍵——照字面比，正常的夾永遠「不同」；`--check` 要照 `write()` 的保留規則比，且抓不到舊宣告留下的孤兒檔（Argon A13 採納，頂層核過 `write()`）。今天「手用 `--dry-run` 比」也有同一個坑。
- **跟已裁的關係**：「編譯產物不記帳、直接蓋」「check 不順手重新編譯」都不碰——`--check` 只比不寫，比的是重新算一次的結果，不是帳。

## G8　錯誤訊息沒行號、沒有警告層（`-Wall`）

- **現象**：
  - SpecBad 只有一行、沒有 `agent.py` 的行號（`SpecBad tool read is listed twice`、`HOOKS hook timer: every_ms …`）；TOOLS／HOOKS 用迴圈組時難找。Python 自己的錯有行號。
  - 警告只有兩種。沒用到的 `defs.lib`、從起點走不到的狀態都靜靜過。
  - loop 間隔 `interval_ms` 寫死 300、沒有正式地方調；`INTERFACES={"aos-loop":{"interval_ms":50}}` 看起來調了、其實沒效果。這不是編譯器少擋：`interfaces.json` 頂層本來就開放給各子系統放設定，編譯器不知道誰讀哪個鍵（Argon A5 採納，初稿提的「沒人讀的 INTERFACES 鍵」警告拿掉）。
- **重現**：`repro/a/t02-errors.sh e1 e4 e6b e12b`（行號）、`repro/a/t02-errors.sh e7 v2`（該警告沒警告）。
- **不補會怎樣**：小錯花時間找；「看似有效其實沒效」的設定最難發現。
- **最小補法**：報 SpecBad 時接上第一個不在 aos 套件裡的呼叫框行號 `(agent.py line N)`——只是錯誤訊息，不寫進產物，跟已裁「不對回原始碼」不衝突。編譯時的 warning 候選：走不到的狀態、寫進本機絕對路徑（含 `defs.load` 的改寫）；要不要 `--werror` 留給拍板。動態包執行期撞名（G6）與工具描述過長（G13，歸 `tools_def check`）不是 `agent.py` 編譯器管得到的，分開算（Argon A16）。

## G9　同一支工具一直失敗沒人發現（沒有 sanitizer 那類自動偵測）

- **現象**：劇本假腦讓 glob 帶 `{}` 一直失敗：25 秒內 8 次一模一樣的失敗呼叫，仍 running，stderr 只有 warning。現有的只有 goal 的「十次沒進展就暫停」、kernel 預算、要人手動掛的 `a.bp.add.tool_error(times=2)`。
- **重現**：`repro/c/repro-loop.sh`（要先起 probe-c 的樹、它的 `kernel.json` 有劇本端點）。
- **不補會怎樣**：接真模型時燒 token，直到撞上預算。跟 G4 疊起來最痛（說明錯→一直被拒→一直重試）。
- **最小補法**：act 格看到連續 N 次同名、同參數、非 0 的呼叫，就丟一則 `[aos]` 提醒給腦，或走 tool_error hook；判法可借 gdb 的 `tool_error(times=)`。

## G10　測試框架半套：劇本只能寫在共用的 kernel 裡、沒有錄放

- **現象**：假腦的劇本（`endpoint.script`）做得到「叫 math 6*7 → 答 42」這種最小單元測試（PASS，6.7 秒），但劇本只能放在 `llms/def/kernel.json` 的端點，不能跟 agent 定義或測試放在一起；劇本不能引用輸入；真腦出過的一段對話不能重播。
- **重現**：`repro/c/unittest/test_agent.sh`。
- **不補會怎樣**：每寫一支 agent 測試就改一次整棵樹共用的 kernel；真腦出的問題無法重現。今天測試多在 aos 本身，agent 一多就會痛。
- **最小補法**：讓 agent 的 `llm.json`（或夾裡一份劇本檔）帶 script 給 fake 端點；加一支小指令把 `history.jsonl` 的回答抄成 script。

## G11　core dump 對不出是哪一份定義死的

- **現象**：死後現場大半都在（死在哪格、traceback、那封信），但 stack 與表只記定義的**路徑**；死後重新編譯，當時跑的 `fsm.json`／`tools.json` 就沒了。第一次問腦前死的沒有 `observed.jsonl`。
- **重現**：讓 think 格 raise 或格 exit 3 無 next（隊員 C 的 crash1、crash2 定義在暫存樹 `probe-c/t1/tree/agents/`）。
- **不補會怎樣**：事後拼不出當時的狀態機與工具表；「跑著讀到新定義」是特性，所以「死時是哪一版」更難回答。
- **最小補法**：phase 轉 stopped 且碼非 0 時，把當時定義夾幾個檔的雜湊（或副本）寫進 stack。**這有洞**（Argon A17 採納）：因為跑著會讀到新定義，若死之前剛重新編譯過，死的那一刻夾裡已是新版，抄到的不一定是出事那格讀到的；`loop.json` 更是起動時就讀了。所以它只保證「死時夾裡是什麼」。要更準就得每格記一次讀到哪一版，那就接近已裁的「不做快照」。
- **跟已裁的關係**：使用者裁了「不做快照」——那是指跑著的 agent 不要凍住舊定義。這條只在**死的那一刻**留底，不改跑的行為；但它鄰近那個裁定，請使用者判斷算不算同一件事。
