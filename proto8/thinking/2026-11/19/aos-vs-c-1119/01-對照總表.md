## 一、語言本身

| C 的東西 | 它在 C 解什麼問題 | aos 的對應 | 狀態 | 證據 |
|---|---|---|---|---|
| 標頭檔：一隻 agent 的對外介面 | 不讀實作也知道怎麼叫它 | `_metainfo.json` 的 summary（一句）、`aos-agent ctl state`（工具、llm、system 第一行） | 半套 | 「它收什麼信、回什麼」沒有地方宣告：`agent.py` 九個欄位裡沒有，grep `agent_spec*` 無 message／letter 欄 |
| 標頭檔：一個庫對外有什麼 | 用庫的人看清單就知道 | 庫＝`packs/*.json`＋`tools/<夾>/`；只有 std 有 `lib/tools/base/_index.json` | 半套 | `defs.lib` 只查根在不在（`agent_spec_lib.py` `_where`），編譯不讀任何清單 |
| 型別檢查：狀態機、hook 的結構 | 結構寫錯在編譯時擋 | `defs.state`、`_checked`、hook 的 validate | 有 | 狀態名拼錯 `wiat`、`timeout_ms="5"`、hook event 錯、`every_ms:"fast"` 都編譯時 SpecBad（`repro/a/t02-errors.sh` e1 e6b e12 e12b） |
| 型別檢查：工具存在、`_tooldef` 對 | 叫的東西不存在要在連結時報 undefined reference | `std.tool()` 查夾在不在；`defs.tool(名, 路徑)` 不查；`_tooldef` 編譯不讀 | 半套 | `defs.tool("ghost", defs.home("/lib/tools/base/nope"))` 編譯退 0、`agent_def check` 回 `{"problems": []}`；執行時 `aos-tools: warning: tool ghost skipped: PathMissing`，工具從腦的清單無聲消失（隊員 A e2、B `repro/b/r1_missing_tool.sh`、C `repro/c/repro-lint.sh`，頂層另跑一次確認） |
| 型別檢查：狀態格程式在不在 | 同上 | 編譯不查 argv 指的檔 | 沒有 | `["python3","nocell.py"]` 編譯、check 都過；一掛上就 `can't open file … RunFailed exit code 2`（`repro/a/t06-runtime.sh` e7） |
| 型別檢查：LLM 設定值 | 值的型別要對 | `llm_json` 只查鍵名在 `llm_keys`、model 是字串 | 半套 | `{"temperature": "hot", "max_tokens": -5}` 編譯、check 都過；掛上即死 `CfgBad temperature in llm.json must be a number`——執行期有型別規則，編譯時沒用（e6） |
| 型別檢查：model 名 | 連結時找不到符號報錯 | 無；腦包表在 kernel 那棵樹 | 沒有 | `model: "no-such-brain"` 編譯過；執行時 `EndpointUnknown`→`BrainFailed`、agent 停（e12c）。編譯時本來就看不到 kernel，見 03 |
| 型別檢查：鍵名隨身體不同 | 不同目標平台合法的東西不同 | 不宣告 FSM 時照目標夾 `interfaces.json` 的 `llm_keys` | 有 | eca-claude 抄本帶 `temperature`：`SpecBad LLM key 'temperature' is not one of llm_keys (model)`（x3） |
| 介面型別：agent 之間的信件格式 | 兩邊對格式有共識 | 信封由 `mailbox_send` 的 `_tooldef` 在寄時查（status 六選一）；`lib/schema/comm/1/` 只管 `body.comm`，只有 `aos-comm check` 用 | 半套（只讀文件） | 每隻 agent「收哪種信」沒有 schema；本文是自由文字 |
| 巨集／條件編譯 `-D` | 依環境編出不同定義 | `agent.py` 是 Python，讀 `os.environ` | 有（無正式 `-D`） | `WITH_SHELL=1 MODEL=luna` 讓工具多 shell、model 換 luna；給 `-DWITH_SHELL=1` 報 `FlagUnknown`；產物不記用了哪些環境變數（`repro/a/t03-cond.sh`） |
| 常數與設定層 | 可調參數放哪、編譯後還能不能改 | 編譯時：`timeout_ms`、`every_ms`、LLM；執行期：stack 的 `self_hook`／`self_llm`／`self_tools` 疊層 | 半套 | `loop.json` 的 `interval_ms: 300` 寫死（`agent_spec.py` 約 333 行）；`FILES={"loop.json":…}` 報 SpecBad；`INTERFACES={"aos-loop":{"interval_ms":50}}` **被收下、沒效果、沒警告**（v1、v2）。`interfaces.json` 頂層本來就開放給各子系統放設定，編譯器只管 `aos-agent` 那格，不知道誰讀哪個鍵，所以「沒效果」怪不到它（Argon A5）；真正的缺是 loop 間隔沒有正式地方調（`loop.json` 在保留名單裡，`FILES`、`extern` 都不能改） |
| 可見性 `static`／`extern` | 分清楚對外與內部 | `defs.extern(檔)`＝這份檔手寫、編譯不寫；別的庫的工具帶 `庫名_` 前綴 | 半套 | 庫裡沒有「內部」：`lib2.tool("t2")` 拿得到一支不在任何包裡的工具（`lib.tool()` 本來就是單支取用的公開寫法，不算漏洞，只是庫沒辦法藏東西）。`agent.py` 這層有對應 `static` 的東西：被 `defs.load` 載入時只交出九個大寫欄位，裡面的輔助函式、變數、import 的模組都不外露（Argon A4）。`extern` 在 aos 的意思是「不由編譯產生」，跟 C 的跨檔宣告不全同（見 03 刻意不同） |

## 二、編譯

| C 的東西 | 它在 C 解什麼問題 | aos 的對應 | 狀態 | 證據 |
|---|---|---|---|---|
| 前處理／編譯／連結分段、看中間結果 | 分段除錯 | `--dry-run` 印最後整份 `{檔名: 內容}`；Python 裡 `defs.compile()`／`defs.write()` 分開叫 | 有（只看得到最後結果） | 包展開、靜態／動態判斷的中間步驟看不到；比 `--dry-run` 與 `--dry-run --dynamic` 才看得出差別 |
| 錯誤訊息指到原始碼行號 | 一眼找到錯在哪 | Python 自己的錯有行號；SpecBad 只一行、指宣告內容 | 半套 | 語法錯 `line 26 … '[' was never closed`、NameError 有行號；狀態、工具、hook 的 SpecBad 都**沒有行號**（只說 `state think`、`tool read`），TOOLS 用迴圈組時難找（e1 e4 e6b e12b）。`defs.load` 底那支出錯才帶行號 |
| warning 一級、`-Wall`／`-Werror` | 可疑寫法先提醒，必要時當錯 | `flags.warn` 只兩種：`--dynamic` 時退回靜態、`agent.py` 被 import | 半套 | `-Werror` 報 FlagUnknown；沒用到的 `defs.lib`、沒用到的變數、從起點走不到的狀態 `orphan` 都靜靜過（e7） |
| `make clean`、孤兒檔 | 舊的 `.o` 不會冒充新的 | `--compile` 整份蓋「這次宣告到的」檔；`_metainfo.json` 合併（保留沒宣告的鍵）；`README.md` 已有就不寫；拿掉宣告後的舊檔不刪 | 半套（README 寫明了，沒警告、沒 clean） | 讀 `agent_spec.py` `write()` 約 363–385 行與骨架 README「What it does not touch」（Argon A3、A6，頂層核過程式）。拿掉 `HOOKS` 後舊 `hooks.json` 留著（`interfaces.json` 不再指它，不會被讀）；從 `META` 刪掉的鍵永遠留在 `_metainfo.json`；改了 `DESCRIPTION`，`README.md` 第一行不跟著改，`agent_def check` 只查兩者非空、不比對（`lib/tools/aos/defs/catalog.py` 166–174 行） |
| 增量編譯與相依（make、`gcc -M`） | 底下改了，知道誰該重新編譯 | 無 | 沒有 | 改庫的包、改底的 `agent.py` 後，靜態連結的兩夾都還舊、`agent_def check` 回 `[]`；只能一夾一夾 `--dry-run` 比；沒有東西列出一支 `agent.py` 讀過哪些檔（`repro/a/t04-stale.sh`）。「不記帳」已裁，這裡只描述 |
| 可重現：同一份編兩次 | 同輸入同產物 | — | 有 | 同夾編兩次 sha 相同；`AOS_HOME` 換 symlink 寫法、換夾，`--dry-run` 也相同；用 std 的產物裡沒有 `/home/`、主機名、時間（`repro/a/t01-repro.sh`）；鍵序照宣告、`indent=2`，C 也量到 md5 相同 |
| 可重現：產物不夾帶本機路徑 | 換機器能用 | `defs.home`／`defs.env` 寫成 `$env` 指示 | 半套 | `defs.load` 收**字串路徑**（`defs.load("../base2")`，README 的例子也這樣寫）時，**底裡的相對工具路徑被改寫成本機絕對路徑**（`"/home/…/base2/mytool"`），沒有警告；收指示詞（`defs.load(defs.env("AOS_WS", "/agents/base2"))`）時寫成指示詞、不帶本機路徑（`agent_spec_load.py` `_moved`，Argon A2 指正、頂層核過）。不論哪種，工具實體若放在底那夾，底夾刪了一樣 PathMissing。底的狀態格 `argv` 只在「檔在底夾裡存在」時才改寫（同檔約 179 行 `os.path.exists`）：編譯當下檔還沒放好就不改寫、無聲改去衍生夾找；反過來 argv 裡剛好跟底夾某檔同名的普通參數會被改寫（Argon A7，讀程式確認、沒實跑）。`defs.lib("x", "/abs")` 寫絕對路徑是寫的人自己選的，也沒警告 |
| 交叉編譯 | 替另一台機器、另一種身體編 | 指示詞照原樣寫出；目標夾的 `llm_keys` 照目標查 | 有（跟 C 同） | 編譯時所有庫、包都要在**本機**讀得到：`defs.env("AOS_WS","/lib2")` 沒設 `AOS_WS` 報 SpecBad（x1）。這跟 C 交叉編譯要 `--sysroot` 讀得到目標的標頭與庫是同一回事，不算缺（Argon A10）。對方的腦包名本機驗不了；沒有第二台機器實測 |
| 除錯資訊 `-g` | 從產物指回原始碼 | 狀態名就是 `agent.py` 寫的名；`tools.json` 的 description 寫「copied in the tools of std.pack('look')」 | 已裁 | 執行期錯誤指產物（`CfgBad … in llm.json`），人找得回去、不痛；會痛的是上面「SpecBad 沒行號」，那是錯誤訊息、不是產物 |
| 工具的小編譯器 `tool.py`（tool_spec） | 同上幾項 | `--compile`、`--dry-run`、`--tooldef`、`--metainfo`；`tools_def check` 重新編譯並跑範例 | 大致有，一處會痛 | 型別寫 `"int"`、default 型別錯都 SpecBad（同一行印兩次：stdout、stderr 各一）；語法錯有行號；可重現。**`tool.py` 改了沒重新編譯時，模型看的 `_tooldef.json` 跟執行時檢查用的 PARAMS 不同**（見 02 第 3 條）；`fail()` 錯誤碼靠掃原始碼文字收集：註解裡的 `fail("X")` 會被收、動態組出的碼收不到（`repro/a/t05-tool.sh`） |

## 三、連結與庫

| C 的東西 | 它在 C 解什麼問題 | aos 的對應 | 狀態 | 證據 |
|---|---|---|---|---|
| 靜態連結 | 把庫抄進產物，之後庫怎麼變都不影響 | `--compile`（預設 `--static`）：`tools.json` 逐支寫工具 | 半套 | 靜態抄的只是「包裡有哪些工具」的名單；每支仍寫 `{"$env":"AOS_HOME","$path":"/lib/tools/base/glob"}`，**工具程式與 `_tooldef` 永遠執行時讀**。把 glob 的參數 `pattern` 改 `pat`，靜態的 agent 下一次問腦就拿到 `required ['pat']`；搬走 glob，清單少一支、agent 照樣 running（隊員 B）。骨架 README 開頭第三點有寫「the tool programs themselves … read when the agent runs」，但同句說「shows up at the agent's next start」，實測是下一次問腦（Argon A1 指正頂層初稿說 README 沒寫） |
| 動態連結（.so） | 庫改了不用重新連結就生效 | `--dynamic`／`link="dynamic"`：`tools.json` 寫 `$override:[包…]` | 有；文件有一句不對 | 在 look 包加一支：動態那隻**不用重起**、下一次問腦就看到並叫了它，靜態那隻沒看到。骨架 README 兩處（開頭第三點、「Linking tool packs」）寫「aos reads it every time the agent starts」「next start」，實測是每次問腦前讀；`--compile` 自己印的那句「see the change from their next brain call」是對的 |
| soname／ABI 版本 | 執行時查出「這不是我連的那版」 | 無 | 沒有 | grep `"version"` 掃 `lib/packs`、`lib/tools/base`、`templates/agent-python`、`install.py`、`lib/aos/*.py`：只有 mcp_client 的 clientInfo 0.1。包、工具、std、aos 本身都沒版本號；`_metainfo.json` 只有 summary |
| 庫改了誰告訴你 | 連結器或 loader 報錯 | 重新編譯時 SpecBad；執行時只有 stderr warning | 半套 | 刪一支工具：沒人報錯，`stderr.txt` 每格一行 `skipped: PathMissing`，表上 running，`tools ls -l` 標 `broken`；改參數名：直到腦叫錯才 `ArgumentsBad missing pat` |
| aos 自己升級後舊產物能不能跑 | 舊執行檔遇上新 libc | 無檢查 | 沒有 | 把私有 AOS_HOME 的 `templates/agent-fsm/idle.py` 改名（模擬升級拿掉一格、`install.py` 刪孤兒）：3 秒內這個 home 上 9 隻 agent 全部 `stopped 2 … fsm.json failed with exit code 2`，停在 stopped、daemon 重起也不叫回（`repro/b/r4_home_change_kills.sh`）。事前無法知道哪些定義受影響 |
| 符號撞名（multiple definition） | 兩庫同名在連結時報錯 | 編譯時 SpecBad | 有 | look 與 mailbox 都給不同的 glob：`SpecBad tool glob comes from both std.pack('look') and std.pack('mailbox')`；同名兩次 `defs.tool`：`listed twice`；hook 兩組不同：SpecBad、相同：過；FILES 撞 `tools.json`：SpecBad |
| 編譯後動態包長出同名工具 | C 是先找到的贏，`LD_DEBUG` 看得到 | `$override` 照順序疊、後面的贏 | 有（照 README），但無聲 | 在 mailbox 包加一支 glob 指向 peek_now_time：動態那隻的 glob 無聲被換掉，下一次問腦回時間戳；stderr 一個字都沒有；只有 `tools ls -l` 第 4 欄 `mailbox.json#/tools/glob` 是線索（`repro/b/r2_dynamic_silent_merge.sh`） |
| 弱符號／覆寫：編譯時 | 強符號蓋弱符號 | `defs.tool(名, 路徑)` 換掉包裡同名的 | 有 | 靜態、動態包都退 0（std 包條目只有 path，README 說的「欄位不齊 SpecBad」沒觸發到） |
| 覆寫：執行時（`LD_PRELOAD`） | 不重新連結換掉一個符號 | `aos-agent -t N tools add -n glob --replace 路徑` | 有 | 不加 `--replace` 報 `ToolExists`；加了寫在 stack 的 `tools.json` 疊層，之後包裡長出同名也蓋不過它。stack 這層存的是給的絕對路徑，不是 `$env` |
| 庫的發佈與安裝（pkg-config、套件） | 告訴別人庫在哪、要哪版、依賴什麼 | `defs.lib("名", 根)`；沒有清單檔、沒有安裝指令 | 沒有 | 自做的庫可以無聲依賴 std 工具（`my_rd` 指 `$AOS_HOME/lib/tools/base/read`）；沒有地方寫要哪個 aos、依賴哪些 std 工具；發給別人＝抄夾 |
| 執行時找得到庫 | 找不到 .so 直接報錯 | 庫根是 `$env` 指示，用 agent 的環境解 | 半套 | 庫根在 `$AOS_WS` 下時，同一份定義換一個 `-w` 掛：`my_add2` 無聲消失（表上 running、stderr 3 行 skipped）（`repro/b/r5_lib_needs_ws.sh`） |
| `ldd` | 看一支程式實際連到哪些庫、從哪來 | `aos-agent -t N tools ls -l`（名、種類、解開的路徑、從哪個檔哪個指標來、原始指示）；`observed.jsonl` 的 `def` | 半套 | 靜態的只顯示 `tools.json#/tools/glob`，看不出來自哪個包；**`tools ls` 用叫它的人的 `AOS_HOME` 解**：用 `--envs AOS_HOME=home2` 掛的 agent，`tools ls` 說 `src/…/glob`，`observed.jsonl` 卻是 `home2/…/glob`（`repro/b/r3_ldd_wrong_home.sh`） |
| `nm`／`objdump` | 看產物裡有什麼 | `aos-json-view [--depth N] 檔#/指標`、`aos-agent ctl state`、`aos-gdb` 的 `a.tools.ls()` | 有 | `aos-json-view --depth 2 dyn/tools.json`、`sta/fsm.json#/states/think` 實跑。「這夾是不是 `agent.py` 編的」沒有標記（已裁不記帳） |

## 四、載入與執行

| C 的東西 | 它在 C 解什麼問題 | aos 的對應 | 狀態 | 證據 |
|---|---|---|---|---|
| loader：何時讀哪個檔 | 起動時一次載入 | daemon 表 `exec.json` → `aos-exec -- body.json` → `aos-loop loop.json`（起動讀）→ 每格 `aos-fsm fsm.json`（每格讀）→ 格程式 → 每次問腦前讀 `tools.json`、各包、system、llm | 有 | `loop.json` 的 `interval_ms` 改 2000，`state.json` 仍 300（起動讀）；`fsm.json` 的 idle 改指不存在的檔，下一格就倒（每格讀）。「跑著讀到」是已裁特性 |
| `LD_LIBRARY_PATH` | 選從哪找庫 | `AOS_HOME`（從 daemon 繼承，`ctl add --envs AOS_HOME=…` 可每隻改）；`PATH` 決定 `aos-loop`／`aos-fsm`；定義夾的 `.env`（N-57，只讀文件） | 有，但會混版 | `--envs AOS_HOME=home2`：工具與格用 home2，`PATH` 仍是 daemon 那份 `bin`。一隻 agent 可以用一個 home 的執行檔配另一個 home 的庫，沒人提醒；表與 `ctl state -j` 都不顯示它的 `AOS_HOME` |
| 進入點 `main` | 程式從哪開始 | `_entry` → `body.json` → `loop.json` → `fsm.json` 的 `start`（`stage.txt` 沒有時） | 有 | 看過編出的四檔 |
| argv 與環境 | 給程式啟動參數 | 無 argv；環境 `AOS_HOME`、`AOS_WS`、`AOS_STACK`、`AOS_DAEMON`、`AOS_LLM_KERNEL`、`AOS_CLOCK` 等；啟動參數只能 `ctl add --envs K=V`（明文存 `exec.json`）或 `.env` | 半套（只有環境） | 只印 `/proc/<loop pid>/environ` 的 `AOS_*` 行確認；`exec.json` 是 `{"argv":["aos-exec","--",".../body.json"],"envs":{…}}` |
| errno：錯誤代碼表 | 錯誤碼是封閉清單（errno.h） | `knowledge/aos/errors.json`（代碼結尾慣例、退出碼）；每支工具 `_tooldef` 的 `errors` | 半套（只有命名慣例） | errors.json 自己寫「These are the common endings, not all of them」；粗 grep 約 111 個代碼，8 個不照結尾慣例（BodyUnsupported、DepthExceeded、LetterDropped、LetterRefused、NotFound、StillRunning、SubagentQueued、SweepBusy）；無集中表或檢查 |
| 退出碼 | 父行程 `wait` 拿到 | 格的退出碼→`next`；`next` 沒列的碼＝agent 結束、碼就是結束碼；daemon 表第 4 欄碼、第 6 欄原因 | 有 | 一格第 3 次退 7、next 只有 0 → `stopped 7 … exit code 7`；stop＝0、sleep＝143、`kill -9`＝137 |
| 訊號與收尾 handler | 叫程式暫停、停、收尾 | `ctl pause`／`resume`／`stop`／`sleep`（SIGTERM、10 秒後 SIGKILL）；收尾 hook `after_stop` 帶 `{code, signal, cause}` | 有 | stop：`code 0, cause stop`；sleep 與直接 `kill -TERM`：`code 143, signal 15`；`kill -9` 沒有 after_stop（文件也這樣寫）；pause 期間 say 收 warning、resume 後才答 |
| 行程間通訊 | 訊息佇列、回信 | queue（say／listen，信名即 id，`listen --letter` 等那一封）；mailbox（maildir 式，`reply_to`、`--in-reply-to`、body 的 status 封閉六選一） | 有 | 實寄一封 mailbox 信讀回 `letter.json`；say 與 `listen --letter` 對上 |
| 管線 `|` | 一支的輸出接另一支的輸入 | 無內建；殼的 pipe 可接 | 半套 | `listen --letter L | aos-agent -t B say -` 實跑通；定義裡沒有持久的接線 |
| 搜尋路徑 `-I`、執行期命名空間、單一 daemon | — | — | 已裁 | — |
