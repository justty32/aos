## 先講結論

1. **做得成，而且第一刀很小**：只加一個 lib（`py/aos/agent_spec.py`）與一個骨架（`templates/agent-python/`），不改任何現有程式。做完你就能「空夾放一支二十來行的 `agent.py` → 跑一次 → 掛上去」，不用再抄 19 個檔去改三份。
2. **寫法整套照工具版 `tool.py`**：固定開頭、大寫常數（`DESCRIPTION`、`SYSTEM`、`TOOLS`、`LLM`、`FSM`）、最後一行 `ag.main(...)`。宣告了 `FSM` 就連骨架（`_entry`、`body.json`、`loop.json`、`interfaces.json`）一起生；格的 Python、`.env`、stack、daemon 表上的設定都不管。
3. **打架規則一句話：永遠是 `agent.py` 贏，但蓋掉手改的東西之前先講一聲。** 工具版今天是「直接蓋、不講」，而且完全不知道生成物有沒有被手改過（讀程式確認：沒有指紋、沒有記號）。agent 這格有正規指令專門在改這幾份 json，照抄會出現「agent 剛加的工具，下一次 check 無聲消失」。所以多記一份帳（每份生成檔的指紋），分得出「過時」（放心重生）與「被手改」（停下、`force` 才蓋）。這比 11-18 講的多一步，是要你拍板的第 1 題。
4. **`agent_def check` 重生、`defs check` 只報**：前者查一份、本來就照工具版會寫檔；後者查整棵樹、說明寫明唯讀，只多列「過時」「被手改」兩種問題。
5. **順便補了一個今天的洞**：`agent_def check` 現在完全不看 `fsm.json`，狀態機打錯格名要跑起來才知道；`agent.py` 重生前就會查，錯誤指回 `agent.py`。
6. **kit 與 `self_*` 打不到架**（實讀程式：它們寫 stack、不改定義）。會撞生成物的只有三種：人或 agent 直接改檔、`agent_def tools`／`llm`／`system`、`agent_def new` 抄完的改寫。
7. **要你拍板六題**，都在 [09](09-要使用者拍板的題.md)；第一刀不必等。

## 還沒驗證的

- 「把狀態機的格改名後，停在舊格的 agent 會報 `StateUnknown` 並停下」是照 aos-fsm、aos-loop 的說明推的，沒有實測（[07](07-邊緣狀況.md) 第二節）。
- `loop.json` 只在起跑時讀一次，同樣只讀了說明。
- 兩個例子與所有函式名都是設計稿，沒有寫成程式跑過；「reviewer 重生結果跟手寫的等價」排在第三刀當驗收。
- 各份 json 多一句 `description` 不會被哪支程式嫌棄，依據是 reviewer 範本今天每種檔都帶這個鍵；`hooks.json`、`cli.json` 這兩種在 reviewer 裡沒有，第三刀要另外確認（`hooks.json` 在 agent-fsm 範本裡有帶 `description`）。
