# 邊緣狀況：重生到一半失敗、定義正被跑著的 agent 使用、整夾複製、兩台機器經 git 同步，以及另外挖到的幾條

照 wf 的通則：這裡挖出來的，使用者沒回應就當成天然差異或施工時自然可解，不追問、不列待辦。

## 先講結論

- 四條被點名的都不必加機制：**重跑一次就好**（寫到一半）、**跟今天手改定義同一個風險**（正在跑）、**`agent.py` 跟著走**（`cp -r`）、**`agent.py` 與 json 都進 git**（兩台機器）。
- 真正要小心的有兩條：**改狀態機的格名時，正在跑的 agent 可能停在一個已經不存在的格上**；**在已經手寫好的夾裡第一次重生，會把手寫的蓋掉**（[06](06-打架規則-逐條.md) 第 5 條）。

## 一、重生到一半失敗

| 失敗在哪 | 會怎樣 | 處理 |
|---|---|---|
| 宣告寫錯 | 還沒開始寫檔 | 全部內容先算好、驗完才動筆，什麼都不會變 |
| 寫檔途中（磁碟滿、被 kill、斷電） | 幾份新、幾份舊；每份自己是完整的（暫存檔＋改名） | **重跑一次**。重生本來就是整份蓋，跑幾次結果都一樣 |

不做「整夾先寫到旁邊、再一次換過去」：定義夾裡有手寫檔、有正在跑的 agent 把它當工作目錄，整夾換掉反而危險。

## 二、定義正被跑著的 agent 使用時重生

今天手改定義、或用 `agent_def tools` 改，本來就會立刻影響所有用這份定義的 agent（rules.json 第 1 條講的就是這個）。重生沒有帶來新的風險種類，只是一次動好幾份。

| 改了什麼 | 什麼時候生效 | 風險 |
|---|---|---|
| `system.txt`、`tools.json`、`llm.json` | 下一次問腦 | 同今天。有「自己那份」的 agent 繼續用自己的 |
| `fsm.json`：只改某格跑什麼、下一格去哪 | 下一拍 | 低 |
| `fsm.json`：**把格改名或拿掉** | 下一拍 | **高**：某隻 agent 的 `stage.txt` 正記著那個舊名字，下一拍 aos-fsm 會報 `StateUnknown`、那隻 agent 的身體失敗停下。這是照 aos-fsm 與 aos-loop 的說明推的，沒有實測 |
| `loop.json`、`body.json`、`_entry` | 那隻 agent 下次重新起來 | 低 |
| 幾份檔之間有一瞬間新舊交錯 | 改名與改名之間，極短 | 所有改名排在最後連著做；比人手一份一份改短得多 |

做法：**不加鎖、不查 daemon**。重生完照 `agent_def tools` 的慣例印一句「用這份定義的 agent 從下一次問腦起看到」。格名改掉的風險寫進骨架的 README；lib 不記上一次生了什麼，所以它自己看不出格名變了。

## 三、整夾複製之後 `agent.py` 跟著走

| 怎麼抄 | 結果 |
|---|---|
| `cp -r 整夾` | `agent.py` 與 json 一起過去，新夾立刻能掛、也能再重生。兩夾從此各走各的 |
| `agent_def new`（from 這一夾） | 同上，另外照今天寫 `lineage`、換算 `tools.json` 的相對路徑（[06](06-打架規則-逐條.md) 第 7 條） |
| 只抄 json、沒抄 `agent.py` | 新夾是普通的手寫定義，可以直接改 |
| 抄去當範本給很多人抄 | 每一份都帶著自己的 `agent.py`。改其中一份不會影響別份——跟今天抄範本一樣 |

要留意的只有相對路徑：`agent.py` 裡寫 `../別處/工具` 的話，抄到不同深度就指錯了。所以骨架與說明一律教 `ag.home(…)`、`ag.env("AOS_WS", …)`、或定義夾內的路徑。

多支定義想共用一段 Python（例如同一個拼路徑的小函式）：可以，放一支共用的 `.py` 讓各家 `agent.py` 去 import。改了共用檔之後，各家要各自重生一次才會變。

## 四、兩台機器經 git 同步

做法：**`agent.py` 與 json 都進 git。**

「C 與 .o」的比喻裡 `.o` 通常不進 git，這裡不照搬，理由是 aos 的這份「.o」同時是**掛得上去、正在被用、還會被 `agent_def tools` 改的定義本體**——它跟任何手寫的定義夾一樣，是要保存的東西。

| 做法 | 後果 |
|---|---|
| 都進 git | pull 完就能掛，不必先重生；json 被 `agent_def tools` 改過的內容也跟著同步。一次修改 `agent.py` 會出現兩處 diff（原始碼與 json） |
| 只進 `agent.py`，json 寫進 `.gitignore` | diff 乾淨。但 pull 完要先對每份定義重生才能用，忘了就是「夾裡沒有 `interfaces.json`、掛不上去」；直接改在 json 上的東西不會同步到另一台 |

先例都在同一邊：`tool-python` 骨架的兩份生成 json 在 git 裡；`index_gen` 的 `_index.json` 也在。

配套兩條：

1. **生成結果兩台要一字不差**：不寫時間、機器名、絕對路徑；鍵照宣告的順序；固定縮排。否則每次重生都是假的 diff。
2. **兩台的 aos 版本不同時**，`ag.stock_fsm()` 這類「照範本生」的結果可能不同。這跟兩台 `install.py` 沒同步是同一件事，不另外處理。

json 的 git 衝突照一般檔案解；如果那份 json 沒有人直接改過，最省事是解好 `agent.py` 再重生一次。

## 五、另外挖到的

1. **`agent.py` 存在但不是庚的**（別人剛好有支同名的檔）：第一刀沒有任何指令會自動去跑它，所以不相干。之後若做「`agent_def check` 順手重生」，照 tool_spec 的認法：原始碼裡有 `agent_spec` 這個字串才算。
2. **`_metainfo.json` 壞掉（不是合法 json）**：重生時報錯、不覆蓋它，因為裡面可能有別人的鍵。`agent_def new` 今天遇到也是 `DefBad`。
3. **`system.txt` 是整份蓋**：直接在 `system.txt` 上潤過的字，重生就沒了。文字長、常手改的，用 `ag.by_hand("system.txt")`。
4. **`agent.py` 不該連網路、不該讀工作區以外的東西**：lib 管不到，只寫在說明裡。
5. **拿掉宣告後留下的舊檔**：例如把 `FILES` 裡的 `ladder.json` 拿掉，夾裡那份還在；`interfaces.json` 重生後不再指它的話，它就只是一個沒人讀的檔。要刪自己刪。
