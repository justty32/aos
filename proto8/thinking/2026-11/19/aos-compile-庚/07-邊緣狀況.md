# 邊緣狀況：重生到一半失敗、定義正被跑著的 agent 使用、整夾複製、兩台機器經 git 同步，以及另外挖到的幾條

照 wf 的通則：這裡挖出來的，使用者沒回應就當成天然差異或施工時自然可解，不追問、不列待辦。

## 先講結論

- 四條被點名的都有不必加新機制的解法：**重跑一次就好**（寫到一半）、**跟今天手改定義同一個風險**（正在跑）、**`agent.py` 跟著走、指紋照樣對得上**（`cp -r`）、**原始碼與生成物都進 git**（兩台機器）。
- 真正要小心的只有一條：**改狀態機的格名時，正在跑的 agent 可能停在一個已經不存在的格上**。

## 一、重生到一半失敗

| 失敗在哪 | 會怎樣 | 處理 |
|---|---|---|
| 宣告寫錯、`agent.py` 丟例外 | 還沒開始寫檔 | 全部內容先在記憶體算好、驗完才動筆，所以這一類什麼都不會變 |
| 有檔被手改 | 還沒開始寫檔 | 先比完全部再決定，一份都不寫（[05](05-打架規則-總則.md)） |
| 寫檔途中（磁碟滿、被 kill、斷電） | 幾份新、幾份舊、帳是舊的 | 每份檔照 tool_spec 的寫法「暫存檔＋改名」，單一份不會半截；帳最後寫。**重跑一次**：已經寫好的那幾份「夾裡的＝會生的」算一致，剩下的「＝帳上的」算過時，補完 |
| 寫到一半，而且重跑之前又改了 `agent.py` | 那幾份半路寫下的檔兩邊都對不上，會被當成手改 | 訊息照實講，`force` 一次就過。少見，不為它加機制 |

不做「整夾先寫到旁邊、再一次換過去」：定義夾裡有手寫檔、有正在跑的 agent 把它當工作目錄，整夾換掉反而危險。

## 二、定義正被跑著的 agent 使用時重生

今天手改定義、或用 `agent_def tools` 改，本來就會立刻影響所有用這份定義的 agent（rules.json 第 1 條講的就是這個）。重生沒有帶來新的風險種類，只是一次動好幾份。

| 改了什麼 | 什麼時候生效 | 風險 |
|---|---|---|
| `system.txt`、`tools.json`、`llm.json` | 下一次問腦 | 同今天。有「自己那份」的 agent 繼續用自己的 |
| `fsm.json`：只改某格跑什麼、下一格去哪 | 下一拍 | 低 |
| `fsm.json`：**把格改名或拿掉** | 下一拍 | **高**：某隻 agent 的 `stage.txt` 正記著那個舊名字，下一拍 aos-fsm 會報 `StateUnknown`、那隻 agent 的身體失敗停下。這是照 aos-fsm 與 aos-loop 的說明推的，沒有實測 |
| `loop.json`、`body.json`、`_entry` | 那隻 agent 下次重新起來 | 低 |
| 幾份檔之間有一瞬間新舊交錯 | 改名與改名之間，極短 | 所有改名排在最後連著做；比人手一份一份改短得多 |

推薦：**不加鎖、不查 daemon**（`agent_def` 一向不讀 daemon 的表）。重生完照 `agent_def tools` 的慣例印一句「用這份定義的 agent 從下一次問腦起看到」。另外，重生發現 `fsm.json` 有格的名字不見了，多印一行提醒：停在那一格的 agent 會停下，請用 `ctl set-def` 或重起。

## 三、整夾複製之後 `agent.py` 跟著走

| 怎麼抄 | 結果 |
|---|---|
| `cp -r 整夾` | `agent.py`、生成檔、帳一起過去；沒有任何檔被改寫，指紋照樣全對，新夾立刻是一份完整的「有原始碼的定義」。兩夾從此各走各的 |
| `agent_def new`（from 這一夾） | 見 [06](06-打架規則-逐條.md) 第 7 條：抄完在新位置重生一次，`lineage` 照寫 |
| 只抄 json、沒抄 `agent.py` | 新夾是普通的手寫定義（[06](06-打架規則-逐條.md) 第 4 條），可以直接手改 |
| 抄去當範本給很多人抄 | 每一份都帶著自己的 `agent.py`。改其中一份不會影響別份——這跟今天抄範本一樣 |

要留意的只有相對路徑：`agent.py` 裡寫 `../別處/工具` 的話，抄到不同深度就指錯了。今天手寫的 `tools.json` 用 `cp -r` 抄也一樣會錯（只有 `agent_def new` 會幫忙換算）。所以骨架與說明一律教 `ag.home(…)`、`ag.env("AOS_WS", …)`、或定義夾內的路徑，三種都抄不壞。

多支定義想共用一段 Python（例如同一個 `lib()` 小函式）：可以，放一支共用的 `.py` 讓各家 `agent.py` 去 import。代價是 `defs check` 靠指紋看不出共用檔變了，只有 `agent_def check` 真的跑一次才知道（[05](05-打架規則-總則.md)）。

## 四、兩台機器經 git 同步

推薦：**`agent.py`、生成檔、帳三樣都進 git。**

| 做法 | 後果 |
|---|---|
| 都進 git（推薦） | pull 完就能掛，不必先重生；沒有 `agent.py` 的工具（`ctl add`、`defs`、之後的總覽）照樣讀得到 json。代價是一次修改會出現兩處 diff（原始碼與生成檔） |
| 只進 `agent.py`，生成檔寫進 `.gitignore` | diff 乾淨。但 pull 完要先對每份定義跑一次 check 才能用；忘了跑就是「夾裡沒有 `interfaces.json`、掛不上去」。也違反「生成物不靠 lib 也能跑」 |

先例都在同一邊：`tool-python` 骨架的兩份生成 json 在 git 裡；`index_gen` 的 `_index.json` 在 git 裡、各線不手改。

配套三條：

1. **生成結果必須兩台一字不差**：不寫時間、機器名、絕對路徑；鍵照宣告的順序；固定縮排。否則每次 pull 都是假的 diff。
2. **生成檔的 git 衝突不手解**：先把 `agent.py` 的衝突解好，再 `agent_def check` 加 `force`（衝突過的生成檔一定對不上帳）。
3. **兩台的 aos 版本不同時**，`ag.stock_fsm()` 這類「照範本生」的結果可能不同。這跟兩台 `install.py` 沒同步是同一件事，不另外處理。

定義夾不在 git 裡的情況（使用者自己工作區裡的定義）：沒有同步問題，以上都用不到。

## 五、另外挖到的

1. **`agent_def check` 會執行 `agent.py`**，等於能跑任意 Python。今天 `tools_def check` 也會執行 agent 寫的 `tool.py`，而且兩支都在同一個工具包 `def` 裡，所以沒有新開一個洞；gather、review 兩個 kit 本來就不給 `def` 包。照使用者 11-18「先做防呆就好，先考慮單人使用，模型可信」，不另設防。
2. **`agent.py` 期限**：照 `tools_def` 的 30 秒；超過＝`SpecBad`。`agent.py` 不該連網路、不該讀工作區以外的東西，但 lib 管不到，只寫在說明裡。
3. **`system.txt` 沒地方放「我是生成的」記號**（整份會送給模型）。人打開它看不出來，只有帳知道。用 `ag.by_hand("system.txt")` 的人不受影響。
4. **`agent.py` 存在但沒用 `agent_spec`**（別人剛好有支同名的檔）：照 tool_spec 的認法，原始碼裡有 `agent_spec` 這個字串才算；不算的話整夾當手寫定義。
5. **`_metainfo.json` 壞掉（不是合法 json）**：`agent_def new` 今天遇到會 `DefBad`。重生遇到也報 `DefBad`、不覆蓋它，因為裡面可能有別人的鍵。
6. **有人把生成檔設成唯讀來防手改**（11-18 調查第 25 條的想法）：重生是「暫存檔＋改名」，只要資料夾可寫就照樣換得掉，權限位沿用舊檔的。可以當成之後的防呆選項，現在不做。
