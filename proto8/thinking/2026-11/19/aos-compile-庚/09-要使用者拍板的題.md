# 要使用者拍板的題：六題，每題一句白話說明、選項、各自後果、我的推薦

← [README](README.md)｜上一份：[08-範圍切法](08-範圍切法.md)

只列方向性的、或我的推薦有明顯代價的。能照既有裁定與慣例推出來的都沒拿來問，列在最後一節，你看到不同意再講就好。

**第一刀不必等這六題**（[08](08-範圍切法.md)）；第 1、2 題要在第二刀開工前有答案。

## 第 1 題：有人直接改了生成出來的 json，下次重生時怎麼辦

白話：`fsm.json` 是 `agent.py` 生的，但有人（或某隻 agent）直接打開 `fsm.json` 改了。之後再跑 check，要不要直接蓋掉？

11-18 晚頂層跟你講的是「照工具那格『Python 贏、重生』」，你說「喔對的對的，這太方便了」。工具那格實際的行為是：直接蓋、不講。

| 選項 | 後果 |
|---|---|
| a. 直接蓋，不講（跟工具版一模一樣） | 最簡單。手改的內容無聲消失，check 還回「沒問題」；agent 會以為自己改成功了 |
| **b. 停下來講一聲，加 `force` 才蓋（推薦）** | 不會無聲弄丟東西。多一步；要在 `_metainfo.json` 記每份生成檔的指紋 |
| c. 照蓋，但把被蓋掉的內容印在輸出裡 | 不卡人。輸出沒人看就還是丟了 |

推薦 b。三個選項都是 `agent.py` 贏，差別只在蓋之前講不講。agent 這格跟工具不一樣的地方是：今天就有正規指令（第 2 題那三個）專門在改這幾份檔，撞到的機會大很多。

## 第 2 題：`agent_def tools`／`llm`／`system` 碰到生成的檔，讓不讓它改

白話：今天要幫一份定義加工具，是叫 `agent_def tools add`，它直接改 `tools.json`。如果這份 `tools.json` 是 `agent.py` 生的呢？

| 選項 | 後果 |
|---|---|
| **a. 擋下，告訴他去改 `agent.py` 的 `TOOLS` 再 check（推薦）** | 不會出現「改了又被蓋」。agent 要改一支 Python，比打一個工具呼叫難，小模型可能改壞（改壞只會得到一行錯誤，json 不動） |
| b. 照改，那份檔從此算「被手改」，下次 check 照第 1 題處理 | 當下最順。但每改一次，那份定義就卡在「要 `force` 丟掉、或要有人把改動搬回 `agent.py`」 |
| c. 讓工具自己把改動寫回 `agent.py` | 只有很單純的寫法做得到；`TOOLS` 用迴圈拼出來的就寫不回去。不推薦 |

推薦 a。工具那格有同樣的先例（`tools_def add_tooldef` 碰到生成檔會擋，叫人改腳本）。只看不改的動作（`ls`、`get`）不擋。

## 第 3 題：eca 版（Claude Code、pi 當身體，沒有狀態機）排第幾刀

白話：你定的形狀是 SYSTEM／TOOLS／LLM／FSM 四樣。eca 版的 agent 沒有 FSM，要用另一種模式（`agent.py` 只管 system、工具、腦設定三份，其他照舊抄範本）。這個模式要多早做？

| 選項 | 後果 |
|---|---|
| **a. 第三刀（推薦）** | 先把「有狀態機、整夾都生」這條最直接的路走通、接進 `agent_def`。eca 版要晚一點才能用 `agent.py` |
| b. 提到第二刀前面 | eca 版早點能用。打架規則接進 `agent_def` 要往後延，那段時間只能手打 `python3 agent.py --write-defs` |
| c. 不做 eca 版 | 最省。eca 版的定義永遠用手寫 |

推薦 a。只有你知道自己最常開的是哪一種；如果平常幾乎都在開 eca 版，選 b 比較划算。

## 第 4 題：要不要教 agent 自己寫 `agent.py`

白話：這個工具是只給你（人）用，還是也寫進知識庫、讓 agent 做新定義時也用它？

| 選項 | 後果 |
|---|---|
| **a. 前四刀只給人用，用順了再寫進知識庫（推薦）** | agent 照舊用「抄範本、改 json」。它們碰到你用 `agent.py` 做的定義時，靠錯誤訊息指路。知識庫暫時不變長 |
| b. 第二刀就寫進知識庫 | agent 馬上會用。它們改 Python 比改 json 容易出錯；知識庫與 `agent_def` 的說明都要改寫，之後設計一變又要再改 |
| c. 永遠只給人用 | 最單純。跟 11-18 調查結論第 4 點（程式即資料：agent 用同一組工具讀、改、生程式）的方向不合 |

推薦 a。你 11-06 說過「不如直接把一個資料夾跟幾個python程式和json檔案交給agent」，11-18 的調查也推測這個 lib 主要是給人的；先讓人用出手感。

## 第 5 題：現有的範本要不要改成用 `agent.py` 寫

白話：`templates/` 下的 agent-fsm、reviewer、eca-claude、eca-pi 現在都是手寫的 json。要不要把它們換成「一支 `agent.py`＋生成的 json」？

| 選項 | 後果 |
|---|---|
| **a. 不換，只新增一個骨架 `templates/agent-python/`（推薦）** | 現有的東西一份都不動。reviewer 在第三刀會被重寫一遍當驗收，但只拿來比對，不換掉 |
| b. 只換 reviewer 一份當示範 | 多一個真的例子。reviewer 從此要先改 `agent.py` 才能改 |
| c. 全部換 | 範本最一致。每個抄範本的人都會拿到一支 `agent.py`，等於變成預設做法，跟「給語法糖、不要求一定用」不合 |

推薦 a。

## 第 6 題：最小例子裡的那四格，是借範本的還是抄一份

白話：`ag.stock_fsm()` 生出來的 `fsm.json`，四格的程式要「指到 `$AOS_HOME/templates/agent-fsm/` 那幾支」（借），還是「把那幾支 Python 抄進你的定義夾」（抄）？

| 選項 | 後果 |
|---|---|
| **a. 借（推薦）** | 定義夾只有十來個小檔。範本的格更新時，所有借的 agent 一起跟著變——好處是不用一隻一隻升級，壞處是你沒改它它也可能變 |
| b. 抄 | 定義夾自己就完整（多 105 KB、7 支 Python），範本怎麼改都不影響它。要升級得自己再抄 |

推薦 a。先例是 reviewer（今天就是借的）。不管選哪個，想要另一種的人都能在 `FSM` 裡自己寫路徑；這題只決定預設值。

## 沒拿來問、我直接定的（不同意再講）

| 事情 | 我定的 | 依據 |
|---|---|---|
| `agent_def check` 會不會寫檔 | 會（先重生再查） | 11-18 已向你講過；`tools_def check` 就是這樣 |
| 查整棵樹的 `defs check` 會不會寫檔 | 不會，只列問題 | 它的說明寫「所有 op 只讀」 |
| 生成檔進不進 git | 進，連同 `agent.py` 與帳 | `tool-python` 骨架、`index_gen` 兩個先例 |
| 帳記在哪 | `_metainfo.json` 的 `generated` 鍵 | `lineage` 已經放那裡；N-69「壞了當沒寫」 |
| 檔名、lib 名 | `agent.py`、`aos/agent_spec.py`（縮寫 `ag`） | 對照 `tool.py`、`tool_spec`（`ts`） |
| 刪掉 `agent.py` | 就是退出，夾變回普通手寫定義 | C-45 給語法糖、不要求一定用 |
| `ctl add` 碰到過時的定義 | 不擋、不自動重生，第四刀起印一行警告 | 生成物要不靠 lib 也能跑；自動重生是丁案 |
| kit、`self_*` | 不用處理 | 實讀程式：它們寫 stack、不改定義 |
| 出處行號 | 不寫進生成檔，要看時現算 | 寫進去會讓每次改動都帶一堆假的 diff |
