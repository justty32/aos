# 打架規則（逐條）：十種情況在「C 與 .o」規則下各自會怎樣

← [README](README.md)｜上一份：[05-打架規則-總則](05-打架規則-總則.md)｜下一份：[07-邊緣狀況](07-邊緣狀況.md)

規則在 [05](05-打架規則-總則.md)：產出後 json 跟 `agent.py` 無關，重生直接蓋。這一份只是把它套到每種情況上，寫明「會發生什麼」，沒有另外的機制。

## 一覽

| # | 情況 | 會怎樣 |
|---|---|---|
| 1 | json 被人手改 | 改了就生效；下一次重生被蓋回去，不講 |
| 2 | 改了 `agent.py`，沒重生 | 夾裡還是舊的 json，照舊的跑；沒有人會提醒 |
| 3 | 兩邊都改了 | 同 1：重生時 json 那邊的改動沒了 |
| 4 | 只有 json、沒有 `agent.py` | 就是今天的手寫定義，一切照舊 |
| 5 | 本來手寫，後來才加 `agent.py` | 第一次重生就把宣告到的那幾份整份蓋掉 |
| 6 | `agent_def tools`／`llm`／`system` | 照常改 json；下一次重生被蓋回去 |
| 7 | `agent_def new` 抄一份有 `agent.py` 的定義 | 照今天抄；`agent.py` 跟著過去 |
| 8 | `ctl add --kit`、`ctl set-def --kit`、`self_*` | 不相干，它們寫 stack |
| 9 | `agent.py` 自己壞了 | `SpecBad`，夾裡的 json 一份不動 |
| 10 | lib 說可以、`defs check` 說不行 | 聽 `defs check` 的，當 lib 的錯修 |

## 要多講一句的幾條

**第 1、6 條（改 json）。** 使用者對這兩條合起來的後果親口確認過（[10](10-使用者裁定.md)）：agent 用 `agent_def tools` 加了工具，之後有人從 `agent.py` 重生，那個工具就沒了，沒有任何提示。想讓改動留下來，只有一條路：把它也寫進 `agent.py`。

**第 2 條（沒重生）。** 改了 `tool.py` 沒跑 check，模型看到的還是舊說明——今天工具那格就是這樣。`ctl add` 不會替你重生，也看不出來 json 是舊的。

**第 4 條（沒有 `agent.py`）。** 庚對手寫的定義零影響（C-45：給語法糖、不要求一定用）。把 `agent.py` 刪掉，夾就是一份普通定義，不需要任何「退出」動作。搬到別台只帶夾、不帶 `agent.py` 也一樣能用。

**第 5 條（後來才加 `agent.py`）。** 這是最容易誤傷的一條：在一個已經手寫好的夾裡放一支 `agent.py` 然後 `--write-defs`，原本手寫的 `tools.json`、`fsm.json` 等會被整份換掉，不問。要保險就先 `python3 agent.py --defs` 看會生成什麼，或先 commit。骨架的 README 要寫這一句。不想被蓋的檔用 `ag.by_hand("檔名")`。

**第 7 條（`agent_def new`）。** `new` 抄完會做兩件改檔的事：在 `_metainfo.json` 寫 `lineage`、把 `tools.json` 裡的相對路徑換算到新位置。兩件都照今天做，不必改 `new`。要知道的是：換算只改得到 json，改不到 `agent.py` 裡寫的路徑；如果 `agent.py` 寫了會跑出定義夾外的相對路徑（`../…`），在新位置重生就會把換算好的蓋成錯的。所以骨架與說明一律教 `ag.home(…)`、`ag.env("AOS_WS", …)`、或定義夾內的路徑，這三種抄到哪都對。`lineage` 不會被重生蓋掉，因為 `_metainfo.json` 只設自己的鍵（[03](03-agent-py-長相.md)）。

**第 8 條（kit、`self_*`）。** 實讀 `ctl/kit.py` 與 `set-def --help`：kit 寫的是 stack 裡「自己那份」，說明原文「the definition is not changed」；`self_*` 同理。它們跟 json 不在同一個夾。留意一點（今天就有、不是庚帶來的）：stack 裡的差異是對著舊定義寫的，定義一變，疊起來可能不對（例如那隻 agent 拿掉了一個工具，而新定義把它改名）。11-18 調查第 8 條已歸為天然差異。

**第 9 條（`agent.py` 壞了）。** 宣告錯＝一行 `SpecBad`。語法錯、丟例外＝Python 自己的 traceback（直接跑 `python3 agent.py` 時就是這樣，跟 `tool.py` 相同）。兩種都還沒開始寫檔。

**第 10 條（lib 與 check 意見不同）。** `defs check`、aos-fsm、aos-tools 這些真正讀檔的程式是規範的一方，lib 只是代筆（C-45「規範比實作重要」）。這種情況代表 lib 的事先檢查漏了一條，回頭補 lib。lib 不得為了自己方便發明只有它懂的 key 或格式。
