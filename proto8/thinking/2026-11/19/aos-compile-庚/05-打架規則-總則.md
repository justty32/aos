# 打架規則（總則）：`agent.py` 與夾裡的 json 是「C 與 .o」的關係——產出後各走各的，重生就是直接蓋

## 規則（使用者 11-19 裁定）

使用者原話：「可以。就是說，agent.py產出東西後，產出後的東西就跟他沒關係了。好比C語言和.o之間的關係。」（全文與選項框在 [10](10-使用者裁定.md)）

攤開成五句：

1. **方向只有一個**：`agent.py` → json。沒有反推、沒有合併、沒有對帳。
2. **重生＝直接蓋**。`agent.py` 有宣告的那幾份檔，每次重生整份換掉；夾裡原本是什麼、有沒有人改過，不看、不問、不講。
3. **產出之後，json 就是普通的定義檔**。夾裡不留記號、不記指紋。任何人、任何指令都可以照今天的方式改它；`agent_def tools`／`llm`／`system` 照常改，不擋、不標記。
4. **改過的 json 會在下一次重生被蓋回去**。這是使用者明講接受的後果，跟「改了 `.o` 再重新編譯」一樣。
5. **沒有人知道 json 是不是過時、是不是被改過**，也沒有指令會報這件事。想知道就 `python3 agent.py --defs` 印出來自己比。

這跟工具版 `tool_spec` 今天的行為完全相同（[01](01-現況-工具版tool_spec.md)）。

## 誰會重生

| 指令 | 會不會重生 |
|---|---|
| `python3 agent.py --write-defs` | **會，而且只有它**。這是一個明講的動作，像打 `cc` |
| `agent_def check` | 第一刀不動它：照今天，只查夾裡的 json，不知道有 `agent.py` 這回事 |
| `agent_def new`、`tools`／`llm`／`system` | 不會。照今天改 json、抄夾 |
| `defs check`（查整棵樹） | 不會。一個字都不改 |
| `aos-agent ctl add`／`set-def`、kit、`self_*` | 不會。它們只讀定義夾，或只寫 stack |

11-18 晚頂層向使用者解釋庚時，講的是「`agent_def check` 重生」。照今天的裁定這件事可以做、但會帶出一個新的後果（見 [10](10-使用者裁定.md) 末節「裁定之後冒出來的一件事」），所以排成第二刀、等第一刀用過再決定做不做（[08](08-範圍切法.md)）。

## 錯誤代號

只有一個新的：

| 代號 | 誰出 | 意思與訊息要講的 |
|---|---|---|
| `SpecBad` | `agent.py` | 宣告寫錯；講是哪個宣告、怎麼改，結尾「fix the declaration in agent.py」（沿用 tool_spec 的名字與寫法） |

寫檔失敗沿用 `WriteFailed`。`agent_def`、`defs` 的代號一個都不加、不改。

## 寫檔的兩條保證

規則雖然是「直接蓋」，寫的時候還是守兩條，免得蓋出壞掉的定義：

1. **全部算好、驗完才動筆**。宣告有錯＝`SpecBad`，夾裡一個字都沒動。正在跑的 agent 用的是夾裡那幾份，原始碼寫壞不該連累它們。
2. **每份檔「暫存檔＋改名」**（tool_spec 的寫法）。讀的人不會讀到半截的檔。
