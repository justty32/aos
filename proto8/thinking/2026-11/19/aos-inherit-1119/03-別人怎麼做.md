# 別人怎麼做「繼承」：C++、Python、Lisp（CLOS、image、macro）、原型式、Nix、Docker、kustomize、CSS、Unix 抄一份改，各自在抄借、何時解析、蓋的粒度、撞名、上游改動上的選擇，以及哪些值得 aos 抄

## 先講結論

1. **大家的分歧其實只有兩軸**：「什麼時候把上一層攤平」（寫的時候／建置時／載入時／每次查）與「蓋的粒度」（整份換／逐欄合併／明寫的補丁）。越晚攤平越靈活、越難看懂「現在到底長怎樣」；越早攤平越好懂，但上游改了要重建才跟。
2. **aos 已選了「建置時攤平」**（「C 與 .o」、包生成時展開），這跟 Nix、Docker、kustomize、C++ 模板同一邊。這一邊大家共同的配套是：**有一份「攤平後長怎樣」可看、有一個明確的重建動作、上游記一個版本**。前兩樣 aos 有（`--defs`、`--write-defs`），第三樣沒有（`lineage` 只記名字、只記一層）。
3. **使用者說的 Lisp 有兩種，要分開**：「macro」是建置時展開（跟 `agent.py` 生成同一邊）；「image／REPL 邊跑邊改」是執行時長（跟 stack 疊層同一邊）。Lisp 把兩者放在同一個環境裡，是因為它**能把跑著的 image 存下來**——這正是 [05](05-執行中長出來與定義衍生.md)「收回」那一題。

| C++ 繼承 | 借（子類物件裡含一份父類） | 編譯時定版面、虛擬函式執行時查表 | 一個成員函式（`override` 關鍵字明講要蓋） | 菱形要 `virtual` 繼承；名字遮蔽靠作用域 | 重編才跟（標頭改了全部重編） | **`override` 關鍵字**：明講「我是故意蓋」，蓋錯名字編譯器報。這正是命名空間要的「故意 vs 碰巧」 |
| C++ 組合 | 借（成員物件） | 編譯時 | 不蓋，委派 | 沒有菱形 | 重編 | 「組合優於繼承」：C-87 的「叫」＝組合，已經有 |

## 對 aos 值得抄的

- **明講「我是故意蓋」**（C++ `override`、kustomize 明寫 patch、Nix `override`）：命名空間第一刀已有一半——自己明寫的 `ag.tool` 整格換包裡同名那支＝故意，兩包撞名＝SpecBad。衍生要延伸成：蓋的對象不存在＝報錯（像 `override` 蓋錯名字）。
- **菱形只算一次，或報錯**（Python C3、kustomize）：不要學 `$override` 現在的「照樣疊兩次」。
- **前後加料而不是整個換**（CLOS、hook）：hook 本來就是加料；衍生多半想「多一個 hook」而不是「換掉某個 hook」。
- **攤平後可看**（kustomize build、`nix eval`、`docker image inspect`）：aos 已有 `--defs`。
- **可寫層與收回**（Docker 可寫層＋`docker commit`、Lisp image）：stack 就是可寫層；「收回」是 05 的題。
- **上游記版本**（flake.lock、Docker digest、git）：`lineage` 只記名字、只記一層；要不要多記是一題（[06](06-邊緣狀況與要拍板的題.md)）。

## 是包袱的

- **執行時查找鏈**（原型式、CSS、Python 執行中的 MRO）：跟 10-14「沒有 extends、沒有搜尋路徑」與「C 與 .o」對不上；也會讓「現在生效的是什麼」要一支工具才看得懂。
- **隱性的逐欄合併**（CSS、aos 今天手寫的 `$override`）：會留殘渣（[02](02-現況事實表.md) 結論 3）。
- **Nix 的 fixpoint**（`final`／`prev` 互相引用）：強大但難懂，違反「寫什麼就做什麼」。
- **多重繼承的優先序規則**：一旦要背「誰先誰後」，就是 C-56 補充說的暗規則。

## Lisp 多想一點：使用者說的三樣，各對到 aos 的哪裡

| 使用者說的 | Lisp 裡是什麼 | aos 今天對到 | 缺的 |
|---|---|---|---|
| 「接近python repl + shell指令」 | REPL：讀一行、求值、印結果 | `aos-gdb` 的 Python REPL；`ag.defs()` 可當函式叫 | 在 REPL 裡「拿一隻現成的當底、改兩處、生出來」沒有順手的寫法（[04](04-設計選項.md) 乙） |
| 「執行途中...在他的指令中央插入新指令」 | image 裡重定義函式，下一次呼叫就用新的 | stack 疊層（`self_tools`、`aos-agent hook add`）下一拍生效；gdb 觸發器 | fsm 格沒有 stack 疊層，插格只能改共用定義夾（[02](02-現況事實表.md) D5） |
| 「搞不好最終我會用lisp整個給他整合好」 | 程式即資料（同像性）：定義本身就是一份能被程式操作的 list | aos 的定義本來就是 json＋資料夾（10-16「JSON＋資料夾就是 Lisp 的 list」） | 沒缺：衍生做在「操作那份資料」的層次（Python 今天、Lisp 以後都行），所以**衍生的函式最好是「吃一份定義資料、吐一份定義資料」**，不綁 Python 的類別語法——將來換成 Lisp 也只是換一層殼 |

最後那一列是本節對設計最重要的一句：**衍生做成「資料 → 資料」的函式，不做成 Python class 繼承**。這也是 04 不推薦「宣告物件／class」那條的理由之一。
