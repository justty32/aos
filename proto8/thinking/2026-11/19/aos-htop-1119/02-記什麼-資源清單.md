## 先講結論

- **40 樣裡：已有現成數字 17 樣、有原料要算 16 樣、完全沒人記 7 樣**（37～40 是 Argon 補的，見 [06](06-Argon審與採納.md)）。「已有」只代表檔裡有這個數字，不代表能直接比：同一台 llm kernel 的 `ledger.jsonl` 記寄件人是絕對路徑、`used.json` 是相對 kernel stack 的路徑，要先換成同一種才對得起來；token 排行若不另外讀 eca 小格，會漏掉最貴的那幾隻。 這張表是「可以記什麼」的菜單，不是「kernel 該內建記什麼」——使用者定了記什麼要能自訂（第四段原話），所以哪幾樣進哪台 kernel，由寫那台 kernel 的人挑。
- **經過 kernel 的只有約三分之一**（問腦的 token、次數、耗時、排隊、失敗；起停的次數與被拒）。其餘要嘛 agent 自己記（工具呼叫、說過什麼），要嘛 daemon／作業系統那邊（cpu、記憶體、重起），要嘛根本沒人記（使用者看了什麼）。
- **錢最齊，但沒有「錢」**：token 帳很完整，整個 aos 沒有價目表；`endpoints.json` 只寫 `cost: "high"／"free"`。
- **最大盲點：eca-claude 的花費完全不經過 llm kernel**；它的 token、快取、等值金額只在自己小格的 `live.jsonl`／transcript。
- **快取**：fsm 腦的 ledger 把端點回的 `usage` 整包照存（`llm_http` 不挑欄位），端點有給快取欄就在；`used.json` 只加總 `total_tokens`。真模型沒驗。
- **cpu／mem 反而最難**：agent 每格是短命 python，看 pid 抓不到；daemon 已有的 cgroup 選項（預設 `off`）開了才有每列累計，而且不必 daemon 多做事。
