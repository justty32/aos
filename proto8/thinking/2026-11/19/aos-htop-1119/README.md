# aos 版 htop（線 aos-htop-1119，發想）：kernel 替每個 proc 記什麼、依此怎麼分配，兩者都要能自訂；今天不改程式就能用兩支 hook 做到「記」與「耦合度高→規劃者優先」，卡在沒有宣告、認人靠自報、優先只在擠時有效；htop 與 aos-gdb 是讀這些紀錄的窗，原型一頁

## 先講結論

1. **你說的方向今天就有骨架。** aos 已經有 Linux 那張「每個行程一筆」的大半：daemon 管身分、狀態、份額（rlimit／cgroup）；llm kernel 管 token 帳、三層額度、排隊；agent 自己記工具呼叫。缺的是**沒有一處把它們收成「一個 proc 一筆」**，以及**沒有角色欄**（沒有地方寫「這隻是負責規劃的」）。
2. **「排程這塊我們已經有了」我理解成 llm kernel 的排隊**（級數＋等久升級＋期限＋格數＋保留給 high 的格，不是先來先處理）。但級數這顆旋鈕今天沒人轉：agent 寄信都不寫 `priority`，大家都是 normal。
3. **自訂今天就做得到，不用改程式。** 在乾淨複本的假腦樹上，只在 llm kernel 的 `kernel.json` 掛兩支 hook：一支「記」（每封回信按寄件人累計），一支「分配」（耦合度 0.72 > 0.60 且角色是 planner → 信改 high）。實跑：pat（planner）的信都被改成 high、ann 不動，kernel 照常。
4. **卡的不是能不能做，是做了之後：** 記下的東西沒有「宣告」（htop、gdb 不知道它記了什麼）；認人靠信封上自報的路徑（誰都能冒充 planner）；優先只在擠的時候有效，而且等久的 normal 約 3 秒就追上 high；hook 一壞整輪問腦停；工具呼叫、cpu、eca-claude 的花費根本不經過 kernel。
5. **兩種東西要分開想。** 「每個 proc 的消耗」是經過 kernel 時順手記的；「全域指標」（耦合度、掌控度）是有人定期量、寫成一個數字，kernel 拿來當分配的訊號。耦合度我傾向先用「git 上哪些檔常一起改」，掌控度傾向「你上次碰它之後它做了多少」，兩者都會被騙，騙法列在 04。
6. **htop 與 aos-gdb 是窗，排在後面。** 欄位不能寫死，要照各台 kernel 自己宣告的來；gdb 看一隻的細節、htop 看全部。gdb 去讀或去問 kernel 是單向，不破壞「兩者解耦合」；會破的是反方向（kernel 策略去讀 gdb 的字條）。

## 最值得看的幾點

- **最大的盲點：Claude Code 當腦的 agent（eca-claude）的花費完全不經過 llm kernel**，今天花最多的正是它們；任何「kernel 壓低某隻」的策略都管不到它（[02](02-記什麼-資源清單.md)、[04](04-全域指標-耦合度與掌控度.md)）。
- **「讓規劃者優先」有五種意思**（問腦先後、額度比例、換聰明模型、誰先醒、多起一隻規劃者），只有第一種今天有旋鈕；只讓規劃者插隊、不讓施工者停手，可能讓撞車更快（[04](04-全域指標-耦合度與掌控度.md)）。
- **kernel 的自訂有七種形式**，跟 agent 那套比，kernel 今天停在「手寫定義夾＋hook」，還沒有 agent.py／編譯／std 那一層（[03](03-自訂kernel-形式與最小實測.md)）。
- **原型**：頂上儀表＋「kernel 現在偏向誰、為什麼」卡；分頁「一張大表」（欄位從 kernel 宣告長出來、可勾選、樹狀、每列的動作只印指令不執行）與「哪裡需要你」（卡片照急不急排）。請直接指著說哪個要、哪個不要。

## 要你先說的四題（往下想之前卡在這）

**第 1 題：「讓規劃 agent 優先」的優先要管多深？**
- a. 只管問腦先後——今天的 hook 就做得到；擠時才有效，施工者照常改檔。
- b. 問腦先後＋額度比例、換聰明的模型——仍只在 llm kernel 裡，不碰起停。
- c. 也管施工者的手：耦合度高時，施工者的起停、喚醒排後面或先扣著——要讓起停那台與「誰先醒」也歸 kernel 管（今天喚醒沒有任何 kernel 管）。
- d. 先不定，用多了再說。

**第 2 題：「記什麼、怎麼分配」的自訂，先走哪條路？**
- a. 維持手寫 kernel 定義夾＋hook，只補一個「kernel 宣告自己記了什麼」的慣例——最小；每封信一個行程、hook 壞了整輪停的毛病照舊。
- b. 策略 proc 定期算好一張表，kernel 只查表（像今天的 `budget.senders`）——kernel 輕、不連坐，但表是幾分鐘前的。
- c. 讓 kernel 也走 agent 那條路：寫一支 `kernel.py`，編譯成 kernel 定義夾，宣告編譯時順手寫好——最整齊，代價是又一套編譯器。
- d. 先不定，讓它自然長。

**第 3 題：認人與旁路——角色、額度要不要先有冒充不了的身分？eca 要不要進帳？**
- a. 照舊自報，使用者承擔（跟 11-19「同帳號沒有邊界」同一條）——角色規則誰都能冒充。
- b. kernel 拿寄件人去對 daemon 的表（stack、pid 對得上才算）——擋得住寫錯、搬家，擋不住刻意造假；不動基底。
- c. 寄信那層強制附上身分——要動 aos-post／daemon，是基底改動。
- 不論選哪個：eca-claude 要不要定期把花費報給某台 kernel，才進得了同一本帳？（不報＝它永遠在帳外。）

**第 4 題：「程式碼耦合度」量的是哪一份程式碼？**
- a. aos 自己的 repo（proto8）。
- b. agent 在各個工作區寫出來的程式。
- c. agent 定義夾彼此（誰抄誰、誰用誰的工具）。
- d. 都可以，量測者也是自訂的，每台 kernel 自己挑。

另外一個我的推測，不對請直接說：你說的「排程已經有了」是 llm kernel 的排隊（上面結論 2）。
