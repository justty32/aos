# 全域指標：耦合度與使用者掌控度各有幾種量法、各會被什麼騙；它們跟「每個 proc 的消耗」是兩種東西；用「耦合度高→規劃 agent 優先」走一遍一條自訂策略

← [README](README.md)｜上一份：[03-自訂kernel](03-自訂kernel-形式與最小實測.md)｜下一份：[05-窗口-htop與gdb](05-窗口-htop與gdb.md)

## 先講結論

- **兩種東西要分開**：「每個 proc 的消耗」是經過 kernel 時順手記的（token、次數、等多久），一筆一筆累加；「全域指標」（耦合度、掌控度、等你的題數）不屬於任何一隻，是**有人定期量一次、寫成一個數字**，kernel 拿來當分配的訊號。
- **全域指標的流向**：量測者（一支程式或一隻 agent，定期跑）→ 寫一個 json（例如 kernel 定義夾旁的 `signals.json`）→ kernel 的策略讀它 → 影響某些 proc 的先後或額度。實測時就是這樣接的，只是量測者是我手寫。
- **耦合度我傾向先用「一起改」（從 git log 算哪些檔常一起改）**：不用任何人新記東西、跨 py／cpp／json 都算得到、量到的正是「改一處要連動幾處」。aos 最重的耦合是路徑字串與 json 檔，不是 import，所以 import 圖會漏掉大半。缺點是它量的是過去，而且一個 commit 裝很多檔時會灌水。
- **掌控度我傾向先用「你上次碰它之後，它做了多少」**（產出量，單位用 commit 數、改動行數或寄出的信），而不是只看「幾小時沒看」：同樣三小時，閒著的跟改了四十個檔的，掌控度差很多。缺點是「你碰過它」今天沒人記準（`sender` 自報），要嘛有人開始記，要嘛先用 git 與 history 推。
- **「行動優先級」在 aos 至少有五種意思**（問腦先後、額度比例、用哪個模型、誰先醒、要不要多起一隻），只有第一種今天有現成旋鈕；其他各自碰到 kernel 架構的不同地方。
- **依指標調優先級是一個回饋迴路**，會延遲、會震盪、會被冒充、會被「刷」；這些是 Argon 要特別挑的（見 06）。

## 耦合度：三種量法加一種

| 量法 | 量到什麼 | 怎麼算 | 會被什麼騙 |
|---|---|---|---|
| C1. import／呼叫圖 | 程式模組之間誰引用誰（扇入、扇出） | 解析 py 的 import、cpp 的 include | aos 的連動多半走**路徑字串**（`$AOS_HOME/lib/tools/...`、`aos-exec` 某個夾）和 **json 檔**，import 圖看不到；動態載入、`$override` 也看不到 |
| C2. 檔案契約圖 | 哪些程式寫、哪些讀同一份 json；一份檔被越多人讀，改格式越痛 | 照 [附錄 4 持久檔表](../../../../docs/NORMS/附錄4-持久檔.json) 的 writer／reader 欄數人頭；或掃程式裡出現的檔名 | 附錄 4 是人手維護的，會舊；掃檔名會把註解、測試、說明文件也算進去；讀的人多不等於脆弱（唯讀的人改格式也不一定壞） |
| C3. 一起改（co-change） | 過去改 A 時，有多常也得改 B | `git log --name-only` 算檔與檔一起出現的次數 | 一個 commit 裝一整條線的檔（commit-request 是按線交件）、文件和程式一起交、大改名，都會把無關的檔綁在一起；量的是過去，新寫的還沒歷史。Argon 補兩個反向的：**真的耦合造成的 bug 偏偏「沒一起改」**（改了 A 忘了 B，隔天另一刀補 B，git 上是兩個 commit，C3 算不到）；**改一個範本、重新編譯十個定義夾**會算成高耦合，其實只是機械同步 |
| C4. 執行時往來（補充） | 執行中誰寄信給誰、誰讀誰的檔 | 信箱封存、ledger 的 sender | 這比較像「組織耦合」不是「程式碼耦合」；sender 自報 |

使用者原話是「程式碼耦合度」，最直接是 C1～C3。至於量的是**哪一份程式碼**——aos 本身的 repo？還是 agent 在工作區寫出來的程式？還是 agent 定義夾彼此？——這決定量測者看哪裡，列成第 4 題。

## 掌控度：四種量法

| 量法 | 量到什麼 | 怎麼算 | 會被什麼騙 |
|---|---|---|---|
| K1. 多久沒碰 | 你上次對它說話、回它的題、或看它，到現在幾小時 | `history.jsonl` 的 `role: user` 行；回題紀錄 | `sender` 自報，eca_main 轉述也像你；說了話不等於看了它做什麼 |
| K2. 沒碰之後的產出量 | 從你上次碰它到現在，它做了多少事 | 那之後的 commit 數、改動行數、寄出的信、花的 token | 量多不等於重要：一行 `rm` 比四十個說明檔危險；按檔數算會鼓勵（或懲罰）切碎。**假歸零**（Argon）：你只回一句「好，繼續」，K1 的起點就更新、K2 歸零，畫面顯示「剛看過」，其實前面四十個 commit 你一個也沒看；共用 `ws` 時 commit 也分不出是誰的 |
| K3. 真的看過的紀錄 | 你實際打開過它的輸出沒有 | 窗口（htop 網頁、gdb、專區）記「打開了哪一列、哪個檔」；或你按「看過了」 | 開著沒讀、蓋章式點過；要有人開始記，而且只記得到經過那些窗口的 |
| K4. 授權距離 | 它離你隔了幾層 agent | daemon 巢狀＋`subagents.json` | 深但無害的雜活也算低；淺的那隻也可能一直沒人看 |

K2 用 K1 當起點（「從上次碰它起」），是我覺得最接近他說的「你多久沒有實際看」又今天推得出來的；K3 要不要開始記，等於「記錄使用者本人」，也是方向題；題數有限，這次不問，等窗口用起來他自己會知道要不要。

## 用一條自訂策略走一遍：耦合度高 → 規劃 agent 優先

把它寫成「某人寫的一條策略」，不是 aos 內建：

```
量測者（每天一次，或每次 commit 後）
  └─ 跑 C3：git log 最近 N 天 → coupling = 0.72，寫進 signals.json（含 measured_at、方法、範圍）
kernel（每封問腦信）
  └─ before_verdict hook 讀 roles.json 與 signals.json
       coupling > 0.60 且寄件人的角色是 planner → priority 改 high（附 why）
  └─ 照常排隊：擠的時候 planner 的信先掛
htop／gdb
  └─ 讀 kernel 宣告的策略與 decisions 紀錄 → 顯示「kernel 現在偏向 pat，因為耦合度 0.72」
```

實測做到了中間那段（[03](03-自訂kernel-形式與最小實測.md)）。三個要回答的問題：

1. **kernel 怎麼知道耦合度**：它不量，有人量了放在它讀得到的地方。量多久一次要跟策略相稱：C3 一天一次就夠，C1 每次 commit 也便宜。量測者本身可以是一列 proc（掛在 daemon 表上，像 `_sweeper` 那樣定期跑），不是 daemon 的身體，不加重 daemon。
2. **「負責規劃的」怎麼認**：今天沒有角色欄。可能的來源：人手寫的名單（像實驗的 roles.json，以 stack 路徑當 key）、agent 定義夾自己宣告（agent.py 裡寫 `ROLE = "planner"`，編譯進 interfaces.json）、kernel 從行為推（常改 docs、常派子 agent 的就是規劃者）。前兩種會被冒充（sender 自報），第三種會認錯。
3. **「優先」是哪一種行動**：

| 行動優先級的意思 | 怎麼做 | 動到 kernel 架構哪裡 |
|---|---|---|
| a. 問腦先後 | before_verdict 改 `priority` | 不用動：實測過 |
| b. 額度比例 | planner 的 `budget.senders` 上限調高，或別人的信回 `BudgetMissing` 叫晚點再試 | 不用動（hook 退 10 那條路）；但「比例」今天沒有，只有「上限」 |
| c. 用哪個模型 | before_verdict 改 `body.endpoint`，給 planner 換聰明的端點 | 不用動；但會撞端點的 `fixed`／`model` 釘死規則（`RequestBad`） |
| d. 誰先醒、誰先被起 | worker 的起停請求在框架站 hold 或排後面；planner 先起 | 起停那台要掛同樣的策略；**喚醒今天沒有 kernel 管**，各隻照自己的 interval 醒 |
| e. 多起一隻 planner | kernel 主動請 daemon 起一隻規劃 agent | 要動：kernel 今天只回應來信、不主動起東西（llm kernel 只替問腦掛 proc） |

## 回饋迴路會怎麼出事（我先列的七條＋Argon 補的、核過的五條）

Argon 補的（細節與核對在 [06](06-Argon審與採納.md)）：

- **擠的時候也可能沒效**：排法是「級數（含 aging）→ 期限 → … → 等得久」。worker 的 normal 信等滿 `aging_cycles`（預設 3 格；格＝kernel 那棵樹的時鐘，範本 `_clock` 每 1 秒一格，所以約 3 秒）就升到跟 high 同級，同級時比誰等得久，剛到的 planner 反而排在後面。不擠時沒差、擠超過幾秒又被追上——這條策略只在很窄的區間有效。（Argon 原本說 0.9 秒、數字可以寫 999 壓過 high；核過：格是時鐘格不是 kernel 的 300 ms 一輪，數字只看正負，999＝high，這兩處它說錯了。）
- **只讓規劃者插隊、不讓施工者停手，會加速撞車**：耦合度高時 worker 還在舊結構上改檔，planner 問腦變快、發出新架構，兩邊在同一個 `ws` 交錯，耦合與衝突反而上升。
- **跨隊**：每隊一台 `llm-team` 轉主 kernel，若某隊的 hook 把自己全隊都改 high，主 kernel 那邊就是整隊插隊。
- **半寫的檔讓整站停**：量測者寫 `signals.json` 不是先寫暫存再改名，hook 剛好讀到半截 JSON → hook 失敗 → 預設 `on_error: stop` → 這輪退 1、問腦全停。
- **管得到的被壓、管不到的照跑**：壓低 worker 或回 `BudgetMissing` 只擋得住走 llm kernel 的 fsm agent；eca-claude 不經 kernel、不受影響，變成「越不受管的越搶得到工作區」。

我先列的：

- **延遲**：耦合度一天量一次，策略照昨天的數字跑一整天；規劃者把耦合降下來了，優先還維持到明天。
- **震盪**：門檻單一（0.60）時，數字在門檻附近來回，planner 一會兒 high 一會兒 normal。
- **冒充**：任何 agent 把信封 sender 寫成 planner 的路徑就插隊。
- **刷指標**：若 agent 看得到規則（knowledge 會寫給它看），規劃者有動機讓耦合「看起來」高；或 worker 把大 commit 拆小，讓 C3 數字變好看。
- **餓死**：planner 一直 high、slots 又少時，worker 只能靠 aging 慢慢升；aging 預設 3 格升一級、不封頂，最後大家又都變 high。
- **量測本身花錢**：若量測者是一隻 agent（用腦判耦合），它的花費也要算進同一套帳，而且它自己的信也要排隊。
- **指標壞了全停**：`signals.json` 壞掉、hook 讀不懂又 `on_error: stop`，問腦全停（同體檢 P5 的類型）。
