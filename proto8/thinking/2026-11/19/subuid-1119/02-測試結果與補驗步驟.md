## 一、怎麼跑的

- 乾淨複本：`git archive 2f7e94d5a` 抄到 `~/.aos/scratch/subuid-1119/src/`，在那裡 `python3 install.py`（退 0、28 支），改動套在複本上、`make -C cpp aos-daemon` 重編（無 error、無 warning），驗完才抄回 `~/repo/aos`。**沒在 `~/repo/aos` 跑 install.py**。
- 測試經 `~/.aos/scratch/subuid-1119/tools/run-tests.sh`：先 unset 全部 `AOS_*`，`AOS_DAEMON_B_SCRATCH` 指到 `~/.aos/scratch/subuid-1119/run-<時分秒>/`，每支 `python3 proto8/cpp/aos-daemon/tests/<檔> -v`。
- 這台前提（實查）：`/etc/subuid`、`/etc/subgid` 都是 `guanyu:100000:65536`；`command -v newuidmap newgidmap` 沒有輸出（缺）；`/home/guanyu` 是 750；ext4 吃 ACL。

## 二、結果原文

新測試 `test_subuid.py`：

```
test_bad_config ... ok
test_group_on_state ... ok
test_handshake_and_acl_with_fake_helpers ... ok
test_helper_fails ... ok
test_helpers_missing ... ok
test_real_cpu_hit ... skipped 'needs newuidmap/newgidmap (apt install uidmap)'
test_real_switch ... skipped 'needs newuidmap/newgidmap (apt install uidmap)'
Ran 7 tests in 0.295s
OK (skipped=2)
```

假 helper 那條收到的參數（daemon 算出來的號碼對；`group` 設 60002＝真 gid 160001）與子行程停下的地方：

```
newuidmap 24897 0 1000 1 5 100004 1
newgidmap 24897 0 1000 1 60002 160001 1
aos-daemon: error: LimitBad user sub:5: setgroups: Operation not permitted
```

假 helper 只能把 ns 的號碼對到自己的 uid，而且一定會把 setgroups 設成 deny，所以子行程照設計停在 setgroups（D7：不放行）。這證明了：父子握手、子行程真的開了 user ns、daemon 帶對參數跑了兩支 helper、對完才往下走。小格是 `770`（群組那三位顯示的是 ACL 的 mask；擁有群組本身是 `---`），ACL 讀回來是 `u:100004:rwx`，預設 `u:1000:rwx`、`u:100004:rwx`。

其他兩條的原文：

```
failed to start: LimitBad user sub:5: newuidmap not found on PATH (install the uidmap package)
newuidmap: write to uid_map failed: Operation not permitted
aos-daemon: error: LimitBad user sub:5: /home/guanyu/.aos/scratch/subuid-1119/run-083039/subuid-fail/fake/newuidmap exited 1
```

回歸（aos-daemon 全部 13 支測試，`run-082732`）：

```
test_bad_letter 3 OK | test_cgroup 0 (skipped=1，這台沒 systemd user) | test_ctl 19 OK | test_lifecycle 40 OK
test_limits 12 OK | test_poke 10 OK | test_ref_hash 1 OK | test_stack_make 5 OK | test_stale_stop 1 OK
```

## 三、沒驗到的（要真的 newuidmap）

1. `setgroups`、`setresgid`、`setresuid` 在真對照表下會過，`/proc/<pid>/status` 的 Uid 是 100004。
2. agent 寫的檔真的是 `100004:160000`，使用者照改得動（預設 ACL）。
3. 環境白名單：`HOME=/nonexistent`、非白名單變數不見、`GIT_CONFIG_VALUE_0` 是 ws。
4. 「走得到」檢查真的點名 `/home/guanyu`（家目錄 750）。
5. daemon 照舊停得了、收得掉換了身分的 proc（`rm` 後行程不在）；`cpu_s` 份額照舊命中（`limit_hit: "cpu_s"`）；`procs: 5` 起得來。

1～5 都寫進了 `test_real_switch`、`test_real_cpu_hit`，PATH 上有 newuidmap 就會自己跑；ws 的祖先走不進去時改驗 daemon 報 `cannot reach` 再 skip。

## 四、使用者補驗步驟

1. 裝套件（要 sudo，agent 不能代跑）：

   ```sh
   sudo apt install uidmap
   ```

   選拍板題 Q1 的 b 還要 `sudo apt install acl`。

2. 照 Q1 的選擇讓 subuid 走得進家目錄（三選一，見入口「要你拍板」）。不做這步也能跑第 3 步，只是兩條真機測試會停在「cannot reach /home/guanyu」再 skip——那也算驗了一半（握手與換身分已過，才走得到那一行）。

3. 在乾淨複本跑測試（不碰 `~/aos-home`、不碰 `~/repo/aos`）：

   ```sh
   bash ~/.aos/scratch/subuid-1119/tools/run-tests.sh test_subuid.py test_limits.py
   ```

   期望 `test_real_switch ... ok`、`test_real_cpu_hit ... ok`、`OK`，沒有 skipped 那兩條。結果貼回這份或交給下一條線補進紀錄。

4. 想親眼看（選做）：在暫存樹起一台 daemon，`aos-daemon-ctl -d <stack> add --name who --limits '{"user": "sub:5"}' /bin/sleep -- 60`，另一個視窗 `ps -o uid,pid,cmd -C sleep` 會看到 `100004`；看完 `aos-daemon-ctl -d <stack> shutdown`。
