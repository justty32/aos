## 1. 結論

1. **字很多，寫死的很少。** 題目點名的那幾處共 985 個檔、11,658 處有「stack」這個字；其中 `AOS_STACK` 1,592 處、`.stack` 524 處。但把 `.stack` 這個夾名寫死、拿來決定行為的程式只有 7 處（2.1）；其餘是文件、說明文字與測試。
2. **`AOS_STACK` 這個名字留著的話，1,592 處不用改字**；要改的是「放在裡面的東西會一直在」這個假設。活樹上有 30 個「列已經拿掉、夾還留著」的舊 stack（活著的是 48 列），表示「stack 會留」今天真的有人在用。
3. **活樹現在就是混版在跑。** 量的當下，根底下 30 支 aos-daemon 有 26 支、39 支 aos-loop 有 24 支，跑的是今天 09:44 重建之前的舊執行檔。所以「新舊並存」不是選項，是現況；每一刀都得對「舊的長駐行程還在」相容。
4. **改了什麼時候生效有三種**：`py/` 與短命的 C++，`install.py` 一跑，這台 49 個 proc 全部當下吃到；長駐的 aos-daemon、aos-loop 要那一支重起；`templates/`、`knowledge/` 一存檔（或另一台一 `git pull`）就生效，19 隻 agent 的定義直接指著 repo 的範本夾。
5. **加法的刀可以不停機**：多寫一份 `status`、多收一種 `ctl`、多一個 `settings`、送信先試 socket，沒有的照舊，舊的讀者不受影響。活樹的 stack 裡現在沒有任何一個叫 `status`、`ctl`、`settings`、`persist`、`sock`、`proc` 的東西，新名字不會撞。
6. **「拿掉舊的」不能一列一列來**，但也不必另外停機：這台今天 07:57 開機、08:02 起樹，每次開機本來就是整棵重起。雙寫雙讀撐到整棵重起過一次，就可以拿掉。
7. **題目的六個例子裡，第三個（daemon 多顧 `/proc/<PID>/cwd` 連結）在今天的版面上做不出來**：48 列的 stack 全在預設的 `procs/<名>`，那個名字已經是真的夾。它要嘛跳過（落檔的實作裡「連結」退化成真的夾），要嘛等身體搬家。
8. **「行程站在自己的身體裡」今天已經做到一半**：表上的 pid 有 25／48 列站在自己的 stack；但真正在做事、寫 `state.json` 的那支，只有 11 列（全是 `_clock`、`_sweeper`）站在 stack。
9. **測試**：385 個測試檔、3,516 條，72%（2,526 條）所在的檔提到 stack；真正會被「加法」那幾刀打到的很少，被「改名、搬位置」打到的是大多數（2.3）。
10. **文件**：現行文件裡有這個字的約 344 頁，估計三成（90～110 頁）要重講段落，其餘改詞或改路徑；知識庫與範本是活樹的一部分，要跟著程式的每一刀走，條文可以最後改（3.4）。

  合起來：表上的 pid 站在 stack 的 25／48；做事的那支站在 stack 的 11／48；兩者不是同一支的 20／48。規則在程式裡：daemon fork 出的子行程先 `chdir` 到 daemon 的 cwd（`proto8/cpp/aos-daemon/src/child/child.cpp:93`），再呼叫 aos-exec；aos-exec 走進入口檔所在的夾（`proto8/cpp/aos-exec/src/find/find.cpp:109-115`）。入口在小格裡就站小格，入口是定義夾就站定義夾。根 daemon 站 `~/aos-home/root`（定義夾）。三種站法的細節 [01](01-aos-loop現況.md) 第 2.7 節、[02](02-aos-daemon現況.md) 第 2.5 節也量了。
- **48 列的 stack 全在預設位置** `<上層的 stack>/procs/<名>`，沒有一列自訂。
- **留下來的舊 stack**：各台 `procs/` 底下不在表上的夾共 30 個（`mine_mecha` 16、`mine_paper` 8、`repo-aos` 3、`mine_arena` 3）。
- **每隻自己那份**：28 個 agent 的 stack 裡，`system.txt` 14 份、`tools.json` 12 份、`exec.json` 12 份、`interfaces.json` 11 份；11 個小 loop 各有一份 `loop.json`。這些不會跟著範本變。
- **長命的 Python**：`aos-mcp` 9 支（掛在開著的 Claude Code 畫面上，行程參數裡帶著 `--stack <絕對路徑>`）、畫面的 tmux 7 個（`-f <stack>/claude/tmux.conf`）。

家機看不到，沒量；照文件它是同一套（`wf/workflows/dev-env/03-換機.md:9-20`），負責人叫 `main`。

### 2.5 兩台機器、起樹與換機、改了什麼時候生效

- **兩台各一棵樹，stack 不跟著 git 搬**。使用者 11-23：「直接變成.stack，然後把它git ignore，就這樣。換機那一套就不用了。」（`wf/workflows/dev-env/03-換機.md:17`）。跟著 git 走的只有 repo 裡的檔（程式、範本、知識庫、`wf/tree/root`、`wf/ws/…`）。
- **起**：`cd ~/aos-home && env -u AOS_DAEMON -u AOS_STACK -u AOS_CLOCK -u AOS_KERNEL -u AOS_LLM_KERNEL aos-exec --stack .stack root`（同檔 `:106`），在 tmux 裡。**停**：`aos-daemon-ctl -d ~/aos-home/.stack shutdown`（`:124`），整棵一起停，eca-aos 自己也停。
- **殼設定檔**（`:39-48`）是人手寫的：`AOS_DAEMON="$HOME/aos-home/.stack"`、`AOS_LLM_KERNEL="$HOME/aos-home/.stack/procs/llm"`，整段包在 `[[ -z $AOS_STACK ]]` 裡。兩台各一份，不在 git。前端的 systemd 服務檔也寫著 `AOS_DAEMON` 的路徑（範本 `proto8/frontend/systemd/aos-frontend.service:14`）。
- **「換機」現在的意思**：到另一台 `git pull` → 在 proto8 跑 `python3 install.py` → 需要的話重起樹。
- **這台今天 07:57 開機、08:02 起樹**（`uptime -s`、`ps -o lstart -p 2223`）。每次開機都是整棵重起，全部換成當時的 `bin/`。

改了什麼時候生效：

| 改的東西 | 什麼時候生效 | 範圍 |
|---|---|---|
| `py/`；短命的 C++（aos-exec、aos-fsm、aos-post、aos-json、aos-lock、aos-llm） | `install.py` 之後下一支新起的行程 | 這台全部 49 個 proc，沒得挑。`install.py` 不先清空，一檔一檔換（`proto8/install.py:14-18`、`:174-182`）；`wf/workflows/testing.md:29` 還寫「清空再填」，是舊說法 |
| 長駐的 C++（aos-daemon、aos-loop） | 那一支行程重起之後 | 一支一支換；舊的可以一直活到下次整棵重起 |
| 長命的 Python（`aos-mcp`、開著的畫面） | 那個畫面重開之後 | 一隻一隻 |
| `templates/`、`knowledge/`、`frontend/` | 存檔當下（規矩卡第 5 條，`wf/workflows/common/rules-card.md:44`）；另一台是 `git pull` 當下，這時那台的 `bin/`、`lib/` 還是舊的 | 19 隻定義指著範本夾的 agent；所有會查知識庫的 agent |

| 殼設定檔、前端服務檔 | 使用者手改、開新視窗 | 兩台各一次 |

限制：`install.py` 在 repo 裡跑＝換掉活樹那份，規矩是先回報（同上第 5 條；[wf/org](../../../../../../wf/org/README.md) 第 6 題：`install.py`、動活樹的先問 eca-aos）。要讓一棵樹跑別的版本，只能給它另一份 `AOS_HOME`（另抄一份 proto8 自己裝），測試線一直是這樣做的。

## 3. 對新介面的含意

### 3.1 對著「定了的」逐條

| 定了的 | 量到的 | 含意（推論） |
|---|---|---|
| 現有的 aos-loop／daemon 退成普通實作 | 兩支長駐程式的窗只在一處寫（`proto8/cpp/aos-loop/src/engine/window.cpp:307`，daemon 繼承） | 「普通實作」要補的是加法；不用先拆任何東西 |
| `ctl`、`status` 純文字，`_metainfo` 照現有的 | 活樹的 stack 裡沒有叫 `status`、`ctl` 的東西 | 新檔名不撞；`_metainfo` 這條零衝擊 |
| persist 在哪以 proc 自己說的為準；daemon 從它的目錄讀 | 今天「在哪」只有表上的 `stack` 欄；46 個 py 檔直接讀那一欄 | 多一個來源可以並存；要讓那 46 處改讀新的，是後面「換邊」的事 |
| daemon 多一個放各 proc 的夾，每一項連到那個 proc 的目錄 | 48／48 列的目錄就是 `procs/<名>` 這個真的夾 | 落檔的實作裡「連結」退化成真的夾；差別只在死了以後夾還在 |
| `proc` 與 `procs` 兩個名字 | 今天只有 `procs`；`proc` 這個名字沒人用 | 每台 daemon 的 stack 加一個 `proc → procs` 的連結是加法（guard 工具用真實路徑判，連結不影響；沒試） |
| 入口是根 daemon 的 PID，`AOS_ROOT` | repo 裡 `AOS_ROOT` 0 處；根 daemon 站定義夾 | 新名字不撞。根的 `.env` 裡的值會傳給整棵樹（`proto8/templates/starts/start-api/root/.env:1`「every agent and child daemon inherits them」），加一行就有 `AOS_ROOT`；要寫成 `/proc/<PID>/cwd` 的形式，根得先站進自己的身體 |
| `.stack` 以後沒有；stack＝活著的 proc 的身體 | 2.1 的表；30 個留著的舊 stack | 見第 5 節第 2、3 題 |
| 要留的放 `procs/<名>/persist` | 條文早有一張「持久檔」表：70 列，持久 46、暫時 24（`proto8/docs/NORMS/附錄4-持久檔.md:14`），`$AOS_STACK/` 底下持久 21、暫時 10 | 那張表可以當盤點的起點，但它把 `state.json`、`ctl.json` 也算持久（會進 image）；新模型下那是活的身體，要重分（03、04 的範圍） |
| 活著走 unix socket，掛了走寄信 | 活樹 0 個 socket；常駐的只有 aos-loop、aos-daemon（[05](05-信與IPC現況.md) 結論 2、3） | 送的那邊可以先加（沒有 socket 就照舊寄信）；聽的那邊是另一刀 |
| token 用量各自報 | agent-fsm 的 stack 有 `observed.jsonl`（11 隻）、llm kernel 有 `ledger.jsonl` | 資料今天就有，多一個檔是加法 |

### 3.2 不停機、一刀一刀來的可能順序

先講三條從 2.4、2.5 推出來的規矩（推論）：

1. **新舊兩種都收、都寫，撐到整棵重起過一次。** aos-daemon 是活得最久的行程。只要還有一台舊的 daemon 在，它就會往子項寫 `ctl.json`、接回時讀子項的 `state.json` 核 pid。所以新的 aos-loop 不能只認新的。
2. **程式先、範本後、知識庫跟著。** 範本與知識庫存檔即生效；另一台 `git pull` 後、`install.py` 前，會有「新範本配舊程式」的一段。範本只能用舊程式會忽略的鍵（`proto8/cpp/aos-loop/docs/01-用法.md:19`「其他 key 忽略」；閒置輪詢的 `gate` 就是靠這條）。
3. **拿掉舊的，搭下一次開機起樹。** 不必為它另外停機。

題目給的六個例子，逐個檢驗：

| 例子 | 可不可行 | 量到的 |
|---|---|---|
| ① stack 裡多擺一份純文字的 `status` | 可行，純加法 | 寫的地方只有一處；但落檔的 `status` 行程死了還在（[01](01-aos-loop現況.md) 實測 G3），要從 `/proc/<PID>/cwd` 進去才有「讀得到＝活著」，所以它跟②是一對 |
| ② 行程改成站在自己的 stack 裡 | 可行，只對之後才起的列生效 | 表上的 pid 已有 25／48 列站 stack；做事的那支只有 11／48。兩種做法見下面 A3 |
| ③ daemon 多顧 `procs/<名>` 之外的 `/proc/<PID>/cwd` 連結 | **今天的版面上做不出來** | `procs/<名>` 已經是真的夾（48／48）。能加的只有：自訂 stack 的列（現在 0 列）、根的固定入口 |
| ④ 多一個純文字的 `ctl` 入口 | 可行，加法 | 「寫回來＝收到」普通檔案做不到，今天的執行檔把它換成 FIFO 會卡死（01 實測 E）；做法看 01 第 3.4 節、18、20 |
| ⑤ stack 裡擺 `settings` 與指到自己的 `persist` | 可行，加法 | `persist` 若是指到自己的連結，夾裡會有一個迴圈。查到的抄與走訪程式多半不跟連結（`symlinks=True`、`followlinks=False`、`is_dir(follow_symlinks=False)`），沒逐支驗 |
| ⑥ 送訊息的小工具先試 socket | 送的那邊可行 | 聽的那邊要一支常駐行程；今天常駐的只有 aos-loop，它是單執行緒（01 結論 8） |

把它們排成三段。每一刀寫：做什麼／碰哪些檔／跟舊的怎麼並存／怎麼驗／怎麼退／活樹要不要重起。這是「可以這樣排」，不是定案；行表、字表都還沒談（9p-proc-1125 最後一節）。

**第一段：準備（不改任何行程的行為，隨時可做）**

- **P1　盤點哪些是身體、哪些要留。** 碰：只有文件（`docs/NORMS/附錄4-持久檔.json` 加一欄，或另開一張）。驗：對活樹的 stack 逐檔核（2.4 列了現有的檔名）。退：刪掉。活樹：不碰。
- **P2　一支只讀的小工具，從現有的檔合成新介面的樣子**（印「名稱: 值」的 status、列 `procs/`）。碰：全是新檔（[原型](../原型/README.md) 可以當底）。並存：只讀。驗：對活樹直接跑。退：刪掉。活樹：不碰。好處是使用者今天就能在真的樹上看那個形狀，行表改幾次都不用動任何行程。
- **P3　`AOS_ROOT`。** 碰：根定義的 `.env` 一行（範本 `templates/daemons/daemon-root/.env`、`templates/starts/*/root/.env`，加兩台各自的 `~/aos-home/root/.env` 抄本）、殼設定檔一行。並存：新名字，`AOS_DAEMON` 照舊。驗：在暫存樹起根，孫輩印 `$AOS_ROOT`。退：拿掉那一行。活樹：根下次起來才有（搭下一次開機）。這一版的值是硬碟路徑；`/proc/<PID>/cwd` 的版本等 A3，而且 PID 寫進環境變數會過期（[06](06-路徑、環境變數與命名現況.md) 結論 4、[02](02-aos-daemon現況.md) 結論 5）。

**第二段：加法（長駐的兩支學會新東西；各列重起時才開始有）**

- **A1　多寫一份 `status`。** 碰：`cpp/aos-loop/src/engine/window.cpp`、`config.cpp`、`include/aos/loop.hpp`；daemon 繼承。`py/aos/apps/agent/stack.gitignore` 加一條（它是活的，不進 image）。並存：json 窗照寫；舊執行檔的列沒有這個檔，讀的人要容忍「沒有」。驗：`cpp/aos-loop/tests`（58 條）、`cpp/aos-daemon/tests`（150 條）加新條；活樹上用 P2 的工具比「合成的」與「行程自己寫的」是否一致（只看不擋）。退：退 commit、`install.py`；已經重起的列留下的 `status` 檔要清掉。活樹：不用為它重起。
- **A2　`ctl` 也收純文字。** 碰：同 A1 那三個檔（所以跟 A1 是同一個位子串著做）。並存：`ctl.json` 照收。驗：同上兩個測試夾。退：同上。活樹：不用重起；`aos-daemon-ctl` 先不改，照舊寫 `ctl.json`。
- **A3　表上的 pid 站進自己的身體。** 兩種做法，都只對「新的 daemon 之後起的列」生效：
  - 甲：daemon 一律把起法寫進小格再起（今天帶環境值的列就是這樣，14 列）。碰 `cpp/aos-daemon/src/child/child.cpp`。代價：每列多一支監工；表上的 pid 是監工、不是回答 ctl 的那支；`aos-agent ctl set-def` 今天不收這種列（`proto8/py/aos/apps/agent/ctl/set_def.py:72-73`）。
  - 乙：aos-loop、aos-daemon 讀完設定後自己換目錄到 stack。碰 aos-loop 的 `main.cpp`、`config.cpp`、`run/folder.cpp`（01 第 3.3 節估二、三十行）與 aos-daemon（它用行程的 cwd 算 `daemon.json`、信、名單裡的相對路徑，`cpp/aos-daemon/src/daemon/procs.cpp:66-67`，要改成用它記下的那個起始目錄；02 的範圍）。agent-fsm 範本的 `"exec": "fsm.json"` 是相對路徑，站到別處會找不到（01 實測 I2），要一起處理。
  - 驗：2.4 那張「誰站在哪」的表重量一次，目標是做事的那支全部站 stack；`templates/tests`、`py/tests/apps` 全過。退：退 commit、重起那些列。活樹：要重起才有；自然的時機是下一次開機起樹。
- **A4　`settings`，以及 `persist`。** 碰：aos-loop 起來時寫（同 A1 的檔）；daemon 起完之後讀、記進表（`cpp/aos-daemon/src/daemon/` 的表那幾支）。並存：表上多一欄，舊的 `stack` 欄照舊。驗：`aos-agent ctl who` 印的那幾樣跟 `settings` 對得上。退：同 A1。活樹：不用重起。
- **A5　送信的小工具先試 socket。** 碰：`py/aos/apps/mailbox/`、`cpp/aos-post/`。並存：連不上就照今天寄信，今天沒有任何人在聽，所以行為不變。驗：現有的信測試全過，再加「有人聽」的一條。退：退 commit。活樹：`install.py` 之後當下生效，要先確認退路那條跟今天一個位元組都不差。
- **A6　aos-loop 多聽一個 socket。** 這刀最大，而且跟閒置輪詢線的後段（把閘做進行程裡、有信才醒）是同一塊地，不該各做各的（[11](11-閒置成本、時鐘與等待.md) 的範圍）。
- **A7　只登記、不起的入口。** 碰：daemon 的收信（`procs_requests` 多認一種信）與表。並存要小心：舊 daemon 對信裡不認得的鍵是忽略，而且照樣回 `applied: true`（`proto8/cpp/aos-daemon/docs/05-信箱.md:19`），寄的人分不出「登記了」還是「被當沒看到」，得寄完再去看表。

**第三段：換邊與拿掉舊的（搭一次整棵重起）**

- **Z1　讀的人改讀新的**：各工具改讀 `status`、`settings`，`aos-daemon-ctl` 改寫文字的 `ctl`；知識庫、範本裡給 agent 的那幾句跟著換。前提：整棵已經重起在會寫新東西的執行檔上。
- **Z2　拿掉舊的**：json 窗、`.stack` 的預設、搬 persist、改名這些，看使用者要不要（第 5 節）。每一樣都在 3.3 的清單上。

### 3.3 一旦改了就回不去的、一定要全樹一起換的

**回不去，或很難退：**

1. **把要留的檔搬位置**（history、queue、mailbox 搬進 `persist/`）。新程式一寫，資料就在新地方；退程式不會把資料搬回來。混版期間兩邊各寫一半，對話會裂成兩份。
2. **`AOS_STACK` 指到一個會消失的地方**（身體放 tmpfs、要留的另外放）。還把東西寫在它底下的程式不會報錯，重起後東西就沒了。別的專案自己寫的定義、hook 也在這個風險裡（arena 的定義夾 100 個檔裡有 45 處寫著版面的檔名）。
3. **拿掉 `ctl.json`**。還在跑的舊 aos-loop 從此收不到 stop；daemon 的 stop 沒有時間上限（`proto8/cpp/aos-daemon/docs/08-當機復原與已知限制.md:39`），那一列會一直停在 stopping，只能改下 sleep（送訊號）。
4. **push**。push 之後另一台一 pull，範本與知識庫當下就換。11-24 那次的清單寫的是「沒 push 之前都退得回去」（`06e:12`）。
5. **停著改各台 daemon 的表**。11-24 做過一次，靠備份清冊才退得回；表改壞會被當壞檔丟開、從空表起（`06f:19`）。
6. **改別的專案 repo 裡的定義**。要它們各自交件，退也要它們各自退。

**一定要整棵一起換（＝搭一次整棵重起）：**

1. **換根 daemon 的執行檔。** 正常的做法只有停整棵樹。daemon 被 `kill -9` 後子項會留著、再起時接回（同上檔 `:9-13`），機制有，但沒有人拿它當升級的路走過。
2. **拿掉舊的窗、舊的欄、舊的檔名。**
3. **`procs_state.json` 改名，或改「怎麼認出一台 daemon」。** guard 工具、走整棵樹的指令、kernel 的規則都靠「夾裡有 `procs_state.json`＝一台 daemon」（`proto8/py/tools/agent/guard/scope.py:36-38`、`proto8/py/aos/comm/walk.py:11`）。
4. **stack 的夾搬家或改名。** 兩台各停一次；殼設定檔、前端服務檔手改；開著的 Claude Code 畫面要重開（行程參數裡帶著舊路徑）；guard 與寫檔工具認的字面要先換，不然保護會悄悄失效。11-23 `_stack` 改 `.stack` 是先例，步驟在 `wf/workflows/dev-env/03-換機.md:169-177`。
5. **環境變數改名。**

「這台所有的樹」是最小單位：49 個 proc 共用一份 `bin/`、`lib/`，沒辦法只換 repo-aos 這一棵（除非給它另一份 `AOS_HOME`）。

## 4. 邊緣狀況

1. **表上的 pid 跟做事的那支不是同一支的有 20／48 列。** 今天若把 `procs/<名>` 連到表上那支的 `/proc/<PID>/cwd`：25 列的路是對的（其中 14 列連到的是監工，不是回答 ctl 的那支），23 列會連到定義夾。
2. **15 隻 eca-claude 的 aos-loop 站在同一個夾**（範本夾）。在它們站進自己的身體之前，從那支的 `/proc/<PID>/cwd` 進去看到的是同一個定義夾，分不出誰是誰。
3. **留著的舊 stack 有 30 個。** `procs/<名>` 一旦變成「連到活著的行程」，這 30 個夾就沒有名字可以放。這是 9p-proc-1125 那條邊緣（「persist 的位置得在 proc 還活著時就讓 daemon 知道」）在活樹上的實際數量。
4. **保護靠三個字面。** guard 工具認 stack 的辦法是：路徑裡有一段叫 `.stack`、夾裡有 `procs_state.json`、或上一層叫 `procs` 且再上一層有 `procs_state.json`（`scope.py:36-38`）。身體搬到別處、或表改名，保護不會報錯，只會不再擋。規矩卡的活樹硬規則第 1 條也是用 `.stack` 這個名字指活樹。
5. **範本就是 19 隻活 agent 的定義本身。** 改範本的 commit 一進工作樹，就是對它們上線；沒有「先裝再說」的緩衝。
6. **另一台的三段式**：`git pull`（範本、知識庫換新）→ `install.py`（Python 換新）→ 重起（長駐的換新）。每一段之間都是混版。
7. **閒置輪詢線還在往舊版面加東西**（2.6）。它的第 3 刀要改範本的 `loop.json`，跟這裡 A1～A3 的範圍重疊。照 [17](17-open進度總掃描.md) 結論 3，使用者已經說那條線照做，所以是這裡的 A1、A2、A4 排在它的前幾刀後面。
8. **落檔的 `status` 死了還在。** 被 `kill -9` 之後檔案還寫著 running。只從名字那條路（`procs/<名>/status`）讀的人會被騙；從 `/proc/<PID>/cwd/status` 讀的人不會。
9. **別的專案的 9 隻 agent 用自己 repo 裡的定義**，那些 repo 由別的 agent 管。加法的刀它們不用動；Z1、Z2 要寄信請它們改。
10. **每隻自己那份不會跟著變**（`system.txt` 14 份、`tools.json` 12 份、小格的 `exec.json` 12 份）。11-24 是用一次性腳本停著改的。
11. **`persist` 做成指到自己的連結時**，整份抄 stack 的動作（人手 `cp -r`、備份）會不會繞圈，要先試。另外 [16](16-過去定案與新模型的衝突檢查.md) 的衝突 D 記著使用者兩次說過不想硬性依賴 symlink；這裡的 `persist` 連結與 `proc → procs` 連結都碰到那一條。
12. **「不認得的鍵就忽略」幫了加法，也會騙人。** 舊的 aos-loop 忽略 `loop.json` 的新鍵、舊的 daemon 忽略信裡的新鍵並回 `applied: true`（3.2 的 A7）。新東西送給舊行程時不會報錯，只是沒做；每一刀的驗法都要有一條「對方其實是舊的」時看得出來。

## 5. 要問使用者的

**第 1 題　過渡期可不可以新舊兩種都寫、都收？** 你 11-05 說過「其實不用管舊版本遷移這件事，我們在proto8內，就是一律當成沒有舊版。畢竟是prototype-8」；11-24 又說新的實作「可以和我們現在的aos體系共存」。

- a. 可以有過渡期：長駐的那兩支新舊都寫、都收，等整棵樹重起過一次就把舊的拿掉，不留相容的程式。
- b. 不要過渡期：等介面全部談定，停樹一次全換（像 11-24 三分那次）。
- c. json 窗永遠留著，當成落檔那個實作自己的內部格式；介面只加不減。

推薦 a。理由：活樹現在就有 50 支行程跑著舊執行檔，混版擋不掉；a 的過渡最短可以只有一天（下一次開機）。

**第 2 題　`AOS_STACK` 這個名字留不留？**

- a. 留。意思改成「我的身體在哪」；落檔的實作裡它照舊是硬碟上的夾，`persist` 指回它。
- b. 換新名字（身體一個、要留的一個），`AOS_STACK` 退場。
- c. 先不定，等 03、06 的盤點。

推薦 a。理由：1,592 處不用改字，別的專案的定義也不用動；要改的只有定義頁與「會留」那幾句。

**第 3 題　「.stack就沒有了」包不包括硬碟上 `~/aos-home/.stack` 這個夾？**

- a. 不包括。夾不動，它只是落檔實作放身體的地方；文件不再把 `.stack` 當一個概念講。
- b. 包括。夾改名並搬一次（兩台各停一次樹、手改殼設定檔與前端服務檔、文件約 340 處、guard 認的字面先換）。
- c. 等要做 tmpfs 或 FUSE 那個實作時一起搬。

推薦 a，c 次之。理由：b 是 3.3 清單上最貴的一項，而且換來的只是名字。

**第 4 題　根自己與別的專案的樹（43 個 proc、24 隻 agent）要不要跟著每一刀走？** 它們跟 repo-aos 用同一份 `bin/`、`lib/`。

- a. 照現在：同一份。每一刀都必須對舊版面完全相容，才准裝。
- b. 會改行為的刀，先在另一份 `AOS_HOME` 起一棵試驗樹跑，穩了才裝進共用那份。
- c. 把 repo-aos 這棵分出去用自己的一份，拿它當先行的樹。

推薦 b。理由：不用動現在的擺法，試驗樹本來就是測試線每天在做的事；c 會讓兩份程式長期並存。
