# 權限、隔離、身分：過去的規劃對照新模型（報告 15）

← [架構規劃入口](../README.md)

寫的人是這批的第 15 隻子 agent。只讀 repo、只寫這一份；實測只在 `/home/guanyu/.aos/scratch/aos-proc-arch-1125/15/` 跑，沒留行程。「新模型」指 [9P proc 第一輪談話](../../9p-proc-1125.md)「定了的」那一節。三種話分開：使用者說的（引號、逐字）、查到的（附 `檔名:行號` 或實測編號）、我的推論（標「推論」；外部知識沒在這台驗過的標「憑記憶」）。

幾個詞先用白話說一次：**user namespace**＝Linux 給行程開的一間自己的辦公室，裡面的工號（uid）跟外面不同，bwrap 沙箱與 `sub:N` 都靠它；**mount namespace**＝每個行程自己的一份「看得到哪些資料夾」；**SO_PEERCRED**＝unix socket 的來電顯示，核心告訴收的那邊「打來的行程 pid、uid 是多少」；**ACL**＝資料夾上另貼的一張「這幾個人也能進」名單。

## 1. 結論

1. **原則一條都沒被推翻。**「只防走規矩的存取…」（11-21）、「先做防呆…單人使用，模型可信」（11-18）、保底是 Linux（C-47）、權限歸 daemon 那層（C-64）放進新模型都原樣成立；「daemon＝Linux 與 aos 之間的橋」就是 C-64 的新說法。
2. **最大的衝突在入口。**（實測 1）`/proc/<PID>/cwd` 只有「同一個 Linux 帳號、而且沒進自己的 user namespace」的行程走得進去。今天兩條隔離路，`limits.user: "sub:N"`（11-19 已做）與 aos-sandbox 的 bwrap，都會開 user namespace，裡面的 proc 連根 daemon 的入口都走不進去，`procs/<名>` 那種指到 `/proc` 的連結對它全是死路。反方向沒事：外面的 daemon 與使用者走得進裡面每一隻。
3. **這不是可以繞過去的限制**（推論，依 man 頁）：走得進 `/proc/<PID>/cwd` 的人也走得進 `/proc/<PID>/root`（同一道檢查），等於看得到那支行程看得到的一切。所以「靠 /proc 入口互通」與「彼此之間有牆」是同一件事的正反面。牆立在哪裡，入口就得在那裡換一種形式（綁進去的路徑，或 socket）。
4. **活著走 socket，白送一個身分事實。**（實測 2）收的那邊拿得到對方的 pid、uid，是核心填的，對方改不了。同帳號時 uid 沒用，但 pid 往上找祖先就對得到 daemon 表上的哪一隻。過去「同帳號什麼都分不出」（K9、11-21 規劃）的死角，在活著那條路補上了；掛了走寄信那條路照舊是寄的人自己寫的字。
5. **三十項的分布**（第 3 節）：原樣成立 13、說得更清楚 6、要改寫 4、被取代 3（其中兩項只取代「活著」那一半）、互相衝突 3、不相干 1。衝突的三項是 `sub:N`、每隻 agent 自己的命名空間（機制那一半）、11-05 的 no-pid；最後一項的舊裁定算不算數由報告 16 的 A 題問。
6. **變簡單的**：活著時認人；判死活與認自己的行程；C-64 原話那個「讓kernel成為某daemon的ctl/清單的唯一可讀寫者」同帳號也做得出防呆版；「遞給你的夾」有了落腳處。**變難的**：入口要有兩種值；persist 由 proc 自己挑，daemon 設不了它的權限；身分的根變成「誰寫得進 daemon 的 `procs/`」；兩條路的身分強度不一樣。
7. **最該請使用者裁的三題**（第 8 節）：入口在規格裡怎麼寫；socket 上「對面是誰」要不要算進介面；身分用什麼字串。

| bwrap 只多開 user＋mount namespace、保留外面的 `/proc` | 外面行程的 `cwd` 一律 Permission denied（同實測 1） |
| 外面的行程經 socket 遞一個開好的夾（fd）給沙箱裡的行程 | 沒綁進來的夾也讀得到；但從那個 fd 走 `..` 讀得到夾外面的檔（逃得出去） |

**實測 4：走得進入口，不等於讀得到裡面的檔。** `sub:5` 的 proc 自己建一個 700 的夾站進去、`status` 設 644：daemon 這邊 `readlink` 與 `stat` 都成功，列夾、讀 `status`、讀 `settings` 全是 Permission denied。走入口是直接跳到那個夾；夾本身與裡面的檔，照查普通的檔案權限。

**實測 5：目標可以自己把入口關掉。** 同帳號的行程呼叫一次 `prctl(PR_SET_DUMPABLE, 0)` 之後，別人走它的 `/proc/<PID>/cwd` 是 Permission denied，真實路徑照舊讀得到（`ptrace(2)` 第 4 步）。

## 4. 特別回答的四件事

先放一張共用的圖。任何一次存取（讀 status、寫 ctl、投信）要過三道檢查，過去的零件各自落在其中一道：

```
第一道 走不走得到     /proc 入口的規則、mount namespace（bwrap）、祖先目錄的 x 位
第二道 檔案自己的權限  擁有者與位元、ACL（subuid、aos-share、K16）、socket 檔的位元
第三道 收的那邊自己判  來電顯示（SO_PEERCRED）、kernel 站的規則、kernel_gate
       （guard 是呼叫的那邊自己擋自己，不在這三道裡）
```

新模型沒有新增或拿掉任何一道：它把第一道的預設路徑換成 `/proc` 入口，並給第三道一個新事實（對方的 pid）。

### 4.1 入口只有同帳號走得進去，跟「以後用分帳號做權限」怎麼並存

實測 1 把 9p-proc-1125 那句「不同 Linux 帳號走不進去」補成三句：

- 同帳號、但進了自己 user namespace 的（今天的 bwrap 沙箱）也走不進去。
- 外面的（開那個 namespace 的帳號）走得進裡面：daemon 與使用者永遠看得到自己起的每一隻。方向只朝下，形狀跟 daemon 的樹一樣。
- 走得進入口不等於讀得到檔（實測 4）；目標還可以自己把入口關掉（實測 5）。

| 選項 | 做法 | 擋得住什麼 | 代價 |
|---|---|---|---|
| A 同帳號＋namespace | 不分帳號。要關的 proc 由 daemon 搭布景（照 aos-sandbox 今天的旗標：mount、pid、網路一起隔），把根（或它該看的那幾個 proc 夾）綁進去，`AOS_ROOT` 改指綁進去的位置。沒被關的照舊用 `/proc/<PID>/cwd` | 沒綁的看不到、殺不到外面的行程、連不到外面的網路 | 沙箱裡 `procs/<名>` 不能是指到 `/proc` 的連結；布景搭錯就全開（11-18 sbx-fix 的教訓）；布景搭好後要多給一個夾很麻煩；eca 本體要進沙箱得綁一堆 |
| B 分帳號＋普通路徑＋ACL | K4～K18 已裁的路。入口與 `procs/<名>` 改走真實路徑，每個 proc 夾照 K16 設 ACL | Linux 真的擋：讀寫、kill、偷看行程 | `/proc` 入口的好處對這些 proc 全沒了（路徑上限、死了馬上讀不到）；身體只能放在有真實路徑、吃 ACL 的地方（`/mnt/c` 不行）；家目錄 x 位那題要先解；11-14、11-18 列過的換 uid 的坑（檔案擁有者、git、收件人搬不動的信、看別人全是 65534）全部跟來 |
| C 由 daemon 代轉 | 被關的 proc 只拿到自己 daemon 的一條 socket，要讀誰、寫誰、投誰都請 daemon 代做，或由 daemon 遞一個開好的夾 | 每次存取都過一個能說不的地方；天然認得寄件人 | daemon 變成每次都要經過的一站，它忙或死，底下全停；要寫代轉協議；遞夾那招 `..` 逃得出去（實測 3），只算防呆 |
| D 現在不隔離 | 全部同帳號走 `/proc` 入口；`sub:N` 與沙箱照今天的用途（工具級、不必跟別人說話的 proc） | 沒有牆 | 零成本；跟隔離等級甲一致 |

**推薦：規格現在只要做到「不把入口的值寫死」**，把 `AOS_ROOT` 定義成「一條走得到根的路，值由起你的 daemon 給」，預設值照使用者定的 `/proc/<PID>/cwd`（就是 D）。之後要牆，先走 A，B 的 ACL 在真的要硬擋時疊上去，C 留給跨樹與跨機器。理由：使用者 11-25 講到 FUSE 時 `AOS_ROOT` 會是另一個值，他說「不過這只是針對AOS_ROOT而已，沒差」；A 不動他定的預設、不用 root、同帳號所以他照樣改得動 agent 寫的檔；B 跟入口衝突最深。寫成題目在第 8 節題 1、題 5。

### 4.2 誰可以寫某個 proc 的 ctl、誰可以讀它的 status／settings／persist

| 手段 | 看的是什麼 | 擋得住 | 擋不住 |
|---|---|---|---|
| 檔案位元＋ACL（第二道） | 呼叫的行程是哪個 uid、gid | 別的 uid：讀、寫、連 socket（實測 2 的 600） | 同 uid 的任何行程（今天全部）；原地改檔看不出誰改的（11-21 的 T5）；root。ctl 若是普通檔，「可寫」就是可以下任何命令，分不出「准 stop 不准別的」。`/mnt/c` 上位元沒有意義 |
| SO_PEERCRED（第三道的事實） | 連線那一刻對方的 pid、uid、gid，核心填的 | 寄件人欄亂寫；不同 uid 一眼分出；同帳號靠 pid 分 | 見下面「同帳號反查」；連線被繼承時認到的是連線的那支；收的人自己在 namespace 裡會看成 0 或 65534；只有活著的行程當場收才有，落檔的 ctl 檔沒有 |
| kernel 當權限站（第三道的政策） | 請求的內容（要做什麼），加上寄件人 | 走規矩的請求裡不該做的事：名字白名單、同時幾隻、份額夾值、留給 agent 判 | 不經過它的。今天拿掉 `AOS_KERNEL` 直寄 daemon 就繞過；直接寫檔的 pause、塞 queue、讀 history 根本沒有信 |

對照 Plan 9 原樣（報告 07 第 2.6 節與它的對照表「誰在問」那列）：那邊「誰能控制這個行程」就是 `ctl` 檔的權限位元（擁有者才寫得進），而且是核心一個人替所有行程認人。aos 是每個 proc 自己回答，所以第一列只分得出 Linux 帳號（今天全部同一個），要分得出「哪一隻」只能靠第二列。

**同帳號時，SO_PEERCRED 的 pid 可以反查它是哪個 proc 嗎？** 可以，有三條線，可信度不同：

| 反查的線 | 怎麼做 | 好不好騙 | 斷在哪 |
|---|---|---|---|
| 祖先鏈 | 從 pid 往上讀 `PPid`（`/proc/<pid>/status` 模式 444，人人可讀），碰到 daemon 記的那支就是那一列。今天 daemon 一層層是父子（`ps` 實看），所以祖先鏈倒過來唸就是名字路徑（推論） | 難：行程改不了自己的祖先 | 脫離祖先的行程；eca 的 `claude` 掛在 tmux 底下（要登記它的 pid）；登記來的外來 proc 只有 pid 直接對上 |
| cgroup 的格 | 讀 `/proc/<pid>/cgroup`，路徑裡就是哪一列（`docs/09-份額.md:93` 每列一格） | 同帳號能自己搬格（同檔 `:103`「不防同 uid 故意改寫 cgroupfs」）；換成 `sub:N` 之後搬不了 | 要開 cgroup（預設關） |
| cwd、環境變數 | 讀 `/proc/<pid>/cwd` 或 `environ` | 一個 `cd` 就騙過（實測 2） | 只能當顯示 |

所以結論是：同帳號下它給的是「防呆級的真話」，守規矩的行程不用自報就被認出來，隨手亂填的寄件人會被看穿；刻意要冒名的（改對方的工具讓對方替你連）照舊擋不住，跟「擋不住會開 shell 刻意造假的 agent」是同一句。前提是 daemon 的目錄要有地方答得出「這個 pid 是誰」，這本來就是橋的工作；收的人只把號碼交給 daemon 問，不自己去翻 `/proc`，這樣碰 pid 的仍然只有 daemon（第 29 項）。

三種手段各管一件事，疊起來用（推論）：位元與 ACL 管「哪個 uid 進得來」，來電顯示管「這條連線是哪一隻」，kernel 管「這件事該不該做」。對到 proc 目錄：

| 東西 | 誰讀 | 誰寫 | 靠什麼 |
|---|---|---|---|
| `status`、`_metainfo` | 進得來的都可以 | 自己 | 位元。它是公開的，別把祕密寫進去（Linux 自己的 `/proc/<PID>/status` 也是人人可讀） |
| `settings` | 至少 daemon 要讀得到（實測 4 讀不到就等於沒登記） | 自己 | 位元或 ACL |
| `ctl` | — | 位元決定哪些 uid 碰得到；活著的行程當場收時，再看對方是誰決定聽不聽 | 預設照今天：都聽，只把「誰寫的」記下來 |
| `persist`（信箱以外） | 自己與使用者 | 自己 | 夾 700；分帳號時加預設 ACL 給 daemon |
| `persist` 裡的信箱 | 自己 | 別人只能投、不能列 | 投遞箱樣板（`aos-share drop`）；同帳號時只是慣例 |
| daemon 的 `procs/` | 進得來的都可以 | 只有 daemon | 這個夾的寫入權就是命名權（第 7 節） |

### 4.3 每隻 agent 只看得到掛給它的子樹

**在這套裡怎麼做**（選項 A 的細節；實測 3 驗過每一步的機制）：

1. daemon 起 proc 時搭布景：開 mount namespace，只綁系統唯讀底、aos 的家（唯讀）、它自己的身體與 persist、工作區與地盤，再加「掛給它的 proc」，每個是一個綁進去的夾，或只綁那個 proc 的 socket 與信箱。全部放在一個根底下，`AOS_ROOT` 指它。
2. 裡面：綁進來的讀得到、連得上，對方的來電顯示看得到外面的真 pid；沒綁的不存在。
3. 外面：daemon 與使用者從 `/proc/<裡面那支的 PID>/cwd` 照樣看得到它的身體，連只存在於它 namespace 裡的 tmpfs 都行。`/proc/<PID>/root` 是「看它眼中的世界」的窗，`ls` 出來的就是它看得到的全部，可以拿來稽核布景有沒有搭錯。

**為什麼不能讓被關的 proc 也走 `/proc` 入口**（推論）：`cwd` 與 `root` 是同一道檢查（`proc_pid_root(5)`）。能走進根 daemon 的 `cwd`，就能走進它的 `root`，那是整台機器。Linux 在 user namespace 的邊界把這條路整個擋掉，沙箱才成立。

**跟 index「每隻 agent 自己的根」的關係**：同一張清單的兩個產物。清單＝「掛給這隻 agent 的東西」，每項有名字、指到哪、可讀或可寫、一句話。

| 產物 | 給誰 | 作用 | 等級 |
|---|---|---|---|
| 它的根 index（`_index.json`，項目用 `$ref` 加一句話） | 腦 | 地圖：有哪些東西、各是什麼。這是使用者 11-24 說的「…這和plan 9 namespace不太一樣，因爲我們還添加description等…」那一半 | 防呆：走 index 的工具只看得到這幾樣，shell 照樣哪裡都去得了 |
| 布景的綁定 | 核心 | 地圖以外真的沒有路。這是 Plan 9 命名空間有的那一半 | 牆 |

兩個從同一張清單生出來才不會對不上（地圖有、布景沒綁，工具報找不到；布景綁了、地圖沒寫，看得到卻不知道）。私有地盤（`wf/ws`）與 persist 就是清單裡可寫的那幾格。kernel 在這裡的位置：決定清單內容的人（第 19、27 項）。

| 選項 | 內容 | 代價 |
|---|---|---|
| a | 只做清單與地圖，不搭布景 | 便宜；沒有牆。今天的等級 |
| b | 清單＋daemon 搭布景（mount namespace） | 見 4.1 的 A |
| c | 清單＋分帳號與 ACL | 見 4.1 的 B |
| d | 用 FUSE：一台伺服器照「誰在問」回答不同的 `procs/` | 可以中途改；但單點、每次操作多一趟來回、跨帳號要 root 開 `user_allow_other`（這台 `/etc/fuse.conf` 那行是註解，實看）。細節歸報告 09 |

**推薦 a 先做，要牆時走 b。** 理由：清單是四個選項共用的；先把「掛給它的清單」這個檔定下來，現在只拿去生 index 也有用。

### 4.4 寄件人的身分在兩條路各怎麼認

| | 活著：走 socket | 掛了：走寄信 |
|---|---|---|
| 現成的事實 | 核心給的 pid、uid（實測 2），加一個釘住行程的把手 | 信上的 `sender`，寄的人自己寫的（今天就是）；信夾的擁有者 |
| 怎麼變成「是哪一隻」 | pid 走祖先鏈或 cgroup，對到 daemon 的名字（4.2） | 照信上寫的；分了帳號才有第二個事實可對（K9、11-21 的七刀） |
| 同帳號時 | 防呆級的真話 | 完全自報 |
| 寄的人要知道自己是誰嗎 | 不用。收的人反查，所以搬到別台 daemon 底下一個字都不用改 | 要，得有人在起它時告訴它 |
| 轉手 | 下一站看到的是轉手的那支 | 同：每一站只認得上一站（C-47「不記走過哪些站」） |

三件要注意的事：

1. **兩條路強度不一樣。** 想冒名的人只要挑對方睡著時寄信，或直接往信箱丟檔。所以只在 socket 那條擋人等於沒擋；可以放心做的是「把到手的事實附上」（顯示、記帳），不拿它擋。
2. **寄信那條路上，能認人的只有「跟 daemon 或 kernel 說話」的那幾步**（推論）。報告 20 推薦「問信箱在哪」＝讀 daemon 留的表（讀檔，沒有人知道是誰在問），叫醒掛在「寄完信提醒對方的 daemon」那一下；照那個做法，認得出的只是誰來提醒，不是信是誰寄的。要讓寄信那條路的寄件人也有核心給的事實，只有代投一途：寄件人把信交給 daemon 或 kernel，由它落檔並寫上它認到的寄件人（plan9-ns-1124 寫的「daemon 代送」）。
3. **牆與認人是綁在一起的**（推論）：被關進布景的 proc 看不到別人的信箱，寄信一定要有人代投，代投的人順手就認了寄件人；沒被關的直接投、身分自報。這跟 10-24 的 S14 與「只防走規矩」是同一件事。

**跨機器**（報告 07 把這題留給這份與報告 20）：出了這台機器就沒有來電顯示，9P 連線上報的名字也是自己寫的。這時身分只能來自通道本身，例如兩台之間走 ssh，對面是哪個帳號由 ssh 決定（憑記憶、推論）。過去只談到兩次，都沒定：11-14 三圈裡給專區回信的「L2 簽章」（`thinking/2026-11/14/sec-1114/05-採納表.md` A3），與 11-24 家機 `main` 的意見「兩個人的樹碰在一起」需要身分（`aos的目標-1124/README.md` 第三輪）。現在不用定；規格只要不把「寄件人驗得了」寫成承諾。

**推薦**：現在只定一句，規格寫「活著那條路，收的人拿得到 Linux 給的對方 pid 與 uid；daemon 的目錄要答得出『這個 pid 是誰』」。要不要拿它擋人，照 11-21 的 1D（各 kernel 自己選、範本預設不看）。寄信那條不動。這不違反 11-23「寄件人驗證…先不做」：沒有做驗證，只是不把到手的事實丟掉。寫成題目在第 8 節題 2。

## 5. 對著「定了的」逐條：權限面的含意

| 定了的 | 權限面的含意 |
|---|---|
| persist 在哪以 proc 自己說的為準；daemon 可在 `/tmp` 給預設位置 | daemon 設不了 proc 自己挑的位置的權限，K16 只剩預設位置適用（題 4）。`/tmp` 大家可寫又是黏著位夾：別的 uid 在裡面跟連結、開別人的檔有額外限制（這台 `protected_symlinks`、`protected_regular` 都開著，`proc_sys_fs(5)`），預設那塊要開成自己的 700 夾 |
| 介面基於 9P，支援這套的就是 aos proc | 外來 proc 不是 daemon 起的：份額與身分換不了，認人只有 pid 直接對上 |
| ctl、status 純文字；寫 ctl 回來＝收到 | 格式不影響權限。只有活著的行程當場收的 ctl 才知道是誰寫的 |
| 目前只給 status | 進得來就讀得到 |
| token 各自報、kernel 的帳在 kernel | 自報的不拿來記帳 |
| daemon＝橋，也是 aos proc | 所有碰 Linux 的權限動作（上限、換身分、cgroup、布景、pid 對名字）都在它身上；它的 `procs/` 就是命名權 |
| kernel＝普通 aos proc | 權限站沒有特權，靠 daemon 的 ctl 願意只聽它 |
| `proc` 與 `procs` 同指一處 | 兩個名字的權限要一樣，不要一個開一個關 |
| 入口＝根 daemon 的 PID | 只有同帳號、沒進 user namespace 的走得進（題 1） |
| stack＝活著的身體 | 「不碰別人的 stack」要改寫；身體的權限每次起來重設（今天換了身分的 proc 就是這樣：daemon 每次起都重設小格的 ACL，`docs/09-份額.md:52`） |
| 要留的放 persist | 跟私有地盤同構；別人只需要裡面的信箱 |
| 活著走 socket、掛了走寄信 | 兩條路身分強度不同（4.4） |
| 問信箱時要不要叫醒是 daemon 的設定 | 「問」是一個動作，這一步是寄信那條路唯一能認人的地方 |

給做綜合的人：權限面對介面只有四個要求（都是推論，寫成題目的在第 8 節）。

1. `AOS_ROOT` 的值不寫死（題 1）。
2. daemon 的目錄答得出「這個 pid 是底下的誰」（題 2）。
3. `status`、`settings`、信箱要讓 daemon 讀得到、投得進（題 4）。
4. persist、信、筆記裡不存 PID，也不存 `/proc` 開頭的路徑。

## 6. 新模型讓哪些變簡單、哪些變難

**變簡單**

1. 活著時認人：不用先分帳號，就有自報以外的事實（第 10 項）。
2. 判死活、認自己的行程：走得進入口就是活著；daemon 對換了身分的 proc 也走得進去（第 26 項）。
3. 「認自己」不用問 kernel：proc 站在自己的身體裡，`settings` 就在手邊。今天「站 3 秒不回，14 處工具一起失敗」那種連坐少掉大半（推論）。
4. C-64 原話的「唯一可寫者」：daemon 看得到是誰在寫 ctl，同帳號也做得出防呆版（第 18 項）。
5. 監督的人往裡看：`/proc/<PID>/cwd` 與 `root` 讓 daemon、使用者看得到被關起來的 proc，不用進它的 namespace。
6. 「遞給你的夾」「權限寄給 kernel 要」有了具體動作：往某隻的根裡掛一項（第 13、27 項）。
7. 哪些是別人可以碰的，第一次有明確名單（ctl、status、信箱）。規則 1、guard 的禁寫清單、ACL 樣板都能照這張名單寫。
8. 跨帳號說話：socket 檔的位元一開就連得上，不必先解決 11-12 留下的「跨帳號寄信的資料夾權限」。
9. 家目錄那題（第 28 項）：proc 站在自己的身體裡、路徑都相對時，換了身分的 proc 不必從 `/` 一路走下來（推論；11-21 的 T2 註記過「相對路徑不檢查祖先」；程式與庫的絕對路徑仍要走得到）。

**變難**

1. 入口跟兩種隔離都衝突，要有兩種值（4.1）。
2. persist 自己挑：daemon 沒辦法替它設權限；讀不到 `settings` 會變成不出聲的故障（實測 4）。
3. 身分的根變成 `procs/` 這個夾：誰寫得進去，誰就能把名字指到自己。同帳號下任何人都寫得進去（今天改表也一樣，但新模型裡這是唯一的身分來源）。
4. 一隻 proc 是一串行程，入口卻是一支行程；eca 本體不在 daemon 的子孫裡（第 9、22 項）。
5. 兩條路身分強度不同，規矩要寫清楚，免得誤以為都驗過（4.4）。
6. 「同帳號一定走得進」不是保證：目標可以自己關掉（實測 5）。
7. kernel 少一個攔截點：活著那條路不用問位置，11-21 的「回抄本」「回位置＋開權限」要換做法（第 19 項）。
8. 布景搭好之後要多掛東西不容易：沒有 root 的 daemon 沒辦法往已經在跑的 namespace 裡補綁定（憑記憶，沒實測）；可以先綁一個之後能往裡面放東西的夾、遞一個開好的夾（實測 3，防呆級）、重起，或走 FUSE。

## 7. 邊緣狀況

1. **包了沙箱之後，daemon 的直接子行程不是站在身體裡的那支。**（實測 3）bwrap 外面那支的 cwd 是起它的地方，站在 `/aos` 的是孫行程。`procs/<名>` 要連到裡面那支的 PID。
2. **PID 是每個 pid namespace 各算各的。** `/proc/<PID>/cwd` 這串字拿進沙箱，指的是不存在的行程，或者剛好同號的另一支（推論）。所以這種字串不能跨 namespace 傳。
3. **`readlink /proc/<PID>/cwd` 讀到的字是對方眼中的路徑**（實測 3 讀到 `/aos`），外面不能拿來當路徑用；要進去就直接走那個入口。
4. **名字被頂替。** `procs/<名>` 連到 `/proc/<PID>/cwd`，那支死了、PID 被別的行程拿到，名字就指到別人。daemon 是父行程時可以「先拿掉連結、再收屍」，沒收屍之前 PID 不會被回收（憑記憶），這個窗就關掉；登記來的外來 proc 關不掉，只能縮短。根的 PID 同理。
5. **表外的行程＝人**只是推定。收的人看到「不在任何 daemon 表上的同帳號 pid」會當成使用者的殼；同帳號下任何脫離祖先鏈的行程都長這樣。
6. **權限站掛了。** 若 daemon 的 ctl 設成只收權限站那支，站一死就沒人能起停。一定要留「表外的人照收」這條保底（N-42-2 原意）。
7. **驗的人要在外面。**（實測 2）kernel、llm kernel 若自己被換成 `sub:N`，看別人全是 0 或 65534。11-21 已經替使用者定了「驗的人不換身分」，照舊。
8. **工具與子 agent 替它連線**：來電顯示是工具那支的 pid，要走祖先鏈才對得到 agent。像我這種 eca 的子 agent，環境裡的 `AOS_STACK` 就是 eca-aos 的（實看），照哪一條線查都算成 eca-aos 那一隻；這跟使用者 11-12 說的「…他們面對的就是這個eca proc」一致。
9. **`/mnt/c` 不能放身體或信箱。** 那裡不吃 ACL（`docs/09-份額.md:55`）、權限位元沒有意義（`wf/ws/eca-aos/notes.md` 11-23 查的），也 bind 不了 unix socket（`proto8/py/aos/agentlib/cli_session.py:17` 的註記）。今天幾棵樹的工作區在 `/mnt/c`，stack 不在，還好。
10. **`limits.user` 兩種寫法，誰走得進不一樣**（第 21 項）：`sub:N` 是開那個 namespace 的帳號（使用者、daemon）走得進；真帳號只有 root 走得進，使用者自己的殼走不進（推論）。aos-sandbox 的 `user: 帳號`（經 sudo 換成 `aos-run`）是後者。
11. **沙箱「設定壞了照跑」**（11-12「甲，出事自己負責」）是給工具級沙箱的裁定。哪天拿布景當「每隻 agent 的世界」，搭不成還照跑就等於全開；到時要分成兩種，不是現在的事。
12. **`AOS_ROOT` 是每次起樹都不同的值**，只能活在環境變數裡；寫進 persist、信、筆記的都要用名字（第 17 項）。

## 8. 要問使用者的

**題 1：入口在規格裡怎麼寫？**「定了的」說入口是根 daemon 的 PID；實測 1 顯示被隔離的 proc（今天的 aos-sandbox、`sub:N`）走不進去。

- a. 寫成「`AOS_ROOT` 是一條走得到根的路，值由起你的 daemon 給」，預設值就是 `/proc/<PID>/cwd`；被隔離的 proc 拿到的是綁進去的路徑。`procs/<名>` 也只規定「走得進去」，不規定它是連結。
- b. 寫死 `/proc/<PID>/cwd`；被隔離的 proc 不算在樹裡，只靠綁進去的 socket 與信箱跟樹說話。
- c. 寫死 `/proc/<PID>/cwd`，而且不拿會開 user namespace 的東西關 agent（`sub:N`、bwrap 只留給工具）。

推薦 a。理由：預設不變，只是不把值寫死；使用者 11-25 講到 FUSE 時 `AOS_ROOT` 會是另一個值，他說「不過這只是針對AOS_ROOT而已，沒差」。報告 17 也問了同一題，推薦的方向相同（名字那條路才是介面）；報告 16 的 A 題問的是更上面一層：11-06「不放寬」還算不算數。

**題 2：socket 上「對面是誰」要不要算進介面？**

- a. 算：規格寫明收的人拿得到 Linux 給的對方 pid、uid，daemon 的目錄要答得出「這個 pid 是誰」；預設只附上（顯示、記帳），不擋。
- b. 不算：照舊只看訊息裡自己寫的寄件人，要認人的實作自己想辦法。
- c. 算，而且預設就擋：自己寫的跟查到的對不上就拒收。

推薦 a。理由：這個事實是白送的，同帳號也分得出誰是誰；擋不擋留給各 kernel（11-21 的 1D）。c 會誤傷轉手與工具代連的情況。報告 20 的 3.10 是同一個方向：收的人看到的另放一個鍵、由收的人寫，不跟自己報的混在一起。

**題 3：身分用什麼字串？** 今天是 stack 路徑（11-13「就統一用stack」），額度、`by_sender`、鎖的名牌都拿它當 key；新模型的 stack 是每次都不同的 `/proc/<PID>/cwd`。

- a. 名字路徑：從根往下的名字（例 `repo-aos/eca-aos`），重起不變、跨機器也成立；由 daemon 起它時給，不寫進 persist。
- b. persist 的路徑：最像今天，但 proc 可以自己挑、一搬身分就變。
- c. 兩個都帶：名字路徑當身分，persist 裡的信箱當回信位址。

推薦 c（身分照 a，回信位址本來就是另一欄）。理由：名字是 daemon 給的、收的人反查得到；位址是位址。跟報告 06、20 重疊，以綜合稿為準。

**題 4：persist 與身體的權限誰設？** K16（11-13 已裁）是「stack 的 ACL 由 daemon 自動設」；新模型是 persist 由 proc 自己挑。只有分了帳號才有差別。

- a. daemon 只管它給的預設位置；proc 自己挑的自己管。規格只要求 `status`、`settings`、信箱要讓 daemon 讀得到、投得進，不然當沒登記。
- b. 不管誰挑的，daemon 起它之後都去那個位置重設一次權限。
- c. 規格不管權限。

推薦 a。理由：b 會讓 daemon 去改別人挑的任意路徑（`thinking/2026-11/19/subuid-1119.md` Q1 的選項 d 就是因為「daemon 會默默改你家目錄的權限」不被推薦）；c 會讓「daemon 讀不到 settings」變成常見的不出聲故障。

**題 5（方向，可以晚點答）：以後要牆，先走哪條？**

- a. 同帳號＋daemon 搭布景（4.1 的 A）。
- b. 分帳號 `sub:N`＋ACL（4.1 的 B，K4～K18 已裁、daemon 已會換）。
- c. 兩條都留，各 daemon 自己選。
- d. 現在不排（照 11-24「權限這塊可以先記錄下來，之後可以來做。」），只要題 1 選 a 不擋路。

推薦 d，並記下「到時先 a」。理由：a 不動入口的預設、不用 root、這台現成就有 bwrap（沒有 `setfacl` 指令）；b 的已裁內容不作廢，留給真的要硬擋的那一步。
