# 16 過去定案與新模型的衝突檢查

← [架構規劃入口](../README.md)

這份只做一件事：把 [9p-proc-1125](../../9p-proc-1125.md)「定了的」每一條，拿去對過去寫成條文的定案與使用者歷來的原話，分成四種關係擺出來。我不裁決。標「推論」的是我的讀法；其餘都附出處。使用者的話一律逐字。

## 1. 結論

1. **新模型大半接得上舊話。** 介面這個想法他 10-14、10-28 就講過；daemon 當橋，「橋梁」是 11-05 的原字；kernel 是 daemon 底下的一個 proc，是他 11-12 回憶的早期想法；stack 是跑的時候才有東西的地方，是 10-16 夜的原意；要留的東西放哪由主人定，N-14、N-16 本來就這樣寫。
2. **真的衝突六處**（第 3 節）。四處是他說新話時沒提到舊裁定，要他明講哪個算數：
   - A　別人不碰 pid（11-05 原話、11-06 選項框選「不放寬 (Recommended)」）↔ 入口是根 daemon 的 PID；
   - B　image 是 root daemon 的 stack 加 ws、可遷移性是上位原則 ↔ stack 是活的身體、不留；
   - D　不想硬性依賴 symlink（11-03、11-11 各說一次）↔ procs/<名> 連到 proc 的目錄；
   - F　一般 proc 只看得到 kernel（11-11）↔ 大家自己從根走進去、活著直接連 socket。

   另兩處是他自己明講要改的，方向不用裁，只要補洞：C　aos proc 的定義；E　窗是 JSON、state 分兩扇、純文字帶 `.txt`。
3. **A 和 B 是連著的。** 11-06 把「經 daemon」降成建議時，唯獨 no-pid 那批沒放寬，寫下的理由是「pid 搬不走」，也就是可遷移性。可遷移性若還是上位原則，A 就得另想辦法；若降級，A 的理由也跟著沒了。
4. 他 11-17 定過通則：條文打架時「新的覆蓋舊的」（`T/11/17/待裁網頁-題號對照.md:5`，原話「喔等等，應該說新的覆蓋舊的」）。照這條，11-25 的話預設就贏。所以第 3 節要他看的其實是：**舊裁定當年擋掉的那些後果，現在接不接受**。
5. **舊條文有規定、新模型沒提到、但一定會被影響的有 24 項**（第 4 節）。最要緊三項：死掉或睡著的 proc 去哪看（11-19 才裁過「留在表上並標明死了」）；socket 上來的話算 queue 還是 mailbox；不是 proc 的函數（工具）還有沒有 stack。
6. **名詞**：`stack`、`proc`、`daemon` 三列要改寫，`小格`、`heap`、`state_flux`、`介面` 四列要補句，新詞六個；「身體」一詞現在有三個意思（第 5 節）。
7. **「aos proc」過去沒有被正式定義過。** 名詞表只有 `proc`（「跟 Linux 同字同義」）；在 daemon 表上才算，是知識庫與程式的做法。11-12 他說過一次「只要這個手段能聯絡上的，那自然是proc」，被問到跟 C-80 衝突時自己收回；11-24、11-25 等於把那次收回再翻回來（第 6 節）。

- 11-05 晚原話：「靠着pid來找東西，不太符合我們aos體系的概念。除去daemon本身與linux原生proc有所接觸，可能會透過pid來強行控制一些東西，或是弄一些linux原生的特殊機制外，其他人若有相關需求，最好都是透過daemon進行轉接。至於如何找到daemon，大多時候是透過環境變數。」（`T/11/05/no-pid/README.md:9`）
- 落成 N-17：對 `/proc` 判活「只剩 daemon 自己」，「其他人不碰 pid」（`窗/06-N-17/01:4`）；N-67 ④「行程狀態（pid…）不是真相」（`定義/09-N-67.md:10`）。
- 11-06 把「經 daemon」降成建議時，專門問了這批要不要跟著放寬，他選「不放寬 (Recommended)」，落地寫「理由寫進可遷移性條文：pid 搬不走」（`T/11/06/os-concepts/README.md:20`；C-83 `理念/09:9`）。

**新的**：「linux的/proc/<PID>不用加東西，我們就是給根daemon的PID，然後讓大家自己去訪問/proc/<PID>。」（`新:15`）；實測表：proc 被 `kill -9` 之後那條路馬上讀不到，「不用問任何人就知道死了」（`新:50`）。

**照新的做，當年列過的後果會回來**（11-06 那題「放寬」那一欄，`T/11/06/os-concepts/10:56`）：

| 後果 | 依據 |
|---|---|
| 沙箱裡走不通：沙箱是新的 pid namespace，「裡面看不到外面任何 pid」，`/proc/<根 PID>` 在裡面不存在或是別的行程 | `T/11/05/no-pid/04-沙箱.md:7`（這正是 no-pid 當年的起因） |
| 不同 Linux 帳號走不進去 | 本機 `man 5 proc_pid_cwd`：讀這個連結要過 `PTRACE_MODE_READ_FSCREDS` 檢查；`新:56` 也寫了 |
| 今天已有的 `limits.user: "sub:N"`（每支 proc 自己一個 uid，`N28/09:11`）就是「不同帳號」 | 推論，沒實測；指到報告 08、15 |
| 根重起，PID 就變；被接回的子項（`adopt` 預設開，`N28/05:5`）環境裡還是舊的 PID 路徑 | 推論：行程的環境變數起來後改不了 |
| `procs/<名>` 連結只記 PID，沒有 N-17 另外兩道（`started_at_ticks`、`boot_id`）；PID 被別的行程重用時會連到別人的夾 | 推論；N-17 `窗/06-N-17/01:4`；no-pid 當年也把「pid 重用、重開機」列為解掉的題（`T/11/05/no-pid/04-沙箱.md` 那張表） |
| kernel 管不到直接寫檔、直接連線的人 | 11-06 那一欄原字「判官管不到直接寫檔的人」；跟 F 是同一件事 |
| 跨機器沒有 `/proc` | 同一欄「跨機 pid 無意義」；`新:111` 已提 |

**照舊的做**：PID 路徑不能直接交到大家手上。入口得是一條固定名字的路（硬碟上的夾、連結或掛載點），由根 daemon 接到自己身上。`新:110` 的邊緣第一條已經有這個零件。

**要他裁**：11-06 那個「不放寬」還算不算數。選項與推薦見第 8 節第 1 題。

### B　image＝root daemon 的 stack＋ws、可遷移性是上位原則　↔　stack 是活的身體、不留（定 11、12、1）

**舊的**

- 11-05「在我們這邊，daemon就像是硬體，各stack就是各程序所佔據的記憶體空間。ws則是外置記憶體。」（`T/11/05/portable-flow/02:5`）→ C-79「image＝root daemon 的 stack＋ws」（`時空:14`）；11-07 sol 審查 #19 再裁一次「image＝stack＋ws」（`T/11/06/os-concepts/README.md:54`）。
- 11-05 夜「我知道linux有原生暫停，但我想要的是暫停後能遷移。」（`時空:10`）；11-06 定 C-83「可遷移性是上位原則」；11-10「我原本預期他就是cp過去，起daemon她就自動繼續了。」（`T/11/10/two-machines/README.md:65`）；11-15「我當初設計aos體系，想要的就是可遷移性」；11-22「我有個核心訴求，就是可以跨機器搬遷」（`T/11/22/工作區與stack-1122/01:11`）。
- N-67 ⑥ 驗法：「睡著 → `cp -a`／git → 另一台 `aos-exec` 醒來接著跑」（`定義/09-N-67.md:12`）。

**新的**：11-23「把stack一起隨機器搬遷，不是一個好主意。這塊之後我會細說。」；11-25「.stack就沒有了，它本身就是指向"一個活著的proc的身體所在"」；預設的 persist 可以放 /tmp（定 1）。11-24 談 FUSE 時他還說過「持久性/單點故障沒差，我們可以定期保存。」（`wf/progress.json` `plan9-ns-1124`；那句講的是放在記憶體裡的佇列）。

**兩邊的後果**

- 照條文字面：stack 要留、要能整夾 cp 走，跟定 11 直接相反。這條路走不通，條文一定要改；問題是改成什麼。
- 照新的、image 改成 persist 加 ws：C-83 還站得住，但預設放 /tmp 的那塊過不了關機（這台的 /tmp 是記憶體，`新:121`），更別說搬家；N-67 ⑥ 的驗法要改成搬 persist。
- 照新的、可遷移性降級：C-83 ② 的判準「會不會破壞可遷移性」（`理念/09:7`）是「經 daemon 降成建議」和「no-pid 不放寬」兩個裁定共用的理由，一降級，A 也跟著鬆。

**要他裁**：可遷移性還是不是上位原則、搬的單位是什麼。11-23 他說「之後我會細說」，還沒說。見第 8 節第 2 題。

### C　不在 daemon 下的不管、proc 都在 daemon 底下　↔　支援這套的就是 aos proc（定 2）

他自己說這塊「有點走歪了」，方向不用裁。兩種定義怎麼擺在第 6 節。要補的洞只有一個：**C-80 還留不留**。11-05「不在任何daemon下的，我們不管，我們這套體系的基礎就是daemon/loop/exec三者合一。」（`設施/02b:5`）可以有兩種讀法：定義（不在 daemon 下的不是 aos proc）或管理範圍（是不是都行，只是沒人管）。11-12 那次收回，效果等於照前一種讀（推論；經過在第 6 節）。見第 8 節第 3 題。

### D　不希望硬性依賴 symlink　↔　procs/<名> 連到 proc 的目錄（定 7、9、10）

**舊的**（同一個設計題他答過兩次，都偏「不要」）

- 11-03，頂層擺兩條路（a 名單上記路徑；b 小格裡放 symlink），他答：「那就記錄在名單上。我是希望盡量不要用捷徑啦。」（`T/11/03/procs/01:21`）→ N-28「不建捷徑」（`N28/03:6`）。
- 11-11：「然後kernel給狀態位址...希望不是使用symlink，我不希望aos體系硬性依賴symlink，或許可以折衷？寄信問，取得狀態位址這樣。」（`T/11/11/kernel/01:59`）→ C-47 ①、N-28 的 `procs_state_path` 查詢信（`N28/07:9`）。
- 11-22 又提一次顧慮：「但我擔心symlink在跨機器，比如git push/pull的時候會出問題」（`T/11/22/工作區與stack-1122/01:11`）。

**新的**：11-24「我原本以為可以是/proc/daemon/procs/aaa軟連結到/proc/aaa」；11-25「並且或許可以是類似symlink」「如果是fuse的話…也不需要symlink」。他自己用了「或許」「類似」。

**後果**

- 落檔的實作（今天的 aos-daemon）要照新模型，`procs/<名>` 就是硬碟上的 symlink，`proc` 這個別名又是一條，再加核心給的 `cwd` 連結：整條入口三層都是連結，這就是「硬性依賴」。
- 不用 symlink 的落檔做法只剩 11-03 選的那種（表上記路徑、工具去解），代價是 `cd $AOS_ROOT/procs/x` 這種直接走路徑的用法在落檔版不成立，「大家自己去訪問」要靠工具。
- 當場回答的實作（FUSE）沒有這題。

**要他裁**：落檔版用不用 symlink。見第 8 節第 4 題。

### E　窗是 JSON、state 分兩扇、純文字帶 .txt　↔　ctl／status 純文字、沒副檔名、只給一個 status（定 3、4、5）

他 11-25 第 1 段自己說了「改成部分用json」，方向不用裁。被翻掉的條文：N-13、N-14「窗的內容是 JSON」；N-06「一個 JSON 物件＝一道指令」；11-05「唯一與json無關的，就是環境變數」。要補的洞三個：

1. **副檔名**：C-54「純文字帶 `.txt`」是他 10-23 逐條選的。`ctl`、`status` 要列成例外（比照 `.env`「照 dotenv 生態、不帶」）。
2. **兩扇窗併成一個檔，對落檔的實作是走回頭路**：11-09 拆 state_flux 的理由是「這種固定的寫檔開銷實在不好」。當場回答的實作沒有寫檔開銷，一個檔沒問題；落檔的 aos-loop 若把回音欄也寫進同一個 `status`，每被敲一下就重寫一次。
3. **落檔的實作「寫回來＝收到」不成立**（定 4 那列）。這條加上第 2 點，等於問：**落檔的實作算不算合格的 aos proc**。11-24 他說「不管你在硬碟,/tmp,fuse都可以」。見第 8 節第 5 題。

### F　一般 proc 只看得到 kernel　↔　大家自己從根走進去、活著直接連 socket（定 10、13）

**舊的**

- 11-11：「我的想法是一律寄到AOS_KERNEL，然後就如同linux一樣，user space的proc他只能看到kernel，除非有特殊需求，否則他看不到硬體，所以他可能就是只有AOS_KERNEL。」（`T/11/11/kernel/01:44`）；選項框：一般 proc 讀狀態＝「kernel 給一個狀態位址」，`AOS_DAEMON`「照傳，約定不用」（同檔 `:52,54`）。
- 11-21 放軟過一次：「讓aos proc訪問daemon當然可以，只是說可能有些東西可以被kernel攔截」「我覺得原則是只防走規矩的存取，不守規矩的就是要自己承擔風險。」（`T/11/21/kernel-攔截daemon存取-1121/README.md:38,42`）。

**新的**：每個 proc 手上有 `AOS_ROOT`，沿 `procs/<名>` 走得到任何一隻，直接讀它的 `status`、直接連它的 socket。kernel 只在對方掛了、要問信箱在哪的那一步才被問到。

**後果**：11-21 他要的是「有哪些東西可以讓aos kernel攔截」。新模型裡「走規矩的路」本身就不經過 kernel（kernel 是普通 aos proc，不在別人互連的路上），能攔的只剩退路那一步。要攔活著的那條，得靠擺法（把 socket、ctl 的權限只開給 kernel）或 Linux 權限。這題的細節在報告 14、15；這裡只擺出兩句話對不上。

**要他裁**：不急。等 14、15 回來再合成一題比較好（所以沒列進第 8 節）。

## 6. 「aos proc」的兩種定義

### 兩邊擺在一起

| | 今天 | 新模型 |
|---|---|---|
| 一句話 | 被某台 daemon 起的、記在它表上的一列 | 能支援這套介面的 Linux 行程 |
| 寫在哪 | 知識庫「proc: one running thing under a daemon」；`知/world.md:20`「A proc is always under exactly one daemon.」；C-80；程式（列表、認名字、停、寄信都先查表） | 11-24「任何linux proc，只要你能提供這些可存取的檔案佈局，如ctl/status等，那你就是aos proc，不管你在硬碟,/tmp,fuse都可以，哪怕是網路上也行」；11-25「能支援這套的就是aos proc」 |
| 誰說了算 | daemon（表上有沒有那一列） | proc 自己（擺不擺得出那幾個檔） |
| 怎麼變成 | 只有一條路：讓 daemon 起你 | 擺出介面就是；要讓別人用名字找到，再去某台 daemon 登記（「只登記、不起」還沒談，`新:134`） |
| 不在任何 daemon 底下的 | 「我們不管」；直接 `aos-exec` 跑的歸 Linux 管（`N28/09:5`） | 照定義仍是 aos proc，只是沒有名字、沒人顧 |
| 死了以後 | 出錯或被打掉的，表上那列留著（`stopped`＋原因）；自己退 0 的下表（`N28/05:8,9`） | 介面消失；它還算不算原來那隻 proc，沒談 |
| 生死、重起、份額、收 stderr | daemon 全包（它是父行程） | 只有 daemon 起的才有；自己登記的沒有 |
| kernel 准不准 | 設了 `AOS_KERNEL` 時，掛 proc 的請求先寄給 kernel，准了 daemon 才起（C-47，`K概/02:11`） | 自己登記的不經過任何 kernel（推論；報告 14） |

## 7. 邊緣狀況（對條文時看到的；都還沒有使用者的話）

- **「落檔的實作」在三條上都對不齊**：寫 ctl 回來不代表收到；死了檔還在、status 還寫著 running（N-17「被 SIGKILL 的程式…它的 state 會停在 `running` 之類」`窗/06-N-17/02:13`）；state_flux 併進 status 會回到 11-09 之前的寫檔開銷。而 aos-loop 正是落檔的實作。
- **PID 重用**：見 A 的表。舊的護欄是三欄一起對，新的連結只有一欄。
- **站在自己身體裡（`cwd` 這招）會動到相對路徑的基準**：N-59 寫明起跑後程式要 cd 去哪是它自己的事（`定義/03-N-59.md:10`），所以換地方站不算違規。但 N-28 好幾處寫「相對路徑從 daemon 的 cwd 算」「cwd＝daemon 的 cwd」（`N28/03:6`、`N28/02:14`）；daemon 一換站的地方，這些基準跟著變，要在換之前定住（推論）。
- **`settings` 記不記自己的 daemon 是誰**：`新:126` 把 `ctl who` 印的 parent 也歸進 settings。11-20 他說過：「所以aos-agent他還是不要記錄自己在哪個daemon下好了」（`T/11/18/default-stack-1118/05-使用者補充-1120.md:7`）；11-21「agent不該和daemon耦合」。
- **兩本帳**：proc 自報的用量跟 kernel 記的對不上時聽誰的（定 6）。全系統都是自報這件事，11-24 家機 main 的反饋已提過。
- **「身體」「settings」「status」三個新字都跟現有的字撞**（第 5 節）。
- **11-25 上午的「具名錨點」是在 stack 改義之前說的**（定 10 那列）。兩句都是他的話、同一天，字面上後一句讓前一句的錨變成活的路徑。
- **順手叫醒若打開**，跟 11-03「只有指令叫醒」、`stopped` 的列「只有指令叫起」怎麼分：建議只叫 `sleeping` 的（推論）。
