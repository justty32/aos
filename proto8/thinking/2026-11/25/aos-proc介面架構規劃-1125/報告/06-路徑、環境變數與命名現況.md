# 06 路徑、環境變數與命名的現況，對到 `AOS_ROOT`

← [架構規劃入口](../README.md)

三種話分開標：**原話**＝使用者說的（逐字）；**查到**＝附 `檔:行` 或實際輸出；**推論**＝我的推論，還沒有使用者的話。路徑從 repo 根 `/home/guanyu/repo/aos` 算；「活樹」指公司這台的 `~/aos-home/.stack`（只讀）。

## 1 結論

1. **真正算介面的 `AOS_*` 大約二十組**，其餘是某支程式內部用或測試用。新模型只要多一個 `AOS_ROOT`；`AOS_CLOCK`、`AOS_LLM_KERNEL` 今天就是從根的位置拼出來的（根定義的 `.env` 寫 `${AOS_STACK}/clock`、`${AOS_STACK}/procs/llm`），可以改成從 `AOS_ROOT` 推。
2. **「頭上最近的 daemon」當錨點不是新東西**：使用者 11-05 就說過同一句，表上的路徑已經照做；根的鐘登記表今天就用 `procs/repo-aos/procs/eca-aos/queue` 這種「名字那條路」當位址。
3. **今天「相對 daemon」的路，除了 `stack` 以外全是往外爬的**：兩張活表 16 列裡，`stack` 16 個都在 daemon 底下，`ws` 12 個、`def` 13 個、`exec` 9 個全部是 `../` 開頭。身體一換地方（tmpfs、`/proc`、FUSE），這些全斷。往外的要改用別的錨點。
4. **PID 不能放進會留很久的地方。** 實測這台開機以來平均每秒起 149 個行程，PID 大約每 6.5～7.8 小時繞一圈。舊的 `/proc/<舊PID>/cwd` 先是讀不到；號碼被別的行程拿走之後，會安靜地指到那個行程的資料夾。而 daemon 當掉時子項不會跟著死、新 daemon 會把它們接回，這些行程的環境變數一輩子不會更新。
5. **建議（推論）**：環境變數與落檔的東西只放名字——一個固定名字的入口，加上 `procs/<名>`；PID 只出現在連結指過去的目標裡，由活著的 daemon 維護。實測做得到：根重起後同一個值照樣通，unix socket 也連得上。
6. **`AOS_STACK` 今天身兼三職**：放狀態的夾、proc 的身分（信的寄件人、查自己叫什麼、鎖的持有人）、找信箱與歷史的起點。它改指「活的身體」之後，後兩職要拆出去。
7. **兩個今天在用的手法在新模型下會失靈**：把路徑「解開連結取真實位置」會把名字和 PID 都解掉；`..` 是核心照真實位置走的，走不回 daemon。「往上」只能靠環境變數、靠字串去尾，或在身體裡放一個往上的連結。
8. **經 `/proc/<PID>/cwd` 的路只在同一個 PID 命名空間、同一個帳號裡有效**：`aos-sandbox` 裡面看不到（實測）。

### 2.3 指示詞、相對與絕對路徑的規矩、三種夾

**指示詞**（N-45，`docs/NORMS/06-基礎設施-命令列與指示詞/01-N-45-path-env-ref.md:5-12`）：

- `{"$env": 名, "$path": 子路徑}`＝那個環境變數的值接上子路徑。讀的是**用到那一刻**的環境；`$path` 是字串拼接，寫絕對路徑也是接上去。
- `{"$ref": "檔#/指標"}`＝把那份 JSON 的那一格換進來。`#` 左邊是檔案系統（相對的從寫著它的那份檔所在的夾算），右邊是 JSON 裡面。
- 所以 `{"$env": "AOS_DAEMON", "$path": "procs/eca-aos"}` 本來就是一個「具名錨點」。

**表上的路徑**（N-28，`docs/NORMS/04-基礎設施-loop與daemon/02-N-28/04-手把與狀態窗.md:12-13`）：

| 掛的時候怎麼寫 | 表上怎麼存 | 每次起的時候 |
|---|---|---|
| 相對路徑，或程式自己組的絕對路徑 | 換算成**相對 daemon 的 stack**（`cpp/aos-daemon/src/child/child.cpp:366-390`） | 從現在的 daemon stack 拼回 |
| 人在命令列親手打的絕對路徑 | 相對那份照存，另外在 `as_written` 原樣記一份（`py/aos/daemon_ctl/entry.py:373-383`） | 那個絕對路徑在這台還在就用它，不在才退回相對那份（`cpp/aos-daemon/src/daemon/reconcile.cpp:195-218`） |
| 指示詞（`--ws-json`、`--stack-json`、`--path-json`） | `as_written` 記指示詞原形 | 照 **daemon 當下的環境**再解一次；解不開就留 `stopped` 並寫原因 |

原話：11-10「要用相對位置、絕對位置、環境變數指定都可」「add xxx 會換算(除了絕對路徑)」。

**相對路徑從哪裡算，今天不只一個起點**（查到；前五項是 11-25 打雜工那份報告的結論）：表上的從 daemon stack；hook 的處理程式從那份清單所在的夾；`notes_path` 從工作區；eca 小格的 `ws.txt`、`stack.txt` 從小格；回信位置 `reply_to` 從收信那個信箱的根（跨到不同頂層資料夾時退成絕對）；工具的參數從工作區（知識庫入口第 4 條規則）；`$ref` 從寫著它的檔。

**三種夾**（`knowledge/aos/world.md:7-14`）：

| 夾 | 是什麼 | 怎麼找 | 預設在哪 |
|---|---|---|---|
| 定義（def） | 原始碼；不准手改自己的 | 表上的 `def` 欄；跑的時候是 `AOS_CD` | 範本在 `$AOS_HOME/templates/…` |
| 工作區（ws） | 做事的地方、外部記憶；可以好幾隻共用 | `AOS_WS` | 掛的人給 |
| stack | 一隻跑著的 agent 的狀態：對話、信箱、佇列、自己改過的設定 | `AOS_STACK` | `<daemon stack>/procs/<名>/`；單獨跑 aos-exec 時是 `<工作區>/.stack/` |

- proc 的名字今天的規則只有一條：要能當資料夾名——不能空、不能有 `/` 或 `#`、不能 `.` 開頭（`cpp/aos-daemon/src/daemon/procs.cpp:12-13`）；沒有長度上限。
- 名字和 stack 的夾名可以不一樣：掛的時候 `-s` 可以指到別處；改名的做法是 rm 再用新名字、舊 stack 掛回，stack 夾不搬（`knowledge/aos/cli/agent.md:24`）。
- `.stack` 這個名字寫死在找路的程式裡的地方：aos-exec 的預設（`env.cpp:43`）、找 daemon 的退路（`table.py:22-23`）、認 agent 的退路（`common.py:244`）、guard 認「這是 stack」（`py/tools/agent/guard/scope.py:75`）。整個衝擊面看 [13 號報告](13-文件、測試與活樹的遷移衝擊.md)。

**甲、舊的 `/proc/<PID>/cwd` 會怎樣**（在自己的 PID 命名空間裡跑，才能故意讓號碼被拿走）：

```
1 根活著         /proc/2/cwd -> name: root-v1
2 根死了         FAILED No such file or directory
3 根重起(pid 3) FAILED No such file or directory
4 舊號碼被拿走   pid 2 -> name: unrelated
```

第 4 行是重點：拿著舊值的行程不會得到錯誤，會讀到別人的東西。

**乙、固定名字的入口**（一個不變的連結，指到根的 `/proc/<PID>/cwd`；根每次起來自己把它換掉）：

```
1 根第一代       gen1 | received by gen1
  同一個 socket 用真實路徑 (145 bytes) FAILED AF_UNIX path too long
2 根死了         FAILED No such file or directory
3 根重起、值沒變 gen2 | received by gen2
```

拿著這個值的行程不用做任何事，根重起後自動看到新的根；根死著的期間讀不到；socket 走這條路連得上。

```python
    body = os.path.join(base, "bodies", "x" * 60, tag); os.makedirs(body); r, w = os.pipe(); pid = os.fork()
    if pid == 0:
        os.chdir(body); open("status", "w").write("name: root\ngeneration: %s\n" % tag)

            c, _ = s.accept(); c.sendall(b"received by " + tag.encode()); c.close()
    os.read(r, 1); return pid
def status():
    try: return open(link + "/status").read().split()[-1]
    except OSError as e: return "FAILED " + e.strerror

    c = socket.socket(socket.AF_UNIX)
    try: c.connect(path); return c.recv(100).decode()
    except OSError as e: return "FAILED %s" % e
```

**丁、三個小確認**（`e4_alias_up_lock.py`）：

```
(1) via proc/ alias : name: agent | same folder as procs/ spelling: True
(2) walking up by ./daemon: agent -> sub-daemon -> root (stopped where there is no daemon entry)
(3) lock says alive : {'root': True, 'agent': True}
    after kill -9   : {'agent by real folder': False, 'agent by name route': False}
```

## 3 對新介面的含意

### 3.1 逐條對「定了的」（只講路徑、環境變數、命名這一面）

| 定了的 | 含意 |
|---|---|
| persist 在哪以 proc 自己說的為準 | 位置可以在任何地方，所以沒辦法用「相對 daemon」表示；別人只能走 `procs/<名>/persist`（活著時）或問 daemon。guard、清道夫這些今天靠「表上的 stack 欄」認地盤的工具，要改成向 daemon 問 persist 在哪（推論） |
| daemon 多一個放各 proc 的夾 | 就是今天的 `procs/<名>`。名字的規則今天只有「能當資料夾名」。今天名字和 stack 夾名可以不同；新模型下 `procs/<名>` 的名字就是表上的名字，這個落差會消失（推論）。另外，連結要指到「站在身體裡、回答 ctl 與 status 的那一支」，不一定是 daemon 自己起的那一支（第 4 節第 13 點） |
| kernel＝普通 aos proc | `AOS_KERNEL`（今天指信箱夾）與 `AOS_LLM_KERNEL`（今天指 stack）可以統一成「指到那個 proc 的目錄」（推論） |
| `proc` 與 `procs` 指同一處 | 同一隻有兩種寫法，拿字串比「是不是同一隻」會錯。寫進檔與環境變數的要定一種標準寫法（推論：`procs`，今天就叫這個） |
| 入口＝根 daemon 的 PID，`AOS_ROOT` | 見 3.5、3.6 |
| stack 的意思換了、`.stack` 沒有了 | 見 3.2、3.3。`aos-daemon-ctl` 與 `aos-agent` 的最後一條退路（找 `./.stack`、往上兩層）跟著失去依據 |
| 要留的放 `procs/<名>/persist` | 見 3.3 |
| 送訊息兩條路 | 今天「存起來的信箱路徑」都假設信箱永遠在：`AOS_NOTIFY_BOX`、鐘登記表的收信位置、信上的 `reply_to`。新模型下這些路穿過活的身體，對方一睡就斷。細節看 [20 號報告](20-送訊息兩條路的細節.md) |

### 3.2 每個現有變數的去留（整張表是推論）

| 變數 | 建議 | 新模型下 |
|---|---|---|
| `AOS_ROOT`（新） | 加 | 根的入口，整棵繼承，子 daemon 不改寫。值放什麼見第 5 節第 1 題 |
| `AOS_DAEMON` | 留，值換寫法 | 意思不變（頭上最近的那台）。值＝名字那條路：根的子項是 `$AOS_ROOT`，再下一層是 `$AOS_ROOT/procs/<名>`。指到的東西從「硬碟上一直在的夾」變成「活的身體」 |
| `AOS_STACK` | 改意思 | 自己的身體。今天兼的另外兩職要拆（3.3） |
| `AOS_LLM_KERNEL` | 留，可由 `AOS_ROOT` 推 | 同一棵樹裡＝`$AOS_ROOT/procs/llm`；llm kernel 在別棵樹時照舊由人設 |
| `AOS_CLOCK` | 留，可由 `AOS_ROOT` 推 | `$AOS_ROOT/clock`。鐘檔在根的身體裡的話，根死了就讀不到；今天根死了檔還在、數字不動，讀的人分不出「鐘停了」和「根死了」。等待怎麼做看 [11 號報告](11-閒置成本、時鐘與等待.md) |
| `AOS_KERNEL` | 留，值的意思可統一 | 指到 kernel 那個 proc 的目錄；「沒設就找 daemon」的退路照舊 |
| `AOS_WS`、`AOS_HOME`、`AOS_ENTRY`、`AOS_CF`、`AOS_CO`、`AOS_CLOCK_INTERVAL`、`AOS_AGENT`、`AOS_FORK_DEPTH`、`AOS_CLI_DEF` | 留，不變 | 跟 proc 介面無關 |
| `AOS_CD` | 留，變重要 | proc 若改站在自己的身體裡，定義裡照「我站在定義夾」寫的相對路徑要改成從 `AOS_CD` 算（見第 4 節第 2 點） |
| `AOS_STACK_IN_CALLER` | 留 | 工具小格還叫不叫 stack 沒談到（第 4 節第 8 點） |
| `AOS_PARENT_STACK` | 留，改意思 | 父的 proc 目錄（名字那條路）。今天存檔的形式本來就是 `{"$env":"AOS_DAEMON","$path":"procs/<父名>"}`，改動小 |
| `AOS_NOTIFY_BOX` | 改意思或消失 | 一條寫死的信箱路徑只涵蓋「寄信」那條路。可以改成「收通知的是誰」，送的時候照兩條路走 |
| `AOS_LINUX_USER_STACK` | 改名或改意思 | 人不是 proc，沒有活的身體；這個「stack」其實只是人的信箱所在，照新定義名不副實 |
| `AOS_WRITE_ALLOW`、`AOS_WRITE_DENY`、`AOS_GUARD_CFG` | 留 | guard 判斷「這是別人的 stack」的依據要連 persist 一起算 |
| `AOS_LOOP_*` | 留在 aos-loop 這個「普通實作」裡 | 不屬於介面 |
| `AOS_USER_ZONE`、`AOS_USER_TOOL`、`AOS_FEEDBACK`、`AOS_VIEW_HOME`、`AOS_JSON_MAX_*` | 不受影響 | — |

### 3.3 `AOS_STACK` 改指身體之後，今天靠它找的東西改靠什麼找

今天 `AOS_STACK` 同時回答三個問題（查到）：

| 問題 | 今天怎麼答 | 出處 |
|---|---|---|
| 我的狀態放哪 | `$AOS_STACK/history.jsonl`、`queue/`、`mailbox/`、`letters.json`、自己改過的 `tools.json`、`llm.json`、`system.txt`、`hookeds.json`、`tools/<名>/` | `knowledge/aos/me.md` 的 What is in your stack 節 |
| 我是誰 | 信箱的信與問腦的信，寄件人＝`$AOS_STACK` 這個字串；鎖的持有人＝`$AOS_WS`，沒有才是 `$AOS_STACK`；名字＝拿它去表上反查 | `py/aos/apps/mailbox/__init__.py:151-153`、`cpp/aos-llm/src/send/send.cpp:116,123`、`cpp/aos-util/src/proc.cpp:80-125`、`ctl/who.py:31-48` |
| 別人怎麼找我的信箱 | 表上那一列的 `stack` 欄加 `/mailbox` | `py/aos/apps/mailbox/__init__.py:325-339` |

新模型下三個問題要分開答（推論）：

1. **自己要留的東西**（history、信箱、佇列、自己改過的設定）：從自己的身體走 `persist`，也就是 `$AOS_STACK/persist/history.jsonl` 這樣。這就是使用者推薦的標準位置 `procs/<名>/persist`，從自己這頭看。落檔的實作可以讓 `persist` 指回自己，檔一個都不用搬。
2. **活的東西**（ctl、status、socket、鎖）：直接在 `$AOS_STACK` 底下。
3. **身分**：不能再用 stack 的路徑。身體的位置在「直接用 Linux 這套」時帶 PID，每次起來都不同；信的寄件人、父子登記、問腦的帳都會存起來，存了就過期。建議用名字那條路（從根算的 `procs/<名>/procs/<名>`）。它跨重起不變，鐘登記表今天已經這樣記。
4. **別人找我的信箱**：我活著時是 `procs/<我>/persist/mailbox`；我死了這條路走不到，照「定了的」去問我的 daemon。
5. **自己的身體不能靠上層活著才走得到。** 如果把 `AOS_STACK` 的值寫成名字那條路（`$AOS_DAEMON/procs/<我>`），中間那台 daemon 一當掉，我明明活著卻走不到自己的檔。今天 daemon 當掉，底下的 agent 照跑（`cpp/aos-exec/docs/03-環境變數.md:49`）。所以「身體在哪」和「我叫什麼」得是兩樣東西，一個變數裝不下；怎麼交給 proc 見第 5 節第 3、4 題。

### 3.4 「具名錨點」怎麼落在這套上

原話（11-25）：「我希望是用具名錨點，一個最重要最根本的錨點就是離自己最近的頭上的那個daemon的stack。沒有的話那你就是root daemon，你是特殊存在。」

**現況已經有的**（查到）：`{"$env": "AOS_DAEMON", "$path": …}` 就是這個錨點，N-28 寫的基準點也是同一句。每台 daemon 的狀態檔記著「上面是誰」，根那格是空的。

**「頭上最近的 daemon」往上走哪條路**（推論，三條可以並存）：

| 路 | 怎麼走 | 代價 |
|---|---|---|
| 環境變數 | daemon 起子項時給 `AOS_DAEMON`（今天的做法） | 只有它起的行程拿得到；值會留在行程裡很久（3.6） |
| 字串去尾 | 名字那條路去掉最後的 `/procs/<名>` | 只能在字串上算；交給系統走 `..` 會走到身體真正所在的上一層（實測丙） |
| 身體裡一個往上的連結 | 每個 proc 的目錄裡放 `daemon`，指到上面那台；根沒有這一項 | 介面多一個名字；好處是外面的人 `cd` 進任何一個 proc 都能一路走到根（實測丁），今天做不到 |

**往外的路要換錨點**（推論，依據是 2.5 的數字與 11-05 那段註解）：

- 今天 `ws`、`def`、`exec` 存成「從 daemon stack 往外爬的 `../..`」。這靠的是 stack 在硬碟上一個固定的位置。
- 新模型的 `AOS_DAEMON` 天生穿過連結。11-05 的解法是把基準點解成真實位置，那樣會把名字解掉（實測丙）。兩者不能兼得。
- 所以 `AOS_DAEMON` 這個錨點只拿來指 daemon **底下**的東西，不帶 `..`。往外的：範本與 lib 用 `AOS_HOME`（今天已經這樣）；工作區裡的用 `AOS_WS`；其餘照人寫的絕對路徑或他自己的環境變數（`as_written` 已經有這個口）。
- 樹裡跨子樹的（例如根底下的 llm kernel）用 `AOS_ROOT`。

**根是特殊存在，今天已經特殊在哪**（查到）：

- 上面沒有 daemon：狀態檔的 `daemon` 欄是 `null`；程式的判法是「繼承到的 `AOS_DAEMON` 沒設，或解開後就是自己」（`daemon.cpp:193-206`）。
- 它的環境來自人的殼，所以有「一個變數兩個意思」的坑：`AOS_DAEMON` 對人是「對哪台說話」，對正要起來的 daemon 是「我的上司」。使用者 11-10 的裁定：「喔沒關係，root這東西本來使用者就要多注意一點。」起根那一行要 `env -u AOS_DAEMON …`。**`AOS_ROOT` 會有一模一樣的坑**：殼裡 export 著舊的 `AOS_ROOT` 去起一台新的根，它會以為自己在別人底下。
- 鐘只在根（`cpp/aos-daemon/docs/10-根daemon.md` 的「時鐘只放在根」）。
- 跟這台機器綁在一起的東西歸它，不跟著搬（N-67 ⑤）。
- 新模型再加一條：它是唯一需要「從外面找得到」的。

### 3.5 外面的殼沒有任何 `AOS_*` 時怎麼找到根

今天不用找：殼設定檔寫死 `export AOS_DAEMON="$HOME/aos-home/.stack"`，那是硬碟上一個不變的路徑。入口改成 PID 之後，殼設定檔寫不出來。選項（推論）：

| 選項 | 怎麼做 | 好處 | 代價 |
|---|---|---|---|
| a 固定名字的連結 | 根起來時把一個固定位置的連結指到自己的 `/proc/<PID>/cwd`（實測乙） | 值永遠不變，殼設定檔照寫；根死了讀不到；socket 路徑短 | 根當掉又沒重起時，連結還指著舊號碼，過幾小時可能指到別的行程，要另外驗（見下）；一台好幾個根時要分名字 |
| b pid 檔 | 根把 PID 寫進一個檔，要用的人自己組 `/proc/<PID>/cwd` | 最簡單 | 每個讀的人都要自己組、自己驗號碼有沒有被拿走；組出來的值放進環境變數又是會過期的值 |
| c `/run/user/<uid>/` 底下 | 同 a，位置放在登入帳號的執行期目錄 | 只有自己進得去、關機就清、路徑短；這台已經在那裡放畫面的 socket | 沒有 systemd 登入管理的環境沒有這個目錄；daemon 與人的殼不一定都有 `XDG_RUNTIME_DIR`（2.5 那個坑） |
| d `~/.aos/` 底下 | 同 a，位置放家目錄 | 每台都有；`~/.aos/` 已經是放 aos 自己東西的地方 | 重開機後留著一個指不到的連結；家目錄若是幾台共用的網路磁碟會指錯台 |
| e 起根的人自己指定 | 起根時說「把入口公布在哪」，沒說就不公布 | 暫存樹、測試樹不會蓋掉主樹的入口 | 多一個要記的設定 |
| f 掃 `/proc` 找 | — | 不用任何設定 | 條文明講不准（2.2） |

- a 到 e 不互斥：e 決定「誰公布、公布在哪」，a／c／d 是位置的候選。
- **多個根是常態**：今天每條施工線的暫存樹都是一個根（規矩卡硬規則第 3 條）。只留一個寫死的位置，測試樹一起來就把主樹的入口蓋掉。
- **入口要能驗「是不是我要找的那一個」**，而且不靠 PID：看對方 `status` 裡的名字，加上它握在自己身體上的鎖（實測丁 (3)）。隨便一個拿到舊號碼的行程不會握那把鎖。

### 3.6 PID 會變：哪些地方會留著舊值、怎麼辦

子項拿到 `AOS_ROOT=/proc/12321/cwd` 之後，根一重起這個值就失效。會留著舊值的（查到的是「這些地方今天會把環境裡的值留很久或存下來」；「放 PID 會過期」是推論）：

| 哪裡 | 為什麼留著 | 出處 |
|---|---|---|
| daemon 當掉後被接回的行程 | daemon 被 `kill -9`、OOM 時子項不跟著死；新 daemon 用「pid＋起動時刻＋開機編號」把它們接回。行程的環境改不了 | `cpp/aos-daemon/docs/08-當機復原與已知限制.md`、`cpp/aos-daemon/src/daemon/adopt.cpp:56-91` |
| 那些行程之後起的每一支 | aos-loop 每一圈起的程式都抄它的環境 | 2.1 |
| 沒死的子 daemon 之後掛的每一隻 | `as_written` 的指示詞照 **daemon 當下的環境**解 | `reconcile.cpp:164-171` |
| eca 的畫面（tmux、Claude Code、它帶的 MCP） | 畫面是從開畫面那個人的殼起的，不是 daemon 的子項；agent 停了之後預設 600 秒才關畫面，期間再起來就取消，被 kill 的根本不排關畫面。所以樹重起時畫面常常還在 | `cli_mcp.py:186-189`、`knowledge/aos/cli/eca.md` 的 Delayed screen closure 節 |
| eca 小格的 `claude/env.json`、`claude/mcp.json` | 每一圈把環境裡的值寫進檔 | `cli_mcp.py:193-200, 262-288` |
| hook 的 `on_clock.json`、`event.json` | 記鐘檔與 stack 的絕對路徑 | `py/aos/agentlib/hook_clock.py` 的 `_clock_file`、`py/aos/hook_run.py:78-87` |
| 子 daemon 的狀態檔 `daemon` 欄 | 照字面記繼承到的值 | `daemon.cpp:193-195` |
| 小格 `exec.json` 的 `envs` | 掛的時候 `--envs` 給的值照字面存 | 2.5 |
| 人的殼、VS Code、systemd 的服務檔 | 起動那一刻的值 | `03-換機.md:60, 175` |
| 信 | 寄件人是 stack 路徑；`reply_to` 跨頂層資料夾時是絕對路徑 | 3.3 |

- 整棵樹照正常程序停再起（`shutdown`）的話，底下的行程都是新起的，會拿到新值。出問題的是「根當掉」這一種，以及不歸 daemon 管的那幾樣（畫面、殼、存下來的檔）。
- N-67 ⑦ 本來就規定「環境變數的值不落檔」；上表中間那幾列是已知還沒修的例外。值裡有 PID 的話，這些例外從「搬家時會錯」變成「根重起就錯」。
- 新 daemon 接回行程時，會去讀那支行程環境裡的 `AOS_STACK` 與 `AOS_DAEMON`，解成真實位置，比對是不是自己這棵樹的（`adopt.cpp:56-91`）。這兩個值若帶 PID，根重起後不是解不開就是解到別處，這段比對要重看（推論）。

怎麼辦（推論）：

| 做法 | 說明 | 代價 |
|---|---|---|
| A 值裡不放 PID | `AOS_ROOT` 放固定名字的入口；從它拼出來的 `AOS_DAEMON` 等也就沒有 PID | 要多一個固定入口（3.5）。上表每一列都不用改 |
| B 放 PID，讀不到就重找 | 每支程式用之前先驗、失效就重找 | 每個讀的人都要會；號碼被拿走時不是讀不到而是讀錯（實測甲第 4 行），還得驗名字；而且重找一樣需要一個固定入口 |
| C 根一死整棵跟著死 | 子項盯著根，根沒了自己退 | 不會有活著的行程帶舊值；但今天「daemon 當掉、agent 照跑、新 daemon 接回」的行為就沒了 |
| D 根重起後通知接回的子項換值 | 寫它們的 ctl | 行程自己的環境改不了，只能影響它之後起的；管不到畫面、殼、存下來的檔 |

我推薦 A。它沒有推翻「入口是根 daemon 的 PID」：PID 還是入口，只是放在連結指過去的那一頭，不放在會被抄來抄去的那一頭。

### 3.7 跨機器時名字那條路怎麼維持

查到的現況：

- 兩台開發機各有各的根（都在 `~/aos-home`），stack 不跟機器走；兩棵樹之間沒有連線，跨機器靠 git 與 `wf/inbox/` 的信。
- 定義靠 `AOS_HOME` 這種具名錨點在兩台都指得到。現有的規矩是「名字兩台要一樣、位址各台自己解」（例：llm 端點的名字，`03-換機.md:31`）。
- 兩台的家目錄不同（`/home/guanyu`、`/home/lorkhan`），凡是存絕對路徑的都換不了台。
- 同一棵樹裡今天就有兩隻都叫 `main`（mine_arena、mine_paper 底下各一隻），通知只顯示「from main」，要看寄件人的路徑才分得出（`wf/ws/eca-aos/notes.md:137`）。短名字不夠當身分。

推論：

1. **名字那條路本身跟機器無關**：`procs/repo-aos/procs/eca-aos` 在兩台是同一串字。跟機器有關的只有「從哪個根開始」。所以進 git、進信的參照一律寫成「錨點＋名字路」，不寫 PID、不寫家目錄。
2. **`procs/<名>` 這一格是什麼，可以每格不同**：本機的是指到 `/proc/<PID>/cwd` 的連結；遠端的可以是掛進來的遠端目錄，或一個本機的代理 proc。這跟「daemon＝Linux 與 aos 之間的橋」同一個形狀，只是橋的另一頭是另一台機器。
3. **unix socket 過不了機器**（憑記憶：socket 檔在網路檔案系統上只是一個名字，連的人和聽的人要在同一個核心裡）。所以「活著走 socket」到了遠端要嘛經代理，要嘛那一格另外說明怎麼連；「掛了走寄信」需要一個兩邊都寫得到的信箱。
4. **遠端的根叫什麼，由掛它的人取**：今天 proc 的名字就是掛的人給的，proc 自己不知道；遠端的根掛進本機的 `procs/<名>` 時，名字由本機決定，不需要一個全世界統一的命名機關。Plan 9 把別台的東西掛在 `/n/<名>` 是同一個做法（憑記憶，細節看 [07 號報告](07-9P與Plan9原樣.md)）。

## 4 邊緣狀況

1. **中間那台 daemon 當掉，底下活著的 proc 從名字那條路走不到**（推論，依據實測丙的形狀）。今天走得到，因為都是硬碟上的普通資料夾。影響：寄信給它、看它的 status 都要等 daemon 回來，或手上要另有它身體的真實位置。
2. **「站在自己的身體裡」撞上「站在定義夾」**。N-59 規定資料夾程式起跑時站在自己的定義夾，定義裡的相對路徑靠這個（例：agent-fsm 的格可以寫 `["python3", "idle.py"]`）。要用 `/proc/<PID>/cwd` 當入口，那支長命的行程得站在身體裡。可以只讓長命的那支換地方、每圈起的短命程式照舊；或定義一律改用 `AOS_CD`。沒實測。細節看 [01](01-aos-loop現況.md)、[03 號報告](03-agent-fsm身體與stack現況.md)。
3. **沙箱裡的工具進不了樹**（實測戊）。`aos-sandbox` 要在外面先把名字那條路解成真實位置再綁進去，裡面的環境變數也要換成綁進去的位置。預設放 `/tmp` 的 persist 在沙箱裡也看不到（它給裡面一個空的 `/tmp`）。
4. **不同帳號走不進 `/proc/<PID>/cwd`**（`9p-proc-1125.md` 已記）。換成子帳號跑的 proc 要另外確認，看 [08](08-Linux機制實測.md)、[15 號報告](15-權限過去的規劃對照新模型.md)。
5. **名字那條路也可能超過 108 bytes**（推論）。每一層多 `/procs/<名>`；分身的名字是 `f-<父名前 32 字>-<毫秒>-<4 位>`（`py/tools/agent/fork/_entry:11`），一層就 60 bytes 上下。例：`~/.aos/root/procs/repo-aos/procs/<分身名>/sock` 在這台約 100 bytes，再深一層或名字再長一點就超過。連 socket 之前要先把最後一格讀成短的 `/proc/<PID>/cwd` 再連，而且那個短路徑不能存起來。
6. **固定入口本身也會指著舊號碼**：根當掉又沒人重起時，它還指著舊的 `/proc/<PID>/cwd`，跟實測甲同一個問題。靠 3.5 最後一點的「驗名字與鎖」，或讓根由 systemd 這類自動重起（重起時會把入口換掉）。
7. **daemon 維護 `procs/<名>` 連結的時機**（推論）：自己的子項死了，在「收屍」之前那個 PID 不會被別人拿走，所以先拿掉連結再收屍就沒有空窗。接回來的行程不是自己的子項，沒有這層保護，只能靠「pid＋起動時刻」輪流看，會有一小段空窗。
8. **「stack」今天有兩個用法**：proc 的 stack，以及「叫別人時給它的小格」（工具小格 `<stack>/tools/<名>/`，N-50、C-70）。11-25 的新定義講的是前一個。工具不是 proc、沒有活的身體，它的小格放的又是要留的東西（例如待辦清單），照新說法比較像 persist 的一部分。後一個用法要不要跟著改，沒談到。
9. **改名**：今天改名不搬 stack 夾。新模型下預設的 persist 位置「用名字算」，改名之後新名字算出來的是另一個位置，要有人把舊的接過去。
10. **`AOS_STACK` 當殼設定檔的開關**：人的殼設定檔用 `[[ -z $AOS_STACK ]]` 判斷「是不是在 agent 的殼裡」。只要 agent 的殼裡還有這個變數就沒事；哪天它改名或拿掉，暫存樹裡的 agent 會被殼設定檔改成指向真的樹。
11. **`as_written` 的絕對路徑「在就用」**：今天舊位置還在就優先用舊位置（11-22 規劃的邊緣狀況 12 記過這會默默接回舊樹）。新模型下若有人把 `/proc/<PID>/…` 這種字串打進去，它會被原樣存下來，下次起的時候「在就用」，可能指到別的行程。帶 `/proc/` 的絕對路徑應該擋掉、不存。
12. **`realpath` 的習慣**：今天比「是不是同一個夾」多半先取真實位置（`common.py:119-121`、`py/aos/daemon_table.py:83`）。對活的 proc 這樣比沒問題；對死的，名字那條路解不開，只能比字串，所以需要一個標準寫法（3.1 `proc`／`procs` 那一列）。
13. **一列不只一支行程，表上記的 pid 是最外面那支**（查到）。根的表上 `repo-aos` 那列記的是 pid 2228，實際是三支疊著：2228（根 fork 出來的監工，站在小格 `.stack/procs/repo-aos`）→ 2233（`aos-exec -- 定義夾`，站在定義夾）→ 2239（真正的 daemon，站在定義夾）。`procs/<名>` 的連結若照表上的 pid 指，會指到監工、不是 daemon 本尊。所以要嘛本尊起來後自己把 PID 登記回去（跟「讀得到 `settings`／`status` 的那一刻起才算 aos proc」是同一步），要嘛三支都站在同一個身體裡（推論）。

## 5 要問使用者的

1. **`AOS_ROOT` 的值放什麼？**
   - a 一個固定名字的入口（一個連結，目標才是根的 `/proc/<PID>/cwd`）
   - b 直接放 `/proc/<PID>/cwd`，每支程式用之前自己驗、失效了重找
   - c 兩個都給：`AOS_ROOT` 放固定名字，PID 另外放一個檔給想直接用的人
   - 推薦 a。理由：值永遠不過期，被接回的行程、畫面、殼、存下來的檔都不用改；這台 PID 大約七小時繞一圈，b 會讀到別人的東西。
2. **固定入口放哪、一台好幾個根怎麼分？**
   - a 起根的人指定公布在哪，沒指定就不公布；主樹的慣例位置是 `~/.aos/root`
   - b 只有一個寫死的位置（`~/.aos/root`）
   - c `/run/user/<uid>/aos/<根的名字>`，每個根一個名字
   - 推薦 a。理由：今天每條施工線的暫存樹都是一個根，寫死一個位置會互相蓋。
3. **一個 proc 的身分用哪個字串？**（信的寄件人、父子登記、問腦的帳、鎖是誰的）
   - a 從根算的名字那條路（`procs/repo-aos/procs/eca-aos`）
   - b 它 persist 的位置
   - c 照舊用身體的位置
   - 推薦 a。理由：重起、換實作（硬碟、tmpfs、FUSE）、換機器都不變；根的鐘登記表今天已經這樣記。
4. **daemon 起 proc 時要交給它三樣東西（身體在哪、預設的 persist 在哪、它叫什麼），走什麼管道？**
   - a 全走環境變數（`AOS_STACK` 給身體，另外新增兩個）
   - b 環境變數只給身體；另外兩樣 daemon 先擺在身體裡（一個 `persist` 連結、`settings` 或 `status` 裡的名字），proc 不滿意自己換掉再登記
   - c proc 起來之後自己去問 daemon
   - 推薦 b。理由：不加環境變數（11-05 談鐘的間隔時的原話：「我實在很不想再添加環境變數，但這太香了」），而且別人看這個 proc 也是從同一個地方看到。
5. **proc 的目錄裡要不要有一個「往上」的入口？**（例如叫 `daemon`，指到頭上那台；根沒有這一項）
   - a 要，取代環境變數
   - b 不要，照舊只靠 `AOS_DAEMON`
   - c 兩個都有：環境變數給它自己起的程式用，連結給外面走進來的人用
   - 推薦 c。理由：這樣「頭上最近的 daemon」和「根是沒有上一層的那個」變成走檔案就看得到的事實；外面的人 `cd` 進任何一個 proc 都找得到它的 daemon 與根，今天只能靠「往上兩層」猜。

## 6 沒查到／沒把握的

- **怎麼查的**：為了看行程拿到什麼，讀了 8 支 `aos-daemon`／`aos-loop` 行程的 `/proc/<pid>/environ`，只印 `AOS_` 開頭的名字與值；其中一支（pid 2232）是根替 mine_arena 那一列留著的監工行程，值跟根的一樣。別棵樹的 stack 與表沒讀。表的統計只算根與 `repo-aos` 兩張。
- PID 消耗速度只量了今天這台，取樣時有二十隻規劃子 agent 在跑；家機沒量。平常的速度跟「閒置輪詢」那條線有關，降下來之後繞一圈的時間會變長，但問題的性質不變。
- 「eca 的畫面在整棵樹重起後還留著舊環境」是照知識庫那一節與程式寫的，沒實際重起樹驗。
- 「unix socket 過不了網路檔案系統」「符號連結一條路徑最多跟 40 層」是憑記憶的 Linux 知識，沒實測。
- 直接讀 `AOS_HOME` 的 Python 沒逐支列；N-63 的表寫「沒有程式直接讀它」，跟現況對不上。
- aos-exec「走進定義夾」與「proc 站在身體裡」怎麼並存，只指出衝突，沒做原型。
- 子帳號（每支一個 user namespace）的 proc 讀不讀得到別人的 `/proc/<PID>/cwd`，沒測，留給 08 號。
- 3.2 的去留表、3.3 的拆法、3.5～3.7 的選項都是推論，沒有使用者的話。
