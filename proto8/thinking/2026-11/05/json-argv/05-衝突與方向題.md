## 方向題（原則推不出；推薦放第一）

### Q1 給人用的程式（aos-post、aos-daemon-ctl、aos-agent…）要不要也改成「一份 JSON 定義生旗標表＋`--help`」？

背景：03 讓純 aos 函數的旗標、help、tool schema 同源；給人用的程式現在旗標表寫在程式碼裡（C++ `parse_cli` 表、Python `aos_flags.parse` 表）、help 手寫英文。
- **不做，維持程式碼裡的表 (Recommended)**：給人用的介面要人體工學（子命令、位置參數、散文 help），JSON Schema 表達不了；它們也不需要 tool schema（agent 走 `bash` 叫、看 `--help`）。後果：兩種程式兩種寫法，但各自只有一份定義。
- 做：`cmd/<名>/_cli.json` 生 C++／Python 表與 help。後果：多一個生成步驤、C++ 要 codegen；好處只有「JSON 預設介質」的一致感。
- 折衷：只給 Python 的 `cmd/` 做。後果：C++／Python 不一致，違「統一成單一介面」。

### Q2 一個工具資料夾要不要有多個 method？（`memory` 的 add／get／ls 之類）

背景：使用者「一串 argv 組起來＝一個 method」；C-55／C-71 資料夾＝table、入口只佔一層；現況 lib 工具多用 stdin 鍵 `op`／`action` 分支（01 盤點）。三種寫法：
- **子資料夾＝子 method (Recommended)**：`memory/add/_entry`、`memory/get/_entry`，各有自己的 `_tooldef.json`；`aos-exec memory/add`；登記成 tool 時名字 `memory_add`（底線）。後果：每個 method 一份 schema、腦看到的是扁平工具清單（OpenAI 本來就扁平）；資料夾變多。
- stdin 鍵 `op` 分支（現況）：一份 schema 用 `enum` 列 op，其他鍵全選填。後果：schema 鬆、型別檢查弱、`--help` 一長串；但檔少。
- 工具內子命令 `aos-exec memory add`：argv 進工具再解。後果：工具要自己做子命令解析，跟「純 aos 函數少用旗標」背道。

### Q3 旗標跟 stdin 同鍵時：蓋掉、還是報錯？

- **旗標蓋 stdin、不報錯 (Recommended)**：同 N-58「旗標 ＞ 環境 ＞ `.env`」、同 argparse。後果：人可以 `cat base.json | aos-exec tool --limit 5` 覆蓋一格。
- 報 `ArgumentsBad`：兩邊都給就是寫錯。後果：安全但失去「管線＋覆蓋」用法。
（這題原則其實推得出，列出來只因使用者點名問；03 已照推薦寫。）

## fable 代定（可翻案；不帶給使用者）

- 巢狀物件旗標收整段 JSON 字串；陣列靠重複旗標；不做短旗標、nargs、點路徑。
- `positional` 預設不宣告；宣告也只建議一個（`read PATH` 那種）。
- 型別檢查只做 `type`／`required`／`enum`；`type` 陣列取第一個非 `null`。
- `--help` 版面見 03；`errors:` 行來自 `_tooldef.json` 選填 `errors`。
- `aos-tools ls --json`／aos-mcp 只取 `description`、`parameters` 給模型。
- C++ 現在不做 schema 映射；需要時加 `aos::argv_to_json`，規則抄 03。
