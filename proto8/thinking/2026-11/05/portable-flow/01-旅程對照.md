## 環境變數清點（步③能砍到幾個）

今天視窗二要 export 的：`PATH`（步 0 解掉後不必每殼設）、`AOS_DAEMON`（aos-daemon-ctl／aos-agent 找 daemon；試驗場 `env.sh` 設成 `$PG/ws/.stack`）、`AOS_KERNEL`（agent-fsm 問腦寄到哪；`env.sh` 設成 `$AOS_DAEMON/procs/llm/mailbox`）、`AOS_AGENT`（選用，省 `--target`）。

- **daemon 底下的 proc 一個都不必設**：daemon 起子項時給 `AOS_WS`／`AOS_STACK`／`AOS_DAEMON`（N-64 ④），`AOS_KERNEL` 是繼承 daemon 自己的環境——所以 **`AOS_KERNEL` 其實可以由 daemon 定義（daemon.json 的 `envs`／`.env`）給子項，不必人設**；但 daemon 的 `.env` 寫的是絕對路徑就又綁死位置，要寫成 `{"$env": "AOS_STACK", "$path": "procs/llm/mailbox"}`（aos-exec 的 `.env` JSON key 吃指示詞，N-59）。
- **人在視窗二只剩 `AOS_DAEMON` 一個**（要跟 daemon 說話總得知道它在哪）；能不能也砍掉＝[05 題 4](05-衝突與方向題.md)（預設 `./.stack` 違 N-63「不猜位置」）。
- 結論：步③最少 **1 個**（`AOS_DAEMON`），而且值隨 ws 走（`$PWD/.stack`），可以寫在 `using-aos-agent.sh` 之類的殼檔裡一行帶過。

## 「沿用」的邊緣（步②；代定，可翻案）

1. **怎麼知道已有 daemon 在跑**：看它 stack 的 `state.json`（`pid`＋`started_at_ticks`＋`boot_id` 對 /proc，N-17 確定法，aos-daemon-ctl `ls` 現成）；不看檔案新不新。
2. **複製過來的 stack 裡是睡著的 daemon**：pid 對不上（別台的 boot_id）＝沒在跑＝「起」（照舊 adopt、wake）；不是沿用。
3. **沿用時新 proc 的基準點**＝那個 daemon（它給的 `AOS_DAEMON`），自然成立，不用多設計。
4. **同一個 ws 兩個 daemon**：步 2 代定擋掉（`DaemonRunning`）；要故意兩個就給不同 `--stack`，照舊自擔。
