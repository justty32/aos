# 兩種模式怎麼落到現成的東西上（fable 照原則定的細節，可翻案）

原則：不改 aos-daemon 的介面（N-28、N-54）、不加環境變數（C-69）、「掛 proc」只有一條路——**往 daemon 的 ctl 信箱寄一封 `procs_added`／`procs_removed`／`procs_stopped`／`procs_started` 的信**（N-16 的信，body 認的 key 照 [aos-daemon docs 05](../../../../impls/aos-daemon/docs/05-信箱.md)）；aos-daemon-ctl、aos-agent 都只是這封信的語法糖。所以「kernel」在 aos 裡就是：**誰在寄這封信、寄之前有沒有判斷**。

## 0 模式 0：daemon 本身（今天）

- 誰能寄誰就掛（N-54 末「誰能寄：純靠 Linux 檔案權限」）。試驗場今天就是這樣：人用 `aos-agent add`、llm kernel 之後也會自己寄（[03](03-問腦改掛daemon.md)）。
- 這就是使用者說的「最基礎的 kernel 實作（來者不拒）」。不改名、不加字。

## 1 模式 1：繼承式——daemon 自己的身體當判官

「收到信後跑一個函數決定是否要掛…把函數覆蓋掉，末尾呼叫 base class 函數」。落法（**零改 aos-daemon**）：

- **覆寫＝daemon.json 給自己一個 `exec` 身體**（N-28：daemon 自己每次串行跑一次的身體，選填、現成）。身體＝一個 aos 函數（資料夾程式）`judge/`：每拍 `aos-post take-all $AOS_STACK/requests`（daemon **對外的收件箱**，自己開、名字代定 `requests/`），逐封判。
- **base 呼叫＝轉寄進 daemon 自己的 ctl 信箱**：判「掛」的那封，body 原樣（或改寫過）`aos-post send --reply-to <原信的 reply_to> $AOS_STACK/procs_ctl_mailbox`，daemon 下一圈照 N-28 套（它分不出這封是誰寄的，也不該分，C-52）。回信 `{"applied": true}` 由 base 直接寄給原寄件人（`reply_to` 轉嫁），判官不轉手。
- **判「不掛」**：`aos-post done --reply '{"applied": false, "error": {"code": "…", "msg": "…"}}'` 回給原寄件人、收掉。
- **判官的介面**（寫在 `judge/` 的 README）：讀 `requests/`；政策寫在定義裡的 `judge.json`（例：名單白名單、同時最多幾個 running——從 `$AOS_DAEMON/procs_state.json` 數、時間窗）；不認的 body key 原樣轉寄（C-48）。它只做判斷＋轉寄，**不自己跑任何東西**（第三句）。
- **為什麼叫「合一」**：身體在 daemon 的行程裡、跟名單同一圈串行跑；「末尾呼叫 base」就是那一寄。限制：daemon 的 `exec` 是阻塞的（N-28「跑法跟 loop 一樣，阻塞到它結束」），**判官要快**——要問腦才能判的，用模式 2。
- **身體要找得到自己的 daemon**：今天 daemon 只給子項設 `AOS_DAEMON`、不給自己的身體。代定（一行改動、可翻案）：**daemon 跑身體那次也設 `AOS_DAEMON`＝自己的 stack**（身體是 daemon 起的，照 N-64 ④ 同一句）。零改的替代：定義的 `.env` 寫 `{"AOS_DAEMON": {"$env": "AOS_STACK"}}`——但 `.env` 預設不蓋已有的（N-59），人殼裡若已有別台的 `AOS_DAEMON` 就會寄錯台，所以推薦改 daemon。
- **第一個實例＝llm daemon**（使用者 11-05「把 llm 的 daemon＋kernel 叫起來」）：`def/daemon.json`＝`{"exec": {"argv": ["aos-llm-kernel", "kernel.json"]}, "interval_ms": 300}`（`procs` 不寫＝空名單，問腦 proc 全由身體掛上來）；對外收件箱＝kernel 的 `mailbox/`（它認的信是問腦請求、不是 `procs_*`，所以這台不另開 `requests/`）；判斷＝排隊、額度、deadline；base 呼叫＝`procs_added` 寄進自己的 ctl 信箱。佈局在 [07](07-llm-daemon佈局.md)、流程在 [03](03-問腦改掛daemon.md)。
- `aos-daemon-ctl`／`aos-agent add` 在模式 1 下照舊直達 ctl 信箱＝繞過判官。要擋，見 § 3；不擋就是「兩個入口」、自擔（11-03 口徑）。
- 另一條路（不推薦、留翻案）：aos-daemon 加一個 key（例 `procs_judge`）每封信套之前先跑一次。多一條規則、動基礎層；今天身體那條就夠。

## 2 模式 2：0 號 proc 式——唯一能下 ctl 的 kernel proc

「kernel 作為一個唯一有權限對 daemon 下 daemon-ctl 指令的 proc，其他人要掛 proc 就把請求丟給這個 kernel proc」。落法：

- **同一支 `judge/` 改掛成 daemon 的一個 loop 型 proc**（`demo/procs-kernel/`：`_entry`＝aos-loop、`loop.json` 每拍 `judge`；名字代定、可翻案）：收自己 stack 裡的 `requests/`（＝`$AOS_KERNEL`，§ 4），判「掛」的轉寄到 `$AOS_DAEMON/<procs_ctl_mailbox>`——它是 daemon 的子項，`AOS_DAEMON` 天然有（N-64 ④）、信箱名從 `procs_state.json` 讀。這就是使用者說的「轉交型 kernel」；可以慢、可以問腦（它自己的腦走 `AOS_LLM_KERNEL`，不走自己，10-15「判官自己的腦不走自己」）。
- **llm kernel 掛問腦 proc 的信**：llm kernel 自己是一台 daemon 的身體（§ 1）、掛在自己那台上，不經別台的 0 號——它那台沒有別人。真要把 llm kernel 當 proc 掛在一台走 0 號的 agent daemon 上，它的掛信也得過 0 號，所以 aos-llm-kernel 掛信的目的地一律＝**`$AOS_KERNEL` 有設就寄那裡、沒設就寄 `$AOS_DAEMON` 的 ctl 信箱**（§ 4）；0 號照一般請求判（白名單放 llm kernel、或不設上限）。
- **跟 Linux 0 號的差別**（天然差異，不追）：0 號 proc 不是 daemon 起的第一個，而是 daemon.json `procs` 裡的一列；daemon 沒了它照樣是 daemon。
- N-42「兩隻 kernel 不併成一支」（10-16）照舊：procs-kernel（通用、管所有 proc）與 llm-kernel（管腦）是兩支；llm-kernel 經 procs-kernel 掛問腦 proc，就是 10-15「第一種是第二種的特例」在 11-05 定義下的樣子。
