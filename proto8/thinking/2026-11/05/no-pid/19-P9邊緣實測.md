## 過門檻的項目與建議

**high 等待過門檻（B3-02）**：單槽 low 的執行額度 5000 ms、fake_slow 3 秒，high 自己 800 ms，等 **3105.48 ms > 1600 ms** 才掛上。兩封實際掛單的 `exec.timeout_ms` 都留證；先等 low 掛上，再改下一圈 kernel 設定成 800，並沒有假設 body 能覆寫 timeout。控制組兩方都 800 時只等 575.72 ms，不能拿它代替長 low 壓力。現行非搶占設計觸發 [os-impl C5](../../06/os-impl/01-逐項分類-續.md) 的保留 high 格候選；本次不實作。執行額度從掛起端點才開始，不含排隊。

**晚套孤兒確實出現（LATE）**：SIGSTOP daemon，`ctl add --timeout-s 1` 在 1.038 秒報 `DaemonMissing`，信仍在 new。SIGCONT 後 0.020 秒表上多出 `orphan`，回信箱多 1 封。已達 [os-impl 05 的孤兒判準](../../06/os-impl/05-續-邊緣排程與方向題.md)。下一步可併既定判官排隊／代為到期處理寄件人逾時撤信；只撤 new 不能保證取消已進 cur 的工作，需保留這個競態說明。這次照要求只記，不先改呼叫語意。

**回信 >100 只在刻意壓力下（REPLY）**：正常 110 次 ask 都收掉，最後 **0 封**；晚套案 **1 封**。另故意寄 105 次 ping 而完全不領，箱內 **105 封**；將其中 3 封的 sent_at 改老後，下次開箱剩 102，現有十分鐘清理有效。此數字達堆積門檻，但屬無人收件壓力，不能說平常操作會堆積，也不需要重做已存在的清理器。

其餘 B3：60 秒同 sender 的 2 封是不同上下文，**重寄 0**；stack 未達 100 MB；50 次 SIGKILL、200 次 JSON 檢查 **壞檔 0**；100 loops 的 86 圈中位 **108.42 ms**、最大 **111.16 ms < 200 ms**。tick 實跑 **600.000076834 秒、1→588（587 格）**，慢 **2.166679% < 10%**，沒有觸發補 timer 的理由。

## 其餘結論與新發現

長身體不是新增 bug：sleep 15 秒、門檻 10、身體途中寫 ctl，在 **10.072 秒**標 stuck，身體完成後 **4.802 秒**回 running；改門檻 20，同一 15 秒身體到 paused 都保持 running。對這種有已知上界的身體，「調大門檻」夠用；不能外推到無上限的身體。

三層 B／A／根各 kill 一次，分別約 **0.041／0.041／0.021 秒**接回；只重起被殺的那層，葉 PID6 一直保留。根是由外部 harness 重開，沒有宣稱子能重開根。子公開 `daemon` 欄指直屬父；父沒有讀子信箱。三輪 restart_on_stuck 最後 stopped＋reason，實際只重起兩次。

thought 遇 judge max_running1 且已有1 running，在 **0.234 秒**拒 `SlotMissing`，沒有殘留 child；這只證明格滿會失敗，不能代使用者判成「想排隊」。另 max_children1 已有1子時，agents 拒 `ChildSlotMissing`，thought 卻可在 **1.998 秒**答完：max_children 是 agents 工具局部配額，thought 直接走 ctl，要限制整體掛子應用 judge。

B2 新增本機 git image→第三處 clone，**6.34 秒退0**，三地都收假腦回信；clone 後 **6/6 子列 running、27/27 空目錄重建**。cp 的持久 queue counter **26→42**；git 食譜明排 queue.json，clone **42→16** 屬重建，不能宣稱持久 counter 跨 git 累加。本隊沒有對原始碼 repo commit；只有 `/tmp` 的專用 image repo 建必要快照。

sandbox 預設斷網時 bwrap 報 `NETLINK_ROUTE ... Operation not permitted`。用 `net:true` 避開被禁的網路命名空間建立，全程沒有網路 IO；ro 信箱報 MailboxBad，rw 可寄且可 rm 他人。殺沙箱的父後，沙箱消失、外部 daemon 的子仍 running。這案用同樣 ctl add 的普通 loop 驗所有權邊界，沒有再用完整 thought 重演。需要分權仍應只給判官入口。

apply-ideas 選了能本機做的兩案：凍住時先寫 stop ctl，醒來仍當基準線、running；AOS_TICK 指不存在檔時，timeout_ticks1 在 3 秒後仍等，補 tick1 才退。現版已有 missing-file warning，04 那句「沒人警告」已不適用。`limits` 空但 NOFILE32 的例子也量到；未觀察到誤判，不觸發 C4。

## 使用者裁定（11-06 晚，家機）

三題方向題（隊長整理、各附推薦），使用者原話逐字：「好，都按照推薦」。

1. **llm kernel 的 high 等太久**（B3-02：等 3105.48 ms，超過自己 800 ms 逾時的兩倍）→ 照推薦：做 [os-impl C5](../../06/os-impl/01-逐項分類-續.md)「留一格給高優先」，跟判官排隊同一步排。
2. **`ctl add` 報逾時後信晚到仍被套用（孤兒，LATE）**→ 照推薦：併判官排隊＋寄件人逾時第二步一起處理。使用者 11-06 公司已裁「判官窗＋到期拒信」（[os-impl 05](../../06/os-impl/05-寄信者自設逾時.md)）本就涵蓋；把本案列進那步的驗收。注意：信已被 daemon 領走（進 cur）就撤不回，只能保證 new 裡的不被套用。
3. **thought 不受 agents 的子數上限**（`max_children` 只是 agents 工具的局部配額）→ 照推薦：整體上限只靠判官 `max_running`，文件寫清楚。

另：[P7](17-P7實作結果.md) 邊界那處（父重開時看子 state 的 `done`、不再接回已跑完的 loop）照舊保留。
