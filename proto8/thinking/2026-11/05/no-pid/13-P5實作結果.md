## 代定（可翻案）

1. **範例沒寫上限**（`mem_mb`、`cpu_s`）：這台公司 WSL 沒有 s6，寫了就 `CommandMissing s6-softlimit`；thought 大多時間在等回信，CPU 用量小。bash-boxed 寫了上限，在這台跑不起來（沒改它）。
2. **ro 綁整個 `lib/` 而不是只綁 `tool_io.py`**：子範本 `tools.json` 的每支工具（clock、self_tools、agents…）都指到 lib，thought 做「工具 rm」時 aos-tools 會查每條路徑在不在；只綁 `tool_io.py` 會報 `PathMissing tool agents …`。
3. **模式 1 綁整個 `$AOS_DAEMON` rw，不用「只 rw 綁 ctl 信箱」那種更嚴的寫法**：實測更嚴的寫法掛得上子，但 thought 要往子的 stack 寫 `thought.json`（aos-agent 也要寫子的工具覆蓋層），所以報 `WriteFailed … Read-only file system`（會自己 rm 收回子，不留東西）。
4. **模式 2 加 rw 綁 `$AOS_DAEMON/procs`**：原計畫只有「`requests/` rw＋daemon stack ro」，實測同樣卡 `WriteFailed`（`thought.json`）。`$path` 寫 `/procs`（開頭有斜線）：`AOS_DAEMON` 結尾有沒有 `/` 都對。
5. `_entry` 照 bash-boxed 用 JSON argv，沒加註解行（aos-exec 的 JSON 入口不收註解）。code map 從捷徑過去的 `_tooldef.json` 拿 thought 的說明；兩份 `sandbox.json` 第一個鍵是 `description`。

## 沒做的與原因

- **C++ 半**（aos-llm `warn_idle` 改句子、刪讀 pid）：等 E 隊 S7 進 main 後接（規定不碰 C++）。
- **agents 的 `add`／`ask`、self_tools 的 `add`／`rm` 沒在沙箱裡測**，只測了 `ls`：寫的地方一樣是子的 stack、父的覆蓋層（都在 `$AOS_DAEMON` 底下），照理一樣通。
- **沒讓假腦劇本自己叫 boxed thought**（劇本假腦不會叫 thought）：改成用父的身分直接叫，走的路跟 act 叫工具一樣（`AOS_STACK` 落在父的 stack 裡）。
- 換帳號（`user`）、上限（s6）都沒測：這台沒有 s6。

## 張力判斷：「沙箱先不支援」對「沙箱裡的東西只要一個信箱就夠」

- **技術上已經解掉**：11-05 夜裁「先不支援」時，擋路的是 pid（沙箱看不到 daemon 的 pid，誤判死了）。P1～P4 拿掉 pid 之後，綁 daemon 的資料夾就通，模式 2 還能讓判官真的擋住沙箱裡的人。
- **但「只要一個信箱」只在模式 1 的字面上接近**：thought 不只寄信，還要寫子的 stack（`thought.json`、工具覆蓋層），要讀父的定義、子的範本、lib。也就是說，沙箱裡要的是「一個信箱＋子的 stack 寫得進去＋看得到幾個定義資料夾」，不是只有一個信箱。要做到真的只要一個信箱，得把「寫子的 stack」這幾步也改成寄信給 daemon（例：`ctl add` 帶 `thought.json`、覆蓋層），那是 aos-agent／daemon 的改動，這次不動。
- **剩下的是方向題「要不要正式支援」**。**推薦：正式支援，但只寫「支援、照範例綁」，不改程式**——範例已經有、測過，留著「先不支援」反而讓人以為不能用；「只要一個信箱」當遠期目標，等判官長成權限閘門時再把寫子 stack 那幾步收進信裡。另一個選法是維持「先不支援」、範例只當實驗；代價是範例跟裁定字面打架。

使用者選了「現在正式支援 (Recommended)」。選項原文：thought／agents／self_tools 在沙箱裡正式支援，照範例綁 daemon，程式不改；「沙箱裡只要一個信箱」當遠期目標，等判官成為權限閘門後，再把寫子 stack 那幾步改成寄信。

- **現在**：正式支援。綁法照 [cmd/aos-sandbox/examples/thought-boxed](../../../../cmd/aos-sandbox/examples/thought-boxed/)（模式 1 `sandbox.json`、模式 2 `sandbox-kernel.json`），程式不改。small-thought 11-05 夜的「沙箱先不支援」由這條取代（原句留在原處，旁邊加了改讀註）。
- **遠期目標（不排日期）**：沙箱裡只留一個信箱。等判官長成權限閘門，thought 寫子 stack 的那幾步（`thought.json`、工具覆蓋層）改成寄信給 daemon 代寫；到時模式 2 多給的 rw `procs/` 就能收回。

## 新發現的邊緣（沒修，攤出來）

1. **daemon 的 stack 放在工作區裡（試驗場就是 `ws/.stack`）時，綁 `AOS_WS` 就等於綁了整台 daemon**：連 bash-boxed 那種葉工具都寫得到 ctl 信箱、別隻的 stack。aos-sandbox README 已寫一句提醒；要真的關住，daemon 的 stack 別放在工作區裡。
2. **沙箱裡看不到父的定義資料夾時，thought 不報錯、子的腦默默改用範本預設**：thought 用 `aos-agent llm --target <父> show` 拿父的 endpoint，失敗就當「父沒寫」。定義放哪沒有環境變數可指，範例綁不了，README 寫了要自己加 ro。要修可以讓 thought 在 `llm show` 失敗時印一行 warning，或讓 aos-agent 的 `llm show` 讀子的 stack 那份就好、不讀定義。**11-06 已修**（`7125f7dc`，G 隊）：改成報錯、不印 warning——`llm show` 父失敗就接它的代號（多半 `InterfaceMissing`），原因尾加「give endpoint」；只有 `LlmMissing`（父沒宣告 llm）照舊走範本預設。判準：結果還照契約（「沒給 endpoint＝同父的腦」）才算提醒行，做不到就是錯（lib/docs/01 規則 3；KISS「寫什麼就做什麼」，不讓沒給偷偷變成另一個腦）；不加新代號（照接下層，同 agents）。後果：範例照原樣綁、沒 ro 綁父定義時，thought 不給 endpoint 會報 `InterfaceMissing`（bwrap 實測；給 endpoint 或 ro 綁父定義就通），aos-sandbox README 那句已改。
   - **11-06 使用者裁定**（選項框「thought 掛子 agent 時讀不到父的腦設定……要怎麼處理？」）：選「報錯 (Recommended)」——照上面的修法，不改成 warning。
3. **thought 在 `ctl add` 之後、`tools ls` 那步失敗時不會收回子**（`must()` 直接退，沒走 `undo`）：子留在表上 running、紀錄是租約；租約過了（約 95 秒）下一次叫 thought 才把它停掉、記 failed（實測照這樣收了）。不是沙箱的問題，是 thought 的一個漏網步驟。**11-06 已修**（`7125f7dc`，G 隊）：`tools ls` 失敗或印的不是 JSON 也走 `undo`，當下 `ctl rm` 收回、錯誤行尾寫 `(during tools ls; rolled back: removed t-…)`；收不回時紀錄留 running 租約，照舊由下一次對帳收。ctl add 之後到 say 之前的其他步本來就走 `undo`。假腦實測（`/tmp/g-team/`，故意讓子的 `tools ls` 失敗）：改前子留在表上 running、紀錄是租約；改後表上沒有、紀錄清掉。
4. **模式 2 的 rw `procs/` 給得比需要的多**：沙箱裡也寫得到別隻 agent 的 stack（含它們的 `queue/`），只是 ctl 信箱擋住了。要更窄得等「寫子 stack 改寄信」（見張力判斷）。
5. 對照組報的是 `StateMissing` 不是 `DaemonMissing`：daemon 資料夾因為 `AOS_STACK` 綁在它底下而「存在但空的」。腦看到的代號跟「沒設 AOS_DAEMON」不同；knowledge 的 thought 頁沒寫 `StateMissing`。
