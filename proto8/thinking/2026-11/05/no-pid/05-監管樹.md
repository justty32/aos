# 監管樹：daemon 自己卡住或 crash 怎麼辦（使用者 11-05 晚裁定 (1)(2)(4)）

## 使用者原文（11-05 晚，逐字）

> 2.……我原本想說daemon不可以掛，使用者有義務讓daemon成爲最早開始執行，最晚結束的linux行程，並且他必須正常運行。後來想想，我們一大堆daemon在跑，總會有幾個daemon可能卡住，或是crash，那怎麼辦...你有啥好想法嗎。

頂層提的方向（監管樹、state.json 分 phase 與最近反應時間、只有上層動 pid、下層靠 stack 續跑），使用者：「你的想法很好，我也是這麼想的！，剩下都沒問題！」

## 定下的

1. **每台 daemon 都是某台 daemon 底下的 proc**；問誰的死活就問它的上一層。使用者只要顧住**根 daemon**；根是普通 daemon、不另做規定（下「根 daemon」），要一直在就自己交 systemd 或 s6-supervise（notes/s6-runit 已有筆記），也可以壞了就壞了。
2. **crash**：上一層 `waitpid` 到它退了（自己的子，不用 pid 判）→ **照表重起**，孩子從自己的 stack 檔續跑（adopt、接回、`sleeping` 第一圈 wake——daemon 08 當機復原那套已經做好）。
3. **卡住**：上一層照 [02 § 1](02-轉接設計.md) 判（有刺激、`responded_at` 沒跟上、過 N 秒）→ 列標 **`stuck`**，**預設只標、等人處理**；列上寫 **`restart_on_stuck: true`** 才自動 SIGTERM→10 秒 SIGKILL 整群→照表重起。**只有上一層動 pid**。
4. **呼叫者**：只寄信、等回信，逾時就當失敗；想知道原因，讀對方上一層的 `procs_state.json`（那列 `phase`＝`running`／`stuck`／`stopped`／`sleeping`＋`reason`）。

## 怎麼做（fable 代定、可翻案）

### 子 daemon 是哪一種 proc

現在 `ctl add` 掛子 daemon＝exec 型（edge-daemon #11：父不能 sleep 它、父收工就拔、父再開不回來、它底下的 proc 一直 `sleeping` 沒人叫）。監管樹要它**能 sleep／wake／重起**，exec 型做不到、loop 型包一層 aos-loop 又是雙層窗（daemon 本身就是 aos-loop）。推薦**第三種寫法**（使用者 11-03「exec是基石，loop是另一種基本形式，搞不好以後還會有更多形式」）：

- proc 物件寫 **`{"daemon": <定義資料夾或 daemon.json>, "stack"?, "ws"?, "restart_on_stuck"?}`**：父用 `aos-exec -- 小格/daemon.json#/_entry` 起（同 loop 型的起法，但**不包 aos-loop**：目標本身是 aos-daemon），`AOS_STACK`＝小格、`AOS_DAEMON`＝父的 stack（既有）。
- 收工：父送 SIGTERM，子 daemon 自己走收工（把它的 procs 留 `sleeping`），父列留 `sleeping`；開門：父照 `sleeping` 列 wake，子起來自己 wake 它的 procs——**整棵樹一層層醒**。
- 退了：`code 0`／訊號退都**照表重起**（跟 loop 型「結束不自動重起」N-28 不同；daemon 型就是要一直在）；人下 `stop`／`sleep`／`rm` 的才不重起。連續重起失敗（例 3 秒內退、連 3 次）＝列留 `stopped`＋`reason`，不無限重起（代定）。
- 父怎麼認子是 daemon：寫法就是 `daemon` key，不用去讀子的檔猜。

### 卡住怎麼看（父做的事，每拍、只對 daemon 型與 loop 型）

| 刺激 | 哪裡看 | 卡住的判法 |
|---|---|---|
| 子 daemon 的 ctl 信箱有信沒人收 | 子 stack 的 `procs_state.json` 頂層 `procs_ctl_mailbox` → `<信箱>/new/` 最舊一封的 `sent_at` | `sent_at + N < now` 且子 `state.json` 的 `responded_at < sent_at` |
| 子（daemon 或 loop）的 ctl 有新指令沒採用 | 小格 `ctl.json` 的 `seq` vs 子 `state.json` 的 `ctl_seq` | `ctl.json` 的 mtime + N < now 且 `ctl_seq` 沒追上（這裡看 mtime 只為知道「什麼時候寫的」，是刺激時間、不是判活） |
| 沒刺激 | — | **不判**（睡著的不會被誤判） |

N 代定 10 秒。父要讀子的 `state.json`／`procs_state.json`——跟 C-52「daemon 不讀子項狀態」打架，見 [06 衝突 3](06-衝突與邊緣.md)（使用者已裁監管樹，所以是條文要加註）。

跟 N-17「不從檔案判斷」像不像：11-06 頂層問過，使用者 11-06：「照原設計」——判卡住就讀 `responded_at` 比刺激時間，不改成寄 ping（[12](12-P5b條文結果.md)）。

### `stuck` 這一列

- `phase` 值集加 **`stuck`**（N-17 那套值多一個；只出現在父的表、只對 daemon 型與 loop 型）；`reason`＝`no response to <刺激> for 12s`。
- `stuck` 時父**照常不碰它**；人處理＝`ctl rm`（送 TERM／KILL 收掉）或 `ctl start`（父先收掉再起）。`restart_on_stuck: true`＝父自己做 rm＋start 那套、log 一行、列回 `running`。
- 它底下的 procs：子 daemon 被 KILL 時它們變孤兒（setsid 過，不會被一起殺）；子 daemon 重起後 adopt 接回（既有）。

### 根 daemon（使用者 11-05 晚，逐字）

> 關於root daemon，我覺得不用限制他一定要怎樣怎樣，他就是一個普通daemon，只是說因爲他頭上沒daemon了，所以使用者要保証他能正常運行。硬要說的話，以後搞不好會是弄一個linux user，然後這個linux user有一個root daemon，掛在沙盒下，並且可以透過一些手段進行使用者切換(可能搭配一隻有root權限的小程式)。大概是這樣。但也可以就只是一個普通的linux user proc，壞了就壞了。

- **根不做特殊規定**：跟其他 daemon 同一支程式、同一套檔；只是 `state.json` 的 `daemon` 欄 null、頭上沒人判它 stuck、沒人重起它——**由使用者顧著**。可以就是一個普通的使用者行程，壞了就壞了；要它一直在就自己交 systemd（`Restart=always`）或 s6-supervise（`notes/s6-runit`），aos 不自己做「根的根」、不替人選。
- 根 crash 後再起＝它 adopt 接回整棵樹（底下子 daemon 還活著就接、死了就重起）——跟任何一台 daemon 再起一樣，沒有根專用的路。
- `ctl ls` 對根只印 `root daemon (no supervisor)`。
- **以後**（使用者說「搞不好」、標遠期；同晚再補：「其實也不用不同賬號，應該說，更往後的是我希望一個daemon就有一個賬號，然後以此去做相關linux權限設置。」——**已被下一句取代**：「喔不是，應該說一個agent一個賬號。」）：**一個 agent 一個 Linux 帳號**（舊說法「一台 daemon 一個帳號」作廢），用它設 Linux 權限（誰能寫誰的 ctl 信箱、誰能讀誰的 stack）；根 daemon 掛在沙箱下、用一支有 root 權限的小程式切換帳號起子 daemon——跟 aos-sandbox 的 `s6-setuidgid` 是同一條線（kernel-daemon 模式 2 的帳號分開、C-64）。這次不做、不預留 key。

## 什麼時候做

這一塊是 daemon 的 C++（aos-daemon 加 daemon 型、stuck 判定、重起）；**不在大重構 S6 的範圍**，排在 no-pid 第一波（去 pid）之後、當第二波（[07 步驟](07-實作步驟.md) 的 P6～P8）。先把「別人不碰 pid」做掉，監管樹是 daemon 自己的加功能。
