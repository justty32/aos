# P1 實作結果（11-06；commit `09d38608`）

只動 `aos-daemon/src/daemon/daemon.cpp`、`src/common/common.hpp` 與 aos-daemon 的 docs/03、docs/08；`child.cpp` 沒動（少跟家機 S7 分支撞）。

## 做了什麼

1. **鎖不再被子行程帶走**：`check_running` 拿到 flock 之後掛 `pthread_atfork`，daemon 每次 fork 出來的子行程第一件事就是關掉這把鎖。
2. **鎖不到時不碰 /proc**：只看 `state.json` 的 `phase` 是不是 `stopping`（分「收工途中」與「沿用它」兩種訊息），訊息不再帶 `(pid N)`。
3. **adopt 比 boot_id**：上次的表頂層 `boot_id` 跟這次開機不同＝表上的行程都當不在了。
4. `common.hpp` 的 `DaemonRunning` 註解改講 flock。

## 代定（可翻案）

1. **關鎖改掛在每次 fork 上（`pthread_atfork`），不是只在 `run_child` 關**：實查發現 daemon 自己的身體是由 aos-loop 的 `run_folder` fork 的，`run_child` 管不到；掛 atfork 一處就同時管 proc 與身體兩條路。翻案＝改回 `run_child` 關，身體那條另想辦法。
2. **鎖不到時看到 `stopping` 就說「收工途中」**，不再先確認那份 `state.json` 是不是現在鎖著的那台寫的（舊做法要 pid 對得上才信 phase）。
3. **表沒寫 `boot_id`＝當作別次開機**（proto8 不管舊格式）；**這台讀不到 boot_id＝不比**，照舊只比 pid＋ticks。
4. **「起 loop 型之前看小格」（`live_in_cell`）沒補 boot_id**：規劃只列 adopt，照「改動最小」不動。

## 實測（WSL `/tmp` 自己的資料夾，殺程序只用自己記的 pid）

- **修前重現成功**：兩種情況各做一次——exec 型 proc 是內嵌單子（`sleep 12`）、daemon 的身體是 inst 檔——`kill -9` daemon 後立刻再起，兩種都 `DaemonRunning`，而且舊 daemon 的子行程還活著（鎖在它手上）。
- **修後兩種都起得來**。另外驗了：daemon 活著時再起照樣 `DaemonRunning`（訊息不帶 pid）；同次開機 `kill -9` 再起，exec 型照樣接回原 pid；把表頂層 `boot_id` 改成假的再起＝不接回、照名單另起一份新的。
- impls 頂層一次建，建得過。

## 新發現的邊緣（沒修，攤出來）

1. **身體是單子時 `kill -9` daemon，舊身體變孤兒照跑完**，新 daemon 起來又跑自己的身體＝有一陣子兩份身體同時跑。以前被鎖擋著（新 daemon 等它跑完），現在不等。exec 型 proc 不會這樣（新 daemon 接回、不重起）。
2. **上一台死在收工途中**（`state.json` 停在 `stopping`）、新的一台剛拿到鎖還沒寫 state 的那一瞬間，第三台來撞鎖會被告知「收工途中」——只是訊息不準，結果一樣是不起。
3. **`live_in_cell` 沒比 boot_id**（見代定 4）：重開機後小格裡子 loop 的 pid＋ticks 撞上別的行程，會被當成活著接回；機率跟 adopt 那條一樣低。
