## 原文（整理版，字句照原話）

### 信件：信封與 body

> 關於信件這塊，我們現在的aos-post，就是在body外邊包一層東西。就是說，信件是IPC手段，然後我們的"非同步呼叫aos函數"又是基於這個手段的。body內部的json格式我們不多做限制，因爲不管是寄信收信，body的處理都是依靠當初規定這份json格式的人去處理的，對外暴露的，就是說你跑這個程式，body內的東西我會幫你準備好。

### 暫停時間

> 我突然想到另一個更重要的概念。就是說，我們aos體系基於檔案系統還有一個好處：我們可以暫停時間。就是說，我們只要把daemon以及一切都停下來(sleep)，那麼整個資料夾都停下來了(當然，除了一些外部的東西會寫檔)，這類似lisp的image，只是說他這個是更好理解的，畢竟人和AI可以翻資料夾。這除了可以用git之外，這種非同步呼叫也是，可以去看看說目前是哪些信。

### 時鐘：回到 tick-tock（頂層問「凍住時牆上時鐘照走、deadline／租約醒來全過期，時鐘是誰的」之後）

> hoho，這就要回去看proto8概念中的aos-tick/tock了

> 就是說，大家心理有個默契，一次tick/tock就大概是那個時間，需要實際時間的就可以換算。至於一些邊緣狀況就之後再說。這個默契...我實在很不想再添加環境變數，但這太香了...AOS_TICK_INTERVAL。然後我們就是推薦大家用tick回合數來算。但一些需要精確時間的，比如人類使用者體驗這塊，一些與外部的交互這塊，與linux proc的交互這塊(daemon)

> （頂層提「時鐘檔放 daemon stack、間隔寫旁邊、靠 AOS_DAEMON 找，可免加環境變數；誰讓時鐘走」之後）好吧，看來得再加個環境變數：AOS_TICK。要參照哪個就去看這個。至於aos-tick跑在哪，那其實也不重要了。只是說，假如aos-tick跑到一半，被sleep，那麼當他被重啓的時候，該如何界定時間，這個是邊緣狀況，之後處理

## 結論（當場）

- 三層：aos-post 信封（`sender`、`sent_at`、`reply_to`、`in_reply_to`）＝IPC；「寄信＝非同步呼叫 aos 函數、回信＝回傳」建在信上；`body` 格式歸定這個函數的人，aos-post 不看不驗——現行 aos-post 文件「body 的形狀由收信的程式自己驗」已如此。
- 全部 sleep＝整個資料夾凍住（外部寫檔除外），像 lisp image 但人與 AI 能直接翻；可 git，也能直接看「現在有哪些信在途」。

- 時間＝tick（C-05、C-16、C-37、N-01 早已定）：凍住＝tick 不走＝時間沒走。**推薦大家用 tick 回合數算**；一次 tick 大概多久是默契，用 `AOS_TICK_INTERVAL` 給（要實際時間就換算）。**要精確時間的照用牆上時鐘**：人類使用者體驗、與外部的交互、與 Linux proc 的交互（daemon）。邊緣狀況之後再說。
- **`AOS_TICK`＝要參照的那個時鐘**（看它就知道用哪個 tick）；aos-tick 跑在哪不重要。邊緣（之後處理）：aos-tick 跑到一半被 sleep，重啟時怎麼界定時間。
- 衝突（攤給使用者、未處理）：現行實作 aos 內部約定幾乎都用秒（kernel deadline／額度、aos-lock `--lease-ms`、daemon 3 秒判定、今晚定的卡住判定「N 秒沒人收」），照 N-01 應改 tick。

## 頂層提的、留明天聊（未定）

- 非同步呼叫的 body 也要有定義檔（像 `_tooldef.json`），寄信端可照它產生。
- 收信方看不懂 body：只靠「不回＝失敗」，還是約定可選的錯誤回信。
- 暫停時間的邊緣：凍住時牆上時鐘照走（`sent_at`、deadline、鎖租約、3 秒判定醒來都已過期）；寫到一半的 `tmp/`；在飛的 HTTP 請求；沒全睡就 git commit 拿到的是不一致的快照；凍住時改信／改 history 再續跑（[eca § 之後再改](../../../2026-10/30/eca/09-方向題.md#之後再改停著時改-history-再繼續10-30使用者先記下)）。
