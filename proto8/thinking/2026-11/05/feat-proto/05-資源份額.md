# 件 5：資源限制與份額（fable 照原則定，可翻案）

使用者原文（11-05 午，逐字）：「啊，還有，會想要限制特定aos proc所占用的資源。以及daemon/kernel自己本身被限制占用資源，並且會分配份額給proc」；隨後給方向：「讓daemon偷偷給底下的proc包s6」。前情：[aos-sandbox](../../../../extras/sandbox/README.md)（10-24，`s6-softlimit`＋`s6-setuidgid`＋bwrap 的 chain，key `mem_mb`／`cpu_s`／`procs`／`file_mb`／`files`／`user`）；aos-daemon 起每個 proc＝fork 子行程 → setsid、接串流、設 `AOS_STACK`／`AOS_DAEMON` → `run_cli`（`impls/aos-daemon/src/child/child.cpp`）；C-64 用檔案為了借 Linux 權限、C-09／C-10 有限的就是資源、用格數表示。WSL 實測（`/tmp`）：hard limit 只能降不能升、soft 可升到 hard；`ulimit -v` 到頂＝Python `MemoryError`；`ulimit -t 1` 到頂＝被訊號收掉。WSL 沒裝 s6（家機 Manjaro 有）。

## 已定（照原則推得出）

- **份額寫在 daemon 那張表上，proc 自己不知道**（使用者「偷偷」＝C-52 下層不知道上層做了什麼；C-69 aos 不多訂環境變數）。每列選填 **`limits`**，key 照 aos-sandbox 同一套：`mem_mb`、`cpu_s`、`procs`、`file_mb`、`files`、`user`（一詞一義，R4）；daemon.json 頂層選填 **`limits`**＝沒寫的列用的預設（沒寫＝不限）。
- **「daemon 自己被限制」＝由起它的人包**（`aos-sandbox` 或殼的 `ulimit -H`）：rlimit 是繼承的，daemon 的 hard limit 子項天生超不過；子 daemon 再包它的子項只能更緊（Linux 天然如此，不用寫程式）。
- **「分配份額」的天然差異照實寫**：rlimit 是**每個行程各自**的上限，不是從 daemon 總額扣——三列各寫 `mem_mb: 1024` 加起來可以超過 daemon 自己的 1024（daemon 的 1024 只限它本身那個行程）。要真共享總額＝cgroup v2（要 root 或 systemd 委派），列為未來選項、這輪不做。
- **超額＝rlimit 的天然行為**：記憶體到頂＝malloc 失敗（程式多半退非 0）；`cpu_s` 到頂＝SIGXCPU 收掉；`files` 到頂＝open 失敗。對 daemon 來說都是「loop 型退非 0＝留 `stopped`＋`reason`」（11-05 晚已裁）、exec 型照結束碼下表——**不加新的錯誤路徑**（C-53 錯誤路徑濃縮）。
- **llm kernel 的份額＝token／次數**（C-09：有限就是資源）：kernel 總額度（`budget`）已有；包的額度＝件 2；**每個寄件人的額度**這輪補上（下代定 4）。

## 代定（照推薦定，可翻案）

1. **做法：daemon 在 fork 出的子行程裡自己 `setrlimit`／`setuid`，不 exec s6**（見衝突 1）。語意跟 `s6-softlimit`／`s6-setuidgid` 一模一樣（`mem_mb`→`RLIMIT_AS`＋`RLIMIT_DATA`，不碰 `RLIMIT_STACK`，理由同 aos-sandbox；`cpu_s`→`RLIMIT_CPU`；`procs`→`RLIMIT_NPROC`；`file_mb`→`RLIMIT_FSIZE`；`files`→`RLIMIT_NOFILE`；soft＝hard＝寫的值），零外部依賴、不動 PATH（ideas § 24）。`user` 要 root，沒 root＝那列起不來（`LimitBad`）。
2. **寫壞或超過 daemon 自己的 hard**：`limits` 不是物件、值不是正整數＝跟 `stack` 同規則（daemon.json `CfgBad`、procs_ctl 不採用、信壞信）；`setrlimit` 被拒（EPERM：比 daemon 的 hard 寬）＝子行程 stderr.txt 一行 `aos-daemon: LimitBad mem_mb 4096 exceeds the daemon's own hard limit`、退 1 → 列 `stopped`＋`reason`。**不自動夾成 daemon 的 hard**（寫什麼就做什麼，C-56）。
3. **表上看得到**：`procs_state` 每列印 `limits`（生效的那份：列的，或 daemon 預設）；`aos-daemon-ctl ls --json` 帶出、`aos-agent ctl state` 多一行 `limits …`。
4. **llm kernel 每寄件人的額度**：`kernel.json` 的 `budget` 多一格 `senders: {<信封 sender>: {max_calls, max_tokens}}`（窗同 `budget.window`；`used.json` 多 `senders`）；到頂＝那封回 `BudgetMissing sender X: max_calls N reached`。寄件人靠信封 `sender`（aos-post 寫的、不驗，10-15「先信任」）——跟 Linux 權限分帳號時才真擋得住，照 11-05 口徑自擔。
5. **aos-agent 這邊**：定義的 `interfaces.json` 可宣告 `"limits": {...}`（跟 `tools`／`llm` 並列，是這隻**建議**的份額），`ctl add` 轉成 `aos-daemon-ctl add --limits <JSON>`；`ctl add --limits JSON` 蓋過宣告。件 4 的 `agents add` 多收 `limits` 原樣轉。沒有邊緣隊的 E1／E2 前，aos-agent 只讀宣告、不送（stderr 提醒一行）。
6. **跟 aos-sandbox 的關係**：不重用它的 chain（它是給人把一個函數整個關起來的，含 bwrap 命名空間；daemon 這邊只要上限與身分，兩行系統呼叫）。要命名空間就照舊把 proc 的 `exec` 寫成 `aos-sandbox CONFIG …`——那是定義自己的事，daemon 不管。
7. **不做**：份額總和檢查（rlimit 本來就不共享，檢查給人假安全感）、cgroup、每列 `nice`／`ionice`（沒人要）。

## 留給使用者的題（推薦在前）

- **題 6：daemon 自己 `setrlimit`（推薦）還是 exec `s6-softlimit`**——見衝突 1。

## 衝突（哪條、在哪、各自後果）

1. **使用者「包 s6」vs C-56 KISS／ideas § 24「aos 的程式都不動 PATH」**：(a) 推薦 daemon 在子行程直接 `setrlimit`／`setgid`／`setuid`——就是 s6-softlimit／s6-setuidgid 內部做的那兩個系統呼叫，不多一個外部程式、WSL 沒 s6 也能跑、`run_cli` 在行程內 exec 的做法不用改；代價是「s6 那套」只剩語意、沒有那支程式。(b) 照字面 exec `s6-softlimit … s6-setuidgid … aos-exec …`——daemon 的子行程得改成 execvp（現在是行程內 `run_cli`）、PATH 要有 s6、不在時只能 warn 一行照跑（份額形同沒設）。選 (a)；使用者若要「真的是 s6 那支」就翻成 (b)。
2. **「分配份額」vs rlimit 不共享**：天然差異（user.md：沒回答的邊緣狀況當天然差異），寫進 aos-daemon docs 一句；cgroup 列候選。
3. **C-52 下層不知道上層 vs 子項撞上限時看到的錯**：子項只看到 `MemoryError`／被訊號收掉，不知道是 daemon 包的——這正是「偷偷」要的；原因在表上那列的 `limits`＋`reason`，給人看（P-17 人來看）。
