# 現況
**`$ref`（指示詞，N-45）**：JSON 裡任何位置的 `{"$ref": "檔[#/指標]"}` 整個物件換成指到的值，換進來的值接著解。相對檔名（可寫 ./、../）一律從「寫著它的那份檔所在的資料夾」算，不管寫在檔內多深；被換進來的檔裡的 `$ref` 從那份被換進來的檔的資料夾算。`#/a/b`（沒檔名）＝寫著它的那份檔的根算起。指標取的是檔的原文（不穿過檔裡的 `$ref`）。`$ref` 可以是陣列（幾份淺層合成一份）。繞圈＝鏈上同一個（檔,指標）再出現。不知道是哪份檔（stdin、信）時 `#/…` 原封不動。`$path`/`$prefix` 是換完後的純字串拼接。
**index 路徑（今晚定）**：`_index` 表每項可放 `index: 路徑`、物件裡的 `_index` 鍵可以是路徑字串；只顯示、不跟著走。算法：起點＝裝著那份 index 的容器（資料夾，或 json 物件）；在物件裡，名字＝往下一個 key、`..`＝外層物件，根物件（＝這個檔）的 `..`＝檔案所在資料夾；到了檔案系統照資料夾走；`#/指標` 只能接在檔案系統那邊（物件裡直接寫 `w.json#/…` 不收，要先 `..` 走出檔——使用者裁維持）；物件裡的名字一律當 key（不看磁碟）、檔案系統那邊進 json 要明寫 `#`；`#/…` 開頭＝本檔的根（跟 `$ref` 同義）。
例：`kb/v.json#/o/p/_index` 寫 `../r/_index` → `kb/v.json#/o/r/_index`；寫 `../../../x.json#/_index` → `kb/x.json#/_index`。

# 我整理的「統一」幾種形
(a) 全同像：`$ref` 的相對路徑照 index 算。起點＝裝著那個指示詞物件的容器（指示詞像捷徑檔，從它所在的「資料夾」算）。整份檔就是一個指示詞時容器＝檔所在資料夾（不變）。其他位置全變：`{"tools": {"$ref": "tools.json"}}` 現在＝同資料夾的 tools.json，(a) 後＝本檔 `#/tools.json` 這個 key（指不到＝錯）；要寫 `../tools.json`。寫在 `/a/b/c` 的要 `../../../x.json`。新得到的能力：`{"$ref": "../defs/cmd"}` 檔內相對參照。
(b) 只統一寫法與解析器：一支共用的「起點＋字串→檔#/指標」函式，`#/`、`./`、`../`、絕對、跳脫規則兩邊同一份碼；`$ref` 的起點固定給「檔所在資料夾」，index 給容器。現有寫法意思全不變。
(c) index 改回照 `$ref`（從檔所在資料夾算）：等於推翻他今晚的裁示，只列出。
(d) 記號分開的中間形：不帶 `#` 的仍是檔案系統（從檔所在資料夾）；另收 `#../x`、`#./x`＝從所在容器算的檔內相對（現在「# 後不是 /」本來就是不收的空位）。現有寫法全不變，但跟 index 的讀法不一樣（index 沒有 `#./`）。
(e) (a) 加「看到 `#` 就把前面當檔名、從檔所在資料夾算」的放寬——使用者今晚對 index 已裁不放寬。

# 我看到的邊緣狀況（請補）
1. 起點是「指示詞物件自己」還是「裝著它的容器」？我取後者（捷徑檔類比；index 也是從表所描述的容器算）。陣列當容器（argv 陣列元素）：`..` 走出陣列。入口檔根就是 argv 陣列時，元素裡的 `cmd.json#/0` 也得改 `../cmd.json#/0`。
2. 換進來的東西裡的相對路徑，「所在容器」是換之前的位置（來源檔＋來源位置）還是換之後的位置？我認為只能是之前（同現行「從被換進來的那份檔算」，也同檔案系統裡捷徑資料夾的 `..`）；但這跟「最後產出的檔當整份」那句話要並存。
3. 檔內相對走路時，中途的 key 本身是個指示詞（捷徑）要不要穿過？現行指標不穿過（取原文）。
4. `$ref` 陣列淺層合併後，每個 key 記來源檔——要變成記來源檔＋位置。
5. 不知道是哪份檔（stdin、信）：檔內相對可以在手上那份裡走，但走出根就不知道去哪；現行 `#/` 是原封不動。
6. 搬動類工具（daemon 小格、aos-grow、ref --move）：改寫時要把「檔內相對」也換算，或一律正規化成「走出檔再 `檔#/指標`」。
7. C-51 那句「不進規範」：(a) 之後同像就實質成了 N-45 的規範內容。
8. 界線：只統一 `$ref`，還是所有寫在 JSON 裡的相對路徑值（`$override`、hooks 的 handler、cli.json 的 tools、env_file…現在都是「從那份設定檔的資料夾算」）也要跟？
9. (a) 的日常後果：最常見的用法「指同資料夾另一份檔」幾乎一律要多寫 `../`，個數隨寫的深度變；把一個 `$ref` 在檔內挪深一層，字面就得改。

# 我的初步建議

**一、整理與推導的錯誤（深度差一層的陷阱）**
1. **`_index` 與 `$ref` 的容器位階差一層**：
   在 `kb/v.json#/o/p/_index` 中，`_index` 是 `p` 物件裡的屬性，用來描述 `p` 自己，所以起點容器是 `#/o/p`（深度 2，走出檔案要 3 個 `..`）。但在 `{"o": {"p": {"$ref": "..."}}}` 中，整個 `{"$ref": ...}` 就是要替換掉 `p` 的值，裝著它的父容器是上一層 `#/o`（深度 1，走出檔案只要 2 個 `..`）。
   你實作時若直接把 C++ `dir_of(key)` 傳下來的「當前格指標 `#/o/p`」當成起點容器而沒退回父容器，所有 `..` 的層數會全面多算一層。
2. **深度 0 與深度 1 的語義斷裂，以及檔內相對例子寫錯**：
   你在 (a) 說「整份檔是指示詞時容器＝資料夾（不變），其他位置全變」，這表示深度 0 寫 `"tools.json"` 是找**磁碟檔案**，但移進深度 1（`{"k": {"$ref": "tools.json"}}`）容器變成根物件 `#/`，照 index「物件內名字一律當 key、不看磁碟」規則，`"tools.json"` 會突然變成找本檔的 **`#/tools.json` 這個 key**。
   同理，你在 (a) 舉 `{"$ref": "../defs/cmd"}` 當檔內相對例子：若這個 `$ref` 寫在深度 1（父容器為根 `#/`），一個 `..` 就已經**走出檔案到磁碟資料夾**了，根本不是指同檔的 `#/defs/cmd`（在深度 1 要寫 `"defs/cmd"`，深度 2 才是 `"../defs/cmd"`）。

**二、漏掉的邊緣狀況**
1. **`$ref` 陣列本身算不算容器深度**：
   你提到陣列元素（如 `argv`）的 `..` 要走出陣列；那 `{"a": {"$ref": ["x.json", "y.json"]}}` 裡的陣列算不算一層容器？若算，陣列寫法比單一字串寫法還要多寫一個 `../`，完全違反直覺。必須明定「`$ref` 語法自身的陣列不計入容器層級」。
2. **陣列淺層合併後的「同層異深」**：
   當 `$ref` 陣列把 `../x.json#/sub`（深度 1）與 `../y.json#/a/b/c`（深度 3）淺層合併成同一個物件後，往內繼續解時，同一個物件下相鄰的兩個 key，其內部 `$ref` 要走出各自來源檔所需的 `../` 個數竟然不同。
3. **檔內相對路徑撞上未展開的 `$ref` 與繞圈偵測**：
   現行指標取原文、不穿過 `$ref`。若支援檔內相對 `../sibling/sub`，而 `../sibling` 本身是個未展開的 `{"$ref": "../other.json"}`，走原文會因找不到 `sub` 而報錯，這與檔案系統 symlink 資料夾可穿過的同像直覺相悖。此外，繞圈偵測不能只看字面，必須先把檔內與跨檔的 `..` 全部正規化成唯一的 `(絕對檔路徑, #/正規化指標)` 才能比對。
4. **JSON key 含特殊字元的歧義**：
   JSON 的 key 可以叫 `".."`、 `"."` 或含 `"/"`。JSON Pointer 有 `~0`/`~1` 跳脫，但若把物件 key 導覽與相對路徑混在同一套語法，物件內寫 `../x` 與名為 `".."` 的 key 會撞車。
5. **「最後產出當整份」與實際 C++ 淺層展開的矛盾**：
   11-11 說「先用 `$ref` 弄好最後產出再拿去用」，但現況 7 支程式的 130 處呼叫是**邊走邊淺層展開（`resolve_shallow`）**，並非先全檔展開。只要任何工具把展開一半的子樹抽出來改放別層或餵給別處，原本綁定深度的 `../../../` 就會斷裂。

**三、成本估算不對的地方**
1. **嚴重低估 Python 側 8 處 `aos-directive --file` 的改動範圍**：

### (B) 提案：「統一」的其他形、建議方案與執行步驟

**一、根本矛盾與另外兩種「統一」的形**
為什麼 `index` 用容器相對很順、`$ref` 卻會到處寫 `../../../`？因為 **`_index` 90% 是往容器「內部子項」指（往下走），而 `$ref` 本身是被替換的葉節點，不可能指自己的子項，99% 是去拉「外部同夾檔案」或「本檔根 `#/defs`」**。若採用 (a)，等於把最簡短的無前綴語法（`"foo"`）讓給 `$ref` 幾乎不用的「同層兄弟 key」，卻懲罰 100% 的跨檔引用去數 `../../../`。

除了你列的 (a)～(e)，還有兩種更乾淨的形：
- **形 (f) 以 `#` 區分「磁碟起點」與「檔內容器起點」的統一（推薦新形）**：
  緊扣使用者 11-11 的公理「JSON 檔內是 `#`、檔案系統是 `/`，兩者不同」：
  - **不帶 `#` 開頭的相對路徑**（`a.json`、`../a.json#/x`）：起點永遠是**本檔所在資料夾**（走檔案系統）。
  - **`#/` 開頭**：起點是**本檔根**（絕對指標）。
  - **`#` 後接相對路徑**（`#../defs/cmd`、`#./sibling`）：起點是**所在 JSON 容器**（走檔內同像，`#` 後不允許走出檔案根）。
  若把這套同時用在 `$ref`（甚至反推問使用者 `index` 要不要也這樣分），既擁有檔內容器同像，跨檔又永遠不用數 `../../../`。
- **形 (g) 語法與解析器統一，但預設起點依機制職責分流（即你的 (b) 強化版）**：
  共用同一支解析器與跳脫／正規化規則；`#/` 在兩邊完全同義（本檔根），但相對路徑的起點作為傳入參數：`index` 傳「所描述的容器」，`$ref` 傳「本檔所在資料夾」。

**二、具體建議與分步規劃**
建議不要直接硬上 (a)，先向使用者攤開上述「深度綁定後果」，請他在以下三選一拍板：
1. **首推：形 (g) 或 形 (f)**——共用解析器、統一 `#/` 與 `#/指標` 規範；`$ref` 跨檔維持從檔案資料夾算（若要檔內相對則用 `#../`）。130 處 C++ 與現有資料檔零破壞。
2. **次推：若使用者連 `index` 跨檔也不想數 `../../../`**——將形 (f) 同時套用於 `index` 與 `$ref`（無 `#` 走磁碟、`#/` 走檔根、`#../` 走容器）。
3. **若使用者看完代價仍裁定要 (a) 全同像**，則分三步執行：
   - **第一步（定死 4 條邊界規範）**：① 起點定為「`$ref` 所在位置的父容器」（深度 $d$ 走出檔固定要 $d$ 個 `..`，根為 0 個）；② `$ref` 陣列本身不計深度；③ 檔內相對不穿過未展開的 `$ref`，繞圈以正規化後的 `(檔, #/指標)` 判定；④ 明確劃界：只改 `$ref` 與 `index`，其餘設定欄（`env_file`、hooks 等）仍是單純檔案路徑，不跟進。
