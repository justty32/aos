## 一段白話總結

通用 kernel 框架就是把現在的判官改成一支可以設定的小程式，叫它「框架站」。它每跑一次做一輪：從自己的收件箱拿信，照設定決定放行、拒絕還是排隊；放行的原樣轉寄給下一站，拒絕的自己回一封說為什麼。跟判官比，它多了四樣：下一站可以寫在設定裡（不寫就是自己那台 daemon），所以站可以一個接一個串起來；數「現在幾個在跑」可以另外指定去哪台 daemon 數；回信可以選「下游直接回給原寄件人」或「先回給我、我再轉」；還有三個可以插自己程式的時機——判之前、判之後、回信經過時。站跟站之間只認 aos-post 的信封，信裡裝什麼各類自理，站不知道自己在一條鏈上。另外加一種新的信：一般程式想看狀態時不再直接去翻 daemon 的檔，而是寄信問「狀態在哪」，最底的 daemon 回自己那張表的路徑，中間的站可以用「回信經過時」那個時機把路徑換成刪減過的版本。現有判官的功能一項不少，整支改名收進框架。問腦總機這次不動，要不要也收進來是留給你的一題。

## 零件小表

| 零件 | 做什麼 | 設定一行例子 |
|---|---|---|
| 收信 | 每輪從 `$AOS_STACK/requests/` 拿信、逐封看 | （不用設定） |
| 規則 | `procs_*` 的白名單與同時在跑上限；寫了才判 | `"allowed": ["kid"], "max_running": 5` |
| hook 三時機 | 判決前、判決後、回信經過時，跑你指定的 aos 函數，可改可攔 | `"hooks": {"audit": {"event": "after_verdict", "handler": "hooks/audit", "async": true}}` |
| 下一站 | 放行的信轉寄去哪 | `"next": "/srv/team/kernel_b/requests"`（沒寫＝`AOS_DAEMON`） |
| 數量另指 | 上限去哪台 daemon 的表上數 | `"count_daemon": "/srv/team/daemon"` |
| 回信二選一 | 不動 `reply_to`（回信跳過我）／改成自己（回信先回我） | `"reply_via_me": true` |
| 排隊 | 沒格時先來先掛；寄件人可在信裡寫最多排多久 | `"queue": true`（信裡 `"queue_wait_ms": 30000`） |
| 狀態查詢信 | 問「狀態在哪」，最底 daemon 回表的路徑 | 信 `{"procs_state_path": true}` |

## 代定清單（照原則定的，每條可翻案）

框架本體

- **K-F1** 框架用 Python 寫，是資料夾程式 `lib/aos/kernel/`；一輪＝一次執行，由 daemon（當身體）或 loop proc 一次次叫。
- **K-F2** 拆成 `_entry`（一輪的順序）＋`letters.py`、`procs_rules.py`、`queue_fifo.py` 三個模組，手寫 kernel 的人可以只拿其中幾個用。
- **K-F3** 設定檔叫 `kernel.json`，先過 aos-directive（可寫 `$env`／`$path`），相對路徑從它所在的資料夾算，每輪重讀。
- **K-F4** 判官原有的鍵名照留（`allowed`、`max_running`、`queue`、`keep_ordered`）；新鍵叫 `next`、`count_daemon`、`reply_via_me`、`hooks`。
- **K-F5** `next` 的值是下一站的信箱資料夾；沒寫＝`$AOS_DAEMON` 的 ctl 信箱。
- **K-F6** 寫了 `next` 又寫了 `max_running`，就一定要寫 `count_daemon`，不然 `CfgBad`（見衝突 2）。
- **K-F7** `next` 指到自己的收件箱＝`CfgBad`；兩站互指成環不偵測。
- **K-F8** `allowed`、`max_running` 都沒寫的站不驗 body，全部原樣轉。
- **K-F9** 排隊只做先來先掛；要優先序、額度就自己寫 kernel 身體（照 N-42 (2) 現有的話）。
- **K-F10** `queue_wait_ms` 轉寄時原樣帶、不改數字；每站從自己收到的信封時間起算。

回信

- **K-F11** `reply_via_me` 是布林、預設 false；開了以後下游回信寄到 `$AOS_STACK/replies/`，對照記在 `forwarded.json`。
- **K-F12** `keep_ordered: true` 一定要同時 `reply_via_me: true`，不然 `CfgBad`。
- **K-F13** 代回前先看原回信箱還在不在，不在＝丟掉；`forwarded.json` 等不到回信的列不自動清。
- **K-F14** 開了 `reply_via_me` 的站不留原請求的內容，`before_reply` 的 hook 只看得到回信。

hook

- **K-F15** 三個事件叫 `before_verdict`、`after_verdict`、`before_reply`；只寫在 `kernel.json` 一份，不像 agent 有兩份疊。
- **K-F16** `before_verdict` 一封信只跑一次；`after_verdict` 每次判決定下跑一次（進隊一次、出隊再一次）。
- **K-F17** 能改的：判決前改 `body`；判決後改 `verdict`（只收 forward／refuse）與 `error`；回信經過時改回信的 `body`。
- **K-F18** 判決前後退 10＝這封拒掉，代號 `HookRejected`；回信經過時不能攔，只能改內容。
- **K-F19** `condition` 只有 `after_verdict` 收（比判決結果）；另兩個不收。
- **K-F20** 寫了 `before_reply` 的 hook 卻沒開 `reply_via_me`＝`CfgBad`。
- **K-F21** hook 自己失敗、`on_error: stop`＝這輪退 1（`HookFailed`），信留著下一輪重來。
- **K-F22** 「跑一個 handler」的共用程式抽到 `lib/hook_run.py`，agent 的 `hooks.py` 與框架都用它（中層 lib 不能 import 高層的 `lib/agent`）。

名字

- **K-F23** `lib/aos/judge` 整支改名 `lib/aos/kernel`；`judge.json`、`judge_replies/`、`judge_ordered.json`、stderr 前綴 `judge:` 都換新名，舊名不認。
- **K-F24** 範本 `kernel/daemon-judge` 改名 `kernel/daemon-kernel`；`kernel/procs-kernel` 不改。
- **K-F25** 「判官」這個詞在現行說明文件改叫「通用 kernel 的站」（框架站）；舊記錄不改。
- **K-F26** 新錯誤代號三個：`HookFailed`、`HookRejected`、`KernelFailed`；其餘沿用判官的。

狀態查詢信

- **K-F27** 查詢信的 key 叫 `procs_state_path`：請求寫 `true`，回信寫那份表的絕對路徑（daemon 沒開窗＝null）；可以跟別的 key 寫在同一封。
- **K-F28** 表裡的相對路徑從那份檔所在的資料夾算；hook 換出來的刪減表要自己寫絕對路徑。
- **K-F29** 沒設 `AOS_KERNEL` 時不寄信，照現在的找法（`AOS_DAEMON`，再來 `./.stack`）直接算路徑；指令明給 `--daemon` 也不問。
- **K-F30** 設了 `AOS_KERNEL` 卻問不到＝報 `KernelFailed`，不退回去直讀 `AOS_DAEMON`。
- **K-F31** 等查詢回信預設 3 秒（同 `ping`）；人的殼沒有 `AOS_STACK` 時，回信信箱用 `$AOS_KERNEL/reply/`。
- **K-F32** 記不記：`aos-agent` 一次執行只問一次、不落檔；`on_clock` 記在自己小格的 `on_clock.json`、讀不到重問一次。
- **K-F33** 新子命令 `aos-agent ctl state-path` 印問來的路徑，lib 的工具經它拿位址。
- **K-F34** `aos-daemon-ctl`、`aos-mailbox`、`aos-sweeper`、`aos-eca-screen`、`promote` 是指名 daemon 的工具，照舊直讀、不改。

其他

- **K-F35** 新增一支整棵鏈的假腦劇本 `extras/kernel-chain-check/check.py` 當驗收。
- **K-F36** 試驗場不因這次遷移而必須改；讓它真的走 `AOS_KERNEL` 排在最後一步、可不做。
- **K-F37** 問腦總機在方向題裁定前一行不動。

## 跟既有原則的衝突

**衝突 1：N-42「兩支不併成一支」（使用者 10-16）對上「在這個框架下，我們去擴充更多功能如llm之類」（使用者 11-11）。**
衝突在哪：照 11-11 那句，問腦總機該是「框架＋問腦專屬那包」；照 10-16 那句，問腦跟通用 kernel 是分開的兩支。
各自後果：照 10-16＝問腦總機不動，收信與排隊在 Python、C++ 各有一份；照 11-11＝問腦用 Python 重寫掛到框架上、刪掉 C++ 那支，45～60 小時。→ 列成下面的方向題。

**衝突 2：11-11 選項框「數量另外指一台（沒寫且下一站不是 daemon 時設了 `max_running`＝報設定錯）」的字面，對上 C-52 的 11-06 讀法「不認身份、可認公開介面」。**
衝突在哪：照字面，框架要自己分辨「下一站是不是 daemon」；可是下一站只是一個信箱資料夾，要分辨就得去看它旁邊有沒有 daemon 的檔來猜，等於認對方的身分。
各自後果：
- 照代定（K-F6）：寫了 `next` 就一律要寫 `count_daemon`，即使下一站其實就是一台 daemon 也要多寫這一行；框架完全不猜。沒寫 `next` 的（＝現在所有判官）不受影響。
- 照字面：下一站剛好是 daemon 時可以少寫一行；代價是框架裡多一段「看信箱的上一層有沒有 `procs_state.json`」的猜法，下一站換一種擺法就可能猜錯而不報錯。

目前照代定走；要照字面的話說一聲。

## 給使用者的方向題

**題 1：問腦總機要不要也收進這個框架？**

背景例子：現在試驗場的總機是一支 C++ 程式（2343 行），自己收信、自己排隊（急件優先、額度、一次只載一個本機模型）、自己把問腦的工作掛到 daemon 上跑完再回信。框架站（判官改的）做的是「判一下、轉寄出去」。兩支的頭尾像（收信、回信、排隊窗），中間不一樣。你 10-16 說過兩支不併，11-11 說框架下要擴充 llm，兩句頂到了。

| 選項 | 做什麼 | 後果 |
|---|---|---|
| **A 先不併（推薦）** | 這次只做框架、收判官；問腦總機不動。N-42 那句留著，註明「等框架跑穩、問腦真的需要 hook 或鏈上轉寄時再議」 | 0 小時。兩種語言各有一份收信與排隊；問腦沒有 hook。之後要併路還在 |
| B 全併 | 框架長出「排序可換」「自己跑」兩個口；問腦專屬那包用 Python 重寫；刪掉 C++ 那支；N-42 明寫翻案 | 45～60 小時、要回家用真腦驗。骨架只剩一份、問腦自動有 hook；但框架變大、問腦每輪變慢、重寫期間全樹問腦受影響 |
| C 只補 hook | C++ 留著，只在裡面加同樣契約的三個 hook 點 | 12 小時。行為對齊、程式仍兩份；等於替問腦加一個沒人提過的功能 |

推薦 A 的理由：問腦總機是每隻 agent 都靠的東西，現在跑得好；框架還沒做出來，不知道要長什麼口才裝得下它。三種的圖在 [04](04-問腦併不併.md)。

## 不在範圍

- 寄信（mailbox）與時鐘算不算資源、要不要過 kernel：使用者沒回，照通則不追問、不設計。
- 沙箱與權限：以 Linux 為保底，不另設計權限系統。
- 「`AOS_KERNEL`、`AOS_DAEMON` 兩個都沒設就報錯」不做；猜 `./.stack` 留著（11-12 未定案）。
