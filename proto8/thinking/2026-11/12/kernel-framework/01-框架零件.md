# 通用 kernel 框架的零件：一支 Python 資料夾程式 `lib/aos/kernel`，每跑一次做一輪，照 `kernel.json` 收信、判、轉寄、回信、排隊

← [kernel-framework](README.md)｜下一份 [02-判官收編](02-判官收編.md)｜第二版：照 [Argon 審查](07-Argon審查.md)改過，採納表在 [README](README.md#argon-審查與改圖)

框架是一包方便零件，不是概念：照 [C-47](../../../../docs/CONCEPTS/04-kernel.md)，請求寄到哪、那裡對寄件人就是 kernel；自己手寫一支收信的程式也算。這包零件只是讓「常見的那種站」不用每次重寫。

## 形式

- **語言 Python**，資料夾程式，放 `lib/aos/kernel/`（中層 lib，跟現在的判官同一層）。現有判官、hook 契約、kernel 範本都是 Python；lib 工具走 `tool_io.py`。
- **一輪＝一次執行**：`aos-exec <lib/aos/kernel> <kernel.json 的絕對路徑>`，做完一輪退 0（沒信也退 0）。自己不常駐、不打拍子。
- **誰來一次次叫它**（三種擺法，都是範例，不是只有這三種）：

| 擺法 | 怎麼掛 | `AOS_KERNEL` 指哪 |
|---|---|---|
| daemon 的身體（繼承式） | `daemon.json` 的 `exec`＝這支，daemon 每圈跑一次；`AOS_STACK`＝daemon 自己的 stack | `<daemon stack>/requests` |
| daemon 底下一個 loop proc（0 號 proc 式） | `loop.json` 的 `exec`＝這支 | `<那個 proc 的 stack>/requests` |
| 鏈的中間站 | 上面兩種任一，`kernel.json` 多寫 `next` 指到別站 | 同上 |

- 跟 aos-daemon loop 身體的關係：框架不認識 daemon 的 loop，daemon 也不認識框架——daemon 只是每圈跑一次 `exec`、看結束碼（[N-43](../../../../docs/NORMS/01-總則/02-N-43.md)）。當身體時這一輪卡多久，daemon 那一圈就卡多久（hook 慢＝使用者 11-11「等他，如果不想等，那就hook那邊走async」）。
- **共通的只有 aos-post 信封**（`sender`、`sent_at`、`reply_to`、`in_reply_to`、`body`）。body 各類自理；框架內建的規則只看得懂 `procs_*` 這一類，其他 body 一律原樣轉。信封不加「哪一類」「走過哪些站」「最初寄件人」。站不知道自己在鏈上，只知道這封信從哪來（信封）、要轉去哪（`next`）。

資料夾：

```
lib/aos/kernel/
  _entry            通用 kernel 的站：把「掛 proc 那一包」的五個口交給 round()
  round.py          骨架：一輪的大順序、鎖、hook 三時機的派發、拒信與回信（全體只有這一份）
  letters.py        收信、轉寄、拒信、代回（包 aos-post）
  runner.py         「自己跑」零件：把一封信掛成 proc、收成品、逾時、重掛一次（問腦那包用，見 04）
  procs_rules.py    掛 proc 那一包：allowed、max_running、去表上數 running
  queue_fifo.py     掛 proc 那一包：排隊窗 queue.json 與寄件人期限
  _metainfo.json  _tooldef.json  README.md
  tests/test_kernel.py
lib/aos/kernel_llm/   問腦專屬那一包＋它自己的 _entry（見 04）
lib/hook_run.py     hook 的共用引擎（agent 的 hooks.py 與這裡共用）：驗一格的形狀、照名字排序、
                    比 condition、寫 event.json、跑 handler、解結束碼與 stdout、處理 on_error；
                    事件表由呼叫的人給
```

站的 stack（`$AOS_STACK`）：

```
requests/            對外收件箱（AOS_KERNEL 指這裡）
queue.json           排隊窗（開了 queue 才有；公開，給寄件人查第幾位）
bodies/<信名>.json   before_verdict 改過、還在排隊的信的新 body（站自己用，不是公開窗）
replies/             開了「回信先回我」時，下游的回信寄到這
forwarded.json       轉寄後信名 → {原信名, 原回信箱, 原寄件人}
hooks/<名>/          hook 的小格（event.json 是最後一次的事件）
```

## 設定檔 `kernel.json`

讀進來先過 `aos-directive`（所以可以寫 `{"$env": …, "$path": …}`）。**`next`、`count_daemon`、每個 hook 的 `handler` 這三欄如果是相對路徑的普通字串，載入時一律從 `kernel.json` 所在的資料夾轉成絕對路徑**（aos-exec 跑起來時 cwd 在 lib 那邊，不能靠 cwd）。每輪重讀，改了下一輪生效。不認得的鍵不管（C-48）。

最小的站（什麼都不管，全部原樣轉給自己那台 daemon——「啥都不管也是一種管理」）：

```json
{}
```

等於現在判官範本的站：

```json
{"allowed": ["peek_now_time", "fsm1", "kid"], "max_running": 5, "queue": true}
```

鏈的中間站，零件全開：

```json
{"next": "/srv/team/kernel_b/requests",
 "allowed": null,
 "max_running": 8, "count_daemon": "/srv/team/daemon",
 "queue": true,
 "reply_via_me": true,
 "keep_ordered": false,
 "hooks": {
   "need_owner": {"event": "before_verdict", "handler": "hooks/need_owner", "timeout_ms": 5000},
   "audit":      {"event": "after_verdict",  "handler": "hooks/audit", "async": true},
   "hide_table": {"event": "before_reply",   "handler": "hooks/hide_table"}}}
```

| 鍵 | 意思 | 沒寫 |
|---|---|---|
| `next` | 下一站的信箱資料夾 | `$AOS_DAEMON` 那台的 ctl 信箱 |
| `allowed` | `procs_added` 的名字白名單 | 不限 |
| `max_running` | 同時最多幾個 running | 不限 |
| `count_daemon` | 去哪台 daemon 的表上數 running（值＝那台的 stack 資料夾） | 沒寫 `next` 時＝`$AOS_DAEMON` |
| `queue` | 沒格時排隊（先來先掛）還是立刻拒 | `false`＝立刻拒 |
| `reply_via_me` | 回信二選一：`false`＝不動 `reply_to`（回信跳過我）；`true`＝改成我自己（回信先回我） | `false` |
| `keep_ordered` | 有序信照有序轉寄 | `false` |
| `hooks` | `{名字: 一格}`，格的鍵照 agent 的 hook 契約 | 沒有 hook |

## 骨架與五個口

骨架只有一份（`round.py` 的 `round()`），通用 kernel 與問腦總機都跑它。每一輪的大順序固定，中間五件事是可以換的口，由「包」提供：

| 口 | 做什麼 | 掛 proc 那一包（原判官） | 問腦那一包（[04](04-問腦併不併.md)） |
|---|---|---|---|
| 收成品 `collect` | 把「下游的答案」拿回來 | 收 `replies/` 裡下游的回信（開了 `reply_via_me` 才有） | 收跑完的問腦 proc 的成品、該重掛的重掛 |
| 驗信 `check` | 這封信收不收、什麼時候認領 | 一來就認領；只驗規則要看的欄 | 排隊時留在 `new/`、掛上才認領；驗代號、釘死的參數、priority；收拾寄件人已走的信 |
| 排序 `order` | 先看誰 | 先來先掛 | 級數＋aging → 期限 → 黏著 → 速度 → 等得久 → 先寄 |
| 放不放 `admit` | 這封現在放行、拒、還是排 | 期限、`allowed`、`max_running` | 期限、總格／保留格／包格／後端格、額度 |
| 去處 `dispatch` | 放行的信怎麼處理 | 轉寄給 `next` | 掛成 proc 在自己那台 daemon 跑 |

骨架自己做的（每個包都一樣）：讀設定、鎖（`requests/.flock`，第二個身體同時跑＝`LockFailed` 退 1）、hook 三時機、拒信的形狀、寄回信、錯誤行。判決一律叫 `pass`（放行）／`refuse`（拒）／`queue`（排）。手寫 kernel 的人可以照樣寫五個口交給 `round()`，也可以只拿 `letters.py`、`runner.py` 幾個零件自己組。

下面先講掛 proc 那一包（通用 kernel 的站）。

## 一輪的順序

```
讀 kernel.json（壞＝CfgBad 退 1）；鎖 requests/.flock
1. aos-post init＋take-all requests/
2. 先收掉「已經轉寄過」的原信：requests/cur/ 裡的信名，在 forwarded.json 找得到
   （是某列的 key、或某列的 letter）、或下一站信箱 new/、cur/ 有同名信 → 收掉原信；
   那一列如果不等回信（reply_to 是 null）就順手刪掉
3. 代回回信（開了 reply_via_me，或 forwarded.json 還有等回信的列）：
     收 replies/ → 每封：查 forwarded.json → before_reply hook → 代回原回信箱 → 刪列、收信
4. requests/cur/ 逐封（已在隊的先、照原隊序；新信照 aos-post 處理順序）：
     信封壞 → warning、丟
     新信：before_verdict hook（可改 body；退 10＝直接拒 HookRejected，不跑規則、不跑 after_verdict）
     內建規則，照這個順序：
        ① 期限：queue_wait_ms 是正數而且已過 → refuse SlotMissing
        ② allowed（有寫才判）→ 不在名單 refuse NameUnknown
        ③ max_running（有寫才判）→ 有格 pass；
           沒格：開了 queue 而且 queue_wait_ms 不是 0 → queue，否則 refuse SlotMissing
     after_verdict hook：新信判完跑一次；已在隊的信只有「這一輪離開隊」（變 pass 或 refuse）才跑，
                         繼續排的不跑
     pass  ：轉寄給 next → 收掉原信
     refuse ：回 {"applied": false, "error": {code, msg}}、收掉、stderr 一行 warning
     queue  ：留在 cur/、記進 queue.json
5. 寫 queue.json
退 0
```

第 2 步排在第 3 步前面是有原因的：站在「已轉寄、還沒收掉原信」時死掉，下游的回信可能比站先回來；要是先代回、刪了對照，再回頭看原信就認不出它轉過了，會再轉一次。

## 零件

### 收信

- 行為：對外收件箱固定 `$AOS_STACK/requests/`（沒有就建）；每輪 `take-all` 認領、照 aos-post 的處理順序逐封看。上一輪認領了沒做完的（還在 `cur/`）這一輪接著做。
- 錯誤（自己的，退 1）：`StackMissing`、`CommandMissing`（PATH 沒 aos-post／aos-directive）、`PostFailed`（init／take-all／see 失敗）。信封壞＝丟掉＋一行 warning，不算錯。
- 對應判官：`_entry` 370～391 行（init、take-all、逐封 see）。

### 規則

- 行為：內建只有判官現有的那幾條：
  - 期限：信的 body 帶 `queue_wait_ms`（非負整數，不是就拒 `BodyBad`）。**正數**而且從這站收到的信封 `sent_at` 起算已經過了＝拒 `SlotMissing`，就算當下有格也拒（11-07 已裁：過期的不能補掛）。**`0` 不算到期**，意思只是「沒格時不要排」。
  - `allowed`：`procs_added` 每個名字都要在名單裡，不然拒 `NameUnknown`。
  - `max_running`：`count_daemon` 表上 `running`＋`stuck` 的列＋這輪已放行的新名字＋這封的新名字，超過就拒 `SlotMissing`（或排隊）。`procs_started`、`procs_woken` 也算新名字。
  - 規則要看的欄形狀不對（`procs_added` 不是物件等）＝拒 `BodyBad`。
- `allowed`、`max_running` 都沒寫、信也沒帶 `queue_wait_ms` 時，站不驗 body，連是不是物件都不管，原樣轉。
- 其他 `procs_*`、`ping`、查詢信（[03](03-狀態查詢信.md)）、不認得的 key：不判、原樣轉。停／收／睡／醒要不要判是收件 proc 自己的事（N-42 (2)）；要判就寫 hook。
- 其他類的 body（不是 `procs_*`）要判：寫 `before_verdict` hook。優先序、額度這種「排程器」不是這包零件的事，照舊自己寫一個 kernel 身體。
- 對應判官：`verdict`（156～185 行）、`load_policy`（96～123 行）、`expiry_message`（327～337 行；`0` 不算到期、過期的有格也拒，都是現有行為）。

### hook 三個時機

沿用 agent 的 hook 契約（[hook 圖紙](../../10/self-family/hook/01-圖紙.md)、現行 [aos-agent docs/06](../../../../cmd/aos-agent/docs/06-hook.md)）：格的鍵 `event`、`handler`、`condition`、`intercept`（預設 true）、`async`（預設 false）、`on_error`（`stop`／`continue`，預設 `stop`）、`timeout_ms`（預設 60000）；事件 JSON 從 stdin 進、同時留一份在 `hooks/<名>/event.json`；`aos-exec --stack <小格>/ <handler>` 自成行程群組；退 0＋stdout 空＝不改、退 0＋JSON 物件＝只取認得的鍵、退 10＝攔下、其他或逾時＝hook 自己失敗；同一事件多個 hook 照名字排序跑、前一個改過的後一個看得到、被攔下就不往下跑。`intercept: false` 或 `async: true` 的 hook＝純通知：不看它的 stdout，退 10 也不攔。

| 事件 | 什麼時候 | 事件 JSON 多的欄 | `condition` 比什麼 | 能改 | 退 10（攔下） |
|---|---|---|---|---|---|
| `before_verdict` | 一封新信、內建規則判之前。一封只跑一次（排隊中的信之後每輪不再跑） | `letter`（信名）、`sender`、`sent_at`、`reply_to`、`body` | 不收 | `body` | 這封直接拒，代號 `HookRejected`，原因＝hook 的 stdout（空就寫 `blocked by hook 名字`）；不跑內建規則、不跑 `after_verdict`（同 agent：被攔下的工具不觸發 `after_tool`） |
| `after_verdict` | 判決定下的那一刻：新信判完（pass／refuse／queue）一次；排隊的信離開隊（pass 或到期 refuse）再一次；繼續排的不跑 | 上面那些＋`verdict`、`error`（refuse 時的 `{code, msg}`） | `verdict` | `verdict`（只收 `"pass"`、`"refuse"`）、`error` | 這封拒，`HookRejected`，原因同上 |
| `before_reply` | 下游回信到了、代回給原寄件人之前。**只有 `reply_via_me: true` 的站才有** | `letter`（原信名）、`sender`（原請求的寄件人）、`reply_to`（原回信箱）、`reply_sender`（回信的寄件人）、`body`（回信的 body） | 不收 | `body` | 原回信不代回，改代回 `{"applied": false, "error": {"code": "HookRejected", "msg": "reply blocked by hook 名字: <stdout>"}}`（原因寫明是回信被攔，不是請求沒做） |

- 每份事件 JSON 都有 `event`、`hook`、`stack`（站的 stack）。
- `after_verdict` 把判決改成 `"refuse"` 卻沒給完整的 `error`＝填 `{"code": "HookRejected", "msg": "refused by hook 名字"}`。把 refuse 改成 pass 時照放行、不再回頭驗規則（寫什麼就做什麼）。
- hook 只寫在 `kernel.json` 的 `hooks`，一份，不像 agent 有定義＋stack 兩份疊。
- 設定錯（退 1 `CfgBad`）：格的形狀不對、事件名不認得、寫了 `before_reply` 的 hook 卻沒開 `reply_via_me`。
- hook 自己失敗：`on_error: stop`＝這一輪印 `kernel: error: HookFailed …`、退 1，信留在 `cur/` 下一輪重來（當 daemon 身體＝下一圈再跑；當 loop proc＝停下等人，跟站自己其他的錯同一條路）；`continue`＝印一行 warning、當沒這個 hook。`async: true` 的放出去就不管。
- `hooks/<名>/event.json` 裡有沒改過的原內容；站的 stack 要不要給別人讀，靠 Linux 權限。
- 對應判官：現在沒有；插在 `_entry` 419～422 行的逐封迴圈（`verdict` 前後）與 `relay_replies` 代回之前（218～227 行）。

### 下一站

- 行為：放行＝把 body 原樣（或 hook 改過的）用同一個信名寄進 `next`。沒寫 `next`＝`$AOS_DAEMON/<procs_state.json 頂層的 procs_requests>`（現在的行為）。
- 防重（一輪的第 2 步）：原信名在 `forwarded.json` 找得到（比列的 key，也比列裡的 `letter`），或下一站信箱 `new/`、`cur/` 有同名信＝當作轉過了、收掉原信。
- 設定錯：算出來要轉去的信箱（不管是明寫的 `next`，還是從 `$AOS_DAEMON` 算出來的）解開捷徑後就是自己的 `$AOS_STACK/requests`＝`CfgBad`。
- 錯誤：沒寫 `next` 又沒有 `AOS_DAEMON`（或不是資料夾）＝`DaemonMissing` 退 1；那台表上 `procs_requests` 明寫 null＝`MailboxMissing` 退 1；下一站信箱不存在或寄不進去＝這封拒 `ForwardFailed`、一輪照樣退 0。
- 對應判官：`forward`（247～268 行）、`already_forwarded`（238～244 行）、`daemon_view` 找 ctl 信箱（126～148 行）、`main` 347～349 行寫死 `AOS_DAEMON`。

### 數量另指

- 行為：`max_running` 要數的那張表在 `count_daemon` 那台（讀它的 `procs_state.json`，超過 100 列切檔照舊經 aos-directive 解）。表還沒寫出來＝當 0 個 running。
- 設定錯（`CfgBad`）：寫了 `next` 又寫了 `max_running`，卻沒寫 `count_daemon`。11-11 裁的是「下一站不是 daemon 又沒寫＝設定錯」；框架不去猜下一站是不是 daemon，因為猜不準：(a) `next` 是信箱、不是 stack，ctl 信箱不一定就在 stack 的下一層；(b) daemon 剛起、表還沒寫出來時會被當成不是 daemon；(c) 下一站如果是「當別台 daemon 身體的中間站」，它上一層真的有一張表，猜了就會去數錯台。所以落成「寫了 `next` 就自己講去哪數」。
- 錯誤：`count_daemon` 不是資料夾＝`DaemonMissing` 退 1；表讀不懂＝`StateBad` 退 1。
- 在飛的（轉了、那台還沒套）不算 running，照舊是已知限制。
- 對應判官：`daemon_view` 數 running（128～146 行）。

### 回信二選一

- `reply_via_me: false`（預設）：轉寄時 `reply_to` 照原樣帶過去（存成絕對路徑），下游直接回給原寄件人，回信跳過我。
- `reply_via_me: true`：轉寄時 `reply_to` 改成 `$AOS_STACK/replies/`，並在 `forwarded.json` 記 `{轉寄後信名: {"letter": 原信名, "reply_to": 原回信箱絕對路徑, "sender": 原信封的寄件人}}`（只記信封上的欄，不留原 body）。每輪收 `replies/`：照回信的 `in_reply_to` 查表 → 跑 `before_reply` hook → 用原信名當 `in_reply_to` 寄回原回信箱 → 刪列、收信。原信沒 `reply_to`＝不改 `reply_to`。
- 代回失敗收斂成一條路：原回信箱不在、或 `aos-post send` 寄不進去＝一行 warning、刪列、收掉回信，不重試（寄件人本來就靠自己的逾時）。查不到對照的回信＝warning、收掉。
- 拒信：站自己回 `{"applied": false, "error": {"code", "msg"}}` 給原信的 `reply_to`（沒 `reply_to` 就只收掉），stderr 一行 `kernel: warning: letter <名> refused: 代號 原因`。拒信是站的答案，不是站的錯，照樣退 0。
- `keep_ordered` 跟 `reply_via_me` 是兩個獨立的鍵，各照字面：
  - `keep_ordered: true`＝有序信照有序轉寄（信名會變）。這時不管有沒有 `reply_to` 都在 `forwarded.json` 記一列當防重依據；不等回信的列（沒開 `reply_via_me`、或原信沒 `reply_to`）記 `"reply_to": null`，原信收掉後就刪。
  - 只開 `keep_ordered`、沒開 `reply_via_me`＝下游直接回，回信的 `in_reply_to` 是轉寄後的新信名，跟原信名對不上；要對得上就兩個都開。
- 不記走過哪些站、不帶最初寄件人：後站看到的 `reply_to` 就是前站的 `replies/`，跳不過前站（已裁，風險使用者自擔）。
- 錯誤：`forwarded.json` 讀不懂或寫不了＝`StateBad` 退 1。
- 對應判官：`refuse`（271～277 行）、`relay_replies`（199～235 行）、`judge_replies/`、`judge_ordered.json`（現在只給有序信用，這裡變成所有信都能用）。

### 排隊

- 行為：照搬判官現有的。`queue: true` 時沒格的信留在 `requests/cur/`、先來先掛；隊首還沒格時，後面要新格的不能插隊，不要新格的（stop、ping、查詢信）照轉。窗 `$AOS_STACK/queue.json`＝`{"queued": [{"letter", "names", "queued_at", "queued_at_cycles"?, "expires_at"?}]}`，陣列順序＝第幾位。窗讀不懂＝warning、當空窗、從 `cur/` 重排。
- `before_verdict` 改過 body 的信如果進了隊，新 body 存在 `$AOS_STACK/bodies/<信名>.json`（不放進公開的 `queue.json`），出隊轉寄或拒掉後刪。
- 寄件人期限 `queue_wait_ms`：算法在上面「規則」；隊裡的信每輪也先看期限。轉寄時原樣帶，不改數字。
- 排隊中不另回「排隊中」的信；一封請求只有最後一封回信。
- 錯誤：`queue.json`、`bodies/` 寫不了＝`StateBad` 退 1。
- 對應判官：`queue_view`／`write_queue`／`expiry_message`（298～337 行）、主迴圈 378～459 行。

## 錯誤代號總表

| 種類 | 代號 |
|---|---|
| 站自己的錯（stderr `kernel: error: 代號 原因`，退 1） | `ArgumentsBad`、`CfgMissing`、`CfgBad`、`StackMissing`、`DaemonMissing`、`StateBad`、`MailboxMissing`、`CommandMissing`、`PostFailed`、`HookFailed`（新）、`LockFailed`（新：另一個身體鎖著同一個收件箱） |
| 拒信的代號（寫在回信的 `error.code`，同一句印成 warning） | `BodyBad`、`NameUnknown`、`SlotMissing`、`ForwardFailed`、`HookRejected`（新） |

下游回的 `applied: false`（例：daemon 對壞 body 回 `BodyBad`）是下游的答案，站原樣代回或根本沒經手，不換成自己的代號。
