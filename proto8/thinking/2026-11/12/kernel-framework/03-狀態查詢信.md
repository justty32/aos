# 「狀態在哪」查詢信：一般 proc 寄一封信問 `AOS_KERNEL`，最底的 daemon 回自己那張表的檔案路徑；工具先問再讀

← [kernel-framework](README.md)｜上一份 [02-判官收編](02-判官收編.md)｜下一份 [04-問腦併不併](04-問腦併不併.md)｜第二版：照 [Argon 審查](07-Argon審查.md)改過；現況對齊 kernel 小修線（[kernel-small-fixes](../kernel-small-fixes.md)，待進 main）

使用者 11-11：「然後kernel給狀態位址...希望不是使用symlink，我不希望aos體系硬性依賴symlink，或許可以折衷？寄信問，取得狀態位址這樣。」選項框：一般 proc 讀狀態＝「kernel 給一個狀態位址」；問來的位址要不要記＝「工具自己決定」。

## 信的形狀

請求（body，跟 `ping` 同一種寫法，可以跟別的 key 寫在同一封）：

```json
{"procs_state_path": true}
```

回信（最底的 daemon 回的）：

```json
{"applied": true, "procs_state_path": "/home/me/ws/.stack/procs_state.json"}
```

- 請求與回信用同一個 key：請求寫 `true`＝「我要這個」，回信寫值。值是**絕對路徑**，指到一份 aos-daemon 的 `procs_state.json`（格式是 daemon 公開的那一份，超過 100 列切檔照舊經 aos-directive 解）。
- 表裡的相對路徑（各列的 `stack` 等）從**那份檔所在的資料夾**算——對 daemon 自己那份來說就是 daemon 的 stack，跟現在一樣。
- daemon 沒開 `procs_state` 窗＝回 `{"applied": true, "procs_state_path": null}`，工具看到 null 報自己的 `StateMissing`。
- `procs_state_path` 寫了卻不是 `true`＝壞 body，照小修線的做法回 `{"applied": false, "error": {"code": "BodyBad", "msg": …}}`。
- 回信怎麼走照信封的 `reply_to`，跟其他信一樣。沒帶 `reply_to`＝沒人收得到答案。

## 最底：aos-daemon

改 `impls/aos-daemon/src/daemon/mailbox.cpp`，像 `ping` 那樣多認一種信：`apply_letter` 認 `procs_state_path`（有寫就必須是 `true`、不改底、跟其他 key 並寫時其他 key 照常套）；`done_letters` 回信時多帶 `procs_state_path`＝自己那份表的絕對路徑（沒開窗＝null）。不動持久格式，**不用重建什麼**。

## 中間站

- **框架站預設原樣轉**：`procs_state_path` 對它是不認得的 key，不判、照 `next` 轉，回信照 `reply_via_me` 的設定走。不需要為查詢信寫任何專用程式。
- **要給刪減版**：那一站開 `reply_via_me: true`，寫一個 `before_reply` 的 hook——看到回信 body 有 `procs_state_path`，就照事件裡的 `sender`（原請求的寄件人）產一份刪減過的表，把 `procs_state_path` 換成那份的絕對路徑。刪減表裡各列的 `stack` 要寫絕對路徑（因為檔搬了位置）。這種 hook 的 `on_error` 用預設的 `stop`：失敗時回信卡在站裡、寄件人逾時，不會把沒刪減的原路徑漏出去。
- **要真的隔得住，靠 Linux 權限**：換路徑只是給一份方便讀的版本。底層 daemon 的 `procs_state.json`、中間站的 `hooks/<名>/event.json`（裡面有沒刪減的原路徑）都要用 Linux 權限對下游關掉讀取；刪減表寫在下游讀得到的地方（不一定在站自己的 stack 裡）。
- **手寫的 kernel**：要不要答、答哪份，它自己決定（「有些kernel他可能只能處理掛proc或只能處理llm call，都無所謂」）。不答＝查表的指令等到逾時；掛、停、收這些寄信的指令不受影響（見下）。

## 工具怎麼「先問再讀」

分兩類：

**查表的指令**（`aos-agent ctl ls`／`who`／`state`／`where` 等，本來就是要看表）——共用一個函數（`py/daemon_ctl` 新增 `state_path()`）：

| 情況 | 位址怎麼來 |
|---|---|
| 指令明給了 `--daemon D` | 指名那一台：`D/procs_state.json`，不問（跟 `aos-daemon-ctl` 同一個道理） |
| 有設 `AOS_KERNEL` | 寄 `{"procs_state_path": true}` 到 `AOS_KERNEL`、等回信（預設 3 秒，同 `ping`；`--timeout-s` 可調）；回信的路徑就是答案 |
| 沒設 `AOS_KERNEL` | 不寄信，照現在的 `find_daemon`（`$AOS_DAEMON`，再來 cwd 的 `./.stack`）算出 `<那台>/procs_state.json`。這時 daemon 就是 kernel，位址本來就給了。猜 `./.stack` 照留（使用者 11-12 裁：「1.留。」） |

**寄信的指令**（`aos-agent ctl add`／`rm`／`stop`／`start`／`sleep`／`wake`）——有設 `AOS_KERNEL` 時**只看那封請求自己的回信**（`applied: true` 或 `false`＋代號），不另外寄查詢信、不先讀表預查、不先核 daemon 活不活。寄出去之後背後是黑盒子；只會處理掛 proc、不答查詢信的 kernel 也照樣能用。排隊位置照舊看 `AOS_KERNEL` 旁邊的 `queue.json`。沒設 `AOS_KERNEL` 時行為跟現在一樣（預查、核活、對表都留著）。

其他：

- 查表時有設 `AOS_KERNEL` 卻問不到（沒回信）＝報 `KernelFailed`（`no reply from AOS_KERNEL=… within N s`），**不退回去直讀 `AOS_DAEMON`**（照傳但約定不用；退回＝繞過 kernel）。回信是 `applied: false`＝把那個代號與原因接進自己的錯誤行。人要直接看某台，用 `aos-daemon-ctl`。
- 讀表時把各列的相對路徑（`stack` 等）照表檔所在的資料夾解成絕對路徑再交出去（`py/daemon_ctl/table.py` 現在就會把路徑欄拼回絕對，只是基準從「daemon 的資料夾」改成「表檔所在的資料夾」）。用表的人一律拿絕對路徑，不必知道基準在哪。
- 等回信用的信箱：有 `AOS_STACK`＝`$AOS_STACK/daemon_reply/`（現在的）；沒有 `AOS_STACK`（人的殼）而有 `AOS_KERNEL`＝`$AOS_KERNEL/reply/`（跟問腦的共用回信信箱同一個擺法）。
- **記不記**（工具自己決定）：
  - `aos-agent`（一次性指令）：一次執行裡只問一次、記在行程內，不落檔。
  - `lib/agent/hooks.py` 的 `on_clock`（每拍都會被叫、`clock` 寫 proc 名時）：它真正要的是那個 proc 的鐘檔，不是整張表。第一次叫既有的 `aos-agent ctl ls --json` 找到那列的 `stack`，把算好的鐘檔路徑記在自己小格的 `on_clock.json`；之後每拍直接讀鐘檔，讀不到才重查一次。不用新的子命令，`hooks.py` 也不用自己會讀表。
- **不硬性依賴 symlink**：全程是「寄信→拿到一個普通路徑→讀檔」，沒有任何一步靠捷徑。

## 現況與要改的地方

小修線做完後的現況：daemon 對壞 body 回 `BodyBad`；`aos-daemon-ctl` 沒給 `--reply-to` 時帶共用回信信箱、收到拒信報代號；`aos-agent ctl who --json` 多一欄 `daemon`（這次讀的是哪台的表）；`fork`、`subagent` 不再自己讀 `AOS_DAEMON`，改用那一欄當基準——所以掛、停、收的信已經都寄 `AOS_KERNEL`，但**只設 `AOS_KERNEL`、沒有 `AOS_DAEMON` 還是 `DaemonMissing`**（讀表與放 stack 要知道那台）。小修線列了「仍需要 `AOS_DAEMON`（或 `./.stack`）的 9 處」，逐處對：

| # | 位置（小修線清單） | 現在用 daemon 做什麼 | 改不改 | 怎麼改／為什麼不改 |
|---|---|---|---|---|
| 1 | `cmd/aos-agent`：`common.py` 的 `daemon_path`／`need_table`／`table`、`daemon_up`；`ctl who`／`ls`／`state`／`where`、`phase_body` | 直接讀 daemon 的表、state 窗核活著沒 | **改** | 查表的經 `state_path()`；`phase_body` 的預查與 `daemon_up` 的核活，有 `AOS_KERNEL` 時不做（以回信為準） |
| 2 | `py/daemon_ctl/post.py` 的 `reply_box` | 沒有 `$AOS_STACK` 時回信信箱放 `<ctl 信箱>/reply/` | **改** | 沒 `AOS_STACK` 又有 `AOS_KERNEL` 時用 `$AOS_KERNEL/reply/` |
| 3 | `lib/agent/fork/_entry` | 分身 stack 放 `<daemon>/procs/<分身>/`；details 與失敗分身的路徑相對 daemon；之後叫 `aos-agent` 帶 `--daemon` 那台 | **改** | 基準從 `who --json` 的 `daemon` 欄改成**自己那一列的 `stack`**（已是絕對路徑）：分身放在自己 stack 的隔壁（同一個上層資料夾；預設佈局下就是現在的 `<daemon>/procs/<分身>/`），路徑寫絕對；叫 `aos-agent` 不再帶 `--daemon`（明給＝指名那台、會跳過 kernel）。理由：中間站換過表之後，`daemon` 欄會是中間站的資料夾，拿它放分身就放錯地方 |
| 4 | `lib/agent/subagent/_entry` | 帳上 stack 存相對 daemon 的路徑 | **改** | `subagents.json` 改存絕對路徑（對帳本來就是比表上那列的 stack）。**要重建什麼**：舊的 `subagents.json` 裡是相對路徑，不認；有子 agent 在跑的先收掉再升級，或刪掉那份帳 |
| 5 | `lib/agent/hooks.py`（clock 名字解析） | 讀 `$AOS_DAEMON/procs_state.json` 找那列的 clock | **改** | 照上面 `on_clock`：經 `aos-agent ctl ls --json`、記鐘檔路徑 |
| 6 | `lib/aos/promote/swap.py`（idle 判斷） | 沒給 `daemons` 時對 `$AOS_DAEMON` 跑 `aos-daemon-ctl ls --json` | 不改 | 它是指名 daemon 的工具（明給一串 daemon 逐台查），跟 `aos-daemon-ctl` 同類，有 Linux 權限就能用 |
| 7 | `templates/agent-fsm/wait.py` | 相對的 `$AOS_LLM_KERNEL` 從 `$AOS_DAEMON` 算 | 不改 | 只是算路徑的基準，不讀狀態、不寄請求 |
| 8 | `lib/aos/judge/_entry` | 下一站＝`$AOS_DAEMON` 的 ctl 信箱、數 running 讀它的表 | **改**（另一份） | 整支變成框架站（[01](01-框架零件.md)、[02](02-判官收編.md)）：可寫 `next`、`count_daemon`；沒寫時照舊用 `AOS_DAEMON`——它自己就是 kernel，讀下一站的表是它份內的事 |
| 9 | `py/aos_sweep_proc.py` | 清道夫認行程身分，比對 `/proc/<pid>/environ` 的 `AOS_DAEMON` | 不改 | 清道夫是跟著某台 daemon 的系統工具，不是一般 proc 讀狀態 |

| 位置 | 怎麼改 |
|---|---|
| `py/daemon_ctl/table.py` | `find_daemon` 不動（直寄工具、沒設 kernel 時還是用它）；新增 `state_path()`；讀表的幾處改成吃「表檔的路徑」（hook 換過的檔名不一定叫 `procs_state.json`），相對路徑照表檔所在夾解 |

| `aos-agent ctl who --json` 的 `daemon` 欄 | 留著，意思照字面「這次讀的那份表在哪個資料夾」；`fork`、`subagent` 不再用它 |
| `aos-daemon-ctl`、`aos-mailbox`、`aos-sweeper`、`aos-eca-screen`、`cmd/aos-agent/aos_agent/decl.py:92` | 不改：指名 daemon 的工具 |
| `lib/agent/agents_ctl`、`self_*`、`goal`、`clock_register`、`mailbox_send` | 不改程式：只叫 `aos-agent`／`aos-mailbox`、自己不讀 `AOS_DAEMON`（小修線已盤過）；`_tooldef.json` 的 `env` 說明補上 `AOS_KERNEL` |

做完之後：只設 `AOS_KERNEL`、沒有 `AOS_DAEMON` 的 proc，`fork`、`subagent`、`ctl` 全部能用。

錯誤代號：新增 `KernelFailed`（`aos-agent`、`py/daemon_ctl`）；其餘沿用 `StateMissing`、`StateBad`、`MailboxMissing`、`DaemonMissing`、下游回的 `BodyBad`。
