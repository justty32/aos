# 邊緣狀況清單：每條寫現有原則下的自然答案；全部推得出來，沒有新增方向題

← [kernel-framework](README.md)｜上一份 [05-施工步驟](05-施工步驟.md)

底下常用到的幾條：寄信不回＝這次呼叫失敗、寄件人自己算逾時（N-66）；不為邊緣狀況加機制、寫什麼就做什麼（C-56）；每層只管自己、只說自己的錯（C-52、C-53）；出錯時要能輕鬆回到原狀、錯誤路徑收斂（C-53 的 11-06 註）；非正規操作的風險使用者自擔（11-11）。

## 回信

| # | 狀況 | 自然答案 |
|---|---|---|
| 1 | 前站把回信位址改成自己（`reply_via_me`）之後，**前站當機** | 下游的回信寄進前站的 `replies/`，信留在那；前站重起後第一輪照 `forwarded.json` 代回（兩樣都在 stack 裡、重起不掉）。前站一直不回來＝原寄件人等到自己的逾時 |
| 2 | 同上，但當機的是**後站** | 信留在後站的 `requests/`（`new/` 或 `cur/`），後站重起接著做；沒等到＝寄件人逾時 |
| 3 | 前站的 stack 被整個清掉（`forwarded.json` 沒了） | 之後到的回信查不到對照＝一行 warning、收掉；寄件人逾時。不補救 |
| 4 | 回信先回我，下游回信到了，但**原寄件人已不在** | 代回前看原回信箱還在不在：不在＝warning、收掉、刪對照；還在＝寄進去，沒人收是寄件人那邊的事（共用回信信箱本來就會清十分鐘前的舊信） |
| 5 | 下游一直不回信（例：下游站睡著） | `forwarded.json` 那一列一直留著，不自動清；它是公開看得到的檔，人清或重建 stack。有 `reply_to` 才記表，所以只有「等回信卻等不到」的才會留 |
| 6 | 兩站（或更多）都開 `reply_via_me` | 回信一站一站代回，每站的 `before_reply` 各跑一次；每站只知道自己的上一個回信位址 |
| 7 | 前站開了 `reply_via_me`，後站想直接回原寄件人 | 做不到：後站看到的 `reply_to` 就是前站的 `replies/`（不記走過哪些站、不帶最初寄件人，已裁） |
| 8 | `before_reply` 的 hook 失敗 | `on_error: stop`（預設）＝這輪退 1，回信留在 `replies/` 下一輪重試；`continue`＝原內容照樣代回。拿來刪減內容的 hook 要用 `stop`，才不會失敗時把原內容漏出去 |

## 排隊與逾時

| # | 狀況 | 自然答案 |
|---|---|---|
| 9 | 信在某站排隊中，**寄件人已逾時、想撤信** | 信還在那站的 `new/`＝`aos-post regret` 撤得掉；已被認領進 `cur/`（排隊中）＝撤不掉，靠信裡的 `queue_wait_ms` 到期由那站自己拒掉（現在的做法）。沒帶期限的（`--on-queued ok`）會一直排（11-07 已裁） |
| 10 | 鏈上**兩站都排隊** | `queue_wait_ms` 原樣往下帶，每站從自己收到的信封 `sent_at`（＝前站轉寄的時刻）起算，所以兩站加起來可能排得比寄件人肯等的久；寄件人等滿就當失敗，之後仍可能被掛上（跟現有「逾時後可能仍被掛上」是同一個已知限制）。不改 body 裡的數字、不加機制 |
| 11 | **在飛的不算 running**（轉了、那台還沒套） | 照舊是已知限制：連著很快寄好幾封可能多放幾個；`count_daemon` 另指、中間隔越多站越明顯。站當 daemon 身體而且下一站就是自己時沒這問題 |
| 12 | **數量另指的那台 daemon 不在** | `count_daemon` 不是資料夾＝設定指錯，這輪 `DaemonMissing` 退 1（信留著，修好接著做）。資料夾在但那台沒在跑＝照表上寫的數（站不查別人活不活）；表是舊的就可能一直算滿，人去修 |
| 13 | 站被 daemon **重起**時，排隊中的信 | 信在 `requests/cur/`、隊序在 `queue.json`，都在 stack 裡：重起後照原隊序接著排，`queued_at` 不變。`queue.json` 壞了＝當空窗、照 `cur/` 的處理順序重排（現在的做法） |
| 14 | 站重起時，**已轉寄、還沒收掉原信** | 下一輪防重（`forwarded.json` 有記、或下一站信箱還有同名信）認出來、收掉原信。剩一個窗口：沒開 `reply_via_me`、下一站已經做完並移走那封、站才重起＝可能再轉一次（`procs_added` 重套＝換同一份設定，無害；現有已知限制） |
| 15 | 整棵樹凍住搬家 | 期限是牆鐘，醒來已過期的排隊信一起拒（11-07 已裁）；`forwarded.json` 裡的原回信箱是絕對路徑，搬家後對不上＝照第 4 條丟掉，在飛的請求作廢重寄（跟 N-63 的 11-06 註同一個態度） |
| 16 | 下一站的信箱還沒建（下一站還沒起） | 這封拒 `ForwardFailed`（不是沒格，所以開了排隊也不排）；寄件人重試 |

## hook

| # | 狀況 | 自然答案 |
|---|---|---|
| 17 | **hook 逾時或出錯**時信怎麼辦 | 逾時＝失敗的一種（整群收掉）。`on_error: stop`＝這輪印 `HookFailed`、退 1，信留在 `cur/` 下一輪從頭再來；`continue`＝warning、當沒這個 hook 繼續判。`async` 的不知道它成不成 |
| 18 | `stop` 的 hook 一直壞 | 每輪到那封就退 1，後面的信都被擋住——這就是 `stop` 的字面意思；人修 hook 或改成 `continue`。當 daemon 身體時 daemon 不會因此停（記一行、下一圈再跑，N-28 現有行為） |
| 19 | hook 跑過了、站在收掉信之前死掉 | 下一輪那封還在 `cur/`、又不在 `queue.json`，當新信、hook 再跑一次。hook 有副作用的自己處理重複 |
| 20 | hook 把 body 改壞 | 之後內建規則照改過的 body 判（可能拒 `BodyBad`），或原樣轉給下游、由下游說壞。寫 hook 的人自擔 |
| 21 | `after_verdict` 把「拒」翻成「放行」，但格已滿 | 照轉，running 會超過 `max_running`（寫什麼就做什麼）；自擔 |
| 22 | hook 當 daemon 身體時很慢 | 那台 daemon 整圈等它（「等他，如果不想等，那就hook那邊走async」，已裁） |
| 23 | `before_verdict` 對 `ping`、查詢信也會跑 | 會，每封新信都跑；handler 自己看 body 決定管不管 |

## 壞信與繞圈

| # | 狀況 | 自然答案 |
|---|---|---|
| 24 | **壞信在中間站** | 信封壞（讀不出來）＝在哪站壞就在哪站丟、一行 warning、不回（讀不到 `reply_to`）。body：中間站只驗自己規則要看的那幾欄（不合拒 `BodyBad`），其餘不替下游驗、原樣轉 |
| 25 | **壞信在最底** | daemon 驗完整的 body，壞＝回 `applied:false`＋原因（另一條線在做）；回信照 `reply_to` 直接回或經前站代回。中間站不把下游的拒信換成自己的代號 |
| 26 | **同一封信繞回自己**：`next` 設成自己的 `requests/` | 設定檢查時就擋：`CfgBad` |
| 27 | 兩站互指成環（A→B→A） | 不偵測（不記走過哪些站，已裁）。信會一直在兩站之間跳，每輪一跳；看得到（兩邊 stderr、信箱）；設定的人自擔，改掉 `next` 就停 |
| 28 | 一封信同時帶好幾種 key（`procs_added`＋`ping`＋`procs_state_path`） | 規則只看 `procs_*` 那幾個；整封一起轉、最底一封信一封回信 |
| 29 | 同一個 `requests/` 被兩個身體同時跑（掛了兩份） | 認領是原子的，各搶各的信；`queue.json` 互相蓋。設定錯，自擔 |

## 查詢信

| # | 狀況 | 自然答案 |
|---|---|---|
| 30 | 查詢信經過會**改路徑的 hook，改出來的路徑讀不到** | 工具讀那份檔時報自己的錯（檔不在＝`StateMissing`、讀不懂＝`StateBad`），不回頭去猜 `AOS_DAEMON`。hook 自己失敗看第 8 條 |
| 31 | 設了 `AOS_KERNEL`，但那邊沒人回查詢信（站沒在跑、或手寫的 kernel 不答） | 工具等 3 秒報 `KernelFailed`，不退回直讀 `AOS_DAEMON`。不給看也是一種管理；kernel 睡著是設計系統的人要管的風險（11-07）。人要直接看用 `aos-daemon-ctl` |
| 32 | 工具記住了問來的路徑，後來那台搬家或換台 | 記不記是工具自己的事：`aos-agent` 不落檔，沒這問題；`on_clock` 讀不到時重問一次 |
| 33 | 手寫的 kernel 會把請求分到不同 daemon，查詢信該回哪台 | 它自己決定回哪份（或合成一份）；框架站只有一個 `next`，沒這問題 |
| 34 | 人的殼只有 `AOS_KERNEL`（沒有 `AOS_STACK`、`AOS_DAEMON`） | 等回信的信箱用 `$AOS_KERNEL/reply/`；那裡沒有寫入權限＝工具自己的錯 |

## 不在這份範圍

寄信（mailbox）與時鐘算不算資源、要不要過 kernel：使用者沒回，照他的通則不追問、不設計。沙箱與權限以 Linux 為保底，不另設計權限系統。
