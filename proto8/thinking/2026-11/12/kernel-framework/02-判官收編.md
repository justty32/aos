# 判官怎麼收進框架：功能逐項對到零件、改名清單、範本與試驗場怎麼跟著改

← [kernel-framework](README.md)｜上一份 [01-框架零件](01-框架零件.md)｜下一份 [03-狀態查詢信](03-狀態查詢信.md)

結論：判官不是另外留一支，`lib/aos/judge` 直接改成 `lib/aos/kernel`。判官現有的功能一項不少，只是變成「框架站開了規則」的一種設定。proto8 不做舊版相容、不留舊名（使用者 11-05「一律當成沒有舊版」）。

## 功能逐項對零件

| 判官現在的功能（`lib/aos/judge/_entry`） | 收進哪個零件 | 有沒有變 |
|---|---|---|
| 收 `$AOS_STACK/requests/`、每輪 take-all、照處理順序逐封 | 收信 | 不變 |
| `allowed` 白名單（`procs_added`） | 規則 | 不變 |
| `max_running`（含 `procs_started`／`procs_woken` 算新名字） | 規則＋數量另指 | 多一個 `count_daemon`；沒寫 `next` 時跟現在一樣數 `AOS_DAEMON` |
| body 形狀不對拒 `BodyBad` | 規則 | 只在寫了規則時驗 |
| `ping`、其他 `procs_*`、不認的 key 原樣轉 | 下一站 | 不變 |
| 放行＝body 原樣、同信名轉進 `$AOS_DAEMON` 的 ctl 信箱 | 下一站 | 去處可用 `next` 改；沒寫＝跟現在一樣 |
| 防重（看 ctl 信箱 `new/`、`cur/` 同名信，或有序對照表） | 下一站 | 多看 `forwarded.json` |
| `reply_to` 照原樣帶（daemon 直接回原寄件人） | 回信（`reply_via_me: false`） | 不變 |
| `keep_ordered`＋`judge_replies/`＋`judge_ordered.json` 代回有序信 | 回信（`reply_via_me: true`） | 代回變成所有信都能用；`keep_ordered: true` 要同時寫 `reply_via_me: true` |
| 不掛＝回 `applied: false`＋stderr 一行 warning | 回信（拒信） | 前綴 `judge:` 變 `kernel:` |
| `queue`、`queue.json`、先來先掛、隊首擋後面 | 排隊 | 不變（列多一個選填 `body`） |
| `queue_wait_ms`（寄件人期限，到期 `SlotMissing`） | 排隊 | 不變 |
| ctl 信箱位置讀 `procs_state.json` 的 `procs_requests` | 下一站（沒寫 `next` 時） | 不變 |
| 自己的錯九個代號、拒信四個代號 | 錯誤代號總表 | 各多一個（`HookFailed`、`HookRejected`） |
| 兩種擺法（daemon 身體、loop proc） | 形式 | 不變 |
| 已知限制：在飛的不算 running；daemon 做完才重起時無序信可能重寄 | 照留 | 開 `reply_via_me` 後有 `reply_to` 的信多了 `forwarded.json` 當防重依據，窗口變小 |

判官沒有、框架新加的：`next`、`count_daemon`、`reply_via_me`（泛化）、hook 三個時機、設定檔可寫指示詞。

## 改名清單（同一個 commit 換完，舊名不認）

| 舊 | 新 |
|---|---|
| `lib/aos/judge/` | `lib/aos/kernel/` |
| `judge.json` | `kernel.json` |
| `$AOS_STACK/judge_replies/` | `$AOS_STACK/replies/` |

| `tests/test_judge.py` | `tests/test_kernel.py` |

「判官」這個中文詞在現行說明文件裡改叫「通用 kernel 的站」（簡稱框架站）；舊的 thinking 記錄照慣例不改。順帶好處：`templates/judge-llm`（比對產出的裁判函數，跟 kernel 無關）跟它的 `judge.json` 不再跟 kernel 這邊撞名。

**要重建什麼**：正在跑的判官，重起前把 stack 裡的 `judge_replies/`、`judge_ordered.json` 刪掉（新程式不認；當時在飛、等代回的有序信作廢，寄件人等到逾時重寄）。`queue.json`、`requests/` 形狀沒變，不用動。

## 遷移步驟

1. 抽出 `lib/hook_run.py`（跑一個 handler、解回話），`lib/agent/hooks.py` 改用它，行為不變。框架在中層 lib，照 [lib 分層](../../../../lib/docs/01-分層等.md)不能 import 高層的 `lib/agent`，所以共用的部分放到最底。
2. `lib/aos/judge` → `lib/aos/kernel`：照上表改名，拆成 `_entry`＋三個模組，加 `next`、`count_daemon`、設定過 aos-directive。原本 142 行的測試改名後要全過。
3. 同一個 commit 改掉所有引用（下一節）。
4. 加 `reply_via_me`，再加 hook 三時機（各自一個 commit，見 [05](05-施工步驟.md)）。

## 試驗場三層

現況：根 daemon 掛 `_clock`、`switchboard`（問腦總機那台）、`foreman`（領班那台，下面是 agent）、`_sweeper`；**沒有判官、全樹不設 `AOS_KERNEL`**，所以 agent 的掛 proc 信一直是直寄領班那台。

- **遷移本身不用動試驗場**：它沒用到 `lib/aos/judge`。
- **跟進（放在最後一步、可不做）**：讓試驗場真的走「一律寄 `AOS_KERNEL`」——

| 層 | 改什麼 |
|---|---|
| 根 | 不動 |
| 總機（`switchboard`） | 不動；`AOS_LLM_KERNEL` 照舊另一個變數 |
| 領班（`foreman`） | 這台 daemon 的身體改成框架站（繼承式）：`daemon.json` 加 `exec` 指 `lib/aos/kernel`＋一份 `kernel.json`（先寫 `{"max_running": N, "queue": true}`）；它的 `.env` 寫 `AOS_KERNEL=<領班 stack>/requests`，底下的 agent（fsm_ann、eca_bob、eca_cody）就一律寄那裡 |
| 人的殼（`env.sh`） | 拿掉 `unset AOS_KERNEL`，改成設 `AOS_KERNEL` 指領班的 `requests`；要直接碰某台 daemon 照舊用 `aos-daemon-ctl` |

repo 裡對應的範本 `templates/daemon-root` 同樣可選加一個帶框架站的領班例子，跟試驗場那步一起做。
