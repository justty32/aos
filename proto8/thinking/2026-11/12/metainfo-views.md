## 使用者裁定（11-12 晚）

原話（同一則訊息回了好幾題，整段照錄；`$ref`、kernel、linux user、遊樂場那幾句是別的線的，這裡只記不處理）：

### 對[未定](#未定要使用者定)五題各裁了什麼

| 題 | 原話 | 裁定 |
|---|---|---|
| 1 執行類的格算觀點還是規則 | 「當然，全都是觀點，全都是參考用，出事了自行負責。」 | 全是觀點、參考用（題 1 的 (c) 那個方向）。`timeout_ms`、`sandbox`、`side_effect`、`cost` 都不是規則，也不是安全邊界。隊長原本建議 (a) 當規則、壞了擋下——被翻。 |
| 2 `_index` 與 `_metainfo` 靠不靠攏 | 「_index的obj內要不要再多塞東西...可以，想塞啥塞啥，出事了自己負責。」「_metainfo不算index，_metainfo他是描述自身節點的一個子節點，可以塞任何東西來描述自身，因爲index也是一種描述自身的東西，所以也可以塞入其中。」 | index 的一項裡除了 `description`、`index` 還想放什麼都可以，後果自負。`_metainfo` 是節點描述自己的子節點、什麼都能放；index 是能放進去的其中一種，`_metainfo` 本身不是 index。結論一的讀法乙（`_metainfo` 就是一種 index）不成立。 |
| 3 主觀的 metainfo 放哪 | 「主觀的metainfo的位置也不規定。」 | 不規定、不給推薦位置。整理法三（寫進工具登記檔）不做。 |

### 推出的後果（已落實的）

**一、執行的程式拿通用那份當參考值照著用，它不是保證。** act、aos-mcp 照 `timeout_ms` 到了就殺、aos-mcp 把 `side_effect`／`idempotent`／`resource` 換成 MCP 提示、shell 帳看 `arbitrary_exec`——這些照舊，只是地位講明：是照著一份公開的聲稱做事，聲稱寫錯、寫壞、被有權限的人改掉，程式不替你把關。真要擋得靠別層：linux 的資源上限與檔案權限、由起 proc 的那一層套沙箱（[C-64](../../../docs/CONCEPTS/01-設計理念/05-布局成長與檔案權限.md)；跟 [kernel-as-bridge](kernel-as-bridge/README.md)「每一層的硬體是上一層」接得上，那題的結論不在這裡下）。

**二、壞掉的 `_metainfo`、壞掉的格＝當沒寫：略過、提醒一句、不擋（使用者已確認）。** 頂層拿這點回去問：「壞掉的 `_metainfo` 從『擋下』改成『略過』，對嗎？也就是工具的 timeout 或花費上限寫壞時，不再報錯擋住，工具照跑；代價是那一次可能沒有 timeout。」使用者（11-12 晚）：

> 「對，略過，出事自己負責」

跟下午「_metainfo.json 壞掉時，index_view 對那個資料夾不該直接報錯。」同一條，現在所有讀法一致。[codebase-cleanup 待裁 1](codebase-cleanup/README.md#待使用者裁) 與 [thinking-to-docs U7](thinking-to-docs/README.md) 就此結案＝(b) 略過。略過之後各執行點實際用的值：

| 讀的地方 | 壞了之後 | 之前 |
|---|---|---|
| `lib/metainfo.py`（共用讀法：`read`、`timeout_ms`、`eval_cost`） | 回「沒有」，略過了什麼寫進呼叫者給的 `notes` | 丟 `FileBad`／`CalBad` |
| act 格（`templates/agent-fsm/act.py`） | 那支工具**不設上限**（跟沒寫 `timeout_ms` 一樣），stderr 提醒一行，照跑 | 整格停 |
| aos-mcp | 那支工具用 aos-mcp 的**預設逾時**（60 秒，或 `--timeout-s` 給的），stderr 提醒一行 | 整台 `ToolsBad` |
| `mcp_tool`（外部 MCP 的包檔那格） | 用預設 60000 毫秒，stderr 提醒一行 | `PackBad` |
| `metainfo_check`（審視工具） | 壞的那個宣稱當沒宣稱（`unclaimed`），輸出多一個 `notes` 寫明略過了什麼 | `FileBad`／`CalBad` |
| aos-sandbox（`sandbox` 那格；使用者另裁「甲，出事自己負責」，見代定第 1 點） | 不套沙箱、直接跑 prog，stderr 提醒一行 | `CfgBad` 不跑 |
| aos-tools、`tool_io`、`tools_def`、`aos_index`、`defs/catalog` | 本來就略過，不變 | — |

**三、現在沒有程式讀主觀那份。** 位置不規定＝跟主觀的 index 一樣，程式不會自己去找；`index_view` 有 `index` 參數讓讀的人指定，`_metainfo` 的特性沒有對應的管道。要讓執行的程式照某一份主觀的跑（呼叫者指定看哪份：整理法三、題 1 的 (d)），得另開管道——他沒講要，沒做，列在未定。

**四、`_index` 的一項多放東西：程式本來就容得下，沒改。** `index_view`（`lib/aos_index.py`）只看每項的 `description` 與 `index` 兩格，各有各的形狀檢查；其他鍵不讀、不檢查、不報錯，也不印（代定：不印、也不提示有額外欄位，要看就 `json_get`）。補了一個測試釘住。

**五、`_metainfo` 什麼都能放：程式本來就容得下，沒改。** 各讀法只取自己認得的格，不認得的不管（C-48）；`_metainfo` 裡的 `index`、`tooldef` 照舊能用。

### 代定（可翻案；第 1 點已被使用者翻案並落實）

- **aos-sandbox 的設定壞了照舊報錯、不放行——使用者翻案。** 原本代定的理由：它讀的是 `_entry` 明寫指給它的那一處，略過＝不關沙箱照跑不是裁定必然推出的。對讀的人指出這跟「`sandbox` 也是觀點」相碰（設定就放在 `_metainfo.json#/sandbox`）。頂層拿去問：沙箱設定寫壞時，甲 也略過、不關沙箱照跑、跟其他格一致／乙 只有沙箱例外、壞了不讓跑。使用者（11-12 晚）：

  > 「甲，出事自己負責」

  已落實，張力已解：aos-sandbox 遇到壞的設定＝當沒寫，不套沙箱、直接跑 prog，stderr 一行 `aos-sandbox: warning: sandbox config ignored, running unsandboxed: 原因`。各種「壞」怎麼算：

  | 情形 | 現在 |
  |---|---|
  | 檔讀不了、不是 JSON、指到的不是物件、`#` 後面不是 `/` | 略過＋warning、不套沙箱照跑 |
  | 某個 key 型別不對（`net`、上限、`user`、`base`／`ro`／`rw`／`commands`／`env`） | 同上（整份設定略過，不是只略過那一格） |
  | 裡面有 `$ref`、`$env` 指的變數沒設 | 同上（代定：算設定讀不出來） |
  | 設定不在：檔不在、`#/` 指不到（沒有 `sandbox` 這格） | 照舊 `CfgMissing` 報錯 |
  | 環境做不到：列的路徑不在（`PathMissing`）、bwrap／s6／`commands` 列的指令不在（`CommandMissing`）、要換身分不是 root（`UserBad`） | 照舊報錯（推不出來，見下） |
  | bwrap 起來之後自己失敗（例：機器不准開 user namespace） | 照舊：那是 bwrap 的結束碼，aos-sandbox 已經 exec 走了、接不到 |

  分法是「設定讀不出來或形狀不對＝觀點壞了＝略過」對「設定讀得懂、環境做不到＝不是設定壞」。後一種原話推不出來（明確要沙箱而機器做不到，是照跑還是不跑），維持報錯、列給頂層問。
- **某個 key 壞了是整份設定略過**，不是只略過那一格：照原話「不關沙箱照跑」；只丟掉一格（例如壞的 `ro`）會變成一個跟設定寫的不一樣的沙箱。
- **設定壞了、prog 又不在 PATH 上**＝`CommandMissing`（沒東西可跑）。
- **提醒印在 stderr、一支工具一行**，不進工具的結果。
- **`index_view` 不印一項裡多出來的鍵**（見上第四點）。
- **`metainfo_check` 多一個 `notes` 鍵**（有略過才出現）：不然審視的人看到 `unclaimed` 分不出是沒寫還是寫壞。

### 原話讀法上的疑義（照列，沒有自己選邊的地方照最小的做）

1. **「_index的obj內」的 obj 指哪個物件**：讀成 index 一項的值（`{"description": …}` 那個物件，原話四「obj裡面以後不只會有純文字description」）。若他指整份 `_index` 物件的頂層，現在的程式會把多出來的頂層鍵當成一項、印出鍵名（不報錯）。
2. **通用與主觀現在用什麼分**：之前用位置分（天然位置那份＝通用、自己存的＝主觀），這次用「非私有／私有」分。現況兩種分法重合；agent 放在別處、但別人讀得到的看法算哪邊，照這次的字面是通用視角（公開給別人的聲稱）。條文兩句都寫、沒有替他二選一。
3. **「全都是觀點」有沒有包含「主觀蓋過去就算數」**：題 1 的 (c) 原文有後半句「主觀蓋過去就算數」。他只說全是觀點、參考用，加上主觀的位置不規定；沒說執行的程式要去讀主觀那份。所以只落實前半（地位與壞了略過），後半留在未定 1。

## 結論一：index 那套講的是什麼（一句一個出處，原話編號照 [index](index.md)）

| 層 | 指什麼 | 誰寫、放哪 | 誰說了算、要不要規定 | 出處 |
|---|---|---|---|---|
| 客觀 | 東西本身：節點的值、底下實際有什麼 | 沒有人寫，用 `ls`／`json_ls` 看 | 它自己；不用規定 | 原話四「yyy這個節點的值客觀上可能是任何json value」；原話九「如果想要真正客觀，那就乖乖用shell ls或是aos json ls」 |
| 通用觀點 | 天然位置（被描述節點的上一層）那份 `_index`，各 agent 共用 | 有權限的誰都能寫；格式與位置有規定 | 沒指定就看它；改它不用明講、風險自負 | 原話六「在沒有指定位置的時候…去看其上方節點的index」；原話九「天然位置的話就是適用於各agent的通用視角」；「改通用視角這塊就是有權限就能改，不用明講，風險自己承擔。…沒指定的話就預設用通用視角」 |
| 主觀 | 某個 agent 自己對節點的看法（含它的 cache） | agent 自己寫，放哪不規定 | 看的時候自己指定；指定的蓋過天然的；不規定 | 原話七「agent自己存的則是主觀」；原話八「agent自己要記錄自己的主觀的東西，就自己想想要放哪，我們不規定」；「指定的那一份有的，會覆蓋掉天然那份。」 |

- description 也是觀點不是事實：原話四「description，就是讓agent能在主觀上對yyy這個節點(含其值)有所理解」。
- 過時怎麼辦：未定（[index 未定](index.md#未定之後再說)「index 過時（節點已不在）怎麼辦」）；只有原話六提過 cache「可以定期更新，或是在存取該節點的時候看看其index，再決定要不要更新」。
- 同一節點多處有 index 時聽誰的：只定了「指定的蓋過天然的」，其餘未定。

**兩處模糊，照原話各列兩種讀法：**

1. 「客觀」這個詞。原話七：「放在天然位置的index，其實會是所謂的客觀index」；原話八同樣說「客觀index是這樣」；原話九改說天然位置那份是「通用視角」、真正客觀要 `ls`。
   - 讀法 A（三層）：客觀＝東西本身、通用觀點＝天然位置那份、主觀＝自己的；原話七的「客觀index」是通用那份的早先叫法。這次原話三個詞並列，[index 的決定](index.md#決定)也寫「以此為準」，本檔照 A 往下做。
   - 讀法 B（兩層）：客觀＝天然位置那份，「通用觀點」是它的別名，主觀＝自己的。
   - 對 `_metainfo` 的差別：B 之下定義旁邊那份 `_metainfo` 就是「客觀的」，程式照它執行、壞了擋下都理所當然；A 之下它只是通用觀點，實測可以推翻它、壞了可以略過。
2. 「metainfo其實也是一樣」。
   - 讀法甲：`_metainfo` 的內容也分得出這三層（本檔結論二）。
   - 讀法乙：`_metainfo` 這個檔本身就是一種 index／description（通用觀點那一層的東西），該跟 `_index` 當同一類處理（本檔結論四的整理法二）。

## 結論二：套到 `_metainfo`——順

**三層各對到什麼：**

- **客觀**＝函數實際怎麼跑：`_entry` 的實作與當下那一次執行。量到的那本帳 `observed.jsonl`（N-68「他見」）最靠近客觀，但它是過去的統計，工具改版或輸入規模變了一樣會過時（Argon 指出，同意）。
- **通用觀點**＝定義旁邊那份（資料夾的 `_metainfo.json`、json 物件的 `_metainfo` 鍵，以及獨立的 `_tooldef`、`_index`）：設計者寫、大家共用、沒指定就看它。
- **主觀**＝某個 agent／讀者自己對這個函數的看法：N-68 的「agent 自報的估值」、呼叫者自己想等多久、評分者給的 `comfort`。

所以 `_metainfo` 整份本來就不是客觀，是「宣稱」。N-68 早就寫了同一件事：「`cost` 是函數自己宣稱、估的」「設計者寫的估值與 agent 自報的估值要分清」「實測不回寫」。這次等於把 N-68 的三個詞跟 index 的三個詞對上。

**現有內容逐類看**（實掃 80 份 `_metainfo.json`：`summary` 80、九軸各 75～78、`cost` 68、`timeout_ms` 60、`arbitrary_exec` 25、`sandbox` 1、`tooldef` 1；`comfort`、`index` 條文有、現有檔沒人寫）：

| 類 | 哪幾格 | 照這套看 | 主觀那份蓋過去的後果 |
|---|---|---|---|
| 說明類 | `summary`、`tooldef.description`、`index`、`comfort` | 純觀點，完全套得上 | 只影響讀的人自己怎麼理解 |
| 宣稱類 | 九軸（`side_effect`、`idempotent`、`deterministic`、`resource`、`interrupt`、`parallel`）、`cost`、`arbitrary_exec`、`tooldef.parameters` | 設計者對事實的宣稱；客觀答案在程式與實測 | 讀者自己判斷錯；`parameters` 寫錯＝腦給錯參數 |
| 執行類 | `timeout_ms`（act、aos-mcp 到了就殺）、`sandbox`（aos-sandbox 照它關）；宣稱類裡被程式拿去做決定的 `side_effect`／`idempotent`（aos-mcp 轉成 MCP 的唯讀／冪等提示）、`arbitrary_exec`（shell 帳） | 不是描述，是被照著執行的規則 | 有安全與預算後果，見結論三第 2 點 |

**今天下午已裁的四條，在這套下怎麼讀：**

- **裡外都認、外面贏**：「裡」（`_metainfo` 裡的格）與「外」（獨立的 `_tooldef`、`_index`）都在同一個節點旁邊，都屬通用觀點那一層；這條是同一層裡兩種擺法的合併規則，不是通用對主觀的規則。跟「指定的蓋過天然的」可以排成一條線：`_metainfo` 裡的 < 獨立那份 < 讀者指定的（`index_view` 的三層就是這樣）。順。用詞要小心：這裡的「外面」＝獨立檔，跟「裝不下的節點寫在外面（上一層）」不是同一個外面。
- **壞掉不報錯**：觀點壞了就當沒有這份觀點，退回去看別份或看東西本身。順。執行類那幾格壞了算不算「觀點壞了」，就是待裁 1／U7（結論三第 3 點）。
- **只有 `{}` 也算定義**：`_metainfo.json` 在不在是客觀的記號（這是一個定義），裡面寫什麼才是觀點。讀得通，但有一個邊角：agent 在普通資料夾的天然位置放一份寫了 `summary` 的 `_metainfo.json`，在 defs 根底下會被當成定義（只有 `tooldef`／`index` 的不會）。
- **只活在概念與規範、不做單一程式**：觀點本來就沒有中央裁判，各讀者自己決定看哪份。最順的一條；「主觀的放哪不規定」直接沿用，不需要新程式。代價是各工具認不認「指定另一份」不會一致。

## 結論三：邊緣狀況

1. **三份都在時誰贏。** 現有三條規則：同一節點「獨立檔贏 `_metainfo` 裡的」；跨層「讀者指定的贏天然的」；N-68「要拿估值排程、挑目標時，被評為不準的宣稱改用實測的中位數」。前兩條同方向（越靠讀者越贏）；第三條是客觀贏通用，只管 `cost`、只在被評為不準時。index 那邊沒有對應第三條的東西（index 過時未定）。沒有衝突，但「主觀 vs 實測」誰贏沒人說過。
2. **執行類的格能不能是主觀的。** 後果：自己把 `timeout_ms` 寫長（或拿掉——act 沒寫＝不設上限）＝卡住的工具不會被殺、整輪卡住；寫短只傷自己。`cost` 自報寫小＝之後的額度閘門（[LLM kernel `_metainfo` 第二步](../../../../wf/session_logs/2026-10-parts/12-10-24.md#llm-kernel-下一步從-session-log-逐字搬來)的 `llm_tokens` 預估額度）如果看的是自報那份就被騙過。`sandbox` 拿掉＝出沙箱。`side_effect` 寫 false＝MCP 那頭當唯讀、可能不再問人。
   - **讀的人有兩種**（Argon 指出，同意）：腦（讀 `tooldef`、說明來選工具、給參數）與執行的程式（act、aos-mcp、aos-sandbox 照 `timeout_ms`、`sandbox` 管執行）。腦讀主觀的沒事；題目只在「執行的程式聽不聽呼叫者自己帶來的那份」。
   - **檔案權限只在「不准」時才是防線**：多數 agent 對公用工具夾唯讀、對自己的檔可寫。不准主觀蓋過時，要改規則就得寫得到定義夾（「改通用視角有權限就能改、風險自己承擔」已裁，這條路本來就開著）；一旦准，唯讀的 agent 不必碰公用檔，寫自己那份就能放寬 timeout、拿掉沙箱、跳過批准（Argon 指出，同意；本檔初稿寫「防線是權限不是規則」只對一半）。
   - **蓋的粒度**：今天的合併規則是「一層、同名整個換」。主觀那份只寫半套 `sandbox` 就會把通用那份整塊換掉（Argon 指出，同意）。
   - 現況：沒有任何程式讀主觀的 metainfo，所以今天行為上＝「不准」。
3. **壞掉。** 現在六處讀 `_metainfo`：`lib/metainfo.py`（特性；act、aos-mcp、`metainfo_check` 經它）遇壞報 `FileBad`／`CalBad`，act 整格停、aos-mcp 報 `ToolsBad`；另外五處（aos-tools、`tool_io`、`tools_def`、`aos_index`、`defs/catalog`）略過。照這套有兩種說法，就是[待裁 1](codebase-cleanup/README.md#待使用者裁)／U7 的 (a)(b)：(a)「觀點壞了略過、規則壞了擋下」——`timeout_ms` 是規則，壞了不該悄悄變成不設上限；(b)「全都只是參考」（10-24 原話「kernel也可以透過這個，來做參考」）——壞了一律略過。這題的答案跟第 2 點同一個：把執行類當規則就 (a)，當觀點就 (b)。
4. **過時、指不到。** 通用那份過時今天就有（改了程式沒改 `tooldef`＝腦給錯參數），不是新問題。主觀那份更容易過時（沒人替它維護），跟 index 過時是同一題、同樣未定。主觀那份的鍵寫路徑，工具搬家後變孤兒；照「沒列到的就不管」的精神，指不到＝當沒說。
5. **fork、subagent、封存。** 通用那份跟著定義夾走，沒問題。主觀那份「放哪不規定」：放在 agent 自己夾裡就會跟著 fork 抄走；裡面寫相對路徑的照同像規則從容器算、抄走後還對得上，寫絕對路徑的會指回舊樹的工具。subagent 是另一個身，不會自動拿到父的主觀看法。封存時留在 agent 夾裡、跟著進封存。
6. **腦看到的說明以哪份為準。** 現在腦只看到合併後的 tooldef（`_metainfo.tooldef` 疊上獨立的 `_tooldef`），特性看不到（N-69「模型看不到」）。`summary`（給人與審視者）跟 `tooldef.description`（給腦）是兩個讀者的兩句話，可以講得不一樣，沒有人比對。agent 自己對工具的主觀說明目前沒有通道給腦——最接近的現成東西是每隻 agent 自己的工具登記檔（`tools.json`，可 `$override` 定義那份、後面贏），但登記格只帶 `path`、`env`、`env_file`，不帶說明與特性。
7. **`comfort` 已經是「把多份主觀寫進通用那份」的先例**（`ai_by` 按評分者分），跟「跑的時候誰都不改 `_metainfo`」並存靠的是「他見的舒適度不回寫」。主觀的 metainfo 若也想寫回定義旁那份，會撞這條。
8. **一份通用的被很多 agent 共用**：`lib/` 的工具被所有 agent 用，某一隻改了它的 `timeout_ms`，影響全部。index 的同一條（風險自負）後果只是看錯，這裡是行為變。

## 結論四：`_index` 與 `_metainfo` 的關係、看得到的整理法

兩者方向不同：`_metainfo` 是節點**講自己**（放在節點裡），index 是上一層**講孩子**（放在上一層）；`_metainfo.index` 講的是自己的孩子。index 一項的值是物件，原話四「之所以用json obj，是因為obj裡面以後不只會有純文字description」。

| 整理法 | 小例子 | 對條文與六處讀法 | 好處 | 代價 |
|---|---|---|---|---|
| 一、只換說法（現況不動） | 檔都不變；條文多一段：「定義旁那份＝通用觀點、實測帳＝客觀、agent 自己的看法放哪不規定」 | N-69 補一段、N-68 補一句對照、C-88 補一句；程式 0 檔 | 最小；不違反今天任何一條裁定 | 主觀的 metainfo 沒有程式讀，只是一個說法 |
| 二、index 的一項＝上一層對那個節點的 metainfo | `tools/_index.json`：`{"mul": {"description": "乘法", "timeout_ms": 2000}}`；agent 的主觀版本就是它自己那份 index 裡的那一項 | 格式今天就合法（不認得的鍵忽略），只定寫法：N-69、C-88、knowledge/docs/01 各一句、程式 0 檔。要讓 act、aos-mcp 真的照它殺：只改 aos-tools 一處（兩者都是經 `aos-tools ls --json` 拿特性）＋測試 | 裝不下 `_metainfo` 的節點（可執行檔、陣列、別人的 json）第一次有地方寫特性；主觀的不用新格式；最貼「不只 description」 | `timeout_ms` 的來源多一處，「上一層講的」與「節點自己講的」誰贏要定；跟「description 先不寫進 `_metainfo`」方向相反（那邊是往裡收、這邊是往 index 放） |
| 三、主觀的寫進 agent 自己的工具登記檔 | `tools.json`：`{"$override": "定義/tools.json", "tools": {"mul": {"metainfo": {"timeout_ms": 500}, "tooldef": {"description": "我的筆記"}}}}` | aos-tools 一檔（登記格多兩欄、照現成的後面贏合併）、它的 README、N-69／P-41 各一句；act、aos-mcp 不用改 | 沿用現成的 `$override`；每隻 agent 一份、跟著 fork 走；腦看得到自己的筆記 | 只管得到登記成工具的函數；等於規定了主觀的放哪（原話八是「不規定」）；執行類的格因此真的能被主觀蓋過 |
