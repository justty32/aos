## 使用者原話（11-12 晚，逐字）

> 「然後是kernel這塊我也有新的想法，就是說，我一直說kernel負責排程和資源分配，後來發現linux kernel這個最通用的kernel，他的核心功能其實是作業系統與硬體的橋梁，套用到我們這邊，首先是root daemon本身就是一個kernel，他的所謂硬體對象就是linux，那，如果root daemon底下掛了另一個daemon，那對這個子daemon來說，root daemon就是他的硬體，去幫我想想。」

同一則訊息開頭：「接下來我會輸出一連串想法，要麻煩你都派fable隊長。」結尾：「這些都可以讓argon幫忙」

## 結論

1. **套到現況是順的，而且幾乎不用動東西。** 它把使用者三句舊話（「daemon就像是硬體」「daemon所擔任的，就是橋梁」「其實daemon也算是一種kernel」）併成一句，新的只有「硬體是相對的：你的硬體＝你的上一層」。

2. **層次圖：**

   ```
   agent、工具            只看得到橋頭（AOS_KERNEL）
   ────────────────
   子 daemon（一座橋）     它的硬體＝根 daemon
     管它的事：起、關、重起、時鐘、環境 ──→ 跟根拿
     它做的事：開行程、讀寫檔、牆鐘、網路 ──→ 直通 linux
   ────────────────
   根 daemon（一座橋）     它的硬體＝linux
   ────────────────
   linux                  旁邊還有別種「地」：LLM 供應商、人
   ```

3. **「下面」有兩個意思，在根身上重合，在子 daemon 身上分開**：「誰起我、能關我」（這次講的硬體）與「我的請求寄給誰」（C-47 講的 kernel）。子 daemon 的硬體是根，但它開行程是直接找 linux，不是找根。這跟真的虛擬機一樣（一般指令直通真 CPU，只有電源與特權的事經主機），不算打折。細節 [01](01-對到現況.md#兩種下面)。

4. **逐項對現況**（15 項，[01](01-對到現況.md#逐項橋了沒)）：根對 linux 已是橋 7 項（起停行程、重起、訊號與 pid、活不活著的表、環境變數、時鐘、單一行程上限與換帳號）；沒有的 3 項（牆鐘、總量上限、網路）；其餘是只指派位置或歸別人管。子 daemon 對根：跟根拿 5 項，直接碰 linux 7 項（最要緊：它底下的 proc 是它自己 fork 的；信與檔案誰都直接寫）。

5. **「父只看活著」跟「上一層是硬體」是合的**：硬體本來就不看作業系統裡面；照表重起＝重新上電，`restart_on_stuck`＝看門狗。

6. **橋跟「排程＋資源分配」的關係**：有先後——握著唯一的橋才排得了程；daemon 是什麼都不管的裸橋，判官、總機是橋頭的管制。問腦總機是通往「LLM 這種硬體」的橋頭管制，它同時借本機 daemon 起問腦 proc。細節 [02](02-整理法.md)。

7. **四種整理法**（[02](02-整理法.md#四種整理法)，不替使用者選）：甲「一層一個 kernel、分動手與做主兩半」；乙「kernel 只留給真的碰底下的（daemon），判官、總機改名」；丙「C-47 不動，另立一條講層與硬體」；丁（Argon 提）「kernel＝橋，排程是橋上的管制、可以是零」。甲丙丁都只改幾句條文；乙要大改名。

8. **對框架圖紙：四種都不用重畫**（0 節）。圖紙畫的全是「橋頭管制」那一半的零件，新看法補的是「橋通往哪」那一半。只有乙要重定名字那組代定（約 6 條）。K-F50（總機不看 `AOS_KERNEL`）在新看法下理由更順：`AOS_KERNEL` 是給上面的東西找橋頭的，kernel 自己往下找硬體走另一條線。K-F47（Python 重寫）是工法，不受影響。

9. **最要緊的邊緣狀況**（全部在 [03](03-邊緣狀況.md)）：
   - 嚴不嚴格 aos 說了不算、linux 說了才算：同一台機器上沒設帳號與沙箱時誰都能繞過上一層；這時「上一層是硬體」是約定。
   - 硬體壞了軟體照跑：根被 `kill -9`，底下全部還活著，根回來再接回——比喻不貼，但是好的那種。
   - 資源往下切現在只在請求鏈上成立；監管樹上根把子 daemon 算一格，裡面掛幾個不知道，要擋得靠 linux 的總量上限。
   - 跳層寄信：子層裡的 proc 可以直接請根掛 proc，子層收工時不知道有它。
   - agent 不是 subagent 的硬體：動手掛的是 daemon；agent 樹是「誰叫誰做事」，方向相反，一層層的硬體關係不往 agent 走。跨機的遠端 daemon 比較像外接設備，也不是下一層。

## 隊長的建議（可不採）

- 嚴不嚴格：取「上層畫框、下層在框裡直通」（[03 的 ②](03-邊緣狀況.md#嚴不嚴格)）。它就是現況往前一步，跟 11-06「盡量解耦合」、11-11「保底……就是linux本身」都合；真要全部經上一層的地方，用擺法做（把那層做成站），不立成規矩。
- kernel 一詞：丁。不改名、跟「從外面看的身分」接得最順；條文等使用者想完再改。
- 框架圖紙：不重畫，照原訂假日開工不受這題影響。

## 要使用者定的三題

| 題 | 選項 | 後果 |
|---|---|---|
| 1.「上一層是硬體」嚴到哪 | ① 照現況 | 不用做事；總量上限沒人擋 |
| | ② 上層畫框、下層在框裡直通 | 以後補 cgroup、沙箱、帳號時都掛在「起 proc 的那層套」這條線上；信怎麼走不變 |
| | ③ 全部經上一層 | 根什麼都知道，但跟「父只看活著」相反；每多一層多等一拍；根一停底下起不了新行程 |
| 2. kernel 這個詞留給誰 | 甲／丁 | 都叫 kernel，條文補幾句（約 5 處） |
| | 乙 | 只有 daemon 叫 kernel；`AOS_KERNEL`、`kernel/`、框架的名字都要重定，11-12 剛改過的十幾處再改一輪 |
| | 丙 | C-47 不動、另立一條；改最少，但「橋」與「kernel」變成兩個詞 |
| 3. 要不要為這個看法重畫框架圖紙 | 不重畫 | 假日照原圖紙開工 |
| | 重畫 | 只有選乙，或想把「查我有多少額度」這類問硬體規格的信加進框架時才需要 |

## 使用者回覆（11-12 晚）

原話（逐字，同一則訊息裡一口氣回了好幾題，kernel 這段如下）：

> 「kernel這塊，我的請求寄給誰...這個確實有點寬泛，他背後的那個概念(資源排程)和我們的現在的概念有點衝突(硬體橋梁)，linux kernel當然同時包含這兩種概念，但我覺得硬體橋梁比較重要，資源排程這塊linux kernel更像是對硬體的資源進行排程與管理。所以資源排程這塊我覺得還是別叫kernel好了。kernel這塊等等細聊。」

決定（只寫他明講的）：

- 硬體橋樑比較重要。
- 資源排程這塊還是別叫 kernel。

對到三題：

- **題 2（kernel 一詞留給誰）**：方向已說——排程那塊不叫 kernel；細節他說等等細聊。新名字他沒給。（他沒說選哪一種整理法；這方向跟乙「kernel 只留給橋」最近，跟丁「排程是橋上的管制、也叫 kernel」有出入——只是對照，不是他的選擇。）
- **題 1（嚴到哪）**、**題 3（重畫圖紙）**：未答。

若排程那一半改名，牽涉到的（事實，不展開；清單在 [02 的乙](02-整理法.md#乙kernel-只留給橋)）：環境變數 `AOS_KERNEL`（與 `AOS_LLM_KERNEL`）、資料夾 `proto8/kernel/`、`impls/aos-llm-kernel`、框架圖紙裡名字那組代定（K-F23～K-F26、`kernel.json`、`lib/aos/kernel`）、條文 C-47、N-42、N-63 等。
