# kernel 是橋樑：跟「排程＋資源分配」的關係、問腦總機與判官算什麼、三種整理法（不替使用者選）

## 新看法跟舊話的關係

新看法不是推翻舊話，是把使用者三句舊話併成一句：

- 11-05「daemon就像是硬體」、11-06「假如root daemon就是底下的那個硬體板子」——從上面看 daemon；
- 11-05「所有牽涉到linux原生行程的機制，都以daemon爲界面，而daemon所擔任的，就是橋梁」——daemon 自己在做的事；
- 11-05「其實daemon也算是一種kernel，只是他就是來者不拒，可以說是一種最基礎的kernel實作」。

新的只有一點：**硬體是相對的**。同一台 daemon，對上面的東西是硬體，對它自己來說是通往更底下那層的橋。

「橋樑」跟「排程＋資源分配」（[C-47](../../../../docs/CONCEPTS/04-kernel.md)、[N-42](../../../../docs/NORMS/09-kernel.md)）是同一件事的兩半：

- **動手的那半**：把一封請求變成底下那層的動作。現在只有 daemon 在做（信→`fork`）。
- **做主的那半**：這封准不准、誰先誰後、給多少。判官、問腦總機在做。

兩半有先後：**先有橋，而且橋是唯一的路，才管得了排程與分配**——握著唯一通路的人才做得了主；很多人共用一座橋，才長出誰先誰後。daemon 是什麼都不管的裸橋，判官是加在橋頭的管制。反過來也成立：橋不是唯一的路時（底下的人可以繞過去直接碰 linux），橋頭的排程就管不住，見 [03 § 嚴不嚴格](03-邊緣狀況.md#嚴不嚴格)。（「先後」這層是 Argon 補的，同意。）C-47 現在的說法「請求寄到哪，那裡對寄件人就是 kernel」「寄送出去之後……背後就應該是黑盒子」本來就是橋的說法（上面的人只看得到橋頭），只是沒講「橋的另一頭是什麼」。C-47 最後一段「排序與准不准由收件的 kernel 決定，實際掛上去由 daemon 執行」已經把兩半分開講了。

## 問腦總機、判官在新看法下算什麼

- **問腦總機**：LLM 是另一種硬體——[C-29](../../../../docs/CONCEPTS/04-kernel.md) 的「外部 PU……跟外部設備的概念靠攏」。總機是通往這種硬體的橋頭上做主的那半；動手的那半是問腦 proc 裡的 endpoint 函數（`lib/base/llm_http`），像驅動程式。使用者 11-11「我們有多種syscall，有些syscall是走另一個kernel」在這裡讀成：**地不只一種**，linux 是一種，LLM 供應商是一種，人（C-28 的畫家）也是一種，各有各的橋。
  總機同時踩兩塊硬體：LLM 是它排程的對象，本機 daemon 是它借來起問腦 proc 的（Argon 補的，同意）。
- **判官（與框架的站）**：純做主，不碰底下。它對寄件人是 kernel（C-47 從外面看），但它自己不是橋身，是橋頭的關卡。
- **隊 kernel**：一座橋接到另一座橋（轉交），形二。

## 四種整理法

### 甲：一個 kernel 兩半

一句話：kernel 以「層」為單位，一層＝一台 daemon（動手）加它門口的站（做主）；兩半都叫 kernel，橋是本、排程是橋上的事。

```
   上面的東西（agent、工具）
   ─────────────────────── 只看得到橋頭 AOS_KERNEL
   這一層的 kernel ┌ 做主：判官／總機／框架站
                   └ 動手：daemon
   ─────────────────────── 這一層的硬體
   上一層 daemon 或 linux 或 LLM
```

影響：C-47 加一段（兩半、硬體是相對的）；附錄1 名詞的 daemon、kernel 兩列各補一句；板子比喻補一行；C-29 補一句。約 5 處，各一兩句。框架圖紙不重畫——它畫的全是做主那半；「繼承式／0 號 proc 式」兩個範例擺法變成「兩半在不在同一台」。

### 乙：kernel 只留給橋

一句話：只有真的碰底下的才叫 kernel（就是 daemon）；判官、總機、框架改叫別的（站、總機、排程站）。

```
   agent ─→ 站（排程、准入）─→ kernel（＝daemon）─→ 硬體
```

影響：最大。C-47 重寫；N-42、N-63 兩個實例、附錄1、`kernel/` 的說明與出廠內容檔（11-12 [kernel-norms](../kernel-norms.md) 改過的那十幾處）再改一輪；環境變數 `AOS_KERNEL`、`AOS_LLM_KERNEL` 的名字、資料夾 `proto8/kernel/`、`impls/aos-llm-kernel` 要不要跟著改名都得裁。框架圖紙的零件不變，但名字那組代定（K-F23～K-F26、`kernel.json`、`lib/aos/kernel`）要重定。還會跟 11-11「kernel這個身分是從外面看進去的」「轉交也算」打架——那兩句是照「誰收信誰就是」認的，不看碰不碰底下。

### 丙：kernel 的定義不動，另立「層與硬體」一條

一句話：C-47 照舊（資源管理＋排程、從外面看的身分）；新看法寫成另一條講「層」的概念——每一層對上面是硬體、對下面是軟體，daemon 是層與層之間的橋。

```
   C-47 講的：寄件人 ─→ kernel（誰收信誰就是）
   新條講的：  ┌ 層 n+1（子 daemon 與它底下的）
              ├ 層 n  （根 daemon）       ← 上一層是下一層的硬體
              └ 層 0  （linux）
```

影響：最小。新增一條概念、板子比喻補一行，C-47 只加一個連結。框架圖紙不動。代價是「kernel」與「橋」變成兩個詞兩條，使用者這次說的「root daemon本身就是一個kernel」得靠舊句「daemon 是最基礎的 kernel」接上。

### 丁：橋為體、排程為用（Argon 提的）

一句話：C-47 的定義升成「kernel＝把上面的請求變成底下那層動作的橋；排程與資源分配是橋上的管制，可以是零」。每個收信的各自是一座橋、各有各的硬體，不必把「daemon＋站」綁成一層。

```
   daemon      ＝ 零管制的裸橋     硬體：linux（子 daemon：根）
   判官／框架站 ＝ 有管制的橋       硬體：daemon
   問腦總機    ＝ 有管制的橋       硬體：LLM ＋ daemon
```

影響：跟甲差不多（C-47 改開頭一句加一段、名詞表與板子比喻各補一句），不改名、圖紙不重畫。跟甲的差別：甲說「一層是一個 kernel」，丁說「每個收信的都是」——丁跟 11-11「kernel這個身分是從外面看進去的」「轉交也算」接得比較順。要留意的一點：判官這種只轉信的站，它「底下的動作」就是再寄一封信，照丁它也算橋，等於「橋」放得很寬。

## K-F47、K-F50 在新看法下

- **K-F50**（總機的掛信去處只看設定裡的 `next`，不看 `AOS_KERNEL`；跟 N-63 衝突）：新看法給了一個更自然的理由。`AOS_KERNEL` 是給「上面的東西」找橋頭用的；一個東西自己就是 kernel 時，它往下找的是**自己的硬體**，走另一條線：預設是上一層起它時給的 `AOS_DAEMON`，要改接別處才在設定寫 `next`（圖紙 K-F5 本來就這樣）。兩條線分開，總機才不會把掛信寄回給一般 proc 用的那個入口。照這個讀法，N-63 那句「認 `AOS_KERNEL` 的是 aos-llm-kernel 與 aos-agent」裡的 aos-llm-kernel 本來就放錯邊。四種整理法下都一樣。
  Argon 提醒：硬體在哪應該由上一層起你時給（環境變數），不該焊死在設定檔，不然換掛到別台底下就壞；它提議另加一個變數。我的看法：不用加——`next` 沒寫就用 `AOS_DAEMON`，那就是上一層給的；`kernel.json` 也能寫 `$env`。所以這題圖紙已有答案，不列方向題。
- **K-F47**（問腦用 Python 重寫進框架）：是工法，新看法不影響。新看法只多說一件事：框架裡「自己跑」那個零件（寄信請 daemon 掛 proc）其實是「跟我的硬體要一個行程」，所以它放在骨架夾裡當通用零件（K-F49）是對的。
