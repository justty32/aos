## 現有東西夠不夠對標 wf/ 規矩（11-12 晚，家機）

使用者問：

> 「很好，幫我看看，我們現在這些東西，足夠對標wf/規矩了嗎？」

頂層初步看法（未逐項驗證；唯讀對標調查的結論見下面〈調查結論〉）：骨架夠了、周邊還不夠——路由與找東西（`_index`＋`index_view`）、agent 之間的信（信箱＋新信提醒）、手上的事（goal／todo）、技能（eca 開了 Skill）看起來對得上。猜有落差的六點（編號對應下面使用者的回覆）：

1. wf 內容是 markdown，aos 的 index／json 工具處理的是資料夾與 json。
2. 沒有檢查工具（wf-lint、codemap_gen 的對應）。
3. always-on 的規矩怎麼進到每一輪。
4. 「等使用者的事」（WAIT_USER）沒有直接對應。
5. 現在讀 wf 的是 Claude Code 主 session、不是 aos agent，要經 aos MCP 或 skill 餵。
6. 給人看：全變 json 後人怎麼讀。

使用者回覆：

> 「.json比markdown好，有需要的話再做一些輔助工具和程式幫助人看json就好。2.先放着，這是後面一邊玩一邊自然會要做的。3.後續玩一玩，自然會想到怎麽做，反正有hook。4.把人類這個linux user作爲agent，寄信過去就是了。5.對，這個明天開始。」

調查期間使用者又說：

> 「就是說，沒有硬性缺的了，現在wf/的東西，我們拼拼湊湊就能有了。」

> 「以後一定會比wf/好用，放心。寄信這個以後自然就能夠搞定，反正必須的都有了。」

決定：

- D1：內容走 json、不走 markdown；人要看 json，有需要再做輔助工具與程式（第 1、6 點）。
- D2：檢查工具先放著，邊玩邊做（第 2 點）。
- D3：always-on 規矩怎麼進每一輪，之後玩了自然會想到，有 hook 可用（第 3 點）。
- D4：等使用者的事——把人類這個 linux user 當成一個 agent，寄信給他（第 4 點）。
- D5：主 session 經 aos MCP／skill 用 aos 的東西，明天開始（第 5 點）。

### 調查結論

一句話：骨架與必須的都有了，沒有硬性缺的；缺的是小輔助（人讀 json、信「回了才消」、共享的 open 清單）或使用者說之後自然會做的（檢查工具、always-on 的掛法）。明天主 session 先卡在 aos MCP 登記檔兩格壞掉、0 支工具（11-12 晚已修，見 [02 第 1 點](wf-to-aos/02-寄信給人與主session.md#明天主-session-開始現在卡在三點)）。
