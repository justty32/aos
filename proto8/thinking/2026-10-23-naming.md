## 使用者原文

背景：另一個 agent 把 proto8 的命名總表做成 artifact「aos JSON 與命名」（https://claude.ai/artifact/VteK24uuTCMvkahn8YuJEC）與「aos 資料夾佈局」（https://claude.ai/artifact/QNNLmDa2ebRTxS7H1fZWR3），標出 18 處看起來不一致的地方。使用者看完：

> 都先幫我統合。統合好後更新文件和artifact，我等一下重看

這句**翻案**三條先前的裁定：N-17「兩套狀態欄不改名」、「錯誤代號照 impls 沿用、不改名」（C-54）、「aos-tick 的錯不帶代號」。

## 決定：舊名 → 新名

對照表在 [2026-10-23-naming.csv](2026-10-23-naming.csv)（52 列）。同一個名字改過幾次就有幾列，後面的列取代前面的；現行名字以最後那列與 [C-54 命名方法](../docs/CONCEPTS/01-設計理念/C-54-命名方法.md) 為準。欄位：

- `項`：artifact 不一致清單的編號（1～18）；`—`＝跟著改的程式內部名字
- `舊名`、`新名`：`不改`＝照規則留著，理由寫在後面
- `在哪`：哪支程式、哪份檔或哪條條文
- `理由`：照哪條原則推出來（C-54、C-55、C-48、N-45…）
- `定案`：`否`＝原則推得出；`已定（…）`＝原則推不出、使用者逐條選過（括號裡是他的選擇）

訂下的四條規則（都已定）：

1. **副檔名表格式**：JSON 帶 `.json`、JSON Lines 帶 `.jsonl`、純文字帶 `.txt`（使用者選「純文字也帶 .txt」）。
2. **時間**：時間點的 key 叫 `<發生了什麼>_at`，值一律 ISO 8601 UTC 到毫秒；時長與其他單位照 C-54 用後綴（`_ms`、`_ticks`）。見下方「10-25」。
3. **計數**：上限叫 `max`，計數叫 `counter_<被數的東西>`。見下方「10-25」。
4. **錯誤代號第四種**：C-54 的三種（沒有 `…Missing`、不認得 `…Unknown`、壞了或不合 `…Bad`）之外，「動作做不成」＝動作＋`Failed`（`LaunchFailed`、`MkdirFailed`、`WriteFailed`…）；`Internal` 是照理不會發生的錯。

## 10-23 晚：入口改名 `_entry`、刪 `_` 附註

使用者原文：

> 換_entry，有好處嗎

（頂層講了利弊之後）

> 改。然後_開頭=附註這個概念刪掉。

之後補一句：

> 不認得的key就是忽略

決定：

- **入口預設名是 `_entry`**（原 `_exec`）：`AOS_ENTRY` 預設值、每個入口檔、JSON 裡的 key（loop.json／fsm.json 帶的、daemon 蓋到小格 loop.json 的、`檔#/_entry`）、程式、測試、demo、條文、code map 都用 `_entry`。條文裡使用者原話的 `_exec` 照留；歷史敘述旁註「10-23 改名，原 `_exec`」。
- **沒有「`_` 開頭的 key＝附註、宿主程式忽略」**：C-48 的私有 key 慣例（含 `_notes`）、C-55 的「`_` 開頭的附註照 C-48」半句都刪；`_` 開頭的 key 是普通 key。
- **通則：不認得的 key 一律忽略、不報錯**，不分開頭是不是 `_`；寫進 C-48。
- 行為不變：各程式對不認得的 key 都是忽略。旗標（命令列的 `--x`）不是 key，不認得的旗標報 `FlagUnknown`。

## 10-23 晚：重看 17 條代定

頂層把 17 條代定用選擇題一條條問，使用者逐條選：14 條照代定（csv 各列 `定案` 欄），3 條改成別的：

- **行 6 副檔名**：使用者選「純文字也帶 .txt」。規則：JSON 帶 `.json`、JSON Lines 帶 `.jsonl`、純文字帶 `.txt`。所以 fsm 的狀態檔是 `state.txt`（暫存 `.state.txt`）、daemon 小格的 `stderr.txt`（兩版），demo 的 `current.txt`、`plan.txt`、stamp 的 `runs.txt`、時鐘檔 `tick.txt`。`_entry` 是入口（程式），不算純文字檔；`.env` 照行 42 不改。
- **行 19 `.aos/`**：使用者選「改叫 `.stack/`」（跟 `AOS_STACK` 同字）——`AOS_STACK` 沒設時預設 `$AOS_WS/.stack/`。**翻案**使用者 10-19「工作區的 .aos/ stack 照舊」。
- **行 34 題目資料夾**：使用者選「改成一致的階段名」，再選 `new / cur / done`。縮寫表的 `cur` 是 Maildir 的「已認領、處理中」，拿來放產出會跟它衝突（C-54 一詞一義），使用者選「**cur 照 Maildir 原意**」。所以：
  - `new/`＝還沒做的題目（原 `inbox/`）；`cur/`＝被認領、正在處理的題目；`done/`＝處理完的題目。
  - 產出（答案檔）不放 `cur/`，放 `out/`——`out/` 不是階段名，是產出放的地方。
  - think 挑題時把題目從 `new/` 搬到 `cur/`（認領），act 把答案寫進 `out/<題名>`、再把題目從 `cur/` 搬到 `done/`。中途失敗的題目留在 `cur/`。

## 10-23 深夜：「要跑什麼」一律 `exec`

使用者原文：

> fsm.json，現在是用val，幫我改成exec

頂層指出 loop／daemon 的「要跑什麼」叫 `run`，fsm 改 `exec` 之後兩邊不同名，會違反 C-54 一詞一義。使用者選：

> exec，loop／daemon 的 run 也一起改 exec

決定（csv 最後三列）：

- 全體系「要跑什麼」這一格一律叫 **`exec`**：fsm 每一格、loop.json、daemon.json、子項物件、daemon 寫進小格的 loop.json；daemon 把字串子項包成 `{"exec": 它}`。
- `exec`＝交給 aos-exec 跑的目標（字串或 `[目標, 參數...]`），跟執行器 `aos-exec` 同義；aos-exec 進資料夾後跑的入口叫 `_entry`，兩者不混。
- C-55：`val` 只用在「值長成物件時原值放 `val`」（ctl 的 `paused`／`stopped`、`priority`）。C-54 R3 的例子同步。
- `max_runs`、`run_once`（run 當動詞「跑」）不動；旗標沒有鏡射這個 key。

## 10-25：計數 `counter_`、時間點 `<發生了什麼>_at`

使用者 10-25：「state.json中，runs改counter，at改成recorded_at」，再說「計數這塊，幫我改成counter_*」；頂層問時間點的兩題，使用者回「都好」（頂層代定、可翻案）。

- loop／daemon 的 state.json：計數叫 `counter_runs`、這份 state 的時間叫 `recorded_at`。
- 計數規則：`counter_<被數的東西>`（[C-54 命名方法 R6](../docs/CONCEPTS/01-設計理念/C-54-命名方法.md)），其他 JSON 的計數也照這條。
- 時間點：不用單獨的 `at`，一律 `<發生了什麼>_at`（fsm trace `started_at`、信 `sent_at`、kernel-llm served `served_at`…）；沒用 `max_` 的上限照 R6 補（kernel-llm `budget.max_calls`／`max_tokens` 等）。見 [C-54 命名方法 R3、R6](../docs/CONCEPTS/01-設計理念/C-54-命名方法.md)。
