# 2026-10-16 結束碼只是參考；用檔案是為了借 Linux 權限

← [討論紀錄](README.md)｜落成：[C-63、C-64](../CONCEPTS/01-設計理念.md#結束碼與檔案權限10-16-使用者定)｜相關：[KISS 重審 § 使用者拍板](2026-10-16-kiss-recheck.md#使用者拍板10-16)、[NORMS 待定](../NORMS/08-待定.md)

背景：KISS 重審五件拍板之後，頂層整理時挖出兩條邊緣，轉述給使用者——(甲)「收到 SIGTERM 優雅收工也退 0（N-52），呼叫方只看結束碼分不出做完還是被叫停；例 seq 中間某步被叫停，seq 會當成功接著跑」；(乙)「兩個人同時改 daemon 的 `children`（ctl，N-54）會互相蓋掉」。

## 原文（10-16，照原意整理）

「1. 結束碼這東西就只是參考，他是 unix 時代的遺留，那個年代，程式的行為比較單純，所以返回一個數字就能代表大多數狀況，現在不一樣了。

2. 之所以要用檔案，就是因為可以透過 linux 的檔案讀寫權限機制，來做一些神奇的事情。像是讓 kernel 成為某 daemon 的 ctl／清單的唯一可讀寫者。」

## 決定

- **結束碼只是參考**（→ [C-63](../CONCEPTS/01-設計理念.md#結束碼與檔案權限10-16-使用者定)）：它是 Unix 時代的遺留，那時程式單純、一個數字就夠；現在不夠了。**真正的結果與狀態看 JSON**（stdout 的結果、state 窗等）。跟 [N-43](../NORMS/01-總則.md)「結束碼不要太依賴，只定 0／非 0」是同一件事。
- **(甲) 結案**：收到 SIGTERM 照 N-52 退 0 不改。要分「做完」還是「被叫停」的，看 JSON（例 loop 結束那份的 `end`（N-31）、state 窗的 `signal`），不看結束碼。
- **用檔案的理由之一是借 Linux 的檔案權限**（→ [C-64](../CONCEPTS/01-設計理念.md#結束碼與檔案權限10-16-使用者定)）：例如讓 kernel 成為某個 daemon 的 ctl／清單唯一能寫的人。接 C-04（Linux 那邊的事、權限歸 daemon 那層）。
- **(乙) 結案**：多人同時寫同一份 ctl 會互蓋，靠權限讓它只有一個寫的人來解決（例 kernel），不另加鎖或指令資料夾。
