## 決定（10-30）

使用者 10-30 看完衝突七條與方向題三條：「都照建議」。

1. **衝突 1**：名字用 `aos-round`；C-54 R13 補一句「標準庫層級、全域只有一個意思的單字程式可以不帶領域」（同 aos-loop、aos-fsm）。
2. **衝突 2**：N-43、P-35 加註「10 是對直接收到它的那層說的，表上接住就不往上」，碼的意思不動、不加新碼。
3. **衝突 3**：錯誤碼與 `"*"` 准寫進表、風險自擔（`max` 是唯一煞車）；P-20 加註「表上沒接住時才是預設停」，範本表只接 0 與 10。
4. **衝突 4**：「現在在哪」以 fsm 的 `state.txt` 為準，每格對 state 與資料對不上要自保（沒事做就退 0 往下走）。
5. **衝突 5**：trace 只留 fsm 的一格一行、加 `next` 欄；round 的 `unit` 行退場。
6. **衝突 6**：`hook/pause` 與 `round --step` 退場，agent-round 掛勾表那列與代定 27 劃掉。
7. **衝突 7**：`timeout_ms` 數字照舊 600 秒、說明改成「管一格」；要整輪上限在外面再包一層。
8. **方向題 1**：agent 不自帶 round 表，要客製走 D「拆散」；等真有需要再開槽。
9. **方向題 2**：不做「嚴格答一題就停」；要一次一題用 loop 的 `max` 或一次只塞一題。
10. **方向題 3**：舊 round 骨架換完就刪，不並存。

## 實作時代定（10-30，隊長與工人照原則定的細節，可翻案）

- **第 1 步**：物件 `next` 的 key 只收 `"0"`～`"255"` 的標準十進位寫法（沒有正負號、空白、前導 0）或 `"*"`，其他＝CfgBad（`"010"`、`"256"` 當表壞）；值不是字串也是 CfgBad；trace 的 `next` 欄在 main 組那一行時加，`append_trace` 介面不變。
- **trace 那一行算不算失敗**（第 1 步發現、11-02 使用者裁）：頂層問「aos_ws.py 要改成『next 不是 null 就不算失敗』嗎？」，使用者原文：「改」。fsm 的 trace 行 `next` 不是 null＝表上接住、照表走了一步，不算失敗；`next` 是 null 才照原規則（非 0、非 10、或被訊號停＝失敗）；沒有 `next` 的 `unit` 行（aos-eca-turn、舊 round）照舊。aos_human 的 `failure` 叫 `aos_ws.failed`，跟著變。
- **第 2 步**：五個格的錯誤行名字是 `round/<格>`（例 `round/think: EndpointFailed …`）；格開頭一行 `roundlib.main("<格>", 函數)`（解 argv、要 `AOS_STACK`、設模組變數、抓錯印一行）；空了停不停由兩張表定，`MAX_RETRIES` 只有 think 讀。格的自保：think 看到最後一則 assistant 還有沒回的 tool_calls＝不問腦、退 0 去 act 補完；最後一則的 role 不是 user／tool／assistant＝`HistoryBad`。finish 看到最後一則不是「沒 tool_calls 的 assistant」＝不收信、退 0（回 idle → think 接著答，不丟題）。idle 補認領或 `queue claim` 退 10 之後一律看 `cur/` 有沒有信決定退 0 或 10。
- **第 3 步**：env 整份在 exec 時交給 aos-fsm（`os.execvpe`），不改自己的環境；相對 `AOS_STACK`／`AOS_WS` 轉絕對時保留結尾 `/`；aos-fsm 起不來＝`CommandMissing`。單子逾時殺在 think：trace 最後一行 `think` 碼 143、state 停在 think、loop 退 143。
- **第 4 步**：agent-nia 的 loop.json `max` 40 數的是格（一題約 6 格，一次最多答 6 題左右，demo README 寫明）。
- **第 5 步**：ask_round 判「答完了」只看 `queue pop --timeout-s 0 <信號>`（信不見了＝finish 那格已收信、state 回到 idle），不讀 state.txt、不靠 aos-round 的 10；aos-round 退 10 只用在「queue 空了信卻還在」＝`AnswerMissing`。
- **第 6 步**：aos_ws、aos_human、aos-listen 讀 trace 的 `unit` 行相容讀留著（舊 stack、eca 的 turn 也寫 `unit` 行）。
- **第 7 步**：C-54 R13 照決定 1 補一句；N-39 加註註明 `at` 10-23 起改名 `started_at`（正文的欄位名沒改）。
- **`letter_warning`**：由 queue 格在丟壞信時寫 `$AOS_STACK/letter_warning.txt`，idle、more 兩格叫 `queue claim` 時就一起記到，見 [agent-lifecycle 實作時代定 Q-17](../agent-lifecycle/07-衝突.md#實作時代定10-30隊長與工人照原則定的細節可翻案)。
- **找不到 aos-fsm**：`aos-round` 先照 exec 時的 PATH 自己找（`shutil.which`），找不到就說「PATH 上找不到可執行的 aos-fsm」、找到卻起不來才印那個路徑；代號 `CommandMissing`。`aos-parts run`、`aos-tools call` 叫 aos-exec 同樣寫法。
- **舊協議 agent 沒認領信**：listen 等一封時，**信還在 `queue/new/`、沒人在跑、而且 stack 的 `trace.jsonl` 比這封信新**（寄出之後有程式跑過這個 stack、停了、卻沒認領它），就印一行 `aos-listen: LetterUnclaimed …沒人認領…可能還是舊協議…或 loop 的 max 先到了。不等了`、退 1；退之前再看一次信是不是還在 new/。只有「沒人在跑＋信在 new/」、trace 不比信新（先 say、先開 listen、再開 agent 是正常用法）＝照舊提醒一次、繼續等。aos-chat 跑完 agent 後信還在 new/ 沒被認領，「還有 N 封沒答」多帶同一個提示（chat 不退）；chat 不帶 agent 等別人跑時的提醒也是這句。
