## 約束（放最前面，所有方案都要在這條下成立）

使用者提醒回看 [JSON 格式族](2026-10-15-json-families.md)與 C-48 的原文：「不要把指示詞納入正規設計，指示詞是用來拆分 json 檔案和讀 env 變數的，設計中對此的認知只要有『自己的一些檔案可以透過指示詞拆成小檔』這樣就好，不要依賴她。」

所以：**「拿 bob 資料夾當函數、讓它在 workspace 工作」這套呼叫機制，不能依賴 `$ref` 或任何指示詞**（包括曾提議的 `$abs_path`）。`$ref` 改基準只是讓「拆小檔」好用，不是呼叫機制的一部分。呼叫機制只能靠檔案系統本身：cwd、資料夾、檔案。

## 原文（10-15 晚，照貼）

**場景**：「我現在有個 /home/a/workspace/ 資料夾，然後有 /home/a/agents/bob/ 資料夾，然後我會 cd 到 workspace 資料夾，然後跑 `aos-inst ../agents/bob`」「也就是我想要在這個資料夾跑 bob 這個函數，讓他在這個 workspace 工作」「拿 ../agent/bob 作爲函數呼叫，讓他在 ./ 工作，然後我又不想碰環境變數」。

**規範重申**：「當初的規範定下來，就是說 stdin 作爲標準輸入，inst.json 的內容就是走 stdin 進去，這是標準使用，命令行是要空出來的」。

**流程**：「aos-inst 從 stdin 讀到一份 json 後，他就是先按照 aos-inst 自己的 cwd，去解指示詞（$ref/$env），然後是根據解出來的東西，同樣根據 aos-inst 自己的 cwd 去把 stdin/out 等檔案路徑定下來，然後要真正執行之前，再去將 cwd 切到指定的 cwd 路徑。」

**決定**：「首先 $ref 確實應該用該檔案所在的位置開始算」「從 stdin 來，其實更像是在 workspace 中創造一個叫做 inst.json 的檔案，然後將內容交給 aos-inst 這樣。然後 aos-inst TARGET 這樣的用法我覺得應該拿掉，就是完全從 stdin 來就好，要用 aos-exec TARGET 作爲語法糖。」「$ref 確實要改，改之前要派 agent 評估影響」。

**對 `$ref` 影響評估的拍板**：symlink——「不，捷徑我覺得他更像是一個懶得每次都 copy 過去的方法，所以就是從 symlink 所在開始算。」；Python 傳 dict 的基準＝呼叫者 cwd（照推薦）；「TARGET 這東西都拿掉。」（JSON 裡寫的 TARGET 字串與命令列 TARGET 都是）；「aos-tree 我覺得可以先刪掉，這只是個無關緊要的小工具，用來驗証概念用的，看起來好看的東西。」

**新指示詞**（AI 提 `$path`，使用者先改名再質疑）：「那應該改叫 $abs_path」「然後，其實 $abs_path 真的有必要嗎？我覺得不用吧，再想想」。

## 決定

1. **`$ref` 的相對檔名，從那個指示詞所在的檔的資料夾算**，基準＝`dirname(abspath(檔))`，**不解 symlink**（捷徑＝懶得 copy，從捷徑所在算）。stdin 那份＝當成 aos-inst 的 cwd 裡放了一份 inst.json，所以它裡面的 `$ref` 基準是 cwd；Python 直接傳 dict 的基準也是呼叫者的 cwd。`$ref` 取回來的東西裡再有 `$ref`，從被取的那份檔算。現況「base_dir 整趟都用它」要改。（身分 id 現在用 realpath，跟這條不同，見未決 F。）
2. **inst 的 `cwd`、`stdin`／`stdout`／`stderr`／`exit` 這些路徑，一律從 aos-inst 自己的 cwd 算**。`cwd` 這個 key 只決定子程式在哪跑，不影響別的路徑怎麼算。現況串流是「從解出來的 cwd 算」，要改。
3. **沒寫 `cwd`＝子程式在呼叫者站的地方跑**（現況如此，不變）。
4. **aos-inst 拿掉 TARGET，設定只從 stdin 來**（N-12 的標準用法；命令列空出來）。
5. **新增 `aos-exec TARGET`，給人用的語法糖**（細節見未決 A）。
6. **TARGET 全拿掉**：命令列的（aos-inst／loop／daemon／fsm／gate 都是）與 **JSON 裡寫的 TARGET 字串**（daemon 的 `children`、閘門的 `target`、kernel 設定裡 gates／judges 的路徑、fsm 的格、tasks 的 argv…）。替代＝**內嵌 inst 物件**（同像性，`(daemon (fsm b c))`）；要拆成小檔就用 `$ref`，那是拆檔便利、不是機制。各處怎麼換見未決 C。
7. **刪 aos_tree**（print／inline 小工具，實作時做；test_tree 一起）。
8. **指示詞的定位**照約束：`$ref`＝拆檔、`$env`＝讀環境變數，到此為止。**`$abs_path` 不做**：它唯一的用處就是讓呼叫機制靠它找檔，而呼叫機制不准靠指示詞；單純當拆檔工具它沒有用。

## 呼叫機制怎麼不靠指示詞成立（AI 整理，照 C-46 現有設計推到底）

C-46 已經定了：**呼叫＝新建一個 frame 資料夾當 cwd，裡面 `frame.json {"parent": "<定義資料夾>"}` 指回定義，`args.json` 引數、`ret.json` 回傳，找名字往上找（Lisp 環境式）**。這裡面**只有一條路徑**（parent），而且是**呼叫方寫的**——呼叫方一定知道被叫者在哪（人知道、agent lib 從自己的定義算）。被叫者凡是要找自己的檔，**一律讀 cwd 的 `frame.json`**，不讀環境變數、不靠指示詞、不 cd。aos-inst 本身對此一無所知，它只是跑一張 inst。

**bob 例子（人叫，零指示詞）**：

```
cd /home/a/workspace
echo '{"question": "幾點？"}' | aos-exec ../agents/bob
cat ret.json
```

- aos-exec：TARGET 是資料夾 → 定義＝`/home/a/agents/bob`（abspath，不解 symlink）；在 cwd 寫 `frame.json {"parent": "/home/a/agents/bob"}`（已經有就不動＝同 frame 續聊）；自己的 stdin 有東西就寫成 `args.json`；讀 bob 的 `.aos/inst.json`（沒有再 `inst.json`），灌給 aos-inst 的 stdin；結果透明轉交。
- bob/inst.json：`{"argv": ["aos", "agent", "run"]}`——**一個路徑都沒有**。`aos agent run` 讀 cwd 的 frame.json → parent → 讀 `parent/loop.json` 當 `aos loop` 的 stdin 灌進去（跟 `aos agent fsm` 找 fsm.json 是同一條路 `chain()`）。loop 的 inst `{"argv": ["aos", "agent", "fsm"]}` 在同一個 cwd 跑，fsm.json／brain.json／tools 照 chain 找。`ret.json` 落在 workspace。
- 沒寫 `cwd` → 全部在 workspace 跑；同一個 bob、兩個 workspace 同時叫互不相干。
- 不用 aos-exec 的裸寫法（今天 frame.md 的「直接叫」）照樣成立：`echo '{"parent": "/home/a/agents/bob"}' > frame.json && echo '{…}' > args.json && aos loop < /home/a/agents/bob/loop.json`。
- bob 若把 inst.json／loop.json／fsm.json 用 `$ref` 拆過小檔：aos-exec、`aos agent run` 都是**從檔讀**的，解指示詞時基準＝那份檔，拆檔照樣好用；用 shell `<` 重導向灌進去的那份基準是 cwd，拆過檔的人自己知道（或改用 aos-exec）。

**工具叫 agent（painter 叫 brush）**：現況 `painter/tools/brush.json` 用 `sh -c` 拼 `$AOS_DEMO` 寫 frame.json——這是今晚唯一真正卡「絕對路徑從哪來」的地方。不靠指示詞的解法在未決 E（巢狀＋symlink）。

## 未決（附推薦；使用者習慣「都按照推薦」）

### A. aos-exec 的確切行為

- **推薦**：`aos-exec [旗標] TARGET [-- argv…]`，**不 cd**。TARGET 是**資料夾**＝函數呼叫：寫 `frame.json`（沒有才寫）、自己的 stdin 非空就寫 `args.json`、讀 `$AOS_DIRNAME/inst.json`→`inst.json` 當入口；TARGET 是**檔**（可接 `#/位置`）＝只是把那份檔灌給 aos-inst，不寫 frame.json、不碰 args.json（純「人手打 `aos-inst x.json`」的替身）。兩種都是：讀檔（指示詞基準＝那份檔）→ 蓋旗標與 `--` → 灌 aos-inst → 結果與錯誤透明轉交；aos-exec 自己只有「引數不對」`ArgumentsBad`、「找不到入口」`InstMissing` 這類錯。`檔#/位置`、資料夾找 inst.json 這兩條規矩從 N-35 的「TARGET」搬到 aos-exec 名下。
- 對照「先 cd 再跑」：`cwd` 預設變成定義資料夾、串流落進定義資料夾、同一個 bob 兩個 workspace 互蓋，跟場景相反，不推。
- stdin → `args.json` 是不是多做了：aos-exec 的 stdin 本來就空著（設定在命令列），拿來當引數正是 N-12「stdin＝參數」；但它讓 aos-exec 帶了一點 C-46 的味道（知道 frame.json、args.json）。替代＝人自己寫 args.json。推薦做，理由是「拿資料夾當函數呼叫」是使用者要的那句話，寫 frame.json 就已經是 C-46 了，args 順手。
- 名字：使用者說 aos-exec，照用（`aos exec`；跟 C++ 的 `core/exec` 不相干）。
- Python 的 `run(x)`（N-25）：推薦只收 dict（基準＝呼叫者 cwd，決定 1）；路徑形的需求由 aos-exec 的函數版 `exec(target)` 接。

### B. 旗標（`--timeout-ms` 等鏡射旗標）與 `--`

- **推薦搬到 aos-exec**：aos-inst 命令列零引數（多給＝`ArgumentsBad`）；旗標、`--` 本來就是「人手打」的方便（N-22 自己說不是硬規則），人用的那層才有。loop／daemon／fsm／gate 同樣零引數（起子程序本來就走 stdin，N-22）。`-` 跟 TARGET 一起退場；「都沒給＝從 `{}` 起」退場（stdin 空＝`JsonSyntax`）。N-21～N-24 改寫。
- 留在 aos-inst（現況）違反「命令行要空出來」；全拿掉會少了 `aos-exec x.json -- sh -c '…'` 試東西的手感，都不推。

### C. JSON 裡 TARGET 字串的替代（決定 6 的落法，各處一條）

- **daemon `children`**：每項＝內嵌 loop 設定物件（現在已接受），**`id` 改必填**（原本從 TARGET 算；缺＝`IdMissing`）；daemon 指令裡的 id 照舊。推薦。
- **閘門 `target`**：只收內嵌 inst 物件（現在已接受）。推薦。
- **kernel 設定裡 gates／judges 的路徑**：改內嵌；判官是 agent 定義資料夾（`judges/agent/`）的，照 E 的巢狀法——kernel 自己也當函數叫（`aos-exec demo/kernels/general`，frame.json 指回 kernel 定義資料夾，判官＝`judges/agent/` 從 parent 底下找）。推薦；kernel 細節等 kernel 那條線再定。
- **fsm 的格**：只收內嵌 inst（純值形＝內嵌 inst 物件、展開形＝`{"val": <inst>, "next"}`），N-36「格從表所在資料夾算」那句刪掉；demo 的 `cells/*.json` 用 `{"$ref": "cells/intake.json"}` 拆檔照留。推薦。
- **proto8-1 tasks（seq／par／if／not）**：argv 不再收 TARGET，改從 stdin 收 inst——N-12 說 stdin 多份＝一次呼叫、意思由程式定：**seq／par＝stdin 串流一份一張 inst、照順序**；if＝`{"cond": <inst>, "then": <inst>, "else": <inst>}` 一份物件；not＝一張。人手打用 `cat a.json b.json | aos-seq` 或一張 inst 包起來。推薦。
- **loop 的 `inst`**：已經是內嵌物件，不動。
- **`aos loop`／`aos daemon` 給人從檔起**：`aos-exec` 一張 inst `{"argv": ["aos", "loop"], "stdin": "…"}` 要路徑（從 cwd 算）——所以推薦 D 的「`stdin` 收內嵌 JSON」：`{"argv": ["aos", "loop"], "stdin": {"$ref": "loop.json"}}`（拆檔便利）或整份內嵌。

### D. inst 的 `stdin` 收內嵌 JSON

- **推薦做**：`stdin` 字串＝檔路徑（現況，從 aos-inst 的 cwd 算）；物件／陣列＝內容，aos-inst 落成 `.` 開頭暫存檔（N-05）、跑完刪，灌給子程式；`stdin_inherit` 衝突照 N-26 Conflict。陣列**一律當多份**（跟 N-12、N-35 把串流當陣列同一套），要傳「一份陣列」就 `[[…]]`。這不是呼叫機制的一部分（bob 走 frame.json 就通），是 C-48 雙形的自然延伸，讓「子程式吃 JSON 參數」不必先落檔。

### E. 工具叫 agent：被叫者的定義在哪（唯一真正缺絕對路徑的地方）

- 現況：工具 inst `sh -c` 拼 `$AOS_DEMO`，frame.md 說不在 demo 就寫死絕對路徑。
- **推薦：巢狀＋symlink，零路徑**。工具可以是一個**資料夾**：`painter/tools/brush/`（裡面 inst.json、fsm.json、brain.json…，就是一個定義資料夾）。agent lib 的 tool 步驟看到 `tools/<名>/` 是資料夾＝agent 當工具：開 `work/<n>/`、寫 `frame.json {"parent": "<painter 定義>/tools/brush"}`（painter 的定義資料夾 lib 從自己的 chain 就知道，絕對路徑是算出來的、不是寫的）、寫 `args.json`、跑它的 inst.json——**跟 aos-exec 做的事一模一樣，同一段程式**。多個 painter 共用一把 brush：`tools/brush -> ../../brush` 放一個 **symlink**（使用者今晚正好說捷徑＝懶得 copy；parent 寫 symlink 的路徑、不解開，brush 在裡面找自己的檔照 parent 走，讀到的就是本尊的檔）。`_tool` 的 description／parameters 放在資料夾裡的 inst.json（N-04 多放東西）。
- 不推的：工具 inst 裡寫 `"call": "../brush"` 這種相對路徑 key（又是 TARGET 字串）；環境變數（撤回）；`$abs_path`（約束）。
- 隨這條：`demo/bin/aos-demo` 與 `AOS_DEMO` 大半可以退場（demo 的 README／run.py 還用到的再看）。

### F. 身分（id）

- symlink：`$ref` 基準不解 symlink，id 現在用 realpath——**推薦 id 也改 abspath**（同一理由：捷徑＝一份懶得 copy 的副本，兩個捷徑＝兩個身分；N-35 的 realpath 改字）。
- TARGET 沒了之後：id＝設定的 `id`（寫了才有）＞ null；daemon children 的 `id` 必填（C）；aos-exec 跑的那張沒寫 `id` 時，**推薦 aos-exec 代填**＝入口檔的 `abspath#/位置`（跟今天 `aos-inst TARGET` 的 id 同形），這樣結果裡的 id 不退步。kernel 信的 id 本來就是信檔名，不受影響。

### G. `_schema`

- 私有 key（`_` 開頭，宿主忽略，C-48），TARGET 字串拿掉後它只是資料；demo／測試從所在檔的資料夾算只是慣例，不進規範、不特別處理。要讓程式幫忙就 `{"$ref": "schema.json"}` 嵌進來（拆檔便利）。
