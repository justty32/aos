總評：六站有趣、核心流程玩得起來，但幾個指令與等待狀態會讓新手懷疑自己做錯；**3/5**。

### 六站

- 第 1 站：**過，約 2 分鐘**；模型列表、呼叫、改問題與錯模型都成功，但要求一句話卻回了一大篇。
- 第 2 站：**過，約 1 分鐘**；101／100 很清楚，永久 waiting 時也確實會讓出 CPU。
- 第 3 站：**過，約 1 分鐘**；kernel 自動完成並寫出答案，故意丟例外也在第 10 次後進 bad。
- 第 4 站：**過，約 1 分鐘**；三格一次成功，看到 binary 自動變成 `$b64` 很有意思。
- 第 5 站：**沒過，約 1 分鐘**；第四次實際退 0，不是 README 說的 101，而且照叫五次仍未完成，得等候再多叫一次。
- 第 6 站：**過，約 4 分鐘**；agent 真的會用 sh，也能閒聊，但連續送話、listen 與 reset 的行為很容易誤解。

### 發現清單

1. 從第 6 站所在目錄直接照抄 `playground/down.sh` 會找不到檔案 → 我期待走完整份 README 後能直接收工 → 改成絕對路徑、`cd` 回 repo，或寫 `$AOS_REPO/playground/down.sh`。
2. 兩句話緊接著 `say`，前一句工具要求沒有回覆、後一句閒聊反而先被處理 → 我期待 inbox 逐封依序處理 → 修正排隊行為，並在指南提醒「等上一題完成再送下一題」。
3. 第 5 站第四次實際退出碼是 0，照抄五次也不一定產生 `answer.json` → 我期待指南描述與實際狀態一致 → 說清楚第四次只是宣告 wait、下一次才可能退 101，並提供可直接等到完成的指令。
4. `aos-user bob listen --once` 每次都從 0001 重播全部舊信 → 我期待它只顯示下一封或尚未讀取的回覆 → 調整 `--once` 語意，或在 README 明講要搭配 `--new`／長駐 listen。
5. 第 6 站沒有寫 reset 的完整操作 → 我期待能直接照抄測撞名 → 補上先 `aos-kernel rm`、進 bob 執行 `aos-agent . --reset`、重新 add 的完整範例。
6. reset 後改問題會撞 `bob-q1-s1`，錯誤只在 `status`，listen 仍重播舊回覆 → 我期待聊天畫面直接告訴我新問題失敗 → 把撞名錯誤送到 outbox，並在 reset 範例補上移除舊 LLM 單的方法。
7. 上環境時 banner 把 `kernel：$K`、`daemon 家：$AOS_DAEMON_HOME` 原樣印出 → 我期待看到實際路徑 → 修正變數展開。
8. 第 2 站 add 後立即 `ls` 還看不到行程 → 我期待照抄就看到 README 描述的 waiting → 在指令區直接加入 `sleep 1`，不要只放在註解。
9. 步數上限的回覆是「走了 1 格先停，回我一句再繼續」，但 `status` 同時標 `stuck=yes` → 我期待回覆直接說已達上限／卡住 → 統一使用者訊息與狀態用詞。
10. 第 2、4、5 站的 state/status 是整坨 JSON／Janet 資料 → 我期待初玩時先看到 pc、done、waiting 等摘要 → README 可提供一條精簡的 `jq` 查法。

故意弄壞實測了四樣：永久等檔、Python 例外連續十次進 bad、agent 步數上限變 stuck、agent reset 後改問題撞 LLM 名稱。沒有翻 proto README 或 notes。
