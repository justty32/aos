## 1. 從零到第一次 `aos-llm call`

抄 README 的 `endpoint.json`／`endpoints.json`，`models` 印出的第一行就是 `google/gemma-4-e4b`，一次命中，`call` 4.7 秒拿到回答。**沒有一步要猜**，除了工具路徑（見下）。

- **模型名打錯**（`gemma-4-e4c`）：現象 → 4 毫秒退 1、`error.kind=model_not_found`、訊息明說「未送出 chat 請求」，而且 `raw.preflight` 把真正的模型清單附上了。我期待 → 至少要等一次 HTTP 才知道錯。建議 → 不用改，這條比我預期好，raw 裡附清單是神來一筆。
- **base_url 指死埠**（1299）：現象 → `connect: Connection refused` 退 1，`notes` 記一筆 `model_preflight_skipped` 說明預檢也連不上、仍照原流程送。我期待 → 只看到一句 connect。建議 → 不用改。
- **REQ 裡寫 `model`**：現象 → `bad_request: 不准指定 model；model 固定在 endpoint 設定`，退 1、有寫出 OUT。我期待 → 就是這樣。建議 → 不用改。
- **工具怎麼叫**：現象 → proto4-5 README 全寫 `./aos-llm`（假設你 cd 進 proto4-5），proto4-3 README 開頭卻說「假設你已把絕對路徑加進 PATH」所以寫 `aos-…`。我在 `/tmp/play4-opus` 工作，兩種都不能直接照抄，只好打絕對路徑。我期待 → 兩份文件同一個慣例。建議 → proto4-5 開頭補一句「把 proto4-5 也加進 PATH」，指令改寫成 `aos-llm`。

## 2. LLM 排程當 kernel module

- **quickstart 缺兩步**：現象 → proto4-5 那節寫的是 `aos-kernel-init … --module` → `(cd K && aos-kernel-tick)` → 改 endpoints → `aos-kernel llm`，**完全沒提要先開 `aos-daemon`、也沒提 `aos-kernel-boot`**。我期待 → 照著做就有東西在跑。實際 → 得回頭翻 proto4-3 README 才知道要 `setsid -f aos-daemon` + `aos-kernel-boot K`。建議 → 那個程式碼區塊補這兩行。
- **「換掉 model」的提醒躲起來了**：現象 → 自動生的 `K/llm/endpoints.json` 裡 model 是佔位字串 `loaded-model-id`，提醒只寫在 `K/kernel.log` 第 2 行，`init` 跟 `boot` 的畫面輸出都沒提。我期待 → 在畫面上。建議 → `aos-kernel-init --module` 的輸出直接印一行。
- **忘了換的下場（這條修得好）**：現象 → `aos-kernel llm K req --name oops --wait 20` 在 **0.78 秒**回「LLM 失敗：model_not_found: 模型 'loaded-model-id' 不在 endpoint 的 /models 列表；未送出 chat 請求」，退 1，0 token。我期待 → 可能要等到逾時。建議 → 不用改。
- **生出來的檔壓成一行**：現象 → `K/llm/endpoints.json` 是無換行的 minified JSON，README 卻叫我 `$EDITOR` 它。我期待 → 給人改的檔就排版好。建議 → 寫檔時 `indent=2`（小）。
- **四種投單都對**：`--wait 60` 印回答＋結果檔路徑退 0；不等 → 印「下一回合處理」，6 秒後結果檔就有了；同名同內容 → 「同一張請求已存在」退 0、不重送（`llm done` 計數沒動）；同名不同內容 → 「id 已經存在於 results：hello」退 1，還指明撞在 results。四句話各不相同，一看就知道差在哪。建議 → 不用改。
- **daemon 停掉再丟 `--wait 3`（重點修法，過了）**：現象 → 3 秒後回「kernel 沒回應；請求沒送出去，已撤單」退 1；`K/syscalls/` **是空的**；daemon 重開 + boot 後那張**沒有偷偷跑**，`results/` 裡沒有 `dead.json`。我期待 → 就是這樣。建議 → 不用改，這條完全修對了。
- **但不帶 `--wait` 也會被撤單**：現象 → daemon 停著時 `aos-kernel llm K req --name later`（沒有 `--wait`）同樣回「已撤單」退 1，重開後也不跑。我期待 → README 說「不想等就省略 `--wait`，由下一回合處理」，我以為會排著等我開機。建議 → 行為本身我覺得對（不留幽靈單），但 README 要補一句「kernel 沒活著時，不管有沒有 `--wait` 都不收單」。

## 3. Python 逐步程式三格

- **範例裡的 `K` 沒交代**：現象 → README 的兩格範例寫 `aos.llm_submit(K, …)`，但同一頁列的可用全域只有 `state`／`here`／`pc`／`aos`，`K` 從哪來沒人說。我期待 → 有個內建變數。實際 → 自己在檔案頂端寫 `K = "/tmp/play4-opus/K"`。建議 → 範例補一行 `K = "/abs/K"`，或說明它就是普通變數。
- **三格跑起來很順**：`submit` → `wait`（`return aos.wait_for(state["r"])`）→ `consume`，`aos-kernel add` 之後約 10 秒全部跑完，`procs/done/`。中途 `aos-kernel ls` 看到 `LAST_EXIT 101 / CPU_STATE waiting / WAIT 等了 6 回合`，同一行 `llm: running 1`，一眼看懂它卡在哪一層。建議 → `WAIT` 欄只寫「等了 N 回合」，不寫在等哪個檔；補上檔名會更好（小）。
- **`--reset` 重跑不卡（這條也修對了）**：現象 → `--reset` 後重新 `add`，4 秒跑完三格，`llm done` 停在 4 沒增加，`answer.txt` 內容一樣 → 確實沒重打 LLM、沒重花 token。我期待 → 可能卡在「id 已經存在」。建議 → 不用改。
- **但改了問題再 `--reset` 就會撞牆**：現象 → 把問題從「貓」改成「狗」、`--reset`、重排 → `aos.llm_submit` 拋 `RuntimeError: aos-kernel 回 1: id 已經存在於 results：q1`，格子退 1，kernel 照 `bad_after` **一秒一次重試 10 次**才把它丟進 `procs/bad/`。我期待 → 訊息告訴我下一步怎麼辦。實際 → 訊息只說撞到了，沒說「要重問就先刪 `K/llm/results/q1.json`」，而且明明是不可能自己好的錯，還白試 9 次。建議 → 錯誤訊息尾巴加一句怎麼解；README 也補一句。
- **`--status` 會噴上次的錯**：現象 → `--reset` 之後（`.state.json` 已刪、`job.py.error` 還在）跑 `--status`，畫面先吐出上一次整段 traceback，才印 `{"pc":0,…}`，看起來像剛剛又炸了一次。我期待 → 只印狀態。建議 → 錯誤檔的內容改成一行提示（「上次錯誤在 job.py.error」），或 `--reset` 時一併刪掉它。

## 五個問題的答案（補充例子）

**① 容易上手（4）**：3 個檔（`endpoints.json`、`job.py`、`proc.json`）、8 個指令、約 6 分鐘。扣分在 quickstart 缺 `aos-daemon`／`aos-kernel-boot`。
**② 容易理解（4）**：結果的三組欄位（日常／除錯／`raw`）分得很好，`model` vs `model_requested` 一講就懂。想歪的地方：`aos.llm` 和 `aos.llm_submit` 是兩個不同的家，這句只寫在 proto4-6 的 **Lua** 那節，Python 那節沒有；我先以為 `llm_submit` 會用 `K/llm/endpoints.json` 以外的設定。
**③ 複雜藏好（4）**：`K/syscalls/`、`requests/running/`、`state.json` 這些我全程沒必要打開。被迫知道的兩件：得去讀 `K/kernel.log` 才看到換 model 的提醒；撞名要自己去刪 `K/llm/results/<name>.json`。
**④ 控制結構（3）**：`aos-llm models`／`call` ＋ `aos-kernel llm` 這三個就夠投單了。**缺的是收單**：沒有 `aos-kernel llm --ls`／`--rm <name>` 之類，看排隊只能靠 `aos-kernel ls` 那一行摘要，清掉舊結果只能自己 `rm` 檔。**重疊的是 `llm-cpu` 那整組 CLI**（`init`/`submit`/`tick`/`ls`），跟 module 掛法功能一樣，新手會不知道該選哪個。
**⑤ 要背的少（4）**：檔名 6 個（`endpoints.json`、`K/llm/endpoints.json`、`K/llm/results/<name>.json`、`<PROG>.state.json`、`<PROG>.error`、`K/kernel.log`）；旗標 8 個（`--wait`／`--json`／`--name`／`--reset`／`--status`／`--module`／`--ncpu`／`--timeout-ms`）；環境變數 1 個必背（`AOS_DAEMON_HOME`）＋3 個可選覆蓋。以「一個作業系統」來說不算多。

## 前五名最該改的

1. **proto4-5 的 quickstart 補上 `setsid -f aos-daemon` 與 `aos-kernel-boot K` 兩行** — 現在照抄跑不起來，這是新手第一個坑。（小）
2. **Python 範例補一行 `K = "/abs/K"`** — 範例用了未定義的變數，是唯一逼我猜的地方。（小）
3. **撞名的錯誤訊息加一句「要重問就先刪 `K/llm/results/<name>.json`」** — 順手也讓這種必死的錯不要被 `bad_after` 白試 10 次。（小）
4. **「請把 model 換成…」印到 `aos-kernel-init --module` 的畫面上**，別只寫進 `kernel.log`；順便把生成的 `endpoints.json` 排版成多行。（小）
5. **README 補一句：kernel 沒活著時，不帶 `--wait` 也會撤單不排隊**；同時把 proto4-5 的 `./aos-llm` 統一成 proto4-3 的 PATH 慣例。（小）

沒有一條是大改，這一輪 LLM 層的行為我挑不出該動程式的地方。

