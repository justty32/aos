# gptsol 試玩報告 r3

總評：**happy path 已經真的能用，三種語言也接得起來；目前最傷新手的是「CLI 說失敗但請求之後仍執行」以及 kernel 看不出行程正在等檔。**

五項分數依序為「容易上手／容易理解／藏住複雜度／控制結構／少背東西」：

- proto4-5：**4／3／3／—／3**
- proto4-6：**4／4／3／4／3**
- 逐步 lisp（只讀 README 比較）：控制結構 **3／5**

## 1. OS 那層

- 現象：設定 `AOS_DAEMON_HOME` 後，daemon → init → boot → `aos-kernel ls` 四步一次成功，看到兩顆 idle CPU → 我期待：README 的最短路徑可以直接照抄 → 建議：保留這段，但把它獨立成「五分鐘開機」區塊，先別讓大量限制清單淹過它。
- 現象：`aos-kernel-init` 完成後又印下一步指令，`aos-kernel-boot` 也告訴我怎麼看狀態 → 我期待：新手不必回頭翻 README → 建議：這種引導很好，其他工具也照此做。
- 現象：README 同時示範 `setsid -f`、背景 `&`、`--home` 和環境變數，並提醒 `--home` 不傳子孫 → 我期待：只要知道怎麼開 daemon → 建議：新手路徑只推薦 `AOS_DAEMON_HOME=… setsid -f …` 一種，其餘放進進階說明。

## 2. 第一層 `aos-llm`

- 現象：單一 endpoint 檔只靠 README 列出的 `name/kind/base_url/model/timeout_ms` 就能寫成，`models` 列出四個本機模型 → 我期待：最好有一份完整 JSON 可抄 → 建議：在「呼叫一次」旁直接補單一 endpoint 的完整範例。
- 現象：正常 `call` 約 8.4 秒、退出 0、寫出 `result.json` → 我期待：成功有文字和用量 → 建議：可以另提供 `--text` 或範例 `jq -r .text result.json`，避免第一次被巨大 `raw` 淹沒。
- 現象：我看得懂 `ok/id/endpoint/model/text/usage/ms/error`；`model_requested` 要停一下，`finish_reason` 偏 API 話，`raw` 幾乎看不懂 → 我期待：結果檔先放日常會看的資訊 → 建議：README 把欄位分成「日常／除錯／原始供應商資料」三組。
- 現象：正常、錯模型、死埠的退出碼分別是 0、1、1，完全符合 README → 我期待：退出碼能分成功、呼叫失敗、輸入錯 → 建議：維持現況。
- 現象：錯模型仍真的跑了約 11 秒、用了 773 tokens，最後才因實際模型不同回 `model_mismatch` → 我期待：模型名錯應在生成前被服務端拒絕 → 建議：錯誤訊息補一句「請求可能已經執行並消耗資源」。
- 現象：死埠 4 ms 就得到 `connect`、`retryable:true`、退出 1 與結果檔 → 我期待：立刻知道是服務沒開 → 建議：這個錯誤已很清楚，不用改。

## 3. LLM kernel module

- 現象：`--module llm_cpu_module.py` 初始化後，下一個 tick 自動建立 `K/llm/endpoints.json` → 我期待：README 所說的範例檔會出現 → 建議：初始化訊息直接印出「請編輯哪個檔」，不用讓人猜何時出現。
- 現象：範例 endpoints 同時含 local、DeepSeek 與 pi；我只改 local 的模型名 → 我期待：本機 quickstart 不出現可能花錢的 endpoint → 建議：預設檔只放 local，其他範例另放文件。
- 現象：`--wait 60` 成功後，CLI 印結果且檔案在 `K/llm/results/wait-one.json` → 我期待：同步等待不用自己找檔 → 建議：成功時預設只印 `text`，完整 JSON 可加旗標。
- 現象：不等的請求先看到 `llm: ... running 1 ... local 1/1`，稍後變成 `done 2` → 我期待：`ls` 能看排隊、執行與容量 → 建議：狀態列已夠直觀。
- 現象：同一 `--name duplicate` 第二次顯示 `id 已經存在`、退出 1，第一份不受影響 → 我期待：不覆蓋舊請求 → 建議：補印撞到的是 request、running 還是 result，方便清理。
- 現象：daemon 關掉時，`--wait 2` 顯示「kernel 沒回應」並退出 1 → 我期待：這張請求沒有送出去 → 建議：不能把它描述成一般失敗。
- 現象：daemon 重開後，那張已退出 1 的 `daemon-down` 請求仍被執行，結果真的出現在 results → 我期待：退出 1 就代表不會再發生副作用 → 建議：這是第一優先；要嘛逾時撤單，要嘛明說「結果未知，可能稍後執行」並給查單指令。

## 4. 三支逐步執行器

- 現象：JSON 五格成功完成；等待格先把 `pc` 從 3 推到 4，檔案未出現時只增加 `checks`，出現後同一次呼叫接著跑第 4 格 → 我期待：等待格本身會停在原 pc → 建議：README 用一張 `pc=3 → 宣告等待 → pc=4/waiting → 執行第4格` 小時間線解釋。
- 現象：JSON 的 `wait_for` 保存絕對路徑，shell 三秒後寫出 `gate.txt` 即繼續 → 我期待：相對路徑依程式目錄解析 → 建議：現況符合文件。
- 現象：Python 五格完成，`aos.call(..., args=["teal","two words"])` 完整保留第二個含空白參數 → 我期待：不用自己處理 shell quoting → 建議：這個介面很好。
- 現象：Python 的 `llm_submit`、下一格 `wait_for`、再下一格讀 JSON，三件事拆得很乾淨 → 我期待：非同步流程能從 state 看懂 → 建議：把這種「三格完整版」放進 README，目前範例把 submit 與 wait 合在同一格。
- 現象：Python bytes 在 `job.state.json` 變成 `{"$b64":"AP8QgA=="}`，重讀後仍能當 bytes → 我期待：JSON 不會破壞 binary → 建議：現況清楚。
- 現象：Lua 的同步 `aos.llm` 成功，並保留 `answer.json.req.json` 對帳 → 我期待：同步版本不需要 kernel → 建議：把它標成「最短的第一支 LLM 逐步程式」。
- 現象：Lua `state.binary = aos.b64(...)` 在狀態檔是純字串 `"AP8BgA=="`，不像自動 binary 的 `$b64` 物件 → 我期待：用了名叫 `b64` 的 helper 就會存成 `$b64` binary → 建議：說清楚 `aos.b64` 只是編碼字串，或另提供回傳 `$b64` 包裝物的函式。
- 現象：三支 reset 後排進 kernel，最後都進 `K/procs/done/{json-job,lua-job,python-job}.json` → 我期待：完成碼 100 會被 kernel 收走 → 建議：現況符合文件。
- 現象：剛 `aos-kernel add` 完立刻 `ls` 仍顯示佇列 0，下一回合才出現 → 我期待：add 成功後立即可見 → 建議：雖然 CLI 有提醒，最好讓 `ls` 也列「尚未被 tick 收進 state 的檔案」。

## 5. 五個故障案例

- 現象：Python 第二格丟例外後退出 1，畫面指出格號、函式、行號與 error 檔；state 保持 `pc:1`，重跑會再試同一格 → 我期待：失敗不推進並知道去哪看 → 建議：這是五個案例中做得最好的。
- 現象：Lua 定義四個函式但 return 表只列三格，執行器安靜地跑成 `trace:"124"`、`n:3`，漏掉的函式完全沒有警告 → 我期待：看得出可能漏列步驟 → 建議：至少在文件強調「未列進 return 的函式完全不可見」；能檢查時再加 lint。
- 現象：Python 跑到 `pc=2` 後在前面插一格，工具警告程式由 4 格變 5 格、函式名對不上，但仍執行目前第 2 格，造成 `second` 重跑 → 我期待：危險錯位預設停止 → 建議：變更後應拒跑，要求 `--continue-changed` 或 `--reset` 明確選擇。
- 現象：永遠等不到檔的 JSON 行程持續佔著 cpu0，`RUNS` 一直加、`LAST_EXIT` 永遠是 0 → 我期待：kernel 知道它是在等待，不把它顯示成普通 running → 建議：逐步工具應把 waiting 摘要交給 kernel 狀態。
- 現象：`aos-kernel ls` 看不出等待原因；只有另跑 `aos-step-json job.json --status` 才看到 `never-created.flag` 與 checks → 我期待：一個 `ls` 就能判斷下一步 → 建議：至少顯示 `WAITING <path>`，更理想是等待時不長期佔 CPU。
- 現象：`--reset` 後 state 回到 `{}`, `pc:0`，但舊的 `trace.txt` 仍保留 → 我期待：reset 只重設執行器，不會回滾程式副作用 → 建議：README 在 reset 旁直接警告「不會清輸出檔或撤銷外部動作」。

## 五個自問題

1. **容易上手：4／5。** 最短同步 Lua 路徑是寫 `endpoint.json`、寫 `job.lua`，再跑兩次 `aos-step-lua job.lua` 到 LLM 格；我實際走完整 Python 排程則需要 daemon、`aos-kernel-init --module`、boot、五次 step、`aos-kernel add`，約 9 個執行指令。
2. **容易理解：4／5。** `aos-llm call endpoint.json request.json result.json` 讓 endpoint/request 很直觀，`job.py` 的 `llm_submit → wait_for → consume_llm` 也看得懂；最容易想歪的是 wait 格會先推進 pc，以及 Lua `aos.b64` 不會自己形成 `$b64` 物件。
3. **複雜度藏好：3／5。** `aos.call(..., args=...)` 藏好了 argv 與擷取輸出；但我仍被迫知道 `/tmp/.../K/llm/results/<id>.json`、相對路徑以 `here/cwd` 哪一個為準，以及 `--wait` 不會替 kernel tick。
4. **控制結構簡單但全面：4／5。** JSON/Python/Lua 都有 `--status/--reset/--stderr`、pc/history/wait/完成碼 100；但 lisp 狀態是 JDN＋`.aos-step/`，其他三支是旁邊的 JSON，Python 自動掃 def、Lua 強制 return 表、JSON 只能 inst，介面沒有完全對齊。
5. **要背的東西少：3／5。** 日常至少要記 `endpoint.json/request.json/proc.json/job.*/*.state.json` 五種角色，及 `--status/--reset/--module/--name/--wait/--stderr` 六個常用旗標；環境至少有 `AOS_DAEMON_HOME`，玩 lisp 又要記 PATH，`AOS_EXEC/AOS_LLM/AOS_KERNEL` 雖非必需仍增加認知量。

## 前五名最該改的

1. **CLI 等 kernel 逾時後，必須撤單或明確回報「可能稍後執行」，不能用普通退出 1 製造未送出的錯覺。— 中**
2. **讓 `aos-kernel ls` 直接顯示逐步行程正在等待哪個檔，最好等待時能讓出 CPU。— 中**
3. **補一份從 local endpoint 到第一支 LLM step 的完整、只含本機設定的 copy-paste quickstart。— 小**
4. **程式跑一半變動時預設拒跑，要求使用者明確選 `--reset` 或 `--continue-changed`。— 中**
5. **統一並說清 Python bytes、Lua binary、`aos.b64` 與 `$b64` 的關係。— 小**
