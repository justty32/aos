## 1. 先把 OS 那層架起來

四個指令一次過，沒卡。`init` 會把「開機／排行程／拿掉行程」三行下一步直接印出來，這招很好。

- **現象**：README 寫 `cd proto4-3` 然後 `./aos-kernel-init K`，K 會長在 repo 裡 → 我期待範例用絕對路徑，不然照抄的人第一件事就是弄髒 repo → 建議範例改成 `aos-kernel-init /tmp/myK`。
- **現象**：README 有時 `./aos-kernel`、有時 `aos-kernel`、還有 `(cd K && aos-kernel-tick)` → 我期待一致 → 建議統一 `./`，或明說「自己加 PATH」。

## 2. 第一層 `aos-llm`

- **現象**：我照 README 寫 `{"local":{...}}`，回 `ENDPOINT 不是 endpoint 物件或 endpoints.json`、rc=2，卡住。最後靠 `llm-cpu init /tmp/x` 生一份範例才知道真格式是 `{"default":"local","endpoints":[...]}` → 我期待 README 就有一個五行的範例檔 → **建議把範例 JSON 貼進 README**（這是本輪最大的坑）。
- **現象**：把 model 打錯成 `google/gemma-9-nonexistent`，LM Studio 照樣拿它載著的模型回答，燒了 9.8 秒、789 tokens，**回來才**判 `model_mismatch`、`text` 給 null → 我期待錢／時間別先花掉 → 建議送出前先比對 `/models`，或 README 明講「mismatch 是事後檢查，費用照算」。
- **現象**：失敗結果的 `model` 欄意思會變——mismatch 時是「對方實際回的」，connect 失敗時是「我設定的」 → 我期待固定一種 → 建議 `model` 永遠是回應的（沒回應就 null），設定值看 `model_requested`。
- **現象**：結果檔九成是 `raw`（連 reasoning_content 全文都在），`--wait` 直接把整份倒到終端機 → 我期待預設看到答案 → 建議 `--wait` 只印 `text`＋結果檔路徑。
- 看得懂的欄位：`ok/text/finish_reason/usage/ms/error`。看不懂的：`usage.cached`（一直 null，不知道是「沒有」還是「不支援」）、`raw` 的存在意義。
- **退出碼跟 README 完全一致**：成功 0、`ok:false` 1（含 REQ 帶 `model`）、endpoint 解不開 2。這點很讓人安心。

## 3. 第二層：LLM 排程當 kernel module

- **現象**：我第一步照 OS 那節 `init` 沒帶 `--module`，等要玩 LLM 時補 `--module` 得到「已經有這個資料夾了，不動它」rc=1，只能整個 K 砍掉重來 → 我期待能補掛，至少要有警告 → 建議 proto4-3 README 的 init 範例就帶 `--module` 註解一行「事後補不了」。
- **現象**：module 自動生的 `K/llm/endpoints.json` 裡 model 是佔位字串 `loaded-model-id`，不改就 `model_mismatch`；README 只寫 `$EDITOR K/llm/endpoints.json`，沒說「一定要改哪一格」 → 建議那行後面補「把 local 的 model 換成你 `aos-llm models` 看到的 id」。
- **現象**：忘了 `export AOS_DAEMON_HOME`，`aos-kernel ls` 大字印 **`daemon dead`**，但同一時間 `aos.llm_submit` 照樣送得出去、結果照樣回來 → 我期待別假警報 → 建議 ls 分開講「找不到 daemon 家（AOS_DAEMON_HOME 沒設？）」跟「真的死了」。
- 好的地方：`ls` 多一行 `llm: queued 0 running 1 done 1 endpoints: local 1/1, deepseek 0/2`，一眼看得出容量；同名丟第二次回 `id 已經存在：hello` rc=1，乾脆；沒 daemon 時回 `kernel 沒回應（daemon 在跑嗎？aos-kernel ls K 看看）` rc=1，指路很清楚。
- **現象**：預設 endpoints.json 內建一個 DeepSeek（要錢）的 endpoint → 我期待預設檔別放會花錢的東西 → 建議跟 `pi` 一樣加 `enabled:false`。

## 4. 三支各寫一支自己的程式

三支都寫完、都跑完、都被 kernel 收進 `procs/done/`。**`wait_for` 是這輪最好用的東西**：JSON 那支等我用 shell 慢慢寫出的 `signature.txt`，檔一到，同一次呼叫就接著跑最後一格，`history` 還多一筆 `(wait)`，跟 README 寫的一模一樣。Python 那支 `llm_submit → wait_for → 讀進 state` 三格也是一次通。

- **現象**：Python 的 `aos.call` 有哪些選項（`capture`／`read`／`json`）只寫在 **Lua** 那節；我是照 Lua 的猜 `capture=True` 才成功 → 建議 Python 那節也列一次。
- **現象**：README 說「`llm` 會保留 `out.req.json`」，實際檔名是 `ans.json.req.json` → 建議寫成 `<OUT>.req.json`。
- **現象**：Lua 的 `ms` 永遠是 0——那格打 LLM 花了 8 秒（看 `at` 前後差得出來），`ms` 還是 0 → 建議拿掉或修掉，現在等於騙人。
- **現象**：Lua 裡 `aos.b64(s)` 回**純 base64 字串**，而不合法 UTF-8 的字串會自動變 `{"$b64":...}`；同一份 state 裡兩種長相並存（`"sig":"AP9MVUEB"` vs `"raw":{"$b64":"AP4D"}`），只有後者讀回來會還原 → 建議 `aos.b64` 直接回 `{"$b64":...}` 那個物件，或 README 明講差別。
- **現象**：`aos-step-lua --help` 回「不認得選項」rc=2，另外兩支有正常 help → 建議補上。

## 5. 故意弄壞五樣

- **Python 丟例外**：`aos-step-py: 第 1 格 two（0 起算，PROG 第 4 行）失敗：我故意炸的（全文：.aos-step-py/error 或 --status）` rc=1。**滿分訊息**，我完全知道下一步。state 放不進 JSON 也一樣好（會講「object」）。
- **現象**：`.aos-step-py/error` 是**每個資料夾一份**。我在同一資料夾跑第二支壞程式，第一支的 traceback 就被蓋掉了 → 建議改成 `<PROG>.error` 或 `.aos-step-py/<PROG>.error`。
- **Lua 少一格**：`return` 表裡刪掉 `{name="seal",...}`，**完全沒有警告**，rc=0，那個函式就這樣人間蒸發（少了 `name` 才會回「第 2 格缺 name」rc=2）→ 建議偵測「檔裡有 local function 沒被列進 return」時警告一句。
- **跑到一半插一格**：兩行警告都到位——「PROG 改過了（上次 4 個、現在 5 個）…確定要重來就 `--reset`」「第 2 格函式名對不上（上次 c、現在 a2），仍照目前程式執行」，然後照新程式跑完。這段做得很好。
- **`wait_for` 等一個永遠不來的檔（排在 kernel 上）**：`aos-kernel ls` 顯示 `PROC 3 / RUNS 11 / LAST_EXIT 0 / running`——跟一支健康的長程式**長得一模一樣**，看不出它在等誰、等多久，而且它會永遠占著兩顆 CPU 的其中一顆。`stderr:"err.txt"` 也是空的，只有自己去下 `--status` 才看得到 `waiting`。→ 建議 kernel `ls` 把 `waiting.for` 跟 `checks` 撈上來顯示。
- **失敗的格排在 kernel 上**：`LAST_EXIT=1` 但 kernel 會**永遠重跑**，不會收工也不會標記；`err.txt` 一樣空的 → 建議連續失敗 N 次就丟進 `procs/bad/`。
- **`--reset` 之後再跑**：Python 那支重跑時 `aos.llm_submit(K, req, "pystep1")` 撞 `id 已經存在：pystep1`，整支程式就在第 1 格永久卡死。這是「重來」最自然的動作，卻一定會踩到 → 建議 `--reset` 順手清掉自己送過的請求，或 `llm_submit` 的 name 自動帶序號。

## 六個問題的答案

① **上手**：OS 層 4 個指令、LLM 第一層 2 個、逐步 1 個——**如果 README 有 endpoints.json 範例**，從零到「Python 逐步程式打通 LLM」大概 8 個指令 15 分鐘。實際上我在 endpoints 格式上耗掉最久。

② **理解**：`endpoint`／`request`／`module`／`wait_for` 一講就懂。想歪兩個：（a）`llm_submit` vs `llm`——README 只在 Python 那節提「拆成兩格」，我一開始以為 `llm_submit` 是「非同步版的 llm」，其實是「丟給 kernel 排隊，跟同步版走完全不同的家（`K/llm/` vs 我自己的 endpoints.json）」；（b）`$b64` 我以為是「一種寫法」，其實是「只有這一個 key 的物件」這條規則。

③ **藏好了嗎**：被迫知道的細節有——`K/llm/results/<name>.json` 的檔名規則（不知道就不會用 `wait_for`）、`.aos-step-py/error`、`AOS_DAEMON_HOME`、「add 之後下一回合才看得到」、`procs/` 的 id 會回收（我 `rm 3` 之後新排的又叫 3，跟 `done: 1, 2` 擺一起很容易誤會）。

④ **一致性**：`--status`／`--reset` 三支一致，但 proto4-4 那支叫 `aos-step`（不叫 `aos-step-janet`）、`--status` 印 JDN 不是 JSON、欄位是 `:changed`／`:error` 而不是 `steps`／`history`／`last`、沒有 `--stderr`、也沒有 b64。命名也分家：`wait_for`／`llm_submit`（py、lua）vs `aos/wait-for`／`aos/llm-submit`（janet）。**缺的共通功能**：四支都沒有「這格失敗過幾次」的計數，kernel 也沒有逾時。

⑤ **要背的**：1 個環境變數日常一定要（`AOS_DAEMON_HOME`；`AOS_EXEC`／`AOS_LLM`／`AOS_KERNEL` 用不到）、4 個檔名（`inst.json`、`endpoints.json`、`<prog>.state.json`、`K/llm/results/<name>.json`）、3 個旗標（`--status`／`--reset`／`--wait`）。不算多，但 `.aos-step-py/error` 跟 `procs/done` 是「出事才會知道」的，最好在錯誤訊息裡自己講（Python 有講，其他沒有）。

## 前五名最該改的

1. **proto4-5 README 貼一份 `endpoints.json` 完整範例**——現在照 README 寫出來的檔一定 rc=2，這是唯一一個「照做也做不出來」的地方。（小）
2. **`aos-kernel ls` 把 `waiting` 跟連續失敗次數顯示出來**——現在「在等一個永遠不來的檔」跟「每秒炸一次」都長得像健康行程，還永久吃著 CPU 槽。（中）
3. **`--reset` 之後 `llm_submit` 撞 id**——重來是新手最常做的動作，一做就死在同一格。`--reset` 順手清掉，或名字自動帶序號。（小～中）
4. **model 打錯要先擋**——現在是送出去、等答案、燒完 token 才判 mismatch；本機只是慢，接雲端就是真花錢。（中）
5. **失敗的行程要有下場**——連續失敗 N 次進 `procs/bad/`，順便讓 inst 的 `stderr` 收得到步驟錯誤（現在 `err.txt` 永遠是空的）。（中）

（Lua 的 `ms` 恆為 0、`aos-step-lua --help`、`.aos-step-py/error` 撞名、`<OUT>.req.json` 檔名寫錯——都是小修，值得順手做。）

## 我跑過的指令（精簡）

```sh
export AOS_DAEMON_HOME=/tmp/play3-opus/home
setsid -f ./aos-daemon ; ./aos-daemon-ctl ls
./aos-kernel-init /tmp/play3-opus/K --ncpu 2 ; ./aos-kernel-boot /tmp/play3-opus/K ; ./aos-kernel ls /tmp/play3-opus/K
./aos-daemon-ctl rm /tmp/play3-opus/K/inst.json
./aos-kernel-init /tmp/play3-opus/K --ncpu 2 --module /abs/proto4-5/llm_cpu_module.py

./aos-llm models endpoints.json#local
./aos-llm call endpoints.json#local request.json result.json          # rc=0
./aos-llm call ep-badmodel.json request.json bad-model-out.json       # rc=1 model_mismatch
./aos-llm call ep-badport.json  request.json bad-port-out.json        # rc=1 connect
./aos-llm call endpoints.json#nosuch request.json /dev/null           # rc=2
./llm-cpu init /tmp/play3-opus/llmcpu-sample        # 挖 endpoints.json 範例用

./aos-kernel llm /tmp/play3-opus/K reqs/q1.json --name hello --wait 60
./aos-kernel llm /tmp/play3-opus/K reqs/q2.json --name cache          # 不等
./aos-kernel llm /tmp/play3-opus/K reqs/q1.json --name hello          # rc=1 id 已存在

aos-step-json job.json / --status / --reset      # 4 格，含 wait_for signature.txt
aos-step-py   job.py   / --status / --reset      # 5 格，call+args、llm_submit、wait_for、bytes
aos-step-lua  job.lua  / --status / --reset      # 4 格，aos.llm 同步、aos.b64
aos-step-py   boom.py  ；njs.py ；m.py（插一格）；aos-step-lua bad2.lua

./aos-kernel add /tmp/play3-opus/K <各支的 proc.json>
./aos-kernel rm  /tmp/play3-opus/K 3
./aos-daemon-ctl stop
```
