- 現象：`models endpoint.json` 約 0.03 秒列出四個模型，第一行就是 `google/gemma-4-e4b` → 我期待：能在花 token 前確認模型 id → 建議：保留「先 models、再 call」的順序。
- 現象：錯模型約 0.03 秒退出 1，明寫「未送出 chat 請求」，`usage` 全為 `null` → 我期待：不打模型、不花 token → 建議：修法有效，不用再改語意。
- 現象：base URL 指向空埠約 0.03 秒退出 1；先記 `/models` 預檢略過，再回 `connect refused` → 我期待：快速失敗並指出連不上 → 建議：可以把最後的連線錯誤放第一句，預檢細節留在 `notes`，新手更容易掃讀。
- 現象：結果檔同時提供 `text`、`usage`、`model_requested`、`raw` 等欄位 → 我期待：平常只看答案，出錯才往下挖 → 建議：README 的「日常／除錯／原始資料」三組分類很好，保留。

## 2. LLM 排程作為 kernel module

- 現象：`daemon → kernel-init --module → kernel-boot` 可直接跑通，第一個 tick 自動建立 `K/llm/endpoints.json` → 我期待：不用自己建整棵 LLM 家目錄 → 建議：保留自動建家。
- 現象：自動建立的模型是 `loaded-model-id`，背景 tick 的提醒沒有直接出現在終端；我是查看檔案才發現要改 → 我期待：boot 或 `aos-kernel ls` 明顯提醒 placeholder 尚未換掉 → 建議：在 `ls` 顯示 `model needs configuration`。
- 現象：`aos-kernel llm ... --wait 60` 約 0.93 秒取得「甲。」及結果路徑 → 我期待：像同步呼叫一樣簡單，但工作仍由排程器完成 → 建議：這個介面很順。
- 現象：不加 `--wait` 約 0.13 秒回覆「下一回合處理」與結果路徑 → 我期待：立即拿到可追蹤的位置 → 建議：可再補一個 `aos-kernel llm status K NAME`，免得自己找檔案。
- 現象：同名同內容第二次約 0.03 秒成功，明說「同一張請求已存在」 → 我期待：不重送、不重花 token → 建議：修法有效，訊息也夠白話。
- 現象：同名不同內容約 0.03 秒退出 1，指出撞在 `running` → 我期待：拒絕覆蓋並告知撞在哪 → 建議：修法有效。
- 現象：結果檔已出現時，`aos-kernel ls` 一度仍顯示 `running 1` → 我期待：結果存在後立即顯示 done → 建議：註明 `ls/state.json` 最多落後一個 tick，或在 `ls` 時順手刷新 module 狀態。
- 現象：daemon 停掉後送 `--wait 3`，3.04 秒後明說「沒送出去，已撤單」；`K/syscalls/` 無殘件 → 我期待：逾時後不留下將來可能偷跑的工作 → 建議：修法有效。
- 現象：重開 daemon、重新 boot 並等 5 秒，`offline-one` 仍沒有結果 → 我期待：已撤掉的單不會復活 → 建議：這條已真正解決。

## 4. 五個問題

1. **容易上手：3/5。** 完整指定流程從讀 README 到第一支逐步程式出答案約 3 分 17 秒；最短路徑約四階段、九個 shell 指令，另要建四份檔。例：`aos-llm models endpoint.json` 很直觀；但 `job.py` 裡的 `aos.llm_submit(K, req, name)` 必須讀原始碼才寫得出來。
2. **容易理解：3/5。** endpoint、request、`strict_model` 和結果三組欄位講得清楚，例如錯模型真的在 chat 前被擋；module 也能從 `aos-kernel-init ... --module llm_cpu_module.py` 理解。但 `aos.llm` 與 `aos.llm_submit` 的差異只列名字沒解釋，最容易讓我以為兩者都會排進 kernel。
3. **複雜度藏好：3/5。** `aos-kernel llm` 成功藏住 requests/running/results 搬運，直接呼叫也只需 `endpoint.json`。反例是必須知道 `AOS_DAEMON_HOME` 要一路繼承，以及為查函式簽名被迫讀 `proto4-6/aos_py.py`。
4. **控制結構：4/5。** `aos-llm models/call` 加 `aos-kernel llm` 已涵蓋查模型、同步呼叫、排程呼叫；直接層與排程層的重疊有合理用途。主要缺口是沒有像 `aos-kernel llm status K NAME` 的查單指令，也沒有取消已送出請求的入口。
5. **要背的東西少：2/5。** 實際碰到至少 `endpoint.json`、`request.json`、`K/llm/endpoints.json`、`K/llm/results/*.json`、`job.py`、`inst.json`；旗標至少有 `--module`、`--name`、`--wait`、`--json`、`--reset`。環境則要記 `PATH`、`AOS_DAEMON_HOME`，Python 工具另可能用 `AOS_KERNEL`／`AOS_LLM`／`AOS_EXEC`。

3. 讓 `aos-kernel ls` 明顯警告 `K/llm/endpoints.json` 還是 `loaded-model-id`。（小）
4. 改善或說明 `aos-kernel ls` 的 `WAIT`／running 狀態落後問題。（中）
5. 增加 `aos-kernel llm status K NAME`，集中顯示 queued、running、done、結果路徑。（中）
