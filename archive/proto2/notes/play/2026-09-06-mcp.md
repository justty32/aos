# aos-mcp 試玩

## 做的時候的坑

- `agent` 與 `llm` 是兩個世界。要讓整段自己走，兩邊都要開鐘。
- `aos-user listen --new --once` 才能等下一封，不會把舊回覆再印一次。
- `agent_inbox_drop` 沒有現成 CLI。這一支只好自己解析 `--home`，再原子寫一個 JSON 檔。
- 一般工作流要補 code map，但這輪只准動四個檔，所以沒有補。

## 玩的紀錄

- `world_setup` 建到 `play-mcp/`。主世界改名 `mcp-agent`。
- agent 的 `llm.json` 指向共用 LLM，指定 `deepseek-flash`。
- `clock_register` 成功。pid 是 2981509，每 0.5 秒一格。
- 我說：「這是 aos-mcp 試玩。請只回一句：MCP 試玩成功，我能替使用者說話。」
- agent 回：「MCP 試玩成功，我能替使用者說話。」
- `agent_status` 是 step 16、busy 8、uptime 8 秒。最後 `clock_unregister` 成功。

## 玩的時候的坑

- `agent_status` 會帶整個共用 LLM 的今日用量。資料很多，這次真的被截到 4000 字。
- 共用 LLM 同時有別輪請求，但 `deepseek-flash` 約 8 秒就回來，沒有卡住。

## 缺什麼接點

- 缺一支「指定來源，把信投進 agent inbox」的 CLI。現在 `agent_inbox_drop` 自己寫檔。

## 介面簡不簡潔（我自己的評分與哪裡可以更簡）

8/10。日常只要世界路徑與一句話。daemon 與 LLM 路徑不用每次重填。
目前 agent 與 LLM 要各 register 一次。以後若常忘，可以再加一個成對開鐘的高階工具。

## 內部機理簡不簡單

8/10。大多數工具只把參數交給既有 CLI。
例外只有 world_setup 的 git 解包與 inbox_drop 的一封 JSON。

## 效能與邊緣狀況（留給使用者看）

- `world_setup` 會把 git archive 整包先放進記憶體。範例很小沒差；以後變大會慢。
- 同一個 `dest` 重跑會蓋同名檔，也可能留下舊檔。proto2 先不處理。
- `agent_listen` 每次開一支短命子行程。現在簡單優先。
- `source` 只擋路徑名字，沒有做更多格式規則。
