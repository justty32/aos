# jobs 實作與試玩

## 做的時候的坑

- 規格原本要加 `aos-agent job-finish`，但本輪不准改共用檔。完成器改成 `.aos/inst` 第三行直接跑 Python。
- `register_clock` 會等 daemon 回覆，不是規格文字寫的 `--no-wait`。先用現成接點，不另繞一套。

## 玩的紀錄

- 人：「用 run_long 跑 `sleep 15; echo done` 然後告訴我做完了沒」
- agent：「已經開跑了：job `sleep-done-test` 目前還在跑……所以還沒做完。」
- 完成信：「job sleep-done-test 做完了：exit 0，跑了 16 秒。stdout 最後幾行：done」
- agent 讀完信：「做完了！job `sleep-done-test` 已跑完，exit 0，輸出就是 `done`。」
- job 的鐘完成後自己消失。父 agent 的鐘也在玩完後手動 unregister，沒有留鐘。

## 玩的時候的坑

- 模型在 `run_long` 後又叫了一次 `jobs_list`，才回第一句。多花一格，但沒有卡住等 15 秒。
- 實跑的 `sleep 15` 記成 16 秒。秒數從建立 job 開始算，包含等 daemon 開鐘的時間。

## 缺什麼接點

- `register_clock` 沒有 `no_wait` 選項。現在通常很快，但最差會等十秒。

## 介面簡不簡潔（我自己的評分與哪裡可以更簡）

- 9/10。四個工具各做一件事。`run_long` 只有指令與可選名字。
- 以後若固定一小時不夠，才需要加 `max_seconds`；現在不先加。

## 內部機理簡不簡單

- 8/10。整包只有一個 Python 檔。job 也只靠 shell、JSON、daemon。
- 完成器塞成一條很長的 Python 指令，不好讀，但能守住四行 inst 和不新增共用子命令。

## 效能與邊緣狀況（留給使用者看）

- 完成時會把完整 stdout、stderr 讀進記憶體。log 很大時會慢，也可能吃很多記憶體。
- 完整 log 不限大小。跑久後 jobs 資料夾會一直長。
- 鐘或機器在 result.json 寫出前死掉，指令之後會從頭再跑。
- 沒有併發上限。一次開很多 job，就會真的一起跑。
- 結果檔和信不是原子寫入。中途斷電可能留下半個 JSON。
