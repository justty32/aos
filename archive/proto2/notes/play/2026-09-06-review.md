# review：回顧與自我優化

## 做的時候的坑

- 規格要算「同類任務平均兩倍」，但現有 `on_act` 沒有任務編號或 tag。第一版只在 ledger 已有 `task_key`、`task_id` 時算。
- `on_idle` 看不到中間的 llm、wait、act 格。我用 `step` 是否相連判斷「連續 3 格 idle」。
- 成本門檻的欄位名規格沒定。我放在 `llm.json` 的 `review.daily_cost` 和 `review.tool_cost`。
- 新增 pack 本來要同步 code map，但本輪硬規則只准動四個指定檔，所以沒有動 code map。
- 教訓格式同時要寫「之後平均」，剛學到時不一定已有之後的資料。第一版照拍板格式收數字；下次回顧只負責把兩邊都沒下降的標成 `【無效】`。

## 玩的紀錄

我在 scratchpad 的 `play-review` 開一個世界，用共用 LLM 的 `deepseek-flash`。
先叫它讀檔、查 `pwd` 和字數、看自己的格數。

關鍵對話：

> 使用者：回顧一下你剛剛做得好不好，寫一條教訓。
>
> agent：這種偶發的小事不該寫成教訓，寫了只會污染記憶——所以我沒有新增任何教訓。

我接著明確叫它把同一條 `head -n 1 notes.txt` 分三次跑。
最後叫它看最近 50 格。

> agent：已照你要求寫好教訓：「重複讀檔：原本平均 0 元／1 格 → 讀過的內容先從記憶回、不重跑 → 之後平均 0 元／0 格」。

`review_recent` 當時看到 3 次 `sh`、0 次錯誤、0.002 秒、12309 token、成本 `null`，也抓到「連續呼叫 sh」。
agent 最後真的用了 `lesson_add`，教訓有寫進 `memory/lessons.md`。
玩完已 unregister 自己的世界，沒有留鐘。

## 玩的時候的坑

- 第一次 agent 自己選 `n_steps: 8`。一次 LLM 工具往返就跨過好幾格，所以它看不到稍早的 ledger。
- `deepseek-flash` 在共用 `engines.json` 沒有 price。帳本的 cost 是 `null`，回顧不亂猜；為了測教訓格式，我明講沒單價用 0。
- 預設 prompt 說偶發小事不要寫教訓，模型第一次因此拒絕使用者的「寫一條」。這個判斷本身合理，但也表示直接要求不一定會寫。
- 模型前兩次沒有照固定句型寫 `lesson_add`，都拿到白話錯誤；第三次照錯誤裡的例子才成功。
- 三次工具同一格一起跑。ledger 三行的 `step` 相同，所以「格數」跟「呼叫次數」不能混著看。

## 缺什麼接點

- 缺「現在是哪個任務、任務編號、粗略 task key 或 tag」的接點。沒有它，單一任務超過同類平均兩倍只能等 cost 包以後自己把欄位寫進 ledger。
- 缺一個直接拿「上次任務開始格」的接點。現在模型自己猜 `n_steps`，很容易像實玩一樣選太小。

## 介面簡不簡潔（我自己的評分與哪裡可以更簡）

7／10。
六個工具的名字、參數和錯誤都算直白。
`lesson_add` 的固定句型偏長，模型也連錯兩次。
`review_recent` 若能直接填「上一個任務」，會比猜 `n_steps` 更簡單；目前沒有這個接點。

## 內部機理簡不簡單

8／10。
全部在一個 pack，只用 `os`、`json`、`glob` 和文字檔。
沒有資料庫、索引或背景 LLM。
代價是同一份 ledger 會被幾個工具各自掃一次，程式也長到五百行左右。

## 效能與邊緣狀況（留給使用者看）

- `review_patterns` 每次逐行讀最近 30 天 ledger。帳很多後會慢。
- lessons、archive、prompt 覆蓋都沒有鎖。兩個進程同時寫會互蓋。
- 壞掉或搬走的 JSON／JSONL 直接跳過，不補舊帳。
- 時間有時區時只做粗略比較。跨時區的 `since` 可能不準。
- 「拿很多內容卻沒用」目前用回傳字數和最後回話字數粗估，不懂語意。
- 沒有明確 adopt 紀錄時，只用短結論是否出現在後續記憶或 outbox 判斷；證據不足就回「不知道」。
