# bigmem 實作與試玩

## 做的時候的坑

- 規格預想新增 `history_read`、`mem_send`、`ref_save` 等 Ctx 接點。但本輪不能改共用檔。兩包只用現有路徑與 JSON 把手完成。
- `on_act` 看得到工具結果，卻不能換掉即將寫進對話的字串。現在先存檔與記摘要，下一次 `on_system_prompt` 再換指標。
- 最上層規則要求同步 code map，但本輪准動清單不含 code map。本輪沒有越界修改。

## 玩的紀錄

- 我叫 `bigmem-agent` 分別存「天空是藍色」、「草地是綠色」、「香蕉是黃色」，再找「藍色」。
- 第一輪模型回：「三條記憶已經分別送出……查『藍色』的請求也排好了。」
- 記憶世界收到 4 個請求。SQLite 裡有 3 筆記憶。
- mem 結果成了 4 封信。模型用 `inbox_read_all` 讀完。
- 最後模型回：「查『藍色』找到了一條：天空是藍色。」

## 玩的時候的坑

- 第一版提示只說結果稍後進信箱。模型在同一輪不停叫 `inbox_sources` 等結果。但結果只有回 idle 才收，變成自己等自己。已把提示改成「排完先回話，不要輪詢」。
- 改提示後模型會先結束這輪。下一個 idle 收到 4 份結果，整條走通。

## 缺什麼接點

- 缺一個能在工具結果寫進 `prompts.json` 前，直接回傳替代值的掛勾。
- 缺記憶世界專用的 `mem_send`／`mem_take`。現在 bigmem 自己走 requests/results。
- 缺安全的 `history_read`／`history_replace`。現在歸檔工具直接讀寫自己的 `prompts.json`。
- 缺送主線 LLM 前可擋下請求的接點。沒有它，80000 字門檻不能真的保證「先停問模型」。

## 介面簡不簡潔（我自己的評分與哪裡可以更簡）

- 8/10。五個記憶工具和三個 ref 工具都只有必要參數。
- `mem_archive_history` 還要人自己算序號。以後若有「最舊幾則」接點，可以再少一個選擇。

## 內部機理簡不簡單

- 8/10。ref 一檔、agent 端記憶一檔、SQLite 世界一支腳本。
- 因為缺替代工具結果的接點，ref 多了一段 pending 摘要與下一輪置換。

## 效能與邊緣狀況（留給使用者看）

- SQLite 的 `%文字%` 搜尋資料多後會全表掃描。先求簡單，之後換 MongoDB 文字索引。
- `ref_list` 每次會掃 refs 資料夾。指標很多後會慢。
- 同一請求重送、同時改對話、資料庫備份、權限、循環 ref、檔案被搬走都沒做。
- 40000／80000 字的自動觸發未接。這輪只有手動 `mem_archive_history`；門檻值已照拍板寫進文件。
