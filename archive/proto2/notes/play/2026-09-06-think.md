# think 深度思考工具包

## 做的時候的坑

1. 規格寫「沿用 wait 分流」，但 pack API 的 `llm_request` 是旁線請求。它不會拿走主線的 `wait`。本輪照指定接點做：工具當格回開始，`on_result` 旁線收件。
2. pack API 沒有「目前實際會用哪台 engine」的接點。pack 得自己讀 agent 的 `llm.json`、LLM 的 `defaults.json` 和 `engines.json`。
3. 金額只能估。引擎沒寫 `price` 就只能留 `null`。送出去之後也不能把請求收回。
4. 多步最後一發可能正文空白。不能拿空白蓋掉前面可用的結論，所以另外保留 `best`。

## 玩的紀錄

第一輪：

> 使用者：設計一個公平分披薩給三個人的方法，先深思再答。

> agent 呼叫：`think`

> 工具：開始想了 id=20260906-172332-917956

這發用了 5999 個 completion token。
5999 個全是 reasoning token。
正文是空的。
agent 看不到結論，自己改叫 `think_steps` 重跑。

第二輪用乾淨世界重玩：

> agent 呼叫：`think_steps`

> 信箱：想完了 id=20260906-172827-938197

> agent 呼叫：`conclude`

> conclude：採用「切分者最後選」規則，讓切分者有動機將披薩切得盡量均等。

> agent 最後回答：一人切、兩人先挑、切的人拿剩的。切完讓先挑的人檢查校準。

三步真的各送一個請求。
第三步又只剩隱藏 reasoning，正文空白。
修正後狀態是 `budget_exceeded`，但 `conclude` 有拿到第二步的最佳結論。

## 玩的時候的坑

1. 快模型會把很短的披薩題擴寫成一大串理論比較，讓深思變得太重。
2. `think` 等待時，快模型一直叫 `thoughts_list` 和信箱工具。它不會真的安靜等通知。
3. 第一發正文空白後，模型違反「同題不要重複送」，自己又開一份 `think_steps`。
4. deepseek-flash 可能把整個輸出額度都吃在 reasoning，最後沒有 content。
5. 模型最後補出的「讓兩人校準」沒有嚴格公平保證。深思有跑，不代表答案一定正確。

## 缺什麼接點

1. 缺一個每格都會叫的 `on_tick(ctx)`。現在逾時只能在下一個 idle、工具、回話或組 prompt 的格才發現。
2. 缺一個「旁線完成前先睡，不再叫主線 LLM」的接點。現在模型等待時會一直輪詢，白花 token。

## 介面簡不簡潔（我自己的評分與哪裡可以更簡）

8/10。

- 常用流程只有 `think` 或 `think_steps`，完成後 `conclude`。
- `budget` 四個鍵都直接對應規格，沒有多加參數。
- `thought_read` 的參數叫 `id`，`conclude` 卻叫 `thought_id`。統一會更好，但規格就是這樣寫。

## 內部機理簡不簡單

8/10。

- 全部在一個 Python 檔。只用 `os`、`json`、`datetime`。
- 狀態只多一張「請求檔名到 thought id」的表。其餘都放 `thoughts/<id>/`。
- 讀 engine、估錢、整理 usage 佔了不少行。若共用接點以後提供這些，可再縮短。

## 效能與邊緣狀況（留給使用者看）

1. `thoughts_list` 會列整個 `thoughts/` 再取最近 20 個。資料非常多時會慢。
2. 每一步把完整 LLM result 存進 JSON。長期使用會吃磁碟。
3. 沒有自動清理舊思考。
4. 沒有鎖。同一個 agent 若被兩個進程同時推，可能互相蓋 state 或 meta。
5. 金額預估只看 token 上限和單價。供應商實際回多少、怎麼算 reasoning，仍可能超過估計。
