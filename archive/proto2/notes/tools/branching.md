# branching 工具包——分幾條線同時想

一句話：深度思考是一條線往下想，分支思考是在同一個地方開幾條線同時想，再把短結論收回來。

它是深度思考的延伸，不重做 `think`、`critique` 那些工具。
`thoughts/` 放一條線的多步內容，`branches/` 放同一題的多條線。
兩邊的 id 都用時間戳，看到名字就知道是哪一次思考。

## 分岔

### `fork(directions: [..], budget?, mode?)`

- `directions` 放二到三個互不重疊的方向。每個方向只寫一件事。
- `mode` 是 `llm` 或 `kid`，預設 `llm`。
- `budget` 可寫每條最多 token、全部最多 token、最多花多少錢。
- 工具先把現在的 `prompts.json` 抄到 `<home>/branches/<id>/base.json`。
- 每個方向再抄一份，最後加一則：「你負責這條：……。只想這條。想完只回一段總結，不要叫工具。」
- 這一格把全部工作丟出去，立刻回「開了 N 條，id=……」。不等結果。
- 回傳另附預估最多 token、預估最多花費、目前實花 0。沒有單價就把錢寫成 `null`，不亂猜。

資料夾先用這個樣子：

```text
branches/<id>/base.json
branches/<id>/meta.json
branches/<id>/01/prompts.json
branches/<id>/01/summary.md
branches/<id>/02/prompts.json
branches/<id>/02/summary.md
```

`meta.json` 記方向、模式、請求檔名、還在跑的、已完成的、預算和花費。
每條的 `prompts.json` 只屬於那條線。主線不會讀它。

## 每條線在哪裡跑

建議第一版預設直接丟 N 個 LLM 請求到 `requests/`。
這是最省事的做法。一格可以全丟。
`max_concurrent` 會決定同一台引擎同時跑幾條，塞不下的自然排隊。
結果各自回到 `results/`，不用多養世界，也不用收時鐘。

每條開一個小孩 agent，只留給真的要查資料、叫工具、跑很多輪才想得完的題目。
這種情況用 `mode: "kid"`。
小孩放在 `kids/branch-<id>-<序號>/`，初始記憶就是那條副本。
它做完只交一段總結，工具包再把總結收進 `branches/`。
它比較重，還要處理回話、停止和留下來的資料夾，所以不當預設。

每條開一個 job 世界不選。
job 適合跑一段會結束的命令，不適合會看記憶、可能叫工具的思考。
若 job 也要懂這些，它就只是比較難用的小孩。

## 收攏

### `join(branch_id)`

- 每次呼叫先收一次結果。
- 還沒全到，就回「還差 N 條」，並列出還在等的序號。
- 全到了，就把各條總結合成一則工具結果放回主線。
- 每條總結最多 800 個中文字。超過就截斷，並清楚標出。
- 工具結果只放方向、總結、用量和花費。不放各條思考過程。
- 主線模型看完後，自己選贏家，也可以把幾條的好處合起來。

第一版不要再開一輪「評審」請求。
主線本來就有題目和上下文，讓它自己選就夠了。
多一個評審會再花一次錢，也可能只是把選擇往後推。

主線在分支跑的時候沒有換成任何一條線。
所以「回到分岔口」就是 `join` 完成的那一格。
主線的 `prompts.json` 只會多看到 `fork` 的開工回話與 `join` 的總結。

### `adopt(branch_id, n)`

建議做。
它把第 n 條的完整 `prompts.json` 取代主線的 `prompts.json`。
`kid` 模式就採用那個小孩最後的完整記憶。
有時某條線已經把事情做完，只拿 800 字總結反而會丟掉能直接接著做的內容。
採用前先檢查分支已完成，序號存在，而且 id 屬於自己。

## 再分岔

第一版深度限 1。
分支裡不能再 `fork`。
這會讓數量成倍增加，花費與收攏關係也很快看不懂。
真的撞到需要時，再讓 `meta.json` 多記父分支。

## 狀態機

建議把分支進度記在 `state.json`，不要把結果寄進信箱。
信箱是人和 agent 的消息。分支是同一個工具呼叫留下的工作，混在一起會讓模型誤以為別人在說話。

`state.json` 加這一塊：

```json
{"branches":{"<id>":{"pending":["01.json","02.json"],"done":[]}}}
```

`wait` 每格先照舊看主請求，再把所有 `pending` 掃一次。
看到一個結果就搬到 `done`，抽出最多 800 字的總結，寫進該條資料夾。
掃完就結束這一格，不等 N 個一起出現。
`join` 也會先掃一次，所以模型不用猜結果是不是剛好到了。
分支內容只落 `branches/`，不接進主線 `prompts.json`。

## 預算與記帳

第一版最多三條。每條預設 `max_tokens: 1500`，全部最多 4500 個輸出 token。
送出前先算 `條數 × 每條 max_tokens`。
超過總上限或估計金額上限，就整次拒絕，一條也不開。不要只開一半。
已送出的請求不能退錢。實際花費超過估計就照實記，不補開新請求。

每條結果都保留 LLM 回的用量。
`join` 回總用量和實際花費。
工具帳照現有記法算在 `fork` 名下，多條的 token 和錢相加，等待格數算到全部到齊。
`kid` 模式各小孩本來的帳照記，父這邊只記分支工具的總數，避免同一筆錢加兩次。

## 給模型的預設 prompt

> 只有同一題真的有兩到三條不同走法，而且先各自想完再比較會更清楚時，才用 `fork`。
> 最多寫三個方向。每個方向只負責一個角度，不能只是換句話說。
> 先用「做法」「最可能失敗的地方」「完全不同的假設」切開方向。
> 一輪能想完就用 `llm`。需要工具或很多輪才用 `kid`。
> 開完先做別的事。需要答案時用 `join`，不要重複開同一題。

## 跟現有東西怎麼接

- 新增 `packs/branch.py`，放 `fork`、`join`、`adopt` 和上面的預設 prompt。
- `aos-agent` 的 `wait` 從只看一個 `request`，改成順手掃 `state.json` 裡的 `branches`。
- `aos-agent` 收分支結果時只寫 `branches/`。只有 `join` 的工具結果進主線記憶。
- `aos-agent` 執行 `adopt` 後，下一格直接用採用後的記憶。
- `.gitignore` 加 `branches/`。它和 `thoughts/` 一樣，都是執行時的私有資料。

## 現在故意不做

- 分支裡再分支。
- 超過三條。
- 自動新增、合併或刪掉方向。
- 自動評審、自動投票、自動採用贏家。
- 取消已送出的請求，或清理很舊的 `branches/`。
- 某一條失敗後重試、換引擎，或拿其他條補位。
- 主程式同時有兩個進程改同一個 `state.json`。
- `adopt` 後想回到原主線的復原工具。
- 精準保證金額不超支。送出前只能估，回來後照實記。

## 要使用者拍板

- T-51：第一版預設用 `llm`，只有需要工具或多輪時才用 `kid`？建議是。
- T-52：一次最多三條、每條 1500 輸出 token、總共最多 4500？建議先這樣。
- T-53：`join` 每條最多帶回 800 個中文字，不帶思考過程？建議是。
- T-54：要做 `adopt`，讓選中的整段記憶取代主線？建議做。
- T-55：第一版禁止巢狀分支，也不加評審請求？建議都先不要。
