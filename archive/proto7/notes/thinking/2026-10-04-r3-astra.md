# 思想擴充第三輪：受限 node 與必然的轉手

**轉接任務包的目標，是讓受限 node 持續保持簡單，同時取得足以正確完成工作的輸入。** 困難在於定義哪些差異必須保留，以及誰能證明轉接後仍保留了它們。

接續[使用者對第二輪的駁斥](2026-10-04-r2-synthesis.md)，本輪把「不能吃原始資訊」當成正常設計條件。以下皆為提案；沒有修改檔案、實作或執行探針。

## 1. 受限 node：先定義它必須分辨什麼

單一功能的 node 可以把輸入限制得很窄：只接一種訊息、只理解幾個詞、只做一次判斷。這會縮小實作與測試範圍，也讓替換、複製、小模型化或純程式化更容易。轉接成本則移到介面，仍須計入整體成本。

| 限制 | 合理用途 | 轉接器需要處理的事 |
|---|---|---|
| 只認上級 | 固定責任與交付入口 | 由上級準備並交付輸入 |
| 只認某格式 | 固定欄位、型別、長度 | 選欄、編碼、精度處理 |
| 只認某協議 | 一問一答、每件一個檔案 | 請求對應、交付與回條 |
| 只認某詞彙 | 只懂「通過／不通過／待定」 | 將來源情況映射成有限狀態 |
| 只看某時間尺度 | 每回合一次、只看整分鐘 | 取樣、聚合、期限表示 |
| 容量受限 | 每次最多一件、固定視窗 | 範圍選取與超量處理 |

原則 3「先把單元弄好」，在這裡可以具體成為：**先定義這個 node 必須分辨哪些情況，再設計能保留那些差異的輸入。**

例如 node 只判斷是否達到 80°C，正確的 `{"hot":true}` 已足夠。原始數值雖然丟掉了，這項工作需要的資訊仍完整。

反過來，若兩個來源情況應讓 node 做出不同反應，轉接後卻變成同一輸入，下游就無法補救。這是目的介面是否足夠的必要檢查：

> **被轉接合併的情況，不能包含這個 node 必須區分的情況。**

這也包括時間上的差異：「現在正常」與「期間曾經異常、現在恢復」，對只看最新值的 node 完全相同；需要處理後者，就要有事件或窗口輸入。

若 node 只收布林、持續使用舊值，又沒有未知、撤回或停止使用舊值的方式，轉接器無法承諾來源失效後仍正確。問題在這次用途與介面的組合，不能靠附出處解決。

## 2. 轉手是翻譯：無損、確定性、可驗證要分開

「純程式處理」不代表無損；「有出處」也不代表語意已驗證。至少要分別聲明保留了什麼、能否重算、驗證涵蓋什麼。

| 轉換 | 可提供的保證 | 可能失去的東西 |
|---|---|---|
| 格式轉換 | 在型別與編碼範圍內可逆 | 浮點精度、空值差異、重複鍵 |
| 單位換算 | 規則明確，可重算或給誤差界 | 捨入後的小差異 |
| 選取、投影 | 精確保留指定範圍 | 範圍外內容；選錯範圍仍會出事 |
| 詞彙對應 | 固定字典可逐項檢查 | 多義詞、目的詞彙不存在的差異 |
| 聚合 | 對指定窗口與資料集精確 | 個別值、順序、相關性 |
| 取樣 | 精確描述取得的樣本 | 未取得的事件與短暫變化 |
| LLM 摘要、語意翻譯 | 可要求格式、追蹤依據、做部分驗證 | 細節、否定、例外、範圍及推論界線 |

摘要一旦省略原有差異便有資訊損失，但不表示每次都會產生錯誤。抽取原文片段可以忠實保留片段，同時遺漏片段外的重要條件。

**失真應相對於接收契約衡量。** 不要求保留的欄位可以省略；必須保留的例外被刪掉，就是違約。不能讓摘要者自己決定哪些內容算進評分分母。

建議保留以下指標，不急著合成一個總分：

| 指標 | 定義 |
|---|---|
| 必要內容缺陷率 | 錯誤或缺失的必要欄位／契約要求欄位；同欄只計一次 |
| 無依據主張率 | 來源不支持的主張／輸出主張；空輸出記不適用 |
| 行為失真率 | 已交付輸入導致錯誤反應的案例／有標準答案的已交付案例 |
| 驗證漏擋率 | 被放行的錯誤候選／全部錯誤候選 |
| 有效交付率 | 期限內正確交付／全部合法請求 |
| 數值與時間誤差 | 數值偏差、期限延長量、過期放行率 |
| 延遲 | 來源版本可用至 node 消費的 p50／p95／p99；另列未完成與逾期件 |

有效交付率必須與錯誤率一起看，否則全部拒絕也能得到零錯誤。

## 3. 任務包：外接的感官，有明確責任

受限 node 維持原來的工作。轉接鏈由合法的上級或介面持有者組裝：

```text
固定依據 → 選取／轉換／聚合 → 候選輸入 → 驗證 → 上級既有入口 → node
                                      ↘ 證據附檔，供驗證者與追查者讀
```

共同契約是：輸入與規則要能辨識版本；成功只涵蓋明列保證；缺資料不能默認成零、否或空集合。

| 任務／分類 | 職責 | 前置條件 | 保證 | 明確不管 |
|---|---|---|---|---|
| 取據／通用 | 取得並固定本次依據 | 有合法讀取途徑與版本識別 | 後續處理同一份內容，缺漏明示 | 來源是否說真話、永久保存 |
| 選取投影／通用 | 選欄位、範圍與條件 | 選取規則、必留差異已定義 | 按規則處理，不偷補缺值 | 業務規則是否選對 |
| 轉碼換算／通用 | 格式、單位、固定詞彙轉換 | 型別、字典、精度、捨入規則 | 可重算；不能表達的值不猜 | 建立領域字典、開放語意理解 |
| 窗口聚合／通用 | 多筆資料轉成指定統計量 | 窗口、分母、完整性條件明確 | 說清涵蓋範圍與缺口 | 還原未取得的樣本 |
| 時間轉接／通用 | 時間事實轉成接收端表示 | 時鐘域、起算點、期限邊界 | 不重設期限，不冒充跨域等價 | 保證工作準時完成 |
| 摘要／LLM | 產生指定內容與詞彙的候選 | 依據、內容要求、預算 | 留下候選及依據關聯 | 保證語意正確、核准交付 |
| 驗證／通用 | 核對目的契約與可檢查條件 | 依據、候選、驗證規則 | 明示已驗、失敗與未知部分 | 把格式通過當完整語意證明 |
| 附註／通用 | 記錄依據、轉換與驗證結果 | 實際使用的資料可辨識 | 紀錄綁定實際候選內容 | 把引用變成真實性背書 |
| 交付／通用 | 從合法入口送出核准內容 | 交付資格、協議與有效結果 | 交付內容與驗證對象一致 | node 的後續決策、業務副作用去重 |

使用 LLM 的語意評審另屬 LLM 任務。基本鏈不需要 agent 專用任務；要接 agent 的記憶、角色訊息或專用信箱協議時，再加 agent 接面任務。一般檔案信箱本身仍是通用能力。

這是 **kernel 的通用轉接包，加上可選的 agent／LLM 包**，不必升成 kernel 核心必備功能。

任務能獨立測試，不代表每項都要開程序。第一版用一個普通任務依序執行即可；既有 `tasks.json` 的排列不保證前一任務已完成，不能拿它代替轉接鏈的依賴順序。

## 4. 多跳：切斷重述誤差，保留真正的新事實

**每跳回原始重新投影，是轉接器的能力，不要求受限 node 直讀。** 原始依據可以經上級傳遞、由授權副本提供，或請有權的上級重新投影。

這個做法需要四條界線：

1. **固定依據版本。** 每跳讀 `latest` 會把不同時刻的事實混在一起，並非同一份資訊的重投影。
2. **保留中間層新產生的有效事實。** 上級新增限制、正式核准、當地觀察，都有自己的來源地位。回原始不能把它們洗掉；應重讀原始依據及這些必要的新事實。
3. **來源取不到就降低保證。** 可以依設定改用上一跳輸出，但要聲明依據改變；不能沿用「已回原始驗證」。
4. **上一跳足夠時可以直接接。** 若它完整保留下一跳需要的差異，就不必反覆讀原文。

第四點很重要。例如平均值不能任意再平均，但保留 `sum` 與 `count`，就能精確組合各組平均。轉接包值得尋找的是這類**足夠小、又能繼續正確加工的表示**。

對明確的數值換算，可傳遞誤差界。若下一步是倍率 `a` 的換算，再引入至多 `q` 的捨入誤差，則誤差界為 `|a|×前一步誤差＋q`。接著遇到門檻判斷，誤差區間若跨過門檻，就不能硬交一個確定答案。

驗證證據放在 node 外，綁定**依據版本、轉換規則版本、實際輸出內容**。雜湊只確認內容身分，引文存在只確認字串存在；兩者都不證明結論正確。

有損處理由組裝者依 node 用途允許：定出必留差異、容許精度與未知時行為。規則選錯由規則作者負責；執行錯由轉換器負責；漏掉承諾會檢查的錯由驗證器負責；送錯內容由交付者負責。正常來源故障走缺據／未知分支，候選違約走拒絕分支，不把模型的預期失誤推成 node 誤用。

## 5. 時間：同一個期限，可以有不同表示

| node 真正需要的資訊 | 合適的輸入 | 不能偷偷等同的東西 |
|---|---|---|
| 工作進度 | 階段、已完成回合 | 已經過幾秒 |
| 期限是否到達 | 未到／已到／未知 | 收到後重新倒數 |
| 剩餘來源回合 | 來源時間線還差 N 個邊界 | 自己還能執行 N 次 |
| 剩餘嘗試次數 | 可再嘗試 N 次 | 父回合乘節拍比例 |
| 相對某事件的期限 | 事件識別與固定截止點的投影 | 相對本次轉送時間起算 |

例如來源已完成第 17 回合，契約定義第 20 回合完成時到期，轉接器可以交付「觀察時還差三個來源完成邊界」。它不能承諾孩子還能跑三次；後者涉及工作機會或配額分配。

父子 daemon 的關係不提供回合匯率。父線 pause、子線繼續，以及 wake 提前推進，都會打破依設定 interval 推算的比例。需要跨線時，優先轉接「期限到了沒」這種判定；只有映射與誤差條件成立時才換算數量。

**相對期限只在原始起算點解讀一次。** 「事件後五秒」應固定成那個事件的截止點；每跳從同一截止點計算剩餘量，不能變成「收到後再給五秒」。

時間附註至少交代時鐘域、起算事件、觀測邊界、截止點、取整方式與觀測時刻。固定的是期限依據；判斷「現在是否有效」還需要新的時間觀測，兩者不能混成永遠有效的一份快照。

若 node 只收整數秒，取整方向依用途決定：「不可提早喚醒」與「不可延長有效期」的方向不同；傳輸和排隊時間也要算進去。只有過去觀測、沒有延遲界線時，不能承諾消費當下仍剩同樣時間。

RTOS 可借的是這種明確性。Zephyr 提供 floor／ceil／near 換算，並以固定 timepoint 計算後續剩餘 timeout；文件也明確提醒不要反覆重新建立起算點。[Zephyr Kernel Timing](https://docs.zephyrproject.org/latest/kernel/services/timing/clocks.html)

對 aos 的推論是：先把時間語意、誤差與遲到行為定清楚。準確翻譯期限不等於準時交付；只有讀取、排隊、轉換、驗證與消費各段都有可成立的上界，才能合成端到端上界。p99 與觀測最大值仍只是量測結果。

## 6. daemon／tick：本輪需要的新增是零

[現行 spec](../../../proto7-2/spec.md) 已有普通任務、掛載與檔案交接。轉接包可以用一個 `keep` 任務處理鏈，由它管理自己的資料、版本與交付。

時間來源可讀既有回合檔；轉接延遲可在任務端量測。這不要求核心理解事實、摘要、目的詞彙或驗證政策，也不要求同步 hook。

兩個部署界線要保留：

- 核心「只留上一次」不等於保存完整證據；要重投影的版本由任務包或來源保存。
- 跨子 daemon 空間時，由合法的橋接任務交付到子空間收件區；不能假設孩子能用現有 mounts 跨出自己的空間根讀父檔案。

[介面調查](../../../proto7-2/notes/layer-interfaces.md)與[核心精簡方案](../../../proto7-2/notes/core-slimming.md)仍有版本與提案界線。本輪不依賴其中尚在提案的 `x` 透傳或任務包安裝器。

日後若真的要量 daemon 內部精確邊界，再評估通用的觀測模組；任務端量不到的量，先標未知。本輪沒有理由因此預先加核心欄位。

## 7. 具體草稿與兩個離線探針

### 目錄與一條轉接鏈

以下目錄、命令與設定都是提案，未建立；`pack.json` 也不表示已有安裝器。

```text
packs/
  fact-adapt/                   # kernel／通用
    README.md
    spec.md                     # 任務契約與失敗分類
    pack.json
    contracts/hot-input.json
    chains/hot.json
    bin/relay                   # 最初一支程式，依序執行各步
    probes/                     # 以下兩個探針
  llm-digest/                   # kernel／LLM，可選
    README.md
    spec.md
    bin/summarize
relay-state/                    # 部署後由上級持有，放在槽外
  evidence/
  receipts/
```

範例：上級 `parent` 替 `parent/children/hot` 準備輸入。子 node 每件工作只吃一份 `{"hot":布林}`；沒收到新件就不工作，不會沿用前件的值。

來源 `records/42.json` 是固定版本：

```json
{"id":"sensor-a:42","temperature_mC":79960,"quality":"valid"}
```

上級 `.aos/tasks.json` 的登記沿用現有欄位；`relay` 是擬議程式：

```json
{
  "tasks": [{
    "name": "hot_adapter",
    "mode": "keep",
    "argv": ["packs/fact-adapt/bin/relay",
             "--config", "packs/fact-adapt/chains/hot.json"],
    "mounts": {
      "source": "sources/temp/out",
      "child_input": "parent/children/hot/inbox"
    }
  }]
}
```

`chains/hot.json` 是任務包自用設定，不交給 tick 解讀。`binding` 由 relay 對應到自己的 `mnt/<名稱>`：

```json
{
  "schema": "fact-adapt.chain/0",
  "version": "hot-rule/1",
  "target_contract": "hot-input/1",
  "basis": {
    "binding": "source",
    "object": "records/42.json",
    "id": "sensor-a:42"
  },
  "steps": [
    {"task": "select", "fields": ["temperature_mC", "quality"]},
    {"task": "validate", "require": {"quality": "valid"},
     "types": {"temperature_mC": "integer"}},
    {"task": "project", "op": "gte", "field": "temperature_mC",
     "value": 80000, "output": "hot"},
    {"task": "encode", "schema": "hot-input/1"},
    {"task": "verify",
     "checks": ["schema", "hot-equals-basis-threshold"]}
  ],
  "delivery": {
    "binding": "child_input",
    "object": "m42.json",
    "receipt": "relay-state/receipts/m42.json"
  },
  "on_unknown": "withhold",
  "on_invalid": "reject"
}
```

交付結果是 `{"hot":false}`。若先把 79.96°C 四捨五入成 80°C 再比較，就會產生錯誤；因此門檻投影直接使用原始精度。

relay 先固定依據與候選，驗證同一份候選，再保存綁定輸出內容的驗證紀錄，最後發布輸入。node 不讀附註。紀錄可供重試核對，但多檔寫入不因此成為交易，也不自動保證副作用恰好一次。

### 探針一：固定來源，量多跳重述是否累積

**設計：**1,000 件結構化真值，含數字、單位、否定、例外與門檻附近值；20 個 seed，鏈長 1／2／4／8。末端永遠只吃同一個小型 schema，不給它原始資訊。

比較 A「投影上一跳輸出」與 B「每跳回固定原版」。兩組保持相同鏈長、目的契約、排程和假 LLM 服務成本；亂數按案例、跳次與錯誤類別固定，原文讀取及重算成本另計。

假 LLM 注入遺漏、否定翻轉、數值偏移；另測同一案例每跳都犯相同錯的共同偏誤，以及零注入、確定性捨入對照。加入「中層新增有效限制」案例，檢查 B 是否錯把它洗掉。

量第 2 節各項失真率、有效交付率、讀取量及分段延遲。預期 B 能減少上一跳錯誤的繼承，但共同偏誤不一定改善。驗收要求確定性對照符合契約、中層限制不消失、正常合法件能完成；不預設 B 必勝。

### 探針二：時間轉手，量忠實卻過期的輸入

**設計：**離線事件模擬器建立父子不同節拍、pause、wake、排隊及假 LLM 耗時；末端只認「繼續／到期／未知」。沿用 A／B，另設「每跳讀 latest」及「收到後重新起算」反例組。

注入來源換版、原版不可取得、錯誤時間單位、捨入、拿錯證據，以及驗證後交付不同內容。時鐘軌跡與故障在各組相同，期限判斷使用的時間觀測另外記錄。

分開評分「是否忠於指定版本」與「消費時是否仍有效」。量期限延長量、過期放行率、提早拒絕率、未知率、有效交付率及延遲；模擬時間與測試程式實際耗時分列。

驗收要求：不把最新版冒充指定原版、不重設原期限、不讓回條套用不同輸出；在假時鐘與明定可驗條件內，過期錯放為零，正常合法件可完成。假 LLM 結果只驗機制，不推估真模型品質。

## 8. 何時該做，現在保留什麼

不必等 node 很多。以下任何一項出現，就值得針對那個單元做第一條鏈：

- 第一個 node 的既定輸入無法直接接受來源，而且轉換會持續重複。
- 同一轉換開始被兩個以上 node 重寫，需要共同測試與版本管理。
- 下游行為已依賴有損轉述，錯誤無法只靠原樣搬運解决。
- 第一個跨時間線期限需求，不能用接收者自己的回合直接表達。
- 出現「來源正確、node 也照規格工作，但結果錯了」的案例，需要追到中間轉換。

現在最便宜的準備，是未來寫介面時保留四項約定：**目的契約版本、固定依據的識別、可放在 node 外的證據關聯、時間的單位與起算點。**

再替第一個真實 node 留幾組「必須得到不同反應」的案例，就有了第一版驗收材料。這些不要求現在建立包管理器、通用鏈引擎或新增核心功能。

重投影、證據保存期、摘要嚴格度、未知時處理與快取都可以做成設定。快取應依據資料與規則版本；依賴「現在」的倒數，不能只用原資料版本當快取鍵。

## 9. 最值得使用者拍板的問題

目前沒有必須立刻決定的核心架構題。開工前最有價值的是兩個業務定義：

1. **第一個受限 node 究竟要完成什麼工作？哪兩種輸入情況即使非常相似，它也絕不能做出相同反應？** 這決定轉接必須保留什麼，比先選摘要格式更根本。
2. **在這個工作裡，錯一次、漏一次、晚一次，各會造成什麼後果？** 這決定有損處理的驗收門檻；系統無法從來源資料自行推導這些取捨。

## 我最不確定的三件事

1. **最小輸入契約會不會漏掉跨時間的差異。** 單次輸入看似足夠，node 有記憶、重試或窗口行為後可能不夠。最需要用真實 node 驗的是整段輸入歷程，而非只驗一份 JSON。
2. **能持續重投影的依據到底能縮到多小。** 原文可能太大、保存昂貴或只有上級可讀；縮成小型表示又可能過早刪掉未來需要的差異。第一個用途能否找到可組合的表示，會決定成本。
3. **外部語意驗證能否帶來獨立的糾錯能力。** 摘要者與驗證者若共享相同誤解，搬到 node 外只是移動錯誤位置。假後端能驗證交付與拒絕機制，仍不能證明真模型在必要差異上可靠。
