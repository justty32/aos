## 0. 正面回應駁斥：我錯在哪、哪裡還站得住

**錯的地方。** r2 說「一個 node 有收／持／轉三個口，收＝我掛了誰」，然後把拓撲全建立在「掛得到就直讀」上。這把**搆得到**（mount）和**吃得下**（parse、理解、裝得進自己的格式）混成一件事。受限 node 掛得到 `services/bank/out/ledger.json`，但它的輸入契約只有 `{"remaining": int}`，掛再多也沒用。所以「事實拉、直讀來源」只對**通用讀者**（能讀任意 JSON 的腳本、或 LLM）成立；對受限 node，收口有兩半——**reach** 與 **digest**——r2 只處理了前一半。使用者的駁斥成立。【高】

**而且 repo 裡受限 node 早就是常態，不是遠期。** 列幾個：`counter.py` 只吃 `tock.json`；namespace 的 `reviewer.py` 只認 `llm-submit.v1`，介面不合就寫可讀拒絕、一件不送；hsched 的 kernel 只吃 §10 格式的政策，還得過 8 道驗證；agent 只吃 letters＋roster＋goal 組成的 prompt；**daemon 自己是最受限的 node**——只吃 `{"op","node","by"}`，連多一個不認識的 op 都回 `ok: false`。「天生不能吃原始資訊」就是這套系統從核心到探針一路的寫法。【高】

**還站得住的地方，但要改主詞。** 失真來自中繼與讀取時機、不是距離（r2 結論 1），這條不變。要改的是：「直讀來源」的主詞不是受限 node，而是**最後一個能直讀的人**——受限 node 前面那個轉接器。r2 的五個判斷、雜湊回驗、AoI，全部搬到轉接器身上做，受限 node 一個都不用懂。【高】

**我要補的一個反向觀察（推論）。** 使用者說「資訊傳給它必定被轉手」，對；但「一層傳一層會累積延遲和錯誤」這件事的元凶不是轉手的**次數**，而是轉手的**位置**——轉手發生在**組織鏈上**（上級轉述給下級、下級再轉述），而不是發生在**消費者自己的門口**（消費者的轉接器直接讀來源、重新投影）。把轉手從鏈上搬到門口，跳數就是 1，而且每一回合都能回來源重算。這是本輪的主軸。【中偏高】

還有一個：**讓 LLM 直接讀原始資訊，本身就是一次轉手，而且是最差的那種**——有損、不確定、不可驗證（blindread q4 rep2 引對原文推錯結論；R-15 憑記憶重打掉單位）。所以 r2 把「LLM 直讀」當黃金標準也錯了：黃金標準是**確定性轉接器直讀，LLM 只吃轉接器給的窄格式**。受限不是 LLM node 的缺陷，是它的失真控制。【中偏高】

## 1. 受限 node 的本質

### 1.1 為什麼是好設計

| 好處 | 為什麼受限才有 | repo 證據 |
|---|---|---|
| **可驗證** | 輸入面窄 → 能寫 schema、能造 fixture、能在門口驗；輸出面窄 → 下游能驗 | hsched 驗證器 8 項、越權生效 0；namespace 介面不合可讀拒絕 |
| **可替換** | 契約是格式，不是實作：純腳本、小模型、大模型、人，都能站在同一個格式後面 | hsched D 組：LLM 提政策、確定性執行；Atuned 用同格式的手調政策反而贏 |
| **可大量複製** | 複製能力不複製身分（r1）：同一支程式、不同掛載 | namespace 五代 reviewer 同一支程式 |
| **便宜** | 不吃原始資訊就不用養能讀任意東西的腦；多數可以是純程式 | counter.py 41 行 |
| **防干擾／防注入** | 吃不到的東西就騙不了它：攻擊面＝schema | R-2 視窗被 12 封信擠爆，是吃太多原始資訊的 node 才會發生的事 |
| **可重播、可測** | 窄輸入＋確定性 → 回合可重放 | hsched 離線協議驗證 32 項全綠靠預錄回答 |
| **錯誤歸屬清楚**（原則 9、10） | 契約窄，才分得出「輸入不合（B）」還是「自己的錯」 | core-slimming 的錯誤四分支正是靠核心的輸入窄 |

一句話：受限 node 是 Parnas 的資訊隱藏加上「窄腰」（IP 沙漏那種）——上面多少來源都行、下面多少實作都行，中間只有一個小格式。**窄腰就是原則 3 的「單元」**：先把格式定好，單元就測得了；拓撲是轉接器把窄腰接起來長出來的。【高】

### 1.2 受限的種類（一個 node 可以同時有好幾種）

| 種 | 只認什麼 | 例子 | 轉接器要做的 |
|---|---|---|---|
| 出處 | 只信某個寫者／某個掛載 | 「只吃上級的」 | 門禁（gate）：驗 `src.node`、路徑在允許表內 |
| 格式 | 某 schema／某版本 | daemon ctl、`llm-submit.v1` | 選取、投影、格式轉換 |
| 協議 | 請求—回條的舞步、冪等鍵 | namespace 的 requests／receipts、ctl_id | 協議轉換（把事實包成請求、回條拆成事實） |
| 詞彙 | 固定的 enum、名冊 | `op: kill|restart`、roster 名字 | 詞彙對應表 |
| 單位 | token 不是美元、回合不是毫秒 | grant 的五種維度 | 單位換算（匯率本身是事實） |
| 時間尺度 | 一回合一值、只看最新、每 20 回合一次 | counter、hsched 每 20 回合問一次政策 | 重取樣（latest／hold／window 聚合） |
| 容量 | 每回合最多 N 封、最多 K bytes | agent 的 memory 視窗 | 選取＋排序＋截斷，並宣告丟了什麼 |
| 身分 | 只認自己 run 的通知 | `wait_tock` 的 run 過濾 | 已由核心做（見 5.1） |
| 位置 | 只碰 `mnt/` 下固定名字 | S-10、reviewer 的 `mnt/model` | 掛載表（核心已有） |

### 1.3 契約（原則 10）長什麼樣

一個受限 node 的功能定義只要四件事：**`need`（我非有不可的欄位）、schema（格式與版本）、`state` 處理（見 4.1，`unknown` 時我做什麼）、時鐘來源（我的「現在」從哪個檔讀）**。這四件就是它的 fixture，也是轉接器驗證器的輸入。藍圖那邊給每個組件寫的「前置條件／明確不管」，對受限 node 來說就是這張表。【高】

## 2. 轉手是翻譯：操作、有損與否、怎麼驗

### 2.1 操作表

| 操作 | 確定性 | 對 `need` 無損？ | 怎麼驗 | 歸類 |
|---|---|---|---|---|
| 複製（copier） | 是 | 是 | 雜湊 | 通用 |
| 選取（select 欄位／記錄） | 是 | 選到的無損；整體有損但**可列舉**（`omitted`） | 從來源重算 | 通用 |
| 投影／改名／改形狀（reshape） | 是 | 是（雙射時） | 反投影或重算 | 通用 |
| 格式轉換（JSON↔CSV、編碼） | 是 | 來回一致才無損 | round-trip 雜湊 | 通用 |
| 單位換算（convert） | 是 | **匯率本身是事實**（價目表、量到的 interval），有版本有 TTL；取整有界誤差 | 重算＋誤差界 | 通用 |
| 時間尺度換算（resample） | 是 | **有損但精確可描述**：latest＝取樣（取樣定理）、hold＝可能過時、window 聚合＝丟細節 | 重算；aliasing 用「來源變了幾次 vs 我看到幾次」量 | 通用 |
| 聚合（sum／max／count） | 是 | 有損、精確 | 重算（G-Counter 就是這個） | 通用 |
| 詞彙對應（map） | 是（有表） | 多對一時有損 | 表有版本；重算 | 通用 |
| 去重、排序 | 是 | 是 | 重算 | 通用 |
| 門禁（gate） | 是 | 不改內容 | 允許表 | 通用 |
| 預設值補齊（default） | 是 | **加了來源沒有的東西**＝一種編造，必須標 `defaulted` | 列舉 | 通用 |
| 取樣（每 k 筆、隨機） | 是 | 有損、可宣告 | 分母 | 通用 |
| 摘要、翻譯、推論（LLM） | **否** | **有損且模糊** | 只能部分驗：quote 子字串、數字專名出現、claim→evidence | LLM 專用 |

兩個分界線比「有損／無損」更有用：**(a) 確定性可重算 vs 不可重算**；**(b) 損失可列舉（omitted、分母、誤差界）vs 不可列舉**。前 12 列都是「可重算且可列舉」——我叫它**精確有損**；只有最後一列是**模糊有損**。失真控制整套只針對模糊有損；精確有損靠「每回合從來源重算」就自動歸零。【高】

### 2.2 失真指標（轉接器契約裡的「失真預算」）

| 指標 | 量法 | 對應 r2 七種失真 |
|---|---|---|
| `need` 遺漏率 | 輸出缺 `need` 欄位的回合比例 | 遺漏 |
| 改值率 | 結構化：逐欄比對重算結果；文字：quote 不是子字串 | 改寫 |
| 無據率 | claim 指不到 `about` 裡的證據 | 編造 |
| AoI（來源回合） | 來源現在的 round − `about[i].src.round` | 過時 |
| 混疊率 | 來源在兩次取樣間變了 ≥2 次的比例 | 遺漏（時間版） |
| 量化誤差 | 取整、匯率誤差界 | 改寫（數值版） |
| `unknown` 率 | 驗證不過而輸出 unknown 的回合比例（**這是代價，不是失真**） | — |
| 決策錯誤率 | 受限 node 依感官做的決定與「依真值」不同的比例 | 總指標 |

像 RTOS 的 deadline 一樣，**每條轉接鏈宣告自己的預算**（例：`max_age_rounds: 2`、`fuzzy_hops: 0`、`need_drop: 0`），驗證器守預算，守不住就輸出 `unknown`。【中偏高】

## 3. 轉接任務包（`adapt`）

### 3.1 定位

core-slimming §10.3 已有 `relay`（通用：copier、跨空間信箱、事件轉發）與 `llm-digest`（LLM：annotator、verify）。本輪的提議是**把 `relay` 擴成 `adapt`**：通用的那些步驟全進去，LLM 步驟獨立成子包 `adapt-llm`，依賴 `adapt`。類別＝通用（把 LLM 換成 cron 一樣要選取、換單位、重取樣）。

### 3.2 包裡的任務（每個都是純函式一個步驟，鏈由一個程序跑）

| 步驟 | 職責 | 前置條件 | 保證 | 明確不管 | 類 |
|---|---|---|---|---|---|
| `gate` | 只放行允許的來源 | 來源檔帶 `src`，或路徑可對允許表 | 不在表內的不進鏈 | 偽造 `src`（合作式） | 通用 |
| `select` | 取欄位／記錄 | 路徑語法合法 | 選到的值 byte 相同；列 `omitted` | 路徑指不到→unknown，不猜 | 通用 |
| `reshape` | 改名、改形狀 | 雙射表 | 可反投影 | 語意 | 通用 |
| `convert` | 單位換算 | 匯率檔有 `src`、在 TTL 內 | 誤差 ≤ 宣告界；輸出附匯率版本 | 匯率對不對 | 通用 |
| `resample` | 時間尺度換算 | 宣告 latest／hold／window＋聚合函式 | 輸出帶 `for_rounds`、混疊計數 | 補回漏掉的樣本 | 通用 |
| `aggregate` | sum／max／count／mean | 輸入可重算 | 精確 | — | 通用 |
| `map` | 詞彙對應 | 表有版本 | 查不到→unknown | 同義詞猜測 | 通用 |
| `validate` | schema＋`need`＋失真預算＋`fuzzy_hops` | 鏈宣告有預算 | 不過就 unknown，不放過期或缺欄的 body | 語意對錯 | 通用 |
| `stamp` | 附 `src`／`about`／`via`／`aoi` | 每步回報自己讀了什麼 | 每份輸出可回溯 | 全鏈歷史（每手自己留，r2） | 通用 |
| `summarize`／`translate`／`infer` | LLM 產生另一份 | 輸入已是窄格式；有端點 grant | 輸出帶 claims＋quote；標 `fuzzy: 1` | 正確性（交給 validate 的 LLM 外掛） | LLM |

所有通用步驟都滿足**冪等、可重算、輸出附列舉的損失**；這是能「每跳回原始」的前提。

### 3.3 鏈怎麼組、怎麼掛到受限 node 前面

- **一條鏈＝一個「感官」**：讀若干來源（經掛載），產一份暫存器 `in/<sense>.json`。受限 node **只讀 `in/`**，與 r2 的 `out/`（事實）、`inbox/`（意圖）成一組：**in＝感官、out＝事實、inbox＝意圖**。
- **鏈的規則**：(1) 預設每一步的輸入是**來源**，不是上一步；只有宣告 `pipe` 的步驟才吃上一步；(2) **模糊有損步驟最多一個、必須在鏈尾、後面只接 validate 與 stamp**；(3) 整條鏈每回合從來源重算，LLM 步驟以 `about` 雜湊快取（來源沒變就不再呼叫）。(2)＋(3) 讓誤差沒有地方累積。【中偏高】
- **三種擺法，同一份鏈宣告**：
  | 擺法 | 誰跑 | 什麼時候用 |
  |---|---|---|
  | 消費端（預設） | 受限 node 自己的 node 裡一個 keep 任務 `adapt`，或**函式庫模式**（受限 node 程式內呼叫 `adapt.read("budget")`，同一程序） | 大多數：跳數 1、每回合回原始 |
  | 生產端 | 來源 node 自己跑鏈，把常用投影寫進自己的 `out/digest/` | 扇入大（N 讀者 × M 來源）、或存取控制只讓它讀原文 |
  | 共用中繼 | 一個中繼 node | 要一致切面的 node 群（r2 §5.3） |
  生產端與中繼的輸出對消費端來說只是**另一個來源**，消費端的鏈照樣跑 validate——`via` 裡已經有一個 `fuzzy` 的話，消費端就不能再加模糊步驟（規則 2 跨 node 也成立），只能用精確步驟或申請加掛原文。
- **函式庫模式 vs 任務模式**：任務模式多一個常駐程序，而且**和受限 node 之間有回合內的先後問題**（兩者都等同一個 tock.json，誰先醒沒保證）。解法不是改核心，而是**讓受限 node 把時間也當感官**：它等的是 `in/clock.json` 的 `for_round`，不是 `tock.json`；轉接器成了它唯一的輸入，含時間——這正好就是使用者說的「時間也要被轉手」。函式庫模式沒有這個問題。【中】
- **效應器是同一個包反著跑**：受限 node 的輸出也是窄格式，要變成 ctl 檔、信、grant 請求，一樣是 reshape＋map＋validate＋stamp（hsched 的 `answers/<rev>.txt` → 驗證器 → kernel，agent 的 send／write／save 工具，都是效應器）。**感官給行動的依據，閘門給行動的許可**：兩邊都是確定性程式、都回去讀原始資料，受限 node 夾在中間只做它那一件事。【中偏高】

## 4. 失真控制

### 4.1 三態進格式

受限 node 唯一要讓步的一件事：**每個感官的值都帶 `state: ok | unknown | absent`**，而且 node 的契約要寫明 unknown 時做什麼（預設：保留現狀，跟核心的三態判定同一精神）。沒有這一條，驗證器在失真超預算時只有兩個爛選擇：餵過期的 body（node 不知情）、或不寫（node 看到的還是上一份，仍不知情）。有了這一條，「不知道」可以一路從來源傳到最窄的 node，而 node 不必讀任何依據。【高】

### 4.2 誰負責

| 環節 | 對什麼負責 | 不對什麼負責 |
|---|---|---|
| 來源 node | `out/` 的內容正確、帶 `src` | 誰怎麼讀它 |
| 轉接鏈的擁有者（通常＝受限 node 的部署者） | 鏈的失真預算、`need` 不漏、unknown 率 | 來源本身錯 |
| 生產端 digest／中繼 | 自己 `via` 裡宣告的預算 | 下游再加工 |
| 受限 node | 在 ok 的感官上做對自己那件事；unknown 時照契約 | 感官對不對（它看不到） |
| 閘門（副作用入口） | 回原始資料驗許可 | 導航用的感官 |

**失真責任跟著鏈宣告走**，不跟著資料走；受限 node 永遠不是失真的責任方——這是它「天生不能吃原始資訊」換來的權利。【高】

### 4.3 什麼時候允許有損

- 精確有損：隨時允許，條件是 `omitted`／分母／誤差界列得出來，且 `need` 一欄不丟。
- 模糊有損：只允許在**導航、提案、粗估**用途；凡是支用、權限、否定條件、不可逆提交（astra r2 的回查條件），鏈裡不得有 fuzzy 步驟，或閘門必須回原文。驗證器可以機械地從鏈的 `purpose` 欄擋。
- 多跳：靠 `via` 裡的 `fuzzy` 計數與「依原始來源去重信心」（astra）；雜湊讓任何一跳只要掛得到來源就能重驗。

## 5. 時間作為原始資訊

### 5.1 核心早就內建了一個轉接器：tock.json

tock 每回合把 `round.json` 投影成每個槽一份的 `tock.json {run, round, at, early}`——消費端、每回合重投影、帶身分過濾（`wait_tock` 只認自己的 run）、覆寫暫存器。這就是 §3 整個包的原型，而且它轉手的正是時間。**包該長得像 tock.json，而不是像 log 管線。**【高】

### 5.2 受限 node 要的時間長什麼樣（都是原始時間事實的投影）

| 要的形狀 | 原始資訊 | 轉接操作 | 有損？ |
|---|---|---|---|
| 現在第幾回合（自己的線） | `round.json`／`tock.json` | 複製 | 無 |
| 期限到了沒（別人的鐘） | 來源的 `round.json` + grant 的 `until_round` | 每回合重讀來源鐘，輸出 `{remaining_source_rounds, expired}` | 無（不換算） |
| 還剩幾次（自己的回合） | 上一列 + 兩線的節拍比 | **換算**：需要量到的 interval（C4 `timing`），附誤差界 | 精確有損，誤差＝抖動 |
| 自從 X 以來幾回合 | 自己的事件紀錄 + round | 相減 | 無 |
| 經過多少 ms | `timing`（monotonic） | 加總 | 無（有了 C4 才有） |
| 這條線一回合約多久、準不準 | clock-quality（讀 `timing`） | 聚合 | 精確有損 |
| 來源停了沒 | status 的 `paused_by`／`phase` | 投影 | 無 |
| 牆鐘日期（對外行程） | `at` | 複製 | 無（只給人、給外部） |

**規則**：期限類一律**不換算**，每回合回來源的鐘讀「剩多少、到了沒」（這就是「每跳回原始」用在時間上）；只有**規劃類**（「我來得及嗎」）才換算成自己的回合，而且要附誤差界、標 `estimate`。被 pause 的來源：remaining 不縮，但要輸出 `source_paused: true`，讓 node 契約決定當 unknown 還是照舊。【中偏高】

### 5.3 跟 RTOS 的接法

- 受限 node 的時間確定性＝它感官的 AoI 上界＝轉接器的週期＋驗證延遲。取樣定理（r2 §3.1）在這裡變成**轉接器的契約**：`latest` 要無損，轉接器週期必須短於來源變化週期；做不到就標混疊。
- 「遲到之後怎麼做先定好」（astra）在這裡落地成 `max_age_rounds` 超過→`unknown`→node 保留現狀，整條鏈都是確定性的。
- wake 讓回合數膨脹（r2 §7.2）：只數回合的受限 node 會被騙，只有 `timing` 的 ms 能救；所以 **C4 多了一個理由**——時間轉接需要它。【高】

## 6. 對 daemon／tick 的影響：零新增

| 需要 | 核心要不要動 | 理由 |
|---|---|---|
| `in/` 目錄、`aos.sense.v1` 信封、鏈宣告 | 不動；kernel 慣例 | 普通目錄、普通檔 |
| 轉接任務 | 不動；keep 任務或函式庫（core-slimming 擴充點 A、C） | tock.json 已示範這型 |
| 鏈宣告放哪 | 不動；`<node>/adapt/<sense>.json`，或 tasks.json 項目的 `x.adapt`（core-slimming §5.2 的透傳欄） | 核心不讀 |
| 來源可及 | 不動；`mounts`／`mount_allow`／執行中加掛 | S-23 |
| 時間的 ms | **r2 的 C4 `timing`**（已提，通用） | 只有 daemon 有 monotonic 時刻 |
| 回合不被 wake 調快 | r2 的 C5 `min_interval_ms`（已提） | 同 r2 |
| 出處地基 | r2 的 C6 身分欄位（已提） | 同 r2 |

本輪**沒有一條新的核心要求**；r2 的三條裡 C4 的理由變強了。刻意不做：核心不排任務的回合內先後、tock.json 不多寫欄位（時間轉接的其他形狀全由包做）、核心不認識 `in/`。「把 LLM 換成 shell 腳本還成不成立」：整個包成立，只有 `adapt-llm` 子包不成立，所以它才分出去。【高】

### 7.2 一條鏈：受限 node `watch` 只吃 `{"remaining": int, "deadline_rounds": int}`

`team-a/watch/adapt/budget.json`：

```json
{"schema": "aos.adapt.v1", "sense": "budget", "purpose": "navigate",
 "from": {"ledger": "mnt/bank/out/ledger/latest.json",
          "grant":  "mnt/bank/out/grants/g-17.json",
          "clock":  "mnt/bank/.aos/round.json"},
 "need": ["remaining", "deadline_rounds"],
 "steps": [
   {"op": "gate",     "allow": {"ledger": {"src.node": "services/bank"}, "grant": {"src.node": "services/bank"}}},
   {"op": "select",   "as": {"spent": "ledger.body.accounts.team-a.spent",
                             "cap": "grant.body.amount", "until": "grant.body.window.until_round",
                             "now": "clock.round"}},
   {"op": "convert",  "out": {"remaining": ["sub", "cap", "spent"],
                              "deadline_rounds": ["sub", "until", "now"]}},
   {"op": "validate", "budget": {"max_age_rounds": {"ledger": 2, "grant": 50}, "fuzzy_hops": 0, "need_drop": 0}},
   {"op": "stamp"}],
 "to": "in/budget.json", "on_fail": "unknown"}
```

產出 `team-a/watch/in/budget.json`：

```json
{"schema": "aos.sense.v1", "sense": "budget", "state": "ok", "for_round": 213,
 "body": {"remaining": 1388, "deadline_rounds": 17},
 "about": [{"path": "services/bank/out/ledger/latest.json", "sha256": "7f3a…", "src": {"node": "services/bank", "tid": "ledger", "run": 99, "round": 442}},
           {"path": "services/bank/out/grants/g-17.json",   "sha256": "c21e…", "src": {"node": "services/bank", "tid": "alloc",  "run": 12, "round": 400}}],
 "via": [{"node": "team-a/watch", "tid": "adapt", "run": 5, "ops": ["gate", "select", "convert", "validate"], "fuzzy": 0}],
 "aoi": {"ledger": 1, "grant": 42}, "omitted": ["ledger.body.accounts.*", "grant.body.scope"]}
```

驗證不過時 body 不出現：`{"state": "unknown", "for_round": 214, "why": "ledger aoi 3 > 2", "about": [...]}`。`watch` 的全部程式就是：讀 `in/budget.json`，`state != ok` 就什麼都不做，否則照兩個數字決定要不要寫一封請求。它不知道 bank、不知道雜湊、不知道回合是誰的。

### 7.3 探針一 `adapt-loss`：投影上一跳 vs 每跳回原始

- **擺法**：1 個來源 node（每回合寫一份 10 欄觀測，其中 3 欄是某受限 node 的 `need`；每回合 1/5 機率關鍵欄位改變）；受限 node 每 3 回合依 `need` 做一次決定（正確與否對照真值）。三種鏈，各跑 h＝1、2、3、5 跳、200 回合、5 seed：
  - (A) **鏈式**：每跳一個中繼 node，吃上一跳的輸出，每跳都有一個假 LLM `summarize`（p_rewrite／p_drop／p_invent／p_stale 各 5%）；
  - (B) **每跳回原始**：中繼存在但只是「另一個來源」；受限 node 的鏈直接讀來源，fuzzy ≤1 在鏈尾；
  - (C) **純精確**：(B) 拿掉 fuzzy 步驟。
- **量**：決策錯誤率、`need` 遺漏率、無據率、AoI、unknown 率、讀取 bytes、假 LLM 呼叫數。
- **假設**：(H1) A 的錯誤率隨 h 近似 1−(1−p)^h，B 與 h 無關、≈ 單跳 p，C ≈ 0；(H2) C 的 unknown 率＝混疊率，可用轉接器週期壓到 0；(H3) B 的 LLM 呼叫數 ≤ A 的 1/h（快取命中）；(H4) 驗證器把 A 的改寫／編造／過時三類各抓到 ≥95%、誤報 0，抓不到遺漏，`need` 遺漏另由 need 檢查抓到 100%。
- **成功標準**：H1 方向 5 seed 一致；B 錯誤率 ≤ C＋2 個百分點；合法案例全部完成（不能用 unknown 換零錯誤：unknown 率 ≤ 5%）；檔案數不隨回合長。

### 7.4 探針二 `adapt-time`：期限不換算 vs 換算

- **擺法**：父線 interval 1000 ms（grant 發行者，`until_round`＝父回合），子線 150 ms 上一個受限 node 只吃 `{deadline_rounds}`（**以自己的回合計**）。兩種時間鏈：(a) **換算**：用量到的兩線 interval 把父回合換成子回合（有 C4 用 `timing`，沒有就先用 ISO `at` 近似）；(b) **不換算**：每個子 tock 重讀父 `round.json`，輸出 `{remaining_parent_rounds, expired}`，規劃用的子回合估計另標 `estimate`。注入：子線被吵鬧者每 20 ms wake（回合膨脹）、父線 pause 3 秒、父 interval 中途改 500 ms、子轉接器故意放慢到 1200 ms（違反取樣定理）。
- **量**：過期後仍行動、未到期卻停手的次數；期限提前量的 ms 誤差；unknown 率；混疊計數。
- **假設**：(H1) (b) 的過期錯誤 0，(a) 在 wake 風暴與 interval 改變下出錯；(H2) (a) 的 ms 誤差 ≈ 兩線抖動和，有 `timing` 時可給出界、沒有時給不出；(H3) 轉接器放慢後 (b) 的混疊計數 > 0 且被標出，期限判定仍不錯（因為是讀「到了沒」而不是數變化）；(H4) 父 pause 期間 (b) 輸出 `source_paused`，node 照契約保留現狀。
- **成功標準**：H1、H3、H4 成立；H2 允許「界不穩」（那就是 C4 的量測問題，不是包的）。

## 8. 「時機到了」的訊號，與現在最便宜的準備

**該做了的訊號**（出現任一條就值得開工，前三條最可能先到）：
1. 第二個消費者要同一份來源的**不同形狀**——第一次出現兩份手寫的投影程式。
2. 第一個**非 Python、或小模型、或人**要站在某個格式後面（可替換性被真的用到）。
3. 生產環境出現 hsched 那種 `stale_envelope`：輸出端閘門擋下了輸入過時——代表輸入端沒有轉接器。
4. 第一個跨時間線的期限交接（父子 daemon、不同 interval）。
5. 某個 LLM node 讀原始資訊的 token 占成本 > 一半、或再度出現 R-2 式的視窗擠爆。
6. 某條 kernel 規則需要的來源它掛不到（存取或經濟理由）——第一個被迫的中繼。

**現在就能做、幾乎零成本的準備**：
- kernel 慣例文件加一段：`in/`＝感官、`out/`＝事實、`inbox/`＝意圖；`aos.sense.v1` 信封欄位（`state`、`for_round`、`body`、`about`、`via`、`aoi`、`omitted`）。
- **從現在起寫的每個受限 node 只讀 `in/`**，哪怕今天 `in/` 是一支 10 行腳本寫的——先養習慣，包來了只是換掉那支腳本。
- 每個 node 契約寫 `need` 清單與 unknown 行為（藍圖那份正在做的事，順手加兩欄）。
- 核心：C4 `timing`（已提）；core-slimming 的 `x` 透傳欄（已提）。
- 把 tock.json 在 spec 裡**點名為「核心唯一內建的轉接器」**，包的設計以它為範本——這句話不改任何行為，但定了方向。

## 9. 最值得拍板的三題

**Q1 三態要不要進每個受限 node 的格式？**
(a) **每個感官帶 `state: ok|unknown|absent`，node 契約必須寫 unknown 的行為**；(b) 轉接器不過就不寫，node 看到的是上一份；(c) 轉接器寫 last-good＋age，由 node 自己判。
**推薦 (a)**：這是核心三態原則延伸到最窄的 node；(b) 讓過時無聲；(c) 把判斷塞回受限 node，違反它的受限。這題影響所有 node 契約，不是選項。

**Q2 模糊有損（LLM）轉手要不要硬規定「最多一跳、放鏈尾」？**
(a) **硬規定，驗證器照 `via.fuzzy` 擋，含跨 node**；(b) 只算預算、不設硬上限；(c) 不管。
**推薦 (a)**：它是唯一能讓誤差不累積的結構性規則，而且 (1−p)^h 的帳算得出代價；代價是深組織裡只掛得到 digest 的 node 只能用精確步驟或申請加掛原文——我認為那正是想要的壓力。

**Q3 期限類時間預設換不換算？**
(a) **不換算：每回合回來源鐘讀「剩多少／到了沒」；換算只給規劃用、標 estimate 附誤差界**；(b) 統一換算成消費者回合；(c) 由發行者在 grant 裡預先換好。
**推薦 (a)**：跟 r1「不換算回合」、r2「跨線不比回合」一致；(b) 在 wake、pause、改 interval 下都會錯；(c) 把發行者綁死在消費者的節拍上。

（不用拍板、建議直接做：`in/` 慣例與信封；`adapt` 擴自 `relay`；函式庫／任務兩種模式都提供；任務模式下受限 node 以 `in/clock.json` 為鐘。）

## 10. 我最不確定的三件事

1. **`select`／`convert` 要不要有自己的表達式語言。** 7.2 用了 dotted path 與 `["sub", a, b]` 這種最小寫法，但這正是歷史上每個管線工具長成怪物的起點（jq、JSONPath、CEL…）。替代方案是「一步＝一個 Python 純函式，鏈宣告只點名函式」——簡單，但 S-01「LLM 只讀檔就看得懂」會變弱，而且就綁 Python 了。哪邊對，要等前三條鏈真的寫出來才知道。【低】
2. **「fuzzy ≤ 1 跳」在深組織裡守不守得住。** 如果掛載政策讓多數邊緣 node 只掛得到上級 digest，而 digest 已經 fuzzy，規則 2 會把它們全逼成「只能精確步驟」或「申請加掛原文」。這是對的壓力還是不可行的限制，取決於使用者看到的那個「非常多受限 node」的未來裡，掛載權限會多開放——我沒有這個資訊。【中偏低】
3. **時間換算的誤差界穩不穩、以及受限 node 到底要不要「我來得及嗎」。** proto7-2 還沒有 `timing`，抖動數據只有 fleet／longrun 的側面證據（c 差一倍）；如果多數受限 node 只需要「到了沒」，那 5.2 的換算整列可以砍掉，包會更小。還有任務模式的回合內先後問題，我用「轉接器當 node 的鐘」解，但沒驗過它在 pause／wake 下的行為。【中偏低】
