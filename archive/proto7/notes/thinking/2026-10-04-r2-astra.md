# 思想擴充第二輪：事實如何抵達，以及何時才算抵達

**這輪最值得增加的，不是更多時鐘，而是讓每次決策說得清楚：用了哪份事實、哪個版本、缺了什麼，以及提交行動時哪些前提仍然成立。**

接著上一輪的資源模型，可以把整條鏈補成：

> 來源發布事實 → 各層選擇、整理與傳遞 → 分配者依據明確版本提出方案 → 資源入口核對仍有效的條件 → 執行並產生新事實。

其中有四個容易混在一起的問題：

- **內容有沒有變**：完整性。
- **內容從哪裡來**：出處與證據。
- **現在還能不能採用**：有效性與權威。
- **何時看見、何時處理**：時間與排程。

出處完整不代表仍有效；喚醒成功不代表已讀；讀到最新版本不代表幾份資料彼此相容。

以下皆為設計提案。已讀指定背景、上一輪報告及相關原始文獻；未修改檔案，也未執行探針。wake 依本輪已定的「提前結束回合」推演；目前 [proto7-2 spec](../../../proto7-2/spec.md) 仍寫回合中 wake 無效，不能當成現有實作已支援。

## 1. 失真從哪裡來：同機仍然有「資訊距離」

同一台電腦消除了地理距離，沒有消除排队、讀取時機、權限與理解成本。直接掛載通常能省掉中繼等待，但不能因此假設所有讀取一樣快，更不能假設大家同時看到同一狀態。

「邊緣」應相對於某個事實來源來說，而非固定指組織底層。第一線最先知道執行結果，中心反而可能是該事實的邊緣。

可以把距離拆成四項：

| 距離 | 意思 | 例子 |
|---|---|---|
| 授權距離 | 要經幾次核准才讀得到 | 必須向兩層主管申請掛載 |
| 轉手距離 | 經過幾次轉送 | 原文逐層複製 |
| 加工距離 | 經過幾次摘要、合併與解釋 | 三層 LLM 各改寫一次 |
| 察覺距離 | 要等幾次處理機會 | 資料已存在，但接收者下一回合才讀 |

這四項不應壓成單一「幾跳」。五次原樣搬運，可能比一次錯誤摘要可靠；直接讀來源，也可能因讀者忙碌而很晚才採用。

### 七種失真，加上一種更隱蔽的混版

| 現象 | 怎麼發生 | 主要對策 |
|---|---|---|
| 延遲 | 等回合、等中繼、等 LLM、等鎖 | 分段量測；減少不必要中繼 |
| 遺漏 | 最新檔覆蓋舊版、未訂閱、摘要省略 | 事件保存、消費游標、必要主張檢查 |
| 改寫 | 數字、否定、單位、例外條件被改動 | 保留原文；衍生內容另存 |
| 編造 | 加入來源未支持的主張 | 主張對應證據；無證據標成推論 |
| 過時 | 快取未更新、撤銷尚未傳到 | 標明版本；行動入口重新核對 |
| 重複 | 重送、多條路線、gossip 回流 | 穩定 ID、冪等處理 |
| 順序錯亂 | 各路徑速度不同、程序並行 | 來源序號、明確依賴與版本規則 |
| **混版** | 分別讀到真的資料，組合卻不成立 | 決策記錄讀取版本；提交時驗必要前提 |

例如：「grant 第 3 版、帳第 44 版、目標第 2 版」每份都是真資料，卻可能是帳已撤銷該 grant、提案仍依舊目標產生的組合。

**直接讀來源能減少傳話失真，不能自動解決混版。**

另外，遺漏必須先有「應該收到什麼」的定義。只有看到第 43 號，不能推論漏了前 42 件：那些可能屬於其他主題或沒有授權閱讀。完整性要相對於明確的訂閱範圍判斷。

## 2. 事實的最小模型：一份可以追問的紀錄

這裡的「事實」最好先理解成：

> **某個來源，在某個位置，發布了一份可以引用的紀錄。**

這避免把系統保存的每一句話都預先當成真理。

至少要分清三種紀錄：

| 種類 | 它確立了什麼 | 例子 |
|---|---|---|
| 觀察 | 來源聲稱看到了什麼 | provider 回報這次用了 8,000 token |
| 權威提交 | 有資格的服務改變了某種狀態 | 帳本接受一筆預留；發行者撤銷 grant |
| 衍生判斷 | 某個處理者如何解讀輸入 | LLM 認為剩餘額度足夠完成工作 |

「LLM 說額度夠」和「帳本接受預留」必須是不同型別。**轉述可以傳遞內容，不能繼承原來源的授權能力。**

這種區分與 W3C PROV 把資料、產生資料的活動及參與者分開的方向相近；aos 可以借概念，無須搬入整套格式。[W3C PROV-DM](https://www.w3.org/TR/prov-dm/)

### 必備與選配

建議在 kernel／module 層建立小型共用外殼：

| 欄位 | 用途 | 是否必備 |
|---|---|---|
| `schema` | 知道怎麼解讀 | 必備 |
| `id` | 去重、精確引用 | 必備 |
| `producer` | 誰發布、哪個部署實例 | 必備 |
| `kind`、`body` | 紀錄種類與內容 | 必備 |
| `position` | 來源事件序號、觀察到的回合脈絡 | 可排序事件流必備 |
| `basis` | 依據哪些精確版本 | 衍生內容必備 |
| `transform` | 摘要、翻譯、推論或格式轉換 | 加工內容必備 |
| `supersedes`／撤回引用 | 哪份舊聲明被修正 | 按型別需要 |
| `validity` | 哪些条件下可採用 | 按業務需要 |
| 信心與評估結果 | 不確定性如何判斷 | 選配 |

不推薦所有事實都強制填 TTL、信心與完整轉手鏈。

- **TTL** 是「讀者願意接受多舊」或「權利何時失效」，不代表歷史事件到期後不再發生過。
- **信心** 要說是來源自述、評估器結果還是經校準的機率。裸的 `0.95` 很容易製造假精確。
- **轉手鏈** 要區分搬運與加工。原樣搬運保留原 ID；摘要、翻譯、推論建立新 ID，引用父資料。搬運回條另外記。

如此完整加工鏈是一張引用圖，不必每次把全部祖先重新塞進 JSON。

### 回合戳不能兼任事件 ID

同一 run 可以跨很多回合，同一回合也可以產生很多事件。因此事件最好有自己的：

```text
發布實例 + 事件流 + 序號
```

序號由單一寫入者或明確的序列化機制產生。整個 node 裡有多個任務，不能假設它天然就是一個依序執行的發布者。

回合戳則表達脈絡，例如「發布者最後確知已完成的是第 105 回合」。如果長任務只讀過一次 tock，就不能把那個數字冒充精確發布回合。

## 3. 「核心只留上一次」：相容，但沒有免費的完整歷史

應將兩種保存責任分開：

- **核心運行狀態**：最近回合、最近 run、最近控制結果。
- **業務證據**：授權、扣帳、撤銷、目標版本、決策輸入。

前者照現有原則只留上一次；後者由發布者或領域 module 自行保存。

重要事實應採：

```text
保存不可變版本 → 公布引用／更新 latest → 發出通知
```

儲存位置在槽外的業務資料區。發布者不能先通知，再期待歷史 module 趕快抄走，否則兩次取樣間仍可能被覆寫。

現有 [歷史 module 規格](../../../proto7-2/spec.md) 明確容許漏回合。它適合觀測，不能因增加輪詢頻率就變成完整帳務紀錄。

### 保存契約也是事實協定的一部分

「有原文連結」還不等於「能回頭查」。至少需回答：

- 誰保存原版本？
- 保存到何時？
- 引用者能否要求暫時保留？
- 已清除時如何回覆？

第一版不必做全域引用計數。可以先採領域規則：

- grant、結算與決策依據，留到相關在途工作結清及指定稽核期結束。
- 一般狀態快照允許覆寫，明示不保證歷史。
- 原版本不可取得時，回 `unavailable`；不能拿最新版冒充。

雜湊能檢查取回的內容對不對，不能把已刪掉的內容變回來。

事件溯源則更進一步：把業務事件當成重建狀態的依據。它要求從提交點保存事件，不是事後輪詢最新檔案。重播時也不能再次送出原本的外部副作用。[Event Sourcing 原始說明](https://martinfowler.com/eaaDev/EventSourcing.html)

## 4. 時間：回合、因果與經過多久，各管一件事

### 回合是局部邏輯時間，還不是 Lamport 時鐘

回合可以排序同一條時間線、同一生命期的回合邊界；但不能直接排序：

- 父線第 8 回合與子線第 90 回合。
- 同一回合內的兩次發布。
- 不同任務間沒有記錄下來的讀寫關係。

Lamport 時鐘除了本地前進，還需要接收訊息時合併對方的時鐘。它保證因果在先者的數值較小，但反過來不成立：數值較小不代表真的影響過另一事件。[Lamport 原論文](https://lamport.azurewebsites.net/pubs/time-clocks.pdf)

因此，B 在自己的第 5 回合讀到 A 的第 500 回合，**不應把 B 的回合跳到 501**。那會改變 B 的任務壽命、期限與排程。

第一版較適合保留：

```text
本地回合：工作在什麼階段
來源序號：來源發布到哪裡
精確依賴：這份輸出用了哪些輸入
```

例如：

```text
A 的觀察 a17
    → B 的摘要 b9，basis=[a17]
    → C 的提案 c4，basis=[b9, grant3, objective2]
```

父子 daemon 的巢狀關係只說明管理與啟動關係，不會自動使所有子事件受每個父回合排序。

### 各種工具應放的位置

| 工具 | 適合處理 | 不能因此得到 |
|---|---|---|
| Lamport 時鐘 | 維持已記錄因果方向、做穩定排序 | 並行判定、秒數、新鮮度 |
| 向量時鐘 | 多寫者間辨識因果版本與並行更新 | 未記錄通訊的因果、內容正確性 |
| HLC | 需要接近物理時間的跨系統排序與索引 | 完整因果判定、準時完成 |
| CRDT | 有明確合併規則的集合、計數與協作資料 | 任意業務限制都成立 |
| 事件溯源 | 帳、授權與決策歷史的重建 | 自動解決跨來源一致性 |

向量時鐘需要在相關事件與通訊處正確維護，不能把「各 node 最近看過的回合」隨便湊成向量就算完成。[Fidge 原論文](https://fileadmin.cs.lth.se/cs/Personal/Amr_Ergawy/dist-algos-papers/4.pdf)

HLC 結合物理與邏輯時間，保留單向因果條件。對目前同機、業務不依賴牆鐘的 aos，尚無必要先引入。[HLC 原論文](https://cse.buffalo.edu/tech-reports/2014-04.pdf)

CRDT 可讓符合條件的更新收斂；但一般可合併計數器即使最後正確算出負餘額，也沒有阻止先前超支。上一輪的額度仍需要權威准入，或事前切出互不重疊的支用權。[CRDT 原論文](https://reed.cs.depaul.edu/lperkovic/csc536/lecture10/techreport.pdf)

### 「看過最大序號」不等於「完整讀到這裡」

應區分：

- `latest_seen=43`：我持有第 43 版。
- `consumed_through=43`：在指定事件流與範圍內，直到 43 都處理了。
- `basis=[f43]`：這次決策確實用了 f43。

第二種才是完整前綴的承諾。來源若只提供最新快照，通常只能聲稱第一種。

同樣地，精簡 `basis` 很有用，但沒有記錄到依賴，應判「未證明相關」，不能直接判「兩者並行」。

### 牆鐘只給人看，不妨礙量測真實耗時

可以同時保留三種時間：

| 時間 | 用途 |
|---|---|
| 回合 | 業務階段、邏輯期限 |
| 單調經過時間 | 延遲、動作耗時、逾時、每秒速率 |
| 日期時間 `at` | 給人閱讀、對外行程的時間轉接 |

同一主機、同一開機及相容時鐘域內，可用單調鐘量跨程序延遲；不必讓業務回合同步。Python 提供 `monotonic_ns()`，其用途是量時間差，不受系統日期調整影響。[Python time 文件](https://docs.python.org/3/library/time.html)

重開機後不能直接把舊單調值拿來相減。若有時間命名空間或要把休眠時間算進期限，也需另定時鐘域與語意。

沒有任何物理耗時假設時，純回合系統可以承諾邏輯順序，不能承諾「三秒內看見」。

## 5. 拓撲：責任樹、可見範圍與資訊流可以不同

建議的預設組合是：

> **上級指出值得注意的事；來源供應精確版本；下游在授權範圍內按需取回。**

```mermaid
flowchart LR
    S["來源：保存原始版本"] --> M["中繼：篩選、摘要、協調"]
    M --> C["接收者：選擇要處理的事"]
    S -->|"核准掛載後取回原文"| C
    C --> P["提案：附實際輸入版本"]
    P --> G["權威入口：核對並提交"]
```

| 流動方式 | 價值 | 成本與限制 |
|---|---|---|
| 只吃上級 | 責任清楚、減少資訊量 | 等待逐層累加；摘要容易成唯一依據 |
| 直接讀來源 | 降低轉述失真、按需查證 | 需要發現來源、授權、版本與一致性處理 |
| 發布／訂閱 | 讓需要的人及早知道變化 | 訂閱範圍、背壓、游標與通知遺漏 |
| Gossip | 分散探索、散布索引與快取 | 重複、回流、難判完整；同機未必划算 |

掛載是組織對可見範圍的安排，但不必與上下級樹完全相同。上級可以准許成員直接讀共同帳本，仍保留自身的分配責任。

現有掛載是合作式協定；引用某個來源不表示已獲得讀取授權，也不表示作業系統已強制唯讀。跨子 daemon 的空間邊界仍需明示服務信箱或橋接。

### 中繼什麼時候值得存在？

中繼有价值的工作包括：

- 從大量來源中挑出與目標相關的少數資料。
- 合併重複證據，指出矛盾。
- 隱去接收者不該看到的內容。
- 把資料轉成適合某類決策的視圖。
- 代替下游完成昂貴而可共用的整理。

但若它只是把「額度 12,000、截止回合 80」換句話說，就可能增加成本與風險。

是否值得經過中繼，應比較**省下的閱讀與判斷成本**，以及增加的等待、資訊損失和查證成本；這也接上上一輪「管理成本算進總成本」。

### 不必先做全系統事實總帳

需要的是**各領域有清楚的權威**：

- 資源帳本確立支用與結算。
- 目標發布者確立有效目標版本。
- 觀察來源保存原始測量。
- 決策者保存自己的輸入與輸出。

可以有共同索引回答「去哪裡找」，但索引不是另一個能改寫所有事實的中心。

只有同一個不可拆分的限制需要共同提交順序時，才在該限制的範圍建立權威帳；不用把全部 aos 排成一條總時間線。

## 6. LLM：可以增加觀點，但原文與權威不可被洗掉

「LLM 只能加註」是值得採用的結構，但需要落成四條規則：

1. 原始版本不可變；更正另發新版本。
2. 摘要、推論與翻譯另有 ID，明示加工種類。
3. 關鍵主張連到精確原版本與段落。
4. 額度、撤銷、期限等控制條件，由確定性程式讀具型別的原資料。

如此 LLM 可以說「我認為這份 grant 足夠」，卻不能用一句摘要取代真正的 grant。

這仍不保證下游一定善用原文。**原文留著，只降低失去證據的風險；要防止錯誤行動，還需規定何時必須回查。**

建議回查條件包括：涉及支用、權限、否定條件、不可逆提交，或摘要明示存在衝突。一般導航與粗估則可容許摘要。

### 怎麼量摘要失真

不以文字相似度當主要指標。應量：

- 必要主張遺漏率。
- 輸出主張中沒有證據支持的比例。
- 數字、單位、否定、範圍與例外条件的錯誤率。
- 引用是否真的支持所指主張。
- 最後的錯誤決策率。
- 回查量、延遲與總成本。

若每跳獨立有機率 `p` 破壞某個必要主張，且不會修復，經 `h` 跳後至少一次受損的機率是：

```text
1 − (1 − p)^h
```

例如每跳 5%、十跳，約為 40%。這只是探針模型；真 LLM 的錯誤通常相關，不能直接套成實測預測。

尤其要防一種放大：

> 第一層把「尚未核准」摘要成「已核准」，後面十層都忠實引用它，最後看起來像十個來源一致同意。

這仍只有一個錯誤根源。證據應按原始來源去重，不能按轉述份數增加信心。

摘要還會改變選擇偏差：即使每句都正確，只挑成功案例，也足以讓上層錯估團隊表現。因此摘要應聲明範圍，例如「100 件中選出 8 件異常」，保留分母與選取規則。

## 7. 接上上一輪：決策要攜帶版本，行動要核對前提

使用權、帳、目標都要傳遞，但它們對新鮮度的要求不同。

| 資料 | 舊版本還能做什麼 | 新行動前要確認什麼 |
|---|---|---|
| grant 發布紀錄 | 證明曾授予什麼 | 是否撤銷、到期、已用完 |
| 帳快照 | 解釋當時估算 | 當前可預留量與在途狀態 |
| 目標版本 | 解釋方案為何如此選擇 | 現在接受哪版目標的提案 |
| 評估結果 | 記錄某套標準下的表現 | 工作集、評分規則是否可比較 |

因此，每份重要提案應留一份 `read_set`：

```json
{
  "grant": "g-a@3",
  "ledger_revision": 44,
  "objective": "review@2",
  "facts": ["source-a:observations:17", "evaluator-b:results:28"]
}
```

它表示「這次實際依據什麼」，不是把所有看過的資料塞進去。

提交時，權威入口檢查仍必要的條件。未必每個版本改動都要拒絕：帳增加了一筆無關收入，方案可能仍成立；grant 已撤銷則不成立。**應驗語意上的前提，避免把全系統任何更新都變成重做理由。**

多個獨立權威間若真的要求整組原子提交，仍需協調協定。多讀幾份 JSON、附上版本，不會自動形成交易。

### 新鮮度不能只靠時間戳證明

讀者拿著 grant 第 3 版，沒有再聯絡權威，就無法區分：

- 目前仍是第 3 版。
- 已撤銷，只是通知還沒到。

TTL、雜湊、Lamport 或向量時鐘都不能消除這個差別。因此應允許資料標成：

- 已知仍相容。
- 已知失效。
- 尚未核對。

讀取舊資料可以繼續分析；需要當前資格的副作用，則在入口核對。

目標換版也需要套用邊界：影響新提案、尚未准入的工作，還是連在途工作都重新驗收。這由目標政策決定，不能靠覆寫檔案暗中決定。

## 8. 多快看到：事件通知、回合推進與實際處理

一次事實抵達後被採用，可以拆成：

```text
來源提交
→ 通知被偵測
→ 接收者取得處理機會
→ 實際讀取
→ 計算／判斷
→ 下游提交
```

wake 只能直接改善其中幾段。任務若正在等 LLM，提前 tock 未必使它立刻讀信。

因此需要分開看：

- daemon 接受 wake。
- 回合完成提前收尾。
- 任務讀到某事實。
- 任務依該事實做了決策。

只有接收任務自己的游標或回條，才能表示後兩項。tock 通知不能代替業務已讀回條。

### 輪詢與事件的取捨

固定輪詢容易理解，成本約隨活躍讀者數與輪詢頻率增加。在到件時機均勻、讀者無阻塞等假設下，平均額外等待約半個輪詢週期；這不是端到端上限。

事件通知可降低空轉與稀疏訊息的等待，但需要管理合併、溢位及睡前競爭。Linux inotify 會合併相同事件，也可能因佇列溢位遺漏，因此不能拿通知次數當業務事件數。[inotify 手冊](https://man7.org/linux/man-pages/man7/inotify.7.html)

建議「持久資料＋事件提示＋低頻補查」：

- 資料先提交，再通知。
- 建立 watch 後重查一次，再等待。
- 重複通知合併成「有資料待查」。
- 通知漏掉時，補查仍能找到保留的資料。
- 若只保留最新值，就明示不能還原中間事件。

### wake 提前結束回合的最小語意

建議：

- 等待中的開回合：提前執行正常 tock。
- tick／tock 執行中：保留待處理提示，不重入。
- 活任務依 S-11 繼續，不因 wake 被 kill。
- paused node 不因 wake 解除任何 owner 的 pause。
- 合併 wake 時，不能把處理途中新到的提示一併清掉。

**還需明文定義下一個 tick。**已定的是提前結束回合；若收完後仍等到原定時點，下一次任務啟動不一定變快。若目的是縮短下一次決策等待，推薦收完後提前進下一個正常 tick，並明示節拍是重設起點還是保留原相位。

### 新連動：wake 可能改變資源供給速度

若提前 tock 後也提前 tick，會一起加速：

- `resume rounds:N` 的消耗。
- 按回合計的心跳與超時。
- grant 的回合期限。
- 每回合補額。
- `each` 任務與按回合評估的管理支出。
- 最新狀態檔的覆寫速度。

假設每回合補 20,000 token，請求者能大量 wake 授權時間線，就可能提高實際每秒補額。這是時間契約的結果，不是普通的抖動。

推薦沿用上一輪的「權威時間域」，再分清：

- 業務狀態機使用當地回合。
- 配額與 lease 指定控制時間線，必要時不接受業務 wake 加速。
- 真正的每秒速率由單調時間 adapter 管理。

獨立控制線只是另一個普通 node，不是新增全域時鐘。若契約本來就要按事件回合發放，也可以採用，但必須接受其速度隨事件量變動。

## 9. RTOS：先保證語意與失敗處理，再談時間上界

目前 aos 可以逐步做到三個層次：

| 層次 | 可以承諾什麼 |
|---|---|
| 邏輯確定性 | 舊回合確知關閉才開新回合；同一次事件不重複提交 |
| 可觀測的軟即時 | 在指定硬體、負載與工作規模下，量到延遲分布與逾期率 |
| 硬即時 | 在明列假設下，任何允許的執行都不超過時間上界 |

目前適合前兩層。

每動作一個程序、Python、檔案系統，不等於完全不能研究時間上界；但目前沒有為程序啟動、鎖、I/O、工作大小及主機干擾建立足夠的界線。固定 interval 只是意圖，**不是抖動上限**。Python 官方也明示 sleep 可能因排程而比要求時間長任意量。[Python time 文件](https://docs.python.org/3/library/time.html)

`action_timeout_s` 也應拆成「偵測逾時」「送終止訊號」「確知程序結束」。前一項到期，不保證後兩項瞬間完成。

### kernel／module 可提供的選項

| 選項 | 有用的承諾 | 限制 |
|---|---|---|
| 截止時間排序 | 越急的可執行工作越早取得機會 | 沒有容量與執行上界，不保證完成 |
| 執行預算 | 限准入次數、token、CPU 時間或占用時間 | 各量綱不同；不能互相冒充 |
| 過期結果政策 | 遲到結果不再套用，或降級採用 | 不代表外部呼叫已取消或不計費 |
| 依賴優先級傳遞 | 優先服務真正阻擋急件的工作 | 不會增加容量，也不會增加權利 |
| 節拍與抖動量測 | 找出哪段造成尾端延遲 | 觀測最大值不是最壞情況證明 |
| 平台適配 | CPU 配額、親和性、OS 排程等 | 需按部署驗證，不能只加 JSON 欄位 |

Linux SCHED_DEADLINE 本身也依賴執行預算、期限與准入控制；它不會替檔案 I/O 或遠端 LLM 自動提供完成保證。[Linux SCHED_DEADLINE 文件](https://www.kernel.org/doc/html/latest/scheduler/sched-deadline.html)

一個值得借的 RTOS 思想是：**即使不能保證工作準時完成，也能先把遲到後的行為定清楚。**例如停止新准入、保留未知在途、拒用過期結果，而非拼命補跑。

### 核心「不擋路」的具體要求

| 項目 | 核心／daemon 最少負責 | kernel／module 負責 |
|---|---|---|
| 回合 | 明確開始、完成與恢復邊界 | 業務期限與政策 |
| wake | 安全提前收尾、不重入、不越過 pause | 訂閱、偵測、過濾與通知政策 |
| 身分 | 可讀的 node、slot、run、daemon 世代 | 業務實例、事件流與保存 |
| 時間量測 | 最近 tick／tock 耗時、遲到量、收尾原因 | 分布、歷史、告警與負載實驗 |
| 事實 | 不必理解內容 | schema、出處、依賴、撤銷、版本 |
| 排程 | 執行既有任務與控制介面 | EDF、預算、優先級、退路 |
| 歷史 | 維持只留上一次 | 重要事件在来源提交時保存 |

時間線重建時需要可辨識的新生命期，但不必立即讓核心管理所有業務 ID。部署／事實 module 可先管理實例；若未來直接引用核心回合歷史，才需要核心提供不混淆的時間線世代。daemon 重啟世代不能兼任所有世代。

量測則需定義清楚參考點。S-08 是 tick 動作結束才開始回合；不能一處從程序呼叫前計 interval，另一處從結束後算抖動。

目前 spec 的 `at`、`tick_at`、`tock_at` 不足以證明已具備完整單調耗時量測。建議新增最近一次 duration 與原因，仍維持只留上一次。

完整分布也不能假設輪詢一定收得到。若量測 module 可能漏樣本，必須報缺口；探針可用外部包裝器逐次記錄。不能只留下較慢、較容易被取樣的回合，卻把圖表當完整分布。

**這一輪不建議要求核心承諾固定抖動上限。**先要求量得準、邊界清楚、不把不確定當完成；真正要承諾上界時，再對指定部署做工作量限制與平台驗證。

## 10. 事實檔草擬格式

以下是 module 協定草圖，不是現有 aos 指令。雜湊字串為示意。

原始事實：

```json
{
  "schema": "aos.fact/1",
  "id": "bank-7:ledger:442",
  "producer": {
    "space_instance": "space-root-1",
    "node": "services/bank",
    "instance": "bank-7",
    "slot": "ledger",
    "run": 99
  },
  "position": {
    "stream": "ledger",
    "seq": 442,
    "timeline_instance": "bank-clock-2",
    "observed_completed_tock": 105
  },
  "kind": "ledger.reservation_committed",
  "body": {
    "request_id": "team-a:req-18",
    "reservation_id": "reservation-18",
    "grant_ref": "g-a@3",
    "amount": 10000,
    "unit": "mock_total_tokens"
  },
  "basis": [
    {
      "fact_id": "team-a:requests:18",
      "service": "team-a",
      "object": "requests/18.json",
      "digest": "sha256:<exact-bytes>"
    }
  ]
}
```

這份紀錄表達「第 442 筆已接受預留」，不表達「現在還剩多少」。它也不靠 `producer` 自述建立安全身分；可信程度仍取決於部署與入口。

LLM 加註：

```json
{
  "schema": "aos.fact/1",
  "id": "analyst-4:summaries:27",
  "producer": {
    "space_instance": "space-root-1",
    "node": "teams/a",
    "instance": "analyst-4",
    "slot": "analyst",
    "run": 108
  },
  "kind": "derived.summary",
  "body": {
    "claims": [
      {
        "text": "請求 18 已取得 10000 token 的預留。",
        "evidence": [
          {
            "fact_id": "bank-7:ledger:442",
            "pointer": "/body"
          }
        ]
      }
    ]
  },
  "basis": [
    {
      "fact_id": "bank-7:ledger:442",
      "service": "resource-bank",
      "object": "facts/ledger/442.json",
      "digest": "sha256:<exact-bytes>"
    }
  ],
  "transform": {
    "type": "llm_summary",
    "policy": "summary-policy/2"
  }
}
```

`service` 由部署綁定成已核准掛載，`object` 相對於該服務；不用來源機器的絕對路徑。雜湊對保存的確切位元組計算，避免重排 JSON 後誤認為同一內容。

這份摘要沒有權力延長預留、改變數量，或證明預留尚未結算。那些是其他權威事實。

## 11. 三個離線探針

以下數字是建議實驗條件與門檻，沒有實測結果。

### 探針一：把傳遞速度與語意失真拆開量

**假設：**直接取來源能減少中繼等待；不可變原文與關鍵欄位回查，能阻止指定摘要錯誤進入行動。

**設計：**

- 固定 seed，1,000 份含數字、否定、例外、撤銷的事實。
- 團隊深度 1、3、5 層。
- 分別比較逐層轉送／直接讀來源，以及原文／假 LLM 摘要，避免一次改兩個因素卻不知道效果來自哪裡。
- 假 LLM 按腳本注入省略、改數字、拿掉否定、無依據推論。
- 另比較「有引用但來源只留最新版」與「保留精確版本並回查」。
- 注入重送、亂序、慢讀者及原文不可取得。

**量測：**發布至讀取、讀取至採用的延遲；各類失真率；錯誤決策率；原文取回率；讀取量與摘要成本。

**成功標準：**

- 保留期內的原版本可正確取回；錯版替代為 0。
- 在明定的結構化控制條件範圍內，摘要錯誤造成的錯誤准入為 0。
- 重送不重複執行。
- 來源穩定且掛載可用後，所有合法案例完成，不能靠全部拒絕取得零錯誤。
- 來源已清除時明示不可驗證。
- 直接讀取若未降低延遲，能指出瓶頸在哪一段。

此探針驗結構，不推論真 LLM 的失真機率。

### 探針二：不同時鐘、混版與「看似最新」

**假設：**精確輸入版本加權威提交檢查，足以處理主要跨線競爭，不需要全域回合或全系統總帳。

**設計：**

- bank、objective、worker、observer 四條不同節拍時間線，含一個子 daemon。
- 同回合發布多件事實；任務跨回合完成。
- 撤銷已提交，但 worker 仍拿舊 grant。
- 提案形成期間目標換版。
- observer 暫停期間來源連續更新三次。
- 同一路徑重建新實例；舊提案稍後到達。
- 調整假日期時間，保持事件與單調時間軌跡不變。

**成功標準：**

- 跨線回合大小不被拿來判先後；同回合事件不撞 ID。
- 舊實例資料不混入新實例。
- 撤銷提交後，權威入口不再接受該舊權利的新准入。
- 每個提案可指出實際使用的 grant、目標與帳版本。
- 目標換版按預先選定的套用邊界處理。
- 取樣缺口被記為缺口，不假裝完整前綴。
- 日期時間調整不改變純邏輯決策。
- 條件重新穩定後，合法工作能繼續完成。

### 探針三：wake 的收益、風暴成本與配額時鐘

**假設：**事件提示加補查能改善稀疏工作的反應時間；但大量 wake 可能增加系統負載，並改變按回合計的資源契約。

**設計：**

- interval 1 秒，比較純輪詢與事件提示加補查。
- 假處理耗時 0、50、500 ms。
- 在 tick、等待、tock、pause 各階段到件。
- 漏掉 10% 通知、重複送大量 wake，並加入 CPU／檔案負載。
- 同時比較兩種補額：當地事件回合、獨立控制時間線。
- 明確分開測「只提前 tock」與「下一 tick 也提前」。

**量測：**完整階段延遲、p50／p95／p99、最大觀測值、回合數、程序成本、miss、gap、配額發放量。

**成功標準：**

- tick／tock 重疊、未關先開、越過 pause 都為 0。
- 有保存的事實最終全部處理；漏通知可由補查找回。
- 稀疏、未過載組的可用延遲 p95 至少下降 50%。
- 假 LLM 成為瓶頸時，如實顯示喚醒收益受限。
- 相同控制時間軌跡下，業務 wake 不增加獨立控制線的發放額。
- 當地回合補額若加速，結果與契約一致且可見。
- 過載時顯示排隊與遲到，不靠補造回合或抹掉未知在途美化結果。

尾端延遲不達標，就是該部署尚不能提供所測服務目標；不把觀測最大值宣布為硬上界。

## 12. 最值得使用者拍板的五個問題

### 1. 共用事實格式放在哪一層？

- **A：kernel／module 共用協定，核心只提供執行脈絡。**
- B：所有對外資料都由核心要求統一外殼。

**推薦 A。**先用 grant、帳與目標三類驗證；若每個 module 都重複補同一項底層資訊，再把那項資訊放進核心。

### 2. 下游預設如何取得資訊？

- **A：上級提供摘要與索引，核准後可直接取來源。**
- B：一律由上級轉述，原文也經上級取得。

**推薦 A。**責任仍分層，查證不必逐層排隊；掛載由組織政策決定。

### 3. 哪些資料承諾可追溯？

- **A：一般狀態可取樣；授權、帳與重要決策依據由來源保存精確版本。**
- B：全部資料都只保留最新，接受歷史查不到。
- C：全部事實統一永久保存。

**推薦 A。**以「是否影響權利、支出或重要行動」作初始判準，不先養一個全域永久總帳。

### 4. LLM 摘要能否直接作為控制依據？

- **A：摘要用於導航與提案；權利、數量、期限由原資料與權威入口決定。**
- B：信任上級摘要，下游直接執行。

**推薦 A。**原型驗收要求指定控制欄位的摘要錯誤准入為 0，同時量回查成本與待定比例。

### 5. 配額與 lease 預設跟哪個時間走？

- **A：明指控制時間線；業務 wake 不自動加速它。**
- B：跟當地事件回合，接受事件越多、期限與補額越快。
- C：一律改用實際經過時間。

**推薦 A，現實每秒速率另用時間 adapter。**保留 aos 回合抽象，也避免通知流量默默改變經濟規則。

## 我最不確定的三件事

1. **多少因果資訊才值得保存。**精確 `basis` 足以解釋很多決策，但可能漏掉隱含輸入；完整記錄所有讀取又可能太貴。最需要探針找出的，是哪些漏記會真的造成錯誤行動，以及哪些只是增加稽核細節。

2. **原文回查能降低多少真實 LLM 錯誤。**保留證據可避免無法追溯，不能保證模型理解正確。模型也可能引用對的段落、得出錯的結論。結構化權利與帳可以確定性檢查；開放語意仍需另外驗證。

3. **事件加速何時會轉成整體減速。**少量事件很可能受益；大量 node、每回合程序成本與檔案競爭，可能使 wake 風暴拉長其他人的尾端延遲。真正需要量的是有效工作完成速度與總成本，並找出應合併通知、限制開回合頻率或拆分 daemon 的負載界線。
