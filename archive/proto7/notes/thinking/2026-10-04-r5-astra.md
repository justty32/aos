**思想擴充第五輪：把第四輪的強結論收回到成立的範圍**

這輪保留的主線是：**各 node 不必先同步時間，也能透過明確的交接合作；語言層讓等待與接續可表達，九軸提供組合檢查的依據。** 要修正的是，把有用的類比當成保證，以及把需要時才加入的能力說成共同必備架構。

以下依[第四輪題目](2026-10-04-r4-topic.md)，反芻 [Fable 報告](2026-10-04-r4-fable.md)、[astra 報告](2026-10-04-r4-astra.md)與[綜合](2026-10-04-r4-synthesis.md)。只提方向，不列拍板題；全程唯讀，未更動 repo 或 scratchpad。

**一、逐條處理七個分歧與空白**

1. **CDC 借多少：兩份各抓到一部分，需要拆開分類。**

   Fable 抓對「速度不同，需要保存與確認」；astra 對保證範圍的限制較準。但「位準／事件／握手」不是同一層的分類：前兩者談資訊，握手談交接方式。

   更清楚的順序是：先說下游需要知道目前狀態、每件事件，還是某段期間的性質；再說資料怎麼保留、何時確認、滿了怎麼辦。「最近十回合最大值」是窗口內容，既可只留最新窗口，也可逐窗保存。事件也可以用保留到確認的單件信箱交付，不必一律套 FIFO。

   因此，撤回「只有三種原語，而且 aos 全有了」。原子覆寫、序號與回條只是材料，不能直接推出不漏件、及時交付或效果只發生一次；第一軸也不必拿這組分類取代原本的整批／串流。

2. **相對論的界線：採 astra 的弱類比。**

   回合是各時間線的序號；「我看到 B 第 100 回合」是一次觀察。這足以支持局部視角，不必進一步稱為物理固有時，或宣稱不存在共同時間。同機可共享時間來源，卻仍沒有共同工作進度。

   Fable 的「沒跟牆鐘有約，快慢就不是問題」也太滿。沒有截止時間，速度差仍會造成積壓、漏取樣與資源占用。能撤回的是「第 5 回合必然落後第 100 回合」，不能把速度差的後果一起撤掉。

3. **流速算不算資源：可以相容，但須區分觀測與供應。**

   「最近每秒十回合」是量測結果；「提供多少執行機會」才是可分配的供應。若某個任務包能在指定條件下承諾服務率，流速可以進入資源契約，但不是光有回合計數就得到的保證。

   保留 Fable 的「補給率」直覺，採 astra 的較窄表述：daemon 控制節拍，不等於保證吞吐量；wake 不增加算力。流速不必另立第十軸，也不必把 daemon 重新定義成通用資源分配者。

4. **框架放什麼：兩份談不同層次，不必二選一。**

   `pc` 與區域變數回答「從哪裡繼續」；請求身分、預留與未知效果回答「現在憑什麼能繼續」。有外部效果的工作可能兩者都需要，純轉換則不必帶整套帳務。

   方向是：**小框架保存接續需要的狀態與引用，責任紀錄由負責的任務包保存。** astra 的「未履行責任」應按需增加，不能變成每一步的固定負擔。槽外保存也只是位置選擇；何時可清、重開如何找到，仍是包自己的契約。

5. **期限最後一哩：astra 補得對，入口要落在實際能控制效果的地方。**

   「效果入口」可以是接受列印工作的服務、寫入資料的工具，或管理某項資源的任務包；它不是另一個全域組件。只有能把條件核對與接受請求連在一起的地方，才能承諾期限內准入。若只是讀完有效檔，再呼叫無法配合的外部工具，中間的空窗仍在。

   同時修正 Fable 的兩個鐘：效期用**契約指定的鐘**，等待上限也用**等待者選定的基準**，不固定為「對方回合／自己回合」。准入、完成與逾時後責任的區分沿用[第四輪 astra](2026-10-04-r4-astra.md)，但不要求每個純讀取步驟都走完整流程。

6. **編舞投影：降為局部合作的可選工具。**

   一段角色已知的合作，可以先寫共同流程，再產生各 node 的步驟；但「產物是局部的」不代表「設計不需要全域知識」。把拓撲稱為投影結果，沒有消除這個前提。

   依[原則 3](../principles.md)，先讓單一 node 說清楚自己的輸入、輸出與等待，再容許任務包包裝固定合作。撤回「投影自然保證不死鎖」與「這是唯一形狀」；實際保證仍受通道、失敗與等待條件限制。

7. **這層值不值得存在：價值在減少重複的交接與恢復工作。**

   它值得留下的資訊是：「正在等哪件事、採用哪份依據、效果是否已發生、重開後怎麼繼續。」這在單一 node 跨 run 時就可能有用，不必等到跨 node 才成立。

   普通 Python 可以繼續承擔一整段工作。語言層若能讓人少寫交接邏輯、看懂卡在哪裡，就有價值；若只是把 Python 改成更多表格，就沒有。多前端應共享目標格式與執行語意，比對 JSON 是一種驗證方式，不能取代對等待、效果及恢復行為的驗證。

**二、第四輪還有哪些話說得太滿**

除上述七條，以下幾處需要明確修正：

- **「每個 await 必跨回合；程序內運算同回合免費」撤回。** await 表達等待依賴；結果已就緒時未必需要下一回合。一支程序也可能跨很多回合。合併步驟可省交接成本，但不能順便刪掉重新取樣、取消、授權核對與恢復位置。
- **「pause 自己，再請對方 wake」不能當通用等待法。** 現有 `wake` 不移除 pause owner；清單未空仍不開新回合。而以自己回合計算的耐性，也會跟著停住。一般等待應先作用在工作本身；若選擇停整個 node，就須有仍會運行、且有權恢復它的一方承接喚回與期限。[spec §2.3–2.4](../../../proto7-2/spec.md)
- **「pause 後沒有新事實，事實不會變舊」撤回。** 既有任務仍可寫檔，外部世界仍在變。回合差停止增加，只表示這個度量停了，不能推出資料仍適用。
- **「負載是可預測雜訊，控制事件不可預測」撤回。** 負載可能突變，pause 也可能事先排定；量測分位數不是硬上界。保留「估計附條件，期限依原契約判」即可，不需要用這個二分替它背書。
- **九軸提供檢查依據，尚不是完整證明。** `once` 是啟動策略，不代表有限生命週期；宣告掛載不代表執行時必然可達；格式相容也不會自動產生正確轉接。未知限制的是工具能替工作增加哪些自動行為，不是保證任務不能執行。[九軸報告](2026-10-04-axes-astra.md)
- **幾率性不單獨決定重試、快取或把關。** 確定運算仍可能遭遇暫時故障、產生副作用；隨機工作也可能安全重送。須分清重送同一請求、重新抽樣與沿用結果。第四輪由可預測性推出的「機械驗證足夠／必須找另一主體」一併撤回，本輪只留定義。
- **「不知道」是判斷結果，不是統一等待政策。** 它不能冒充否定，也不必永遠原地等；等待、停止或查詢既有結果，由工作契約決定。尤其效果未知，不能默認為尚未執行。
- **「核心零新增」保留為本輪方向，不能當所有保證都已可達的結論。** astra 也要收窄這點：任務包無法補回已消失的事件，或替不支援查詢的外部服務證明效果。核心精簡的意思是責任有歸屬，不是把完整平台搬到每個 node。[原則 7–10](../principles.md)、[組件契約](../../../proto7-2/notes/component-contracts.md)

**三、把使用者原話的情境補回來**

「任務拖慢 ticktock」至少有三種不同情況，不能只用「各走各的鐘」帶過：

| 被拖慢的是什麼 | node 可能呈現的樣子 | 對合作的意義 |
|---|---|---|
| 任務本身 | 回合照走，工作尚未完成，後續啟動可能因忙碌跳過 | 等工作結果，不能拿回合數代替進度 |
| tick／tock 的控制與整理動作 | 回合開關本身延後 | 同線的取樣、派工與期限檢查也可能延後 |
| 共用 CPU／I/O | 任務與時間線都變慢，其他 node 也可能受影響 | 分開時間線不等於隔離資源 |

依[現有 spec](../../../proto7-2/spec.md)，tick 不等一般任務完成；`early_tock` 也有 interval 邊界，不能解讀成最慢任務無限拖住回合。收回合後還有節拍等待，提前 tock 也不等於下一回合一定立即開始。

所以，下午兩點 A 在第 5 回合、B 在第 100 回合，先辨認的是**A 的哪一段變慢，以及它造成什麼後果**。不補跑 95 回合，也不把「慢就慢」解讀成不必處理積壓。尤其逾時檢查若依賴同一條被拖慢的時間線，檢查本身也會晚到；登記期限不等於準時介入。

語言層對非 agent／LLM 用途也有直接意義：

- **備份或批次轉檔：**固定輸入版本、並行處理、等待遠端交付、重開後接續；領域演算法仍是一支普通程式。
- **感測資料處理：**說清楚要最新溫度、每次異常，或一段期間的最大值；慢消費者才不會把「沒看到」當成「沒發生」。

等待、交付、接續與必要的資源管理歸通用包；agent 狀態與 LLM 專用處理另分層。這些用途不必附帶模型、prompt 或完整帳本，符合[原則 5、8](../principles.md)。

**四、一頁骨架：時間流速 × 語言層 × 九軸**

從我的 node 出發，只描述：**我依據什麼、等什麼、何時能繼續，以及中斷後留下什麼。**  
時間流速影響取得證據與提供服務的時機；語言表達依賴與接續；九軸檢查這些組合有哪些依據。

`Lisp／Python 函式庫等 → 共同目標格式：任務表＋需要的步驟與契約 → 普通任務包執行`

| 面向 | 語言層需要保留的意思 |
|---|---|
| 時間契約 | 哪個鐘、哪次觀察、等哪件事；估計、期限與工作進度分開 |
| 1．I/O | 格式與單位；需要保留哪些狀態、事件或窗口差異 |
| 2．生命週期 | 等完成、等就緒，還是等下一件交付 |
| 3．跨呼叫狀態 | 接續需要的少量狀態，以及必要紀錄的引用 |
| 4．資源 | 工作、等待與積壓需要多少容量；供應條件是什麼 |
| 5．可中斷性 | 停下會留下什麼，如何確認停止或接續 |
| 6．執行保證 | 同一請求能否重送；未知效果如何確認 |
| 7．組合 | 依賴、並行、交接，以及不能被合併掉的邊界 |
| 8．環境 | 實際來源、版本、掛載、權限與其他成立條件 |
| 9a．幾率性 | 固定比較條件後，是否仍包含隨機因素 |
| 9b．可預測性 | 相對於觀察者及其掌握資訊，結果是否落在預料範圍；只留定義 |

每個工作只採用需要的部分。daemon／tick-tock 維持基本職責；編譯、通道、接續與檢查由任務包承擔。共同格式不承諾自動消除速度差，也不要求全網先有共同流程。

**五、這一輪改變了什麼看法**

1. 從「跨速率的三種原語已齊備」，改成「先說需要保留什麼，再確認交付方式實際保證什麼」。
2. 從「await 決定一回合一步」，改成「語言保存必要的等待、觀察與恢復邊界」；執行粒度不由 CPU 類比預先定死。
3. 從「共同框架保存完整合作責任」，改成「責任隨工作需要增加」；簡單工作應維持簡單。

**六、仍然最不確定的三件事**

1. 最小共同語意要多大，才能讓多前端與接續真正省事，而不把普通程式拆成大量表格。
2. 外部工具能提供多少結果查詢、去重與期限能力；這決定上層保證能走到哪裡。
3. 當工作與時間線一起受負載拖慢時，量測與調節任務能維持多可靠的服務條件；目前不能從回合計數推得。
