# 各 node 時間流速不同 × 任務體系之上的語言 × 九軸——思考報告第四輪（Fable）

依據：`r4-topic.md`（含使用者三段追加）、`lang-fable.md`、`axes-astra.md`、九軸原文、`principles.md` 11 條、r1～r3 綜合與我前三輪報告、`proto7-2/spec.md`、`component-contracts.md`、`core-slimming.md`、`layer-interfaces.md`。只讀 repo，沒跑模型。接著前三輪想，講過的只引用。**全是方向，不是決定；本輪不列拍板題。**

把握程度：【高】＝repo 證據或推理直接得出；【中】＝合理但沒驗；【低】＝猜測。

---

## 0. 先講五句

1. **回合是每個 node 的「固有時」，不是座標時。** 沒有「別人的現在」這種事實，只有「我上次看到它在第幾回合、已過了我幾回合」。「下午兩點才第 5 回合」不是落後——除非有人用牆鐘跟它約過；aos 的回合不補課（spec §11「慢就慢」），所以它根本不是在模擬牆鐘。【高】
2. **流速不是宣告，是量出來的事實，而且一個 node 有三個流速**：時間線的（回合／秒）、每個任務的（完成／回合）、觀察者的（取樣／它的回合）。流速的變化分兩類：**可預測的雜訊**（抖動、負載）與**不可預測的控制事件**（pause、wake、改 interval、超載）。前者能換算附誤差界，後者只能回來源讀——這正好給 r3「期限不換算、規劃才換算」一個更乾淨的理由。【高】
3. **跨流速只有三種原語，aos 全有了**：暫存器（傳「位準」）、FIFO（傳「事件」）、握手（傳「控制」）。這是硬體 CDC 的三件套。規則一句話：**位準可以走暫存器，事件絕對不能走暫存器**——longrun 漏 33% 的 tock、A3-01 意圖被重播，都是把事件塞進暫存器。【高】
4. **語言層的目標格式是「程式＝步驟表、程序＝基本塊、state.json＝協程框架」**。編譯器真正要做的只有一件事：**在每個 await 處切開**，await 之間的東西合成一支程序（一回合內免費），await 本身一定跨回合。這就是 async/await 的狀態機轉換，不是新發明。多前端（Lisp、Python 函式庫、LLM 直寫）都只是這張 JSON 的不同寫法。【高】
5. **九軸是這個語言的型別系統，而「時鐘域」是其中的單位型別**：「team-b 的第 160 回合」和「我的第 160 回合」是不同型別，相加是型別錯誤，比較要經轉換且結果是 `estimate`。拆開第 9 軸後，型別系統多了兩條獨立規則：**幾率性決定能不能重試／快取，可預測性決定能不能機械把關**。【中偏高】

## 1. 時間流速：站在單一 node 看

### 1.1 回合是固有時

相對論借得上的只有一句：**沿著不同世界線走過的固有時不同，不變的是事件與因果序。** 套到 aos：

| 相對論 | aos | 已有的對應 |
|---|---|---|
| 固有時 τ | 自己的 `round` | S-08 |
| 座標時 | **沒有**；牆鐘 `at` 只給人看 | spec §0 |
| 同時性相對 | 「別人的現在」不是事實，是一次觀測 | r2 AoI |
| 光錐／因果 | 「依據了哪一版」（`about` 雜湊） | r2 §4.1 |
| 時間膨脹 | pause（流速 0）、wake（變快）、負載（變慢） | P2-01、r2 §7.2 |

推論：**所有「某 node 幾點幾分在第幾回合」的句子都是牆鐘陳述**，只有在 node 跟牆鐘有約（人、供應商、r1 的牆鐘窗口）時才有意義。沒約的話，快慢不是問題，只是兩條固有時不同。要「對齊」的從來不是回合，而是**事實的版本**（它看過我哪一版、我看過它哪一版）。【高】

### 1.2 流速是量出來的事實，而且有三個

一個 node 身上其實有三個速率，常被混成一個：

| 速率 | 單位 | 誰決定 | 誰看得到 |
|---|---|---|---|
| **時間線速率** | 回合／牆鐘秒 | `interval_ms`、pause 清單、wake、tick／tock 耗時（槽數、/proc 掃描、不理 SIGTERM 的任務各拖 1 秒）、`early_tock` 時最慢的任務、機器負載 | `at` 差分（粗）；C4 `timing`（細）|
| **任務服務率** | 完成／回合 | 任務自己跑多久；`each` 跑 3 回合就只有 1/3 的服務率，`skipped: busy` 看得到 | last-round 的 `skipped`、任務自己的 `seq` |
| **觀察者取樣率** | 讀到的來源版本數／來源版本數 | 讀者的時間線速率 vs 來源變化率 | 讀者自己的 `seen.json` 缺號 |

三個不相等是常態：node 第 100 回合不代表它做了 100 件事；每回合都忙的 `each` 任務會把服務率壓到遠低於時間線速率。**所以回合是時鐘，不是進度條**；進度要靠任務自己發布的計數（r2 的 `run.seq`），不能從別人的回合推。【高】

流速的變化來源分兩類，這個分法是本輪的主軸之一：

- **可預測的雜訊**：tick／tock 耗時的抖動、負載造成的遲到。有界（r2 推估 U < 0.7 時 p99 遲到 < 20% interval），可以量、可以附誤差界。**邊界就是准入門檻 U**：U 過 1 以後排隊爆開，就從可預測變成不可預測（fleet 的 1.8×／4×／5.5×）。
- **不可預測的控制事件**：pause／resume、wake、改 `interval_ms`、unregister、daemon 重開。由**別人**決定、不連續、沒有分布可言。它們出現時任何比例換算都錯（r3 已說），但它們**都是可讀的事實**（status 的 `paused_by`、`phase`、`interval_ms`、`woke` 事件）。

所以對流速的正確態度：雜訊用誤差界吃掉，控制事件回來源讀。這就是 r3「規劃類換算標 estimate；期限類不換算」的底層理由，比「換算會錯」更精確：**換算只對可預測那一半成立**。【中偏高】

### 1.3 別人的「現在」：三態

單一 node 讀到別人的 `round.json`／`last-round.json`／status，能分出的只有三種：

| 看到 | 判定 | 怎麼分 |
|---|---|---|
| round 在前進（跟我上次看到的不同） | 活著，比我快或慢 | 比 `(round, open)` 與上次 |
| round 沒動、`paused_by` 非空 | **已知停住**（它的固有時停了，事實不會變舊） | 讀 status（這是控制事件，有出處）|
| round 沒動、沒 pause、`at` 很久沒變 | **不知道**：很慢？卡住？死了？ | 只能等或讀 `phase`／`last_error`；不能當死 |

這張表的意義是：「對方很慢」和「對方死了」在單次觀測裡**分不出來**，分得出來的只有「對方被明確停住」。所以跟慢 node 協作，不要用「幾回合沒動＝死」做判斷；要用它自己發布的心跳（它的 `seq` 或 status 的 `at`），而且 `at` 是牆鐘，用它就是跟牆鐘約了。【高】

**兩種新鮮度要分開**（補 r2 的 AoI）：

- **來源新鮮度**：AoI 用來源回合算，被 pause 的來源 AoI 不長——它沒有新事實，正確。
- **世界新鮮度**：來源觀測的是外面的世界（感測器、人、市場），來源停了世界沒停。這種只能用牆鐘或世界自己的事件計數算。

受限 node 的契約要寫清楚它要的是哪一種；多數「監看」node 要的是第二種，而第二種在被 pause 的來源那裡**永遠拿不到**，應輸出 `unknown`（r3 的 `source_paused` 其實就是這個）。【中偏高】

### 1.4 跨流速的三種原語：CDC

硬體跨時脈域（CDC）的教訓最貼近，因為它面對的正是「兩邊各走各的鐘、比例未知且會變」。CDC 只有三種合法做法，aos 每一種都已經有對應：

| CDC 原語 | 傳什麼 | 規則 | aos 已有的 | 違反時的症狀 |
|---|---|---|---|---|
| **兩級同步器 → 暫存器** | **位準**（一個會停留的值） | 任何速率比都安全；代價是延遲與混疊（看不到中間變化） | `round.json`、`tock.json`、`out/latest.json`、r3 的 `in/<sense>.json` | 慢讀快：漏版本（longrun 33%）；快讀慢：同一版讀到很多次 |
| **非同步 FIFO**（灰碼指標） | **事件**（每一個都算數） | 寫者追加、讀者游標；滿了要背壓 | 一寫者一檔＋`seq`、`consumed_through` 游標、帳本 jsonl、件式交付 | 把事件塞進暫存器＝丟事件 |
| **握手**（req／ack，四相） | **控制**（要對方做一件事） | 旗子舉著直到對方回應；跟速率比完全無關 | `ctl/` → `ctl-done/`、槽 `ctl.json` → `ctl-done.json`、`mount-req` → `mount-done`、請求／回條信箱 | 沒等 ack 就撤旗＝對方沒看到；重舉同一面旗＝做兩次（A3-01） |

三條推論：

1. **位準／事件是輸入的型別，不是傳輸的選項。** 「現在溫度 80°C」是位準，「曾經超過 80°C」是事件。r3 astra 的「必要區分」（always-normal vs hot-then-normal）就是在問：這個 node 吃的是位準還是事件？吃事件的 node 前面一定要有 FIFO，不管速率比是多少。這把第一軸的「流量模式」跟時間流速綁在一起：**第一軸該標的不是 batch／stream，是 level／event**。【高】
2. **快讀慢要做「邊緣偵測」，慢讀快要做「FIFO 或承認混疊」。** 兩個方向是對稱的：速率比 r＝來源回合／我的回合，r < 1 看到重複（要用來源版本去重，不能用自己的回合當冪等鍵），r > 1 看到缺號（要 FIFO，或在契約裡接受 `latest`）。轉接鏈要宣告自己是哪一邊、容忍哪一種。【高】
3. **握手是唯一不怕速率的東西，所以控制面天然跨域。** daemon 主迴圈 20 ms、node 2 秒，ctl 照樣可用，正是因為它是握手而不是暫存器。推論：**跨速率要「等對方做完一件事」，走握手，不要輪詢對方的回合。**【高】

### 1.5 等待與期限：每一次跨 node 的等，都有兩個鐘

等一個不同流速的 node，涉及兩個互相獨立的計時：

- **效期（validity）**：這件事還有效嗎——用**對方（或發行者）的鐘**，回來源讀「到了沒」（r1、r3 共識）。
- **耐性（patience）**：我願意等多久——用**我自己的回合**，因為等的成本是我的回合（也可能是我的 grant 窗口）。

兩個哪個先到都該觸發。r3 的 `max_age_rounds` 是耐性，grant 的 `until_round` 是效期；混成一個就是 K-2 那類坑。對受限 node，兩者都是轉接器交付的位準（`expired`、`waited_rounds`），它自己不算。【中偏高】

**等慢 node 的正確姿勢不是輪詢，是 pause 自己＋請對方 wake 我**：wake 經 daemon ctl 約 20 ms 就開回合（layer-interfaces 實測），而且是握手——它就是跨時脈域的**中斷線**。閒等的 node 不花回合、不花 CPU，被叫醒時對方的事實已經在。tickless 探針做的就是這個，只是沒這樣命名。代價是 r2 說過的「wake 讓回合變快」，所以以回合計的東西（配額）仍要掛在控制時間線。【中偏高】

### 1.6 流速算不算資源、算不算軸

分三層回答：

- **對時間線而言，是資源。** r1 已把「一條時間線的回合槽」列為資源（capacity＋窗口＋set）；流速就是這個資源的**補給速率**。而且它是**有爭奪的**：interval 的擁有者、每個 pause 的 owner、任何有 `.aosd` 寫權的 wake 者、以及負載，都在動同一個旋鈕；pause 已經有 owner 清單，就是多控制者的證據。用 r1 的定義（「誰站在中間、誰就定義了資源」）：**daemon 就是流速這種資源的閘門**，ctl 是它的請求格式。這是第一個閘門不在 kernel 層而在核心的資源——不需要新東西，只是認出來。【中】
- **對任務而言，不是第十軸。** 任務不擁有流速，它活在某個流速底下；那是第八軸「環境」的一部分（跑在哪條時間線、它的鐘怎麼走）加上第四軸（要幾個回合）。astra 的「時間契約」（讀取規則、時間基準、反應要求、中斷缺口）正是把它放進環境與 I/O，而不是另立一軸，我同意。【中偏高】
- **對 node（時變函式）而言，是觀測得到的事實。** clock-quality（r2）產出的 p50／p99 就是它；別的 node 讀這份事實決定「這條線的回合能不能當時間用」。它是**可預測性**的證書（見第 3 節），不是宣告。【中】

### 1.7 類比：借什麼、避什麼

| 來源 | 借 | 避 |
|---|---|---|
| 相對論 | 固有時；因果序才是不變量；「同時」不存在 | 任何形式的全域時間 |
| Lamport／向量時鐘 | 依據關係用 per-object 版本（r2 已定） | 收到訊息就把回合往前跳；全 node 向量 |
| **CDC** | 三原語、位準／事件分型、邊緣偵測、背壓 | 零延遲假設；雙時脈共用記憶體（aos 的多檔目錄快照不原子，r2 已指出）|
| 固定時步模擬（accumulator） | 「邏輯只看步數，不看 dt」——spec §0 已是 | **補課**（落後就連跑幾步）：aos 不補（§11）；要補課是 kernel 包的 `resume --rounds N` |
| lockstep | 要一致切面的 node 群用 gang／barrier（kernel 包） | 全系統 lockstep：一個慢 node 拖全部 |
| rollback 網路碼（GGPO） | 先用預測值做、晚到再重算——**只准用在冪等、可重算的步驟**（第六軸） | 對有外部副作用的步驟推測執行 |
| dead reckoning | 兩次觀測之間估對方進度——只給規劃，標 estimate（r3 已定） | 用估計值判期限 |
| **編舞程式設計（choreography）** | 跨 node 程式寫一份全域舞步，投影成每個 node 的步驟表（第 2.5 節） | 讓語言認識拓撲 |

## 2. 語言層：共同的目標格式與編譯器要正視的事

### 2.1 目標格式長什麼樣：兩張表＋一個框架

lang-fable 說「tasks.json 一項＝一條指令、inst＝execve 參數塊、步驟表＝控制流程」。本輪把它收成一個完整的對應，重點是**三樣東西各司其職**：

| 傳統 | aos 目標格式 | 性質 |
|---|---|---|
| 程式映像的佈局（哪些執行緒、各自怎麼起） | `tasks.json`（name、mode、max_live、from／until_round、mounts） | **放置**：靜態、每回合由 tick 直譯 |
| 程式本體（.text） | 步驟表 `*.steps.json`（wait／run／count／ctl／guard，加一個 `emit`＝寫檔） | **控制流程**：由直譯器任務一回合推一步 |
| 協程框架／暫存器 | 槽裡的 `state.json`（`pc`、計數、等哪個 run） | **狀態**：換 run 不清，keep 死了接得上 |
| 符號表／重定位 | `mounts`（名字 → 空間路徑）；`slot` 釘名 | **連結**：由編譯器從程式引用的路徑推出來 |
| 系統呼叫 | `ctl` 檔、`mount-req`、daemon ctl | 握手 |
| 中斷 | `tock.json`（時鐘）、`ctl.json` kill（非同步終止） | — |
| 陷阱／例外 | 三態 `unknown`（直譯器預設：原地不動，下回合再看） | — |

**關鍵是「程式即資料」要落在目標格式而不只在前端**：步驟表是 JSON，`cat` 得懂（S-01），檢查器讀得了（第 2.4 節的型別檢查就是讀它），而且 kernel 可以改它（selfprog 的合法形式）。Lisp 的優點「S 式≈JSON」在這裡兌現：前端是不是 Lisp 無所謂，**目標一定要是資料**。【高】

### 2.2 編譯器真正的工作：在 await 處切開

CPU 的指令一條一個週期；aos 的「步」一步至少一回合。但**一支程序內部要做多少事都在同一回合內**（任務內層是任何語言）。所以：

> **基本塊＝一支程序。塊的邊界＝await。** await 只有四種：等別的 run 結束（exit.json）、等某個檔出現／變版、等某個回合、等某個 ctl 回條。

編譯器的工作因此很單純，而且是已知的技術——**async/await 的狀態機轉換**（C# 的 `async`、Rust 的 generator、Kotlin 的 suspend 都是這樣編的）：

1. 把程式在每個 await 處切開，每段變成一步的 `run`（一支 once 程序或一段內嵌腳本）。
2. 跨段存活的區域變數**提升到 `state.json`**（協程框架）。
3. `pc` 寫進框架；直譯器任務每收 tock 讀框架、推一步、寫回。
4. 沒有 await 的連續段**合併**成一支程序——這是編譯器最重要的最佳化，決定一件工作要幾回合。
5. 互不依賴的段**展開成並行的 once 項**（`max_live`、不同 `slot`），匯合點是「等這幾個 exit.json 都在」——這是資料流語言的 fire 規則。

三個 aos 特有的差異，編譯器要正視：

- **三態是回傳型別，不是錯誤碼。** 每個 await 回 `Ok v | Absent | Unknown`；前端可以用 `match` 寫三個分支，寫不滿的由編譯器補預設（`Unknown → 原地等`，`Absent → 看契約`）。這等於把核心的三態原則抬到語言層，LLM 在 selfprog 把「讀到 tock.json」當成「等到了」的錯，型別層就擋掉。【高】
- **狀態在檔案裡、不在記憶體。** 框架升到檔案後，「區域變數」可以被 `cat`、可以被另一個 run 接手——這是優點（S-01、keep 接前任），代價是框架要小、要原子寫。編譯器要拒絕把大東西放進框架（交付物寫槽外，W7）。
- **沒有「下一句馬上執行」。** 「A 做完馬上 B」若 A、B 在同一基本塊，免費；若中間有 await，至少一回合。前端要讓這條線看得見（例如 Lisp 裡 `await` 是顯式的；Python 函式庫裡 `.then()` 是顯式的），別讓人以為是普通函式呼叫。

### 2.3 多前端編譯到同一張表

| 前端 | 像什麼 | 擅長 | 要小心 |
|---|---|---|---|
| Lisp／S 式 | 巨集展開：`(retry 3 (run ...))` 展成 count＋run 兩步 | 把「重試、扇出／匯合、超時」這類模式寫成巨集，一處定義 | 不要讓巨集產生目標格式沒有的步型 |
| Python 函式庫（builder） | Airflow 定 DAG、PyTorch tracing：執行 Python 只是為了**產生圖** | 工程師熟；可以跑型別檢查當單元測試 | 誘惑是把邏輯寫進 Python 閉包——那就不是資料了 |
| LLM 直寫步驟表 | 直接產出目標格式 | 它本來就會寫「有序計畫」（lang-fable §5） | 要給 schema 與檢查器回饋 |
| 人手寫 JSON | 組語 | 小工作 | — |

**驗證前端的方式只有一種：比對產出的 JSON。** 同一個程式用三種前端寫，目標格式要 byte 相同（或正規化後相同）——golden test。這也是「產出物一樣就好」的可檢驗版本。【高】

### 2.4 九軸怎麼變成型別系統

型別系統的用途是：**在編譯期拒絕會在執行期出事的組合**，而且不需要執行。九軸正好提供「步驟的簽名」；下面是我認為最值得先做的規則（每條都對應 selfprog 或探針裡真的出過的錯）：

| 規則 | 用到的軸 | 擋什麼 | 對應的真實錯 |
|---|---|---|---|
| `await (exit of X)` 要求 X 的生命週期是 finite／once | 2 | 等一個常駐服務「結束」 | selfprog 把一次性工作寫成 keep 14 次 |
| `retry n` 只能包冪等步，或包「查回條→決定」複合步 | 6 | 重試造成重複副作用 | retry_lost 的雙跑風險 |
| 被 kill 後自動重起要求可中斷性 safe／resumable | 5 | 半份交付物 | W7、astra §1 |
| 跨 run 讀 state 要宣告，編譯器才釘同一 `slot` | 3 | 換槽後失憶 | A3-01 那類「證據隨換 run 消失」 |
| 需要 grant 的步，自動包成 reserve→step→settle（像 RAII／bracket） | 4 | 忘了結算、在途未知被歸還 | r1 的「在途不退款」 |
| 消費端的 `need` ⊆ 生產端輸出 schema，否則插 adapt | 1、7 | 吃不下 | r3 reach≠digest |
| 程式引用的 `mnt/x/...` 自動生成 `mounts`；掛不到就編譯錯 | 8 | 執行期才發現掛載缺 | 「寄不出去先寫加掛請求」 |
| **時間值帶時鐘域**：`round@team-b` 與 `round@self` 不同型別；相減要經 `convert`，結果是 `estimate` 型；期限比較只准 `read_source` | 8＋時間契約 | 用自己的回合判別人的期限 | hsched 的 `stale_envelope`、r3 探針二 |
| **幾率性**：非確定步 **不准** 進「失敗就重跑」的重試（重跑可能給不同答案，應視為新一次決策）；確定步失敗**不值得**重跑（同輸入同結果），只有外部故障 X 才重跑 | 9a | 無意義的重試、把重跑當成「再抽一次」 | hsched 政策重問 |
| **可預測性**：非確定但可預測（有 schema／界）的步，後面插**機械驗證器**即可；不可預測的，後面必須接人或另一個獨立判斷 | 9b | 把 LLM 自由文字當控制依據 | r2「摘要不當控制依據」 |
| 到受限 node 的路徑上 fuzzy 步 ≤ 1、且在鏈尾 | 9＋7 | 誤差累積 | r3 規則 |

幾個觀察：

- 這套規則**沒有一條需要核心知道九軸**；全部在編譯器（任務包）與檢查器裡。對核心的要求是零（第 5 節）。【高】
- 沒宣告的軸＝未知；未知時型別檢查**保守**（不准重試、不准自動重起、不准機械把關），而不是拒絕編譯——這是 astra「沒宣告先視為未知、任務仍能跑」的語言版。【高】
- 時鐘域當單位型別，是 F# 的 units of measure 那一路：便宜、機械、抓得到最常見的錯（混用兩條線的回合）。它直接把第 1 節的「固有時」變成編譯期檢查。【中偏高】
- 「fuzzy ≤ 1」是**仿射（affine）約束**：一條路徑上這個效果最多用一次。效果系統（effect system）就是為這種事設計的；不必真的做成形式系統，只要檢查器數 `via.fuzzy` 就是。【中】

### 2.5 跨 node（不同流速）的程式＝編舞

一支跨 node 的程式，每個 node 各走各的鐘，彼此只靠檔案。最貼切的模型不是多執行緒，是**編舞程式設計（choreographic programming）**：全域寫一份「誰在什麼條件下給誰什麼」，編譯器**投影（endpoint projection）**成每個 node 自己的步驟表，node 之間的交接自動變成 FIFO 或握手（第 1.4 節的原語）。好處是正確性由構造保證（不會死鎖、不會一邊等另一邊沒送的東西），而且**每個 node 的步驟表仍然是單 node 視角**（原則 3）——拓撲是投影出來的結果，不是語言認識的東西。【中】

流速差在這個模型裡的位置：

- 每個跨 node 的 await 自動帶兩個鐘（1.5 節）：效期用對方的時鐘域型別，耐性用自己的回合。
- 位準型交接投影成「寫 `out/`＋對方讀」；事件型交接投影成「一寫者一檔＋游標」；控制型投影成「請求＋回條」。選哪個由第一軸的 level／event 決定，不由作者手選。
- 「對方太慢」在語言裡**沒有特殊語法**：就是耐性先到、走 `Unknown`／`Absent` 分支。慢不是錯誤。

這一節把握度最低，因為 choreography 在工業上還不普及；但它是唯一同時滿足「全域可讀、單點可測、各走各鐘」三件事的已知形狀。先當方向，不當設計。【中偏低】

## 3. 第九軸拆開：點到為止

使用者定義：**幾率性**＝每次是否一樣；**可預測性**＝結果是否落在觀察者預料的範圍內，而且**它是相對於觀察者的**（懂的人預期 LLM 大多不對，不懂的人預期都對）。這塊先只當定義，不展開。只記三件跟本輪有關的推論：

1. **對 kernel 的影響分得很乾淨**：幾率性管「重做」（重試、快取、重播）——確定的東西重跑沒意義、可快取；隨機的東西重跑是新一次抽樣，不是「再試一次」。可預測性管「把關」——落在已知界內的，驗證器是機械的；不在的，才需要另一個主體判斷。兩者各自獨立，所以第 2.4 節把它們寫成兩條規則而不是一條。【中偏高】
2. **時間流速就是「隨機但可預測」的例子**：抖動有分布（U < 0.7 時有界），所以能換算附誤差界；pause／wake 這類控制事件不在任何分布裡，所以只能讀。而「預料範圍」正是觀察者相對的——有 `timing` 的觀察者預得準，只有 ISO `at` 的預得粗，受限 node 什麼都預不了只能吃轉接器給的 `estimate`。這跟使用者的主體性之說是一致的，不必另外處理。【中】
3. **其他軸也各藏兩件事**（只列，不展開）：第 1 軸「搆得到／吃得下」（r3）與「位準／事件」（本輪）；第 2 軸「啟動策略／run 的本質」（astra）；第 4 軸「上限／份額／供應保證」（r1 astra）；第 5 軸「本地不壞／外部沒在途」（astra）；第 6 軸「啟動最多一次／效果恰好一次」（astra）；第 8 軸「可達／有授權／有效」（astra）。共同形狀是**「它做什麼」與「我們能對它說死什麼」**分開——第 9 軸的拆法只是這個形狀最明顯的一例。往後要不要全拆，是很後面的事。【中】

  時脈域） │  state.json ＝ 協程框架      九軸 ＝ 每步的型別簽名            │  時脈域）

**同一件事的不同面**（這張表是本輪最想留下的）：

| 看起來是不同的題 | 其實是同一件事 |
|---|---|
| r3「期限不換算，回來源讀」／本輪「期限用對方時鐘域的型別」／r1「grant 自己宣告鐘」 | **時鐘域是單位型別**；跨域比較只准經來源 |
| r2「取樣定理」／r3「必要區分」／本輪「位準 vs 事件」 | **輸入的流量型別**：位準可暫存器，事件要 FIFO |
| r2「意圖用推、事實用拉」／本輪「握手 vs 暫存器」 | 控制走握手（不怕速率），事實走暫存器（接受混疊） |
| r3「fuzzy ≤ 1」／本輪「仿射效果」／9b「不可預測要另一主體把關」 | **效果預算**是型別層的事，檢查器數就好 |
| 核心「once 最多一次」「retry_lost」／第 6 軸／9a「確定的重跑沒意義」 | **重做政策由幾率性＋冪等性共同決定**，編譯器包，不由核心猜 |
| lang「state.json 的 pc」／第 3 軸／核心「同槽接前任」 | **協程框架**：核心給的槽重用語意就是為它存在的 |
| r1「時間線回合是資源」／本輪「流速是資源、daemon 是閘門」 | 同一個資源的存量與補給率 |
| r3「受限 node 的 need」／本輪「端點投影後的局部型別」 | **node 的輸入型別**；拓撲是投影的結果 |

一句話收：**前四輪談的全是「跨一條邊界」——速率域、格式域、授權域、確定性域——每條邊界都要同步器、兩邊的型別、一份預算；aos 的核心只提供邊界本身（node、回合、槽、檔），其餘都是任務包。**【中偏高】

## 5. 對核心的要求：零

逐項檢查本輪提到的每樣東西能不能用「任務、包裝、工具」三個接面做到（core-slimming §5）：

| 東西 | 做法 | 核心要動嗎 |
|---|---|---|
| 步驟表直譯器、編譯器、型別檢查器 | 任務包（`step`、`compile`）；只用 once＋exit.json＋edit_json＋ctl | 否 |
| 時鐘域型別、兩個鐘的等待 | 編譯器＋adapt 包的 `time` 任務（r3） | 否 |
| 位準／事件分型、FIFO、游標 | kernel 慣例（一寫者一檔＋seq，r2 已提） | 否 |
| 等慢 node：pause 自己＋對方 wake | 現成（tickless 探針） | 否 |
| 流速當事實：clock-quality | observe 包（r2 已提）；精度靠 C4 `timing`（r2 已提，**不是新要求**，本輪只是第三個理由） | 否 |
| 流速當資源：閘門 | daemon 本來就是；只是認出來 | 否 |
| 九軸宣告、證書 | 包的契約檔（astra §2） | 否 |

刻意不要的：核心不認識步驟表、不排回合內先後、不加 hook、不認識時鐘域、不量別人的流速。唯一碰到核心邊緣的是 lang-fable 不確定 #3（槽被 tock 刪掉前直譯器要讀到 exit.json）——它在本輪仍是「取樣能不能跟上」的問題，解法在直譯器那邊（釘 slot、`seen_round` 比對），不在核心。【高】

## 6. 這一輪最重要的三個新觀點

1. **跨流速只有三種原語，而且是輸入的型別決定用哪一種**：位準走暫存器、事件走 FIFO、控制走握手。這一句同時解釋了 longrun 漏 tock、A3-01 重播、r3 的必要區分、r2 的事實拉意圖推，並把第一軸該標的東西從 batch／stream 改成 level／event。【高】
2. **語言層的編譯器就是 async/await 的狀態機轉換**：基本塊＝一支程序、await＝回合邊界、state.json＝協程框架、三態＝回傳型別。目標格式不是新機器碼，是「步驟表＋tasks.json＋框架」三件已經存在的東西；多前端只是同一張 JSON 的不同寫法，golden test 就能驗。【高】
3. **流速的變化分成可預測的雜訊與不可預測的控制事件，分界線是准入門檻 U**；前者能換算附誤差界，後者只能回來源讀。這給 r3 的「期限不換算、規劃才換算」一個更精確的底層理由，也讓「時鐘域是單位型別、估計是另一型別」有了依據。而流速本身是時間線這個資源的補給率，daemon 是它的閘門——不是任務的第十軸。【中偏高】

## 7. 我最不確定的三件事

1. **「一回合一步」會不會讓語言層被真實用法繞過。** 編譯器合併基本塊能把回合數壓到「await 的個數」，但一件三個 await 的工作在 2 秒 interval 的 node 上還是 6 秒；若多數人退回「一支 Python 自己管」，型別系統就沒有東西可檢查。wake 能補延遲，但會動到回合≈時間（r2 的 `min_interval_ms`）。要等第一個真實工單才知道。【低】
2. **位準／事件的分型在真實感官上能不能二分。** 「平均溫度」是位準，「超溫次數」是事件，但「最近 10 回合的最大值」兩邊都沾；窗口聚合可能需要第三型（astra 的「小而可組合的表示」sum／count 也許就是它）。分不乾淨的話，第 1.4 節的規則會留下灰區。【中偏低】
3. **編舞／端點投影是不是過度類比。** 它漂亮地滿足「全域可讀、單點可測、各走各鐘」，但投影需要知道參與的 node 有哪些——跟「拓撲自然長出來」（原則 3）有張力：也許只適合一個團隊內部的固定舞步，不適合開放的 node 網路。而且 aos 的邊是檔案不是通道，死鎖自由那類定理要重新證。【低】
