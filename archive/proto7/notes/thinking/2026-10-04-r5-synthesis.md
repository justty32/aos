## 1. 第四輪七個分歧，收斂結果

| # | 分歧 | 收斂 |
|---|---|---|
| 1 | CDC 借多少 | **借分類，不借保證**。撤回「三種原語、aos 全有了」。先說下游要知道什麼（目前狀態／每件事件／一段期間的性質），再說怎麼保留、何時確認、滿了怎麼辦。核心本身只保證「最新值」與「請求＋回條」兩種；不漏件的事件通道是任務包自己的契約（保留多久、誰付）。窗口不是第三種傳輸，是有人替你吃事件後算出來的值。第一軸是**加上**這組區分，不取代原本的整批／串流。 |
| 2 | 相對論類比 | **只留一句**：回合是 node 自己的計數器，看別人的回合是一次觀察。不談固有時、時間膨脹。astra 補：「沒跟牆鐘約就不算落後」也太滿，速度差照樣造成積壓、漏取樣、占資源。 |
| 3 | 流速算不算資源 | **流速是觀測，不是新資源**。可分配的仍是回合槽、CPU、處理名額、保留容量；改流速的旋鈕（interval、pause、wake）就是 r1 已有的使用權。Fable 撤回「daemon 是流速資源的閘門」（跟原則 4、7 有張力）。wake 不增加算力。 |
| 4 | 框架放什麼 | **框架小，只放接續需要的狀態與把手**（請求 id、預留 id、等哪個檔）；責任本體由負責的任務包在槽外保存（帳本、信箱、回條區）。astra 補：責任紀錄**按需增加**，純轉換不帶整套帳務。 |
| 5 | 期限最後一哩 | **效果入口＝實際能控制效果的地方**（gateway、管某資源的包、tick 看 `until_round`），就是 r1 的強制點，不是新的全域組件。帶期限的等待要向入口拿回條，不是讀完有效自己判。沒有入口的地方縫關不上，契約寫明只能事後查。效期與耐性各用契約／等待者選定的鐘，不固定成誰的回合。 |
| 6 | 編舞 vs 原則 3 | **降級為可選的部署模板**：角色已知的固定合作（一個團隊）可以寫一份共同流程，產出各 node 的步驟表；開放網路照原則 3，各 node 對著鄰居的契約寫自己的表。撤回「投影保證不死鎖」。 |

## 2. 第四輪撤回或收窄的說法

- **「每個 await 必跨回合」撤回**（astra）：結果已就緒就不必等下一回合；執行粒度不由 CPU 類比定死。合併步驟不能順便刪掉重新取樣、取消、授權核對、恢復位置。
- **「pause 自己＋請對方 wake」不是通用等待法**：現在的 wake 不移除 pause owner，名單未空照樣不開回合；而且自己的耐性跟著凍住，對方死了就永遠睡。只有另一個仍在走、有權喚回它的一方承接期限時才成立。
- **「pause 後事實不會變舊」撤回**：已在跑的任務還能寫檔，外部世界照走。
- **「負載是可預測雜訊、控制事件不可預測」撤回**（astra）：負載會突變，pause 可以事先排定。只留「估計要附條件，期限照原契約判」。
- **九軸是檢查依據，不是證明**；第四輪的十一條型別規則先只留三條能自付的：等「結束」只能等有限工作；重試只包冪等步或「先查回條再決定」；時間值帶是哪條線的。其餘之後再說。
- **幾率性不單獨決定重試**：要分「重送同一請求」「重新抽樣」「沿用結果」。由可預測性推出「機械驗證就夠／要另一主體」也撤回，**可預測性只留定義**。
- **「不知道」是判斷結果，不是統一的等待政策**：等、停、查，由工作契約決定；效果未知不能當成沒執行。
- **核心零新增仍成立，但不等於保證都做得到**：任務包補不回已經消失的事件，也替不支援查詢的外部服務證明不了效果。

## 3. 第四輪漏掉的角度

**「被任務拖慢 ticktock」**（使用者原話）。對著 proto7-2 spec 查：
- 任務本身**拉不長回合**：固定節拍時回合等滿 interval；`early_tock` 只會縮短；忙的任務只是 `skipped: busy`。
- 回合真正變慢的來源：有人 pause、tick／tock 失敗退避或停在 error 等人、tock 自己的工作量、機器超載、interval 本來就大。前兩種是有人決定或已知的狀態，**都在 status 裡讀得到**；後兩種缺量測（r2 提過的 `timing`）。
- astra 補：共用 CPU／I/O 時任務和時間線一起慢，分開的時間線不等於隔離的資源；**逾時檢查若依賴同一條被拖慢的線，檢查本身也會晚到**。
- 所以等一個慢 node，第一步是**先讀它的 status**，看是哪一段慢、造成什麼後果，再決定等不等。

**語言層對非 agent／LLM 用途**：步驟表的原型是 PLC 的順序功能圖（SFC），本來就是給不寫程式的操作員看的。備份（輪替不冪等，不准無腦重試）、批次轉檔、CI、感測→判斷→致動、定期報表，都吃得到前面那幾點價值。LLM 只是多一種作者（原則 5）。

**多任務＝多執行緒**（使用者的對應）：兩層都對——**執行緒＝槽**（`max_live`），**協程＝一支步驟表**（內部等待是切換，扇出才多占槽）。

**直譯器自己的洞**（Fable）：子任務結束是事件，但 exit.json、last-round 都是只留最新的檔。修法在直譯器：子任務把結果寫成槽外的結果檔（帶 run id），直譯器讀它；exit.json 只當旁證。

## 4. 骨架（落地時對著它查）

1. 回合是 node 自己的計數器；跨 node 對齊的是**依據版本**。回合變慢的原因多半在 status 裡，先讀再等。
2. 跨 node 傳的東西先分清下游要知道什麼：**目前狀態／每件事件／一段期間**。核心只保證最新值與請求＋回條；其餘是任務包的契約。
3. 每次等待分清**效期**（契約指定的鐘）與**耐性**（等待者選的鐘）；能動手的地方由入口核對、給回條。沒有入口的寫明只能事後查。
4. 語言層產物＝**tasks.json（放置）＋步驟表（控制流）＋小框架（接續狀態與把手）＋契約**；責任本體住在負責的包。前端任意。
5. 九軸是每一步的簽名，工具只做**保守檢查**：沒宣告就是未知，任務照跑，只是不替它自動重試、平行化、替換。第 9 軸＝幾率性＋可預測性（後者只留定義）。
6. daemon／tick-tock：**零新增**。

兩份的逐軸對照表見 [Fable §4](2026-10-04-r5-fable.md) 與 [astra §四](2026-10-04-r5-astra.md)。

## 5. 仍然不確定（帶到落地）

1. **最小共同語意要多大**，才讓多前端與接續真正省事，而不是把 Python 拆成一堆表格。
2. **直譯器只讀結果檔**時，子任務在寫結果前被殺，就只剩一個解不開的「不知道」；真實工作裡這種情況多不多，會不會逼出「once 結束後多留幾回合」這類核心需求。
3. **外部工具能提供多少查詢、去重、期限能力**，決定上層保證走得到哪裡。
4. **順序依賴**：語言層最強的價值（子工作對核心可見）要等資源界線真的在入口執行才值錢；這層也許該排在資源包之後。
