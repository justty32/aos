## 1. 綜合第 3 節七條，逐條處理

### 1.1 CDC 借多少 → 借分類，不借保證；窗口不是第三種原語

兩邊各對一半。Fable 的「三種原語」對的是**分類**：跨 node 傳的東西只有位準、事件、控制三類，輸入契約要說清楚吃哪一類——這條留。astra 對的是**保證**：硬體的 FIFO 是一塊有深度、有 `full` 旗的實體；aos 的「FIFO」只是慣例（一寫者一檔＋`seq`＋游標），**深度、保留期、誰付儲存都要有人承諾**。所以我在第四輪說的「aos 全有了」太滿，改成：**核心只保證位準（`round.json`、`tock.json`、`out/latest`）與握手（ctl → ctl-done）兩種；事件通道是任務包的慣例，要自帶保留契約**。astra 的「有限緩衝、來源不等、消費者可永久暫停、不漏件四者不能同時成立」就是那張契約的第一條，跟 CDC 的背壓是同一件事，兩邊沒有真分歧。【高】

**窗口**（「最近 10 回合最大值」、「期間曾否過熱」）不是第三種傳輸原語，是**由轉接器從事件算出來的位準**：消費端拿到的是一個會停留的值（可走暫存器），但算它的人必須吃事件（要 FIFO）。所以窗口是 r3「精確有損」轉接的一種，它的範圍、缺口怎麼標（`gap`／`unknown`）是轉接器的契約；儲存成本也因此落在轉接器——這正是 astra「慢消費者在要資源」的位置。這一條同時解掉我第四輪的不確定 #2 與 astra 的第三列：**傳輸三類不變，輸入契約三種（位準／事件／窗口）**，窗口＝「位準，但要有人替我吃事件」。【中偏高】

### 1.2 相對論類比 → 只留一句，連「固有時」都可以不要

Fable 與 astra 實質一致（沒有座標時、不建換算公式、跨線比依據版本）。差在 Fable 的表多借了「時間膨脹＝pause／wake／負載」一列——這列借過頭：相對論的膨脹是對稱、有公式的；pause 是**有 owner 的控制事件**，既不對稱也沒公式。更誠實的說法根本不需要物理：**回合是 node 自己的計數器**（spec §3：tick +1），別人讀到它只是一次觀察。「固有時」當口號可以，當模型不行；骨架（第 4 節）用「自己的計數器」。【高】

### 1.3 流速算不算資源 → 流速是供給率；旋鈕是三種既有使用權；量到的是觀測

把物件拆開就沒有分歧：

| 東西 | 是什麼 | 誰早就說過 |
|---|---|---|
| 回合槽（一條線一回合幾個槽） | **資源** | r1 |
| `interval_ms`、`paused.json` 的 owner 清單、wake | 動供給率的**旋鈕＝使用權**（r1 Fable 已把 `paused.json` 列為三種既有 grant 之一） | r1 |
| 量到的回合／秒、p50／p99 | **觀測** | r2 clock-quality |
| 「指定負載下一秒內回覆」 | **契約**裡的保證 | astra r4 |
| 流速本身 | 資源的**供給率**：不是分配對象，是上面幾樣的導數 | 本輪 |

所以我第四輪「daemon 是流速這種資源的閘門」**撤回**：它沒有新內容，而且把「資源」這個詞往 daemon 身上掛，跟 r1 共識「daemon 裡不出現任何資源概念」（原則 4、7）有張力。daemon 只是三種既有使用權的執行者，一如 tick 是 tasks.json 的執行者。astra「wake 不會憑空增加算力」補的是：回合供給率 ≠ CPU 供給率，兩者由 r2 的准入 U 連起來。【高】

### 1.4 框架放什麼 → 框架放把手，責任放在責任的擁有者那裡

不是張力，是 async/await 類比本來就有的兩層：**協程框架**（`pc`＋區域變數）與**框架指向的堆上物件**。aos 對應：框架＝槽裡的 `state.json`，壽命＝任務名字在表上的壽命（spec §5.1：名字拿掉才刪槽，§8：「就是不要了」）；astra 要的「未履行的責任」（請求身分、預留、等哪種回條、在途效果）**壽命必須長過槽**，所以住在發它的那個包的槽外狀態裡：預留在帳包的帳本、請求在對方信箱、回條在入口的 done 區（r1：「已發出的使用權寫在檔案裡，不會跟著分配者一起死」）。框架只放**把手**（請求 id、預留 id、等哪個檔）。這樣框架仍然小、仍然 `cat` 得懂；astra 的「新 run ≠ 新業務請求」自動成立，因為請求 id 是框架裡的值，換 run 不清（W6）。編譯器的 reserve→step→settle 括號就是在保證：**框架裡每個把手都有槽外的擁有者**；槽帶著活把手死掉時，擁有者看到的是孤兒預留，照 r1「在途不退款」處理。【中偏高】

### 1.5 期限的最後一哩 → 「效果入口」就是 r1 的強制點；期限是回條，不是你手上的值

空白其實 r1 填過：**強制只能放在副作用入口**（持有 key 的 gateway、tick），grant 的 `enforcement: key／os／tick／audit` 欄說的就是「這條界線有沒有人在動手時核對」。所以：

- 有入口的資源（LLM 端點經 gateway、起任務經 tick 看 `from／until_round`、掛載經 tick）：astra 的「觀察／准入／提交」三段成立，**語言層的「帶期限的 await」要編成「向入口要回條」，不是「讀最新觀察再自己判」**。Fable 第四輪型別規則「期限比較只准 `read_source`」修成：**觀察階段只准回來源讀；支用階段只收入口回條**。
- 沒有入口的（普通檔案寫入）：這段縫關不上，契約只能寫 `audit`，誤放事後查——這是 spec §11「合作式」的既有界線，不是新洞。

tick 看 `until_round` 是核心裡唯一的入口，r1 已定進核心；本輪不需要再多一個。【高】

### 1.6 編舞投影 vs 原則 3 → 降級為「團隊部署模板」；開放邊只靠契約

投影要事先知道參與者，這在**封閉群組的部署時**是成立的——而那正是 r1 的模板／實例複製、core-slimming 的 pack install 展開成多個 node 的 tasks.json。所以編舞不是「跨 node 程式的模型」，只是「一次產出一個團隊 N 份步驟表」的一種寫法。**開放網路沒有編舞**：每個 node 對著鄰居的契約（r3 的 `need`、axes-astra 的 node 契約）寫自己的表，拓撲照原則 3 長出來。我第四輪說的「正確性由構造保證（不會死鎖）」撤回：aos 的邊是檔案、兩邊都在輪詢，那類定理不轉移；真正需要而且已經有的保證弱得多——**沒有 node 會永遠卡住，因為耐性一定會到、走 Unknown 分支**。【中偏高】

### 1.7 這一層值不值得存在 → 價值不在表達力，在三件 Python 單檔做不到的事

兩份第四輪都把疑慮放在「是不是 Python 的劣化版」。該比的不是寫法，是**一支 Python 自己管**（不管寫得多好）結構上拿不到的東西：

1. **子工作對核心可見**：步驟展開成 once 任務，就吃到核心的三樣保證（最多一次、exit.json、kill 收得到）與 kernel 包的視野（記帳、監督、`max_live`）；Python 在任務裡自己 `subprocess` 十次，核心一個都看不到，r1 的資源界線形同虛設。
2. **死後可讀**：`state.json` 的 `pc` 與把手是 S-01 意義下 `cat` 得懂的位置；Python 程序死了只剩 out.log。
3. **跑前可查**：步驟表是資料，檢查器不用執行就能擋「等常駐任務結束」「重試非冪等步」；Python 要跑了才知道。

三件都用不到的工作，就寫 Python——這層不該搶它。lang-fable §7 的「現在不做、三個訊號出現再做」維持；本輪只把「值得存在的理由」從「LLM 寫 Python 會錯」換成上面三條，**第一條與 LLM 無關**（原則 5）。【中】

**直譯器自己違反了 1.1 的規則。** 子任務結束是**事件**（exit.json、last-round 的 `ended`），但兩者都是只留最新的暫存器（spec §5.1：報完再留一回合就刪槽；§3：last-round 覆寫）。一個忙過一回合的直譯器就會漏。修法不在核心：**讓子任務把結果寫成槽外的位準**（`<job>/result.json`，帶 run id；W7 本來就要求交付物在槽外），直譯器讀位準，任何速率都安全；exit.json 退為「結果檔不在時的旁證」。結果檔也不在、槽也沒了＝Unknown，照契約（耐性到了走 Absent 分支或升級給人）。這跟 astra「由任務包在槽外保存帶請求身分的業務結果」是同一件事。【高】

## 3. 第四輪漏掉、題目裡有的角度

### 3.1 使用者原話「被任務拖慢 ticktock」——在 proto7-2 裡它多半不是任務

對著 spec §2.1 查，回合變慢的真實來源只有這幾個，而且**都讀得到**：

| 來源 | 機制 | 哪裡看 |
|---|---|---|
| 有人 pause | owner 清單非空就不開回合 | status `paused_by`、`pause_pending`、`steps_left` |
| tick／tock 失敗退避 | 退出碼 3 或失敗 → 0.5～8 秒退避，**而且不算回合**；A3 停點等人 | status `last_error`、`round_open: null`、`recovery_pending` |
| tock 自己的工作 | 掃槽、/proc、不理 SIGTERM 的任務各拖 1 秒 | r2 的 C4 `timing`（還沒做） |
| 機器超載 | 每個動作一個程序，U > 1 排隊爆開（r2） | 同上 |
| interval 本來就大 | 設定 | `timeline.json` |

**任務在回合裡跑多久，不會把回合拉長過 interval**：`early_tock: false` 時回合固定等滿 interval（使用者 user-advice 要的「固定節拍」已是選項）；`true` 時任務只能把回合**縮短**；跑過一回合的 `each` 只會 `skipped: busy`。所以「下午兩點才第 5 回合」的 node，幾乎一定是被 pause、卡在 error 等人、或機器被壓垮——三種裡兩種是**有人決定的控制事件**，第三種是 r2 早就點名的量測缺口。這把第四輪「控制事件回來源讀」從原則變成一張可對的清單；也讓「等慢 node」的第一步變成**先讀它的 status，再決定要不要等**。【高】

### 3.2 語言層對非 agent／LLM 用途的意義（原則 5）

步驟表的原型是 IEC 61131 的 SFC，發明它的人是為了給**不寫程式的操作員**看懂、改得動的順序控制。aos 上同樣形狀的非 LLM 工作：備份（dump → 驗證 → 輪替 → 通知，輪替不冪等所以不准無腦重試）、ETL 批次、CI（build → test → 部署，部署前要 gate）、感測→判斷→致動的 PLC 式控制、定期報表。1.7 的三件價值對它們全部成立；九軸檢查的「retry 只包冪等步」是運維最老的規矩；9b 的「隨機但可預測」首先是感測器雜訊與網路延遲，LLM 只是最新的一例——這跟使用者「有時隨機性在可預料範圍內」的直覺一致。**LLM 只是多一種作者**，不是這層存在的理由。【中偏高】

### 3.3 「多任務代表多執行緒」

使用者的對應是對的，第四輪的 async/await 說法沒有否定它，只是少講一層：**執行緒＝槽（`max_live`），協程＝一支步驟表**。一支步驟表內的 await 是協程切換（不需要並行）；扇出是編譯器多開幾個 once 項、多占幾個槽。兩個對應各管一層。【高】

### 3.4 pause 底下的耐性

pause 只停新回合（spec §2.4），所以以自己回合計的耐性在 pause 時**凍住**。對 token 類預算這是對的（r1 Fable），對牆鐘期限是錯的——這正是 r3「期限類不換算、回來源讀」的另一個理由，也是 2 節那個「pause 自己等 wake」洞的根源。【高】

## 4. 骨架：一頁以內

**六句話：**

1. 回合是 node 自己的計數器，沒有別人的現在；跨 node 對齊的是**依據版本**，不是回合。回合變慢的原因都寫在 status 裡，先讀再等。
2. 跨 node 傳的東西只有**位準、事件、控制**三類；輸入契約宣告吃哪一類（位準／事件／窗口），窗口＝轉接器替你吃事件後給的位準。核心只保證位準與握手；事件通道是包契約，要說保留期、誰付。
3. 每一次等待有**兩個鐘**（效期：來源的；耐性：自己的，pause 時會凍住）與**三個階段**（觀察／准入／提交）；能動手的地方由入口核對，程式只收**回條**；沒有入口的縫寫成 `audit`。
4. 語言層的產物＝`tasks.json`（放置）＋步驟表（控制流）＋框架 `state.json`（`pc`、區域變數、對外責任的**把手**）＋契約（九軸＋時間契約）；責任本體住在發它的包那裡。前端任意，比產物。
5. 九軸是每一步的簽名；工具只做**保守檢查**（沒宣告＝未知＝不替它重試、平行、替換）。第 9 軸拆成「能不能重做」（幾率性）與「能不能機械把關」（可預測性；相對於觀察者，只留定義）。
6. 對 daemon／tick-tock：**零新增**。

**一張表（落地時對著它查）：**

| 軸 | 流速不同時它變成的問題 | 步驟表／契約裡的對應物 | 誰在哪裡查 |
|---|---|---|---|
| 1 I/O | 慢讀快漏版本、快讀慢讀重複；窗口要有人算 | `flow: level／event／window`（加格式、單位） | 編譯期：event 不准接 latest；window 要指定轉接器 |
| 2 生命週期 | 等的是「結束」還是「就緒」 | await 對象的型別 finite／service | 編譯期 |
| 3 跨呼叫狀態 | 換 run、換槽後怎麼接 | 框架：`pc`、變數、把手；釘 `slot` | 編譯期釘槽；執行期讀框架 |
| 4 資源 | 慢消費者要人保管；流速是回合槽的供給率 | reserve→step→settle 括號；通道保留契約 | 入口（帳、gateway）動手時核對 |
| 5 可中斷性 | pause 停回合不停任務與外部；逾時≠對方沒做 | safe／resumable；逾時後留下什麼 | 編譯期（自動重起要 safe）＋事後對帳 |
| 6 執行保證 | 重試會不會做兩次 | retry 只包冪等步或「查回條→決定」 | 編譯期＋入口去重 |
| 7 組合 | 多跳不重新計齡；模糊步 ≤ 1 | 鏈帶 `basis`；數 fuzzy | 編譯期數；執行期帶依據 |
| 8 環境／時間 | 時鐘域不能相加；期限回來源；估計另一型 | `round@<線>` 單位；`estimate` 型；時間契約（讀取規則、基準、反應、缺口） | 編譯期型別；支用時入口 |
| 9a 幾率性 | 重跑是「再試」還是「再抽」 | deterministic／stochastic | 編譯期：確定步失敗不重跑、隨機步不當重試 |
| 9b 可預測性 | 誰有資格把關 | bounded（有 schema／界）／unbounded；觀察者相對 | 有界插驗證器；無界要另一主體。只留定義 |

## 5. 這一輪改變了什麼看法（相對第四輪）

1. **CDC 借分類不借保證。** 核心只有位準與握手；事件通道是包契約；窗口不是第三種原語，是轉接器算出來的位準。而且第四輪提的步驟直譯器自己就在用暫存器讀事件——修法是子任務把結果寫成槽外位準，不是改核心。
2. **「被任務拖慢 ticktock」在 proto7-2 多半是誤診。** 任務拉不長回合（固定節拍模式）或只能縮短（early_tock）；真的慢是 pause、tick／tock 退避（不算回合）、tock 自身成本、機器超載，而且全部在 status 裡讀得到。「不知道」的範圍比第四輪說的小得多。
3. **語言層幾個「大」說法都降級、幾個「張力」都消掉。** 流速不是新資源（旋鈕是 r1 的三種既有使用權）；框架小是因為只放把手，責任住在擁有者那裡；效果入口就是 r1 的強制點，期限是回條不是值；編舞只是部署模板；這層的價值換成「子工作對核心可見、死後可讀、跑前可查」三條，第一條與 LLM 無關。

## 6. 仍然最不確定的

1. **直譯器當純位準讀者能不能守住核心零新增。** 子任務被殺在寫結果檔之前，只剩會消失的 exit.json；直譯器最後只能得到一個解不開的 Unknown，靠耐性收場。這在邏輯上成立，但真實工單裡「永遠 Unknown 的子步驟」會不會多到逼人回頭要「once 結束保留 N 回合」，沒驗過。【低】
2. **輸入契約能不能在不先知道消費端「必要區分」的情況下宣告。** 位準／事件／窗口三分很乾淨，但要選哪一種，仍得先回答 r3 那題「這個 node 絕不能混淆哪兩段歷程」；astra 第四輪的疑慮沒消。【中偏低】
3. **語言層的價值有順序依賴。** 三條價值裡最強的「子工作對核心可見」要等 r1 的資源界線真的在入口被執行才值錢；在那之前它只剩可讀與可查兩條，可能不夠讓人離開 Python。這層是不是該排在資源包之後，而不是之前，現在看不出來。【中】
