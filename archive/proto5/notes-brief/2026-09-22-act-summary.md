# `act` 怎麼跑工具：精簡總結與待拍板（2026-09-22）（精簡版）
完整版：[../notes/2026-09-22-investigations/2026-09-22-act-summary.md](../notes/2026-09-22-investigations/2026-09-22-act-summary.md)

## 結論

Claude 建議第一版保留同步工具 A，再加 tool cpu 的 B：**短工具直接跑，需搬出去的工具交背景工作者，結果仍以真正的 tool 訊息接回。**先不做 agent 內 thread pool；收據式 async 留給明確的長工作。以下是建議，決策仍由使用者做；工具期限也要配合今天的逾時總結一起看。

## 先分清三個問題

| 問題 | 現況 | 另一種選擇 |
|---|---|---|
| 工具在哪裡跑？ | agent 開子進程 | 另一顆 cpu 的 worker |
| agent 占不占著這顆 cpu 等？ | 留在本次呼叫裡等 | 存檔、退 101，下次再接結果 |
| 模型收到什麼？ | 真工具結果，作 tool 訊息 | 先收接單收據，完成後再來 user 訊息 |

tool_calls 契約要求每個 call 有同 id 的 tool 訊息配對，沒有要求工具同步跑。晚點補齊結果也可以。因此，**B「交 tool cpu、最後回真結果」與 D「立即回收據、完成走 input」是兩種對話行為**，可以共用同一個背景執行器。

## 歷代事實與教訓

| 版本 | 怎麼跑、留下什麼限制 |
|---|---|
| proto2 | 普通工具在 act 同步串行；jobs.run_long 立刻回收據，完成後 hook 注入 user；think／branch 也用收據。背景工作之外，「結果到→叫醒→繼續」必須完整。 |
| proto3 系 | 總結將其概括為記憶體原型，重點是 request id＋wait-for，未形成完整實用工具層；原調查另區分 3-2 已能同步呼叫 Janet 工具函式。 |
| proto4-2／4-3 | cpu 是常駐 aos-run，一次等一個 child；quantum 算完成次數，不算秒。kernel 沒用 running 擋換人，同一行程可能跨 cpu 重疊；這是靜態推論。 |
| proto4-5 | LLM 排程器派出背景 worker 後返回，kernel tick 才短；module 機制本身沒有非阻塞保證。 |
| proto4-6 | wait_for 宣告等檔，後續檔未到回 101，到檔則同次繼續下一格；沒有等待逾時。 |
| proto4-7 | act 同步串行，每工具 60 秒、輸出截 8000 字元；只有 LLM 分 ask／wait。 |
| proto5 現在 | act 同步串行、不限時、不截輸出。自癒救得了「記憶已寫、state 未寫」，救不了「工具已做、記憶未寫」，後者可能整批重跑、副作用重複。 |

歷代普通工具同步等是常態；長工作則已有搬到外部的先例。沒有任何一代定過「每格最多阻塞幾毫秒」，不能把同步現況當成所有長工作都該占住共享 cpu 的決定。

## 五個方案與 Claude 的看法

| 方案 | 怎麼運作、取捨 | 原作者建議 |
|---|---|---|
| A：一格同步跑完 | 狀態少、好理解；整批耗時相加、占住 cpu，一支不回就卡住。 | 預設保留，加每工具逾時。 |
| B：tool cpu，仍回 tool 真結果 | act 寫請求、往 waits 加結果檔、退 101；門開後按序接 tool，再 think。 | 要做這個，與 llm cpu 共用請求／結果／waits 協議。 |
| C：agent 內 thread／pool | 獨立工具可從耗時相加變接近最慢者；agent 若還等 join，aos-run 仍在等它。跨格存活就接近 B。 | 不做，因為它沒有解決讓出 cpu。 |
| D：收據加完成 input | 模型能先回話；但改變對話語意，需要 job id，而且 input 只在 idle 收會延後。 | 之後給明確標 async 的長工作，例如服務或長 job。 |
| E：工具各自標模式 | 每個工具選 A／B／D。 | 最終形態；第一版只做 A＋B，避免一次承擔全部複雜度。 |

## 具體建議與理由

| 建議 | 怎麼做、為什麼 |
|---|---|
| 1．短工具預設同步 | ls、cat、算數等保留 A；每工具加 60 秒期限，避免單支永久卡住。 |
| 2．B 與 llm cpu 共用協議 | 都是「提交工作、稍後拿結果」：請求 id＋payload、queued/running/done、結果檔、waits。LLM payload 是 engine＋body；工具是 inst＋arguments＋agent 資料夾。think 與 act 的提交動作相同，回來分別接 assistant 或 tool。 |
| 3．允許 agent 自己加 waits | think 提交、act 提交、連敗暫停都需要；因此要推翻目前「只劃不加」。 |
| 4．同批多 call 先串行 | 保留固定順序，並行等有需要再做。 |
| 5．結果不明不自動重試 | worker 死了可能已完成副作用；回「結果不明」tool 給模型，避免盲目重做。 |
| 6．模式放工具頂層私有欄位 | `_run: "sync"` 為預設，另有 `"cpu"`；`"async"` 以後加。底線開頭本來就不送模型，適合放執行策略。 |
| 7．交給 worker 的 inst 先解好 | 在 agent 端用 load_obj 解析 `$env` 與路徑，以 agent 為中心；送原始 `_meta` 會誤用 worker 的環境。 |
| 8．kernel 保證同一行程不並跑 | 舊版可能在兩顆 cpu 重疊；kernel 規範要補保障，才能守住 agent 同資料夾不並跑的前提。 |

## 要使用者拍板的六題

| 題號／問題 | 選項 | Claude 建議與理由 |
|---|---|---|
| 1．慢工具沒回來，模型等不等？ | A：等真結果，也就是 B 執行方案。B：先收收據，也就是 D 執行方案。 | 建議 A 為主：維持真結果配對的對話語意。D 留給明確標 async 的長工作，接受後續通知與喚醒管理。 |
| 2．預設工具模式？ | A：同步，工具檔標 `_run: "cpu"` 才丟出去。B：一律丟 tool cpu。 | 建議 A：短工具保留最少狀態的直接路徑，需搬出去者才使用背景協議。 |
| 3．tool cpu 與 llm cpu 共不共用協議？ | A：同一套請求／結果／waits，payload 不同。B：各做各的。 | 建議 A：兩者都是提交後稍後拿結果，差別留在工作內容與結果如何接回對話。 |
| 4．aos-agent 能不能自己加 waits？ | A：可以。B：不行，tool cpu 等待就得另存 pending。 | 建議 A：think、act 提交及連敗暫停都有需要，直接使用既有等待入口。 |
| 5．同一 assistant 的多個 call 怎麼跑？ | A：串行。B：並行。 | 建議 A：先保留固定順序，並行等有需要再說。 |
| 6．執行結果不明怎麼辦？ | A：回「結果不明」tool，不重試。B：自動重試。 | 建議 A：工作者失聯不代表副作用沒發生，自動重送可能做第二次。 |
