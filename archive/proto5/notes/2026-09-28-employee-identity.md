# 正式員工、Linux 身分與固定 tick worker

← [筆記索引](README.md)｜前文：[從人的角度理解架構](2026-09-28-human-architecture.md)｜[使用建議](../advice.md)

這是 2026-09-28 使用者提出的架構方向紀錄，尚未實作，也不是現行規範。目的在於沿用 Linux 的使用者與權限體系，避免在 access 裡重新建造一套相同的東西。

同日後續先放下正式員工／工具的分類，以一 agent 一 Linux 使用者討論資源，並重新考慮是否需要 CPU worker。見[資源與任務排程紀錄](2026-09-28-linux-resources-and-task-scheduling.md)；下文保留先前方向的演進脈絡。

## 使用者確定的分類

**正式員工 agent 有自己的 Linux 使用者身分，而且只有正式員工享有固定 CPU worker，專門負責該員工的 tick。其他全都是工具，也就是外包人員。**

是否使用 LLM、是否能思考或執行多步任務，不是正式員工與工具的分界。工具內部即使是一個能自主完成任務的 agent，在這個分類裡仍然是外包。

這裡的 CPU 是 proto5 的 worker 執行程序，不是獨占實體 CPU 核心。固定的是員工與 tick worker 的負責關係；worker 程序重啟、PID 改變後，仍應由替代的 worker 負責同一名員工。這是對「固定」的語意說明，故障恢復的具體接線尚未設計。

因此，「建立正式員工」涉及獨立身分與固定 tick worker 的配置；「呼叫外包」則是呼叫工具。兩者的生命週期與資源承諾不同，不能把原先的產子 agent 一概當成同一種操作。

## root daemon 與部署邊界

討論最初採用完整 Linux 虛擬機作為隔離邊界，在虛擬機裡以 sudo 啟動 daemon。daemon 具有管理程序與切換執行身分所需的權限，員工工作則使用各自的普通 Linux 身分。使用者認為這比安排無特權 daemon 的身分切換機制直觀。

接著使用者提出新的探索問題：如果願意承擔風險，是否可以直接在宿主機以 sudo 啟動 daemon，而不使用虛擬機？因此，**VM 或宿主機部署尚未最終選定**；本紀錄不把 VM 寫成不可變更的要求，也不把探索問題視為執行 sudo daemon 的授權。

架構上可以直接在宿主機運行 root daemon；VM 是可選的部署隔離層，不是正式員工制度的必要條件。拿掉 VM 後，root daemon 的權限與失誤影響範圍就直接落在宿主機。

現行程式還沒有上述切換 Linux 使用者的實作。直接用 sudo 啟動現有 daemon，不會自動讓工具以員工身分降權執行；root daemon 與普通使用者工作程序的分工需要另外實作。

## 尚未定義的細節

外包是否使用共用 pool、LLM 與工具工作的派工方式仍未決定；通常權限身分已由下述追加決定確定。「員工專屬 worker 負責 tick」不代表員工所有工具與 LLM 工作都必須由該 worker 執行。

access 最後保留哪些設定、Linux group／ACL 如何接入、帳號與 worker 如何建立及回收，也未在本輪訂成規格。這些留作後續設計背景，不在此補成使用者未選定的方案。

先前 [daemon 拆分審查](2026-09-24-daemon-split-review/README.md) 中「daemon 永不 root」的建議屬於當時的審查脈絡；本輪使用者提出 root daemon 的方向，閱讀時應區分歷史建議與新的使用者意圖。

## 同日追加決定：工具代表委託員工行事

使用者明確決定：**通常工具繼承委託員工的權限，包括工具內部呼叫 LLM、再呼叫其他工具。員工是 Linux UID／group／DAC 的權限單位。** 工具出錯可能影響該員工權限範圍內的資料，這是採用的語意；不再要求每個工具與委託員工另外隔離。

因此，新架構不需要逐工具 bwrap。每工具 mount、權限 group、`_jail` 都不再是此架構的必要設定；共享權限交給 Linux group／ACL。cwd 是執行起點，不是可存取範圍的邊界。

**外層隔離仍保留，包住整套 aos／daemon 以保護宿主。** 取消逐工具隔離不等於取消外牆；外牆的具體部署機制仍依前述調查選擇。

這是新架構決定，現行 bwrap 尚未移除。員工身分、委託權限傳遞與外層隔離需要一起落地遷移，不能直接把現版 `_jail` 關掉就當作完成。
