**實際跑了什麼**

README 從頭到尾：

1. PATH、daemon：通過。只把 `W` 換成指定工作區下的 `quick`；另設 `PYTHONDONTWRITEBYTECODE=1`，避免執行時在 repo 產生快取。
2. kernel：`init → check → boot` 通過，檢查全為 `ok`。
3. 一次性／反覆工作：通過。`once.out` 有日期；`count` 顯示 `done、runs 3`。README 有先解釋回音不含 stdout、CLI 成功不代表工作成功，這兩點很有用。
4. agent：通過。人格、工具、登記及原子投檔照範例操作，模型確實呼叫 `date`，最後以繁體中文回答時間，輸入搬進 `done/`。
5. 停機：通過。agent、kernel、daemon 依序回報 `stopped`。

第二套只依規範另建 `spec-run`，手写 kernel 設定，兩顆一般 CPU、一顆共用 llm CPU。手建家的目錄問題修好後，近乎同時投給 alpha、beta：兩者分別只拿到 `alpha_code`、`beta_code`，實際工具結果為 `ALPHA-731`、`BETA-926`，都回到 idle，記憶沒有混入另一方的結果。共享模型會排隊，第一次查看時一方已有 tool call、另一方還沒有 assistant 訊息，稍後均完成。

自製 `write_text` 工具：Python 從 stdin 讀 JSON arguments，將 `text` 寫入 agent 家的 `result.txt`，stdout 回傳 JSON。模型實際呼叫成功；核對檔案內容為「繁體中文工具接線成功 WRITE-482」。

故障與修復：

- **info.json 缺欄位**：缺 `_metainfo` 回 `MetainfoInvalid`，缺 `llm.model` 回 `LlmInvalid: llm 缺了 model`。補回後 tick 正常。另在排程中移除 model，十次失敗後成為 `bad`；修檔仍維持 bad，按文件 stop/start 後恢復。
- **工具檔壞掉**：非法 JSON 指出完整檔名與行列；缺 `_meta` 則指出檔名、第 0 個元素與格式要求。修回後正常。
- **endpoint 指錯**：改成 localhost 的未服務埠。`check` 仍全綠；執行時顯示 `EngineFailed`、`Connection refused`，三次後附上完整 `touch … 繼續` 指令。修 endpoint、touch 後得到回話。
- **模型逾時極短**：HTTP timeout 設 1 ms，日誌明確寫「HTTP 等了 1 ms 仍未完成」。三次後暫停；恢復 180000 ms 並 touch，成功回答。
- **tick 中途 kill -9**：kernel tick 被殺後，序號由 534 繼續到 548。另在 agent 收輸入、`intake` 已落盤時硬殺；重跑 tick 後一萬則測試訊息完整接回，數量與唯一數皆一萬。
- **daemon kill -9 後重開**：在 beta 模型工作在途時硬殺。新 daemon 孩子表為空；依文件重新 boot kernel，beta 接著完成工具呼叫與回話，恢復測試的 user 訊息僅一份。

以上故障均靠文件與錯誤訊息修回；硬殺結果是這次實測窗口的觀察，不代表窮盡所有崩潰時機。
