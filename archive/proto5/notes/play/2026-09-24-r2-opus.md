# proto5 試玩 r2（Opus，新使用者）

只從 `proto5/README.md` 進，讀了 README、agent.md、aos-agent.md、aos-llm-call.md，kernel.md §6、daemon.md §6 只查了需要的段落。沒讀 notes／backlog。
工作目錄在 scratchpad `play2-opus/`（s1＝照 README 走；s2＝照規範自己架＋故意弄壞＋寫工具）。最後 pgrep 是空的。

## 做了什麼、結果

1. **README 十分鐘上手**：五段照抄全過，一個字都沒補。agent 大約 10 秒回「現在是…11 點 55 分」，三個 stop 都印了 stopped。
2. **照規範自己架**：一顆 llm cpu（取名 `L`）、alice 配 `host`（uname -n）、carol 配 `count`（python 讀 stdin 的 arguments）。兩邊同時投輸入，約 16 秒都走完 idle→think→act→think→idle，記憶互不混。
3. **故意弄壞**：
   - info.json 拿掉 `llm`：agent.err 印 `LlmInvalid: info.json 缺了 llm`，看得懂；修好後 fails 自己歸 0。放著不管約 45 秒後變 `bad`，`ls` 那行附了 agent.err 的路徑；照 aos-agent.md §11 先 stop 再 start 就好了。
   - 工具檔寫壞：`JsonSyntax: <絕對路徑> 不是合法 JSON…`，很清楚。
   - endpoint 指錯：`EngineFailed: … Connection refused`，連敗 3 次後 stuck，訊息直接給了要 touch 的檔名；修好 llm.json、touch 那個檔，就接回來了。
   - 逾時：內圈（llm.json 設 300ms）顯示 `Timeout: HTTP 等了 300 ms`，清楚。外圈（info 設 30ms）顯示 `逾時（30 ms）`，但後面附的 llm.err「最後一行」是幾分鐘前留下的 Connection refused，會誤導人。
   - tick 中途 `kill -9`：10 秒內殺了 81 次 aos-agent tick 和 kernel tick，輸入沒丟也沒重複接，最後正確答 7。kill -9 llm cpu：顯示「結果不明（Interrupted）」、自動重問，最後答對。
   - daemon `kill -9` 後重開：所有 cpu 都跟著死了。重開 daemon 後 `ls` 顯示 cpu `missing`，`check` 卻全部 ok。在 kernel.md §6 裡找到一行「daemon 重啟過也要 boot」，boot 一次就恢復了。
4. **自己寫工具** `write_note`（python 腳本，讀 stdin 的 `{name,text}` 寫進 `notes/`）：第一次就成功，模型寫了一首秋天的詩到 autumn.txt。拿掉執行位之後，check 會報 bad；模型拿到的是「exit 126：不能執行 argv[0]=… 相對 cwd …」，很好懂。

## 五條打分

- **容易上手：4**。README 照抄零失誤，check 的 ok/warn/bad 很友善。扣一分是因為 README 之後就只剩規範可以讀，缺一篇「自己架第二個 agent、自己寫工具」的短範例；規範裡的例子都埋在很多細節中間。
- **容易理解：3**。「一個資料夾就是一個 agent、工具就是 OpenAI tools 加一格 `_meta`」這個核心很好懂。但 agent.md 和 aos-agent.md 一半以上在講崩潰恢復（intake／consuming／sweep／base_len／消費 id），新手要自己分出「哪些我要管、哪些不用管」。規範標頭還一直連到 notes 的審查報告。
- **複雜的東西藏好了：3**。崩潰安全藏得非常好，kill -9 怎麼殺都沒事。但有兩個狀態會漏出來、又看不見：「卡住等 continue」和「daemon 重開後 cpu missing」。
- **外層控制結構簡單但全面：4**。init／check／boot／add／ls／stop 加上 agent 的 start／stop／last 已經夠用。缺的是看 agent 狀態（有沒有卡住、在等什麼）和 continue。
- **要背的東西少：3**。要記的有：PATH 要在開 daemon 之前設、AOS_K、停機順序、daemon 重開後要再 boot、continue 檔名要從 log 抄、兩個逾時設在兩個檔、bad 之後要 stop 再 start。

## 卡住的地方

1. **aos-agent 卡住看不出來**（aos-agent.md §9、§1 `last`）。我以為 carol 早就走完了，其實它在先前的內圈逾時測試裡已經連敗 3 次、在等 continue。`last` 還是印舊的回話，`ls` 顯示 `running fails 0`，新投的 input.json 就默默放著沒人收。我是事後翻 agent.err 才發現，大約浪費了 5 分鐘。
2. **daemon kill -9 重開後**（README 沒寫；kernel.md §6 只有一句）。我以為 daemon 會自己把 cpu 拉回來，實際上要手動 `aos-kernel boot`。`check` 全部 ok，`ls` 的 `missing` 也沒提示下一步該做什麼。
3. **外圈逾時的訊息附了舊的 llm.err 最後一行**（aos-agent.md §6.1）。我以為是連不上模型，其實是 info.llm.timeout_ms 太小，這一次 llm.err 根本沒寫新東西。訊息也沒說 30 ms 是哪一格設定。
4. **`check --agent` 只吃一個**（kernel.md §6）。我以為可以一次查兩個 agent，結果寫兩次 `--agent` 只查了最後一個，也沒有任何提示。
5. **Connection refused 沒寫連的是哪裡**（aos-llm-call.md §5）。我以為會附 endpoint，實際沒附，要自己想到去看 llm.json。
6. **`aos-agent last` 在 info.json 壞掉時也跑不了**。我以為 last 只讀記憶，實際上它先讀驗 info，壞了就退 1。

## 改了會更順的清單（照痛度排）

1. 給 `aos-agent` 加一個狀態指令（例如 `status`），印出 state、errors、在等哪個門（附完整 touch 指令）、有沒有還沒收的 input；`last` 在卡住時也附一行警告。
2. daemon 重開後，`check`／`ls` 要能看出 cpu `missing`，並提示「執行 aos-kernel boot」；README 第 5 段後面補一句「daemon 掛了：重開 daemon 再 boot」。
3. 外圈逾時的訊息不要附舊的 llm.err 最後一行（或註明那一行的時間），並寫明是 `info.llm.timeout_ms` 那一格。
4. `aos-agent continue [dir]`：自己找出 continue 檔並 touch，不用從 log 抄那串長檔名。
5. EngineFailed 附上 endpoint 和模型代號。
6. `check --agent` 可以重複寫；或者寫第二次時直接報用法錯。
7. README 加第 6 段「自己寫一支工具」（stdin 收 arguments、stdout 回結果、相對路徑從 agent 家算、要有執行位），我這次照 agent.md §3.3 就寫成了，值得放到門口。
8. agent.md、aos-agent.md 開頭先放一節「使用者只需要懂的」（info 各格、工具格式、四種退出／卡住／恢復的做法），崩潰恢復的機制移到後面或附錄。
9. 規範標頭與 README「程式」那節不要連到 notes 的審查報告（新手會點進去）。
10. `aos-agent last` 讀不了 info 時，退回去讀 `prompts/history.json`。
11. `aos-agent stop` 在沒設 AOS_K 時，拿 tick.json 裡記的 K 來用（它本來就記著）。
12. `aos-agent --help` 補上每個子命令一句話的說明（aos-kernel 有，agent 沒有）。

## 你會不會想用它

會。照抄就跑得起來、怎麼 kill 都不會壞、加工具只要寫一個小腳本，這三點很吸引我；補上「看 agent 卡在哪」和「daemon 重開要 boot」這兩個缺口，我就願意拿它來跑日常的小代理。
