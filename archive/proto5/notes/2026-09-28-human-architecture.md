# 從人類理解與修改的角度看 proto5

← [筆記索引](README.md)｜[proto5](../README.md)｜[程式導航](../lib/README.md)

2026-09-28 與使用者討論的閱讀筆記，收錄整體架構、概念拆分，以及程序管理、交接與恢復的進一步說明。這是理解現行系統的導讀，不是新的實作規格或搬檔方案；具體行為仍以程式為準。

## 為什麼重新拆概念

程式能正確運作，與人能掌握、修改它，是不同要求。測試主要驗前者，後者需要從人的操作方式檢查：設定直覺上應在哪裡、改一件事要碰幾個地方、哪些細節想控制、哪些不想知道、隔一個月還能否猜出名稱的意思。

按程式責任拆成很多小檔，不一定降低閱讀成本；一件事可能反而要跳更多地方才看得完整。「功能都提供了」不能當成易用性已完成。常見操作需要人記多少概念、改多少地方，也應視為成本。使用者覺得難懂時，除了補解釋，也要檢查介面與結構是否讓人多費力。

使用者目前希望先理解單 agent，父子 agent 試用暫緩。

## 第一層：五個人能獨立理解的大概念

### 1. Agent 本身：我是誰，怎麼做事

人格、工作原則、回答方式、模型與身分。人的操作意圖是「換模型」「改成程式助理」「回答詳細一點」。目前主要落在 `info.json` 與 `prompts/system.json`。

### 2. 記憶：經歷過什麼，要留下什麼

當前對話、歷史封存、長期筆記，以及壓縮、忘記與找回資訊。人的操作意圖是「這個任務重新開始」「記住這個習慣」「找昨天的結論」。目前分布在 `prompts/history.json`、壓縮封存與 notes 工具。人格與記憶都會送給模型，但修改意圖不同。

### 3. 能力：有哪些事可以做

工具及其製作、測試、安裝、移除登記、別名與篩選。人的操作意圖是「給它算表格的能力」「拿掉 bash」「把函式變工具」。目前是 `tools/` 與 `info.json` 的工具登記。能力分組與 `--without` 等新建議尚未實作，見 [advice](../advice.md)。

### 4. 工作環境與權限：在哪裡做，能碰什麼

cwd、掛載、讀寫權限、網路與沙盒。人的操作意圖是「處理這個專案」「這份資料只能看」。目前主要是 `access.json`：cwd 只是起點，其他掛載仍可達。有 write 工具不代表任何地方都能寫。

agent 預設 cwd 沙盒、共享權限 group、個別工具例外是使用者提出的後續方向，完整優先序尚未定案，不當成現行功能。

### 5. 執行底座：讓事情確實跑起來

工作單、執行器、排程、程序生死、交接與恢復。日常介面應先回答：如何開關、同時能做多少、在跑或在等、哪裡壞了與怎麼恢復。tick、batch、ack 等細節在排查或改底層時才展開。

「說話、查看、修改」是橫跨五塊的人用介面。整理時可問：明明只想修改一塊，為什麼還得理解另外三塊？這些交界就是可理解性與可修改性的檢查點。

## 現行程式與資料的地圖

proto5 是獨立的 Python 原型，不進 CMake，也不靠 C++ core 執行。`cli/` 是薄入口，`lib/` 才是功能本體；`tools/` 是模型可呼叫的工具包，`templates/` 是成員模板，`spec/` 是規範，`tutorials/` 是教程，`examples/` 是示範，`lib/test/` 是測試。

`aos-agent` 入口先進 agent 模組，再由 CLI 分派到 say、listen、tools 等實作。agent 執行核心是 `idle → think → act → think`：idle 收輸入，think 問模型，若模型要工具則 act，工具結果再送模型；模型最後回答後回 idle。

daemon 與 cpu 常駐；kernel 和 agent 每次 tick 推進一段、存進度後退出。cpu 是工作程序，不是硬體核心，很多 agent 可以輪流使用同一個池。default 池通常跑 agent tick 與工具，llm 池跑 `aos-llm call`；兩者的 cpu 實作相同，工作與環境不同。

`aos-llm call` 只問模型一次，不跑工具、不掌握整個 agent 迴圈，也不直接修改 agent 記憶。工具由 agent 建工作批次，依 access 快照包成 `aos-jail` 執行，再交 kernel 排程。

執行資料分家保存：daemon 家放池宣告、程序資料與 kernel tick 登記；kernel 家放池設定、請求／回音與 `ledger.sqlite`；cpu 家放工作與結果；agent 家放人格、記憶、工具、權限、輸入與狀態。使用者此次實際位置是 `/tmp/haha/daemon`、`kernel`、`agent1`，工作區是 `/tmp/haha/proj`。

team、company、market 是往上加的協作層，仍用相同底座。理解單 agent 時可先略過。

## 第二層：把執行底座再拆五件事

### 1. 工作單：描述要做什麼

描述程式、argv、cwd、環境、輸入輸出與執行逾時，不決定何時開始。對應 inst 格式與 `aos_inst`。

### 2. 執行器：把程式跑一次

啟動程式、接串流、等待、處理逾時／停止、回報退出碼與耗時。對應 `aos-exec`。外面加上「等單 → 跑一次 → 回報 → 再等單」的長期迴圈，就是 `aos-cpu`。

### 3. 排程器：決定何時做、交給誰

排隊、選池、找可派 cpu、記住在途工作、收結果與决定後續。對應 kernel。agent 是一份可反覆執行的工作，沒事停車，有輸入或結果再喚醒。

### 4. 程序管理：維持接工作的人手

啟動 cpu、察覺退出、依規則重拉、增減數量、停機與啟動 kernel tick。對應 daemon。kernel 決定「哪份工作交給誰」，daemon 管「這些工作程序是否存在」。

### 5. 交接與恢復：中斷後接得回來

request／response 交件與回音、ack 簽收、帳本與狀態、鎖、原子發布與重放。這些橫跨多個角色，不是另一支常駐服務。

正常路徑：工作單 → kernel 排程 → cpu 執行 → 回結果 → kernel 記帳。daemon 維持程序；交接與恢復貫穿整段。閱讀順序先正常路徑、再失敗路徑。

tick 是「起來處理一輪、存進度、退出」的執行方式，不另算一套系統。agent 以 102 表示停車、103 表示下一步可以馬上再排。

## 深入 4：程序管理

### 宣告與現況

kernel 的池設定表達「default 要幾顆」；kernel 算出成員並向 daemon 宣告。daemon 保存池宣告，再把實際程序維持到所需狀態。這是「持續維持需求」，不只是「收到命令就開 N 個」。

每個 cpu 號碼有生命週期：pending（待啟動）、running（活著）、dead（退出待重拉）、failed（啟動失敗待重試）、killing（正在停止）。移出需求、等待收掉的屬 draining。程序還活著不代表工作成功，也不代表模型有回答。

daemon 以 `pool.json` 記宣告、`kids/<號>.json` 記 PID／代數／退出與重試資訊、`summary.json` 提供摘要。穩定編號與 OS PID 不同：default/0 可以重啟很多代、每代 PID 不同。

### 啟動不是放任孩子立即工作

daemon 建立 cpu 後，先記好管理資料，再送 go 讓它開始。若 daemon 在記帳前當掉，尚未拿到 go 的孩子會因控制管線關閉而退出，減少「已啟動卻沒有紀錄」的窗口。

### 失敗與重拉

cpu 退出由 daemon 收屍、更新狀態，若仍在池宣告裡就依規則重拉。連續失敗會退避，避免無限高速重啟。工具自己退非零，通常只是 cpu 回報一次工作失敗，不等於 cpu 死了；kernel 或 agent 再決定要不要重試。

### 減人、重啟、停機是不同意圖

正常增減池走 `aos-kernel cpu add/rm`。kernel 縮池會等被收的 cpu 手上工作完成再交給 daemon 收掉。`aos-daemon kill` 是保留宣告、把程序砍掉重來，不等於永久減少數量。直接 `aos-daemon scale` 改的是 daemon 宣告，kernel 所有的池會要求 force，因此不是日常調整入口。

一般收工用 `aos down`：先讓 kernel 完成停機流程、收在途結果、縮池，最後停掉無其他 kernel 使用的 daemon。強制停止走另一條處理路徑，不能與正常停機的等待完成混為一談。

### daemon 自己當掉

cpu 不綁 daemon 的壽命：daemon 被 KILL 後，cpu 可能還活著；這時沒人重拉 cpu，也沒人持續開新的 kernel tick。下一任 daemon 先處理上一任留下的 cpu，等它們退出後再建立新一代，避免同一個 cpu 家兩個主人。

這不是無縫續跑保證：被打斷的工作會依結果走 stopped／Interrupted 等處理，是否再試由上層決定。daemon 本身需要有人重開，例如執行 `aos up`。

## 深入 5：交接與恢復

### 一份工作有兩次交接

第一次是交工作：kernel 記帳並把 request 放進 cpu 收件匣。第二次是交結果：cpu 先發布 response，再刪原 request；kernel 收到結果、記入自己的狀態，再安排 ack。ack 表達「結果已接手」，不是工作成功與否；失敗結果也需要簽收。

發送端先完整寫好暫存內容，再原子發布，避免收件人读到半張單。kernel 查執行情況時先查 request、再查 response，配合 cpu「先回結果、再刪原單」的順序。

### 為什麼不是做完就刪光

如果 cpu 在 kernel 收到前就刪結果，kernel 會永遠等不到。保留 response 到 ack，讓消費者有機會恢復後再收；單號用來對應哪份工作的結果。

### 帳本與檔案不是同一筆交易

SQLite 可以保證帳本的一次交易完整提交或回滾，但不能讓「改帳本」和「往別的資料夾放檔案」自動成為同一筆原子操作。kernel 因此先持久化安排，再執行檔案交接；帳本裡留有待發送、待回覆、待簽收、待刪除等出貨紀錄。

若記帳後、投遞前當掉，下次補投；若投遞後、清掉出貨紀錄前當掉，下次可能重做，因此協定用穩定的工作身分與「已存在／已刪除」等判定讓特定交接動作可重做。不同窗口各有規則，不代表任意工作都會重新執行或能自動恢復。

### 鎖、原子發布、進度各管一種問題

鎖避免同時兩個執行者修改同一份狀態；原子發布避免看見半份文件；進度與帳本記住完成到哪裡；恢復程序據此決定補做什麼。日誌主要供人排查，不是可取代帳本的可靠狀態來源。

agent 也採這個思路：intake 記收訊做到哪、batch 記送出的模型／工具工作、sweep 記哪些暫存待清。故而 state.json 看起來有很多與「聊天」無關的欄位；它們服務的是程序中斷後的接續。

### 通知與證據分開

門鈴、wake、回音通知用於讓系統快點處理；真正的工作、結果與狀態仍在檔案或帳本。通知不是成果本身，系統也有定時 tick／巡檢等補充路徑，不能只憑一次通知消失就認為工作不存在。

### 系統知道什麼、不能保證什麼

若工具已對外送出郵件，但尚未把成功結果交回就崩潰，底座未必知道外部動作成功與否。重試可能重複，不重試可能漏做。這需要工具自己的去重鍵、外部查詢或人工判斷；本系統沒有對任意副作用提供 exactly-once 保證。程序退出碼為零也只能證明程式如此回報，不保證業務答案正確。

## 這輪概念拆分的範圍

單 agent 與執行底座的主要概念已涵蓋：agent 本身、記憶、能力、工作環境與權限，以及工作單、執行器、排程器、程序管理、交接與恢復。程序管理回答「做事的人還在嗎」，交接與恢復回答「事情做到哪裡，有沒有交接清楚」；程序活著但沒收到工作，與程序已退出但結果已留下，是不同情況。

往下是各塊的實作細節，例如排程公平性、逾時／取消、重試、診斷與清理，不必現在再擴成一批大概念。團隊、公司、市場屬上層協作，依使用者目前先理解單 agent 的方向暫不展開。這表示閱讀地圖大致齊全，不表示程式沒有缺陷、所有設計都已定案，或 advice／WAIT_USER 的問題都已完成。
