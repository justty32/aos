**必修**

目前不宜判定全部通過。以下以最後重讀的工作樹為準，已納入審查期間新增的 `kernel_has()` 修正。我沒有修改檔案、啟動模型或 daemon／kernel。一般測試被唯讀沙盒擋在建立暫存目錄；下述部分問題已用不落檔的記憶體模擬確認，不能當作整套測試通過。

- **M1｜郵差可被模型借用來覆寫牢外檔案。**  
  `aos_team_post.py` 的 `Post.process_file()`：`done/`、`rejected/` 位於模型可寫的 outbox，搬檔時卻直接跟隨目錄符號連結。模型把 `rejected` 換成指向其他成員家的連結，再放一個不合法的 `state.json`，郵差退件時就會以 `os.replace()` 覆蓋那個家的 `state.json`。**這不需要冒名信通過驗證。**  
  建議把封存區移到模型不可寫的位置；收件、搬檔使用固定目錄的檔案描述符並拒絕符號連結，不能只做一次 `realpath` 檢查。

- **M2｜不同團隊共用 kernel 時，工作名稱會撞。**  
  `aos_team_post.py` 的 `launch()`：每隊第一張單都可能使用 `v-t-0001-r1-a1-1`，request 也同名。第二隊可能把第一隊的 `RequestExists` 當成提交成功，之後讀／ack 第一隊的回音，自己的驗收卻沒跑。`proc_name()` 另只取資料夾末段，`/a/team`、`/b/team` 的郵差與心跳也會撞名。  
  建議所有 kernel 名稱與 request 都加入團隊的穩定唯一識別；`AlreadyExists` 必須核對工作屬於自己，不能直接視為成功。

- **M3｜另開行程的驗收仍有重交窗口，逾時重試也可能重疊執行。**  
  `aos_team_post.py` 的 `launch()`、`collect_job()`：`Popen()` 成功後、儲存 PID 前崩潰，磁碟仍是 `new`；恢復會再開一支，甚至不先收已存在的結果。逾時時也直接重交，沒有確認舊行程／kernel 工作已停止；多支共寫同一個 `result.json`。新增的 `kernel_has()` 沒補到這條路。  
  建議每次提交有獨立執行代號與結果路徑；恢復先辨識既有執行，重試前結清舊執行。直接 spawn 路徑需要可靠的啟動握手或監督程序。

- **M4｜ack 狀態跨重試沿用，且晚到回音會失去追蹤。**  
  `aos_team_post.py` 的 `launch()`、`ack_job()`、`collect_job()`：第一次失敗回音 ack 後留下 `acked=True`，重交沒有清掉。第二次結果先到、回音尚未到時，`ack_job()` 仍回 True，工作提早封存，第二次回音沒人收。另有「結果收完等十分鐘」或重試耗盡後直接封存的路徑，晚到回音同樣被遺漏。記憶體模擬已確認舊 `acked` 會讓新 request 被當成已簽收。  
  建議 ack 狀態綁定每個 request，保留所有在途／待簽收 request；逾時不能直接丟掉追蹤。

- **M5｜驗收結果沒有核對身分與格式。**  
  `aos_team_post.py` 的 `collect_job()`：忽略結果內的 `task/rev/attempt`，直接用 job 的數值重新貼標籤；`pass` 還用 `bool()` 轉換。模擬放入 `t-9999 rev9 attempt9` 的結果，實際送出的事件成了 `t-0001 rev1 attempt1`。正常分目錄能隔離不同 attempt，但收件本身沒有守住契約。  
  建議嚴格核對工作、rev、attempt、執行代號及逐條結果，`pass` 必須是布林；錯配與壞結果走明確失敗處理。`aos_team_verify.verify()` 也應核對目前單子版本，不能只把旗標當結果標籤。

- **M6｜刪除後重加同名例行，可能沿用舊任務而漏派。**  
  `aos_team_beat.py` 的 `Beat.request_id()`、`one()`：狀態會依新的登記 request 清空，但派工 ID 只有「名字、到期秒數、重試次數」。同名 `once` 刪掉後以相同時刻重加，即使目標／負責人已改，仍找到舊任務；舊單 done 就直接把新例行標完成。  
  建議派工與報告 ID 都包含**這次例行登記的 request**，不要只以名字代表例行身分。

- **M7｜心跳失敗通知有永久漏寄窗口。**  
  `aos_team_beat.py` 的 `check_inflight()`：先存 `handled`、清掉 `inflight`，一次性還設 `finished=True`，之後才 `report()`。中間崩潰，恢復已沒有通知待辦；一次性甚至直接略過。  
  建議先持久化「待寄失敗報告」，送完才勾掉；報告給多個收件人也要能逐件恢復。

- **M8｜表格沒填滿也能驗收通過。**  
  `aos_team_verify.py` 的 `check_table_filled()`：已用記憶體模擬確認 `[{}]`、錯誤 contract 加空 `columns` 都回「1 列 × 0 欄都填了」。Markdown 同名欄位用 `header.index()`，兩欄都讀第一欄，第二欄空白仍通過；CSV 的同名欄也會被 `DictReader` 合併。  
  建議驗證 `wf-table/1` 契約、欄名非空且唯一、至少一個受檢欄位，以及列寬；不要讓零欄檢查視為成功。

- **M9｜書記會破壞人寫的內容與 Markdown 格式。**  
  `aos_team_post.py` 的 `update_section()`：移除整節所有空白行，會把兩段文字黏成一段；任何符合 `- [t-0001 …]`／`- [q-0001 …]` 的人寫行也直接刪除。已模擬確認。標題界線只看 `startswith('#')`，也不辨識程式碼區塊。  
  建議使用明確的機械管理區塊，區塊外逐位元組保留；機械輸出的 workflow、選項等欄位也要攤成單行，避免內容插入新標題。

- **M10｜完成工作在封存前崩潰，恢復永遠不搬。**  
  `aos_team_post.py` 的 `collect_job()`：先把 `status='complete'` 寫入，再搬到 `jobs-done/`。中間崩潰後，收尾分支只接受 `collected/broken`，`complete` 工作永久留在 `jobs/`、每秒重讀。模擬已確認不會再呼叫搬移。  
  建議恢復時把 `complete` 視為「尚待封存」，冪等地完成搬移。

- **M11｜時區錯字靜默通過，夏令時間重複小時也會算錯。**  
  `aos_team_beat.py` 的 `_zone()`、`check_routine()`、`Schedule.latest()`：無效時區直接退回本機；有效的夏令時間案例也有錯。模擬紐約每日 01:30，在 2026-11-01 第二次 01:15，最近已到期應是當天第一次 01:30，程式卻算成前一天。  
  建議拒絕無效 IANA 時區，以 UTC 比較實際時刻；明定不存在／重複的當地時間如何排程並補測試。

**建議**

- **S1｜停滯判斷還不是任務本身的進展。**  
  `watch()` 在健康代碼改變時重設寬限，而且非 ok 就跳過一般停滯判斷；持續不健康但代碼輪換可能一直不報。`last_progress()` 又採整個成員的記憶／事件檔 mtime，其他任務或 compact 都能替卡住的單刷新時間；被忽略的任務事件也會更新 `updated_at`。建議另記連續不健康起點，逐步改用與任務相關的有效進展事件。

- **S2｜每秒成本與積壓要分開看。**  
  依你提供的 0.037 CPU 秒，每秒一輪約佔單核心 **3.7%**。平常每輪讀名冊、所有 `open/` 紀錄、活動 jobs、outbox、watch／clerk 狀態；不是每輪掃全部歷史 sent。每 30 秒另掃所有任務、查成員健康；書記有變時重讀任務與問題。  
  大量未收信會讓 `open/` 線性增長；outbox 全部處理完才看期限，沒有每輪額度；投遞去重還會 glob 成員累積的 `input/done/`。`mail --follow` 則每秒重讀全部歷史紀錄。建議補積壓量測、每輪處理上限與歷史查詢索引。

- **S3｜書記可能自己製造 wf-lint 失敗。**  
  所有 open 單子／問題都列在同一節，沒有超過 1 KB 的資料表轉存或 8 KB 文件拆分機制；生成行也不是導航連結，會撞 BIGLIST／OVERSIZE。應保留短摘要，詳細列表指向既有 JSON 資料。

- **S4｜驗收路徑的基本檢查可用，但保證要寫準。**  
  `inside()` 能擋靜態的越界 `..`、外部絕對路徑與外部符號連結；但它接受「指向專案內」的絕對路徑，與規範要求相對路徑不一致。`realpath` 後再開檔也仍有換連結窗口。建議明確拒絕絕對路徑，若要把牢外讀檔當安全邊界，需補不跟隨連結的開檔方式。

- **S5｜補測目前漏掉的窗口與交叉情境。**  
  現有 crash tests 沒涵蓋 spawn 後未記 PID、重試沿用 ack、完成狀態已寫但未封存、失敗報告未寄，以及多團隊共用 kernel。另 `routine import`、紀錄保留清理、模型預先自查驗收入口，與 catalog 的承諾仍有落差，應明列未完成範圍。
