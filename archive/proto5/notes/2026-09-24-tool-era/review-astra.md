**必修**

已實際讀指定來源，並核對相關實作；未改檔、未跑模型、未啟動 daemon／kernel。整體方向成立，但目前還不適合直接照任務書開工。

以下檔名均指 `proto5/notes/2026-09-24-tool-era/`。

- **M1｜`plan.md` 開頭、`catalog.md` T-wf／T-verify／T-json：第一波「沒牆也安全」不成立。**  
  base 的 `--root` 只限制部分檔案工具，bash 仍能讀寫主機其他位置、繼承環境；拋棄式專案不會縮小它的權限。`cmd_ok` 即使不經 shell，若執行工人能修改的 `p/tools/wf-lint.sh`，仍是在牢外執行工人提供的程式。`json_edit` 禁寫幾種檔名，也擋不住其他工具或自訂路徑。  
  **改法：**把無牆版本明訂為受信任環境的功能原型；正式模型驗收等牆完成。第一波驗收只執行受保護位置的固定檢查器，限制參數與路徑。信任資料依實際設定及引用關係辨識，不能只看檔名。依據：[base 邊界說明](../../tools/README.md)。

- **M2｜`catalog.md` T-post、`plan.md` 隊 2 驗收③：防重投方法會失效。**  
  「投信成功→收件人把信移進 done→郵差尚未搬 outbox 就崩潰」後，原收件檔已不在，郵差會再投一次。反過來，「搬完 outbox→記帳前崩潰」會漏掉紀錄及後續驗收。單靠 rename 或最後補一行 log 都不夠。  
  **改法：**補持久投遞紀錄、固定 message ID、收件去重憑據及各階段恢復規則；去重必須涵蓋尚未收、正在 intake、已封存三種情況，並訂憑據清理期限。測試要讓收件人在郵差崩潰窗口內真的收走信。依據：[state §4.1／4.4](../../spec/agent/state.md)。

- **M3｜`workflows-as-team.md` §2.3、`plan.md` 信件格式：投遞、順序與中途來信契約缺了一段。**  
  現行 agent **只在 idle 收輸入**；act／think 中收到的信要等整輪結束，不會在工具步驟之間看到。資料夾輸入按檔名排序；郵差的時間開頭檔名與人的 `say-…` 混在一起，不代表按時間收。`input` 也不保證固定是 `input/`。  
  **改法：**團隊模板明訂資料夾輸入；共用 `say` 的投遞解析及不覆蓋規則，避免人與郵差互蓋。明訂只保證哪種順序，以及一次可能收多封。將「改變正在做的事」另列取消／暫停協定；第一版若不支援，直接寫明延到 idle。參照：[say 規則](../../spec/aos-agent/cli-talk.md)、[idle 收件](../../spec/aos-agent/idle.md)。

- **M4｜`catalog.md` T-handoff／T-post／T-verify／T-ask：缺任務生命週期與可信的完成判定。**  
  現稿沒定誰能改任務、誰能回 DONE、審查結果怎麼對應條目、舊回報能否結束重派後的新任務。`FAILED` 在 workflows 表示「終止且不自行重試」，此處卻用來要求工人繼續修。`handoff` 已自動寄 REQUEST，領隊人格又要求另外 `team_say` 派工，可能重派。  
  **改法：**定 queued／執行／驗收／待人／終局轉移，以及任務版本、執行次數、合法回報者；寄件身分由郵差依 outbox 所屬者認定。`handoff` 一次完成建單與派送。驗收不過改成結構化驗收結果＋新的修正請求；加重試與總時間上限，避免無限返工。`judge` 應是審查子任務，只有對應版本的逐條結果齊全才完成。

- **M5｜`catalog.md` T-post／T-lock：idle 不等於卡住，更不等於資源已釋放。**  
  `assignee` 只表示被派到，不能證明已接單；idle 可能正在正常等回信或人答覆。相反地，停在 think／act、kernel 壞掉的人永遠不會符合 idle 看門條件。`stop` 也不會停止已送出的工具，直接回收鎖可能讓兩人同時使用資源。  
  **改法：**分開記派送、收件、等待對象、最後進展及健康狀態；逾時通知只報「觀察到停滯」，不冒充工人的技術判斷，且同次停滯只通知一次。鎖由持有者釋放，或確認相關工作已停止後回收。

- **M6｜`catalog.md` T-wf、`workflows-as-team.md` §2.4：只包腳本跑不起導入。**  
  `wf-init.sh` 依自身位置找 `template/`、`flavors/`，也 source 其他 shell 檔；只複製 `tools/` 不足。工人只有專案內的 read，又要讀專案外的 `IMPORT.md`，讀取入口也未接好。原腳本先寫入 `AGENTS.md`，中途失敗後重跑可能因它已存在而拒絕，並非目前宣稱的可重跑。  
  **改法：**封裝固定版本的完整必要資料樹，提供唯讀手冊入口；補導入階段紀錄或 staging／恢復流程，並驗「半途失敗後再跑」。依據：wf-init.sh（`~/repo/workflows/tools/wf-init.sh`）。

- **M7｜`workflows-as-team.md` §2.4、`plan.md` 第一波例子：Done when 引用正確，輸入與驗收防線不足。**  
  IMPORT.md（`~/repo/workflows/IMPORT.md`） 的四條確實一致；但空專案查不到分支慣例、使用者偏好等事實，原文禁止瞎填。只驗殘留為零和 lint 成功，也可能放過刪掉必要內容的結果。另外 `grep -c` 在零命中時退 1，不能直接當「退 0 才過」的 `cmd_ok`。  
  **改法：**給固定的專案事實與導入選項，包含範例區塊如何處理；增加必要產物及關鍵內容檢查。殘留用專門 predicate，區分零命中與讀檔失敗，明訂掃描範圍。此例適合驗「導入文件」，不能宣稱已驗 heartbeat 引擎或 reviewer 路徑。

- **M8｜`catalog.md` T-beat、`plan.md` 落穿例子：心跳會重派，且跟 Markdown 清單尚未接通。**  
  到期後直到 DONE 才更新日期，期間每次心跳都會再次派工。workflows 清單原本在 Markdown，T-beat 卻讀 `team/*.json`；工人照工作流修改 Markdown，機械心跳可能完全看不到。「每天九點」也不是單純每 N 天間隔。  
  **改法：**選唯一資料來源，補登記／遷移工具；每次到期有固定 occurrence ID 與 in-flight 狀態。明訂時區、每日時刻、漏跑處理、失敗重試及使用者授權來源，不能把模型新增的列自動當授權。

- **M9｜`catalog.md` T-score、`axes.md` 量法：承諾的量測資料目前不完整。**  
  `aos-llm call` 只回 `choices[0].message`，沒保留 API usage；`work/*.out` 會被清掉。assistant 則數漏算失敗請求，compact 後還會變少；輸入封存時間是收件時間，不是人投話時間。kernel 的 `ms` 是經過時間，**不是 CPU 秒**。現有資料也無法可靠拆出每任務的排隊／模型／工具時間。  
  **改法：**第一波前段就定義並記錄 task ID、批次／call ID、起訖、成敗、usage 等事件；score 最後只負責彙整。CPU／RSS 另量，無資料填 `null`。不能把新增記錄點留到最後一隊才發現要改地基。依據：[模型輸出](../../lib/aos_llm_call.py)（第 143 行）、[工作檔清理](../../spec/aos-agent/pause-clean.md)。

- **M10｜`catalog.md` T-compact、`plan.md` 隊 4 領地：壓縮方向對，但恢復與接線尚不足。**  
  持 tick 鎖且 idle／無 batch／intake 是必要條件；然而「先搬走舊 history、再寫新 history」中途崩潰，下一次可能把不存在的記憶視為空陣列。自動 compact 要改 tick 接線，隊 4 領地卻没列。保留所有舊 user 與最終回答，也不能保證記憶有上限。  
  **改法：**先複製並原子發布 archive，再原子替換 history；補恢復憑據、旗標消費及同把鎖內呼叫方式，避免再次拿鎖。明訂輪次、重複壓縮及 archive 保留政策；對未完成任務保留必要狀態，並提供第一波可用的原文取回方式。

- **M11｜`plan.md` 第二波 B、`catalog.md` T-say／T-ask／T-compact：牆接線不是改 `_meta` 就完成。**  
  [權限契約](../2026-09-24-agent-access/contract.md) 是「有 access 表就全工具關牢」，不能逐支選擇繞過。現稿又讓工具寫家內 outbox／旗標，與家及子目錄的信任資料重疊規則需要明確對齊；不能假定可寫映射必定通過。  
  **改法：**先共同定案外置 outbox／申請目錄，或明確的子目錄例外；牢外郵差讀請求後驗身分、角色、路徑及操作。`team_say`、`handoff` 本身可機械化，但「固定寫某目錄」不代表郵差代辦的所有效果都安全。

- **M12｜`plan.md` 並行領地、合併步驟：現在會撞檔，reset 還可能丟掉成果。**  
  `--template` 也要改 `aos_agent_cli.py`，與隊 4 撞；compact 自動接線、tools 開發指令也有共用入口。各隊都被要求改 README／notes 索引。`git reset` 到 main 不等於把自己的提交整合到最新 main，`--hard` 更可能清掉工作。  
  **改法：**CLI、tick 接線及共用索引指定單一整合者；先合骨架與共用契約，再平行做模組。用 rebase 或整合分支保留各隊提交後測試。等 talk 才共用 `/context`、等牆才做牢內驗收都合理，但不能只靠把隊 4 排最後避開衝突。

- **M13｜`catalog.md` T-wrap-py、`plan.md` 第二波驗收②：選的範例收不到任何函式。**  
  指定的 find_big_lists.py（`~/repo/workflows/tools/find_big_lists.py`） 中 `scan`、`main` 都沒有型別註解，按現稿規則會被跳過。「不認得型別就當 string」也會產生看似合法、實際不能呼叫的工具。  
  **改法：**換成有註解的固定 fixture，或提供人工 schema／薄 adapter。第一版明訂支援的參數形式、JSON 回傳值、依賴及 async 限制；不支援就拒收並說原因。這些都不需要 LLM。

- **M14｜`axes.md` §4、`plan.md` 第一波過關線：門檻互相矛盾。**  
  3 次過 2 次約 67%，若按穩定軸比例對應只能拿 2 分，卻又要求所有軸大於 2；團隊 L3 要 ≤10 次，驗收卻允許 25 次。資源軸把反覆工作判 2 分，郵差又估 R3。有些工具的 S5 宣稱冪等，但 append、寄新信本來就會再做一次。  
  **改法：**分開功能試跑門檻與正式評分，補完整且互斥的分數區間；測試次數不足就不評穩定分。比較同一初始狀態下的結果，另驗「同一請求 ID 重試」；不要要求所有合法的新操作都冪等。資源以實測增量成本評，不以是否反覆執行直接扣分。

- **M15｜`axes.md` §2.3：「真正寫欄位剩六～七軸」推論混用了兩套編號。**  
  概念版第 7／8 軸是組合／環境；metadata 版第 7／8 欄是 guarantee／dry_run。`45a8d82` 的提交說明明寫 **8 個描述軸**，不能再扣掉概念版的兩軸推成六個。  
  **改法：**刪掉這段數量推導，分開列概念分類、Python metadata、C++ 描述型別。可以說「本次搜尋未找到明稱六軸的定義」，不能把未找到寫成已證明歷史上不存在。

**建議**

- **S1｜`workflows-as-team.md` §1：改成「以 Markdown 為主」。**  
  它也包含 JSON／CSV、腳本與可選 skills。routines 完成後更新日期，並非刪掉例行項目；只有一次性 schedule 完成後刪列。「三層＝lead／worker／reviewer」也不是原模板原樣搬來，應明示是這次的改編。

- **S2｜§2 三個 agent＋四個機械員：作為角色分工合理，不必宣稱最少需要三個 agent。**  
  全機械驗收的案例不用啟動 reviewer；門房能完整處理時也不用 lead。郵差＋書記合併合理，但同步跑長達 120 秒的 verify 會阻塞其他投遞，宜改成提交一次性驗收工作、後續收結果。

- **S3｜T-route／T-crystal：不叫模型做得到，但只能保證明訂範圍。**  
  門房優先採明確句型、完整參數、否定與歧義測試；關鍵字多重命中就落穿，避免「不要導入 heartbeat」反而觸發導入。固化第一版只提候選；同一工作流出現三次不足以證明規則正確，需負例及未參與提案的測試案例。

- **S4｜LLM 標記要同時交代工具本身與整條流程。**  
  T-route、機械 compact、靜態 wrap-py、統計 crystal 都可不叫模型。T-verify 本身也可不叫，但 `judge` 交 reviewer 後整條流程仍有模型。填已知佔位、套用已決定的刪段規則也可機械做，不必一律列為模型工作。摘要「只有 wrap-cli 可能要模型」需限定為工具內部、第一版預設行為。

- **S5｜清單大類都有涵蓋，但幾個承諾尚未落到交付。**  
  `board`／模型查任務表、審查逐條回報、人查看待答問題、排程寫入、任務取消／重派缺完整接口；agent 修改目前主要是人格與 access，模型／排程／工具設定修改需明示另案或人工。T-toolnew／T-tooltest 在 catalog 寫第一波，plan 卻派第二波；`/compact`、`/answer` 的 talk 接線也要指派負責者。

- **S6｜原子寫入還要配併發控制。**  
  任務表、notes、SESSION-LOG／WAIT_USER、json_edit 的讀改寫需要單一寫入者、穩定鎖或版本檢查；rename 只能避免半檔，不能避免兩人後寫蓋前寫。這正是 proto2 已付過代價的教訓。

- **S7｜補長期運作成本與公平驗收。**  
  三次測試要重置任務、記憶、郵件與排程狀態，不只是重建 `p`；固定模型設定及資源配置。archive／mail.log／done 要有保留政策。人易懂分數中，模型扮新手只能算代理測試，不能直接代表真人理解程度。

**確認沒問題的**

- workflows 是分層手冊、需要外部引擎執行；aos kernel 能承接機械排程，理解正確。
- `IMPORT.md` 四條 Done when 引用正確；heartbeat 導入可當範圍有限的首個案例，但尚未證明能在 25 次呼叫內完成。
- 信件直接帶內容、不給模型輪詢等信工具、規則放工具、按角色縮減工具表，都符合 proto2 教訓。
- ai_core 九軸表、metadata 欄位引文及治理原則引用基本正確；另提「五項使用者標準＋邊界」且明示待確認，也合理。
- 模板建 agent、AST 靜態包 Python、機械驗收先做、模型造工具與摘要後做，整體順序值得保留。
