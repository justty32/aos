# 能拿它們來幹嘛（發散，十一個＋四個）

**六軸**：協調者給了五軸——**少**用 LLM、**穩**、**省**資源、**快**、人易**懂**；我補第六軸**安**全（會不會亂動東西、亂花錢），因為這兩支會自己改檔、自己跑指令。

「少」在這裡的意思是**整件事總共要問幾次模型**：一張單子在它們裡面會問很多次，但比起 aos-agent 用 deepseek 一格一格試錯，常常總數反而少。

## 1. agent 把寫程式的活丟給 claude-cpu

aos 的 agent（便宜模型）負責聊天、拆事情；碰到「改這個 repo 的三個檔、跑測試到綠」就寫一張任務書，用一個 `delegate` 工具 `aos-kernel add --once --pool claude`，**立刻回一個單號**，之後再用 `delegate_status` 查（不在工具裡同步等，照「沒有同步工具」那條拍板；同步等會佔住 default 池一顆 cpu 半小時）。
大腦便宜、手很強。前提：agent 的工具拿得到 `AOS_KERNEL_HOME`——這正是 agent-access 提案說「不該給」的東西，所以 `delegate` 要做成**受信任的投遞入口**：只收任務書文字，池、模型、工作區、額度寫死在入口那邊（現在 kernel 沒有「誰能用哪個池」，見 [cost-safety §2](cost-safety.md#2-誰能叫它們)）。

## 2. codex-cpu 當唯讀審查員

調度者現在每一輪都這樣做：`codex exec -m gpt-6-astra -s read-only -o review.md - < review-task.md`。改成單子之後，審查排進 kernel、`aos-kernel ls` 看得到在排隊還是在跑、逾時會砍、報告落在固定位置。
`-s read-only` 本身就是一道牆，這是最安全、最先可以做的一種。

## 3. 造工具的工具

單子：「照 proto5/tools/README 的 base 格式，寫一個叫 `http_get` 的工具，含工具檔與程式與一個自測」。回來一個資料夾，人看過後 `aos-agent tools add` 裝給 agent。
aos-agent 自己造工具要很多格、便宜模型常寫壞；claude 寫這種小程式很穩。產出是**普通檔案**，之後跑工具完全不花錢——花一次、用很多次，所以「少」與「省」是＋。

## 4. agent 的臨時大腦

llm.json 多一種 `kind: "claude-cli"`，aos-llm 掛了、LiteLLM 沒額度、或這個 agent 要處理難題時，把 `info.llm.model` 換成那個代號。細節在 [others §3](others.md#3-當一個-agent-的大腦可選)。
慢（每則幾十秒起跳）、吃使用者的額度，所以是**備胎**，不是日常。

## 5. 用 session 養一個「熟某 repo 的顧問」

一個 cli 家長期指著一個 repo，第一次花錢讀懂整個 repo，之後每次 `--resume … --fork-session` 問問題，都從「已經讀懂」開始。別的 agent 把它當通訊錄裡的一個人問。
好處是不用每次重讀；壞處是 session 會越來越長，要定期讓它自己寫一份摘要、開新 session（它們有 compact，但在 `-p` 下何時觸發**未實測**）。

## 6. 宣告式池同時開幾個 codex 跑一批任務書

proto5-2 的 `aos-kernel cpu add --pool codex --count 4`，然後一口氣放 40 張單子（每個模組寫測試、每份文件翻譯、每個檔 lint 修正）。kernel 排隊、四顆輪流做、做完的回音一張張回來。
池大小＝並行上限＝燒額度速度，調一個數字就控制；**要注意每張單子寫的檔不能重疊**（kernel 不管這個）——最好一張單子一個 git worktree。

## 7. 把工作流的每一步變成一張單子

`wf/workflows` 的派隊流程（寫任務書 → 隊員做 → 唯讀審查 → 修 → commit）每一步都是一張單子；前一張的回音到了才放下一張。
現在是調度者手動接力；變成單子後可以由一支小程式、或一個 aos-agent 當「接力手」。**ff-merge、push 仍然留給人**（鐵律 2：不可逆的對外動作要使用者授權，agent 寄的單子不算授權）。

## 8. 人直接丟任務書、排一晚上的佇列

`aos-cli say` 或 `aos-kernel add --once` 丟十張單子給 1 顆 claude cpu，自己去打遊戲或睡覺；早上 `aos-kernel ls` 看結果。
跟現在「開一個 claude 互動視窗」比：可以排隊、不佔螢幕與鍵盤、斷線不怕、每張的輸出都落在檔案裡。注意：一次塞進 kernel 的單子，**額度用完也不會自己停**（連敗暫停只管 aos-cli 自己要放的）；要「用完就停」得交給 aos-cli 一張一張放（受控投遞），而同一個 cli 家一次只跑一張，所以要排十張就開十個 cli 家、或做一個佇列。

## 9. 試玩員

記憶裡「每段做完派人試玩」：現在是調度者手動開 Opus／gpt-sol，只給 README、五條標準打分。做成單子：牢裡只掛**允許它讀的文件**（README、tutorials）與跑 aos 需要的程式（唯讀、放在它不會去翻的位置）＋一個空的試玩資料夾可寫；報告寫進單子自己的輸出資料夾，**由牢外收件再放進 `notes/play/`**。
整個 `proto5/` 唯讀掛進去它照樣讀得到原始碼；只有「不掛」才是真的只拿得到 README。

## 10. 一寫一審對拍

一張 claude 單子寫、回音到了自動放一張 codex 唯讀單子審、審出必修再放一張 claude 單子修，最多三輪。兩家模型的盲點不同，互審比自審準。
兩倍花費、兩倍時間，適合「錯了很貴」的地方（規範定稿、崩潰窗口）。

## 11. 因為它們很成熟才做得到的

aos-agent 現在做不到、短期也不值得自己做的：
- **大 repo 理解與多檔重構**：它們自己會搜、會開子 agent、會分段讀，aos-agent 的 base 工具加便宜模型撐不起幾十個檔。
- **網路**：claude 的 WebFetch／WebSearch、codex 的 `--search`；aos 沒有網路工具。
- **看圖**：codex `-i`、claude 讀圖片檔；截圖除錯、看設計稿。
- **現成的審查指令**：`codex review`、`codex exec review`、`claude ultrareview`（雲端、另計費）。
- **固定形狀的輸出**：claude `--json-schema`、codex `--output-schema`——拿來當可靠的「從一堆文字抽出 JSON」工具，餵給 aos 的程式。
- **自帶的權限與沙盒**：codex `-s`、claude `--restricted`；比 aos 自己的 base 工具「bash 關不住」強一截（但仍不如 bwrap）。

## 再補幾個（審查員建議）

- **故障診斷**：丟一份 `aos-kernel ls -v`、cpu.log、agent.err 給它，回一份「哪裡壞了、怎麼修」的報告，不准改檔。
- **失敗測試縮成最小重現**：一條紅掉的測試，要它縮成最短的重現腳本。
- **交接摘要**：一條工作線收尾時，把 diff 與筆記縮成一頁交接書。
- **規範與程式的差異審查**：唯讀比對 `spec/` 與 `lib/`，列出對不上的地方。

這幾種都**先產報告或 patch，附基準 commit 與驗證結果**，由人或調度者決定要不要套。
