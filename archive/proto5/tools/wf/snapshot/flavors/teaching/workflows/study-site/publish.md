# publish — 把課程發布成靜態站

[study-site](README.md)｜[WORKFLOWS](../../WORKFLOWS.md)

把驗收完的課程掛上任何靜態託管（GitHub Pages 或同類）。這一步**只處理發布**，不改內容。

**何時用**：內容已過 [quality-gates](quality-gates.md)，要給別人看得到。
**何時不用**：課程只給自己或本機用；還沒驗收完 → 先驗收。

## Done when

- 每個公開檔案（總入口、各課的 HTML／CSS／JS）都回傳 HTTP 200。
- 部署頁面沒有外部執行期請求。
- 實際網址、版本、部署紀錄與行動裝置驗證結果寫進該課 `驗收紀錄.md`。

## 契約

- **只發布成品**：HTML、CSS、JavaScript 與必要資產。`PROJECT-BRIEF.md`、`BUILD-SPEC.md`、`派工計畫.md`、工作流檔一律**不發布**。
- **單一入口**：整站一個總入口頁，各課掛在自己的 slug 底下。
- **slug 表**：來源目錄 ↔ 發布路徑的對應寫成一張表（在部署設定裡），新增一門課就加一列。slug 用穩定的 ASCII 路徑，別跟著課名改。
- **原始碼留在來源目錄**：組站步驟只在部署環境把成品組成待發布目錄，不把產物複製回版控，也不把整個資料庫當站台根目錄。
- **不假設部署在網域根目錄**：課內資產一律相對路徑（`./styles.css`、`./app.js`）。跨課連結在組站時依 slug 表改寫。
- **部署環境不安裝套件**、不抓圖、不建置框架；只做複製與組裝。

| 新增一門課要動 | 動作 |
|---------------|------|
| slug 表 | 加一列 `<來源目錄> → <slug>` |
| 觸發路徑 | 確認新來源在部署觸發範圍內 |
| 跨課連結改寫 | 該課若用 `../../<其他課>/` 形式連別課，加一條改寫規則 |
| 總入口 | 加一個連到新 slug 的入口 |

## 流程

1. **發布前確認**（不可自作主張）：遠端 repo 與分支是不是使用者指定的、帳號與可見性正確、託管是否已有既存設定或自訂網域。**任何一項與現況衝突就停下來問**，不得覆蓋。守鐵律 2（授權來源）。
2. 確認工作樹只含本案與使用者已知的變更，推送範圍列得出來。
3. 部署，等它跑完，**不重複觸發**。
4. **驗證**：逐一請求總入口與各課檔案，確認全部 HTTP 200；檢查沒有外部請求；在行動寬度（約 `390px`）確認導覽、輸入、重設可用。
5. 把網址、版本、部署紀錄與驗證結果寫進 `驗收紀錄.md`；跑不了的（真人實機觸控）記 [WAIT_USER](../../WAIT_USER.md)。

> 〔導入判斷〕課程只在本機使用、不對外發布 → 本流程不啟用，`study-site` 的驗收止於本機靜態 server。同步：`workflows/study-site/README.md` 流程第 6 步與內容表、專案 `WORKFLOWS.md` 派發表的 publish 那列。

## 交接

- 發布後才發現內容要補 → [enrich-existing](enrich-existing.md)（只加厚文字）或回 [study-site](README.md)。
- 部署設定與帳號權限要使用者動手 → [WAIT_USER](../../WAIT_USER.md) 一行；為什麼選這個託管 → [decisions](../decisions.md)。
