# 4. 選項物件：`$opt` / `$val`

形狀固定：

```json
{"$opt": 任何值}
{"$opt": 任何值, "$val": 值}
```

- `$opt` 的值**什麼型別都可以**（字串、數字、物件、陣列、`null`……）——機制本身**不解讀、
  不驗型別、也不解裡面的指示詞**，原樣交給宿主規範去判斷。「`$opt` 該是什麼形狀」是宿主
  規範自己定義的事，不是指示詞機制管的。
- `$val` 是「本來要直接寫在那一格的值」，型別照那一格的規則驗；`$val` 本身**可以再是
  指示詞**（`$env`／`$fmt`／`$ref`），解完再驗。
- 選項物件只**讀 `$opt`、`$val`** 這兩個 key，其他 key（含 `$ref`／`$fmt`／`$env`）**一律忽略**，不會報錯。
- 「這個位置認得哪些選項、`$opt` 該是什麼形狀、哪些選項要求一定要帶 `$val`、哪些不准帶
  `$val`、哪些選項彼此互斥」——**全部由宿主規範決定**，本文不定義任何實際的選項名字或
  型別規則。宿主規範也決定「這個位置根本不准用 `$opt`」的位置怎麼算錯。
  - 舉例：inst 規範（見 [inst-posix.md](../inst-posix/README.md) 3.3）自己約定 `$opt` 是「選項名
    字串」或「非空選項名字串陣列」，陣列裡名字重複算錯、選項名區分大小寫只認小寫——這是
    inst 這個宿主自訂的慣例，不是機制本身的規定，別的宿主可以用別的形狀。
- 不認得的選項＝`UnknownOption`（由宿主的選項表決定認不認得）；帶了不該帶的 `$val`、漏了
  必帶的 `$val`、或選了互斥的選項組合＝`OptionConflict`（同樣由宿主的選項表決定）。
