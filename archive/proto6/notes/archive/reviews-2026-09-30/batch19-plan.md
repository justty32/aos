### 4.1 三層與 tick 核心（T-07 改寫、T-10 新、B-626 換主題）

〔使用者方向 2026-09-30，第十九批〕

- **tick 是一個定期被執行的程式**，怎麼被執行不管（daemon、cron、人手都行）。人手跑的風險自己承擔。
- **管轄區**＝tick 執行時的 cwd。aos 體系裡的慣例：兩個 tick 的管轄區不重疊、但可以包含，被包含的從屬於包含它的。tick 對管轄區有最高裁量權，這是約定，不是 tick 運作的前提。
- **三層**：
  1. **核心**（本質是加了功能的 aos-exec）：同資料夾互斥鎖、照任務表依序跑（每項是 inst 的超集）、上下層判定。
  2. **標準配備**：出廠附、預設全掛、不能拆（4.2）。
  3. **其他掛載**：kernel、agent、clock、自訂任務。
- **核心一格的流程**：取鎖 → 全掛檢查（4.3）→ 讀 `.aos/tasks.json` 並驗形狀 → 照陣列順序，每項照 inst 跑 → 放鎖、回結束碼。
- 「tick 不跟 once、LLM 嘗試、agent 一輪共用外殼」（第十八批裁定 1）保留。

### 4.4 上下層判定（B-628 新、T-10）

〔使用者方向 2026-09-30，第十九批第 2、8 條〕

- **預設上層**：從本 tick 的資料夾往上，最近一個「有 tick 的資料夾」。判準看疑-10。路徑逐段比對，不展開 symlink（沿 T-03）。
- **覆蓋**：經 daemon 登記時帶 `parent_id` 指定上層，就蓋過預設。覆蓋存在 daemon 的登記裡；daemon 重啟後，照現行逐層重建由上層重新登記回來。不在 daemon 底下的 tick 沒有覆蓋，只看資料夾。誰要同意、覆蓋後管轄權歸誰，看疑-5。
- **下層**：有效上層是我的 tick。
- **登記的前提**（建議預設）：在 daemon 登記時，有效上層也必須已經在同一個 daemon 登記（沿現行「首次要父層同意」）；否則回 `not_registered`。
- **換父兩條路**：
  1. **搬資料夾**：搬進別的 tick 的資料夾，新位置最近的那個自動成為上層。路徑就是 id，所以等於舊 id 解除、新 id 重登；引用舊路徑的回址會失效，風險自負（T-03）。
  2. **改登記**：用 `parent_id` 覆蓋。
  兩條都要被搬的那棵先暫停、程序全空（沿第十八批 Q10）。
- **身分繼承**：inst 的 `user` 省略時「繼承上層」，上層指有效上層（建議預設）。
- **巢狀 git**（建議預設）：上層的 git 提交不管下層 tick 的資料夾（自動當成 ignore），免得上層還原時蓋掉下層。

### 4.5 tick–daemon 通道（B-612～614、P-117～119 新）

〔使用者方向 2026-09-30，第十九批第 9 條〕以下 method 名、變數名、上限都是建議預設。

**誰有通道**：只有 daemon 開的 tick。daemon 開 tick 時放兩個環境變數：

- `AOS_DAEMON_SOCKET`：socket 路徑，就是現在的管理 socket。
- `AOS_TICK_TOKEN`：本格憑證。

任務會繼承這兩個變數；在「投件權就是執行權」之下這是預期行為。inst 的 `envs` 用 `clear` 時兩個都會被清掉，等於不給那一項通道。cron、人手跑的 tick 沒有這兩個變數，只能走檔案收件。

**憑證**：

- **發放**：daemon 每開一格就產生一張，至少 128 位元隨機，綁定「node id、`registration_id`、`tick_seq`」。
- **核對**：通道上的每個請求都在 params 帶 `token`；daemon 以固定時間比對，對上就把呼叫者當成那個 tick。
- **作廢**：該格的 tick 主程序結束（daemon 收到它結束）即作廢；daemon 重啟時全部作廢（只存在記憶體）。
- 砍掉「上一格掛的行程」時，核權看掛載者的 **tick 路徑**，不看當時那張憑證。

**走通道的事務**（沿用現有 method 的，只多收一個 `token` 參數；沒帶 `token` 的照舊看 socket 對面帳號，給人手與 CLI 用）：

| 事務 | method | 說明 |
|---|---|---|
| 登記、解除（含覆蓋上層） | `node.register`、`node.unregister` | 帶 token 時，呼叫者＝那個 tick |
| 掛行程、砍掉（原 once） | `node.mount`、`node.kill`（新） | 取代 register once:true 加 wake 加 unregister 三步；被掛的也可以是另一個 tick；資源與核權歸掛的那個 tick |
| 叫醒別的 tick | `node.wake` | 同現行 |
| 送訊息 | `node.send`（新） | 參數：`to`、`message`（跟檔案收件同一個 JSON-RPC 物件）、`urgent` |
| 取暫存訊息 | `node.take`（新） | 本格取走、daemon 同時刪掉；交給 tick 之後怎麼落地看疑-7 |

**暫存訊息**：

- 放 daemon 記憶體，**不保證送達**，daemon 當掉就丟。
- 每個收件 tick 設上限（例如 256 件、合計 16 MiB），滿了回 `mailbox_full`；單件上限沿用 IPC 的 256 KiB。
- 收件 tick 下一格開跑時交給它。**急件**：送到時照 `node.wake` 叫醒收件 tick；一般件等它自己下一格。急件要不要受上層節流看疑-9。
- **誰能送**：看疑-6。「投件權就是執行權」同樣適用。

**錯誤碼方向**（都在 -32000，`data.code`）：`token_invalid`（不認得、過期、跟 node 對不上）、`not_authorized`、`not_registered`（收件 tick 不在這個 daemon）、`mailbox_full`、`message_too_large`、`stopping`、`busy`。沒有環境變數的情況在客戶端就擋掉，印 `no_channel`，不送到 daemon。

**格式放寬**：通道上的訊息屬 daemon IPC，照 C-07 維持嚴格（不認得的欄位拒收）。

## 九、疑點（請你裁定，不替你選）

只列第十九批沒講到、又會影響設計的。標「先定」的不定就不能動筆，括號裡是會卡住的隊。

**疑-1（先定；卡 T3）標準配備怎麼掛到核心上？**

- a 核心留幾個固定掛勾（格首、每項前後、格末），標準配備是一整包程式，掛在這些掛勾上。
- b 標準配備就是任務表裡幾項固定的系統任務，加上包在每項任務 argv 前面的包裝程式（例如切帳號、進 cgroup 框）；核心只多提供「本格每項結果的紀錄」給它們讀。
- c 標準配備跟核心是同一支 `aos-tick`，只在規格上分層；「沒全掛」是用旗標或設定關掉其中的部分。

這題也決定 3、125 兩個結束碼歸誰，以及 `kind:system` 還需不需要。

**疑-2（先定；卡 T1、T3）標準配備的清單邊界。** 第 12 條明列 git 提交、needs、收件、切換使用者、cgroup 框、once。下列幾樣要不要也算進去？每樣各答「算／不算」：

- 投件與鬧鐘（B-624）；
- 發布摘要 `published.json`；
- `aos-clean`；
- daemon 端的重啟清空、node 框、排空停機（B-603、B-604）；
- 通道上的傳訊任務（第十九批第 9 條說它屬之後的 tick 任務設計）。

**疑-3（先定；卡 T2、T3）「全掛」怎麼算？**

- a 只看標準配備有沒有裝上；功能被設定限縮不算沒掛。例如沒 helper 時只准通用 user、cron 跑的 tick 沒有通道，都算全掛。
- b 看底下的機制實際能不能用；沒 helper、沒通道都算沒全掛，要警告、要問 y／n。
- c 分開算：cgroup v2、git 缺了算沒全掛；沒 helper、沒通道只是功能受限，不警告。

**疑-4（先定；卡 T1、T3、T5、T6）任務帶 `user`。**

- a 現在就允許；由標準配備的切換使用者落實，額度照 inst 核；沒 helper 時 `user` 不是通用 user 的那項以 125 失敗。
- b 移出永遠禁止清單，但本版仍拒收，等以後再開。

**疑-5（先定；卡 T2、T3）登記覆蓋上層：誰要同意，覆蓋後管轄權歸誰？**

- 同意：a 新舊兩個上層都同意（沿第十八批 Q10；舊上層指資料夾推得的那個）／b 新上層同意就好／c 新上層加子 tick 自己。
- 管轄權：a 資料夾上層對那個資料夾仍有檔案上的最高裁量，覆蓋只改「管理關係」（誰分資源、誰叫醒、誰能解除）／b 覆蓋後管轄權也一起轉走。

**疑-6（先定；卡 T2）通道上誰能送訊息給誰？**

- a daemon 用寄件 tick 的執行帳號，檢查它對收件 tick 的 `requests/` 有沒有寫權，跟檔案投件同一個判準。
- b 只准上下層之間互傳。
- c 同一個 daemon 底下都能互傳。

**疑-7（先定；卡 T2、T3）暫存訊息交給 tick 之後怎麼落地？**

- a tick 格首取回，寫進自己的 `requests/`，之後跟檔案收件完全一樣（有 Q1、去重）。
- b tick 取回後不落檔，直接交給收件任務處理。
- c 核心不碰，由收件任務自己上通道取。

**疑-8（不卡）`kind` 的分段順序還要不要？** 現在 `system` 必排最前、`custom` 最後，排錯整表拒收。

- a 保留分段與檢查。
- b 核心只看陣列順序，`kind` 只當標籤。

會跟著疑-1 走；疑-1 選 b 時，系統任務大概還需要排最前。

**疑-9（不卡）急件叫醒要不要受上層節流？** 急件由 daemon 直接叫醒，會繞過上層 kernel 的 `max_active_members` 與排程。

- a 直接叫醒，不問上層。
- b daemon 只通知收件 tick 的上層，由上層決定叫不叫。
- c 直接叫醒，但上層可以設定「我的下層不准別人叫醒」。

**疑-10（不卡）「有 tick 的資料夾」怎麼判？**（決定預設上層）

- a 有 `.aos/inst.json` 或 `inst.json`，跟投件時「目標是不是 node」同一個判準。
- b 有 `.aos/tasks.json`。
- c 在 daemon 有登記。

**已寫成建議預設、不另問的**：tick id 正規化成資料夾；鎖檔 `.aos/tick.lock`；路徑比對不展開 symlink；登記時有效上層也要已登記；身分繼承跟有效上層；巢狀 git 自動 ignore 下層；答 n 回 2；沒終端機的警告同時寫事項；通道的變數名、method 名、上限、錯誤碼；急件「能送就能叫醒」（疑-9 選 a 時）。
