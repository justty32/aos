## 1. kernel 是角色，不是程式？

kernel＝工作資料夾（tasks.json 放政策）＋它擁有的一份 daemon 設定。沒有常駐 `aos-kernel`。**建議：是。**

## 2. 一個 kernel 一個 daemon？

A：每個 kernel 一份 daemon 設定，多層＝daemon 跑 daemon。B：全機一個 daemon，kernel 只管其中一組項。**建議：A。** 但注意 A 的多層目前只能同帳號（16）。

## 3. 成員狀況靠 push 還是 pull？

push：成員 `after_all` 寄 summary。pull：kernel 讀成員的 `.aos/tick/last/`。**建議：push**，pull 留除錯。agent 隊同意。

## 4. kernel 怎麼 SIGHUP 自己的 daemon？

a 加環境變數 `AOS_DAEMON_PID`（指開我這項的那個 daemon 主程序）；b 鎖檔寫 pid；c 控制 socket 加 `reload`。**建議：a。** 前提 kernel 項跟 daemon 同帳號。第 4 階段才要。

## 5. LLM 額度要不要強制？

grant 是建議、agent 自律。強制的路：池代發（agent 把請求寄給池那一項）或逐次呼叫前檢查。`before_kind` 寫 tasks-blocked 擋不到當次。**建議：POC 先自律。**

## 6. grant 用信（私門）還是用檔？

信：每成員一扇私門，寄到＝叫醒；重讀加不了門，加成員要重開。檔：kernel 寫 `public/grants/<成員>.json`，另用 `aos-ctl wake` 叫；加成員只要重讀，但 agent 要知道檔在哪。**建議：私門**（agent 隊也選這個），第 4 階段再評估檔。

## 7. 下層 kernel 怎麼知道上層的門？

a 寫死在下層 `policy.json`；b 啟動下層那份 `inst.json` 的 `envs` 用 `$env` 把上層的門與自己在上層的名字存成別名。**建議：b**，不用重複寫路徑；a 當備用。

## 8. 額度的窗口用誰的格？

**建議：kernel 的格**（C-01），grant 帶 `window_start_seq`、`window_ticks`，數字是窗口總額。

## 9. 任務的 `kind` 要不要訂 `"kernel"`？

**建議：要，只是標籤**，給範本掛 hooks 用。

## 10. 名字：還叫 kernel 嗎？

**建議：保留 kernel，不用 node。**

## 11. kernel 的格壞了要不要救？

**建議：不救。** 任務非 0 整格仍回 0，成員照上次 grant 跑。

## 12. 成員資料夾要不要放在 kernel 資料夾底下？

**建議：不要求。** 成員是誰只看 daemon.json。

## 13. 要不要留「成員彼此講話」給 kernel 轉？

**建議：不要。**

## 14. 隨機性當排程依據（T-06 第 6 條）

**建議：先不做**，summary 的 `usage` 預留位置。

## 15. 第 0 階段做完要不要停在方案 D？

**建議：不停**，但第 0 階段另搭一個真正沒有 kernel 的版本並排看，看完再拍。

## 16. 多層要不要逐層切帳號？（新）

現行帳號模組要 root 才掛得起來、成員不准 root，所以只有最頂層能分帳號，下層 daemon 不能再分。要逐層切，得改帳號模組（例如下層 daemon 經上層 root 端代開），是新能力。**建議：POC 多層同帳號；要不要做逐層切帳號等 POC 後拍。**

## 17. kernel 限制的是「開格數」還是「真正計算數」？（新）

成員收到任何信都會跑一格，kernel 攔不住；kernel 能限的是它主動叫醒的格數，與 LLM 額度（靠成員自律）。**建議：接受「收信開格」，kernel 管 LLM 額度與主動叫醒數；要限制開格數就得把成員的門收窄（誰能寄）。**

## 18. 「壓住下層」要哪一種？（新）

停止派新工作（在跑的做完）、立即終止、原地凍結三種。對常駐的下層 daemon，`pause` 無效。**建議：POC 做「停止派新工作」＝寄 grant `awake:0` 給下層 kernel；要立即終止用 `kill`＋cgroup。原地凍結不做。**
