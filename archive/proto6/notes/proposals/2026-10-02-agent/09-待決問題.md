# 待使用者決定的問題（每題附建議）

← [提案入口](README.md)｜上一份：[分階段](08-分階段.md)｜下一份：[範例 JSON](10-範例JSON.md)

方向性的都在這，我只擺選項與後果。**沒回答不等於採納建議**：方向題（額度強制、隔離、上下層形狀）沒拍就保持待決、不動手；只有例行細節（檔名、欄位名、預設數字）沒回答才照建議值做。使用者 10-02 說方向題他還沒想，只是想看概念。

| # | 問題 | 選項 | 建議與判準 |
|---|---|---|---|
| 1 | **一格＝一次 LLM 呼叫**，還是一格裡循環到沒有工具呼叫才停？ | a 一格一次，要連續就叫自己下一格；b 一格內循環 | **a**。kernel 要按格計費、要在工具與下一次呼叫之間插手，只有 a 做得到。代價：一次任務多幾格、每格多幾十毫秒 |
| 2 | **一步拆成五項任務**（方案 A）還是一支程式（B）？ | A／B | **A**。看 `tasks.json` 就知道一步做什麼；LLM 項能被 hook 擋。B 只快在第一天 |
| 3 | **睡＝一直 `paused`**（kernel 狀態檔預置；信、grant、`wake` 來了跑一格、跑完照樣暫停）？ | 一直 paused／長週期不自醒 | **一直 paused**，對齊 kernel 提案 10-02 改版。`pause` 只停週期、來信仍跑，正好當睡；壓住改靠「不給 grant」 |
| 4 | 工具呼叫＝**寫成 inst 交給 `aos-exec`**？ | a inst＋aos-exec；b `act` 自己 Popen | **a**。證據留在 `work/tools/`、結束碼走 inst 規矩、工具沿用 agent 帳號（09-28 方向） |
| 5 | **信的欄位**：照 kernel 提案 `type`、`version`、`from`（inst 字面值），agent 之間再加 `reply_door`、`text`、`ref`？ | 照這／另訂 | **照這**，六個 `type` 一份 schema。`from` 不是身分證據，能寄才是 |
| 6 | **LLM 端點**：agent 自己直連（`$env` 給 URL 與 key），kernel 只管 pause／wake？ | a 直連；b 經 kernel 代理 | **a 先**。b 是常駐服務，等 kernel 那邊決定。要換成 b 時只改 `AOS_LLM_URL` |
| 7 | **子 agent 怎麼生**：平的（同一 daemon）還是子 daemon？ | 平／巢／兩個都要 | **先平、第四階段再巢**。proto5 父子樹撤回成「一律平的」；巢的有兩個坑（環境變數外漏、沒人送 SIGHUP） |
| 8 | **記憶壓縮**沿 proto5：機械、不叫模型、32000 token？ | 沿用／改 | **沿用**。使用者裁過；叫模型摘要預設關 |
| 9 | **一 agent 一 Linux 帳號**（09-28 方向）？POC 要不要先做？ | a 第三階段起；b 全程同帳號 | **a**。需要 root 開 daemon；門的資料夾權限要有帳號才有意思 |
| 10 | tick／daemon 的 spec 與程式**完全不提 agent**？ | 是／加 `kind:"agent"` 之類的保留字 | **是**。agent 只是範本＋幾支普通程式；kind 值隨便寫是第二十四批定的 |
| 11 | **信箱在記憶體**，daemon 重開丟信：先不管？ | 不管／`inbox` 落檔已夠／daemon 加落盤 | **不管**。「默認一切正常」；`inbox` 是每格第一項，窗口極小 |
| 12 | 主管怎麼對子 daemon 送 SIGHUP？`AOS_DAEMON_PID` 只會是「啟動自己的那個 daemon」，主管與子 daemon 是上層的兩個項，拿到的是上層 pid | a 啟動子 daemon 的 inst 用 `sh -c 'echo $$ > team/daemon.pid; exec aos-daemon …'`，零改程式；b 上層 `restart` 整組重開；c 控制 socket 加 reload | **a**；同帳號才送得到訊號。c 是使用者明講不收的 |
| 13 | **子 daemon 要不要能切帳號**？帳號模組要 root 開，主程式降權後開不了 root 子 daemon | a 子 daemon 不切帳號（成員同主管帳號）；b 上層帳號模組的 root 端代開子 daemon 為 root | **a 先**。b 等於開放降權主程式要 root 做事，違反帳號模組的安全前提 |
| 14 | **人怎麼跟 agent 講話**：人也是 daemon 的一項（有門、`aos-mq peek`），還是另造 `aos-say`／`aos-listen`？ | a 人也是一項＋薄包裝；b 專用 CLI | **a**，第三階段再包 `aos-say`。proto5 的教訓是「要背的太多」，少造指令 |
| 15 | agent 一直 `paused` 後 `interval_ms` 用不到；定時醒要靠 summary 的 `after_ticks`／request `wake_me`。沒 kernel 時要不要保底週期？ | a 沒 kernel 就不 paused、`interval_ms` 5 分；b 一律 paused，定時交給人或 cron | **a**，第 0～2 階段用 |
| 16 | agent 狀況 **push**（每格 `after_all` 寄 summary）還是 kernel 來讀檔？ | push／pull | **push**，對齊 kernel 提案。閒置 agent 不跑格，信量只跟活躍數成正比。`public/status.json` 留給人看 |
| 17 | 工具**平行跑**？ | 先依序／平行 | **先依序**。proto5 平行過，順序不保證惹過麻煩 |
| 18 | 新程式名：一支 `aos-agent` 帶子命令，加一支 `aos-llm`？ | 照這／拆五支 | **照這**，少五個檔名要背 |
| 19 | **grant 寄到成員自己的門**（一扇門叫醒全部訂戶，共用門一封 grant 全員醒）？ | a 私門；b 共用門 | **a**；kernel 提案 10-02 已採。門要在 daemon 開起來時列好（重讀不開新門） |
| 20 | 「連續做」由誰叫：kernel 看 summary `ready` 寄 grant，還是 agent 自己 `wake`？ | a kernel 叫，沒 kernel 才自叫（`self_wake`）；b 永遠自叫 | **a**。b 等於繞過 kernel 的排程 |
| 21 | 額度要不要**硬強制**？agent 握著金鑰、能寫自己的 `tasks.json`，`think` 自查或 `after_task.think` hook 都只是配合式 | a 先自律（配合式）；b kernel 當 LLM 代理（常駐服務，金鑰只有它讀得到） | **a**。b 是方向題，等使用者拍 |
| 22 | **grant 什麼時候寄**？每格重寄會跟 summary 互相叫醒 | a 只在要叫它、或政策／窗口變了才寄；agent 空格不寄 summary；b 每格重寄 | **a**；kernel 提案 10-02 已採 |
| 23 | 有 kernel 卻**還沒收到 grant**，agent 先等還是用自己的預設額度？ | a 等（這格不打 LLM、summary 說 `ready:true`）；b 用 `config/agent.json` 的預設額度 | **a**。有 kernel 就聽 kernel；b 會讓額度形同虛設 |
| 24 | 子 daemon 的**環境變數**：要不要讓 daemon 自己把繼承來的 `AOS_DAEMON_*` 先拿掉再給（像 tick 對 `AOS_TASK_*`）？ | a 範本用 inst `envs` 的 `clear`＋別名化處理；b 改 daemon 一行 | **b** 之後再說，POC 先 a；是小改、不是功能 |
| 25 | **誰寄回普通回答**、一格處理幾封對話信？ | a `act` 在沒 tool_calls 時寄回 `reply_door`，一格一封；b 多封合成一輪 | **a**，不用先造多對話排程 |
| 26 | 多層**同帳號**（子 daemon 不能再切帳號）接受嗎？ | 接受／要改帳號模組 | **接受**，kernel 提案同 |

## 跟 kernel 提案對齊的結果（10-02 審查後）

兩邊照 astra 審查互改一輪後已一致：agent＝daemon 清單上的一項、一直 `paused`、grant 寄私門且就是叫醒、不每格重寄、agent 空格不寄 summary、`after_ticks`、窗口總額＋`window_start_seq`、grant 存 `state/`、六個 `type` 一份 schema、`after_task.think` 而非 `before_kind.llm`、`pause`／`kill` 的真實語意、多層同帳號。還沒拍的在第 21、23、24 題。
