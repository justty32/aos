# 四、thread 版（B）要付的改動

← [入口](README.md)｜上一份：[實測](03-實測.md)｜下一份：[其他路線](05-其他路線.md)

由一位助手逐檔盤點 `proto6/src/py/`（lib 28 檔、tests 654 條、共 12,343 行）。路徑在 `proto6/src/py/lib/`。工作量只給相對大小。使用者方向 2、6 已把 cgroup、帳號搬暫緩、kill／restart 待定，所以**跟那三樣有關的項在 B 下反而不用做**，另標〔方向 2／6 後消失〕。

tick 側（1～6）集中、量小。daemon 側（7～11）是重寫 `run_once` 與設定模型。

## B. 自然消失

- `aos_daemon_run.py` 第 13 行 `EXEC`、第 38～51 行 drain thread 與「先 waitid 不收屍」那段。
- `aos_daemon_kill.py` 第 11～35 行 `kill_targets()` 的 /proc 走樹（它存在只因 aos-exec 把任務開在另一個 session）。
- `aos_exec_spawn.py`（117 行）：proto5 的非同步入口，proto6 daemon 根本沒 import。**不分 A、B，現在就可移暫緩區。**
- 「用 inst.json 包 aos-tick」的樣板、aos-exec 找 `.aos/inst.json` 的規則、`exec_out_path`，對 tick 項都不再適用。

## C. 做不到或變難

| # | 事 | 說明 |
|---|---|---|
| 1 | 殺卡住的 tick | 只能合作式取消；tick 卡在 Python 本身（`aos_tick_record.py` 第 68 行 `os.rename` 卡 NFS、讀表卡住）無解。現在靠 SIGKILL aos-exec＋後代一刀切 |
| 2 | 帳號切換 | `setuid` 是整個程序的事；root 端 `aos_daemon_root.py` 第 98～117 行只會 fork→setuid→execve。thread 的 tick 不可能以別的帳號跑〔方向 2 後：外面另開 daemon，不是問題〕 |
| 3 | 故障隔離 | tick 的 bug 現在被程序邊界擋成「那一次 exit=1」；thread 版 `MemoryError`、`RecursionError`、segfault 都是 daemon 的事 |
| 4 | stderr 捕捉 | thread 內任何第三方寫 `sys.stderr` 的東西都進 daemon 的 stderr，分不了項；只有經 sink 的行能分 |
| 5 | 環境變數隔離 | 之後任何 tick 模組若直接讀 `os.environ` 就靜默壞掉，沒有程序邊界幫忙抓 |
| 6 | inst 外殼給 tick 的東西 | 現在 inst 能給 aos-tick `exit` 檔、`cwd`、`envs`；thread 版要在 daemon 設定重做，或承認 tick 項沒有 |
| 7 | daemon 死了 tick 活著 | 對 tick 本身不成立（第 11 項），只對任務成立 |

不是問題的：同程序 flock 自我互斥——`aos_tick.py` 第 197～199 行與 `aos_daemon.py` 第 125～127 行都是 `flock`，全 repo 沒有 `lockf`；thread 間照樣互斥。

## D. 現行程式裡已經是函式邊界的

- tick→任務：`aos_tick_run.py` 第 20 行 import `aos_exec_run` 只為第 65、70、96 行的開檔與寫 exit；第 75 行自己 Popen。hooks、tasks-blocked 同一條路（`aos_tick_hooks.py` 第 60 行、`aos_tick.py` 第 246 行），環境傳 dict。
- tick 核心已是函式：`aos_tick.py` 第 129 行 `run_tick(cwd, table)` 回 int，無 `sys.exit`；第 141 行註解已預想「在同一個 Python 裡呼叫」。
- aos-exec 核心已是函式：`aos_exec.py` 第 122 行 `run_target()`；第 17～18 行文件寫「之後會直接 import 反覆叫」。這就是 A′ 的依據。
- daemon 內已有的 thread：每項一條（第 181～182 行）、每次兩條 drain、控制 socket 一條、每扇門一條。主 thread 只裝 signal handler；tick 模組零 signal handler，所以進 thread 不碰 signal 限制。wake／pause／resume／mq 在 thread 版一字不改。

## 一句話

tick 側六處參數化、量小；daemon 側要重寫 `run_once` 與設定模型、補 pipe 與退出語意。最重的 kill 與 cgroup 兩項，使用者的方向 2、6 已經把它們拿走，所以 B 的真實代價比乍看小——剩下的代價不在改動量，在 [09](09-分層視角.md) 說的那三類漏到上層的語意。
