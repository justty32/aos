# 任務與排程：讓執行機會與等待有理由

> 狀態：歷史（09-28 概念稿），現行以 [spec](../spec/README.md) 為準。09-29 起架構改為 node／kernel 樹，見 [kernel 樹](2026-09-29-kernel-tree.md)。

← [三大概念](concepts.md)｜前篇：[agent](agent.md)

**規劃草案，待逐塊討論。** 排程決定誰何時做、能用多少，基底落實限制，agent 決定工作內容。這不是要求先造完整排程產品；kernel 的程序形狀、集中或分散安排仍未定。首版先把工作歸屬、在途執行與結果對應說清楚。

## 1．任務輪次：人看到的一件事從哪裡到哪裡

一次要求可能跨多個 tick、工具與模型呼叫。任務層描述開始、暫停、繼續與完成，避免把某個程序退出誤認成整件事結束。例如字數工具已完成，agent 還沒解釋計算範圍，人的要求可能仍未完成。

這層與 agent 的狀態互相交接，但 idle 不自動等於任務完成。途中新訊息算同一輪還是下一輪、暫停時在途工具如何處理，仍是未定語意；不先讓名稱迫使所有工作符合一種固定輪次。

## 2．ready、wait 與准入：想做和現在能做不同

ready 表示工作條件已備妥，wait 表示仍等結果、時間或條件；即使 ready，也可能因名額不足尚不能開始。准入是在啟動前取得機會，不是先開一堆程序讓 Linux 替它們排隊。

例如十個工具同時就緒，只能啟動其中幾個，其餘保持持久待辦。取消 CPU worker 後，全局限制仍須保留。要定義哪些等待占名額、如何回收失敗的啟動；通知丟失不能讓工作永遠卡住，也不能靠頻繁 tick 所有冷 agent 補救。

## 3．優先與公平：先做誰，怎樣不讓別人永遠等

人的互動可能希望先回應，背景整理也不能永久挨餓。這層制定跨 agent 的選擇政策，基底不用理解「這是使用者正在等的事」。例如新來的短查詢先處理，但長任務等待已久時也要能前進。

優先權由可信政策決定，不由工具自行宣稱。先讓選擇順序與等待原因可解釋，再談複雜最佳化。公平的單位是 agent、任務還是某類請求，以及長短工作如何平衡，仍待討論，不能把「互動優先」直接寫成絕對插隊。

## 4．LLM 額度與 token：共用雲端機會

十幾個 endpoint 不一定有十幾份獨立額度，可能共享帳戶或模型限制。排程管理受管 LLM 呼叫的併發、速率、token 預估與已知消耗；agent 提供呼叫需求與 context，單次 client 負責傳送。

例如兩個 agent 同時呼叫同一配額域，必須一起算，而非各自以為尚有名額。逾時後遠端可能已處理，取消本機等待也不保證不計費；未知結果要留下來，不能宣稱 exactly-once。先做簡單名額與退避，token 結算、金鑰是否集中代理等細節再定。

## 5．粗資源預算：限制整體，也限制個別

一個 agent 可以派出多個工作，應看它們合計的資源，而非只看單支工具。本機程序、雲端請求及待派隊列的上限各有用途；cgroup 才是基底落實的限制，排程預算不能取代它；磁碟 quota 依 09-29 [裁定](2026-09-29-verdicts.md)是可選的記帳，不是硬上限。

例如每個 agent 的記憶體上限都合理，同時執行很多個仍可能超過整機能力，因此還需共同父層與全局准入。預算是上限，不是預留同等實體資源。額度調小時在途工作繼續、停止或等待回落，需明確選擇。

## 6．觀測與人工控制：讓人知道為什麼還沒做

至少應能分辨等待工具、等待配額、尚未到期、執行中與結果未知；人的暫停、取消和重試也要有可查的效果。例如顯示「共用模型額度不足」比只說 busy 更能讓人理解下一步。

觀測使用基底的事實，但排程負責解釋政策原因。喚醒及開始得快，不等於支援逐字串流，兩者分開規劃。人工取消何時確認、未知副作用如何讓人選擇，是後續要定的控制邊界，而非加一個按鈕就完成。

## 用同一件小事串起來

字數統計任務 ready 後先取得本機機會，由基底執行；agent 要整理回答時若需模型，另排共用 LLM 額度。等待期間不占唯一的 tick 執行機會。人查進度能看見等的是工具還是配額，結果回來才推進回答；整輪何時完成依後續契約判定。

建議依准入與等待 → 任務邊界 → LLM 額度 → 公平與觀測逐塊討論，再看萬 agent 計畫（已封存檔 README.md，索引見 [archive/README.md](archive/README.md)）。用少量假工作驗證理由與恢復，再擴大規模；FUSE、分散式 kernel 與父子 demo 都不是此閱讀路線的前提。
