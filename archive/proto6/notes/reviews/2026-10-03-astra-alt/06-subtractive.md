# 減法路線：先讓 agent 工作，再證明 kernel 有必要（astra，2026-10-03）

## 一段話結論

**POC 可以先不造 kernel。**
固定成員用現有 daemon 收信叫醒。
每個 agent 在 tick 裡完成一次模型呼叫與工具接續。
額度先各自固定分配。
這樣可以省掉 `aos-kernel`、grant／summary／request、額度窗口、多層接線與 PID 小補。
絕對最少可以只新增一支私有 `step.sh`。
我較建議三支範本腳本，保留 LLM 獨立一項。
兩者都不需要新增 aos 公開命令或修改核心。
但這只驗到「agent 能做事」，沒有驗到「多層資源政策有用」。
若三份提案的全部能力都要保留，把它們改寫成 shell 並不會省掉那些邏輯。

本次只讀文件與程式。
未改檔、未 commit、未跑測試。
下面的實驗都尚未執行。

## 替代方案

### 方案 A：固定小隊，沒有 kernel，各自持有固定額度

#### 長相

先限縮成兩個可信任的 agent。
兩者沿用同一 Linux 帳號。
每人一次只處理一個對話。
每格最多一次 LLM 呼叫。
先只有一個固定的唯讀 `wc` 工具。

```text
/tmp/aos-min/
  daemon.json
  daemon-state.json
  doors/
    alice/s
    bob/s
    human/s
    ctl/s
  recipe/
    prepare.sh
    call.sh
    finish.sh
  agents/
    alice/
      .aos/inst.json
      .aos/tasks.json
      config/request-base.json
      config/budget.json
      config/wc-inst.json
      state/pending.jsonl
      state/session.json
      state/usage.json
      work/<seq>/
        request.json
        prepared
        response.tmp
        response.json
        llm-ok
        tool/
          inst.json
          out
          exit
      input.txt
    bob/
      …同一份範本
  human/
    .aos/inst.json
    .aos/tasks.json
    replies.jsonl
```

三支腳本由所有 agent 共用。
模型請求直接採端點接受的 JSON。
工具直接採既有 inst。
先不造 `agent.json`、`tools.json` 的通用擴充格式。

daemon 設定如下。
所有目錄事先建立。
啟動環境的 `PATH` 包含現有 aos 指令。

```json
{
  "cwd": "/tmp/aos-min",
  "interval_ms": 60000,
  "modules": {
    "control": {"socket": "doors/ctl/s"},
    "state": {"$ref": "daemon-state.json"},
    "mq": {
      "ALICE": "doors/alice/s",
      "BOB": "doors/bob/s",
      "HUMAN": "doors/human/s"
    }
  },
  "insts": {
    "agents/alice": {"mq": ["ALICE"]},
    "agents/bob": {"mq": ["BOB"]},
    "human": {"mq": ["HUMAN"]}
  }
}
```

狀態檔預置暫停。

```json
{
  "insts": {
    "agents/alice": {"paused": true},
    "agents/bob": {"paused": true},
    "human": {"paused": true}
  }
}
```

這使它們靠來信或 `wake` 單跑。
不是靠長週期假裝睡著。
現有 state 會還原暫停狀態。
daemon 會先處理待補執行，再判斷是否暫停。
證據：[aos_daemon_state.py](../../../src/py/lib/aos_daemon_state.py)第 28–36 行；[aos_daemon_run.py](../../../src/py/lib/aos_daemon_run.py)第 69–85 行。

各資料夾的 `.aos/inst.json` 都可用：

```json
{"argv": ["aos-tick"]}
```

agent 的任務表只留三項。

```json
{
  "stderr": {"$opt": "append", "$val": "errors.log"},
  "tasks": [
    {"id": "prepare", "argv": ["sh", "../../recipe/prepare.sh"]},
    {"id": "llm", "kind": "llm", "argv": ["sh", "../../recipe/call.sh"]},
    {"id": "finish", "argv": ["sh", "../../recipe/finish.sh"]}
  ]
}
```

人的任務只收結果。
不回信。
因此不會形成回聲循環。

```json
{
  "tasks": [{
    "id": "receive",
    "argv": [
      "sh", "-c",
      "aos-mq take \"$AOS_DAEMON_MQ_HUMAN\" >> replies.jsonl"
    ]
  }]
}
```

第一版只有一種很小的應用信封。

```json
{"version": 1, "id": "q1", "text": "請算 input.txt 的字數"}
```

答案沿用 `id` 與 `text`。
固定寄到 HUMAN 門。
先不接受任意 `reply_door`、不做通訊錄、不做多對話路由。
若要驗 agent 互相交棒，再替固定工具加一個固定目的門。

`aos-mq` 已能原樣傳 JSON。
`take` 的身分來自 `AOS_DAEMON_INST`。
不需要新造收發 CLI。
證據：[aos_mq.py](../../../src/py/lib/aos_mq.py)第 30–66 行。

一格的分工如下。

| 階段 | 做什麼 |
|---|---|
| `prepare` | take 一次，保存全部信，再選一件工作。先續上一格的工具結果。沒有工作就全擋後項。有工作就組 request，最後才寫 `prepared`。 |
| `call` | 確認本格 `prepared`。檢查本地額度。先扣一次呼叫，再用 curl 發一次有逾時的 HTTP。回應有效才發布 `response.json` 與 `llm-ok`。 |
| `finish` | 只吃本格有效回應。工具呼叫交既有 `aos-exec`。更新對話。普通答案寄 HUMAN。還有可執行的工作才 self-wake。 |

三支腳本都在執行時讀本格 `seq`。
接力檔放在 `work/<seq>/`。
不能拿上一格的 response 補本格失敗。

也不能在 `tasks.json` 用 `$ref` 指向前項才會產生的 request。
任務表會在開格時展開已知欄位。
證據：[aos_tick_table.py](../../../src/py/lib/aos_tick_table.py)第 173–184 行。

工具先固定為 `wc -w input.txt`。
模型只選工具名稱。
不讓模型提供 shell 原始碼。
每次補出一份完整 inst。
`cwd` 指 agent 家。
輸出路徑指本次呼叫目錄的絕對路徑。

工具 runner 不用新造。

```sh
aos-exec --timeout-ms 30000 work/<seq>/tool/inst.json
```

現有 CLI 已接受 `--timeout-ms`。
證據：[aos_exec.py](../../../src/py/lib/aos_exec.py)第 242–265 行。

**額度採整場實驗的固定呼叫數。**

例如整場最多 12 次。
Alice 配 6 次。
Bob 配 6 次。
每人只寫自己的 `usage.json`。
不設窗口。
不重置。
不互借。

HTTP 嘗試前先扣額。
連線失敗也算一次嘗試。
中斷可能浪費額度，但不靠成功回應才記帳。
額度耗盡就留下原因，不再自叫。
這只限制合作式腳本。
它不是供應商帳單的硬上限。

#### 比原提案好在哪

最重要的減法，是取消本輪不需要的協商。

原 kernel 比較中的「沒有 kernel」仍要求成員共讀共寫額度檔。
那不是必要条件。
靜態分額讓每個 agent 只管自己的狀態。
因此不需要共用可變帳與跨成員記帳鎖。
原比較見 [kernel 方案比較](../../proposals/2026-10-02-kernel/02-方案比較.md)。

三項也保留了五項方案最有用的邊界。

- `inbox` 與 `think` 合成準備。
- `act` 與 `remember` 合成完成。
- LLM 保持獨立的 `kind:"llm"` 與結束碼。
- 沒有 kernel，就刪掉 summary。

這比一開始公開五個子命令，少承諾兩段接力介面。
它仍能在前置階段擋掉本格 LLM。

新增量應誠實計算。

| 項目 | 方案 A |
|---|---|
| 新 aos 公開命令 | 0 |
| tick／daemon 原始碼修改 | 0 |
| 新常駐服務 | 0 |
| 新範本腳本 | 3 |
| 新全隊政策程序 | 0 |
| 新共用協議 schema | 暫不建立 |
| 私有資料約定 | 仍有信封、session、usage、接力檔 |
| 額外執行依賴 | shell、jq、curl |

**「沒有新 CLI」不等於「沒有新程式」。**
私有格式也不等於沒有契約。
持久 JSON 仍應帶版本。
不能把複雜度藏在腳本裡，再稱為零成本。

#### 代價與邊緣狀況

**失敗接線仍不可省。**

tick 遇到任務非零，仍會跑下一項。
整格通常仍回 0。
所以 `call` 必須確認準備完成。
`finish` 必須確認本格呼叫成功。
不能靠 `stop_on_nonzero` 自動察覺模型失敗。
證據：[aos_tick.py](../../../src/py/lib/aos_tick.py)第 178–188 行。

**一次叫醒不是一件工作。**

`take` 一次取走整個信箱。
`wake` 只是一個布林待補旗標。
三封信可能只留下「補跑一次」。
已取到本地的剩餘工作，需要腳本自行續跑。
證據：[aos_daemon_mq.py](../../../src/py/lib/aos_daemon_mq.py)第 93–111 行；[aos_daemon_ctl.py](../../../src/py/lib/aos_daemon_ctl.py)第 173–176 行。

**中斷仍會留下不確定性。**

- take 後尚未落檔，可能丟信。
- HTTP 已送出但沒拿到回應，不知道服務端做到哪裡。
- 工具完成但 session 未寫完，可能重跑工具。
- 寄出答案後尚未標完成，可能重寄答案。

本輪不做自動重試。
先保存證據，由人決定續跑。
因此工具先限唯讀。
這不是已解決可靠執行。

**靜態額度會浪費。**

Alice 用完時，Bob 剩的額度不能自動借出。
兩人也可能同時計算。
固定呼叫數不能代表固定 token 或固定金額。

**同帳號不提供成員間隔離。**

專用投遞門只避免不必要的廣播。
現行 mq 可從任一可連的門取指定 inst 的信箱。
證據：[aos_daemon_mq.py](../../../src/py/lib/aos_daemon_mq.py)第 90–103 行。

**規模先限少量成員。**

省掉 kernel 不會省掉 daemon 每項一條執行緒。
證據：[aos_daemon_run.py](../../../src/py/lib/aos_daemon_run.py)第 181–182 行。
不能由兩人跑通推論萬人可用。

#### 要翻的裁定

**作為有限 POC，不必翻現行裁定。**

裁定 10 已把 kernel、agent 列為可掛上的任務。
裁定 11 要求行為發生在 tick 裡。
它沒有要求 agent 必須拆成五項。
見 [裁定 10 方向](../../verdicts/10-tick-minimal-core/01-方向.md)第 10–16 行；[裁定 11 方向與追答](../../verdicts/11-tick-as-unit/01-0930-方向與追答.md)第 5–18 行。

不做三種信，是不採尚未定案的提案契約。
不做 FUSE、namespace、`/llm/clone`，是不採這輪思想實驗。
兩者都不是翻已裁定的實作。

**若永久取消 kernel，就要翻裁定 09 方向 2、3，並重談方向 5。**
那是在放棄多層多 kernel、各層自定資源，以及上下層管理。
見 [裁定 09 方向](../../verdicts/09-special-computing-os/01-方向與審稿裁定.md)第 6–14 行。

長期記憶與通用工具也只是本輪不驗。
不宣稱撤銷它們原有的設計方向。

#### 最小實驗

時間盒：一天到兩天。

第一個半天用 fixture 代替 HTTP。
第一格回固定 `wc` tool call。
第二格回固定答案。
確認兩格後停止。

第二個半天換 curl。
各 agent 配三次呼叫。
完成一次真實的「工具 → 回答」。

第二天只驗幾個邊界。

| 實驗 | 看什麼 |
|---|---|
| 連寄三件工作 | 本地待辦會接續處理，不把叫醒次數當工作數。 |
| 第二次 HTTP 失敗 | 不重用第一次 response，不重跑舊工具。 |
| 工具回非零 | 下一輪 context 看得到失敗。 |
| 額度用完 | 不再呼叫，也不持續自叫空轉。 |
| 一人用完、另一人有餘額 | 記下靜態分額造成的閒置。 |
| 工具完成後中止 | 能看見證據，且沒有假裝已完成復原。 |

這輪真正要回答的是：
**沒有全隊政策，使用者的短任務是否已經能完成。**

### 方案 B：只在需要時，加一個讀檔與叫醒的薄 kernel

#### 長相

沿用方案 A。
多一個政策工作資料夾。
多一支 `policy.sh`。
不新增 `aos-kernel` 公開命令。

```text
policy/
  .aos/inst.json
  .aos/tasks.json
  members.json
  cursor.json
  policy.sh
```

政策任務只有一項。

```json
{
  "tasks": [
    {"id": "policy", "argv": ["sh", "policy.sh"]}
  ]
}
```

成員完成一格時，發布一份小型狀態快照。

```json
{"version": 1, "seq": 8, "ready": true, "calls_left": 2}
```

這裡的 `ready` 指「有工作，而且本地條件允許繼續」。
不是單純信箱非空。

政策一格只做四件事。

1. 讀固定名單與成員快照。
2. 用 `aos-ctl status` 查正在跑與待補的項。
3. 照固定輪流順序選人。
4. 用 `aos-ctl wake` 叫醒。

成員關掉自我續跑。
本地呼叫額度仍各自管理。
不做 grant 窗口。
不改 daemon 設定。
不需要 PID。

#### 比原提案好在哪

保留 kernel 作為政策角色。
但先不用政策通訊協議。

沒有 summary 寄送。
沒有 grant 消費。
沒有 request 分流。
沒有多層轉述。
只用本機檔案快照與現有控制介面。

這能先驗一個窄問題：
**在相同工作負載下，中央決定續跑順序有沒有價值。**

如果沒有差別，就不必急著把政策角色做成產品。
如果有差別，再抽出真正需要的政策與介面。

#### 代價與邊緣狀況

`running` 與 `pending` 都要占名額。
`wake` 收到就回覆。
成員可能尚未進入 running。

證據：[aos_daemon_ctl.py](../../../src/py/lib/aos_daemon_ctl.py)第 122–155、179–183 行；[aos_daemon_run.py](../../../src/py/lib/aos_daemon_run.py)第 98–108 行。

這仍不是全隊原子快照。
成員可能在查詢期間改變狀態。
外部來信也會另外叫醒它。
因此這個 kernel 只管自己主動派出的續跑。
它不保證所有開格或所有 LLM 的同時上限。

讀檔還帶來幾個代價。

- kernel 要知道成員狀態檔的位置與格式。
- 換帳號後，要補讀取權限。
- 狀態過時可能多叫一次空格。
- 輪詢增加一格左右的等待。
- 政策壞掉後，已落到成員本地的續作可能等住。

政策讀取或解析失敗時，這格停止新增叫醒。
不為這個實驗造自動救援。

#### 要翻的裁定

**不必翻。**

政策是一個程式。
掛在 tick 任務表上。
只在 tick 裡執行。
直接符合 [裁定 11 排程原則](../../verdicts/11-tick-as-unit/01-0930-方向與追答.md)第 14–18 行。

push summary 改成讀本地快照，是提案選項的改變。
它不是翻既有裁定。

本輪仍延後多層。
若把「kernel 永遠可讀所有下層內部檔案」升成方向，才需要重新檢查 [裁定 09 的分層邊界](../../verdicts/09-special-computing-os/01-方向與審稿裁定.md)第 12–14 行。
所以这里只讀成員刻意發布的快照。

#### 最小實驗

時間盒：一天。

沿用方案 A 的兩個假成員。
讓兩者都有續作。
每格執行時間故意長於政策週期。

比較有無 `policy.sh` 的：

- 同時執行數。
- 各人的等待格數。
- 完成時間。
- 空格數。
- 額度閒置量。

再寄一封外部信給未獲選的成員。
觀察它仍然會開格。
這能讓「限制主動派工」的邊界直接可見。

### 方案 C：絕對最少，一格只跑一支 `step.sh`

#### 長相

沿用方案 A 的 daemon、資料夾與有限功能。
三支腳本合成一支。
任務表只放一項。

```json
{
  "tasks": [
    {"id": "step", "argv": ["sh", "../../recipe/step.sh"]}
  ]
}
```

脚本依序收信、組請求、扣額、呼叫、執行工具、記憶、回信。
前一步失敗就不進入依賴它的下一步。
仍然每格最多一次模型呼叫。

#### 比原提案好在哪

**這是新增程式邊界最少的版本。**

只新增一支私有腳本。
不公開五個子命令。
不需要在不同任務之間發布成功標記。
request、response 仍可留檔供查看。

如果目的只是一兩天內讓使用者試玩，這條路成立。
「五項」不是 tick 的必要條件。

#### 代價與邊緣狀況

tick 只看得到整步成敗。
不能獨立跳過內部 LLM 階段，再繼續跑工具或記憶階段。
`kind:"llm"` 若標在整步上，擋住的會是整步。

HTTP 中斷、工具副作用與訊息遺失仍然存在。
合檔沒有消除這些窗口。

要保留原提案全部能力時，一支腳本會迅速長大。
因此它只適合有明確功能上限的原型。

#### 要翻的裁定

**不必翻。**

它仍以 tick 為單位。
沒有常駐 agent。
也沒有背景程序繞過 tick。

五項或一項仍是 [agent 待決問題](../../proposals/2026-10-02-agent/09-待決問題.md)第 2 題。
不能把提案推薦五項，當成使用者已裁定五項。

永久無 kernel 的翻案範圍與方案 A 相同。

#### 最小實驗

時間盒：半天到一天。

先完成固定 fixture 的兩格工具對話。
再換一次真 HTTP。
只檢查整步失敗時的證據是否足夠。

若使用者開始需要「只擋 LLM」或「分別觀察模型與工具錯誤」，才拆成方案 A 的三項。

### 最小版與原提案的功能差距

下表以方案 A 為主。
「延後」不是宣稱不需要。
它表示這輪不以該功能作為驗收。

| 能力 | 原提案 | 最小版的處置與損失 |
|---|---|---|
| 收信、叫醒、回話 | 既有 mq／ctl 接線 | 保留。固定投遞門與回信目的地。 |
| 一格最多一次 LLM | 五項 agent 流程 | 保留。三項流程。 |
| 工具執行 | 通用工具表與 `_inst` | 先一個固定唯讀工具。失去任意工具擴充與通用參數處理。 |
| 多工具呼叫 | 一個回應可依序跑多個 | 延後。第一版只接受零或一個。其餘明確報錯。 |
| 多封待辦 | 一格一封，持續處理 | 保留本地排隊。先一個進行中的對話。 |
| 長期記憶 | notes、壓縮、封存 | 延後。只驗短對話。達實驗長度上限就停。 |
| 每人呼叫額度 | kernel grant 窗口 | 改整場固定分額。不能借調或自動補額。 |
| token／金額管理 | 有用量與額度規劃 | 先只觀察。呼叫數不等於金額上限。 |
| 全隊派工順序 | kernel 決定 | A 沒有。B 才加入續跑順序。 |
| 所有計算的硬並行限制 | 原案也不能靠少寄 grant 保證 | 不提供。來信仍能叫醒。 |
| 不可繞過的 LLM 額度 | 原案先採自律 | 同樣沒有。agent 仍可直接使用金鑰。 |
| 動態成員與資源調整 | 改設定、SIGHUP、預留門或重開 | 延後。固定名單。省去自動套用與 PID 接線。 |
| 多層摘要與授權 | summary／grant／request | 延後。没有驗到分層政策。 |
| 帳號隔離、cgroup | 既有模組接入 | 最小示範先不掛。失去成員隔離與資源框保證；需要時可用現有模組補靜態部署。 |
| git 歷史 | hooks | 延後。只有工作證據檔，沒有每格 git 復原點。 |
| 訊息持久化、可靠恢復 | 原案也未提供完整保證 | 不提供。接受遺失與重複窗口。 |
| namespace | Plan 9 檔位 1 | 延後。沒有固定虛擬路徑與入口可見性限制。 |
| FUSE、`/llm/clone` | 思想實驗 | 延後。沒有檔案式服務介面，也不新增相關常駐服務。 |

這個差距表也指出了 kernel 的必要條件。

**固定分配可以由人與設定檔表達。**
只有當系統需要根據新狀況重新分配，才需要執行中的政策角色。
例如某人有剩餘額度、另一人被卡住。
或兩件工作爭同一資源，需要有人決定先後。

原提案本來也保留無 kernel 的對照實驗。
見 [kernel 分階段第 0 階段](../../proposals/2026-10-02-kernel/05-分階段落地.md)與 [agent 分階段第 2 階段](../../proposals/2026-10-02-agent/08-分階段.md)。
這條減法路線，是讓那個對照先成為完整可玩的版本。

## 不換方向的改良

1. **正式命令晚於第二個使用案例。**  
   先用範本腳本。
   等另一種 agent 或另一種政策也需要相同能力，再抽 `aos-llm`、`aos-agent`、`aos-kernel`。
   抽出的應是重複能力，不是預想中的分層。

2. **假模型先用 fixture 任務。**  
   在任務表把 HTTP 項換成複製固定回應。
   不必為第一次流程實驗先做 `fake:` URL 與劇本引擎。

3. **額度檢查放在真正呼叫前。**  
   前置任務可寫 `tasks-blocked`。
   `call` 自己也應確認本地額度。
   不要用 `before_kind.llm` 寫檔來擋當次。
   現行順序是先查擋板，才跑該 hook。
   證據：[aos_tick.py](../../../src/py/lib/aos_tick.py)第 163–178 行。

4. **固定部署不掛 reload。**  
   沒有動態成員、沒有動態資源，就沒有取 PID 與送 SIGHUP 的需求。
   這是刪掉需求，不是另造一種 PID 發現機制。

5. **按現行程式計算待造項目。**  
   現在 `give_env()` 已先清除繼承的 `AOS_DAEMON_*`，再設定本層值。
   不應再把昨天的環境外漏修補算成必要新工作。
   證據：[aos_daemon_run.py](../../../src/py/lib/aos_daemon_run.py)第 163–178 行。

6. **用新狀態與新分支衡量減法。**  
   檔案數少，不代表狀態少。
   比較時應列出窗口、待授權、待回報、待重試等狀態是否真的消失。
   三支短腳本可能比一支包辦全部的腳本更容易理解。

## 試過但放棄的想法（各一兩句）

- **用共用額度檔取代 kernel。**  
  它又引入多人記帳與鎖。固定分額更適合這輪。

- **把原提案全部改寫成 shell／jq。**  
  窗口、授權、摘要與多層狀態一樣都要處理。那是換語言，不是減法。

- **把全部 agent 串在同一個父 tick。**  
  能省派工，也會改變個別叫醒、身分與 daemon 資源框的粒度。不是原有 agent 模型的免費替換。

- **先做 FUSE，讓 CLI 看起來消失。**  
  客戶端命令少了，服務端介面與生命週期管理卻增加。這輪想驗的是 agent 工作能力，收益不對題。

- **直接接常駐 agent 迴圈。**  
  會繞過格的界線。要翻 [裁定 11「不准背景程序繞過 tick」](../../verdicts/11-tick-as-unit/01-0930-方向與追答.md)第 16 行，代價過大。

- **為半途中斷先做完整交易與重試。**  
  那會把短任務原型變成可靠工作流引擎。現行 [POC 裁定](../../verdicts/11-tick-as-unit/03-1001-POC默認一切正常.md)第 7–14 行允許先不做；本輪應揭露窗口，而不是偷偷擴工。
