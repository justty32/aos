## 一段話結論

我支持保留這四層。
它把運行機制、推進單位、資源政策、agent 行為分開，方向成立。
目前需要收窄的是三個承諾：「完全脫離 Linux」、「tick 有固定時間長度」、「kernel 管資源就能強制限制資源」。
daemon 減法也成立，但移出去的責任要有明確去處。
我傾向先補清各層的少量契約，再試 FUSE 與 kernel。
不需要為了讓「時空」比喻完整，先造全域時鐘、通用交易或完整恢復系統。

本文把 [10-03 分層想法](../2026-10-03-aos-layering.md)視為尚未裁定的方向。
現況以程式與現行 spec 為準。
提案與既有報告只當選項。
本次全程唯讀，未改檔、未 commit、未執行 build 或測試。

## 站得住的地方

- **政策放 kernel，機制放運行層，是好的分工。**  
  daemon 提供執行機會。
  kernel 決定把機會給誰。
  daemon 跑 tick、tick 跑 kernel、kernel 再控制 daemon，是正常的控制回饋。
  這不構成架構上的循環矛盾。
  既有裁定也把排程政策放在 tick 任務表上。
  見 [裁定 11／方向與追答](../verdicts/11-tick-as-unit/01-0930-方向與追答.md)，第 14–18 行。

- **檔案系統與 tick 是足夠小、也能實際使用的基底。**  
  檔案讓狀態有位置。
  tick 讓行為有推進點。
  現行核心已能獨立提供互斥、照表執行與紀錄。
  它不必先有 kernel 或 agent。
  見 [tick 核心](../../spec/tick.md)，第 9–19 行。

- **多層 kernel 不必綁成多層 daemon。**  
  政策上的上下層，可以跨越平行的 daemon。
  同一 daemon 也可以承載多層 kernel。
  需要不同帳號時，再切成不同部署實例。
  這符合「各 kernel 可以有不同資源定義」的原意。
  見 [特殊計算 OS 裁定](../verdicts/09-special-computing-os/01-方向與審稿裁定.md)，第 6–14 行。

- **agent 放最後，可以避免底層被某一種 agent 寫法綁住。**  
  一格一次 LLM、一次完整回合，或固定 worker 接工作，都可以是上層選擇。
  但它們不必成為 tick 的定義。
  [agent 提案](../proposals/2026-10-02-agent/README.md)第 9 行也保留了這個邊界。

- **新分層讓 FUSE 有了更直接的理由。**  
  如果目標是讓檔案操作成為 aos 的共同介面，FUSE 的價值確實增加。
  先前「先讓 agent 跑起來，暫時不做 FUSE」的建議，不能直接拿來否定現在的目的。
  [Plan 9 替代報告](2026-10-03-astra-alt/03-plan9-alt.md)第 22–28 行也承認，純檔案客戶端是支持 FUSE 的理由。

## 矛盾與缺口

### 1. 「運行層」可以隔開 Linux 知識，但不宜等同於 daemon 這一支程式

**問題。**

目前 Linux 相依不只存在於 daemon。
inst 本身就包含程序、工作目錄、環境、串流與結束碼。
tick 也直接啟動程序。

**為什麼重要。**

如果「完全脫離 Linux」是說 kernel 的政策不需要理解 PID、UID 或訊號，這做得到。
如果它表示上層任務完全沒有 Linux 語義，就與保留任意 POSIX inst 有衝突。
FUSE 只改操作入口，不會自動消除這個差異。

**證據或推演。**

[inst 規格](../../spec/inst.md)第 5–11、33–42 行公開了這些宿主概念。
[tick 執行單項](../../src/py/lib/aos_tick_run.py)第 58–88 行仍配置環境、串流並等待子程序。

這些概念不必全部漏進 kernel 政策，但都需要某處承擔：

| Linux 概念 | aos 上層可使用的說法 | 仍須承擔的責任 |
|---|---|---|
| 程序、PID | 一次執行、執行結果 | 啟動、等待、辨認哪次執行 |
| UID、權限 | 某個執行域可用的能力 | 實際身分、檔案與控制入口的存取 |
| 訊號 | 取消請求、停止結果 | 是否能取消、取消到什麼範圍 |
| fd、串流 | 輸入、輸出、結果 | 關閉時機、EOF、阻塞與輸出收尾 |
| cwd | 工作位置、相對路徑起點 | 路徑解析與每次執行的上下文 |
| env | 執行參數、入口位置 | 哪些值繼承、哪些值屬於本次執行 |
| 宿主時間 | 外部期限、定期觸發 | 真實經過時間與外部服務逾時 |

**建議的調整或選項。**

我較傾向把「運行層」定成一組責任。
它可以包含 daemon、FUSE 介面與 POSIX 執行轉接。
不必全塞進同一支 daemon。

kernel 只依賴 aos 的操作與結果。
任意 POSIX 工具則明列為接觸外部世界的入口。
這能保留現有 inst，也保留上層抽象的自由。

另一條路是限制上層只能執行 aos 定義的任務。
抽象會更完整。
代價是要另定任務模型與相容方式。
這已超過單純 FUSE 化。

### 2. tick 作為動作很清楚，作為固定時間長度則與現行規則衝突

**問題。**

目前「十個 tick」同時帶有兩種意思。
一種是做十次動作。
另一種是經過十個週期。

**為什麼重要。**

這會直接影響預算窗口、保留期與重試間隔。
即使完全沒有故障，兩種意思也會分開。

**證據或推演。**

[裁定 11／方向與追答](../verdicts/11-tick-as-unit/01-0930-方向與追答.md)第 12 行說，十格約等於十個 `interval_ms`。
但 [最核心 daemon 裁定](../verdicts/11-tick-as-unit/07-1001-最核心daemon.md)第 13 行規定，週期從上一格結束後起算。
[第二十五批](../verdicts/11-tick-as-unit/26-1002-第二十五批.md)第 32 行又讓訊息觸發額外叫醒。

例如一格跑三十秒，結束後再等一秒。
十格不會約等於十秒。
反過來，大量訊息可以讓 kernel 提早多跑幾格。
如果額度每十格更新，來信量就會影響額度更新速度。

此外，`seq` 在開格時增加。
它不是成功完成次數。
見 [紀錄實作](../../src/py/lib/aos_tick_record.py)，第 98–108 行。

**建議的調整或選項。**

我較傾向把 tick 定成「某個時域的一次推進」。
`seq` 記錄開過幾格。
「上層給十格」表示上層再推進十次。
daemon 週期只決定何時觸發。
外部逾時繼續使用真實時間。

這要明確修訂裁定 11 第 12 行的「標準長度」說法。
不必翻掉第 13、15、17 行的上層格數與外界時間例外。

另一個選項是另設純時鐘 tick。
急件叫醒工作，但不推進那個時鐘。
這保留時間窗口的直覺。
代價是多出兩種推進來源。

### 3. 「空間＋時間」還需要公開狀態的讀寫約定

**問題。**

檔案位置不等於資料版本。
同一格讀到的多個檔案，也不一定屬於同一時刻。
兩個資料夾的第 20 格沒有天然的先後關係。

**為什麼重要。**

kernel 要根據成員狀態派工。
若沒有說清楚它讀到的是什麼，很容易把普通檔案誤當成全隊快照。
這是正常並行就會遇到的問題。

**證據或推演。**

現行互斥只保護同一工作資料夾。
開格固定的是任務表展開結果。
它沒有凍結任務稍後讀取的普通檔案。
見 [tick 核心](../../spec/tick.md)，第 13–22 行。

紀錄也分檔更新。
讀取者先讀主檔，再展開其他檔。
因此可以跨過另一次更新。
見 [紀錄實作](../../src/py/lib/aos_tick_record.py)，第 42–50、125–130 行。

兩個 daemon 即使共用檔案系統，也不會因此取得共同時鐘。
A 的第 20 格讀到了 B 的第 8 格結果，才是一條有用的因果關係。
單獨比較 20 與 8 沒有意義。

**建議的調整或選項。**

先補三個便宜的約定：

- 每份公開狀態由誰負責寫。
- 一份結果何時算發布完成。
- 結果如何標明來源與版本。

kernel 可以接受不同時刻產生的成員摘要。
只要不要宣稱它們是同時快照。

若之後需要「所有 agent 看同一版世界」，再採共同版本與發布者。
那是 [整體另想方案 B](2026-10-03-astra-alt/04-whole-redesign.md)的額外能力。
不應因為用了「時空」這個詞，就自動加進核心。

### 4. 檔案系統加 tick 足以承載排程政策，但不會自動提供強制力

**問題。**

kernel 可以決定誰該做事。
但它能否阻止其他人做事，取決於是否掌握不可繞過的入口。

**為什麼重要。**

「最多叫醒兩個」與「最多同時執行兩個」是不同保證。
「不再給額度」與「已開始的工作不能超額」也是不同保證。

**證據或推演。**

[kernel 推薦方案](../proposals/2026-10-02-kernel/03-推薦方案.md)第 72–80 行已承認，只限制 kernel 主動叫醒的格。
成員收到其他訊息仍會開格。

同一份提案把 CPU、記憶體與程序數交給 cgroup。
LLM 額度則由 agent 自律。
見 [kernel 與 agent 介面](../proposals/2026-10-02-kernel/04-agent介面.md)，第 33–41 行。

因此 daemon 減法後，可以保留的能力如下：

| 責任 | 減法後可由誰承擔 | 缺少它時的實際保證 |
|---|---|---|
| 決定優先序、分配額度 | kernel | 可做政策與合作式派工 |
| 記錄實際用量 | 執行者或服務入口 | 只能根據回報估計 |
| 強制 CPU、記憶體、程序數上限 | 外部部署或可選執行機制 | kernel 無法只靠檔案強制 |
| 選擇 Linux 帳號 | 啟動 daemon 的部署者 | 同一 daemon 沿用啟動身分 |
| 限制誰能讀寫控制入口 | 宿主存取機制與部署設定 | 路徑名稱本身不提供隔離 |
| 等待直接子程序、取得結果 | 執行轉接層 | 無法可靠判定一次執行結束 |
| 清除殘留後代 | 任務自己或外部清理者 | 完成後仍可能有程序存活 |

把硬上限放外面，本來就是容許的選項。
[特殊計算 OS 裁定](../verdicts/09-special-computing-os/01-方向與審稿裁定.md)第 33–35 行已區分政策額度與部署硬上限。

**建議的調整或選項。**

每種資源只需明講誰分配、誰量測、誰強制。
沒有強制者，就叫合作式限制。
這不是失敗，而是清楚的保證範圍。

若只想限制昂貴的 LLM 計算，可以在 LLM 執行前檢查 grant。
其他訊息仍可叫醒 agent 收信。
這不必改掉收到訊息就叫醒的裁定。

若想限制所有 tick 的同時數，才需要所有開格都經過准入點。
這會碰到第二十五批的叫醒規則。
不能只改 kernel，就聲稱所有入口都被限制。

### 5. 政策層次、資料夾層次與 daemon 層次需要分開

**問題。**

10-02 提案把 kernel、它擁有的 daemon 設定、下層 daemon 綁得很緊。
新方向則讓 daemon 互不從屬。
兩套模型不能原封不動地疊在一起。

**為什麼重要。**

可瀏覽的目錄父子關係，不自然等於權限父子關係。
也不自然等於整組停止或資源上限的範圍。

**證據或推演。**

[kernel 推薦方案](../proposals/2026-10-02-kernel/03-推薦方案.md)第 84–102 行，以 daemon 跑 daemon 實現上下層。
[Plan 9 的 daemon 跑 daemon](../proposals/2026-10-02-plan9/10-daemon跑daemon.md)第 5、45–52 行，又依賴私有 namespace、上層控制與 cgroup 清理。

這些能力不是掛上 FUSE 就自然得到。
減法後，也不能繼續把它們算作免費保留。

**建議的調整或選項。**

分開描述三件事：

- 工作資料放在哪裡。
- 哪個 daemon 執行哪些工作。
- 哪個 kernel 對哪些成員分配資源。

政策樹可以跨 daemon。
不同 kernel 也可以共用 daemon。
這與 [kernel 替代報告](2026-10-03-astra-alt/01-kernel-alt.md)第 5–11 行一致。

另外補一條最小啟動契約。
哪個 kernel 由誰首次喚起。
它靠什麼再次獲得執行機會。
不能讓 kernel 必須先批准自己，自己才有機會執行。
保留現行週期或外部觸發都可以。
不需要再造一個更上層排程器。

## 實作時會咬人的地方

### 1. tick 改成 lib，不只是把 CLI 包一層

現行 `run_tick()` 會呼叫 `os.chdir(cwd)`。
多個 tick 放進同一程序後，不能再把工作目錄當成各自獨有。
需要顯式傳遞路徑與執行上下文。
環境變數也應按次組裝。

這是 lib 邊界要改的責任。
它不是選 thread 或程序的結論。
見 [aos_tick.py](../../src/py/lib/aos_tick.py)，第 129–141 行。

### 2. thread 的鎖不能保留跨 daemon 的互斥保證

同程序鎖可以簡化同一 daemon 內的協調。
但另一個 daemon 不會拿到同一把鎖。

如果接受兩個 daemon 同跑一個資料夾，就可以把那種情況列為不保證。
但不能同時宣稱原本「同一資料夾一次一格」仍完整成立。
兩邊還會共用 `current`、`last` 與暫存目錄。
見 [tick 互斥契約](../../spec/tick.md)，第 13–15 行，以及 [紀錄輪換](../../src/py/lib/aos_tick_record.py)，第 98–123 行。

### 3. `echo do > d/tick` 的成功，不應含糊

寫入成功可以表示命令被接受。
也可以表示整格已完成。
這兩種介面會導出完全不同的等待行為。

我較傾向先採「接受命令」。
完成狀態另外讀。
若仍保留合併叫醒，寫十次不保證跑十格。
kernel 也不能用寫入次數當成完成次數。

控制檔還需定義完整命令的邊界。
不能把每個收到的 write 區塊都當成一條命令。
這點原提案已指出。
見 [Plan 9 檔案伺服器](../proposals/2026-10-02-plan9/03-daemon變成檔案伺服器.md)，第 82、88–96 行。

### 4. `.aos/d` 是地址，`me` 不會自動成為本次執行身分

共享目錄裡的普通連結只能指向一個固定目標。
同一資料夾由兩個 daemon 啟動時，它無法同時代表兩個啟動來源。

可選固定配置、顯式傳入本次 item 路徑，或每任務獨立 namespace。
三者的成本不同。
舊提案的 `self` 靠的是第三種。
見 [Plan 9 檔案伺服器](../proposals/2026-10-02-plan9/03-daemon變成檔案伺服器.md)，第 39–45 行。

`me` 也不應被當成授權證明。
若改成每項只能控制自己，就是新增權限規則。
這會改變 [第二十五批追加裁定](../verdicts/11-tick-as-unit/26-1002-第二十五批.md)第 60–66 行的「能連就能控制別項」。

### 5. FUSE handler 與 tick 可能互相等待

推演一個情況：
handler 等 tick 做完才回應。
tick 又寫 daemon 的控制檔。
若服務執行緒或所需鎖被前者占住，就可能形成循環等待。

同程序本身不代表必然死鎖。
重點是等待關係與鎖。
daemon 內部可以直接呼叫同一套控制函式。
外部再透過 FUSE 進入。

[Plan 9 daemon 跑 daemon](../proposals/2026-10-02-plan9/10-daemon跑daemon.md)第 50 行已提醒自讀與轉送風險。
但「絕不能讀自己的樹」不宜當成所有情況的定律。

### 6. 不清後代，可能連「這次完成」都等不到

現行 daemon 在直接子程序退出後，還會等待輸出 reader。
若殘留後代握著輸出 pipe，reader 可能一直等不到 EOF。
該項就一直維持 `running`。
見 [aos_daemon_run.py](../../src/py/lib/aos_daemon_run.py)，第 20–23、48–62 行。

所以「等待直接子程序」、「收集輸出」、「清除後代」要分開定義。
可以把完成判定交給執行轉接層。
也可以直接寫日誌檔，或限制輸出收尾等待。
不必因此把整套 cgroup 管理搬回 daemon。

### 7. daemon 重開，不等於舊工作已結束

現行 daemon 退出時不殺正在跑的工作。
state 又只保存暫停與已停狀態。
它不是執行中工作的接續紀錄。
見 [daemon 核心](../../spec/daemon/core.md)，第 17 行，以及 [state 契約](../../spec/daemon/state.md)，第 13 行。

重開細節可以繼續暫緩。
但未來需選定：舊工作未知、外部先清乾淨，或自動接手。
掛載點重新出現，不足以證明先前命令完成。
這與是否處理兩個獨立 daemon 搶同一資料夾，是不同問題。

另外，FUSE 連線已關閉與 daemon 活著但不回應，要分開看。
後者可能讓操作持續等待。
停止或恢復入口因此不能只存在於那棵失去回應的樹內。

## 問使用者的問題

這些是影響承諾範圍的方向題。
不是要求現在全部回答。
thread／程序、daemon 是否只收 tick、kill／restart 是否保留，維持原本待定。

| 題 | 選項與後果 | 建議 |
|---|---|---|
| 「脫離 Linux」要到哪裡？ | 政策不懂 Linux：可保留 POSIX 工具。所有任務都不懂 Linux：需另定受限執行模型。 | 先以政策層獨立為目標。 |
| 十個 tick 代表什麼？ | 十次推進：會受工作長度與額外叫醒影響。十個時間週期：需分開時鐘與工作叫醒。 | 採局部推進，明改舊標準長度說法。 |
| kernel 最先要限制哪個量？ | 主動派工數：最便宜。昂貴計算數：在計算入口准入。所有 tick：需統一開格入口。 | 先挑一種昂貴計算，不先承諾管住所有 tick。 |
| 同一 daemon 是否是一個互信執行域？ | 是：帳號與授權較簡單。否：需要逐項隔離與控制權限。 | 減法版先按互信域理解。跨域再分 daemon。 |
| agent 是否一定要有 kernel 才能運行？ | 一定要：較容易統一政策，但啟動鏈更長。可以沒有：能先固定分配，也能做有無 kernel 的對照。 | 保留直接使用 tick 的能力。需要動態分配時再接 kernel。 |
| 近期最想驗哪個價值？ | 檔案化操作：先試 FUSE。特殊計算分配：先試薄 kernel。agent 工作能力：先試有限任務鏈。 | 依這次最想親手體驗的能力選一條，不把三條綁成一次大改。 |
