## 2. 實作教會我們的事

以下編號都指 [findings](findings.md)。

**① rename 不能當鎖（#1、8～10、19）。** 同名 rename 會覆蓋，交件、認領、收屍要共用短鎖，真正做工作時放鎖。認領時重設時間，才不會把排隊很久的單當死單；發布前再核對，擋掉已被收屍的遲到回覆。兩種 CPU 共用這套機制，一格可收多份過期單、最多做一份新單；代價是所有交件者都得守同一把鎖。

**② 先驗完，再動檔（#5、14～16、20～21、32）。** 結果要全驗完才清等待、跑同步工具。讀不出回覆路徑的壞請求只能留原位報錯；有地址才回失敗結果。型別、私有設定、壞編碼要分清楚，代價是驗證較細，避免把格式錯誤當模型失敗或產生副作用。

**③ 逾時要有旗標，暫停要能再用（#3～4、6、25）。** 退出碼 143 不代表逾時，要另記旗標；CPU 回報成功也不表示工具成功。三敗暫停前要封存舊 continue.json，否則第二次會自己解鎖。errors 只收非負整數，送件不算成功；目前 CPU 工具逾時不把已收輸出給模型，與同步工具不同。

**④ 能補收尾，不等於只做一次（#11～13、18、22～23、26）。** 工具批次完整寫進記憶後，可以補收尾，避免重吃結果。送件、記等待、寫記憶不會一起成功或失敗，中斷可能重送、串單或永遠等。請求編號能辨認歸屬，還需送件恢復與消費紀錄，才能處理「恰好一次」。這輪只評估、沒做一般對帳，以少狀態換取人工處理中斷。

**⑤ 停機要砍到孫程序（#28～29、33～34）。** 工具另開 session，Linux 得找後代群組一起 TERM、兩秒後 KILL。daemon 同時停所有 runner，清乾淨才回成功；先寫回音再刪請求，仍救不了「已啟動、未寫回音」的崩潰。kernel 不套工作限時，rm 等本次結束；代價是不能緊急停止，逃離親子樹的程序也未必抓得到。

**⑥ 防重疊還要防有人永遠輪不到（#27、30、35）。** running=false 可能過期，換人還得拿槽位鎖、等舊 runner 真退出。短間隔搶不到空檔，就要求 runner 做完先等交接；代價是換人重建 runner，kernel 中途死掉要補跑 tick。連敗跟行程走，但只存最後退出碼，可能漏掉中間結果。

**⑦ 解好指令，不等於拍下整份環境（#24、31）。** 路徑與引用要在來源家解好再搬，否則意思會變。未清空的環境與 PATH 仍繼承 CPU；真跑驗到 CPU 值與 agent 解析值並存。要固定就明寫環境；add 後引用不再跟原檔更新。

**⑧ 驗證數字要講清楚（#2、7、17）。** 新契約改了行為，就更新衝突斷言，不能刪測試。根 build 快取指錯路徑，因此從根用同 default 配置、另放 proto5.1/.build，跑過八個 C++ 測試。修改與文件留在 proto5.1；根快取仍未修好。

## 4. KISS 之下先接受、以後可能要回頭的洞

- 沒有請求對帳與跨檔交易，中斷可能串單、重做或漏計錯誤（#11～13、23、26）。
- 排隊與等待沒期限，半批沒送完可能永遠等（#8、23）。
- 收屍不等於殺掉原工作，HTTP 慢慢回資料也可能超過名義時限（#9、23）。
- API key 明文留在請求與 done；沒強制落盤，不承諾斷電保存（#16）。
- 另開入口同時跑同一 agent，仍沒有 agent 自己的並行鎖（第二段回報）。
- daemon 不自動收養崩潰留下的 runner，終止也抓不到所有逃離親子樹的程序（#28～29）。
- 排程只看最後結果，可能漏中間退出碼；kernel 死在交接途中會讓 runner 等補跑 tick（#30、35）。

## 5. 建議下一步

1. 試跑實際任務，確認工具副作用是否必須依序發生。
2. 要崩潰後自動續跑，再決定是否加請求身分、送件恢復與消費紀錄。
3. 放入真實 API key 前，決定是否接受明文留存。
