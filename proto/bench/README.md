# bench：可預測性的兩把尺

這是量尺，不是測試。它不判斷「對不對」，只回答「同一件事講的跟做的差多少、做很多次散多開」。

尺是使用者拍板的正式指標（[構想集 01 章](../../wf/workflows/ideas/01-what-and-goals.md) A-04）：可預測性最優先，而可預測性今天有兩個現成量得到的落點。

- **尺①　自報 vs 實際**：一支串在原稿裡自報「要走幾格、要跑幾筆指令、要打幾次 LLM」，跟實際跑出來的差多少。
- **尺②　分布寬度**：同一支串跑五次，格數、牆鐘秒、指令數、token 各自散多開。

這裡只有第一版，量得到什麼就量什麼；量不到的記在最後一節「原型缺什麼」。

## 怎麼跑

```sh
python3 proto/bench/run.py                       # 三支串各跑五次
python3 proto/bench/run.py --runs 3              # 改成各跑三次
python3 proto/bench/run.py --series a-inst,c-llm # 只跑其中幾支
python3 proto/bench/run.py --keep                # 留下每次的暫存家，好事後翻現場
python3 proto/bench/run.py --out /tmp/xxx        # 換輸出目錄
```

不用裝任何東西（純標準庫，Python 3.11+）。每一次跑都會：

1. 開一個全新的暫存目錄，把那支串整個複製進去；
2. 把 `AOS_HOME` 指到那個暫存目錄底下的 `home/`（**不碰使用者的 `~`**）；
3. `aos init` 每一塊地；需要 LLM 的那支再 `aos llm init` 並把處理單元改成假後端；
4. 計時，跑 `aos run <地> --until idle --budget 500 --json`；
5. 收數字，把暫存目錄刪掉（除非 `--keep`）。

**假後端不打網路。** LLM 世界的兩個處理單元被改成 `slow:40`（tier `fast`）與 `slow:180`（tier `smart`），也就是睡指定毫秒再把 prompt 原樣回。真後端要自己改 `$AOS_HOME/.aos/config.json`，bench 不做這件事。

輸出在 `proto/bench/results/<時間>/`：

- `raw.jsonl`：一次跑一行，所有原始欄位都在（含暫存目錄路徑、`stderr` 尾巴、接力棒的 `resources` 欄長什麼樣）。
- `summary.md`：一張表——串｜尺｜自報｜實際五次｜最大最小差｜結論一句，外加「跑成功了沒」「哪支最不穩」「自報值今天躺在哪」三節。

## 三支固定的串

| 資料夾 | 是什麼 | 用到的地 | 要不要 LLM 世界 |
| --- | --- | --- | --- |
| `series/a-inst` | 10 步 `inst`，每步 `/bin/sh` 往堆疊框裡追加一行，全確定 | 1 塊 | 不要 |
| `series/b-call` | 父地 `call` `sync` 子地；子地 5 步，最後一步把結果寫到父指定的 `$AOS_RESULT` | 2 塊（父＋子） | 不要 |
| `series/c-llm` | `prep` 寫三筆請求 → 三步 `aos deliver` 投給 LLM 世界 → 三個 `await` → 收尾把三段回話併起來 | 1 塊＋LLM 世界 | 要 |

自報值就寫在各自 `main.aos.json` 的**頂層 `resources`**：

```json
{"format_version": 1, "name": "main",
 "resources": {"ticks": 10, "insts": 10, "llm_calls": 0, "note": "…"},
 "steps": [ … ]}
```

自報是**寫串的人估的**，不是量完回填的。例如 (a) 自報 10 格，理由是「十步，一步一格」——實際會是 11 格，那一格的差就是尺①要看的東西。

## 兩把尺怎麼算

### 收哪些數字

| 數字 | 從哪來 | 註 |
| --- | --- | --- |
| 格數 | `aos run --json` 的 `ticks` | 這趟 run 一共走了幾格 |
| 牆鐘秒 | bench 自己包在 `aos run` 這支子行程外面計時 | 不含 `init`／`llm init`／起 serve 的準備時間 |
| 指令數 | 數 `.aos/ticks/<N>/insts/*.json` 的檔數，父地＋子地相加 | 原型沒有計數器，只能數檔 |
| 有動作的格數 | 數 `.aos/ticks/<N>/` 的目錄數 | 只有真的跑了指令的格才有目錄，所以它≠格數；只寫進 `raw.jsonl` |
| LLM 次數／token | 帳簿 `$AOS_HOME/.aos/ledger.jsonl` 的行數與 `tokens_in`＋`tokens_out` 總和 | 假後端的 token 是**估的**（非空白字元數 ÷ 4），不是真的 |
| 成功／失敗 | `aos run` 的退出碼＝0、`reason`＝`idle`、且接力棒裡每條串都 `done` | 三個條件都成立才算成功 |

### 尺①：自報 vs 實際

一行一個指標：`自報值`（原稿寫的）對上 `五次的實際值`。結論句只講三種情況：

- 五次都一樣、而且等於自報 → 自報準。
- 五次都一樣、但跟自報差一個固定數 → **固定偏差**，那是自報公式漏算的常數，補進公式就準了。
- 五次不一樣 → 自報用「一個數字」根本講不完，該改成範圍或上界。

### 尺②：分布寬度

同一支串跑五次，取 `最大 − 最小`（表裡的「最大最小差」），再除以中位數得到**相對寬度**。分級：

- 差＝0 → 完全可預測。
- 相對寬度 < 5% → 可以當常數看。
- 5% ~ 25% → 會晃，但還在一個量級。
- \> 25% → 不穩，別拿它當保證。

「哪支最不穩」那節就是拿**牆鐘秒的相對寬度**排序。用牆鐘不用格數，是因為格數在原型裡是純確定性的（見下一節）。

## 數字怎麼讀

三件事先知道，不然表會看錯。

**一、格數永遠比自報多一格（至少）。** `aos run` 要多走一格才發現「沒有 running 的串了」，這一格不做任何事，但照樣計入 `ticks`。所以任何串的實際格數 = 自報 + 1（起碼）。這不是 bug，是「閒著」的偵測方式；但它代表**自報公式必須知道 run 的實作細節**才寫得準，這件事本身是個訊號。

**二、牆鐘秒大部分不是在做事，是在睡。** `aos run` 沒給 `--every` 時，只要有串停在 `await` 或同步 `call` 等結果，就固定睡 100 毫秒（`aosp/run.py` 的 `_WAIT_NAP_MS`）。(b) 一趟 6 筆指令總共不到 20 毫秒，牆鐘卻要 0.45 秒——0.4 秒全是那四次等待睡眠。**所以牆鐘秒在今天的原型裡量的是「等了幾次」，不是「花了多少力氣」。** 要量力氣，看指令數與 token。

(c) 那支的差是 +4 不是 +1，因為 `await` 不是「等一格」——父地的鐘跟 LLM 世界的鐘各走各的，父要多輪詢幾格才等到回話。**這個 +4 只在假後端固定睡 40／180 毫秒時是常數**；換真後端就會跟著回話快慢跳，那時尺①的結論會從「固定偏差」變成「一個數字講不完」。

**三、格數／指令數／token 三個數字目前是完全確定的，只有牆鐘會抖。** 這是好消息也是壞消息：好消息是控制流真的可預測；壞消息是假後端 `slow:<ms>` 睡的是固定毫秒、token 是照字數估的，所以 (c) 這支串「有 LLM」但**沒有 LLM 的不確定性**。真後端一接上，token 與格數大概都會開始抖，這張表要重跑。

還有一條讀法上的提醒：`raw.jsonl` 每筆都有 `baton_resources`，那是接力棒 `.aos/series.json` 裡每條串的 `resources` 欄。它跑完永遠是 `null`——原型有這個欄位，但沒有人寫它。

## 原型缺什麼才能量得更準

按「不補就量不準」的順序排。

1. **`resources` 沒人讀也沒人寫。** 接力棒 `.aos/series.json` 每條串都有 `resources` 欄（`aosp/series.py:47`），初始化成 `None` 之後全程沒人碰；原稿頂層寫的 `resources` 也只是被載入器原樣抄進 `.aos/program/`，沒有任何程式讀它。結果是尺①今天完全靠 bench 自己在外面兜：一邊 `json.load` 原稿，一邊數檔案。**要它變成系統自己的帳**，最小改法是：`compile` 時把原稿的 `resources` 抄進接力棒那條串的 `resources.declared`，`exec` 每走一格往 `resources.actual` 加一筆。這樣 `aos status --json` 就直接看得到「講的 vs 做的」，不必外掛量尺。

2. **沒有指令計數與 token 計數的匯總。** 指令數只能數 `.aos/ticks/<N>/insts/*.json`，token 只能整份讀帳簿再自己加。兩個都是 O(檔案數) 的掃描，串一長就慢，而且**跨地的呼叫要 bench 自己知道有哪幾塊地**（(b) 的子地就是手動列在 `run.py` 的 `lands` 裡的）——原型沒有「這趟 run 一共碰了哪些地」的記錄。`.aos/calls/` 有呼叫記錄，但同步呼叫不會往登記表留東西，父子關係得自己拼。最小改法：`aos run --json` 的報告裡多三個累計欄（`insts`、`llm_calls`、`tokens`），子地的併進父的。

3. **牆鐘被固定的睡眠常數蓋掉，量不到真正的耗時。** `_WAIT_NAP_MS = 100` 是寫死的，任何一支有 `await`／同步 `call` 的串，牆鐘都是「等待次數 × 100ms」加上零頭。這讓尺②的牆鐘那一列基本上在量「輪詢了幾次」。最小改法：報告裡把每格的「做事時間」與「睡覺時間」分開記（`ticks_detail` 已經有每格的 note，補兩個毫秒欄就好），或至少讓 `_WAIT_NAP_MS` 可以從設定調。

再往下三條，不擋今天的量測，但擋下一版：

4. **假後端沒有抖動。** `echo:` 是零延遲、`slow:<ms>` 是固定延遲、`fail:` 是固定失敗，沒有「隨機延遲」或「隨機失敗」的模式。要量「LLM 帶進來的不確定性」，需要一個 `jitter:<min>-<max>` 之類的假後端，或讓 `slow:` 吃一個範圍。
5. **token 是估的。** 假後端的 `tokens_in`／`tokens_out` 是非空白字元數 ÷ 4（`aosp/llm.py:_est_tokens`），欄位名跟真的一樣，所以帳簿看不出這筆是估的還是真的。帳簿該多一個 `estimated: true`。
6. **失敗樣本量不到。** 三支串都是成功路徑。可預測性最該量的其實是「壞掉的時候散多開」（逾時、`no_daemon`、`await_timeout`），但那需要能穩定製造失敗的串——`fail:` 假後端可以做 LLM 那半邊，指令那半邊得靠故意寫壞的 `expect`。第二版該補一支 `d-fail`。

## 這個資料夾不碰什麼

`run.py` 只讀 `proto/aos.py`（當子行程叫）跟 `proto/bin/aos`（放進 `PATH` 讓地上的指令叫得到）。它**不 import `aosp`**，也不改 `proto/aosp/`、`proto/tests/`、`proto/run-all.sh`、`proto/examples/` 任何一個檔。`results/` 是輸出，可以整個刪掉。
