## 一、三分鐘看懂：inst json 是什麼

inst json 就是**一張「幫我跑這個程式」的單子**，把平常在 shell 裡要打的那一行拆成欄位寫下來：跑什麼（`argv`）、在哪跑（`cwd`）、多給哪些環境變數（`envs`）、輸入輸出接到哪個檔（`stdin`／`stdout`／`stderr`）、最多跑多久（`timeout_ms`，到了先 SIGTERM、過 `grace_ms` 再 SIGKILL）。`aos_inst.py` 讀這張單子、起那個程式、等它結束，然後在自己的 stdout 吐一份結果 `{"code", "signal", "timed_out", "ms", …}`。

小例子——shell 寫法：

```sh
cd work && timeout 30 python3 brain.py < q.txt > plan 2> err.log
```

inst 寫法：

```json
{"argv": ["python3", "brain.py"], "cwd": "work", "stdin": "q.txt", "stdout": "plan", "stderr": "err.log", "timeout_ms": 30000}
```

它解決的事：(1) **不用 sh 幫忙拼字串**——argv 是陣列，檔名有空格、引號都不會壞，也不會被 shell 展開；(2) **逾時收尾是內建的**，不用自己寫 `timeout`、也不會留孫程式沒收；(3) **結果是結構化的**（結束碼、被哪個訊號停、有沒有逾時、跑了幾毫秒），上層（loop、fsm、tasks）用程式讀，不用猜；(4) 單子是**資料**，fsm 的表、loop 的設定可以把它內嵌進去（一份 json 裡既有狀態表又有每格的單子），別人多塞的 key 它不管（N-04）。

## 二、跟新做法的關係

**新做法已經涵蓋的**：
- `cwd`：aos-exec 固定 `cd DIR`，程式資料夾就是起跑 cwd；inst 的 `cwd` key 在這裡多半不需要。
- `envs`：aos-exec export `AOS_WS`／`AOS_STACK`／`PATH`；其他變數 shell 入口一行就能設。
- 入口位置：`AOS_ENTRY`。proto8 是找 `.aos/inst.json`（N-35 的 `$AOS_DIRNAME`），新做法是找 `.aos/exec`——同一個位子，一個是資料、一個是可執行檔。
- 參數透傳：aos-exec 把多的 args／stdin 原樣交給入口，等於 inst 的 `stdin_inherit`、`--` 糖。

**inst 獨有、新做法沒有的**（照 `aos_inst.py` 實際有的）：
- `timeout_ms`／`grace_ms`：逾時收子程式、SIGTERM→SIGKILL 兩段式。現在 agent-bob 的 think 卡住只能靠 brain.py 自己寫的 120 秒逾時；loop 沒辦法殺一個卡住的格。
- 訊號轉送：Ctrl-C 轉給子程式、等它收好再退。sh 入口用 `exec` 的話 OS 幫你做了，沒 `exec`（像 fsm 那支還要寫 state）就得自己接。
- 結構化結果：aos-exec 是 `exec` 掉自己，上層只拿到**結束碼一個數字**；inst 多給 signal／timed_out／ms。
- `stdout`／`stderr` 指到檔、`*_append`、`*_mkdir`：sh 用 `>` 也能做，但那就是 sh 在做。
- 單子是資料：可以內嵌進 fsm 表、loop 設定，不必每格開一個資料夾放一支 `.aos/exec`。

**「不走 sh、更快」到底快多少**（10-19 在 WSL、/mnt/c 實量 50 次平均；ext4 會再快一些，級距不變）：

| 一跳 | 時間 |
|---|---|
| `sh -c true`（一層 sh） | 約 1 ms |
| `aos-exec DIR`（sh 版 aos-exec＋sh 入口） | 約 6 ms |
| `python3 -c pass`（光起直譯器） | 約 11 ms |
| `aos-exec DIR`，入口 shebang 是 python3 | 約 20 ms |
| `python3 aos_inst.py 單子.json`（單獨起一個 aos-inst 行程） | 約 35 ms |

所以：**單獨起一個 aos-inst 行程比 sh 慢 5～6 倍**，「更快」不成立。「更快」只在**一種情況**成立——呼叫者本來就是跑著的 Python／C++（aos-loop、fsm、tasks），直接在行程內 `aos_inst.run(dict)`，省掉的是中間那層 sh 與 aos-exec（估每跳省 3～5 ms）。agent-bob 一圈經過 loop→fsm→某個 state 共兩次 aos-exec，殼的開銷估 15 ms 左右，對照一輪 LLM 12 秒，**比例不到千分之二**；只有「幾千格每秒的小格子」才會感覺到。真要快是 C++（`core/exec` 本來就是 C++23 的 POSIX 批次執行器），不是 Python 的 inst。

## 三、幾種可能的接法（不選）

**(a) 不接，入口一律可執行檔。** aos-exec 不改；「aos 只訂環境變數」原則完整；巢狀照現在 `aos-exec think` 沿用工作區。代價：逾時、訊號收尾、結構化結果各入口自己想辦法（sh 寫 `timeout`、`trap`）；user.md「少用 sh」要重看——現在入口本身就是 sh，但不是 `sh -c` 串字串。

**(b) inst json 當一種入口：`.aos/exec` 是 shebang stub。** `.aos/exec` 內容一行 `#!/usr/bin/env -S aos-inst exec.json`（N-51 的 stub），旁邊放 `exec.json`；或 json 檔自己第一行 shebang、aos-inst 跳過第一行。aos-exec 不改（它只看「可執行」）；原則不破（入口仍是可執行檔，aos-inst 只是 bin/ 裡的一支程式，跟 aos-loop 同地位）。巢狀：單子的 argv 寫 `["aos-exec", "think"]`，正常。代價：每跳是 python 啟動約 35 ms（上表），**比 sh 慢**；拿到 timeout 與結構化結果，但結果 JSON 吐在 stdout 會跟入口自己的 stdout 混（N-26 的老問題），而新做法說「結果＝工作區內容」。

**(c) aos-exec 認得 json 入口，在行程內跑。** aos-exec 看到 `$AOS_ENTRY` 是 `.json` 就自己讀單子起程式，不 fork sh。aos-exec 要重寫成 Python（或 C++）；**原則被碰到**：aos 除了環境變數還訂了一種檔案格式與它的 key；使用者原話「AOS_ENTRY 的目標必須是可執行檔」被改。巢狀：每層巢狀多一個 aos-exec 行程——Python 版每跳 20～35 ms，比 sh 版慢；C++ 版才真的省。

**(d) inst 留在 loop／fsm 這一層，不碰 aos-exec。** aos-loop（已經是 Python）的 `loop.json` 允許 `run` 那格直接寫一張 inst（`{"argv": …, "timeout_ms": …}`），loop 在行程內 `run()`，不經 aos-exec、不經 sh；要跑一個資料夾仍寫 `"run": "fsm"`。aos-exec 不改；原則不破（inst 是 aos-loop 這支「程式」自己的設定格式，aos 層只訂環境變數）；這其實就是 proto8 原本的形狀（loop 包 inst、fsm 每格一張 inst）。巢狀：單子裡要叫子資料夾仍寫 `aos-exec x`，環境變數自然往下傳。省掉的是 loop→格之間那層 sh（估每跳 3～5 ms）加上拿到 timeout。代價：loop／fsm 兩種寫法並存（資料夾或單子）。

## 四、邊緣狀況（會撞到的）

1. **json 檔不能帶 shebang**：第一行 `#!` 讓它不是合法 JSON，編輯器、`jq`、fsm 內嵌都壞；要嘛 stub 與 json 分兩個檔（b），要嘛 aos-inst 容忍首行。
2. **cwd 規矩相撞**：inst 說「相對路徑從呼叫者 cwd 算」，新做法說「起跑 cwd＝程式資料夾」——順序上剛好一致（aos-exec 先 cd 再跑），但單子若寫了 `cwd`，`stdin`／`stdout` 就改從那個 cwd 算，跟 `$AOS_WS`、`$AOS_STACK` 三種基準並存，寫單子的人容易指錯。
3. **結果通道**：aos-exec `exec` 掉自己，上層只有結束碼；inst 的結果 JSON 走 stdout。新做法「結果＝工作區內容、沒有別的結果通道」——inst 那份 JSON 要丟掉、寫進 `$AOS_STACK`，還是允許 stdout 當結果通道？loop 的停止碼 10 也是走結束碼，兩套並存。
4. **逾時沒人管**：現在任何一格卡住（模型沒載入、網路不通），aos-loop 只會等；loop 殺不掉子程式的孫程式（aos-exec 是 exec 鏈、fsm 是 sh 再 fork）。inst 的 timeout 是目前唯一現成解；不接 inst 就要另想。
5. **AOS_ENTRY 一個值、兩種型態**：若 aos 同時認可執行檔與 json（c），`AOS_ENTRY=.aos/exec` 要找兩次（`exec`、`exec.json`）或改成兩個變數，跟「一個入口」的簡單性相撞。
6. **python 入口的巢狀成本**：agent-bob 一圈 4～5 層入口；全走 sh 約 15 ms，全走 python 入口估 100 ms 上下。對 LLM 回合是零頭，對「資料夾當函數、千次呼叫」的用法就不是。

## 五、拍板點（一句話答，最先該答的排前面）

1. **「更快」你要的到底是哪個？** (甲) 少一層 sh 的毫秒數——實量只有單跳 3～5 ms、一圈不到千分之二，可能不值得；(乙) inst 帶來的功能（逾時收尾、結構化結果、單子可內嵌）。答甲還是乙，決定下面要不要再談。
2. **inst 要留在哪一層？** aos-exec 層（c，aos 要認 json）、入口層（b，shebang stub）、loop／fsm 層（d，aos-exec 不動）、不留（a）。
3. **「入口必須是可執行檔」是鐵律嗎？** 是＝(c) 出局、只剩 (a)(b)(d)。
4. **逾時收尾要不要是 aos 層保證的？** 要＝某一層一定得有 inst 或等價物；不要＝各入口自理（brain.py 那種自己寫逾時）。
