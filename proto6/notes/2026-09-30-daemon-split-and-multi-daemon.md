# 2026-09-30 待議：daemon 職責太雜與多 daemon

← [筆記索引](README.md)｜[第二十批裁定](verdicts/11-tick-as-unit.md)｜[整理區](../spec/README.md)

**這是討論紀錄，不是裁定。** 多 daemon 範圍與 daemon 拆分都已裁定（見下）；第 4 點部件沒掛時的行為仍是建議預設。

## 起因

使用者問「目前架構還不錯，你覺得呢」，記錄者提的疑慮之一是 daemon 複雜度集中（daemon.md 近千行）。使用者回：「daemon 太複雜了嗎……我之後還在考慮多 daemon 的狀況。」

## 記錄者的看法（未裁定）

daemon 不是本質複雜，是**職責混在一起**。可分四組：

| 組 | 內容 | 條號 |
|---|---|---|
| A. 開格核心 | 登記、定時開格、叫醒／暫停、收尾、重啟、通道憑證 | B-601、B-603、B-604、B-607、B-612 |
| B. 訊息轉送 | `aos-mq` 在 node 之間搬訊息、急件 | B-614 |
| C. 程序與資源 | 掛常駐行程、cgroup 框與上限、收屍 | B-605、B-610、B-613 |
| D. 維運 | 熱重載、排空停機、佈建、helper 動作 | B-608、B-609 |

- 多 daemon 時：A 各管各的最單純；**B 最麻煩**（`aos-mq` 只走通道後，跨 daemon 的 node 互送要 daemon 之間轉送，發現、授權、對方不在都沒設計）；C 次之（一棵 cgroup 樹只准一個 daemon，並排多 daemon 要劃分）；D 各管各的。
- 建議方向：照 tick 的做法，**daemon 核心只留 A，B、C 拆成可掛的部件**，「保證跟著掛了什麼走」延伸到 daemon；B 最好在設計多 daemon 前先拆，例如 daemon 之間互送也用同一套 `aos-mq` 協議、多轉一手。
- 另一個相關疑慮：`aos-mq` 只走通道後，**不開 daemon 時 node 之間就完全不能溝通**（以前檔案收件沒有 daemon 也能運作）。

## 待使用者回答

多 daemon 指的是哪種（可複選）：
- (a) 多帳號：每個使用者各開自己的 daemon
- (b) 分樹：同一台機器的 node 樹分給幾個 daemon 各管一塊
- (c) 巢狀：daemon 開在另一個 daemon 管的 node 裡（現行 B-611：內層當成沒有 cgroup 照跑）
- (d) 跨機器：每台一個 daemon，串起來
- (e) 備援：一個掛了另一個接手

## 使用者回答（09-30 晚）

- **多 daemon 指 (a) 多帳號、(c) 巢狀、(e) 備援。** 也就是一台電腦上有多個 daemon 實例，各管各的；每個 daemon 有自己的 node 樹；daemon 底下的 node 可能管著另一個 daemon。(b) 分樹、(d) 跨機器不在範圍。
- **aos 不處理兩個 daemon 一起管同一個 node。** 記錄者補充：現行規則下這種誤設不會壞，同資料夾一次只有一格拿到鎖、另一格回 75，75 當普通結束不停格（B-602、B-607），只是輪流跑、互相拖慢。
- **備援 (e) 選「甲」：** 備援其實就是掛了自動重開，交給 systemd／cron 等外部工具，aos 不管。B-611 第二個 daemon 取不到鎖就回 125 照舊，不加等鎖待命模式。
- **不同 daemon 底下的 node 之間，不走 daemon 轉送**（以後可能給 daemon 做相關外掛）。要溝通就用檔案收件（普通程式，aos 不管）。所以目前基底這塊不管。記錄者補充：這讓原本最麻煩的 B 組（訊息轉送）不必為多 daemon 先拆。
- **巢狀時外層 daemon 重開：** 內層 daemon（外層某 node 用 node.mount 掛的常駐行程，重開不接回，B-613）會被收掉，整棵內層樹停，再由掛它的 tick 重掛。aos 不管，風險使用者自己承擔。

## 使用者裁定：daemon 拆分（09-30 晚）

1. **不開 daemon 時 node 之間不能溝通：不管。** 目前的基底不考慮這件事（連「改用檔案收件」都不當成基底的答案寫進去）。
2. **daemon 拆：** 核心留 A 組（開格核心：登記、定時開格、叫醒／暫停、收尾、重啟、通道憑證）。B 組（`aos-mq` 訊息轉送）與 C 組（cgroup 框與上限、helper 的 cgroup 上限動作）拆成可掛部件。D 組（熱重載、排空停機、helper 動作）留在核心，但各自也有開關。
3. **部件的形式：** 同一支程式、設定檔開關（不是分開的程式）。
4. **記錄者建議預設（使用者未回，spec 標〔建議預設，未拍板〕）：**
   - cgroup 部件沒掛＝沒有 cgroup，走現成 cgroup=off 路線。
   - 訊息部件沒掛時，`mq-post` 回錯誤（例如 `not_available`）、`mq-get` 取不到東西；任務表不必因 daemon 掛了什麼而改。
   - runner 清自己名下程序屬開格，留核心。
5. spec 依此改寫中（另一隊）。

## 同時提過的其他疑慮（供參考）

- 反應延遲逐層累加：最快下一格，跨 N 層就 N 格。
- 「aos 不管」的範圍變大，kernel／agent 可能各自重造可靠性。
- 可選組合多（git、cgroup、helper、fsync），測試矩陣變大。
- 建議下一步先把整理區做成原型驗證，再讓 kernel／agent 搬進來。
