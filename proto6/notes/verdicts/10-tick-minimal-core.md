## 方向

1. **tick 是一個程式，定期被執行。** 具體怎麼被執行的不管。
2. **tick 執行時的 cwd 就是它的管轄區。**
   - 管轄區可以重疊，風險自行承擔。
   - 在 aos 體系中通常遵循：**兩個 tick 的管轄區不能重疊，但可以包含**；被包含的那個 tick **從屬於**包含它的 tick。
   - tick 對管轄區內的東西有**最高裁量權**。
3. **tick 每次要執行什麼任務，都可以隨意掛載。** 例如：
   - 把 tick 當 clock，做 interrupt 之類的動作；
   - 拿去當 kernel；
   - 第一次行動時把某個行程掛到 daemon 上跑、第四次行動時再砍掉；被掛上去的行程也可以是另一個 tick；
   - 掛 agent 相關任務，讓這個資料夾變成 agent。
4. **借來的機制都是可插拔的、掛在 tick 上的任務。** 目前很多心力放在讓 tick 管理轄下的東西，為此借用了 cgroup 等機制；但 tick 的動作就是這麼單純，這些借來的機制假如不存在，tick 也應該能繼續完成它的職責。
5. **連管轄權都不是前提。** 雖然說 tick 對管轄區有最高裁量權，但就算實際上不給它管轄權（例如 Linux 權限上碰不到某些東西），tick 也應該能繼續完成職責。「最高裁量權」是 aos 體系裡的約定，不是 tick 運作的前提。
6. **tick 的真正核心，本質上是加了一些功能的 aos-exec。** aos-exec 是單次執行一份 inst 的程式（見 [inst](../../spec/base/inst.md)）；aos-tick 則是呼叫多個任務、並且包含「切換使用者」等功能的東西。
7. **核心邊界（同日追答）**：
   - **同一資料夾同時只能跑一個 tick**：要，算核心。
   - **daemon 就是負責定期跑 aos-tick 的程式。** 切換使用者照先前定的做（helper），這個功能是可插拔的。
   - **辨識一個 tick 的方式：看資料夾路徑或 inst.json 路徑。**
   - **接指令不算在 tick 內**（收件、分派 method、回 -32601 等），是掛上去的任務。
8. **核心邊界（再追答）**：
   - **任務是 inst.json 格式的超集。** 以後說不定每個任務都有自己的使用者（切換使用者本身仍可插拔）。
   - **任務依賴（needs）是必須的**，算核心。
   - **git 提交也納入核心**（先說可插拔，同日改口）：有 git 才有原子操作與任務依賴，所以留在核心。
   - **上下層納入核心**：每個 tick 都有上層與下層，**預設看資料夾包含**（上層＝最近一個包含它、也有 tick 的資料夾），**也可以另外登記**指定上層（同日追答修正「只看資料夾包含」）。

9. **接指令分兩塊**：
   - **一塊是系統任務**：之後做 tick 任務時，由掛上去的系統任務處理（收件、分派、回錯誤等）。
   - **另一塊是 daemon 傳訊**：同一個 daemon 底下的 tick，可以透過 daemon 互相傳遞訊息。
     - 訊息由 daemon **放在記憶體**，等收件 tick 下一格開跑時交給它；**訊息格式與檔案收件相同**。
     - **不保證送達**（daemon 當掉就丟）。
     - 送到時要不要叫醒收件 tick：**看訊息是否為急件**。
     - 「投件權就是執行權」**同樣適用**。
     - 不在 daemon 底下的 tick（cron、人手跑的）用不了這條路，只走檔案收件：**可以**。
   - **本質是 tick 與 daemon 之間的 IPC**：tick 在執行過程中可以掛載特定任務，走這條特殊通道向其他 tick 發訊。
   - 那個特定任務其實就是**普通的傳訊任務**，只是多了設定：要不要走特殊通道、急件（只在走特殊通道時有用）；這些設定只在傳訊對象是另一個 tick 時有用。
   - 傳訊任務本身屬之後的 tick 任務設計；**因為一些核心問題也要走這條通道，所以先把通道設計出來。**
   - **通道設計（同日追答）**：
     - 走這條通道的核心事務：登記與解除（含用登記覆蓋預設上層）、把行程掛到 daemon 上跑與砍掉（現在的 once；被掛的也可以是另一個 tick）、叫醒別的 tick、daemon 把暫存訊息交給正在跑的 tick。
     - tick 找通道：daemon 開 tick 時用**環境變數**告訴它 socket 在哪；不是 daemon 開的 tick 就沒有通道。
     - 身分證明：daemon 開 tick 時發**一次性憑證**，tick 在通道上出示；不靠 cgroup 或程序編號反查。**每格一張、這格內有效**，這格結束或 daemon 重啟即作廢。
10. **once 算在之後的 tick 任務**，不屬 tick 核心。

11. **任務依賴（needs）與 git 提交都從核心拿出去**（同日再改，推翻第 8 條的「needs 必須」「git 納入核心」）：兩者都是可插拔的。tick 核心剩：互斥鎖、照任務表依序跑（任務是 inst 超集）、上下層（預設資料夾包含、可登記覆蓋）。〔已被第二十批取代，見 [11](11-tick-as-unit.md)〕

12. **標準配備**：摘出核心的很多東西是剛需。分三層——tick 核心（互斥鎖、照表跑、上下層）；**標準配備**（aos 出廠就附、預設掛上：git 提交、needs、收件、切換使用者、cgroup 框、once 等剛需）；其他掛載（kernel、agent、clock、自訂任務）。〔已被第二十批取代，見 [11](11-tick-as-unit.md)〕
    - **後續設計主要依照標準配備去做**；spec 的保證以「掛了標準配備」為前提。**沒掛的話出現的錯誤我們不管**，不必逐條寫退化行為。〔已被第二十批取代，見 [11](11-tick-as-unit.md)〕
    - **標準配備必須全掛，不能拆開。**〔已被第二十批取代，見 [11](11-tick-as-unit.md)〕
    - **人手跑 tick**：風險由人自己承擔（第十八批審稿裁定 16「不在框就拒跑」撤掉）。
    - **沒全掛時**：做一些檢查、跳警告，再讓人選 y／n 決定要不要跑；沒有終端機可問（daemon、cron 叫起的 tick）時**預設照跑**，只記警告。〔已被第二十批取代，見 [11](11-tick-as-unit.md)〕

## 改寫計畫疑點的裁定（同日）

題號對應[第十九批改寫計畫](../reviews/2026-09-30/batch19-plan.md)的疑點。

1. **標準配備怎麼掛**：跟核心同一支 `aos-tick`，只在規格上分層（c）。〔已被第二十批取代，見 [11](11-tick-as-unit.md)〕
2. **清單邊界全算**：投件與鬧鐘、發布摘要、`aos-clean`、daemon 端的重啟清空與排空、通道上的傳訊任務，都屬標準配備。〔已被第二十批取代，見 [11](11-tick-as-unit.md)〕
3. **「全掛」怎麼算**：缺 cgroup v2 或 git 才算沒全掛；沒 helper、沒通道只算功能受限（c）。〔已被第二十批取代，見 [11](11-tick-as-unit.md)〕
4. **任務帶 `user`：現在就允許**，由切換使用者落實（a）。
5. **登記覆蓋上層**：新舊兩個上層都要同意；覆蓋後管轄權仍跟著資料夾，覆蓋只改管理關係（a）〔記錄者註：使用者答「5.a」，兩小題都取 a〕。
6. **通道上誰能送訊息給誰**：看寄件 tick 的帳號對收件 tick 的 `requests/` 有沒有寫權（a）。
7. **暫存訊息怎麼交**：由收件任務自己上通道取（c）。

8. **cgroup 常因不給 sudo 而不能用，採 a＋b**（同日追加）：〔已被第二十批取代，見 [11](11-tick-as-unit.md)〕
   - a：cgroup 仍是標準配備的一部分；spec 把「systemd 使用者委派子樹（`systemd-run --user --scope -p Delegate=yes`，不用 sudo）」寫成第一推薦的準備方式並附檢查步驟。〔已被第二十批取代，見 [11](11-tick-as-unit.md)〕
   - b：標準配備內建沒 cgroup 時的備援，用不需 root 的機制頂替（例如 subreaper＋程序群組收尾子程序、單程序 rlimit）；保證變弱但仍算全掛。〔已被第二十批取代，見 [11](11-tick-as-unit.md)〕
9. **git 同理，採 a＋b**：版本不夠或 git 本身出問題都可能讓 git 不能用。a：寫清楚最低版本與檢查步驟；b：標準配備內建沒 git 時的備援（記錄者建議：暫存檔＋fsync＋rename 的檔案日誌，保住「做完才刪原件」與依賴讀已完成結果；失去歷史與回溯，補投改讀保留期內的待送副本）。細節由落 spec 隊寫成建議預設。〔已被第二十批取代，見 [11](11-tick-as-unit.md)〕
   - 連帶：「全掛」的判定（第 3 題 c：缺 cgroup v2 或 git 才算沒全掛）改成——有備援就仍算全掛，只是保證較弱；落 spec 隊依此調整並標明。〔已被第二十批取代，見 [11](11-tick-as-unit.md)〕

10. **跨帳號任務（任務帶別的 `user`）**（落 spec 後追答）：不掛到 daemon。**tick 自己一直握著鎖，經 helper 以別的帳號開這個任務**（helper 多一個「以指定帳號開程序」的固定動作），任務只需知道「開我的那一格仍握著鎖」。取代先前暫定的「借 `node.mount` 開、不繼承鎖」。〔已被第二十批取代，見 [11](11-tick-as-unit.md)〕
11. **覆蓋上層時舊上層沒在 daemon 登記：放寬，只要新上層同意。** 沒在 daemon 登記的，aos 管不著。〔記錄者歸類：同理，不在 daemon 底下的 tick 需要通道的事一律算功能受限、不另設替代路（池掛不了 LLM 呼叫、agent 自跑 once、無格次序號的失聯判斷）。〕

疑點 8～10 與舊暫定 4 題（unknown 份額、git 歷史被整理、超分擋什麼、失聯判斷）使用者未答，落 spec 時照計畫的建議預設與上一輪暫定寫，條文標「暫定」。

## 跟已落 spec 的衝突（歷史；已依本份改寫，見「落點」）

- **cgroup v2 必要**（第十四、十五批，[B-605](../../spec/daemon.md)）與**每任務一層 cgroup**（第十七批，[B-202](../../spec/base/execution.md)）：照第 4 條，cgroup 不屬 tick 核心；照第 12 條它是標準配備的一部分，跑標準配備的環境仍需要 cgroup v2。〔取代註：第 8 條追加後不再成立——cgroup v2 只是完整保證的條件，沒有時走內建備援仍算全掛，見 [B-631](../../spec/tick.md)。〕
- **人手跑 tick 不在框就拒跑**（第十八批審稿裁定 16，[B-627](../../spec/tick.md)）：跟第 1 條「怎麼被執行不管」相衝。
- **從屬關係**：spec 現在的上下層由 daemon 登記的 `parent_id` 決定，而且明寫「與目錄位置無關」（[P-402](../../spec/protocol/work.md)）；第 2、8 條改成預設看資料夾包含、可另外登記覆蓋；`parent_id` 登記保留為覆蓋手段。「與目錄位置無關」的說法要改，第十八批審稿裁定 6 與 Q10 的換父要改寫成「搬資料夾或改登記」兩條路。
- **任務表禁止 `user`**（第十八批 C-07 永遠禁止的鍵，[contracts](../../spec/contracts.md)、[B-620](../../spec/tick.md)）：跟第 8 條「任務是 inst 超集、以後可能每個任務有自己的使用者」相衝。
- **tick 是基底的範圍**（第十八批 Q22，[B-626](../../spec/tick.md)）：`kind:system`＋tick 自己做的事＋aos-clean 都算基底；照第 3、4 條，其中多數可能應該是掛上去的任務。
