## 方向

1. **aos 是給特殊計算用的 OS。** 一般 OS 服務的是 CPU 計算，分配資源的單位是 CPU 指令；aos 要處理的是 LLM 呼叫、agent 的一輪任務這類計算。分配資源的單位從 CPU 指令變成一個「表達式」，也就是任意計算。但仍有限制：這個計算必須符合特定規格，包括能被 Linux 管制。外部計算（例如量子計算）也可以當外部函式庫來管。
2. **多層、多個 kernel。** 現有 OS 都是單一 kernel；aos 是多層多 kernel。
3. **抽象、資源、安全隔離的定義，每個 kernel 都可以不同。**
   - 抽象：例如某個 kernel 把特定種類的 agent 任務設成一種需要排程的任務種類。
   - 資源：不限 CPU、記憶體這類，人的特定意見也可以是一種資源（只是舉例，見第 6 條）。
   - 安全隔離：也可以在不同地方有所變化。
4. **Linux 是基底。** 借用 Linux 已經很完善的機制：Linux kernel 管 CPU、硬碟等；cgroup、使用者帳號等當安全隔離的基礎。
5. **上下層定義不同時不必對齊。**
   - 上下層的資源定義不同，不管。上層對下層的管理應該「潤物細無聲」：下層不知道自己被怎麼管理。
   - 隔離可以比上層寬。下層不知道上層，上層也只認它自己了解的東西。
6. **「人的意見當資源」先不管，只是舉例。** 更好的、現在就有的管理目標是**隨機性**：用愈多 LLM，隨機性愈高。管理目標是隨機性愈低愈好，但要跟任務完成度、資源消耗等一起權衡，以此當作排程的依據。

## 審稿裁定（同日，逐題問答）

題號對應[審稿](../reviews/2026-09-30/README.md)合併後的 20 題。

1. **tick 最特殊，是一切的基底**，不跟其他計算單位（once、LLM 嘗試、agent 一輪等）放進同一個外殼。其餘單位的外殼（設-14）與「隨機性」要不要成為外殼的一欄，之後再弄。
   - 補充：tick 裡的**系統性任務**算在基底內；agent／kernel／custom 系列的任務不算，歸其餘單位，之後再弄（含它們的逾時與取消）。
2. **投件權就是執行權**（裁-1）。能投件給某 node，就等於能用它的身分跑東西；spec 的隔離與 key 保護承諾要照這句改窄。
3. **多帳號部署的佈建缺口，給 helper 加固定動作**（必-1、設-13、設-17）：把 cgroup 框交給某帳號、建共享群組、改檔案群組等。helper 仍只做固定清單上的事。
4. **取消核權時，node 的主人兩者都算**（裁-7）：node 根目錄的擁有者，以及 inst 裡的執行帳號。
5. **node 在自己框裡另開子框、留住程序，接受**（設-3）：當作逃生口，讓 node 能刻意留常駐程序；收尾照舊只看 `tick` 與 `task-*`。
6. **改設定、改樹不必重開 daemon**（裁-8、裁-14、裁-15 的 roots 部分）：
   - daemon 設定可以**熱重載**。
   - 隔離帳號可以用**前綴或範圍**指定（推翻第十一批「不支援萬用名稱」）。
   - 搬 node 時可以**帶新的上層重新登記**。
   - 經 IPC 即時操作要**開放得更多**，不只頂層樹的增刪：**除了重大或危險的操作要重開，其餘都盡量支援即時改。** 落 spec 時把 daemon 設定與操作列表，逐項標「即時改／要重開」給使用者看。
7. **停機兩種都要**（裁-9）：新增**排空模式**（停收新工作、等在途做完，可設上限時間再停），現行的短寬限立即停也保留。
8. **cgroup 上限**（裁-11、新裁-1）：
   - 調高、調低都能**隨時改**；調低時現用量超過新上限，由 Linux 自己處理，aos 只記一筆。拿掉「整棵子樹全空才改」。
   - 頂層 kernel 的額度檔**只是分配政策**，不承諾頂層真的被卡住；硬上限由部署者在更外層自己處理，包括部署者事先自己把頂層框設好。
9. **格式版本演進兩者並用**（設-5）：schema 放寬、允許沒定義的欄位（舊程式忽略），小改動不升版號；不相容的大改才升版，新程式讀新舊兩版、寫新版，另有一支指令批次轉檔。
10. **agent 自開 once 做完仍不叫醒，維持第十七批**（裁-2）：spec 寫明結果由 agent 自己想辦法收（例如自己設醒來時間）。
11. **agent 之間的問答機制先不管**（裁-12）：等 agent 的基本機制定下來、之後擴充工具時再處理；現行照第十六批。
12. **agent 請求被拒收、卡在 unknown 的使用者輸入都延後**（新裁-2、裁-10）：aos 不太處理這塊，留到之後設計 agent 機制時再考慮。
13. **投件出事的痕跡**（設-1、設-9）：
    - 投件被丟掉：agent 範本對每個請求**預設設鬧鐘**，逾時沒回就自己發現；runner-stderr.log 照舊、不寫待辦。
    - 壞掉的收件原件：**錯誤只報一次**，原件留著，**過了保留期由清理程式刪掉**。
14. **結果副本維持現狀**（設-6、建-17、建-18）：git 歷史先不回收；結果要被引用、同 ID 重送要補投回應這兩處，落 spec 時用最小方式補上。
15. **spec 多處重寫先不動**（設-2）：依第十八批大改 spec 時一起重排正本與引用。
16. **人手跑 tick 不在正確的框裡就拒跑**（必-2）：報錯退出；人手要跑一格改經 daemon（例如「請 daemon 立刻跑一格」的指令）。
17. **git 最低版本升到 2.36，設 `core.fsync`**（設-7）：commit 相關物件與 ref 都保證落盤後才刪原件。推翻第十五批的 git 2.35。
18. **診斷資訊**（設-8、新設-1）：
    - 做 `aos work trace <id>`，沿路串起同一件工作在各處的紀錄；另寫一頁「出事時看哪裡」除錯指南。
    - daemon 裡完成的 once 診斷：**自動淘汰**（容量上限或保留期）＋**手動清除指令**。

第 20 題（裁-3，agent 設定檢查的結束碼要不要跟 kernel 統一）沒問，依第 12 條「agent 內部機制延後」歸延後（這是記錄者的歸類，不是使用者逐字裁定）。

## 記錄時的理解（不是使用者逐字裁定）

有疑問以使用者後續裁定為準。

- 第 3、4 條合起來的讀法：aos 本身只提供讓各 kernel 定義抽象／資源／隔離的框架，加上一個最小的「可排程計算」外殼（能被 Linux 啟動、限制、殺掉，結果交回檔案）；各 kernel 在外殼上定義自己的任務種類。
- 第 5 條的讀法：上層只用它自己認得的資源與規則管下層，不要求下層配合或知情；Linux 管的部分（cgroup、帳號）因為本身是巢狀的，天生不可能比上層寬，第 5 條的「可以更寬」指的是 kernel 自己定義、Linux 管不到的那部分。
- 第 6 條的「隨機性」要怎麼量、怎麼跟完成度與消耗權衡，本批沒定。
