## 要找的東西（依重要性）

1. **spec 內部互相打架**：兩篇（或條文與 schema／範例）對同一件事規定不同。
2. **裁定沒落實或落錯**：特別是第十六、十七批（verdicts 07、08）宣稱改過的地方，逐條去 spec 核對；也看早批被後批推翻後，spec 裡有沒有殘留舊說法。
3. **邊緣狀況缺口**：照 spec 實作時會卡住、不知道該怎麼做的狀態。只挑真的會發生、會影響實作的，不要湊數。
4. **schema／範例和文字對不上**：欄位名、必填、列舉值、檔名格式。
5. **notes 過時**：現行 notes（非 archive）講的跟 spec／最新裁定相反又沒標註。
6. 壞連結、條號引用錯（有 `spec/check_ids.py` 可以跑）。
7. **設計原則上的問題**（使用者 09-30 追加，跟上面一樣重要）：
   - **冗餘**：同一件事在多處重寫（不是引用正本）、兩套機制做同一件事、可以合併或刪掉的規則／欄位／狀態／檔案。
   - **該考慮卻沒考慮到的狀況**：不只是單條的邊緣情況，也包括整體層面——規模（上萬 agent、長時間運行）、復原與一致性（當機、半寫檔、git 提交失敗）、安全與權限邊界、人工介入與除錯、演進（版本升級、設定改動）等，spec 完全沒碰到的面向。
   - **設計本身的弱點**：某個規則雖然自洽，但會帶來明顯代價或跟 spec 自己宣稱的原則（例如「能下指令、能管檔案就能交給 agent」「工具就是工具」「只用標準庫」「少外部依賴」）互相違背。
   - **使用者的設計視角（09-30）當檢查用的尺**：「這是給特殊計算用的 OS。一般 OS 分配資源的單位是 CPU 指令；這裡的單位是一個『表達式』＝任意計算（一次 LLM 呼叫、agent 的一輪任務等），但它必須符合特定規格，包括能被 Linux 管制；外部計算（例如量子計算）也可以當外部函式庫來管。」請檢查：spec 裡各種被排程、分配資源的東西（work／attempt、LLM job、tick 任務、once、agent 一輪……）是當成同一種計算單位，還是各自一套；「計算必須符合的規格」有沒有明講、缺哪些條件（啟動、取消、能否中途暫停、怎麼被 Linux 限制、成本事先未知、結果交回）；Linux 管不到的外部計算（遠端 API、LLM endpoint）靠什麼管。這是使用者的方向，只拿來檢查 spec，不要改寫它。
   - 同一把尺的第二句：「現有 OS 都是單一個 kernel，我要做的是多層、多個 kernel。」檢查 kernel 樹撐不撐得起：額度怎麼一層層往下分、下層能否超過上層、中間層 kernel 掛掉或重啟時子樹怎麼辦、各層規則衝突誰說了算、跨分支的計算或訊息怎麼走、層數變深的延遲與開銷，以及哪些地方偷偷假設只有一個 kernel（只有 root 能做的事、全域唯一的檔案或設定）。
   這類問題照樣攤給使用者判斷：講清楚問題與代價、列可能的方向，不要擅自改寫他的大方向；多半歸到「要使用者裁定」。

不要報：純文風、用詞偏好、「可以寫得更好」但不影響理解的。

## 報告格式（大白話、繁體中文）

- 開頭一段：審了什麼、怎麼審、總共幾條。
- 分四類，各自連續編號：「必修」（會導致實作做錯或做不下去）、「設計問題」（第 7 類：冗餘、沒考慮到的面向、設計弱點）、「建議」、「要使用者裁定」（有兩種以上合理做法、應由他選）。
- 每條：一句話標題 → 引用位置（`proto6/` 起的相對路徑:行號，兩邊都列）→ 問題是什麼、為什麼會出事（舉具體情境）→ 建議怎麼改（要使用者裁定的，列選項，不替他選）。
- 用大白話，少術語；術語第一次出現就用一句話解釋。

你可以開自己的 subagent 平行做事（例如分篇審、一隊專門核對裁定落實），最後由你彙整、去重、每條親自核實過原文再寫進報告。
