# 時空體系下的四層（astra，2026-10-03）

## 一段話結論

這套體系最重要的原則，是讓 LLM 能用 JSON 或文字直接理解並操作 aos。
daemon、時間線、node 與任務，都應有可找到、可讀懂的描述。
需要操作時，LLM 寫入文字或 JSON。
操作之後，LLM 能讀到對象的狀態與結果。
daemon 提供運行環境。
tick-tock 為資料夾提供時間線。
kernel 與 agent 由其中的任務內容認定。
基礎理論已經成立。
接下來的重點，是把這些概念落成一致的可讀介面，同時接好多時間線與跨回合任務。

本文以[最新分層筆記](../2026-10-03-aos-layering.md)及使用者後續補充為準。
最重要原則見筆記第 7–9 行。
第 88–94 行的 Claude 對照不算使用者原話。

下文分清「使用者說的」、「推論」與「建議」。
檔名與樹狀圖只示意資訊位置。
不在本輪制定控制協議、訊息格式或權限。
本次全程唯讀，未改檔、未 commit。

## 四層一覽

| 層 | 是什麼 | 不做什麼 | 最大的未定點 |
|---|---|---|---|
| daemon | aos 與 Linux 的運行介面。提供 FUSE 空間與多條時間線。對外提供可讀寫的控制入口。 | 核心不認 daemon 從屬。不制定 kernel 政策。不內建切帳號與 cgroup 管理。 | 技術落地：把運行能力接成可讀的物件、狀態與操作。 |
| tick、tock | 一個資料夾的時間線。tick 接入任務。tock 告知回合結束。 | 不因回合結束就收掉任務。不因長任務存在就停止時間前進。 | 技術落地：分開呈現回合進度、任務出生與任務完成。 |
| kernel | 資源管理與排程任務。以任務為管理單位，以 tick-tock 為時間單位。 | 不要求專屬 daemon。不由資料夾包含關係推定管轄權。 | 控制細節與管轄範圍明確留後。 |
| agent | 一個任務承載的 idle、think、act 狀態機。依 tick-tock 變換。 | 不要求獨占 node。不先固定成五項流程或每格一次 LLM。 | agent 細節明確留後。 |

**推論：可讀性要涵蓋整個操作過程。**

LLM 需要知道對象在哪裡。
需要知道能對它做什麼。
需要知道現在發生了什麼。
需要知道操作是否已生效。

單純把數字包進 JSON，未必已經好用。
反過來，環境變數與退出碼本來也可以是文字。
問題通常是上下文隱藏，或語義不足。

**建議：維持一條清楚的介面原則。**

可修改的安排與操作，提供文字或 JSON 入口。
運行層產生的觀察，提供文字或 JSON 出口。
LLM 透過操作改變對象，再讀狀態確認效果。

這不要求底層全部改成文字運算。
Linux 訊號、程序等待與檔案描述符，可以留在運行層內。
也不要求把二進位工作產物全部轉成文字。
需要的是可讀的操作、描述與結果資訊。

## daemon

**使用者說的。**

daemon 是 aos 與 Linux 的介面。
FUSE 與 tick 的空間要整合。
以 tick 能碰到的資料夾為正統。
整合方式傾向在空間根整棵穿透。
任務可以不經 FUSE 讀寫。
見[筆記](../2026-10-03-aos-layering.md)，第 13、33–44 行。

daemon 要同時承載多條時間線。
每條時間線目前服务一個資料夾。
見同檔第 50–56 行。

本輪方向延續 daemon 減法。
切帳號、cgroup 與權限配置移到外面。
daemon 沿用啟動者的身分。

**推論：FUSE 樹是 LLM 操作 aos 的可讀入口。**

普通資料可以穿透到實體檔案。
運行資訊可以由 daemon 即時呈現。
兩者放進同一套空間。

控制檔供 LLM 寫入操作。
狀態檔供 LLM 讀取運行情況。
狀態改變應來自實際操作。
不能把改寫一個狀態字串，含糊地當成操作已完成。

**建議的樹狀示意。**

```text
space/                              daemon D 的 FUSE 空間根
  .runtime/
    control                         daemon 本身的文字／JSON 操作入口
    status.json                     daemon 的可讀狀態

  team/                             node id：team
    .aos/
      tasks.json                    工作安排
      runtime/
        control                     此時間線的操作入口
        clock.json                  回合與時間線狀態
        tasks/
          <任務識別>/
            birth.json              任務出生說明
            status.json             任務運行與完成資訊
            control                 任務操作入口
    policy/
    state/
    agents/
      a/                            node id：team/agents/a
        .aos/                       同類時間線與任務介面
        config/
        state/
        work/
      b/                            node id：team/agents/b
        .aos/
        config/
        state/
        work/
    shared/
```

這不是定案檔名。
也沒有要求每份資訊都另存一份持久檔。
FUSE 可以從運行中的同一份狀態產生文字視圖。

普通資料經 FUSE 存取與直接存取，應對到同一份內容。
巢狀與共享資料夾放行。
資料夾包含不自動建立管理權。

**兩條控制 daemon 的路都要保留。**

第一條是 tick 生出任務，再由任務開另一個 daemon。
啟動描述沿用可讀的 inst。
父時間線把這個任務當普通任務管理。
新 daemon 的空間落在 tick 給的資料夾裡。

第二條是寫其他 daemon 的控制檔。
LLM 可以用明示路徑選擇對象。
不必先從程序樹找 PID，再自行推導要送哪個訊號。

從屬來自第一條路的啟動來源。
daemon 核心不需要知道父子關係。
控制成環依使用者指示放行。
見[筆記](../2026-10-03-aos-layering.md)，第 79–85 行。

**現況已符合的部分。**

現行控制協議已是一行 JSON 進、一行 JSON 出。
`status` 已回傳可讀的狀態鍵。
不是只能用 Linux 訊號控制任務。
見[控制文件](../../src/py/docs/ctl.md)，第 15–23 行。

MQ 也已使用 JSON。
不能把 socket 一概視為二進位協議。
見[MQ 文件](../../src/py/docs/mq.md)，第 15–20 行。

這些內容格式可以保留。
需要變的是入口與管理對象的接法。

**尚未符合「直接好用」的部分。**

| 現況 | 缺的是什麼 | 建議的文字化方向 |
|---|---|---|
| daemon 重讀設定靠 `SIGHUP`。退出靠 `SIGINT`／`SIGTERM`。 | 缺少 daemon 本身的對等 aos 操作入口。 | 提供文字或 JSON 控制入口。訊號可留在底層實作。 |
| 控制入口與預設對象來自環境變數。 | 必要上下文藏在某個程序環境裡。 | 在空間中公開入口位置與對象身分。環境變數可保留為便利指向。 |
| 非 `status` 控制成功時，CLI 不印正文。 | LLM 只看到程序回 0。 | 讓操作結果有文字或 JSON 可讀。分清請求已接受與對象已改變。 |
| 狀態檔只保存暫停、已停等狀態。 | 它不是完整運行資訊。 | 分清設定、保存狀態與即時觀察。不要把舊狀態檔當成新狀態樹。 |

訊號入口見[aos_daemon.py](../../src/py/lib/aos_daemon.py)，第 77–109 行。
環境變數與 CLI 輸出見[aos_ctl.py](../../src/py/lib/aos_ctl.py)，第 54–76 行。
保存狀態見[重讀與狀態文件](../../src/py/docs/reload-state.md)，第 29–33 行。

**二進位的實際界線。**

現有 root helper 的正文仍是 UTF-8 JSON。
它另用 Linux 機制傳递檔案描述符。
這是內部通道。
不是要求 LLM 手工產生二進位控制封包。
見[aos_daemon_root.py](../../src/py/lib/aos_daemon_root.py)，第 7–15 行。

帳號功能既然移出 daemon，就不需要為了可讀性把它重新塞回來。
若外部工具仍使用這種內部通道，對 aos 顯示可讀的操作與結果即可。

**正常流程裡的工程差距。**

tick 返回後，任務仍可能活著。
現行 daemon 卻在 `aos-exec` 返回後清 cgroup。
它也可能等待存活後代持有的輸出管線。
見[aos_daemon_run.py](../../src/py/lib/aos_daemon_run.py)，第 20–23、48–62 行。

可讀狀態必須反映這些不同事件。
不能只有一個含糊的 `running`，同時指 tick、任務與整條時間線。

FUSE 與直接讀寫交錯，也不會自動產生快照。
可讀性不等於資料同時性。
需要快照的工作另行處理。

## tick、tock 與回合

**使用者說的。**

tick 是動作，也是必有的時間單位。
tick 結束代表回合開始。
tock 結束代表回合結束。
任務可以跨回合。
tock 只告知回合資訊。
見[筆記](../2026-10-03-aos-layering.md)，第 31–46 行。

node 是資料夾主體。
一條時間線目前服務一個資料夾。
node id 是相對 daemon 空間根的資料夾路徑。
見同檔第 52–56 行。

依本輪補充，同一 daemon 內同一資料夾只留一條時間線。
巢狀與共享資料夾放行。

**推論：時鐘與任務出生都必須可讀。**

LLM 不應只能從日誌時間戳猜目前回合。
也不應只能從環境變數猜任務由誰啟動。

可讀的時鐘資訊，應能說明是哪條時間線。
應能說明目前回合與回合進度。
應能分清時間線停止、tick 動作結束與回合結束。

任務出生資訊則回答另一組問題。
這個任務從哪裡來。
由哪條時間線接入。
在哪一回合啟動。
使用哪份 inst。
取得哪些空間範圍。

這些是資訊需求。
不是本輪的新 schema。

**建議：把 LLM 的寫入與運行層的確認分開。**

| 資訊 | LLM 可寫什麼 | LLM 可讀什麼 |
|---|---|---|
| 啟動安排 | inst 與工作安排。 | 哪份安排被採用。 |
| 時間線控制 | 已提供的文字／JSON 操作。 | 該時間線目前的運行與回合資訊。 |
| 任務出生 | 要啟動的工作描述。 | tick 實際接入後的出生說明。 |
| 任務存續 | 對該任務提出控制操作。 | 它仍在運行，或已經完成。 |
| 任務結果 | 任務產生的文字、JSON 或產物描述。 | 完成狀態、程序結果與產物位置。 |

任務出生說明不必公開整份程序環境。
只需呈現 aos 操作所需的資訊。
環境變數可以指向這份說明。
它不必成為唯一來源。

**一回合裡的線。**

tick 取得可讀的啟動安排。
給新任務空間。
完成任務與 daemon 的對接。
tick 結束後，任務繼續運行。

tock 告知回合結束。
尚未完成的任務繼續存在。

將來的回合通知，也應採 LLM 可理解的文字或 JSON 語義。
通知怎麼送、何時交付、如何接收，仍留給之後。

**現況已有 JSON，但事件語義需要更新。**

`record.json` 已有 `seq`、`started_at_ms`、`ended` 與 `exit`。
它不是不可讀的時鐘。
但目前 `ended` 表示全部任務與 hooks 跑完。
尚未表達新體系的三種事件。
見[aos_tick_record.py](../../src/py/lib/aos_tick_record.py)，第 98–108、132–142 行。

| 事件 | 新體系中的意義 |
|---|---|
| tick 結束 | 起頭完成，回合開始。 |
| tock 結束 | 回合結束。 |
| 任務結束 | 某次工作真正完成。 |

現行 tick 在開子程序後直接等待。
全部工作跑完才收尾。
因此 `after_all` 不能直接改名 tock。
見[aos_tick_run.py](../../src/py/lib/aos_tick_run.py)，第 75–88 行；[aos_tick.py](../../src/py/lib/aos_tick.py)，第 156–188 行。

**出生資訊目前不完整。**

現行任務取得 `AOS_TASK_ID`、`AOS_TASK_INDEX` 與 `AOS_TICK_CWD`。
它们是文字。
但沒有完整表達新任務的出生回合與獲配空間。
這些注入值也可能因環境清空或覆寫而改變。
見[aos_tick.py](../../src/py/lib/aos_tick.py)，第 262–274 行；[aos_tick_run.py](../../src/py/lib/aos_tick_run.py)，第 31–38 行。

我建議保留環境變數作為執行轉接。
另外讓任務描述能從檔案空間直接讀到。
LLM 就不必身處同一程序，才知道任務的來歷。

**退出碼需要上下文。**

現行任務結果已能區分 `exit` 與 `signal`。
退出碼檔也已是文字數字。
不需要把它誤稱為二進位格式。

真正的缺口是：這個數字屬於哪個任務。
它表示程序結果，還是回合結果。
任務是否真的啟動過。

現行 tick 拿不到鎖時可以回 0。
遇到擋板時也可以回 0。
任務失敗也不一定改變 tick 的回傳碼。
見[aos_tick.py](../../src/py/lib/aos_tick.py)，第 129–148、178–188 行。

因此，面向 LLM 的說明不能只留一個 0。
應能讀到「未開格」、「受阻擋」、「任務仍在跑」或相應完成情況。
具體欄位留後。

現行失敗清單只記非零結果。
空清單不等於某個跨回合任務已成功完成。
見[aos_tick_record.py](../../src/py/lib/aos_tick_record.py)，第 71–80、125–147 行。

這不要求推翻只記失敗的診斷紀錄。
需要補的是任務運行視圖。

**正常流程中的技術事項。**

`current/last` 會隨回合輪換。
長任務自己的出生與結果，不能只靠這兩個位置。
見同檔第 98–123 行。

若多條時間線放在同程序，現行 `os.chdir()` 也需要改造。
見[aos_tick.py](../../src/py/lib/aos_tick.py)，第 129–141 行。

回合節奏、跨線換算、重開後格數與計數慣例，維持技術問題的定位。
不再列為使用者必須回答的方向題。

## kernel

**使用者說的。**

有資源管理與排程任務，就算 kernel。
管理單位是任務。
管理時間單位是 tick-tock。
資源與算法可以自行規定。
見[筆記](../2026-10-03-aos-layering.md)，第 51、66–70 行。

kernel 可以對運行任務做 kill、restart 等管理。
管理另一條時間線時，經 daemon ctl 停止或繼續它。
管轄與權限先不展開。

**推論：kernel 的操作應能讓 LLM 直接參與。**

資源規則可以放在文字或 JSON 政策資料裡。
管理對象可以由可讀路徑與描述找到。
對任務與時間線的操作，也應經同類可讀入口完成。

kernel 不需要先取得 Linux PID，才能表達「停止這個任務」。
它不需要知道 `SIGTERM` 的數字，才能表達管理意圖。

運行層如何落實控制，屬於下層技術。
kernel 仍可保留 Linux 專用工具作為選項。
但那不應成為 aos 操作的唯一入口。

**具體長相。**

```text
team/
  .aos/             node 的時間線與任務安排
  policy/           可讀的資源定義與排程規則
  state/            管理任務使用的狀態
  work/             本次政策計算
```

一次管理機會可以讀任務狀態。
按自己的政策計算分配。
準備後續啟動安排。
對既有任務或時間線執行控制。

新任務仍由 tick 接入。
kernel 不因為負責排程，就另造一個繞過 tick 的啟動來源。

**操作應呈現的內容。**

| 對象 | LLM 寫入的意圖 | LLM 讀取的結果 |
|---|---|---|
| 普通任務 | 已提供的任務控制操作。 | 該次任務的目前狀態與結果。 |
| 時間線 | 停止或繼續該時間線。 | 時間線狀態與本地回合資訊。 |
| 作為任務啟動的 daemon | 對其承載任務做管理。 | 任務狀態，以及該 daemon 公開的資訊。 |
| 其他 daemon | 寫對方的控制檔。 | 對方的操作結果與運行狀態。 |

這裡只定可讀性要求。
不定 kill 的步驟。
不定 restart 是否沿用某份狀態。
也不把停止時間線解釋成殺掉全部既有任務。

**現況差距。**

舊提案用 daemon 的 `status.running` 計算同時醒著的成員。
新 tick 很快返回。
它不在跑，不代表任務已完成。
見[kernel 推薦方案](../proposals/2026-10-02-kernel/03-推薦方案.md)，第 64、72–80 行。

可讀狀態因此需要對準任務。
只把既有 `running` 搬進 `status.json`，仍沒有解決語義錯位。

舊提案也透過改 daemon 設定、送 `SIGHUP` 套用部分安排。
見同份提案第 49–65 行。
新介面可以讓 LLM 寫可讀安排，再經 daemon 的文字控制入口要求套用。
不必把原始訊號當成唯一操作方法。

目前 `tasks.json` 已是 JSON。
但它在開格時展開。
本回合稍後才寫入的內容，不會自動改變已展開的安排。
見[第二十批裁定](../verdicts/11-tick-as-unit/22-1001-第二十批.md)，第 8–17 行。

因此，可讀介面也要讓 LLM 知道安排何時被採用。
「已寫入」與「已開始執行」需要分清。
具體時機由實作安排。

**正常流程裡的推演。**

長任務仍在跑時，新回合照常到來。
持續占用型資源不會因換回合而自然歸還。
消耗型資源則可能使用另一套計法。
兩者都由 kernel 政策決定。

資源數字也應帶可理解的名稱與單位。
單獨一個 `10`，不足以說明十個什麼。
這是可讀性建議。
不是替使用者規定資源種類。

kernel 讀完狀態後，任務可能才完成。
下次管理時再看見，是正常觀察延遲。
可讀介面不需要假裝所有資訊都是同時快照。

資源量測、任務發現與宿主強制機制，依使用者指示留在技術層。
不再列為方向問題。

## agent

**使用者說的。**

agent 是 idle、think、act 三狀態的狀態機。
由一個任務承載。
依託 tick-tock 做狀態變換。
其他細節先不管。
見[筆記](../2026-10-03-aos-layering.md)，第 74–75、86 行。

**推論：agent 既是可讀體系的使用者，也應是可讀對象。**

agent 可以讀時鐘、任務描述與資源安排。
它也應讓外部讀到自己的三狀態與工作結果。
不應只從有沒有 stdout，猜它正在 think 還是 act。

agent 的內部狀態與任務運行狀態要分開。
`idle` 不必表示承載任務已退出。
`think` 也不表示每次 tick 都應重新呼叫一次模型。

這只區分概念。
不增加第四個 agent 狀態。
不在本輪制定轉移條件。

**具體長相。**

```text
agents/a/
  .aos/             node 的時間線與任務介面
  config/           既有 agent 設定
  state/            三狀態、記憶與工作狀態
  work/             尚未完成的輸入與產物
```

模型請求、工具 inst、對話文字與結果 JSON，都可沿用先前的技術儲備。
二進位產物可以保留原格式。
另以可讀資料說明其位置與用途。
不必把整份二進位內容編成一串 LLM 難以使用的文字。

對外需要操作 agent 時，仍經它的任務或時間線入口。
是否允許直接指定某個 agent 狀態，屬於之後的 agent 設計。
本輪不把寫入 `think` 當成已定的控制方式。

**現況與舊提案的差距。**

舊提案的請求、回應與工具 inst，本來就有 JSON 基礎。
可讀性可以保留。

但五項接力與「一格最多一次 LLM」，不是目前的核心定義。
見[agent 一格做什麼](../proposals/2026-10-02-agent/04-一格做什麼.md)，第 5、20–27 行。

`work/` 也不能只因 tock 到來就清除。
跨回合工作仍可能使用它。
同份提案第 61–67 行的「本格資料」需要重新對齊。

**正常流程中的注意點。**

模型或工具未完成時，時間線可以繼續推進。
可讀狀態應能讓人知道仍是同一件工作。
不能因為又看到一次 tick，就誤判成新的計算。

同一 node 可以同時具有 kernel 與 agent 職能。
時間線存在，不代表這些任務自然串行。
共享狀態的寫入由後續實作處理。

Linux 工具仍可能使用環境與退出碼。
但 agent 使用它們時，應能取得有對象、有結果說明的文字資料。
這樣工具轉接細節就不必滲入整個狀態機。

## 交叉例子

以下採一個 daemon、三個 node。
這只是展示配置。
kernel 與 agent 並不必須分居。

| node id | 時間線 | 任務職能 |
|---|---|---|
| `team` | K | kernel |
| `team/agents/a` | A | agent A |
| `team/agents/b` | B | agent B |

三條時間線各自推進。
K2、A2、B2 不表示同一時刻。

本例用兩個持續占用的工作名額。
TA 跨過 A1、A2、A3。
TB 較早完成。
這只是 kernel 的示例政策。

| 事件順序 | 誰做了什麼 | LLM 應能直接讀寫的內容 |
|---|---|---|
| D 啟動 | D 提供空間與三條時間線的運行設施。 | 讀 daemon 狀態。找到各 node 的時間線入口。 |
| K1 | K 的 tick 啟動管理任務。kernel 準備 A、B 的安排，各預留一個名額。 | 讀管理任務的出生說明。讀寫政策與啟動安排。 |
| A1 | A 的 tick 啟動 TA。tick 返回後，TA 繼續存在。 | 讀 TA 的來源 inst、出生 node、出生回合與獲配空間。 |
| A1 結束 | tock 告知 A1 結束。TA 尚未完成。 | 讀到 A1 已結束。仍讀到 TA 在運行。 |
| B1 | B 的 tick 啟動 TB。 | 讀 TB 的出生與運行資訊。它不與 TA 混用同一份狀態。 |
| B2 | TB 按自身邏輯完成。 | 讀 TB 的完成結果與產物位置。退出碼可保留為原始資訊。 |
| K2 | kernel 看見 TB 完成，釋放名額。它經 ctl 停止 B 線。 | 寫 B 線的文字／JSON 控制入口。再讀 B 線狀態。 |
| A2 | 原 TA 繼續存在。依 A 線的時間資訊推進自身狀態。 | TA 的出生資訊不變。A 的時鐘前進。任務目前狀態更新。 |
| A2 結束 | tock 告知 A2 結束。TA 仍未完成。 | 不把回合結束誤顯示成任務完成。 |
| A3 | TA 繼續工作，並在這一回合依自身邏輯完成。 | 同一任務的狀態轉為已完成。結果能直接讀取。 |
| K3 | kernel 看見 TA 完成，更新占用。它經 ctl 讓 B 線繼續。 | 讀完成資訊。寫 B 線的繼續操作。讀回狀態。 |
| B 的後續回合 | 新工作仍由 B 的 tick 接入。 | 新任務有自己的出生描述。舊任務結果不被當成新結果。 |

這張表不指定 agent 的狀態轉移條件。
也不定控制回應與通知的傳輸方式。
只檢查每個已定動作是否能被 LLM 看懂與操作。

TA 只啟動一次。
它跨三個本地回合存在。
回合資訊與任務生命期分開呈現。

若 TA 是開另一個 daemon 的任務，父時間線仍按普通任務看待它。
LLM 可讀其 inst 與任務狀態。
也可從新 daemon 的空間讀取其運行資訊。

若 kernel 要控制另一個 daemon，則寫對方控制檔。
這是已定的第二條路。
不必改成由 daemon 核心理解父子關係。

目前最大的三個落地點如下。
它們不是新增方向題。

1. **可讀的操作與狀態介面。**
   LLM 要能找到對象、寫操作、讀效果。
2. **時間線與任務生命期分離。**
   出生、回合推進與完成，需要有不同的可讀描述。
3. **共用實作與特殊位置並存。**
   daemon、時間線、任務可共用控制與狀態程式。
   仍需保留核心設施的特殊地位。

## 跟現況與裁定的差距

**先保留已經做對的部分。**

inst、任務表、控制協議、MQ 與 tick 紀錄，已有 JSON 基礎。
日誌也有文字輸出。
新原則不要求全部重寫。

主要缺口如下。

| 現況 | 判斷 | 調整方向 |
|---|---|---|
| ctl 與 MQ 已使用 JSON。 | 保留。不是二進位協議問題。 | 接入 FUSE 的可讀寫入口，對齊新的管理對象。 |
| daemon 自身重讀與退出仍靠訊號。 | 缺少 aos 層的直接入口。 | 提供文字／JSON 操作。訊號留在底層。 |
| 部分入口與對象只從環境變數取得。 | 格式可讀，但上下文隱藏。 | 公開可找到的描述與路徑。環境變數作便利指向。 |
| 控制成功時 CLI 常只回 0。 | LLM 難以直接判讀操作結果。 | 提供可讀結果，區分接受請求與狀態改變。 |
| 回合紀錄的 `ended` 表示同步工作全部結束。 | 與新 tick-tock 語義不同。 | 分清 tick、tock 與任務完成。 |
| 任務只留下非零結果清單。 | 適合診斷，不足以當完整運行狀態。 | 保留失敗紀錄，另呈現任務目前狀態。 |
| `current/last` 隨回合輪換。 | 不足以承載跨回合任務的出生與結果。 | 分開任務資訊與目前回合觀察。 |
| 內部 helper 傳 fd。 | 是 Linux 內部機制。 | 不要求 LLM 操作 fd。對外提供可讀意圖與結果。 |
| 任務輸出可能是任意 bytes。 | 不代表所有產物都適合直接閱讀。 | 提供文字摘要與產物描述，保留原產物。 |

## 留給之後

最重要原則已經確定。
留後的是具體接法。

| 項目 | 本輪已確認的要求 | 仍留後的內容 |
|---|---|---|
| 控制塊 | LLM 能以文字或 JSON 表達操作，並讀到結果。 | kill、restart 等具體行為與控制格式。 |
| 訊息交流 | 回合與任務資訊要有可讀語義。 | 傳輸方式、通知時機、交付與接收機制。 |
| 權限 | 控制入口與資料入口存在。 | 誰能操作哪些對象。 |
| agent | 一個任務承載 idle、think、act。狀態可理解。 | 狀態轉移、模型與工具執行細節。 |
| 管轄範圍 | 不從資料夾包含關係自行補出管理權。 | kernel 的具體管理範圍。 |

跨 daemon id、重開後回合數、節奏調整、跨線對照、node 出生消失、任務發現、資源量測、任務表修改、外部事件入口與結果可見性，都維持技術事項的定位。

本文對它們提出的只是可讀性要求。
不再將它們列成使用者待答問題。

控制成環依使用者指示放行。
也不以「LLM 可操作」為理由，額外加入未要求的控制限制。

## 問使用者的問題

本輪沒有新增方向題。

JSON／文字優先已是整套體系的首要原則。
後續實作要檢查的是：LLM 能否找到對象、讀懂狀態、寫入操作，再讀到實際效果。
