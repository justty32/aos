## 收斂：幾條線各自想到同一件事

- **沒有人建議換掉骨架。** 政策在 tick 裡跑、daemon 當笨 cron，六條都保留。要翻這條的只有兩個選項，都標明了：01 的 daemon 啟動席次、03 的 systemd。
- **把 LLM 從 agent 的格拆出來，交給固定工作槽。** 02、03、04、05 四條各自走到這裡。好處是同時計算數可直接限住，冷 agent 不占 daemon 執行緒，長呼叫不鎖住 agent 資料夾。代價是一次對話跨更多格，而且會碰「一 agent 一 Linux 帳號」。
- **grant 改成檔，叫醒另外做。** 01 和 05 都提。kernel 寫期望狀態，成員讀最新版，信只當提醒。重複或晚到的信不會多給額度。
- **五項縮成三項。** 02 和 06 都提，分成準備、LLM、收尾。LLM 留獨立一項，`kind:"llm"` 仍擋得住。
- **先存檔，再發 MQ 提示。** 03、04、05 都提。工作正本放檔案，MQ 只說「有東西可看」。不改 MQ 放記憶體的裁定。
- **每次計算一個獨立目錄，中斷就標 `unknown`。** 02、04、05、06 都提。後一項只吃本次產物，有外部效果的工具不自動重做。
- **request 併進 summary。** 02 提。一份狀態回報帶用量、下一步和需求，kernel 收到不必回 grant，可以斷開互叫循環。

## Claude 建議的實驗順序

各報告的首選不同。06 主張先做無 kernel 基準組，04 主張先驗 agent 資料化，05 主張先驗期望狀態。這三個可以串起來，前一步是後一步的對照組：

1. **無 kernel 基準組。** 兩個 agent、三項任務表、固定額度，用 06 方案 A 的做法，約一到兩天。它順便驗了三項任務、每次計算獨立目錄和 `unknown`。
2. **同一負載加政策。** 先加 06 方案 B 的薄 kernel，再換成 05 方案 A 的期望狀態檔，量 kernel 到底有沒有價值。
3. **LLM 工作槽。** 用 04 方案 A 或 05 方案 C，驗「分配單位是一次計算」。做之前要先答帳號那題。
4. **Plan 9 那條獨立做。** 03 方案 A 加方案 B，半天，不必等前三步。

方向題沒答之前，第 1 步和第 4 步都做得下去，因為兩者都不翻任何裁定。
