## 需要「線」的地方（依回合順序）

〔推論〕最後一欄照第 9 行的原則寫：每條線上的東西都該是 LLM 讀得懂的文字或 JSON。只寫形式，不定欄位。

| # | 哪一步 | 誰 → 誰 | 線上要帶的意思 | 哪些層在等 | LLM 可讀的形式〔建議〕 |
|---|---|---|---|---|---|
| L1 | tick 啟動任務 | tick → daemon | 「這個任務屬於 node X、第 N 回合啟動」 | daemon、kernel（靠它看見有誰在跑） | 任務資料夾裡一份出生 JSON |
| L2 | tick 給任務空間 | tick → 任務 | 「你的範圍是這個資料夾、現在第 N 回合」 | tick、agent | 同一份出生 JSON；不靠環境變數 |
| L3 | tock 通知 | tock → 還活著的任務 | 「第 N 回合結束了」 | 跨回合任務（靠它數時間）、agent（靠它換狀態） | node 下的回合 JSON（今天 `record.json` 已是） |
| L4 | kernel 管任務 | kernel 任務 → daemon | 「停掉／重啟 node X 的任務 T」 | kernel | 一行文字或一行 JSON 寫進控制檔 |
| L5 | kernel 管時間線 | kernel 任務 → daemon ctl | 「時間線 X 停止／繼續」（第 69 行） | kernel | 同 L4 |
| L6 | 控制別的 daemon（路二） | 某任務 → 別的 daemon 的控制檔 | 同 L4、L5，對象換成 daemon（第 84 行） | daemon 之間 | 同 L4；跟 L5 用同一組動詞 |
| L7 | 成員回報 | 成員任務 → kernel 任務 | 「我第 M 回合的狀態、用量」 | kernel | 成員 node 下一份 JSON |
| L8 | 任務之間 | agent 任務 ↔ agent 任務 | 對話、交棒 | agent | JSON 信或 JSON 檔 |

〔推論〕路一（第 83 行）不需要新線：子 daemon 對父時間線就是普通任務，用 L1、L3、L4 管它。

〔推論〕L7、L8 沒有訊息線也能先用檔案做：寫在對方看得到的資料夾，對方下個回合讀。L1～L6 不行，因為它們是「正在跑的程序」和 tick、tock、daemon 之間的事，要有人去讀。

〔使用者〕第 56 行定了 node id＝相對空間根的路徑。所以 L1、L3、L4、L5、L7 線上「哪個 node」這一欄已有現成的鍵，不必另發 id。

## 今天有的線是什麼

〔現況〕任務到 daemon 今天只有 socket 加環境變數。控制 socket 在 `aos_daemon_ctl.py`，指令有 `wake`、`pause`、`resume`、`status`、`kill`、`restart`（第 29 行）。訊息門在 `aos_daemon_mq.py`。兩者的路徑由 `give_env()` 用環境變數發給每一項（`aos_daemon_run.py` 第 163～179 行）。第二十五批（[26](../../verdicts/11-tick-as-unit/26-1002-第二十五批.md)）定了它們的形狀。

〔推論〕對照新體系：

- L5 幾乎現成。`pause`、`resume` 就是「時間線停止、繼續」，差在對象今天是一項 inst，不是一個 node 路徑。
- L4 只做到一半。`kill`、`restart` 對的是一項正在跑的那一次（`aos_daemon_kill.py` 第 38～52 行送 SIGTERM、SIGKILL），不是 node 底下某個跨回合任務。
- 方向是 daemon → tick → 任務單向發路徑，任務主動連。**沒有** daemon 主動找到正在跑的任務的線，L3、L4 要的就是這種。
- LLM 可讀：socket 上的請求與回覆已是一行 JSON，但它不是檔，LLM 要靠程式去連。環境變數、Linux 訊號、只記非 0 的結束碼（`task-exits.json`）都不是 LLM 能直接讀寫的。

這是之後設計時的起點，不是答案。

## 建議的順序（〔建議〕，不是裁定）

1. 先定 L1 與 L3。沒有它們，「任務跨回合」只是任務自己活著，沒人告訴它時間。兩者都可以先做成檔。
2. L2 併進 L1 的出生 JSON。
3. L5 先用今天的 `pause`、`resume` 改對象。L4、L6 跟它共用同一組動詞。
4. L7、L8 先用檔案。
5. 權限最後。使用者說 tick-tock 邊緣默認正常，權限是 daemon 與 tick-tock 的技術問題。
