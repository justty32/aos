# 二、分層看：哪一跳是程序邊界、哪一跳是函式邊界

← [入口](README.md)｜上一份：[POSIX 優勢拆解](01-POSIX優勢拆解.md)｜下一份：[實測](03-實測.md)

## 現在的四跳

```text
daemon ──Popen──▶ aos-exec ──Popen──▶ aos-tick ──Popen──▶ 任務
  ▲                                                        │
  └──────────── socket（aos-ctl／aos-mq）◀──────────────────┘
```

| 跳 | 現在是什麼邊界 | 程式位置 |
|---|---|---|
| daemon → aos-exec | 程序。daemon 一項一條 thread，thread 裡 `Popen([aos-exec, inst])` | `aos_daemon_run.py` 第 27、35 行；thread 在第 182 行 |
| aos-exec → aos-tick | 程序。inst 的 argv 寫 `aos-tick <dir>` | `aos_exec_run.py`（proto5 原樣） |
| aos-tick → 任務 | **函式＋Popen**。tick 直接 import `aos_exec_run` 的開檔、寫 exit 函式，自己 `Popen` 任務；**不**另開一支 aos-exec | `aos_tick_run.py` 第 20、65、75、96 行 |
| 任務 → daemon | socket＋環境變數 | `aos_daemon_ctl.py`、`aos_daemon_mq.py`、`give_env()` 第 163 行 |

兩個事實常被忽略：

1. **daemon 已經是 thread 模型。** 每一項一條 thread（第 182 行），thread 只做 Popen＋wait。使用者說的「需要同時跑多個 tick 就用 thread」現在就是這樣。
2. **tick → 任務本來就是函式邊界加一次 Popen。** 所以「tick 變 lib」只動 daemon → tick 這一跳（順便收掉 aos-exec 那一跳）。任務層什麼都不變。

## 三個選項下每一跳變什麼

| 跳 | A 全程序 | B tick 進 lib | C 混合 |
|---|---|---|---|
| daemon → tick | 程序。可選 A′：daemon 直接 import `aos_exec_run` 的函式開 inst，省掉 aos-exec 那支程序（每格少 25 ms，[實測](03-實測.md)），程序邊界仍在 | 函式：thread 裡呼叫 `run_tick(cwd)` | 一項是資料夾就走函式，是 inst 就走程序 |
| tick → 任務 | 不變 | 不變 | 不變 |
| 任務 → daemon | FUSE（使用者方向 1）。身分用路徑：工作資料夾放 `.aos/d` → 掛載點、`me` → 自己那項 | 同左 | 同左 |
| daemon → 下層 daemon | 一項的 inst 是 `aos-daemon --config …`，程序 | 下層 daemon 不可能是 thread（它要自己掛 FUSE、自己當一個身分）；所以 B 也得保留「一項可以是程序」，否則 daemon 跑 daemon 做不到 | 同 A |

第四列是 B 的硬傷：**只要 daemon 跑 daemon 還要做，daemon 就必須會開程序。** 到那時 B 就是 C。

## FUSE 認身分：跟程序／thread 無關

FUSE handler 拿得到呼叫者的 pid（已實測：`fuse_context.pid` 是呼叫 thread 的 tid，[實測](03-實測.md)第四節）。兩條路：

- **路徑認**（使用者提的 `me` 連結）：每個工作資料夾一個 `me` 連結指到掛載點裡自己那一項。任務寫 `.aos/d/me/ctl`，daemon 從**被寫的檔是哪一項的**就知道是誰，不看 pid。A、B 都行，連人手 `echo do > .aos/d/me/ctl` 也行。
- **pid 認**：A 下 tick 是一個 pid，daemon 開它時記下來；B 下 tick 是一個 tid，`threading.get_native_id()` 也記得下來；任務是 tick 的子孫，兩案都要從 `/proc/<pid>/status` 的 PPid 往上爬。

所以「thread 版 FUSE 比較好認身分」不成立；真正省事的是路徑認，兩案通用。

B 多一個坑：**daemon 自己的 thread 不能碰自己掛的 FUSE 樹**（單執行緒 FUSE loop 會自鎖；多執行緒也有鎖序問題；[plan9 第十篇](../2026-10-02-plan9/10-daemon跑daemon.md)已提）。A 下 tick 是外面的程序，碰 `.aos/d/…` 沒事；B 下 tick lib 內任何一行碰到 `.aos/d/…` 就卡死。tick 核心現在不碰 daemon 的東西，但 hooks、tasks-blocked 模組跑的仍是子程序，沒事；風險在以後有人在 tick lib 裡加「順便寫個狀態到 d/」。

## 對使用者六條減法的影響

| 使用者方向 | A | B |
|---|---|---|
| 1 daemon 變 FUSE | 無關，兩案都做得到 | 同左，但要守「daemon thread 不碰自己的樹」 |
| 2 cgroup、帳號拉出 daemon | 自然：想框就在 inst argv 包 `systemd-run`／`prlimit` | 做不到：tick 跟 daemon 同一個框、同一個帳號；只能框任務 |
| 3 daemon 互不從屬、重開要管 | 鎖跟著 tick 程序活，重開語意現成（[01](01-POSIX優勢拆解.md) 第 13 項） | 要另外設計：鎖 fd 傳任務，或接受重開時與孤兒任務重疊 |
| 4 核心不管子程序 | 「不管」＝不殺、不收屍、不框；開了只 wait。daemon thread 裡 `Popen` 後 `wait()` 就是現狀 | 字面上最乾淨：daemon 不開任何程序；但第四列（daemon 跑 daemon）會把它推回 C |
| 5 tick 變 lib、鎖與環境變數變好處理 | 鎖：flock 已夠；環境變數：`me` 連結兩案通用 | 鎖沒變好（[01](01-POSIX優勢拆解.md)「真正換到的」）；環境變數的改善來自 FUSE，不來自 thread |
| 6 一項是否只能是 tick 資料夾 | 一項＝inst，資料夾只是其中一種 argv | 一項＝資料夾最自然；但第四列要求保留 inst 形式 |

## 一句話

thread 只能取代四跳裡的一跳，而且那一跳在「daemon 跑 daemon」時還是得回到程序。使用者六條減法裡，有五條 A 跟 B 一樣做得到；第 2 條（框與帳號拉出去）A 反而更順。
