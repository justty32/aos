# 一萬個 agent：執行與排程改造提案

> 2026-09-28 交接快照；[原始來源](../../../proto5/notes/2026-09-28-ten-thousand-agents/runtime.md)保留於原位置。本文的現行行為與實測均指當時 proto5／環境，非 proto6 已實作；僅調整導航與探針重跑路徑。

範圍：Linux 單機、10,000 個已註冊 agent、每小時少於 100 個活躍 agent、雲端 LLM。這不是 10,000 個同時執行的程序；每小時活躍人數也不保證瞬間併發小於 100，故仍須入口限流。

狀態：2026-09-28 設計提案，未修改產品、未跑一萬 agent 壓測。使用者已選 Linux user／cgroup／project quota 的方向；本頁的表格欄位、門檻、排程方法是建議，尚非已定規格。aos-kernel 最終職責由使用者後續決定，本輪不引入分散式 kernel。

## 1. 先讓沒有工作的 agent 不花執行成本

現行已不是所有 agent 每秒 tick：idle 無輸入會停車，預設最晚五分鐘重訪。來源：[agent idle 分支](../../../proto5/lib/aos_agent.py) 第 79–94 行；[park 預設與分類](../../../proto5/lib/aos_kernel_info.py) 第 18、317–331 行。一萬個 park 均勻分散仍約每秒 33 次重訪，整批同時啟動還可能形成波峰。

目前每次 tick 在判斷 idle 前，已讀 system、完整 history 及工具表；來源：[設定載入](../../../proto5/lib/aos_agent_info.py) 第 19–22 行、[模型視圖](../../../proto5/lib/aos_agent_home.py) 第 346–364 行。閒置重訪成本會隨歷史與工具增加。

**必要改造，第一階段：** 無事件、無到期工作時不開 agent 程序。已被開出的 tick 先拿現有家目錄鎖，只讀小型進度與待辦摘要；無事立即退出，真正進入 think／act 才載入模型內容。既有自動 compact、wait 條件不能被短路遺漏：有到期維護或待觀察條件時，摘要必須指出下一個到期時間；對不會主動通知的外部檔案條件，仍保留有界補查。

**驗證：** 以檔案存取追蹤確認無事 tick 不開 history 或工具 manifest；沒有外部條件與維護到期的冷 agent，在觀察窗內啟動次數為零。讓 history 從小檔變大檔，不應增加無事 tick 的讀取量。active agent 的 compact／wait 語意仍通過原有測試。

**延後：** 常駐 agent server、模型內容快取、FUSE。短命程序足以先驗證低活躍率目標。

## 2. SQLite 留著，但每次只處理有事的列

現行 SQLite `load()` 全讀並解碼所有 procs／pools／busy；`save()` 仍序列化全部 procs 比對，只將異動列寫回。來源：[store](../../../proto5/lib/aos_kernel_store.py) 第 75–95、135–142 行。因而「換 SQLite」不等於已經是增量排程。

**必要改造，第二階段：** 持久排程索引只保存 agent 身分、ready 標記、next_due、任務狀態與執行世代等小欄位；history 留在 agent 家。用 SQL 索引找 ready／到期列，採有限批次 claim、更新、完成，不每 tick 重建全量 Python 字典。SQLite 交易仍保存派出意圖與結果接收狀態，不能改成只有記憶體 heap。

建議先保持單一排程寫入者與單機 SQLite；以狀態／next_due／優先級查詢與穩定 tie-breaker 支援確定的選取次序。欄位與排序需隨任務語意定稿，不在本頁直接定死。agent 的進度檔與排程索引各管一份責任；跨檔案／DB 的更新用待交接記錄和重放修復，不能假裝兩者同一交易。

**驗證：** 100、1,000、10,000 註冊量下只啟動同樣少量工作，記錄每輪查詢列數、JSON 解碼量、CPU 時間；idle metadata 不應整表進入 Python。重啟後 ready／due 工作不遺失；多次重放不重建同一派工。

**延後：** 多寫入者、分片 DB、遠端排程節點。現有歷史量測只有一名 idle agent，不能拿來宣稱萬人已過；見[one-boot 量測](../../../proto5/notes/2026-09-24-one-boot/README.md) 第 44–58 行。

## 3. 事件先可靠保存，再按門鈴

現行 daemon 每圈監看的是 **kernel 家**，不是每個 agent：來源：[daemon ticks](../../../proto5/lib/aos_daemon_ticks.py) 第 194–209 行。不要在精簡 worker 時，反而改成每 20 ms 掃一萬個 agent input 目錄。

**必要改造，第二階段一併做：** 收件入口先保存請求，再更新 ready 索引／待交接記錄，最後通知排程端；接收者對穩定 request ID 去重。通知只降低延遲，可靠性由持久請求與重放負責。若要承諾斷電後仍收件成功，必須定義 fsync 與確認時點；單純 rename 只解決半檔可見性。

文件 JSON-RPC 可以保留，不必為此先換成 socket broker。agent 家仍是輸入、狀態與結果的權威來源；SQLite 是派工／到期／執行歸屬的權威，對「家中有待辦」的摘要可從檔案重建。正常事件只核對受影響 agent。尤其「輸入已發布、ready 尚未寫入就崩潰」必須靠可重放 spool／outbox 或巡檢修復；若 outbox 也是第二次獨立寫入，寫它之前仍可能崩潰，不能因此刪掉原始收件處的補查。

第一版建議讓正式投件介面負責此流程，以少量共用入口通知；若仍支援任意程序直接寫 agent input，必須保留能找到這類未通知輸入的巡檢。巡檢按持久名冊游標、批次預算與錯開到期時間推進，不每輪掃完整目錄樹，也不喚醒 agent 來做檔名檢查。啟動及事件溢出可啟動一次分批修復，定期低頻巡檢涵蓋持久交接裂縫。補查週期依所承諾的遺失通知恢復時間設定，不直接沿用「所有人每五分鐘起程序」。

若採 inotify，只把它當門鈴：隊列溢出、服務重啟或 watch 建立失敗時標記索引可能過期，進入分批重新核對。事件合併時只須保證 agent 仍 ready，不需要每個檔案事件一一對應一次 tick。

**驗證：** 在請求發布、索引更新、通知三者之間逐點中止；刻意漏通知與重啟；若使用 inotify 再測 overflow。請求最終均被找到，恢復時間有上限，單 agent 不因重複通知平行執行；全量核對期間即時新工作仍能進入佇列。

**延後：** 每 agent 常駐 socket server、FUSE 事件入口；串流 stdout 是另一項較後的需求。

## 4. 拿掉常駐 cpu worker，但保留入口名額

現行 `while queue and free` 以池中的空 worker 限制派工，來源：[kernel dispatch](../../../proto5/lib/aos_kernel_engine.py) 第 184–205 行。直接啟動工作後，這個全局限制仍必要：每 agent 的 cgroup 上限相加可以遠超過整機。

**必要改造，第三階段：** 持久全局佇列先取得名額，再經可信啟動入口建立工作。分開限制活躍 tick、非 LLM 工具程序與 LLM 請求；另有 aos 父 cgroup 的總 CPU／記憶體／task 上限，為控制程序保留餘裕。名額數根據實際工具負載調整，不由「每小時少於 100 人」推導固定併發 100。

維持 inst／exec 作為工作描述與執行邊界。特權端只接受受控身分與工作識別，先完成 UID／群組／cgroup 的配置及降權，再解析不可信 inst、展開 `$ref`／`$env`、開工作輸入輸出、載入員工可改的程式。現行開檔與指示詞解析發生在啟動過程，不能僅在最後 `Popen` 加 user 參數；見[宿主 root 草案](../2026-09-28-host-root-design.md)。

啟動失敗必須歸還名額；取消、超時、daemon 重啟需依執行 ID 清理整個工作 cgroup 的後代，不能只看主 PID 是否結束。LLM 等候由獨立額度管理，勿占住唯一的 tick 執行席位造成等待循環。

**驗證：** 同時投遞超過名額的工作，活躍量不越界、其餘持久排隊；測 fork／thread、工具留下孫程序、OOM、取消與啟動失敗；假造 UID／資源歸屬不被採信，root 不代讀寫員工指定路徑。

**延後：** 自適應並行度、複雜公平排程、每工作獨立 UID。先保留可觀察的佇列長度、等待時間及拒絕原因。

## 5. 新訊息與恢復不能造成同一 agent 雙寫

目前家目錄有 tick 檔案鎖，來源：[agent tick](../../../proto5/lib/aos_agent.py) 第 64–75 行。這個保護應保留；新排程索引不能取代家目錄的實際互斥。

**必要改造，貫穿第二、三階段：** claim 一個 agent 時產生執行 ID／世代。執行途中來新訊息只記 pending／ready，不開第二個 tick；完成提交時，原子檢查本輪之後是否仍有新待辦，再決定保持 ready 或休眠，避免喚醒被完成流程覆蓋。世代標記也用於辨識重啟前的遲到結果。

如果使用逾時 lease，它只代表需要查證執行者是否失聯；過期不等於舊程序已死。重新派出前要確認舊執行已退出或已清理，並持有互斥。拒收舊世代結果也無法回滾已發生的外部副作用，工具重試仍需要自己的冪等條件。

**驗證：** 在最後一次「無待辦」檢查前後投訊息、重複投同一 ID、tick 執行中殺 daemon、舊結果晚到。任一 agent 同時最多一個狀態推進者；已接收輸入不因切回 idle 遺失；無法確認的外部副作用不偷偷重做。

**延後：** 分散式租約與共識。單機互斥、持久執行記錄與可核對的程序／cgroup 已足夠作首版基礎。

## 6. daemon／kernel 暫時按責任分，不急著定新外形

提案中 daemon 管可信啟動、降權、cgroup、回收、即時通知入口；排程部分管 ready／due、全局名額、LLM 排隊、任務預算與結果交接。Linux 管 PID 的實際執行與資源強制限制。這是責任清單，不是要求新增常駐服務；可保留現有 daemon／kernel 名字漸進替換。

**必要：** 控制路徑的成本與已就緒／正在執行的工作量相關，冷 agent 只占登記、資料與配額等持久狀態。全局限制及故障可見性先於高階公平策略。

**驗證：** 後續分階段以 100→1,000→10,000 個註冊 agent、固定少量活躍工作測試；記錄 idle CPU／RSS／喚醒次數、ready 到啟動延遲、尖峰隊列、重啟恢復時間、磁碟寫入量。每階段過門檻才提高規模，門檻依選定家用機及使用者回應目標制定。本頁未執行這些壓測。

**延後：** kernel 分散式化、每 agent daemon、FUSE、一輪任務的最終排程政策。資料夾精簡跟隨被移除的責任進行，不先刪掉仍用於交接與恢復的紀錄。
