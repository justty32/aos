本篇是 2026-09-28 的規劃提案，未修改產品或系統設定。目標是一台家用機保存 10,000 個 agent，一小時活躍不到 100 個，共用十幾個雲端 LLM endpoint。活躍數不是同時併發上限，工具仍可能展開並行工作。

**關鍵是讓閒置 agent 幾乎只占儲存空間，讓執行成本隨正在做的工作增加。** 不先引入分散式 kernel、Docker、FUSE、新語言或額外訊息中介；從現有 Python、SQLite、檔案交接與 Linux 機制逐步改。這不是現版已具備萬 agent 能力的聲明。

## 要改的六塊

1. **idle 不再排例行 tick。** 無事件、無到期任務的 agent 不保留程序，不讀 history；需要恢復或核對時另走受控流程，不把一萬個 agent 當每輪輪詢清單。
2. **SQLite 存可直接取用的 ready／due／job／attempt 索引。** 延續現有帳本，改成查需要派的工作與最近到期點，避免每輪載入、掃描所有 agent。啟動恢復可以核對全量，穩態熱路徑不要全量掃描。
3. **Linux 管身分、資源與容量。** 受控 launcher 在執行工作前套用 UID／群組與 agent cgroup；manager 掌握共同父 cgroup 與子樹。自有資料用宿主檔案系統 project quota，外掛 workspace 分開計容量。
4. **直接 exec 逐步取代 CPU worker。** 保留啟動、等待、取消、結果與恢復責任，移除單純等工作及轉交工作的常駐程序。daemon／kernel 屬於控制層，不跟著工作搬到 agent 資源域。
5. **LLM 用共享額度排隊。** 統一看 endpoint 背後的實際帳戶／配額域與工作身分，分開控制本機程序、遠端請求併發與 token 額度；退避等待不占可用執行名額。先做可理解的門票與回收，再擴充 token 策略。
6. **保留小而明確的任務協定與量測。** 分清接件、任務、每次執行嘗試及最終結果，讓重送、失敗和取消可以追蹤。用可重跑 mock LLM 及故障注入驗證，不用真實帳單來測一萬個 idle agent。

以上是邏輯職責，不代表要新開六個服務。最小首版可在現有控制程序內加索引、受控啟動與共享額度管理；只有需要隔離或量測顯示有必要時才拆程序。

## 分階段落地

### 0．先建立基線與最小契約

以可重跑工具建立 agent 目錄與合成歷史，用 mock LLM 模擬成功、延遲、限流及中斷。分開測全部 idle、少量工作、一小時內不到 100 個 agent 活躍，以及同時突發與工具並行。先記錄目前瓶頸，不能先假定 SQLite、磁碟或程序啟動哪一個最慢。

同時寫清最小 owner、在途 job／attempt 識別、接件與完成回應、取消與結果重送；新的 Linux 派工必須驗證 owner，不接受工具自填任意 UID 或 cgroup。首版不必先完成整套 task／run 分層規格；任務期間新訊息歸屬與 token 政策可以後定，但不能把身分驗證留到遷移之後。

**完成可見標準：** 一組指令可重建相同負載，留下環境、延遲、控制程序資源、程序數、SQLite／目錄存取量與錯誤結果；最小契約有正反例。此時數字是基線，不是達標聲明。

### 1．讓 idle 真正便宜

先沿用現有執行後端，改 ready／due 索引與喚醒登記。把通知和持久接件分開：通知可用來提早處理，不能成為唯一不丟工作的依據。檔案發布與 SQLite 更新之間仍有裂縫，需要分批、有預算的補查；它不是每輪全量掃描，也不需啟動 agent 做檔名檢查。保存任務結果與可恢復狀態，避免為了省掃描又失去崩潰後重建的資料。

**完成可見標準：** 增加 idle agent 數時，不新增對應常駐程序、不讀它們的 history；沒有事件或到期的 agent 不被週期性派 tick。新訊息、到期任務、漏通知與控制程序重啟都有可重跑案例，穩態派工查詢只觸碰相關 ready／due 工作。

### 2．兩個 Linux agent，先把邊界做對

在可丟棄環境建立兩個 agent，接入 UID／群組、父與每 agent cgroup、project quota 及整套 aos 的外牆。帳號與 quota 的部署配置和日常執行分開；先證明檔案系統真的啟用並強制 quota，不能只因目錄存在就視為完成。受控 launcher 在執行員工可改的程式或開它指定的路徑之前降權，並在工作開始之前進入資源域。不能只在現有 `on_spawn` 回呼事後搬 PID。

先讓少量工作走新的 direct exec 後端，與舊 worker 後端分開選路；驗明相同 owner／job／attempt 契約後逐步切換。取消逐工具 bwrap 要和身分及外牆一起落地，不能單獨關掉現版保護。外牆究竟採宿主 root 還是 namespace 內管理身分等方案，仍待選定；本輪規劃不承諾在使用者真機部署 root daemon。

**完成可見標準：** A 不能冒名 B；A 的 tick 與其工具合計受同一額度限制；並行工具不能各獲一份倍增額度；工具後代在取消時可回收。自有 quota 滿與記憶體限制觸發能留下可查失敗，外掛 workspace 不冒算成自有容量，控制層仍能回報／恢復。

### 3．LLM 門票與可恢復任務

用最小任務契約接上共享配額調度、有限併發、限流退避與取消回收。最小 LLM 名額控制可在前兩階段先接 mock，不必等所有 Linux 遷移完成。LLM 在遠端執行，也要計算請求與等待狀態；endpoint 數不等於獨立配額數。先將等待原因和輪到誰說清楚，再引入較細的 token 預估、實際用量結算與策略。能自行讀 key 並直連 API 的工具可能繞過排隊；首版管理受管呼叫，是否以保管 key 的代理強制所有呼叫另定。

**完成可見標準：** 多 agent 共用同一配額域不超發；429／逾時／取消／控制程序重啟後，門票不永久遺失，也不把不確定完成的外部副作用當成可任意重跑。接件回應與完成結果可區分，重送結果可去重，排隊與退避原因可查。

### 4．萬級驗收與可回退遷移

把前面的重跑工具擴至完整目標：一萬個已登記 agent、一小時內不到一百個活躍者，另測突發並行、巨大歷史、磁碟滿、控制程序中斷與通知丟失。先測一萬筆 metadata 與目錄，不在宿主建立一萬個真帳號；帳號規模另於隔離環境驗證，不能用 mock 宣稱全部 Linux 身分整合通過。分開量測冷啟動／恢復與平常運作；不要求恢復完全不讀全量，也不能把一次冷啟動成本藏進平常每輪派工。

**完成可見標準：** 固定硬體與負載的結果可重現，沒有待辦遺失、永久占票或跨 agent 權限錯置；同時報告資源與排隊延遲。使用者可接受約 0.5 秒反應，這是偏好而非所有負載下的延遲保證，驗收需標明測量區間與負載。

遷移先切少量 agent，再擴大。保留設定／資料格式版本、遷移前快照與核對工具；退回舊後端前先停止新派工並收斂在途工作，不能讓兩邊重複執行同一任務。若新資料已不能由舊版讀取，回退必須有明確轉換或備份恢復路徑，不能只換一個旗標。
