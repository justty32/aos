# 基底：把一件工作可靠地做完

> 狀態：歷史（09-28 概念稿），現行以 [spec](../spec/README.md) 為準。09-29 起架構改為 node／kernel 樹，見 [kernel 樹](2026-09-29-kernel-tree.md)。

← [三大概念](concepts.md)｜下一篇：[agent](agent.md)

**規劃草案，待逐塊討論。** 三大責任分區已獲接受，以下六塊是閱讀用細分，尚非已定介面或完成的實作。基底不理解人格與任務意圖，只提供執行、限制、交接與恢復機制；daemon 的大部分底層責任在這裡。

## 1．工作描述：把「要做什麼」說完整

工作描述是一次執行的材料：程式與 argv、cwd、env、標準輸入輸出，以及逾時等條件。agent 或排程層交出描述，基底依描述執行。例如「在專案目錄執行字數統計，把結果交回」不需要基底知道使用者為什麼要統計。

它描述一次操作，不等於整輪任務，也不應讓不可信欄位自行選 UID。接下來要釐清描述何時固定、哪些參照可在執行時讀取；否則排隊期間檔案變了，執行內容也可能變。

## 2．執行器：啟動、等待、取得結果

執行器把描述變成程序，管理輸入輸出、逾時與取消，回報啟動失敗、退出碼、訊號等結果。例如統計程式退出 0，只表示這次執行成功，不表示整份報告任務完成。

取消 CPU worker 的方向不會取消這些責任，也不能讓任何工作都立即啟動；排程先給機會，執行器再做。關鍵要定義取消何時算完成：主程序退出，和所有後代確實停止，不一定是同一時刻。

## 3．身分與資源：把授權落到 Linux

一個 agent 對應 Linux 使用者；cgroup 管執行資源，project quota 管自有容量（09-29 [裁定](2026-09-29-verdicts.md)：磁碟額度可選、只記帳，不是硬上限）。工具沿用委託 agent 的權限與資源，並行工具不能各獲一份倍增額度。外部 workspace 的容量歸屬另算，讀寫引起的記憶體消耗仍可能計入。

排程決定額度，基底在工作開始前落實，不靠工具自律。控制程序不跟著進入 agent 的資源域。例如 agent 的工具記憶體超限，管理端仍須能回報原因。日常啟動一定要經過一個特權點（切換 UID、放進 root 擁有的 cgroup 都要權限），09-29 裁定為極小 root helper：主 daemon 不是 root（後續已改：第八批改為 sudo 模式開 daemon 再 fork helper，現見 B-303），helper 只做查登記→建 leaf→降權→exec 固定 runner（[B-303](../spec/base/identity-resources.md)）；整套 aos 的外牆仍待選定；取消逐工具 bwrap 必須和這些機制一起遷移。

## 4．儲存與持久狀態：程序不在，事情還在

agent 資料夾長存，程序可以短暫；請求、結果與未完成交接不能只放記憶體。基底負責讓資料可靠發布與恢復，agent 決定記憶內容，排程決定任務狀態的意義。

例如工具結果已寫好但回報前斷電，重啟應能找到結果，而非直接再做一次。檔案與 SQLite 各自的交易不會自然合成同一交易。要釐清哪些資料是正本、何時確認收妥，以及 quota 滿時控制端如何保留失敗證據；這裡先不訂目錄或 schema。

## 5．通訊與交接：收到、做完、知道對方收到

JSON-RPC 可以經檔案傳送；某次短命處理讀請求、寫回應，就能扮演 server 的角色，不必常駐。spec 目前把收件的 server 角色交給控制接入口（[B-501／B-502](../spec/base/transport.md)），tick 只是發出 checkpoint.commit 的一方（後續已改：B-502 已刪，現見 B-501／tick 與 [tick.md](../spec/tick.md)）；讓 tick 自己當 server 只是曾討論的做法，尚未採納（見[環境穩定性](between-ticks-configuration.md)）。投件與回應表達事情，通知只讓接收端早點處理；持久記錄與去重承擔不漏件的責任。

例如同一結果重送，接收者不應重複結算。RPC id 只對應請求與回應，不能保證外部副作用只發生一次。接件確認、完成結果與結果已取走要如何區分，仍需逐項定義。立即喚醒與逐字串流也是兩個不同問題。

## 6．生命週期：讓程序的生死可對帳

這塊管理喚醒、啟停、收尾和重啟後的對帳。它回答「某次執行是否還活著」，不替 agent 決定下一句說什麼。冷 agent 無事不常駐，有事件或到期才需要程序。

例如控制程序重啟，不能只看舊 PID 就認定那仍是原工作，也不能因等待超時就假定它已死。需要穩定的執行識別與可查的受管範圍。恢復時哪些工作可重試、哪些結果未知，必須交回上層按語意決定。

## 用同一件小事串起來

以「統計文件字數」為例：agent 交出工作描述，排程給執行機會；基底以它的身分和資源限制啟動工具，等待結果、保存並通知。若中途停止，生命週期管理收尾；若重啟，先對帳已有結果，再決定是否需要上層處理。這是紙上例子，不要求呼叫真實 API 或修改系統。

建議依工作描述與執行器 → 身分資源與持久狀態 → 通訊交接與生命週期閱讀，再進入 [agent](agent.md)。先看清一件工作的頭尾，再細化失敗窗口；不急著一次訂完所有欄位。
