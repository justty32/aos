# agent：從收到事情到決定下一步

← [三大概念](concepts.md)｜前篇：[基底](base.md)｜下一篇：[任務與排程](scheduling.md)

**規劃草案，待逐塊討論。** 這篇拆解 agent 的語意責任，不指定目錄、CLI 或程序拓撲。agent 的資料夾是持久本體，tick 短暫推進狀態；冷 agent 不必常駐，也不應為了確認沒事反覆載入整份 history。

## 1．設定與人格：這個 agent 以什麼原則做事

設定描述使用哪個模型、如何工作；人格與工作原則影響理解和回答。例如同樣收到統計要求，一名 agent 會只回數字，另一名會解釋統計範圍。這些是 agent 的語意，不是 daemon 的執行規則。

設定不能自行授予 Linux 權限，也不能把「我很重要」變成排程優先權。設定在任務途中改變時，要立即套用還是下一輪使用，是後續要說清楚的邊界；目前不先發明版本欄位。

## 2．輸入與對話：理解誰帶來什麼事情

輸入可能是人的訊息、工具結果或其他工作的通知。基底確認收件與傳遞，agent 判斷內容如何影響目前工作，哪些需要回覆。例如統計到一半收到「改算第二份文件」，它必須理解這不是原工具的結果。

對話中的新訊息不應造成同一 agent 同時兩次修改狀態。是否插入目前一輪、取消原工作或排下一輪，屬於待討論語意，不能因為收到訊息就暗自定成新任務。也要區分已收件與已理解處理，避免回覆讓人誤會進度。

## 3．記憶與 context：留下什麼，這次帶什麼

history 保存對話經過，notes 留較持久的知識；context 是這次交給模型的材料。三者不是同一份東西，記下來不代表每次都整份送出。例如前十次統計的完整輸出可留在歷史，這次只帶新要求和相關摘要。

agent 負責選擇、整理和解釋內容，基底負責保存。摘要可能丟失細節，因此整理後如何回到原始證據、哪些內容不能省略，是關鍵問題。排程給 token 預算，agent 在預算內選 context；兩層要能回報不足，不能偷偷把不完整摘要當成全部事實。

## 4．能力與工具：能呼叫什麼，怎麼理解結果

能力包含工具登記、描述、參數與呼叫方式。agent 選擇工具並理解結果，基底真正執行。例如登記字數工具，表示模型知道如何要求它工作；不表示 Linux 因此多授予一個資料夾的讀取權。

工具通常代表委託 agent 行事，沿用相同權限與資源，內部再呼叫工具也一樣。多個工具能否同時執行，仍受排程准入控制。結果格式錯誤、部分成功、可重試失敗該如何回到 agent，是需要約定的交界；不能只把退出碼 0 當成語意正確。

## 5．tick 與狀態：每次把事情推進一小步

idle、think、act、wait 是理解狀態的詞彙：沒事、需要思考、需要動作、正在等條件。它們不是四個常駐服務。一次 tick 可以整理輸入、提交工作、存下等待狀態後退出；結果到達再繼續，不占著程序空等雲端。

LLM 單次 API client 可以獨立，agent 才理解回覆中的文字與工具要求。某次呼叫結果未知時，不能假定遠端完全沒做就立即重試。idle 是否代表一輪任務完成、wait 包含哪些條件，仍未定；狀態名稱不能代替任務完成契約。

## 用同一件小事串起來

使用者說「統計這份文件字數，並說明計算範圍」。agent 依工作原則整理 context，決定呼叫統計工具，交件後保存等待狀態。基底執行並回傳數字；下一次 tick 解釋結果、記入對話並回答。若收到更改文件的訊息，先依後續確定的任務語意處理，不讓兩個 tick 各寫一份互相覆蓋的答案。

建議先串起輸入 → tick → 工具結果 → 回覆，再細看設定與記憶，最後銜接[任務與排程](scheduling.md)。可以用固定假回覆理解流程，無需真 API；父子 agent 教學仍延後，不把多 agent 協作當成理解單一 agent 的前提。
