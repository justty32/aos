# 軟性設計原則：兩次 tick 之間的環境穩定性

← [筆記索引](README.md)

2026-09-28，使用者先提出兩次 tick 之間有效設定不變的硬性保證，後續撤回鐵則，改為**設計原則，軟性遵守，不放進 spec**。對應 B-305、跨篇強制約束與驗收已移除；這個想法保留為設計指導，不是整個取消。

設計時盡量避免在一次 tick 結束到下一次 tick 開始之間，無預告地改變 agent 的有效環境，例如權限、可存取資料夾、可用工具，以及 CPU／磁碟等資源配置。目的是讓 agent 與人更容易理解、預測行為；共享上層設定造成的間接變動，也值得用同樣角度考慮。

這不是強制不變式，不要求設定只能在 tick 內或新 run 生效，也不指定唯一的更新通道。具體設計可以按實際需求取捨，不設硬性驗收或額外待辦。JSON-RPC 交給 tick 處理只是曾討論的可能做法，尚未採納為要求。

此原則關注有效配置的可理解性，不表示預留資源、固定用量或可用空間，也不禁止一般業務檔案變動。真人經 aos 操作仍可參考這項設計原則；外部 root／真人直接手改造成的風險由操作者承擔，不能要求 aos 保證環境不變。
