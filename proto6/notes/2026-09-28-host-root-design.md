## 核心概念

使用者已定：正式員工有自己的 Linux 身分、固定負責其 tick 的 CPU worker；其他都是工具／外包。CPU 是 worker 程序，不是實體核心。VM 與宿主機部署仍可選。

**建議讓 root daemon 做程序管理，讓員工 UID 做工作，讓 Linux 在 daemon 外面設第二道牆。** 不要求先拆成多個服務；先把同一套程式中「哪些事情在降權前做、哪些在降權後做」分清楚。未來若有需要，才把極小的特權入口獨立出去。

```text
外部限制（systemd／Linux 強制存取控制等）
└─ daemon：受限的 root 程序管理者
   ├─ 排程 kernel：一般服務身分
   ├─ 員工 A 專屬 worker：UID A，只推進 A 的 tick
   ├─ 員工 B 專屬 worker：UID B，只推進 B 的 tick
   └─ 工具執行：依已驗證的委託身分啟動短命程序
```

圖中 kernel 的服務身分、外包如何執行是建議，不是使用者已拍板的規格。

## 現行程式與新方向的差距

現行 daemon 的池式啟動會讀取 target 的 inst，解開指示詞，再啟動程序；kernel tick 登記接受 `home` 與 `cli` 絕對路徑。這原本是同一信任環境的彈性介面，不是給不可信員工使用的 root 管理 API。

尤其 `aos_exec_run._execute_inst()` 會在啟動子程序前建目錄、開輸入與輸出檔；`aos_exec_spawn` 會先解析指示詞，`$ref` 能讀檔、`$env` 能讀解析者環境。**只在最後啟動子程序時切 UID 不夠：前面可能已用 root 讀寫員工指定的檔案。**

目前 agent tick 已經是短步驟：產生 LLM／工具工作、交件、返回，後續由回音叫醒；工具工作可由 `_pool` 選池，未指定時使用 `tool_pool`。現有 access 把工具包進 bwrap，未提供 Linux 員工身分與專屬 worker 的安全绑定。

程式依据：[daemon 啟動](../../proto5/lib/aos_exec_spawn.py)、[執行與重導向](../../proto5/lib/aos_exec_run.py)、[kernel tick 登記](../../proto5/lib/aos_daemon_ticks.py)、[指示詞](../../proto5/lib/aos_directives.py)、[agent 派工](../../proto5/lib/aos_agent_batch.py)、[jail](../../proto5/lib/aos_jail.py)。這裡沒有宣稱現行版本可安全用 sudo 上線。

## 第一個邊界：人事名冊不是員工自己填

建議由管理者維護受保護名冊，登記「員工 ID → UID／GID、附加群組、agent 家、專屬 worker、資源上限」。root daemon 只根據這份名冊執行既定動作。員工可以申請工作，不能在工作單裡自行指定 `uid: 0`、別人的員工 ID，或換成另一個權限較大的 pool。

身分要從可信入口取得：例如每個 worker 建立時交給它專屬連線，或使用 Unix socket 的對端身分。若保留資料夾投件，必須是各員工隔離且有受信任绑定的入口，不能把「大家都能寫的 queue 中，JSON 自稱來自 A」當成驗證。

kernel 可以保持排程角色，但不因排程而持有 root。root daemon 仍須獨立檢查請求是否符合名冊：不能因為 kernel 送來就接受任意 UID、任意程式或任意控制路徑。

初版建議帳號由管理者預先建立，daemon 只啟停已登記員工，不自行修改 `/etc/passwd`、`/etc/group` 或配置 sudo。這可以讓第二道牆直接禁止改系統帳號檔，也避免把「聘任」一開始就做成完整帳號管理系統。

## 第二個邊界：先降權，再讀員工的工作內容

root 可以讀管理者的名冊、啟動固定且不可被員工改寫的 runner、管理自己建立的程序。root 不直接執行員工指定的 Python、shell、tick.json 或工具包，也不以 root 解析它們的 `$ref`、開重導向檔、建立任意 cwd。

建議的順序是：驗證員工與動作 → 建立受管理的執行範圍 → 設定可信群組與 UID／GID、清除不必要權限及繼承環境／檔案描述符 → 以員工權限讀取 inst、開檔與執行。實際降權細節需在實作時驗證，不能只檢查 effective UID 一個值。

daemon 自己及固定 runner 的程式、Python 模組路徑、直譯器和上層目錄都不能由員工改寫。root 不從員工 cwd 或可改寫 PATH 找程式。管理檔與輸出路徑也要防符號連結及檢查後替換；單純先 `realpath()` 看起來正確，並不足以解決競態。

root 的結果紀錄應寫固定管理位置，工作內容的 stdout／stderr 可走管線交回，或由降權程序寫自己的輸出檔。不要讓工作單把 root 的 log 路徑改成任意宿主檔案。

## 專屬 worker 怎麼運作

建議把專屬性解釋成「這個 worker 一生只負責員工 A 的 tick」，而不是「A 的一切計算都只能在它身上完成」。程序掛掉後由 daemon 重建，仍绑定 A；沒有事情時睡眠，不需要持續空轉。

沿用現有非同步節奏：tick 整理狀態 → 提交 LLM／工具工作 → 返回等待 → 結果到達後再 tick。同一員工同時只允許一格 tick，worker 的重啟世代與未完成工作需要對帳，不能僅看相同 PID 或名稱。

專屬 tick 槽不接一般工具／LLM 工作，也不在 tick 裡同步等整個工具鏈完成。否則 tick 佔住唯一槽位、又等排在同一槽位後面的工具，就會自鎖；即使工具另有槽位，tick 長時間卡住也會失去接訊息、取消與推進狀態的機會。

工具資源可以共享「配額和排隊能力」，不等於所有工具在同一個 UID 的長命程序裡執行。每件工作啟動時要落到正確 UID；已永久降權為 A 的 worker，不能事後自行切成 B。LLM 呼叫同理；若要集中保存供應商金鑰，可以另設受限代理，但這是後續可選設計。

若外包再同步呼叫另一個外包，共享池全部被等待中的父工作佔住，仍可能死鎖。初版可以不提供池內同步巢狀派工；需要時再設計讓出執行槽或非同步子工作，不能僅靠「池夠大」當正確性條件。

## 外包身分的簡單起點與代價

**候選預設：外包沿用委託員工的 UID。** A 叫來的工具算 A 的程序，讀写權限、工作成果所有權和配額都容易理解；它沒有自己的正式員工帳號或固定 tick worker。

代價是同一 UID 的工具不能只靠 Unix 檔案權限與 A 自己隔離。若 A 的記憶、prompts、狀態由 A 擁有，工具通常也具備相同的 DAC 權限。工具能否改這些資料，必須明確選擇：接受「外包代表 A 行事」，或另外用掛載／程序隔離、強制存取控制等限制工具。唯讀掛載與 UID 各自負責不同問題。

因此 access 不一定全部刪掉。可以讓 Linux UID／group／ACL 管誰擁有什麼，access 保留此次工具能看見哪些掛載、cwd、網路等執行環境。工具移除 jail 的例外，也不能順便移除宿主機對 daemon 的外部牆。

另一候選是臨時工作 UID；隔離更細，但成果交接、群組與生命週期會複雜化。這輪不替使用者選定。

## 第二道牆與驗證順序

員工 UID 是限制員工；使用者問的第二道牆還必須限制 **daemon 自己**。外部 systemd／Linux 安全政策應由管理者持有，daemon 無權改寫自己的政策，也不能經過管理 socket 叫另一個不受限 root 服務代辦。

限制 daemon 的檔案寫入範圍、能力與裝置／網路等，和防止 daemon 冒用宿主既有 UID，是不同問題。需要切 UID 的 root 程序若仍可任意 setuid，單靠設定檔白名單不能抵擋 daemon 本身已被控制；具體能擋哪種失敗見[第二道牆調查](investigations/proto5-host-root-second-wall.md)。這不是 VM 等級的隔離，也不能把「UID 是 0 但有幾個限制」直接叫做安全完成。

若進入原型階段，建議先在可丟棄環境驗證兩個預建員工：專屬 tick worker 重啟後仍绑定原員工；A 不能冒名派給 B；工具不能以重導向、指示詞或替換程式讓 root 代讀寫；daemon 不能寫准許範圍外的測試檔。再測停止／取消是否清掉整棵工作程序、等待與巢狀工作是否卡死。這些是後續驗收構想，這輪只做設計。
