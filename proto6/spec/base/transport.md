## B-501：投件入口與授權〔使用者方向 2026-09-29〕

人、agent、工具共用有權限即可使用的檔案或指令入口。可依一般 Linux 權限，把訊息或工具／LLM 結果完整發布到指定的 ignored 收件區，不必先換成 blob 引用，也不必全經一個 RPC gateway。檔案發布依 [B-402](storage.md)，消費依 [tick](../tick.md)；有權限也能直接讀取檔案，正式輸出以已提交版本為準，見 [agent 輸入與輸出](../agent/input.md)。

不能拿內容自稱的 sender 當授權依據。IPC 看 socket 對面的帳號；檔案投件靠 OS 權限及可信投遞資料辨認來源，無法驗證的名稱只當自述。收件按[訊息協議](../protocol/messages.md)解析，大小限制與 wire 格式見協議篇。

**method 就是指令**〔使用者方向 2026-09-29，第十七批〕：method 是去掉 `aos`、以 `.` 連接的指令，params 是完整 inst，表示「在你那裡跑這條指令」，argv 保留 `aos`；base 是收件 node。收件 node 接哪些 method 由它的任務表決定（[B-620](../tick.md)），跟發件者是誰無關。錯誤分兩種，不混用：

- **-32601**：只表示收件 node 沒有任務宣告這個 method，或展開後 argv 跟 method 對不上（少了 `aos`、命令段不同）。沒人宣告的由 tick 開格時自己回（B-620）；有宣告但 argv 不符的由那項任務回。
- **-32000 加業務碼**：來源沒被授權做這件事（例如 `member_not_authorized`、`cancel_not_authorized`），由處理那個 method 的任務判斷，碼表見 [P-306](../protocol/messages.md)。

通過後按 inst 身分授權規則執行，回應沿工作結果格式。接件執行該命令的本地動作，不再投同一份 RPC。

**投件權就是執行權**〔使用者方向 2026-09-30，第十八批〕（[T-08](../terms.md)）：params 是完整 inst，envs、指示詞、stdin 路徑與程式都照 inst，所以**能投件給某 node，就等於能用它的身分跑任意程式**；aos 不替跨 node 的 inst 另設防。這件事**會傳遞**：A 能投給 K、K 能投給池，A 就等於也能用池的身分。UID 隔離與 key 保護只對整條投件鏈以外的帳號成立；鏈上的帳號互相信任，風險由開放投件權的人承擔。

node 登記與喚醒的 IPC 以 [daemon](../daemon.md) 為正本；執行身分依 [inst](inst.md)，不靠資料夾位置推定。

〔使用者方向 2026-09-29〕**跨隊有權限就直投對方收件區，不經上層轉送**（第九批）；沿用相同收件格式、請求／結果識別與喚醒規則，不另造入口。

**驗收**：有投件權限的人與 agent 都能交件；正文冒稱另一身分不取得權限，沒有寫入權限的投件被拒絕，半份檔案不算正式收件。沒有任務宣告的 method 回 -32601；有宣告但來源沒被授權的回 -32000 業務碼，不回 -32601。

## B-503：檔案去重與確認〔使用者方向 2026-09-29〕

請求 ID 在所屬目標的收件區／已接納區定址。檔案還在，同 ID 同內容就不重收；同 ID 不同內容報衝突，不覆蓋原件。不同 ID 的相同文字仍是不同請求；結果須配對原工作與實際嘗試，不能冒認新嘗試，見 [共用契約](../contracts.md)。〔建議預設，未拍板〕ID 可帶發件 node 識別以避免撞名，但名稱本身不證明身分。

三種確認各有證據：**收件**是完整發布並按約定保存，**完成**是有可信結果，**已消費**是接收端把內容及相應變動 commit。收件不等於工作成功，讀過不等於已消費；不另做三張確認表。收件原件的移除依 [tick Q1](../tick.md)。

〔建議預設，未拍板；第十八批從 [P-304](../protocol/messages.md) 搬上〕「同內容」指已發布檔案的 bytes 完全一致（比對方式見 P-304）。收件區或追蹤區的已提交原件都是去重依據。

- **請求同 ID 同內容**：不重新接納或執行。已有已提交回應就補投原回應；仍在處理就繼續等，不另送第二種「處理中」回應。commit 後遺留的收件原件依 [Q1](../tick.md) 補清，不重吃。〔使用者方向 2026-09-30，第十八批〕補投的原回應**從 git 歷史撈**：取當初提交的待送回應檔（`.aos/outbox/responses/<id>.json` 最後一次存在的版本）原 bytes，放回待送區照 [Q2](../tick.md) 投出，不重新產生、不另存副本。歷史裡找不到就當證據已清，照下面的保留期規則處理。
- **回應同 ID 同內容**：只消費一次，commit 後的遺留原件只補清；不再回覆這份回應，避免來回無限投件。
- **同 ID 異內容**（請求或回應都算，包括只改 method、params 或 reply_to）：不覆蓋、不執行新內容，留下 `id_conflict` 待處理事項，不採最後寫入者。發布時的 EEXIST 只證明撞名；投件者有讀權並比對原件才可判同／異內容，只有寫入及穿越權、無法比對時，保留本地原件並報投遞未確認，不猜已收、不覆蓋；接收端再用自己可讀的原件及已提交證據判斷。只有新投件者有經核對、且不同於原請求的回件 node 時，才向新地址送衝突錯誤；同一回件地址只留本地診斷及事項，免得錯誤搶佔原請求尚未發布的回應。任何情況都不取代原請求的成功／失敗回應。
- **同文字、新 ID** 是新請求，不能用換 ID 繞過 unknown。

「查詢或重送沿用 ID」指**重投完全相同的原請求以取得已保存回應**，不是用同 ID 改成另一個查詢 method；一般查詢直接讀有權限的已提交檔案或摘要，不叫醒 node。重投也受 [Q2](../tick.md) 與 [C-03](../contracts.md) 約束：有可信在途／已接件證據，可等候或以原 ID 取回已保存回應；能證明從未送出才可正常送出。補投原內容只交付同一請求，不是開新嘗試；無法判定曾否執行且無可信去重依據時留 unknown，**不靠定時重送重做工具或 LLM**。

去重證據沿 [B-404](storage.md) 留存：保留期內的必要證據不清，unknown 到期可清，其他未結材料保留；證據仍在就不重收。保留期後清掉證據，不承諾無限期去重，也不另留永久 tombstone。查詢已清掉的材料明說不可取得；有封存位置則告知位置，不假裝內容仍在。不能自動換新 ID 重送來繞過 `unknown` 不自動重做的規則；去重也不保證外部副作用只發生一次。

**驗收**：同 ID 同內容重投不造成重複處理，已有回應時補投的是 git 歷史裡的原 bytes，異內容報衝突；commit 後遺留的收件原件只補清，不再次消費。結果還沒消費不能清理，已過保留期且證據已清的請求不宣稱仍有去重保證。
