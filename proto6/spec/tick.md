# 通用 tick：核心與標準任務表範本

← [規格入口](README.md)｜[daemon](daemon.md)｜[kernel 樹](scheduling/README.md)｜[agent 任務](agent/README.md)

依據：[09-29 新架構](../notes/2026-09-29-kernel-tree.md)、[使用者裁定](../notes/2026-09-29-verdicts.md)第三～十二批、[第十八批](../notes/verdicts/09-special-computing-os.md)、[第十九批](../notes/verdicts/10-tick-minimal-core.md)、[第二十批](../notes/verdicts/11-tick-as-unit.md)。下文「任務表」指 node 內的任務註冊表；與 daemon 登記表的區別見[名詞](terms.md)。

〔使用者方向 2026-09-30，第十九批〕**tick 是一個定期被執行的程式**（`aos-tick`），怎麼被執行不管：daemon、cron、人手都行（B-627）。tick 執行時的目前目錄（cwd）就是它的**管轄區**。〔第十八批〕tick 不跟 once、LLM 嘗試、agent 一輪這些計算單位共用外殼（[T-07](terms.md)）。〔使用者方向 2026-09-30，第二十批〕tick 也是整個 aos 的衡量基準：排程以格計、反應最快是下一格，aos 內部的時長與起算點都用本 node 的格數（B-633、[C-01](contracts.md)）。

〔使用者方向 2026-09-30，第二十批進行順序〕**本篇先假設 cgroup 與 git 都不存在**，把 tick 的基礎設計好；下一步才把這兩個納入。git 開格與收尾任務、存檔點、`aos-cg` 每項一框等已寫好的草稿，都移到篇末「下一步納入：git 與 cgroup」，**不是現行規則**。現行各條裡要靠 git 的保證（例如「先提交再送」「提交後才刪原件」），先寫沒有 git 時怎麼做，並標「下一步納入 git 時補」。

〔使用者方向 2026-09-30，第二十批；推翻第十九批「本篇的保證以標準配備全掛為前提」與完整／備援兩級〕**保證跟著「掛了什麼」走**：tick 核心的四件事（B-626）不靠任何系統級任務也成立；其餘保證看任務表掛了哪幾項系統級任務、任務包了哪些普通程式。〔建議預設，未拍板〕各條只寫「掛了時保證什麼」，沒掛的後果不逐條寫。

## B-626：核心與系統級任務的界線

〔使用者方向 2026-09-30，第二十批追答 8、9；推翻第十九批「三層：核心／標準配備／其他掛載」與疑點裁定 1「標準配備跟核心同一支 `aos-tick`、不另做包裝」〕

1. **tick 核心**（`aos-tick`）只做四件事：同資料夾互斥鎖（B-602）、照任務表依序跑（B-620）、上下層判定（B-628）、每項結束碼紀錄（B-633）。照表跑時另外只認兩件事：停格檔與任務帶的 `user` 跟 tick 不同（B-620）。核心只要 Python 3.9 與 flock，不靠 daemon、git、cgroup、helper，也不靠任何系統級任務。
2. **系統級任務**：從核心拆出、掛在任務表上的程式，以 `kind:"system"` 標記——收件（`aos-inbox`，B-623）、投件與鬧鐘（`aos-outbox`，B-624）、發布摘要（`aos-publish`，B-624）、清理（`aos-clean`，[B-404](base/storage.md)）；〔下一步納入 git 時補〕git 開格與收尾（`aos-git`，篇末）。各自是獨立的程式，**寫在任務表上才跑，沒寫就不跑**；彼此只靠檔案（結束碼紀錄、待送區）交接，不靠任務 `id` 相認。標準任務表範本就是預設的一組（B-629）。
3. **普通程式**：任務會用到的工具，不是系統級任務，要的任務自己在 argv 包——`aos-as`（切換帳號，[B-303](base/identity-resources.md)）、`aos-needs`（前置沒成功就不跑，B-621）；〔下一步納入 cgroup 時補〕`aos-cg`（每項一框，篇末）。
4. **其他任務**：kernel、agent、clock、自訂任務等；它們的外殼、逾時與取消延後（[P-008](protocol/README.md#p-008)）。

- **daemon 不在任務表上**：一格結束後殺殘留、重啟清空、排空停機、helper 都歸 daemon（[B-603～605](daemon.md)）。
- **`kind:"system"`**〔使用者方向 2026-09-30，第二十批追答 9；取代第十九批「留給以後真正屬於標準配備的任務、範本沒有 system 類」〕：意思是「這一項是系統級任務」。只是標記，核心不看，不授予身分或權限；`system` 不開放自訂子名（`system.x` 拒收，[T-06](terms.md)）。〔建議預設，未拍板〕撤掉第十九批暫定的 kind 分段檢查（system 最前、custom 最後）：範本的系統級任務分在頭尾兩段，照陣列順序就好。
- **`aos-clean` 是系統級任務**〔第二十批；取代第十九批疑點裁定 2「範本裡仍是 custom 類」〕：範本裡是 `kind:"system"`。
- **管轄權是約定，不是前提**〔第十九批第 2、5 條〕：tick 對管轄區有最高裁量權，這是 aos 體系裡的約定。Linux 權限上碰不到某些東西時，tick 照樣跑完一格，碰不到的那件照各自規則失敗。管轄區可以重疊，風險自己承擔；aos 體系裡的慣例是不重疊、可以包含（B-628）。

**驗收：**拿掉 daemon、git、cgroup、helper 與所有系統級任務，任務表只放一項 `true`，直接跑 `aos-tick`：互斥、照表跑、上下層判定與結束碼紀錄照常成立；沒有人回 -32601、不投件、不刪收件原件。

## B-602：同一資料夾一次一格：互斥鎖

〔使用者方向 2026-09-30，第十九批，核心〕**同一資料夾同時只能跑一個 tick。** 這把鎖屬核心，不依賴 git、cgroup 或 daemon。

- **認哪個資料夾**〔第十九批第 7 條〕：辨識一個 tick 看資料夾路徑或 inst.json 路徑；給的是 node 資料夾裡的 `.aos/inst.json` 或 `inst.json` 時，一律正規化成那個資料夾（[inst 目標](base/inst.md#inst-目標檔案或資料夾)）。tick 在這個資料夾裡跑，cwd 就是它；argv 見 [P-203](protocol/node.md)。
- **鎖檔**：`.aos/tick.lock`，ignored，不存在就建立。不放 git 管理目錄；`aos-clean` 與一般清理（下一步納入的 git 還原也一樣）都不得移除或替換它。
- **取鎖**：定位資料夾之後第一件事就是對鎖檔取**非阻塞**獨占 flock；拿不到回 75，什麼都不做（也不寫結束碼紀錄），不在程式內重試。全格持鎖。
- **任務繼承**：任務繼承同一個 open file description 的鎖 fd，號碼放環境變數 `AOS_TICK_LOCK_FD`。工具以 fstat 對上鎖檔並核對獨占鎖，才算在 tick 內；沒有繼承鎖就自己取同一把鎖，不能只信環境變數。任務不得解鎖，退出前關閉自己的副本。這是同帳號的合作約定，不是授權。
- **後代也擋下一格**：只要還有任何程序握著這份鎖（例如任務留下的後代），下一格就拿不到鎖、回 75；這一點不需要 cgroup 就成立。〔第二十批〕核心不清後代；daemon 開的格由 daemon 格後收尾（[B-604](daemon.md)）。經 `aos-as` 用別的帳號開的程序同樣繼承這份鎖 fd（[B-303](base/identity-resources.md)）。
- daemon 不同時開同一 node 的兩格，是 daemon 自己的開格安排（[B-601](daemon.md)），不是互斥的來源。

〔使用者方向 2026-09-30，第二十批疑點裁定 8；取代第十九批建議預設「其他寫入者也須協調這把鎖或先暫停 tick」〕**CLI 或工具在 tick 之外自己取鎖改檔，當成外部世界，aos 不管。**〔記錄者理解〕本輪沒有 git，它們的改動就直接留在資料夾裡；下一步納入 git 時再定它們跟提交、還原的關係（篇末）。

**驗收：**同資料夾同時跑兩個 `aos-tick`，一個回 75、不改檔；用資料夾路徑與 `.aos/inst.json` 路徑各跑一次，搶的是同一把鎖；前一格留下握著鎖 fd 的後代時，在沒有 cgroup 的機器上下一格也回 75；沒有 git repo 也取得到鎖。

## B-620：任務註冊表：照表依序跑

〔使用者方向 2026-09-29；2026-09-30 第十九批、第二十批改寫〕任務表只放 `.aos/tasks.json`，陣列位置就是順序。**每項任務是 inst 的超集**：一份 [inst](base/inst.md) 加 aos 的欄位（`id`、`kind`、`methods`）。欄位、JSON 與 schema 以 [P-202](protocol/node.md) 為準，本節只定意思。〔暫定，第二十批新疑點〕`group`、`needs` 兩欄撤：needs 改由包裝 `aos-needs` 表達（B-621）；組只在有 git 還原時才有意思，下一步納入 git 時再定（篇末草稿是「組由存檔點界定」）。

**核心做的**〔第十九批、第二十批，核心〕：

- 開格時讀一次表，只驗四件事：是合法 JSON、`_metainfo` 對、每項（整份 `$ref` 展開後）是合法 inst、`id` 在本表唯一。**表壞了**整表拒絕載入，任務一項也不跑，不退回舊表；stderr 印 `config_invalid:` 加哪裡錯，tick 回 2。
- 照陣列順序一項一項照 inst 跑，前一項結束才開下一項；任務以可信 wait 的正常退出 0 算成功。每項結束後寫進結束碼紀錄（B-633）。
- 每項的環境多放 `AOS_NODE_DIR`、`AOS_TICK_LOCK_FD`、`AOS_TICK_RECORD`，以及這一項專屬的 `AOS_TASK_ID`（任務表該項的 `id` 字串，原樣）與 `AOS_TASK_INDEX`（這一項在任務表陣列的位置，從 0 起）；〔使用者方向 2026-09-30，第二十批命名〕整格共用的叫 `AOS_TICK_*`，這一項專屬的叫 `AOS_TASK_*`。見 [P-203](protocol/node.md)。
- **停格檔**〔使用者方向 2026-09-30，第二十批疑點裁定 1（改）：停掉本格靠偵測檔案，不靠結束碼〕：任務要叫核心停掉本格剩下的項，就建立約定的檔案；核心每跑完一項就檢查，存在就不開後面的項。〔建議預設，未拍板〕檔名 `.aos/tick/stop`（ignored），內容不拘（建議寫一行 UTF-8 原因）；核心取鎖後、開第一項前先刪掉上一格留下的；停下時結束碼紀錄寫 `ended:true` 與 `stopped_after`（在哪一項之後停的，[P-213](protocol/node.md)），這格回 1。**停格檔只管本格**：下一格照常開、照常跑；要擋住之後各格用擋板檔（下一點）。〔使用者方向 2026-09-30，第二十批〕一格結束時留下停格檔，daemon 順帶暫停這個 node（[B-607](daemon.md)）。結束碼沒有特別意義，任務回 3、100 都只是一般的失敗。系統級任務與普通程式要叫停時就建停格檔（例如 `aos-inbox` 看到 `methods` 重複）。
- **擋板檔**〔使用者方向 2026-09-30，第二十批：停格檔與擋板檔並用，本輪就啟用〕：`.aos/tick-blocked`（ignored）擋住之後各格；node 有擋板檔時 daemon 不開格（[B-607](daemon.md)）。〔建議預設，未拍板〕核心取鎖後第一件事就看它：有就不跑任何任務、不寫結束碼紀錄、不加 `seq`、不刪停格檔，stderr 印 `blocked:` 加檔內原因，回 1；所以人手或 cron 直接跑也被擋。誰建：任務（例如發現需要人處理的故障）或人手，內容寫一行 UTF-8 原因；`aos-config-add` 故障時也寫它（[P-207](protocol/node.md)）。誰刪：人手修好後刪，aos 不自動刪。跟停格檔的分工：停格檔只停本格、每格開頭自動清；擋板檔擋之後各格、要人刪。
- **任務的帳號**〔使用者方向 2026-09-30，第二十批疑點裁定 6；取代第十九批「由標準配備的切換使用者開這一項」〕：任務可以帶 `user`，省略就用 tick 自己的有效帳號。帶了而且跟 tick 的有效帳號不同（名稱先解析成 UID 再比）時，核心**不切帳號**：那一項不跑，照 inst 算 125、不寫 `exit`，stderr 印 `user_mismatch: <id>`，紀錄記 `exit:125`，其餘照表處理。要用別的帳號跑，就在 argv 包普通程式 `aos-as <帳號> -- 原指令`（[B-303](base/identity-resources.md)），准不准照該 node 的身分額度核（[B-301](base/identity-resources.md)）。不另設服務帳號（第九批）；要 root 的固定步驟交 helper（[B-609](daemon.md)）；管成員的事由上層 kernel 在自己的 tick 用自己的帳號做。任務類別不授予身分或權限。
- `kind`、`methods` 與其他欄位核心不看：`kind` 只是標記（B-626），`methods` 由收件任務讀（B-623）。
- 核心的結束碼：0 全部成功、1 有任務失敗（含回 125 的）、被停格檔停下或被擋板檔擋住、2 argv 或任務表不合法（尚未開任務）、75 鎖被占；碼表見 [P-203](protocol/node.md)。

其他：

- **`methods`**〔第十七批〕：node 接受哪些檔案請求由任務表決定，每項用 `methods` 宣告自己處理哪些 method；同一 method 只能由一項任務宣告，重複由收件任務驗（B-623）。method 的意思與 -32601 的條件見 [B-501](base/transport.md)。
- **一個 module 一項任務**：收件、產生請求及處理結果都在該項內做；投件與清收件原件交系統級任務，任務不另登記清收件工作。
- 〔使用者方向 2026-09-29〕資源 module、`aos-clean`、收信程式都是同一張表上的項目，不再分 pre／post 掛勾；有權限者同樣能直接跑這些程式（〔第二十批疑點裁定 8〕在 tick 外跑算外部世界，B-602）。資源 module 的啟用與父層限制見 [scheduling/admission](scheduling/admission.md)。

**驗收：**任務帶 `user` 整份照收；帶了跟 tick 不同的帳號時那一項回 125、紀錄記 125，其餘照表跑；包了 `aos-as` 而且有 helper、有通道時以指定帳號跑，任務內用 `AOS_TICK_LOCK_FD` 核對得到獨占鎖，它結束前下一項不開、同資料夾另一格回 75。某項建立 `.aos/tick/stop` 後，後面的項不跑、紀錄 `ended:true` 並記 `stopped_after`、整格回 1，下一格照常跑；任務回 3 或 100 照一般失敗處理，後面照跑。表裡 `id` 重複時一項都不跑、回 2。

## B-633：每項結束碼紀錄與格數

〔使用者方向 2026-09-30，第二十批追答 8、疑點裁定 5〕核心多開放一件事：**本格每一項怎麼結束，寫成一份檔讓後面的任務讀得到**。這份紀錄直接取代第十九批的 git 備援日誌（B-632）；git 與無 git 合成同一種模式。本 node 的**格數**也記在這裡。

〔建議預設，未拍板；位置、欄位與寫法〕

- **位置**：ignored 的 `.aos/tick/current.json`（本格）與 `.aos/tick/last.json`（上一格）。任務環境 `AOS_TICK_RECORD`＝`current.json` 的絕對路徑。格式見 [P-213](protocol/node.md)。
- **內容**：`seq`（格數）、`tasks`（已跑完的項，照順序；每項正常結束記 `exit`，被訊號結束記 `signal`，沒跑到的不列）、`ended`（這格跑完或被停格檔停下時寫成 true，同時加 `exit`＝這格 tick 的結束碼）、`stopped_after`（被停格檔停下時，是哪一項跑完後停的；記那一項的 `id` 字串）、`started_at_ms`（只給人看，不參與計算）。
- **格數 `seq`**：本 node 第幾格，從 1 起，每格加 1：取 `last.json` 的 `seq` 加 1，沒有就從 1 起。跨重啟、換 daemon、改用 cron 都接著數，不倒退。aos 內部的時長與起算點都用它數（[C-01](contracts.md)）。跟 daemon 每筆登記的 `tick_seq`（叫醒後等新格用，登記換了就重算，[B-607](daemon.md)）是兩回事。
- **寫法**：取鎖之後、讀任務表之前：舊的 `current.json` 原子 rename 成 `last.json`，再寫新的 `current.json`（`ended:false`、`tasks:[]`）。表壞回 2 時也寫（`ended:true`、`exit:2`、`tasks:[]`）。每項結束後整份重寫（暫存檔→rename）；跑完或被停格檔停下時寫 `ended:true`。只在持鎖時寫；不 fsync：當機時少一筆，下一格看到的是 `ended:false`，照「上一格沒正常收尾」處理，較保守。
- **讀**：任務讀 `current.json` 看本格前面各項；讀 `last.json` 看上一格有沒有正常收尾（收件任務刪原件就靠它，B-623）。核心自己除了算 `seq` 不讀它做任何決定。「正常收尾」指 `ended:true` 而且沒有 `stopped_after`。
- **寫不進時**（唯讀資料夾、滿碟）：照跑，stderr 印 `record_unwritable`，不設 `AOS_TICK_RECORD`；讀的任務把「沒有紀錄」當「不知道」。
- **擋板檔擋住的格**不寫紀錄、不加 `seq`（B-620），跟鎖被占一樣當成沒開過格。
- **別刪它**：`.aos/tick/` 不被 `aos-clean` 清，下一步納入的 git 還原也不碰它。刪掉了 `seq` 從 1 重數，以格數算的保留期、鬧鐘會算錯，風險自負。

**驗收：**有 `.aos/tick-blocked` 時直接跑 `aos-tick` 回 1、stderr 有 `blocked`、沒有任務跑、兩份紀錄與 `seq` 都不變，刪掉擋板後下一格照常；任務第二項讀得到第一項的結束碼；第三項被 SIGKILL 時紀錄是 `signal:9`；tick 在第二項中途被殺，下一格的 `last.json` 是 `ended:false`；同一資料夾連跑十格，`seq` 從 1 到 10，換成 cron 跑仍接著數；資料夾唯讀時仍照表跑完、stderr 有 `record_unwritable`；鎖被占回 75 時兩份紀錄都不變。

## B-628：上下層判定：預設看資料夾包含、可登記覆蓋

〔使用者方向 2026-09-30，第十九批第 2、8 條，核心；推翻「上下層看登記、與目錄位置無關」〕每個 tick 都有上層與下層。

- **預設上層**：從本 tick 的資料夾往上找，最近一個「有 tick 的資料夾」。〔暫定，計畫疑-10 未答，照 a〕「有 tick」跟投件時「目標是不是 node」同一個判準：資料夾裡有 `.aos/inst.json` 或 `inst.json`（[inst 目標](base/inst.md#inst-目標檔案或資料夾)）。路徑逐段比對，不展開 symlink（沿 [T-03](terms.md)）。找不到就沒有上層。這是純路徑計算，不靠 daemon。
- **登記覆蓋**〔疑點裁定 5、11〕：經 daemon 登記時可以指定上層（`parent_id`），蓋過預設。覆蓋要**新舊兩個上層都同意**；〔建議預設〕舊上層指**目前的有效上層**——第一次覆蓋時就是資料夾推得的那個，再次換上層時是目前覆蓋的那個（B-606）。〔使用者方向 2026-09-30，第十九批疑點裁定 11〕舊上層沒在 daemon 登記（例如 cron 跑的）時，aos 管不著它，**只要新上層同意**。覆蓋後**管轄權仍跟著資料夾**，覆蓋只改管理關係：誰分資源、誰叫醒、誰能解除登記。覆蓋存在 daemon 的登記裡，只在 daemon 底下有；cron 或人手跑的 tick 只看資料夾。登記規則與重啟後怎麼長回來見 [B-606](daemon.md)。
- **有效上層**：有覆蓋就是覆蓋的那個，否則是預設上層。〔建議預設〕daemon 設定列的頂層（root）有效上層是 null，算部署者在設定裡做的覆蓋；它的資料夾上層沒在同一個 daemon 登記時照上一點只要新上層同意（這裡沒有上層，由部署者決定），已在同一個 daemon 登記時整份設定不收（[B-606](daemon.md)）。**下層**是有效上層是我的 tick。
- **換上層兩條路**〔撤第十八批「只有重新登記一條路」〕：
  1. **搬資料夾**：搬進別的 tick 的資料夾，新位置最近的那個自動成為預設上層。路徑就是 id，所以等於舊 id 解除、新 id 重登；引用舊路徑的回址會失效，風險自負（T-03）。
  2. **改登記**：用 `parent_id` 覆蓋（B-606）。
  兩條都要被搬的那棵先暫停、程序全空（沿第十八批 Q10）。
- 〔建議預設，未拍板〕**身分繼承**：inst 的 `user` 省略時繼承上層，指的是有效上層（[inst](base/inst.md)）。
- **巢狀 git**：下一步納入 git 時補（草稿在篇末 B-630）。

**驗收：**`/a` 與 `/a/b` 都有 `.aos/inst.json`、`/a/x` 沒有時，`/a/b` 與 `/a/x/c` 的預設上層都是 `/a`；沒有 daemon 也算得出來。資料夾上層已在 daemon 登記時，只有新上層同意的覆蓋被拒；資料夾上層是 cron 跑、沒在 daemon 登記的，只要新上層同意就收。已覆蓋成 B 再改成 C，要 B 與 C 同意。設定只列 `/a/b` 為頂層、`/a` 由 cron 跑時，daemon 下 `/a/b` 是頂層，直接跑的核心照資料夾仍算出 `/a`。覆蓋後 `/a` 對 `/a/b` 資料夾的管轄不變，叫醒與分資源改由新上層做。

## B-629：標準任務表範本

〔使用者方向 2026-09-30，第二十批追答 8、9；推翻第十九批「標準配備：必須全掛、不能拆、跟核心同一支 `aos-tick`」「功能受限不算沒掛」「有備援就算全掛」〕**標準任務表範本**就是預設的一組系統級任務，加上原本的 kernel／agent 任務。本輪（沒有 git）的順序：

**收件 → 使用者任務 → 投件 → 發摘要 → 清理**

〔使用者方向 2026-09-30，第二十批進行順序、疑點裁定 4〕下一步納入 git 時，在最前面插 git 開格、在使用者任務之後插 git 收尾，投件與發摘要排在 git 收尾之後（保住「先提交再送出」）；〔建議預設〕那時清理移到 git 收尾之前，讓清理變動當格提交（篇末 B-630）。

〔建議預設，未拍板；`id`〕

| # | `id` | `kind` | argv | 做什麼 | 正本 |
|---|---|---|---|---|---|
| 1 | `inbox` | system | `aos-inbox` | 刪上一格已消費的收件原件、替沒人宣告的 method 回 -32601、壞件只報一次、驗 `methods` 重複 | B-623 |
| … | 使用者任務 | kernel／agent／custom | 各自的程式；要換帳號的包 `aos-as <帳號> --`，要前置的包 `aos-needs <前置 id…> --` | 各自 | [B-303](base/identity-resources.md)、B-621 |
| n-2 | `outbox` | system | `aos-outbox` | 投待送檔、經通道送、鬧鐘 | B-624 |
| n-1 | `summary` | system | `aos-publish` | 發布 `published.json` | B-624 |
| n | `clean` | system | `aos-clean --config config/clean.json` | 過了保留期的清理 | [B-404](base/storage.md) |

- **範本只是預設**（[T-10](terms.md)）：任務表可以拿掉任何一項，拿掉了那一項的保證就沒有。例如沒掛 `inbox` 就沒人回 -32601、收件原件也不刪；沒掛 `outbox` 就不投件。
- 預設 kernel 範本（[P-814](protocol/kernel-tasks.md)）與 agent 範本（[P-715](protocol/agent-tasks.md)）都照這個順序：頭一項 `inbox`，中間是原本的任務，尾三項 `outbox`、`summary`、`clean`。
- **不在範本上的**：once 與通道傳訊是任務自己呼叫的通道事務（[B-613](daemon.md)、[B-614](daemon.md)）；鬧鐘歸 `aos-outbox`；重啟清空、格後收尾、排空、helper 歸 daemon（[B-603～605](daemon.md)、[B-609](daemon.md)）。
- **通道**：daemon 開 tick 時給的通道（環境變數、憑證、事務）以 [B-612～614](daemon.md) 為正本；任務繼承這些環境變數，在投件權就是執行權（[T-08](terms.md)）之下這是預期行為。沒有通道（不是 daemon 開的格）只算功能受限：`aos-as`、once、通道傳訊用不了，其他照常。

**驗收：**範本任務表在沒有 git、沒有 cgroup 的機器上照常跑完；拿掉 `outbox` 後不投件、其餘照常；`inbox` 建了停格檔時後面各項都不跑、整格回 1。

## B-621：aos-needs：前置沒成功就不跑

〔使用者方向 2026-09-29〕`needs` 的前置成功才執行。〔使用者方向 2026-09-30，第二十批疑點裁定 2〕needs 做成普通程式 `aos-needs`，核心不做。

- **`aos-needs <前置任務 id…> -- <原指令…>`**（argv 見 [P-204](protocol/node.md)）：讀結束碼紀錄（`AOS_TICK_RECORD`）；每個前置都在本格紀錄裡、而且正常退出 0，才 exec 原指令（結束碼就是原指令的）；否則不跑，stderr 印 `needs_unmet: <id>`，回 125。沒有紀錄可讀也回 125（`no_record`）。前置只看本格，不沿用上一格的成功，也不另做跨格任務排程器。
- 被 `aos-needs` 擋下的項在紀錄裡是 `exit:125`，算失敗；再依賴它的項也會被擋。
- 〔記錄者理解〕本輪沒有 git，也就沒有「組內全成功才一起生效」與失敗還原：失敗任務寫到一半的改動留在資料夾裡，`aos-needs` 只擋後面的項不跑。組與還原下一步納入 git 時補（篇末「存檔點與組」）。
- 任務預設以正常退出且碼為 0 表示本步成功，不代表整件產品任務完成。

**驗收：**`aos-needs a -- …` 在 `a` 失敗或還沒跑時回 125、原指令沒跑，`a` 成功時照跑、結束碼是原指令的；`b` 被擋下後，`aos-needs b -- …` 也回 125。

## B-623：收件：分派、-32601，下一格刪原件（Q1）

〔使用者方向 2026-09-29；第二十批改成系統級任務〕以下是收件任務 `aos-inbox` 做的（B-629），它排在任務表第一項。

**刪上一格已消費的原件**（Q1）〔使用者方向 2026-09-29；2026-09-30 第二十批追答 8 改時機、疑點裁定 5〕：`aos-inbox` 開始時先讀 `last.json`（B-633）；上一格正常收尾，就把 `requests/`、`responses/` 裡跟消費副本（`state/messages/{requests,responses}/<id>.json`）bytes 相同的原件刪掉；不同就報衝突、保留（[B-503](base/transport.md)）；上一格沒正常收尾或沒有紀錄時不刪。〔記錄者理解〕本輪沒有 git，也就沒有「已提交」：上一格被殺時留下的消費副本，任務照 B-503 當成已收，處理到一半的靠任務自己的狀態恢復。〔下一步納入 git 時補〕改成「只刪 HEAD 裡已提交副本相同的原件」，提交前當機的由還原讓原件重收（篇末 B-630）。

**分派與 -32601**〔第十七批〕：列一次 `requests/` 裡已發布的請求；method 沒有任何任務宣告的，照 [B-501](base/transport.md) 回 -32601：原件複製進追蹤區當消費證據、錯誤回應放進待送區（路徑見 [P-202](protocol/node.md)），本格由 `outbox` 投出，原件下一格刪。有宣告的留給那項任務自己讀。

**`methods` 重複**〔第二十批從核心搬來〕：`aos-inbox` 讀 `.aos/tasks.json` 的 `methods`；同一 method 有兩項宣告時不分派任何件，在本 node 寫一件 `config_invalid` 事項（同一問題沿用同一 `issue_id`，[S-405](scheduling/operations.md)），建立停格檔（B-620）、回 1。

**接件前核對回址**〔建議預設，未拍板〕：處理 method 的任務接件前，核對 `reply_to` 是可用的 node 回件位置、目前身分投得進它的 `responses/`；回不了就不接納會產生副作用的請求，保留原件及本地錯誤供修正，不能先執行再假裝已回覆。接納後固定原請求的 `reply_to`，回應照 B-624 投出；投遞遇暫時性失敗只補送同一份回應，不重做請求。`reply_to` 不是來源或授權證明（B-501）。

任務先把原件逐 byte 複製到追蹤區，留下消費證據；組歸屬不另寫 task／group 欄位。〔記錄者理解〕連帶：原件在收件區多留到對方下一格；寄件方的鬧鐘因此可能晚一格才看到「已處理」（B-624）。

〔使用者方向 2026-09-30，第十八批〕**壞掉的收件錯誤只報一次**：`requests/` 裡讀不懂、沒有合法 ID 或安全回址、因而回不了錯誤回應的件，發現的一方（收件任務或宣告該 method 的任務）在本 node 寫一件事項；〔暫定〕`issue_id` 由檔名固定算出（[P-601](protocol/ops.md)），`.aos/attention/` 的 open 或 done 已有同一 `issue_id` 就不再寫，所以同一個壞件不會每格重報。原件留在收件區不動，過了保留期由 `aos-clean` 刪（[B-404](base/storage.md)）。只算 `requests/`，`responses/` 與同 ID 異內容的衝突照各自規則。

〔使用者方向 2026-09-30，第十九批，疑點裁定 7〕**通道上的暫存訊息**：同一 daemon 底下別的 tick 經通道送來的訊息，daemon 放在記憶體；收件任務不代取，由要收的那項任務自己上通道用 `node.take` 取（[B-614](daemon.md)），格式跟檔案收件相同。取走後怎麼落地、要不要留消費副本由那項任務決定；不保證送達，daemon 當掉就丟。〔建議預設〕沒人取的訊息不回 -32601。

請求 ID、同 ID 衝突及保留期內的去重見 [base/transport](base/transport.md)，完整檔案發布與儲存位置見 [base/storage](base/storage.md)，追蹤區路徑見 [P-206](protocol/node.md)。

**驗收：**沒有任務宣告的 method 由收件任務回 -32601，任何任務都沒讀到它，原件在下一格被清；argv 少了 `aos` 或跟 method 不符，由宣告它的任務回 -32601。上一格被殺（`ended:false`）時原件不刪。同一個壞收件連跑多格只有一件事項。兩項宣告同一 method 時收件任務建停格檔、不分派，後面各項不跑。

## B-624：派出：投件、鬧鐘與發摘要（Q2）

〔使用者方向 2026-09-29；2026-09-30 第二十批疑點裁定 4、進行順序〕任務把帶固定 ID 的請求或回應放進追蹤的 `.aos/outbox/`；投件任務 `aos-outbox` 排在使用者任務之後（B-629），投出待送區裡的檔。〔記錄者理解〕本輪沒有 git，「先提交再送」只剩「本格前面的任務都跑完才送」：失敗任務寫出的待送檔也會投出；前面有項建了停格檔時核心不開後面的項，這格不投。〔下一步納入 git 時補〕投件排到 git 收尾之後，只投已提交的待送檔，失敗組的待送檔由收尾還原（篇末 B-630）。LLM／工具結果留待後續格收，不在原地等遠端工作結束。待送封套與鬧鐘紀錄的格式見 [P-206](protocol/node.md)。

投件成功後移除待送檔。投出之後、移除之前當機：下一格再投相同 bytes，接收方依 [B-503](base/transport.md) 去重。能投件不等於能經 daemon 叫醒對方；誰來叫醒見 [S-201／202](scheduling/admission.md)。

〔建議預設，未拍板〕**發布摘要**：發摘要任務 `aos-publish` 排在投件之後，把 `.aos/summary/summary.json` 目前的原 bytes，以暫存檔再 rename 的方式整份發布成 ignored 的 `.aos/summary/published.json`（格式與權限見 [P-307](protocol/messages.md)），給只有摘要讀權的上層讀；讀者一次 open 就拿到完整一版。本輪沒有 git，不保證跟其他檔是同一版；〔下一步納入 git 時補〕從最近 commit 取。發布失敗留舊值、在 stderr 報錯、回 1，下一格再發；過時或缺失不等於 idle。有 repo 讀權的上層讀 `summary.json`，讀目前檔案；都要核對 `node_id` 是自己的直接下層（B-628）。摘要是觀測，不能蓋掉較新的收件事件；上層不為了查詢而叫醒成員 tick，也不因要讀摘要就取得成員 repo 或下層內容的權限。

〔使用者方向 2026-09-29 晚，第十五批〕**投件只查一件事：目標是不是一個 node**（照 [inst 目標](base/inst.md#inst-目標檔案或資料夾)的找法：`target_node` 是資料夾，且有 `.aos/inst.json` 或 `inst.json`）。

- 不是 node，或投件時沒有寫入權限：在 stderr 印一行（`target_not_node`／`target_not_writable`），這封不投、不重試、不改投別處，待送檔跟成功投件一樣移除，不寫待辦。權限補上後要再送，由投件者重新產生待送檔。
- 送出遇到暫時性錯誤：留著待送檔，下格再投。
- 是 node 就投進去，之後 aos 都不管：對方有沒有裝任務、有沒有被 tick、多久才處理，都不過問。

〔使用者方向 2026-09-30，第十九批第 9 條〕**經通道送**：待送的**請求**（`.aos/outbox/requests/`）帶 `channel:true` 時，本格有通道就改用 `node.send` 經 daemon 送（[B-614](daemon.md)），訊息跟檔案投件是同一個 JSON-RPC 物件；〔暫定，交接疑點「通道能否也傳回應」照 a〕回應一律走檔案投件。`urgent:true` 是急件，送到時 daemon 叫醒收件 tick，只在走通道時有用。誰能送看寄件 tick 的帳號對收件 tick 的 `requests/` 有沒有寫權（疑點裁定 6），由 daemon 判。〔建議預設，未拍板〕處理結果：

- 送成功：跟檔案投件一樣移除待送檔。不保證送達。
- `mailbox_full`：留著待送檔，下格再試。
- `forbidden`：跟 `target_not_writable` 一樣印一行、移除待送檔。
- 本格沒有通道（`no_channel`），或其他錯誤（例如收件 tick 不在同一個 daemon 的 `not_registered`、`message_too_large`）：改走檔案投件，照上面的規則。

〔使用者方向 2026-09-29 晚，第十五批；2026-09-30 第二十批改成格數〕**鬧鐘（可選）**：待送封套可帶 `alarm_ticks`（本 node 的格，[P-206](protocol/node.md)）。投出成功後投件任務在 ignored 的 `.aos/alarms/` 記一筆，到期格＝投出那格的 `seq` 加 `alarm_ticks`；到了那一格或之後的第一格，投件任務去看，那封原件還在對方收件區就算沒被處理，在 stderr 印 `request_not_handled`；不寫待辦、不重投、不取消。原件已被取走就算處理了，不印。看完不管結果都刪掉這筆。aos 不為鬧鐘另外叫醒 node，要準時就讓這個 node 有定期 tick；沒設就完全不等、不逾時。經通道送出的不設鬧鐘；本格沒有結束碼紀錄（不知道 `seq`）時也不設，stderr 印一行。〔記錄者理解〕對方下一格收件任務才刪原件（B-623），`alarm_ticks` 要留對方至少多一格的餘裕。〔使用者方向 2026-09-30，第十八批〕agent 範本對每個請求預設帶鬧鐘（[P-706](protocol/agent-tasks.md)）；被丟掉的件沒有鬧鐘、兩者對不上的問題延後（[P-008](protocol/README.md#p-008)）。

可重投同 ID、同 bytes 的封套，這只是補投同一封檔案，不授權重做不明的工具／LLM 執行。〔第十九批〕once 由 module 後續讀已記下的材料，經通道用 `node.mount` 掛到 daemon（[B-613](daemon.md)），不往待送區塞 IPC。無可信結果且不能證明未執行的工作記 unknown，不自動再執行；見 [S-401](scheduling/operations.md)。

## B-627：人手或 cron 直接跑一格：風險自負

〔使用者方向 2026-09-30，第十九批第 12 條；撤第十八批審稿裁定 16「不在框就拒跑」〕`aos-tick` 誰都能直接跑（人手、cron、其他程式），不看自己在哪個 cgroup，照常做完一格；風險由跑的人自己承擔。

## B-630：〔下一步納入〕git 開格與收尾任務

〔草稿，非現行規則；依第二十批追答 8、疑點裁定 3、5〕git 做成任務表上的系統級任務：開格一項、收尾一項，中間每組跑完打一個存檔點（下面「存檔點與組」）。程式是 `aos-git`，argv 草稿見 [P-205](protocol/node.md)。tick 本身不保證整格原子，掛了開格與收尾而且有 git 才有。範本順序：git 開格 → 收件 → 使用者任務（每項後一個存檔點）→ 清理 → git 收尾 → 投件 → 發摘要。

**開格 `aos-git open`**：

1. **擋板**：有 `.aos/tick-blocked` 就不碰工作樹，stderr 印 `tick_blocked`，建停格檔。
2. **看 git 能不能用**：`git --version` ≥ 2.36、`git rev-parse --absolute-git-dir` 成功、有 HEAD；不能用就照 B-632 做。
3. **上一格沒正常收尾就還原**到 HEAD（範圍照 B-622）；正常收尾或沒有 `last.json` 不還原。連帶：格間人手改的、沒提交的檔會被這格的 `close` 一起提交；修復者要自己提交修好的改動。任務自己換了 HEAD 或分支時保留現場、寫擋板、建停格檔。
4. **刪已提交的收件原件**：HEAD 裡有同 ID、bytes 相同的消費副本才刪（取代本輪由收件任務照 `last.json` 刪）。
5. **巢狀排除**：把下層 tick 的資料夾寫進 git 管理目錄的 `info/exclude`（不改 `.gitignore`）。
6. **清掉舊存檔點、打本格第一個存檔點**。失敗就寫擋板、建停格檔。

**存檔點與組**：`aos-git mark` 把此刻的工作樹存成暫存提交，記在 `refs/aos/marks/<任務 id>`（取 `AOS_TASK_ID`），不動分支、HEAD 與 index。相鄰兩個存檔點之間的各項是一組；組內每項 `exit:0` 才成功。`close` 把失敗組改過的路徑回到該組開始時的存檔點；後面的組改到同一路徑時也算失敗、一起還原。範本在每項使用者任務後面放一個存檔點。〔使用者方向 2026-09-29〕組內全成功才一起生效、前面已提交的組不因後面失敗而撤回——納入 git 時照這個落。

**收尾 `aos-git close`**：讀 `current.json` 與存檔點算各組成敗（沒有紀錄就不提交、寫擋板、建停格檔）；還原失敗組；剩下的改動 commit 一次，訊息 `aos-tick <seq>`；清掉存檔點、回 0；還原或 commit 失敗寫擋板、建停格檔，核心就不開後面的投件與發摘要。之後投件只投 HEAD 裡已提交的待送檔、發摘要從 HEAD 取，保住「先提交再送」。

## B-622：〔下一步納入〕git 提交與還原的共同規則

〔草稿，非現行規則；原文〔使用者方向 2026-09-29〕與〔第十八批〕落盤規則保留〕git 任務把每個 node 資料夾當成一個 git repo；外部收件與不想管理的內容放 `.gitignore`；不用帳本或 SQLite。**落盤**〔使用者方向 2026-09-30，第十八批〕：git 最低 2.36，aos 自己的程式每次呼叫 git 都帶 `-c core.fsync=committed,reference`。**管理範圍**：第一格前先有初始 commit（`aos node new` 會建）；以基線 commit 的 ignore 規則管修改、新增、刪除與 index；任務改 `.gitignore` 不能逃出還原範圍；不用全樹 `git clean -x`，不遍歷 git 管理目錄或子 repo；沒變動不 commit。**故障**：寫擋板檔、建停格檔，daemon 依 [B-607](daemon.md) 停格，錯誤摘要走[待處理事項](scheduling/operations.md)；修復者暫停、持鎖、核對、自己提交修好的改動後移除擋板。**原子**只指同一 repo 的已提交版本與恢復基線；ignored 檔、另一個 repo、外部 workspace 與不可逆後果不會跟著還原。〔使用者方向 2026-09-29〕別濫用 git：沒變動不 commit，可定期合併提交、可用 submodule；合併提交要暫停、持鎖，submodule 不承諾跨 repo 的組原子性。
