# 設計原則（使用者說過的，彙整）

← [proto7](../README.md)｜[核心 spec](../spec/core.md)

**這裡只收使用者明確說過、會影響之後所有設計判斷的原則。** 每條附日期與原話出處；新原則往下加。做設計、寫任務書、審建議時先對一遍。

1. **核心極簡，其他做成 module 或選項。** 核心只留必要的；歷史記錄做成可選 module，核心只留「上一次」（10-04，見 [user-advice](../user-advice.md) 與 [proto7-2 對照](../../proto7-2/notes/changes-from-7-1.md)）。
2. **真的兩難就做成選項。**「這些都隨意。如果真的有糾結的，那就做選項」（10-04）。
3. **站在單一 node 的角度，從小處著手。**「這是 nodes 所組成的網路，如果要縱覽，那變數太多。我們從小處着手，先把單元弄好，後續整體拓撲就會自然長出來」（10-04，見 [思考第一輪綜合](thinking/2026-10-04-r1-synthesis.md)）。
4. **上層概念不碰底層。**「團隊這東西只是一個上層概念，不該扯到 daemon／tick 這類底層概念；就算要，那也是給 daemon／tick 添加 module」（10-04）。
5. **agent／LLM 只是途中的一個目標，不是唯一目標。** 目前最有價值的確實是圍繞 agent／LLM 做處理與優化，但後續還會有其他目標（10-04）。所以：
   - **對 daemon／tick 的每條建議都要問**：這只是方便了 agent／LLM，還是同樣能惠及其他需求？只對 agent／LLM 有用的，不進 daemon／tick 核心；要的話做成 module。
   - **kernel 是一堆任務的集合包**，把任務分成兩類並標清楚：**通用任務**（可用於其他用途，例如記帳、配額、排程、事件轉發）與 **agent／LLM 專用任務**（只對 agent／LLM 有用，例如 LLM 端點分配者、摘要者）。
6. **資源可以無限定義，優化目標與分配／排程算法也都無限**（核心 S-17；10-04 擴充見 [LLM 端點是一種資源](2026-10-04-llm-endpoint-resource.md)）。目前的資源定義與五種維度型別先用，使用者覺得只是部分、還會再想。
7. **daemon／tick-tock 保持核心精簡，類似用途集結成模組，乃至模組包。** 使用者擔心一輪輪改進循環讓 daemon／tick-tock 變臃腫（10-04）。新功能預設進模組，不進核心。
8. **kernel 也分層：核心任務、通用任務、agent 任務、LLM 任務……乃至任務包**（10-04）。kernel 是一堆任務的集合包，任務按用途分類、成包提供（擴充第 5 條的「通用 vs agent／LLM 專用」）。
9. **KISS：核心只做最基礎的保護；錯誤分類、納入同一處理分支；誤用不歸組件管。**（10-04）
   - 核心的保護只做最基礎的；不再一個個窗口加檢查。
   - **錯誤先分類**，同類走同一個處理分支（例如：「確定不存在」「不知道（讀不到、壞、型別不對）」「確定壞了」各一條路），不在各處各判一次。
   - **很多東西先默認正常。** 使用者知道這跟改進循環「去查邊緣狀況」有點矛盾，所以界線是：**以錯誤方式操作某組件所導致的問題，不是那個組件的問題，不該由那個組件處理**（例如把生命週期檔換成 FIFO、手改 owner.json、任務故意脫離身分）。這類記為「誤用，不處理」，寫進文件的界線即可。
   - 回歸測試與審查要先分清「組件自己的錯」與「誤用造成的錯」，後者不列為 bug。
