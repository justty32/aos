# LLM 端點是一種資源（使用者想法，2026-10-04）

← [proto7](../README.md)｜[核心 spec](../spec/core.md)｜上一份：[分層想法](2026-10-03-aos-layering.md)

**前半是使用者口述，照原意整理；後半是頂層的對照與待定點，不是決定。**

## 使用者原意

使用者說這就是核心思想裡「**資源可以無限定義**」的例子（S-17；分層想法第 35、68 行）。

- LLM 呼叫端點是一種資源。
- **最低等級**：大家各自打 API 到 LiteLLM proxy。
- **高一點**：開一個 node 專門**獨占**特定端點（甚至整個 LiteLLM proxy），從其他 node 收請求，照請求的優先級分配。
- **再往上包裝**：一個團隊向 LLM 分配者拿到一份使用權，例如「下午兩點到三點，deepseek 端點，額度三百萬 token」；團隊自己的分配者再收團隊內的請求，把這份使用權往下分。

```mermaid
flowchart TD
  P["LiteLLM proxy／端點"] --- R["根分配者 node（獨占端點）"]
  R -- "使用權：deepseek、14:00–15:00、3M token" --> T["團隊分配者"]
  R -- "零散請求，依優先級" --> X["其他 node"]
  T -- "再分" --> A["成員 a"]
  T -- "再分" --> B["成員 b"]
```

## 頂層對照（跟現有東西的關係）

- **分層**：分配者就是 kernel 角色（做資源管理、排程，S-16），一個 node 上的普通 keep 任務。請求與回覆走掛載（S-23）的信箱；daemon／tick 不用認識「LLM」。
- **使用權＝可往下切的配額**：子使用權必須落在父使用權之內（時間窗是子集、額度不超過剩餘）。這就是 astra 調查裡的階層排程、seL4 MCS 的預算下放、resource container（[其他 OS 調查](../../proto7-1/notes/research/2026-10-03-other-os-borrow.md)），以及 proto7-1 的 hsched 探針「慢策略、快執行」。
- **帳**：每筆用量要記到「哪個使用權、哪個任務的哪一次 run」——跟 proto7-2 spec §8「用量以 run 為單位」同一套。

## 待定點（之後做探針時再定；糾結的做成選項）

1. **時間窗用牆鐘還是回合？** 使用者的例子是「兩點到三點」（牆鐘），但核心約定邏輯不依賴牆鐘（S-01 的 `at` 只給人看）。可能兩種都支援：使用權寫 `until` 牆鐘或 `rounds`。
2. **誰強制？** 照現在的合作式協定，成員也能繞過分配者直接打 proxy。真要強制，強制點只能在端點那一端：只有根分配者拿得到真的 key；或由根分配者替每份使用權開 LiteLLM 的 virtual key（LiteLLM 支援 key 帶預算、速率上限與期限，能不能精確用 token 數當額度要再查）。
3. **用不完、提早歸還、收回**：時間窗到了剩下的額度作廢，還是還給上層？上層能不能中途收回？
4. **優先級與搶占**：高優先請求來了，正在用的低優先能不能被打斷？
5. **等待的代價**：請求進信箱後分配者要多快看到——對應第三波的事件喚醒需求（N-83），以及 P2-01 定下的「wake 提前結束回合」。

## 使用者原意（續）：無限的分配算法，依託無限的優化目標

- 在使用權之上，還有**無限的資源分配算法**，各自依託**無限的優化目標**（S-17「排程算法隨意」）。
- **團隊 A** 的目標是 token 消耗最少：內部分配就看哪個成員的方案最簡單，具體怎麼分直接讓 LLM 決定。
- **團隊 B** 要的是正確率：專門開一個 agent 做分配；這個 agent 膨脹到一定程度，會變成一個**專職分配的團隊**。
- 這個分配團隊之後還能**複製**，給其他有需求的 node 或團隊用。

```mermaid
flowchart LR
  G["上層使用權"] --> A["團隊 A 分配者<br/>目標：token 最少<br/>LLM 挑最簡方案"]
  G --> B["團隊 B 分配者<br/>目標：正確率"]
  B -. 膨脹 .-> BT["專職分配團隊"]
  BT -. 複製 .-> C1["給團隊 C 用"]
  BT -. 複製 .-> C2["給 node D 用"]
```

## 頂層對照（續）

- **分配者可抽換，介面要固定**：各團隊的算法、目標、甚至是不是 LLM 都可以不同，但「請求怎麼寫、使用權（grant）長什麼樣、用量怎麼回報」要是同一份格式，否則分配團隊複製過去就接不上。這對應 astra 調查的「可插拔排程＋確定性驗證與退路」與 Plan 9 的服務卡：分配者對外宣告自己收什麼、給什麼。
- **LLM 當分配者的位置**：proto7-1 實驗三的結論是 LLM 放進**快路徑**（每回合排程）不划算；這裡 LLM 是在**慢路徑**決定「這份使用權怎麼切」，切完由確定性的規則執行與擋超額——跟 hsched 探針「慢策略、快執行」一致。上層照樣只看子使用權有沒有超出父使用權，不用懂團隊內部的算法。
- **團隊＝一棵 node 子樹，複製＝搬一份資料夾＋登記**：這對 daemon／tick 有具體要求——
  1. 一個團隊要能**整棵自足**：掛載、名冊用相對於團隊根的路徑，不寫死別人的 node id；
  2. proto7-2 現在 register 是一個 node 一個 node 登記，複製團隊要能**一次登記整棵**（或團隊自己開子 daemon，路一）；
  3. 複製出來的團隊要有自己的身分（不跟本尊共用狀態、帳目分開）。
- **目標本身也是資料**：團隊的優化目標（token 最少、正確率…）寫成檔案，分配者讀它；換目標不用換程式，也方便上層比較各團隊的成效。

## 待定點（續）

6. 分配團隊被複製後，跟本尊是**各自獨立**，還是本尊的改進要能**同步**給複本？
7. 上層要不要**評估**各團隊分配算法的成效（例如同樣額度誰完成得多），進而調整給誰多少使用權？這等於分配算法之上還有一層「分配算法的分配」。
