## 一、一頁看懂現在在哪

### proto7-2 走到哪

- **基礎設施做完、精簡完。** 照你 10-04 的建議重做了 daemon／tick／tock：node 改登記、只剩一張 `tasks.json`、任務資料夾照名字重用、核心只留「上一次」。核心精簡後 lib 從 4501 行減到 2791 行，restart、子 daemon、重試、診斷、稽核都搬成六個模組包。
- **三個任務包在核心上面長出來了：** `step`（步驟表直譯器，就是思考輪說的「語言層」第一塊）、`budget`（先預留再執行再結算的帳本）、`adapt`（鄰居 node 最新值的轉接）。三個包都是核心零改動做出來的。
- **測試 364 項，六輪 astra 對抗式回歸都修完**，今天第七輪又開了 15 條線做審查、調查、提案，程式沒動。
- **還沒做的：** kernel 任務包、事件保存、agent／LLM 作者與 adapt-llm、包的安裝器（aos7-pack）、回到 C++。

### 這個設計穩在哪（六輪＋今天看下來，沒被推翻的）

1. **「核心零新增」一直站得住。** 今天三份落地提案（事件保存、LLM 作者、kernel 任務包）各自獨立審，結論都是「不改 daemon／tick／tock 就能成立」。思考第四～六輪也都說核心零新增。這表示你 10-03 的分層（daemon 是運行層、檔案系統＋tick 是時空、kernel 和 agent 都只是任務）到目前為止沒有被哪個真實需求撞破。
2. **「只留上一次」＋槽重用，長跑檔案數不會長。** 這是你 10-04 要的，六輪長跑都成立。
3. **身分與未知的基本功做對了。** 「不存在」跟「讀不到」分開；程序用 PID＋啟動時間認，不會誤殺別人；多數 SIGKILL 中斷都能接回（step 中斷 9／9、budget 九個持久點 27／27）。prior-art 把 proto7-2 跟 systemd、OTP、Kubernetes、Temporal 比完的結論是：小型監督器與「重新觀測再決定」的骨架已經有了，該借的只是幾條契約的措辭，不是整套架構。
4. **「不知道」不當「失敗」處理**這條原則在核心層做到了，是今天好幾份報告拿來當標尺的東西。

### 哪裡反覆出事（講模式，不逐條列）

六輪回歸加今天的報告，bug 的名字每輪不同，但背後反覆是同一批模式：

**模式 A：該負的義務只記在 daemon 的記憶體裡。** 取消登記後 daemon 被殺，舊任務永遠沒人收（deep-play C8-01）；node 搬走重建，新舊任務一起活（C8-02）；registry 先刪記憶體再寫檔（R8-03）。kernel-pack 報告回頭看 proto7-1 的 kernel，也是「先做動作、再寫紀錄」；hsched 探針「有票沒交付」同一型。這些不是個別 bug，是**「誰欠了誰一個動作」這件事沒有落到磁碟**。

**模式 B：同一個字，不同包不同意思。** 最典型是 `unknown`：budget 的退出碼 3 是「操作結果不明」，但 step 看到的是一份合法的結果檔 `ok:false`，所以走失敗分支，設了 `on_unknown: resend` 也不會重送（play7 A8-10、spec-readability F03、packs-use 4.4、code-quality R8-27 四條線各自撞到）。LLM 作者報告再往上疊一層：核心的「程序事實」、操作的「請求有沒有被受理」、帳務的「扣了沒」是三種不同的不知道。

**模式 C：有條件的保證被寫成絕對保證。** subd 寫「stop 一定留回條」，但核心契約明說回條可能寫失敗（F05）；step 寫「不依賴槽留多久」，補派判斷其實依賴（F06）；once_retry 寫「至少一次」，實際是「及時看到特定 lost 時可補派」（F10、prior-art 11.3）；`log.on` 叫「完整流水帳」，實際寫失敗會靜靜略過（prior-art 11.5）。文件比程式樂觀，人照文件操作就會踩空。

**模式 D：兩個各自正確的機制，交接處出事。** k-crosscheck 說今天剩下的殘洞「集中在兩項已存在機制交接的地方」：已關回合＋最後觀測未知＋回合倒數；清場快照＋官方子程序剛好在那之後出生；once 中斷＋排程變更＋同名 keep 重用槽。play7 的 A8-06（kill 回成功，但那次 run 其實還沒開始跑，之後照樣跑起來）、A8-09（stop 已生效、回條沒寫，重開後誤收）都是交接空窗。而且小修會引回歸：97191272 修了取整，引入兩個新的（A8-01／02）。

**模式 E：「最新值」的檔被拿來當「事件」用。** 回條同名覆寫、`last-round.json` 只留最新、history 是取樣器。第五輪已經把這講清楚（核心只保證「最新值」與「請求＋回條」，逐件不漏是上層契約），今天 event-store 報告用程式行序把每一條流失路徑都標出來，確認這條線沒有錯，但也確認**光靠事後觀測補不回來**。

**一句話：核心本身穩；反覆出事的是「核心交出去的事，上層用什麼契約接住」。** 這也是為什麼下面六題幾乎都是契約題，不是程式題。

## 二、值得深想的六個大問題

每題的結構一樣：為什麼現在浮出來 → 今天哪些證據推的 → 跟你既有想法的關係 → 幾種看法與代價 → 想清楚會解鎖什麼。

### Q1　事件保存到底要保證什麼：「看得到」、「不會漏」，還是「事後能證明」

**為什麼現在浮出來。** 原定落地順序的下一塊就是事件保存。但「保存事件」這四個字底下其實有三種完全不同的需求，今天的報告逼著把它拆開。

**證據。** [event-store](../../../proto7-2/notes/reviews/2026-10-05/event-store.md) 列了 12 條現在會流失的路徑（回合總結被覆寫、換 run 清槽、回條同名覆寫、tasks.json 舊版消失……），然後說：核心零改動能存三種東西——快照取樣、daemon 自己追加的事件、合作任務主動發布的事件；**但「所有底層事件都不漏」要來源端配合（先存待交資料，收到確認才清），單靠 history、JSONL、集中收集都做不到。** 它還指出 kill -9 和整台斷電是兩種不同承諾，現在的寫檔沒有 fsync，只能承諾前者。[prior-art §11.4](../../../proto7-2/notes/reviews/2026-10-05/prior-art.md#114-觀測歷史恢復證據與去重帳不能共用同一保存假設) 說四種讀者（給人看的歷史、恢復工作的證據、防重送的去重帳、稽核）不能共用一套保存假設；[§11.5](../../../proto7-2/notes/reviews/2026-10-05/prior-art.md#115-logon-也不是完整必達的事件來源) 補了一句硬界線：兩段不同的歷史最後留下同一份 `last-round.json`，事後讀的人沒辦法分辨。

**跟你既有想法的關係。** 「核心只留上一次、歷史做成可選 module」是你 10-04 定的；第五輪把它推進成「核心只保證最新值與請求＋回條，逐件不漏是任務包自己的契約」。今天的報告沒有推翻這條，反而證實它：**零改動做得到「觀測」，做不到「必達」。** 問題變成：你要的是哪一種？如果要必達，來源（任務、甚至 daemon）就得參與「先存再清」的交接，這會不會算是碰核心？

**幾種看法。**
- **只做觀測。** 事件保存就是一個更好的 history：取樣、分段、誠實標缺口。代價：kernel／agent 之後要「逐件處理」的需求接不上，agent 看到的世界有洞；好處：零改核心、最小。
- **觀測＋合作來源逐件。** 核心的事繼續取樣，但任務包（step、budget、之後的 LLM 包）用穩定事件 ID 主動發布、保存端回確認。代價：每個包都要多寫一段「待交→確認→清」的契約，加上容量滿了怎麼辦（有限容量、讀者可永久停、來源不停、事件不漏，四者不能同時成立）。這是 event-store 的預設建議。
- **核心加事實出口。** 讓 daemon／tick／tock 在提交結果時留下可重讀的待交證據。代價：這是改核心，而且之前明確否決過同步 hook；要重新提，得正面說「我在改一個已經做的決定」。
- **分級承諾。** 不問「要不要不漏」，改問「哪一類資料要活多久」：給人看的可以漏、恢復證據要活到工作結案、去重帳要活過可能重送的期間、稽核要在發生時就存。這是 prior-art 的分法，跟上面幾條可以疊。

**想清楚會解鎖什麼。** 事件保存是後面兩塊的地基：LLM 作者的輸入要「穩定 ID＋處理回條」才能不重做；adapt 的「逐件 vs 最新值」那題的逐件分支就接到這裡；kernel 要監督進度也靠它。定了保證等級，三份報告裡一半的待決題會自動收掉。

### Q2　「不知道」要不要變成跨包統一的語言

**為什麼現在浮出來。** 三態（是／否／不知道）是從核心一路講到第四輪「三態是回傳型別」的東西。但今天四條線同時撞到：**三態在核心層成立，一跨包就走樣。**

**證據。** budget 退出碼 3 ＝「不知道」，經過 `aos7-step-result` 包裝變成一份合法結果 `code:3, ok:false`，step 看到的是「確定失敗」（play7 A8-10、spec-readability F03、packs-use 4.4）。packs-use 4.3 再補一刀：退出 3 時可能「已結算、只是輸出失敗」，所以連「3＝預留還在」都不絕對。[llm-author §七](../../../proto7-2/notes/reviews/2026-10-05/llm-author.md) 把它疊到三層：核心的程序事實（活著／結束／lost）、操作事實（請求有沒有被受理、有無回覆）、帳務事實（未預留／預留中／已結算／用量未知），而且明說「本地 lost 不證明遠端沒執行；本地 kill 成功不等於遠端取消」。kernel-pack §4.2 也說 kernel 看到 budget 的 unknown 不能推論 step 會重送。你 10-04 的原則 9 說「錯誤先分類，同類走同一分支」——核心做到了，包與包之間沒有。

**跟你既有想法的關係。** 「抽象化→一體性→在特定空間簡單處理」：三態如果是語言的一部分，它應該在所有空間裡意思一樣，不然「一體性」就斷在包的邊界上。另一方面，第五輪也說過「『不知道』是判斷結果，不是統一的等待政策：等、停、查，由工作契約決定」——這句其實已經承認「怎麼處理」可以各包不同，但「它是什麼意思」要不要統一，還沒講。

**幾種看法。**
- **統一成核心語言。** 定一條跨包契約：退出碼、結果檔、暫存器裡的「不知道」長一樣、傳得過去（例如包裝程式看到 rc 3 就不發布結果檔，讓 step 走自己的未知路徑）。代價：要改 step-result 或 step 的映射，等於替所有包立一條規矩；而且三層（程序／操作／帳務）的不知道可能本來就不該合成一個字。
- **各包方言，文件寫清楚。** 承認 budget 的 3 和 step 的 on_unknown 是兩件事，在接法旁放對照表（packs-use 的建議）。代價：每多一個包就多一張對照表；LLM 作者之後讀這些檔案時，得知道每個包的方言。
- **分層命名。** 不統一「不知道」，統一「不知道的是哪一層」：程序層、操作層、帳務層各一個欄位，誰看誰的。llm-author 的三層表就是這條路的草圖。代價：欄位變多，但每個欄位的意思固定。

**想清楚會解鎖什麼。** 這題定了，loop7 第四組（budget unknown 被 step 當失敗）就知道是改程式還是改文件；LLM 包的「候選有效但 usage 未知」雙狀態也有地方放；kernel 規則讀各包的公開狀態時不用猜。

### Q3　義務要不要寫到磁碟成為核心事實——「只留上一次」的邊界在哪

**為什麼現在浮出來。** 模式 A 是六輪裡最頑固的一型：取消登記、node 替換、停止、kill 意圖……每一種「我欠一個動作」都曾經只在記憶體裡。今天 deep-play 用獨立重現（中斷 3／3 漏收，正常 0／3）把它釘死，並點名根因：回收義務只在 daemon 記憶體，「宜持久化意圖」。

**證據。** [evidence-summary deep-play](../../../proto7-2/notes/reviews/2026-10-05/evidence-summary.md#deep-play) 的 C8-01／02；code-quality R8-02／03；play7 A8-05（登記持久化失敗後重送仍回成功）；kernel-pack §6 整節講「先保存意圖，再送控制」，並拿 proto7-1 kernel 的「先 apply 再寫紀錄」當反例；§6.6 把「提交後能不能撤回」列成要你選的政策。prior-art §11.6：子樹清理需要活著的執行者和「不隨父死亡消失的清理意圖」，「這是新增契約的成本，不能包裝成只是多一個設定」。

**跟你既有想法的關係。** 「核心只留上一次」講的是**歷史**不留；但「我還欠一個動作」不是歷史，是**現在的狀態**。這兩個東西被同一條原則掃到一起了——義務沒地方住，就只好住記憶體。另一邊，你 10-03 說「tick-tock 的邊緣狀況默認都正常，出事交給 daemon 處理」；現在的問題是 daemon 自己死了，它欠的事沒人接。原則 7 擔心核心變胖，所以「加一個待辦檔」看起來像在核心加東西；但 kernel-pack 示範了在任務包層怎麼做（state 一次 rename 提交規則狀態＋水位＋pending），證明同一招不一定要進核心。

**幾種看法。**
- **daemon 的義務持久化進核心。** 回收、取消登記、替換這幾件 daemon 自己的事，先寫意圖檔再做；重開時先還債。代價：核心多一個檔、多一段恢復；好處：三對同族 bug 一次收掉，而且這是「daemon 跟 Linux 的介面」本來就該管的程序回收，不算越界。
- **義務全放任務包／模組，核心只給事實。** 核心只保證「我看到什麼」（birth、exit、lost），誰想要「一定收乾淨」就自己當那個活著的執行者。代價：daemon 自己造成的漏收（它殺了一半死掉）沒有包能補，因為包不知道 daemon 欠了什麼。
- **區分「義務」與「歷史」兩種檔。** 把「只留上一次」收窄成「只留上一次的歷史」，另立一條「未履行的義務必須落盤，履行完就刪」。這其實是 kernel-pack、step 的 pending、budget 的 intent 已經各自在做的事，差別只在要不要把它說成一條通則。代價：要重寫一段 spec，並決定 daemon 層適不適用。

**想清楚會解鎖什麼。** loop7 第三組（kill／回收時序，高嚴重度三對）的修法方向；kernel 任務包的 state 設計；之後 LLM gateway 的 `send_intent`、作者的 `publication intent` 都是同一個形狀，定一次通則就不用每包重想。

### Q4　LLM 是「作者」還是「轉換器」；它的不確定性怎麼進三態

**為什麼現在浮出來。** 原定順序事件保存之後就是 agent／LLM。今天 llm-author 報告把「LLM 寫任務」和「adapt-llm」兩件事並排審，發現它們對核心的要求相同（零改），但對**包層**的要求差很多，而且 12 個待決題裡最前面的四個都是方向題，不是技術題。

**證據。** [llm-author](../../../proto7-2/notes/reviews/2026-10-05/llm-author.md)：三個舊實驗的教訓——selfprog 三個模型都算對結果，但「每檔只算一次」0／3（一次性工作被寫成反覆執行）；llmkernel 用 2～5 秒的模型迴圈追 400 ms 回合，追不上還自己改 interval；hsched 讓 LLM 直接挑下一件比確定性規則差，LLM 提政策、確定性 kernel 執行才勉強打平。所以報告的預設是「候選、驗證、發布分開」：模型只產生候選，可信的編譯器與檢查器做驗證，發布是部署政策不是模型的決定。adapt-llm 那邊的核心題是「慢結果」：模型看的是 A 版，回覆時來源已經是 C，`current_only`（可能永遠沒結果）和 `within_age`（消費者得知道它落後）必須明選，而且「不能把 A 的答案改標成 C」。token 這邊：budget 現在只接受「全用或全沒用」，部分結算（預留 1000 用 623）會變 unknown，所以還沒辦法直接接 token。

**跟你既有想法的關係。** 這題直接接你的「程式語言可以給 LLM 使用」三種用法：直接生成、做成工具、生成工具的框架。llm-author 的「固定工具的作者」是第二種（LLM 選工具、組步驟），第一刀刻意不做第一種（寫任意程式）。「LLM 可讀」這條絕殺在這裡是雙向的：LLM 要讀得懂 tasks.json／steps.json 才能當作者，但它寫出來的東西要能被**不是 LLM 的檢查器**驗，才敢發布。第四輪拆開的「幾率性 vs 可預測性」在這裡有實際用途：LLM 輸出不固定（幾率），但格式受 schema 限制、數值有界（可預測），所以機械驗證器能擋一部分，剩下的「結論是不是真的由引文支持」要另一個主體（你說的可預測性相對於觀察者，先不深究，但它已經在門口了）。

**幾種看法。**
- **先當作者（寫步驟表）。** 用 CSV 兩步範例，LLM 組合可信工具，產生候選，人審或固定試驗自動發布。代價：價值要靠「跟手寫步驟表比省多少」來證明，第六輪已經說 step 跟手寫 Python 在單一工作看不出差別；好處：驗證成本最低、有獨立答案。
- **先當轉換器（adapt-llm）。** 一條非控制用途的摘要／擷取鏈，驗「慢答案還有多少可用價值」。代價：要先有單次 LLM gateway 和 token 部分結算（第二刀），而且語意驗收標準（什麼叫轉對）得先寫；好處：這是跨 node 的真需求，而且直接測你「各 node 時間流速不同」那一輪的結論。
- **先做共用的單次呼叫包。** 不管作者還是轉換器，都先把「固定請求→預留→送出意圖→一次呼叫→存原始回覆與用量→結算」這條走通。代價：看不到產品價值，純基礎；好處：兩邊都要，而且它是「LLM 的不確定性怎麼進三態」的實際落點（intent 已存、HTTP 沒發就死，停在 unknown，不自動重送）。
- **先不碰 LLM，把 Q1、Q2 定了再來。** 理由是 llm-author 自己列的交接：作者輸入要穩定 ID＋處理回條（Q1），rc 3 不穿透各層（Q2）。代價：LLM 這條「目前最有價值」的線再往後推。

**想清楚會解鎖什麼。** 12 個待決題裡 8 個跟著這題走；也決定 budget 要不要先長出部分結算；還有「何時升級成完整 agent」這個更後面的題在哪裡開始算。

### Q5　kernel 任務包：是「決策骨架」還是「排程器」；誰有權控制一個槽

**為什麼現在浮出來。** core-slimming §10 把 kernel 拆成核心任務／通用／agent／LLM 四類和十個包，但那是方案。今天 kernel-pack 報告讀完 proto7-1 的 kernel 和探針後，建議第一版**刻意縮到**「觀測—決定—提交—交付—恢復」一條可驗證的路，動作只有綁定原始 run 的 kill，restart、排程、資源分配、多控制者全部後延。

**證據。** [kernel-pack](../../../proto7-2/notes/reviews/2026-10-05/kernel-pack.md) §2「kernel 管決策接續，規則管用途」；§4.1 建議三個現有包保持獨立（裝 kernel 不必連帶裝三包，反過來也是），不照早期分類表加反向依賴；§6.6 把「kill 提交後、同一 run 恢復進度了，還要不要殺」列成必須你選的政策（預設：不自動撤回，釘原 run，因為「保存意圖後、送出前」跟「送出後、記錄前」留下的本地狀態一模一樣，分不出來）；§7.3 說完整 restart 不宜進最小版（舊意圖對 N，槽已經到 N+2，舊 ID 的證據已離開 birth）。§3.1 一句關鍵的：「掛得到某個 node，只表示能存取；不能據此自動取得 kill 權限」——觀測權與控制權要分開列，核心現在不提供仲裁。prior-art §12 的借用順序也一致：有界重試與停手原因、父結束後孩子的處置、意圖版本與已生效版本分開，都放包層。

**跟你既有想法的關係。** 你 10-03 說「有資源管理、排程任務的，就算 kernel」「管任務好說，就是在 tick-tock 的時候對跑著的任務做 kill、restart」「資源和排程算法可以隨意規定」。kernel-pack 等於在問：**「隨意規定」的那層跟「決策怎麼接續」的那層要不要分開做？** 它說骨架不知道「卡住」「預算不足」的業務意義，只管意圖、提交、回條、恢復；規則才管用途。這跟原則 8「kernel 也分層」同方向，但比 core-slimming 的分法更瘦。另外「要管的東西包括另一條時間線怎麼辦→用 daemon ctl」這句，第一版也被排除（不碰 daemon pause／resume／wake）。

**幾種看法。**
- **骨架先行。** 第一版只做可接續的決策骨架＋一個「進度停滯就 kill」的範例。代價：看起來什麼都不會做，排程、資源分配要等；好處：模式 A（義務落盤）在這裡第一次被當成設計原則做出來，之後所有規則都站在它上面。
- **直接做排程／資源包。** 拿 proto7-1 的 sched、supervisor、account 概念直接移。代價：kernel-pack 說這要先決定「誰是啟動者、誰是控制者、誰是准入權威」，否則核心 keep 的補起跟 supervisor 的退避會互相打架（supervisor 探針已經看到）。
- **kernel 不做成包，做成慣例。** 每個任務包自己管自己（step 管重送、budget 管帳、adapt 管新鮮度），所謂 kernel 只是「一組讀公開狀態的規則」。代價：跨包的決策（預算不足要不要 pause node）沒人做，而且 kernel-pack §4.3 已說 pause 不能當硬預算閘門。

**想清楚會解鎖什麼。** 7 個待決題；core-slimming §10 那張十個包的表要不要重畫；還有「多控制者」這件事（agent 團隊互相管）是在 kernel 層解還是 agent 層解。

### Q6　什麼時候從 Python 原型回 C++——以及「回去」的到底是什麼

**為什麼現在浮出來。** proto7-2 已經是第二次重做，測試 364 項、六輪修完，報告開始問「哪些 C++ 設計已被原型推翻」。這是第一次有人把 C++ 現況跟原型逐項對表。

**證據。** [cpp-core §2](../../../proto7-2/notes/reviews/2026-10-05/cpp-core.md)：八項核心差異——C++ 的回合是「一次起整批、等全部結束才推進」，原型是「tick 起了就走，runner 持續監督，tock 收事實」；C++ 用 inbox 搬檔＋every 產指令，原型只有一張 tasks.json；C++ 身分是指令 id＋預猜回合＋裸 PID，原型是 node＋slot＋run 加 PID＋starttime；C++ 歷史按 turn 永久長，原型只留最新；C++ 的 loop 認得 agent（掃 say/、特殊處理 exit 75），原型核心不知道 agent。三個名字會移植錯：C++ `core/tick` 是行事曆判定不是回合啟動器、`aos run` 是外層 loop 不是單次任務監督、`core/tool` 跟 `modules/tools` 不同層。現有 C++ 另有 13 項缺口（啟動失敗被寫成成功、讀不到當不存在、裸 PID 誤停、固定 .tmp 破壞原子發布……），幾乎每一項都對應原型第一、二輪修過的 A2／A3 系列。[§6.2](../../../proto7-2/notes/reviews/2026-10-05/cpp-core.md#62-先後順序與驗收門檻) 給了 0～6 階段的路線，第 5 階段是「C++ 核心接既有 Python 包，不必先把所有 Python 翻成 C++」。平台題：CMake 放行 POSIX／macOS，原型程序判定直接靠 Linux `/proc`。

**跟你既有想法的關係。** 這題是你「抽象化→一體性→特定空間簡單處理」最直接的考題：**要固化成 C++ 的，應該是已經收成整體、在自己空間裡能被簡單處理的那一層。** 現在哪一層算收成整體了？daemon／tick／tock 的檔案契約（spec.md）看起來是；三個包的契約還在每輪改；kernel／agent 還沒有。你 10-03 也說過「tick 是程式還是 lib 都可以，形式無所謂」、「daemon 和 tick-tock 剩下的是技術選型」——所以回 C++ 不是方向題，是「哪個時間點、哪一層、用什麼驗收」。還有一條：原型的測試是黑箱式的（看檔案、看程序），cpp-core §7 說測試語言可以保留、換判定依據就好，這跟你「操作與協議都用 JSON／文字」是同一件事的好處——語言換了，契約不用換。

**幾種看法。**
- **現在不回，等三個包和 kernel 的契約也穩。** 代價：C++ 那邊 13 項缺口繼續躺著，`aos` 執行檔跟原型愈走愈遠；好處：少做一次重寫。
- **只回核心（daemon／tick／tock／run），包留 Python。** 照 §6.2 的 0～4 階段，第 5 階段用混合語言，Python 包透過同一套檔案契約接上。代價：要先凍結相容邊界（舊 `.aos/batch` 跟新槽怎麼隔離、單一 `aos` 子命令怎麼命名、runner 身分辨認要改）；好處：最早能驗「契約真的跟語言無關」。
- **回去時順便定平台。** 只支援 Linux（跟著 `/proc`），還是做 backend。這題不決定，第 1 階段的程序身分就寫不了。
- **不回 C++，Python 就是正式版。** 代價：跟 monorepo「只有一支 `aos`」的設定衝突，而且效能、部署都還沒量；好處：省最多。

**想清楚會解鎖什麼。** 決定要不要把今天的 cpp-core 當成一份「現在不做」的存檔，還是開一條線；也決定 proto7-2 的 spec.md 是不是該被當成「一體性已成立」的那份契約來凍結。

## 三、六題之間的關係（看一眼就好）

- Q1（保存保證）與 Q3（義務落盤）是同一件事的兩面：一個管「發生過的要留多久」，一個管「還沒做完的要不要落地」。兩個都在問「核心只留上一次」的邊界。
- Q2（統一「不知道」）是 Q4（LLM）的前提：LLM 的不確定性進不進得了三態，取決於三態有沒有跨包的意思。
- Q5（kernel 骨架）用到 Q3 的答案（意圖先落盤）和 Q2 的答案（讀各包的公開狀態不用猜）。
- Q6（回 C++）要等「哪一層算收成整體」，而那就是 Q1～Q5 定完之後的 spec。

要拍板的題目，按這六題歸好類在 [r7-decisions](2026-10-05-r7-decisions.md)。
