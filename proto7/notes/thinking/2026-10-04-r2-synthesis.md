# 事實的傳遞與時間確定性：兩份思考報告的綜合（第二輪）

← [事實的傳遞與時間確定性](../2026-10-04-fact-propagation.md)｜原報告：[Fable](2026-10-04-r2-fable.md)、[astra](2026-10-04-r2-astra.md)｜上一輪：[第一輪綜合](2026-10-04-r1-synthesis.md)

題目是使用者 10-04 的想法：一層傳一層會累積延遲和錯誤，中間有 LLM 更糟；時間值得參考；RTOS 的時間確定性交給 kernel 的選項或 module。兩份報告各自獨立寫成。Fable 照使用者追加的兩條標準寫（站在單一 node 的角度看；每條要求標「通用」或「只為 agent／LLM」）；astra 寫在追加之前，本篇**用這兩條標準重新過濾過它的內容**：總覽式的部分改寫成 node 自己做得到的規則，再補上標記。**這些都是提案，不是決定。**

> 事實核對：P2-01 已由頂層定為「固定 interval 時，wake 提前結束回合，並馬上開下一回合」（commit b524c8da），proto7-2 spec §2.1 第 4 步已改成這個語意。兩份報告寫的時候還把它當作未定或矛盾，本篇不再這樣看。

## 結論

1. 失真來自**中繼和讀取時機**，不是來自距離。所謂「邊緣」，不是某一種 node，而是「我掛不到來源，只掛得到轉述者」這種局部狀態，所以要改的是掛載，不是傳輸。
2. 每個 node 都只照同一條局部規則走：**事實寫在自己家、讓人來拉，意圖才寫進別人的信箱**。衍生的東西（摘要、索引）另外存一份，並帶上依據（路徑＋雜湊）；原文不經 LLM。拓撲、中繼、一致切面，都是從這條規則自然長出來的。
3. 時間的部分：**回合只在同一條時間線內比先後，跨線不比回合**，改比「依據了哪一版」（雜湊、`about`／`basis`）。HLC、全域向量時鐘都不要；事件溯源只用在帳這類承諾。
4. RTOS 這題在 aos 上談的是**量得到、准入得了、遲到之後怎麼做先定好**，不是硬即時。核心現在連自己的節拍都量不到，這是唯一真正的缺口。
5. 這輪要核心做的事很少，**全都是通用的**：寫出 tick／tock 的耗時與遲到量；wake 的最短週期做成選項；核心自己的檔把身分欄位補齊。凡是只為 LLM 才需要的（摘要者、可 grep 的驗證器），全部放 module。

## 使用者的回應與駁斥（10-04）

使用者同意失真來自轉手與讀取時機，也同意同一台電腦上原始資訊可以又正確又快地傳。但駁斥「讓下游直接讀來源」能當普遍解法：

- **很多 node 天生就不能吃原始資訊。** 設計 node 架構時，必然有一些 node 只負責單一功能、結構簡單，所有與外界的交互都受限——只吃上級給的，或只吃特定協議、特定格式。這類 node 因原始設計，就是不能直接讀原始資訊，所以資訊傳給它時**必定會被轉手**。
- **這類 node 會非常多。**「相信我，我看到了遠期的未來。」
- **所以「直接分享事實」不可行時，必須有處理**：把原始資訊轉成受限 node 能吃的形式，而且盡量不失真。這會成為 **kernel 的一個任務包**（事實轉手／轉接）。很難，**現在先記下、先不做**，但使用者相信時機很快會到。
- **時間也是原始資訊。** tick、回合數這些關於時間的東西，本質上也是原始資訊，只是取得的途徑更簡單直接；傳到受限 node 時，一樣要面對上面這些轉手問題。所以節拍不只是「核心量不量得到」，也是一種要被轉手的事實。

**對本綜合的影響**：結論 2「拓撲從同一條直讀規則長出來」只對**能直讀的 node** 成立；受限 node 這一大類要靠轉手任務包，屬於待做的 kernel 任務包。

## 分歧與頂層傾向

| 題目 | Fable | astra | 頂層傾向 |
|---|---|---|---|
| 出處放哪層 | 核心 spec 寫一句 `src` 約定，核心自己的檔先示範，但不檢查 | 共用格式放 kernel／module，核心只提供執行脈絡 | **偏 astra，加上 Fable 的「核心檔補齊身分欄」**：`src` 格式寫在 kernel 慣例裡；核心只負責讓自己的檔帶齊 node／tid／run／round（拍板題 2） |
| 事件序號 | `src.seq`：同一個 run 內遞增 | `id`＝發布實例＋事件流＋序號，由單一寫者產生 | 合用：預設 `run.seq`，需要多條事件流的 module 再加流名。都不進核心 |
| 回頭驗 | 有雜湊就不用全鏈：首、尾、跳數跟著事實走，每一手自己留 `about` | 雜湊驗得出內容對不對，但救不回已經刪掉的內容，所以要有保存契約；拿不到原版就回 `unavailable` | **合用**：雜湊負責驗，保存契約負責「還找得到」 |
| wake 讓回合變快 | 核心加 `min_interval_ms`（同時防 wake 風暴、保住「回合≈時間」） | 配額和 lease 指定一條控制時間線，業務的 wake 不會讓它變快；每秒速率交給 monotonic adapter | **兩個都要，各管一件事**：最短週期防的是 CPU 風暴（核心選項）；控制時間線防的是經濟規則被加速（第一輪已定：每份 grant 自己宣告鐘）。**注意**：Fable 寫「預設＝interval＝現狀」，但 P2-01 已經改成馬上開下一回合，所以**預設要設 0 才是現狀**，否則等於把 P2-01 撤掉 |
| 一致切面 | 每個決策都寫 `acted_on`，事後能追溯為什麼不一致 | 提案帶 `read_set`；提交時由權威入口檢查**語意上的前提**（grant 被撤銷就不成立，帳多了一筆無關的收入不必重做） | **astra 走得更遠，合用**：同一個欄位，事後拿來追溯，提交時拿來核對 |
| TTL | 有一條規則：ttl ≥ 刷新週期＋轉手延遲＋讀者思考時間 | 不強制每份事實都填 TTL | 選填；填了就照 Fable 的規則驗 |
| 摘要驗證 | 每條陳述帶 `quote`，驗證器檢查它是不是原文的子字串 | 主張要連到證據；碰到支用、權限、否定、不可逆提交時必須回查原文 | 合用；**嚴格度做成選項**，由探針一決定預設 |
| 准入 | kernel 在登記前算利用率 U，超過界線就拒絕（fleet 的過載剛好被這個界算中） | 只承諾量測和逾期率，不談上界 | Fable 的准入是 kernel 層的選項，可以做；兩邊都不要求核心承諾上界 |

## 各自獨有、值得留的

**Fable**
- **一個 node 只有三個口**：收（我掛了誰）、持（自己的 `.aos/` 和資料檔）、轉（給別人掛的 `out/`）。核心已經有兩個半，只缺 `out/` 這個慣例。
- 讀到一份事實時，**node 只用本地資訊做五個判斷**：是原話還是轉述、多舊、跟現在這版一樣嗎、還有效嗎、我漏了嗎。答案只有四種動作：用、重驗後用、繞過轉述者直接讀、等。
- **取樣定理**：核心檔都是覆寫的暫存器；讀者比寫者慢，就一定會漏（longrun 漏了 33%）。所以節拍的確定性，正是暫存器語意成立的前提。
- 事實照「丟了或重複了會怎樣」分四類：觀測、承諾、意圖、衍生。分類決定用什麼容器，也決定誰保管歷史。另外，**意圖的消費證據要活得比下一次同名意圖久**（A3-01）。
- **資訊年齡（AoI）**＝來源現在的回合 − 我依據的那一回合，用來源的鐘算，是探針的主指標。
- 多人寫的事實改成「一個寫者一個檔，讀的時候合併」：檔名就是出處，不用鎖。proto7-2 §8 的累加其實已經是 G-Counter。
- epoch 不進核心：第一個任務在 node 下寫 `epoch.json`，rm -rf 重建時自然換新。

**astra**（已用 node 視角過濾）
- **混版**：每份資料都是真的，組合起來卻不成立（grant 第 3 版＋帳第 44 版＋目標第 2 版）。直接讀來源解決不了，要靠 `read_set` 加上提交時核對。
- **轉述可以傳遞內容，但不繼承授權**：「LLM 說額度夠」和「帳本接受了預留」必須是不同型別。這條是通用的，不只適用於 LLM。
- `latest_seen`、`consumed_through`、`basis` 是三件事；只有第二件算是對完整前綴的承諾。
- 新鮮度光靠時間戳證明不了：手上拿著舊 grant，分不清它還有效，還是撤銷通知還沒到。所以要標三態：已知相容、已知失效、尚未核對。這就是三態原則套用在事實上。
- 錯誤會被放大：第一層把「未核准」寫成「已核准」，下游十層都忠實引用，看起來就像十個來源一致同意。**信心要照原始來源去重**。摘要也要寫出範圍和分母。
- 發布順序要固定：先保存不可變的版本，再更新 latest，最後才通知。另外，**建立 watch 之後要先重查一次再等**；通知只是提示，最後要靠低頻補查兜底。
- 從 RTOS 借來的：即使做不到準時，也要**先把遲到之後的行為定清楚**（停止新准入、保留未知的在途、不採用過期的結果）。`action_timeout_s` 應該拆成偵測逾時、送出終止、確知結束三段。
- 量測要先定好參考點（S-08：回合從 tick 動作結束才開始）；量測 module 漏了樣本要報出缺口，不能只畫比較慢的那些回合。

## 跟第一輪怎麼接起來（使用權、帳也是事實）

- grant、帳、目標都屬於**承諾類**事實：由發行者或帳本 module 保存精確版本，不套用「只留上一次」。
- **使用權不該被搬運，只該被掛載**（F §9）：`grants/` 是發行者的 `out/` 掛進來，不是複製到我家；複製就是雙重花費的起點。
- 從 node 看，**資源＝動手前必須出示一份 grant 的東西**；「子不超出父」只對照自己手上那一份去查，遞迴在局部看不見。
- 提案帶 `read_set`，gateway 或帳本在提交時核對前提。這是第一輪「強制只放在副作用入口」的延伸。
- wake 會讓回合制的 grant 窗口和每回合補額變快，所以第一輪「每份 grant 自己宣告用哪個鐘」要預設指定控制時間線，不跟業務回合走。
- CRDT 式的計數防不了超支，這跟第一輪「精確額度靠預留＋權威結算」一致。

## 對 proto7-2 daemon／tick 的要求清單

對照 [proto7-2 spec](../../../proto7-2/spec.md) 現況（本篇只讀，不改 proto7-2）。標記：〔通用〕＝把 LLM 換成 cron、備份、CI 一樣成立；〔只為 agent／LLM〕不進核心。

**必須進核心**（只有 daemon／tick 做得到）

| 要什麼 | 標記 | 理由 | 現況 |
|---|---|---|---|
| last-round.json（status 每個 node 一份）加 `timing: {late_ms, tick_ms, run_ms, tock_ms}`，用 monotonic 時鐘算；再加收尾原因 | 核心／〔通用〕 | 只有 daemon 知道 monotonic 時刻；沒有這幾個數，抖動量測、准入、截止排程都做不了 | **缺**：只有 ISO `tick_at`／`tock_at` 和 `early` |
| timeline.json 選項 `min_interval_ms`：wake 提前結束回合後，下一個 tick 不早於上一個 tick＋min | 核心選項／〔通用〕 | wake 是 daemon 做的，下限只能由 daemon 擋；防 wake 風暴（每個 wake 就是一對程序） | **缺**。**預設 0＝現在 P2-01 的行為** |
| 核心自己的檔帶齊身分欄位（node、tid、run、round） | 核心／〔通用〕 | 這是事實出處的地基，也是 log 和重算器要用的 | 部分（Fable 指出 tock.json、exit.json 少了 node／tid，本篇沒有逐一核對） |
| wake 提前結束回合 | 核心／〔通用〕 | 低延遲、閒線省 CPU | **已有**（P2-01）。astra 另外提了「合併 wake 時，不能把處理途中新到的提示一起清掉」，spec 沒寫明，見不確定的事 |
| `until_round` | 核心／〔通用〕 | 第一輪已定 | **已有** |
| status 寫出頻率選項（`status_every_ms`） | 核心選項／〔通用〕 | tickless 全停時，CPU 全花在重寫 status 上 | 缺；**量到瓶頸再做** |

**刻意不進核心**：`src` 格式、序號、epoch（kernel 慣例）；向量時鐘、全域序號、事件匯流排、inotify；擋下沒有 `src` 的檔；固定的抖動上限；核心檔加「人話摘要」或「最近一回合總結」〔只為 agent／LLM，做成 module 讀 last-round 再產出〕。

## kernel 層任務清單

**通用任務**（把 LLM 換成腳本仍成立）
- `factlib`：`stamp`（產生 `src`）、`sha256`、`aoi`、`gap`、`merge_dir`（一個寫者一個檔的合併）。
- 慣例：`out/`（事實）和 `inbox/`（意圖）；四類事實和各自的容器；事實用拉、意圖用推；TTL 規則；先保存、再更新 latest、最後通知。
- `epoch.json`、`seen.json`／`consumed_through` 游標。
- **確定性 copier**（原樣搬運，附上 `src`／`about`；備份、鏡像也是它）。
- 索引暫存器（去哪裡找）；`read_set` 加上入口的前提核對；依原始來源去重的信心計算；保存契約（拿不到原版就回 `unavailable`）。
- clock-quality module（讀 `timing` 算 p50／p99）；登記前的利用率准入；deadline／EDF；watchdog 和執行預算；優先級捐贈；過期結果政策；tickless（閒線 pause、有事就 wake）。
- 控制時間線（配額和 lease 用它，不被業務 wake 加速）；帳本、grant 函式庫、gateway 骨架（第一輪）。
- 複製一群 node、批次登記的工具（團隊相關，照使用者的定案走 module）。

**agent／LLM 專用任務**（沒有 LLM 就沒有這個問題）
- annotator（LLM 摘要者）和 `digest/` 慣例；relay 裡的 annotator 那一半（copier 那一半是通用的）。
- 摘要驗證器：檢查 `quote` 是不是子字串、數字和專名有沒有在原文出現、`about` 解析不解析得到。
- 回查觸發規則（碰到支用、權限、否定條件、不可逆提交時，LLM 讀者必須回去讀原文）；兩層閱讀策略（先讀摘要，再讀原文）。
- 摘要要聲明範圍和分母；摘要失真的量測。
- 第一輪的 LLM 端點分配者；`save` 工具、名冊固定進 prompt（R-2／R-13／R-15）。

## 要使用者拍板的題目

先排除可以做成選項、不必拍板的：**下游預設能不能直接讀來源**（每個 node 群自己設 `mount_allow`；建議預設可以讀，要一致切面的群自己收緊）、**配額跟哪個鐘走**（每份 grant 自己宣告，預設控制時間線）、**摘要驗證多嚴**（驗證器的選項，探針一定預設）、**TTL 填不填**（選填）、**`min_interval_ms`**（選項，預設 0）。真正要定的只剩下面幾題：

1. **核心要不要收「寫出節拍量測」？** (a) 收 `timing`＋`min_interval_ms` 選項＋補齊身分欄；(b) 只收 `timing`；(c) 都不收。**推薦 (a)**：三件都是通用的，每件十幾行，而且只有 daemon 做得到；不收的話，RTOS 這題只能空談。
2. **事實出處（`src`）放哪一層？** (a) 核心 spec 寫約定但不檢查（Fable）；(b) kernel 慣例，核心只負責讓自己的檔帶齊身分欄（astra 加上頂層傾向）；(c) 核心強制檢查。**推薦 (b)**：最貼近「核心極簡」；如果各 module 都在重複補同一項底層資訊，再把那一項升進核心。
3. **LLM 摘要能不能直接當控制依據？** (a) 不能：摘要只拿來導航和提案，權利、數量、期限由原資料和權威入口決定；(b) 可以信任上級的摘要。**推薦 (a)**：其實它是通用規則「轉述不繼承授權」的一個特例；嚴格度做成選項。
4. **哪些資料要承諾追溯得到？** (a) 一般狀態只取樣；授權、帳、重要決策依據由來源保存精確版本，至少留到在途工作結清加上稽核期；(b) 全部只留最新；(c) 全部永久保存。**推薦 (a)**：判準是「會不會影響權利、支出或重要行動」，不另外養一個全域永久總帳。

## 不確定的事

- **真模型的摘要失真率**：repo 裡沒有任何數據，p 全是猜的。可 grep 的 quote 檢查會不會因為太嚴，把正常的改寫（「3612」寫成「約 3.6k」、英翻中）都判成不合格（F 不確定 #1；A #2）。
- **准入常數 c 穩不穩**：fleet 測到 22 ms，proto7-2 長跑測到約 50 ms，差了一倍，可能隨槽數增加（F #2）。
- **`basis`／`read_set` 要記多少才夠**：記太少會漏掉隱含的輸入，全記又太貴（A #1）。
- **wake 加速到什麼程度會變成整體減速**：要找出合併通知、限制開回合頻率的負載界線（A #3）。
- **一個寫者一個檔，對 LLM 讀者的呼叫數成本**：N 到幾十時可能要加索引（F #3）。
- **P2-01 的實作細節**：處理 wake 的途中又來新的 wake，會不會被合併掉；被 wake 結束的回合，`late_ms` 怎麼算。等 `timing` 定了再一起寫明。

## 建議的探針

全部離線，用假 LLM 後端。

**探針一 `relay`：同一套 node 規則，三種掛法**（F §11.4＋A 探針一）
- 擺法：4 個來源、1 個中繼（copier＋假 LLM annotator，故意比來源慢）、4 個讀者。每個 node 都照「五個判斷」的同一套規則走，**只改掛載表**：(A) 只掛 digest；(B) 掛 digest 也掛來源，雜湊不符或 AoI 太大時直接讀來源；(C) 只掛來源。假 LLM 分別注入改寫、遺漏、編造、過時（各 5%），轉送和摘要兩個因素分開量。
- 假設：AoI 是 C < B < A；B 的決策錯誤率接近 C，讀取量卻少很多；驗證器抓得到改寫、編造、過時，抓不到遺漏；中繼調快只會讓 A 的 AoI 下降，B 幾乎不變（中繼省的是 token，不是延遲）。
- 成功標準：方向在 5 個 seed 下都一致；B 的讀取 bytes ≤ C 的 50%，錯誤率 ≤ C＋2 個百分點；驗證器三類抓到率都 ≥ 95%、誤報 0；**不能靠全部拒絕來換零錯誤**（合法案例要全部完成）。

**探針二 `clockq`：節拍品質、准入、wake 下限**（F §11.5＋A 探針三）
- 擺法：先做 `timing` 和 `min_interval_ms`。逐步增加 node（interval 1 s／200 ms／100 ms），畫出 `late_ms` 的 p50／p99 對 U 的曲線。另外放一個吵鬧者每 20 ms wake 一次，比較最短週期 0 和 200 ms 的差別。在被吵的 node 放一個回合制的 grant 窗口和一個控制時間線的窗口，量兩者在牆鐘上多久到期。
- 假設：U < 0.7 時，p99 遲到量 < interval 的 20%；用 U 做准入守得住；沒有下限時，回合制窗口會被調快幾十倍，控制時間線的窗口不受影響。
- 成功標準：上面三條都成立；tick／tock 重疊、還沒關就開、越過 pause 的次數都是 0；「c 不隨槽數增加」這一項允許失敗（失敗就改成每個 node 用自己量到的 c）。

**探針三 `readset`：混版與跨線**（A 探針二，用 node 視角收斂）
- 擺法：bank、objective、worker、observer 四條節拍不同的線（含一個子 daemon）。worker 拿著已撤銷的舊 grant 去提案；提案途中目標換版；observer 暫停期間來源更新了三次；同一路徑重建一個新 epoch，舊提案稍後才到；調整假牆鐘。
- 假設：只要提案帶 `read_set`、入口核對語意前提，就處理得了主要的跨線競爭，不需要全域回合或總帳。
- 成功標準：撤銷之後，舊權利的新准入是 0；每個提案都指得出自己用了哪一版 grant、目標和帳；舊 epoch 的資料不會混進新的；取樣缺口被記成缺口；調整牆鐘不改變純邏輯的決策；條件恢復後，合法工作能繼續完成。
