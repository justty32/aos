# 無限資源／目標／算法：兩份思考報告的綜合（第一輪）

← [LLM 端點是一種資源](../2026-10-04-llm-endpoint-resource.md)｜原報告：[Fable](2026-10-04-r1-fable.md)、[astra](2026-10-04-r1-astra.md)

題目是使用者 10-04 的想法：資源無限定義 → 優化目標無限 → 分配／排程算法無限；分配團隊可以複製；任務排程也是同一套。兩份報告是各自獨立寫的，本篇只整理共識、分歧，以及要使用者定的事。**這些都是提案，不是決定。**

## 結論

1. 兩邊都認為這套想法收斂得成一個小骨架：**使用權（grant）格式＋「子不超出父」的檢查＋帳（預留／結算／歸還）＋請求信箱**；目標、算法、分配者是規則、LLM 還是團隊，全都是可以換的肉。
2. daemon／tick 幾乎不用為它長出新東西，分配者、帳、gateway 都是 kernel 層的普通任務或 module；真正會碰到核心的頂多兩三件小事（使用權到期、團隊相對路徑、整棵登記），而且是不是非進核心不可，兩邊看法不同。
3. 遞迴兩頭都停得下來：往上停在「付錢的人定的目標」，往下停在「額度小到養不起 LLM 分配者，只能用確定性規則」；分配開銷要設**整棵子樹的總上限**。
4. 複製只複製能力（模板），不複製身分、帳與使用權；改進靠鎖版本、明確升級，不自動同步。
5. 強制只能放在副作用入口（持有 key 的 gateway、tick）；LiteLLM 查證後確認**沒有原生的 token 總額上限**，要靠自訂單價把美元換成 token 來繞，而且有沒有超支還要實測。

## 共識

| 主題 | 兩邊都同意的 | 出處 |
|---|---|---|
| 概念模型 | 資源、使用權、請求、帳、目標、算法、分配者七個詞；分配者對上是持有人、對下是發行者，同一個角色一層層重複 | F §1.1、§1.4；A §2 |
| 骨架 vs 肉 | 共用的是格式、檢查與帳；daemon 裡不出現任何資源概念，也不加鉤子讓 tick 去呼叫分配者 | F §8.3；A §2、§10 |
| 代數 | 子窗口 ⊆ 父窗口；切出去的額度不能留在原地再花；集合只能縮小、獨占的只能整份轉交；**優先級不是資源，只在同一個父底下有意義** | F §2.1；A §3 |
| 歸還 | 到期或撤銷只擋新的支用；**在途、結果未知的不退款，留在預留裡**（就是三態原則：不知道就不動） | F §2.1；A §3.6 |
| 精確額度 | 要靠支用前預留、支用後結算，結算以 gateway／供應商回條為準，不信任務自己報 | F §9.3；A §1、§11.3 |
| 遞迴止點 | 往上止於使用者給的總預算與目標；最底層一定要有不用 LLM 的退路；分配者的開銷要封頂 | F §2.3、§3.3；A §4 |
| LLM 的位置 | 只放慢路徑，提出方案就好，由確定性驗證器擋越權；hsched 的實驗顯示 LLM 策略還沒贏過手調規則 | F §2.3；A §1、Q4 |
| 目標 | 寫成資料，先過硬限制、再比軟偏好，不壓成單一加權分數；不同團隊的目標不能互相比，上層只用自己的指標去看 | F §3；A §5 |
| 驗收 | 「正確率」「token 最少」都要有人定義什麼叫交付，而且驗收不能由團隊自己來（防 Goodhart） | F §3.3；A §5 |
| 複製 | 模板／實例分開；使用權、帳、在途請求一律不複製（不然會雙重花費）；狀態和帳永遠不合併 | F §4；A §6 |
| 時間 | 跨 daemon **不換算回合**，用發行者的鐘判定；讀不到權威時鐘就不准新的支用，在途的照常對帳 | F §6.2；A §8.2 |
| 分配者掛掉 | 已發出的使用權寫在檔案裡，不會跟著分配者一起死；新請求先在信箱排著，由確定性規則接手 | F §7；A §9 |

## 分歧與頂層傾向

| 題目 | Fable | astra | 頂層傾向 |
|---|---|---|---|
| 核心改動 | `until_round`、mount 相對路徑兩件直接進核心；整棵登記看走哪條路 | 都先做成 module（部署時展開模板、逐 node 登記），核心等需要的保證明確了再動 | **`until_round` 進核心**：kernel 死掉後要讓 tick 到期就不再起任務，這件事 module 做不到。**相對路徑先走 module**：複製工具展開時改寫 tasks.json 就行，探針做下來嫌麻煩再談核心（拍板題 1） |
| 速率切分 | 任一時刻 Σ 子 ≤ 父；窗口不重疊的子可以各拿全額 | 突發量（burst）也要一起切；第一版所有支用都經共同祖先的閘門 | **astra**：比較保守，第一版也比較簡單 |
| 開銷上限 | 每份使用權寫 `allocator_cost_cap: 0.05`；從 hsched 推出 LLM 分配者的最小使用權大約是單次決策成本的 100 倍 | 每層 5% 不夠（20 層後只剩 0.95^20 ≈ 36%），要設整棵子樹的總上限 | **合用**：用子樹總上限封頂，用 Fable 的門檻（`min_llm_grant`）決定哪一層以下禁用 LLM |
| 資源型別 | kernel 只認五種維度型別（consumable／reclaimable／capacity／rate／set），任何資源都是這五種的組合 | 每種資源由自己的 module 說清楚怎麼切、怎麼組合、怎麼准入、怎麼量、怎麼結算；不認識的就拒絕 | **合用**：共用函式庫內建五種型別當預設，資源 module 可以另外帶自己的規則；兩邊都承認型別未必封閉（捆綁資源、人的承諾） |
| 強制欄位 | grant 加一欄 `enforcement: key/os/tick/audit`，讓人一眼看出這條界線是牆還是承諾 | 保證是部署本身的性質，改欄位升級不了；用 `assurance` 欄描述 | 實質相同。**欄位只描述現況**，由 gateway 或部署填，不由發行者自己宣稱 |
| LLM 端點強制 | 每個團隊一把 LiteLLM key，團隊內部合作式＋稽核 | 原型先由根 gateway 持有 key；virtual key 之後當第二道限制 | **原型照 astra**（假 gateway，不碰真 key）；真部署再加 Fable 的每團隊 key（查證過，team 預算約束得了成員） |
| 時鐘寫法 | 每份使用權宣告自己用哪個鐘，跟著資源的原生時鐘走（token 用回合、人和供應商用牆鐘） | 邏輯期限一律帶時鐘世代與邊界（`completed_tock`）；牆鐘另外由 adapter 檢查，條件全都成立才放行 | **合用**：grant 可以同時帶多個期限條件，取 AND；回合期限照 astra 標世代與邊界 |
| 帳格式 | `events.jsonl`，動詞是 split／reserve／settle／return（可回收資源再加 release） | 帳戶之間的 transfers（複式），守恆自動成立 | 用 astra 的 transfers 當內部形式，Fable 的動詞當 `op` 標籤；探針一兩種都可以試 |

## 各自獨有、值得留的觀點

**Fable**
- 資源是用「有沒有人站在中間」來定義的：誰能站到消費者和那樣東西之間，誰就定義了一種資源，而站的位置就是信任邊界。
- proto7-2 其實**已經有三種使用權**：tasks.json 的一項（槽＋`from_round`）、`mounts`／`mount_allow`、`paused.json`。「任務排程也是同一套」在基礎設施層已經成立，tick 就是確定性的執行者。
- 分配開銷應該跟「決策次數」掛鉤，不是跟「成員數」掛鉤。團隊 A 那種「LLM 決定每一筆」只適合小團隊，團隊一大就要變成「LLM 提政策、規則執行」。
- 評估分配者的陷阱：hsched 各組只差幾個百分點，比重跑之間自己的差距還小。所以上層應該**先看守不守規矩、再看成效**，而且要慢慢調。
- pause 的時候回合窗口會「拉長」：對 token 額度是優點，對牆鐘資源卻是 bug。
- key 可以直接當成使用權本身（capability），撤銷就是刪 key。

**astra**
- **使用上限、競爭份額、供應保證是三件不同的事**：「最多 3M」不保證一小時內拿得到 3M（`supply_promise`）。
- **帳守恆不代表授權正確**：ledger 探針已經實際驗到，外洩的 grant 被別人花掉，帳卻完全沒錯。
- proto7-2 的 `usage.json` 只是取樣下界，不能拿來當精確額度。
- 重啟、複製、遷移是三種不同的操作，直接複製一個執行中的資料夾，就是在把重啟誤做成雙重花費。
- 子樹（團隊）、委派（使用權）、服務依賴（圖）、付款歸屬（跟著每筆請求）是四種結構，不要混在一起。
- 分配者接管時提高**寫入世代**，閘門就會拒絕舊程序寫進來的交易；撤銷要先封住新的支用，再搬餘額。
- 「token 最少」如果沒有交付條件，最佳解就是什麼都不做；上層交給子團隊的除了 grant，還要有**交付契約**。
- 上層評估該問的是「再給這個團隊一小份額度，預期能多拿到什麼成果」，不是平均分數。
- 子 daemon 的空間根有邊界，不能假設掛得到父根，所以需要跨空間信箱。部署時先建好但不啟用，全部登記完再發啟用標記。
- 時間窗用半開區間 `[from, until)`；牆鐘回撥不能讓已經關掉的窗口重新打開。

## 對 proto7-2 daemon／tick 的要求清單

對照 [proto7-2 spec](../../../proto7-2/spec.md) 的現況（本篇只讀，不改 proto7-2）。

**必須進核心**（不做就接不上，而且只有 daemon／tick 做得到）

| 要什麼 | 理由 | 現況 |
|---|---|---|
| tasks.json 項目加 `until_round`（和 `from_round` 對稱） | 讓「回合槽使用權」有期限，分配者死了，tick 到期也會停手不再起 | **缺**（只有 `from_round`） |
| 回合、槽、run、三態判定維持可靠語意 | 所有 gateway 和帳都建立在這上面 | 已有 |
| 事件喚醒（只在有需要時做） | 請求進信箱要多快被看到，取決於回合中的 `wake` 有沒有效 | **缺**：spec §2.1 寫回合中 `wake` 無效，P2-01 還等使用者決定；資源筆記寫「P2-01 定下 wake 提前結束回合」，兩份文件**不一致**。兩邊都建議先量延遲再說 |

**可以先留在 kernel／module**（核心不懂資源）

| 要什麼 | 理由 | 現況 |
|---|---|---|
| 團隊相對路徑（mount 相對團隊根） | 複製工具展開模板時改寫就行；嫌麻煩再談核心（Fable 主張直接進核心） | 缺；現在 mount 是相對空間根 |
| 整棵登記 | 走路一（子 daemon）就天然整棵；不然由部署 module 逐 node register，最後再發啟用標記 | 路一（`subroot`）已有；批次 register 缺 |
| grant 函式庫（`within`／`split`／`expired`＋五種型別） | 分配者和 gateway 共用；可以從 hsched 的驗證器演化出來 | 缺（探針有雛形） |
| 帳本 module（單一寫入者、只加不改、去重、寫入世代） | 精確額度靠它；它自己保留歷史，不適用「核心只留上一次」 | 缺（ledger 探針有雛形）；spec §8 只有取樣下界的 usage |
| gateway module（每種資源一個） | 強制點；結算證據來自這裡 | 缺 |
| 請求／回條信箱格式 | 分配團隊複製過去要接得上；只是文件約定 | 檔案與 mount 已有，缺業務格式 |
| 稽核 module（讀 LiteLLM spend log 比對帳） | 合作式下至少要看得到有人繞過分配者 | 缺 |
| 模板升級 | 鎖版本、`restart reload` | 已有（reload 回條附 diff） |
| 帳和交付物放在槽外 | 槽會被 tock 刪掉 | 已有約定（W7） |
| 跨空間信箱 | 子 daemon 掛不到父根 | 缺 |

## 使用者的回應（10-04）

- **看的角度：站在 node 自己的角度，從小處著手。**「這是 nodes 所組成的網路，如果要縱覽，那變數太多。我們從小處着手，先把單元弄好，後續整體拓撲就會自然長出來。」Fable 的資源定義「很接近了，但那是整體總覽的看法」，直覺上只是部分；五種維度型別是基本維度、很好，但直覺上同樣有些片面。使用者後續還會再想，**目前先用這套**。
- **第 1 題：可以。** `until_round` 進核心；相對路徑先走 module。
- **第 2 題：團隊只是上層概念，不該扯到 daemon／tick 這類底層概念**；就算要，也是給 daemon／tick 加 module。所以不走「每個團隊一個子 daemon」也不走「整棵登記進核心」——團隊是 kernel 層（node 之間的約定）的事。
- **其餘：隨意**（照推薦；能做成選項的做成選項）。

## 要使用者拍板的題目

先排除可以做成選項、不必拍板的：**窗口用哪個鐘**（每份 grant 自己宣告）、**分配開銷誰付**（`cost_cap` 欄）、**到期沒用完的額度怎麼辦**（`on_expire` 欄，預設「沒花的還給父、在途不動」）、**LLM 分配者要不要開**（goal 的 `decide` 欄，預設確定性規則）、**複本要不要同步改進**（兩邊都說鎖版本、明確升級，自動同步日後再做成一種更新政策）。真正要定的只剩下面幾題：

1. **核心要不要收兩個小改動？** (a) 收 `until_round`，相對路徑先走 module；(b) 兩件都進核心；(c) 都不收。**推薦 (a)**：`until_round` 是幾行的事，module 卻做不到；相對路徑在複製工具裡就能解決，符合核心極簡。
2. **團隊的邊界用什麼做？** (a) 路一：每個團隊一個子 daemon；(b) 路二：同一個 daemon 批次登記整棵。**推薦 (a) 先做**：核心不用改，身分和時鐘天然分開；代價是多一個程序。探針二做完再看要不要補 (b)。這題兩條路都能保留，真的糾結的話也可以做成選項。
3. **第一階段要給哪種信任保證？** (a) 合作式＋明確的閘門與帳，LLM 端點日後加每團隊一把 key 當第二道；(b) 一開始就做不可繞過的隔離（憑證、執行身分）。**推薦 (a)**：(b) 等到真的要防不受信任的任務花真錢時才需要，而且靠補欄位做不出來。
4. **grant 第一版承諾到哪？** (a) 只承諾上限與資格；(b) 連最低供應量或完成期限一起保證。**推薦 (a)**：(b) 需要再建一套供應能力和保留容量的模型，等第一個真的需要保證的資源出現再加。
5. **上層要不要依成效調各團隊的配額（「分配算法的分配」）？** (a) 第一版只看守不守規矩（越權、回報、在途堆積）；(b) 也照成效調。**推薦 (a)，並用探針三先測成效訊號是不是雜訊**：兩邊都懷疑在現在的規模下，成效差距會被重跑之間的雜訊淹掉。測出有訊號，再改成 (b)。

## 不確定的事與查證

**兩邊都不確定的**
- 共用介面能保持多小：五種型別或通用外殼，是否涵蓋得了捆綁資源（GPU＋CPU 槽）、人的承諾、不可逆動作（F 不確定 #3；A #1）。
- 評估分配者到底是訊號還是雜訊；如果是雜訊，「演化」這個敘事就只剩複製、沒有天擇（F #2；A #3）。
- 真實端點能給多完整的用量與副作用證據，例如用量上界、取消、去重（F #1；A #2）。

**查證結果：LiteLLM virtual key**（2026-10-04 查官方文件）
- **沒有原生的 token 總額上限**。key 和 team 的預算是美元（`max_budget`、`budget_duration`、`soft_budget`），另外有 `tpm_limit`／`rpm_limit`（速率）、`max_parallel_requests`、模型清單、到期。`tpm` 是速率，不是總量。來源：[Budgets, Rate Limits](https://docs.litellm.ai/docs/proxy/users)、[Virtual Keys](https://docs.litellm.ai/docs/proxy/virtual_keys)。
- **團隊預算約束得了成員**：key 屬於某個 team 時，只執行 team（和 team member 的 `max_budget_in_team`）的預算，個人預算不適用。所以「每團隊一把 key」在美元層面可行。來源同上。
- **繞法**：在 proxy 設定的 `model_info` 寫 `input_cost_per_token`／`output_cost_per_token`（例如都設成 0.000001），讓 1 美元＝100 萬 token，`max_budget: 3` 就約等於 3M token。注意：**成本設成 0 的模型會跳過所有預算檢查**，不能設 0。來源：[Custom Pricing](https://docs.litellm.ai/docs/proxy/custom_pricing)。
- **待查**：預算是在請求前拿已累計的花費去檢查，還是會預留？單次大請求或並行請求最多會超支多少？一把 key 能不能發子 key？這些文件沒寫，要開一次本機 LiteLLM 搭假後端實測（不打真模型）。

## 建議的探針

三個都是離線的（假 LLM 後端，政策回答用預錄），合併自兩邊的探針設計。

**探針一 `split`：多資源、三層委派、帳與失敗**
- 擺法：根→團隊→成員三層；三種資源：token 額度、速率（含突發量）、檔案獨占寫權；假 gateway 計費會隨機浮動，並有一定機率不回條。注入的狀況：分配者被 kill、重送請求、複製 grant、同時搶最後額度、到期時還有在途、舊寫入世代、壞的 LLM 提案（超過父額度、過期、試圖 pause 控制 node）。
- 假設：用共用的 grant 格式加上每種型別的檢查，擋得住所有越權；到期和崩潰都不破壞守恆；換資源型別不用改 daemon／tick；子樹的管理開銷上限有效。
- 成功標準：越權生效 0 次、負額 0 次；每個事件前綴都守恆（獨立重算器驗證）；重送不重複扣帳；在途未知不被釋放；兩個寫者同時提交成功 0 次；開銷到上限後只走退路，回條標明原因。

**探針二 `clone`：複製、跨節拍、跨空間**
- 擺法：把團隊 B 的模板複製成 C，走路一（子 daemon），A、B、C 的節拍分別是 10、70、200 ms；複製時 B 手上有在途工作；部署中途停掉再重跑；升級 B 的模板，C 照舊；用假牆鐘測回撥，以及暫停中牆鐘期限到期。
- 假設：模板展開後不含任何部署絕對路徑；C 不繼承 B 的使用權、帳、在途工作；跨節拍不需要回合匯率；部署到一半不會產生業務副作用。
- 成功標準：在 C 裡 grep 不到 `teams/b`；C 的 `grants/` 在根發新的之前是空的；權威期限過後新的准入 0 次；回撥不會重開窗口；升級只在 C 自己 reload 之後才生效。另外記錄兩件事：複製要幾步手工（決定相對路徑要不要進核心）、請求到准入的延遲分布（決定 `wake` 要不要改）。

**探針三 `select`：不同目標與分配算法的分配**
- 擺法：兩個團隊共用同一份工作 trace（借 hsched）。A 的目標是「必要工作達標後成本最低」，B 的目標是「按期合格的件數最多」；再加一個專挑簡單題的作弊隊。比較三種分配方式：固定規則、每件問假 LLM、每 N 回合更新一次政策。上層照父指標調配額，每個窗口最多動 10%，連續兩個窗口同方向才動。
- 假設：管理成本封頂得住；有父驗收時作弊隊會輸、沒有時會贏；配額移動不會震盪。
- 成功標準：作弊隊在兩種設定下的配額變化方向相反；100 回合後配額沒有來回翻轉；子樹的管理支出 ≤ 5%。**用 5 個 seed 看方向是否一致這一項允許失敗**：如果不一致，結論就是「這個規模下評估分配者只是雜訊」，拍板題 5 就維持 (a)。
