# 事實的傳遞與時間確定性——思考報告第二輪（Fable）

依據：`proto7/notes/2026-10-04-fact-propagation.md`、同日 LLM 資源筆記與第一輪綜合（`notes/thinking/2026-10-04-r1-synthesis.md`，含使用者 10-04 的回應）、`proto7/spec/core.md`、`proto7-2/spec.md`＋`lib/aos7_daemon_timeline.py`、兩份調查報告、探針 README（event、tickless、fleet、longrun、blindread、nest3、subtimeline、hsched、ledger）、proto7-1 問題清單（R-2、R-13、R-15、K-6、D-2）、astra 第二輪回歸（負載段、A3-01～09）。只讀 repo，沒跑模型。接著上一輪 `fable-report.md` 想，不重複那裡講過的。

**視角照使用者 10-04 的回應改：站在單一 node 的角度。** 一個 node 收到、持有、轉出事實時，它自己要知道什麼、做什麼判斷、要什麼介面；全局拓撲當成這些單元規則長出來的結果，不先設計。團隊只是上層概念，不碰 daemon／tick。

**照 `proto7/notes/principles.md` 第 5 條標記**：對 daemon／tick 的每條要求都標〔通用〕（同樣惠及非 agent／LLM 的需求）或〔只方便 agent／LLM〕（後者一律不進核心、做 module）；kernel 層任務分〔通用任務〕與〔agent／LLM 專用任務〕。彙總在第 10 節。

把握程度：【高】＝repo 證據或數學直接得出；【中】＝合理但沒驗；【低】＝猜測，值得探針。

## 0. 先講六句最重要的話

1. **一個 node 只需要三個口：收（我掛了誰）、持（我自己的 `.aos/` 與資料檔）、轉（我寫在自己家給別人掛的 `out/`）。** 它不需要知道自己在樹的第幾層、不需要知道誰是中心誰是邊緣；「邊緣」不是一種 node，是「我掛不到來源、只掛得到轉述者」這個**局部狀態**。所有拓撲（鏈、扇入、一致切面、索引）都是每個 node 各自決定「掛誰、信誰、轉什麼」長出來的（第 1 節）。【高】
2. **事實用拉的，意圖用推的。** 一個 node 轉出事實的正確動作是**寫在自己家**（路徑就是出處、不複製就不會改寫、讀者自己決定要多新）；只有**意圖**（請求、控制檔、grant）才寫進別人信箱，因為意圖必須被對方注意到。「一律只吃上級傳來的」是把事實當意圖推，每推一層就失真一層。【高】
3. **核心其實已經有一套事實模型，只是沒命名：所有核心檔都是「帶回合號、覆寫、最後寫入者贏」的暫存器。** 暫存器對讀者有一條取樣定理：讀者週期必須短於寫者更新週期，否則一定漏（longrun：輪詢 150 ms 的任務漏掉 33% 的 tock）。這把「事實的傳遞」和「RTOS 時間確定性」接起來——**讀者節拍的確定性，就是暫存器語意成立的前提。**【高】
4. **內容雜湊比轉手鏈更有用。** 事實（或摘要）帶著它所依據的來源檔的 sha256，node 不用讀整條鏈、不用任何時鐘，就能回頭驗「這講的是不是現在這版」。回合號只能在一條時間線內比先後；雜湊能跨時間線偵測**過時**與**改寫**，而且不靠寫的人誠實。**編造**是唯一雜湊抓不到的，它的特徵是「出處解析不到」，用驗證器擋。【高】
5. **RTOS 能借給 aos 的不是硬即時，而是「可量、可准入、有下限」**：tick／tock 的耗時與遲到量要寫出來（proto7-2 現在**沒寫**，只有給人看的 ISO 時間）、登記 node 前算一次利用率（fleet 的過載剛好被 Liu–Layland 式的界算中）、wake 提前結束回合時要有**最短週期下限**，否則有 `.aosd` 寫權的人就能把別人的回合時鐘調快，上一輪以回合計的使用權窗口會在牆鐘上提早到期。【中偏高】
6. **這輪對核心提的三條（timing、min_interval、`src` 約定）全部通過「把 LLM 換成 shell 腳本還成不成立」的檢驗；真正 agent／LLM 專用的只有「摘要者＋可 grep 的驗證器」那一組，全放 module。** 事實傳遞的問題本身不是 LLM 問題——log 管線、備份、CI 一樣有出處、過時、重複；LLM 只是把「改寫」和「編造」兩種失真加進來的那一跳。【高】

## 1. 從單一 node 看：收、持、轉

### 1.1 node 的三個口，proto7-2 已經有兩個半

| 口 | 是什麼 | proto7-2 現況 | 缺什麼 |
|---|---|---|---|
| **收（intake）** | 我讀得到的別人的東西 | `mounts`／`mount_allow`、執行中加掛（S-23） | 無——這就是「我信誰」的宣告 |
| **持（hold）** | 我自己的狀態 | `.aos/`（核心暫存器：round、last-round、tock、birth…）＋槽裡任務自己寫的檔（state.json 接前任） | 一句約定：哪類東西能用覆寫、哪類不能（1.3） |
| **轉（publish）** | 我寫給別人掛的東西 | 沒有正式名字；信箱 `inbox/` 是給**意圖**用的 | 一個慣例目錄（例如 `out/`）＋每份檔帶 `src`（1.4） |

核心不需要為第三個口加任何功能：`out/` 只是 node 資料夾下一個普通目錄，別人用現有 mounts 掛。缺的是**慣例**。【高】

### 1.2 收：一個 node 讀到一份事實時的五個判斷

這五個判斷全部只用本地資訊（我掛到的檔、我自己的 round.json、對方檔裡的欄位），不需要任何全局知識：

| # | 問 | 看哪裡 | 判不出時 |
|---|---|---|---|
| 1 | **這是原話還是轉述？** | 有沒有 `about`（有＝衍生）、`hops.count` | 沒 `src` 的檔當轉述 |
| 2 | **多舊？** | 來源的 `src.round`／`seq` 對來源**現在**的 round.json（掛得到才行）；算 AoI（2.3） | 掛不到來源＝不知道，標 `unverified` |
| 3 | **跟現在這版一樣嗎？** | `about[i].sha256` 對來源檔現在的雜湊 | 同上 |
| 4 | **還有效嗎？** | `ttl`，用**它宣告的鐘**（不是我的回合） | 沒 `ttl`＝沒說，不當失效 |
| 5 | **我漏了嗎？** | 同一來源上一次看到的 `(run, seq)` 和這次之間有沒有缺號 | 缺號只能記 gap，補不回來（除非來源有 log module） |

然後只有四種動作：**用／重驗後用／繞過轉述者直讀來源（寫加掛請求）／等**。這跟三態判定同一精神：不知道不等於否。「要不要繞過上級」在這裡不是組織政策，是第 2、3 題答不出來時的局部反應。【高】

### 1.3 持：一個 node 自己留什麼

照「丟了或重複會怎樣」分四類，這決定容器，不是依內容分：

| 類 | 例子 | 丟一筆 | 重複一筆 | 容器 | node 要留多久 |
|---|---|---|---|---|---|
| **觀測** | status、progress、usage、last-round、tock | 沒事 | 沒事 | 暫存器（覆寫） | 只留上一次（核心現狀對） |
| **承諾** | 我收到的 grant、我記的帳、驗收結果 | 錢憑空消失或出現 | 雙重花費 | 只加不改的 log，單一寫者（module） | 全部，自己輪替 |
| **意圖** | 我收到的請求、ctl；我寫出去的請求 | 事情沒做沒人知道 | 做兩次 | 檔即請求、回條即消費（現有） | **消費證據要活得比下一次同名意圖久**（A3-01 就是被 keep 換 run 蓋掉） |
| **衍生** | 我做的摘要、名冊、索引 | 沒事，可重算 | 沒事 | 暫存器 | 只留上一次 |

所以「核心只留上一次」對第一、四類剛好；第二類不該用核心容器（帳本 module 自己留）；第三類核心的「回條每名字留一份」只對了一半。**「事實的歷史誰保管」：觀測與衍生沒人保管（取樣，缺號可偵測不可補）；承諾由寫它的 module 保管；意圖的消費證據由消費者保管到不再可能被重播。**【高】

### 1.4 轉：一個 node 出手時的四條規則

1. **寫自己家**：事實寫 `out/`，不寫進別人的 inbox。寫別人 inbox 的只有意圖。
2. **原文不經 LLM**：要搬原文就用確定性複製（R-15 的 `save` 工具已經是先例）；LLM 只能產生**另一份**檔（衍生），帶 `about` 指回原文。原文永遠不被覆蓋。
3. **出手必帶 `src`**：`{"node", "tid", "run", "round", "seq"}`，`seq` 是本 run 內遞增。核心自己的檔已經帶 `round`、`run`，差一個 `seq`。
4. **衍生必帶 `about` 與 `hops`**：`about`＝我依據的每份檔的路徑＋雜湊＋它的 `src`；`hops`＝`{count, first, last}`。全鏈不隨檔走——每一手自己留著自己的 `about`，追責時遞迴去找（3.5）。

四條都是 node 自己做得到、也只影響自己的規則。【高】

### 1.5 node 需要的介面（全在 kernel 層，核心零改動）

〔通用〕——任何會讀寫別人檔案的任務都用得到，不只 agent：
- `factlib`（純函式庫）：`stamp()` 產 `src`、`sha256()`、`aoi(src, source_round)`、`merge_dir()`（4.4 的一寫者一檔合併）、`gap(prev, now)`。
- 慣例目錄：`out/`（事實）、`inbox/`（意圖，已有）。
- `epoch.json`（3.4）：由第一個跑在這個 node 上的任務寫。
- 本地的「上次看到誰的第幾號」暫存器（`seen.json`），給第 5 個判斷用；放槽裡接前任。

〔agent／LLM 專用〕——只有「中間有 LLM 改寫」時才需要：
- `verify(digest)`（6.3 的 quote／grep 檢查）、`digest/` 目錄慣例、annotator 任務。

### 1.6 拓撲是怎麼長出來的

把 1.2～1.4 當作每個 node 的局部規則，全局結構是結果：

| 全局現象 | 從哪些局部決定長出來 |
|---|---|
| **鏈／邊緣** | 某些 node 掛不到來源、只掛到轉述者（掛載是 kernel 層的組織決定，不是基礎設施限制） |
| **中繼（扇入）** | 一個 node 的 `digest/` 被很多人掛——它沒有宣告自己是中繼，是被掛出來的（5.2 算它什麼時候划算） |
| **一致切面** | 一群 node 選擇只掛同一份 digest、不掛來源——它們自願換到同一份快照（5.3） |
| **索引** | 某個 node 把它掛到的所有來源的最新 `(run, seq)` 整理成一份衍生事實（5.4）；它也只是一個 node |
| **「總帳」** | 不存在；每個 node 的 `out/` 加上掛載表就是全部 |
| **組織結構** | ＝掛載權限的集合，而且是**可以事後讀出來的**：`birth.json` 的 `mounts` 列出了每個任務信誰 |

一個 node 從頭到尾不需要知道「樹有幾層」「我是第幾層」——這跟上一輪分配者「對上持有、對下發行、不知道深度」是同一個形狀。【高】

## 2. 失真從哪裡來（node 看得到的樣子）

### 2.1 七種失真、三個來源

| 失真 | 來自中繼 | 來自讀取時機 | 來自 LLM | repo 已見的例子 | node 本地的偵測 |
|---|---|---|---|---|---|
| **延遲** | 每跳 ≥ 中繼者半到一個回合 | 等自己的 tock（≈ interval／2） | 秒到分鐘 | hsched 政策每層落後 2～5 回合；event tock 驅動 p50≈interval／2 | AoI（2.3） |
| **遺漏** | 摘要丟欄位 | 讀者比寫者慢、暫存器被覆寫 | 視窗擠掉 | longrun 漏 10～37%；R-2 rita 被 12 封視窗擠出世界 | `seq` 缺號 |
| **改寫** | 「整理」改了值 | — | 重打、換單位 | R-15 掉 `d` 單位，36→29 | 雜湊／quote 比對 |
| **編造** | 補洞 | — | 幻覺 | blindread q4 rep2 自己推出相反規則 | `about` 解析不到 |
| **過時** | 中繼快照舊 | 讀到時新、用到時舊 | 舊流水當現況 | blindread q4 rep1；N-69；hsched `stale_envelope` 6 次 | **用時再驗**雜湊／`rev` |
| **重複** | 重送 | 兩條路到達 | 重複動作 | A3-01／A3-05 意圖重播；gang 整批重起 | 事實有 `src`，意圖有發起者取的 id |
| **順序錯亂** | 中繼快慢不一 | 跨線回合不可比 | — | K-2；A-7 信裡的 round 對收件者沒意義 | 只比同一來源的 `(run, seq)` |

兩個觀察：

- **中繼造成五種，讀取時機造成三種，但其中「過時」是 LLM 世界最常見、最不能靠加速解決的**：它發生在讀到之後、用之前，一次思考就是幾十到上千回合（A-2：thinking 模型 119 秒）。結論不是讓 node 更快拿到，而是**讓 node 在動手那一刻能便宜地重驗**（1.2 的第 3 題）。【高】
- **aos 特有的讀取時機失真**：(a) 「任務還沒準備好 tock 先到是常態」（K-6），第一筆觀測可能是上一回合的；(b) 同槽新 run 讀前任 state.json（接前任），那是上一個 epoch 的意圖；(c) 讀一**組**檔不原子——單檔 rename 原子，目錄快照不原子，會半新半舊。(c) 的對策是清單暫存器（像 `round.json` 的 `tasks_rev`）：先讀清單再讀檔，版本對不上重讀。【高】

### 2.2 「邊緣」在同一台電腦上是什麼

距離 0，所以邊緣只能是三件事的函數：**轉手次數 h**（事實到我之間被幾個任務讀了再寫）、**回合差**（每跳要等中繼者走到 tock 才看到、再寫出：牆鐘延遲 ≈ Σ_i interval_i×(0.5～1)＋處理時間_i）、**組織距離**（誰掛得到誰）。合起來：**邊緣 node ＝ 掛不到來源、只能經 h ≥ 1 個中繼讀到事實的 node ＝ 掛載表的補集。** 要縮短距離，改掛載權限，不改傳輸。【高】

### 2.3 用「資訊年齡」當統一量尺

延遲量「寫到讀多久」；決策品質取決於**動手那一刻手上的事實多舊**。借控制理論的 Age of Information：

> **AoI ＝ 來源現在的回合 − 我所依據那份事實的 `src.round`**，單位是**來源的回合**（讀來源的 round.json，掛得到才算得出）。

用來源的鐘是因為「舊」只對產生它的線有意義（被 pause 的來源 AoI 不長——它沒有新事實，正確）。AoI 把不同拓撲放在同一張表比、自然包含「讀後才過時」、而且就是 hsched 裡 `stale_envelope` 被拒的那個數字。探針一的主指標。【高】

## 3. 事實的最小模型

### 3.1 取樣定理

暫存器對讀者的唯一保證：

> **讀者週期 < 寫者更新週期 ⇒ 不漏；否則漏掉比例 ≈ 1 − 寫者週期／讀者週期。**

longrun 對得上：tock 每 147 ms，輪詢 150 ms 漏 33%、每回合做事 150 ms 漏 37%、輪詢 10 ms 漏 0。所以第 8 節的節拍確定性不是炫技，是**核心暫存器對上層可用的條件**。機械判準：**讀者比寫者慢（LLM 讀者永遠比 tock 慢）⇒ 寫者改寫 log（module 自己輪替）、或讀者接受缺號並偵測它**（歷史 module 選後者）。【高】

### 3.2 最小欄位：哪些是核心約定、哪些是慣例

| 欄 | 內容 | 層 |
|---|---|---|
| `src` | `{"node","tid","run","round","seq"}` | **核心約定**：只寫、不查；核心自己的檔示範 |
| `seq` | 同 run 內遞增 | 核心約定（`run` 已由 tick 保證遞增，`run.seq` 就是每個寫者的全序） |
| `epoch` | 時間線身分（3.4） | kernel 慣例 |
| `about` | `[{"path","sha256","src"}]` | kernel 慣例，驗證器強制 |
| `hops` | `{count, first, last}` | kernel 慣例 |
| `ttl` | `{clock, until}` | 慣例；必須 ≥ 刷新週期＋傳播延遲（4.5） |
| `confidence`、`model`、`digest` | 衍生才有 | 慣例 |

### 3.3 「核心只留上一次」的相容

見 1.3。補一點：核心暫存器雖然只留上一次，但**缺號偵測不需要歷史**——`round` 跳號、`run.seq` 跳號都看得出來。核心給的是**gap detection，不是 gap recovery**；要 recovery 自己開 log module。【高】

### 3.4 epoch：`(node, round)` 不夠唯一

repo 踩過三次：同名重建回合從 1 重數（subtimeline）、daemon 重開 gen 變但回合接著數（gen 不是時間線身分）、nest3 裡 D1 重啟掛載點字串就換。調查報告提過 `timeline_epoch`（D-10）沒做。

最便宜的做法不進核心：**第一個拿到該 node 回合的任務在 `<node>/epoch.json` 寫一個隨機 id**；rm -rf 重建時檔案消失、新 id 自然產生；只刪 timeline.json 再寫回（回合接著數）時檔案還在——行為剛好對。路一巢狀時可以用**出生路徑**當 epoch（`L0#r12/d1#3/L1`：父 node、父回合、父任務 run、自己），順便記了「我是誰在第幾回合生的」。【中】

### 3.5 轉手鏈記多深

首、尾、跳數隨事實走；每一手自己留 `about`。**有了雜湊，鏈的主要用途（回頭驗）已經不需要鏈**；剩下的追責用途遞迴去找最後一手的 `about` 即可。鏈是分散存放的，跟「資料檔不合併、只合併導航」同一精神。【高】

## 4. 時間

### 4.1 回合是哪一種時鐘

每條線各自、由 tick 推進、**不因收到訊息而跳**的計數器——不是 Lamport（要 max＋1），不是向量。但 aos 有別的系統沒有的條件：**程序來來去去（run），時間線長存**。Lamport／向量都是「程序帶鐘」；aos 應該**事實帶鐘、時間線只給節拍**：

- 時間線給 `(epoch, round)`，寫者給 `(run, seq)`，合起來是這份事實在它自己線上的全序座標。
- 要表達「我依據了誰」，不在程序裡維護全 node 向量，而是在事實的 `about` 列出**它實際讀過的那幾份事實的 `src`**——per-object version vector（Bayou／Dynamo 那一路），長度＝來源數不是 node 數。在 aos 裡依據關係幾乎都是樹或 DAG（掛載表決定），所以它很小，而且**同一個欄位同時解決因果與出處**。【高】

待定點 4「跨子 daemon 的回合怎麼比」：**不比**。跨線只問 (a) 我依據的那份來源現在還是最新版嗎（雜湊或來源的 `(run, seq)`）、(b) 這兩份誰依據誰（`about` 包含關係）。都不需要節拍比。hsched 已示範：讀發行者的 round.json、用對方的鐘、不換算。

### 4.2 pause 讓「回合差」不等於「舊」

被 pause 的線回合停、事實不變舊（沒新事實）；但它的**意圖**（goal、grant）可能該失效了（牆鐘窗口過了）。**觀測的新舊用來源的回合；意圖的有效期用它自己宣告的鐘。** 混在一起就是 K-2 的坑。【高】

### 4.3 雜湊是「不用鐘的過時偵測」

回合只能線內比；向量要維護；牆鐘不可靠。雜湊什麼都不用：讀 `about[i].sha256` → 對來源現在的雜湊 → 同＝講的是現在這版，異＝過時或改寫。代價一次 sha256（100 KB 不到 1 ms）＋要掛得到來源（掛不到就只能信中繼——正是邊緣的定義）。這把待定點 1、2、3 串起來：出處帶雜湊、鏈不必記、摘要標記＝`about`。LLM 友善：它只要會叫一個工具或讀驗證器的回條。【高】

### 4.4 HLC、CRDT、事件溯源各放哪

- **HLC**：不需要。aos 已把 `at` 給人看、邏輯另走，分開比混合乾淨。【高】
- **事件溯源**：就是帳本 module（承諾類）。不推廣到觀測類（會回到「什麼都留」的垃圾問題）。【高】
- **CRDT**：aos 最自然的 CRDT 不是演算法，是**「一個寫者一個檔，讀時合併」**。名冊、成員狀態、計數這類多人寫的事實，與其共用檔＋flock（selfmod 量到 lost update；A3-06 owner 編碼碰撞），不如每個寫者寫 `<目錄>/<寫者>.json`，讀者 `ls` 後合併：集合＝聯集、單值＝取 `(round, seq)` 最大、計數＝各自相加（proto7-2 §8「每個 run 的最大值相加」**已經是** G-Counter）。**檔名就是出處**，不用鎖，不互相覆蓋。flock 留給必須單一真相的控制檔（tasks.json、paused.json）。從 node 視角看這條最重要：node 只管寫自己那個檔，不用跟任何人協調。【高】

### 4.5 TTL 規則

hsched 的教訓：模型給的政策 `until_round` 常比下一次詢問還早（第 1 回合給到 21、第 40 給到 60），中間退回預設、每次執行 2～4 次「到期」保底。不是 LLM 笨，是事實的有效期沒涵蓋自己的刷新週期：

> `ttl ≥ refresh_period ＋ hops × hop_latency ＋ reader_think_time`

寫 goal、grant、政策的 node 照這條算；驗證器可以直接拒 `ttl < refresh_period` 的意圖。【高】

## 5. 從單元規則長出來的拓撲：三件要驗的事

### 5.1 四種流法在單機上的真面目

| 流法 | 單機上是什麼 | 出處 | 複製 | 誰決定新舊 |
|---|---|---|---|---|
| 只吃上級 | 上級把事實寫進我的 inbox | 上級自報 | 每層一份 | 上級 |
| 直讀來源 | 我掛來源的 `out/` | 路徑 | 0 | 我 |
| 發布／訂閱 | 寫者寫自己 `out/`、訂閱者掛它＝**跟直讀是同一件事** | 路徑 | 0 | 訂閱者 |
| gossip | 互抄 | 亂 | N 份 | 沒人；只有跨機器會分區才有意義，備援不考慮 ⇒ 不做 |

單機只剩兩種真選項：直讀（事實）與推送（意圖）。**事實拉、意圖推。**【高】

### 5.2 中繼什麼時候划算（給被很多人掛的 node 自己算）

三種價值：扇入壓縮（N 讀者×M 來源 → M＋N 次讀）、換單位（bytes → tokens，LLM 讀者的主要成本）、存取控制（只有它掛得到來源）。三種成本：＋1 跳延遲、每跳失真 ε、單點過時。粗模型：

> 划算 ⇔ `N × (M × T_raw − T_dig) × 單價 > 中繼呼叫成本 ＋ ε × 錯一次的損失 ＋ 延遲損失`

推論：(1) **中繼是 token 經濟不是延遲手段**——它永遠讓延遲變長；(2) N 小不划算，N 大時「摘要＋指標」優於「摘要取代原文」：讀者先讀摘要，關鍵決策前照 `about` 重驗。blindread 證明兩層閱讀可行：deepseek 用 card 版讀 31 次、hardcoded 讀 53 次，分數一樣。【中，模型粗】

### 5.3 「只吃上級」唯一站得住的理由：一致切面

一層傳一層有個被忽略的好處：**所有下游依據同一份快照**。邊緣各自直讀，兩個邊緣會在不同時刻讀到不同版本——沒有 consistent cut。ARINC 653 的 major frame、TTA 的全域時間表都是用「同一個邊界換資料」買一致切面。拿掉只吃上級要補的不是速度，是**可追溯的不一致**：每個決策寫 `acted_on: [src…]`（＝Linux 報告的 `snapshot_id`／`observations`），事後能答「你們兩個為什麼做出相反決定」。要同一份的 node 群仍可選只掛同一份 digest——這是 kernel 層掛載表的事，核心不管。【高】

### 5.4 「事實的總帳」：不要，命名空間就是總帳

集中所有事實＝做一個中繼掉所有東西的中心，正是使用者不要的。「事實在哪」的總帳**已經存在**：掛載表＋服務卡＝命名空間。要的是索引不是副本：一份暫存器列「哪些目錄、各自最新 `(run, seq)`」，過時了也沒關係（只是提示）。它也只是某個 node 的衍生事實。【高】

## 6. LLM 在傳遞鏈上

### 6.1 repo 已見的三種 LLM 失真，三種都靠確定性部件解

- **過時當現況**（blindread q4 rep1、N-69）：對策結構化——狀態檔標「我是現任」＋`src.run`。
- **憑記憶重打**（R-15）：對策已做——`save` 不經 LLM 原樣複製。這是「LLM 只能加註、不能改寫」的第一個結構性實例，應升格成原則（1.4 第 2 條）。
- **視窗遺漏**（R-2、R-13）：對策已做——名冊固定進 prompt＋每對象至少留一封。

**沒有一種靠 prompt。**【高】

### 6.2 多跳累積

每跳每個事實單元被改寫／遺漏／編造的機率合計 p，d 跳後完整率 (1−p)^d：p＝10% 時 3 跳 73%、5 跳 59%；p＝3% 時 5 跳 86%。repo 沒有真模型摘要失真的數字（blindread 量讀不量寫），探針要**分開量三種 p**，因為對策不同。【中】

### 6.3 「只能加註、不能改寫」做成結構

1. **搬運不經 LLM**：中繼 node 的任務＝確定性 copier ＋ LLM annotator；原文由 copier 放 `relay/raw/`（或只給指標），LLM 只能寫 `digest/`；LLM 的掛載寫權只有 digest 目錄（合作式，`writes.jsonl` 看得到越界）。
2. **摘要必須可 grep**：digest 每條陳述帶 `quote`（原文片段）與 `about`；驗證器做純字串的事——`quote` 是不是原文子字串、雜湊對不對、數字與專名是否原文出現。抓得到改寫、編造、過時；抓不到遺漏（另比欄位清單）與「引對了推錯了」（blindread q4 rep2，屬下游推論）。【中——真模型會不會因太嚴而大量不合格，要量】
3. **回頭路要便宜**：`about.path` 是空間路徑；掛得到直接讀，掛不到寫加掛請求（S-23）。繞過上級的觸發條件＝1.2 的第 2、3 題答不出來或 AoI 超閾值。

副產品：有了可 grep 的 digest，**摘要失真可以離線量**。

## 7. 延遲的另一半：多快看到

### 7.1 三種機制、三個數量級

| 機制 | 延遲 | CPU | 權限 | 數據 |
|---|---|---|---|---|
| 任務內輪詢（keep 任務每 10 ms 看） | 3～6 ms | 一個常駐程序；100 個 inbox 每 20 ms 掃約 0.02 CPU 秒／秒 | 讀得到來源目錄 | event `watch` 3／6 ms；tickless 的 kernel |
| tock 驅動 | ≈ interval／2，最慢一個 interval | 每回合兩個 Python（50～100 ms CPU） | 無 | event `tock200` 131／195 ms |
| pause＋wake | ≈ tick＋tock ≈ 70～100 ms | 幾乎 0（省 90%） | **寫者要掛得到讀者的 `.aosd`** | tickless C：70／90～100 ms |

**要低延遲用輪詢，要省 CPU 用 wake，tock 驅動兩頭都不佔。** wake 的真正用途是閒線睡、有事醒（NO_HZ），不是讓事實傳得快。node 自己先問「我是忙線還是閒線」。【高】

### 7.2 wake 提前結束回合的兩個副作用

（資源筆記寫 P2-01 已定 (b)，proto7-2 spec 仍寫待定；第一輪綜合已指出不一致。下面的 C5 兩種情況都適用。）

1. **回合長度變成變數**：常被 wake 的 node 回合數膨脹，它線上以回合計的東西（`wake.rounds`、冷卻、回合制 grant 窗口）在牆鐘上提早到期。**有 `.aosd` 寫權的人可以把別人的時鐘調快**——不是安全問題，是正確性問題。
2. **wake 風暴＝fleet 過載**：每個 wake 一對 tick／tock；100 個 node 各每 50 ms 被 wake ＝ 每秒 4000 個程序，比撐爆 16 核的 544 個多 7 倍。

一個選項解兩個：**timeline.json 加 `min_interval_ms`（預設＝interval，即現狀）**：wake 可提前結束回合，但下一個 tick 不早於上一次 tick＋min。每條線宣告**週期帶 [min, max]**：固定節拍 min＝max；事件驅動 min 小 max 大；同回合多個 wake 自然合併。這是 RTOS 的最小週期、wake 的速率上限、讓「回合≈時間」在已知範圍成立，三合一，幾行。【中偏高】

### 7.3 對 tick-tock 的影響

語意不變（tick 開、tock 關），回合長度從常數變區間，而且**區間是 node 自己宣告、別人讀得到的事實**。讀別人事實的 node 因此算得出「對方 N 回合最短多久、最長多久」——跨線寫 TTL（4.5）需要的就是這個。

## 8. RTOS 時間確定性：在 aos 上能談到哪裡

### 8.1 做不到的

任務 WCET（Python、LLM）；搶占（pause 不停正在跑的，唯一搶占點是 tock 的 kill，粒度一回合）；硬截止（daemon 是 Python＋thread，過載時主迴圈 20→115 ms）。所以 aos 的確定性只能是**「節拍邊界抖動有界，而且界是量出來、公布出來的」**。這夠了，因為上層要的是 3.1 的取樣定理成立。

### 8.2 核心現在量不到自己的節拍（真缺口）

筆記寫「tick／tock 的耗時要量得到（status 已有）」——核對 proto7-2：`status.json` 只有**設定的** `interval_ms`；`round.json`／`last-round.json` 只有 ISO 牆鐘 `tick_at`／`tock_at`（spec §0 明說只給人看）；daemon 內部用 `time.monotonic()` 算等待但**沒寫出任何 ms**。proto7-1 的 status 有「最近一回合實際用的 interval_ms」，重寫時掉了。

建議 last-round.json 加四個 monotonic 算的整數（status 每 node 放最近一組）：

```json
"timing": {"late_ms": 12, "tick_ms": 38, "run_ms": 1004, "tock_ms": 41}
```

`late_ms`＝這回合 tick 實際開始 −（上回合 tick＋interval），負數＝提前（wake）。沒有這四個數，抖動量測、截止排程、利用率准入全做不了。【高——缺口是核對程式確認的】

### 8.3 利用率准入：用 fleet 的數字反推

每線每回合固定成本 c（tick＋tock CPU）、週期 interval_i：

> `U = Σ_i c / interval_i ≤ 核數 × 0.7`

c 的實測：fleet（proto7-1）約 22 ms×2＝45 ms；astra-2 長跑（proto7-2，三態判定更重）每回合約 98 ms 累計 CPU。驗算 fleet 過載：150 條×約 4 回合／秒×0.045 s ≈ 27 核 > 16 ⇒ 實測間隔中位 1.8×、p90 4×、最大 5.5×——**界算中了**。反推容量：16 核、c＝0.1 s、interval 1 s ⇒ 約 110 條線內抖動可控；100 ms ⇒ 11 條。

這給 kernel 一個**確定性的 register 准入**：登記前讀 timing 估 c、加總 U、超界拒絕或要求拉長 interval。daemon 不懂這個，kernel 算完再寫 register 控制檔。【中——c 隨槽數會長】

### 8.4 kernel 選項／module 能提供的

| 保證 | 做法 | 需要核心 | 誰受惠 |
|---|---|---|---|
| 節拍抖動量測 | module 讀 `timing` 算 p50／p99，寫 `clock-quality.json`——也是一份事實，別的 node 讀它決定「這條線的回合能不能當時間用」 | 8.2 | 〔通用任務〕：cron、備份、任何週期性工作 |
| 最短週期 | `min_interval_ms` | 7.2 | 〔通用〕 |
| 利用率准入 | kernel 在 register 前算 U | 8.2 | 〔通用任務〕 |
| 截止時間排程 | 請求帶 `deadline: {clock, round}`，類別內 EDF，只排准入順序 | 無 | 〔通用任務〕 |
| 執行時間預算（watchdog） | 任務項帶 `budget_rounds`／`budget_ms`，kernel 在 tock 時刻比對、超過寫 ctl kill | 無 | 〔通用任務〕 |
| 優先級繼承 | hsched 的捐贈 | 無 | 〔通用任務〕；LLM 只是它的一個客戶 |
| 控制面保留 | kernel 跑在自己的 node、短 interval、不跟工作線搶槽 | 無 | 〔通用〕慣例 |
| tickless | pause 閒線、有事 wake（探針已做） | N-83 可選 | 〔通用任務〕 |

這一節沒有任何一項是 agent／LLM 專用的——RTOS 那套本來就是為非 LLM 的週期性工作發明的。daemon 裡不放「截止時間」概念——同上一輪「daemon 不懂 token」。

### 8.5 核心「不擋路」清單

1. tick／tock 不等任務、有逾時（已是）。2. 控制檔處理有預算（已是）。3. status 寫出成本別隨 node 數長到擋主迴圈（tickless 全停仍 0.12 CPU 秒／秒，全花在每 20 ms 重寫 101 node 的 status；可選 `status_every_ms` 或每 node 一檔；〔通用〕）。4. **寫出 timing**——唯一真缺的（〔通用〕）。5. 不做 cgroup、SCHED_FIFO、daemon 內量 CPU（OS-gated）。

## 9. 資源與使用權，從單一 node 看

上一輪是總覽（樹、遞迴、分配者）。從一個 node 看，整套東西縮成**三個口裡各放一類檔**：

| 口 | 資源相關的內容 | 事實類別 | node 自己要做的判斷 |
|---|---|---|---|
| **收** | 我持有的 grant（別人寫給我的） | 承諾 | 每次動手前：這份 grant 的鐘（它宣告的）還在窗口內嗎？維度（五種型別）夠不夠？`rev` 有沒有變？ |
| **持** | 我的用量 log、我的 `seen`、我在途的 reserve | 承諾／觀測 | 在途未知不歸還（三態）；用量以 run 為單位、只增 |
| **轉** | `out/usage.json`（觀測，給發行者取樣）、`inbox` 寫出去的請求（意圖）、若我也發行：`grants/<id>.json`（承諾） | 觀測／意圖／承諾 | 請求帶 `charge`、`deadline`、發起者取的 id；發出去的 grant 子 ⊆ 父（只對照我自己持有的那份） |

從 node 看，「資源」的定義變得很局部：**資源＝我動手前必須出示一份 grant 的那種東西；gateway＝收口裡會檢查我 grant 的另一個 node。** 一個 node 不需要知道樹、不需要知道根在哪：它只認識**發給它 grant 的那一個 node（父）**和**向它要 grant 的那幾個 node（子）**，而且父的鐘它經掛載讀得到。「子不超出父」的檢查它只對自己手上那一份做。遞迴在局部是看不見的——這正是拓撲能自然長出來的原因。【高】

兩個從 node 視角才看得清楚的點：

- **grant 是別人寫給我的承諾，但它在我這裡是收口的檔，我不該改它**；我要變更只能發請求（意圖）。所以 `grants/` 應該是發行者的 `out/` 被我掛進來，不是複製到我家——複製就是上一輪說的雙重花費的起點。從 node 看，**使用權根本不該被搬運，只該被掛載。**【高】
- **五種維度型別從 node 看是「我動手前要檢查的五種算術」**（扣額、剖面、子集、窗口、優先級不跨父），不是資源的分類學。使用者覺得它「片面」可能是因為它只描述「怎麼檢查」，沒描述「我為什麼需要它、拿不到怎麼辦、能不能自己造」——這些是 node 的目標與退路，是肉，應該留在 goal 與 `fallback`。這一點我沒把握，留給使用者後續再想。【低】

團隊從 node 看：**一群 node 掛同一個發行者、讀同一份 goal**——它是掛載表上的一個圖樣，不是 daemon／tick 認識的東西。要工具（複製一群 node、批次登記）就是 module，不碰核心，合使用者 10-04 的回應。上一輪我主張進核心的 C1（相對團隊根）照綜合改走 module；C3（整棵登記）不做。

## 10. 對 daemon／tick 的具體要求

照 principles.md 第 5 條，每條先問「只方便 agent／LLM，還是同樣惠及其他需求」。檢驗方法：把 LLM 全部換成 shell 腳本（cron、備份、CI、感測器匯入），這條要求還成不成立。

### 10.1 必須進核心（小）

| # | 要什麼 | 大小 | 為什麼非核心不可 | 誰受惠 |
|---|---|---|---|---|
| **C4** | last-round.json／status 加 `timing: {late_ms, tick_ms, run_ms, tock_ms}`（monotonic） | 十幾行 | 只有 daemon 知道 monotonic 時刻；任務層算不出遲到量 | **〔通用〕**：任何週期性工作都要知道節拍準不準；跟 LLM 無關 |
| **C5** | timeline.json 的 `min_interval_ms`（預設＝interval） | 幾行 | wake 是 daemon 做的，下限只能在 daemon 擋 | **〔通用〕**：防 wake 風暴吃 CPU、保住「回合≈時間」，對 cron 類任務一樣要緊 |
| **C6** | spec §0 加一句約定：給別人讀的 JSON 帶 `src`（node、tid、run、round、seq）；核心自己的檔補齊（tock.json、exit.json 補 `node`／`tid`） | 文件＋幾個欄位 | 約定不是功能；核心檔先示範 | **〔通用〕**：出處與序號是 log 管線、稽核、重算器都要的；S-01 的「LLM 讀得懂」只是它的一個客戶。**注意**：`quote`／`about`／`digest` 這些**不在** C6 裡，它們只對有 LLM 改寫的鏈有用，留 module |
| （上一輪）**C2** | tasks.json 的 `until_round` | 幾行 | 已拍板 | 〔通用〕：任何有期限的任務 |

C1 改 module、C3 不做（使用者 10-04）。合計不到一百行，而且**沒有一條是 agent／LLM 專用的**。我曾考慮過、但因為只方便 LLM 而**不建議進核心**的：核心檔附「人話摘要」欄、status 加「最近一回合總結」小檔（N-76）——這些做成 module 讀 last-round 再產出即可。

### 10.2 留在 kernel／module：分兩類

**〔通用任務〕**（LLM 換成腳本仍成立）：
- `factlib` 的通用部分（`stamp`、`sha256`、`aoi`、`gap`、`merge_dir`）；`out/` 慣例、epoch 檔、`seen.json`。
- 索引暫存器（5.4）、clock-quality module（8.4）、利用率准入、deadline／EDF、watchdog、優先級捐贈、tickless kernel。
- 帳本、gateway 骨架、grant 函式庫（上一輪）；歷史 module（已有）。
- **確定性 copier**（原樣搬運、附 `src`／`about`）：它是通用的——備份、鏡像都是它。
- node 群複製與批次登記工具（團隊相關，照使用者定走 module）。
- 慣例文件：四類事實與容器、TTL 規則、事實拉意圖推、一寫者一檔。

**〔agent／LLM 專用任務〕**（沒有 LLM 就沒有這個問題）：
- annotator（LLM 摘要者）與 `digest/` 慣例；`verify(digest)` 的 quote／grep 驗證器——它存在的唯一理由是「中間有會改寫的東西」。
- relay＝copier＋annotator 的組合（copier 本身通用）。
- LLM 端點分配者、`save` 工具、名冊固定進 prompt、記憶視窗補一封（R-2／R-13／R-15 那些）。
- 「兩層閱讀」策略（先摘要後原文）——對腳本沒意義，腳本直接讀原文。

### 10.3 刻意不做

不做全域事件匯流排或 inotify 進 daemon（單機上輪詢便宜，事件只能當提示、醒來還是重讀）；不做核心層向量時鐘或全域序號；不在核心擋沒 `src` 的檔；不讓 daemon 認識「團隊」；不為 LLM 在核心檔裡加任何欄位。

## 11. 具體化

### 11.1 事實檔（觀測，暫存器，放 `out/`）

```json
{
  "schema": "aos.fact.v1",
  "kind": "observation",
  "src": {"node": "agents/amy", "tid": "agent", "run": 57, "round": 212, "seq": 3, "epoch": "e-9f3a"},
  "at": "2026-10-04T15:02:11+08:00",
  "ttl": {"clock": {"kind": "round", "node": "agents/amy"}, "until": 230},
  "body": {"reviewing": "review-17", "tokens_used": 3612, "state": "think"}
}
```

### 11.2 摘要檔（衍生，可 grep，放 `digest/`）

```json
{
  "schema": "aos.digest.v1",
  "kind": "digest",
  "src": {"node": "relay-b", "tid": "relay", "run": 9, "round": 41, "seq": 1},
  "model": "fake-llm-v1",
  "hops": {"count": 1, "first": "agents/amy:agent#57@212.3", "last": "relay-b:relay#9@41.1"},
  "about": [
    {"path": "agents/amy/out/status.json", "sha256": "7f3a…", "src": {"node": "agents/amy", "run": 57, "round": 212, "seq": 3}},
    {"path": "agents/bob/out/status.json", "sha256": "c21e…", "src": {"node": "agents/bob", "run": 12, "round": 88, "seq": 7}}
  ],
  "claims": [
    {"text": "amy 在審 review-17，已用 3612 tokens", "quote": "\"tokens_used\": 3612", "about": 0},
    {"text": "bob 閒置", "quote": "\"state\": \"idle\"", "about": 1}
  ],
  "omitted": ["amy.body.ttl"],
  "confidence": {"by": "relay", "level": "verbatim"}
}
```

驗證器：每條 `quote` 是 `about[i]` 現在內容的子字串（改寫＝不過）；`sha256` 等於現在的雜湊（不等＝標 `stale`，下游要知道）；路徑解析不到＝編造；claims 裡的數字必須在 quote 裡出現。

### 11.3 決策依據紀錄（5.3 的一致切面替代）

```json
{"decision": "assign review-18 to bob",
 "acted_on": [
   {"path": "relay-b/digest/latest.json", "src": {"node": "relay-b", "run": 9, "round": 41, "seq": 1}, "verified": "hash-ok"},
   {"path": "agents/bob/out/status.json", "src": {"run": 12, "round": 88, "seq": 7}, "verified": "direct"}],
 "aoi": {"agents/bob": 2}}
```

### 11.4 探針一：`relay`——同一組 node 規則、三種掛法

**擺法**：4 個來源 node（各自每回合寫一份觀測，狀態照腳本變，含 1/10 機率的「關鍵變化」）、1 個中繼 node（keep：copier＋假 LLM annotator）、4 個讀者 node（每 3 回合做一次決策，正確與否取決於依據的事實是否是當時真值）。interval 500 ms，中繼 1000 ms（故意慢）。**每個 node 跑同一套 1.2 的規則，只改掛載表**，各跑 200 回合：

- (A) 讀者只掛中繼的 digest（只吃上級）；
- (B) 掛 digest 也掛來源；決策前驗雜湊，不符或 AoI > 3 直讀（摘要＋指標）；
- (C) 只掛來源（直讀）。

假 LLM 失真旋鈕：`p_rewrite`、`p_drop`、`p_invent`、`p_stale`，預設各 5%。

**假設**：(H1) AoI：C < B < A，且 A ≥ 中繼 interval／來源 interval＋1；(H2) 決策錯誤率：A 隨跳數與 p 累積，B 接近 C，C 最低；(H3) 讀取量 A < B < C（B 只在驗不過時多讀）；(H4) 驗證器抓到 ≥ 95% 的 rewrite／invent／stale，抓不到 drop；(H5) 中繼 interval 調 250 ms 時 A 的 AoI 降、CPU 升，B 幾乎不變（中繼是 token 經濟不是延遲手段）。

**成功標準**：H1、H2 方向對且 5 seed 一致；B 讀取 bytes ≤ C 的 50%、錯誤率 ≤ C＋2 個百分點；H4 三類抓到率各 ≥ 95%、誤報 0；檔案數不隨回合長。

### 11.5 探針二：`clockq`——節拍品質、准入界、wake 下限

**擺法**：先做 C4、C5（或先用 `log.on` 事件時間近似）。16 核，逐步加 node（interval 1 s、200 ms、100 ms 三組），量 `late_ms` p50／p99 對 U 的曲線。再開一個吵鬧者每 20 ms 對某 node 寫 wake：比 `min_interval_ms` 預設 vs 200 ms 的回合數膨脹與 CPU。最後在被吵的 node 放一份回合制窗口（`until_round`＝現在＋20）的事實，量它牆鐘上多久到期。

**假設**：(H1) U < 0.7 時 p99 late_ms < 20% interval；U 過 1 後線性惡化（重現 1.8×／4×）；(H2) 用 U 做准入後所有線 p99 守住；(H3) 沒下限時 20 回合窗口 0.4 秒內到期（調快 50 倍）；有 200 ms 下限 ≥ 4 秒；(H4) 槽數 0、2、8 下 c 差 ≤ 2 倍，否則准入帶槽數修正。

**成功標準**：H1～H3 成立；H4 允許失敗（失敗就改成每 node 量到的 c）。順便量 proto7-2 的 c 當容量基準。

### 11.6 探針三：`perwriter`——一寫者一檔 vs 共用檔

**擺法**：10 個寫者 node（interval 100～300 ms）維護「成員狀態」：(A) 共用 `roster.json`＋flock 讀改寫；(B) 各寫 `roster/<node>.json`，讀者合併。一個照稿腦讀者每回合答「誰在線、誰最新」。中途 kill -9 兩個寫者、同名重建一個（epoch 變）。

**假設**：(H1) A 有 lost update，B 為 0；(H2) B 讀者從檔名就得到出處；(H3) 同名重建後 B 靠 epoch 分得出前後兩段，A 分不出；(H4) 讀 10 個小檔的成本 ≤ 讀 1 個大檔的 1.5 倍（S-01 的代價）。

**成功標準**：H1～H3 成立；H4 超過就加索引暫存器再量。

## 12. 最值得使用者拍板的五題

**Q1 出處放哪一層？**
(a) 核心約定且檢查；(b) **核心只寫約定、自己的檔示範、不檢查（C6），驗證器在 kernel**；(c) 純慣例，核心 spec 不提。
**推薦 (b)**：一句話加幾個欄位；(a) 違反極簡且擋不住合作式偽造；(c) 會讓各 node 群各發明一套 `src`。

**Q2 轉手鏈與跨線因果怎麼記？**
(a) 全鏈隨事實走；(b) **首尾跳數隨事實，每一手自己留 `about`（路徑＋雜湊＋來源 src），跨線不比回合、只比雜湊與 `about` 包含**；(c) 向量時鐘。
**推薦 (b)**：雜湊讓鏈的主要用途消失；(c) 在 node 來來去去的世界維護不了。

**Q3 LLM 摘要怎麼標？**
(a) 只標 `digest: true`；(b) 標＋`about`；(c) **(b)＋每條陳述帶 `quote`、驗證器 grep；搬運一律不經 LLM**。
**推薦 (c)，嚴格度由探針一決定**：真模型合格率太低就退到 (b)＋「數字與專名必須原文出現」。

**Q4 核心要不要量自己的節拍、要不要有最短週期？**
(a) 不量不設；(b) **量（C4）＋最短週期（C5）**，其餘全在 kernel；(c) EDF／watchdog 也進 daemon。
**推薦 (b)**：沒有四個數，RTOS 這題只能空談；(c) 違反 daemon 不懂政策。

**Q5 一個 node 預設能不能繞過轉述者直讀來源？**
(a) 預設只掛父；(b) **預設可掛來源，轉述者的 digest 是提示；要一致切面的 node 群自己收緊 `mount_allow`，而且每個決策寫 `acted_on`**；(c) 核心強制某一種。
**推薦 (b)**：事實拉、意圖推的落地；(a) 把失真當預設；(c) 不是核心的事。

（不用拍板、建議直接做：多人寫的事實改一寫者一檔；TTL 規則進驗證器；`save` 升格成「原文不經 LLM」原則。）

## 14. 我最不確定的三件事

1. **可 grep 的摘要對真模型會不會太嚴。** 合法摘要本來就會改寫（「3612 tokens」→「約 3.6k」、英→中）。`quote` 子字串檢查會把這些當不合格；放寬成「數字與專名原文出現」又抓不到語意改寫。repo 裡沒有任何真模型摘要的數據，p_rewrite／p_drop／p_invent 全是猜的；探針一只跑假 LLM 的話這題還是沒答。【低】
2. **利用率准入的常數 c 穩不穩。** fleet 的 22 ms 與 astra-2 的約 50 ms 已差一倍（proto7-1 vs 7-2、空任務 vs 含任務），tick 掃槽、tock 三態判定都隨槽數長。若 c＝c0＋k×槽數，准入要改、kernel 要持續量。16 核的數字搬到別台機器成不成立沒證據。【中偏低】
3. **「一寫者一檔」對 LLM 讀者的代價，以及五種維度從 node 看到底缺什麼。** 前者：讀者要 `ls`＋讀 N 個檔，blindread 顯示讀取次數是呼叫上限的主要消耗（haiku 14 次用完沒交答案）；N 到幾十時 S-01 可能因呼叫數爆掉而不成立，要索引——索引又是會過時的衍生事實。後者：我在 9 節猜使用者覺得「片面」是因為型別只講「怎麼檢查」、不講「為什麼需要、拿不到怎麼辦」，但這是猜的。【中／低】
