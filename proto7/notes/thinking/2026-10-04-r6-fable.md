## 3. 第一小塊：`step` 第一版＋結果檔，跑一個備份工作

**挑它的理由**（原則 3、5、7、9）：單一 node、不用 LLM、不用 kernel、不用控制包；是骨架第 4 句的本體，又順帶驗第 1、2、5、6 句；r5 的三條價值裡「死後可讀」「跑前可查」不等資源包就成立（r5 不確定 #4 擔心的是第一條，第一版不押它）。備份工作（dump → verify → rotate → notify）正好有一步**非冪等**（rotate），能驗「保守檢查」不是裝飾。

### 3.1 要哪些檔

| 位置 | 檔 | 內容 |
|---|---|---|
| `proto7-2/modules/step/` | `aos7-step`（可執行 Python，≤300 行） | keep 任務本體：每收到 tock 讀自己槽 `state.json`，照步驟表前進最多一步 |
| | `README.md`、`tests/test_step.py` | 包的 spec 與測試（格式同 subd 包） |
| `<node>/` | `backup.steps.json` | 步驟表（下面） |
| | `.aos/tasks.json` 一項 | `{"name": "backup", "mode": "keep", "argv": ["python3", "<modules>/step/aos7-step", "backup.steps.json"]}` |
| | `out/backup/<step>.json` | 結果檔（子任務寫，原子覆寫）：`{"run": $AOS7_RUN, "step": "dump", "ok": true, "data": {...}, "at"}` |
| 槽 `.aos/tasks/backup/` | `state.json`（框架） | `{"pc": "verify", "tries": {"verify": 1}, "waiting": {"slot": "backup.verify", "run": 57}, "vars": {"archive": "..."}}` |
| 槽 `.aos/tasks/backup.<step>/` | 核心自己管 | 每個 `run` 步一個 once 槽（`slot` 釘 `backup.<step>`，`x.step: {"job": "backup", "step": "dump"}`） |

**步驟表第一版只有四種步**（lang-fable 的五種拿掉 `ctl`、`guard`，留到第三塊）：

```json
{"start": "dump",
 "steps": {
   "dump":   {"run": ["sh", "dump.sh", "${result}"], "idempotent": true,  "ok": "verify", "fail": "retry_dump"},
   "retry_dump": {"count": 3, "then": "dump", "exhausted": "park"},
   "verify": {"run": ["sh", "verify.sh", "${vars.archive}", "${result}"], "idempotent": true, "ok": "rotate", "fail": "park"},
   "rotate": {"run": ["sh", "rotate.sh", "${vars.archive}", "${result}"], "idempotent": false, "ok": "notify", "fail": "park", "unknown": "park"},
   "notify": {"wait": {"exists": "out/backup/ack.json"}, "patience_rounds": 10, "on_timeout": "park", "then": "end"},
   "park":   {"end": "parked"},
   "end":    {"end": "ok"}}}
```

- `run`：拿表鎖 `edit_json` 加一項 `once`（`slot` 釘名、`x.step`、`${result}` 展開成結果檔路徑），把 `{slot, run}` 記進 `waiting`；之後每回合先讀**結果檔**（`run` 要等於記的 run），有就照 `ok` 走；沒有再看槽的 `exit.json`：`never_started` → 重寫同一步（確定沒起，無副作用）；`code≠0`／`lost` → `fail`；槽已被 tock 刪、結果檔也沒有 → `unknown`（預設＝`fail`，非冪等步要明寫 `unknown` 分支）。
- `wait`：每回合看一次檔（只准 `exists`／`glob`／`result.ok`／單一數字比較）；`patience_rounds` 以**自己的回合**計（pause 時凍住，照 r5 §3.4 承認）。
- `count`：計數存框架 `tries`。`end`：寫 `state.pc=end`、結果 `status`，直譯器退出 0；keep 下一回合起新 run 讀到 `pc=end` 就直接退出（或 `restart_on_end: true` 從頭來——選項）。
- `aos7-step check <表>`：不執行就擋三件事——`goto` 目標都存在；`retry`／`count` 迴圈裡的 `run` 步都 `idempotent: true`；每個 `run` 步都是 once（天然 finite，等結束合法）。

**用到的核心零件（全部現成）**：`once`＋`slot`＋`launch`、`exit.json`＋`never_started`、`x` 透傳、`edit_json` 三態（壞表拒寫 → 直譯器這回合不前進、記 `state.err`）、`wait_tock`（run 過濾）、槽內 `state.json` 換 run 不清、`cwd＝node`。**不用**：restart、retry_lost、`timing`、`wake`、掛載。

### 3.2 怎麼驗（測試形狀，`modules/step/tests/`，離線）

1. **走通**：四步全綠，`out/backup/` 四份結果檔 `run` 各對上，`state.pc=end`，總結 `ended` 每步一筆 code 0。
2. **重試邊界**：`dump` 注入失敗兩次再成功 → `tries.dump=2`、槽 `backup.dump` 只起 3 次；`rotate` 失敗 → **不重試**直接 `park`；`check` 對「把 rotate 放進 count 迴圈」的表回非 0。
3. **直譯器死後可讀、能接續**：在 `waiting` 寫完後 `kill -9` 直譯器 → keep 下一回合新 run 讀同槽 `state.json` 接 `pc` 與 `waiting.run`，**不重複起 once**（表上沒有第二個同槽項）；`cat state.json` 看得出卡在哪。
4. **結果檔 vs exit.json**（r5 不確定 #2 的探針）：(a) 子任務寫結果前被殺且從沒起來 → `never_started` → 直譯器重寫同一步；(b) 子任務起了、寫結果前被殺 → `unknown` 分支（`dump` 冪等重起、`rotate` park）；(c) interval 10 ms、直譯器故意睡兩回合、槽已被 tock 刪 → 直譯器照結果檔走，不依賴 exit.json。
5. **檔案數不長**：200 回合、重跑 20 次 job，`.aos/tasks/` 槽數＝步數＋1、`out/backup/` 檔數固定（覆寫）。
6. **骨架第 1 句**：pause node 5 秒再 resume，`patience_rounds` 沒被扣（耐性以自己回合計），`notify` 照常等到。

探針（不進 unittest）：真的把一個資料夾 tar＋sha256、輪替三份，看 `out/backup/` 與 `state.json` 一眼能不能講出「上次備份成功在第幾回合、現在卡哪」。

### 3.3 它做完後的順序（3～5 步）

1. **（本塊）`step` v1＋結果檔慣例**，備份工作當探針。
2. **慣例寫進文件**：結果檔路徑與欄位、`out/`／`inbox/` 三目錄、`src`／`basis` 最小欄、`x` 欄每包一個 key——補到組件契約 §2.8「任務」卡與 proto7-2 README；零程式。
3. **`step` v2 接控制包**：加 `ctl` 步（經掛載寫 daemon ctl：pause 自己當 `stop`、`wake` 當選項）與 `patience` 到期 kill 子任務（帶 `waiting.run`）；等控制包 commit 後做。
4. **`account` 第一片**：grant 檔格式＋`within`／`expired`＋把 `until_round` 當 tick 側入口；`step` 加 `reserve→run→settle` 括號（效期鐘進來）。這時 r5 價值第一條「子工作對核心可見」才開始值錢。
5. **`adapt` 第一條鏈**：挑一個受限 node（r3 拍板題 2）做 `time` 或 `window` 轉接；`step` 的 `wait` 才需要「別人的鐘」。之後才是 kernel-core 搬 proto7-1。

## 4. 跟正在進行的精簡循環怎麼接

**HEAD 已到精簡第 5 步**（錯誤四分支 eab869c9；擴充點＋subd＋audit 8c6f08b8）；工作樹正在做第 6 步（控制包、kill 必帶 run、拿掉 ctl-seen）；之後是第 7 步刪誤用保護、第 8 步 spec 拆分與 docstring 減肥。

**精簡方案與骨架的對齊點（沒有真衝突）**：

- `retry_lost` 移出成取樣的模組（頂層定案 5）vs. 直譯器要「沒起成就重起」：**不衝突**——`step` 自己讀 `never_started` 事實決定重寫，不依賴 retry_lost；這正是 core-slimming §5.2「事實出口給模組讀」的用法【高】。
- F47「欠的 tock.json 只記不補」：直譯器每回合重讀 `state.json`，漏一次 tock 只是晚一回合【高】。
- `x` 透傳：core-slimming 給 `x.pack`，`step` 用 `x.step`，r3 的 adapt 說不靠 `x`——要一句約定「`x` 底下每包一個 key、核心不看」，否則第二個包就撞【中】。
- 核心行數預算（§9）：`step` 在 `modules/`，不計入；但 `step` 若日後想要「once 結束後多留 N 回合」（r5 不確定 #2），得走 §9 的三問，本輪的結果檔設計就是為了不走到那一步。
- 第 8 步 spec 拆分會把「核心只留上一次」「W7 交付物在槽外」留在核心 spec——結果檔慣例要引這兩條，不自己再寫一遍。

## 5. 落地才冒出來的技術題（短；★＝真的糾結、做成選項，原則 2）

1. 結果檔路徑誰決定：直譯器在產生 once 項 argv 時把 `${result}` 展開成 `<node>/out/<job>/<step>.json`（不用環境變數，G8 沒有 per-item env）。建議固定慣例，不糾結。
2. ★ **一步一回合 vs. 加完 once 就 `wake`**：守固定節拍（user-advice）還是快（lang-fable 不確定 #2）。選項 `wake: false|true` 放步驟表頂層，預設 `false`。
3. 子任務寫結果前被殺：`never_started` → 重寫；有 out.log 無結果 → `unknown` 分支，冪等步預設重起、非冪等步預設 `park`。規則，不糾結。
4. 槽名：每個 `run` 步一槽（`<job>.<step>`）還是一個槽重用。建議每步一槽：state 分離、槽數＝步數不隨回合長、日後可平行。不糾結。
5. 條件語言紅線：只准 `exists`／`glob`／`result.ok`／單一數字比較；不開運算式（r3 的 jq 警告）。寫死，不糾結。
6. ★ **耐性到期做什麼**：`on_timeout: fail|unknown|kill`（逾時≠對方沒做，r4 astra）。選項，預設 `unknown`→`park`。
7. `x` 命名空間：每包一個 key。一句約定，不糾結。
8. 九軸宣告放哪：v1 內聯在步（`idempotent`）；包級 `axes.json` 等 `pack.json` 定稿。不糾結。
9. 框架 `state.json` 壞掉（半寫、非物件）：核心三態的延伸——不前進、寫 `state.err`、等人；不從結果檔反推 `pc`。不糾結（原則 9）。
10. ★ **`end` 之後 keep 怎麼辦**：直譯器退出 0 後 keep 會再起；`restart_on_end: false`（新 run 看到 `pc=end` 立刻退出，總結每回合一筆 ended code 0）或 `true`（週期工作從頭來）。選項，預設 `false`；要「不再起」改寫表項 `enabled: false` 或用 `until_round`。
11. 時間契約在 `wait` 的最小欄：v1 只有 `patience_rounds`（自己的回合）；`until` 用別線的鐘延到 `adapt` 第一條鏈。不糾結。
12. `check` 要不要擋「等 keep 任務結束」：v1 的 `run` 全是 once，問題不存在；v2 若允許 `wait` 等別的槽，再加「對象必須 finite」那條。不糾結。

## 6. 最後

**這一輪最重要的三個結論**

1. **骨架落地對核心是零新增，而且不是口號**：逐句對位後每個核心欄位都在 HEAD 裡，新東西全是任務包（`step`、`adapt`、`account`）、檢查器與慣例；唯一的例外候選 `timing` 第一塊用不到。
2. **第一小塊是 `step` v1＋結果檔**，單 node、非 LLM（備份），只用 once／slot／launch／exit／never_started／x／edit_json 三態六樣現成零件，六個測試形狀能同時驗骨架第 1、2、4、5、6 句，並直接探 r5 不確定 #2。
3. **落地順序倒過來比較穩**：先慣例與直譯器（可讀、可查），控制包落地後再接 `ctl`／kill，再 `account`（這時「子工作對核心可見」才值錢），最後 `adapt`；跟精簡循環並行，只有 restart 相關的要等第 6 步。

**最不確定的三件事**

1. **`unknown` 分支會不會太常被走到**（r5 不確定 #2 的落地版）：子任務起了、寫結果前死、槽又被刪——這在 interval 快的 node 上多不多，第一塊的測試 4(b)(c) 才量得到；多的話壓力會回到「once 結束保留 N 回合」這個核心題【低】。
2. **每步一槽、`end` 後 keep 再起的樣子人看不看得慣**：槽數＝步數、每回合總結多一筆 code 0，跟 user-advice「不要一大堆檔」精神上貼不貼，要給使用者看過實際資料夾才知道【中】。
3. **`step` 放在 `modules/` 還是 `packs/`**：core-slimming §10.4 說格式相同、語意屬 kernel 層的歸 `packs/`，但 `packs/` 目前不存在、`pack.json` 也沒定稿；第一塊若先放 `modules/step/`，之後搬家要連帶改 argv 路徑。不影響設計，影響第一個 commit 的位置【中】。
