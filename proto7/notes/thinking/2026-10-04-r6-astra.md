**第六輪思考報告：把骨架接到現有體系**

**建議先做一個可獨立使用的通用 `step` 任務包：單一 node、兩個非 LLM 步驟、槽外結果檔、可跨 run 接續。** 先驗證交接是否省事、卡點是否看得懂，再接資源入口與鄰居通道；daemon／tick-tock 核心零新增。

現況以查閱期間的 HEAD `18edfcbf` 為準，未採用其他隊伍未 commit 的改動。本文是落地提案；所有新增包名、檔名與欄位均未實作。本輪只讀，未改檔、未 commit、未動 scratchpad，也未執行探針。

主要依據為[第五輪骨架與不確定事項](2026-10-04-r5-synthesis.md)、[十一條原則](../principles.md)；第四輪已撤回的說法不再沿用。

**一、先把「現有」與「正在搬」分清楚**

最近的核心精簡已完成工具外移、部分誤用保護精簡、錯誤四分支，以及三個擴充出口；但[頂層定案](../../../proto7-2/notes/core-slimming.md)尚未全部落實。

| 狀態 | HEAD 中的實際情況 |
|---|---|
| **現成** | `modules/tools/`、`modules/subd/`、`modules/audit/`；普通任務 `counter.py`、`history.py` |
| **現成** | `tasks.json.x` 透傳至 `birth.json.x`、lost 的 `never_started`、daemon 的 `stop-guard.json` |
| **已定、尚未搬完** | restart／reload、`ctl-seen`／`ctl_id`、`retry_lost` 仍在核心；定案是移出控制／重試功能、kill 必帶 run |
| **方案、尚未實作** | 診斷包、`packs/`、`pack.json` 安裝機制、`aos7-pack` |
| **尚無** | proto7-2 的 kernel／agent；proto7-1 有試做素材，但不能直接整包搬入 |

因此，第一片可以使用現有工具與檔案介面，**不必等安裝器，也不依賴即將搬走的核心重試與 restart 語意**。現況入口見 [README](../../../proto7-2/README.md)、[spec](../../../proto7-2/spec.md)。

**二、骨架六句，逐句對位**

下表的「慣例」指包自己採用的格式，不是向核心增加欄位語意。

| 第五輪骨架 | 現成 | 小改／慣例 | 新包與落點 |
|---|---|---|---|
| **① 本地回合、跨 node 對依據版本、先讀狀態** | `.aos/round.json.round`、槽內 `tock.json`；`.aosd/status.json.nodes[id]` 的 `phase`、`paused_by`、`round`、`last_error` | 輸出附 `src`、`basis`、版本；`tasks_rev` 只辨識任務表，不能代替業務依據版本 | `adapt` 保存、轉接依據；`observe` 量測流速與缺口 |
| **② 目前狀態／每件事件／一段期間** | 最新檔、掛載；daemon、任務控制及加掛都有請求／回條 | 各包 `contracts/*.json` 宣告下游需要什麼，以及保存、確認、容量滿政策 | `adapt` 的傳遞部分做逐件信箱；`window` 消費資料後產生期間值 |
| **③ 效期／耐性、入口核對並回條** | `from_round`／`until_round`、等待工具、控制回條 | 契約分列 `validity`、`patience`，各帶鐘、起算點與邊界 | `step` 管等待；`account` 或效果擁有者管准入與效果回條 |
| **④ 放置＋步驟表＋小框架＋契約** | `tasks.json`、`argv/inst`、`keep/each/once`、同槽狀態接續 | 子工作用包裝程式發布槽外結果；框架只留接續狀態與引用 | `step`：直譯器、步驟表、`frame.json`、結果協定 |
| **⑤ 九軸簽名與保守檢查** | `x` 可透傳契約引用；核心不解讀 | 包內契約是宣告，部署設定是政策，執行證據另外保存 | 先做 `step` 內的小檢查工具；有第二個使用者再考慮拆共用包 |
| **⑥ daemon／tick-tock 零新增** | 普通任務、argv 包裝、工具、公開檔案介面 | 新包守住既有所有權與寫檔規則 | 基礎設施擴充放 `modules/`；上層任務包放提議中的 `packs/` |

這裡有三個不能省略的限制：

- **請求／回條不等於可靠事件信箱。** 核心的同名回條會覆寫；逐件保存與去重仍是包的責任。
- **`until_round` 是啟動准入，不是完成期限。** 本地回合超過界線就不起新 run；已啟動的工作仍可能繼續產生效果。
- **「先讀 status」不是所有原因都在 status。** 基本狀態先看，必要時補讀 `last-round.json.errors` 或未來診斷工具；取樣看不到的細節不能補成事實。

這些界線由 [spec 的控制、槽與任務表規則](../../../proto7-2/spec.md)決定，不應由語言層改寫。

**三、主要產物放在哪裡**

程式與預設契約建議放 `proto7-2/packs/<包>/`；下表未加 repo 前綴的路徑都是 `<node>/` 底下的執行資料。新增路徑均為提案。

| 產物 | 分層／包 | 建議檔案與欄位 |
|---|---|---|
| 步驟表 | 通用 `step`，**新包** | `jobs/<job>/steps.json`：步驟識別、工作引用、輸入綁定、下一步；不把控制流塞進 `tasks.json` |
| 小框架 | 通用 `step`，**新包** | `jobs/<job>/frame.json`：程式版本、`pc`、階段、請求／嘗試識別、結果位置、等待起點；帳與信箱只留把手 |
| 結果檔 | `step` 封套＋工作自己的結果，**包裝慣例＋新包** | `jobs/<job>/results/<step>/<attempt>.json`：請求、輸入版本、實際 node／slot／run、結果狀態、产物引用與雜湊 |
| 通道契約 | 所屬包，**新慣例** | `contracts/*.json`：整批／串流另列；下游需求分 latest／每件事件／期間；事件另列順序、確認、保存、容量與滿載處理 |
| 時間契約 | 所屬包，**新慣例** | 同契約檔的 `validity`、`patience`：`clock`、起算點、截止邊界、遲到結果政策；鐘要能辨識來源與世代 |
| 入口回條 | 效果／資源擁有者，**新包** | 所屬包的 `receipts/<request>.json`：綁請求、依據、准入／提交階段、結果；只證明該入口真正控制得到的部分 |
| grant 與帳 | 通用 `account`，**新包；舊探針有素材** | `account/grants/`、`ledger/`、`receipts/`：使用權、預留、結算、在途未知；不能拿取樣的 `usage.json` 充當精確帳 |
| 出處與固定依據 | 通用 `adapt`，**新包／慣例** | `src`、`basis/about`、規則版本；`adapt/evidence/` 保存需要重算的版本，雜湊不代替保存 |
| 確定性轉接 | 通用 `adapt`，**新包** | `chains/<sense>.json`、`in/<sense>.json`、證據區；一般 copier／信箱傳遞沿 r3 收進此包，避免另建重複的 relay |
| LLM 轉接 | LLM `adapt-llm`，**新包** | 模型／prompt 版本、候選、引文、驗證結果；不讓摘要成為使用權或效果回條 |
| 時間量測 | 通用 `observe`，**部分素材現成、量測新做** | `observe/timing.json`：觀測範圍、鐘、取樣區間、缺口、估計值；精確 daemon 內部耗時目前仍缺 |

前幾輪的完整理由直接沿用：[r1 使用權／帳／信箱](2026-10-04-r1-synthesis.md)、[r2 出處／時間](2026-10-04-r2-synthesis.md)、[r3 轉接包](2026-10-04-r3-synthesis.md)。

`adapt` 的一條確定性鏈仍可以在一個程序內順序執行。只有需要獨立觀測、控制或恢復的工作邊界，才拆成 `step` 的子任務；不把每個欄位轉換都拆成一個槽。

**四、任務包分層表**

依[精簡方案 §10](../../../proto7-2/notes/core-slimming.md)與原則 8，建議如下。這是用途分類，不是每個包都必須依賴完整 kernel。

| 分層 | 包 | 放什麼 |
|---|---|---|
| **kernel 核心任務** | `kernel-core` | 等 tock、讀快照、接續自身狀態、規則介面、把決定寫成 tasks／控制／掛載請求；不帶資源種類與分配算法 |
| **通用任務包** | `step` | 步驟表、框架、结果交接、等待與保守檢查 |
| 同上 | `account` | grant、帳、預留／結算、分配者、資源入口框架；資源與算法可擴充 |
| 同上 | `adapt` | 固定依據、確定性轉換、一般信箱、事件／窗口、時間轉接 |
| 同上 | `observe` | 現有 history 的用途、來源缺口、流速與時間品質觀測 |
| 同上 | `supervise`、`schedule` | 通用監督、退避、排程、准入政策、控制者協調 |
| **agent 包** | `agent-team` | agent 狀態機、角色名冊、角色訊息、記憶與工具協定、團隊部署模板 |
| **LLM 包** | `llm-endpoint`、`adapt-llm`、`llm-operator` | client／端點、LLM 專用入口、摘要與候選驗證、LLM 決策者；通用執行動作仍歸通用包 |

daemon／tick 層的 `tools`、`subd`、`audit`，以及待移出的控制／重試／診斷功能，仍屬 **`modules/` 的模組、包裝程式或工具**。依賴方向是上層使用它們，不是核心反過來呼叫任務包。

有一處文件分類需對齊：[組件契約 §2.8](../../../proto7-2/notes/component-contracts.md)把帳本、准入等列作 kernel 核心任務例子，[精簡方案 §10](../../../proto7-2/notes/core-slimming.md)則分入通用包。本輪建議採後者，讓不需要記帳的用途也能單獨使用 `step`。

proto7-1 的 kernel／agent 可以抽取規則與狀態機；舊的槽查找、用量累計、控制去重與 pause 欄位需重新接合，不能整包搬入。差異見[四層交接調查](../../../proto7-2/notes/layer-interfaces.md)。

**五、九軸落檔，但第一版只檢查三條**

九軸放 `contracts/<工作>.json`；部署政策放 `config.json`；本次結果與測試證據另存。`tasks.json.x` 最多放契約版本與引用，完整宣告不必重複抄進去。

| 軸 | 建議宣告內容 | 誰使用 |
|---|---|---|
| 1 I/O | 格式、單位、整批／串流、latest／事件／期間需求 | `step` 接線、`adapt` 轉接 |
| 2 生命週期 | 有限工作／服務、完成條件 | 等待檢查器；`once` 本身不代表有限 |
| 3 跨呼叫狀態 | 狀態歸屬、版本、接續與重設方式 | 工作與直譯器 |
| 4 資源 | 需求、估計、上限、使用權引用分列 | `account`／入口；`max_live` 只代表槽數 |
| 5 可中斷性 | 中斷後可保證什麼、怎麼恢復 | 工作、監督包 |
| 6 執行保證 | 冪等範圍、邏輯請求鍵、效果查詢／回條 | 重試工具與效果入口 |
| 7 組合 | 輸入綁定、依據版本、順序及失敗傳遞 | 步驟表／轉接鏈 |
| 8 環境 | 掛載、服務版本、授權與時鐘來源 | 部署與入口 |
| 9 幾率性／可預測性 | 固定比較條件後是否含隨機因素；相對觀察者是否可預料 | 先作描述；可預測性不推導驗證或重試政策 |

第一版只檢查第五輪留下的三條：**等結束的對象須是有限工作；重試須有冪等承諾或先查回條；時間值須標明哪條線的鐘。** 結構錯誤如不存在的步驟引用另外照格式檢查。

沒宣告仍可照普通任務執行，只是不替它自動重試、平行化或替換。宣告也不會改掉 tick 的行為：不宜自動重做的副作用工作，不能因填了九軸就安全地設成 `keep`。依據見[九軸原稿](2026-10-04-axes-astra.md)及[第五輪修正](2026-10-04-r5-synthesis.md)。

**六、第一小塊：單 node 的「CSV 轉換 → 統計報表」**

選一份固定版本 CSV，第一步轉成 JSON，第二步讀取已提交的 JSON 產生統計。兩步都有限、可重算、只寫這份工作的輸出目錄，沒有 LLM、網路或外部副作用。

這片驗證骨架的主幹：**依據固定、子工作由核心管理、結果可保存、直譯器可接續、未知不冒充未執行。** 跨 node、不漏事件與資源強制留給後續切片。

| 建議新增檔案 | 用途 |
|---|---|
| `proto7-2/packs/step/README.md`、`spec.md` | 先定直譯器、工作包裝程式、結果的契約卡：職責、前置條件、保證、明確不管 |
| 同包 `bin/aos7-step` | 一個普通 `keep` 任務，`max_live: 1`；讀框架、查結果、登記下一步 |
| 同包 `bin/aos7-step-result` | 普通任務包裝程式；執行工作、檢查其約定的產物、原子發布結果 |
| 同包 `bin/aos7-step-check`、`tests/` | 小檢查器與下列探針 |
| `<node>/jobs/<job>/steps.json`、`contracts.json`、固定輸入 | 兩步流程、契約與輸入版本 |
| 同工作目錄的 `frame.json`、`results/`、`out/` | 接續框架、每次嘗試的結果、實際產物；全部在槽外 |

`.aos/tasks.json` 仍用現有格式：一個直譯器 `keep`，每次只登記下一個子工作的 `once`。第一版直接指定 argv／設定位置，不先做套件安裝器、語言前端或平行控制流。

**執行與恢復必須寫死的約定：**

1. 分清 `job_id`、`step_id`、跨重送保持的邏輯 `request_id`、每次嘗試的 `attempt_id`，以及核心的 `slot#run`。核心 run 由實際 birth／環境取得，不預猜回合號。
2. 先保存派工意圖，再拿 `tasks.json.lock` 加項；任務名稱用合法的英數、`_`、`-`。表項與 argv 帶同一份嘗試識別。
3. 直譯器重開先找匹配的槽外結果，再查待啟動表項與槽；有證據就接續，不重新登記已派出的工作。
4. **框架與任務表不是同一筆交易。** 中斷後若所有證據都不在，可能是尚未派出，也可能是跑過而未交付；第一版保留 `unknown`，不自動重送。
5. 已就緒結果可以立即推進 `pc`；新子任務仍由下一個 tick 啟動。子工作活著時，即使 once 表項已移除，槽仍可觀測，也能帶精確 run 送 kill。
6. 結果是工作交付的依據，`exit.json` 是程序旁證。效果完成但結果尚未落檔時被殺，不能因缺結果就宣稱没做過。

第一版結果保留到工作擁有者明確結案；不靠核心延長 once 槽壽命。等待先採本 node 回合耐性，起點寫入框架；pause 時耐性不前進，不宣稱牆鐘逾時。

**探針形狀與驗收：**

| 探針 | 必須看見的結果 |
|---|---|
| 正常兩步 | 第二步只讀第一步已提交的指定版本；兩步有獨立核心 run，產物正確 |
| 子工作仍活時收掉直譯器 | `keep` 重開後接回同一嘗試，不多派一次 |
| 結果已提交、`pc` 尚未更新時中斷 | 重開消費既有結果，流程只推進一次 |
| 直譯器漏看多回合、once 槽已清 | 仍靠槽外結果繼續 |
| once 表項移除後控制活工作 | status 仍可見；帶 run 的 kill 只作用於指定執行 |
| 產物已寫、結果未提交時殺工作 | 不誤報成功，不把未知當未執行，不自動重送 |
| 派工窗口與壞任務表 | 分別在兩次提交前後中斷；證據不足停在未知；表壞時拒寫，保留其他任務 |
| 契約、效期與耐性 | 檢查器抓到三類已知違約；`until_round` 擋過期新啟動；已啟動工作不被冒稱到期取消；耐性到期不抹掉遲到結果 |

另用同一案例對照手寫 Python：比較恢復需要的人工作業、重複派工次數，以及能否直接讀檔找出卡點。這才回答第五輪「這層值不值得存在」。

**後續順序共五步：**

1. 定最小契約，完成上述單 node 切片與探針。
2. 接一個可查詢、可去重的本地資源入口，補准入／提交回條，再接 `account` 的最小 grant 與預留。
3. 加一個鄰居，用 `adapt` 傳固定依據與最新值，驗證不同回合速度下的效期與耐性。
4. 有逐件需求再補事件保存、確認、容量與窗口；不漏件保證在這一步才成立。
5. 接 agent／LLM 作者及 `adapt-llm`，共用已驗過的產物格式；需要時再增加前端。

**七、怎麼接正在進行的改進循環**

| 工作 | 與核心精簡的關係 |
|---|---|
| 契約卡、兩步範例、框架／結果格式、檢查器、離線案例 | 可以並行；只落在新任務包 |
| 只用公開 tasks／結果介面的原型 | 可以獨立準備；整合驗證固定在精簡收尾的 commit |
| restart／reload、自動 lost 重試、監督包控制動作 | 等移出後的控制／重試契約穩定再接 |
| 依賴詳細 status 的診斷與時間品質工具 | 等基本欄位與診斷包邊界確定；先寫不依賴擴充欄位的部分 |

改進循環仍依原則 10：**先補包的契約卡，再做探針，再按組件歸屬修正。** step 派重複工作是 step 的問題；包沒保存承諾的結果是包的問題；不能一律往 tick 加保護。

核心精簡與骨架沒有根本衝突，但三處必須收窄承諾：

- **retry_lost 移出後可能漏取樣。** 不承諾每個 lost 都會補跑；`never_started` 也只是「看起來沒起」，不是無效果證明。
- **核心只留最新，包保存自己的責任。** 正常結果可由槽外檔案解決；結果前中斷的未知不能靠多留幾回合完全消除。
- **r2 的精確 `timing` 要求不能當既定核心需求偷渡。** observer 只能量取樣，工作包裝程式只能量它包住的部分；目前沒有足夠接面取得完整 daemon 內部定點耗時。

本輪沒有提出必要的核心例外。若未來精確內部量測確實不可替代，再單獨說明現有任務／包裝／工具接面為何做不到，不先列為第一片依賴。

**八、落地才需要逐題定的技術題**

| 題目 | 建議 |
|---|---|
| **〔選項〕耐性用哪個鐘？** | 第一版本地回合；需要真實時間再選單調鐘，並定義跨 run／重開機接續。兩者會有不同的 pause 行為 |
| **〔選項〕結果與事件保留多久？** | 第一版明確結案才清；之後可選確認後清或期限／容量上限，但相應縮短查詢、去重與補讀保證 |
| **〔選項〕未知時怎麼辦？** | 預設停；可選查入口、交人工，或在工作契約允許下重送。不能提供無條件「未知就重試」 |
| **〔選項〕遲到結果怎麼處理？** | 保存事實；是否採用結果由工作選擇。停止等待不等於撤銷效果 |
| 派工跨檔窗口要不要做交易？ | 暫不做；先量未知的頻率與人工恢復成本，再決定包內是否需要更完整紀錄 |
| 換程式版本後能否接舊框架？ | 執行中工作先固定程式／契約版本；沒有明確遷移規則就不直接接 |
| 何時算成功？ | 程序退出、產物交付、業務效果分開；由工作契約說明結果能證明到哪一層 |
| 要不要延長 once 槽保存？ | 第一片不需要；先驗槽外結果，未知效果仍交給工作／入口查證 |

這些是實作時的處理建議，不是本輪要求使用者立即拍板的清單。

**這一輪最重要的三個結論**

1. **落點已足夠清楚：基礎設施擴充留 modules，工作語意進任務包；目前沒有理由增加 daemon／tick 核心。**
2. **第一片做獨立的通用 step 包。** 先用兩個非 LLM 工作驗證可觀測、可接續、可讀的交接，不必等待完整 kernel、資源系統或語言前端。
3. **最先落實的應是結果與責任保存。** once、退出碼、最新總結各有範圍；步驟表的價值在於如實呈現已完成、等待與未知，並減少重寫恢復邏輯。

**最不確定的三件事**

1. 最小步驟語意能不能真的比手寫 Python 省事；還是把同樣的複雜度搬成更多 JSON。
2. 派工窗口、結果前中斷造成的未知有多常見；保守停住的成本是否值得增加包內恢復機制。
3. 真正接上的資源與外部工具能提供多少查詢、去重與期限控制；這決定骨架能承諾到哪裡，不能由宣告補足。
