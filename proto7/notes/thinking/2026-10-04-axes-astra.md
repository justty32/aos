# 九軸用在 aos：從任務特性，走向可組合的 node 契約

**我的判斷：九軸最有價值的用途，是讓 kernel 知道「什麼條件成立時，可以對這個任務做什麼」。** 例如可否重試、停止、接續、換掉，或把輸出交給下一個 node。這比單純替任務分類更直接，也能長出 agent／LLM 之外的組件系統。

套到 node 時，關鍵則是把「單次輸入→輸出」擴成「輸入歷程→輸出歷程」。第三輪提出的受限 node，正好提供組合的判準：**轉接可以丟掉資訊，但不能丟掉這個 node 必須分辨的差異。**

以下是設計提案。現況依指定 spec 解讀；`pack.json` 格式來自精簡方案，三輪綜合中的構想不視為已實作功能。本次只讀文件，未修改檔案、未執行探針。

## 1. 任務＝函式：九軸逐軸落地

| 軸 | 在 aos 任務裡的具體意思 | 已有什麼、還缺什麼 |
|---|---|---|
| **1. I/O 型態** | 從哪裡讀、寫到哪裡；資料格式、單位、整包／串流／互動；何時算交付 | 已有 argv、inst、檔案、掛載、stdout；缺業務 schema、交付條件，以及 latest 取樣與逐件事件的區分 |
| **2. 生命週期** | 單次 run 是有限工作還是常駐服務；是否跨回合；何時算完成 | `keep／each／once` 已有，但它們是**啟動策略**。`once` 可以啟動常駐服務，`keep` 也可以反覆起短任務 |
| **3. 跨呼叫狀態** | 哪些狀態會影響下一次執行；歸 run、槽、node，還是外部服務 | 同槽自寫檔會留下；缺狀態格式、版本、重設與並行存取契約。槽被刪就不再保留，交付物須放槽外 |
| **4. 資源特性** | CPU、RAM、GPU、端點、額度、獨占寫權；需求、估計用量、有效使用權 | `max_live` 只限制槽數；資源宣告、grant、准入與結算屬 kernel。估計值、使用上限、供應保證要分開 |
| **5. 可中斷性** | SIGTERM、SIGKILL 各會造成什麼；能否重算、續跑、回復；外部工作是否仍在途 | 已有 kill／restart 機制；缺任務自己的恢復承諾。**tock 是通知，不是中斷** |
| **6. 執行保證** | 相同邏輯請求重送的效果；交易邊界；dry-run 是否真的無業務副作用 | 已有 once 啟動保證與 `retry_lost` 規則；缺業務效果的冪等範圍、去重鍵、保存期限與提交證據 |
| **7. 組合模式** | 誰接誰、如何綁定輸入、先後／平行、失敗後重跑哪段 | 應成為任務包的**連線契約**；不只是一個任務自己的標籤。`tasks.json` 排列不保證執行完成順序 |
| **8. 環境模式** | node、掛載、來源、服務版本、可讀寫範圍、使用權；依賴消失怎麼辦 | 已有空間與掛載；應補部署需求。掛載表示可達，不自動代表資料有效、具有授權或受到強制隔離 |
| **9. 確定性** | 固定輸入、初態、版本與外部觀測後，哪些結果可重現 | 核心不判定；LLM 任務需要，但讀時鐘、亂數、外部服務或競爭同檔的傳統程式也需要 |

這些區分依據 九軸原文（`~/repo/ai_core/docs/kb/kb-ss/doc_05_axes_metadata.md`，repo 外）、[任務表與生命週期](../../../proto7-2/spec.md)及[槽的保存規則](../../../proto7-2/spec.md)。

原文有三個值得在 aos 裡拆開的聯想：

- **無狀態 ≠ 確定性。** 不記住上次呼叫，也可能每次讀到不同外部資料。
- **安全中斷 ≠ 安全重試。** 本地檔案沒壞，不代表遠端請求尚未扣款；可續跑也不代表可以任意並開第二份。
- **確定性 ≠ 正確、無損或準時。** 固定取整可以每次都錯；固定丟掉欄位可以每次都漏。

`once` 預設的「最多一次」針對啟動，不保證成功交付，更不保證外部效果恰好一次。`retry_lost` 只處理特定「看似尚未起來」的 lost，接受可能重複的代價；不是所有失敗都重試的開關。精簡方案末段已定方向要把它移成模組，本報告不依賴它留在哪一層。[once 規則](../../../proto7-2/spec.md)

## 2. metadata 放哪裡，以及它真正代表什麼

建議分三份，避免把能力、政策與事實混在一起：

| 層次 | 建議位置 | 內容與讀者 |
|---|---|---|
| **任務定義** | 包內 `pack.json` 引用的契約檔 | 作者宣告九軸、前置條件、效果範圍；給安裝器、組合檢查器與 kernel 讀 |
| **node 部署** | 包自己的 `config.json` | 綁定實際掛載、來源、使用權、重試政策、期限；給該 node 的 kernel 任務讀 |
| **執行與驗證證據** | 包自己的 state／evidence 位置 | 記錄實際採用的版本、邏輯請求、run、提交回條、測試範圍；給恢復與驗證者讀 |

`tasks.json` 繼續只承載啟動所需資料。包設定路徑可以經 argv 傳入；第一版不需要 `x` 透傳，更不需要 tick 認識九軸。這沿用[任務包方案](../../../proto7-2/notes/core-slimming.md)與第三輪「設定放包自己的檔」的方向。

**作者宣告、測試證據、這次執行狀態必須分開。** `idempotent: true` 是承諾；重複執行測試通過是有限證據；這次遠端是否已提交則是另一個事實。三者不能互相代替。

宣告也有作用範圍：任務版本、設定、依賴換了，舊證據不一定適用。邏輯請求鍵須跨重試保持相同，不能直接拿每次都變的 `AOS7_RUN` 當去重鍵。

沒宣告的軸先視為**未知**：任務仍能照既有方式執行，只是 kernel 沒有依據替它自動重試、搶占或替換。先讓幾個真正需要管理的任務填，不要求每支小腳本填滿九軸。

## 3. node＝時變函式：需要描述的是整段歷程

可以寫成：

\[
(s_{k+1},\,o_k)=F_{v_k}(s_k,\,u_k,\,\sigma_k)
\]

`k` 是自己的回合；`s` 是內部狀態與在途工作；`u` 是本回合實際讀到的外部版本、事件與時間資訊；`σ` 是會影響結果的讀寫順序；`v` 是規則、設定與組件版本。

外部變量改變時，可以先當作輸入改變；規則或模型換版時，才需要改變 `F` 本身。這使「哪個東西時變」能被記錄與測試。

**回合只是離散的觀察尺度，不自動提供整回合快照。** 任務會跨回合，也可能在回合中途讀掛載；同樣的回合起點檔案，不一定導出同樣結果。

| 軸 | 改寫成 node 契約 |
|---|---|
| I/O | 吃哪些事實／意圖、發布哪些事實；每個入口是 latest、逐件事件或窗口 |
| 生命週期 | 啟用、暫停、恢復、退役；內部 run 換了，服務是否仍被視為同一個 |
| 狀態 | 自有檔案、事件游標、在途請求；重開沿用什麼，複製時必須重新建立什麼 |
| 資源 | 持續服務所需資源與准入條件；供應不足時等待或降級 |
| 可中斷性 | pause、kill、daemon 重開分別允許什麼；恢復後如何對帳 |
| 執行保證 | 事件、決策與副作用各自如何去重；保證跨哪些生命週期成立 |
| 組合 | 上下游的歷程是否相容；回授是否可能形成無限觸發 |
| 環境 | 必要來源、掛載、服務、協議、詞彙、容量與可見範圍 |
| 確定性 | 相同初態、版本與完整輸入歷程，是否得到相同業務輸出歷程 |

確定性測試可以忽略無關的 run id 或顯示時間，但不能忽略漏件、重複副作用與業務順序。如果必須固定執行交錯才能重現，就只宣告這個較弱保證，不宣告所有合法交錯都等價。

### 需要新增的部分

我建議先加一份**時間契約**，不急著把九軸擴成十二軸：

- **讀取規則**：何時取樣、事件順序、允不允許合併或跳過。
- **時間基準**：哪個 node 的鐘、起算點、期限邊界；跨線不直接換算回合。
- **反應要求**：延遲目標、截止時間、遲到後等待／丟棄／降級；目標不冒充保證。
- **中斷後的缺口**：補事件、只取最新，或明確輸出 gap／unknown。

外部依賴放第八軸；受限性分布在第一、七、八軸。**「受限程度」不適合壓成一個分數**：只吃布林值但要求逐件不漏，可能比能吃任意 JSON 的取樣器更難服務。

第三輪的必要區分，應從單份資料推廣到歷程：**若兩段來源歷程需要 node 做出不同反應，轉接後就不能變成同一段輸入歷程。**「一直正常」與「曾過熱、現在恢復」具有相同 latest；只靠最新值，任何確定性驗證器都救不回中間那次過熱。[第三輪綜合](../../../proto7/notes/thinking/2026-10-04-r3-synthesis.md)

另須保留現有邊界：pause 只停新回合，既有任務仍能工作；daemon 重開接續回合，不替業務恢復狀態。若 node 宣告「暫停後不再提交」，必須由自己的任務或提交入口實現。

## 4. 九軸能讓哪些 kernel 任務通用化

| 任務包 | 可以自動做的事 | 動手前仍須成立的條件 |
|---|---|---|
| **監督／重試** | 依效果契約選重算、續跑、查回條或等待 | 相同邏輯請求與輸入版本；旧 run 狀態符合政策；重試仍有額度。效果未知時不能當作沒做 |
| **排程／搶占** | 在符合中斷契約的任務間挑選停止對象 | Safe 要說明涵蓋哪種訊號；Resumable 要有有效 checkpoint；資源確知釋放後才重新分配 |
| **資源分配** | 將需求與可用 grant 配對，決定准入或排隊 | 需求宣告不是授權；真正支用仍由資源入口檢查、預留與結算 |
| **轉接／驗證** | 比對格式、單位、時間模式與必要區分；插入已知驗證步驟 | 必須已有對應驗證器。非確定性標籤不能憑空產生「判斷內容是否正確」的能力 |
| **觀測／認證** | 依軸值挑選重播、重送、中斷、缺件與資源量測測試 | 報告測試版本與覆蓋範圍；未知、失敗與通過分開 |

**管理動作應由多軸共同決定。** 可重試至少涉及第六軸的效果、第一軸的固定輸入、第三軸的恢復状态、第四軸的成本，以及第八軸的有效依賴。

這也暴露一個實作邊界：`keep` 本來就會補起空槽，kernel 讀到「不可自動重試」不會讓 tick 自動改行為。需要此政策的任務，可以由包裝程式在每次 run 起來時先做恢復判定，或交給 supervisor 管理 `once／enabled／from_round`；不能只加 metadata 就宣稱受到保護。

## 5. 串接時，軸值怎麼合成

以下針對 `A → B`，尤其是「整段重跑」；結果不足以判定時保留未知，不強填一個布林值。

| 項目 | 保守合成規則 |
|---|---|
| I/O／組合 | A 的輸出保證必須滿足 B 的前置條件；schema、單位、權威性、事件／取樣語意都要相容 |
| 生命週期 | 常駐 A 不會自然「跑完再交給 B」；須定義每件資料或服務就緒的交接點 |
| 狀態 | 合併讀寫範圍；共享寫入需要次序或相容規則。有副作用不等於有跨呼叫記憶 |
| 冪等 | 含非冪等步驟，預設不可整段重試；兩段都冪等，仍須確認中間值、共享狀態與效果身分 |
| 交易／dry-run | 各段交易不推出全鏈交易；須有共同提交邊界。全鏈 dry-run 必須涵蓋每個業務副作用 |
| 中斷 | 除各段外，也要保護交接窗口；checkpoint 必須與輸出提交一致 |
| 資源／時間 | 真正串行且前段釋放後：耗時可相加、峰值可取最大；緩衝、常駐、並行與等待另外算 |
| 環境 | 合併必要依賴與權限需求；有衝突或缺授權就不能照原契約部署 |
| 確定性 | 兩段確定、依據固定、次序受控才可推出；含非確定步驟預設不保證，除非證明差異不影響可見結果 |
| 資訊損失 | 另記保留與丟失的差異；精確但有損也必須通過下游的必要區分檢查 |

**兩個冪等不能直接做 AND。** A「把 b 設成 a」，B「把 a 設成 b＋1」，各自重做都不再改變結果；但整段每重跑一次，a 又增加一次。這是舊組合文件（`~/repo/ai_core/docs/kb/kb-ss/doc_21_composition_dimension.md`，repo 外）「最弱一環」規則之外，aos 需要補上的條件。

同樣地，非確定步驟後接驗證器，只能保證通過已檢查的條件；仍可能每次產出不同但都合格的答案，不因此變成確定函式。

## 6. 契約卡與錯誤歸屬

九軸可以產生契約卡骨架，例如「環境需要固定版本輸入」「輸出按邏輯請求鍵去重」。但**無法自行推導什麼叫完成、哪些損失可接受**；這些仍由功能定義給出。

沿用現有四類即可：

- **M 誤用**：呼叫者違反已寫明的前置條件，例如把持續變動檔案當不可變輸入。
- **X 外部故障**：I/O 或程序中斷導致結果未知，組件依契約保留並等待。
- **B 組件 bug**：前置成立，任務宣稱冪等卻重複產生效果；或 kernel 違反中斷條件仍搶占。
- **G 契約缺口**：沒有說明去重範圍、提交邊界或缺事件如何處理。

所以「違反軸宣告＝誤用」不成立。**承諾者沒做到保證，是承諾者的 bug；使用者沒守前置，才是誤用。** 不把 kernel 層協定的問題推給 daemon／tick。[組件契約與四類錯誤](../../../proto7-2/notes/component-contracts.md)

## 7. 兩份宣告草稿

以下名稱與 schema 都是提案；`evidence` 明寫只有宣告，避免看起來已經驗證。

第一份是供 `pack.json` 引用的任務契約：把固定版本的溫度事件轉成窄格式，保留事件身分；輸出位置由部署設定按 key 綁定。

```json
{
  "schema": "aos.axes.task/draft-1",
  "task": "temperature-project@1",
  "io": {
    "channel": "file-json", "flow": "batch",
    "input": "temperature-event/1", "output": "hot-event/1"
  },
  "lifecycle": {"run": "finite", "launch_default": "once"},
  "state": {"cross_call": "none"},
  "resources": {"cpu_slots": 1, "ram_estimate_mib": 16},
  "interruptibility": {
    "sigterm": "safe", "sigkill": "safe",
    "scope": "published-artifact", "recovery": "recompute"
  },
  "guarantees": {
    "idempotency_key": ["source_epoch", "event_id", "rules_hash"],
    "effect_scope": "one-artifact-per-key",
    "commit": "single-file-rename",
    "dry_run": false
  },
  "composition": {"preserves": ["hot", "event_id", "source_order", "gap"]},
  "environment": {
    "requires": ["immutable-input-version", "exclusive-keyed-output-path"],
    "enforcement": "cooperative"
  },
  "determinism": {"kind": "deterministic", "scope": "artifact-content"},
  "evidence": {"status": "declared", "reports": []}
}
```

此處 Safe 只承諾程序中斷不留下半份已發布成果；不涵蓋斷電持久性。無跨呼叫狀態也不代表沒有寫檔效果。重算仍會消耗資源。

第二份是 node 契約：只吃轉接過的事件，必須識別「曾過熱」，不要求它理解原始溫度資料。

```json
{
  "schema": "aos.axes.node/draft-1",
  "node": "heat-monitor",
  "io": {
    "input": "hot-event/1", "output": "alarm-fact/1",
    "flow": "ordered-events", "unknown": "publish-unknown"
  },
  "lifecycle": {"service": "persistent", "retire": "drain"},
  "state": {"path": "data/monitor/", "clone": "fresh-identity-and-cursor"},
  "resources": {"profile": "small-cpu", "on_unavailable": "wait"},
  "interruptibility": {
    "task_restart": "reconcile-and-resume",
    "timeline_pause": "no-business-freeze-guarantee"
  },
  "guarantees": {
    "dedupe_key": ["source_epoch", "event_id"],
    "scope": "alarm-publication", "retention": "until-source-retired"
  },
  "composition": {
    "must_distinguish": ["always-normal", "hot-then-normal", "input-gap"]
  },
  "environment": {
    "source": "mounted-adapter-events",
    "requires": ["retain-until-ack"], "direct_raw_read": false
  },
  "determinism": {"kind": "trace", "rule_version": "monitor@1"},
  "time": {
    "order": "source-sequence", "clock": "source",
    "response_target_local_rounds": 2, "hard_deadline": null,
    "on_gap": "unknown"
  },
  "evidence": {"status": "declared", "reports": []}
}
```

事件保存、游標與去重是包自己的責任；宣告它們，不表示核心突然具有逐件交付保證。

## 8. 一個離線小探針：九軸能否擋下錯誤組合

**探針 `trace-contract`：假來源 → 轉接任務 → 受限監看 node。** 不接 LLM；先用單一離線模型模擬讀取、中斷與重開，不改 daemon。

固定兩段來源歷程：「正常→正常」與「正常→過熱→正常」。比較 latest 取樣、保存至確認的事件流兩種接法，再注入重複交付、延遲、輸出已提交但游標尚未更新時中斷，以及來源保存期耗盡。

驗收五件事：

1. 檢查器事先拒絕 latest 接到「不得漏掉曾過熱」的 node。
2. 事件鏈在保存條件成立時，重開後告警不漏、不重複發布。
3. 相同初態、版本與輸入歷程，產生相同業務輸出。
4. 保存期耗盡時明示 gap／unknown，不靜默當成正常。
5. 正常案例全部完成，不能靠全部拒絕換取零錯誤。

另放入一個故意宣稱冪等、實際追加重複告警的假任務，確認測試能推翻宣告。這個探針只驗證上述狹窄契約，不代替真实程序中斷或檔案系統測試。

## 9. kernel 之上最有潛力的兩條線

**第一條：帶行為檢查的組件組裝與工作流。** 像管線，但除了資料格式，還會檢查事件完整性、效果、資源、時間與恢復条件。先讓人畫 `A→B`，工具解釋哪裡能接、缺哪個轉接器；通過後產生普通任務與包設定。

它自然能長成可恢復工作流：哪段可以重算、哪段必須查提交回條、哪個結果要保留，都由契約決定。起步可以是一個程序依序跑幾步，不必先建立大型排程語言。agent 可以提出組裝方案，確定性檢查器負責檢查；備份、資料處理、監看同樣能用。

**第二條：契約測試與可替換組件目錄。** 把第九軸的 LLM 認證擴到其他軸：中斷能否恢復、重送是否重複、哪些資源量測可信、缺件是否誠實回報。證據綁定版本、設定、環境與測試集。

目錄便能搜尋：「找一個吃得下相同輸入、保證至少同樣強、需求沒有超出現有供應的替代品。」有狀態 node 還須檢查狀態相容或提供遷移方式。先讓兩個內部包可替換，比先做市集更容易驗證價值；agent 是目錄的使用者，LLM 認證只是其中一類測試。

「node 的物理學」適合先當實驗方法：量延遲、積壓、回授與擾動是否被放大。九軸提供描述入口，但還沒有足夠資訊推導整體穩定性，不宜現在再立第三套平台。

## 10. 照原則檢查

**本案對 daemon／tick-tock 核心新增為零。** 宣告、組合檢查、版本留存、恢復與驗證都由普通任務、包裝程式或工具承擔；核心仍只留上一次。來源只有 latest，就承認只能取樣，不要求核心替上層補歷史。

契約、重試、資源准入、轉接、驗證與目錄都是**通用**；agent 狀態機、記憶與工具協議歸 **agent**；模型／prompt 版本、端點細節與摘要品質測試歸 **LLM**。用 LLM 提出通用排程政策，不會使整個排程包變成 LLM 專用。

第一版也不必做九個管理器：先讓現有 `supervise`、`schedule`、`account`、`adapt` 各讀自己需要的欄位。這符合[單一 node、核心精簡與先定功能的原則](../../../proto7/notes/principles.md)。

## 11. 值得你拍板或想的兩題

1. **第一個驗值點要放重試，還是受限 node 串接？** 我偏向串接：用上面的五項驗收，能直接測出九軸是否提供原本沒有的判斷能力；若眼前已有一個反覆出錯的重試任務，則先拿它更划算。
2. **第一個真實 node，絕不能混淆哪兩段輸入歷程？** 建議先給三組案例，並分別說明錯一次、漏一次、晚一次的後果；這比先定完整 schema 更能決定契約內容。

## 我最不確定的三件事

1. **宣告能否足夠小，又足夠可信。** 冪等與中斷承諾若最後都需要專屬判定器，共通價值可能主要在契約格式與測試入口，而非通用推導。
2. **必要區分能否被有限案例說清楚。** node 有狀態與回授後，單筆案例很容易漏掉歷程差異；測試能提高信心，無法替使用者完整定義用途。
3. **組合檢查能自動推到哪裡。** 格式、時間模式與明確效果容易檢查；語意正確、並行等價與可替換性困難得多。最實用的第一版，可能是可靠地指出「這裡還不知道」，而非替每條鏈發合格證。
