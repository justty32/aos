# 整理版

## 一、基礎架構

### 1. 單一路徑尋址，與 aos index 體系

- JSON 和檔案系統用單一路徑尋址。這是爲了降低 agent 的認知負擔。
- 在此基礎上延伸出 aos index 體系。
- 這和 Plan 9 namespace 不太一樣，因爲我們還添加 description 等。
- 目的：讓 agent 眼中的世界更加單純，讓他觀察起來更加舒服。

### 2. 把檔案系統當作 lua/lisp 來使用：`_entry` 與 aos-exec

- 以 POSIX 呼叫爲基礎，善用 stdin/out/err 等，作爲 `_entry`。
- 這個舉動有好有壞。要說他降低了 agent 的認知負擔嗎？倒也沒有。
- 硬要說的話，就是讓他能夠適配 Linux 體系，允許接入各種不同技術棧。
- 其核心就是一個 aos-exec。

### 3. 函數屬性：`_metainfo`

- 在 `_entry` 的基礎上，延伸出函數屬性。這是動態的，相對於檔案屬性。
- 最基礎的就是九軸，但也可以隨意設置，也就是 `_metainfo`。

### 4. 生長式的開發模式（以後想走的一條路）

- 還可以以此延伸出另一套開發模式：從單一資料夾開始，逐步長出子資料夾，類似生長型神經網路那樣。
- 這塊是我以後的一條想走的路，目前暫時不多說。
- 總之，這是後續很多東西的基礎。

### 5. aos-loop／daemon：應該是界面形式

- 這塊其實有點走歪了，應該是要用界面形式的。
- 也就是：任何 Linux proc，只要你能提供這些可存取的檔案佈局，如 ctl/status 等，那你就是 aos proc。
- 不管你在硬碟、/tmp、FUSE 都可以，哪怕是網路上也行。
- 這就是單純的 Plan 9 思想。硬要說有啥不同的話，就是我們主打 JSON，串接先前的概念。

前面這些是所謂的基礎架構。

## 二、aos agent

- 這不必多說，就是 fsm，一個簡單的東西。
- 其核心可以想成是一個 source code，也就是一坨定義好的資料夾；
  - 然後指定他要被實例化到哪（stack），
  - 指定其第一個可訪問的外部記憶體位置（workspace），
  - 然後讓他成爲 aos proc，讓他去跑。
- 之所以這樣設計：
  - 一方面是爲了承接先前的架構；
  - 另一方面也是讓這個 agent 回歸原始本質，輕量化；
  - 同時也讓 agent 好修改自身。
- 當然，這會有些缺點，這個之後再說。

## 三、aos kernel（重頭戲）

- 假設以後有上千個 agent 在跑，他們需要爭搶有限的資源：從基礎的 cpu/mem，到權限/優先級、少量的 LLM 端點等。
- 以往就是由人類去思考演算法。但那是舊時代——他們對於哪怕是幾毫秒的延遲都要計較的時代。
- 新時代，agent 可以粗略地做排程和資源分配，所以 agent 就可以自己進行／設計這些。
- 所以 aos 提供了一個很酷的東西：允許自行設計 kernel，從資源到排程，並且允許 kernel 嵌套堆疊。
- kernel 的本質是爲了更好更方便的使用硬體，這就是 Linux 等舊時代的 kernel 所做的。
- 而 aos kernel 則將 Linux 視作底層硬體，並將各種抽象的東西視作間接硬體，去管理／排程各種五花八門的東西：從 token 用量到人類可理解性，再到更專業更細分的程式碼耦合度等。
- 有了 agent 的幫助，是能做到的。而 aos 就是提供這樣一個框架。
