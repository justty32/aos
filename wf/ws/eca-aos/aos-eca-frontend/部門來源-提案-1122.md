# 全景頁的部門從哪裡來：提案

> **11-22 已裁**：使用者「我人還在外面玩，總之先按推薦做」（eca-aos 轉來）→ 1＝乙現在做、丙以後接；2＝a；3＝a。乙已由線 `aos-eca-frontend-1122-parents-b` 施工。

## 結論先講

1. 今天全景頁認上層是**五種線索輪流猜**；其中三種（設定檔、名字前綴、比對規則）就是使用者嫌醜的那套，**今天就能拿掉**，不用等公司體制定案。
2. 真正費工的不是「拿掉」，是「多一台 daemon 就看不見」：全景頁只讀一張 daemon 表。乙案（一個部門一台子 daemon）成立的話，子 daemon 在頁上只會是機房裡的一格，裡面的人全看不到。
3. **不建議拿 `wf/ws/` 當部門來源**：它是 repo 工作流的規矩、不是 aos 的結構，全景頁（proto8 的選配外掛）讀它等於把產品綁在這個 repo 上。
4. 推薦：**乙做法（只信官方紀錄）現在做，丙做法（照 daemon 樹）等乙案定了再接上**。這是推薦，由使用者定。

## 今天怎麼認（`proto8/frontend/bin/aos-frontend`）

- 只讀一張表：`table_rows()`（678 行）跑 `aos-agent ctl ls --json`，也就是 `$AOS_DAEMON` 那一台。
- 每一隻依序找上層（`parents()`，377～419 行），找到就停：
  1. `aide`：隊長寫在全景頁自己家裡的 `teams/<隊>/aide.json`，小助手掛在隊長下。
  2. `config`：`~/.aos/view/config.json` 的 `parents` 手寫對照。
  3. `subagent`：誰的 subagent 紀錄裡有它（daemon 自己的資料）。
  4. `prefix`：名字是別人名字加 `-…`，就當它的下屬。
  5. `rule`：`parent_rules` 萬用字元；`init` 預設寫進 `["ok-*","repo-aos"]`、`["xiaosi","repo-aos"]`（203 行），`repo-aos` 是舊頂層的名字。
- 網頁那邊（`ui/v2/src/model/tree.ts` 9～11 行）：**有下屬就是部門**；不是 agent 的根都丟進「機房」。
- 順帶看到的同類寫死：「下令」的預設收件人寫死 `repo-aos`（`ORDER_KINDS`，約 2014 行）；`VIEW_TOOLS` 寫死 `~/aos-home/ws/tools`（61 行）。

## 三種做法

### 甲：照 `wf/ws/` 的資料夾樹讀

`wf/ws/eca-aos/aos-eca-frontend/` ＝ aos-eca-frontend 掛在 eca-aos 底下。

- 要改：全景頁要知道 repo 在哪（新設定或往上找），掃 `wf/ws/` 的資料夾名對到表上的名字。
- 能拿掉：設定檔、前綴、比對規則三種。
- 會出的問題：
  - **層次錯位**：proto8 是產品，`wf/` 是這個 repo 的工作流層；`wf/ws/README.md` 自己說「現在只是規矩，不是牆」，資料夾是 agent 自己 `mkdir` 的。等於把一份手寫設定檔換成另一份手寫資料夾樹，使用者嫌的「靠手寫的東西猜」沒變。
  - 對不上實況：agent 收掉了夾還在；sol 工人、小助手、kernel 沒有地盤，照樣要另一套規則。
  - 別的樹、別台機器沒有 `wf/ws/` 就整個失效。
  - 多台 daemon 以後名字可能重複，資料夾名對不到是哪一台的。
- 代價：小（半天），但只是換一種猜法。

### 乙：只信官方紀錄（今天就能做，不等公司體制）

上層只看 daemon 自己記的 subagent 紀錄；子 daemon（若有）當成一個容器。

- 要改：`parents()` 只留 `subagent`（和要不要留 `aide` 另議，見題 3）；`init` 不再寫預設規則；`ORDER_KINDS` 不寫死 `repo-aos`；API.md 的 `parent_by` 值變少；測試裡用 `parents` 設定的那段（`tests/demo_v2.py:182`）改成真的 subagent 關係。
- 能拿掉：`config.parents`、`parent_rules`、名字前綴、迴圈切斷那段大半也用不到（subagent 紀錄本身不太會成環）。
- 會出的問題：
  - **不是用 `subagent` 掛的人變成孤兒**：人用 `aos-agent ctl add` 掛的、別的程式起的，頁上會平鋪在最上層。今天 `ok-*`、`xiaosi` 那兩條規則就是為這種人補的；搬家後活樹是 eca-aos 加三個 subagent，目前不受影響。
  - 上層停掉或被拆，subagent 紀錄跟著沒了，下屬瞬間變成最上層（今天的猜法反而會照名字留住）。
- 代價：小。動 `aos-frontend` 一個函式加幾處寫死，網頁端不用動。

### 丙：照 daemon 樹讀（等乙案成立）

部門＝一台子 daemon；部門內的上下級照乙做法的 subagent 紀錄。

- 要改（這才是大件）：
  - 往下讀：表上哪一列是子 daemon（要定判準，例如那列的 stack 裡有 `procs_state.json`），就對它再跑一次 `aos-agent --daemon <那列的 stack> ctl ls`，一路往下。
  - **名字不再唯一**：每台 daemon 一張表，兩個部門可以都有 `sol-1`。節點的 id 要改成帶路徑（`部門/名`），牽動 API 的 `?name=`、`state/activity.json`、`teams/<隊>`、say 紀錄、寄信紀錄、中轉信的寄件人，網頁端每個用 id 的地方都要跟。
  - 對人說話、寄信、看狀態，每個呼叫都要帶 `--daemon`。
  - 網頁端「部門」的意思從「有下屬」換成「是一台 daemon」（或兩種並存）。
- 能拿掉：同乙做法，外加網頁端「有下屬就是部門」的推論。
- 會出的問題：
  - 公司體制 02 寫的乙案最大缺口：**部長住哪台**。部長在上一層、帶的人在部門 daemon 裡，部長就不在自己部門的格子裡；頁上要怎麼畫要等那題答了才知道。
  - 部門 daemon 停著時讀不到它的表：頁上要顯示「這個部門停了」而不是「這個部門沒人」。
  - 層數一多，每輪要跑的 `ctl ls`／`ctl state` 變多（今天每隻 agent 每輪就跑一次 `ctl state`），20 秒一輪可能不夠。
- 代價：大（幾天），而且要等公司體制第 2、3 題的答案。

## 推薦

**先做乙，丙等乙案定了再接。** 乙今天就把使用者嫌的三種猜法拿掉，改動小、只動一個函式；丙需要的「往下讀子 daemon」「id 帶路徑」跟乙不衝突，到時候在乙的基礎上加。甲不推薦。

## 要使用者選的題

1. **走哪種**：甲／乙／丙，或「乙現在做、丙以後接」（推薦）。
2. **不是用 `subagent` 掛的 agent 放哪**：a. 平鋪在最上層（推薦，誠實反映沒人帶它）；b. 跟非 agent 的 proc 一起放機房；c. 保留一條「手寫上層」的退路（就是又一份設定檔）。
3. **小助手的 `aide.json` 那條留不留**：它是隊長自己宣告的、不是猜的，但存在全景頁自己的家裡、不是 daemon 的紀錄。a. 先留著，等中轉信箱那套重新設計時一起看（推薦）；b. 一起拿掉，小助手也要用 `subagent` 掛。
