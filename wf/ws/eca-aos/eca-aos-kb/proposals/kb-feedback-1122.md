# 題 1：頁太密

實例：
- `aos/body.md` 的 Hooks 一條（第 18 行）：一條裡講了五件事——fsm 的 hook 看得到什麼、eca 看不到什麼、要擋 CLI 工具時去哪看、fsm 什麼時候檢查 on_clock、eca 什麼時候檢查 on_clock。
- `aos/me/self_hook.md` 第 26 行（brain_failed）：一條講了四種 body 的錯誤欄位，括號裡又套括號。

改法：

- **1a 每頁開頭三到五行重點，內文不動**
  - 好處：改得最少；讀的人掃完重點，多半就知道要不要往下讀。
  - 代價：內文照舊那麼密；重點和內文講同一件事，以後改內文要記得同步改重點。
  - 要改：先做最常讀的 5 頁（_description.md 已經有，所以是 body、me、packs、mailbox、cli/eca），之後碰到哪頁再補哪頁。
- **1b 一條只講一件事：長條拆成小標題加短行**（示範稿就是這種）
  - 好處：真的變好讀；一行一件事，以後要改也只動那一行。
  - 代價：頁會變長一點（示範稿 4,189 → 4,645 字，多約 10%，其中約 200 字是示範稿開頭的說明）；要重寫的是長條，改的時候容易改錯意思，每頁都要對著原文逐條核對。
  - 要改：超過 4 KB 的 29 頁；照「邊用邊建」可以只改用到的頁。
- **1c 1a 加 1b，只在用到某頁時才改那一頁**
  - 好處：工作量跟著實際用量走，不會一次改一大批。
  - 代價：有一段時間，新寫法的頁和舊寫法的頁會混在一起。

推薦：**1c**。理由：使用者已經定了邊用邊建，1a 單做治不了「讀兩遍」的問題。

# 題 2：fsm 和 eca 交錯寫

實例：
- `aos/body.md` 幾乎每一條都是「agent-fsm: …; eca: …」。
- `aos/me/self_hook.md` 的事件清單，每個事件都附一段「On an eca …」。

改法：

- **2a 同一條裡固定順序、分行寫：先 eca 一行、再 agent-fsm 一行、兩者都適用的寫在最後**（示範稿就是這種）
  - 好處：不用搬內容；eca 讀第一行就夠，fsm 跳過一行就好；錨點不會斷。
  - 代價：eca 還是看得到 fsm 的那些行，只是比較好跳過。
  - 要改：21 頁，可以跟 1b 一起改。
- **2b 一頁分成兩節：「# eca」與「# agent-fsm」**
  - 好處：只讀自己那一節。
  - 代價：兩邊都適用的事實要寫兩次，或另開一節；標題換了，指到舊標題的連結要跟著改（例如 `aos/body.md#/System text, history` 有 4 處連過去）。
  - 要改：21 頁，再加上改連結。
- **2c 另寫一頁「eca 讀法」：eca 該讀哪幾頁、哪幾節，以及哪些可以跳過**
  - 好處：只要新寫一頁，原有的頁一頁都不用動；可以從入口頁連過去。
  - 代價：原本的頁一樣交錯；這頁得跟著其他頁的內容更新，不然會跟其他頁對不上。
  - 要改：新寫 1 頁，入口頁加 1 行。

推薦：**2c 先做，2a 跟著 1c 用到哪頁改哪頁**。理由：2c 成本最低、馬上有用；2b 動到錨點和連結，代價最大。

# 題 3：排錯內容少

實例（感想裡提到、我查過知識庫確實沒有的）：
- 前端讀失敗：`frontend/bin/aos-frontend` 的 `_collect` 在拿不到 daemon 表時，只丟出「aos-agent ctl ls --json failed」（`run_json` 把子程式的 stderr 丟掉了）。知識庫 `aos/` 裡沒有任何一頁講前端。
- eca 的 Read／Glob／Grep 讀不到工作區以外的檔：感想說要 grep 原始碼才查得到。我在 `templates/docs/01-eca-claude.md` 和知識庫裡都**沒找到**寫明這件事的句子，所以這是**待查證**的事實，查證前不寫進知識庫。
- 已經寫了、但散在各頁的：`ClockMissing` 出現在 5 頁。

改法：

- **3a 新寫一頁「常見故障」：一條一個症狀，寫症狀 → 原因 → 怎麼查**
  - 好處：遇到問題時有一個地方可以找。
  - 代價：每一條都要先在真的環境裡重現或查證才能寫；不在活 daemon 上下指令的話，有些條目只能交給有權限的人去查證。
  - 要改：新寫 1 頁，入口頁或 errors.md 加 1 行；先放已經查證過的 2～3 條，之後碰到一個就補一條。
- **3b 不另開頁，故障寫在各自那頁的最後**（例如 clock.md 寫 ClockMissing、cli/eca.md 寫讀不到工作區）
  - 好處：跟相關說明放在一起。
  - 代價：要先猜到該去哪一頁找，這正是感想裡抱怨的情況。
- **3c 3a 加一條規矩：誰查出一個故障，就交給 eca-aos-kb 補一條**
  - 好處：符合邊用邊建；頁的內容來自真的遇到的故障。
  - 代價：要各線願意回報，可以在任務書或規矩卡加一句。（規矩卡在 `wf/`，不在我能改的範圍，要 eca-aos 去改。）

推薦：**3c**。

# 題 4：系統文字要先 echo $AOS_HOME

實例：`templates/eca-claude/system.txt` 第 3 行寫「File tools do not expand $AOS_HOME, so get it once with the shell (echo $AOS_HOME)」。

改法（都不在知識庫裡，是範本或程式的事，要轉給 eca-aos-templates）：

- **4a 範本在定義編譯時（或 aos-eca-turn 每輪開始時）把 $AOS_HOME 換成絕對路徑，寫進系統文字**
  - 好處：第一步就拿到路徑。
  - 代價：要改程式；換台或搬樹之後要重新編譯。
- **4b 系統文字改成叫 agent 用 `index_view` 看知識庫**（要 aos 工具自己展開 `$AOS_HOME`；我在 `py/tools/base/index_view/_entry` 和 `py/aos/tool_io.py` 裡都沒找到展開它的程式碼，所以多半要改程式）
  - 好處：不用 shell。
  - 代價：要改 aos 工具讀路徑的方式，影響所有用路徑的工具。
- **4c 不改**：一行 echo 的成本很小。

推薦：**4c**（先不改）。4a 和 4b 都要改程式，代價我判斷不了；真的要改，交給 eca-aos-templates 評估。
