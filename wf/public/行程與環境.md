# wf/public/行程與環境 — 收行程只收自己的、先清 AOS_*、起樹前先 source env.sh、數行程與程序群組的坑

← [wf/public](README.md)｜規矩在 [06](../workflows/dispatch/aos-teams/06-公司WSL活樹與任務書硬規則.md) 第 2、4 條；`pgrep -af aos-daemon` 多列幾行見 [pitfalls](pitfalls.md#pgrep--af-aos-daemon-會多列幾行不一定是多了-daemon)；zsh 不分詞見 [pitfalls「隊長的 shell」](pitfalls.md#隊長的-shellbash-工具)；哪些改動活樹當下就吃到見 [活樹旁邊](活樹旁邊.md)

## 收行程不按名字、不按命令列字串：只收自己的 stack 或自己記下的 pid

`pkill`、`killall`、`kill $(pgrep …)` 都不准：自己暫存夾的測試 daemon 跟活樹根 daemon 的命令列可能一模一樣（例 `aos-daemon --enable-logs daemon.json`），`pkill -INT -f` 收自己的會兩台一起停（活樹停過約 4 分 20 秒，使用者自己起回來）。

- 只准 `aos-daemon-ctl -d <自己暫存樹 stack 的絕對路徑> shutdown`（下之前 echo 路徑確認），或 kill 自己起的時候記下、且 `readlink /proc/<pid>/cwd` 核對在自己暫存夾裡的 pid；tmux 只動自己用 `-S <暫存夾內 socket>` 起的。
- 收尾貼 `pgrep -u "$USER" -af aos-daemon`，確認活樹的 daemon 還在。
- repo 裡的測試也不留 `pkill -f`（`py/tests/apps/agent/test_rm_keep.py` 原本那一行已改成收自己記的 pid）。

## 對 aos-exec 那組送 SIGINT，收不到它底下的 aos-daemon

aos-daemon 自己另開一組，實測收尾只對 aos-exec 那組送 SIGINT，留下過 3 支 llm kernel daemon 跑 4.5 小時。收尾要對 **daemon 的 pid**（讀它 stack 的 `state.json` 或啟動時記下）送 SIGINT，收完用 `pgrep -af aos-` 對自己的 /tmp 夾確認沒殘留。

## agent 的 Bash 帶著活樹的 `AOS_*`：跑測試或 aos 指令前先清，清的寫法在 zsh 裡會靜靜失效

頂層是樹裡的 agent，子 agent 全部繼承它的 `AOS_STACK`／`AOS_DAEMON`／`AOS_HOME`／`AOS_WS`。不清掉就跑測試或 aos 指令，檔會寫進活的 stack、信會寄到活樹（`aos-agent ctl add` 帶著頂層的 `AOS_STACK`，回信箱就開在頂層那格的 `daemon_reply/`；也有線把 `daemon_reply/`、`interfaces.json`、`observed.jsonl` 留在頂層的 stack 裡）。

- 起任何 aos 行程、跑任何測試前先清；跑完 `ls` 活樹裡頂層那一格 stack，對照開工前的清單。
- Bash 工具的殼是 zsh：`env -u $VARS` 不會把變數拆成多個字，等於沒清；在 zsh 裡 `source` 一份 bash 寫法的環境檔，清的那段不生效。
- 清環境一律寫成一支 bash 腳本、用 `bash 腳本 指令…` 跑，腳本開頭「不是 bash 就拒絕」、清完「還有殘留就拒絕」（範例在 [testing](../workflows/testing.md#不碰跑著的樹)）。

## 在 agent 的 shell 裡起活樹：先在 bash 裡 `source env.sh` 再 `aos-exec root`，沒人替你擋

殼裡還帶著 `AOS_STACK` 就起樹，root 會把那一格當成 root stack：真的領班與底下的 agent 掛在錯的 root 底下、看到錯的鐘（起樹前 source 的環境檔只清了 `AOS_DAEMON`／`AOS_KERNEL`／`AOS_CLOCK` 時發生過，約 35 秒後自己停掉、清乾淨重起）。

- 起樹照[每台設定說明書「起樹、停樹」](../workflows/dev-env/03-換機.md#起樹停樹)：11-23 起公司那台只起 `~/aos-home` 的根一行（`cd ~/aos-home && env -u AOS_DAEMON -u AOS_STACK -u AOS_CLOCK -u AOS_KERNEL -u AOS_LLM_KERNEL aos-exec --stack .stack root`），llm kernel（列 `llm`）與 repo 那棵（列 `repo-aos`，子 daemon，stack `~/repo/aos/.stack`）跟著起；起完 `aos-daemon-ctl -d ~/aos-home/.stack ls` 四列 running、`aos-daemon-ctl -d ~/repo/aos/.stack ls` 最後一行是 `supervisor …/aos-home/.stack/: running`。家機還沒改（llm kernel 自己一台 `~/aos-home/.llm-stack`、repo 那棵單獨起，見說明書「家機照做」）。在 agent 的殼裡（帶著 `AOS_STACK`，殼設定檔那段會跳過）要先在 bash 裡 `source $AOS_HOME/env.sh` 清掉那隻 agent 的 `AOS_*`，再 export `AOS_DAEMON`、`AOS_LLM_KERNEL`，才下起樹那一行。
- 公司那台 11-23 起樹之前的舊做法（留底）：`cd ~/aos-home && source env.sh && aos-exec root`（用 bash）：`env.sh`（正本 `$AOS_HOME/env.sh`，樹裡的 `env.sh` 轉去它）會清掉 `AOS_HOME` 以外全部的 `AOS_*`；起完看根 daemon 的 cwd 與 stack 是不是 `~/aos-home` 那一格。
- 跳過 `source env.sh` 直接打 `aos-exec root` 不會被擋（巢狀呼叫本來就帶 `AOS_STACK`，aos-exec 分不出是在起新樹）。原本擋這件事的 `aos-tree-start` 使用者 11-18 裁掉（「aos-tree-start這東西就不用了吧，刪掉。」）。

## 數「有幾份某程式在跑」別用 `pgrep -fc <名>`

它會把命令列裡含那個名字的 shell、別隊的等待迴圈、把它當參數的程序都算進去，數字會多好幾倍。改用 `ps -eo args | grep -c '^/usr/bin/python3 \(-B \)\?<那支程式路徑>'` 這種「開頭就是那支程式」的數法（有帶 `-B` 這類旗標的也要算進去）；等待迴圈的比對字串別跟迴圈自己的命令列重疊。

## 碰 `killpg`、程序群組收尾的改動，不要在公司 WSL 上跑

對程序群組反覆送 SIGKILL 直到群組變空這類收尾改動，在公司 WSL 上跑會讓整個 WSL 掛掉重開、`/tmp` 被清空。要做就在可丟棄的環境，並先檢查 pgid 不是 0、1 或測試程序自己的群組。

## Monitor 腳本 `nohup` 起的子程序會被連坐：要用 `setsid`

由 Monitor 腳本 `nohup` 起的子程序，Monitor 到期時會一起被殺；要活得比 Monitor 久就用 `setsid` 起。
