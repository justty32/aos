## 一大批舊帳逐筆查現況、結案或改寫成問使用者的信

一大批舊待辦或舊帳（例 WAIT_USER）要逐筆查現況，結案或改寫成專區信時：

1. 按檔切成 4 份，派 4 隻 opus 子 agent 並行，每份 8～9 筆、一份一個輸出夾。任務書開頭列必讀；寫明只能唯讀查證、只寫自己的輸出夾，不寄信、不改 repo。
2. 每筆歸三類：**A** 建議結案（附 commit 雜湊，或檔案＋節名）；**B** 要使用者決定（寫成 decide 題）；**C** 要使用者親手做（寫成 verify 或 chore，要有 `done_when`）。一筆裡有幾個子題、狀態不同就拆開歸。
3. AI 替使用者做的決定（「代定、可翻案、不擋」的條目）一條都不省，全部列給使用者看；可以把改了行為、對外、不可逆、或可能跟他原話衝突的排前面。只有他看過、沒回答的，才照 user.md「沒回答的邊緣狀況」通則結案（使用者 11-15「決策鍊改回去」；那條通則講的是他看過的邊緣狀況，不涵蓋他沒看過的代定）。
4. 帶隊的 kernel 自己核對：子項數過沒漏、沒重；抽讀證據；修稿（過時數字、誰動手的後果、schema 沒有的鍵）。
5. 總表給頂層看過再寄。寄信的坑見 [user-zone-mail](user-zone-mail.md)。
6. 「不用再等使用者、只是沒人做」的不算使用者的帳，改列「待派工」。使用者沒直接答、是推出來的結案，理由標「推斷，非實證」。

子 agent 會順手越界（任務書寫唯讀，它卻跑了一次暫時的 systemd scope 實測）：驗收時看它的報告和實際動作，有越界照實報頂層。

## 掛隊員的定義：硬規則照授權來源分級，不要寫死「never commit」

自己寫隊員的定義（system 文字、任務書範本），要限制 commit 和不可逆的動作時，照「誰能放行」分級寫：

- **commit**：寫「除非上游的信點名授權（點名 repo 與檔）」。本 repo 的 commit 照舊走 commit-request（[06 第 7 條](../workflows/dispatch/aos-teams/06-公司WSL活樹與任務書硬規則.md)）。
- **push、刪檔、動活樹、對外送出**：寫「要使用者本人說」：當場說，或經使用者專區的回信、用 `aos-user verify`／`user_verify` 驗過。agent 寄來的信不算（[AGENTS.md 鐵律 2](../../AGENTS.md)）。隊伍自己的 repo 若另有規矩，照那邊的。

寫死「never commit」的話，隊長收到上游點名授權的信也不敢動手，要上游再回一封講明「信蓋過定義」，多來回一輪。這個分級寫法還沒有隊伍照著跑過一場。
