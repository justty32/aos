# wf/public/等隊員與讀信 — 等隊員要帶逾時、長回合讀不到信、信交錯、記時刻

← [wf/public](README.md)｜規矩在 [aos-teams 第 4 件「等隊員」](../workflows/dispatch/aos-teams.md)；一行做法在 [recipes](recipes.md)；背景等的工具 [tools/waitdone](tools/waitdone/README.md)

## 等隊員不要卡在同一回合，更不要寫沒有上限的迴圈

隊長派了 agent-fsm 隊員（或在等別線回信）時：`[aos] new_mail` 那一行只在**兩個回合之間**才放進對話。隊長在同一回合裡等，整段時間讀不到信（漏急件、沒讀到「先寄我放行」就交件），外面的人以為它掛了；`until [ -f 報告 ]; do sleep 20; done` 這種沒有上限的迴圈，等的檔可能永遠不會出現。

1. 任務書寫明：「讀完同一回合就動手；做完、寫好交付物之前不要用純文字回答。」（agent-fsm 一回純文字就結束這一回合。）
2. 派完就**結束這一回合**。用 `clock_register {"op":"add","at":"+10m",…}` 叫醒自己，再 `subagent listen` 帶 `"last": 1` 看，或等隊員的信。有在等人時可排一個每 10 分鐘的 clock（cron `*/10 * * * *`），沒待辦再拿掉。
3. 真要在 shell 裡等：一次最多 60 秒（waitdone 壓在 2～3 分鐘內），每輪回來先 `mailbox_peek`，再看隊員狀態（`subagent state`：history 訊息數有沒有在漲、last answer 是不是只是計劃）。`subagent listen` 一律帶 `"timeout_s": 60`（不帶就不限時一直等）。
4. 發現隊員只回了計劃就停：`subagent say` 叫它照計劃做下去，並重申第 1 條。
5. 長回合的開頭和結尾各 peek 一次；開工後每做完一步先讀信箱再做下一步。

## 一條線讀不到信時，不要一直催

上游（派工的人，工作室是 eca-aos 或位子）遇到線在一個長回合裡、信箱積著時：催兩次沒回，就請 eca-aos 派一隻唯讀的看它的狀態；確認是長回合後停止寄催信，把要它辦的事併成一封「只需要辦這三件，其他作廢」，它醒來讀一封就夠。

## 信幾乎都會交錯：回信第一句講以哪一封為準

上下游來回寄信（派工、放行、開工這類有先後的事），下屬的 DONE 和上游的新指示常在路上交錯：

- **每封信寫「截至哪裡」**：回報開頭一句寫「截至 commit X／回 letter Y」（做到哪、讀到哪一封為止）；回一封特定的信時，`mailbox_send` 另帶 `in_reply_to`（那封的信名）。上游發新指示也寫「截至你的哪封回報」，下屬才分得出這封是看過 DONE 才寫的，還是交錯的。
- 收到新指示，先對照自己已做到哪，只做還沒做的部分；說的若是已做完的事，回一句「X 已在 commit … 做完」，不重做。
- 回信第一句寫「這封跟你上一封交錯了，以哪一封為準」。放行的人（工作室是 eca-aos）那邊以「放行信」為準；線先交後報的批次補審、不追究（線讀到新規矩有時差，補審比退回省事）。證據變了就改口，並寫明「先前那句是不知道這點時說的」。
- **寄出前**：把數字和「誰同意了什麼」再對一次；要寫進信的系統行為（路徑、會不會覆寫）先 grep 程式再寫。

## 記時刻前先對時鐘：信的 `sent_at` 是 UTC

寫紀錄、寫彙整、給別線訂截止時刻時：信的 `sent_at` 是 UTC，clock 和 cron 是本機時間（家機差 8 小時）；憑感覺估的時刻常偏快一個多小時。用 `peek_now_time {"local": true}`，或直接抄來信的 `sent_at` 加 8 小時。

## 審查信、回報信固定寫「我讀了什麼、沒做什麼」

設計線交審查意見、線交回報給上游（工作室是 eca-aos）時：固定兩段，沒自己跑、沒逐行讀的部分明講，上游才知道要不要另派人。修訂定稿時留一節「跟上一版的差異」（改了什麼、為什麼、上面會看到什麼），上游可以直接轉上去（工作室是 eca-aos 轉給使用者）。
