## 派小修前先查 main 有沒有人做了

- **適用**：照 advices 或待辦清單派小修；暫存樹是從舊 main 切出來的。
- **坑**：ok-misc 的 T24、T25、T26 帶 sol 做完、測完，才發現別線已先進 main（246d4aa49、2ef627f1b、96c7cda52），白費約三隻 sol 半天的額度。
- **做法**：開工前 `git log --oneline <基底>..HEAD -- <要動的檔>`，並在 wf/advices 那條先標「已排入（線名）」（頂層 11-14 規矩）。交件前再核一次。
- **出處**：`wf/temp/ok-misc/wrapup-1114/經驗.md` 第 2 則

## 先問介面、先讀程式裡已寫的，再動手

- **適用**：要接別線的欄位或函式；要加 system 文字、旗標；要在信裡說系統怎麼運作。
- **做法**：
  - 寄信問擁有線欄位定義再動手：ok-kmsg 問 ok-astra，回信說「after_verdict 那條路現在就能用、wait.py 不用改」，範圍當場縮成改一支函式。
  - 先讀相關程式的 docstring：`lib/agent/cli_cfg.py:155` 早就寫了「`--resume` 時新加的 append prompt 送不到」，ok-wake 花一輪實測才知道（細節見 [model-notes](model-notes.md)）。
  - 新判斷條件上線前，拿一份真資料對一次（真的表上一列、真的 `state.json` 的鍵名）；要看活樹的先請部長點名（[活樹旁邊](活樹旁邊.md)）。
- **驗過**：ok-kmsg、ok-wake 11-14。
- **出處**：`wf/temp/{ok-kmsg,ok-wake}/wrapup-1114/經驗.md`

## 查證別人報的 bug：先看對方用的是哪一版

- **適用**：別隊報「aos 的某行為壞了」。
- **做法**：先確認對方跑的是哪一版程式（活樹換樹前是舊 lib）：把活樹的檔和 repo 的檔 diff 一下（看活樹要點名）。「逾時就刪名單」這類推測，順著錯誤處理一路追：`must()` 遇錯就 die，根本走不到刪名單那一步（`lib/agent/agents_cmd.py` 110-114 行）。
- **驗過**：ok-kf 11-14，查 skyrim-agent 報的題。
- **出處**：`wf/temp/ok-kf/wrapup-1114/經驗.md`「查證別人的 bug」

## 會蓋掉使用者舊裁定的改動：先找到他當時看到的原文

- **適用**：施工中發現某個改動會讓使用者先前的一條裁定不成立。
- **做法**：不憑「這是必然後果」過關。查他裁的時候眼前的題目或文件有沒有寫到這個後果；專區找不到，再查 `proto8/user-advice/` 當天的原話（他也會在終端裁）。找不到就寄一題 decide，選項照實寫「這會蓋掉哪一天的哪一條」（寄法見 [user-zone-mail](user-zone-mail.md)）。
- **驗過**：head-core 11-14 兩次：P-13（頂層先只翻專區說沒有，decide 寄出後才發現他在終端選過，多問一次）；aos-sandbox scope 第 8 點（翻的是 11-12 晚的裁定，使用者答 strict）。
- **出處**：`wf/temp/head-core/wrapup-1114/經驗.md`（notes.md 14:11～14:34）

## 算式先寫小模擬、錯誤碼先實測，不信推論也不信審稿

- **適用**：計劃裡有配額、分配、放行這類多層算式；或設計靠系統呼叫的錯誤碼分辨情形。
- **做法**：
  - 算式：寫一支幾十行的 Python，把審查者提的反例和計劃的驗收劇本都當測資，全部對才寫進定稿。
  - 錯誤碼：寫十行的小實驗在本機跑。例：`renameat2` 帶 NOREPLACE，來源不在、目的地已在時回 ENOENT，不是 EEXIST（駁了 Argon 的一點）。
- **驗過**：ok-llmk2 11-14（Argon 審出兩個多層漏洞和 `self_reserve` 漏扣，改式後 `~/code/llmk2-1114/formula_check.py`（11-15 已刪） 四個劇本全對；`llmk2-1114/05-採納表.md:9-10`）；ok-sec E12（`~/code/sec-1114/e12-rn/`（11-15 已刪）；`sec-1114/09-Q10採納表.md`）。
- **出處**：`wf/temp/{ok-llmk2,ok-sec}/wrapup-1114/經驗.md`；`proto8/thinking/2026-11/14/llmk2-1114/03-計劃.md` §3.1

## 「UX 不好」先量再設計

- **適用**：改版面、改頁面這類憑感覺的題。
- **做法**：把「設計 → 量 → 再設計」做成固定迴圈，比一次寫完再驗收省重工。任務書明寫量測寬度（每輪設計會改寬）。使用者從頁面寄來的一句話是最快的需求來源：收到就回一句，把要他選的寫成 decide 信放專區。
- **驗過**：ok-view 11-14：astra 量到的數字推翻了第一稿兩個核心假設（決定單中位數 945 px 高，稿以為兩題 480；名牌可寫字只有 76 px）；02d → astra-r2 → 02e → astra-r3。
- **出處**：`wf/temp/ok-view/wrapup-1114/經驗.md` 第 4、5 則

## 一條線只做設計與審查、施工交給另一條線

- **適用**：設計線（只審不寫碼）配施工線。
- **做法**：
  - 欄位名在兩邊對齊前都不 commit；施工方先把每個名字定義成一處常數（之後 `reason` 改 `cause` 只動三行）；設計方回「初步傾向」要快，正式意見等 Argon。
  - 用字規則一次定下來寄給相關線（`reason` 是句子、`cause` 是代號），別線會自己跟。
  - 設計線審 diff 會漏「換檔那一瞬間」和「真的列長什麼樣」，這兩樣另有人看（[審查與實測](審查與實測.md)）。
- **驗過**：ok-devt 配 ok-limits 11-14（bcaf76823、83fd2fd39）；ok-board 看到用字規則後把 `gone_why` 改成 `gone_cause`。
- **出處**：`wf/temp/ok-devt/wrapup-1114/經驗.md`；`proto8/thinking/2026-11/14/ok-devt-1114.md`

## 原型交給 fable 帶隊、只在暫存樹做；新檔先上、接線最後

- **適用**：要快速拿到「細圖＋過測試的原型」，又不想動 repo。
- **做法**：每隊各自 `git archive` 複本＋自己的暫存 daemon，不碰 repo；隊長只收報告與裁定。進 repo 時新檔一批先上（零既有檔改動，好放行，下游立刻有真檔可讀），接到既有路徑的那一步放最後（06 第 5 條）。
- **驗過**：ok-board 11-14，兩隊 2.5 小時拿到批 2、3 兩份細圖與原型（`board-1114/07`）；批 0＋1 全新檔，ok-view 立刻有真 `board.json` 可讀。
- **出處**：`wf/temp/ok-board/wrapup-1114/經驗.md`

## 搬信進別的信箱要改寫 `reply_to`

- **適用**：程式或測試把一封信原樣 rename 到另一個信箱（例如轉給 kernel 的 requests 夾）。
- **坑**：aos-post 把 `reply_to` 存成相對寄達信箱的路徑；kernel 照自己的 requests 夾解讀（`lib/aos/kernel/letters.py:264`），回信會寄丟，add 等 30 秒後失敗。
- **做法**：搬之前把 `letter.json` 的 `reply_to` 改成絕對路徑。
- **驗過**：ok-limits 11-14（`test_kernel_that_does_not_answer_only_slows_the_add`）。
- **出處**：`wf/temp/ok-limits/wrapup-1114/經驗.md`
