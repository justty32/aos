# wf/public/設計與查證 — 動手前先查、先量、先問；設計線與施工線怎麼分

← [wf/public](README.md)｜正統規劃流程在 [07](../workflows/dispatch/aos-teams/07-預設流程與agent-fsm.md)；審查與實測見 [審查與實測](審查與實測.md)

## 派小修前先查 main 有沒有人做了

照 advices 或待辦清單派小修、暫存樹又是從舊 main 切出來的時候，常做完、測完才發現別線已先進 main，白費整隊的額度。開工前 `git log --oneline <基底>..HEAD -- <要動的檔>`，並在 wf/advices 那條先標「已排入（線名）」；交件前再核一次。

## 先問介面、先讀程式裡已寫的，再動手

要接別線的欄位或函式、要加 system 文字或旗標、要在信裡說系統怎麼運作時：

- 寄信問擁有線欄位定義再動手：常一問就知道現成的路能用，範圍當場縮小。
- 先讀相關程式的 docstring：行為限制常早就寫在那裡（例 `proto8/py/aos/agentlib/cli_cfg.py` 寫了 `--resume` 與 append prompt 的事，見 [model-notes](model-notes.md)），不必花一輪實測。
- 新判斷條件上線前，拿一份真資料對一次（真的表上一列、真的 `state.json` 的鍵名）；要看活樹的先請 eca-aos 點名（[活樹旁邊](活樹旁邊.md)）。

## 查證別人報的 bug：先看對方用的是哪一版

別隊報「aos 的某行為壞了」時：先確認對方跑的是哪一版程式（活樹可能還是舊的複本）：把活樹的檔和 repo 的檔 diff 一下（看活樹要點名）。「逾時就刪名單」這類推測，順著錯誤處理一路追：例 `proto8/py/aos/agentlib/agents_cmd.py` 的 `must()` 遇錯就 die，根本走不到刪名單那一步。

## 會蓋掉使用者舊裁定的改動：先找到他當時看到的原文

施工中發現某個改動會讓使用者先前的一條裁定不成立時，不憑「這是必然後果」過關：查他裁的時候眼前的題目或文件有沒有寫到這個後果；專區找不到，再查 `wf/user/advice/` 當天的原話（11-22 從 `proto8/thinking/user-advice/` 搬來）（他也會在終端裁，只翻專區會漏）。找不到就寄一題 decide，選項照實寫「這會蓋掉哪一天的哪一條」（寄法見 [user-zone-mail](user-zone-mail.md)）。

## 使用者一句備註有兩種讀法：照最小的做，把兩種讀法擺給他

不從一句備註推翻他先前親手選的裁定。例：11-13 的備註「kernel.json的next感覺有點畫蛇添足。」可以讀成只講問腦那包，也可以讀成連框架站的 `next` 一起拿掉（那是他 11-11 親手選的）；照小的做、把兩種讀法連同先前的裁定拿去問，他回「好啦，next也可以。」

向使用者轉述「來源沒有建議」「來源建議甲」之前，先打開來源核對那一題的原句（轉述錯過一次）。

## 算式先寫小模擬、錯誤碼先實測，不信推論也不信審稿

計劃裡有配額、分配、放行這類多層算式，或設計靠系統呼叫的錯誤碼分辨情形時：

- 算式：寫一支幾十行的 Python，把審查者提的反例和計劃的驗收劇本都當測資，全部對才寫進定稿。
- 錯誤碼：寫十行的小實驗在本機跑。例：`renameat2` 帶 NOREPLACE，來源不在、目的地已在時回 ENOENT，不是 EEXIST。

## 「UX 不好」先量再設計

改版面、改頁面這類憑感覺的題：把「設計 → 量 → 再設計」做成固定迴圈，比一次寫完再驗收省重工（量到的數字常推翻第一稿的核心假設）。任務書明寫量測寬度（每輪設計會改寬）。使用者從頁面寄來的一句話是最快的需求來源：收到就回一句，把要他選的寫成 decide 信放專區。

## 一條線只做設計與審查、施工交給另一條線

設計線（只審不寫碼）配施工線時：

- 欄位名在兩邊對齊前都不 commit；施工方先把每個名字定義成一處常數（之後改名只動幾行）；設計方回「初步傾向」要快，正式意見等 Argon。
- 用字規則一次定下來寄給相關線（例：`reason` 是句子、`cause` 是代號），別線會自己跟。
- 設計線審 diff 會漏「換檔那一瞬間」和「真的列長什麼樣」，這兩樣另有人看（[審查與實測](審查與實測.md)）。

## 原型交給 fable 帶隊、只在暫存樹做；新檔先上、接線最後

要快速拿到「細圖＋過測試的原型」又不想動 repo：每隊各自 `git archive` 複本＋自己的暫存 daemon，不碰 repo；隊長只收報告與裁定。進 repo 時新檔一批先上（零既有檔改動，好放行，下游立刻有真檔可讀），接到既有路徑的那一步放最後（06 第 5 條）。

## 搬信進別的信箱要改寫 `reply_to`

程式或測試把一封信原樣 rename 到另一個信箱（例如轉給 kernel 的 requests 夾）時：aos-post 把 `reply_to` 存成相對寄達信箱的路徑，kernel 照自己的 requests 夾解讀（`proto8/py/tools/aos/kernel/letters.py`），回信會寄丟、add 等 30 秒後失敗。搬之前把 `letter.json` 的 `reply_to` 改成絕對路徑。
