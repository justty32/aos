# wf/public/審查與實測 — 獨立審稿員怎麼問、哪些東西要拿真的來跑

← [wf/public](README.md)｜Argon 審的做法見 [model-notes](model-notes.md)；放行時看哪三樣見 [patch-and-commit「放行」](patch-and-commit.md)

共通的一點：**單元測試全綠、設計線說合定稿，都不等於對真的東西成立**。

## 另派一隻全新的審稿員：不給結論，只問「不該變的不變」

改到每隻 agent 都會走的路（掛 agent、清掃器、收行程），或知識庫、規矩檔這類「改後的句子要跟程式或原規矩相符」的批次、而交件方只逐字審了一部分時：

- 設計線審 diff 只看「合不合設計」。另派一個全新的審稿員，只給它 diff、規格、和一串「逐條答成立／不成立＋行號」的問題；明講只讀不跑、不碰活樹。
- 問題問邊界：呼叫端環境裡本來就有那個變數怎麼辦、路上有沒有多一次查表、**換檔中途新舊混用會不會壞**。
- 對文件批次：提示裡不給交件方的結論，要它先自己回程式找出處，再拿交件方的報告對行號；要求「沒查完的明講」。
- 一次只要幾分鐘，常找到交件人和設計線沒看到的東西（壞帳本沒測試、目標沒限範圍、換檔順序）。

## 讀 daemon 表的程式：至少一條測試用真 daemon 起出來的列

任何讀 daemon 表（`procs_state.json`，不是 `state.json`）、啟動單子的程式；設計裡要寫「值放在表上哪裡」「怎麼認某一類列」時：

- 讀碼推出來的列形狀常是錯的：以為 envs 在那一列的 `launch.exec.envs`，實際 `launch.exec` 只是指到小格檔的指標，envs 在小格的 `exec.json`／`loop.json`。測試用手捏的列全綠，對真的列一直回 null。
- 帶 envs 的 add 會被 daemon 包一層 aos-exec：表上 exec 欄變 null、`ctl set-def` 拒收、as_written.exec 不記、`--path-json` 的指示詞被改寫。「順手加一個環境變數」等於換掉整條啟動路（[定義與換定義](定義與換定義.md) 的 set-def 坑同源）。
- 照 argv[0] 的程式名認 llm kernel 列，在真表上認不到（exec 指向定義夾，`_entry` 是 `["aos-loop","loop.json"]`）。改認「stack 同時有 `endpoints.json` 和 `requests/`」，掛法怎麼變都認得到。
- **做法**：測試起一台暫存 aos-daemon（`interval_ms` 20），用真的 `ctl add` 掛上去，從 `procs_state.json` 讀列；要經 kernel 的用 `proto8/lib/agent/subagent/tests/kernel_fixture.py`。交件信附那一列的原樣輸出，沒附就退回。設計裡寫「一律寫進 envs」之前，先問施工的人「帶與不帶，掛出來的列逐欄一樣嗎」。
- 篩選條件也要拿真 daemon 跑：「只收有 mailbox/ 的」會漏掉剛起、還沒收過信的 agent。

## 接線前用便宜的真模型在暫存樹跑一輪

改了 eca 這類包 CLI 的程式（收信、中途餵信、起 `claude -p`），測試用的是假 CLI 時：假 CLI 全綠，真模型一跑就可能抓到吞信的問題（例：模型叫了背景任務先回一個 result，程式一看到 result 就關 stdin，之後的信寫不進去；細節見 [model-notes「claude -p 做到一半再交新話」](model-notes.md)）。

- 在暫存樹用 repo 的程式跑真的一輪，模型用 haiku 或 sonnet。每種情境一個 case（閒著、長 CPU、四次工具、背景、改三檔），中途寄一封信，記延遲並看 history。修了再跑一次。
- 只給它真的小工作（06 第 8 條）。

## 「開關關著逐位元不變」：拿改前的原檔當對照組

新功能有開關，要證明關著時行為跟改前完全一樣：把改之前的檔備份到 repo 外（後綴 `.orig`），用 `importlib.machinery.SourceFileLoader` 載入（`.orig` 普通 import 載不進來）；用 patch 換掉最底下那個起行程的函式，新舊版各在幾種設定下呼叫一次，比它們拿到的 argv、prompt、timeout，一樣才印 ALL SAME。每個 commit 都在乾淨複本上重跑。比「只比新碼的開與關兩條路」可靠。

## 守門程式：測試全綠不等於擋得住

寫或改 guard 這類「擋住不該做的事」的程式時：

- 先列一張表：每支工具怎麼解它的路徑參數（`#`、`~`、相對路徑、最後一節是不是符號連結），guard 照表去算。洞多半出在 guard 跟工具算出來的檔不一樣。
- 每補一個洞配一個**斷言「擋下」**的測試。舊測試可能把洞寫成正確行為，全綠也看不出來。
- 另派人專找繞過的路；找到的洞交還 guard 的主人修。上游說「根源在下層工具」時，先讀下層工具的檔頭註解：註解引了使用者的裁定就停下來，修在不違反裁定的那一層；先在暫存樹做最小重現再停手回報。
- 做「寫不成只 warning」這類測試：等必要的那次寫入回來後才把父夾 `chmod 0555`（包一層 launcher），不用 mock 被測程式（例 `proto8/templates/tests/agent-fsm/test_brain_wait_file.py`）。

## 讓隊員看網頁又不碰活樹：瀏覽器層唯讀守門

隊員要對著活樹的網頁量版面、截圖，但不能對活樹送出任何寫入時：node 24 內建 WebSocket 直接驅動 headless Chrome（不用 puppeteer），`Fetch.enable` 攔下所有對活樹埠的非 GET 請求（`READONLY=1` 則攔所有埠）；互動在自己的 demo 後端做。blocked 清單會印出來，可以當證據。看活樹的頁本身仍要任務書點名。
