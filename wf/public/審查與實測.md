## 另派一隻全新的審稿員：不給結論，只問「不該變的不變」

- **適用**：改到每隻 agent 都會走的路（掛 agent、清掃器、收行程）；或知識庫、規矩檔這類「改後的句子要跟程式或原規矩相符」的批次，而交件方只逐字審了一部分。
- **做法**：
  - 設計線審 diff 只看「合不合設計」。另派一個全新的審稿員，只給它 diff、規格、和一串「逐條答成立／不成立＋行號」的問題；明講只讀不跑、不碰活樹。
  - 問題問邊界：呼叫端環境裡本來就有那個變數怎麼辦、路上有沒有多一次查表、**換檔中途新舊混用會不會壞**。
  - 對文件批次：提示裡不給交件方的結論，要它先自己回程式找出處，再拿交件方的報告對行號；要求「沒查完的明講」。
- **驗過**：head-core 11-14 三次（清掃器＋aos-share、1a 權限腳本、add-parent），三次都找到交件人和設計線沒看到的東西：壞帳本沒測試、env_file 目標沒限範圍、換檔順序。每次約 2～4 分鐘、6～14 萬 token。head-front：ok-kb 三批、ok-astra 五批知識庫共查出 6 句不符（95bdc412f）；規矩檔改寫第一輪 6 處、第二輪 4 處（`wf/temp/head-front/review-q2.md`、`review-q2-v2.md`）。
- **出處**：`wf/temp/{head-core,head-front,ok-devt}/wrapup-1114/經驗.md`

## 讀 daemon 表的程式：至少一條測試用真 daemon 起出來的列

- **適用**：任何讀 daemon 表（`procs_state.json`，不是 `state.json`）、啟動單子的程式；設計裡要寫「值放在表上哪裡」「怎麼認某一類列」。
- **坑**：
  - 讀碼推「envs 在那一列的 `launch.exec.envs`」，實際 `launch.exec` 只是指到小格檔的指標，envs 在小格的 `exec.json`／`loop.json`。測試用手捏的列形狀，全綠、對真的列一直回 null；設計線和部長只看 diff 與測試尾段就說合定稿。
  - 帶 envs 的 add 會被 daemon 包一層 aos-exec：表上 exec 欄變 null、`ctl set-def` 拒收、as_written.exec 不記、`--path-json` 的指示詞被改寫。「順手加一個環境變數」等於換掉整條啟動路（[定義與換定義](定義與換定義.md) 的 set-def 坑同源）。
  - 照 argv[0] 是不是 `aos-llm-kernel` 認 llm kernel 列，在真表上認不到（exec 指向定義夾，`_entry` 是 `["aos-loop","loop.json"]`）。改認「stack 同時有 `endpoints.json` 和 `requests/`」，掛法怎麼變都認得到。
- **做法**：測試起一台暫存 aos-daemon（`interval_ms` 20），用真的 `ctl add` 掛上去，從 `procs_state.json` 讀列；要經 kernel 的用 `lib/agent/subagent/tests/kernel_fixture.py`。交件信附那一列的原樣輸出，沒附就退回。設計裡寫「一律寫進 envs」之前，先問施工的人「帶與不帶，掛出來的列逐欄一樣嗎」。
- **驗過**：ok-limits 11-14（`test_add_parent_daemon.py`、`test_who_registered_daemon.py`；修訂 1 在 83fd2fd39；`~/code/limits-1114/probe-envs-1414/probe2.out`）；ok-misc T20；ok-board 的 A9（「只收有 mailbox/ 的」漏掉剛起、沒收過信的 agent，真 daemon 實跑才發現）。
- **出處**：`wf/temp/{ok-limits,head-core,ok-devt,ok-misc,ok-board}/wrapup-1114/經驗.md`

## 接線前用便宜的真模型在暫存樹跑一輪

- **適用**：改了 eca 這類包 CLI 的程式（收信、中途餵信、起 `claude -p`），測試用的是假 CLI。
- **坑**：假 CLI 全綠，真 haiku、sonnet 一跑就抓到兩個吞信的問題：模型叫了背景任務先回一個 result，程式一看到 result 就關 stdin，之後的信寫不進去；模型取走中途信後先答一句才接著改檔，那句不在最後的 result 裡。
- **做法**：在暫存樹用 repo 的程式跑真的一輪，模型用 haiku 或 sonnet。每種情境一個 case（閒著、長 CPU、四次工具、背景、改三檔），中途寄一封信，記延遲並看 history。修了再跑一次。只給它真的小工作（06 第 8 條）。
- **驗過**：ok-wake 11-14（`~/code/wake-1114-build/scripts/real_turn.py`；修在 `lib/agent/cli_stream.py:117`、`:38`）；head-comm 當部長時要求的。
- **出處**：`wf/temp/{ok-wake,head-comm}/wrapup-1114/經驗.md`

## 「開關關著逐位元不變」：拿改前的原檔當對照組

- **適用**：新功能有開關，要證明關著時行為跟改前完全一樣。
- **做法**：把改之前的檔備份到 repo 外（後綴 `.orig`），用 `importlib.machinery.SourceFileLoader` 載入（`.orig` 普通 import 載不進來）；用 patch 換掉最底下那個起行程的函式，新舊版各在幾種設定下呼叫一次，比它們拿到的 argv、prompt、timeout，一樣才印 ALL SAME。每個 commit 都在乾淨複本上重跑。比「只比新碼的開與關兩條路」可靠。
- **驗過**：ok-wake（`~/code/wake-1114-build/scripts/cmp_off.py`，6 種設定）；ok-board（改 `mail_notify/_entry`，fable-1 report.md「測試」）11-14。
- **出處**：`wf/temp/{ok-wake,ok-board}/wrapup-1114/經驗.md`

## 守門程式：測試全綠不等於擋得住

- **適用**：寫或改 guard 這類「擋住不該做的事」的程式。
- **做法**：
  - 先列一張表：每支工具怎麼解它的路徑參數（`#`、`~`、相對路徑、最後一節是不是符號連結），guard 照表去算。洞多半出在 guard 跟工具算出來的檔不一樣。
  - 每補一個洞配一個**斷言「擋下」**的測試。舊版有兩個測試把洞寫成正確行為（`test_guard.py:812`、`:824-828`），全綠也看不出來。
  - 另派人專找繞過的路；找到的洞交還 guard 的主人修。上游說「根源在下層工具」時，先讀下層工具的檔頭註解：註解引了使用者的裁定就停下來，修在不違反裁定的那一層（`lib/tool_io.py:234-237` 註明是 11-10 的裁定，洞其實在 guard.py；ok-pilot 先在暫存樹做最小重現 `~/code/ok-pilot-guard-1114/repro.sh` 再停手回報）。
  - 做「寫不成只 warning」這類測試：等必要的那次寫入回來後才把父夾 `chmod 0555`（包一層 launcher），不用 mock 被測程式（`templates/tests/agent-fsm/test_brain_wait_file.py`）。
- **驗過**：ok-onboard 11-14，guard 交件時 105 個測試過，獨立審查找到 8 個洞，前兩個（路徑帶 `#` 的切法、keep 參數）由 ok-pilot 實測成立（`wf/temp/head-front/review-guard.md`；表在 `~/code/onboard-1114/holes-1/notes/resolve.md`）。
- **出處**：`wf/temp/{ok-onboard,head-front,head-tools,ok-kmsg}/wrapup-1114/經驗.md`；信 01794637269674582668.704457.2585532
