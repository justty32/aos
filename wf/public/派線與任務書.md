下一份交接書、任務書送出前對一次。

## 派線前的預掃要涵蓋全部組別：沒掃的組要明寫

不能只掃「已知的那幾組」。預掃做得好可以砍掉大半工作量——逐件比對「預期檔名＋預期大小」這種便宜檢查，常常讓一條線的實際工作量掉一個數量級。但**漏掃的那組會在收線時才爆出來**：派線當下還查不出識別碼的那一組被跳過，「其實早就有了」到收線核驗才發現。那是預掃範圍的缺口，不是線的錯。**交接書要嘛把預掃做完，要嘛明寫哪幾組沒掃過。**

## 線推翻交接書時要接受，不要逼它湊數

實跑後線回報「交接書寫的三個其實只有兩個，理由是……」，或「照字面搬檔會觸發整批重算，成本比預期高一個量級」——這種通常是**線對、交接書錯**，它手上有你寫交接書時沒有的實測資料。驗收條數寫死是為了防它亂加驗證，不是要它為了湊滿數字造假失敗案例。收到這種回報就改交接書，別叫它再跑一次去「補齊」。

## 交接書的「背景」與「工作步驟」自相矛盾：送出前對一次，衝突處寫死哪個為準

例：背景寫「可以直接原樣複製過去」，步驟卻寫「佈局零改動」，而實際資料有一半不符合那個佈局假設。線只好二選一，選錯就整批白做。（[TEMPLATE.handoff](../workflows/TEMPLATE.handoff.md) 檔尾有這條提醒。）

## 禁區寫成「唯一准用的做法」，不寫「不要碰 X」

任務書只寫「不碰 `~/aos-home`、跑完把起的行程收掉」，子 agent 就用 `pkill -f` 收自己的測試 daemon，連使用者的樹一起停了（[行程與環境](行程與環境.md)）。「不要碰 X」擋不住「我以為我沒碰」。會動到行程、環境、共用檔的事，把**准用的那一兩種指令寫死**，其餘一律禁止。

## 任務書要明講的幾件事：開隊前當 checklist 對一遍

- **commit 署名**：Opus 隊會照它環境裡的提醒寫自己的署名行。任務書要寫「結尾兩行**一定**照抄這裡給的，不是你環境提醒裡那行」，並要它收尾前 `git log --format=%b main..HEAD` 自查。
- **真跑次數一開始就限**：寫死「各 2 次、做不完寫『留下一輪』、目標 N 分鐘內收線」。三隊同機各跑 3 次會拖到一小時以上。
- **隔離的隊碰不到主 repo**：`git worktree remove`、`branch -d`、殺主 repo 的行程要派**不隔離**的隊在主 repo 做。
- **測試別靠信箱檔名順序**：信的 id 開頭是亂數，排序不等於時間；改成「信箱裡任一封含這段字」。

並行開好幾隊時：

- **scratchpad 是共用的**：工人的暫存放 scratchpad 裡自己的子資料夾、帶批次前綴，不然會落到 repo 根，或同名檔被別隊蓋掉。
- **各隊切不重疊的範圍，收尾自己 `git rebase main` 再跑測試**，調度者就能逐隊 ff-merge、不用另派人 rebase。共用檔（SESSION-LOG、日誌）指定唯一一隊能碰。
- **拆檔前先問誰讀它**：有程式直接讀某份 md（整份或某一段）的，拆了就壞；先改程式再拆。
- **使用者要關機**：叫各隊 10 分鐘內停真跑、只 commit 能過測的、報告寫「做到哪、下一輪從哪接」；沒 commit 的 worktree 檔案還在硬碟，下次派人進去撈。

## 規則改了就開新工人；契約先定稿再派

- 便宜模型的工人可能把中途追加的規則當側路訊息拒收；規則改了就開新工人、把規則寫進主交接書，不要用續訊息機制追加。
- 契約先定稿再派；中途每改一次規則，已做完的批都要回補。

## 子 agent 說「檢查過、沒事」：要附指令與輸出，調度者自己再看一眼

有線回報「唯讀檢查過活樹的 stack、沒被寫到」，實際上頂層那一格有殘留（它清環境的寫法在 zsh 裡沒生效，見 [行程與環境](行程與環境.md)）。任務書寫明：每一句「檢查過」後面貼實際跑的指令與輸出；關係到使用者東西的那幾項（活樹的 stack、daemon 還在不在），調度者收線時自己再跑一次。回報格式見 [等隊員與讀信「我讀了什麼、沒做什麼」](等隊員與讀信.md#審查信回報信固定寫我讀了什麼沒做什麼)。

## 有截止點的日子：每條線要有「趕不上就還原乾淨」的時刻

約好幾點停樹、換版本的日子，半成品留在會被帶上線的夾裡，等於被帶上線。派線時就寫：幾點前沒測到綠，就把那幾夾還原到最後一個綠的 commit，剩下的留成 repo 外的補丁；要換的那個 commit 由調度者在截止前釘住（pin 的坑見 [活樹旁邊「換樹當晚」](活樹旁邊.md#換樹當晚pin-是-main-的一個-commit不能跳過中間某一筆)）。

## 舊東西：舊設計謹慎採用，成熟元件原樣複製

兩種態度，別搞混：

- **舊原型的設計**（proto2／3／4 系列）是遺產：裡面有想清楚的東西，也有後來被推翻的。開新段先派人去撈「哪些決定還站得住」，任務書點名參考路徑、要它逐條說採不採、為什麼；不要整包照抄（使用者 2026-09-13）。
- **已經成熟的元件**（inst.json、aos-exec、`$ref` 解析這類）直接**原樣複製、只改最小差異**，不要派隊重寫，它們的既有規則也**不列待問**（使用者看到成熟元件被重寫、既有規則被列成待問時：「直接複製過來就好了啊」「這啥鬼問題」）。派 plan／審稿隊前先告訴它哪些是現成的。

## 公司 WSL 只有 8 核：同時最多一條跑程式或全套測試的線

同時最多**一條**會跑程式或全套測試的線（當時是 codex 線），其餘只讀碼。長跑與故障注入要限 node 數並 `nice`：多線同跑重負載會讓 load 衝到上百、使用者電腦很卡，時間敏感的測試也會假失敗。

## codex 隊員的坑（11-14 起不走 codex，留作參考）

- **字眼會被擋**：codex（ChatGPT 帳號）有資安內容過濾，任務書寫「競態、/proc、kill -9、故障注入、對抗式」的線會被擋、token 白費。當時改寫成「程式品質與正確性審查」「中斷後恢復」等說法就能跑。**已被取代**：現在照 [06 硬規則第 8 條](../workflows/dispatch/aos-teams/06-公司WSL活樹與任務書硬規則.md#任務書必貼的硬規則)「不編理由、不繞它講明的限制」。
- **叫它收尾**：`codex exec` 跑起來後收不到訊息；要它收尾只能殺掉再續跑。`codex exec resume` 沒有 `-s` 旗標，改用 `-c sandbox_mode=…` 雖然是同一個沙箱，但會被安全分類器標成「Safety Bypass Flag」警告；要續跑就**開新的 `codex exec -s workspace-write`**（把上一輪的 out.md 當任務書的一段），不用 resume 帶 `-c sandbox_mode`。`resume --help` 會列出繞過沙箱的旗標，照樣不准用。
- codex 會順手做圖紙沒叫它做的事，diff 要逐行審，見 [審查與實測](審查與實測.md#外包施工的-diff-逐行審看少掉的檢查多出來的規矩)。
