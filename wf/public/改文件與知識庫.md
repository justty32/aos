## 改寫必讀規矩檔：草稿夾、對照表、請沒看過表的人來對、一口氣換上

- **適用**：把舊條文改寫成「只寫現行做法」，或任何一次動好幾份全場必讀的規矩檔。
- **坑**：
  1. `wf/` 存檔當下全場就在讀。讓子 agent 直接改現役檔，六份規矩檔有約十分鐘是改到一半的版本。
  2. 改寫的人自己做的「舊條文→新位置」表會漏：第一輪獨立審稿找到 6 處（整條掉了、意思被改、草稿照舊 HEAD 寫會蓋掉別線剛加的兩條），第二輪又 4 處（把一句 AI 的轉述當成使用者原話）。
  3. 草稿寫好到換上去之間，現役檔又被別線改了兩次（ed5032f9b、b4f8a3c34）。
- **做法**：
  1. 子 agent 一律寫草稿夾（`wf/temp/<線>/draft/`），任務書寫明不准碰現役檔。
  2. 改寫前全文先原樣抄進 `archive/`，用程式逐行比對跟 HEAD 一樣。
  3. 做一張「舊條文→新位置」表，再請一隻**沒看過這張表**的審稿員自己從舊檔抓規矩句到草稿裡找。
  4. 使用者原話用程式比對：把舊檔每個「」字串拿去新檔找，找不到的逐個看。只剩封存副本才有的原話，收進一節「已被取代的原話（留底）」。
  5. 換上去當下：逐檔 `git log`（有新 commit 先併、封存副本重抄）→ 逐檔「cp 到暫存檔再 mv」一口氣換完 → `check_anchors.py` → 一個 commit。
  6. 換完當成新來的 agent 照新文件實做一次（例：照短卡的字跑 claim、乾跑、交件）。
- **小改**（只動幾句）：python 小腳本 `str.replace` 精確舊句、`assert count == 1`、寫暫存檔再 mv；每批跑 check_anchors。審稿方一眼看得出只動了字。
- **偏好檔、鐵律**：部長逐字看 diff 再上交頂層（抓到過使用者原話「不可以問我問題」被寫成「不追著問」）。
- **驗過**：ok-kb 11-14，c913897a6（22 檔）；審稿紀錄 `wf/temp/head-front/review-q2.md`、`review-q2-v2.md`；對照表 `wf/temp/ok-kb/draft/前後對照.md`。小改：ok-astra。
- **出處**：`proto8/thinking/2026-11/14/kb-1114.md`「過程裡學到的」；`wf/temp/{ok-kb,head-front,ok-astra}/wrapup-1114/經驗.md`

## 文件對不對，請新人照索引走一遍來量

- **適用**：想知道「agent 進來查不查得到、要讀多少」。
- **做法**：定十來個常見問題；請一隻沒看過這條線的 agent 從 `AGENTS.md` 與知識庫入口出發，只跟連結與索引；每個開過的檔算整檔 bytes、每題獨立計；記走不走得到、有沒有互相衝突的答案。改完再請另一隻走一次比。
- **坑**：
  - 兩次要同樣的起點與量法，寫明讀的是 repo 那份還是活樹複本（換樹前是舊的）。
  - 換模型（sol 對 Claude）挑的路不一樣，bytes 只能看大方向。
  - 走得越深找到越多：只走到答案就停的那次說「衝突剩 1 題」，要它把相關的檔全跟到又找到 6 處。量「讀多少」和量「有沒有衝突」是兩種走法，分開做。
  - 沒有依據的數字目標不要訂（訂了 20 KB，入口三份必讀檔本身就 34 KB）。
- **驗過**：ok-kb 11-14：下午 sol 走、改完 Claude 走，15 題都走得到，13 題讀得少，最貴五題 52～77 KB → 31～49 KB（a059690e1）。
- **出處**：`proto8/thinking/2026-11/14/kb-1114/06-驗收-重走15題.md`、`kb-1114/01-sol4原文.md`；`wf/temp/{ok-kb,head-front}/wrapup-1114/經驗.md`

## 知識庫頁對程式：先分「會撞到的」和「只是沒寫的」

- **適用**：把知識庫（或任何說明頁）逐頁對程式。
- **做法**：
  1. 蒐集時每條標種類（跟程式對不上／過時／漏寫／太長／重複）與把握（確定／猜），附程式的檔與行。
  2. 「對不上、確定」的直接改，每條改前再回現在的程式核對一次（當天別線也在改程式：`--limits` 收不收 `mem_total_mb` 那句改完兩小時就又過時，50e7a35bc）。
  3. 「漏寫」的不要全補：只補 agent 照頁做會撞到的（查不到的錯誤代號、會用錯的預設與互斥、會改結果的旗標）；純短名、`-j` 這類留一句「More flags: run X --help」。
  4. 沒頁的工具不另寫頁：在索引加指標列，鍵寫成到那一段的路徑（例 `../mailbox.json#/tools`），`index_check.py` 會檢查解不解得到。
  5. 交完請部長派獨立審稿員抽核（三批抽核各找到幾句要修的，見 [審查與實測](審查與實測.md)）。
- **驗過**：ok-kb 11-14，3274da594、f1ef04ba0、b72613da3；ok-astra 借調的批次 A。
- **出處**：`wf/temp/ok-kb/astra/批次A-cli與tools補漏.md`；`wf/temp/ok-kb/wrapup-1114/經驗.md`

## 改文件時的小坑

- **`check_anchors.py wf` 會掃到 `wf/temp/` 裡別線的草稿**：別線草稿有壞錨點時整個退 1。看輸出裡的路徑，不是自己的檔就照交、在回報寫一句（ok-kb、ok-astra 交 68dc9bcb5 前都遇到，壞的是 ok-release 的草稿）。
- **知識頁有位元組上限**：`cli/daemon.json` 補完審稿要求的句子漲到 8353 bytes，得縮同頁另三句才回到 8285（ok-astra，95bdc412f）。補句子前先看頁還剩多少。
- **一行字串的 JSON 知識頁被兩線同時改，`git apply` 會失敗**：用 python 讀出字串，只換自己的段落再寫回，兩邊的字都保住（ok-misc，`cli/parts/llm.json`）。
- **wf 版和產品版有數字不同時，兩份都寫明差在哪**：看包 wf 24 支、產品版 26 支（換樹前活樹沒有 aos-comm），不寫讀的人會以為有一份寫錯（ok-onboard，c3003f7a3）。
- **量數字要量對樹**：量測腳本的 `AOS_HOME` 寫死成暫存樹，量到的是暫存樹的舊說明（1,023），main 上已是 1,069。數字寫進文件前先確認量的是哪一棵（ok-astra）。
- **`scan.py` 印的「in N files」是有命中的檔數**，不是掃了幾檔；「0 files」不是沒掃到（ok-onboard；工具見 [tools/scan](tools/scan/README.md)）。
- **出處**：`wf/temp/{ok-kb,ok-astra,ok-misc,ok-onboard}/wrapup-1114/經驗.md`
