密鑰外洩面、環境繼承、暫存檔權限這類跨元件的安全意見。跟 uid、權限層有關的另見 [daemon與行程](daemon與行程.md)「daemon 靠 /proc/<pid>/environ 認自己的行程」。

## 原型把整份環境寫進檔，帶出 API key

- 主題：安全（也牽涉 daemon 與行程的環境繼承、指令與工具的除錯工具）
- 哪裡：aos-daemon 起 proc 時，把起樹那個殼的環境整份往下傳；暫存樹用的清環境腳本只 unset `AOS_*`；aos 沒有「看某個 proc 環境」的現成工具。
- 現象（經過，不寫任何值）：
  1. ok-board 的原型隊員在 `~/code/board-1114/` 暫存樹做頻道 proc 原型，為了確認 loop proc 拿到哪些 `AOS_*`，在 proc 裡把整份環境寫進暫存樹 stack 底下的一個 txt 檔（約 9 KB，權限 644）。
  2. 暫存樹是經清環境腳本起的，但它只清 `AOS_*`；使用者殼裡其他變數（含至少一把 API key）原樣傳進 daemon，再傳進每個 proc。
  3. 隊員收尾時自己發現、在完工信裡報出。ok-board 先 chmod 600、沒刪，報 head-comm 轉使用者專區。使用者授權刪檔、key 不換，頂層已刪。
  4. 二次擴散：ok-board 為了查「值有沒有進到報告或 log」，把幾個值抽出來寫成 `/dev/shm` 底下的清單檔再 `grep -F -f`，又多落地一份。已 chmod 600、報出、另題問使用者。查擴散應該在行程內比對（讀進記憶體、只印檔名），或只比雜湊。
- 為什麼會發生：
  - 要看「proc 實際拿到什麼環境」，最順手就是 `env > file` 或讀 `/proc/<pid>/environ`；aos 沒有更窄的工具，任務書也沒寫禁止。
  - 清環境的慣例只針對 `AOS_*`（為了不碰活樹），沒人想到其他變數也會一路傳進暫存樹的每個 proc。
  - 暫存檔預設 644、放在家目錄底下，寫出來就是別人可讀的。
- 建議：
  1. 規矩：原型、測試、除錯不准把整份環境寫進檔、log、信；要看只列名字，或只列 `AOS_*`。寫進 aos-teams 06 硬規則和任務書範本。（xiaosi 11-14 已群發，06 和範本還沒寫進去。）
  2. 小工具：一支 `aos-env`（或 `aos-agent ctl env NAME`），預設只印某個 proc 環境的變數名，`--aos` 才印 `AOS_*` 的名和值，其他值一律不印。有了它，看環境就不必自己 dump。
  3. 共用的測試輔助、換樹、清環境類腳本若要記環境，一律濾掉名字含 `KEY`、`TOKEN`、`SECRET`、`PASS`、`CREDENTIAL` 的，值換成 `<redacted>`。
  4. proc 不該繼承使用者的密鑰：loop proc（頻道、看門這類不用模型的）根本不需要 API key。daemon 起 proc 時環境改成白名單（`PATH`、`HOME`、`LANG`、`AOS_*`、定義裡明列的），模型 kernel 要 key 就由 kernel 的定義或 env_file 明確給。這也縮小 proc 被誘導印環境時的外洩面。要跟 ok-sec 的權限層一起看。
  5. 暫存樹的 stack 夾考慮用 umask 077 起，誤寫的檔預設不給別人讀。
