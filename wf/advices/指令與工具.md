## ctl add 兩條路各自組參數，加旗標容易漏一邊

- 主題：指令與工具
- 哪裡：`aos-agent ctl add`（`proto8/cmd/aos-agent/aos_agent/ctl/add.py`）：`cmd()` 直接寄 daemon，`add_via_kernel()` 經 $AOS_KERNEL，兩處各寫一次 `call_dc(dc.add_letter, …)`。

- 痛的程度：拖慢（旗標被默默丟掉）
- 提出者與日期：ok-misc 2026-11-14（問題由 ok-kf 回報）
- 出處：wf/temp/ok-misc/aos-advice/ctl-add-兩條路各自組參數.md；commit 0a3ffe5c4
- 狀態：已解（246d4aa49，ok-pilot 11-14：`add_kwargs` 由兩條路與 set-def 共用，測試斷言兩條路參數相同；漏傳 dotenv_override 早先由 0a3ffe5c4 補）

## impls 的 make 目標名不編執行檔

- 主題：指令與工具
- 哪裡：proto8/impls 的 CMake 目標：每個 impl 有 `<名字>`（靜態庫）和 `<名字>_main`（執行檔）。
- 現象：`make -j8 aos-exec aos-loop aos-llm-kernel` 只連結靜態庫，bin 還是前一天的，測試 6 紅、錯誤訊息是改之前的字。改下 `make aos-exec_main …` 才重編 bin。
- 建議：庫改名 `<名字>_lib`，讓 `<名字>` 是執行檔；或讓 `<名字>` 依賴 `<名字>_main`。改不了至少在 impls/README 的編法段寫「make 目標用 `<名字>_main`」。
- 痛的程度：小不便（看起來像改壞了）
- 提出者與日期：ok-misc 2026-11-14
- 出處：wf/temp/ok-misc/aos-advice/impls-make目標名不編執行檔.md；misc-1114 暫存樹 build（T17）
- 狀態：已解（50518d069，ok-pilot 11-14：只走建議的「至少寫進 impls/README」，CMake 目標名沒改）

## commit-request claim 把 git 轉義過的中文路徑原樣存下，蓋不到真檔

- 主題：指令與工具
- 哪裡：`wf/tools/commit_queue.py` 的 `norm()`（363～373 行）與 `claim()`（695～706 行）；比對在 `held_by_others()`（531～543 行）、`release()`（708～726 行）。
- 現象：
  - claim 中文檔名後，claim 清單裡存的鍵不是 `proto8/cmd/aos-agent/docs/01-用法例子.md`，而是 git `core.quotepath=true` 的轉義寫法：連外層雙引號一起、檔名是八進位位元組（`"proto8/cmd/aos-agent/docs/01-\347\224\250…md"`）。
  - 這個鍵跟真檔路徑對不上：別線 claim 同一檔不會被擋（`held_by_others` 用 `cl.get(p)` 逐字比），claim 形同沒做；release 也要給一模一樣的轉義字串才放得掉（`p in cl`）。
  - submit 不會誤 commit：`submit()` 第 495 行同樣經 `norm()`，接著第 507～510 行先做 `os.path.lexists`，轉義路徑會被擋成 does not exist。
- 原因：不是佇列自己產生的。commit_queue.py 取路徑的 git 呼叫全帶 `-z`（108 ls-tree、484 diff-files、565 check-ignore、632 status、658 diff-tree、731／734 diff），這時 git 不轉義。是輸入沒擋：使用者從 `git status` 抄來的字串（含外層雙引號）直接當參數傳進來；`norm()` 只把路徑換成相對 repo 根，沒拆 `"…"`、沒反轉 `\ooo`；`claim()` 也不檢查檔案或上層夾在不在，於是原樣存成鍵。
- 建議：
  1. `norm()` 或 `claim()` 遇到 `"` 開頭的 C 風格字串，先反轉義成 UTF-8 再存。
  2. 或者 claim 時，檔案和它的上層夾都不存在就報 PathBad（新檔可以 claim，但上層夾要在）。
  3. 加一條測試：claim 中文檔名的轉義寫法，要嘛存成 UTF-8 鍵、要嘛報錯；別線再 claim 正常路徑時要被擋。
  4. 不用遷移：ok-pilot 11-14 查過現有 claims.json（在 `~/.cache/aos-commit-queue/<repo 路徑雜湊前 10 碼>/`，91 條）沒有轉義鍵。
- 暫時繞法：從 `git status` 抄中文路徑前先 `git -c core.quotepath=off status`，或自己打正常路徑；claim 後看一眼 `commit-request claims`，看到 `"\…"` 開頭的鍵就是沒保護到，照列表上的原字串 release 再重 claim。交 `--files` 的同類坑見 [public/patch-and-commit「commit-request 的坑」](../public/patch-and-commit.md)。
- 痛的程度：會出錯，算擋路（claim 看起來成功，其實沒保護到檔，別線可以同時改同一檔）
- 提出者與日期：ok-kf 2026-11-14（程式位置 ok-pilot 補）
- 出處：wf/temp/ok-kf/aos-advice/commit-request-claim-quoted-path.md；ok-kf 11-14 09:41 claim `proto8/cmd/aos-agent/docs/01-用法例子.md`、`02-已知限制.md`，release 時發現；head-core 要求寫成稿
- 相關：本檔「commit-request claim 一個資料夾，蓋不到夾裡的檔」，同樣是 claim 逐字比對路徑字串。
- 狀態：未處理。整理時查（只讀）：`norm()`、`claim()` 現在都沒有反轉義也沒有存在檢查，上面行號與 `-z` 各處都對過。第十批（11-14）在 HEAD b892fbd83 再查一次：commit_queue.py 最後一次改是 f446f3d86（knowledge 的 _index.json，跟這條無關），`norm()`（363～373）、`claim()`（695～706）、`held_by_others()`（531～543）、`release()`（708～726）、`submit()`（495、507～510）行號都還對，仍沒改。

## `#` 在 json 工具和檔案工具裡意思不同；`keep` 的說明寫「從工作區」，實際哪裡都能建檔

- 主題：指令與工具（工具說明跟行為不符）
- 哪裡：
  - 檔案工具 `write`、`edit`、`mkdir` 等：`proto8/lib/tool_io.py` 的 `ws_path()`（第 234～237 行）。
  - json 工具 `json_set`、`json_add`、`json_del`、`json_multi_set`：路徑寫成 `FILE#/POINTER`。
  - `mailbox_read`、`mailbox_send` 的 `keep`：兩份 `_tooldef.json` 都寫「a file name (from your workspace; its folder must exist)」；`proto8/lib/agent/mailbox_read/_entry` 第 39～41 行原樣轉成 `--keep-to`；下層 `proto8/cmd/aos-mailbox/aos_mailbox/__init__.py` 的 `keep_open()` 照收任何路徑，用 `O_CREAT|O_APPEND` 開檔。
- **先講清楚：下層的行為是設計，不是洞。** 檔案工具和 keep 的絕對路徑照用、不限工作區，是使用者 11-10、11-13 的裁定（tool_io.py:234 的 `ws_path` 檔頭有註明：「拿掉工作區限制、有權限就能動」）。這條不要求改行為，只記兩件「說明跟行為不符」的事。
- 現象：
  - **(a) `#` 的意思依工具而不同。** json 工具把 `#` 當「檔案」和「JSON 指標」的分界；檔案工具把 `#` 當普通字元，照字面接到工作區後面、不做 normpath，`ws/#/../..` 交給作業系統時，`#` 那一節不存在也照樣往上退。同一個路徑字串交給兩類工具，會落在不同的檔。寫守門程式的人照「`#` 是分界」去解所有工具的路徑，就會算錯檔：lib/agent/guard（20b65475c）就這樣被繞過（查的是工作區本身，寫的是工作區外），已排進 guard 修洞，下一版只有 json 工具才切 `#`。知識庫和 tooldef 都沒說 `#` 在檔案工具裡是普通字元。
  - **(b) `keep` 的說明跟行為不符。** 說明寫「從工作區」，實際絕對路徑照收，能在 stack、定義夾、活樹建檔或追加一行 JSON（內容的 title、what 由 agent 決定）。會誤導以為「拿掉寫檔工具就寫不了檔」的組包者（只讀的隊員還留著 mailbox_read，照樣能靠 keep 建檔），也會誤導照 tooldef 判斷哪些參數會寫檔的守門程式（guard 原本沒查 keep，也已排進修洞）。
- 建議：

## aos-daemon-ctl 的說明寫 rm 是「先 stop 再 remove」，實作是直接送 SIGTERM

- 主題：指令與工具（--help 字樣；也碰到 daemon 與行程）
- 哪裡：`proto8/cmd/aos-daemon-ctl/bin/aos-daemon-ctl` 總說明第 18 行；`proto8/impls/aos-daemon/src/daemon/reconcile.cpp` 第 292 行。
- 現象：
  - 說明原文：`rm NAME        detach (stop, then remove; stack kept, so it does not ask)`。
  - 實作：列不在期望表上、phase 是 running 時直接 `term(c)`，註解寫「表上多出來的：送 SIGTERM 就往下走，不等」。不寫子行程的 ctl stop，也就是不等它把這一輪跑完。
  - 後果：讀說明的人會以為 rm 跟 stop 一樣是「跑完這一次再停」，其實 rm 跟 sleep 一樣是當場 SIGTERM、10 秒後 SIGKILL，agent 的 after_stop hook 最多只有那 10 秒。知識庫 `aos/me.json#/self_ctl` 對 rm 的寫法是對的（「you leave the daemon table right away」），只有這一行說明不一致。
- 建議：那一行改成照實寫，例如 `rm NAME        detach now (SIGTERM, like sleep; the row is removed; stack kept)`；`rm` 子命令自己的說明（同檔約 154 行起）一併核對。
- 痛的程度：小不便
- 提出者與日期：ok-devt 2026-11-14
- 出處：wf/temp/ok-devt/aos-advice/daemon-ctl-rm-help.md（引 `proto8/thinking/2026-11/14/ok-devt-1114/01-現況.md`「三」）；wf/temp/ok-devt/wrapup-1114/建議.md 開頭列的第二份。提出者註明 reconcile.cpp 那段是在 ok-limits 的 B7 diff 上下文裡讀到的、沒另開原始碼核行號。
- 狀態：未處理。整理時查（補上提出者沒核的那半）：aos-daemon-ctl 第 18 行原文對；reconcile.cpp 第 292 行是 `term(c);  // 表上多出來的：送 SIGTERM 就往下走，不等（10-23 壓測後改）`；`rm` 子命令自己的說明（約 154～159 行）寫「Asks the daemon to stop and remove NAME from its table」，同樣沒說是 SIGTERM。「10 秒後 SIGKILL」整理時沒核。
