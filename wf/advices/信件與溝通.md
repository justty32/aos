## mailbox_read 預設刪信，專區回信讀完就驗不了

- 主題：信件與溝通
- 哪裡：MCP `mailbox_read`（不帶 keep）＋ `aos-user verify`。
- 現象：用 `mailbox_read` 讀了兩封使用者專區回信，信夾就被刪掉，之後沒東西可驗。拿 `~/.aos/user/done/<月>/<原信>/reply.json` 去驗也不行：`aos-user: error: VerifyBad not a user-zone reply (no zone key or no in_reply_to)`。只能逐欄比對，少了 level 1 驗證；push、刪檔這類授權正是最需要驗的。
- 建議：擇一或都做。帶 `zone` 鍵的信 `mailbox_read` 預設 keep，或至少在輸出末行提醒「這是專區回信，要驗請 keep:true」；`aos-user verify` 也接受 done/ 底下的 reply.json，或接受信名自己去 done/ 找。
- 痛的程度：拖慢
- 提出者與日期：ok-pilot 2026-11-14；狀態更新 ok-misc 2026-11-14
- 出處：wf/temp/ok-pilot/aos-advice/mailbox_read預設刪信讓專區回信驗不了.md；wf/temp/ok-pilot/notes.md「摩擦：專區回信讀了就沒了」；狀態更新 wf/temp/ok-misc/aos-advice/mailbox_read預設刪信-已解.md
- 狀態：已解（ace14088d8，線雜 ok-misc 11-14）。`aos-mailbox read`（和包它的 MCP `mailbox_read`）讀到專區信（body 的 `zone` 是 `"user-zone/1"`，退信也算）預設歸檔到 `<stack>/mailbox/archive/<信名>/`、不刪，其他信照舊讀完就刪；每封留下的信後面印一行 `(unverified user-zone reply: kept in …; verify it with user_verify {"letter": "<信名>"} …)`，`-j` 模式改在那封 JSON 加 `"kept": "archive"`。`user_verify` 用信名找信的順序是 new → cur → archive，讀過的信也驗得了。`aos-mailbox read --drop` 回到舊行為，和 `--keep` 不能同給。驗過：ok-misc 在乾淨複本跑 aos-mailbox 12、mailbox_send／mailbox_read 6、user_verify 6 支測試全綠。另一個建議「`aos-user verify` 接受 done/ 底下的 reply.json」不採納：信已經留下，直接驗原信就好，aos-user 也照頂層交代沒動。設計與 Argon 審在 wf/temp/ok-misc/mailbox-keep-zone/01、02。活樹待換樹。

## fyi 信的 status 規則不在 schema/letter.json 裡

- 主題：信件與溝通
- 哪裡：`~/.aos/user/schema/letter.json` 與 `aos-user send` 的檢查。
- 現象：照 schema 寫 fyi 信，status 用 NEEDS-USER（schema 的 enum 有），送出被退：`SchemaBad fyi status must be one of DONE, FAILED, BLOCKED`。照 schema 寫的檢查器抓不到這條。

## MCP subagent ask／listen 有 60 秒硬上限，蓋過 timeout_s

- 主題：信件與溝通
- 哪裡：aos MCP 的 `subagent` 工具（op ask、listen）。
- 現象：`ask`／`listen` 帶 `timeout_s: 600`，60 秒就被砍：`aos-mcp: error: CommandFailed subagent timed out (60 s); its process group was killed`。工具說明寫預設 600，看不出 MCP 層另有上限。sol 的題目常要 1～5 分鐘，ask／listen 對真題幾乎等不到。繞法：say、結束這輪、clock_register 叫醒再 listen（timeout_s ≤ 50）；或背景看 history.jsonl（[wf/public/tools/waitdone](../public/tools/waitdone/README.md)）。
- 建議：MCP 層照 timeout_s，或在說明寫明上限；超過上限直接回 ArgumentsBad；逾時回「還沒答」（例 `AnswerPending`＋已等多久），不殺行程、不算錯，可以續等。
- 痛的程度：拖慢
- 提出者與日期：ok-pilot 2026-11-14；ok-llmk2 2026-11-14（listen，活樹上仍撞到）；ok-board 2026-11-14（listen timeout_s 600 被砍、改 55 才回 AnswerMissing；繞法是 clock_register +4m 叫醒自己再 listen last 1，每次等 sol 多一輪 clock）
- 出處：wf/temp/ok-pilot/aos-advice/MCP-subagent的60秒上限蓋過timeout_s.md；wf/temp/ok-pilot/notes.md 第二輪第 4 點；wf/temp/ok-llmk2/aos-advice/subagent-listen-60s.md；wf/temp/ok-board/aos-advice/ok-board-advices.md 第一節
- 狀態：已解（252669c47：MCP 層 subagent／fork 不再被 60 秒砍，timeout 0＝不限時；後續測試修正 77a822e1c）。活樹待換樹（ok-llmk2、ok-board 當天在活樹上還是撞到）。另外 MCP client 自己也有工具逾時（Claude Code 是 MCP_TOOL_TIMEOUT），超過還是會被 client 砍；「逾時回還沒答、可續等」那條沒做。

## aos-agent 沒有 ask，一問一答要拆成 say＋listen

- 主題：信件與溝通
- 哪裡：`aos-agent` 指令（proto8/cmd/aos-agent）。
- 現象：`aos-agent ask --target fsm_ann "現在幾點？"` 回 `CommandUnknown unknown subcommand ask`。agent 的 `subagent` 工具有 `op: ask`，人用的 aos-agent 沒有；腳本得寫 `aos-agent say … >/dev/null; aos-agent listen --target X --timeout-s N`。兩步之間若別人也對同一隻 say，listen 拿到的可能不是自己那句的回答。
- 建議：加 `aos-agent ask --target X [--timeout-s N] TEXT`：say 後只 listen 自己那封信的回答（用 say 印的信名配對），逾時退非 0；名稱、行為跟 subagent 工具的 ask 對齊。
- 痛的程度：小不便
- 提出者與日期：ok-kf 2026-11-14
- 出處：wf/temp/ok-kf/aos-advice/aos-agent-no-ask.md；proto8/thinking/2026-11/14/kernel-framework-1114.md 批 13、14
- 狀態：已解（2ef627f1b，ok-pilot 11-14：`aos-agent ask`＝say 之後 listen，同 subagent 的 op ask；**不配對信名**，--help 與知識庫寫明。history 不記信名，真配對另案，見本檔「agent 的回答對不到是回哪封信」）

## 信件一封一個夾，跨 uid 後寄件人能鎖信、收件人能改信

- 主題：信件與溝通
- 哪裡：aos-post 的信件格式（一封信＝`tmp/<信>/letter.json` 夾，rename 進 `new/`）。
- 現象：跨 uid 之後，寄件人是信夾的擁有者，可以把信夾設成 0700 再丟進去：收件人搬不動、讀不到，使用者 `rm -rf` 得到 Operation not permitted，只能用 `aos-asuser --fix` 救。另外，把「夾」搬到別的父夾需要對夾本身有 w，所以收件人必須有寫權，結果它能原地改寫使用者寄來的信，st_uid 仍是使用者（實測 E7b、E7c）。
- 建議：改成一封一個檔（`tmp/<信>.json` → `new/<信>.json`），信箱的預設 ACL 只給收件人和使用者 r--。刪檔、搬檔只看父夾權限，毒信一定刪得掉，收件人也改不了信。附件另想辦法（另放、信裡寫路徑）。
- 痛的程度：今天同一個 uid 沒事；開安全模式就擋路
- 提出者與日期：ok-sec 2026-11-14
- 出處：wf/temp/ok-sec/aos-advice/信夾格式與跨uid.md；proto8/thinking/2026-11/14/sec-1114/05-採納表.md A2、A3、B1、03-計劃.md Q10；實測 ~/code/sec-1114/e78.sh
- 狀態：已排入（ok-sec，Q10 選 2「現在做一信一檔」）。使用者 11-14 下午選 2（`proto8/user-advice/20261114.md` 第十段，d38a0d36f）；施工計劃、Argon 原文、採納表在 6ef376842（`proto8/thinking/2026-11/14/sec-1114/07～09`），整包在換樹那一刻上。原先寫的「與『不要修改到aos-post』衝突，待使用者裁」已過時（第九批整理改，依 ok-kb 清理清單）。

## agent 的回答對不到是回哪封信，ask／listen 只能拿「最新那則」

- 主題：信件與溝通
- 哪裡：agent 的 history 格式（agent-fsm `templates/agent-fsm/idle.py` 約 167 行寫 history；aos-eca、mail_notify 同樣）；`aos-agent listen`、`aos-agent ask`；MCP subagent 工具的 `op ask`（`proto8/lib/agent/subagent/_entry`）。
- 現象：
  - history 每列只有 `{"role","content"}`，不帶信名。信名只在 queue 的 new／cur，和 before_queue、after_queue 兩個 hook 的參數裡。
  - listen 的配對只是「最新那則」加上「回答數有沒有變多」。subagent 的 op ask 和 2ef627f1b 新加的 `aos-agent ask` 都是 say 之後接 listen，同樣沒配對。
  - 兩種情況會拿錯：別人同時對同一隻 say，拿到的可能是回給別人的；fsm 一次收一整批信只回一則，這一則其實同時回了好幾封。
  - ok-pilot-adv-2 11-14 照本檔「aos-agent 沒有 ask」要做真配對，查到這點停手，只做了跟 op ask 同語意的 ask，並在 --help 寫明限制。
- 建議：agent 端記下「這則回答回的是哪幾封信」，例如 stack 裡另寫一檔記「回答序號 → 信名清單」；或記成 history 列的額外鍵，但要確認送端點前會剝掉（sender.py 註解寫 idle 把 body 原樣送端點）。記好之後 listen、ask、subagent 工具就能只等自己那封的回答。會改範本和 history 格式，要先定設計。
- 痛的程度：小不便（單人對單隻問答不會出事，多人同時問同一隻才會）
- 提出者與日期：ok-pilot 2026-11-14
- 出處：wf/temp/ok-pilot/aos-advice/回答對不到是哪封信.md；ok-pilot-adv-2 回報（存於 ok-pilot 的對話）；commit 2ef627f1b
- 狀態：已排入（ok-pilot，reply-match-1114）。整理時查：2ef627f1b 只加了 `aos-agent ask`（`cmd/aos-agent/aos_agent/ask.py` 檔頭與 --help 寫「不配對信名」），history 格式、idle.py 沒動。
- 相關：本檔「aos-agent 沒有 ask」（已解，那條建議裡「用信名配對」的部分就是這條）。
