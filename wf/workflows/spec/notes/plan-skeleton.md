# 新實作計畫（骨架草稿）

> **草稿，spec 出來再對齊。** 這份是在 spec 還沒寫完的時候先擬的骨架，用的依據是 2026-09-05 拍板的 8 條、ideas 13 章、還有 spec 主編交接書裡「spec 會有哪 14 份」那張表。spec 交出來以後，這裡每個里程碑的「依賴哪幾份 spec」要逐條回去對，對不上的就改這份，不是改 spec。

---

## 一、里程碑

八個。每個里程碑做完就是一次「東西真的動了」，不是一份文件。

驗收條件只准三類：**檔案存在**（某路徑上有某檔）、**指令回傳**（打某一行，回傳碼是幾、輸出裡有什麼）、**表格填滿**（某張表每一列都有值）。前兩類機器判得了，第三類判準只有「有沒有填」。

---

### M1 一步走得動

**做完能幹嘛**：在一個資料夾裡打 `aos exec`，它照接力棒讀出下一筆指令、跑掉、把結果寫到指定的地方、推游標；同樣的輸入連跑十次，十次一樣。

**依賴 spec**：`01-terms`、`02-layout`、`04-inst-format`、`05-series-format`、`06-exec-and-run`（只要「一步的精確順序」那半）、`schemas/`（inst batch、series）

**驗收**
- 檔案存在：`.aos/` 版面照 `02-layout` 建起來，接力棒檔在、結果檔落在指令裡寫的那個路徑
- 指令回傳：`aos exec` 回 0；連打三次，接力棒游標從 0 走到 3；餵一份壞掉的接力棒，回非 0 而且訊息指得出是哪一欄壞
- 表格填滿：`14-conformance` 裡屬於 04、05 兩份的「必須」條款，每條有一個測試名字

---

### M2 算到底

**做完能幹嘛**：打一次 `aos run`，它自己反覆走到沒有新指令為止；停了以後看得出為什麼停（走完了／步數用光／逾時／壞了）。

**依賴 spec**：`06-exec-and-run`（整份）、`02-layout`（停止原因檔放哪）

**驗收**
- 檔案存在：停止原因檔在，內容說得出四種停法是哪一種
- 指令回傳：`aos run --step 5` 回 0；空的接力棒立刻停也回 0；步數用光那次回傳碼跟走完不一樣
- 表格填滿：三種走法（固定次數／隔一段時間／到條件）各一列，每列有測試名字

---

### M3 壞了看得見

**做完能幹嘛**：父開一個子資料夾要它做事，做完拿得回結果；子死了、崩了、卡住了，父不用猜，看檔案就知道。

**依賴 spec**：`07-call-and-delivery`、`05-series-format`（成敗判定那段）、`04-inst-format`

**驗收**
- 檔案存在：三態各驗一次——結果檔不在／結果檔在／狀態檔說壞了
- 指令回傳：把子行程 kill 掉，父的 `run` 停在原地並留下停止原因；同一個 id 投兩次，第二次被拒絕而且回報投的人
- 表格填滿：投遞協定那幾步（寫→刷→改名→刷目錄、隨機名、去重）每步一列，每列有測試名字

---

### M4 有人管時鐘

**做完能幹嘛**：看得見現在有哪幾塊地在跑、停得掉其中一塊、daemon 掛掉重開以後對得上帳。

**依賴 spec**：`08-daemon`、`12-cli`（控制面那組）、`02-layout`（控制收件匣）

**驗收**
- 檔案存在：登記表在，欄位跟 spec 對得上
- 指令回傳：`aos daemon ls` 列得出剛起的那塊地；`kill` 掉 daemon 之後子行程還在跑；daemon 重開後 `ls` 的內容跟 kill 前一致
- 表格填滿：重啟對帳表（登記表說在跑／實際在不在／處置）每列有值

---

### M5 LLM 世界

**做完能幹嘛**：任何一塊地要用 LLM，就是往 LLM 那塊地投一筆請求，結果落到請求裡寫的路徑；每呼叫一次記一行帳。

**依賴 spec**：`09-llm-world`、`07-call-and-delivery`（狀態檔）、`11-tools-and-contacts`（部分）

**驗收**
- 檔案存在：請求檔、結果檔、帳本檔各一；帳本一次呼叫一行
- 指令回傳：`aos llm` 四種退出碼各觸發一次（成功、用法錯、後端失敗、被取消），用離線假 transport
- 表格填滿：並行上限與排隊那張表（處理單元、上限、現在幾個在跑）每列有值

---

### M6 一個 agent 就是一個資料夾

**做完能幹嘛**：跑得動第一級順手劇本——待在一個程式碼資料夾裡，全程只打 `aos …`，做完一件小改動；而且停掉、隔天再來，記憶還在。

**依賴 spec**：`10-agent`、`11-tools-and-contacts`、`12-cli`（agent 那組五個子命令）

**驗收**
- 檔案存在：agent 資料夾裡該有的檔都在（限制參數檔、journal、收件匣）；隔天重開，昨天的 journal 還在
- 指令回傳：`say` / `listen` / `talk` / `state` 各回 0，`state` 三種值各出現過一次
- 表格填滿：順手表三欄（多餘的動作／看不見的狀態／錯誤不指路）每條附一個「拿現成 coding agent 做同一件事」的對照

---

### M7 門房第一級＋源碼與編譯器

**做完能幹嘛**：新開一塊地會自己出現在登記表裡，刪掉會自己消失；人寫的源碼 json 有東西幫他編成指令批，寫錯了會被擋下來。

**依賴 spec**：`13-doorman-l1`、`03-source-and-compile`、`08-daemon`（登記表）

**驗收**
- 檔案存在：新建一個 `.aos/` 之後登記表多一列；`rm -rf` 之後少一列
- 指令回傳：編譯器對壞源碼回非 0 並指出哪一欄；對好的源碼回 0 且吐出過 schema 的指令批
- 表格填滿：門房「只記不做」的事件表（偵測到什麼／記在哪／不做什麼）每列有值

---

### M8 量尺

**做完能幹嘛**：有一組固定的工作負載，三支串各跑五次，畫得出成本與結果的分布——「可預測性最優先」這句話第一次有數字。

**依賴 spec**：`14-conformance`、`01-terms`（指標的名字）

**驗收**
- 檔案存在：工作負載目錄在，每支串一個資料夾；跑完的原始紀錄一次一檔
- 指令回傳：整套跑一遍回 0；`14-conformance` 的檢查全套跑一遍全過
- 表格填滿：兩把尺各一張表——「自報 vs 實際」每列有兩個數字；「同一件事跑五次」每列有五個數字

## 二、為什麼第一個里程碑是這個

13 章給了「OS 的第一塊」三個候選（都未裁）：門房第一級的偵測生死、成本帳的薄關口、接力棒格式。M1 選的是**接力棒格式**（連著 `aos exec` 一起做，因為格式沒有執行器就驗不了）。

理由，一句一條：

- **可預測性最優先**，而可預測性今天唯一量得到的兩把尺（自報 vs 實際、跑很多次的分布寬度）都要先有「同一件事跑很多次」這個動作才成立；接力棒＋exec 就是這個動作本身。
- 另外兩個候選都是**觀測器**：門房觀測地的生死，成本帳觀測 LLM 呼叫。第一天做觀測器，會沒有東西可觀測。
- 三個候選裡只有接力棒**今天已經有拍板的答案**（E-01）；另兩個還停在建議預設。做已經拍板的那個，返工的機會最小。
- 13 章自己也寫了「接力棒與批 header 是同一題，該先答」，理由是去重、輸入歷程、串歸屬三條線同時壓在它上面。
- 排序原則就一條：**先把不含 LLM 的那條路整條走通，再把 LLM 接上去**。M1～M4 全程沒有 LLM，所以每一步都可重跑、可比對；LLM 到 M5 才進場，進場的時候底下已經是一條量得出來的基線。反過來排的話，第一天就把不確定性混進基線，之後沒有辦法分辨「這次不一樣」是機器還是模型造成的。
- 門房（M7）排在後面不是因為它不重要，是因為它要觀測的東西（地的生死、登記表）在 M4 才存在。成本帳的薄關口併進 M5，不另立里程碑——它就是一行帳，不值得一個里程碑。

## 三、新實作放哪（已裁：同 repo 新子目錄）

三個選項，各一句利弊。

| 選項 | 好處 | 壞處 |
|---|---|---|
| **同 repo 新子目錄**（例如 `next/`） | spec 就在隔壁 `wf/workflows/spec/`，改 spec 跟改程式同一個 commit，最不容易漂；wf 那套（lint、dispatch、記憶）直接能用 | 舊 `core/` 就在旁邊，很難守住「不准當憑據」；兩套建置系統在同一棵樹裡要小心不要互相汙染 |
| **同 repo 新 branch** | 可以整棵樹重來，舊碼眼不見為淨，隨時 diff 得回去 | spec 在 main 上長，新實作在別的 branch，兩邊要一直同步——這正是 12 章講的「三份真相在漂」；而且這個 repo 是 submodule，`dev-env.md` 記過 worktree 隔離弄丟過四個 commit，多分支平行操作風險偏高 |
| **新 repo** | 最乾淨，舊碼不可能被 include 到；建置系統可以完全重選 | spec、wf 工作流、記憶全在舊 repo，跨 repo 同步是最容易漂掉的一環；使用者那一整套流程要重搭一次 |

**我建議：同 repo 新子目錄，直接長在 main 上。**

理由：最大的風險不是「不小心抄到舊碼」，是「規範跟實作對不上」——12 章整節在講這件事，L-06 還要把「實作閉合就在同一個 commit 回寫文件」立成鐵律。那條鐵律要成立，spec 跟程式就得同一個 repo、同一次 commit 進得去。「不准回頭翻舊碼」是靠規矩守的，不是靠目錄隔離守的。

**標記：要使用者裁。** 這是方向性的，我只擺選項。

## 四、每個里程碑大概什麼隊形

「Opus / Sonnet」照使用者定的規矩：普通工作 Opus、簡單工作 Sonnet。

| 里程碑 | 隊形 |
|---|---|
| M1 一步走得動 | 3 Opus 並行（① 接力棒與指令兩種格式＋schema ② `aos exec` 一步的執行 ③ 測試骨架與 conformance 對照）＋1 Sonnet 收尾對 spec 條款 |
| M2 算到底 | 2 Opus（run 三種走法／停止原因與預算）＋1 Sonnet 跑測試與大小檢查 |
| M3 壞了看得見 | 3 Opus（呼叫記錄與結果落點／狀態檔三態／投遞協定與去重）＋1 Sonnet 對欄位名一致性 |
| M4 有人管時鐘 | 2 Opus（daemon 本體與登記表／控制面與對帳）＋1 Sonnet 做 kill 與重啟的手動劇本 |
| M5 LLM 世界 | 2 Opus（LLM 世界的地與請求格式／假 transport 與四種退出碼）＋1 Sonnet 做帳本格式與檢查 |
| M6 agent | 2 Opus（agent 資料夾形狀與每圈 prompt／五個子命令）＋1 Opus 專門跑第一級劇本並填順手表（這條要真模型，可能得走 WAIT_USER） |
| M7 門房＋編譯器 | 2 Opus 並行且互不相干（門房一隊、編譯器一隊）＋1 Sonnet 驗登記表增減 |
| M8 量尺 | 1 Opus（工作負載與跑法）＋2 Sonnet（跑五次、整理成兩張表） |

通則：每個里程碑最後派 1 個 Opus 從頭讀一遍，找「照這樣下去下一個里程碑會卡在哪」，列 5 條以內。里程碑之間不並行——每一個都踩在前一個的格式上。

## 五、要使用者裁的問題（一行一條）

1. 新實作放哪：同 repo 新子目錄、新 branch、還是新 repo？（我建議子目錄，見第三節）
   → 答：同 repo 新子目錄（F-01）。
2. 語言與建置沿不沿用今天這套（C++23 + CMake + vcpkg）？新實作幾乎都是讀寫 json、動檔案系統、fork/exec、原子改名，別的語言也做得了，而 vcpkg 的 baseline 坑 `dev-env.md` 已經記過一次。這題我不自己定。
   → 答：原型玩完再決定（F-02）。
3. 舊 `core/` 的程式碼，一行都不准抄，還是可以抄不含判斷的那種零件（例如 fork/exec 的封裝）？
   → 答：可抄不含判斷的零件（例如 fork/exec 封裝、原子寫檔）（F-03）。
4. 測試沿不沿用今天的慣例（每個小專案掛 `aos_<專案>_tests`、一律從 repo 根跑 ctest）？
   → 答：沿用（ctest 從 repo 根跑）（F-04）。
5. 第一個里程碑選接力棒＋exec，還是照 M-03 建議預設的門房第一級＋成本帳薄關口？
   → 答：已由「原型直接做接力棒＋exec」決定。
6. 「先玩」跟「動工」的界線畫在哪：這份計畫是取代先玩，還是 M1 做完先去玩一輪、拿玩出來的阻礙回來改計畫？
   → 答：已由「流水線：spec 出一部分就做原型」決定。
7. 新舊兩支 `aos` 執行檔會同時存在一段時間，新的叫什麼名字，還是舊的直接停掉？
   → 答：舊的直接停掉，新的叫 `aos`（F-05）。
8. 那 63 條「預設（未經拍板）」要不要在動工前先批一輪，還是撞到哪條才裁哪條？
   → 答：已由裁決單決定。
9. 里程碑要不要嚴格一個做完才開下一個，還是允許不相干的（例如 M7 的編譯器）提早並行？
   → 答：里程碑不相干的可以提早並行（F-07）。
10. 里程碑的數量與順序本身，這八個對不對？
    → 答：對，照這樣（F-06）。
11. 第一版要不要保留今天的 `modules/` 擴充機制，還是新實作先不做擴充？
    → 答：第一版不做 modules 擴充（F-08）。
12. `.aos/` 放 tmpfs 這個實驗開關，第一版就留，還是等 M7 門房做完再說？
    → 答：第一版就留，預設仍在磁碟（F-09）。

## 六、spec 出來以後的對齊動作

- 「依賴 spec」逐份對回真檔名；spec 若合併或拆分過，這裡跟著改。
- 把 `14-conformance` 整張表拆進八個里程碑，**每一條「必須」都要有里程碑認領**；沒人認領的就是里程碑漏了。
- spec 各檔末尾「待使用者拍板」的清單，跟本文第五節合併去重，變成一張總表交給使用者。
