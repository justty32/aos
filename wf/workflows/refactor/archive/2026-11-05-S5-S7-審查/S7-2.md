## 和 no-pid P1（daemon 的 `lock_fd_` 被不 exec 的子行程繼承）的交集

- **S7 沒有修 P1，也沒有讓它變糟。** `lock_fd_`（`aos-daemon/src/daemon/daemon.cpp:409`，O_CLOEXEC）S7 完全沒碰。子行程走 `run_cli` 跑內嵌單子、不 exec 時，照樣會帶著這個 fd，P1 還是要做。
- S7 沒有新增長時間開著的 fd。新的 `write_text` 都是 O_CLOEXEC，而且當場就關（舊的 fopen 版本沒有 CLOEXEC，算小改善）。`aos-llm ask` 的 `sender.flock` 和改前一樣：O_CLOEXEC，開到行程結束；ask 本身不 fork。
- llm kernel 自己的 `.flock` 鎖：S7 之後 kernel 不再連 aos-exec，行程內沒有 fork／run_inst 的路，所以不會有類似 P1 的問題。
- 文字上的交集只有 `aos-daemon/src/child/child.cpp:147`：`run_child` 裡的 sigset 改成 `aos::caught_signals()`，就在 P1 要加 `close(lock_fd)` 的同一個函式裡，但不是同一段。`run_child` 是 static 函式，P1 要多傳一個參數進去。另外 `caught_signals()` 是在 fork 之後、exec 之前叫的，它只呼叫 sigemptyset／sigaddset，是 async-signal-safe，不違反 fork 前後的界線（同一段裡的 `setenv` 是 S7 之前就有的問題，不在 S7 範圍）。
- P2 會碰 `aos-loop/src/engine/window.cpp`（加 `responded_at`）。S7 改的是同一檔裡的 `write_window`（第 34 行起），P2 改的是寫 state 的內容，預期不會衝突，就算有也只是上下文衝突。
- 結論：照 06 的代定順序走——S7 先併，P1／P2 疊在上面。
