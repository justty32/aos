## 4. 第一輪做了什麼、數字（C 檔、04）

- 問題：
  - **每節約 4.7 萬 token**（全庫外推約 6,800 萬／趟）；已隔離驗證主因是 agent 每次請求帶整份累積歷史：同一題在新實例 1.04 萬、做過 5 題後 2.27 萬，每多做一題多約 2,500。
  - **重跑逐字相同 0%**；溫度 0 無效（第一輪本來就是溫度 0，直接打 API 三次也三種輸出）。

  - 節點 bytes ÷ 原文 bytes 中位 0.94——**改寫後的節點跟原文差不多大，沒有濃縮**；而使用者已裁「內文照原文存」，這套改寫流程整個不再需要。

## 6. 關聯與引用：aos 已經有的、語料現有的（E、F 檔）

- **aos 早就有「檔案路徑＋`#`＋JSON 路徑」**：`{"$ref": "file.json#/a/b"}`（RFC 6901 JSON Pointer，`#` 後必須 `/`，規範 N-45／N-62），`aos-exec cfg.json#/tools/stamp`、`aos-json get FILE#/POINTER`、loop／fsm／daemon／kernel 設定檔都用同一種切法（共用 `aos-util` 的切分函數）。**唯一還沒接上的是知識庫**：`memory` 的節點名是 `a/b`（資料夾路徑），JSON 葉內部尋址註明「這版不做」。
- 語料 `lore` 內的連結：詞條→詞條 352 筆（集中在 relationship_map 260、characters 110、events 83）、詞條→evidence 835 筆（每檔幾乎都有一行「詳見：evidence」）、詞條→索引 116；**指到檔內某段的寫法 0 筆**；`[[…]]` 0。

- 第一輪 40 個節點：節點間連結 0，只有 `## sources` 裡 80 個裸路徑（全部存在）；另有集中別名表 `aliases.json`（126 個中文名／標題／slug → 40 個節點）。
- 也就是說：**語料裡大部分「關聯」是隱性的（文字裡提到名字）**；要變成顯式連結，得先有一張「名字→節點」表（lore 的 1,490 個檔名就是現成的名字清單，可用字串比對，不一定要 LLM），再決定哪些提及值得成為連結（使用者想法 6：別濫用）。這段是隊長的觀察，算待驗的假設。

## 7. 成本基準與 metainfo 現況（H、I 檔）

- **第一輪每節**：3 次 LLM 呼叫（中位）、牆鐘 21 秒（中位，最大 35 秒）、攤提 4.7 萬 token；**拿不到每節的 in／out token**——批次腳本只在每批前後讀 kernel 總帳，kernel 帳只存總 token。並行度最多 2 個 writer 同時在跑。
- **問答 agent 每題**（有完整紀錄）：input 8.7k～33k、output 100～360、calls 3～7、牆鐘 12～30 秒；**input 佔 99%**，output 幾乎可忽略——成本幾乎全在「餵進去的上下文」。cached input 約佔 1/4。
- **美金**：LiteLLM 沒有這些 chatgpt 模型的價目（走訂閱帳號），所以美金算不出來；能用的單位是 token（in／out／cached）、calls、秒。
- aos 本體自動記得的：kernel `used.json` 只有每窗與累計的 calls、總 token，按 endpoint、按寄件人（＝工作區）分；**沒有 in／out 拆分、沒有逐封、沒有時間**；`aos-llm ask` 只回 message、丟掉 usage；kernel 收尾就刪掉每封請求的目錄，事後無法重拆。kernel 文件說缺 usage 記 null，現行程式記 0（文件與實作不一致）。
- **metainfo 現況**：aos 已有 `_metainfo.json`（35 個工具帶），欄位是 `summary`、`time_ms: {val, max}`、`resource`、`side_effect`、`idempotent`、`deterministic`、`interrupt`、`parallel`——**數量值已經是 `{val, max}` 的雙形**，規劃（10-24）說「全選填、其餘 key 自由加」。但沒有任何工具帶 `cost`、`llm_tokens`、`llm_calls`；目前**只有 `time_ms.max` 真的被讀**（agent 的 act 拿它當工具逾時、MCP 拿去當提示），kernel 11-04 起已不讀 metainfo。另有 `_tooldef.json`（給模型看的 description＋JSON Schema 參數＋錯誤代號）。NORMS 裡 `_metainfo` 一節仍標「待定」（M1～M10 已照推薦定、未落條文）；SESSION-LOG 掛著「LLM kernel `_metainfo` 第二步」一條 open。
- 也就是說：使用者想法 5 的「自我宣稱」已有現成的家（`_metainfo.json`，擴欄位即可），「他者觀測」目前沒有家，原料（每封 usage、時間）在 kernel 與 `aos-llm` 兩處被丟掉。

## 8. 分類與 tag 現況（J 檔）

- 語料**沒有任何 tag 欄位**（frontmatter 0、明示 tags／category 欄 0）。現有分類只有：13 個類別資料夾；少數類別的正文固定欄位——events 每條有「分類」（ACTIVITY_STORY 52／MAIN_STORY 18／MINI_STORY 20）、activities「敘事線」、factions「故事定位」、operators「檔案」（代號、性別、出身地、種族）與「戰場定位」；各類 INDEX.md 裡的分組小標（國家、組織、章序等）。

## 8b. agent 能用的工具與上下文量（K 檔）

- aos 現成給 agent 的工具 29 支：檔案類（read、write、edit、view、ls、stat、copy、move、mkdir、trash、json_read、json_edit、aos_json）、執行類（bash、run_python、math、clock）、知識庫（memory、memory_write、memory_export）、**分派類**：
  - `agents`：在同一個 daemon 開子 agent——`op:new` 可**當場寫一份新的 agent 定義**（從既有定義複製再覆寫檔案）並掛上，`op:add` 用既有定義開，`say`／`ask` 跟子 agent 對話；父 agent 只拿到子的最後回答，不拿子的歷史。
  - `thought`：開一個用完即丟的子 agent 做一件事，只回 ≤600 字的短結論，子的工具往返不進父的歷史；可巢狀到孫一層（深度上限 2）。**沒實測過能省多少**。
  - `self_tools`：agent 給自己加減工具，下一輪生效。
  - `claude`／`codex`：把事交給外部 CLI（唯讀）。
- 第一輪 writer 實際只掛 5 支工具（自訂的 `bash_logged`、clock、memory、read、write）。**一次請求的固定成本**：system prompt 3.7 KB＋工具定義 3.0 KB＋任務信約 0.6 KB ≈ 7 KB；但同一個 writer 做到第 30 題時，一次請求帶 180 則訊息、**105 KB**——幾乎全是之前的歷史。
- 問答 agent：system 2.2 KB＋工具定義 1.4 KB；每多一次工具呼叫多約 1.7～2.7 KB（讀到的原文）；7 次呼叫的題目末次請求 12.5 KB。
