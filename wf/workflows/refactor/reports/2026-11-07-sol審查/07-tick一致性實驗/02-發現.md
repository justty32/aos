## 逐條發現

<a id="f1"></a>
### 1. 寫時鐘的 aos-tick 不認空檔，讀的人卻當第 0 格
- **類別**：程式現況｜**嚴重度**：錯誤行為（已實測）
- **檔:行**：`proto8/cmd/aos-tick/bin/aos-tick:44-51`（寫的人）；`proto8/impls/aos-util/src/tick.cpp:90-104`、`proto8/lib/tool_io.py:58-71`、`proto8/py/aos_ws.py:41-54`（讀的人）
- **commit／哪隊**：讀的規則是 `b190e00c0`（T1，T 隊，codex sol 寫碼）；aos-tick 是 T 線之前的舊碼，T1 改讀法時沒有回頭對齊它
- **問題**：
  - 時鐘檔像一張寫著「現在第幾回合」的紙條。讀紙條的三份程式都把「空白紙條」當第 0 回合，這是使用者裁的。
  - 可是負責往紙條上加一的 `aos-tick`，看到空白紙條就報 `ClockBad`、什麼都不寫。
  - 實測：先放一個空的時鐘檔再起 `tick: true` 的 daemon。`_tick` 連失敗 3 次後被留在 `stopped`，6 秒後檔還是空的，表上 `tick` 一直是 0。這棵樹裡所有寫 tick 的期限（inst 的 `timeout_ticks`、stuck、鎖的租約、ask）都永遠不會到期。照 N-65 ②（時鐘停了就不到期、不退牆鐘、不 warning），這是預期中的後果，不會有別的提醒。只有表上的 `_tick` 列看得出來。
  - 同類的小差異還有：只有空白、`5\r\n`、前面有空格，讀的人都收、`aos-tick` 都拒；超過 64 位元的數，`aos-tick` 照寫，讀的人全部 `TickBad`。同一件事有兩個代號（寫的人 `ClockBad`、讀的人 `TickBad`）。
  - 空檔怎麼來：人 `touch`、搬家時手建，或者寫到一半斷電。`aos-tick` 先寫暫存檔再改名，但沒有 fsync，有些檔案系統斷電後會留下 0 位元組的檔。
- **使用者原話**：11-06 選項框「當第 0 格 (Recommended)」，題目是「有設 `AOS_TICK`、檔不在或空」（`proto8/thinking/2026-11/05/tick-time/04-T線實作結果.md:19`）。
- **建議**：可以直接修。讓 `aos-tick` 照讀的人同一套規則讀：先去掉前後空白，空的就當 0。要不要把 `ClockBad` 併成 `TickBad` 是命名題，影響 aos-tick 的錯誤代號表，可以順手問。

<a id="f2"></a>
### 2. tick.interval_ms 明寫 1000 時不往下傳，近的贏破功
- **類別**：設計／程式現況｜**嚴重度**：錯誤行為（已實測）
- **檔:行**：`proto8/impls/aos-daemon/src/daemon/daemon.cpp:71`（`opts.contains("interval_ms") && interval != 1000` 才 setenv）；源頭在 `proto8/thinking/2026-11/06/daemon-board/README.md:35` 推薦欄的「沒寫或＝1000 不設」
- **commit／哪隊**：程式 `d6c38be32`（T7，T 隊，codex sol）；「＝1000 不設」那半句是 `b232c592c`（daemon-board，claude 記的推薦欄）
- **問題**：
  - 實測：根寫 `tick: {interval_ms: 300}`，中層 daemon 寫 `tick: {interval_ms: 1000}`。中層自己的時鐘照 1000 毫秒走（3 秒走 3 格），中層底下的子看到的 `AOS_TICK_INTERVAL` 卻是根傳下來的 `300`。
  - `AOS_TICK_INTERVAL` 是「一格大約多久」的換算表。子拿錯換算表，退牆鐘的期限和給人看的換算都會差 3 倍以上。
  - 這條在 tick-time 04 邊緣 9 已經寫了（「要不要改成『明寫就設』再說」），但沒有帶到使用者面前，現在還是舊行為。
- **使用者原話**：「設，近的贏」（`proto8/thinking/2026-11/06/daemon-board/README.md:30`，題目是「`tick.interval_ms` 寫了，要不要連 `AOS_TICK_INTERVAL` 設給子樹」）。「＝1000 不設」是推薦欄裡 agent 補的細節，原話只說「寫了就設」。
- **建議**：
  - A（推薦）：改成「明寫就設」，寫了 1000 也設。daemon.cpp 那一行拿掉 `!= 1000` 就好，最貼原話字面。
  - B：維持現狀，在 N-28 與 daemon docs 寫明「明寫 1000 等於沒寫，會沿用上層的值」。代價是寫的人以為自己設了，其實沒設。

### 3. null 在三處意思不同
- **類別**：程式現況｜**嚴重度**：錯誤行為（已實測）
- **檔:行**：`proto8/lib/agent/thought/_entry:214-218`、`proto8/lib/agent/agents/_entry:446-450`（用 `"timeout_s" in args` 判斷有沒有給）；對照 `proto8/impls/aos-exec/src/inst/fields.cpp:88-104`（`null`＝沒給）、`proto8/py/daemon_ctl/post.py:138`（`None`＝沒給）
- **commit／哪隊**：`a858fe1a0`（T6，tick 隊，codex sol）
- **問題**：
  - 實測：thought 收到 `{"timeout_s": null, "timeout_ticks": 2}` 報「兩個互斥」；只給 `{"timeout_ticks": null}` 報「必須是正整數」。agents 的 `ask` 也一樣。
  - 同樣的寫法在 inst 單子裡照常跑，因為 C++ 那邊把 `null` 當成沒寫。`daemon_ctl.ask` 也把 `None` 當沒給。
  - 腦（LLM）呼叫工具時，很常把選填欄位送成 `null`。這時它想用 tick 等待，卻會被擋下來。
  - 這跟 [01-設定檔](../01-設定檔.md) 第 3 條（`tool_io` 不把 `null` 當沒給）是同一個根，只是這次出現在 tick 的互斥檢查。
- **使用者原話**：沒找到針對 `null` 的原話，這是推論。相關的原則是 KISS 的「寫什麼就做什麼——給的值照字面用」（`wf/workflows/common/conventions.md:11`），而設計表寫的是「兩種都寫＝擇一」（`proto8/thinking/2026-11/05/tick-time/03-11-06-裁定與新設計.md` § 二）。
- **建議**：統一成「`null`＝沒給」（推薦），跟 inst、daemon_ctl 一致。最好在 `tool_io` 讀參數時一次處理，跟 01 第 3 條一起修。
