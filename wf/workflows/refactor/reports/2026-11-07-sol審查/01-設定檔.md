## 這區白話總結

大部分設定檔是乾淨的：S5 搬夾是純搬移，相對路徑全都還對；29 份工具登記檔都是合法 JSON，`errors` 清單跟程式真的會丟的代號逐支比過，一個不差；試驗場照使用者的選擇，領班和總機的鐘都留著。

真正有問題的集中在三處，都是「各自看沒錯，接起來會出事」。第一，根 daemon 的 systemd 範例：daemon 一當掉，systemd 會連子程序一起殺掉，跟「根當掉後重起、把活著的子接回來」的設計相反。第二，金鑰改成歸端點小 proc 之後，LiteLLM 三個端點一定要有 `LITELLM_KEY`，可是試驗場、env.sh、systemd 範例都沒有設它，所以實跑必定 `EndpointFailed`。第三，工具登記檔寫了 `default`，但共用模組只拿它來印說明。腦把選填欄位送成 `null` 時（很常見），工具會直接報錯，`AOS_THOUGHT_FROM` 這個預設也就被蓋掉了。

## 最該先處理的 3 條

1. 錯誤行為（待確認）：`proto8/impls/aos-daemon/examples/root/aos-root.service:15` 的 `KillMode=mixed`，daemon 當掉時子程序會被一起殺掉。
2. 錯誤行為（已實測）：`proto8/kernel/llm-kernel/endpoints/litellm/_entry:2` 一定要有 `LITELLM_KEY`，但沒有任何地方設它，三個 LiteLLM 端點都會失敗。
3. 錯誤行為（已實測）：`proto8/lib/tool_io.py` 收到 `null` 不當成「沒給」，`from: null` 會蓋掉 `AOS_THOUGHT_FROM` 預設。

### 1. systemd 範例的 `KillMode=mixed` 會在 daemon 當掉時殺掉所有子
- **類別**：設定檔｜**嚴重度**：錯誤行為（待確認）
- **檔:行**：`proto8/impls/aos-daemon/examples/root/aos-root.service:13,15`；`proto8/impls/aos-daemon/examples/root/README.md:29`
- **commit／哪隊**：`57e55e650`（P8，sol）
- **問題**：
  - `aos-exec` 會用 exec 把自己換成 aos-daemon，所以 systemd 盯的主程序就是 daemon。daemon 的子程序都在同一個 cgroup 裡（cgroup 可以想成 systemd 替這個服務圈起來的一組程序）。
  - 主程序意外結束時，systemd 要先把整個 cgroup 清空才會照 `Restart=always` 重起。除了 `KillMode=process`，其他設定都會把剩下的子程序殺掉。
  - 可是 `impls/aos-daemon/docs/10-根daemon.md:20` 寫「根 crash 後重起與普通 daemon 相同：從自己的 stack 接回活列」。放在 systemd 底下，接回的時候子早就死了，正在跑的工作會全部重跑。
  - README:29 只說「與 daemon crash 後接回不同，按需要調整」，沒有講清楚後果。
  - 沒有實測：沙箱連不上 user bus（P8 自己也記了沒驗）。上面的推論是照 systemd.kill 手冊的規則。
- **建議**：這題要問使用者，因為兩個選項各有代價。
  - A（推薦）：改成 `KillMode=process`。daemon 當掉時子程序留著、可以接回；代價是 `systemctl stop` 的 60 秒期限到了，systemd 也不會替你收掉沒走的子。
  - B：維持 `mixed`，README 寫明「在 systemd 底下，根當掉＝整棵樹重跑」。
  - 不管選哪個，家機有 user bus，都可以 `kill -9` 根實測一次。

### 2. LiteLLM 端點一定要 `LITELLM_KEY`，但沒有任何地方設它
- **類別**：設定檔｜**嚴重度**：錯誤行為（已實測）
- **檔:行**：`proto8/kernel/llm-kernel/endpoints/litellm/_entry:2`；`proto8/kernel/llm-kernel/kernel.json:6,12,14`；試驗場 `~/code/playground/env.sh`、`README.md`；`aos-root.service:9`
- **commit／哪隊**：`02edef8f5`（E1，N 隊，sol）
- **問題**：
  - 使用者原話：「金鑰應該由那個小proc自己保管，我們在定義那個小proc的時候就要跟他說讀哪個環境變數當金鑰了」。範本照字面做了，這部分沒錯。
  - 但 E1 之前的範本，smart-high 根本沒有 key，是直接不帶金鑰打 LiteLLM。改了之後，`llm_http` 只要沒設這個變數就報 `EndpointFailed`。
  - 我在 scratchpad 起了範本 kernel 實測：fake 端點退 0；smart-high 回 `EndpointFailed environment variable LITELLM_KEY (--key-env) is not set`。
  - 家機的 shell 設定檔、試驗場 `env.sh`、試驗場 README、systemd 範例都沒提這個變數。kernel docs/01:56 說「值只在起 llm daemon 的 root 殼 export」，可是 systemd 底下沒有那個殼，`AOS_LLM_KERNEL` 一樣不會有。
- **建議**：
  - 試驗場 README 和 env.sh 註解補一行「用真腦前先 `export LITELLM_KEY=…`；LiteLLM 沒設金鑰的話隨便給一個值」。
  - systemd 範例加 `EnvironmentFile=%h/aos/root.env`（金鑰和 hub 變數都放這份），README:11 的「先改…」也要列出 hub 變數。

### 3. 選填欄位送 `null` 會被拒，schema 寫的 `default` 等於沒用
- **類別**：設定檔（工具登記）｜**嚴重度**：錯誤行為（子 agent 已實測）
- **檔:行**：`proto8/lib/tool_io.py`（`arguments()`）；`proto8/lib/agent/thought/_entry:187,214`；`proto8/lib/agent/agents/_entry:438-449`；條文 `proto8/lib/docs/01-分層等/02-規則5a至11與引用.md:8`（規則 9：null＝沒給）
- **commit／哪隊**：J2 `85f22b2a3`（sol）、T6 `a858fe1a0`
- **問題**：
  - tool_io 對 `null` 只是不驗型別，不會把它拿掉；各工具自己寫的檢查又一律把 `null` 當成給了一個壞值。
  - 實測結果：
    - thought 給 `"from": null`，回 `ArgumentsBad`，工具登記格裡 `env.AOS_THOUGHT_FROM` 的預設被蓋掉（`7cfdccf00` 才剛做的功能）。
    - 給 `"timeout_s": null` 加 `timeout_ticks`，回「兩個不能同時給」。
    - ls、bash、json_read、json_edit、self_tools、agents 的 `on_queued` 也都一樣。
  - OpenAI strict 模式常把沒填的選填欄位送成 `null`，所以這不是罕見情況。
  - 另外，`default`、`errors`、`env` 三欄 tool_io 只拿來印 `--help`，不會替工具補預設值，這點沒有地方寫明。
- **建議**：問使用者。
  - A（推薦）：在 tool_io 統一處理，型別驗完後把值是 null 的鍵拿掉（符合「只改共用介面」）。schema 沒寫 `type` 的鍵不拿，例如 aos_json 的 `value`，因為對它來說 `set` 一個 null 是合法操作。
  - B：各工具自己改。
  - C：改條文，改成「null 等於給了」。
