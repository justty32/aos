## special-cases

六題裁定的「選項字面」都有落進條文、出處都掛「使用者 11-06 選項框」；題 4「等撞名再說」確實沒寫（docs 裡 grep 不到 `_` 保留的規則，daemon 只在 `tick.name` 真撞到 procs 時才 `CfgBad`）。毛病是三處「寫得比使用者選的多」：升格門檻寫成四條通用規矩、公開介面的定義多塞了「README 寫明的」、K1 判準的讀者清單多了「看表的人」——都是把 04 草稿裡使用者沒被問到的部分，掛在「使用者選項框」名下寫進去。

### 1. 升格門檻：使用者只選「第 3 次升格」，條文寫成四條規矩並擴到「條文與程式裡所有一般規則＋例外」
- **類別**：代定｜**嚴重度**：方向性代定（輕：方向跟使用者一致，但範圍與條數是 agent 定的）
- **檔:行**：`proto8/docs/CONCEPTS/01-設計理念/03-續-C-52-例外.md:31-38`（標題「使用者 11-06 選項框「第 3 次升格」…不只 C-52，條文與程式裡所有「一般規則＋例外」都照這幾條：1 認名型第一次就消 2 第 3 次升格 3 清單 5 項或 3 天 2 項 4「先不做」要寫等什麼」）；`wf/workflows/common/conventions.md`「特例」那行同樣掛「使用者 11-06 選項框」
- **commit／哪隊**：`c56e53751`（K 隊；條文是 sol 寫）
- **問題**：05 題 6 問的是「升格判準的數字（判準 2、4）」，推薦項 A 是「第 3 次升格、清單到 5 項或 3 天加 2 項就改寫」——所以規矩 2、3 的數字算使用者裁的。規矩 1（認名型第一次就消）跟題 1「不認身份」同方向、勉強算；規矩 4（「先不做」要寫等什麼）是 04 的判準 5，沒問過使用者。再加上一句「不只 C-52，…所有一般規則＋例外都照這幾條」，把一題「數字」的裁定寫成了全 repo 的工作規矩。
- **使用者原話**：「6. 升格門檻 →「第 3 次升格 (Recommended)」」（`proto8/thinking/2026-11/06/special-cases/README.md` 使用者裁定）
- **建議**：直接修：規矩 4 標「（04 判準 5，fable 推薦、沒問）」；「不只 C-52…」那句改成「C-52 的例外表照此；其他條文要不要照辦，等有第二張例外表再說」。要不要把它變全 repo 通則擺給使用者：A 變通則（推薦，規矩本身合理）、B 只管 C-52。

### 2. 「公開介面」的定義多塞了「README 寫明的檔名與格式」，比使用者看的選項寬
- **類別**：代定｜**嚴重度**：方向性代定（會決定以後什麼算耦合）
- **檔:行**：`03-續-C-52-例外.md:13`（「公開宣告的介面（對外標頭、schema、`interfaces.json`、README 寫明的檔名與格式）」）
- **commit／哪隊**：`c56e53751`（K 隊 sol）
- **問題**：05 題 1 推薦項 A 寫的是「公開宣告的介面（標頭、schema、`interfaces.json`）」。條文多了「README 寫明的檔名與格式」——任何程式在 README 提到自己的檔名就算公開了，等於把「認內部檔名」這種耦合用一句 README 就洗白，跟規矩 1「認名型第一次就消」的力道相反。用比喻：原本說「只能走正門」，條文改成「門牌上寫過的側門也算正門」。
- **使用者原話**：「1. C-52 讀法 →「不認身份、可認公開介面 (Recommended)」」（special-cases README）；選項正文「上層可以依賴下層**公開宣告**的介面（標頭、schema、`interfaces.json`）」（`05-衝突與方向題.md` 題 1）
- **建議**：擺給使用者：A（推薦）刪「README 寫明的檔名與格式」，公開介面只有三種：標頭、schema、`interfaces.json`——要公開就宣告；B 留著，但補一句「README 寫明的要同時在 `interfaces.json` 宣告才算」。

### 3. K1 判準的讀者清單從草稿的「外部 agent、腦、寄信方」多了「回信的收件人、看表的人」，為的是把 daemon `reason` 納進判準
- **類別**：代定｜**嚴重度**：品質
- **檔:行**：`03-續-C-52-例外.md:14`；表 `:24`（⑦ aos-daemon「給看表的人、`aos-daemon-ctl`」）
- **commit／哪隊**：`c56e53751`（K 隊 sol）
- **問題**：04 的 K1 草稿說讀者是「外部 agent、腦，或回信的收件人；aos 內部上下層之間不適用」。條文把「看表的人」加進去，daemon 把 proc 的 `stderr.txt` 末行接進表上 `reason` 就合了判準。這本來就是 11-05 之前的既有行為，列進表沒錯，但判準文字被改寬了沒說。
- **使用者原話**：「2. 例外表 →「改成判準＋現行表 (Recommended)」（K1）」
- **建議**：直接修：`:14` 註一句「「看表的人」是寫條文時為納入 ⑦ 加的（K 隊）」；或把 ⑦ 改成「既有行為，不經判準」。

### 4. C-81 K7 條文比選項多一句「或外人是起它的、它還沒開跑」
- **類別**：代定｜**嚴重度**：品質
- **檔:行**：`proto8/docs/CONCEPTS/03-基礎設施/02-資料夾程式-工作區與-stack.md:21`
- **commit／哪隊**：`c56e53751`（K 隊 sol）
- **問題**：使用者選的字面是「宣告過的覆蓋層可寫」、其他「經信箱或 ctl」；「起它的那方在它開跑前可寫」是 04 的 K7 草稿裡的第二個口子。實務上 `ctl add` 寫子 stack 本來就這樣、不加這句 ctl add 會變違規，所以句子合理，只是出處該標草稿而不是選項框。
- **使用者原話**：「5. 別人的 stack →「宣告過的覆蓋層可寫 (Recommended)」（K7）」
- **建議**：直接修：加「（第二個口子是 04 K7 草稿，沒問）」。
