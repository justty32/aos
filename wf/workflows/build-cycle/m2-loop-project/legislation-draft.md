### 2.1 A 區：機器模型（接在 §A-6 之後）

```markdown
- **§A-7 loop 的職權判準** `(planned, M2)`：一件事歸**回合層**（loop）的**充要條件**
  是——**它必須在沒有任何 inst 可跑的時刻運作**。歸回合層的事項以下表**窮舉**；
  **判準與表衝突時以表為準**（判準用來裁未來的新事項，表是已拍板的內容）：

  | 歸回合層的事項 | 為什麼它必須在沒有 inst 可跑的時刻運作 |
  |---|---|
  | claim（fetch） | 沒有取件就沒有任何可跑的 inst |
  | decode 調度 | 「這一批何時被解析」這個決定本身不在批內 |
  | execute 調度 | 「這一批何時開始跑」這個決定本身不在批內 |
  | writeback | 批已跑完、`.runi` 尚未釋放，此刻沒有下一批可跑 |
  | 睡眠／退避 | 定義上就在沒有工作的時候運作 |
  | 控制窗口（§A-8） | 必須在回合**之間**醒著 |
  | 崩潰偵測 | 前一回合沒跑完（`.runi` 殘留）時運作 |

  表以外的一切 **MUST NOT** 寫成回合層的 C++，**MUST** 做成**系統 inst**（跑在這台
  機器上的 OS——已擁抱指令可寫指令，系統軟體就用這個 ISA 自己寫）。三條推論：
  ① 跨資料夾排程屬 OS 層，`aos exec` 與 `--loop` 的介面 **MUST** 是「推進**這一個**
  資料夾」、**MUST NOT** 是「跑這一組資料夾」；② 中斷／doorbell 歸回合層（它必須在
  回合之間醒著＝真硬體）——**本條只裁歸屬，不要求實作**；③ 回合歷史 **MUST NOT** 是
  回合層的 C++，歸系統 inst。
  **代價認列**：系統 inst 需要「彙整層注入策略」——那是**一個**新機制換掉 N 個 loop
  功能，本階段不做；在它到位之前，回合層崩潰後人手上只有一個 `.runi`、沒有它為什麼
  死的資訊。
  來源：loop §25（第十輪）；core-layering「次外圈 `exec_loop`」；verdicts B6（就此
  裁掉）＋C 表「沒有中斷線」（歸屬）；M2 spec 裁決 1，裁於 2026-08-28。
- **§A-8 控制窗口** `(planned, M2)`：回合週期 **MUST** 有一個明確的**控制窗口**
  相位——**起於 writeback 完成、止於下一次 fetch 開始**，**包含**其間的睡眠與退避。
  外部介入 **MUST NOT** 依賴手快：回合層 **MUST** 在每一次控制窗口內至少檢查一次
  控制面（§G-7），**SHOULD** 在進入睡眠之前與離開睡眠之後各檢查一次（只檢查一次的
  話，`stop` 的最壞延遲會多加一整個間隔）。**回合進行中 MUST NOT 檢查**——「跑完
  當前回合才停」由此得到機械保證。
  **控制面 MUST 不依賴任何 inst 能跑**：這台機器可能正處於沒有任何 inst 可跑、或
  inst 全部跑不動的狀態，控制面在那些時刻仍 **MUST** 有效。（**理由要照這樣寫**：
  掃一個收件匣本身其實做得成一筆 inst，它做不成的真正原因是「必須在沒有回合可跑時
  運作」，不是「本質上做不成 inst」。）
  來源：loop §26（第十輪，「回合邊界在協定上存在、在時間上不存在」）；M2 spec 裁決 2，
  裁於 2026-08-28。
```

### 2.2 G 區：**新開**（整區照貼，接在 F 區之後、「已知未決」附錄之前）

```markdown
## G 執行語意（回合層 loop）

- **§G-1 四階段管線** `(planned, M2)`：一回合 **MUST** 由四個相位依序構成——
  **fetch**（彙整＋取件，§D-1）→ **decode**（讀取整批＋指示詞求值，§C-2／§C-4）→
  **execute**（依 §A-2／§A-5 執行整批）→ **writeback**（算出批次彙總狀態、寫 header
  `result`、釋放 `.runi`、遞增 `turn`）。這四個名字是**規範用語**，其他文件與程式碼
  **MUST** 用同一組名字稱呼它們。
  **指示詞求值屬 decode、MUST NOT 屬 execute**：整批在任何一筆執行之前完成全部求值
  （§A-3 的同一條約束）。exec 層 **MUST NOT** 被要求承擔任何一個相位的調度（§A-6）。
  來源：verdicts B4「四階段管線沒被命名」；cpu-analogy「exec 是指令、exec_loop 是取指
  與控制流」；M2 spec 做完之後長什麼樣 3，裁於 2026-08-28。
- **§G-2 writeback 與批次彙總狀態** `(planned, M2)`：回合層 **MUST** 為每一個跑完的
  批次算出一個**彙總狀態**，值域**恰好四個**（§C-8 `result` 欄的值域在此定義）：

  | 值 | 意義 |
  |---|---|
  | `ok` | 這一批被完整推進，且沒有任何一筆失敗 |
  | `partial` | 這一批被推進，其中有些筆失敗、有些筆成功 |
  | `failed` | 這一批被推進，但**批次內容**整個失敗（整批解析失敗、指示詞求值失敗、或每一筆都失敗） |
  | `machine_failed` | **這台機器本身**出問題，批次沒能被正常推進 |

  彙整層寫出 header 時 `result` **MUST** 是 `null`（它不可能知道結果），連同上表共
  五態；`null` 的意思是「尚未 writeback」。
  **判準 MUST 建立在回傳值的分層上**：回合層自身的失敗（世界進不去、`.aos` 壞、版面
  版本不認得、彙整失敗、取件失敗、釋放失敗、`turn` 遞增失敗、`fork`／`waitpid` 失敗、
  寫 `exit` 檔失敗）＝ `machine_failed`；**批次內容的失敗**（整批 JSON 解析失敗、
  指示詞求值失敗、子行程跑壞）＝ `failed`／`partial`，**MUST NOT** 算成
  `machine_failed`。**逾時 ＝ 一次已完成的執行 ＝ 成功的 slot**（§G-6、§D-9 碼 0 的
  既有涵蓋），**MUST NOT** 為它新增第五個值；**空批次**（§C-2 合法的 `[]`）＝ `ok`
  （它被消化掉、`.runi` 釋放了、`turn` 前進了，那就是進展）。
  **寫回的時點**：**MUST** 在 execute 完成之後、`release_instruction`（刪 `.runi`）
  **之前**——現場還在的時候寫。寫回**之前** **MUST** 先讀回 header 的 `id` 與自己
  這一批比對，**不符 MUST NOT 寫**、只記一行 warning（防第二支 `aos exec` 在本批還在
  跑時發布新批並覆蓋 header，使 `result` 寫到別人的檔上）。寫回失敗 **MUST NOT** 讓
  這一回合失敗，記 warning 即可（比照彙整層 header 寫入失敗的既有取捨）。
  **退避的判準 MUST 來自回合層自己剛算出的這個狀態，MUST NOT 要求先讀回 header**
  ——寫 header 是為了**可觀察性**與交棒給後續階段（header sidecar 會被下一輪彙整覆蓋，
  保存期很短）。
  來源：§C-8（`result` 欄「值域於 M2 定義」）；loop 第 6／15 條；M2 spec 裁決 4＋
  plan 裁-5／裁-6／裁-7／裁-9b；M3 規劃隊轉來的 header 雙 writer 實測，裁於 2026-08-28。
- **§G-3 節流與退避** `(planned, M2)`：節流的判準 **MUST** 是「**有沒有進展**」，
  **MUST NOT** 是「有沒有做事」。三種圈的處置**窮舉**如下：

  | 這一圈 | 判準 | 睡多久 | 退避狀態 | 庫層失敗計數 |
  |---|---|---|---|---|
  | **有進展** | `result` ∈ {`ok`,`partial`} | **不睡**，立刻進下一圈 | **MUST** 重置 | **MUST** 歸零 |
  | **空回合** | 這一圈沒取到批次 | **MUST** 睡**基數**（不是當前退避值） | **MUST NOT** 遞增，**MUST NOT** 重置 | 不變 |
  | **無進展** | `result` ∈ {`failed`,`machine_failed`} | **MUST** 睡當前退避值 | **MUST** 遞增 | 僅 `machine_failed` 遞增（§G-5） |

  退避 **MUST** 是指數的、**MUST** 有上限：**基數 ＝ `--loop` 的間隔本身**（`--loop 0`
  已依 §G-4 下限化）、**倍率 2**、**上限 `max(間隔, 60000)` 毫秒**。退避是**乘在既有
  間隔上**的，`--loop <ms>` 的語意 **MUST NOT** 因此改變。
  **「這一圈有沒有取到批次」（實作上的 `did_work`）MUST NOT 單獨決定睡不睡**——它只
  用來分辨「空回合」與其他兩種圈。
  **空回合那一列是規範的一部分，不是實作細節**：空閒不是故障；把空閒算成無進展會讓
  一個閒置世界退到上限，新投遞要等一分鐘才被看到。
  來源：loop 第 14／21 條（失敗關掉唯一的節流閥、`did_work` 語意錯位）；verdicts D 表
  「失敗算有做事」；M2 spec 裁決 4＋plan 裁-8，裁於 2026-08-28。
- **§G-4 睡眠語意與 `--loop 0`** `(planned, M2)`：`--loop <毫秒>` 的間隔**只用於空閒
  與無進展的圈**（§G-3）；有進展時 **MUST NOT** 延遲下一圈。
  **`0` MUST NOT 忙碌輪詢**：沒有工作時 **MUST** 至少睡一個最小間隔。現行行為＝印一行
  warning 並視為 **1 毫秒**，本條照實立法——**條款規定的是行為，不是常數的來歷**。
  「沒工作就不燒 CPU」是規範，睡眠只是目前的實作手段：事件驅動（inotify 之類）
  **MAY** 在未來取代它，**語意不變**。
  來源：loop 第 13 條（`--loop 0` ＝ 文件唯一示範的用法，而它是忙碌輪詢）；verdicts
  D 表；`run.cpp` 現行行為（warn ＋下限化）；M2 spec 裁決 3＋plan 裁-8b，裁於
  2026-08-28。
- **§G-5 庫層失敗的計數與停機** `(planned, M2)`：回合層 **MUST** 對 `machine_failed`
  **計數**，**MUST NOT** 無聲丟棄任何一次（現行「只認 `3`、其餘整個丟掉」是缺陷，不是
  取捨）。**連續 10 次** `machine_failed` **MUST** 停機：**MUST** 在 stderr 印出連續
  次數與最後一次的 errno，並以**退出碼 4**（§D-9）返回。
  計數 **MUST** 只數 `machine_failed`，**MUST NOT** 數 `failed`／`partial`——一批指令
  永遠跑不成是使用者的問題，為它停機會打壞正當用法。**有進展** **MUST** 讓計數歸零；
  **空回合** **MUST NOT** 影響計數。本條只在 `--loop` 模式出現：單次 `aos exec` 的
  一次庫層失敗仍是退出碼 1。
  來源：loop 第 15／20 條（loop 忽略除 3 以外的回傳值；fork bomb 滿速無聲自我惡化）；
  M2 spec 裁決 4＋plan 裁-9，裁於 2026-08-28。
- **§G-6 計時與砍行程的所有權** `(planned, M2)`：`timeout_ms` 的**值**仍住在 inst
  schema（§C-3 不動，§F-1 **MUST NOT** 因本條遞增——這是**語意搬遷**，不是格式修改），
  **計時與砍行程 MUST 由回合層執行**。
  exec 層 **MUST NOT** 自帶計時：`aos::execute()` 與 `aos_instruction_execute()`
  **MUST NOT** 施行 `timeout_ms`，**MUST** 阻塞至子行程自行結束。這是一次**已釋出
  API 的行為變更**，**MUST** 在 C ABI 與 C++ API 的文件中明寫；`ExecResult::timed_out`
  **MUST NOT** 移除（ABI 凍結），改由回合層填寫。
  砍法照現行行為立法：期限到達時 **MUST** 對子行程的**行程群組**送 `SIGTERM`、給一段
  寬限期、若直接子行程仍存活 **MUST** 對該群組送 `SIGKILL` 並收屍。**逾時 MUST 算成
  一次已完成的執行**（§G-2 的成功 slot、§D-9 碼 0 的既有涵蓋不變）。
  來源：verdicts A 表「`timeout_ms` 移出最內圈」；core-layering「超時由誰動手砍」；
  `exec.cpp` 現行行為（SIGTERM → 寬限 → SIGKILL）；M2 spec 裁決 5＋plan 裁-1／裁-3，
  裁於 2026-08-28。
- **§G-7 控制面：control inbox** `(planned, M2)`：控制這台機器 **MUST** 走投遞協定
  ——「控制機器」與「對它下指令」同構。回合層 **MUST** 持有一個 **control inbox**：
  **`.aos/control.tempd/`**（§B-1 的 `.tempd` ＝投遞匣資料夾，§B-2 的版面樹）。
  **MUST NOT** 另開 signal／pid 檔的 ad-hoc 通道（既有的訊號收尾見 §G-8，不擴充）。
  - **記錄格式**：一份控制記錄 **MUST** 是**恰好一個 key** 的 JSON 物件
    `{"op":"<動詞>"}`，值 **MUST** 是字串。多於或少於一個 key、值不是字串、JSON 不
    合法，一律無效。控制記錄 **MUST NOT** 走 inst 的格式層（`op` 過不了 §C-6 的
    schema，而讓格式層長出第二套 schema 違反 §A-6）。**v1 MUST NOT** 有
    `version`／`id`／`ts` 欄位——擴充點是 `op` 本身（不認得的動詞硬失敗、不猜，
    §C-5 的同一條哲學）。
  - **這個匣不彙整**：`.aos/control.json` **MUST NOT** 存在——控制記錄逐筆消化，
    **MUST NOT** 被併成一份批檔，**沒有** `.runi`、**沒有**取件鎖。（這是與
    `inst.tempd/` 的刻意不對稱，寫在條款裡是為了擋住「順手讓它比照 `inst` 推導路徑」
    的改動。）
  - **投遞**：檔名與發布比照 §D-2（唯一檔名、先寫 `.temp` 後 `rename`）。順序不保證，
    投遞者 **MUST NOT** 假設任何順序。
  - **消化**：回合層 **MUST** 在控制窗口（§A-8）掃描這個匣；一次掃描 **MUST** 消化
    掉當時所有認得的記錄。處理完 **MUST** 以 `unlink` 刪除該記錄（比照「發布成功後
    才刪投遞」），**MUST NOT** 改名成新的狀況字（§B-1 的狀況清單是封閉的）。
    **刪除 MUST 先於退出。**
  - **無效記錄**：格式壞掉、或 `op` 不認得 → **MUST** 就地改名加 `.bad` ＋ 噴 warning
    ＋ **繼續跑**（§D-4 的處置、§D-8 的清理歸屬：**MUST NOT** 自動刪，歸人或
    `aos recover`）。**MUST NOT** 把無效記錄當成任何動詞。
  - **v1 的動詞集合封閉為一個**：**`stop`** ＝ **跑完當前回合後停下，退出碼 0**。
    `step`／`hold` 不在本階段。**本條 MUST NOT 新增子命令**：控制記錄用檔案協定直接
    寫，文件給可複製的範例。
  - **消費語意是 at-least-once**：回合層若崩在「讀到 `stop`」與 `unlink` 之間，下次
    啟動會**再停一次**。`stop` 是冪等的，所以不會壞事；**條款照實寫，MUST NOT 假裝

  來源：loop §26（第十輪）；M2 spec 裁決 2＋plan 裁-10／裁-11／裁-12；§D-2／§D-4／
```

## 三、`format.md`／`usage.md` 的 timeout 段落怎麼改

裁決 5 讓 `aos::execute()`／`aos_instruction_execute()` **不再施行 `timeout_ms`**，
於是兩份文件裡**拿 timeout 當論證或範例**的地方會變成自打嘴巴或無聲的陷阱。
逐段列出（**檔名＋段落標題＋原句**）與改法。**原句以套用當下的檔案為準**；若已被別隊
動過，只套用「改法」的意圖。

### 3.1 `core/inst/docs/format.md` — 段落標題「**驗證狀態**」

**原句**（未知 key 為什麼要拒絕的那段）：

> 未知的 key 是刻意拒絕的，而不是忽略。否則較舊的執行檔
> 可能會默默執行一筆含有較新安全欄位（例如
> `timeout_ms`）的記錄，卻完全沒有 timeout。拒絕也能把像
> `"stdou"` 這樣的拼寫錯誤變成明確的失敗，而不是默默失去重導向。

**為什麼非改不可**：搬遷之後，「執行一筆含有 `timeout_ms` 的記錄卻完全沒有 timeout」
**正是 `aos::execute()` 的規定行為**（§G-6）。這段是 SPEC §C-5 的理據來源，論證垮掉
會連累條款的可信度。**§C-5 條文本身不動**，改的只是這份說明文件的例子。

**改法（建議案）**——換成不依賴 `timeout_ms` 的既有欄位，論證強度不變：

> 未知的 key 是刻意拒絕的，而不是忽略。否則較舊的執行檔
> 可能會默默執行一筆含有它不認識的重導向欄位（例如一份指定了 `stderr` 的記錄，
> 而舊執行檔只認得 `stdout`）的記錄，把本該落到檔案裡的診斷輸出漏回呼叫端。
> 拒絕也能把像 `"stdou"` 這樣的拼寫錯誤變成明確的失敗，而不是默默失去重導向。

**改法（備案）**——保留「未來欄位」的形狀，但把例子改成假想欄位並指向版本機制：

> 未知的 key 是刻意拒絕的，而不是忽略。否則較舊的執行檔
> 可能會默默執行一筆含有較新安全欄位（例如將來某個格式版本才加入的資源上限欄位）
> 的記錄，卻完全沒有那道限制——這也是格式版本住在批 header 的理由（SPEC §F-1）。
> 拒絕也能把像 `"stdou"` 這樣的拼寫錯誤變成明確的失敗，而不是默默失去重導向。

> **MUST NOT** 再用 `timeout_ms` 當這段的例子（不論哪個案）。

### 3.2 `core/inst/docs/format.md` — 段落標題「**綱要(schema)**」

**原句**：

> 寫回仍是同一個物件，解析後才輸出實際字串。`env` 的 key 與 `timeout_ms` 不接受

**改法**：**不動**。這句講的是「哪些位置不接受指示詞」（SPEC §C-4），與施行者是誰無關。
同節的完整範例記錄（含 `"timeout_ms":5000` 的那一行 JSON）也**不動**——它示範的是
**格式**，不是執行語意。

### 3.3 `docs/usage.md` — 段落標題「**`aos init` 與 `aos exec` —— 初始化並推進一回合**」（loop 說明那段）

**原句**：

> 間隔只用於空回合：有工作時會立刻進下一輪；沒有 instruction 或可彙整投遞時才等待。
> `--loop 0` 合法，但會 busy poll。回合回 0 或 1 都會繼續（1 的診斷已印到 stderr）；
> 遇到既有 `.runi` 則停止並回 3。

**為什麼非改不可**：驗收條件 6 明文要求 `docs/usage.md` **不再出現「busy poll」字樣**；
而且「回合回 0 或 1 都會繼續」在 §G-5 之後不再為真（連續 10 次庫層失敗會停機回 4）。

**改法**：

> 間隔用於**空回合與沒有進展的回合**：有進展時會立刻進下一輪；沒有 instruction 或
> 可彙整投遞時睡一個間隔；一批**全失敗**或機器本身出問題時**指數退避**（倍率 2，
> 上限 `max(間隔, 60 秒)`），有進展就重置（SPEC §G-3）。
> `--loop 0` 合法：aos 會印一行 warning 並以最小間隔 1 毫秒運作，**不會忙碌輪詢**
> （SPEC §G-4）。回合回 0 或 1 都會繼續（1 的診斷已印到 stderr），但**連續 10 次
> 庫層失敗**會停機並回 4（SPEC §G-5）；遇到既有 `.runi` 則停止並回 3。

**同段順手**（S9／S10 一起做，不是本節的 timeout 題）：補一小段 control inbox 的
可複製範例（投一份 `{"op":"stop"}` 進 `.aos/control.tempd/`，先 `.temp` 後 `mv`），
**輸出要貼實跑結果**。

### 3.4 `docs/usage.md` — 同段的 instruction 範例（`sleep 30` ＋ `timeout_ms: 500`）

**原句**（範例 JSON 的第二筆）：

> ```json
> { "argv": ["/bin/sh", "-c", "sleep 30"], "timeout_ms": 500 }
> ```
>
> 常用欄位：`argv`（必要，不可為空）、`stdin` / `stdout` / `stderr`（重導向到
> 檔案）、`exit`（把 exit code 寫進這個檔）、`cwd`、`env`、`timeout_ms`。

**改法**：**JSON 範例不動**（這一節講的是 `aos exec`，逾時由回合層施行，行為不變），
只在「常用欄位」那句尾巴補一個括號：

> …、`cwd`、`env`、`timeout_ms`（**逾時由回合層施行**——用 `aos exec` 會照做；
> 直接呼叫函式庫的 `execute()` 不會，見下方「當函式庫用」與 SPEC §G-6）。

### 3.5 `docs/usage.md` — 段落標題「**一個完整的例子**」（函式庫用法）★ 最危險的一處

**原句**（節錄）：

> ```cpp
>     aos::inst_t job;
>     job.argv = {"/bin/sh", "-c", "printf 'hi\\n'"};
>     job.stdout_path = "out.txt";
>     job.timeout_ms = 1000;
> ```
>
> …
>
> ```cpp
>     const aos::ExecState exec_state = aos::execute(jobs.front(), result);
>     std::printf("%s status=%d timed_out=%d\n", aos::to_string(exec_state),
>                 result.status, static_cast<int>(result.timed_out));
> ```

**為什麼非改不可**：這個範例搬遷後會**無聲失去逾時**——設了 `timeout_ms = 1000`、
呼叫 `aos::execute()`，卻永遠不會逾時；而且它印的 `timed_out` 從此**恆為 0**
（該欄位改由回合層填，§G-6）。這是整份文件裡唯一「照做就會踩坑」的地方。

**改法（建議案）**：**刪掉 `job.timeout_ms = 1000;` 那一行**，並在範例**之後**補一段：

> **逾時不由 `execute()` 施行。** `timeout_ms` 是 instruction 格式的欄位，但**施行者
> 是回合層**（SPEC §G-6）：`aos exec` 會照做，直接呼叫 `aos::execute()` 則會**阻塞到
> 子行程自行結束**，`result.timed_out` 由呼叫端（回合層）填寫，`execute()` 自己
> 不會設它。要自己施行期限，用 `spawn`／`poll_child`／`signal_child_group`／
> `reap_child` 這組非阻塞入口自行組計時迴圈。

**改法（備案，若要保留「設了欄位」的示範）**：那一行改成帶警語的形式——

> ```cpp
>     job.timeout_ms = 1000;  // 由回合層施行；execute() 不會施行它（SPEC §G-6）
> ```

並照樣補上面那段說明。**兩案都 MUST 補說明段**；只刪一行不補說明會讓讀者以為欄位沒了。
