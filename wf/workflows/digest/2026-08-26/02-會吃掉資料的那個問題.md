**這篇講什麼**：有一條路徑會安靜地吃掉剛投進來的工作，今天被三次獨立驗證　|　**幾分鐘**：4 分

## 一句話

`aos exec`（開工指令）會說「我拒絕開工」並回退出碼 3，但它在說這句話**之前**已經把收件匣清空了。人照唯一想得到的方式去救援，那批剛投進來的工作就永久消失——沒有警告、沒有備份、指令回 0。

## 用信箱走一遍

先講清楚三樣東西，底下都用這組講：

- **信箱**＝收件匣，別人把新工作投進來的地方（`.aos/inst.tempd/`）
- **待辦清單**＝這一回合真正要做的那批（`.aos/inst.json`）
- **桌上壓著的舊清單**＝上一回合沒做完留下來的（`.aos/inst.json.runi`）

**現場**：桌上壓著一份舊清單，代表上一回合中途斷掉。同時，有人往信箱投了一封新工作進去。

你喊開工。收信員做的第一件事是走去信箱，把裡面的信全部抄成一份新的待辦清單，然後**把信箱清空**。

抄完之後他才抬頭，看到桌上壓著舊清單，於是說：

```
aos exec: refusing .: .aos/inst.json.runi already exists
exit=3
```

白話：「桌上還有沒做完的，我不動手，現場留給你。」

問題是信箱已經空了。那封信不在信箱裡了，它躺在剛抄好的那份新清單上。

**你現在只有一個看起來合理的動作**：把桌上那份沒做完的舊清單放回正位，接著做。這個動作會直接蓋掉剛抄好的新清單。

```
mv .aos/inst.json.runi .aos/inst.json
exit=0
```

沒有警告、沒有備份、退出碼 0。剛才那封信：**0 筆，永久消失**。

## 為什麼可以相信這是真的

三條互相獨立的線，撞在同一個點上：

1. **兩場完全不同的黑客松**——不同題目、不同角色設定、不同場地——各自獨立踩到同一件事。
2. 一位評委（Torvalds 角色）去讀原始碼確認：抄信那一步確實排在取件之前，「桌上有舊清單就回 3」那一段排在它**後面**。
3. **主辦人自己在乾淨環境端到端重跑過**，上面那兩段就是真實輸出。

這是今天所有產出裡可信度最高的一條。

## 為什麼會變成這樣

**規格不是寫錯，是漏寫。** 規格第六節只寫了「一回合就是：彙整 → 取件 → 執行」，**從頭到尾沒說「拒絕開工之前會不會先彙整」**。程式選了先彙整，規格沒有任何一句話否定它。

**還有一件事要講清楚**：`mv .runi inst.json` 這個救援動作，**規格從來沒建議過**，評委 grep 過確認。那是前人實測時自己補出來的土法。規格只說了兩句：斷掉之後「要人來處理，這是刻意的」、斷掉留下的檔「要人手動清」。

所以最準確的說法是：**規格沒有指定任何恢復動作，而人手上僅有的兩個動作都是破壞性的**——搬回去等於整批重跑一遍（中間如果呼叫過付費模型，就是再付一次錢），刪掉等於直接丟掉那一批。

## 同一個根因，還有更深的一層

規格裡有兩句話，單獨看都對，放在一起就矛盾：

- 一句說：桌上那份舊清單存在，**就代表**有一回合沒跑完。
- 另一句說：子行程被放進各自獨立的行程群組——也就是說，開工指令結束之後，它生出來的子程式**可能還活著**。

只要有子程式活得比父程式久，那份舊清單就會在「這回合其實完整跑完了」的時候，宣稱「沒跑完」。

**四位參賽者獨立撞到這一條。評委說它是本輪最強的訊號、沒有之一。** 這一條底下沒有現成選項可挑，因為它動到的是「怎麼判斷一回合到底有沒有跑完」本身。

## 代價有數字

有人真的在中途砍掉正在跑的 agent loop，然後照上面那個土法救援，結果**同一件事付了兩次錢**：

- 一位量到花了 31,316 個 token，去做完 15,658 個 token 的事。
- 另一位拿到兩個不同的呼叫編號當硬證據，而且**第二次呼叫把第一次的計費紀錄覆蓋掉了**——現場自己銷毀自己。

## 你有哪些選擇

以下只攤開，不推薦。

**一、什麼都不做**
成本 0。風險是這條路徑會靜默吃資料，而且已知有人會照那個土法救援。下次遇到，投遞照樣不見，而且**不會有任何訊號告訴你它不見了**。

**二、只補一句規格**——明講「拒絕開工之前不彙整」。
最便宜，把「該怎樣」定下來。代價：規格會跟現在的程式行為對不上，在有人改程式之前，這個洞照樣在。

**三、做一支正式的救援指令**——讓人有一個安全的動作可以做，取代那個土法。
代價：這會直接碰到專案裡「斷掉就是要人來處理，現場留給人是刻意設計」那條原則。要不要為此開一個例外，是你的判斷。
