# 檔案結構變了——但你原本記得的路徑一條都沒動

> **這篇講什麼**：你要的「大檔都拆掉」做完了，資料夾變胖很多，但你不用重新學路　|　**幾分鐘**：4 分鐘

專案裡的 `.md` 從 **104 個變成 274 個**（其中 12 個是那天新寫的紀錄與這批精簡版，其餘是拆出來的），你會看到一堆新資料夾。**先看下一段。**

---

## 最重要的一件事：舊路徑全部還在

拆檔的做法不是「把檔案搬走」，而是：**原本那個檔名留在原地，變成一頁導覽**——上面一張表告訴你哪塊搬到哪個新檔，內容則搬進一個**跟它同名的資料夾**。

所以你記得的路徑、書籤、還有專案裡到處互指的連結，**全部照常有效**——點進去不會撲空，只會多一次跳轉。

我把全部 274 個 `.md` 的連結掃過一遍：**沒有任何一條因為這次拆檔而斷掉**。剩下三條壞連結是本來就壞的——兩條在 `reference/llmkit/`（從別的專案原封搬來的參考資料，指向那邊的檔），一條是某個 README 裡格式打錯的連結。

## 門檻不是「一律 8KB」——這點跟你當初講的不一樣

你說的是「超過 8KB 都拆」。實際照的是 `wf/DEV-GUIDE.md`〈結構整理原則〉訂的**三套門檻**，按內容性質分：

| 內容性質 | 門檻 |
|---|---|
| `workflows/` 流程筆記 | 8192 bytes |
| 使用手冊／產品文檔（`docs/`） | 300 行 |
| 程式碼 | 300 行 |

那份原則自己也寫著：門檻是**觸發檢視的訊號、不是硬性上限**。

---

## 哪些沒拆、為什麼

**`docs/` 底下有三個檔超過 8KB 但沒拆**：`aos-folder.md`（294 行）、`usage.md`（293 行）、`inst-directives.md`（199 行）。按上面那張表，文檔看的是行數，它們都沒破 300。

**有幾篇判定「不該拆」**：一篇從前提推到結論的論證、一份前後連貫的實測筆記。切開之後兩半都會變成看不懂的殘篇。

**另外有一件你會看到、但不是這輪漏掉的**：`hackathon/records/` 底下有三份很大的紀錄（`agent-loop.md`、`argv-split.md`、`deliver-contract.md`，最大的 160KB 以上）。那些是**今天稍晚才跑出來的新東西**，時間上落在這輪整理之後，所以沒被掃到。要不要拆等你決定。

## 程式碼也拆了，而且是編譯過的

三個小專案裡超過 300 行的檔全部拆完。現在**沒有任何一個原始碼檔超過 300 行**（最長的是 `core/inst/src/resolve.cpp`，280 行）。

從專案根目錄做過完整重新編譯：**沒有任何錯誤，四組測試全部通過。**

其中一個是**對外公開的標頭檔** `core/llms/include/aos/llms.hpp`。拆它的做法是把原本的檔變成一支「只有幾行引用」的傘狀檔案，把真正的內容擺進 `aos/llms/` 底下。所以外面的程式寫 `#include <aos/llms.hpp>` 拿到的東西跟以前一模一樣，**一行都不用改**。

---

## 以後要注意的一件事：新增程式檔要去哪裡登記

專案有條鐵律：**改了程式碼就要同步 code map**（那張「哪個檔負責什麼」的地圖）。它自己也被拆了，登記的位置因此變了：

- `wf/workflows/common/code-map.md` — 只剩**總圖**（結構、單向相依鐵律、快速索引）。**不要在這裡加逐檔的列。**
- `wf/workflows/common/code-map/` — 逐檔表格，按小專案分四冊：`inst.md`、`tooljson.md`、`llms.md`、`build.md`。

**新增一個原始碼／測試檔時，那一列加去哪**：

| 檔案位置 | 去哪加 |
|---|---|
| `core/tooljson/` | `code-map/tooljson.md` |
| `core/llms/` | `code-map/llms.md` |
| `common/`、`app/`、`cmake/`、建置設定 | `code-map/build.md` |
| `core/inst/` | 先到 `code-map/inst.md`，它會再指你進 `code-map/inst/` 的 library／capi／cli／tests 其中一份 |

`core/inst/` 是唯一要多轉一層的，因為它最大。這一步跟程式碼改動放**同一個 commit**。
