**這篇講什麼**：專案裡卡最久的那顆釘子被拔起來了——投遞現在有形狀，可以開工寫程式　|　**幾分鐘**：5 分

## 一句話

aos 的交接是三步：**有人投信 → 收信員把信抄成待辦清單 → 執行**。後面兩步早就寫好了，**第一步「投信」從來沒實作過**，它到今天為止只是一句口頭約定：先寫一個暫存檔，再改名成正式檔名。整套流程的安全性全押在那一次改名上。

這場黑客松沒寫程式，它是去問出「動手之前必須先定的三件事」。三件都拿到帶實測證據的答案了。

## 為什麼它拖到現在

不是沒人有空。是三件事沒定，先寫就會把錯的規則凍在介面上：

1. **這支命令長什麼樣？** 四種寫法在打架——東西從檔案來、還是從前一支程式的管線來？一次一筆還是一批？要不要現在就支援「投給別的目標」？
2. **給每筆工作一個編號，那編號承諾什麼？** 麻煩在於信被收走之後那個檔案就刪掉了，下一回合再問「這編號以前來過嗎」，磁碟上一點證據都沒有。除非另外開一本永久帳。
3. **成功和失敗各回什麼？** 退出碼怎麼編、輸出要有哪些欄位。

四位參賽者（Pike／Hickey／Cantrill／Evans 的風格模擬，不是本人意見）各做一套假件實跑，共兩輪。以下是評委（Lamport 角色）在〈如果現在就得拍板〉給的答案。

## 三個答案

**一、命令寫成 `aos deliver <資料夾> (-f <檔案> | -)`。**

**目標資料夾一定要寫，資料從哪來也一定要寫**——要嘛 `-f 某個檔`，要嘛一個單獨的 `-` 表示「從前一支程式接過來」。少寫就直接拒絕，不准猜。

代價是每次多打幾個字。好處是三種場景（手打檔案、管線、agent 一次送一批）都不用另外造暫存檔，也不會有人打了半條命令，程式就在那裡默默等輸入。

三位選這個寫法，一位（Pike 角色）明白不同意、堅持不要那個旗標。**這是唯一沒有四人一致的一題。**

**二、第一版不給編號。**

四位都量出同一個數字：問「這件事以前送過嗎」，**四個時點只有一個答得出來**——信已投進去、還沒被收走的那段。投進去之前只有暫存檔（代表有人在嘗試，不代表送成功）；被收走之後檔案已刪；程式重開後記憶體歸零。

所以第一版不出現任何暗示「重送是安全的」的字眼。

**三、退出碼只有三個，欄位能少就少。**

`0` 成功、`1` 操作失敗（例如寫不進去）、`2` 呼叫方自己的問題（命令寫錯、資料格式錯、目標版本不對）。細節只在輸出的 JSON 裡出現一次。

成功只保證回「這批有幾筆」。失敗只回共用檢查器**真的講得出口**的：錯在哪一類、第幾筆。**不承諾「錯在哪一格」**——現有檢查器產不出那個，寫進契約等於答應日後補齊。

## 第一步不是寫命令列

這是評委講得最具體的一段：**先寫一個內部的「發布」動作，命令列介面之後才接上去。**

那動作很短：把已經驗過的內容寫進同目錄的暫存檔，改名成正式檔名，**而且絕不覆蓋別人已經放在那裡的信**。

重點是它必須把三種狀態分開，而且分開這件事要寫進測試：

- **改名之前就失敗**＝東西沒送出去（信箱裡乾淨，沒有半成品）
- **改名成功**＝送出去了
- **改名成功、但還來不及回話就掛了**＝**送出去的人自己不知道**

## 為什麼第三種是整件事的重點

第三種聽起來像邊角，其實是整個設計的核心。實測是在改名剛完成、回話還沒送出的那一瞬間把程式殺掉——

```
kill_returncode=-9  caller_stdout_bytes=0
disk_visibility=published  visible_ready=1
caller_knowledge=unknown
```

白話：**信確實已經躺在信箱裡了，但送信的人一個字都沒收到。**

接著他做了任何人都會做的事：不確定，那就再送一次。結果：

```
visible_ready_after_retry=2
effect_lines=2
```

**信箱裡兩封一模一樣的信，後面真的執行了兩次。**

所以「沒收到回話」不能推論成「沒送出去」。這第三種狀態必須是一個**程式講得出口的答案**（「我不知道」），而不是讓呼叫方自己猜。這一條由 Hickey 角色實跑，現場輸出可重跑。

## 一個只有真的動手打才會發現的陷阱

另一種寫法（`aos deliver 資料夾 檔名`）裡，有人真的打了這條：

```
$ aos deliver fixtures/world one.json
{"ok":true,"count":1}
```

看起來像在說「送 `fixtures/world` 底下那個 `one.json`」。實際讀的是**你當下所在資料夾**的 `one.json`，完全另一個檔。而且它回你成功。

**成功不等於投對地方。** 這種東西不會出現在規格討論裡，只有真的把命令打下去才撞得到。這也是評委要求「資料來源必須明寫」的直接理由。

## 一條被判定為「致命」的坑

**在沒有那本永久帳的情況下，對外承諾「同一個編號送兩次是安全的」。**

評委用的字是「致命」，不是「比較難做」。原因在這份輸出：

```
history=never      truth=NotAlready  disk_sha256=b417...8992
history=published  truth=Already     disk_sha256=b417...8992
disk_equal=yes
```

白話：**兩段完全不同的歷史——一段從沒送過，一段送過而且信已經被收走了——在磁碟上長得一模一樣。** 同樣的輸入，正確答案卻是相反的兩個。

所以這不是「做得不夠好」，是**沒有任何程式能同時對兩邊誠實回答**。要能回答就得另開一本永久帳，並連帶負擔它存多久、何時清、壞掉怎麼修。

同名相撞也實測過：**舊寫法會讓兩個送信的人都收到「成功」，信箱裡卻只剩後面那封**——前一封被靜默蓋掉。改成「絕不覆蓋」後才變成一個成功、一個明確失敗。這只有一個人在 Linux 上跑過一次。

## 還沒解決的

- 命令寫法仍是三比一，不是全體同意。
- 錯誤訊息要細到什麼程度沒有共識——現有檢查器能給的比大家想要的少。
- 完全沒碰持久性：斷電、強制寫入磁碟、網路磁碟、非 Linux，一項都沒測。這輪只證明「要嘛看得見、要嘛看不見，沒有中間狀態」。

## 要不要跑第三輪

**第二輪沒有翻案**，它做的是把證據等級提高（假的變真的、推論變實跑），並給出第一步的具體形狀。

**主辦人建議收在兩輪。要不要跑第三輪，你決定。**
