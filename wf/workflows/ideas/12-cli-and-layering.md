# 12 指令面、核心分圈、名冊與規範
← [入口](README.md)

這章講「人打什麼、程式怎麼分家」。前面幾章講模型，這章反過來，從一個人坐在終端機前想打的那一行開始，往下推底層要有哪幾支程式、切成幾圈、誰負責寫哪個檔。最後講一件無聊但致命的事：規範以哪一份為準。

## 從終端倒推，不是從底層堆上來

aos 一開始就是為了 agent loop 做的，所以先把「我想打什麼、想看到什麼」定死，再回頭看底層缺什麼。

- 先定坐在終端機前想打的指令與想看到的畫面，再回頭補底層〔裁決 2026-08-30〕
- 好用的介面外包出去：`--interface <程式>` 把 stdin／stdout 轉接給已經做得很好的程式，aos 自己不長一套終端機 UI〔裁決 2026-08-30〕
- `--step N`（走幾步就停）與「看它現在在幹嘛」這兩樣，是使用者自己給的答案：有限步數與可觀測狀態〔裁決 2026-08-30〕

## 三層各一個名字

三個名字對應三種深淺不同的「跑」，細節見 [寫→編譯→執行](05-write-compile-run.md) 與 [daemon](07-daemon.md)。

- `aos exec`＝讓一個資料夾走一步〔裁決 2026-09-03〕
- `aos run`＝反覆走到不再有新事可做〔裁決 2026-09-03〕
- daemon＝外面那圈常駐的，管所有正在走的資料夾，也是人下一次性指令的桌子〔裁決 2026-09-03〕
- 命名原則：小專案照它**做的事**命名（動詞），資料格式照它**是什麼**命名（名詞）——所以放指令資料結構的那個專案叫 `exec`，裡面裝的資料格式仍叫「一筆指令」〔裁決 2026-08-30〕
- `aos exec` 是唯一入口，但它不吞任何職責：這支程式裡永遠不會有 LLM 的程式碼、金鑰或連線；行程邊界就是隔離邊界〔裁決 2026-08-24〕

## 指令面分兩組

一組操作資料夾（一塊地），一組操作住在資料夾裡的 agent。

- 資料夾那組：把目前資料夾變成一塊地（`aos init`）、走一步（`exec`）、算到底（`run`）、從外面投一筆進去（`deliver`）、停掉（`stop`）、常駐（`daemon`）〔裁決 2026-08-30〕
- 走幾步、每步隔多久這種旗標掛在 `run` 上，例如「連走五步、每步間隔 50 毫秒」〔裁決 2026-08-30〕
- agent 那組：開一隻（`init`，互動問答挑思考引擎、人格、開場白，順便把資料夾變成一塊地）、跟它說話（`say`）、看它說了什麼（`listen`）、把前兩者串成一問一答（`talk`）、看它是空閒／思考中／執行工具中（`state`）〔裁決 2026-08-30〕
- `say` 與 `listen` 是原語，`talk` 是這兩個合成出來的；原語要能單獨用〔裁決 2026-08-30〕
- agent 沒有「停」：不 `run` 它，投遞匣裡那份還在，下次 run 就復活；資料夾層的 `stop` 有，但只能一個一個停（見 [daemon](07-daemon.md)）〔AI 觀察〕

## 核心切成四圈，每圈只知道自己以內

「核心」指的是我們自己要寫的那幾支小程式，由內往外一圈包一圈。

- 四圈由內往外：① 執行單筆指令的核心 ② 反覆取指的迴圈 ③ 彙整（也算核心專案，但用注入的方式跟迴圈配合，不再多包一層）④ 再外面就不包了，`deliver` 之類除非真的很核心，否則當普通指令做〔裁決 2026-08-27〕
- 最裡面那圈自己又分三小層：指令這個資料結構與執行它的函式、它的序列化（現在是 json）、一個「讀某資料夾的指令檔並全部執行」的命令〔裁決 2026-08-27〕
- 超時這種選項不放最裡面：寫在 json 裡，由迴圈那層在核心讀到它之前先剝掉並自己套用〔裁決 2026-08-28〕
- 迴圈屬於核心第二圈，不是外掛〔裁決 2026-08-27〕；因為控制流就是迴圈——執行單筆指令只是「指令」，取指與控制流在迴圈身上，兩個合起來才是那顆 CPU〔裁決 2026-08-28〕
- 上層能力不必是新的一圈：最裡面執行的是 POSIX 呼叫，本來就承載得了任何東西，所以想加功能通常是加一支普通程式，不是加一圈〔AI 觀察 2026-08-27〕
- 「迴圈只收無法變成一筆指令的東西」這條判準先不裁，邊做邊想〔裁決 2026-08-30〕
- 拿指令面試跑那條判準的結論只供參考：核心＝執行＋迴圈（取件、回合邊界、彙整發布、超時、分支）到此封閉，agent 整套不進核心〔AI 觀察 2026-08-30〕
- Linux 什麼都自己做（硬體全包），aos 只留執行與回合機、其餘靠往資料夾投訊息（學名：下面是大核心、上面是微核心）；這種靠傳訊息的做法，代價在這裡不是微秒，是一個回合〔AI 觀察 2026-09-03〕

## 名冊有封閉判準，不用一直累積

要幾支程式不是憑感覺加，是從協定推出來的。

- 外部的人每執行一個協定步驟，就配一支程式（例如投遞）〔AI 觀察 2026-08-28〕
- 機器留下的每一種靜態狀態，配一個「看」和一個「修」（看狀態、壞了修回來）〔AI 觀察 2026-08-28〕
- 每一份規範配一支驗證器（檢查版面對不對、格式過不過）〔AI 觀察 2026-08-28〕
- 照這三條推出來的名冊到此封閉：執行、迴圈、投遞、看狀態、修復、驗證〔AI 觀察 2026-08-28〕
- 控制介面（看得見誰在跑、殺得掉、停得了）已經從「便利」升為「必要」，因為使用場景是同時跟好幾個慢 REPL 交流、每個可能跑十幾分鐘〔裁決 2026-09-01〕
- 核心的名冊跟指令的名冊不是同一份：回合內跑、又不能變成一筆指令的才進核心；人在終端機打的都是指令面〔AI 觀察 2026-08-30〕

## 規範只能有一份說了算

- 要有一份被指定為「正本」的規範：編號條款、寫清楚哪些必須哪些建議，其他所有東西（parser、文件、餵給 LLM 的說明）都從它派生〔AI 觀察 2026-08-28〕
- 現在真相有三份在各自漂移（規格、實作文件、手寫的 parser），第四份是 LLM 讀到哪份就理解成哪樣——這是要避免的狀態〔AI 觀察 2026-08-28〕
- 規範要有一份機器可讀的 schema，別讓三處手工同步〔AI 觀察 2026-08-28〕
- 版本欄要兩個不要一個：指令格式的版本，和版面（`.aos/` 結構）的版本，是兩件事〔AI 觀察 2026-08-28〕
- 判例式的裁決記錄只是索引，不是法典；還要一條「裁決怎麼進正本」的流程〔AI 觀察 2026-08-28〕

## 版面規格是歸屬表，不是檔名表

版面就是 `.aos/` 底下有什麼。光列檔名沒用，要列誰能動。

- 每條路徑標唯一的 writer 與方向；有兩個 writer 的路徑，就是未來損壞的準確位置〔AI 觀察 2026-08-28〕
- 每條路徑再標一欄「這算不算世界的一部分」，判準見 [一塊地](03-land-and-life.md)〔AI 觀察 2026-09-01〕
- 這條界線會隨設計落地移動，所以還要記「現在算哪一類、什麼落地後會改」〔AI 觀察 2026-09-01〕
- writer 清單要多一列載入器：人寫的原稿放頂層，父層點名打開時載入器才把它讀進 `.aos/`；頂層是人的地盤〔裁決 2026-09-03〕
- 版面需要第二個軸：現在只有「指令檔的各種狀況」一個軸，事件流與當下狀態投影塞不進「名字.副檔名.狀況」這種三段式命名〔AI 觀察 2026-08-28〕
- 靜態清單進版控、動態狀態不進〔AI 觀察〕

## 決定是怎麼下的

這幾條是做事的規矩，不是機制，但它決定文件會不會又漂掉。

- 方向性的裁決屬於使用者；AI 只挖邊緣狀況、擺出選項與後果，不代裁〔裁決 2026-08-30〕
- 「為什麼選 A 不選 B」寫進判例記錄，不另外再存一份表〔裁決 2026-08-30〕
- 實作中被迫下的新裁決算正式裁決，要記回構想文件〔裁決 2026-08-28〕
- 一階段的「要先裁的」沒裁完也可以動工，但碰到那個決定的那一行就得停下來裁，不准臨時湊合〔裁決 2026-08-28〕

## 我的意見

- **名字沒收尾。** `pu`（處理單元）是使用者親自取的名字，之後所有討論與程式都用 `init`／`run`，但沒有任何一處明說撤回。名字背後的意思（一個資料夾就是一顆處理單元）是對的，值得保留為概念；建議正文一律用 exec／run／daemon，`aos init` 取代 `pu init`，然後請使用者補一句正式撤回。
- **兩份名冊被混成一份。** 「核心該有哪幾圈」與「終端該打哪幾個指令」判準不同（一個看回合內外，一個看人順不順手），兩邊清單有重疊也有缺口：驗證器與修復在指令面那組沒出現，agent 那五個子命令在核心那邊被判「一個字都不進」。建議寫成兩張表，中間標出共用的協定知識（怎麼讀寫 `.aos/` 版面）——那不是一圈。
- **核心說封閉了，但前提還缺一塊。** 試跑結論是核心只差「分支」——迴圈要看懂本回合結果來決定繼續、停、還是睡。新模型把這件事分給兩個地方（`.aos` 自己選下一個開誰、`run` 的停止條件），所以要先確認那兩處算不算迴圈的職責。見 [`.aos` 裡面](04-inside-aos.md)。
- **控制介面已升成必要，卻一支都還沒設計。** 「同時跟多個慢 REPL 交流」一旦成立，看不到誰在跑就管不動。這比規範正本更急，因為它是每天會碰到的那一面。
- **正本規範跟「先去玩」有點衝。** 使用者已裁「概念層收尾、先去玩」，立正本規範卻是動工型的工作。折中：先立薄的一份（版面歸屬表＋兩個版本欄），玩的時候撞到什麼再往裡加。

## 現況對照

- 今天的指令是 `aos init`／`aos run`／`aos agent …`／`aos say`／`aos deliver`，沒有 `aos pu`。
- 核心底下今天有執行、迴圈、tick、wire、agent、llm、tool 幾個小專案，沒有「彙整」；`agent` 整套在核心裡，跟試跑結論相反。
- 看狀態、修復、驗證三支都還不存在，也不能停在回合邊界；`.gitignore` 排掉整個 `.aos/`。
