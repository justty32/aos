# 第二輪：fork/exec 這個原語夠不夠通用
← [call-format](README.md)｜[ideas](../README.md)｜[WORKFLOWS](../../../WORKFLOWS.md)

上一節問的是**格式與序列化**；這一節問的是 **fork/exec 這個原語本身夠不夠通用**。
結論先講：**invocation 層面夠，interface 層面不夠，而且界外有六樣東西。**

> **使用者的總裁決**：「這確實只是呼叫**機制**不是呼叫**約定**，它不能成為通用契約，
> 它只能作為**『fork/exec as CPU instruction』這個概念的基石**。」
> 下面每條的裁決都收在該條裡。

## 機制 vs 約定（最深的一條，已接受）

fork/exec 規定「怎麼把控制權交出去」（argv 位元組向量、env、cwd、三個 fd、回來 8
個 bit），**不規定那些位元組是什麼意思**。每個被呼叫者自己發明解析（getopt、
`--flag=x` vs `--flag x`、子命令、stdin JSON…），同一個引數位置在兩支程式裡沒有共通
語意。連 C 都有 calling convention，這層沒有。

對「LLM 生成 instruction」這個核心用例是要害：模型得逐支程式記住 CLI 慣例，格式幫不
上忙。**裁決：接受，不修。它就不是通用契約。**

## exit status 分不開傳輸失敗與應用失敗（已決定要改）

任何 RPC 第一件要分清的事，這個原語分不開。`127`＝找不到命令、`126`＝setup 失敗，但
doc 自己承認「無法和一個真的以相同值結束的程式區分開來」；逾時被 SIGTERM 是 143，別人
殺的也是 143。`ExecState` 在記憶體裡有分，但那道分界**跨不過檔案系統**，而下一回合只
看得到檔案系統。**裁決：使用者之後會改。** 與上一節第 2 條是同一件事。

## 共用記憶體、常駐、串流在界外（已接受，就是會變 daemon）

- exec 會炸掉位址空間，所以「以呼叫者記憶體為操作對象」的呼叫天生不能是 inst——
  這就是匯聚為什麼是注入式 lib。
- LLM CPU 每回合載 30GB 權重不可行，所以它會是常駐 server；那就**有** IPC、**有**協定、
  **有**握手，只是藏進 `aos llm exec` 裡。[model](../turn-based-folder/model.md) 那句「沒有
  訊息格式、沒有 IPC、沒有握手」**只在最外圈成立**。

**裁決：這東西天生會變成 daemon，這沒辦法，也的確如此，那就這樣就好。LLM CPU 之後
會變成另一個 daemon。**

## 呼叫粒度的地板（不是缺陷，是設計）

一次 fork/exec ≈ 0.5–2ms 加一整套頁表，微秒級的自然粒度會被錯估一千倍。
**裁決：本來就是這樣設計的——細粒度的工作就在程式內，這裡是更高層次的 CPU 指令。**

## 權限只能全給（已推到上層）

POSIX 傳的是環境權威：整個 fs 命名空間、整包 env、所有繼承的 fd。格式無法表達「這次
只准碰這三個檔」——沒有 fd 傳遞、沒有命名空間限制、沒有降權。而 format.md 說「指令檔
等同可執行程式碼，只該來自你信任的來源」，核心用例卻是跑 LLM 生成的 instruction。
**裁決：權限這塊由上層呼叫 `aos exec` 的那一方處理，核心不管。**

## 沒有高階形式（承認是問題，解法在外層）

函式傳不進行程；可以傳可執行檔路徑，但閉包沒了。「跑 X，每遇到一項回呼我」只能翻轉
成「X 寫檔、下一回合讀」。代價是**呼叫沒有代數**：沒有 map、compose、partial
application，組合只能靠檔案路徑手接。
**裁決：確實是問題，所以外層需要另外弄一些更通用的呼叫契約。**

## 跨機器不延伸（已有答案）

fork/exec 定義上是本機的；包 ssh 會讓引號規則、env、cwd、路徑同時換命名空間，而記錄長
得一模一樣。**裁決：沒差，之後會用 plan 9。**

## 那個 2000ms（不用理）

exec.md 的逾時流程寫死「給 2000 ms 有秩序關閉」再 SIGKILL，而 format.md 有一段宣言說
「沒有任何上限……每一條上限都是一個猜出來的常數」。兩者互打。
**裁決：不是使用者設計的，是 AI 自己加的，別管。**
