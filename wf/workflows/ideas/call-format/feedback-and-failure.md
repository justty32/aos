# 第五輪：回饋路徑、失敗語意、協定完整性
← [call-format](README.md)｜[ideas](../README.md)｜[WORKFLOWS](../../../WORKFLOWS.md)

打的是**這個系統能不能察覺自己正在壞掉**。前四條讀 `core/inst/src/handoff.cpp` 驗證過。

> **使用者的總裁決**：「這些全都是**實作的時候自然會遇到的**，要嘛放到**外圈**，要嘛
> **交給使用者自行 handle 風險**。」

## 一、投遞被判無效時，生產者永遠不會知道

`aggregate_instructions` 遇到解析失敗的投遞：`rename(path, path + ".bad")`，issue 塞進
`HandoffResult`，繼續（`handoff.cpp:30`）。那份 result 回給**呼叫 aggregate 的人**（loop），
**不是生產者**。

從生產者看：檔案消失了。**被接受**（`remove_accepted_deliveries` 刪掉）和**被隔離**
（rename 成 `.bad`）**在它眼裡完全一樣**，連 poll 都分不出。

對 LLM 生產者這是致命的：產出一批、投遞、沒有錯誤、工作蒸發，然後繼續用同一套錯誤格式
產下一批。[agent-messaging](../agent-messaging.md) 講的「傳話失真層層放大成錯誤風暴」，
**在這裡連被發現的機會都沒有**。

## 二、失敗永遠不算失敗，所以會全速無限失敗下去

三條疊起來：exec 說「非零狀態、訊號終止、找不到命令、逾時，都是一次**已完成的執行**」
且不中止後續；loop 沒有「失敗回合」的概念；系統沒有歷史。

於是**一筆每回合都失敗的 inst 會以輪詢的最高速度永遠失敗下去，而系統認為一切正常**——
沒有退避、沒有重試上限、沒有升級、沒有任何地方記下它失敗過。不是崩潰，是**安靜的滿速
空轉**，而 `--loop 0` 讓它跑得最快。

## 三、交接協定是慣例，不是強制

`cwd` 預設就是那個資料夾，沒有東西攔一筆 inst 去寫 `.aos/inst.json`。投遞、彙整、`.bad`
隔離、原子 rename——**整套協定的保證都是自願的**，任何指令都能把批次直接塞進 `inst.json`
的位置，連 JSON 驗證都繞過（驗證發生在彙整）。而這些指令是 LLM 生成的。

這不是安全問題，是**這個系統能不能相信自己讀到的東西**的問題。

## 四、`.bad` 是命名標準不認識的第三種狀況，而且沒人清

已定案的命名標準寫死「整套狀況字彙目前**只有兩個**：`.temp` 與 `.runi`」，實作有第三個
`.bad`——**規格與實作在「已定」那一欄不一致**。而且 `.bad` **永久堆積**：
`remove_accepted_deliveries` 只刪成功的。一個還沒學會格式的 LLM 會把 inbox 塞滿永不消失
的檔案。

## 五、沒有背壓，而「不設上限」的理由在這裡剛好不成立

`format.md` 的宣言：「每一條上限都是猜出來的常數，而它們保護的資源本來就有更好的邊界
（`ulimit`／cgroup／`ARG_MAX`）」——理由是**那些資源有 OS 級的真實邊界**。

但 **inbox 深度沒有任何 OS 邊界**。生產快於消費時無限成長，而 `aggregate` 每次
`readdir` 整個 inbox——**越積越慢，越慢越積**。這裡需要的不是猜常數，是**背壓**，而背壓
只有格式與協定層做得到。

## 六、沒有 change feed，觀察者每回合都是 O(世界大小)

LLM CPU 要決定下一步就得知道世界現在什麼樣。沒有 generation、沒有 delta、沒有「自從 N
以來改了什麼」，只能重掃整個資料夾。[prior-work](../prior-work.md) 的 `WorkspaceDelta`
是為**正確性**提的，這裡是同一個洞的**效能**面。

與第四輪的「沒有歷史」是同一件事的兩半：**沒有歷史 → 不知道發生過什麼；沒有 delta →
連現在什麼樣都要重算。**

## 七、`parallel` ＋ 同一個輸出路徑 ＝ 靜默資料遺失

文件赦免的是「多個子行程共用終端，stdout 互相插入」。但 `parallel: true` 的兩筆指到同一
個 `stdout` 路徑時，兩邊各自以 O_TRUNC 開檔互相截斷——那不是輸出難看，是**資料遺失**，
而格式**無法表達互斥**（回到 [format-gaps](format-gaps.md) 第五條：依賴邊執行器看不見）。

## 八、`aggregate` 用同一個狀態回報兩種不同情況

實作在 `inst.json` 已存在時直接 `return HandoffState::Ok`（`handoff.cpp:57`）——這其實
**回答了開放問題「彙整時已有一份沒被讀走的批次怎麼辦」：等下一輪，不覆蓋**，行為是對的。

但它回的 `Ok` 與「inbox 是空的」回的是**同一個狀態**（`Ok` ＋ `published=false`）。loop
分不出「這輪沒人投遞」和「上一批還卡著沒被取走」——而這兩種情況該做的事不一樣。
