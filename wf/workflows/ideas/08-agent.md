# 08 agent
← [入口](README.md)

agent 在 aos 裡不是特別的東西。一個 agent 就是一個資料夾，跟別的資料夾用同一套規則生、同一套規則死。
它跟別人不一樣的地方只有一件：它每次動一下，做的事是「把話丟給 LLM、拿回一張要做的事情清單、照著做、再丟一次」。
這一章講這個循環放進時鐘裡會長什麼樣——每一格做什麼、慢的事往哪擺、什麼時候算跑完、關機重開怎麼接回去。
時間與時鐘見 [時間](06-time-and-clocks.md)，誰推時鐘見 [daemon](07-daemon.md)，地的生死見 [一塊地](03-land-and-life.md)。

## agent 就是一塊地，沒有第二套規則

agent 不是核心裡的一個零件，是拿現有零件拼出來的東西。

- 一個 agent 就是一個資料夾，有自己的 `.aos/`，父地用開子資料夾的方式帶它。〔傾向 2026-09-04〕
- 生一個 agent＝開一個資料夾再去登記；殺一個 agent＝把資料夾刪掉。生死規則直接沿用一塊地的，不另立一套。〔AI 觀察〕
- agent 沒有專屬的行程，也沒有執行緒。它是一塊地，加上一份「每一格跑一次」的小狀態機。〔AI 觀察〕
- agent 整套一個字都不進核心：它是普通的指令與普通的資料夾拼出來的。〔傾向 2026-08-30〕
- aos 這套東西最初就是為了 agent 這個循環而做的，所以先定「坐在終端前想打什麼」再回頭補底層。〔裁決 2026-08-30〕

## 循環本身：一圈至少三步

使用者給的定義很短，照抄就夠用。

- agent 的本質是一個連續循環的指令：把 prompt 丟 LLM、取 LLM 結果並呼叫工具、取工具結果再丟 LLM。〔傾向 2026-09-04〕
- 所以 agent 本質上就是一個 `aos run`（反覆讓這塊地走一步），一圈至少三次執行：丟出去、取回來、執行工具。〔傾向 2026-09-04〕
- 這三步之間的狀態不能只存在記憶體裡。agent 每一格都要能從檔案讀出「我現在在哪一步」。〔AI 觀察〕

## 逐格走法：有事的格很短，中間夾一堆空等的格

把上面那圈放進時鐘，樣子是這樣的。這一套使用者看完回「的確會是這樣」。〔傾向 2026-09-04〕

- 父世界有時鐘，agent 是父世界裡的一塊地，跟著父動。要問 LLM 時，agent 開一塊脫節的小地，把 prompt 寫進去，請 daemon 讓它自己走，然後在自己的狀態檔標「在等這塊小地」。這一格很快就結束。〔傾向 2026-09-04〕
- 接下來每一格，agent 只做一件事：看那塊小地的固定產出路徑上有沒有檔案。沒有就結束這一格。這對 agent 幾乎不花錢，世界其他地照常動。〔傾向 2026-09-04〕
- 同時那塊小地在 daemon 手上跑它那條很久的呼叫，跑完把結果寫到固定路徑，工作結束。〔傾向 2026-09-04〕
- 檔案出現的那一格，agent 讀進來。結果是一張清單，當場執行：快的工具這一格就跑完、結果落在自己的產出處；慢的工具再開一塊脫節小地，狀態改成「在等那塊」。接著組下一份 prompt 寫進新的小地，回到第一格。〔傾向 2026-09-04〕
- 所以「一圈至少三次執行」真正的樣子是：兩個有事做的格，中間夾著一堆空等的格。夾幾格由 LLM 多慢與時鐘多密決定。〔AI 觀察〕
- agent 那份小狀態機只有三種狀態：在等 LLM、在等工具、該組下一份 prompt。〔AI 觀察〕
- agent 本身通常不需要自己的時鐘：它每一格做的都是有界的（寫檔、看檔在不在、跑快工具），可以當同步子地借父的鐘。真正脫節、需要自己的鐘的只有那些問 LLM 與跑慢工具的小地。〔AI 觀察〕
- 只有「父停了它也要繼續」的 agent 才自己去登記一個時鐘，由 daemon 直接帶。兩種都合法，差別只在誰讓它動。〔AI 觀察〕

## 跑到什麼時候：停不是死

- agent 跑到什麼時候：跟 Claude Code 一樣，跑到 LLM 不再呼叫工具。（使用者這句帶著問號，語氣有保留。）〔傾向 2026-09-04〕
- 放進時鐘模型就是：LLM 吐出的清單是空的，agent 沒有東西可執行，狀態變成閒著。〔AI 觀察〕
- 停不是死。資料夾還在，只是睡了；下一封信進來就醒過來再跑一圈。〔AI 觀察〕
- 所以 agent 的跑法分兩段：有事就一路跑到清單空為止，然後等下一封信。〔AI 觀察〕
- 這條件跟 `aos run` 的通用停法（這次走一步沒產出新指令就停）是同一個形狀，見 [時間](06-time-and-clocks.md)。〔AI 觀察〕

## 關機、重開、等待期間世界會變

- 一次全停的時候，還在跑的那塊小地被殺、結果沒寫出來，agent 的狀態檔就停在「在等它」。重開時發現那塊地死了又沒有結果，就重發一次。狀態全在檔案裡，重開就是接著走。〔AI 觀察〕
- 等待期間世界會變：組 prompt 那一格看到的地，跟結果回來那一格的地可能已經不一樣了。這正常，工具結果下一圈會告訴 LLM。〔AI 觀察〕
- 但組下一份 prompt 的時候要把等待期間收到的信一起放進去，否則 agent 永遠慢一圈。〔AI 觀察〕

## 每圈 prompt 怎麼組＝這塊地能長多大

- 每圈 prompt 怎麼組（整塊地全給，還是只給上一圈結果再加一點），使用者說這是後續的工程問題，之後再說。〔傾向 2026-09-04〕
- 這一題跟「記憶就是地」是同一題：它決定 agent 的地能長多大、每一圈要花多少錢。相關的歸屬見 [一塊地](03-land-and-life.md)。〔AI 觀察〕

## agent 層還缺一層限制

舊做法有兩個病：agent 會靜默死掉、agent 停不下來。病根是「這隻 agent 每回合都要在」這件事沒有任何檔案承載，只存在於「上一回合有沒有投遞成功」。新模型裡資料夾本身就是那個承載，一半的病治好了；另一半要靠限制參數。

- 「agent 每回合都要在」必須有檔案承載，不能靠上一回合投遞成功。〔AI 觀察 2026-08-30〕
- agent 這一層缺一組限制參數：總時限、最多呼叫幾次、token 上限、能用哪些工具。靜默死亡與「怎麼停」正是缺它。〔AI 觀察 2026-08-30〕
- 換句話說，`aos run` 那條「沒產出新指令就停」是自然停；限制參數是保底的強制停。兩個都要。〔AI 觀察〕

## 使用者也是一個 agent，住在 `~`

- 使用者自己也算一個 agent，他的資料夾就是 `~`；剛好只有一個人。〔裁決 2026-08-30〕
- 別的 agent 可以把信寄到 `~`；使用者對任何 agent 說話時，寄件人就是 `~`；使用者讀信就是在 `~` 底下聽。〔裁決 2026-08-30〕
- 所以通訊錄裡天然有一格是 `~`，信件要帶寄件人欄。通訊錄本身見 [工具與通訊錄](11-tools-and-contacts.md)。〔AI 觀察〕

## 兩級劇本：一個人用，跟指揮一隊

「順手」是拿這兩級來量的。

- 兩級劇本與量法在 [什麼與目標](01-what-and-goals.md)；跟 agent 直接相關的是：第二級裡每隻子 agent 各住一個資料夾、靠通訊錄互相投遞，使用者只跟主 agent 說話。〔裁決 2026-08-30〕
- 第二級要先有通訊錄與「派生一隻子 agent」的最小路徑；沒有就先把「做不到」記成第一條發現。〔AI 觀察 2026-08-30〕

## 我的意見

- **LLM 吐出的清單裡混了慢指令，誰來判定？** agent 這塊同步地只准跑會很快結束的東西，但 LLM 不知道這回事，它照樣會叫 `curl`。是靠這塊地的環境裡根本沒那個指令、直接失敗，還是要求清單自己標「這條慢」？沒答。歸屬在 [時間](06-time-and-clocks.md)，但受害的是 agent。
- **小地失敗了怎麼回來，是這章最大的洞。** 現在 agent 只看「檔案在不在」，於是「還沒好」跟「永遠不會好」長得一模一樣。重開時「發現它死了就重發」需要 agent 查得到那塊小地的時鐘狀態，這條路徑沒定義。建議至少讓小地有一個狀態檔，把三態（還沒好／好了／壞了）寫明。細節在 [呼叫與失敗](09-call-and-failure.md)。
- **agent 的停跟 run 的通用停法是不是同一條，沒有人明說。** 兩句話（「LLM 不再叫工具」與「這次沒產出新指令」）在 agent 身上剛好同時成立，但那是巧合還是同一條規則的兩個講法？我建議正式併成一條，agent 那句只當白話解釋。
- **空等的格是要付錢的。** 一圈固定夾一堆什麼都不做的格，互動起來會鈍。門房那層的門鈴（檔案一到就標記、下一格才處理）正是為這件事準備的，見 [門房](10-doorman.md)；在那之前，時鐘密度就是「反應快」跟「空轉多」之間的旋鈕，沒有第三條路。
- **第二級劇本還缺子 agent 的設定歸屬。** 子 agent 用誰的引擎、能用哪些工具、繼不繼承父的，只有 AI 建議「不繼承」，沒人拍板。這件事不定，通訊錄會偷偷變成權限表。

## 現況對照

- 今天的 agent 住在 `.aos/agents/<名字>/` 裡，屬於指令層，不是一個資料夾。這在新模型下是正式的缺口。
- 今天工具往返固定佔三個回合；手動走一步而不跑 `aos run`，會永遠停在「等工具結果」。
