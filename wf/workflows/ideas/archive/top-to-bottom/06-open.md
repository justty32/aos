# 06 · 還沒定的

← [top-to-bottom](README.md)｜上一層 [05-why](05-why.md)｜現況對照 [07-existing-aos](07-existing-aos.md)

**使用者原話（2026-09-03）**：

> 我覺得idea到這邊，我們該有的concept都差不多有概論了，你覺得呢？還缺啥嗎？

回答是：**主幹已經齊了，剩下的缺口全在「兩層之間那座橋」上**——就是 [03](03-inside-aos.md)
說的、`.aos` 裡 `aos run <子資料夾>` 那一行。

## 四條缺口

**這四條的完整版在 [play-watchlist](../play-watchlist.md)**（那是「玩的時候順手核對」的清單）。
這裡只列標題與一句話，**不重抄**。

| # | 缺口 | 一句話 |
|---|---|---|
| 1 | **父層怎麼拿到子資料夾的結果** | `aos run <子資料夾>` 是**等它做完**（呼叫）還是**丟出去自己繼續**（派工）？拿回來的是一個檔、一個回傳碼，還是整個資料夾的終態？ |
| 2 | **子資料夾看不看得到父層** | 能不能讀 `../`？能＝有作用域、跟父層共享一部分世界；不能＝每個資料夾密封，要什麼都得明確送進去。這也是「閉包」在這套模型裡有沒有落點 |
| 3 | **失敗** | 子資料夾跑壞、inst 失敗、或等太久，父層怎麼知道、怎麼處置？**完全沒討論過** |
| 4 | **資料夾壽命** | 跑完之後留著還是刪？誰動手刪？**目前只講了「生」，沒講「死」** |

**AI 觀察（非裁決，可否決）**：第 1 條決定了資料夾到底能不能**當函數用**（等回傳）還是
**只能當 actor 用**（只能送訊息）；第 3 條沒答案，[05](05-why.md) 講的「可預測性要有界」
就無從量起。

## 現況與模型對不上：今天的 agent 住錯位置

今天跑起來的 agent 住在 `.aos/agents/<name>/` **裡面**（也就是 inst 層／機器層），但照
2026-09-03 拍板的新模型，一隻 agent 應該是一個**獨立的資料夾**（operative），要呼叫 LLM
是在它自己的 `.aos` 裡下命令。

**這處落差玩的時候大概會直接撞到，先記著，不必現在改。** 對照見 [07](07-existing-aos.md)。

## 已裁，不再算缺口：`.aos/` 到底給人還是給機器

這條原本標成「對不上」（`.aos/` 今天是機器的暫存區，模型卻說它是一段人可以寫的腳本）。
**已裁（2026-09-03）**：**人寫的原稿放資料夾頂層，`.aos/` 一直都是機器的**；父層點名打開
這個資料夾的時候，loader 才把原稿讀進 `.aos/` 變成可以走的腳本——「打開＝unquote」的具體
動作就是這次讀入。所以**這不是概念矛盾，是那個 loader 還沒做**（`G14`，見 [03](03-inside-aos.md)）。

## 頂層 daemon 在缺口表裡沒有專屬的格子

**AI 觀察（非裁決，可否決）**：[01](01-top.md) 已裁「daemon＝REPL、daemon 也可看成一個
資料夾、頂層不需特例」，模型上是自洽的。但**既有的缺口清單（26 條那份）裡沒有一格是專門
給「頂層 daemon」的**——它現在是靠「排程器住哪一層」與「行程誕生」那兩格順帶涵蓋。

具體沒被涵蓋的一小塊：daemon 桌上目前只有**常駐清單**（登記某某資料夾要一直跑），**沒有
「一次性指令」這個入口**——而 REPL 的「讀一句」正是一次性的「去跑某個資料夾」。要當 REPL，
daemon 得多一個一次性投遞的入口。

**這條沒有裁決，也不急**：先玩，撞到了再說。

## 不是缺，是「已裁先玩」

**排程、資源計量、權限不是漏掉沒想到**，是 2026-09-03 已經明白裁定的：

**裁決（2026-09-03）**——使用者收尾的話，照原意記：

> 在這裡只能大概知道要管理什麼；具體怎麼管理，牽涉到具體的任務使用經驗。作業系統的最初，
> 也是大家試著讓一台電腦跑多個程序、遇到了阻礙，才發想出的解決方式。**所以先在這裡停下
> 腳步，先去用現有的東西玩玩看。**

後果：**缺口表暫停往下設計**，那邊列的提案**不動工**。要重啟設計的人，**從玩的過程記下的
阻礙開始**，不從那些觀察開始。

另外，**權限這塊使用者明說是「很後面才做的」。**
