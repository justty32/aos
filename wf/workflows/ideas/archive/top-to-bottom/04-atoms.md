# 04 · 最底下：原子 inst，再也託付不下去了

← [top-to-bottom](README.md)｜上一層 [03-inside-aos](03-inside-aos.md)｜為什麼這樣設計 [05-why](05-why.md)

一路往下：資料夾可以託付給子資料夾，子資料夾又可以再託付給它的子資料夾……**那什麼時候
停？**

## 停在「原子 inst」

**裁決（2026-09-03）**——本體只有兩樣，其中第一樣就是底：

> **原子 inst**——工具呼叫、LLM 呼叫。它們**不是資料夾**，**無法再往下託付**，是**底**。

**大白話**：

- **一次工具呼叫**——跑一個 POSIX 指令、開一個檔、打一次 API。
- **一次 LLM 呼叫**——問模型一句，拿回一段話。

這兩樣**沒有內部**可以再拆給誰做。你不能說「這次 LLM 呼叫我再派三個子資料夾去完成」——
派了那就不是這一次呼叫了，那是上面一層的事。

**學名**：lisp 裡叫 **primitive**（求值一路往下鑽，鑽到不能再展開的那一格）。

## 對照表：一路數下來，哪一層是哪一層

**AI 觀察（非裁決，可否決）**，這張表把 lisp／C／aos 三邊對齊：

| lisp | C 的說法 | aos 裡是什麼 | 穩態／暫態 |
|---|---|---|---|
| quoted form（就是資料） | `.h`／`.c` 源碼 | 你放進資料夾的檔 | **穩態**（躺著） |
| 展開＋拆平 | 編譯 | 拆平器的輸出 | 穩態→穩態，**確定性** |
| 拿掉 quote、開始跑 | 呼叫、載入 | **從模板開一條串** | **躺著變成在跑的那一刻** |
| continuation | 執行到哪（PC） | `series.json`（接力棒） | 暫態 |
| 環境框架、暫存器 | 堆疊框 | 臨時資料夾 | 暫態 |
| **primitive** | **機器指令** | **原子 inst** | **暫態的最底** |
| value | 回傳值 | `out/` 裡的檔 | 產出後轉穩態 |
| normal form（算完了） | 行程結束 | 接力棒走到底／資料夾不再變 | 穩態 |

三句話收攏：**你放的檔是躺著的部分，接力棒是正在被算的部分，原子 inst 是算到底碰到的
那一格。**

## 再往下就是真的機器

原子 inst 之下**不再是 aos 的事**：一次工具呼叫最後落到 Linux 上的一個行程，那個行程再往下
就是 **CPU 週期**。

**這是這套模型的地板。** aos 從最上面的 Linux 開始，繞了一圈資料夾樹與腳本，最後又回到
Linux 手上——中間那段才是 aos。

## 一步＝一次歸約

**裁決（2026-09-03）**：`aos exec` ＝**一步歸約**（small-step）。

**歸約**（reduction）的大白話：**把一個算式往「答案」的方向推一格。** `(+ 1 2)` 歸約一次
變成 `3`；一個資料夾歸約一次，就是它裡面的暫態部分被推進了一格。

**使用者自己的比喻（2026-09-01，遊戲模型）**：**一次 `aos exec` ＝遊戲裡的一格
`_process(delta)`**——引擎叫一次，每個東西動一下，然後把控制權交還。三個讀法互相不排斥：

- **單一資料夾看** → 它是 eval（算式在被歸約）
- **多個資料夾互相投遞看** → 它是 actor（一群行程在互傳訊息）
- **機器層看** → 它是 CPU 的取指—解碼—執行週期

## 為什麼底一定要是「不確定」的那一格

**AI 觀察（非裁決，可否決）**：接力棒（series）那一段是**確定的**——程式拆平、程式推進；
真正不確定的只有 **LLM 呼叫**那一格。所以**把工作從 LLM 搬到接力棒，就是在買可預測性**
（見 [05-why](05-why.md)）。

推到極端：**LLM 只留在真的需要「決定要往哪走」的那一格，其餘全是確定性程式的事。**
（這是提案，不是裁決。）
