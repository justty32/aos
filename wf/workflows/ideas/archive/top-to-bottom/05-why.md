# 05 · 為什麼這樣設計

← [top-to-bottom](README.md)｜上一層 [04-atoms](04-atoms.md)｜還沒定的 [06-open](06-open.md)

前面四檔講「長什麼樣」，這一檔講「**憑什麼這樣選**」。

## 要優化的是三個東西，時間空間只是順帶

**使用者原話（2026-09-03，這是他定的方向）**：

> **aos 的目標優化指標：硬性的時間、空間只是很粗淺的優化；最重要的優化是三個——
> 消耗的金錢（token）、可預測性、人類可理解性。**

他當時依「金錢 → 可預測性 → 可理解性」的順序列出，但**沒說那是不是優先序**。同日補裁：

**裁決（2026-09-03）**——使用者回答「三個裡哪個最優先」：

> 最優先的是可預測性。

**可預測性最優先。**（金錢與可理解性之間誰先誰後，**還沒裁**。）

**連鎖（AI 觀察，非裁決，可否決）**：

- 下一節「**套幾層＝幾輪回不來**」**首先是可預測性問題**，其次才是成本。
- 下下節的 **RTOS 從「一條可以對照的線」升為主線**——RTOS 就是把可預測性放第一的 OS。
- [os-metrics §七 n 與 §八](../os-metrics-and-resources.md) 裡按「金錢優先」推出來的觀察與
  提案（含「**帳本當 OS 的第一塊**」）**前提已經變了，要重看**——但不刪，那邊已標註。

**大白話三句**：

| 指標 | 白話 |
|---|---|
| **金錢（token）** | 這件事做完要燒多少錢 |
| **可預測性** | 同一件事做十次，成本與結果會不會差很多 |
| **人類可理解性** | 一個人打開這個資料夾，看不看得懂、接不接得了手 |

**為什麼不是時間？** 一般作業系統丟一堆**計算**任務進去，看它花多少資源（**主要是時間**）
跑完；但 aos 的任務**抽象**，「算完了沒」本身就要先定義，而且壁鐘時間幾乎全被 LLM 的延遲
吃掉，aos 自己的開銷在裡面只是雜訊。所以**主指標從時間換成 token 與回合數**。

**AI 觀察（非裁決，可否決）**：三者會互相拉扯——**可預測性通常靠冗餘買**（重跑、多方審核），
**可理解性通常靠多寫買**（解釋、日誌），**兩者都花 token**，跟第一個目標反向。而使用者說
時間空間「粗淺」，反過來就是**時間空間可以拿去換這三樣**（例如多跑幾回合換可預測性）。

## 套幾層＝幾輪回不來＝成本

這是「為什麼 inst 鏈那個語法糖要留」的核心理由（見 [03](03-inside-aos.md)）。

**AI 觀察（非裁決，可否決）**：lisp 的巢狀可以無限深，代價只是堆疊。資料夾這邊**每深一層，
就是一根接力棒停在那裡等**。在回合制底下，深度直接翻譯成「**幾個回合回不來**」——那是
**token 與可預測性**的成本，不是堆疊的成本。

所以同一件事有兩種寫法，**成本不同**：

| 寫法 | 成本 | 好處 |
|---|---|---|
| **開一個子資料夾**（生一個行程） | 多一輪、多 token、多一分不確定 | 邏輯獨立、看得懂 |
| **在 `.aos` 裡連著寫一串 inst**（內聯） | 便宜 | 但一長就難讀 |

跟 C 的「函數呼叫 vs 內聯」是同一件事。**兩種都要留，依情況選。**

## RTOS 那條線

**使用者口述（2026-09-03，玩到一半想起來的）**：

> 突然想到，有個東西叫做 **RTOS**。

**RTOS**（即時作業系統）的大白話：**它不比誰跑得快，它比誰能保證「一定在期限內做完」。**

**2026-09-03 裁「可預測性最優先」之後，這條線不再只是旁邊的對照，而是主線。**

**AI 觀察（非裁決，可否決）**：RTOS 是現成 OS 家族裡**唯一把「可預測性」當主指標**的——
它量的不是吞吐量，是 deadline 有沒有守住、最壞情況有沒有上界。這跟使用者定的三個指標裡的
可預測性**直接對上**：橫向對比時，aos 該對的可能不是通用 OS，而是 RTOS 那半邊。

RTOS 的三樣工具在 aos 都有現成落點：

| RTOS | aos |
|---|---|
| deadline（期限） | **每一格的預算**（超過預算的事等下一格） |
| 優先序 | 一條串自己報的建議優先級 |
| 最壞執行時間 | **每回合最壞 token 數** |

aos 時間粒度粗又不規則，所以做不到**硬**即時；但「**軟即時＝以回合與 token 為單位的預算**」
是成立的。而「套幾層＝幾輪回不來」正好是這條線上的一個成本來源：**要有界，深度就得有界。**

## 上面微核心、下面大核心

**使用者口述（2026-09-03）**：

> 然後作業系統又有**微核心、大核心**的區別。

大白話：**大核心**＝什麼都塞進核心裡（Linux 那種）；**微核心**＝核心只留最小一撮，其餘全是
外面互相傳訊息的服務。

**AI 觀察（非裁決，可否決）**：

- 這題其實**已經在別的名字下裁過了**——「core 只差一個分支就封閉、agent 整套不進 core」、
  「外部處理器只監控資料夾、不引用 aos lib」，**這就是微核心的形狀**（核心只剩執行＋回合機，
  其餘靠訊息溝通，而**訊息就是往資料夾投遞**）。差別只是沒人把它叫微核心。
- **微核心的代價是傳訊開銷**；在 aos 這個開銷不是微秒，是**一個回合**（有時還多一次 LLM
  呼叫＝錢）。所以這筆帳要**以回合與 token 算**——時間粒度粗反而讓微核心變便宜。
- **整個堆疊是「下面大核心、上面微核心」**：Linux（大核心）吸掉硬體那一層，aos 在它上面做
  微核心式的抽象。
- **真正的軟肋**：微核心假設服務之間的訊息無損，但這裡的訊息會**語意失真**（agent 轉述會
  走樣）。這條在 aos 不成立。

## 一條要守的線：邊緣狀況只能來自 LLM

**AI 觀察（非裁決，可否決）**：Linux 吸掉了硬體那一類邊緣狀況，但 aos 有 Linux 吸不掉的
一類——**LLM 的不確定**與**訊息語意失真**。所以「可以理想地抽象」要守的線是：

> **aos 的邊緣狀況只來自 LLM，不來自機器。一旦有邊緣狀況是機器來的，就是這條抽象漏了。**

## 最上層的判準：作業系統就是方便人使用

**使用者口述（2026-09-01）**，一個逐步收緊的定義：

1. **核心概念：作業系統就是方便人使用。**
2. 往下三件具體的事——**方便人寫程式**、**方便人寫的程式跑**、**方便人管理正在跑著的程式**。
3. 再往下一層：**管理資源的使用**。

這是**判準**，不是描述：任何一個設計選項都可以拿「這讓人更方便寫／更方便跑／更方便管嗎」
去問。也因此 **aos 不必抄現代 OS 的全部**——不服務這四條的部分可以不要。
