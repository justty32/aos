# 從圖靈完備到作業系統——aos 的根基論證

← [ideas](README.md)｜[WORKFLOWS](../../WORKFLOWS.md)

使用者口述的**上游理論底**（2026-09-01）：為什麼 agent loop 可以被當成 CPU，以及為什麼
在它之上要蓋的東西叫「作業系統」。其他構想檔講的是這台機器**長什麼樣**，這篇講的是
**憑什麼長成那樣**。

## 一、圖靈完備的三要件

一個運作模式要圖靈完備，要同時滿足三件事。使用者對三者的解釋（非教科書定義，是他要用的
那層意思）：

| 要件 | 使用者的解釋 | 在 aos 由誰擔當 |
|------|--------------|-----------------|
| **可計算** | 就是可計算，這是最基本的要求，不用多說 | **LLM** |
| **可根據條件分支** | 本質上是**能夠對外在環境做出反應、並改變自身行為** | **tooling** |
| **可連續執行自身** | 因為**自身體積沒辦法無限膨脹**，所以一定要能執行自己 | **agent loop** |

三者裡只有後兩條被重新定義過，值得留意：

- **分支被解釋成「對環境的反應」**——不是 `if` 這個語法，而是「外面變了、我就變」。所以
  tooling 才是分支的載體：它是這台機器唯一能看見外部狀態的器官。
- **連續執行自身被解釋成「體積不能無限膨脹」**——理由是空間，不是時間。若不能執行自己，
  要做長的計算就只能把步驟全部攤平寫進本體，本體隨計算長度線性膨脹。能執行自己，長度
  才換得到迴圈。

## 二、agent loop ＝ CPU

三要件湊齊 → **agent loop 圖靈完備 → 它就可以被視作 CPU**，或者說，可以拿去跟現代計算
體系做橫向對比。這是整條論證的樞紐：一旦 agent loop 被承認是計算單元，「在它上面蓋作業
系統」就是個有意義的句子，而不是比喻。

抽象 CPU 疊在 `inst` 之上這件事在 [turn-based-folder/model](turn-based-folder/model.md)
已經有，[llm-cpu](llm-cpu.md) 講 LLM CPU 怎麼疊。本篇補的是它們共同缺的那一句：**為什麼
「CPU」這個詞用在這裡是成立的**。

## 三、aos 的目標

> **一個橫向對比現代計算體系中的作業系統的框架——也就是，以 agent loop 作為計算單元的
> 作業系統。**

「橫向對比」是關鍵詞：不是拿現代 OS 的實作來抄，是拿它的**位置**來對。現代 OS 站在 CPU
之上管資源、排程、抽象化；aos 要站在 agent loop 之上做同一件事。

> **使用者自陳（2026-09-01）：這裡省略了太多步驟。** 從「agent loop 是 CPU」到「所以要蓋一套
> OS」中間的推導沒有展開，是直接跳過去的。**2026-09-02 補上**（下面「三之一」，三題三裁）。
> 原本「開著」的狀態收掉——要重新拷問的人從那三個裁決本身打，不是從「沒推導」打。

### 三之一、補上的推導（2026-09-02）

推導其實有兩層：**為什麼 CPU 之上必須有 OS**（本節），與**這個 OS 要有什麼**（第六節的
26 條）。第六節先於本節寫成，所以 26 條原本分不出「必要」與「現代 OS 有所以列上去」——
本節三個裁決就是拿來分的，分完的結果寫進 [cpu-to-os-gaps.json](cpu-to-os-gaps.json) 的
`status`。

**第一步：OS 是「多」逼出來的。** 一顆 loop、跑一支程式、一個人用、跑一次——這種情況不需要
OS，直接寫 series 餵它就好。四種「多」各綁一組缺口。**使用者裁決：多程式、多次、多 CPU 要；
多人先不管。**

| 多什麼 | 要不要 | 綁到的缺口 |
|---|---|---|
| 多程式（同一顆 loop 上不止一件事） | **要** | `G06` 行程、`G07` 程式／行程分界、`G10` 排程、`G14` 載入器 |
| 多次／跨時間（結束後要留東西、要 replay） | **要** | `G04` 可存 context、`G26` 記憶 |
| 多 CPU（pi 已是第二顆） | **要** | `G03` 隔離、`G12` IPC、`G23` 訊息失真 |
| 多人 | **先不管** | `G25` |

推論（AI 觀察，可否決）：

- 多人不要 → `G25`「使用者是誰」塌成**「恰一個使用者，而他也是一隻 agent 住 `~`」**
  （隊 W 已實作 `say --to ~`／`from`）。授權問題整條消失，只剩「哪隻 agent 發的」來源標記。
- 多 CPU ＋ 多程式同時承認 → `G10`「排程器住哪一層」不能只在一顆 loop 裡答，得答
  **「一支程式能不能跨 CPU 換手」**。這條**開著**，跟 [verdicts B](verdicts.md) 的
  「跨資料夾排程歸屬未定」是同一題。

**第二步：省略掉的步驟分三類。** 第四節說有「工程選擇」與「理念」，補一類**「必然」**。
使用者裁決：

| 步驟 | 類別 | 備註 |
|---|---|---|
| 檔案系統即記憶體 | **必然** | 由三要件第三件推出：體積不能無限膨脹 → 狀態必在 loop 之外 → 這台機器的「外面」只有檔案系統 |
| 同像性（程式與行程也住檔案系統） | **理念** | 第四節第 2／3 點；承重點是自我改寫（[theses-review §一](theses-review.md)） |
| 回合制（一次 exec ＝ 一格，沒有常駐） | **選擇** | 有承重：[game-process-model](game-process-model.md) 與 REPL 讀法都壓在上面 |
| `B3` 一回合內無資料流 | **選擇** | 有承重：REPL 讀法的存在條件（[theses-review §二](theses-review.md)） |
| 全塔 json、lisp 只留哲學 | **選擇** | [assembly-and-chains/source-and-ir](assembly-and-chains/source-and-ir.md) |
| 外部處理器只監控資料夾、不引用 aos lib | **選擇** | 2026-08-25 那句 |

後果：**選擇要用第五節那把尺（更方便寫／跑／管嗎）來守**，不能拿「機器本來就這樣」擋。
「有承重」的兩條是選擇，但一改就有別的東西跟著垮，改之前先看承重是什麼。

**第三步：橫向對比對到現代 OS 的哪半邊。** 現代 OS 有兩面——**對下**管硬體（中斷、驅動），
**對上**服務程式與人（syscall、方便）。第五節四條全是對上。aos 的「下」是 LLM API 與
tooling，L0 五條就是對下那半邊。**使用者裁決：拆開——`G04`、`G05` 歸 CPU（loop 自己的
spec），`G01`、`G02`、`G03` 歸 OS。**

後果：L0 不再整層是「欠 CPU 的債」。`G04`／`G05` 從 OS 帳移到 loop 帳（仍要做，但做在
loop 裡，不是 OS 裡）；`G01`–`G03` 是 OS 的，跟 L1 一起還。第六節「L0 是欠 CPU 的」那句
要照這個讀。

**推導鏈收攏成一句**：agent loop 是 CPU；人要多程式、多次、多 CPU 地用它；狀態必然在檔案
系統；所以要有一層管行程、記憶、隔離／中斷／特權——那層就是 OS，它對人的判準是第五節。

## 四、工程選擇與理念：檔案系統即記憶體

省略掉的步驟裡，有一些是工程選擇、有一些是理念。已明說的一條：

**借用 linux 與 lisp 的同像性，讓檔案系統同時是三樣東西——**

1. **記憶體**
2. **程式的載體**
3. **正在執行的程式的載體**

第 2 與第 3 分開列是有意義的：程式與行程共用同一種表示、住在同一個地方，這正是同像性
在這台機器上的形狀。它也解釋了為什麼 aos 的世界是「一個資料夾」而不是一個 runtime
——資料夾就是記憶體，`.aos` 裡的東西既是碼也是活的狀態。

**lisp 會是很重要的哲學參照。** 不是語法上的參照，是「程式與資料同型」這個立場。

> **往下一層**：這個立場具體長什麼樣——**檔案是 atom、資料夾是 list**，以及「只有 lisp
> 承載得了」這個排他主張——見 [program-form](program-form.md)。

## 五、作業系統是什麼——使用者的定義

使用者口述（2026-09-01），一個**逐步收緊**的定義：

1. **核心概念：作業系統就是方便人使用。**
2. 往下定出三件具體的事——**方便人去寫程式**、**方便人寫的程式跑**、**方便人去管理正在
   跑著的程式**。
3. 再往下加一層：**管理資源的使用**。例：LLM API 的呼叫，就是一個需要排隊進行的事情。

> **一個讀法（我的，不是裁決，可否決）**：前三件的主詞都是「人」，第四件的主詞是
> 「資源」。第四件之所以在，是因為前三件要在**有限資源**下仍然成立——排隊不是為了效率，
> 是為了讓「人寫的程式跑得起來」這句話在資源不夠時不變成空話。

這個定義是**判準**，不是描述：任何一個設計選項，都可以拿「這讓人更方便寫／更方便跑／更
方便管嗎」去問。它也決定了 aos 不必抄現代 OS 的全部——現代 OS 裡不服務這四條的部分，
可以不要。

> **往下一層**：這把尺要怎麼量——**評估指標與資源觀**（現代 OS 丟計算任務量時間，aos 任務
> 抽象；**目標優化指標已定為金錢／可預測性／人類可理解性三項**，時間空間只是粗淺優化；
> 資源分配靠 linux、權限很後面）見
> [os-metrics-and-resources](os-metrics-and-resources.md)（2026-09-03 口述進行中）。

## 六、從 CPU 到 OS，中間省略了什麼

第三節那個缺口的展開。**目的**：把「agent loop 是 CPU」到「所以蓋一套 OS」之間被跳過的
每一步列出來，供逐條對應。

已抽到 [cpu-to-os-gaps.json](cpu-to-os-gaps.json)（26 列）。欄位：

- `id`——編號 `G01`–`G26`，穩定不重排
- `layer`——落在哪一層（L0 CPU 前提／L1 OS 核心機制／L2 資源管理／L3 方便人／L4 橫向對比失效處）
- `name`——這一步的名字
- `modern`——現代計算體系裡它是什麼
- `aos_now`——aos 現在的狀況
- `why_gap`——為什麼它是 CPU → OS 之間必經的一步
- `material`——已有的材料（構想檔／裁決條目），沒有就是 `無`
- `status`——對應狀態，初始一律 `未對應`

**統計**：26 列。分層 L0 5／L1 9／L2 5／L3 3／L4 4。材料狀態：原有 **3 條全新的空白**
（`G13`／`G18`／`G25`），2026-09-01 後只剩 `G25`（使用者是誰）。`status` **2026-09-02 依
三之一的裁決分過一次**：`G01`–`G03` 歸 OS、`G04`／`G05` 歸 CPU、多程式／多次／多 CPU 綁到的
八條標「必要」、`G25` 先不做、`G24` 標理念；其餘 12 條仍 `未對應`（裁決沒直接碰到，實作走到再分）。

**五層各是什麼意思。**

**L0 是欠 CPU 的，不是欠 OS 的**（**2026-09-02 修正**：只有 `G04`／`G05` 歸 CPU，
`G01`–`G03` 歸 OS，見三之一第三步）。中斷、特權級、隔離、可存的 context、可分支的機器狀態
——這些是 OS 得以存在的**前提**；前提不齊，上面蓋什麼都是志向。其中 `G05` 特別刺眼：第一
節說「分支由 tooling 擔任」，但機器層讀不到 tooling 的結果（`loop` 只認 `result == 3`），
**三要件裡的第二件在實作上還沒兌現**。

**L1 是 OS 的最小核心。** 行程、程式與行程的分界、控制介面、換手、排程器、syscall、IPC
生產端、命名空間、載入器。九條裡有六條已經在 verdicts 的「仍開著」裡——只是**過去是以機器
的語言記的，沒有以 OS 的語言記過**，換個語言看才顯出它們其實是同一批債。

**L2 是你點名的資源管理。** 材料最多的一層：隊 S 已盤點七條打 LLM 的路徑、列出四條方案
（世界／spool／loop 閘／flock），但**一條都還沒選**。

**L3 是你的三件事。** 它們不是獨立的缺口，是 L1／L2 的**驗收面**——`G20` 押在 `G14`、
`G21` 押在 `G05`、`G22` 押在 `G08`。三件事能不能成立，取決於底下那些有沒有補起來。

**L4 是橫向對比會出事的地方。** 照抄現代 OS 會踩到的四條。其中 `G23`（訊息語意失真）最深：
現代 OS 的所有協作機制都預設通訊無損，這裡不成立。
