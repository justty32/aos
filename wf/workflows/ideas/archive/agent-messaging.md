# agent 間的訊息傳遞與錯誤累積

← [ideas](README.md)｜[LLM CPU](llm-cpu.md)｜[WORKFLOWS](../../WORKFLOWS.md)

大量 agent 合作時，訊息在 agent 之間層層轉手，每一手都可能失真。這一頁記的是**這個
失真為什麼特別難處理**，以及目前想到的幾條對策方向。還沒有拍板的機制設計。

## 問題模型：傳話失真會層層放大

打仗時的無線電比喻：團長告訴營長「攻擊四十八公里外的敵軍堡壘」，營長聽成「七十八
公里外」。這個錯誤不會停在營長身上——它會**照原樣往下傳**，後面每一層都以錯的前提
繼續做正確的推導，整條指揮鏈一起走偏。

通訊工程後來發展出各種錯誤更正與錯誤避免的手段（校驗、重傳、糾錯碼），**但那些全部
建立在數學邏輯上**：位元有沒有翻轉是可判定的，所以錯誤可偵測、可更正。

回頭看 LLM 之間的交流，失真的形式不一樣：

- 打錯字。
- 某個詞的**意涵略為偏移**——字面沒錯，但下游接收到的概念已經不是上游的那個。

這類錯誤發生在**語意層**，不是位元層。目前**難以用數學手段糾正**；也許終究可以，但
那是很久以後的事。所以現階段要另外想辦法。

在大量 agent 合作的場景，單一次微小偏移會像**蝴蝶效應**一樣被放大成**錯誤風暴**——
一個小偏差被下游當成前提，再各自展開出更多偏差。

> **前提假設**：基礎計算單元（LLM）**本身錯誤率就大於一**。在這種系統上，不能假裝
> 底層元件是可靠的然後只做上層邏輯——只能正面承認它會錯，並為此付出成本。
>
> （「大於一」照上面的錯誤風暴說法讀，比較像是**分支率**：平均一個錯誤會引發多於
> 一個下游錯誤，於是發散而不是收斂。這個讀法是補的，不是原話的定義。）

## 對策方向（三條，都還沒拍板）

### 1. 關鍵節點安排人類審核

在規劃上萬 agent 合作的架構時就想過這條：不是每個節點都審，而是挑**關鍵節點**插入
人類審核，把錯誤擋在它擴散開之前。

### 2. 多次、多 agent 審核（類比量子計算）

LLM 審核本身也會出錯，所以單一個審核者不夠。做法類似量子計算：**同一件事重複多次、
交給多個 agent 審**，用冗餘把錯誤率壓下來。

代價也跟量子計算一樣：**一個程式裡面有大量算力要花在驗證上**，真正做事的算力只占
一部分。但在基礎單元錯誤率就這麼高的系統裡，這是必要開銷，沒有更便宜的路。

### 3. 固化：簡單工作根本不需要 LLM

更早之前提過的方向。很多工作簡單到根本不必經過 LLM——**直接寫死成一支程式就好**。

固化掉的那一段是確定性的：它不會有語意偏移，也就**不需要分配驗證預算**。所以固化
同時解決了錯誤來源與驗證成本兩件事，只是適用範圍限於夠簡單、夠穩定的工作。

## 與本專案的接點（對應是補的，未經拍板）

aos 現有的分層剛好對上第 3 條：

- [`inst`](../common/code-map.md) 那層執行 POSIX 指令，是**確定性**的——這層本來就是
  「固化」的形狀。要固化一件工作，等於是把它從 LLM 那顆 CPU 搬回 `inst` 這顆。
- [`aos llm exec`](llm-cpu.md) 那顆 LLM CPU 是**機率性**的，錯誤率就在這裡。
- 所以「哪些工作該固化」在 aos 裡有具體形式：**該由哪顆 CPU 執行**。

另外兩條也各有對應：

- 第 2 條的驗證開銷會直接吃掉 LLM 資源，屬於 [llm-cpu](llm-cpu.md)「排程器的責任」
  那一節的問題——有限的 LLM 容量要怎麼在「做事」與「驗證」之間分配。
- 第 1 條的人類審核在本 repo 已經有一條現成的軸：[WAIT_USER](../../WAIT_USER.md)。

## 開放問題（尚未拍板）

- **哪些節點算「關鍵節點」**：怎麼判定一則訊息值不值得人類審核，是靠影響範圍、下游
  分支數、不可逆性，還是別的指標。
- **多 agent 審核要幾份、怎麼收斂**：多數決、全體一致、還是由另一個 agent 仲裁；
  審核者之間如果同源（同一個模型），錯誤會不會相關而讓冗餘失效。
- **驗證預算怎麼定**：做事與驗證的算力比例是固定的、按風險調整的，還是可插拔策略。
- **失真怎麼偵測**：既然數學手段目前不管用，有沒有比「再問一次 LLM」更便宜的訊號
  （例如要求下游把理解回述、比對關鍵數值、把數字／識別碼抽出來做結構化校驗）。
- **哪些錯誤其實可以數學化**：像「四十八 → 七十八」這種**數值**失真，其實是可以校驗
  的；先把可結構化的部分（數字、路徑、識別碼、列舉值）從自然語言裡抽出來單獨保護，
  可能就能擋掉相當比例的錯誤，不必等語意層的通解。
- **固化的邊界**：什麼樣的工作夠簡單到可以寫死；由誰判斷、什麼時候判斷；固化之後
  需求變了要怎麼回收。
- **錯誤發生後怎麼收**：偵測到偏移時是重跑該回合、往上回溯到偏移發生的那一手、還是
  整條鏈作廢重來。
