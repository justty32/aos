# 新 json 是什麼檔：源碼、IR，與「全塔 json」（§二十二–§二十六）

← [assembly-and-chains](README.md)｜[ideas](../README.md)｜[WORKFLOWS](../../../WORKFLOWS.md)

[compile-pipeline](compile-pipeline.md) 定出了「寫 → 編譯 → 執行」三段，但**最上游那份
「新 json」到底是什麼檔**還沒答。這一篇是同日（2026-09-01）把它答完的過程——
**注意它有時序：先裁 lisp 進場（§二十二–§二十五），收工前使用者自己改判成全 json
（§二十六）。**

## 第七部分 · 新 json 是什麼檔（使用者口述 ＋ 裁決，2026-09-01）

### 二十二、使用者：源碼檔，或 LLVM IR——**「那就兩個檔案吧」**

> **時序注意**：§二十二–§二十五 是同日**先**發生的一段，裡面的 **lisp 語法裁決在
> §二十六被使用者自己改判掉了**（改成全塔統一 json）。**「兩個檔案」與那條語意線仍然
> 有效，改掉的只是記法。** 讀的時候別把這裡當最終格式。

使用者先說：新 json 就是 **`.h`／`.c` 源碼檔**（**舒服編輯的**那種），
**或 LLVM IR／編譯器中間層**。

主 session 指出「源碼與 IR 是**兩站**不是一站」之後，**使用者裁決**：

> **那就兩個檔案吧。** 而且**從這裡開始 lisp 就可以進場了：lisp 的抽象能力足夠同時作為
> LLVM IR 和 `.h`／`.c` 的載體。**

**兩站共用 lisp 這一種記法。**

### 二十三、（觀察）兩份檔、一種記法

**一種記法扛兩站是 lisp 的看家本領**：源碼是 S 運算式，展開後**還是** S 運算式。拆平器
因此是**樹到樹的同型改寫**——lisp 傳統裡那就是**宏展開**，**不必寫兩套解析器**。

**「只有 lisp 承載得了」以精確版回歸**：Python／Lua 適合**「寫程式」**
（[program-form](../program-form.md) 那條收回仍然成立），但**「源碼與 IR 共用載體、
編譯器只是同型改寫」只有 lisp 族做得自然**。

> **`G24`「同像性到底在撐什麼」有了答案候選（未裁）**：撐的是**編譯管線的簡單**——
> 每一站同一種樹，**改寫器 agent 也會寫**。這與 [theses-review §一](../theses-review.md)
> 說的**自我改寫**是同一件事的兩面。

另外兩件小事：**`.h`／`.c` 的分法給 `B5` 留了車位**（`.h` ＝介面／簽名／型別、`.c` ＝身體
——[verdicts B5](../verdicts.md) 真要有型別，位置已經備好）；**源碼是「住在世界裡、用檔案
工具就能改」的 json**，那正是**「同像性撐自我改寫」的落地點**。

> **開放小岔路（記著，不急）**：lisp 樹落到檔案上，用**真 sexp 文字**還是 **json 編碼的
> 樹**？直覺是**源碼用 sexp、IR 用 json**，格式細節後定。
> workshop [lisp-in-aos](../../workshop/records/lisp-in-aos.md) 否定的「json 陣列＝S 運算式」
> 講的是**同像性**層面，**當樹的載體無妨**。

### 二十四、使用者：「全部都可以是 lisp」

> 當然，硬要說的，其實**全部都可以是 lisp**。

**（觀察）兩個強度要分開：**

| 強度 | 主張 | 代價 |
|---|---|---|
| **弱版** | 全部**寫成** lisp（筆記法：json 樹換 sexp 樹） | **免費**，跟現有裁決無衝突 |
| **強版** | 全部**被當成** lisp（單一 eval，`series`／`inst` 都是 form） | 撞上**「嚴解析、鬆執行」**與 **ISA 刻意封閉**兩條已裁決 |

**立場**：筆記法**隨時可以全 lisp**；語意上保留一條線——
**程式歸 eval（源碼／IR／宏），協定歸解析（`series`／`inst` 批／機器狀態）**。
線的兩邊恰好對應**「程式歸改寫、架構狀態歸世界」**。

順帶：[turing-to-os](../turing-to-os.md) 裡「**lisp 是哲學參照**」到這裡
**從哲學參照變成字面事實**——整套系統長成一棵可改寫的樹。

### 二十五、使用者的約束：「但考慮到底層要介接 posix C abi」

**（觀察）界線畫在 `inst`：**

- **`inst` 往上全是樹**；**`inst` 本身＝樹壓扁成 POSIX 叫法**（argv 是 list、env 是名值表
  ——POSIX 呼叫約定就是**退化版 sexp**，[call-format](../call-format.md) 早記過
  「CLI 呼叫＝lisp 呼叫的序列化」）。
- 編譯管線的**最後一站＝backend 出機器碼**，而**機器碼就是 inst 批**。

POSIX 與 lisp 的兩處不合各有現成答案：

1. **去程全是字串**（型別在邊界上掉光）→ 正是**「嚴解析、鬆執行」**管的事，
   那條已裁決**拿到一份新工作**。
2. **回程只有一個 int** → aos 已經用檔案系統繞過（`out/`）。
   > **由此舊帳「exit status 分不開傳輸失敗與應用失敗」有了清楚分法（觀察，未裁）**：
   > **exit code 只管傳輸層（跑沒跑起來），應用層成敗寫檔案，兩個頻道各管各的。**

**使用者裁決（2026-09-01，兩條）：**

1. **「所以還是從這邊開始進 lisp 就好」**——**lisp 從源碼／IR 層進場，不往 `inst` 以下滲。**
2. **「協定還是用 `.json`」**——**`series.json`、`inst` 批等協定檔維持 json。**

所以第二十四節那句「全部都可以是 lisp」**降級為筆記法上的可能性**，而那條語意線
（程式歸 eval、協定歸解析）**獲使用者採納**。

## 第八部分 · 最終裁決：全塔統一 json（使用者，2026-09-01 收工前）

### 二十六、**「lisp 就是太理想了，其實用啥都可以」**

同日稍後，**使用者自己回頭改判 §二十二／§二十五 的格式部分**：

> 這**本質上是工程問題**……**lisp 就是太理想了，其實用啥都可以。**

他提出 **IR 與 `.h`／`.c` 也用 `.json`**（理由：**agent 產 json 比較舒服**），討論後拍板：

> **好，就這樣！**

**最終形狀：全塔統一 json——源碼 → IR → `series` → `inst` 批，一路都是 json。**
**lisp 保留為哲學**（整套系統是一棵可改寫的樹），**語法層不進場**；
**哪天想手寫再加 sexp 糖衣**（sexp ↔ json 樹的轉換是機械且無損的，**印刷決策可逆**）。

> **這條取代的是 §二十二「lisp 當兩站載體」與 §二十五 裁決 1「lisp 從源碼／IR 進場」的
> 格式部分。** 同日的時序是：**先裁 lisp 進場、後改判全 json。**
> **沒被取代的**：兩個檔案（源碼與 IR 是兩站）、界線畫在 `inst`、協定歸解析那條語意線。

**（觀察）改判之後什麼有變、什麼沒變：**

- **沒變的是承重點**。前面 lisp 論證裡真正在扛的是**「樹」**，不是括號——**json 全數保留
  這個性質**，拆平器**仍然是同型改寫**。所以 §二十三 對 `G24` 的答案候選**不受影響**。
- **json 多賺三樣**：agent 生成**穩定**；**格式驗證卡在編譯器門口**（合「嚴解析、鬆執行」
  那條已裁決）；**一套解析器吃全家**。
- **唯一實質損失是 json 沒有註解**。源碼檔要「**舒服編輯**」，得自己想辦法
  （例如 `_comment` 欄之類）。
