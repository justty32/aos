> 之後想到再補。**除了第三節與第九節（他定的方向）之外沒有裁決**，第七、八節全是 AI 觀察與提案。

[turing-to-os 第五節](turing-to-os.md)定的是「OS 是什麼」（方便人寫／跑／管 ＋ 管資源），
本篇往下一層問**怎麼知道它做到了**：拿什麼指標量、要優化什麼、量的是哪些資源。

## 一、使用者口述：評估方式（2026-09-03）

一般作業系統的評估方式，是**給它一大堆計算任務，看它消耗多少資源（CPU／記憶體…）來完成**。
**指標就是資源的消耗，最主要是時間**，另外還有一些硬性的負載、耗電量、記憶體之類。

**重點在於：它的任務都是所謂的「計算」。** 換到 aos，**任務會比較抽象，指標會多樣化**，
例如 token 之類。

## 二、現代 OS vs aos 對照

| 面向 | 現代 OS | aos |
|---|---|---|
| **工作負載** | 一大堆**計算**任務（benchmark 套件裡的可計算工作） | **抽象任務**——不是純計算，達成什麼算完成本身要定義 |
| **主指標** | **時間**（其餘資源多半可換算回時間） | 指標**多樣化**；使用者已定目標優化指標為**金錢（token）／可預測性／人類可理解性**三項（第三節），時間、空間降為「粗淺」 |
| **資源清單** | CPU 時間、記憶體、耗電量、系統負載 | **token**（使用者點名）；AI 補的候選：LLM 呼叫次數、回合數、壁鐘時間、錢、context window 佔用、磁碟／檔案系統 |

> 資源清單那格只有 **token 是使用者點名的**，其餘是我補的候選，未經裁決。

## 三、目標優化指標（使用者口述，**這節是他定的方向**）

> **aos 的目標優化指標：硬性的時間、空間只是很粗淺的優化；最重要的優化是三個——
> 消耗的金錢（token）、可預測性、人類可理解性。**

他依「金錢 → 可預測性 → 可理解性」這個順序列出，**是否為優先序未說**，這裡不代為判定。

## 四、使用者口述：資源的分配與管理

然後是**資源的分配與管理**，包括**計算資源**、**記憶體資源**。

**權限這塊是很後面才做的。**

## 五、使用者口述：為什麼可以理想地抽象

**因為我們早就訂好 aos 是跑在 linux 上面的，善用 linux 的機制，這些東西（資源分配與管理）
就不需要考慮太多。** linux 本身的複雜在於它要處理很多跟硬體相關的邊緣情況；**aos 基於它
之上，所以可以很理想地去做抽象**。

另一個原因是 **aos 的時間粒度很粗、且允許不規則**。

## 七、AI 觀察（非裁決，可否決）

**a. OS benchmark 的前提是「正確性已定」，aos 沒有這個前提。** 現代 benchmark 只量成本，
因為任務做完沒做完是二值的；aos 任務抽象，**達成度本身不確定**，所以評估至少是二維的
（成本 × 達成度）。而且 LLM 非確定性（[gaps `G19`](cpu-to-os-gaps.json)「資源的不可靠與
不確定」），同一份任務跑兩次不會一樣——**要多次跑看分布，不是單次計時**。

**b. 時間在 OS 當主指標，是因為別的資源都能換算成時間。** 記憶體不夠就換頁變慢、負載高就
排隊變慢，最後都落回一個數字。aos 若指標真的多樣，就得問**有沒有共同分母**——**錢**是最
明顯的候選（對上 [gaps `G18`](cpu-to-os-gaps.json)「成本作為一等資源」）。第三節把金錢
放進三個目標之一，這條因此更像是「錢已經是分母之一，但另外兩個未必換算得回錢」。

**c.「記憶體資源」在 aos 有兩個候選，而且稀缺的是後者。** 一是**檔案系統**——按
[turing-to-os 第四節](turing-to-os.md)，檔案系統就是記憶體本體，但它幾乎無上限；二是
**context window**——每回合硬上限，**真正會撞牆的是它**。所以「管理記憶體資源」在這台機器
上很可能其實是**管理 context**，對上 [turing-to-os 第一節](turing-to-os.md)第三要件
「體積不能無限膨脹」。

**d. 計量與排程共用同一組計數器。** [series 第三部分](assembly-and-chains/series.md)裡
serie 自報未來幾回合的資源消耗（cpu／llm…）與建議優先級，那是**排程的輸入**；評估要的則是
**實際消耗**。同一組欄位兩個用途，而**兩者的差（申報 vs 實際）本身就是一個指標**——它也是
排程器**能不能信任自我申報**的依據。對上 [gaps `G15`](cpu-to-os-gaps.json)「資源的列舉與計量」。

**e. 評估的「任務集」是什麼還沒有。** 現代 OS 有標準 benchmark 套件；aos 要能量，就需要
**一組固定的 series 當 benchmark**。現成起點可能是
[dispatch/trial](../dispatch/trial/README.md)：那個資料夾收 2026-08-30 兩級大量試用的成果
——L1 單人／L2 團隊共 60 條發現（兩份 csv）＋ `repro/` 底下 28 支可重跑的最小重現腳本，當初
就設計成**修完可以當回歸**。把它們從「重現 bug」改讀成「固定工作負載」，就是任務集的雛形。

**f. aos 的計算資源是「LLM 呼叫」，而它的閥門不在我們手上。** 限速在 API 端（併發上限、
rate limit、配額）。排隊那題已傾向**「外部處理器自己的家務」**
（[WAIT_USER A5](../../WAIT_USER.md)，只等確認就收掉）。若那句成立，**「管理計算資源」
在 aos 可能只剩計量與預算，不含真的分配**——這會影響 [gaps `G16`](cpu-to-os-gaps.json)
（配額、併發上限與排隊）該落在哪一層。

**g.「善用 linux 機制」可以直接畫一條線。** linux 量得到、管得動的資源——工具子程序的
CPU／記憶體／磁碟／網路，經 cgroups、rlimit、nice、flock、inotify——**全部委外**；aos 自己
只需計量 **linux 看不見的那幾樣**：token、LLM 呼叫次數、context window、錢。推論：**aos 原生
的資源清單，恰好等於「linux 盲區」的清單**（正是第二節資源清單那格 aos 側的東西）。

**h. 粒度粗且不規則 → 很多 OS 機制可以不做。** 不需要搶佔（呼應
[game-process-model](game-process-model.md) 對 `G09` 的回答：引擎從不搶佔、靠自願返回）；
排程器可以**慢到只在 tick 邊界跑**，慢到**它自己可以是一個 LLM 呼叫**；計量也只需以
**「回合」為單位**，不必到毫秒。

**i. 同一件事的反面：用時間量 aos 自身沒有意義。** 粒度粗代表壁鐘時間幾乎全被 LLM 延遲
吃掉，aos 自己的 overhead 在裡面是雜訊。這回頭支持第一節那句「指標會多樣化」與第三節把
時間降為「粗淺」——**主指標從時間換成 token／回合**。

**j. 邊緣狀況不是消失，是搬家。** linux 吸掉硬體那一類，但 aos 有 linux 吸不掉的一類：
**LLM 非確定性**（`G19`）與**訊息語意失真**（[gaps `G23`](cpu-to-os-gaps.json)，L4 橫向對比
失效處）。所以「理想地抽象」要守的線是：**aos 的邊緣狀況只來自 LLM，不來自機器**——一旦有
邊緣狀況是機器來的，就是這條抽象漏了。

**k. 三個目標裡只有金錢是「消耗量」。** 可預測性與可理解性是**行為的性質**，不是消耗——
現代 OS benchmark 從不量這兩樣（最接近的只有即時系統的抖動／tail latency）。所以 **L4
橫向對比失效處又多一條：連「優化目標」本身都對不上**，不只是資源軸對不上。

**l. 可預測性有兩個現成的可量化落點。** 一是 **series 自我申報與實際消耗的差**（承 d）；
二是**同一 series 多次跑的成本／結果分布寬度**（承 a）。兩個都算得出來，**不必等「可預測性」
被定義**就能先量。

**m. 可理解性沒有機器量得了的尺。** 只能由人或 LLM 評——後者代表**評估 aos 本身要花 token，
評估會消耗它所量的資源**。它在既有材料的落點是 [turing-to-os 第五節](turing-to-os.md)的
「方便人去管理正在跑著的程式」，以及 [agent-messaging](agent-messaging.md) 的「關鍵節點
人類審核」。

**n. 三者互相拉扯，這是多目標優化。** 可預測性常靠**冗餘**買（重跑、多 agent 審核、驗證），
可理解性常靠**多寫**買（解釋、日誌、固化），**兩者都花 token**——都跟第一個目標反向。而
使用者說時間空間「粗淺」，反過來意味著**時間空間可以拿去換這三樣**（例如多跑幾回合換
可預測性），這是他的排序留下的空間。

**o. RTOS 是現成 OS 家族裡唯一把「可預測性」當主指標的**——它量的不是吞吐是 deadline 有沒有守住、
最壞延遲有沒有界。這跟第三節使用者定的三個指標裡的可預測性直接對上：橫向對比時，aos 該對的
可能不是通用 OS，而是 RTOS 的那半邊。

p. RTOS 的三樣工具在 aos 有現成落點：**deadline → 每格的預算**（game-process-model 已有「超過
預算的事等下一格」）、**優先序 → series 自報的建議優先級**、**WCET（最壞執行時間）→ 每回合最壞
token 數**。aos 時間粒度粗且不規則（第五節），所以做不到硬即時，但「軟即時＝以回合與 token 為
單位的預算」是成立的；`core/tick` 的 heartbeat／routine／schedule 就是這條線的萌芽。

q. **微核心／大核心這題其實已經在別的名字下裁過**：core-layering 說「core 只差一個分支就封閉、
agent 整套不進 core」、「外部處理器只監控資料夾、不引用 aos lib」——這就是微核心的形狀（核心只剩
exec＋loop，其餘全是靠 IPC 溝通的 server，IPC＝資料夾投遞）。差別是這裡沒人把它叫微核心。

r. 微核心的代價是 IPC 開銷；在 aos 上這個開銷不是微秒而是**一個回合**（有時還多一次 LLM 呼叫＝
錢）。所以微核心在 aos 的帳要以回合與 token 算，時間粒度粗反而讓它便宜。真正的軟肋是 gaps
`G23` 訊息語意失真——微核心假設 server 之間的訊息無損，這裡不成立。

s. 整個堆疊是**下面大核心、上面微核心**：linux（大核心）吸掉硬體那層（第五節），aos 在它上面做
微核心式的抽象。兩層各自的邊緣狀況不同（呼應觀察 j）。

## 八、頂層的四個提案（2026-09-03，使用者問「你有啥想法」；未裁決）

1. **「OS 的第一塊」可以由三個指標決定——選「帳」。** 三個指標現在一個都量不到，因為沒有帳。
   每回合記這個 serie 花了多少 token、幾次呼叫、第幾回合；跟候選 `B1` 批 header 不衝突，帳就住在
   header 旁邊。沒有帳，三個指標只是志向。
2. **三個指標指向同一條策略：縮小 LLM 出場的面積。** 「複雜式由程式確定性拆平、LLM 不出場」
   （[source-and-ir](assembly-and-chains/source-and-ir.md)）是第一個實例——每把一件事從 LLM 搬到
   確定性程式，三個指標同時變好。推到底：LLM 只留在真的要分支的那一格，其餘是編譯器的事。
3. **可理解性換成一個可測的問題：人在任意 tick 邊界打開資料夾，能不能看懂並接手。** 這題同時就是
   崩潰恢復的驗收；「檔案系統即記憶體」已鋪好路，只差判準。
4. **原型（開新工作，等使用者點頭）：** 挑三支固定 series，本機 LM Studio 各跑五次，記 token／
   回合數／壁鐘時間，畫分布——金錢與可預測性的第一條基線。金錢以「token 數 × 模型單價表」算，
   本機跑出來是零元，直接記錢會失真。

## 九、停下腳步：先去用現有的東西玩（使用者裁決，2026-09-03）

使用者收尾的話，照原意記：**在這裡只能大概知道要管理什麼；具體怎麼管理，牽涉到具體的任務使用經驗。**
作業系統的最初，也是大家試著讓一台電腦跑多個程序、遇到了阻礙，才發想出的解決方式。
**所以先在這裡停下腳步，先去用現有的東西玩玩看。**

後果：本篇與 [turing-to-os](turing-to-os.md) 的缺口表**暫停往下設計**；第八節的四個提案**不動工**
（含第 4 條原型）。「OS 的第一塊」延後到玩過之後再選。要重啟設計的人，從玩的過程記下的阻礙
開始，不從這篇的觀察開始。
