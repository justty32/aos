# 09 呼叫、交接、失敗
← [入口](README.md)

這章講一筆指令怎麼被叫起來、做完的東西怎麼交接回來、以及「沒做成」的時候會發生什麼事。前兩件想得很細，最後一件幾乎是空白——這是全書最大的洞。指令長什麼樣子見 [`.aos` 裡面](04-inside-aos.md)，什麼時候輪到它跑見 [時間](06-time-and-clocks.md)。

## 一筆指令就是一次 POSIX 呼叫

最裡面那層只做一件事：把一筆指令變成「開一支程式、給它一組參數、等它結束」。這是作業系統本來就有的動作。

- 開程式那套動作（fork/exec）只是「怎麼把控制權交出去」的機制，不是「那些位元組是什麼意思」的約定；它撐不起通用契約，只當「一筆指令＝一條 CPU 指令」的基石〔裁決 2026-08-28〕
- 接受這個代價、不修：每支程式自己發明命令列怎麼解析，模型得一支一支記〔裁決 2026-08-28〕
- 呼叫的粒度有地板（開一支程式要一兩毫秒），這是設計：微秒級的細活在程式內部做，這一層是更高層次的指令〔裁決 2026-08-28〕
- 一次呼叫只能「全給」——整個檔案系統、整包環境變數，表達不了「只准碰這三個檔」；准不准做交給外面那層〔裁決 2026-08-28〕，外層的候選是門房（見 [門房](10-doorman.md)）〔AI 觀察〕

## 八條不該改掉的優點

被拷問過一輪之後，這幾條是「動它就是退步」的，原樣留著〔裁決 2026-08-28〕。

- 參數是一個陣列，不是一整條命令列字串——這是選對的最重要一項〔裁決 2026-08-28〕
- 遇到不認得的欄位就拒絕，不是默默忽略〔裁決 2026-08-28〕
- 刻意不設任何上限：上限都是猜出來的常數，資源本來就有更好的邊界（ulimit、cgroup）〔裁決 2026-08-28〕
- 輸入、輸出、錯誤三條流是檔案不是管線——所以回合看得見、可重跑、崩了有現場〔裁決 2026-08-28〕
- 五十年的既有介面白送：每種語言、每支工具都已經會接，不用寫綁定層〔裁決 2026-08-28〕
- 崩潰隔離白送：被叫的那支段錯誤不會把你帶走〔裁決 2026-08-28〕
- 觀察與搶佔白送：ps、strace、cgroup、訊號全部現成〔裁決 2026-08-28〕
- 呼叫的邊界剛好就是狀態的邊界——世界是檔案系統，回合是粗粒度的〔裁決 2026-08-28〕

## 嚴格解析、寬鬆執行

同一份東西，讀進來的時候很嚴，跑起來的時候很鬆。這是刻意的。

- 讀：整批一起驗，一個欄位拼錯整批都不跑〔裁決 2026-08-28〕
- 跑：某一筆回非零、逾時、找不到那支程式，都不會中止後面的〔裁決 2026-08-28〕
- 三樣東西天生在界外：共用記憶體、常駐服務、串流。開新程式會把記憶體整個換掉，所以「以呼叫者的記憶體為對象」的動作不可能是指令〔裁決 2026-08-28〕
- 兩個後果：「把多份東西併起來」那支不能是指令，只能被迴圈直接呼叫進去用（注入式函式庫）；LLM 不能每回合重載，所以是常駐服務〔裁決 2026-08-28〕
- 也因此沒有高階形式：傳不進函式、沒有閉包、沒有組合。確實缺，解法是外層另做一份更通用的呼叫契約，怎麼做還沒想好〔裁決 2026-08-28〕

## 交接：三次改名

指令怎麼從投的人手上安全走到跑的人手上：三步，每步靠一次改名（改名是原子的，不會看到半成品）。

- 三步：投遞（先寫暫存名再改名）、彙整（收件匣併成一批，寫暫存名再改名蓋掉）、取件（讀進來後**先讓它從原位消失**才執行）〔裁決 2026-08-26〕
- 檔名分三段 `<名字>.<副檔名>.<狀況>`；狀況只有兩個詞：「還在生成，別碰」和「已取走，正在跑」〔裁決 2026-08-26〕
- 崩潰之後留下的現場要人來處理，不靜靜蓋掉重跑〔裁決 2026-08-26〕
- 要改的三件事，實作時自然會想到更好的做法〔裁決 2026-08-28〕：
  - 「正在跑」那個固定檔名不是鎖：改名原子但不互斥，兩支同時進來會讀到同一份、同一回合跑兩次。要用真正的互斥原語（獨佔建檔或不許覆蓋的改名）〔裁決 2026-08-28〕
  - 沒有把資料刷到磁碟：改名只保證目錄項換掉，不保證內容落地，崩潰後可能撿到零長度的現場。順序該是寫檔 → 刷檔 → 改名 → 刷目錄〔裁決 2026-08-28〕
  - 行程編號當檔名不唯一：會回收、會繞回、跨容器直接撞，改用隨機名幾乎沒成本〔裁決 2026-08-28〕

## 開子資料夾：等它＝呼叫，不等＝傳訊

父點名去跑一個子資料夾時有兩種語意。「等不等」已經有答案，「拿回什麼」還沒有。

- 同步的子世界＝父等它做完再往下走，這就是一次呼叫〔傾向 2026-09-04〕
- 脫節的子世界＝父不等，繼續走自己的；之後每一格去看固定路徑上那個檔在不在，這就是傳訊〔傾向 2026-09-04〕
- 拿回什麼還沒定；目前的提議是子資料夾 `out/` 底下一條固定路徑的檔，不在就當這格還沒有，在了才讀〔AI 觀察 2026-09-04〕
- 同一個檔，父主動去讀＝回傳值，子主動投到別人那裡＝傳訊，差別只在誰動手〔AI 觀察〕
- 這一題決定資料夾能當函數（等得到回傳）還是只能當演員（只能送訊息）〔AI 觀察 2026-09-03〕
- 巢狀深度＝幾輪才回得來，首先是可預測性的成本，其次才是 token〔AI 觀察〕

## 回傳值與成敗判定

這個格式最要命的一件事：它沒有回傳值。

- 結果的位置得由呼叫的人事先挑好、寫進那筆記錄；「參數寫在裡面、結果落在外面」這個不對稱是後面所有組合問題的源頭〔AI 觀察 2026-08-28〕
- 結束狀態只有 8 個位元，分不開「沒跑起來」和「跑了但做錯」，使用者說之後會改〔裁決 2026-08-28〕；後來從欠帳升為擋路：接力棒要推游標之前必須先能判定這一步成不成〔裁決 2026-09-01〕
- 候選分法：結束碼只管傳輸層（跑沒跑起來），做成沒做成寫進檔案，兩個頻道各管各的〔AI 觀察 2026-09-01〕

## 失敗語意：這裡是空的

子資料夾跑壞了、某筆指令失敗了、等太久了——父怎麼知道、之後怎麼處置，完全沒討論過。沒有它，「最壞情況要有界」無從量起。

- 這一題被列為還沒討論的缺口〔AI 觀察 2026-09-03〕
- 使用者裁定先去玩、這題不現在裁〔裁決 2026-09-03〕
- LLM 逾時、回垃圾、工具失敗，要重試、留錯誤標記、還是讓這塊地直接死，也沒定；模型裡沒有例外機制〔AI 觀察 2026-09-04〕
- 只看「檔在不在」分不出「還沒好」和「永遠不會好」——這是三態問題，不是兩態〔AI 觀察〕
- 兩個要避開的坑〔AI 觀察 2026-08-28〕：
  - **失敗永遠不算失敗，所以會全速無限失敗**：跑失敗也算「一次完成的執行」，沒有失敗回合、沒有歷史；一筆每格都失敗的指令會用最高速度永遠失敗下去，系統還認為一切正常〔AI 觀察 2026-08-28〕
  - **投遞被判無效，投的人永遠不會知道**：壞投遞被隔離、問題只回報給跑的那一方，從投的人看「被接受」和「被丟掉」長得一樣。對 LLM 致命：工作蒸發，它繼續用同一套錯格式產下一批〔AI 觀察 2026-08-28〕
- 一格失敗之後的語意也還沒挑：停在原地、記成一個失敗回合、自動重試、還是交給人〔AI 觀察 2026-08-28〕

## 投遞撞名與多寫者

「下一筆指令放哪一格」是全系統最擠的位置。

- 撞名規則要先定才做得了中斷語意：同名再投是覆蓋、拒絕、還是排隊？外面來的中斷有沒有優先權？被蓋掉的要不要留痕？現在是後寫的贏，不出聲〔AI 觀察 2026-09-01〕
- 這一格有三個寫者：跑的那一圈、接力棒自投下一步、外面的人插隊，所以是熱點，得原子寫加刷磁碟；外面的投遞為什麼只能落在兩格之間，見 [`.aos` 裡面](04-inside-aos.md)〔AI 觀察 2026-09-01〕

## 新實作的檢查表

這些被使用者一句「都是工程問題」整體裁掉〔裁決 2026-08-28〕，但新實作第一週就會用到，留成清單。

- 真正的互斥原語取代固定檔名當鎖；寫檔 → 刷檔 → 改名 → 刷目錄照做〔AI 觀察 2026-08-28〕
- 投遞帶 id、那批在開頭記下收了哪些 id，崩在「已發布、還沒刪投遞」之間也不會跑兩次〔AI 觀察 2026-08-28〕
- 收件匣要有背壓；它沒有作業系統那層的天然邊界，「不設上限」在這裡不成立〔AI 觀察 2026-08-28〕
- 格式要長出一塊具名的擴充區，外圈的選項才不會跟「不認得就拒絕」互撞〔AI 觀察 2026-08-28〕
- 非 UTF-8 的檔名要有逃生門（Linux 檔名是位元組串，JSON 字串裝不下）〔AI 觀察 2026-08-28〕
- 兩筆並行寫同一個輸出路徑會靜默互相截斷，格式要能表達「這兩筆互斥」〔AI 觀察 2026-08-28〕
- 指令要能宣告足跡（只動哪裡、越界算什麼）；沒有它「一格＝資料夾從 N 變 N+1」站不住〔AI 觀察 2026-08-28〕，要做規劃更是非有不可〔AI 觀察 2026-09-01〕
- 繼不繼承父行程的環境變數要做成明示的開關（金鑰不該被自動帶進去）〔AI 觀察 2026-08-28〕

## 我的意見

- **失敗語意是最大的洞，而且擋著別的東西。** 不能判定「這一步成不成」，接力棒就推不了游標、`run` 的停止條件沒依據。建議把它從「先去玩再說」裡拉出來當必答題。
- **三態比兩態重要。** 父只看一個檔在不在，分不出「還在做」和「做壞了」。我的預設：結果檔放固定路徑，子資料夾另寫一個狀態檔標明壞了；父怎麼處置寫在父的腳本裡，機器只保證「壞了看得見」。
- **「投的人收不到回饋」和「失敗不算失敗」是同一個缺：系統不記事。** 補歷史（回合編號、每格留痕）一次解掉一大半；歷史已裁定加在 `run` 那層〔裁決 2026-08-28〕。
- **足跡宣告要做的話不是加分項是前提。** 想讓 agent 做規劃，每個動作得先講清楚前置條件和效果，否則連不起鏈。第一版可以只「宣告但不強制」。

## 現況對照

- 今天沒有刷磁碟；彙整順序是寫暫存 → 發布 → 才刪投遞，中間崩掉會讓同一批跑兩次。
- 今天壞投遞被改名成規格外的第三種狀況檔，永久堆積；環境變數一律繼承父行程。
