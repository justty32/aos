# 04 `.aos` 裡面：一段命令腳本、原子指令、語法糖、兩層之間唯一的橋
← [入口](README.md)

上一章講資料夾之間怎麼互相看待（見 [資料夾就是 list](02-folders-as-lists.md)）。這章鑽進 `.aos` 裡面，看一個資料夾自己是怎麼一步一步走的：裡面裝的是一段命令腳本，腳本走到最底就是一次工具呼叫或一次 LLM 呼叫，再也拆不下去。中間那些攤平、接力棒、中間值檔，全是為了省錢省回合而做的糖。這章最要緊的一句話是：腳本這一層跟資料夾那一層互不相關，兩層之間只有一座單向的橋。

## `.aos` 裡面就是一段命令腳本
`.aos/` 是機器的地盤，裡面有一份入口腳本；打開這個資料夾，就是照著這份腳本走。

- **腳本的基本字只有兩種**：一般的 POSIX 呼叫（跑一個程式），加上 `aos` 自己的子命令（`aos run`、`aos deliver`…）。〔裁決 2026-09-03〕
- **`aos` 子命令是包好的好用命令**，資料夾那一層「使用」它們，它們本身就是糖。〔裁決 2026-09-03〕
- **它看起來像一份 shell script，因為它本來就是**：資料夾是收整袋原料的廚師，`.aos` 的內容就是廚師的做法，做法用命令語言寫。〔AI 觀察〕
- **腳本不是人直接寫進 `.aos/` 的**：人寫的原稿放資料夾頂層，被父層點名打開時才由載入器讀進 `.aos/`；細節見 [資料夾就是 list](02-folders-as-lists.md)。〔裁決 2026-09-03〕

## 最底下是原子指令，再往下就是真的機器
資料夾可以把事託付給子資料夾，子資料夾再託付給它的子資料夾……總要有個底。

- **原子指令＝一次工具呼叫或一次 LLM 呼叫**：跑一個 POSIX 指令、開一個檔、打一次 API，或問模型一句拿回一段話。它們不是資料夾，沒有內部可以再派給誰，是底。〔裁決 2026-09-03〕
- **底下不再是 aos 的事**：一次工具呼叫最後落到 Linux 上的一個行程，行程再往下是 CPU 週期。aos 從 Linux 出發，繞一圈資料夾樹與腳本，又回到 Linux 手上。〔AI 觀察〕
- **真正不確定的只有 LLM 那一格**：接力棒那段是程式在推，是確定的。把工作從 LLM 搬到確定性腳本，就是在買可預測性；推到極端，LLM 只留在「決定往哪走」的那一格。〔AI 觀察〕
- 一次 `exec` 讓資料夾走一步是什麼意思，見 [時間](06-time-and-clocks.md)。

## 一筆指令長什麼樣、一回合怎麼跑
指令（inst）是腳本被攤開後的最小一格，機器一次拿走一整批。

- **一筆指令就是一次 POSIX 呼叫的序列化**：argv 陣列、環境變數、工作目錄、標準輸入；一筆一個 json 檔。〔裁決 2026-08-28〕
- **一回合＝一整批指令同時跑**，不是一次一筆；該模仿的不是一次發射一條的 CPU，而是遊戲引擎一格掃過所有東西。〔裁決 2026-08-28／2026-09-01〕
- **一回合之內沒有資料流**：同一批裡的指令互相看不到彼此的結果，所有「上一步的產出餵給下一步」都跨回合。〔裁決 2026-09-01〕
- **逾時不在最內圈**：執行一筆指令的那層不管時間，時間由外圈管（見 [時間](06-time-and-clocks.md)）。〔裁決 2026-08-28〕
- **控制流不自己前進**：機器跑完這批就停在這裡，下一批在哪由投遞的人決定；這正是要的。〔裁決 2026-08-28〕

## 指令鏈是語法糖：攤平、接力棒、`out/`
`.aos` 裡那一整套「把 `f(g(x))` 攤平成一步一個名字、進度寫在接力棒上、中間值放 `out/`」，都不是本體。

- **本體只有兩樣**：原子指令；以及開／讀／選——開一個子資料夾、讀它的產出、決定下一個開誰。其餘全部可以改寫成「每一步開一個子資料夾」。〔裁決 2026-09-03〕
- **指令鏈是為省成本而存在的糖**：複雜邏輯本來可以直接託付給子資料夾，所以攤平那套只是省錢省回合的寫法。〔裁決 2026-09-03〕
- **為什麼還要糖**：開一個子資料夾＝生一個行程，至少多一輪、多 token、多一分不確定；在 `.aos` 裡連寫一串指令是內聯。像 C 的函數呼叫對內聯：意思相同、成本不同，兩種寫法都要留。〔AI 觀察〕
- **對照 lisp**：特殊形式只有幾個，其餘都是巨集疊出來的糖。〔AI 觀察〕
- **`.aos` 會有兩種長相**：薄的（只做開／讀／選，邏輯全在子資料夾）與厚的（一整串指令）。〔AI 觀察〕
- 攤平、接力棒格式、中間值壽命這些糖怎麼做，見 [寫→編譯→執行](05-write-compile-run.md)。

## 兩層互不相關，只有一座單向的橋
腳本層（機器層）與資料夾層（行程層）是兩套東西，不互相長進去。

- **資料夾不會被壓進指令，指令也不會長成資料夾**。〔裁決 2026-09-03〕
- **唯一的橋是腳本裡 `aos run <子資料夾>` 那一行**：它是腳本裡的一行，做的卻是開外面一個資料夾。〔裁決 2026-09-03〕
- **橋是單向的**：裡面可以開外面，外面永遠不會被折進裡面。〔裁決 2026-09-03〕
- **攤平那整套永遠不碰資料夾層**：它只講「這段腳本怎麼寫得順」。〔裁決 2026-09-03〕
- **父層得自己記開過誰、下一個開誰**：誘人的省法是「看子資料夾有沒有產出就好」，再走一步就變成「材料齊了就自動跑」——那是 Make 的模型，跟「父點名才開」相反。這幾行記在同一根接力棒上，不是第二根。〔AI 觀察〕
- 開了子資料夾之後父等不等、拿回什麼、壞了怎麼辦，見 [呼叫與失敗](09-call-and-failure.md)。

## 跳轉與中斷：都是「寫下一格在哪」
這台機器只有「當前」和「下個」，沒有「未來十個」；要走很多步，只能每一步自己投出下一步。

- **跳轉＝指令跑完自己改下一格；中斷＝外部直接把下一格換掉**。〔裁決 2026-09-01〕
- **兩者是同一件事**：都是「寫下一格指令的位置」，差別只在誰寫——自己寫是跳轉，別人寫是中斷。〔AI 觀察〕
- **還沒被取走的投遞就是程式計數器**：收件匣裡那筆還沒被拿走的，就是「下一條要執行的指令在哪」，不用另外發明一個暫存器。〔AI 觀察〕
- **中斷只能落在兩格之間**：整批取走才執行，外部投遞打不進一格的中間；跟遊戲「輸入在 frame 邊界處理」一樣。所以中斷線就是兩格之間的收件匣，缺的是把它寫成規範，不缺機制。〔AI 觀察〕
- 自投的下一步與外部中斷寫的是同一格，撞了誰贏，見 [呼叫與失敗](09-call-and-failure.md)。

## 這台機器沒有的三樣
- **原子性、封閉指令集、確定性，三樣都沒有，認了**：一筆指令跑到一半可能留下半成品、指令集是整個 PATH、LLM 每次回的不一樣。這終究不是能完全類比 CPU 的東西。〔裁決 2026-08-28〕

## 我的意見
- **`.aos` 是檔還是目錄**：使用者原話把它當一個元素寫成 `(.aos dir1 …)`，別處又說它「像 shell script」，實作裡它是一個目錄。本書統一講法：`.aos/` 是一個目錄（機器的地盤），裡面的入口腳本才是那段命令腳本；「`.aos` 是第一個元素」指的是這整個目錄。入口腳本叫什麼列為待決定。
- **薄的 `.aos` 長什麼樣沒描述過**。「開／讀／選」三個動詞是唯一線索。「選」若要靠 LLM 決定下一個開誰，那薄的 `.aos` 裡還是有一筆 LLM 指令，薄厚差的只是比例，不是種類。建議明說：薄的允許一筆 LLM 指令當「選」，但選完必須落在「開哪個子資料夾」這種可機器判定的動作上。
- **批的 id、版本、彙總狀態在新模型裡沒落點**。舊拷問說「給批一個名字」是第一件該做的事；新模型改用接力棒講進度，但接力棒也還沒定格式。這兩題其實是同一題（接力棒裡要記什麼），建議合成一題放 [寫→編譯→執行](05-write-compile-run.md) 的待決定，這裡只互指。
- **兩層互不相關，可是父層「開過誰」記在機器層的接力棒裡**。資料夾層的狀態住在腳本層的檔案裡，可以接受，但要講清楚：接力棒記的是「這段腳本走到哪」，「開過誰」只是其中幾行，不是資料夾層另有一份帳。
- **「一回合內沒有資料流」與「留著批」是同一個決定的兩面**，但後者在新文件裡常被單獨講。新實作若沿用批，這條約束一定要一起寫進去，否則同批指令互相引用結果的坑會再挖一次。
