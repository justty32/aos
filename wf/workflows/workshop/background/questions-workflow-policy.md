### 題目：現在留下的完成事項是刻意的歷史，還是應恢復 open-only？

**這題其實在問什麼**：`SESSION-LOG` 與 `WAIT_USER` 是「現在還欠什麼」的桌面，還是也兼當「以前做過什麼」的歷史。
**為什麼會有這題**：頂層規則明寫三軸只列 open，但現況曾留完成項；研討者不知道這是你改了需求，還是手工維護 drift。
**選項差在哪**：

| 選項 | 你會得到什麼 | 你會賠掉什麼 | 什麼時候會後悔 |
|---|---|---|---|
| 嚴格 open-only | 清單只顯示現在要做的，訊噪比最低 | 完成後沒有專屬歷史，只剩 Git 或其他紀錄 | 經常要回答「上次怎麼解的」，卻沒有好查入口 |
| 原檔保留完成史 | 上下文與歷史在同一處 | open view 會越來越長，新舊責任混在一起 | agent 又把已解項當待辦，或人每次要掃過整段歷史 |
| open-only＋另存 archive | 活 view 乾淨，完成證據仍可查 | 多一個歸檔生命週期與清理政策 | 完成史從來不看，卻繼續維護另一套目錄 |

**如果現在不決定會怎樣**：會擋住 `wf done` 究竟刪除、標記還是搬移，也無法判定現有檔案是正確需求還是 drift。
**最小的驗證方式**：打開最近一個月的 Git 歷史，找三次完成項；檢查你後來是否真的回頭靠 `SESSION-LOG`/`WAIT_USER` 的完成文字取得資訊。若從來沒有，歷史的價值目前只是假設；若常有，再比較它是否更適合獨立 archive。

### 題目：既有專案要持續吸收 template 更新、只做診斷，還是安裝後永久分叉？

**這題其實在問什麼**：workflows 骨架複製進專案後，還是不是一個要持續追版的上游；若是，系統只提供差異，還是可自動換未改檔。
**為什麼會有這題**：這個 `wf/` 已經比 template 多了 workshop、ideas、tick 與大量客製，卻沒有當初來源版本；所以「更新」會混合上游新版與本地刻意改動。
**選項差在哪**：

| 選項 | 你會得到什麼 | 你會賠掉什麼 | 什麼時候會後悔 |
|---|---|---|---|
| 安裝後永久分叉 | 模型最簡單，每個專案完全自主 | 上游修正與新 workflow 得手工移植 | 多個專案重複修同一個骨架漏洞 |
| 來源鎖＋人工三方合併 | 能準確看舊基底、新基底、本地差異 | 要保存 base/source metadata，合併仍由人決定 | 更新很頻繁，每次手動採用未改檔太累 |
| 自動換未修改檔 | 安全區域自動追版，客製檔只看 diff | 需要可靠的 base hash、部分失敗與恢復契約 | 一次誤判「未修改」覆蓋了人以為已客製的政策 |
| 只做 doctor | 只讀找 placeholder、壞連結、孤兒路由，風險低 | 不幫忙吸收上游變更 | 真痛點是升級合併，doctor 只能告訴你仍要自己做 |

**如果現在不決定會怎樣**：會擋住 workflows module 是否需要 source version/base hash/upgrade；若第一題已說安裝升級不痛，這題可以長期拖。
**最小的驗證方式**：找一份舊 template 與現在 `wf/` 的共同祖先（若沒有就用目前 template 當假祖先），對三個典型檔手工做一次 three-way diff；記「可自動換、必須人判、只需 doctor」各有幾份。一小時就能判斷 upgrade 機制有沒有真 workload。

### 題目：schedule／tick 是普遍 runtime 能力、少數專案特例，還是暫時維持人工喚醒？

**這題其實在問什麼**：「到某時間再做」是每個 workflows 專案都需要的底層功能，還是這個 repo 裡少數工作用 cron/人敲一下就夠。
**為什麼會有這題**：現有 `tick`/`schedule` 文件工作流已存在，但清單目前是空的；若直接升成 runtime，task schema 就要提前收 `next_at`、cursor 與 wake/Deliver 順序。
**選項差在哪**：

| 選項 | 你會得到什麼 | 你會賠掉什麼 | 什麼時候會後悔 |
|---|---|---|---|
| 人工喚醒 | 不做 scheduler，沿用現有 tick/cron | 無人到期事仍需外部機制 | 你常忘記 tick，或任務需跨夜自動繼續 |
| 只收 `next_at` | task 會記得何時到期，人/cron 只負責叫醒 | 仍沒有內建活性，需外部呼叫 | 使用者以為登記時間就會自動跑，實際沒有喚醒者 |
| 納入 `aos wf` runtime | ready、schedule、wake 有同一生命週期 | 得管常駐／外部觸發、時區、重試與 cursor | 只有一兩個定時特例，卻讓全體 task 都背 scheduler 欄位 |

**如果現在不決定會怎樣**：只擋住 workflows runtime 的 schedule 部分，不擋 Deliver 或手動 `wf start/wait/resume/done`；在清單是空的現況下可以拖。
**最小的驗證方式**：回看過去一個月實際有幾件事需要「在沒有人的時候到點自動做」，再用 OS scheduler/cron 對一個一分鐘後的假 task 呼叫一次現有 tick；若外部喚醒已完全足夠，內建 runtime 的價值就得靠更高使用頻率來證明。
