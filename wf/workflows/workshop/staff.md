# workshop — 書記與祕書（收場那兩棒）

← [workshop README](README.md)｜**發給參與者的在 [briefs.md](briefs.md)**

本檔＝**研討會收場之後的兩個角色**：書記把原始發言收攏成紀錄、祕書把紀錄變成使用者看得懂的
背景資料，以及主持人在這兩棒裡只做哪幾件事。〈書記任務書〉是可以整段複製去用的模板。

## 書記（**收攏交給他，不是主持人自己寫**）

**2026-08-25 使用者定的分工**：研討會結束後的總結**另開一個 codex 專門做**，叫**書記**。
理由直白——**省主持人的 token**。主持人不必把所有發言讀進自己的 context 再重寫一遍，
他只要把原始發言餵給書記、檢查書記動了哪些檔、然後**把檔案展示給使用者**。

| | |
|---|---|
| **書記是誰** | 一個獨立的 `codex exec` 實例，**不參與發想**，只負責收攏 |
| **他讀什麼** | 議題書 ＋ 本輪所有參與者的原始發言（**從 stdin 餵進去，不必他自己找檔**） |
| **他寫什麼** | `records/<主題-kebab>.md` **這一個檔，不准動別的** |
| **寫給誰看** | **使用者本人**。要「聽得懂的話」——不是給模型看的摘要 |
| **沙盒** | `-s workspace-write`（他要寫檔）。**主持人事後檢查 `git status`，確認只動了那一個檔** |

**主持人在收場時只做三件事**：餵原始發言給書記、檢查 `git status` 只動了那一個檔、
**丟一個檔案連結給使用者**。使用者 2026-08-25 的原話：「所謂展示檔案，就是丟個檔案連結
讓我去看……就這麼簡單。」

**不要自己把紀錄讀一遍再複述**——那正是這個角色要省掉的成本。也不要在連結旁邊
附一份自己寫的摘要，那等於白開了書記。

### 書記任務書

```markdown
## 你的身份
**書記**。你不參與發想，你的工作是把一場研討會的發言**收攏成一份紀錄**。

## 你要寫的檔
`wf/workflows/workshop/records/<檔名>.md`
<新開場＝新建；續場＝在既有檔案**追加**一節，不要改寫前面的輪次>

## 讀者
**使用者本人**。他是這個專案的作者，技術背景足夠，但他要的是**聽得懂的話**：
- 把參與者的術語換成他用過的詞。他自己的原話優先。
- **講清楚「所以呢」**——某條想法對他手上的決定有什麼影響。
- 不要寫成條列式的摘要堆。該有段落就寫段落。

## 紀錄格式
1. **檔頭表格**：主題、開場日期（絕對日期）、已跑輪數、狀態、參與的身份、
   **缺哪個角度**（誰沒發言、哪個視角沒人代表——半場的紀錄若看起來像全場，
   下次續場的人會以為那些角度已經涵蓋過了）、reasoning effort。
2. **每輪一節**，固定四段：**成形的方向**、**還在生長的想法**、
   **大家問出來的問題**、**明顯的坑**。不要寫「共識／分歧」——那是辯論的骨架。
3. **轉交提案**：這場談出來、但需要使用者拍板才能改規格的事。

## 硬規則
- **只准寫上面那一個檔**。不要碰 `docs/`、不要碰程式碼、不要跑 build／ctest。
- **`codex exec resume` 不吃 `-s`、`-C`、`--add-dir`**（沙盒與工作目錄從原 session 繼承）。
  所以**書記／祕書要寫工作區以外的檔是做不到的**——要嘛寫進 repo 再由主持人搬走，
  要嘛開一個新 session 用 `codex exec` 帶 `-C`。
- **不要加你自己的意見**。你是書記，不是第五位參與者。
- **標明哪條是誰提的。** 若某條是多位獨立提出的，**明寫「幾位獨立地都提了」**
  ——那是最強的訊號，不要讓它看起來只是其中一條。
- **標記使用者自己說過的話**，用引用格式保留原話。
- 繁體中文。長度以講清楚為準，不設上限。
- 寫完只回一句「已寫入 <路徑>」，不要把內容再貼一遍。
```

## 祕書（**讓使用者看得懂**）

**2026-08-25 使用者加的角色。** 原話：

> 另外請一個**祕書**，在書記弄出問題後，幫我準備一些**背景資料**，包括這種名詞的
> **白話解釋、嚴格、詳細說明**等等，**重點是讓我能看懂**，不然你讓我去啃那一大堆結論，
> **我也是很頭痛**。

書記解決的是「把發言變成紀錄」，祕書解決的是**「紀錄變多之後，人讀不動」**。
這兩件事會同時發生：研討會開得越多、紀錄越完整，使用者要拍板時的閱讀成本就越高。

| | |
|---|---|
| **祕書是誰** | 一個獨立的 `codex exec` 實例，**不出想法、不整理紀錄** |
| **他什麼時候上場** | **書記把問題整理出來之後**（`OPEN-QUESTIONS.md` 這類） |
| **他寫什麼** | `BACKGROUND.md`——① **名詞表**，② **每一題的導讀** |
| **他不做什麼** | **不幫使用者做決定**、不重寫結論、不再產出一份長摘要 |

**名詞表**每個詞四行固定格式：**白話**（不准用術語，一句話，拿他已經懂的東西打比方）／
**嚴格**（精確定義，這裡才可以用術語）／**在 aos 裡具體是什麼**（哪個檔、哪支命令；
還不存在就明說是提案）／**為什麼會冒出這個詞**（哪一場、誰、解決什麼）。

> **同義詞一定要合併。** 好幾場用不同名字講同一件事，是使用者頭痛的主要來源之一。

**每一題的導讀**固定五塊：這題其實在問什麼（白話重述）／為什麼會有這題／
選項差在哪（表格：得到什麼、賠掉什麼、什麼時候後悔）／現在不決定會怎樣／
**最小的驗證方式**。

> **「最小的驗證方式」是祕書最有價值的一塊。** 專案現在是一個人、`core/inst` 剛落地、
> agent loop 還沒跑過一次——**很多題不必用想的，花一小時做個小實驗就知道了。**
> 能指出這種題，就等於把一個「要拍板的決定」降級成「跑一次就有答案的事」。
> **這批「最小的驗證方式」現在是 [hackathon](../hackathon/README.md) 的現成題庫**（`background/` 共 20 條）。

### 主持人在這裡的位置

一樣是**不讀內容、只檢查改動範圍、丟連結**。順序是：

```
參與者發言 → 書記寫紀錄 → 書記收攏出問題清單 → 祕書寫背景資料 → 主持人丟連結
```

**問題清單與背景資料都好了之後**，才把選項丟給使用者選。
先丟選項再補背景，等於要他在看不懂的狀態下拍板。
