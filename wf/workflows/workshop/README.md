# workshop — 研討會／腦力激盪（多 agent 提供靈感）

← [WORKFLOWS](../../WORKFLOWS.md)｜[專案 INDEX](../../INDEX.md)

> **本檔＝流程**（研討會怎麼跑）。**這資料夾裡有什麼**（12 場紀錄、背景資料、問題清單、
> session id）看 **[INDEX.md](INDEX.md)**。
> 議題書與參與者任務書在 **[briefs.md](briefs.md)**；書記／祕書那兩棒（含書記任務書）在
> **[staff.md](staff.md)**；**實測過的 codex 指令形態在 [commands.md](commands.md)**。

**做什麼**：使用者出主題，**我當主持人**，讓多個 `codex exec` 實例各自扮演一種**身份**
（資深工程師、架構師、產品經理、普通用戶……），從那個身份的視角**提供靈感**，跑幾輪之後由我
把想法收攏成一份紀錄。**只存收攏後的東西，不存過程**。

**這是發想，不是辯論**。目的是**多**——想法的數量與角度。不逼取捨、不投票、不分勝負。
需要拍板的時候是使用者拍，不是靠參與者互打產生。

**這不是**開發工作流：workshop 不改程式、不跑 build。談出方向後轉交
[ideas](../ideas/README.md) / `docs/` / [feature-dev](../feature-dev/README.md)；
**想直接把某個方向做做看，開 [hackathon](../hackathon/README.md)**。

> **沿革**：本工作流原名 `council`（圓桌議會），角色是對立的**立場**（最小機制派／反投機派／
> 辯護人），跑出來必然是辯論。使用者要的是研討會，所以角色改成**身份**，工作流也跟著改名。
> `records/` 裡標著「辯論風格」的舊紀錄是那個版本的產物，內容仍然有效。

## 角色

| 角色 | 是誰 | 職責 |
|------|------|------|
| **主持人** | 我（Claude） | 出議題背景、挑身份、派任務書、**把原始發言交給書記**、向使用者展示紀錄。**不出想法，也不自己寫紀錄** |
| **參與者 ×3–5** | `codex exec` 一次性實例 | 從自己的身份出發**提供靈感**、接住別人的想法往前長 |
| **書記** | 另一個 `codex exec` 實例 | **收攏成紀錄**，寫給使用者看的話。**不參與發想**。見 [staff.md](staff.md) 的〈書記〉 |
| **祕書** | 另一個 `codex exec` 實例 | **讓使用者看得懂**：名詞白話解釋、每一題的導讀。見 [staff.md](staff.md) 的〈祕書〉 |
| **拍板者** | 使用者 | 出主題、隨時注入新概念、決定採納什麼 |

參與者**跨輪保留 context**：一輪結束後 codex session 不結束，下一輪用
`codex exec resume <session-id>` 接同一位（**2026-08-25 使用者指定**，改掉了原本的無狀態設計）。
session id 記進該主題的紀錄檔，**只在開場那台機器上有效**。

所以想法池現在有兩個用途：**餵給沒跑過那一輪的人**，以及**當作紀錄**。續場若隔了很久、
或換了機器 resume 不到，就退回無狀態模式——把完整想法池寫進任務書，參與者照樣接得住。

### 身份怎麼挑

身份是**視角**，不是立場。同一個主題下他們**不需要對立**，本來就會自然地在意不同的東西。

常用的一批（每題挑 3–5 個，不必固定）：

| 身份 | 他自然會在意什麼 |
|------|------------------|
| **資深工程師** | 實作起來會踩什麼、維護五年後長什麼樣、哪裡會半夜被叫起來 |
| **架構師** | 邊界劃在哪、誰依賴誰、這個決定十年後還站不站得住 |
| **產品經理** | 誰要用、解決誰的痛、不做會怎樣、什麼時候該停 |
| **普通用戶** | 我第一次碰到它會怎麼想、哪裡會誤解、我根本不在乎什麼 |
| **開發者（要接這個工具的人）** | 接進我的專案有多痛、文件夠不夠、報錯看得懂嗎 |
| **研究者／學術視角** | 有沒有前人做過、這東西其實是什麼的特例 |
| **新手** | 哪些詞我聽不懂、哪一步我會卡住 |

**挑身份的判準**：他們的**輸出會不一樣**就是好指派。如果兩個身份會講出同一批東西，
換掉其中一個。**不要指派「反對派」這種立場**——那會把研討會變回辯論。

## 一場研討會怎麼跑

**預設 3 輪，中途不停**（輪數可改）。跑完把每輪的想法池一起交給使用者。

0. **開場**：把使用者的主題寫成**議題書**（格式見 [briefs.md](briefs.md)）。使用者點頭才開場。
1. **R1 各自發想**：參與者**互不見面**，只拿到議題書與自己的身份。刻意隔離，先求角度散開。
2. **R2 接續**：拿到**完整想法池**（標明哪個身份提的）。任務是**延伸、組合、做變體**——
   **明文禁止評判與否決**。看到不同意的東西，做法是提出自己的版本，不是駁倒它。
3. **R3 收攏**：一起把想法池整理成**方向**——哪些其實是同一件事、哪些可以疊在一起、
   哪些還缺一塊。**仍然不逼定案。**
4. **收場**：**把原始發言餵給書記**，他寫紀錄；我檢查他只動了那一個檔，然後把檔案展示給使用者。

**使用者可以在任何一輪注入新概念**（實際發生過）。主持人要把它明確標成該輪的新增小節，
並判斷它該不該獨立成另一個議題。

**輪紀錄**固定四段：**成形的方向**、**還在生長的想法**、**大家問出來的問題**、
**明顯的坑**。不寫「共識／分歧」——那是辯論的骨架。寫的人是書記，不是主持人。

## 紀錄

- 落點：`records/<主題-kebab>.md`，**一個主題一個檔、追加式**。
- 檔頭記：主題、開場日期（絕對日期）、已跑輪數、狀態、參與的身份。
- 檔身：每輪一節（照上面四段），最後一節是收攏後的整體紀錄。
- **同一主題再開場**＝在同一個檔追加新輪次，參與者讀得到全部前情。
- **中止的場次照樣記**，但要在檔頭明寫**誰沒發言、缺了哪個角度**——半場的紀錄若看起來像全場，
  下次續場的人會以為那些角度已經涵蓋過了。
- **可以同時開多場**（不同主題各自一個紀錄檔）。並行的瓶頸不是機器，是主持人收攏的頻寬。
- 方向成熟後**轉交** ideas / docs，這裡改留一行指標——不留兩份真相。
- **主持人不自己改規格文件**：轉交是提案，要使用者拍板。

## 踩坑

- **想法互相重複**＝身份挑得太近，或議題書太抽象。換身份、或把議題書寫具體，別怪參與者。
- **參與者開始互相否決**＝任務書的「禁止評判」沒寫清楚，或身份被寫成了立場。
- **字數上限壓縮語意**：500 字以下時繁中會被壓到要猜語意的程度。發想輪給 600–700。
- **未登入的 github copilot MCP** 會在 stderr 噴一行 `AuthRequired` ERROR。**無害**：
  想法一律從 `-o` 的檔案讀，stderr 不看。`-c 'mcp_servers={}'` **擋不掉**（2026-08-24 實測，
  MCP 照連照噴），不要浪費時間在這上面。
- **`read-only` 會讓參與者被現有實作綁住想像**。談「應該長怎樣」的主題時，硬規則裡補一句
  「現有實作只是參考，可以主張推翻」。
