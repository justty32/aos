# workshop — 研討會／腦力激盪（多 agent 提供靈感）

← [WORKFLOWS](../../WORKFLOWS.md)｜[專案 INDEX](../../INDEX.md)

> **本檔＝流程**（研討會怎麼跑）。**這資料夾裡有什麼**（11 份紀錄、17 份背景資料、問題清單、
> session id）看 **[INDEX.md](INDEX.md)**。

**做什麼**：使用者出主題，**我當主持人**，讓多個 `codex exec` 實例各自扮演一種**身份**
（資深工程師、架構師、產品經理、普通用戶……），從那個身份的視角**提供靈感**，跑幾輪之後由我
把想法收攏成一份紀錄。**只存收攏後的東西，不存過程**。

**這是發想，不是辯論**。目的是**多**——想法的數量與角度。不逼取捨、不投票、不分勝負。
需要拍板的時候是使用者拍，不是靠參與者互打產生。

**這不是**開發工作流：workshop 不改程式、不跑 build。談出方向後轉交
[ideas](../ideas/README.md) / `docs/` / [feature-dev](../feature-dev/README.md)。

> **沿革**：本工作流原名 `council`（圓桌議會），角色是對立的**立場**（最小機制派／反投機派／
> 辯護人），跑出來必然是辯論。使用者要的是研討會，所以角色改成**身份**，工作流也跟著改名。
> `records/` 裡標著「辯論風格」的舊紀錄是那個版本的產物，內容仍然有效。

## 角色

| 角色 | 是誰 | 職責 |
|------|------|------|
| **主持人** | 我（Claude） | 出議題背景、挑身份、派任務書、**把原始發言交給書記**、向使用者展示紀錄。**不出想法，也不自己寫紀錄** |
| **參與者 ×3–5** | `codex exec` 一次性實例 | 從自己的身份出發**提供靈感**、接住別人的想法往前長 |
| **書記** | 另一個 `codex exec` 實例 | **收攏成紀錄**，寫給使用者看的話。**不參與發想**。見下面〈書記〉 |
| **祕書** | 另一個 `codex exec` 實例 | **讓使用者看得懂**：名詞白話解釋、每一題的導讀。見下面〈祕書〉 |
| **拍板者** | 使用者 | 出主題、隨時注入新概念、決定採納什麼 |

參與者**跨輪保留 context**：一輪結束後 codex session 不結束，下一輪用
`codex exec resume <session-id>` 接同一位（**2026-08-25 使用者指定**，改掉了原本的無狀態設計）。
session id 記進該主題的紀錄檔，**只在開場那台機器上有效**。

所以想法池現在有兩個用途：**餵給沒跑過那一輪的人**，以及**當作紀錄**。續場若隔了很久、
或換了機器 resume 不到，就退回無狀態模式——把完整想法池寫進任務書，參與者照樣接得住。

### 身份怎麼挑

身份是**視角**，不是立場。同一個主題下他們**不需要對立**，本來就會自然地在意不同的東西。

常用的一批（每題挑 3–5 個，不必固定）：

| 身份 | 他自然會在意什麼 |
|------|------------------|
| **資深工程師** | 實作起來會踩什麼、維護五年後長什麼樣、哪裡會半夜被叫起來 |
| **架構師** | 邊界劃在哪、誰依賴誰、這個決定十年後還站不站得住 |
| **產品經理** | 誰要用、解決誰的痛、不做會怎樣、什麼時候該停 |
| **普通用戶** | 我第一次碰到它會怎麼想、哪裡會誤解、我根本不在乎什麼 |
| **開發者（要接這個工具的人）** | 接進我的專案有多痛、文件夠不夠、報錯看得懂嗎 |
| **研究者／學術視角** | 有沒有前人做過、這東西其實是什麼的特例 |
| **新手** | 哪些詞我聽不懂、哪一步我會卡住 |

**挑身份的判準**：他們的**輸出會不一樣**就是好指派。如果兩個身份會講出同一批東西，
換掉其中一個。**不要指派「反對派」這種立場**——那會把研討會變回辯論。

## 一場研討會怎麼跑

**預設 3 輪，中途不停**（輪數可改）。跑完把每輪的想法池一起交給使用者。

0. **開場**：把使用者的主題寫成**議題書**（格式見下）。使用者點頭才開場。
1. **R1 各自發想**：參與者**互不見面**，只拿到議題書與自己的身份。刻意隔離，先求角度散開。
2. **R2 接續**：拿到**完整想法池**（標明哪個身份提的）。任務是**延伸、組合、做變體**——
   **明文禁止評判與否決**。看到不同意的東西，做法是提出自己的版本，不是駁倒它。
3. **R3 收攏**：一起把想法池整理成**方向**——哪些其實是同一件事、哪些可以疊在一起、
   哪些還缺一塊。**仍然不逼定案。**
4. **收場**：**把原始發言餵給書記**，他寫紀錄；我檢查他只動了那一個檔，然後把檔案展示給使用者。

**使用者可以在任何一輪注入新概念**（實際發生過）。主持人要把它明確標成該輪的新增小節，
並判斷它該不該獨立成另一個議題。

**輪紀錄**固定四段：**成形的方向**、**還在生長的想法**、**大家問出來的問題**、
**明顯的坑**。不寫「共識／分歧」——那是辯論的骨架。寫的人是書記，不是主持人。

## 議題書（我寫給參與者的第一塊）

```markdown
## 主題
<一句話。可以是開放的，不必是能被回答的問句>

## 背景
<現況、為什麼現在談這個。給足夠的事實，但不要暗示答案>

## 使用者自己說的
<原話的意思，盡量保留，不要幫他整理掉細節>

## 想聽到什麼
<例如：越多具體做法越好／想知道哪裡會痛／想知道用起來像什麼>

## 範圍外
<明確不談什麼，避免發散到別的題目>

## 可讀資料
<repo 內相關路徑，指路用；參與者可自行延伸>
```

## 參與者任務書（每輪、每人一份）

任務書＝議題書 ＋ 下面這幾塊，寫成一個檔丟 stdin：

```markdown
## 你的身份
<身份名>：<這個身份在意什麼、他會從哪裡看這件事>

## 目前的想法池
<前幾輪收攏後的內容，標明哪個身份提的；R1 時寫「本輪為第一輪，無前情」>

## 本輪任務
<R1：各自發想；R2：延伸／組合／變體，禁止評判；R3：收攏成方向>

## 硬規則
- 唯讀：可以讀這個 repo 的任何檔，**不要改任何檔、不要跑 build / ctest**。
- 繁體中文，**700 字以內**。超過會被截。
- **這是發想，不是辯論**。不要否決別人的想法；不同意就提出你自己的版本。
- **想法要具體**。「應該更模組化」不算想法，「把 X 拆成 Y 和 Z，因為……」才算。
- 照下面格式輸出，不要加開場白與收尾客套。

## 輸出格式
**我是誰**：<一句話，你這個身份看這件事的角度>
**想法**：<3–6 條，每條一句話講清楚，越具體越好。彼此不必一致>
**我最想接著長的**：<想法池裡別人的哪一條，你想怎麼把它往前推。R1 寫「無，首輪」>
**我會問的問題**：<你這個身份自然會問、但目前沒有答案的>
**我沒把握的**：<標記你不確定的地方。不是自我批判，是標不確定性>
**一句話**：<能直接被抄進紀錄的一句>
```

「我沒把握的」是**標不確定**，不是辯論式的自陳弱點——研討會裡沒有人需要防守。

## 書記（**收攏交給他，不是主持人自己寫**）

**2026-08-25 使用者定的分工**：研討會結束後的總結**另開一個 codex 專門做**，叫**書記**。
理由直白——**省主持人的 token**。主持人不必把所有發言讀進自己的 context 再重寫一遍，
他只要把原始發言餵給書記、檢查書記動了哪些檔、然後**把檔案展示給使用者**。

| | |
|---|---|
| **書記是誰** | 一個獨立的 `codex exec` 實例，**不參與發想**，只負責收攏 |
| **他讀什麼** | 議題書 ＋ 本輪所有參與者的原始發言（**從 stdin 餵進去，不必他自己找檔**） |
| **他寫什麼** | `records/<主題-kebab>.md` **這一個檔，不准動別的** |
| **寫給誰看** | **使用者本人**。要「聽得懂的話」——不是給模型看的摘要 |
| **沙盒** | `-s workspace-write`（他要寫檔）。**主持人事後檢查 `git status`，確認只動了那一個檔** |

**主持人在收場時只做三件事**：餵原始發言給書記、檢查 `git status` 只動了那一個檔、
**丟一個檔案連結給使用者**。使用者 2026-08-25 的原話：「所謂展示檔案，就是丟個檔案連結
讓我去看……就這麼簡單。」

**不要自己把紀錄讀一遍再複述**——那正是這個角色要省掉的成本。也不要在連結旁邊
附一份自己寫的摘要，那等於白開了書記。

### 書記任務書

```markdown
## 你的身份
**書記**。你不參與發想，你的工作是把一場研討會的發言**收攏成一份紀錄**。

## 你要寫的檔
`wf/workflows/workshop/records/<檔名>.md`
<新開場＝新建；續場＝在既有檔案**追加**一節，不要改寫前面的輪次>

## 讀者
**使用者本人**。他是這個專案的作者，技術背景足夠，但他要的是**聽得懂的話**：
- 把參與者的術語換成他用過的詞。他自己的原話優先。
- **講清楚「所以呢」**——某條想法對他手上的決定有什麼影響。
- 不要寫成條列式的摘要堆。該有段落就寫段落。

## 紀錄格式
1. **檔頭表格**：主題、開場日期（絕對日期）、已跑輪數、狀態、參與的身份、
   **缺哪個角度**（誰沒發言、哪個視角沒人代表——半場的紀錄若看起來像全場，
   下次續場的人會以為那些角度已經涵蓋過了）、reasoning effort。
2. **每輪一節**，固定四段：**成形的方向**、**還在生長的想法**、
   **大家問出來的問題**、**明顯的坑**。不要寫「共識／分歧」——那是辯論的骨架。
3. **轉交提案**：這場談出來、但需要使用者拍板才能改規格的事。

## 硬規則
- **只准寫上面那一個檔**。不要碰 `docs/`、不要碰程式碼、不要跑 build／ctest。
- **`codex exec resume` 不吃 `-s`、`-C`、`--add-dir`**（沙盒與工作目錄從原 session 繼承）。
  所以**書記／祕書要寫工作區以外的檔是做不到的**——要嘛寫進 repo 再由主持人搬走，
  要嘛開一個新 session 用 `codex exec` 帶 `-C`。
- **不要加你自己的意見**。你是書記，不是第五位參與者。
- **標明哪條是誰提的。** 若某條是多位獨立提出的，**明寫「幾位獨立地都提了」**
  ——那是最強的訊號，不要讓它看起來只是其中一條。
- **標記使用者自己說過的話**，用引用格式保留原話。
- 繁體中文。長度以講清楚為準，不設上限。
- 寫完只回一句「已寫入 <路徑>」，不要把內容再貼一遍。
```

## 祕書（**讓使用者看得懂**）

**2026-08-25 使用者加的角色。** 原話：

> 另外請一個**祕書**，在書記弄出問題後，幫我準備一些**背景資料**，包括這種名詞的
> **白話解釋、嚴格、詳細說明**等等，**重點是讓我能看懂**，不然你讓我去啃那一大堆結論，
> **我也是很頭痛**。

書記解決的是「把發言變成紀錄」，祕書解決的是**「紀錄變多之後，人讀不動」**。
這兩件事會同時發生：研討會開得越多、紀錄越完整，使用者要拍板時的閱讀成本就越高。

| | |
|---|---|
| **祕書是誰** | 一個獨立的 `codex exec` 實例，**不出想法、不整理紀錄** |
| **他什麼時候上場** | **書記把問題整理出來之後**（`OPEN-QUESTIONS.md` 這類） |
| **他寫什麼** | `BACKGROUND.md`——① **名詞表**，② **每一題的導讀** |
| **他不做什麼** | **不幫使用者做決定**、不重寫結論、不再產出一份長摘要 |

**名詞表**每個詞四行固定格式：**白話**（不准用術語，一句話，拿他已經懂的東西打比方）／
**嚴格**（精確定義，這裡才可以用術語）／**在 aos 裡具體是什麼**（哪個檔、哪支命令；
還不存在就明說是提案）／**為什麼會冒出這個詞**（哪一場、誰、解決什麼）。

> **同義詞一定要合併。** 好幾場用不同名字講同一件事，是使用者頭痛的主要來源之一。

**每一題的導讀**固定五塊：這題其實在問什麼（白話重述）／為什麼會有這題／
選項差在哪（表格：得到什麼、賠掉什麼、什麼時候後悔）／現在不決定會怎樣／
**最小的驗證方式**。

> **「最小的驗證方式」是祕書最有價值的一塊。** 專案現在是一個人、`core/inst` 剛落地、
> agent loop 還沒跑過一次——**很多題不必用想的，花一小時做個小實驗就知道了。**
> 能指出這種題，就等於把一個「要拍板的決定」降級成「跑一次就有答案的事」。

### 主持人在這裡的位置

一樣是**不讀內容、只檢查改動範圍、丟連結**。順序是：

```
參與者發言 → 書記寫紀錄 → 書記收攏出問題清單 → 祕書寫背景資料 → 主持人丟連結
```

**問題清單與背景資料都好了之後**，才把選項丟給使用者選。
先丟選項再補背景，等於要他在看不懂的狀態下拍板。

## 指令形態（已實測）

```bash
# 家裡（WSL / Linux）
codex exec -s read-only -c model_reasoning_effort=medium \
  -C /home/lorkhan/repo/simple_tools/aos \
  -o <scratchpad>/r1-p1.md - < <scratchpad>/r1-p1.brief.md

# 公司（Windows codex.exe，從 Git Bash 跑；-C 與 -o 用 Windows 路徑，stdin 用 POSIX 路徑）
codex exec --json -s read-only \
  -c model_reasoning_effort=xhigh -c model_reasoning_summary=none \
  -C 'C:\code\mine\simple_tools\aos' \
  -o 'C:\...\r1-p1.md' - < <scratchpad>/r1-p1.brief.md
```

- **`model_reasoning_effort` 預設 `medium`**（使用者 2026-08-24 指定）。
  **難題用 `xhigh`**（2026-08-25 使用者對「核心行程」那場指定）。`gpt-5.6-sol` 支援
  `low`／`medium`／`high`／`xhigh`／`max`／`ultra`；`ultra` 會自動委派任務，研討會不需要。
  **一輪之內不要混等級**——混了紀錄就不誠實，要嘛全部重跑，要嘛在檔頭明寫誰是哪一級。
- **`-c model_reasoning_summary=none`**：不要回傳推理摘要。**這是唯一真的省流量的旗標**
  （使用者在公司網路時提的）。codex **沒有**關掉串流的開關，而且關了也省不到——串流與否
  傳的是同一批 token。真正能壓流量的只有三件事：**少讀檔**（每讀一個檔就整份塞進上行
  context）、**減人**、**關推理摘要**。
- **參與者可以自己開 sub agent** 做雜活（**2026-08-25 使用者指定**）：指名 **Terra**
  （`gpt-5.6-terra`）或 **Luna**（`gpt-5.6-luna`），**一次最多一個**。`codex features list`
  裡 `multi_agent` 是 stable/true。
- **抓 session id 要用 `--json`**：stdout 變成 JSONL（本機，不影響流量），從裡面 grep 第一筆
  `session_id`。`-o` 照樣只寫最後發言。**不要用 `--ephemeral`**，那會不存 session。
- **平行 vs 依序**：預設平行（同一個訊息裡一起發）。**網路吃緊時改依序**，一個 for
  迴圈跑完四五位，丟背景等通知——2026-08-25 使用者在公司網路下就是這樣跑的。
- **五位一起跑約要幾分鐘**，而且**沒有辦法用「關掉串流」加速**——等的是模型生成的時間，
  串流只是把同樣的時間切成一段段送。要縮短只有三條路：降 reasoning effort、叫他們少讀檔、
  或減人。
- **`-o` 只寫最後發言**，乾淨可直接讀；stdout 那些事件不用管。
- **`-`＋stdin**：任務書當檔案餵進去，比塞進 argv 可靠（長文、換行、引號都不會出事）。
- **逾時**：每位包一層 `timeout 600`。有人掛掉或吐空檔，就在輪紀錄裡**明寫少了誰**，
  用剩下的繼續——不要靜默略過。
- **拋棄式檔案**：任務書與原始發言全部放 session 的 scratchpad，**不進 repo**。
- 參與者**讀得到 `../` 的兄弟專案**（read-only sandbox 只擋寫，不擋跨目錄讀）。

## 紀錄

- 落點：`records/<主題-kebab>.md`，**一個主題一個檔、追加式**。
- 檔頭記：主題、開場日期（絕對日期）、已跑輪數、狀態、參與的身份。
- 檔身：每輪一節（照上面四段），最後一節是收攏後的整體紀錄。
- **同一主題再開場**＝在同一個檔追加新輪次，參與者讀得到全部前情。
- **中止的場次照樣記**，但要在檔頭明寫**誰沒發言、缺了哪個角度**——半場的紀錄若看起來像全場，
  下次續場的人會以為那些角度已經涵蓋過了。
- **可以同時開多場**（不同主題各自一個紀錄檔）。並行的瓶頸不是機器，是主持人收攏的頻寬。
- 方向成熟後**轉交** ideas / docs，這裡改留一行指標——不留兩份真相。
- **主持人不自己改規格文件**：轉交是提案，要使用者拍板。

## 踩坑

- **想法互相重複**＝身份挑得太近，或議題書太抽象。換身份、或把議題書寫具體，別怪參與者。
- **參與者開始互相否決**＝任務書的「禁止評判」沒寫清楚，或身份被寫成了立場。
- **字數上限壓縮語意**：500 字以下時繁中會被壓到要猜語意的程度。發想輪給 600–700。
- **未登入的 github copilot MCP** 會在 stderr 噴一行 `AuthRequired` ERROR。**無害**：
  想法一律從 `-o` 的檔案讀，stderr 不看。`-c 'mcp_servers={}'` **擋不掉**（2026-08-24 實測，
  MCP 照連照噴），不要浪費時間在這上面。
- **`read-only` 會讓參與者被現有實作綁住想像**。談「應該長怎樣」的主題時，硬規則裡補一句
  「現有實作只是參考，可以主張推翻」。
