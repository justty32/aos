# 題目導讀：unknown、crash 與斷電耐久
← [BACKGROUND](../BACKGROUND.md)｜[workshop](../README.md)｜[待答問題](../OPEN-QUESTIONS.md)

### 題目：LLM／有副作用工具可能已執行但本機沒記下時，要停住、只在 provider 可對帳時自動恢復，還是直接自動重試？

**這題其實在問什麼**：本機只知道「沒拿到完整結果」時，預設是當作沒做再做一次，還是先阻止重複付費、寄信、部署。
**為什麼會有這題**：遠端可能在回覆傳回前已經做完；本機 `rename`、`.runi` 與重導向都無法證明 provider 的事實，所以自動重試可能重做副作用。
**選項差在哪**：

| 選項 | 你會得到什麼 | 你會賠掉什麼 | 什麼時候會後悔 |
|---|---|---|---|
| unknown 一律停住 | 不會因猜測而默默重付錢／重做 | 無人值守活性差，需人判定 retry/lost/adopt | 外呼便宜且天生冪等，系統卻總是等人 |
| 可對帳才自動恢復 | 有 provider key/request ID 證據時可自動，無證據時保守 | adapter 要理解每家 provider 查詢／冪等能力 | provider 介面常變，通用 core 與 adapter 邊界模糊 |
| unknown 自動重試 | loop 最有活性、實作最簡單 | 明示接受重複付費與副作用 | 第一次重複寄信、部署或收費就難以挽回 |

**如果現在不決定會怎樣**：會擋住無人 agent loop 的 crash 預設、Effect/resolve 是否進近期 scope；互動玩具實驗可以每次 unknown 就手動停。
**最小的驗證方式**：先不用付費 API：做一個假 provider，收到 request 就把 key 記到另一檔，但在回結果前故意斷線；分別實演停住、查 key 後取回、直接重送，觀察三種介面要留哪些證據。實驗能驗機制，不能代替你選風險。

### 題目：首版只保優雅 Ctrl-C，還要涵蓋 hard kill，或連斷電都列入恢復契約？

**這題其實在問什麼**：你所說的「可恢復」要對付的是收到中止通知、連通知都來不及的強制死亡，還是內存與磁碟全斷。
**為什麼會有這題**：三種故障能留下的證據不同：Ctrl-C wrapper 有機會收尾，hard kill 只剩之前已落盤的事實，斷電還得考慮 cache/fsync 與 directory entry。
**選項差在哪**：

| 選項 | 你會得到什麼 | 你會賠掉什麼 | 什麼時候會後悔 |
|---|---|---|---|
| 只承諾 Ctrl-C | wrapper 可主動記狀態，測試矩陣最小 | `kill -9`、crash、斷電只觀察不保自動恢復 | 實際最常見的是宿主被強制關掉，恢復契約幾乎沒涵蓋現場 |
| Ctrl-C＋hard kill | 可依預先落盤的 request/`.runi` 辨識未完成 | 要做 kill-point 測試與更審慎的 commit 順序，遠端仍可 unknown | 產品在 laptop/電源不穩環境長跑，斷電後本地證據也丟失 |
| 連斷電都承諾 | 契約最強，檔案與目錄耐久進入驗收 | 每次投遞成本、跨平台差異與故障測試大增 | 實際資料可重算，卻為極少斷電事件付出每次 I/O 成本 |

**如果現在不決定會怎樣**：會讓「可恢復」成為每個人想像不同的詞，擋住 supervisor、temp 清理、fsync 與測試驗收；可先將首輪定為「只觀察、不承諾」來取得現場資料。
**最小的驗證方式**：對一個只寫臨時檔的假三步 loop，在「request 已寫」、「副作用已發生」、「result 尚未 rename」三點各做 Ctrl-C 與 hard kill；不必真拔電，先看 hard kill 是否已逼出你需要的證據。斷電級只能用專門 power-cut/VM 測試，一小時沒有辦法用想的驗完。

### 題目：Deliver／Publish 只保證 rename 的可見性原子，還是提供 `--durable` 承諾斷電後仍存在？

**這題其實在問什麼**：Deliver 回成功時，只代表此刻其他 process 會看到完整檔，還代表立刻斷電、重開機也不會丟。
**為什麼會有這題**：`rename` 解的是 namespace 可見性，不自動刷出 file data 與 parent directory entry；若把兩者混叫「耐久」，會給呼叫者假保證。
**選項差在哪**：

| 選項 | 你會得到什麼 | 你會賠掉什麼 | 什麼時候會後悔 |
|---|---|---|---|
| 只保 rename 可見性 | 契約輕、快、跨平台容易誠實描述 | 不保證 power loss 後投遞仍在 | world 當無人長跑工作，斷電後丟一筆不可重建請求 |
| 可選 `--durable` | 重要投遞可明示付 fsync 成本，一般路徑保持輕 | 要定義檔案／目錄 fsync、錯誤與平台保證 | 使用者無法知道何時需要旗標，導致一律開或一律忘 |

**如果現在不決定會怎樣**：會擋 Deliver `--durable` 是否進第一版，也會讓「成功」的文件難以誠實下筆；可先不收旗標並明說只保可見性。
**最小的驗證方式**：用目標平台做一個 1000 次小檔投遞 benchmark，比較單純 write＋rename 與 file fsync＋rename＋directory fsync 的延遲，同時寫下「哪些資料真的不能重算」。這能在一小時量成本；實際斷電保證仍需另一套故障測試。
