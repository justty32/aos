# 題目導讀：子工作提交、等待與失敗
← [BACKGROUND](../BACKGROUND.md)｜[workshop](../README.md)｜[待答問題](../OPEN-QUESTIONS.md)

### 題目：lane／子工作可直接改世界、完成即共享，還是只能交 proposal／delta 由 root 原子 commit？

**這題其實在問什麼**：多個子工作同時算時，它們能不能直接把公用檔案改掉，還是只能交一包候選改動，由一個人決定何時算進世界。
**為什麼會有這題**：`.runi` 只鎖一個 queue，不鎖共享 world；兩個 lane 直改同檔都可自認成功，卻沒有單一回合順序與 crash 後結果歸屬。
**選項差在哪**：

| 選項 | 你會得到什麼 | 你會賠掉什麼 | 什麼時候會後悔 |
|---|---|---|---|
| 子工作直接寫／立即共享 | 實作直接，父不需另一次 commit | 隔離、回滾、確定因果與衝突政策少 | 第一次兩個 lane 改同一檔或讀到對方半成品 |
| 完成後一次 commit | 子工作期間隔離，結果有明確可見時點 | 需要快照/delta、衝突處理與 commit 失敗契約 | 子工作本來就必須與父共享逐步狀態，批次 commit 人為阻塞 |
| proposal/delta 交 root | 併行計算、單點承認，root 權力落在提交邊界 | root 是瓶頸，得懂 delta 套用、衝突與 receipt | 大量互不衝突的小結果都卡在中央提交者 |

**如果現在不決定會怎樣**：會擋住子工作磁碟 ABI、root 權力的具體邊界、receipt 歸屬與父 crash 恢復；但目前沒有 lane 或第二個 world，對 T5 完全可拖。
**最小的驗證方式**：不做 lane runtime：複製一個只有兩檔的玩具 world，用兩個 shell process 同時修同檔與修不同檔；再各做一次「直寫」與「各寫 delta、最後一次套用」。比較你實際需要的是衝突保護、完整可見，還是只是理論上喜歡 root。

### 題目：父等待子工作要採同步阻塞、持久 join handle，還是接完成事件／receipt？

**這題其實在問什麼**：父工作啟動子工作後，是原地一直等、先留一個拉環下次再查，還是先結束、等子工作送回完成通知。
**為什麼會有這題**：子工作若跨回合或父 process crash，一個記憶體內的 `waitpid` 不足以表達「之後繼續等同一件事」。
**選項差在哪**：

| 選項 | 你會得到什麼 | 你會賠掉什麼 | 什麼時候會後悔 |
|---|---|---|---|
| 同步阻塞 | 程式流最直接，父結束就表示子已收齊 | 長工作佔住父回合，crash 後續等較難 | 子工作等人/等網路很久，父整個 world 被卡住 |
| 持久 join handle | 父可結束回合，之後檢查同一組子工作 | 要定 handle 身分、保留、搬移與 stale 語意 | 子工作都很短，卻每次生成一套耐久 join 狀態 |
| 完成事件／receipt | 父不持續阻塞，子完成後原子投回結果 | 需要 inbox/queue、correlation、重複事件與順序契約 | 父其實需要「所有子都完成」的 barrier，結果還得自己再 join |

**如果現在不決定會怎樣**：會擋住父回合能否在子工作未完時結束、crash 後如何續等以及結果投遞位置；目前沒有子工作 runtime，可拖到第一個真跨回合子工作。
**最小的驗證方式**：用一個 5 秒完成、一個需手動建檔才完成的假子工作，各用三種方式寫最小 shell driver；在父中途結束後重開，看哪一種最容易回答「我在等哪一件事」。

### 題目：子工作失敗後，父要停住、隔離該子工作、重試，還是照常提交下一回合？

**這題其實在問什麼**：一個分出去的工作失敗時，整體世界要不要停；若不停，失敗是被關在旁邊、自動再做，還是當作一筆正常結果繼續。
**為什麼會有這題**：沒有失敗政策，`failed` 只是一個字，無法決定 lane 還能不能被收割、receipt 算不算完成、父是否可 commit。
**選項差在哪**：

| 選項 | 你會得到什麼 | 你會賠掉什麼 | 什麼時候會後悔 |
|---|---|---|---|
| 父停住 | 現場最完整，不會默默在不完狀態繼續 | 一個不關鍵子工作可卡所有進度 | 多個獨立工作中只壞一個，其他明明可完成 |
| 隔離子工作 | 父可處理其他工作，failed lane 留現場 | 需要生命週期、收割與之後如何處理的界面 | 失敗 lane 一直堆積，沒人負責最終決定 |
| 自動重試 | 對短暫錯誤有活性 | 要有上限、退避、冪等，否則可重複副作用 | 錯誤是永久的或已造成外部作用，重試只會放大損失 |
| 照常提交 | 失敗成為可被下一步處理的正常資料 | 父與後續步驟必須真正理解 failure result | 後續步驟沒檢查就把不完結果當成成功事實 |

**如果現在不決定會怎樣**：會擋住 lane 生命週期、失敗 receipt、自動重試與人工恢復介面；沒有 lane 前可拖，不必為 T5 先定。
**最小的驗證方式**：準備三個假子工作：一個成功、一個永久失敗、一個第一次失敗第二次成功；用四種政策手動推兩回合，只看父世界最後能不能清楚回答「成功了哪些、還欠哪些」。

### 題目：序言或尾聲失敗時，業務批次要不要跑，並且要不要保留 `.runi` 把整回合視為未完成？

**這題其實在問什麼**：固定的回合前置／收尾步驟壞了時，中間真正要做的工作還算不算可執行；尤其是尾聲壞了，前面已做的事要算這回完成還是留現場。
**為什麼會有這題**：`kernel.json` 方向已被使用者收下，但現有「一回合＝一整批」與 `.runi` 正常返回就刪的契約還沒納入序言/尾聲失敗。
**選項差在哪**：

| 選項 | 你會得到什麼 | 你會賠掉什麼 | 什麼時候會後悔 |
|---|---|---|---|
| 核心失敗就不跑業務 | 序言/尾聲是硬門檻，安全不變式清楚 | 非關鍵的收尾故障也可阻斷業務 | 尾聲只是紀錄/清理，卻讓已完業務長期無法前進 |
| 業務可跑，尾聲失敗算未完 | 保留已做業務與尚未收尾的誠實現場 | 恢復時得分辨只重做尾聲還是整批，不能盲目重跑 | 沒有 phase 證據，留 `.runi` 只告訴你沒完，不告訴你欠哪段 |
| 業務與下一回照常 | 核心 hooks 不會卡 queue，活性高 | 序尾不再是可依賴契約，錯誤只能旁記 | 尾聲負責 commit/cursor/不變式，一次忽略就讓後續讀到不一致狀態 |

**如果現在不決定會怎樣**：會擋 `kernel.json` 進規格與 executor 控制流；不擋現有沒有 kernel 的 `aos exec` 與 T5 私有 driver，因此可在 kernel 真正實作前拖。
**最小的驗證方式**：不改 C++：用 shell 串起 `prologue; business; epilogue`，讓三段各有一個可辨識的檔案作用，分別在序言與尾聲故意失敗；對三種政策各實演一次重開，看哪個現場能讓你無需猜測就知道可以重做什麼。
