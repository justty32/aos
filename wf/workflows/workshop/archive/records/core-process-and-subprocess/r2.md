# R2 想法池（延伸／組合／變體）

← [核心行程、子行程，與外部處理器的契約](README.md)

主軸是使用者在 [decisions.md](decisions.md) 注入的「行程有自己的資料夾」。

## 成形的方向

1. **「好像不太對」的答案：行程樹可以巢狀，取件權不必巢狀。** 狀態分散在子目錄，claim／commit
   權集中於 root。使用者原句「子行程的執行方式就是在 `xxx/.aos/inst.json` 中，被另一個 `aos exec`
   去呼叫」裡，「另一個 `aos exec`」會產生第二個 owner，跟「單一 `aos exec` 掌握至高權力」打架。
   分開就兩條都成立：**資料夾巢狀（拓樸），執行權不巢狀（權限）。**

2. **兩種拓樸**：

   | | **A 完整巢狀／遞迴 capsule** | **B 中央核心／集中 lane** |
   |---|---|---|
   | 子資料夾裡有什麼 | `procs/<id>/.aos/{kernel.json,inst.json,inst.tempd}`——**一個完整的小世界** | 只有 `procs/<id>/{state,outbox,result}`——**私有狀態，沒有 queue** |
   | queue 在哪 | 子世界自己的 `.aos/` | 父的 `.aos/lanes/<id>/` |
   | 誰推進 | root 帶 capability 呼叫 `aos exec <child>`，**每次只推一回合，不啟動子 loop** | 唯一的 root `aos exec` 以 root-fd／cwd 輪流 multiplex 所有 lane |
   | 好處 | **子世界跟主世界同構**——最大複用；可單獨搬移、測試、除錯 | **不產生第二個 owner**；root 完整掌握 claim／排程／回收 |
   | 代價 | **多層 kernel 的升級與版本相容**；多層 `.runi` 的診斷體驗 | 子世界**不能自啟動**、不能單獨搬走 |

3. **合成：「同一磁碟 ABI、兩種執行拓樸」。** 先固定資料夾 ABI，遞迴 `exec` 與單 root 排程就是
   可替換的實作：兩種拓樸共用同一個 `<proc>/root/.aos/`，變的只有誰去推它。同時滿足「複用」與
   「簡潔」，不必現在選 A 或 B。

4. **變體：親緣從實體路徑解綁。** lane 平放在 `.aos/lanes/<uuid>/`，親子關係用 `parent`／
   `world_root` 欄位表達；父只在 `.aos/procs/<id>.json`／`proc-table.json` 記 URI、能力與 join 狀態。
   路徑可搬，身分與佇列不變。

5. **job → lane 是單向升格路徑**（「拆成 job 和 lane，各自發展」，加一條原子升格通道）：
   - **job**＝一次性、不可變、沒有私有 queue、由父回合領取並執行、產生 receipt 的 envelope。
     版面：`jobs/<id>/{request.json,status.json,result/}`。
   - **lane**＝有 `kernel.json`、inbox、`.runi`、cursor、私有狀態、獨立恢復。
   - **升格**：原子建立 `<id>.temp` → 寫 manifest ＋輸入快照 → `rename` 成 lane；原 job 留下
     `promoted_to`／join handle，**沿用同一個 correlation ID**。
   - **觸發點**：首次需要跨回合等待、重試、私有狀態、收第二件工作、或 spawn 別人。

6. **root 的至高權力清單**：唯一能配 ID、建立／終止／收割 lane、claim、授予可寫路徑的 capability、
   分配執行額度／CPU slot、升級 kernel、隔離與處理 crash、承認 completion、跨 lane commit、把子行程
   的 delta 套用父世界。子行程只能向父的 `control.tempd/` 投 spawn／wake／cancel 請求。
   **並行計算、單點提交**：lane 只交 proposal，barrier 之後由 root 發布。

7. **kernel 分層合成**：有效 kernel ＝ root 強制段 ＋ 父政策 ＋ 本地 hooks，合成後的 hash 隨
   `.runi` 留存（回合現場記得用哪一版 kernel 跑的）。`kernel.json` 不必每個資料夾各寫一份完整的。

## 還在生長的想法

- **`aos exec --once`**：父呼叫子時只推一回合，明講不啟動子 loop。
- **`.aos/children.tempd/`（子行程結果）與 `control.tempd/`（子行程控制請求）**：方向相反，分開不混用。
- **lane 狀態機**：`created → ready → running → waiting → done|failed`。
- **「只能寫自己的子樹」成為可執行契約**：把 root fd／capability 疊進 `proc-table`。

## 大家問出來的問題

1. **親緣綁路徑還是 UUID？** 子世界移出父樹之後，process ID、父子關係、capability、`$ref`、
   未收的 receipt 還有沒有效？
2. 父等子是阻塞、join，還是收事件？
3. 子行程的成果立即共享，還是 commit 之後才進父世界？
4. 尾聲失敗時，由哪一層保留現場？（多層 `.runi` 時才有意義）
5. job 升格的門檻是「首次 yield」還是「首次需要獨立恢復」？
6. 移動之後 capability 是否失效？

## 明顯的坑

- **完整巢狀的真正代價是升級**：多層 `kernel.json` 的版本相容與升級、多層 `.runi` 的診斷體驗。
  A 的好處（子世界跟主世界同構）正是它的痛處（每一層都要一起升級）。
- **「巢狀」照字面做成子 loop 就會產生第二個 owner**，違背單一 root。父呼叫子必須推一回合就回來。
- **升格不沿用同一個 correlation ID**，job 的 receipt 與 lane 的結果就對不起來。
