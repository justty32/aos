# R1：不專屬單題的部分

> 還在生長的想法、大家問出來的問題、明顯的坑。這三段橫跨四題，所以沒有拆進單題檔。

## 還在生長的想法

- **能力到底是什麼，尚未成形**：安全邊界還是排程提示、威脅模型是什麼、綁 fd／inode、path 還是
  UUID。這不只影響 `World` 厚度，也決定移動後能力能否續效。
- **「搬移」還不是一個完整動作**：能否在回合中搬、能否跨 filesystem、move 與 copy 怎麼分。只允許
  世界靜止時同 filesystem 內 rename，現有原子模型能沿用；要跨 filesystem 或帶著未完成回合搬，queue、
  receipt、kernel 現場與身分表怎麼一起切換，沒有完成的協定。
- **C 的「共同磁碟 ABI」只有概念清單，沒有最小形狀**：identity、queue、owner／claim、kernel 來源或
  快照、生命週期、未完成回合與原子提交邊界。直接把 A、B 需求取聯集，可能把尚未理解的差異永久寫進 ABI。
- **分層 kernel 的有效快照放哪裡，尚未成形**：內容隨 `.runi` 保存、存不可變物件後由 hash 指過去，
  還是每個世界常駐一份物化檔；三者的清理與復原成本不同。

## 大家問出來的問題

| 問題 | 它卡住哪個決定 |
|---|---|
| `.runi` 要能**重建**當時的有效 kernel，還是只要驗出 hash 不同？舊 `.runi` 到哪裡取有效內容？ | 決定第二題只存 hash 是否足夠，也決定離線重播能否成立 |
| move／crash 時，身分、位置、政策、回合各以哪個檔為真源？搬移中的 receipt 由誰原子改址？ | 決定 UUID／混合方案是否真的比路徑可靠，而不只是多一本表 |
| 移動能不能發生在回合中？能不能跨 filesystem？若能，原本三次 `rename` 的原子性如何保留？ | 決定第四題承諾的是「改名」還是真正可攜搬移 |
| move 與 copy 怎麼分？複製後是否換身分？ | UUID 若不定 copy 語意，會出現兩份資料宣稱是同一個行程 |
| capability 是安全邊界還是路由資料？綁 fd／inode、path 還是 UUID？ | 同時卡住第一題與第四題；也影響 move 後既有能力是否有效 |
| 子結果何時原子 commit？ | A／B 若提交邊界不同，C 的共同 ABI 就不能只統一資料夾名稱 |
| 父改 kernel、父失聯或世界搬家後，下一回合沿用舊政策還是立刻繼承新政策？ | 決定第二題的繼承是動態查找，還是 claim 時快照 |
| 不引用 aos lib 的外部處理器，要用什麼一致性測試證明自己正確解讀新 ABI？ | 四題一旦改磁碟契約，外部處理器如何維持「構造很簡單」仍缺答案 |

## 明顯的坑

- **把 root fd 當成安全沙盒。**未定義絕對路徑、`..`、symlink 與 fd 繼承前，root fd 只能改善定址，
  不能自動形成權限邊界。
- **`.runi` 只留 kernel hash，卻宣稱事故可重現。**hash 沒有內容；父檔一改，舊回合只能知道「對不上」，
  不能知道「當時跑了什麼」。
- **把 A 的同構誤當成免費複用。**多層 kernel／版本／`.runi` 的升級與診斷是 A 的主要代價；樹越深，
  每一層都可能是不同版本、不同事故現場。
- **用 C 延後所有決定。**C 只能延後「誰推進 lane」，不能延後 identity、queue、claim owner、kernel
  來源與恢復語意；第四題不先定，磁碟裡的引用連要指位置還是指身分都不知道。
- **以為 UUID 穩定就代表一切續效。**`$ref` 的 world-root 語意仍可能因搬家而變；capability 是否續效
  要另定；registry 本身還會帶來目錄／表雙真相與孤兒。
- **把跨 filesystem 搬移仍叫作一次原子 rename。**這個前提不成立；要跨 filesystem，就要另有搬移交易
  與失敗恢復協定。
