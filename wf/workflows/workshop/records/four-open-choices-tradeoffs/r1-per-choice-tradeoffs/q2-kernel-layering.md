# 二、`kernel.json` 要單層，還是分層合成

> R1〈成形的方向〉的第二題。

這題的強訊號不是四位選了同一邊，而是**四位獨立地都指出兩邊各自保住了不同的東西**：
單層保住「整個資料夾帶走就自足」，分層保住「root 政策只改一處就真的強制到所有子行程」。

| 選擇 | 得到什麼 | 付出什麼 | 什麼時候會後悔 | 能不能反悔 |
|---|---|---|---|---|
| **單層：每個世界一份完整 kernel** | 一個世界自己就能驗證、搬移、離線重播；外部工具只讀一個檔，不必理解繼承；事故現場較容易重現 | 每個子世界都複製政策；修漏洞或升版本要掃過所有 `.aos`，漏一份就產生政策漂移 | 子世界／lane 數量多、壽命長，或 root 有必須一致套用的安全政策時 | **單層轉分層較容易**：可先把舊的完整檔視為本地 override；但仍要定義它與新 root／父政策的優先順序，並批改舊 kernel |
| **分層：root 強制段＋父政策＋本地 hooks** | root 政策一次更新；父層規則可複用；本地只寫差異，不必在每層複製整份 kernel | 合併、覆寫、刪除、衝突與版本相容都會變成磁碟 ABI；父失聯時怎麼辦也要定義；世界搬到別的父下面，可能不改本地檔卻改了行為；外掛若要理解來源，也得實作同一套合成規則 | 世界常被搬移、要離線單獨重播，或不能接受「祖先改檔後，子世界下一回合暗中換政策」時 | **分層轉單層要把每個世界的有效 kernel 展開並落盤。**這是存量資料遷移，而且會失去原本的來源／繼承資訊 |
| **第三條路：分層撰寫，物化有效內容** | 平時保留 root／父／本地的複用；每一回合或每個世界另有一份可直接執行、可重現的有效 kernel | 同時要管理「來源層」與「有效內容」，必須定義何時重算、哪一份是執行真相，以及更新中途 crash 怎麼恢復 | 若兩份表示經常失同步，除錯會從一個真源變成追兩套狀態 | 轉成純單層可保留物化內容、丟掉來源；轉成純分層可丟物化檔，但會失去既有事故重現能力。兩個方向都要遷移 metadata |

資深架構師與要接工具的開發者明確提出第三條路；資深工程師和研究人員也從事故重建角度得到
同一個必要條件：**`.runi` 只存合成後的 hash 不夠。**四位獨立地都指出，父 kernel 改掉後，
hash 只能證明「現在這份不是當時那份」，不能把當時真正執行的內容找回來。若 `.runi` 的目的
包含重跑／診斷，就得存有效內容或可取回內容的不可變版本；若只想驗出版本不符，hash 才足夠。

這也碰到使用者對外部處理器的原話：

> **外部處理器的構造會很簡單，甚至不需要引用 aos lib。**

要接工具的開發者指出，若外部處理器也必須自己解析 root／父／本地的合成規則，這份「簡單」
就會變重；若它只看已物化的有效檔，複雜度仍可留在 `aos exec` 一側。
