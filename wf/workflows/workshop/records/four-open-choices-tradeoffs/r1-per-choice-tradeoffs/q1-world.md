# 一、`World` 抽象要不要收

> R1〈成形的方向〉的第一題。

**四位獨立地都指出同一個分界**：只要一支 `aos exec` 要同時推進多個世界，`cwd` 就不夠用，
因為它是整個 OS 行程共用的；`root fd` ＋ `*at` 系列 I/O 才能讓每次操作明講自己屬於哪個
世界。反過來，如果每個世界本來就永遠由獨立 OS 行程推進，那這層抽象可能只是多繞一層。

| 選擇 | 得到什麼 | 付出什麼 | 什麼時候會後悔 | 能不能反悔 |
|---|---|---|---|---|
| **收 `World`：root fd ＋版本＋能力** | 世界辨識、版本檢查與能力檢查集中在同一入口；一支 `aos exec` 可推多個世界；測試可注入假的 root；日後做集中 lane 時已有可用的世界 handle | handoff、`$ref`、重導向與其他 I/O 都要從「相對 cwd 的字串」改成「相對哪個 fd」；還要定義 `fork` 後 fd 如何帶過去、symlink、`..`、絕對路徑與 `fchdir` 怎麼算 | 最後仍是一世界一行程，而且 `World` 被做成很厚、每次小操作都得穿過它 | **若只是內部 handle，磁碟格式不變，反悔主要是改實作。**但若能力落盤、API 對外公開，或外掛已依賴 fd／cwd 語意，拿掉或收緊規則就會成為相容性變更 |
| **不收，維持 `aos exec` 內的 cwd／版本判斷** | 現有路徑協定與外掛假設不用動，眼前實作最少 | 驗證容易散在各入口；一支行程仍只能安全地以一個 cwd 推一個世界；之後每個需要世界概念的單元各自帶路徑與規則 | lane 變多、要由單一 root multiplex，或想把同一套操作拿來獨測時，會遇到全面的路徑 API 重構 | **仍可後補，磁碟本身通常不用搬。**但越多外掛把 cwd 當契約，後補時的 API 相容成本越高 |

資深工程師與要接工具的開發者明說，**B 集中 lane 幾乎會逼出 `World`**；資深架構師與研究人員
也都把「多世界」列為收它的主要收益。這使本題的「所以呢」很具體：它不是抽象美不美的問題，
而是第三題若走集中推進，現在不收，之後就得補。

三位（工程師、架構師、研究人員）另行提醒：**root fd 不是沙盒。**若仍准絕對路徑、`..` 或
可逃出根的 symlink，「能力」就沒有形成安全邊界。工程師、架構師與研究人員都不確定目前所說的
capability 到底是**真的權限邊界**，還是只是 root 排程時帶著走的路由／提示；要接工具的開發者
則把同一問題問成：能力究竟綁 fd／inode、路徑，還是 UUID。這個答案若只是實作提示，不必把
`World` 做成安全容器；若是安全承諾，路徑規則就會成為對外契約。
