## 成形的方向

1. **核心系統指令的「恆常」靠版本化的核心描述檔，不靠尾指令自我複製**（已拍板，見
   [decisions.md](../decisions.md)）。`.aos/kernel.json` 宣告**版本化的序言與尾聲**，`aos exec`
   **在取件時合成**「序言＋使用者批次＋尾聲」。系統指令仍是普通 instruction、仍在頭尾；耐久性
   **歸機器，不歸指令自己**。尾指令自我複製的壞處：失敗一次就永久斷鏈、crash 遺失、重跑增殖、
   手改與重複投遞都會破壞它。
   > 「核心行程不是 `inst.json` 裡永不消失的幾筆，而是 executor 對每批工作套用的版本化協定。」

2. **匯聚留在 `aos exec`**（使用者說匯聚是「灰色地帶，我傾向保留」）。理由是啟動自舉：
   匯聚／claim／release 是「使批次可被安全解讀」的提交協定，普通 instruction 在被安全取出之前
   不能負責取出自己；它像取指前端／DMA。「CPU 只做取指令→執行」這條的讀法：取指前端本來就不是指令。

3. **「行程」的詞彙：world／lane／process。**
   **world**＝持久資料夾、**lane**＝一份 `inst.json` 及其信箱與鎖、**process**＝有 ID／狀態／信箱
   的可排程工作。folder 是耐久、權限與故障域，不是 OS process；`chdir` 只是執行投影。

4. **判準：func 有沒有自己的 lane，決定它是不是真的子行程。** 有獨立 queue／`.runi`／信箱／
   cursor／故障狀態才算子行程；沒有就只是主回合裡的一批 job。使用者說「子行程在 `aos core dofuncs` 這一筆指令下被統一管理、排程」，
   兩種讀法（同步做完 vs 各有回合）代價差很多。

5. **`dofuncs` 的形狀**：快照 `.funcs` → 按持久 cursor 挑 ready 的 → 每回合只推進有限工作量 →
   原子投遞下回合 → 投遞成功之後才更新 cursor。不改已載入的批次（維持回合邊界）；
   帶 correlation ID ＋ receipt，同一 ID 重跑不得重複副作用。

6. **多核＝多個 lane、多個 claim loop，不是多個 writer。** `.runi` 只鎖 queue，鎖不住世界；
   兩核改同一個檔都會自認成功，回合順序不存在。寫入衝突由單一提交者（root）解決（已拍板）。

7. **外部處理器的「零 lib 契約」清單**：版本、schema、路徑基準、命名、同檔案系統 rename 的前提、
   原子 publish、唯一 claim、ack／complete、request／correlation ID、結果歸屬與結果路徑、狀態機
   （成功／失敗／取消）、冪等與重試、crash 遺留與清理、排序保證、容量上限、版本相容、信任邊界
   （不可信路徑）。要附 **golden files ＋ 一支 conformance CLI**。`rename` 只保證可見性原子；
   承諾斷電耐久要另立 `fsync` 規則。

8. **exe／lib 的切線**：**lib＝無政策的協定原語**（parse／validate／deliver／claim／release／
   result／路徑／claim token／原子交易）；**exe＝世界辨識、排程、政策、權限、診斷、人機錯誤訊息、
   恢復、loop**。lib 只是參考實作，契約才是本體。
