## 使用者原話

> 假如 aos exec 只保持單純的取指令執行指令，其他啥都不做，剩餘那些匯聚/deliver,...等，全部都是用 argv 去執行，並且他們都算是 core，這樣的話這個體系的好壞

## 這場沒有誰在場

這份紀錄是半場，不是全場。下次續場的人請先看這一節，不要以為底下沒提到的角度已經被談過了。

**議題書指定要記的三個空位**：這場沒有產品經理，所以**沒有人問「這值不值得做、該排在 T 幾、跟 T5／T6 搶不搶時間」**——四位一開場就在討論「該拆哪幾支」，沒有人討論「現在該不該動它」。沒有普通用戶／新手；「要接這工具的開發者」那一席是會去讀規格、會自己寫替代 aggregate 的人，他代表不了第一次打 `aos init` 的人。沒有獨立的維運席位，維運視角只由資深工程師從失敗現場的角度帶到一部分。

**我從想法池裡另外看出來的空位**：

1. **沒有人替使用者原話裡的那個極端版本辯護。** 原話問的是「全部都是用 argv 去執行」，但兩輪八份發言裡**沒有任何一位主張整包外放**，也沒有任何一位主張「四支全部留在裡面、什麼都不拆」。四位第一輪就各自跳到同一個中間解（投遞出去、取件釋放留下），此後兩輪都在那個中間解上面加東西。這個共識強得可疑——它可能是對的，也可能只是四位都從同一批背景資料出發、沒有人被指派去唱反調。
2. **沒有人去量。** 四位都用了「一次 fork＋execve 約 1–3ms」這個數字，四位也都在「我沒把握的」裡標明**那是估的、沒實測**。架構師第 2 輪直接點名：這是全場唯一沒有證據的共同前提。整個成本論證（包含「閒置回合才是痛點」這個三位撞在一起的結論）都架在一個沒人量過的數字上。
3. **沒有測試／CI 的角度。** 只有資深工程師第 2 輪順手提了一句「CLI 測試要造檔案系統狀態、等子行程，慢且會 flake」。拆完之後測試矩陣長什麼樣、CI 要怎麼跑、跨行程的錯誤路徑要怎麼測，沒有人系統地談。
4. **沒有寫文件的人。** 拆完之後 `docs/aos-folder.md` 的條文要怎麼重寫、哪一份是正本，只被架構師從「規格得指定正本、分歧時函式贏」的角度掃到一句。
5. **沒有 agent loop／LLM 那一側的人**（議題書把它列在範圍外，這是照規矩來的）。但要記一筆：開發者提到 T5 那份 agent loop 腳本是這套協定**第一個真正的外部使用者**，而那一側沒有人在場替自己說話。
6. **沒有跨平台角度。** 只有 OS 研究者順帶提了「aos 是 Linux-only，所以 git 當年因為 Windows fork 太貴而收回 plumbing 的那半個理由不成立」。若哪天不再是 Linux-only，整個成本結論要重算。

## 第 1 輪

### 成形的方向

**這場最強的一件事在第一輪就出現了：四位獨立地都提了同一個切法——投遞（deliver）該變成外部程式，取件（claim）與釋放（release）該留在 `aos exec` 裡面。** 四位是各自從不同理由走到這裡的，這點比結論本身更值得記：

- 資深工程師是從失敗現場：邊界不能由邊界裡面的東西畫。
- 架構師是從「這四件事不是同一類」：投遞的呼叫者本來就在世界外面，彙整在回合開始之前，這兩件出去沒問題；但取件與釋放**就是回合邊界本身**。
- OS 研究者是從 Maildir：Maildir 之所以免鎖，不是因為它用 `rename`，是因為取件的鎖由讀者自己持有；把取件拆出去等於把 Maildir 退回 mbox。
- 開發者是從手感：他這輩子不會手打 claim 和 release，他只想手打 deliver。

所以呢——**你原話裡「全部都是用 argv」這個版本，這場沒有人支持；四個人分別給了四個不同的理由，指向同一個中間解。**

第二件成形的事是**「都算 core」該怎麼讀**。三位獨立地都給了同一個答案：**同一支執行檔、同一次 build、版本一起走**，而不是「同一個 repo 裡的四支散裝執行檔」。資深工程師講的是升級期間的實際故障：instruction 的 argv[0] 若走 PATH，機器上有兩個 `aos` 就會出現「彙整懂 v2、執行懂 v1」；所以驅動器該注入 `/proc/self/exe`，不查 PATH。OS 研究者說這是 busybox 的現成答案——同一支執行檔靠子命令分派。開發者的版本最白話：`git clone` 加一次 `cmake --build` 之後 `build/bin/aos` 裡全都有，不用裝第二包、不設 PATH、CI 不 vendor 四支散裝執行檔；**做不到這點他寧可它們留在 `aos exec` 裡面**。

第三件是**同一份實作、兩個入口**（資深工程師提，架構師與 OS 研究者的第 2 輪都接了）。那三支已經是以 instruction 檔路徑為參數的公開函式，再長出 `aos handoff aggregate|claim|release <path>` 的 argv 入口就好，而 `run_exec.cpp` 內部**仍然走函式呼叫、不要 fork 自己**。他的對照是 git 的 plumbing／porcelain：plumbing 是給別人組合的，但 `git commit` 內部從來不去 fork `git hash-object`。

第四件是**彙整政策外包**這個好處是實在的（OS 研究者、開發者）。改成按 mtime 排序、加配額、加優先權，都只是換一支程式，`aos` 本體不必為每種政策長參數。OS 研究者說這是 MTA 把投遞政策交給 procmail／sieve 而活下來的同一招，跟 roadmap T5 那句紅利同源。

### 還在生長的想法

**bootstrap 悖論的解法**（OS 研究者）。議題書點出的那個死結——彙整若自己也是一筆 instruction，它得先被放進 `inst.json` 才會被執行，而把東西放進 `inst.json` 正是彙整在做的事——研究者說 init 早就解過了：pid 1 不從佇列來，sysvinit 沒把自己寫進 `/etc/inittab`。具體提案是加一份 `.aos/boot.json`，**不經彙整、每回合由 `aos exec` 無條件串在批次最前面**。代價跟 inittab 一樣：那是特權位置，改壞了世界就起不來。

**`kernel.json` 那層間接**（架構師）。他的顧慮是：`aos aggregate` 這個 argv 字串一旦寫進 instruction，就會變成 `.aos` **磁碟格式**的一部分；資料夾是可攜的、會被搬走、會被 commit，所以那串字跟檔名一樣永遠不能改。要留退路就別讓 instruction 直接寫程式名，經一層 `.aos/kernel.json` 指名誰扮演哪個角色。（這直接碰到四個已知未拍板的設計選擇之一。）

**`.runi` 該有內容**（資深工程師、架構師，兩位獨立提出，理由不同）。工程師要的是診斷：往 `.runi` 寫 receipt（driver pid、起始時間、預期筆數），三種現場才分得出來。架構師要的是原子性與身分：`.runi` 記下取件者的 pid＋boot id，release 驗身分才刪，否則一筆放錯位置的 release 就能在回合還在跑的時候把鎖打開，讓第二支 `aos exec` 進來——**這件事在今天的結構上不可能發生**。（這直接碰到「親緣綁路徑或 UUID」那題。）

**退出碼只帶類別，細節寫成 receipt**（架構師）。`HandoffState` 九個值加 `HandoffResult{path, error, published, issues[]}` 壓不進 8 bit 的退出碼，而 0／1／2／3 已經被 `aos exec` 佔走了。他的提案是退出碼只帶四類（ok／無事／busy／壞了），細節寫成 `.aos` 裡一份機器可讀的 receipt——**那正是上一場黑客松要 core 長出來的東西**，argv 化剛好逼它提早落地。

**閒置路徑留在行程內**（架構師，與資深工程師的成本分析同源）。回合開頭先 `stat` 一下 `inst.json` 與 `inst.tempd`，兩邊都空就直接 return，真的有工作才去 exec 那三支。

**表面該怎麼收**（開發者）。拆完主 help 會從 4 條變 8 條，但只有一條是他該打的。收成二級命令 `aos world claim .aos/inst.json`，主 help 不列、`aos world --help` 才展開——**公開但不推銷**。同一批必須附 `aos world recover <folder>`（印出 `.runi` 內容，問要 `--resume` 還是 `--discard`）與 `aos world conformance <folder>`（跑一組協定自檢），否則「可替換」對他等於「可自己搞砸」。

**前人做過什麼**（架構師與 OS 研究者各自舉了一批）。maildir／qmail 就是這個協定，而它的切法正好就是四位撞到的那個切法：投遞是獨立程式、取件的鎖由讀者自己持有。git 同理：plumbing 是程式、index 是檔案、`index.lock` 由建立它的行程持有、crash 之後要人手動刪——**這和 `.runi` ＋退出碼 3 是同一個答案**。研究者另外把整個構想歸到 exokernel：MIT 的 Xok 把抽象推給應用層，結果人人都連同一份 ExOS libOS，那份 libOS 就成了事實上的新核心，只是沒鎖版本。他的建議是承認那三支是 aos 的 libOS 並替它鎖版本，別假裝可替換。（他自己在第 2 輪收回了大半，見下。）

### 大家問出來的問題

- **release 那支自己失敗（`unlink` 回 EACCES）時誰回報？**（資深工程師）今天是 `aos exec` 回 1、世界誠實地卡死；外放後那筆的退出碼寫進某個檔，沒人看。
- **第一批 instruction 是誰放進 `inst.json` 的？**（資深工程師）這是 bootstrap 問題的最短講法。
- **`aos` 這個執行檔名算不算 `.aos` 格式的一部分？在沒裝 aos 的機器上，那個資料夾還是不是一個合法的世界？**（架構師）
- **世界檢查（`.aos` 在不在、`version` 認不認得）要複製進四支裡，還是四支都不驗、只信參數？**（架構師）他傾向後者，但那表示 helper 對著錯的資料夾會安靜地做出錯的事。
- **helper 被當成 instruction 跑的時候，它自己的 `cwd` 欄位可以改基準**——規格第四節那條「一律以 `<folder>` 為基準」還由誰保證？（架構師）
- **`.runi` 鎖的是「那一批」還是「那個世界」？**（OS 研究者）前者拆得開，後者拆不開。
- **先補投遞再談拆，還是拆的過程順便把投遞定義掉？**（OS 研究者）投遞至今沒實作，等於崩潰語意從未被真正測過。
- **拆完主 help 列幾條、哪幾條標「不該手打」？救援指令叫什麼？機制那幾筆會不會出現在我打開的 `inst.json` 裡、我改到會怎樣？我只換 aggregate、其他照用，做不做得到？**（開發者）

### 明顯的坑

**第一個坑是全場最大的一個，四位都指到了它：`.runi` 那條不變式會降級成約定。** 今天「`.runi` 存在 ⟺ 有一回合沒跑完」之所以成立，唯一的理由是把 `inst.json` 搬成 `.runi` 的行程和最後刪掉它的是同一個行程。一旦取件與釋放變成 batch 裡的普通指令，「取件完就死、一筆沒跑」「跑到一半死」「跑完但釋放自己失敗」這三種情況在檔案系統上會長得一模一樣。OS 研究者再補一刀：`handoff.cpp` 的 claim 本來就是 lstat→read→rename 的 TOCTOU（規格第十二節自己記了），拆開之後那個死亡窗口從幾微秒變成一次 `fork`＋`execve`；要拆就得先讓不變式改由 `link()`＋`unlink()` 或 `renameat2(RENAME_NOREPLACE)` 維持。

**第二個坑：退出碼 3 會整個消失。** `run_exec.cpp` 今天會印 `refusing ...: .aos/inst.json.runi already exists` 並回 3，而 `--loop` 就是靠這個碼停下來的。取件變成一筆 instruction 之後，它只是「批次裡某一筆指令 exit=3」，而規格第八節明講回合退出碼不表達個別指令的成敗——**`--loop` 從此不會停，會抱著一個壞掉的世界一直轉**。診斷也一起退化：從一行帶主詞、路徑、`strerror` 的訊息，變成要去翻某個重導向檔（沒設的話就跟其他子行程的輸出交錯噴）。

**第三個坑：最常走的路徑變成最貴的路徑。** 三位獨立算到同一個結論。aggregate 在 inbox 空的時候，今天只是 lstat＋opendir；外放之後最少多一次 fork。一次 fork＋execve＋載入 aos 約 1–3ms，一回合多幾次就是 5–10ms，而 `--loop` 的單位是毫秒、已知 `--loop 0` 會吃掉一顆核心。**大批次不痛，閒置輪詢才痛，而閒置輪詢是常態。** 架構師補充：多出來的不是 JSON（aggregate 本來就寫、claim 本來就讀），是三次 `execve` 加三次動態連結——回合的**固定**成本大約三倍，每筆 instruction 的邊際成本不變。

**第四個坑：argv 字串會變成磁碟格式的一部分**（架構師）。見上面 `kernel.json` 那段。

**第五個坑：契約的位置整個搬家。** 從編譯期的型別檢查，搬到執行期的退出碼與檔名。九種狀態＋路徑＋errno＋逐份投遞的問題清單，要壓進 8 個位元加一段 stderr 文字。

**第六個坑：可呼叫的東西就會被呼叫，然後人把自己弄壞**（開發者）。他手打 `aos world claim` 之後 Ctrl-C，`inst.json.runi` 就留在那裡，下次 `aos exec` 回 3、他卡死。規格說「把現場留給人」，可是人手上沒有工具。

**第七個坑：bootstrap 會變成一個靜默錯誤**（開發者）。若 aggregate 自己也是一筆 instruction，`aos init` 就得預寫一份開機批次；改壞它的症狀是「沒有 `inst.json` ＝ 退出碼 0、什麼都沒發生」——最難查的那種報錯。

**第八個坑：輸出會混亂**（開發者）。「成本我不在意，輸出混亂我很在意」——機制那幾筆的 stderr 混進批次輸出之後，他分不出哪一行是 aos 自己說的。

**第九個坑不是技術的：那些數字沒人量過。** 四位都在自己的「沒把握」欄裡寫了同一句話。

## 第 2 輪

### 成形的方向

**四比零這件事被三位各自統計出來、寫進了自己的第 2 輪**：四個身份全部獨立說「deliver 該外放、claim／release 該留內」，無人主張整包外放。這是全場最強的訊號。

**`.runi` 從一個檔名升級成一份租約。** 三位獨立走到這裡（資深工程師從診斷、架構師從身分驗證、OS 研究者從原子性），連補救手段都撞在一起。資深工程師把三件事疊成一個東西：`.runi` 帶 header（pid、boot id、時間、筆數），一疊解三件事——三種現場分得出來、release 驗身分才刪（擋掉「放錯位置的 release 中途開鎖」）、recover 就是把 header 印給人看。

**架構師在這裡補了一個沒人講的細節，而且它會改變做法**：`.runi` 現在的內容**就是那批 JSON**，出事時 `cat` 一下就知道卡住的是哪一批；包一層 header 會毀掉這一點。所以 receipt 要**旁邊放**（`inst.json.runi.receipt`），而且**先寫 receipt、後 rename `.runi`**——孤兒 receipt 無害，反過來不成立。

開發者對這條的立場值得單獨記：**他不否決「claim／release 留內」，他要的不是呼叫權，是可見性。** 照留內，另外給一支唯讀的 `aos world status <folder>`，印 `.runi` 在不在、幾筆待彙整、幾個 `.bad`、上一回合何時結束。

**`--loop` 的停止條件該搬回檔案系統**（架構師）。他對「退出碼 3 會消失」的解法是：3 不是「某支程式的碼」，是**世界的狀況**。所以 `--loop` 停不停不該去讀子程序的退出碼，該在每回合開頭自己 `stat` 一次 `.runi`。這把契約從退出碼搬回檔案系統狀態，**而那本來就是這個模型的唯一真源**；這樣即使 claim 哪天真的外放，停止條件仍然留在 `aos exec` 裡面。

**「零工作的回合必須是零 fork」**（資深工程師把架構師的閒置路徑提案推成一句可驗收的規則）。回合開頭 stat `inst.json` 與 `inst.tempd`，兩邊都空就 return。

**bootstrap 那份特權檔，三位各自改了它一次，形狀不一樣**：

- OS 研究者自己收回了 R1 的單層 `boot.json`，改成 FreeBSD 的雙層：**開機批次編進執行檔當內建預設，`.aos/boot.json` 只在存在時覆蓋**——刪光了照樣能開，而單層 inittab 改壞就進不去系統。
- 架構師改的是它的性質：它不該是「指令表」，該是**角色表**。理由是依賴方向——boot.json 若只是一批 instruction 串在最前面，它仍然跑在 claim 之後，彙整還是沒自舉；改成角色表（誰扮演 aggregate、誰扮演 deliver），`aos exec` 開頭讀它、直接 execve、不經 `inst.json`，悖論才真的解掉。**他同時宣布這張表就是他 R1 講的 `kernel.json` 間接層，兩者合併成同一張。** 這樣被凍結的東西就從「`aos aggregate` 這個字串」換成「一個能隨 `.aos/version` 一起版本化的檔」——字串收不回來，版本化的檔收得回來。
- 開發者要的是它的操作面：instruction 不寫程式名，`kernel.json` 寫 `"aggregate": "@self"`；他不動零行照樣能跑，要換就打 `aos world kernel set aggregate ./my-aggregate.py`。
- 資深工程師管的是它的失敗語意：改壞 boot 批次不是「起不來」，是**每回合失敗一次、退出碼仍然 0**（第八節：子行程非零不影響回合碼）。所以 boot 批次必須有**不同的失敗語意**——任一筆非零就中止本回合、不跑 payload、回專屬碼並停 `--loop`，否則那個特權位置會變成一個靜默的無限迴圈。

**recover 得進規格，不能只是個指令**（架構師）。一旦 `aos world recover` 存在，「crash 現場留給人」就從「人拿 shell 修」變成「人跑一支 aos 指令」，而那支指令要做的是**規格目前沒有定義的狀態轉移**（把 `.runi` 搬回 `inst.json`）。所以它不能只當 `aos world` 的一員，得在規格第六節明文成為**第四步**（連同「棄置」），否則它是一支在規格外偷偷改世界的程式。

**先做 deliver，其餘等 receipt 格式定下來**（開發者）。他把順序講得最清楚：不是四支一起拆，是 deliver 先單獨出去，因為 T5 那份 agent loop 腳本是這套協定第一個真正的外部使用者，現在得自己 `mktemp`＋`rename`，有 `aos deliver` 就縮成一行。

### 還在生長的想法

**規格得指定哪一份是正本**（架構師接工程師的「同一份實作、兩個入口」）。兩個入口意味著**公開契約變成兩份**（函式／argv）且必須永遠同義，所以規格要明寫：**argv 只是函式語意的投影，分歧時函式贏**。否則十年後會有人靠上 argv 的某個副作用。

**argv 入口只能是薄殼，錯誤路徑的測試永遠留在函式那層**（資深工程師）。今天 handoff 的錯誤分支是直接叫函式測的，快又確定；改用 CLI 測就要造檔案系統狀態＋等子行程，慢而且會 flake。

**機制那幾筆不該出現在人打開的 `inst.json` 裡**（資深工程師，回答開發者第 1 輪問了但沒人答的問題）。放進 `boot.json`，順便化解「argv 變成磁碟格式」那條——argv 寫在一個 `aos init --repair` 能重寫的檔裡，才不會變成資料夾格式裡改不掉的部分。

**這會讓 `.aos/version` 第一次真的有事做**（資深工程師）。boot.json／角色表一存在，就第一次有了「舊版寫的、新版讀的」這種東西。過舊的時候**不要 best-effort**，印 `hint: aos init --repair .`。

**退出碼碼表要共用，而且「無事可做」要從 0 裡拆出來**（資深工程師接架構師「退出碼只帶類別」）。aggregate 回 0 的時候，腳本分不出「收了 5 份」和「inbox 是空的」，**而那正是 `--loop` 拿來決定要不要睡的資訊**。他自己標明：這與規格第八節衝突，要改規格。

**`.aos` 該長出一個執行紀錄區**（架構師的新想法 A）。跨 process 之後只剩退出碼＋stderr，於是開發者要的 `.aos/log/<verb>.err` 和上一場黑客松要的 receipt 收斂成同一件事：機制自己的輸出寫進 `.aos`，不寫 stderr。它們仍然不可攜，所以規格第十節「`.aos` 全部不進 git」不必改。

**沒人提的那條收不回來的線：機制的參數會變成使用者資料**（架構師的新想法 B）。`<folder>` 本體會被 commit，寫著 `["aos","aggregate",...]` 的腳本會流出去、被貼進別人的 repo。那串字的相容壓力**比 C ABI 還大**——函式庫至少還有 soname 能並存，argv 沒有。

**該問的不是拆幾支，是 driver 能不能被換掉**（架構師的新想法 C，這條直接對上你的原話）。若 `aos exec` 只剩「讀角色表 → 依序 execve aggregate、claim、跑批次、release」，它就是一支兩百行內讀得完的東西，**那才是 core，其餘三支是政策**。這等於把 core 的定義從「哪些程式」改成「**哪一份順序**」——回合的順序是核心，回合的內容不是。他自己接著承認這條畫不到你原話要的位置，見下面的問題。

**aos 沒有持得住鎖的主體，這才是病灶**（OS 研究者的新想法 1，這是他兩輪裡最硬的一條）。他去看那些「機制外放還活下來」的系統，發現它們都有一個常駐者握著把柄：make 的 jobserver 靠**繼承的 pipe fd**、init 靠 pid 1 永不退出、systemd 靠 cgroup。**而 aos 是刻意沒有常駐 process 的**，它唯一持得住的東西是檔名。所以要嘛讓檔案系統自己維持不變式（`link()`＋`unlink()` 或 `renameat2(RENAME_NOREPLACE)`），要嘛就別把鎖交出去。

**`aos --list-core`**（OS 研究者，對照 `busybox --list`）。印出這個 build 含有哪些 applet，讓「彙整懂 v2、執行懂 v1」在啟動時就查得出來。

**`aos exec --dry-run .` 與 `--explain .`**（開發者）。一個印這回合會跑哪幾筆（含機制那幾筆）但不執行，一個印實際走了哪條路、有沒有 fork——後者正好讓「閒置留在行程內」這件事變成他看得見、驗得到的東西。

**`aos init --from ./aos-boot.json`**（開發者）。因為 `.aos/` 不進 git，他沒辦法把 boot／角色設定交給隊友。

**conformance 是 argv 契約的可執行版本**（架構師接開發者）。它比文件硬，而且順便回答了 exokernel 那個憂慮：libOS 會變成事實上的核心，是因為沒人定義過什麼叫「合格的替代品」。

### 大家問出來的問題

- **boot 批次失敗回哪個碼、`--loop` 停不停？**（資深工程師）他主張停，而且跟碼 3 同級。
- **deliver 補上之後，既有那些直接寫 `<pid>.json` 的腳本怎麼被發現？**（資深工程師）沒檢查就是靜默的資料損毀。
- **角色表本身改壞了要怎麼被發現？**（架構師）它不在批次裡，唯一的驗證者只能是 `aos exec` 自己，那開機檢查與 `.aos/version` 的先後順序是什麼？
- **若 core ＝ 回合的順序，`aos exec` 還算不算「其他啥都不做」？**（架構師）他直接引你的原話說：讀表、決定順序本身就是在做事，**這條線他畫不到你原話要的位置**。
- **第一批 instruction 是誰放進去的？**（資深工程師第 1 輪問的，第 2 輪只有架構師回答）架構師認為答案是 `aos deliver`——**bootstrap 走投遞、而不是走特權入口**——但那要求 deliver 先落地。
- **這套協定的讀者到底是誰？**（OS 研究者）若永遠只有 `aos` 自己會呼叫它，那 conformance 與凍結 ABI 都是在替一個假想的使用者付錢。
- **`.runi` 鎖的是「那一批」還是「那個世界」？**（OS 研究者第二次問）他點名：四份發言都預設了答案，卻沒有一份講明。
- **`.aos/` 不進 git，那 `kernel.json` 與 `boot.json` 要怎麼跟著專案走？**（開發者）
- **`aos world status` 撞到 `.runi` 的時候該回 0 還是非零？**（開發者）

### 明顯的坑

**特權位置會變成靜默的無限迴圈**（資深工程師）。見上面 boot 批次那段：改壞它的表現是每回合失敗一次而退出碼仍然 0。

**包一層 `.runi` 會毀掉「`cat` 一下就知道是哪批」**（架構師）。這是第 2 輪才被發現的、對第 1 輪熱門提案的直接反例。

**git 自己走過這條路然後走回來了**（OS 研究者）。`git-commit.sh` 當年**真的**去 fork `git-update-index`，後來一支支收回成 C builtin。收回的理由一半是 Windows fork 太貴（aos 是 Linux-only，這半不成立），**另一半是錯誤穿不過退出碼——這半完全成立**。

**退出碼裝不下狀態，前人的兩條路都有代價**（OS 研究者）。systemd 明講退出碼不夠用，改用 `$SERVICE_RESULT` 傳給 `ExecStopPost=`；fsck 走另一條，把狀態壓成位元遮罩，代價是每一套 init script 裡都有一段 `case $? in`。

**介面開放不等於有人來寫**（OS 研究者，他自己給架構師「誰有資格寫一顆 CPU」那個好處潑的冷水）。Plan 9 把一切變成檔案介面，任何語言都能寫服務，實際上服務仍然幾乎全是 C、由同一群人寫。

**沒有測試套件的規格會分岔**（OS 研究者）。Maildir 的對應物就是它自己：規格只是一篇文章、沒有測試套件，Courier 與 Dovecot 的解讀分歧至今。他補一句：aos 是單人專案，分歧成本近乎零——**除非真的要讓外人寫 CPU**。

**receipt 只能幫人判斷，不能自動 resume**（資深工程師）。boot id 在容器與 WSL 裡共用宿主的值，pid 又會重用。他另外擔心 recover 會養出「照著 resume」的習慣，反過來繞過「現場留給人」那條刻意的規則。

**exokernel 那個對照，提出者自己收回了**（OS 研究者）。他第 1 輪說可能過重，第 2 輪更確定過重：真正的限制不是 libOS 分裂，是**單人專案養不起兩個實作**。

**那些數字，第 2 輪還是沒有人量**（架構師點名：這是全場唯一沒有證據的共同前提）。

## 這個體系的好與壞

第 2 輪四位每人各交了「最硬的三個好、最硬的三個壞」，共 12 好 12 壞。收攏之後的樣子相當極端：**12 個好塌成 3 條，而且每一條都是四位獨立地都提了**；12 個壞塌成 6 條，其中只有第一條是四位全中。

### 好（三條，每一條都是四位獨立地都提了）

**好 1：投遞（deliver）外放，是把整套協定裡唯一沒實作、安全性卻全押在上面的那一步，補成一個有退出碼可驗的真契約。**（四位獨立地都提了，而且四位都把它排在自己的第一條。）今天「先寫 `.temp` 再 `rename`」只是一句口頭約定；第二個生產者一出現，彙整就會讀到寫到一半的 JSON。而**投遞者本來就在世界外面**——這是四支裡唯一一支「呼叫者本來就不在 `aos exec` 裡」的。開發者的講法最直接：這是**唯一無爭議的淨賺**。

**好 2：介面從函式庫變成 argv 之後，寫第二顆抽象 CPU 不必再連 C/C++ 函式庫，shell 或 Python 一樣拿得到同一套交接協定。**（四位獨立地都提了。）今天要重用這套協定，得連 `libaos_inst.so` 或綁 C ABI，等於**新 CPU 實質上只能是 C/C++**。架構師補了一句對你的決定最有用的話：**這不是新功能，是把已經做好的東西接出去**——那三支已經是以 instruction 檔路徑為參數的公開函式了。（要跟第 2 輪 OS 研究者潑的那盆冷水一起讀：Plan 9 證明介面開放不等於真的有人來寫。）

**好 3：彙整政策（排序、去重、配額、優先權）從編譯期寫死變成換一支程式就換掉，`aos` 本體不必為每一種政策長參數，那支真正負責執行指令的核心也不必重建、重新驗證。**（四位獨立地都提了。）OS 研究者的對照是 MTA 把投遞政策交給 procmail／sieve；開發者的版本是「從改 C++ 重編 repo 變成換一支腳本」。

### 壞（六條）

**壞 1：`.runi` 那條唯一的崩潰不變式會降級成一句約定。**（四位獨立地都提了，四位也都把它排在自己的第一條。）「`.runi` 存在 ⟺ 有一回合沒跑完」成立的唯一理由，是把它搬出來的行程和刪掉它的是同一個行程。一旦釋放交給另一支程式，**「取件完就死」「跑到一半死」「跑完但釋放自己失敗」在磁碟上會長得一模一樣**。

**壞 2：退出碼 3（`.runi` 已存在、拒絕啟動）會退化成「批次裡某一筆指令 exit=3」，而規格明講回合退出碼不表達個別指令的成敗，於是 `--loop` 失去它唯一會停下來的條件，抱著一個壞掉的世界一直轉。**（三位獨立地都提了：資深工程師、OS 研究者、開發者。架構師沒把它列進三壞，因為他在第 2 輪給了解法——`--loop` 改成在回合開頭自己 `stat` 一次 `.runi`。）

**壞 3：契約從編譯期的型別搬到執行期的退出碼與檔名。**（兩位提出，講法不同：資深工程師、架構師。）工程師講的是後果——**編譯器從此擋不住「彙整被換成不相容的一支」，錯誤只會在半夜卡住的時候才現形**。架構師講的是尺寸——現有的失敗描述是九種狀態加路徑、errno 與逐份投遞的問題清單，壓不進 8 個位元。

**壞 4：一旦 instruction 檔裡寫得出 `aos aggregate` 這種字串，那串字就成為資料夾格式的一部分。**（架構師一位提出。）資料夾可攜、會被複製、會被 commit，所以那個名字的相容壓力**比函式庫更大——函式庫至少還有版本號能並存，argv 沒有**。（他第 2 輪自己給了解法：寫進一張隨 `.aos/version` 走的角色表，就收得回來。）

**壞 5：最常走的路徑變成最貴的路徑。**（OS 研究者把它列進三壞；成本結論本身是三位獨立算到的。）inbox 空著的閒置回合，今天只是 lstat 加 opendir，外放後至少多一次 fork＋execve，而輪詢單位是毫秒、**閒置正是常態**。

**壞 6：把內部步驟變成公開可執行程式，就是在邀請人去呼叫它。**（開發者一位提出。）他手打一次 claim 再 Ctrl-C，資料夾就卡在退出碼 3，**而現在沒有任何一支指令能救他**。

### 四句話總結（每位一句）

- **資深工程師**：投遞外放是補完協定，取件與釋放外放是拿唯一的崩潰不變式換自由。
- **架構師**：把機制變成程式，就是把契約從型別搬到字串——所以真正該爭的不是拆幾支，而是那些字串寫在哪：寫進 instruction 就永遠改不了，寫進一張隨 `.aos/version` 走的角色表才收得回來。
- **作業系統研究者**：機制能不能外放取決於誰持得住鎖——make 的 jobserver 有繼承的 fd、init 有 pid 1、systemd 有 cgroup，而 aos 刻意什麼常駐的都沒有、只剩檔名，所以 deliver 該出去，claim 與 release 出去就是把號誌畫在沙上。
- **要接這工具的開發者**：deliver 先出去；claim 與 release 留在畫邊界的那支裡，改補唯讀的 `aos world status` 與 `aos world recover`——「看得見」和「出事能自救」比「能手打它們」有價值得多。

## 轉交提案

以下每一條都是這場談出來、但**需要你拍板才能動規格或動 roadmap** 的事。照「碰到規格哪裡」分組。

### 一、要改 `docs/aos-folder.md` 的

1. **第六節加第四步：救援與棄置。**（架構師）`aos world recover` 只要存在，就會做一次規格目前沒有定義的狀態轉移（把 `.runi` 搬回 `inst.json`）。不寫進規格，它就是一支在規格外偷偷改世界的程式。附帶要拍的：救援自動化到什麼程度才不違背「把現場留給人」這條**刻意**的規則（提出者自己標了沒把握）。
2. **`.runi` 從一個檔名升級成一份租約。**（三位獨立提出：資深工程師、架構師、OS 研究者，理由分別是診斷／身分／原子性。）具體形狀有一個第 2 輪才被發現的限制：`.runi` 現在的內容就是那批 JSON，`cat` 一下就知道卡的是哪一批，**包一層 header 會毀掉這點**；所以架構師主張 receipt 旁邊放（`inst.json.runi.receipt`），且**先寫 receipt、後 rename `.runi`**。這條直接碰到四個未拍板選擇裡的「親緣綁路徑或 UUID」。
3. **退出碼碼表：把「無事可做」從 0 裡拆出來。**（資深工程師，他自己標明這與第八節衝突。）理由是 `--loop` 要靠它決定睡不睡。同一條底下架構師主張退出碼只帶四個類別（ok／無事／busy／壞了），細節寫成 receipt。
4. **`--loop` 的停止條件明文寫成「回合開頭自己 `stat` 一次 `.runi`」。**（架構師）這把停止條件從退出碼搬回檔案系統狀態，而檔案系統狀態本來就是這個模型的唯一真源；這樣即使哪天 claim 真的外放，停止條件仍然留在 `aos exec` 裡。
5. **`.runi` 鎖的是「那一批」還是「那個世界」，要在規格裡講明。**（OS 研究者兩輪都問。）他點名：上面每一條提案都預設了一個答案，但沒有一份發言講明是哪個。**前者拆得開，後者拆不開**——所以這題不定，上面幾條都是懸空的。
6. **deliver 的規格：argv 形式還是 stdin JSON 是主形式、退出碼語意是什麼。**（開發者提出兩種形式，自己標明不確定哪個是主）另外資深工程師問了一件會造成靜默資料損毀的事：deliver 補上之後，既有那些直接寫 `<pid>.json` 的腳本要怎麼被發現。

### 二、碰到已知未拍板選擇的

7. **要不要引入角色表／`kernel.json` 這層間接，以及它算不算 `.aos/version` 的版本化範圍。**（架構師提出並在第 2 輪把它與 boot.json 合併成同一張表；開發者要求它長成 `"aggregate": "@self"` ＋ `aos world kernel set`。）這是四個未拍板選擇裡的「`kernel.json` 分層」那一題。**拍板的關鍵在架構師那句：寫進 instruction 的字串永遠收不回來，寫進一張版本化的檔才收得回來。**
8. **bootstrap 要走特權入口還是走投遞。**（三位各改了一次形狀：OS 研究者 → 雙層預設、架構師 → 角色表、資深工程師 → 專屬失敗語意；而架構師另外主張根本答案是 `aos deliver`，bootstrap 走投遞而非特權。）附帶要拍的：boot 批次失敗回哪個碼、`--loop` 停不停（資深工程師主張停、與碼 3 同級），以及角色表本身改壞了誰來驗、跟 `.aos/version` 檢查的先後順序。
9. **「都算 core」的定義要寫進哪份文件、寫成哪一條。** 三位獨立地都給了同一個答案：**同一支執行檔、同一次 build、版本一起走、用 `/proc/self/exe` 不查 PATH**。資深工程師把反例講得最硬：定義成「repo 內的獨立執行檔」等於把 core 協定的可用性交給部署，那就不是 core。開發者的驗收條件是：`git clone` ＋一次 `cmake --build` 之後全都在 `build/bin/aos` 裡，做不到他寧可維持現狀。
10. **要不要把 core 的定義從「哪些程式」改成「哪一份順序」。**（架構師的新想法 C，只有他一位提。）若 `aos exec` 只剩「讀角色表 → 依序 execve → 跑批次」，那它就是 core，其餘三支是政策。**這條會改 roadmap 對 core 的講法，而且提出者自己說它畫不到你原話要的位置**——因為讀表、決定順序本身就是在做事，不算「其他啥都不做」。這題只有你能拍。

### 三、不改規格、但要在動手前先有的

11. **去量那個數字。** 四位都用了「一次 fork＋execve 約 1–3ms」，四位都標明沒實測，架構師點名這是全場唯一沒有證據的共同前提。整個成本論證（尤其「閒置回合才是痛點」）都架在它上面。同一條底下的可驗收版本是資深工程師那句：**「零工作的回合必須是零 fork」**。
12. **先決定這套協定的讀者是誰。**（OS 研究者）若永遠只有 `aos` 自己會呼叫，那 conformance 套件與凍結 ABI 都是在替一個假想的使用者付錢；他也用 Maildir 舉了反面：規格沒有測試套件，Courier 與 Dovecot 的解讀分歧至今。**這題的答案會直接決定第 7、9、10 條要做到多硬。**
13. **`.aos/` 不進 git，那角色表／boot 設定怎麼跟著專案走。**（開發者，提案是 `aos init --from ./aos-boot.json`。）
14. **拆完之後的可見性與自救工具要不要一起做**：`aos world status`（唯讀）、`aos world recover`、`aos world conformance`、`aos exec --dry-run` / `--explain`、`aos --list-core`、機制輸出一律 `aos <verb>: ` 前綴並預設寫進 `.aos/log/<verb>.err`。（開發者提了大部分，OS 研究者提 `--list-core`，架構師把 log 與 receipt 收斂成 `.aos` 的執行紀錄區。）
15. **若採用「同一份實作、兩個入口」，規格要指定哪一份是正本。**（資深工程師提出做法、架構師補這條）**argv 只是函式語意的投影，分歧時函式贏**——不寫死，十年後會有人靠上 argv 的某個副作用。附帶：argv 入口只能是薄殼，錯誤路徑的測試永遠留在函式那一層。

## 白話導讀

> 這一節是**翻譯**，不是第二份摘要。上面的紀錄一個字都沒改。上面讀不動的時候從這裡進去，看懂了再回上面對照。

### 一、這場到底在吵什麼

現在 `aos exec` 這支程式一個人包辦一整回合：把收件匣裡別人丟進來的紙條收成一份清單、把整份清單從檯面上拿走、照著清單做事、做完把清單撕掉。**這場在吵的是：要不要把其中幾件事拆成「可以自己單獨打指令叫起來」的小程式**——好處是別人（一支 shell 腳本、一支 Python、將來那顆抽象 CPU）也能照同一套規矩下單，壞處是「清單還掛在檯面上就代表上一輪沒做完」這個目前唯一可靠的判斷，會從硬保證掉成口頭約定。四位談下來的結果是：**只有「下單」那一步該拆出去**，你原話裡「全部都拆」的那個版本，這場沒有任何一位支持。

### 二、冒出來的新詞

#### （甲）這場的四個動作

規格裡本來就有這四個字，但 [BACKGROUND](../BACKGROUND.md) 只收了「投遞」，所以另外三個在這裡補白話。

**彙整（aggregate）**
白話：把大家各自丟進收件匣的紙條，按固定順序疊成今天要做的那一份清單。
在 aos 裡：**已存在**，`core/inst/src/handoff.cpp`；把 `.aos/inst.tempd/*.json` 全部併進 `.aos/inst.json`。

**取件（claim）**
白話：把那份清單從檯面上拿走收進口袋，好讓後來的人一眼看出「這疊已經有人在做了」。
在 aos 裡：**已存在**，同一支 `handoff.cpp`；做法是把 `inst.json` 原子地改名成 `inst.json.runi`。

**釋放（release）**
白話：做完了，把口袋裡那份清單撕掉——撕掉這個動作本身，就是「這一輪有正常結束」的唯一證據。
在 aos 裡：**已存在**，同一支 `handoff.cpp`；就是刪掉 `.runi`。

**投遞（deliver）**
白話與嚴格定義見 [BACKGROUND](../BACKGROUND.md) →〈[投遞契約與追蹤](../background/delivery-contract.md)〉。這場要補的只有一句：**它至今只有規格、沒有程式**，現在誰要下單都得自己先寫暫存檔再改名，而這正是四位一致說它最該先做的理由。

其餘在紀錄裡出現、但 BACKGROUND 已經解釋過的詞——`.runi`、receipt、Maildir、TOCTOU、`renameat2(RENAME_NOREPLACE)`、`kernel.json`、init(1)、conformance、GNU make jobserver——一律見 [BACKGROUND](../BACKGROUND.md)，這裡不重寫。

#### （乙）拆解本身用到的詞

**argv**
白話：你在終端機打的那一行字，被空白切成一格一格；程式拿到的就是那排格子。
在 aos 裡：**已存在**——`.aos/inst.json` 裡的每一筆 instruction 本來就是一排這樣的格子。所謂「改成用 argv 執行」，意思就是「讓機制自己也變成清單上的一行字」。

**`fork` ＋ `execve`**
白話：作業系統「先生一個分身、再把分身整個換成另一支程式」這兩個動作；每叫一次都要重新把那支程式從硬碟載進來，所以不是免費的。
在 aos 裡：**已存在**，而且只在 `core/inst/src/exec.cpp` 這一層碰得到。紀錄裡「一次約 1–3ms」講的就是這一對動作的價錢——**而這個數字四位都標明是猜的、沒人量過。**

**退出碼（exit code）**
白話：一支程式結束時只能留下一個 0 到 255 的號碼，表達「大概是哪一類結果」，塞不下一句話。
在 aos 裡：**已存在**；`aos exec` 已經用掉 0／1／2／3，其中 **3 ＝「`.runi` 還在、拒絕啟動」**（[roadmap D6](../../roadmap.md) 已定）。

**同一支執行檔、多個子命令（busybox 那一招）／`/proc/self/exe`**
白話：像一把瑞士刀，很多工具長在同一把刀身上，換的時候整把一起換，不會出現「刀身是新的、開瓶器是舊的」；`/proc/self/exe` 則是「我這支程式自己的檔案在哪」——照著它叫自己，就不會不小心叫到機器上另一份舊的 `aos`。
在 aos 裡：子命令分派**已存在**（`aos exec` 就是一個），但「機制那幾支也做成子命令、而且用 `/proc/self/exe` 叫自己不查 PATH」是**提案，目前不存在**。

#### （丙）這場提出來、目前一個都不存在的東西

**角色表（把 `kernel.json` 與 `boot.json` 併成同一張）**
白話：一張「誰扮演哪個角色」的名單——上面寫「收件的人是誰、下單的人是誰」，而不是把那個人的名字直接抄進每天的工作清單裡；名單可以改版，抄進清單裡的名字改不掉。
在 aos 裡：**提案，目前不存在。** `kernel.json` 本身也還不存在（見 [BACKGROUND](../background/execution-and-turns.md)）。

**租約版的 `.runi`（外加旁邊那張 receipt）**
白話：現在檯面上那份「有人在做」的記號只是一張沒署名的紙；改成租約就是在旁邊多放一張小抄，寫上「誰拿的、幾點拿的、幾筆」，出事時人看小抄就知道是誰卡住了。
在 aos 裡：**提案，目前不存在。** `.runi` 本身存在，但裡面**就是那批清單原文**（`cat` 一下就知道卡的是哪批），所以第 2 輪才改成「小抄放旁邊」（`inst.json.runi.receipt`），別包在裡面。

**`aos world status` / `aos world recover` / `aos world conformance`**
白話：分別是「只看不動、告訴我這個資料夾現在什麼狀況」、「卡住了，幫我把現場搬回可以重跑的樣子」、「考一考你這支自己寫的替代品有沒有照規矩做」。
在 aos 裡：**三支都是提案，目前不存在。** 現在卡住的時候，人手上一支工具都沒有。

**`aos exec --dry-run` / `--explain`**
白話：一個是「先印給我看這回合會跑哪幾行，但別真的跑」，一個是「跑完告訴我你實際走了哪條路、有沒有真的去生分身」。
在 aos 裡：**提案，目前不存在。**

**`aos --list-core`**
白話：印出「我這把瑞士刀上到底有哪些工具」，好在一開始就看出手上這支跟對面那支版本對不上。
在 aos 裡：**提案，目前不存在。**

**`.aos/log/<verb>.err`（執行紀錄區）**
白話：讓機制自己的抱怨聲寫進資料夾裡的固定位置，而不是跟你自己那些指令的輸出一起噴在螢幕上攪成一團。
在 aos 裡：**提案，目前不存在。**

#### （丁）拿來對照的前人系統

這一區的東西 **aos 裡一個都沒有**，它們只是四位用來說明「這件事別人做過、下場如何」的例子。

**git 的 plumbing／porcelain**
白話：git 有一批給人打的漂亮指令（porcelain，例如 `git commit`），和一批給程式組合用的粗管子（plumbing）；關鍵是——`git commit` 內部從來不去叫那些粗管子，它直接呼叫函式。
對應到這場：這就是「同一份實作、兩個入口」那個提案的來源；也是「argv 只是函式語意的投影，分歧時函式贏」那句話要防的事。

**procmail／sieve（郵件系統把投遞政策外包）**
白話：郵件伺服器自己不決定「這封信該丟哪個資料夾」，那件事交給使用者自己寫的一支小程式。
對應到這場：這是「好 3：彙整政策外包」的前例，也和 roadmap [T5](../../roadmap.md) 那句紅利同源。

**inittab／FreeBSD 的雙層預設**
白話：舊 Linux 的開機清單 `inittab` 只有一份，改壞了機器就起不來；FreeBSD 的做法是「預設值編死在程式裡，外面那份只在存在時覆蓋」，所以外面那份刪光了照樣開得起來。
對應到這場：這是 bootstrap 悖論（彙整要先被彙整才跑得起來）的兩種解法形狀。

**exokernel／libOS**
白話：一種把「作業系統該怎麼抽象」全部推給應用層自己決定的研究型設計；結果是大家都去用同一份現成的函式庫，那份函式庫就變成事實上的新核心，只是沒人替它鎖版本。
對應到這場：**提出者自己在第 2 輪收回了大半**，他的結論是真正的限制不是這個，是「單人專案養不起兩個實作」。

**Plan 9**
白話：一套把所有東西都變成檔案介面的系統，任何語言都能寫服務——實際上服務仍然幾乎全是 C、由同一群人寫。
對應到這場：這是拿來替「好 2：介面開放了，別人就能來寫」潑冷水的反例。

**fsck 的位元遮罩／systemd 的 `$SERVICE_RESULT`**
白話：兩種「退出碼裝不下狀態」的前人解法——一種是把好幾個是非題壓進同一個號碼裡（代價是每個腳本裡都要有一段拆碼的程式），一種是乾脆放棄退出碼、改用另外一個管道把細節傳出去。
對應到這場：這是「壞 3：契約從型別搬到退出碼」實際會走到的兩條路。

**boot id**
白話：機器每開機一次就換一個新編號，用來分辨「這個 pid 是這次開機的，還是上次關機前留下的」。
對應到這場：租約版 `.runi` 想拿它驗身分，但資深工程師自己標了問題——**容器和 WSL 裡它是共用宿主的值**，所以只能幫人判斷，不能拿來自動恢復。

### 三、那三個好、六個壞，各是什麼意思

上面〈這個體系的好與壞〉那一節寫得很濃。這裡每條一句話，讓你不必回去啃原文。

#### 三個好（每一條都是四位獨立地都提了）

1. **好 1（把唯一沒實作的那一步補起來）**：現在「下單」只是一句「請你先寫暫存檔再改名喔」的口頭約定，沒有程式、沒有退出碼可驗；一旦有第二個人來下單，收件那邊就會讀到寫到一半的檔案——把它做成一支真程式，這個洞就補起來了。
2. **好 2（別人不必寫 C++ 也能接）**：現在要重用這套交接規矩，得去連 aos 的 C/C++ 函式庫，等於下一顆 CPU 實質上只能用 C/C++ 寫；改成打指令之後，shell 和 Python 一樣接得上。**而且這不是新功能，是把已經做好的東西接出去。**
3. **好 3（換政策不必重編）**：「清單要按什麼順序疊、要不要去重、要不要限量、誰先誰後」現在寫死在 C++ 裡，改一次就要重編、重驗整包；變成一支外部程式之後，換政策就是換一支腳本，那支真正負責執行指令的核心動都不用動。

#### 六個壞

1. **壞 1（唯一的崩潰判斷會失效）**：今天「檯面上有清單 ⟺ 上一輪沒跑完」之所以成立，唯一的理由是「拿走清單的人」和「撕掉清單的人」是同一個人；一旦撕的動作交給另一支程式，「拿走就死」「做到一半死」「做完但撕失敗」這三種完全不同的現場，在磁碟上會長得一模一樣。（四位全中，四位也都排第一。）
2. **壞 2（`--loop` 從此停不下來）**：現在撞到「上一輪沒跑完」會回退出碼 3，而 `--loop` 就是靠這個碼停的；取件變成清單上的一行之後，那只是「某一行的退出碼是 3」，而規格明講整回合的退出碼不代表個別指令的成敗——於是 `--loop` 會抱著一個壞掉的資料夾一直轉。（架構師沒把它列進三壞，因為他給了解法：`--loop` 改成每回合開頭自己去看一眼檔案在不在。）
3. **壞 3（錯誤從編譯期搬到半夜）**：現在有人把彙整換成不相容的一支，編譯器當場就擋下來；改成打指令之後編譯器管不著，同一個錯只會在半夜卡住的時候才現形——而且原本九種狀態加路徑、錯誤碼、逐份問題清單那麼多資訊，要壓進一個 0–255 的號碼。
4. **壞 4（打進清單裡的字永遠改不掉）**：一旦 `aos aggregate` 這種字串寫進 instruction 檔，那串字就變成資料夾格式的一部分——資料夾會被複製、被搬走、被 commit 出去，所以那個名字再也改不了；**函式庫至少還有版本號能讓新舊並存，這種字串沒有。**（架構師第 2 輪自己給了解法：寫進一張會跟著 `.aos/version` 走的角色表，就收得回來。）
5. **壞 5（最常走的路變成最貴的路）**：收件匣是空的那種「什麼都沒發生」的回合，今天只是看一眼資料夾就結束；外放之後至少要多生一次分身，而輪詢的單位是毫秒——**大批次不痛，空轉才痛，而空轉是常態。**
6. **壞 6（能打的指令就會有人打，然後把自己弄壞）**：把內部步驟變成公開指令，就是在邀請人去打它；開發者手打一次「取件」再 Ctrl-C，資料夾就卡在退出碼 3——**而現在沒有任何一支指令能救他。**

### 四、所以呢

#### 這場會動到你哪些還沒拍板的東西

對到 [OPEN-QUESTIONS](../OPEN-QUESTIONS.md) 的題號：

| 題號 | 這場加了什麼 |
|---|---|
| [第 7 題](../OPEN-QUESTIONS.md)（`aos deliver` 第一版長什麼樣） | 四位一致把它排成最該先做的一件，開發者另外主張它該**單獨先出去**，不必等其他三支。 |
| 第 8、9 題（Deliver 的 key、退出碼與 receipt） | 多了兩條具體主張：退出碼**只帶四類**（好了／沒事／忙／壞了），細節寫成 receipt；以及**「無事可做」要從 0 裡拆出來**，因為 `--loop` 要靠它決定睡不睡。後者與規格第八節衝突，提出者自己標了。 |
| 第 2 題（近期 core 回撤到哪裡） | 多了一個沒被提過的答案候選：**core 的定義從「哪些程式」改成「哪一份順序」**（架構師新想法 C）——而他自己說這條畫不到你原話要的位置。 |
| 第 13 題（crash 承諾到哪一級） | 壞 1 說的就是：一旦外放，現在這一級的承諾**在磁碟上就分不出來了**。 |
| 第 23 題（序言／尾聲失敗怎麼算一回合） | 直接對上：boot 批次若沿用「子行程失敗不影響回合碼」，改壞它的症狀是**每回合安靜地失敗一次、退出碼仍然 0**。 |
| 第 28、30 題（`.runi` 保存什麼、handle 用什麼） | 租約版 `.runi` 想在裡面記 pid＋boot id；但第 2 輪發現 `.runi` 現在的內容就是那批清單，包一層會毀掉「`cat` 一下就知道卡哪批」。 |
| 第 29 題（本地 kernel 誰建立誰升級） | 角色表若成立，這題就從「kernel 怎麼升級」變成「角色表怎麼升級」，而且 `.aos/` 不進 git，它要怎麼跟著專案走也還沒有答案。 |
| 第 34 題（怎麼證明外部實作讀對 ABI） | 多了一個前置問題：**先決定這套協定的讀者是誰**——若永遠只有 `aos` 自己會呼叫，conformance 與凍結介面都是在替一個假想的使用者付錢。 |
| 第 25 題（Publish 要不要公開） | 好 2 是同一個問題的另一面：外放的價值全押在「真的有第二個實作者」上，而 Plan 9 那盆冷水說明介面開放不等於有人來寫。 |

對到 [roadmap](../../roadmap.md)：

- **[T5](../../roadmap.md)**：T5 那份 agent loop 腳本是這套協定**第一個真正的外部使用者**，它現在得自己寫暫存檔再改名，有 `aos deliver` 就縮成一行——這是好 1 最實際的落點。另外，T5 的驗收和 D6 那個**已經記在 roadmap 上的矛盾**（「Ctrl-C 之後再 exec 一次繼續」vs「`.runi` 在就拒絕啟動」），roadmap 自己列的兩條路裡的第②條就是「長出真正的復原路徑（`aos recover`）」——**這場架構師主張的「recover 要進規格第六節成為第四步」，正是那條路的具體形狀。**
- **[D6](../../roadmap.md)**：D6 已定「`.runi` 在就拒絕啟動、退出碼 3、把現場留給人」。壞 1 與壞 2 動搖的不是這個決定，是**它今天靠什麼成立**；架構師的「`--loop` 每回合開頭自己看一眼 `.runi`」不改 D6 的決定，只把它的實現位置從退出碼搬回檔案系統。

#### 你現在有哪些選項，各賠掉什麼

以下不含推薦，只列出這場攤開的路和各自的帳單。

- **A：什麼都不動。** 賠掉：投遞永遠是口頭約定，T5 那份腳本繼續自己寫暫存檔再改名；只要出現第二個下單的人，彙整就有機會讀到寫到一半的檔案。這場四位一致認為好 1 是唯一無爭議的淨賺，不動就是不拿它。
- **B：只把投遞做出來，其他三支不碰。** 賠掉：得先拍 OPEN-QUESTIONS 第 7、8、9 題（命令形狀、key 保證到哪、成功／錯誤／退出碼那一套），開發者自己也說順序上得等 receipt 格式定下來；而好 2、好 3 這兩個好處拿不到。
- **C：投遞外放 ＋ 導入角色表。** 賠掉：第 29 題（誰建立誰升級）與第 23 題（序言失敗怎麼算）得一起拍；還多一個沒答案的問題——`.aos/` 不進 git，這張表要怎麼跟著專案走給隊友。換到的是壞 4：字串從「永遠收不回來」變成「跟著版本走、收得回來」。
- **D：連取件與釋放一起外放（你原話的版本）。** 賠掉：壞 1 那條唯一的崩潰不變式；而且要先做兩件前置——把取件從「先看再讀再改名」改成檔案系統自己保證的做法（`link()`＋`unlink()` 或 `renameat2`），以及把 `--loop` 的停止條件搬回「自己看一眼檔案」。**這場沒有任何一位支持這條**，但紀錄也標明了：沒有人被指派去唱反調，這個一致可能只是四位從同一批背景資料出發。
- **E：先去量那個數字。** 賠掉：時間，而且量完可能發現成本論證整個站不住、上面的排序全部要重排。換到的是：這是唯一能拆掉「全場唯一沒有證據的共同前提」的動作，可驗收的形狀已經有了——**「零工作的回合必須是零 fork」**。
- **F：先回答「這套協定的讀者是誰」。** 賠掉：這題不是動手做事，短期看不到東西。但它會直接決定第 7、9、34 題要做到多硬——若讀者永遠只有 aos 自己，conformance 與凍結介面就不必做；若真的要讓外人寫第二顆 CPU，那就得做，而 Maildir 的下場（規格沒有測試套件，兩套實作至今解讀分歧）是現成的反例。

還有一件不屬於任何選項、但四位都指到的事：**上面〈轉交提案〉第 5 條（`.runi` 鎖的是「那一批」還是「那個世界」）沒有答案之前，這場關於 `.runi` 的每一條提案都是懸空的**——前者拆得開，後者拆不開，而每一份發言都各自預設了一個答案卻沒講明。
