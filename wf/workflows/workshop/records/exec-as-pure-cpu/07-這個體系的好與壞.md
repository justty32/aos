## 這個體系的好與壞

四位各交「最硬的三個好、最硬的三個壞」，收攏成 3 好（每條四位都提）、6 壞（只有壞 1 四位全中）。

### 好（三條，每一條都是四位獨立地都提了）

**好 1：投遞外放，把協定裡唯一沒實作、安全性卻全押在上面的那一步，補成有退出碼可驗的真契約。**（四位都排第一。）「先寫 `.temp` 再 `rename`」現在只是口頭約定；第二個生產者一出現，彙整就會讀到寫到一半的 JSON。投遞者本來就在世界外面，是四支裡唯一呼叫者不在 `aos exec` 裡的。開發者：唯一無爭議的淨賺。

**好 2：介面變成 argv 後，寫第二顆抽象 CPU 不必連 C/C++ 函式庫，shell 或 Python 一樣拿得到同一套交接協定。** 今天重用得連 `libaos_inst.so` 或綁 C ABI，新 CPU 實質只能是 C/C++。這不是新功能，是把已做好的公開函式接出去。要跟 Plan 9 的反例一起讀：介面開放不等於真有人來寫。

**好 3：彙整政策（排序、去重、配額、優先權）換一支程式就換掉，`aos` 本體不必為每種政策長參數，執行指令的核心也不必重建、重驗。** 前例是 MTA 把投遞政策交給 procmail／sieve。

### 壞（六條）

**壞 1：`.runi` 那條唯一的崩潰不變式降級成約定。**（四位都排第一。）它成立只因為搬出它和刪掉它的是同一個行程；釋放交給另一支程式後，「取件完就死」「跑到一半死」「跑完但釋放自己失敗」在磁碟上一模一樣。

**壞 2：退出碼 3（`.runi` 已存在、拒絕啟動）退化成「批次裡某一筆 exit=3」，回合退出碼又不表達個別指令成敗，`--loop` 失去唯一的停止條件。**（資深工程師、OS 研究者、開發者。解法：`--loop` 回合開頭自己 `stat` 一次 `.runi`。）

**壞 3：契約從編譯期的型別搬到執行期的退出碼與檔名。**（資深工程師、架構師。）編譯器擋不住「彙整被換成不相容的一支」，錯誤半夜卡住才現形；九種狀態加路徑、errno、逐份問題清單壓不進 8 位元。

**壞 4：instruction 裡寫得出 `aos aggregate` 這種字串，那串字就成為資料夾格式的一部分。**（架構師。）資料夾可攜、會被複製、會被 commit；函式庫還有版本號能並存，argv 沒有。解法：寫進隨 `.aos/version` 走的角色表。

**壞 5：最常走的路徑變成最貴的路徑。**（OS 研究者列入三壞；成本結論三位獨立算到。）閒置回合今天只是 lstat 加 opendir，外放後至少多一次 fork＋execve；輪詢以毫秒計，閒置是常態。

**壞 6：內部步驟變成公開可執行程式，就是邀請人去呼叫它。**（開發者。）手打一次 claim 再 Ctrl-C，資料夾卡在退出碼 3，現在沒有任何指令能救。

### 四句話總結（每位一句）

- **資深工程師**：投遞外放是補完協定，取件與釋放外放是拿唯一的崩潰不變式換自由。
- **架構師**：把機制變成程式，就是把契約從型別搬到字串——所以真正該爭的不是拆幾支，而是那些字串寫在哪：寫進 instruction 就永遠改不了，寫進一張隨 `.aos/version` 走的角色表才收得回來。
- **作業系統研究者**：機制能不能外放取決於誰持得住鎖——make 的 jobserver 有繼承的 fd、init 有 pid 1、systemd 有 cgroup，而 aos 刻意什麼常駐的都沒有、只剩檔名，所以 deliver 該出去，claim 與 release 出去就是把號誌畫在沙上。
- **要接這工具的開發者**：deliver 先出去；claim 與 release 留在畫邊界的那支裡，改補唯讀的 `aos world status` 與 `aos world recover`——「看得見」和「出事能自救」比「能手打它們」有價值得多。
