# 四個懸而未決的設計選擇，各自的優缺點
← [workshop](../README.md)

## 先讀這段（500 字懶人包）

`World` 只和「單一 OS 行程推多世界」綁在一起；root 權力可歸 `aos core`，`aos exec` 不必懂
子行程。每世界用完整 kernel 後，政策也不再綁親緣；A／B 誰推可以先不決定。

1. **`World`**：換到同一行程推多世界；賠內部路徑改造。
2. **kernel**：換到每世界自足；賠逐份升級。
3. **拓樸**：完整子世界可獨跑、core 可統管；賠管理協定。
4. **親緣**：不用 UUID 較直觀；賠搬家即換身分、舊 receipt 失效。

## R1 想法池

### 成形的方向

#### 一、`World` 抽象要不要收

**四位獨立地都指出同一個分界**：只要一支 `aos exec` 要同時推進多個世界，`cwd` 就不夠用，
因為它是整個 OS 行程共用的；`root fd` ＋ `*at` 系列 I/O 才能讓每次操作明講自己屬於哪個
世界。反過來，如果每個世界本來就永遠由獨立 OS 行程推進，那這層抽象可能只是多繞一層。

| 選擇 | 得到什麼 | 付出什麼 | 什麼時候會後悔 | 能不能反悔 |
|---|---|---|---|---|
| **收 `World`：root fd ＋版本＋能力** | 世界辨識、版本檢查與能力檢查集中在同一入口；一支 `aos exec` 可推多個世界；測試可注入假的 root；日後做集中 lane 時已有可用的世界 handle | handoff、`$ref`、重導向與其他 I/O 都要從「相對 cwd 的字串」改成「相對哪個 fd」；還要定義 `fork` 後 fd 如何帶過去、symlink、`..`、絕對路徑與 `fchdir` 怎麼算 | 最後仍是一世界一行程，而且 `World` 被做成很厚、每次小操作都得穿過它 | **若只是內部 handle，磁碟格式不變，反悔主要是改實作。**但若能力落盤、API 對外公開，或外掛已依賴 fd／cwd 語意，拿掉或收緊規則就會成為相容性變更 |
| **不收，維持 `aos exec` 內的 cwd／版本判斷** | 現有路徑協定與外掛假設不用動，眼前實作最少 | 驗證容易散在各入口；一支行程仍只能安全地以一個 cwd 推一個世界；之後每個需要世界概念的單元各自帶路徑與規則 | lane 變多、要由單一 root multiplex，或想把同一套操作拿來獨測時，會遇到全面的路徑 API 重構 | **仍可後補，磁碟本身通常不用搬。**但越多外掛把 cwd 當契約，後補時的 API 相容成本越高 |

資深工程師與要接工具的開發者明說，**B 集中 lane 幾乎會逼出 `World`**；資深架構師與研究人員
也都把「多世界」列為收它的主要收益。這使本題的「所以呢」很具體：它不是抽象美不美的問題，
而是第三題若走集中推進，現在不收，之後就得補。

三位（工程師、架構師、研究人員）另行提醒：**root fd 不是沙盒。**若仍准絕對路徑、`..` 或
可逃出根的 symlink，「能力」就沒有形成安全邊界。工程師、架構師與研究人員都不確定目前所說的
capability 到底是**真的權限邊界**，還是只是 root 排程時帶著走的路由／提示；要接工具的開發者
則把同一問題問成：能力究竟綁 fd／inode、路徑，還是 UUID。這個答案若只是實作提示，不必把
`World` 做成安全容器；若是安全承諾，路徑規則就會成為對外契約。

#### 二、`kernel.json` 要單層，還是分層合成

這題的強訊號不是四位選了同一邊，而是**四位獨立地都指出兩邊各自保住了不同的東西**：
單層保住「整個資料夾帶走就自足」，分層保住「root 政策只改一處就真的強制到所有子行程」。

| 選擇 | 得到什麼 | 付出什麼 | 什麼時候會後悔 | 能不能反悔 |
|---|---|---|---|---|
| **單層：每個世界一份完整 kernel** | 一個世界自己就能驗證、搬移、離線重播；外部工具只讀一個檔，不必理解繼承；事故現場較容易重現 | 每個子世界都複製政策；修漏洞或升版本要掃過所有 `.aos`，漏一份就產生政策漂移 | 子世界／lane 數量多、壽命長，或 root 有必須一致套用的安全政策時 | **單層轉分層較容易**：可先把舊的完整檔視為本地 override；但仍要定義它與新 root／父政策的優先順序，並批改舊 kernel |
| **分層：root 強制段＋父政策＋本地 hooks** | root 政策一次更新；父層規則可複用；本地只寫差異，不必在每層複製整份 kernel | 合併、覆寫、刪除、衝突與版本相容都會變成磁碟 ABI；父失聯時怎麼辦也要定義；世界搬到別的父下面，可能不改本地檔卻改了行為；外掛若要理解來源，也得實作同一套合成規則 | 世界常被搬移、要離線單獨重播，或不能接受「祖先改檔後，子世界下一回合暗中換政策」時 | **分層轉單層要把每個世界的有效 kernel 展開並落盤。**這是存量資料遷移，而且會失去原本的來源／繼承資訊 |
| **第三條路：分層撰寫，物化有效內容** | 平時保留 root／父／本地的複用；每一回合或每個世界另有一份可直接執行、可重現的有效 kernel | 同時要管理「來源層」與「有效內容」，必須定義何時重算、哪一份是執行真相，以及更新中途 crash 怎麼恢復 | 若兩份表示經常失同步，除錯會從一個真源變成追兩套狀態 | 轉成純單層可保留物化內容、丟掉來源；轉成純分層可丟物化檔，但會失去既有事故重現能力。兩個方向都要遷移 metadata |

資深架構師與要接工具的開發者明確提出第三條路；資深工程師和研究人員也從事故重建角度得到
同一個必要條件：**`.runi` 只存合成後的 hash 不夠。**四位獨立地都指出，父 kernel 改掉後，
hash 只能證明「現在這份不是當時那份」，不能把當時真正執行的內容找回來。若 `.runi` 的目的
包含重跑／診斷，就得存有效內容或可取回內容的不可變版本；若只想驗出版本不符，hash 才足夠。

這也碰到使用者對外部處理器的原話：

> **外部處理器的構造會很簡單，甚至不需要引用 aos lib。**

要接工具的開發者指出，若外部處理器也必須自己解析 root／父／本地的合成規則，這份「簡單」
就會變重；若它只看已物化的有效檔，複雜度仍可留在 `aos exec` 一側。

#### 三、子行程拓樸選 A、B，還是先固定磁碟 ABI

**四位獨立地都給出相同的主要交換**：A 把每個子行程做成可單獨拿走的小世界；B 把 claim、
排程、commit 與回收集中給唯一的 root。C 並不是沒有代價的折衷，它只把「誰推進」延後，
身分、queue、owner、政策來源與 crash 復原仍得先定。

| 選擇 | 得到什麼 | 付出什麼 | 什麼時候會後悔 | 能不能反悔 |
|---|---|---|---|---|
| **A：完整巢狀** | 子世界與 root 同構；整個目錄可獨跑、獨測、搬移、交付與重播；同一套 `aos exec` 可複用 | 每層都有 kernel、版本與 `.runi`；升級要處理整棵樹，事故時也得先找出是哪一層卡住；多層未完成回合與 receipt 的轉換更難 | lane 很多、很短命，或樹很深時，為每一層維持完整世界的升級與診斷成本會壓過同構的好處 | **沒有共同 ABI 時，轉 B 要搬 queue、鎖、引用、未結 `.runi` 與 receipt。**這不是只換 scheduler |
| **B：集中 lane** | 唯一 root 可做公平排程、集中 claim／commit／回收與跨 lane 提交；kernel 與恢復機制可一次升級；不會長出第二個 owner | queue 在父層、state 在子層，讀一個 lane 要跨位置；root 是瓶頸也是共同故障域，一倒全部停；子行程不能只帶自己的資料夾獨跑 | 要把子行程交付別人、搬到遠端、讓它脫離父世界獨立執行，或需要不同信任域時 | **轉 A 同樣要把父層 queue、owner 與未完成狀態拆回各子世界。**若一開始沒固定共同格式，就是全樹遷移 |
| **C：先固定磁碟 ABI，A／B 只換推進者** | 若共同語意真的成立，日後切換遞迴 `exec` 或 root multiplex 時不用搬世界資料，只換 scheduler／owner 的實作 | ABI 必須先容納 identity、queue、claim owner、kernel 來源、生命週期、恢復與原子提交邊界；若 A／B 的信任域、故障域或原子性其實不同，共同格式會凍結兩者需求的聯集 | 為了暫緩決定而先凍出一個過寬 ABI，之後才發現 A／B 根本不能共享同一套恢復或所有權語意時 | **ABI 定對了，A／B 間主要換實作；ABI 定錯了，仍是全量遷移。**C 只能延後推進方式，不能免除磁碟契約的決定 |

四位也都再次確認前一場的警訊：**A 的核心代價不是「看起來比較複雜」，而是每一層都成為
升級與事故現場。**資深研究人員另指出，B 的集中不是純收益：它把 root 變成共同瓶頸與故障域；
要接工具的開發者則把代價放在外部整合上——queue、state、table、receipt 分散後，單獨測試或
搬走一個 lane 反而要帶更多東西。

這題也直接碰到使用者的原話：

> **CPU 做的事情非常簡單：取出下個指令，執行，然後繼續取指令。**

參與者沒有重開「CPU 該不該簡單」的辯論；他們把差別落到磁碟契約：A 與 B 都可以讓 CPU
維持取指／執行，但 A 讓「下一個指令」散在各子世界，B 讓 root 從集中 lanes 取，C 則要求
兩種取法對同一份 owner／claim／恢復語意有一致解讀。

#### 四、親緣綁路徑、綁 UUID，還是把身分／親緣／位置拆開

本題不再只是「目錄好不好看」。**四位獨立地都把它改寫成：身分、親緣與位置是不是同一件事。**
三位（工程師、架構師、要接工具的開發者）明確提出混合形狀；研究人員則用同一個分法總結四題，
要求身分與位置各自有版本化語意。

| 選擇 | 得到什麼 | 付出什麼 | 什麼時候會後悔 | 能不能反悔 |
|---|---|---|---|---|
| **綁路徑：目錄樹就是行程樹** | `tree`／`ls` 就看得懂親緣；不需 registry；相對 `$ref` 與「只能寫自己子樹」直觀 | rename／搬移會同時改身分；能力、未收 receipt、`$ref` 與 parent 關係可能全部失效或要重寫 | 要抽出一個子世界、經常搬 lane、重新掛父層，或希望 queue 在搬家後仍是同一個 queue 時 | 轉 UUID 要替所有存量配 ID、建立表並掃全樹改引用；既有路徑型 receipt／能力如何續效也要另做遷移規則 |
| **綁 UUID：lane 平放，欄位表達親緣與位置** | 身分與 queue 可在搬家後保持不變；receipt 可繼續指向同一個行程；路徑只是一個可更新的位置 | 要維護 `proc-table`／registry，處理表與目錄不一致、孤兒、循環、重號；人看目錄不再直接知道親緣；複製資料夾時要定義是否換號 | lane 幾乎永遠不搬時，為穩定身分多養了一本帳，卻沒有換到實際收益 | 轉回路徑要展開親緣樹、處理循環與撞名、重寫 UUID 引用，並可能失去歷史身分；也是存量遷移 |
| **混合：`proc_id`、`parent_id`、`location` 分離** | UUID 表示身分，parent 表示親緣，path／URI 只表示目前位置；可保留易看的目錄佈局，又不必讓 rename 自動改身分；內部 `$ref` 仍可相對 world root | 三者各自何時更新、以誰為真源都要成為交易；move／copy 的差異、失敗恢復與 registry 對帳仍不能省 | 實際上從不搬、不複製、不重新掛父層時，三個概念會顯得比一棵目錄樹重很多 | 日後可換 location 而不換 identity，這正是混合方案的收益；但若要完全丟掉 UUID，仍須遷移所有以 ID 表達的引用與歷史 |

資深工程師另提醒：即使 UUID 不變，`$ref` 若仍以 `world_root` 解讀，搬家後的**語意**仍可能變；
「ID 穩定」不等於「引用到的內容穩定」。資深架構師也指出，能力在 move 後是否續效是另一條政策，
不是用了 UUID 就自動得到。這表示 UUID 能穩住「它是誰」，卻沒有替使用者回答「它搬走後還擁有
什麼」。

> 行程這東西，最好是得有自己的資料夾。就，類似巢狀複製的拓樸……
> 總之，我的一些模糊的想法是這樣：**複用、簡潔，是目標。**

路徑方案最直接保住「資料夾就是行程」；UUID／混合方案則保住「行程仍有資料夾，但資料夾位置
不必兼任永久身分」。參與者整理出的代價是：兩者都能符合原話，差別在使用者要不要把「可搬、
可重新掛接」當成現在就要進磁碟 ABI 的能力。

### 還在生長的想法

**能力到底是什麼，尚未成形。**資深工程師與資深架構師直接標記自己沒把握它是安全邊界還是
排程提示；研究人員問的是威脅模型；要接工具的開發者問它綁 fd／inode、path 還是 UUID。
這不只影響 `World` 厚度，也決定移動後能力能否續效。四位目前只把岔路指出來，沒有替使用者
選其中一種。

**「搬移」也還不是一個完整動作。**研究人員問能否在回合中搬、能否跨 filesystem；要接工具的
開發者問 move 與 copy 怎麼分。若只允許世界靜止時、同一 filesystem 內 rename，現有原子模型
還能沿用；若要跨 filesystem 或帶著未完成回合搬，queue、receipt、kernel 現場與身分表要怎麼
一起切換，四位都沒有給出完成的協定。

**C 的「共同磁碟 ABI」目前只有應包含哪些概念，還沒有最小形狀。**四位列出的共同核心包括
identity、queue、owner／claim、kernel 來源或快照、生命週期、未完成回合與原子提交邊界；同時
四位都警告，若直接把 A、B 需求取聯集，可能只是把尚未理解的差異永久寫進 ABI。

**分層 kernel 的有效快照放哪裡，尚未成形。**工程師與研究人員要求事故時能取回內容，架構師
提出「有效快照＋來源」，開發者提出「分層寫、物化有效檔」。仍未回答的是：內容直接隨 `.runi`
保存、存不可變物件後由 hash 指過去，還是每個世界常駐一份物化檔；三者的清理與復原成本不同。

### 大家問出來的問題

| 問題 | 誰問的 | 它卡住哪個決定 |
|---|---|---|
| `.runi` 要能**重建**當時的有效 kernel，還是只要驗出 hash 不同？舊 `.runi` 到哪裡取有效內容？ | 工程師、架構師、研究人員、開發者分別以不同說法問到 | 決定第二題只存 hash 是否足夠，也決定離線重播能否成立 |
| move／crash 時，身分、位置、政策、回合各以哪個檔為真源？搬移中的 receipt 由誰原子改址？ | 工程師、架構師 | 決定 UUID／混合方案是否真的比路徑可靠，而不只是多一本表 |
| 移動能不能發生在回合中？能不能跨 filesystem？若能，原本三次 `rename` 的原子性如何保留？ | 研究人員；開發者也標記跨 filesystem 非原子的疑慮 | 決定第四題承諾的是「改名」還是真正可攜搬移 |
| move 與 copy 怎麼分？複製後是否換身分？ | 研究人員、開發者 | UUID 若不定 copy 語意，會出現兩份資料宣稱是同一個行程 |
| capability 是安全邊界還是路由資料？綁 fd／inode、path 還是 UUID？ | 四位都問到，其中工程師、架構師、研究人員明說自己不確定威脅模型 | 同時卡住第一題與第四題；也影響 move 後既有能力是否有效 |
| 子結果何時原子 commit？ | 架構師 | A／B 若提交邊界不同，C 的共同 ABI 就不能只統一資料夾名稱 |
| 父改 kernel、父失聯或世界搬家後，下一回合沿用舊政策還是立刻繼承新政策？ | 架構師、研究人員、開發者 | 決定第二題的繼承是動態查找，還是 claim 時快照 |
| 不引用 aos lib 的外部處理器，要用什麼一致性測試證明自己正確解讀新 ABI？ | 要接工具的開發者 | 四題一旦改磁碟契約，外部處理器如何維持「構造很簡單」仍缺答案 |

### 明顯的坑

- **把 root fd 當成安全沙盒。**工程師、架構師、研究人員三位獨立地警告：未定義絕對路徑、
  `..`、symlink 與 fd 繼承前，root fd 只能改善定址，不能自動形成權限邊界。

- **`.runi` 只留 kernel hash，卻宣稱事故可重現**。**四位獨立地都指出**：hash 沒有內容；
  父檔一改，舊回合只能知道「對不上」，不能知道「當時跑了什麼」。

- **把 A 的同構誤當成免費複用**。**四位獨立地都把多層 kernel／版本／`.runi` 的升級與診斷
  列為 A 的主要代價。樹越深，這個代價不是相加而已，而是每一層都可能成為不同版本、不同事故
  現場。

- **用 C 延後所有決定**。**四位獨立地都指出**：C 只能延後「誰推進 lane」，不能延後
  identity、queue、claim owner、kernel 來源與恢復語意。尤其第四題不先定，磁碟裡的引用連要指
  位置還是指身分都不知道。

- **以為 UUID 穩定就代表一切續效。**工程師指出 `$ref` 的 world-root 語意仍可能因搬家而變；
  架構師指出 capability 是否續效仍要另定；registry 本身還會帶來目錄／表雙真相與孤兒。

- **把跨 filesystem 搬移仍叫作一次原子 rename。**研究人員與開發者都點出這個前提不成立；
  一旦要跨 filesystem，第四題就不只是命名選擇，而要另有搬移交易與失敗恢復協定。

## 哪幾題其實是同一個決定

這一節是本輪最強的收攏。四位不是把四題看成四個可任意排列的開關，而是反覆指出下面幾組
會互相鎖住。

### B 集中 lane 與 `World` 幾乎是同一個實作決定

資深工程師與要接工具的開發者**兩位獨立地明說「B 幾乎要求 World」**；架構師與研究人員描述
B 時所需的 root multiplex，也同樣依賴每次 I/O 能明確指向不同世界。選 B 卻不收 `World`，
就得用「一 lane 一 OS 行程」或反覆切 cwd 等別的機制補洞；若目標是單一 root 行程內輪流推進，
兩題實際上綁在一起。

### C 與「路徑還是 UUID」不能一前一後地拖延

**四位獨立地都指出**：C 要先固定磁碟 ABI，而 identity 本身就是 ABI。若 receipt、capability、
owner 與 `$ref` 還不知道是指向位置還是身分，就沒有一份能讓 A／B 共用的格式。也就是說，
C 可以暫緩第三題的「誰去推」，但**不能用來暫緩第四題**。

### 分層 kernel 與親緣的表達方式是同一個政策來源決定

資深架構師與要接工具的開發者直接指出：分層 kernel 的「父」究竟是實體目錄祖先、`parent_id`
指到的邏輯父，還是 proc-table 中的 owner，取決於第四題。研究人員也把「政策來源」與「位置」
是否綁定列為四題的共同核心。若用實體祖先找 kernel，就等於讓搬家可能換政策；若用 UUID 親緣
找，就必須讓 registry 參與每回合的政策解析。

### A 與分層 kernel 會把升級成本沿樹深放大

工程師、架構師、研究人員**三位獨立地都指出**這組合的乘數效應：A 讓每層都是完整世界，
分層又讓每層的有效政策依賴祖先；升級時不只要處理多份 kernel，還要確認每一層在當時繼承到
哪一版，事故時也要保留整條來源鏈。這不是說兩者不能同選，而是同選後「有效快照」與版本相容
不再是附加功能。

### 能力的綁定方式把 `World`、身分與搬移三題串在一起

四位都從不同角度問到同一件事：能力若綁 root fd／inode，重啟與搬移後怎麼續；若綁 path，
rename 後怎麼續；若綁 UUID，又由誰把 UUID 解析成目前位置並防止逃出 root。能力若只是排程資料，
問題較輕；若是安全邊界，第一題與第四題就必須一起形成可驗證的契約。

### 最難反悔的不是 A 或 B，而是落盤的身分、政策現場與恢復契約

資深工程師和要接工具的開發者各自用幾乎相同的一句話收尾；架構師與研究人員也獨立得到同一個
結論：scheduler 是實作，只要共同 ABI 正確就能換；真正會迫使所有既有資料夾遷移的，是磁碟裡
如何表示 identity／parent／location、哪一版 kernel 形成本回合，以及未完成的 claim／receipt
怎麼恢復。這是四題之間最一致的共同判準。

## R2 想法池（延伸／組合／變體）

R1 時四位互不見面；R2 開始前，四位都拿到了本檔的 **R1 全文**，所以這輪是在同一份想法池上
接話、拆開原本綁在一起的選擇。使用者先把狀態說清楚：

> **我這邊還在思考，這幾個 choice 我都懸而未決。**

接著給的是傾向，不是決定：

> **1. World** 我傾向於**一個 `aos exec` 推多世界**，但**路徑要改**？我是覺得對於頂層
> `aos exec` 來說，**沒有子行程這件事**，他就是普通的執行指令，只是有些指令他就是
> 子行程的 `aos exec`。
>
> **2. kernel** ……**`aos exec` 不知道啥是子行程**，但在後續 **aos core** 的發展中，
> 可以有這類子行程管理，所以**每個行程都可以有自己的 kernel**，也就是說，**每個行程都是
> 自己的父行程**……反正他們就是**一步一步去跑 inst**。
>
> **3、4.** 我覺得**沒差**，但**不該綁 UUID**。

本輪的張力是：使用者先前已拍板「多核學 Linux，有一個核心最高 root 行程，由單一
`aos exec` 掌握至高權力」，這輪又說「`aos exec` 不知道啥是子行程」。若兩句都保留，root 的
權力就不能來自 `aos exec` 內建的「父行程模式」；它只能是上層 `aos core` 的管理權，或先由
協定約定、日後再用 OS 權限強制。這成了四位本輪共同接續的主軸。

### 成形的方向

#### `aos exec` 是扁平 CPU；知道樹的是 `aos core`

**四位獨立地都提出同一個拆法**：`aos exec` 永遠只知道「對這個 folder 走一步」，不讀 parent、
不辨認自己是不是子行程；`aos core` 才知道行程樹，並擁有建立、排程、join、收割與 commit 的
管理權。

| 層次 | 它知道什麼 | 它做什麼 |
|---|---|---|
| **`aos exec`** | 一個世界的 folder、自己的 kernel、queue 與本回合 `.runi` | 彙整、claim、執行一步、release；內層 `aos exec <child>` 對它只是普通指令 |
| **`aos core`** | 哪些世界是行程、它們的位置、ready／join／generation 狀態 | 建立與收割、選下一個世界、授予執行額度、收 receipt、承認 commit |
| **子世界** | 只知道自己的資料夾，不保存「我上面有父行程」 | 用自己的 kernel 與 queue 獨立走一回合 |

資深工程師把 root 權力寫成 core 對 proc 表、queue、commit 的唯一寫權；資深架構師說「知道樹並
擁有 commit 權的是 `aos core`」；研究人員把它叫作 core 的建立／收割與 queue 寫權；要接工具的
開發者則放在 `aos core step <path>` 的啟動、join 與配額。四種說法的共同效果是：**「至高權力」
不再是 `exec` 認得的特殊身分，而是誰有權改管理資料與承認結果。**

這也拆開了 R1 綁在一起的兩件事：**集中管理不等於集中在同一個 OS 行程裡執行。**core 可以
保有唯一管理權，同時把每個子世界交給一個普通的 `aos exec <path>`；因此 B 式的集中權力，
不再自動逼出 B 式的集中 lane。

#### 每個世界保有完整 kernel，不向父層動態繼承

**四位獨立地都接住使用者「每個行程都可以有自己的 kernel」的傾向**：每個
`procs/<name>/.aos/` 都保存完整 `kernel.json`，執行時只看自己，不沿目錄或 parent 欄位向上找。
這換到的是世界自足、可獨跑、可搬、可重播；賠掉的是政策不會自動同步，升級責任改由 core
逐份處理。

四位給的複用方式略有不同：資深工程師主張完全不繼承；資深架構師讓 core 在建立／升級時物化
完整 kernel，另以 `kernel.source.json` 記來源；研究人員讓父先明寫子 kernel，再呼叫它；要接
工具的開發者用模板建立。共同點是**複用發生在寫入完整檔時，不在執行當下暗中合成**。

這使 R1 的第二、第四題解綁：kernel 不再需要判斷「父」是目錄祖先還是 UUID parent，搬到別處
也不會只因換父就暗中換政策。代價則從「合成規則」移成「誰負責把每份完整檔升級到正確版本」。

#### 對外路徑規則可以不改；要改的是單一行程 multiplex 的內部 I/O

使用者問「一個 `aos exec` 推多世界，但路徑要改？」**四位獨立地都把答案拆成兩層**：

- 對 instruction、`$ref`、重導向與外部處理器而言，路徑仍以**各自世界的 folder** 為根，不必
  改成相對總 root，也不必讓子世界知道父路徑。
- 若「一個 exec」是指**同一個 OS 行程**同時持有多個世界，內部才要用 root fd／`openat`；
  啟動普通子命令前再 `fchdir(root_fd)`，管理者本身不反覆切全域 cwd。
- 若「一個 exec」是指**命令呼叫樹**，每次 `aos exec <child>` 仍只推一個世界，原本 cwd 模型
  就能保留。

資深工程師把同 OS 行程的版本寫成 `advance_once(World&)`；資深架構師提出
`aos exec w1 w2` 逐個 root fd 推進；研究人員明確要求先分清「單一行程」與「命令樹」；要接
工具的開發者採命令樹，認為多世界不是在同一行程裡切 cwd。**四位都保住了使用者的外部路徑
語意，尚未對齊的是「一個 `aos exec`」究竟指哪一種實作。**

#### 原本的 A／B 被重組成「完整子世界＋集中管理」

**四位獨立地都畫出近似的磁碟形狀**：root 與 `root/procs/<name>` 各有完整的
`.aos/{kernel.json,inst.json,…}`；父端另有只給 core 看的 proc-table／manifest，記 path、
generation、ready／join 等管理狀態。子世界沒有 parent 欄位，queue 也在自己的 `.aos`，不再另設
集中 `lanes/`。

這個形狀拿了 R1 A 的**儲存方式**（每個子行程都是完整小世界），也拿了 R1 B 的**管理方式**
（root core 是唯一管理者），但不要求把所有 queue 搬到父層。資深工程師與要接工具的開發者
明說：共同 ABI 可以縮成「自足的 world step」，proc-table 是 core 的索引，不是 `exec` ABI；
循序呼叫、多子行程，或日後在同一 OS 行程內呼叫 `advance_once(World&)`，磁碟上的子世界都不必
跟著搬。

所以第三題現在有一部分可以先不決定：**誰去推世界可以延後；子世界是否自足、queue 放哪裡、
core 如何認領結果則仍是磁碟契約，不能延後。**

#### 不用 UUID，改用父域名稱／路徑加 generation

四位都接受使用者「不該綁 UUID」的傾向，也都排除 inode 與內容 hash：inode 經搬移／複製不
可靠，內容 hash 又會隨世界演化。替代形狀有兩種：

| 形狀 | 誰提出 | 得到什麼 | 付出什麼 |
|---|---|---|---|
| 父域內的 `(name, generation)`／`<slot>@<generation>`，表內另記相對路徑 | 工程師、架構師、研究人員三位獨立提出 | 同名資料夾刪掉重建後，舊 receipt 不會誤投給新行程；不用全域 registry | 身分只在父域內成立；搬出父域要 detach／adopt，未完成關係不能自然續接 |
| 正規相對路徑就是地址，`.runi` 只代表本次 activation | 要接工具的開發者 | 最少 metadata，`tree` 仍直接可讀 | rename 就是改址，copy 是新世界；若重用同一路徑，還要另靠回合資料避免收錯舊結果 |

四位的共同界線是：**不用 UUID 就不承諾「搬家後仍是同一個行程」。**工程師與開發者只允許
沒有 `.runi`、沒有待收 receipt 時做同 filesystem rename；研究人員把搬移定義成 detach＋新
attach、舊 receipt 失效；架構師則要求跨父域時明做 `adopt`。generation 的用途不是模仿全域
UUID，而是防止「同名新目錄收到上一代的結果」。

### 還在生長的想法

**「一個 `aos exec` 推多世界」仍有三種形狀。**工程師的 `advance_once(World&)` 是同一 OS
行程內 multiplex；架構師的 `aos exec w1 w2` 是同一命令逐 world root fd 推進；研究人員與要接
工具的開發者保留父批次呼叫多個普通 `aos exec <path>` 的命令樹。三者都能讓 `exec` 不懂親緣，
但啟動成本、全域 cwd、總退出碼與故障隔離不同，尚未收成一個介面。

**proc-table 是真源還是可重建索引，還沒對齊。**資深工程師與要接工具的開發者明說它應可由
自足 worlds 重建；資深架構師與研究人員則讓 manager manifest 保存 generation／join 等只存在
父端的狀態。只要有未結 join、配額或上一代 receipt，哪些欄位能重建、哪些必須耐久，就還要分清。

**root 權力的「有權」尚未變成「別人做不到」。**四位都先形成 core 是唯一 writer 的控制協定，
也都把強制機制留著：POSIX 權限、僅 core 持有的 dirfd／authority handle、降權執行，或完整 OS
sandbox。若所有程式仍用同一 UID 且 instruction 可跑任意命令，現在的至高權力只是守約，不是
安全隔離。

**完整 kernel 的升級來源仍有數種版本。**模板、`kernel.source.json`、父先物化再呼叫，都保住
執行時自足，但來源檔是不是規格、core 升級失敗時怎麼留下現場，尚未成形。

**agent loop 刻意留給 R3。**本輪沒有把上述管理協定直接長成 loop；使用者原話：

> 這些東西其實頗多，我會建議 **agent loop 可以延到下一輪**。

### 大家問出來的問題

| 問題 | 誰問的 | 它卡住什麼 |
|---|---|---|
| 「一個 exec」是單一 OS 行程、一條命令樹，還是同一命令接多個 world？ | 研究人員直接問；工程師、架構師、開發者各自給了不同實作 | 決定現在是否需要 `World&`／root fd，也決定多世界的錯誤與退出語意 |
| root 的唯一寫權靠守約、POSIX 權限／fd，還是 sandbox？ | **四位都問到** | 決定「至高權力」只是排程規則，還是真的安全邊界 |
| 一個世界 busy／失敗時，其餘世界是否照跑？總退出碼怎麼算？ | 架構師 | 多世界若進同一次 `aos exec`，就必須有批次失敗語意 |
| 父 `.runi` 未清而子已完成，父 crash 後 receipt 算哪一回合？ | 工程師 | core 收結果與父回合 commit 的原子邊界仍未定 |
| 搬移是否保留未結 join？ | 研究人員 | 不用 UUID 後，detach／adopt 能否延續等待關係仍未回答 |
| 外部處理器能否繞過 core，直接 claim 子世界？ | 要接工具的開發者 | 若可以，core 的唯一管理權是建議；若不行，就需要可強制的權限機制 |

### 明顯的坑

- **把「core 是唯一 writer」直接當成安全隔離**。**四位獨立地都指出**：同 UID、又允許任意
  POSIX 指令時，沒有權限分離或 sandbox，外部程式仍能繞過 core 改檔。

- **同一 OS 行程推多世界，卻繼續靠全域 `chdir`。**工程師、架構師、研究人員三位都改用
  root fd／`*at`；否則一個世界切 cwd 時，其他世界的相對路徑會跟著變。

- **不用 UUID，就假設不必處理舊身分。**工程師、架構師、研究人員三位獨立加入 generation，
  正是為了防止刪除重建後，同名新行程誤收上一代 receipt。

- **拿 inode 或內容 hash 當替代 ID**。**四位獨立地都排除這條路**：inode 經複製／跨檔案系統
  不可攜，hash 則會在世界正常演化時改變。

- **讓活著的世界透明搬家**。**四位都把搬移收緊為新地址、detach／adopt，或只准沒有 `.runi`
  與待收 receipt 時 rename。若仍承諾活搬，舊 join、能力與 receipt 的歸屬就重新變成未解的交易。

- **proc-table 一面說是可重建索引，一面又把唯一的 generation／join 寫在裡面。**工程師、
  架構師、研究人員、開發者給的版面都需要父端管理資料，但哪些是 cache、哪些是耐久真相還沒
  分開；不分就會重新出現表與目錄雙真相。

## 轉交提案（未拍板，不自行改規格）

使用者本輪已明說：

> **我這邊還在思考，這幾個 choice 我都懸而未決。**

所以下列仍只是 R2 收窄後、**要使用者拍板才足以改規格**的提案：

1. **是否採納「扁平 `exec`、階層 `core`」這條邊界。**若採納，`aos exec` 永遠只推一個
   self-contained world，不讀 parent；`aos core` 才管理 proc-table、建立／收割、join 與 commit。
   還要另拍板 root 權力先只靠協定守約，還是現在就要求 POSIX 權限／fd／sandbox 強制。

2. **「一個 `aos exec` 推多世界」究竟是哪一種。**可選命令樹中的多次單世界 exec、單一命令
   接多個 world，或同一 OS 行程內的 `advance_once(World&)`。只有最後兩種需要現在改成 root fd
   型內部 I/O；instruction 與外部處理器看見的路徑仍可維持「相對自己的 folder」。這個實作選擇
   若先保留命令樹，**可以延到之後再定**。

3. **是否採納「每世界一份完整 kernel，不動態繼承」。**若採納，還要定由 core 用模板、
   `kernel.source.json` 或其他方式建立／升級；`.runi` 如何指認本地 kernel 現場也仍須落規格。
   這會取代 R1 的動態分層選項，不再需要用 parent 解出有效 kernel。

4. **是否採納「完整 `procs/<name>` 世界＋core proc-table」的磁碟形狀。**還要拍板 queue 留在
   各子世界、取消集中 `lanes/`，以及 proc-table 哪些欄位可重建、哪些 generation／join／receipt
   狀態是耐久真源。誰實際推進子世界可以之後再換，不必跟磁碟版面一起定死。

5. **不用 UUID 之後，handle 用相對路徑，還是 `(name, generation)`。**同時要拍板 rename、copy、
   detach／adopt 的語意，以及有 `.runi`、待收 receipt 或未結 join 時是否一律禁止搬移。R2 四位
   都不再承諾透明搬家；差別只在要不要用 generation 阻擋同名新世界收錯舊結果。

**agent loop 的實作架構不在這批轉交內。**使用者已指定留到 R3，本輪不先替它改規格。
