# 議題：agent loop 之前要做哪些 core 小專案？

← [workshop](../README.md)

**議題**：在開始 T5 agent loop 之前，應該先做出哪些 aos core 核心小專案？（「零個」是合法答案。）

**使用者提出的四個構想**：取下一條指令（inst 慣例 vs 通用 lib）、快取／暫存器
（暫名 `.aos/inst.cached`，要更精簡的名字）、`aos wait`（回呼而非硬 sleep）、
`aos func foo`（每輪投遞兩筆：本步工作＋抓下一條）。變數與控制流明說不做，要往 lisp 走。

---

## R1 結論

### 共識

1. **使用者說的「cache／暫存器」不是 cache，是 continuation（續體）。** 三位獨立得出同一
   結論，用詞都不同但指同一件事。它不可丟棄、不是加速層、沒有一致性問題要處理——它就是
   「這件事做到哪了」的持久狀態。**CPU 類比在這裡是誤導的**：register／L1 的本質是可丟棄
   的加速層，而這東西丟了就等於工作消失。
2. **`wait` 與 `func` 是同一個原語的兩種狀態**，不是兩個功能。`wait` 是**時間續體**
   （條件是「到了某個時刻」），`func` 是**序列續體**（條件是「還有下一條 form」）。使用者
   注意到的「func 每輪投遞兩筆」與「wait 每輪重投自己」，是同一個機制。
3. **「取下一條指令」不需要新機制。** 現有的投遞協定（`.aos/inst.tempd/`，見
   [`docs/aos-folder.md`](../../../docs/aos-folder.md)）本身就是 continuation 的傳遞方式。
   使用者列的兩個候選（(a) 最後放一筆取件指令、(b) 通用 lib）在三位眼中都是**既有機制的
   用法**，不是新東西。
4. **真正夠格當 T5 前置條件的只有一件事：原子投遞的 API。** 三位從三個方向指到同一處
   ——這正是 roadmap T2 已知的缺口（「投遞那一步只有協定沒有 API」）。M1：痛了就補進
   `core/inst` 的 handoff；M2：若腳本無法安全原子投遞，`aos enqueue` 就是真前置；
   M3：續體與原子投遞不可避。
5. **命名**：兩票 `.aos/k/`（`k` 是 continuation 的慣用符號，短且準確），一票
   `.aos/state.d/`。三位都主張**不要叫 cache**，因為那個字會誤導成可丟棄的加速層。

### 分歧

- **#1 T5 之前要不要做 core？** M1／M2：**零個**——T0–T4 已足以跑完「模型→工具→模型」，
  痛點才配得上抽象。M3：**一個 `core/eval`**——不先標準化續體協定，每個子命令都會自己
  發明一套，之後零碎累積 ad-hoc（`wait`、`func`、然後 `if`、`retry`、`map`……）。
- **#2 `wait`／`func` 的歸屬**。M1：`func` 該是 **module**（它是 evaluator／語言政策，
  不是 POSIX 執行原語）；M2：`wait` 與 `func` **都是 module**；M3：兩者都是**使用者空間
  就夠**（因為續體區一旦標準化，它們只是續體的兩種用法）。三種答案都不是「進 core」。
- **#3 續體區要不要現在就標準化？** M3 主張現在（否則協定會被各家私定）；M1／M2 主張
  等 T5 跑出真痛點。這其實是 #1 的具體形式，但可以獨立回答。
- **#4 使用者原提案沒有辯護人**（**議長的選角失誤**，不是議員的結論）：三個角色都不負責
  為「`wait`／`func` 進 core」辯護，所以「不該進 core」這個一致意見**部分是選角偏斜的
  產物**，不能當成三方獨立驗證。

### 新論點

- **回合中途死掉的洞**（M2）：工具已經造成副作用、但續投遞之前 process 死了。重跑會重複
  副作用，不跑就停機。現有規則（`.runi` 留著、不自動重跑，見
  [`docs/roadmap.md`](../../../docs/roadmap.md) T2）只保證「不自動重放」，**沒有回答
  「那接下來怎麼辦」**。M2 建議磁碟上的 phase／idempotency 檔＋恢復腳本。這是本輪唯一一個
  roadmap 沒有記到的缺口。
- **`$ref`／`$env`／`$opt` 不是 quote／unquote**（M3）：它們是**晚綁定**。所以已有的指示詞
  機制**不能**直接當成 lisp 的 quote 來用——想走 lisp 就需要另一個機制
  （M3 給的形狀是 `["emit", ["quote", inst]]`）。
- **lisp 的具體對應**（M3）：JSON 陣列＝S-expression；`aos exec` 一回合＝一次 reduction
  step，回合邊界＝硬的約簡邊界；續體存 `.aos/k/<id>.json`；`func` 的游標與 `wait` 的
  `{at, then}` 是同一原語的兩種狀態。**這是本輪唯一把「lisp」講到可被反駁的程度的發言。**
- **`wait` 會浪費空轉回合**（M2）：每回合重投自己等於輪詢。在 `--loop` 底下這是可接受的，
  但它讓「回合」這個單位同時承擔了計時器的角色。

### 下輪焦點

1. **補一個辯護人**，讓 R2 有人正面主張「`wait`／`func` 應該進 core」，修掉 #4 的偏斜。
2. **分歧 #1／#3 對決**：`core/eval`（現在標準化續體）vs 零個（等 T5 的痛點）。要求雙方
   給出**可驗證的預測**——例如「不先做的話，T5 腳本會在第幾步撞牆」。
3. **原子投遞 API 的形狀**：它是 `core/inst` 長出一支 `aos enqueue`／handoff API，還是
   一個新的 core 小專案？（共識 4 只說了「它是唯一夠格的」，沒說它長什麼樣。）
4. **回合中途死掉的洞**要不要現在處理，還是明確歸到「不做」。

## R2 結論（交鋒輪，補進原提案辯護人）

R2 有實質位移：**兩人改立場、一人撤回主張**。R1 的「零個 core」共識，在 R2 被兩個方向同時
擠壓成一個具體的例外。

### 共識

1. **唯一該在 T5 之前做的是投遞 API，而且它是 `core/inst` 的擴充，不是新小專案。**
   議員一從「痛了再補」**改成「T5 前就補」**（明說這是讓步）並給出形狀：handoff 加一支
   `deliver(base, bytes)`（同目錄唯一暫檔 → `rename`），CLI 是 `aos enqueue <folder> [file|-]`
   給腳本與其他語言的生產者用；**只保證「完整且可見」**，驗證與隔離仍留在彙整那一步；
   C ABI 等實證再說。議員四的預測、議員三 R1 的「原子投遞不可避」都指向同一處。
2. **`k/`（續體）與 `c/`（熱快取）是兩層，要分開命名——這推翻了 R1 共識 1 的一半。**
   辯護人指出 R1 只對「持久狀態」講對了：`{at, then}`、函數游標確實是續體，但**解析後的
   forms／context 是可丟棄、可重建的熱快取**，兩者可以並存。議員一同意，並加了限制條件：
   `c/` **只放帶內容雜湊的可重建物**，量到成本才定。
   → **使用者原本的 register／L1 直覺被部分平反**：它不是續體的別名，它是第二層。
   但**持久狀態不可以叫 cache**（辯護人自己讓步的一點），兩層必須分名。
3. **`wait`／`func` 是同一個「續體推進一步」機制的薄前端**——這點四位都不反對。議員一給了
   具體版面：`k/w.json:{at,then}`、`k/f.json:{src,i}`，共用一筆 `k-step` 指令；`wait` 未到期
   就重投自己，`func` 投 `[form[i], step]`。分歧只剩「何時做、住在哪」，不再是「它是什麼」。
4. **`core/eval` 不在 T5 之前做**——由主張者議員三自己**撤回**。他接受辯護人的「抽象稅要有
   人付，而現在無人付」，改成設一道門檻：**出現第二種續體格式／第二個互讀者才抽 eval**。
   他仍給了形狀備查：`["aos","eval",".aos/k/<id>.json"]`，讀一個 form、reduce 一步、投遞
   零到多筆 inst，未完狀態落盤；**eval 管 form 與續體，inst 管 POSIX 批次的驗證與執行**。

### 分歧

- **#5 投遞 API 的時機**：議員一**無條件前置**（T5 之前補）vs 議員二**條件式**（等「第二個
  生產者要重寫 `temp→rename`」才補；沒命中就不升格）。兩人對**做什麼**已無異議，只差
  **什麼時候**。
- **#6 `wait`／`func` 的歸屬**：辯護人主張**現在進 core**（理由：腳本能做不等於不該進 core，
  否則 `inst` 也可以被 shell 取代；跨回合自我推進的「喚醒」與「序列展開」就是基礎語意）；
  議員一說是**薄前端**（機制摺在 `k-step`，UX 可以分名）；議員二說 **module**；議員三說
  **非前置**。
- **#7 `c/` 熱快取層現在要不要定**：辯護人要兩層並立即分名；議員一要**等量到成本**。
- **#8 回合中途死掉的洞**：議員二明確歸到**不做**——T5 **不保證**副作用已發生但續投遞未
  完成的情形，`.runi` 停機交人判斷即可；通用 exactly-once 屬 roadmap 已排除的 crash
  recovery，冪等鍵只是工具慣例。議員三反過來擔心 **T5 會漏測這個洞**（他自陳這是自己
  可能錯的地方）。

### 新論點

- **「腳本能做」不是「不該進 core」的理由**（辯護人）：照這個標準，`inst` 本身也可以被 shell
  取代。判準應該是「跨回合自我推進」是不是 aos 的基礎語意——他主張是。
- **停損線**（議員二，回應「等痛點等於永遠不做」這個指控）：T5 原型必須跑完「模型→工具→
  模型」＋回合之間人可以介入＋`Ctrl-C` 後續跑。**升格的兩道門檻**：出現第二個生產者要重寫
  `temp→rename` → 補投遞 API；出現**兩個實作者必須互讀彼此的續體** → 才立續體契約／eval。
  沒命中就不升格。
- **N 版續體格式的代價該不該付**（議員二）：付，但**只容許一個私有原型**。理由是「沒有第二
  個讀者時，統一格式就是在猜」；現在進 core 只會把第一版的偶然形狀永久化。
- **eval 與 inst 的邊界**（議員三）：eval 管 form／續體的生命週期，inst 管 POSIX 批次的驗證、
  執行、彙整。這條線即使 eval 延後也仍然有用。

### 下輪焦點（R3 收斂：逼取捨，不准開新戰場）

1. **#5 二選一**：投遞 API 無條件前置，還是等第二個生產者？要求雙方給出「選另一邊的代價」。
2. **#6 二選一**：`wait`／`func` 現在進 core，還是先當 T5 的薄前端腳本？
3. **#7 一句話定案**：`c/` 現在分名，還是等量到成本再說。
4. **#8 一句話定案**：中途死掉的洞歸「明確不做」，還是列進 T5 的驗收。

## R3 結論（收斂＋使用者在本輪注入的新概念）

> 使用者在 R3 開議時親自加入新概念：**核心 CPU（`aos exec`）本質上是無窮資源，但未來會遇到
> LLM endpoint 這種需要排隊排序的有限資源——CPU 與 GPU 是怎麼交流的、CPU 怎麼指揮 GPU？**
> 所以 R3 不只是收斂輪，後半是發散小節。

### 四題的取捨結果

| # | 題目 | 結果 | 代價（四位講法一致的部分） |
|---|---|---|---|
| #5 | 投遞 API 的時機 | **無條件前置 3:1**（議員二仍主張等第二個生產者） | 要先凍結 `deliver`／`aos enqueue` 的介面，日後背相容包袱 |
| #6 | `wait`／`func` 歸屬 | **沒有人主張現在進 core**（薄前端 2、延後 2）。**辯護人讓步**：延後，但主張最終屬 core | 容忍私有 `k/` 格式先分裂、重複解析，暫時無法互讀 |
| #7 | `c/` 熱快取 | **等量到成本 3:1**（辯護人仍主張現在分名） | 原型期先承受重複解析，日後可能搬檔改名 |
| #8 | 中途死掉的洞 | **明確不做，4:0 全票** | 副作用已發生而續投遞未發生時，只能靠 `.runi` 停機交人判斷，T5 不保證恢復 |

**#6 的關鍵一擊**：議員一／二／三不約而同用同一個論點打掉辯護人的「腳本能做不成理由」——
**證據層級不同**。`inst` 已經承擔經實證、被多方共用的不變式；`wait`／`func` 目前**還沒有
第二個互讀者**。辯護人接受了，把 #6 從「現在進 core」讓到「延後」。

### 有限資源（新概念）的共識

1. **既有機制缺的四樣東西，四位講的是同一份清單**：`.aos/inst.tempd/` 是 command buffer／
   mailbox，但**無順序承諾、無容量上限、無 fence、無退避**；`.runi` 是**回合鎖，不是 endpoint
   的 admission lock**。另外**沒有 doorbell**——目前靠 `--loop` 輪詢代替（議員一）。
2. **第一版留在 `aos llm` module，不進 core**（三位明說，辯護人同意時機在 T5 後）。做法三人
   幾乎同形：**短命 process 搶 endpoint 鎖 → 搶到的那個當排隊者 → 按磁碟票號／FIFO 原子取
   一件 → 做完就退出；429 就把重試時刻落盤，由續體喚醒重投。**
3. **四位一致：這撞上 roadmap 第六節**（「不做全域 LLM daemon 與跨資料夾排程」）。四位也一致
   認為**概念對、時機未到**——沒有人主張現在改那條。
4. **共同的自陳弱點指向同一處**：沒有常駐排隊者時，「競爭者代行 claim」**可能給不出真正的
   公平性**，最終仍需要一個常駐的東西（議員三講得最直白；辯護人補一句「`meta.json` 的原子
   計數可能已經是一個小 scheduler」）。這是整場唯一四人共同承認的未解問題。

### 有限資源的具體版面（辯護人給的，最完整的一份）

core `aos queue`，介面 `submit` / `claim` / `signal` / `poll`：

```text
.aos/q/<device>/in/<seq>.json   檔＝command buffer，目錄＝submission queue
        rename 發布事件         ＝doorbell
.aos/q/<device>/f/<id>.json     ＝fence（poll 未完就重投自己）
.aos/q/<device>/meta.json       記 capacity／next；原子 claim 提供 backpressure
.aos/q/<device>/buf/<id>/in|out ＝staging buffer
```

切分是 **core 只管 queue／sync 原語，`aos llm` module 當 driver**（落盤維持順序與公平）。
辯護人自己把時機定在 **T5 之後**。

**求值模型的講法**（議員三，同一件事的另一種語言）：有限資源是一個 **effect**——
`submit(req, k)` 落盤後化成 `await(fence, k)`；未完成就重投這個 form，完成才帶著結果繼續
reduction。**fence 是續體的對偶**：續體說「我做到哪」，fence 說「你做完了嗎」。

## 總結論（三輪之後，等使用者拍板）

**T5 之前只做一件事**：`core/inst` 補原子投遞——handoff 加 `deliver(base, bytes)`，
CLI 是 `aos enqueue <folder> [file|-]`，只保證「完整且可見」，驗證與隔離仍在彙整那一步。
它不是新小專案。（3:1，反對票主張等第二個生產者出現。）

**T5 之前不做**：`core/eval`（主張者自己撤回）、`wait`／`func` 進 core（無人主張）、
`c/` 熱快取層分名（3:1 等量到成本）、中途死掉的洞（4:0 明確不做）、任何有限資源的佇列原語
（一致認為 T5 後、且第一版在 module）。

**模型上的收穫**（與「該做什麼」無關，但比它重要）：
1. 使用者的「cache」是**兩層**——`k/` 續體不可丟、`c/` 熱快取可丟且可重建。register／L1
   的直覺對，但不能拿來稱呼續體。
2. `wait` 與 `func` 是**同一個「續體推進一步」機制**的兩種薄前端（時間續體／序列續體）。
3. `fence` 是續體的對偶。有限資源在求值模型裡是 effect：`submit` → `await` → 重投。
4. `.aos/inst.tempd/` 已經是 submission queue，但**缺順序、容量、fence、doorbell** 四樣。

**轉交建議**（需使用者拍板，議會不自己改規格文件）：
- `deliver`／`aos enqueue` → 進 [`docs/roadmap.md`](../../../docs/roadmap.md)，插在 T5 之前。
- 「中途死掉的洞」4:0 明確不做 → 進 roadmap 第六節「明確不做的事」。
- `k/`／`c/` 兩層與命名 → 進 [`docs/aos-folder.md`](../../../docs/aos-folder.md)。
- 有限資源／`aos queue`／fence → 獨立成一份 idea（`wf/workflows/ideas/`），不要塞進本記錄。
