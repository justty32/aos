# R3 結論（收斂＋使用者在本輪注入的新概念）

← [agent loop 之前要做哪些 core 小專案？](README.md)

> 使用者在 R3 開議時親自加入新概念：**核心 CPU（`aos exec`）本質上是無窮資源，但未來會遇到
> LLM endpoint 這種需要排隊排序的有限資源——CPU 與 GPU 是怎麼交流的、CPU 怎麼指揮 GPU？**

## 四題的取捨結果

| # | 題目 | 結果 | 代價 |
|---|---|---|---|
| #5 | 投遞 API 的時機 | **無條件前置**（3:1，反方主張等第二個生產者） | 要先凍結 `deliver`／`aos enqueue` 的介面，日後背相容包袱 |
| #6 | `wait`／`func` 歸屬 | **不進 core**（薄前端 2、延後 2；辯護人讓到延後，主張最終屬 core） | 容忍私有 `k/` 格式先分裂、重複解析，暫時無法互讀 |
| #7 | `c/` 熱快取 | **等量到成本**（3:1） | 原型期先承受重複解析，日後可能搬檔改名 |
| #8 | 中途死掉的洞 | **明確不做**（4:0） | 副作用已發生而續投遞未發生時，只能靠 `.runi` 停機交人判斷，T5 不保證恢復 |

#6 的判準是**證據層級**：`inst` 承擔的是經實證、被多方共用的不變式；`wait`／`func` 還沒有第二個
互讀者，所以「腳本能做」不構成現在進 core 的理由。

## 有限資源（新概念）的結論

1. **既有機制缺四樣**：`.aos/inst.tempd/` 是 command buffer／mailbox，但**無順序承諾、無容量上限、
   無 fence、無退避**；`.runi` 是回合鎖，不是 endpoint 的 admission lock。另外**沒有 doorbell**——
   目前靠 `--loop` 輪詢代替。
2. **第一版留在 `aos llm` module，不進 core，時機在 T5 後。** 做法：短命 process 搶 endpoint 鎖 →
   搶到的當排隊者 → 按磁碟票號／FIFO 原子取一件 → 做完就退出；429 就把重試時刻落盤，由續體喚醒重投。
3. **這撞上 roadmap 第六節**（「不做全域 LLM daemon 與跨資料夾排程」）。概念對、時機未到，不改那條。
4. **未解問題**：沒有常駐排隊者時，「競爭者代行 claim」可能給不出真正的公平性，最終仍需要一個常駐的
   東西（`meta.json` 的原子計數可能已經是一個小 scheduler）。

## 有限資源的版面（備查，T5 之後）

core `aos queue`，介面 `submit` / `claim` / `signal` / `poll`：

```text
.aos/q/<device>/in/<seq>.json   檔＝command buffer，目錄＝submission queue
        rename 發布事件         ＝doorbell
.aos/q/<device>/f/<id>.json     ＝fence（poll 未完就重投自己）
.aos/q/<device>/meta.json       記 capacity／next；原子 claim 提供 backpressure
.aos/q/<device>/buf/<id>/in|out ＝staging buffer
```

切分：**core 只管 queue／sync 原語，`aos llm` module 當 driver**（落盤維持順序與公平）。

求值模型的講法：有限資源是一個 **effect**——`submit(req, k)` 落盤後化成 `await(fence, k)`；未完成就
重投這個 form，完成才帶著結果繼續 reduction。**fence 是續體的對偶**：續體說「我做到哪」，fence 說「你做完了嗎」。
