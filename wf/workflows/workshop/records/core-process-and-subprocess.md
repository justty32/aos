# 主題：核心行程、子行程，與外部處理器的契約

← [workshop](../README.md)

|---|---|
| **開場** | 2026-08-25 |
| **已跑輪數** | R1（各自發想）、R2（延伸／組合／變體） |
| **狀態** | 進行中 |
| **參與身份** | 資深工程師 / 資深架構師 / 資深研究人員（作業系統／體系結構） / 要接這個工具的開發者 |
| **缺哪個角度** | **「普通用戶」開場前被使用者拿掉**——理由是現階段還在規劃，複雜的東西之後會包起來只留簡單介面，那個身份只能評判 CLI 好不好用。所以本紀錄**沒有「這東西人看不看得懂」的視角**，續場若要談介面，要補回來。 |
| **reasoning effort** | `xhigh`（本場使用者指定，非 workshop 預設的 medium） |

**主題**：CPU 只該做「取指令→執行→再取」。那匯聚、排下一回合、跑 funcs 該不該變成
`inst.json` 裡**恆常存在的頭尾核心系統指令**？以及「行程」在 aos 裡到底是什麼——
資料夾是主行程、funcs 是子行程、都由核心 CPU 執行；多核就是多支 `aos exec` 指向不同
`inst.json`；外部處理器則簡單到不必引用 aos lib。

**本場不設範圍外**，明講可以主張推翻現有任何決定。

---

## R1 想法池

### 成形的方向

1. **四位一致：核心系統指令的「恆常」不能靠尾指令自我複製，要靠一份版本化的核心描述檔。**
   這是本輪最強的訊號——**四位獨立地都反對使用者原本的尾指令設計，而且提出同一個替代版本**：

   > `.aos/kernel.json`（工程師、架構師、開發者的叫法）／`.aos/system.json`（研究人員的叫法）
   > 宣告**版本化的序言與尾聲**，`aos exec` **在取件時合成**「序言＋使用者批次＋尾聲」。

   系統指令**仍然是普通 instruction、仍然在頭尾**——使用者的形狀保住了。改掉的只有耐久性
   歸誰：**歸機器，不歸指令自己**。反對的理由三種講法：
   - 工程師／架構師：**尾指令失敗一次就永久斷鏈**，資料夾從此沒有心跳。
   - 研究人員：**crash 會遺失、重跑會增殖**——「等於程式自寫 reset vector」。
   - 開發者：crash 之外還有**手改與重複投遞**，恆常性太容易被外力破壞。

   工程師的一句話：**「核心行程不是 `inst.json` 裡永不消失的幾筆，而是 executor 對每批
   工作套用的版本化協定。」**

2. **匯聚留在 `aos exec` 是對的，但理由跟使用者給的不一樣。**
   使用者說匯聚是「灰色地帶，我傾向保留」。參與者同意保留，但給的是**啟動自舉**的理由，
   不是方便：
   - 架構師：**匯聚／claim／release 是「使批次可被安全解讀」的提交協定**，所以它本身
     不能是一筆「需要被解讀」的普通 instruction。
   - 工程師：**普通 instruction 在被安全取出之前，不能負責取出自己。**
   - 研究人員：`chdir`／版本／claim/release 是**位址空間設定與取指前端**，匯聚像
     **DMA／佇列控制器**——留在底層比變成普通指令**更像**真 CPU，不是更不像。

   所以「CPU 只做取指令→執行」這條，四位的讀法是：**取指前端本來就不是指令**。

3. **「行程」要有定義，四位給的三元組幾乎同形。**
   | 誰 | 行程＝ |
   |---|---|
   | 工程師 | 佇列＋私有狀態＋owner |
   | 架構師 | （world 抽成帶 root fd／版本／能力的 `World`；folder 是耐久、權限與故障域，**不是 OS process**，`chdir` 只是執行投影） |
   | 研究人員 | `(world, CPU, queue, turn, runi)` 的一次 **activation** |
   | 開發者 | **world**＝持久資料夾、**lane**＝一份 `inst.json` 及其信箱與鎖、**process**＝有 ID／狀態／信箱的可排程工作 |

   開發者那組 **world / lane / process** 是最好用的詞彙，因為它把使用者原本混在一起的
   「資料夾」「一份 inst.json」「一個可排程的東西」分成三個名字。

4. **判準：func 有沒有自己的 lane，決定它是不是真的子行程。** 三位講法一致——
   **有獨立 queue／`.runi`／信箱／cursor／故障狀態才算子行程；沒有就只是主回合裡的一批 job。**
   使用者說「子行程在 `aos core dofuncs` 這一筆指令下被統一管理、排程」，這句話的兩種讀法
   （同步做完 vs 各有回合）在這裡被切開了，而且**代價差很多**。

5. **`dofuncs` 的具體形狀（三位獨立給出同一套動作）**：
   **快照 `.funcs` → 按持久 cursor 挑 ready 的 → 每回合只推進有限工作量 → 原子投遞下回合
   → 投遞成功之後才更新 cursor**。研究人員加了一條硬約束：**不改已載入的批次**，維持回合
   邊界。開發者加了 **correlation ID ＋ receipt，同一 ID 重跑不得重複副作用**。

6. **多核的真正含義：多個 lane、多個 claim loop，不是多個 writer。**
   四位都指出同一個洞——**`.runi` 只鎖 queue，鎖不住世界**：
   - 工程師：多核指向不同 queue 只代表多個取指器；共享世界就得**宣告資源所有權、單一提交者，
     或接受結果不具決定性**。
   - 架構師：**寫入重疊就須分區所有權或單一提交者。**
   - 研究人員：**沒有 cache coherence**，只有多條局部回合序；要定**單寫者分區、鎖，或 barrier**。
   - 開發者：規格**還須宣告每個路徑的寫入所有權與衝突政策**，否則只隔離了取件，沒有隔離資料競爭。

   工程師的說法：兩核改同一個檔**都會自認成功，但回合順序不存在**。

7. **外部處理器的「零 lib 契約」，四份清單併起來**：
   版本、schema、**路徑基準**、命名、**同檔案系統 rename 的前提**、原子 publish、
   唯一 claim、ack／complete、request／correlation ID、**結果歸屬與結果路徑**、狀態機
   （成功／失敗／取消）、**冪等與重試**、crash 遺留與清理、排序保證、容量上限、
   版本相容、信任邊界（不可信路徑）。
   開發者另外要 **golden files ＋ 一支 conformance CLI**——否則「不用 lib 也接得上」是空話。
   工程師點出 `rename` **只保證可見性原子**；若承諾斷電耐久，還要另立 `fsync` 規則。

8. **exe／lib 的切線，四位一致。**
   **lib＝無政策的協定原語**（parse／validate／deliver／claim／release／result／路徑／
   claim token／原子交易）；**exe＝世界辨識、排程、政策、權限、診斷、人機錯誤訊息、恢復、loop**。
   開發者補一句：**lib 只是參考實作，契約才是本體。**

### 還在生長的想法

- **核心描述檔的名字還沒對齊**：`kernel.json`（3 位）vs `system.json`（1 位）。
- **`.aos/procs/<id>`**（工程師）——子行程各有 turn／status，結果投遞回主行程。這是唯一
  有人給出具體版面的子行程佈局。
- **World 抽象要帶什麼**（架構師）：**root fd**、版本、能力（capabilities）。這正好回答
  規格第十二節「世界本身沒有抽象」那個缺口，而且 root fd 比 `chdir` 更能支援多核
  ——`chdir` 是行程共用的，root fd 不是。
- **外部處理器完成後該做什麼**（開發者問的，沒人答）：ack、寫 receipt，還是**投遞給另一顆 CPU**？
  第三種會讓外部處理器變成 pipeline 的一節，不只是叫用者。
- **turn ID 與最小事件紀錄**（工程師）：五年後最痛的是**副作用已發生但結果未落盤**，所以
  每回合該有 turn ID。他自己標記不確定這值不值得那個複雜度。

### 大家問出來的問題

1. **核心序言／尾聲失敗時，業務批次還跑不跑？**（三位都問了，這題最集中）
   架構師換一種問法：**核心尾聲失敗算不算「本回合未完成」**——也就是要不要留 `.runi`。
2. **多核衝突誰裁決？兩核同改一個檔時誰定因果？**（工程師、研究人員、架構師）
3. **子行程能不能直接寫世界？**（架構師）——這決定 funcs 是隔離的還是共用的。
4. **子行程失敗後，主行程要停住、隔離、重試，還是照常提交下一回合？誰有最終決定權？**（工程師）
5. **誰升級 kernel？核心序尾能不能被世界自己修改？**（工程師、開發者）——如果能，那份
   「恆常」就又回到可被破壞的狀態了。
6. **各核的寫入範圍由誰驗證？**（架構師）
7. **外部處理器完成後是 ack、寫 receipt，還是投遞另一顆 CPU？**（開發者）

### 明顯的坑

- **尾指令自我複製**：crash 遺失、重跑增殖、手改破壞。四位都點名，這是本輪最一致的否定。
- **`.runi` 給人「多核已經安全了」的錯覺**：它只隔離取件，不隔離資料競爭。
- **`chdir` 擋住多核**：cwd 是行程共用的，一支 `aos exec` 只能推進一個世界（規格第十二節
  已記）。要多核就得換 root fd，或一個世界一支行程。
- **`rename` 只保證可見性原子，不保證斷電耐久**。要不要承諾耐久是個尚未回答的問題，而它
  **會大幅改變協定重量**（工程師標為不確定）。
- **funcs 若走獨立 queue，協定可能過重**（架構師標為不確定）；若不走，它就沒有隔離、重啟
  與公平性。開發者的說法：**一旦 func 需要暫停、重試與公平性，它很快就會從 job 長成真正的 lane。**
- **「不用 lib 也接得上」若沒有 golden files 與 conformance 檢查，就只是宣稱**（開發者）。

## 使用者拍板（2026-08-25，R1 之後）

三條，**現在是前提，不是待議**：

1. **`kernel.json` 收。** 四位一致提的「版本化核心描述檔、`exec` 在取件時合成
   序言＋批次＋尾聲」被採納。**尾指令自我複製的設計就此作廢。**
   規格要怎麼改**等 R2 收攏後再動**——`kernel.json` 裡放什麼、`.aos` 版面怎麼加、
   第五節「一回合＝一整批」怎麼改寫，都還沒有形狀。
2. **`func` 這個概念拆掉。** 使用者原話：「func 只是一個模糊的概念，我自己的沒想好，
   我是覺得可以**拆成 job 和 lane，各自發展**。」——採納了 R1 開發者提的
   world／lane／process 詞彙裡的 lane，並讓 job 與 lane 各自演化。
3. **多核學 Linux。** 使用者原話：「多核這塊就**學習 linux，有一個核心最高 root 行程，
   由單一 `aos exec` 掌握至高權力**。」——這選了 R1「單一提交者」那條路，
   放棄「分區所有權」與「明講不保證決定性」兩個選項。

### 使用者本輪注入的新概念：行程有自己的資料夾

> **行程這東西，最好是得有自己的資料夾。** 就，**類似巢狀複製的拓樸**，我們用
> `aos exec xxx` 來將 xxx 資料夾化作行程，在執行的過程中，他會有子行程，那個子行程的
> 執行方式就是在 `xxx/.aos/inst.json` 中，被另一個 `aos exec` 去呼叫……**好像不太對**……
> 總之，我的一些模糊的想法是這樣：**複用、簡潔，是目標。**

使用者自己標記「好像不太對」，並補一句「討論的時候不需要堅持複用和簡潔，盡量發散就好」。
**這是 R2 的主軸。**

## R2 想法池（延伸／組合／變體）

### 成形的方向

1. **使用者那句「好像不太對」，答案是：他把兩件事疊在一起了。**
   工程師一句話點破——**「行程樹可以巢狀，取件權不必巢狀；狀態分散在子目錄，
   claim／commit 權集中於 root。」**

   使用者的原句是「子行程的執行方式就是在 `xxx/.aos/inst.json` 中，被另一個 `aos exec`
   去呼叫」。**「另一個 `aos exec`」就是不對的地方**——它會產生第二個 owner，
   而使用者同一輪剛拍板「單一 `aos exec` 掌握至高權力」。**兩條決定本來就在打架**，
   他感覺到的就是這個。分開之後兩條都成立：**資料夾巢狀（拓樸），執行權不巢狀（權限）。**

2. **四位獨立地給出同一組兩種拓樸**，而且優缺點的判讀也一致：

   | | **A 完整巢狀／遞迴 capsule** | **B 中央核心／集中 lane** |
   |---|---|---|
   | 子資料夾裡有什麼 | `procs/<id>/.aos/{kernel.json,inst.json,inst.tempd}`——**一個完整的小世界** | 只有 `procs/<id>/{state,outbox,result}`——**私有狀態，沒有 queue** |
   | queue 在哪 | 子世界自己的 `.aos/` | 父的 `.aos/lanes/<id>/` |
   | 誰推進 | root 帶 capability 呼叫 `aos exec <child>`，**每次只推一回合，不啟動子 loop** | 唯一的 root `aos exec` 以 root-fd／cwd 輪流 multiplex 所有 lane |
   | 好處 | **子世界跟主世界同構**——最大複用；可單獨搬移、測試、除錯 | **不產生第二個 owner**；root 完整掌握 claim／排程／回收 |
   | 代價 | **多層 kernel 的升級與版本相容**；多層 `.runi` 的診斷體驗 | 子世界**不能自啟動**、不能單獨搬走 |

3. **研究人員給了讓 A／B 不必二選一的合成：「同一磁碟 ABI、兩種執行拓樸」。**
   **先固定資料夾 ABI，遞迴 `exec` 與單 root 排程就成為可替換的實作。**
   兩種拓樸共用同一個 `<proc>/root/.aos/`，磁碟格式不變，變的只有誰去推它。
   **這一條同時滿足使用者要的「複用」與「簡潔」**，而且不必現在就選 A 或 B。

4. **第三種變體：把親緣從實體路徑解綁**（架構師的「可搬移子世界」、研究人員的「邏輯樹」）。
   lane **平放**在 `.aos/lanes/<uuid>/`，親子關係用 `parent`／`world_root` 欄位表達；
   父只在 `.aos/procs/<id>.json`／`proc-table.json` 記 URI、能力與 join 狀態。
   **路徑可搬，身分與佇列不變。** 父子是**邏輯關係**，不受實體路徑綁定。

5. **job → lane 是一條單向升格路徑，四位給的機制幾乎逐字相同。**
   使用者說「拆成 job 和 lane，各自發展」——參與者的版本是**各自發展，但有一條原子的升格通道**。

   - **job**＝一次性、不可變、**沒有私有 queue**、由父回合領取並執行、產生 receipt 的 envelope。
     版面：`jobs/<id>/{request.json,status.json,result/}`（開發者）。
   - **lane**＝有 `kernel.json`、inbox、`.runi`、cursor、私有狀態、獨立恢復。
   - **升格動作**：原子建立 `<id>.temp` → 寫 manifest ＋**輸入快照** → `rename` 成 lane；
     原 job 留下 `promoted_to`／join handle，**沿用同一個 correlation ID**。
   - **觸發點**（四位列的合起來）：首次需要**跨回合等待、重試、私有狀態、收第二件工作、
     或 spawn 別人**。

6. **root 的「至高權力」被列成一份具體清單**（四位合併）：唯一能——
   **配 ID、建立／終止／收割 lane、claim、授予可寫路徑的 capability、分配執行額度／CPU slot、
   升級 kernel、隔離與處理 crash、承認 completion、跨 lane commit、把子行程的 delta 套用父世界**。
   子行程**只能提交請求**：向父的 `control.tempd/` 投 spawn／wake／cancel。
   工程師的公式：**並行計算、單點提交**——lane 只交 proposal，barrier 之後由 root 發布。

7. **kernel 本身可以分層合成**（研究人員，本輪新增）：
   **有效 kernel ＝ root 強制段 ＋ 父政策 ＋ 本地 hooks，合成後的 hash 隨 `.runi` 留存。**
   這讓 `kernel.json` 不必每個資料夾各寫一份完整的，直接服務「複用」；
   而 hash 隨 `.runi` 留存，等於**回合現場記得自己是用哪一版 kernel 跑的**。

### 還在生長的想法

- **`aos exec --once`**（工程師）：父呼叫子時只推一回合，明確不啟動子 loop。
  現在 `--loop` 是旗標、單次是預設，這個名字是把「單次」變成明講的意圖。
- **`.aos/children.tempd/`**（工程師）／**`control.tempd/`**（開發者）：
  父的信箱分成「子行程的結果」與「子行程的控制請求」兩個，方向相反、不要混用。
- **lane 的狀態機**（架構師）：`created → ready → running → waiting → done|failed`。
  這是本場第一次有人給出完整的生命週期。
- **「只能寫自己的子樹」成為可執行契約**（開發者想接的）：把 root fd／capability
  疊進 `proc-table`，讓寫入範圍不是文件上的約定而是機制。

### 大家問出來的問題

1. **親緣綁路徑還是 UUID？**（**四位全問了**，本輪最集中的一題）
   子世界移出父樹之後，process ID、父子關係、capability、`$ref`、未收的 receipt
   還有沒有效？
2. **父等子是阻塞、join，還是收事件？**（工程師）
3. **子行程的成果立即共享，還是 commit 之後才進父世界？**（研究人員）
   ——也就是 R1 架構師問過的「子行程能不能直接寫世界」，這輪被問成了時機問題。
4. **尾聲失敗時，由哪一層保留現場？**（架構師）多層 `.runi` 時這題才有意義。
5. **job 升格的門檻**該是「首次 yield」還是「首次需要獨立恢復」？（研究人員標為不確定）
6. **移動之後 capability 是否失效？**（架構師）

### 明顯的坑

- **完整巢狀的真正代價是升級，不是複雜度**——**三位獨立標記同一件事**：
  多層 `kernel.json` 的版本相容與升級。工程師與開發者都把「值不值得」列為自己最沒把握的一點，
  架構師則說遞迴 `.aos` 最直觀，但**多層 kernel 與多層 `.runi` 的診斷體驗可能很差**。
  **這是本輪最該讓使用者知道的風險**：A 方案的漂亮之處（子世界跟主世界同構）
  正好也是它的痛處（每一層都要一起升級）。
- **「巢狀」若照字面做成子 loop，就會產生第二個 owner**，直接違背剛拍板的單一 root。
  父呼叫子必須是**推一回合就回來**。
- **升格若不沿用同一個 correlation ID**，job 的 receipt 與 lane 的結果就對不起來。

## 續場資訊

四個 codex session **沒有結束、context 留著**，R2 已經用 `codex exec resume <id>` 接續成功，
**R3 用同一批 id**（resume 之後 `thread_id` 不變）。**只在開場那台機器上有效**——office Windows。

> **`codex exec resume` 不吃 `-s` 與 `-C`**（沙盒與工作目錄從原 session 繼承），
> 帶了會直接 usage error 退出碼 2。`--json`／`-o`／`-c` 照常。事件裡的欄位是
> **`thread_id`**，不是 `session_id`。

## 轉交提案（**未拍板，主持人不自己改規格**）

`kernel.json` 使用者已經拍板要收（見上面「使用者拍板」）。**還等決定的是它的形狀**：

1. **「世界本身沒有抽象」**（[`.aos` 標準第十二節](../../../../docs/aos-folder.md)）——架構師的
   `World`（root fd ＋版本＋能力）是現成的答案，而且 root fd 順帶解掉 `chdir` 擋住多核那條。
2. **`.aos/kernel.json` 進 `.aos` 標準第三節版面的具體樣子**，以及第五節「一回合＝一整批」
   要不要改寫成「一回合＝序言＋批次＋尾聲」。R2 另外提出 kernel 可以**分層合成**
   （root 強制段＋父政策＋本地 hooks），若採納，第三節不只是加一個檔。
3. **拓樸選 A（完整巢狀）、B（集中 lane），還是研究人員的「同一磁碟 ABI、兩種執行拓樸」。**
   第三條可以先不選，但**磁碟 ABI 要先固定**——這是它成立的前提。
4. **親緣綁路徑還是 UUID。** 四位都問了，而且它決定 `procs/`／`lanes/` 的版面第一層。
