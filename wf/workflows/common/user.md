| 項目 | 設定 |
|------|------|
| 語言 | 回覆與 `wf/`／`docs/` 一律繁體中文；程式碼沿用各檔既有語言 |
| 分支慣例 | 直接 commit `main`；push 見下方「push 授權」。分支只用於凍結或實驗 |
| 直接做、不用問 | 改 `wf/` 文件、加測試、跑唯讀指令、build／ctest、開子 agent 隊、做原型讓他試 |

| 回覆風格 | 先結論、短、**大白話**（見下方）；問「要不要」時附**可執行判準**（門檻數字）與後果。他說「不想看」時用實測取代拍板 |
| 沒回答的邊緣狀況 | 視為天然差異或實作時自然可解，不追問、不列待辦（見表下）|

> **他沒回答的邊緣狀況怎麼處理**（2026-09-01 他自己說的通則）：我挖出來的邊緣狀況他沒回應，
> 就代表**要麼只是比喻上的天然差異**（拿現成概念比喻 aos 時，比喻本來就不會處處貼合），
> **要麼實作的時候自然能解決**。兩種都不必再追問、也不列進待辦——留在原本記它的地方，
> 供實作時想得起來就好。

## 說話方式

2026-09-01 他兩次要求「講人話」「跟我說話請用白話」，並寫進 /goal；之後每次 /goal 都重申。
他的理論功力在構想本身，不在 CS 術語；高密度、多線交叉引用的總結他讀不動，會退回來要重講，等於白寫。
所以：完整句子、一段一個重點；術語第一次出現用日常比喻帶過；編號引用（G 幾、B 幾、WAIT_USER 第幾條）點到為止，別讓他查表。技術深度不用降，是表達方式要降。

## push 授權

鐵律 2 說 push 先確認。但他 2026-09-06、09-07、09-09、09-13 都明講「通通允許 push」「隨便 push」——他在路上用手機 app 和 GitHub 看進度，沒推就看不到。
所以：**新 session 開頭照鐵律 2 問一次「還是通通允許嗎」**；他說是，這個 session 內每個 commit 後就直接 `git push origin main`，不再逐次問。

## 不寫自動記憶

2026-09-30 他說 Claude Code 的自動記憶機制是垃圾，`wf/` 才是結構化的記憶與 skills。
所以：**值得跨 session 留下的東西（偏好、規矩、踩過的坑、決定）一律寫進 `wf/` 對應的檔**，照 [STRUCTURE](../../STRUCTURE.md) 的分層放；不寫進 `~/.claude/projects/…/memory/`。那個資料夾只留一句「去看 wf」。

## 出門／不在時（2026-10-09 定）

他出門只能用手機、也不常看。所以**大小決策全部由頂層先自己做**，不停線等他；做錯可以之後改回來。
他回來會說「跟我說說這段時間發生了啥、你做了哪些大決定」——這時用白話報告：發生了什麼、我替他做了哪些決定（附翻案位置）。
因此不在時要**隨手記一份代定清單**（記在當天的 SESSION-LOG 條目或該輪的筆記裡），報告時照它講。

## compact 前先寫交接（2026-10-15 定）

他發現 compact 之後頂層會變笨——忘了規範、忘了這個 session 裡給過的授權和偏好。原文：「像這種comapct後變笨的狀況，有可以改善的方法嗎」「好，派人去設 hook」。

所以：**他說要 compact 前，頂層先把交接寫進 [wf/HANDOFF.md](../../HANDOFF.md)**——session 內授權（push、在家／出門、模型分配）、正在討論的設計與已定／未定、當晚新定的規範條目編號。compact 後 repo 根 `.claude/settings.json` 的 SessionStart hook（matcher `compact`）會跑 [`wf/tools/compact_reload.sh`](../../tools/compact_reload.sh)，把本檔全文和 HANDOFF 最新一條自動讀回來。

## 開發階段不設行數上限（2026-10-09 定）

原型開發階段**不設核心行數上限**；等到成果整理階段再重構、拆檔、濃縮。

## 收工

他大約 16:30 會自己說要收工（2026-09-22：「不用掛收工提醒，大概四點半我就會跟你說」）。所以**不掛收工提醒的計時器**，等他開口。

## 「審」的範圍

他說「審」文件時，除了前後不一致、裁定有沒有落實、壞連結，**也要審設計原則**：冗餘（同一件事多處重寫、兩套機制做同一件事）、該考慮卻沒考慮到的狀況（規模、當機復原、權限、人工介入、版本演進）、跟自己宣稱的原則打架的弱點（2026-09-30 補）。仍然只攤問題給他裁定。審稿提示一開始就把設計問題列成獨立一類（報告分必修／設計問題／建議／要使用者裁定）。

領域詞彙以 `docs/aos-folder.md` 的定義為準；常猜錯再開 `glossary.md`（見 [common/README](README.md)）。

## 討論紀錄只留原文、決定、結論（2026-10-12 夜改）

早上定的是「討論紀錄不刪」（含 AI 寫的審查、思考稿）；**當晚使用者改了**：「thinking 這塊，應該說，只留下我的原文整理後的版本，還有一些決策後的結果，或是跟 AI 討論後的結論。」

所以 `proto*/thinking/` 每份檔只能有三種內容：**使用者原文（整理版）、決策結果、跟 AI 討論後的結論**（使用者說「照建議」採納的 AI 建議也算決定，欄位名、預設值、規則都要留）。AI 的分析過程、利弊表、被推翻的方案、「被使用者改了」的舊版段落、探針、審查都不留——**被推翻的直接刪，不標刪除線留著**；整份都是 AI 產出就整份刪。舊版靠 git 歷史找。
使用者說「清乾淨」指的仍是程式、測試、程式說明文件；thinking 底下要整份刪，還是逐份問過或照他明說的規則做。

## 少用 sh（2026-10-15 定）

看 inst-exec 第三版時，對「agent 當工具用 `sh -c 'aos loop; cat ret.json'`」的回覆：「G這塊應該不用sh吧，就argv[0]用aos-loop就好？拜託，少用sh(把這個記下來)。」

所以：**inst 的 `argv[0]` 直接寫要跑的程式**（`aos loop`、`aos fsm`、指令名），不用 `sh -c` 串東西。要重導、要換資料夾、要接結果，先找 inst 現成的 key（`stdin`／`stdout`／`cwd`）或資料夾慣例（frame：定義掛成 `.aos`、這次的話與結果放在 frame 裡，交給門房 `aos exec frame 定義` 去跑；使用者的工作區由 `AOS_WS` 給，見 [NORMS 定義與工作區](../../../proto8/NORMS/10-基礎設施-定義與工作區.md)）；真的只有 sh 能做的，提案時標出來讓他看。（例子 10-16 依新設計更新、10-16 夜 frame 改名）
