# code map — core/inst/ 函式庫本體

← [core/inst 分冊入口](../inst.md)｜[本資料夾導覽](README.md)｜[code map 總圖](../../code-map.md)

`core/inst/` 函式庫本體的逐檔職責：對外公開標頭，以及 inst／format／resolve／handoff／exec 五個核心分層。
handoff 層有四個 `.cpp`：`handoff.cpp`（取件／釋放）、`handoff_aggregate.cpp`（彙整＝§D-4／§D-5 的掃收件匣→發布）、`handoff_dedup.cpp`（§D-6 的去重與 roll-forward）、`handoff_deliver.cpp`（投遞），加上四個內部標頭 `handoff_fs`／`handoff_header`／`handoff_dedup`／`handoff_issue`。
**新增／刪除 `core/inst/include/aos/` 的標頭，或 `core/inst/src/` 底下屬於這五層的原始碼檔（`inst.cpp`／`format*.cpp`／`.hpp`／`resolve.cpp`／`handoff*.cpp`／`.hpp`／`exec.cpp`／`spawn_prep.*`／`wait.*`），就在這一份加／減那一列。**
C ABI 包裝層見 [capi.md](capi.md)、CLI 層見 [cli.md](cli.md)；跨層的「新增一個 instruction 欄位」維護鏈在 [分冊入口](../inst.md)。

## core/inst/include/aos/ — 對外公開標頭

| 檔案 | 負責 | 關鍵型別／函式 |
|------|------|----------------|

## core/inst/src/ — 五個核心分層

| 檔案 | 負責 |
|------|------|
| `inst.cpp` | **inst 層**：`inst_t::clear()`、`to_string(InstState)`。不碰位元組／JSON，也不碰行程 |
| `format.cpp` | **format 層的公開進入點**：`validate`（對仍是指示詞的位置延後值檢查）、`read_one`／`read_all`／`write_one`／`write_all`（保持整批原子性），以及 `pending_directives` 的查找 `find_directive` |
| `format_internal.hpp` | **內部標頭**（不對外）：format 層三個檔之間的宣告——`find_directive`／`encode`／`decode`。format 層是唯一懂 instruction JSON schema 的層，這個標頭不可以被 handoff／resolve／exec 引用 |
| `format_decode.cpp` | **format 層**：instruction JSON → `inst_t`。認得的 key（`known_key`）、字串位置的 `$env`／`$ref` 指示詞辨認並記進 `pending_directives`、`stderr` 專屬的 `{"$opt":"merge"}` 都在這裡 |
| `format_encode.cpp` | **format 層**：`inst_t` → instruction JSON。未解析的指示詞照原樣寫回，所以能無損 round trip |
| `resolve.cpp` | **resolve 層**：以明示的環境與 `base_path` 交易式解析 `$env`／`$ref`；讀取被引用 JSON、套用 RFC 6901 pointer，以正規化路徑＋pointer 追蹤無限深引用鏈及循環。錯誤帶回 instruction 位置、檔案、pointer、鏈與 errno；完成後重新呼叫 format 驗證。不依賴 handoff 或 exec |
| `handoff.cpp` | **handoff 層的取件與釋放**，以及兩個 `to_string`；只依賴 inst＋format，不印訊息、不執行 instruction。`claim_instruction`：拒絕既有 `.runi`→讀 base→rename 成 `.runi`→**`fsync_dir`**（§D-5 的耐久性同樣拘束取件：`.runi` 存在 ⟺ 有一回合沒跑完）；`read_file` 回 `ENOENT` 時**再 `lstat` 一次**，存在但讀不到（斷掉的 symlink）回 `InstructionReadFailed` 而不是 `NoInstruction`——兩層對「存在」的定義必須對齊，否則夾出「存在但永遠取不走」的第三態。`release_instruction`：`unlink(.runi)`→**`fsync_dir`**（不再靠 CLI `advance_turn` 順帶落盤的巧合，M2 搬走 turn 之後那條線就沒了）。目錄 fsync 失敗只記 `DirectorySyncFailed` issue 續行，不改回傳值 |
| `handoff_aggregate.cpp` | **handoff 層的彙整動作**（§D-4／§D-5）：掃收件匣→攤平成一批→排他發布成 base→維護 header sidecar。`aggregate_instructions()` 只做編排，實體工作切成具名階段函式（`list_deliveries`／`collect_deliveries`／`publish_dedup_hit`／`publish_new_batch`），讀起來就是 §D-5 那張順序表；一輪的工作狀態綁在 `Round` struct 上。§D-6 的去重在 `handoff_dedup.*`，不在這裡。發布順序照 SPEC §D-5：唯一名寫批（`unique_temp_path`）→唯一名寫 header→**rename header（去重承諾的提交點，`swept` 寫 `false`）**→`fsync_dir`→**排他** rename 批（`publish_exclusive`，來源就是自己那份唯一暫存；`EEXIST`＝別人先發布了，本輪放棄、`unlink` 自己的暫存、不清投遞、不標 swept）→`fsync_dir`→刪投遞→`fsync_dir`→全數成功才把 header 改寫成 `swept:true`。**沒有共用的 `<base>.temp` 固定槽位**——共用可變狀態會讓兩個彙整者互相覆蓋對方的批，於是 A 可能發布 B 的批卻只清 A 看到的投遞，剩下的下一輪重跑＝重複執行。去重（§D-6）的閘門是 `swept`，判定與錨的搜尋都在 `handoff_dedup.*`；撞 `EEXIST` 時不刪錨（那不見得是自己的檔）。崩在「寫完批、還沒發布」之間會留下 `<stem>-<pid>-<seq>.json.temp` 殘骸，**刻意不掃刪**（§D-8，清理歸人或 M3 的 `aos recover`）。投遞出問題分三條路：內容無效→隔離成 `.bad`（排他，撞名換唯一名，絕不覆蓋）、讀不到→留在原地記 `DeliveryReadFailed`（`ENOENT` 靜默）、非普通檔→跳過記 `DeliveryNotRegular`（擋 FIFO 卡死 `open`）；以 `.json` 結尾但形狀不合的名字記 `DeliveryNameIgnored` 出聲。`opendir` 用 RAII guard 持有。**同一輪 `HeaderWriteFailed` ＋ `DeliveryRemoveFailed` 一起出現＝致命**（回 `PublishWriteFailed`，不新增列舉值），否則是無上限的副作用重播 |
| `handoff_dedup.hpp`／`.cpp` | **內部標頭**（不對外）。SPEC §D-6「批 id 與去重」的**檔案系統面**：`current_header`（讀現任 header，讀不到／讀不懂記 `HeaderInvalid` 並視同沒有 header）、`find_rollforward_anchor`（掃 base 所在目錄的兄弟唯一暫存 `<stem>-*.json.temp`、跳過 `<stem>-head-*`、排序後逐一讀，**位元組逐位元等於本輪重算的 canonical 批**的第一個才是錨——身分由內容決定，名字只是索引）、`mark_header_swept`（投遞全清且目錄落盤後把 header 改寫成 `swept:true`，寫不成只記 issue）。**與 `handoff_header.*` 的分工**：那個檔是純字串運算、刻意不碰 fs；這個檔碰 fs 與 `HandoffResult`。不要把這裡的東西塞回去 |
| `handoff_issue.hpp` | **內部標頭**（不對外，header-only）。三個 handoff `.cpp` 共用的兩個小動作：`add_issue`、`sync_directory`（`rename`／`unlink` 之後 fsync 目錄，失敗只記 `DirectorySyncFailed` **不改變控制流**，回傳有沒有真的落盤——彙整用它決定該不該標 swept）。它們同時要碰 `HandoffResult`（公開型別）與 `detail::fsync_dir`（內部標頭），所以放不進 `handoff_fs.hpp`（那個檔刻意不認識 `HandoffResult`） |
| `handoff_deliver.cpp` | **handoff 層的第四個公開動作**：`deliver_instructions`（SPEC §D-3）——三步協定裡唯一由外部生產者執行的那一步，協定細節全部內建：先過唯一 parser 驗整批（壞了就整批拒收、一個檔都不寫）、`write_all` 取 canonical 位元組、收件匣不存在就報錯（不自動建世界）、`next_delivery_name` 取唯一名、`O_EXCL` 建 `.temp`（含 fsync）、`publish_exclusive` 排他 rename（撞名換序號重試，上限 8 次）、`fsync_dir`。目錄 fsync 失敗不算投遞失敗（投遞已在收件匣，缺的只是耐久性），errno 走 `DeliverResult::sync_error` 讓上層警告——謊報失敗會害生產者重投。只依賴 inst＋format，不印訊息 |
| `handoff_header.hpp`／`.cpp` | **內部標頭**（不對外）。handoff 層的批 header sidecar（§C-8 **五**欄位 `version`／`id`／`origin`／`result`／`swept`）與批 id：`derive_header_paths`（只推 `<名字>-head.json`；發布用的暫存是唯一名，不是固定的 `-head.json.temp`）、`BatchDigest`（§D-6 的 64-bit FNV-1a，吃排序後每份投遞的「檔名 `\0` 內容 `\0`」，輸出 16 位 hex）、`encode_header(id, swept)`、`decode_header`→`HeaderFields{id, swept}`。解碼是一個**最小的頂層物件掃描器**（期待 `{`，反覆「字串 key→`:`→值→`,` 或 `}`」；字串跳過跳脫序列，物件／陣列用深度計數跳過且跳過時仍把字串當一個 token），**只採頂層**的 `id` 與 `swept`——巢狀物件／陣列元素／字串值裡的 `"id"` 都不算數（§C-8 的 `result` 欄在 M2 會變成含 id 的物件）。讀不懂＝視同沒有 header（失效方向往「多跑一次」倒）；缺 `swept` 欄＝`false`。純字串運算：不碰檔案系統、不做交接決策，**也不經過格式層**（格式層只管 inst schema，header 不是 inst） |
| `handoff_fs.hpp`／`.cpp` | **內部標頭**（不對外）。handoff 層的路徑推導與低階檔案存取：從 base path 推出 `.runi`／`.tempd`（`HandoffPaths`，**沒有 `.temp` 欄**：彙整不再產生固定槽位）、EINTR-safe 的整檔讀寫（`write_file` 在 close 前 `fsync`；`write_file_exclusive` 同款但用 `O_EXCL` 建檔；`error` 保留**先發生**的 errno，`close` 只在前面沒出錯時才有資格寫）、`fsync_dir`、`publish_exclusive`（排他發布：優先 `renameat2(RENAME_NOREPLACE)`，不支援時退階 `link`＋`unlink`，目的檔已存在一律回 `EEXIST`、不覆蓋；**退階路徑收尾的 `unlink` 失敗回 `true`**，errno 走可選出參 `leftover_error`——目的檔已經連好，謊報失敗會害生產者重投）、`next_unique_token`／`next_delivery_name`（`<pid>-<seq>`，行程內 atomic 計數）、`unique_temp_path`／`unique_bad_path`（把權杖插在最後一個 `.json` **之前**再接狀況字，仍符合 §B-1 文法：`inst.json`→`inst-4711-0.json.temp`）、`parent_directory`、`DirGuard`（`DIR*` 的 RAII，例外穿出去也不洩漏 fd；成功路徑仍顯式 `close()` 並檢查回傳）、投遞檔名判定與 path join。不碰 `HandoffResult`、不做交接決策；`.cpp` 這個檔需要 `_GNU_SOURCE`（`renameat2` 是 GNU 擴充，宣告在 `<cstdio>`），其他 handoff 檔仍用 `_POSIX_C_SOURCE 200809L` |
| `exec.cpp` | **exec 層**：唯一碰 `fork`／`execve`／`waitpid` 的檔。`execute()`：組 `argv`＋`envp`（透過 `spawn_prep`）→ `fork` → 子行程 `setpgid`＋重導向（stderr merge 時在 stdout 設好後 `dup2(1, 2)`）＋`chdir`＋`execve`（`run_child`，全程 async-signal-safe）→ 父行程視 `timeout_ms` 決定直接 `wait_retry` 或 `wait_until` 輪詢；逾時先對整個行程群組送 `SIGTERM`、給 `kTimeoutGraceMs`（2000ms）緩衝，仍不收就 `SIGKILL` 整個群組——打群組是因為忽略 `SIGTERM` 的孫行程才殺得掉。結束後若 `exit_path` 非空就把 exit code 寫進那個檔（close 前 `fsync`——這是崩潰後對帳的證據，S7 fsync 掃尾）；重導向用的 `child_redirect` 只開檔＋`dup2`，內容是子行程寫的，不 fsync（已知豁免） |
| `spawn_prep.hpp`／`.cpp` | **內部標頭**（不對外）。`prepare_spawn()`：在 `fork` 之前把所有會配置記憶體的準備工作做完——合併繼承的環境變數與 `inst.env`（後者覆蓋前者）、組 `envp`、若 `argv[0]` 沒有 `/` 就沿 `PATH`（或 `confstr(_CS_PATH)` 的預設值）逐段找可執行檔。子行程只拿到已經算好的穩定指標 |
| `wait.hpp`／`.cpp` | **內部標頭**。`wait_retry()`：EINTR-safe 的 `waitpid` 包裝。`wait_until()`：用 `CLOCK_MONOTONIC` 算經過時間，指數退避（上限 `kMaxPollMs`＝50ms）輪詢 `waitpid(WNOHANG)` 直到逾時 |

**改 exec 的行為要小心兩件事**：① `fork` 之後、`execve` 之前只能呼叫 async-signal-safe 的操作（細節與理由見 `core/inst/docs/architecture.md`「`fork` 兩側各自要做的工作」）；② 逾時後的 `SIGKILL` 一定要打整個行程群組（`-pid`），不是單一 `pid`。

**這一層有幾處刻意的設計，不要「修」**：PATH 撞到同名目錄時回 exit 126 而不是 127；三處 `kill(-pid, ...)` 的回傳值刻意忽略；`wait_until()` 出錯時直接 return、不 kill 不 reap。外部審查工具會反覆把它們當成 bug 提出來。
