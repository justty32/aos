## 說話方式

2026-09-01 他兩次要求「講人話」「跟我說話請用白話」，並寫進 /goal；之後每次 /goal 都重申。
他的理論功力在構想本身，不在 CS 術語；高密度、多線交叉引用的總結他讀不動，會退回來要重講，等於白寫。
所以：完整句子、一段一個重點；術語第一次出現用日常比喻帶過；編號引用（G 幾、B 幾、進度第幾條）點到為止，別讓他查表。技術深度不用降，是表達方式要降。
2026-11-12 他說「有需要我判斷的可以跳選項給我」：要他判斷的題，直接用選項框問（一框一題、選項寫白話）。

**agent.py → 定義夾一律用編譯的說法（2026-11-19）**：原話「然後以後也用編譯、重新編譯來說，不要再用生、重生這樣」（同日先問過「生成、重生、抄，這都是啥意思。」）。中文（回覆、`wf/`、`docs/`、說明、規範）照下表說，第一次出現可括號帶一句白話；英文訊息用右欄。引號內的原話、舊的 thinking 紀錄不回頭改。

| 不再說 | 改說 | 英文 |
|---|---|---|
| 生成、生出 | 編譯、編出 | compile |
| 重生、重生成 | 重新編譯 | recompile |
| 生成檔 | 編譯產物 | compiled files |
| 抄（編譯時把包裡的東西複製進 json） | 靜態連結 | static (linking) |
| 借（json 只寫去哪拿、執行時才讀） | 動態連結 | dynamic (linking) |

**kernel、daemon 直接叫 kernel／daemon，不用比喻當名字（2026-11-20）**：原話「拜託，手、門只是比喻，幫我乖乖用kernel/daemon稱呼好ㄇ」（同句前面先問「把手放在新檔agent_hooks是啥？」）；頂層接著用選項框問「文件裡現有的比喻用詞要不要派線清掉？」，他選「指 kernel／daemon 的「手」「門」,「把手」改叫「物件」,其他比喻也清」。中文（回覆、`wf/`、`docs/`、說明、規範、程式裡的中文註解）照下表說；上面「術語第一次出現用日常比喻帶過」只是第一次解釋時可以打個比方，比喻不拿來當東西的名字。程式碼、識別字（變數名、檔名、鍵名）不改；引號內的原話、舊的 thinking 紀錄不回頭改。其他比喻詞等他逐個確認後再補進表。

| 不再說 | 改說 | 英文 |
|---|---|---|
| 手、門（指 kernel 或 daemon） | 照實寫 kernel 或 daemon | kernel / daemon |
| 把手（翻 handle） | 遙控器（例：「hook 遙控器」＝拿來發 hook 的那個；「agent 遙控器」＝拿來操作一隻活著的 agent 的那個 `Agent` 類別） | handle |

「把手」怎麼定成「遙控器」的（2026-11-20，原話逐字）：頂層先照選項框寫「物件」，他說「hook物件...這有點像是一個遙控器的感覺？你用"物件"，我會聯想到物件導向。」；頂層再問（遙控器／直接寫英文 handle／維持「把手」／物件），他答「我覺得handle不錯，但又感覺跟常見的函數callback的handler相衝，搞得好像hook會呼叫這個handler一樣。還有其他嗎？感覺這又有點類似hook的操控器？拿到了之後我們可以手動觸發hook這樣？」；頂層第三次問（操控器／遙控器／控制器／先維持「把手」，註明「觸發器」gdb 已拿去指別的東西），他選「操控器」，接著改口「操控器...還是用遙控器吧」。所以中文寫「遙控器」，不寫「物件」（會想到物件導向）、也不寫 handle（會跟 callback 的 handler 混）；程式識別字（`handle`、`agent_hooks`、`hook_handle.py`）照舊。

## 使用者專區的回信也算授權（2026-11-13 晚）

原話（逐字，對使用者專區規劃 05 的 12 題）：「照推薦，第12題就放ws/tools。舊的信箱沒在用，刪掉。先不考慮手機。push/刪檔這塊也算。網頁和看板...先做網頁就好。就先只考慮家裏這臺。」

- U5 照推薦：經使用者專區（`~/.aos/user/`）、用 `aos-user verify` 驗過的回信，算他本人的話。
- U6「push/刪檔這塊也算」：不照推薦（推薦是「先不算」），**連 push、刪檔這類不可逆的也算**。
- 「驗過」＝收信方跑 `aos-user verify <回信資料夾>`：寄件人是專區、內容跟專區 `done/` 留的副本逐欄一樣、專區流水帳有同一筆。**擋得住**轉述（「使用者跟我說可以」）與往別人信箱丟的假回信；**擋不住**會開 shell、刻意連副本與流水帳一起造假的 agent（全部 agent 跟使用者是同一個 Linux 帳號）。做法與限制見 [user-zone-plan 使用者裁定](../../../../proto8/thinking/2026-11/13/user-zone-plan.md#使用者裁定11-13-晚)。

## 不寫自動記憶

2026-09-30 他說 Claude Code 的自動記憶機制是垃圾，`wf/` 才是結構化的記憶與 skills。
所以：**值得跨 session 留下的東西（偏好、規矩、踩過的坑、決定）一律寫進 `wf/` 對應的檔**，照 [STRUCTURE](../../../STRUCTURE.md) 的分層放；不寫進 `~/.claude/projects/…/memory/`。那個資料夾只留一句「去看 wf」。

## 出門／不在時（2026-10-09 定）

他出門只能用手機、也不常看。所以**只在他明說出門／不在的那段期間**，實作層級的決定可以由頂層先做，不停線等他；做錯可以之後改回來。**方向題除外**：照樣寄使用者專區、等他答（見下面「不在時有事要他裁」；鐵律 5）。
出處：10-09 早上那句只留轉述、沒有逐字，見 [decisions-2026-10-09](../../../../archive/proto7-2/notes/decisions-2026-10-09.md)：「出門後大小決策全由頂層先做…做錯可以改回來」。原本這裡寫成「大小決策全部由頂層先自己做」的常設偏好；使用者 11-15「決策鍊改回去」，收窄成上面這樣。
他回來會說「跟我說說這段時間發生了啥、你做了哪些大決定」——這時用白話報告：發生了什麼、我替他做了哪些決定（附翻案位置）。
因此不在時要**隨手記一份代定清單**（記在 `wf/progress.json` 對應的條目或該輪的筆記裡），報告時照它講。
