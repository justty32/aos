# team-model — 誰來做：角色三層、聰明度分級、選人判準

← [WORKFLOWS](../WORKFLOWS.md)｜[INDEX](../INDEX.md)

本檔記**誰來做**——分幾層角色、每層派哪一級的模型、按什麼順序選人（分級與速度是使用者定的、跨專案共通，源頭是 `~/repo/moddings/skyrim/agentctl/docs/team-model.md`，兩邊要一起改）。**怎麼做**在別處：切線與交接書見 [dispatch](dispatch/README.md)（含本專案的隊形與 codex 呼叫），資源鎖見 [resources](resources.md)，通訊見 [inbox/PROTOCOL](inbox/PROTOCOL.md)。

**何時用**：要開一個 agent 團隊、要決定某一層派哪級模型、要按用途分角色。
**何時不用**：只有一條線、一兩個檔的小改（見 [dispatch](dispatch/README.md) 的「何時不用」）；只是要送一則情報 → [inbox](inbox/README.md)。

## Done when

- 下方分級表與消耗速度表已按**你自己的模型清單**填完。
- 這一輪要開的每一層都**指名了誰**——頂層、領導、工人各自是哪一格。

## 一、角色三層

### 頂層 agent（使用者直接面對的那一個）

職責四件：接收指令、開 agent 團隊、傳達指令、**協調使用者自己也會用到的資源**（鍵盤滑鼠螢幕，乃至 CPU、硬碟、網路）。**資源授權的源頭是使用者**——頂層只是代為分配，**不能自己創造授權**。

模型：**通常 Opus 就夠了**——頂層只是轉達與調度，某些情況下 Sonnet 也可以；skyrim 那邊 2026-08-30 已由 Fable 降回 Opus。aos 目前這條 session 由 Fable 當頂層是歷史原因，**只派隊、不親做內容**（鐵律 5：方向性的留給使用者）。頂層**比領導笨是正常的**：計畫不在頂層做。

對使用者說話要**適合使用者理解**：初次出現的東西先用白話講一句。**預設不必翻譯**；只有使用者說今天不想動腦才逐項翻，翻譯本身吃太多 context 時，改成直接指出**該先看哪些檔**（[digest](digest/README.md) 工作流就是做這件事）。

頂層通常可以有**自己的私人輔助者**（查資料、盤點），不必事事經過領導。輔助者**不算團隊 headcount**，數量由使用者指定，**沒指定就默認兩個**。

平時**不掛信箱醒鐘**、不逐則讀信——那是領導的事。**例外**：團隊裡有外部 agent 要直接找頂層時，頂層也要盯自己的信箱（見第七節）。

### 團隊領導（＝計畫制定者）

職責：把目標拆成計畫、寫交接書、派工、監看、核驗、收線。本專案的隊長是 **Opus**：寫任務書、審 diff、跑 ctest、commit。

模型：**依任務難度是 Fable 或 Opus**。負擔重（計畫＋指揮＋匯報），所以 **Opus 是最低標準**；**若「制定計畫」被分出去給某個成員，領導只剩指揮與匯報，Sonnet 也可以。**

**通常不建議 gpt-sol 當領導**：那是另一套 agent 體系，即使有 inbox，和頂層溝通仍然有成本。

兩條實務提醒：交接書的**範圍詞會被線遞移展開**，範圍要用排除法寫死、**件數 gate 與容量 gate 並列**（見 [dispatch](dispatch/README.md)）；領導自己 context 吃緊時**寫 state 檔交棒**，不硬撐。

### 工人

依任務難度／內容，加上**使用者給的 headcount**，開不同聰明程度的 agent。gpt-sol、gpt-terra、gpt-luna 這類便宜 AI **通常在這層大量使用**；本專案的隊員是 **codex CLI 的 `gpt-5.6-sol`**（2026-08-28 改制，不再開 Opus／Sonnet 隊員），工人**不 commit**。gpt-sol 自己再開 terra／luna **我們管不著**——它在那一層就是領導，這不算「領導不建議 gpt-sol」的例外；我們只告訴它**那邊能用多少資源**，頂多建議它開兩三個當助手。

## 二、聰明度分級（總分）

**這是使用者定的總分**（2026-08-30，原話「我這邊定下來的是總分，之後我們慢慢會有更詳細的分類分級」），所以留一欄給用途細分。分級以 **Claude 的收費與聰明度為基準**，往下補級很正常。

| 級 | 誰 | 用途細分 |
|---|---|---|
| S | Fable | 目前唯一一個 S；細分待補 |
| A | Opus | **軟體工程層面**；其餘用途見 B 列 |
| A | gpt-sol（codex `gpt-5.6-sol`）| 各方面；**軟體工程算 B+** |
| B | Opus | 軟體工程之外 |
| C | gpt-terra、Sonnet | 待細分 |
| D | gpt-luna | 待細分 |
| E、F… | （預留）| 之後 DeepSeek 之類可以更低 |

新增用途欄（調查、寫作、實機操作…）時**只加欄、不改既有級別**——級別是使用者定的。

## 三、token 消耗速度

兩條規則：

- **Claude 系列**：消耗速度基本**與聰明度成正比**（越聰明越貴）。
- **GPT 系列**：整體**往下移兩級**。

重點是推導出來的那一格：**「聰明度高、消耗速度低」的那一格就是性價比之神，工人層大量用它。**

| 模型 | 聰明度 | 消耗速度 | 結論 |
|---|---|---|---|
| gpt-sol | A | C（A 下移兩級）| **性價比之神；工人層主力** |
| gpt-terra、gpt-luna | C／D | E／F（同規則下移兩級）| 便宜到掉出 Claude 的表 |
| Fable／Opus／Sonnet | 見上表 | 與聰明度同級 | — |

## 四、選人判準（按序看這六項）

1. **任務難度／內容**——決定聰明度下限。
2. **使用者給的 headcount**——外生的上限，**不自己加碼**。
3. **token 消耗速度**——所以工人層大量用便宜模型，貴的留給真的需要的那幾件。
4. **溝通方便與否**——跨體系（GPT ↔ Claude）即使有 inbox 仍有成本，所以**領導層不建議 gpt-sol**。
5. **管理上限**——**開太多領導不好管**；寧可少開領導、把量壓在工人層。
6. **時程**——用「產出速度 × 繞圈數 × 模型癖好」反推每段派誰、排多久，算法見 [speed](team-model/speed.md)。

## 五、方案與時間軸

隨帳單與錢包變動，替代表與連帶效果拆到 [plans](team-model/plans.md)。現況（2026-08-30）：Claude 與 GPT 各買一個月 200 美元方案，**大約 9 月初退掉 GPT**；屆時工人層的 gpt-sol／terra／luna 消失，便宜的活改 Sonnet、A 級的活改 Opus，整體會更貴，到時再重新規劃。

## 六、context 管理

每層管自己下級的 context——管得好就是清雜訊，直接提升決策品質。五條規則見 [context](team-model/context.md)。

## 七、信箱——每個角色一格

角色分層之後通訊也跟著分層：每個 agent 一格，開團隊再配團隊一格（本專案同機的隊用子 agent 通道，跨資料夾才走 inbox）。

- **頂層**平時不掛醒鐘；只有 `NEEDS-USER`、`FAILED`、領導的 `DONE`、資源／鎖請求該吵醒它。
- **領導**對自己團隊送來的 STATUS **全醒**；上呈時重寫標題、帶自己的判斷，不是原文轉貼。
- **工人**沒有醒鐘，**每完成一個工作步驟輪詢一次**，延遲上限就是一個工作步驟。

誰醒誰不醒以 [inbox/wake-policy](inbox/wake-policy.md) 為準。
