### 三、哪條路最值得繼續走

**第一：「批次的執行進度已經寫在檔案系統上，只是沒人讀」。** 不需要新檔案、新協定、新控制平面。兩個提案是同一條路的兩半：

- `"needs": "<exit 檔>"`：前一筆的 exit 檔不存在或非 0 就跳過這一筆。可以先用 `bin/gate` 在不改 C++ 的前提下模擬證明，再決定要不要進 C++。
- fork 前的 running marker：補上 `exit` 檔補不了的那一半。

**第二：靠 id 復原。** `codex exec resume <thread_id>` 能原封不動拿回被砍那輪的答案，`thread_id` 在 JSONL 第一行、早於答案。本機證據會被重播抹掉，provider 端的不會；journal 一個 id，最壞情況從「再付一次錢」變成「再查一次帳」。

---

### 四、哪條路看起來好、但有隱藏成本

- **`aos exec --resume`（跳過 exit 檔存在且為 0 的那幾筆）**：exit 檔在 parent `wait` 完才寫，崩潰時缺的正是已計費那一筆，`--resume` 會精準重跑最貴的那一站。值得做，但不能當省錢方案；省錢要靠租約或 id 對帳。
- **「三支 CLI 都通了，golden slice 挑一支就好」**：三支都是 agent 不是模型端點，會自己用 shell 讀檔。沒把模型 cwd 指到空資料夾的量測，量到的有一部分是 CLI 的能力，不是這條 loop 的能力。`aos llms`（OpenAI 相容端點，已存在）沒人測，是本輪最大的集體盲點。
- **`--output-schema` 讓 parser 消失**：它是 codex 專屬旗標，拿它當「解析不是問題」的證據等於把 golden slice 綁在一家廠商上；而且只讓去程有型別，回程仍是純文字。
