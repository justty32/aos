以下四條四位都撞到。

**`aos exec` 被砍掉之後，模型 CLI 不會死，它變成孤兒繼續跑、繼續花錢。** 子行程 `setpgid` 自成 process group（規格第十二節〈已經被實作決定的〉），信號打不到它。孤兒會跑完、寫出結果，甚至投遞下一批（`.aos/inst.tempd/` 出現新投遞）；但 parent 已死、沒人 `wait`，所以 `exit` 檔不會寫（`model.exit` 缺、`phase.called` 卻在），`.runi` 留著，下一次 `aos exec` 回 3：

```
aos exec: refusing w1: .aos/inst.json.runi already exists
exit=3
```

結果是 `.runi` 說「有一回合沒跑完，人來處理」，而那回合其實完整跑完、還推進了 loop。SIGINT 與 SIGKILL 都一樣。

**人工恢復 `mv .runi inst.json` 在有真模型的 batch 裡等於重新付一次錢。** 重播會再呼叫一次模型：兩個不同的 `thread_id`，同一個模型回合計費兩次（p1 量到共 31,316 input token、`total_model_calls=4` 做 3 次的事），而第一次的結果一直在 `raw.txt` 裡。手上沒有任何安全的恢復動作。

**`stdout` 的截斷語意會把上一次的證據抹掉。** `stdout`／`exit` 是「必要時建立並截斷」，重播時第一次的 `thread.started` 與 `usage` 被清掉，從世界裡再也看不出被收了兩次錢；空輸出的回合也分不出「沒輸出」與「沒跑」。中間檔都只留最後一回合：

| 檔案 | 出現 | 消失 |
|---|---|---|
| `inst.tempd/<pid>-<n>.json.temp` | 投遞開始 | 同一瞬間 rename 掉 |
| `inst.tempd/<pid>-<n>.json` | 投遞完成 | 下一次 exec 的 aggregate |
| `inst.json` | aggregate 發布 | 同一次 exec 的 claim（外面看不到） |
| `inst.json.runi` | claim | 回合結束 release（外面看不到，除非 crash） |
| `state/tool.out/.err/.exit` | 工具回合 | 永不消失，每回合被覆寫 |
| `state/model.raw` | 模型回合 | 永不消失，每回合被覆寫 |

整條 loop 的歷史只在 `transcript.jsonl`。要留現場就自己 `cp` 快照。

**「下一批要跑什麼」的 instruction JSON 字面值要抄 2–3 次**（seed／bootstrap、決策、投遞後各一份，有時是兩種語言：shell heredoc 加 Python dict literal）。`$ref` 拼不了 batch，沒有第二種寫法。
