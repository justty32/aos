- **F（鎖可被批次打開）打到的那句話**：`docs/aos-folder.md`〈六、交接協定〉——「所以這個不變式成立：> **`.runi` 存在 ⟺ 有一回合沒跑完。**」以及緊接的「**`.runi` 已存在時拒絕啟動**（退出碼 3）……也不會有兩支 `aos exec` 同時跑同一個資料夾」。決策版在 `docs/roadmap/decisions.md`〈D6 — `.runi` 存在時代表什麼？　**已定：拒絕啟動**〉，用字相同。

- **同一件事已經在別場被獨立記成規格級發現**：`wf/workflows/hackathon/records/agent-loop.md`〈規格級的發現／一〉（退出 3 之前 inbox 已被搬空）與〈二、`.runi` ＋ `mv` 的恢復路徑會靜默吃掉一份已經完成的產出〉——後者把四步串完：孤兒完成回合並投遞 → 人跑 `aos exec` 回 3 但產出被搬進 `inst.json` → 人照文件 `mv .runi inst.json` → **產出被靜默刪除、退出 0** → 再跑一次重播那個模型呼叫。**這正是 A3 的真模型版本。**
- **`aos recover` 的介面已經被寫出來過**：`wf/workflows/experiments/t5-agent-loop/subcommand-specs.md`〈`aos recover [WORLD]`〉——命令不能假裝有 program counter，應先**唯讀列出** `.runi`、每筆 exit/result 證據與可能仍活著的未知子行程，動作分成 `--replay`／`--abandon`／`--adopt RECEIPT`，並明寫「**沒有足夠證據時預設必須停住，而不是自動重播**」。
- **A4（退出碼 3 一碼兩義）對到的條文**：`docs/aos-folder.md`〈八、退出碼〉四碼表（`3 = 拒絕啟動：.runi 已存在`）與〈十二／已經被實作決定的〉的「**只有退出碼 3（`.runi` 已存在）會讓迴圈退出**」；決策版在 `docs/roadmap/decisions.md`〈D10 — 回合的退出碼怎麼算？〉。`wf/workflows/common/gotchas.md`〈使用 aos〉已經記過「`aos exec` 的退出碼不反映子行程成敗」這一半。
- **「`.runi` 存在時 inbox 不得被消耗」在測試檔裡的相鄰行為**：`core/inst/tests/test_run_handoff.cpp` 的 `TEST_CASE("exec leaves deliveries pending while inst.json already exists")`（第 78 行）與 `TEST_CASE("exec refuses an existing runi with status three")`（第 97 行）——**前者測的是 `inst.json` 存在，不是 `.runi` 存在**。這兩個測試之間就是那個缺口。
- **差分測試要比對的那份 canonical parser 行為**：`core/inst/tests/test_format_read.cpp` 的 `read_all accepts a single instruction object`（第 25 行）、`read_all accepts a formatted array of instruction objects`（第 48 行）、`read_all accepts an empty array and rejects an empty document`（第 66 行）、`read_all is atomic and reports a one-based record number`（第 83 行）、`read_all reports a non-object array element`（第 107 行）；宣告在 `core/inst/include/aos/inst.hpp`，文件在 `core/inst/docs/cxxapi.md`〈函式〉。
- **FFI 那條路今天的真實狀態（比 p3 坑 6 的結論更精確）**：`core/inst/include/aos/inst.h` 的公開 C ABI 只有單筆 instruction 的 `aos_instruction_read_buffer`／`read_fd`／`read_file`／`write_*`／`execute`，**沒有 `read_all`、沒有任何 handoff 入口**（`aggregate`／`claim`／`release` 一個都沒有）；`core/inst/docs/capi.md`〈讀取、寫入與執行〉明寫三個 read 入口只接受單筆 object。**但 mangled 符號那條路有人走通過**，見 `wf/workflows/hackathon/records/deliver-contract.md`〈第 2 輪紀錄／1. 各人做了什麼〉的 Hickey persona 段落與〈第 2 輪紀錄／3. 好處／壞處／壞處〉：他用 ABI-local `ctypes` 直接呼叫 `libaos_inst.so` 的 `aos::read_all()`，依賴 `libstdc++ vector layout = 24 bytes`、`sizeof(aos::inst_t) = 280`、固定 mangled symbol 與短命 process，明確標為「證據 shim，不是產品 FFI」。**同一份紀錄的〈第 2 輪／5. 仍然不知道的〉也記了同一個 C ABI batch 缺口**，`wf/workflows/hackathon/records/core-scope/rounds/round-3.md`〈6. 仍然不知道的〉第三段同樣確認 `read_all()` 沒有 C ABI。
