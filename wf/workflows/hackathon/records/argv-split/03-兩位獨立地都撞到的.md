#### 兩位獨立地都撞到的

**（八）影子世界會打壞規格第四節的相對路徑基準。**p2（情境 2）與 p4（坑 1）兩位獨立地實測到檔案落在錯的地方：

```
（p2）指令：[{"argv":["/bin/sh","-c","pwd > out.txt"]}]
甲 aos exec        → out.txt: .../lab/sc-pathA/out.txt          內容: .../lab/sc-pathA
乙 exec-split      → out.txt: .../lab/sc-pathB/.aos/cpu.d/out.txt   內容: .../lab/sc-pathB/.aos/cpu.d

（p4）--- world B ---
B/.cpu/e1.txt          <<< 規格第四節說相對路徑以 <folder> 為基準，這裡跑到 .cpu 去了
B/.cpu/e2.txt
B/out.txt              <<< 只有寫絕對路徑的那筆落對地方
```

p4 把它接回研討會問而沒人答的那題：「架構師問『helper 的 `cwd` 誰保證』——答案是**沒人**。」p2 的講法是：「這**不是我懶**，今天的 `aos exec` 沒有任何辦法被叫成『只執行這一批、交接我自己來』。要做乙就一定要有個影子世界，就一定會動到 cwd 基準。**『拆四支』這件事在今天的二進位上根本不可表達。**」p3 是預見了這個問題才放棄那條路（見坑一）；p1 沒撞到，因為他的乙案執行那一步是自己的驅動器做的。

**（九）SIGINT 對背景 job 是被忽略的。**p3（坑 3）與 p4（坑 4）兩位獨立地撞到，處置不同。p3 查出原因——**非互動 shell 會把背景 job 的 SIGINT／SIGQUIT 設成 `SIG_IGN`**，訊號根本沒送到——改用 `subprocess` 直接起（`lab/E_sigint.py`）之後得到正確結果 `rc=-2`，並且**兩版腳本都留著沒刪**。p4 量到同一件事的證據（`/proc/<pid>/status` 的 `SigIgn: 0000000000000006`，bit 2 = SIGINT、bit 3 = SIGQUIT）但沒有繞過去：「任務書要求『`SIGINT` 都試』，**我沒做到**，要在能給前景終端機的環境裡才測得到。KILL 與 TERM 的資料是有效的。」

#### 一位撞到、但值得單獨記的

- **`/bin/sleep` 自己就是一次 fork**（p2，坑五）。用 shell 寫輪詢迴圈的話，光是睡覺就讓「零 fork 閒置」永遠不可能。他用 bash 內建的 `read -t` 配一個沒人寫的 fifo 才做到。「這件事對『用 shell 寫 core helper』是個真警告。」
- **`set -e` 吃掉退出碼 3**（p3，坑 10）。A1 第一次跑到 `aos exec` 回 3 就整個腳本結束，執行後的狀態根本沒印出來——「而那正是全場最重要的一組證據。這個題目裡『非零退出碼是正常結果』，`set -e` 不能用。」
- **`zsh` 的 `&&` 鏈把 `pkill` 回 1 當成失敗**（p1，坑 8），整串靜靜中斷，只印了標題就結束。之後所有時序敏感的東西都改寫成獨立的 bash 腳本。p3（坑 9）撞到同一個殼的另一面：`find` 被 alias 成 `bfs`、`ls` 有一次讓整個 bash 呼叫卡到逾時，全部改用 `/usr/bin/find` 絕對路徑。p2（坑九）也記了一次 `ls -la` 掛兩分鐘。
- **`handoff_tool.c` 第一版直接 segfault，退出碼 139**（p1，坑 4）。`char acc[4096][4096]` 是 16 MB 開在 stack 上，改成 `static` 就好。「貼出來是因為它是我唯一一次『以為做完了但根本沒跑起來』。」
- **並行測試的歸因差點做錯**（p1，坑 9）。第一眼看到 23/30 就想寫「claim 有 race」，做了「事先彙整好」的對照（0/30）才確定是 aggregate。「如果沒做那個對照，這份回報會指控錯一支程式。」
- **影子世界自己會洩漏相位**（p2，坑六）。`.aos/cpu.d/` 底下 `aos` 會做它自己的一套交接，於是「批次寫進去了沒」「aos claim 了沒」「aos release 了沒」本身就是三個相位標記，讓天真版看起來好像分得出來。他用 `SNAP_EXCLUDE` 排掉，但另外記了一筆：「**任何真的 CPU 都得被『告知』要跑什麼，而『被告知過』本身就會在磁碟上留痕跡。**研討會假設 CPU 不留痕跡，那個假設在真的實作裡不成立。」
- **在單體裡 race 不到「取件完就死」**（p2，坑二）。`claim_instruction()` 返回到 `execute_batch()` 第一次 fork 之間只有幾十微秒，隨機延遲打不中；想用超大批次拖長 parse 時間開窗口，但那會改變 `.runi` 內容就沒法逐位元比對。最後**手工做一次 `mv`**，並在腳本註解與回報裡照實標明「這是構造出來的現場，不是殺出來的」。p3 用 gdb 斷點解掉了同一個問題（K1 停在第一次 `fork`）。
- **相位標記的順序第一版寫錯**（p2，坑七）。`claimed` 寫在 claim 之後，開了一個「`.runi` 在、標記不在」的窗口。「是我自己盯著想才發現的，不是測出來的（那個窗口一樣是微秒級，我一樣 race 不到）。**所以這條我只有推理，沒有實測。**」他從中收出一條規則：「**『給重跑許可』的標記寫在危險動作之前，『收回許可』的標記寫在之後。**這樣每一個模糊窗口裡都沒有子行程在跑，猜錯永遠往保守的方向錯。」p3 獨立踩到同一類的東西（坑 11）：`aos-release2` 一開始寫成先清 sidecar 再 unlink `.runi`，那會製造「有 `.runi`、沒有 receipt」的不可判定現場——「孤兒 sidecar 無害，孤兒 `.runi` 有害。」
- **gdb 第一次跑忘了重建世界**（p3，坑 1 後半）。`inst.json` 已被前一輪消耗掉，三個情境全都印 0 fork，「我當場以為驗收條件普遍成立，回頭才發現是世界空了。」
- **`.temp` 檔名共用**（p1）。規格第六節自己說投遞要帶 pid「因為 `rename` 原子但寫入不是」，但彙整那一步用的是固定的 `inst.json.temp`。「行程內時只有一個彙整者所以看不到，外放（或多推進者）之後這是個現成的資料損毀來源。我的實作照抄了這個錯。」
