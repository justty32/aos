#### 六個壞

| 條目 | 裁決 | 依據 |
|---|---|---|
| **壞 1(a)**：三種死法在磁碟上長得一模一樣 | **證實了**（四位獨立，四種殺法、四種快照工具） | p1 `e24be31a…`／p2 六個現場三個 diff 零差異＋時間戳也救不了（mtime 是批次寫下的時刻、ctime 是 rename 的時刻，**兩個都在回合開始前就凍住**）／p3 gdb K1–K3 `f92bcff0…`／p4 `0a4278ce…`。承重最硬的是 p3 的 gdb（不靠 race 打得中）與 p2 的時間戳分析。 |
| **壞 1(b)**：「成立的唯一理由是同一個行程」 | **真的推翻了** | 測的就是原命題（因果），結果相反。**p1 的 P/Q 對照**：完全沒外放、就是現有二進位、**逐位元相同的批次**，一個 `kill -9`（rc=137）一個 `unlink` 吃 EACCES（rc=1），`.runi` 都是 `a697f32d…`。**p3 的實驗 F**：批次裡一行 `rm .aos/inst.json.runi`，`trace.txt` 時間序 `BATCH-A step1 → BATCH-B running → BATCH-A step2` 證明兩批同時在跑。（p2 的 M1 是手工 `mv` 構造的，他標明了，所以這條的承重不放在他身上。）**結論：「同一個行程」買到的是偵測，從來沒買到診斷。** |
| **壞 1(c)**：一旦釋放外放就分不出來 | **真的推翻了**（三個獨立做法） | p1（`flock`＋journal）、p2（相位標記三次 `rename`＋`flock` 租約，碼 4/5/6，`SIGKILL` 與 `SIGINT` 都試）、p3（write-ahead sidecar，碼 11/12/13，唯讀 `aos-recover` 三次判對，讀今天的現場 → `UNCLASSIFIABLE` rc=1）。**測的就是原命題**：原命題主張「外放之後不可能有磁碟上的判別」，三個反例各自在 claim 與 release 分屬不同行程的前提下做出判別。成立。 |
| **壞 1：p4 的分歧**（只推翻 1/3；(b)(c) 分不出來是因為孤兒把整批跑完了） | **這一格是換了命題的假推翻，但它換出了一個真發現** | **等一下，這裡有兩個不同的東西。** p4 殺的是驅動器，執行器活下來把整批跑完了——所以他的「(b) 跑到一半死」**根本沒有被製造出來**，他的 b 與 c 是**同一個世界狀態**。同一個狀態當然分不出來，那不是可分辨性的結果。他的輸出自己說了：`b) 2/2 reported exit, executor released cleanly` / `c) 2/2 reported exit, executor released cleanly`。**但他順手抓到的東西是真的、而且研討會沒說過**：鎖的壽命跟工作的壽命脫鉤了（單體對照組 `exitfiles=1/2`，工作真的停了）。至於他說這件事「沒有便宜的解」——**被 p2 同一輪的 `lease-demo.sh` 推翻**：孤兒跑完之後核心自動放掉租約，判定翻成 `DEAD_MID_BATCH`，沒有任何收尾程式碼跑過。 |
| **壞 1：p4 的「取件完就死不需要新格式就分得出來」** | **證據不足** | 他靠 exit 檔數 = 0 判別，判對三次。但 p2 的坑六證明影子世界自己會洩漏相位，而 p4 的 exit 檔（`e1.txt`／`e2.txt`）依他自己的輸出是落在 `B/.cpu/` 裡的。**他可能在讀鷹架的痕跡。** 原理（exit 欄位本來就是進度游標）是合理的、也便宜，但這一格要重測。 |
| **壞 2**：退出碼 3 退化成某一筆的 exit，`--loop` 失去唯一停止條件 | **形狀 (b) 證實了；普遍性真的推翻了** | 證實：p2 情境 3 端到端輸出——那一筆 `aos-claim` 自己回 3、**回合退出碼 = 0**。推翻普遍性：p3 在 (a) 形狀下 `p3-exec --loop rc=3`，並排真 `aos exec --loop rc=3`。**但要記一筆**：(a) 之下 3 被保留是 p3 的 driver 的一個設計決定，不是形狀的性質——所以〈壞 2〉的真實內容沒有消失，它變形成 p1 那條「12 個整數沒有人管」。 |
| **壞 2：p4 的新路徑**（照閘門原話字面實作會弄丟 3） | **真的（新發現，不是推翻）** | `AOS_GATE=1 → EXIT=10`／`AOS_GATE=0 → EXIT=3`。資深工程師的原話只 stat `inst.json` 與 `inst.tempd`，沒 stat `.runi`。**那句話要進規格（轉交提案第 4 條）必須補一個檔名。** 便宜、確定、該收。 |
| **壞 3**：契約從編譯期型別搬到執行期退出碼與檔名 | **證實了，而且下限比研討會講的低** | p2 的端到端三段輸出：外部 jq 彙整器 rc=0 放行拼錯 key 的投遞 → `aos exec` 執行期 rc=1 → **規格第六節規定 `.runi` 照刪** → 那批消失，連 `.bad` 都沒有；C++ 版會隔離成 `1.json.bad` 留在原地。我去讀了規格第六節，那句「整批 JSON 解析失敗也算回合正常返回，`.runi` 一樣刪掉……那批壞內容就此消失」**確實在那裡**。所以這不是「半夜卡住」，是資料蒸發。 |
| **壞 4**：`aos aggregate` 這種字串會變成 `.aos` 磁碟格式的一部分 | **證據不足**（無人測）＋**已知只在形狀 (b) 成立**（分析，非實驗） | p3 的形狀論述是對的但它是分析不是實驗：在 (a) 裡程式名寫在 driver 或角色表裡，`<folder>` 一個字都沒多。**這條要等角色表（提案 7）拍板才有東西可測。** |
| **壞 5**：最常走的路徑變成最貴的路徑 | **方向證實了；量級兩頭都錯；「至少多一次 fork」真的推翻了——但推翻的代價是外放的定義被改小了** | 方向：四位一致。量級：分子高估（真值見下節），分母根本沒人量過（6–9 µs，不是毫秒級），兩個錯**互相抵銷**成一個看起來差不多的結論——p3 與 p4 都獨立指出了這件事。零 fork：p2 `/proc/stat` 交錯基準線（37 vs 32/53/77/34）與 p3 兩把獨立儀器（gdb catchpoint 0 命中；`ns_last_pid` 0.01/回合）是最硬的兩組。**但三個零 fork 的做法都是靠「把偵測留在裡面」達成的**，三位也都誠實標了。所以字面的「至少多一次 fork」推翻成立，而「exec 什麼都不知道還能零 fork」**沒有人做到，也沒有人宣稱做到**。 |
| **壞 6**：可呼叫的東西就會被呼叫，然後人把自己弄壞 | **證據不足**（機制被順手演出來了，傷害沒測） | p2、p3 明寫沒碰。但 p2 情境 3 其實正是〈壞 6〉的現場：手打一次 claim，世界卡在退出碼 3，**而今天沒有任何一支指令能救他**。機制成立，代價未量。 |
