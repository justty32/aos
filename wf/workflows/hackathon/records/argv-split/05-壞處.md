#### 壞處

- **換一支不驗 schema 的彙整器，代價是整批資料無聲蒸發。**（p2 實測）同一份拼錯 key（`"stdou"`）的投遞走兩條路：

  ```
  --- 外部 aos-aggregate（jq 版）---
    rc=0    發布出來的 inst.json：[{"argv":["/bin/true"],"stdou":"x.txt"}]
  --- C++ 的 aggregate_instructions()（走 aos exec）---
  aos exec: warning: .aos/inst.tempd/1.json: UnknownKey
    aos exec rc=0        投遞匣現在是：1.json.bad          <- 隔離、留在原地給人看
  --- 那份被放行的批次，最後撞到誰？---
  aos exec: .aos/inst.json.runi: record 1: UnknownKey
    aos exec 在拿到那批之後 rc=1
    .aos 現在是：inst.tempd version                        <- .runi 沒了，那批消失了
  ```

  規格第六節：「整批 JSON 解析失敗也算回合正常返回，`.runi` 一樣刪掉……那批壞內容就此消失」。**連 `.bad` 都沒有。**
- **退出碼是一個沒有主人的協定。**（p1、p2）規格第八節只規定 `aos exec` 的退出碼，外放程式該回什麼沒人規定（p1 自編 0 做了事／10 沒事做／3 Busy／1 錯誤）。今天這些狀態是 `HandoffState` enum、編譯器管；外放後變成 12 個沒人管的整數。規格說「退出碼只給跑 `aos exec` 的那個人看」，但 `--loop`、agent loop、cron 底下那個人不存在。
- **python 寫的外放工具會讓毫秒級輪詢失效。**（p1）10.64 ms/回合，回合率約 94/s，`--loop 1` 要 944/s。誰都能寫一支，回合頻率就由最慢的那支決定、沒人在守。
- **「零 fork 的閒置閘門」與「彙整政策完全外包」衝突。**（p4）閘門必須知道「何時該叫彙整」，那就是彙整的觸發條件；彙整若想按 mtime 攢批、定時、按配額，閘門就會判錯。要判斷「沒事做」，exec 就得懂幾乎整份 `.aos` 規格。三種處置：p1 `mtimeguard`（觸發路徑改由設定餵入）、p2「偵測留在裡面、政策外放」、p3 承認「**閒置快速路徑本身就是一條寫死在核心裡的政策。**」（裁決：觸發判準不能完全外放，見〈好 3〉裁決。）
- **乙讓鎖活得比工作久——外放製造的新狀態。**（p4）殺掉驅動器，孤兒執行器把整批跑完、副作用全上磁碟，世界永遠鎖著、沒有活著的行程知道。單體到不了這個狀態。（解法：核心持有的 `flock` 租約，見〈壞 1〉裁決。）
- **`aos` 執行檔對「當機制用」太胖。**（p2、p3）每次 `execve` 0.79–0.877 ms，大半是映射與重定位 42 MB 的 `.so`，含跟交接無關的 32 MB `libaos_llms`；`/bin/sh` 只要 0.437 ms：

  ```
  $ LD_DEBUG=statistics ./build/bin/aos 2>&1 >/dev/null | head -8
    total startup time in dynamic loader: 516041 cycles
              time needed for relocation: 412913 cycles (80.0%)
                   number of relocations: 4793
  $ LD_DEBUG=statistics /bin/true 2>&1 >/dev/null | head -8
    total startup time in dynamic loader: 39954 cycles
  minor_faults: /bin/true 228   aos 519
  ```
- **`.runi` 是只有一個位元的錯誤回報。**（p2）三種需要不同處置的狀況（可無損重跑／絕不能重跑／只要刪檔）塌成同一個檔名；`unlink` 的 `EACCES` 印出來回 1，磁碟上什麼都沒留。看到 `.runi` 的人不知道那批跑了沒，只能賭。
- **兩個 `.aos` 在同一個世界裡。**（p4）執行器是獨立行程就需要自己的世界，「一個資料夾＝一個世界」不再成立。
- **`flock` 的 fd 繼承是地雷，`flock` 在 NFS 上不可靠。**（p1）批次裡有 daemon 化的長命子行程就會永久握住鎖。要做對必須在 fork 之後 exec 之前關掉那個 fd（`FD_CLOEXEC`）。
- **規格第六節「所以這個不變式成立：`.runi` 存在 ⟺ 有一回合沒跑完」是沒有證明的斷言**（p3），整場研討會架在上面；批次裡一個 `rm` 就打掉它。
