## 第 1 輪紀錄

### 1. 各人做了什麼

**Carmack persona 這一路**先量再讀。第一件事是寫一支 `spawn_bench.c` 把「fork＋execve 約 1–3ms」量掉；第二件事是在沒有 `strace` 的情況下，用 `/proc/<pid>/io` 的 `rchar` 當回合計數器（空回合固定讀 `.aos/version` 2 bytes，`Δrchar / 2 == 回合數`），量出真 `aos exec --loop` 一個空回合的成本；第三件事是把四支機制真的寫成獨立的 argv 程式，**C／sh／python 各一套**（`handoff_tool.c` 用 busybox 式 hardlink 分派，語意照 `handoff.cpp` 抄），配一支五模式的回合驅動器 `split_driver.c`，把甲案、乙案，加上他自己另外加的兩個「守門」變體（`guarded`、`mtimeguard`）放在同一支尺上量。量完拿同一套工具去打主張二的殺行程實驗，最後在主張三撞到一個規格層級的錯誤——**16 個並行的真 `aos exec` 會把同一批指令執行兩次**。三個主張都碰到了。東西在 `p1/lab/`（`bench/` 量測、`bin/` 工具、`worlds/` 每個實驗的現場、`out/` 快照與 diff）。

**Cantrill persona 這一路**先去把〈壞 1〉那句「三種死法長得一模一樣」真的殺出來——第一刀就砍到自己人：**今天這顆單體 `aos` 就已經分不出來了**。接著把四支全外放成 POSIX sh（`hack/bin/aos-{deliver,aggregate,claim,release}`），在天真版上重現三個現場零差異，然後做了一個**會分**的版本（mode c）：`inst.json.runi.claimed` → `.running` → `.ran` 的相位標記（每次轉換一個 `rename(2)`）＋一份由整棵行程樹持有的 `flock` 租約。三種死法各自不同，而且他寫得出一支 `aos-world-recover` 對每一種做**不同的**處置。順路量了 1–3ms、數了真實的 fork 次數（讀 `/proc/stat` 的 `processes` 欄，基準線與案例交錯量），並證明「零工作的回合必須是零 fork」在外放的設計裡做得到。東西在 `p2/hack/`（`bin/` 14 支腳本、`bench/`、`lab/`、`out/`，`NOTES.md` 記跑法）。

**Lamport persona 這一路**先問「這條不變式到底在保證什麼」，把 `.runi` 的三種可能讀法寫成三條可否證的命題（`L-batch` 那一批／`L-slot` 那個檔位／`L-world` 那個世界），再設計實驗去分辨**現在這顆 binary 實際上滿足哪一條**——不是文件說哪一條。答案是：規格第六節的散文預設 `L-world`，實作給的是 `L-slot`，而且連 `L-slot` 都沒守住。然後用 **gdb 斷點**在三個精確位置各殺一次（K1 停在第一次 `fork`、K2 停在第二次 `fork`、K3 斷在 `aos::release_instruction` 入口），確認今天就分不出來；做出四支全外放的 `kit/p3-exec`（144 行、真正做事的 `turn()` 只有 40 行），確認它產生**逐位元相同**的三個現場；再加一層 write-ahead 紀錄讓三者變成可判定，寫了一支唯讀的 `aos-recover`。成本那邊用 aos 自己的 `fork()` 路徑量斜率（掃 `K ∈ {0,1,2,4,8,16,32,64,128}` 筆 instruction，對 `t(K)` 做線性回歸）。東西在 `p3/lab/`（腳本）與 `p3/kit/`（外放的四支）。

**Thompson persona 這一路**砍到最小。自己寫兩支 C benchmark（`lab/bench.c` 量 fork＋execve＋waitpid，`lab/round.c` 逐個系統呼叫複製 `run_exec_once()` 的空回合路徑），四支 argv 程式全部是 shell、**加起來 24 行**，然後做了**三個**驅動器：甲＝只外放投遞（`aos exec` 原封不動）、乙＝四支全外放、**丙＝只外放彙整一支**。丙是他自己加的，因為做完甲乙才發現題目問的「最少幾支」答案不在甲乙之間。最後回到主張三，跑了一個 `grep`：`grep -rn 'deliver' core/inst/src/run*.cpp app/src/main.cpp` → **沒有任何結果**，於是主張三整個翻掉。東西在 `p4/lab/`。

**四位都沒有 build、都沒有改任何 C++。** p1 另外貼了證據：`find . -name CMakeCache.txt` → 0 個，`core/inst/src/*.cpp` 時間戳仍是 2026-08-24 19:40。

### 2. 坑的總表

**本節是主體。**

#### 四位獨立地都撞到的

**（一）不改 C++ 就做不出真正的乙——`aos exec` 沒有「只跑這一批」的入口。**這是本輪最硬的一個障礙，四位各自用不同的話講了同一件事：

- p1（坑 10）：「`aos exec` 一定會自己做 aggregate→claim→execute→release，而外部取件留下的 `.runi` 正好觸發它的退出碼 3。乙案的執行那一步我是在自己的驅動器裡做的，**不是**真的 `aos`。」
- p2（坑一）：「使用者問的問題是『假如 `aos exec` 只保持單純的取指令執行指令』，而回答這個問題的第一步——把 `aos exec` 叫成那個樣子——今天做不到。四位在研討會上談了兩輪『該拆哪幾支』，**沒有一位發現這個題目在今天的二進位上不可實驗**。」
- p3（坑 5）：試過三條路想用真的執行器——把 `.runi` 複製到 scratch world 再 `aos exec`（路徑基準會錯）、把 scratch world 做成 symlink（`.aos` 會繞回原來那個）、bind mount（要 root）——全部繞不過去。
- p4（坑 1）：造暫存世界 `<w>/.cpu` 繞過去了，代價是兩個實測到的破口。

p1 貼出來的那道牆：

```
$ $B/aos-claim .aos/inst.json ; echo "claim=$?"                  # claim=0
$ $AOS exec . ; echo "exec=$?"
aos exec: refusing .: .aos/inst.json.runi already exists
exec=3
```

「取件外放」與「現有的 exec 當純執行器」在定義上互斥，中間沒有繞路。

**（二）殺掉推進者不會停下那批工作——孤兒繼續跑。**四位獨立地都撞到，而且四位都一開始以為是自己的腳本壞了。

- p1（坑 6）：`kill -$SIG $$` 不會殺掉子行程。`mid_exec` 案裡驅動器死了，但批次的 `sh -c 'sleep 0.4; echo done'` 活下來把事做完了（`side-effect.log: 存在 -> done`）。他順帶指出今天的 `aos exec` 也一樣（`exec.cpp` 只有 timeout 那條路會 `kill(-pid, ...)`，被殺的時候沒有任何清理）。
- p2（`lease-demo.sh`）：driver 被 `-9` 之後，批次的 `sleep 4` 被孤兒化繼續跑，而**租約也還握著**，因為 fd 是繼承的。
- p3（坑 7）：`aos-runbatch` 對子行程做了 `os.setpgrp()`（對齊規格第十二節），所以 `killpg` 打不到孫子，`mid_batch` 現場裡 `step2-end` 還是寫出來了。
- p4（坑 3 與主張二）：他第二次的訊號實驗因此整組作廢——`tree_kill` 先殺子行程再殺根，`/bin/sleep 5` 先死，`aos exec` 的 `waitpid` 回來，**按規格第八節「子行程被訊號殺掉算一次完成的執行」**，於是它寫完 `e2.txt`、刪掉 `.runi`、正常回 0。「想中斷一個 aos 回合，殺子行程沒用，一定要殺 `aos exec` 本身。」

p4 把這件事推成一個**只有外放才會出現的新狀態**：殺掉驅動器，孤兒執行器照樣把整批跑完、寫滿 `2/2` 個 `exit` 檔、放掉自己的鎖，只有外層 `.runi` 永遠留著；單體對照組同一個訊號是 `rc=137 .runi=PRESENT exitfiles=1/2`——**工作真的停了**。他的話是：「不是『三種現場長得一樣』，是**鎖的壽命跟工作的壽命脫鉤了**。」

**（三）第一版實驗設計是錯的，而且錯得很有說服力——四位獨立地都差點把反過來的結論寫進回報。**

- p1（坑 5）：`real_crash.sh` 第一版兩個 world 用了不同的批次（P 用 `sleep 3`，Q 用 `chmod 555 .aos`），diff 當然有差異（`size=34` vs `size=106`），「我差一點就把『今天分得出來』寫進回報。修完之後結論整個反過來。」
- p2（坑三、坑四）：兩個。一是**量測工具汙染證據**——第一版 `snapshot` 在讀之前先 `chmod -R u+w`，遞迴 chmod 改掉了 `.runi` 的 ctime，量出 m1/m2/m3 的 ctime−mtime 分別是 2ms／502ms／2003ms，「看起來像時間戳可以判別死法。差點就寫進報告。」二是三個現場各用一個世界、批次裡寫著世界的絕對路徑，於是批次位元組不同、sha256 全不一樣，「第一次跑出來三個 diff 都有差異，我差點以為『原來分得出來』。」
- p3（坑 3、坑 8）：SIGINT 那組第一次量錯數據作廢（見下）；實驗 D 第一次跨版本比對顯示「不同」，查下去只是兩個腳本用了不同的批次文字（161 bytes vs 220 bytes）。
- p4（坑 2、坑 3）：訊號實驗整組壞過兩次，第一次 `$!` 抓到的不是 `setsid` 孫行程的行程群組，「第一次跑出來的 SIGINT 表格（三格都 `CLEAN`）我一度當成發現，寫進草稿才回頭驗證。」

**（四）「零工作的回合必須是零 fork」四位都做到了 0 fork，但四位付的代價不一樣，而且其中一種寫法會把退出碼 3 弄丟。**（數字見第 4 節主張一；分歧見〈壞處〉。）

#### 三位獨立地都撞到的

**（五）這台機器沒有量測工具。**p1、p3、p4 三位獨立地都把它列為最大的坑。p1：「量什麼都要自己想辦法。」p3（坑 1、坑 2）：連 `inotifywait` 都沒有，只好用 `ctypes` 直接呼叫 libc 的 `inotify_init1`／`inotify_add_watch` 手解事件——「這代表『量一個回合有多貴』這件最基本的事，在乾淨的機器上今天沒有現成工具做得到；如果 roadmap 真要走成本路線，`aos exec --explain` 不是加分項，是量測的前提。」p4（坑 5）：`--loop 1` 的回合率沒有直接計數，只能從 `/proc/<pid>/stat` 的 CPU tick 反推。

三位各自造了不同的儀器，這件事本身值得記：p1 用 `/proc/<pid>/io` 的 `rchar`（並用三個 loop 間隔交叉驗證回合數對得上才敢用）；p2 用 `/proc/stat` 的 `processes` 欄數全系統 fork（基準線與案例交錯量）；p3 用兩把獨立的尺互相印證——`gdb -batch` 的 `catch fork` 加 `commands`/`continue` 自動放行，以及 `/proc/sys/kernel/ns_last_pid` 的位移（N=100，用 `/bin/true` 當基準線扣掉 harness）。

**（六）`CLK_TCK=100`，CPU 時間解析度只有 10 ms，回合太便宜量不到。**p1（坑 3）、p3（坑 4）、p4（坑 5）三位獨立地都撞到。p1 的版本最完整：`--loop 5` 與 `--loop 10` 量到 15.2 / 15.1 µs 每回合，比 `--loop 1` 的 8.6 µs 高了快一倍，「那不是真的，是回合數太少（3945 / 1986）讓 ±10 ms 的量化誤差放大成 ±2.5 / ±5 µs。**我一開始差點就把 15 µs 當答案寫下去。**」繞法是把取樣拉到 60 秒、56667 個回合，誤差降到 ±0.18 µs。p3 誠實標了同一件事的後果：他的 7.9 µs/回合「只有一個點支撐，可能有 ±50% 的誤差，但不會差一個數量級」。

**（七）外部彙整器不驗 schema。**p2、p3、p4 三位獨立地都撞到，但只有 p2 把後果測出來——見〈壞處〉第一條。p3（坑 6）走到更深的地方：他本來想用 `ctypes` 直接叫 `libaos_inst.so` 的三支交接函式，做成「同一份實作、兩個入口」的**真**版本，但符號是 C++ mangled（`_ZN3aos22aggregate_instructionsERKNSt7__cxx11...`），參數是 `std::string&` 與帶 `std::vector` 的 `HandoffResult&`，「`std::string` 與 `std::vector` 的 ABI 要手工組，錯一個位元組就是 UB，而且我沒有辦法驗證我組對了」，所以 `kit/aos-aggregate` 是**照著 `handoff.cpp` 重寫**的——「這是重寫不是投影，行為分歧的風險存在。」p4（坑 6）直接標自己那支是玩具：用 `jq -s` 攤平，「不做 schema 驗證、不隔離 `.bad`、不排序保證」。

#### 兩位獨立地都撞到的

**（八）影子世界會打壞規格第四節的相對路徑基準。**p2（情境 2）與 p4（坑 1）兩位獨立地實測到檔案落在錯的地方：

```
（p2）指令：[{"argv":["/bin/sh","-c","pwd > out.txt"]}]
甲 aos exec        → out.txt: .../lab/sc-pathA/out.txt          內容: .../lab/sc-pathA
乙 exec-split      → out.txt: .../lab/sc-pathB/.aos/cpu.d/out.txt   內容: .../lab/sc-pathB/.aos/cpu.d

（p4）--- world B ---
B/.cpu/e1.txt          <<< 規格第四節說相對路徑以 <folder> 為基準，這裡跑到 .cpu 去了
B/.cpu/e2.txt
B/out.txt              <<< 只有寫絕對路徑的那筆落對地方
```

p4 把它接回研討會問而沒人答的那題：「架構師問『helper 的 `cwd` 誰保證』——答案是**沒人**。」p2 的講法是：「這**不是我懶**，今天的 `aos exec` 沒有任何辦法被叫成『只執行這一批、交接我自己來』。要做乙就一定要有個影子世界，就一定會動到 cwd 基準。**『拆四支』這件事在今天的二進位上根本不可表達。**」p3 是預見了這個問題才放棄那條路（見坑一）；p1 沒撞到，因為他的乙案執行那一步是自己的驅動器做的。

**（九）SIGINT 對背景 job 是被忽略的。**p3（坑 3）與 p4（坑 4）兩位獨立地撞到，處置不同。p3 查出原因——**非互動 shell 會把背景 job 的 SIGINT／SIGQUIT 設成 `SIG_IGN`**，訊號根本沒送到——改用 `subprocess` 直接起（`lab/E_sigint.py`）之後得到正確結果 `rc=-2`，並且**兩版腳本都留著沒刪**。p4 量到同一件事的證據（`/proc/<pid>/status` 的 `SigIgn: 0000000000000006`，bit 2 = SIGINT、bit 3 = SIGQUIT）但沒有繞過去：「任務書要求『`SIGINT` 都試』，**我沒做到**，要在能給前景終端機的環境裡才測得到。KILL 與 TERM 的資料是有效的。」

#### 一位撞到、但值得單獨記的

- **`/bin/sleep` 自己就是一次 fork**（p2，坑五）。用 shell 寫輪詢迴圈的話，光是睡覺就讓「零 fork 閒置」永遠不可能。他用 bash 內建的 `read -t` 配一個沒人寫的 fifo 才做到。「這件事對『用 shell 寫 core helper』是個真警告。」
- **`set -e` 吃掉退出碼 3**（p3，坑 10）。A1 第一次跑到 `aos exec` 回 3 就整個腳本結束，執行後的狀態根本沒印出來——「而那正是全場最重要的一組證據。這個題目裡『非零退出碼是正常結果』，`set -e` 不能用。」
- **`zsh` 的 `&&` 鏈把 `pkill` 回 1 當成失敗**（p1，坑 8），整串靜靜中斷，只印了標題就結束。之後所有時序敏感的東西都改寫成獨立的 bash 腳本。p3（坑 9）撞到同一個殼的另一面：`find` 被 alias 成 `bfs`、`ls` 有一次讓整個 bash 呼叫卡到逾時，全部改用 `/usr/bin/find` 絕對路徑。p2（坑九）也記了一次 `ls -la` 掛兩分鐘。
- **`handoff_tool.c` 第一版直接 segfault，退出碼 139**（p1，坑 4）。`char acc[4096][4096]` 是 16 MB 開在 stack 上，改成 `static` 就好。「貼出來是因為它是我唯一一次『以為做完了但根本沒跑起來』。」
- **並行測試的歸因差點做錯**（p1，坑 9）。第一眼看到 23/30 就想寫「claim 有 race」，做了「事先彙整好」的對照（0/30）才確定是 aggregate。「如果沒做那個對照，這份回報會指控錯一支程式。」
- **影子世界自己會洩漏相位**（p2，坑六）。`.aos/cpu.d/` 底下 `aos` 會做它自己的一套交接，於是「批次寫進去了沒」「aos claim 了沒」「aos release 了沒」本身就是三個相位標記，讓天真版看起來好像分得出來。他用 `SNAP_EXCLUDE` 排掉，但另外記了一筆：「**任何真的 CPU 都得被『告知』要跑什麼，而『被告知過』本身就會在磁碟上留痕跡。**研討會假設 CPU 不留痕跡，那個假設在真的實作裡不成立。」
- **在單體裡 race 不到「取件完就死」**（p2，坑二）。`claim_instruction()` 返回到 `execute_batch()` 第一次 fork 之間只有幾十微秒，隨機延遲打不中；想用超大批次拖長 parse 時間開窗口，但那會改變 `.runi` 內容就沒法逐位元比對。最後**手工做一次 `mv`**，並在腳本註解與回報裡照實標明「這是構造出來的現場，不是殺出來的」。p3 用 gdb 斷點解掉了同一個問題（K1 停在第一次 `fork`）。
- **相位標記的順序第一版寫錯**（p2，坑七）。`claimed` 寫在 claim 之後，開了一個「`.runi` 在、標記不在」的窗口。「是我自己盯著想才發現的，不是測出來的（那個窗口一樣是微秒級，我一樣 race 不到）。**所以這條我只有推理，沒有實測。**」他從中收出一條規則：「**『給重跑許可』的標記寫在危險動作之前，『收回許可』的標記寫在之後。**這樣每一個模糊窗口裡都沒有子行程在跑，猜錯永遠往保守的方向錯。」p3 獨立踩到同一類的東西（坑 11）：`aos-release2` 一開始寫成先清 sidecar 再 unlink `.runi`，那會製造「有 `.runi`、沒有 receipt」的不可判定現場——「孤兒 sidecar 無害，孤兒 `.runi` 有害。」
- **gdb 第一次跑忘了重建世界**（p3，坑 1 後半）。`inst.json` 已被前一輪消耗掉，三個情境全都印 0 fork，「我當場以為驗收條件普遍成立，回頭才發現是世界空了。」
- **`.temp` 檔名共用**（p1）。規格第六節自己說投遞要帶 pid「因為 `rename` 原子但寫入不是」，但彙整那一步用的是固定的 `inst.json.temp`。「行程內時只有一個彙整者所以看不到，外放（或多推進者）之後這是個現成的資料損毀來源。我的實作照抄了這個錯。」

### 3. 好處 / 壞處

#### 好處

- **交接協定本身的分層是對的，四位獨立地都證實了「這不是新功能，是把已經做好的東西接出去」。** p1：「外放在**介面**上完全沒有阻力——照著抄一份出來只花了一個檔案，語意抽查全過（`claim` 第二次回 3、空 `aggregate` 回 10）。」p2：「語意窄到我用 shell 三十行就重寫完了，而且行為對得起來。」p3：「我把 claim 和 release 各自寫成 4 行 `sh` 就跟 C++ 版行為一致（實驗 D 的逐位元比對是這件事的證明）。」p4：「四支加起來 24 行 shell，一個下午內全部跑起來。」
- **`rename(2)` 當狀態機便宜到量不出來。**（p2）相位標記整套加起來就是三次 `mv`，同目錄、零位元組、原子。「要在一個沒有資料庫、沒有 daemon 的系統裡表達『我走到哪一步了』，這是最便宜的方式。」
- **外放之後寫出了比 C++ 版更對的 claim。**（p2）`aos-claim` 用 `link()`＋`unlink()`，遇到已存在的 `.runi` 會原子地 `EEXIST`，沒有規格第十二節自己列出的那個 `lstat`＋`rename` TOCTOU。「一支 shell 腳本在正確性上贏過 in-tree 的 C++——這件事本身就說明『機制外放』不等於『機制變爛』。」
- **三步交接是 rename-based 的，這讓外放的取件天生就是原子的。**（p1）32 並行、60 次試驗、0 次重複執行。「`rename` 幫你把互斥做完了，不管呼叫它的是同一個行程還是不同行程。」
- **`.aos` 這個「世界在檔案系統上」的模型救了整個實驗。**（p2）「我能逐位元 diff 三個崩潰現場，是因為狀態真的全在檔案系統上，沒有藏在誰的記憶體裡。換一個把狀態放在 sqlite 或共享記憶體的系統，這一輪根本做不出來。」
- **規格已經替「只外放彙整」留好了門，而研討會沒人提到。**（p4）「`aos exec` 內建的彙整在 `inst.json` 已經存在時直接 `return Ok`（`handoff.cpp` 第一個 `lstat`），所以外部彙整先跑完，內建那支就自動變成 no-op。這個『已經有一批就不發布』的規則本來是防覆蓋用的，順手把外放彙整變成了零成本的疊加。**這是我在這題裡最喜歡的一個發現。**」
- **外放讓崩潰狀態變得可以檢查。**（p1、p2、p3 三位獨立地都做出來了）p1：「因為釋放本來就是獨立的一步，加一把 `flock` 跟一份 journal 幾乎沒有成本，而換到的是三者可分辨——比今天強。」p3：「write-ahead 那層便宜得意外……而且它跟『同一個行程』完全正交——**今天不外放也可以先加上**，馬上就把『今天就分不出來』那個洞補掉。」
- **`exit` 欄位當進度游標比 receipt 好用。**（p4）「不必新增格式、不必決定寫在哪、不會毀掉『出事時 `cat .runi` 就看到那一批』。」
- **`p3-exec` 全長 144 行、`turn()` 只有 40 行**（p3），涵蓋進 world、驗版本、四步交接、`--loop`、退出碼 3 停止、閒置快速路徑。「架構師『新想法 C：core 的定義從哪些程式改成哪一份順序』實際做出來就是這個尺寸，讀得完。」
- **投遞是真的白撿，而且跟拆不拆 `aos exec` 是兩件無關的事。**（p4）「五行 shell，`aos` 完全不參與，任何語言都能寫，T5 那份 agent loop 腳本今天就能少寫十行。這條建議該立刻做，**不要跟拆解綁在一起排期**。」

#### 壞處

- **換一支不驗 schema 的彙整器，代價不是「半夜卡住」，是整批資料無聲蒸發。**（p2，實測）同一份帶拼錯 key 的投遞（`"stdou"` 而不是 `"stdout"`）走兩條路：

  ```
  --- 外部 aos-aggregate（jq 版）---
    rc=0    發布出來的 inst.json：[{"argv":["/bin/true"],"stdou":"x.txt"}]
  --- C++ 的 aggregate_instructions()（走 aos exec）---
  aos exec: warning: .aos/inst.tempd/1.json: UnknownKey
    aos exec rc=0        投遞匣現在是：1.json.bad          <- 隔離、留在原地給人看
  --- 那份被放行的批次，最後撞到誰？---
  aos exec: .aos/inst.json.runi: record 1: UnknownKey
    aos exec 在拿到那批之後 rc=1
    .aos 現在是：inst.tempd version                        <- .runi 沒了，那批消失了
  ```

  規格第六節寫著「整批 JSON 解析失敗也算回合正常返回，`.runi` 一樣刪掉……那批壞內容就此消失」。**連 `.bad` 都沒有。**
- **退出碼是一個沒有主人的協定。**（p1）「規格第八節只規定 `aos exec` 的退出碼，沒有規定外放程式該回什麼。我只好自己編一套（0 做了事／10 沒事做／3 Busy／1 錯誤）。四支程式、每支三到四個狀態，中間任何一個人理解不一樣，整個回合的控制流就錯。今天這些狀態是 `HandoffState` 這個 enum，編譯器管；外放之後變成 12 個整數，沒有人管。**這是我在乙案裡最想罵人的地方。**」p2 從另一面講同一件事：「規格第八節自己說『退出碼只給跑 `aos exec` 的那個人看』。可是 `--loop` 底下、agent loop 底下、cron 底下，**那個人不存在**。」
- **python 寫的外放工具會讓毫秒級輪詢直接失效。**（p1）10.64 ms/回合 vs 1 ms 目標，實際回合率掉到約 94/s，而 `--loop 1` 要求的是 944/s。「而外放的整個賣點就是『誰都能寫一支』，那麼誰都能用 python 寫一支。**這個體系會把『回合頻率』變成一個由最慢的那支外放程式決定的、沒有人在守的東西。**」
- **「零 fork 的閒置閘門」與「彙整政策完全外包」互斥。**（p4）「閘門必須知道『什麼情況下該叫彙整』，那就是彙整的觸發條件。今天是『inbox 非空』，但如果有人的彙整想按 mtime 攢批、想每 10 秒才收一次、想按配額，閘門的判斷就是錯的——它會在該叫的時候不叫。二選一。**研討會兩條都接受了，沒有人注意到。**」p1 撞到同一個矛盾的另一個版本：「要判斷『沒事做』，exec 必須知道 `.runi` 是忙碌標記、`inst.json` 是可取的批次、`inst.tempd/` 是投遞匣、以及投遞的檔名規則。**那基本上就是整份 `.aos` 規格。**」——他做了 `mtimeguard` 來解（exec 不認識任何命名規則，只被**設定**餵一組觸發路徑），p2 做了「偵測留在裡面、政策外放」來解，p3 直接承認解不掉：「driver 又開始懂政策了，『exec 只做取指令執行指令』這句話當場破功。**閒置快速路徑本身就是一條寫死在核心裡的政策。**」
- **乙讓鎖活得比工作久，而這是外放製造的新狀態。**（p4）「殺掉驅動器，孤兒執行器照樣把整批跑完、把副作用全寫上磁碟，然後世界永遠鎖著、沒有任何活著的行程知道這件事。單體不可能到這個狀態。這件事沒有便宜的解——要嘛驅動器與執行器共命（那就沒外放）、要嘛加行程監督（那就在 `aos` 外面長出一個 init）。」
- **`aos` 這支執行檔對「當機制用」太胖。**（p2、p3 兩位獨立地都指出）每次 `execve` 要付 0.79–0.877 ms，大半是映射與重定位 42 MB 的三顆 `.so`，包括跟交接完全無關的 32 MB `libaos_llms`；而 `/bin/sh` 只要 0.437 ms。p3：「『同一支執行檔、同一次 build』這條在版本一致性上是對的，在成本上是自己給自己找的麻煩。」p3 貼的證據：

  ```
  $ LD_DEBUG=statistics ./build/bin/aos 2>&1 >/dev/null | head -8
    total startup time in dynamic loader: 516041 cycles
              time needed for relocation: 412913 cycles (80.0%)
                   number of relocations: 4793
  $ LD_DEBUG=statistics /bin/true 2>&1 >/dev/null | head -8
    total startup time in dynamic loader: 39954 cycles
  minor_faults: /bin/true 228   aos 519
  ```
- **`.runi` 是一個只有一個位元的錯誤回報機制。**（p2）「它說『有事』，不說什麼事。三種需要三種不同處置的狀況——一種可以無損重跑、一種絕對不能重跑、一種只要刪掉檔案——全部塌成同一個字串。而規格第十二節那句『那正是「有一回合沒跑完」的誠實表述』是在替一個吞掉的 errno 找藉口。`unlink` 給了你 `EACCES`，你印出來然後回 1，磁碟上什麼都沒留。半夜三點被叫起來的人看到一個 `.runi`，他不知道那批跑了沒，**他只能賭**。」
- **兩個 `.aos` 在同一個世界裡。**（p4）「`.cpu/.aos/` 只是我的權宜，但它預示了真做起來的形狀：只要執行器是獨立行程，它就需要自己的世界，於是『一個資料夾＝一個世界』就不成立了。」
- **`flock` 的 fd 繼承是地雷，而且 `flock` 在 NFS 上不可靠。**（p1，坑 7）「如果批次裡有個 daemon 化的長命子行程，那把鎖會被永久握住，整個世界永遠顯示『有回合在跑』。**要做對必須在 fork 之後 exec 之前把那個 fd 關掉（`FD_CLOEXEC`），我沒做。**」
- **想罵人的那一句。**（p3）「規格第六節那句『所以這個不變式成立：`.runi` 存在 ⟺ 有一回合沒跑完』是一句**沒有證明的斷言**，而整場研討會、四位、兩輪、十二條好壞，全部架在它上面。我花了半小時就用一個 `rm` 把它打掉。」

### 4. 三個主張各收到什麼

#### 主張一（成本）：四位都量了，四位都推翻了那個數字；驗收條件四位都做到了

**「一次 fork＋execve 約 1–3ms」——四位獨立地都量了，四位都推翻。**單位一律微秒（µs）或毫秒（ms），量法貼在各人回報裡。

| 被 exec 的那支 | p1（`spawn_bench.c`，`taskset -c 2`，n=2000） | p2（`forkexec.c`，n 見括號） | p3（`bench_fork.py` 線性回歸，30 次/點 × 9 點） | p4（`bench.c`，n=2000） |
|---|---|---|---|---|
| 純 `fork`＋`_exit` | p50 **27.1 µs**（mean 28.6） | p50 **35.7 µs** | — | — |
| 靜態小 C | p50 **71.9 µs** | p50 **84.0 µs** | — | — |
| 動態小 C／`/bin/true` | p50 **128.4 / 130.4 µs** | p50 **142.8 / 149.4 µs**（vfork 115.1） | 斜率 **0.222 ms/筆** | p50 **151.5 µs** |
| `/bin/sh -c :` | p50 **432.0 µs** | p50 **449.1 µs**（n=500） | 單支底價 **0.437 ms** | p50 **447.2 µs** |
| `aos`（同一支執行檔、busybox 式） | p50 **769.0 µs**（n=500） | p50 **789.2 µs**（n=1000） | 斜率 **0.861 ms/筆** | p50 **778.8 µs** |
| python3 腳本 | p50 **5487 µs**（5.49 ms） | p50 **5720.8 µs**（5.72 ms，n=200） | 單支底價 **5.669 ms** | — |

四位的結論措辭不同但方向一致：

- **p1**：「這個數字 90% 由『被叫的那支程式怎麼啟動』決定，跟 fork 幾乎無關。**四個人拿一個混淆了 primitive 與 callee 的數字論證了兩輪。**建議把它從所有論證裡刪掉，換成『一次外放 = 130 µs（binary）／430 µs（shell）／5.5 ms（python）』。」
- **p2**：「**這個數字不是一個常數，它是一個實作選擇**，跨度 68 倍。整個成本論證架在一個『它是常數』的假設上，那個假設才是真正錯的地方。」
- **p3**：「實測 0.861 ms，高估 1.2–3.5 倍。」那 0.639 ms 的差價花在動態連結（見〈壞處〉）。
- **p4**：「高估了 1.3× 到 20×……而且它偏保守。」

**空回合今天到底多便宜——四位獨立地都量了，四位都量到微秒級。**

| 量法 | 數字 |
|---|---|
| p1：`/proc/<pid>/io` 的 `rchar` 當回合計數器，60 秒 / **56667 個回合**，量化誤差 ±0.18 µs/回合 | CPU/回合 **8.6 µs**；wall/回合 1058.9 µs 減掉實測 nanosleep 1052.5 µs → **6.4 µs**。兩個獨立方法夾出「**空回合 ≈ 6–9 µs**」 |
| p2：兩點消去法，`aos exec 空世界` 減 `aos 無參數`（各 n=1000） | 邊際 **27.2 µs**（816.4 − 789.2） |
| p3：ctypes 掛 inotify 在 `.aos/inst.tempd` 上精確數回合（`--loop 1`，3776 回合 / 4000.9 ms） | wall **0.0596 ms**，CPU **7.9 µs/回合** |
| p4：`round.c` 逐系統呼叫複製 `run_exec_once()` 的空回合路徑（n=5000） | **2.2 µs**（他標明這是複本不是本體）；交叉驗證 `--loop 1` 跑 5 秒 40 ms CPU / 約 4700 回合 → **約 8.5 µs** |

**外放之後變多少：**

| 誰 | 情境 | 數字 |
|---|---|---|
| p1 | `split_driver` 五模式，n=20000（`full` 是 C 版工具） | inproc 2.30 µs / 0 fork；deliveronly **2.28 µs / 0 fork**；guarded 2.21 µs / 0 fork；mtimeguard **1.11 µs / 0 fork**；**full 158.55 µs / 1.00 fork**（self 17.30 + children 141.25）；full(sh) **490.63 µs**（n=5000）；full(py) **10641 µs**（n=500） |
| p2 | `loopcmp.py` 兩點消去法（T=3s vs 12s，`--loop 10`） | 甲 `aos exec --loop 10` **22.9 µs/回合**（0.229% 一顆核心）；乙天真版 **2852.1 µs/回合**（28.5%）；乙＋守門 **43.6 µs/回合**（0.436%） |
| p3 | 單支底價相加 | 外放 1 支 **+0.861 ms → wall 15×、CPU +108×**；外放 3 支 **+2.58 ms → wall 43×、CPU +327×** |
| p4 | `round.c` 外放彙整一支 | **154 / 450 / 802 µs**（`/bin/true` / `sh` / `aos`）＝ **70× / 205× / 365×** |

**驗收條件「零工作的回合必須是零 fork」——四位獨立地都做到 0 fork，證據的硬度不同。**

- **p2** 是唯一真的去數全系統 fork 的（`/proc/stat` 的 `processes` 欄，基準線與案例**交錯量**，每段 8 秒、輪詢 10 ms、約 800 個閒置回合）：

  ```
  基準（什麼都不跑）        32        甲 aos exec --loop 10        32     -> 每閒置回合 0 次 fork
  基準（什麼都不跑）        53        乙 split-loop 10（無守門）   5955   -> 每閒置回合 7.4 次 fork
  基準（什麼都不跑）        77        乙+守門 split-loop --gate    37     -> 落在噪音裡，0 次 fork
  基準（什麼都不跑）        34
  ```
- **p3** 用兩把獨立的儀器互相印證：`gdb` 的 `catch fork`（0 筆 instruction → 0 次命中；1 筆 → 1 次；3 筆 → 3 次），以及 `/proc/sys/kernel/ns_last_pid` 位移（N=100，扣掉 harness）：

  ```
  基準線：/bin/true                     → 0.00
  今天：aos exec（空 world）             → 0.00
  乙：p3-exec（空 world）                → 2.06
  乙：p3-exec --idle-fast（空 world）     → 0.01
  ```
  他的話：「**這條驗收條件不是外放的阻擋條件，是外放的必做項。**」
- **p1** 做了兩個守門變體並量了：`guarded` 2.21 µs / 0 fork、`mtimeguard` **1.11 µs / 0 fork**——「比今天真 `aos exec` 的 8.6 µs 還快 7.7 倍。所以成本這一題**不是外放的固有代價，是『每回合無條件 fork』的代價**。」
- **p4** 做到了，但量出一個沒人提過的代價：**照資深工程師的原話字面實作，退出碼 3 會消失。**

  ```
  $ AOS_GATE=1 ./bin/aos-round4 L     # 閘門只 stat inst.json 與 inst.tempd
    乙 WITH gate   EXIT=10   <-- 3 沒了
  $ AOS_GATE=0 ./bin/aos-round4 L
  aos-claim: refusing: L/.aos/inst.json.runi already exists
    乙 WITHOUT gate EXIT=3
  ```
  「那句話要進規格得補上 `.runi`。」

**p4 另外提出一個四位研討會參與者都沒提的參數：`--loop` 的週期。**「`run.cpp` 實測 `--loop 0` 會被夾成 1（`aos exec: warning: --loop 0 would busy-poll ... using 1 ms instead`），所以下限是 1 ms。`--loop 1`：多 802 µs 讓週期從 1.0 ms 變 1.8 ms，還吃掉近半顆核心——真的痛。`--loop 100`：0.8%——是雜訊。**整個成本論證只對 `--loop 1` 成立。研討會把一個週期參數的問題講成了架構問題。**」

#### 主張二（不變式）：「三種死法一樣」四位都證實；「這是外放造成的」三位獨立地都推翻；「分不出來」三位獨立地都做出反例

**（a）三種死法在磁碟上真的一模一樣——四位獨立地都證實了。**四位用了四種不同的殺法與四種不同的快照工具（都刻意排除 mtime／inode，只比型別／權限／大小／內容雜湊）：

- p1：三個快照的 sha256 全部是 `e24be31aaa5508e4…`，`kill -9` 與 `SIGINT` 都試過，結果相同。
- p2：六個現場（三死法 × `SIGKILL`／`SIGINT`）三個 diff 全部「零差異」，並且**證明時間戳也救不了**——`.runi` 的 mtime 是那批 JSON 被寫下來的時刻、ctime 是 rename 的時刻，「**兩個都在回合開始之前就凍住了，之後回合死在哪裡，一個位元都不會動**」，三個現場的 ctime−mtime 都是約 1 ms。
- p3：gdb 三個精確斷點，`.aos/inst.json.runi` sha256 三次都是 `f92bcff06f874b16…`。
- p4：`SIGKILL` 與 `SIGTERM` 各三次，sha256 前 16 碼三份一致（`0a4278ce9cd0ca88`）。

**（b）「這條不變式成立的唯一理由是同一個行程」——p1、p2、p3 三位獨立地都推翻了，而且證據形狀各不相同。**

- **p1**（對照實驗）：拿**完全沒外放、就是現有這顆二進位**做對照，兩個 world 用**逐位元相同的批次**。案 P 是批次跑到一半 `kill -9`（退出碼 137），案 Q 是批次跑完但從外面在執行中把 `.aos` 改成 555 讓 `unlink` 吃 EACCES（`aos exec: cannot remove ./.aos/inst.json.runi: Permission denied`，退出碼 1）。兩邊的 `.runi` 都是 `a697f32d1de87591…`：「**完全沒有差異：今天的行程內設計也分不出這兩種崩潰。**『同一個行程』買不到『分得出崩潰在哪一階段』，它從來就只買到『偵測』。」
- **p2**（同一件事，加上規格的自白）：他把規格第十二節那句「刪除 `.runi` 失敗：印錯誤、回 1……**那正是『有一回合沒跑完』的誠實表述**」拿來對打——「那句話是自我安慰。回合跑完了，副作用全做了，`.runi` 卻說沒跑完。**外放不會把它從『成立』降級成『約定』，因為它現在也只是約定。**差別只在：今天那個『約定』寫在 C++ 裡，沒人看得到；外放之後至少它是一支你 `cat` 得出來的腳本。」
- **p3**（`rm` 一行就開鎖，這是本輪最短的一個反證）：批次裡放一筆 `rm .aos/inst.json.runi`。指令是任意 POSIX 命令、`cwd` 就是 `<folder>`（規格第四節），所以這一筆**今天就寫得出來，不需要任何 argv 化**：

  ```
  === P1 = aos exec（批次中間有一個 rm .aos/inst.json.runi）
    [P1 起跑 0.5s] .aos = ['inst.tempd', 'version']
  === 此時投遞 BATCH-B 並起 P2 = aos exec ===
    P2 rc=0     P1 rc=1
  === trace.txt（時間序）===
  BATCH-A step1
  BATCH-B running
  BATCH-A step2-after-2s
  ```
  「`trace.txt` 的時間序證明**兩批真的同時在跑**。今天那條不變式不是由『同一個行程』保證的，是由『沒有人會寫 `rm .aos/inst.json.runi`』保證的。」

  p3 另外做了一件別人沒做的事：**把同一個外放版的三個現場跟今天的三個現場對比**——「**六個現場，一個指紋。**外放沒有讓可分辨性下降，因為可分辨性本來就是零。」

**（c）「一旦釋放交給另一支程式就分不出來」——p1、p2、p3 三位獨立地都做出了會分的版本，三個做法不同。**

| 誰 | 做法 | 結果 |
|---|---|---|
| p1 | 驅動器整回合握著 `.aos/round.lock` 上的一把 `flock`（核心強制）＋一份只回答「跑到哪一階段」的 `round.journal`；判斷程式也是外部程式、只看磁碟 | 三個位置全部分得出來，`SIGKILL` 與 `SIGINT` 都試過。`mid_exec` 在孤兒還活著時回報「還在跑」（因為 fd 被繼承），等孤兒跑完再判一次得到「跑到一半死」 |
| p2 | 相位標記 `inst.json.runi.claimed` → `.running` → `.ran`（每次一個 `rename(2)`）＋ `inst.json.lease` 上的 `flock` 租約 | `DEAD_AFTER_CLAIM`（碼 4）／`DEAD_MID_BATCH`（碼 5）／`RAN_NOT_RELEASED`（碼 6），三個 diff 各差一個檔名；`SIGKILL` 與 `SIGINT` 都試過（同一位置換信號零差異——他標明「這個零差異是對的」）。成本：三個零位元組檔案、一個空 lease 檔、每回合多三次同目錄 `rename` 與一次 `flock` |
| p3 | write-ahead：每個動作之前先把「我要做這件事」寫上磁碟並 `fsync`，做完才記「做到了」；receipt **旁邊放**（`inst.json.runi.receipt`）不包進 `.runi`；`aos-release2` **先 unlink `.runi`** 再清 sidecar | `DIED_AFTER_CLAIM`（11）／`DIED_MID_BATCH`（12，「已完成 1 筆，未完成的第 [1] 筆」）／`DONE_NOT_RELEASED`（13）；正常跑完 `CLEAN`、recover 回 0；同一支 recover 讀今天的現場 → `UNCLASSIFIABLE  .runi 在，但沒有 receipt`，rc=1 |

p2 把它接成一句直接對打 OS 研究者的話：「他說『aos 刻意什麼常駐的都沒有、只剩檔名，所以 claim 與 release 出去就是把號誌畫在沙上』。**這句話漏了一件事：鎖只需要活得跟回合一樣久，而回合正好就是一個行程樹的生命期。**`aos` 是沒有 daemon，但它有核心。……號誌不是畫在沙上，是畫在核心的 file table 上。」p3 的版本是：「**『取件與釋放在不同行程』與『三種現場分得出來』是兩件互相獨立的事。**前者不蘊含後者（實驗 C），前者也不排除後者（實驗 G）。研討會把它們綁在一起了。」

**p4 在這一題上跟另外三位分歧，而且他的理由是實測的。**他只推翻「三分之一」：「取件完就死」不需要任何新格式就分得出來——`exit` 檔數 = 0，他的 `bin/aos-forensic` 純靠磁碟判別，三次都判對。但 (b)「跑到一半死」與 (c)「跑完但釋放失敗」在他手上分不出來，**原因不是資訊不夠**：

```
  a) DIED AFTER CLAIM, BEFORE EXECUTION: 0/2 ran
  b) EXECUTION COMPLETED, RELEASE FAILED: 2/2 reported exit, executor released cleanly
  c) EXECUTION COMPLETED, RELEASE FAILED: 2/2 reported exit, executor released cleanly
  monolith control: rc=137 .runi=PRESENT exitfiles=1/2
```

「殺掉驅動器**不會停下那批工作**。孤兒執行器跑完了整批、寫滿 2/2 個 `exit` 檔、放掉自己的鎖，只有外層 `.runi` 永遠留著。單體對照組同一個訊號是 `exitfiles=1/2`——工作真的停了。**這才是〈壞 1〉的真正版本：不是『三種現場長得一樣』，是『鎖的壽命跟工作的壽命脫鉤了』。加 receipt header 解不掉這個，因為 receipt 是驅動器寫的，而驅動器已經死了。**」（p2 的 `lease-demo.sh` 演的正是同一個現場，但他的租約在孤兒跑完之後由核心自動放掉，於是判定從 `RUNNING` 轉成 `DEAD_MID_BATCH`。兩人的實驗都留著。）

**順帶那題：`.runi` 鎖的是「那一批」還是「那個世界」——四位都答了，四個答案不一樣。**

| 誰 | 答案 | 依據 |
|---|---|---|
| p1 | **那一份 instruction 檔的那一批** | 「規格第六節末已經寫死了——『每顆 CPU 各鎖各的：`inst.json.runi` 只鎖核心 CPU，`insts/llm.json.runi` 只鎖 LLM 那顆』。我的實作（`derive_paths` 全部從 instpath 推導）繼承的也是這個。研究者說『前者拆得開』——那就是拆得開的那個。」 |
| p2 | **第三個答案：那個世界的那一顆 CPU 的那一個槽** | 讀 `handoff.cpp` 的 `derive_paths()`，`paths.runi = base + ".runi"`；`claim_instruction()` 拒絕的條件是那個**固定名字存在**，跟那一批的內容沒有任何關係——`.runi` 裡面沒有任何批次身分。「**兩個都不是他講的那兩個，答案是第三個，而第三個拆得開。**真正該補的是**批次身分**——內容雜湊就夠了，否則 recover 沒辦法確認『我搬回去的這一批就是當初取走的那一批』。」 |
| p3 | **第三個答案：`L-slot`（那個檔位），而且連 `L-slot` 都沒守住** | 他把三種讀法各寫成一條可否證的命題。`derive_paths()`（`handoff.cpp:28`）鎖名不帶批次身分 → `L-batch` 不成立；`aggregate_instructions()` 的守衛只有 `lstat(inst.json)`、**完全不看 `.runi`**（`handoff.cpp:141`），而 `run_exec_once()` 把 aggregate 排在 claim 之前（`run_exec.cpp:135`）→ `L-world` 也不成立。「**轉交提案第 5 條的二分法本身不完整。**既然實作已經是（漏水的）`L-slot`，**投遞與彙整外放在不變式上不需要付任何新代價**，因為它們今天就已經在鎖外面跑了。」 |
| p4 | **那個世界**，而乙把它逼到明面上 | 「`.runi` 是從 instruction 路徑推導出來的固定名稱，裡面沒有任何東西指認那一批。而乙把這件事逼到明面上：外層 `.runi` 是世界鎖，`.cpu` 內層 `.runi` 是批次鎖，兩者壽命不同。今天單一個 `.runi` 把兩件事混在一起。研究者說『前者拆得開、後者拆不開』是對的，但推論反了：**該拆成兩個檔的是鎖，不是取件程式。**」 |

#### 主張三（範圍）：兩位推翻、方向相反；一位沒打穿但改了問題的形狀；一位同意方向但推翻理由

**p4 推翻，靠一個 `grep`：投遞本來就不在 `aos exec` 裡。**

```
$ grep -rn 'deliver' core/inst/src/run*.cpp app/src/main.cpp
exit=1  <- nothing
```

「**aos 裡沒有任何投遞的程式碼。**投遞不在 `run_exec.cpp` 裡，不在回合裡，`aos exec` 從來沒有 fork 過它。所以『把 deliver 外放』**根本不是在拆 `aos exec`**——它只是替一件本來就在世界外面、而且從來沒實作過的事寫一支程式。五行 shell，今天就能寫，不必碰 C++，不必動規格，一次 fork 都不會多。**四位是各自從四個不同理由，一致地推薦了那四支裡唯一一支本來就不在裡面的。**」於是他做了第三個版本（丙＝只外放彙整），並交出一張表：

| | 外放幾支 | 空回合 | 退出碼 3 | 規格 §4 相對路徑 | 世界裡有幾個 `.aos` |
|---|---|---|---|---|---|
| 今天／甲 | 0（投遞不在回合裡） | 2.2 µs | 保住 | 對 | 1 |
| **丙** | **1（彙整）** | 2.2 µs（有閘門） | **保住，連診斷訊息一字不差** | 對 | 1 |
| 乙 | 4 | 802 µs | **丟了（回 10）** | **壞了（`exit` 檔跑進 `.cpu/`）** | **2** |

「**如果一定要外放大於零支，答案是恰好一支，而且是彙整，不是投遞。**理由不是成本，是**只有彙整有政策**——排序、配額、優先權、按 mtime、按時段，這些都是真的有人想換的旋鈕。取件是一次 `rename`，釋放是一次 `unlink`，兩支都沒有任何旋鈕可轉，把它們外放買到的是零，賣掉的是上面那張表右邊三欄。」他最後對評委留了一句：「如果你們認為『投遞本來就不在回合裡』這點不成立，請直接指出，因為主張三的整個結論都架在那個 `grep` 上。」

**p1 也推翻，方向同樣是「該優先外放的是彙整」，但走的是完全不同的一條路：他量到了一個真的重複執行 race。**同一個 world 上放 N 個推進者，批次只做「往 log 追加一行」，跑完數行數，應該剛好 1：

```
=== 甲：16 個並行的真 aos exec，30 次試驗 ===
  試驗 1: 執行了 2 次 (期望 1)   ...   試驗 25: 執行了 3 次 (期望 1)
  30 次試驗，異常 23 次
=== 乙：16 個並行的外部 aos-claim，30 次試驗 ===
  30 次試驗，異常 0 次

併發度掃描（每格 30 次試驗）：
  N=2   重複執行  0/30   N=4   重複執行  0/30
  N=8   重複執行  2/30   N=16  重複執行 14/30

=== 對照：甲 但事先彙整好，16 個 aos exec 只搶 claim，30 次 ===  異常 0 / 30
```

「**race 出在 aggregate，不在 claim。**機制：N 個行程各自跑 aggregate，都 `lstat(inst.json)` 看到 ENOENT，都讀到同一份 `a.json`。P1 發布、取件、執行、釋放（`.runi` 消失）；此時還捧著 `a.json` 內容的 P2 把它**再發布一次**，於是同一批被執行第二次。`.runi` 保護不到它，因為 aggregate 跑在 claim **之前**。」他的結論是「外放的優先順序應該是 **aggregate 第一，deliver 第二，claim／release 最後**……而研討會把它排在『不該動』那一邊。」他同時對自己誠實：「我的外放版在 32 並行、60 次試驗下 0 異常，但**那不代表我的實作免疫**，它有同一個結構性的 race（一樣共用 `.temp` 檔名），只是讀到刪的視窗窄得多。0/60 是『沒觀察到』，不是『不會發生』。」

**p2 同意「deliver 該外放」的方向，但推翻四位收攏出來的那條理由。**他跑了四個情境（換彙整政策、相對路徑基準、把 claim 當一筆 instruction 跑、兩支同時推進），交出的是：

- **乙做得到而甲做不到的**：換彙整政策（**差異就是一行 `head -n 2`**）；用非 C/C++ 寫第二顆 CPU（「我這整包就是證據，全是 sh」）；原子的併發保護（`flock` 沒有 TOCTOU，而規格第十二節自己承認 C++ 版的 `lstat`＋`rename` 有）。
- **乙壞掉而甲沒壞的**：規格第四節整條垮掉；驗證邊界跟著搬走（整批靜靜蒸發）；每個閒置回合 7.4 次 fork（除非加守門）。
- 但——「**四位收攏出來的那條理由『claim 與 release 就是回合邊界本身，所以不能出去』被我的 mode c 推翻了。**出去的是**機制**（誰去 rename、誰去 unlink），留下來的是**租約**（誰在那段時間裡活著）。這兩件事可以分開，而且分開之後比不分開更強。真正不能出去的不是 claim 和 release，是**握著 fd 的那個行程**——而那個行程本來就必須存在，因為總得有人等子行程。」
- 他另外指出**使用者原話的字面版在邏輯上不可能**（情境 3）：「要跑『取件』這一筆指令，得先取件。這是自我指涉。」而且順帶把〈壞 2〉實測出來了：

  ```
  $ cat $W/.aos/inst.json
  [{"argv":[".../aos-claim",".../sc-selfclaim"],"exit":"claim.exit"}]
  $ aos exec $W
  aos-claim: refusing: .../sc-selfclaim/.aos/inst.json.runi already exists
    回合退出碼 = 0
    那一筆 aos-claim 自己的退出碼（寫在 exit 檔裡）= 3
  ```

**p3 沒打穿主張三**（他把時間押在主張二與第 5 條上，並且照評分表「專心打穿一個比三個都摸一下有價值」自陳這是刻意的），但他交出了一個會改變問題形狀的更正：**「外放」有兩種完全不同的形狀，而研討會只討論了其中一種。**

> （a）機制是 **driver 用 argv 叫的程式**（他的乙）；（b）機制是**批次裡的一筆 instruction**（〈壞 2〉假設的形狀）。

「〈壞 2〉『退出碼 3 會退化成某一筆的退出碼、`--loop` 從此不停』**只在（b）成立**。在（a）裡退出碼完全保留：」

```
$ timeout 5 ../kit/p3-exec --loop 20 wL3
p3-exec: refusing: .aos/inst.json.runi already exists
p3-exec --loop rc=3  （3 = 停了）
$ timeout 5 ../build/bin/aos exec --loop 20 wL3
aos exec --loop rc=3
```

「〈壞 4〉（argv 字串變成磁碟格式）也一樣：只在（b）成立。在（a）裡程式名寫在 driver 或角色表裡，`<folder>` 一個字都沒多。**使用者原話問的『全部都用 argv 去執行』有這兩種讀法，而研討會沒有分開，六個壞裡至少有兩個是（b）專屬的。**」他對甲乙的比較只給了兩格：「乙做得到甲做不到的：換彙整政策不重編、crash 現場可判定。**甲做得到乙做不到的：我沒找到。**閒置零 fork 乙加一個旗標就有。」

### 5. 仍然不知道的

- **乙案的執行語意，四位獨立地都沒做到。**四位都量了乙案的成本，四位都沒有復現 `aos exec` 真正在做的事。p1：「`$ref`/`$env`/`$opt` 解析、`parallel`、`timeout` 的兩段式 SIGTERM→SIGKILL、行程群組、`exit` 欄位回寫，這些我一樣都沒復現。乙案的成本我量了，語意我沒驗。」p3 的執行器支援 `argv`/`cwd`/`stdin`/`stdout`/`stderr`/`exit`/`env`/`timeout_ms`/`parallel` 與 `{"$opt":"merge"}`，但**不支援 `$ref`／`$env`**，並自標：「主張二的實驗裡，『執行批次』那一步不是 aos 在做。我認為這不影響結論，因為主張二問的是交接不變式——**但這是我的判斷，不是實驗證明的**。」
- **`$ref`／`$env`／`$opt` 過外部彙整器的往返沒人測。**規格第七節明講「還沒解析的指示詞必須能原樣寫回」是協定的一部分。p2 把它列為自己這輪最大的缺口：「如果 jq 版的彙整器會吃掉指示詞，那〈好 3〉『換一支程式就換掉政策』的門檻比研討會想的高得多——**外部彙整器必須是一個完整的 format 層實作，不是一支 `jq -s`**。」
- **SIGINT 的三處死亡，p4 拿不到有效資料**（背景 job 忽略 SIGINT）。p1、p2、p3 各自用別的方法測了，結果與 SIGKILL 相同。p4 要在能給前景終端機的環境裡才測得到。
- **斷電沒測**（p3）。「我的 write-ahead 有 `fsync`（含目錄 `fsync`），理論上撐得住掉電，但我沒有辦法在這台機器上驗證，所以我只敢說它撐得住 `kill -9`。」
- **相位標記順序修正之後窗口是不是真的關了，只有推理沒有實測**（p2，坑七）。同一個 race 打不中的問題。
- **`.runi` 沒有批次身分造成的具體傷害沒有做出來**（p2）。他推論出「recover 沒辦法確認搬回去的是不是當初那一批」，但沒有做出一個真的因此出錯的情境。
- **p1 的外放 aggregate 沒有被證明沒有 race。**「32 並行 60 次 0 異常只是沒觀察到；結構上它有跟 aos 一樣的 read-publish 非原子問題。我沒有設計出能穩定觸發它的實驗。」
- **`mtimeguard` 只在閒置路徑上量過**（p1）。「我沒有驗證『有貨的時候它真的會觸發、而且不會漏』。mtime 的解析度、以及『aggregate 發布 inst.json 之後 inbox 的 mtime 又變了』這個回授迴圈，我都沒有處理。**這是個 benchmark，還不是個實作。**」inotify 版「我想到了、沒做」。
- **`aos-deliver` 的並行安全沒測**（p1）：「規格說檔名帶 pid 就安全，我沒去驗這句。」**deliver 的規格形式**（argv 還是 stdin JSON 是主形式）也沒人比較過（p2 走 stdin，「因為好寫」）。
- **`insts/llm.json` 那個檔位的鎖沒測**（p3）。「`aos` 今天沒有任何子命令能對 `insts/llm.json` 做交接，argv 那層根本不存在，所以從命令列測不了。**這件事本身就是〈好 2〉的現況證據。**」
- **`link()` / `renameat2(RENAME_NOREPLACE)` 修 claim 的 TOCTOU 沒做**（p4 明說放棄；p2 的 `aos-claim` 用了 `link()`＋`unlink()` 但沒有跟 C++ 版做對照壓力測試）。
- **`kernel.json` 角色表沒人碰**（p4：「那是設計題不是實作題，這一輪我只回答能用機器回答的。」）
- **「乙多出來的能力值不值得」沒有結論**（p2 只給證據不給結論）：「因為值不值得取決於**這套協定的讀者是誰**（轉交提案第 12 條），而那題沒有人回答，我也回答不了——**那是使用者的決定，不是量得出來的**。」
- **主張三的完整情境矩陣沒人跑完**（p3 明說只做了三格；p2 做了四個情境；p4 做了六欄的比較表但只有三個版本各跑一次）。

### 那個成本數字：先問這幾個數字各自在測什麼

**等一下，這裡不是一個量的四個值，是四個不同的量。**

| 數字 | 它實際在測什麼 |
|---|---|
| **fork 27–36 µs** | 核心複製一個位址空間並回收它。**這是 primitive 的成本。** 它跟「外放一支程式」這件事幾乎無關，因為外放一定要 execve。 |
| **動態執行檔 128–151 µs** | fork ＋ execve ＋ **`ld.so` 把一支小型動態連結執行檔載起來** ＋ waitpid。大頭在動態連結，不在 fork。 |
| **`aos` 769–789 µs** | 同上，但 callee 要映射 42 MB／7 顆 `.so`、跑 4793 次 relocation，其中 32 MB 是跟交接完全無關的 `libaos_llms`。**這測的是一個連結決定，不是一個機制的成本。** |
| **python 5.49–5.72 ms** | CPython 直譯器的啟動時間。**這測的是語言選擇。** |

所以：**「一次 fork＋execve 約 1–3ms」錯在哪？不在數值，在型別。** 它被當成**機制的常數**用了兩輪，而它其實是**你決定去叫哪一支程式的參數**，跨度 68 倍（p2 的講法最準）。把一個參數當常數，任何架在它上面的比較都失效——而且失效的方向不確定：對精瘦的 binary 它高估 8–23 倍，對 python 它**低估** 2 倍。

**那它在講哪一種情況？** 它落在 `/bin/sh`（0.44 ms）與 python（5.5 ms）之間，跟 `aos <verb>`（0.79 ms）只差 1.3–3.8 倍。**換句話說，「1–3ms」大致是「一支胖的動態連結執行檔或一支輕量直譯腳本」的量級**——研討會四位心裡想的很可能就是「叫一支 `aos aggregate` 子命令」，而那一格的真值 0.79 ms 確實在 1 ms 的量級上。**他們的直覺沒有離譜，他們的錯誤在於把一個特例寫成通則，然後拿通則去論證。**

**還有一個沒人罵的錯，比這個更嚴重：分母也沒人量過。** 研討會拿一個沒量過的分子，去比一個從來沒被提出來的分母。實測的分母是 **6–9 µs**（p1 兩個獨立方法夾出 6.4／8.6；p3 7.9，他自標只有一個點支撐、可能 ±50%）。p4 的 **2.2 µs** 是一支逐系統呼叫的**複本**，不是本體，而且跟他自己的交叉驗證 8.5 µs 差四倍——**我不採用 2.2**。p2 的 **27.2 µs** 量的是另一件事（含行程進入成本，見他的講評）——**也不採用**。**採用 6–9 µs。**

於是正確的陳述是這樣，請把它帶去改規格與 roadmap：

> 一次外放的成本不是一個常數，是 **130 µs（精瘦 binary）／440 µs（`/bin/sh`）／790 µs（今天這支 `aos`）／5.5 ms（python）**。今天一個空回合是 **6–9 µs**。所以倍率是 **15×–600×**，取決於你叫誰。
> **而這個倍率有沒有關係，由 `--loop` 的週期決定**（p4）：`--loop 1`（下限，`--loop 0` 會被夾成 1）時 800 µs 讓週期從 1.0 ms 變 1.8 ms 並吃掉近半顆核心；`--loop 100` 時同一個 800 µs 是 0.8%，是雜訊。
> **而且倍率可以歸零**：閒置回合零 fork 三位獨立做到了（p2 `/proc/stat` 交錯基準線、p3 兩把儀器、p1 的 1.11 µs），代價是觸發判準必須留在裡面。

**結論：〈壞 5〉不該再被當成反對外放的理由。** 它真正說的是「不要每回合無條件 fork」和「不要用 python 寫機制」，這兩件事都是實作紀律，不是架構障礙。

### `.runi` 鎖的是「那一批」還是「那個世界」

**四個人給了四個答案，是因為這個問題問的是一件事，而他們各自答了三件不同的事。** 先把三件事分開：

- **範圍（scope）**：這把鎖保護的是哪一個資源？
- **身分（identity）**：鎖上寫著誰／哪一批佔用了它？
- **壽命（lifetime）**：它從什麼時候活到什麼時候？誰讓它結束？

p1 與 p3 答的是**範圍**；p2 答了範圍，然後指出真正缺的是**身分**；p4 答的其實是**壽命**（他的乙把外層世界鎖與內層批次鎖逼到明面上，說的是兩者**壽命不同**）。**四個人沒有互相矛盾，他們在回答三個不同的問題。** 這就是為什麼四個答案不一樣，也是為什麼研討會問了兩輪沒人答得清楚——**問題本身是欠定的。**

#### 有幾種可能的讀法

p3 的三分法是對的，我採用它，並補上被漏掉的那一維：

| 讀法 | 不變式 | 鎖名要帶什麼 | 拆得開嗎 |
|---|---|---|---|
| **L-batch（那一批）** | 對每一批 `b`，全世界最多一個執行者在跑 `b` | **批次身分** | 拆得開，多批可並行 |
| **L-slot（那個檔位）** | 對每個 instruction 檔位 `s`，最多一批在跑，且下一批不得在前一批結束前開始 | 檔位路徑 | 半拆得開 |
| **L-world（那個世界）** | `R` 成立時，`.aos` 的狀態不得被任何人改變 | 世界路徑 | 拆不開 |

#### 現在的實作實際上是哪一種

**是 L-slot，而且它連 L-slot 都沒守住。** 我逐條驗過：

1. `derive_paths()` 純粹從 instruction 檔路徑推出鎖名（`paths.runi = base + ".runi"`），**鎖名不帶任何批次身分** → **L-batch 不成立**。
2. `aggregate_instructions()` 的守衛只有 `lstat(paths.base)`（`inst.json` 在不在），**完全不看 `.runi`**；而 `run_exec_once()` 把 aggregate 排在 claim **之前** → **`R` 成立時世界照樣被改動，L-world 不成立**（p3 實驗 A1 的實測就是這件事）。
3. 連 L-slot 也漏：A1 之後同一個檔位上 `B ∧ R` 同時成立——**規格沒有定義這個狀態。**

#### 規格散文寫的是哪一種

**規格第六節同時寫了兩種，相隔十行，自相矛盾。**

- 「**`.runi` 已存在時拒絕啟動**……也不會有兩支 `aos exec` 同時跑同一個資料夾」——這是 **L-world** 的語言。
- 「**每顆 CPU 各鎖各的**：`inst.json.runi` 只鎖核心 CPU，`insts/llm.json.runi` 只鎖 LLM 那顆」——這是 **L-slot** 的語言。

**所以 p1 那條答案是錯的。** 他引用「每顆 CPU 各鎖各的」推出「鎖的是**那一批**」——但那句話區分的是 **CPU（檔位）**，不是**批次**。他的證據是檔位，他的標籤是批次。這個名字錯有後果：**如果真是 L-batch，recover 就能確認「我搬回去的這一批就是當初取走的那一批」；而實際上它不能**（p2 正確地指出這才是真正該補的東西）。p4 的「世界」則是**規格散文說的那個**，不是實作給的那個。

**給使用者的一句話：** 第 5 條要在規格裡定的不是「那一批 vs 那個世界」，是三件事各自寫一行——

> **範圍 = 檔位**（今天就是，寫下來即可）。**身分 = 目前沒有**（要補，內容雜湊就夠，否則 recover 只能賭）。**壽命 = 目前只綁在一個檔名上**（要不要升級成核心持有的租約，是提案 2 真正在問的問題）。
> 並且**刪掉或修正**「不會有兩支 `aos exec` 同時跑同一個資料夾」這句——它今天是假的。

### p1 那個「16 並行、30 次有 23 次重複執行、race 在 aggregate」

**站得住。** 我沒有跑他的實驗，我去讀了原始碼，機制逐步對得上：

1. `aggregate_instructions()` 的守衛是 `lstat(paths.base)`——N 個行程可以同時通過。
2. 每個行程 `opendir` 收件匣、把每份投遞讀進記憶體、組成 `combined`。
3. 寫 `paths.temp`（**固定名字 `inst.json.temp`，不帶 pid**），`rename` 成 `inst.json`。
4. **`remove_accepted_deliveries()` 在 `rename` 之後才跑**——所以在 P1 刪掉投遞檔之前，P2 已經把同一份內容捧在記憶體裡了。
5. P1 claim（`rename` 成 `.runi`）→ 執行 → release（`unlink .runi`）。此時 P2 的 `rename` 落地，`inst.json` **帶著同一批內容重新出現** → 再被 claim 一次 → **同一批執行第二次**。

`.runi` 保護不到這條路徑，因為 aggregate 跑在 claim **之前**且不看 `.runi`。**他的歸因也做對了**：拿掉 aggregate（事先彙整好、16 支只搶 claim）是 0/30，這是本輪最重要的一個對照組，他自己也承認第一眼差點指控錯一支程式。併發度掃描（N=2/4 乾淨、N=8 出現 2/30、N=16 是 14/30）的形狀也符合一個窗口寬度決定的 race。**成立。**

**而且它推翻的東西比他寫的多一條。** 規格第十二節有這麼一句：

> 「`.runi` 的檢查與 `rename` 之間有 TOCTOU。兩支 `aos exec` 撞在一起時第二支的 `rename` 會因為 `inst.json` 已被搬走而失敗，**所以不會重複執行**，只是退出碼與訊息不精確。」

**那個「所以不會重複執行」是假的。** 規格只推理了 claim 那一層，而重複執行從 aggregate 那一層繞過去了。這句話今天在規格裡，會讓下一個讀它的人放心地不去修。

**還有一個他沒測到、但同一段程式碼裡更嚴重的東西**：兩個彙整者同時 `write_file` 到**同一個固定的 `inst.json.temp`**，然後各自 `rename`。`rename` 是原子的，**寫入不是**——規格第六節自己在同一張表裡就是這樣替投遞辯護的（「檔名帶 pid，因為 `rename` 原子但寫入不是」），然後在下一列給彙整用了一個固定檔名。**那是一個現成的資料損毀來源，而不只是重複執行。** 我把它排進 p1 下一輪的第一項。

#### 它跟本題（外放與否）有沒有關係

**有，但不是他說的那個關係。**

- **有關的部分**：這個 bug 的**前提**是「同一個世界上有多個推進者」。今天的用法是一支 `--loop`，N=1，所以它睡著。而外放的整個世界觀就是「很多支獨立的小程式各自碰同一個世界」——**外放不會製造這個 bug，但它會把這個 bug 叫醒。** 這是「該不該外放」時必須先付掉的一筆帳。
- **無關的部分**：**外放不會修好它。** p1 自己的外放版有同一個結構性 race，只是窗口窄；他也誠實標了 0/60 是「沒觀察到」。真正的修法（aggregate 開頭加 `lstat(.runi)` 守衛、`.temp` 帶 pid 或 `O_EXCL`）**是行程內的兩行改動**。所以他從「aggregate 是唯一有正確性問題的那支」推到「所以該優先外放 aggregate」——**那一步不成立**，前提支持的是「該優先修 aggregate」。

**淨結果：這是本輪唯一一個真正的正確性 bug，它翻掉了規格的兩句話，而它給主張三的貢獻是「研討會挑錯了要擔心的東西」，不是「該外放 aggregate」。**

### 哪個坑是致命的，哪個只是麻煩

**致命的（會靜默毀掉使用者的資料，或讓結論本身不成立）：**

1. **`aggregate` 在 `R` 之下照樣吃掉收件匣，而「顯而易見的救援」會吃掉一整批**（p3 A1／A3，我從原始碼確認）。**這是今天就存在的靜默資料遺失，跟 argv 化完全無關，而轉交提案第 1 條正準備把它寫進規格。** 這是全場第一名要修的東西。
2. **不驗 schema 的外部彙整器把「隔離一份壞投遞」變成「整批無聲蒸發，連 `.bad` 都沒有」**（p2 實測，規格第六節的條文我核對過）。**這條直接決定「只外放彙整」該不該做**——它是丙的成敗所在，而今天沒有任何一份外部彙整器過得了這一關。
3. **乙在今天的二進位上不可表達**（四位獨立撞到）。這不只是不方便，它讓**本輪所有乙案的數字都變成在量鷹架**：影子世界打壞規格第四節的相對路徑基準（p2 情境 2、p4 的 `B/.cpu/e1.txt`），世界裡多出第二個 `.aos`，而 p2 的坑六證明影子世界**自己會洩漏相位**。**任何拿乙案數字去做決策的人，都在拿一個沒有人做出來過的東西的量測結果做決策。**
4. **鎖的壽命與工作的壽命脫鉤**（p4 發現、p1 與 p2 各自撞到）。殺掉驅動器，孤兒執行器把整批跑完、副作用全上磁碟，世界永遠鎖著，沒有任何活著的行程知道。**單體到不了這個狀態。** 它有解（p2 的核心租約），但那個解意味著「外放之後仍然必須有一個行程從頭活到尾」——**那正好把「純 CPU」這個想法的一半還回去了。**

**只是麻煩的：**

- **fork 的成本**。可以歸零（三位獨立做到），而且它有沒有關係由 `--loop` 週期決定。
- **`aos` 執行檔太胖（0.79 ms、42 MB、32 MB 的 `libaos_llms`）**。這是連結決定，拆得掉，不該拿來反對提案 9 的原則。
- **退出碼變成 12 個沒有人管的整數**（p1）。真的問題，但它是「寫下來」就能解的問題，不是物理限制。
- **`.temp` 固定檔名**。兩行改動。
- **`/bin/sleep` 自己是一次 fork、`set -e` 吃掉退出碼 3、`zsh` 的 `&&` 鏈、SIGINT 對背景 job 被忽略**——全部是實驗環境的坑，值得記在 NOTES 裡，不進結論。

### 哪一份回報不可信

**沒有一份是不誠實的。** 四位都主動貼出了自己跑壞的實驗、作廢的數據、以及「我沒做到」。這一輪的誠實度整體是我看過最好的，四位都拿滿分或接近滿分。

但「誠實」跟「可以拿去做決策」是兩件事。**如果現在要我從這四份裡挑一份數字不要帶走，是 p4 的成本表。** 具體是哪一點：

- **分母是複本，不是本體。** `round.c` 是逐系統呼叫複製 `run_exec_once()` 的空回合路徑，他標明了；但**整張 70×／205×／365× 的表都拿它當分母**，而他自己的交叉驗證給 8.5 µs——**差了將近四倍，而且他沒有調和**。倍率繼承了那四倍。
- **乙那一欄在量他自己的鷹架。** 802 µs 是「`aos exec` 起一個影子世界」的成本，而他自己的輸出證明那個影子世界打壞了規格第四節。
- **forensic 那一格可能在讀鷹架的痕跡**（p2 的坑六，他沒有做對應的排除）。

另外兩處我也不會原樣帶走，但問題比較小：**p1 主張三的結論**（資料支持「修」，結論寫成「搬」）與 **p2 的 27.2 µs「空回合」**（型別跟別人不同，卻拿去乘倍率）。

**這三處有一個共同形狀，值得單獨講：它們都不是量錯了，是量了一個東西然後用另一個東西的名字說出來。** 這正是研討會犯的那個錯（拿 callee 的成本當 fork 的常數），四位裡有三位在打它的同時各自犯了一次縮小版。**下一輪請每個人在貼出任何一個數字之前，先寫一行「這個數字在測什麼」。**

### 如果現在就得拍板

**先講結論：不要照研討會的建議走，因為那條建議把幾樣東西叫錯了名字。但也不要走乙。實際該做的事，有一大半跟 argv 化無關。**

#### 該外放幾支：**零到一支。上限是一支，而且是彙整。**

- **claim 與 release 留下——但理由要換掉。** 研討會的理由（「它們就是回合邊界本身」）**被 p2 的 mode c 推翻了**：出去的是機制（誰去 `rename`、誰去 `unlink`），留下的是租約（誰在那段時間裡活著），這兩件事分得開。**真正的理由是划不來**：外放它們買到的是「可以換掉一個 `rename` 和一個 `unlink`」——零個旋鈕；賣掉的是規格第四節的路徑基準、一個世界裡的第二個 `.aos`、以及一個必須有人監督的孤兒狀態。**這個交易沒有人會想做**（p4 這句話我照收）。
- **deliver：**寫，但**不要叫它「拆 `aos exec`」，也不要跟拆解綁在一起排期。** 它從 `aos exec` 裡拿出去的是**零行程式碼**；它補的是規格第十二節自陳「沒有實作」的那一步。五行 shell，今天就能寫，一次 fork 都不會多。**這是唯一無爭議的淨賺，而它跟這場辯論無關。**
- **aggregate：**它是四支裡**唯一有旋鈕的**（排序、配額、優先權、按 mtime、按時段），而且規格已經替它留好了門——`aggregate_instructions()` 在 `inst.json` 已存在時直接 `return Ok`（我在原始碼確認），所以外部彙整先跑完，內建那支自動變成 no-op，**零成本疊加**。這是本輪最漂亮的一個發現。**但今天不能做**，理由在下一段。

#### 先做哪一步（順序是重點）

1. **修 `aggregate`，今天就修，跟 argv 完全無關。**（a）開頭加一個 `lstat(.runi)` 守衛；（b）`inst.json.temp` 帶 pid 或用 `O_EXCL`。這兩行同時修掉：p3 的 A3 靜默資料遺失、p1 的重複執行 race、以及那個沒人測過的交錯寫入損毀。**在這之前不要動 `aos world recover`**——照現在的規格寫出來的 recover 會吃掉使用者的一整批投遞。
2. **修規格第六節的三句話。**（a）「所以這個不變式成立：`.runi` 存在 ⟺ 有一回合沒跑完」少了一個析取項，應該是「**或有一回合正在跑**」；（b）「也不會有兩支 `aos exec` 同時跑同一個資料夾」是假的，刪掉或改成真的；（c）第十二節那句「所以不會重複執行」是假的。**外加第 5 條：把鎖的範圍（檔位）、身分（今天沒有）、壽命（今天只綁一個檔名）分三行寫清楚。**
3. **寫 `aos deliver`。** 獨立排期，不等任何人。
4. **加崩潰現場的可判別性——今天就可以加，不必外放。** 三位獨立做出來了，而 p3 說得最準：**它跟「是不是同一個行程」完全正交。** 一份 write-ahead sidecar（receipt 放旁邊、不包進 `.runi`，這樣 `cat .runi` 仍然看得到那一批）加上「先 unlink `.runi` 再清 sidecar」的順序，就把「今天就分不出來」那個洞補掉。**成本是三個零位元組檔案。** 順帶把 p2 收出來的那條順序規則寫進規格：**「給重跑許可」的標記寫在危險動作之前，「收回許可」的標記寫在之後**——這樣每一個模糊窗口裡都沒有子行程在跑，猜錯永遠往保守的方向錯。
5. **然後——也只有到這時候——再考慮把彙整外放（丙）。** 而且要有一個前置條件，不是建議是**門檻**：**外部彙整器必須通過一組對照測試，證明它跟內建彙整在同一批投遞上產生逐位元相同的磁碟結果，包含 `.bad` 隔離、字典序、「已有未取批次就不發布」，以及規格第七節那條 `$ref`／`$env`／`$opt` 的原樣往返。** 沒有這一關，「換一支腳本就換掉政策」換到的是「把使用者的資料交給一支玩具」——p2 已經把那個代價實測出來了。
6. **不要做乙。** 理由不是成本（成本可以歸零），是**它今天不可表達**，而讓它可表達需要在 `aos exec` 上長出一個「執行這一批，但把世界基準當成那邊」的入口——那是規格第四節與第六節的修改，不是一次重構。在有人回答轉交提案第 12 條（**這套協定的讀者是誰**）之前，沒有理由付那個價。p2 說得對：**「值不值得」不是量得出來的，那是使用者的決定。**

#### 最後一句，給下一輪

研討會把「四位獨立地都提了」當成信心的來源。這一輪的證據指向相反的方向：**四位共用的 1–3ms 是錯的、四位都排第一的〈壞 1〉因果是錯的、四位收攏的主張三挑錯了名字。** 共識的寬度跟正確性沒有關係——**因為四個人共享的是同一份沒被量過的前提。** 這句話是 p1 說的，我原樣收下，並且把它反過來也用在這一輪：**這一輪四位量出來的東西，只有被兩把獨立儀器印證過的那些，我才寫進上面的裁決。**

**這是建議，不是決定。最後拍板的是使用者。**
