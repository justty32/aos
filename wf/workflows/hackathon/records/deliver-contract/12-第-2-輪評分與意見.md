## 第 2 輪評分與意見

總分（證據強度／誠實度／走了多遠／回答三個數字／路線價值，各 5 分）：Hickey persona 25、Pike persona 23、Evans persona 22、Cantrill persona 21。

### 下一輪各人要做的

- **Pike persona**：把同 target 雙 producer、rename 後失去回覆兩個 publish 接縫各列出操作序列、允許終態與不變式，驗「兩個 producer 不得都成功」與「rename 後失去回覆只能回 Unknown」；不再擴 JSON 欄位。
- **Hickey persona**：競爭測試擴成多輪，逐輪核對 `successful claims = visible ready = 1`、零覆蓋與孤兒 temp 數；補 rename 前死亡與 cleanup 失敗，明定哪些失敗保證「未發布」、哪些只能回 Unknown。
- **Cantrill persona**：做 `InstState` 對照表，逐格標「現有 API 可產生／只能第二次 parse 猜出／需要擴充 canonical type」；第二類欄位從首版契約刪掉。
- **Evans persona**：同一套 corpus 對 toy validator 與 canonical `read_all()` 逐案比對、報分叉數；用非量身訂做的 caller 檢驗刪除 `delivery` 是否失去任何可觀測能力。

### 路線判斷

- **最值得繼續**：「canonical validation＋exclusive publish＋明確輸入來源」路線（Hickey persona）。canonical probe 的 `batch_two state=Ok count=2`、`second_argv0_type state=FieldTypeMismatch error_record=2` 避免第二套合法性定義；no-replace race 的 `published_claims=1 visible_ready=1 disk_payload=A reported_winner=A` 驗到「成功」必須保持的不變式。
- **看起來漂亮、有隱藏成本**：11 欄 tagged union。只讀 `result` 仍 `same_decision=5/5`；`json_pointer/expected/actual` 不是現有 canonical error type 能給的，現在公開就得擴 canonical API 或偷偷再 parse 一次。
- **致命**：把無 ledger 的 `--key` 說成冪等保證。相同證據對應不同正確答案；reply-loss 下 caller 也不能從沒收到 stdout 推知未發布。
- **只是麻煩**：普通 rename 的靜默覆蓋、明示 `-` 多一個 token、人類診斷另做 renderer、孤兒 temp 清理——都有可測試的繞法。
- **不能當比較依據**：Evans persona 的「數字一」表（沿用前輪、加總口徑自相矛盾）；統一「每個現場各自計數，再逐欄相加」前，不能用它判 `(b)` 與 `(d)` 勝負。

### 如果現在就得拍板

第 7 題選 **(d) world＋stdin／檔案**，寫 C++ 前收緊成 `(d')`：`aos deliver WORLD (-f FILE | -)`。先完整驗 CLI grammar 才碰 stdin，相對 FILE 以 caller cwd 解；一次成功呼叫使整批恰好成為一個 ready delivery，任何回傳的拒絕或 publish 前失敗不得產生 ready。

第 8 題選 **第一版沒有 key**。`delivery` 若暫時存在只能是非持久 correlation，不得出現 `Already`、`Conflict` 或「可安全重試」的暗示；沒有 ledger 時四個位置只能可靠回答 `1/4`。

第 9 題選最接近證據的 **delivery＋count 版**，但 exit 固定為 `0=published`、`1=operational failure`、`2=rejected/usage`，細因只在 JSON 出現一次。成功首版只凍結 `count`；`delivery` 等有查詢或對帳 consumer 才取得資格；失敗只公開 canonical parser 現在能誠實產生的 `error` 與 one-based `record`，不承諾 JSON Pointer、`expected` 或 `actual`。

第一步先寫並測 **私有 Publish 原語**，不是完整 CLI：已驗證 bytes 寫入同目錄 exclusive temp，以 no-replace 語意發布，絕不覆蓋既有 ready。三個狀態分開：rename 前失敗＝NotPublished，rename 完成＝Published，rename 後尚未回覆便死亡＝caller Unknown；這三個狀態與不變式寫進測試後，才接 canonical `read_all()` 與 CLI／JSON 薄層。以上是評審建議，拍板由使用者決定。
