#### ② 真模型跑不跑得起來、哪一支，以及那四件事

**三支在這台機器上都跑得起來**（codex-cli 0.149.1 已登入、claude 2.1.246、pi 0.84.2；LM Studio `localhost:1234` 沒在跑）。四位都用 codex 跑完整條 loop，只有 p4 三支都接進 loop。

冒煙指令：

```
printf '...' | timeout 120 codex exec --json -o codex-last.txt -s read-only -C . --skip-git-repo-check -
printf '...' | timeout 120 claude -p --input-format text --output-format json --permission-mode dontAsk
printf '...' | timeout 120 pi -p --mode json --no-tools --no-session
```

`-o` 寫出的最後一則**沒有結尾換行**。

**stdin**：codex 結尾加 `-`；claude 用 `-p --input-format text`。pi：p1、p2 各有 `printf ... | pi -p ...` exit 0 的成功現場；p4 斷言「只能塞 argv」但沒有失敗現場，評委判為重測前不可採用。**待重測定案。**

**抽最後一則**：三支都有機器可讀輸出，寫法三家三種：

```
codex : jq -r 'select(.type=="item.completed" and .item.type=="agent_message") | .item.text' | tail -1
claude: jq -r '.result'
pi    : jq -r 'select(.type=="turn_end") | .message.content | map(select(.type=="text")) | last | .text'
```

codex 另可用 `-o FILE` 直接落最後一則，`--output-schema FILE` 強制最後一則符合給定的 JSON Schema。

**session id**：

| codex | claude | pi |
|---|---|---|
| JSONL 第一行 `{"type":"thread.started","thread_id":"..."}` | 同一個 JSON 物件的 `.session_id`（失敗回應也有） | JSONL 第一行 `{"type":"session","version":3,"id":"..."}` |

session id 早於答案到達，把 stdout 直接導到檔案就有收據。

**中途 kill 掉留什麼（只測了 codex）**：

- `-o` 的檔全有全無，被砍就不存在，不會讀到半截答案。
- JSONL 停在 `turn.started`，看得出「開始了、沒完成」。
- SIGINT 與 SIGKILL 留下的磁碟現場一樣，只差退出碼 1 與 137。
- 本機檔案看不出 provider 那邊有沒有計費、有沒有完成。
- provider 端的 session 完整、可 resume：`codex exec resume <thread_id> --json --skip-git-repo-check "Repeat verbatim the JSON object you returned in your previous turn..."` 能原封不動拿回被砍那輪的答案。**可靠的復原路徑是 id，不是本機檔案。** resume 不省那 15k token 的 system prompt。

claude 與 pi 的 kill 行為沒測。

**OPEN #6（golden slice 鎖哪支）沒有收斂：**

- p1：鎖 pi（`--no-tools --mode json` 最便宜、最像單純的 LLM 呼叫），保留 codex 當參考實作。但 pi 沒接進他的 loop。
- p2：鎖 codex，一則訊息一行 JSON，adapter 最短。
- p4：鎖 codex（stdin 直通、不包圍籬、信封最薄）；真正的答案可能是不用 CLI、改走 `aos llms`。第一條理由建立在未查證的「pi 不吃 stdin」上。
- p3：只有 codex 的一手資料，傾向鎖有結構化輸出的那支。
