## 規格級的發現

參賽者回報「看起來是實作與規格對不上」的 11 條，規格節次指 `docs/aos-folder.md`。每條的判定與該怎麼轉交在[評委逐條表態](15-五規格級的發現11-條逐條表態.md)。

### 一、退出碼 3 的「拒絕啟動」不是 no-op——它會先把 inbox 搬空

`run_exec.cpp` 的順序是 `aggregate → claim → execute → release`，aggregate 在 claim 前，所以 `.runi` 存在時 `aos exec` 回 3 之前，已經把 `inst.tempd/` 的投遞搬成 `inst.json`。人「跑一次看一眼」會搬動狀態。

規格：第六節〈交接協定〉「迴圈體就是『彙整 → 取件 → 執行』」、第八節〈退出碼〉「3 ＝ 拒絕啟動」，沒寫退出 3 之前會不會先彙整。

### 二、`.runi` ＋ `mv` 的恢復路徑會靜默吃掉一份已經完成的產出

四步：`aos exec` 被 kill → 孤兒完成回合並投遞產出 → 人跑 `aos exec` 看狀況，退出 3 但產出被搬進 `inst.json` → 人 `mv .runi inst.json`，產出被蓋掉（沒 warning、沒備份、退出 0）→ 再跑，重播模型呼叫、第二次付錢。p4 在真模型上走完四步。

規格：第六節「crash 之後要人來處理——這是刻意的」、第十二節〈仍然開著的〉「crash 留下的 `.runi` 要人手動清」，沒指定人該做什麼。

### 三、不變式「`.runi` 存在 ⟺ 有一回合沒跑完」在子行程活得比 parent 久的時候不成立

四位都撞到。規格第六節的不變式與第十二節〈已經被實作決定的〉「子行程各自 `setpgid` 自成一個 process group」單獨看都對，合起來矛盾：子行程活得比 parent 久時，`.runi` 在回合其實已完成時仍宣稱沒跑完。

### 四、規格沒有指定任何恢復動作，人手上僅有的兩個動作都是破壞性的

規格裡沒有 `mv .runi inst.json`，那是實測時自己補的。`mv` ＝重播＋重新計費＋截斷證據；`rm`（規格字面的「清」）＝丟掉那一批。有 LLM 的批次裡重播就是重新計費，而且 `aos exec` 回 0、沒有警告。

規格：第六節「`.runi` 已存在時拒絕啟動……要人來處理」、第八節「退出碼只回答『這個回合有沒有正常跑完』」。

### 五、`stdout` 的截斷語意與重播、與 forensic 直接互斥

`stdout`／`exit` 是「必要時建立並截斷」，任何導向固定路徑的 instruction 被重播時都會抹掉前一次的證據。

規格：第七節〈instruction 的格式〉（以 `core/inst/docs/format.md` 為準）與第六節的重播路徑。
