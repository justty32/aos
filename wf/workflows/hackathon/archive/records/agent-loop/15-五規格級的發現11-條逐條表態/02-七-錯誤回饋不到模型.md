**七（錯誤回饋不到模型）——真的，但是設計錯配，不是實作 bug。** 第六節的彙整規則在多個獨立生產者下是對的；agent loop 是單一有記憶的消費者，同一條規則變成「模型永遠不知道自己講錯話」。轉交時寫成「`.aos` 的設計前提與 agent loop 的形狀不同」，不當 bug 報。`aos agent` 該站在投遞前。

**八（批次不短路）——不是對不上，是功能請求。** 第八節明寫子行程失敗算一次完成的執行、回合照樣 0，第五節沒承諾短路。`"needs"` 放進「要加什麼」，不放進「哪裡對不上」；它是評委最想看到被做出來的東西。

**九（`$ref` 拼不了 batch）——不是對不上，不拿去改規格。** 「`$ref` 做 loop 時可能很好用」那句不在規格裡，出自本場題目書。`inst-directives.md` 明寫取回的值必須是字串、展開成多個 argv 元素是刻意否決的；實測一字不差是規格預測的行為。該保留的設計輸入是 agent loop 需要展開語意，而 `inst-directives.md` 已留門：「真的需要時，另設一個明確表達展開語意的指示詞會更誠實。」這是**新指示詞的提案**，證據是重複的批次模板。

**十（投遞檔名）——不是對不上，但規格那句話該改。** 彙整以「有沒有狀況後綴」定義收不收，`185452-0.json` 被收符合規格。該改的是第六節「檔名帶 pid」：改成「**檔名必須唯一；帶 pid 只是達成唯一的最省事做法，同一個生產者投第二次時必須再加序號**」。

**十一（投遞那一步沒有實作）——真的，但第十二節自己已寫。** 已知開口被四份資料確認；新資訊只有防碰撞 counter。強化的是優先序（有第二個生產者之前就該補），不是必要性。
