### 二、`aos agent` 該收掉什麼——有優先序的清單

排序判準：**拿掉它會不會死。** 會花錢、會靜默掉資料的排前面；只是打字多的排後面。

**P0 — 會花錢或會靜默吃掉資料的**

1. **崩潰現場的可判定性＋復原**：`aos exec` 在 fork 前落盤 running marker，加一支唯讀的 `recover`。唯一有實際金額（三份重複計費現場）、唯一世界內部寫不出來的一條：腳本裡的冪等守衛會輸給孤兒 race，marker 只有 `aos exec` 在 fork 那個時間點寫得了。這是 `aos exec` 的 C++，所以 T5「整個 loop 可以完全不含新 C++」對「跑」成立、對「救」不成立；無人看管又花錢時，救不是可選的。
2. **投遞前驗證**（`aos deliver --check` 或任何「只驗證不執行」的入口）：投遞前擋下的錯誤能餵回模型、模型自己改；投遞後才隔離成 `.bad`，loop 靜默死亡。投遞前用 `jq -e .` 驗一次就沒有 `.bad`。成本是一次 parse。

**P1 — 四位都重寫過，收掉省的是打字和打錯**

3. **`aos status --json`（含 `--loop` 的停止條件）**：`exit=0` 四種處境一個碼；sentinel 檔 aos 不認得；終止條件現在只能放在世界外的行程裡。
4. **回合模板／`aos agent step`**（「下一批要跑什麼」只寫一次）：四位都抄 2–3 次，且現有指示詞（`$ref`）解不掉。
5. **pipeline stage 的檔名生成**：真的存在，但大小取決於架構怎麼切，39 次不是普遍價碼。

**P2 — 真的重複，但繞得過或已經半解決**

6. **`aos deliver`（temp+rename＋防碰撞檔名）**：13 行誰都寫得出；真正該收的是那個 counter，因為只有讀過前人現場的人才躲得掉。規格第十二節自己就寫著投遞沒有實作。
7. **宣告式 tool registry（name → argv 的表，由 aos 查）**：自己寫會寫錯（路徑逃脫）。降到 P2 是因為 `aos tooljson` 已存在、沒人讀過；有人真的去讀之前不為這條開新規格。
8. **adapter 契約（抽最後一則＋取 session id）**：本質是廠商差異，收成「一份契約＋各家設定」，不收成子命令。寫錯會大聲壞，優先序低。
9. **`emit-context`／回程的型別**：去程有 schema、回程是手拼純文字。痛的是形狀不是錢，排最後。

**明確不要收的**

- **不要為了 LLM 往 instruction 加欄位。** 現有五個欄位包得下三家 CLI。
- **不要為了效能動 `aos exec`。**
