**p4 在這一題上跟另外三位分歧，而且他的理由是實測的。**他主張「取件完就死」不需新格式就分得出來（`exit` 檔數 = 0），但「跑到一半死」與「跑完但釋放失敗」分不出來：

```
  a) DIED AFTER CLAIM, BEFORE EXECUTION: 0/2 ran
  b) EXECUTION COMPLETED, RELEASE FAILED: 2/2 reported exit, executor released cleanly
  c) EXECUTION COMPLETED, RELEASE FAILED: 2/2 reported exit, executor released cleanly
  monolith control: rc=137 .runi=PRESENT exitfiles=1/2
```

裁決（見〈壞 1〉裁決）：殺驅動器時孤兒把整批跑完，b 與 c 是同一個世界狀態，「跑到一半死」根本沒被製造出來——這一格是換了命題。但他抓到的是真發現：**鎖的壽命跟工作的壽命脫鉤了**。「沒有便宜的解」不成立：p2 的 `flock` 租約在孤兒跑完後由核心自動放掉，判定從 `RUNNING` 轉成 `DEAD_MID_BATCH`。「取件完就死靠 exit 檔數判別」證據不足（exit 檔落在影子世界 `B/.cpu/`，可能讀到鷹架痕跡），要重測。

**順帶那題：`.runi` 鎖的是「那一批」還是「那個世界」——四位都答了，四個答案不一樣。**

| 誰 | 答案 | 依據 |
|---|---|---|
| p1 | 那一份 instruction 檔的那一批 | 規格第六節末「每顆 CPU 各鎖各的」（裁決：那句區分的是檔位不是批次，標籤錯） |
| p2 | 那個世界的那一顆 CPU 的那一個**槽** | `derive_paths()` 的 `paths.runi = base + ".runi"`，鎖名不帶批次身分。真正該補的是**批次身分**（內容雜湊就夠），否則 recover 無法確認搬回去的是當初那一批 |
| p3 | `L-slot`（那個檔位），而且連 `L-slot` 都沒守住 | 鎖名不帶批次身分 → `L-batch` 不成立；`aggregate_instructions()` 守衛只有 `lstat(inst.json)`、不看 `.runi`，而 `run_exec_once()` 把 aggregate 排在 claim 之前 → `L-world` 不成立。投遞與彙整今天就在鎖外面跑，外放它們在不變式上不付新代價 |
| p4 | 那個世界 | 乙把外層世界鎖與內層批次鎖逼到明面上，兩者壽命不同；該拆成兩個檔的是鎖，不是取件程式 |

（`derive_paths()` 在 `core/inst/src/handoff_fs.cpp`，見〈下一輪的資料包〉。完整裁決見〈`.runi` 鎖的是「那一批」還是「那個世界」〉。）
