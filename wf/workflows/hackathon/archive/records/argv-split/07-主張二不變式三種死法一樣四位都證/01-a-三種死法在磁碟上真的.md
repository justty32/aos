**（a）三種死法在磁碟上真的一模一樣——四位獨立地都證實了。**四種殺法、四種快照工具（都排除 mtime／inode，只比型別／權限／大小／內容雜湊）：p1 sha256 全為 `e24be31aaa5508e4…`；p2 六個現場（三死法 × `SIGKILL`／`SIGINT`）零差異；p3 gdb 三個精確斷點 `f92bcff06f874b16…`；p4 `0a4278ce9cd0ca88`。時間戳也救不了：`.runi` 的 mtime 是批次寫下的時刻、ctime 是 rename 的時刻，兩個都在回合開始前就凍住。

**（b）「這條不變式成立的唯一理由是同一個行程」——p1、p2、p3 三位獨立地都推翻了。**今天的單體就分不出來：

- p1 對照實驗：現有二進位、逐位元相同的批次，一個 `kill -9`（rc=137）、一個執行中把 `.aos` 改 555 讓 `unlink` 吃 EACCES（rc=1），兩邊 `.runi` 都是 `a697f32d1de87591…`。「同一個行程」只買到偵測，沒買到診斷。
- p2：規格第十二節說刪 `.runi` 失敗「那正是『有一回合沒跑完』的誠實表述」，但那時回合已跑完、副作用全做了。不變式今天就只是約定。
- p3：批次裡放一筆 `rm .aos/inst.json.runi`（任意 POSIX 命令、cwd 是 `<folder>`，今天就寫得出來），鎖就開了，兩批同時在跑：

  ```
  === P1 = aos exec（批次中間有一個 rm .aos/inst.json.runi）
    [P1 起跑 0.5s] .aos = ['inst.tempd', 'version']
  === 此時投遞 BATCH-B 並起 P2 = aos exec ===
    P2 rc=0     P1 rc=1
  === trace.txt（時間序）===
  BATCH-A step1
  BATCH-B running
  BATCH-A step2-after-2s
  ```
  外放版的三個現場跟今天的三個現場是同一個指紋：可分辨性本來就是零。

**（c）「一旦釋放交給另一支程式就分不出來」——p1、p2、p3 三位獨立地都做出了會分的版本。**

| 誰 | 做法 | 結果 |
|---|---|---|
| p1 | 驅動器整回合握 `.aos/round.lock` 的 `flock`＋只記「跑到哪一階段」的 `round.journal`；判斷程式只看磁碟 | 三個位置都分得出來（`SIGKILL`、`SIGINT`）。孤兒還活著時判「還在跑」（fd 被繼承），孤兒跑完再判得「跑到一半死」 |
| p2 | 相位標記 `inst.json.runi.claimed` → `.running` → `.ran`（各一個 `rename(2)`）＋`inst.json.lease` 的 `flock` 租約 | `DEAD_AFTER_CLAIM`（4）／`DEAD_MID_BATCH`（5）／`RAN_NOT_RELEASED`（6），三個 diff 各差一個檔名。成本：三個零位元組檔、一個空 lease 檔、每回合多三次同目錄 `rename` 與一次 `flock` |
| p3 | write-ahead：每個動作前先寫「要做」並 `fsync`，做完記「做到了」；receipt 放旁邊（`inst.json.runi.receipt`）不包進 `.runi`；釋放先 unlink `.runi` 再清 sidecar | `DIED_AFTER_CLAIM`（11）／`DIED_MID_BATCH`（12）／`DONE_NOT_RELEASED`（13）；同一支 recover 讀今天的現場 → `UNCLASSIFIABLE`，rc=1 |

鎖只需要活得跟回合一樣久，而回合正好是一個行程樹的生命期：`aos` 沒有 daemon，但有核心——號誌畫在核心的 file table 上。「取件與釋放在不同行程」與「三種現場分得出來」是兩件獨立的事。
