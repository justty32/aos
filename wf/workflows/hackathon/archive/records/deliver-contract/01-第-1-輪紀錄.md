## 第 1 輪紀錄

### 1. 各人做了什麼

四位各做一套假 `aos deliver`（未改 C++、未 build），跑人工檔案、pipe 單筆、agent batch 三個現場。路線與數字以第 2 輪為準，見 [08](08-第-2-輪紀錄.md)。

### 2. 坑的總表

四位都撞到、到第 2 輪仍成立的坑：

- **canonical batch validator 的接縫**：公開 C ABI 只有單筆 instruction parser，不能一次驗整個 array 並定位第二筆；假件能跑不等於真實作能沿用 validator。
- **aggregate 會刪掉 delivery，連帶刪掉 key 的歷史證據**：publish 前的 `.temp` 只是 attempt，不是 committed publish；aggregate 後缺 key 與內容的綁定，process 重開後缺耐久 ledger。四位都交「第一版不要使用者提供的 key」。
- **(a) 把 FILE 同時當 payload 與 world locator**：pipe 與 agent caller 只有 bytes，得各造一份檔；巢狀 `.aos` 讓同一個 FILE 推出兩個候選 world（`.../outer/inner` 與 `.../outer`）。
- **(c) 沒有第二個 target 使用者**，卻要求每次多交 `--target`；相對 target 的基準、`X` 是 CPU 名還是路徑、`X.json`／`X.tempd` 的公開形狀都沒答案。
- **rename 實驗不是 durability 證明**：no-replace、同名競爭、雙 producer 並行、file／directory fsync、斷電都沒測；普通 rename 可能覆蓋同名 ready。
- **(b) 的相對 FILE 有兩解**：`aos deliver fixtures/world one.json` 實際讀 caller cwd 的 `./one.json`，使用者可能以為是 `fixtures/world/one.json`。

測試接線的坑：`aos init` 不會建 world 資料夾，要先 `mkdir` 再 init；現有 binary 沒有 `deliver` 子命令（`unknown command 'deliver'`）。
