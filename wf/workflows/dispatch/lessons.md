# 派線踩過的坑

[dispatch](README.md)｜[WORKFLOWS](../../WORKFLOWS.md)

十一條都是實跑之後才長出來的，寫在這裡是為了**下一份交接書送出前對一次**。

## 1. 派線前的預掃要涵蓋全部組別

不能只掃「已知的那幾組」。預掃做得好可以砍掉大半工作量——逐件比對「預期檔名＋預期大小」這種便宜檢查，常常讓一條線的實際工作量掉一個數量級。

但**漏掃的那組會在收線時才爆出來**：派線當下還查不出識別碼的那一組被跳過，結果「其實早就有了」是收線核驗時才發現的。**那是預掃範圍的缺口，不是線的錯。**

**交接書要嘛把預掃做完，要嘛明寫哪幾組沒掃過。**

## 2. 線推翻交接書時要接受，不要逼它湊數

實跑後線回報「交接書寫的三個其實只有兩個，理由是……」，或「照字面搬檔會觸發整批重算，成本比預期高一個量級」——這種通常是**線對、交接書錯**。它手上有你寫交接書時沒有的實測資料。

**驗收條數寫死是為了防它亂加驗證，不是要它為了湊滿數字造假失敗案例。** 收到這種回報就改交接書，別叫它再跑一次去「補齊」。

## 3. 交接書的「背景」與「工作步驟」自相矛盾就會出事

實例：背景寫「可以直接原樣複製過去」，步驟卻寫「佈局零改動」，而實際資料有一半不符合那個佈局假設。線只好二選一，選錯就整批白做。

**送出前對照一次背景與步驟，衝突處要寫死哪個為準。**（[TEMPLATE.handoff](../TEMPLATE.handoff.md) 檔尾有這條提醒。）

## 4. 整檔改寫用單一 Update 操作，不要拆成 Delete＋Add

有些 agent 工具的 patch 機制會**拒絕**「同一路徑同時 Delete＋Add」的原子 patch。線收到拒絕後會很自然地繞路，拆成兩份獨立 patch 送出：先刪、再加。中間**該檔在工作樹上真的不存在**——實測有過二十幾秒的空窗，被另一條線掃到並回報成疑似違規刪除。

後果不只是誤報：那段空窗內線若崩潰，工作區的主入口就缺檔。檔案雖然救得回來，線仍會留下壞掉的工作樹。

這**不是線的惡意**，是工具拒絕之後的自然繞路，所以下一條線還會這樣做。禁止 `rm` 防的是 shell 的 `rm`，這一類操作會從旁邊溜過去。兩條防呆：

1. **整檔改寫一律用單一 Update 操作**（一次完成、原子）。
2. **每個批次邊界跑 `git status --short | grep -E '^(D |.D)'`，要零命中。** 成本近乎零，上面那次就是這道檢查抓到的。

## 5. 合併成功之後才刪分支

2026-08-30 收隊時跑了 `git merge --ff-only … | tail -1 && git worktree remove … && git branch -D …`：merge 被使用者未提交的改動擋下，但 `| tail` 吃掉了退出碼，鏈繼續跑把分支刪了，靠 `branch -D` 印出的 hash 才救回。

- 合併指令**單獨跑**、看完整輸出與退出碼，成功後才刪 worktree／分支。
- 主 repo 常有使用者未提交的改動：合併前先比 `git diff --name-only main <分支>` 和 `git status --short` 的交集，重疊檔只 `git stash push -- <那幾個檔>`，合併後 `stash pop`，再確認他的改動還在。

## 6. worktree 起點可能很舊

2026-08-30 一隊的 isolation worktree 建在比 main 落後 40 多個 commit 的舊點，照交接書測了一整輪已刪掉的舊程式，33 條發現全作廢（22 萬 tokens）。Agent 工具的 worktree 不保證從 main HEAD 開。
所以 worktree 隊的 prompt **第一步**：`git merge-base --is-ancestor HEAD main && git reset --hard main`，確認 `git log -1` 跟主 repo 的 main 一致才開工；收線時隊長說「停在舊 commit」就先查產出是不是對著現況做的。

## 7. 任務書要明講的幾件事（2026-09-24、09-25 踩到）

開隊前當 checklist 對一遍，每條都讓我多繞過一輪：

- **commit 署名**：Opus 隊會照它環境裡的提醒寫自己的署名行。任務書要寫「結尾兩行**一定**照抄這裡給的，不是你環境提醒裡那行」，並要它收尾前 `git log --format=%b main..HEAD` 自查。
- **真跑次數一開始就限**：寫死「各 2 次、做不完寫『留下一輪』、目標 N 分鐘內收線」。三隊同機各跑 3 次會拖到一小時以上。
- **隔離的隊碰不到主 repo**：`git worktree remove`、`branch -d`、殺主 repo 的行程要派**不隔離**的隊在主 repo 做。
- **測試別靠信箱檔名順序**：信的 id 開頭是亂數，排序不等於時間；改成「信箱裡任一封含這段字」。

並行開好幾隊時：

- **scratchpad 是共用的**：臨時檔放 scratchpad 裡自己的子資料夾，不然同名檔會被別隊蓋掉。
- **各隊切不重疊的範圍，收尾自己 `git rebase main` 再跑 lint／測試**，我就能逐隊 ff-merge、不用另派人 rebase。共用檔（SESSION-LOG、WAIT_USER、日誌、`wf-lint.sh`）指定唯一一隊能碰。
- **拆檔前先問誰讀它**：有程式直接讀某份 md（整份或某一段）的，拆了就壞；先改程式再拆。
- **使用者要關機**：叫各隊 10 分鐘內停真跑、只 commit 能過測的、報告寫「做到哪、下一輪從哪接」；沒 commit 的 worktree 檔案還在硬碟，下次派人進去撈。

## 8. 舊東西：舊設計謹慎採用，成熟元件原樣複製

兩種態度，別搞混：

- **舊原型的設計**（proto2／3／4 系列）是遺產：裡面有想清楚的東西，也有後來被推翻的。開新段先派人去撈「哪些決定還站得住」，任務書點名參考路徑、要它逐條說採不採、為什麼；不要整包照抄（使用者 2026-09-13）。
- **已經成熟的元件**（inst.json、aos-exec、`$ref` 解析這類）直接**原樣複製、只改最小差異**，不要派隊重寫，它們的既有規則也**不列待問**。2026-09-30 proto6 開工時派隊照 proto5 重寫了一套 aos_inst，plan 隊又把「`$ref` 怎麼處理」「沒 `.aos` 找什麼」列成待問，使用者很火：「直接複製過來就好了啊」「這啥鬼問題」。派 plan／審稿隊前先告訴它哪些是現成的。

## 9. 公司 WSL 只有 8 核：同時最多一條跑程式的線（2026-10-05）

同時最多**一條**會跑程式或全套測試的 codex 線，其餘只讀碼。長跑與故障注入要限 node 數並 `nice`。這次 deep-play 開 20 node×4 常駐任務，加 chaos，又有其他線同跑全套測試，load 衝到 200 以上、使用者電腦很卡，測試因時間敏感假失敗（原樣複本 359/364 也有這個因素）。

## 10. codex 的資安過濾與收尾手法（2026-10-05）

- **字眼會被擋**：codex（ChatGPT 帳號）有資安內容過濾，任務書寫「競態、/proc、kill -9、故障注入、對抗式」的線被擋（code-review 白費 13 萬、model-check 6 萬 token）。改寫成「程式品質與正確性審查」「中斷後恢復」等說法就能跑。
- **叫它收尾**：`codex exec` 跑起來後收不到訊息；要它收尾只能殺掉，再 `codex exec resume <session id> "<收尾提示>"`。resume 不吃 `-s`，唯讀要用 `-c sandbox_mode='"read-only"'`。
- **子程序會被連坐**：由 Monitor 腳本 `nohup` 起的子程序，Monitor 到期時會一起被殺；要用 `setsid`。

## 11. 會對程序群組亂送訊號的測試改動，在公司 WSL 上會把整個 WSL 弄掛（2026-10-05）

修「假綠」測試（test-review T8 系列）那條線改了共用收尾工具 `tests/_proc.py`，讓 `reap` 對程序群組反覆送 SIGKILL 直到群組變空，另外動了 subd、daemon、matrix 等測試。跑這些測試時 WSL 連續兩次整個掛掉、重開，`/tmp` 被清空。改動沒 commit，使用者說直接丟掉。**之後碰 `tests/_proc.py`、`killpg`、程序群組收尾的改動，不要在公司 WSL 上跑**；要做就在可丟棄的環境，並先檢查 pgid 不是 0、1 或測試程序自己的群組。

## 12. 「故意改壞再還原」驗證測試時，Python 可能沿用改壞版的快取（2026-10-09）

Python 只看檔案大小與修改時間（秒）判斷 `__pycache__` 是否過期。同一秒內改壞又還原、大小剛好相同，就會繼續跑改壞版的快取，測試連紅數分鐘、看起來像負載不穩（loop7 的 `test_unsure_listed`，L3 查明）。做「拿掉修法就紅」驗證時：跑測試加 `python3 -B`，或還原後 `touch` 一下該檔。

## 13. 數「有幾份全套在跑」別用 `pgrep -fc run_all.py`（2026-10-09）

它會把命令列裡含 run_all.py 的 shell、別隊的等待迴圈、把 run_all.py 當參數的程序都算進去——曾顯示 9 份、實際只有 1 份，害一隊白等 30 分鐘。改用 `ps -eo args | grep -c '^/usr/bin/python3 \(-B \)\?proto7-2/tests/run_all.py'` 這種「開頭就是那支程式」的數法；等待迴圈的比對字串別跟迴圈自己的命令列重疊。
