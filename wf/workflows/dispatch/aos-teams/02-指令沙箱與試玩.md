## 隊員怎麼開

隊員是 sol 的 agent-fsm，不走 codex CLI（使用者 11-14「不要走codex」）。掛法、任務書怎麼寫、怎麼等、怎麼驗收：[入口「3. 掛 sol 隊員」](../aos-teams.md)，完整步驟在 [kits/card](../kits/card.md)。本檔以前的 `codex exec` 指令、`/goal`、codex 沙箱旗標與 slug 表是舊隊形，不在這裡了。

權限邊界照[入口](../aos-teams.md)：不管開哪一種 agent，都不加全繞過沙箱／權限的旗標。

## 派工時的幾條

- **任務書寫一句可驗證的完成條件**，讓隊員抄進 goal（[kits/card](../kits/card.md) 第 3 步）。gpt 系愛做到一半就說做完，使用者原話：「對了，codex gpt那邊，他有一個壞習慣，就是讓他做事，他會做到一個階段就停下來說自己做完了。這需要你去設定/goal。」收回報時照完成條件逐條對，沒做完就再派一張單接著做。
- **審查／報告類產出一定要求寫進檔**（sol 寫它的 `out/`；Claude 子 agent 寫進線的工作區或任務書指定的路徑），不要只靠最後一則訊息——子 agent 的回報只有最後一輪會回到我手上，主篇曾因此遺失一次。
- 別用 `TaskOutput` 讀 Claude 子 agent 的任務（會倒整份 transcript 進 context）；等通知即可。
- **純規劃的線只寫自己的項目夾且不 commit**，由派它的人收。
- **要兩份獨立意見時，跨體系才真獨立**：一份 sol、一份 Claude 子 agent（頂層代定、可翻案）；同一個模型另開對話的兩份同源，綜合時要打折。
- 實作層級的裁決我可以代裁並寫進交接書（多條線共用的契約由我先定，才能真並行）；**方向性的留給使用者**（鐵律 5），題目寄使用者專區（[入口「2. 問使用者」](../aos-teams.md)）。
- 線遇方向題：題目寄使用者專區（`aos-user send --kind decide`，會出現在全景頁），**那一題停下來等他答**；不靠那一題的工作照做。方向題不自己代定（鐵律 5；使用者 11-15「決策鍊改回去」，原本這裡寫「不停線、自己先代定」，是從 10-09 出門時的一句轉述放大來的）。
- **任務書也寫「aos 指令不順就送意見」**（使用者 11-07 晚想法 18，[kb-ideas](../../../../proto8/thinking/2026-11/07/kb-ideas/README.md)）：派出去的 agent（Claude、sol、子 agent）用 aos 指令卡住、說明看不懂或覺得不順手時，順手 `$AOS_HOME/bin/aos-feedback add <指令> '<哪裡不順>' '<建議>' --kind usage|help|errors|args|other --score <0～1> --model <自己的模型名>` 送一筆；aos 基礎函數與標準庫的意見只收、有空再改，各線自己的工具可以當場改。格式與舒適度見 [N-68](../../../../proto8/docs/NORMS/10-基礎設施-定義與工作區/10-N-68.md)。成篇的改進意見投 [wf/advices](../../../advices/README.md)。

## Claude API 不穩時

**Claude API 不穩時，工作改派 sol**（sol 那邊被限流則反過來：改派 Claude 子 agent，Sonnet 做純文字、Opus 做程式）。使用者 2026-09-22：「claude api 目前狀況不好，改派 codex astra」——當時走 codex、型號 astra；現在一般工作的型號是 sol、走 agent-fsm。這時 sol 做調查，我做精簡總結、決策、寫規範；設計判斷仍不交給 gpt 系。

## 每段做完派人試玩（2026-09-13 起）

使用者：「每次做完一個段落都可以讓他們去玩玩看，給建議，然後我們改進。」設計者自己看不出哪裡難懂，要靠沒讀過設計筆記的人去撞。
做法：段落 commit 後開一個**只拿 README 入口**的 agent（Claude 子 agent 與 sol 各一更好），照 README 架起來、寫小程式、故意弄壞幾樣，照五條標準各打分＋舉例——**容易上手、容易理解、複雜的藏起來、外層控制結構簡單但全面、要背的少**。回報存該原型自己的 `notes/play/`（README 表一輪一列），我整理成「要改的清單」給他挑。
