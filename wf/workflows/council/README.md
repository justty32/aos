# council — 圓桌議會（多 agent 多輪討論）

← [WORKFLOWS](../../WORKFLOWS.md)｜[INDEX](../../INDEX.md)

**做什麼**：使用者出主題，**我當議長**，指揮多個 `codex exec` 實例當議員，跑**多輪討論**，
每輪由我寫出一份結論交給使用者。**只存結論，不存過程**——議員的原始發言是拋棄式的。

**這不是**開發工作流：council 不改程式、不跑 build。它的產出是**想法的收斂結果**，
談出定案後轉交 [ideas](../ideas/README.md) / `docs/` / [feature-dev](../feature-dev/README.md)。

## 角色

| 角色 | 是誰 | 職責 |
|------|------|------|
| **議長** | 我（Claude） | 立議程、指派角色、派任務書、收發言、**寫每輪結論**、向使用者回報。**不參與辯論** |
| **議員 ×3** | `codex exec` 一次性實例 | 依指派的視角發言、攻擊分歧、自陳弱點 |
| **拍板者** | 使用者 | 出主題、收議後決定採納什麼 |

議員**每輪都是新實例、無狀態**（不用 `codex exec resume`）。他們看到的「歷史」就是**結論帳**
本身——所以「只存結論」不只是收納習慣，它同時是議員的記憶模型。

**角色每題臨時指派**：開議時我依主題設計三個**真正對立**的視角，不用固定班底。
慣用的三角形是「推進派 / 保守派 / 第三軸」——例如
「模型純度 vs 實作可行性 vs 使用者實際怎麼用」。三個視角若會得出同一結論，就是指派失敗，重派。

## 一場議會怎麼跑

**預設 3 輪，中途不停**（輪數開議時可改）。跑完一次把三輪結論一起交給使用者。

0. **立題**：把使用者的主題寫成**議程書**（格式見下）。這步要使用者點頭才開議。
1. **R1 發散**：三位議員**互不見面**、平行作答，只拿到議程書＋自己的角色。
   刻意隔離，避免一開場就同調。
2. **R2 交鋒**：議員拿到議程書＋R1 結論（含**別人的濃縮立場**，標明角色）。
   本輪任務是**攻擊或補強指定的分歧項**，明文禁止重述立場。
3. **R3 收斂**：逼取捨——每位議員必須對每個分歧項給出「該選哪個、代價是什麼」，
   不准再開新戰場。
4. **收議**：我寫總結論（定案 / 未定案 / 建議下一步）進**結論帳**，三輪結論一起回報使用者。

每輪我寫的**輪結論**固定四段：**共識**、**分歧**（編號，下一輪的焦點）、**新論點**、**下輪焦點**。
最後一輪的第四段改成**待使用者拍板**。

## 議程書（我寫給議員的第一塊）

```markdown
## 議題
<一句話問句，要能被回答，不是一個名詞>

## 背景
<3–6 行。此刻的現況、為什麼現在要談>

## 判準
<拿什麼衡量好壞。沒有判準的討論會變成品味之爭>

## 範圍外
<明確不談什麼，避免議員發散到別的題目>

## 可讀資料
<repo 內相關路徑，指路用；議員可自行延伸>
```

## 議員任務書（每輪、每人一份）

任務書＝議程書 ＋ 下面這幾塊，寫成一個檔丟 stdin：

```markdown
## 你的角色
<角色名>：<這個視角在意什麼、為什麼由你來扛>

## 目前結論帳
<前幾輪的輪結論原文；R1 時寫「本輪為第一輪，無前情」>

## 本輪任務
<R1：獨立作答；R2：攻擊分歧 #n；R3：對每個分歧項給取捨>

## 硬規則
- 唯讀：可以讀這個 repo 的任何檔，**不要改任何檔、不要跑 build / ctest**。
- 繁體中文，**400 字以內**。超過會被截。
- 照下面格式輸出，不要加開場白與收尾客套。

## 輸出格式
**立場**：<一句話>
**理由**：<最多 3 點，每點附證據——repo 路徑或明確推理>
**最強反駁**：<針對他人立場或本輪指定分歧>
**我可能錯在哪**：<自陳一個弱點。空著視為未完成任務>
**一句話結論**：<能直接被抄進結論帳的一句>
```

固定格式是為了讓我彙整時**不必猜**；「我可能錯在哪」是防止議員變成單方面推銷。

## 指令形態（已實測）

```bash
codex exec -s read-only -C /home/lorkhan/repo/simple_tools/aos \
  -o <scratchpad>/r1-member1.md - < <scratchpad>/r1-member1.brief.md
```

- **平行**：同一輪三位議員在同一個訊息裡一起發，不要一個一個等。
- **`-o` 只寫最後發言**，乾淨可直接讀；stdout 那些事件不用管。
- **`-`＋stdin**：任務書當檔案餵進去，比塞進 argv 可靠（長文、換行、引號都不會出事）。
- **逾時**：每位議員包一層 `timeout 600`。有人掛掉或吐空檔，就在輪結論裡**明寫少了誰**，
  用剩下兩位繼續——不要靜默略過。
- **拋棄式檔案**：任務書與原始發言全部放 session 的 scratchpad，**不進 repo**。

## 結論帳

- 落點：`records/<議題-kebab>.md`，**一個議題一個檔、追加式**。
- 檔頭記：議題、開議日期（絕對日期）、已跑輪數、狀態（進行中／已收議／已轉交）。
- 檔身：每輪一節（照上面四段），最後一節是總結論。
- **同一議題再開議**＝在同一個檔追加新的輪次，議員讀得到全部前情。
- 定案後**轉交** ideas / docs，這裡改留一行指標——不留兩份真相。

## 踩坑

- **未登入的 github copilot MCP** 會在 stderr 噴一行 `AuthRequired` ERROR。**無害**：
  結論一律從 `-o` 的檔案讀，stderr 不看。`-c 'mcp_servers={}'` **擋不掉**（2026-08-24 實測，
  MCP 照連照噴），不要浪費時間在這上面。
- **read-only sandbox 會讓議員被現有實作綁住想像**。談「應該長怎樣」而不是
  「現在長怎樣」的題目時，在硬規則裡補一句「現有實作只是參考，可以主張推翻」。
- **三個角色講出同一套話**＝角色指派失敗，不是共識。重派角色再跑那一輪。
