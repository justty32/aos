# 協作流程的收穫（含失敗處）

**這篇是給誰的**：要從零重寫這套系統的人——但講的不是系統，是**怎麼跟 AI 一起把它做出來**。
上一輪（分支 `roadmap-run`，2026-08-28 至 08-29，凍結於 `5b74b47`）在兩天內產出 202 個檔、
+18,326 行，其中程式碼約 7,900 行、**其餘一萬多行是文件**。

使用者結束這條分支時說的是：

> 「像這樣一改再改，實在浪費 token，不如全部打掉重來，這才是 agent 的正確方法。」

**所以這一篇必須誠實。** 先講哪些做法真的有用、值得原樣帶走，再講哪裡開始走歪，以及下次
從零開始該怎麼開場。

---

## 一、真的有用的四件事

### 1. 動手前的兩道閘門（spec → plan → do）

一件有份量的事**真的開始寫之前**，先過兩份要使用者點頭的文件：

- **spec**：要做成什麼樣（**結果狀態，不是動作清單**）／驗收條件（**可機械檢查的那種**）／
  **明確不做什麼**（防膨脹）／**先裁的決定**（動工前必須拍板的問題，逐條列）。
- **plan**：步驟（**每步一個可停下的檢查點**）／動哪些檔／每步怎麼驗／風險與退路。

規則兩條，很硬：**沒點頭就不寫下一份、不碰程式**；**spec 只講「什麼」、plan 只講「怎麼」
——spec 裡出現檔名與步驟就是越界**。使用者說「這份我不看了，你直接做」＝他放棄該閘門，
記一行在文件開頭，照樣往下走。

**為什麼值得帶走**：`明確不做什麼` 和 `先裁的決定` 這兩欄是整個機制的價值所在。前者擋住
範圍膨脹，後者把「AI 會自己湊合的地方」提前攤到人面前。實測有效——最後一輪的實作隊碰到
規格衝突時真的停下來記進報告請主線覆核，而不是自己決定。

> **原文**：`roadmap-run:wf/workflows/build-cycle/README.md`（4 KB，可以直接抄）。

### 2. 對抗驗證隊：獨立、隔離、只准打不准修

在「build 成功、ctest 4/4 全綠」之後，另外開一隊去**故意撞它**：收件匣塞異常檔案、在檔案
系統步驟中斷、同時啟動多支執行者、自寫 LD_PRELOAD 攔截 syscall。結果是 **28 條發現、
57 支攻擊腳本**。

**這是整條分支唯一真正產生新知識的環節。** 那條「修好一個 bug 讓另一個 bug 現形、重複執行
率從 9.8% 升到 37% 再降到 0–1%」的發現（見[踩過的坑](02-踩過的坑.md)第一節），
**只跑 ctest 是永遠看不到的**。

四個做法值得原樣抄：

- **在獨立的 git worktree 裡跑，結束時 `git status --porcelain` 必須為空**。審查隊不改任何
  東西，包括不改測試。
- **「打了但沒有問題的」也要全部列出來——那也是證據**。報告裡那張表有三十幾列（900 次並發
  投遞零碰撞、1100 筆交錯零遺失零重複、真 ENOSPC、5000 筆批次、100 萬層巢狀……）。沒有這張
  表，讀者無法分辨「沒查」和「查過沒事」。
- **誠實列出「審查沒覆蓋到的角落」**：真正的斷電沒測、tmpfs 的 fsync 是 no-op、退階路徑一次
  都沒被自然走到、pid 重用只是估算。**這一節比發現清單更值錢。**
- **把最有價值的攻擊腳本轉成 ctest**，而且**要驗過「在修補前的執行檔上真的會紅」**——一個
  沒紅過的回歸測試不知道自己在守什麼。實際轉了四支。

> **原文**：`roadmap-run:wf/workflows/build-cycle/archive/m1-loop-side/review/report.md`
> （77 KB，**挑著讀**：§0 總結、§3 兩張驗證表、§4 沒覆蓋到的角落、§5 需主線裁決的三件事、
> §6.2.3 那條併發數字）；腳本在同目錄 `review/scripts/`。

### 3. 給使用者的白話版（digest）

跟 AI 做事最貴的隱形成本是：**使用者不可能讀完 AI 產出的東西**。做法是每隔一段時間產出一批
「十分鐘追進度」的短文——每篇標「這篇講什麼／幾分鐘」，導航頁寫「只有十分鐘就讀 1 和 3」
「第 4 篇是唯一需要你動作的一篇」。

**寫得好的關鍵是不用術語重講一次技術文件**，而是換一個角度：不是「§D-6 加了 swept 欄」，
而是「**全新的工作被當成舊垃圾丟掉**」。

而且它會**逼出矛盾**：寫 digest 的人發現進度日誌摘要寫「3 處刻意設計不修」、詳細報告的處置
表寫「4 條」——**這是重述時才會發現的錯**。

> **原文**：`roadmap-run:wf/workflows/digest/2026-08-28/`（五篇，語感可以直接參考）。

### 4. 動工前把假設寫成可機械檢查的清單

有一階段的實作 plan 在**前一階段還沒收工時**就寫好了。它的第零節列了 **16 條對前一階段落地
結果的假設**，每條配「**怎麼核**」（一行 `grep` 或 `ls`）與「**不符的話影響哪裡**」。前一
階段收工當天逐條打勾。做法很便宜、而且真的抓到東西——核對報告列了六件 plan 沒假設到、但會
碰到的事。

> **原文**：`roadmap-run:wf/workflows/build-cycle/m3-roster/plan.md` 第零節 ＋ 同目錄
> `m2-assumptions-check.md`。

## 二、哪裡開始走歪的

### 走歪的起點：立法跑在實作前面太遠

這條分支的第一階段叫「**立法**」——零 C++，只寫一份 41 KB 的規範性規格。第二階段才開始實作。

**問題出在順序**：規格是在「知道會撞到什麼」**之前**寫的。於是——

- 實作完，審查挖出 28 條，其中**六條要改規格**（提交點的射程、去重的閘門、命名文法、刪投遞
  的時機、發布的排他性、耐久性的範圍）。
- 更糟的是**規格自己長出了一套處理落差的機制**：條款要標 `(planned, <階段>)`、要維護一份
  「已知未決」附錄、實作完要回頭「摘標」。審查抓到的第一條文件缺陷就是「**11 處 `planned`
  標記殘留，而這 11 條全部已實作**」，導致「**帶著標記的條款現在反而是最準的**」。

**那套三向標記機制不是解方，是症狀。** 它存在的唯一理由是：立法與實作被拆成兩個階段，於是
永遠有一段時間規格在說謊，而且需要一整套簿記來追蹤它在哪裡說謊。

### 第二個症狀：一個裁決要同步四到七個地方

一件事落地要同步：`docs/SPEC.md`（條款）→ `ideas/verdicts.md`（判例索引）→ 對應的
`ideas/<主題>.md`（原始討論）→ `common/gotchas.md`（症狀速查）→ `common/code-map/*.md`
（逐檔職責）→ `roadmap.md`（進度）→ `SESSION-LOG.md`（活狀態）。

每一處都有存在的理由，分層也很漂亮（法典 vs 判例、是什麼 vs 為什麼）。**但這就是「一改再改
浪費 token」的機械成因**：改一行程式碼的行為，要動七個檔。

**而且它真的漂了。** 這一包在核對時抓到四處：

- **同一個數字在三份文件裡是 35%，在原始報告裡是 37.0%**（而且 8.7% 那個對照組是別台負載下
  量的）——摘要轉述時失真，然後被抄進規格條款。
- **報告 §6.2.3 說某個補法「已實作並實測」，同一份報告的 §6.4 說它「沒有實作也沒有量過」**
  ——後半是加寫 §6.2.3 時忘了更新的殘留。
- **實作報告寫某個測試檔有 8 案，實際數是 9 案。**
- 進度日誌說「3 處刻意設計不修」，處置表說「4 條」。

**四份真相，沒有一份是機器可讀的，也沒有任何驗證器。** 分支上規劃過一支 `aos check` 來消滅
漂移，**但那支程式沒有寫**。

### 第三：規劃的深度沒有跟實作的把握度匹配

最後一個階段產出了一份 **87 KB 的實作 plan** ＋ 一份 spec ＋ 一份假設核對報告，**一行程式碼
都沒寫**，然後整條分支凍結。那份 plan 的品質很高（36 項待裁清單，每項附建議案、替代案、
理由）。**但它是純浪費**——它建立在一個沒有發生的未來上。

### 第四：設計討論跑在實作之前太遠

動工之前先跑了**十輪設計拷問**，產出一份 22 KB 的裁決總表。實作開始之後：

- 「回合歷史加在 loop」被後來的一條判準蓋過去，改判給「系統 inst」——而系統 inst 需要的注入
  機制**到凍結為止都沒做**，所以回合歷史今天無家可歸。
- 「跨資料夾排程屬哪一層」直接被**裁掉**（歸 OS 層）。
- 一條實測結論被**更正**——現行程式碼早就不是那樣了，討論打的是一個已經不存在的版本。

**十輪拷問裡真正站住的，是那些帶著實測數字的條目**；純推演的那些，一半在碰到程式碼時被
推翻或改判。

## 三、多隊模式：什麼活能外包，什麼不能

工作模式是：一個調度者只派隊不動手；每隊一個隊長（強模型）＋若干隊員（`codex exec`）。
隊長寫任務書、審 diff、跑測試、commit；**隊員不 commit**。

| 這種活外包給隊員 | 這種活不要外包 |
|---|---|
| 有明確素材、明確產出格式、明確驗收標準（「把這 77 KB 濃縮成一篇，逐條標驗證來源」） | 需要判斷「哪些重要」的活 |
| 逐檔同步文件、code map | 決定要不要改規格條款 |
| 寫測試、跑壓力腳本 | 決定一個發現該修還是該過帳 |

**三條血的教訓**：

1. **任務書要自給自足**。隊員是冷啟動的，沒有你的上下文。背景、素材路徑、讀者設定、硬規則
   全部要寫進去——這一包的任務書每份 5–9 KB，比產出還長，值得。
2. **隊員很容易「照抄素材」**。任務書要明講「**要濃縮、要標驗證來源、要獨立可讀**」，而且
   **隊長收到稿子後要自己核對事實**（數字、路徑、hash），不要照單全收。這一輪抽驗了每個被
   引用的測試案例名與檔案路徑，全部真實存在——但也**因此才發現素材本身有四處自相矛盾**。
   **核對是有產出的，不只是防呆。**
3. **報告類產出一定要落檔進 repo**，不要只留在最後一則訊息或暫存區——agent 的回報只有最後
   一輪會回到調度者手上，**主篇曾因此遺失過一次**。

## 四、下次從零開始該怎麼開場

以下是根據上面那些帳目給的建議，**不是規則**。

**1. 先做出一個會跑的最小東西，再立法。** 把順序倒過來：**規格的角色是「把已經站住的行為
釘住」，不是「先想清楚再做」**。一份在實作前寫的 41 KB 規格，有六條會被第一次認真的對抗
驗證改掉，而且中間那段時間它在說謊。具體一點：先做出「投遞一份 JSON、跑掉、看到結果」這條
最短的路，**用它跑通一次真實的用例**，再回頭把已經站住的部分寫成條款。

**2. 每個結論只有一個家。** 不要「法典 ＋ 判例 ＋ 症狀速查 ＋ 逐檔職責 ＋ 進度 ＋ 活狀態」
六份。分層很美，但**沒有驗證器的多份真相一定會漂**，而且漂了沒人知道。如果一定要多份，
**先寫那支驗證器**——這條分支就是把它排在最後，然後永遠沒排到。

**3. 對抗驗證提前，而且不要只跑單元測試。** 這條分支唯一真正產生新知識的是審查隊，而它發生
在**一整個階段做完之後**。把它提前：每做完一塊會動到檔案系統或並行的東西，就**立刻**用壓力
腳本打一次（並發 K 支、200 回合、量重複執行率與遺失率）。**ctest 全綠不代表什麼**——那條
37% 的重複執行率，是在 ctest 4/4 全綠、165 個案例全過的情況下量出來的。

**4. 規劃的深度要跟「下一步真的會發生嗎」匹配。** 87 KB 的 plan 只在它真的會被執行時才有
價值。**規劃到「下一步能不能開始」為止就好**，除非那個階段明天就動工。

**5. 記裁決時，把反向代價一起記。** 這條分支最貴的一個 bug，根因是一個**被正確記錄下來的
取捨**（選內容導出的 id 以避開名冊）——正向理由記了，**反向代價（分不出殘留與重投）沒記**，
後來變成一條每天都會踩到的靜默資料遺失。**記裁決時要多問一句：「它還會把什麼東西當成
相同／當成不同？」**

**6. 保留 digest，而且更早開始。** 使用者不會讀技術文件。每一批工作結束就產一份白話版，
**用換角度的方式重講**。它同時是給使用者的、也是一次免費的一致性檢查。

## 五、最後：這套流程真正的失敗處

不是任何單一環節做壞了。**每一個環節單看都是對的**——閘門是對的、審查是對的、把裁決記回
索引是對的、code map 同步是對的、白話版是對的。

**問題是它們相乘。**

一次「改一行程式碼的行為」的完整代價變成：改程式 → 改測試 → 改 code map → 改 gotchas →
改 SPEC 條款 → 改 verdicts 判例 → 改 ideas 原始討論 → 改 roadmap → 改進度日誌 →（下一批）
改 digest。**十處。** 而且每一處都有一個好理由。

這就是「一改再改實在浪費 token」的真正形狀：**不是改錯太多次，是每一次改的成本被流程放大了
十倍。**

**所以下次從零開始，最該先決定的不是架構，是「一次改動要付多少代價」。**
先把那個數字壓下來，再開始寫程式。
