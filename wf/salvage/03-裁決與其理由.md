# 裁決與其理由

## 這份文件在保存什麼

`aos` 把資料夾當世界、`.aos/` 當指令區；`aos exec <資料夾>` 只推進這個世界
一回合，一回合是一整批 JSON 指令。`roadmap-run` 做完 M0→M2 後凍結，系統將從零
重寫。這裡不要求沿用舊選擇，只要求推翻時也明白自己推翻了什麼。

以下路徑全在 `roadmap-run`。「SPEC」＝`docs/SPEC.md`（當時唯一 normative 規格）；
「verdicts」＝`wf/workflows/ideas/verdicts.md`；「M1 審查」＝
`wf/workflows/build-cycle/archive/m1-loop-side/review/report.md`；「M2 報告」＝
`wf/workflows/build-cycle/archive/m2-loop-project/implementation-report.md`；「keep」＝
`wf/workflows/ideas/call-format/keep.md`；「debts」＝`wf/workflows/ideas/machine-shape/debts.md`。
報告補實作證據，不高於 SPEC。

## 刻意的設計：看起來像 bug，但不是疏漏

1. **PATH 搜尋可能回 126，不回 shell 的 127。** PATH 沒有可執行檔、卻有同名目錄或
   不可執行候選時，`spawn_prep.cpp` 會記 `saw_eacces` 而回 126；專案刻意不追 127。
   （證據：M1 審查 §6.1 A 隊-1；`core/inst/src/spawn_prep.cpp`；測試
   `execute reports a non-executable PATH candidate as 126` 正面斷言 126。）

2. **`kill(-pid, …)` 失敗刻意不往上傳。** M1 時 `exec.cpp` 三處皆忽略，理由是讓錯誤
   路徑極簡；若失敗是 `EPERM` 而非無害的 `ESRCH`，後面可能永久等在 `waitpid`。
   M2 後收斂為 `signal_child_group()` 一處忽略；**`EPERM` 沒有驗過**。（證據：
   M1 審查 §6.1 A 隊-2；凍結末端 `core/inst/src/exec.cpp`。）

3. **C API 失敗後的 `errno` 可能被解構子 `close()` 蓋掉。** API 回讀寫錯誤時，
   呼叫者可能拿到後來的 `errno`。`capi.md` 承諾保留原失敗，`OwnedFd` 解構卻直接
   `close()`；落差已知且裁不修。**雙重失敗沒有驗過**。（證據：M1 審查 §6.1
   A 隊-3；`core/inst/src/capi_io.cpp`、`core/inst/docs/capi.md` 「讀寫」。報告 #24 是另一處。）

4. **逾時輪詢自己出錯就 return，不 kill、不 reap。** 時鐘或非阻塞收屍失敗時，
   子行程可繼續跑並留 zombie。M1 裁不修；M2 只把 `wait_until()` 搬到
   `core/loop/src/deadline.cpp`。**失敗分支沒有驗過**。（證據：M1 審查 §6.1
   A 隊-4；M2 報告 S6；凍結末端上述原始碼。）

5. **嚴解析，鬆執行。** 格式層嚴驗型別與 schema；合法 `inst_t` 到執行層就不多做
   語意審查。邊界在序列化層，不是 exec 漏驗。（證據：SPEC §C-1；verdicts A 表。）

6. **未知 key 硬失敗。** 舊執行檔遇新欄位回 `UnknownKey`，不會半理解還繼續跑。
   （證據：SPEC §C-5、§C-6；keep。）

7. **不設輸入上限。** 位元組、`argv`、`env`、JSON 深度皆無上界；不把猜的常數寫成法，
   界線交給 `ulimit`/cgroup/`ARG_MAX`。代價是深層 JSON 可爆堆疊，不可直接吃不可信輸入。
   （證據：SPEC §C-7；keep；`core/inst/docs/capi.md`；未見耗盡實測。）

8. **`aos exec` 退出碼不反映子行程成敗。** `/bin/false` 回 1，但 aos 做完回合就回 0；
   個別結果讀 `exit` 檔。（證據：SPEC §D-9；M2 報告 §3.1 明載 non-zero 造成的
   `failed`/`partial` 仍回 0。）

9. **整批 decode 失敗也刪 `.runi`。** 診斷留 stderr，壞批消失，不留現場等修。
   （證據：SPEC §D-7 明標「刻意取捨」。）

10. **`failed` 不計入十次停機。** 壞批是使用者問題，不是機器壞掉；它會退避，
    但不累加 `machine_failed`。（證據：SPEC §G-5；測試
    `a batch that keeps failing never stops the loop` 連跑 13 圈不停。）

11. **空回合是第三種圈。** 它睡基數，既不累積也不重置退避；空閒不是故障。
    （證據：SPEC §G-3 窮舉表；M2 報告 §3.3。）

12. **control inbox 刻意不對稱。** `.aos/control.tempd/` 裡的記錄逐筆消化、不彙整、
    沒有 `.runi`、沒有取件鎖；`.aos/control.json` 必須不存在。這段條文就是為了
    擋住「順手照 inst 推導路徑」的重構。（怎麼知道：SPEC §D-1、§G-7。）

13. **`.bad` 不自動刪。** 隔離後留給人或未來的 `aos recover`；crash 現場一貫由人處理。
    （證據：SPEC §D-8；verdicts A 表。`aos recover` 在凍結點未實作。）

14. **exec 是凍結的矽。** fork/exec 機制不再長新機制，演化只在指令內容與外圈；
    所以 exec 永遠不認批 header，`$ref` 也不擴成「取一筆 inst 來執行」。
    （怎麼知道：SPEC §A-6、§C-8、§C-9；verdicts A 表「§22 凍結的矽」。）

前四條會被外部審查工具反覆當成 bug。重寫可以推翻它們，但要連錯誤路徑的
複雜度、無人收屍與相容性一起重裁，不要當成原作者沒看到。

## 關鍵裁決：為什麼機器長成這樣

### loop 不是「放所有外圈功能」的框

歸 loop 的充要條件是「必須在沒有 inst 可跑時運作」。窮舉表只有 claim/fetch、
decode/execute 調度、writeback、睡眠／退避、控制視窗、崩潰偵測；衝突時表優先，
表外做系統 inst。因此跨資料夾排程歸 OS，`aos exec` 只推進這一個資料夾；doorbell 歸
loop；回合歷史歸系統 inst。（證據：SPEC §A-7 窮舉表與推論；verdicts A 表 §25。）

### 控制面也走投遞協定

控制機器與對它下指令同構，所以不另開 signal/pid 檔，而在回合間掃 inbox；沒指令
可跑時仍要叫得停。（證據：SPEC §A-8、§G-7；verdicts A 表 §26。）

### 內容導出的批 id，以及必須連反向代價一起記的教訓

批 id 選「排序投遞檔名＋內容」的 64-bit FNV-1a，因為隨機 id 需要已留 v2 的 manifest。
反向代價後來才補記：內容 id 分不出崩潰殘留與同名同內容重投。

審查 #1 量到新投遞被刪、未執行、回 0、無 stderr、`turn` 不動：靜默遺失。header
加 `swept` 後把去重限於清理未完，卻暴露併發雙重彙整：tmpfs K=2 重複率由 9.8%
升到 37.0%；再加來源查核後九跑為 0–1%、`LOST` 全 0，仍非 exactly-once。教訓是裁決
要連「還會把什麼當相同」一起記。（證據：SPEC §C-8、§D-4、§D-6；M1 審查 §0 #1、
§6.2–§6.2.3。）

### `timeout_ms` 是語意搬遷，不是欄位搬遷

`timeout_ms` 留在 v1 schema、不 bump，但計時與砍行程改由 loop 擁有。兩個已釋出
`execute` API 簽名不變，語意卻改為等子行程自行結束，是 API 行為變更。（證據：
SPEC §C-3、§F-1、§G-6；M2 報告 S6、§3.4；`test_capi.c` 與 `test_exec_status.cpp` 各一案。）

### `--loop 0` 照實立法成 1 ms

`0` 會 warning 並視為 1 ms，不忙輪詢；當時刻意不再發明 `kFloor` 常數。持續庫層失敗時
1、2、4…256 ms 退避，十次後約 0.5 秒就停機。（證據：SPEC §G-4、§G-5；M2 報告 §6.4；
測試 `exec loop zero interval no longer busy polls startup failures` 斷言回 4 與行數。）

## 欠帳，不是待辦

下列不是排程清單，也不代表當時已有解法；它們是數個已裁決選擇相乘後，重寫仍得
面對的系統性缺口。

- **兩顆 CPU 共寫一份記憶體，卻沒有記憶體模型。** LLM CPU 照 GPU 模型異步寫回
  同一資料夾，process CPU 可能同時推進它；目前沒有 barrier、happens-before、
  coherence 或結果去重，`.temp` 只保護 `.aos/` 投遞，不保護一般結果寫回。
  （怎麼知道：verdicts C 表第 1 條；debts §1。未實作、未驗證。）

- **沒有中斷線。** 異步結果回來時世界不會自己知道，只能在每回合塞輪詢 inst。
  doorbell 的歸屬已裁為回合層，因為它必須在回合之間醒著；這只裁歸屬，沒有實作。
  （怎麼知道：SPEC §A-7 推論②；verdicts C 表第 2 條；`debts.md` §3。）

- **git 會撞上 `.aos/` 的暫態。** 政策已定：`.runi`、`.temp`、`.tempd/`、`.bad`
  不進 git，`version` 與 `turn` 要進，`inst.json`/header 由使用者選。但回滾語意
  沒有因此解掉：回滾到含 `inst.json` 的 commit 就會重演舊回合。
  （怎麼知道：SPEC §E-3、§E-4；verdicts C 表第 3 條；`debts.md` §2。）

- **回合歷史與「彙整層注入策略」都沒有做。** 回合歷史已裁為系統 inst，不准寫成
  loop C++；但系統 inst 要如何被注入彙整層仍無機制。所以 loop 崩潰後，人手上只有
  `.runi`，沒有死因。header `result` 只記「這批的下場」，而且下一次彙整會覆寫
  sidecar，保存期很短，不是歷史。（怎麼知道：SPEC §A-7 的「代價認列」，
  §G-2 對 header 保存期的說明；verdicts A 表「回合歷史」。凍結點未實作。）

重寫若改了基本裁決，欠帳也要重新推導；舊實作被捨棄不等於問題消失。
