# 已驗證的規格結論

aos 把資料夾當機器，一般檔案是世界狀態，`.aos/` 是指令區。每回合取一整批 JSON instruction，整批跑完才讓程式計數器前進。

這是凍結分支 `roadmap-run` 的結果。原文見 `roadmap-run:docs/SPEC.md`；**已驗**表示有 ctest、攻擊腳本或實跑，**未驗**表示只有條文、讀碼或沒觸及真實故障。
佐證見 `roadmap-run:wf/workflows/build-cycle/archive/m1-loop-side/review/report.md`、`roadmap-run:wf/workflows/build-cycle/archive/m2-loop-project/implementation-report.md` 與 `roadmap-run:wf/workflows/ideas/verdicts.md`。

## 1. `.aos/` 是什麼樣子

**命名。** `<名字>.<副檔名>.<狀況>`；副檔名有 `.json`、`.d`、投遞匣 `.tempd`，狀況封閉為 `.temp` 生成中、`.runi` 運行中、`.bad` 已隔離。三個既有例外：`version`、`turn` 無副檔名，`insts/` 沒叫 `insts.d/`（§B-1～§B-2）。**已驗**：M1 實跑 `.temp`/`.bad`/異物；ctest `#7 ...never overwrites...bad`、`#10 ...warns about .json names...`。**未驗**：「新狀況字要修憲」是維護規則，runtime 無法證明。

```text
.aos/
  version  turn  turn.temp  .gitignore
  inst.json  inst.json.runi  inst-<pid>-<seq>.json.temp
  inst-head.json  inst-head-<pid>-<seq>.json.temp
  inst.tempd/  control.tempd/  insts/
```

`aos init` 建新世界；舊世界缺 `.gitignore`/`turn`/`control.tempd/` 不拒絕，後兩者當 `0`/空匣。**已驗**：init/舊世界 ctest、M2 `ls .aos`。**未驗**：`insts/` 第二 CPU 只有 `llm-head.json` 庫層案；CLI 無入口，未端到端驗交接。

`turn` 是 PC：init 寫 `0\n`，release 後遞增。版面為 `1`；缺/不認得 `version` 就拒絕，turn/header/control 不 bump（§B-3～§B-4）。**已驗**：`exec can consume two consecutive rounds` 量到 `0→1→2`；缺 turn 會建成 `1`、version 仍 `1`；版本七種異常均回 1。

## 2. 真正的指令是一整批

一回合＝一批，單筆只是 slot（§A-1）。檔案是完整 JSON 物件/陣列，`[]` 合法、JSON Lines 不合法，讀到 EOF 才解析（§C-2）。整批先全數驗證與 resolve，任一失敗就全不跑（§A-2）。**已驗**：`read_all` 的陣列/atomic/JSON Lines 三案；`exec claims the complete input...` 以壞的第二筆證明第一筆未產生 marker。

同批無資料流：`$ref` 在任一 slot 執行前已求值，依賴必須跨回合（§A-3）。`parallel:true` 只讓批內重疊，仍要 join 全批（§A-5）。**已驗**：A-3 來自第九輪實測/讀碼，M1 §4(10) 未重打 A 區；A-5 有 `exec starts the next record...`、`exec joins parallel records...`。

四階段規範用語是 **fetch → decode → execute → writeback**：彙整/取件、讀批/resolve、執行、寫結果/release/推 turn（§G-1）。**已驗**：M2 將四相分檔，並有整批拒絕、resolve、writeback 案；**未驗**：無故障注入逐相證明邊界。

## 3. header 與 handoff

`inst-head.json` 五欄：`version`=1；`origin` 為 `aggregated`/`direct`；彙整寫 `result:null`、`swept:false`，刪光來源並 fsync dir 後改 `true`。只有未 swept（缺欄也算）才以 `id` 去重；已 swept 不擋新重投。exec 不讀 header（§C-8）。**已驗**：五欄案、`#1` 連投/未 swept/已 swept 三案；grep exec 零命中。

交接的三步是（§D-1）：

```text
deliver:   <name>.json.temp       --rename--> inst.tempd/<name>.json
aggregate: inst-<pid>-<seq>.json.temp --rename--> inst.json  (排他)
claim:     inst.json              --rename--> inst.json.runi
release:   unlink inst.json.runi  (不是第四次 rename)
```

- 投遞名 `<pid>-<seq>`、用 `RENAME_NOREPLACE`；deliver 走唯一 parser、寫 canonical JSON、回單行 JSON，不自建 inbox（§D-2～§D-3）。**已驗**：50 並發共 **900** 次，零遺失/撞名/`.temp`；`test_run_deliver.cpp` 覆蓋連投、canonical、空批、壞參數。**未驗**：真 pid 重用未跑到（`pid_max=4194304`）。
- 彙整只收無狀況後綴，無順序保證；壞件改 `.bad`，`inst.json` 已在就不覆蓋。只在發布/空批/去重完成後刪投遞。發布前重查來源；有一份消失就不發布/清理/寫 header（§D-4）。**已驗**：彙整/隔離 ctest；`conc.sh` 每組 200 回合，K=2/3/4 重複率由 37.0/49.5/51.3% 降到 **0–1%**，9 次 `LOST` 全 0。**未驗**：查核到 rename 仍有競態，不是 exactly-once。
- 耐久順序：批 temp+fsync → header temp+fsync → rename header（提交點）→ fsync dir → 排他 rename 批 → fsync dir → 刪投遞 → fsync dir → `swept:true`；claim/release 後也 fsync dir（§D-5）。**已驗**：LD_PRELOAD trace 順序一致；ext4 `RenameFailed` 200/200→0/200。**未驗**：未真斷電；tmpfs 的 fsync 是 no-op；claim/release 只讀 diff。`link+unlink` 未自然走到，只有未獨立重跑的 `scripts/fault.c` 注入證據。
- 批 id 是排序後「檔名＋內容」的 64-bit FNV-1a（16 hex）。未 swept 且 id 同時，sibling temp 必須與 canonical 批逐 bit 同才 roll-forward；只保證整組殘留，不保證混新件（§D-6）。**已驗**：header 4 案＋手工 5 種崩潰狀態；殘留混新件實跑 OLD 再跑、NEW 未被吃，符合明示邊界。
- `.runi` 表示回合未完；正常返回就刪（含壞批/slot 失敗）；已有就回 3（§D-7）。`.bad` 不自刪，歸人/`recover`（§D-8）。**已驗**：`exec removes runi after a library-level failure`、`exec refuses an existing runi...`；`.bad` 三輪仍在且不再讀。**未驗**：真斷電必留 runi 未驗。

## 4. 退出碼的分界

分界只問「**aos 自己有沒有把這一步做完**」，不映射子行程的 exit（§D-9）。

| 碼 | 意義 |
|---:|---|
| 0 | 這步完成；包含無批、子行程非零/找不到/重導失敗/逾時、壞投遞已隔離、deliver 空批 |
| 1 | aos 自己跑不動或收不了尾；世界/header/handoff/decode/exit 寫檔/turn 失敗等 |
| 2 | CLI 用法錯，且必須在碰檔案系統前判定 |
| 3 | exec 發現 `.runi` 已存在 |
| 4 | 只限 `exec --loop`：連續 10 次 `machine_failed` 停機 |

**已驗**：M1 S9 將 0～3 的 12 種失敗各跑一次；M2 `test_backoff.cpp`/`test_loop.cpp` 均拿到 4。碼 1 **不等於回合沒發生**：壞 turn 案已產生效果並 release，僅 turn 遞增失敗，仍回 1。

## 5. `result`、節流與控制面

header `result` 的四值依回傳值分層（§G-2）：

| 值 | 判準 |
|---|---|
| `ok` | 整批推進且 slot 全成功 |
| `partial` | 有成功、有失敗 |
| `failed` | 批內容整體失敗：decode 失敗或 slot 全失敗 |
| `machine_failed` | 世界、handoff、fork/waitpid、寫 exit、release/turn 等機器本身失敗 |

彙整先寫 `null`，共五態。逾時是成功 slot；fetch 到 `[]` 是 `ok`。writeback 在 execute 後、release 前；先比 header id，不同只 warning。**已驗**：`test_writeback.cpp` 六案產生四值、`null`、id 不符不寫；outcome 案釘住壞 JSON/機制壞/空批；4 個 timeout 案。`deliver []` 在彙整層消化、不發布；`inst.json=[]` 才會 fetch 並推 turn，兩案不矛盾。

節流只看有沒有進展（§G-3）：

| 圈 | 結果 | 睡眠／狀態 |
|---|---|---|
| 有進展 | `ok` / `partial` | 不睡，重置退避與機器失敗計數 |
| 空回合 | 沒取到批 | 睡基數；退避不增也不清，計數不變 |
| 無進展 | `failed` / `machine_failed` | 睡當前退避並遞增；只後者加機器失敗計數 |

退避從 `--loop` 間隔起、倍率 2、上限 `max(interval,60000)` ms。**已驗**：`test_backoff.cpp` 6 個純計算案覆蓋三種圈、重置、上限與10次停機，另有 2 個端到端案；持續失敗的批跑 13 圈不會被當機器失敗停機。**未驗**：修補後 `--loop` 長跑與非 tmpfs 的長期時序沒做。

`.aos/control.tempd/` 收 `{"op":"stop"}`（§G-7）；先 `.temp` 再 rename，不彙整、無 `.runi`。loop 在回合間掃；`stop` 先 unlink，回合完後回 0。壞記錄/陌生 op 改 `.bad`、warning、繼續；是 at-least-once。**已驗**：tip 的 `test_control.cpp` 9 案，含邊界 stop、消費、壞/op/撞名、多份、舊世界；另有煙霧。**未驗**：讀 stop 到 unlink 間崩潰及 unlink/readdir 故障未注入。

## 證據邊界與素材衝突

- M1 報告 §6.2.3 說來源查核已實作並量到 0–1%，SPEC §D-4 也已入法；§6.4(9) 卻說「未實作、未量」。本篇依有實測表的 §6.2.3；後者應是殘留。
- M2 報告寫 `test_control.cpp` **8** 案，tip 實檔有 **9** 個 `TEST_CASE`；以實檔為準。
- SPEC §G-2 把 release/turn 失敗列為 `machine_failed`，卻要在 release **前**寫 result，當下無法知道後續失敗；需重新裁決。
- SPEC §D-4 寫 `8.7%→35%`；審查表為 8.7%（舊基線）、9.8%（同機）、37.0%（補前）。本篇用表值。
