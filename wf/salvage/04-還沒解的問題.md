# 還沒解的問題

**這篇是給誰的**：要從零重寫這套系統的人。上一輪（分支 `roadmap-run`，凍結於 `5b74b47`）
做完了指令執行器與回合機，但下面這些**從頭到尾沒有被解決**。

**寫這篇的用意不是交待待辦清單**，而是：**重寫的時候不要以為這些已經解決了**，也不要在
同樣的地方重新發現一次「這裡沒有答案」。

**系統的模型**（三句話）：一個資料夾＝一個世界，`.aos/` 是它的指令區；外部生產者投遞 JSON
指令，執行器把投遞彙整成一批、取件、fork/exec 跑掉整批、釋放。一回合＝一整批。
另外**規劃中還有第二顆 CPU**（一個常駐的 LLM daemon），用同一個資料夾協定跟第一顆交換
工作——**那顆從未動工**，下面很多問題都繞著它。

---

## 一、唯一一條寫進規格「已知未決」的

**SIGINT 之後從斷點繼續，跟 `.runi` 的語意互相矛盾——哪一邊改，從頭到尾沒有拍板。**

- 驗收條件那邊要的是：Ctrl-C 之後從斷點繼續。
- 協定那邊定的是：`.runi` 存在 ⟺ 有一回合沒跑完；`.runi` 已存在就拒絕啟動。
- 實測：**單次** `aos exec` 被 SIGINT 中止會留下 `.runi`，下一次固定拒絕啟動；人工搬回去
  只能**重播整批**，而外部作用可能已經做過了。（`--loop` 模式的優雅收尾是好的，問題只出
  在單次呼叫。）

M2 做的 `stop` 走的是控制記錄收件匣，**完全沒有碰訊號語意**，所以這條原封不動。

> **怎麼知道的**：`docs/SPEC.md` 末尾「已知未決」第 1 條（也是唯一剩下的一條）；
> 原始實測在 `wf/workflows/experiments/t5-agent-loop.md`（2026-08-25）。

**要先想清楚的**：一個「被中斷的回合」到底該留下什麼？只留一個鎖檔，等於把所有恢復責任
丟給人。真正要的可能是「這一批跑到第幾筆、哪幾筆的副作用已經發生」——**而那需要回合歷史，
而回合歷史也沒有做**（見第三節）。

## 二、兩顆 CPU 的欠帳：沒有記憶體模型，也沒有中斷線

這兩條的性質跟其他問題不同：**它們是使用者已下的裁決兩兩相乘產生的**，單看每個裁決都
沒問題。所以它們不是待辦，是**已經產生的欠帳**。

### 沒有記憶體模型

裁決是：LLM CPU 是常駐 daemon，工作**投遞到外部資料夾、好了寫回來**，「類似 CPU 與 GPU
的交流」。那是**非同步**的——它在 process CPU 的回合**之外**繼續跑，然後在某個時刻**寫回
同一個資料夾**。

於是：**兩個獨立執行單元同時寫同一份記憶體，而這台機器沒有記憶體模型。** 沒有 barrier、
沒有 happens-before、沒有 coherence——真實多核心架構裡最貴的那份規格，這裡完全空白。

三個會咬人的地方：

- 「資料夾 state N ＋ 指令 → state N+1」這個核心式子失效：有**兩個**推進者，「state N」是
  誰的 N？兩顆 CPU 的回合編號之間**沒有定義任何關係**。
- LLM 寫回來時 process CPU 可能正在跑：一筆指令可能讀到寫到一半的結果檔，或讀到舊值後被
  覆寫。**現有的 `.temp` 兩步發布只保護投遞區，不保護結果寫回。**
- 沒有 id 就沒有去重：daemon 因為網路重試而重送結果時認不出來。

**不需要完整的記憶體模型，但至少要有一句話說明兩顆 CPU 的寫入如何排序。** 那句話不存在。

### 沒有中斷線

GPU 模型定了 LLM CPU 把結果**寫回外部資料夾**。那麼——**世界怎麼知道結果回來了？**

目前答案是：**不知道**，除非下一批裡有一筆指令主動去看。於是**每一個非同步結果都需要一筆
對應的輪詢指令**，N 個外掛 CPU 就是 N 筆輪詢指令，每回合都跑，不管有沒有東西回來。

真實的 CPU 與 GPU 之間有中斷、doorbell、completion queue。這裡搬了 mailbox，**沒搬通知
機制**。歸屬**已經裁了**（doorbell 必須在回合**之間**醒著＝真硬體，所以歸回合層），
但**只裁歸屬、沒有要求實作**，而實作從未開始。

> **怎麼知道的**：`wf/workflows/ideas/machine-shape/debts.md` 第 1、3 節；歸屬的裁決在
> `docs/SPEC.md` §A-7 推論②。

## 三、回合歷史沒有做——所以崩潰之後沒有任何線索

原本想把回合歷史做進回合層。後來被一條判準蓋過去了：**一件事歸回合層的充要條件是「它必須
在沒有任何 inst 可跑的時刻運作」**——回合歷史不符合，所以它**歸「系統 inst」**（用這台機器
自己的指令集來寫系統軟體）。

裁決本身是漂亮的。**代價是實作卡住了**：系統 inst 需要一個「彙整層注入策略」——把系統自己
的指令注入到每一批裡的機制。**那個機制從頭到尾沒有做。**

於是分支凍結時的實際狀態是：

- **回合層崩潰之後，人手上只有一個 `.runi`，沒有它為什麼死的資訊。**
- header 的 `result` 欄只補上了「這一批的下場」一格，而**那份 sidecar 下一輪彙整就會被覆蓋，
  保存期很短**。

**同一個機制卡住的還有跨資料夾排程。** 歸屬也裁了（屬 OS 層，`aos exec` 的介面 MUST 是
「推進**這一個**資料夾」），做法也定了（做成系統 inst）——但注入機制不存在，所以**「同時
管很多個世界」在這套系統裡今天沒有地方可以住**。規格上它有歸屬，工程上它無家可歸。
**這一條要當成未解問題，不要當成已解。**

> **怎麼知道的**：`wf/workflows/roadmap.md` M2 那節末尾「留給後面階段的一行」；判準與代價
> 認列在 `docs/SPEC.md` §A-7。

## 四、四項「存貨」——第二顆 CPU 被它們擋住

這四項是十輪設計拷問停打時剩下的，使用者**明確表示還沒想好**，所以動第二顆 CPU 之前必須
先解。**沒有一項有草案。**

1. **序列化格式**。裁過「晚點再說」。屆時要打的是：數字精度、串流解析、`inst.json` 過大時
   嚴格解析的攻擊面。
2. **外層契約**。**唯一一個會反噬基石的題目**：一旦外層有型別與回傳值，`fork`/`exec` 這個
   原語可能退化成單純的啟動器。
3. **LLM CPU 那顆 daemon 的形狀**：投遞什麼、怎麼組批、讀哪些文件當 context。十輪拷問
   **全在打 process CPU 這半邊**，這邊連草圖都沒有。
4. **匯聚是 lib 還是 inst**：原語若真能承載任何東西，匯聚為什麼是注入式的 lib？
   「一句話就能裁，裁了就是原語的邊界宣告」——但那句話沒被說出來。

> **怎麼知道的**：`wf/workflows/roadmap.md` 的「M4 第二顆 CPU（閘門後）」節。

## 五、規格層面仍然開著的

| 開著的問題 | 為什麼還沒解 |

| **外層契約會反噬基石** | 同上一節的存貨 2，使用者還沒想好 |
| **`.aos` 版面需要第二個軸** | events／status 不是 `inst.json` 的「狀況」，塞不進 `<名字>.<副檔名>.<狀況>` 這個文法。今天的命名標準沒有位置放它們 |

## 六、已知但刻意過帳到後面階段的（然後那些階段沒有發生）

這四條**確認存在**，當時刻意不修（硬補會做出一個之後要拆掉的半套），排到後面的階段——
而那些階段隨著分支凍結一起作廢了。**它們現在是純粹的已知缺陷。**

1. **`.aos/turn`（機器的 PC）壞掉之後救不回來。** 內容不是「十進位整數＋LF」時每一輪都回
   錯誤碼，但**批次其實照跑、`.runi` 照刪、副作用照發生**——世界不會停，只是 PC 永遠凍在
   原地，而且沒有任何指令能把它修好（手改檔案除外）。
2. **退出碼 1 不代表「這一回合沒有發生」。** PC 的遞增排在釋放成功**之後**，所以遞增失敗
   那一趟，`.runi` 已刪、批次已跑完、副作用已落地，只有 PC 沒動。規格用文字擋住了這個誤讀，
   **但沒有任何機制能把 PC 補回去**。
3. **被反覆一次性叫起來的 `aos exec` 不受停機保護。** 退避與失敗計數都住在 `--loop` 的迴圈
   裡；用 cron／systemd timer／多個 agent 各自呼叫的話，**單次 `aos exec` 沒有跨呼叫的記憶**，
   一個持續失敗的世界會被全速重打。
4. **`.runi` 不是一把鎖**（取件是 check-then-act）。詳見[踩過的坑](02-踩過的坑.md)第四節。

> **怎麼知道的**：`wf/workflows/common/gotchas.md` 的「M1 審查交棒」節，四條逐條列著
> 「確認存在但刻意不在本階段修」以及各自綁到哪一階段。

## 七、實作隊留給主線、但沒人裁的

最後一輪實作報告末尾留了四個問題給主線，**分支凍結時全部沒有回覆**：

1. 一條驗收條件的機械檢查（grep 要零筆）與規格的文件義務（MUST 在文件中明寫替代 API）
   **正面衝突**，兩者不可能同時滿足。實作隊自己判斷把檢查收斂到程式碼層級，請主線覆核
   ——沒有人覆核。
2. **`partial` 這個值的判準有一個可見的後果**：把「子行程回非零」算成 slot 失敗，是讓四個值
   都活著的唯一讀法；但這代表**一個穩態就是「每輪都回非零」的世界**（例如一個沒事做就
   `exit 1` 的輪詢器）**會被判成失敗 ⇒ 無進展 ⇒ 退避到上限**。
3. SIGINT 那條（本篇第一節）原樣保留，等使用者親裁。
4. `--loop 0` 照實立法成 1 毫秒是**刻意選了較弱的法**。實測尺度：遇到持續性庫層失敗時，
   十次停機只花約 0.5 秒（1+2+…+256 毫秒），比 `--loop 200` 的容忍度低很多。

**另外還有一條是打撈時新發現的規格內部張力**：規格把「釋放失敗、`turn` 遞增失敗」列為
`machine_failed`，卻同時要求 `result` **在釋放之前**寫回 header——所以這兩種失敗**永遠不可能
被記進 header**。退避用的是回合層自己算出的狀態、不讀 header，所以行為上沒錯，但條款自身
需要重裁。

> **怎麼知道的**：`wf/workflows/build-cycle/archive/m2-loop-project/implementation-report.md`
> 第六節；最後一條是本次打撈核對 `docs/SPEC.md` §G-2 時發現的。

## 一句話總結

**這套系統把「process CPU 這半邊」做得相當紮實，另外半邊（第二顆 CPU、兩者之間的記憶體
語意與通知機制）連草圖都沒有。** 重寫的時候如果目標仍然是「兩顆 CPU 共用一個資料夾」，
**先把第二節那兩條想清楚再動手**——它們不是可以邊做邊補的細節，它們決定第一顆 CPU 的協定
該長什麼樣。
