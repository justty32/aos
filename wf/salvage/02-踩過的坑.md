# 踩過的坑

**這篇是給誰的**：要從零重寫這套系統的人。下面每一條都是在 `roadmap-run` 分支上**真的
撞到過**的，不是設想出來的風險清單。

**這套系統長什麼樣**（三句話）：一個資料夾＝一個世界，世界裡的 `.aos/` 是它的指令區；
外部生產者把 JSON 指令**投遞**進 `.aos/inst.tempd/`，`aos exec` 把投遞**彙整**成一批
`inst.json`、**取件**（rename 成 `inst.json.runi`）之後 fork/exec 跑掉整批，跑完**釋放**
（unlink）。整個協定就是**三次 rename ＋ 一次 unlink ＋ 一個計數器檔**。沒有常駐狀態、
沒有資料庫、沒有鎖服務——**所有的並行正確性都押在檔案系統的原子性上**。下面大半的坑都
出在那個押注。

---

## 一、最貴的那條：修好一個 bug 讓另一個 bug 現形

`aos exec` 用一個 header sidecar（`.aos/inst-head.json`）記住「上一批是誰」，在崩潰之後
不要把同一批發布兩次。批的 `id` 是**內容導出**的（對排序後的「投遞檔名＋內容」做 FNV-1a
摘要）——選內容導出而不是隨機 id，是為了避開「隨機 id 需要一份名冊」的設計負擔。

1. **原始行為**：那個 header id **永不失效**。於是「同一組檔名＋同樣內容」的**全新投遞**
   會被去重誤判成崩潰殘留——投遞被刪、什麼都不跑、`turn` 不動、**退出碼 0、stderr 一個字
   都沒有**。從外面看跟「沒事可做」完全一樣（審查 #1）。不需要崩潰、不需要併發，固定檔名
   的生產者每天都會踩到。
2. **修法**：header 加第五欄 `swept`——投遞清乾淨並落盤之後標 `true`，**只有未 swept 的
   header 才啟用去重**。殘留的定義本來就是「sweep 沒完成」。
3. **修完之後，併發重複執行率不降反升。** 同機同時段，tmpfs 上兩支併發、200 回合的重複
   執行率從 **9.8%** 跳到 **37.0%**。原因：修補前擋住併發雙重彙整的**不是任何設計**，
   是那個永不失效的陳舊 header——慢半拍的彙整者讀到前一支剛寫的 header、id 一樣、去重命中、
   於是不發布。**那正是 #1 的 bug 本體。** 把它關掉，這條路就一併開了。
4. **真正的修法**：提交點之前加一道**發布前的來源查核**——發布之前再 `lstat` 一次本輪收下
   的投遞，少了任何一份就乾淨放棄。它涵蓋得到主要窗口，因為協定順序固定：**清投遞必定在
   標 `swept` 之前**。同樣的實驗回到 **0.0–1.0%**，九次跑動裡批次遺失全是 0。

| 200 回合 × K 支併發（tmpfs） | 修補前對照 | 只加 `swept` | 再加來源查核 |
|---|---|---|---|
| K=2 | 9.8% | 37.0% | 0.0 / 0.0 / 0.0% |
| K=3 | 14.8% | 49.5% | 0.0 / 1.0 / 1.0% |
| K=4 | 13.2% | 51.3% | 0.5 / 0.0 / 0.0% |

> **怎麼知道的**：`roadmap-run:wf/workflows/build-cycle/archive/m1-loop-side/review/report.md`
> **§6.2 與 §6.2.3**，腳本在同目錄 `review/scripts/conc.sh`。§6.2.1 有一段**確定性重現**
> （兩趟 `aos exec`、五行 shell），不必併發就能看到 `run.log` 從 1 行變 2 行。
>
> **數字口徑要小心**：`docs/SPEC.md` §D-4、`wf/workflows/common/gotchas.md` 與
> `wf/SESSION-LOG.md` 都寫成「由 **8.7%** 升到 **35%**」。8.7% 是**第一階段在 loadavg 7–13
> 的機器上**量的基準線，37.0% 是**當天同機同時段**量的；35% 這個數字在報告裡不存在。
> **以報告 §6.2 的表為準。**

**三個帶得走的教訓**：

- **一個 bug 意外扮演的保護，從來不是設計，只是巧合。** 修掉它讓真正的缺口現形是好事。
- **只跑單元測試看不到這種事。** 修補當下 ctest 4/4 全綠、165 個案例全過。
- **裁決要連反向代價一起記。** 「選內容導出的 id 以避開名冊」的正向理由當初有記，
  「內容導出的 id 分不出殘留與重投」這個反向代價沒記——後來它變成每天都踩得到的資料遺失。

## 二、無聲故障（在 agent loop 裡最貴）

高嚴重度五條裡有三條是 **rc=0 且零診斷輸出**。人手跑一次程式，卡住或紅字至少會叫人停下；
一個 loop 看到回 0、stderr 空，會把「資料被丟掉」「世界卡死」「副作用重播」全部當成正常
空回合，繼續排下一步。

| 症狀 | 機制 |
|---|---|
| 投遞被清掉、什麼都沒跑 | 上一節的 #1 |
| 投遞無限堆積、`turn` 永遠不動 | `.aos/inst.json` 是**斷掉的 symlink**：彙整用 `lstat`（成功）、取件用 `open`（ENOENT），兩層對「存在」的定義不一致，夾出一個規格沒定義的第三態（#25） |
| 同一批**每回合重跑一次、永無止境** | 「header 寫失敗」與「投遞刪失敗」**分開看都只是可容忍的降級**，疊在一起就是無上限的副作用重播；而且兩者高度相關（同一個唯讀／異常的 `.aos` 會同時觸發，#26） |
| 整台機器永久卡死、六個行程疊著 | 收件匣裡一根 **FIFO**：`open()` 對沒有寫端的 FIFO **無限阻塞**，而且發生在取件之前——鎖沒拿到、stderr 一個字都沒有（#3）。修法是讀之前先 `stat` 驗 `S_ISREG`，非普通檔跳過並出聲，**不隔離**（它不是「內容無效」） |

> **怎麼知道的**：審查報告 §0 與 §1 的 #1／#3／#25／#26；四條都有 CLI 端到端回歸測試
> （`core/loop/tests/test_handoff_regression.cpp`），且都驗過「在修補前的執行檔上真的會紅」。
> FIFO 那案**自帶 `alarm` 看門狗**——退回阻塞就砍行程，而不是掛住 CI。這寫法值得抄。

**兩個教訓**：**兩層程式對「檔案存在嗎」用了不同的 syscall，就會夾出一個規格沒有定義的
狀態**（`lstat` / `stat` / `open` / `access` 各有各的答案）；以及**任何從外部可寫的目錄，
讀之前都要驗檔案型別**——`opendir` 給你名字，不給你保證。

## 三、耐久性：rename 是原子的，內容不是

**整個 `core/inst/src/` 一開始沒有任何 `fsync`。** `rename` 只保證目錄項原子替換，不保證
內容落地。崩潰之後可能留下一個已改名、內容零長度的 `.runi`——而「`.runi` 保留現場」正是
崩潰之後的全部指望。正確順序是**寫檔 → `fsync(fd)` → `rename` → `fsync(dir_fd)`**。

補完之後又發現射程不夠：耐久性只做在「彙整」那一段，**取件的 rename 與釋放的 unlink 完全
沒有**。釋放那邊只是「剛好」被計數器遞增時的 `fsync(.aos)` 順帶救到——而計數器後來就搬到
別的層去了。**這種「靠隔壁的副作用救到」的正確性最危險：搬家的人不會知道自己順手拆掉了
一個保證。**

> **怎麼知道的**：審查 #2／#5／#12／#15／#17，證據是**自寫的 LD_PRELOAD syscall 攔截器**
> （`review/scripts/trace.c`，那台機器沒有 strace／ltrace）——彙整八步的 syscall 序列與
> 規格**一字不差**。
>
> **但這一族全部「無自動化證明」**：驗證 fsync 需要的正是斷電，而測試世界建在 `/tmp`
> （tmpfs），**tmpfs 的 fsync 是 no-op**。報告誠實地把證明欄寫成「讀 commit diff 確認」。
> 真正的斷電（dm-flakey／VM 硬切電）**從頭到尾沒測過**。

## 四、`.runi` 不是一把鎖

取件是 `lstat(runi)` → `read_file(base)` → `rename(base, runi)`。POSIX `rename()` **靜默
覆蓋**目的檔——原子，但**不互斥**。互斥全靠前面那個 `lstat`，是 check-then-act；而且讀檔
在 rename **之前**，所以兩支同時進來會讀到同一份再各自 rename。要互斥得用 `link()` /
`renameat2(RENAME_NOREPLACE)` / `open(O_CREAT|O_EXCL)`。

**這條到分支凍結為止都沒修。** 它造成重複執行的大半被別的東西關掉了（發布路徑改成排他
＋ 發布前來源查核），剩下的 0–1% 才是這條本體。**發布排他與取件互斥是兩件事**——不要把
其中一個當成另一個的解。

## 五、隔離（`.bad`）的三個坑

- **合法但一時讀不到的投遞被貼 `.bad` 永久出局**（#8）：一次暫時性的 EACCES／EIO 就把有效
  工作踢出佇列。`.bad` 的定義是**內容**無效，所以讀取失敗應該只記 issue、**留在原地**下一輪
  再試。
- **第二份同名的壞投遞把第一份 `.bad` 的證據無聲蓋掉**（#7）：隔離也走 rename，也會靜默
  覆蓋。改成排他 rename，撞名就換唯一名。**覆寫等同刪除。**
- **檔名含第二個點的投遞被永久靜默忽略**（#10）：`2026-08-28.report.json` 這種第三方很自然
  會產的名字，既不收也不隔離也不警告。程式用**第一個**點切副檔名，註解讀起來卻是**最後一個**。
  修法刻意**沒有改「收的集合」**（避免行為漂移），只讓它出聲。

**教訓**：**「靜默忽略」是最糟的第三種處置。** 收或不收都行，但一定要出聲——生產者沒有
任何辦法發現自己的檔名不被接受。

## 六、回合層（loop）那一圈的三條

共通點：**它們都不是崩潰，是穩態下的持續錯誤行為**，所以測試很難抓。

- **`--loop 0` 是忙碌輪詢**，而 `--loop 0` 是當時文件裡**唯一示範的用法**。（後來發現實作
  其實早就是「warn ＋視為 1 毫秒」，只有文件沒跟上——**文件和實作各自漂了一段時間，沒有人
  發現**。）
- **失敗算「有做事」，於是關掉唯一的節流閥**。原判準是「這一圈有沒有取到批次」；一批永遠
  跑不成的指令會被判成「有做事」，於是不睡、全速重試。修法是改看「有沒有**進展**」，並且
  **把「空回合」獨立成第三種圈**——空閒不是故障，它睡基數，既不累積退避也不重置。
- **loop 忽略除「已被鎖住」以外的所有回傳值**。fork bomb 式的失敗會**滿速無聲自我惡化**。
  修法是先把回傳值**分層**成「回合層自己壞了」與「批次內容壞了」，只對前者計數、連續 10 次
  停機；後者**刻意不計數**（一批指令永遠跑不成是使用者的問題）。

> **怎麼知道的**：`wf/workflows/ideas/machine-shape/loop.md` 第 13／14／15／20／21 條的實測，
> 以及 `wf/workflows/common/gotchas.md` 的「使用 aos」節。三條都在 M2 修掉了。

**教訓**：**「有沒有做事」和「有沒有進展」是兩個判準，混用它們會關掉節流。** 而且退避的
三種圈（有進展／空閒／無進展）必須**窮舉**——只分兩種一定有一種行為是錯的。

## 七、雜項，但每一條都真的發生過

- **停機訊息印出「原因：成功」**——要印最後一次的 errno，但那種失敗沒有 errno，
  `strerror(0)` 就是 `Success`。**沒有 errno 就不要印 errno。**
- **一個測試在跟時序賭而它會過**：「跑 300 ms 後送訊號、斷言退出碼 0」，而十次失敗的累計
  退避是 511 ms——300 ms 剛好落在停機之前。改寫成斷言「退出碼與 stderr 行數恰好 12 行」。
- **時序測試不要用 `sleep` 佈置**：要測「控制記錄在回合**中途**進來」，解法是**讓被執行的
  批次自己在執行期間投那份記錄**——完全確定性。**這技巧值得直接抄走。**
- **`link`+`unlink` 退階路徑謊報失敗**（#11）：`link` 成功、收尾 `unlink` 失敗時回報整體
  失敗，但目的檔**已經在收件匣裡了**——生產者重投就真的多一份。**部分成功要回成功 ＋ 把
  殘留錯誤放進側通道。**
- **去重命中時，一份毫無關係的暫存殘骸被扶正並執行**（#21）：原本只檢查「解析得出非空批次」。
  **要逐位元比對本輪重算的內容，而且錨要靠內容認身分、不靠檔名。**

## 建置與工具鏈

- **私有相依會偷偷變成使用者的義務**：`PRIVATE` 會在 `INTERFACE_LINK_LIBRARIES` 留下
  `$<LINK_ONLY:dep>`，匯出後使用者就得先找得到 `dep`——即使它是 header-only、即使符號全被
  hidden 蓋掉。而且**外部消費測試沒有清掉套件管理器的環境變數等於白測**：有它在的話，本來會
  失敗的相依問題會被悄悄補上。這條就是這樣漏掉的。
- **批次改文件用非貪婪正則可能吃掉整段**：`.*?` 配上 `DOTALL`，終止字串在後面又出現一次就會
  一路吃過去。真的發生過——一份 code map 被砍掉 130 行還 commit 進去了，因為當時只 `grep`
  關鍵字確認「殘留清乾淨」，沒看檔案剩幾行。**`grep` 只能證明某段不在，不能證明別的還在。**
