# salvage — `roadmap-run` 打撈包

**這包是給誰的**：**要從零重寫 aos 這套系統的人（或 agent）**。假設你什麼都不知道、
沒讀過任何一行舊程式碼、也不打算去讀那條舊分支。

**這包是什麼**：一條跑了兩天、做完 M0→M2 然後被使用者叫停的分支，**留下的教訓與已驗證的
結論**。不是程式碼、不是可以照抄的藍圖，是「**下次不要在同一個地方跌倒**」。

---

## 那條分支發生了什麼

`aos` 的想法是：**把一個資料夾當成一台機器**。資料夾＝一個世界，裡面的 `.aos/` 是它的指令
區；外部生產者把 JSON 指令**投遞**進去，一支 `aos exec` 把投遞**彙整**成一批、**取件**、
fork/exec 跑掉整批、**釋放**。一回合＝一整批。沒有常駐狀態，世界完全躺在檔案系統上。

分支 `roadmap-run` 在 2026-08-28 至 08-29 之間做完三個階段：

| 階段 | 做了什麼 |
|---|---|
| M0 | 立起一份 41 KB 的規範性規格（零 C++） |
| M1 | 命名／版面／交接協定入法；`aos deliver`、程式計數器 `.aos/turn`、批 header；**加一輪 28 條發現的對抗驗證與修補** |
| M2 | `core/loop` 誕生（回合層獨立成第二個核心小專案）、四階段管線、計時搬遷、writeback、退避與停機、control inbox |

規劃到一半的 M3（`status` / `recover` / `check`）**從未動工**；M4（第二顆 CPU）被四項存貨
擋著，也從未動工。

**凍結點**：

- 分支 `roadmap-run`，凍結 commit **`5b74b47`**（tag **`frozen/roadmap-run-2026-08`** 指這裡），
  **未 push**。那個 commit 只把凍結宣告寫進進度日誌；**最後一個含程式碼的 commit 是
  `6ae11e2`**（M2 落地的 merge）。
- 對照 `main` 的 `f2a802b`：**202 個檔、+18,326 行**，其中程式碼（`core/`／`app/`／CMake）
  約 **7,900 行**，其餘是文件與工作流。46 個 commit。

**為什麼凍結**——使用者的原話：

> 「像這樣一改再改，實在浪費 token，不如全部打掉重來，這才是 agent 的正確方法。」

**這不是因為系統做壞了。** 程式碼品質相當高（審查隊的原話：「問題集中在兩個設計判斷上，
不是散落的粗心」）。凍結的理由是**改動成本**：一次「改一行程式碼的行為」的完整代價被流程
放大到要動七到十個檔。那筆帳算在[第 6 篇](06-協作流程的收穫.md)。

## 怎麼查舊分支

打撈包只給結論與指路，**原文都還在**。分支沒被刪，同一個 repo 裡讀得到：

```sh
git show roadmap-run:docs/SPEC.md                 # 41 KB，唯一規範性規格
git show roadmap-run:wf/workflows/ideas/verdicts.md            # 22 KB，裁決總表
git show roadmap-run:wf/workflows/common/gotchas.md            # 15 KB，坑的可查版本
git show roadmap-run:wf/workflows/build-cycle/archive/m1-loop-side/review/report.md
                                                  # 77 KB 審查報告；§6.2.3 是那條併發數字
git ls-tree -r --name-only roadmap-run -- wf      # 看還有什麼
```

**幾份最值得回頭查的**（路徑都在 `roadmap-run` 上）：

- `docs/SPEC.md` — A–G 七區條款，每條附「來源」欄可回溯到當初的討論；末尾是「已知未決」附錄。
- `wf/workflows/build-cycle/archive/m1-loop-side/review/` — 報告 ＋ **58 支腳本**（報告當時寫「57 支」，複測時又搬進併發壓力腳本 `conc.sh`）。
  報告要**挑著讀**：§0 總結、§3 兩張驗證表（含「打了但沒問題的」）、§4 沒覆蓋到的角落、
  §6 修補後複測。
- `wf/workflows/common/code-map/` — 逐檔職責表，**寫的是「為什麼是這個形狀」而不只是
  「這個檔做什麼」**。
- `wf/workflows/digest/2026-08-28/` — 給使用者看的白話版五篇，語感可參考。
- `wf/workflows/build-cycle/m3-roster/` — 規劃完成但從未動工的那一階段（87 KB plan）。

## 這包本身的品管

- 每個結論後面都附「**怎麼知道的**」：哪支腳本、哪個 ctest 案例名、什麼實測數字。
  **沒驗過的一律明說沒驗過**，提案不會被寫成結論。
- 所有引用的檔案路徑、測試案例名、commit hash 都經過核對（`git show` / `git grep` 實查）。
- **核對過程中發現舊素材本身有四處自相矛盾**，各篇已就地標註以哪一份為準。最重要的一處：
  規格與兩份摘要都把併發重複執行率寫成「8.7% → 35%」，而原始報告的表是「同機對照 9.8% →
  37.0%」，35% 這個數字在報告裡不存在。**以報告 §6.2 的表為準。**
