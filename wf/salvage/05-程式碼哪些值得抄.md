# 程式碼哪些值得抄

**這篇是給誰的**：要從零重寫這套系統的人。上一輪（分支 `roadmap-run`，凍結於 `5b74b47`，
tag `frozen/roadmap-run-2026-08`）留下約 7,900 行 C++。**這一包的立場是打撈，不是搬家**
——大部分程式碼該丟掉。但有幾處是**真的被磨過的**：被攻擊腳本打過、被實測逼著改過形狀，
重寫時從零想一遍會很貴。

## 一、handoff 的耐久性鏈：寫 → fsync → rename → fsync 目錄

**`core/inst/src/handoff_fs.cpp`**（7.4 KB，整檔值得讀）。四個零件，形狀是被崩潰狀態機
測試逼出來的：

| 函式 | 為什麼是這個形狀 |
|---|---|
| `fsync_retry(int fd)` | `fsync` 可能被訊號中斷；**重打 `fsync` 是安全的**（fd 沒被回收），而重打 `close` 不是。這個不對稱要記住 |
| `write_file` / `write_file_exclusive` | **在 `close` 之前 `fsync`**，不是之後 |
| `fsync_dir(path, error)` | **每一次 rename 之後都要打一次**。`rename` 只保證目錄項原子替換，不保證目錄項落地 |
| `publish_exclusive(from, to, ...)` | `renameat2(RENAME_NOREPLACE)`，**檔案系統不支援時退階為 `link` ＋ `unlink`**。POSIX `rename()` 靜默覆蓋目的檔——原子，但**不互斥**；要「絕不覆蓋」只有這兩條路 |

**發布順序本身才是重點**（實作在 `core/inst/src/handoff_aggregate.cpp`）：

```
寫批 .temp（fsync）→ 寫 header .temp（fsync）→ rename header ←── 提交點
 → fsync 目錄 → rename 批 → fsync 目錄 → 刪投遞 → fsync 目錄 → 標記 header swept
```

**選 header 當提交點**（而不是批本身）是這個設計最關鍵的一步：崩潰之後靠 header 認得出
「這一批我已經承諾過了」，才能決定要 roll forward 還是清掉重來。

> **怎麼知道的**：這八步的實際 syscall 序列被一支自寫的 LD_PRELOAD 攔截器
> （`wf/workflows/build-cycle/archive/m1-loop-side/review/scripts/trace.c`）逐一比對過，
> **一字不差**；崩潰狀態機的五個狀態手工佈置全部通過。
> **但耐久性本身沒有被真的驗證過**：測試建在 tmpfs，**tmpfs 的 fsync 是 no-op**，真正的
> 斷電從頭到尾沒測。抄這一段可以，但別以為它被證明了。

一併抄走的坑：`publish_exclusive` 的退階路徑**部分成功時要回成功**——`link` 成功、收尾
`unlink` 失敗時目的檔已經在收件匣裡了，回報失敗會讓生產者重投、真的多出一份。把殘留錯誤
放進側通道，不要放進回傳值。

## 二、排他發布 ＋ 發布前的來源查核

**`core/inst/src/handoff_aggregate.cpp` 的 `deliveries_still_present()`**（檔內約第 232 行，
呼叫點第 287 行，註解標成「提交點之前的最後一道門」）。

一句話：**發布之前再 `lstat` 一次本輪收下的每一份投遞，少了任何一份就乾淨放棄**——不發布、
不清投遞、不寫 header。

為什麼需要它（**整包打撈裡投報率最高的一條**）：排他發布**只在勝出者那份批還沒被取走時
有效**。取件把 `inst.json` 換成 `inst.json.runi`，槽位就空了，慢半拍的彙整者照樣 rename
得進去——它手上那份批是稍早讀到的投遞，發布出去就是**同一批執行第二次**。來源查核涵蓋得到
這條路，因為協定順序固定：**清投遞必定在標 `swept` 之前**。

實測：同一支併發壓力腳本、200 回合、2–4 支併發，重複執行率從 **37–51%** 回到 **0–1%**，
批次遺失九次跑動全是 0。**這道門不是互斥**，只是把窗口從「勝出者整批跑完」縮到幾個
syscall；剩下的 0–1% 是誠實的殘留。**條款照實寫、沒有假裝歸零**——這個誠實本身也值得抄。

> **怎麼知道的**：`.../m1-loop-side/review/report.md` §6.2.3；腳本 `review/scripts/conc.sh`。
> 完整來龍去脈在[踩過的坑](02-踩過的坑.md)第一節。

## 三、exec 的 `setpgid` 雙保險

**`core/inst/src/exec.cpp`**（子側第 162 行、父側第 168–172 行）：`fork` 之後**父子兩側都
呼叫 `setpgid`**，而且父側那一發忽略 `EACCES`。

理由：**誰先被排到不一定**。子行程可能還沒跑到 `setpgid` 就被父行程送了群組訊號；父行程也
可能在子行程已經 `execve` 之後才呼叫（此時回 `EACCES`，代表子行程已經自己設好了）。兩側各
打一次，之後的群組訊號才保證打得到正確的群組。

**為什麼重要**：逾時要殺的是**整個行程群組**，不是直接子行程——不然孫行程會活下來。逾時的
四個測試案裡有一案就是「**忽略 SIGTERM 的孫行程也要被 SIGKILL 殺掉**」。

同一個檔還有兩條鐵律值得抄走：

- **`fork` 之後、`execve` 之前只能呼叫 async-signal-safe 的操作**——不能有 C++ 記憶體配置、
  不能 `setenv`、不能字串操作。所有準備（環境變數合併、PATH 解析、`argv`/`envp` 實體化）
  都要在 `fork` **之前**做完。這條逼出了 `core/inst/src/spawn_prep.cpp` 這個檔的存在。
- **在行程層級改訊號處置是有害的**：被忽略的訊號處置**會跨 `execve` 繼承**給子行程，等於
  偷偷改掉使用者程式的行為。（正確做法見第五節的 `SIGXFSZ`。）

## 四、C ABI 的凍結紀律

**`core/inst/include/aos/inst.h`**（C99）＋ **`core/inst/src/capi_handoff.cpp` 開頭的一串
`static_assert`**。三條規則，被真的執行了：

1. **列舉值一經釋出就凍結**：只能在**尾端追加**，不能重排、不能刪除、不能改值。
2. **C++ 列舉與 C 列舉的對齊靠 `static_assert`**，不靠人記。改任何一邊，另一邊編不過。
3. **C-only 的延伸值（配置失敗、緩衝區太小這類）刻意不進 `static_assert`**——它們在 C++ 側
   沒有對應，硬要鏡射會讓兩邊互相綁死。

審查驗過：一整個階段的 `git diff -- inst.h` **全部是尾端追加，無插值、無重排、無改值**。

**代價要一起抄走**：ABI 凍結會反過來限制設計。有一次需要表達「這份 header 已經屬於另一批」
這個新狀態，因為列舉加不動了，只好**借語意最接近的既有值**。那不是好設計，是被 ABI 逼的
——**所以列舉值一開始就要留餘裕，或者乾脆不要那麼早釋出 C ABI**。下一階段的規劃就明確裁了
「這次不開新的 C ABI」，理由是：結構第一次定形時最可能改，而且**對外唯讀介面有更好的形式
——一個帶 schema 版本的 `--json` 輸出**，改起來比 ABI 便宜得多。

## 五、幾個小而好的實作決定

每個都只有幾十行，但都是撞到問題之後才長成這樣的。

**`core/loop/src/backoff.hpp` — 測試接縫做成 header-only 的純計算。** 原本的計畫是「開一個
只給測試用的睡眠 hook」。實際做的是把整個退避邏輯（三種圈的窮舉分流、失敗計數）做成純函式，
測試直接 `#include` 就能對「第 n 次要睡多久」下確定性斷言。三個好處：**斷言強度一樣**、
**沒有全域可變狀態**、**沒有為了測試而匯出的符號**（那個 hook 得標匯出巨集才連得到，等於把
測試接縫放進 ABI）。兩個細節：退避上限取 `max(間隔, 60000)` 而不是 `60000`——才不會讓
`--loop 300000` 的人被 60 秒**縮短**間隔；倍增寫成 `current > cap/2 ? cap : current*2`
——在觸頂前就夾住，`uint64` 不會 wrap。

**`core/loop/src/turn.cpp` — 用 RAII 在範圍內忽略 `SIGXFSZ`。** `ulimit -f` 觸頂時 `write`
會先送 `SIGXFSZ`，預設處置是**砍死行程**（實測退出碼 153）——錯誤路徑一行都跑不到，暫存檔
的殘骸就這樣留下。範圍內忽略它，`write` 就會誠實回 `EFBIG`。**為什麼是 scoped 而不是行程
層級**：被忽略的訊號處置會跨 `execve` 繼承給使用者的程式。抄的時候連註解一起抄。

**另外兩個一句話帶過**：`core/loop/src/control.cpp` 的控制記錄用**定點解析**、不走指令的
格式層（`op` 過不了指令的 schema，而讓格式層長出第二套 schema 就違反了「最內層不長新機制」）；
`core/inst/src/handoff_dedup.cpp` 的 roll-forward 要**逐位元比對**本輪重算的內容、
**錨靠內容認身分不靠檔名**——原本只檢查「解析得出非空批次」，結果一份毫無關係的殘骸被扶正
並執行了。

## 六、跨小專案相依一律 `PUBLIC_DEPS`（實測結論，別靠直覺）

**`core/loop/CMakeLists.txt`**（第一個走這條路的），理由記在 `wf/workflows/add-subproject.md`。

> **相依到另一個小專案一律走 `PUBLIC_DEPS`，即使只有 `.cpp` 用到。**

原因是實測出來的，違反 CMake 直覺：合併版的單一 `libaos.so` 只濾掉 public 清單裡的
`aos::<小專案>`，**private 那份會原樣灌進去**，於是合併版長出 `NEEDED libaos_inst.so.0`
——**單檔部署破功，同一份符號出現在兩顆 DSO 裡**。驗證方式很便宜，抄走：
`readelf -d build/merged/lib/libaos.so | grep NEEDED`，**不得出現任何 `libaos_*.so`**。

**還有一個很好用的機械證明**：分層是不是真的單向，不要用 grep 證，用**編譯器與 CMake** 證。
實際做過的兩道——在下層的 `.cpp` 插一行 `#include <aos/loop.hpp>` 會得到
`fatal error: No such file or directory`；在下層的 `CMakeLists.txt` 加 `PUBLIC_DEPS aos::loop`
會讓 CMake 以 `strongly connected component (cycle)` 直接 configure 失敗。**兩道都比 grep 強，
因為它們不會被文件與註解誤傷**——真的發生過：grep 版的驗收條件會命中文件裡「要逾時請改用
`aos::loop::execute_slot()`」那一行，而那正是規格明文要求寫的。

## 七、測試的兩個手法（比程式碼本身更值得抄）

**`core/loop/tests/test_handoff_regression.cpp`**（19 KB，由四支攻擊腳本改寫而成）：
**自帶 `alarm` 看門狗**——測「收件匣裡的 FIFO 不會讓一輪停擺」時，如果退回阻塞行為，看門狗
會**砍掉測試行程**，而不是讓 CI 掛死。**任何測「不該永久阻塞」的案子都該長這樣。**
斷言的是退出碼、計數器檔、stderr、以及子行程真的留下的腳印，全程手工佈置檔案系統狀態、
不 shell out。

**`core/loop/tests/test_control.cpp` / `test_writeback.cpp` — 用「讓批次自己動手」取代 sleep。**
要測「控制記錄在回合**中途**進來」「header 在執行期間被別人換掉」「彙整剛寫完時 `result` 還是
`null`」這種時序，靠 `sleep` 一定 flaky。解法是**讓被執行的那一批指令自己在執行期間做那件事**
（批次裡就一行 shell）——**完全確定性**，而且順便證明了控制窗口的相位在哪。
**這個手法之所以可行，是因為這台機器的「指令」就是任意的 shell 命令。** 重寫時如果保留這個
性質，這個測試手法就一起免費拿到。

## 八、**別**帶走的

| 東西 | 為什麼別帶 |
|---|---|
| **`core/llms/`**（LLM 客戶端）與 **`core/tooljson/`**（工具描述格式） | 使用者已判定這兩個小專案是**失敗作**：不符合這套系統的回合制／抽象 CPU 模型，要重做。它們在分支上是**擱置**狀態，不是待修——別移植，也別再往裡面投資 |
| **把所有子命令塞進同一支胖執行檔** | 「同一支執行檔、同一次 build」在**版本一致性**上是對的，在**成本**上是自找的：實測每次 `execve` 要付 0.79–0.877 ms，大半花在映射與重定位三顆 `.so`（其中一顆 32 MB 的 LLM 函式庫**跟交接完全無關**），而 `/bin/sh -c :` 只要 0.437 ms。**這是連結決定、不是架構決定，拆得掉**——但重寫時就該一開始拆對 |
| **`core/inst/src/handoff.cpp` 的取件路徑** | `lstat` → 讀檔 → `rename` 的 check-then-act，**不是鎖**，而且讀在 rename 之前。要互斥就從一開始用 `link()` / `renameat2(RENAME_NOREPLACE)` / `open(O_CREAT\|O_EXCL)` |
| **版面路徑常數** | 分支凍結時**至少三份抄本**（兩個小專案的 CLI 各一份、回合層的 `layout.hpp` 一份）。內部標頭跨不過小專案邊界，這是分層的代價——但那代表**版面一改要改三處**。重寫時要嘛讓版面知識有唯一的家、要嘛接受抄本並寫一支驗證器 |
| **`.runi` 的整套語意** | 它同時扮演鎖、崩潰現場、與「有一回合沒跑完」的證據。三個角色綁在一個零長度檔上，結果是崩潰之後人手上**只有一個 `.runi`、沒有它為什麼死的資訊**。這不是實作問題，是設計問題 |

## 九、怎麼查原始碼

```sh

```

**先讀 code map 再讀程式碼**：`wf/workflows/common/code-map/inst.md` 與
`wf/workflows/common/code-map/loop.md` 是逐檔的職責表，而且**每一份都寫了「為什麼是這個
形狀」而不只是「這個檔做什麼」**——那份 loop 的 code map 比它描述的多數程式碼更有打撈價值。
