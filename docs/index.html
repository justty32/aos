AOS

Akatosh Operating System

過度遵從UNIX哲學的奇異AI Agent框架。

一套新的軟體開發範式。

每個 agent 是一個 Linux 行程；它的狀態、設定、信件全是資料夾裡的檔案。

精簡，小巧。

核心程式庫僅7.5k行。◐ 部分

三支核心程式 aos-exec、aos-loop、aos-daemon 的 C++ 原始碼：11-14 量 7,487 行，11-16 量 7,687 行（含註解與空行）；全部 C／C++ 16,750 行。

使用時僅需記住少許cli指令。◐ 部分

總入口是 aos-agent；給人打的 aos-* 指令一共 20 個（不算底層程式）。

缺點

大多功能需要自己做，或是另外找。不過aos本來就鼓勵自己發展適合自己的系統。

高度可攜，可理解。

全部都是檔案，停止核心行程後，可以直接打包成.zip帶著走，損失接近沒有且高度可控。◐ 部分

實測過：同一台機器停下、整個資料夾複製、在新位置起來接著答。還沒驗：跨機器、zip 來回。搬的當下正在跑的模型請求，可能要重花一次。

大多檔案都是.json，不管是人看，或是配合AI，都容易掌握狀況進行除錯。◐ 部分

設定大多是 JSON、對話紀錄是 JSONL；沒量過比例。

缺點

效能上會有無法忽視的損失。◐ 部分

每一輪多起幾個子行程，比較慢；還沒量化。

不過aos的核心概念之一就是LLM的呼叫才是核心瓶頸，這點檔案IO與其相比就是可以容許的，並且相比運行速度，可用性才是aos追求的。除此之外aos也鼓勵混合多種技術棧，自行權衡哪些東西要放在檔案系統。

大量利用Linux介面

無需另外學習一套，並且可以與現有的一整套Linux技術棧相容。◐ 部分

行程、訊號、檔案、權限都是 Linux 原生的；aos 自己的指令與慣例還是要學。

缺點

脫離不了Linux。◆ 已實作

只有 Linux 實作（WSL2 可以）。

允許在僅有少數endpoint的情況下，同時運行千萬個agent。

endpoint：模型的 API 入口。kernel：所有模型呼叫都先經過的排隊處。

相比市面上現有的agent框架來說，aos agent確實少了些靈活性與即時性。但這是aos為了可用性而做的取捨。

不過aos也在Linux介面的基礎上，為常見的coding agent如claude/codex提供了接口，可以將其作為aos agent來使用，後續也會支援更多。◐ 部分

現況

aos 還是原型：檔案格式和指令還會變。只支援 Linux（WSL2 可以）。一棵樹住一台機器；樹和樹之間現在還不會互相連線。

agent 會用你的帳號執行程式：你的帳號碰得到的檔案，它都碰得到。請在拋棄式帳號、虛擬機或容器裡試；換一個資料夾並不能隔離。沙箱是實驗功能。

實測環境：只在一台 Manjaro 機器上照文件一步步跑過；Python 3.11 與 3.14 都通；建置走 vcpkg。其他發行版、不用 vcpkg 的建置還沒驗。
